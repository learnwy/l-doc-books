上下文感知的代码生成

核心概念

上下文感知是区分"AI 补全片段"和"AI 理解项目后生成"的分水岭。一个没有项目上下文的模型，生成的代码可能语法正确但与项目风格冲突、引入不存在的依赖、或者重复实现已有的工具函数。上下文感知的代码生成要求 Agent 在写下每一行代码之前，已经建立了对项目架构、编码规范、类型系统和依赖关系的全局理解。

代码库索引技术
代码库索引是上下文感知的基础设施。它的目标是将整个代码库的信息组织成 Agent 可以快速查询的结构，使 Agent 在需要特定上下文时能够精确获取，而不是将整个代码库塞入上下文窗口。


文本嵌入索引是最通用的方案。将代码文件按函数/类粒度分割为片段（chunk），使用嵌入模型（如 OpenAI text-embedding-3-small、Voyage Code）将每个片段转化为向量，存储在向量数据库中。当 Agent 需要查找相关代码时，用自然语言查询检索最相似的片段。


interface CodebaseIndex {
  chunks: CodeChunk[];
  embeddings: Float32Array[];
  metadata: ChunkMetadata[];

  search(query: string, topK: number): Promise<SearchResult[]>;
  reindex(changedFiles: string[]): Promise<void>;
}

interface CodeChunk {
  filePath: string;
  startLine: number;
  endLine: number;
  content: string;
  symbolName: string | null;
  symbolType: 'function' | 'class' | 'interface' | 'module' | 'other';
}

interface SearchResult {
  chunk: CodeChunk;
  score: number;
  context: string;
}
AST 索引提供比文本嵌入更精确的结构化查询能力。通过解析代码的抽象语法树，Agent 可以查询"所有实现了 Handler 接口的类"、"调用了 database.query 的函数"等结构化问题。AST 索引的构建依赖语言特定的解析器（如 TypeScript 的 ts-morph、Python 的 ast 模块）。


**符号图（Symbol Graph）**将代码库中的符号（函数、类、变量、类型）及其关系（调用、继承、导入）建模为图结构。符号图支持回答"这个函数被谁调用"、"这个类型在哪里被使用"等关系查询，是上下文检索中最有价值的信息源之一。

检索增强代码生成
检索增强生成（RAG）技术在代码生成领域有着特殊的应用形态。与自然语言 RAG 不同，代码 RAG 需要处理结构化更强、精确性要求更高的内容。


代码 RAG 的检索策略通常采用多路检索：


语义检索：用嵌入模型查找与当前任务语义相关的代码片段。适合"查找类似功能的实现"这类需求。


符号检索：基于类型系统和符号图查找精确的接口定义、函数签名和类型别名。适合"查找 UserService 的定义和方法列表"这类需求。


路径检索：基于文件路径模式匹配相关文件。适合"查找所有路由定义文件"这类需求。


依赖检索：基于 import/require 关系追踪依赖链。适合"查找这个模块的所有依赖方"这类需求。


interface MultiPathRetriever {
  semantic: SemanticSearcher
  symbol: SymbolSearcher
  path: PathSearcher
  dependency: DependencyTracer

  async retrieve(query: RetrievalQuery): Promise<RetrievalResult> {
    const results = await Promise.all([
      this.semantic.search(query.text, query.topK),
      this.symbol.search(query.symbols),
      this.path.search(query.pathPatterns),
      this.dependency.trace(query.entryPoints),
    ])

    return this.merge(results)
  }
}

interface RetrievalQuery {
  text: string
  symbols: string[]
  pathPatterns: string[]
  entryPoints: string[]
  topK: number
}
检索结果的排序与去重也至关重要。多路检索可能返回重叠的结果，需要通过去重和重新排序来最大化信息密度。常用的策略包括：基于文件路径去重、基于内容哈希去重、基于 Reciprocal Rank Fusion（RRF）的多路结果合并。


上下文窗口管理
即使有了强大的检索系统，上下文窗口的有限容量仍然是核心约束。一个 200K token 的窗口看似很大，但在实际使用中，系统 Prompt、工具定义、对话历史和已检索内容会快速消耗可用空间。上下文窗口管理的目标是在给定空间内最大化信息价值。


信息价值评估为每一段上下文内容分配一个"价值/体积"比，优先放入价值密度最高的内容。类型定义文件（如 .d.ts）通常价值密度最高——它们以极少的 token 提供了精确的 API 契约。相反，完整的实现文件价值密度较低——大量的逻辑细节中只有小部分与当前任务相关。


渐进式上下文加载分为三个阶段：


    

  1. 骨架阶段：加载项目结构、主要接口定义、当前文件的 import 链。这个阶段提供全局视野。
    2. 

  2. 焦点阶段：加载与当前任务直接相关的文件内容和依赖项。这个阶段提供任务上下文。
    3. 

  3. 细节阶段：按需加载被引用但未展开的具体实现。仅在 Agent 推理时发现信息不足时触发。
    4. 



interface ContextBudget {
  totalTokens: number;
  allocated: {
    system: number;
    taskContext: number;
    codeContext: number;
    conversationHistory: number;
    reserve: number;
  };
}

function optimizeContext(budget: ContextBudget, candidates: ContextCandidate[]): ContextCandidate[] {
  const sorted = candidates.sort((a, b) => b.valueDensity - a.valueDensity);
  const selected: ContextCandidate[] = [];
  let usedTokens = 0;

  for (const candidate of sorted) {
    if (usedTokens + candidate.tokenCount <= budget.allocated.codeContext) {
      selected.push(candidate);
      usedTokens += candidate.tokenCount;
    }
  }

  return selected;
}

跨文件依赖感知
在真实项目中，一个文件的代码变更往往会影响其他文件。跨文件依赖感知让 Agent 在修改一个文件时，自动识别并处理受影响的其他文件。


Import 链分析是最基础的跨文件感知。当 Agent 修改了一个模块的导出接口时，需要自动识别所有导入该接口的文件，并评估是否需要同步修改。


类型传播分析更加深入。当修改了一个 TypeScript 接口的字段时，所有使用该接口作为参数或返回值的函数都可能需要更新。TypeScript 编译器的类型检查错误会自动暴露这些传播链。


interface DependencyAnalyzer {
  getImporters(filePath: string): Promise<string[]>;
  getExports(filePath: string): Promise<ExportInfo[]>;
  getTypeUsages(typeName: string): Promise<TypeUsage[]>;
  getCallGraph(functionName: string): Promise<CallGraphNode>;

  analyzeImpact(change: FileChange): Promise<ImpactReport>;
}

interface ImpactReport {
  directlyAffected: string[];
  transitivelyAffected: string[];
  riskLevel: 'low' | 'medium' | 'high';
  suggestedActions: SuggestedAction[];
}
变更影响半径估算帮助 Agent 决定需要检查多大范围的文件。一个工具函数的签名变更可能影响数十个调用者，而一个组件内部状态的修改通常只影响组件本身。

风格一致性维护
代码风格一致性是上下文感知的"软约束"。它不像类型检查那样有明确的对错判断，但对代码可维护性和团队协作至关重要。Agent 生成的代码如果风格与项目不一致，即使功能正确也会被审查者要求修改。


风格学习是指 Agent 通过分析现有代码来推断项目的编码偏好。关键的风格维度包括：


    

  • 命名规范：camelCase vs snake_case，前缀/后缀习惯（如 I 前缀的接口、use 前缀的 Hook）
    • 

  • 导入组织：分组顺序（外部包 → 内部模块 → 相对路径）、是否使用路径别名
    • 

  • 函数风格：箭头函数 vs function 声明、命名导出 vs 默认导出
    • 

  • 错误处理：try-catch vs Result 类型、错误边界模式
    • 

  • 组件模式：FC 箭头函数 vs function 组件、Props 接口命名
    • 



Agent 可以通过分析同目录下的已有文件来学习这些偏好，然后在生成新代码时遵循相同的模式。更高级的方案是将风格规则编码为项目级配置（如 AGENTS.md 中的编码规则），Agent 在系统 Prompt 中读取这些规则。


小结
    

  • 上下文感知是代码生成质量的决定性因素，从"补全片段"到"理解项目后生成"的跃迁依赖于全面的上下文构建。
    • 

  • 代码库索引（嵌入向量、AST 索引、符号图）是上下文感知的基础设施，不同索引类型适合不同查询需求。
    • 

  • 多路检索（语义 + 符号 + 路径 + 依赖）结合 RRF 排序，实现精准的上下文获取。
    • 

  • 上下文窗口管理以"价值密度"为核心指标，渐进式加载从骨架到细节的三阶段策略是主流方案。
    • 

  • 跨文件依赖感知通过 Import 链和类型传播分析，自动识别变更影响半径。
    • 

  • 风格一致性维护通过分析已有代码或读取项目级规则，确保生成代码与项目风格统一。
    •
