AI 编码 Agent 的核心架构

核心概念

AI 编码 Agent 是一种能够自主感知代码库、规划编码方案、执行代码变更并验证结果的智能系统。与简单的代码生成模型不同，编码 Agent 具备完整的"感知—规划—行动—验证"闭环能力，其架构设计决定了 Agent 的任务处理上限和可靠性边界。

ReAct 循环：Agent 的执行引擎
ReAct（Reasoning + Acting）是当前编码 Agent 最核心的执行范式。它将 LLM 的推理能力与外部工具调用能力结合，形成"思考→行动→观察→再思考"的迭代循环。


一个典型的 ReAct 循环如下：Agent 收到用户请求后，首先进行推理（Reasoning），分析需要做什么、应该先做什么；然后执行一个行动（Acting），比如读取文件或运行命令；接着观察行动结果（Observation）；最后基于观察结果进行下一轮推理，决定接下来的步骤。


interface ReActStep {
  thought: string;
  action: ToolCall;
  observation: string;
}

interface ToolCall {
  name: string;
  parameters: Record<string, unknown>;
}

interface AgentLoop {
  maxIterations: number;
  steps: ReActStep[];
  finalAnswer: string | null;

  run(task: string): Promise<AgentResult>;
}
ReAct 循环的关键设计决策包括：


最大迭代次数：防止 Agent 陷入无限循环。典型值为 20-50 步，复杂任务可能需要 100+ 步。Claude Code 在处理大型重构时经常超过 50 步。


工具选择策略：Agent 在每一步需要从可用工具集中选择最合适的工具。优秀的编码 Agent 会根据当前状态动态调整工具偏好——在理解阶段偏向搜索和阅读工具，在实现阶段偏向编辑和执行工具。


错误恢复：当工具调用返回错误时，Agent 需要在推理阶段分析错误原因并调整策略。这种自纠错能力是区分 L3 和 L4 Agent 的关键指标。

工具调用架构
工具系统是编码 Agent 与物理世界交互的桥梁。一个完整的工具架构包括工具定义、调用协议、结果解析和权限控制四个层面。


工具定义遵循标准化的 Schema 描述。每个工具需要声明名称、功能描述、参数列表（含类型和说明）以及返回值格式。LLM 基于这些描述决定何时使用哪个工具。


interface ToolDefinition {
  name: string;
  description: string;
  parameters: {
    type: 'object';
    properties: Record<
      string,
      {
        type: string;
        description: string;
        required?: boolean;
      }
    >;
  };
  returns: { type: string; description: string };
}

const readFileTool: ToolDefinition = {
  name: 'read_file',
  description: 'Read the contents of a file at the given path',
  parameters: {
    type: 'object',
    properties: {
      path: { type: 'string', description: 'Absolute file path', required: true },
      offset: { type: 'number', description: 'Line number to start reading from' },
      limit: { type: 'number', description: 'Maximum number of lines to read' },
    },
  },
  returns: { type: 'string', description: 'File contents with line numbers' },
};
典型的编码 Agent 工具集包括以下几类：


文件操作工具：read_file、write_file、list_directory、search_files（grep）、glob。这是最基础的工具集，让 Agent 能够浏览和修改代码库。


代码搜索工具：search_codebase（语义搜索）、find_references、find_definition。超越简单的文本搜索，利用嵌入模型或 LSP 协议提供代码级的语义理解。


执行工具：execute_command（终端命令）、run_tests、build。让 Agent 能够运行代码、执行测试和构建项目。


版本控制工具：git_diff、git_log、git_commit。让 Agent 能够与 Git 交互，理解变更历史和管理代码提交。


权限控制是工具架构中至关重要的安全层。不同信任等级的 Agent 应该拥有不同的工具权限：

上下文管理策略
上下文窗口是编码 Agent 最稀缺的资源。一个中型项目可能包含数千个文件和数百万行代码，而即使 200K token 的上下文窗口也只能容纳约 5000 行代码。如何在有限窗口内放入最相关的信息，直接决定了代码生成的质量。


分层上下文策略是业界的主流方案。将上下文分为三层：


系统层上下文（固定）：Agent 的系统 Prompt、工具定义、项目级规则（如 AGENTS.md）。这部分通常占用 5-15% 的窗口空间。


任务层上下文（半固定）：当前任务描述、已完成的步骤摘要、关键决策记录。随任务推进逐步增长，需要定期压缩。


工作层上下文（动态）：当前正在查看的文件内容、工具调用返回结果、错误信息。这是最大的上下文消费者，需要精细管理。


interface ContextManager {
  systemContext: string;
  taskSummary: string;
  workingContext: ContextEntry[];
  maxTokens: number;

  addEntry(entry: ContextEntry): void;
  evict(): void;
  compress(): void;
  getTokenCount(): number;
}

interface ContextEntry {
  source: 'file' | 'command' | 'search' | 'user';
  content: string;
  relevanceScore: number;
  timestamp: number;
}
上下文淘汰策略决定了当窗口空间不足时，哪些信息应该被移除：


LRU（最近最少使用）：移除最早加入且未被后续步骤引用的上下文。简单但可能移除关键的背景信息。


相关性衰减：为每个上下文条目维护一个相关性分数，随时间衰减，新的引用会提升分数。优先移除低分条目。


摘要压缩：不直接移除旧上下文，而是用 LLM 将其压缩为简短摘要。保留关键信息但减少 token 占用。Claude Code 使用的"compact"机制就属于这种策略。

记忆系统与持久化
编码 Agent 的记忆系统解决了一个根本问题：如何在有限的上下文窗口内利用无限的知识。记忆分为短期记忆（当前上下文窗口内容）和长期记忆（持久化存储的知识）。


短期记忆即当前对话的上下文窗口。它的容量受限于模型的最大 token 数，所有的推理和决策都基于短期记忆中的信息。上文讨论的上下文管理策略本质上就是短期记忆的管理。


长期记忆通过外部存储实现，典型方案包括：


文件系统记忆：将关键信息写入项目中的特定文件（如 .agent-memory/），Agent 在后续会话中读取。Claude Code 的 CLAUDE.md 机制就是一种项目级长期记忆。


向量数据库记忆：将代码片段、决策记录、错误修复经验等编码为向量，存储在向量数据库中。Agent 在需要时通过语义检索获取相关记忆。


结构化知识图谱：构建代码库的依赖图、模块关系图、API 调用图等结构化表示，Agent 通过图查询获取精确的结构信息。


interface MemorySystem {
  shortTerm: ContextWindow;
  longTerm: {
    fileMemory: FileBasedMemory;
    vectorMemory: VectorStore;
    knowledgeGraph: CodeGraph;
  };

  recall(query: string, topK: number): Promise<MemoryEntry[]>;
  store(entry: MemoryEntry): Promise<void>;
  forget(filter: MemoryFilter): Promise<void>;
}

interface CodeGraph {
  modules: Map<string, ModuleNode>;
  dependencies: Edge[];
  callGraph: Edge[];
  typeHierarchy: Edge[];

  query(pattern: GraphPattern): QueryResult[];
}
多模型协作架构
在高级编码 Agent 中，单一模型往往无法同时满足推理深度、响应速度和成本效率的三重要求。多模型协作架构通过为不同子任务分配最合适的模型来解决这一矛盾。


路由模型：一个轻量级模型（如 Claude 3.5 Haiku）负责分析任务复杂度，将简单任务路由给快速模型，复杂任务路由给强大模型。


规划模型：一个推理能力强的模型（如 Claude 3.5 Sonnet with extended thinking）负责任务分解和方案设计。规划阶段对推理深度要求高，但调用频率低。


执行模型：一个平衡速度与质量的模型负责具体的代码生成和编辑。执行阶段调用频率高，需要在质量和延迟之间取得平衡。


验证模型：一个专注于代码审查的模型负责检查生成代码的正确性和风格一致性。可以使用与执行模型不同的模型以引入"第二视角"。

这种架构的核心优势在于成本优化：规划阶段使用最强模型确保方向正确，执行阶段使用性价比最高的模型控制成本，验证阶段使用专精模型保证质量。一个典型的编码任务中，规划消耗的 token 仅占总量的 5-10%，但对最终结果的影响却是决定性的。


小结
    

  • 编码 Agent 的核心架构由感知、规划、行动、验证四层组成，形成完整的自主编码闭环。
    • 

  • ReAct 循环是 Agent 的执行引擎，通过"思考→行动→观察→再思考"的迭代实现复杂任务处理。
    • 

  • 工具调用系统是 Agent 与代码库和运行时环境交互的桥梁，权限控制是安全基座。
    • 

  • 上下文管理是编码 Agent 最核心的工程挑战，分层策略和摘要压缩是主流解决方案。
    • 

  • 记忆系统通过文件记忆、向量存储和知识图谱扩展 Agent 的知识边界，突破上下文窗口限制。
    • 

  • 多模型协作架构通过为不同子任务分配最合适的模型，实现推理深度、响应速度和成本效率的平衡。
    •
