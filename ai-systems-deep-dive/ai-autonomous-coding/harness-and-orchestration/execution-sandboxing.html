执行沙箱与安全隔离

核心概念

执行沙箱是自主编码系统中隔离 AI 生成代码运行环境的安全层。当编码 Agent 拥有修改文件、执行 Shell 命令、安装依赖的能力时，一个未经约束的 Agent 可能删除关键文件、引入恶意依赖或泄露敏感信息。沙箱的目标是让 Agent 在一个"可破坏但不影响真实环境"的空间中自由探索，同时对资源消耗和行为边界施加严格约束。

容器化沙箱架构
容器是编码 Agent 最常用的沙箱方案。每个 Agent 任务在一个独立的容器中运行，容器镜像预装了项目依赖和开发工具链，确保环境一致性。


Docker 沙箱的核心配置要素：


sandbox:
  runtime: docker
  image: 'coding-agent-sandbox:node20-slim'

  filesystem:
    readonly_mounts:
      - host: '/repo/snapshot'
        container: '/workspace'
        type: 'overlay'
    writable_layers:
      - '/workspace/src'
      - '/workspace/tests'
      - '/tmp'
    blocked_paths:
      - '/workspace/.env'
      - '/workspace/.git/config'
      - '/workspace/secrets/'

  network:
    mode: 'restricted'
    allow:
      - 'registry.npmjs.org:443'
      - 'github.com:443'
    deny_all_other: true
    dns: 'cluster-resolver'

  resources:
    cpu: '2.0'
    memory: '4Gi'
    disk: '10Gi'
    timeout: '30m'
    max_processes: 100
    max_open_files: 1024
OverlayFS 是容器沙箱中文件系统隔离的关键技术——它将仓库快照作为只读底层，Agent 的所有写入操作发生在上层。这意味着 Agent 可以自由修改文件而不影响原始仓库，任务完成后只需提取上层的 diff 即可得到变更集。


interface SandboxManager {
  create(config: SandboxConfig): Promise<Sandbox>;
  destroy(sandboxId: string): Promise<void>;
  exec(sandboxId: string, command: string): Promise<ExecResult>;
  copyOut(sandboxId: string, path: string): Promise<Buffer>;
  getDiff(sandboxId: string): Promise<FileDiff[]>;
}

interface Sandbox {
  id: string;
  status: 'creating' | 'running' | 'stopped' | 'destroyed';
  createdAt: Date;
  resourceUsage: ResourceUsage;
}

interface ExecResult {
  exitCode: number;
  stdout: string;
  stderr: string;
  duration: number;
  resourceSnapshot: ResourceUsage;
}
对于安全要求更高的场景（如金融、医疗行业），Firecracker microVM 提供了更强的隔离——每个沙箱运行在独立的轻量级虚拟机中，拥有独立的内核。即使 Agent 生成的代码利用了内核漏洞，也无法逃逸到宿主机。Firecracker 的启动时间仅 125ms，使其在安全与性能之间取得了出色的平衡。


文件系统与权限控制
文件系统隔离不仅仅是"把代码放在容器里"——它需要精细的读写权限控制，确保 Agent 只能访问它需要的文件，不能触碰敏感配置。


权限模型分为三个层级：


    

  1. 目录级白名单：Agent 只能在指定目录中写入。典型配置是允许写入 src/、tests/、docs/，禁止写入 .github/、配置根目录。
    

    2. 

  2. 文件模式保护：某些文件即使在可写目录中也需要保护。package-lock.json、.eslintrc 等配置文件通常标记为只读，Agent 修改这些文件需要显式授权。
    

    3. 

  3. 敏感内容过滤：沙箱在挂载仓库快照前，自动将 .env、密钥文件、证书替换为占位符。Agent 看到的是脱敏后的版本，永远无法接触到真实的密钥。
    

    4. 



interface FileSystemPolicy {
  rules: FileRule[];
  sensitivePatterns: string[];
  maxFileSize: number;
  maxTotalSize: number;
}

interface FileRule {
  pattern: string;
  permission: 'read' | 'write' | 'none';
  requireApproval: boolean;
}

const defaultPolicy: FileSystemPolicy = {
  rules: [
    { pattern: 'src/**', permission: 'write', requireApproval: false },
    { pattern: 'tests/**', permission: 'write', requireApproval: false },
    { pattern: '*.lock', permission: 'read', requireApproval: false },
    { pattern: '.env*', permission: 'none', requireApproval: false },
    { pattern: '.github/**', permission: 'read', requireApproval: false },
    { pattern: 'package.json', permission: 'write', requireApproval: true },
  ],
  sensitivePatterns: ['**/*.pem', '**/*.key', '**/.env*', '**/secrets/**', '**/credentials/**'],
  maxFileSize: 1024 * 1024,
  maxTotalSize: 100 * 1024 * 1024,
};
文件系统审计是另一个关键能力——沙箱记录 Agent 的每一次文件操作（读、写、删除、重命名），形成完整的操作时间线。这不仅用于事后审计，还可以在实时检测到异常模式时触发告警（如短时间内大量删除文件）。


网络策略与供应链安全
自主编码 Agent 需要网络访问来安装依赖、查阅文档和调用 API，但不受约束的网络访问会引入严重的安全风险——Agent 可能从恶意源安装带后门的包，或将仓库代码外传到未授权的服务器。


网络隔离策略的核心原则是默认拒绝，显式放行：


network_policy:
  default: deny

  egress_rules:
    - name: 'package-registry'
      destinations: ['registry.npmjs.org', 'pypi.org']
      ports: [443]
      protocol: HTTPS

    - name: 'source-control'
      destinations: ['github.com', 'api.github.com']
      ports: [443]
      protocol: HTTPS

    - name: 'llm-api'
      destinations: ['api.openai.com', 'api.anthropic.com']
      ports: [443]
      protocol: HTTPS

  ingress_rules: []

  dns:
    resolver: 'internal'
    block_external: true

  monitoring:
    log_all_connections: true
    alert_on_blocked: true
    bandwidth_limit: '100Mbps'
供应链攻击是 AI 生成代码面临的独特威胁。LLM 可能生成引用不存在的包名（"幻觉包"），攻击者可以抢注这些包名并植入恶意代码。防御策略包括：

资源限制与超时控制
资源限制是防止 Agent 失控的最后一道防线。一个陷入无限循环的 Agent 可能耗尽所有 CPU 和内存，影响同一宿主机上的其他任务。


interface ResourceLimits {
  cpu: CpuLimit;
  memory: MemoryLimit;
  disk: DiskLimit;
  time: TimeLimit;
  process: ProcessLimit;
}

interface CpuLimit {
  cores: number;
  throttleAt: number;
}

interface MemoryLimit {
  maxBytes: number;
  swapBytes: number;
  oomAction: 'kill' | 'pause-and-alert';
}

interface TimeLimit {
  totalTimeout: number;
  perStepTimeout: number;
  idleTimeout: number;
}

interface ResourceMonitor {
  track(sandboxId: string): ResourceStream;
  alert(sandboxId: string, threshold: ResourceThreshold): void;
  enforce(sandboxId: string, limits: ResourceLimits): void;
}
资源限制的关键实践：


    

  • CPU：分配 2 核上限，使用 cgroups v2 的 CPU 带宽控制。当 CPU 使用率持续超过 90% 达 5 分钟时触发告警。
    • 

  • 内存：硬限制 4GB，OOM 时优先杀死 Agent 进程而非宿主进程。启用内存水位监控，在达到 80% 时预警。
    • 

  • 磁盘：限制 10GB 写入量。使用 quota 机制防止磁盘填满。定期清理临时文件和构建缓存。
    • 

  • 时间：总任务超时 30 分钟，单步操作超时 5 分钟，空闲超时 2 分钟。超时后优雅终止，保留中间产物用于分析。
    • 

  • 进程数：限制最大 100 个进程，防止 fork 炸弹。限制打开的文件描述符数量为 1024。
    • 



Git Worktree 隔离模式
对于不需要执行代码的纯生成场景（如代码审查建议、文档生成），Git Worktree 提供了更轻量的隔离方案。


repo/
├── .git/                    # 共享的 Git 数据库
├── main-worktree/           # 主工作目录（开发者使用）
├── agent-worktree-task-001/ # Agent 任务 1 的工作目录
├── agent-worktree-task-002/ # Agent 任务 2 的工作目录
└── agent-worktree-task-003/ # Agent 任务 3 的工作目录
每个 Worktree 检出独立的分支，Agent 在自己的 Worktree 中操作，不影响其他 Worktree 和主工作目录。任务完成后，Harness 从 Worktree 中提取 diff，创建 PR，然后清理 Worktree。


interface WorktreeManager {
  create(taskId: string, baseBranch: string): Promise<WorktreeContext>;
  getDiff(taskId: string): Promise<FileDiff[]>;
  createPR(taskId: string, title: string, body: string): Promise<PullRequest>;
  cleanup(taskId: string): Promise<void>;
  listActive(): Promise<WorktreeContext[]>;
}

interface WorktreeContext {
  taskId: string;
  path: string;
  branch: string;
  baseBranch: string;
  createdAt: Date;
}
Git Worktree 的优势在于零额外资源开销（不需要容器或 VM），并且与 Git 工作流天然集成。但它不提供执行隔离——Agent 生成的代码在运行时仍需要容器沙箱。因此在实际架构中，Worktree 和容器沙箱通常组合使用：Worktree 管理代码变更的隔离，容器管理执行环境的隔离。

小结
    

  • 执行沙箱是自主编码系统的安全基石，确保 AI 生成的代码在隔离环境中运行，不影响真实生产环境。
    • 

  • 容器沙箱（Docker/Firecracker）是最主流的方案，通过 OverlayFS 实现文件系统隔离，通过 cgroups 实现资源限制。
    • 

  • 文件系统权限采用三级控制模型：目录白名单、文件模式保护、敏感内容过滤，确保 Agent 只能访问必要的文件。
    • 

  • 网络策略遵循默认拒绝原则，仅放行包管理器、源码管理和 LLM API 的 HTTPS 连接。
    • 

  • 供应链安全需要多层防御：依赖白名单、私有镜像源、锁文件校验、幻觉包检测。
    • 

  • 资源限制是最后一道防线：CPU 2 核、内存 4GB、磁盘 10GB、超时 30 分钟，防止失控 Agent 影响系统。
    • 

  • Git Worktree 提供轻量级代码隔离，与容器沙箱组合使用覆盖代码层和执行层的双重隔离需求。
    •
