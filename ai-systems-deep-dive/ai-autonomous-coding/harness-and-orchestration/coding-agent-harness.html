编码 Agent Harness 设计

核心概念

编码 Agent Harness 是包裹在 LLM 编码 Agent 外层的运行时框架，负责管理 Agent 的完整生命周期：从初始化、任务规划、代码执行到验证和结果上报。Harness 与裸 Agent 调用的核心区别在于——它提供了标准化的中间件管道、策略注入、版本管理和可插拔后端，使得编码 Agent 能够像微服务一样被编排、监控和治理。

运行时生命周期
Harness 将编码 Agent 的运行过程抽象为六个标准阶段，每个阶段都有明确的输入输出契约和可注入的中间件钩子。这种设计使得 Agent 行为可预测、可调试、可复现。


六阶段生命周期模型：


    

  1. Init（初始化）：加载配置、解析仓库上下文、建立工作目录、挂载文件系统快照。这个阶段决定了 Agent 看到的"世界"——哪些文件可见、哪些 API 可调用、资源限额是多少。
    

    2. 

  2. Plan（规划）：Agent 分析任务描述，生成执行计划。Harness 在此阶段注入上下文增强信息（如相关代码片段、历史修改记录、架构约束），并对计划进行合规检查——例如禁止修改受保护文件、限制变更文件数量。
    

    3. 

  3. Execute（执行）：Agent 按照计划逐步生成代码。Harness 为每次执行提供隔离的沙箱环境，拦截危险操作（如网络请求、文件系统越权访问），并记录完整的操作序列。
    

    4. 

  4. Verify（验证）：自动运行测试套件、类型检查、Lint 检查和安全扫描。验证层是 Harness 的关键价值——它确保 Agent 输出满足质量门禁，而不仅仅依赖 LLM 的"自信度"。
    

    5. 

  5. Report（上报）：生成结构化的执行报告，包含变更摘要、测试结果、资源消耗和质量评分。上报内容可以直接集成到 PR 评论、Slack 通知或运维看板。
    

    6. 

  6. Archive（归档）：持久化执行上下文、决策轨迹和最终产物。归档数据用于后续的回溯分析、Agent 性能评估和训练数据积累。
    

    7. 



interface HarnessLifecycle<TTask, TResult> {
  init(config: AgentConfig): Promise<RuntimeContext>;
  plan(task: TTask, ctx: RuntimeContext): Promise<ExecutionPlan>;
  execute(plan: ExecutionPlan, ctx: RuntimeContext): Promise<RawOutput>;
  verify(output: RawOutput, ctx: RuntimeContext): Promise<VerifyResult>;
  report(result: VerifyResult, ctx: RuntimeContext): Promise<Report>;
  archive(report: Report, ctx: RuntimeContext): Promise<void>;
}

interface RuntimeContext {
  workDir: string;
  repoSnapshot: FileSystemSnapshot;
  policies: PolicySet;
  middlewares: Middleware[];
  telemetry: TelemetryCollector;
  budget: ResourceBudget;
}
每个阶段之间的转换由状态机驱动，Harness 在每次状态转换时触发中间件管道，实现横切关注点的解耦——日志、鉴权、限流、计量等逻辑不再侵入 Agent 核心代码。


中间件架构
Harness 的中间件采用洋葱模型（Onion Model），与 Express/Koa 的中间件机制类似，但针对 Agent 场景做了扩展。每个中间件可以在请求进入时做预处理、在响应返回时做后处理，且可以决定是否继续传递或提前终止。


中间件按优先级分为四层：


    

  • 安全层：最先执行，负责身份验证、权限校验、敏感文件保护。如果鉴权失败，直接拒绝请求。
    • 

  • 治理层：策略合规检查、资源配额控制、速率限制。防止 Agent 消耗过多 Token 或计算资源。
    • 

  • 增强层：上下文注入、RAG 检索、代码搜索。为 Agent 提供更丰富的背景信息。
    • 

  • 观测层：日志记录、指标采集、追踪上报。最后执行，确保捕获完整的请求-响应链路。
    • 



type NextFn = () => Promise<void>;

interface Middleware {
  name: string;
  priority: number;
  phase: 'security' | 'governance' | 'enrichment' | 'observability';
  handle(ctx: MiddlewareContext, next: NextFn): Promise<void>;
}

interface MiddlewareContext {
  task: AgentTask;
  runtime: RuntimeContext;
  state: Map<string, unknown>;
  abort(reason: string): never;
}

const tokenBudgetMiddleware: Middleware = {
  name: 'token-budget',
  priority: 200,
  phase: 'governance',
  handle: async (ctx, next) => {
    const budget = ctx.runtime.budget;
    if (budget.tokenUsed >= budget.tokenLimit) {
      ctx.abort(`Token budget exhausted: ${budget.tokenUsed}/${budget.tokenLimit}`);
    }
    await next();
    budget.tokenUsed += ctx.state.get('tokensConsumed') as number;
  },
};
中间件的组合是声明式的——通过配置文件指定启用哪些中间件以及它们的参数，而非在代码中硬编码。这使得不同项目、不同团队可以复用同一套 Harness 核心，仅通过中间件配置差异化行为。


策略引擎与配置注入
策略引擎是 Harness 的大脑，它将"允许 Agent 做什么"与"Agent 如何做"分离。策略以声明式配置的形式存在，支持项目级、团队级、全局级的层叠覆盖。


version: '1.0'
agent: 'code-reviewer'
model:
  primary: 'claude-sonnet-4-20250514'
  fallback: 'gpt-4o'
  temperature: 0.2
  max_tokens: 16384

permissions:
  file_write:
    allow: ['src/**', 'tests/**']
    deny: ['*.lock', '.env*', 'dist/**']
  shell_commands:
    allow: ['npm test', 'npm run lint', 'npm run typecheck']
    deny: ['rm -rf', 'curl', 'wget']
  network:
    allow: ['registry.npmjs.org']
    deny: ['*']

limits:
  max_files_modified: 10
  max_lines_per_file: 500
  max_retries: 3
  timeout_minutes: 30
  token_budget: 100000

review:
  require_human_approval:
    when: 'files_modified > 5 OR touches_config'
  auto_merge:
    when: 'all_tests_pass AND files_modified <= 2 AND no_config_changes'
策略的层叠机制遵循最小权限原则：全局策略定义基线，项目策略可以收紧但不能放松，紧急策略可以临时覆盖但带有审计追踪。

策略引擎在 Plan 阶段对执行计划进行预检，在 Execute 阶段对每个操作进行实时拦截。被拦截的操作会生成审计日志，并通知相关审批人。


Agent 注册表与版本管理
在企业环境中，可能同时运行多种编码 Agent（代码生成、代码审查、Bug 修复、测试编写），每种 Agent 又有多个版本。Agent 注册表提供统一的发现、选择和路由机制。


interface AgentRegistryEntry {
  id: string;
  name: string;
  version: string;
  capabilities: string[];
  modelRequirements: ModelRequirements;
  performanceProfile: PerformanceProfile;
  status: 'active' | 'deprecated' | 'experimental';
}

interface AgentRegistry {
  register(entry: AgentRegistryEntry): void;
  resolve(capability: string, constraints?: RouteConstraints): AgentRegistryEntry;
  listVersions(agentId: string): AgentRegistryEntry[];
  deprecate(agentId: string, version: string, reason: string): void;
}

interface RouteConstraints {
  maxLatencyMs?: number;
  maxCostPerCall?: number;
  requiredCapabilities?: string[];
  preferredModel?: string;
}
注册表支持能力路由——调用方不指定具体 Agent，而是描述需要的能力（如"TypeScript 代码生成 + 测试编写"），注册表根据 Agent 的能力声明、性能画像和当前负载自动选择最优实例。


版本管理遵循语义化版本号，Agent 的升级和回滚通过注册表配置完成，无需修改调用方代码。灰度发布策略直接在注册表层面生效——新版本先接收 5% 流量，通过质量门禁后逐步扩大。


可插拔 LLM 后端
Harness 通过抽象的 LLM Provider 接口解耦了 Agent 逻辑与具体模型。切换模型只需修改配置，Agent 代码无需任何变更。


interface LLMProvider {
  id: string;
  chat(params: ChatParams): Promise<ChatResponse>;
  stream(params: ChatParams): AsyncIterable<ChatChunk>;
  embed(texts: string[]): Promise<number[][]>;
  estimateTokens(text: string): number;
}

interface ChatParams {
  model: string;
  messages: Message[];
  temperature?: number;
  maxTokens?: number;
  tools?: ToolDefinition[];
  responseFormat?: ResponseFormat;
}

interface ProviderRouter {
  route(params: ChatParams): LLMProvider;
  addFallback(primary: string, fallback: string): void;
  setLoadBalancer(strategy: 'round-robin' | 'least-latency' | 'cost-first'): void;
}
Provider Router 支持三种路由策略：


    

  • 轮询（Round-Robin）：均匀分配请求到多个后端，适用于负载均衡场景。
    • 

  • 最低延迟（Least-Latency）：实时监测各后端延迟，将请求路由到最快的后端。
    • 

  • 成本优先（Cost-First）：优先使用成本最低的模型，仅在质量不达标时升级到高端模型。
    • 



故障转移是自动的——当主模型返回错误或超时时，Harness 自动切换到备用模型，整个过程对 Agent 透明。这种设计在模型供应商服务中断时提供了关键的业务连续性保障。

小结
    

  • Harness 是编码 Agent 的运行时框架，将裸 Agent 调用升级为可管理、可观测、可治理的工程化系统。
    • 

  • 六阶段生命周期（Init → Plan → Execute → Verify → Report → Archive）为每个 Agent 任务提供标准化的执行流水线。
    • 

  • 中间件管道采用洋葱模型，将安全、治理、增强、观测四类横切关注点与 Agent 核心逻辑解耦。
    • 

  • 策略引擎通过声明式配置实现"允许做什么"与"如何做"的分离，支持四级层叠覆盖和最小权限原则。
    • 

  • Agent 注册表提供能力发现、版本管理和灰度发布机制，使多 Agent 协作像微服务治理一样可控。
    • 

  • 可插拔 LLM 后端通过 Provider 抽象和 Router 策略实现模型切换零代码变更，故障自动转移保障业务连续性。
    •
