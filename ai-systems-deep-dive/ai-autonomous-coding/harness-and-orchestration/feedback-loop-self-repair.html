反馈循环与自修复机制

核心概念

反馈循环是编码 Agent 从"一次性生成"进化为"持续改进"的核心机制。一个没有反馈循环的 Agent 只是一个代码补全器——生成代码后就结束。而具备自修复能力的 Agent 遵循 OODA 循环（Observe → Orient → Decide → Act）：观察执行结果，诊断错误原因，决策修复策略，执行修复操作。这个循环可以多次迭代，直到代码通过所有验证门禁或达到重试上限。

错误分类与诊断引擎
有效的自修复依赖精准的错误分类。不同类型的错误需要完全不同的修复策略——用修复语法错误的方法去修复逻辑错误只会浪费重试次数。


interface ErrorClassifier {
  classify(error: ExecutionError): ErrorClassification;
  extractContext(error: ExecutionError, codebase: CodeContext): DiagnosticContext;
}

interface ErrorClassification {
  category: ErrorCategory;
  severity: 'critical' | 'major' | 'minor';
  confidence: number;
  suggestedStrategy: RepairStrategy;
  relatedFiles: string[];
  rootCauseHypothesis: string;
}

type ErrorCategory = 'syntax' | 'type' | 'import' | 'runtime' | 'test_failure' | 'lint' | 'build' | 'logic';

interface DiagnosticContext {
  errorMessage: string;
  stackTrace: StackFrame[];
  relevantCode: CodeSnippet[];
  typeInfo: TypeContext | null;
  testExpectation: TestExpectation | null;
}
诊断引擎的工作流程是层次化的：


    

  1. 静态分析优先：先运行编译器/类型检查器获取精确的错误位置和类型信息。TypeScript 的 tsc --noEmit 和 ESLint 提供的错误信息是结构化的，可以直接解析。
    

    2. 

  2. 运行时错误追踪：对于运行时错误，解析堆栈追踪（stack trace）定位失败点，向上追溯调用链找到根因。Node.js 的 Error.captureStackTrace 和 source map 支持精确到源码行号。
    

    3. 

  3. 测试失败分析：解析测试框架的输出（如 Vitest/Jest 的 diff），提取期望值与实际值的差异。这些差异直接指向了行为偏差的位置。
    

    4. 

  4. 上下文关联：将错误信息与相关的代码片段、类型定义、测试用例组装成完整的诊断上下文，为修复策略的生成提供充分的信息。
    

    5. 



修复策略与补丁生成
修复策略的选择基于错误分类结果和历史修复经验。Harness 维护一个策略库，为每种错误类型提供分层的修复方案——从最简单的自动修复到需要 LLM 深度理解的复杂重构。


interface RepairStrategy {
  name: string;
  applicableTo: ErrorCategory[];
  priority: number;
  requiresLLM: boolean;
  execute(ctx: RepairContext): Promise<RepairResult>;
}

interface RepairContext {
  error: ErrorClassification;
  diagnostic: DiagnosticContext;
  previousAttempts: RepairAttempt[];
  codebase: CodeContext;
  budget: RepairBudget;
}

interface RepairResult {
  success: boolean;
  patches: FilePatch[];
  explanation: string;
  confidence: number;
  tokenUsed: number;
}

interface RepairBudget {
  maxRetries: number;
  remainingRetries: number;
  maxTokens: number;
  remainingTokens: number;
  timeoutMs: number;
}
修复策略的优先级从高到低：


确定性修复（不需要 LLM）：


    

  • 自动导入缺失的模块（基于依赖图分析）
    • 

  • 应用 ESLint auto-fix 规则
    • 

  • 修正简单的拼写错误（基于编辑距离）
    • 

  • 添加缺失的分号、括号闭合
    • 



模板化修复（LLM 辅助）：


    

  • 类型错误：将错误信息和类型定义发送给 LLM，请求类型对齐修复
    • 

  • 导入路径错误：结合项目文件树，请求 LLM 修正路径
    • 

  • API 用法错误：提供正确的 API 文档，请求 LLM 调整调用方式
    • 



深度修复（完全依赖 LLM）：


    

  • 逻辑错误：需要 LLM 重新理解需求并重构算法
    • 

  • 测试失败：需要 LLM 分析期望行为与实际行为的差异并调整实现
    • 

  • 设计问题：需要 LLM 提出架构级别的改动建议
    • 



const determinisiticRepairs: RepairStrategy[] = [
  {
    name: 'auto-import',
    applicableTo: ['import'],
    priority: 100,
    requiresLLM: false,
    execute: async (ctx) => {
      const missingModule = extractModuleName(ctx.error);
      const resolvedPath = resolveModulePath(missingModule, ctx.codebase);
      if (!resolvedPath)
        return { success: false, patches: [], explanation: 'Module not found', confidence: 0, tokenUsed: 0 };
      const patch = generateImportPatch(resolvedPath, ctx.diagnostic.relatedFiles[0]);
      return {
        success: true,
        patches: [patch],
        explanation: `Added import for ${missingModule}`,
        confidence: 0.99,
        tokenUsed: 0,
      };
    },
  },
  {
    name: 'lint-autofix',
    applicableTo: ['lint'],
    priority: 90,
    requiresLLM: false,
    execute: async (ctx) => {
      const result = await runLintAutofix(ctx.diagnostic.relatedFiles);
      return {
        success: result.fixedCount > 0,
        patches: result.patches,
        explanation: `Fixed ${result.fixedCount} lint issues`,
        confidence: 0.95,
        tokenUsed: 0,
      };
    },
  },

重试策略与退避机制
重试不是简单的"再试一次"——每次重试必须携带前次失败的信息，避免重复犯同样的错误。重试策略的核心是递进式信息累积和指数退避。


重试策略的关键原则：


    

  1. 上下文累积：每次重试都将之前的错误信息和失败的修复尝试作为额外上下文传递给 LLM。这避免了 LLM 重复生成相同的错误代码。
    

    2. 

  2. 策略升级：第一次重试使用最轻量的修复策略，失败后逐步升级到更重的策略。例如：auto-fix → 模板修复 → LLM 深度修复 → 人工升级。
    

    3. 

  3. 指数退避：连续失败时增加重试间隔，避免短时间内消耗过多 Token。间隔从 1 秒开始，每次翻倍，最大 60 秒。
    

    4. 

  4. 预算控制：每个任务有固定的重试预算（次数和 Token 上限）。当预算耗尽时，任务标记为需要人工介入，而非无限重试。
    

    5. 



interface RetryPolicy {
  maxAttempts: number;
  backoff: BackoffConfig;
  escalation: EscalationConfig;
  budgetPerAttempt: AttemptBudget;
}

interface BackoffConfig {
  initialDelayMs: number;
  maxDelayMs: number;
  multiplier: number;
  jitter: boolean;
}

interface EscalationConfig {
  thresholds: EscalationThreshold[];
  humanEscalation: HumanEscalationConfig;
}

interface EscalationThreshold {
  afterAttempts: number;
  action: 'upgrade_strategy' | 'switch_model' | 'escalate_human';
  description: string;
}

堆栈追踪解读与根因分析
堆栈追踪是运行时错误诊断的核心数据。编码 Agent 需要从嘈杂的堆栈信息中提取有用的根因线索，区分"项目代码"和"框架/库代码"，定位真正的错误源头。


interface StackTraceAnalyzer {
  parse(rawTrace: string): ParsedStackTrace;
  findRootCause(trace: ParsedStackTrace, projectRoot: string): RootCause;
  generateFixHint(rootCause: RootCause, codeContext: CodeContext): FixHint;
}

interface ParsedStackTrace {
  errorType: string;
  message: string;
  frames: StackFrame[];
  cause?: ParsedStackTrace;
}

interface StackFrame {
  file: string;
  line: number;
  column: number;
  function: string;
  isProjectCode: boolean;
  isNodeModule: boolean;
  sourceContent?: string;
}

interface RootCause {
  frame: StackFrame;
  category: ErrorCategory;
  hypothesis: string;
  relatedFrames: StackFrame[];
  confidence: number;
}
根因分析的核心策略：


    

  • 过滤框架帧：忽略 node_modules/ 和框架内部的栈帧，聚焦项目代码中最近的调用点。
    • 

  • 因果链追溯：从错误抛出点向上追溯调用链，找到第一个项目代码帧作为可能的根因位置。
    • 

  • Error Cause 链：ES2022 引入的 Error.cause 支持错误链，分析完整的因果链而非仅看最外层错误。
    • 

  • Source Map 映射：对于编译后的代码（TypeScript → JavaScript），使用 source map 将错误位置映射回原始源码行号。
    • 

  • 模式匹配：维护常见错误模式库，如"Cannot read properties of undefined"对应空值检查缺失，"is not a function"对应类型混淆。
    • 



人工升级与知识沉淀
并非所有错误都应该由 Agent 自动修复。当修复信心度低于阈值或涉及架构决策时，及时升级给人类比反复重试更有效率。


人工升级的触发条件：


    

  • 连续失败超过最大重试次数
    • 

  • 修复涉及修改受保护文件（配置文件、数据库模式）
    • 

  • 错误分类为"逻辑错误"且信心度低于 50%
    • 

  • Token 消耗超过单任务预算的 80%
    • 

  • 测试失败涉及多个模块的联动修改
    • 



升级后的知识沉淀机制确保同类错误不会反复升级：


interface KnowledgeBase {
  recordResolution(incident: EscalationIncident, resolution: HumanResolution): void;
  findSimilar(error: ErrorClassification): SimilarResolution[];
  generatePattern(resolutions: HumanResolution[]): RepairPattern;
}

interface EscalationIncident {
  taskId: string;
  error: ErrorClassification;
  attempts: RepairAttempt[];
  escalationReason: string;
}

interface HumanResolution {
  patches: FilePatch[];
  explanation: string;
  preventionAdvice: string;
  shouldAutomate: boolean;
}
当人类解决了 Agent 无法处理的问题后，系统记录完整的错误-修复对。当积累到足够数量的同类案例后，系统自动生成新的修复模式并加入策略库，使 Agent 在未来遇到类似问题时能够自主处理。这种人机协作的知识积累是自修复系统持续进化的关键。

小结
    

  • 反馈循环将编码 Agent 从一次性生成器升级为持续改进系统，通过 OODA 循环实现"生成 → 验证 → 诊断 → 修复"的迭代。
    • 

  • 错误分类是自修复的基础，不同类型的错误（语法、类型、运行时、逻辑）需要完全不同的修复策略，精准分类避免浪费重试次数。
    • 

  • 修复策略分三级：确定性修复（零 Token 消耗）、模板化修复（LLM 辅助）、深度修复（LLM 主导），按优先级逐级升级。
    • 

  • 重试策略强调递进式信息累积，每次重试携带前次失败的完整上下文，配合指数退避和预算控制避免资源浪费。
    • 

  • 堆栈追踪分析需要过滤框架帧、追溯因果链、映射 source map，从嘈杂信息中精准定位根因。
    • 

  • 人工升级不是失败，而是质量保障——涉及架构决策、安全修复等高风险场景时，及时升级比反复重试更高效。
    • 

  • 知识沉淀机制将人类修复经验转化为自动化修复模式，实现自修复系统的持续进化。
    •
