可观测性与 Agent 调试

核心概念

编码 Agent 的可观测性是理解 Agent"在想什么、在做什么、做得怎么样"的系统化能力。与传统软件的可观测性不同，编码 Agent 的行为具有不确定性（相同输入可能产生不同输出）、多步推理性（一个任务涉及数十次 LLM 调用和工具使用）和高成本性（每次调用消耗真实的 Token 和计算资源）。可观测性体系需要覆盖三个维度：日志（发生了什么）、追踪（如何发生的）、指标（表现如何）。

结构化日志体系
编码 Agent 的日志远比传统服务复杂——一个任务可能涉及 20-50 次 LLM 调用、数十次文件读写、多次命令执行和若干次修复循环。非结构化的文本日志在这种规模下几乎不可用。


interface AgentLogEntry {
  traceId: string;
  spanId: string;
  parentSpanId: string | null;
  timestamp: string;
  level: 'debug' | 'info' | 'warn' | 'error';
  event: AgentEvent;
  context: LogContext;
}

type AgentEvent =
  | { type: 'task_started'; taskId: string; description: string }
  | { type: 'llm_call'; model: string; inputTokens: number; outputTokens: number; latencyMs: number }
  | { type: 'tool_use'; tool: string; args: Record<string, unknown>; result: 'success' | 'failure' }
  | { type: 'file_modified'; path: string; linesAdded: number; linesRemoved: number }
  | { type: 'verification'; check: string; passed: boolean; details: string }
  | { type: 'repair_attempt'; attempt: number; strategy: string; success: boolean }
  | { type: 'task_completed'; success: boolean; duration: number; totalTokens: number };

interface LogContext {
  agentId: string;
  agentVersion: string;
  taskId: string;
  repository: string;
  branch: string;
  environment: string;
}
日志的关键设计原则：


    

  • 结构化优先：所有日志使用 JSON 格式，每个字段有明确的类型和语义。便于机器解析、聚合和查询。
    • 

  • Trace ID 贯穿：一个任务从创建到完成，所有日志共享同一个 Trace ID，支持端到端的关联查询。
    • 

  • 事件类型化：使用可区分联合类型（Discriminated Union）定义事件，每种事件有独立的字段，避免通用字段的歧义。
    • 

  • 上下文自动注入：Agent ID、版本、仓库名等上下文信息由日志框架自动附加，无需手动传递。
    • 

  • 敏感信息脱敏：日志中不记录完整的 Prompt 内容和代码（可能包含密钥），仅记录 Token 数量和摘要。完整内容存储在安全的追踪存储中。
    • 



分布式追踪与 OpenTelemetry 集成
编码 Agent 的一个任务涉及多个服务的协作——Harness 调度器、LLM API、沙箱环境、代码分析工具、Git 服务。分布式追踪将这些跨服务的调用串联成一条完整的链路，使得"一个 PR 是怎么生成的"变得可追溯。


interface AgentTracer {
  startTask(taskId: string): TaskSpan;
  startLLMCall(model: string, purpose: string): LLMSpan;
  startToolUse(tool: string): ToolSpan;
  startVerification(check: string): VerificationSpan;
}

interface TaskSpan {
  traceId: string;
  spanId: string;
  setAttribute(key: string, value: string | number | boolean): void;
  addEvent(name: string, attributes?: Record<string, unknown>): void;
  setStatus(status: 'ok' | 'error', message?: string): void;
  end(): void;
}

interface LLMSpan extends TaskSpan {
  recordTokenUsage(input: number, output: number): void;
  recordModel(model: string): void;
  recordLatency(ttftMs: number, totalMs: number): void;
}
OpenTelemetry 是实现分布式追踪的标准框架。编码 Agent 场景的 Span 层次结构：


Task Span (顶级)
├── Plan Span
│   ├── LLM Call: 任务分析
│   └── LLM Call: 生成执行计划
├── Execute Span
│   ├── LLM Call: 生成代码 (file-1)
│   ├── Tool Use: 写入文件
│   ├── LLM Call: 生成代码 (file-2)
│   └── Tool Use: 写入文件
├── Verify Span
│   ├── Tool Use: 运行 TypeScript 编译
│   ├── Tool Use: 运行测试
│   └── Tool Use: 运行 Lint
├── Repair Span (如果验证失败)
│   ├── LLM Call: 错误分析
│   ├── LLM Call: 生成修复
│   └── Verify Span (重新验证)
└── Report Span
    └── Tool Use: 创建 PR
每个 Span 记录关键属性：开始/结束时间、Token 消耗、成功/失败状态、错误信息。通过 Span 的父子关系，可以清晰地看到一个任务的完整执行路径和时间分布。


Token 使用追踪与成本分析
Token 消耗是编码 Agent 运营成本的主要构成部分。精确的 Token 追踪不仅用于成本核算，更是优化 Agent 效率的关键数据源。


interface TokenTracker {
  record(usage: TokenUsage): void;
  getTaskSummary(taskId: string): TaskTokenSummary;
  getAgentSummary(agentId: string, period: TimePeriod): AgentTokenSummary;
  detectAnomaly(current: TokenUsage, baseline: TokenBaseline): AnomalyResult;
}

interface TokenUsage {
  traceId: string;
  spanId: string;
  model: string;
  inputTokens: number;
  outputTokens: number;
  cachedTokens: number;
  costUsd: number;
  purpose: string;
}

interface TaskTokenSummary {
  taskId: string;
  totalInputTokens: number;
  totalOutputTokens: number;
  totalCachedTokens: number;
  totalCostUsd: number;
  llmCallCount: number;
  repairAttempts: number;
  tokensByPurpose: Record<string, number>;
  cacheHitRate: number;
}

当 Token 消耗出现异常（如某个任务消耗了正常值的 5 倍），系统自动触发告警并记录异常原因——可能是 Agent 陷入了修复死循环，或者 Prompt 注入导致生成了大量无关内容。


决策轨迹回放与时间旅行调试
编码 Agent 的调试比传统软件更困难——LLM 的输出不确定性意味着"重现 Bug"几乎不可能。决策轨迹（Decision Trace）记录了 Agent 在每个决策点的输入、推理过程和输出，支持时间旅行式调试：在事后任意时间点回到 Agent 的某个决策节点，查看它"看到了什么、想了什么、做了什么"。


interface DecisionTrace {
  taskId: string;
  decisions: DecisionNode[];
  timeline: TimelineEvent[];
}

interface DecisionNode {
  id: string;
  timestamp: string;
  phase: 'plan' | 'execute' | 'verify' | 'repair';
  input: DecisionInput;
  reasoning: string;
  output: DecisionOutput;
  alternatives: Alternative[];
  metadata: DecisionMetadata;
}

interface DecisionInput {
  prompt: string;
  context: ContextSnapshot;
  toolResults: ToolResult[];
}

interface DecisionOutput {
  action: string;
  parameters: Record<string, unknown>;
  confidence: number;
}

interface DecisionMetadata {
  model: string;
  temperature: number;
  tokenUsage: TokenUsage;
  latencyMs: number;
}
时间旅行调试的核心能力：


    

  1. 快照回放：在任意决策点还原 Agent 的完整上下文——它看到的文件内容、收到的错误信息、已完成的操作列表。这相当于在调试器中"回到过去"。
    

    2. 

  2. What-If 分析：修改某个决策点的输入（如更换 Prompt、调整温度参数），重新运行后续步骤，观察不同决策如何影响最终结果。
    

    3. 

  3. 对比分析：将成功任务和失败任务的决策轨迹并排对比，找出关键分歧点——在哪个决策节点上，两条路径走向了不同的方向。
    

    4. 

  4. Prompt 版本对比：同一个任务使用不同版本的 Prompt 运行，对比决策轨迹的差异，验证 Prompt 改动的效果。

运维看板与告警体系
运维看板是 Agent 运营团队的"驾驶舱"，将海量的日志、追踪和指标数据提炼为可操作的信息。


dashboard:
  panels:
    - name: '实时概览'
      metrics:
        - active_tasks: '当前运行中的任务数'
        - success_rate_1h: '最近 1 小时成功率'
        - avg_duration: '平均任务耗时'
        - total_cost_today: '今日累计成本'

    - name: '质量指标'
      metrics:
        - first_pass_rate: '首次生成通过率'
        - avg_repair_rounds: '平均修复轮次'
        - human_escalation_rate: '人工升级率'
        - code_quality_score: '代码质量评分（平均）'

    - name: '资源消耗'
      metrics:
        - token_usage_by_model: '各模型 Token 消耗'
        - sandbox_cpu_utilization: '沙箱 CPU 利用率'
        - cache_hit_rate: 'Prompt 缓存命中率'
        - cost_per_pr: '每 PR 平均成本'

    - name: '异常检测'
      metrics:
        - failed_tasks_1h: '最近 1 小时失败任务'
        - timeout_rate: '超时率'
        - token_anomalies: 'Token 消耗异常'
        - error_pattern_clusters: '错误模式聚类'

alerts:
  rules:
    - name: '成功率骤降'
      condition: 'success_rate_15m < 70%'
      severity: critical
      action: 'pause_new_tasks + notify_oncall'

    - name: '成本超限'
      condition: 'hourly_cost > $50'
      severity: warning
      action: 'notify_slack + throttle_tasks'

    - name: '修复死循环'
      condition: 'repair_rounds > 5 AND no_progress'
      severity: warning
      action: 'kill_task + escalate_human'
告警的设计遵循信噪比优先原则：只有需要人类立即行动的异常才触发告警，可以自动恢复的问题由系统自行处理。告警疲劳（Alert Fatigue）是运维团队的头号敌人——当每天收到 100 条告警时，真正重要的告警会被淹没。

小结
    

  • 可观测性是编码 Agent 运维的基础，覆盖日志（发生了什么）、追踪（如何发生的）、指标（表现如何）三个维度。
    • 

  • 结构化日志使用 JSON 格式和事件类型化设计，通过 Trace ID 贯穿任务全链路，自动脱敏敏感信息。
    • 

  • 分布式追踪基于 OpenTelemetry，将 LLM 调用、工具使用、验证执行串联为完整的 Span 层次结构。
    • 

  • Token 追踪是成本控制的核心——监控每任务 Token 消耗、修复 Token 占比、缓存命中率等关键指标。
    • 

  • 决策轨迹回放支持时间旅行式调试：回到任意决策点查看 Agent 的输入、推理和输出，进行 What-If 分析。
    • 

  • 运维看板将海量数据提炼为实时概览、质量指标、资源消耗和异常检测四大面板，告警设计遵循信噪比优先原则。
    •
