检索策略与 RAG 管道

核心概念

检索增强生成（Retrieval-Augmented Generation，RAG）是知识库系统最核心的服务模式，通过检索相关知识片段并将其注入 LLM 的上下文窗口来生成准确、有据可查的回答。

  • 检索不到相关知识会导致 LLM 生成幻觉
  • 检索到不相关的噪声则会误导 LLM 产生错误答案
  • RAG 管道的设计直接决定知识库的回答质量
graph LR
    Q[用户查询] --> QR[查询改写]
    QR --> R[多路检索]
    R --> RK[重排序]
    RK --> CF[上下文过滤]
    CF --> CA[上下文组装]
    CA --> LLM[LLM 生成]
    LLM --> PP[后处理]
    PP --> A[最终回答]

RAG 阶段总览

RAG 阶段 核心任务 关键优化点 典型延迟
查询改写 扩展和优化原始查询 HyDE、查询分解 50-200ms
多路检索 从多个索引并行检索 向量 + BM25 + 图检索 20-100ms
重排序 精细化相关性排序 Cross-Encoder reranking 50-200ms
上下文过滤 去重和压缩上下文 相关性阈值、去冗余 5-20ms
上下文组装 构建 LLM 输入 prompt 模板设计、token 管理 1-5ms
LLM 生成 基于上下文生成回答 模型选择、采样策略 500-3000ms

查询改写与扩展

查询改写是 RAG 管道中提升检索召回率的关键环节——用户的原始查询通常简短且模糊，直接用于检索可能遗漏大量相关内容。

HyDE

HyDE（Hypothetical Document Embedding）是一种创新的查询改写方法。

  • 先让 LLM 生成一个假设性的理想答案文档
  • 再用这个假设文档的 Embedding 去检索真实文档
  • 假设文档比原始查询更接近目标文档的语义分布，显著提升向量检索召回率
hydeRewrite(query):
  doc = llm("写一段假设性理想答案
             (约 200 字): " + query)
  返回 [
    {原始查询, weight 0.3},
    {假设文档, weight 0.7},
  ]

查询分解

查询分解将复杂查询拆分为多个简单子查询分别检索。

  • 示例："React 和 Vue 在状态管理上的区别"
  • 分解为 "React 状态管理方案" 和 "Vue 状态管理方案" 两个子查询
  • 各自检索后合并结果
decompose(query):
  subs = llm("分解为 2-4 个子查询")
  返回 [原始查询 0.4]
     + subs 均分剩余 0.6 权重

上下文组装与 Token 管理

上下文组装是将检索结果转化为 LLM 输入的关键步骤，核心挑战是在有限的上下文窗口内最大化有用信息的密度。

上下文压缩技术

压缩方法 做法
抽取式压缩 只保留与查询最相关的句子
LLM 压缩 让 LLM 总结检索片段，去除冗余信息
去重压缩 检测并移除多个检索片段中的重复内容 
graph TD
    R[检索结果 Top-K] --> D[去重]
    D --> C[压缩]
    C --> T[Token 预算分配]
    T --> P[模板填充]
    P --> V[Token 验证]
    V --> L[发送至 LLM]

组装算法

assembleContext(query, chunks, config):
  可用 = maxTokens - 查询预留 - 回答预留
  chunks = 去重(chunks)
  按分数顺序装入, 超出预算即停止
  prompt = 模板替换 {{context}} {{query}}
  返回 { prompt, 是否截断 }

Token 预算分配

Token 预算分配 比例 用途
系统 Prompt 5-10% 角色定义和指令
检索上下文 50-70% 知识片段
用户查询 5-10% 原始问题
生成预留 20-30% LLM 回答空间

高级 RAG 模式

基础 RAG 管道存在几个已知的局限性。

  • 单轮检索可能遗漏需要多次推理的信息
  • 平面检索难以处理需要结构化推理的问题
  • 检索结果可能包含过时或矛盾的信息

Agentic RAG

Agentic RAG 将 RAG 管道嵌入到一个 Agent 循环中。

  • LLM 不仅生成答案，还能决定何时需要更多信息、从哪里检索、如何组合不同来源的知识
  • Agent 在多轮交互中迭代地细化查询和检索
  • 直到获得足够的信息来生成可靠的答案
agenticAnswer(query, maxIterations):
  循环至多 maxIterations 次:
    action = llm 决策(当前查询, 已有上下文)
    synthesize  -> 跳出循环
    search      -> 混合检索, 追加上下文
    graph_query -> 图查询, 追加实体信息
    更新当前查询
  返回 generateAnswer(llm, query, 上下文)

GraphRAG

GraphRAG 将知识图谱与 RAG 结合。

  • 先从知识图谱中检索相关的子图
  • 再将子图信息和文本检索结果一起注入 LLM 上下文
  • 特别适合需要结构化推理的问题，如 "React 生态中的状态管理库有哪些，它们各自的设计理念是什么"

百万级长上下文对 RAG 架构的冲击

2024-2025 年主流模型的上下文窗口从早年的 8K-32K 扩展到百万 token 级：GPT-4.1 支持 1M token 上下文窗口（platform.openai.com/docs/models/gpt-4.1），Gemini 1.5 系列以跨数百万 token 的多模态上下文理解为核心能力（arXiv:2403.05530）。这引发了「长上下文是否取代 RAG」的讨论，当前工程共识是互补而非替代。

  • Google DeepMind 的对比研究提出 SELF-ROUTE 路由：模型先基于检索片段自评能否作答，不能时再回退到全上下文——在保持接近纯长上下文方法回答质量的同时显著降低 token 消耗（arXiv:2407.16833）
  • 成本与延迟：百万 token 推理的费用和首字延迟仍远高于数千 token 的精准检索注入，按查询付费的场景差距被放大
  • 溯源与权限：RAG 天然提供答案到来源的映射和按用户权限的检索过滤，纯长上下文方案难以同时满足这两点
  • 新鲜度与规模：知识库持续更新、文档量远超任何上下文窗口时，检索层不可省略

实践结论：长上下文改变的是 RAG 的设计参数而非存废——单篇长文档可整体放入上下文免检索；跨海量文档、多租户、需溯源的场景仍采用「检索缩小范围 + 长上下文容纳更多检索结果」的组合架构，注入 Top-K 片段数因此从早期的 3-5 片扩展到数十片成为可行。

回答质量评估

RAG 系统的回答质量需要从多个维度进行评估。

评估维度

  • 忠实度（Faithfulness）：回答是否忠于检索到的上下文，不添加未经证实的信息
  • 相关性（Relevance）：回答是否回答了用户的问题
  • 完整性（Completeness）：回答是否覆盖了查询涉及的所有方面

RAGAS 指标

自动化评估通常使用 LLM-as-Judge 的方式——让另一个 LLM 对回答进行评分。RAGAS 是流行的 RAG 评估框架。

评估指标 衡量内容 计算方式 目标值
忠实度 答案是否忠于上下文 断言验证 >0.9
答案相关性 答案是否相关 语义相似度 >0.8
上下文精确度 检索上下文是否精确 有用段落比例 >0.7
上下文召回率 必要信息是否被检索到 覆盖率 >0.8

小结

  • RAG 管道通过检索知识片段注入 LLM 上下文实现有据可查的回答生成
  • HyDE 和查询分解是提升检索召回率的两种有效查询改写策略
  • 上下文组装需要在有限 token 预算内最大化有用信息密度
  • Agentic RAG 将检索嵌入 Agent 循环，支持多轮迭代检索和推理
  • GraphRAG 结合知识图谱实现结构化推理，特别适合关系型问题
  • 百万级长上下文与 RAG 是互补关系：SELF-ROUTE 类路由方案兼取两者之长，检索层仍承担溯源、权限与规模控制
  • RAGAS 框架的四个核心指标全面评估 RAG 系统的回答质量
