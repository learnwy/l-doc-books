知识库 API 设计

核心概念

知识库 API 是多层架构中的最上层，封装了底层所有的检索、推理和生成能力，为外部应用提供统一的访问接口。API 设计需要兼顾功能完整性、使用便捷性和性能可控性——既要让开发者能够利用知识库的全部能力，又要通过合理的抽象隐藏内部复杂性。

RESTful 与 Streaming API 设计
知识库 API 需要同时支持两种交互模式：请求-响应模式用于搜索和浏览，流式模式用于 LLM 生成的问答回答。


搜索 API 采用标准的 RESTful 设计，支持丰富的过滤和排序参数。关键设计决策包括：分页策略（使用 cursor-based 分页而非 offset-based，以避免在数据更新时出现重复或遗漏）、过滤语法（支持布尔表达式和范围查询）和结果格式（包含原文片段、高亮匹配和元数据）。


问答 API 使用 Server-Sent Events（SSE）实现流式输出，让用户在 LLM 生成过程中就能看到部分回答。流式输出不仅改善了用户体验（减少首字节时间），还让客户端能够在生成过程中展示中间状态（如正在检索、正在生成）。


interface SearchRequest {
  readonly query: string;
  readonly topK?: number;
  readonly filter?: FilterExpression;
  readonly sources?: ReadonlyArray<'vector' | 'fulltext' | 'graph'>;
  readonly cursor?: string;
  readonly includeHighlights?: boolean;
}

interface SearchResponse {
  readonly results: ReadonlyArray<SearchResultItem>;
  readonly totalCount: number;
  readonly cursor?: string;
  readonly metadata: SearchMetadata;
}

interface SearchResultItem {
  readonly id: string;
  readonly title: string;
  readonly snippet: string;
  readonly highlights: ReadonlyArray<HighlightSpan>;
  readonly score: number;
  readonly source: string;
  readonly metadata: Record<string, unknown>;
}

interface AskRequest {
  readonly question: string;
  readonly conversationId?: string;
  readonly maxTokens?: number;
  readonly includeReferences?: boolean;
  readonly stream?: boolean;
}

interface AskStreamEvent {
  readonly type: 'status' | 'chunk' | 'reference' | 'done' | 'error';
  readonly data: unknown;
}

type FilterExpression =
  | { readonly type: 'eq'; readonly field: string; readonly value: unknown }
  | { readonly type: 'range'; readonly field: string; readonly min?: number; readonly max?: number }
  | { readonly type: 'in'; readonly field: string; readonly values: ReadonlyArray<unknown> }
  | { readonly type: 'and'; readonly conditions: ReadonlyArray<FilterExpression> }
  | { readonly type: 'or'; readonly conditions: ReadonlyArray<FilterExpression> };
API 版本化与兼容性
API 版本化确保知识库的内部演进不会破坏现有客户端。版本化策略选择 URL 路径版本（如 /v1/search, /v2/search）而非 Header 版本，因为路径版本在浏览器和日志中更直观，也更容易做路由和负载均衡。


版本兼容性策略遵循三个原则。增量添加——新版本可以添加新字段和新端点，但不删除或重命名已有字段。过渡期——废弃的功能在至少两个版本周期内保持可用，并通过 Deprecation Header 提醒客户端。SDK 抽象——官方 SDK 封装版本差异，客户端升级 SDK 即可透明迁移。


interface APIVersionConfig {
  readonly currentVersion: string;
  readonly supportedVersions: ReadonlyArray<string>;
  readonly deprecatedVersions: ReadonlyArray<DeprecationInfo>;
}

interface DeprecationInfo {
  readonly version: string;
  readonly deprecatedAt: Date;
  readonly sunsetAt: Date;
  readonly migrationGuide: string;
}

interface APIRoute {
  readonly path: string;
  readonly method: 'GET' | 'POST' | 'PUT' | 'DELETE';
  readonly version: string;
  readonly handler: RequestHandler;
  readonly rateLimit: RateLimitConfig;
  readonly cacheable: boolean;
}

interface RateLimitConfig {
  readonly windowMs: number;
  readonly maxRequests: number;
  readonly costPerRequest: number;
}

限流与降级策略
知识库 API 中不同端点的资源消耗差异巨大——搜索 API 主要消耗 CPU 和内存，问答 API 还额外消耗昂贵的 LLM 计算资源。限流策略需要根据端点的资源消耗特征进行差异化配置。


降级策略是保障系统可用性的最后一道防线。当 LLM 服务不可用时，问答 API 自动降级为搜索 API——只返回相关文档片段而非生成的答案。当向量数据库不可用时，语义搜索降级为 BM25 全文搜索。每层降级都应对用户透明，通过响应中的 degradation 字段告知客户端当前的服务级别。


interface DegradationStrategy {
  readonly name: string;
  readonly trigger: DegradationTrigger;
  readonly action: (request: APIRequest) => Promise<APIResponse>;
  readonly notifyClient: boolean;
}

type DegradationTrigger =
  | { readonly type: 'service_down'; readonly service: string }
  | { readonly type: 'latency_exceeded'; readonly threshold: number }
  | { readonly type: 'rate_limited'; readonly currentRate: number }
  | { readonly type: 'error_rate'; readonly threshold: number };

const DEGRADATION_CHAIN: ReadonlyArray<DegradationStrategy> = [
  {
    name: 'llm_unavailable',
    trigger: { type: 'service_down', service: 'llm' },
    action: async (req) => fallbackToSearch(req),
    notifyClient: true,
  },
  {
    name: 'vector_db_unavailable',
    trigger: { type: 'service_down', service: 'vector_db' },
    action: async (req) => fallbackToFulltext(req),
    notifyClient: true,
  },
  {
    name: 'high_latency',
    trigger: { type: 'latency_exceeded', threshold: 5000 },
    action: async (req) => returnCachedOrPartial(req),
    notifyClient: true,
  },
];
SDK 设计与开发者体验
官方 SDK 封装了 API 的复杂性，为不同编程语言的开发者提供类型安全和符合语言习惯的接口。TypeScript SDK 是最常用的选择，它能够充分利用类型系统来提供编译时校验和自动补全。


SDK 设计的关键原则包括：零配置默认——开箱即用，只需提供 API Key；渐进式配置——高级用户可以细粒度配置每个参数；流式优先——问答接口默认使用流式输出；错误友好——所有错误都包含清晰的错误码、描述和建议修复方案。


interface KBClient {
  search(query: string, options?: SearchOptions): Promise<SearchResponse>;
  ask(question: string, options?: AskOptions): AsyncGenerator<AskStreamEvent>;
  browse(path?: string): Promise<BrowseResponse>;
  ingest(documents: ReadonlyArray<IngestDocument>): Promise<IngestResponse>;
}

interface KBClientConfig {
  readonly apiKey: string;
  readonly baseUrl?: string;
  readonly version?: string;
  readonly timeout?: number;
  readonly retries?: number;
}

const createKBClient = (config: KBClientConfig): KBClient => ({
  search: async (query, options) => {
    const response = await fetch(`${config.baseUrl}/v1/search`, {
      method: 'POST',
      headers: { Authorization: `Bearer ${config.apiKey}`, 'Content-Type': 'application/json' },
      body: JSON.stringify({ query, ...options }),
    });
    if (!response.ok) throw new KBError(await response.json());
    return response.json() as Promise<SearchResponse>;
  },
  ask: async function* (question, options) {
    const response = await fetch(`${config.baseUrl}/v1/ask`, {
      method: 'POST',
      headers: { Authorization: `Bearer ${config.apiKey}`, 'Content-Type': 'application/json' },
      body: JSON.stringify({ question, stream: true, ...options }),
    });
    const reader = response.body?.getReader();
    if (!reader) return;
    const decoder = new TextDecoder();
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      const text = decoder.decode(value);
      const events = parseSSE(text);
      for (const event of events) yield event;
    }
  },
  browse: async (path) => fetch(`${config.baseUrl}/v1/browse${path ? `?path=${path}` : ''}`).then((r) => r.json()),
  ingest: async (documents) =>
    fetch(`${config.baseUrl}/v1/ingest`, { method: 'POST', body: JSON.stringify({ documents }) }).then((r) => r.json()),
});
小结
    

  • 知识库 API 封装搜索、问答、浏览和管理四大类接口，通过网关统一认证、限流和降级
    • 

  • 搜索 API 使用 RESTful + cursor 分页，问答 API 使用 SSE 流式输出
    • 

  • API 版本化采用 URL 路径策略，废弃功能保留两个版本周期的过渡期
    • 

  • 差异化限流根据端点资源消耗特征配置，LLM 调用的配额严格独立管理
    • 

  • 级联降级策略确保每层服务不可用时都有可接受的 fallback 方案
    • 

  • SDK 遵循零配置默认和渐进式配置原则，为开发者提供类型安全的接口
