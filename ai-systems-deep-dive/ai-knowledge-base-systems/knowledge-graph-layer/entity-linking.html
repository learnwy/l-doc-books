实体链接与消歧

核心概念

实体链接（Entity Linking）是将文本中提到的实体名称（mention）映射到知识库中对应的规范化实体（canonical entity）的过程。在知识库系统中，同一个技术概念可能以多种形式出现——"React"、"React.js"、"ReactJS"、"React 框架"都指向同一个实体。实体链接的任务就是识别这些变体并将它们统一指向同一个知识节点。

候选生成策略
候选生成是实体链接的第一阶段，目标是从知识库中快速召回一组可能与 mention 匹配的候选实体。候选生成的核心矛盾是召回率与效率的平衡——需要尽可能不遗漏正确实体，同时候选数量不能太多以避免后续排序阶段的计算爆炸。


基于别名表的生成是最基本的方法。为知识库中的每个实体维护一个别名列表（包括全称、缩写、同义词和常见拼写错误），通过精确匹配或编辑距离匹配来召回候选。别名表的覆盖率决定了召回率的下限。


基于 Embedding 的生成使用 Bi-Encoder 模型将 mention 和实体分别编码为向量，通过向量相似度检索候选。这种方法能处理别名表中未覆盖的新表述形式，但计算成本更高。


interface CandidateGenerator {
  generate(mention: EntityMention, topK: number): Promise<ReadonlyArray<CandidateEntity>>;
}

interface EntityMention {
  readonly text: string;
  readonly context: string;
  readonly sourceDoc: string;
  readonly position: TextSpan;
}

interface CandidateEntity {
  readonly entityId: string;
  readonly name: string;
  readonly aliases: ReadonlyArray<string>;
  readonly description: string;
  readonly type: string;
  readonly matchScore: number;
  readonly matchSource: 'alias' | 'fuzzy' | 'embedding';
}

const createHybridGenerator = (aliasIndex: AliasIndex, embeddingIndex: EmbeddingIndex): CandidateGenerator => ({
  generate: async (mention, topK) => {
    const aliasCandidates = aliasIndex.lookup(mention.text, topK);
    const fuzzyCandidates = aliasIndex.fuzzyLookup(mention.text, topK, { maxEditDistance: 2 });
    const embeddingCandidates = await embeddingIndex.search(mention.text, topK);
    const merged = deduplicateByEntityId([
      ...aliasCandidates.map((c) => ({ ...c, matchSource: 'alias' as const })),
      ...fuzzyCandidates.map((c) => ({ ...c, matchSource: 'fuzzy' as const })),
      ...embeddingCandidates.map((c) => ({ ...c, matchSource: 'embedding' as const })),
    ]);
    return merged.slice(0, topK);
  },
});
在技术文档场景下，候选生成还需要处理一些特殊情况：版本化实体（"Python 3.11" vs "Python 3.12" 应该链接到不同实体还是同一实体）、嵌套实体（"React Router" 中的 "React" 是否需要单独链接）和新实体发现（当 mention 在知识库中找不到对应实体时的处理）。


上下文感知排序
候选排序利用 mention 的上下文信息来区分同名但不同含义的实体。"Spring" 在软件开发上下文中指 Java Spring 框架，在机械工程上下文中指弹簧，在季节讨论中指春天。


Bi-Encoder + Cross-Encoder 的两阶段排序是当前最有效的方案。Bi-Encoder 独立编码 mention 上下文和实体描述，通过向量内积快速筛选；Cross-Encoder 将 mention 上下文和实体描述拼接后联合编码，捕获更精细的交互特征。

interface EntityRanker {
  rank(mention: EntityMention, candidates: ReadonlyArray<CandidateEntity>): Promise<ReadonlyArray<RankedCandidate>>;
}

interface RankedCandidate extends CandidateEntity {
  readonly rankScore: number;
  readonly contextRelevance: number;
}

const createTwoStageRanker = (biEncoder: BiEncoder, crossEncoder: CrossEncoder, coarseTopK: number): EntityRanker => ({
  rank: async (mention, candidates) => {
    const mentionEmb = await biEncoder.encode(mention.context);
    const coarseScored = candidates.map((c) => ({
      ...c,
      coarseScore: cosineSimilarity(mentionEmb, c.embedding),
    }));
    const topCandidates = coarseScored.sort((a, b) => b.coarseScore - a.coarseScore).slice(0, coarseTopK);
    const pairs = topCandidates.map((c) => ({
      textA: `${mention.text}: ${mention.context}`,
      textB: `${c.name}: ${c.description}`,
    }));
    const fineScores = await crossEncoder.predict(pairs);
    return topCandidates
      .map((c, i) => ({
        ...c,
        rankScore: fineScores[i],
        contextRelevance: fineScores[i],
      }))
      .sort((a, b) => b.rankScore - a.rankScore);
  },
});
集体消歧算法
集体消歧（Collective Disambiguation）是实体链接中处理多义实体的高级策略。与逐个处理每个 mention 不同，集体消歧同时考虑文档中所有 mention 的链接决策，利用实体之间的关联性来互相约束和增强消歧效果。


核心思想是：如果一篇文档同时提到了 "React"、"JSX" 和 "Virtual DOM"，那么 "React" 更可能指向 JavaScript 框架而非化学术语，因为 JSX 和 Virtual DOM 与 React 框架存在强关联。这种文档级别的全局一致性约束显著提升了消歧准确率。


集体消歧的经典算法包括图模型方法（将实体链接建模为图上的推理问题）和全局优化方法（将所有 mention 的链接决策作为一个联合优化问题）。基于知识图谱的相干性评分（coherence score）是度量候选实体组合质量的关键指标。


interface CollectiveDisambiguator {
  disambiguate(
    mentions: ReadonlyArray<EntityMention>,
    candidateSets: ReadonlyArray<ReadonlyArray<CandidateEntity>>,
  ): Promise<ReadonlyArray<DisambiguationResult>>;
}

interface DisambiguationResult {
  readonly mention: EntityMention;
  readonly selectedEntity: CandidateEntity | null;
  readonly confidence: number;
  readonly isNIL: boolean;
}

const computeCoherence = (entitySet: ReadonlyArray<CandidateEntity>, kg: KnowledgeGraph): number => {
  let totalRelatedness = 0;
  let pairCount = 0;
  for (let i = 0; i < entitySet.length; i++) {
    for (let j = i + 1; j < entitySet.length; j++) {
      totalRelatedness += kg.getRelatedness(entitySet[i].entityId, entitySet[j].entityId);
      pairCount++;
    }
  }
  return pairCount > 0 ? totalRelatedness / pairCount : 0;
};
NIL 实体处理与新实体发现
当 mention 在知识库中找不到匹配的实体时（NIL 实体），系统需要决定是创建一个新实体还是标记为未知。NIL 检测的准确性对知识库的持续扩展至关重要——漏检会导致新概念无法被收录，误检则会产生大量低质量的冗余实体。


NIL 检测通常使用阈值策略——当最高排序分数低于预设阈值时判定为 NIL。更精细的方案使用专门的 NIL 分类器，综合考虑排序分数、候选实体数量和上下文特征。


interface NILDetector {
  isNIL(mention: EntityMention, topCandidate: RankedCandidate | null): Promise<NILDecision>;
}

interface NILDecision {
  readonly isNIL: boolean;
  readonly confidence: number;
  readonly suggestedAction: 'create_entity' | 'mark_unknown' | 'manual_review';
  readonly suggestedType?: string;
}

const createNILDetector = (threshold: number, newEntityPolicy: NewEntityPolicy): NILDetector => ({
  isNIL: async (mention, topCandidate) => {
    if (!topCandidate || topCandidate.rankScore < threshold) {
      const suggestedAction = newEntityPolicy.autoCreate ? 'create_entity' : 'manual_review';
      return {
        isNIL: true,
        confidence: topCandidate ? 1 - topCandidate.rankScore : 1.0,
        suggestedAction,
        suggestedType: inferEntityType(mention),
      };
    }
    return { isNIL: false, confidence: topCandidate.rankScore, suggestedAction: 'mark_unknown' };
  },
});

interface NewEntityPolicy {
  readonly autoCreate: boolean;
  readonly minMentionCount: number;
  readonly requireHumanApproval: boolean;
}
新实体发现是知识库动态扩展的关键机制。当系统检测到多个文档中频繁出现相同的 NIL mention 时，说明这可能是一个值得收录的新概念。通过聚类分析将相似的 NIL mention 分组，每个聚类对应一个潜在的新实体，由系统自动创建或提交人工审核。


小结
    

  • 实体链接通过候选生成、候选排序和消歧决策三阶段将文本 mention 映射到知识库实体
    • 

  • 混合候选生成策略结合别名表、模糊匹配和 Embedding 检索，确保高召回率
    • 

  • Bi-Encoder + Cross-Encoder 两阶段排序平衡了效率和精度
    • 

  • 集体消歧利用文档级别的实体关联性互相约束，显著提升多义实体的消歧准确率
    • 

  • NIL 检测和新实体发现机制确保知识库能够持续扩展和收录新概念
    • 

  • 技术文档场景需要特别处理版本化实体、嵌套实体和快速演变的技术术语
