知识库设计原则

核心概念

知识库系统是将组织内外信息资产进行系统化采集、加工、存储和服务的基础设施。

  • 与传统数据库不同，知识库关注的不仅是数据存取
  • 更强调知识的语义理解、关联发现和智能检索
  • Karpathy 提出的多层知识库架构将知识处理分解为独立且可组合的层次
  • 每一层聚焦于特定的知识处理阶段

    C[知识优先] --> D[语义驱动]

与传统文档系统的对比

原则 传统文档系统 现代知识库系统
数据组织 文件夹层级 语义图谱 + 向量空间
检索方式 关键词匹配 语义理解 + 混合检索
知识更新 手动维护 自动化管道 + 增量更新
质量保障 人工审核 自动化质量检测 + 人机协同
服务形态 静态页面 API + 对话式交互

分层解耦原则

分层解耦是知识库架构设计的核心原则，其灵感来源于计算机网络的分层模型。

从 3 层到 8 层

  • Karpathy 的 3 层架构（Raw → LLM Doc → Index）是最基本的分层模型
  • 实践中可以扩展为 8 层以应对更复杂的需求
  • 核心要求：每一层只依赖下一层提供的接口，而不关心其内部实现
层次 职责
原始文档层 多格式文档的采集与归一化，知识库的数据源头
存储层 统一持久化：文件存储、向量数据库、图数据库
索引层 构建倒排索引、向量索引和图索引 
graph LR
    R[Raw] --> L[LLM 处理]
    L --> I[Index/API]
    R2[原始层] --> S[存储层]
    S --> IX[索引层]
    IX --> LP[LLM 层]
    LP --> KG[图谱层]
    KG --> CA[缓存层]
    CA --> CT[目录层]
    CT --> AP[API 层]

分层的关键收益

  • 独立扩展性——向量索引层可单独更换为更高性能的 ANN 引擎而不影响上层服务
  • 可测试性——每层可以用 mock 接口进行单元测试
  • 技术异构性——不同层使用最适合的技术栈，例如原始文档层用对象存储，图谱层用 Neo4j

层接口抽象

interface KBLayer<TIn, TOut> {
  readonly name: string;
  process(input: TIn): Promise<TOut>;
  validate(out: TOut): Promise<boolean>;
}
const createPipeline = (layers) => ({
  layers,
  run: async (input) => {
    let cur = input;
    for (const layer of layers) {
      cur = await layer.process(cur);
      if (!(await layer.validate(cur))) throw new Error(`${layer.name} failed`);
    }
    return cur;
  },
});

知识优先原则

知识优先原则要求系统设计以知识的语义质量为最高优先级，而非文档格式的保真度。

格式与内容分离

  • 传统文档管理系统追求格式完整保留（PDF → PDF）
  • 知识库系统应当将格式与内容分离，以结构化语义作为内部表示

三项核心实践

实践 含义
语义抽取优先 解析阶段优先提取标题层级、表格数据、代码块，而非保留视觉格式
知识去重 相同知识点只保留一份规范化表示，通过引用链接回原始来源
语义关联 因果、包含、依赖、对比等关系显式建模，而非依赖用户脑补

知识粒度的选择

  • 过粗的粒度（整篇文档）会导致检索结果不精确
  • 过细的粒度（单个句子）则丢失上下文
  • 经典基线配方：段落级别（150-500 tokens）配合滑动窗口和重叠区域——2023 年前后的通用起点，至今仍是多数系统的默认值
  • 2024 年后的实践更倾向「子块检索 + 父块生成」的 Parent-Child 分层索引，配合 Contextual Retrieval、Late Chunking 等上下文增强方案（详见知识处理章的切分新范式）
粒度级别 Token 范围 适用场景 优势 劣势
句子级 20-50 事实性问答 精确匹配 缺少上下文
段落级 150-500 通用检索 平衡精确与上下文 可能包含噪声
章节级 500-2000 综述类查询 完整上下文 检索粒度粗
文档级 2000+ 文档推荐 全局理解 无法定位具体知识点

上表的单一粒度选择是经典模型；Parent-Child 分层允许系统同时持有两级粒度——子块进索引、父块进生成，粒度选择从「二选一」变为「分层组合」。

渐进增强原则

渐进增强原则借鉴 Web 开发中的同名理念——系统在最基础的功能上就能工作，高级功能作为增强层叠加。对于知识库，这意味着即使没有 LLM、没有知识图谱，系统也能通过基础全文检索提供服务。

四级增强层次

层级 能力
1 基础检索 倒排索引关键词搜索 + BM25 排序，无需任何 AI 模型
2 语义增强 向量检索，Embedding 映射语义空间，混合检索提升召回率
3 知识增强 知识图谱，实体消歧、关系推理和多跳问答
4 智能增强 集成 LLM，对话式检索、答案生成和知识总结

混合检索与 RRF 融合

interface RetrievalStrategy {
  readonly level: string;
  retrieve(q: string, k: number): Promise<Result[]>;
}
const rrf = (resultSets, k = 60) => {
  const map = new Map();
  for (const results of resultSets)
    results.forEach((r, rank) => {
      const e = map.get(r.id);
      const s = 1 / (k + rank + 1);
      if (e) e.score += s;
      else map.set(r.id, { ...r, score: s });
    });
  return [...map.values()].sort((a, b) => b.score - a.score);
};

降级保障

  • 每一层都有独立的价值，高级层故障不会导致整个系统不可用
  • LLM 服务不可用时，系统自动降级到语义检索或关键词检索
  • 用户在降级状态下仍然能获得有用的结果

质量闭环原则

知识库的质量不是一次性工程，而是需要持续的监控、评估和改进。质量闭环原则要求在系统设计之初就内建度量和反馈机制。

质量度量维度

维度 度量方式
知识覆盖率 与领域本体对比，量化对目标领域的覆盖程度
检索准确率 标注数据集评估相关性，使用 NDCG、MAP 等标准指标
知识新鲜度 衡量知识时效性，对快速变化的技术领域尤为重要
答案质量 LLM 增强模式下评估答案的准确性、完整性和一致性

反馈机制

  • 隐式反馈：用户点击、停留时间、查询重写频率
  • 显式反馈：用户评分、纠错标注
  • 反馈用途：改进检索排序、更新知识质量权重、识别知识缺口
graph TD
    A[知识入库] --> B[质量检测]
    B --> C{达标?}
    C -->|是| D[索引更新]
    C -->|否| E[标记待审]
    D --> F[检索服务]
    F --> G[用户反馈]
    G --> H[质量分析]
    H --> A

小结

  • 分层解耦是知识库架构的基石，从 Karpathy 3 层到实践 8 层，每层聚焦单一职责
  • 知识优先原则要求以语义质量驱动设计，格式只是知识的载体
  • 渐进增强保障系统在任何层级都可独立服务，高级功能作为叠加增强
  • 质量闭环将评估和反馈内建于系统，确保知识库持续进化
  • 合理的知识粒度选择是检索质量的基础：段落级 150-500 tokens 是经典基线，Parent-Child 分层与上下文增强切片是当前主流演进方向
  • 混合检索策略通过 RRF 等融合算法结合不同检索范式的优势
