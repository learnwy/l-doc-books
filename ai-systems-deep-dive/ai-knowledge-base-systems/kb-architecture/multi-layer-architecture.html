多层知识库架构

核心概念

多层知识库架构是 Karpathy 提出的 3 层模型（Raw → LLM Doc → Index）的工程化扩展，将知识处理分解为 8 个独立层次，每层承担明确的职责。这种架构的设计哲学类似于 OSI 网络模型——通过标准化的层间接口实现各层的独立演进和灵活组合。

原始文档层与存储层
原始文档层（L1）是知识库的数据入口，负责从多种来源和格式中采集文档，并将其转换为统一的内部表示。支持的格式通常包括 PDF、HTML、Markdown、Word、纯文本、Jupyter Notebook 和代码文件等。


文档解析的核心挑战在于格式归一化。不同格式的解析器需要处理完全不同的文档结构：PDF 需要处理布局分析和 OCR，HTML 需要处理 DOM 树和样式清理，Markdown 相对简单但需要处理扩展语法。


interface RawDocument {
  readonly id: string;
  readonly source: string;
  readonly format: 'pdf' | 'html' | 'markdown' | 'docx' | 'text';
  readonly rawContent: Buffer;
  readonly metadata: DocumentMetadata;
  readonly fetchedAt: Date;
}

interface ParsedDocument {
  readonly id: string;
  readonly title: string;
  readonly sections: ReadonlyArray<Section>;
  readonly metadata: DocumentMetadata;
}

interface Section {
  readonly heading: string;
  readonly level: number;
  readonly content: string;
  readonly tables: ReadonlyArray<TableData>;
  readonly codeBlocks: ReadonlyArray<CodeBlock>;
}

interface DocumentMetadata {
  readonly source: string;
  readonly author?: string;
  readonly createdAt?: Date;
  readonly updatedAt?: Date;
  readonly tags: ReadonlyArray<string>;
  readonly language: string;
}
存储层（L2）提供统一的持久化能力，包括三种存储引擎：对象存储用于原始文件和大型文本块，关系数据库用于元数据和结构化信息，向量数据库用于 Embedding 向量。存储层的关键设计决策是版本管理策略——知识库中的文档可能频繁更新，需要支持版本追溯和增量更新。

索引层与 LLM 处理层
索引层（L3）是检索性能的关键，负责构建多种索引以支持不同的检索策略。传统的倒排索引支持 BM25 关键词检索，向量索引（HNSW、IVF）支持语义检索，图索引支持基于知识图谱的推理检索。


索引构建是一个离线过程，通常通过 Pipeline 实现自动化。当新文档入库或已有文档更新时，索引层需要执行增量更新而非全量重建，以保证索引的新鲜度。


LLM 处理层（L4）利用大语言模型对文档进行深层语义处理。核心任务包括自动摘要生成、实体和关系抽取、知识点结构化和问答对生成。这一层是整个架构中计算成本最高的部分，需要通过批处理和缓存策略来控制成本。


LLM 处理的关键设计模式是流水线模式——每个文档依次经过摘要、实体抽取、关系抽取和质量检测四个阶段。每个阶段使用专门优化的 Prompt 和模型配置，确保输出质量的稳定性。


interface LLMProcessor {
  summarize(doc: ParsedDocument): Promise<Summary>;
  extractEntities(doc: ParsedDocument): Promise<ReadonlyArray<Entity>>;
  extractRelations(doc: ParsedDocument, entities: ReadonlyArray<Entity>): Promise<ReadonlyArray<Relation>>;
  generateQAPairs(doc: ParsedDocument): Promise<ReadonlyArray<QAPair>>;
}

interface Summary {
  readonly abstract: string;
  readonly keyPoints: ReadonlyArray<string>;
  readonly category: string;
}

interface Entity {
  readonly name: string;
  readonly type: string;
  readonly description: string;
  readonly aliases: ReadonlyArray<string>;
  readonly sourceSpan: TextSpan;
}

interface Relation {
  readonly subject: Entity;
  readonly predicate: string;
  readonly object: Entity;
  readonly confidence: number;
}

interface QAPair {
  readonly question: string;
  readonly answer: string;
  readonly supportingEvidence: ReadonlyArray<TextSpan>;
}
知识图谱层与缓存层
知识图谱层（L5）将 LLM 处理层提取的实体和关系组织成语义网络。知识图谱的核心价值在于实现跨文档的知识关联——同一个实体可能在多篇文档中出现，通过实体消歧和链接，这些分散的知识碎片被整合为统一的知识网络。


知识图谱层的主要操作包括实体对齐——将不同文档中指代相同事物的实体合并；关系推理——基于已有关系推导隐含关系；一致性检查——检测知识图谱中的矛盾和冲突。


缓存层（L6）在高频查询场景下至关重要。知识库的查询模式通常符合幂律分布——少数热门查询占据大部分流量。缓存层通过多级缓存策略（内存 L1 → Redis L2 → 磁盘 L3）减少对下层的重复计算。


interface CacheConfig {
  readonly l1MemoryMaxItems: number;
  readonly l2RedisUrl: string;
  readonly l3DiskPath: string;
  readonly ttlSeconds: Record<CacheType, number>;
}

type CacheType = 'query_result' | 'embedding' | 'llm_response' | 'graph_query';

interface CacheLayer {
  get<T>(key: string): Promise<T | null>;
  set<T>(key: string, value: T, type: CacheType): Promise<void>;
  invalidate(pattern: string): Promise<number>;
}

const createMultiLevelCache = (config: CacheConfig): CacheLayer => {
  const l1 = new Map<string, { value: unknown; expiresAt: number }>();

  return {
    get: async <T>(key: string): Promise<T | null> => {
      const l1Entry = l1.get(key);
      if (l1Entry && l1Entry.expiresAt > Date.now()) {
        return l1Entry.value as T;
      }
      return null;
    },
    set: async <T>(key: string, value: T, type: CacheType): Promise<void> => {
      const ttl = config.ttlSeconds[type] * 1000;
      l1.set(key, { value, expiresAt: Date.now() + ttl });
    },
    invalidate: async (pattern: string): Promise<number> => {
      let count = 0;
      for (const key of l1.keys()) {
        if (key.includes(pattern)) {
          l1.delete(key);
          count++;
        }
      }
      return count;
    },
  };
};

目录层与 API 层
目录层（L7）为知识库提供人类可理解的导航结构。虽然向量检索和知识图谱能处理精确查询，但用户常常需要通过浏览和导航来发现知识。目录层自动构建分类体系，包括基于知识图谱的主题分类、基于标签的多维分类和基于使用频率的热门推荐。


目录层的一个重要功能是 CLAUDE.md 式索引——以自然语言描述知识库的结构和内容覆盖范围，让 AI Agent 能够快速理解知识库的能力边界，并据此决定何时以及如何调用知识库 API。


API 层（L8）是知识库对外暴露的唯一接口。所有的内部复杂性都被封装在 API 之后，外部使用者只需要关心统一的查询接口。API 层支持多种交互模式：搜索模式（输入查询返回相关文档）、问答模式（输入问题返回生成的答案）、浏览模式（通过目录导航获取知识）和批量模式（用于数据导出和系统集成）。


API 设计需要遵循几个关键原则：幂等性——相同的请求应返回相同的结果；版本化——API 版本号确保向后兼容；降级策略——当某一层不可用时，API 能自动降级到更基础的检索模式；限流保护——防止高成本的 LLM 调用被滥用。


小结
    

  • 8 层架构从 Karpathy 3 层模型扩展而来，每层聚焦单一职责并通过标准接口通信
    • 

  • 原始文档层处理多格式归一化，存储层提供四种异构存储引擎
    • 

  • 索引层构建倒排、向量、图三种索引支撑混合检索
    • 

  • LLM 处理层通过流水线模式实现摘要、实体、关系和 QA 对的自动提取
    • 

  • 知识图谱层整合跨文档知识，缓存层通过多级策略优化查询性能
    • 

  • 目录层提供人类可读的导航结构和 AI 可理解的能力索引
    • 

  • API 层封装全部复杂性，支持搜索、问答、浏览和批量四种交互模式
    •
