多层知识库架构

核心概念

多层知识库架构是 Karpathy 提出的 3 层模型（Raw → LLM Doc → Index）的工程化扩展，将知识处理分解为 8 个独立层次。

  • 每层承担明确的职责，通过标准化层间接口通信
  • 设计哲学类似 OSI 网络模型——各层独立演进、灵活组合
graph TD
    L1[L1 原始文档层] --> L2[L2 存储层]
    L2 --> L3[L3 索引层]
    L3 --> L4[L4 LLM 处理层]
    L4 --> L5[L5 知识图谱层]
    L5 --> L6[L6 缓存层]
    L6 --> L7[L7 目录层]
    L7 --> L8[L8 API 层]

八层职责总览

层级 名称 核心职责 输入 输出
L1 原始文档层 多格式采集与解析 PDF/HTML/Markdown 统一文本 + 元数据
L2 存储层 持久化与版本管理 文本 + 元数据 存储对象引用
L3 索引层 多模态索引构建 存储对象 倒排/向量/图索引
L4 LLM 处理层 语义理解与增强 原始文本 摘要/实体/关系
L5 知识图谱层 语义网络构建 实体 + 关系 知识图谱
L6 缓存层 热点加速与降级 查询请求 缓存结果
L7 目录层 知识分类与导航 知识图谱 + 元数据 目录树 + 标签
L8 API 层 统一服务接口 外部请求 结构化响应

原始文档层与存储层

L1：数据入口与格式归一化

原始文档层负责从多种来源和格式中采集文档，并将其转换为统一的内部表示。

  • 支持格式：PDF、HTML、Markdown、Word、纯文本、Jupyter Notebook、代码文件
  • 核心挑战是格式归一化，不同格式的解析器处理完全不同的文档结构
格式 解析难点
PDF 布局分析和 OCR
HTML DOM 树和样式清理
Markdown 相对简单，需处理扩展语法

L1 核心数据模型

模型 关键字段
RawDocument source、format、rawContent、metadata
ParsedDocument title、sections（标题层级 + 内容）、metadata
Section heading、level、content、tables、codeBlocks 
RawDocument --解析--> ParsedDocument
metadata 贯穿两者:
  source / tags / language

L2：统一持久化

存储层提供统一的持久化能力，关键设计决策是版本管理策略——文档可能频繁更新，需要支持版本追溯和增量更新。

存储类型 技术选型 存储内容 一致性要求
对象存储 MinIO / S3 原始文件、文本块 最终一致
关系数据库 PostgreSQL 元数据、版本记录 强一致
向量数据库 Milvus / Qdrant Embedding 向量 最终一致
图数据库 Neo4j 知识图谱三元组 强一致

索引层与 LLM 处理层

L3：多索引构建

索引层是检索性能的关键，负责构建多种索引以支持不同的检索策略。

  • 倒排索引：支持 BM25 关键词检索
  • 向量索引（HNSW、IVF）：支持语义检索
  • 图索引：支持基于知识图谱的推理检索
  • 索引构建是离线 Pipeline 过程；文档更新时执行增量更新而非全量重建
graph LR
    D[文档入库] --> C[文本切分]
    C --> E1[Embedding]
    C --> E2[分词器]
    E1 --> V[向量索引]
    E2 --> I[倒排索引]
    D --> M[元数据提取]
    M --> F[过滤索引]
    V --> H[混合检索]
    I --> H
    F --> H

L4：LLM 深层语义处理

LLM 处理层利用大语言模型对文档进行深层语义处理，是整个架构中计算成本最高的部分，需要通过批处理和缓存策略控制成本。

  • 核心任务：自动摘要生成、实体和关系抽取、知识点结构化、问答对生成
  • 关键设计模式是流水线：摘要 → 实体抽取 → 关系抽取 → 质量检测
  • 每个阶段使用专门优化的 Prompt 和模型配置，确保输出稳定
LLMProcessor 四个方法:
  summarize        -> Summary
  extractEntities  -> Entity[]
  extractRelations -> Relation[]
  generateQAPairs  -> QAPair[]
输出模型 关键字段
Summary abstract、keyPoints、category
Entity name、type、aliases、sourceSpan
Relation subject、predicate、object、confidence
QAPair question、answer、supportingEvidence

知识图谱层与缓存层

L5：跨文档知识关联

知识图谱层将 LLM 处理层提取的实体和关系组织成语义网络，核心价值在于实现跨文档的知识关联。

操作 含义
实体对齐 将不同文档中指代相同事物的实体合并
关系推理 基于已有关系推导隐含关系
一致性检查 检测知识图谱中的矛盾和冲突

L6：多级缓存

缓存层在高频查询场景下至关重要——知识库查询通常符合幂律分布，少数热门查询占据大部分流量。

CacheLayer 接口:
  get(key)
  set(key, value, type)
  invalidate(pattern)
CacheType:
  query_result | embedding
  llm_response | graph_query
缓存级别 技术实现 容量 延迟 适用数据
L1 内存 Map / LRU 10K 条 <1ms 热门查询结果
L2 分布式 Redis 100K 条 1-5ms Embedding / LLM 响应
L3 磁盘 SQLite 1M 条 5-20ms 图查询结果

目录层与 API 层

L7：导航与能力索引

目录层为知识库提供人类可理解的导航结构——向量检索和知识图谱能处理精确查询，但用户常需通过浏览和导航发现知识。

  • 自动构建分类体系：图谱主题分类、标签多维分类、使用频率热门推荐
  • CLAUDE.md 式索引：以自然语言描述知识库的结构和内容覆盖范围
  • 让 AI Agent 快速理解知识库能力边界，决定何时及如何调用 API

L8：统一服务接口

API 层是知识库对外暴露的唯一接口，所有内部复杂性都被封装在 API 之后。

交互模式 行为
搜索模式 输入查询返回相关文档
问答模式 输入问题返回生成的答案
浏览模式 通过目录导航获取知识
批量模式 用于数据导出和系统集成 
graph TD
    S[搜索 API] --> R[路由层]
    Q[问答 API] --> R
    B[浏览 API] --> R
    BT[批量 API] --> R
    R --> C[缓存层]
    C --> KG[图谱层]
    KG --> IX[索引层]

API 设计原则

  • 幂等性——相同的请求应返回相同的结果
  • 版本化——API 版本号确保向后兼容
  • 降级策略——某一层不可用时自动降级到更基础的检索模式
  • 限流保护——防止高成本的 LLM 调用被滥用

小结

  • 8 层架构从 Karpathy 3 层模型扩展而来，每层聚焦单一职责并通过标准接口通信
  • 原始文档层处理多格式归一化，存储层提供四种异构存储引擎
  • 索引层构建倒排、向量、图三种索引支撑混合检索
  • LLM 处理层通过流水线模式实现摘要、实体、关系和 QA 对的自动提取
  • 知识图谱层整合跨文档知识，缓存层通过多级策略优化查询性能
  • 目录层提供人类可读的导航结构和 AI 可理解的能力索引
  • API 层封装全部复杂性，支持搜索、问答、浏览和批量四种交互模式
