知识结构化与语义标注

核心概念

知识结构化是将非结构化或半结构化的文本转换为机器可理解的语义表示的过程。

  • 在知识库架构中，这一阶段位于文档解析之后、索引构建之前，是 LLM 处理层的核心任务
  • 结构化的目标不是简单地提取关键词或标签
  • 而是构建包含实体、关系、属性和层级的语义网络
graph TD
    T[解析文本] --> NER[命名实体识别]
    NER --> RE[关系抽取]
    RE --> SA[属性标注]
    SA --> KS[Schema 映射]
    KS --> QV[质量验证]
    NER --> EL[实体链接]
    EL --> KG[知识图谱]
    RE --> KG

结构化任务总览

结构化任务 输入 输出 技术方案 准确率基线
命名实体识别 原始文本 实体 + 类型 + 位置 BERT-CRF / LLM 85-95%
关系抽取 文本 + 实体对 关系三元组 Joint Extraction / LLM 75-90%
属性标注 实体上下文 属性键值对 模板匹配 + LLM 80-90%
实体链接 实体 mention 规范化实体 ID Bi-Encoder + Cross-Encoder 80-92%
Schema 映射 自由文本 结构化 Schema LLM + 规则 70-85%

命名实体识别与类型系统

命名实体识别（NER）是知识结构化的第一步，负责从文本中定位和分类关键实体。

领域自适应类型系统

  • 通用 NER 模型识别的人名、地名、组织名在技术文档中价值有限
  • 编程语言、框架、API、算法名称和配置参数才是核心实体
  • 设计领域自适应的类型系统是 NER 质量的关键
类型层级 包含类型
技术概念 Algorithm、Pattern、Protocol
工具实体 Language、Framework、Library、Tool
系统实体 Service、API、Database、Queue
度量实体 Metric、Parameter、Config

类型定义示例

类型 示例 正则模式片段
Algorithm BM25、PageRank、Transformer [A-Z]\w*(Sort|Search)
Metric NDCG@10、P99 延迟、QPS P\d+|NDCG|MAP|QPS 
类型定义三要素:
  name     类型名
  examples 少样本示例
  patterns 辅助识别正则

LLM NER 与传统方法的差异

  • 核心区别在于 Few-Shot 能力：LLM 通过精心设计的 Prompt，无需大量标注数据即可识别新实体类型
  • LLM NER 输出格式不够稳定
  • 需要通过结构化输出约束（JSON Schema 或 Function Calling）保证格式一致性

关系抽取与知识三元组

关系抽取的目标是从文本中识别实体之间的语义关系，形成（主体, 关系, 客体）三元组。

技术文档中的典型关系

关系类型 示例
依赖关系 React 依赖 JSX
实现关系 BERT 实现了 Transformer 架构
优化关系 HNSW 优化了 ANN 检索速度
替代关系 Vite 替代 Webpack

两种抽取范式

  • 管道式：先 NER 再 RE，实现简单
  • 联合式：NER + RE 同时抽取，处理重叠关系（同一实体参与多个关系）表现更好，实现复杂度更高
graph LR
    T1[文本] --> N1[NER]
    N1 --> E1[实体对枚举]
    E1 --> R1[关系分类]
    T2[文本] --> J[Joint Model]
    J --> TR[三元组输出]

LLM 结构化 Prompt 抽取

在 LLM 时代，关系抽取可以通过结构化 Prompt 高效实现，关键是在 Prompt 中明确定义关系类型的边界和示例，避免模型生成过于泛化或不准确的关系。

三元组输出附带 confidence（置信度）和 evidence（原文证据），供后续验证。

ExtractedTriple:
  subject + relation + object
  confidence 置信度
  evidence   原文证据片段

关系 Schema 定义

关系 主体类型 客体类型 示例
DEPENDS_ON Framework/Library/Tool Framework/Library/Language Next.js 基于 React 构建
OPTIMIZES Algorithm/Tool/Framework Metric/Algorithm/Service HNSW 大幅提升 ANN 搜索速度

语义标注与元数据增强

语义标注超越了简单的关键词标签，为知识块添加多维度的结构化元数据。

标注维度

标注维度 标注方式 标签类型 用途
主题分类 分类模型 预定义层级标签 目录导航、过滤
内容类型 规则 + 分类 枚举类型 检索意图匹配
难度级别 LLM 1-5 级 个性化推荐
内容摘要 LLM 自由文本 检索片段展示
先验知识 LLM 概念列表 学习路径推荐
时效性 规则 时间标签 新鲜度过滤

两条自动标注技术路线

  • 分类模型标注（如 BERT 微调）：适合标签集固定的场景，准确率高且推理成本低
  • LLM 标注：适合标签集开放的场景，生成更细粒度和上下文相关的标签，但成本更高
  • 实践最优策略：两者结合——分类模型处理标准维度（主题、类型、难度），LLM 处理开放维度（摘要、先验知识、关联推荐）
SemanticAnnotation 字段:
  topic         主题标签
  contentType   tutorial 等枚举
  difficulty    1-5 级
  prerequisites 先验概念列表
  freshness     新鲜度标签
  method        model|llm|hybrid

Schema 映射与知识规范化

Schema 映射是将自由抽取的结构化信息对齐到预定义知识 Schema 的过程。

为什么需要规范化

  • 没有 Schema 映射，不同文档抽取出的知识无法互相关联和比较
  • 同一概念可能被表述为不同名称：「微服务架构」vs「Microservices」vs「微服务模式」

两个规范化层面

层面 做法
术语规范化 建立术语同义词表，将变体映射到规范名称
结构规范化 将不同格式和粒度的知识对齐到统一 Schema，如 API 描述必含端点、方法、参数和返回值 
normalizeEntity(entity, 同义词表):
  查表: 小写实体名 -> 规范名
  未命中则保留原名
  写入 normalizedName

小结

  • 知识结构化将非结构化文本转换为实体、关系、属性构成的语义网络
  • 领域自适应的实体类型系统是 NER 质量的基础，技术文档需要 Algorithm、Framework、API、Metric 等专属类型
  • 关系抽取通过管道式或联合式方法生成知识三元组，LLM + 结构化 Prompt 是当前最灵活的方案
  • 语义标注结合分类模型和 LLM，为知识块添加主题、类型、难度等多维元数据
  • Schema 映射和术语规范化确保跨文档知识的互操作性和一致性
  • 端到端的结构化管道需要在每个阶段内建质量验证，避免错误在管道中传播放大
