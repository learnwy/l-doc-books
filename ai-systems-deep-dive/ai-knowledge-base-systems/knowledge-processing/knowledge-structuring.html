知识结构化与语义标注

核心概念

知识结构化是将非结构化或半结构化的文本转换为机器可理解的语义表示的过程。在知识库架构中，这一阶段位于文档解析之后、索引构建之前，是 LLM 处理层的核心任务。结构化的目标不是简单地提取关键词或标签，而是构建包含实体、关系、属性和层级的语义网络。

命名实体识别与类型系统
命名实体识别（NER）是知识结构化的第一步，负责从文本中定位和分类关键实体。在技术文档场景下，实体类型系统需要根据领域进行定制。通用 NER 模型识别的人名、地名、组织名在技术文档中价值有限，而编程语言、框架、API、算法名称和配置参数才是核心实体。


设计领域自适应的类型系统是 NER 质量的关键。技术文档的实体类型层级通常包括：技术概念（Algorithm、Pattern、Protocol）、工具实体（Language、Framework、Library、Tool）、系统实体（Service、API、Database、Queue）、度量实体（Metric、Parameter、Config）。


interface EntityTypeSystem {
  readonly types: ReadonlyArray<EntityType>;
  readonly hierarchy: ReadonlyArray<TypeHierarchy>;
}

interface EntityType {
  readonly name: string;
  readonly description: string;
  readonly examples: ReadonlyArray<string>;
  readonly patterns: ReadonlyArray<string>;
}

interface TypeHierarchy {
  readonly parent: string;
  readonly children: ReadonlyArray<string>;
}

LLM 驱动的 NER 与传统 BERT-CRF 方法的核心区别在于 Few-Shot 能力。通过精心设计的 Prompt，LLM 可以在不需要大量标注数据的情况下识别新的实体类型。但 LLM NER 的输出格式不够稳定，需要通过结构化输出约束（JSON Schema 或 Function Calling）来保证输出格式的一致性。


关系抽取与知识三元组
关系抽取的目标是从文本中识别实体之间的语义关系，形成（主体, 关系, 客体）三元组。技术文档中的典型关系包括：依赖关系（React 依赖 JSX）、实现关系（BERT 实现了 Transformer 架构）、优化关系（HNSW 优化了 ANN 检索速度）、替代关系（Vite 替代 Webpack）。


关系抽取的两种主流范式是管道式（先 NER 再 RE）和联合式（NER + RE 同时抽取）。联合抽取模型在处理重叠关系（同一实体参与多个关系）时表现更好，但实现复杂度更高。


在 LLM 时代，关系抽取可以通过结构化 Prompt 高效实现。关键在于 Prompt 中需要明确定义关系类型的边界和示例，避免模型生成过于泛化或不准确的关系。

语义标注与元数据增强
语义标注超越了简单的关键词标签，为知识块添加多维度的结构化元数据。标注维度包括主题分类、难度级别、内容类型（教程、参考、概念解释、问题解答）、适用场景和先验知识要求。


自动标注的技术路线有两种：基于分类模型的标注和基于 LLM 的标注。分类模型（如 BERT 微调模型）适合标签集固定的场景，准确率高且推理成本低。LLM 标注适合标签集开放的场景，能够生成更细粒度和上下文相关的标签，但成本更高。


实践中最有效的策略是两者结合——使用分类模型处理标准维度（主题、类型、难度），使用 LLM 处理开放维度（摘要、先验知识、关联推荐）。

Schema 映射与知识规范化
Schema 映射是将自由抽取的结构化信息对齐到预定义知识 Schema 的过程。没有 Schema 映射，不同文档抽取出的知识就无法互相关联和比较——同一个概念可能在不同文档中被表述为不同的名称（如 "微服务架构" vs "Microservices" vs "微服务模式"）。


知识规范化涉及两个层面。术语规范化：建立术语同义词表，将变体映射到规范名称。结构规范化：将不同格式和粒度的知识对齐到统一的 Schema，例如确保所有的 API 描述都包含端点、方法、参数和返回值。


interface KnowledgeSchema {
  readonly entities: ReadonlyArray<EntitySchema>;
  readonly relations: ReadonlyArray<RelationSchema>;
  readonly constraints: ReadonlyArray<SchemaConstraint>;
}

interface EntitySchema {
  readonly type: string;
  readonly requiredProperties: ReadonlyArray<PropertyDef>;
  readonly optionalProperties: ReadonlyArray<PropertyDef>;
}

interface PropertyDef {
  readonly name: string;
  readonly valueType: 'string' | 'number' | 'boolean' | 'enum' | 'reference';
  readonly enumValues?: ReadonlyArray<string>;
}

interface SchemaConstraint {
  readonly type: 'uniqueness' | 'cardinality' | 'domain_range';
  readonly description: string;
  readonly validation: (triple: ExtractedTriple) => boolean;
}

const normalizeEntity = (entity: ExtractedEntity, synonymMap: Map<string, string>): ExtractedEntity => {
  const normalized = synonymMap.get(entity.text.toLowerCase()) ?? entity.text;
  return { ...entity, normalizedName: normalized };
};
小结
    

  • 知识结构化将非结构化文本转换为实体、关系、属性构成的语义网络
    • 

  • 领域自适应的实体类型系统是 NER 质量的基础，技术文档需要 Algorithm、Framework、API、Metric 等专属类型
    • 

  • 关系抽取通过管道式或联合式方法生成知识三元组，LLM + 结构化 Prompt 是当前最灵活的方案
    • 

  • 语义标注结合分类模型和 LLM，为知识块添加主题、类型、难度等多维元数据
    • 

  • Schema 映射和术语规范化确保跨文档知识的互操作性和一致性
    • 

  • 端到端的结构化管道需要在每个阶段内建质量验证，避免错误在管道中传播放大
    •
