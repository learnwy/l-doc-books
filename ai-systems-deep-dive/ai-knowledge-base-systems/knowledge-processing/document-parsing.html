文档解析与格式转换

核心概念

文档解析是知识库系统的第一道工序，负责将多种格式的原始文档转换为统一的内部结构化表示。

  • 这一环节的质量直接决定后续所有处理阶段的上限
  • 无论 LLM 多么强大，输入文本若丢失关键的表格数据或代码结构，后续的知识抽取和检索都无法弥补
graph LR
    P[PDF] --> U[统一文档模型]
    H[HTML] --> U
    M[Markdown] --> U
    D[DOCX] --> U
    C[Code] --> U
    U --> V[质量验证]

各格式解析对比

格式 解析难度 核心挑战 常用工具 信息保留率
Markdown 低 扩展语法（GFM、MDX） remark / unified 95%+
HTML 中 动态内容、样式噪声 cheerio / jsdom 80-90%
PDF 高 布局分析、多栏、OCR PyMuPDF / Unstructured 60-85%
DOCX 中 嵌入对象、样式映射 mammoth / docx 75-90%
代码文件 中 注释提取、结构识别 tree-sitter / AST 90%+

PDF 解析与布局分析

PDF 是知识库中最具挑战性的格式之一。

面向呈现的格式特性

  • PDF 存储的是「在坐标 (x, y) 处绘制字符 a」，而非「这是一个标题」这样的语义信息
  • 提取结构化文本需经历四个步骤：字符提取 → 行检测 → 段落识别 → 布局分析

多栏检测难题

  • 学术论文通常使用双栏排版
  • 解析器若不能正确识别栏边界，会将左右栏文字交错拼接，产生无意义文本
  • 传统管线使用深度学习布局检测模型（如 LayoutLM、DiT）识别页面区域；2024 年以来的主流方案则由视觉语言模型端到端完成布局理解与结构抽取（见下节「VLM 原生解析范式」）
PageRegion 字段 含义
type title / text / table / figure 等
bbox 区域坐标（x、y、宽、高）
confidence 布局模型置信度
readingOrder 阅读顺序编号 
parsePDF(buffer):
  pages   = extractPages(buffer)
  layouts = analyzeLayout(每页)
  regions = 过滤页眉页脚
          + 按 readingOrder 排序
  return assembleDocument(regions)

OCR 与 LLM 后处理

  • OCR 是处理扫描版 PDF 的必要手段
  • 传统 OCR 引擎（Tesseract 5.x、PaddleOCR）仍可承担多语言混合识别，但识别准确率受图像质量、字体和排版复杂度影响
  • 2024 年起主流路线转向视觉语言模型直接「读图出文本」——AI2 的 olmOCR 用 VLM 解析 PDF，在公式、表格与复杂排版上显著优于传统 OCR 管线（arXiv:2502.18443）
  • 关键文档建议在 OCR 后增加 LLM 后处理步骤——利用上下文理解纠正常见 OCR 错误；若采用下节的 VLM 原生解析方案，这一纠错通常已内建于模型推理本身

VLM 原生解析范式

2024 年以来，文档解析的主流范式正从「布局检测模型 + OCR 引擎的多阶段流水线」转向视觉语言模型（VLM）原生解析：将页面渲染为图像后直接输入视觉语言模型，一步输出结构化的 Markdown 或 JSON。

工具 开发方 技术路线
MinerU OpenDataLab 布局理解与内容抽取结合的端到端开源解析工具
Docling IBM 文档理解模型 + 统一 DoclingDocument 文档对象模型
olmOCR AI2 视觉语言模型直出纯文本，面向大规模语料构建
Marker 开源社区 深度学习模型将 PDF 高保真转换为 Markdown
  • 核心优势：表格还原、阅读顺序判断和公式识别不再依赖多阶段规则拼接，而是利用 VLM 的跨模态理解一次完成，中间误差不再逐级传播
  • MinerU 面向精确内容抽取场景，支持公式转 LaTeX、表格转 HTML/Markdown 等富结构输出（arXiv:2409.18839）
  • IBM Docling 将解析结果统一为带类型标注的文档对象模型，下游索引与检索可直接消费（arXiv:2408.09869）；olmOCR 则证明该范式可在数亿页级语料上经济运行，从网络 PDF 中解锁数万亿 token 的高质量训练文本（arXiv:2502.18443）
  • 实践建议：新建知识库的 PDF 解析层应优先评估 VLM 原生方案；LayoutLM/DiT + OCR 流水线作为成本敏感或无 GPU 批量场景的备选保留

HTML 清洗与结构提取

HTML 解析的核心挑战不在于格式转换，而在于噪声过滤。

噪声来源与提取策略

  • 噪声元素：导航栏、侧边栏、广告、版权声明、Cookie 弹窗
  • 有效的 HTML 清洗需要准确识别正文区域并剥离噪声
提取策略 原理
DOM 启发式 Readability 算法，分析文本密度和标签特征
文本密度统计 基于统计的正文区域判定
机器学习分类 训练分类器识别正文节点

Readability 算法通过评估每个 DOM 节点作为正文的可能性，是最广泛使用的方案。

清洗实现

cleanHTML(html, config):
  dom = parseDOM(html)
  移除 nav/header/footer
     + sidebar/ads/script/style
  保护 pre, code, table 元素
  main = extractMainContent(dom)
  return { title, sections,
           cleanedRatio = main长度/dom长度 }

SPA 动态渲染处理

  • 单页应用（SPA）页面无法通过传统 HTML 解析获取动态渲染内容
  • 需使用无头浏览器（Headless Chrome）先渲染页面，再提取渲染后的 DOM
  • 无头浏览器资源消耗远高于静态解析，通常只在检测到需要 JavaScript 渲染时启用

文本切分策略

文本切分（Text Chunking）是将长文档分割为适合检索和 LLM 处理的小段落的过程。切分策略直接影响检索质量——过大的块检索精度低，过小的块缺乏上下文。

四种切分策略对比

策略 实现方式 优势 劣势 适用场景
固定大小 按 token 数等分 实现简单 可能切断语义 格式统一的文本
重叠滑动 固定窗口 + 重叠 减少信息丢失 存储冗余 通用文本
语义切分 按段落/章节边界 语义完整 块大小不均 结构化文档
递归切分 先大后小递归 灵活自适应 实现较复杂 混合格式文档

递归切分

递归切分长期是工业界的默认基线策略。

  • 首先尝试按最大的语义边界（章节标题）切分
  • 结果块仍然太大时，在块内按次级边界（段落）继续切分
  • 依此递归，直到所有块都在目标大小范围内
recursiveChunk(text, config, 层级):
  若 tokens(text) <= targetSize:
    返回 [整块]
  sep = separators[层级]
  按 sep 切分并累积片段
  片段超过 maxSize 时:
    递归到下一层级分隔符
  最后 addOverlap(chunks)

长上下文时代的切分新范式

2024-2025 年，检索架构围绕三类新技术演进，切分从孤立的预处理步骤变为可被上下文增强的环节：

  • Contextual Retrieval（Anthropic，2024）：每个切片入库前，先用 LLM 生成一段置于其前的上下文说明（该切片在整篇文档中的位置与作用），再行嵌入与索引。Anthropic 报告上下文增强嵌入结合上下文摘要可将检索失败率降低 49%，再配合重排序降低 67%（anthropic.com/news/contextual-retrieval）
  • Late Chunking（Jina AI）：先用长上下文 Embedding 模型对整篇文档做 token 级编码，再按块边界对 token 向量池化得到块向量——每个块向量因此携带全文语境，缓解小块语义残缺问题（arXiv:2409.04701）
  • Parent-Child 分层索引（small-to-big）：用小块（子块）检索保证精度，命中后返回其所属大块（父块）供生成保证上下文完整，将「检得准」与「答得好」解耦

三类方案的共同思路：切片粒度只需服务于检索精度，生成所需的完整上下文通过分层映射或上下文增强补回，不再要求单个切片自含全部信息。

代码与结构化数据解析

代码文件和结构化数据（JSON、YAML、CSV）需要专门的解析策略。

AST 解析与粒度映射

  • 代码解析的目标不仅是提取文本，还要保留结构信息——函数签名、类层级、导入关系
  • 基于 AST（抽象语法树）的解析器能够准确识别代码结构
代码层次 知识库映射
文件级别 一个文档
函数/类级别 知识块
签名和注释 知识元数据 
Declaration 结构:
  kind  function|class|interface
  name + signature
  docComment 文档注释
  children   嵌套声明

Schema 信息保留

  • JSON 文件若不了解其 Schema，就无法准确理解字段的含义
  • 解析时应同时保存 Schema 信息（通过 JSON Schema 或从样本数据推断）
  • 以便在检索和问答时提供准确的字段说明

小结

  • 文档解析是知识库质量的第一道关卡，信息保留率直接决定后续处理的上限
  • PDF 解析的主流路线已从「布局分析 + OCR + 后处理」的多阶段流水线转向 MinerU/Docling/olmOCR 类 VLM 原生解析，传统管线保留为成本敏感场景的备选
  • HTML 清洗的核心是正文提取和噪声过滤，Readability 算法是最广泛的基线
  • 递归切分是经典基线；Contextual Retrieval、Late Chunking 与 Parent-Child 分层索引是当前切分质量的三个主要增强方向
  • 代码解析需要基于 AST 保留结构信息，将函数/类映射为知识块
  • 所有解析结果都应包含质量评分和置信度，为后续环节提供可靠性信号
