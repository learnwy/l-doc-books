文档解析与格式转换

核心概念

文档解析是知识库系统的第一道工序，负责将多种格式的原始文档转换为统一的内部结构化表示。这一环节的质量直接决定了后续所有处理阶段的上限——无论 LLM 多么强大，如果输入的文本丢失了关键的表格数据或代码结构，后续的知识抽取和检索都无法弥补。

PDF 解析与布局分析
PDF 是知识库中最具挑战性的格式之一。与 HTML 或 Markdown 不同，PDF 是一种面向呈现的格式——它存储的是「在坐标 (x, y) 处绘制字符 a」，而非「这是一个标题」这样的语义信息。从 PDF 中提取结构化文本需要经历字符提取、行检测、段落识别和布局分析四个步骤。


布局分析的核心难题是多栏检测。学术论文通常使用双栏排版，如果解析器不能正确识别栏边界，就会将左右栏的文字交错拼接，产生无意义的文本。现代解析方案通常使用基于深度学习的布局检测模型（如 LayoutLM、DiT）来识别页面中的不同区域。


interface PDFParseOptions {
  readonly ocrEnabled: boolean;
  readonly ocrLanguages: ReadonlyArray<string>;
  readonly layoutModel: 'rule-based' | 'ml-based';
  readonly tableDetection: boolean;
  readonly imageExtraction: boolean;
  readonly maxPages?: number;
}

interface PageLayout {
  readonly pageNumber: number;
  readonly width: number;
  readonly height: number;
  readonly regions: ReadonlyArray<PageRegion>;
}

interface PageRegion {
  readonly type: 'title' | 'text' | 'table' | 'figure' | 'code' | 'header' | 'footer';
  readonly bbox: BoundingBox;
  readonly content: string;
  readonly confidence: number;
  readonly readingOrder: number;
}

interface BoundingBox {
  readonly x: number;
  readonly y: number;
  readonly width: number;
  readonly height: number;
}

const parsePDF = async (buffer: Buffer, options: PDFParseOptions): Promise<ParsedDocument> => {
  const pages = await extractPages(buffer);
  const layouts = await Promise.all(pages.map((page) => analyzeLayout(page, options)));
  const regions = layouts.flatMap((layout) =>
    layout.regions
      .filter((r) => r.type !== 'header' && r.type !== 'footer')
      .sort((a, b) => a.readingOrder - b.readingOrder),
  );
  return assembleDocument(regions);
};
OCR（光学字符识别）是处理扫描版 PDF 的必要手段。现代 OCR 引擎（如 Tesseract 5.x、PaddleOCR）支持多语言混合识别，但识别准确率受图像质量、字体和排版复杂度影响。对于关键文档，建议在 OCR 后增加一个 LLM 后处理步骤——利用语言模型的上下文理解能力来纠正常见的 OCR 错误。


HTML 清洗与结构提取
HTML 解析的核心挑战不在于格式转换，而在于噪声过滤。网页中包含大量与正文内容无关的元素——导航栏、侧边栏、广告、版权声明、Cookie 弹窗等。有效的 HTML 清洗需要准确识别正文区域并剥离噪声。


主流的正文提取策略包括基于 DOM 结构的启发式方法（如 Readability 算法）、基于文本密度的统计方法和基于机器学习的分类方法。Readability 算法通过分析 DOM 节点的文本密度和标签特征来评估每个节点作为正文的可能性，是最广泛使用的方案。


interface HTMLCleanConfig {
  readonly removeNavigation: boolean;
  readonly removeSidebar: boolean;
  readonly removeAds: boolean;
  readonly preserveCodeBlocks: boolean;
  readonly preserveTables: boolean;
  readonly preserveImages: boolean;
  readonly maxDepth: number;
}

interface CleanResult {
  readonly title: string;
  readonly content: string;
  readonly sections: ReadonlyArray<Section>;
  readonly metadata: Record<string, string>;
  readonly cleanedRatio: number;
}

const cleanHTML = (html: string, config: HTMLCleanConfig): CleanResult => {
  const dom = parseDOM(html);
  removeBySelectors(dom, [
    'nav',
    'header',
    'footer',
    '.sidebar',
    '.advertisement',
    '.cookie-banner',
    'script',
    'style',
    'noscript',
  ]);
  if (config.preserveCodeBlocks) {
    protectElements(dom, 'pre, code');
  }
  if (config.preserveTables) {
    protectElements(dom, 'table');
  }
  const mainContent = extractMainContent(dom);
  return {
    title: extractTitle(dom),
    content: mainContent.textContent,
    sections: extractSections(mainContent),
    metadata: extractMetadata(dom),
    cleanedRatio: mainContent.textContent.length / dom.textContent.length,
  };
};
对于单页应用（SPA）生成的页面，传统的 HTML 解析无法获取动态渲染的内容。这种场景需要使用无头浏览器（Headless Chrome）先渲染页面，再提取渲染后的 DOM 结构。但无头浏览器的资源消耗远高于静态解析，因此通常只在检测到页面需要 JavaScript 渲染时才启用。


文本切分策略
文本切分（Text Chunking）是将长文档分割为适合检索和 LLM 处理的小段落的过程。切分策略直接影响检索质量——过大的块检索精度低，过小的块缺乏上下文。

递归切分是目前工业界最常用的策略。它首先尝试按最大的语义边界（章节标题）切分，如果结果块仍然太大，则在块内按次级边界（段落）继续切分，依此递归直到所有块都在目标大小范围内。


interface ChunkConfig {
  readonly targetSize: number;
  readonly maxSize: number;
  readonly overlapSize: number;
  readonly separators: ReadonlyArray<string>;
}

interface TextChunk {
  readonly content: string;
  readonly startOffset: number;
  readonly endOffset: number;
  readonly tokenCount: number;
  readonly metadata: ChunkMetadata;
}

interface ChunkMetadata {
  readonly sectionTitle: string;
  readonly chunkIndex: number;
  readonly totalChunks: number;
  readonly hasOverlap: boolean;
}

const recursiveChunk = (text: string, config: ChunkConfig, separatorIndex = 0): ReadonlyArray<TextChunk> => {
  if (countTokens(text) <= config.targetSize) {
    return [createChunk(text, 0, text.length)];
  }
  const separator = config.separators[separatorIndex];
  if (!separator || separatorIndex >= config.separators.length) {
    return fixedSizeChunk(text, config);
  }
  const parts = text.split(separator);
  const chunks: TextChunk[] = [];
  let currentChunk = '';
  for (const part of parts) {
    if (countTokens(currentChunk + separator + part) > config.maxSize) {
      if (currentChunk) chunks.push(createChunk(currentChunk, 0, currentChunk.length));
      if (countTokens(part) > config.maxSize) {
        chunks.push(...recursiveChunk(part, config, separatorIndex + 1));
        currentChunk = '';
      } else {
        currentChunk = part;
      }
    } else {
      currentChunk = currentChunk ? currentChunk + separator + part : part;
    }
  }
  if (currentChunk) chunks.push(createChunk(currentChunk, 0, currentChunk.length));
  return addOverlap(chunks, config.overlapSize);
};
代码与结构化数据解析
代码文件和结构化数据（JSON、YAML、CSV）需要专门的解析策略。代码解析的目标不仅是提取文本，还要保留代码的结构信息——函数签名、类层级、导入关系等。基于 AST（抽象语法树）的解析器能够准确地识别代码结构。


对于代码仓库类的知识源，有效的解析策略是将代码的不同层次映射为知识库中的不同粒度。文件级别对应知识库中的一个文档，函数/类级别对应知识块，函数签名和注释对应知识元数据。这种映射关系使得代码知识也能被有效检索。


结构化数据的解析相对简单，但需要注意的是 Schema 信息的保留。一个 JSON 文件如果不了解其 Schema，就无法准确理解字段的含义。解析时应同时保存 Schema 信息（通过 JSON Schema 或从样本数据推断），以便在检索和问答时提供准确的字段说明。


interface CodeParseResult {
  readonly language: string;
  readonly imports: ReadonlyArray<ImportDeclaration>;
  readonly declarations: ReadonlyArray<Declaration>;
  readonly comments: ReadonlyArray<Comment>;
  readonly structure: CodeStructure;
}

interface Declaration {
  readonly kind: 'function' | 'class' | 'interface' | 'type' | 'variable';
  readonly name: string;
  readonly signature: string;
  readonly docComment?: string;
  readonly startLine: number;
  readonly endLine: number;
  readonly children: ReadonlyArray<Declaration>;
}

interface CodeStructure {
  readonly exports: ReadonlyArray<string>;
  readonly dependencies: ReadonlyArray<string>;
  readonly complexity: number;
}
小结
    

  • 文档解析是知识库质量的第一道关卡，信息保留率直接决定后续处理的上限
    • 

  • PDF 解析需要布局分析 + OCR + LLM 后处理的多阶段流水线
    • 

  • HTML 清洗的核心是正文提取和噪声过滤，Readability 算法是最广泛的基线
    • 

  • 递归切分策略按语义边界层级逐步细化，是工业界最常用的文本切分方案
    • 

  • 代码解析需要基于 AST 保留结构信息，将函数/类映射为知识块
    • 

  • 所有解析结果都应包含质量评分和置信度，为后续环节提供可靠性信号
    •
