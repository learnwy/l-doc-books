特征存储与复用

核心概念

特征存储（Feature Store）是机器学习基础设施中的核心组件，负责特征的集中管理、版本控制、在线/离线服务和跨团队复用。它解决了特征工程中最普遍的痛点：训练-服务特征不一致（Training-Serving Skew）、特征重复计算和特征发现困难。

graph TD
    A[数据源] --> B[特征计算管线]
    B --> C[特征存储]
    C --> D[离线存储]
    C --> E[在线存储]
    D --> F[模型训练]
    E --> G[在线推理]
    C --> H[特征注册中心]
    H --> I[特征发现与搜索]
    H --> J[特征血缘追踪]
    H --> K[特征版本管理]
    F --> L[模型]
    L --> G
特征存储组件 职责 技术选型 性能要求
离线存储 历史特征、训练数据 数据湖/数据仓库 高吞吐、低成本
在线存储 实时特征服务 Redis/DynamoDB 低延迟（< 10ms）
特征注册中心 元数据、血缘、版本 数据库 + API 一致性
特征计算引擎 批量/流式特征生成 Spark/Flink 高吞吐
特征服务 API 在线/离线特征获取 gRPC/REST 低延迟、高可用

双存储架构

特征存储的核心设计挑战在于同时满足训练和推理两种截然不同的访问模式。离线存储服务于批量训练，强调吞吐量和历史数据完整性；在线存储服务于实时推理，强调延迟和可用性。

离线存储 以时间分区的方式保存历史特征快照，支持时间旅行（Point-in-Time Join）查询：

interface OfflineStore {
  write(features: FeatureBatch): Promise<void>;
  readTrainingData(config: TrainingDataConfig): Promise<TrainingDataset>;
  pointInTimeJoin(entities: EntityTimestamp[], featureViews: string[]): Promise<JoinedDataset>;
}

interface TrainingDataConfig {
  entityDf: EntityDataFrame;
  featureViews: string[];
  timestampColumn: string;
  startDate: Date;
  endDate: Date;
  ttl?: number;
}

interface EntityTimestamp {
  entityId: string;
  eventTimestamp: Date;
}

在线存储 维护每个实体的最新特征值，支持毫秒级查询：

interface OnlineStore {
  writeLatest(entityKey: string, features: FeatureRow): Promise<void>;
  readLatest(entityKeys: string[], featureNames: string[]): Promise<Map<string, FeatureRow>>;
  batchRead(requests: OnlineReadRequest[]): Promise<OnlineReadResponse[]>;
}

interface FeatureRow {
  entityId: string;
  features: Record<string, FeatureValue>;
  eventTimestamp: Date;
  createdTimestamp: Date;
}

type FeatureValue =
  | { type: 'int64'; value: number }
  | { type: 'float64'; value: number }
  | { type: 'string'; value: string }
  | { type: 'bytes'; value: Uint8Array }
  | { type: 'float_list'; value: number[] };

Training-Serving Skew 是特征存储要解决的首要问题：

graph LR
    A[特征定义] --> B[批量计算]
    A --> C[流式计算]
    B --> D[离线存储]
    C --> E[在线存储]
    D --> F[训练管线]
    E --> G[推理服务]
    F --> H{特征一致?}
    G --> H
    H -->|一致| I[模型表现正常]
    H -->|不一致| J[Training-Serving Skew]
    J --> K[性能下降]
Skew 类型 根因 检测方法 预防策略
计算 Skew 训练和推理用不同代码计算特征 单元测试对比 统一特征定义
数据 Skew 训练用历史数据，推理用实时数据 分布对比监控 Point-in-Time Join
时间 Skew 训练时使用了未来信息 时间戳校验 严格时间过滤
版本 Skew 模型期望 V1 特征，服务提供 V2 版本绑定检查 特征版本锁定

特征定义与注册

特征注册中心是特征存储的元数据层，统一管理特征的定义、血缘和版本信息。

特征视图（Feature View） 是特征的逻辑组织单元，将相关特征按实体和数据源分组：

interface FeatureViewDefinition {
  name: string;
  description: string;
  entities: EntityDefinition[];
  features: FeatureDefinition[];
  source: DataSourceConfig;
  ttl: number;
  tags: Record<string, string>;
  owner: string;
  createdAt: Date;
  version: string;
}

interface EntityDefinition {
  name: string;
  valueType: ValueType;
  description: string;
  joinKeys: string[];
}

interface FeatureDefinition {
  name: string;
  valueType: ValueType;
  description: string;
  transformation?: TransformationConfig;
  validationRules: ValidationRule[];
  monitoring: MonitoringConfig;
}

type ValueType = 'int64' | 'float64' | 'string' | 'bool' | 'bytes' | 'float_list' | 'int_list';

interface TransformationConfig {
  type: 'sql' | 'python' | 'aggregation';
  expression: string;
  windowSize?: number;
  dependencies: string[];
}

特征搜索与发现 帮助数据科学家快速找到已有特征，避免重复开发：

interface FeatureRegistry {
  register(view: FeatureViewDefinition): Promise<void>;
  search(query: FeatureSearchQuery): Promise<FeatureSearchResult[]>;
  getLineage(featureName: string): Promise<FeatureLineage>;
  listVersions(featureName: string): Promise<FeatureVersion[]>;
  getUsage(featureName: string): Promise<FeatureUsageStats>;
}

interface FeatureSearchQuery {
  keyword?: string;
  entity?: string;
  owner?: string;
  tags?: Record<string, string>;
  valueType?: ValueType;
  minUsageCount?: number;
  createdAfter?: Date;
}

interface FeatureUsageStats {
  totalModels: number;
  totalPipelines: number;
  lastAccessTime: Date;
  avgDailyReads: number;
  consumers: ConsumerInfo[];
}

特征计算与物化

特征计算将原始数据转化为特征值并写入存储。根据数据的时效性需求，计算模式分为批量和流式两种。

批量物化 定期执行，将历史数据批量计算并写入离线和在线存储：

sequenceDiagram
    participant S as 调度器
    participant C as 计算引擎
    participant D as 数据源
    participant O as 离线存储
    participant N as 在线存储

    S->>C: 触发批量物化任务
    C->>D: 读取原始数据
    D-->>C: 返回数据批次
    C->>C: 执行特征变换
    C->>O: 写入历史特征
    C->>N: 更新最新特征值
    C-->>S: 物化完成报告
    S->>S: 更新物化元数据

流式物化 对实时数据进行在线特征计算，适用于需要秒级更新的场景：

interface MaterializationConfig {
  mode: 'batch' | 'streaming' | 'hybrid';
  schedule?: CronExpression;
  batchConfig?: {
    sourceQuery: string;
    partitionKey: string;
    incrementalColumn?: string;
  };
  streamConfig?: {
    sourceTopic: string;
    processingTimeWindow: number;
    watermarkDelay: number;
    checkpointInterval: number;
  };
  sinkConfig: {
    offlineStore: boolean;
    onlineStore: boolean;
    backfillOnDeploy: boolean;
  };
}

interface MaterializationJob {
  id: string;
  featureView: string;
  config: MaterializationConfig;
  status: 'running' | 'completed' | 'failed';
  metrics: {
    processedRows: number;
    failedRows: number;
    latencyP99: number;
    throughput: number;
  };
}
物化模式 数据延迟 计算成本 一致性 适用场景
纯批量 小时-天级 低 强 日报特征、离线分析
纯流式 秒-分钟级 高 最终一致 实时推荐、欺诈检测
混合模式 批量+实时 中等 混合 大多数生产场景

新形态：向量化特征与检索服务

随着 embedding 即特征成为主流实践，特征存储正在从"标量键值服务"扩展为"向量检索服务"。这一新形态带来三处结构性变化：

特征类型扩展：稠密向量成为常见特征值类型（对应前文 FeatureValue 的 float_list），一个 embedding 特征动辄上千维，显著改变在线存储的容量与带宽预算；维度截断、量化（PQ/SQ）等压缩手段开始出现在特征物化管线中。

在线存储承担 ANN 检索：传统在线存储只回答"取实体 X 的特征向量"，新形态下还要回答"找出与查询向量最相似的 K 个实体"。开源特征库 Feast 已加入向量检索支持（当前处于 Alpha 阶段）并支持以 Qdrant 作为向量在线存储（github.com/feast-dev/feast），专用向量数据库（Qdrant/Milvus/Pinecone 类）则经常作为 embedding 特征的在线存储后端与特征存储并置。

graph TD
    A[上游 Encoder<br/>文本/图像/行为] --> B[特征计算管线]
    B --> C[特征存储]
    C --> D[离线存储<br/>历史向量快照]
    C --> E[在线存储<br/>标量 KV + ANN 索引]
    E --> F[推理时点查<br/>get_online_features]
    E --> G[相似检索<br/>vector search top-K]
    D --> H[训练数据集<br/>Point-in-Time Join]
    G --> I[召回/RAG/相似推荐]

一致性与血缘的新问题：embedding 特征引入了两类新的 skew 来源——编码器版本 skew（模型升级后新旧向量空间不可比，必须像特征版本一样绑定 encoder 版本号）与索引重建延迟（ANN 索引落后于最新向量写入时的检索漂移）。治理上要求把"encoder 版本 + 维度 + 距离度量"登记为特征元数据的必填字段。

特征复用与治理

特征复用是特征存储的核心价值之一。当组织中多个团队和模型共享相同的特征定义和计算逻辑时，能显著减少重复开发、降低不一致风险。

特征复用模式 从简单的共享读取到复杂的特征市场：

interface FeatureGovernance {
  accessControl: {
    featureView: string;
    permissions: Permission[];
  }[];
  qualityMonitoring: {
    featureView: string;
    checks: QualityCheck[];
    alertConfig: AlertConfig;
  }[];
  retentionPolicy: {
    featureView: string;
    offlineTTL: number;
    onlineTTL: number;
    archivePolicy: ArchivePolicy;
  }[];
  costTracking: {
    featureView: string;
    computeCost: number;
    storageCost: number;
    consumers: string[];
  }[];
}

interface QualityCheck {
  metric: 'null_rate' | 'value_range' | 'distribution_drift' | 'freshness';
  threshold: number;
  alertSeverity: 'critical' | 'warning' | 'info';
}

特征血缘追踪 记录特征从数据源到模型消费的完整链路，当上游数据变更时能快速评估影响范围：

治理维度 具体内容 工具/方法 价值
访问控制 谁可以读写哪些特征 RBAC/ABAC 数据安全
质量监控 空值率、分布漂移、延迟 自动化检查 + 告警 模型可靠性
成本追踪 计算和存储成本归属 按特征视图统计 资源优化
生命周期 特征的创建、废弃和归档 自动化策略 存储治理
文档化 特征含义、计算逻辑、使用方式 自动生成 + 人工补充 可发现性

  • 特征存储通过双存储架构（离线+在线）统一服务训练和推理需求
  • Training-Serving Skew 是特征工程中最常见的问题，统一特征定义和 Point-in-Time Join 是核心预防手段
  • 特征注册中心实现特征的搜索发现和复用，避免跨团队重复开发
  • 批量和流式物化分别满足离线和实时特征更新需求，混合模式是生产最优解
  • embedding 特征推动特征存储向向量检索服务演进：在线存储承担 ANN 查询，Feast 等开源方案已提供向量检索支持
  • embedding 特征需将 encoder 版本、维度和距离度量登记为元数据必填项，防止编码器版本 skew 与索引重建漂移
  • 特征治理涵盖访问控制、质量监控、成本追踪和生命周期管理
  • 特征复用的价值随组织规模增长而指数级提升，是 ML 平台成熟度的关键标志
