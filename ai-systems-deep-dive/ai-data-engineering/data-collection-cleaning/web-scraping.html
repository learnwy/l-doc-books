Web 爬虫与数据采集

核心概念

Web 爬虫与数据采集是 AI 数据工程的第一个环节，负责从互联网和各种数据源中获取原始数据。在 AI/ML 项目中，高质量的训练数据往往决定了模型效果的天花板。数据采集不仅仅是"下载网页"那么简单，它涉及反爬对抗、增量采集、分布式调度和数据质量初筛等系统性工程问题。2023 年以来，生成式 AI 重塑了抓取生态：OpenAI GPTBot 等 AI 爬虫通过 robots.txt 专属 token 与站长协商抓取授权，站点侧的 AI 反抓取管理成为新常态；采集目标也从页面字段转向 LLM 可用的训练语料，Markdown 化采集与 LLM 结构化抽取成为与传统 CSS/XPath 解析并列的主流路径。

数据采集的核心原则是：在法律和道德框架内，以最高效率获取最高质量的数据。

一个生产级爬虫系统需要模块化的架构设计，各组件职责清晰且可独立扩展。

反爬对抗策略

现代网站部署了多层反爬机制，爬虫需要针对性地应对。

Cookie/Session 会话状态验证 模拟登录、Session 管理

验证码 人机验证 OCR 识别、打码服务

  pool: string[];
  rotationStrategy: 'round-robin' | 'random' | 'least-used';

const createRequestWithRetry = async (
  url: string,
  config: CrawlerConfig,
  proxyConfig: ProxyConfig,
): Promise<CrawlResult> => {
  const maxRetries = 3;

  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const proxy = selectProxy(proxyConfig);
    const delay = config.requestInterval * (1 + Math.random() * 0.5);
    await sleep(delay);

    try {
      const response = await fetch(url, {
        headers: {
          'User-Agent': getRandomUA(),
          'Accept-Language': 'zh-CN,zh;q=0.9,en;q=0.8',
        },
      });

      if (response.status === 429) {
        await sleep(delay * Math.pow(2, attempt));
        continue;
      }

      return parseResponse(url, response);
    } catch {
      markProxyFailed(proxy, proxyConfig);
    }
  }

  throw new Error(`Failed to crawl ${url} after ${maxRetries} attempts`);
};

AI 抓取生态：robots 协商、LLM 抽取与语料化采集

生成式 AI 让抓取从纯粹的"爬虫 vs 反爬"对抗，演化为三层并存的生态：授权协商、语义抽取和面向语料的采集。

AI 爬虫的 robots 管理（双向视角） 主流 AI 厂商的爬虫不再只遵循笼统的 User-agent: * 规则，而是提供专属 robots token 让站长精细控制：

  • OpenAI 官方 bots 文档定义了 GPTBot 等一组 robots.txt 标签，站长可以用它们管理自己内容是否被用于训练 OpenAI 的生成式模型或触发实时检索（platform.openai.com/docs/bots）
  • Common Crawl 的 CCBot 提供 robots.txt 退出通道（User-agent: CCBot / Disallow: /），并以反向 DNS 验证 + 公开 IP 段 JSON 的方式帮助站长识别假冒 CCBot 的流量（commoncrawl.org/ccbot）
  • Google 在官方爬虫文档中区分了用于搜索索引与用于 AI 训练/grounding 的爬虫控制方式，站长可分别设置

作为采集方：自建 AI 数据管线时应声明真实 UA、遵守目标站的 AI 爬虫规则、在 robots.txt 框架内工作；作为站长方：为内容资产配置 AI 爬虫授权策略（全量允许 / 训练禁止 / 完全禁止）已成为 SEO 与数据治理的标准动作。双方都依赖"身份可验证"——UA 声明 + 反向 DNS 校验是当前识别 AI 爬虫的通行做法。

LLM 结构化抽取替代手写解析 传统路径要求为每个站点手写 CSS 选择器/XPath，页面改版即失效。LLM 抽取将"理解页面结构"交给模型：输入清洗后的页面文本或 DOM，配合 JSON Schema 约束输出，即可零样本完成字段抽取。代价是每页一次 LLM 调用的成本与延迟，因此生产中常用混合策略——高频站点保留手写解析器，长尾站点走 LLM 抽取，用小样本金标集对比两者的字段级准确率再路由：

graph TD
    A[原始页面] --> B[正文/DOM 清洗]
    B --> C{站点类型}
    C -->|高频核心站点| D[手写 CSS/XPath 解析器]
    C -->|长尾/新站点| E[LLM + JSON Schema 抽取]
    D --> F[结构化记录]
    E --> F
    F --> G{抽样校验}
    G -->|字段准确率达标| H[入库]
    G -->|不达标| I[人工修复解析器 / 调整 Prompt]
    I --> D
    I --> E
interface LlmExtractionTask {
  pageContent: string;
  schema: Record<string, 'string' | 'number' | 'boolean' | 'string[]'>;
  instruction: string;
  fallbackParser?: string;
}

interface ExtractionRoute {
  route(domain: string, page: string): 'handwritten' | 'llm';
}

async function extractStructured(
  task: LlmExtractionTask,
  route: ExtractionRoute,
): Promise<Record<string, unknown>> {
  if (route.route(parseDomain(task.pageContent), task.pageContent) === 'handwritten' && task.fallbackParser) {
    return runLegacyParser(task.fallbackParser, task.pageContent);
  }
  return callLlmWithSchema({
    prompt: `${task.instruction}\n\n${task.pageContent}`,
    schema: task.schema,
  });
}

面向语料的 Markdown 化采集 当目标是 LLM 训练/RAG 语料而非数据库记录时，采集产物从"字段表"变成"干净文档"。以 Firecrawl 为代表的一类服务直接把网页转为 Markdown/清洁文本输出（firecrawl.dev），省去模板维护；通用做法是"正文抽取 → 转 Markdown → 去噪（导航/广告/脚本残留）→ 语言识别 → 去重"，Markdown 的标题层级和列表结构天然保留了文档语义，比纯文本更利于后续切分与检索。

增量采集与变更检测

对于需要持续更新的数据源，增量采集比全量重新采集效率高出数十倍。

WebSocket 推送 实时数据源 零延迟 需要维护连接

数据采集的合规与伦理

数据采集必须在法律和伦理框架内进行，这不仅是道德要求，也是业务可持续性的保障。

合规要求 具体措施 风险等级
robots.txt 遵守 Disallow 规则及 AI 爬虫专属 token 法律风险
速率限制 每域名每秒不超过 1 请求 被封禁
个人数据 不采集可识别个人信息 GDPR/个保法
版权内容 注意内容使用授权 知识产权
服务条款 检查网站 ToS 中的爬虫条款 合同纠纷

robots.txt 的语义在 AI 时代已经扩展：除了传统的 Disallow 路径规则，GPTBot、CCBot 等 AI 爬虫 token 让站长能区分"允许搜索索引"与"允许用于模型训练"。采集训练语料前，应先解析目标站针对 AI 爬虫的声明，无法确证授权时选择官方开放数据集（如 Common Crawl 语料库）或付费数据服务。
