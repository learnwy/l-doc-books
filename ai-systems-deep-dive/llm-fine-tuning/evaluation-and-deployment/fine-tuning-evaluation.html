微调效果评估体系

核心概念

微调效果评估是确认模型是否达到预期目标的系统化方法论。LLM 评估面临独特挑战：开放式生成的输出空间巨大，同一问题可能有多个合理答案，且不同评估维度（准确性、流畅性、安全性、指令遵循）之间可能存在冲突。完整的评估体系需要覆盖能力保持、任务适配和安全对齐三个层面。

自动化基准测试
通用基准测试是评估微调模型是否出现"灾难性遗忘"的第一道防线。微调后的模型应该在目标任务上提升，同时在通用能力上不出现显著退化：


import lm_eval

results = lm_eval.simple_evaluate(
    model="hf",
    model_args="pretrained=./fine-tuned-model,dtype=auto",
    tasks=["mmlu", "hellaswag", "arc_challenge", "truthfulqa_mc2"],
    batch_size=8,
    num_fewshot=5,
)

for task_name, task_result in results["results"].items():
    accuracy = task_result.get("acc,none", task_result.get("acc_norm,none", 0))
    print(f"{task_name}: {accuracy:.4f}")

LLM-as-Judge 评估
对于开放式生成任务，使用强大的 LLM（如 GPT-4）作为评审者可以提供比传统指标更有意义的评分：


from openai import OpenAI

client = OpenAI()

def llm_judge_evaluate(
    question: str,
    response: str,
    criteria: list[str],
) -> dict[str, float]:
    prompt = (
        f"请评估以下 AI 回答的质量。\n\n"
        f"问题：{question}\n\n"
        f"回答：{response}\n\n"
        f"评估维度：\n"
    )
    for criterion in criteria:
        prompt += f"- {criterion}\n"
    prompt += "\n请对每个维度打分（1-5分），并给出简要理由。以 JSON 格式输出。"

    completion = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        response_format={"type": "json_object"},
        temperature=0,
    )
    import json
    return json.loads(completion.choices[0].message.content)


evaluation_criteria = [
    "准确性：回答是否包含事实错误",
    "完整性：是否充分覆盖了问题的各个方面",
    "可操作性：是否提供了具体可执行的建议",
    "安全性：是否包含有害或不当内容",
    "格式质量：回答的结构和表述是否清晰",
]
为了提高评估的可靠性，常用的技巧包括多次评估取平均、交换候选回答顺序消除位置偏差、以及使用多个评审模型的集成：

人工评估与 A/B 测试
在模型上线前，人工评估和 A/B 测试是不可替代的最终验证手段。人工评估适合评估模型的整体质量和边界情况：


interface HumanEvaluation {
  evaluator: string;
  prompt: string;
  modelAResponse: string;
  modelBResponse: string;
  preference: 'A' | 'B' | 'tie';
  dimensions: {
    helpfulness: number;
    accuracy: number;
    safety: number;
    coherence: number;
  };
}

interface ABTestConfig {
  sampleSize: number;
  confidenceLevel: number;
  minimumDetectableEffect: number;
  trafficSplit: [number, number];
  primaryMetric: string;
  guardrailMetrics: string[];
}

const abTestPlan: ABTestConfig = {
  sampleSize: 5000,
  confidenceLevel: 0.95,
  minimumDetectableEffect: 0.02,
  trafficSplit: [50, 50],
  primaryMetric: 'user_satisfaction_rate',
  guardrailMetrics: ['safety_violation_rate', 'factual_error_rate', 'response_latency_p99'],
};
A/B 测试的核心是确保统计显著性。样本量需要根据预期效应大小和置信度水平提前计算，避免过早结论或漏检真实差异。


评估流水线设计
将评估自动化为流水线，确保每次训练后都能快速获得全面的质量反馈：


from dataclasses import dataclass, field

@dataclass
class EvaluationPipeline:
    model_path: str
    baseline_path: str
    tasks: list[str] = field(default_factory=lambda: ["mmlu", "hellaswag"])
    custom_test_set: str = ""
    judge_model: str = "gpt-4o"
    min_general_score: float = 0.95
    min_task_score: float = 0.80

    def run(self) -> dict:
        results = {}
        results["general_benchmarks"] = self.run_general_benchmarks()
        results["task_benchmarks"] = self.run_task_benchmarks()
        results["llm_judge"] = self.run_llm_judge()
        results["safety_check"] = self.run_safety_check()
        results["regression_check"] = self.check_regression(results)
        return results

    def check_regression(self, results: dict) -> dict:
        general = results["general_benchmarks"]
        passed = all(
            score >= self.min_general_score * baseline_score
            for score, baseline_score in zip(
                general["current"].values(),
                general["baseline"].values(),
            )
        )
        return {"passed": passed, "details": general}

小结
    

  • 微调评估需要覆盖能力保持、任务适配和安全对齐三个层面
    • 

  • 自动化基准测试是检测灾难性遗忘的第一道防线
    • 

  • LLM-as-Judge 为开放式生成提供了可扩展的评估方案
    • 

  • 位置交换和多次评估是提高 LLM 评审可靠性的关键技巧
    • 

  • A/B 测试是上线前的最终验证，需确保统计显著性
    • 

  • 评估流水线应自动化运行，设置明确的阻断条件防止质量退化
