Google 通用晋升策略

Scope / Impact / Leadership 三维度框架

无论你是什么角色、什么级别，Google 的晋升评估本质上都在衡量三个核心维度：Scope（范围）、Impact（影响力）和 Leadership（领导力）。理解这三个维度，是制定晋升策略的基础。

Scope（范围）

Scope 衡量的是你的工作影响范围有多大。随着级别的提升，Google 对你的 scope 期望从个人任务扩展到团队、组织、公司乃至行业。

级别 期望 Scope
L3 个人任务和 bug 修复
L4 完整功能或项目
L5 团队级系统和方向
L6 多团队/产品领域
L7 产品线/大部门
L8+ 公司/行业

扩大 Scope 的策略：

  • 主动承担跨团队问题：当你发现一个影响多个团队的问题时，不要等别人解决——主动站出来协调各方，推动解决方案。这是展示超越当前级别 scope 的最直接方式。
  • 参与跨职能项目：加入涉及工程、产品、设计等多个职能的项目，这样你的工作天然就具有更大的 scope。
  • 建立跨团队技术标准：如果你发现多个团队在重复解决类似问题，提出一个统一的解决方案或最佳实践——这是扩大 scope 的经典路径。

Impact（影响力）

Impact 衡量的是你的工作产出了多少实际价值。Google 强调"可量化的影响力"——你需要能够用数据说明你的贡献。

量化 Impact 的方法：

  • 用户指标：你的工作影响了多少用户？提升了多少用户满意度？降低了多少用户投诉？
  • 技术指标：延迟降低了多少？可靠性提升了多少（SLO 达成率）？代码覆盖率提高了多少？
  • 商业指标：节省了多少成本？增加了多少收入？提高了多少转化率？
  • 工程效率：开发速度提升了多少？上线周期缩短了多少？减少了多少重复工作？

Leadership（领导力）

Leadership 在 Google 的语境中不仅指管理人员的能力，更包含 IC 的技术领导力。

IC 的领导力表现：

  • 在技术讨论中引导方向，帮助团队做出正确的技术决策
  • 编写高质量的 Design Doc，影响团队的技术路线
  • 在 Code Review 中提供教育性的反馈，提升团队整体代码质量
  • 主动发现并推动解决没有明确负责人的问题
  • 指导 junior 工程师的技术成长

Manager 的领导力表现：

  • 建设高效的团队，吸引和留住优秀人才
  • 创造让团队成员发挥最佳水平的环境
  • 在校准会议中为团队成员有效代言
  • 做出正确的优先级决策，确保团队聚焦于最有价值的工作

Cross-functional Projects（跨职能项目）

跨职能项目是晋升到 L6+ 级别的重要加分项。参与跨职能项目不仅扩大了你的 scope，还展示了你与不同职能有效协作的能力。

如何发现跨职能机会：

  • 关注你所在 PA 的 OKR 和季度优先级——大型跨团队项目通常与这些优先级直接相关
  • 参加跨团队的技术讲座和讨论，了解其他团队面临的挑战
  • 与产品经理、设计师、数据科学家建立常规的沟通渠道

跨职能协作的常见挑战：

  • 优先级冲突：不同团队可能对项目优先级有不同看法。解决方案是找到共同利益点，用数据说服各方。
  • 沟通障碍：工程师和非工程师使用不同的专业术语。解决方案是学习用对方理解的语言表达你的观点。
  • 责任归属：跨团队项目中"谁负责什么"可能不清晰。解决方案是在项目初期就明确 RACI 矩阵。

Internal Mobility（内部转岗）

Google 有成熟的内部转岗（transfer）机制，允许员工在不同的团队、PA 甚至城市之间流动。合理利用内部转岗可以加速你的职业发展。

转岗的时机：

  • 你在当前团队的晋升路径被阻塞（如缺乏高影响力项目、与 Manager 关系不佳）
  • 你想探索新的技术方向或产品领域
  • 你所在的团队面临组织不确定性（如裁员风险）
  • 你想通过新环境的挑战来加速成长

转岗的流程：

  1. 在内部工作平台（通常是 Google 的内部招聘系统）浏览开放的职位
  2. 与目标团队的 Manager 或团队成员进行非正式沟通（"coffee chat"）
  3. 正式申请转岗，通常需要通过目标团队的面试
  4. 获得当前 Manager 的批准（通常有 30-90 天的过渡期要求）

转岗的注意事项：

  • 至少在当前团队工作 12 个月后才建议考虑转岗——频繁转岗会影响你的信誉
  • 转岗不会改变你的级别，但薪酬可能根据新团队的地理位置和薪资带进行调整
  • 转岗后的第一个绩效周期通常会受到"ramp-up 期"的影响，评级可能略低于预期

Google 特色制度对晋升的影响

Readability 要求

Readability 是 Google 工程师独有的制度——你需要获得至少一种编程语言的代码可读性认证，才能在代码库中拥有完整的提交权限。对晋升的影响：

  • L3→L4：强烈建议获得
  • L4→L5：建议在晋升周期前获得
  • L5→L6：几乎是硬性要求
  • 拥有多种语言的 Readability 是技术广度的有力证明

Design Doc 文化

Design Doc 是 Google 工程决策的核心载体。任何重大的技术变更都需要一份 Design Doc 来阐述动机、方案、权衡和风险。

Design Doc 对晋升的价值：

  • 它是你技术判断力和系统思维的最直接展示
  • Promotion Committee 会审阅你的 Design Doc 来评估你的能力
  • 一份被广泛认可的 Design Doc 比一千行代码更有说服力

写好 Design Doc 的核心原则：

  • 清晰定义问题和约束条件
  • 列出所有可行方案并对比分析
  • 明确说明为什么选择了当前方案
  • 考虑可扩展性、可靠性、安全性等非功能需求
  • 定义成功指标和验证方法
  • 包含迁移策略和回滚计划

Code Review 文化

Code Review 在 Google 不仅是质量保证机制，也是知识传播和技术成长的核心渠道。你的 Code Review 活动会被 Promotion Committee 审视：

  • 作为审查者：你是否能发现非显而易见的问题？你的反馈是否建设性且有教育意义？
  • 作为被审查者：你是否虚心接受反馈并持续改进？你的代码质量是否稳步提升？
  • 活跃度：你是否积极参与团队的 Code Review 工作？

通用晋升时间线参考

级别跃迁 典型时间 快速路径 主要卡点
L3→L4 1.5-2 年 1 年 独立性不足
L4→L5 2-3 年 1.5 年 只是执行者，不会定义问题
L5→L6 3-5 年 2-3 年 影响力局限于本团队
L6→L7 3-5 年 2 年 技术广度不足
L7→L8 5+ 年 不适用 需要公司级别的贡献

这些时间仅供参考——实际晋升速度取决于个人表现、团队环境、业务机遇等多种因素。Google 没有"你必须在 X 年内晋升到 Y 级别否则会被淘汰"的硬性要求（L5 是终端级别），但持续停滞可能导致绩效评估被标记为 Moderate Impact。
