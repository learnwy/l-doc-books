Amazon 职级体系全景：从 L4 到 L12 的完整层级架构

职级体系的设计哲学

Amazon 的职级体系（L-Level System）是公司组织架构的骨干。与 Google 的 TC（Technical Career）Ladder 或 Meta 的 E-Level 体系不同，Amazon 的职级系统有几个显著特点：

统一编号，跨职能通用。无论你是 SDE（Software Development Engineer）、PM（Product Manager）、SDM（Software Development Manager）、TPM（Technical Program Manager）还是 BIE（Business Intelligence Engineer），都使用同一套 L-Level 编号系统。L6 的 SDE 和 L6 的 PM 在组织层级上是对等的。

级别定义影响力范围，而非技术深度。L4 的影响力范围通常是个人任务，L5 是小功能模块，L6 是一个完整项目或系统，L7 是一个组织（org）范围的问题，L8 是公司级的战略方向。级别越高，对"技术能力"的要求反而让位于对"影响力和判断力"的要求。

没有自动晋升，只有证明已在更高级别运作。Amazon 的晋升标准是"你已经在下一个级别持续运作了一段时间"，而不是"你在当前级别做得足够好"。这意味着你需要先承担更高级别的责任并证明胜任，才能获得晋升。

各级别详细解析

L3：时薪岗位

L3 主要是仓储、物流和客服等时薪岗位。对于技术和企业员工来说，L3 几乎不存在。极少数实习生可能以 L3 身份进入，但这是例外而非常规。

L4：SDE I / 入门级

L4 是 Amazon 技术岗位的标准入门级别。典型的 L4 是：

  • 新毕业生：顶尖大学的 CS 本科或硕士毕业生，但 Amazon 对新毕业生的 L4 录取比例远低于 Google 或 Meta
  • 有 1-4 年经验的跳槽者：这是更常见的 L4 来源。Amazon 倾向于招有一定工作经验的人
  • 从实习转正的少数人：Amazon 实习转正率并不高

能力期望：独立完成明确定义的任务，编写高质量代码，参与代码审查和运维值班（on-call）。不需要独立设计系统，但需要理解团队的系统架构。

典型停留时间：1-3 年。L4 到 L5 的晋升是相对最容易的一次。

L5：SDE II / 中级

L5 是 Amazon 人数最多的级别，也是很多人的"终点站"。L5 同时也是大量管理者的级别——在 Amazon，L5 Manager 可以管理 L3/L4/L5 的下属。

能力期望：独立承担完整功能模块的设计和交付，能够指导 L4 工程师，参与团队级别的技术决策。L5 需要开始展示"ownership"——对自己负责的系统有端到端的责任感。

为什么很多人卡在 L5：三个因素叠加——(1) L5 到 L6 的晋升标准大幅跃升，(2) L5 Manager 的存在让很多人的精力分散在管理和技术之间，(3) 大量外部招聘进入 L5 导致竞争激烈。

典型停留时间：2-4 年（晋升到 L6），或长期停留。

L6：Senior SDE / 高级

L6 是 Amazon 的"第一个真正的高级别"。获得 L6 晋升是一个重大里程碑。

能力期望：驱动跨团队的项目成果，对一个完整系统或产品领域有端到端的设计和决策权，能够影响团队方向。L6 是 Amazon 期望大量工程师"到达并停留"的级别。

外部招聘的降级集散地。很多在其他公司担任 Principal 或 Staff Engineer 的工程师，跳槽 Amazon 时会被降级到 L6。Amazon 宁愿把你降级到 L6 然后看你表现，也不愿意冒险给你 L7。

典型停留时间：3-5 年以上（晋升到 L7），或长期停留。很多优秀工程师在 L6 级别工作整个职业生涯。

L7：Principal SDE / 首席

L7 是 IC（个人贡献者）轨道的第一个"稀有级别"。到了 L7，你的影响力范围需要是整个 org（组织）级别的。

能力期望：定义一个组织级别的技术方向，推动跨多个团队的架构决策，在技术社区中建立影响力。L7 不只是"更高级的 L6"——它要求你从"做好一个系统"转变为"定义多个系统的方向"。

晋升难度。L6 到 L7 是 Amazon 公认最难的晋升跳跃之一。这个晋升高度依赖你的管理者——他们需要为你撰写晋升文档、在 OLR 委员会中为你辩护、并帮你获得足够的组织级影响力机会。

总薪酬：450,000−450,000-450,000−700,000+（美国市场）。

L8：Senior Principal SDE / 资深首席

L8 需要公司级别的影响力。在 Amazon，L8 通常是一个大型组织（如 AWS 的某个核心服务线）的技术决策者。

能力期望：定义公司级别的技术战略，影响多个组织的技术方向，解决没有现成方案的系统性问题。

稀缺性。L8 的 IC 在 Amazon 非常稀少。整个公司的 L8 SDE 可能只有几百人。

L10：Distinguished Engineer / 杰出工程师

L10 是 IC 轨道的顶点（L9 在 Amazon 不存在）。Distinguished Engineer 在公司内部拥有近乎传奇的地位。

能力期望：在一个重大技术领域有全球级别的影响力，定义了该领域的发展方向。L10 不只是技术专家——他们是"技术愿景家"。

稀缺性。整个 Amazon 可能只有个位数到两位数的 L10 IC。

L12：VP 级别及以上

L12 对应 Vice President 级别。这已经进入 Amazon 的 S-team（高级领导团队）附近的层级。在管理轨道中，L8 通常是 Director，L10 是 VP，L12 是 SVP。

不同职能轨道的级别对应

级别 SDE（IC） SDM（管理） PM TPM
L4 SDE I — PM I TPM I
L5 SDE II Manager PM II TPM II
L6 Senior SDE Senior Manager Senior PM Senior TPM
L7 Principal SDE Principal Manager Principal PM Principal TPM
L8 Sr. Principal SDE Director Sr. Principal PM Sr. Principal TPM
L10 Distinguished Engineer VP — —
L12 — SVP — —

关键差异：

  • SDM 从 L5 开始。你不能在 L4 做管理者。想走管理轨道，至少先做到 L5 IC 然后转管理
  • PM 和 TPM 的天花板通常在 L7/L8。很少有 PM 或 TPM 做到 L10 或更高
  • IC 轨道和管理轨道可以互转。L6 Senior SDE 可以转为 L6 Senior Manager，但需要重新证明管理能力

晋升机制

OLR（Organizational Leadership Review）

Amazon 每年运行两次 OLR 周期（通常在 Q1 和 Q3）。OLR 是晋升决策的主要场所：

  1. 员工通过 Forte 系统提交自评和工作成果
  2. 收集同事反馈
  3. 管理者进行校准（calibration）
  4. OLR 委员会讨论并决定最终评级
  5. 基于评级做出薪酬调整和晋升决定

晋升文档

L6 及以上的晋升通常需要正式的晋升文档（Promo Doc）。这份文档由你的管理者撰写，需要包含：

  • 你在更高级别持续运作的证据
  • 具体的影响力案例和量化成果
  • 对领导力准则的践行证据
  • 来自跨团队利益相关者的背书

晋升政治

Amazon 的晋升不完全是能力问题，也包含组织政治因素：

  • 你的管理者是最关键的变量。管理者在 OLR 委员会中为你的晋升案例辩护，如果你的管理者不积极或政治资本不足，即使你的表现优秀也可能被搁置
  • 组织中的"晋升名额"有限。在经济下行期或组织重组期，晋升名额会被压缩
  • 影响力需要可见性。做了很好的技术工作但没有被正确的人看到，等于没做

对管理者的启示

职级体系的设计应该反映影响力范围，而非资历。Amazon 用"你在什么范围内产生影响"来定义级别，而非"你工作了多少年"。这种设计鼓励员工主动扩大影响力，而非被动等待年限。

最难的跳跃往往在中高层。L5→L6 和 L6→L7 是 Amazon 最难的两次晋升。组织设计者应该预料到这些"瓶颈层"的存在，并设计合理的疏导机制。

晋升制度需要对抗政治化。Bar Raiser 式的独立评审者、标准化的晋升文档格式、多人组成的 OLR 委员会——这些都是对抗晋升政治化的制度工具。
