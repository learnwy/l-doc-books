多 CDN 策略与调度

概述

大型互联网企业通常不会依赖单一 CDN 厂商，而是采用多 CDN（Multi-CDN）策略。这种架构通过同时使用多家 CDN 服务商，在性能、成本、可靠性和厂商依赖之间寻求最优平衡。多 CDN 策略从简单的主备切换发展到如今的智能实时调度，已成为企业级内容交付架构的标准实践。

多 CDN 策略动机

性能优化

单一 CDN 厂商无法在所有区域都提供最优性能：

  • 厂商 A 在北美表现最佳，厂商 B 在亚太更优
  • 不同厂商的网络互联关系不同，同一用户到不同 CDN 的延迟差异显著
  • 动态选择当前最优厂商，可将全球 P95 延迟降低 20-40%

可靠性保障

单点故障消除：

  • 2021 年 Fastly 大规模故障影响全球众多网站
  • 2022 年 Cloudflare 因配置变更导致数小时中断
  • 多 CDN 架构在单一厂商故障时自动切换，确保业务连续性

故障隔离：

  • 不同厂商的基础设施独立
  • 一家厂商的 DDoS 攻击不影响通过其他厂商的流量
  • 不同厂商使用不同的上游网络和 Peering 关系

成本优化

  • 利用多家厂商竞价降低单位带宽成本
  • 按区域选择性价比最高的厂商
  • 利用 Commit 合约和 Burst 定价的差异优化账单
  • 避免单一厂商的价格垄断

厂商独立性

  • 降低对单一厂商的依赖风险
  • 保持谈判筹码（随时可以调整流量分配比例）
  • 利用不同厂商的特色功能（一家的边缘计算 + 另一家的视频处理）

调度架构

DNS 级调度

最基础的多 CDN 调度方式，通过智能 DNS 将不同用户请求路由到不同 CDN：

实现方式：

  • 自建权威 DNS 或使用第三方 GSLB 服务（如 NS1、Route 53 Traffic Policy）
  • 根据策略返回不同 CDN 的 CNAME 或 IP
  • 策略可基于：地理位置、性能探测结果、权重比例、时间段

优劣势：

  • 优势：实现简单、对 CDN 厂商透明
  • 劣势：调度粒度粗（受限于 DNS TTL）、不能感知单次请求的内容特征

HTTP 级调度

在 HTTP 层进行更精细的调度：

请求级重定向：

  • 前端或中间层服务根据请求内容选择 CDN
  • 大文件走厂商 A（带宽成本低）、小文件走厂商 B（延迟低）
  • 实时流走厂商 C（视频优化能力强）

SDK/客户端调度：

  • 客户端 SDK 内置多 CDN 调度逻辑
  • 根据实时测速结果选择最优 CDN
  • 支持请求级的快速重试和切换

混合调度

结合 DNS 调度和 HTTP 调度：

  • DNS 做粗粒度的区域调度（大比例分流）
  • HTTP/SDK 做细粒度的实时调度（性能优化和故障快切）

实时质量探测

探测体系

多 CDN 调度的决策质量取决于质量数据的准确性和时效性：

合成探测（Synthetic Monitoring）：

  • 在全球各区域部署探测节点
  • 定期向各 CDN 发送测试请求
  • 测量延迟、吞吐量、可用性等指标
  • 典型方案：ThousandEyes、Catchpoint、Cedexis

真实用户监控（RUM）：

  • 在页面中嵌入性能采集脚本
  • 收集实际用户的加载时间、错误率、协议统计
  • 数据来源最真实，但受限于采样率和隐私政策

被动流量分析：

  • 分析实际流量的 TCP/HTTP 性能指标
  • 利用 TCP Timestamps 估算 RTT
  • 分析重传率和连接失败率

质量评分模型

将多维探测数据综合为单一评分，用于调度决策：

Score = w1 × (1 - Latency/MaxLatency)
      + w2 × Availability
      + w3 × (1 - ErrorRate)
      + w4 × (Throughput/MaxThroughput)

评分模型需要：

  • 按区域独立计算（同一 CDN 在不同区域表现不同）
  • 按内容类型分别计算（静态/动态/视频表现不同）
  • 历史衰减（近期数据权重更高）
  • 异常值处理（避免单次探测抖动影响决策）

自动切换策略

故障切换

当检测到某 CDN 厂商异常时的切换流程：

检测阶段：

  1. 连续 N 次探测失败（避免瞬时抖动误判）
  2. 或真实用户错误率超过阈值
  3. 或厂商主动发布故障通告

切换阶段：

  1. 触发 DNS TTL 倒计时（立即生效需要低 TTL）
  2. DNS 将流量切换到备用 CDN
  3. 客户端 SDK 同时收到切换信号，立即重试
  4. 监控备用 CDN 的承载情况

恢复阶段：

  1. 故障 CDN 探测恢复正常
  2. 观察期（通常 5-15 分钟）确认稳定
  3. 逐步恢复流量（先 10% → 50% → 100%）
  4. 避免突发流量回灌导致再次过载

性能调度

非故障场景下基于性能的动态调度：

  • 每 N 秒（通常 30-60s）更新各 CDN 的质量评分
  • 根据评分差异调整流量权重
  • 设置最小分配比例（避免某 CDN 完全无流量而无法探测）
  • 变更幅度限制（防止频繁大幅切换导致缓存失效）

成本感知调度

在满足性能 SLA 的前提下优化成本：

  • 计算各 CDN 的单位带宽成本
  • 在性能差异可接受范围内优先使用低成本 CDN
  • Commit 合约流量优先消耗（避免浪费保底带宽）
  • 月底临近 Commit 时调整分配确保合约达标

缓存一致性管理

多 CDN 缓存同步挑战

使用多 CDN 时，每家厂商独立维护缓存，带来一致性问题：

  • 内容更新后需要向所有 CDN 发送 Purge
  • 不同 CDN 的 Purge 完成时间不同
  • 中间可能有用户从不同 CDN 获得不同版本

解决方案

统一 Purge 管理：

  • 建立 Purge 中心：一次调用，同时向所有 CDN 发送清除请求
  • 跟踪各 CDN 的 Purge 完成状态
  • 所有 CDN 确认完成后才标记为已生效

版本化 URL：

  • 内容 URL 包含版本号或哈希
  • 更新 = 新 URL，旧缓存自然失效
  • 无需主动 Purge，各 CDN 自动获取新版本

缓存指令一致：

  • 确保源站对所有 CDN 返回一致的缓存指令
  • 避免因 CDN 配置差异导致的 TTL 不一致
  • 使用 s-maxage 精确控制 CDN 行为

运营管理

厂商管理

  • 定期（季度）评估各 CDN 的性能和成本
  • 维护各厂商的技术对接和紧急联系渠道
  • 合约管理：Commit 流量、超额定价、SLA 条款
  • 新厂商评估和接入流程

统一配置管理

多 CDN 环境下的配置管理复杂度：

  • 不同 CDN 的配置格式和 API 不同
  • 需要抽象层统一管理缓存规则、安全策略、路由配置
  • 配置变更需要同步到所有 CDN
  • 典型方案：自建配置管理平台或使用 Multi-CDN 管理 SaaS

统一报表与计费

  • 各 CDN 厂商的报表格式和指标定义不同
  • 需要标准化后统一汇总
  • 统一视图：整体流量分布、各区域性能对比、成本趋势
  • 计费核对：CDN 账单与自有流量数据比对

实战案例分析

视频平台多 CDN 架构

                    ┌─── CDN-A (北美/欧洲，静态+视频)
用户 → DNS/SDK →──┼─── CDN-B (亚太，静态+动态加速)
                    ├─── CDN-C (全球，纯视频流)
                    └─── 自建节点 (核心区域，热点内容)

调度策略：

  • 静态资源按区域最优性能分配
  • 视频流按成本和质量综合评分分配
  • 热点内容优先走自建节点（成本最低）
  • 故障时 <30s 自动切换

电商大促多 CDN 策略

大促期间的特殊策略：

  • 提前预热：将大促页面推送到所有 CDN 预缓存
  • 容量预留：与各 CDN 确认保障带宽
  • 弹性溢出：当首选 CDN 逼近容量上限时自动溢出到备选
  • 降级方案：极端情况下静态页面兜底

小结

多 CDN 策略是企业级内容交付的标准实践，它通过多厂商冗余、智能调度和成本优化，在性能、可靠性和成本三个维度实现最优平衡。成功的多 CDN 架构需要投入在质量探测、调度引擎和统一管理平台的建设上。随着边缘计算的发展，多 CDN 策略也在向"多边缘"策略演进——不仅分发内容，还分发计算能力。
