动态加速与优化

概述

传统 CDN 通过缓存静态内容提升性能，但现代 Web 应用中大量请求是动态的——API 调用、个性化页面、实时数据查询——这些内容无法被缓存。动态加速（Dynamic Site Acceleration, DSA）通过优化网络路径、传输协议和连接管理，为不可缓存的动态流量提供加速。本文探讨动态加速的核心技术和优化策略。

动态加速的核心原理

动态内容无法通过缓存消除回源延迟，但可以通过以下方式缩短端到端传输时间：

  • 缩短网络路径：通过 CDN 内部网络绕开公网拥堵
  • 优化传输协议：减少握手延迟、提高传输效率
  • 连接复用：减少重复建连开销
  • 预测性连接：提前建立连接，消除等待时间
  • 压缩与编码：减少传输数据量

关键指标是 TTFB（Time To First Byte），即从用户发起请求到收到第一个字节的时间。动态加速的目标是最小化 TTFB。

网络路径优化

智能选路

公网路由基于 BGP 协议，选路依据是 AS 路径长度而非实际延迟或质量。CDN 内部网络可以做到更优：

实时链路质量探测：

  • 在 CDN 节点间持续发送探测包，测量延迟、丢包率、抖动
  • 每 5-30 秒更新一次路由表
  • 探测覆盖直连路径和经由中间节点的间接路径

多路径选择：

  • 对于用户到 CDN 入口：选择延迟最低的入口节点
  • 对于 CDN 入口到源站：在多条可用路径中选择当前质量最优的
  • 支持按比例分流到多条路径，提高容错性

避障路由：

  • 检测到链路降级时自动绕行
  • 维护链路黑名单和灰名单
  • 支持手动标记和自动恢复

CDN 中继（Relay/Overlay Network）

利用 CDN 节点构建覆盖网络：

用户 → 就近CDN入口节点 →[CDN内部网络]→ 源站附近CDN出口节点 → 源站

这条路径通常优于用户直连源站，因为：

  • CDN 节点间使用高质量专线或优化过的公网路径
  • TCP 分段传输——长距离单连接分拆为多段短连接，每段独立优化
  • 避开公网的拥堵路由和低质量跨境链路

传输协议优化

TCP 优化

TCP 协议在高延迟和高丢包网络中性能下降严重。CDN 在多个层面优化 TCP：

拥塞控制算法：

  • 使用 BBR 替代传统的 Cubic/Reno，在有丢包的链路上保持高吞吐
  • 边缘节点与用户之间使用针对最后一公里优化的拥塞控制
  • 节点间骨干链路使用高带宽利用率的拥塞控制

连接参数调优：

  • 增大初始拥塞窗口（IW10 或更大），加速慢启动
  • 启用 TCP Fast Open（TFO），节省一次 RTT
  • 优化 MSS 和缓冲区大小适配链路特性

TCP 分段加速：

  • 将一条长距离 TCP 连接分割为多段短连接
  • 每段独立进行拥塞控制和重传
  • 单段丢包不影响其他段的传输进度

QUIC / HTTP/3

QUIC 从协议层面解决了 TCP 的根本限制：

0-RTT 连接建立：对已知服务器可以在第一个数据包就发送应用数据，消除握手延迟。

无队头阻塞：多路复用的流之间独立传输，单个流的丢包不阻塞其他流。

连接迁移：通过 Connection ID 而非四元组标识连接，用户切换网络时连接不断。

CDN 中的 QUIC 部署实践：

  • 边缘节点面向用户启用 QUIC/HTTP3
  • CDN 内部网络通常仍使用 TCP（更可控、工具链更成熟）
  • 回源连接按源站支持情况选择 QUIC 或 HTTP/2

HTTP/2 优化

对于尚未支持 HTTP/3 的场景，HTTP/2 的优化包括：

  • Server Push：预测性推送关联资源（但实践中效果有争议）
  • 优先级调度：关键资源优先传输
  • 头部压缩（HPACK）：减少重复 Header 的传输开销
  • 多路复用：单连接上并行传输多个请求响应

连接管理优化

连接池与复用

CDN 节点与源站之间维护连接池：

  • 保持一定数量的持久连接（Keep-Alive）
  • 新请求直接使用已有连接，避免三次握手 + TLS 握手的延迟
  • 连接池按源站域名分组管理
  • 空闲连接定期清理，避免资源泄漏

连接复用可以节省 1-3 个 RTT（TCP 握手 + TLS 握手），对高延迟链路效果尤其显著。

TLS 优化

TLS 握手是 HTTPS 连接延迟的主要来源之一：

  • TLS 1.3：握手只需 1-RTT（首次）或 0-RTT（重连）
  • OCSP Stapling：避免客户端独立查询证书状态
  • 会话恢复（Session Resumption）：利用 Session Ticket 跳过完整握手
  • 证书优化：使用 ECC 证书（比 RSA 更小更快）、精简证书链

预连接（Pre-connect）

在用户真正发起请求之前预建连接：

  • DNS 预解析（DNS Prefetch）
  • TCP 预连接（Preconnect）
  • TLS 预握手

这些预连接由上一个页面或资源的 Hint 触发，用户无感知地完成耗时的连接建立过程。

边缘预处理

请求合并（Request Collapsing）

多个用户同时请求同一个动态资源时，合并为一次回源：

  • 适用于"相同请求、相同响应"的场景（如公共 API）
  • 不适用于个性化响应
  • 需要设置合理的等待窗口（太短合并效果差，太长增加延迟）

边缘预计算

将部分可在边缘完成的计算下沉到边缘节点：

  • ESI（Edge Side Includes）：页面的静态部分缓存，动态部分边缘拼装
  • A/B 测试分流：在边缘完成用户分桶，避免回源
  • 地理信息注入：边缘注入用户地理位置信息，源站无需再次解析 IP
  • 请求路由决策：在边缘完成微服务路由，减少中心负载

压缩与传输编码

动态压缩

对动态响应实时压缩：

  • Brotli：压缩率比 gzip 高 15-25%，但 CPU 消耗更大
  • gzip：兼容性最广，适合实时压缩（level 4-6 为性能和压缩率的平衡点）
  • zstd：新一代压缩算法，在可训练字典模式下对 JSON/API 响应效果优异

策略选择：静态资源可离线用高级别 Brotli 预压缩存储，动态响应用快速 gzip 实时压缩。

传输优化

  • Chunked Transfer：流式传输，边生成边发送
  • Range 请求：支持断点续传和并行分块下载
  • 差异传输（Delta Encoding）：只传输与上次响应的差异部分

性能度量与优化验证

关键指标

  • TTFB：到首字节时间（反映网络路径 + 源站处理时间）
  • RTT：用户到边缘节点的网络往返时间
  • 连接复用率：复用连接请求 / 总请求
  • 协议分布：HTTP/1.1 vs HTTP/2 vs HTTP/3 的使用比例
  • 加速收益：经 CDN vs 直连源站的 TTFB 差值

A/B 测试验证

动态加速的效果应通过严格的 A/B 测试验证：

  • 对照组：直连源站
  • 实验组：经 CDN 动态加速
  • 观察指标：TTFB、页面加载时间、业务转化率

小结

动态加速是 CDN 从"缓存分发"向"全站加速"演进的关键能力。它通过网络路径优化、协议升级、连接管理和边缘预处理等多维度手段，为不可缓存的动态流量提供显著的性能提升。选择和组合这些技术时，需要结合业务特征、用户分布和成本约束进行综合考量。
