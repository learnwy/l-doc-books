缓存策略与失效

概述

缓存是 CDN 的核心能力，缓存策略的设计直接决定了命中率、内容新鲜度和源站负载之间的平衡。一个优秀的缓存系统需要回答三个核心问题：缓存什么（缓存键设计）、缓存多久（TTL 策略）、何时失效（失效机制）。本文深入探讨这三个问题的工程实践。

缓存键设计

缓存键的组成

缓存键（Cache Key）决定了哪些请求被视为"相同"并共享缓存：

基础缓存键通常包含：

  • 协议（HTTP/HTTPS）
  • 主机名（Host Header）
  • 请求路径（URI Path）
  • 查询参数（Query String）

精细化缓存键可能额外包含：

  • 特定请求头（如 Accept-Encoding、Accept-Language）
  • Cookie 中的特定字段
  • 设备类型标识
  • 地理位置信息

缓存键优化

缓存键设计过宽（包含过多变量）会导致缓存碎片化，命中率降低；设计过窄（忽略必要差异）会导致内容错误。

参数排序规范化：?a=1&b=2 和 ?b=2&a=1 应视为相同。CDN 通常在生成缓存键前对查询参数排序。

无关参数剥离：追踪参数（utm_source、fbclid）不影响内容，应从缓存键中移除。

Vary 头处理：源站通过 Vary 头声明哪些请求头影响响应内容。CDN 需要将 Vary 列出的头纳入缓存键，但过多 Vary 字段会导致缓存效率急剧下降。

# 源站响应头示例
Vary: Accept-Encoding, Accept-Language
# CDN 会为每种 Encoding × Language 组合缓存一份

缓存分区

大规模 CDN 通常将缓存空间按客户或域名进行分区：

  • 防止单个客户的大量内容挤出其他客户的缓存
  • 便于按客户维度的缓存清除操作
  • 支持不同的缓存策略配置

TTL 策略

TTL 决策来源

缓存时间的确定遵循优先级链：

  1. CDN 平台强制策略：最高优先级，覆盖所有其他设置
  2. 客户自定义规则：按路径、文件类型等设置特定 TTL
  3. 源站响应头：Cache-Control: max-age=3600、Expires
  4. CDN 默认策略：当源站未明确指定时的兜底

常见 TTL 策略模式

静态资源长缓存：带哈希指纹的资源（app.a1b2c3.js）设置极长 TTL（1年）。内容变更时 URL 变化，旧缓存自然失效。

HTML 短缓存：页面 HTML 通常设置较短 TTL（1-5分钟），确保用户快速获取更新。HTML 中引用的静态资源通过哈希指纹实现长缓存。

API 响应微缓存：对于变化频率有限的 API（如商品列表），设置极短 TTL（5-30秒）。虽然时间短，但在高并发下仍能显著降低源站压力。

分层 TTL：不同缓存层设置不同的 TTL。通常 L1 边缘设置较短 TTL（保证新鲜度），L2 中间层设置较长 TTL（保证命中率）。

Stale-While-Revalidate

HTTP 的 stale-while-revalidate 指令允许在 TTL 过期后的一段时间内，先返回过期内容，同时异步回源更新：

Cache-Control: max-age=300, stale-while-revalidate=60

含义：前 300 秒使用缓存，300-360 秒内先响应旧内容并异步回源，360 秒后强制回源。这种机制平衡了新鲜度和响应速度。

主动失效机制

Purge（清除）

主动清除指定内容的缓存，适用于内容紧急更新场景：

精确 Purge：清除特定 URL 的缓存

PURGE /images/banner.png HTTP/1.1
Host: cdn.example.com

通配符 Purge：清除匹配模式的所有缓存

PURGE /products/* HTTP/1.1

Tag-based Purge：基于标签清除一组相关内容

# 源站响应时标记标签
Surrogate-Key: product-123 category-electronics

# 清除所有带特定标签的内容
PURGE tag=product-123

Purge 传播

Purge 指令需要传播到所有边缘节点：

  • 全网广播：Purge 请求发送到所有节点。延迟取决于节点数量和传播机制
  • 传播延迟：大规模 CDN 通常需要几秒到几十秒完成全网清除
  • 确认机制：提供 Purge 状态查询 API，确认所有节点是否已完成清除
  • 优先级队列：紧急 Purge（如安全事件）优先处理

版本化与条件更新

除了清除缓存，还可以通过版本化策略避免缓存失效问题：

  • URL 版本化：/v2/api/products 或 /api/products?v=2
  • 内容哈希：/assets/style.abc123.css
  • 条件请求（If-Modified-Since / If-None-Match）：客户端携带版本信息，CDN 判断是否需要重新发送

缓存一致性保障

一致性挑战

CDN 缓存的一致性面临多重挑战：

  • 内容更新后的传播延迟（不同节点可能在不同时刻更新）
  • Purge 命令的可靠传递（网络抖动可能导致部分节点未收到）
  • 竞态条件（Purge 和回源并发时可能缓存旧内容）

一致性级别选择

级别 机制 延迟 适用场景
最终一致 TTL 过期自动更新 分钟级 博客、新闻、静态资源
快速一致 主动 Purge + 短 TTL 秒级 电商商品、价格信息
强一致 每次请求回源验证 无缓存 用户个人数据、支付相关

实际系统中，不同类型的内容应该采用不同级别的一致性策略，在性能和正确性之间取得平衡。

热点与冷启动处理

热点内容处理

当某个内容突然变热（如突发新闻、热搜）：

  • 缓存预热：提前将预期热点内容推送到边缘节点
  • Request Coalescing：多个并发请求合并为一次回源
  • 二级缓存兜底：L1 未命中时从 L2 获取，避免直接打源站
  • 限流保护：对同一对象的回源并发数设上限

缓存冷启动

新上线节点或新加入的内容面临缓存为空的问题：

  • 缓存预加载：从其他节点或源站批量拉取热门内容
  • 请求路由过渡：新节点逐步接入流量，先小比例观察
  • 父节点兜底：冷启动期间提高回源到 L2 的权重
  • 跨节点借调：从邻近节点拉取缓存副本（Cooperative Caching）

缓存性能度量

关键指标体系：

  • 缓存命中率（CHR）：命中请求 / 总请求。按字节和请求数分别统计
  • 源站回源率：每秒回源请求数和带宽
  • 缓存效率：(1 - 回源带宽/总服务带宽) × 100%
  • TTL 实际使用率：对象在 TTL 到期前被替换的比例（过低说明缓存空间不足）
  • Purge 延迟：从发起清除到全网生效的 P99 耗时

小结

缓存策略是 CDN 工程中最考验技术判断力的领域。没有放之四海而皆准的最优策略，需要根据具体业务的内容特征、更新频率、一致性要求和用户分布来定制方案。持续监控缓存性能指标，结合 A/B 测试验证策略效果，是缓存优化的正确方法论。
