CDN 架构与路由

概述

CDN（Content Delivery Network）通过在全球范围内部署缓存节点，将内容推送到距离用户最近的位置，从而降低访问延迟并减轻源站压力。现代 CDN 的架构远比"缓存+分发"复杂——它涉及多层缓存层级、智能路由决策、回源路径优化以及与源站的深度协作。理解 CDN 的架构设计和路由机制，是优化内容交付性能的基础。

CDN 架构层级

全局架构视图

一个典型的大规模 CDN 系统包含以下层级：

用户请求 → DNS/AnyCast → 边缘节点(L1) → 中间层(L2) → 源站Shield → 源站
                                ↕ 本地缓存                ↕ 区域缓存

边缘层（L1 / Edge POP）：

  • 部署在城市级，节点数量最多（数百至数千个）
  • 直接面向终端用户，处理绝大多数请求
  • 缓存最热门的内容，命中率目标 85-95%
  • 单节点存储容量有限，以 SSD + 内存为主

中间层（L2 / Mid-Tier / Parent）：

  • 部署在区域级，数量较少（数十个）
  • 作为多个 L1 节点的上级缓存
  • 聚合 L1 的回源请求，减轻源站压力（Request Collapsing）
  • 缓存长尾内容，弥补 L1 容量不足

源站屏蔽层（Origin Shield）：

  • 可选的额外缓存层，部署在源站近端
  • 将来自全球各区域的回源请求收敛为少量连接
  • 显著降低源站负载，特别适合源站在单一区域的场景

多层缓存的权衡

层级越多，缓存命中率越高，源站压力越小，但代价是：

  • 每增加一层就增加了潜在的延迟（缓存未命中时）
  • 缓存一致性维护更复杂
  • 资源投入（存储、带宽、运维）更大

实践中通常采用 2-3 层架构。对于长尾内容丰富的场景（如视频平台），中间层和 Shield 层价值很大；对于热点集中的场景（如头部新闻），边缘层直接命中率很高，中间层价值有限。

请求路由机制

DNS 调度

DNS 是 CDN 最基础的路由机制：

  1. 用户访问 cdn.example.com，发起 DNS 查询
  2. CDN 的权威 DNS 服务器（如 GSLB）接收查询
  3. 根据多种信号决定返回哪个边缘节点的 IP：
    • 用户的 LDNS IP（判断用户大致位置）
    • EDNS Client Subnet（更精确的用户位置）
    • 各节点的实时负载和健康状态
    • 网络链路质量探测结果
  4. 返回最优节点 IP，用户直连该节点

DNS 调度的局限性：

  • 精度依赖 EDNS Client Subnet 的支持程度
  • DNS TTL 导致切换不够实时（通常设置 30-300s）
  • 无法感知单次请求的具体内容和用户偏好

AnyCast 路由

AnyCast 利用 BGP 路由协议实现就近接入：

  • 多个地理分散的节点宣告同一个 IP 地址
  • 网络层自动将流量路由到最近（BGP 路径最短）的节点
  • 无需 DNS 参与，切换速度取决于 BGP 收敛时间

AnyCast 的优势在于天然的 DDoS 防护（攻击流量被分散到全球节点）和更快的故障切换。劣势在于路由控制粒度较粗，难以做精细化的负载均衡。

HTTP 重定向（302调度）

通过返回 HTTP 302 将用户重定向到最优节点：

  • 中心调度服务器接收初始请求
  • 根据用户 IP、请求内容、节点状态综合决策
  • 返回 302 指向选定的边缘节点
  • 后续请求直接访问边缘节点

302 调度的优势是决策精确度极高（可感知请求级信息），劣势是首次请求多一次 RTT，且调度服务器成为瓶颈。通常用于大文件下载、视频流等场景，首次调度开销相对于传输时间可忽略不计。

回源策略

回源路径优化

当边缘节点缓存未命中时，回源路径的质量直接影响用户体验：

直连回源：边缘节点直接与源站建立连接。简单直接，但在源站距离远时延迟高，且每个边缘节点独立建连导致源站连接数膨胀。

层级回源：按照 L1 → L2 → Shield → Origin 的层级回源。大幅减少源站连接数和回源流量，是大规模 CDN 的标准做法。

智能选路回源：CDN 内部网络选择最优路径回源。利用 CDN 节点间的专线或优化路由，绕开公网拥堵链路。

Request Collapsing

当同一资源同时被多个用户请求且缓存未命中时，避免每个请求都独立回源：

  • 第一个请求触发回源，后续相同请求排队等待
  • 回源完成后，一次性响应所有等待中的请求
  • 显著降低源站压力（"惊群效应"缓解）
  • 需要注意超时控制和队列深度限制

回源重试与容灾

  • 源站探活：定期健康检查源站可用性
  • 多源站切换：主源站不可用时自动切换到备用源站
  • 陈旧内容兜底（Stale-While-Revalidate）：回源失败时返回过期缓存，保证可用性
  • 源站限流：检测源站压力并主动降低回源频率

节点内部架构

请求处理流水线

边缘节点内部的请求处理通常经过以下阶段：

  1. 连接接入：TLS 终结、HTTP/2 复用、QUIC 处理
  2. 请求解析：URL 规范化、请求头分析、缓存键生成
  3. 缓存查找：内存缓存 → SSD 缓存 → 判断是否回源
  4. 访问控制：IP 黑名单、Token 验证、WAF 规则
  5. 内容处理：压缩、图片优化、动态插入（ESI）
  6. 响应发送：HTTP 流式响应、Range 请求处理

缓存存储架构

边缘节点通常采用分层存储：

  • L1 - 内存热缓存：存储最热门对象（RAM Cache），容量小但命中速度极快
  • L2 - SSD 温缓存：存储中等热度的对象，命中速度 ms 级
  • L3 - HDD 冷缓存：存储长尾内容，适合大文件和低频访问资源

缓存索引通常全量驻留内存，通过高效的数据结构（如 Cuckoo Filter、Bloom Filter）快速判断对象是否在本地。

调度系统设计

GSLB（全局负载均衡）

GSLB 是 CDN 调度系统的核心组件：

  • 整合 DNS 调度、HTTP 调度和 AnyCast 路由
  • 实时收集各节点的负载、延迟、容量信息
  • 执行调度策略：最近原则、最低负载、加权轮询
  • 支持策略分层：全局默认策略 → 客户级覆盖 → 内容级精细调度

实时质量反馈

调度的精确性依赖于质量探测数据的时效性：

  • 主动探测：GSLB 持续向各节点发送探测请求，测量延迟和可用性
  • 被动探测：从真实用户请求中提取性能指标（首字节时间、下载速率）
  • 客户端测速：通过嵌入的 JavaScript 或 SDK 收集真实用户体验数据
  • 综合评分：将多种信号综合为节点质量评分，作为调度依据

小结

CDN 架构与路由是一个系统工程，需要在多个维度（缓存层级、路由精度、回源效率、节点性能）进行协同优化。理解请求从用户到源站的完整路径，以及每个环节的设计选择和权衡，是 CDN 工程师的核心能力。后续章节将深入探讨缓存策略和动态加速这两个关键技术领域。
