分布式追踪概念

核心概念

分布式追踪（Distributed Tracing）是记录请求在分布式系统中端到端传播路径的技术。一个用户请求在微服务架构中可能经过数十个服务节点，追踪系统为每个请求生成全局唯一的 Trace，Trace 由多个 Span 组成，每个 Span 代表请求在一个服务中的处理过程。通过将所有 Span 按时间线和因果关系组织，追踪系统重建出请求的完整调用图，揭示延迟瓶颈、错误源头和服务依赖关系。

上下文传播
上下文传播（Context Propagation）是分布式追踪的核心机制，确保 TraceID 和 SpanID 在跨服务调用时正确传递。传播协议定义了上下文信息在不同传输层（HTTP Header、gRPC Metadata、消息队列属性）中的编码格式。


W3C Trace Context 是 W3C 标准化的传播格式，通过 traceparent 和 tracestate 两个 HTTP Header 传递上下文。traceparent 包含版本、TraceID、ParentSpanID 和 TraceFlags 四个字段，tracestate 承载厂商特定的扩展信息。


traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
tracestate: congo=t61rcWkgMzE,rojo=00f067aa0ba902b7
B3 传播格式（Zipkin 定义）使用 X-B3-TraceId、X-B3-SpanId、X-B3-ParentSpanId 和 X-B3-Sampled 四个 Header，也支持单 Header 压缩格式 b3: {TraceId}-{SpanId}-{Sampling}-{ParentSpanId}。B3 在 Zipkin 和 Jaeger 生态中广泛使用。


消息队列的上下文传播将 SpanContext 作为消息属性（Kafka Header、RabbitMQ Property）附加到消息中。消费者从消息属性中提取上下文，创建新的 Span 并设置 Parent 为发送者的 Span，实现跨异步边界的追踪链路连接。


采样策略
追踪采样（Sampling）决定哪些请求的追踪数据被记录和发送到后端。在高流量系统中，记录所有请求的追踪会产生巨大的数据量和性能开销，采样策略在可观测性和成本之间寻找平衡。

尾部采样（Tail-based Sampling）在 OpenTelemetry Collector 中实现，Collector 缓冲一段时间内的所有 Span，等 Trace 完整后根据条件（总延迟 > 阈值、包含错误 Span、匹配特定服务）决定是否保留。尾部采样确保异常请求的追踪不被丢弃，但需要足够的内存缓冲和合理的等待时间。


自适应采样根据当前流量和资源状况动态调整采样率。低流量时保持 100% 采样，高流量时自动降低采样率以控制后端存储压力。OpenTelemetry 的 parent_based 采样器遵循父 Span 的采样决策，保证同一 Trace 内的所有 Span 要么全部记录要么全部丢弃。

Jaeger 由 Uber 开发，是功能最全面的开源追踪系统。Jaeger 的 Architecture 包括 Agent（端采集）、Collector（接收和处理）、Query（查询服务）和 Ingester（Kafka 消费者）。Jaeger UI 提供追踪搜索、Trace 时间线视图、服务依赖拓扑图和追踪对比（Compare）功能。


Tempo 是 Grafana Labs 的追踪后端，设计理念是"只存储追踪，不建索引"。Tempo 直接将追踪数据以 Parquet 格式存储到对象存储（S3/GCS），不建立额外索引，通过 TraceID 直接寻址查询。这种设计极大降低了运维成本和存储开销，但需要依赖其他系统（日志或指标中的 TraceID）来发现感兴趣的追踪。


小结
    

  • 分布式追踪通过 Trace 和 Span 重建请求的端到端调用图，揭示延迟瓶颈和错误源头
    • 

  • W3C Trace Context 是标准化的上下文传播格式，B3 在 Zipkin 生态中广泛使用
    • 

  • 消息队列通过消息属性实现异步边界的追踪链路连接
    • 

  • 尾部采样确保异常请求不被丢弃，自适应采样在可观测性和成本间动态平衡
    • 

  • Jaeger 功能全面适合独立部署，Tempo 成本最低适合 PLG 技术栈
    • 

  • TraceID 是连接追踪与指标/日志的核心标识，贯穿三大支柱集成
