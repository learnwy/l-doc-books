OpenTelemetry 实战

核心概念

OpenTelemetry（OTel）是 CNCF 的可观测性标准框架，统一了分布式追踪、指标和日志的 API、SDK 和数据协议。OpenTelemetry 的目标是提供厂商中立的遥测数据采集能力——应用使用 OTel SDK 生成遥测数据，通过 OTLP（OpenTelemetry Protocol）发送到 OTel Collector，Collector 将数据导出到任意后端（Jaeger、Prometheus、Loki、Datadog 等）。更换后端无需修改应用代码，实现了遥测数据的可移植性。

SDK 集成与自动插桩
OpenTelemetry SDK 分为自动插桩（Auto-Instrumentation）和手动插桩（Manual Instrumentation）两种集成方式。自动插桩通过运行时注入或编译时修改，自动为常用框架和库（HTTP 服务器、数据库驱动、消息队列客户端）生成 Span，无需修改业务代码。手动插桩由开发者在关键业务逻辑中创建自定义 Span，记录业务特定的上下文信息。


import { NodeSDK } from '@opentelemetry/sdk-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-grpc';
import { OTLPMetricExporter } from '@opentelemetry/exporter-metrics-otlp-grpc';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';
import { PeriodicExportingMetricReader } from '@opentelemetry/sdk-metrics';

const sdk = new NodeSDK({
  serviceName: 'order-service',
  traceExporter: new OTLPTraceExporter({
    url: 'http://otel-collector:4317',
  }),
  metricReader: new PeriodicExportingMetricReader({
    exporter: new OTLPMetricExporter({
      url: 'http://otel-collector:4317',
    }),
    exportIntervalMillis: 15000,
  }),
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();
手动插桩用于记录业务逻辑中的关键操作，如订单创建、支付处理和库存扣减。通过 tracer.startActiveSpan() 创建 Span，设置 Attributes 记录业务上下文（订单 ID、金额、SKU），通过 span.recordException() 记录异常信息。


import { trace, SpanStatusCode } from '@opentelemetry/api';

const tracer = trace.getTracer('order-service');

async function createOrder(request: CreateOrderRequest): Promise<Order> {
  return tracer.startActiveSpan('createOrder', async (span) => {
    span.setAttribute('order.user_id', request.userId);
    span.setAttribute('order.item_count', request.items.length);
    try {
      const order = await orderRepository.create(request);
      span.setAttribute('order.id', order.id);
      span.setAttribute('order.total', order.total);
      span.setStatus({ code: SpanStatusCode.OK });
      return order;
    } catch (error) {
      span.recordException(error as Error);
      span.setStatus({ code: SpanStatusCode.ERROR, message: (error as Error).message });
      throw error;
    } finally {
      span.end();
    }
  });
}
语义约定（Semantic Conventions）标准化了 Span 属性的命名，确保不同语言和框架生成的遥测数据具有一致的结构。HTTP Span 使用 http.request.method、url.full、http.response.status_code 等标准属性名，数据库 Span 使用 db.system、db.statement、db.operation 等属性名。


Collector 架构与部署
OpenTelemetry Collector 是遥测数据的中转站，采用 Pipeline 架构：Receiver 接收数据 → Processor 处理数据 → Exporter 导出数据。多个 Pipeline 可以并行运行，处理不同类型的遥测数据。


receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 5s
    send_batch_size: 1024
  memory_limiter:
    check_interval: 1s
    limit_mib: 512
  attributes:
    actions:
      - key: environment
        value: production
        action: upsert
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow-traces
        type: latency
        latency: { threshold_ms: 1000 }

exporters:
  otlp/tempo:
    endpoint: tempo:4317
    tls: { insecure: true }
  prometheusremotewrite:
    endpoint: http://mimir:9009/api/v1/push
  loki:
    endpoint: http://loki:3100/loki/api/v1/push

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch, tail_sampling]
      exporters: [otlp/tempo]
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [prometheusremotewrite]
    logs:
      receivers: [otlp]
      processors: [memory_limiter, batch, attributes]
      exporters: [loki]
Collector 的部署模式包括 Agent（Sidecar/DaemonSet）和 Gateway 两种。Agent 模式在每个节点或 Pod 旁部署 Collector 实例，负责本地数据的接收和初步处理。Gateway 模式部署集中式 Collector 集群，接收所有 Agent 转发的数据，执行尾部采样等全局策略后导出到后端。生产环境推荐 Agent + Gateway 两层架构。

最佳实践包括：在应用启动的最早期初始化 SDK（确保所有框架加载前完成插桩）；使用 OTEL_SERVICE_NAME 等环境变量配置 SDK 参数（避免硬编码）；在 Kubernetes 中通过 Operator 自动注入 SDK 配置；为关键业务操作添加手动 Span，自动插桩覆盖基础设施层面。


资源检测（Resource Detection）自动识别应用运行环境的元数据（Kubernetes Pod Name、Node Name、Container ID、Cloud Provider/Region），附加到所有遥测数据上。这些元数据使运维人员能够快速定位问题发生在哪个节点、Pod 和容器中。


小结
    

  • OpenTelemetry 提供厂商中立的遥测采集标准，通过 OTLP 协议实现后端可替换
    • 

  • 自动插桩零代码修改覆盖基础设施层，手动插桩记录关键业务操作的上下文
    • 

  • Collector 的 Pipeline 架构实现数据的接收、处理和多后端导出
    • 

  • Agent + Gateway 两层部署架构平衡了本地性能和全局策略执行
    • 

  • 语义约定标准化 Span 属性命名，确保跨语言跨框架的遥测数据一致性
    • 

  • 环境变量配置和 Kubernetes Operator 简化了 SDK 的部署和管理
