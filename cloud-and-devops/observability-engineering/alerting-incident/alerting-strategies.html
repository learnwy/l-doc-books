告警策略

核心概念

告警策略（Alerting Strategy）定义了系统在什么条件下通知运维人员采取行动。有效的告警策略追求高信噪比——关键问题及时触发告警（避免遗漏），同时减少误报和低价值告警（避免告警疲劳）。告警疲劳（Alert Fatigue）是可观测性实践中最严重的组织问题，当告警数量过多且频繁误报时，运维人员开始忽略告警，导致真正的关键问题被错过。

基于 SLO 的告警
基于 SLO（Service Level Objective）的告警是最有效的告警策略，它直接衡量用户体验而非底层资源指标。传统告警基于资源阈值（CPU > 80%），但资源利用率高不一定影响用户；SLO 告警基于用户可感知的服务质量（成功率 < 99.9%、P99 延迟 > 500ms）。


错误预算燃烧速率（Error Budget Burn Rate）是 SLO 告警的核心指标。如果 SLO 是 99.9%（月度错误预算 = 0.1% × 30天 = 43.2 分钟），燃烧速率 1x 表示按正常速率消耗错误预算（月底刚好用完），10x 表示以 10 倍速率消耗（4.32 天就会耗尽）。


# 1小时燃烧速率（快速检测）
(
  sum(rate(http_requests_total{status=~"5.."}[1h]))
  /
  sum(rate(http_requests_total[1h]))
) / (1 - 0.999) > 14.4

# 6小时燃烧速率（避免误报）
(
  sum(rate(http_requests_total{status=~"5.."}[6h]))
  /
  sum(rate(http_requests_total[6h]))
) / (1 - 0.999) > 6
多窗口多燃烧速率告警（Multi-Window Multi-Burn-Rate Alerts）是 Google SRE 推荐的告警模式。通过组合短窗口（1h）高燃烧速率（14.4x）和长窗口（6h）中燃烧速率（6x）的条件，在快速检测和低误报之间取得平衡：短窗口捕捉突发问题，长窗口确认持续恶化。


Alertmanager 配置
Prometheus Alertmanager 是告警管理的核心组件，负责告警的分组（Grouping）、抑制（Inhibition）、静默（Silencing）和路由（Routing）。


global:
  resolve_timeout: 5m
  slack_api_url: 'https://hooks.slack.com/services/...'

route:
  receiver: default-slack
  group_by: ['alertname', 'service']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - match:
        severity: critical
      receiver: pagerduty-critical
      group_wait: 10s
      repeat_interval: 30m
    - match:
        severity: warning
      receiver: slack-warning
      group_wait: 1m

inhibit_rules:
  - source_match:
      severity: critical
    target_match:
      severity: warning
    equal: ['service']

receivers:
  - name: pagerduty-critical
    pagerduty_configs:
      - routing_key: '<key>'
        severity: critical
  - name: slack-warning
    slack_configs:
      - channel: '#ops-alerts'
        title: '{{ .GroupLabels.alertname }}'
        text: '{{ range .Alerts }}{{ .Annotations.summary }}{{ end }}'
  - name: default-slack
    slack_configs:
      - channel: '#ops-default'
告警分组将相同类型的告警合并为一条通知，避免同一问题触发大量独立告警。抑制规则在高级别告警触发时自动抑制低级别的相关告警——当服务 Critical 告警生效时，同一服务的 Warning 告警被自动静默。静默功能用于在计划维护期间临时屏蔽指定告警。

告警审查会议（Alert Review）每月或每季度进行一次，团队共同审查所有告警规则：移除不再有效的告警、调整频繁误报的阈值、为新增服务补充告警覆盖、验证告警文档的准确性。每条告警规则应包含 Runbook 链接，指导值班人员在收到告警后如何诊断和处理。


告警文档（Runbook）的标准结构包括：告警含义（什么指标异常说明什么问题）、影响范围（哪些用户/功能受影响）、诊断步骤（如何确认问题和定位根因）、修复步骤（标准操作流程）和升级路径（何时需要升级到高级工程师或管理层）。


小结
    

  • 有效告警策略追求高信噪比——关键问题不遗漏（高召回率）且误报最小化（高精确率），告警疲劳是可观测性实践中最严重的组织问题
    • 

  • SLO 告警基于用户可感知的服务质量而非底层资源指标，错误预算燃烧速率量化服务质量恶化速度
    • 

  • 多窗口多燃烧速率模式（短窗口 1h + 长窗口 6h）在快速检测突发问题和避免误报之间取得平衡
    • 

  • Alertmanager 通过分组（合并同类告警）、抑制（高级别屏蔽低级别）和路由（按严重程度分发）管理告警生命周期
    • 

  • 告警治理通过月度审查会议和质量指标（误报率<10%、响应时间、告警覆盖率>95%）持续优化告警系统
    • 

  • 每条告警规则必须附带 Runbook（含告警含义、影响范围、诊断步骤、修复步骤和升级路径），指导值班人员完成诊断和修复
    •
