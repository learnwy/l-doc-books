CI/CD 集成模式

平台与流水线的关系定位

CI/CD 系统是现代软件交付的心脏。几乎每个稍具规模的工程组织都已经拥有成熟的 CI/CD 基础设施——Jenkins、GitLab CI、GitHub Actions、ArgoCD 或其组合。IDP 面临的不是"要不要做 CI/CD"的问题，而是"如何与已有 CI/CD 系统优雅协作"的问题。

一个致命的反模式是：平台团队试图构建一个"比 Jenkins 更好的 Jenkins"。这条路不仅开发成本巨大，更会引发开发者的强烈抵触——没有人愿意重新学习一套构建系统。正确的定位是：IDP 作为 CI/CD 系统之上的编排层和体验层，它不替换流水线引擎，而是让流水线的使用变得更简单、更一致、更可治理。

这种定位带来三个核心价值：

  • 降低配置复杂度：开发者无需编写数百行 YAML，通过平台模板生成标准化流水线配置
  • 强制一致性：所有团队的构建流程遵循相同的安全扫描、测试要求和发布策略
  • 提供全局视图：跨所有服务的部署状态、构建成功率和变更频率汇聚到统一仪表盘

集成架构模式

根据平台对 CI/CD 系统的控制程度和抽象深度，可以分为三种主流集成模式：

模式一：模板注入模式（Template Injection）

平台提供流水线模板库，开发者在项目中引用模板而非从零编写。模板封装了组织标准的构建步骤、安全检查和部署策略。

# 开发者在项目中只需写这几行
include:
  - project: platform/ci-templates
    ref: v2.3
    file: /templates/go-service.yml

variables:
  SERVICE_NAME: payment-gateway
  DEPLOY_TARGETS: [staging, production]

优势：侵入性最低，开发者保留对流水线的完全可见性和可调试性。劣势：模板版本管理复杂，开发者仍可绕过模板直接编写自定义流水线。

模式二：代理执行模式（Proxy Execution）

平台接收开发者的高级意图（如"部署到生产"），在后台编排对 CI/CD 系统 API 的调用。开发者不直接与 CI/CD 系统交互，而是通过平台的统一界面操作。

开发者 → [平台 API] → [编排引擎] → [CI/CD API] → [构建/部署]
                                    ↓
                            [审批工作流]
                            [策略检查]
                            [审计日志]

优势：平台拥有完整的控制权，可以插入策略检查、审批流程和审计日志。劣势：增加了一个间接层，调试问题时需要同时理解平台层和 CI/CD 层。

模式三：声明式协调模式（Declarative Reconciliation）

平台定义"期望状态"（如"payment-gateway 的 v2.1 应运行在 production 集群"），由 GitOps 控制器持续协调实际状态与期望状态的差异。CI 负责构建制品，CD 由独立的协调器完成。

apiVersion: platform.internal/v1
kind: Deployment
metadata:
  name: payment-gateway
spec:
  artifact: registry/payment-gateway:v2.1
  target:
    cluster: production-east
    namespace: payments
  strategy:
    type: canary
    steps:
      - weight: 10
        pause: { duration: 5m }
      - weight: 50
        pause: { analysis: true }
      - weight: 100

优势：状态可追溯、自动漂移修复、与 Kubernetes 生态天然契合。劣势：需要团队理解声明式和最终一致性的思维模式。

流水线标准化策略

无论选择哪种集成模式，流水线标准化都是 IDP 的重要价值输出。标准化不是限制，而是"让 80% 的常见情况变得极其简单，同时允许 20% 的特殊情况有逃生通道"。

标准化层次：

层次 标准化内容 灵活性
必选（Hard Rules） 安全扫描、许可证检查、签名验证 不可跳过
默认（Soft Defaults） 测试覆盖率阈值、代码规范检查 可申请例外
推荐（Best Practices） 性能测试、混沌测试 自愿采纳

标准步骤的执行保证：通过 CI 系统的 "required checks" 机制确保必选步骤不被绕过。即使开发者绕开平台直接操作 CI 系统，关键安全步骤仍然强制执行。

部署策略抽象

部署策略是 CI/CD 集成中最能体现平台价值的领域之一。直接编写 Canary 或 Blue-Green 部署的配置需要深入理解流量路由、健康检查和回滚机制——这些复杂性应由平台承担。

平台向开发者暴露的部署策略选择器：

deployment_strategy:
  type: canary | blue-green | rolling | immediate

  # Canary 特有参数
  canary:
    initial_weight: 5%
    increment: 10%
    analysis_interval: 5m
    rollback_on:
      - error_rate > 1%
      - p99_latency > 500ms

  # Blue-Green 特有参数
  blue_green:
    warmup_duration: 2m
    switch_traffic: manual | auto
    keep_previous: 1h

平台在底层将这些高级配置翻译为具体工具的实现——可能是 Argo Rollouts 的 CRD、Flagger 的 Canary 资源、或者直接操作 Kubernetes Service 和 Ingress。开发者选择策略时不需要知道底层用了什么工具。

构建制品管理

IDP 集成 CI/CD 时必须解决制品管理的一致性问题：一个制品从构建到部署到生产的全链路追踪。

制品签名与验证：所有通过平台流水线产生的容器镜像自动签名（如使用 Sigstore/Cosign）。部署时验证签名，确保只有经过认证流水线构建的制品才能进入生产环境。

SBOM 生成：构建过程自动生成 Software Bill of Materials，记录制品的所有依赖及其版本。这为后续的漏洞影响分析和合规审计提供数据基础。

制品元数据关联：每个制品携带丰富的元数据——源代码 commit、构建者、测试报告链接、安全扫描结果。在服务目录中可追溯任一运行中版本的完整构建历史。

推进策略（Promotion）：制品不直接部署到生产，而是经过多环境逐级推进：dev → staging → production。每次推进需满足该环境的准入条件（如 staging 要求集成测试全部通过）。

跨服务部署编排

当一个变更涉及多个微服务的协调部署时（如 API 版本升级需要提供方和消费方同步更新），单个服务的 CI/CD 流水线不足以处理。平台在这里提供跨服务的部署编排能力。

依赖感知部署：根据服务目录中的依赖关系，自动确定部署顺序。如果 Service A 依赖 Service B 的新接口，确保 B 先部署并验证后再部署 A。

部署组（Deploy Group）：将多个服务绑定为一个部署组，支持原子化的全组回滚。如果组内任一服务部署失败，整组回滚到上一个已知良好状态。

变更冻结窗口：平台维护组织级别的部署日历，在关键业务时段（如电商大促前 48 小时）自动冻结非紧急部署。紧急修复需要更高级别的审批才能绕过冻结。

小结

CI/CD 集成是 IDP 最需要"谦逊"的能力领域——不替代而是增强已有系统。模板注入模式适合起步阶段，代理执行模式提供更强控制，声明式协调模式代表长期方向。无论选择哪种模式，流水线标准化、部署策略抽象和制品全链路追踪都是平台必须解决的核心问题。最终目标是让开发者用一行配置或一次点击完成原本需要百行 YAML 和数小时调试的部署任务。
