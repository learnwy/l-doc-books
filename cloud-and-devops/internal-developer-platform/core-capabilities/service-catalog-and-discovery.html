服务目录与发现

服务目录解决什么问题

当一个工程组织的微服务数量突破三位数时，一个看似简单的问题变得异常困难："谁负责支付网关服务？它的 API 文档在哪里？它依赖哪些下游？最近一次部署是什么时候？"

这些信息散落在 Git 仓库的 README 里、Confluence 页面的角落中、Slack 频道的聊天记录里、某位资深工程师的脑海中。新人加入团队需要数周才能建立起对服务全景的模糊认知；跨团队协作时，光是找到正确的联系人就可能消耗数小时。

服务目录是这个问题的系统性解决方案：它提供一个中心化的、始终最新的、可搜索的服务注册表，将每个服务的元数据——所有权、接口定义、依赖关系、运行状态——结构化地组织在统一的视图中。

从 IDP 的视角看，服务目录是所有其他平台能力的元数据基础。自助式资源供给需要知道"为哪个服务供给"；环境管理需要知道"这个服务的依赖图是什么"；可观测性集成需要知道"监控数据应该关联到哪个服务"。没有可靠的服务目录，其他能力就失去了锚点。

数据模型设计

服务目录的核心是一个精心设计的数据模型——它定义了"一个服务"到底包含哪些结构化信息。数据模型的设计需要平衡完整性（信息足够丰富）和可维护性（信息不会过时）。

核心实体：

apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: payment-gateway
  description: 处理所有支付渠道的统一网关
  tags: [payments, gateway, critical]
  annotations:
    github.com/project-slug: org/payment-gateway
    pagerduty.com/service-id: PD123456
spec:
  type: service
  lifecycle: production
  owner: team-payments
  system: payment-system
  providesApis:
    - payment-api
  consumesApis:
    - user-api
    - risk-api
  dependsOn:
    - resource:postgresql-payments
    - resource:redis-cache

实体类型层次：

实体类型 描述 示例
System 业务能力的顶层分组 支付系统、用户系统
Component 可独立部署的软件单元 payment-gateway, user-service
API 服务间的接口契约 Payment API v2 (OpenAPI)
Resource 基础设施依赖 PostgreSQL 实例、Redis 集群
Domain 业务域的逻辑分组 交易域、用户域
Group 团队或组织单元 team-payments, platform-sre

关系建模：实体之间通过有向关系连接——ownsComponent、providesApi、consumesApi、dependsOn。这些关系构成一个图结构，支撑依赖分析、影响评估和拓扑可视化。

数据鲜活性保障

服务目录最大的敌人是数据腐烂（Data Decay）。一份上周还准确的信息，这周可能因为团队重组、服务迁移或 API 变更而过时。如果开发者发现目录中的信息不可靠，他们会迅速放弃使用——一旦失去信任，重建比初始建设更难。

保障数据鲜活性的策略：

自动采集优先：凡是能从已有系统自动获取的信息，绝不要求人工填写。代码仓库信息从 GitHub/GitLab 同步；部署状态从 CI/CD 系统采集；运行时指标从监控系统拉取；团队归属从 HR 系统或 LDAP 映射。

声明式元数据文件（catalog-info.yaml）：将服务的核心元数据以 YAML 文件形式存放在代码仓库中，与代码一起版本化管理。这样做的好处是：元数据变更经过 Code Review、可追溯历史、天然与代码保持同步。

健康度评分：为每个服务的目录条目计算"信息完整度分数"。例如：有描述 +10 分、有 API 文档链接 +15 分、有负责人 +20 分、最近 30 天有代码提交 +10 分。低分服务的负责团队收到自动提醒。

变更事件驱动更新：当检测到关键事件（团队重组、仓库迁移、API 版本升级）时，自动标记受影响的目录条目为"待验证"，并通知负责人确认。

发现体验设计

有了完整准确的数据之后，如何让开发者高效地找到所需信息是下一个设计挑战。发现体验直接决定服务目录的实际使用率。

全文搜索：支持对服务名称、描述、标签、API 端点的全文搜索。搜索结果按相关性排序，关键信息（所有者、状态、最近更新时间）在搜索结果卡片中直接展示。

关系图谱浏览：提供交互式的依赖关系可视化。开发者可以从任意一个服务出发，探索其上下游依赖、共同依赖的基础设施，以及通过传递依赖间接关联的服务。

分面过滤：按类型（服务/库/前端）、生命周期（开发中/生产/已废弃）、团队、技术栈等维度进行筛选。分面过滤帮助开发者在大量结果中快速缩小范围。

上下文感知推荐：根据开发者当前正在开发的服务，推荐可能相关的其他服务。例如，正在开发用户注册功能时，推荐认证服务和邮件通知服务。

服务记分卡与治理

服务目录不仅是信息查询工具，还可以作为工程质量治理的载体。通过定义一组"好服务应满足的标准"，并自动评估每个服务的达标情况，形成可量化的工程健康度视图。

典型的记分卡维度：

维度 检查项示例 权重
文档 有 README、有 API 文档、有架构图 20%
测试 单元测试覆盖率 >80%、有集成测试 20%
安全 无已知高危漏洞、依赖定期更新 25%
运维 有告警规则、有 Runbook、SLO 已定义 20%
所有权 有明确负责人、有 On-call 轮换 15%

记分卡的结果不应用于惩罚，而应用于引导。低分服务的团队获得具体的改进建议和优先级排序，而非笼统的"请改进"指令。平台团队可以基于记分卡数据识别系统性问题（例如"全组织的测试覆盖率普遍偏低"），并投入工具或培训资源解决。

实现方案选型

Backstage（CNCF 项目）：由 Spotify 开源的开发者门户框架，服务目录是其核心功能。优势在于活跃的社区、丰富的插件生态和灵活的定制能力。适合有 3+ 人平台团队且愿意投入定制开发的组织。

Port：商业化的 IDP 产品，提供开箱即用的服务目录和自助操作能力。适合希望快速获得结果、不想承担太多自建成本的团队。

OpsLevel：专注于服务目录和记分卡的 SaaS 产品。强调"从 Day 1 开始"的简单性，适合初创阶段的平台团队。

自建方案：基于 Graph Database（如 Neo4j）或关系数据库构建。灵活度最高但投入最大，仅推荐在现有商业/开源方案无法满足独特需求时选择。

小结

服务目录是 IDP 的元数据基石，解决了"组织里有什么、谁负责、如何找到"的核心发现问题。成功的服务目录需要：精心设计的数据模型覆盖实体和关系、自动化驱动的数据鲜活性保障、以用户为中心的发现体验设计，以及基于记分卡的温和治理机制。它不仅是一个查询工具，更是平台所有其他能力的信息锚点。
