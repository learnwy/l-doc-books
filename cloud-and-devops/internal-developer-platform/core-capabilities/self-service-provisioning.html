自助式资源供给

从工单驱动到自助驱动

传统的资源供给流程像一条漫长的接力赛跑道：开发者提交工单 → 项目经理审批 → 运维团队排队 → 手动执行 → 验证确认 → 通知开发者。即使每个环节只耗时 4 小时，一个"创建数据库实例"的请求也可能需要 2-3 个工作日才能完成。

当组织只有 10 个开发者时，这种模式尚可接受。但当开发者数量增长到数百人，每天数十个资源请求涌入时，运维团队成为瓶颈、开发者陷入等待、组织敏捷性被严重削弱。更隐蔽的损失是：开发者为了避免等待而走捷径——使用不安全的配置、跳过必要的步骤、或者在本地模拟生产环境然后祈祷"上线后也能跑"。

自助式资源供给的核心理念是：将标准化的操作封装为开发者可直接触发的自动化动作，同时保留必要的治理控制（预算限制、安全策略、审计日志）。开发者获得的是速度和自主权，组织保留的是安全和可控性。

自助操作的设计原则

最小权限默认值（Secure Defaults）

自助操作应预设安全的默认配置。当开发者请求一个 PostgreSQL 实例时，默认应启用加密存储、配置网络隔离、设置合理的资源限制。开发者可以选择覆盖某些默认值，但需要更高级别的审批。

幂等性保证

每个自助操作必须是幂等的——重复执行不会产生副作用。这不仅防止意外的双重创建，也让错误恢复变得简单：如果操作中途失败，重新触发即可。

可观察的执行过程

操作触发后，开发者应能实时看到执行进度、当前步骤和预计完成时间。黑盒式的"请求已提交，请等待"体验与工单驱动相比并无本质改善。

渐进式自助（Progressive Self-Service）

不是所有操作都适合完全自助。按风险等级分层：

风险等级 审批方式 示例
低风险 无需审批，即时执行 创建开发环境、查看日志
中风险 自动策略检查 + 团队 Lead 审批 创建生产数据库、申请外网访问
高风险 多级人工审批 删除生产资源、修改安全组规则
极高风险 禁止自助，必须走变更管理 网络架构变更、核心中间件升级

操作抽象层设计

自助供给的技术核心是"操作抽象层"——它将底层基础设施的复杂 API 转化为面向开发者的简洁接口。

声明式操作定义：

apiVersion: platform.internal/v1
kind: SelfServiceAction
metadata:
  name: create-postgresql
  displayName: 创建 PostgreSQL 数据库
  description: 为服务创建独立的 PostgreSQL 实例
spec:
  inputs:
    - name: service_name
      type: string
      required: true
      description: 关联的服务名称
    - name: size
      type: enum
      options: [small, medium, large]
      default: small
      description: 实例规格
    - name: environment
      type: enum
      options: [dev, staging, production]
      required: true
  steps:
    - id: provision
      action: terraform:apply
      input:
        module: modules/postgresql
        variables:
          instance_name: '${{ inputs.service_name }}-db'
          instance_class: '${{ inputs.size }}'
          vpc: '${{ lookup.vpc_for_env(inputs.environment) }}'
    - id: register
      action: catalog:register
      input:
        entity:
          kind: Resource
          name: '${{ inputs.service_name }}-postgresql'
          spec:
            type: database
            owner: '${{ context.user.team }}'
    - id: notify
      action: slack:notify
      input:
        channel: '${{ context.user.team_channel }}'
        message: 'PostgreSQL 实例已创建：${{ steps.provision.output.endpoint }}'
  policies:
    - type: budget-check
      params:
        max_monthly_cost: 500
    - type: naming-convention
      params:
        pattern: '^[a-z][a-z0-9-]+$'

操作编排引擎：负责按步骤顺序执行操作、处理失败回滚、记录审计日志。主流实现包括 Backstage Scaffolder、Crossplane Compositions、Terraform Cloud Run Tasks。

资源生命周期管理

供给只是开始。自助平台还需要覆盖资源的完整生命周期：创建 → 配置 → 扩缩 → 监控 → 清理。

配置变更：资源创建后的配置调整（如增加数据库连接数、修改内存限制）也应自助化。通过 GitOps 模式：开发者修改配置文件并提交 PR，CI 流水线自动应用变更，平台确保变更在安全范围内。

弹性伸缩：提供自助的手动扩缩能力，同时集成自动弹性策略。开发者设定伸缩规则（如"CPU > 70% 时扩容"），平台负责执行和告警。

成本可见性：每个自助创建的资源关联到团队的成本账户。开发者在创建资源时看到预估月度成本，团队负责人定期收到资源使用报告。不使用的资源通过"闲置检测"自动标记并建议清理。

优雅退役：资源不再需要时，提供安全的删除流程——检查是否有其他服务依赖、备份必要数据、从服务目录注销、清理相关权限和网络规则。

治理与合规集成

自助化不意味着放弃治理。相反，自助平台应将治理要求编码为自动化策略，让合规变成"默认发生的事"而非"开发者额外要做的事"。

策略即代码（Policy as Code）：使用 OPA/Rego 或 Kyverno 定义治理策略。例如：

  • 生产数据库必须启用多可用区部署
  • 所有存储资源必须启用加密
  • 单团队资源总成本不超过月度预算
  • 服务必须有至少一个负责人

审批工作流：中高风险操作触发自动化审批流。审批人通过 Slack/邮件收到请求详情和风险评估，一键批准或拒绝。审批历史完整记录，支持合规审计。

漂移检测：定期扫描实际资源配置与期望配置的偏差。如果有人通过控制台手动修改了通过平台创建的资源，自动发出告警并提供修复建议。

用户界面模式

自助操作可以通过多种界面形态触达开发者：

Web Portal：提供表单化的图形界面，适合不频繁的操作（如创建新服务）。优势是直观、可发现性高；劣势是表达能力有限。

CLI 工具：提供命令行接口，适合频繁操作和脚本化场景。platform create db --name orders-db --size medium --env staging

ChatOps：通过 Slack/Teams Bot 触发操作。适合简单查询和低风险操作。@platform create env for payment-service

API：RESTful 或 gRPC 接口，供其他系统集成调用。CI/CD 流水线中的资源创建通常走这条路径。

IDE 插件：在开发者最常用的工具中直接嵌入自助能力。VS Code 插件支持右键创建开发环境或查看服务依赖。

最佳实践是提供多种界面但共享同一个后端引擎，确保无论通过哪种方式操作，策略执行和审计记录保持一致。

小结

自助式资源供给将开发者从工单等待中解放出来，同时通过策略即代码保留了治理控制。成功的自助平台需要：安全的默认配置、渐进式的审批分层、声明式的操作抽象、完整的资源生命周期管理、以及多形态的用户界面。关键的设计哲学是"让正确的事情变成最简单的事情"——当合规操作比绕过操作更快时，开发者自然会选择合规。
