容器与 Kubernetes 密钥

Kubernetes Secret 的安全缺陷

Kubernetes 原生的 Secret 资源是集群中管理敏感数据的标准方式，但其默认行为存在多个需要注意的安全隐患。理解这些限制是选择正确加固方案的前提。

Base64 不是加密：K8s Secret 的 data 字段使用 Base64 编码，这仅仅是一种数据表示格式，任何人拿到 Secret YAML 都能直接解码获取明文。Base64 的目的是支持二进制数据存储，不提供任何安全保护。

etcd 明文存储：默认配置下，Secret 以明文形式存储在 etcd 数据库中。拥有 etcd 备份访问权限或直接 etcd 连接能力的人可以读取所有 Secret。

广泛的读取权限：在同一 Namespace 中，默认的 RBAC 配置可能允许过多的 ServiceAccount 读取 Secret。一个被攻破的 Pod 可能获取同 Namespace 内所有 Secret。

挂载共享：通过 Volume 挂载的 Secret 对 Pod 内所有容器可见（包括 Sidecar）。如果一个 Pod 有多个安全等级不同的容器，低安全容器也能访问高安全密钥。

Secret 传播不加密：API Server 到 kubelet 的 Secret 传递默认通过 TLS 保护，但 kubelet 将 Secret 写入节点 tmpfs 时，节点上的其他进程可能通过 /proc 访问。

etcd 加密与 KMS Provider

解决 etcd 明文存储的第一步是启用静态加密（Encryption at Rest）。

EncryptionConfiguration 允许指定加密提供者：

apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - kms:
          apiVersion: v2
          name: aws-encryption-provider
          endpoint: unix:///run/kmsplugin/socket.sock
      - identity: {} # fallback: 不加密（读取旧数据）

加密提供者的选择：

提供者 安全级别 适用场景
identity 无加密 默认/迁移过渡
secretbox 本地密钥加密 单节点测试环境
aesgcm AES-GCM 加密 需要手动轮换密钥
kms v2 外部 KMS 保护 生产环境推荐

KMS v2 Provider 是生产环境的最佳选择——加密密钥由外部 KMS（AWS KMS、GCP Cloud KMS、Azure Key Vault、HashiCorp Vault）管理，即使 etcd 数据被盗，没有 KMS 访问权限无法解密。

External Secrets Operator

External Secrets Operator (ESO) 是 CNCF 沙箱项目，解决了「如何将外部密钥管理系统的密钥同步到 Kubernetes Secret 对象」的问题。

核心 CRD：

  • SecretStore / ClusterSecretStore：定义如何连接外部密钥管理系统（认证方式、端点）
  • ExternalSecret：声明需要同步哪些外部密钥、以什么格式创建 K8s Secret
  • ClusterExternalSecret：跨 Namespace 的 ExternalSecret

工作流程：

配置示例（连接 AWS Secrets Manager）：


apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-secretsmanager
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1
      auth:
        jwt:
          serviceAccountRef:
            name: external-secrets-sa
---
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: app-secrets
spec:
  refreshInterval: 5m
  secretStoreRef:
    name: aws-secretsmanager
  target:
    name: app-secrets
    creationPolicy: Owner
  data:
    - secretKey: db-password
      remoteRef:
        key: production/myapp/database
        property: password
ESO 的 refreshInterval 确保外部密钥变更能在指定时间内同步到集群。当外部密钥轮换时，K8s Secret 自动更新，使用 Volume 挂载的 Pod 会在 kubelet 同步周期内获取新值（默认 1 分钟）。


Sealed Secrets
Sealed Secrets（Bitnami）解决了一个特定问题：如何在 Git 仓库中安全存储 Kubernetes Secret 的定义。


核心思想：使用非对称加密——集群中运行的 Controller 持有私钥，开发者使用对应公钥加密 Secret 值为 SealedSecret CR。SealedSecret 可以安全提交到 Git，Controller 在集群中解密并创建原始 Secret。


# 加密 Secret
kubeseal --format yaml < secret.yaml > sealed-secret.yaml

# sealed-secret.yaml 可以安全地提交到 Git
# Controller 在集群中自动解密为 Secret
适用场景：完全 GitOps 工作流，所有资源（包括密钥）都以声明式方式存储在 Git 中。但需要注意：密钥轮换时需要重新 seal，且 Controller 的加密密钥本身也需要备份。


CSI Secret Store Driver 详解
Secrets Store CSI Driver 是 Kubernetes SIG Auth 维护的项目，通过标准 CSI Volume 机制将密钥直接挂载到 Pod，绕过了 K8s Secret 对象。


优势：密钥不作为 K8s Secret 对象存在于 etcd 中——减少了 Secret 对象被 RBAC 误配暴露的风险。


支持的后端 Provider：


    

  • HashiCorp Vault
    • 

  • AWS Secrets Manager / AWS Systems Manager Parameter Store
    • 

  • Azure Key Vault
    • 

  • GCP Secret Manager
    • 



SecretProviderClass 配置示例：


apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: vault-db-creds
spec:
  provider: vault
  parameters:
    roleName: 'myapp'
    vaultAddress: 'https://vault.internal:8200'
    objects: |
      - objectName: "db-password"
        secretPath: "secret/data/myapp/db"
        secretKey: "password"
  secretObjects: # 可选：同时创建 K8s Secret（用于环境变量注入）
    - secretName: db-secret
      type: Opaque
      data:
        - objectName: db-password
          key: password
容器镜像安全与密钥
容器构建过程中的密钥处理是另一个常被忽视的风险点。


Docker Build 中的密钥注入：


❌ 反模式——ARG 传递密钥：


ARG NPM_TOKEN
RUN echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > .npmrc
RUN npm install
RUN rm .npmrc  # 仍然存在于前序镜像层中！
✅ 正确方式——BuildKit Secret Mount：


# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm install
# Secret 不会出现在任何镜像层中
构建命令：docker build --secret id=npmrc,src=$HOME/.npmrc .


多阶段构建隔离：即使密钥在构建阶段泄露到中间层，只要最终镜像来自一个干净的阶段，生产镜像中不会包含密钥。但中间镜像如果被推送到 Registry，仍然存在泄露风险。


镜像扫描：在 CI/CD Pipeline 中集成镜像密钥扫描（Trivy、Snyk Container），检测镜像层中残留的密钥——包括 SSH Key、AWS 凭据、私钥文件等。作为镜像推送前的 Gate 检查。
