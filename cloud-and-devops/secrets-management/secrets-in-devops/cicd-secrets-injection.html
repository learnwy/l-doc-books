CI/CD 密钥注入

流水线中密钥的安全挑战

CI/CD 流水线是现代软件交付的自动化引擎，但这些自动化流程需要大量凭据才能运行——拉取代码仓库的 SSH Key、推送镜像的 Registry Token、部署到云平台的 IAM 凭据、运行集成测试的数据库密码。这些「机器身份」的密钥管理面临独特的安全挑战。

流水线密钥的特殊性在于：

  1. 执行环境不可信：CI Runner 可能是共享的、临时的、甚至是公共的（开源项目的 PR 构建）
  2. 日志广泛可见：构建日志通常对开发团队可见，密钥可能意外出现在日志中
  3. 供应链风险：流水线中的第三方 Action/Plugin 可能窃取环境中的密钥
  4. PR 攻击面：恶意 Pull Request 可能修改构建脚本以导出密钥

GitHub Actions Secrets

GitHub Actions 提供了多层级的密钥存储：Organization Secrets、Repository Secrets、Environment Secrets。每一层都有不同的访问范围和管控粒度。

密钥层级设计：

层级 范围 适用场景
Organization Secret 所有仓库或指定仓库组 共享的 Docker Registry 凭据、NPM Token
Repository Secret 单个仓库所有工作流 该项目的部署密钥、API Token
Environment Secret 仓库中特定环境 production/staging 各自的数据库密码

Environment 保护规则是 GitHub Actions 密钥安全的关键特性：

# 部署到 production 环境需要审批
jobs:
  deploy-prod:
    environment:
      name: production
      url: https://myapp.com
    steps:
      - name: Deploy
        env:
          DB_PASSWORD: ${{ secrets.PROD_DB_PASSWORD }}
        run: ./deploy.sh

配合 Environment 保护规则：要求指定审批人批准、限制部署分支（仅 main）、设置等待计时器。这确保了 production 密钥不会被任意分支或 PR 触发的工作流获取。

Fork PR 安全：GitHub 默认不向 Fork 仓库的 PR 工作流暴露密钥（Secrets 对 fork PR 不可见）。但 pull_request_target 事件会在主仓库上下文运行——如果该工作流执行了 PR 代码，就会将密钥暴露给攻击者。

日志遮蔽：GitHub Actions 自动检测 Secrets 的值并在日志中替换为 ***。但这只对精确匹配有效——如果密钥被 Base64 编码、拆分、或部分截取后打印，遮蔽不会生效。

GitLab CI/CD Variables

GitLab 的 CI/CD Variables 系统提供了更细粒度的控制选项：

变量属性：

  • Protected：仅在受保护的分支/标签上可用（如 main、release/*）
  • Masked：在 Job 日志中自动遮蔽（要求值满足特定格式：Base64 可解码、无换行）
  • File 类型：值写入文件而非环境变量，路径通过变量名引用（适合证书、密钥文件）

Group 级别变量继承到所有子组和项目，实现组织级密钥的统一管理。变量优先级：Job > Project > Group > Instance。

与 Vault 的原生集成（GitLab Premium+）：

deploy:
  variables:
    VAULT_AUTH_ROLE: 'gitlab-deploy'
  secrets:
    DATABASE_PASSWORD:
      vault: production/db/password@secret
      file: false

GitLab Runner 自动通过 JWT 认证到 Vault，获取密钥注入到 Job 环境。这避免了在 GitLab 中存储长期凭据——Runner 使用短生命周期的 JWT Token 换取即时密钥。

Jenkins Credentials Plugin

Jenkins 通过 Credentials Plugin 提供密钥管理，支持多种凭据类型：Username/Password、SSH Key、Secret Text、Secret File、Certificate。

安全存储：Jenkins 将凭据加密存储在 Master 节点的 credentials.xml 中，加密密钥派生自 Jenkins 实例的 Secret Key（$JENKINS_HOME/secrets/master.key）。

作用域控制：

  • System：仅 Jenkins 系统操作可用（如连接 Agent 节点）
  • Global：所有 Job 可访问
  • Folder：仅特定文件夹下的 Job 可访问

Declarative Pipeline 绑定：

pipeline {
    environment {
        DB_CREDS = credentials('production-db-credentials')
        // 自动创建: DB_CREDS_USR, DB_CREDS_PSW
    }
    stages {
        stage('Deploy') {
            steps {
                sh 'deploy --user $DB_CREDS_USR --pass $DB_CREDS_PSW'
            }
        }
    }
}

Jenkins 密钥的风险点：

  • 任何有 Job 配置权限的用户都可以编写脚本打印环境变量
  • Pipeline Replay 功能允许修改脚本逻辑而不留痕迹
  • credentials.xml 备份可能包含可解密的凭据
  • 共享库（Shared Library）代码运行在沙箱外，可以直接访问凭据

缓解方案：使用 Folder-scoped credentials 限制访问范围、禁用 Pipeline Replay、启用 Audit Trail 插件记录凭据使用。

临时凭据与 OIDC 联邦

最安全的 CI/CD 密钥策略是根本不存储长期凭据——改用即时生成的临时凭据。OIDC（OpenID Connect）联邦是实现这一目标的现代方案。

工作原理：

  1. CI/CD 平台（GitHub/GitLab）在每次 Job 运行时签发一个短生命周期的 OIDC JWT Token
  2. Token 包含上下文信息（仓库、分支、工作流、触发者）
  3. 云平台配置信任该 CI/CD 平台的 OIDC Provider
  4. Job 使用 OIDC Token 向云平台换取临时凭据（STS AssumeRoleWithWebIdentity）
  5. 临时凭据在 Job 结束后自动过期

GitHub Actions + AWS OIDC 示例：

permissions:
  id-token: write # 获取 OIDC Token 的权限

steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789:role/github-deploy
      aws-region: us-east-1
      # 无需 AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY

AWS 侧配置 Trust Policy：

{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::123456:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:sub": "repo:myorg/myrepo:ref:refs/heads/main"
    }
  }
}

条件约束确保只有特定仓库的特定分支才能获取凭据——即使攻击者控制了组织中的另一个仓库，也无法冒充。

密钥泄露防护

即使做了完善的密钥管理，运行时泄露仍然可能发生。防御措施包括：

构建日志净化：除了平台自带的遮蔽功能，还应在脚本中主动避免打印敏感信息。使用 set +x 禁用 Bash 的命令回显、将密钥操作重定向到 /dev/null、在 Docker build 中使用 --secret flag 而非 ARG。

密钥扫描：在 CI/CD Pipeline 中集成密钥扫描工具（gitleaks、truffleHog、detect-secrets），确保提交的代码不包含硬编码密钥。作为 PR 检查的必要条件。

最小权限设计：每个 Pipeline Job 只获取当前步骤所需的最小权限密钥。部署 Job 有部署权限，测试 Job 只有测试环境权限——不要复用同一个全能凭据。

短生命周期强制：所有 Pipeline 使用的凭据应有尽可能短的有效期。GitHub Actions 的 GITHUB_TOKEN 默认每次 Job 生成、Job 结束失效。AWS STS 临时凭据设置为 Job 最大运行时间的 1.5 倍。
