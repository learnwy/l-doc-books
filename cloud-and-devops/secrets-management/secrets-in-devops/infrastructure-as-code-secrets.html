基础设施即代码中的密钥

IaC 的密钥困境

基础设施即代码（Infrastructure as Code）将基础设施的创建和管理转化为代码和声明式配置。然而，这些配置不可避免地需要引用敏感凭据——云平台 API Key、数据库 Root 密码、TLS 证书、SSH 密钥。IaC 工具面临的核心矛盾是：代码应该版本化并可审查，但其中包含的密钥不能暴露。

Terraform、Pulumi、CloudFormation 等 IaC 工具的密钥风险集中在三个层面：

  1. 配置文件层：.tf / .yaml 文件中直接硬编码密钥值
  2. 状态文件层：terraform.tfstate 中以明文存储所有资源属性（包括生成的密码）
  3. 执行输出层：terraform plan/apply 的输出可能展示敏感值

Terraform 中的密钥管理

State 文件的安全问题是 Terraform 密钥安全的核心挑战。Terraform State 记录了所有已管理资源的完整属性——包括 aws_db_instance 的 master password、aws_iam_access_key 的 secret key 等。

Remote State 后端加密是最低安全基线：

terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "production/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true                    # S3 SSE 加密
    kms_key_id     = "arn:aws:kms:..."      # 指定 KMS 密钥
    dynamodb_table = "terraform-locks"       # 状态锁
  }
}

确保 S3 Bucket 策略禁止公开访问、版本控制启用（审计历史变更）、访问日志启用。

sensitive 标记防止输出泄露：

variable "db_password" {
  type      = string
  sensitive = true  # plan/apply 输出中显示为 (sensitive value)
}

output "connection_string" {
  value     = "postgres://admin:${var.db_password}@${aws_db_instance.main.endpoint}/mydb"
  sensitive = true
}

但 sensitive 标记不影响 State 文件中的存储——State 中仍然是明文。这只是输出层的保护。

Vault Provider 集成——最佳实践是从 Vault 动态获取密钥：

provider "vault" {
  address = "https://vault.internal:8200"
  # 认证通过环境变量 VAULT_TOKEN 或其他 auth method
}

data "vault_generic_secret" "db" {
  path = "secret/data/production/database"
}

resource "aws_db_instance" "main" {
  engine         = "postgres"
  instance_class = "db.t3.medium"
  username       = data.vault_generic_secret.db.data["username"]
  password       = data.vault_generic_secret.db.data["password"]
}

这种方式下密钥不出现在 .tf 文件中，但仍会被记录在 State 文件中。解决 State 泄露的最终方案是严格控制 State 后端的访问权限。

SOPS：加密即版本控制

SOPS（Secrets OPerationS）由 Mozilla 开发，解决了「敏感配置文件如何安全地存储在 Git 中」的问题。它的核心思想是对文件中的值进行加密，保留键名明文——既能安全存储密钥，又保持配置文件的可读结构。

SOPS 的加密粒度：

# 加密前
database:
  host: db.internal
  password: super-secret-password

# SOPS 加密后
database:
  host: db.internal          # 非敏感字段保持明文
  password: ENC[AES256_GCM,data:abc...,iv:...,tag:...,type:str]
sops:
  kms:
    - arn: arn:aws:kms:us-east-1:123:key/abc-123
  lastmodified: "2024-01-15T10:30:00Z"
  version: 3.8.1

多密钥源支持：SOPS 支持同时使用多个 KMS 密钥加密——AWS KMS、GCP Cloud KMS、Azure Key Vault、age、PGP。解密时任何一个密钥源可用即可解密。这实现了多云环境的密钥冗余。

与 Terraform 结合使用 sops provider：

provider "sops" {}

data "sops_file" "secrets" {
  source_file = "secrets.enc.yaml"
}

resource "aws_db_instance" "main" {
  password = data.sops_file.secrets.data["database.password"]
}

SOPS 的工作流：

  1. 创建 .sops.yaml 配置规则（哪些文件用哪些密钥加密）
  2. sops secrets.yaml 编辑密钥文件（自动解密、编辑、重加密）
  3. 加密后的文件提交到 Git
  4. CI/CD 或 Terraform 运行时通过 IAM 角色获取 KMS 解密权限
  5. 自动解密并使用

git-crypt：透明加密的 Git 工作流

git-crypt 提供对 Git 仓库中特定文件的透明加密——文件在本地检出时是明文，push 到远端时自动加密。对于已授权的开发者，加解密过程完全透明。

配置（.gitattributes）：

secrets/** filter=git-crypt diff=git-crypt
*.secret filter=git-crypt diff=git-crypt
terraform.tfvars filter=git-crypt diff=git-crypt

优势：对使用者完全透明、无需改变工作流。 劣势：密钥管理依赖 GPG（操作复杂）、不支持字段级加密、所有被加密的文件使用同一个密钥（无法差异化访问控制）。

适用场景：小团队、少量密钥文件、已有 GPG 基础设施。对于大规模场景推荐 SOPS。

Pulumi 的密钥管理

Pulumi 在密钥管理方面有原生优势——内置加密 State 和密钥标记。

Pulumi 密钥标记：

const config = new pulumi.Config();
const dbPassword = config.requireSecret('dbPassword');
// dbPassword 类型为 Output<string>，自动标记为 secret
// 在 pulumi stack export 中加密存储
// 在 pulumi up 输出中显示为 [secret]

Pulumi State 加密：与 Terraform 不同，Pulumi 使用项目密码或 KMS 加密 State 中的 secret 标记值。即使 State 文件泄露，标记为 secret 的值仍然是密文。

# 使用 AWS KMS 加密 State
pulumi stack init --secrets-provider="awskms://alias/pulumi-secrets"

**ESC（Environments, Secrets, and Configuration）**是 Pulumi 2024 年推出的集中化密钥管理层：

  • 定义环境（dev/staging/prod）的配置和密钥
  • 支持从 Vault、AWS SM、1Password 等动态拉取密钥
  • 密钥在 Pulumi 服务端加密存储
  • 支持短生命周期的 OIDC 凭据

CloudFormation 与 AWS CDK 的密钥实践

CloudFormation 参数：使用 NoEcho: true 防止密钥在控制台和 API 响应中可见：

Parameters:
  DBPassword:
    Type: String
    NoEcho: true
    Description: Database master password

但 NoEcho 只是显示层保护——密钥仍然明文存在于 CloudFormation 模板和变更集中。

最佳实践——动态引用：

Resources:
  MyDB:
    Type: AWS::RDS::DBInstance
    Properties:
      MasterUserPassword: !Sub '{{resolve:secretsmanager:prod/db:SecretString:password}}'

动态引用在部署时实时从 Secrets Manager 获取值，密钥从不出现在模板或变更集中。

IaC 密钥安全清单

在任何 IaC 项目中，应逐项检查以下安全要求：

检查项 必须/建议 实现方式
State 后端加密 必须 S3+KMS / GCS+CMEK / Terraform Cloud
State 访问控制 必须 IAM Policy 最小权限
密钥不硬编码 必须 变量、Vault Provider、SOPS
Plan 输出遮蔽 必须 sensitive 标记
.tfvars 不入库 必须 .gitignore + SOPS 加密
pre-commit 扫描 建议 tflint + tfsec + gitleaks
State 版本控制 建议 S3 Versioning
定期 State 审计 建议 自定义脚本检测明文密钥

最后提醒：IaC 中的密钥管理没有银弹。核心策略是密钥生命周期外置——IaC 负责基础设施拓扑，密钥管理由专用系统（Vault / Secrets Manager）负责，两者通过动态引用松散耦合。
