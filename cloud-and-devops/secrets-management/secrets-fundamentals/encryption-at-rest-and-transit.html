Part VI · 可观测性与安全密钥与凭据管理 简介密钥管理基础 简介静态与传输加密

静态与传输加密

加密在密钥保护中的角色

加密是保护密钥机密性的根本技术手段。无论密钥存储在磁盘上（静态状态）还是在网络中传递（传输状态），都需要通过加密防止未授权访问。理解加密技术的正确应用方式，是密钥管理工程师的基本功。

一个直觉上的悖论是：保护密钥本身也需要密钥。这导致了「谁来保护保护者」的递归问题。行业解决方案是密钥层次结构——通过从软件层逐级上升到硬件层（HSM），最终将信任锚点固定在物理安全设备上，打破了无限递归。

静态加密（Encryption at Rest）

静态加密保护存储介质上的密钥数据。即使攻击者获得了磁盘访问权限（物理盗窃、虚拟机快照泄露、备份文件失窃），没有解密密钥就无法读取内容。

全盘加密（FDE）：操作系统级别的加密（LUKS、BitLocker、FileVault）保护整个存储卷。优势是对应用透明，劣势是只防御离线攻击——系统运行时数据对已登录用户是明文的。

文件级加密：对特定的配置文件或密钥文件单独加密。SOPS（Secrets OPerationS）是典型代表——支持 YAML/JSON/ENV 文件的字段级加密，加密密钥可以是 AWS KMS、GCP KMS、Azure Key Vault 或 PGP 密钥。

# SOPS 加密后的配置文件示例
database:
  password: ENC[AES256_GCM,data:abc123...,iv:...,tag:...]
  host: production-db.internal # 非敏感字段保持明文
sops:
  kms:
    - arn: arn:aws:kms:us-east-1:123456:key/abcd-1234

数据库级加密：数据库引擎提供的透明数据加密（TDE）保护数据文件和备份。但需注意：TDE 保护的是文件层面，运行中的数据库进程内存中数据仍是明文。对于存储在数据库中的密钥（如应用层的 credential store），还需要应用层加密。

信封加密的实现细节：

信封加密的优势：


    

  1. DEK 可以针对每个密钥独立生成，泄露一个 DEK 不影响其他密钥
    2. 

  2. 密钥轮换时只需用新 KEK 重新加密 DEK，不需要重新加密所有数据
    3. 

  3. KEK 永远不离开 HSM，即使整个存储系统被攻破也无法解密

传输加密（Encryption in Transit）
传输加密保护密钥在网络传递过程中不被中间人截获或篡改。


TLS 1.3是当前网络传输加密的标准。相比 TLS 1.2，它移除了不安全的密码套件、减少了握手往返次数、实现了前向保密（Forward Secrecy）。密钥管理系统的所有 API 通信必须强制 TLS 1.3（或至少 TLS 1.2 with AEAD cipher suites）。


**mTLS（双向 TLS）**在标准 TLS 基础上增加了客户端证书验证——服务端不仅验证客户端的身份，客户端也验证服务端的身份。这在服务间密钥分发场景中尤为重要，防止攻击者伪造密钥管理服务器诱导应用发送认证凭据。


密钥传输的安全模式：


    

  1. 直接传输：通过 TLS 加密通道直接传递密钥明文。简单直接，但要求通道两端都是可信的。适用于应用从 Vault API 获取密钥的场景。
    

    2. 

  2. 密钥封装（Key Wrapping）：用接收方的公钥加密密钥后传输。即使 TLS 通道被攻破（如 TLS 终端在负载均衡器），密钥仍然安全。适用于跨组织或跨网络边界的密钥分发。
    

    3. 

  3. 密钥协商（Key Agreement）：双方通过 Diffie-Hellman 密钥交换协议协商出共享密钥，密钥本身从未在网络中传输。适用于端到端加密场景。
    

    4. 



密钥管理系统的加密架构
成熟的密钥管理系统将静态加密和传输加密组合成完整的保护体系。以 HashiCorp Vault 为例：


存储层加密：Vault 的所有持久化数据（secrets、policies、audit logs）在写入后端存储（Consul、Raft、S3）之前，使用 AES-256-GCM 加密。加密密钥是 Vault 的 Root Key，通过 Shamir 密钥分割存储。


传输层加密：所有客户端到 Vault 的通信强制 TLS。Vault 集群节点间通信使用独立的 TLS 证书。Vault Agent 到 Vault Server 使用 Token 认证 + TLS 加密。


内存保护：Vault 使用 mlock 系统调用防止敏感内存被交换到磁盘。Unseal Key 在使用后立即从内存清除。


加密实践中的常见错误
自己实现加密：使用经过审计的加密库（libsodium、Go crypto/aes、AWS Encryption SDK），不要自己实现加密算法或组合模式。


密钥与密文共存：加密密钥和加密数据存储在同一位置（同一数据库、同一配置文件），等于没有加密。


忽略密钥轮换：加密密钥长期不更换，一旦泄露则所有历史数据都可解密。应实现加密密钥的版本管理——新数据用新密钥加密，旧数据在访问时透明重加密。


ECB 模式：使用 AES-ECB 模式加密结构化数据，相同明文块产生相同密文块，攻击者可推断模式。始终使用 GCM 或 CTR 模式。


缺失完整性保护：只加密不验证完整性（如 AES-CBC without HMAC），攻击者可以在不知道密钥的情况下篡改密文。使用 AEAD（Authenticated Encryption with Associated Data）模式同时保证机密性和完整性。


合规要求对加密的影响
不同合规框架对加密有明确的技术要求：


    

  • PCI-DSS：持卡人数据必须使用强加密保护存储和传输，密钥管理流程需要文档化
    • 

  • HIPAA：PHI（受保护健康信息）在传输和静态状态都应加密，虽非强制但属于「可寻址」要求
    • 

  • GDPR：加密被明确认可为保护个人数据的技术措施，可能影响数据泄露的通知义务
    • 

  • SOC 2：要求证明加密控制的有效性，包括密钥管理流程的审计
    • 



这些合规要求不仅规定了加密的使用，还对密钥管理流程（生成、存储、轮换、销毁）提出了具体标准。在设计加密架构时，应提前考虑合规审计的可追溯性需求。
