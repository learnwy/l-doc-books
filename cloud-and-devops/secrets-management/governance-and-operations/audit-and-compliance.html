审计与合规

密钥审计的战略意义

密钥审计不仅仅是记录「谁访问了什么」——它是整个密钥管理体系可信度的基础。没有审计，你无法回答最基本的安全问题：这个密钥被谁在什么时间基于什么原因使用了？异常访问是否正在发生？密钥泄露后的影响范围有多大？

对于安全团队，审计日志是事件响应的第一手证据来源。对于合规团队，审计是向审计员证明「我们的密钥管理实践满足要求」的唯一手段。对于运维团队，审计帮助发现僵尸密钥和过度权限。

审计日志设计

一套完整的密钥审计日志应记录密钥全生命周期中的每个关键事件：

密钥操作事件：

事件类型 记录内容 安全级别
创建 创建者、密钥路径、策略绑定 INFO
读取 请求者身份、来源 IP、时间戳 INFO
更新 修改者、变更前后对比（不含值）、原因 WARN
删除 删除者、密钥标识、批准记录 WARN
轮换 触发方式（自动/手动）、版本号 INFO
吊销 触发者、原因、影响范围 CRITICAL
认证失败 请求者、认证方式、失败原因 WARN
权限拒绝 请求者、目标路径、缺少的权限 WARN

HashiCorp Vault 审计日志是行业标杆。Vault 要求至少启用一个审计设备（Audit Device）才能正常运行——如果所有审计设备都不可用，Vault 会拒绝所有请求（fail-closed 设计）。

# 启用文件审计设备
vault audit enable file file_path=/var/log/vault/audit.log

# 启用 syslog 审计
vault audit enable syslog tag="vault" facility="AUTH"

# 启用 socket 审计（发送到日志聚合系统）
vault audit enable socket address="logstash:9090" socket_type="tcp"

Vault 审计日志的特点：

  • 完整请求/响应记录：记录完整的 API 请求和响应（密钥值自动 HMAC 哈希，可用于关联但不泄露明文）
  • 请求不可绕过：即使是 Root Token 的操作也会被记录
  • 时间戳精确到纳秒：支持严格的时序分析
  • Client Token HMAC：使用 HMAC 处理 Token 值，相同 Token 的所有操作可以关联

异常检测与告警

审计日志的价值在于被分析和响应。被动存储日志只是合规最低门槛，主动检测异常才是安全防御。

应检测的异常模式：

  1. 时间异常：非工作时间的密钥访问、节假日的批量操作
  2. 频率异常：单个身份在短时间内大量读取不同密钥（可能是凭据遍历攻击）
  3. 来源异常：从未出现过的 IP 地址或地理位置访问密钥
  4. 模式异常：通常只读取一个密钥的服务突然请求其他密钥
  5. 权限提升：频繁的权限拒绝后突然成功（可能是凭据被重用）
  6. 认证异常：大量认证失败（暴力破解尝试）

告警规则示例（基于 Elasticsearch/Splunk 查询）：

# 检测：同一 Token 在 5 分钟内从不同 IP 访问
# 可能指示 Token 泄露被多个攻击者使用
alert: vault_token_multi_source
expr: |
  count by (token_hmac) (
    unique(source_ip)
    where event_type == "request"
    in last 5m
  ) > 1
severity: critical

蜜罐密钥（Canary Token）：在密钥管理系统中部署诱饵密钥——没有任何合法服务应该访问这些密钥。任何对蜜罐密钥的读取请求都是入侵指标：

# 在 Vault 中创建蜜罐密钥
vault kv put secret/honeypot/database-admin \
  password="THIS-IS-A-CANARY-DO-NOT-USE"

# 设置策略：只有特定告警 Token 能创建/更新，但所有角色都可以「看到」路径
# 任何读取操作触发即时告警

合规框架要求

不同行业合规框架对密钥管理有具体的要求。理解这些要求有助于在设计阶段就满足合规需求，避免事后改造。

SOC 2 Type II（服务组织控制报告）：

控制域 密钥管理要求
CC6.1 逻辑和物理访问控制：密钥存储有明确的访问控制策略
CC6.6 系统操作安全：密钥传输加密、定期轮换
CC7.2 系统监控：密钥操作的审计和告警
CC8.1 变更管理：密钥创建/修改有变更审批流程

PCI-DSS v4.0（支付卡行业数据安全标准）：

  • Req 3.6：密钥管理流程文档化，包括密钥生成、分发、存储、变更、退休和销毁
  • Req 3.7：加密密钥有明确的过期时间（密码周期）
  • Req 8.3：所有访问加密密钥的操作需要多因素认证
  • Req 10.3：密钥操作审计日志保留至少 12 个月

GDPR（通用数据保护条例）：

  • 第 32 条：要求实施适当的技术和组织措施保护个人数据，加密被明确提及
  • 第 33-34 条：数据泄露通知——如果加密密钥完好（攻击者无法解密数据），可能免除通知义务
  • 密钥管理的审计记录是证明「技术措施适当」的关键证据

HIPAA（健康保险可携带性与责任法案）：

  • 加密是「可寻址」要求（非强制，但不实施需要书面理由）
  • 密钥管理流程需要包含在安全管理计划中
  • 需要定期风险评估确认密钥管理控制的有效性

合规报告与证据收集

在审计期间，审计员通常会要求以下证据：

密钥清单（Inventory）：所有密钥的完整列表，包括类型、所有者、创建时间、上次轮换时间、下次轮换计划。Vault 的 sys/leases API 和密钥引擎 list 操作可以生成这个清单。

访问控制矩阵：哪些身份（人员/服务）可以访问哪些密钥，权限级别是什么。对应 Vault 的 Policy 定义。

轮换历史记录：每个密钥的轮换历史——何时轮换、自动还是手动、是否有例外（延迟轮换的审批记录）。

事件响应记录：安全事件中密钥吊销的完整时间线——何时发现、何时响应、影响评估、恢复步骤。

建议建立自动化的合规报告生成流程——每月自动生成密钥状态报告，标记即将过期的密钥、超期未轮换的密钥、异常访问统计。这既减少审计准备时间，也是持续合规（Continuous Compliance）的实践。

审计基础设施的安全

审计系统本身也是攻击目标——攻击者可能试图删除或篡改审计日志以掩盖入侵痕迹。

保护措施：

  • WORM 存储：审计日志写入不可修改的存储（S3 Object Lock、Immutable Azure Blob）
  • 实时转发：日志生成后立即转发到独立的日志聚合系统，即使源系统被攻破也无法删除已转发的日志
  • 完整性校验：日志链使用加密哈希链接（类似区块链），任何篡改都可检测
  • 分离权限：密钥管理系统管理员不应有审计日志的删除权限

Vault 的 fail-closed 设计是最好的保障——如果审计设备不可用，Vault 直接停止服务，确保不存在「无审计记录」的操作窗口。
