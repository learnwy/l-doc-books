HashiCorp Vault 架构

Vault 的设计哲学

HashiCorp Vault 诞生于 2015 年，其核心设计理念是将密钥管理从分散的、不可审计的状态统一为集中化、策略驱动、可审计的安全基础设施。Vault 不仅是一个密钥存储系统，更是一个完整的「密钥即 API」平台——任何密钥的获取都是一次经过认证、授权和审计的 API 调用。

Vault 的三个核心设计原则：

  1. 密钥永不静态暴露：应用通过 API 按需获取密钥，密钥有租约（Lease）限制有效时间
  2. 身份优先：密钥的访问基于身份而非网络位置——即使在内网也需要认证
  3. 动态密钥优于静态密钥：优先生成短生命周期的动态凭据，而非长期有效的静态密码

架构组件详解

Vault 的架构分为以下核心层次：

**存储后端（Storage Backend）**是 Vault 的持久化层。所有数据在写入前经过加密，存储后端只看到密文。支持的后端包括：

存储后端 HA 支持 推荐场景
Integrated Raft ✅ 生产环境首选（Vault 1.4+）
Consul ✅ 已有 Consul 集群的环境
S3/GCS ❌ 仅存储，不适合生产 HA
MySQL/PostgreSQL ❌ 开发/测试环境
In-Memory ❌ 仅开发

Integrated Raft 已成为现代 Vault 部署的标准选择——它消除了对外部存储系统的依赖，简化了运维复杂度，同时提供了内置的 HA 和数据复制能力。

**屏障层（Barrier）**是 Vault 安全架构的核心。所有进出存储后端的数据都必须经过屏障层的加密/解密。屏障使用 AES-256-GCM 加密，密钥来自 Root Key。未解封（Sealed）状态下，屏障是锁死的——即使拥有存储后端的完整访问权限，也无法读取任何数据。

**密钥引擎（Secrets Engine）**是 Vault 生成和管理密钥的可插拔后端。不同的引擎服务不同类型的密钥需求：

  • KV（Key-Value）：静态密钥存储，支持版本控制
  • Database：动态生成数据库凭据，自动过期回收
  • AWS/GCP/Azure：动态生成云平台 IAM 凭据
  • PKI：证书颁发机构，签发 TLS 证书
  • Transit：加密即服务，应用无需接触加密密钥
  • SSH：签发 SSH 证书或一次性密码（OTP）
  • TOTP：生成和验证一次性密码

**认证后端（Auth Method）**验证客户端身份并签发 Vault Token：

  • Token：直接使用 Vault Token
  • AppRole：为自动化系统设计的 RoleID + SecretID 认证
  • Kubernetes：使用 K8s ServiceAccount Token 认证
  • AWS IAM：使用 AWS IAM 身份认证
  • OIDC/JWT：对接企业 SSO 系统
  • LDAP/GitHub/Okta：对接现有身份提供者

初始化与解封过程

Vault 的初始化是一个密码学精密操作，引入了 Shamir 密钥分割算法保护最敏感的 Root Key。

初始化流程：

  1. Vault 生成一个 Root Key（用于加密屏障层）
  2. Root Key 通过 Shamir 算法分割为 N 个 Key Shares
  3. 设定阈值 T——至少 T 个 Share 才能重建 Root Key
  4. 每个 Share 分发给不同的运维人员（物理分离保管）

典型配置是 5 个 Share、3 个阈值（5/3），意味着任何 3 个 Share 持有者合作才能解封 Vault，单独持有者无法独自访问。

解封（Unseal）流程：Vault 重启后处于 Sealed 状态，屏障层锁定，所有请求被拒绝。运维人员依次提供 Unseal Key（Share），达到阈值后 Root Key 被重建（仅在内存中），屏障层解锁，Vault 恢复服务。

Auto Unseal：在云环境中，可以使用云 KMS（AWS KMS、GCP Cloud KMS、Azure Key Vault）自动解封——Root Key 用 KMS 加密存储，启动时调用 KMS API 解密。这消除了人工解封的运维负担，但将信任转移到了云 KMS 的安全性上。

策略与访问控制

Vault 的授权模型基于 Policy（策略）。策略使用 HCL（HashiCorp Configuration Language）定义，指定哪些路径可以执行哪些操作：

# 允许读取 production 数据库凭据
path "database/creds/production-readonly" {
  capabilities = ["read"]
}

# 允许列出所有 KV 密钥名称（不含值）
path "secret/metadata/*" {
  capabilities = ["list"]
}

# 禁止访问 root token 相关路径
path "auth/token/create-orphan" {
  capabilities = ["deny"]
}

策略通过 Token 或 Entity 绑定到身份。一个身份可以关联多个策略，最终权限是所有策略的并集（deny 优先）。

动态密钥与租约管理

Vault 最强大的特性是动态密钥——按需生成、有时间限制、自动回收的凭据。

以数据库动态密钥为例：应用请求 database/creds/my-role 路径，Vault 连接到目标数据库，创建一个带有指定权限的临时用户，返回用户名密码，并设置一个 Lease（租约）。当 Lease 过期或被显式吊销时，Vault 连接到数据库删除该临时用户。

这种模式的安全优势是巨大的：

  • 每个应用实例使用独立的凭据，审计可以追踪到具体的请求者
  • 凭据有明确的过期时间，泄露后的时间窗口有限
  • 不需要人工管理密码——没有「共享密码」的安全隐患
  • 吊销是确定性的——Vault 直接删除数据库用户，而非依赖密码修改传播

高可用与灾难恢复

HA 模式：多个 Vault 节点组成集群，通过 Raft 共识选举 Leader。只有 Leader 处理写操作，Follower 处理读操作（或转发到 Leader）。Leader 故障时自动切换，RTO 通常在 10 秒以内。

性能复制（Performance Replication）：跨数据中心部署多个集群，Primary 集群同步策略和配置到 Secondary 集群，每个集群独立处理本地请求。适用于全球部署的低延迟需求。

灾难恢复复制（DR Replication）：Primary 完整复制到 DR 集群，DR 集群在正常情况下不提供服务，仅在 Primary 完全不可用时手动提升为 Primary。

备份策略：使用 vault operator raft snapshot save 定期备份 Raft 数据。快照是加密的——恢复时仍需要 Unseal Key。建议在不同地理位置保存多份快照，并定期测试恢复流程。
