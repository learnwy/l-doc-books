云原生密钥服务

云平台密钥管理的定位

每个主流云平台都提供了原生的密钥管理服务，作为其安全基础设施的核心组件。与自建 Vault 相比，云原生方案的核心优势在于零运维负担和深度平台集成——密钥的存储、加密、轮换由云平台保证 SLA，而与 IAM、计算、数据库等服务的联动几乎是开箱即用的。

选择云原生方案还是自建方案，本质上是在以下维度做权衡：

维度 云原生方案 自建 Vault
运维成本 接近零 需要专人维护集群
多云支持 锁定单一平台 天然多云
功能灵活性 受限于平台提供的能力 可扩展密钥引擎
定制策略 有限 完全可定制
合规认证 平台已获得认证 需要自己证明
成本模式 按调用量付费 固定基础设施成本

AWS Secrets Manager 与 KMS

AWS 的密钥管理分为两个互补的服务：

**AWS KMS（Key Management Service）**管理加密密钥，提供加密/解密操作。KMS 不存储应用密钥（如数据库密码），而是管理用于保护其他数据的加密密钥（CMK/Customer Managed Key）。

KMS 的核心概念：

  • CMK（Customer Master Key）：逻辑密钥资源，实际密钥材料在 HSM 中
  • 数据密钥：由 CMK 生成的密钥，用于客户端加密
  • 密钥策略：与 IAM 策略配合，细粒度控制密钥使用权限
  • 自动轮换：CMK 支持年度自动轮换，旧版本密钥保留用于解密历史数据

AWS Secrets Manager 存储和管理应用密钥（密码、API Key、Token 等），底层使用 KMS 加密。

Secrets Manager 的核心能力：

  • 自动轮换：通过 Lambda 函数自定义轮换逻辑，内置 RDS/Redshift/DocumentDB 的轮换模板
  • 跨账号共享：通过资源策略（Resource Policy）允许其他 AWS 账号访问密钥
  • 版本管理：每个密钥保留多个版本，支持 AWSCURRENT/AWSPREVIOUS 标签实现滚动更新
  • 与 ECS/EKS/Lambda 集成：容器和函数可以直接引用 Secrets Manager ARN

典型使用模式——RDS 密码自动轮换：

  1. Secrets Manager 存储数据库主密码
  2. 配置 30 天自动轮换，关联 Lambda 轮换函数
  3. 轮换时 Lambda 生成新密码、更新 RDS、更新 Secret 版本
  4. 应用通过 SDK 获取当前版本密码，无需重启

定价：每个密钥 0.40/月+0.40/月 +0.40/月+0.05/10000 次 API 调用。对于大量密钥的场景成本可控。

Google Cloud Secret Manager 与 Cloud KMS

Google Cloud 的方案同样分为密钥管理（Cloud KMS）和应用密钥存储（Secret Manager）两层。

Cloud KMS 的差异化特性：

  • 密钥环（Key Ring）：组织密钥的逻辑容器，按项目和区域划分
  • 密钥版本：每次轮换创建新版本，可以精确控制每个版本的状态（启用/禁用/销毁）
  • HSM 支持：Cloud HSM 提供 FIPS 140-2 Level 3 认证的硬件保护
  • 外部密钥管理器（EKM）：密钥材料存储在客户自有的外部 KMS 中，Google 从不接触明文密钥

Secret Manager 的核心特性：

  • 版本管理：自动为每次更新创建新版本，支持指定版本或 latest 引用
  • IAM 集成：使用标准 GCP IAM 角色控制访问（secretmanager.secretAccessor 等）
  • 区域/全局选择：密钥可以存储在特定区域（满足数据驻留要求）或全局复制
  • 密钥轮换通知：通过 Pub/Sub 发送轮换提醒，但轮换逻辑需要客户自己实现

与 GKE（Google Kubernetes Engine）的集成：通过 Workload Identity 让 Pod 以 GCP Service Account 身份直接访问 Secret Manager，无需在集群中存储 GCP 凭据。

Azure Key Vault

Azure Key Vault 整合了密钥管理、密钥存储和证书管理三大功能于一体。

三种对象类型：

  • Keys：加密密钥（RSA/EC），支持 HSM 保护，用于加密/签名操作
  • Secrets：任意字符串密钥（密码、连接串、API Key）
  • Certificates：TLS 证书的完整生命周期管理（生成 CSR、导入、续期）

Azure 特有集成：

  • Managed Identity：Azure 资源（VM、App Service、AKS）使用系统分配的托管标识访问 Key Vault，无需管理凭据
  • Azure Policy：强制要求所有资源组使用 Key Vault 存储密钥，拒绝硬编码模式
  • Event Grid：密钥即将过期时触发事件，驱动自动化轮换流程
  • Disk Encryption：Azure Disk Encryption 直接使用 Key Vault 中的密钥加密 VM 磁盘

访问策略 vs RBAC：Key Vault 支持两种授权模式。传统的 Vault 访问策略（全有或全无粒度）和新的 Azure RBAC（细粒度角色分配）。新部署推荐使用 RBAC 模式。

软删除与清除保护：删除的密钥进入软删除状态（默认保留 90 天），可以恢复。启用清除保护后，即使拥有最高权限也无法在保留期内永久删除密钥——防止内部威胁的恶意销毁。

多云策略与方案对比

在多云或混合云环境中，需要一个统一的密钥管理策略：

方案一：以 Vault 为统一层。Vault 作为所有应用的密钥入口，底层通过各云平台的 KMS 保护 Vault 自身的 Root Key（Auto Unseal）。应用只需对接 Vault API，与底层云平台解耦。

方案二：联邦模式。每个云平台使用原生方案管理本平台资源的密钥，通过 External Secrets Operator 或 Terraform 统一编排。密钥不跨云传输，但管理界面统一。

方案三：云不可知的加密层。使用 SOPS + 各平台 KMS 的方式——加密配置文件可以存储在 Git 中，解密密钥由各平台 KMS 分别持有。不同平台部署使用不同的 KMS 解密。

选型建议：

  • 单一云平台 + 小团队 → 直接使用云原生方案
  • 多云 + 中等规模 → Vault 统一层
  • 严格数据主权要求 → 联邦模式（密钥不离开各平台区域）
  • 已有 GitOps 流程 → SOPS + 多 KMS

成本与性能考量

云密钥服务的成本模型通常是「低存储费 + 按调用计费」：

服务 存储费 API 调用费 免费额度
AWS Secrets Manager $0.40/密钥/月 $0.05/万次 无
AWS KMS $1/CMK/月 $0.03/万次 前 20000 次免费
GCP Secret Manager $0.06/版本/月 $0.03/万次 前 6 个版本免费
Azure Key Vault $0.03/操作 含在操作费中 无

对于高频访问场景（如每次请求都获取密钥），应在应用侧实现缓存——带 TTL 的本地缓存可以将 API 调用减少 99%，同时保证密钥在可接受的延迟内刷新。
