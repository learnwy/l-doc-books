限流与背压

概述

限流（Rate Limiting）与背压（Backpressure）是系统在入口和内部传播层面控制过载的两大核心机制。限流在系统边界处主动拒绝超出处理能力的请求，防止过载；背压则在系统内部当下游处理能力不足时，将压力信号反向传播至上游，使整个处理链路协调减速。两者配合使用，构成了从入口到内部的完整过载保护体系。

2026年的分布式系统面临前所未有的流量挑战：AI Agent的爆发式API调用、营销活动引发的瞬间洪峰、以及恶意流量攻击。在这种环境下，没有限流和背压保护的系统就像没有减压阀的压力容器——不知道何时会因过载而爆炸。

令牌桶算法详解

令牌桶是最常用的限流算法，其核心参数：

  • 速率（Rate）：令牌生成速率，如100 token/s
  • 桶容量（Burst）：允许的最大突发量，如200 tokens
  • 当前令牌数：[0, Burst]之间

工作流程：

  1. 以恒定速率向桶中添加令牌
  2. 每个请求消耗一个令牌
  3. 桶空时拒绝请求（或排队等待）
  4. 桶满时新令牌丢弃
tokens(t)=min⁡(burst,tokens(t0)+rate×(t−t0))tokens(t) = \min(burst, tokens(t_0) + rate \times (t - t_0))tokens(t)=min(burst,tokens(t0​)+rate×(t−t0​))

令牌桶的优雅之处在于：它允许短时间突发（消耗桶中积累的令牌），同时保证长期平均速率不超过Rate。

背压机制
背压是响应式系统（Reactive Systems）的核心概念——当消费者处理速度跟不上生产者时，通过信号机制让生产者减速，而非无限缓冲或直接丢弃。


背压传播模型：


背压的实现方式：


    

  1. 阻塞式：消费者不拉取时生产者阻塞（Go channel、Java BlockingQueue）
    2. 

  2. 响应式拉取：消费者通过request(n)声明处理能力（Reactor/RxJava）
    3. 

  3. 显式拒绝：队列满时返回拒绝信号（HTTP 429/503）
    4. 

  4. TCP窗口：TCP协议本身的流控机制
    5. 

  5. 动态速率调整：根据下游延迟动态降低发送速率
    6.

CoDel（Controlled Delay）
基于排队时间自适应丢弃
通用过载保护





Google的CoDel算法通过监控请求的排队延迟来做出丢弃决策：如果最近一段时间内的最小排队延迟超过目标值（如5ms），开始丢弃队尾请求。这比简单的队列长度限制更加智能——它直接度量了用户感知的延迟。

自适应限流实现
固定阈值限流的最大问题是：阈值设多少？设低了浪费容量，设高了保护不住。自适应限流根据系统实时状态动态调整：


基于延迟的自适应（TCP Vegas思路）：


    

  • 维护一个基准延迟值（系统空闲时的最小RTT）
    • 

  • 当实际延迟超过基准的K倍时，开始限流
    • 

  • 延迟恢复正常后，逐步放开限制
    • 



基于CPU的自适应（Sentinel模式）：


    

  • 当系统CPU使用率超过80%时激活限流
    • 

  • 限流阈值 = 当前QPS × (目标CPU利用率 / 实际CPU利用率)
    • 

  • 每秒重新计算一次
    • 



基于Little's Law的自适应：


    

  • limit=avgRT×successQPSlimit = avgRT \times successQPSlimit=avgRT×successQPS
    • 

  • 当inflight请求数超过limit时拒绝新请求
    • 

  • 优势：无需预设固定阈值，自动适应系统能力变化
    • 



gRPC中的背压实践
gRPC基于HTTP/2，天然支持流控：


    

  • Stream级别：通过WINDOW_UPDATE帧控制单个Stream的发送量
    • 

  • 连接级别：控制整个TCP连接的发送窗口
    • 

  • 应用级别：Server Streaming时通过flow control暂停发送
    • 

  • Deadline传播：上游设置的deadline传播到整个调用链，超时后自动取消
    • 



最佳实践
限流响应设计
被限流的请求应给客户端提供有意义的反馈：


    

  • HTTP 429 Too Many Requests：标准状态码
    • 

  • Retry-After Header：建议客户端等待的秒数
    • 

  • X-RateLimit-Limit：当前限流配额
    • 

  • X-RateLimit-Remaining：剩余配额
    • 

  • X-RateLimit-Reset：配额重置的Unix时间戳
    • 



客户端配合机制
限流的效果依赖客户端的配合行为：


    

  1. 指数退避重试：收到429后使用指数退避（+随机jitter）
    2. 

  2. 请求合并：批量API替代高频单次调用
    3. 

  3. 本地缓存：减少不必要的重复请求
    4. 

  4. 优雅降级：客户端收到限流信号后主动降低请求频率
    5. 



限流告警与运营
    

  • 限流触发率>5%时告警（可能需要扩容而非限流）
    • 

  • 区分正常限流（保护性）和异常限流（容量不足）
    • 

  • 按用户/租户维度统计限流影响，避免头部用户体验受损
    • 

  • 定期Review限流配额，随业务增长调整

总结
限流与背压是系统过载保护的两道核心防线：限流在边界处主动拒绝超额请求，背压在内部传播减速信号。生产系统需要多层限流架构（CDN→Gateway→Service→DB）、自适应限流减少人工配置、以及合理的Load Shedding策略应对极端过载。关键认知：拒绝部分请求以保全整体，远好于接受所有请求然后全部超时——在过载面前，快速失败是对所有用户最负责任的选择。
