PR 工作流与分支策略

工作流模型的演进

Pull Request 工作流并非一成不变的固定模式，而是随着团队规模、发布节奏和质量要求的变化不断演进的。选择合适的工作流模型是高效审查的第一步——错误的模型会让审查成为瓶颈而非助力。

主流工作流对比

模型 适用场景 分支策略 发布节奏 PR 审查特点
GitHub Flow 持续部署的 SaaS 团队 main + feature branches 每天多次 小 PR、快速审查
GitLab Flow 需要环境隔离的团队 main + environment branches 按环境推进 分层审查
Trunk-Based Development 高成熟度团队 main + 短命 feature branches 持续集成 极小 PR、高频合并
Git Flow 版本化发布的产品 main + develop + release + hotfix 按版本发布 多环节审查

GitHub Flow 深入解析

GitHub Flow 是目前最广泛采用的 PR 工作流，其核心原则是：

  1. main 分支始终是可部署的
  2. 新工作在从 main 创建的 feature branch 上进行
  3. 定期推送到远端分支以获取反馈
  4. 准备好时创建 Pull Request
  5. 通过审查后合并到 main
  6. 合并后立即部署

这种简单性是其最大优势——规则少、认知负担低、新人容易上手。

Trunk-Based Development

对于追求极致交付速度的团队，Trunk-Based Development（TBD）是更激进的选择：

  • Feature branch 存活时间不超过 1-2 天
  • 每天向 main 合并多次
  • 未完成的功能通过 Feature Flag 隐藏
  • 审查压力分散：因为 PR 极小，审查几乎是即时的
TBD 对团队的要求更高：需要完善的 CI/CD 管线、Feature Flag 基础设施、以及团队对"小步快跑"的共识。


Draft PR 的战略使用
Draft PR（草稿 Pull Request）是一个被严重低估的协作工具。它不是"未完成的 PR"——它是一种主动寻求早期反馈的机制。

Draft PR 的最佳实践
    

  1. 明确标注期望的反馈范围：在描述中写明"请只关注整体设计方向，不需要审查实现细节"
    2. 

  2. 及时转为正式 PR：一旦代码就绪，立即移除 Draft 状态，不要让它长期处于草稿
    3. 

  3. 不要在 Draft 中堆积过多变更：Draft PR 也应该保持合理的体积

Stacked PRs：2026 年的游戏规则改变者
2026 年 4 月，GitHub 官方推出了原生的 Stacked Pull Request 支持（通过 gh-stack CLI 扩展），这是对大型功能开发模式的根本性变革。


什么是 Stacked PRs
Stacked PRs（堆叠式 Pull Request）是一种代码审查模式——每个分支不是直接指向 main，而是按顺序指向其下方的前一个分支。这让开发者能在早期层仍在审查时继续推进后续工作。


为什么 Stacked PRs 重要
GitHub 在发布公告中引用的研究数据表明：200-400 行的 PR 缺陷减少 40%，审批速度比大 PR 快 3 倍。对 150 万个 PR 的分析证实了这一结论。Stacked PRs 的设计目标是：即使底层功能规模很大，也让每个单独的 PR 保持在这个最优范围内。

实用建议
    

  • 一个 stack 控制在 3-4 个 PR——超过这个数量，跟踪依赖关系的认知负担开始超过审查收益
    • 

  • 每个 PR 应当是逻辑自洽的——即使单独被 revert 也不会破坏系统
    • 

  • 底层 PR 优先审查和合并——reviewer 应当从 stack 底部开始
    • 

  • 使用 AI Agent 辅助拆分——gh skill install github/gh-stack 可以教 AI 编码代理自动将大型 diff 拆分为 stack
    • 



Feature Flag 驱动的增量交付
Feature Flag 是 Trunk-Based Development 和 Stacked PRs 的关键基础设施。它让"合并到 main"和"对用户可见"成为两个独立的操作。


在 PR 工作流中的角色
    

  1. 解除 PR 体积与功能完整度的耦合：功能可以分 5 个 PR 交付，但用户只在 Flag 开启后看到完整功能
    2. 

  2. 降低审查压力：reviewer 知道不完整的代码不会影响生产用户，可以更放心地 approve 中间状态
    3. 

  3. 安全的回退机制：如果发现问题，关闭 Flag 即可，无需代码 revert
    4.
