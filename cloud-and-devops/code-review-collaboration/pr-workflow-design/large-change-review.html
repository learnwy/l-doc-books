大型变更的 Review 策略

大 PR 的真实代价

对 50000+ Pull Request 的分析数据清晰地揭示了一个规律：超过 400 行的 PR，缺陷检出率下降约 70%。这不是 reviewer 不够认真——而是认知负荷的客观限制。当 reviewer 面对一个修改了 23 个文件、涉及 1800 行变更的 PR 时，人脑无法同时持有所有相关的上下文。

大 PR 的隐性成本远不止审查质量下降：

成本维度 小 PR（< 400 行） 大 PR（> 1000 行）
首次审查响应时间 4-8 小时 2-5 天
平均审查轮次 1.5 轮 3-4 轮
合并冲突概率 < 10% > 50%
缺陷检出率 75%+ 30% 以下
reviewer 心理抗拒 低 高（"下次再看"）

拆分的核心原则

将大型变更拆分为可审查的单元，是解决大 PR 问题的根本方案。但拆分不是随意切割——每个子 PR 需要满足以下条件：

  1. 逻辑自洽：独立可理解，不需要看其他 PR 才能明白这个 PR 在做什么
  2. 独立可用：合并后系统仍然正常工作（可能功能不完整，但不会 break）
  3. 可独立 revert：如果发现问题，可以单独回滚这个 PR 而不影响其他已合并的 PR
  4. 合理的体积：每个子 PR 保持在 200-400 行

六种拆分技术

技术一：按架构层拆分

将一个跨层功能按架构层次垂直切分：

每层的 PR 由最熟悉该层的 reviewer 审查——DBA 审查数据模型，后端工程师审查业务逻辑，前端工程师审查 UI 代码。


技术二：重构先行
当新功能需要修改现有代码结构时，先提交一个纯重构 PR，再在重构后的基础上实现新功能：






顺序
PR 内容
审查重点





1
纯重构：提取方法、重命名、移动文件
行为是否不变




2
新功能实现
新逻辑是否正确





这种拆分的巨大优势是：重构 PR 的审查标准是"行为不变"——reviewer 只需确认测试全部通过且无行为差异。新功能 PR 则在干净的代码结构上实现，reviewer 不需要同时理解重构和新逻辑。


技术三：Stacked PRs
利用 GitHub Stacked PRs（gh-stack）或 Graphite 将功能分层开发：


Day 1: 创建 PR 1（基础设施） + PR 2（核心逻辑） + PR 3（API）
Day 1-2: 三个 PR 并行审查
Day 2: 从底部开始依次合并
相比传统的顺序提交（一个审完再开始下一个），Stacked PRs 能将 3 周的交付周期压缩到 2 天。


技术四：Feature Flag 遮蔽
将不完整的功能隐藏在 Feature Flag 后面，允许分多个 PR 合并到 main 而不影响线上用户：


    

  1. PR 1：添加 Feature Flag 配置 + 空的功能骨架
    2. 

  2. PR 2-4：逐步实现功能细节（Flag 关闭状态下不可达）
    3. 

  3. PR 5：开启 Feature Flag（这个 PR 做最终审查，确认功能完整性）
    4. 



技术五：接口先行
对于新增 API 或模块间交互的场景：


    

  1. PR 1：定义接口（interface/protocol/API schema）+ mock 实现
    2. 

  2. PR 2：实现接口的真实逻辑
    3. 

  3. PR 3：调用方迁移到新接口
    4. 



这种方式让依赖方可以基于 PR 1 的 mock 并行开发，不需要等待真实实现完成。


技术六：数据迁移分离
涉及数据库 schema 变更的功能尤其需要拆分：


    

  1. PR 1：添加新列/新表（向后兼容，旧代码不受影响）
    2. 

  2. PR 2：新代码读写新结构
    3. 

  3. PR 3：数据迁移脚本
    4. 

  4. PR 4：清理旧列/旧表
    5. 



每一步都可以独立回滚，不会导致数据丢失。


当无法拆分时的审查策略
有些变更确实难以拆分——大规模重命名、框架升级、全局配置变更。对于这些情况，需要特殊的审查策略：


引导式审查
Author 在 PR 描述中提供明确的审查路径：


## 审查建议

请按以下顺序审查：

1. 先看 `config/new-framework.yaml` — 理解配置变更的意图
2. 再看 `src/core/adapter.ts` — 核心适配层的实现
3. 最后扫一遍 `src/**/*.ts` 中的 import 变更 — 都是机械性替换

重点关注：第 2 步中的错误处理逻辑可以跳过：所有 import 路径变更（已由 codemod 自动生成并通过测试验证）
分段审查会议
对于超大型 PR，安排一个 30 分钟的同步审查会议：


    

  1. Author 花 5 分钟讲解整体方案和关键决策
    2. 

  2. Reviewer 提出方向性问题（10 分钟）
    3. 

  3. 确认审查重点区域，分配不同 reviewer 关注不同模块（5 分钟）
    4. 

  4. 各自进行异步详细审查（会后）
    5. 



信任边界划分
将大 PR 中的变更分为"需要仔细审查"和"可信任自动化结果"两类：






分类
示例
审查策略





需要人工审查
新的业务逻辑、错误处理变更
逐行审查




可信任测试结果
机械性重命名、import 路径变更
确认测试通过即可




可信任工具输出
codemod 生成的代码
抽样验证 + CI 通过





预防大 PR 的机制设计
最好的策略是从源头预防大 PR 的产生：


组织层面
    

  1. 任务拆解规范：在 Sprint Planning 中，要求每个 task 的预估产出不超过 400 行代码
    2. 

  2. 每日集成文化：鼓励每天至少提交一次 PR，即使功能未完成（用 Feature Flag 保护）
    3. 

  3. 拆分能力培训：将"如何拆分变更"作为工程师 onboarding 的必修内容
    4. 



技术层面
    

  1. CI 体积警告：PR 超过 400 行时自动添加 Warning 标签并 @author
    2. 

  2. 超限审批流程：超过 1000 行的 PR 需要 Tech Lead 批准才能请求审查
    3. 

  3. Stacked PR 工具链：配置 gh-stack 或 Graphite，降低拆分的操作成本
    4. 

  4. 自动拆分建议：AI 工具（如 Graphite Diamond）可以分析大 PR 并建议拆分方式
    5. 



度量与反馈
追踪团队的 PR 体积分布，在周报或 retro 中展示：


目标是让 80% 以上的 PR 保持在 400 行以内。当大 PR 占比上升时，这是一个团队需要改进拆分实践的信号。
