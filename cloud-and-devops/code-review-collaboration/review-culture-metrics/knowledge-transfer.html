知识传递与 Onboarding

代码审查作为知识传播引擎

在所有知识传播机制中，代码审查是最自然、最高频、最低成本的一种。每次审查都是一次微型的知识交换：reviewer 从 author 的实现中学习新的解题思路，author 从 reviewer 的反馈中获得经验传承。这种交换每天发生数十次，远比偶尔的 Tech Talk 或文档更新频率高。

Google 的工程实践文档将知识传递列为代码审查的首要目标之一——与缺陷检出处于同等地位。原因很朴素：当只有一个人了解某个系统时，这个人的离开就是团队的灾难。代码审查是预防这种"Bus Factor = 1"风险的最自然方式。

Bus Factor 与知识分布

理解 Bus Factor

Bus Factor（巴士因子）是衡量"多少人同时离开会导致项目停摆"的指标。Bus Factor = 1 意味着某个系统只有一个人了解——这是极高的组织风险。

轮换算法
一种简单有效的跨模块轮换算法：


对于模块 M 的每个新 PR:
  1. 从 CODEOWNERS 中选择 1 位专家 reviewer
  2. 从"过去 3 个月未审查过模块 M 的团队成员"中
     随机选择 1 位作为学习者 reviewer
  3. 如果所有人都在过去 3 个月审查过 M，
     则选择审查次数最少的人
新人 Onboarding 的审查路径
三阶段渐进参与模型
新人加入团队后的审查参与应当是渐进式的——不是第一天就要求独立审查大 PR，也不是前三个月完全不参与审查。


阶段一：观察（第 1-2 周）




活动
目的

了解"我们如何做审查"

感受团队的代码风格和审查标准




旁观一次 Pair/Mob Review
观察 reviewer 如何思考和表达




为自己的第一个 PR 请求审查
亲身体验 author 端的流程

新人审查的支持体系
Review Buddy 制度：每位新人在前 6 周有一位 Review Buddy——


    

  • Buddy 会重复审查新人审查过的 PR，提供"审查审查"的反馈
    • 

  • Buddy 在新人不确定时给予指导："这种情况我们通常会..."
    • 

  • Buddy 帮助新人理解团队特有的隐含规则
    • 



安全的提问空间：新人在审查中应该被鼓励大量提问——"为什么这里用了这个模式？"这类问题不是暴露无知，而是表达了对代码质量的关注。团队应明确传达：问题越多越好。

审查中的教学时刻
当 reviewer 发现一个值得深入讲解的问题时，可以超越"修改建议"的范围，提供一个小型的知识分享：


💡 SUGGESTION + 延伸知识:

这里使用了 `setTimeout(callback, 0)` 来延迟执行。虽然能工作，但更好的方式是使用 `queueMicrotask(callback)`。

原因：setTimeout 将任务放入宏任务队列，受到最小延迟(1ms)限制，且优先级低于微任务。queueMicrotask 将任务放入微任务队列，会在当前执行栈清空后、下一次渲染前立即执行。

详见：https://developer.mozilla.org/docs/Web/API/queueMicrotask
这种"审查中的教学"是团队知识积累最有机的方式——它在真实的代码上下文中发生，比抽象的培训更容易被记住和应用。

持续改进的组织实践
月度知识传递回顾
每月用 15 分钟回顾：


    

  1. 本月有哪些审查中产生了值得记录的知识点？
    2. 

  2. 是否有新的 lint 规则或编码规范需要从审查中提炼？
    3. 

  3. 知识热力图中的 🔴 是否在减少？
    4. 

  4. 新人的审查参与进展如何？
    5. 



构建学习型审查文化
最终目标是让审查从"质量关卡"升级为"学习引擎"——每个参与者在每次审查中都能学到一些东西。这需要：


    

  • Reviewer 愿意花时间解释"为什么"，而不只是说"改"
    • 

  • Author 愿意提问和承认不理解
    • 

  • 团队将审查中学到的知识系统性地沉淀为文档和规则
    • 

  • 组织为知识传递投入时间预算（不把所有时间都压在"产出功能"上）
    •
