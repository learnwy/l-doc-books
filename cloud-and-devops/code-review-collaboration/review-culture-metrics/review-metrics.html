Review 效能度量

为什么要度量审查

"不能度量的东西无法改进"——这条管理原则在代码审查领域同样成立。但度量审查不是为了监控开发者、设定 KPI 排名或惩罚慢的 reviewer。它的真正目的是：发现系统性瓶颈、验证流程改进的效果、以及为资源分配提供数据支撑。

LinearB 对 810 万个 Pull Request 的大规模分析提供了行业基准。这些数据帮助团队理解"我们的审查效率在什么水平"——是 Elite（前 20%）、Mid-tier（中间 60%）、还是 Lagging（后 20%）。

核心度量指标

PR Pickup Time（首次响应时间）

定义：从 PR 创建到第一位 reviewer 开始审查的时间。

这是审查效率最重要的单一指标，因为它直接关联开发者的等待体验和上下文切换成本。

等级 Pickup Time 团队特征
Elite < 7 小时 Review 优先级文化强、自动分配、小 PR
Mid-tier 6-50 小时 有流程但执行不一致
Lagging 50-137+ 小时 PR 堆积、reviewer 瓶颈严重

Google 的数据：平均审查周转时间 4 小时。小变更约 1 小时，大变更约 5 小时。这是行业标杆。

优化杠杆：

  • 减小 PR 体积（小 PR 更容易被快速处理）
  • 自动化 reviewer 分配（消除"等人主动认领"的延迟）
  • 建立"Review 高于新代码"的优先级文化
  • 每日固定审查时段（批次处理）

Review Cycle Time（全周期时间）

定义：从 PR 创建到最终合并的总时间，包括所有审查轮次、修改和等待。

Cycle Time = Pickup Time + Review Time + Revision Time + Re-review Time + Merge Queue Time


每个组成部分都可以独立优化。通常 Pickup Time 占比最大（超过 50%），是优化的首要目标。


Review Depth（审查深度）
定义：衡量审查的实质性程度，而非仅仅是速度。


量化方式：


    

  • 评论密度：每 100 行变更的评论数量
    • 

  • 评论类型分布：Blocker / Suggestion / Nit 的比例
    • 

  • Approve 前的讨论轮次：完全无讨论的 Approve 可能是 Rubber Stamping 的信号
    • 

  • 实质性评论率：排除"LGTM"/"Looks good"后的评论占比
    • 



Rework Rate（返工率）
定义：PR 合并后 14 天内，同一区域被再次修改的概率。


返工率是审查质量的滞后指标——如果审查没有捕获问题，这些问题会在合并后以 Bug fix 或 hotfix 的形式出现。

与 DORA 指标的关联
DORA（DevOps Research and Assessment）四个核心指标中，审查效率直接影响其中两个：

审查快 → 合并快 → 部署频率高

审查是 lead time 的主要组成部分

审查深度 → 缺陷拦截 → 失败率低

LinearB 的数据发现，Elite 团队（Pickup Time < 7 小时）的部署频率是 Lagging 团队的 4-7 倍。审查速度与交付速度高度正相关。

度量的误用与陷阱
古德哈特定律
"当一个度量成为目标时，它就不再是一个好的度量。"如果团队将 Pickup Time 作为 KPI 考核，可能出现的行为扭曲：


    

  • Reviewer 打开 PR 但不认真看（数字好看但实质为空）
    • 

  • 快速 Approve 不提评论（降低 Pickup Time 但损害审查质量）
    • 



正确的度量态度




做
不做





追踪趋势而非绝对数值
用指标排名或惩罚个人




在团队层面讨论指标含义
让管理层单方面设定阈值




结合定性反馈理解数据
仅靠数字下结论




识别系统性瓶颈
归咎于个别"慢的人"




定期回顾指标的有效性
一次设定永不调整





应当追踪但不应作为 KPI 的指标
    

  • 个人审查速度（容易引导 Rubber Stamping）
    • 

  • 评论数量（容易引导无意义的 Nit 刷数据）
    • 

  • 个人被 Reject 的次数（抑制实验和创新）
    • 



应当作为团队健康信号而非个人绩效指标来使用这些数据。


基线建立与改进循环
第一步：建立基线
在改进之前，先用 2-4 周收集当前状态的数据：


    

  1. 当前 Pickup Time 的 P50 是多少？
    2. 

  2. 当前 Cycle Time 的 P50 是多少？
    3. 

  3. PR 体积的分布是什么样的？
    4. 

  4. 无评论 Approve 的比例是多少？
    5. 



第二步：识别最大杠杆点
通常最大的杠杆点是 PR 体积 和 Pickup Time：


    

  • 缩小 PR 体积 → 审查时间变短 → Cycle Time 下降 → 合并冲突减少 → 正循环
    • 

  • 缩短 Pickup Time → Author 等待减少 → 上下文保持 → 返工减少
    • 



第三步：设定改进目标
不要试图同时改进所有指标。每个季度选择 1-2 个指标重点优化：


    

  • Q1 目标：Pickup Time P50 从 12 小时降到 6 小时
    • 

  • Q2 目标：PR 体积中位数从 500 行降到 300 行
    • 



第四步：验证与迭代
每月回顾指标变化，在 Sprint Retro 中讨论：


    

  • 指标是否在改善？改善幅度是否符合预期？
    • 

  • 改进措施（如自动分配、体积警告）是否真正落地？
    • 

  • 是否有意外的副作用（如审查质量随速度提升而下降）？
    •
