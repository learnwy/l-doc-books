建立 Review 文化

文化先于流程

工具和流程可以在一周内部署到位，但文化的建立需要数月甚至更长时间。代码审查文化不是"我们要求所有 PR 必须经过审查"这样的规则——而是团队中每个人发自内心地相信审查是有价值的，并愿意主动投入时间和精力去做好它。

两个拥有完全相同工具链和流程规范的团队，可能产出截然不同的审查体验：一个团队的审查是高效的知识交换，另一个团队的审查是令人厌烦的官僚程序。差异在于文化——即"我们这个团队如何看待审查"的共同信念。

Review 行为准则

制定团队的 Code of Conduct

每个团队应当有一份显式的审查行为准则。这份准则不应该是 HR 文件的复制品，而是团队自己讨论和制定的、真正反映团队价值观的约定。

核心条目建议：

原则 具体行为
尊重与善意 评论针对代码而非人；假设对方有合理的理由
建设性 每条批评伴随一个具体的改进建议
及时响应 承诺在 SLA 内完成审查（通常 4 小时工作日内）
平衡投入 审查他人代码的优先级不低于编写新代码
持续学习 将审查视为双向学习的机会
明确表态 审查完毕后给出清晰的 Approve/Request Changes/Comment

准则的落地方式

行为准则不应该停留在文档里。落地的关键是将其融入日常：

  • 新人 Onboarding：第一周就阅读并讨论审查准则
  • 定期回顾：每季度在 retro 中讨论准则是否需要更新
  • 正向强化：当有人践行了准则精神时，公开表扬
  • 违反时的处理：由 Tech Lead 私下沟通而非公开批评

Reviewer 轮换与分配机制

为什么需要轮换

固定的 reviewer 分配会导致多个问题：

  • 瓶颈：个别人审查队列过长，成为全团队的阻塞点
  • 知识孤岛：只有固定的两三个人了解某个模块
  • 倦怠：同一类型的代码看太多次会产生审美疲劳，降低审查质量

轮换策略

推荐的复合策略：


    

  1. 至少 1 位 reviewer 是该模块的 CODEOWNER（确保专业度）
    2. 

  2. 另 1 位从全团队中 round-robin 分配（确保知识传播）
    3. 



工具支持
GitHub 和 GitLab 都支持自动 reviewer 分配规则。GitHub 的 CODEOWNERS + Auto-assign 组合、GitLab 的 Merge Request Approvals 都可以实现自动化轮换。


Ship/Show/Ask 模型
并非所有变更都需要同等程度的审查。Ship/Show/Ask 模型为不同风险等级的变更提供了差异化的审查路径。


三层模型定义




模式
行为
适用变更
比例目标





Ship
直接合并，事后通知团队
琐碎修复、文档更新、紧急 hotfix
约 20%




Show
合并后在团队频道展示
常规功能、重构
约 50%




Ask
传统审查流程
高风险、核心架构、不确定方向
约 30%





Ship 的安全保障
Ship 模式不是"不负责任地合并"——它需要以下前提条件：


    

  • CI 管线全部通过
    • 

  • Feature Flag 保护未完成功能
    • 

  • 完善的监控和告警
    • 

  • 快速回滚能力（< 5 分钟）
    • 

  • 变更者对变更负全责
    • 



如何判断一个变更属于哪种模式
Review 优先级的组织共识
"Review 高于新代码" 的文化
这是最难建立但最重要的共识之一。当一个工程师面前有两件事——继续写自己的功能、或者审查同事已经写完等待合并的 PR——正确的选择是先审查。


理由链条：


    

  1. 同事的 PR 被阻塞 → 同事无法继续后续工作
    2. 

  2. 同事被阻塞 → 团队整体交付速度下降
    3. 

  3. PR 等待越久 → 合并冲突概率越高 → 最终需要更多时间解决
    4. 

  4. 你的新功能晚开始 1 小时 → 只影响你自己
    5. 

  5. 同事的 PR 晚合并 4 小时 → 影响整个依赖链
    6. 



让这个共识落地
    

  • 每天第一件事：打开审查队列，先处理等待中的审查
    • 

  • Slack 提醒：待审查超过 4 小时自动提醒 reviewer
    • 

  • 公开仪表盘：展示每人的审查响应时间
    • 

  • Tech Lead 榜样：领导者自己始终快速响应审查
    • 



分歧处理的升级路径
构建安全的分歧环境
技术分歧是健康的——它意味着人们在认真思考。但分歧需要有结构化的处理方式，否则会演变为人际冲突或者"谁声音大谁赢"的局面。


四步升级路径




步骤
触发条件
行为





1. PR Comment 讨论
正常分歧
各自陈述观点和理由




2. 同步对话
3+ 轮 comment 未解决
15 分钟视频/面对面讨论




3. 引入第三方
双方对话后仍无共识
Tech Lead 或领域专家参与




4. Decision Owner 裁决
仍无法达成一致
指定的决策者做出最终判断





"Disagree and Commit" 原则
当决策做出后（无论是否是你偏好的方向），团队成员需要全力支持执行——不应在后续工作中消极对待或暗中推翻。如果事后证明决策有误，通过正式渠道提出修订（新 ADR），而非个人行动。


文化的度量信号
如何判断团队的审查文化是否健康？以下信号可作为参考：


正面信号
    

  • 新人在第一周就开始参与审查（即使只是小 PR）
    • 

  • PR 中出现正面反馈（"这个设计很优雅"）的频率与建设性批评相当
    • 

  • 团队成员主动寻求审查反馈（"你能帮我看看这个设计对不对"）
    • 

  • 审查讨论线程以学习收获结束（"TIL，谢谢指出"）
    • 



警告信号
    

  • 审查变成形式主义——全部是"LGTM"无实质评论
    • 

  • 审查变成战场——某些人的 PR 总是引发长期争论
    • 

  • 逃避行为——有人故意在周五下午提交大 PR，或者选择"不需要审查"的路径
    • 

  • 审查队列持续增长——大家都忙着写新代码，没人优先审查
    •
