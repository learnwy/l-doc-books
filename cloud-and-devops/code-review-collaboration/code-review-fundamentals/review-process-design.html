Review 流程设计

审查生命周期全景

一次完整的代码审查不是从"reviewer 打开 diff"开始的，而是从 author 提交代码之前就已经启动。理解审查的完整生命周期，才能在每个环节进行针对性的优化。

每个环节都有可优化的空间。LinearB 对 810 万个 PR 的分析发现，超过一半的 PR 在生命周期中有 50% 以上的时间处于空闲等待状态——不是在被审查，而是在等人来看。


PR 描述的工程规范
PR 描述是 reviewer 理解变更的第一入口。一份好的 PR 描述能让审查效率提升 2-3 倍。


必备要素




要素
说明
示例





What
这个 PR 做了什么
添加用户注册的邮箱验证功能




Why
为什么要做这个改动
减少垃圾注册，当前垃圾账号占比 23%

邮件服务不可用时降级为跳过验证





PR 描述模板
成熟团队会在仓库中配置 PR 模板（.github/PULL_REQUEST_TEMPLATE.md），确保每个 PR 都包含必要的上下文信息。关键是模板不应过于繁琐——过度复杂的模板会被开发者跳过或敷衍填写。


附加上下文
对于涉及 UI 变更的 PR，附上截图或录屏；对于性能优化，附上 benchmark 对比数据；对于架构调整，附上设计文档链接或简要的架构图。这些额外上下文大幅降低 reviewer 的理解成本。


审查关注点的层次框架
Reviewer 打开一个 PR 后，应当按照从宏观到微观的顺序进行审查，而非逐行扫描。


第一遍：全局理解（2-5 分钟）
    

  1. 阅读 PR 描述，理解变更的目的和范围
    2. 

  2. 查看文件列表——变更了哪些模块？是否符合预期？
    3. 

  3. 判断 PR 的风险等级和所需审查深度
    4. 



第二遍：架构与设计（5-15 分钟）
    

  1. 变更是否符合系统架构方向？是否突破了模块边界？
    2. 

  2. 抽象层次是否合适？是否过度工程或过于简陋？
    3. 

  3. 新增的依赖是否合理？是否引入了不必要的耦合？
    4. 

  4. API 设计是否向后兼容？公共接口是否合理？
    5. 



第三遍：实现细节（10-30 分钟）
    

  1. 逻辑是否正确？边界条件和错误路径是否覆盖？
    2. 

  2. 并发安全性——是否存在竞态条件或死锁风险？
    3. 

  3. 性能考量——是否有 N+1 查询、不必要的循环、热路径中的阻塞操作？
    4. 

  4. 测试是否充分覆盖了新增逻辑？
    5. 



第四遍：细节扫描（2-5 分钟）
    

  1. 命名是否清晰表达意图？
    2. 

  2. 是否有死代码、注释掉的代码、遗留的调试语句？
    3. 

  3. 文档是否需要更新？
    4. 



Approve 与 Request Changes 的决策框架
审查结束后，reviewer 需要做出明确的决策。这个决策不应该是模糊的——它应该基于清晰的标准。


应当 Approve 的情况
    

  • 代码正确地实现了预期功能
    • 

  • 没有安全风险或数据完整性问题
    • 

  • 设计方向合理，即使不是 reviewer 偏好的方式
    • 

  • 存在的小问题已在 comment 中标记为 Nit/Suggestion
    • 



关键原则："Better, not perfect." 代码不需要完美才能合并——它只需要比现状好，并且不引入新的风险。追求完美的审查会阻塞进度、打击 author 的积极性，最终导致团队逃避审查。


应当 Request Changes 的情况
    

  • 存在正确性问题（Bug 或逻辑错误）
    • 

  • 有安全漏洞或数据泄露风险
    • 

  • 设计方向与团队的架构决策冲突
    • 

  • 缺少必要的测试覆盖
    • 

  • 变更的范围与 PR 描述不一致
    • 



灰色地带的处理
当不确定时，使用 Comment 而非 Request Changes。在评论中明确表达："这不是 blocker，但我想讨论一下 X 的设计选择。如果你有合理的理由，Approve。"这种方式尊重了 author 的判断力，同时表达了 reviewer 的关切。


审查效率的时间管理
批次处理 vs 即时响应
研究表明，每天固定 2-3 个时段进行审查（如早上到岗后、午饭后、下午 4 点）比随时中断当前工作去审查更高效。这种批次处理方式：


    

  • 减少上下文切换的认知成本
    • 

  • 保护深度工作的完整时段
    • 

  • 仍然满足 4 小时的首次响应 SLA
    • 



审查时长控制
单次审查会话不应超过 60 分钟。超过这个阈值，注意力显著下降。如果一个 PR 需要超过 60 分钟来审查，这本身就是一个信号——要么 PR 太大需要拆分，要么 reviewer 需要更多背景上下文。


审查负载均衡
一个 reviewer 每天合理的审查量是 3-5 个中等规模的 PR。超过这个量，审查质量会明显下降。团队应当通过 reviewer 轮换和自动分配来平衡负载，避免个别成员成为审查瓶颈。


流程的持续改进
审查流程不是一次设计好就永远不变的。团队应当定期回顾和优化：


    

  • 月度回顾：审查指标是否在改善？平均响应时间、周转时间、返工率的趋势如何？
    • 

  • 痛点收集：在 Sprint 回顾中收集审查相关的痛点——什么让审查变慢或变得不愉快？
    • 

  • 规则更新：当某类问题反复出现时，考虑将其自动化（添加 lint 规则）或文档化（更新编码规范）
    • 

  • 新人体验：定期从新人视角审视流程——是否有隐含的知识未被文档化？
    •
