Mob Programming 与 Ensemble

从 Pair 到 Mob 的跃迁

如果 Pair Programming 是两个人的协作，那么 Mob Programming 就是把这种协作模式扩展到整个团队。Mob Programming（又称 Ensemble Programming、Software Teaming）是指 3-6 个人围绕同一个任务、在同一时间、使用同一台电脑（或共享环境）协作编程的实践。

这听起来像是巨大的资源浪费——6 个人做 1 个人的事？实际效果远非如此。当一个团队 Mob 工作时，代码在产出的瞬间就已经通过了多人审查，不需要后续的 Code Review 流程。设计决策在实施时就获得了团队共识，不需要事后的 ADR。知识在所有人之间同步传播，不存在单点故障。

一项实践研究表明，Mob Programming 团队虽然使用更多人力，但"完成"的定义不同——Mob 产出的代码是"完全完成"的（已审查、已测试、已达成共识），而独立开发的代码还需要经过审查、测试、讨论和返工的额外周期。总交付时间往往更短。

为什么 5-10 分钟而非更长？ 短轮换间隔有多个好处：


    

  • 防止任何人因长时间不参与而走神
    • 

  • 每个人都频繁接触代码，真正理解实现
    • 

  • 减少"太专家化"的风险——每个人都能 drive 任何部分
    • 

  • 降低个人表演压力——只需 5 分钟的集中注意力
    • 



会话组织
准备阶段（10 分钟）
    

  1. 明确目标：今天这个 Mob session 要完成什么？（具体到可验收的标准）
    2. 

  2. 共享上下文：如果涉及特定领域知识，先做简短的背景介绍
    3. 

  3. 环境就绪：确保共享环境已配置好，所有人都能看到屏幕
    4. 

  4. 约定规则：确认轮换间隔、休息时间、讨论决策方式
    5. 



执行阶段
Strong-Style 规则：在 Mob 中通常采用 Strong-Style 原则——"要让一个想法进入计算机，必须经过另一个人的手。" 这意味着有想法的人应该成为 Navigator 来指导 Driver，而不是抢过键盘自己打。


讨论与编码的平衡：


    

  • 当团队在方向上有分歧时，暂停编码，进行 5 分钟的讨论
    • 

  • 讨论不超过 5 分钟——如果 5 分钟内无法达成共识，用代码实验验证
    • 

  • 采用"先试后议"原则：不确定哪个方案好？先用代码实现一个，看效果再决定
    •

Mob 的认知负荷比 Pair 更高——因为所有人都在持续参与，没有"默默观察"的休息空间。严格的休息机制是可持续性的保障。

mob.sh 工作流
mob.sh 是专门为 Mob Programming 设计的 CLI 工具，自动化了轮换时的 git 操作：


# Driver 开始工作
mob start

# 计时器到，交给下一个人
mob next

# 下一位 Driver 接手
mob start

# 会话结束，创建最终 commit
mob done
每次 mob next 都会自动 commit WIP 代码并 push 到临时分支，下一位 Driver 执行 mob start 时自动 pull 并继续。整个过程无需手动处理 git 操作。

不适合 Mob 的场景
    

  • 简单、重复的任务（浪费多人时间）
    • 

  • 独立研究和学习（需要个人节奏）
    • 

  • 团队超过 6 人（讨论效率急剧下降）
    •

Mob 中的团队动态
心理安全是前提
Mob Programming 要求极高的心理安全感——每个人的思考过程、犯的错误、不理解的地方都暴露在所有人面前。如果团队中存在嘲笑、指责或评判的文化，Mob 会成为一种折磨而非赋能。


建立心理安全的具体行动：


    

  • 允许任何人随时说"我不理解"——这是学习的信号，不是能力的缺陷
    • 

  • 犯错时正常化处理——"好的，让我们回退一步"而非"怎么连这个都不知道"
    • 

  • 领导者（Tech Lead/Senior）带头暴露自己的不确定性
    • 



防止主导性格接管
在 Mob 中，性格外向或经验丰富的成员容易无意识地主导整个会话。对策：


    

  • 严格的 Driver 轮换计时器——不允许某人"因为手热"一直 drive
    • 

  • Navigator 约束规则——只有当前 Navigator 给 Driver 指令，其他人先向 Navigator 提建议
    • 

  • 显式邀请安静成员发言——"[名字]，你怎么看这个方案？"
    • 

  • 回顾中反馈——"今天大家的参与度是否均衡？"
    • 



引入 Mob 的渐进策略
不要试图让团队一夜之间从独立工作转为全天 Mob。推荐的渐进路径：


    

  1. 第一周：每周 1 次 Mob session（1-2 小时），选择一个适合的任务
    2. 

  2. 第二周：增加到每周 2-3 次，开始尝试不同类型的任务
    3. 

  3. 第一个月后：团队回顾——Mob 在哪些场景价值最大？哪些不适合？
    4. 

  4. 长期稳态：根据回顾结果，找到团队的最佳 Mob 时间比例（通常 30-50%）
    5.
