服务目录

核心概念

服务目录（Service Catalog）是开发者门户的核心数据层。它为组织中的所有软件资产——服务、库、API、文档、基础设施组件——建立一个统一的、可搜索的注册中心。服务目录回答的核心问题是："这个服务是谁的？它做什么？怎么用？健康状况如何？"

在微服务架构下，一个中型组织可能有数百个服务。没有服务目录，开发者面临的常见困境包括：不知道某个功能对应哪个服务、找不到服务的负责人、不清楚服务间的依赖关系。服务目录通过结构化元数据解决这些问题。

实体模型与元数据管理
Backstage 的服务目录基于实体模型（Entity Model），每个软件资产都是一个实体。实体通过 catalog-info.yaml 文件定义，存放在对应的 Git 仓库中。


# catalog-info.yaml：服务实体定义
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: order-service
  description: 订单管理服务，处理订单创建、支付和履约
  annotations:
    github.com/project-slug: my-org/order-service
    backstage.io/techdocs-ref: dir:.
    grafana/dashboard-url: https://grafana.example.com/d/order-service
    pagerduty.com/service-id: P1234567
  tags:
    - typescript
    - grpc
    - critical
  links:
    - url: https://wiki.example.com/order-service
      title: 设计文档
      icon: docs
spec:
  type: service
  lifecycle: production
  owner: order-team
  system: e-commerce
  providesApis:
    - order-api
  consumesApis:
    - payment-api
    - inventory-api
  dependsOn:
    - resource:order-db
    - resource:order-cache
interface EntityKinds {
  Component: {
    description: '软件组件（服务、前端、库）';
    types: ['service', 'website', 'library'];
    required: ['name', 'owner', 'type', 'lifecycle'];
  };
  API: {
    description: 'API 定义（REST、gRPC、GraphQL、事件）';
    types: ['openapi', 'grpc', 'graphql', 'asyncapi'];
    required: ['name', 'owner', 'type', 'definition'];
  };
  Resource: {
    description: '基础设施资源（数据库、队列、存储）';
    types: ['database', 'cache', 'queue', 'storage'];
    required: ['name', 'owner', 'type'];
  };
  System: {
    description: '相关组件的逻辑分组';
    example: '电商系统 = 订单服务 + 支付服务 + 库存服务';
    required: ['name', 'owner'];
  };
  Group: {
    description: '团队或组织单元';
    source: 'LDAP/Okta 自动同步';
    required: ['name', 'type', 'children'];
  };
  User: {
    description: '个人用户';
    source: 'LDAP/Okta 自动同步';
    required: ['name', 'memberOf'];
  };
}
元数据的质量直接决定服务目录的价值。平台团队应该定义元数据标准（哪些字段是必填的），并通过 CI 检查确保每个仓库的 catalog-info.yaml 符合标准。


依赖可视化与影响分析
服务目录的高级能力是自动构建服务间的依赖关系图谱，支持影响分析和变更规划。


interface DependencyAnalysis {
  upstreamDependencies: {
    question: '我的服务依赖谁？';
    useCase: '评估上游故障对本服务的影响';
    visualization: '向左展开的依赖树';
  };
  downstreamDependents: {
    question: '谁依赖我的服务？';
    useCase: '评估本服务变更的影响范围';
    visualization: '向右展开的依赖树';
  };
  impactAnalysis: {
    scenario: '如果 payment-api 不可用，哪些系统受影响？';
    method: '从 payment-api 向下遍历依赖图';
    output: '受影响的服务列表 + 影响程度评估';
  };
  dataFlow: {
    sources: ['catalog-info.yaml 中的 dependsOn/consumesApis', 'Kubernetes Service 间的网络流量', '分布式追踪数据'];
    reconciliation: '声明式依赖 + 运行时依赖 → 完整视图';
  };
}
dependency_enrichment:
  static_analysis:
    source: 'catalog-info.yaml 声明'
    pros: '简单、可控、无运行时开销'
    cons: '可能遗漏未声明的依赖'

  runtime_discovery:
    source: 'Service Mesh 流量数据 / 分布式追踪'
    pros: '发现真实的运行时依赖'
    cons: '需要流量才能发现、有延迟'

  combined_approach:
    strategy: '声明式为主、运行时为补充'
    reconciliation:
      - '运行时发现但未声明的依赖 → 提醒补充声明'
      - '已声明但运行时未观测到的依赖 → 标记为潜在过时'
依赖可视化最重要的应用场景是变更影响分析：在修改某个服务的 API 之前，通过依赖图快速识别所有消费方，评估变更的影响范围，并提前通知相关团队。


服务目录治理
服务目录的长期价值取决于数据的准确性和完整性。这需要持续的治理策略。


interface CatalogGovernance {
  dataQuality: {
    required_fields: ['name', 'owner', 'type', 'lifecycle', 'description（>50字符）', 'tags（至少1个）'];
    recommended_fields: [
      'links（设计文档URL）',
      'annotations.grafana/dashboard-url',
      'annotations.pagerduty.com/service-id',
      'spec.providesApis / spec.consumesApis',
    ];
    enforcement: 'CI 流水线中的 catalog-info.yaml 校验';
    scoring: '实体完整度评分（0-100），门户中展示';
  };
  lifecycle_management: {
    stages: ['experimental', 'production', 'deprecated', 'decommissioned'];
    transitions: {
      experimental_to_production: '满足 production-readiness 检查清单';
      production_to_deprecated: '通知所有消费方，提供替代方案';
      deprecated_to_decommissioned: '确认无消费方后执行';
    };
  };
  orphan_detection: {
    definition: '无 owner 或 owner 团队已解散的实体';
    detection: '每周扫描 + 与 LDAP 团队信息交叉比对';
    remediation: '自动通知、限期认领、未认领则标记弃用';
  };
}
catalog_health_dashboard:
  metrics:
    total_entities: '组织中的实体总数'
    coverage: '有 catalog-info.yaml 的仓库占比'
    completeness: '平均元数据完整度评分'
    freshness: '最后更新时间 > 90天的实体比例'
    orphans: '无有效 owner 的实体数量'

  targets:
    coverage: '> 95%'
    completeness: '> 80 分'
    freshness: '> 90% 在90天内更新'
    orphans: '< 5%'

  actions:
    low_coverage: '在 CI 中强制要求 catalog-info.yaml'
    low_completeness: '展示实体评分排名，激励团队完善'
    stale_entities: '自动发送提醒到 owner'
    orphans: '定期清理会议'
服务目录治理的核心理念是"数据即产品"——像对待面向用户的产品数据一样对待目录数据，持续监控其质量并及时修复。


小结
    

  • 服务目录为所有软件资产建立统一、可搜索的注册中心
    • 

  • 实体模型包括 Component、API、Resource、System、Group/User 六种类型
    • 

  • 通过 catalog-info.yaml 声明元数据，CI 检查确保数据质量
    • 

  • 依赖可视化结合声明式（catalog-info）和运行时（Service Mesh/Tracing）数据
    • 

  • 数据治理是目录长期价值的保障——覆盖率、完整度、新鲜度是核心指标
    • 

  • 将目录数据视为产品，持续监控质量并及时修复
    •
