平台 API 设计

核心概念

平台 API 是平台工程对外暴露能力的核心接口。它不同于业务 API（面向终端用户），而是面向内部开发者和自动化系统的基础设施 API。平台 API 的设计质量直接决定了平台的可编程性和扩展性——好的 API 让开发者可以将平台能力无缝集成到自己的工作流中。

平台 API 承载着平台的契约承诺。一旦发布，就需要维护向后兼容性，因为大量内部工具和自动化脚本依赖这些 API。API 的设计决策比实现代码更难修改，因此需要前期投入更多的设计思考。

API 契约设计
平台 API 的契约定义了请求格式、响应结构、错误处理和认证方式。一致的契约设计降低了消费者的学习成本。


interface PlatformAPIConventions {
  urlStructure: {
    pattern: '/api/v{version}/{resource}';
    examples: [
      'GET /api/v1/services',
      'POST /api/v1/services',
      'GET /api/v1/services/{name}',
      'GET /api/v1/services/{name}/deployments',
      'POST /api/v1/environments',
      'DELETE /api/v1/environments/{id}',
    ];
  };
  requestFormat: {
    contentType: 'application/json';
    naming: 'camelCase for JSON fields';
    pagination: {
      request: '?page=1&pageSize=20';
      response: '{ items: [], total: 100, page: 1, pageSize: 20 }';
    };
    filtering: '?status=active&team=order-team&sort=-createdAt';
  };
  responseFormat: {
    success: {
      structure: '{ data: T, metadata: { requestId, timestamp } }';
    };
    error: {
      structure: '{ error: { code, message, details, requestId } }';
      codes: {
        VALIDATION_ERROR: '请求参数不合法';
        NOT_FOUND: '资源不存在';
        CONFLICT: '资源状态冲突';
        QUOTA_EXCEEDED: '配额超限';
        PERMISSION_DENIED: '权限不足';
      };
    };
  };
}
# OpenAPI 定义示例：平台服务管理 API
openapi: '3.1.0'
info:
  title: Platform Service API
  version: '1.2.0'
paths:
  /api/v1/services:
    get:
      operationId: listServices
      summary: 查询服务列表
      parameters:
        - name: team
          in: query
          schema:
            type: string
        - name: lifecycle
          in: query
          schema:
            type: string
            enum: [experimental, production, deprecated]
        - name: page
          in: query
          schema:
            type: integer
            default: 1
        - name: pageSize
          in: query
          schema:
            type: integer
            default: 20
            maximum: 100
      responses:
        '200':
          content:
            application/json:
              schema:
                type: object
                properties:
                  data:
                    type: array
                    items:
                      $ref: '#/components/schemas/Service'
                  total:
                    type: integer
    post:
      operationId: createService
      summary: 创建新服务
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateServiceRequest'
      responses:
        '201':
          description: 服务创建成功
        '409':
          description: 服务名称已存在
API 契约应该是 Design First 的——先设计 OpenAPI 规范，经过评审后再实现。这确保了 API 的一致性和可预测性，也让消费者可以基于规范提前开始集成开发。


版本策略与兼容性
版本管理是平台 API 生命周期中最具挑战性的部分。需要在演进速度和向后兼容性之间找到平衡。


interface VersioningStrategy {
  majorVersioning: {
    when: '不兼容的接口变更（删除字段、改变语义）';
    approach: 'URL 路径版本（/api/v1 → /api/v2）';
    parallelSupport: '至少支持 2 个主版本并行';
    migrationWindow: '6 个月（通知 → 弃用 → 下线）';
  };
  nonBreakingChanges: {
    allowed: [
      '添加新的可选请求参数',
      '添加新的响应字段',
      '添加新的 API 端点',
      '添加新的枚举值（仅限响应）',
      '放宽请求参数的约束（如从 required 变为 optional）',
    ];
    forbidden: [
      '删除或重命名现有字段',
      '改变字段的数据类型',
      '改变字段的语义含义',
      '添加新的必填请求参数',
      '删除枚举值',
      '收紧响应结构约束',
    ];
  };
  compatibilityChecks: {
    tool: 'oasdiff / optic';
    integration: 'PR 合并前自动检测 Breaking Changes';
    policy: 'Breaking Changes 需要 API Review Board 审批';
  };
}
api_lifecycle:
  stages:
    alpha:
      stability: '不保证兼容性'
      audience: '内部测试'
      url: '/api/alpha/...'
      sla: '无'

    beta:
      stability: '尽量保持兼容，但可能有变更'
      audience: '早期采用者'
      url: '/api/beta/...'
      sla: '基础 SLA'

    stable:
      stability: '严格向后兼容'
      audience: '所有用户'
      url: '/api/v1/...'
      sla: '完整 SLA（99.9%）'

    deprecated:
      stability: '不再添加新功能'
      audience: '存量用户（引导迁移）'
      headers: 'Sunset: <date>, Deprecation: true'
      timeline: '6 个月后下线'
版本策略的核心原则是"对消费者友好"：尽量通过非破坏性变更演进 API，避免频繁发布新主版本。当确实需要破坏性变更时，提供充足的迁移窗口（至少 6 个月）和详细的迁移指南。


向后兼容设计模式
向后兼容是平台 API 的核心约束。以下设计模式帮助在保持兼容性的同时持续演进 API。


interface CompatibilityPatterns {
  additiveChanges: {
    pattern: '只添加不删除';
    example: '添加 metadata 字段到响应中，不删除已有字段';
    consumer_impact: '忽略未知字段 → 无影响';
  };
  fieldDeprecation: {
    pattern: '弃用字段但继续返回';
    example: '旧字段 createdDate → 新字段 createdAt';
    implementation: '两个字段同时返回，createdDate 标记 deprecated';
    timeline: '保持 6 个月后评估移除';
  };
  envelopePattern: {
    pattern: '响应包装在信封中';
    example: '{ data: T, metadata: { version, links } }';
    benefit: '信封层可自由扩展，不影响数据层';
  };
  tolerantReader: {
    pattern: '消费者忽略未知字段';
    guideline: '文档中明确要求消费者实现 tolerant reader';
    benefit: '提供方可以自由添加新字段';
  };
  featureFlags: {
    pattern: '通过请求头启用新行为';
    example: 'X-Platform-Feature: new-pagination';
    benefit: '同一端点支持新旧行为，消费者可渐进迁移';
  };
}
api_design_review_checklist:
  naming:
    - '资源名使用名词复数（services, environments）'
    - '动作使用 HTTP Method 表达'
    - '一致的命名风格（camelCase）'

  compatibility:
    - '新字段必须是 optional'
    - '不修改现有字段的类型或含义'
    - '枚举值只增不减'
    - '通过 oasdiff 验证无 Breaking Changes'

  security:
    - '所有端点要求认证'
    - '权限检查基于资源而非端点'
    - '敏感操作有审计日志'
    - '请求限流（per-user, per-team）'

  documentation:
    - '每个端点有完整的 OpenAPI 定义'
    - '包含请求/响应示例'
    - '错误码有详细说明'
    - '版本变更记录在 Changelog 中'
向后兼容设计模式的核心思想是"宽进严出"（Postel's Law）：在接受请求时尽量宽容（忽略未知参数），在发送响应时严格遵守契约。这为 API 的演进提供了最大的灵活空间。


小结
    

  • 平台 API 是面向内部开发者的基础设施 API，需要高度可编程性和一致性
    • 

  • Design First 方法确保 API 质量——先设计规范，评审后再实现
    • 

  • 版本策略遵循"对消费者友好"原则，尽量通过非破坏性变更演进
    • 

  • 向后兼容的核心模式：只添加不删除、字段弃用而非移除、信封模式
    • 

  • PR 中自动检测 Breaking Changes 是 API 治理的关键自动化
    • 

  • Postel's Law（宽进严出）为 API 演进提供最大灵活空间
