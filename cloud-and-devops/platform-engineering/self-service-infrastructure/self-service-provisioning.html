自助式资源供给

核心概念

自助式资源供给（Self-Service Provisioning）是平台工程从"工单驱动"走向"产品化服务"的关键转变。它让开发者通过标准化的接口（门户、CLI 或 API）直接申请和管理云资源，无需提交工单等待运维团队处理。

传统模式下，开发者申请一个数据库需要经历：提交工单 → 运维评估 → 手动创建 → 配置网络 → 返回连接信息，整个过程可能需要数天。自助式供给将这一流程缩短到分钟级别，同时通过策略引擎确保合规和安全。

声明式资源申请
声明式资源申请是自助供给的技术基础。开发者通过描述期望状态（而非执行步骤）来申请资源，平台负责将期望状态转化为实际资源。


# 开发者提交的资源声明文件
apiVersion: platform.example.com/v1
kind: ResourceBundle
metadata:
  name: order-service-resources
  namespace: order-team
  labels:
    app: order-service
    tier: critical
    cost-center: engineering
spec:
  database:
    engine: postgresql
    version: '15'
    size: medium
    highAvailability: true
    backup:
      enabled: true
      retentionDays: 30

  cache:
    engine: redis
    version: '7'
    size: small
    clusterMode: false

  queue:
    engine: kafka
    topics:
      - name: order-events
        partitions: 6
        replicationFactor: 3
      - name: order-notifications
        partitions: 3
        replicationFactor: 3
interface DeclarativeProvisioningFlow {
  step1_declare: {
    action: '开发者编写资源声明 YAML';
    location: '应用仓库的 platform/ 目录';
    validation: '本地 Schema 校验（IDE 提示）';
  };
  step2_commit: {
    action: '提交到 Git，触发 CI 流水线';
    checks: ['YAML Schema 合法性', '策略引擎预检（成本、配额、安全）', '命名规范检查'];
  };
  step3_approve: {
    action: '自动或人工审批';
    autoApprove: '非生产环境 + 标准规格 + 预算内';
    manualApprove: '生产环境 critical 资源 + 超预算';
  };
  step4_provision: {
    action: 'Crossplane/Terraform 创建资源';
    feedback: '实时状态更新到门户和 Slack';
    timeout: '5 分钟（非生产）/ 15 分钟（生产）';
  };
  step5_inject: {
    action: '连接信息自动注入到应用';
    mechanism: 'External Secrets → Kubernetes Secret → 环境变量';
    verification: '健康检查确认连接可用';
  };
}
声明式申请的关键优势是可版本化、可审计和可回滚。所有资源变更都以 Git 提交的形式记录，任何时候都可以追溯"谁在什么时候申请了什么资源"，也可以通过 Git revert 快速回滚资源变更。


审批流程自动化
智能审批是自助供给的关键环节。过于严格的审批会回退到工单模式，过于宽松则有安全和成本风险。最佳实践是基于风险等级和上下文自动决策。


interface ApprovalPolicy {
  riskAssessment: {
    factors: [
      { name: 'environment'; weight: 0.3; scoring: { dev: 1; staging: 5; prod: 10 } },
      { name: 'costImpact'; weight: 0.25; scoring: { low: 1; medium: 5; high: 10 } },
      { name: 'dataClassification'; weight: 0.25; scoring: { public: 1; internal: 5; confidential: 10 } },
      { name: 'resourceTier'; weight: 0.2; scoring: { experimental: 1; standard: 5; critical: 10 } },
    ];
    thresholds: {
      autoApprove: '< 4.0';
      singleApprover: '4.0 - 7.0';
      multiApprover: '> 7.0';
    };
  };
  quotaManagement: {
    teamQuota: {
      dev: { databases: 5; cacheInstances: 3; queueTopics: 10 };
      staging: { databases: 2; cacheInstances: 2; queueTopics: 5 };
      production: { databases: 3; cacheInstances: 2; queueTopics: 10 };
    };
    overQuota: '触发审批 → 评估是否需要扩大配额';
  };
}
审批自动化的目标是让 80% 以上的标准请求无需人工介入即可完成。对于需要人工审批的请求，平台应该提供充足的上下文信息（成本预估、安全影响、现有资源使用情况），让审批者能快速做出决策。


资源生命周期管理
自助供给不仅包括资源创建，还包括资源的整个生命周期：更新、扩缩容、备份和销毁。


interface ResourceLifecycle {
  create: {
    trigger: '声明式申请 + 审批通过';
    automation: 'Crossplane Composition 自动编排';
    notification: '创建完成通知到 Slack/门户';
  };
  update: {
    trigger: '修改资源声明并提交';
    safeGuards: [
      '破坏性变更（如缩容）需要显式确认',
      '生产环境变更自动创建变更记录',
      '不可逆操作（如删除数据列）需要多级审批',
    ];
  };
  scale: {
    manual: '修改 size 参数';
    auto: '基于指标的自动扩缩容策略';
    cooldown: '扩容后 15 分钟内不缩容';
  };
  backup: {
    automated: '平台默认策略（每日备份、保留 30 天）';
    onDemand: '开发者自助触发即时备份';
    restore: '从备份恢复到新实例（避免覆盖生产）';
  };
  destroy: {
    trigger: '删除资源声明或显式销毁';
    safeGuards: ['生产资源销毁需要多级审批', '软删除（标记弃用）+ 7 天保留期', '数据备份确认后才实际删除'];
  };
  dormancy: {
    detection: '30 天无访问的非生产资源';
    action: '自动通知 → 确认保留或自动暂停';
    savings: '非生产资源休眠可节省 40-60% 成本';
  };
}
资源生命周期管理中最容易被忽视的是"资源回收"。许多组织的云账单中有 30-40% 的费用来自不再使用的"僵尸资源"。平台应该自动检测闲置资源并提醒所有者，或在确认后自动回收。


小结
    

  • 自助式资源供给是平台工程从工单驱动到产品化服务的核心转变
    • 

  • 声明式申请以 Git 为中心，实现资源变更的版本化、可审计和可回滚
    • 

  • 智能审批基于风险等级自动决策，目标是 80% 请求无需人工介入
    • 

  • 资源生命周期管理覆盖创建、更新、扩缩容、备份和销毁全流程
    • 

  • 闲置资源检测和回收是成本优化的重要手段
    • 

  • 配额管理在保障自助灵活性的同时，防止资源滥用和成本失控
    •
