基础设施抽象

核心概念

基础设施抽象是平台工程的技术基石。它在底层云资源（AWS/GCP/Azure 的原生 API）和上层开发者之间构建一个语义化的中间层，让开发者以业务语义描述需求（"我需要一个 PostgreSQL 数据库"），而非操作云资源的底层细节（VPC、子网、安全组、实例类型等）。

抽象的核心价值在于关注点分离：开发者关注"要什么"，平台团队关注"怎么做"。这种分离使得底层实现可以独立演进——从 AWS RDS 迁移到 Google Cloud SQL，开发者的声明无需变更。

Terraform 抽象层
Terraform 是最成熟的基础设施即代码（IaC）工具。在平台工程中，Terraform 通过模块化和标准化实现基础设施抽象。平台团队封装底层复杂性为可复用模块，开发者只需调用模块并填写简单参数。


// Terraform 模块抽象层次设计
interface TerraformModuleHierarchy {
  level1_primitive: {
    description: '原子资源模块（1:1 映射云资源）';
    example: 'aws_rds_instance, aws_security_group';
    maintainer: '平台团队';
    consumer: '高级工程师、特殊场景';
  };
  level2_composite: {
    description: '组合模块（多个原子资源组合）';
    example: 'database（含 RDS + 安全组 + 参数组 + 备份策略）';
    maintainer: '平台团队';
    consumer: '一般开发者';
  };
  level3_application: {
    description: '应用级模块（完整应用基础设施）';
    example: 'microservice（含 ECS/EKS + ALB + RDS + Redis + 监控）';
    maintainer: '平台团队';
    consumer: '通过脚手架自动生成';
  };
}
# 平台团队提供的标准化 Terraform 模块示例
module "api_database":
  source: 'git::https://platform.internal/modules/database?ref=v2.3.0'
  inputs:
    name: 'order-service-db'
    engine: 'postgresql'
    engine_version: '15'
    size: 'medium'
    environment: 'production'
    backup_retention_days: 30
    multi_az: true

# 平台团队在模块内部处理的复杂性（对开发者透明）
internal_complexity:
  - 'VPC 子网选择（基于 environment 自动路由）'
  - '安全组规则（仅允许同 VPC 的应用访问）'
  - '参数组配置（基于 size 自动优化）'
  - '监控告警（CPU > 80%, 连接数 > 90%）'
  - '备份策略（跨区域复制）'
  - '加密配置（KMS 密钥自动创建）'
Terraform 抽象的局限性在于它仍然是命令式工作流（plan → apply），需要 CI/CD 流水线驱动。对于需要持续调谐（Reconciliation）的场景，Kubernetes 原生的方案更为合适。


Crossplane 声明式抽象
Crossplane 将基础设施管理带入 Kubernetes 的声明式模型中。它以 Kubernetes CRD（Custom Resource Definition）的形式暴露云资源，让基础设施管理与应用管理使用同一套工具链和工作流。


# Crossplane CompositeResourceDefinition：定义平台抽象
apiVersion: apiextensions.crossplane.io/v1
kind: CompositeResourceDefinition
metadata:
  name: databases.platform.example.com
spec:
  group: platform.example.com
  names:
    kind: Database
    plural: databases
  versions:
    - name: v1
      served: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                engine:
                  type: string
                  enum: ['postgresql', 'mysql']
                size:
                  type: string
                  enum: ['small', 'medium', 'large']
                environment:
                  type: string
                  enum: ['dev', 'staging', 'production']
# 开发者使用平台抽象（极简声明）
apiVersion: platform.example.com/v1
kind: Database
metadata:
  name: order-db
  namespace: order-service
spec:
  engine: postgresql
  size: medium
  environment: production
interface CrossplaneAdvantages {
  kubernetesNative: {
    benefit: '与应用部署使用同一工具链（kubectl, ArgoCD）';
    implication: '开发者不需要学习新工具';
  };
  continuousReconciliation: {
    benefit: '控制器持续将实际状态调谐到期望状态';
    implication: '手动修改云资源会被自动恢复';
  };
  compositionAsAbstraction: {
    benefit: 'Composition 定义资源组合，隐藏底层细节';
    implication: '一个 Database CRD 可以映射到 RDS + SecurityGroup + Backup';
  };
  multiCloud: {
    benefit: '同一个 CRD，不同 Composition 映射到不同云';
    implication: '开发者声明不变，平台团队按环境路由';
  };
}
Crossplane 的核心优势是持续调谐——控制器会不断检查实际状态与期望状态的差异并自动修复。这比 Terraform 的一次性执行模型更适合生产环境中的持续管理。


Backstage 集成与开发者界面
基础设施抽象的最终目标是让开发者无感知地使用。Backstage 作为开发者门户，为基础设施抽象提供了直观的界面层。


interface InfraAbstractionLayers {
  uiLayer: {
    tool: 'Backstage Software Templates';
    experience: '表单选择 → 一键创建';
    feedback: '实时状态显示、预计完成时间';
  };
  apiLayer: {
    tool: 'Platform API（REST/GraphQL）';
    experience: 'CLI 或 SDK 调用';
    useCase: 'CI/CD 集成、自动化脚本';
  };
  declarativeLayer: {
    tool: 'Kubernetes CRD + Crossplane';
    experience: 'YAML 声明提交到 Git';
    useCase: 'GitOps 工作流、高级定制';
  };
  directLayer: {
    tool: 'Terraform CLI / Cloud Console';
    experience: '直接操作底层资源';
    useCase: 'Escape Hatch、调试、特殊场景';
    governance: '需要额外审批';
  };
}
好的抽象设计应该提供多层访问方式：大多数开发者通过 UI 和 API 完成操作（高抽象层），有经验的工程师可以通过声明式 YAML 精细控制（中抽象层），特殊情况下可以直接操作底层资源（低抽象层）。这种分层设计兼顾了易用性和灵活性。


小结
    

  • 基础设施抽象的核心是关注点分离：开发者描述"要什么"，平台处理"怎么做"
    • 

  • Terraform 通过三层模块化（原子→组合→应用级）实现渐进式抽象
    • 

  • Crossplane 将基础设施管理带入 Kubernetes 原生声明式模型，支持持续调谐
    • 

  • 多层访问方式（UI → API → YAML → 直接操作）兼顾易用性和灵活性
    • 

  • 好的抽象让底层实现可以独立演进，开发者声明不变
    • 

  • Backstage 是基础设施抽象的理想前端，提供可视化的自助体验
    •
