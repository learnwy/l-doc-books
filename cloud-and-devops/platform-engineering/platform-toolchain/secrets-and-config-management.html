密钥与配置管理

核心概念

密钥与配置管理是平台工程中安全与便捷性交汇的关键领域。应用运行时需要数据库密码、API 密钥、TLS 证书等敏感信息，也需要功能开关、服务端点、资源限制等非敏感配置。如何安全地存储、分发和轮换这些信息，同时不增加开发者的认知负荷，是平台工程需要解决的核心问题。

传统做法中，密钥散落在各种地方——环境变量、配置文件、CI/CD 变量甚至代码仓库中。这种分散管理带来安全风险（密钥泄露）和运维困难（密钥轮换需要逐个更新）。平台化的密钥管理将密钥集中存储在专用系统中，通过自动化机制安全地注入到应用运行时。

HashiCorp Vault 架构
Vault 是平台工程中最广泛使用的密钥管理系统。它提供密钥存储、动态密钥生成、加密即服务和身份认证等能力。


interface VaultArchitecture {
  secretEngines: {
    kv: {
      description: '键值对存储（静态密钥）';
      useCase: 'API 密钥、第三方服务凭证';
      versioning: 'KV v2 支持版本历史';
    };
    database: {
      description: '动态数据库凭证生成';
      useCase: '应用连接数据库时动态获取临时凭证';
      lifecycle: '凭证自动过期、自动轮换';
      benefit: '消除长期静态数据库密码';
    };
    pki: {
      description: 'PKI 证书签发';
      useCase: '服务间 mTLS 证书自动签发和轮换';
      automation: 'cert-manager 集成自动续签';
    };
    transit: {
      description: '加密即服务';
      useCase: '应用数据加密/解密（不暴露密钥）';
      benefit: '密钥管理与应用逻辑分离';
    };
  };
  authentication: {
    kubernetes: {
      method: 'Kubernetes ServiceAccount Token';
      flow: 'Pod → K8s API → Vault → 返回 Token';
      benefit: '无需在 Pod 中预置任何凭证';
    };
    jwt: {
      method: 'JWT/OIDC Token';
      flow: 'CI/CD 系统 → JWT → Vault → 返回 Secret';
      useCase: 'GitHub Actions / GitLab CI 访问 Vault';
    };
  };
}
# Vault 策略示例
path "secret/data/order-service/*" {
  capabilities = ["read", "list"]
}

path "database/creds/order-service-db" {
  capabilities = ["read"]
}

path "pki/issue/order-service" {
  capabilities = ["create", "update"]
}

# 动态数据库凭证配置
vault write database/roles/order-service-db \
  db_name=production-postgres \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl="1h" \
  max_ttl="24h"
Vault 的动态密钥是其核心差异化能力。应用不再使用固定的数据库密码，而是在需要时向 Vault 请求临时凭证。这些凭证自动过期，即使泄露也影响有限。


External Secrets Operator
External Secrets Operator（ESO）是连接 Vault 与 Kubernetes 的桥梁。它自动将 Vault 中的密钥同步到 Kubernetes Secret，让应用以标准方式消费密钥。


# ExternalSecret 定义
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: order-service-secrets
  namespace: order-service
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: order-service-secrets
    creationPolicy: Owner
  data:
    - secretKey: DATABASE_URL
      remoteRef:
        key: secret/data/order-service/database
        property: url
    - secretKey: REDIS_URL
      remoteRef:
        key: secret/data/order-service/redis
        property: url
    - secretKey: STRIPE_API_KEY
      remoteRef:
        key: secret/data/order-service/stripe
        property: api_key
---
# ClusterSecretStore 定义
apiVersion: external-secrets.io/v1beta1
kind: ClusterSecretStore
metadata:
  name: vault-backend
spec:
  provider:
    vault:
      server: 'https://vault.example.com'
      path: 'secret'
      version: 'v2'
      auth:
        kubernetes:
          mountPath: 'kubernetes'
          role: 'external-secrets'
interface ESOWorkflow {
  syncFlow: {
    step1: 'ESO 控制器检测 ExternalSecret 资源';
    step2: '使用 ServiceAccount 向 Vault 认证';
    step3: '从 Vault 读取指定路径的密钥';
    step4: '创建/更新 Kubernetes Secret';
    step5: '应用通过环境变量或 Volume 消费';
    step6: '定期刷新（refreshInterval）';
  };
  benefits: [
    '开发者只需声明需要哪些密钥',
    '密钥轮换自动同步到 K8s Secret',
    '支持多种后端（Vault, AWS SM, GCP SM, Azure KV）',
    '密钥不出现在 Git 仓库中',
  ];
  bestPractices: [
    'refreshInterval 设为 1h（平衡性能和新鲜度）',
    '使用 ClusterSecretStore 避免重复配置',
    '密钥路径遵循 {service}/{environment}/{key} 规范',
    '为 ESO ServiceAccount 配置最小权限',
  ];
}
ESO 的关键优势是它让密钥管理对开发者完全透明——开发者只需要声明需要哪些密钥（ExternalSecret），平台自动处理认证、读取、同步和轮换。


配置中心与运行时注入
除密钥外，应用还需要大量非敏感配置。配置中心提供集中化的配置管理、版本控制和运行时热更新能力。


interface ConfigManagement {
  configSources: {
    staticConfig: {
      storage: 'Git 仓库中的 YAML/JSON 文件';
      deployment: 'CI/CD 时打包到容器镜像';
      update: '需要重新部署';
    };
    configMap: {
      storage: 'Kubernetes ConfigMap';
      deployment: '独立于应用镜像';
      update: '修改 ConfigMap + 重启 Pod';
    };
    runtimeConfig: {
      storage: '配置中心（Consul / etcd / 自建）';
      deployment: '应用启动时拉取';
      update: '运行时热更新（无需重启）';
    };
  };
  featureFlags: {
    purpose: '功能开关，控制功能的渐进发布';
    tools: ['LaunchDarkly', 'Unleash', 'Flagsmith'];
    patterns: ['灰度发布：按用户百分比开放功能', 'A/B 测试：按用户分组展示不同版本', '紧急开关：快速关闭有问题的功能'];
  };
}
# Kubernetes ConfigMap 最佳实践
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-service-config
  namespace: order-service
  labels:
    app: order-service
    config-version: 'v2.3'
data:
  config.yaml: |
    server:
      port: 8080
      gracefulShutdown: 30s

    rateLimit:
      enabled: true
      requestsPerSecond: 100

    cache:
      ttl: 300s
      maxSize: 10000

    featureFlags:
      newCheckoutFlow: true
      paymentV2: false

# 配置变更触发 Pod 滚动更新
# 通过 config hash 注解实现
spec:
  template:
    metadata:
      annotations:
        checksum/config: '{{ sha256sum .Values.config }}'
配置管理的最佳实践是分层管理：基础配置（端口、超时等）固化在代码或 ConfigMap 中；环境特定配置（端点地址、资源限制）通过环境变量覆盖；动态配置（功能开关、限流阈值）通过配置中心实时推送。这种分层设计兼顾了稳定性和灵活性。


小结
    

  • 密钥应集中存储在 Vault 等专用系统中，通过 ESO 自动同步到 Kubernetes
    • 

  • Vault 的动态密钥消除了长期静态密码的安全风险
    • 

  • ESO 让密钥管理对开发者透明——声明需求，平台自动处理
    • 

  • 配置分三层管理：静态配置、环境配置和动态配置
    • 

  • 功能开关支持灰度发布、A/B 测试和紧急功能关闭
    • 

  • 安全原则：永远不在 Git 中存储密钥，所有访问都有审计日志
    •
