可观测性平台

核心概念

可观测性平台是平台工程中保障服务可靠性的关键基础设施。它统一收集、存储和分析系统的三大信号——日志（Logs）、指标（Metrics）和追踪（Traces），让开发者能快速定位和解决生产问题。平台工程的目标是让可观测性成为"默认内置"而非"额外集成"。

传统模式下，每个团队自行选择和集成监控工具，导致工具碎片化、数据孤岛和故障排查困难。平台化的可观测性将工具选型和集成封装在平台层，开发者只需关注业务指标和告警规则。

OpenTelemetry 统一采集
OpenTelemetry（OTel）是 CNCF 的可观测性标准，统一了日志、指标和追踪的采集协议和 SDK。平台工程推荐以 OTel 作为可观测性的统一采集层，避免工具锁定。


# OpenTelemetry Collector 配置
apiVersion: opentelemetry.io/v1alpha1
kind: OpenTelemetryCollector
metadata:
  name: platform-collector
spec:
  mode: daemonset
  config: |
    receivers:
      otlp:
        protocols:
          grpc:
            endpoint: 0.0.0.0:4317
          http:
            endpoint: 0.0.0.0:4318
      prometheus:
        config:
          scrape_configs:
            - job_name: kubernetes-pods
              kubernetes_sd_configs:
                - role: pod

    processors:
      batch:
        send_batch_size: 1000
        timeout: 10s
      memory_limiter:
        check_interval: 1s
        limit_mib: 512
      resource:
        attributes:
          - key: cluster
            value: production-us-east
            action: upsert

    exporters:
      otlp/tempo:
        endpoint: tempo.observability:4317
      prometheusremotewrite:
        endpoint: http://mimir.observability:9009/api/v1/push
      loki:
        endpoint: http://loki.observability:3100/loki/api/v1/push

    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [memory_limiter, batch, resource]
          exporters: [otlp/tempo]
        metrics:
          receivers: [otlp, prometheus]
          processors: [memory_limiter, batch, resource]
          exporters: [prometheusremotewrite]
        logs:
          receivers: [otlp]
          processors: [memory_limiter, batch, resource]
          exporters: [loki]
interface OTelPlatformIntegration {
  autoInstrumentation: {
    description: '无代码修改的自动追踪注入';
    mechanism: 'Kubernetes Operator 自动注入 OTel SDK';
    languages: ['Java', 'Python', 'Node.js', 'Go', '.NET'];
    config: '通过 Pod 注解触发：instrumentation.opentelemetry.io/inject-nodejs: true';
  };
  standardAttributes: {
    required: ['service.name', 'service.version', 'deployment.environment', 'k8s.namespace.name', 'k8s.pod.name'];
    recommended: ['team.name', 'service.tier', 'cost.center'];
    enforcement: 'OTel Collector 的 resource processor 自动补充';
  };
  samplingStrategy: {
    traces: {
      headSampling: '10% 基准采样';
      tailSampling: '错误请求和慢请求 100% 保留';
      rule: 'P99 延迟 > SLO 阈值 → 100% 采样';
    };
  };
}
OTel 自动注入是平台工程的标志性能力——开发者无需修改一行代码，部署到 Kubernetes 后即可自动获得追踪数据。这通过 OTel Operator 的 MutatingWebhook 实现，在 Pod 创建时自动注入 SDK sidecar。


统一仪表板与告警
可观测性数据的价值最终通过仪表板和告警体现。平台团队应该为每种服务类型提供标准化仪表板模板，开发者可以在此基础上定制业务指标。


interface DashboardStrategy {
  standardDashboards: {
    serviceOverview: {
      panels: ['请求率（QPS）', '错误率', '延迟分布（P50/P90/P99）', '饱和度（CPU/内存/连接数）'];
      source: 'OTel 指标 + Kubernetes 指标';
      autoProvisioned: true;
    };
    kubernetesHealth: {
      panels: ['Pod 状态分布', '重启次数', '资源使用率', 'HPA 状态'];
      source: 'kube-state-metrics';
    };
    businessMetrics: {
      panels: '团队自定义';
      examples: ['订单创建量/分钟', '支付成功率', '库存预警数'];
      source: '应用自定义指标';
    };
  };
  alertingPlatform: {
    tool: 'Grafana Alerting / Alertmanager';
    routing: '按团队和严重级别路由';
    channels: ['PagerDuty（P1/P2）', 'Slack（P3/P4）', 'Email（摘要）'];
    standardAlerts: ['错误率 > 1%（5分钟窗口）', 'P99 延迟 > SLO 阈值', 'Pod 重启 > 3次/小时', '磁盘使用 > 85%'];
  };
}
# Grafana 告警规则示例（平台标准）
apiVersion: monitoring.grafana.com/v1
kind: AlertRule
metadata:
  name: high-error-rate
  namespace: order-service
spec:
  groups:
    - name: service-health
      interval: 1m
      rules:
        - alert: HighErrorRate
          expr: |
            sum(rate(http_server_request_duration_seconds_count{
              status_code=~"5..",
              service_name="order-service"
            }[5m]))
            /
            sum(rate(http_server_request_duration_seconds_count{
              service_name="order-service"
            }[5m]))
            > 0.01
          for: 5m
          labels:
            severity: critical
            team: order-team
          annotations:
            summary: 'order-service 错误率超过 1%'
            runbook: 'https://wiki.example.com/runbooks/high-error-rate'
告警设计的核心原则是"可操作的告警"：每条告警都应该有明确的 Runbook（操作手册），告诉值班人员如何排查和修复。无 Runbook 的告警应该被视为平台缺陷。


关联分析与故障排查
三大信号的真正价值在于关联分析：通过 TraceID 将日志、指标和追踪串联起来，实现从告警到根因的快速定位。


interface CorrelationStrategy {
  traceContext: {
    propagation: 'W3C Trace Context 标准';
    format: 'traceparent: 00-{traceId}-{spanId}-{flags}';
    injection: 'OTel SDK 自动传播到下游服务';
  };
  logCorrelation: {
    mechanism: '日志中自动注入 trace_id 和 span_id';
    query: '在 Grafana 中从追踪跳转到关联日志';
    benefit: '精确定位特定请求的日志上下文';
  };
  metricCorrelation: {
    exemplars: '指标数据点关联到具体的 TraceID';
    query: '从异常指标点击跳转到具体追踪';
    benefit: '从宏观指标异常深入到微观请求细节';
  };
  workflow: [
    '1. 告警触发 → Grafana 仪表板',
    '2. 识别异常时间窗口和服务',
    '3. 从异常指标点击 Exemplar → 追踪详情',
    '4. 在追踪中找到异常 Span',
    '5. 从 Span 跳转到关联日志',
    '6. 日志中定位具体错误信息',
    '7. 修复或回滚',
  ];
}
关联分析的前提是统一的元数据标准。所有信号必须包含一致的标签（service.name, deployment.environment, k8s.namespace.name），才能在 Grafana 中实现无缝跳转。平台团队通过 OTel Collector 的 resource processor 强制补充这些标签。

  • 可观测性平台统一日志、指标和追踪的采集、存储和分析

  • OpenTelemetry 是推荐的统一采集标准，避免工具锁定

  • OTel 自动注入让开发者无需改代码即可获得追踪能力
    • 

  • 标准化仪表板模板 + 可操作的告警是平台可观测性的核心交付

    • 

  • 每条告警必须有 Runbook——无 Runbook 的告警是平台缺陷
