CI/CD 平台设计

核心概念

CI/CD 平台是平台工程中使用频率最高的基础设施。每个开发者每天都会与 CI/CD 系统交互多次——从代码提交到构建、测试、部署，CI/CD 流水线贯穿整个交付流程。平台工程视角下的 CI/CD 不再是各团队各自维护的脚本集合，而是一个标准化、可扩展的平台服务。

平台化的 CI/CD 设计需要解决三个核心问题：标准化（统一流水线模板降低认知负荷）、多租户（隔离不同团队的构建环境和资源）和性能优化（构建缓存和并行化缩短反馈时间）。

流水线即代码
流水线即代码（Pipeline as Code）是 CI/CD 平台化的基础。流水线定义存储在代码仓库中，与应用代码一起版本化管理。平台团队提供共享模板，开发者通过组合和定制来满足特定需求。


# 平台提供的共享流水线模板
# .github/workflows/platform-ci.yml
name: Platform CI
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  ci:
    uses: platform-org/ci-templates/.github/workflows/typescript-service.yml@v3
    with:
      node-version: '20'
      test-command: 'pnpm test'
      lint-command: 'pnpm lint'
      build-command: 'pnpm build'
      docker-registry: 'registry.example.com'
      helm-chart: 'charts/service'
    secrets: inherit
interface PipelineTemplateDesign {
  layeredTemplates: {
    base: {
      scope: '所有项目共用';
      includes: ['checkout', '缓存恢复', '依赖安装', '安全扫描'];
    };
    language: {
      scope: '按语言分类';
      examples: ['typescript-service', 'java-springboot', 'go-service'];
      includes: ['编译', '单元测试', 'lint', '构建镜像'];
    };
    deployment: {
      scope: '按部署策略分类';
      examples: ['canary-deploy', 'blue-green-deploy', 'rolling-deploy'];
      includes: ['部署、健康检查、回滚策略'];
    };
  };
  customization: {
    override: '开发者可覆盖模板中的步骤参数';
    extend: '通过 pre/post hooks 添加自定义步骤';
    escape: '完全自定义流水线（需审批）';
  };
  versioning: {
    strategy: '语义化版本（v1, v2, v3）';
    migration: '主版本升级提供迁移指南';
    deprecation: '旧版本保留 6 个月';
  };
}
模板设计的关键原则是"合理默认、允许覆盖"。80% 的项目应该可以直接使用模板而无需修改，剩余 20% 通过参数覆盖或自定义 hooks 满足特殊需求。如果超过 30% 的项目需要大量定制，说明模板设计需要改进。


多租户 CI 设计
多租户是平台化 CI 的关键挑战。不同团队共享 CI 基础设施时，需要确保资源隔离、安全隔离和性能公平。


interface MultiTenantCI {
  resourceIsolation: {
    runnerPools: {
      strategy: '按团队或优先级分配专用 Runner 池';
      sizing: '基于历史使用量自动扩缩容';
      fairScheduling: '防止单团队垄断所有资源';
    };
    buildEnvironment: {
      containerIsolation: '每次构建使用独立容器';
      networkIsolation: '构建容器无法访问其他团队资源';
      secretIsolation: '团队 Secret 仅该团队流水线可访问';
    };
  };
  quotaManagement: {
    concurrentBuilds: {
      default: 5;
      critical: 10;
      experimental: 2;
    };
    maxBuildDuration: {
      default: '30 分钟';
      extended: '60 分钟（需申请）';
    };
    storageQuota: {
      cache: '每团队 50GB';
      artifacts: '每团队 100GB';
    };
  };
  costAllocation: {
    method: '按构建分钟数和资源消耗归属到团队';
    reporting: '月度成本报告 → 团队负责人';
    optimization: '识别高成本流水线并建议优化';
  };
}
多租户 CI 的关键决策是共享 Runner 还是专用 Runner。共享 Runner 成本低但存在"邻居噪音"问题（一个团队的大量构建影响其他团队）；专用 Runner 隔离好但成本高。推荐的策略是：默认共享 + 关键服务专用。


构建缓存与性能优化
构建速度直接影响开发者反馈循环。平台工程的目标是将 CI 构建时间控制在 10 分钟以内。分层缓存和并行化是最有效的优化手段。


interface BuildOptimization {
  layeredCaching: {
    dependencyCache: {
      what: 'npm/pnpm/maven 依赖缓存';
      key: 'lockfile hash';
      hitRate: '> 95%';
      savings: '节省 2-5 分钟';
    };
    buildCache: {
      what: '编译产物缓存（Turborepo, Nx）';
      key: '源文件 hash';
      hitRate: '> 70%';
      savings: '节省 3-10 分钟';
    };
    dockerLayerCache: {
      what: 'Docker 层缓存';
      key: 'Dockerfile + 依赖 hash';
      hitRate: '> 80%';
      savings: '节省 5-15 分钟';
    };
    remoteCache: {
      what: '跨 CI 运行共享的远程缓存';
      tool: 'Turborepo Remote Cache / Gradle Build Cache';
      benefit: '不同 PR 间共享编译结果';
    };
  };
  parallelization: {
    testSharding: '将测试套件分片到多个 Runner 并行执行';
    matrixBuilds: '多平台/多版本并行构建';
    pipelineStages: '无依赖的阶段并行执行';
  };
  incrementalBuilds: {
    affectedOnly: '只构建和测试受变更影响的模块';
    tool: 'Nx affected / Turborepo --filter';
    savings: 'Monorepo 场景下节省 50-80% 构建时间';
  };
}
ci_performance_targets:
  feedback_time:
    lint_check: '< 2 分钟'
    unit_tests: '< 5 分钟'
    full_ci: '< 10 分钟'
    docker_build: '< 3 分钟'

  reliability:
    success_rate: '> 95%（排除代码错误）'
    flaky_test_rate: '< 1%'
    infrastructure_failure: '< 0.1%'

  optimization_actions:
    slow_builds:
      detection: 'P95 构建时间 > 15 分钟'
      action: '分析构建日志，识别瓶颈步骤'
    flaky_tests:
      detection: '同一测试在不同运行中结果不一致'
      action: '隔离到 flaky 套件，标记并修复'
    cache_miss:
      detection: '缓存命中率 < 80%'
      action: '检查缓存 key 策略和存储容量'
构建性能的持续监控同样重要。平台团队应该追踪构建时间趋势、缓存命中率和失败原因分布。当构建时间出现退化时，应该主动介入而非等待开发者投诉。


小结
    

  • CI/CD 平台化的核心是标准化模板 + 多租户隔离 + 性能优化
    • 

  • 流水线模板采用分层设计：基础层 → 语言层 → 部署策略层
    • 

  • 多租户隔离包括资源隔离、安全隔离和成本归属
    • 

  • 分层缓存（依赖→构建→Docker 层）是缩短构建时间的最有效手段
    • 

  • CI 构建时间目标：完整流水线 < 10 分钟，单元测试 < 5 分钟
    • 

  • 持续监控构建性能趋势，主动识别和修复退化问题
    •
