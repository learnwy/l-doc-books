容器编排平台

核心概念

容器编排平台是现代平台工程的运行时基座。Kubernetes 已成为事实上的标准，但在大规模组织中，管理多个 Kubernetes 集群——跨环境（开发/预发/生产）、跨区域（多数据中心/多云）——带来了显著的复杂性。平台工程的目标是将这些复杂性封装在平台层，让开发者以业务语义而非 Kubernetes 原语来描述部署需求。

多集群管理的核心挑战包括：配置一致性（如何确保所有集群的安全策略和网络配置一致）、跨集群服务发现（如何让不同集群的服务互相通信）以及运维效率（如何高效地在数十个集群上执行变更）。

Kubernetes 多集群管理
多集群管理工具负责将统一的配置和策略分发到所有集群，确保一致性和合规性。


interface MultiClusterArchitecture {
  managementTools: {
    argocd: {
      pattern: 'Hub-and-Spoke（中心辐射）';
      mechanism: '中央 ArgoCD 管理所有集群的 GitOps';
      scaling: 'App of Apps 模式管理大量应用';
    };
    fleet: {
      pattern: 'Rancher Fleet';
      mechanism: '声明式多集群 GitOps';
      feature: '集群分组 + Bundle 分发';
    };
    karmada: {
      pattern: '联邦调度';
      mechanism: '统一 API 面，工作负载自动分发到成员集群';
      feature: '跨集群调度策略';
    };
  };
  clusterProvisioning: {
    tool: 'Cluster API (CAPI) / Crossplane';
    workflow: '声明集群规格 → 自动创建 → 自动注册到管理面';
    standardization: [
      '统一 CNI（如 Cilium）',
      '统一 Ingress Controller（如 Nginx/Envoy）',
      '统一监控 Agent（OpenTelemetry）',
      '统一安全策略（OPA Gatekeeper）',
    ];
  };
}
# ArgoCD ApplicationSet：多集群部署
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: order-service
  namespace: argocd
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            environment: production
  template:
    metadata:
      name: 'order-service-{{name}}'
    spec:
      project: order-team
      source:
        repoURL: https://github.com/org/order-service
        targetRevision: main
        path: deploy/overlays/{{metadata.labels.region}}
      destination:
        server: '{{server}}'
        namespace: order-service
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
ArgoCD 的 ApplicationSet 是管理多集群部署的有效工具。通过集群标签选择器，一份配置可以自动分发到所有匹配的集群。结合 Kustomize 的 overlay 机制，可以在保持基础配置一致的同时，为不同区域定制特定参数。


命名空间策略与多租户
Kubernetes 命名空间是平台多租户隔离的基本单元。每个团队或服务拥有独立的命名空间，配合 RBAC、网络策略和资源配额实现隔离。


interface NamespaceStrategy {
  namingConvention: {
    pattern: '{team}-{service}-{environment}';
    examples: ['order-team-order-service-dev', 'order-team-order-service-prod'];
  };
  provisioning: {
    trigger: '新服务创建时自动创建命名空间';
    includes: [
      '命名空间创建',
      'RBAC RoleBinding（团队成员读写、其他只读）',
      'NetworkPolicy（默认拒绝入站、允许同命名空间）',
      'ResourceQuota（CPU、内存、Pod 数量限制）',
      'LimitRange（单 Pod 资源上下限）',
    ];
  };
}
# 命名空间标准化模板
apiVersion: v1
kind: Namespace
metadata:
  name: order-service-prod
  labels:
    team: order-team
    environment: production
    cost-center: engineering
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: standard-quota
  namespace: order-service-prod
spec:
  hard:
    requests.cpu: '8'
    requests.memory: '16Gi'
    limits.cpu: '16'
    limits.memory: '32Gi'
    pods: '50'
    services: '10'
    persistentvolumeclaims: '5'
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: order-service-prod
spec:
  podSelector: {}
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              team: order-team
        - namespaceSelector:
            matchLabels:
              role: ingress-controller
命名空间策略的设计需要平衡隔离性和灵活性。过于严格的网络策略会阻碍合法的跨服务通信，过于宽松则无法提供有效隔离。推荐的做法是"默认拒绝 + 显式允许"：默认禁止所有跨命名空间流量，团队通过声明式网络策略显式打开必要的通信路径。


平台级 Kubernetes 扩展
平台团队通常需要在 Kubernetes 基础能力上构建平台级扩展，以标准化运维实践和降低开发者负担。


interface PlatformExtensions {
  admissionWebhooks: {
    purpose: '在资源创建/更新时执行策略检查';
    examples: ['禁止使用 latest 镜像标签', '强制设置资源 limits', '禁止特权容器', '强制设置 Pod 安全上下文'];
    tool: 'OPA Gatekeeper / Kyverno';
  };
  customControllers: {
    purpose: '自动化平台级运维操作';
    examples: [
      '自动注入 Sidecar（日志收集、Service Mesh）',
      '自动配置 HPA 基于标准化规则',
      '自动创建 ServiceMonitor 用于 Prometheus',
      '自动注入环境变量（集群信息、服务发现）',
    ];
  };
  operators: {
    purpose: '管理复杂有状态工作负载';
    examples: [
      '数据库 Operator（PostgreSQL、MySQL）',
      '消息队列 Operator（Kafka、RabbitMQ）',
      '缓存 Operator（Redis）',
    ];
    benefit: '开发者声明需求，Operator 处理复杂的运维逻辑';
  };
}
# Kyverno 策略示例：强制镜像来源
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: restrict-image-registries
spec:
  validationFailureAction: Enforce
  rules:
    - name: validate-registries
      match:
        any:
          - resources:
              kinds: ['Pod']
      validate:
        message: '镜像必须来自内部镜像仓库'
        pattern:
          spec:
            containers:
              - image: 'registry.example.com/*'
平台级 Kubernetes 扩展的核心价值是"护栏而非围墙"——通过自动化策略和控制器保障安全和一致性，同时不限制开发者的合理操作。策略应该有明确的错误信息，告诉开发者"为什么不行"和"怎么修复"。
