Part IV · 容器与编排微服务架构 简介服务通信 简介同步通信模式

同步通信模式

核心概念

同步通信（Synchronous Communication）是微服务间最直接的交互方式，调用方发送请求后阻塞等待响应。REST API 和 gRPC 是两种主流的同步通信协议，分别基于 HTTP/JSON 和 HTTP/2 + Protocol Buffers。同步通信的优势是编程模型简单、调试直觉；劣势是调用链路上的任何服务故障或延迟都会级联传播，形成分布式系统的脆弱点。

RESTful API 设计
REST（Representational State Transfer）是最广泛使用的 API 设计风格，以资源为中心，通过 HTTP 方法（GET/POST/PUT/PATCH/DELETE）表达对资源的操作。RESTful API 设计遵循统一接口、无状态和分层系统等架构约束。


资源命名使用名词复数形式，通过 URL 路径表达资源层级关系。操作语义映射到 HTTP 方法：GET 查询（幂等）、POST 创建、PUT 全量更新（幂等）、PATCH 部分更新、DELETE 删除（幂等）。


GET    /api/v1/orders                  # 查询订单列表
GET    /api/v1/orders/{orderId}        # 查询单个订单
POST   /api/v1/orders                  # 创建订单
PUT    /api/v1/orders/{orderId}        # 全量更新订单
PATCH  /api/v1/orders/{orderId}        # 部分更新订单
DELETE /api/v1/orders/{orderId}        # 删除订单
GET    /api/v1/orders/{orderId}/items  # 查询订单下的商品项
API 版本管理通过 URL 路径（/v1/、/v2/）或 HTTP Header（Accept: application/vnd.api+json;version=2）实现。URL 版本直觉简单但破坏 REST 纯粹性，Header 版本保持 URL 稳定但对客户端要求更高。企业实践中 URL 版本更为普遍。


分页通过 page/pageSize 或 cursor/limit 参数实现。游标分页（Cursor-based）在大数据量场景下性能优于偏移分页（Offset-based），因为它不需要数据库执行 OFFSET 操作。HATEOAS（Hypermedia as the Engine of Application State）在响应中嵌入相关资源的链接，使客户端可以动态发现 API 结构。


gRPC 高性能通信
gRPC 是 Google 开发的高性能 RPC 框架，基于 HTTP/2 协议和 Protocol Buffers 序列化格式。gRPC 的核心优势是强类型契约（.proto 文件）、自动代码生成、双向流式通信和低延迟。Protocol Buffers 的二进制编码比 JSON 小 3-10 倍，序列化/反序列化速度快 5-10 倍。


syntax = "proto3";

package order.v1;

service OrderService {
  rpc CreateOrder(CreateOrderRequest) returns (CreateOrderResponse);
  rpc GetOrder(GetOrderRequest) returns (Order);
  rpc ListOrders(ListOrdersRequest) returns (ListOrdersResponse);
  rpc StreamOrderUpdates(StreamOrdersRequest) returns (stream OrderUpdate);
}

message CreateOrderRequest {
  string user_id = 1;
  repeated OrderItem items = 2;
  Address shipping_address = 3;
}

message Order {
  string order_id = 1;
  string user_id = 2;
  OrderStatus status = 3;
  repeated OrderItem items = 4;
  google.protobuf.Timestamp created_at = 5;
}

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;
  ORDER_STATUS_PENDING = 1;
  ORDER_STATUS_CONFIRMED = 2;
  ORDER_STATUS_SHIPPED = 3;
  ORDER_STATUS_DELIVERED = 4;
}
gRPC 支持四种通信模式：一元调用（Unary，请求-响应）、服务端流（Server Streaming）、客户端流（Client Streaming）和双向流（Bidirectional Streaming）。服务端流适合实时数据推送（如价格变动），双向流适合实时交互（如聊天和协作编辑）。


gRPC 拦截器（Interceptor）是扩展横切关注点的标准机制，功能类似 HTTP 中间件。常见拦截器包括：认证拦截器（JWT 验证）、日志拦截器（请求/响应记录）、重试拦截器（自动重试幂等操作）和追踪拦截器（注入 TraceID）。


容错与弹性模式
同步通信的最大风险是级联故障（Cascading Failure）。当下游服务响应变慢或不可用时，上游服务的线程池会被阻塞请求耗尽，最终整个调用链路崩溃。断路器（Circuit Breaker）、超时控制、重试策略和限流降级是四种核心容错模式。

重试策略必须配合幂等性设计。GET 和 DELETE 操作天然幂等，POST 操作通过幂等键（Idempotency Key）保障：客户端在请求头中携带唯一的幂等键，服务端在处理前检查该键是否已处理过。指数退避（Exponential Backoff）+ 随机抖动（Jitter）避免重试风暴。


小结
    

  • REST 适合公共 API 和第三方集成，gRPC 适合服务间高性能通信
    • 

  • RESTful 设计以资源为中心，通过 HTTP 方法表达操作语义
    • 

  • gRPC 通过 Protobuf 实现强类型契约和自动代码生成，支持四种流式通信模式
    • 

  • 断路器、超时、重试和舱壁隔离是同步通信的四大容错模式
    • 

  • 重试策略必须配合幂等性设计，指数退避 + 抖动防止重试风暴
    • 

  • 级联故障是同步通信的最大风险，容错设计是生产环境的必需品
    •
