事件溯源模式

核心概念

事件溯源（Event Sourcing）是一种数据持久化模式，将系统状态的变更记录为一系列不可变的领域事件（Domain Event），而非直接存储当前状态快照。系统的当前状态通过回放（Replay）事件序列从零推导得出。每个事件代表一个已经发生的业务事实（如"订单已创建"、"商品已添加"、"支付已完成"），事件一旦写入就不可修改或删除。

事件存储设计
事件存储（Event Store）是事件溯源架构的核心组件，负责持久化所有领域事件。事件存储的核心操作是追加事件（Append）和按聚合 ID 读取事件流（Read Stream）。事件存储保证同一聚合内事件的严格有序性，通过乐观并发控制（Expected Version）防止并发写入冲突。


interface DomainEvent {
  eventId: string;
  aggregateId: string;
  aggregateType: string;
  eventType: string;
  eventVersion: number;
  payload: Record<string, unknown>;
  metadata: EventMetadata;
  occurredAt: Date;
  sequenceNumber: number;
}

interface EventMetadata {
  correlationId: string;
  causationId: string;
  userId: string;
  traceId: string;
}

PostgreSQL 实现事件存储的表设计包含 aggregate_id（聚合标识）、sequence_number（聚合内序号，用于乐观并发）、event_type（事件类型名称）、payload（事件数据，JSONB 格式）和 metadata（元数据，包含关联 ID 和追踪信息）。唯一约束 (aggregate_id, sequence_number) 保证并发安全。


快照（Snapshot）机制优化长事件流的回放性能。当聚合的事件数量超过阈值（如每 100 个事件），存储当前状态的快照。恢复聚合时，先加载最新快照，再回放快照之后的事件。快照是可选的性能优化，不改变事件溯源的语义。


聚合与事件生成
聚合（Aggregate）是事件溯源中的核心领域对象，每个聚合维护一个事件流。聚合通过处理命令（Command）生成事件，通过回放事件重建状态。聚合的状态是完全由其事件流决定的——给定相同的事件序列，聚合总是重建为相同的状态。


class OrderAggregate {
  private state: OrderState = { status: 'DRAFT', items: [], total: 0 };
  private uncommittedEvents: DomainEvent[] = [];

  createOrder(command: CreateOrderCommand): void {
    if (this.state.status !== 'DRAFT') {
      throw new Error('Order already exists');
    }
    this.apply({
      eventType: 'OrderCreated',
      payload: {
        orderId: command.orderId,
        userId: command.userId,
        createdAt: new Date(),
      },
    });
  }

  addItem(command: AddItemCommand): void {
    if (this.state.status !== 'DRAFT') {
      throw new Error('Cannot modify non-draft order');
    }
    this.apply({
      eventType: 'ItemAdded',
      payload: {
        productId: command.productId,
        quantity: command.quantity,
        unitPrice: command.unitPrice,
      },
    });
  }

  private apply(event: Partial<DomainEvent>): void {
    this.applyEvent(event as DomainEvent);
    this.uncommittedEvents.push(event as DomainEvent);
  }

  private applyEvent(event: DomainEvent): void {
    switch (event.eventType) {
      case 'OrderCreated':
        this.state.status = 'CREATED';
        break;
      case 'ItemAdded':
        this.state.items.push(event.payload as OrderItem);
        this.state.total += event.payload.quantity * event.payload.unitPrice;
        break;
    }
  }
}
事件设计原则：事件应包含足够的上下文信息使消费者能独立处理（胖事件 vs 瘦事件的权衡）；事件命名使用过去式表达已发生的事实；事件 payload 使用显式的数据类型而非通用的 Map；关联 ID（Correlation ID）串联因果链路便于追踪。


投影与读模型
投影（Projection）是从事件流构建读优化视图的过程。投影器（Projector）订阅事件存储的事件流，根据事件类型更新对应的读模型。读模型可以使用任何适合查询需求的存储技术（关系数据库的物化视图、Elasticsearch 的搜索索引、Redis 的缓存数据）。


投影的核心特性是可重建性（Rebuildable）。由于事件存储保留了完整的事件历史，任何投影都可以从头重建。这意味着可以随时添加新的读模型、修改现有投影的逻辑、或在数据损坏时从事件流完全恢复。投影重建的性能取决于事件总量和处理速度，大型系统可能需要数小时甚至数天完成全量重建。


最终一致性是投影的固有特征——事件写入事件存储后，投影器需要一定时间处理并更新读模型。在大多数业务场景中，毫秒到秒级的延迟是可接受的。对于需要强一致性的查询（如"我刚创建的订单能立即看到吗"），可以在写操作返回后客户端携带 lastEventSequence 轮询读模型直到一致。


事件版本化与演进
事件一旦写入就不可修改，但业务模型会持续演进，事件的 Schema 需要随之变化。事件版本化（Event Versioning）策略确保新代码能处理所有历史版本的事件。

上投影（Upcasting）是最常用的版本化策略。当聚合从事件存储加载事件时，经过 Upcaster 管道将旧版本事件转换为当前版本的格式。Upcaster 是纯函数，按版本号链式调用（v1 → v2 → v3）。上投影不修改存储中的原始事件，保留了完整的历史原貌。


事件溯源系统的长期运维需要关注存储增长管理。归档策略将超过保留期的历史事件迁移到冷存储（S3/Glacier），保留最新快照和近期事件在热存储中。截断策略在特定时间点对聚合做快照后，删除快照之前的所有事件，但这种做法牺牲了完整历史的可回放性。


小结
    

  • 事件溯源将状态变更记录为不可变事件序列，天然具备完整的历史追溯能力
    • 

  • 事件存储保证聚合内事件有序，乐观并发控制和快照机制保障一致性和性能
    • 

  • 聚合通过处理命令生成事件，通过回放事件重建状态，状态由事件流唯一决定
    • 

  • 投影从事件流构建读优化视图，可重建特性使新读模型可随时添加
    • 

  • 事件版本化通过上投影策略处理 Schema 演进，不修改历史事件原始数据
    • 

  • 事件溯源适合复杂业务逻辑、审计需求强和需要时间旅行能力的系统
