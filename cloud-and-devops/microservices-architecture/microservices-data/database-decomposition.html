数据库拆分策略

核心概念

数据库拆分（Database Decomposition）是微服务架构中实现服务数据独立性的核心策略。每个微服务拥有自己的私有数据库（Database per Service），其他服务不能直接访问该数据库，只能通过服务的 API 获取数据。这种模式是微服务松耦合的数据层基础——服务可以独立选择最适合自己业务特征的数据库技术（SQL/NoSQL/时序/图），独立进行 Schema 变更和性能优化，不受其他服务影响。

数据所有权与边界
数据所有权（Data Ownership）原则要求每条业务数据只有一个服务是其权威来源（Authoritative Source）。其他需要该数据的服务通过 API 查询或事件订阅获取数据的副本，副本数据允许有短暂延迟（最终一致性），但不允许直接修改。


确定数据所有权的方法与 DDD 的限界上下文分析一致。每个限界上下文拥有自己的领域模型和对应的数据存储。同一个业务概念（如"客户"）在不同上下文中可能有不同的视角：订单上下文只关心客户 ID 和收货地址，CRM 上下文关心客户的完整画像和交互历史。


数据引用模式处理跨服务的数据关联。服务 A 中需要引用服务 B 的数据时，只存储 B 的实体 ID（外键引用），而非复制完整数据。当需要展示组合数据时，通过 API 组合查询或使用 CQRS 模式预先物化。


跨服务数据一致性不依赖分布式事务，而是通过 Saga 模式（长事务分解为补偿链）和事件驱动（发布-订阅状态变更事件）实现最终一致性。业务设计上需要接受短暂的数据不一致窗口，并在 UI 层面对用户设置合理的预期。


Schema 演进与数据迁移
微服务独立拥有数据库后，Schema 变更成为每个团队的自主操作，不再需要 DBA 统一协调。但 Schema 变更仍需谨慎管理，尤其是在蓝绿部署和滚动更新期间，新旧版本代码可能同时运行并访问数据库。

数据迁移工具（Flyway、Liquibase、golang-migrate）管理 Schema 变更的版本化和自动执行。迁移脚本按版本号顺序排列，每次部署时自动执行未应用的迁移。迁移脚本应可重入且有回滚脚本（Down Migration），CI 中自动测试迁移的前滚和回滚。


从单体数据库到微服务数据库的迁移是最复杂的数据拆分场景。推荐使用"数据库视图"过渡法：先在单体数据库中为目标服务创建视图，服务通过视图访问数据 → 将视图背后的表迁移到独立数据库 → 用 CDC 同步维护视图数据 → 最终移除视图，服务切换到独立数据库直连。


CQRS 与读写分离
CQRS（Command Query Responsibility Segregation）将系统的写操作（Command）和读操作（Query）分离到不同的模型和数据存储中。写侧使用规范化的关系模型保证数据一致性，读侧使用反规范化的物化视图（Materialized View）优化查询性能。


CQRS 在微服务中的典型应用：订单服务的写操作（创建、修改、取消）使用 PostgreSQL 保证事务一致性，搜索和列表查询使用 Elasticsearch 提供全文检索和聚合分析。写数据库的变更通过 CDC（Change Data Capture）实时同步到 Elasticsearch，读写之间存在毫秒到秒级的最终一致性延迟。


CQRS 的读模型可以针对不同的查询场景构建多个物化视图。商品服务可能需要：面向搜索的 Elasticsearch 索引（全文检索）、面向推荐的 Redis 缓存（热门商品）、面向报表的 ClickHouse 表（销售统计）。每个物化视图从同一个事件流中消费数据，按自己的需求进行转换和聚合。

Polyglot Persistence
Polyglot Persistence（多语言持久化）是微服务架构下每个服务选择最适合自己业务特征的数据库技术的实践。不再强制所有服务使用统一的关系型数据库，而是根据数据模型、访问模式和性能需求灵活选择。

Polyglot Persistence 的挑战包括：运维团队需要掌握多种数据库的运维技能、跨数据库的数据一致性需要应用层保障、监控和告警系统需要覆盖所有数据库类型。企业实践中通常限制为 3-5 种核心数据库技术，通过平台团队提供标准化的托管服务降低运维成本。
