每服务一数据库模式

核心概念

每服务一数据库（Database per Service）是微服务架构中数据管理的核心原则——每个微服务拥有自己独立的数据库实例或 Schema，其他服务不能直接访问该数据库。这一原则保证了服务的松耦合和独立部署能力。如果多个服务共享同一个数据库，任何 Schema 变更都需要协调所有相关服务，本质上回到了单体架构的耦合状态。

然而，每服务一数据库带来了分布式数据管理的核心挑战：跨服务查询、数据一致性和事务管理。在单体架构中，一个 SQL JOIN 就能完成的操作，在微服务架构中可能需要多次 API 调用和复杂的数据组合逻辑。如何在保持服务自治的同时解决这些数据管理挑战，是微服务架构师面临的最关键设计决策。

数据库选型与多语言持久化
每服务一数据库模式的一个重要优势是多语言持久化（Polyglot Persistence）——每个服务可以根据自身的数据特性选择最合适的数据库技术，而非被迫使用统一的数据库方案。


关系型数据库（PostgreSQL、MySQL）：适用于需要复杂查询、事务保证和数据完整性约束的服务。订单服务、财务服务等核心业务服务通常选择关系型数据库。


文档数据库（MongoDB、DynamoDB）：适用于数据结构灵活、读多写少的服务。产品目录服务（产品属性差异大）、用户画像服务（半结构化数据）常选择文档数据库。


键值存储（Redis、Memcached）：适用于高频读取、低延迟要求的缓存和会话管理场景。


搜索引擎（Elasticsearch、OpenSearch）：适用于全文搜索和复杂聚合分析场景。搜索服务、日志分析服务的主存储。


时序数据库（InfluxDB、TimescaleDB）：适用于时间序列数据。监控指标、IoT 数据、用户行为事件的存储。

跨服务查询模式
当一个业务操作需要来自多个服务的数据时，不能通过数据库 JOIN 完成，需要在应用层实现数据组合。


API 组合模式（API Composition）：由一个组合服务（Composer）调用多个下游服务的 API，在内存中组合数据后返回给调用方。适用于查询场景——读取操作不涉及事务一致性要求。


interface OrderDetail {
  order: Order;
  customer: Customer;
  items: (OrderItem & { product: Product })[];
  payment: Payment;
}

const getOrderDetail = async (orderId: string): Promise<OrderDetail> => {
  const order = await orderService.getOrder(orderId);

  const [customer, items, payment] = await Promise.all([
    customerService.getCustomer(order.customerId),
    Promise.all(
      order.items.map(async (item) => ({
        ...item,
        product: await productService.getProduct(item.productId),
      })),
    ),
    paymentService.getPayment(order.paymentId),
  ]);

  return { order, customer, items, payment };
};
CQRS 模式（Command Query Responsibility Segregation）：将写操作和读操作分离到不同的模型和存储中。写端使用规范化的数据模型保证业务规则和数据完整性，读端维护一个预聚合的非规范化视图专门服务查询需求。读端视图通过消费写端产生的事件来保持同步。

分布式事务管理
跨服务的业务操作（如"创建订单 → 扣减库存 → 扣款"）需要保证原子性——要么全部成功，要么全部回滚。在每服务一数据库模式下，传统的 ACID 事务不再适用，需要使用 Saga 模式实现分布式事务。


编排式 Saga（Orchestration Saga）：由一个中央协调器（Saga Orchestrator）负责按顺序调用各服务的操作，并在失败时触发补偿操作。协调器维护 Saga 的状态机，清晰地定义了正向操作和补偿操作的执行顺序。


编舞式 Saga（Choreography Saga）：没有中央协调器，各服务通过事件驱动的方式协作。服务完成本地事务后发布事件，下一个服务监听事件并执行自己的操作。编舞式 Saga 避免了单点协调器，但链路长时难以跟踪和调试。


Saga 的补偿设计原则：每个正向操作都必须有对应的补偿操作。补偿操作必须是幂等的（可安全重试）。补偿操作的执行顺序与正向操作相反。某些操作（如发送邮件）无法真正"撤销"，需要设计语义补偿（如发送取消通知）。


Schema 演进与数据迁移
每服务一数据库模式下，Schema 变更的影响被限制在单个服务内部，但仍需要安全的演进策略来避免部署中断。


向后兼容变更（安全变更）：添加新列（带默认值）、添加新表、添加新索引。这些变更可以先应用到数据库，再部署新版本应用代码。


向后不兼容变更（破坏性变更）：删除列、重命名列、修改数据类型。这些变更需要多步迁移策略：第一步部署同时读写新旧列的代码版本，第二步迁移数据从旧列到新列，第三步部署只读写新列的代码版本，最后删除旧列。


数据迁移工具：Flyway 和 Liquibase 是最流行的数据库迁移工具。它们将 Schema 变更定义为有序的迁移脚本，自动跟踪已执行的迁移，确保所有环境的数据库 Schema 一致。将迁移脚本纳入 CI/CD 流水线，实现 Schema 变更的自动化和可审计。


小结
    

  • 每服务一数据库是微服务架构数据管理的核心原则，保证服务松耦合和独立部署，但引入了跨服务查询和分布式事务的复杂性
    • 

  • 多语言持久化允许每个服务选择最适合的数据库技术，关系型适合事务、文档型适合灵活Schema、搜索引擎适合全文检索
    • 

  • API 组合模式适用于简单的跨服务查询，CQRS 读视图适用于复杂查询和高频读取场景
    • 

  • Saga 模式（编排式/编舞式）替代 ACID 事务实现跨服务的最终一致性，补偿操作必须幂等
    • 

  • Schema 向后不兼容变更需要多步迁移策略，数据库迁移工具（Flyway/Liquibase）确保变更的自动化和可审计
    • 

  • 在团队规模较小或服务边界不清晰时，可以从共享数据库起步，随着架构成熟逐步拆分
