Saga 分布式事务模式

核心概念

Saga 模式是微服务架构中管理跨服务业务事务的核心方案。传统单体应用使用数据库的 ACID 事务保证数据一致性，但在微服务架构中，每个服务拥有独立的数据库，无法使用跨数据库的分布式事务（2PC）来保证一致性。Saga 将一个跨服务的业务事务分解为一系列本地事务，每个本地事务更新自己服务的数据并发布事件触发下一步，当某个步骤失败时，通过执行补偿事务（Compensating Transaction）回滚之前已完成的步骤。

编排式 Saga
编排式 Saga（Choreography-based Saga）通过事件驱动的方式协调参与者，没有集中的协调器。每个服务完成本地事务后发布领域事件，其他服务订阅感兴趣的事件并执行自己的本地事务。这种去中心化的协调方式适合参与者较少（3-5个）的简单业务流程。


编排式 Saga 的优势是去中心化、服务间松耦合、易于添加新的参与者。劣势是业务流程分散在各个服务中，难以全局追踪事务状态，当参与者增多时事件链路变得复杂难以理解和调试。


事件设计是编排式 Saga 的关键。事件应该包含足够的上下文信息，使订阅者无需回调发布者就能完成自己的处理。事件命名遵循"过去式动词"约定（如 OrderCreated、PaymentCompleted），表达已经发生的事实。事件 Schema 的版本管理通过 Schema Registry 实现，确保生产者和消费者之间的兼容性。


补偿事务需要特别设计。补偿操作不是简单的"撤销"，而是一个独立的业务操作。例如"退还库存"不是删除库存扣减记录，而是创建一条新的库存补充记录。补偿事务必须满足幂等性要求，因为在网络不稳定的情况下，同一补偿操作可能被重复执行。


协调式 Saga
协调式 Saga（Orchestration-based Saga）引入一个 Saga 协调器（Orchestrator），由协调器按照预定义的流程图依次调用各参与服务的命令。协调器维护 Saga 的状态机，记录当前执行到哪一步、哪些步骤已完成、是否需要执行补偿。


interface SagaStep<T> {
  execute(context: T): Promise<void>;
  compensate(context: T): Promise<void>;
}

class CreateOrderSaga {
  private steps: SagaStep<OrderContext>[] = [
    {
      execute: (ctx) => this.orderService.createOrder(ctx),
      compensate: (ctx) => this.orderService.cancelOrder(ctx),
    },
    {
      execute: (ctx) => this.inventoryService.reserveStock(ctx),
      compensate: (ctx) => this.inventoryService.releaseStock(ctx),
    },
    {
      execute: (ctx) => this.paymentService.processPayment(ctx),
      compensate: (ctx) => this.paymentService.refundPayment(ctx),
    },
  ];

  async run(context: OrderContext): Promise<void> {
    const completedSteps: number[] = [];
    for (let i = 0; i < this.steps.length; i++) {
      try {
        await this.steps[i].execute(context);
        completedSteps.push(i);
      } catch (error) {
        for (const stepIndex of completedSteps.reverse()) {
          await this.steps[stepIndex].compensate(context);
        }
        throw error;
      }
    }
  }
}
协调式 Saga 的优势是业务流程集中定义、状态追踪清晰、易于实现复杂的分支逻辑和超时处理。劣势是协调器可能成为单点故障和性能瓶颈，且引入了额外的服务依赖。


状态机是协调器的核心，定义了 Saga 在正常流程和补偿流程中的所有合法状态转换。状态持久化到数据库中，确保协调器重启后可以从断点继续执行。Temporal 和 Cadence 等工作流引擎提供了开箱即用的 Saga 协调器实现，内置了状态持久化、超时处理和重试机制。

隔离性与语义锁
Saga 模式天然缺少 ACID 事务的隔离性（Isolation），在 Saga 执行期间，中间状态对其他事务可见。这可能导致脏读（读取到未最终提交的中间状态）和不可重复读（同一数据在 Saga 执行期间被其他事务修改）等异常。


语义锁（Semantic Lock）是解决隔离性问题的常用策略。在订单 Saga 中，创建订单时将状态设为"PENDING"而非"CONFIRMED"，告诉其他事务该订单正在处理中。只有 Saga 的最后一步成功后，才将状态更新为"CONFIRMED"。其他查询订单的事务看到"PENDING"状态时可以选择等待或按业务规则处理。


交换律（Commutative Updates）设计使得并发的 Saga 操作无论执行顺序如何都能产生正确结果。例如余额扣减操作设计为"扣减指定金额"而非"设置为指定余额"，两个并发的扣减操作无论先后都能得到正确的最终余额。


重新读取值策略在补偿前重新读取数据的最新值，确保补偿操作基于最新状态执行。如果重新读取发现数据已被其他事务修改到不可补偿的状态，则触发人工介入流程。


小结
    

  • Saga 将跨服务事务分解为本地事务 + 补偿事务，实现最终一致性
    • 

  • 编排式 Saga 适合简单流程（3-5 步），协调式 Saga 适合复杂流程（5+ 步）
    • 

  • 补偿事务是独立的业务操作而非简单撤销，必须满足幂等性
    • 

  • Saga 缺少 ACID 隔离性，通过语义锁、交换律和重新读取等策略缓解
    • 

  • Temporal/Cadence 等工作流引擎提供开箱即用的 Saga 协调器
    • 

  • 事件设计应包含充足上下文，Schema 版本通过 Registry 管理兼容性
