网络策略

核心概念

Kubernetes NetworkPolicy 是集群内的网络安全机制，控制 Pod 之间以及 Pod 与外部之间的网络通信。默认情况下 Kubernetes 集群中所有 Pod 可以自由通信，NetworkPolicy 允许管理员定义细粒度的入站（Ingress）和出站（Egress）规则，实现微分段网络安全。

默认拒绝策略
零信任网络安全的第一步是实施默认拒绝策略。通过创建一个空规则的 NetworkPolicy 选中所有 Pod，可以拒绝所有未明确允许的流量。


默认拒绝所有入站流量：创建 NetworkPolicy，podSelector 设为空（匹配 Namespace 内所有 Pod），policyTypes 包含 Ingress，ingress 规则为空数组。这意味着除非有其他 NetworkPolicy 明确允许，否则所有入站流量被拒绝。


默认拒绝所有出站流量：类似地，policyTypes 包含 Egress，egress 规则为空数组。注意拒绝出站流量会影响 DNS 解析——需要额外允许到 kube-system 命名空间 CoreDNS 的 UDP 53 端口出站流量。


默认拒绝策略应作为每个新 Namespace 的标准配置。然后为每个服务创建明确的允许规则，形成白名单模式。这种方式确保新部署的服务默认安全，只有经过审核的通信路径被允许。


多条 NetworkPolicy 的效果是累加的——如果任意一条策略允许某个流量，该流量就被允许。策略之间是逻辑或（OR）关系，不存在优先级冲突。


常见网络策略模式
前端到后端隔离：允许 Web Pod 访问 API Pod 的 8080 端口，允许 API Pod 访问 Database Pod 的 5432 端口。其他所有 Pod 间通信被拒绝。


命名空间隔离：只允许同一 Namespace 内的 Pod 互相通信，拒绝跨 Namespace 的访问。通过 namespaceSelector 匹配当前 Namespace 的标签实现。


系统服务访问：允许所有 Pod 访问 kube-system 命名空间中的 CoreDNS（UDP 53），允许 Prometheus（kube-monitoring 命名空间）抓取所有 Pod 的 metrics 端口。


外部访问控制：通过 ipBlock 限制 Pod 可以访问的外部 IP 范围。例如只允许访问公司 VPN 的 CIDR，或者拒绝访问互联网（0.0.0.0/0）。except 字段可以排除特定子网。


CNI 插件与网络策略执行
NetworkPolicy 是 Kubernetes 的 API 定义，实际的策略执行依赖 CNI（Container Network Interface）插件。不同的 CNI 插件对 NetworkPolicy 的支持程度和实现方式不同。


Calico 是最广泛使用的支持 NetworkPolicy 的 CNI 插件。它通过 iptables 或 eBPF 实现策略执行。Calico 还提供了扩展的 GlobalNetworkPolicy 和 NetworkSet CRD，支持集群级策略和 IP 地址集合的复用。


Cilium 基于 eBPF 实现高性能的网络策略。除了标准 NetworkPolicy，Cilium 提供了 CiliumNetworkPolicy CRD，支持 L7 层策略——基于 HTTP 方法、路径和 Header 的细粒度控制。例如允许 GET /api/products 但拒绝 DELETE /api/products。


Flannel 不支持 NetworkPolicy。如果集群使用 Flannel 作为 CNI，创建 NetworkPolicy 资源不会有任何效果。需要使用 Calico 的策略引擎覆盖（Flannel + Calico 组合）或迁移到支持策略的 CNI。

网络策略审计与可视化
大规模集群中 NetworkPolicy 的管理需要可视化和审计工具。


网络策略编辑器（如 Cilium Network Policy Editor）提供了图形化界面设计和验证 NetworkPolicy。np-guard 自动分析集群流量并推荐最小权限的 NetworkPolicy。


策略审计模式在执行策略前记录被拒绝的流量日志，帮助识别策略配置中的遗漏。Cilium 的 Policy Audit Mode 记录所有本会被拒绝的流量，在确认无误后切换为执行模式。


Hubble（Cilium 的可观测性平台）提供了实时的网络流量可视化。通过 Hubble UI 可以看到 Pod 间的通信关系图、被策略拒绝的流量和网络延迟信息。这对排查网络连通性问题和验证策略正确性极为有用。


在大规模集群中推进 NetworkPolicy 部署应采用渐进式策略。第一阶段在审计模式下部署策略，收集流量数据并分析策略影响。第二阶段对非关键 Namespace 启用策略执行，验证白名单的完整性。第三阶段逐步扩展到所有 Namespace，并将策略管理集成到 CI/CD 流水线中——每个应用部署自动携带对应的 NetworkPolicy。

小结
    

  • NetworkPolicy 是 Kubernetes 内置的网络安全机制，控制 Pod 间的入站和出站流量
    • 

  • 默认拒绝策略 + 白名单模式是零信任网络安全的基础，应作为每个 Namespace 的标准配置
    • 

  • 常见模式包括三层隔离、命名空间隔离、系统服务访问和外部 IP 控制
    • 

  • CNI 插件决定了策略执行能力，Calico 和 Cilium 是支持 NetworkPolicy 的主流选择
    • 

  • Cilium 的 L7 策略和 eBPF 实现提供了超越标准 NetworkPolicy 的细粒度控制
    • 

  • 策略审计模式和 Hubble 可视化帮助安全地推进网络策略部署
    •
