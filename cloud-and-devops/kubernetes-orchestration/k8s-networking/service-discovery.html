Service 发现与 DNS

核心概念

Service 发现是微服务架构的基础能力——在动态环境中，服务实例不断创建和销毁，消费者需要可靠的机制找到可用的服务端点。Kubernetes 通过 Service 资源和 CoreDNS 提供了内置的服务发现机制，使 Pod 可以通过稳定的 DNS 名称和虚拟 IP 访问服务。

CoreDNS 与集群 DNS
CoreDNS 是 Kubernetes 集群的默认 DNS 服务，以 Deployment 形式运行在 kube-system 命名空间中。每个 Pod 的 /etc/resolv.conf 自动配置为指向 CoreDNS 的 ClusterIP。


Service 的完整 DNS 名称格式为 {service}.{namespace}.svc.cluster.local。同一 Namespace 内的 Pod 可以直接使用 Service 名称（如 api-service），跨 Namespace 使用 {service}.{namespace} 格式。DNS 搜索域（search domain）自动补全后缀。


Headless Service（clusterIP: None）不分配虚拟 IP，DNS 直接返回后端 Pod 的 IP 地址。StatefulSet 配合 Headless Service 为每个 Pod 创建独立的 DNS A 记录（{pod}.{service}.{namespace}.svc.cluster.local），实现有状态应用的稳定网络标识。


ExternalName Service 创建 CNAME DNS 记录指向外部域名。这适合将集群外的服务（如 RDS 数据库）抽象为 Kubernetes Service，使集群内服务通过统一的 Service 名称访问外部依赖，便于未来迁移。


CoreDNS 的 Corefile 配置支持自定义 DNS 行为。kubernetes 插件处理集群内 DNS 查询，forward 插件将外部域名转发到上游 DNS 服务器。cache 插件缓存 DNS 响应减少查询延迟。


CoreDNS 的性能调优对大规模集群至关重要。默认的 CoreDNS 副本数（2）在千节点以上集群中可能成为瓶颈。建议根据集群规模调整副本数——每 1000 个 Service 约需 1 个 CoreDNS 副本。autopath 插件减少 DNS 查询的搜索域迭代次数，从平均 5 次查询降低到 1 次。bufsize 参数避免 DNS 响应因超过 UDP 包限制而回退到 TCP。

NodeLocal DNSCache 在每个节点上运行本地 DNS 缓存。DNS 查询先命中本地缓存，缓存未命中再转发到 CoreDNS。这减少了跨节点的 DNS 查询延迟、CoreDNS 的负载和 conntrack 表的压力。对大规模集群和 DNS 密集型应用，启用 NodeLocal DNSCache 可以显著改善性能。


EndpointSlice 与服务端点
EndpointSlice 是 Kubernetes 1.21+ 的服务端点管理机制，替代了传统的 Endpoints 资源。EndpointSlice 将 Service 的后端端点分片存储，解决了大规模 Service（数千个端点）的性能问题。


EndpointSlice 控制器监听 Pod 和 Service 的变更，自动维护 EndpointSlice 中的端点列表。每个 EndpointSlice 默认包含最多 100 个端点。当 Pod 变为 Ready 时被添加到 EndpointSlice，变为 NotReady 时被移除。


topology-aware routing（拓扑感知路由）通过 EndpointSlice 的拓扑信息优先将流量路由到同一可用区的 Pod。这减少了跨 AZ 的网络传输成本和延迟。通过设置 Service 的 service.kubernetes.io/topology-mode: Auto annotation 启用。


服务发现模式与实践
环境变量模式是 Kubernetes 最早的服务发现方式。kubelet 在 Pod 启动时注入所有已存在 Service 的环境变量（如 {SERVICE_NAME}_SERVICE_HOST 和 {SERVICE_NAME}_SERVICE_PORT）。这种方式的限制是 Pod 启动后创建的 Service 不会被注入。


DNS 模式是推荐的服务发现方式。Pod 通过 DNS 名称解析获取 Service IP，即使 Service 在 Pod 之后创建也能正常发现。DNS 模式与语言和框架无关，是最通用的服务发现机制。


对于需要更高级服务发现能力的场景（如服务健康权重、服务元数据查询），可以使用 Consul 或 etcd 等外部服务注册中心。Consul Connect 提供了服务网格级别的服务发现和安全通信。

小结
    

  • Kubernetes 通过 Service 和 CoreDNS 提供内置服务发现，DNS 是推荐的发现方式
    • 

  • Service 的四种类型（ClusterIP/NodePort/LoadBalancer/Headless）满足不同访问需求
    • 

  • CoreDNS 处理集群内 DNS 查询，NodeLocal DNSCache 优化大规模集群性能
    • 

  • EndpointSlice 分片存储服务端点，拓扑感知路由优化跨 AZ 流量
    • 

  • Headless Service 配合 StatefulSet 提供有状态应用的稳定 DNS 标识
    • 

  • ExternalName Service 将外部服务抽象为集群内 Service，便于统一管理
    •
