GitOps 与持续部署

核心概念

GitOps 是一种以 Git 仓库作为声明式基础设施和应用配置的唯一事实来源（Single Source of Truth）的运维模式。所有变更通过 Git 提交和合并请求完成，自动化工具持续将 Git 中的期望状态同步到目标集群。GitOps 为 Kubernetes 部署带来了版本控制、审计追踪和自动化恢复能力。

ArgoCD 架构与实践
ArgoCD 是最流行的 Kubernetes GitOps 工具。它运行在目标集群中，持续监控 Git 仓库中的配置，自动检测和同步配置漂移。


ArgoCD 的核心资源是 Application，它定义了 Git 仓库地址、目标路径、目标集群和同步策略。ArgoCD 支持 Helm Chart、Kustomize、纯 YAML 和 Jsonnet 等多种配置格式。


同步策略（Sync Policy）控制 ArgoCD 的自动化程度。手动同步要求运维人员确认后才执行部署。自动同步（Auto Sync）在检测到 Git 变更后自动部署。自修复（Self Heal）在检测到集群状态偏离 Git 定义时自动修复漂移。


ArgoCD 的同步波次（Sync Waves）和资源钩子（Resource Hooks）控制资源的部署顺序。Sync Wave 通过 annotation 指定资源的部署顺序号，低号先部署。PreSync Hook 在正式同步前执行（如数据库迁移），PostSync Hook 在同步后执行（如通知发送）。


多集群管理是 ArgoCD 的重要能力。单个 ArgoCD 实例可以管理多个 Kubernetes 集群。ApplicationSet 控制器支持模板化的应用定义，自动在多个集群或环境中创建和管理 Application。


Flux CD 与持续交付
Flux 是另一个主流的 GitOps 工具集，由 Weaveworks 创建并捐献给 CNCF。Flux v2 基于 GitOps Toolkit 构建，将功能分解为多个专门的控制器。


Source Controller 管理 Git 仓库、Helm 仓库和 OCI 仓库的拉取和缓存。Kustomize Controller 处理 Kustomization 资源的渲染和应用。Helm Controller 管理 HelmRelease 资源的安装和升级。Notification Controller 处理事件通知和外部触发。


Flux 的多租户模型通过 Namespace 隔离实现。每个团队在自己的 Namespace 中定义 GitRepository 和 Kustomization 资源，Flux 确保团队只能管理自己的资源。RBAC 和 ServiceAccount 提供额外的权限控制。


镜像自动更新（Image Automation）是 Flux 的特色功能。Image Repository Controller 监控容器镜像仓库的新标签，Image Policy 定义镜像选择策略（如最新的 semver 版本），Image Update Automation 自动更新 Git 仓库中的镜像标签并提交。

GitOps 仓库结构设计
GitOps 仓库的组织结构直接影响团队协作效率和部署灵活性。常见的结构模式包括单仓库和多仓库。


单仓库模式将所有环境和应用的配置放在一个 Git 仓库中。通过目录结构区分环境（base/overlays/staging、overlays/production）。优点是统一管理、原子性变更和简化权限。缺点是大型组织中仓库膨胀和变更频繁。


多仓库模式将基础设施配置和应用配置分离，或按团队/环境拆分仓库。应用团队管理自己的配置仓库，平台团队管理基础设施仓库。优点是权限隔离和独立部署节奏。缺点是跨仓库变更的协调复杂。


环境晋级（Environment Promotion）是 GitOps 的关键实践。变更先部署到 staging 环境验证，确认后通过 PR 合并到 production 分支或目录。自动化的 Promotion Pipeline 可以基于测试结果自动触发晋级。


GitOps 安全与合规
GitOps 模型天然具备安全和审计优势，但也引入了新的安全考量。


密钥管理是 GitOps 的核心挑战——密码和证书等敏感数据不应明文存储在 Git 仓库中。Sealed Secrets 使用非对称加密，将 Secret 加密后可以安全存入 Git，只有集群中的控制器能解密。SOPS（Secrets OPerationS）支持使用 AWS KMS、GCP KMS 或 Age 加密 YAML 文件中的敏感值。External Secrets Operator 从外部密钥管理系统（如 AWS Secrets Manager、HashiCorp Vault）同步密钥到 Kubernetes Secret。


GitOps 的审计追踪依赖 Git 的提交历史。每次配置变更都有提交者身份、时间戳和变更内容的完整记录。结合 Git 分支保护规则和 PR 审核流程，可以实现变更的四眼原则（至少两人审核）。


漂移检测和自修复确保集群状态始终与 Git 定义一致。如果有人通过 kubectl 直接修改了集群资源，GitOps 控制器会检测到漂移并自动将状态恢复到 Git 定义。这消除了配置漂移的风险，确保了声明式管理的可信性。


GitOps 的 RBAC 模型将集群写权限集中在 GitOps 控制器上。开发者和运维人员不需要直接的集群写权限，所有变更通过 Git 提交完成。这大幅减少了需要管理的集群权限，降低了安全风险。

小结
    

  • GitOps 以 Git 为唯一事实来源，通过拉取模式实现声明式部署和漂移自修复
    • 

  • ArgoCD 提供丰富的 Web UI 和 ApplicationSet 多集群管理，是最流行的 GitOps 工具
    • 

  • Flux 基于控制器分解架构，原生支持镜像自动更新和多租户隔离
    • 

  • 仓库结构设计（单仓库/多仓库）影响协作效率，需根据团队规模和组织结构选择
    • 

  • 密钥管理通过 Sealed Secrets、SOPS 或 External Secrets Operator 解决 Git 中存储敏感数据的问题
    • 

  • 环境晋级通过 PR 合并实现变更的渐进式部署和验证
    • 

  • GitOps 为 Kubernetes 部署提供了版本控制、审计追踪和自动恢复的运维最佳实践
    •
