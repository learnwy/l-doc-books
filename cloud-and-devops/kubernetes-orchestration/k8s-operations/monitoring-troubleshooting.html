集群监控与故障排查

核心概念

Kubernetes 集群监控覆盖基础设施层（节点、网络）、平台层（控制平面、工作负载）和应用层（业务指标、日志）。完善的监控体系是保障集群稳定运行和快速定位问题的基础。Prometheus + Grafana 是 Kubernetes 生态中最广泛使用的监控技术栈。

Prometheus 监控体系
Prometheus 是 CNCF 的核心监控项目，采用拉取模式（Pull）从目标端点采集时序数据。Prometheus Operator（kube-prometheus-stack）是在 Kubernetes 中部署 Prometheus 的标准方式，它通过 CRD 简化了监控配置管理。


ServiceMonitor 和 PodMonitor 是 Prometheus Operator 的核心 CRD。ServiceMonitor 定义了通过 Service 发现监控目标的规则，PodMonitor 直接基于 Pod 标签发现目标。Prometheus Operator 自动将 Monitor 配置转换为 Prometheus 的 scrape 配置。


PrometheusRule CRD 定义告警规则。告警规则基于 PromQL 表达式评估条件，触发后发送到 AlertManager。AlertManager 负责告警的分组、去重、抑制和路由——将告警发送到 Slack、PagerDuty、邮件等通知渠道。


关键的 Kubernetes 监控指标包括：kube_pod_container_status_restarts_total（Pod 重启次数）、kube_pod_status_phase（Pod 状态分布）、kube_deployment_status_replicas_unavailable（不可用副本数）、apiserver_request_total（API 请求总量）和 etcd_server_leader_changes_seen_total（etcd Leader 切换次数）。


Grafana 提供可视化仪表盘。kube-prometheus-stack 预置了数十个开箱即用的仪表盘，覆盖节点、Pod、Namespace、控制平面等多个维度。自定义仪表盘通过 Grafana Dashboard JSON 模型定义，可以存储在 ConfigMap 中通过 GitOps 管理。


日志管理
Kubernetes 日志管理采用集中式采集和存储架构。容器日志写入 stdout/stderr，由容器运行时捕获并存储在节点文件系统上。日志采集器（DaemonSet 部署）从每个节点收集日志并发送到集中存储。


EFK/ELK 栈（Elasticsearch + Fluentd/Fluent Bit + Kibana）是传统的日志方案。Fluent Bit 作为轻量级日志采集器运行在每个节点上，解析容器日志并添加 Kubernetes 元数据（Pod 名称、Namespace、标签），然后发送到 Elasticsearch。Kibana 提供日志搜索和可视化。


Loki 是 Grafana Labs 推出的日志聚合系统，与 Prometheus 的理念一致——只索引标签不索引日志内容，大幅降低了存储和运营成本。Promtail 作为日志采集器，Loki 作为后端存储，Grafana 统一展示指标和日志。


故障排查方法论
Kubernetes 故障排查遵循自顶向下的方法：先确认症状层次（应用、Pod、节点、集群），再逐层定位根因。


Pod 故障是最常见的排查对象。kubectl describe pod 查看事件和状态详情。常见 Pod 状态包括：CrashLoopBackOff（容器反复崩溃重启）、ImagePullBackOff（镜像拉取失败）、Pending（等待调度）和 OOMKilled（内存不足被杀）。kubectl logs 查看容器日志，--previous 参数查看上次崩溃的日志。


调度失败排查通过 kubectl describe pod 查看 Events 中的调度失败原因。常见原因包括资源不足（Insufficient cpu/memory）、Taint 不容忍、亲和性不满足和 PVC 绑定失败。kubectl get events --sort-by=.metadata.creationTimestamp 按时间排序查看集群事件。


网络问题排查使用 kubectl exec 进入 Pod 执行网络诊断。nslookup 检查 DNS 解析，curl/wget 检查 HTTP 连通性，traceroute 检查网络路径。kubectl port-forward 将 Pod 端口转发到本地便于直接调试。

可观测性最佳实践
可观测性（Observability）是监控的演进——不仅告诉你系统是否正常，还帮助你理解系统为什么异常。完整的可观测性包含指标（Metrics）、日志（Logs）和追踪（Traces）三大信号。


分布式追踪通过在请求链路中传播 Trace ID 实现跨服务调用的关联。OpenTelemetry 是 CNCF 的可观测性标准，提供了统一的 SDK 和 Collector 采集指标、日志和追踪数据。Jaeger 和 Tempo 是常用的分布式追踪后端。


SLO（Service Level Objective）驱动的监控将关注点从基础设施指标转向用户体验指标。通过定义 SLI（Service Level Indicator，如请求延迟 P99 < 200ms）和 SLO（如月度可用性 > 99.9%），建立 Error Budget 机制在可靠性和开发速度之间取得平衡。


告警设计原则：告警应该可操作（收到告警后有明确的处理步骤）、有意义（反映用户可感知的影响）和可收敛（同一问题不会产生大量重复告警）。使用 Recording Rules 预计算复杂的 PromQL 表达式，降低查询延迟和 Prometheus 负载。


成本管理是大规模监控的重要考量。Thanos 或 Cortex 提供 Prometheus 的长期存储和多集群聚合能力。通过采样策略和指标保留策略（低优先级指标短保留、高优先级指标长保留）控制存储成本。

小结
    

  • Kubernetes 监控覆盖节点、平台和应用三个层次，Prometheus + Grafana 是标准技术栈
    • 

  • Prometheus Operator 通过 CRD（ServiceMonitor、PrometheusRule）简化监控配置管理
    • 

  • 日志管理从 EFK 栈向 Loki 栈演进，Loki 通过仅索引标签大幅降低成本
    • 

  • 故障排查遵循自顶向下方法，kubectl describe、logs 和 exec 是核心排查工具
    • 

  • OpenTelemetry 统一了指标、日志和追踪的采集标准，是可观测性的发展方向
    • 

  • SLO 驱动的监控将关注点从基础设施转向用户体验，Error Budget 平衡可靠性和速度
    • 

  • 完善的可观测性体系是生产环境稳定运行和快速恢复的基础
