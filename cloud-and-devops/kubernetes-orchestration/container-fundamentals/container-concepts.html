容器核心概念

核心概念

容器是一种轻量级的虚拟化技术，通过操作系统级别的隔离将应用程序及其依赖打包为标准化的运行单元。与传统虚拟机不同，容器共享宿主机内核，无需运行独立的操作系统，因此具有更快的启动速度、更低的资源开销和更好的可移植性。

Linux 容器隔离原理
容器的隔离能力建立在 Linux 内核的两个核心机制之上：Namespace（命名空间）和 Cgroup（控制组）。


Namespace 提供了资源的逻辑隔离。PID Namespace 使每个容器拥有独立的进程树，容器内的 PID 1 进程是容器的 init 进程。Network Namespace 为每个容器提供独立的网络栈（IP 地址、路由表、端口空间）。Mount Namespace 隔离文件系统挂载点。UTS Namespace 允许每个容器有独立的主机名。User Namespace 映射容器内外的用户 ID，实现非特权容器。IPC Namespace 隔离进程间通信资源。


Cgroup 提供了资源的使用限制和计量。CPU Cgroup 限制容器的 CPU 使用份额和核心绑定。Memory Cgroup 限制容器的内存使用量，超限时触发 OOM Killer。Block I/O Cgroup 限制容器的磁盘读写速率。Network Cgroup 限制容器的网络带宽。


容器的文件系统基于 Union File System（联合文件系统）实现。OverlayFS 是最常用的实现，它将多个只读层（镜像层）和一个可写层（容器层）叠加为统一的文件系统视图。镜像层在多个容器之间共享，只有容器层是容器独占的，这种设计大大减少了存储占用。


容器运行时分为高级运行时和低级运行时。高级运行时（如 containerd、CRI-O）负责镜像管理、容器生命周期管理和网络配置。低级运行时（如 runc）直接调用 Linux 系统调用创建和管理容器进程。OCI（Open Container Initiative）标准定义了容器镜像格式和运行时规范，确保了不同运行时之间的互操作性。


容器镜像与分层存储
容器镜像是容器运行的蓝图，包含应用程序代码、运行时依赖、系统库和配置文件。镜像采用分层结构，每一层代表一次文件系统变更。


Dockerfile 是构建容器镜像的声明式配置文件。每条指令（FROM、RUN、COPY、ADD）创建一个新的镜像层。Docker 利用构建缓存加速重复构建——如果某一层及其之前的所有层都没有变化，该层直接使用缓存。


镜像优化是生产环境的重要实践。多阶段构建（Multi-stage Build）将编译环境和运行环境分离，最终镜像只包含运行必需的文件。选择精简的基础镜像（如 Alpine Linux、Distroless）可以将镜像大小从数百 MB 减少到十几 MB。精简镜像也减少了潜在的安全漏洞面。


镜像标签（Tag）用于标识镜像版本。latest 标签虽然方便但在生产环境中应避免使用，因为它的含义会随新镜像推送而变化。推荐使用语义化版本号（如 v1.2.3）或 Git 提交哈希作为标签，确保部署的可重复性。镜像摘要（Digest）基于内容哈希生成，是引用特定镜像版本的最可靠方式。


容器网络模型
容器网络是容器化架构中最复杂的部分之一。不同的网络模式提供了不同的隔离级别和性能特征。


Bridge 网络是 Docker 的默认网络模式。Docker 在宿主机上创建虚拟网桥（docker0），每个容器获得连接到网桥的虚拟网卡（veth pair）。同一网桥上的容器可以直接通信，外部访问通过 iptables NAT 规则转发。


Host 网络模式让容器直接使用宿主机的网络栈，没有网络隔离但也没有 NAT 开销。这种模式适合对网络性能极度敏感的应用，但端口可能冲突。


Overlay 网络跨多个 Docker 主机创建虚拟网络，使不同主机上的容器可以像在同一局域网中一样通信。Overlay 网络基于 VXLAN 隧道技术实现，是 Docker Swarm 和 Kubernetes 网络的基础。


容器网络接口（CNI）是 Kubernetes 的网络插件标准。不同的 CNI 插件（Calico、Cilium、Flannel、Weave）提供了不同的网络实现。Calico 基于 BGP 实现三层路由，性能优异。Cilium 基于 eBPF 实现网络策略和可观测性，是下一代容器网络的趋势。


容器编排基础
单机容器运行通过 Docker CLI 或 docker-compose 管理。docker-compose 使用 YAML 文件定义多容器应用的服务组成、网络和存储配置，适合开发环境和简单部署场景。


当应用扩展到多台机器时，需要容器编排平台来管理容器的调度、扩缩容、服务发现和故障恢复。Kubernetes 已成为容器编排的事实标准，在所有主流云平台上都有托管服务。


容器编排解决的核心问题包括：将容器调度到合适的节点（考虑资源需求、亲和性和反亲和性）、在容器故障时自动重启或重新调度、管理容器的网络连接和服务发现、处理滚动更新和回滚、管理配置和密钥、收集日志和监控指标。

小结
    

  • 容器基于 Linux Namespace 和 Cgroup 实现进程级隔离，比虚拟机更轻量但隔离级别较低
    • 

  • 容器镜像采用分层存储，多阶段构建和精简基础镜像是生产环境的必要优化
    • 

  • OCI 标准确保了容器镜像和运行时的互操作性，containerd 和 runc 是主流运行时
    • 

  • 容器网络从单机 Bridge 到跨主机 Overlay，CNI 标准统一了 Kubernetes 网络插件接口
    • 

  • 容器编排解决多机环境下的调度、扩缩容和故障恢复，Kubernetes 是事实标准
    • 

  • 容器技术的核心价值是标准化交付单元和环境一致性，是云原生架构的基石
