Pod 与 Deployment 实战

核心概念

Pod 是 Kubernetes 中最小的可调度单元，一个 Pod 包含一个或多个共享网络和存储的容器。Deployment 在 Pod 之上提供了声明式更新、滚动升级和自动回滚能力。掌握 Pod 与 Deployment 的配置和运维是 Kubernetes 实践的基础。

Pod 生命周期与探针
Pod 的生命周期从 Pending 开始，经过 Running，最终到达 Succeeded 或 Failed。理解各阶段的行为和转换条件是排查问题的关键。


Pending 阶段 Pod 已被 API Server 接受但尚未调度或镜像尚未拉取。常见停留原因包括资源不足、镜像拉取失败和 PVC 绑定等待。Running 阶段至少一个容器正在运行。Succeeded 状态表示所有容器正常退出（退出码 0）。Failed 表示至少一个容器异常退出。


Init Container 在主容器之前按顺序执行。每个 Init Container 必须成功完成后下一个才会启动。典型用途包括等待依赖服务就绪、执行数据库迁移、下载配置文件和设置文件权限。


Sidecar 容器与主容器共同运行在同一 Pod 中，提供辅助功能。常见 Sidecar 模式包括日志采集（Fluent Bit）、代理（Envoy）、监控（Prometheus exporter）和密钥注入（Vault Agent）。Kubernetes 1.28 引入了原生 Sidecar Container 支持，使用 restartPolicy: Always 标记。


三种探针控制 Pod 的健康状态。Liveness Probe 检测容器是否存活，失败时 kubelet 重启容器。Readiness Probe 检测容器是否就绪接收流量，失败时从 Service 端点移除。Startup Probe 用于慢启动应用，在成功前 Liveness Probe 不会生效。探针支持 HTTP、TCP 和 exec 三种检查方式。

探针配置中最常见的错误是 livenessProbe 与 readinessProbe 使用相同的端点和阈值。正确的做法是 readinessProbe 检查应用是否可以处理请求（包括依赖服务的连通性），而 livenessProbe 只检查进程是否存活（避免因下游服务故障导致级联重启）。


资源管理与 QoS
Kubernetes 通过 resources.requests 和 resources.limits 管理容器的 CPU 和内存分配。requests 定义容器的最低资源保证，调度器基于 requests 决定 Pod 放置。limits 定义容器的资源上限，超过 CPU 限制会被节流，超过内存限制会被 OOM Kill。


QoS（Quality of Service）等级决定了 Pod 在资源压力下的优先级。Guaranteed（requests = limits）优先级最高，不会被驱逐。Burstable（requests < limits 或只设置了部分）优先级中等。BestEffort（无 requests 和 limits）优先级最低，最先被驱逐。


CPU 以 millicores 计量（1000m = 1 核心），内存以字节计量（Mi、Gi）。CPU 是可压缩资源，超过限制会被节流但不会被杀。内存是不可压缩资源，超过限制会触发 OOM Kill。


Deployment 更新与回滚策略
Deployment 的滚动更新通过 maxUnavailable 和 maxSurge 两个参数控制。maxUnavailable 定义更新过程中不可用 Pod 的最大数量或百分比，maxSurge 定义超出期望副本数的最大 Pod 数量。两者共同决定了更新速度和可用性的平衡。


蓝绿部署可以通过两个 Deployment + Service 标签切换实现。创建新版本 Deployment，验证通过后修改 Service 的 selector 指向新版本，最后删除旧版本 Deployment。这种方式实现了瞬时切换，但需要双倍资源。


金丝雀发布通过调整新旧版本 Deployment 的副本数比例控制流量分配。例如旧版本 9 个副本、新版本 1 个副本实现 10% 的金丝雀流量。更精确的流量控制需要 Istio VirtualService 或 Argo Rollouts。


Argo Rollouts 是 Deployment 的增强替代方案，原生支持蓝绿部署、金丝雀发布和实验分析。Analysis 资源定义了自动化的金丝雀分析规则，基于 Prometheus 指标自动判断是否继续推进或回滚。


回滚操作是 Deployment 的重要安全机制。kubectl rollout undo 回退到上一个版本，kubectl rollout undo --to-revision=N 回退到指定版本。Deployment 默认保留最近 10 个 ReplicaSet 的历史版本（通过 revisionHistoryLimit 配置）。回滚操作本质上是将旧版 ReplicaSet 的模板恢复为当前活跃模板。kubectl rollout status 监控更新进度，kubectl rollout history 查看版本历史。

小结
    

  • Pod 是 K8s 最小调度单元，Init Container 和 Sidecar 提供了灵活的容器编排模式
    • 

  • 三种探针（Liveness/Readiness/Startup）控制 Pod 健康状态和流量管理
    • 

  • 资源 requests/limits 配置影响调度和 QoS 等级，Guaranteed 级别提供最高保障
    • 

  • Deployment 滚动更新通过 maxUnavailable/maxSurge 控制更新速度和可用性
    • 

  • 蓝绿部署和金丝雀发布是高级部署策略，Argo Rollouts 提供原生支持
    • 

  • 生产环境应为所有容器设置资源限制、健康检查和安全上下文
