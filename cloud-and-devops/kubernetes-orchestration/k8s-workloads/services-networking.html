Service 与网络策略

核心概念

Kubernetes Service 是将一组 Pod 暴露为网络服务的抽象。Pod 是临时性的，IP 地址随重建而变化，Service 提供了稳定的虚拟 IP（ClusterIP）和 DNS 名称作为访问入口。Service 通过标签选择器自动追踪后端 Pod 的变化，结合 kube-proxy 实现透明的负载均衡。

Service 类型深度解析
ClusterIP 是默认的 Service 类型。Kubernetes 从配置的 ClusterIP 范围中分配一个虚拟 IP，该 IP 只在集群内部可达。kube-proxy 在每个节点上创建 iptables/IPVS 规则，将发往 ClusterIP 的流量 DNAT 到后端 Pod。DNS 服务为 Service 创建 A 记录（{service}.{namespace}.svc.cluster.local），集群内 Pod 可以通过 Service 名称直接访问。


NodePort 在 ClusterIP 基础上，在每个节点的指定端口（默认范围 30000-32767）上监听。外部流量通过任意节点 IP 加 NodePort 访问 Service。NodePort 的限制包括端口范围有限、暴露了节点 IP 和无法自动实现节点间负载均衡。生产环境不推荐直接使用 NodePort。


LoadBalancer 类型触发 cloud-controller-manager 在云平台创建负载均衡器（如 AWS NLB/ALB、GCP Load Balancer）。云负载均衡器接收外部流量并分发到节点的 NodePort。这是生产环境暴露服务的标准方式。AWS Load Balancer Controller 提供了更精细的 ALB/NLB 配置能力。


externalTrafficPolicy 控制外部流量的路由方式。Cluster 模式（默认）将流量均匀分配到所有节点上的 Pod，可能产生跨节点转发。Local 模式只将流量路由到接收流量的节点上的 Pod，保留客户端源 IP 且避免跨节点跳转，但可能导致流量分配不均匀。


Ingress 与入口流量管理
Ingress 资源定义了 HTTP/HTTPS 层的路由规则，将外部请求路由到集群内的 Service。Ingress Controller 是 Ingress 的实现者，常见选择包括 nginx-ingress、Traefik、Envoy Gateway 和 AWS ALB Ingress Controller。


Ingress 支持基于主机名和路径的路由。同一 Ingress 可以定义多个规则，将不同域名或路径路由到不同的 Service。TLS 配置通过 Secret 引用 SSL 证书，cert-manager 可以自动化证书的申请和续期。


Gateway API 是 Ingress 的下一代替代方案，提供了更丰富和更规范化的流量管理能力。Gateway API 将关注点分离为 GatewayClass（基础设施提供者）、Gateway（集群入口点）和 HTTPRoute（路由规则），更好地支持多租户和多团队场景。


NetworkPolicy 网络隔离
NetworkPolicy 是 Kubernetes 的网络安全机制，控制 Pod 间的网络通信。默认情况下所有 Pod 可以自由通信，NetworkPolicy 允许管理员定义细粒度的入站和出站规则。


NetworkPolicy 通过 podSelector 选择目标 Pod，通过 ingress/egress 规则定义允许的流量。规则可以基于 Pod 标签（podSelector）、Namespace 标签（namespaceSelector）和 IP 地址段（ipBlock）。多条规则之间是逻辑或（OR）关系。


最佳安全实践是实施默认拒绝策略。创建一个空 ingress/egress 规则的 NetworkPolicy 选中 Namespace 内所有 Pod，就实现了默认拒绝所有入站/出站流量。然后为每个服务添加明确的允许规则。


NetworkPolicy 的实际执行依赖 CNI 插件。Calico、Cilium 和 Weave Net 支持 NetworkPolicy，Flannel 不支持。Cilium 通过 eBPF 实现高性能的网络策略执行，还支持 L7 层的细粒度策略（如允许特定 HTTP 方法和路径）。

服务发现与 DNS
CoreDNS 是 Kubernetes 集群的默认 DNS 服务，负责将 Service 名称解析为 ClusterIP。每个 Pod 的 /etc/resolv.conf 被配置为指向 CoreDNS，nameserver 为 CoreDNS 的 ClusterIP。


Service 的 DNS 记录格式为 {service}.{namespace}.svc.cluster.local。同 Namespace 内的 Pod 可以直接使用 Service 名称访问，跨 Namespace 需要使用 {service}.{namespace} 格式。


CoreDNS 的性能在大规模集群中可能成为瓶颈。NodeLocal DNSCache 在每个节点上运行 DNS 缓存 DaemonSet，减少跨节点的 DNS 查询延迟和 CoreDNS 的压力。对于延迟敏感的服务，建议启用 NodeLocal DNSCache。


外部 DNS（ExternalDNS）自动将 Service 和 Ingress 的外部域名同步到 DNS 服务商（如 Route 53、CloudFlare）。当创建带 annotation 的 Service 或 Ingress 时，ExternalDNS 自动创建对应的 DNS 记录。


小结
    

  • Service 为 Pod 提供稳定的访问入口，ClusterIP/NodePort/LoadBalancer/Headless 适用不同场景
    • 

  • LoadBalancer 是生产环境暴露服务的标准方式，externalTrafficPolicy 影响流量路由和源 IP 保留
    • 

  • Ingress 和 Gateway API 提供 HTTP/HTTPS 层的路由管理，Gateway API 是更现代的选择
    • 

  • NetworkPolicy 实现 Pod 间网络隔离，最佳实践是默认拒绝然后显式允许
    • 

  • CoreDNS 提供集群内 DNS 服务发现，NodeLocal DNSCache 优化大规模集群性能
    • 

  • ExternalDNS 自动同步外部域名，cert-manager 自动管理 TLS 证书
