Deployment 与 ReplicaSet

核心概念

Deployment 是 Kubernetes 中管理无状态应用的核心工作负载资源。它通过声明式配置定义应用的期望状态（镜像版本、副本数、资源配置等），由 Deployment 控制器自动创建和管理 ReplicaSet，ReplicaSet 再确保指定数量的 Pod 副本始终运行。这种级联管理机制实现了应用的声明式部署、滚动更新和自动回滚。

滚动更新策略
滚动更新（Rolling Update）是 Deployment 的默认更新策略。它逐步替换旧版本的 Pod 为新版本，在整个过程中保持服务可用。


更新过程中 Deployment 控制器创建新的 ReplicaSet，逐步增加新 ReplicaSet 的副本数并减少旧 ReplicaSet 的副本数。两个关键参数控制更新速度：maxUnavailable 定义更新过程中最多有多少 Pod 不可用（默认 25%），maxSurge 定义最多可以额外创建多少 Pod（默认 25%）。


对于 10 个副本的 Deployment，默认配置下更新过程中至少保持 8 个 Pod 可用（10 - 25% = 7.5，向上取整为 8），最多存在 13 个 Pod（10 + 25% = 12.5，向上取整为 13）。调大 maxSurge 可以加快更新速度，调小 maxUnavailable 可以提高更新期间的可用性。


更新触发条件是 Pod Template（.spec.template）的变化。修改镜像版本、环境变量或资源配置都会触发滚动更新。修改副本数（.spec.replicas）不会触发滚动更新，只是简单的扩缩容。


progressDeadlineSeconds 定义更新进度的超时时间（默认 600 秒）。如果在此时间内更新没有取得进展（新 Pod 无法就绪），Deployment 会报告更新进度超时条件。minReadySeconds 定义新 Pod 就绪后等待多久才被认为可用，用于延缓更新速度和验证新版本稳定性。


回滚与版本管理
Deployment 保留历史 ReplicaSet 用于回滚。revisionHistoryLimit（默认 10）控制保留的历史版本数量。每次更新创建一个新的 ReplicaSet，旧的 ReplicaSet 副本数缩容至 0 但不删除。


回滚操作通过 kubectl rollout undo 执行，将 Deployment 恢复到上一个或指定版本。回滚本质上是将目标 ReplicaSet 重新设为活跃，其过程与正常滚动更新相同。kubectl rollout history 查看部署历史，kubectl rollout status 监控更新进度。


金丝雀发布可以通过 Deployment 的 pause/resume 机制实现。触发更新后立即 pause，此时只有少量新版本 Pod 运行。验证新版本后 resume 继续完成更新，或 undo 回滚。更成熟的金丝雀策略应使用 Argo Rollouts 或 Flagger 等专门工具。


ReplicaSet 工作原理
ReplicaSet 的核心职责是确保任意时刻都有指定数量的 Pod 副本在运行。它通过标签选择器（Label Selector）识别自己管理的 Pod，并持续协调实际副本数与期望副本数。


当 Pod 因节点故障、OOM Kill 或其他原因被终止时，ReplicaSet 控制器检测到实际副本数低于期望值，立即创建新的 Pod 来补充。反之如果实际副本数超过期望值（如手动创建了匹配标签的 Pod），ReplicaSet 会删除多余的 Pod。


ReplicaSet 通过 ownerReferences 建立与 Pod 的所有权关系。每个被 ReplicaSet 管理的 Pod 在 metadata.ownerReferences 中引用其 ReplicaSet。当 ReplicaSet 被删除时，其拥有的 Pod 默认也会被级联删除（通过 Garbage Collector）。使用 --cascade=orphan 删除 ReplicaSet 可以保留 Pod。


Pod 模板哈希（pod-template-hash）标签是 Deployment 用来关联 ReplicaSet 和 Pod 的机制。每个 ReplicaSet 的名称包含 Pod 模板的哈希值，确保同一 Pod 模板只创建一个 ReplicaSet。


扩缩容与自动伸缩
手动扩缩容通过修改 Deployment 的 replicas 字段实现。kubectl scale 命令或直接编辑 Deployment 都可以。扩缩容是即时操作，不触发滚动更新。


HPA（Horizontal Pod Autoscaler）根据指标自动调整 Deployment 的副本数。默认支持 CPU 和内存利用率指标，通过 Metrics Server 采集。Custom Metrics API 支持使用 Prometheus 指标（如 QPS、延迟）触发扩缩容。


HPA 的关键参数包括：minReplicas（最小副本数）、maxReplicas（最大副本数）和 behavior（扩缩容速率控制）。behavior 可以分别配置扩容和缩容的策略，如限制每 60 秒最多增加 2 个 Pod，或缩容时使用 5 分钟的稳定窗口避免频繁波动。


VPA（Vertical Pod Autoscaler）自动调整 Pod 的 CPU 和内存 requests/limits。VPA 分析历史资源使用数据推荐合适的资源配置。updateMode 支持三种模式：Off（只推荐不修改）、Auto（自动调整，需要重建 Pod）和 Initial（只在 Pod 创建时设置）。HPA 和 VPA 不能同时基于相同指标使用。

小结
    

  • Deployment 通过级联管理 ReplicaSet 和 Pod 实现无状态应用的声明式管理
    • 

  • 滚动更新通过 maxUnavailable 和 maxSurge 参数控制更新速度和可用性
    • 

  • Deployment 保留历史 ReplicaSet 支持快速回滚，revisionHistoryLimit 控制保留数量
    • 

  • ReplicaSet 通过标签选择器和协调循环维护期望副本数
    • 

  • HPA 基于指标自动水平扩缩容，VPA 自动优化资源配置，KEDA 支持事件驱动扩缩
    • 

  • 生产环境应结合 PDB、健康检查和 HPA 构建弹性的应用部署
