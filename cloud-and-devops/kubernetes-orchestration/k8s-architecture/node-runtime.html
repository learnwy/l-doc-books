Kubernetes 节点与运行时

核心概念

Kubernetes 节点（Node）是集群中实际运行容器工作负载的工作机器。每个节点上运行着 kubelet、容器运行时和 kube-proxy 三个核心组件，它们协同工作将控制平面的调度决策转化为实际运行的容器。

kubelet 工作机制
kubelet 是每个节点上最重要的代理进程。它从 API Server 获取分配给本节点的 Pod 规格，驱动容器运行时创建和管理容器，并定期向 API Server 汇报节点和 Pod 的状态。


kubelet 通过 Watch 机制实时监听 API Server 上分配给本节点的 Pod。当发现新的 Pod 需要运行时，kubelet 将 Pod 规格转化为 CRI 调用，由容器运行时创建容器。当 Pod 被删除时，kubelet 执行优雅终止流程（Graceful Shutdown），先发送 SIGTERM 信号，等待 terminationGracePeriodSeconds 后发送 SIGKILL。


Pod 生命周期管理包括多个阶段。Init Containers 在主容器启动前按顺序执行，用于初始化操作（如数据库迁移、配置文件生成）。主容器启动后，PostStart Hook 被触发。容器运行期间，Liveness Probe 检查容器是否存活（失败则重启），Readiness Probe 检查容器是否就绪接收流量（失败则从 Service 端点移除），Startup Probe 用于慢启动容器的初始化检查。


kubelet 的资源管理功能包括：CPU Manager（为特定 Pod 分配独占 CPU 核心）、Memory Manager（NUMA 感知的内存分配）、Device Plugin（管理 GPU、FPGA 等硬件设备）和 Topology Manager（协调 CPU、内存和设备的拓扑亲和性）。


节点状态上报通过 NodeStatus 和 Lease 两种机制。NodeStatus 包含节点的条件（Ready、MemoryPressure、DiskPressure 等）、容量和可分配资源。Lease 对象提供轻量级的心跳机制，默认每 10 秒更新一次。控制平面在 40 秒未收到心跳后将节点标记为 NotReady。


容器运行时接口（CRI）
CRI 是 kubelet 与容器运行时之间的标准化接口，定义了镜像管理和容器管理两类 gRPC API。CRI 的引入使 Kubernetes 可以支持多种容器运行时，而不仅限于 Docker。


containerd 是当前最主流的 CRI 实现。它是从 Docker 项目中分离出的核心运行时，经过 CNCF 孵化为独立项目。containerd 通过 CRI 插件直接与 kubelet 通信，省去了 Docker Shim 的中间层，降低了延迟和资源开销。


CRI-O 是 Red Hat 主导的轻量级 CRI 实现，专为 Kubernetes 设计。它严格只实现 CRI 接口需要的功能，没有 containerd 的额外特性（如镜像分发、内容存储），因此更加轻量。CRI-O 是 OpenShift 的默认运行时。


镜像管理是 CRI 的重要职能。containerd 支持多种镜像格式（OCI、Docker v2）和镜像加速技术。Stargz Snapshotter 实现了镜像的按需加载——容器启动时只拉取实际需要的文件，而非整个镜像层，可将大镜像的启动时间从分钟级缩短到秒级。


Sandbox（PodSandbox）是 CRI 的核心概念。每个 Pod 对应一个 Sandbox，Sandbox 负责管理 Pod 级别的 Linux Namespace（网络、IPC、PID）。Pause 容器（infra container）是 Sandbox 的实现——它是 Pod 中第一个启动的容器，创建并持有 Pod 的网络命名空间，其他容器共享这个命名空间。


kube-proxy 与服务网络
kube-proxy 是每个节点上的网络代理，负责实现 Kubernetes Service 的网络转发规则。它监听 API Server 上 Service 和 Endpoint 的变更，在节点上配置相应的网络规则。


iptables 模式是最常用的代理模式。kube-proxy 为每个 Service 的 ClusterIP 和端口创建 iptables 规则链，将流量 DNAT 到后端 Pod 的 IP 和端口。iptables 规则的数量与 Service 和 Endpoint 的数量成正比，在大规模集群（数千 Service）中可能导致性能问题。


IPVS 模式使用 Linux IPVS（IP Virtual Server）模块实现负载均衡。IPVS 工作在内核态，使用哈希表存储规则，规则查找时间复杂度为 O(1)，性能不随规则数量增长而下降。IPVS 还支持更丰富的负载均衡算法（轮询、最少连接、源地址哈希等）。大规模集群应使用 IPVS 模式。


无 kube-proxy 模式是新兴趋势。Cilium 等 eBPF 网络方案可以完全替代 kube-proxy，直接在内核态实现 Service 负载均衡。eBPF 避免了 iptables/IPVS 的 conntrack 表开销，在高连接数场景下性能更优。

节点管理与运维
节点的生命周期管理包括加入集群、维护和退役。


节点加入集群通过 kubeadm join 或云平台的节点组（Node Group/Node Pool）自动完成。kubeadm 使用 Bootstrap Token 机制实现安全的节点加入流程。云平台的托管节点组自动处理节点的创建、加入和删除。


节点维护时使用 kubectl drain 命令优雅地驱逐节点上的 Pod。drain 先标记节点为不可调度（cordon），然后逐个驱逐 Pod，等待 Pod 在其他节点重新调度后完成。PodDisruptionBudget（PDB）确保在维护期间服务始终保持最小可用副本数。


节点自动扩缩容通过 Cluster Autoscaler 或 Karpenter 实现。Cluster Autoscaler 在 Pod 因资源不足无法调度时自动添加节点，在节点利用率低于阈值时自动移除节点。Karpenter 是 AWS 推出的更智能的节点管理器，它直接响应未调度的 Pod 需求，选择最合适的实例类型，无需预定义节点组。


小结
    

  • kubelet 是节点上的核心代理，负责 Pod 生命周期管理、资源管理和状态上报
    • 

  • CRI 标准化了 kubelet 与容器运行时的接口，containerd 和 CRI-O 是主流实现
    • 

  • Pause 容器作为 PodSandbox 持有 Pod 级别的网络命名空间
    • 

  • kube-proxy 通过 iptables/IPVS 实现 Service 网络代理，eBPF 方案正在替代传统 kube-proxy
    • 

  • 节点管理包括优雅驱逐（drain）、PDB 保护和自动扩缩容（Cluster Autoscaler/Karpenter）
    • 

  • 托管 Kubernetes 服务简化了节点管理，通过节点组和自动扩缩容实现声明式节点运维
    •
