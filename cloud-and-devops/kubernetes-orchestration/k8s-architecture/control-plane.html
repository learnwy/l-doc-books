Kubernetes 控制平面

核心概念

Kubernetes 控制平面（Control Plane）是集群的大脑，负责维护集群的期望状态、调度工作负载和响应集群事件。控制平面由多个核心组件组成，它们协同工作实现声明式 API、自动化调度和自愈能力。理解控制平面的架构和工作原理是深入掌握 Kubernetes 的基础。

kube-apiserver 深度解析
kube-apiserver 是 Kubernetes 控制平面的唯一入口，所有组件和用户都通过 API Server 与集群交互。它是一个无状态的 REST API 服务器，实际状态存储在 etcd 中。


API Server 的请求处理流程包含多个阶段：认证（Authentication）验证请求者身份、授权（Authorization）检查操作权限、准入控制（Admission Control）执行策略检查和修改、验证（Validation）检查资源格式合法性，最后持久化到 etcd。


认证机制支持多种方式：X.509 客户端证书、Bearer Token（ServiceAccount Token）、OpenID Connect（集成企业 SSO）和 Webhook Token Authentication（自定义认证）。生产环境通常组合使用多种认证方式。


授权模式中 RBAC 是最常用的。Role 定义在特定 Namespace 中的权限集合，ClusterRole 定义集群范围的权限。RoleBinding 和 ClusterRoleBinding 将角色绑定到用户、组或服务账户。


API Server 的性能直接影响集群响应速度。大规模集群中，API Server 需要处理来自数千个节点的 Kubelet 心跳、Watch 事件和 API 请求。优化措施包括：启用 API Priority and Fairness（APF）防止单个客户端占用过多资源、使用 WatchBookmark 减少 Watch 重建开销、配置适当的请求限流参数。


kube-scheduler 调度机制
kube-scheduler 负责将未调度的 Pod 分配到合适的节点上运行。调度决策基于 Pod 的资源需求、节点的可用资源、亲和性规则和约束条件。


调度过程分为两个阶段：过滤（Filtering/Predicates）和打分（Scoring/Priorities）。过滤阶段排除不满足 Pod 要求的节点，如资源不足、Taint 不匹配、NodeSelector 不满足等。打分阶段对过滤后的节点计算优先级分数，选择分数最高的节点。


亲和性（Affinity）和反亲和性（Anti-Affinity）控制 Pod 的分布策略。节点亲和性（nodeAffinity）指定 Pod 倾向或必须调度到哪些节点。Pod 亲和性（podAffinity）使相关 Pod 调度到同一区域以降低延迟。Pod 反亲和性（podAntiAffinity）使同一应用的 Pod 分散到不同节点或 AZ 以提高可用性。


Taint 和 Toleration 机制用于节点隔离。Taint 标记在节点上表示该节点有特殊属性（如 GPU 节点、专用节点），只有配置了对应 Toleration 的 Pod 才能调度到该节点。NoSchedule 阻止新 Pod 调度，NoExecute 还会驱逐已运行的不容忍 Pod。


拓扑分布约束（TopologySpreadConstraints）控制 Pod 在拓扑域（如 AZ、节点）间的均匀分布。maxSkew 参数定义了不同拓扑域间 Pod 数量的最大差值。这是实现跨 AZ 高可用的推荐方式。


控制器与协调循环
控制器是 Kubernetes 自动化的核心。每个控制器实现一个协调循环（Reconciliation Loop），持续观察集群的实际状态并采取动作使其趋向期望状态。


kube-controller-manager 运行着数十个内置控制器。Deployment 控制器管理 ReplicaSet 的创建和滚动更新。ReplicaSet 控制器确保指定数量的 Pod 副本运行。Node 控制器监控节点健康状态并在节点失联时标记为 NotReady。Endpoint 控制器维护 Service 和 Pod 之间的关联。


控制器的工作模式遵循 Level-Triggered（电平触发）而非 Edge-Triggered（边沿触发）设计。控制器不依赖事件的即时通知，而是定期检查全局状态并计算需要的操作。这种设计使控制器天然具备幂等性和容错能力——即使错过了某个事件，下次协调循环仍能纠正状态偏差。


cloud-controller-manager 将 Kubernetes 与云平台集成。它运行云特定的控制器：Node 控制器在节点不可达时检查云 API 确认节点是否已被删除；Route 控制器在云平台中配置路由规则；Service 控制器在创建 LoadBalancer 类型 Service 时调用云 API 创建负载均衡器。

控制平面高可用架构
生产环境的 Kubernetes 控制平面必须实现高可用，避免单点故障。托管 Kubernetes 服务（EKS、GKE、AKS）由云平台保障控制平面高可用，用户无需管理。自建集群需要自行配置。


API Server 天然支持多实例水平扩展，多个实例前置负载均衡器。etcd 使用 Raft 共识协议，需要奇数个节点（通常 3 或 5 个）保证在少数节点故障时仍能达成共识。Scheduler 和 Controller Manager 使用 Leader Election 机制，同一时间只有一个实例活跃执行任务，其他实例待命。


控制平面节点应分布在不同的可用区（AZ）。典型的三 AZ 部署中，每个 AZ 部署一个控制平面节点，任意一个 AZ 故障后集群仍能正常运行。etcd 的写入延迟受跨 AZ 网络延迟影响，应选择低延迟的 AZ 组合。


小结
    

  • Kubernetes 控制平面由 API Server、etcd、Scheduler 和 Controller Manager 组成，实现声明式管理和自动化
    • 

  • API Server 是集群唯一入口，请求经过认证、授权、准入控制和验证四个阶段
    • 

  • Scheduler 通过过滤-打分两阶段算法选择最优节点，亲和性和 Taint 机制实现精细化调度
    • 

  • 控制器通过协调循环持续将实际状态趋向期望状态，Level-Triggered 设计保证容错性
    • 

  • 控制平面高可用通过多实例 API Server、奇数节点 etcd 和 Leader Election 实现
    • 

  • 托管 Kubernetes 服务由云平台保障控制平面可用性，是生产环境的推荐选择
