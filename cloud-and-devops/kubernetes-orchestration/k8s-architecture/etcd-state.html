etcd 与集群状态管理

核心概念

etcd 是 Kubernetes 集群的唯一状态存储，保存了集群的所有配置数据、资源状态和元数据。它是一个分布式的、强一致性的键值存储系统，使用 Raft 共识协议保证数据在多个节点间的一致性。etcd 的可靠性和性能直接决定了 Kubernetes 集群的稳定性。

Raft 共识协议与数据一致性
Raft 是 etcd 的共识基础，保证在网络分区和节点故障时数据的一致性。Raft 将共识问题分解为 Leader 选举、日志复制和安全性三个子问题。


在一个 N 节点的 etcd 集群中，系统可以容忍 (N-1)/2 个节点故障。3 节点集群容忍 1 个故障，5 节点集群容忍 2 个故障。因此 etcd 集群必须是奇数节点——偶数节点不会提升容错能力但增加了一致性开销。


Leader 选举过程：每个节点初始为 Follower 状态。当 Follower 在选举超时内未收到 Leader 的心跳时，它转变为 Candidate 并发起选举。获得多数票的 Candidate 成为新的 Leader。Leader 负责接收所有写请求并将日志条目复制到 Follower。


写入流程是理解 etcd 一致性的关键。客户端的写请求发送到 Leader，Leader 将操作追加到本地日志并并行发送给所有 Follower。当多数节点确认接收后，Leader 提交该条目并响应客户端。这种多数确认机制确保了即使 Leader 故障，已提交的数据也不会丢失。


MVCC（多版本并发控制）是 etcd 的数据模型核心。每次写操作创建一个新版本（revision），旧版本不会被立即删除。Watch 机制利用 MVCC 从指定 revision 开始监听变更事件，这是 Kubernetes 控制器实现状态同步的基础。etcd 定期执行 Compaction 清理旧版本以控制存储大小。


etcd 性能优化
etcd 的性能瓶颈通常在磁盘 I/O 上。Raft 日志和数据库文件的写入是延迟的主要来源。生产环境中应将 etcd 部署在 SSD 存储上，低延迟磁盘可以将写入延迟从数十毫秒降到毫秒级。


etcd 的关键性能指标包括：WAL fsync 延迟（应低于 10ms）、Backend commit 延迟（应低于 25ms）、请求延迟 P99（应低于 100ms）和 Leader 选举频率（应极少发生）。Prometheus 可以通过 etcd 暴露的 /metrics 端点采集这些指标。


数据库大小是另一个关注点。etcd 建议数据库大小不超过 8GB。大型 Kubernetes 集群中，大量的 Event、ConfigMap 和 Secret 资源可能快速增长数据库。定期执行 Compaction 和 Defragmentation 维护数据库健康。设置 auto-compaction 自动清理历史版本。


网络延迟影响 Raft 共识的效率。etcd 节点间的网络延迟应低于 10ms，建议部署在同一数据中心的不同可用区。跨 Region 部署 etcd 会导致写入延迟显著增加，不推荐用于 Kubernetes。


etcd 备份与灾难恢复
etcd 数据是 Kubernetes 集群最关键的资产。丢失 etcd 数据等同于丢失整个集群状态，因此定期备份是必须的运维实践。


etcd 快照（Snapshot）是备份的标准方式。使用 etcdctl snapshot save 命令创建数据库的一致性快照。快照应自动化定期执行（如每小时），并将快照文件存储到安全的外部存储（如 S3）。恢复时使用 etcdctl snapshot restore 在新的 etcd 集群上恢复数据。


备份策略应考虑 RPO（恢复点目标）。如果使用每小时快照，最多丢失 1 小时的数据。对于关键环境，可以结合快照和 etcd 的增量备份来降低 RPO。


灾难恢复场景包括：单节点故障（Raft 自动恢复，无需干预）、少数节点故障（替换故障节点并加入集群）、多数节点故障（从快照恢复整个集群）和全部节点故障（从最新快照恢复到新集群）。

Kubernetes 中的 etcd 使用模式
Kubernetes 通过 API Server 间接使用 etcd。所有 Kubernetes 资源（Pod、Service、Deployment 等）以键值对形式存储在 etcd 中。键的格式为 /registry/{resource-type}/{namespace}/{name}。


Watch 机制是 Kubernetes 事件驱动架构的基础。API Server 对 etcd 建立 Watch 连接，当资源发生变更时 etcd 推送通知。API Server 再将这些变更事件传递给订阅的客户端（kubelet、控制器等）。这种级联 Watch 机制使整个集群能够快速响应状态变化。


etcd 加密保护敏感数据。Kubernetes 支持在 etcd 存储层对 Secret 等敏感资源进行加密（EncryptionConfiguration）。加密方式包括 AES-CBC、AES-GCM 和 KMS（集成外部密钥管理服务）。KMS 方式最为安全，因为加密密钥不存储在 Kubernetes 集群中。


大规模集群中可能需要拆分 etcd。一种方式是将 Event 资源存储到独立的 etcd 集群，因为 Event 数量大但重要性较低。通过 API Server 的 --etcd-servers-overrides 参数指定特定资源使用不同的 etcd 后端。


小结
    

  • etcd 是 Kubernetes 的唯一状态存储，使用 Raft 共识协议保证强一致性
    • 

  • 3 或 5 节点的奇数集群是标准部署，容忍少数节点故障
    • 

  • 磁盘 I/O 是 etcd 性能的关键瓶颈，SSD 和低延迟网络是必要条件
    • 

  • 定期快照备份是保护集群状态的必须实践，备份频率决定了 RPO
    • 

  • MVCC 和 Watch 机制是 Kubernetes 事件驱动架构的基础
    • 

  • 敏感数据应通过 EncryptionConfiguration 加密存储，KMS 集成提供最高安全级别
