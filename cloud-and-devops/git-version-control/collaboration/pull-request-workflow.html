Pull Request 工作流

PR 的核心价值

Pull Request（PR） 不仅是合并代码的机制，更是团队协作的核心载体。一个优秀的 PR 工作流能同时实现代码质量保障、知识共享和变更可追溯性。

PR 的作用 说明
Code Review 在合并前进行代码审查
CI 集成 自动运行测试和检查
文档化变更 PR 描述记录变更的动机和方案
知识传递 审查者了解代码库的新变更
变更追溯 通过 PR 链接可追踪任何变更的上下文

PR 创建最佳实践

一个高质量的 PR 应具备：

git checkout -b feat/user-profile
# ... 开发 ...
git add -A
git commit -m "feat(profile): add user avatar upload"
git push -u origin feat/user-profile

PR 描述模板：

## 变更说明
简述本 PR 的目的和实现方案。

## 变更类型
- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 文档更新

## 测试
描述如何测试这些变更。

## 截图（如适用）

## 关联 Issue
Closes #123
原则 说明
保持小而聚焦 单个 PR 不超过 400 行变更
原子性 一个 PR 只做一件事
自解释 标题和描述清晰说明变更内容
可测试 包含测试或说明测试方法
关联 Issue 使用 Closes/Fixes 关键字关联

提示： 研究表明，超过 400 行的 PR 审查质量会显著下降。如果功能较大，考虑拆分为多个递增式 PR。

小结
    

  • PR 是代码审查、CI 集成和知识传递的核心载体，保持小而聚焦是首要原则
    • 

  • 通过 Branch Protection Rules 强制 CI 检查通过才允许合并
    • 

  • 根据团队偏好选择合并策略：squash 最简洁，merge commit 最完整，rebase 最线性
    • 

  • Merge Queue 解决高并发 PR 场景下的合并竞态问题
    • 

  • Draft PR 支持早期反馈和渐进式开发，减少后期大规模返工
