Part I · 版本控制与协作Git 与版本控制 简介基础与原理 简介分支模型

分支模型

分支的本质

在 Git 中，分支（Branch） 本质上是一个指向某个 commit 的可移动指针。创建分支只是创建一个 41 字节的文件（40 字符 SHA-1 + 换行符），几乎没有成本。

git branch feature
cat .git/refs/heads/feature

git branch -a

git log --oneline --graph --all --decorate

Git Flow

Git Flow 是 Vincent Driessen 在 2010 年提出的分支模型，适合有明确版本发布周期的项目。

分支类型 生命周期 来源 合并目标 用途
main 永久 — — 生产环境代码
develop 永久 main — 集成开发分支
feature/* 临时 develop develop 功能开发
release/* 临时 develop main + develop 版本发布准备
hotfix/* 临时 main main + develop 紧急修复 
git flow init

git flow feature start user-auth
git flow feature finish user-auth

git flow release start v1.2.0
git flow release finish v1.2.0


提示： Git Flow 适合发布周期较长（周/月级别）的项目，对于持续部署的 SaaS 产品可能过于复杂。






GitHub Flow
GitHub Flow 是 GitHub 推荐的简化分支模型，核心原则是 main 分支始终可部署。


工作流程：


git checkout -b feature/new-header
git add -A && git commit -m "feat: add new header component"
git push origin feature/new-header

Trunk-Based Development
Trunk-Based Development（主干开发） 要求所有开发者频繁（至少每天）向主干分支（trunk/main）提交代码，配合特性开关（Feature Flag） 控制功能发布。


git checkout main
git pull --rebase origin main

git add -A && git commit -m "feat: add dark mode behind flag"
git push origin main

小结
    

  • Git 分支本质是指向 commit 的轻量指针，创建和切换成本极低
    • 

  • Git Flow 适合版本化发布的项目，通过多分支类型管理不同阶段的代码
    • 

  • GitHub Flow 以 PR 为核心，简洁高效，适合持续部署的大多数团队
    • 

  • Trunk-Based Development 追求极致的持续集成，依赖 Feature Flag 实现功能与发布解耦
    • 

  • 选择分支策略需综合考虑发布频率、团队规模和 CI/CD 成熟度
    •
