Actions 性能优化

核心概念

GitHub Actions 的性能直接影响开发者体验和 CI 成本。每分钟的 Runner 时间都是真金白银——GitHub-hosted Runner 按分钟计费，自托管 Runner 则消耗基础设施资源。优化的目标是在不牺牲质量门禁的前提下，将工作流执行时间压缩到最短。

多层缓存策略
缓存是性能优化中 ROI 最高的手段。GitHub Actions 提供了 actions/cache 和 actions/setup-* 内置的缓存机制。关键是设计多层缓存：精确命中 → 前缀回退 → 冷启动。


- name: Cache pnpm store
  uses: actions/cache@v4
  id: pnpm-cache
  with:
    path: |
      ~/.local/share/pnpm/store
      node_modules/.cache
    key: pnpm-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml') }}
    restore-keys: |
      pnpm-${{ runner.os }}-

- name: Cache Turborepo
  uses: actions/cache@v4
  with:
    path: .turbo
    key: turbo-${{ runner.os }}-${{ github.sha }}
    restore-keys: |
      turbo-${{ runner.os }}-${{ github.base_ref || 'main' }}-
      turbo-${{ runner.os }}-
interface CacheLayer {
  name: string;
  paths: string[];
  keyTemplate: string;
  restoreKeys: string[];
  hitRate: string;
  savedTime: string;
}

const cacheStack: CacheLayer[] = [
  {
    name: 'pnpm-store',
    paths: ['~/.local/share/pnpm/store'],
    keyTemplate: 'pnpm-{os}-{lockfileHash}',
    restoreKeys: ['pnpm-{os}-'],
    hitRate: '85-95%',
    savedTime: '1-3 min',
  },
  {
    name: 'turbo-cache',
    paths: ['.turbo'],
    keyTemplate: 'turbo-{os}-{sha}',
    restoreKeys: ['turbo-{os}-{baseBranch}-', 'turbo-{os}-'],
    hitRate: '70-90%',

  },

    paths: ['/tmp/.buildx-cache'],
    keyTemplate: 'docker-{os}-{dockerfileHash}',

];
缓存的最大限制是 10GB 总容量（所有分支共享），超过后按最近最少使用（LRU）淘汰。关键是控制缓存大小——对于 node_modules，缓存 pnpm store 而不是 node_modules 本身，因为 store 是内容寻址的、跨项目共享的。


Job 拆分与并行化
将大 Job 拆分为多个并行 Job 是最直接的加速手段。关键原则是识别无依赖关系的任务，让它们同时执行。


jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm run lint

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm -r typecheck

  test-unit:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm vitest --shard=${{ matrix.shard }}/4

  test-e2e:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        browser: [chromium, firefox]
    steps:
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm playwright test --project=${{ matrix.browser }}

  build:
    needs: [lint, typecheck]
    runs-on: ubuntu-latest
    steps:
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm build
测试分片（Sharding） 是并行化测试的标准方式。Vitest 原生支持 --shard 参数，按文件名哈希将测试分配到不同分片。Playwright 也支持类似的分片机制。


需要注意的是，并行化有开销：每个 Job 都需要独立的 Runner 启动、代码检出和依赖安装。如果任务本身只需要 30 秒，拆分后反而因为启动开销而变慢。经验法则：单个任务 > 2 分钟时才值得拆分。


条件执行与跳过
不是所有变更都需要运行完整的工作流。通过条件执行，可以跳过不相关的步骤和 Job。


jobs:
  detect:
    runs-on: ubuntu-latest
    outputs:
      src-changed: ${{ steps.filter.outputs.src }}
      docs-changed: ${{ steps.filter.outputs.docs }}
      deps-changed: ${{ steps.filter.outputs.deps }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            src:
              - 'src/**'
              - 'packages/**'
            docs:
              - 'docs/**'
              - '*.md'
            deps:
              - 'pnpm-lock.yaml'
              - 'package.json'

  test:
    needs: detect
    if: needs.detect.outputs.src-changed == 'true'
    runs-on: ubuntu-latest
    steps:
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm test

  security:
    needs: detect
    if: needs.detect.outputs.deps-changed == 'true'
    runs-on: ubuntu-latest
    steps:
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm audit

  deploy-docs:
    needs: detect
    if: needs.detect.outputs.docs-changed == 'true'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploy docs"
另一个强大的优化是 Commit 消息指令。约定 [skip ci] 或 [ci skip] 跳过 CI，[full ci] 强制完整构建：


jobs:
  build:
    if: |
      !contains(github.event.head_commit.message, '[skip ci]') &&
      !contains(github.event.head_commit.message, '[ci skip]')
Runner 与资源优化
选择合适的 Runner 规格可以显著影响性能和成本。GitHub 提供了标准 Runner（2 vCPU, 7GB RAM）和大型 Runner（4-64 vCPU）。


jobs:
  quick-checks:
    runs-on: ubuntu-latest

  heavy-build:
    runs-on: ubuntu-latest-4-cores

  macos-build:
    runs-on: macos-14

优化策略是按需分配——轻量任务（lint、typecheck）用标准 Runner，重型任务（构建、E2E 测试）用大型 Runner。


对于自托管 Runner，可以利用 ephemeral Runner（一次性 Runner）和 Runner Groups 实现弹性伸缩：


jobs:
  build:
    runs-on:
      group: high-memory-runners
      labels: [self-hosted, linux, x64]
    container:
      image: node:20-alpine
小结
    

  • 多层缓存（pnpm store → Turborepo → Docker 层）是 ROI 最高的优化手段
    • 

  • Job 并行化 + 测试分片可以将测试阶段缩短 2-4 倍
    • 

  • 路径过滤和变更检测确保只运行受影响的工作流，Monorepo 可节省 60-80% 时间
    • 

  • Runner 按需分配——轻量任务用标准 Runner，重型任务用大型或自托管 Runner
    • 

  • 缓存总容量限制 10GB，优先缓存包管理器 store 而非 node_modules
    •
