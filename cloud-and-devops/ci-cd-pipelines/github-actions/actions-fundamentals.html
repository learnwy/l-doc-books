GitHub Actions 基础

核心概念

GitHub Actions 是 GitHub 原生的 CI/CD 平台，它将工作流自动化直接集成到代码仓库中。与 Jenkins、CircleCI 等独立 CI 系统不同，Actions 与 GitHub 的 PR、Issues、Releases 等功能深度集成，触发条件丰富，生态系统庞大。理解 Actions 的执行模型和核心概念是高效使用它的前提。

工作流配置语法
工作流文件存放在 .github/workflows/ 目录下，使用 YAML 格式。GitHub 在每次事件发生时扫描该目录，匹配触发条件的工作流会被执行。


name: CI
on:
  push:
    branches: [main]
    paths-ignore: ['docs/**', '*.md']
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened]
  schedule:
    - cron: '0 2 * * 1'
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment'
        required: true
        type: choice
        options: [staging, production]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read
  pull-requests: write
触发器（on） 支持 30+ 种事件类型。最常用的是 push、pull_request 和 workflow_dispatch（手动触发）。schedule 支持 cron 表达式实现定时构建。


并发控制（concurrency） 避免同一分支的多次推送导致资源浪费。cancel-in-progress: true 会取消同组中正在运行的旧工作流，只保留最新的。


interface WorkflowTrigger {
  event: string;
  filters: Record<string, string[]>;
  types?: string[];
  inputs?: Record<string, WorkflowInput>;
}

interface WorkflowInput {
  description: string;
  required: boolean;
  type: 'string' | 'boolean' | 'choice' | 'environment';
  default?: string;
  options?: string[];
}
表达式与上下文
GitHub Actions 的表达式系统是其灵活性的核心。${{ }} 语法在工作流解析时求值，可以访问丰富的上下文对象。


jobs:
  build:
    runs-on: ubuntu-latest
    if: github.event_name == 'push' || github.event.pull_request.draft == false
    env:
      NODE_ENV: ${{ github.ref == 'refs/heads/main' && 'production' || 'development' }}
    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          fetch-depth: ${{ github.event_name == 'pull_request' && 2 || 0 }}

      - name: Get changed files
        id: changes
        run: |
          echo "files=$(git diff --name-only HEAD~1 | tr '\n' ',')" >> $GITHUB_OUTPUT

      - name: Run tests if source changed
        if: contains(steps.changes.outputs.files, 'src/')
        run: pnpm test

Step 输出是 Steps 之间传递数据的标准方式。通过写入 $GITHUB_OUTPUT 环境文件，后续步骤可以通过 steps.<id>.outputs.<key> 引用。


Job 编排与依赖
Job 默认并行执行。通过 needs 关键字可以定义 Job 之间的依赖关系，形成 DAG（有向无环图）执行模型。


jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pnpm lint

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pnpm typecheck

  test:
    needs: [lint, typecheck]
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [18, 20, 22]
      fail-fast: false
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: pnpm install --frozen-lockfile
      - run: pnpm test

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - run: echo "Deploying..."
矩阵策略（strategy.matrix） 可以自动扩展 Job，为每个组合创建一个实例。结合 fail-fast: false，可以在一个矩阵实例失败时继续运行其他实例，收集完整的兼容性报告。


环境（environment） 关联 Deployment Protection Rules，可以要求手动审批、等待计时器、或限制允许的分支。这是 CD 中的关键安全控制。


Runner 与执行环境
Runner 是 Job 的执行环境。GitHub 提供托管 Runner（Ubuntu、macOS、Windows），也支持自托管 Runner。


jobs:
  build-linux:
    runs-on: ubuntu-latest

  build-macos:
    runs-on: macos-latest

  build-self-hosted:
    runs-on: [self-hosted, linux, gpu]
    container:
      image: node:20-alpine
      volumes:
        - /data:/data
托管 Runner 的优势是零维护，但有限制：每个 Job 最多 6 小时，ubuntu-latest 有 7GB RAM。对于需要 GPU、大内存或特殊硬件的场景，自托管 Runner 是唯一选择。


自托管 Runner 的安全风险需要注意：不要在公开仓库上使用自托管 Runner，因为 fork PR 可以在你的 Runner 上执行任意代码。


小结
    

  • GitHub Actions 的核心层次是 Workflow → Job → Step → Action，理解执行模型是高效使用的前提
    • 

  • 触发器支持 30+ 种事件，concurrency 控制避免资源浪费
    • 

  • 表达式系统 ${{ }} 提供丰富的上下文访问和条件逻辑能力
    • 

  • Job 通过 needs 形成 DAG 依赖，matrix 策略实现多维度并行测试
    • 

  • 托管 Runner 零维护但有资源限制，自托管 Runner 灵活但需注意安全
    •
