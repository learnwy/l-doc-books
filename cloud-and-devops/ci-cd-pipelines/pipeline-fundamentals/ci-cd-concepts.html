CI/CD 核心概念

核心概念

持续集成（CI）和持续交付/部署（CD）是现代软件工程的基石实践。CI 强调开发者频繁将代码合并到主干分支，每次合并触发自动化构建与测试；CD 则将通过验证的代码自动推送到预发布或生产环境。这一实践从根本上改变了软件交付的节奏——从季度发布到每日甚至每小时发布。

持续集成的核心原则
持续集成不仅仅是一个工具或流程，它是一种开发文化。Martin Fowler 定义的 CI 实践包含几个关键原则：单一代码仓库、自动化构建、自测构建、每日提交和快速反馈。


主干开发（Trunk-Based Development） 是 CI 的理想分支策略。开发者在短生命周期的特性分支上工作，通常不超过一天就合并回主干。这与长生命周期的 GitFlow 模式形成对比——后者容易导致合并冲突和集成延迟。

  trigger: TriggerRule;

  branches: string[];

}

interface Stage {

  jobs: Job[];
  dependsOn?: string[];

}

interface Job {
  name: string;
  runner: string;
  steps: Step[];
  timeout: number;
  retries: number;
  cache?: CacheConfig;
}
构建速度是 CI 成功的关键指标。业界公认的标准是 10 分钟规则——从提交到获得反馈不应超过 10 分钟。超过这个时间，开发者会切换上下文，反馈循环的价值急剧下降。


为达到这个目标，常用的加速策略包括：


    

  • 增量构建：只重新编译变更的模块，利用构建缓存避免重复工作
    • 

  • 并行化：将独立的测试套件分配到多个运行器上同时执行
    • 

  • 分层测试：先运行快速的单元测试，通过后再运行慢速的集成测试
    • 

  • 依赖缓存：缓存 node_modules、Docker 层等不常变化的依赖
    • 



持续交付 vs 持续部署
持续交付（Continuous Delivery）和持续部署（Continuous Deployment）虽然缩写相同，但理念有本质区别。


持续交付确保代码始终处于可发布状态。流水线会自动将代码推送到预发布环境并完成全部验证，但最终的生产发布由人工触发。这给了团队一个"安全阀"——可以选择合适的时机发布，比如避开业务高峰期。


持续部署则完全消除人工环节。每次通过所有自动化验证的代码变更都会自动部署到生产环境。这要求极高的测试覆盖率和监控能力，因为没有人工兜底。


选择哪种模式取决于业务场景：


    

  • B2C 互联网产品：持续部署更合适，快速迭代、A/B 测试驱动
    • 

  • 金融/医疗系统：持续交付更安全，合规要求需要审批记录
    • 

  • 开源项目：持续交付，版本发布需要变更日志和语义化版本
    • 

  • 内部工具：持续部署，用户群体固定，风险可控
    •

interface PipelineMetrics {
  deployFrequency: number;
  leadTimeForChanges: number;
  changeFailureRate: number;
  timeToRestore: number;
}

const calculateDeployFrequency = (deploys: Deployment[], periodDays: number): number => {
  const successfulDeploys = deploys.filter((d) => d.status === 'success');
  return successfulDeploys.length / periodDays;
};

const calculateLeadTime = (commits: CommitWithDeploy[]): number => {
  const leadTimes = commits.map((c) => c.deployedAt.getTime() - c.committedAt.getTime());
  return leadTimes.reduce((a, b) => a + b, 0) / leadTimes.length;
};

const calculateChangeFailureRate = (deploys: Deployment[]): number => {
  const failed = deploys.filter((d) => d.causedIncident);
  return failed.length / deploys.length;
};
追踪这些指标的价值在于：它们将 CI/CD 从一个技术实践提升为业务能力。当 CTO 可以展示"我们的变更前置时间从 2 周缩短到 2 小时"时，技术投资的 ROI 变得可量化。


流水线即代码
现代 CI/CD 系统普遍采用"流水线即代码"（Pipeline as Code）的理念——用版本控制的配置文件定义流水线，而不是在 Web 界面上手动配置。这带来了几个关键优势：


    

  • 版本历史：流水线变更可追溯，可审计
    • 

  • 代码审查：流水线配置变更经过 PR 审查
    • 

  • 环境一致性：不同分支可以有不同的流水线配置
    • 

  • 灾难恢复：CI 系统崩溃后可从代码仓库快速恢复
    • 



# 典型的流水线即代码结构
pipeline:
  stages:
    - name: build
      parallel:
        - job: build-frontend
          image: node:20-alpine
          cache: [node_modules]
          script:
            - pnpm install --frozen-lockfile
            - pnpm build
        - job: build-backend
          image: golang:1.22
          cache: [/go/pkg/mod]
          script:
            - go build ./cmd/server
    - name: test
      dependsOn: build
      parallel:
        - job: unit-tests
          script: pnpm test --coverage
        - job: integration-tests
          services: [postgres, redis]
          script: pnpm test:integration
    - name: deploy
      dependsOn: test
      condition: branch == 'main'
      script: ./deploy.sh
不同 CI 平台的配置语法虽然不同，但核心抽象是一致的：阶段（Stage） 定义执行顺序，作业（Job） 是最小执行单元，步骤（Step） 是具体操作。理解这个抽象，切换平台时只需要"翻译"语法。


小结
    

  • CI/CD 是现代软件交付的核心实践，CI 关注集成质量，CD 关注交付效率
    • 

  • 持续交付保留人工审批环节，持续部署完全自动化——选择取决于业务风险容忍度
    • 

  • 10 分钟反馈规则是 CI 体验的生命线，通过增量构建、并行化和缓存来保障
    • 

  • DORA 四个关键指标（部署频率、前置时间、失败率、恢复时间）量化 CI/CD 成熟度
    • 

  • 流水线即代码将 CI/CD 配置纳入版本控制，实现可审计、可审查、可恢复
    •
