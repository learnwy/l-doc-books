制品管理

核心概念

制品（Artifact）是 CI/CD 流水线中构建阶段的产出物——编译后的二进制文件、Docker 镜像、npm 包、静态资源包等。制品管理解决的核心问题是：如何确保部署到生产环境的代码与通过测试的代码完全一致。这个问题看似简单，实际上涉及版本控制、不可变性、完整性校验和生命周期管理等多个维度。

不可变制品原则
制品管理的第一原则是不可变性（Immutability）：一旦制品被发布到注册表，就不能被修改或覆盖。这个原则保证了可追溯性和可重复性——任何时候拉取同一个版本号的制品，得到的内容都完全相同。


违反不可变性的常见反模式是可变标签。例如 Docker 的 latest 标签会随每次推送而变化，main 分支标签也是如此。这导致"昨天能用今天不能用"的幽灵问题。


interface ArtifactVersion {
  name: string;
  version: string;
  digest: string;
  immutable: boolean;
  createdAt: Date;
  buildRef: string;
  sourceCommit: string;
}

const versioningStrategy = {
  release: {
    pattern: 'v{major}.{minor}.{patch}',
    immutable: true,
    retention: 'forever',
  },
  prerelease: {
    pattern: 'v{major}.{minor}.{patch}-rc.{n}',
    immutable: true,
    retention: '90d',
  },
  snapshot: {
    pattern: '{branch}-{sha7}-{timestamp}',
    immutable: true,
    retention: '30d',
  },
  mutable: {
    pattern: 'latest',
    immutable: false,
    retention: 'overwritten',
  },
};
正确的做法是使用内容寻址或Git SHA作为制品的唯一标识，然后用人类可读的标签（如 v1.2.3）作为别名指向它。Docker 中这就是 digest（sha256:abc...）和 tag 的关系。


- name: Build and push image
  run: |
    DIGEST=$(docker build --push -t $REGISTRY/$IMAGE:$SHA . | grep digest | awk '{print $NF}')
    echo "digest=$DIGEST" >> $GITHUB_OUTPUT

- name: Tag release
  if: startsWith(github.ref, 'refs/tags/v')
  run: |
    crane tag $REGISTRY/$IMAGE@$DIGEST ${{ github.ref_name }}
语义化版本管理
对于发布型制品（npm 包、Helm Chart、公共 API），语义化版本（SemVer）是行业标准。SemVer 通过版本号传达变更的性质：MAJOR.MINOR.PATCH。


自动化语义化版本的工具链基于约定式提交（Conventional Commits）。semantic-release 或 changesets 分析提交历史，自动决定版本号递增方式：


interface ConventionalCommit {
  type: 'feat' | 'fix' | 'docs' | 'chore' | 'refactor' | 'perf' | 'test';
  scope?: string;
  breaking: boolean;
  description: string;
}

const versionBump = (commits: ConventionalCommit[]): 'major' | 'minor' | 'patch' => {
  if (commits.some((c) => c.breaking)) return 'major';
  if (commits.some((c) => c.type === 'feat')) return 'minor';
  return 'patch';
};
在 Monorepo 中，changesets 工作流更为灵活。开发者在 PR 中添加 changeset 文件声明变更的包和级别，CI 自动汇总并生成版本 PR：


- name: Create Release
  uses: changesets/action@v1
  with:
    publish: pnpm changeset publish
    version: pnpm changeset version
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
制品安全与完整性
制品的安全性关乎供应链安全。从构建到部署的每个环节都可能被篡改——CI 环境被入侵、传输过程被中间人攻击、注册表被入侵等。


签名与验证是防篡改的核心手段。Sigstore 的 cosign 工具为 Docker 镜像提供无密钥签名：


cosign sign --yes $REGISTRY/$IMAGE@$DIGEST

cosign verify \
  --certificate-identity "https://github.com/org/repo/.github/workflows/build.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  $REGISTRY/$IMAGE@$DIGEST
SBOM（软件物料清单） 记录制品包含的所有依赖及其版本。当新漏洞被披露时，SBOM 让你快速判断哪些制品受影响：


interface SBOMEntry {
  name: string;
  version: string;
  license: string;
  purl: string;
  vulnerabilities: Vulnerability[];
}

interface ArtifactSecurity {
  artifact: ArtifactVersion;
  signature: string;
  sbom: SBOMEntry[];
  attestations: Attestation[];
  scanResults: ScanResult;
}
SLSA（Supply-chain Levels for Software Artifacts） 框架定义了四个供应链安全等级，从基本的构建来源记录（Level 1）到全面的硬件隔离构建（Level 4）。GitHub Actions 和 Google Cloud Build 已支持生成 SLSA 证明。


制品生命周期管理
制品如果不清理，注册表存储会无限增长。合理的保留策略需要在存储成本、可审计性和灾难恢复之间取得平衡。


interface RetentionPolicy {
  name: string;
  selector: (artifact: ArtifactVersion) => boolean;
  retention: string;
  action: 'delete' | 'archive';
}

const policies: RetentionPolicy[] = [
  {
    name: 'keep-releases-forever',
    selector: (a) => /^v\d+\.\d+\.\d+$/.test(a.version),
    retention: 'forever',
    action: 'archive',
  },
  {
    name: 'prune-snapshots-30d',
    selector: (a) => a.version.includes('-snapshot'),
    retention: '30d',
    action: 'delete',
  },
  {
    name: 'prune-pr-builds-7d',
    selector: (a) => a.version.startsWith('pr-'),
    retention: '7d',
    action: 'delete',
  },
  {
    name: 'keep-rc-90d',
    selector: (a) => a.version.includes('-rc.'),
    retention: '90d',
    action: 'delete',
  },
];
自动清理通常通过定时任务（CronJob 或 Scheduled Workflow）执行。在清理前，需要确保没有活跃部署正在使用即将被删除的制品——这通常通过查询 Kubernetes 集群中正在运行的镜像 digest 来实现。


保留策略还需要考虑合规要求。金融和医疗行业通常要求保留所有发布制品 3-7 年，这时需要将冷数据归档到低成本存储（如 S3 Glacier）。


小结
    

  • 制品管理确保"测试通过的代码"与"部署的代码"完全一致
    • 

  • 不可变性是制品管理的第一原则——用内容寻址 + 标签别名替代可变标签
    • 

  • 语义化版本 + 约定式提交实现自动化版本管理和变更日志生成
    • 

  • 供应链安全需要签名验证（cosign）、SBOM 和 SLSA 证明多层防护
    • 

  • 保留策略按制品类型差异化——Release 永久，Snapshot 30 天，PR 7 天
    •
