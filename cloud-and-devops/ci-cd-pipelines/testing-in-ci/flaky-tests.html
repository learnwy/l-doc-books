Flaky 测试治理

核心概念

Flaky 测试（不稳定测试）是 CI 系统的癌症——它们在相同代码上时而通过、时而失败，没有确定性。当 CI 中有 5% 的 flaky 测试时，开发者开始习惯性地点击"重试"；当达到 15% 时，CI 的信任度崩塌，团队开始忽略失败的测试。Google 的工程实践报告显示，大型代码库中 flaky 测试占所有测试失败的 84%。

检测与识别
检测 flaky 测试的第一步是区分"真失败"和"不稳定失败"。最简单的方法是对失败的测试自动重试——如果重试通过，就标记为 flaky。


jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/setup-pnpm

      - name: Run tests with retry
        run: pnpm vitest --run --reporter=json --outputFile=results.json
        continue-on-error: true

      - name: Retry failed tests
        if: steps.test.outcome == 'failure'
        run: |
          FAILED=$(jq -r '.testResults[] | select(.status == "failed") | .name' results.json)
          echo "$FAILED" | xargs pnpm vitest --run
更系统化的方法是维护一个 flaky 测试数据库：


interface FlakyRecord {
  testId: string;
  testFile: string;
  testName: string;
  firstSeen: Date;
  lastSeen: Date;
  totalRuns: number;
  failureCount: number;
  flakyRate: number;
  status: 'active' | 'quarantined' | 'resolved';
  assignee?: string;
  rootCause?: string;
}

const detectFlaky = (testResults: TestResult[], history: FlakyRecord[]): FlakyRecord[] => {
  const newFlaky: FlakyRecord[] = [];

  for (const result of testResults) {
    if (result.status === 'failed' && result.retryStatus === 'passed') {
      const existing = history.find((r) => r.testId === result.id);
      if (existing) {
        existing.failureCount++;
        existing.totalRuns++;
        existing.lastSeen = new Date();
        existing.flakyRate = existing.failureCount / existing.totalRuns;
      } else {
        newFlaky.push({
          testId: result.id,
          testFile: result.file,
          testName: result.name,
          firstSeen: new Date(),
          lastSeen: new Date(),
          totalRuns: 1,
          failureCount: 1,
          flakyRate: 1,
          status: 'active',
        });
      }
    }
  }

  return newFlaky;
};
Vitest 的 --retry 参数提供了内置的重试机制。Playwright 的 retries 配置更为精细——可以区分"首次失败"和"重试失败"，配合 trace: 'on-first-retry' 自动录制失败时的操作轨迹。


隔离与治理
当 flaky 测试被识别后，最糟糕的做法是置之不理。正确的流程是 隔离 → 修复 → 验证 → 复原。


隔离（Quarantine） 将 flaky 测试从关键路径移出，避免阻断正常 CI。但隔离不是删除——测试仍然运行，只是失败不阻断。


const QUARANTINED_TESTS = new Set([
  'src/features/payment/__tests__/checkout.test.ts',
  'src/features/search/__tests__/autocomplete.test.ts',
]);

interface QuarantinePolicy {
  maxQuarantineDays: number;
  autoQuarantineThreshold: number;
  reviewSchedule: 'weekly' | 'biweekly';
  escalationPolicy: EscalationRule[];
}

const policy: QuarantinePolicy = {
  maxQuarantineDays: 14,
  autoQuarantineThreshold: 3,
  reviewSchedule: 'weekly',
  escalationPolicy: [
    { daysInQuarantine: 7, action: 'notify-owner' },
    { daysInQuarantine: 14, action: 'notify-tech-lead' },
    { daysInQuarantine: 21, action: 'delete-or-rewrite' },
  ],
};
name: Flaky Test Review
on:
  schedule:
    - cron: '0 9 * * 1'

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

            const quarantined = require('./test-quarantine.json');

常见根因修复
时序问题是最常见的 flaky 根因。在前端测试中，表现为"元素还没渲染就点击了"、"API 响应还没回来就断言了"。


// 反模式：固定延迟
await page.click('#submit');
await page.waitForTimeout(2000);
expect(await page.textContent('.result')).toBe('Success');

// 正确：等待特定条件
await page.click('#submit');
await expect(page.locator('.result')).toHaveText('Success', { timeout: 10000 });
共享状态问题通常出现在测试间共享数据库或全局变量。修复方法是每个测试使用独立的数据上下文：


interface TestIsolation {
  beforeEach: () => Promise<void>;
  afterEach: () => Promise<void>;
}

const databaseIsolation: TestIsolation = {
  beforeEach: async () => {
    await db.execute('BEGIN');
  },
  afterEach: async () => {
    await db.execute('ROLLBACK');
  },
};
外部依赖问题通过 Mock 或 VCR（Video Cassette Recorder）模式解决。VCR 首次运行时录制真实的 HTTP 响应，后续运行回放录制：


import { setupServer } from 'msw/node';
import { http, HttpResponse } from 'msw';

const handlers = [
  http.get('https://api.github.com/repos/:owner/:repo', () => {
    return HttpResponse.json({
      id: 1,
      full_name: 'org/repo',
      stargazers_count: 42,
    });
  }),
];

const server = setupServer(...handlers);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
预防机制
预防优于治疗。在开发流程中嵌入防 flaky 机制：


- name: Stress test new tests
  if: github.event_name == 'pull_request'
  run: |
    NEW_TESTS=$(git diff --name-only HEAD~1 | grep '\.test\.' || true)
    if [ -n "$NEW_TESTS" ]; then
      for i in $(seq 1 5); do
        echo "Run $i/5"
        echo "$NEW_TESTS" | xargs pnpm vitest --run
      done
    fi
这个策略对 PR 中新增的测试文件运行 5 次。如果新测试在 5 次运行中有任何一次失败，就在合并前暴露 flaky 问题。

小结
    

  • Flaky 测试占大型代码库测试失败的 84%，是 CI 信任度的最大杀手
    • 

  • 检测 flaky 的标准方法是自动重试——重试通过的失败即为 flaky
    • 

  • 隔离（Quarantine）将 flaky 从关键路径移出，但必须设置修复期限（14 天）
    • 

  • 时序问题用显式等待替代固定延迟，共享状态用事务回滚隔离，外部依赖用 MSW Mock
    • 

  • PR 中对新测试运行多次是最有效的预防机制——在合并前暴露 flaky
    •
