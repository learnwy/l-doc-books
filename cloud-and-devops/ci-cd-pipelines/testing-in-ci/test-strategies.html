CI 测试策略

核心概念

CI 中的测试策略决定了什么时候运行什么类型的测试。测试金字塔（Test Pyramid）是经典的指导原则：底层是大量快速的单元测试，中间是适量的集成测试，顶层是少量的端到端测试。但在 CI 环境中，测试策略还需要考虑执行时间、资源成本和反馈质量的三角平衡。

分层测试执行
分层执行的核心思想是 Fail Fast：先运行最快、最可能失败的测试，只有通过后才运行慢速测试。这最大化了反馈速度。


jobs:
  fast-checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm run lint
      - run: pnpm -r typecheck
      - run: pnpm vitest --run --reporter=verbose

  integration:
    needs: fast-checks
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_DB: test
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
        ports: ['5432:5432']
        options: >-
          --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5


    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm test:integration
        env:
          DATABASE_URL: postgresql://test:test@localhost:5432/test

  e2e:
    needs: fast-checks
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2]
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/setup-pnpm
      - run: pnpm playwright install --with-deps chromium
      - run: pnpm playwright test --shard=${{ matrix.shard }}/2
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: playwright-report-${{ matrix.shard }}
          path: playwright-report/

  timeout: number;

测试覆盖率门禁
覆盖率是 CI 中最常用的质量指标。但覆盖率数字本身有陷阱——100% 行覆盖率不等于代码没有 Bug，而过低的阈值又形同虚设。


有效的覆盖率策略是增量覆盖率——只检查新增和修改的代码的覆盖率，而不是全局覆盖率。这避免了"遗留代码拖累新代码"的问题。


- name: Run tests with coverage
  run: pnpm vitest --run --coverage

- name: Check coverage
  uses: davelosert/vitest-coverage-report-action@v2
  with:
    json-summary-path: coverage/coverage-summary.json
    json-final-path: coverage/coverage-final.json
    vite-config-path: vitest.config.ts
interface CoveragePolicy {
  global: CoverageThreshold;
  perFile: CoverageThreshold;
  newCode: CoverageThreshold;
}

interface CoverageThreshold {
  lines: number;
  branches: number;
  functions: number;
  statements: number;
}

const coveragePolicy: CoveragePolicy = {
  global: { lines: 70, branches: 60, functions: 70, statements: 70 },
  perFile: { lines: 50, branches: 40, functions: 50, statements: 50 },
  newCode: { lines: 80, branches: 70, functions: 80, statements: 80 },
};
覆盖率报告应直接展示在 PR 中，让审查者一目了然。好的覆盖率工具还能标注哪些新增行未被覆盖，引导开发者补充测试。


服务容器与测试环境
集成测试需要外部服务（数据库、缓存、消息队列）。GitHub Actions 的 services 字段提供了声明式的服务容器管理。


services:
  postgres:
    image: postgres:16-alpine
    env:
      POSTGRES_DB: test
      POSTGRES_USER: test
      POSTGRES_PASSWORD: test
    ports: ['5432:5432']
    options: >-
      --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5


  redis:
    image: redis:7-alpine
    ports: ['6379:6379']
    options: >-
      --health-cmd "redis-cli ping" --health-interval 10s --health-timeout 5s --health-retries 5
options 中的 health check 确保服务完全就绪后才开始测试，避免"连接拒绝"类的 flaky 失败。


对于更复杂的环境需求，可以使用 Docker Compose：


steps:
  - name: Start services
    run: docker compose -f docker-compose.test.yml up -d
  - name: Wait for services
    run: |
      timeout 60 bash -c 'until docker compose exec db pg_isready; do sleep 1; done'
  - name: Run tests
    run: pnpm test:integration
  - name: Cleanup
    if: always()
    run: docker compose -f docker-compose.test.yml down -v
小结
    

  • 测试策略的核心是分层执行——快速检查优先，Fail Fast 最大化反馈速度
    • 

  • 增量覆盖率比全局覆盖率更有价值——只检查新代码的覆盖率避免遗留代码拖累
    • 

  • GitHub Actions 的 services 字段提供声明式服务容器，health check 避免 flaky 失败
    • 

  • E2E 测试使用分片（shard）并行化，失败时上传报告 artifact 辅助调试
    • 

  • 测试层之间通过 needs 建立依赖，确保快速层通过后才运行慢速层
    •
