金丝雀部署

核心概念

金丝雀部署（Canary Deployment）得名于矿工用金丝雀检测有毒气体——先将新版本暴露给一小部分用户，观察其表现，确认安全后逐步扩大流量比例。与蓝绿部署的"全量切换"不同，金丝雀部署是渐进式的风险暴露，允许在影响范围最小的时候发现问题。

流量分配策略
金丝雀部署的核心是流量路由。根据不同的分配策略，金丝雀可以更精确地控制暴露范围。


interface CanaryConfig {
  name: string;
  stages: CanaryStage[];
  analysis: AnalysisConfig;
  rollbackPolicy: RollbackPolicy;
}

interface CanaryStage {
  weight: number;
  duration: number;
  pauseForApproval: boolean;
  metrics: MetricThreshold[];
}

const progressiveDelivery: CanaryConfig = {
  name: 'web-app-canary',
  stages: [
    { weight: 1, duration: 300, pauseForApproval: false, metrics: [{ name: 'error_rate', threshold: 1 }] },
    { weight: 5, duration: 600, pauseForApproval: false, metrics: [{ name: 'error_rate', threshold: 1 }] },
    { weight: 25, duration: 900, pauseForApproval: true, metrics: [{ name: 'error_rate', threshold: 0.5 }] },
    { weight: 50, duration: 1200, pauseForApproval: false, metrics: [{ name: 'error_rate', threshold: 0.5 }] },
    { weight: 100, duration: 0, pauseForApproval: false, metrics: [] },
  ],
  analysis: {
    interval: 60,
    comparisonWindow: 300,
    baselineSource: 'stable',
  },
  rollbackPolicy: {
    automatic: true,
    maxFailedChecks: 3,
  },
};
基于权重的路由是最常见的方式——负载均衡器按比例将流量分配到金丝雀和稳定版本。更高级的策略包括：


    

  • 基于 Header 路由：内部测试人员通过特定 Header 直接访问金丝雀版本
    • 

  • 基于地域路由：先在特定地域灰度，再全球推广
    • 

  • 基于用户 ID 路由：固定用户始终访问同一版本，避免体验不一致
    • 



apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: app-canary
spec:
  hosts:
    - app.example.com
  http:
    - match:

            x-canary:
              exact: 'true'
      route:

自动化分析与决策
金丝雀部署的价值取决于自动化分析——人工观察仪表盘是不可扩展的。自动化金丝雀分析（Automated Canary Analysis, ACA）通过统计比较金丝雀和基准版本的指标来做出决策。


interface CanaryAnalysis {
  canaryMetrics: TimeSeriesData[];
  baselineMetrics: TimeSeriesData[];
  comparisonResult: ComparisonResult;
}

interface ComparisonResult {
  score: number;
  verdict: 'pass' | 'fail' | 'inconclusive';
  metricResults: MetricComparison[];
}

interface MetricComparison {
  name: string;
  canaryValue: number;
  baselineValue: number;
  deviation: number;
  critical: boolean;
  result: 'pass' | 'fail' | 'marginal';
}

const analyzeCanary = (
  canary: MetricSnapshot,
  baseline: MetricSnapshot,
  thresholds: Record<string, number>,
): ComparisonResult => {
  const results: MetricComparison[] = Object.keys(thresholds).map((metric) => {
    const canaryVal = canary[metric];
    const baselineVal = baseline[metric];
    const deviation = baselineVal > 0 ? ((canaryVal - baselineVal) / baselineVal) * 100 : 0;

    return {
      name: metric,
      canaryValue: canaryVal,
      baselineValue: baselineVal,
      deviation,
      critical: metric === 'error_rate' || metric === 'latency_p99',
      result: Math.abs(deviation) <= thresholds[metric] ? 'pass' : 'fail',
    };
  });

  const criticalFailed = results.some((r) => r.critical && r.result === 'fail');
  const passRate = results.filter((r) => r.result === 'pass').length / results.length;

  return {
    score: passRate * 100,
    verdict: criticalFailed ? 'fail' : passRate >= 0.8 ? 'pass' : 'inconclusive',
    metricResults: results,
  };
};

CI/CD 流水线集成
将金丝雀部署集成到 CI/CD 流水线中，实现从代码合并到生产灰度的全自动化。


jobs:
  deploy-canary:
    runs-on: ubuntu-latest
    environment: production-canary
    steps:
      - name: Deploy canary
        run: |
          kubectl set image deployment/app-canary app=registry.io/app:${{ github.sha }}
          kubectl rollout status deployment/app-canary --timeout=300s

      - name: Set initial weight
        run: |
          kubectl patch virtualservice app-canary --type=merge -p '{
            "spec": {"http": [{"route": [
              {"destination": {"host": "app-stable"}, "weight": 95},
              {"destination": {"host": "app-canary"}, "weight": 5}
            ]}]}
          }'

      - name: Wait and analyze (5 min)
        run: |
          sleep 300
          ERROR_RATE=$(curl -s "http://prometheus:9090/api/v1/query?query=rate(http_errors[5m]){version='canary'}" | jq '.data.result[0].value[1]')
          if (( $(echo "$ERROR_RATE > 0.01" | bc -l) )); then
            echo "Canary failed: error rate $ERROR_RATE"
            exit 1
          fi

      - name: Promote to 50%
        run: |
          kubectl patch virtualservice app-canary --type=merge -p '{
            "spec": {"http": [{"route": [
              {"destination": {"host": "app-stable"}, "weight": 50},
              {"destination": {"host": "app-canary"}, "weight": 50}
            ]}]}
          }'

      - name: Full promotion
        run: |
          kubectl set image deployment/app-stable app=registry.io/app:${{ github.sha }}
          kubectl rollout status deployment/app-stable --timeout=300s
前端金丝雀实践
前端应用的金丝雀部署有其特殊性——静态资源通过 CDN 分发，流量路由通常在服务端或边缘节点完成。


常见的前端金丝雀方案是HTML 入口文件路由：CDN 缓存静态资源（JS/CSS），但 HTML 文件不缓存或短缓存，由边缘函数根据灰度规则返回不同版本的 HTML（指向不同的 JS Bundle）。


interface FrontendCanaryConfig {
  stableAssetPrefix: string;
  canaryAssetPrefix: string;
  canaryPercentage: number;
  stickySession: boolean;
  cookieName: string;
}

const edgeRouter = (request: Request, config: FrontendCanaryConfig): Response => {
  const cookie = parseCookie(request.headers.get('cookie') ?? '');
  let isCanary = cookie[config.cookieName] === 'canary';

  if (!cookie[config.cookieName]) {
    isCanary = Math.random() * 100 < config.canaryPercentage;
  }

  const assetPrefix = isCanary ? config.canaryAssetPrefix : config.stableAssetPrefix;
  const html = generateHTML(assetPrefix);

  const response = new Response(html, {
    headers: { 'Content-Type': 'text/html' },
  });

  if (config.stickySession) {
    response.headers.set('Set-Cookie', `${config.cookieName}=${isCanary ? 'canary' : 'stable'}; Path=/; Max-Age=3600`);
  }

  return response;
};
小结
    

  • 金丝雀部署通过渐进式流量暴露（1% → 5% → 25% → 50% → 100%）最小化风险
    • 

  • 自动化金丝雀分析（ACA）通过统计比较金丝雀和基准指标来决定升级或回滚
    • 

  • 流量路由支持权重、Header、地域、用户 ID 等多种维度
    • 

  • 关键指标是错误率和 P99 延迟——超阈值即自动回滚
    • 

  • 前端金丝雀通过 HTML 入口文件路由 + CDN 静态资源分发实现
    •
