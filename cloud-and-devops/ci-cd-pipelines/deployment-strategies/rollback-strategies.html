回滚策略

核心概念

回滚（Rollback）是生产环境的最后一道安全防线。当部署导致故障时，能否在分钟内恢复到已知良好的状态，直接决定了事故的影响范围。回滚策略的设计目标不是"避免问题"（那是测试和灰度的工作），而是当问题不可避免地发生时，最快速、最安全地恢复服务。

graph TD
    A[部署完成] --> B[监控指标]
    B --> C{异常检测}
    C -->|正常| D[持续监控]
    C -->|异常| E{回滚决策}
    E -->|自动回滚| F[执行回滚]
    E -->|人工确认| G[通知值班]
    G --> H{确认回滚?}
    H -->|是| F
    H -->|否| I[继续观察]
    F --> J[验证恢复]
    J --> K[事后分析]
回滚类型 恢复时间 适用场景 数据风险 自动化程度
容器镜像回滚 30s-2min 无状态服务 无 全自动
蓝绿切换回滚 5-10s 蓝绿部署 无 全自动
Git Revert + 部署 5-15min 代码级回滚 无 半自动
数据库回滚 10min-1h 有状态变更 高风险 手动
功能开关关闭 < 1s 功能级回滚 无 全自动
CDN 缓存回滚 1-5min 前端资源 无 全自动

即时回滚机制

最快的回滚是不需要重新部署的回滚。这需要在部署架构中预先构建回滚能力。

容器镜像回滚：Kubernetes 的 rollout undo 命令将 Deployment 回滚到上一个 ReplicaSet，不需要重新构建或推送镜像。

jobs:
  rollback:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Rollback deployment
        run: |
          kubectl rollout undo deployment/app-production
          kubectl rollout status deployment/app-production --timeout=300s

      - name: Verify rollback
        run: |
          CURRENT_IMAGE=$(kubectl get deployment/app-production -o jsonpath='{.spec.template.spec.containers[0].image}')
          echo "Rolled back to: $CURRENT_IMAGE"

          HEALTH=$(curl -sf https://app.example.com/health | jq -r '.status')
          if [ "$HEALTH" != "ok" ]; then
            echo "Health check failed after rollback!"
            exit 1
          fi

      - name: Notify
        uses: actions/github-script@v7
        with:
          script: |
            await github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: '🔴 Production Rollback Executed',
              body: `Deployment was rolled back.\nTriggered by: @${{ github.actor }}\nTime: ${new Date().toISOString()}`,
              labels: ['incident', 'rollback']
            })
interface RollbackTarget {
  type: 'previous' | 'specific-version' | 'last-known-good';
  version?: string;
  revision?: number;
}

interface RollbackExecution {
  target: RollbackTarget;
  startedAt: Date;
  completedAt?: Date;
  healthCheckPassed: boolean;
  rollbackReason: string;
  triggeredBy: 'automatic' | 'manual';
  notificationsSent: string[];
}

const executeRollback = async (target: RollbackTarget, reason: string): Promise<RollbackExecution> => {
  const execution: RollbackExecution = {
    target,
    startedAt: new Date(),
    healthCheckPassed: false,
    rollbackReason: reason,
    triggeredBy: 'automatic',
    notificationsSent: [],
  };

  switch (target.type) {
    case 'previous':
      await kubectl('rollout', 'undo', 'deployment/app-production');
      break;
    case 'specific-version':
      await kubectl('set', 'image', 'deployment/app-production', `app=${target.version}`);
      break;
    case 'last-known-good':
      const lkg = await getLastKnownGoodVersion();
      await kubectl('set', 'image', 'deployment/app-production', `app=${lkg}`);
      break;
  }

  await kubectl('rollout', 'status', 'deployment/app-production', '--timeout=300s');
  execution.healthCheckPassed = await verifyHealth();
  execution.completedAt = new Date();

  return execution;
};

功能开关回滚

功能开关（Feature Flag）是最优雅的回滚机制——无需重新部署，无需重启服务，毫秒级生效。它将"部署"和"发布"解耦：代码部署到生产环境但功能默认关闭，通过开关逐步开放给用户。

interface FeatureFlag {
  key: string;
  defaultValue: boolean;
  targeting: TargetingRule[];
  killSwitch: boolean;
  staleAfterDays: number;
}

interface TargetingRule {
  conditions: Condition[];
  percentage: number;
  value: boolean;
}

const featureFlags: FeatureFlag[] = [
  {
    key: 'new-checkout-flow',
    defaultValue: false,
    targeting: [
      {
        conditions: [{ attribute: 'user.group', operator: 'in', values: ['beta'] }],
        percentage: 100,
        value: true,
      },
      {
        conditions: [],
        percentage: 5,
        value: true,
      },
    ],
    killSwitch: false,
    staleAfterDays: 30,
  },
];

const isEnabled = (flagKey: string, context: EvaluationContext): boolean => {
  const flag = featureFlags.find((f) => f.key === flagKey);
  if (!flag || flag.killSwitch) return false;

  for (const rule of flag.targeting) {
    if (matchesConditions(rule.conditions, context)) {
      return Math.random() * 100 < rule.percentage ? rule.value : flag.defaultValue;
    }
  }

  return flag.defaultValue;
};

功能开关的回滚只需要一步：将 killSwitch 设为 true，或将 percentage 设为 0。这比任何部署级回滚都快。

graph LR
    A[功能开关控制面板] --> B{Kill Switch}
    B -->|OFF| C[正常评估规则]
    B -->|ON| D[立即关闭功能]
    C --> E{百分比规则}
    E -->|命中| F[返回 true]
    E -->|未命中| G[返回 false]

前端回滚策略

前端回滚有其特殊挑战：静态资源通过 CDN 全球分发，浏览器可能缓存了旧版本的 JS/CSS，而 HTML 入口文件指向了新版本的资源。

多版本共存是前端回滚的基础。部署时不删除旧版本的资源，新旧版本的 JS/CSS 同时存在于 CDN 上：

interface FrontendRollbackConfig {
  retainVersions: number;
  cdnPurgeTimeout: number;
  htmlCacheControl: string;
  assetCacheControl: string;
}

const config: FrontendRollbackConfig = {
  retainVersions: 5,
  cdnPurgeTimeout: 120,
  htmlCacheControl: 'no-cache, no-store, must-revalidate',
  assetCacheControl: 'public, max-age=31536000, immutable',
};

回滚步骤：

  1. 将 HTML 入口文件回指到上一个版本的 asset hash
  2. 清除 CDN 上 HTML 的缓存（资源文件不需要清除，因为它们是内容寻址的）
  3. 等待 CDN 缓存传播（通常 1-5 分钟）
- name: Rollback frontend
  run: |
    PREVIOUS_VERSION=$(cat .deploy/versions.json | jq -r '.[-2].hash')
    aws s3 cp "s3://assets/${PREVIOUS_VERSION}/index.html" "s3://website/index.html" \
      --cache-control "no-cache, no-store, must-revalidate"
    aws cloudfront create-invalidation \
      --distribution-id $CDN_ID \
      --paths "/index.html"

回滚演练与就绪

回滚策略只有在经过演练后才是可信的。团队应该定期在非生产环境执行回滚演练，验证回滚流程的有效性。

演练项目 频率 验证内容 成功标准
容器回滚 月度 rollout undo 执行成功 < 2min 恢复
数据库回滚 季度 迁移回滚脚本可用 数据一致性
功能开关回滚 月度 Kill switch 立即生效 < 1s 生效
CDN 回滚 月度 缓存清除正确 < 5min 传播
全链路回滚 半年 端到端恢复 < 10min 恢复 
interface RunbookStep {
  order: number;
  action: string;

小结

  • 回滚是生产环境的最后安全防线，设计目标是最快速、最安全地恢复服务
  • 容器镜像回滚（rollout undo）和蓝绿切换是最快的基础设施级回滚
  • 功能开关是最优雅的回滚——毫秒级生效，将"部署"和"发布"解耦
  • 前端回滚基于多版本共存 + CDN 缓存清除，HTML 不缓存是关键
  • 回滚策略必须经过定期演练才可信——未演练的回滚计划等于没有计划
