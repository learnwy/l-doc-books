Part VII · 数据与伸缩数据平台工程 简介数据平台架构 简介数据网格与联邦

数据网格与联邦

概述

数据网格（Data Mesh）是由 Zhamak Dehghani 于 2019 年提出的数据架构范式，它将领域驱动设计（DDD）的思想应用于数据平台，主张将数据所有权从集中式数据团队下放到各业务领域团队。这一理念挑战了过去二十年集中式数据仓库的正统模式，引发了数据工程社区的深刻反思。

传统集中式数据平台的根本问题在于组织可扩展性瓶颈：当数据消费者从几十人增长到数千人时，中央数据团队成为系统性瓶颈。他们既要理解所有业务域的语义，又要构建和维护所有数据管道，这种模式在组织规模增长时必然崩溃。

四大核心原则

领域所有权（Domain Ownership）

数据由产生它的业务域团队拥有和管理。每个域团队不仅负责运营系统，也负责将自身数据以高质量数据产品的形式对外发布。

领域分解的典型模式：

  • 源端对齐域（Source-aligned）：与产生数据的系统对齐，如订单域、用户域
  • 聚合域（Aggregate）：跨多个源域组合数据，如客户 360 视图
  • 消费端对齐域（Consumer-aligned）：为特定消费场景优化，如营销分析域

数据即产品（Data as a Product）

每个域发布的数据必须满足产品化标准：

维度 要求
可发现 在数据目录中注册，有清晰的文档和示例
可寻址 有唯一标识符和稳定的访问地址
可信赖 有 SLA 保证，包含质量指标和数据契约
自描述 Schema 定义、语义标注、血缘信息内嵌
可互操作 遵循全局约定的格式和命名规范
安全可控 内建访问控制和数据分类标签

数据产品思维的关键转变：数据团队从"内部服务提供者"变为"产品团队"，数据消费者是其用户，产品质量由消费者满意度衡量。

自助式数据平台（Self-serve Data Platform）

为领域团队提供通用的数据基础设施能力，降低构建数据产品的门槛：

┌─────────────────────────────────────────────────┐
│           自助式数据平台                          │
├─────────────────────────────────────────────────┤
│  存储层：对象存储 + 表格式 + Schema Registry     │
│  计算层：Spark/Flink 集群 + SQL 引擎            │
│  管道层：编排框架 + CDC 连接器 + 模板            │
│  治理层：目录 + 血缘 + 访问控制 + 质量监控       │
│  体验层：CLI + SDK + 开发者门户                  │
└─────────────────────────────────────────────────┘
         ↑           ↑           ↑
     订单域团队   用户域团队   支付域团队

平台团队的职责从"建管道"变为"建平台"——提供声明式 API、模板和自动化工具，使领域团队能够自主发布数据产品。

联邦式计算治理（Federated Computational Governance）

治理策略通过代码和自动化嵌入平台，而非依赖人工审批流程：

  • 全局策略：数据分类标准、命名规范、SLA 等级定义
  • 自动化执行：策略编码为平台能力，自动检测违规
  • 联邦协作：域代表组成治理委员会，协商全局标准
  • 合规即代码：隐私标注、数据保留等规则自动化执行

联邦查询架构

数据网格中，数据物理上分散在各域的存储中。联邦查询提供跨域数据访问能力：

查询联邦模式

虚拟化方式：通过联邦查询引擎在查询时跨源访问数据

  • Trino/Presto：支持数十种数据源的连接器
  • Dremio：反射（Reflection）机制加速虚拟化查询
  • Starburst Galaxy：企业级 Trino 托管服务

物化方式：将跨域数据预先物化到统一存储

  • 消费端域团队构建聚合管道
  • 通过数据契约保证上游变更不破坏下游
  • 物化刷新频率根据 SLA 要求决定

数据产品接口

每个数据产品对外暴露标准化接口：

# data-product.yaml - 订单域数据产品定义
apiVersion: dataproduct/v1
metadata:
  name: orders-completed
  domain: order-management
  owner: order-team@company.com
spec:
  schema:
    format: iceberg
    location: s3://order-domain/products/orders-completed/
    catalog: unity-catalog
  sla:
    freshness: 15min
    availability: 99.9%
  quality:
    completeness: '> 99.5%'
    uniqueness: 'order_id is unique'
  access:
    classification: internal
    policy: row-level-security(region)

实施路径

第一阶段：域识别与团队对齐

  1. 分析现有数据资产，识别自然的域边界
  2. 确定每个域的数据产品负责人
  3. 评估团队能力差距，制定赋能计划

第二阶段：平台能力建设

  1. 构建自助式数据平台的核心能力
  2. 提供数据产品模板和 SDK
  3. 建立数据目录和发现机制
  4. 实现自动化治理策略

第三阶段：渐进式迁移

  1. 选择 1-2 个成熟域作为试点
  2. 将已有数据管道迁移为域数据产品
  3. 验证跨域查询和数据消费链路
  4. 总结经验后逐步推广

第四阶段：生态成熟

  1. 建立数据产品市场（Marketplace）
  2. 度量数据产品的消费量和满意度
  3. 持续优化平台能力和治理规则
  4. 培育数据驱动的组织文化

挑战与批判

数据网格并非适用于所有组织，它面临的主要挑战：

组织就绪度

数据网格本质上是一种组织架构变革，而非纯技术方案。它要求：

  • 各业务团队有意愿和能力承担数据责任
  • 管理层支持长期投入（通常 18-36 个月见效）
  • 组织文化鼓励跨团队协作和知识共享

重复建设风险

去中心化可能导致各域重复构建相似能力。平台团队需要持续抽象共性需求，将其下沉为平台能力。如果平台抽象不足，各域会各自造轮子；如果抽象过度，又会失去灵活性。

全局一致性

跨域数据一致性是分布式数据所有权的固有挑战。解决方案包括：

  • 全局实体标识符标准（如统一的用户 ID 生成策略）
  • 参考数据管理（Reference Data）集中维护
  • 最终一致性模型 + 数据契约保证

人才模型

数据网格要求领域团队具备数据工程能力，这对人才招聘和培养提出更高要求。组织需要在集中式数据专家团队与嵌入式领域数据工程师之间找到平衡。

与相关范式的关系

范式 核心关注点 与数据网格的关系
数据仓库 集中式存储与分析 可作为消费端域的实现方式
数据湖 灵活存储 可作为域存储的底层
Data Fabric 智能元数据层 互补：Fabric 提供技术自动化，Mesh 提供组织模式
湖仓一体 统一湖仓 可作为自助式平台的存储层

适用性判断

数据网格适合以下组织画像：

  • 数据团队超过 30 人且仍在增长
  • 业务域清晰且相对独立
  • 集中式模式已出现明显瓶颈
  • 组织文化支持分布式决策

对于数据团队少于 10 人的组织，集中式架构仍然是更高效的选择。数据网格的核心价值在组织规模足够大时才能体现。
