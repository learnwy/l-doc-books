湖仓一体架构

概述

湖仓一体（Lakehouse）是将数据湖的灵活性与数据仓库的可靠性融合为一体的新一代数据架构。它直接在低成本对象存储之上构建 ACID 事务、Schema 管理和高性能查询能力，打破了过去十年数据湖与数据仓库各自为政的割裂局面。

传统架构中，组织通常需要维护两套系统：数据湖存储原始数据供 ML/AI 使用，数据仓库存储结构化数据供 BI 分析。这带来了数据冗余、一致性问题和双倍的运维成本。湖仓一体的核心承诺是：一份数据，多种工作负载。

从两层到一层的演进

传统两层架构的问题

源系统 → 数据湖（原始存储） → 数据仓库（分析服务）
                ↓                        ↓
          ML/AI 工作负载            BI/报表工作负载

这种架构存在根本性缺陷：

  • 数据重复：同一份数据在湖和仓中各存一份，ETL 管道负责同步
  • 一致性风险：湖和仓之间的 ETL 延迟导致数据快照不一致
  • 治理割裂：两套系统各有独立的权限模型和审计日志
  • 成本翻倍：存储和计算资源均需双重投入

湖仓一体架构

源系统 → 对象存储（Open Table Format）
              ↓
     ┌────────┼────────┐
     ↓        ↓        ↓
   BI 引擎  ML 引擎  流处理

通过在对象存储之上引入事务层，湖仓一体实现了：

  • ACID 事务保证数据一致性
  • Schema 演进支持结构化管理
  • 时间旅行支持历史数据访问
  • 多引擎并发读写同一份数据

三大开放表格式

Delta Lake

Delta Lake 由 Databricks 开源，是湖仓一体概念的首个工业级实现。它基于 Parquet 文件格式，通过事务日志（_delta_log/）实现 ACID 语义。

核心机制：

  • 事务日志：每次写入生成一个 JSON 日志文件，记录添加和删除的文件
  • 乐观并发控制：多写者通过文件重命名实现无锁并发
  • 检查点：定期将日志合并为 Parquet 格式的检查点，加速元数据读取
  • Z-Order 聚类：通过多维排序优化数据局部性
# Delta Lake 写入示例（PySpark）
df.write \
  .format("delta") \
  .mode("overwrite") \
  .partitionBy("event_date") \
  .option("overwriteSchema", "true") \
  .save("s3://lakehouse/events/")

# 时间旅行查询
spark.read \
  .format("delta") \
  .option("timestampAsOf", "2024-01-01") \
  .load("s3://lakehouse/events/")

Apache Iceberg

Iceberg 由 Netflix 设计并捐赠给 Apache 基金会，以其优雅的分层元数据设计著称。它引入了 Catalog → Metadata File → Manifest List → Manifest File → Data File 的五层结构。

核心优势：

特性 实现方式
隐藏分区 分区转换函数对用户透明，查询无需感知分区字段
Schema 演进 通过 ID 映射字段，列重命名、添加、删除不影响历史数据
快照隔离 读写操作基于不同快照，互不干扰
分区演进 可在线变更分区策略，历史数据无需重写
行级删除 Position Delete 和 Equality Delete 两种模式

Iceberg 的隐藏分区是其最具创新性的设计。例如，对时间戳字段 event_ts 定义 hours(event_ts) 分区转换，查询 WHERE event_ts BETWEEN ... 时引擎自动利用分区裁剪，用户完全无需在 SQL 中指定分区列。

Apache Hudi

Hudi（Hadoop Upserts Deletes Incrementals）由 Uber 开源，专注于增量数据处理和 CDC 场景。它提供两种表类型：

  • Copy-on-Write（COW）：写时合并，读取性能最优，适合读多写少场景
  • Merge-on-Read（MOR）：写入追加日志，读时合并，适合写密集型场景

Hudi 的独特价值在于其增量查询能力——只返回上次查询以来变更的数据，非常适合构建增量 ETL 管道。

关键技术能力

ACID 事务

三大格式均基于乐观并发控制实现事务：

  1. 写者读取当前表状态
  2. 在本地完成数据文件写入
  3. 尝试原子性地提交元数据变更
  4. 若冲突则重试（Delta/Iceberg）或回退（Hudi）

这种设计在对象存储上实现了类似数据库的事务保证，但不依赖分布式锁服务。

时间旅行

时间旅行允许用户查询表的历史版本：

  • 审计与合规：追溯任意时间点的数据状态
  • 数据修复：发现错误后回滚到正确版本
  • ML 可复现：使用特定快照重新训练模型
  • 增量处理：基于两个快照间的差异构建管道

存储优化

湖仓需要持续优化底层文件布局：

  • 小文件合并（Compaction）：合并大量小文件为少量大文件，减少元数据开销
  • 排序优化：按查询模式重新组织数据排列，提升扫描效率
  • 过期快照清理：删除不再需要的历史版本，释放存储空间
  • 孤儿文件清理：删除未被任何快照引用的数据文件

格式选型对比

维度 Delta Lake Iceberg Hudi
社区生态 Databricks 主导 厂商中立 Uber 主导后逐步社区化
元数据设计 事务日志（扁平） 分层元数据树 Timeline + File Groups
分区演进 需重写数据 原生支持 需重写数据
并发写入 乐观锁 + 文件重命名 乐观锁 + 重试 MVCC
增量查询 Change Data Feed Incremental Scan 原生增量查询
引擎兼容性 Spark 最优，逐步开放 广泛（Spark/Flink/Trino/...） Spark/Flink
流式写入 Structured Streaming Flink Sink Flink/Spark Streaming

选型建议：

  • 已深度使用 Databricks → Delta Lake 是自然选择
  • 多引擎环境 + 复杂分区需求 → Iceberg 的开放性和分区演进最合适
  • CDC + 高频 Upsert 场景 → Hudi 的 MOR 表类型和增量查询能力最强

实际落地挑战

计算引擎适配

不同查询引擎对三大格式的支持程度参差不齐。虽然趋势是趋同，但在细节特性上（如行级删除的读取支持、时间旅行 API）仍有差异。组织需要在选型阶段评估自身引擎生态的兼容性。

元数据规模

当表包含数十亿个文件时，元数据管理本身成为瓶颈。Iceberg 的分层设计在超大规模表上优势明显，但也需要定期执行 Expire Snapshots 和 Rewrite Manifests 操作。

运维复杂性

湖仓一体并非"免运维"——小文件合并、排序优化、快照清理等后台操作需要合理调度。组织需要建立自动化维护流程，或采用 Databricks/Tabular 等托管服务。

未来方向

湖仓一体正在向更深层次演进：

  1. 格式统一趋势：Delta Lake 开放 UniForm 兼容 Iceberg 读取，Apache XTable 提供格式互转
  2. 流批一体：表格式原生支持流式读写，模糊批与流的边界
  3. AI Lakehouse：集成向量索引和特征存储，直接支持 ML 工作负载
  4. 声明式表管理：自动化的布局优化、分区演进和容量规划
