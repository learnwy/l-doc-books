Part VII · 数据与伸缩数据平台工程 简介采集与处理 简介ETL/ELT 编排

ETL/ELT 编排

概述

数据管道编排是连接数据平台各组件的"神经系统"，负责协调数据提取、转换和加载任务的执行顺序、依赖关系和失败恢复。一个成熟的数据平台可能运行着数千个相互依赖的任务，每天按照精确的拓扑顺序执行。编排系统的可靠性和可观测性直接决定了数据交付的及时性和准确性。

从 ETL 到 ELT 的范式转变不仅改变了数据处理的位置，也深刻影响了编排系统的设计理念——从重量级的全流程管控，转向轻量级的任务协调和数据就绪事件驱动。

ETL 与 ELT 范式对比

传统 ETL

源系统 → Extract → Transform → Load → 数据仓库
         (提取)    (在管道中转换)  (加载)

ETL 将转换逻辑内嵌在管道中，通常使用专用 ETL 工具（Informatica、Talend、DataStage）实现。转换在数据仓库外部完成，需要独立的计算资源。

局限性：

  • 转换逻辑与 ETL 工具深度耦合，难以版本控制
  • 调试困难：中间状态不可查询
  • 扩展成本高：ETL 服务器需要独立的计算资源

现代 ELT

源系统 → Extract → Load → Transform（在仓库内）
         (提取)   (原样加载)  (利用仓库算力)

ELT 将原始数据先加载到目标存储，再利用数据仓库自身的计算能力完成转换。dbt 是 ELT 转换层的事实标准。

优势：

  • 原始数据完整保留，转换逻辑可随时修改和重建
  • SQL 表达转换逻辑，数据分析师可直接参与
  • 版本控制：dbt 模型纳入 Git 管理
  • 利用弹性计算：云仓库按需扩展转换负载

编排系统核心概念

DAG（有向无环图）

编排的基本抽象是 DAG——任务节点和依赖边构成的有向无环图：

# Airflow DAG 示例
from airflow import DAG
from airflow.operators.python import PythonOperator
from airflow.providers.common.sql.operators.sql import SQLExecuteQueryOperator
from datetime import datetime, timedelta

default_args = {
    'retries': 3,
    'retry_delay': timedelta(minutes=5),
    'execution_timeout': timedelta(hours=2),
}

with DAG(
    'daily_user_metrics',
    default_args=default_args,
    schedule_interval='0 3 * * *',
    start_date=datetime(2024, 1, 1),
    catchup=False,
    tags=['metrics', 'daily'],
) as dag:

    extract_events = PythonOperator(
        task_id='extract_events',
        python_callable=extract_from_source,
    )

    load_raw = PythonOperator(
        task_id='load_to_raw',
        python_callable=load_to_warehouse,
    )

    transform_metrics = SQLExecuteQueryOperator(
        task_id='transform_user_metrics',
        sql='sql/user_metrics.sql',
        conn_id='snowflake_default',
    )

    validate_output = PythonOperator(
        task_id='validate_data_quality',
        python_callable=run_quality_checks,
    )

    extract_events >> load_raw >> transform_metrics >> validate_output

调度策略

策略 描述 适用场景
时间调度 按 Cron 表达式定时触发 固定频率的报表作业
数据感知调度 检测上游数据就绪后触发 依赖外部数据源的管道
事件驱动 响应外部事件（文件到达、API 回调） CDC 管道、实时 ETL
手动触发 人工或 API 触发 数据回刷、临时分析

回填（Backfill）

回填是重新处理历史时间范围数据的能力，在以下场景必不可少：

  • 转换逻辑修改后需要重算历史结果
  • 上游数据修复后需要重新处理受影响的分区
  • 新增数据管道需要补充历史数据

良好的编排系统支持声明式回填：指定时间范围，系统自动按依赖拓扑重新执行相关任务。

主流编排工具

Apache Airflow

Airflow 是目前最广泛使用的开源编排框架，拥有最大的社区和插件生态。

架构组件：

  • Scheduler：解析 DAG 文件，生成任务实例，分配执行
  • Executor：执行任务的后端（Local、Celery、Kubernetes）
  • Worker：实际运行任务的进程
  • Metadata DB：存储 DAG 定义、运行状态和日志
  • Web UI：可视化 DAG 和监控执行状态

Airflow 的核心优势是灵活性——DAG 用 Python 代码定义，可以使用任何 Python 逻辑动态生成任务。但这种灵活性也是双刃剑：DAG 解析在 Scheduler 进程中执行，复杂的动态生成逻辑可能拖慢调度性能。

Dagster

Dagster 以「Software-Defined Assets」为核心理念，将编排从"任务执行顺序"提升为"数据资产定义"：

from dagster import asset, AssetIn, DailyPartitionsDefinition

partitions = DailyPartitionsDefinition(start_date="2024-01-01")

@asset(partitions_def=partitions)
def raw_events(context):
    """从源系统提取事件数据"""
    partition_date = context.partition_key
    return extract_events(date=partition_date)

@asset(
    ins={"raw_events": AssetIn()},
    partitions_def=partitions,
)
def user_metrics(context, raw_events):
    """计算用户活跃度指标"""
    return compute_metrics(raw_events)

Dagster 的差异化价值：

  • 类型系统：资产有输入输出类型定义，编译时检查
  • 可测试性：资产函数可单独单元测试
  • 物化视图语义：声明"这个资产应该是什么"，而非"执行哪些步骤"
  • 内建 I/O 管理：资产间的数据传递由框架管理

Prefect

Prefect 以"负向工程"（Negative Engineering）为设计哲学——处理故障和异常比处理正常路径更重要：

  • 动态工作流：运行时动态决定下一步执行什么
  • 优雅的重试：细粒度的重试策略和失败处理
  • 原生异步：基于 Python asyncio 的并发执行
  • 混合执行模型：编排在云端，执行在用户基础设施

dbt（转换编排）

dbt 不是通用编排工具，但它是 ELT 转换层的标准编排方案：

  • 将 SQL 模型组织为 DAG，按依赖顺序执行
  • 增量模型减少重复计算
  • 内建测试框架验证数据质量
  • 丰富的文档生成能力

编排模式与最佳实践

分层管道设计

Bronze（原始层）: 源数据原样落地
    ↓
Silver（清洗层）: 去重、类型转换、基础质量修复
    ↓
Gold（服务层）: 业务聚合、宽表构建、指标计算

每一层有独立的 DAG，层间通过数据就绪事件触发。这种设计使得单层变更不影响其他层，回填和调试更加可控。

幂等性设计

每个任务必须是幂等的——重复执行产生相同结果：

  • 写入操作使用 INSERT OVERWRITE（覆盖分区）或 MERGE（Upsert）
  • 避免依赖全局状态（如递增计数器）
  • 使用确定性的处理逻辑（相同输入必然相同输出）

失败处理策略

# 分层重试策略示例
default_args = {
    'retries': 3,                           # 自动重试 3 次
    'retry_delay': timedelta(minutes=5),    # 每次间隔 5 分钟
    'retry_exponential_backoff': True,      # 指数退避
    'on_failure_callback': alert_oncall,    # 失败通知
}

关键原则：

  • 区分可重试错误（网络超时）和不可重试错误（Schema 不匹配）
  • 设置合理的超时时间防止任务永远挂起
  • 部分失败不阻塞不相关的下游任务

SLA 管理

为关键数据产品定义 SLA：

  • 数据新鲜度 SLA：数据在源系统产生后 N 小时内可用
  • 管道执行 SLA：DAG 在预定时间后 N 分钟内开始/完成
  • SLA 违约告警：超时自动通知 On-call 人员

可观测性

编排系统的可观测性直接影响故障定位速度：

关键指标

  • DAG 执行时间趋势：检测性能退化
  • 任务失败率：识别不稳定的管道节点
  • SLA 达成率：衡量数据交付可靠性
  • 调度延迟：Scheduler 是否成为瓶颈
  • 数据新鲜度：下游表的更新时间与预期的差异

血缘可视化

通过可视化 DAG 和数据血缘，快速定位问题的影响范围：

  • 某个源表延迟时，哪些下游报表会受影响？
  • 某个转换逻辑修改后，哪些数据产品需要回刷？
  • 当前系统中最长的关键路径是什么？

未来趋势

  1. 声明式编排：从"定义执行步骤"转向"声明目标状态"，系统自动推导执行计划
  2. 数据感知调度：基于数据质量信号和就绪状态触发，减少空跑和脏数据传播
  3. 统一编排平面：跨 Spark、Flink、dbt 等异构引擎的统一调度和监控
  4. AI 辅助运维：利用历史运行数据预测 SLA 风险，自动调整资源分配
