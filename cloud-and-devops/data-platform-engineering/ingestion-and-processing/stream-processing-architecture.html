流处理架构

概述

流处理架构处理无界的、持续到达的数据流，为应用提供毫秒到秒级延迟的实时计算能力。在用户行为分析、欺诈检测、实时推荐和物联网监控等场景中，批处理的分钟到小时级延迟已无法满足业务需求。流处理引擎在数据到达的瞬间就开始计算，将结果实时推送给下游系统。

流处理的核心复杂性在于：数据是无序的、可能重复的、随时可能中断的。引擎必须在这些不确定性下保证计算结果的正确性和完整性。

流处理核心概念

时间语义

流处理中时间有三层含义：

  • 事件时间（Event Time）：事件实际发生的时间，由数据源端产生
  • 摄入时间（Ingestion Time）：数据进入流处理系统的时间
  • 处理时间（Processing Time）：引擎实际处理数据的时间

事件时间是语义上最正确的选择，但引入了乱序处理的复杂性——后到达的数据可能携带更早的事件时间。

窗口（Window）

窗口将无界流切分为有限大小的数据块进行聚合计算：

窗口类型 描述 适用场景
滚动窗口（Tumbling） 固定大小，无重叠 每分钟 PV 统计
滑动窗口（Sliding） 固定大小，有重叠 5分钟内滚动平均
会话窗口（Session） 按活动间隙动态划分 用户会话分析
全局窗口（Global） 所有数据在一个窗口 配合触发器使用

水位线（Watermark）

水位线是流处理系统对事件时间进度的估计，它告诉系统"时间戳小于 W 的数据应该都已到达"。水位线决定了窗口何时关闭并输出结果。

水位线策略的权衡：

  • 保守水位线（大延迟容忍）：等待更长时间，数据更完整，但结果延迟高
  • 激进水位线（小延迟容忍）：快速产出结果，但可能丢失迟到数据
  • 启发式水位线：根据历史延迟分布动态调整

处理语义保证

级别 含义 实现成本
At-most-once 数据最多处理一次（可能丢失） 最低
At-least-once 数据至少处理一次（可能重复） 中等
Exactly-once 数据恰好处理一次（不丢不重） 最高

Exactly-once 是生产环境的默认要求，其实现通常依赖分布式快照（Checkpoint）和事务性 Sink。

核心引擎架构

Apache Flink

Flink 是当前最强大的流处理引擎，以其低延迟、高吞吐和精确一次语义著称。

架构分层：

┌─────────────────────────────────────────┐
│        SQL/Table API                     │
├─────────────────────────────────────────┤
│        DataStream API                    │
├─────────────────────────────────────────┤
│     Runtime（流式执行引擎）               │
│  ┌─────────┬───────────┬──────────────┐ │
│  │ 状态后端 │ Checkpoint │ 网络传输层  │ │
│  └─────────┴───────────┴──────────────┘ │
├─────────────────────────────────────────┤
│     部署层（K8s / YARN / Standalone）    │
└─────────────────────────────────────────┘

Flink 的关键设计决策：

异步屏障快照（Asynchronous Barrier Snapshotting）：基于 Chandy-Lamport 算法，在不停止处理的情况下获取全局一致快照。Checkpoint Barrier 在数据流中传播，算子收到所有输入的 Barrier 后保存状态。

分层状态管理：

  • MemoryStateBackend：小状态，低延迟
  • HashMapStateBackend：中等状态，堆内管理
  • RocksDBStateBackend：大状态（TB级），磁盘存储，支持增量 Checkpoint
// Flink SQL 流处理示例
tableEnv.executeSql("""
  CREATE TABLE orders (
    order_id STRING,
    user_id STRING,
    amount DECIMAL(10,2),
    order_time TIMESTAMP(3),
    WATERMARK FOR order_time AS order_time - INTERVAL '5' SECOND
  ) WITH (
    'connector' = 'kafka',
    'topic' = 'orders',
    'properties.bootstrap.servers' = 'kafka:9092',
    'format' = 'json'
  )
""");

// 5分钟滚动窗口的实时收入统计
tableEnv.executeSql("""
  SELECT
    TUMBLE_START(order_time, INTERVAL '5' MINUTE) AS window_start,
    COUNT(*) AS order_count,
    SUM(amount) AS total_revenue
  FROM orders
  GROUP BY TUMBLE(order_time, INTERVAL '5' MINUTE)
""");

Apache Kafka Streams

Kafka Streams 是一个轻量级流处理库（非独立集群），直接嵌入应用进程：

  • 无独立集群：作为 Java 库运行在应用 JVM 中
  • 天然集成 Kafka：以 Kafka Topic 作为输入输出
  • 弹性扩展：通过消费者组机制自动分区分配
  • 本地状态存储：基于 RocksDB 的本地状态，支持交互式查询

适用场景：微服务间的事件处理、轻量级流式转换、不想运维独立流处理集群的团队。

Apache Pulsar + Pulsar Functions

Pulsar 融合了消息队列和流处理的能力：

  • 分层架构（计算层 Broker + 存储层 BookKeeper）实现独立扩展
  • 原生支持多租户和 Geo-Replication
  • Pulsar Functions 提供轻量级 Serverless 流处理

状态管理深入

状态是流处理区别于无状态转换的核心能力。有状态计算允许引擎"记住"历史信息：

状态类型

  • KeyedState：按 Key 分区的状态（如每用户的会话信息）
  • OperatorState：算子级别的全局状态（如 Kafka offset）
  • BroadcastState：广播到所有并行实例的配置状态

状态一致性

Checkpoint 机制保证状态的一致性：

  1. JobManager 定期触发 Checkpoint
  2. Barrier 注入到源算子的输出流中
  3. 算子收到所有输入流的 Barrier 后，将当前状态异步写入持久化存储
  4. 所有算子完成快照后，Checkpoint 标记为完成
  5. 故障恢复时，从最近的完成 Checkpoint 恢复所有算子状态

大状态优化

当状态规模达到 TB 级时：

  • 使用增量 Checkpoint（只上传变更的 SST 文件）
  • 开启本地状态恢复（优先从本地磁盘恢复，减少网络传输）
  • 合理设置 RocksDB 参数（Block Cache、Write Buffer 数量）
  • 考虑状态 TTL（自动清理过期状态）

端到端 Exactly-Once

实现端到端精确一次需要源、处理和目标三者协同：

源端：可重放（如 Kafka 的 offset 管理） 处理端：分布式快照保证内部状态一致性 目标端：两阶段提交（2PC）或幂等写入

Source (重放) → Checkpoint (一致状态) → Sink (事务提交)
   ↓                    ↓                     ↓
 可回溯            分布式快照            2PC/幂等

Flink 的 TwoPhaseCommitSinkFunction 提供了通用的两阶段提交抽象，支持 Kafka、JDBC 等事务性目标的精确一次写入。

流处理模式

事件驱动应用

流处理不仅用于数据分析，也用于构建事件驱动的业务应用：

  • 规则引擎：实时匹配复杂事件模式（CEP）
  • 欺诈检测：识别异常交易序列
  • 实时决策：动态定价、实时风控

流表二象性

流和表是同一数据的两种视角：

  • 流 → 表：对流应用聚合操作，结果物化为表
  • 表 → 流：表的变更日志构成一个流（CDC）

这种二象性是 Kafka Log Compaction 和 ksqlDB 的理论基础。

部署与运维

资源规划

流处理作业是长期运行的，资源规划需要考虑：

  • 峰值流量的缓冲余量（通常 2-3 倍日均）
  • 追赶积压数据的额外计算需求
  • 状态存储的增长趋势

监控指标

关键监控指标：

  • 端到端延迟：从事件产生到结果可见的时间
  • 消费延迟（Lag）：待处理的积压数据量
  • Checkpoint 耗时和大小：状态健康度的指标
  • 反压（Backpressure）：下游处理速度跟不上上游产出速度

未来趋势

  1. 流批一体成熟化：统一编程模型下批作业自动享受流处理优化
  2. Serverless 流处理：按事件计费，自动扩缩容
  3. 流式机器学习：在线学习、特征实时计算
  4. 边缘流处理：在靠近数据源的位置进行初步流式计算
