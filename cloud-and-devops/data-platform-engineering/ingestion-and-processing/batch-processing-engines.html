批处理引擎

概述

批处理引擎是数据平台中处理大规模离线计算任务的核心组件。它们在固定的时间窗口内对累积的数据集执行完整的转换、聚合和分析操作。尽管实时处理日益重要，批处理仍然承担着数据平台 80% 以上的计算工作负载——从每日报表生成到机器学习模型训练，从历史数据回刷到数据质量校验。

批处理引擎的核心挑战在于如何将 PB 级数据的处理时间压缩到可接受的时间窗口内，同时保持资源利用的经济性和故障恢复的可靠性。

MapReduce 到 Spark 的演进

MapReduce 的贡献与局限

Google 2004 年发表的 MapReduce 论文奠定了分布式批处理的基础模型。Hadoop MapReduce 实现将这一理念普及到开源世界。然而 MapReduce 有几个根本性限制：

  • 磁盘密集：每个 Map/Reduce 阶段之间的中间结果必须写入 HDFS
  • 编程模型僵化：只有 Map 和 Reduce 两个原语，复杂逻辑需要多次 Job 串联
  • 启动开销大：JVM 容器启动、数据本地化调度消耗大量时间
  • 交互分析不可行：秒级查询变成分钟级执行

Apache Spark 的突破

Spark 于 2014 年成为 Apache 顶级项目，其核心创新是弹性分布式数据集（RDD）和内存计算：

# Spark 典型批处理流程
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, sum, window

spark = SparkSession.builder \
    .appName("DailyRevenue") \
    .config("spark.sql.adaptive.enabled", "true") \
    .getOrCreate()

# 读取增量数据
orders = spark.read.format("iceberg") \
    .load("catalog.db.orders") \
    .filter(col("order_date") == "2024-01-15")

# 复杂聚合
daily_revenue = orders \
    .groupBy("region", "product_category") \
    .agg(
        sum("amount").alias("total_revenue"),
        count("order_id").alias("order_count")
    ) \
    .withColumn("avg_order_value",
                col("total_revenue") / col("order_count"))

# 写入结果表
daily_revenue.write \
    .format("iceberg") \
    .mode("overwrite") \
    .partitionBy("region") \
    .save("catalog.db.daily_revenue")

Spark 的关键技术优势：

特性 实现机制 性能影响
内存计算 RDD 缓存在内存，避免磁盘 I/O 10-100x 加速
DAG 执行 将作业编译为有向无环图，优化执行计划 消除不必要的 Shuffle
延迟计算 Transformation 不立即执行 全局优化机会
自适应执行（AQE） 运行时动态调整执行计划 解决数据倾斜

现代批处理引擎对比

Apache Spark

定位：通用分布式计算引擎，最广泛使用的批处理框架

核心模块：

  • Spark SQL：结构化数据处理，Catalyst 优化器
  • DataFrame/Dataset API：类型安全的编程接口
  • MLlib：分布式机器学习库
  • GraphX：图计算框架

部署模式：

  • Standalone：自管理集群
  • YARN：Hadoop 集成
  • Kubernetes：云原生部署，动态资源分配
  • Serverless（Databricks/EMR Serverless）：无集群管理

DuckDB

定位：嵌入式分析数据库，单机批处理的新选择

DuckDB 以"SQLite for Analytics"为设计目标，在单节点上通过向量化执行引擎实现令人惊讶的性能：

  • 进程内执行，零网络开销
  • 列式存储引擎，自动并行
  • 直接查询 Parquet/CSV/JSON 文件
  • 支持数十 GB 数据集的秒级分析

适用场景：数据量在 100GB 以内的分析任务，本地开发调试，CI/CD 中的数据验证。

Apache Flink（批模式）

Flink 虽以流处理著称，但其批处理模式同样强大。Flink 将批处理视为"有界流"的特殊情况，统一了流批编程模型。Flink 批处理的优势在于当组织已有 Flink 流处理基础设施时，可以复用相同的代码和运维体系。

Presto/Trino

定位：分布式 SQL 查询引擎，侧重交互式分析

Trino 不自己存储数据，而是通过连接器查询外部数据源。在批处理场景下，它适合：

  • 跨数据源的联邦查询
  • 中等规模（TB 级）的 ad-hoc 分析
  • 数据探索和验证

性能调优关键策略

数据倾斜处理

数据倾斜是批处理中最常见的性能杀手。当某些分区的数据量远超其他分区时，整个作业的执行时间由最慢的 Task 决定。

解决策略：

# 方式一：Spark AQE 自动倾斜处理
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256MB")

# 方式二：手动加盐（Salt）打散热点 Key
from pyspark.sql.functions import concat, lit, rand

salted_df = hot_df.withColumn(
    "salted_key",
    concat(col("join_key"), lit("_"), (rand() * 10).cast("int"))
)

Shuffle 优化

Shuffle 是网络传输和磁盘 I/O 的重灾区：

  • 减少 Shuffle 数据量：在 Shuffle 前进行 Filter 和局部聚合
  • Broadcast Join：小表广播到所有节点，避免 Shuffle
  • Bucket Join：预分桶的表直接本地 Join
  • Shuffle 压缩：启用 LZ4/Zstd 压缩减少传输量

资源配置

批处理作业的资源配置直接影响执行效率和成本：

Executor 数量 × 每个 Executor 核数 × 每个 Executor 内存 = 总资源

经验法则：

  • Executor 内存建议 4-8GB（过大触发 GC 压力）
  • 每个 Executor 4-5 核（过多导致内存竞争）
  • 并行度设置为总核数的 2-3 倍（隐藏调度延迟）

文件布局优化

底层文件的组织方式对扫描性能影响巨大：

  • 文件大小：目标 128MB-1GB，过小导致元数据开销，过大影响并行度
  • 分区策略：按查询模式选择分区字段，避免过度分区
  • 排序：在分区内按高频过滤列排序，提升 Predicate Pushdown 效率
  • 格式选择：Parquet 用于列式分析，Avro 用于写密集场景

批处理编程模型

声明式 SQL

大多数批处理任务可用 SQL 表达，这也是 dbt 成功的基础：

-- 典型增量计算模式
INSERT OVERWRITE TABLE mart.user_metrics
PARTITION (dt = '2024-01-15')
SELECT
  user_id,
  COUNT(DISTINCT session_id) AS session_count,
  SUM(page_views) AS total_page_views,
  SUM(purchase_amount) AS total_spend
FROM staging.user_events
WHERE dt = '2024-01-15'
GROUP BY user_id;

DataFrame API

当逻辑复杂度超出 SQL 表达能力时（如自定义序列化、复杂 UDF、流程控制），DataFrame API 提供更大灵活性。关键是在声明式和命令式之间找到平衡——优先用 SQL 表达，仅在必要时使用 DataFrame 操作。

调度与依赖管理

批处理作业通常以 DAG 形式组织：

  • 上游表产出后触发下游计算
  • 时间窗口对齐（日、小时、分钟粒度）
  • 失败重试和回刷能力
  • SLA 监控和告警

关键设计决策：是基于时间调度（"每天凌晨3点运行"）还是基于数据就绪事件调度（"上游表更新后触发"）。事件驱动模式能减少空等待和资源浪费，但实现复杂度更高。

未来趋势

  1. Serverless 化：完全按作业付费，消除集群管理，如 AWS EMR Serverless、Databricks Serverless
  2. 流批一体：统一编程模型下批处理成为"有界流"的特例
  3. AI 增强调优：利用历史执行数据自动优化资源配置和执行计划
  4. Rust 重写浪潮：DataFusion、Polars 等 Rust 生态引擎在性能上挑战 JVM 引擎
