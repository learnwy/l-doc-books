数据血缘与可观测性

概述

数据血缘与可观测性是数据平台从"能用"到"可信、可控"的关键跨越。数据血缘回答"数据从哪来，到哪去，经过了什么变换"；数据可观测性回答"数据管道现在健康吗，哪里出了问题"。两者共同构成了数据平台的"全链路透视"能力。

在拥有数千条管道和数万张表的数据平台中，缺乏血缘和可观测性意味着：一次上游变更可能悄无声息地破坏下游数百个报表；一条管道的静默失败可能数天后才被业务方发现；数据问题的根因定位可能需要数小时甚至数天的人工排查。

数据血缘基础

血缘图模型

数据血缘本质上是一个有向图，节点代表数据实体（表、列、任务），边代表数据流转关系：

源表A.col1 ──┐
              ├──→ 转换任务T1 ──→ 目标表C.col3
源表B.col2 ──┘

图的粒度层次：

粒度 节点类型 边含义 典型应用
数据集级 表/Topic/文件 "产出" 影响分析概览
列级 列/字段 "派生自" 精确影响分析
任务级 ETL/查询 "读取/写入" 管道依赖管理
行级 行/记录 "源自" 审计合规

列级血缘

列级血缘追踪每一列的数据来源，是影响分析中最有价值的粒度：

-- 示例：目标表 mart.user_summary
CREATE TABLE mart.user_summary AS
SELECT
  u.user_id,                              -- ← raw.users.user_id
  u.name,                                  -- ← raw.users.name
  COUNT(o.order_id) AS order_count,        -- ← raw.orders.order_id (聚合)
  SUM(o.amount) AS total_spend             -- ← raw.orders.amount (聚合)
FROM raw.users u
JOIN raw.orders o ON u.user_id = o.user_id
GROUP BY u.user_id, u.name;

列级血缘揭示：

  • mart.user_summary.total_spend 派生自 raw.orders.amount
  • 如果 raw.orders.amount 的类型从 INT 变为 DECIMAL，直接影响 total_spend

血缘采集方法

静态分析法——解析 SQL/代码的 AST 提取血缘：

优点：不需要运行作业，覆盖所有代码路径缺点：无法处理动态 SQL、UDF 内部逻辑

# sqlglot 列级血缘解析示例
import sqlglot
from sqlglot.lineage import lineage

# 解析 SQL 获取列级血缘
result = lineage(
    "total_spend",
    """
    SELECT user_id, SUM(amount) AS total_spend
    FROM orders
    GROUP BY user_id
    """,
    schema={"orders": {"user_id": "VARCHAR", "amount": "DECIMAL"}}
)
# result: orders.amount → total_spend

运行时采集法——从引擎执行日志或 Hook 中捕获实际血缘：

优点：反映真实执行路径，包含动态逻辑缺点：只能捕获已执行的路径，需要引擎支持

混合法——静态分析为基础，运行时补充动态部分（推荐实践）

血缘存储

血缘图的存储和查询需要专用的图存储或索引：

  • 图数据库（Neo4j）：原生图存储，复杂图遍历性能优秀
  • 关系型 + 递归查询：PostgreSQL 的 WITH RECURSIVE，适合中小规模
  • 专用血缘服务：OpenLineage 标准 + Marquez 后端

数据可观测性

可观测性的五大支柱

借鉴 SRE 的可观测性理念，数据可观测性关注：

  1. 新鲜度（Freshness）：表最后更新时间与预期的偏差
  2. 数据量（Volume）：行数和字节数的波动
  3. Schema：结构变更是否在预期内
  4. 分布（Distribution）：值的统计分布是否异常
  5. 血缘（Lineage）：上下游关系是否发生变化

监控指标体系

# 数据可观测性指标定义
metrics:
  freshness:
    table: mart.daily_revenue
    expected_update: '每天 06:00 前'
    alert_threshold: '延迟 > 2h'

  volume:
    table: staging.events
    baseline: '7天移动平均'
    alert_threshold: '偏差 > 30%'

  distribution:
    table: mart.orders
    column: amount
    checks:
      - 'mean 偏差 < 20%'
      - 'null 比例 < 0.1%'
      - 'max < 1,000,000'

数据 SLA

为每个关键数据产品定义 SLA：

SLA 维度 定义 度量方法
时效性 SLA 数据在 T+N 小时内可用 监控表的 updated_at
完整性 SLA 缺失率 < X% 定期完整性扫描
可用性 SLA 月度可查询时间 > 99.9% 健康检查探针
准确性 SLA 对账误差 < X% 周期性对账

OpenLineage 标准

OpenLineage 是一个开放的血缘元数据标准，定义了事件驱动的血缘上报协议：

事件模型

{
  "eventType": "COMPLETE",
  "eventTime": "2024-01-15T03:00:00Z",
  "run": {
    "runId": "run-uuid-123"
  },
  "job": {
    "namespace": "production",
    "name": "daily_user_metrics"
  },
  "inputs": [
    {
      "namespace": "production",
      "name": "staging.events",
      "facets": {
        "schema": {
          "fields": [
            { "name": "user_id", "type": "VARCHAR" },
            { "name": "event_type", "type": "VARCHAR" }
          ]
        }
      }
    }
  ],
  "outputs": [
    {
      "namespace": "production",
      "name": "mart.user_metrics",
      "facets": {
        "columnLineage": {
          "fields": {
            "active_days": {
              "inputFields": [{ "namespace": "production", "name": "staging.events", "field": "event_date" }]
            }
          }
        }
      }
    }
  ]
}

生态集成

支持 OpenLineage 的工具：

  • 引擎：Spark（OpenLineage Spark Agent）、Flink、dbt
  • 编排器：Airflow（Lineage Backend）、Dagster
  • 后端：Marquez、Atlan、DataHub

告警与响应

告警策略

分级告警避免告警疲劳：

  • P0（紧急）：关键报表 SLA 违约，影响业务决策
  • P1（高）：重要管道失败，N 小时内需修复
  • P2（中）：数据质量轻微下降，需排查
  • P3（低）：统计异常但不影响业务，周级处理

告警富化

告警不应只是"表 X 异常"，还应包含：

  • 受影响的下游表和报表列表（通过血缘图计算）
  • 可能的根因候选（通过上游血缘追溯）
  • 历史相似事件的处理方案
  • 数据所有者和 On-call 联系方式

根因分析

异常告警：mart.daily_revenue 行数下降 50%
  ↓ 血缘上溯
staging.orders 行数正常
staging.payments 今日为空
  ↓ 进一步上溯
source.payment_service CDC 管道 3:00 开始失败
  ↓ 根因
上游支付服务数据库连接池满，CDC 超时

实施路径

第一阶段：基础血缘

  1. 部署 Marquez 或 DataHub 作为血缘后端
  2. 为 Spark/Airflow 启用 OpenLineage 集成
  3. 实现表级血缘的自动采集
  4. 构建基础的影响分析 UI

第二阶段：可观测性监控

  1. 部署新鲜度和数据量监控
  2. 建立关键表的 SLA 定义
  3. 配置分级告警策略
  4. 集成到 On-call 轮值流程

第三阶段：高级能力

  1. 实现列级血缘采集
  2. 引入统计异常检测
  3. 建立自动化根因分析
  4. 构建数据健康评分体系

实践建议

  1. 先覆盖关键路径：优先对业务最核心的数据管道建立完整的血缘和监控
  2. 自动化优先：血缘采集必须自动化，手工维护的血缘信息会迅速过期
  3. 统一标准：采用 OpenLineage 等开放标准，避免被特定工具锁定
  4. 上下文丰富：告警需要包含足够的上下文信息，减少人工排查时间
  5. 持续校准：定期验证血缘数据的准确性，清理陈旧的血缘关系
