查询引擎优化

概述

查询引擎是数据平台面向用户的核心接口，它接收 SQL 查询请求并返回计算结果。一个优秀的查询引擎能在秒级内完成对数十亿行数据的复杂分析操作。查询引擎的优化贯穿从 SQL 解析到结果返回的全链路——查询计划优化决定"做什么"，执行引擎优化决定"怎么做"。

现代查询引擎（Trino、ClickHouse、DuckDB、Databricks Photon）在向量化执行、自适应优化和代码生成等方面取得了显著进展，使得交互式分析在 PB 级数据上成为现实。

查询处理流程

一条 SQL 从提交到结果返回经历以下阶段：

SQL 文本
  ↓ 解析（Parser）
AST（抽象语法树）
  ↓ 语义分析（Analyzer）
逻辑计划（Logical Plan）
  ↓ 优化器（Optimizer）
优化后逻辑计划
  ↓ 物理计划生成（Planner）
物理计划（Physical Plan）
  ↓ 执行引擎（Execution Engine）

逻辑计划优化

逻辑计划阶段关注"语义等价的最优表示"，常见优化规则：

谓词下推（Predicate Pushdown）：将过滤条件尽早应用，减少后续处理的数据量

-- 优化前：先 JOIN 再过滤
SELECT * FROM orders o JOIN users u ON o.user_id = u.id
WHERE u.country = 'CN'

-- 优化后：先过滤 users 表再 JOIN
SELECT * FROM orders o JOIN (SELECT * FROM users WHERE country = 'CN') u
ON o.user_id = u.id

投影裁剪（Projection Pruning）：只读取查询实际需要的列

常量折叠（Constant Folding）：编译时计算常量表达式

子查询解关联（Subquery Decorrelation）：将相关子查询转换为 JOIN

基于代价的优化（CBO）

CBO 依赖统计信息选择最优执行计划：

统计信息 用途
表行数 估算中间结果集大小
列 NDV（基数） 评估 JOIN 的选择性
直方图 处理数据倾斜的过滤估算
列 min/max 范围过滤的选择性估算
空值比例 NULL 处理的代价评估

CBO 的典型决策场景：

  • JOIN 顺序：多表 JOIN 时哪张表先连接（组合空间随表数指数增长）
  • JOIN 算法：Hash Join vs Sort-Merge Join vs Nested Loop
  • 聚合策略：预聚合（Partial Aggregate）+ 全局聚合 vs 直接全局聚合
  • 数据分布：是否需要重新分区（Repartition）

物理执行策略

向量化执行（Vectorized Execution）

传统火山模型（Volcano Model）逐行处理数据，函数调用开销巨大。向量化执行一次处理一批数据（通常 1024-4096 行），充分利用 CPU 缓存和 SIMD 指令：

火山模型：每行一次虚函数调用
  next() → 1 行 → next() → 1 行 → ...

向量化模型：每次处理一批
  next_batch() → 1024 行 → next_batch() → 1024 行 → ...

向量化的性能优势：

  • CPU 缓存友好：连续内存访问，减少 Cache Miss
  • SIMD 利用：单条指令处理多个数据元素
  • 减少函数调用：批次摊销虚函数开销
  • 分支预测优化：对整批数据统一处理，减少分支

代码生成（Code Generation）

编译执行通过在运行时生成特化代码消除解释开销：

  • 表达式编译：将 SQL 表达式编译为原生机器码
  • 融合算子：将多个算子融合为一个紧凑的循环
  • 类型特化：消除泛型处理的开销

Spark 的 Whole-Stage Code Generation 将整个 Pipeline（Filter → Project → Aggregate）编译为一个 Java 方法，消除了算子间的虚函数调用。

Pipeline 执行

现代引擎将执行计划分割为 Pipeline：

Pipeline 0: Scan → Filter → Project → Partial Aggregate
                                            ↓ (Shuffle/Exchange)
Pipeline 1: Final Aggregate → Sort → Output

Pipeline 内数据以推模式（Push-based）流转，减少缓冲区切换。Pipeline 边界是需要全量物化的算子（如 Sort、Hash Build 侧）。

JOIN 优化

JOIN 是查询中最昂贵的操作之一：

Hash Join

最常用的等值 JOIN 算法：

  1. Build 阶段：将小表构建为内存 Hash Table
  2. Probe 阶段：用大表逐行探测 Hash Table

优化技巧：

  • 小表放 Build 侧：减少内存占用
  • Bloom Filter 预过滤：在 Probe 前过滤掉确定不匹配的行
  • 分区 Hash Join：当两表都无法放入内存时，按 Hash 分区分别 JOIN

Sort-Merge Join

适用于两表已按 JOIN Key 排序的场景：

  • 不需要额外内存构建 Hash Table
  • 适合范围 JOIN 和不等值 JOIN
  • 可复用已有的排序（如表本身按 JOIN Key 聚类）

Broadcast Join

当一侧表足够小时，将其广播到所有计算节点：

# Spark Broadcast Join 提示
from pyspark.sql.functions import broadcast

result = large_df.join(
    broadcast(small_df),  # 小表广播
    on="key"
)

阈值设置：Spark 默认 10MB，可调整 spark.sql.autoBroadcastJoinThreshold。

自适应查询执行（AQE）

传统优化器在查询执行前做所有决策，但统计信息可能不准确。AQE 在运行时收集实际数据统计，动态调整执行计划：

Spark AQE 能力

  • 动态合并小分区：Shuffle 后过多的小分区自动合并
  • 动态切换 JOIN 策略：发现实际数据量小于阈值时切换为 Broadcast Join
  • 动态处理数据倾斜：检测到倾斜分区后自动拆分

Runtime Filter

在 JOIN 执行过程中，利用 Build 侧的信息生成运行时过滤器，反向推送到 Probe 侧的数据扫描：

Join
├─ Build: small_table (过滤后只有 100 个 key)
└─ Probe: large_table → 生成 Bloom Filter → 在扫描时跳过不匹配的分区

主流查询引擎对比

引擎 架构 执行模型 最佳场景
Trino 分布式，无存储 Pipeline + 向量化 联邦查询、交互式分析
ClickHouse 分布式，列式存储 向量化 + 稀疏索引 实时 OLAP、时序分析
DuckDB 单机嵌入式 向量化 + 并行 本地分析、嵌入应用
Spark SQL 分布式 Code Gen + AQE 大规模 ETL、ML 管道
Databricks Photon 分布式 C++ 向量化引擎 高性能 Lakehouse 查询
Apache Doris 分布式，MPP 向量化 + Pipeline 实时报表、Dashboard

性能诊断方法

EXPLAIN ANALYZE

查看实际执行计划和各算子的执行统计：

EXPLAIN ANALYZE
SELECT region, SUM(amount)
FROM orders
WHERE order_date >= '2024-01-01'
GROUP BY region;

关注指标：

  • 每个算子处理的行数 vs 预估行数（判断统计信息准确性）
  • Shuffle 的数据量（判断是否需要优化 JOIN 或聚合策略）
  • Scan 阶段跳过的行数比例（判断谓词下推效果）

查询 Profile

生产环境的查询性能分析：

  • 执行时间分解（扫描、计算、网络、序列化）
  • 内存使用峰值和 Spill 情况
  • 并行度利用率
  • I/O 等待时间占比

实践建议

  1. 保持统计信息更新：定期执行 ANALYZE TABLE，确保 CBO 决策准确
  2. 合理设置并行度：过低浪费资源，过高增加调度和协调开销
  3. 监控 Spill：频繁 Spill 到磁盘说明内存不足，需要调整配置或优化查询
  4. 利用物化视图：对高频查询模式预计算结果，换取查询延迟降低
  5. 分区裁剪验证：确认查询条件能有效利用分区字段，避免全表扫描
