Part VII · 数据与伸缩数据平台工程 简介存储与查询 简介列式存储格式

列式存储格式

概述

列式存储格式是现代数据分析系统的基石技术。与传统行式存储按记录组织数据不同，列式格式将同一列的所有值连续存放，使得分析查询只需读取涉及的列而跳过其余列。在典型的 OLAP 场景中，一条查询通常只访问表中 5-10% 的列，列式存储能减少 90% 以上的 I/O，同时同一列的相似值聚集在一起为高效压缩创造了条件。

Apache Parquet、Apache ORC 和 Arrow IPC 是当前最重要的三种列式格式，它们各自在不同生态中占据主导地位，理解其设计取舍对数据平台的性能优化至关重要。

列式 vs 行式存储

数据组织对比

假设一张表有 4 列（id, name, age, city），5 行数据：

行式存储（逻辑布局）：

[1, "Alice", 30, "Beijing"] [2, "Bob", 25, "Shanghai"] [3, "Carol", 28, "Shenzhen"] ...

列式存储（逻辑布局）：

id:   [1, 2, 3, 4, 5]
name: ["Alice", "Bob", "Carol", "Dave", "Eve"]
age:  [30, 25, 28, 35, 22]
city: ["Beijing", "Shanghai", "Shenzhen", "Beijing", "Guangzhou"]

性能特征对比

操作 行式优势 列式优势
单行查询 WHERE id=3 ✓ 一次读取获取完整记录 需要跨列拼接
聚合查询 AVG(age) 需读取所有列 ✓ 只读 age 列
全表扫描 顺序 I/O ✓ 列裁剪 + 压缩
插入单条记录 ✓ 追加到末尾 需要向每列追加
压缩率 一般（混合类型） ✓ 极高（同类型数据）

Apache Parquet

Parquet 是 Hadoop 生态中最广泛使用的列式格式，由 Twitter 和 Cloudera 联合开发。它是 Spark、Hive、Impala、Presto 等几乎所有大数据引擎的首选格式。

文件结构

┌─────────────────────────────────┐
│         Magic Number            │
├─────────────────────────────────┤
│       Row Group 0               │
│  ┌─────────────────────────┐    │
│  │ Column Chunk (col_a)    │    │
│  │  ├─ Page 0 (Data Page) │    │
│  │  ├─ Page 1 (Data Page) │    │
│  │  └─ Page 2 (Dict Page) │    │
│  ├─────────────────────────┤    │
│  │ Column Chunk (col_b)    │    │
│  │  └─ ...                 │    │
│  └─────────────────────────┘    │
├─────────────────────────────────┤
│       Row Group 1               │
│  └─ ...                         │
├─────────────────────────────────┤
│       Footer                    │
│  ├─ File Metadata              │
│  │   ├─ Schema                 │
│  │   ├─ Row Group Metadata     │
│  │   └─ Column Statistics      │
│  └─ Footer Length              │
├─────────────────────────────────┤
│         Magic Number            │
└─────────────────────────────────┘

关键设计决策：

  • Row Group：一组行的列式分块，是 I/O 并行的基本单位（建议 128MB-1GB）
  • Column Chunk：一个 Row Group 内某一列的数据，连续存储
  • Page：Column Chunk 内的数据页，是压缩和编码的基本单位（建议 1MB）
  • Footer 在尾部：写入时追加式，读取时先读尾部元数据

编码策略

Parquet 支持多种编码方式，针对不同数据分布自动选择：

编码 适用场景 压缩效果
Dictionary Encoding 低基数列（如国家、状态码） 极高（字典 + 整数索引）
Run-Length Encoding (RLE) 排序后的连续重复值 高
Delta Encoding 有序数值列（如时间戳） 高
Bit Packing 小范围整数 中等
Plain 无特征数据 依赖压缩算法

谓词下推与列裁剪

Parquet 的统计信息支持两层过滤：

  1. Row Group 级过滤：Footer 中的 min/max 统计可以跳过整个 Row Group
  2. Page 级过滤（Parquet 2.0+）：Column Index 支持 Page 粒度的跳过
# 列裁剪 + 谓词下推示例
df = spark.read.parquet("s3://data/events/") \
    .select("user_id", "event_type", "timestamp") \  # 列裁剪：只读 3 列
    .filter(col("timestamp") > "2024-01-01")          # 谓词下推：跳过不匹配的 Row Group

Apache ORC

ORC（Optimized Row Columnar）由 Hortonworks 开发，在 Hive 生态中占据主导地位。与 Parquet 相比，ORC 在某些方面有不同的设计选择。

ORC vs Parquet

维度 ORC Parquet
生态 Hive/Presto 优先 Spark/通用生态
索引 内建 Bloom Filter + 行索引 需外部实现
ACID 支持 原生（Hive ACID） 依赖表格式（Delta/Iceberg）
嵌套类型 支持但实现较简单 Dremel 风格，对嵌套支持更优
压缩 默认 Zlib/Snappy 默认 Snappy/Zstd
谓词下推 Stripe + Row Group 两级 Row Group + Page 两级

ORC 结构特点

ORC 引入了 Stripe 概念（对应 Parquet 的 Row Group），每个 Stripe 包含：

  • Stream 数据（列的编码值）
  • Row Index（每 10000 行的统计信息，支持行级跳过）
  • Stripe Footer（列统计和编码信息）

ORC 的行索引使其在高选择性过滤场景（如点查）上表现优于 Parquet。

Apache Arrow 与 IPC 格式

Arrow 定义了语言无关的内存列式数据格式，其 IPC（Inter-Process Communication）格式用于进程间零拷贝数据交换。

Arrow 的定位

Arrow 不是替代 Parquet/ORC 的持久化格式，而是内存中的标准列式表示：

磁盘格式（Parquet/ORC）→ 反序列化 → Arrow 内存格式 → 计算引擎处理
                                        ↕
                               Arrow IPC（进程间传输）

核心价值：

  • 零拷贝：不同语言/框架之间共享数据无需序列化
  • SIMD 友好：内存布局对齐，支持向量化计算
  • 标准化：Pandas、Spark、DuckDB、Polars 均支持 Arrow 格式

Arrow Flight

Arrow Flight 是基于 gRPC 的高性能数据传输协议，用于在服务间批量传输 Arrow 格式数据。相比传统 JDBC/ODBC，Flight 通过列式批量传输和零拷贝实现了数量级的性能提升。

压缩算法选择

列式格式通常在编码之上叠加通用压缩：

算法 压缩率 压缩速度 解压速度 适用场景
Snappy 中 极快 极快 默认选择，平衡性最好
Zstd 高 快 快 存储成本敏感场景
LZ4 中低 极快 极快 延迟敏感的热数据
Gzip/Zlib 高 慢 中 冷数据归档
Brotli 极高 很慢 中 极度存储敏感

选择建议：

  • 热数据（频繁查询）：Snappy 或 LZ4
  • 温数据（偶尔查询）：Zstd（level 3-6）
  • 冷数据（归档保留）：Zstd（level 9+）或 Gzip

文件大小与布局优化

理想文件大小

文件过大或过小都会影响性能：

  • 过小（<1MB）：元数据开销占比高，列表操作慢，读取请求数暴增
  • 过大（>1GB）：并行度受限，单文件故障影响范围大，尾部延迟高
  • 推荐范围：128MB-512MB（视工作负载和引擎特征调整）

排序优化

在文件内部对数据排序能极大提升谓词下推效果：

-- 按查询模式排序后写入
INSERT INTO target_table
SELECT * FROM source_table
ORDER BY event_date, user_id;  -- 按最常用的过滤字段排序

排序后，Row Group 的 min/max 统计更加紧凑，Row Group 级过滤可以跳过更多数据。

Z-Order / Hilbert 曲线

当查询涉及多个过滤字段时，单列排序无法同时优化所有字段。Z-Order 和 Hilbert 曲线通过空间填充曲线将多维数据映射到一维排列，实现多列同时受益的数据局部性。

实践建议

  1. 格式选择：新项目优先 Parquet（生态最广），Hive 生态用 ORC
  2. Row Group 大小：128MB-256MB，平衡并行度和 I/O 效率
  3. 编码：让引擎自动选择，必要时针对高基数列关闭字典编码
  4. 压缩：默认 Zstd（level 3），热路径用 Snappy
  5. 排序：按最频繁的过滤条件排序，减少扫描量
  6. 定期合并：消除小文件，重新组织数据布局
