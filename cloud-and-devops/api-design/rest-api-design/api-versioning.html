API 版本管理

核心概念

API 版本管理解决的核心问题是变更兼容性——如何在不破坏现有客户端的前提下演进 API。任何有外部消费者的 API 都会面临这个挑战：一旦发布，API 就是一份契约，单方面违约（破坏性变更）会导致客户端崩溃。

兼容性变更分类
API 变更的兼容性判定是版本管理的基础。需要区分向后兼容变更和破坏性变更。


interface ChangeClassification {
  type: string;
  backward: 'compatible' | 'breaking';
  examples: string[];
}

const classifications: ChangeClassification[] = [
  {
    type: '新增可选字段',
    backward: 'compatible',
    examples: ['响应中增加 avatar 字段', '请求中增加可选的 tag 参数'],
  },
  {
    type: '新增端点',
    backward: 'compatible',
    examples: ['增加 GET /users/:id/preferences'],
  },
  {
    type: '删除字段',
    backward: 'breaking',
    examples: ['删除响应中的 deprecated_field'],
  },
  {
    type: '修改字段类型',
    backward: 'breaking',
    examples: ['id 从 number 变为 string'],
  },
  {
    type: '修改必填性',
    backward: 'breaking',
    examples: ['可选字段变为必填'],
  },
  {
    type: '修改语义',
    backward: 'breaking',
    examples: ['status 值从 "active" 改为 "enabled"'],
  },
  {
    type: '新增枚举值',
    backward: 'compatible',
    examples: ['status 增加 "archived" 值'],
  },
];
向后兼容变更的黄金法则是：只增不减，只松不紧。

版本实现策略
URL 路径版本是最广泛采用的策略。它的最大优势是直观——URL 本身就表达了版本信息，浏览器可以直接访问，缓存代理可以按 URL 区分。


import { Hono } from 'hono';

const v1 = new Hono();
v1.get('/users/:id', async (c) => {
  const user = await getUser(c.req.param('id'));
  return c.json({
    id: user.id,
    name: user.name,
    email: user.email,
  });
});

const v2 = new Hono();
v2.get('/users/:id', async (c) => {
  const user = await getUser(c.req.param('id'));
  return c.json({
    id: user.id,
    displayName: user.name,
    emailAddress: user.email,
    avatar: user.avatarUrl,
    createdAt: user.createdAt.toISOString(),
  });
});

const app = new Hono();
app.route('/v1', v1);
app.route('/v2', v2);
Stripe 的日期版本模式是另一种优雅的方案。每个 API 版本用发布日期标识（如 2024-01-15），通过 Header 指定版本。新客户端默认使用最新版本，老客户端固定在创建时的版本。


interface VersionedBehavior {
  version: string;
  transforms: Transform[];
}

interface Transform {
  field: string;
  action: 'rename' | 'remove' | 'convert' | 'add';
  from?: string;
  to?: string;
  converter?: (value: unknown) => unknown;
}

const versionTransforms: VersionedBehavior[] = [
  {
    version: '2024-06-01',
    transforms: [
      { field: 'name', action: 'rename', from: 'name', to: 'displayName' },
      { field: 'createdAt', action: 'convert', converter: (v) => new Date(v as number).toISOString() },
    ],
  },
];

const applyVersionTransforms = (data: Record<string, unknown>, clientVersion: string): Record<string, unknown> => {
  const applicableTransforms = versionTransforms.filter((v) => v.version > clientVersion).flatMap((v) => v.transforms);

  let result = { ...data };
  for (const transform of applicableTransforms) {
    switch (transform.action) {
      case 'rename':
        result[transform.to!] = result[transform.from!];
        delete result[transform.from!];
        break;
      case 'remove':
        delete result[transform.field];
        break;
      case 'convert':
        result[transform.field] = transform.converter!(result[transform.field]);
        break;
    }
  }
  return result;
};
废弃与下线
版本管理不仅包括创建新版本，还包括废弃（Deprecation）和下线（Sunsetting）旧版本。这是对API生命周期的完整管理。


interface VersionLifecycle {
  version: string;
  status: 'current' | 'deprecated' | 'sunset';
  releasedAt: string;
  deprecatedAt?: string;
  sunsetAt?: string;
  migrationGuide?: string;
}

const versions: VersionLifecycle[] = [
  { version: 'v1', status: 'sunset', releasedAt: '2023-01-01', deprecatedAt: '2024-01-01', sunsetAt: '2024-07-01' },
  {
    version: 'v2',
    status: 'deprecated',
    releasedAt: '2024-01-01',
    deprecatedAt: '2025-01-01',
    sunsetAt: '2025-07-01',
    migrationGuide: '/docs/migration/v2-to-v3',
  },
  { version: 'v3', status: 'current', releasedAt: '2025-01-01' },
];
废弃的标准做法是在响应 Header 中添加 Deprecation 和 Sunset 标头：


const deprecationMiddleware = (deprecatedAt: string, sunsetAt: string) => {
  return async (c: Context, next: Next) => {
    await next();
    c.header('Deprecation', deprecatedAt);
    c.header('Sunset', sunsetAt);
    c.header('Link', '</docs/migration>; rel="deprecation"');
  };
};

小结
    

  • API 版本管理的核心是不破坏现有客户端，向后兼容变更可以直接发布
    • 

  • URL 路径版本最直观通用，日期版本适合长期演进的复杂 API
    • 

  • 兼容性黄金法则：只增不减、只松不紧——新增字段、新增端点、新增枚举值是安全的
    • 

  • 版本转换层（Transform）支持在单一代码库中维护多个版本行为
    • 

  • 废弃流程需要明确的时间线（Active → Deprecated → Sunset → Removed）和多渠道通知
    •
