错误处理

核心概念

API 错误处理直接影响开发者体验（DX）。一个好的错误响应应该让消费者在不查阅文档的情况下理解发生了什么、为什么发生、如何修复。这三个维度构成了错误处理设计的核心框架。

错误响应格式
统一的错误格式是良好 DX 的基础。业界有两种主流标准：RFC 7807（Problem Details）和自定义格式。


interface ProblemDetail {
  type: string;
  title: string;
  status: number;
  detail: string;
  instance: string;
  errors?: FieldError[];
}

interface FieldError {
  field: string;
  message: string;
  code: string;
  rejectedValue?: unknown;
}

const validationError: ProblemDetail = {
  type: 'https://api.example.com/errors/validation',
  title: 'Validation Failed',
  status: 422,
  detail: '请求参数校验失败，请检查以下字段',
  instance: '/users',
  errors: [
    { field: 'email', message: '邮箱格式不正确', code: 'INVALID_FORMAT', rejectedValue: 'not-an-email' },
    { field: 'age', message: '年龄必须在 18-120 之间', code: 'OUT_OF_RANGE', rejectedValue: 15 },
  ],
};
RFC 7807 的 type 字段是错误类型的 URI，可以链接到文档页面。这让开发者通过点击链接就能找到详细说明和解决方案。


错误码设计是另一个关键决策。好的错误码是机器可读的，客户端可以基于错误码做分支处理：


const ERROR_CODES = {
  VALIDATION_FAILED: 'VALIDATION_FAILED',
  RESOURCE_NOT_FOUND: 'RESOURCE_NOT_FOUND',
  DUPLICATE_RESOURCE: 'DUPLICATE_RESOURCE',
  INSUFFICIENT_PERMISSIONS: 'INSUFFICIENT_PERMISSIONS',
  RATE_LIMITED: 'RATE_LIMITED',
  PAYMENT_FAILED: 'PAYMENT_FAILED',
  ACCOUNT_SUSPENDED: 'ACCOUNT_SUSPENDED',
} as const;

type ErrorCode = (typeof ERROR_CODES)[keyof typeof ERROR_CODES];

interface AppError {
  code: ErrorCode;
  message: string;
  httpStatus: number;
  retryable: boolean;
}

const errorRegistry: Record<ErrorCode, Omit<AppError, 'code'>> = {
  VALIDATION_FAILED: { message: '请求参数校验失败', httpStatus: 422, retryable: false },
  RESOURCE_NOT_FOUND: { message: '请求的资源不存在', httpStatus: 404, retryable: false },
  DUPLICATE_RESOURCE: { message: '资源已存在', httpStatus: 409, retryable: false },
  INSUFFICIENT_PERMISSIONS: { message: '权限不足', httpStatus: 403, retryable: false },
  RATE_LIMITED: { message: '请求过于频繁', httpStatus: 429, retryable: true },
  PAYMENT_FAILED: { message: '支付处理失败', httpStatus: 402, retryable: true },
  ACCOUNT_SUSPENDED: { message: '账号已被冻结', httpStatus: 403, retryable: false },
};
输入校验错误
输入校验是最常见的错误来源。校验应该是全量的——一次返回所有校验错误，而不是一个一个地返回（用户修一个提交一次，再修一个再提交）。


import { z } from 'zod';

const createUserSchema = z.object({
  name: z.string().min(2).max(50),
  email: z.string().email(),
  age: z.number().int().min(18).max(120),
  role: z.enum(['user', 'admin', 'moderator']),
});

const handleValidation = (schema: z.ZodSchema, data: unknown): ProblemDetail | null => {
  const result = schema.safeParse(data);

  if (result.success) return null;

  const errors: FieldError[] = result.error.issues.map((issue) => ({
    field: issue.path.join('.'),
    message: issue.message,
    code: issue.code.toUpperCase(),
  }));

  return {
    type: 'https://api.example.com/errors/validation',
    title: 'Validation Failed',
    status: 422,
    detail: `${errors.length} 个字段校验失败`,
    instance: '',
    errors,
  };
};
Zod 的 safeParse 返回所有校验错误，而不是在第一个错误处停止。这正是我们需要的行为。


错误处理中间件
在 Hono 或 Express 等框架中，集中式的错误处理中间件确保所有错误都经过统一格式化。


import { Hono } from 'hono';

class AppError extends Error {
  constructor(
    public code: ErrorCode,
    public status: number,
    message: string,
    public details?: FieldError[],
  ) {
    super(message);
    this.name = 'AppError';
  }
}

const errorHandler = (err: Error, c: Context): Response => {
  if (err instanceof AppError) {
    return c.json(
      {
        type: `https://api.example.com/errors/${err.code.toLowerCase()}`,
        title: err.code,
        status: err.status,
        detail: err.message,
        instance: c.req.path,
        errors: err.details,
      },
      err.status as StatusCode,
    );
  }

  if (err instanceof z.ZodError) {
    return c.json(
      {
        type: 'https://api.example.com/errors/validation',
        title: 'VALIDATION_FAILED',
        status: 422,
        detail: '请求参数校验失败',
        instance: c.req.path,
        errors: err.issues.map((i) => ({
          field: i.path.join('.'),
          message: i.message,
          code: i.code,
        })),
      },
      422,
    );
  }

  console.error('Unhandled error:', err);
  return c.json(
    {
      type: 'https://api.example.com/errors/internal',
      title: 'INTERNAL_ERROR',
      status: 500,
      detail: '服务器内部错误',
      instance: c.req.path,
    },
    500,
  );
};

const app = new Hono();
app.onError(errorHandler);
关键原则是内部错误不泄露细节。500 错误只返回通用消息，堆栈和内部信息记录到日志系统，不发送给客户端。


重试与限流
对于可重试的错误（429、503），API 应该通过响应头告诉客户端何时可以重试。


interface RetryInfo {
  retryAfter: number;
  remaining: number;
  limit: number;
  resetAt: Date;
}

const rateLimitHeaders = (info: RetryInfo): Record<string, string> => ({
  'Retry-After': info.retryAfter.toString(),
  'X-RateLimit-Remaining': info.remaining.toString(),
  'X-RateLimit-Limit': info.limit.toString(),
  'X-RateLimit-Reset': Math.floor(info.resetAt.getTime() / 1000).toString(),
});

const retryableResponse = (c: Context, retryInfo: RetryInfo): Response => {
  const headers = rateLimitHeaders(retryInfo);
  return c.json(
    {
      type: 'https://api.example.com/errors/rate-limited',
      title: 'RATE_LIMITED',
      status: 429,
      detail: `请求过于频繁，请在 ${retryInfo.retryAfter} 秒后重试`,
      instance: c.req.path,
    },
    { status: 429, headers },
  );
};
客户端应实现指数退避重试策略，避免 Thundering Herd（惊群）效应：


const retryWithBackoff = async <T>(
  fn: () => Promise<T>,
  maxRetries: number = 3,
  baseDelay: number = 1000,
): Promise<T> => {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      if (attempt === maxRetries) throw error;
      const isRetryable = error instanceof AppError && error.status === 429;
      if (!isRetryable) throw error;
      const delay = baseDelay * Math.pow(2, attempt) + Math.random() * 1000;
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }
  throw new Error('Unreachable');
};
小结
    

  • 好的错误响应回答三个问题：发生了什么、为什么发生、如何修复
    • 

  • RFC 7807 Problem Details 是标准的错误格式，type URI 链接到详细文档
    • 

  • 输入校验必须全量返回——Zod 的 safeParse 收集所有错误，一次性反馈
    • 

  • 集中式错误处理中间件确保格式统一，500 错误不泄露内部细节
    • 

  • 限流响应使用 Retry-After Header，客户端实现指数退避避免惊群效应
    •
