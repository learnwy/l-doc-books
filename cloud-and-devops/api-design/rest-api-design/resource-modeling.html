资源建模

核心概念

资源建模是 REST API 设计的核心活动——它决定了 API 的结构、URL 体系和数据流向。资源不等于数据库表，它是面向使用场景的抽象。好的资源模型让 API 符合消费者的心智模型，而不是暴露系统内部的实现细节。

资源粒度设计
资源粒度是最关键的设计决策之一。太细导致 N+1 请求问题，太粗导致过度获取（over-fetching）。


interface User {
  id: string;
  name: string;
  email: string;
  avatar: string;
  createdAt: string;
}

interface UserProfile {
  id: string;
  name: string;
  avatar: string;
  bio: string;
  socialLinks: SocialLink[];
}

interface UserSettings {
  id: string;
  theme: 'light' | 'dark' | 'auto';
  language: string;
  notifications: NotificationPreference[];
}
将 User 拆分为三个子资源是粒度设计的经典案例：


GET /users/123              → 基础信息（列表场景）
GET /users/123/profile      → 详细档案（个人页场景）
GET /users/123/settings     → 配置偏好（设置页场景）
这种设计的好处是按需获取——列表页只请求轻量的基础信息，设置页只请求配置数据，避免了传输不需要的字段。


聚合资源（Aggregate Resource）是另一种常见模式——将多个相关资源组合成一个响应：


interface Dashboard {
  user: UserSummary;
  recentOrders: OrderSummary[];
  notifications: Notification[];
  stats: UserStats;
}

// GET /users/123/dashboard → 一次请求获取仪表盘需要的所有数据
聚合资源在 BFF（Backend for Frontend）模式中特别常见——每个前端页面有对应的聚合接口。


关系与嵌套
资源间的关系通过 URL 嵌套和引用来表达。核心原则是嵌套表示强归属，引用表示弱关联。


强归属（嵌套）
GET /orders/456/items         订单的商品项（离开订单无意义）
GET /posts/789/comments       文章的评论（属于文章）

弱关联（引用）
GET /users/123                 用户资源中包含 { "teamId": "team-42" }
GET /teams/42                  独立的团队资源
嵌套的深度不应超过 2 层。超过 2 层说明资源模型需要重新审视：


❌ /users/123/orders/456/items/789/reviews
✅ /order-items/789/reviews 或 /reviews?order_item_id=789
interface ResourceRelation {
  type: 'composition' | 'aggregation' | 'association';
  expression: 'nested' | 'reference' | 'embedded';
  example: string;
}

const relations: ResourceRelation[] = [
  {
    type: 'composition',
    expression: 'nested',
    example: '/orders/456/items → 订单项从属于订单',
  },
  {
    type: 'aggregation',
    expression: 'embedded',
    example: '订单响应中内嵌用户摘要',
  },
  {
    type: 'association',
    expression: 'reference',
    example: '订单响应中包含 userId 引用',
  },
];
内嵌（Embedding） vs 引用（Reference） 是关联资源的表述选择。内嵌减少请求数但增加响应体积；引用保持响应精简但可能导致 N+1。可以用 ?expand=author,tags 参数让客户端按需选择。


集合操作设计
集合资源（Collection）的设计需要覆盖过滤、排序、分页、搜索等操作。这些操作通过 Query String 表达，保持 URL 的资源语义不变。


interface CollectionParams {
  page: number;
  perPage: number;
  sort: string;
  order: 'asc' | 'desc';
  filter: Record<string, string>;
  fields: string[];
  search: string;
}

// GET /users?page=2&per_page=20&sort=created_at&order=desc&role=admin&fields=id,name,email

interface PaginatedResponse<T> {
  data: T[];
  meta: {
    total: number;
    page: number;
    perPage: number;
    totalPages: number;
  };
  links: {
    self: string;
    first: string;
    prev: string | null;
    next: string | null;
    last: string;
  };
}

游标分页使用最后一条记录的标识作为起始点，数据库可以利用索引高效查询。对于无限滚动和大数据集场景，游标分页是更好的选择。


interface CursorPagination<T> {
  data: T[];
  pageInfo: {
    hasNextPage: boolean;
    hasPreviousPage: boolean;
    startCursor: string;
    endCursor: string;
  };
}

const encodeCursor = (id: string, sortValue: string): string => {
  return Buffer.from(JSON.stringify({ id, sortValue })).toString('base64url');
};

const decodeCursor = (cursor: string): { id: string; sortValue: string } => {
  return JSON.parse(Buffer.from(cursor, 'base64url').toString());
};
批量操作
单资源 CRUD 不够用时，需要设计批量操作接口。批量操作的挑战是原子性——部分成功怎么处理？


interface BatchRequest<T> {
  operations: BatchOperation<T>[];
}

interface BatchOperation<T> {
  method: 'create' | 'update' | 'delete';
  resourceId?: string;
  body?: Partial<T>;
}

interface BatchResponse<T> {
  results: BatchResult<T>[];
  summary: {
    total: number;
    succeeded: number;
    failed: number;
  };
}

interface BatchResult<T> {
  index: number;
  status: number;
  body?: T;
  error?: ApiError;
}

// POST /users/batch
// 返回 207 Multi-Status，每个操作独立的状态码
批量操作的状态码选择：


    

  • 200：所有操作都成功
    • 

  • 207 Multi-Status：部分成功部分失败（推荐）
    • 

  • 400：请求格式错误
    • 

  • 413：批量大小超限
    • 



小结
    

  • 资源建模面向使用场景而非数据库表——API 是给消费者用的，不是暴露实现的
    • 

  • 粒度设计的核心是避免 N+1 和 over-fetching，子资源和聚合资源是两种工具
    • 

  • 嵌套表示强归属（不超过 2 层），引用表示弱关联，?expand 参数提供灵活性
    • 

  • 游标分页在性能和大数据集场景优于偏移分页，是无限滚动的标准选择
    • 

  • 批量操作使用 207 Multi-Status 处理部分成功场景，每个操作独立报告状态
    •
