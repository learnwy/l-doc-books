REST 设计原则

核心概念

REST（Representational State Transfer）是 Roy Fielding 在 2000 年博士论文中提出的架构风格。它不是协议也不是标准，而是一组约束条件。满足这些约束的系统被称为 RESTful。REST 的核心洞察是：Web 本身就是一个巨型分布式系统，其成功的架构原则可以推广到 API 设计中。

HTTP 方法语义
REST 将 HTTP 方法映射到 CRUD 操作，但这不仅仅是命名约定——每个方法有明确的安全性和幂等性语义。


interface HttpMethod {
  method: string;
  safe: boolean;
  idempotent: boolean;
  requestBody: boolean;
  typicalStatusCodes: number[];
}

const methods: HttpMethod[] = [
  { method: 'GET', safe: true, idempotent: true, requestBody: false, typicalStatusCodes: [200, 304, 404] },
  { method: 'POST', safe: false, idempotent: false, requestBody: true, typicalStatusCodes: [201, 400, 409] },
  { method: 'PUT', safe: false, idempotent: true, requestBody: true, typicalStatusCodes: [200, 204, 404] },
  { method: 'PATCH', safe: false, idempotent: false, requestBody: true, typicalStatusCodes: [200, 204, 404] },
  { method: 'DELETE', safe: false, idempotent: true, requestBody: false, typicalStatusCodes: [204, 404] },
];
安全方法（GET, HEAD, OPTIONS）不修改服务器状态，可以被安全重试和缓存。幂等方法（GET, PUT, DELETE）多次执行的效果与一次相同——这对网络不稳定时的重试至关重要。


PUT 和 PATCH 的区别常被混淆。PUT 是完整替换——发送资源的完整表述；PATCH 是部分更新——只发送要修改的字段。


// PUT: 完整替换
// PUT /users/123
const putBody = {
  id: 123,
  name: 'Alice',
  email: 'alice@example.com',
  role: 'admin',
};

// PATCH: 部分更新
// PATCH /users/123
const patchBody = {
  role: 'admin',
};
URL 设计规范
URL 是 REST API 的门面——好的 URL 设计让 API 不言自明。核心原则是 URL 表示资源（名词），HTTP 方法表示操作（动词）。


✅ 正确
GET    /users                 获取用户列表
GET    /users/123             获取单个用户
POST   /users                 创建用户
PUT    /users/123             更新用户
DELETE /users/123             删除用户
GET    /users/123/orders      获取用户的订单
GET    /users/123/orders/456  获取特定订单

❌ 错误
GET    /getUsers              动词出现在 URL 中
POST   /createUser            动词出现在 URL 中
GET    /user/123              单数（应复数）
DELETE /users/123/delete      delete 既出现在方法又出现在 URL
interface UrlConvention {
  rule: string;
  example: string;
  reason: string;
}

const conventions: UrlConvention[] = [
  { rule: '使用复数名词', example: '/users, /orders', reason: '集合语义一致' },
  { rule: 'kebab-case', example: '/user-profiles', reason: 'URL 不区分大小写' },
  { rule: '嵌套不超过 2 层', example: '/users/123/orders', reason: '深嵌套难以理解' },
  { rule: '查询用 Query String', example: '/users?role=admin&sort=name', reason: '过滤非路径的一部分' },
  { rule: '版本在路径或 Header', example: '/v1/users', reason: '向后兼容' },
  { rule: '分页用标准参数', example: '?page=2&per_page=20', reason: '可预测的接口' },
];

interface ApiResponse<T> {
  data: T;
  meta?: PaginationMeta;
}

interface ApiError {
  error: {
    code: string;
    message: string;
    details?: ErrorDetail[];
  };
}

interface ErrorDetail {
  field: string;
  message: string;
  code: string;
}

const createErrorResponse = (status: number, code: string, message: string, details?: ErrorDetail[]): Response => {
  const body: ApiError = {
    error: { code, message, details },
  };
  return new Response(JSON.stringify(body), {
    status,
    headers: { 'Content-Type': 'application/json' },
  });
};
HATEOAS 与成熟度模型
Richardson 成熟度模型将 REST API 分为四个级别。大多数实际 API 停留在 Level 2（HTTP 动词 + 资源），而 Level 3（HATEOAS）是真正的 REST。


HATEOAS（Hypermedia As The Engine Of Application State）意味着 API 响应中包含下一步可执行操作的链接。客户端通过跟随链接导航，而不是硬编码 URL。


interface HateoasResponse<T> {
  data: T;
  _links: Record<string, HateoasLink>;
}

interface HateoasLink {
  href: string;
  method: string;
  title: string;
}

const userResponse: HateoasResponse<User> = {
  data: { id: 123, name: 'Alice', email: 'alice@example.com' },
  _links: {
    self: { href: '/users/123', method: 'GET', title: '当前用户' },
    update: { href: '/users/123', method: 'PUT', title: '更新用户' },
    delete: { href: '/users/123', method: 'DELETE', title: '删除用户' },
    orders: { href: '/users/123/orders', method: 'GET', title: '用户订单' },
  },
};
HATEOAS 在实际项目中的采用率不高，但在对外公开 API 和长生命周期系统中很有价值——它让客户端不依赖硬编码的 URL 结构，API 演进更灵活。


小结
    

  • REST 是架构风格而非协议，核心是六个约束条件，其中无状态和统一接口最关键
    • 

  • HTTP 方法的安全性和幂等性语义决定了重试和缓存策略
    • 

  • URL 设计以名词（资源）为核心，HTTP 方法表达操作，嵌套不超过 2 层
    • 

  • 状态码是 REST 的语义载体——401 是未认证，403 是无权限，不可混淆
    • 

  • Richardson 成熟度模型分四级，Level 2 是实际标准，Level 3（HATEOAS）是理想目标
    •
