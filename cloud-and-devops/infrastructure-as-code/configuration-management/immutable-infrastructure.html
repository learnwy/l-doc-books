不可变基础设施

核心概念

不可变基础设施（Immutable Infrastructure）是一种运维范式，其核心原则是服务器一旦部署就不再进行任何修改。需要变更时，不修改现有服务器，而是基于新配置构建全新的服务器镜像，用新实例替换旧实例，旧实例随后销毁。这种"替换而非修补"的策略从根本上消除了配置漂移和"雪花服务器"问题，使基础设施具备与软件制品相同的可重复性和版本化特征。

镜像构建流水线
Packer 是不可变基础设施中最核心的镜像构建工具，它使用统一的配置模板（HCL 或 JSON）在多个云平台上并行构建虚拟机镜像。Packer 的构建流程包括 Source（定义基础镜像和构建环境）、Provisioner（执行配置操作）和 Post-Processor（后处理，如注册镜像和输出元数据）三个阶段。


source "amazon-ebs" "base" {
  ami_name      = "webapp-{{timestamp}}"
  instance_type = "t3.medium"
  region        = "ap-southeast-1"
  source_ami_filter {
    filters = {
      name                = "ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-amd64-server-*"
      root-device-type    = "ebs"
      virtualization-type = "hvm"
    }
    owners      = ["099720109477"]
    most_recent = true
  }
  ssh_username = "ubuntu"

  tags = {
    Name        = "webapp-base"
    BuildTime   = "{{timestamp}}"
    SourceAMI   = "{{ .SourceAMI }}"
    Environment = "production"
  }
}

build {
  sources = ["source.amazon-ebs.base"]

  provisioner "ansible" {
    playbook_file = "./ansible/site.yml"
    extra_arguments = [
      "--extra-vars", "app_version=${var.app_version}"
    ]
  }

  provisioner "shell" {
    inline = [
      "sudo apt-get clean",
      "sudo rm -rf /var/lib/apt/lists/*",
      "sudo rm -rf /tmp/*"
    ]
  }

  post-processor "manifest" {
    output     = "packer-manifest.json"
    strip_path = true
  }
}
镜像分层策略将构建过程分解为基础层（OS + 安全补丁）、中间层（运行时 + 框架）和应用层（业务代码 + 配置）。基础层和中间层的构建频率较低（周级），应用层随每次部署更新。分层构建减少了重复工作，基础层变更自动触发上层依赖链的重建。


镜像测试在发布前验证构建产物的正确性。InSpec 和 Goss 是两种主流的镜像验证工具，前者使用 Ruby DSL 编写合规测试，后者使用 YAML 定义期望的系统状态（端口监听、服务运行、文件存在）。测试在临时实例上执行，通过后镜像才被标记为可部署版本。


部署策略与流量切换
不可变基础设施的部署核心是用新实例集群替换旧实例集群，同时保证服务的持续可用性。蓝绿部署（Blue-Green Deployment）和滚动部署（Rolling Deployment）是两种最常用的策略。


蓝绿部署维护两套完整的环境，当前服务运行在蓝色环境，新版本部署到绿色环境。经过充分验证后，负载均衡器将流量从蓝色切换到绿色。切换是原子操作，出现问题时可秒级回滚到蓝色环境。代价是需要双倍的基础设施资源。


滚动部署按批次逐步替换实例，每批新实例通过健康检查后加入负载均衡池，对应数量的旧实例从池中移除并销毁。AWS Auto Scaling Group 的 Instance Refresh 和 Kubernetes 的 Rolling Update 都实现了滚动部署策略。关键参数包括批次大小（min_healthy_percentage）和等待时间（instance_warmup）。


金丝雀部署（Canary Deployment）将少量流量（如 5%）路由到新版本实例，通过监控指标对比新旧版本的错误率、延迟和资源使用情况。如果金丝雀指标健康，逐步扩大新版本流量比例直至全量切换；如果指标异常，立即销毁金丝雀实例并回滚。


状态管理与数据持久化
不可变基础设施的核心约束是实例不可修改，这要求应用严格分离无状态计算和有状态存储。应用服务器作为无状态组件可以自由替换，而数据库、文件存储和会话状态则需要外部化到持久存储服务。

外部化存储的数据迁移需要独立的变更管理流程。数据库 Schema 变更通过迁移工具（Flyway、golang-migrate）管理，与应用部署解耦。向前兼容策略确保新旧版本代码可以同时操作当前的数据库 Schema，使蓝绿和金丝雀部署期间数据层保持稳定。


日志和监控是不可变基础设施的生命线。由于不能 SSH 到服务器排查问题，所有诊断信息必须通过结构化日志、分布式追踪和指标收集系统获取。应用启动时即开始向日志收集器和 APM 系统报告状态，确保短生命周期实例的行为可追溯。


容器化与不可变基础设施的融合
容器技术是不可变基础设施理念的天然载体。Docker 镜像的分层和不可修改特性完美契合"构建一次、处处运行"的原则。容器编排平台（Kubernetes）提供了声明式的部署管理，自动处理滚动更新、健康检查和故障恢复。


容器化不可变基础设施的典型流程：源代码变更 → CI 构建 Docker 镜像 → 推送到镜像仓库 → 更新 Kubernetes Deployment 的镜像标签 → Kubernetes 执行滚动更新 → 旧 Pod 自动终止。整个过程中没有任何"登录服务器修改配置"的步骤。


VM 级别和容器级别的不可变基础设施并非互斥，而是互补。VM 镜像（通过 Packer 构建）提供一致的 Kubernetes 节点环境，容器镜像（通过 Dockerfile 构建）提供一致的应用运行环境。两层不可变性的叠加确保从操作系统到应用程序的全栈一致性。


小结
    

  • 不可变基础设施通过"替换而非修补"策略从根本上消除配置漂移
    • 

  • Packer 构建流水线实现镜像的分层构建、自动化测试和多云发布
    • 

  • 蓝绿、滚动和金丝雀三种部署策略在可用性、回滚速度和资源成本之间取舍
    • 

  • 状态外部化是不可变基础设施的核心前提，计算与存储严格分离
    • 

  • 日志和监控系统替代 SSH 成为运维排障的主要手段
    • 

  • 容器技术是不可变理念的天然载体，与 VM 级不可变性形成全栈互补
    •
