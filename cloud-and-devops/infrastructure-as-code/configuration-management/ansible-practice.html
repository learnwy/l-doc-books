Ansible 自动化实战

核心概念

Ansible 是当前最流行的开源自动化平台，以无代理架构（Agentless）和 YAML 声明式语法著称。Ansible 通过 SSH（Linux）或 WinRM（Windows）连接目标主机，将模块（Module）推送到远端执行，执行完成后自动清理。这种架构消除了在目标主机上安装和维护代理软件的运维负担，使 Ansible 成为快速上手的自动化工具。

Inventory 与主机管理
Inventory 定义了 Ansible 可操作的目标主机及其分组关系。静态 Inventory 使用 INI 或 YAML 格式编写，适合固定规模的基础设施。动态 Inventory 通过脚本或插件从云平台 API、CMDB 或服务注册中心实时获取主机列表，适合弹性伸缩的云原生环境。


all:
  children:
    webservers:
      hosts:
        web-sg-01:
          ansible_host: 10.0.1.10
        web-sg-02:
          ansible_host: 10.0.1.11
      vars:
        http_port: 8080
        max_connections: 1000
    databases:
      hosts:
        db-sg-01:
          ansible_host: 10.0.2.10
          postgresql_version: '16'
      vars:
        backup_schedule: '0 2 * * *'
  vars:
    ansible_user: deploy
    ansible_ssh_private_key_file: ~/.ssh/deploy_key
主机变量的优先级遵循从低到高的链式覆盖：Inventory defaults → group_vars/all → group_vars/ → host_vars/ → Playbook vars → extra-vars（-e）。这种分层机制允许在不同粒度上定义和覆盖配置，group_vars 和 host_vars 目录按约定名称自动加载。


动态 Inventory 插件（如 amazon.aws.aws_ec2、azure.azcollection.azure_rm）通过 API 查询实例列表，支持按标签、区域和实例状态过滤。缓存机制减少 API 调用频率，TTL 配置平衡实时性和性能。企业环境推荐将动态 Inventory 与 CMDB 集成，确保 Ansible 操作的主机范围与资产管理系统一致。


Playbook 编排与任务设计
Playbook 是 Ansible 的核心编排文件，定义了在哪些主机上按什么顺序执行哪些任务。每个 Play 指定目标主机组和要执行的任务列表，多个 Play 组成一个 Playbook。任务（Task）调用模块执行原子操作，Handler 在被通知时执行一次性操作（如重启服务）。


- name: Deploy web application
  hosts: webservers
  become: true
  vars:
    app_version: '2.5.0'
    deploy_dir: /opt/webapp

  pre_tasks:
    - name: Verify connectivity
      ansible.builtin.ping:

  roles:
    - role: common
      tags: [base]
    - role: nginx
      vars:
        nginx_worker_processes: auto
      tags: [web]

  tasks:
    - name: Deploy application artifact
      ansible.builtin.unarchive:
        src: 'https://releases.example.com/webapp-{{ app_version }}.tar.gz'
        dest: '{{ deploy_dir }}'
        remote_src: true
      notify: restart webapp

    - name: Configure application
      ansible.builtin.template:
        src: app-config.yml.j2
        dest: '{{ deploy_dir }}/config.yml'
        owner: webapp
        group: webapp
        mode: '0640'
      notify: restart webapp

  handlers:
    - name: restart webapp
      ansible.builtin.systemd:
        name: webapp
        state: restarted
        enabled: true
任务设计的最佳实践包括：使用完全限定集合名称（FQCN，如 ansible.builtin.copy）避免命名冲突；通过 block/rescue/always 结构实现错误处理和回滚；使用 when 条件控制任务执行；通过 loop 和 with_* 实现批量操作；使用 register 捕获任务结果供后续任务使用。


执行策略通过 strategy 参数控制，linear（默认）在所有主机上逐任务同步执行，free 允许每个主机独立推进不等待其他主机，host_pinned 在单个主机上执行完所有任务再切换。滚动部署通过 serial 参数实现，按批次在主机子集上执行，保证服务的持续可用性。


Ansible Vault 与安全实践
Ansible Vault 提供内置的敏感数据加密机制，使用 AES-256 对称加密算法保护密码、密钥和证书等机密信息。加密可以应用于整个文件或文件内的单个变量值（Inline Vault），后者的粒度更细，便于代码审查。


database_config:
  host: db-production.internal
  port: 5432
  username: app_service
  password: !vault |
    $ANSIBLE_VAULT;1.1;AES256
    6261636b656e645f70617373776f72643d
    ...
Vault 密码的管理方式包括：交互式输入（--ask-vault-pass）、密码文件（--vault-password-file）和脚本获取（从密钥管理系统动态读取）。多 Vault ID 机制支持不同安全级别使用不同密码，如 dev 和 prod 环境各自独立的加密密钥。


企业安全实践还包括：最小权限 SSH 用户（避免 root 直连）、become 机制的细粒度 sudo 配置、连接超时和重试策略、敏感输出的 no_log: true 标记、以及审计日志的集中收集。AWX/Ansible Tower 提供 RBAC 权限模型和执行审计功能，适合多团队协作的企业环境。


测试与 CI/CD 集成
Ansible 自动化代码同样需要测试保障。Molecule 是 Ansible 角色的标准测试框架，支持在 Docker、Vagrant 或云实例中自动创建测试环境、执行 Playbook、验证结果并清理资源。

CI/CD 集成将 Ansible 执行嵌入自动化流水线。GitLab CI、GitHub Actions 和 Jenkins 通过 Ansible 插件或直接调用 ansible-playbook 命令执行部署任务。Pipeline 设计遵循 Lint → Test → Deploy Staging → Verify → Deploy Production 的阶段模型，每个阶段的失败都会阻止后续执行。


Ansible 与 Terraform 的协同模式是现代基础设施自动化的典型架构：Terraform 完成资源创建后通过 local-exec 或 remote-exec Provisioner 触发 Ansible Playbook，或者 Terraform 输出动态 Inventory 供 Ansible 消费。两者的职责边界明确：Terraform 管理资源生命周期，Ansible 管理系统配置。


小结
    

  • Ansible 以无代理架构和 YAML 语法降低自动化门槛，通过 SSH 推送模块执行
    • 

  • Inventory 支持静态和动态两种模式，变量优先级链实现多层级配置覆盖
    • 

  • Playbook 通过 Play、Task、Handler 和 Role 四层抽象编排复杂部署流程
    • 

  • Vault 提供 AES-256 加密保护敏感数据，支持文件级和变量级两种粒度
    • 

  • Molecule 框架覆盖语法检查到幂等性测试的完整质量链
    • 

  • Ansible 与 Terraform 协同形成资源编排+系统配置的完整自动化体系
    •
