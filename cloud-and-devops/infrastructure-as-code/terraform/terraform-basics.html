Terraform 基础与核心概念

核心概念

Terraform 是 HashiCorp 推出的开源基础设施即代码工具，采用声明式语言 HCL（HashiCorp Configuration Language）描述基础设施的期望状态，通过 Provider 插件体系与各类云平台和服务进行交互。Terraform 的核心工作流为 Write → Plan → Apply 三步循环，开发者编写配置文件描述资源，Terraform 生成执行计划展示变更差异，确认后自动完成资源的创建、更新或销毁。

HCL 语法与资源定义
HCL（HashiCorp Configuration Language）是 Terraform 的核心语言，设计目标是在保持机器可读性的同时提供良好的人类可读性。HCL 的基本构建块包括 Block、Argument 和 Expression 三种语法元素。


资源定义是 Terraform 配置的核心，每个 resource 块描述一个基础设施对象。资源类型由 Provider 定义，每种资源类型拥有固定的参数模式。Terraform 通过资源之间的引用自动构建依赖关系图，决定创建和销毁的顺序。


terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "ap-southeast-1"
}

resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true

  tags = {
    Name        = "production-vpc"
    Environment = "prod"
  }
}

resource "aws_subnet" "public" {
  count             = 3
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index)
  availability_zone = data.aws_availability_zones.available.names[count.index]

  tags = {
    Name = "public-subnet-${count.index + 1}"
    Type = "public"
  }
}
变量系统是 HCL 的参数化机制，支持 string、number、bool、list、map、object 等类型。输入变量通过 variable 块定义，支持默认值、类型约束和验证规则。输出值通过 output 块暴露，用于跨模块数据传递和外部集成。


数据源（Data Source）允许 Terraform 查询已存在的基础设施信息，不创建新资源。常见用途包括查找 AMI ID、获取可用区列表、读取远程状态等。数据源以 data 块定义，在 Plan 阶段即执行查询。


Provider 生态与多云管理
Provider 是 Terraform 与外部 API 交互的插件，每个 Provider 封装了一组资源类型和数据源的 CRUD 操作。Terraform Registry 托管了超过 3000 个 Provider，覆盖主流云平台、SaaS 服务和内部系统。


Provider 配置支持别名机制，允许在同一配置中使用同一 Provider 的多个实例。典型场景包括多区域部署、多账户管理和灾备配置。通过 alias 参数为 Provider 创建别名，在资源定义中通过 provider 参数引用特定的 Provider 实例。


provider "aws" {
  region = "ap-southeast-1"
  alias  = "singapore"
}

provider "aws" {
  region = "us-east-1"
  alias  = "virginia"
}

resource "aws_s3_bucket" "singapore_bucket" {
  provider = aws.singapore
  bucket   = "app-data-sg"
}

resource "aws_s3_bucket" "virginia_bucket" {
  provider = aws.virginia
  bucket   = "app-data-us"
}
多云管理策略需要考虑 Provider 版本锁定、凭证管理和资源命名一致性。版本约束使用 ~>（悲观约束）语法限制 Provider 升级范围，避免破坏性变更。凭证配置遵循最小权限原则，推荐使用环境变量或 Vault 集成而非硬编码。跨云资源的依赖关系通过输出值和数据源桥接，保持各 Provider 配置的独立性。


自定义 Provider 开发使用 Go 语言的 Terraform Plugin SDK，实现 Resource 和 DataSource 接口。企业内部系统（如 CMDB、DNS、证书管理）可通过自定义 Provider 纳入 Terraform 管理范围，实现全栈基础设施的统一编排。


执行计划与变更管理
terraform plan 是 Terraform 工作流的核心环节，它对比当前状态与期望配置，生成详细的执行计划。Plan 输出使用 +（创建）、-（销毁）、~（更新）、-/+（替换）符号标记每个资源的变更类型，帮助运维人员在变更实施前充分理解影响范围。


Plan 文件可以保存为二进制格式（-out=planfile），确保 Apply 阶段严格执行审查过的变更。这种模式在 CI/CD 流水线中尤为重要，Plan 阶段在 PR 中展示变更，合并后 Apply 阶段使用保存的 Plan 文件执行，避免两个阶段之间的配置漂移。

terraform apply -target 允许精确执行部分资源的变更，但应谨慎使用，因为它可能跳过依赖链中的必要变更。推荐做法是将基础设施按业务边界拆分为独立的 Terraform 工作空间，每个空间独立管理 Plan 和 Apply。


表达式与内置函数
Terraform 提供丰富的表达式系统，包括条件表达式、循环构造和内置函数，使配置具备编程能力。for_each 和 count 是两种主要的资源复制机制，for_each 基于 Map 或 Set 迭代，产生的资源以键名寻址，比基于索引的 count 更稳定。


variable "environments" {
  type = map(object({
    instance_type = string
    min_size      = number
    max_size      = number
  }))
  default = {
    staging = {
      instance_type = "t3.medium"
      min_size      = 1
      max_size      = 3
    }
    production = {
      instance_type = "m5.xlarge"
      min_size      = 3
      max_size      = 10
    }
  }
}

resource "aws_autoscaling_group" "app" {
  for_each = var.environments

  name         = "asg-${each.key}"
  min_size     = each.value.min_size
  max_size     = each.value.max_size

  launch_template {
    id      = aws_launch_template.app[each.key].id
    version = "$Latest"
  }
}
动态块（dynamic）用于生成重复的嵌套配置块，避免硬编码每个规则。安全组规则、IAM 策略语句和标签映射是动态块的高频应用场景。内置函数分为字符串、数值、集合、编码、文件系统、日期和类型转换七大类，lookup、merge、flatten、cidrsubnet 是基础设施配置中最常用的函数。


条件表达式 condition ? true_val : false_val 支持基于环境参数的配置分支。结合 locals 块可构建复杂的派生值体系，将业务逻辑与资源定义分离，提高配置的可维护性。


小结
    

  • Terraform 采用 Write → Plan → Apply 三步工作流，通过声明式 HCL 描述基础设施期望状态
    • 

  • HCL 语法围绕 Block、Argument、Expression 构建，变量系统支持类型约束和验证规则
    • 

  • Provider 插件体系支持 3000+ 集成，别名机制实现多区域/多账户管理
    • 

  • 执行计划提供变更预览，lifecycle 块控制资源的创建、销毁和更新策略
    • 

  • for_each 优于 count 用于资源复制，动态块消除嵌套配置的重复
    • 

  • 多云管理需要统一的 Provider 版本策略、凭证管理方案和资源命名规范
    •
