Argo CD 与 Flux 实战

核心概念

Argo CD 和 Flux 是 Kubernetes 生态中两大主流 GitOps 持续交付工具，均为 CNCF 毕业项目。两者都实现了 GitOps 的拉模式，以集群内代理的形式持续监控 Git 仓库，将 Kubernetes 资源的实际状态同步到 Git 中定义的期望状态。尽管目标一致，两者在架构设计、用户体验和扩展能力上存在显著差异。

Argo CD 架构与部署
Argo CD 由 API Server、Repo Server、Application Controller 和 Dex（SSO）四个核心组件组成。API Server 提供 REST/gRPC 接口和 Web UI，Repo Server 负责从 Git 仓库拉取配置并渲染 Kubernetes 清单，Application Controller 执行状态同步和健康检查。


apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: webapp
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/company/gitops-config.git
    targetRevision: main
    path: apps/webapp/overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: webapp
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
      allowEmpty: false
    syncOptions:
      - CreateNamespace=true
      - PrunePropagationPolicy=foreground
      - PruneLast=true
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
Application 是 Argo CD 的核心资源，定义了 Git 仓库路径（Source）到 Kubernetes 集群和命名空间（Destination）的映射关系。syncPolicy.automated 启用自动同步，selfHeal 在检测到手动修改时自动恢复到 Git 定义的状态，prune 自动删除 Git 中已移除的资源。


ApplicationSet 是 Argo CD 的高级资源，支持从模板批量生成 Application。Generator 机制支持 Git 目录发现、集群列表、矩阵组合和 PR 触发等多种模式。ApplicationSet 特别适合多集群部署和多租户环境，一个 ApplicationSet 可以自动为每个集群或环境生成对应的 Application。


同步窗口（Sync Window）控制自动同步的时间范围，在维护窗口期外阻止自动部署。结合通知引擎（Notification Engine），Argo CD 可在同步成功、失败或健康状态变化时发送 Slack、Teams 或 Webhook 通知。


Flux 架构与部署
Flux 采用微服务架构，由 GitOps Toolkit 中的多个独立控制器组成。Source Controller 管理 Git 仓库和 Helm Chart 仓库的拉取与缓存，Kustomize Controller 应用 Kustomize 渲染后的清单，Helm Controller 管理 Helm Release 的安装和升级，Notification Controller 处理事件分发。


apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: gitops-config
  namespace: flux-system
spec:
  interval: 1m
  url: https://github.com/company/gitops-config.git
  ref:
    branch: main
  secretRef:
    name: git-credentials
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: webapp
  namespace: flux-system
spec:
  interval: 5m
  targetNamespace: webapp
  sourceRef:
    kind: GitRepository
    name: gitops-config
  path: ./apps/webapp/overlays/production
  prune: true
  healthChecks:
    - apiVersion: apps/v1
      kind: Deployment
      name: webapp
      namespace: webapp
  dependsOn:
    - name: infrastructure
  timeout: 3m
Flux 的依赖编排通过 dependsOn 字段实现 Kustomization 之间的顺序控制。典型场景是先部署基础设施组件（cert-manager、ingress-nginx），等待健康检查通过后再部署应用。这种声明式依赖比 Argo CD 的 Sync Waves（注解方式）更清晰。


Flux 的镜像自动化功能由 Image Reflector Controller 和 Image Automation Controller 两个组件提供。前者扫描容器镜像仓库中的标签，后者根据策略（SemVer、时间戳、字母排序）自动更新 Git 仓库中的镜像引用。这种 GitOps 原生的镜像更新方式保持了 Git 作为单一可信源的原则。


apiVersion: image.toolkit.fluxcd.io/v1beta2
kind: ImagePolicy
metadata:
  name: webapp
  namespace: flux-system
spec:
  imageRepositoryRef:
    name: webapp
  policy:
    semver:
      range: '>=1.0.0 <2.0.0'
多集群与多租户管理
企业环境通常需要管理多个 Kubernetes 集群（开发、测试、预发布、生产、多区域生产），GitOps 工具需要支持集中管理和分散执行的混合模式。






管理模式
Argo CD 实现
Flux 实现





Hub-Spoke（集中管理）
管理集群安装 Argo CD，Application 指向远程集群
管理集群安装 Flux，通过 KubeConfig Secret 操作远程集群




每集群独立
每个集群安装独立 Argo CD
每个集群安装独立 Flux




多租户
AppProject 限制命名空间和仓库权限
Kustomization 的 serviceAccountName 和 targetNamespace




环境促进
ApplicationSet 模板 + Git 分支/目录
Kustomization 依赖链 + Flagger





Argo CD 的 AppProject 是多租户隔离的核心机制，它限制每个团队可访问的 Git 仓库、目标集群和命名空间。结合 RBAC 策略，AppProject 实现了"团队 A 只能在 staging 集群的 team-a 命名空间部署来自 team-a-repo 的应用"等细粒度控制。


Flux 的多租户模型更贴近 Kubernetes 原生，每个租户在自己的命名空间中创建 GitRepository 和 Kustomization 资源，通过 ServiceAccount 的 RBAC 权限控制资源操作范围。平台团队在 flux-system 命名空间管理基础设施组件，应用团队在各自命名空间管理应用配置。


小结
    

  • Argo CD 提供开箱即用的 Web UI 和丰富功能集，适合需要可视化管理的团队
    • 

  • Flux 的微服务架构更轻量灵活，原生镜像自动化和声明式依赖编排是独特优势
    • 

  • ApplicationSet（Argo CD）和 Kustomization 依赖链（Flux）分别解决规模化部署问题
    • 

  • 多集群管理推荐 Hub-Spoke 模式，多租户通过 AppProject 或命名空间 RBAC 隔离
    • 

  • 两者都支持 Kustomize 和 Helm，选择取决于团队对 UI、扩展性和架构偏好的权重
    • 

  • 企业采用通常从一个工具开始标准化，避免同时运维两套 GitOps 系统的管理成本
    •
