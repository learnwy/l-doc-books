主从复制与多主复制

概述

数据复制是分布式系统实现高可用性、低延迟和读扩展的基础机制。通过在多个节点上维护数据的副本，系统能够在部分节点故障时继续提供服务，并允许用户就近读取数据以降低延迟。复制的核心挑战在于：如何在多个副本之间保持数据一致性，同时不过度牺牲性能和可用性。

本文系统介绍三种主流复制模型的架构设计、一致性保证和工程权衡，帮助工程师在实际系统中做出合理的复制策略选择。

核心概念

单主复制（Leader-Follower）

单主复制是最广泛使用的复制模型，其核心规则简单：所有写入必须经过唯一的主节点（Leader），从节点（Follower）异步或同步复制主节点的变更日志。

CRDT 示例 — G-Counter（增长计数器）：


class GCounter:
    """每个节点维护自己的计数器，总值为所有节点之和"""
    def __init__(self, node_id, nodes):
        self.node_id = node_id
        self.counts = {n: 0 for n in nodes}

    def increment(self):
        self.counts[self.node_id] += 1

    def value(self):
        return sum(self.counts.values())

    def merge(self, other):
        """合并操作：取每个节点的最大值 (满足交换律和幂等性)"""
        for node in self.counts:
            self.counts[node] = max(self.counts[node], other.counts[node])
无主复制（Leaderless）
无主复制模型（Dynamo 风格）中没有固定的主节点，客户端直接向多个节点发送读写请求：


Quorum 机制：


给定 N 个副本，写入 W 个节点成功、读取 R 个节点：


    

  • 当 W + R > N 时，读取至少能获得一个最新值
    • 

  • 典型配置：N=3, W=2, R=2
    • 



N=3 的常见配置：

W=3, R=1: 写入必须全部成功，读取任一节点即可 (写慢读快)
W=2, R=2: 平衡配置 (容忍一个节点故障)
W=1, R=3: 写入极快，读取需要全部节点 (适合写密集)
反熵修复机制：


    

  • 读修复（Read Repair）：读取时发现过期副本，后台触发更新
    • 

  • 反熵进程（Anti-Entropy）：后台线程周期性比较副本，修复差异
    • 

  • Merkle Tree：高效检测副本间数据差异
    •

处理复制延迟的应用层策略
class ReplicationAwareClient:
    """应用层处理复制延迟的策略"""

    def __init__(self, master_conn, replica_conns):
        self.master = master_conn
        self.replicas = replica_conns
        self._last_write_ts = {}

    def write(self, user_id, query):
        """写入走主库，记录写入时间"""
        result = self.master.execute(query)
        self._last_write_ts[user_id] = time.time()
        return result

    def read(self, user_id, query, consistency='eventual'):
        """读取时根据一致性要求选择节点"""
        if consistency == 'strong':
            # 强一致性：总是读主库
            return self.master.execute(query)

        if consistency == 'read_your_writes':
            # 读己之写：刚写入后短时间内读主库
            last_write = self._last_write_ts.get(user_id, 0)
            if time.time() - last_write < 5:  # 5秒窗口
                return self.master.execute(query)

        # 最终一致性：读从库（负载均衡）
        replica = random.choice(self.replicas)
        return replica.execute(query)

总结
复制模型的选择本质上是在一致性、可用性、延迟和复杂度之间的权衡。单主复制提供最简单的一致性模型，是大多数场景的默认选择；多主复制为多区域部署和离线应用提供了写入灵活性，代价是冲突处理的复杂度；无主复制通过去中心化实现了极致的可用性，但要求应用层处理数据不一致的情况。


2026 年的趋势是越来越多的系统采用 Raft/Paxos 共识协议作为复制基础（如 TiDB、CockroachDB、etcd），在保证强一致性的同时通过 Multi-Group 机制实现水平扩展。工程师应当根据业务的一致性需求和部署拓扑做出选择，而非盲目追求"最强"的一致性保证。
