复制一致性与共识算法

概述

在分布式系统中，复制引入了数据副本之间的不一致窗口，而共识算法则是实现副本间强一致性的基础设施。理解不同一致性级别的语义差异，以及共识算法如何在节点故障和网络分区下保证正确性，是设计可靠分布式系统的核心能力。

本文从复制延迟引出的一致性问题出发，系统梳理各级一致性模型的定义与工程语义，并深入 Raft 共识算法的完整实现机制。

核心概念

一致性级别谱系

分布式系统中的一致性保证形成了一个从强到弱的连续谱系：

级别 保证 性能代价 典型系统
线性一致性 (Linearizability) 所有操作如同在单节点上顺序执行 极高 ZooKeeper, etcd
顺序一致性 (Sequential) 所有节点看到相同的操作顺序 高 很少单独使用
因果一致性 (Causal) 有因果关系的操作保持顺序 中 COPS, MongoDB Causal
读己之写 (Read-your-writes) 用户总能看到自己的写入 低 大多数 Web 应用
单调读 (Monotonic reads) 不会看到比之前更旧的数据 低 会话一致性
最终一致性 (Eventual) 副本最终会收敛 最低 DynamoDB, Cassandra

线性一致性详解

线性一致性是最强的一致性模型，要求系统表现得如同只有一个数据副本：

时间轴:
Client A: |---write(x=1)---|
Client B:           |---read(x)---| → 必须返回 1
Client C:     |---read(x)---|       → 可能返回 0 或 1
                                      (写入尚未完成时)

核心约束: 一旦任何读取返回了新值，所有后续读取必须返回新值

因果一致性
因果一致性只保证有因果关系的操作被所有节点以相同顺序观察到：


操作 1: Alice 发帖 "Hello"         (事件 A)
操作 2: Bob 回复 "Hi Alice!"       (事件 B, 因果依赖 A)
操作 3: Carol 发帖 "Good morning"  (事件 C, 与 A/B 无因果关系)

因果一致性保证:
- 所有节点都先看到 A 再看到 B (因果顺序)
- C 相对于 A/B 的顺序在不同节点可以不同 (并发操作)
向量时钟实现因果追踪：


class VectorClock:
    """向量时钟 - 追踪事件间的因果关系"""
    def __init__(self, node_id, num_nodes):
        self.node_id = node_id
        self.clock = [0] * num_nodes

    def increment(self):
        """本地事件发生时递增"""
        self.clock[self.node_id] += 1
        return self.clock.copy()

    def update(self, other_clock):
        """收到消息时合并时钟"""
        for i in range(len(self.clock)):
            self.clock[i] = max(self.clock[i], other_clock[i])
        self.clock[self.node_id] += 1

    def happens_before(self, other):
        """判断因果关系: self → other?"""
        return (all(s <= o for s, o in zip(self.clock, other))
                and any(s < o for s, o in zip(self.clock, other)))

    def concurrent(self, other):
        """判断并发: 两个事件无因果关系"""
        return (not self.happens_before(other)
                and not other.happens_before(self.clock))
Raft 共识算法
Raft 是当前最广泛使用的共识算法，通过 Leader 选举、日志复制和安全性保证实现强一致性：


Raft 核心机制：






机制
功能
保证





Leader Election
选举唯一的 Leader
每个 Term 最多一个 Leader




Log Replication
Leader 将日志复制到 Follower
日志一旦提交不会丢失




Safety
限制哪些节点可以成为 Leader
新 Leader 包含所有已提交日志




Membership Change
集群成员变更
变更过程不会产生脑裂





日志复制流程：


Term 3, Leader = Node A

1. Client → Leader: Write(x=5)
2. Leader: Append to local log [Term=3, Index=7, cmd=set(x,5)]
3. Leader → All Followers: AppendEntries RPC
4. Follower: Append to log, respond success
5. Leader: Majority (3/5) responded → Commit index 7
6. Leader → Client: Success
7. Leader → Followers: Update commit index (via next heartbeat)
Multi-Raft
单 Raft 组的吞吐受限于 Leader 节点。Multi-Raft 将数据划分为多个 Raft Group，每个 Group 独立进行共识：


Data Partition 1 → Raft Group 1 (Leader on Node A)
Data Partition 2 → Raft Group 2 (Leader on Node B)
Data Partition 3 → Raft Group 3 (Leader on Node C)
...

优点: Leader 负载分散到多个节点，总吞吐线性扩展
缺点: 跨 Group 事务需要额外协调 (2PC 或 Percolator)
典型实现: TiKV, CockroachDB, etcd (单 Group)

// etcd 线性一致性读实现 (简化版)
func (s *EtcdServer) linearizableRead(ctx context.Context) error {
    // 1. 获取当前 Leader 的 commit index
    commitIndex := s.getCommitIndex()

    // 2. 向集群发送 ReadIndex 请求确认 Leadership
    //    (防止读到已经不是 Leader 的旧节点)
    if err := s.confirmLeadership(ctx); err != nil {
        return err
    }

    // 3. 等待本地 applied index >= commit index
    //    确保本地状态机已经应用了所有已提交的日志
    if err := s.waitApplied(ctx, commitIndex); err != nil {
        return err
    }

    // 4. 从本地状态机读取 (此时保证线性一致)
    return nil
}
Quorum 读写实现
class QuorumStore:
    """Dynamo 风格 Quorum 读写"""
    def __init__(self, nodes, n=3, w=2, r=2):
        self.nodes = nodes
        self.n = n  # 副本数
        self.w = w  # 写入仲裁数
        self.r = r  # 读取仲裁数
        assert w + r > n, "Must satisfy W + R > N for consistency"

    async def write(self, key, value):
        version = self._generate_version()
        results = await asyncio.gather(*[
            node.put(key, value, version)
            for node in self._get_replicas(key)
        ], return_exceptions=True)

        successes = sum(1 for r in results if not isinstance(r, Exception))
        if successes >= self.w:
            return {'status': 'ok', 'version': version}
        raise WriteFailure(f"Only {successes}/{self.w} writes succeeded")

    async def read(self, key):
        results = await asyncio.gather(*[
            node.get(key)
            for node in self._get_replicas(key)
        ], return_exceptions=True)

        valid = [r for r in results if not isinstance(r, Exception)]
        if len(valid) < self.r:
            raise ReadFailure(f"Only {len(valid)}/{self.r} reads succeeded")

        # 返回版本最高的值
        latest = max(valid, key=lambda x: x['version'])

        # 读修复: 将最新值写回过期节点
        self._async_read_repair(key, latest, valid)
        return latest

总结
一致性与共识是分布式系统正确性的基石。工程师需要深刻理解：线性一致性虽然提供最强保证但代价高昂；因果一致性在保证正确因果关系的同时保留了良好的性能特性；最终一致性在大多数互联网场景下是合理且高效的选择。


Raft 共识算法通过 Leader 选举和日志复制的清晰抽象，使得强一致性复制变得可工程化。Multi-Raft 通过数据分片将吞吐从单 Leader 瓶颈中解放出来。在 2026 年的实践中，共识算法已经从"学术概念"变为"基础设施组件"——几乎所有 NewSQL 数据库都内置了 Raft 或 Paxos 变体，工程师的工作重心从"实现共识"转向"选择合适的一致性级别并正确配置"。
