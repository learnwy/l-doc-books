存储引擎对比：LSM-Tree 与 B-Tree

概述

存储引擎是数据库的心脏，决定了数据如何被写入磁盘、如何被检索、以及系统在不同工作负载下的性能表现。当前主流的两种存储引擎架构——LSM-Tree（Log-Structured Merge-Tree）和 B-Tree——代表了两种截然不同的设计哲学：前者为写优化而生，后者为读优化而设计。

理解两者的内部机制和工程权衡，是做出正确数据库选型的前提。MySQL（InnoDB）、PostgreSQL 默认使用 B-Tree；RocksDB、LevelDB、Cassandra、ScyllaDB 使用 LSM-Tree；而 TiDB、CockroachDB 等 NewSQL 系统则在 LSM-Tree 之上构建分布式事务层。

核心概念

B-Tree 的工作原理

B-Tree（及其变体 B+ Tree）是自 1970 年以来最广泛使用的数据库索引结构。其核心思想是将数据组织为固定大小的页（通常 4KB-16KB），形成平衡的树形结构：

          [Root Page: 30 | 70]
         /         |          \
   [10|20]      [40|50|60]     [80|90]
   /  |  \      / | | \       /  |  \
 [数据页]  [数据页]  ...    [数据页]

关键特性：

特性 说明
就地更新（Update-in-place） 修改数据时直接覆写对应页
WAL（Write-Ahead Log） 写入前先记录日志，保证崩溃恢复
页分裂与合并 节点满时分裂，空闲时合并
排序存储 叶节点按键顺序链接，支持高效范围查询

写入流程：

  1. 通过 WAL 记录变更意图（顺序写）
  2. 定位目标页（树遍历，O(log N) 次 I/O）
  3. 在内存中修改页内容
  4. 异步将脏页刷回磁盘（随机写）

LSM-Tree 的工作原理

LSM-Tree 由 O'Neil 等人在 1996 年提出，其核心理念是将随机写转化为顺序写，通过分层合并实现高写入吞吐：

实战指南
量化对比：写放大分析
写放大（Write Amplification）是衡量存储引擎效率的核心指标，定义为实际写入磁盘的数据量与应用层写入量的比值。


B-Tree 写放大分析：


应用写入 1 byte →
  WAL 写入: ~1x (含元数据开销)
  页写入: 至少写一整页 (4KB-16KB)
  → 最坏情况写放大: 16KB / 1B = 16,384x
  → 典型情况 (批量写入): 2-5x
LSM-Tree 写放大分析（Leveled Compaction）：


假设放大因子 T=10, 层数 L:
  每层 Compaction 写入约 T 倍数据
  总写放大 ≈ T * L (理论上界)
  → RocksDB 默认: 10 * 5-7 层 ≈ 50-70x
  → 实际测量 (含压缩): 10-30x
读路径对比
# B-Tree 读路径 (伪代码)
def btree_read(key):
    page = root_page
    while not page.is_leaf:
        # 二分查找定位子页 - 1次磁盘 I/O
        page = page.find_child(key)
    return page.find_value(key)
    # 总 I/O: O(log_B N), 通常 3-4 次

# LSM-Tree 读路径 (伪代码)
def lsm_read(key):
    # 1. 查 MemTable (内存)
    if result := memtable.get(key):
        return result
    # 2. 逐层查 SSTable (磁盘)
    for level in levels:
        if level.bloom_filter.may_contain(key):
            if result := level.search(key):
                return result
    return NOT_FOUND
    # 最坏 I/O: 每层 1 次, 共 L 层

调优建议
B-Tree 调优：


    

  • 增大 Buffer Pool 减少磁盘 I/O（推荐分配 70-80% 可用内存）
    • 

  • 调整页大小匹配工作负载（大页适合顺序扫描，小页适合随机点查）
    • 

  • 启用 Change Buffer 优化二级索引写入（InnoDB）
    • 

  • 关注页分裂频率，必要时预分配空间
    • 



LSM-Tree 调优：


    

  • 合理设置 MemTable 大小（过小导致频繁 flush，过大增加恢复时间）
    • 

  • 选择匹配工作负载的 Compaction 策略
    • 

  • 配置 Bloom Filter 位数（通常 10 bits/key，假阳性率 ~1%）
    • 

  • 限制 L0 文件数防止读放大
    • 

  • 启用 Rate Limiter 避免 Compaction 风暴影响前台请求
    • 



2026 年趋势：混合引擎
现代系统越来越倾向于混合使用两种引擎：

  • CockroachDB：底层 Pebble（LSM-Tree），上层 SQL 接口

总结
LSM-Tree 和 B-Tree 的选择本质上是写优化 vs 读优化的工程权衡。没有绝对更好的存储引擎，只有更匹配工作负载的选择。关键决策维度包括：读写比例、延迟敏感度、空间效率需求、运维复杂度容忍度。


在 2026 年的技术格局中，存算分离架构使得存储引擎的选择更加灵活——对象存储成为通用持久层，LSM-Tree 和 B-Tree 的角色正在从"数据存储"演变为"数据组织与索引"，这一趋势在 DDIA 第二版中被深入讨论。工程师应当建立对两种引擎内部机制的深入理解，在实际架构设计中做出有据可依的选型决策。
