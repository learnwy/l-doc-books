列式存储与 OLAP 优化

概述

列式存储（Columnar Storage）是面向分析型查询（OLAP）场景的存储架构创新。与传统行式存储逐行组织数据不同，列式存储将同一列的所有值连续存放在一起。这种看似简单的组织方式变革，带来了压缩率、查询性能和向量化执行三个维度的量级提升。

在数据仓库和实时分析领域，ClickHouse 单节点可在亚秒内扫描数十亿行、DuckDB 让笔记本电脑具备 TB 级分析能力——这些成就的基础都是列式存储架构。理解列式存储的设计决策，是构建高效数据分析系统的必备知识。

核心概念

行式存储 vs 列式存储

行式存储 (Row-oriented):
Row 1: [id=1, name="Alice", age=30, city="Beijing", salary=50000]
Row 2: [id=2, name="Bob",   age=25, city="Shanghai", salary=45000]
Row 3: [id=3, name="Carol", age=35, city="Beijing", salary=60000]

列式存储 (Column-oriented):
id:     [1, 2, 3, ...]
name:   ["Alice", "Bob", "Carol", ...]
age:    [30, 25, 35, ...]
city:   ["Beijing", "Shanghai", "Beijing", ...]
salary: [50000, 45000, 60000, ...]

性能影响分析：

维度 行式存储 列式存储 分析场景优势
I/O 量 读取整行（含不需要的列） 仅读取查询涉及的列 列存减少 10-100x I/O
压缩率 混合类型，压缩率低 同类型数据，压缩率高 列存 3-10x 更高压缩率
向量化执行 逐行处理，缓存不友好 批量处理同类型数据 列存 5-10x CPU 效率
写入效率 追加一行简单高效 需要写入多个列文件 行存更适合事务写入
点查询 一次 I/O 获取完整行 需要跨列组装 行存更优

列式压缩技术

同列数据具有相同类型和相似分布，使得高效压缩成为可能：

压缩技术 原理 适用场景 压缩比
Run-Length Encoding (RLE) 连续重复值存储为 (值, 次数) 排序列、低基数列 10-1000x
Dictionary Encoding 将值映射为整数字典 ID 字符串列、枚举列 5-20x
Bit Packing 用最少位数表示整数值 小范围整数 2-8x
Delta Encoding 存储相邻值的差值 时间戳、自增 ID 5-50x
Frame of Reference (FOR) 块内值减去最小值 范围有限的数值 2-4x
LZ4 / ZSTD 通用无损压缩 通用后置压缩 2-5x

压缩示例：

原始数据 (city 列, 100万行):
["Beijing", "Shanghai", "Beijing", "Beijing", "Guangzhou", ...]

Step 1: 排序后 RLE
[("Beijing", 450000), ("Guangzhou", 150000), ("Shanghai", 400000)]

Step 2: Dictionary Encoding
Dictionary: {0: "Beijing", 1: "Guangzhou", 2: "Shanghai"}
Data: [0, 0, 0, ..., 1, 1, ..., 2, 2, ...]

压缩前: 100万 × 平均8字节 = 8MB
压缩后: 字典 30B + 位图 ≈ 125KB
压缩比: 64x

向量化执行引擎

列式存储天然适配向量化执行（Vectorized Execution），即一次操作处理一批同类型值而非逐行处理：

// 传统逐行执行 (Volcano Model)
for each row in table:
    if row.age > 30:
        sum += row.salary

// 向量化执行 (Batch Processing)
// 一次处理 1024 个值，充分利用 CPU SIMD 指令
age_batch = load_column_chunk("age", offset, 1024)
mask = simd_compare_gt(age_batch, 30)  // 一条指令比较 1024 个值
salary_batch = load_column_chunk("salary", offset, 1024)
sum += simd_masked_sum(salary_batch, mask)
向量化执行的性能优势来源：


    

  1. CPU Cache 友好：连续内存访问，L1/L2 缓存命中率高
    2. 

  2. SIMD 指令利用：AVX-512 一次处理 64 字节（16 个 int32）
    3. 

  3. 分支预测友好：批量判断减少 CPU 分支预测失败
    4. 

  4. 编译优化：编译器更容易对循环进行自动向量化
    5.

实战指南
ClickHouse 实践：MergeTree 引擎
ClickHouse 的 MergeTree 引擎结合了 LSM-Tree 的写入模式和列式存储的查询优势：


-- 创建分析表
CREATE TABLE events (
    event_date Date,
    user_id    UInt64,
    event_type LowCardinality(String),  -- 自动字典编码
    properties String,
    metric     Float64
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(event_date)     -- 按月分区
ORDER BY (event_type, user_id, event_date)  -- 排序键 (影响压缩和查询)
SETTINGS index_granularity = 8192;     -- 稀疏索引粒度

-- 典型分析查询：扫描数十亿行在亚秒完成
SELECT
    event_type,
    count() AS cnt,
    uniq(user_id) AS unique_users,
    avg(metric) AS avg_metric
FROM events
WHERE event_date >= '2026-01-01'
  AND event_date < '2026-02-01'
GROUP BY event_type
ORDER BY cnt DESC
LIMIT 20;
DuckDB 实践：嵌入式 OLAP
import duckdb

# DuckDB 直接查询 Parquet 文件（无需导入）
con = duckdb.connect()

# 查询 10GB Parquet 数据集
result = con.execute("""
    SELECT
        l_returnflag,
        l_linestatus,
        sum(l_quantity) as sum_qty,
        sum(l_extendedprice) as sum_base_price,
        avg(l_discount) as avg_disc
    FROM read_parquet('s3://bucket/lineitem/*.parquet')
    WHERE l_shipdate <= DATE '2026-01-01' - INTERVAL 90 DAY
    GROUP BY l_returnflag, l_linestatus
    ORDER BY l_returnflag, l_linestatus
""").fetchdf()

列式存储下的建模建议：


    

  • 预聚合宽表优于多表 JOIN（列存 JOIN 代价高）

  • 利用 Dictionary Encoding 容忍冗余字符串列

最佳实践
排序键选择策略
排序键（Sort Key / ORDER BY）是列式存储性能优化的核心杠杆：


    

  1. 高频过滤列作为前缀：排序后相同值连续存放，RLE 压缩极高效
    2. 

  2. 基数从低到高排列：低基数列排在前面，压缩效果最佳
    3. 

  3. 考虑查询模式：如果 90% 查询按 (tenant_id, date) 过滤，则以此为排序键
    4. 

  4. 避免高基数列作前缀：UUID 等高基数列会破坏压缩效果
    5.

总结
列式存储通过三个核心机制实现 OLAP 场景的性能飞跃：列裁剪大幅减少 I/O、同类型压缩提升存储效率、向量化执行充分利用现代 CPU。在 2026 年的数据分析生态中，列式存储已从"专用优化"变为"默认选择"。


关键设计决策包括：排序键的选择直接决定压缩率和查询性能；分区策略影响数据生命周期管理和裁剪效率；文件格式的选择（Parquet vs Arrow vs 专有格式）取决于数据交换需求和查询引擎集成度。工程师应当建立"列思维"——将每一列视为独立的压缩数据流，从列的视角思考数据组织与查询优化。
