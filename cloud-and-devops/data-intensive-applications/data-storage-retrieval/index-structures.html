索引结构与查询优化

概述

索引是数据库从海量数据中高效定位目标记录的关键机制。一个精心设计的索引可以将查询时间从线性扫描的 O(N) 降低到对数级别的 O(log N) 甚至常数级别的 O(1)。然而索引并非免费午餐——每个索引都会增加写入开销和存储空间占用，工程师必须在查询加速与写入性能之间做出权衡。

本文从经典 B+ 树索引出发，系统介绍各类索引结构的设计原理、适用场景和性能特征，覆盖从 OLTP 到全文搜索再到向量检索的完整索引知识体系。

核心概念

B+ 树索引

B+ 树是关系型数据库最普遍的索引实现。与 B-Tree 不同，B+ 树将所有数据存储在叶节点，内部节点仅保存路由键：

内部节点: [key1 | ptr1 | key2 | ptr2 | ... | keyN | ptrN+1]
叶节点:   [key1:val1 | key2:val2 | ... ] → next_leaf

索引类型矩阵：

类型 结构 适用查询 空间开销 写入代价
主键索引 (Clustered) 数据按主键物理排序 主键查找、范围扫描 无额外开销 页分裂
二级索引 (Non-clustered) 独立 B+ 树指向主键 非主键条件查询 额外树空间 双重写入
复合索引 多列组合的 B+ 树 多条件组合查询 列数 × 数据量 高
覆盖索引 (Covering) 包含查询所需全部列 避免回表 高 高
前缀索引 仅索引字符串前 N 字符 模糊前缀匹配 低 低

复合索引与最左前缀原则

复合索引按列顺序排序，遵循最左前缀匹配规则：

-- 创建复合索引 (a, b, c)
CREATE INDEX idx_abc ON orders(user_id, status, created_at);

-- 可以使用索引的查询:
SELECT * FROM orders WHERE user_id = 100;                    -- ✓ 使用 (a)
SELECT * FROM orders WHERE user_id = 100 AND status = 'paid'; -- ✓ 使用 (a,b)
SELECT * FROM orders WHERE user_id = 100 AND status = 'paid'
  AND created_at > '2026-01-01';                             -- ✓ 使用 (a,b,c)

-- 无法使用索引的查询:
SELECT * FROM orders WHERE status = 'paid';                  -- ✗ 跳过了 a
SELECT * FROM orders WHERE created_at > '2026-01-01';        -- ✗ 跳过了 a,b

哈希索引

哈希索引通过哈希函数将键映射到固定位置，实现 O(1) 的等值查找：

hash(key) → bucket_id → value

优点: 等值查询极快
缺点: 不支持范围查询、不支持排序、哈希冲突处理
适用: 内存数据库 (Redis)、等值连接优化

主要实现：

  • Bitcask（Riak 的存储引擎）：内存中维护哈希表，磁盘追加写
  • Memory-optimized tables（SQL Server In-Memory OLTP）

倒排索引

倒排索引是全文搜索的基础数据结构，将"词项→文档列表"的映射关系持久化：

词典 (Term Dictionary):
  "distributed" → [doc1, doc5, doc12, doc89]
  "systems"     → [doc1, doc3, doc5, doc12]
  "database"    → [doc2, doc5, doc7, doc12]

查询 "distributed AND systems":
  交集 → [doc1, doc5, doc12]

倒排索引的组件：

组件 功能 技术实现
Term Dictionary 词项到 Posting List 的映射 FST (Finite State Transducer)
Posting List 包含词项的文档 ID 列表 压缩整数列表 (VInt, PFor)
Term Frequency 词项在文档中的出现频率 TF-IDF 评分
Position 词项在文档中的位置 支持短语查询
Norm 文档长度归一化因子 BM25 评分

向量索引（ANN 索引）

随着 AI 应用的普及，向量索引成为 2024-2026 年最受关注的索引类型。向量索引解决的是高维空间中近似最近邻（ANN）搜索问题：

算法 原理 召回率 构建时间 查询延迟 内存占用
HNSW 层次化导航小世界图 高 (>95%) 高 低 高
IVF-PQ 倒排索引 + 乘积量化 中-高 中 中 低
ScaNN Google 的 AH 量化 高 中 极低 中
DiskANN 磁盘友好的图索引 高 极高 中 低(磁盘)
Flat (暴力) 全量距离计算 100% O(1) O(N) 低 
空间索引
用于地理空间数据的高效查询：


    

  • R-Tree：将空间对象包围在最小边界矩形（MBR）中，构建层次结构
    • 

  • Geohash：将二维坐标编码为一维字符串，利用前缀匹配实现空间查询
    • 

  • S2 Geometry：Google 开发，将地球表面映射到 Hilbert 曲线上的单元格

实战指南
索引设计方法论
-- 步骤 1: 分析查询模式
EXPLAIN ANALYZE SELECT * FROM orders
WHERE user_id = 100 AND status = 'paid'
ORDER BY created_at DESC LIMIT 20;

-- 步骤 2: 识别选择性
SELECT
  COUNT(DISTINCT user_id) / COUNT(*) AS user_selectivity,
  COUNT(DISTINCT status) / COUNT(*) AS status_selectivity
FROM orders;
-- user_selectivity: 0.85 (高选择性 → 适合放前面)
-- status_selectivity: 0.0001 (低选择性 → 放后面)

-- 步骤 3: 创建优化索引
CREATE INDEX idx_orders_covering ON orders(user_id, status, created_at DESC)
INCLUDE (order_amount, product_id);  -- 覆盖索引避免回表

向量索引实战：构建语义搜索
import numpy as np
from hnswlib import Index

# 构建 HNSW 索引
dim = 768  # BERT embedding 维度
num_elements = 1_000_000

index = Index(space='cosine', dim=dim)
index.init_index(
    max_elements=num_elements,
    ef_construction=200,  # 构建精度 (越高越慢但召回率更高)
    M=16                  # 每个节点的最大连接数
)

# 插入向量
vectors = np.random.randn(num_elements, dim).astype('float32')
index.add_items(vectors, ids=np.arange(num_elements))

# 查询
index.set_ef(50)  # 查询时的搜索范围
query = np.random.randn(1, dim).astype('float32')
labels, distances = index.knn_query(query, k=10)

索引维护策略
-- 定期检查索引使用情况 (PostgreSQL)
SELECT
  schemaname, tablename, indexname,
  idx_scan,       -- 索引被使用的次数
  idx_tup_read,   -- 通过索引读取的行数
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;  -- 未使用的索引排在前面

-- 索引膨胀检查
SELECT
  pg_size_pretty(pg_relation_size(indexrelid)) AS size,
  100 * (1 - avg_leaf_density / 90) AS bloat_pct
FROM pgstatindex('idx_orders_user_id');
复合索引列顺序原则
    

  1. 等值条件列优先：精确匹配的列放前面

  2. 高选择性列优先：唯一值比例高的列靠前

  3. 范围条件列靠后：范围查询会中断后续列的索引使用

总结
索引结构的选择应当由查询模式驱动。B+ 树索引适合 OLTP 场景的等值和范围查询；倒排索引是全文搜索的标准方案；向量索引解决了 AI 时代的语义相似性检索需求；空间索引则服务于地理位置应用。


工程师需要建立"索引成本意识"——每个索引都有写入代价、存储代价和维护代价。最佳的索引策略不是"为所有查询建索引"，而是根据 80/20 法则，为最关键的查询路径建立最少但最有效的索引组合。在 2026 年的实践中，混合索引（如 PostgreSQL 同时使用 B+ 树、GIN、GiST 和 HNSW）已成为复杂应用的标准配置。
