分布式一致性模型

概述

分布式一致性模型定义了系统在面对并发操作、网络延迟和节点故障时，向外部观察者提供什么样的行为保证。从最强的线性一致性到最弱的最终一致性，每个级别都代表了正确性与性能之间的不同权衡点。深入理解这些模型的形式化定义和工程含义，是设计正确分布式系统的理论基础。

本文系统梳理主流一致性模型的层次关系，结合 CAP、PACELC 定理分析其在实际系统中的体现，为工程师提供一致性选择的理论指导。

核心概念

一致性模型层次图

线性一致性（Linearizability）
线性一致性要求所有操作等效于在某个全局时间轴上的原子操作：


形式化定义:
  对于任何执行历史 H，存在一个合法的顺序 S，使得:
  1. S 包含 H 中所有已完成的操作 (及部分未完成操作)
  2. 对于 H 中 op1 在 op2 之前完成的情况，在 S 中 op1 排在 op2 之前
  3. S 中每个读操作返回最近一次写操作的值
线性一致性检验示例：


时间 →
Client A: |--write(x=1)--|
Client B:       |--read(x)→?--|
Client C:            |--write(x=2)--|
Client D:                  |--read(x)→?--|

合法线性化:
  write(x=1), read(x)→1, write(x=2), read(x)→2  ✓
  write(x=1), write(x=2), read(x)→2, read(x)→2  ✓

非法 (违反线性一致性):
  Client B 读到 1, Client D 读到 1  (如果 write(x=2) 已返回成功)

因果一致性（Causal Consistency）
因果一致性只保序"有因果关系"的操作，允许"无因果关系"的并发操作被不同节点以不同顺序观察：


# 因果关系的三种来源:
# 1. 进程顺序: 同一客户端的操作有因果关系
# 2. 读写依赖: 读取某值后基于该值的写入有因果关系
# 3. 传递性: A→B, B→C 则 A→C

class CausalStore:
    """基于 Lamport 时钟的因果一致性实现"""
    def __init__(self, node_id):
        self.node_id = node_id
        self.logical_clock = 0
        self.data = {}
        self.pending = []  # 等待因果依赖满足的操作

    def write(self, key, value, causal_deps):
        """写入时附带因果依赖"""
        self.logical_clock += 1
        entry = {
            'key': key,
            'value': value,
            'timestamp': (self.logical_clock, self.node_id),
            'deps': causal_deps  # 因果前驱的时间戳列表
        }
        self.data[key] = entry
        self._broadcast(entry)

    def deliver(self, entry):
        """收到远程写入时检查因果依赖是否满足"""
        if self._deps_satisfied(entry['deps']):
            self._apply(entry)
            self._check_pending()
        else:
            self.pending.append(entry)  # 依赖未满足，暂存

    def _deps_satisfied(self, deps):
        """检查所有因果前驱是否已应用"""
        for dep_ts in deps:
            if not self._has_applied(dep_ts):
                return False
        return True

会话保证（Session Guarantees）：


class SessionGuarantees:
    """在最终一致性之上提供会话级保证"""

    def __init__(self, client_id):
        self.client_id = client_id
        self.read_set = {}   # 已读取的版本号
        self.write_set = {}  # 已写入的版本号

    def read_your_writes(self, key, replicas):
        """保证读到自己的写入"""
        my_write_version = self.write_set.get(key, 0)
        for replica in replicas:
            value, version = replica.get(key)
            if version >= my_write_version:
                self.read_set[key] = version
                return value
        # 所有副本都落后: 路由到主节点
        return self._read_from_primary(key)

    def monotonic_reads(self, key, replicas):
        """保证不会读到比之前更旧的值"""
        last_read_version = self.read_set.get(key, 0)
        for replica in replicas:
            value, version = replica.get(key)
            if version >= last_read_version:
                self.read_set[key] = version
                return value
        return self._read_from_primary(key)
CAP 定理与 PACELC
CAP 定理：


在网络分区（P）发生时，系统必须在一致性（C）和可用性（A）之间选择。


重要澄清:
- CAP 中的 C 特指线性一致性 (最强级别)
- CAP 中的 A 指所有非故障节点都能响应请求
- CAP 不是"三选二"而是"分区时二选一"
- 正常运行时 (无分区)，可以同时提供 C 和 A
PACELC 模型（Daniel Abadi, 2012）：


IF Partition:
  Choose Availability or Consistency (same as CAP)
ELSE (normal operation):
  Choose Latency or Consistency

完整表述: PA/EL, PA/EC, PC/EL, PC/EC

系统分类:
  DynamoDB, Cassandra: PA/EL (分区时选 A, 正常时选低延迟)
  MongoDB (默认):     PA/EC (分区时选 A, 正常时选一致性)
  Spanner, etcd:      PC/EC (分区时选 C, 正常时也选一致性)
  PNUTS (Yahoo):      PC/EL (分区时选 C, 正常时选低延迟)

一致性级别测试工具
# 使用 Jepsen 风格的一致性检验
class LinearizabilityChecker:
    """检验系统是否满足线性一致性"""

    def __init__(self):
        self.history = []  # [(op_type, key, value, start_time, end_time)]

    def record_operation(self, op_type, key, value, start, end):
        self.history.append({
            'type': op_type,  # 'write' or 'read'
            'key': key,
            'value': value,
            'start': start,
            'end': end
        })

    def check(self):
        """检查历史是否可线性化 (NP-complete, 小规模可穷举)"""
        ops = sorted(self.history, key=lambda x: x['start'])
        return self._try_linearize(ops, [], {})

    def _try_linearize(self, remaining, linearized, state):
        if not remaining:
            return True
        # 尝试将每个可选操作放在当前位置
        candidates = [op for op in remaining
                      if not self._must_come_after(op, linearized)]
        for op in candidates:
            if self._is_valid(op, state):
                new_state = self._apply(op, state.copy())
                new_remaining = [o for o in remaining if o != op]
                if self._try_linearize(new_remaining, linearized + [op], new_state):
                    return True
        return False
系统设计中的一致性选择
# 电商系统的一致性策略设计
services:
  order-service:
    consistency: serializable # 订单状态变更需要强一致
    implementation: single-leader with sync replication

  inventory-service:
    consistency: linearizable # 库存扣减不允许超卖
    implementation: raft consensus (TiKV)

  product-catalog:
    consistency: eventual # 商品信息秒级延迟可接受
    implementation: async replication + CDN cache

  user-profile:
    consistency: read-your-writes # 用户能看到自己的修改
    implementation: session-sticky routing to primary

  search-index:
    consistency: eventual # 搜索索引分钟级延迟可接受
    implementation: CDC → Elasticsearch async sync

  analytics:
    consistency: eventual # 数据分析允许小时级延迟
    implementation: batch ETL to data warehouse
可调一致性（Tunable Consistency）
# Cassandra 风格的可调一致性
class TunableConsistencyClient:
    """按操作选择一致性级别"""

    def write_critical(self, key, value):
        """关键写入: 强一致性"""
        return self.session.execute(
            "INSERT INTO data (key, value) VALUES (?, ?)",
            [key, value],
            consistency_level=ConsistencyLevel.QUORUM  # W = N/2 + 1
        )

    def write_fire_and_forget(self, key, value):
        """日志类写入: 高吞吐"""
        return self.session.execute(
            "INSERT INTO logs (key, value) VALUES (?, ?)",
            [key, value],
            consistency_level=ConsistencyLevel.ONE  # W = 1
        )

    def read_strong(self, key):
        """强一致性读取"""
        return self.session.execute(
            "SELECT value FROM data WHERE key = ?",
            [key],
            consistency_level=ConsistencyLevel.QUORUM
        )

    def read_fast(self, key):
        """就近读取（可能过期）"""
        return self.session.execute(
            "SELECT value FROM data WHERE key = ?",
            [key],
            consistency_level=ConsistencyLevel.LOCAL_ONE
        )

总结
分布式一致性模型提供了一个从强到弱的保证频谱，每个级别对应不同的性能代价和编程复杂度。工程师的核心能力不在于"实现最强一致性"，而在于"识别每个数据和操作的最低一致性需求"——用最弱的保证满足业务正确性，从而获得最优的性能和可用性。


2026 年的趋势是"混合一致性"成为主流：同一系统内不同数据采用不同一致性级别，关键路径使用共识协议保证线性一致性，非关键路径使用最终一致性优化性能。Jepsen 测试已经成为分布式数据库发布前的标配验证，一致性不再是靠信任而是靠工程验证来保证。
