ACID 与 BASE：事务语义对比

概述

ACID 和 BASE 是数据系统中两种对立的事务语义模型。ACID 源自关系型数据库的严格正确性保证，BASE 则是分布式系统为了可扩展性而做出的务实妥协。理解两者的精确语义、隔离级别的细微差异、以及它们之间的渐变关系，是做出正确数据一致性设计决策的基础。

本文从 ACID 四大特性的精确定义出发，深入分析各隔离级别的异常现象，然后对比 BASE 模型的设计哲学，帮助工程师建立完整的事务语义认知框架。

核心概念

ACID 特性精确定义

特性 含义 常见误解
Atomicity (原子性) 事务要么全部成功，要么全部回滚 不是指"同时执行"，而是指"不可分割"
Consistency (一致性) 事务将数据库从一个有效状态转移到另一个有效状态 是应用层属性，不完全由数据库保证
Isolation (隔离性) 并发事务互不干扰，如同串行执行 实际中通过隔离级别进行弱化
Durability (持久性) 已提交事务的数据不会丢失 受限于硬件故障范围

隔离级别与异常现象

SQL 标准定义了四个隔离级别，每个级别允许不同的并发异常：

隔离级别 脏读 不可重复读 幻读 写倾斜 性能
Read Uncommitted 可能 可能 可能 可能 最高
Read Committed 不可能 可能 可能 可能 高
Repeatable Read 不可能 不可能 可能 可能 中
Serializable 不可能 不可能 不可能 不可能 最低

异常现象详解：

-- 脏读 (Dirty Read): 读到未提交的数据
-- Transaction 1:
UPDATE accounts SET balance = 0 WHERE id = 1;  -- 未提交
-- Transaction 2:
SELECT balance FROM accounts WHERE id = 1;  -- 读到 0 (脏数据)
-- Transaction 1:
ROLLBACK;  -- 回滚了!

-- 不可重复读 (Non-repeatable Read): 同一事务内两次读取结果不同
-- Transaction 1:
SELECT balance FROM accounts WHERE id = 1;  -- 返回 1000
-- Transaction 2: COMMIT(UPDATE balance = 500 WHERE id = 1)
-- Transaction 1:
SELECT balance FROM accounts WHERE id = 1;  -- 返回 500 (变了!)

-- 幻读 (Phantom Read): 同一条件两次查询返回不同行集
-- Transaction 1:
SELECT * FROM bookings WHERE room = 'A' AND time = '10:00';  -- 0 行
-- Transaction 2: INSERT (room='A', time='10:00') + COMMIT
-- Transaction 1:
SELECT * FROM bookings WHERE room = 'A' AND time = '10:00';  -- 1 行!

-- 写倾斜 (Write Skew): 两个事务各自读取后做出冲突写入
-- 约束: 至少一个医生在值班
-- Transaction 1: SELECT count(*) FROM on_call → 2; UPDATE SET off_call WHERE id=1
-- Transaction 2: SELECT count(*) FROM on_call → 2; UPDATE SET off_call WHERE id=2
-- 两个事务都成功提交 → 没有医生在值班! (违反约束)

可序列化实现方案

方案 原理 吞吐量 适用场景
真正串行执行 单线程顺序执行事务 低 VoltDB, Redis 事务
两阶段锁定 (2PL) 读锁和写锁，执行完才释放 中 MySQL InnoDB (Serializable)
可序列化快照隔离 (SSI) 乐观并发+冲突检测 高 PostgreSQL, CockroachDB

SSI (Serializable Snapshot Isolation) 原理：

1. 事务开始时获取一致性快照 (与 MVCC 相同)
2. 事务正常执行读写 (不加锁)
3. 提交时检测冲突:
   - 检查读取的数据是否被其他已提交事务修改
   - 检查写入的数据是否与其他事务的读取条件冲突
4. 如果检测到冲突 → 中止事务 (乐观中止)
5. 如果无冲突 → 提交成功

优点: 读不阻塞写，写不阻塞读，吞吐量远高于 2PL
缺点: 高冲突场景下中止率高

BASE 模型

BASE 是 Eric Brewer 提出的与 ACID 对立的设计哲学：

属性 含义 工程体现
Basically Available 系统基本可用，允许部分失败 降级、限流而非停服
Soft state 状态可以有中间态 副本间允许短暂不一致
Eventually consistent 最终所有副本收敛到一致状态 异步复制、后台修复

MVCC（多版本并发控制）实现
大多数现代数据库使用 MVCC 实现 Read Committed 和 Repeatable Read：


class MVCCStore:
    """简化的 MVCC 实现"""
    def __init__(self):
        self.data = {}  # key → [(version, value, committed)]
        self.tx_counter = 0
        self.active_txns = set()

    def begin_transaction(self):
        self.tx_counter += 1
        tx_id = self.tx_counter
        self.active_txns.add(tx_id)
        # 快照: 记录事务开始时所有活跃事务
        snapshot = self.active_txns.copy()
        return Transaction(tx_id, snapshot, self)

    def read(self, key, tx):
        """读取对当前事务可见的最新版本"""
        if key not in self.data:
            return None
        for version, value, committed_by in reversed(self.data[key]):
            if self._is_visible(committed_by, tx):
                return value
        return None

    def _is_visible(self, committed_by, tx):
        """判断某版本是否对当前事务可见"""
        if committed_by == tx.tx_id:
            return True  # 自己写的总可见
        if committed_by in tx.snapshot:
            return False  # 事务开始时仍活跃 → 不可见
        if committed_by > tx.tx_id:
            return False  # 后于自己开始的事务 → 不可见
        return True  # 已提交且早于自己 → 可见

-- 场景 1: 电商库存扣减 → 需要 Serializable 或应用层加锁
BEGIN;
SELECT stock FROM products WHERE id = 1 FOR UPDATE;  -- 行锁
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;

-- 场景 2: 报表查询 → Read Committed 即可
-- 允许看到并发修改的最新状态，不需要快照一致性
SELECT sum(amount) FROM transactions WHERE date = '2026-05-08';

-- 场景 3: 跨多行一致性读取 → Repeatable Read
-- 需要整个事务期间看到一致的快照
BEGIN;
SELECT balance FROM accounts WHERE user_id = 1;
SELECT balance FROM accounts WHERE user_id = 2;
-- 两次读取必须基于同一快照
COMMIT;

class EventualConsistencyPattern:
    """应用层实现最终一致性的常见模式"""

    async def write_with_retry(self, key, value):
        """写入失败重试 + 幂等性"""
        idempotency_key = generate_uuid()
        for attempt in range(3):
            try:
                await self.store.put(key, value, idempotency_key)
                return
            except TimeoutError:
                await asyncio.sleep(2 ** attempt)
        # 最后尝试失败: 写入补偿队列
        await self.compensation_queue.enqueue(key, value)

    async def read_with_fallback(self, key):
        """多副本读取 + 降级"""
        try:
            return await self.primary.get(key)
        except NodeUnavailable:
            # 降级: 从可能过期的副本读取
            result = await self.replica.get(key)
            result['_stale'] = True  # 标记可能过期
            return result

混合一致性架构
现代系统常采用分层一致性策略：


写入路径: ACID (强一致, 经过主数据库)
  ↓ CDC (Change Data Capture)
异步同步: 最终一致性 (同步到搜索索引、缓存、数仓)
  ↓
读取路径: 根据场景选择
  - 关键读取 → 主库 (强一致)
  - 普通读取 → 从库/缓存 (最终一致)

总结
ACID 和 BASE 代表了事务语义的两端，但实际工程中大多数系统处于两者之间的某个位置。关键认知是：一致性是有代价的——更强的一致性保证意味着更高的延迟和更低的吞吐。工程师的核心能力在于识别业务场景的真实一致性需求，选择恰好满足需求的最弱一致性级别，从而在正确性和性能之间取得最优平衡。


在 2026 年的实践中，SSI（可序列化快照隔离）正在成为主流选择——它以接近 Read Committed 的性能提供 Serializable 的保证（低冲突场景下），CockroachDB 和 PostgreSQL 都默认或推荐使用 SSI。这使得"默认 Serializable"成为可能，大大简化了应用开发者的心智负担。
