流处理架构与实时计算

概述

流处理（Stream Processing）是处理无界、持续到达的数据流的计算范式。与批处理的"存储后处理"不同，流处理在数据到达的瞬间进行计算，实现毫秒到秒级的处理延迟。在 2026 年，随着 AI 实时推理、实时风控和事件驱动架构的普及，流处理已从"可选优化"变为"基础设施必备"。

本文深入分析现代流处理框架的核心架构，包括事件时间语义、状态管理、容错机制和架构选型，帮助工程师构建生产级实时数据管道。

核心概念

流处理的核心挑战

挑战 描述 解决方案
无界数据 流没有终点，何时触发计算？ 窗口（Window）
乱序事件 事件到达顺序 ≠ 发生顺序 Watermark
状态管理 增量计算需要维护中间状态 有状态算子 + State Backend
容错 节点故障后如何恢复状态？ Checkpoint + Savepoint
Exactly-Once 如何保证每条消息恰好处理一次？ 分布式快照 + 两阶段提交
背压 上游速度 > 下游处理能力 动态背压传播

事件时间 vs 处理时间

事件时间 (Event Time):  事件实际发生的时间 (嵌入事件中)
处理时间 (Processing Time): 事件被系统处理的时间 (系统时钟)
摄入时间 (Ingestion Time): 事件进入系统的时间

示例:
  用户 10:00:00 点击按钮 (Event Time)
  消息 10:00:03 到达 Kafka (Ingestion Time)
  Flink 10:00:05 处理该消息 (Processing Time)

为什么事件时间重要:
  - 网络延迟导致事件乱序到达
  - 设备离线后批量上传
  - 跨时区用户行为需要统一时间线

Watermark 机制

Watermark 是流处理系统用来追踪事件时间进度的机制：

// Flink Watermark 策略
WatermarkStrategy
    .<Event>forBoundedOutOfOrderness(Duration.ofSeconds(5))
    .withTimestampAssigner((event, timestamp) -> event.getTimestamp());

// 含义: 允许最多 5 秒的乱序
// Watermark = 已观察到的最大事件时间 - 5秒
// 当 Watermark 超过窗口结束时间时触发窗口计算

Exactly-Once 语义实现
端到端 Exactly-Once 需要三个层面的协同：


Source (Exactly-Once Read):
  → Kafka Consumer: 提交 offset 与 Checkpoint 绑定
  → 故障恢复时从 Checkpoint 记录的 offset 重放

Processing (Exactly-Once State):
  → Checkpoint: 状态快照与 Barrier 对齐
  → 恢复时从最近的 Checkpoint 恢复状态

Sink (Exactly-Once Write):
  → 两阶段提交: Pre-commit → Checkpoint → Commit
  → 幂等写入: 相同消息写入多次结果不变

Flink 实时欺诈检测
public class FraudDetector extends KeyedProcessFunction<Long, Transaction, Alert> {
    // 有状态: 记录用户最近的小额交易
    private ValueState<Boolean> flagState;
    private ValueState<Long> timerState;

    @Override
    public void open(Configuration parameters) {
        flagState = getRuntimeContext().getState(
            new ValueStateDescriptor<>("flag", Types.BOOLEAN));
        timerState = getRuntimeContext().getState(
            new ValueStateDescriptor<>("timer", Types.LONG));
    }

    @Override
    public void processElement(Transaction tx, Context ctx, Collector<Alert> out) {
        Boolean lastSmall = flagState.value();

        if (lastSmall != null && tx.getAmount() > 500.0) {
            // 模式: 小额交易后紧跟大额交易 → 可疑
            out.collect(new Alert(tx.getAccountId(), tx.getAmount()));
        }

        if (tx.getAmount() < 1.0) {
            flagState.update(true);
            // 设置 1 分钟超时: 如果 1 分钟内没有大额交易则清除标记
            long timer = ctx.timerService().currentProcessingTime() + 60_000;
            ctx.timerService().registerProcessingTimeTimer(timer);
            timerState.update(timer);
        } else {
            cleanUp(ctx);
        }
    }

    @Override
    public void onTimer(long timestamp, OnTimerContext ctx, Collector<Alert> out) {
        cleanUp(ctx);
    }

    private void cleanUp(Context ctx) {
        flagState.clear();
        Long timer = timerState.value();
        if (timer != null) {
            ctx.timerService().deleteProcessingTimeTimer(timer);
            timerState.clear();
        }
    }
}

Lambda 架构:
  Event Stream → [Speed Layer: Flink] → Serving (近似实时结果)
             → [Batch Layer: Spark]  → Serving (精确结果, T+1)

Kappa 架构:
  Event Stream (Kafka, 长期保存) → [Stream Layer: Flink] → Serving
  需要回溯时: 从 Kafka offset 0 重放 → Flink 重新计算
Kafka + Flink 实时管道
# PyFlink: 实时用户行为聚合
from pyflink.table import EnvironmentSettings, TableEnvironment

t_env = TableEnvironment.create(EnvironmentSettings.in_streaming_mode())

# Source: Kafka
t_env.execute_sql("""
    CREATE TABLE user_events (
        user_id STRING,
        event_type STRING,
        event_time TIMESTAMP(3),
        WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND
    ) WITH (
        'connector' = 'kafka',
        'topic' = 'user-events',
        'properties.bootstrap.servers' = 'kafka:9092',
        'format' = 'json',
        'scan.startup.mode' = 'latest-offset'
    )
""")

# 实时聚合: 每 5 分钟窗口统计
t_env.execute_sql("""
    CREATE TABLE user_metrics (
        window_start TIMESTAMP(3),
        user_id STRING,
        event_count BIGINT,
        unique_events BIGINT
    ) WITH (
        'connector' = 'jdbc',
        'url' = 'jdbc:postgresql://db:5432/metrics',
        'table-name' = 'user_metrics'
    )
""")

t_env.execute_sql("""
    INSERT INTO user_metrics
    SELECT
        window_start,
        user_id,
        COUNT(*) as event_count,
        COUNT(DISTINCT event_type) as unique_events
    FROM TABLE(
        TUMBLE(TABLE user_events, DESCRIPTOR(event_time), INTERVAL '5' MINUTE)
    )
    GROUP BY window_start, user_id
""")

总结
流处理架构的核心是在延迟、准确性和复杂度之间取得平衡。事件时间语义和 Watermark 解决了乱序问题；有状态计算和 Checkpoint 解决了容错问题；Exactly-Once 语义解决了正确性问题。这三大机制构成了现代流处理框架的技术基石。


2026 年的趋势是流处理进一步"民主化"——从需要深厚分布式系统知识的专家工具，演变为 SQL 即可驱动的实时分析平台（如 RisingWave、Materialize）。同时 AI 实时推理的需求将流处理从"数据管道工具"提升为"AI 基础设施"，数据新鲜度成为 AI 系统可靠性的关键指标。
