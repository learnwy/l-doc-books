InnerSource 是在企业内部采用开源协作模式的实践：


## InnerSource 关键原则

1. **代码可见**：内部项目代码对所有员工可见
2. **接受贡献**：任何团队都可以向其他团队的项目提交 PR
3. **透明决策**：技术决策通过公开讨论做出
4. **标准化流程**：统一的贡献指南和 Review 流程
5. **社区驱动**：鼓励跨团队协作和知识分享


许可证合规管理
企业使用开源软件必须遵守许可证条款。不合规可能导致法律诉讼和声誉损失。


npx license-checker --production --json > licenses.json

npx license-checker --production --failOn "GPL-2.0;GPL-3.0;AGPL-3.0"

cat > .license-policy.json << 'EOF'
{
  "allowed": ["MIT", "Apache-2.0", "BSD-2-Clause", "BSD-3-Clause", "ISC"],
  "review": ["MPL-2.0", "LGPL-3.0"],
  "forbidden": ["GPL-2.0", "GPL-3.0", "AGPL-3.0"]
}
EOF

提示： 许可证合规检查应集成到 CI 流水线中，在代码合并前自动检查新引入依赖的许可证。这比事后审查高效得多。

企业开源项目发布
将内部项目开源是企业展示技术实力和吸引人才的有效方式，但需要充分的准备。


## 开源发布检查清单

### 法律与合规

- [ ] 确认代码不包含商业机密
- [ ] 选择合适的开源许可证
- [ ] 完成知识产权审查
- [ ] 获得法务部门书面批准

### 技术准备

- [ ] 移除内部系统依赖
- [ ] 移除硬编码的配置和密钥
- [ ] 添加完整的测试套件
- [ ] 搭建 CI/CD 流水线

### 文档与社区

- [ ] 编写 README 和快速开始
- [ ] 准备 CONTRIBUTING.md
- [ ] 添加 Code of Conduct
- [ ] 设置 Issue 和 PR 模板
- [ ] 指定维护团队和响应 SLA

小结
    

  • 企业开源战略从消费到合规、贡献、发布，成熟度逐步提升。
    • 

  • InnerSource 是在企业内部培养开源协作文化的有效实践。
    • 

  • 许可证合规检查应集成到 CI 流水线，按绿/黄/红三级分类管理。
    • 

  • OSPO 是企业管理开源活动的专职部门，负责合规、社区、教育和战略。
    • 

  • 企业发布开源项目需要充分的法律、技术和社区准备，不可仓促上线。
