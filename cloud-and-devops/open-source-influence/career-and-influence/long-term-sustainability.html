长期可持续性

可持续性的三个维度

开源项目的长期可持续性不仅是技术问题，更是人的问题和组织问题。一个可持续的项目需要在技术、人力和财务三个维度同时保持健康。





维度
健康指标
危险信号





技术
测试覆盖率高、依赖更新及时
技术债务积累、安全漏洞未修




人力
多位活跃维护者、新人持续加入
单人维护、无人接手




财务
有稳定资金来源
完全依赖志愿者时间







提示： 可持续性问题通常在项目成功后才暴露。在项目早期就开始思考可持续性，比等到危机出现再补救要容易得多。






维护者的身心健康
开源维护者的倦怠（Burnout）是一个日益严重的行业问题。长期处于高压、低回报、无边界的状态下，维护者的身心健康会显著受损。






倦怠信号
表现
应对策略





精力耗尽
看到 Issue 通知就焦虑
设定工作时间边界




成就感丧失
觉得维护工作毫无意义
回顾项目影响力和用户反馈




去人格化
对用户的请求感到烦躁
暂时休假、委托他人管理




孤独感

决策疲劳
无法做出技术决策
减少决策范围、授权团队





健康边界设定：


## 维护者工作契约（与自己）

### 时间边界

- 每周投入不超过 10 小时
- 周末不处理 Issue（紧急安全问题除外）
- 每季度至少休息一周

### 响应承诺

- Issue 首次响应：工作日 48 小时内
- PR Review：工作日 1 周内
- 安全漏洞：24 小时内

### 不做的事

- 不为不礼貌的请求提供帮助
- 不承诺具体的发布日期
- 不承担超出能力范围的功能请求


提示： 设定边界不是不负责任，而是为了长期负责。一个健康的维护者比一个倦怠的维护者能为项目创造更多价值。公开你的工作边界，大多数社区成员都会理解和尊重。

# 项目传承计划

## 当前维护者
- @primary-maintainer（全面负责）
- @co-maintainer（核心模块）
- @docs-maintainer（文档）

## 关键信息
- npm 发布权限：@primary-maintainer, @co-maintainer
- 域名管理：registrar.example.com（凭证在 1Password）
- CI/CD Secret：GitHub Org Secrets

## 交接流程
1. 候选人需要有 6 个月以上的持续贡献记录
2. 由现有维护者投票决定
3. 逐步转移权限（先 Triage → Write → Admin）
4. 3 个月过渡期内原维护者提供指导

## 应急联系
如果所有维护者均无法联系：
- 联系基金会：foundation@example.org
- 项目可由社区 Fork 继续发展
EOF


项目生命周期管理
开源项目有自然的生命周期。接受这一点并为每个阶段做好准备，比试图让项目永远保持巅峰更明智。






生命周期阶段
特征
策略





诞生
高度创新、少量用户
快速迭代、收集反馈




增长
用户快速增长、功能扩展
建立社区、完善文档




成熟
增长放缓、API 趋于稳定
保持质量、减少破坏性变更




维护
仅修复 Bug、不再添加新功能
明确告知用户、推荐替代方案




归档
停止维护
在 README 中标记、建议 Fork

构建抗脆弱性
最好的可持续性策略不是消除风险，而是让项目具备从风险中恢复甚至获益的能力。






抗脆弱策略
描述
实施方式





多维护者
不依赖单一个人
积极培养 3+ 位维护者




多资金来源
不依赖单一赞助商
混合个人/企业/Grant 资金




文档化一切
降低对个人记忆的依赖
架构决策、流程、凭证全部文档化




自动化
减少人工操作的依赖
CI/CD、自动发布、Bot 管理




社区多样性
避免单一企业/地区贡献者
主动拓展不同背景的贡献者







提示： 每年进行一次"如果我明天消失"的思想实验：项目能否继续运转？关键信息是否有人知道？权限是否有他人持有？不能回答"是"的地方就是需要改进的地方。






小结
    

  • 开源可持续性需要在技术、人力和财务三个维度同时保持健康。
    • 

  • 维护者倦怠是真实存在的问题，设定工作时间边界和响应承诺至关重要。
    • 

  • 每个项目都应有传承计划（SUCCESSION.md），包含关键信息和交接流程。
    • 

  • 接受项目有自然的生命周期，在合适的时候正式归档并推荐替代方案。
    • 

  • 通过多维护者、多资金来源、文档化和自动化构建项目的抗脆弱性。
