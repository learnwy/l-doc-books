Google Cloud Functions 与 Cloud Run

核心概念

Google Cloud Platform（GCP）提供两种 Serverless 计算服务：Cloud Functions（FaaS）和 Cloud Run（Serverless 容器）。Cloud Functions 定位类似 AWS Lambda，以函数为部署单元；Cloud Run 基于 Knative 构建，以容器为部署单元，支持更灵活的运行时和更长的执行时间。两者共同构成 GCP Serverless 生态的核心。

Cloud Run 是 GCP Serverless 战略的主力产品。它的核心理念是"任何容器都能 Serverless 运行"——只要容器监听 HTTP 端口，Cloud Run 就能将其作为 Serverless 服务运行，自动扩缩容（包括缩容到零）、按请求计费。

Cloud Functions 深入解析
Cloud Functions 第二代（2nd gen）基于 Cloud Run 和 Eventarc 构建，是第一代的全面升级。第二代支持更长的执行时间、更大的实例规格、并发处理和 CloudEvents 标准。


Functions Framework 是 Cloud Functions 的开源运行时框架，支持本地开发和测试。开发者在本地编写和调试函数，通过 functions-framework 启动本地服务器：


import { http } from '@google-cloud/functions-framework';

http('helloWorld', (req, res) => {
  const name = req.query.name || 'World';
  res.send(`Hello, ${name}!`);
});
import { cloudEvent, CloudEvent } from '@google-cloud/functions-framework';

interface PubSubData {
  message: {
    data: string;
    attributes: Record<string, string>;
  };
}

cloudEvent<PubSubData>('processPubSub', (event: CloudEvent<PubSubData>) => {
  const message = event.data?.message;
  if (message?.data) {
    const decoded = Buffer.from(message.data, 'base64').toString();
    console.log(`Received message: ${decoded}`);
  }
});
Eventarc 是 GCP 的统一事件路由服务，连接 Cloud Audit Logs、Pub/Sub 和自定义事件到 Cloud Functions 和 Cloud Run。Eventarc 使用 CloudEvents 规范，提供标准化的事件格式和路由机制。

Cloud Run 架构与特性
Cloud Run 的架构基于 Knative Serving，但在 GCP 上全托管运行。Knative 的核心抽象包括 Service、Revision、Configuration 和 Route。


Service 是顶层资源，定义容器镜像、环境变量、资源限制等。每次部署新版本创建一个 Revision。Route 控制流量在不同 Revision 之间的分配，支持渐进式发布。


apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: my-api
spec:
  template:
    metadata:
      annotations:
        autoscaling.knative.dev/minScale: '0'
        autoscaling.knative.dev/maxScale: '100'
        run.googleapis.com/cpu-throttling: 'false'
    spec:
      containerConcurrency: 80
      timeoutSeconds: 300
      containers:
        - image: gcr.io/my-project/my-api:latest
          ports:
            - containerPort: 8080
          resources:
            limits:
              cpu: '2'
              memory: 1Gi
          env:
            - name: DB_HOST
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: host
并发模型是 Cloud Run 区别于 Lambda 的核心差异。Cloud Run 允许每个实例同时处理多个请求（默认 80，最大 1000）。这意味着一个运行 Node.js/Go 的容器实例可以同时服务 80 个请求，大幅减少所需的实例数和冷启动频率。


CPU 分配模式：Cloud Run 提供两种模式。"仅在请求处理时分配 CPU"（默认）意味着容器在无请求时 CPU 被限流，不适合后台任务。"始终分配 CPU"允许容器在空闲时也使用 CPU，支持后台处理，但计费更高。


Cloud Run Jobs：除了服务（Service），Cloud Run 还支持作业（Jobs）——运行到完成的容器任务。适合批量数据处理、ETL 管道、定时任务。Jobs 支持并行执行多个任务（最多 10000 个），每个任务运行独立的容器实例。


Cloud Run 高级网络与安全
Ingress 控制：Cloud Run 服务默认接受来自互联网的请求。可以配置为仅接受来自 VPC 内部或 Cloud Load Balancing 的请求，增强安全性。结合 IAM 身份验证，可以实现服务间的零信任网络。

Direct VPC Egress 是较新的功能，直接将 Cloud Run 实例放入 VPC 子网，消除了 VPC Access Connector 的额外延迟和成本。


Cloud Run 多区域部署：结合 Cloud Load Balancing，可以将 Cloud Run 服务部署到多个区域，实现全球低延迟访问。负载均衡器自动将请求路由到最近的区域。配合 Cloud CDN，静态资源在边缘缓存，动态请求路由到最近的 Cloud Run 实例。


Cloud Run 与 Secret Manager 集成：敏感配置（数据库密码、API Key 等）通过 Secret Manager 管理，Cloud Run 在启动时自动挂载为环境变量或文件卷。Secret Manager 支持版本控制和自动轮换，Cloud Run 可以配置在密钥更新时自动重部署。


小结
    

  • GCP Serverless 生态以 Cloud Functions（FaaS）和 Cloud Run（Serverless 容器）为核心
    • 

  • Cloud Functions 2nd gen 底层运行在 Cloud Run 上，功能向 Cloud Run 看齐
    • 

  • Cloud Run 的多并发模型（单实例 80+ 请求）比 Lambda 更高效，减少冷启动频率
    • 

  • CPU 分配模式：请求时分配（省钱但无后台任务）vs 始终分配（支持后台处理）
    • 

  • Eventarc 提供统一事件路由，基于 CloudEvents 标准
    • 

  • Cloud Run Jobs 支持批量任务，最多 10000 并行任务实例
    • 

  • Direct VPC Egress 消除 VPC 连接的额外延迟和成本
    • 

  • 多区域部署 + Cloud Load Balancing + Cloud CDN 实现全球低延迟
    •
