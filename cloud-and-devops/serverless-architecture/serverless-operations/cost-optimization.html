Serverless 成本优化

核心概念

Serverless 的"按量付费"模型看似天然具有成本优势，但缺乏有效的成本管理可能导致账单远超预期。成本优化不仅仅是选择更便宜的方案，而是在性能、可靠性和成本之间找到最优平衡点。Serverless 成本的三大组成部分是：计算费用（Lambda 调用 + 执行时长）、存储和数据传输费用、以及配套服务费用（API Gateway、SQS、DynamoDB 等）。

一个常见的误区是只关注 Lambda 费用。实际上，在典型的 Serverless 应用中，Lambda 费用可能只占总成本的 20-40%，API Gateway、DynamoDB、CloudWatch Logs 和数据传输等配套服务占据 60-80%。

Lambda 计算成本优化
Lambda 的计算费用由两部分组成：请求次数和执行时长（GB-秒）。优化策略围绕减少调用次数和缩短执行时间展开。


内存配置优化：Lambda 的 CPU 能力按内存比例分配。增加内存不仅提升内存容量，也增加 CPU 能力。在某些 CPU 密集型场景中，将内存从 128MB 提升到 512MB 可能使执行时间从 2 秒缩短到 0.5 秒——虽然单位 GB-秒价格不变，但总 GB-秒数大幅减少。


AWS Lambda Power Tuning 工具通过自动化测试找到成本-性能最优点：

ARM64 架构：Lambda 支持 ARM64（Graviton2）和 x86_64 两种架构。ARM64 的价格比 x86_64 低 20%，且对于大多数工作负载性能相当或更好。简单地将函数架构从 x86_64 切换到 ARM64 即可节省 20% 计算成本。


// SAM 模板中指定 ARM64
// template.yaml
// Resources:
//   MyFunction:
//     Type: AWS::Serverless::Function
//     Properties:
//       Architectures: [arm64]
//       Runtime: nodejs20.x
批量处理：对于 SQS 和 Kinesis 触发的函数，增加 BatchSize 可以减少调用次数。单次调用处理 10 条消息比 10 次调用各处理 1 条消息成本更低（调用次数减少 90%）。配合 MaximumBatchingWindowInSeconds 收集更多消息后一次处理。


减少冷启动开销：冷启动期间的 Init Duration 也计入计费时长。通过减小代码包体积、使用轻量运行时、延迟加载依赖等方式缩短 Init Duration，直接减少计费的 GB-秒数。


API Gateway 与网络成本优化
API Gateway 通常是 Serverless 应用的第二大成本项。优化策略包括选择正确的 Gateway 类型、减少不必要的请求和利用缓存。


HTTP API vs REST API：HTTP API 的价格仅为 REST API 的 30%（1.00vs1.00 vs1.00vs3.50/百万请求）。对于不需要 REST API 独有功能（请求验证、缓存、使用计划、API Key 管理）的场景，切换到 HTTP API 可以节省 70% Gateway 费用。


Function URL 替代 Gateway：对于内部服务间调用或简单的 Webhook，使用 Lambda Function URL 完全免除 Gateway 费用。Function URL 直接暴露 Lambda 的 HTTPS 端点，无需 API Gateway 中间层。


API Gateway 缓存（仅 REST API）：对于读多写少的 API，启用 API Gateway 缓存可以显著减少 Lambda 调用次数。缓存按容量和时长计费（0.5GB 缓存约 $14/月），但如果能减少 50%+ 的 Lambda 调用，整体成本降低。


CloudFront + Function URL：用 CloudFront 作为 API 的前端，启用边缘缓存，减少回源到 Lambda 的请求。CloudFront 的请求价格（$0.01/万次）远低于 API Gateway，且提供全球低延迟。


DynamoDB 成本优化
DynamoDB 是 Serverless 架构中最常用的数据库，也是重要的成本中心。DynamoDB 提供两种计费模式：按需（On-Demand）和预置（Provisioned）。


按需 vs 预置模式：按需模式无需容量规划，按实际读写次数计费。预置模式需要指定读写容量单位（RCU/WCU），价格约为按需模式的 20-30%。对于流量稳定的生产负载，预置模式 + Auto Scaling 是更经济的选择。

GSI 优化：每个全局二级索引（GSI）独立消耗容量。过多的 GSI 会显著增加成本。审查是否所有 GSI 都在使用，移除未使用的索引。考虑使用单表设计（Single-Table Design）减少 GSI 数量。


DynamoDB TTL：为临时数据设置 TTL（Time-to-Live），DynamoDB 自动删除过期记录。TTL 删除不消耗 WCU，是免费的清理机制。适合会话数据、缓存记录、临时令牌。


DynamoDB DAX：DynamoDB Accelerator 是内存缓存层，读取延迟从毫秒级降至微秒级。对于读密集型工作负载，DAX 可以将 DynamoDB 读取成本降低 80-90%。DAX 按节点计费（最小 t3.small 约 $29/月）。


日志与可观测性成本控制
CloudWatch Logs 是 Serverless 成本中常被忽视的部分。Lambda 自动将所有 console.log 输出发送到 CloudWatch Logs，摄入价格为 0.50/GB。高流量的Serverless应用可能每月产生数十GB日志，费用可达0.50/GB。高流量的 Serverless 应用可能每月产生数十 GB 日志，费用可达0.50/GB。高流量的Serverless应用可能每月产生数十GB日志，费用可达50-200。


日志级别控制：在生产环境只记录 WARN 和 ERROR 级别的日志。使用 Lambda Powertools Logger 的采样功能，仅记录 10% 的 DEBUG 日志。


日志保留策略：默认情况下 CloudWatch Logs 永不过期。设置合理的保留期（如生产 30 天、开发 7 天）自动删除旧日志。对于长期存储需求，将日志导出到 S3（$0.023/GB/月，比 CloudWatch 便宜 95%）。


结构化日志替代 X-Ray：X-Ray 收费 $5/百万 Traces。对于不需要完整追踪的场景，使用结构化日志（JSON 格式 + correlation ID）配合 CloudWatch Logs Insights 进行查询，替代 X-Ray 的大部分追踪功能。

成本监控与治理
AWS Cost Explorer 可以按 Lambda 函数维度分析成本。启用 Lambda 的标签传播（Tag Propagation），为每个函数添加团队、项目、环境标签，实现精细的成本归属。


AWS Budgets 设置月度预算告警。为每个 Serverless 应用或团队设置预算，超过 80% 时触发邮件/SNS 告警，超过 100% 时触发自动化响应（如降低预置并发）。


Serverless Cost Optimization 检查清单：


FinOps 实践：建立 Serverless 成本可视化仪表板。每周审查成本趋势，识别异常增长。将成本优化纳入 DoD（Definition of Done）——新函数上线前必须完成 Power Tuning、日志级别配置和标签设置。


小结
    

  • Serverless 成本三大组成：Lambda 计算（20-40%）、配套服务（40-60%）、数据传输（10-20%）
    • 

  • Lambda 优化：Power Tuning 找最优内存、ARM64 节省 20%、批量处理减少调用次数
    • 

  • API Gateway 优化：HTTP API 替代 REST API 节省 70%、Function URL 免费、CloudFront 缓存
    • 

  • DynamoDB 优化：预置模式节省 70-80%、TTL 免费清理、DAX 减少 80-90% 读取成本
    • 

  • 日志成本：级别控制 + 保留策略 + S3 导出，可节省 90% 日志费用
    • 

  • 成本治理：标签归属 + AWS Budgets 告警 + 周度审查 + FinOps 实践
