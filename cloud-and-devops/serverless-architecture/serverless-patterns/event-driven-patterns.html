事件驱动架构模式

核心概念

事件驱动架构（Event-Driven Architecture, EDA）是 Serverless 应用的天然设计范式。在 EDA 中，系统的各个组件通过事件进行异步通信——生产者发布事件，消费者订阅并处理事件，两者之间通过事件总线（Event Bus）或消息队列解耦。Serverless 平台的事件触发机制使得 EDA 的实现变得简单直接。

事件驱动与传统的请求-响应模式有本质区别：请求-响应是同步、紧耦合的，调用方必须等待响应；事件驱动是异步、松耦合的，生产者发布事件后立即返回，不关心谁在消费。这种解耦使系统更具弹性和可扩展性。

事件总线与路由
事件总线是 EDA 的核心组件，负责接收、过滤、路由和投递事件。AWS EventBridge 是 Serverless 生态中最强大的事件总线服务。


AWS EventBridge 支持丰富的事件源：AWS 服务事件（超过 100 种）、SaaS 集成（如 Zendesk、Datadog、Shopify）、自定义事件。EventBridge 的核心能力是基于内容的路由——通过规则（Rule）定义事件过滤条件，将匹配的事件路由到指定目标。


import { EventBridgeClient, PutEventsCommand } from '@aws-sdk/client-eventbridge';

const eventBridge = new EventBridgeClient({});

await eventBridge.send(
  new PutEventsCommand({
    Entries: [
      {
        Source: 'order-service',
        DetailType: 'OrderCreated',
        Detail: JSON.stringify({
          orderId: 'ORD-12345',
          userId: 'USR-67890',
          total: 299.99,
          items: [{ sku: 'PROD-001', quantity: 2, price: 149.99 }],
        }),
        EventBusName: 'ecommerce-bus',
      },
    ],
  }),
);
EventBridge 规则支持复杂的内容过滤：前缀匹配、数值范围、存在性检查、逻辑组合（AND/OR/NOT）。

Google Cloud Pub/Sub 是 GCP 的消息传递服务，支持主题（Topic）和订阅（Subscription）模式。Pub/Sub 保证至少一次投递（At-least-once），消费者需要处理幂等性。结合 Eventarc，Pub/Sub 可以作为 Cloud Functions 和 Cloud Run 的事件源。

扇出与扇入模式
扇出（Fan-out） 是事件驱动架构中最常见的模式：一个事件触发多个并行处理流程。典型场景是订单创建事件同时触发库存扣减、支付处理、邮件通知、数据分析四个独立的 Lambda 函数。


SNS + Lambda 是最简单的扇出实现。SNS 主题接收事件，多个 Lambda 函数订阅同一主题，SNS 并行调用所有订阅者。


扇入（Fan-in） 是扇出的逆过程：多个并行处理流程的结果汇聚到一个聚合点。实现扇入比扇出复杂，因为需要处理超时、部分失败和结果聚合。


AWS Step Functions 是实现扇入的标准方案。Parallel 状态允许多个分支并行执行，Wait for Callback 支持等待外部系统完成。所有分支完成后，结果自动聚合传递给下一个状态。


事件编排 vs 事件编排的区别：


编排（Choreography）：没有中心协调者，服务通过事件自主反应。每个服务监听自己关心的事件，处理后发布新事件。适合简单流程，但复杂流程中的控制流和错误处理难以追踪。


编排（Orchestration）：有一个中心协调者（如 Step Functions）定义完整的工作流程。协调者调度各个步骤的执行、处理错误和重试、维护状态。适合复杂的业务流程。

死信队列与错误处理
在事件驱动架构中，消息处理失败是常态而非异常。死信队列（Dead Letter Queue, DLQ）是处理失败消息的标准机制：当消息经过最大重试次数后仍然失败，将其转移到 DLQ 而非丢弃。


SQS DLQ 配置：为每个处理队列配置一个 DLQ。设置 maxReceiveCount（最大接收次数），超过此次数的消息自动转移到 DLQ。


import { SQSClient, CreateQueueCommand, SetQueueAttributesCommand } from '@aws-sdk/client-sqs';

const sqs = new SQSClient({});

const dlqResult = await sqs.send(
  new CreateQueueCommand({
    QueueName: 'orders-dlq',
  }),
);

const queueResult = await sqs.send(
  new CreateQueueCommand({
    QueueName: 'orders',
    Attributes: {
      RedrivePolicy: JSON.stringify({
        deadLetterTargetArn: 'arn:aws:sqs:us-east-1:123:orders-dlq',
        maxReceiveCount: '3',
      }),
    },
  }),
);
Lambda Destinations 提供了更现代的错误处理方式。异步调用的成功和失败结果可以分别路由到不同的目标（SQS、SNS、EventBridge、另一个 Lambda）。相比 DLQ，Destinations 支持成功路由和更丰富的目标类型。


幂等性设计是事件驱动架构的基石。因为至少一次投递（At-least-once Delivery），消费者必须能够安全地处理重复消息。常用的幂等性策略包括：


    

  • 幂等键：使用消息 ID 或业务键作为幂等键，配合 DynamoDB 条件写入
    • 

  • 数据库约束：利用 UNIQUE 约束防止重复插入
    • 

  • 乐观锁：通过版本号防止并发冲突
    • 

  • 去重表：独立的去重记录表，记录已处理的消息 ID
    • 



事件驱动数据管道
事件驱动架构在数据处理管道中有广泛应用。典型的 Serverless 数据管道由数据摄入、转换、存储和分析四个阶段组成，每个阶段由事件触发。


实时流处理：Kinesis Data Streams + Lambda 实现实时事件处理。Lambda 通过事件源映射消费 Kinesis 分片，支持批量处理和并行化。Kinesis 增强扇出（Enhanced Fan-out）为每个消费者提供独立的 2MB/s 吞吐量。


批量数据处理：S3 事件 + Lambda 实现文件级触发的 ETL 管道。文件上传到 S3 时触发 Lambda 进行数据清洗和转换，结果写入另一个 S3 桶或 DynamoDB 表。对于大文件（>6GB），使用 Step Functions 编排多个 Lambda 分段处理。


变更数据捕获（CDC）：DynamoDB Streams + Lambda 实现数据库变更的实时同步。每条 DynamoDB 记录的创建、更新、删除操作都会生成流事件，Lambda 消费这些事件同步到 Elasticsearch、缓存或其他数据存储。


小结
    

  • 事件驱动架构是 Serverless 的天然设计范式，通过异步事件实现服务松耦合
    • 

  • EventBridge 提供基于内容的复杂路由，Pub/Sub 适合高吞吐低延迟场景
    • 

  • 扇出（SNS + Lambda）并行处理，扇入（Step Functions）聚合结果
    • 

  • Choreography 适合简单流程，Orchestration（Step Functions）适合复杂业务流
    • 

  • DLQ 和 Lambda Destinations 是错误处理的两种互补方案
    • 

  • 幂等性设计是至少一次投递保证下的必需策略
    • 

  • 事件驱动数据管道：Kinesis 实时流 + S3 批量 + DynamoDB CDC
    •
