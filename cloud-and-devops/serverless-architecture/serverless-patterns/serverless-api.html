Serverless API 设计

核心概念

Serverless API 是使用函数即服务（FaaS）和 API Gateway 构建的 RESTful 或 GraphQL 接口。与传统的 API 服务器不同，Serverless API 无需持续运行的服务进程——每个请求触发函数执行，执行完毕后释放资源。这种模型天然适合流量波动大、资源利用率不稳定的 API 场景。

构建生产级 Serverless API 需要解决几个核心挑战：API Gateway 选型与配置、函数组织策略（单函数 vs 多函数）、认证授权、请求验证、错误处理和 API 版本管理。

单函数 vs 多函数架构
Serverless API 的函数组织策略直接影响开发体验、部署效率和运维复杂度。主要有三种模式：


一路由一函数（Micro-function）：每个 API 路由映射到独立的 Lambda 函数。GET /users、POST /users、GET /users/:id 分别是三个函数。优点是最细粒度的权限控制、独立部署和独立缩放。缺点是函数数量爆炸（百级 API = 百个函数）、冷启动频率高（每个函数独立的冷启动池）、代码共享困难。


单函数应用（Monolithic function）：所有 API 路由合并到一个 Lambda 函数内部，由框架（Express、Hono、Fastify）处理路由。优点是与传统 API 开发体验一致、冷启动池共享、代码组织简单。缺点是部署粒度粗（一个路由的变更触发整个函数重新部署）、内存和超时按最大需求配置。


按领域分组（Domain-based grouping）：按业务领域（用户、订单、支付）分组，每个领域一个函数。这是生产环境中最推荐的平衡策略。

推荐实现：使用 Hono 框架构建领域分组的 Serverless API。Hono 是超轻量级的 Web 框架（14KB），支持 AWS Lambda、Cloudflare Workers、Deno Deploy 等多个 Serverless 运行时。


import { Hono } from 'hono';
import { handle } from 'hono/aws-lambda';
import { zValidator } from '@hono/zod-validator';
import { z } from 'zod';

const app = new Hono();

const createUserSchema = z.object({
  name: z.string().min(1).max(100),
  email: z.string().email(),
});

app.get('/users', async (c) => {
  const users = await getUsersFromDB();
  return c.json({ users });
});

app.post('/users', zValidator('json', createUserSchema), async (c) => {
  const body = c.req.valid('json');
  const user = await createUser(body);
  return c.json({ user }, 201);
});

app.get('/users/:id', async (c) => {
  const id = c.req.param('id');
  const user = await getUserById(id);
  if (!user) return c.json({ error: 'User not found' }, 404);
  return c.json({ user });
});

export const handler = handle(app);
认证与授权
Serverless API 的认证授权有多种实现方式，选择取决于安全需求和架构复杂度。


API Gateway 内置 JWT 授权器（仅 HTTP API）：API Gateway 直接验证 JWT Token，无需调用 Lambda。配置 JWKS URI（如 Cognito 的 /.well-known/jwks.json），Gateway 自动验证 Token 签名和过期时间。延迟最低，但授权逻辑有限。


Lambda Authorizer：自定义授权逻辑的 Lambda 函数。支持两种模式：Token-based（从 Authorization Header 提取 Token）和 Request-based（访问完整请求上下文）。返回 IAM Policy 文档决定是否允许访问。


import type { APIGatewayTokenAuthorizerEvent, AuthResponse } from 'aws-lambda';
import { verify } from 'jsonwebtoken';

export const handler = async (event: APIGatewayTokenAuthorizerEvent): Promise<AuthResponse> => {
  const token = event.authorizationToken.replace('Bearer ', '');

  try {
    const decoded = verify(token, process.env.JWT_SECRET!) as {
      sub: string;
      role: string;
    };

    return {
      principalId: decoded.sub,
      policyDocument: {
        Version: '2012-10-17',
        Statement: [
          {
            Action: 'execute-api:Invoke',
            Effect: 'Allow',
            Resource: event.methodArn,
          },
        ],
      },
      context: { role: decoded.role, userId: decoded.sub },
    };
  } catch {
    throw new Error('Unauthorized');
  }
};
授权缓存：Lambda Authorizer 支持结果缓存（TTL 0-3600 秒），避免每次请求都调用授权函数。缓存键基于 Token 值或请求特征。

API 版本管理与文档
API 版本管理是长期维护 Serverless API 的关键实践。常用策略包括 URL 路径版本化（/v1/users）、HTTP Header 版本化（Accept: application/vnd.api+json;version=1）和查询参数版本化（/users?version=1）。


URL 路径版本化是 Serverless API 最推荐的方案，因为 API Gateway 的路由规则天然支持路径匹配。不同版本可以路由到不同的 Lambda 函数或函数别名（Alias），实现版本间的完全隔离。


Lambda 别名与版本：每次发布创建一个新的 Lambda 版本（不可变的代码快照），通过别名（v1、v2、prod、staging）引用特定版本。API Gateway 的阶段变量（Stage Variable）可以指向不同别名，实现无需修改 Gateway 配置的版本切换。


API 文档自动生成：结合 Zod Schema 定义请求/响应模型，使用 @asteasolutions/zod-to-openapi 自动生成 OpenAPI 3.0 规范。Swagger UI 或 Redoc 渲染交互式文档，部署到 S3 + CloudFront 作为静态站点。


限流与使用计划：API Gateway REST API 支持使用计划（Usage Plan），为不同的 API Key 设置请求配额和限流。HTTP API 通过 Lambda Authorizer 或第三方服务（如 AWS WAF）实现限流。

  • Serverless API 通过 API Gateway + Lambda 构建，HTTP API 延迟更低、成本更低

    •
