工作流编排与 Step Functions

核心概念

工作流编排（Workflow Orchestration）是协调多个 Serverless 函数按照预定义的逻辑顺序执行的机制。在复杂的业务场景中，单个函数无法完成整个流程——订单处理需要验证库存、扣减支付、生成物流单、发送通知等多个步骤。AWS Step Functions 是 Serverless 工作流编排的标准服务，基于状态机模型定义和执行多步骤工作流。

Step Functions 使用 Amazon States Language（ASL）定义状态机。每个状态（State）代表工作流中的一个步骤，可以是 Lambda 调用、等待、选择分支、并行执行或 Map 迭代。状态机引擎负责步骤间的协调、错误处理、重试和持久化。

状态机设计模式
Step Functions 提供了八种状态类型，组合使用可以实现复杂的业务逻辑。


Task 状态：调用 AWS 服务或 Lambda 函数。Step Functions 的 SDK 集成允许直接调用 200+ AWS 服务 API（如 DynamoDB PutItem、SQS SendMessage、ECS RunTask），无需编写 Lambda 中间层。


{
  "QueryDatabase": {
    "Type": "Task",
    "Resource": "arn:aws:states:::dynamodb:getItem",
    "Parameters": {
      "TableName": "Orders",
      "Key": {
        "orderId": { "S.$": "$.orderId" }
      }
    },
    "ResultPath": "$.orderData",
    "Next": "ProcessOrder"
  }
}
Choice 状态：基于输入数据的条件分支。支持字符串、数值、布尔值的比较运算和逻辑组合（And/Or/Not）。


Parallel 状态：并行执行多个分支，所有分支完成后将结果数组传递给下一个状态。如果任何分支失败，整个 Parallel 状态失败（可配置 Catch）。


Map 状态：对数组中的每个元素并行或按顺序执行子工作流。Distributed Map 支持处理数百万条记录，从 S3 CSV/JSON 文件直接读取数据，每批最多 10000 个并行子执行。


{
  "ProcessItems": {
    "Type": "Map",
    "ItemsPath": "$.items",
    "ItemProcessor": {
      "ProcessorConfig": {
        "Mode": "DISTRIBUTED",
        "ExecutionType": "STANDARD"
      },
      "StartAt": "ProcessSingleItem",
      "States": {
        "ProcessSingleItem": {
          "Type": "Task",
          "Resource": "arn:aws:lambda:us-east-1:123:function:process-item",
          "End": true
        }
      }
    },
    "MaxConcurrency": 100,
    "Next": "AggregateResults"
  }
}
Wait 状态：暂停执行指定时间或到指定时间点。结合 Callback 模式实现等待人工审批或外部系统回调。


错误处理与重试策略
Step Functions 提供了声明式的错误处理机制，通过 Retry 和 Catch 字段定义重试策略和错误路由。


Retry 策略：为每个 Task 状态配置重试规则。支持按错误类型匹配（States.ALL 匹配所有错误、States.TaskFailed 匹配任务失败、Lambda.ServiceException 匹配特定服务错误）。指数退避参数包括 IntervalSeconds（初始间隔）、MaxAttempts（最大重试次数）和 BackoffRate（退避系数）。


{
  "ProcessPayment": {
    "Type": "Task",
    "Resource": "arn:aws:lambda:us-east-1:123:function:process-payment",
    "Retry": [
      {
        "ErrorEquals": ["PaymentGatewayTimeout"],
        "IntervalSeconds": 2,
        "MaxAttempts": 3,
        "BackoffRate": 2.0
      },
      {
        "ErrorEquals": ["States.ALL"],
        "IntervalSeconds": 5,
        "MaxAttempts": 2,
        "BackoffRate": 1.5
      }
    ],
    "Catch": [
      {
        "ErrorEquals": ["InsufficientFunds"],
        "ResultPath": "$.error",
        "Next": "NotifyInsufficientFunds"
      },
      {
        "ErrorEquals": ["States.ALL"],
        "ResultPath": "$.error",
        "Next": "HandleGenericError"
      }
    ],
    "Next": "ConfirmOrder"
  }
}
Catch 路由：当所有重试耗尽后，将错误路由到指定的恢复状态。错误信息通过 ResultPath 注入到状态输入中，恢复状态可以读取错误详情进行补偿操作。


Saga 模式实现：Step Functions 是实现 Saga 模式的理想工具。每个业务步骤对应一个 Task 状态，每个 Task 的 Catch 路由到对应的补偿步骤。补偿步骤按逆序执行，回滚之前成功的操作。

Standard vs Express 工作流
Step Functions 提供两种执行模式：Standard（标准）和 Express（快速）。两者在执行时长、状态持久化、价格和适用场景上有本质区别。


Standard 工作流：每个状态转换都持久化到存储。执行可以持续最长 1 年。支持精确一次（Exactly-once）语义。执行历史完整记录，支持审计和回溯。按状态转换次数计费。适合长时间运行的业务流程（订单处理、审批流、数据管道）。


Express 工作流：状态不持久化（仅保存最终结果）。执行最长 5 分钟。至少一次（At-least-once）语义。不记录完整的状态转换历史。按执行次数和执行时长计费。适合高频、短时间的事件处理（IoT 数据处理、API 编排、实时转换）。

嵌套工作流：Standard 和 Express 可以嵌套使用。外层 Standard 工作流处理长时间运行的业务流程，内部调用 Express 工作流处理高频子任务。例如：Standard 工作流管理订单生命周期（小时级），内部的 Express 工作流处理实时库存查询（毫秒级）。


替代方案与工作流生态
Step Functions 并非唯一的 Serverless 工作流方案。根据场景不同，其他工具可能更合适。


Temporal 是一个开源的分布式工作流引擎，支持使用代码（TypeScript、Go、Java、Python）而非 JSON/YAML 定义工作流。Temporal 的优势在于：强类型工作流定义、版本化和迁移、活动心跳和长轮询、信号和查询。适合需要复杂业务逻辑和跨服务编排的场景。


EventBridge Pipes 是轻量级的点对点数据管道。源（SQS、Kinesis、DynamoDB Streams）→ 过滤 → 转换（Lambda、Step Functions、API Destination）→ 目标。适合简单的 ETL 管道，比 Step Functions 更简洁且成本更低。


Apache Airflow (MWAA) 是 AWS 托管的 Apache Airflow，使用 Python DAG 定义工作流。适合数据工程和 ML 管道，但不适合实时业务流程。

小结
    

  • Step Functions 基于状态机模型编排多步骤 Serverless 工作流
    • 

  • 八种状态类型（Task、Choice、Parallel、Map、Wait 等）组合实现复杂逻辑
    • 

  • SDK 集成直接调用 200+ AWS 服务 API，避免编写中间 Lambda
    • 

  • Distributed Map 支持处理数百万条记录，最多 10000 并行子执行
    • 

  • 声明式错误处理：Retry（指数退避）+ Catch（错误路由）+ Saga（补偿链）
    • 

  • Standard（长时间、精确一次）vs Express（高频、短时间），可嵌套使用
    • 

  • Temporal 适合代码定义的复杂工作流，EventBridge Pipes 适合简单管道
