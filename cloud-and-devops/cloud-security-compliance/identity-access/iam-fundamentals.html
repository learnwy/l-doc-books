IAM 权限管理基础

核心概念

身份与访问管理（Identity and Access Management, IAM）是云安全的基石。IAM 系统控制"谁"（身份）可以对"什么资源"（对象）执行"什么操作"（权限）。在 AWS 中，IAM 采用基于策略的访问控制模型——通过 JSON 格式的策略文档定义权限，将策略附加到身份（用户、角色、组）或资源上。

IAM 的核心原则是最小权限（Least Privilege）：每个身份只应拥有完成其工作所需的最小权限集。过宽的权限不仅增加安全风险，也使得安全审计和故障排查更加困难。

IAM 策略深入解析
IAM 策略是权限控制的核心机制。策略文档由 Statement 数组组成，每个 Statement 定义一条权限规则。


策略结构：


{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowDynamoDBReadAccess",
      "Effect": "Allow",
      "Action": ["dynamodb:GetItem", "dynamodb:Query", "dynamodb:Scan"],
      "Resource": [
        "arn:aws:dynamodb:us-east-1:123456789012:table/Users",
        "arn:aws:dynamodb:us-east-1:123456789012:table/Users/index/*"
      ],
      "Condition": {
        "StringEquals": {
          "aws:RequestedRegion": "us-east-1"
        },
        "IpAddress": {
          "aws:SourceIp": "10.0.0.0/8"
        }
      }
    }
  ]
}
策略评估逻辑：AWS 的策略评估遵循以下优先级规则：


    

  1. 显式拒绝（Explicit Deny）：任何策略中的 Deny 都无条件生效
    2. 

  2. SCP 边界：Organizations SCP 限制组织成员的最大权限
    3. 

  3. Permission Boundary：限制 IAM 实体的最大权限
    4. 

  4. 基于身份的策略：附加到 User/Role/Group 的策略
    5. 

  5. 基于资源的策略：附加到资源（S3 Bucket Policy、SQS Policy）的策略
    6. 

  6. 默认拒绝（Implicit Deny）：未明确允许的操作默认拒绝
    7. 



条件键（Condition Keys） 是实现精细化权限控制的利器。全局条件键（aws:开头）适用于所有服务，服务特定条件键（如 s3:prefix、dynamodb:LeadingKeys）提供资源级的精细控制。

IAM Role 与联邦认证
IAM Role 是现代云安全的核心身份机制。与 IAM User 不同，Role 不拥有长期凭证（Access Key），而是通过 STS（Security Token Service）颁发临时凭证。临时凭证自动过期（默认 1 小时，最长 12 小时），大幅降低凭证泄露的风险。


EC2 Instance Role：EC2 实例通过 Instance Profile 关联 IAM Role。实例上的应用通过 Instance Metadata Service 自动获取临时凭证，无需硬编码 Access Key。AWS SDK 自动检测并使用这些凭证。


Lambda Execution Role：每个 Lambda 函数关联一个 Execution Role，定义函数可以访问的 AWS 资源。Lambda 在调用函数时自动注入临时凭证到运行时环境。


OIDC 联邦认证：允许外部身份提供商（如 GitHub Actions、GitLab CI、Google Workspace）的身份直接 Assume AWS IAM Role，无需在 AWS 中创建 IAM User 或分发 Access Key。


import { STSClient, AssumeRoleWithWebIdentityCommand } from '@aws-sdk/client-sts';

const sts = new STSClient({});

const assumeRole = async (oidcToken: string) => {
  const response = await sts.send(
    new AssumeRoleWithWebIdentityCommand({
      RoleArn: 'arn:aws:iam::123456789012:role/GitHubActionsRole',
      RoleSessionName: 'github-deploy',
      WebIdentityToken: oidcToken,
      DurationSeconds: 3600,
    }),
  );

  return {
    accessKeyId: response.Credentials?.AccessKeyId,
    secretAccessKey: response.Credentials?.SecretAccessKey,
    sessionToken: response.Credentials?.SessionToken,
  };
};
SAML 联邦认证：企业身份提供商（如 Okta、Azure AD、OneLogin）通过 SAML 2.0 协议与 AWS 集成。员工使用企业单点登录（SSO）访问 AWS Management Console 和 API，无需独立的 AWS 凭证。

基于属性的访问控制
ABAC（Attribute-Based Access Control） 是 IAM 的高级访问控制模式，基于身份和资源的属性（标签）动态决定访问权限。与传统的 RBAC（基于角色的访问控制）相比，ABAC 更灵活、更可扩展。


在 ABAC 模式中，IAM 策略使用条件键匹配标签值。例如，一个策略可以表达"允许用户访问与自己团队标签相同的 EC2 实例"——当新团队成员加入时，只需设置正确的标签，无需修改策略。


{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["ec2:StartInstances", "ec2:StopInstances"],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "ec2:ResourceTag/Team": "${aws:PrincipalTag/Team}"
        }
      }
    }
  ]
}

IAM 安全审计
持续审计 IAM 配置是维护安全姿态的关键。AWS 提供了多种工具帮助发现和修复 IAM 安全问题。


IAM Access Analyzer 分析资源的跨账户和公开访问。它基于数学推理（而非启发式规则）分析策略，能够确定性地识别允许外部访问的资源。支持的资源类型包括 S3 桶、IAM Role 信任策略、KMS 密钥、Lambda 函数和 SQS 队列。


IAM Credential Report 列出账户中所有 IAM User 的凭证状态：密码是否启用、Access Key 的创建时间和最后使用时间、MFA 是否启用。用于识别长期未使用的凭证和未启用 MFA 的用户。


CloudTrail + Athena 可以查询 IAM API 调用历史，分析权限使用模式。基于实际使用生成最小权限策略，替代过宽的初始策略。

小结
    

  • IAM 采用基于策略的访问控制，策略评估遵循显式拒绝 > SCP > 边界 > 身份/资源策略
    • 

  • IAM Role + 临时凭证是推荐的认证方式，避免长期 Access Key
    • 

  • OIDC/SAML 联邦认证实现外部身份（CI/CD、企业 SSO）无密钥访问 AWS
    • 

  • 条件键（IP、MFA、标签、区域、VPC）实现精细化权限控制
    • 

  • ABAC 基于标签动态授权，减少策略数量，适合大规模环境
    • 

  • IAM Access Analyzer 基于数学推理确定性识别外部访问风险
    • 

  • 持续审计：Credential Report + CloudTrail + Access Analyzer + Config Rules
    •
