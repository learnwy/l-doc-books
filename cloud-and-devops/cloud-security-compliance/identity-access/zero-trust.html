零信任安全模型

核心概念

零信任（Zero Trust）是一种安全架构范式，其核心原则是"永不信任，始终验证"（Never Trust, Always Verify）。传统的安全模型基于网络边界——内部网络可信、外部网络不可信。零信任打破了这种假设，认为任何身份（用户、服务、设备）在任何位置都不应被默认信任，每次访问都必须经过身份验证、授权和持续验证。

零信任模型在云环境中尤为重要。云架构的网络边界模糊——远程办公、多云环境、SaaS 集成使得传统的"城堡与护城河"模型失效。零信任将安全控制从网络边界转移到每个访问请求上。

零信任架构组件
零信任架构由五个核心组件构成：身份（Identity）、设备（Device）、网络（Network）、应用（Application）和数据（Data）。NIST SP 800-207 是零信任架构的权威参考标准。


身份验证与认证是零信任的第一道关卡。每个访问请求必须携带经过验证的身份凭证。强认证（MFA）是必选项——仅凭密码不足以建立信任。现代零信任架构推荐使用 FIDO2/WebAuthn 等无密码认证方式，消除密码泄露风险。


设备信任评估验证发起请求的设备是否满足安全要求。设备是否有最新的操作系统补丁？是否启用了磁盘加密？是否安装了端点检测响应（EDR）软件？设备不合规的请求应被限制访问范围。


上下文感知授权综合身份、设备、位置、时间、行为等多维信号做出动态授权决策。例如：来自已知 IP 的请求可以正常访问；来自新 IP 的请求要求额外的 MFA 步骤；来自高风险国家的请求限制为只读权限。


微分段（Micro-segmentation） 将网络划分为极小的安全域，每个工作负载或应用都有独立的安全边界。即使攻击者突破了一个微分段，也无法横向移动到其他分段。在 Kubernetes 中，NetworkPolicy 实现了 Pod 级别的微分段。

AWS 零信任实践
AWS 提供了多个服务支持零信任架构的落地实施。


AWS Verified Access 是 AWS 的零信任网络访问（ZTNA）服务。它替代传统 VPN，为企业内部应用提供基于身份和设备信任的安全访问。员工无需连接 VPN 即可安全访问 AWS 或本地数据中心的应用。


Verified Access 的工作流程：用户访问应用 URL → Verified Access 端点拦截请求 → 通过身份提供商（IdP）验证身份 → 评估设备信任状态 → 根据策略允许或拒绝访问。


import { EC2Client, CreateVerifiedAccessEndpointCommand } from '@aws-sdk/client-ec2';

const ec2 = new EC2Client({});

await ec2.send(
  new CreateVerifiedAccessEndpointCommand({
    VerifiedAccessGroupId: 'vag-12345',
    EndpointType: 'load-balancer',
    AttachmentType: 'vpc',
    DomainCertificateArn: 'arn:aws:acm:us-east-1:123:certificate/abc',
    ApplicationDomain: 'internal-app.example.com',
    LoadBalancerOptions: {
      LoadBalancerArn: 'arn:aws:elasticloadbalancing:us-east-1:123:...',
      Port: 443,
      Protocol: 'https',
    },
    PolicyDocument: JSON.stringify({
      Version: '2012-10-17',
      Statement: [
        {
          Effect: 'Allow',
          Principal: '*',
          Action: 'ec2:VerifiedAccess',
          Condition: {
            StringEquals: {
              'ec2:VerifiedAccessTrustProviderType': 'user',
            },
          },
        },
      ],
    }),
  }),
);
IAM Identity Center（原 AWS SSO） 集中管理人员对多个 AWS 账户和应用的访问。通过与企业 IdP（Okta、Azure AD）集成，实现统一的身份管理和单点登录。权限集（Permission Set）定义每个用户/组在每个账户中的 IAM 权限。


AWS Private CA + mTLS 实现服务间的零信任认证。每个微服务持有 Private CA 颁发的证书，服务间通信使用双向 TLS（mTLS）互相验证身份。结合 App Mesh 或 Istio，自动管理证书的颁发、分发和轮换。


零信任网络架构
零信任网络架构是零信任模型在网络层的具体实现，核心目标是消除"可信网络"的概念。


BeyondCorp 模型（Google 的零信任实践）是最早的大规模零信任实施案例。核心思想：公司网络的安全性不应优于互联网——所有应用都应该能安全地暴露在互联网上，通过身份和设备信任而非网络位置控制访问。


软件定义边界（SDP） 在网络层实现零信任。SDP 控制器管理授权列表，SDP 网关只允许经过身份验证和授权的连接通过。未授权的请求甚至无法发现 SDP 网关的存在（"暗网"效果），大幅缩小攻击面。

零信任实施路线图
零信任不是一个可以一次性部署的产品，而是一个渐进式的安全转型过程。推荐分四个阶段实施：


Phase 1 - 身份基础（1-3 月）：统一身份管理（AWS SSO / Okta）、全员 MFA、消除长期 Access Key、实施 IAM 最小权限。


Phase 2 - 网络微分段（3-6 月）：VPC 重新设计（多账户 + 多 VPC）、安全组最小化、Kubernetes NetworkPolicy、启用 VPC Flow Logs。


Phase 3 - 应用级控制（6-12 月）：部署 Verified Access 或 ZTNA 替代 VPN、服务间 mTLS、API Gateway 强认证、Web 应用防火墙。


Phase 4 - 持续验证（12+ 月）：行为分析（UEBA）、持续设备合规检查、动态风险评分、自适应访问策略。

  • 五大支柱：身份、设备、网络、应用、数据

  • AWS Verified Access 提供 ZTNA 能力，替代传统 VPN

  • 微分段通过安全组和 NetworkPolicy 实现工作负载级隔离

  • 服务间零信任通过 mTLS + 服务网格实现
