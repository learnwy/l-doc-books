策略即代码

核心概念

策略即代码（Policy as Code, PaC）是将安全策略、合规规则和治理约束以编程语言的形式定义、测试和自动化执行的实践。传统的安全策略依赖文档描述和人工审核——"所有容器不允许以 Root 用户运行"写在安全手册里，依赖审核人员逐一检查。PaC 将这些策略转化为可机器执行的代码，在 CI/CD 流水线、Kubernetes Admission 和 Terraform Plan 等关键控制点自动拦截违规操作。

PaC 的核心价值是将安全左移（Shift-Left Security）——在基础设施变更和应用部署的早期阶段就发现和阻止违规，而非在生产环境中事后检测。这大幅降低了合规风险和修复成本——在 PR 阶段修复一个违规配置的成本远低于在生产事故后回溯修复。

Open Policy Agent 与 Rego
Open Policy Agent（OPA）是最广泛使用的通用策略引擎，其策略语言 Rego 是声明式的、基于 Datalog 的查询语言。OPA 的设计理念是"策略解耦"——策略逻辑与应用代码和平台完全分离，通过标准化的 API 交互。


Rego 策略示例——禁止容器以 Root 运行：


package kubernetes.admission

deny[msg] {
  input.request.kind.kind == "Pod"
  container := input.request.object.spec.containers[_]
  container.securityContext.runAsUser == 0
  msg := sprintf("Container '%v' must not run as root (UID 0)", [container.name])
}

deny[msg] {
  input.request.kind.kind == "Pod"
  container := input.request.object.spec.containers[_]
  not container.securityContext.runAsNonRoot
  msg := sprintf("Container '%v' must set securityContext.runAsNonRoot to true", [container.name])
}

deny[msg] {
  input.request.kind.kind == "Pod"
  container := input.request.object.spec.containers[_]
  container.securityContext.privileged
  msg := sprintf("Container '%v' must not run in privileged mode", [container.name])
}
Gatekeeper 是 OPA 在 Kubernetes 上的原生实现。它通过 Kubernetes Admission Webhook 拦截所有资源创建/修改请求，将请求数据发送给 OPA 引擎评估策略，违规的请求直接被拒绝。


ConstraintTemplate + Constraint 是 Gatekeeper 的策略管理模型。ConstraintTemplate 定义策略逻辑（Rego 代码），Constraint 定义策略的应用范围和参数。这种分离使得同一策略逻辑可以用不同的参数在不同的命名空间中应用。


Kyverno 声明式策略
Kyverno 是 Kubernetes 原生的策略引擎，最大的差异化优势是使用 YAML（而非 Rego）定义策略，大幅降低了学习门槛。对于纯 Kubernetes 场景，Kyverno 通常比 OPA/Gatekeeper 更易上手。


apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-resource-limits
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: check-cpu-memory-limits
      match:
        any:
          - resources:
              kinds:
                - Pod
      validate:
        message: 'CPU and memory limits are required for all containers'
        pattern:
          spec:
            containers:
              - resources:
                  limits:
                    memory: '?*'
                    cpu: '?*'

    - name: restrict-image-registries
      match:
        any:
          - resources:
              kinds:
                - Pod
      validate:
        message: 'Images must come from approved registries: gcr.io, docker.io/library'
        pattern:
          spec:
            containers:
              - image: 'gcr.io/* | docker.io/library/*'
Kyverno 的 Mutate 能力允许策略不仅验证，还可以自动修改资源。例如，自动为所有 Pod 添加安全上下文、自动注入 Sidecar、自动添加标签。这在合规场景中非常实用——与其拒绝不合规的资源，不如自动将其修正为合规状态。

IaC 安全扫描
在基础设施即代码（IaC）流水线中集成策略检查，确保 Terraform/CloudFormation 配置在部署前满足安全要求。


Checkov 是最流行的开源 IaC 安全扫描工具，内置 1000+ 条安全检查规则，覆盖 AWS、Azure、GCP、Kubernetes 和 Terraform。


interface CheckovResult {
  checkType: string;
  results: {
    passedChecks: { id: string; resource: string }[];
    failedChecks: { id: string; resource: string; guideline: string }[];
    skippedChecks: { id: string; resource: string; reason: string }[];
  };
  summary: {
    passed: number;
    failed: number;
    skipped: number;
  };
}
CI/CD 集成：在 PR 阶段运行 Checkov 扫描，将检查结果作为 PR Comment 反馈给开发者。扫描失败可以配置为阻止合并（Hard Fail）或仅警告（Soft Fail）。初始接入阶段建议使用 Soft Fail，逐步收紧到 Hard Fail。


策略生命周期管理
策略即代码的 GitOps：所有策略定义存储在 Git 仓库中，通过 PR 审查变更，通过 CI/CD 自动部署到集群。策略变更的审查应该包括安全团队和平台团队的协同审核。


策略测试：策略代码也需要测试。OPA 内置了测试框架（opa test），Kyverno 支持 kyverno test 命令。测试用例应覆盖正向（合规资源应通过）和反向（违规资源应被拒绝）两类场景。


渐进式推广（Dry-Run → Audit → Enforce）：新策略应先以 Dry-Run 模式部署（记录违规但不拦截），观察影响范围和误报率。确认无误后切换到 Enforce 模式实际拦截违规操作。Gatekeeper 和 Kyverno 都支持通过 enforcementAction: dryrun 或 validationFailureAction: Audit 实现。


小结
    

  • PaC 将安全策略从文档描述转化为可机器执行的代码，在 CI/CD 和 Admission 等控制点自动拦截违规操作
    • 

  • OPA/Gatekeeper 使用 Rego 语言适合复杂逻辑和跨平台场景，Kyverno 使用 YAML 适合纯 Kubernetes 场景且学习门槛更低
    • 

  • Gatekeeper 的 ConstraintTemplate + Constraint 模型实现了策略逻辑与应用范围的分离，同一策略可参数化应用
    • 

  • Kyverno 的 Mutate 能力可以自动修正不合规资源而非仅仅拒绝，提升开发者体验
    • 

  • Checkov 内置 1000+ IaC 安全规则，在 PR 阶段拦截 Terraform/K8s 配置中的安全风险
    • 

  • 新策略应遵循 Dry-Run→Audit→Enforce 的渐进式推广路径，避免误报导致的业务中断
    •
