事故响应

事故管理概述

事故（Incident）是指对服务可用性或性能产生显著影响的非预期事件。高效的事故响应流程能够最小化用户影响、加速恢复并通过事后复盘持续改进系统可靠性。

事故分级
事故分级（Severity Level）决定了响应的速度、范围和参与人员。清晰的分级标准避免过度响应或响应不足。

提示： 事故分级时宁可高估也不要低估。如果不确定是 SEV2 还是 SEV3，按 SEV2 处理。在事故处置过程中可以根据进一步的信息调整级别，但初期响应不足可能导致影响范围扩大。

事后复盘
事后复盘（Post-Mortem / Incident Review）是事故管理中最有价值的环节。其目的不是追究责任，而是识别系统性改进机会。


复盘报告模板
cat > incident-report-template.md << 'EOF'
# 事故报告：[事故标题]

## 基本信息
- 事故编号：INC-YYYY-NNN
- 严重级别：SEV-N
- 影响时长：HH:MM
- 影响范围：[受影响的服务和用户数]
- 事故指挥官：[姓名]

## 时间线
| 时间 | 事件 |
| ---- | ---- |
| HH:MM | 告警触发 |
| HH:MM | 事故声明 |
| HH:MM | 根因定位 |
| HH:MM | 修复部署 |
| HH:MM | 服务恢复 |

## 根因分析
[描述导致事故的根本原因]

## 影响分析
[量化事故对用户和业务的影响]

## 改进项
| 改进项 | 负责人 | 截止日期 | 优先级 |
| ------ | ------ | -------- | ------ |
| [改进措施] | [姓名] | [日期] | P0/P1/P2 |

## 经验教训
[从事故中学到的关键经验]
EOF




复盘原则
说明





无指责文化
关注系统改进而非个人追责




基于事实
用数据和时间线还原真相




5 Why 分析
连续追问直到发现根因




可操作的改进项
每个改进项有明确的责任人和截止日期




公开透明
复盘报告全团队可见







提示： "无指责文化"（Blameless Culture）是高效事故管理的基石。当团队成员担心被追责时，他们会隐藏信息和回避风险操作，反而降低了系统可靠性。将注意力集中在"如何改进系统以防止再次发生"而非"谁犯了错误"。

Runbook 运维手册





cat > runbook/high-error-rate.md << 'EOF'
# Runbook: API 错误率告警

## 告警条件
API 5xx 错误率 > 5%，持续 5 分钟

## 排查步骤
1. 检查最近是否有部署：kubectl rollout history deployment/api -n production
2. 查看 Pod 状态：kubectl get pods -n production -l app=api
3. 查看错误日志：kubectl logs -l app=api -n production --tail 100 | grep ERROR
4. 检查上游依赖：kubectl exec -it <pod> -- curl -s http://db:5432

## 恢复操作
- 如果是新部署导致：kubectl rollout undo deployment/api -n production
- 如果是资源不足：kubectl scale deployment/api --replicas=10 -n production
- 如果是上游依赖故障：启动降级模式

## 升级条件
- 15 分钟内无法定位根因
- 影响范围持续扩大
EOF


小结
    

  • 事故管理遵循"检测 → 分级 → 响应 → 恢复 → 复盘 → 改进"的闭环流程。
    • 

  • 事故分级决定响应速度和参与人员，宁可高估不可低估。
    • 

  • 常见恢复手段包括版本回滚、紧急扩容和功能降级，优先选择风险最低的方案。
    • 

  • 事后复盘的核心是无指责文化和可操作的改进项，每个改进项必须有明确的责任人和截止日期。
    • 

  • Runbook 是值班工程师的操作指南，应覆盖所有常见告警场景的排查和恢复步骤。
    •
