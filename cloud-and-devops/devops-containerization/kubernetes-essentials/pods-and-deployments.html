Pod 与 Deployment

Pod 基础

Pod 是 Kubernetes 中最小的可部署单元。一个 Pod 封装了一个或多个紧密关联的容器，它们共享网络命名空间（同一 IP 地址）和存储卷。

apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: my-app
    version: v1
spec:
  containers:
    - name: app
      image: myapp:1.0.0
      ports:
        - containerPort: 3000
      resources:
        requests:
          cpu: '100m'
          memory: '128Mi'
        limits:
          cpu: '500m'
          memory: '512Mi'
      livenessProbe:
        httpGet:
          path: /health
          port: 3000
        initialDelaySeconds: 15
        periodSeconds: 10
      readinessProbe:
        httpGet:
          path: /ready
          port: 3000
        initialDelaySeconds: 5
        periodSeconds: 5




Pod 特性
说明





共享网络
同一 Pod 内容器共享 IP 和端口空间




共享存储
可声明共享 Volume




共同调度
同一 Pod 的容器运行在同一节点




生命周期绑定
Pod 内所有容器同时启动和停止







Pod 生命周期
Pod 从创建到终止经历多个阶段，理解这些阶段对于排查问题至关重要。


kubectl get pod my-app -o jsonpath='{.status.phase}'

kubectl describe pod my-app

kubectl get events --field-selector involvedObject.name=my-app




阶段
说明
常见原因





Pending
等待调度或拉取镜像
资源不足、镜像拉取




Running
至少一个容器在运行
正常状态




Succeeded
所有容器成功退出
Job 完成




Failed
至少一个容器非零退出
应用错误




Unknown
无法获取 Pod 状态
节点通信异常





容器探针
Kubernetes 通过三种探针监控容器健康状态：






探针类型
作用
失败后果





livenessProbe
检测容器是否存活
重启容器




readinessProbe
检测容器是否就绪接收流量
从 Service 端点移除




startupProbe
检测容器是否启动完成
暂停其他探针检测





spec:
  containers:
    - name: app
      startupProbe:
        httpGet:
          path: /health
          port: 3000
        failureThreshold: 30
        periodSeconds: 10
      livenessProbe:
        httpGet:
          path: /health
          port: 3000
        periodSeconds: 10
        failureThreshold: 3
      readinessProbe:
        httpGet:
          path: /ready
          port: 3000
        periodSeconds: 5
        failureThreshold: 2


提示： startupProbe 在容器启动完成前会阻止 livenessProbe 和 readinessProbe 的执行。对于启动较慢的应用（如 Java），使用 startupProbe 可以避免在启动阶段被 livenessProbe 误杀。






Deployment 资源
Deployment 是管理 Pod 副本集的高级控制器。它通过 ReplicaSet 维护指定数量的 Pod 副本，并支持声明式的滚动更新和回滚。


apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
  labels:
    app: api-server
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-server
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: api-server
    spec:
      containers:
        - name: api
          image: myapi:1.2.3
          ports:
            - containerPort: 3000
          resources:
            requests:
              cpu: '200m'
              memory: '256Mi'
            limits:
              cpu: '1000m'
              memory: '1Gi'
kubectl apply -f deployment.yaml

kubectl get deployment api-server

kubectl scale deployment api-server --replicas=5

kubectl rollout status deployment api-server


滚动更新与回滚
Deployment 的滚动更新策略确保应用更新过程中始终有可用实例服务请求。


kubectl set image deployment/api-server api=myapi:1.3.0

kubectl rollout status deployment/api-server

kubectl rollout history deployment/api-server

kubectl rollout undo deployment/api-server

kubectl rollout undo deployment/api-server --to-revision=2




更新策略参数
说明
推荐值





maxSurge
超出期望副本数的最大 Pod 数
1 或 25%




maxUnavailable
更新期间不可用的最大 Pod 数
0 或 25%




minReadySeconds
Pod 就绪后等待时间
10-30s




revisionHistoryLimit
保留的旧 ReplicaSet 数量
10







提示： 设置 maxUnavailable: 0 和 maxSurge: 1 可以实现零停机滚动更新——在新 Pod 就绪之前不会终止旧 Pod。但这需要额外的集群资源来运行临时多出的 Pod。






资源管理
合理的资源请求（requests）和限制（limits）是集群稳定运行的关键。


spec:
  containers:
    - name: app
      resources:
        requests:
          cpu: '200m'
          memory: '256Mi'
        limits:
          cpu: '1000m'
          memory: '1Gi'




资源配置
作用
不设置的后果





requests
调度器分配节点的依据
无法保证资源




limits
容器可使用的资源上限
可能耗尽节点资源





kubectl top pods

kubectl top nodes

kubectl describe node <node-name> | grep -A 5 "Allocated resources"


小结
    

  • Pod 是 Kubernetes 最小部署单元，同一 Pod 内容器共享网络和存储。
    • 

  • 三种探针（liveness、readiness、startup）协同监控容器健康，确保只有就绪的 Pod 接收流量。
    • 

  • Deployment 通过 ReplicaSet 管理 Pod 副本，支持声明式的滚动更新和一键回滚。
    • 

  • 滚动更新通过 maxSurge 和 maxUnavailable 控制更新节奏，maxUnavailable: 0 实现零停机更新。
    • 

  • 合理配置 requests 和 limits 确保调度器做出正确决策，防止资源争抢。
    •
