架构与概念

Kubernetes 设计哲学

Kubernetes 的核心设计理念是声明式配置——用户描述期望的系统状态（Desired State），由控制器持续驱动系统向期望状态收敛。这与传统的命令式运维（逐步执行操作）形成鲜明对比。





设计原则
说明





声明式 API
描述目标状态而非操作步骤




控制器模式
持续调谐实际状态向期望状态收敛




不可变基础设施
通过替换而非修改来更新




松耦合
组件通过 API 交互，可独立替换




自愈能力
自动检测并修复故障







集群架构
Kubernetes 集群由控制平面（Control Plane）和工作节点（Worker Node）组成。控制平面负责集群的决策和调度，工作节点负责运行实际的应用负载。


控制平面组件

职责

分布式键值存储，保存集群全部状态

决定 Pod 运行在哪个节点




kube-controller-manager
运行各类控制器（Deployment、Node 等）




cloud-controller-manager
对接云平台 API（负载均衡、存储等）

提示： 在生产环境中，控制平面通常部署为高可用模式（3 或 5 个 etcd 节点 + 多个 API Server）。单节点控制平面适用于开发和测试环境。






核心资源对象
Kubernetes 通过资源对象（Resource）描述集群中的各种实体。所有资源都遵循统一的 API 结构。


apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: default
  labels:
    app: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: app
          image: myapp:1.0.0

kubectl 基础操作
kubectl 是与 Kubernetes 集群交互的命令行工具，支持声明式和命令式两种操作方式。


kubectl apply -f deployment.yaml

kubectl get pods -n default -o wide

kubectl describe pod my-app-xxx-yyy

kubectl logs -f my-app-xxx-yyy --tail 100

kubectl exec -it my-app-xxx-yyy -- sh

kubectl delete -f deployment.yaml

小结
    

  • Kubernetes 采用声明式 API 设计，用户描述期望状态，控制器持续驱动系统收敛。
    • 

  • 集群分为控制平面（API Server、etcd、Scheduler、Controller Manager）和工作节点（kubelet、kube-proxy、容器运行时）。
    • 

  • 所有资源对象遵循统一的 YAML 结构：apiVersion、kind、metadata、spec。
    • 

  • 生产环境使用 kubectl apply -f 声明式管理，所有配置纳入版本控制。
    • 

  • 本地学习推荐使用 minikube 或 kind 快速搭建实验集群。
