版本策略

Monorepo 版本管理的特殊性

在 Polyrepo 中，每个仓库只需管理自己的版本号。但在 Monorepo 中，多个包共存于同一仓库，版本管理面临新的问题：一次 PR 可能同时修改了三个包，这三个包的版本号应该如何变更？关联的包是否需要同步更新版本？这些问题的答案取决于你选择的版本策略。



Fixed 模式 vs Independent 模式




维度
Fixed（固定模式）
Independent（独立模式）





版本号
所有包共享同一版本号
每个包有独立的版本号




发布
所有包一起发布
只发布有变更的包




消费方
简单——只需记住一个版本号
灵活——按需更新




适用场景
紧密耦合的包集合
松耦合的工具库集合




典型项目
Babel、Angular
Lodash 系列、独立工具





Fixed 模式示例
{
  "version": "2.5.0",
  "packages": {
    "@myorg/ui": "2.5.0",
    "@myorg/utils": "2.5.0",
    "@myorg/types": "2.5.0",
    "@myorg/config": "2.5.0"
  }
}
Independent 模式示例
{
  "packages": {
    "@myorg/ui": "3.1.0",
    "@myorg/utils": "2.8.4",
    "@myorg/types": "1.5.2",
    "@myorg/config": "1.0.1"
  }
}


提示： 如果你的包之间经常需要一起使用，Fixed 模式降低了消费方的心智负担。如果包之间相对独立，Independent 模式避免了不必要的版本号膨胀。






Changesets 工作流
Changesets 是目前 Monorepo 版本管理的事实标准工具。它将"记录变更意图"和"执行版本更新"分离为两个独立步骤：


// 安装 Changesets
// pnpm add -D @changesets/cli -w
// pnpm changeset init

// 步骤 1：开发者在 PR 中记录变更意图
// pnpm changeset
运行 pnpm changeset 会引导你选择受影响的包和变更级别：


🦋  Which packages would you like to include?
◉ @myorg/ui
◉ @myorg/utils

🦋  Which packages should have a major bump?
◯ @myorg/ui
◯ @myorg/utils

🦋  Which packages should have a minor bump?
◉ @myorg/ui

🦋  Please enter a summary for this change:
◉ Added new DatePicker component with range selection support
生成的 changeset 文件：


---
'@myorg/ui': minor
'@myorg/utils': patch
---

Added new DatePicker component with range selection support. Updated date formatting utilities.
{
  "$schema": "https://unpkg.com/@changesets/config@3.0.0/schema.json",
  "changelog": "@changesets/cli/changelog",
  "commit": false,
  "fixed": [],
  "linked": [["@myorg/ui", "@myorg/types"]],
  "access": "restricted",
  "baseBranch": "main",
  "updateInternalDependencies": "patch",
  "ignore": ["@myorg/web", "@myorg/admin"]
}




配置字段
含义





fixed
固定版本组，组内包同步版本




linked
链接版本组，组内包的 major/minor 同步




access
npm 发布权限（public/restricted）




updateInternalDependencies
内部依赖的自动更新级别




ignore
不参与版本管理的包（如应用）







Conventional Commits
Conventional Commits 是一种标准化的提交信息格式，可以与 Changesets 配合实现自动化版本推断：


feat(ui): add DatePicker component
fix(utils): handle timezone offset in formatDate
docs(types): update JSDoc for ApiResponse type
chore(config): bump typescript to 5.7.0
BREAKING CHANGE: DatePicker API changed from single date to date range




前缀
版本影响
说明





feat
minor
新功能




fix
patch
Bug 修复




docs
无
文档更新




chore
无
工具/配置




BREAKING CHANGE
major
不兼容变更





{
  "name": "my-monorepo",
  "devDependencies": {
    "@commitlint/cli": "^19.0.0",
    "@commitlint/config-conventional": "^19.0.0"
  }
}
// commitlint.config.ts
import type { UserConfig } from '@commitlint/types';

const config: UserConfig = {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'scope-enum': [2, 'always', ['ui', 'utils', 'types', 'config', 'web', 'admin']],
  },
};

export default config;


版本消费流程


自动化版本 PR
Changesets 提供了 GitHub Action 来自动化版本更新和发布：


# .github/workflows/release.yml
name: Release

on:
  push:
    branches: [main]

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - run: pnpm install --frozen-lockfile

      - name: Create Release PR or Publish
        uses: changesets/action@v1
        with:
          publish: pnpm changeset publish
          version: pnpm changeset version
          commit: 'chore: version packages'
          title: 'chore: version packages'
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}


小结
    

  • Monorepo 版本策略分为 Fixed（统一版本）和 Independent（独立版本），选择取决于包间耦合度
    • 

  • Changesets 将"记录变更"和"执行版本更新"分离，是 Monorepo 版本管理的事实标准
    • 

  • Conventional Commits 标准化提交信息格式，支持自动推断版本变更级别
    • 

  • linked 配置让相关包的 major/minor 版本保持同步，适合有紧密关联的包组
    • 

  • 通过 GitHub Action 实现自动化的版本 PR 和 npm 发布，减少人工操作
    •
