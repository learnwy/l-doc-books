包设计原则

单一职责原则

单一职责原则（Single Responsibility Principle）在包设计中的含义是：每个包应该只做一件事，并且做好这件事。一个名为 @myorg/utils 的包如果同时包含日期处理、HTTP 请求、字符串操作和文件系统工具，那它实际上是一个"杂货铺"而非一个有明确职责的包。

但"单一职责"不意味着把每个函数都拆成一个包。关键是找到合理的内聚度——包内的代码应该因为同一个原因而变化。






拆分粒度
示例
适用场景





过粗
@myorg/utils（万能包）
❌ 不推荐




适中
@myorg/date-utils
✅ 大多数场景




过细
@myorg/format-date
❌ 通常不必要







API Surface 控制
API 表面积（API Surface）是指包对外暴露的公开接口数量。表面积越大，包的维护负担越重——每一个公开 API 都是一个承诺，修改它可能影响所有消费方。


// packages/ui/src/button.ts
interface ButtonProps {
  variant: 'primary' | 'secondary' | 'ghost';
  size: 'sm' | 'md' | 'lg';
  children: React.ReactNode;
  onClick?: () => void;
  disabled?: boolean;
}

export function Button({ variant, size, children, onClick, disabled }: ButtonProps) {
  const className = getButtonClassName(variant, size, disabled);
  return (
    <button className={className} onClick={onClick} disabled={disabled}>
      {children}
    </button>
  );
}

function getButtonClassName(
  variant: ButtonProps['variant'],
  size: ButtonProps['size'],
  disabled?: boolean,
): string {
  return [
    'btn',
    `btn-${variant}`,
    `btn-${size}`,
    disabled && 'btn-disabled',
  ].filter(Boolean).join(' ');
}
上面的例子中，Button 组件和 ButtonProps 类型是公开 API，而 getButtonClassName 是内部实现。消费方无需知道样式类名如何生成。




提示： 评估是否应该公开一个 API 的标准：如果将来需要修改它的实现，是否会破坏消费方的代码？如果会，就要三思是否真的需要暴露。






Barrel Exports
Barrel export 是使用 index.ts 文件统一管理包的公开接口的模式。它是控制 API 表面积的主要手段：


// packages/ui/src/index.ts
export { Button } from './button';
export type { ButtonProps } from './button';
export { Input } from './input';
export type { InputProps } from './input';
export { Modal } from './modal';
export type { ModalProps } from './modal';
export { Toast, useToast } from './toast';
export type { ToastProps } from './toast';
{
  "name": "@myorg/ui",
  "exports": {
    ".": {
      "types": "./src/index.ts",
      "default": "./src/index.ts"
    }
  }
}
子路径导出
当包的功能可以逻辑分组时，使用子路径导出（Subpath Exports）提供更细粒度的导入路径：


{
  "name": "@myorg/ui",
  "exports": {
    ".": {
      "types": "./src/index.ts",
      "default": "./src/index.ts"
    },
    "./button": {
      "types": "./src/button.ts",
      "default": "./src/button.ts"
    },
    "./form": {
      "types": "./src/form/index.ts",
      "default": "./src/form/index.ts"
    }
  }
}
// 消费方的两种导入方式
import { Button } from '@myorg/ui';
import { Button } from '@myorg/ui/button';


包的内部结构
一个设计良好的共享包应该有清晰的内部结构：


packages/ui/
├── src/
│   ├── button.ts
│   ├── button.test.ts
│   ├── input.ts
│   ├── input.test.ts
│   ├── modal.ts
│   ├── modal.test.ts
│   ├── toast.ts
│   ├── toast.test.ts
│   ├── internal/
│   │   ├── use-focus-trap.ts
│   │   └── classname-utils.ts
│   └── index.ts
├── package.json
├── tsconfig.json
└── vitest.config.ts




目录/文件
职责





src/index.ts
Barrel export，定义公开 API




src/*.ts
各组件/函数的实现




src/*.test.ts
对应的测试文件




src/internal/
内部工具，不通过 index.ts 导出







提示： internal/ 目录的约定明确告诉开发者：这些代码是内部实现，不应被外部包直接引用。配合 exports 字段的限制，可以在运行时也阻止外部访问。






包的依赖设计
共享包应该尽量减少外部依赖，降低消费方的安装成本和潜在的版本冲突：


{
  "name": "@myorg/http-client",
  "dependencies": {},
  "peerDependencies": {
    "zod": "^3.0.0"
  },
  "devDependencies": {
    "zod": "^3.24.0",
    "vitest": "^3.0.0",
    "typescript": "^5.7.0"
  }
}

// 渐进式 API 迁移
/** @deprecated Use formatCurrency instead */
export function formatMoney(amount: number): string {
  return formatCurrency(amount, 'CNY');
}

export function formatCurrency(amount: number, currency: string): string {
  return new Intl.NumberFormat('zh-CN', {
    style: 'currency',
    currency,
  }).format(amount);
}


小结
    

  • 单一职责原则要求每个包有明确的功能边界，既不过粗也不过细
    • 

  • API 表面积应尽量小，每个公开接口都是一个需要长期维护的承诺
    • 

  • Barrel exports 通过 index.ts 统一管理包的公开接口，配合 exports 字段限制访问
    • 

  • 共享包应最小化外部依赖，框架类依赖使用 peerDependencies
    • 

  • Breaking changes 应提供过渡期，使用 @deprecated 标记引导消费方迁移
    •
