多仓迁移

迁移策略选择

从 Polyrepo 迁移到 Monorepo 有两种基本策略：大爆炸迁移（一次性合并所有仓库）和渐进式迁移（分批逐步合并）。选择哪种策略取决于团队规模、仓库数量和业务紧迫度。

保留 Git 历史
迁移时保留 Git 历史是团队的常见需求。使用 git subtree 或 git filter-repo 可以将旧仓库的完整历史合并到 Monorepo 中：


方法一：git subtree
# 1. 创建 Monorepo 根仓库
mkdir my-monorepo && cd my-monorepo
git init

# 2. 添加旧仓库作为 remote
git remote add ui-repo https://github.com/org/ui-lib.git
git remote add utils-repo https://github.com/org/utils.git

# 3. 使用 subtree 合并，保留历史
git subtree add --prefix=packages/ui ui-repo main
git subtree add --prefix=packages/utils utils-repo main

# 4. 清理 remote
git remote remove ui-repo
git remote remove utils-repo
方法二：git filter-repo（推荐）
# 1. 克隆旧仓库
git clone https://github.com/org/ui-lib.git ui-lib-temp
cd ui-lib-temp

# 2. 重写历史，将所有文件移动到目标子目录
git filter-repo --to-subdirectory-filter packages/ui

# 3. 在 Monorepo 中添加为 remote 并合并
cd ../my-monorepo
git remote add ui-temp ../ui-lib-temp
git fetch ui-temp
git merge ui-temp/main --allow-unrelated-histories
git remote remove ui-temp


提示： git filter-repo 比 git filter-branch 快得多（100x+），且更安全。它是 Git 官方推荐的历史重写工具。






渐进式迁移计划
渐进式迁移将整个过程分为多个阶段，每个阶段都可独立验证和回滚：


Phase 0：准备阶段
{
  "name": "my-monorepo",
  "private": true,
  "packageManager": "pnpm@9.15.0",
  "scripts": {
    "build": "turbo run build",
    "test": "turbo run test",
    "lint": "turbo run lint"
  }
}
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'
  - 'tooling/*'
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["^build"]
    },
    "lint": {
      "dependsOn": []
    }
  }
}

依赖引用迁移
迁移过程中最耗时的工作之一是将旧的 npm 包引用替换为 workspace 引用：


{
  "dependencies": {
    "@myorg/utils": "^1.5.0",
    "@myorg/types": "^1.2.0"
  }
}
{
  "dependencies": {
    "@myorg/utils": "workspace:*",
    "@myorg/types": "workspace:*"
  }
}
// scripts/migrate-deps.mts
import { readFileSync, writeFileSync, readdirSync } from 'node:fs';
import { join } from 'node:path';

const INTERNAL_PACKAGES = ['@myorg/utils', '@myorg/types', '@myorg/ui', '@myorg/config'];

function migratePackageJson(filePath: string): void {
  const pkg = JSON.parse(readFileSync(filePath, 'utf-8'));

  for (const depType of ['dependencies', 'devDependencies'] as const) {
    const deps = pkg[depType];
    if (!deps) continue;

    for (const name of INTERNAL_PACKAGES) {
      if (deps[name]) {
        deps[name] = 'workspace:*';
      }
    }
  }

  writeFileSync(filePath, JSON.stringify(pkg, null, 2) + '\n');
}

提示： 迁移后的第一周是"观察期"，保留旧仓库的只读副本，便于在发现问题时快速对照排查。






小结
    

  • 迁移策略应基于仓库数量和团队规模选择，渐进式迁移适合大多数场景
    • 

  • 使用 git filter-repo 保留完整的 Git 历史，是迁移中的关键步骤
    • 

  • 按依赖图的拓扑顺序从底层包开始迁移，确保每个阶段都可独立验证
    • 

  • 自动化脚本将旧的 npm 版本引用批量替换为 workspace:*
    • 

  • 迁移后保留旧仓库的只读副本作为安全网，经过一段观察期后再归档
    •
