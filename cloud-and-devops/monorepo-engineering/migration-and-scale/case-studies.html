案例分析

三种典型 Monorepo 架构

Monorepo 并非一种固定的架构模式，不同的业务场景和团队特征会催生出截然不同的仓库结构。本节通过三个典型案例——前端 Monorepo、全栈 Monorepo 和开源库 Monorepo——展示不同场景下的架构选择和实践差异。



案例一：前端 Monorepo
场景特征
一个中型团队维护多个前端应用（主站、管理后台、H5 页面），共享 UI 组件库和工具函数。所有应用使用 React + TypeScript 技术栈。


架构设计
frontend-monorepo/
├── apps/
│   ├── web/                   # Next.js 主站
│   ├── admin/                 # Vite + React 管理后台
│   └── h5/                    # Vite + React 移动端
├── packages/
│   ├── ui/                    # 共享 UI 组件库
│   ├── hooks/                 # 共享 React Hooks
│   ├── utils/                 # 通用工具函数
│   └── api-client/            # API 请求封装
├── tooling/
│   ├── tsconfig/
│   └── eslint-config/
├── turbo.json
└── pnpm-workspace.yaml

案例二：全栈 Monorepo
场景特征
一个全栈项目包含 React 前端、Node.js 后端 API 和共享的类型定义。前后端共享数据契约、验证逻辑和工具函数。


架构设计
fullstack-monorepo/
├── apps/
│   ├── web/                   # Next.js 前端
│   └── api/                   # Fastify 后端
├── packages/
│   ├── types/                 # 共享类型定义
│   ├── validators/            # 共享验证逻辑 (zod schemas)
│   ├── utils/                 # 共享工具函数
│   └── db/                    # 数据库 Schema 和 ORM
├── tooling/
│   ├── tsconfig/
│   └── eslint-config/
└── docker-compose.yml
// packages/validators/src/user.ts
import { z } from 'zod';

export const createUserSchema = z.object({
  name: z.string().min(2).max(50),
  email: z.string().email(),
  role: z.enum(['admin', 'editor', 'viewer']),
});

export type CreateUserInput = z.infer<typeof createUserSchema>;
// apps/api/src/routes/users.ts
import { createUserSchema } from '@myorg/validators';

app.post('/users', async (request, reply) => {
  const result = createUserSchema.safeParse(request.body);
  if (!result.success) {
    return reply.status(400).send({ errors: result.error.issues });
  }
  const user = await db.user.create({ data: result.data });
  return reply.send({ data: user });
});
// apps/web/src/components/CreateUserForm.tsx
import { createUserSchema, type CreateUserInput } from '@myorg/validators';

function CreateUserForm() {
  const onSubmit = (data: CreateUserInput) => {
    const result = createUserSchema.safeParse(data);
    if (!result.success) return;
    fetch('/api/users', {
      method: 'POST',
      body: JSON.stringify(result.data),
    });
  };
  return <form onSubmit={handleSubmit(onSubmit)}>{/* ... */}</form>;
}

案例三：开源库 Monorepo
场景特征
一个开源工具库需要发布多个 npm 包：核心包、React 适配器、Vue 适配器和 CLI 工具。每个包有独立的版本号和发布周期。


架构设计
oss-monorepo/
├── packages/
│   ├── core/                  # 核心逻辑（框架无关）
│   ├── react/                 # React 适配器
│   ├── vue/                   # Vue 适配器
│   ├── cli/                   # CLI 工具
│   └── types/                 # 公共类型
├── docs/                      # 文档站点
├── examples/
│   ├── react-example/
│   └── vue-example/
├── .changeset/
│   └── config.json
└── turbo.json

小结
    

  • 前端 Monorepo 的核心价值是 UI 组件复用和统一规范，通常不需要 npm 发布
    • 

  • 全栈 Monorepo 通过共享类型和验证逻辑实现前后端的数据契约一致性
    • 

  • 开源库 Monorepo 的核心挑战是多包的版本管理和协调发布
    • 

  • 三种架构的共性是 pnpm workspace + Turborepo + TypeScript 的技术基座
    • 

  • 架构选择应基于业务特征而非技术偏好，不同场景的最优解各不相同
