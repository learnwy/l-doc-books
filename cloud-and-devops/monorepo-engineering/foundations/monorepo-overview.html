Monorepo 概述

什么是 Monorepo

Monorepo（Monolithic Repository）是一种将多个项目、多个包存放在同一个版本控制仓库中的代码组织策略。它与多仓（Polyrepo / Multi-repo）模式形成对比——后者为每个项目或库维护独立的仓库。

需要明确的是，Monorepo 不等于 Monolith（单体应用）。Monorepo 中的每个包仍然是独立的模块，拥有自己的 package.json、独立的构建流程和发布周期。代码在物理上共处一仓，但在逻辑上保持模块化边界。

Monorepo 的核心优势
代码复用与原子提交
在 Polyrepo 模式下，共享库的一个 bug fix 需要经历：修复 → 发布新版本 → 下游项目更新依赖 → 验证兼容性。在 Monorepo 中，这个流程简化为一次原子提交：


// packages/utils/src/format.ts
export function formatCurrency(amount: number, currency: string): string {
  return new Intl.NumberFormat('zh-CN', {
    style: 'currency',
    currency,
  }).format(amount);
}

// apps/web/src/components/Price.tsx
import { formatCurrency } from '@myorg/utils';

export function Price({ amount }: { amount: number }) {
  return <span>{formatCurrency(amount, 'CNY')}</span>;
}


提示： 原子提交的价值在大型重构时尤为明显。例如重命名一个共享函数，Monorepo 可以在一次 PR 中同时修改定义和所有调用点，而 Polyrepo 需要跨仓库协调。




统一工具链
Monorepo 允许在仓库根目录维护统一的工具配置，所有包共享同一套规范：


// 根目录 eslint.config.ts
import type { Linter } from 'eslint';

const config: Linter.Config[] = [
  {
    rules: {
      'no-console': 'warn',
      'no-unused-vars': 'error',
    },
  },
];

export default config;
{
  "compilerOptions": {
    "strict": true,
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}


Monorepo 的典型挑战
仓库体积与 Git 性能
随着代码量增长，git clone、git status、git log 等操作会变慢。Google 的 Monorepo 包含超过 20 亿行代码，他们为此开发了自定义的版本控制系统（Piper）。对于中小规模团队，Git 的 sparse checkout 和 shallow clone 可以缓解这一问题：


git clone --depth 1 --filter=blob:none --sparse https://github.com/org/monorepo.git
cd monorepo
git sparse-checkout set apps/web packages/ui
CI 构建时间
如果每次提交都构建所有包，CI 时间会随包数量线性增长。解决方案是受影响检测（affected detection）——只构建和测试被当前变更影响到的包。Turborepo 和 Nx 都提供了这一核心能力。


代码所有权与权限
Monorepo 中所有代码默认对所有人可见。可以通过 CODEOWNERS 文件和 PR 审查规则来建立代码所有权边界：


# .github/CODEOWNERS
/apps/web/          @team-web
/apps/admin/        @team-admin
/packages/ui/       @team-design-system
/packages/utils/    @team-platform


适用场景与不适用场景
适合 Monorepo 的场景：


    

  • 前端应用 + 共享组件库 + 工具函数库的组合
    • 

  • 全栈项目（前端 + 后端 + 共享类型定义）
    • 

  • 开源库的多包发布（如 Babel、Next.js）
    • 

  • 微服务架构中共享 proto/schema 定义
    • 



不适合 Monorepo 的场景：


    

  • 完全独立、无代码共享的项目
    • 

  • 团队分布在不同组织，无法统一工具链
    • 

  • 对代码隔离和权限控制有严格要求
    • 

  • 技术栈差异极大（如 Go 后端 + Swift iOS + React Web）
    •

小结
    

  • Monorepo 是将多个项目放在同一个仓库中管理的策略，核心价值在于代码复用、原子提交和统一工具链
    • 

  • Monorepo 不等于 Monolith，仓库中的每个包仍然保持独立的模块边界
    • 

  • 主要挑战包括仓库体积增长、CI 构建时间和代码所有权管理
    • 

  • 选择 Monorepo 还是 Polyrepo 应基于代码共享程度、团队规模和工具链投入意愿来决策
    • 

  • Google、Meta、Microsoft 等大厂的实践证明 Monorepo 可以扩展到极大规模，但需要相应的工具支撑
    •
