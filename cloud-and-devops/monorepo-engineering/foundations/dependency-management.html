依赖管理

Monorepo 依赖管理的特殊性

在 Polyrepo 模式下，每个项目的依赖管理相对简单——安装、锁定、更新。但在 Monorepo 中，依赖关系变得立体化：既有外部依赖（来自 npm registry），也有内部依赖（Internal Dependencies，仓库内包之间的引用）。如何协调这两类依赖，是 Monorepo 依赖管理的核心挑战。



内部依赖与 workspace 协议
内部依赖通过 workspace: 协议声明，包管理器会自动将其解析为仓库内的本地包，而不是从 npm registry 下载：


{
  "name": "@myorg/web",
  "version": "1.0.0",
  "dependencies": {
    "@myorg/ui": "workspace:*",
    "@myorg/utils": "workspace:*",
    "@myorg/types": "workspace:*",
    "react": "^18.3.0",
    "react-dom": "^18.3.0"
  },
  "devDependencies": {
    "@myorg/tsconfig": "workspace:*",
    "@myorg/eslint-config": "workspace:*"
  }
}
在安装时，包管理器会在 node_modules 中创建符号链接指向本地包的源码目录。这意味着对内部包的任何修改都会立即反映到依赖方，无需重新安装或发布。


// packages/utils/src/index.ts
export function clamp(value: number, min: number, max: number): number {
  return Math.min(Math.max(value, min), max);
}

// apps/web/src/hooks/useSlider.ts
import { clamp } from '@myorg/utils';

export function useSlider(initial: number) {
  const normalize = (v: number) => clamp(v, 0, 100);
  return { value: normalize(initial) };
}


提示： 内部包的修改无需发布即可被其他包感知，这是 Monorepo 开发体验优于 Polyrepo 的关键原因之一。






外部依赖版本策略
Monorepo 中的外部依赖面临一个关键决策：不同包是否应该使用同一版本的外部依赖？


统一版本策略
推荐在根目录的 package.json 中使用 catalog 或 overrides 来统一关键依赖的版本：


# pnpm-workspace.yaml（pnpm v9+ catalog 功能）
packages:
  - 'apps/*'
  - 'packages/*'

catalog:
  react: ^18.3.0
  react-dom: ^18.3.0
  typescript: ^5.7.0
  zod: ^3.24.0
  vitest: ^3.0.0
{
  "name": "@myorg/web",
  "dependencies": {
    "react": "catalog:",
    "react-dom": "catalog:",
    "zod": "catalog:"
  }
}
版本冲突处理
当不同包需要不同版本的同一依赖时，pnpm 可以通过 overrides 强制统一，或允许版本共存：


{
  "pnpm": {
    "overrides": {
      "typescript": "^5.7.0",
      "postcss": "^8.5.0"
    },
    "peerDependencyRules": {
      "allowedVersions": {
        "react": "18"
      },
      "ignoreMissing": ["@babel/core"]
    }
  }
}


Peer Dependencies 在共享包中的使用
Peer Dependencies 在 Monorepo 的共享包中扮演关键角色。当一个共享 UI 库需要使用 React，但不应该自己安装 React（因为应用层已经安装了），就应该将 React 声明为 peer dependency：


{
  "name": "@myorg/ui",
  "version": "1.0.0",
  "peerDependencies": {
    "react": "^18.0.0",
    "react-dom": "^18.0.0"
  },
  "peerDependenciesMeta": {
    "react-dom": {
      "optional": true
    }
  },
  "devDependencies": {
    "react": "^18.3.0",
    "react-dom": "^18.3.0"
  }
}


提示： 共享包的 devDependencies 中也应该安装 peer dependencies 的具体版本，确保开发和测试时能正常运行。






依赖拓扑与构建顺序
内部包之间的依赖关系形成一个有向无环图（DAG）。构建、测试和发布都必须按照这个拓扑顺序进行：


// turbo.json - 基于依赖图的任务编排
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "typecheck": {
      "dependsOn": ["^build"]
    }
  }
}
"dependsOn": ["^build"] 中的 ^ 表示"先构建当前包的所有依赖包"。Turborepo 会自动根据 DAG 确定正确的构建顺序。




依赖审计与安全
Monorepo 的统一依赖管理也简化了安全审计：


{
  "scripts": {
    "audit": "pnpm audit --prod",
    "audit:fix": "pnpm audit --fix",
    "deps:check": "pnpm outdated -r",
    "deps:update": "pnpm update -r --latest",
    "deps:dedupe": "pnpm dedupe"
  }
}

小结
    

  • Monorepo 中的依赖分为内部依赖（workspace 包间引用）和外部依赖（npm registry），管理策略各不相同
    • 

  • workspace:* 协议实现内部包的本地链接，修改即时生效，无需发布
    • 

  • 外部依赖推荐使用 pnpm catalog 或 overrides 统一版本，避免版本碎片化
    • 

  • 共享包应将框架类依赖声明为 peer dependencies，确保运行时使用同一实例
    • 

  • 内部依赖形成的 DAG 决定了构建顺序，Turborepo 通过 ^ 前缀自动处理拓扑排序
