项目结构

Monorepo 目录设计原则

Monorepo 的目录结构是整个工程实践的"骨架"。一个好的结构应该让新加入的开发者在几分钟内理解仓库的全貌，让工具链能自动发现和处理每个包，让代码的归属和边界一目了然。



标准目录布局
一个典型的 TypeScript Monorepo 目录结构如下：


my-monorepo/
├── apps/
│   ├── web/                        # Next.js 主站
│   │   ├── src/
│   │   ├── public/
│   │   ├── package.json
│   │   └── tsconfig.json
│   ├── admin/                      # 管理后台
│   │   ├── src/
│   │   ├── package.json
│   │   └── tsconfig.json
│   └── api/                        # 后端服务
│       ├── src/
│       ├── package.json
│       └── tsconfig.json
├── packages/
│   ├── ui/                         # 共享 UI 组件库
│   │   ├── src/
│   │   ├── package.json
│   │   └── tsconfig.json
│   ├── utils/                      # 通用工具函数
│   │   ├── src/
│   │   ├── package.json
│   │   └── tsconfig.json
│   └── types/                      # 共享类型定义
│       ├── src/
│       ├── package.json
│       └── tsconfig.json
├── tooling/
│   ├── tsconfig/                   # 共享 TS 配置
│   │   ├── base.json
│   │   ├── react.json
│   │   ├── node.json
│   │   └── package.json
│   └── eslint-config/              # 共享 ESLint 配置
│       ├── base.js
│       ├── react.js
│       └── package.json
├── .github/
│   └── workflows/
│       └── ci.yml
├── package.json
├── pnpm-workspace.yaml
├── turbo.json
└── tsconfig.json


提示： 将配置包放在 tooling/ 目录而非 packages/ 中，可以清晰地区分"面向业务的共享代码"和"面向工程的内部工具"。

关键规则：依赖只能从上层流向下层。apps 可以依赖 packages，packages 之间可以互相依赖，但 packages 绝不能依赖 apps。




包命名约定
统一的命名约定让包的用途和归属一目了然：


{
  "name": "@myorg/ui",
  "name": "@myorg/utils",
  "name": "@myorg/types",
  "name": "@myorg/eslint-config",
  "name": "@myorg/tsconfig",
  "name": "@myorg/web",
  "name": "@myorg/admin"
}

package.json 设计
每个包的 package.json 是其"身份证"，关键字段设计直接影响依赖解析、构建和发布：


{
  "name": "@myorg/ui",
  "version": "1.0.0",
  "private": false,
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./button": {
      "types": "./dist/button.d.ts",
      "import": "./dist/button.mjs"
    }
  },
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "files": ["dist"],
  "scripts": {
    "build": "tsup",
    "dev": "tsup --watch",
    "typecheck": "tsc --noEmit",
    "test": "vitest run"
  },
  "peerDependencies": {
    "react": "^18.0.0"
  },
  "devDependencies": {
    "@myorg/tsconfig": "workspace:*",
    "react": "^18.3.0",
    "tsup": "^8.0.0",
    "typescript": "^5.7.0"
  }
}

作用

定义包的公开入口，取代 main

TypeScript 类型入口
放在 exports 条件的第一位

设为 false 以启用 tree-shaking







内部包的开发模式入口
在 Monorepo 内部，包通常不需要先构建再使用。可以配置 开发模式入口，让消费方直接引用源码：


{
  "name": "@myorg/utils",
  "exports": {
    ".": {
      "types": "./src/index.ts",
      "default": "./src/index.ts"
    }
  }
}
{
  "name": "@myorg/utils",
  "publishConfig": {
    "exports": {
      ".": {
        "types": "./dist/index.d.ts",
        "import": "./dist/index.mjs"
      }
    }
  }
}


提示： 开发时指向源码让修改即时生效，publishConfig 在发布时覆盖 exports，指向构建产物。这是 Monorepo 中非常实用的模式。






根目录配置文件
根目录是 Monorepo 的"控制中心"，承载全局配置和任务编排：


{
  "name": "my-monorepo",
  "private": true,
  "packageManager": "pnpm@9.15.0",
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev --parallel",
    "test": "turbo run test",
    "typecheck": "turbo run typecheck",
    "lint": "turbo run lint",
    "clean": "turbo run clean && rm -rf node_modules",
    "format": "prettier --write \"**/*.{ts,tsx,md,json}\""
  },
  "devDependencies": {
    "prettier": "^3.4.0",
    "turbo": "^2.4.0"
  }
}


小结
    

  • Monorepo 的标准分层为 apps（可部署应用）、packages（共享库）和 tooling（工程配置）
    • 

  • 依赖方向必须从上层流向下层：apps → packages → tooling，禁止反向依赖
    • 

  • 包命名使用 npm scope + kebab-case，目录名与包名后缀保持一致
    • 

  • exports 字段是现代包入口的标准，应替代传统的 main 字段
    • 

  • 开发模式下包可以直接指向源码，通过 publishConfig 在发布时切换到构建产物
    •
