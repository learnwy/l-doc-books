反馈与同行评审

核心概念

给同事提供反馈（feedback）和进行同行评审（peer review）是技术团队中最需要英文写作技巧的场景之一。反馈的核心挑战是如何在 honest（诚实）和 kind（善意）之间取得平衡——既要指出真正的问题，又要维护良好的工作关系。

反馈可以分为三种类型，每种有不同的写作策略：

核心哲学是 Praise in public, correct in private — 公开表扬，私下纠正。


代码审查中的反馈表达
代码审查（code review）是开发者最频繁给出反馈的场景。好的审查评论应该清晰、可行动、且不带攻击性。


使用分级标签标注反馈的重要性：


    

  • [Blocking] — 必须修改才能合并
    • 

  • [Suggestion] — 建议修改，但不阻塞合并
    • 

  • [Nit] — 极小的风格问题，可改可不改
    • 

  • [Question] — 不确定是否有问题，想了解原因
    • 

  • [Praise] — 做得好的地方
    • 



使用标签的审查示例：




[Blocking] This query doesn't use parameterized inputs, which exposes us to SQL injection. Please use prepared statements instead.


[Suggestion] Consider extracting this logic into a separate function — it would improve testability and reusability.


[Nit] The variable name d could be more descriptive. Maybe durationMs or delayInMilliseconds?


[Question] I'm curious about the choice to use Map here instead of a plain object. Was there a specific performance reason?


[Praise] Great error handling here! The fallback chain with clear error messages will make debugging much easier.




审查评论的语言技巧：






攻击性表达
建设性替代





This is wrong.
I think there might be an issue here.




Why did you do it this way?
I'm curious about the reasoning behind this approach.




This doesn't make sense.
Could you help me understand the intent here?




You should use X instead.
Have you considered using X? It might [benefit].




This is too complex.
I wonder if we could simplify this by [suggestion].





关键原则是将 you 句式转换为 we 或 I 句式——You should fix this 变为 We should fix this 或 I'd suggest fixing this。


正面反馈的 SBI 框架
正面反馈（positive feedback）的价值常被低估。具体的正面反馈比模糊的称赞更有激励效果。推荐使用 SBI 框架：Situation（情境）、Behavior（行为）、Impact（影响）。


模糊的正面反馈：




Great job on the project!




具体的 SBI 正面反馈：




I wanted to highlight your work on the API migration last week (Situation). You proactively identified the security vulnerability before it reached production and immediately drafted a fix with comprehensive tests (Behavior). This saved us from a potential security incident that could have affected 15,000+ users and delayed our launch by weeks (Impact). Thank you for the thoroughness and urgency.




更多 SBI 正面反馈示例：




During yesterday's incident response (S), you took charge of communication — keeping stakeholders updated every 30 minutes with clear, concise status reports (B). This prevented panic and allowed the leadership team to make informed decisions about customer communication (I).






In your PR for the caching layer (S), you included a detailed design rationale, performance benchmarks, and edge case tests (B). This made the review process incredibly efficient — I was able to approve in one pass instead of the usual 2-3 rounds (I).




在代码审查中，不要吝啬正面反馈。当你看到好的代码时，留下 [Praise] 评论：




[Praise] Really clean abstraction here. The strategy pattern makes it easy to add new authentication providers without touching the core logic.






[Praise] Excellent test coverage — especially the edge cases for concurrent token refresh. This is exactly the kind of defensive testing we need.




建设性反馈的 COIN 模型
建设性反馈（constructive feedback）是最难写的，因为需要同时做到诚实和善意。推荐使用 COIN 模型：Context（背景）、Observation（观察）、Impact（影响）、Next step（下一步）。




Context: In the last two sprint demos...


Observation: I've noticed that the demo slides were prepared at the last minute, with some screenshots still showing the dev environment instead of staging.


Impact: This made it harder for stakeholders to evaluate the feature's readiness, and we received follow-up questions that could have been avoided with more polished materials.


Next step: Would it help to set a "demo prep" slot on Thursday afternoons? I'm happy to review your slides before the Friday demo.




COIN 模型的关键在于 Observation 使用客观描述，而非评判。对比：






评判性语言
客观描述





You're always late with the demos.
In the last two sprints, the demo slides were completed on the day of the demo.




Your code is messy.
I've noticed the function exceeds 200 lines and handles multiple concerns.




You don't test enough.
The last three PRs had test coverage below our 80% threshold.




You're not a team player.
In the past month, I've noticed the knowledge sharing sessions were declined.





Next step 中提供帮助而非命令。Would it help if... 和 I'm happy to... 比 You should... 和 You need to... 更容易被接受。


Peer Review 文档的写作
正式的同行评审文档（peer review document）通常在绩效评估周期中使用。这类文档需要平衡全面性和具体性。


Peer review 的标准结构：




Peer Review for [Name] — Q1 2024
Strengths
[Name] consistently demonstrates strong technical ownership. During the v3.0 migration, they identified and resolved a critical security vulnerability that could have delayed the launch by weeks. Their proactive approach to testing — especially the comprehensive edge case coverage — has significantly reduced our regression bug count.


They are also an excellent communicator. Their PR descriptions are among the most thorough on the team, often including design rationale, risk assessments, and rollback plans that make code review efficient and educational.


Areas for Growth
I'd encourage [Name] to invest more in mentoring junior developers. They have deep knowledge that the team would benefit from, particularly in systems design and performance optimization. Pairing sessions or tech talks would be valuable.


Additionally, while their individual output is excellent, there are opportunities to improve cross-team collaboration. During the API redesign, several decisions were made without consulting the frontend team, leading to rework.


Overall
[Name] is a strong senior engineer who consistently delivers high-quality work. With more investment in mentoring and cross-team alignment, they would be well-positioned for a staff engineer role.




关键写作原则：


    

  • Strengths 用 SBI 框架提供具体的例子
    • 

  • Areas for Growth 用 I'd encourage... 和 There are opportunities to... 而非 They need to...
    • 

  • 避免使用 but 连接正面和负面反馈（这会削弱正面部分的效果）
    • 

  • 整体评价要指向未来发展方向
    • 



接收反馈的英文表达
给反馈重要，接收反馈同样需要技巧。优雅地接收反馈能建立信任，鼓励团队成员继续给你诚实的反馈。


收到正面反馈时：




Thank you for the kind words! I really enjoyed working on the caching layer. The edge cases were tricky, but the test suite gave me confidence in the solution.




收到建设性反馈时：




Thank you for bringing this up — I appreciate the honest feedback. You're right that the demo prep could be more thorough. I'll start blocking Thursday afternoons for that.




收到你不完全同意的反馈时：




I appreciate you sharing this perspective. I'd like to think about it and maybe discuss further. Could we set up a quick chat next week to dig deeper into [specific point]?




需要时间消化的反馈：




Thanks for the feedback. This is helpful — I'd like some time to reflect on it. Can I follow up with you later this week with my thoughts?

核心原则是永远以 Thank you 开头——即使你不同意反馈内容，也要感谢对方愿意花时间给你反馈的行为。


小结
    

  • 代码审查使用 [Blocking]、[Suggestion]、[Nit]、[Question]、[Praise] 分级标签
    • 

  • 将 You should... 转换为 We could... 或 Have you considered...
    • 

  • 正面反馈使用 SBI 框架（Situation、Behavior、Impact），避免模糊称赞
    • 

  • 建设性反馈使用 COIN 模型（Context、Observation、Impact、Next step）
    • 

  • 观察用客观描述而非评判，Next step 提供帮助而非命令
    • 

  • Peer review 中用 I'd encourage... 和 There are opportunities to... 表达改进建议
    • 

  • 遵循 Praise in public, correct in private 原则
    •
