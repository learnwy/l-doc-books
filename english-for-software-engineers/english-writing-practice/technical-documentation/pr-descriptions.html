PR 描述写作

核心概念

Pull Request（PR）描述是代码审查流程中最重要的书面沟通。一份好的 PR 描述能让审查者在 2 分钟内理解变更的目的、范围和影响，从而提供更有针对性的反馈。反之，一份空白或模糊的 PR 描述会导致审查效率低下、遗漏关键问题。

PR 描述与其他技术文档的区别在于它同时服务于"现在"和"未来"：

核心原则是：Write for the reviewer who has no context — 假设审查者对你过去一周的工作一无所知。


PR 描述的 WHAT-WHY-HOW 结构
一份完整的 PR 描述应包含三大板块：


What（做了什么） — 用 2-3 句话概述变更内容：




This PR adds OAuth 2.0 PKCE flow support to the authentication module, replacing the previous implicit grant flow.




Why（为什么） — 解释变更的动机和背景：




The implicit grant flow is deprecated in OAuth 2.1 and poses security risks for public clients. Two of our enterprise customers (Acme Corp, TechGlobal) have specifically requested PKCE support as part of their security compliance requirements.




How（怎么做的） — 描述实现策略的关键决策：




The implementation follows a three-part approach:


    

  1. Added a PKCE code verifier/challenge generator in auth/pkce.ts
    2. 

  2. Modified the OAuth redirect flow to include the code challenge
    3. 

  3. Updated the token exchange endpoint to validate the code verifier
    4. 



Key design decision: We chose SHA-256 for the code challenge method (S256) rather than plain, as S256 is required by most identity providers and provides better security.




一个完整的 PR 描述模板：

变更范围说明与文件导览
对于大型 PR（超过 10 个文件变更），提供 file-by-file guide 可以大幅提升审查效率。


变更范围声明：




Scope
This PR touches 15 files across 3 packages:


    

  • @auth/core — New PKCE logic (4 files, ~200 lines added)
    • 

  • @auth/client — OAuth redirect flow changes (3 files, ~80 lines modified)
    • 

  • @auth/server — Token validation updates (2 files, ~60 lines modified)
    • 

  • Tests — 6 new test files (~400 lines)
    •

通过提供审查顺序建议（Start reviewing from），你帮助审查者建立了正确的心智模型，使他们在看到后续文件时已经理解了核心逻辑。


PR 中的风险评估与回滚计划
成熟的 PR 描述应包含 risk assessment 和 rollback plan，这在高影响变更中尤为重要。


风险评估模板：

Rollback Plan
If issues are detected post-deployment:


    

  1. Disable ENABLE_PKCE feature flag (instant, no deploy needed)
    2. 

  2. If flag doesn't resolve: Revert this PR via git revert
    3. 

  3. Estimated rollback time: < 5 minutes
    4. 





回滚计划中的关键要素：


    

  • 立即行动 — 最快的止血方案（通常是 feature flag）
    • 

  • 完全回滚 — 如何恢复到变更前的状态
    • 

  • 时间估计 — 回滚操作需要多长时间
    • 

  • 数据影响 — 回滚是否会导致数据丢失或不一致
    • 



对于数据库迁移类的 PR，还需要说明 forward-only 还是 reversible：




⚠️ Migration Note: This includes a database migration that adds a pkce_challenge column to the oauth_sessions table. The migration is reversible — the down migration drops the column. No data loss on rollback.




审查反馈的回应规范
PR 描述不仅包括初始描述，还包括对审查反馈的回应。回应审查意见时的英文规范同样重要。


常用回应模式：


接受建议：




Good catch! Fixed in the latest commit (abc1234).






Great suggestion. I've refactored this section as you recommended.




部分接受：




I agree with the general direction. I've applied this to the validate() function but kept the current approach for parse() because [reason].




礼貌地拒绝：




Thanks for the suggestion! I considered this approach, but opted for the current implementation because [specific technical reason]. Happy to discuss further if you feel strongly about it.




请求澄清：




Could you elaborate on what you mean by "tighter coupling"? I want to make sure I understand the concern before making changes.




标注已解决：




Addressed in commit abc1234. Moved the validation logic into a separate middleware as suggested.

小结
    

  • PR 描述使用 What-Why-How 三板块结构，假设审查者零上下文
    • 

  • 大型 PR 提供 File Guide 和审查顺序建议，降低审查认知负担
    • 

  • 包含 Risk Assessment 表格，量化风险的可能性和影响
    • 

  • 提供明确的 Rollback Plan，包含 feature flag 和时间估计
    • 

  • 回应审查意见时用 Good catch!、Great suggestion 开头表示感谢
    • 

  • 拒绝建议时用 I considered this, but... 句式，附带技术原因
    • 

  • 每次修改后标注 Addressed in commit [hash] 帮助审查者追踪
    •
