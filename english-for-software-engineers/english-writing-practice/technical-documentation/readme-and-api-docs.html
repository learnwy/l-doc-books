README 与 API 文档

核心概念

README 和 API 文档是开源项目和技术产品的"门面"。README 是用户接触项目的第一个文件，决定了他们是否愿意继续深入；API 文档则是开发者集成产品时的核心参考。两者都需要用清晰、准确的英文写作，因为技术文档的读者通常来自全球各地。

README 和 API 文档在目标和写法上有本质区别：

API 文档

无论是 README 还是 API 文档，核心原则是 Don't make me think — 让读者用最少的认知负担获取所需信息。


README 的黄金结构
一个优秀的 README 遵循 HIQSA 结构：Hook（钩子）、Installation（安装）、Quick Start（快速开始）、Sections（详细章节）、Appendix（附录）。


Hook — 项目名称 + 一句话描述 + 徽章：




🚀 FastCache
A blazing-fast, zero-dependency in-memory cache for Node.js with TTL support and LRU eviction.


  




一句话描述应遵循 What it is + Key differentiator + Target platform 的公式。避免空泛的描述如 A useful library for caching。


Installation — 提供所有主流包管理器的安装命令：




Installation
npm install fastcache
# or
yarn add fastcache
# or
pnpm add fastcache


Quick Start — 用最少的代码展示核心功能，让读者在 30 秒内看到效果：




Quick Start
import { createCache } from 'fastcache';

const cache = createCache({ ttl: 60_000 });
cache.set('user:1', { name: 'Alice' });
console.log(cache.get('user:1')); // { name: 'Alice' }


Quick Start 代码应该是可以直接复制粘贴运行的，不需要额外配置。


Sections — 根据项目复杂度，可以包含 API Reference、Configuration、Contributing 等章节。


Appendix — License、Changelog 链接、致谢等。

关键写作原则：


    

  • 每个端点的描述用一句话概括，以动词开头：Creates...、Retrieves...、Deletes...
    • 

  • 参数表格必须标注 Required 还是 Optional
    • 

  • 所有示例使用真实数据格式，不要用 foo、bar 等占位符
    • 

  • 错误码使用 SCREAMING_SNAKE_CASE，并提供人类可读的描述
    • 



技术写作的语态与时态
技术文档中的语态选择直接影响可读性和专业度。核心规则是：


**使用主动语态（active voice）**描述操作和指令：




The function returns a promise that resolves with the user object.




而非被动语态：




A promise that resolves with the user object is returned by the function.




**使用祈使语气（imperative mood）**写操作步骤：




Install the package using npm. Configure the database connection. Run the migration script.




而非：




You should install the package using npm. The database connection should be configured.




时态规则：






场景
时态
示例





描述功能行为
一般现在时
The cache expires entries after the TTL.




操作指令
祈使语气
Set the TTL value in milliseconds.




版本变更说明
一般过去时
Added support for Redis backend.




已知问题
一般现在时
The library does not support clustering.




计划特性
一般将来时
Future releases will include sharding support.





避免使用 simply、just、obviously、easily 等词——对新手来说，这些词暗示"如果你觉得难，那是你的问题"，会产生不必要的挫败感。


文档版本控制与维护
技术文档的一大痛点是与代码不同步。解决这个问题需要建立文档维护的流程和规范。


文档版本控制的最佳实践：


在 README 中明确标注文档对应的版本：




This documentation is for FastCache v2.x. For v1.x docs, see v1 branch.




API 文档中使用版本前缀：




API Reference (v2)
Base URL: https://api.example.com/v2




当 API 发生 breaking change 时，在文档中使用明确的 deprecation notice：




⚠️ Deprecated: The GET /users/:id/profile endpoint is deprecated and will be removed in v3. Use GET /users/:id instead, which now includes profile data in the response.




文档维护的 checklist：


    

  • 每次 PR 如果涉及公开 API 变更，必须同时更新对应文档
    • 

  • README 的 Quick Start 代码每季度验证一次是否仍可运行
    • 

  • 定期检查文档中的外部链接是否失效
    • 

  • 新增的配置项必须在 Configuration 章节中记录
    • 



为文档建立 freshness indicator：




Last updated: March 15, 2024 | Applies to: v2.3.0+




这让读者能快速判断文档的时效性。过时的文档比没有文档更危险——它会导致开发者基于错误的信息进行集成。


小结
    

  • README 使用 HIQSA 结构：Hook、Installation、Quick Start、Sections、Appendix
    • 

  • 一句话描述遵循 What + Differentiator + Platform 公式
    • 

  • API 端点描述包含：方法路径、描述、参数、请求体、响应、错误码
    • 

  • 使用主动语态和祈使语气，避免被动和 you should 句式
    • 

  • 避免 simply、just、obviously 等贬低读者难度感知的词
    • 

  • 文档标注版本号和最后更新日期，建立 freshness indicator
    • 

  • breaking change 必须使用 deprecation notice 提前告知
    • 

  • 每次涉及公开 API 的 PR 必须同步更新文档
    •
