变更日志与发布说明

核心概念

变更日志（Changelog）和发布说明（Release Notes）是软件发布流程中面向不同受众的两种关键文档。Changelog 面向开发者，记录每次变更的技术细节；Release Notes 面向最终用户或产品经理，聚焦于功能价值和用户影响。两者相互补充，但写法截然不同。

Changelog 和 Release Notes 的核心差异：






维度
Changelog
Release Notes





受众
开发者、集成方
最终用户、产品经理




视角
技术实现
用户价值




粒度
每次提交/PR
每个功能/修复




格式
结构化列表
叙述性段落 + 列表




语气
客观、简洁
积极、价值导向




示例
fix(auth): handle token expiry race
Fixed an issue where users were unexpectedly logged out





核心原则是：Changelog speaks to the code, Release Notes speak to the human。


Keep a Changelog 格式
Keep a Changelog 是业界最广泛采用的 Changelog 格式标准。其核心规则包括：


    

  • 每个版本一个章节，按时间倒序排列
    • 

  • 使用语义化版本号（SemVer）
    • 

  • 变更按类型分组
    • 



标准分组类型：


    

  • Added — 新增功能
    • 

  • Changed — 对已有功能的变更
    • 

  • Deprecated — 即将移除的功能
    • 

  • Removed — 已移除的功能
    • 

  • Fixed — Bug 修复
    • 

  • Security — 安全相关修复
    • 



完整的 Changelog 条目示例：


## [2.3.0] - 2024-03-15

### Added

- OAuth 2.0 PKCE flow support for public clients (#4521)
- Rate limiting configuration via environment variables (#4530)
- Health check endpoint at `/api/health` (#4535)

### Changed

- Upgraded Redis client from v3 to v4, improving connection pooling (#4528)
- Default session TTL changed from 24h to 12h for security (#4533)

### Deprecated

- `GET /api/v1/users/:id/profile` — use `GET /api/v2/users/:id` instead (#4525)

### Fixed

- Token refresh race condition causing intermittent 401 errors (#4521)
- Memory leak in WebSocket connection handler (#4527)
- Incorrect timezone handling in scheduled task runner (#4531)

### Security

- Patched XSS vulnerability in markdown renderer (CVE-2024-1234)
每条变更遵循 What changed + Where + Issue reference 的模式。使用过去时态（Added、Fixed）因为描述的是已完成的变更。


Release Notes 的用户视角写作
Release Notes 需要将技术变更翻译为用户能理解的语言。关键是从 what we built 转换到 what you can do now。


技术视角 vs 用户视角：






Changelog（技术）
Release Notes（用户）





Added OAuth 2.0 PKCE flow support
You can now sign in more securely using modern authentication standards




Fixed memory leak in WebSocket handler
Resolved an issue that could cause the app to slow down during long sessions




Changed default session TTL from 24h to 12h
For improved security, sessions now expire after 12 hours of inactivity




Upgraded Redis client to v4
（不写入 Release Notes — 对用户不可见）





Release Notes 的标准结构：




Release Notes — v2.3.0 (March 15, 2024)
🎉 What's New
Secure Sign-In with PKCE
We've upgraded our authentication system to support the latest OAuth 2.0 PKCE standard. This provides stronger security for browser-based applications by preventing authorization code interception attacks. No action is needed on your part — the upgrade is automatic.


Flexible Rate Limiting
You can now configure rate limits via environment variables, giving you fine-grained control over API usage without code changes.


🐛 Bug Fixes
    

  • Fixed an issue where users were unexpectedly logged out during peak traffic periods
    • 

  • Resolved a memory issue that could cause performance degradation in long-running sessions
    • 

  • Fixed incorrect scheduling times for users in non-UTC timezones
    • 



⚠️ Important Changes
    

  • Session duration reduced: For improved security, sessions now expire after 12 hours of inactivity (previously 24 hours). You can customize this via the SESSION_TTL environment variable.
    • 



🔒 Security
    

  • Addressed a cross-site scripting (XSS) vulnerability in the content renderer. We recommend all users upgrade to this version.
    • 



📋 Migration Guide
No breaking changes in this release. If you're using the deprecated /api/v1/users/:id/profile endpoint, please migrate to /api/v2/users/:id before v3.0 (estimated Q3 2024).




注意几个关键写作技巧：


    

  • 使用 emoji 作为视觉锚点（🎉、🐛、⚠️、🔒）
    • 

  • 新功能用 2-3 句话描述价值，而非实现细节
    • 

  • Bug 修复用用户能感知的症状描述，而非技术原因
    • 

  • 重要变更（breaking changes）用 ⚠️ 标记并说明迁移步骤
    • 



Breaking Change 的沟通策略
Breaking change 是 Release Notes 中最敏感的部分。处理不当可能导致用户升级失败、集成中断甚至客户流失。


Breaking change 的沟通遵循 DAWN 框架：Description（描述）、Alternative（替代方案）、Window（过渡期）、Next steps（下一步）。




⚠️ Breaking Changes
Authentication API Endpoint Changes
Description: The /api/v1/auth/token endpoint has been removed. All authentication requests must now use /api/v2/auth/token.


Alternative: The v2 endpoint accepts the same request format with one addition — a client_id parameter is now required.


Migration window: The v1 endpoint was deprecated in v2.1.0 (January 2024) and is removed in this release. If you're still using v1, please migrate immediately.


Next steps:


    

  1. Update your API calls to use /api/v2/auth/token
    2. 

  2. Add the client_id parameter to your token requests
    3. 

  3. Test the updated flow in your staging environment
    4. 



Code example:


// Before (v1 — removed)
const token = await fetch('/api/v1/auth/token', {
  method: 'POST',
  body: JSON.stringify({ username, password }),
});

// After (v2 — current)
const token = await fetch('/api/v2/auth/token', {
  method: 'POST',
  body: JSON.stringify({ username, password, client_id: 'your-client-id' }),
});


提供 before/after 代码示例是 breaking change 沟通中最有效的方式——开发者可以直接对照修改，无需阅读大段文字。


自动化与手写的平衡
现代工程团队通常使用工具（如 conventional-changelog、semantic-release、changesets）自动生成 Changelog。但自动生成的内容往往需要人工润色。


自动生成的 Changelog 通常存在以下问题：


    

  • 直接使用 commit message，粒度过细
    • 

  • 缺少上下文和关联信息
    • 

  • 格式不一致（取决于每个开发者的提交习惯）
    • 

  • 重复条目（一个功能可能有多次提交）
    • 



推荐的工作流是 auto-generate then curate：


    

  1. 使用工具从 commit history 自动生成初始 Changelog
    2. 

  2. 手动合并相关条目（如将 5 个 commit 合并为 1 个功能描述）
    3. 

  3. 补充缺失的上下文和影响说明
    4. 

  4. 调整措辞确保一致性
    5. 

  5. 单独撰写面向用户的 Release Notes
    6.

对于 Release Notes，始终需要人工撰写。因为 Release Notes 的核心价值在于将技术变更翻译为用户价值，这需要对产品和用户的理解，无法通过 commit message 自动推导。


发布说明的语气应积极且自信：




We're excited to announce v2.3.0, bringing enhanced security, better performance, and more flexibility to your workflow.




而非：




This release contains some fixes and changes.




小结
    

  • Changelog 使用 Keep a Changelog 格式，按 Added/Changed/Deprecated/Removed/Fixed/Security 分组
    • 

  • 每条变更遵循 What + Where + Issue ref 模式，使用过去时态
    • 

  • Release Notes 从用户视角写作，将技术变更翻译为 what you can do now
    • 

  • Breaking change 使用 DAWN 框架并提供 before/after 代码示例
    • 

  • 采用 auto-generate then curate 工作流平衡效率与质量
    • 

  • Release Notes 始终手动撰写，语气积极且价值导向
    • 

  • 安全修复必须在 Changelog 和 Release Notes 中同时说明
    •
