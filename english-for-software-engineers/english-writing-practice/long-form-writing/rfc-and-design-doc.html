RFC 与设计文档

核心概念

RFC（Request for Comments）和设计文档（Design Document）是技术团队中最重要的决策文档。RFC 提出一个技术提案并邀请反馈，设计文档则详细记录经过讨论后确定的技术方案。两者共同构成了技术决策的书面记录，确保决策过程透明、可追溯。

RFC 和设计文档在项目生命周期中的角色不同：

讨论期后归档
持续参考直到项目完成





核心原则是 Write to think, not to impress — RFC 是思考的工具，不是炫技的场所。一份好的 RFC 帮助团队做出更好的决策。


RFC 的标准结构
一份完整的 RFC 通常包含以下部分：




RFC: Event-Driven Notification System
Author: Alex Chen Status: Under Review Created: 2024-03-01 Last Updated: 2024-03-10 Reviewers: David Kim, Sarah Lee, Tom Zhang




Summary（摘要）— 一段话概述提案：




This RFC proposes replacing our current polling-based notification system with an event-driven architecture using Redis Pub/Sub and WebSocket. The goal is to reduce notification delivery latency from 30 seconds (current polling interval) to under 1 second, while supporting 10K+ concurrent connections per server instance.




Motivation（动机）— 为什么需要这个变更：




Our current polling-based notification system has three critical issues:


    

  1. High latency: Users experience up to 30 seconds delay between event occurrence and notification delivery
    2. 

  2. Wasteful resources: 95% of poll requests return empty, consuming unnecessary API bandwidth and database queries
    3. 

  3. Poor scalability: Each active user generates 2 requests/minute, creating unsustainable load as we grow toward 1M DAU
    4. 





Proposal（提案）— 技术方案的详细描述：




We propose a three-component architecture:


    

  1. Event Producer: Application services emit events to a Redis Pub/Sub channel when state changes occur
    2. 

  2. Notification Gateway: A dedicated WebSocket server subscribes to Redis channels and pushes events to connected clients
    3. 

  3. Fallback Poller: A reduced-frequency polling mechanism (5-minute interval) for clients that don't support WebSocket
    4.

写作技巧与评审引导
RFC 和设计文档的写作技巧在于如何引导评审者关注正确的问题。


明确提出需要反馈的领域：




Open Questions
I'd specifically appreciate feedback on:


    

  1. Message ordering: Is eventually-consistent ordering acceptable, or do we need strict per-user ordering?
    2. 

  2. Scaling strategy: Should we shard by user ID or by notification channel?
    3. 

  3. Migration path: Is a gradual rollout (10% → 50% → 100%) sufficient, or do we need a parallel run period?
    4. 





使用 I propose 而非 We should — RFC 是提议而非命令：




I propose we use Redis Pub/Sub for the initial implementation, with the option to migrate to Kafka if our event volume exceeds 100K/minute.




而非：




We should use Redis Pub/Sub.




预判反对意见并提前回应：




Some might argue that building a custom notification system is unnecessary when managed services like Firebase exist. While Firebase is excellent for smaller scale, our projections show it would cost 15K/monthat1MDAU,comparedtoapproximately15K/month at 1M DAU, compared to approximately15K/monthat1MDAU,comparedtoapproximately2K/month for a self-hosted solution. Additionally, self-hosting gives us full control over data residency requirements for our EU customers.

RFC 生命周期管理
RFC 不是写完就结束的——它有完整的生命周期，需要持续管理。


RFC 的状态流转：


在 RFC 讨论期，作者应该：


    

  • 在 72 小时内回应每条评审意见
    • 

  • 将重大的评审反馈整合到 RFC 中（标注 Updated based on feedback from [Name]）
    • 

  • 如果收到冲突的反馈，组织一次同步讨论会而非在文档中无限来回
    • 



RFC 被接受后，在文档顶部标注：




Status: ✅ Accepted (2024-03-15) Decision: Proceed with hybrid approach (Redis Pub/Sub + WebSocket + fallback poller) Implementation tracking: JIRA Epic PLAT-500




RFC 被拒绝后，记录拒绝原因：




Status: ❌ Rejected (2024-03-15) Reason: Team consensus that the current polling system is adequate for our scale. Will revisit when DAU exceeds 500K.




被拒绝的 RFC 同样有价值——它记录了团队曾经考虑过什么以及为什么决定不做，防止未来重复讨论同样的问题。


小结
    

  • RFC 使用 Summary → Motivation → Proposal → Alternatives Considered 结构
    • 

  • 设计文档在 RFC 接受后补充 API 设计、数据模型和故障模式分析
    • 

  • 用 I propose... 而非 We should...，保持提议语气
    • 

  • 明确标注 Open Questions 引导评审者关注关键决策点
    • 

  • 预判反对意见并用数据提前回应
    • 

  • RFC 有完整的生命周期：Draft → Under Review → Accepted/Rejected
    • 

  • 被拒绝的 RFC 同样有档案价值，记录拒绝原因防止重复讨论
    • 

  • 72 小时内回应评审意见，冲突反馈转为同步讨论
    •
