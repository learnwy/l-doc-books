类与模块命名体系

类命名的英语原则

类名代表一种抽象概念或实体类型，因此必须使用名词或名词短语。与函数命名侧重动词不同，类命名的核心在于选择准确的名词来表达"这是什么"。

基本规则

所有主流语言中，类名统一使用 PascalCase（每个单词首字母大写）：

// Good — 清晰的名词短语
class UserRepository {}
class PaymentProcessor {}
class EmailValidator {}
class HttpClient {}
class DatabaseConnection {}

// Bad — 含糊或错误的命名
class Manager {} // 太泛化，管理什么？
class Helper {} // 辅助什么？
class Util {} // 工具类应拆分为具体功能
class Data {} // 什么数据？
class DoPayment {} // 类名不应是动词短语

单一职责的命名体现

类名应当精准体现其职责范围。当一个类名需要用 "And" 连接两个概念时，通常意味着该类违反了单一职责原则：

// Bad — 暗示职责过多
class UserAuthenticationAndProfileManagement {}
class OrderCreationAndNotification {}

// Good — 拆分为单一职责
class UserAuthenticator {}
class UserProfileService {}
class OrderFactory {}
class OrderNotifier {}

常见类名后缀词汇表

后缀 含义 示例
Service 执行业务逻辑 PaymentService, NotificationService
Repository 数据持久化访问 UserRepository, OrderRepository
Controller 处理 HTTP 请求 AuthController, ProductController
Factory 创建对象实例 ConnectionFactory, WidgetFactory
Builder 分步构建复杂对象 QueryBuilder, ConfigBuilder
Handler 处理特定事件/请求 ErrorHandler, RequestHandler
Validator 验证数据合法性 EmailValidator, SchemaValidator
Adapter 接口适配转换 LegacyApiAdapter, StorageAdapter
Provider 提供依赖/数据 ConfigProvider, AuthProvider
Manager 管理生命周期/资源 CacheManager, ConnectionManager
Middleware 请求处理中间层 AuthMiddleware, LoggingMiddleware
Strategy 可替换算法 PricingStrategy, SortStrategy
Observer 监听事件变化 StockObserver, FileWatcher
Decorator 动态增强功能 LoggingDecorator, CacheDecorator

接口与抽象类命名

不同语言社区对接口命名有不同的传统约定，理解这些差异有助于在跨语言项目中写出符合规范的代码。

各语言接口命名传统

TypeScript / JavaScript——不加前缀，直接使用名词：

// TypeScript 官方推荐：不用 I 前缀
interface UserRepository {
  findById(id: string): Promise<User>;
  save(user: User): Promise<void>;
}

interface Serializable {
  serialize(): string;
}

// 实现类可加具体实现描述
class PostgresUserRepository implements UserRepository {}
class MongoUserRepository implements UserRepository {}

C# / .NET——使用 I 前缀的传统：

// C# 社区约定：接口以 I 开头
interface IUserRepository {
    User FindById(string id);
    void Save(User user);
}

interface ISerializable {
    string Serialize();
}

class SqlUserRepository : IUserRepository {}

Java——接口不加前缀，实现类加后缀：

// Java 社区约定
interface UserRepository {
    User findById(String id);
    void save(User user);
}

// 实现类命名方式
class JdbcUserRepository implements UserRepository {}
class InMemoryUserRepository implements UserRepository {}
class DefaultUserRepository implements UserRepository {}

抽象类命名

抽象类通常使用 Abstract 或 Base 前缀来表明其不可实例化的特性：

abstract class AbstractShape {
  abstract calculateArea(): number;
}

abstract class BaseController {
  protected handleError(err: Error): void {}
}

// 也可以不加前缀，通过类型系统表达
abstract class Shape {
  abstract area(): number;
}

class Circle extends Shape {}
class Rectangle extends Shape {}

形容词式接口（能力接口）

当接口描述一种"能力"而非"身份"时，使用 -able / -ible 后缀：

interface Comparable<T> {
  compareTo(other: T): number;
}

interface Iterable<T> {
  [Symbol.iterator](): Iterator<T>;
}

interface Disposable {
  dispose(): void;
}

interface Cacheable {
  getCacheKey(): string;
  getCacheTTL(): number;
}

模块与包的命名策略

模块和包的命名处于更高的抽象层级，需要传达组织架构和功能划分的信息。

npm 包命名规范

npm 生态使用 kebab-case（短横线连接的全小写）：

@company/auth-service        # 作用域包
react-query                  # 库名
express-rate-limiter         # 功能描述
next-auth                    # 框架 + 功能

命名要点：

  • 全小写字母，单词用短横线分隔
  • 避免在包名中使用 js 后缀（已经在 npm 生态中，无需说明）
  • 使用组织作用域 @org/ 避免命名冲突
  • 包名应体现功能而非实现

项目目录结构命名

src/
├── components/        # 复数：包含多个组件
├── hooks/            # 复数：包含多个 hooks
├── services/         # 复数：包含多个 service
├── utils/            # 复数：包含多个工具函数
├── types/            # 复数：包含多个类型定义
├── middleware/       # 不可数：中间件层（概念）
├── config/           # 不可数：配置（概念）
├── lib/              # 缩写：库代码
└── __tests__/        # 约定：测试目录

Go 包命名规范

Go 语言对包名有严格的简洁性要求：

// Good — 简短、小写、单个单词
package http
package json
package fmt
package auth
package user

// Bad
package httpUtils       // 不用驼峰
package http_utils      // 不用下划线
package userManagement  // 太长，应拆分

// 使用方式决定包名：包名.函数名 应当自然可读
http.Get()             // 读作 "http get"
json.Marshal()         // 读作 "json marshal"
auth.Verify()          // 读作 "auth verify"

Python 模块命名

# 模块名：snake_case，简短
import user_service
import data_processor
import email_validator

# 包名：全小写，最好单个单词
import requests
import flask
import numpy

泛型与类型参数命名

泛型类型参数的命名有一套独特的单字母约定系统：

参数 含义 使用场景
T Type — 通用类型 Array<T>, Promise<T>
K Key — 键类型 Map<K, V>, Record<K, V>
V Value — 值类型 Map<K, V>
E Element — 元素类型 List<E>, Set<E>
R Return — 返回类型 Function<T, R>
P Props — 属性类型 React 组件 Component<P>
S State — 状态类型 Component<P, S>

当类型含义复杂时，使用描述性名称替代单字母：

// 简单场景：单字母
function identity<T>(arg: T): T {
  return arg;
}

// 复杂场景：描述性名称
interface Repository<Entity, PrimaryKey> {
  findById(id: PrimaryKey): Promise<Entity>;
  save(entity: Entity): Promise<Entity>;
}

// React 组件
interface TableProps<RowData extends Record<string, unknown>> {
  data: RowData[];
  columns: Column<RowData>[];
}

枚举与常量命名

枚举命名

枚举类型名使用 PascalCase 单数形式，枚举值根据语言生态有不同约定：

// TypeScript — 值使用 PascalCase
enum HttpStatus {
  Ok = 200,
  Created = 201,
  BadRequest = 400,
  NotFound = 404,
  InternalServerError = 500,
}

enum UserRole {
  Admin = 'ADMIN',
  Editor = 'EDITOR',
  Viewer = 'VIEWER',
}

// 使用时读起来像自然语言
if (response.status === HttpStatus.NotFound) {
}
if (user.role === UserRole.Admin) {
}
# Python — 类名 PascalCase，值 SCREAMING_SNAKE_CASE
class HttpStatus(Enum):
    OK = 200
    CREATED = 201
    BAD_REQUEST = 400
    NOT_FOUND = 404
    INTERNAL_SERVER_ERROR = 500

常量命名原则

// 配置常量 — SCREAMING_SNAKE_CASE
const MAX_RETRY_COUNT = 3;
const DEFAULT_TIMEOUT_MS = 5000;
const API_VERSION = 'v2';

// 导出常量对象 — 对象名 PascalCase，属性 camelCase
export const AppConfig = {
  apiBaseUrl: 'https://api.example.com',
  maxUploadSize: 10 * 1024 * 1024,
  supportedLocales: ['en', 'zh', 'ja'],
} as const;

类名和模块名是代码架构的外在表达。精准的命名不仅让代码可读性提升，还能在重构和架构讨论中帮助团队达成共识——当大家对 "Repository"、"Service"、"Factory" 有统一认知时，沟通效率会大幅提高。

AI 时代的类与模块命名

类名 / 模块名的 AI 友好性集中在一致性 + 可定位性两点（变量级 AI 命名约定见 01_variable-function-naming.md 同名小节）：

  • 同一抽象层用同一后缀——Repository 用了就别夹 Store；Service 用了就别夹 Handler。LLM 在长上下文里依赖后缀建立心智图，混用会让生成代码也混用
  • 模块命名带"职责动词"提示——auth/ 比 utils/ 对 LLM 更友好；后者是无义垃圾桶，LLM 生成的代码很容易往里塞错东西
  • 避免顶层 index.ts 单独承担命名——当 LLM 看到 import { x } from './foo' 时无法判断 x 来自 foo 模块的哪个具体文件；显式路径 import { x } from './foo/user-repository' 让 LLM 改代码时更稳

反模式提醒：AI 生成的类常出现 XxxHelper / XxxUtil / XxxManager 三种"无义后缀"——LLM 偏爱它们因为它们出现在大量训练语料里。Review 时把这三种后缀当作"重新命名信号"。
