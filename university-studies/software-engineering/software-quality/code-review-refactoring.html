大学软件工程 — 代码审查与重构

知识要点

代码审查（Code Review）和重构（Refactoring）是提升软件内部质量的两大核心实践。代码审查通过人工检查发现代码中的缺陷、设计问题和风格不一致；重构则通过系统化地改善代码结构在不改变外部行为的前提下提升可读性和可维护性。

Martin Fowler 对重构的经典定义是："在不改变软件可观察行为的前提下，改善其内部结构。"重构不是重写，也不是修复 bug——它是对已有代码的结构性改善。代码审查则是一种社会化的质量保障手段，研究表明代码审查能发现 60-90% 的缺陷，且发现缺陷的成本远低于测试。

实践 目标 时机 参与者 成本-收益比
代码审查 发现缺陷、知识传播、保持一致性 代码合并前 作者 + 审查者 高（低成本发现大量问题）
重构 降低复杂度、消除重复、提升可读性 持续进行（TDD 红-绿-重构） 开发者 中长期收益显著
静态分析 自动检测代码缺陷和风格问题 每次提交时（CI 集成） 工具自动执行 高（零边际人力成本）

详细讲解

代码审查的模式与流程

代码审查有多种组织形式，从最正式到最轻量：

正式审查（Formal Inspection）：由 Michael Fagan 于 1976 年在 IBM 提出。包含六个阶段：计划、概览、准备、审查会议、返工、跟踪。Fagan 审查以高缺陷发现率著称，但流程重量级，现代开发中较少使用。

走查（Walkthrough）：代码作者向团队逐行讲解代码，与会者提出问题和建议。比正式审查更灵活，但依赖作者的引导，可能遗漏作者自己未注意到的问题。

轻量级审查（Lightweight Review）：现代开发中最主流的形式，通常通过 Pull Request（PR）或 Merge Request（MR）进行异步审查。审查者在代码变更上直接添加评论，作者响应后修改并再次提交。

高效代码审查的关键原则：

  • 小批量审查：每次审查的代码量控制在 200-400 行。研究表明，超过 400 行时缺陷发现率急剧下降
  • 明确审查清单：关注点包括逻辑正确性、边界条件、错误处理、安全漏洞、性能问题和代码风格
  • 保持建设性：审查是对代码的评价，不是对人的评价。使用"我们"而非"你"，提出建议而非指责
  • 时效性：审查响应时间不应超过一个工作日，避免成为开发流程的瓶颈

代码审查的缺陷发现效率可以量化。设审查花费的总人时为 TTT，发现的缺陷数为 DDD，则审查效率为：

Ereview=DT(缺陷/人时)E_{\text{review}} = \frac{D}{T} \quad (\text{缺陷/人时})Ereview​=TD​(缺陷/人时)

行业基准值约为 0.5∼1.50.5 \sim 1.50.5∼1.5 缺陷/人时。

代码异味与重构目录

代码异味（Code Smell）是 Martin Fowler 提出的概念，指代码中暗示更深层设计问题的表面征兆。代码异味本身不是 bug，但它们会降低代码的可理解性和可修改性。

常见代码异味及其对应重构手法：

代码异味 表现 推荐重构手法
过长方法（Long Method） 方法超过 20-30 行 提取方法（Extract Method）
过大类（Large Class） 类承担过多职责 提取类（Extract Class）
重复代码（Duplicated Code） 相似逻辑出现在多处 提取方法 / 提取超类
过长参数列表 方法有 4 个以上参数 引入参数对象（Introduce Parameter Object）
散弹式修改（Shotgun Surgery） 一个变更需要修改多个类 搬移方法 / 搬移字段
依恋情结（Feature Envy） 方法大量访问其他类的数据 搬移方法（Move Method）
数据泥团（Data Clumps） 多处出现相同的字段组合 提取类
基本类型偏执（Primitive Obsession） 用基本类型代替有意义的对象 以对象取代数据值

核心重构手法详解

提取方法（Extract Method）是使用频率最高的重构手法。当一段代码可以被提取为一个有意义名称的独立方法时，就应该提取。提取后的方法名起到了文档化的作用，使调用者无需阅读实现即可理解意图。

操作步骤：

  1. 识别可以提取的代码块
  2. 创建新方法并赋予意图明确的名称
  3. 将代码块移到新方法中
  4. 识别原代码块中的局部变量，作为参数传入或返回值传出
  5. 在原位置替换为方法调用
  6. 运行测试确保行为不变

搬移方法（Move Method）将方法从一个类移到另一个更合适的类。判断标准是方法应该在其最多使用的数据所在的类中。如果方法 mmm 访问类 AAA 的 aaa 个字段和类 BBB 的 bbb 个字段，且 b>ab > ab>a，则 mmm 可能应该搬移到类 BBB。

以多态取代条件（Replace Conditional with Polymorphism）将复杂的 if-else 或 switch-case 链替换为多态调用。这是开放-封闭原则的直接体现——新增分支不需要修改现有代码，只需添加新的子类。

重构的安全网：自动化测试

重构的最大风险是无意中改变了程序行为。自动化测试是重构的安全网——每次重构操作后运行测试套件，确保所有测试仍然通过。

重构的安全实践：

  1. 确保有足够的测试覆盖率再开始重构
  2. 每次只做一个小的重构步骤
  3. 每步之后立即运行测试
  4. 如果测试失败，立即回退到上一步
  5. 使用版本控制，每个逻辑完整的重构步骤做一次提交

技术债务的量化与管理

Ward Cunningham 提出的技术债务（Technical Debt）隐喻，将短期的设计妥协类比为金融债务——当前节省了时间（借入本金），但未来需要付出额外维护成本（利息）。

技术债务可以从代码复杂度指标中间接量化。常用的复杂度指标：

  • 圈复杂度（Cyclomatic Complexity）：V(G)=e−n+2V(G) = e - n + 2V(G)=e−n+2，衡量控制流复杂度
  • 认知复杂度（Cognitive Complexity）：SonarSource 提出，更贴近人类理解难度
  • 代码重复率：重复代码行数占总行数的比例

SonarQube 等工具将技术债务转换为修复时间——例如"技术债务 = 120 人时"，便于向管理层沟通。如果系统的技术债务增长速率为 rrr（人时/Sprint），而每个 Sprint 分配给重构的时间为 fff（人时），则技术债务的可持续条件为：

f≥rf \geq rf≥r

即每个 Sprint 的还债速率至少要等于新增债务的速率，否则系统将不可逆地退化。

练习与思考

  1. 以下代码存在哪些代码异味？请列出至少 3 种，并给出重构建议：

    function processOrder(name, email, street, city, zip, items, discount, tax) {
    if (items.length > 0) {
        let total = 0;
        for (let i = 0; i < items.length; i++) {
            total += items[i].price * items[i].quantity;
        }
        total = total * (1 - discount) * (1 + tax);
        // send email
        const msg = "Dear " + name + ", your order total is $" + total;
        sendEmail(email, msg);
        // save to db
        db.save({name, email, street, city, zip, total, items});
    }
}

  2. 你的团队决定对一个没有任何测试的遗留系统进行重构。在添加测试之前就开始重构是否合理？如果不合理，如何在没有测试的情况下安全地为遗留代码添加测试？

  3. 代码审查中，高级工程师对新人的代码提出了 30 条评论，其中 25 条是代码风格问题（变量命名、空格等）。这种审查方式有什么问题？如何改进？

  4. 某团队的代码库有 15% 的代码重复率，圈复杂度中位数为 12，有 200 个类超过 500 行。请制定一个为期 3 个月的技术债务治理计划，包括优先级排序和度量目标。

拓展阅读

  • Fowler, M. (2018). "Refactoring: Improving the Design of Existing Code" (2nd Edition)：重构领域的圣经，第二版使用 JavaScript 示例，更贴近现代实践。
  • Feathers, M. (2004). "Working Effectively with Legacy Code"：如何在缺乏测试的遗留系统上安全地进行修改和重构。
  • Kerievsky, J. (2004). "Refactoring to Patterns"：将重构与设计模式结合，展示如何通过渐进式重构引入设计模式。
  • Cohen, J. (2006). "Best Kept Secrets of Peer Code Review"：基于 Cisco 大规模代码审查数据的实证研究，提供量化的审查最佳实践。

小结

代码审查和重构是软件工程中"慢就是快"的典型实践。代码审查通过团队的集体智慧提前拦截缺陷、传播知识、维护代码一致性；重构通过持续改善代码结构来控制技术债务的增长。两者结合，形成了一个正向循环：审查发现异味，重构消除异味，测试保障重构的安全性。在日常开发中，将代码审查作为代码合并的必经环节，将重构作为每次开发的自然组成部分，是构建可持续演化的软件系统的关键。
