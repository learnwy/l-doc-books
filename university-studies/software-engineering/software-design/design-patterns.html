大学软件工程 — 设计模式

知识要点

设计模式（Design Patterns）是软件设计中针对反复出现的问题而总结出的可复用解决方案。1994 年，Erich Gamma 等四位作者（被称为"Gang of Four"，简称 GoF）出版了《设计模式：可复用面向对象软件的基础》，系统归纳了 23 种经典设计模式，奠定了设计模式领域的基石。

设计模式不是可以直接拷贝到代码中的模板，而是对特定设计问题的抽象描述。每个模式包含四个要素：模式名称、问题描述、解决方案和效果评价。设计模式的价值在于它为开发者提供了一套通用的设计词汇，使得团队沟通更加高效。

模式类别 目的 代表模式 解决的核心问题
创建型（Creational） 对象创建机制 工厂方法、抽象工厂、单例、建造者、原型 将对象创建与使用解耦
结构型（Structural） 类和对象的组合方式 适配器、装饰器、代理、外观、组合、桥接、享元 灵活的结构组合
行为型（Behavioral） 对象间的职责分配和通信 策略、观察者、命令、模板方法、迭代器、状态、中介者 算法和职责的灵活分配

详细讲解

创建型模式：控制对象的诞生

工厂方法模式（Factory Method）定义一个创建对象的接口，但将实际实例化过程延迟到子类。当系统需要创建的对象类型可能变化时，工厂方法允许在不修改客户端代码的前提下引入新的产品类型。

// 伪代码：工厂方法
interface Logger { void log(String msg); }
class FileLogger implements Logger { ... }
class ConsoleLogger implements Logger { ... }

abstract class LoggerFactory {
    abstract Logger createLogger();  // 工厂方法
    void writeLog(String msg) {
        Logger logger = createLogger();
        logger.log(msg);
    }
}

单例模式（Singleton）确保一个类只有一个实例，并提供全局访问点。典型应用场景包括配置管理器、连接池和日志系统。但单例模式也带来全局状态和测试困难的问题，现代实践中更推荐通过依赖注入框架管理对象生命周期。

建造者模式（Builder）将复杂对象的构建过程与其表示分离。当对象的构造需要多个步骤，或同一构建过程需要产生不同的表示时，建造者模式特别适用。

结构型模式：灵活的组合艺术

适配器模式（Adapter）将一个类的接口转换成客户期望的另一个接口，使原本因接口不兼容而无法协作的类能够一起工作。适配器有两种实现方式：类适配器（通过继承）和对象适配器（通过组合）。

装饰器模式（Decorator）动态地为对象添加职责，作为子类化的一种替代方案。装饰器的核心思想是组合优于继承。例如 Java I/O 库中，BufferedInputStream 装饰 FileInputStream，DataInputStream 装饰 BufferedInputStream，形成灵活的功能叠加。

装饰器链的行为可以形式化描述。假设原始对象的行为为 f(x)f(x)f(x)，装饰器 D1,D2,…,DnD_1, D_2, \ldots, D_nD1​,D2​,…,Dn​ 依次添加额外行为 g1,g2,…,gng_1, g_2, \ldots, g_ng1​,g2​,…,gn​，则装饰后的最终行为为：

F(x)=gn∘gn−1∘⋯∘g1∘f(x)F(x) = g_n \circ g_{n-1} \circ \cdots \circ g_1 \circ f(x)F(x)=gn​∘gn−1​∘⋯∘g1​∘f(x)

代理模式（Proxy）为另一个对象提供一个替身或占位符以控制对它的访问。常见的代理类型包括：

  • 远程代理：为远程对象提供本地代表（如 RPC stub）
  • 虚拟代理：延迟创建开销大的对象（如懒加载图片）
  • 保护代理：控制对原始对象的访问权限

行为型模式：优雅的职责分配

策略模式（Strategy）定义一系列算法，将每个算法封装起来，使它们可以互换。策略模式让算法的变化独立于使用它的客户端。经典应用：排序算法的动态切换、支付方式选择、压缩算法选择。

观察者模式（Observer）定义对象之间的一对多依赖关系：当一个对象（Subject）的状态发生改变时，所有依赖它的对象（Observer）都会被自动通知。这是事件驱动架构的基础。

假设一个 Subject 有 nnn 个 Observer，每次状态变更的通知时间复杂度为 O(n)O(n)O(n)。在极端情况下，如果 Observer 的回调触发了其他 Subject 的状态变更（级联通知），复杂度可能升为 O(n2)O(n^2)O(n2) 甚至更高，需要警惕通知风暴。

命令模式（Command）将请求封装为对象，从而支持请求的排队、日志记录、撤销/重做等功能。命令模式将"发出请求的对象"与"执行请求的对象"解耦。

设计模式的组合与演进

实际项目中，设计模式很少单独使用。例如：

  • MVC 架构 = 观察者 + 策略 + 组合模式的综合运用
  • 抽象工厂 + 单例：全局唯一的工厂实例
  • 代理 + 装饰器：在访问控制的同时增强功能

GoF 提出的 23 种模式并非终极清单。随着软件技术演化，新的模式不断涌现：

  • 依赖注入（Dependency Injection）：控制反转的一种实现
  • 仓储模式（Repository）：领域驱动设计中的数据访问抽象
  • 事件溯源（Event Sourcing）：将状态变更记录为事件序列

SOLID 原则与设计模式的关系

设计模式的合理运用离不开面向对象设计原则（SOLID）的指导：

原则 全称 核心思想 关联模式
S 单一职责原则 一个类只有一个变化的理由 策略、命令
O 开放-封闭原则 对扩展开放，对修改封闭 装饰器、策略
L 里氏替换原则 子类必须能替换其基类 工厂方法、模板方法
I 接口隔离原则 不应强迫客户依赖不需要的接口 适配器、外观
D 依赖倒置原则 依赖抽象而非具体实现 抽象工厂、桥接

练习与思考

  1. 某电商系统需要支持多种支付方式（微信支付、支付宝、信用卡），且未来可能新增其他支付方式。请分析应使用哪种设计模式，并画出类图或伪代码。

  2. 装饰器模式和继承都可以扩展对象功能。请从灵活性、组合爆炸和运行时动态性三个角度比较二者的优劣。

  3. 单例模式在多线程环境下的实现需要特别注意。请分析"双重检查锁"（Double-Checked Locking）的实现原理以及它在 Java 和 C++ 中的陷阱。

  4. 选择一个你熟悉的开源框架（如 Spring、React 或 Django），找出其中至少 3 种设计模式的应用实例，并说明为什么在该场景中使用该模式是合理的。

  5. "过度设计"（Over-Engineering）是设计模式使用中的常见陷阱。请举一个具体的例子说明何时引入设计模式反而增加了系统的复杂性。

拓展阅读

  • Gamma, E. et al. (1994). "Design Patterns: Elements of Reusable Object-Oriented Software"：GoF 经典原著，设计模式的圣经。
  • Freeman, E. & Robson, E. (2020). "Head First Design Patterns" (2nd Edition)：以直观易懂的方式讲解设计模式，适合初学者。
  • Martin, R.C. (2017). "Clean Architecture"：从架构层面讨论设计原则和模式的应用。
  • Refactoring.Guru 网站（refactoring.guru/design-patterns）：提供精美的图解和多语言代码示例。

小结

设计模式是前人在大量实践中提炼出的设计智慧结晶。学习设计模式的目标不是机械地套用 23 种模板，而是理解每种模式背后的设计原则——封装变化、面向接口、组合优于继承。在实际开发中，应根据具体问题的复杂度和变化可能性来决定是否引入模式，避免为了模式而模式。设计模式的真正价值在于提升代码的可维护性、可扩展性和团队沟通效率。
