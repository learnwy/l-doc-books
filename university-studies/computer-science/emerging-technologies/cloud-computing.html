大学计算机科学与技术 — 云计算

知识要点

云计算是通过互联网按需交付计算资源（服务器、存储、数据库、网络、软件）的模式，用户无需拥有和维护物理基础设施，只需为实际使用的资源付费。这一模式从根本上改变了软件的构建、部署和运营方式——从购买服务器到"租用"算力，从手动运维到自动化弹性伸缩。对计算机科学学习者而言，理解云计算意味着理解分布式系统如何在全球规模上工程化落地。

云计算的三大服务模型定义了不同的抽象层次，每一层封装了更多的基础设施管理责任：

服务模型 全称 用户管理 提供商管理 典型产品
IaaS Infrastructure as a Service 应用、数据、运行时、OS 虚拟化、服务器、存储、网络 AWS EC2, Azure VM
PaaS Platform as a Service 应用、数据 运行时、中间件、OS、基础设施 Heroku, Google App Engine
SaaS Software as a Service 无（仅使用） 全栈 Gmail, Salesforce, Office 365

详细讲解

虚拟化技术

虚拟化是云计算的基石技术，允许在一台物理机器上运行多个隔离的虚拟环境。

硬件虚拟化通过Hypervisor（虚拟机监控器）将物理硬件抽象为多个虚拟机（VM）。两种架构：

  • Type 1（裸机 Hypervisor）：直接运行在硬件上，如 VMware ESXi、KVM、Xen。性能开销低（<5%< 5\%<5%），适合生产环境。
  • Type 2（宿主 Hypervisor）：运行在操作系统上，如 VirtualBox、VMware Workstation。方便开发测试，性能开销较大。

容器化是比 VM 更轻量的虚拟化方案。Docker 容器共享宿主内核，通过 Linux namespace（隔离进程、网络、文件系统视图）和 cgroup（限制 CPU、内存、I/O 资源）实现隔离。容器的启动时间约 100  ms100\;\text{ms}100ms 量级，而 VM 通常需要 10-60  s10\text{-}60\;\text{s}10-60s。

维度 虚拟机 容器
隔离级别 硬件级（独立内核） 进程级（共享内核）
启动时间 秒级至分钟级 毫秒级至秒级
资源开销 高（每个 VM 运行完整 OS） 低（共享内核，仅运行进程）
镜像大小 GB 级 MB 级
安全隔离 强 较弱（内核共享带来攻击面）

容器编排与 Kubernetes

当应用由数十到数千个容器组成时，手动管理不可行。Kubernetes（K8s）是容器编排的事实标准，解决了容器的调度、网络、存储、自动伸缩和故障恢复等问题。

K8s 的核心抽象：

  • Pod：最小部署单元，包含一个或多个共享网络和存储的容器
  • Service：稳定的网络端点，为一组 Pod 提供负载均衡和服务发现
  • Deployment：声明式管理 Pod 的副本数和更新策略（滚动更新、金丝雀发布）
  • ConfigMap/Secret：将配置和敏感信息与容器镜像解耦

K8s 的调度器为每个待调度的 Pod 评估所有可用节点的资源余量、亲和性规则和拓扑约束，选择最佳节点。调度算法的目标是在满足约束条件下最大化资源利用率和分布均匀性。

自动水平伸缩（HPA, Horizontal Pod Autoscaler）根据 CPU/内存使用率或自定义指标动态调整 Pod 副本数。例如当平均 CPU 使用率超过 70%70\%70% 时增加副本，低于 30%30\%30% 时减少副本。

分布式存储与数据库

云环境下的数据持久化面临分布式系统的固有挑战。CAP 定理（Eric Brewer, 2000）指出分布式系统不可能同时满足以下三个属性：

  • 一致性（Consistency）：所有节点在同一时间看到相同的数据
  • 可用性（Availability）：每个请求都能收到非错误响应
  • 分区容错性（Partition Tolerance）：系统在网络分区时仍能运行

由于网络分区不可避免，实际系统必须在 C 和 A 之间取舍：

  • CP 系统：牺牲可用性保一致性，如 ZooKeeper、etcd
  • AP 系统：牺牲强一致性保可用性，如 Cassandra、DynamoDB（最终一致性）

对象存储（如 AWS S3）提供了几乎无限容量的扁平化存储，数据以对象（Key-Value + 元数据）形式组织。S3 的持久性设计目标为 99.999999999%99.999999999\%99.999999999%（11 个 9），通过跨多个可用区的冗余副本实现。

NewSQL 数据库（如 Google Spanner、CockroachDB）试图兼顾 SQL 的强一致事务和 NoSQL 的水平扩展能力。Spanner 使用 TrueTime API（基于原子钟和 GPS 的全球时间同步）实现外部一致性，将时钟不确定性区间 ϵ\epsilonϵ 控制在 <7  ms< 7\;\text{ms}<7ms。

无服务器计算

无服务器（Serverless）架构将基础设施管理完全抽象化，开发者只需编写处理单个事件的函数。FaaS（Function as a Service）是其核心模型——函数按调用次数和执行时间计费，空闲时不收费。

特性 传统服务器 无服务器
伸缩 手动或半自动 自动从 0 到 N
计费 按分配资源（即使空闲） 按实际执行时间
冷启动 无 首次调用有延迟（100  ms-10  s100\;\text{ms}\text{-}10\;\text{s}100ms-10s）
运行时长 无限制 通常限制（151515 分钟，AWS Lambda）

无服务器的冷启动是主要痛点：首次调用时需要分配容器、加载运行时和用户代码。优化策略包括预热（provisioned concurrency）、使用更轻量的运行时和减小部署包大小。

云原生架构模式

微服务架构将单体应用拆分为多个独立部署的服务，每个服务负责一个业务能力。优势是独立开发、独立部署、技术栈异构化，挑战是服务间通信、分布式事务和运维复杂度。

关键模式：

  • API 网关：统一入口，处理认证、限流、路由
  • 服务网格（Service Mesh, 如 Istio）：将服务间通信的可靠性、安全性和可观测性从业务代码中剥离到基础设施层（Sidecar 代理）
  • 事件驱动架构：服务通过消息队列（Kafka、RabbitMQ）异步通信，解耦生产者和消费者
  • GitOps：以 Git 仓库作为基础设施和应用配置的唯一事实来源，通过自动化工具同步到集群

练习与思考

  1. 一个电商网站在"双十一"期间的流量是平时的 505050 倍。比较以下三种方案的成本和响应时间特征：(a) 预先购买足以应对峰值的物理服务器；(b) 使用云 IaaS 的自动伸缩；(c) 使用无服务器架构。分析各方案在平时和峰值时的成本效率。

  2. 解释 CAP 定理为什么说"三者不可兼得"。给出一个具体场景：当两个数据中心之间的网络中断时，一个银行转账系统应该选择 CP 还是 AP？为什么？

  3. 一个容器化应用包含 Web 前端（3 副本）、API 服务（5 副本）和数据库（1 主 2 从）。绘制 Kubernetes 的资源拓扑图（Pod、Service、Deployment），并说明 Service 如何实现对 API 服务的负载均衡。

  4. 比较 Docker 容器和虚拟机在安全隔离方面的差异。如果一个容器中的进程利用内核漏洞实现了容器逃逸（Container Escape），会造成什么后果？列举两种增强容器安全性的技术。

  5. 无服务器函数的冷启动延迟在某些场景下不可接受（如实时交易系统）。提出两种缓解冷启动的技术方案，并分析其成本权衡。

拓展阅读

  • 《Designing Data-Intensive Applications》（Martin Kleppmann）：分布式系统和数据密集型应用设计的必读书籍，深入讲解一致性、复制、分区和事务。
  • 《Kubernetes in Action》（Marko Lukša）：从概念到实践的 K8s 全面指南，配套大量动手实验。
  • Google 论文三件套：GFS（2003）、MapReduce（2004）、Bigtable（2006）——云计算时代的奠基文献。
  • CNCF Landscape（landscape.cncf.io）：云原生技术全景图，涵盖容器运行时、编排、服务网格、可观测性等所有关键领域。

小结

云计算将计算资源转化为按需获取的公用事业，虚拟化和容器化技术是其核心支撑。IaaS/PaaS/SaaS 三层服务模型对应了不同的抽象粒度和管理责任划分。Kubernetes 解决了大规模容器编排的复杂性，CAP 定理揭示了分布式存储的固有取舍，无服务器架构将基础设施管理进一步抽象化。云原生架构模式——微服务、事件驱动、服务网格——正在重塑软件的构建方式。理解云计算不仅是掌握特定工具，更是建立对大规模分布式系统的工程直觉。
