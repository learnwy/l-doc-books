MLOps 与模型部署

知识要点

MLOps（Machine Learning Operations）是将 DevOps 的理念应用于机器学习生命周期的实践体系，目标是让 ML 模型从实验室的 Jupyter Notebook 可靠、可复现、可监控地运行在生产环境中。数据显示，大量 ML 项目止步于"实验成功"阶段而无法投产。MLOps 正是解决这一"最后一公里"问题的工程方法论。

生命周期阶段 关键活动 核心工具
数据准备 特征工程、数据验证 Feast, Great Expectations
模型开发 训练、超参搜索、评估 MLflow, W&B, Optuna
模型注册 版本管理、审批流程 MLflow Model Registry
模型部署 服务化、推理优化 TF Serving, Triton, BentoML
模型监控 性能追踪、漂移检测 Evidently, Prometheus

详细讲解

模型生命周期管理

ML 项目的生命周期远比传统软件复杂。除了代码版本外，还需要管理数据版本、模型版本、超参数配置和实验结果的版本——这被称为"ML 的四重版本控制"。

典型的 ML 开发循环是：准备数据 → 特征工程 → 模型训练 → 评估验证 → 部署上线 → 监控反馈 → 重新训练。这个循环不是一次性的，而是持续迭代的。当数据分布发生变化（Data Drift）或模型性能下降时，需要触发重训练管道。

实验追踪

实验追踪是 MLOps 的基础能力：记录每次训练的代码版本、数据版本、超参数和结果指标，使实验可复现、可比较。

MLflow 是最流行的开源实验追踪工具。核心组件包括 Tracking（记录参数、指标和产出物）、Projects（定义可复现的运行环境）、Models（标准化的模型打包格式）和 Model Registry（模型版本管理和阶段流转）。

Weights & Biases（W&B） 提供了更丰富的可视化和协作功能，支持实验对比、超参数搜索可视化和团队共享。

模型服务

将训练好的模型部署为可接受请求的服务是 MLOps 的关键环节。

TensorFlow Serving 是 TensorFlow 生态的模型服务框架，支持模型热更新（无需停机即可切换到新版本）、批量推理和 gRPC/REST 接口。

NVIDIA Triton 是多框架推理服务器，同时支持 TensorFlow、PyTorch、ONNX 等格式，支持动态批处理（将多个请求合并为一个 batch 以提高 GPU 利用率）和模型集成（多个模型串联组成推理管道）。

BentoML 提供了更简洁的模型打包和部署体验，用装饰器语法定义推理服务，一键打包为 Docker 镜像。

部署模式包括实时推理（REST/gRPC API，延迟要求毫秒级）、批量推理（定期对大量数据跑推理，如每日推荐列表更新）和流式推理（与消息队列结合，对实时数据流做推理）。

特征商店

特征商店（Feature Store）是管理和服务 ML 特征的基础设施，解决"训练-服务偏差"问题——确保训练时和在线推理时使用完全相同的特征计算逻辑。

Feast（Feature Store）是最流行的开源特征商店。核心功能包括特征注册（声明式定义特征及其数据源）、离线存储（用于训练，支持 BigQuery/Redshift/文件系统）、在线存储（用于实时推理，支持 Redis/DynamoDB）以及时间点查询（Point-in-time Join，确保训练数据不会使用"未来信息"造成数据泄漏）。

Tecton（Feast 的商业版）增加了实时特征计算、监控和团队协作功能。

模型监控与漂移检测

模型上线后不是一劳永逸的。真实世界的数据分布会随时间变化（Data Drift），导致模型性能逐渐下降。

监控的三个层次包括：基础设施监控（延迟、吞吐、错误率——与传统服务监控相同）、模型性能监控（准确率、AUC 等指标是否下降，需要有真实标签的反馈回路）以及数据漂移监控（输入特征的分布是否偏离了训练数据，常用统计检验如 KS 检验、PSI 指数）。

Evidently 是开源的 ML 监控工具，提供数据漂移报告、模型性能报告和目标漂移检测。漂移检测的典型工作流是：定期对比生产数据特征分布与训练数据基线，当偏离超过阈值时触发告警，评估是否需要重新训练。

A/B 测试与灰度发布

新模型上线前需要验证其在生产环境中的真实效果。

A/B 测试将用户随机分为两组，一组使用旧模型，一组使用新模型，对比业务指标（点击率、转化率、收入等）。需要注意的是，模型指标（如 AUC）提升不等于业务指标提升。

灰度发布（Canary Deployment）先将少量流量（如 5%）导向新模型，观察一段时间确认无异常后逐步扩大比例。这种方式降低了全量上线的风险。

影子模式（Shadow Mode）更保守：新模型在后台运行并记录预测结果，但不实际影响用户。通过离线比较新旧模型的预测差异来评估。

练习与思考

  1. 描述一个 ML 模型从"Jupyter Notebook 中训练完成"到"生产环境中服务用户请求"需要经过的所有步骤。每个步骤可能遇到什么问题？

  2. 比较 MLflow 和 W&B 在实验追踪方面的功能差异。对于一个 5 人的 ML 团队，你会推荐哪个？为什么？

  3. 设计一个推荐系统的漂移监控方案：你会监控哪些特征的分布变化？阈值如何设定？检测到漂移后的应对流程是什么？

  4. 你的电商推荐模型升级了算法。设计一个 A/B 测试方案来验证新模型效果，包括分流比例、运行时长、评估指标和统计方法。

小结

MLOps 是将 ML 模型从实验推向生产的工程体系。从实验追踪、模型服务到特征管理和漂移监控，每个环节都需要专门的工具和流程支撑。随着企业 ML 应用的成熟，MLOps 能力正在从"锦上添花"变为"必备基础"。下一步可以选择一个具体的 MLOps 工具栈（如 MLflow + Feast + Evidently）进行端到端的实践。
