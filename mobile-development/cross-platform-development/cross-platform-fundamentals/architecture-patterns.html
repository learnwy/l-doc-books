跨平台架构模式

核心概念

跨平台开发的核心挑战在于如何用一套代码覆盖多个目标平台，同时兼顾性能、开发效率和用户体验。经过十余年的演进，业界沉淀出四种主流架构模式：Web 容器模式、桥接模式、自渲染模式和编译转换模式。每种模式在底层实现机制、性能表现、开发体验和适用场景上各有侧重，架构选型直接决定了项目的技术上限和长期维护成本。

Web 容器模式
Web 容器模式是跨平台的最早实践者。其核心思想极为简单——在原生应用中嵌入一个 WebView，将 Web 页面作为应用的 UI 层。原生能力通过 JavaScript Bridge 暴露给 Web 侧。


Cordova 插件架构
import { Camera, CameraResultType } from '@capacitor/camera';

async function takePhoto() {
  const image = await Camera.getPhoto({
    quality: 90,
    allowEditing: true,
    resultType: CameraResultType.Uri,
  });
  return image.webPath;
}
import { Geolocation } from '@capacitor/geolocation';

async function getCurrentPosition() {
  const coordinates = await Geolocation.getCurrentPosition();
  return {
    lat: coordinates.coords.latitude,
    lng: coordinates.coords.longitude,
    accuracy: coordinates.coords.accuracy,
  };
}

桥接模式
桥接模式的核心在于 JS 线程和原生线程之间的通信机制。开发者用 JavaScript/TypeScript 编写业务逻辑和 UI 描述，框架将 UI 描述翻译为原生组件的创建/更新指令，通过桥接层传递到原生线程执行。


React Native 桥接通信（旧架构）
import { NativeModules, NativeEventEmitter } from 'react-native';

const { DeviceInfoModule } = NativeModules;

async function getBatteryLevel(): Promise<number> {
  const level = await DeviceInfoModule.getBatteryLevel();
  return level;
}

const eventEmitter = new NativeEventEmitter(DeviceInfoModule);

const subscription = eventEmitter.addListener('onBatteryLevelChange', (event: { level: number }) => {
  console.log(`Battery: ${event.level}%`);
});

#include <jsi/jsi.h>

using namespace facebook::jsi;

void installMathModule(Runtime& runtime) {
  auto multiply = Function::createFromHostFunction(
    runtime,
    PropNameID::forAscii(runtime, "multiply"),
    2,
    [](Runtime& rt, const Value&, const Value* args, size_t) -> Value {
      double a = args[0].asNumber();
      double b = args[1].asNumber();
      return Value(a * b);
    }

    runtime,
    "nativeMultiply",
    std::move(multiply)
  );
}

}

自渲染模式
自渲染模式绕过了平台原生组件，由框架自带的图形引擎直接在 Canvas/Surface 上绘制所有 UI 元素。Flutter 是此模式的标杆，其底层渲染引擎从 Skia 演进到 Impeller。


Flutter 自绘渲染
import 'package:flutter/material.dart';

class CustomPainterDemo extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return CustomPaint(
      size: const Size(300, 300),
      painter: ChartPainter(),
    );
  }
}

class ChartPainter extends CustomPainter {
  @override
  void paint(Canvas canvas, Size size) {
    final paint = Paint()
      ..color = Colors.blue
      ..strokeWidth = 2.0
      ..style = PaintingStyle.stroke;

    final path = Path();
    final points = [
      Offset(0, size.height * 0.8),
      Offset(size.width * 0.25, size.height * 0.4),
      Offset(size.width * 0.5, size.height * 0.6),
      Offset(size.width * 0.75, size.height * 0.2),
      Offset(size.width, size.height * 0.3),
    ];

    path.moveTo(points[0].dx, points[0].dy);
    for (var i = 1; i < points.length; i++) {
      path.lineTo(points[i].dx, points[i].dy);
    }
    canvas.drawPath(path, paint);

    final dotPaint = Paint()..color = Colors.red;
    for (final point in points) {
      canvas.drawCircle(point, 4, dotPaint);
    }
  }

  @override
  bool shouldRepaint(covariant CustomPainter oldDelegate) => false;
}

编译转换模式
编译转换模式将一种高级语言编译为各平台的原生代码或中间产物。Kotlin Multiplatform（KMP）是该模式的代表——共享的 Kotlin 代码被编译为 JVM 字节码（Android）、LLVM 原生代码（iOS）和 JavaScript（Web）。


Kotlin Multiplatform 示例
// commonMain - 共享业务逻辑
expect class PlatformInfo() {
    val name: String
    val version: String
}

class UserRepository(private val api: ApiClient) {
    suspend fun getUser(id: String): User {
        return api.get("/users/$id")
    }

    suspend fun updateProfile(user: User): Result<User> {
        return runCatching {
            api.put("/users/${user.id}", user)
        }
    }
}
// androidMain
actual class PlatformInfo actual constructor() {
    actual val name: String = "Android"
    actual val version: String = android.os.Build.VERSION.RELEASE
}
// iOS 侧调用 KMP 产物
import shared

let repo = UserRepository(api: ApiClient())
let user = try await repo.getUser(id: "123")
print(user.name)

混合架构实践
真实的大型应用往往不会只用一种模式。以字节跳动为例，抖音同时使用了 Lynx（桥接）渲染动态化页面、Flutter（自渲染）承载特定模块、WebView（Web 容器）加载运营活动页。混合架构的关键在于定义清晰的边界：


interface RouteConfig {
  path: string;
  type: 'native' | 'lynx' | 'webview' | 'flutter';
  module: string;
  fallback?: string;
  preload?: boolean;
}

const routes: RouteConfig[] = [
  { path: '/home', type: 'native', module: 'HomeModule' },
  { path: '/feed', type: 'lynx', module: 'feed_card', preload: true },
  { path: '/campaign/*', type: 'webview', module: 'https://m.example.com/campaign' },
  { path: '/editor', type: 'flutter', module: 'video_editor', fallback: '/editor-lite' },
];

function resolveRoute(path: string): RouteConfig | undefined {
  return routes.find((r) => {
    if (r.path.endsWith('*')) {
      return path.startsWith(r.path.slice(0, -1));
    }
    return r.path === path;
  });
}
小结
四种跨平台架构模式各有千秋：Web 容器模式开发最快但性能最弱；桥接模式在效率和性能间取得平衡；自渲染模式性能和一致性最优但学习成本较高；编译转换模式原生性能最佳但生态尚在成长。实际项目中，混合架构是大型应用的主流选择——不同场景选用最合适的模式，通过统一路由和容器管理实现协同。


核心要点回顾：


    

  • Web 容器模式适合内容展示和快速 MVP，性能天花板低
    • 

  • 桥接模式是移动端跨平台的主流选择，RN/Lynx 为代表
    • 

  • 自渲染模式提供最高的 UI 一致性，Flutter 为标杆
    • 

  • 编译转换模式共享业务逻辑效果最佳，KMP 增长迅猛
    • 

  • 大型应用普遍采用混合架构，按场景选择最优模式
    • 

  • 架构选型需综合考虑性能要求、团队技术栈、开发周期和目标平台
