可测试架构

可测试架构（Testable Architecture）是指从设计之初就考虑测试需求的架构风格。本文介绍依赖边界、纯函数、副作用隔离以及测试金字塔的实践方法。

可测试性的核心原则





原则
不可测试代码
可测试代码





依赖边界
直接实例化依赖
通过协议注入




纯函数
全局状态、单例
输入→输出，无副作用




副作用隔离
网络/存储散布各处
集中到 Effect/Service 层




依赖注入
在方法内部创建依赖
外部注入可替换依赖







依赖边界
通过协议在架构层之间建立清晰的测试边界：


protocol ArticleRepositoryProtocol {
    func fetchArticles() async throws -> [Article]
    func saveArticle(_ article: Article) async throws
}

protocol DateProviderProtocol {
    var now: Date { get }
}

struct SystemDateProvider: DateProviderProtocol {
    var now: Date { Date() }
}

struct FixedDateProvider: DateProviderProtocol {
    let fixedDate: Date
    var now: Date { fixedDate }
}
使用依赖边界使代码可测试：


final class ArticleListViewModel: ObservableObject {
    @Published var articles: [Article] = []
    @Published var lastRefreshed: String = ""

    private let repository: ArticleRepositoryProtocol
    private let dateProvider: DateProviderProtocol
    private let formatter: DateFormatter

    init(
        repository: ArticleRepositoryProtocol,
        dateProvider: DateProviderProtocol = SystemDateProvider()
    ) {
        self.repository = repository
        self.dateProvider = dateProvider
        self.formatter = DateFormatter()
        self.formatter.dateStyle = .medium
        self.formatter.timeStyle = .short
    }

    @MainActor
    func refresh() async {
        do {
            articles = try await repository.fetchArticles()
            lastRefreshed = formatter.string(from: dateProvider.now)
        } catch {
            // 错误处理
        }
    }
}


纯函数
纯函数只依赖输入参数，不访问外部状态，是最容易测试的代码：


struct PriceCalculator {
    func calculateTotal(items: [CartItem], discountCode: String?) -> PriceBreakdown {
        let subtotal = items.reduce(Decimal.zero) { $0 + $1.price * Decimal($1.quantity) }
        let discount = calculateDiscount(subtotal: subtotal, code: discountCode)
        let tax = (subtotal - discount) * Decimal(0.1)
        let total = subtotal - discount + tax

        return PriceBreakdown(
            subtotal: subtotal,
            discount: discount,
            tax: tax,
            total: total
        )
    }

    private func calculateDiscount(subtotal: Decimal, code: String?) -> Decimal {
        guard let code else { return .zero }

        switch code {
        case "SAVE10":
            return subtotal * Decimal(0.1)
        case "SAVE20":
            return subtotal * Decimal(0.2)
        case "FLAT50":
            return min(Decimal(50), subtotal)
        default:
            return .zero
        }
    }
}

struct PriceBreakdown {
    let subtotal: Decimal
    let discount: Decimal
    let tax: Decimal
    let total: Decimal
}
测试纯函数非常简单：


final class PriceCalculatorTests: XCTestCase {
    let calculator = PriceCalculator()

    func testCalculateTotalWithoutDiscount() {
        let items = [
            CartItem(name: "A", price: 100, quantity: 2),
            CartItem(name: "B", price: 50, quantity: 1)
        ]

        let result = calculator.calculateTotal(items: items, discountCode: nil)

        XCTAssertEqual(result.subtotal, 250)
        XCTAssertEqual(result.discount, 0)
        XCTAssertEqual(result.tax, 25)
        XCTAssertEqual(result.total, 275)
    }

    func testCalculateTotalWithPercentDiscount() {
        let items = [CartItem(name: "A", price: 100, quantity: 1)]

        let result = calculator.calculateTotal(items: items, discountCode: "SAVE10")

        XCTAssertEqual(result.discount, 10)
        XCTAssertEqual(result.total, 99)
    }
}


副作用隔离
将副作用集中到专门的层，核心逻辑保持纯净：


struct FormValidator {
    func validateEmail(_ email: String) -> ValidationResult {
        let regex = /^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$/
        if email.isEmpty {
            return .invalid("邮箱不能为空")
        }
        if email.wholeMatch(of: regex) == nil {
            return .invalid("邮箱格式不正确")
        }
        return .valid
    }

    func validatePassword(_ password: String) -> ValidationResult {
        if password.count < 8 {
            return .invalid("密码至少 8 个字符")
        }
        if !password.contains(where: \.isUppercase) {
            return .invalid("密码必须包含大写字母")
        }
        if !password.contains(where: \.isNumber) {
            return .invalid("密码必须包含数字")
        }
        return .valid
    }
}

enum ValidationResult: Equatable {
    case valid
    case invalid(String)
}

小结
    

  • 可测试架构从设计之初就通过协议边界、纯函数和副作用隔离保证可测试性
    • 

  • 依赖边界通过协议抽象实现，使得测试中可以注入 Mock 替代真实依赖
    • 

  • 纯函数是最容易测试的代码，业务计算和数据校验应尽量实现为纯函数
    • 

  • 副作用（网络、存储、推送）应集中在专门的层，便于 Mock 和隔离
    • 

  • 测试金字塔指导测试策略：大量单元测试 + 适量集成测试 + 少量 E2E 测试
    • 

  • MVVM、TCA、Clean Architecture 都是天然适合测试的架构模式
