启动指标体系与监控

知识要点

启动优化的成果需要通过可量化的指标体系来衡量，并依赖持续监控来守护。一个完善的启动指标体系需要回答三个问题：测什么（指标定义）、怎么测（采集方案）、怎么用（分析与告警）。业界通常采用多级时间戳模型，从进程创建到用户可交互划分多个关键节点，形成端到端的启动耗时全景图。

核心启动指标层次：

指标层级 名称 定义 价值
T0 进程创建时间 系统 fork 出进程的时刻 基线参考，不可优化
T1 Runtime 就绪 main 函数 / Application.onCreate 开始 pre-main 阶段度量
T2 首帧渲染完成 viewDidAppear / onWindowFocusChanged 视觉可见时间
T3 首屏数据就绪 首页列表/内容完全加载可交互 用户可用时间
T4 用户体感完成 首次滑动/点击响应正常 体验完整性

详细讲解

指标采集方案设计

T0 获取方式：


    

  • iOS：通过 sysctl 读取进程创建时间
    • 



func processStartTime() -> TimeInterval {
    var kinfo = kinfo_proc()
    var size = MemoryLayout<kinfo_proc>.stride
    var mib: [Int32] = [CTL_KERN, KERN_PROC, KERN_PROC_PID, getpid()]
    sysctl(&mib, 4, &kinfo, &size, nil, 0)
    let startTime = kinfo.kp_proc.p_starttime
    return TimeInterval(startTime.tv_sec) + TimeInterval(startTime.tv_usec) / 1_000_000
}
    

  • Android：通过 /proc/self/stat 读取进程 starttime 字段，或使用 Process.getStartElapsedRealtime()（API 24+）
    • 



T2 采集 — 首帧时间：


    

  • iOS：在首页 ViewController 的 viewDidAppear: 中打点
    • 

  • Android：Activity.reportFullyDrawn() 或注册 ViewTreeObserver.OnDrawListener 在首次 draw 回调中记录
    • 



T3 采集 — 数据就绪：


业务层在首页数据渲染完成后主动上报。需要区分「缓存命中」和「网络请求」两条路径的耗时差异。

分位值选择建议：


    

  • P50：代表大多数用户体验，作为日常看板核心指标
    • 

  • P90：代表较差体验用户，作为优化目标
    • 

  • P99：极端场景（低端机 + 弱网），用于发现系统性缺陷
    •

  1. 版本对比发现 P50 上涨 200ms
    2. 

  2. 按机型维度拆分：低端机上涨 500ms，高端机无变化

  3. 按阶段拆分：T1→T2 阶段上涨，定位到首帧渲染

    5. 

  5. 确认根因并推动修复

告警与防护机制
建立三级告警体系：


防护手段：


    

  • CI 卡口：每次 MR 合入前运行 Benchmark，超过阈值阻止合入
    • 

  • 灰度监控：新版本灰度期间对比启动指标，异常则暂停推量
    • 

  • 动态降级：当检测到启动超时，自动跳过非核心初始化
    •

    •

踩坑经验：


    

  • T0 在 iOS 上取 sysctl 有时与 mach_absolute_time 的基准不一致，需统一到同一时钟源
    • 

  • Android 低版本（< API 24）无法直接获取 getStartElapsedRealtime，需从 /proc 解析
    • 

  • 采样率设置过低会导致 P99 波动大，影响告警准确性
    • 



小结
启动指标体系是优化成果的「守护者」。核心要素包括：多级时间戳模型（T0-T4）提供全景视图、合理的采样与分位值策略保证数据质量、多维度拆分实现精准归因、三级告警加 CI 卡口构成自动化防护网。有了这套体系，启动优化就从「一次性运动」变为「可持续治理」。后续章节将介绍更多性能维度的监控方法，形成完整的 APM 能力。
