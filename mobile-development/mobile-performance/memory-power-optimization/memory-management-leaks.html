内存管理与泄漏检测

知识要点

内存是移动设备最稀缺的资源之一。iOS 没有传统的 swap 空间，系统内存压力大时会直接终止后台应用（Jetsam）；Android 虽有 Low Memory Killer，但频繁的 GC 停顿同样影响流畅度。内存泄漏会导致应用内存持续增长，最终触发 OOM（Out of Memory）崩溃或被系统强制回收。检测和治理内存泄漏是移动应用稳定性保障的基础工作。

移动端内存分类：

内存类型 说明 典型大小 优化方向
代码段 Mach-O / DEX 映射 30-100MB 代码瘦身、动态加载
堆内存 对象分配（malloc/new） 50-300MB 对象生命周期管理
图片缓存 解码后 Bitmap 50-200MB 降采样、缓存淘汰
栈内存 线程栈空间 每线程 512KB-1MB 控制线程数量
文件映射 mmap 映射区域 变动大 按需映射、及时释放

详细讲解

iOS 内存管理机制

iOS 使用 ARC（Automatic Reference Counting）管理堆内存。编译器在编译期自动插入 retain/release 调用，引用计数归零时立即释放对象。

MLeaksFinder 原理：


当 ViewController 执行 dismissViewControllerAnimated: 或从 NavigationController pop 时，MLeaksFinder 在 2 秒后检查该 VC 及其 View 树中的所有对象是否已释放。未释放的对象即为潜在泄漏：


// 简化原理
extension UIViewController {
    func willDealloc() {
        DispatchQueue.main.asyncAfter(deadline: .now() + 2.0) { [weak self] in
            if self != nil {
                // 2秒后仍存活 = 泄漏嫌疑
                assertionFailure("Memory Leak: \(type(of: self!))")
            }
        }
        // 递归检查子 View
        view.willDealloc()
    }
}
Android 内存管理机制
Android 使用 ART（Android Runtime）的分代 GC 管理 Java/Kotlin 堆内存。GC 暂停虽然在 ART 上已显著缩短（并发 GC），但仍可能造成帧丢失。


Android 特有内存问题：


    

  1. Activity 泄漏：最严重的泄漏类型。一个 Activity 泄漏意味着其 View 树、Drawable、Bitmap 全部无法释放，可达数十 MB。
    2. 

  2. Fragment 泄漏：Fragment 的 View 在 onDestroyView 后应释放，但 binding 引用未清理会导致泄漏。
    3. 

  3. 匿名内部类持有外部引用：Handler、Runnable、Listener 等匿名类隐式持有外部 Activity 引用。
    4.

大图与 Bitmap 内存治理
图片是移动端内存的最大消耗来源。一张 1080x1920 的 ARGB_8888 图片解码后占用：


M=W×H×B=1080×1920×4=8.29 MBM = W \times H \times B = 1080 \times 1920 \times 4 = 8.29 \text{ MB}M=W×H×B=1080×1920×4=8.29 MB
其中 WWW 为宽度像素、HHH 为高度像素、BBB 为每像素字节数。

内存水位监控与 OOM 防护
线上环境无法使用 Instruments/LeakCanary，需要轻量级的内存监控方案：


iOS 内存水位监控：


func currentMemoryUsage() -> UInt64 {
    var info = mach_task_basic_info()
    var count = mach_msg_type_number_t(MemoryLayout.size(ofValue: info) / MemoryLayout<integer_t>.size)
    let result = withUnsafeMutablePointer(to: &info) {
        $0.withMemoryRebound(to: integer_t.self, capacity: Int(count)) {
            task_info(mach_task_self_, task_flavor_t(MACH_TASK_BASIC_INFO), $0, &count)
        }
    }
    return result == KERN_SUCCESS ? info.resident_size : 0
}

实践案例
某直播 App 内存泄漏专项治理：


背景：线上 OOM 率持续升高，从 0.3% 涨至 0.8%，Crash 排名第一。


排查过程：


    

  1. 接入 OOMDetector，发现 OOM 前内存峰值集中在 1.8GB+
    2. 

  2. 分析内存分配 Top 10：直播间 View 层级占 400MB（异常）
    3. 

  3. 使用 MLeaksFinder 复现：进出直播间 3 次后发现 LiveRoomVC 未释放
    4. 

  4. Xcode Memory Graph 分析引用链：Timer → Block → self 循环引用

小结
内存管理的核心是「分配有度、释放及时、监控到位」。iOS 端重点治理循环引用（Block、Timer、delegate）和大图内存，Android 端重点关注 Activity/Fragment 泄漏和 GC 压力。线上监控需要建立内存水位告警和 OOM 归因体系。开发期使用 MLeaksFinder/LeakCanary 实现自动化检测，将泄漏拦截在上线之前。
