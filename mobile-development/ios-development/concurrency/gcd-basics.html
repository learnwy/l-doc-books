Part I · iOSiOS 开发 简介并发 简介GCD 基础

GCD 基础

概述

Grand Central Dispatch（GCD）是 Apple 提供的底层并发框架，基于 C 语言实现，通过**队列（DispatchQueue）**抽象来管理任务的并发执行。开发者只需将任务（闭包）提交到队列，GCD 自动管理线程池的创建、调度和销毁，无需手动管理线程生命周期。

GCD 是 iOS 并发编程的基石。虽然 Swift 5.5 引入了 async/await，但 GCD 仍广泛用于精确控制队列行为、与 Objective-C 代码交互、以及底层系统级并发场景。理解 GCD 的队列模型、同步/异步执行语义和 QoS 优先级机制，是掌握 iOS 并发编程的前提。

核心概念
队列类型
GCD 的核心抽象是 DispatchQueue——一个 FIFO 的任务队列。队列分为两种执行模式：






队列类型
行为
特点





串行队列（Serial）
任务按提交顺序逐一执行
天然线程安全，同一时间只有一个任务运行




并发队列（Concurrent）
任务按提交顺序开始，但可并行执行
多个任务同时运行，执行结束顺序不确定





let serialQueue = DispatchQueue(label: "com.app.serial")

let concurrentQueue = DispatchQueue(label: "com.app.concurrent", attributes: .concurrent)

let mainQueue = DispatchQueue.main

let globalQueue = DispatchQueue.global(qos: .userInitiated)
sync vs async
sync 和 async 控制的是调用者是否等待任务完成，而非任务在哪个线程执行：


let queue = DispatchQueue(label: "com.app.work")

queue.async {
    print("异步任务 - 不阻塞调用者")
    print("当前线程：\(Thread.current)")
}
print("async 调用后立即执行")

queue.sync {
    print("同步任务 - 阻塞调用者直到完成")
}
print("sync 任务完成后才执行")




方法
调用者行为
任务执行线程





async
不等待，立即返回
队列指定的线程




sync
阻塞等待任务完成才返回
可能在调用者线程执行（优化）





QoS（Quality of Service）
QoS 告诉系统任务的优先级，系统据此分配 CPU 资源和调度顺序：


let backgroundQueue = DispatchQueue.global(qos: .background)
let userQueue = DispatchQueue.global(qos: .userInitiated)
let utilityQueue = DispatchQueue.global(qos: .utility)

userQueue.async {
    print("高优先级：用户发起的操作")
}

utilityQueue.async {
    print("中优先级：长时间运算")
}

backgroundQueue.async {
    print("低优先级：预加载、清理")
}

DispatchGroup
DispatchGroup 用于追踪一组异步任务，在所有任务完成后收到通知：


let group = DispatchGroup()
let queue = DispatchQueue.global(qos: .userInitiated)
var results: [String] = []

group.enter()
queue.async {
    Thread.sleep(forTimeInterval: 1)
    results.append("用户信息")
    group.leave()
}

group.enter()
queue.async {
    Thread.sleep(forTimeInterval: 0.5)
    results.append("订单列表")
    group.leave()
}

group.enter()
queue.async {
    Thread.sleep(forTimeInterval: 0.8)
    results.append("推荐内容")
    group.leave()
}

group.notify(queue: .main) {
    print("全部加载完成：\(results)")
}
group.wait() 是同步等待版本，可指定超时时间：


let result = group.wait(timeout: .now() + 5)
switch result {
case .success:
    print("所有任务在超时前完成")
case .timedOut:
    print("超时，部分任务未完成")
}
DispatchSemaphore
信号量用于限制并发数量或实现资源互斥访问：


let semaphore = DispatchSemaphore(value: 3)
let queue = DispatchQueue.global(qos: .userInitiated)

for i in 1...10 {
    queue.async {
        semaphore.wait()
        print("任务 \(i) 开始 - \(Date())")
        Thread.sleep(forTimeInterval: 2)
        print("任务 \(i) 完成")
        semaphore.signal()
    }
}
value: 3 表示最多允许 3 个任务同时执行。wait() 将信号量减 1（为 0 时阻塞），signal() 将信号量加 1（唤醒等待者）。


DispatchWorkItem
DispatchWorkItem 封装了任务闭包，支持取消和依赖：


var workItem: DispatchWorkItem?

workItem = DispatchWorkItem {
    for i in 1...100 {
        guard !(workItem?.isCancelled ?? true) else {
            print("任务在第 \(i) 步被取消")
            return
        }
        print("处理第 \(i) 项")
    }
}

DispatchQueue.global().async(execute: workItem!)

DispatchQueue.main.asyncAfter(deadline: .now() + 0.01) {
    workItem?.cancel()
    print("已发送取消信号")
}
DispatchWorkItem 还可以设置完成回调：


let item = DispatchWorkItem {
    print("执行任务...")
}

item.notify(queue: .main) {
    print("任务完成，更新 UI")
}

DispatchQueue.global().async(execute: item)
Barrier
barrier 在并发队列中创建一个独占访问窗口——barrier 任务执行期间，队列中不会有其他任务并发执行。这是实现读写锁的经典模式：


class ThreadSafeCache<Key: Hashable, Value> {
    private var storage: [Key: Value] = [:]
    private let queue = DispatchQueue(label: "com.app.cache", attributes: .concurrent)

    func read(key: Key) -> Value? {
        queue.sync {
            storage[key]
        }
    }

    func write(key: Key, value: Value) {
        queue.async(flags: .barrier) {
            self.storage[key] = value
        }
    }
}
读操作可并发执行（sync），写操作使用 barrier 独占访问，确保数据一致性。


使用方式
模式一：主线程切换
从后台线程获取数据后，必须回到主线程更新 UI：


func loadUserProfile() {
    DispatchQueue.global(qos: .userInitiated).async {
        let profile = self.fetchProfileFromDisk()

        DispatchQueue.main.async {
            self.nameLabel.text = profile.name
            self.avatarView.image = profile.avatar
            self.activityIndicator.stopAnimating()
        }
    }
}
模式二：防抖（Debounce）
利用 DispatchWorkItem 实现搜索输入防抖：


class SearchController {
    private var pendingWorkItem: DispatchWorkItem?

    func textDidChange(_ text: String) {
        pendingWorkItem?.cancel()

        let workItem = DispatchWorkItem { [weak self] in
            self?.performSearch(query: text)
        }

        pendingWorkItem = workItem
        DispatchQueue.main.asyncAfter(deadline: .now() + 0.3, execute: workItem)
    }

    private func performSearch(query: String) {
        print("搜索：\(query)")
    }
}
模式三：并发下载 + 汇总
多个网络请求并发执行，全部完成后合并结果：


func loadDashboard(completion: @escaping (Dashboard) -> Void) {
    let group = DispatchGroup()
    let queue = DispatchQueue.global(qos: .userInitiated)

    var user: User?
    var orders: [Order] = []
    var notifications: [Notification] = []

    group.enter()
    queue.async {
        user = self.fetchUser()
        group.leave()
    }

    group.enter()
    queue.async {
        orders = self.fetchOrders()
        group.leave()
    }

    group.enter()
    queue.async {
        notifications = self.fetchNotifications()
        group.leave()
    }

    group.notify(queue: .main) {
        let dashboard = Dashboard(user: user!, orders: orders, notifications: notifications)
        completion(dashboard)
    }
}
常见陷阱
陷阱一：在主队列上调用 sync 导致死锁
在串行队列上同步派发任务到自身，会造成死锁——当前任务等待新任务完成，但新任务排在当前任务之后，永远无法开始：


DispatchQueue.main.sync {
    print("永远不会执行 ❌")
}
同样的问题也会发生在任何自定义串行队列上：


let serial = DispatchQueue(label: "com.app.serial")
serial.async {
    serial.sync {
        print("死锁 ❌")
    }
}
陷阱二：DispatchGroup 的 enter/leave 不匹配
enter() 和 leave() 必须严格配对。多一个 enter() 会导致 notify 永远不触发；多一个 leave() 会导致崩溃：


let group = DispatchGroup()

group.enter()
someAsyncWork { result in
    if let error = result.error {
        print("错误：\(error)")
        // ❌ 忘记调用 group.leave()，notify 永远不会触发
        return
    }
    group.leave()
}
正确写法——使用 defer 确保 leave() 总被调用：


group.enter()
someAsyncWork { result in
    defer { group.leave() }
    guard let data = result.data else { return }
    process(data)
}
陷阱三：在并发队列中不加保护地读写共享状态
多个线程同时读写同一个变量会导致数据竞争，产生不可预测的结果甚至崩溃：


var count = 0
let queue = DispatchQueue.global()

for _ in 0..<1000 {
    queue.async {
        count += 1  // ❌ 数据竞争
    }
}
应使用串行队列或 barrier 保护共享状态：


var count = 0
let isolation = DispatchQueue(label: "com.app.counter")

for _ in 0..<1000 {
    isolation.async {
        count += 1  // ✅ 串行队列保证互斥
    }
}
陷阱四：过度使用 DispatchQueue.global()
频繁向全局队列提交大量任务可能导致线程爆炸——GCD 线程池默认上限 64 个线程，超出后新任务会排队等待，整体吞吐量下降甚至卡顿：


for i in 0..<10000 {
    DispatchQueue.global().async {
        Thread.sleep(forTimeInterval: 1)  // ❌ 阻塞线程
        print("任务 \(i)")
    }
}
应使用信号量限制并发数，或使用自定义并发队列配合合理的任务粒度。


小结
    

  • DispatchQueue 是 GCD 的核心抽象，分为串行（逐一执行）和并发（可并行执行）两种模式。
    • 

  • Main Queue 是串行队列，绑定主线程，所有 UI 操作必须在此执行；Global Queue 是系统提供的共享并发队列。
    • 

  • sync 阻塞调用者等待任务完成，async 立即返回不等待。绝不要在串行队列上 sync 派发到自身。
    • 

  • QoS 分 5 个级别，从 .userInteractive（最高）到 .background（最低），系统据此分配调度优先级。
    • 

  • DispatchGroup 追踪一组异步任务的完成状态，enter/leave 必须严格配对，推荐使用 defer 保证。
    • 

  • DispatchSemaphore 限制并发数量，wait() 减信号量，signal() 加信号量。
    • 

  • DispatchWorkItem 支持取消和完成通知，适合防抖等需要取消前一次操作的场景。
    • 

  • Barrier 在并发队列中创建独占窗口，是实现读写锁的经典模式：读用 sync，写用 async(flags: .barrier)。
    • 

  • 共享可变状态必须通过串行队列或 barrier 保护，避免数据竞争。
    •
