内存管理

概述

Swift 使用自动引用计数（ARC, Automatic Reference Counting）管理引用类型（class）的内存。ARC 在编译期自动插入 retain（引用计数 +1）和 release（引用计数 -1）调用，当引用计数归零时立即释放对象。与垃圾回收（GC）不同，ARC 没有运行时暂停，内存释放时机确定，但开发者需要主动处理循环引用问题。

理解 ARC 的工作原理、strong / weak / unowned 的区别、闭包捕获列表的使用，以及值类型与引用类型的内存模型差异，是编写高质量 iOS 应用的基础。内存泄漏是 iOS 开发中最常见的性能问题之一，掌握 Instruments 的泄漏检测能力是每位 iOS 开发者的必备技能。

核心概念
ARC 原理
每个 class 实例在堆上分配内存，并维护一个引用计数器。当新的变量、属性或常量指向该实例时，引用计数 +1；当引用离开作用域或被置为 nil 时，引用计数 -1。当引用计数降为 0 时，ARC 立即调用 deinit 并回收内存：


class DatabaseConnection {
    let name: String

    init(name: String) {
        self.name = name
        print("\(name) 连接已创建")
    }

    deinit {
        print("\(name) 连接已销毁")
    }
}

var conn1: DatabaseConnection? = DatabaseConnection(name: "主库")
var conn2 = conn1
var conn3 = conn1

conn1 = nil
conn2 = nil
print("conn3 仍然持有引用")
conn3 = nil
strong（强引用）
Swift 中所有引用默认都是强引用。强引用会增加引用计数，防止对象被释放：


class ViewController {
    let title: String
    var childController: ViewController?

    init(title: String) {
        self.title = title
    }

    deinit {
        print("\(title) 已释放")
    }
}

var root: ViewController? = ViewController(title: "Root")
root?.childController = ViewController(title: "Child")
root = nil
当 root 设为 nil 时，root 引用计数归零，deinit 被调用。此时 childController 也失去最后一个强引用，跟着释放。这是正常的单向持有关系。


weak（弱引用）
weak 引用不增加引用计数，当对象被释放时自动变为 nil。因此 weak 引用必须是 Optional 类型且用 var 声明：


class Apartment {
    let unit: String
    weak var tenant: Person?

    init(unit: String) { self.unit = unit }
    deinit { print("公寓 \(unit) 已释放") }
}

class Person {
    let name: String
    var apartment: Apartment?

    init(name: String) { self.name = name }
    deinit { print("\(name) 已释放") }
}

var john: Person? = Person(name: "John")
var unit4A: Apartment? = Apartment(unit: "4A")

john?.apartment = unit4A
unit4A?.tenant = john

john = nil
unit4A = nil
没有 weak，Person 和 Apartment 会相互强引用形成循环，两者都不会被释放。使用 weak 后，tenant 不阻止 Person 释放。


unowned（无主引用）
unowned 引用也不增加引用计数，但与 weak 不同，它假设被引用的对象始终存在。访问已释放对象的 unowned 引用会导致运行时崩溃：


class Customer {
    let name: String
    var card: CreditCard?

    init(name: String) { self.name = name }
    deinit { print("\(name) 已释放") }
}

class CreditCard {
    let number: String
    unowned let owner: Customer

    init(number: String, owner: Customer) {
        self.number = number
        self.owner = owner
    }

    deinit { print("卡号 \(number) 已释放") }
}

var customer: Customer? = Customer(name: "Alice")
customer?.card = CreditCard(number: "1234-5678", owner: customer!)
customer = nil
CreditCard 的生命周期不可能超过 Customer——信用卡总是属于某个客户。在这种语义下使用 unowned 比 weak 更合适，避免了不必要的 Optional 解包。

循环引用
当两个对象互相持有强引用时，即使外部已无引用，它们的引用计数也不会归零——这就是循环引用（Retain Cycle），也称为内存泄漏：


class Teacher {
    let name: String
    var favoriteStudent: Student?

    init(name: String) { self.name = name }
    deinit { print("Teacher \(name) 释放") }
}

class Student {
    let name: String
    var advisor: Teacher?

    init(name: String) { self.name = name }
    deinit { print("Student \(name) 释放") }
}

var teacher: Teacher? = Teacher(name: "王老师")
var student: Student? = Student(name: "小李")

teacher?.favoriteStudent = student
student?.advisor = teacher

teacher = nil
student = nil
上面的代码中，teacher 和 student 设为 nil 后，两个对象仍然相互强引用，deinit 永远不会被调用。


解决方案：将其中一侧改为 weak 或 unowned。


闭包捕获列表 [weak self]
闭包会捕获其引用的外部变量。当闭包被 class 实例持有，而闭包又捕获了该实例（self）时，形成循环引用：


class NetworkManager {
    var onComplete: (() -> Void)?
    let url: String

    init(url: String) { self.url = url }

    func startRequest() {
        onComplete = {
            print("请求完成：\(self.url)")
        }
    }

    deinit { print("NetworkManager 释放") }
}

var manager: NetworkManager? = NetworkManager(url: "https://api.example.com")
manager?.startRequest()
manager = nil
manager → onComplete 闭包 → self（即 manager），形成循环。解决方案是使用捕获列表：


class NetworkManager {
    var onComplete: (() -> Void)?
    let url: String

    init(url: String) { self.url = url }

    func startRequest() {
        onComplete = { [weak self] in
            guard let self else { return }
            print("请求完成：\(self.url)")
        }
    }

    deinit { print("NetworkManager 释放") }
}
捕获列表的常见写法：


let closure1 = { [weak self] in
    self?.doSomething()
}

let closure2 = { [weak self] in
    guard let self else { return }
    doSomething()
    doAnotherThing()
}

let closure3 = { [unowned self] in
    doSomething()
}

let closure4 = { [weak self, weak delegate] in
    self?.notify(delegate)
}

class ProfileViewController: UIViewController {

    }

值类型 vs 引用类型的内存模型
Swift 的类型系统分为值类型和引用类型，它们有完全不同的内存行为：


struct Point {
    var x: Double
    var y: Double
}

var a = Point(x: 1, y: 2)
var b = a
b.x = 10
print(a.x)
print(b.x)
值类型赋值产生独立副本，修改 b 不影响 a。


class PointRef {
    var x: Double
    var y: Double

    init(x: Double, y: Double) {
        self.x = x
        self.y = y
    }
}

var c = PointRef(x: 1, y: 2)
var d = c
d.x = 10
print(c.x)
print(d.x)
引用类型赋值共享同一实例，修改 d 同时影响 c。


Copy-on-Write（COW）
Swift 标准库的集合类型（Array、Dictionary、Set、String）虽然是值类型，但底层使用写时复制优化：


var arr1 = [1, 2, 3, 4, 5]
var arr2 = arr1

print(arr1.withUnsafeBufferPointer { "\($0.baseAddress!)" })
print(arr2.withUnsafeBufferPointer { "\($0.baseAddress!)" })

arr2.append(6)

print(arr1.withUnsafeBufferPointer { "\($0.baseAddress!)" })
print(arr2.withUnsafeBufferPointer { "\($0.baseAddress!)" })
赋值时，arr1 和 arr2 共享同一块内存（引用计数 +1）。只有在某一方修改时，才会触发真正的复制。这让值类型在大多数场景下既安全又高效。

使用方式
模式一：ViewModel 中正确处理闭包
iOS 开发中最常见的内存泄漏场景——ViewModel 持有闭包，闭包捕获 self：


class SearchViewModel {
    private var searchTask: Task<Void, Never>?
    var results: [String] = []
    var onUpdate: (() -> Void)?

    func search(query: String) {
        searchTask?.cancel()
        searchTask = Task { [weak self] in
            try? await Task.sleep(for: .milliseconds(300))
            guard let self, !Task.isCancelled else { return }
            let results = try? await performSearch(query)
            self.results = results ?? []
            self.onUpdate?()
        }
    }

    private func performSearch(_ query: String) async throws -> [String] {
        []
    }

    deinit {
        searchTask?.cancel()
        print("SearchViewModel 释放")
    }
}
模式二：Delegate 使用 weak
Delegate 模式中，delegate 属性应始终用 weak 声明，避免持有者和代理之间的循环引用：


protocol DataManagerDelegate: AnyObject {
    func dataManager(_ manager: DataManager, didFetch items: [String])
    func dataManager(_ manager: DataManager, didEncounterError error: Error)
}

class DataManager {
    weak var delegate: DataManagerDelegate?

    func fetchData() async {
        do {
            let items = try await loadFromNetwork()
            delegate?.dataManager(self, didFetch: items)
        } catch {
            delegate?.dataManager(self, didEncounterError: error)
        }
    }

    private func loadFromNetwork() async throws -> [String] {
        []
    }
}
注意：delegate 协议必须标记为 AnyObject（或 : class），这样 weak 关键字才能使用——weak 仅适用于引用类型。


模式三：NotificationCenter 与 Timer 的清理
class LiveUpdateController: UIViewController {
    private var timer: Timer?
    private var notificationToken: NSObjectProtocol?

    override func viewDidLoad() {
        super.viewDidLoad()

        notificationToken = NotificationCenter.default.addObserver(
            forName: UIApplication.didBecomeActiveNotification,
            object: nil,
            queue: .main
        ) { [weak self] _ in
            self?.refreshData()
        }

        timer = Timer.scheduledTimer(withTimeInterval: 30, repeats: true) { [weak self] _ in
            self?.refreshData()
        }
    }

    private func refreshData() {
        print("刷新数据...")
    }

    deinit {
        timer?.invalidate()
        if let token = notificationToken {
            NotificationCenter.default.removeObserver(token)
        }
        print("LiveUpdateController 释放")
    }
}
Timer 和 NotificationCenter 的闭包都会强引用 self（如果不加 [weak self]），且它们的生命周期可能超过 ViewController。


常见陷阱
陷阱一：在不需要 [weak self] 时过度使用
并非所有闭包都需要 [weak self]。非逃逸闭包（如 map、filter、forEach）不会导致循环引用：


let names = users.map { self.formatName($0) }

UIView.animate(withDuration: 0.3) {
    self.view.alpha = 0
}
只有当闭包被存储（赋值给属性、传给异步 API）时才可能形成循环。一次性执行完毕的逃逸闭包（如网络请求的 completion handler）虽然暂时持有 self，但执行完后会释放，通常不会造成永久泄漏。


陷阱二：unowned 引用悬垂导致崩溃
如果不能 100% 确保被引用对象的生命周期长于引用者，不要使用 unowned。在有疑问时，始终选择 weak：


class Parent {
    var child: Child?
    deinit { print("Parent 释放") }
}

class Child {
    unowned let parent: Parent
    init(parent: Parent) { self.parent = parent }
}

var parent: Parent? = Parent()
let child = Child(parent: parent!)
parent?.child = child
parent = nil
// print(child.parent)  ← 崩溃！parent 已释放，unowned 引用悬垂
陷阱三：值类型中嵌套引用类型
struct 内部如果包含 class 类型的属性，赋值时 struct 本身被复制，但 class 属性只是复制引用——两个 struct 副本共享同一个 class 实例：


class ImageCache {
    var images: [String: Data] = [:]
}

struct ViewModel {
    var title: String
    var cache: ImageCache
}

var vm1 = ViewModel(title: "A", cache: ImageCache())
var vm2 = vm1

vm2.title = "B"
vm2.cache.images["hero"] = Data()

print(vm1.title)
print(vm1.cache.images.count)
vm1.title 不受影响（值类型），但 vm1.cache.images 已经被 vm2 修改（引用类型共享）。


陷阱四：忘记在 deinit 中清理资源
当 class 持有需要手动清理的资源（Timer、观察者、文件句柄、数据库连接）时，必须在 deinit 中释放，否则即使对象本身被回收，外部资源仍然泄漏：


class FileProcessor {
    private var fileHandle: FileHandle?

    init(path: String) {
        fileHandle = FileHandle(forReadingAtPath: path)
    }

    deinit {
        fileHandle?.closeFile()
    }
}
小结
    

  • ARC 通过编译期插入 retain/release 自动管理引用类型的内存，无 GC 暂停，释放时机确定。
    • 

  • strong 是默认引用，增加引用计数；weak 不增加引用计数且对象释放后自动变 nil；unowned 不增加引用计数但对象释放后访问会崩溃。
    • 

  • 循环引用是 ARC 下最常见的内存泄漏原因——两个对象互相强引用导致引用计数永远不归零。
    • 

  • 闭包捕获列表 [weak self] 是打破闭包-对象循环引用的标准方式，配合 guard let self 使用。
    • 

  • Instruments（Leaks、Allocations）和 Memory Graph Debugger 是检测内存泄漏的核心工具，deinit 日志是最简单的验证手段。
    • 

  • 值类型（struct/enum）存储在栈上，赋值时复制，无引用计数开销，无循环引用风险；引用类型（class）存储在堆上，共享引用，需要 ARC 管理。
    • 

  • 标准库集合使用 Copy-on-Write 优化，兼顾值语义的安全性和引用共享的性能。
    • 

  • 优先使用值类型；在需要引用语义、继承或 deinit 时才使用 class。
    •
