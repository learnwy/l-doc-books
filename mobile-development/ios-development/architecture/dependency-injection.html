Part I · iOSiOS 开发 简介架构 简介依赖注入

依赖注入

概述

依赖注入（Dependency Injection, DI）是一种设计模式，它将对象所需的依赖从内部创建转变为外部传入。核心思想是：一个对象不应该自己创建它所依赖的对象，而应该由外部（调用者或容器）负责提供。

DI 是实现**控制反转（Inversion of Control, IoC）**的具体手段。在 iOS 开发中，DI 使得 ViewModel、UseCase、Repository 等组件之间的耦合度大幅降低，每个组件都可以独立测试。SwiftUI 的 @Environment 机制本质上就是框架级的依赖注入系统。

核心概念
构造器注入（Constructor Injection）
构造器注入是最推荐的 DI 方式。依赖通过 init 参数传入，对象在创建后即拥有所有必需的依赖，状态完整且不可变：


protocol UserRepository {
    func fetchUser(by id: String) async throws -> User
    func saveUser(_ user: User) async throws
}

protocol AnalyticsService {
    func track(event: String, properties: [String: Any])
}

class UserProfileViewModel {
    private let repository: UserRepository
    private let analytics: AnalyticsService

    init(repository: UserRepository, analytics: AnalyticsService) {
        self.repository = repository
        self.analytics = analytics
    }

    func loadUser(id: String) async throws -> User {
        analytics.track(event: "profile_viewed", properties: ["user_id": id])
        return try await repository.fetchUser(by: id)
    }
}
构造器注入的优势在于：依赖关系在编译时就已确定，不会出现"忘记设置依赖"导致的运行时崩溃。


属性注入（Property Injection）
属性注入通过公开的属性设置依赖。它适用于依赖是可选的或需要延迟配置的场景：


class ImageLoader {
    var cache: ImageCache?
    var logger: Logger?

    func loadImage(from url: URL) async throws -> Data {
        if let cached = cache?.image(for: url) {
            logger?.log("Cache hit: \(url)")
            return cached
        }

        logger?.log("Fetching: \(url)")
        let (data, _) = try await URLSession.shared.data(from: url)
        cache?.store(data, for: url)
        return data
    }
}

let loader = ImageLoader()
loader.cache = InMemoryImageCache()
loader.logger = ConsoleLogger()
属性注入的缺点是对象在创建后可能处于不完整状态，使用者需要自行确保依赖已设置。


方法注入（Method Injection）
方法注入将依赖作为方法参数传入，适用于依赖只在特定操作中需要的场景：


class ReportGenerator {
    func generate(
        data: [SalesRecord],
        formatter: ReportFormatter,
        exporter: ReportExporter
    ) throws -> Data {
        let formatted = formatter.format(data)
        return try exporter.export(formatted)
    }
}

protocol ReportFormatter {
    func format(_ records: [SalesRecord]) -> FormattedReport
}

protocol ReportExporter {
    func export(_ report: FormattedReport) throws -> Data
}
方法注入让每次调用都可以使用不同的策略，非常灵活。


Protocol-based DI
Swift 中 DI 的最佳实践是基于 Protocol 定义依赖接口。所有组件依赖抽象而非具体实现：


protocol DateProvider {
    var now: Date { get }
}

struct SystemDateProvider: DateProvider {
    var now: Date { Date() }
}

struct FixedDateProvider: DateProvider {
    let fixedDate: Date
    var now: Date { fixedDate }
}

class EventScheduler {
    private let dateProvider: DateProvider

    init(dateProvider: DateProvider = SystemDateProvider()) {
        self.dateProvider = dateProvider
    }

    func isEventUpcoming(_ event: Event) -> Bool {
        event.startDate > dateProvider.now
    }
}
DI 容器
当项目规模增大后，手动传递依赖会变得繁琐。DI 容器集中管理所有依赖的注册和解析：


class DependencyContainer {
    static let shared = DependencyContainer()

    private var factories: [String: () -> Any] = [:]

    func register<T>(_ type: T.Type, factory: @escaping () -> T) {
        let key = String(describing: type)
        factories[key] = factory
    }

    func resolve<T>(_ type: T.Type) -> T {
        let key = String(describing: type)
        guard let factory = factories[key], let instance = factory() as? T else {
            fatalError("No registration for \(key)")
        }
        return instance
    }
}

extension DependencyContainer {
    func registerServices() {
        register(UserRepository.self) {
            RemoteUserRepository(apiClient: APIClient())
        }

        register(AnalyticsService.self) {
            FirebaseAnalyticsService()
        }

        register(UserProfileViewModel.self) {
            UserProfileViewModel(
                repository: self.resolve(UserRepository.self),
                analytics: self.resolve(AnalyticsService.self)
            )
        }
    }
}
更完善的 DI 容器还支持生命周期管理（单例 vs 每次新建）和线程安全：


class ScopedContainer {
    enum Scope {
        case singleton
        case transient
    }

    private var singletons: [String: Any] = [:]
    private var factories: [String: (Scope, () -> Any)] = [:]

    func register<T>(_ type: T.Type, scope: Scope = .transient, factory: @escaping () -> T) {
        let key = String(describing: type)
        factories[key] = (scope, factory)
    }

    func resolve<T>(_ type: T.Type) -> T {
        let key = String(describing: type)
        guard let (scope, factory) = factories[key] else {
            fatalError("No registration for \(key)")
        }

        switch scope {
        case .singleton:
            if let existing = singletons[key] as? T {
                return existing
            }
            let instance = factory() as! T
            singletons[key] = instance
            return instance
        case .transient:
            return factory() as! T
        }
    }
}
@Environment —— SwiftUI 的 DI 系统
SwiftUI 内置的 @Environment 机制本质上是一个框架级 DI 容器。父视图注入的值可以被任意深度的子视图读取：


@Observable
class ThemeManager {
    var primaryColor: Color = .blue
    var fontSize: CGFloat = 16
}

struct MyApp: App {
    @State private var theme = ThemeManager()

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environment(theme)
        }
    }
}

struct ContentView: View {
    @Environment(ThemeManager.self) private var theme

    var body: some View {
        Text("Hello, World!")
            .foregroundStyle(theme.primaryColor)
            .font(.system(size: theme.fontSize))
    }
}
自定义 EnvironmentKey 实现更精细的控制：


struct APIBaseURLKey: EnvironmentKey {
    static let defaultValue = URL(string: "https://api.production.com")!
}

extension EnvironmentValues {
    var apiBaseURL: URL {
        get { self[APIBaseURLKey.self] }
        set { self[APIBaseURLKey.self] = newValue }
    }
}

struct NetworkView: View {
    @Environment(\.apiBaseURL) private var baseURL

    var body: some View {
        Text("API: \(baseURL.absoluteString)")
    }
}

struct PreviewWrapper: View {
    var body: some View {
        NetworkView()
            .environment(\.apiBaseURL, URL(string: "https://api.staging.com")!)
    }
}
使用方式
模式一：App 入口组装依赖
在应用入口一次性创建所有依赖，然后逐层传递：


@main
struct MyApp: App {
    private let container: AppContainer

    init() {
        let apiClient = APIClient(baseURL: URL(string: "https://api.example.com")!)
        let userRepo = RemoteUserRepository(apiClient: apiClient)
        let analytics = FirebaseAnalyticsService()
        container = AppContainer(
            userRepository: userRepo,
            analytics: analytics
        )
    }

    var body: some Scene {
        WindowGroup {
            RootView(container: container)
        }
    }
}

struct AppContainer {
    let userRepository: UserRepository
    let analytics: AnalyticsService

    func makeUserProfileViewModel() -> UserProfileViewModel {
        UserProfileViewModel(
            repository: userRepository,
            analytics: analytics
        )
    }
}
模式二：测试中替换依赖
构造器注入使测试代码可以轻松替换任何依赖：


class MockUserRepository: UserRepository {
    var stubbedUser: User?
    var savedUsers: [User] = []

    func fetchUser(by id: String) async throws -> User {
        guard let user = stubbedUser else {
            throw NSError(domain: "Test", code: 404)
        }
        return user
    }

    func saveUser(_ user: User) async throws {
        savedUsers.append(user)
    }
}

class MockAnalytics: AnalyticsService {
    var trackedEvents: [(String, [String: Any])] = []

    func track(event: String, properties: [String: Any]) {
        trackedEvents.append((event, properties))
    }
}

@Test
func loadUserTracksAnalyticsEvent() async throws {
    let mockRepo = MockUserRepository()
    mockRepo.stubbedUser = User(id: "1", name: "Alice")

    let mockAnalytics = MockAnalytics()

    let viewModel = UserProfileViewModel(
        repository: mockRepo,
        analytics: mockAnalytics
    )

    _ = try await viewModel.loadUser(id: "1")

    #expect(mockAnalytics.trackedEvents.count == 1)
    #expect(mockAnalytics.trackedEvents.first?.0 == "profile_viewed")
}
模式三：SwiftUI Preview 中注入 Mock
利用 @Environment 在 Preview 中注入测试数据，无需真实网络请求：


#Preview {
    let mockRepo = MockUserRepository()
    mockRepo.stubbedUser = User(id: "1", name: "Preview User")

    return UserProfileView(
        viewModel: UserProfileViewModel(
            repository: mockRepo,
            analytics: MockAnalytics()
        )
    )
}
常见陷阱
陷阱一：Service Locator 反模式
DI 容器如果被组件直接引用和调用（而非在入口组装后传递），就退化为 Service Locator 模式。这隐藏了真实的依赖关系，破坏了可测试性：


class BadViewModel {
    func load() {
        // let repo = DependencyContainer.shared.resolve(UserRepository.self)
        // ← 隐藏依赖，测试时难以替换
    }
}

class GoodViewModel {
    private let repository: UserRepository

    init(repository: UserRepository) {
        self.repository = repository
    }
}
组件应该通过构造器声明自己的依赖，只有组合根（Composition Root，通常是 App 入口）才应该访问 DI 容器。


陷阱二：过度注入
不是所有类型都需要通过 DI 传入。纯数据类型（String、Int、值类型 Model）和标准库类型不需要抽象：


class OverEngineered {
    // init(formatter: DateFormatterProtocol, calendar: CalendarProtocol) ← 过度抽象
}

class Reasonable {
    private let repository: UserRepository
    private let dateFormatter = DateFormatter()

    init(repository: UserRepository) {
        self.repository = repository
    }
}
只对那些会变化的、有副作用的、需要在测试中替换的依赖进行注入。


陷阱三：属性注入遗漏导致运行时崩溃
属性注入的依赖如果忘记设置，会在运行时产生 nil 访问或逻辑错误。尽量使用构造器注入来避免这类问题：


class FragileService {
    var database: Database!

    func query() {
        database.execute("SELECT ...")
    }
}
陷阱四：@Environment 缺失导致 Preview 崩溃
使用 @Environment 时，如果祖先视图没有提供对应的环境值，运行时会崩溃。确保定义合理的 defaultValue，并在 Preview 中显式注入：


struct SafeEnvironmentKey: EnvironmentKey {
    static let defaultValue = AppConfiguration.default
}

#Preview {
    MyView()
        .environment(\.appConfig, AppConfiguration.preview)
}
小结
    

  • 依赖注入将对象的依赖从内部创建转为外部传入，实现控制反转，降低耦合度。
    • 

  • 三种注入方式：构造器注入（首选，编译时安全）、属性注入（可选依赖）、方法注入（操作级依赖）。
    • 

  • Protocol-based DI 是 Swift 中的最佳实践——组件依赖抽象接口而非具体实现。
    • 

  • DI 容器集中管理依赖的注册和解析，支持单例和瞬态两种生命周期；但只有组合根才应访问容器，避免退化为 Service Locator。
    • 

  • SwiftUI 的 @Environment 是框架级 DI 系统，通过 EnvironmentKey 可以自定义注入任意类型。
    • 

  • DI 的核心价值在于测试隔离——通过 Mock 替换真实依赖，实现快速、稳定、无副作用的单元测试。
    • 

  • 只对有副作用的、会变化的、需要测试替换的依赖进行注入，避免过度抽象。
    •
