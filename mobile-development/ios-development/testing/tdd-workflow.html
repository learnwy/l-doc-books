Part I · iOSiOS 开发 简介测试 简介TDD 工作流

TDD 工作流

概述

测试驱动开发（Test-Driven Development，TDD）是一种先写测试、再写实现的开发方法论。其核心循环是 Red → Green → Refactor——先编写一个失败的测试（Red），再用最少的代码让测试通过（Green），最后在测试保护下重构代码（Refactor）。每个循环通常只需几分钟，通过高频小步迭代推进功能开发。

TDD 不仅是一种测试策略，更是一种设计工具——它迫使开发者在编码前思考接口和行为，自然产出低耦合、高内聚的代码。在 iOS 开发中，TDD 特别适合 ViewModel、Service、工具类等纯逻辑模块。理解何时使用 TDD、何时不用，以及它与 BDD 的区别，能帮助团队在效率和质量之间找到平衡。

核心工具
Red-Green-Refactor 循环
TDD 的三个阶段构成一个紧密的反馈循环：






阶段
行为
目标





🔴 Red
编写一个描述期望行为的测试，运行后确认失败
明确需求，确保测试有效




🟢 Green
用最简单的代码让测试通过（允许硬编码）
快速验证方向正确




🔵 Refactor
在所有测试通过的前提下优化代码结构
消除重复，改善设计





关键原则：


    

  • 只在 Red 阶段写测试——不要提前写多个测试
    • 

  • Green 阶段追求最小实现——不要过度设计，先让测试通过
    • 

  • Refactor 阶段不添加新功能——只改结构，不改行为
    • 

  • 每个循环不超过几分钟——如果超过 10 分钟，说明步子太大
    • 



TDD 三法则（Uncle Bob）
    

  1. 在编写一个失败的单元测试之前，不准编写任何生产代码
    2. 

  2. 只编写刚好使一个测试失败的测试代码（编译失败也算失败）
    3. 

  3. 只编写刚好使当前失败测试通过的生产代码
    4. 



Xcode 中的 TDD 工作方式
    

  • ⌘U：运行所有测试（Red/Green 验证）
    • 

  • ⌃⌥⌘U：运行当前光标所在的测试方法
    • 

  • ⌘B：编译（检查 Red 阶段的编译失败）
    • 

  • Test Navigator（⌘6）：查看测试状态和历史
    • 



工作流程
步骤一：分析需求
将功能需求拆解为一系列小的、可验证的行为。用列表记录：


购物车功能：
- [ ] 空购物车的商品数量为 0
- [ ] 添加一件商品后数量为 1
- [ ] 添加同一商品两次，数量增加而非新增条目
- [ ] 移除商品后数量减少
- [ ] 计算总价等于所有商品价格 × 数量之和
- [ ] 清空购物车后恢复初始状态
步骤二：选择最简单的用例开始
从最简单的场景入手，逐步增加复杂度。这样每一步的代码增量最小，风险最低。


步骤三：Red-Green-Refactor 循环
每个用例执行一次完整的 R-G-R 循环，直到所有用例完成。


步骤四：回顾与重构
所有用例通过后，整体审视代码质量——命名是否清晰、职责是否单一、是否有重复逻辑。


实战演示
以购物车功能为例，完整展示 TDD 的迭代过程。


🔴 Red 1：空购物车
import XCTest
@testable import MyApp

final class ShoppingCartTests: XCTestCase {

    func testNewCart_hasZeroItems() {
        let cart = ShoppingCart()
        XCTAssertEqual(cart.itemCount, 0)
    }
}
运行测试 → 编译失败（ShoppingCart 不存在）。编译失败也是 Red。


🟢 Green 1：最小实现
struct ShoppingCart {
    var itemCount: Int { 0 }
}
运行测试 → ✅ 通过。


🔴 Red 2：添加商品
func testAddItem_incrementsCount() {
    var cart = ShoppingCart()
    cart.add(Product(id: "1", name: "键盘", price: 299))
    XCTAssertEqual(cart.itemCount, 1)
}
运行测试 → 编译失败（Product 不存在，add 方法不存在）。


🟢 Green 2：让编译通过并让测试通过
struct Product {
    let id: String
    let name: String
    let price: Double
}

struct ShoppingCart {
    private var items: [CartEntry] = []

    var itemCount: Int { items.count }

    mutating func add(_ product: Product) {
        items.append(CartEntry(product: product, quantity: 1))
    }
}

private struct CartEntry {
    let product: Product
    var quantity: Int
}
运行测试 → ✅ 两个测试通过。


🔴 Red 3：重复添加同一商品
func testAddSameItemTwice_incrementsQuantity() {
    var cart = ShoppingCart()
    let keyboard = Product(id: "1", name: "键盘", price: 299)
    cart.add(keyboard)
    cart.add(keyboard)
    XCTAssertEqual(cart.itemCount, 1)
    XCTAssertEqual(cart.quantity(for: "1"), 2)
}
运行测试 → 失败（itemCount 是 2 而非 1，quantity(for:) 不存在）。


🟢 Green 3：处理重复商品
struct ShoppingCart {
    private var items: [String: CartEntry] = [:]

    var itemCount: Int { items.count }

    mutating func add(_ product: Product) {
        if var entry = items[product.id] {
            entry.quantity += 1
            items[product.id] = entry
        } else {
            items[product.id] = CartEntry(product: product, quantity: 1)
        }
    }

    func quantity(for productId: String) -> Int {
        items[productId]?.quantity ?? 0
    }
}
运行测试 → ✅ 三个测试通过。


🔴 Red 4：计算总价
func testTotal_sumsAllItems() {
    var cart = ShoppingCart()
    cart.add(Product(id: "1", name: "键盘", price: 299))
    cart.add(Product(id: "2", name: "鼠标", price: 99))
    cart.add(Product(id: "1", name: "键盘", price: 299))
    XCTAssertEqual(cart.total, 697, accuracy: 0.01)
}
🟢 Green 4：实现 total
var total: Double {
    items.values.reduce(0) { $0 + $1.product.price * Double($1.quantity) }
}
运行测试 → ✅ 四个测试通过。


🔴 Red 5：移除商品
func testRemoveItem_decrementsCount() {
    var cart = ShoppingCart()
    let keyboard = Product(id: "1", name: "键盘", price: 299)
    cart.add(keyboard)
    cart.add(keyboard)
    cart.remove(productId: "1")
    XCTAssertEqual(cart.quantity(for: "1"), 1)
}

func testRemoveLastItem_removesEntry() {
    var cart = ShoppingCart()
    cart.add(Product(id: "1", name: "键盘", price: 299))
    cart.remove(productId: "1")
    XCTAssertEqual(cart.itemCount, 0)
}
🟢 Green 5：实现 remove
mutating func remove(productId: String) {
    guard var entry = items[productId] else { return }
    entry.quantity -= 1
    if entry.quantity <= 0 {
        items.removeValue(forKey: productId)
    } else {
        items[productId] = entry
    }
}
运行测试 → ✅ 六个测试通过。


🔵 Refactor：整体优化
所有用例通过后，审视代码。将 CartEntry 改为 Equatable 以便未来断言，提取清空方法：


struct ShoppingCart {
    private var items: [String: CartEntry] = [:]

    var itemCount: Int { items.count }
    var isEmpty: Bool { items.isEmpty }

    var total: Double {
        items.values.reduce(0) { $0 + $1.product.price * Double($1.quantity) }
    }

    mutating func add(_ product: Product) {
        if var entry = items[product.id] {
            entry.quantity += 1
            items[product.id] = entry
        } else {
            items[product.id] = CartEntry(product: product, quantity: 1)
        }
    }

    mutating func remove(productId: String) {
        guard var entry = items[productId] else { return }
        entry.quantity -= 1
        if entry.quantity <= 0 {
            items.removeValue(forKey: productId)
        } else {
            items[productId] = entry
        }
    }

    func quantity(for productId: String) -> Int {
        items[productId]?.quantity ?? 0
    }

    mutating func clear() {
        items.removeAll()
    }
}
运行测试 → ✅ 所有测试仍然通过。重构安全完成。

BDD 示例（Quick/Nimble 风格）：


import Quick
import Nimble
@testable import MyApp

final class ShoppingCartSpec: QuickSpec {
    override class func spec() {
        describe("购物车") {
            var cart: ShoppingCart!

            beforeEach { cart = ShoppingCart() }

            context("当添加商品时") {
                it("商品数量增加") {
                    cart.add(Product(id: "1", name: "键盘", price: 299))
                    expect(cart.itemCount).to(equal(1))
                }
            }

            context("当购物车为空时") {
                it("总价为零") {
                    expect(cart.total).to(equal(0))
                }
            }
        }
    }
}
Q：TDD 会不会让开发变慢？ 短期来看，TDD 增加了前期编写测试的时间。但中长期来看，它通过减少调试时间、降低回归风险、改善代码设计来提升整体效率。对于复杂业务逻辑，TDD 通常比"先实现后补测试"更快——因为它将大问题分解为小步骤，每步都有即时反馈。


Q：Green 阶段可以硬编码吗？ 可以，甚至被鼓励。硬编码是"最小实现"的极端形式，它确保你只在有新测试驱动时才增加复杂度。随着更多测试的加入，硬编码自然会被通用实现取代——这就是 TDD 的"三角测量"（Triangulation）技巧。


Q：遗留代码如何引入 TDD？ 不要试图一次性为遗留代码补齐测试。采用修改前先加测试的策略：每次修改功能前，先为现有行为写测试（表征测试），确认测试通过后再进行修改。逐步扩大测试覆盖范围。


小结
    

  • TDD 的核心是 Red → Green → Refactor 循环——先写失败测试，再最小实现，最后重构。
    • 

  • 每个循环应控制在几分钟内完成，保持小步快跑、高频反馈。
    • 

  • TDD 不仅验证正确性，更是一种设计驱动工具——通过测试先行，自然产出低耦合代码。
    • 

  • 适合 TDD 的场景：业务逻辑、数据验证、算法、Bug 修复。不适合：UI 布局、原型探索。
    • 

  • Green 阶段允许硬编码，随着新测试的加入逐步泛化实现（三角测量）。
    • 

  • BDD 关注业务行为描述（Given-When-Then），TDD 关注技术实现验证，两者互补而非替代。
    • 

  • 遗留代码可通过表征测试逐步引入 TDD——修改前先加测试，保护现有行为。
    •
