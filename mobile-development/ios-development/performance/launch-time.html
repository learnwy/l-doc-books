启动速度优化

概述

启动速度是用户对应用的第一印象。Apple 要求应用在 400ms 内完成启动并显示首屏内容，否则在极端情况下可能被 watchdog 机制终止。冷启动耗时过长（>2s）会显著影响用户留存率——研究表明每增加 1 秒的启动时间，用户放弃率上升约 20%。

iOS 应用启动分为 pre-main（操作系统加载阶段）和 post-main（应用代码执行阶段）两大部分。优化启动速度需要同时关注两个阶段：减少 dylib 加载、推迟非必要初始化、异步执行耗时任务、延迟加载次要模块。MetricKit 和 App Launch Instrument 提供了精确的度量能力。

MetricKit
MXAppLaunchMetric 提供生产环境的启动耗时统计，无需手动埋点，由系统自动采集：


import MetricKit

class MetricSubscriber: NSObject, MXMetricManagerSubscriber {
    func didReceive(_ payloads: [MXMetricPayload]) {
        for payload in payloads {
            if let launchMetric = payload.applicationLaunchMetrics {
                let histogram = launchMetric.histogrammedTimeToFirstDraw
                print("首帧绘制耗时分布：\(histogram)")
            }
        }
    }

    func didReceive(_ payloads: [MXDiagnosticPayload]) {}
}

class AppMetrics {
    private let subscriber = MetricSubscriber()

    func start() {
        MXMetricManager.shared.add(subscriber)
    }
}

实战演示
冷启动 vs 热启动
冷启动：应用进程不存在，系统需要从头创建进程、加载可执行文件和所有动态库、执行初始化。这是用户最常感知的启动体验。


热启动：应用进程仍在内存中（被挂起但未被杀掉），系统只需恢复进程状态。耗时极短，通常不需要优化。


温启动：进程已被终止但部分数据仍在系统缓存中（如 dyld shared cache），介于冷启动和热启动之间。

post-main 优化：启动任务调度器
didFinishLaunchingWithOptions 中通常堆积大量初始化逻辑。启动任务调度器将这些任务分为不同优先级，关键路径任务同步执行，非关键任务延迟或异步执行：


enum LaunchTaskPriority: Int, Comparable {
    case critical = 0
    case high = 1
    case normal = 2
    case deferred = 3

    static func < (lhs: Self, rhs: Self) -> Bool {
        lhs.rawValue < rhs.rawValue
    }
}

struct LaunchTask {
    let name: String
    let priority: LaunchTaskPriority
    let action: () async -> Void
}

class LaunchTaskScheduler {
    private var tasks: [LaunchTask] = []

    func register(_ task: LaunchTask) {
        tasks.append(task)
    }

    func execute() async {
        let sorted = tasks.sorted { $0.priority < $1.priority }

        for task in sorted where task.priority == .critical {
            await task.action()
        }

        for task in sorted where task.priority == .high {
            await task.action()
        }

        Task.detached(priority: .utility) { [tasks = sorted] in
            for task in tasks where task.priority == .normal {
                await task.action()
            }
        }

        Task.detached(priority: .background) { [tasks = sorted] in
            try? await Task.sleep(for: .seconds(3))
            for task in tasks where task.priority == .deferred {
                await task.action()
            }
        }
    }
}
使用方式：


class AppDelegate: UIResponder, UIApplicationDelegate {
    private let scheduler = LaunchTaskScheduler()

    func application(
        _ application: UIApplication,
        didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?
    ) -> Bool {
        scheduler.register(LaunchTask(
            name: "Database",
            priority: .critical,
            action: { await DatabaseManager.shared.initialize() }
        ))

        scheduler.register(LaunchTask(
            name: "Analytics",
            priority: .normal,
            action: { await AnalyticsService.shared.start() }
        ))

        scheduler.register(LaunchTask(
            name: "RemoteConfig",
            priority: .deferred,
            action: { await RemoteConfigManager.shared.fetch() }
        ))

        Task { await scheduler.execute() }

        return true
    }
}

class RootCoordinator {

os_signpost 度量启动阶段
在关键启动阶段插入 signpost 标记，配合 Instruments 精确查看每段耗时：


import os.signpost

enum LaunchSignpost {
    static let log = OSLog(subsystem: "com.app.launch", category: .pointsOfInterest)

    static func begin(_ name: StaticString) {
        os_signpost(.begin, log: log, name: name)
    }

    static func end(_ name: StaticString) {
        os_signpost(.end, log: log, name: name)
    }
}

// AppDelegate 中使用
func application(
    _ application: UIApplication,
    didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?
) -> Bool {
    LaunchSignpost.begin("AppLaunch")

    LaunchSignpost.begin("DatabaseInit")
    DatabaseManager.shared.initialize()
    LaunchSignpost.end("DatabaseInit")

    LaunchSignpost.begin("UISetup")
    setupRootViewController()
    LaunchSignpost.end("UISetup")

    LaunchSignpost.end("AppLaunch")
    return true
}
常见问题
Q：冷启动目标耗时应该是多少？
Apple 建议首帧渲染在 400ms 以内。行业最佳实践：冷启动总耗时（到可交互）控制在 1 秒以内，超过 2 秒需要优先优化。


Q：如何减少 dylib 加载时间？
将第三方动态库（.framework）转换为静态库（.a 或通过 SPM 设置 type: .static）。每个动态库的加载开销约 2~5ms，库越多累积越明显。Apple 建议应用内嵌动态库不超过 6 个。


Q：Swift Package 是动态库还是静态库？
SPM 默认根据使用方式自动选择。可以在 Package.swift 中显式指定 .library(name:, type: .static, targets:) 强制静态链接，减少启动时的动态库加载开销。


Q：为什么 DYLD_PRINT_STATISTICS 在 iOS 16+ 不输出了？
Apple 从 iOS 16 / dyld4 开始移除了对 DYLD_PRINT_STATISTICS 的支持。替代方案是使用 App Launch Instrument 或 MetricKit 的 MXAppLaunchMetric。


Q：启动任务应该放在 main thread 还是 background？
必须在主线程完成的任务：UI 初始化、根视图控制器设置、用户状态检查（决定登录还是首页）。可以放到后台的任务：日志系统、分析 SDK、远程配置拉取、缓存预热。


小结
    

  • 冷启动分为 pre-main（dylib 加载、runtime 初始化）和 post-main（应用代码执行到首屏渲染）两个阶段。
    • 

  • pre-main 优化：减少动态库数量（合并为静态库）、避免 +load 中的耗时操作、减少全局静态初始化器。
    • 

  • post-main 优化：使用启动任务调度器按优先级执行初始化、延迟加载非首屏模块、异步初始化非关键服务。
    • 

  • lazy 属性和延迟加载模式将初始化成本推迟到首次使用时，避免在启动路径上浪费时间。
    • 

  • App Launch Instrument 将启动过程精确分解为多个阶段，定位具体瓶颈。
    • 

  • MetricKit 在生产环境自动采集启动耗时分布，无需手动埋点即可监控线上性能。
    • 

  • os_signpost 提供自定义启动阶段标记，配合 Instruments 查看每段精确耗时。
    • 

  • 目标：冷启动首帧渲染 < 400ms，到可交互 < 1s。
    •
