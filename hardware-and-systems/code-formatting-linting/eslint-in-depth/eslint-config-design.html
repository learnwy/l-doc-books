ESLint 配置体系设计

核心概念

ESLint 的配置体系是连接规则能力与项目需求的桥梁。一个设计良好的 ESLint 配置能够在严格性与开发体验之间取得平衡——既能捕获真正的代码问题，又不会产生大量噪音。ESLint 9.x 引入的 Flat Config 是配置体系的重大革新，它用简洁的 JavaScript 数组替代了复杂的级联配置。

规则严格度分级
ESLint 规则的配置值有三个级别："off"（0）、"warn"（1）、"error"（2）。合理的分级策略直接影响开发体验。


const severityStrategy = {
  error: ['no-undef', 'no-unused-vars', 'no-duplicate-imports', 'no-unreachable', 'no-use-before-define'],
  warn: ['prefer-const', 'no-console', 'no-debugger', '@typescript-eslint/no-explicit-any'],
  off: ['semi', 'indent', 'quotes', 'comma-dangle'],
};
分级的核心原则：






级别
含义
适用规则类型
CI 行为





error
必须修复，阻断 CI
真正的 bug、安全问题
构建失败




warn
应当修复，不阻断

构建通过，但有警告




off
不检查
与 Prettier 冲突的格式规则
不检查





一个常见的反模式是将所有规则都设为 error。这会导致开发者在早期原型阶段被大量不相关的错误阻断，最终选择注释掉 ESLint 或忽略所有警告。推荐的做法是：只有可能引起运行时错误的规则才设为 error。


import eslint from '@eslint/js';
import tseslint from 'typescript-eslint';

export default tseslint.config(eslint.configs.recommended, ...tseslint.configs.recommended, {
  rules: {
    'no-unused-vars': 'off',
    '@typescript-eslint/no-unused-vars': [
      'error',
      {
        argsIgnorePattern: '^_',
        varsIgnorePattern: '^_',
      },
    ],
    '@typescript-eslint/no-explicit-any': 'warn',
    '@typescript-eslint/consistent-type-imports': [
      'error',
      {
        prefer: 'type-imports',
      },
    ],
  },
});

文件范围与覆盖规则
不同类型的文件需要不同的规则配置。Flat Config 通过 files 和 ignores 字段实现精确的文件范围控制。


export default [
  {
    files: ['**/*.{ts,tsx}'],
    languageOptions: {
      parser: tsParser,
      parserOptions: { project: './tsconfig.json' },
    },
    rules: {
      '@typescript-eslint/no-floating-promises': 'error',
    },
  },

  {
    files: ['**/*.test.{ts,tsx}', '**/*.spec.{ts,tsx}'],
    plugins: { vitest: vitestPlugin },
    rules: {
      'vitest/expect-expect': 'error',
      'vitest/no-identical-title': 'error',
      '@typescript-eslint/no-explicit-any': 'off',
      '@typescript-eslint/no-non-null-assertion': 'off',
    },
  },

  {
    files: ['**/scripts/**/*.{ts,mjs}'],
    rules: {
      'no-console': 'off',
    },
  },

  {
    files: ['**/*.config.{ts,mjs,js}'],
    rules: {
      'import-x/no-default-export': 'off',
    },
  },

  {
    ignores: ['dist/**', 'node_modules/**', 'coverage/**', '**/*.generated.*'],
  },
];

共享配置与组织策略
对于多项目团队或 monorepo，将 ESLint 配置抽取为共享 npm 包是维护效率的关键。


import type { Linter } from 'eslint';

interface SharedConfigOptions {
  typescript?: boolean;
  react?: boolean;
  strictness?: 'relaxed' | 'recommended' | 'strict';
  testFramework?: 'vitest' | 'jest';
}

function createConfig(options: SharedConfigOptions): Linter.Config[] {
  const configs: Linter.Config[] = [];

  configs.push({
    rules: baseRules[options.strictness ?? 'recommended'],
  });

  if (options.typescript) {
    configs.push(...typescriptConfigs);
  }

  if (options.react) {
    configs.push(...reactConfigs);
  }

  if (options.testFramework) {
    configs.push(testConfig(options.testFramework));
  }

  return configs;
}
import { createConfig } from '@my-org/eslint-config';

export default [
  ...createConfig({
    typescript: true,
    react: true,
    strictness: 'recommended',
    testFramework: 'vitest',
  }),
  {
    rules: {
      'no-console': 'warn',
    },
  },
];

小结
    

  • 规则严格度分级是配置设计的核心：error 仅用于真正的 bug，warn 用于最佳实践
    • 

  • 插件选型需要处理同名规则冲突，尤其是 ESLint 内置规则与 TypeScript ESLint 的对应关系
    • 

  • Flat Config 的 files / ignores 字段允许为不同文件类型设置差异化规则
    • 

  • 共享配置通过工厂函数模式封装为 npm 包，支持 monorepo 和跨仓库复用
    • 

  • 配置演进应采用渐进策略：新规则先以 warn 引入，稳定后提升为 error
    •
