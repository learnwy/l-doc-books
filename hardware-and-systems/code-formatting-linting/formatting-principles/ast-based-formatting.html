基于 AST 的格式化原理

核心概念

代码格式化的本质是将源代码转换为符合特定风格约定的等价代码。现代格式化工具的核心思路是：先将代码解析为抽象语法树（AST），再根据规则将 AST 重新输出为格式化后的文本。这种方式与基于正则表达式的字符串替换截然不同，它能够理解代码的语义结构，从而做出更精确、更一致的格式化决策。

AST 格式化的核心优势在于幂等性——无论输入代码风格如何混乱，只要语义相同，输出结果必然一致。这一特性彻底消除了团队中关于代码风格的争论。


AST 解析与节点遍历
AST 是源代码的树状表示，每个节点对应一个语法结构。以 JavaScript 为例，一段简单的变量声明 const x = 1 + 2; 会被解析为如下结构：


interface ASTNode {
  type: string;
  start: number;
  end: number;
  children?: ASTNode[];
}

const ast: ASTNode = {
  type: 'VariableDeclaration',
  kind: 'const',
  declarations: [
    {
      type: 'VariableDeclarator',
      id: { type: 'Identifier', name: 'x' },
      init: {
        type: 'BinaryExpression',
        operator: '+',
        left: { type: 'NumericLiteral', value: 1 },
        right: { type: 'NumericLiteral', value: 2 },
      },
    },
  ],
};
格式化工具通常使用深度优先遍历来访问 AST 的每个节点。在遍历过程中，工具会为每个节点生成对应的格式化指令：


function formatNode(node: ASTNode, context: FormatContext): Doc {
  switch (node.type) {
    case 'VariableDeclaration':
      return concat([
        node.kind,
        ' ',
        join(
          ', ',
          node.declarations.map((d) => formatNode(d, context)),
        ),
        ';',
      ]);
    case 'BinaryExpression':
      return group([formatNode(node.left, context), ' ', node.operator, line, formatNode(node.right, context)]);
    default:
      return printRaw(node);
  }
}
不同的解析器对同一语言会产生不同的 AST 结构。JavaScript 生态中常见的解析器包括 Babel Parser、Acorn、TypeScript Compiler API 以及较新的 SWC Parser。Prettier 早期主要依赖 Babel Parser，后来逐步支持了多种解析器以适应不同场景。


中间表示与 Doc 命令
AST 到最终文本之间，格式化工具通常引入一层中间表示（Intermediate Representation）。Prettier 借鉴了 Philip Wadler 的论文《A Prettier Printer》，使用了一套称为 Doc 的中间表示系统。

以函数调用 foo(arg1, arg2, arg3) 为例，当参数列表较短时输出为单行，超出行宽时自动展开为多行：


function printCallExpression(node: CallExpression): Doc {
  return group([
    printNode(node.callee),
    '(',
    indent([softline, join([',', line], node.arguments.map(printNode))]),
    softline,
    ')',
  ]);
}
这套 Doc 系统的精妙之处在于：格式化规则只需要描述"什么地方可以换行"，而"是否真的换行"由 Doc 引擎根据行宽约束自动决定。


行宽约束与贪心算法
格式化的最终环节是将 Doc 转换为实际文本。这一步的核心挑战是行宽约束求解：在保证每行不超过指定宽度（如 80 列）的前提下，尽量将内容放在同一行以提高可读性。


Prettier 采用的算法思路源自 Wadler 的贪心策略：


interface PrintState {
  indentLevel: number;
  currentLineWidth: number;
  maxLineWidth: number;
  output: string;
}

function printDoc(doc: Doc, state: PrintState): void {
  switch (doc.type) {
    case 'group': {
      const flatContent = tryFlatten(doc.contents);
      const flatWidth = measureWidth(flatContent);
      if (state.currentLineWidth + flatWidth <= state.maxLineWidth) {
        printFlat(flatContent, state);
      } else {
        printExpanded(doc.contents, state);
      }
      break;
    }
    case 'indent':
      state.indentLevel += 1;
      printDoc(doc.contents, state);
      state.indentLevel -= 1;
      break;
    case 'line':
      state.output += '\n' + ' '.repeat(state.indentLevel * 2);
      state.currentLineWidth = state.indentLevel * 2;
      break;
  }
}
算法的关键决策点在于 group 节点：先尝试将整个 group 扁平化为单行，如果不超出行宽就采用单行模式；否则展开为多行。这是一种贪心策略，它不会全局最优化所有可能的换行组合，而是自顶向下逐个 group 做出局部最优决策。


这种贪心策略的优势是线性时间复杂度，而全局最优的动态规划方案虽然理论上更优，但在实际场景中复杂度过高。Google 的 google-java-format 曾尝试使用动态规划求解最优格式化方案，但最终也采用了类似的贪心策略以确保性能。


注释与空白保留
AST 格式化面临的最大挑战之一是注释处理。注释在语法上不属于任何 AST 节点，但在格式化输出中必须出现在正确的位置。


const result = foo(
  // 第一个参数的说明
  arg1,
  arg2 /* 行内注释 */,
);
格式化工具需要解决三个关键问题：


注释归属：将每条注释关联到最近的 AST 节点。通常的策略是根据注释的位置（行号、列号）将其归类为前导注释（leading）、尾随注释（trailing）或内部注释（inner）。


空行保留：用户在代码中插入的空行往往具有逻辑分组的含义。多数格式化工具会保留原始代码中的单个空行，但会将连续多个空行压缩为一个。Prettier 的策略是保留用户的空行意图，但不允许超过一个连续空行。


Pragma 与指令：某些注释具有特殊含义，如 // prettier-ignore、/* eslint-disable */、// @ts-ignore 等。格式化工具需要识别这些指令并跳过对应区域的格式化。


function attachComments(ast: AST, comments: Comment[]): void {
  for (const comment of comments) {
    const enclosingNode = findEnclosingNode(ast, comment.start, comment.end);
    const precedingNode = findPrecedingNode(enclosingNode, comment.start);
    const followingNode = findFollowingNode(enclosingNode, comment.end);

    if (isOnSameLine(precedingNode, comment)) {
      addTrailingComment(precedingNode, comment);
    } else if (followingNode) {
      addLeadingComment(followingNode, comment);
    } else {
      addDanglingComment(enclosingNode, comment);
    }
  }
}
注释处理是格式化工具中 bug 最集中的区域。Prettier 的 issue 中有大量与注释位置错误相关的报告，这也是 AST 格式化方案的固有难题。


多语言支持与解析器插件
现代格式化工具通常需要支持多种编程语言。Prettier 通过插件架构实现了对不同语言的支持，每个插件提供三个核心能力：解析器、AST 遍历器和打印器。


interface PrettierPlugin {
  parsers: Record<string, Parser>;
  printers: Record<string, Printer>;
  languages: Language[];
}

interface Parser {
  parse(text: string, options: Options): AST;
  astFormat: string;
  locStart(node: ASTNode): number;
  locEnd(node: ASTNode): number;
}

interface Printer {
  print(path: AstPath, options: Options, print: PrintFn): Doc;
  embed?: (path: AstPath, options: Options) => Doc | null;
}
多语言支持中最复杂的场景是嵌入式语言，例如 HTML 中嵌入 JavaScript、CSS，或 JavaScript 模板字符串中嵌入 GraphQL。Prettier 通过 embed 方法处理这种情况：当打印器遇到嵌入式语言时，它会将对应片段交给目标语言的解析器和打印器处理。


这种插件架构使得 Prettier 能够统一处理 .vue 单文件组件（HTML + JavaScript + CSS）、.mdx 文件（Markdown + JSX）等复杂的多语言混合场景。


小结
    

  • AST 格式化通过"解析 → 中间表示 → 求解输出"三阶段实现确定性格式化
    • 

  • Doc 命令系统将"可以换行的位置"与"是否换行的决策"解耦
    • 

  • 贪心算法在 group 节点做出局部最优的折叠/展开决策，保证线性性能
    • 

  • 注释处理是 AST 格式化中最复杂的部分，需要精确的位置归属逻辑
    • 

  • 插件架构通过统一的 Parser + Printer 接口支持多语言和嵌入式语言场景
    •
