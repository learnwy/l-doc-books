CI 流水线中的 Lint 集成

核心概念

CI（持续集成）流水线中的 lint 检查是代码质量的最终防线。与本地 pre-commit 检查不同，CI lint 不可绕过、针对全量代码、且在代码合并前执行。设计合理的 CI lint 策略需要在检查全面性与执行效率之间取得平衡。

GitHub Actions 实践
GitHub Actions 是最常用的 CI 平台之一。以下是一个完整的 lint 工作流配置：


name: Code Quality
on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    name: Lint & Format
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm

      - run: pnpm install --frozen-lockfile

      - name: Format Check
        run: pnpm prettier --check "src/**/*.{ts,tsx,css,json,md}"

      - name: Lint
        run: pnpm eslint . --max-warnings 0

      - name: Type Check
        run: pnpm tsc --noEmit
使用 Biome 的简化版本：


jobs:
  quality:
    name: Code Quality
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: biomejs/setup-biome@v2
      - run: biome ci .

缓存策略与性能优化
CI 中的 lint 性能优化对于大型项目至关重要。主要优化方向包括依赖缓存、增量 lint 和任务并行化。


依赖缓存：缓存 node_modules 和包管理器缓存可以显著减少安装时间：


- uses: actions/setup-node@v4
  with:
    node-version: 22
    cache: pnpm
ESLint 缓存：ESLint 支持缓存功能，跳过未变更的文件：


- name: Restore ESLint cache
  uses: actions/cache@v4
  with:
    path: .eslintcache
    key: eslint-${{ hashFiles('eslint.config.mjs') }}-${{ github.sha }}
    restore-keys: |
      eslint-${{ hashFiles('eslint.config.mjs') }}-

- run: eslint --cache --cache-location .eslintcache .
增量 Lint：只对 PR 中变更的文件运行 lint：


- name: Get changed files
  id: changed
  uses: tj-actions/changed-files@v44
  with:
    files: |
      **/*.ts
      **/*.tsx

- name: Lint changed files
  if: steps.changed.outputs.any_changed == 'true'
  run: eslint ${{ steps.changed.outputs.all_changed_files }}

多平台 CI 配置
除 GitHub Actions 外，其他 CI 平台的 lint 配置模式类似：


GitLab CI：


lint:
  stage: quality
  image: node:22
  cache:
    key: ${CI_COMMIT_REF_SLUG}
    paths:
      - node_modules/
      - .eslintcache
  script:
    - npm ci
    - npx eslint --cache .
    - npx prettier --check .
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
通用 CI 脚本：编写平台无关的 lint 脚本，在 package.json 中统一管理：


{
  "scripts": {
    "lint": "eslint .",
    "lint:fix": "eslint --fix .",
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "typecheck": "tsc --noEmit",
    "quality": "npm run format:check && npm run lint && npm run typecheck",
    "quality:ci": "biome ci ."
  }
}
这样任何 CI 平台只需调用 npm run quality 或 npm run quality:ci 即可，不需要在 CI 配置中硬编码具体的工具命令。


失败报告与开发者体验
CI lint 失败时的报告质量直接影响开发者的修复效率。


Problem Matchers：GitHub Actions 支持 Problem Matchers，可以将 lint 错误直接显示在 PR 的代码 diff 中：


{
  "problemMatcher": [
    {
      "owner": "eslint",
      "pattern": [
        {
          "regexp": "^(.+):(\\d+):(\\d+):\\s+(error|warning)\\s+(.+?)\\s+(.+)$",
          "file": 1,
          "line": 2,
          "column": 3,
          "severity": 4,
          "message": 5,
          "code": 6
        }
      ]
    }
  ]
}
Annotations：使用 GitHub Actions 的注解功能在代码行级别标记问题：


- name: Lint with annotations
  run: |
    eslint . --format @microsoft/eslint-formatter-sarif --output-file eslint.sarif
  continue-on-error: true

- uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: eslint.sarif

小结
    

  • CI lint 是代码质量的不可绕过的最终防线，与本地 pre-commit 形成两层保障
    • 

  • 性能优化的核心是缓存（依赖 + ESLint）和增量策略（只 lint 变更文件）
    • 

  • package.json scripts 作为平台无关的统一入口，避免在 CI 配置中硬编码工具命令
    • 

  • Problem Matchers 和 SARIF 报告可以在 PR diff 中直观展示 lint 问题
    • 

  • Biome 的 ci 命令是最简化的 CI lint 方案，单条命令覆盖格式化和 lint 检查
    •
