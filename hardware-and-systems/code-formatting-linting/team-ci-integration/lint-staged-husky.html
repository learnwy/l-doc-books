lint-staged 与 Husky 实战

核心概念

lint-staged 和 Husky 是前端工程化中实现提交前代码质量门禁的核心工具组合。Husky 负责管理 Git Hooks（尤其是 pre-commit 钩子），lint-staged 负责只对 Git 暂存区（staged）的文件运行 lint 和格式化命令。两者配合使得每次提交都经过自动化检查，从源头防止不合规的代码进入仓库。

Husky 配置与 Git Hooks
Husky v9 的配置流程：


npm install -D husky
npx husky init
npx husky init 会自动完成两件事：在 .husky/ 目录创建 pre-commit 脚本，并在 package.json 中添加 prepare 脚本确保团队成员 npm install 后自动激活 Hooks。


{
  "scripts": {
    "prepare": "husky"
  }
}
#!/usr/bin/env sh
# .husky/pre-commit
npx lint-staged
Husky 还支持其他 Git Hooks：


#!/usr/bin/env sh
# .husky/commit-msg
npx --no -- commitlint --edit "$1"
#!/usr/bin/env sh
# .husky/pre-push
npm run typecheck
npm run test -- --run

lint-staged 配置详解
lint-staged 的核心价值是只检查变更的文件，避免全量扫描的性能浪费。


{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix --max-warnings 0", "prettier --write"],
    "*.{css,scss}": ["prettier --write"],
    "*.{json,md,yaml}": ["prettier --write"],
    "*.{ts,tsx,js,jsx}": ["vitest related --run"]
  }
}
使用 Biome 替代 ESLint + Prettier 时的配置：


{
  "lint-staged": {
    "*.{ts,tsx,js,jsx,css,json}": ["biome check --write --no-errors-on-unmatched"]
  }
}
lint-staged 的文件匹配使用 micromatch 库，支持丰富的 glob 模式：


const lintStagedPatterns = {
  '*.ts': '匹配根目录的 .ts 文件',
  '**/*.ts': '匹配任意深度的 .ts 文件',
  'src/**/*.{ts,tsx}': '匹配 src 下的 TS/TSX',
  '!(*test).ts': '排除测试文件',
  '*.{js,mjs,cjs}': '匹配多种 JS 扩展名',
};
lint-staged 在执行修复命令后会自动将修改后的文件重新添加到暂存区。这意味着 eslint --fix 和 prettier --write 的修改会自动包含在本次提交中。


常见问题与高级配置
大文件性能问题：当暂存区包含大量文件时，lint-staged 可能变慢。可以通过 --concurrent 标志控制并发：


{
  "lint-staged": {
    "*.ts": "eslint --fix"
  }
}
部分暂存文件（Partial Staging）：当一个文件只有部分内容被暂存时（git add -p），lint-staged 会使用 stash 机制保护未暂存的更改。但 --fix 类操作可能导致冲突。


跳过 Hooks：紧急情况下可以跳过 pre-commit 检查：


git commit --no-verify -m "hotfix: urgent patch"

HUSKY=0 git commit -m "skip hooks"

函数式配置：lint-staged 支持 JavaScript 配置文件，允许根据文件路径动态生成命令：


const config = {
  '*.ts': (filenames: string[]) => {
    const files = filenames.join(' ');
    return [`eslint --fix ${files}`, `prettier --write ${files}`, `vitest related --run ${files}`];
  },
  '*.css': 'prettier --write',
};

export default config;
与 CI 的协同
lint-staged + Husky 解决的是开发者本地提交前检查，但不能替代 CI 中的完整检查。两者形成互补的质量保障体系。

本地 Hook 是"快速反馈"层，CI 是"最终防线"层。即使开发者使用 --no-verify 跳过了本地检查，CI 仍然会捕获问题并阻止合并。


小结
    

  • Husky 管理 Git Hooks 的注册和分发，lint-staged 负责筛选暂存文件并执行检查命令
    • 

  • lint-staged 只处理变更文件，避免全量扫描带来的性能浪费
    • 

  • 使用 Biome 时可以简化为单条 biome check --write 命令
    • 

  • 部分暂存文件与 --fix 操作可能产生冲突，需要注意使用场景
    • 

  • 本地 Hooks 和 CI 形成两层质量保障：本地快速反馈，CI 不可绕过的最终防线
