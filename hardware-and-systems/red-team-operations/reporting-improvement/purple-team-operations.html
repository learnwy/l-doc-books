紫队协作与对抗演练

紫队的概念与演进

紫队（Purple Team）并不是一个独立的安全团队，而是一种协作模式——红队（进攻方）和蓝队（防御方）在结构化的框架下进行实时协作，共同提升组织的安全检测和响应能力。紫色是红色与蓝色的混合，精确地表达了这一概念的内涵。

传统的安全评估模式中，红队和蓝队是对立的：红队尝试入侵，蓝队尝试阻止，双方在评估结束后交换发现。这种模式的问题在于效率低——红队可能花费大量时间在蓝队已经能检测的技术上，而那些蓝队真正存在盲区的地方可能因为时间限制未被测试到。

紫队模式解决了这个效率问题。通过红蓝队的实时交互，红队执行攻击技术后立即与蓝队确认是否被检测到，如果被检测到则快速跳过转向下一个技术；如果未被检测到，则深入分析防御缺口的根因并协助蓝队建立检测规则。

MITRE 的 Center for Threat-Informed Defense 将紫队演练定义为"基于威胁情报的协作安全验证"，强调其核心目标不是"红队赢还是蓝队赢"，而是"组织的安全能力提升了多少"。

紫队演练设计

演练模式

紫队演练按照协作紧密度可分为三种模式：

同步模式：红队和蓝队在同一房间（物理或虚拟），红队执行每个攻击技术后立即与蓝队确认检测结果。这是效率最高的模式，适合首次紫队演练或需要快速建立检测基线的场景。


异步模式：红队先独立执行完整的攻击链，在每个关键节点记录精确的时间戳和技术细节。蓝队随后基于这些时间戳检查日志和告警。这种模式保留了一定的对抗真实性，但需要更多的协调成本。


混合模式：部分技术采用同步模式（已知蓝队可能存在盲区的区域），部分技术采用异步模式（需要验证端到端检测链路的场景）。这是成熟组织最常采用的模式。

ATT&CK 技术测试用例设计
每个要测试的 ATT&CK 技术需要设计标准化的测试用例：


测试用例结构：


    

  • ATT&CK ID 与名称：如 T1059.001 PowerShell
    • 

  • 模拟方法：使用的具体工具和命令
    • 

  • 预期检测：蓝队应该看到什么告警/日志
    • 

  • 检测数据源：需要的日志来源（Windows Event Log、EDR 遥测、网络流量）
    • 

  • 判定标准：什么算"检测到"（告警产生 vs 告警准确 vs 分析师调查）
    •

检测能力评估
检测工程成熟度模型
紫队演练的一个核心产出是组织检测能力的系统化评估。可以使用以下成熟度模型：


Level 0（无检测）：没有任何日志或遥测数据覆盖该技术。红队可以无限制地使用该技术。


Level 1（被动日志）：相关日志数据存在（如 Windows Event Log、Sysmon），但没有针对性的检测规则。安全分析师只有在主动调查时才可能发现攻击证据。


Level 2（基础告警）：存在检测规则并能产生告警，但误报率高导致分析师可能忽略真实告警（"告警疲劳"）。


Level 3（精准检测）：检测规则经过调优，告警质量高（误报 <5%）。分析师能在告警的指引下快速确认安全事件。


Level 4（关联分析）：多个检测规则的告警被关联分析，生成高置信度的复合告警。例如"检测到 PowerShell 下载器执行 + LSASS 进程访问 + Kerberoasting 请求"三个事件关联为一个攻击链。


Level 5（自动响应）：检测触发自动化遏制动作（如隔离端点、封锁 IP、禁用账号），无需人工介入。


ATT&CK Navigator 可视化
使用 MITRE ATT&CK Navigator 工具创建热力图，直观展示检测覆盖率：


    

  • 为每个测试的 ATT&CK 技术标注检测成熟度等级
    • 

  • 使用颜色梯度表示覆盖程度（红色=无检测，绿色=自动响应）
    • 

  • 叠加威胁行为者的 TTPs 层，高亮显示高优先级的检测差距
    • 



这个可视化结果是紫队演练最有价值的战略产出——它让组织清楚地看到"面对特定威胁行为者，我们的防御在哪些环节最薄弱"。


检测规则开发
紫队演练中发现的检测差距需要通过开发新的检测规则来弥补。


Sigma 规则
Sigma 是安全行业的通用检测规则格式，类似于 Snort/YARA 在网络/文件领域的地位。Sigma 规则使用 YAML 格式编写，可以转换为各种 SIEM 平台（Splunk、Microsoft Sentinel、Elastic Security、QRadar）的原生查询语法。


Sigma 规则的结构：


title: LSASS Memory Dump via comsvcs.dll
status: production
description: 检测通过 comsvcs.dll MiniDump 功能转储 LSASS 进程内存
references:
  - https://attack.mitre.org/techniques/T1003/001/
logsource:
  category: process_creation
  product: windows
detection:
  selection:
    Image|endswith: '\rundll32.exe'
    CommandLine|contains|all:
      - 'comsvcs'
      - 'MiniDump'
  condition: selection
level: critical
tags:
  - attack.credential_access
  - attack.t1003.001
检测规则质量标准
高质量的检测规则应满足：


准确性：误报率低于 5%。每条规则在部署前应在历史日志上回测，确认不会产生大量误报。


覆盖性：检测技术的多种实现变体，而非只检测特定工具。例如检测 LSASS 访问不应只匹配 mimikatz.exe，而应检测任何非预期进程对 LSASS 的内存读取行为。


上下文丰富：告警应包含足够的上下文信息（源进程、目标进程、用户名、命令行参数）供分析师快速判断。


响应就绪：告警应关联到预定义的响应手册（Playbook），分析师收到告警后知道应该执行哪些调查和遏制步骤。


对抗演练框架
Tabletop Exercise（桌面推演）
桌面推演是一种低成本的对抗演练形式，参与者围坐在会议桌前，模拟讨论安全事件的响应流程，不涉及实际的技术操作。


适用场景：测试事件响应流程的完整性、评估跨部门协调能力、验证通信和升级机制、培训新加入安全团队的成员。


推演模板：


    

  1. 主持人描述攻击场景的初始阶段
    2. 

  2. 参与者讨论他们会如何响应
    3. 

  3. 主持人根据参与者的行动推进场景
    4. 

  4. 引入新的情报和攻击进展
    5. 

  5. 循环直到场景结束
    6. 

  6. 全体回顾总结改进点
    7. 



Adversary Simulation Exercise
完整的对抗模拟演练是紫队活动的最高形式：


红队执行真实攻击链：使用真实的工具和技术，模拟特定威胁行为者的完整攻击流程。


蓝队实时检测和响应：SOC 分析师在不知道红队具体行动的情况下，通过正常的安全监控流程检测和响应攻击。


白队协调观察：一个中立的"白队"（通常由安全管理层和紫队协调员组成）监督整个演练过程，确保安全边界不被逾越，并记录双方的表现。


实时评分：为每个攻击阶段和防御响应建立评分标准，量化评估攻防双方的表现。


演练后复盘
演练结束后的复盘（After Action Review, AAR）是价值转化的关键环节：


时间线重建：将红队的攻击行动和蓝队的检测/响应行动在同一时间轴上对齐，清晰展示检测延迟和响应间隔。


根因分析：对每个未检测到的攻击技术进行根因分析——是缺少数据源？缺少检测规则？规则存在但未触发？还是告警被忽略了？


改进行动计划：将所有发现转化为具体的改进行动项，指定负责人和完成时间。通常包括：新增/修改检测规则、调整日志收集策略、更新事件响应手册、开展针对性培训。

演练节奏
推荐的紫队演练频率：


    

  • 季度演练：全面的紫队演练，覆盖选定威胁行为者的完整 TTPs
    • 

  • 月度验证：使用 Atomic Red Team 或 Caldera 执行自动化检测验证
    • 

  • 持续测试：通过 BAS（Breach and Attack Simulation）平台进行日常的自动化安全验证
    • 



每次演练的结果应与历史数据对比，形成安全能力提升的趋势分析。
