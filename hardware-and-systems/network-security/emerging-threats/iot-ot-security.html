IoT/OT 网络安全

物联网与工控系统的安全格局

物联网（Internet of Things, IoT）和运营技术（Operational Technology, OT）系统正在成为网络安全领域最具挑战性的防护对象。与传统 IT 系统不同，IoT/OT 设备通常具有计算资源受限、操作系统老旧、生命周期长（10-20 年）、无法轻易打补丁等特点，使得传统的 IT 安全方法难以直接套用。

根据 NIST 和 ICS-CERT 的统计数据，2024—2025 年针对工控系统的攻击事件同比增长超过 35%。MITRE ATT&CK for ICS 框架在 2025 年更新到了 v16 版本，新增了多个针对工业协议和 PLC（可编程逻辑控制器）的攻击技术。与此同时，IoT 设备的数量在 2025 年预计超过 180 亿台，每一台联网设备都是潜在的攻击入口。

IT 与 OT 的融合（IT/OT Convergence）加剧了安全挑战。传统的 OT 网络是物理隔离的"气隙"（Air-Gap）网络，但现代工业 4.0 和数字化转型需要 OT 系统与 IT 系统互联——生产数据需要上传到云端分析、远程运维需要访问 PLC、供应链管理需要与 ERP 系统集成。这种融合打破了 OT 的物理隔离保护，使 OT 系统暴露在 IT 侧已知的网络威胁面前。

IoT 安全挑战

设备层面的安全缺陷

IoT 设备的安全问题从设计和制造阶段就已存在：

硬件资源受限：许多 IoT 设备使用低功耗微控制器（如 ESP32、STM32），只有几十 KB 的 RAM 和几百 KB 的 Flash 存储。这些设备无法运行现代的加密协议栈（TLS 1.3 需要显著的计算资源和内存）或 EDR 代理。

默认凭据：大量 IoT 设备出厂时使用相同的默认用户名/密码（admin/admin 或 root/root），且用户很少修改。Mirai 僵尸网络正是利用 60 多组默认凭据感染了数百万 IoT 设备。

固件更新困难：许多 IoT 设备缺乏安全的远程固件更新机制（OTA, Over-The-Air）。即使厂商发布了安全补丁，用户也可能因为不知道如何更新、更新可能导致设备不可用、或者设备已经超出厂商支持期限而无法更新。

不安全的通信协议：许多 IoT 设备使用明文协议通信——HTTP 而非 HTTPS、MQTT 而非 MQTTS、Telnet 而非 SSH。在工控环境中，Modbus、DNP3、OPC Classic 等传统工业协议完全没有内置的认证和加密机制。

IoT 专用安全协议

针对资源受限设备的安全通信协议：

DTLS（Datagram Transport Layer Security）是 TLS 在 UDP 上的适配版本，适用于使用 CoAP（Constrained Application Protocol）通信的 IoT 设备。DTLS 1.3 进一步减少了握手往返次数和计算开销。

OSCORE（Object Security for Constrained RESTful Environments）提供了应用层端到端加密，独立于传输层。即使中间经过代理或网关，消息内容仍然是加密的。OSCORE 使用 COSE（CBOR Object Signing and Encryption）进行加密操作，比 TLS 更轻量。

LwM2M（Lightweight Machine to Machine）是 OMA（Open Mobile Alliance）定义的设备管理协议，提供了设备注册、固件更新、远程监控等生命周期管理能力。LwM2M 内置了 DTLS 安全传输和基于 Bootstrap 的设备初始化流程。

协议 传输层 安全机制 适用场景 资源需求
TLS 1.3 TCP 完整 TLS 协议栈 资源充足的 IoT 网关 高
DTLS 1.3 UDP TLS 的 UDP 适配 CoAP 设备 中
OSCORE 应用层 COSE 端到端加密 极度受限设备 低
PSK-TLS TCP/UDP 预共享密钥 TLS 大规模部署 中-低

OT 安全架构

Purdue 模型与其现代演进

Purdue 企业参考架构（Purdue Enterprise Reference Architecture, PERA）是工控安全领域最经典的网络分层模型，将工业控制系统网络从物理过程到企业管理划分为六个层次：

  • Level 0 - 物理过程层：传感器、执行器、物理生产过程
  • Level 1 - 基本控制层：PLC、RTU（远程终端单元）、DCS（分布式控制系统）控制器
  • Level 2 - 监控层：SCADA 服务器、HMI（人机界面）、工程师工作站
  • Level 3 - 制造运营层：MES（制造执行系统）、历史数据服务器、安全管理系统
  • DMZ：IT/OT 之间的非军事区
  • Level 4/5 - 企业层：ERP、邮件、Web 服务、企业 IT 基础设施
传统 Purdue 模型假设严格的层级隔离——信息只在相邻层之间流动，跨层通信被禁止。但现代工业 IoT（IIoT）和云分析的需求打破了这一假设——Level 0/1 的传感器数据需要直接上传到云端进行 AI 分析，远程专家需要直接访问 Level 2 的 HMI 进行故障诊断。


现代 OT 安全架构在 Purdue 模型的基础上引入了以下演进：IT/OT DMZ 的强化（使用数据二极管实现单向数据流）、OT 专用的零信任网关（按应用级别授权而非网络级别）、以及 OT 安全监控（OT 专用的 NDR 和 IDS）。


工业协议安全
工业控制系统使用的协议大多设计于互联网威胁出现之前，缺乏基本的安全机制：


Modbus TCP：工业控制领域最广泛使用的协议之一。Modbus 没有认证机制——任何能与 Modbus 设备通信的主机都可以读取或写入寄存器值。攻击者如果获得了 OT 网络的访问权限，可以直接向 PLC 发送 Modbus 命令修改生产参数。


OPC UA（Unified Architecture）是 OPC Classic 的现代替代，内置了完整的安全机制——支持 X.509 证书认证、加密通信（AES-256）和细粒度的访问控制。OPC UA 是 IEC 62541 国际标准，被视为工业 4.0 的核心通信协议。


IEC 62443是工业自动化和控制系统（IACS）安全的国际标准系列，定义了安全级别（SL 1-4）和安全区域/管道（Zone/Conduit）模型。IEC 62443 要求按安全级别对 OT 网络进行分段，并在区域之间的管道上实施访问控制和流量检查。


IoT/OT 网络分段策略
网络分段是 IoT/OT 安全最关键的防御措施——将不安全的 IoT 设备和 OT 系统隔离在受控的网络区域中，防止攻击从 IT 网络蔓延到 OT 网络，或从一个受感染的 IoT 设备传播到整个网络。


IoT 设备分段
专用 IoT VLAN：将所有 IoT 设备（摄像头、打印机、智能照明、传感器等）放入专用的网络段，与员工工作站和服务器隔离。IoT VLAN 的出站流量只允许与必要的管理平台和云服务通信，禁止与内部 IT 系统直接通信。


IoT 网关：在 IoT 设备和企业网络之间部署 IoT 安全网关。网关负责设备认证、协议翻译（将不安全的工业协议封装为安全的通信）、流量过滤和异常检测。


NAC（网络访问控制）：使用 802.1X 或 NAC 系统自动识别连接到网络的 IoT 设备并将其分配到相应的安全策略组。Cisco ISE、Aruba ClearPass、Forescout 等产品可以通过设备指纹（MAC OUI、DHCP fingerprint、HTTP User-Agent）自动发现和分类 IoT 设备。


OT 网络分段
数据二极管（Data Diode / Unidirectional Gateway）是物理层面的单向数据传输设备——数据只能从 OT 网络流向 IT 网络，反向完全不可能（因为硬件上只有发送端没有接收端）。数据二极管用于关键基础设施（核电站、电网、军工设施）中 OT 到 IT 的单向数据传输。


OT 防火墙：在 IT/OT DMZ 部署 OT 专用防火墙（如 Fortinet FortiGate Rugged、Palo Alto PA-Series Rugged），支持工业协议的深度检测——能解析 Modbus、DNP3、IEC 104、OPC UA 等协议的命令级别，基于命令类型和参数值实施访问控制（如"允许读取寄存器，但禁止写入"）。


IoT/OT 安全监控
OT 专用 IDS/NDR
传统 IT IDS 无法理解工业协议，需要部署 OT 专用的安全监控工具：


Claroty（已上市公司）和 Nozomi Networks 是 OT 安全监控市场的领导者。它们通过被动监听 OT 网络流量，自动发现所有 OT 设备（PLC 型号、固件版本、网络地址），建立 OT 设备的通信基线，并检测异常行为——未授权的 PLC 编程操作、异常的 Modbus 命令序列、新出现的网络连接。


Dragos 专注于工控系统的威胁检测和响应，其 WorldView 威胁情报团队持续追踪针对工控系统的高级威胁组织（如 ELECTRUM、CHERNOVITE、VOLTZITE）。


统一 IT/OT 安全运营
随着 IT/OT 融合的深入，越来越多的组织开始建设统一的 IT/OT SOC：


将 OT 安全监控工具的告警集成到企业 SIEM/SOAR 平台中，使 SOC 分析师能够在统一的视图中同时看到 IT 和 OT 的安全事件。关键挑战在于 IT 安全团队通常不了解 OT 环境的特殊性（如 PLC 不能随意重启、OT 网络变更需要遵循严格的变更管理流程），需要跨领域培训和专门的 OT 安全分析师角色。


IoT 安全框架与标准
NIST SP 800-183（Networks of 'Things'）提供了 IoT 安全的通用框架，定义了设备层、网络层、平台层和应用层的安全要求。


ETSI EN 303 645（消费者 IoT 安全基线）定义了消费者 IoT 设备的 13 项基本安全要求，包括：不使用通用默认密码、实施漏洞披露策略、保持软件更新、安全存储凭据、安全通信等。这个标准在欧盟的 Cyber Resilience Act（CRA）中被引用，计划在 2027 年成为强制性合规要求。


IEC 62443（工业自动化安全）是 OT 安全的核心标准，涵盖通用要求（62443-1-x）、策略和程序（62443-2-x）、系统级（62443-3-x）和组件级（62443-4-x）的安全要求。越来越多的工业设备供应商在追求 IEC 62443 认证以满足客户的安全合规要求。


组织在制定 IoT/OT 安全策略时，应基于这些标准框架进行风险评估，按优先级实施安全控制。最基础的措施（设备清点、网络分段、默认密码修改、补丁管理流程）应该最先落地，高级措施（OT NDR、威胁情报集成、自动化响应）可以渐进式部署。
