端到端威胁建模实战流程

威胁建模的定位与目标

威胁建模（Threat Modeling）是在系统设计和开发过程中，系统化地识别、评估和缓解安全威胁的结构化方法。它回答四个核心问题——我们在构建什么？哪些地方可能出错？我们应该怎么做？我们做得够好吗？

威胁建模的核心价值在于"左移"（Shift Left）：在安全问题还停留在设计阶段时就发现并修复，远比在生产环境中修复漏洞成本低。根据 NIST 的研究数据，设计阶段修复安全缺陷的成本约为生产阶段的 1/30 到 1/100。

本文将 STRIDE、攻击树、PASTA 等方法论整合为一个端到端的工程流程，覆盖从启动到持续迭代的完整生命周期。

威胁建模全流程概览

阶段一：准备——明确范围与目标
确定建模范围
威胁建模的第一步是明确"分析什么"和"不分析什么"。范围过大会导致分析无法在合理时间内完成，范围过小会遗漏关键威胁。


确定范围需要回答以下问题：


    

  • 系统边界：这次建模覆盖哪些服务、组件和数据流？
    • 

  • 数据资产：系统处理哪些类型的敏感数据（PII、支付信息、商业秘密）？
    • 

  • 合规要求：系统需要满足哪些安全标准（PCI DSS、HIPAA、GDPR、等保 2.0）？
    • 

  • 威胁场景：重点关注外部攻击者、内部威胁还是供应链风险？
    • 

  • 排除项：物理安全、社会工程是否在本次建模范围内？
    •

阶段二：建模——构建系统视图
绘制数据流图
数据流图（Data Flow Diagram, DFD）是威胁建模最核心的输入产物。DFD 将系统抽象为四种基本元素：


外部实体（External Entity）：与系统交互的外部角色或系统，如用户浏览器、移动 App、第三方 API、合作伙伴系统。在 DFD 中用矩形表示。


进程（Process）：系统内部的处理逻辑，如 Web 服务器、API 网关、业务服务、消息队列消费者。在 DFD 中用圆形或圆角矩形表示。


数据存储（Data Store）：持久化数据的位置，如关系数据库、缓存（Redis）、对象存储（S3）、消息队列。在 DFD 中用平行线表示。


数据流（Data Flow）：元素之间的数据传输，标注数据类型和传输协议。在 DFD 中用箭头表示。


标注信任边界
信任边界（Trust Boundary）是 DFD 中最重要的安全分析元素。信任边界标识不同信任级别之间的分界线——跨越信任边界的每一条数据流都是需要重点分析的潜在攻击面。


典型的信任边界包括：


    

  • 互联网与内网边界：用户请求进入企业网络的入口
    • 

  • DMZ 与内部网络边界：面向公网的服务与内部服务之间
    • 

  • 服务间信任边界：不同微服务之间，尤其是跨团队维护的服务
    • 

  • 进程与数据存储边界：应用程序访问数据库时的权限边界
    • 

  • 第三方集成边界：调用外部 API 或接收外部回调时
    • 

  • 容器/Pod 边界：Kubernetes 环境中不同 namespace 或 Pod 之间
    •

阶段三：分析——识别与评估威胁
系统化威胁识别
在 DFD 和信任边界标注完成后，使用 STRIDE 方法对每个跨越信任边界的数据流和每个处理敏感数据的组件进行系统化的威胁识别。


对每个分析目标，逐一检查 STRIDE 六种威胁类型是否适用。产出的威胁条目应包含以下信息：


threat_id: TM-2025-001
title: API 网关认证绕过
category: Spoofing
target: API 网关
data_flow: 用户浏览器 → API 网关
description: |
  攻击者伪造或盗用合法用户的 JWT 令牌，
  绕过 API 网关的认证检查，以合法用户身份
  访问后端服务
impact: 高 - 可获取其他用户的敏感数据
攻击路径分析
对高影响的威胁条目，使用攻击树进行深度分析，梳理攻击者从初始入口到最终目标的完整路径。攻击路径分析的关键是识别攻击链中的关键跳跃点——这些跳跃点通常是最有效的防御部署位置。


结合 MITRE ATT&CK 框架，将抽象的威胁描述映射为具体的攻击技术。例如：


    

  • 初始访问（Initial Access）：T1190 公开应用漏洞利用
    • 

  • 凭据获取（Credential Access）：T1539 窃取 Web 会话 Cookie
    • 

  • 横向移动（Lateral Movement）：T1021 远程服务利用
    • 

  • 数据外泄（Exfiltration）：T1048 通过替代协议外泄
    • 



风险评估与排序
使用 DREAD 或组织自定义的风险评估矩阵，对每个识别出的威胁进行量化评分。评估需要综合考虑：


    

  • 可能性（Likelihood）：基于当前防护水平和已知攻击活动的利用概率
    • 

  • 影响（Impact）：数据泄露规模、业务中断时间、合规处罚金额、声誉损失
    • 

  • 暴露窗口（Exposure Window）：漏洞存在了多长时间，是否有已知的在野利用
    •

阶段四：缓解——制定与验证策略
缓解策略选择
对每个需要处理的威胁，团队有四种策略选择：


缓解（Mitigate）：实施技术控制来降低威胁的可能性或影响。这是最常见的策略，如加密、认证、访问控制、输入验证等。


转移（Transfer）：将风险转移给第三方。典型方式包括购买网络安全保险、将支付处理外包给合规的支付服务商（如使用 Stripe 而非自建支付系统）。


接受（Accept）：在风险评估后，经管理层批准，有意识地接受某些低风险或修复成本远高于潜在损失的风险。接受决策必须记录在案并定期复审。


消除（Eliminate）：通过移除引发风险的功能或组件来彻底消除威胁。例如，移除不必要的管理界面、停用已废弃的 API 端点。


缓解方案设计
每个缓解方案需要包含足够的实施细节：


mitigation_id: MIT-2025-001
threat_id: TM-2025-001
strategy: 缓解
title: 强化 API 网关令牌验证
controls:
  - type: 认证增强
    action: 实施 JWT 签名验证 + 过期检查 + 受众(aud)校验
    owner: 平台团队
    effort: 2 人天
  - type: 检测
    action: 监控异常令牌使用模式（高频刷新、跨地域使用）
    owner: 安全团队
    effort: 3 人天
  - type: 响应
    action: 自动吊销可疑令牌并触发用户重新认证
    owner: 平台团队
    effort: 1 人天
residual_risk: 低 - 攻击者需同时获取签名密钥和有效令牌
验证缓解效果
缓解方案实施后必须验证其有效性。验证手段包括：


    

  • 安全测试：针对缓解的威胁场景执行渗透测试或自动化安全扫描
    • 

  • 代码审查：安全团队审查缓解代码的实现是否正确和完整
    • 

  • 红队演练：由独立的红队尝试绕过缓解措施
    • 

  • 安全回归测试：将威胁场景转化为自动化安全测试用例，纳入 CI/CD 流水线
    • 



阶段五：持续维护——威胁模型即活文档
变更触发机制
威胁模型不是一次性的产物，它必须随系统演进而持续更新。以下变更应触发威胁模型的复审：


    

  • 架构变更：新增微服务、引入新的第三方集成、修改网络拓扑
    • 

  • 数据流变更：新增敏感数据处理、修改数据存储方案
    • 

  • 技术栈变更：升级框架版本、切换云服务商、引入新的中间件
    • 

  • 威胁情报更新：新的攻击技术出现、相关行业发生重大安全事件
    • 

  • 合规要求变化：新的法规颁布、审计发现新的合规差距
    • 



与 DevSecOps 集成
在 DevSecOps 实践中，威胁建模应该嵌入开发流程的关键节点：


需求阶段：识别安全相关需求，标记需要威胁建模的用户故事（Security User Stories）。


设计阶段：对标记的功能执行威胁建模，产出威胁清单和缓解方案。


开发阶段：开发者按照缓解方案实施安全控制，安全编码规范检查集成到 IDE 中。


CI/CD 阶段：静态应用安全测试（SAST）、动态应用安全测试（DAST）、软件成分分析（SCA）自动执行。


运行阶段：运行时应用自我保护（RASP）、安全事件监控、威胁情报驱动的持续更新。


敏捷团队中的威胁建模
在敏捷开发团队中，威胁建模需要适应迭代节奏。推荐的实践模式是"增量式威胁建模"：


Sprint 级别：在 Sprint Planning 中，由安全冠军（Security Champion）对本迭代涉及的新功能或重大变更进行快速的 15-30 分钟威胁分析。使用预定义的威胁建模问卷或 STRIDE 检查清单，识别明显的安全风险。


季度级别：每季度进行一次完整的威胁模型复审，由安全团队主导，更新系统级的 DFD 和威胁清单，重新评估风险优先级。


事件驱动：当发生安全事件或收到严重漏洞报告时，立即对相关组件进行专项威胁建模。

PASTA（Process for Attack Simulation and Threat Analysis）是七阶段的风险中心方法：定义目标 → 定义技术范围 → 分解应用 → 分析威胁 → 漏洞与弱点分析 → 攻击建模 → 风险与影响分析。PASTA 的优势是将业务影响贯穿整个分析过程，适合对风险管理有严格要求的金融和医疗行业。


VAST（Visual, Agile, and Simple Threat Modeling）为大规模敏捷组织设计，使用流程流图（Process Flow Diagram）替代传统 DFD，降低了非安全人员参与威胁建模的门槛。


方法选择决策
选择威胁建模方法时，需要考虑以下因素：


    

  • 团队安全成熟度：安全成熟度低的团队从 STRIDE 开始，积累经验后再引入 PASTA
    • 

  • 系统类型：数据密集型系统使用 LINDDUN 关注隐私；网络应用使用 STRIDE；组织级评估使用 OCTAVE
    • 

  • 开发模式：瀑布开发可以使用完整的 PASTA 七阶段；敏捷开发推荐 STRIDE + 增量式更新
    • 

  • 合规要求：需要向监管机构证明风险管理能力时，PASTA 和 OCTAVE 的文档化产出更符合审计要求
    • 



威胁建模产出物管理
一次完整的威胁建模应产出以下文档：


    

  1. 系统模型：DFD 图、信任边界标注、数据资产分类
    2. 

  2. 威胁清单：所有识别出的威胁，包含描述、分类、目标组件
    3. 

  3. 风险评估：每个威胁的量化评分和优先级排序
    4. 

  4. 缓解计划：每个需要处理的威胁的缓解方案、负责人和时间线
    5. 

  5. 残余风险报告：缓解后仍存在的风险及其接受理由
    6. 

  6. 安全测试用例：从威胁场景推导的安全测试需求
    7. 



这些产出物应该存储在团队可协作的位置（如 Wiki、Confluence 或代码仓库），并建立版本控制和变更追踪机制。威胁模型的版本应该与系统版本关联——当系统从 v2.0 升级到 v3.0 时，威胁模型也应有对应的更新。


总结
端到端的威胁建模不是一次性的安全检查活动，而是贯穿系统生命周期的持续安全实践。从明确范围、构建系统模型、系统化识别威胁、量化评估风险，到制定和验证缓解策略，最终将威胁模型作为活文档持续维护——每个阶段都有明确的输入、方法和产出。在 DevSecOps 和敏捷开发的语境下，威胁建模的关键挑战不是方法论的选择，而是如何将这些方法无缝嵌入开发团队的日常工作流程，使安全分析成为设计和开发的自然组成部分而非额外负担。
