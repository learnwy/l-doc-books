认证与授权安全机制

认证与授权的本质区别

认证（Authentication）回答的是"你是谁"——验证用户声称的身份是否真实。授权（Authorization）回答的是"你能做什么"——确定已认证的用户可以访问哪些资源、执行哪些操作。两者是完全独立的安全机制，但经常被混淆——许多安全漏洞正是因为开发者在实现认证后就认为"安全问题已解决"，而忽略了授权控制。

现代认证机制
多因素认证
多因素认证（Multi-Factor Authentication, MFA）要求用户提供至少两种不同类别的认证因子来验证身份。认证因子分为三类：知识因子（你知道的——密码、PIN）、持有因子（你拥有的——手机、硬件令牌）、固有因子（你本身的——指纹、面部识别）。


**TOTP（基于时间的一次性密码）**是最广泛的 MFA 实现方式。用户和服务端共享一个密钥种子（通常通过二维码传递），然后基于当前时间和密钥种子生成 6 位数字验证码，每 30 秒更新一次。Google Authenticator、Microsoft Authenticator 和 Authy 都实现了 TOTP 标准（RFC 6238）。


TOTP 的安全局限：TOTP 可以被网络钓鱼攻击绕过——攻击者创建假登录页面，同时捕获用户的密码和 TOTP 验证码，然后立即用于真实网站登录。这种实时中间人攻击（Real-time Phishing）在 2024—2025 年极为活跃。


WebAuthn / Passkeys是下一代认证标准，由 FIDO Alliance 和 W3C 联合制定。WebAuthn 使用公钥密码学替代共享密钥：用户设备生成一对公私钥，私钥永远不离开设备（存储在 TPM、Secure Enclave 或安全芯片中），公钥注册到服务端。认证时，服务端发送一个随机挑战（Challenge），用户设备用私钥签名后返回——服务端用公钥验证签名。


Passkeys 相比 TOTP 的核心优势是抗钓鱼：WebAuthn 协议将网站的域名绑定到凭证中（Origin Binding），即使用户被引导到钓鱼网站，私钥也不会对错误域名的挑战进行签名。Apple、Google、Microsoft 在 2024—2025 年全面推广 Passkeys——苹果的 iCloud Keychain 和 Google 的 Password Manager 都支持跨设备同步 Passkeys。

OAuth 2.0 安全设计
OAuth 2.0 是当前 Web 和移动应用最广泛使用的授权框架。它允许第三方应用在不获取用户密码的情况下访问用户在其他服务上的资源（如"使用 Google 账号登录"）。


授权码模式（Authorization Code Flow）是最安全的 OAuth 2.0 授权流程：


OAuth 2.0 常见安全陷阱：


授权码拦截攻击：在移动应用中，攻击者可以注册与合法应用相同的自定义 URL Scheme，拦截授权服务器返回的授权码。PKCE（Proof Key for Code Exchange, RFC 7636）是此攻击的标准防御措施——客户端在发起授权请求时生成一个随机的 code_verifier，发送其哈希值 code_challenge 到授权服务器；换取令牌时提交原始 code_verifier，授权服务器验证哈希匹配后才发放令牌。PKCE 现在是所有 OAuth 2.0 客户端（包括公开客户端和机密客户端）的推荐实践。


开放重定向：如果授权服务器未严格验证 redirect_uri 参数，攻击者可以将授权码重定向到自己控制的服务器。防御方法是精确匹配而非前缀匹配——redirect_uri 必须与注册时完全一致。


令牌泄露：Access Token 应该使用短生命周期（5-15 分钟），通过 Refresh Token 续期。Refresh Token 必须绑定到特定客户端，且支持旋转（每次使用 Refresh Token 时发放新的 Refresh Token 并废弃旧的）。


OpenID Connect
OpenID Connect（OIDC）是建立在 OAuth 2.0 之上的认证层。OAuth 2.0 本身是一个授权框架（发放的是访问资源的令牌），不是认证协议——它不告诉客户端用户是谁。OIDC 通过引入 ID Token（JWT 格式）来解决认证问题。


ID Token 的安全验证：客户端必须验证 ID Token 的签名（使用授权服务器的公钥）、iss（签发者）匹配预期的授权服务器、aud（受众）匹配自己的 Client ID、exp（过期时间）未过期、nonce（随机数）与请求时发送的一致（防止重放攻击）。


JWT 安全实践
JSON Web Token（JWT）是现代 Web 应用中最常用的令牌格式。JWT 由三部分组成：Header（算法和类型）、Payload（声明数据）、Signature（数字签名），用 Base64URL 编码后以 . 连接。


JWT 的安全陷阱
算法混淆攻击（Algorithm Confusion / Key Confusion）是 JWT 最知名的安全漏洞。JWT 支持多种签名算法（HS256 对称、RS256/ES256 非对称）。如果服务端的 JWT 验证库允许 Token 自身声明使用的算法，攻击者可以将算法从 RS256 改为 HS256，然后使用服务端的 RSA 公钥（公开可获取）作为 HMAC 密钥来签名——因为公钥是已知的，攻击者可以伪造任意 Token。


防御方法：永远不要信任 JWT Header 中声明的算法。服务端应该硬编码期望的算法，而不是读取 Token 的 alg 字段。


none 算法攻击：JWT 规范支持 "alg": "none" 表示不签名。如果验证库对此未做处理，攻击者可以将任意 JWT 的算法设为 none 并删除签名部分，服务端将其视为有效 Token。


JWT 不能撤销：JWT 是自包含的——服务端不需要查询数据库就能验证 Token。这意味着一旦签发，在过期之前无法撤销（除非维护黑名单）。对于安全敏感场景（如用户修改密码后应该使所有旧 Token 失效），推荐方案是短生命周期 Access Token（15 分钟）+ Refresh Token 旋转。

授权模型
RBAC：基于角色的访问控制
RBAC 将权限分配给角色，再将角色分配给用户。它是最广泛使用的授权模型，适合权限结构相对稳定的场景。


RBAC 的局限：当业务逻辑需要基于数据属性做授权决策时（如"用户只能编辑自己部门的文档"），纯 RBAC 模型不够灵活——要么创建大量细粒度角色（角色爆炸），要么在代码中硬编码业务逻辑。


ABAC：基于属性的访问控制
ABAC 根据主体属性、资源属性、动作和环境条件的组合来做出授权决策，比 RBAC 灵活得多。


ABAC 策略示例：只有满足以下所有条件时才允许访问："用户角色是经理"且"用户部门与文档所属部门相同"且"当前时间在工作日 9:00-18:00"且"用户位于公司内网"。


ABAC 的技术实现：OPA（Open Policy Agent）是最流行的开源 ABAC 引擎。应用在做授权决策时调用 OPA 的 REST API，传入请求的上下文（用户属性、资源属性、环境信息），OPA 根据 Rego 策略返回允许/拒绝决策。


ReBAC：基于关系的访问控制
ReBAC 是近年来快速兴起的授权模型，它基于实体之间的关系来做出授权决策。Google 的 Zanzibar 论文（2019 年发表）是 ReBAC 的里程碑，描述了 Google 在 Google Drive、YouTube、Google Maps 等产品中使用的统一授权系统——每天处理超过万亿次授权检查。


ReBAC 的核心思想："Alice 可以查看 Document X"这个授权决策，通过检查"Alice 是 Folder Y 的成员"且"Document X 在 Folder Y 中"来推导——而不需要显式地为 Alice 和 Document X 之间创建权限记录。


开源 ReBAC 实现包括 OpenFGA（源自 Auth0/Okta）和 SpiceDB（源自 Authzed）。

令牌存储安全
浏览器端令牌存储的安全性取决于存储位置：


HttpOnly Cookie：最安全的选择。JavaScript 无法访问（抵抗 XSS），浏览器自动在同域请求中发送（无需前端代码处理）。配合 SameSite 属性可以抵抗 CSRF。


localStorage/sessionStorage：容易被 XSS 攻击窃取——任何注入页面的恶意脚本都可以读取存储的令牌。不推荐用于存储敏感令牌。


内存变量：最安全但不持久——页面刷新后令牌丢失。适合短生命周期的 Access Token，配合 HttpOnly Cookie 中的 Refresh Token 实现无感续期。


总结
现代认证与授权安全的核心趋势是：认证从密码走向 Passkeys（无密码 + 抗钓鱼），授权从粗粒度 RBAC 走向细粒度 ABAC/ReBAC，令牌管理从长期有效的 Session ID 走向短生命周期 JWT + 安全刷新机制。无论选择哪种技术方案，核心原则不变：认证要强（多因素、抗钓鱼）、授权要细（最小权限、默认拒绝）、令牌要短（短生命周期、可撤销）、传输要密（全链路 TLS）。
