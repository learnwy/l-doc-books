软件供应链安全

供应链攻击的威胁格局

软件供应链安全已成为 2025 年网络安全领域最紧迫的议题之一。Sonatype 的 2024 年软件供应链状况报告显示，针对开源软件的供应链攻击同比增长 245%，恶意包发布总量突破 70 万个。从 2020 年的 SolarWinds 事件（通过入侵构建系统感染 18,000+ 组织）到 2024 年的 XZ Utils 后门事件（维护者社工攻击植入后门），供应链攻击的规模和精密度都在持续升级。

现代软件的供应链异常复杂。一个典型的企业应用平均依赖 500-1,000 个开源组件，每个组件又有自己的传递依赖（Transitive Dependencies）——最终的依赖树可能包含数千个组件。任何一个环节被入侵——无论是源代码仓库、构建系统、包管理器、还是分发渠道——都可能影响整条链上的所有消费者。

供应链攻击的主要类型
依赖混淆攻击
依赖混淆（Dependency Confusion）由安全研究员 Alex Birsan 在 2021 年首次公开。其原理是利用包管理器的优先级规则：大多数包管理器在私有仓库和公共仓库（npm、PyPI）同时存在同名包时，会优先安装版本号更高的那个。攻击者只需在公共仓库发布一个与目标组织内部包同名但版本号更高的恶意包，就可能被自动拉取到目标组织的构建环境中。


受影响的包管理器：npm、pip、RubyGems、Maven、NuGet 等几乎所有主流包管理器都曾受此攻击影响。


防御措施：


    

  1. 配置私有仓库代理：使用 Artifactory 或 Nexus 作为所有包的代理仓库，控制包的来源
    2. 

  2. 命名空间保护：为内部包使用组织作用域（npm 的 @org/package、Maven 的 Group ID）
    3. 

  3. 锁文件完整性：使用 package-lock.json、poetry.lock 等锁文件固定依赖版本和来源
    4. 

  4. 源仓库限制：在包管理器配置中明确指定允许的仓库源
    5. 



恶意包攻击
恶意包（Malicious Package）攻击者直接在公共包管理器上发布包含恶意代码的软件包。常见手法包括：


Typosquatting（拼写抢注）：注册与热门包名极其相似的包名（如 lodash → lodas、requests → requets），等待开发者输入错误时安装。


Starjacking：在恶意包的 package.json 或 README 中引用热门项目的 GitHub 仓库链接，伪造星标数和社区背书。


维护者劫持：通过社会工程学手段获取合法包维护者的账户（如钓鱼邮件、凭证泄露），然后在正常更新中混入恶意代码。2024 年的 XZ Utils 事件就是通过长期伪装为活跃贡献者，逐步获取维护权限后植入后门。


安装脚本攻击：利用包管理器的安装生命周期钩子（npm 的 preinstall/postinstall、pip 的 setup.py）在安装阶段执行恶意代码。


构建系统入侵
构建系统（CI/CD）是供应链攻击的高价值目标。攻击者如果能入侵构建系统，就可以在合法的构建流程中注入恶意代码——产出的制品带有官方签名，消费者几乎无法察觉。


SolarWinds 事件剖析：攻击者入侵了 SolarWinds 的构建服务器，在 Orion 产品的源代码编译过程中注入了 SUNBURST 后门。被感染的更新包通过 SolarWinds 官方渠道分发给了约 18,000 个客户，其中包括美国财政部、国土安全部等关键政府机构。


CodeCov 事件：2021 年攻击者通过 Docker 镜像构建过程中的缺陷修改了 CodeCov 的 Bash Uploader 脚本，导致使用 CodeCov 的项目的 CI 环境变量（包含 API 密钥、Token）被泄露给攻击者。


SBOM：软件物料清单
软件物料清单（Software Bill of Materials, SBOM）是软件供应链安全的基础设施——就像食品标签列出了所有成分一样，SBOM 列出了软件中包含的所有组件及其版本、许可证和来源。


SBOM 标准格式
SPDX（Software Package Data Exchange）是 Linux Foundation 的 ISO 标准（ISO/IEC 5962:2021），也是 NTIA（美国国家电信和信息管理局）推荐的 SBOM 格式。支持 JSON、RDF、XML、YAML 和 Tag-Value 五种序列化格式。


CycloneDX 是 OWASP 项目维护的 SBOM 标准，专为安全用例设计。除了组件清单外，CycloneDX 还支持漏洞信息（VEX）、服务依赖和构建环境信息。

SBOM 管理实践：


    

  1. 自动生成：在 CI/CD 构建阶段自动生成 SBOM，与构建产物一起存档
    2. 

  2. 版本关联：每个软件版本都有对应的 SBOM，SBOM 与发布产物同时签名
    3. 

  3. 持续监控：SBOM 与漏洞数据库（NVD、GitHub Advisory Database）持续比对，新漏洞发现时自动告警
    4. 

  4. 共享与交换：向客户和合作伙伴提供 SBOM，满足合规要求（美国行政命令 EO 14028 要求供应给联邦政府的软件必须提供 SBOM）
    5.

自动化依赖更新
Dependabot（GitHub 原生）和 Renovate Bot 是最流行的自动化依赖更新工具。它们监控项目的依赖清单，当发现新版本（特别是安全修复版本）时自动创建 Pull Request。


Dependabot 安全实践：


# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: 'npm'
    directory: '/'
    schedule:
      interval: 'daily'
    open-pull-requests-limit: 10
    reviewers:
      - 'security-team'
    labels:
      - 'dependencies'
      - 'security'
依赖更新的风险管理：自动更新虽然能快速修复已知漏洞，但也可能引入兼容性问题甚至恶意版本。推荐实践包括：


    

  1. 对安全更新（patch 版本）自动合并，对功能更新（minor/major 版本）人工审查
    2. 

  2. 完善的自动化测试覆盖，确保更新不破坏功能
    3. 

  3. 使用锁文件固定依赖版本，只在明确决策后更新
    4. 

  4. 监控依赖的维护状态——长期不维护的依赖本身就是安全风险
    5. 



构建系统安全
SLSA 框架
SLSA（Supply-chain Levels for Software Artifacts，读作 "salsa"）是 Google 发起的供应链安全框架，定义了四个递进的安全级别来衡量软件构建流程的可信度。

SLSA Provenance（溯源证明）是 SLSA 的核心产物——一份加密签名的声明，记录了软件是在哪里、由什么工具、从什么源代码构建的。消费者通过验证 Provenance 来确认软件的构建过程是否可信。

构建安全加固
不可变构建环境：使用一次性的构建容器或虚拟机，每次构建后销毁。这防止了攻击者在构建环境中植入持久化后门。GitHub Actions 的 ubuntu-latest runner 和 Google Cloud Build 的构建步骤都是不可变的。


可复现构建（Reproducible Builds）：给定相同的源代码、依赖和构建环境，能产出完全相同（bit-for-bit）的构建产物。可复现构建允许独立方验证构建产物是否确实来自声称的源代码——如果两个独立的构建环境产出相同的产物，就可以高置信度地排除构建系统被篡改的可能性。Debian、F-Droid 和 Tor Browser 都在推进可复现构建。


构建凭证隔离：CI/CD 系统中的密钥和令牌必须严格隔离，不能被构建脚本直接访问。推荐使用短生命周期的 OIDC 令牌替代长期有效的 Service Account Key——GitHub Actions 的 OIDC Token 和 Google Cloud Workload Identity Federation 是实现这一目标的最佳实践。


包管理器安全
npm 安全实践
npm 生态系统是供应链攻击最频繁的目标（超过 200 万个公共包）。


关键安全措施：


    

  1. 锁文件固定：始终提交 package-lock.json，使用 npm ci（而非 npm install）确保依赖版本精确匹配
    2. 

  2. 审计命令：定期运行 npm audit，CI/CD 中使用 npm audit --audit-level=high 作为门控
    3. 

  3. 忽略脚本：在 CI/CD 中使用 --ignore-scripts 禁止安装脚本执行（如果项目允许）
    4. 

  4. 包签名验证：npm 从 2023 年开始支持包签名（Registry Signatures），通过 npm audit signatures 验证
    5. 

  5. Provenance：npm 支持在 GitHub Actions 中自动生成 SLSA Provenance
    6. 



容器镜像供应链
容器镜像的供应链安全需要从基础镜像到最终部署的每一层都有保障：


    

  1. 基础镜像来源：只使用官方维护的基础镜像（Docker Official Images、Chainguard Images）
    2. 

  2. 镜像签名：使用 Cosign 签名所有构建产物，Kubernetes 准入控制器验证签名
    3. 

  3. 镜像扫描：在 CI/CD 和运行时持续扫描镜像漏洞
    4. 

  4. 镜像固定：使用 digest（image@sha256:...）而非 tag（image:latest）引用镜像
    5. 



总结
软件供应链安全是一个系统工程，需要在开发、构建、分发和运行的每个环节建立安全控制。核心实践包括：SBOM 管理提供完整的组件可见性、SCA 工具持续监控依赖漏洞、SLSA 框架保障构建完整性、包管理器安全配置防止依赖混淆和恶意包、以及构建系统加固防止源头投毒。在 2025—2026 年的威胁环境下，忽视供应链安全不是"可能被攻击"的问题，而是"何时被攻击"的问题——每个组织都应该将供应链安全纳入其安全战略的核心位置。
