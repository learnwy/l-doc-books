SAST 与 DAST 工具实践

应用安全测试的两大方法论

应用安全测试的核心方法论分为两大类：静态应用安全测试（Static Application Security Testing, SAST）和动态应用安全测试（Dynamic Application Security Testing, DAST）。两者从不同的视角发现安全漏洞——SAST 从内部（白盒）检查源代码，DAST 从外部（黑盒）检查运行中的应用。它们各有优劣，互为补充，共同构成应用安全验证的基础。

SAST 深度解析
工作原理
SAST 工具在不执行代码的情况下分析源代码（或编译后的字节码/二进制文件），通过构建代码的抽象表示（抽象语法树 AST、控制流图 CFG、数据流图 DFG）来识别安全漏洞。


污点分析（Taint Analysis）是 SAST 最核心的检测技术。它追踪数据从输入源（Source，如 HTTP 请求参数、数据库查询结果）到危险操作（Sink，如 SQL 执行、命令执行、HTML 输出）的流动路径。如果污染数据在到达 Sink 之前没有经过适当的清理（Sanitizer），就报告为潜在漏洞。


Source（污点源）        →  Sanitizer（清理函数）  →  Sink（危险操作）
request.getParameter() →  escape() / encode()    →  response.write()
                       →  parameterized query     →  db.query()
                       →  (无清理 = 漏洞!)         →  Runtime.exec()
语义分析是高级 SAST 工具的差异化能力。简单的模式匹配只能发现固定模式的漏洞（如直接使用 eval()），而语义分析能理解代码的逻辑含义——例如，识别出一个看似安全的自定义验证函数实际上存在绕过条件。GitHub 的 CodeQL 就是基于语义分析的典型代表，它将代码转化为可查询的数据库，安全研究人员可以编写查询来发现复杂的漏洞模式。

Semgrep 在 2024—2025 年快速崛起，成为最受开发者欢迎的 SAST 工具之一。其核心优势是规则编写的简洁性——规则使用与目标代码相似的语法（而非复杂的 DSL），开发者可以在几分钟内编写自定义安全规则。


# Semgrep 规则示例: 检测 SQL 注入
rules:
  - id: sql-injection
    patterns:
      - pattern: |
          $QUERY = "..." + $INPUT + "..."
          ...
          $DB.execute($QUERY)
    message: 潜在的 SQL 注入漏洞,请使用参数化查询
    severity: ERROR
    languages: [python]
CodeQL 的核心优势是其查询能力——安全研究人员可以用类似 SQL 的语言查询代码库中的漏洞模式。GitHub 利用 CodeQL 发现了 Log4Shell 变种和大量开源项目中的零日漏洞。


SAST 实施挑战
误报管理是 SAST 实施的最大挑战。行业数据表明，SAST 工具的误报率通常在 30%—60% 之间，这意味着开发者可能花大量时间审查实际上不是漏洞的报告。


降低误报的策略：


    

  1. 渐进式启用规则：从高置信度规则开始（如 SQL 注入、命令注入），逐步添加更多规则
    2. 

  2. 自定义规则调优：根据项目的技术栈和框架特性调整规则（例如，如果项目使用 ORM，可以降低 SQL 注入规则的敏感度）
    3. 

  3. Baseline 机制：首次扫描时将所有现有发现标记为基线，后续只关注新增发现
    4. 

  4. 误报反馈循环：建立开发者标记误报 → 安全团队审查 → 调整规则的闭环流程
    5. 



语言和框架支持：不同 SAST 工具对不同语言和框架的支持深度不同。选型时需要验证工具是否理解项目使用的框架的安全特性——例如，能否识别 Spring Security 的 @PreAuthorize 注解等价于一个授权检查点。


DAST 深度解析
工作原理
DAST 工具模拟外部攻击者的行为，通过发送精心构造的 HTTP 请求来探测运行中应用的安全漏洞。典型的 DAST 扫描流程包括：


    

  1. 爬虫阶段：自动遍历应用的所有页面和端点，构建应用地图
    2. 

  2. 攻击阶段：对发现的每个输入点（表单字段、URL 参数、HTTP 头部、Cookie）发送攻击载荷
    3. 

  3. 分析阶段：分析应用的响应，判断攻击是否成功（如 SQL 错误信息、反射的 XSS 载荷、延迟响应表示盲注入成功）
    4. 



OWASP ZAP 实战
OWASP ZAP（Zed Attack Proxy）是最广泛使用的开源 DAST 工具，由 OWASP 社区维护。


ZAP 的核心扫描模式：


被动扫描：只分析正常浏览产生的 HTTP 流量，不发送额外的攻击请求。检测项包括：缺失的安全头部、Cookie 安全属性、信息泄露（服务器版本、堆栈跟踪）、过时的 JavaScript 库。被动扫描零风险，适合在所有环境运行。


主动扫描：对目标应用发送大量攻击载荷，检测 SQL 注入、XSS、SSRF、路径遍历等漏洞。主动扫描可能触发大量请求（数万到数十万个），可能导致应用崩溃或数据变更——只应在测试环境运行。


API 扫描：通过导入 OpenAPI/Swagger 规范文件，ZAP 可以自动生成针对每个 API 端点的测试请求，无需手动配置。


# ZAP Docker 模式运行 API 扫描
docker run -t ghcr.io/zaproxy/zaproxy:stable zap-api-scan.py \
  -t https://api.example.com/openapi.json \
  -f openapi \
  -r report.html \
  -c zap-config.conf
Nuclei 模板化扫描
Nuclei 是近年来快速流行的开源漏洞扫描器，其核心创新是基于 YAML 模板的扫描——每个漏洞检测逻辑都封装在一个 YAML 模板中，社区贡献了超过 8,000 个模板，覆盖 CVE 漏洞、安全配置错误、暴露的面板、默认密码等。


# Nuclei 模板示例: 检测 Spring Actuator 暴露
id: spring-actuator-exposed
info:
  name: Spring Boot Actuator 端点暴露
  severity: high

http:
  - method: GET
    path:
      - '{{BaseURL}}/actuator/env'
      - '{{BaseURL}}/actuator/health'
    matchers:
      - type: word
        words:
          - 'spring.datasource'
          - 'spring.mail'
        condition: or
      - type: status
        status:
          - 200

最佳实践是 SAST + DAST 组合使用：在 CI 阶段运行 SAST 发现代码级漏洞（早期发现、精准定位），在测试阶段运行 DAST 发现运行时漏洞（零误报、验证防御有效性）。对于追求更高覆盖率的团队，还可以加入 IAST（在功能测试运行时进行安全分析，结合两者优势）。


安全测试结果管理
漏洞分级与优先级
安全测试工具通常使用 CVSS（Common Vulnerability Scoring System）对发现的漏洞进行评分。但 CVSS 分数不应是漏洞修复优先级的唯一依据——还需要考虑：


业务影响：一个影响支付系统的中等级漏洞可能比影响内部工具的严重级漏洞优先级更高。


可利用性：需要复杂前置条件的漏洞（如需要管理员权限 + 内网访问）比公开可利用的漏洞优先级低。


暴露面：面向互联网的应用中的漏洞比仅在内网可访问的应用中的漏洞风险更高。

总结
SAST 和 DAST 是应用安全测试的两大基石。SAST 在开发早期发现代码级漏洞，提供精准的修复指导；DAST 在测试阶段验证应用的实际安全性，发现运行时配置和逻辑漏洞。两者结合使用，配合有效的漏洞管理流程和持续度量，构成了应用安全验证的完整体系。在工具选型上，开源方案（Semgrep + ZAP + Nuclei）已经能满足大部分团队的需求，商业方案（Checkmarx + Invicti）则在深度分析和企业级管理能力上更具优势。
