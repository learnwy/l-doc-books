API 安全设计模式

API 安全的战略重要性

API（Application Programming Interface）已成为现代软件架构的核心连接组织。Gartner 预测到 2026 年超过 90% 的 Web 应用将通过 API 暴露更多的攻击面。Akamai 的 2025 年互联网安全报告显示，API 攻击流量同比增长 109%，API 已超越传统 Web 页面成为最主要的攻击目标。

API 安全面临的挑战与传统 Web 应用有本质区别：API 通常没有浏览器的安全机制保护（CSP、SameSite Cookie 等）；API 暴露的是结构化数据和业务逻辑，攻击者可以更精准地利用；微服务架构下 API 数量爆发式增长（大型企业通常有数千个内部 API），安全治理的复杂度远超单体应用。

OWASP API Security Top 10

OWASP 在 2023 年发布了 API Security Top 10 的更新版，专门针对 API 场景的安全风险：

排名 风险类别 核心问题
API1 对象级授权失效 未验证用户对特定对象的访问权限
API2 认证失效 认证机制实现不当
API3 对象属性级授权失效 返回了用户无权查看的属性字段
API4 不受限的资源消耗 缺乏速率限制和资源配额
API5 功能级授权失效 未验证用户对特定 API 端点的访问权限
API6 对敏感业务流的不受限访问 业务逻辑缺乏防滥用机制
API7 服务端请求伪造 API 发起的服务端请求未经安全验证
API8 安全配置错误 默认配置不安全、缺少安全头部
API9 资产管理不当 影子 API、未退役的旧版本 API
API10 不安全的 API 消费 盲目信任第三方 API 的响应数据

RESTful API 安全设计

认证与鉴权

API 密钥（API Key）是最简单的认证方式，但安全性最弱——API Key 通常是长期有效的静态字符串，泄露后难以追踪是哪个客户端泄露的。API Key 适合用于识别调用方身份（用于速率限制和计费），但不应作为唯一的认证手段。

OAuth 2.0 Client Credentials是服务间（Machine-to-Machine）认证的推荐方案。调用方使用 Client ID 和 Client Secret 向认证服务器请求 Access Token，然后在 API 请求中携带 Token。Token 具有有限的生命周期和范围（Scope），比 API Key 更安全。

JWT Bearer Token是用户级 API 认证的主流方案。客户端在用户登录后获取 JWT，后续 API 请求在 Authorization: Bearer <token> 头部中携带。服务端通过验证 JWT 签名和声明来确认请求者身份。

输入验证与数据脱敏
严格的请求验证是 API 安全的第一道防线。对于 RESTful API：


    

  1. 路径参数：验证类型和格式（UUID、数字 ID 等），拒绝包含路径遍历字符（../）的值
    2. 

  2. 查询参数：验证类型、范围和长度，使用白名单限制允许的参数名
    3. 

  3. 请求体：使用 JSON Schema 或类型系统严格验证请求体的结构和类型
    4. 

  4. Content-Type：验证 Content-Type 头部与实际请求体格式一致
    5. 

  5. 请求大小：限制请求体大小，防止大载荷 DoS
    6. 



响应数据脱敏：API 响应只应包含调用方需要和有权查看的字段——这是 OWASP API3（对象属性级授权失效）的核心防御。


// 管理员视角的用户信息
{
  "id": "u_12345",
  "name": "张三",
  "email": "zhangsan@company.com",
  "phone": "138****5678",
  "role": "editor",
  "salary": 25000,
  "created_at": "2024-01-15"
}

// 普通用户视角（脱敏后）
{
  "id": "u_12345",
  "name": "张三",
  "role": "editor"
}

速率限制（Rate Limiting）是防御 API 滥用、暴力破解和 DoS 攻击的关键机制。

分层限流策略：


    

  1. 全局限流：保护 API 网关和后端服务的总体处理能力
    2. 

  2. 用户级限流：限制单个用户的请求频率（如每分钟 100 次）
    3. 

  3. IP 级限流：防御来自单一 IP 的暴力攻击
    4. 

  4. 端点级限流：敏感端点（如登录、密码重置）设置更严格的限流
    5. 



限流响应：当请求被限流时，返回 HTTP 429（Too Many Requests）状态码，并在响应头中包含限流信息：


HTTP/1.1 429 Too Many Requests
Retry-After: 60
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1640000000
GraphQL 安全
GraphQL 的灵活查询能力在给开发者带来便利的同时，也引入了独特的安全挑战。


GraphQL 特有风险
查询深度攻击：GraphQL 允许嵌套查询，攻击者可以构造极深的嵌套查询来耗尽服务端资源。


# 恶意深度嵌套查询
query {
  user(id: "1") {
    friends {
      friends {
        friends {
          friends {
            # 无限嵌套...
          }
        }
      }
    }
  }
}
防御：设置查询最大深度限制（通常 7-10 层）、查询复杂度预算（根据字段类型赋予不同的复杂度分数，总分超过预算则拒绝）。


批量查询攻击：利用 GraphQL 的批量查询能力，在单个请求中发送大量操作。


防御：限制单次请求中的操作数量、限制查询复杂度。


内省泄露：GraphQL 的内省（Introspection）功能允许客户端查询完整的 Schema 定义。在生产环境中如果未禁用，攻击者可以通过内省了解所有 API 字段、类型和关系——等于公开了完整的 API 蓝图。


防御：在生产环境禁用内省功能，或限制只有认证用户才能执行内省查询。


API 网关安全
API 网关（如 Kong、Envoy、AWS API Gateway、APISIX）是 API 安全架构的核心组件，作为所有 API 请求的统一入口，承担认证、鉴权、限流、日志和安全防护等职责。


API 网关的安全职责：


    

  1. 统一认证：在网关层完成 Token 验证，后端微服务只需信任网关传递的已验证身份信息
    2. 

  2. TLS 终结：在网关层终结外部 TLS 连接，内部微服务间可使用 mTLS 或明文通信
    3. 

  3. 请求转换：剥离客户端不应传递的头部（如 X-Forwarded-For 欺骗）
    4. 

  4. 流量监控：记录所有 API 调用的详细信息，为安全审计和异常检测提供数据
    5. 



API 资产管理
OWASP API9（资产管理不当）强调了"影子 API"的风险——未被正式记录和管理的 API 端点。企业中通常存在大量影子 API：测试环境遗留的调试接口、已弃用但未下线的旧版本 API、开发者个人部署的临时服务。


API 资产管理实践：


    

  1. API 注册中心：所有 API 必须在注册中心登记，包括端点、版本、所有者和生命周期状态
    2. 

  2. 自动发现：使用 API 发现工具（如 Traceable AI、Salt Security）通过流量分析自动发现未登记的 API
    3. 

  3. 版本管理：使用 URL 路径版本控制（/v1/、/v2/），旧版本设置废弃通知和下线日期
    4. 

  4. API 生命周期：定义从创建、发布、废弃到退役的完整生命周期，退役 API 的流量应返回 410 Gone
    5. 



微服务间通信安全
服务间认证
在微服务架构中，服务间通信（East-West Traffic）的安全同样重要。如果内部网络被攻破，缺乏服务间认证意味着攻击者可以伪造任何微服务的身份来调用其他服务。


**mTLS（双向 TLS）**是服务间认证的推荐方案。每个微服务都有自己的 TLS 证书，通信双方互相验证对方的证书。Service Mesh（如 Istio、Linkerd）可以自动化 mTLS 的证书管理和轮换——开发者不需要修改应用代码，Sidecar 代理自动处理所有 TLS 握手。


**SPIFFE（Secure Production Identity Framework For Everyone）**提供了统一的服务身份标准。每个服务获得一个 SPIFFE ID（格式为 spiffe://trust-domain/path），通过 X.509 证书或 JWT 携带。SPIRE（SPIFFE Runtime Environment）是其开源实现，与 Kubernetes、Envoy 等深度集成。


零信任网络
零信任原则在 API 安全中的体现是：不因为请求来自内部网络就信任它。每个 API 请求，无论来自外部还是内部，都必须经过认证、授权和输入验证。


零信任 API 安全架构的核心要素：验证每个请求的身份（mTLS + JWT）、最小权限访问（每个服务只能访问它需要的 API）、持续监控（所有 API 调用日志集中分析）、微分段（网络策略限制服务间的通信路径）。


总结
API 安全不是一个单一的技术问题，而是一个需要在设计、开发、部署和运维全链路考虑的系统工程。核心原则包括：认证和授权不可缺少（OAuth 2.0 + JWT）、输入必须严格验证（JSON Schema）、输出必须按权限脱敏、速率限制必须分层部署、API 资产必须全面管理。在微服务和云原生架构下，API 网关 + Service Mesh 的组合提供了从外部到内部的全链路 API 安全保障。
