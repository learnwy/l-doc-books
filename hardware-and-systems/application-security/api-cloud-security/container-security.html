容器安全与镜像加固

容器安全的全景视图

容器技术（以 Docker 和 Kubernetes 为代表）已成为现代应用部署的标准范式。Datadog 的 2025 年容器报告显示，超过 78% 的企业在生产环境中使用容器，Kubernetes 集群的平均规模达到 200+ 节点。然而，容器的安全挑战也随之放大：Sysdig 的 2025 年云原生安全报告指出，87% 的容器镜像包含高危或严重漏洞，超过 65% 的容器以 root 用户运行。

容器安全需要覆盖完整的生命周期：构建时（镜像安全）、部署时（编排安全）和运行时（运行时防护）。

容器镜像安全
基础镜像选择
基础镜像的选择直接决定了容器的攻击面大小。一个完整的 Ubuntu 镜像包含数百个软件包，其中许多对应用运行毫无必要——但每个额外的包都可能引入已知漏洞。

Google Distroless 镜像是 2025 年的推荐选择。Distroless 镜像只包含应用及其运行时依赖——没有包管理器、没有 Shell、没有任何不必要的工具。这意味着即使攻击者突破了应用，也无法在容器内执行 Shell 命令或安装工具，极大地限制了攻击者的后续操作能力。


镜像构建安全实践
多阶段构建（Multi-stage Build）将编译环境和运行环境分离，确保最终镜像中不包含编译工具、源代码、测试数据和构建凭证。


# 构建阶段
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server

# 运行阶段（最小化镜像）
FROM gcr.io/distroless/static:nonroot
COPY --from=builder /app/server /server
USER nonroot:nonroot
ENTRYPOINT ["/server"]
镜像层优化安全：每个 Dockerfile 指令创建一个层，即使后续层删除了文件，前面层中的文件仍然存在。这意味着如果在某一层中临时添加了密钥文件，即使后续层执行了 rm 删除，攻击者仍然可以通过检查历史层恢复该文件。解决方案是使用多阶段构建或 --squash 标志合并层。


扫描与签名流程：


    

  1. 构建后立即扫描：使用 Trivy、Grype 或 Snyk 扫描镜像中的操作系统和应用层漏洞
    2. 

  2. 设置阻断策略：存在严重（Critical）漏洞时阻止镜像推送到生产仓库
    3. 

  3. 数字签名：使用 Cosign 对通过扫描的镜像签名
    4. 

  4. 签名验证：Kubernetes 准入控制器验证镜像签名后才允许部署
    5. 



镜像仓库安全
私有镜像仓库（Harbor、AWS ECR、Google Artifact Registry）应该启用以下安全特性：


    

  1. 自动漏洞扫描：镜像推送时自动触发漏洞扫描
    2. 

  2. 内容信任（Content Trust / Notary）：使用数字签名确保镜像完整性
    3. 

  3. 访问控制：基于角色限制镜像的推送和拉取权限
    4. 

  4. 镜像保留策略：自动清理过期镜像，减少攻击面
    5. 

  5. 审计日志：记录所有镜像操作（推送、拉取、删除）
    6. 



Kubernetes 安全
Pod 安全标准
Kubernetes 1.25 正式移除了 PodSecurityPolicy（PSP），替代方案是 Pod Security Standards（PSS）和 Pod Security Admission（PSA）。PSS 定义了三个安全级别：


Privileged（特权）：不做任何限制，仅用于系统级工作负载。


Baseline（基线）：阻止已知的权限提升向量，允许大部分工作负载在不修改的情况下运行。限制包括：禁止特权容器、禁止 hostNetwork/hostPID/hostIPC、限制可添加的 Linux Capabilities、禁止 hostPath 挂载等。


Restricted（限制）：最严格的安全策略，要求容器以非 root 用户运行、只读根文件系统、删除所有 Capabilities、禁止权限提升。


# Namespace 级别启用 Restricted 策略
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
Security Context 配置
Security Context 是 Kubernetes 中控制容器安全属性的核心机制：


apiVersion: v1
kind: Pod
metadata:
  name: secure-app
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: myapp:latest
      securityContext:
        runAsUser: 1000
        runAsGroup: 1000
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop:
            - ALL
      resources:
        limits:
          cpu: '500m'
          memory: '256Mi'
        requests:
          cpu: '100m'
          memory: '128Mi'

网络策略
Kubernetes NetworkPolicy 实现 Pod 级别的网络分段。默认情况下，Kubernetes 集群中所有 Pod 可以互相通信——这意味着一个被入侵的 Pod 可以直接访问集群中的任何其他服务。


# 只允许来自特定标签 Pod 的流量
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-frontend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
网络策略最佳实践：


    

  1. 默认拒绝：为每个 Namespace 创建默认拒绝所有入站和出站流量的策略
    2. 

  2. 最小权限：只允许已知的、必要的通信路径
    3. 

  3. Namespace 隔离：不同环境（dev/staging/prod）使用不同 Namespace 并互相隔离
    4. 

  4. 出站控制：限制 Pod 对外部网络的访问，防止数据泄露和 C2 通信
    5. 



RBAC 与 ServiceAccount
Kubernetes RBAC 控制谁可以对集群中的哪些资源执行哪些操作。常见安全问题包括：


过度权限的 ServiceAccount：许多应用 Pod 使用默认 ServiceAccount，可能被授予了不必要的集群权限。最佳实践是为每个应用创建专用 ServiceAccount，并只授予必要的最小权限。


避免 ClusterRoleBinding：优先使用 Namespace 级别的 RoleBinding，只有真正需要跨 Namespace 操作的组件才使用 ClusterRoleBinding。


运行时安全
容器运行时防护
运行时安全工具监控容器内的行为，检测异常活动并自动响应。


Falco（CNCF 孵化项目）是最广泛使用的开源容器运行时安全工具。它通过 eBPF 探针监控内核级事件（系统调用、文件操作、网络连接），使用规则引擎检测异常行为：


    

  • 容器内执行 Shell 命令
    • 

  • 读取敏感文件（/etc/shadow、/etc/passwd）
    • 

  • 异常网络连接（连接到已知恶意 IP）
    • 

  • 容器内安装软件包
    • 

  • 权限提升操作
    • 



Seccomp 和 AppArmor
Seccomp（Secure Computing Mode）限制容器可以执行的系统调用。大部分容器只需要 50-100 个系统调用，但默认可以调用全部 300+ 个——每个不必要的系统调用都是潜在的攻击面。Kubernetes 1.27+ 默认为所有 Pod 启用 RuntimeDefault Seccomp Profile。


AppArmor 提供更细粒度的进程权限控制，包括文件访问、网络操作和 Capability 使用。Docker 和 Kubernetes 都支持为容器指定 AppArmor Profile。


总结
容器安全是一个纵深防御的系统工程。从构建时的镜像加固（最小基础镜像 + 漏洞扫描 + 数字签名），到部署时的安全配置（非 root 运行 + 只读文件系统 + 网络策略 + RBAC），再到运行时的行为监控（Falco + Seccomp + AppArmor），每一层都在缩小攻击面和检测异常行为。在 2025—2026 年的云原生安全实践中，"Distroless 镜像 + Pod Security Restricted + 默认拒绝网络策略 + Falco 运行时监控"构成了容器安全的推荐基线。
