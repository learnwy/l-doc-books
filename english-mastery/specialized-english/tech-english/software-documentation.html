软件文档英语

核心概念

软件文档（Software Documentation）是软件产品的重要组成部分，涵盖从需求规格说明到用户指南的各类技术文本。在全球化开发环境中，英文文档是事实上的标准（de facto standard），无论是开源项目的 README、API 参考文档还是内部技术规范，都需要使用清晰、规范的英文撰写。软件文档英语具有精确性（precision）、一致性（consistency）和可操作性（actionability）三大特征。

不同类型的文档面向不同受众，使用不同的语言风格和术语密度。理解文档类型的分类和各自的写作要求，是撰写高质量技术文档的前提。

API 参考文档写作
API 参考文档（API Reference）是开发者日常最频繁查阅的文档类型，它要求极高的精确性和一致性。优秀的 API 文档遵循固定的结构模式。


端点描述（Endpoint Description）通常包含以下要素：HTTP method（GET/POST/PUT/DELETE）、path（路径）、summary（简述）、description（详细描述）、parameters（参数）、request body（请求体）、responses（响应）和 examples（示例）。

动词选择在 API 文档中至关重要。描述功能时优先使用主动语态和简明动词：用 "Returns the user object" 而不是 "The user object is returned"；用 "Creates a new resource" 而不是 "A new resource will be created"。常用的文档动词包括 retrieve（检索）、create（创建）、update（更新）、delete（删除）、list（列举）、validate（验证）、authenticate（认证）。


状态码描述是 API 文档的关键部分。200 OK — "The request was successful"；201 Created — "The resource was successfully created"；400 Bad Request — "The request body is invalid or missing required fields"；401 Unauthorized — "Authentication credentials are missing or invalid"；404 Not Found — "The requested resource does not exist"；500 Internal Server Error — "An unexpected error occurred on the server"。


示例代码（Code Examples）应覆盖成功和失败场景。Request 示例展示正确的调用方式，response 示例展示返回数据的完整结构。使用 cURL、JavaScript fetch 或特定 SDK 的示例能帮助开发者快速上手。


README 与项目文档
README 文件是开源项目的门面，也是项目文档的入口。一个完整的 README 通常包含以下章节：


Project Title & Description — 项目名称和一句话描述，回答 "What does this project do?"。使用 badge（徽章）展示构建状态、版本号和许可证信息。


Installation — 安装说明，使用祈使句（imperative mood）：


标准表达模式："Run npm install package-name to install the package." 或 "Install the dependency by running:" 后跟命令行示例。注意使用 "Run"、"Install"、"Clone"、"Configure" 等祈使动词开头。


Usage — 使用方法，展示最小可运行示例（minimal working example）。"Import the module and call the init function:" 是典型的引导句式。


Configuration — 配置说明，通常以表格形式列出配置项。"The following options are available:" 或 "You can customize the behavior by passing an options object:" 是常用的引入句。


Contributing — 贡献指南，说明如何提交 Issue 和 Pull Request。"We welcome contributions! Please read our contributing guide before submitting a PR." 是标准表达。


Changelog / Release Notes 记录版本变更历史。遵循 Keep a Changelog 格式，每个版本下分为 Added（新增）、Changed（变更）、Deprecated（废弃）、Removed（移除）、Fixed（修复）和 Security（安全）六个类别。使用过去时或现在完成时："Added support for TypeScript 5.0"、"Fixed a memory leak in the connection pool"。


需求与设计文档
需求规格说明书（Software Requirements Specification，SRS）和设计文档（Design Document）是企业级软件开发中的核心文档。


需求文档使用高度形式化的语言。核心关键词遵循 RFC 2119 标准：






关键词
含义
使用场景





MUST / SHALL
必须，强制性要求
"The system shall validate all user inputs."




SHOULD
应该，推荐性要求
"The API should return results within 200ms."




MAY
可以，可选性要求
"The client may cache responses for up to 5 minutes."




MUST NOT / SHALL NOT
禁止
"The system must not store passwords in plain text."




SHOULD NOT
不建议
"Error messages should not expose internal details."





功能需求（Functional Requirements）描述系统"做什么"：用 "The system shall..." 句式。非功能需求（Non-Functional Requirements）描述系统的质量属性：性能（performance）、可用性（availability）、可扩展性（scalability）、安全性（security）和可维护性（maintainability）。


设计文档（Design Document，又称 Design Doc 或 Technical Design Document）的标准结构包括：


    

  • Overview — 问题背景和设计目标："This document describes the design of..."
    • 

  • Goals and Non-Goals — 明确范围："A goal of this design is to... A non-goal is to..."
    • 

  • Proposed Design — 核心方案："The proposed approach is to..."
    • 

  • Alternatives Considered — 备选方案："We also considered... but rejected it because..."
    • 

  • Trade-offs — 权衡取舍："The main trade-off is between X and Y."
    • 

  • Timeline — 实施计划："The estimated timeline for implementation is..."
    • 



错误消息与日志文档
错误消息（Error Messages）和日志（Logs）是一种特殊的技术文档，面向的读者包括最终用户和运维工程师。


用户侧错误消息应当遵循三条原则：说明发生了什么（what happened）、解释为什么发生（why）、建议如何修复（how to fix）。


优秀示例："Unable to save your changes. The file size exceeds the maximum limit of 10MB. Please reduce the file size and try again."


劣质示例："Error 500: Internal Server Error" — 既没有解释原因，也没有提供修复建议。






消息质量
特征
示例





优秀
具体、可操作、用户友好
"Your password must contain at least 8 characters."




一般
描述了问题但缺乏指导
"Invalid password format."




差
模糊、技术化、无帮助
"Validation error."





日志消息面向开发者和运维人员，使用结构化格式。标准日志级别包括：DEBUG（调试信息）、INFO（常规操作记录）、WARN（潜在问题警告）、ERROR（错误但可恢复）和 FATAL（致命错误，系统需要终止）。


日志消息的英文写作要点：使用过去时记录已发生的事件（"Request processed successfully"）；包含上下文信息（"Failed to connect to database at host:port"）；避免敏感信息泄露（永远不要记录密码、token 等）。


故障排查文档（Troubleshooting Guide）采用问题-原因-解决方案的固定结构：


    

  • Symptom（症状）— "You see the error message: ..."
    • 

  • Cause（原因）— "This usually happens when..."
    • 

  • Resolution（解决方案）— "To resolve this issue, follow these steps: ..."
    • 

  • Prevention（预防）— "To prevent this from happening, ensure that..."
    • 



文档语言风格指南
技术文档有一套独特的英文写作风格规范，掌握这些规范能显著提升文档的专业度和可读性。


语态选择：优先使用主动语态（active voice）。"The function validates the input" 优于 "The input is validated by the function"。被动语态仅在动作执行者不重要或需要强调结果时使用："All data is encrypted at rest."


时态选择：描述系统行为使用一般现在时（"The API returns a JSON object"）；描述用户操作使用祈使句（"Click the Submit button"）；描述过去的变更使用过去时（"Added support for OAuth 2.0"）。


人称选择：面向用户的文档使用第二人称 "you"（"You can configure the timeout by..."）；避免使用第一人称 "I/we"（除 Contributing 指南外）；API 文档使用第三人称或无人称（"Returns the user object"）。


简洁性原则：一句话一个要点；避免冗余词汇（如 "in order to" 用 "to" 代替）；避免行话和缩写（首次出现须给出全称）；段落不超过五六行。


一致性原则：同一概念始终使用相同术语（建立术语表 glossary）；标题层级保持一致（不跳级）；代码示例风格统一（缩进、引号、分号等）。


小结
    

  • 软件文档按受众分为用户文档、开发者文档和流程文档三大类，各自有不同的语言风格要求
    • 

  • API 参考文档强调精确性和结构化，使用主动语态和简明动词描述端点行为
    • 

  • README 是开源项目的门面，遵循 Title → Description → Installation → Usage → Contributing → License 的标准结构
    • 

  • 需求文档使用 RFC 2119 关键词（MUST/SHALL/SHOULD/MAY）表达不同级别的强制性
    • 

  • 设计文档采用 Overview → Goals → Proposed Design → Alternatives → Trade-offs 的经典框架
    • 

  • 错误消息应遵循 What → Why → How to Fix 三段式原则，兼顾用户友好性和技术准确性
    • 

  • 文档写作优先使用主动语态、一般现在时和第二人称，保持简洁和一致
    • 

  • 建立项目术语表（glossary）是维护文档一致性的最佳实践
    •
