变量与函数命名英语

命名风格基础

编程命名的英语基础始于理解几种主流的大小写风格及其适用场景。不同的编程语言社区对命名风格有明确的偏好约定，遵循这些约定是写出"地道"代码的第一步。

四种核心命名风格

风格 英文名称 格式示例 典型用途
小驼峰 camelCase getUserName JS/TS 变量、函数
大驼峰 PascalCase UserService 类名、React 组件
蛇形 snake_case user_name Python 变量、Ruby 方法
短横线 kebab-case user-profile CSS 类名、URL slug

语言社区的命名传统

// JavaScript / TypeScript
const maxRetryCount = 3; // 变量: camelCase
function calculateTotal() {} // 函数: camelCase
class PaymentGateway {} // 类: PascalCase
const API_BASE_URL = '/api/v2'; // 常量: SCREAMING_SNAKE_CASE
# Python (PEP 8)
max_retry_count = 3               # 变量: snake_case
def calculate_total():            # 函数: snake_case
class PaymentGateway:             # 类: PascalCase
API_BASE_URL = '/api/v2'          # 常量: SCREAMING_SNAKE_CASE
// Go
maxRetryCount := 3                // 变量: camelCase (unexported)
func CalculateTotal() {}          // 导出函数: PascalCase
func calculateTotal() {}          // 私有函数: camelCase
const apiBaseURL = "/api/v2"      // 常量: camelCase

关键原则：在同一项目中绝不混用命名风格。团队一旦选定规范就要贯彻始终，一致性比"完美"的命名规则更重要。

函数命名的 A/HC/LC 模式

函数命名是程序员英语中最核心的技能。优秀的函数名应当像一句精炼的英语短语——读者无需查看函数体就能理解其行为。业界广泛采用的 A/HC/LC（Action/High Context/Low Context）模式提供了系统化的命名框架。

模式结构

函数名 = action + highContext + lowContext
组成部分 说明 示例
Action 动词，描述函数做什么 get, set, fetch
High Context 核心操作对象 User, Payment, Order
Low Context 补充限定信息 ById, FromCache, Async

实际应用

// Action + HighContext
getUser(); // 获取用户
createOrder(); // 创建订单
deleteComment(); // 删除评论

// Action + HighContext + LowContext
getUserById(); // 按 ID 获取用户
fetchOrdersFromAPI(); // 从 API 获取订单列表
validateEmailFormat(); // 验证邮箱格式

核心动词选择指南

选择准确的动词是函数命名的关键。以下是按语义分组的高频动词及其细微区别：

数据获取类

动词 含义 适用场景
get 同步获取已有数据 getUsername() — 从对象属性读取
fetch 异步从远端获取 fetchUserProfile() — 调用 API
find 在集合中查找 findUserByEmail() — 搜索匹配项
query 结构化条件查询 queryActiveOrders() — 数据库查询
load 加载资源到内存 loadConfiguration() — 初始化时加载
retrieve 正式地取回 retrieveArchivedData() — 从归档恢复

数据操作类

动词 含义 适用场景
set 赋值 setTheme('dark') — 设置属性值
update 修改已有数据 updateProfile() — 部分更新
create 新建资源 createUser() — 插入新记录
delete / remove 删除 deleteUser() 永久删除 / removeItem() 从集合移除
add 增加到集合 addToCart() — 追加元素
insert 在特定位置插入 insertAtIndex() — 指定位置

状态与判断类

动词/前缀 含义 适用场景
is 布尔状态判断 isValid, isEmpty, isAuthenticated
has 存在性检查 hasPermission, hasChildren
can 能力/权限检查 canEdit, canDelete
should 条件建议 shouldRetry, shouldCache

转换类

动词 含义 适用场景
to 类型转换 toString(), toJSON(), toArray()
parse 解析字符串 parseDate(), parseConfig()
format 格式化输出 formatCurrency(), formatDate()
serialize / deserialize 序列化 serializeState()
convert 通用转换 convertToCSV()

变量命名的语法规律

变量命名的核心原则是 S-I-D（Short, Intuitive, Descriptive）——简短、直觉化、描述性。

布尔变量：用形容词或介词短语

布尔变量的命名应当形成一个可读的英语断言：

// Good — 读起来像自然语言
const isActive = true; // "it is active"
const hasPermission = false; // "it has permission"
const canDelete = true; // "it can delete"
const shouldAutoSave = true; // "it should auto-save"
const isEmailVerified = true; // "email is verified"

// Bad — 模糊不清
const flag = true;
const check = false;
const status = true; // 什么状态？

数值变量：量词 + 名词

// Good
const maxRetryCount = 3;
const connectionTimeout = 5000; // 单位应明确或在名称中体现
const timeoutMs = 5000; // 通过后缀标明单位
const itemCount = 42;
const totalPrice = 99.99;

// Bad
const max = 3; // max of what?
const timeout = 5000; // 单位不明
const num = 42; // 过于泛化

集合变量：用复数形式

// Good
const users = []; // 复数表示数组
const selectedItems = []; // 形容词 + 复数名词
const userMap = new Map(); // 后缀表示数据结构
const idSet = new Set(); // 后缀表示类型

// Bad
const data = []; // 太泛化
const list = []; // 没有说明 list of what
const arr = []; // 缩写丢失语义

避免缩写陷阱

// Bad — 难以理解的缩写
const usrNm = 'Alice';
const btnClkHndlr = () => {};
const accnt = getAccount();

// Good — 清晰完整的名称
const userName = 'Alice';
const buttonClickHandler = () => {};
const account = getAccount();

// 可接受的广泛认可缩写
const id = 'abc123'; // identifier
const url = '/api/users'; // Uniform Resource Locator
const api = createAPI(); // Application Programming Interface
const db = connectDB(); // database
const i = 0; // 循环变量（仅限小范围）

命名反模式与修正

避免上下文重复

当变量名已经存在于特定上下文中时，无需重复该上下文信息：

// Bad — 在 User 类中重复 "user" 前缀
class User {
  userName; // "User" 上下文已经暗示
  userEmail;
  getUserAge() {}
}

// Good — 利用上下文消除冗余
class User {
  name;
  email;
  getAge() {}
}

反映预期结果

函数名应当反映其返回值的性质，而非内部实现过程：

// Bad — 描述过程
function processData() {} // 返回什么？
function handleClick() {} // 结果是什么？
function doCalculation() {} // 计算什么？

// Good — 反映结果
function getFormattedPrice() {} // 返回格式化的价格
function calculateTax() {} // 返回税额
function buildUserProfile() {} // 返回用户档案对象

单复数的精确使用

// 单数 — 表示一个实体
const user = getUser(id);
const selectedItem = items[0];
const config = loadConfig();

// 复数 — 表示集合
const users = fetchAllUsers();
const selectedItems = getSelection();
const configs = loadAllConfigs();

// 注意不可数名词
const data = fetchData(); // data 是不可数名词，不用 datas
const information = getInfo(); // 同理
const feedback = collectFeedback();

实战练习：命名审查

以下是一组常见的"坏名字"及其改进建议，通过对比学习如何选择更精准的英语表达：

原始命名 问题 改进方案 理由
data2 无语义编号 transformedData 说明数据状态
temp 含义不明 cachedResponse 说明临时存储什么
flag 什么标记？ isRetryEnabled 明确布尔含义
doSomething() 完全无意义 validateInput() 明确动作和对象
handleStuff() 模糊处理 processPayment() 具体化处理对象
mgr 不必要缩写 manager 或更具体如 connectionManager
val 歧义（value? valid?） inputValue 或 isValid 消除歧义

每当你写下一个变量名或函数名时，问自己：如果一个不了解这段代码的同事读到这个名字，他能否在不看定义和注释的情况下猜出它的用途？ 如果答案是否定的，就需要重新命名。

AI 时代的命名考量

AI 辅助编程（Copilot / Cursor / Claude Code）让命名同时承担两层读者：人类同事 + LLM。两者的偏好大体重合，但有几处差异值得注意：

维度 给人类 给 LLM 也读
缩写 适度（社区惯例缩写 OK） 避免（LLM 在长上下文里更容易跟错）
同名复用 同一作用域避免即可 跨文件也避免——LLM 的"语义同名"易混
单复数 users vs user 明显 越明显越好——userList 比 users 对 LLM 更稳
布尔前缀 is/has/should 习惯化 强制使用——LLM 对布尔判定句式特别敏感
同义词漂移 fetch / get / load 互换 选一个用到底——避免 LLM 在生成时混用

LLM 友好的命名小约定

下面这些不是新规则，只是把人本来就应该做的、做得更彻底：

# Less LLM-friendly
function process(d, opts) { /* what is d? */ }

# More LLM-friendly — 类型暗示在名字里
function processOrders(orders: Order[], options: ProcessOptions) { }

# Less — 缩写让 LLM 自动补全跑偏
const ctx = getCtx();
const req = ctx.req;

# More — 全名让 LLM 跟得上指代链
const requestContext = getRequestContext();
const request = requestContext.request;

Prompt 中的命名约定

当你在 prompt 里要求 LLM 生成代码时，显式指定命名风格比期待"模型自己懂"可靠：

Implement a function that validates user input. Use camelCase for
identifiers. Prefer descriptive names over abbreviations (e.g.
"validationErrors" not "errs"). Boolean variables must start with
is/has/should.

这一条特别影响长会话——LLM 在长对话里会逐渐"飘"到自己的命名偏好上，把约定写在 prompt 里能稳定输出。

AI 生成代码的命名审查清单

review AI 生成的代码时，命名维度多查 5 个高频问题：

  • 是否有"Helper / Util / Manager"这类无义后缀？（LLM 偏爱这类名字）
  • 复数 / 单数是否一致？（user 与 users 混用是常见漂移）
  • 布尔变量是否都有 is/has/should/can 前缀？
  • 异步函数是否带 Async 后缀或返回 Promise？
  • 同一个概念在不同地方是否始终用同一个词？（fetch vs get vs load）

判定标准：如果 AI 生成的命名让你在 PR review 阶段需要"翻译一遍"，那命名约定就没传达给 LLM——回去补 prompt，不要在 review 里手工修。
