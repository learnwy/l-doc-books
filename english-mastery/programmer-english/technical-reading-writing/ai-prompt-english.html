AI Prompt 英语

与 LLM 协作已成为程序员日常工作的一部分。Prompt 不是"输入框里的随手一句话"——它是一种技术写作形式，有固定的结构惯例、动词偏好、精度术语和反 Chinglish 模式。本文档把 prompt 写作从"模糊感觉"提升到"可教学技能"。

为什么需要专门学 Prompt 英语

中文母语开发者写 prompt 时常出现两类痛点：

# Pattern A — Chinglish 直译（动词错位、礼貌冗余）
Please help me to write a function that can sort the array.

# Pattern B — 模糊（缺约束、缺格式、缺示例）
Make this code better.

# 优化后
Sort the array in place, ascending, ignoring null entries. Return void.
Refactor for readability: extract helper functions, name them with verbs,
limit each to 20 lines. Keep the public API unchanged.

Prompt 英语与人类技术英语有三处分歧：

维度 写给人类 写给 LLM
礼貌语 适度（"Could you please..."） 删除（"please" 不增加输出质量，反而稀释指令）
上下文 隐含共享（公司、领域、术语） 必须显式（LLM 不读你脑子）
格式要求 可口头协商 写在 prompt 里（"Return JSON with keys X, Y"）

Prompt 的四段式结构（ICFC 模型）

工业界主流 prompt 都隐含或显式地包含四个部分：

段 名称 英语标识词 作用
I Instruction imperative verb 开头 一句话说清要做什么
C Context "Given...", "You are...", "Here is..." 提供前置事实、角色、领域
F Format "Return as...", "Output in..." 指定输出结构
C Constraints "Limit to...", "Do not...", "Only..." 边界条件与禁区

典型完整 prompt：

You are a senior Go reviewer. Given the function below, identify
concurrency bugs only — not style or naming issues. Return a JSON
array where each item has {line, severity, explanation}. Limit to
5 most critical findings.

[code here]

四段并不要求强制顺序；可省略其中 1–2 段，但首段必须是 Instruction。把 instruction 埋在第三段是新手最常见的失败模式。

指令动词的精度梯度

英语中 "make it better" 是模糊指令。LLM 对动词选择极度敏感。下表是程序员高频意图与对应的精度动词：

中文意图 弱 中 强（推荐）
让代码更好 improve clean up refactor for { readability / performance / testability }
找问题 check review audit for { security vulnerabilities / null-pointer risks / race conditions }
解释代码 explain describe walk through { the control flow / the data lifecycle } step by step
生成代码 write implement implement following { TDD / hexagonal architecture / functional style }
改写 change modify rewrite to { use async/await instead of callbacks / replace inheritance with composition }
简化 simplify shorten inline the helper / collapse the conditional / drop the abstraction
减少 bug fix bugs debug identify the root cause of { the failing test / the memory leak }

经验法则：动词越强、宾语越窄，输出越聚焦。"refactor this" 几乎总比 "refactor this for testability by extracting pure functions" 给出更差的输出。

约束词与精度形容词

类别 英语 含义 / 场景
详尽度 exhaustive / comprehensive 要求覆盖所有情况
简洁度 concise / terse 输出尽量短
地道度 idiomatic 符合语言/框架社区惯例
鲁棒度 robust / defensive 对边界、错误输入有处理
脆弱度 brittle （形容现有代码差）—— "this is brittle, harden it"
范围限制 scoped to X / limited to X / only X 圈定输出范围
风格选择 functional / imperative / declarative 编程范式约束
一致性 consistent with the existing style 跟随既有代码风格
显式度 explicit / verbose 不要省略类型 / 不要使用魔法
简化度 idiomatic / succinct 用语言惯用法

组合示例：

Implement a Redis-backed rate limiter. Constraints: idiomatic Go,
no external dependencies beyond go-redis, robust against clock skew,
limited to fixed-window algorithm only. Return concise code with one
short doc comment per exported function.

反 Chinglish 模式

中文母语者写 prompt 高频出现以下 5 类直译错误：

Chinglish Idiomatic English
Please help me to write a function Write a function
Can you analyze this code and tell me what's wrong? Identify bugs in this code
I want you to do X Do X
Make sure you don't forget to handle null Handle null inputs
Give me the best way to do X Recommend the idiomatic way to do X in {language}

核心原则：删除所有指向 LLM"努力 / 注意"的语句。LLM 不"努力"，它只 sample。把规则写成约束，不要写成请求。

反馈循环：用英语修正 prompt

第一轮输出不满意时，反馈式 prompt 比"重写整个 prompt"更高效：

反馈意图 模板句
太冗长 Cut this to half the length, keep all essential information.
太抽象 Show concrete examples for each point.
缺测试 Add unit tests for the edge cases you identified.
风格不对 Rewrite to match the style of {file}.
偏题 Focus only on X — drop everything about Y.
想要更多深度 Expand on point 3 — what are the trade-offs?
想要替代方案 Show two alternative approaches and compare them.

经验：单轮 prompt 不必完美；反馈轮次比初始 prompt 长度更影响最终质量。把 prompt 写作当成"先大致 + 后精修"的迭代过程，而不是"一次写对"的考试。

工具差异的微调

工具 偏好
Claude (Anthropic) 长上下文友好；接受 markdown 标题分段；明确说"think step by step" 仍有效
GPT-4 / o-series 偏好简短 + 结构化（JSON / 列表）；可显式说 "reason internally then output"
Copilot Chat (VS Code) 隐式知道当前文件 + 光标位置；prompt 可省略"in this file"
Cursor / Windsurf agent 多轮 + 工具调用；prompt 可包含"if you find X, run Y" 的条件指令

跨工具迁移 prompt 时，主要调整冗余度：本地 IDE agent 知道仓内文件，云端 chat 不知道；后者需补上下文。

实例：bad → good 改写

例 1：要求 review 代码

# Bad
Please review my code below and let me know if there are any problems.
I appreciate your help.

[code]

# Good
You are a Go code reviewer. Review the function below for:
- concurrency bugs (race conditions, deadlocks)
- error handling gaps (un-wrapped errors, swallowed returns)
- API design issues (unclear naming, leaky abstractions)

Return findings as a markdown table with columns:
{line, category, severity (high/medium/low), suggested fix}.

[code]

例 2：要求生成测试

# Bad
Write some tests for this function.

# Good
Write table-driven tests in Go for the function below. Cover:
- happy path with valid input
- nil input
- empty slice input
- one boundary case for each numeric parameter

Use testify/assert. Name each case with a short descriptor.

[code]

例 3：要求重构

# Bad
Make this function better. It's too long.

# Good
Refactor the 80-line function below: extract pure helpers, name them
with verbs, keep each under 20 lines. Preserve the existing public
signature and behavior. Do not change error messages — downstream
tests match on them.

[code]

常用 prompt 句式快速查表

意图 句式
角色设定 You are a {role} who specializes in {domain}.
给定上下文 Given that {fact1, fact2, ...}, ...
任务边界 Only consider X; ignore Y.
输出格式 Return as {format} with keys {a, b, c}.
风格继承 Follow the conventions in {file/library}.
推理引导 First {step 1}, then {step 2}, then {output}.
否定约束 Do not {action}. / Avoid {pattern}.
替代请求 Propose N alternative approaches with trade-offs.
自检指令 Before returning, verify {invariant}.

把这张表作为日常 prompt 起草的脚手架——拿不准时回查格式，比逐字翻译中文 prompt 快得多。

小结

  • Prompt 英语是一种写作子体，遵循 ICFC 四段（Instruction / Context / Format / Constraints）
  • 删除礼貌词；用动词精度梯度从弱到强选词
  • 形容词（idiomatic / robust / concise）和否定约束（do not / avoid）是高 ROI 表达
  • 反馈轮次比初始 prompt 更影响最终质量；把 prompt 当迭代过程
  • 跨工具迁移时调整冗余度而非重写
