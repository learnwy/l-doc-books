代码注释与提交信息

核心概念

代码注释（code comments）和 Git 提交信息（commit messages）是开发者每天书写量最大的英文文本。虽然它们看似简短、无关紧要，但实际上直接影响代码的可维护性和团队协作效率。好的注释解释 why，好的提交信息记录 what changed and why。

注释和提交信息在角色和生命周期上有明确区别：






维度
代码注释
提交信息





存在位置
源代码文件中
Git 历史记录中




生命周期
随代码修改而变化
永久不可变




核心回答
Why（为什么这样做）
What + Why（做了什么、为什么）




读者
未来修改此代码的人
审查者、未来的考古者




更新责任
修改代码时必须同步更新
写入后不可修改




常见错误
解释 What 而非 Why
写 "fix bug" 这类无信息量的信息





核心哲学是：Code tells you how, comments tell you why, commit messages tell you what happened。


注释的 Why-Not-What 原则
代码注释最常见的错误是解释代码"做了什么"（What），而不是"为什么这样做"（Why）。前者是代码本身应该通过命名和结构表达的，后者才是注释的职责。


坏的注释（解释 What）：


// increment counter by 1
counter += 1;

// check if user is admin
if (user.role === 'admin') {
好的注释（解释 Why）：


// Use manual increment instead of autoIncrement() due to race condition in concurrent writes.
// See: https://github.com/org/repo/issues/1234
counter += 1;

// Admin bypass: skip rate limiting for internal tools dashboard.
// Product decision from 2024-Q1 review (Slack thread: #platform-decisions/2024-01-15)
if (user.role === 'admin') {
好的注释提供了三类信息：


    

  1. 技术原因 — 为什么选择这种实现方式而非更常见的方式
    2. 

  2. 业务背景 — 这段代码背后的产品决策
    3. 

  3. 引用链接 — 相关的 Issue、Slack 讨论或设计文档
    4.

Conventional Commits 规范
Conventional Commits 是目前最广泛采用的提交信息规范，其格式为：


<type>(<scope>): <subject>

<body>

<footer>
Type 的常用值：


    

  • feat — 新功能
    • 

  • fix — 修复 bug
    • 

  • docs — 文档更新
    • 

  • refactor — 重构（不改变功能）
    • 

  • perf — 性能优化
    • 

  • test — 添加或修改测试
    • 

  • chore — 构建工具、CI、依赖更新等
    • 

  • style — 代码格式（不影响逻辑）
    • 



Subject 的写作规则：


    

  • 使用祈使语气（imperative mood）：add 而非 added 或 adds
    • 

  • 首字母小写
    • 

  • 不加句号
    • 

  • 控制在 50 个字符以内
    • 



好的 subject：




feat(auth): add OAuth 2.0 PKCE flow support






fix(cache): prevent stale entries from being served after TTL






refactor(api): extract validation logic into middleware




坏的 subject：




Fixed the bug（不符合祈使语气）feat: update stuff（过于模糊）FEAT(AUTH): ADD OAUTH（不要全大写）




提交 Body 与 Footer 的写法
当 subject 无法完整表达变更内容时，需要在 body 中提供详细说明。Body 的核心职责是回答 Why this change 和 What was the alternative。


完整的提交信息示例：


fix(auth): handle token refresh race condition

When multiple API calls triggered simultaneously, the token refresh
logic could fire multiple concurrent refresh requests. This led to
intermittent 401 errors as stale tokens were used before the refresh
completed.

The fix introduces a mutex lock around the refresh flow, ensuring only
one refresh request is in-flight at any time. Subsequent calls wait
for the pending refresh to complete.

Alternative considered: debouncing the refresh call. Rejected because
it could delay legitimate token refreshes under high concurrency.

Fixes #4521
Co-authored-by: Sarah Chen <sarah@company.com>
Body 的写作原则：


    

  • 用空行将 subject 和 body 分隔
    • 

  • 每行限制在 72 个字符以内（Git 的传统约定）
    • 

  • 第一段说明问题（What was wrong）
    • 

  • 第二段说明解决方案（How it was fixed）
    • 

  • 第三段说明被否决的替代方案（What was considered but rejected）
    • 



Footer 中常用的标记：






标记
用途
示例





Fixes #N
关联并关闭 Issue
Fixes #4521




Refs #N
引用但不关闭 Issue
Refs #4500




BREAKING CHANGE:
标记不兼容变更
BREAKING CHANGE: remove v1 auth endpoints

标记共同作者
Co-authored-by: Name <email>

JSDoc 与 TSDoc 注释规范
函数级注释在 TypeScript/JavaScript 生态中使用 JSDoc/TSDoc 格式。好的函数注释应描述函数的契约（contract），而非实现细节。


标准格式：


/**
 * Resolves a user by ID, falling back to email lookup if ID is not found.
 *
 * @param identifier - User ID (preferred) or email address
 * @param options - Lookup configuration
 * @param options.includeDeleted - Whether to include soft-deleted users
 * @returns The resolved user, or null if not found
 * @throws {AuthorizationError} If the caller lacks read permission
 *
 * @example
 * ```typescript
 * const user = await resolveUser('usr_abc123');
 * const userByEmail = await resolveUser('alice@example.com', { includeDeleted: true });
 * ```
 */
async function resolveUser(
  identifier: string,
  options?: ResolveOptions
): Promise<User | null> {
JSDoc 注释的关键规则：


    

  • 第一行是功能摘要，使用 第三人称单数：Resolves... 而非 Resolve... 或 This function resolves...
    • 

  • @param 描述参数的意义，不重复类型信息（TypeScript 已提供类型）
    • 

  • @returns 描述返回值的含义，包括边界情况（如 null）
    • 

  • @throws 列出可能抛出的异常及条件
    • 

  • @example 提供可运行的使用示例
    • 



避免写这样的 JSDoc：


/**
 * This is the resolveUser function.
 * @param identifier - the identifier parameter
 * @returns the return value
 */
这种注释提供的信息为零，纯粹是噪音。


小结
    

  • 代码注释解释 Why，代码本身表达 What 和 How
    • 

  • 使用 Workaround for、Optimization:、SECURITY: 等标准前缀提高注释可扫读性
    • 

  • 提交信息遵循 Conventional Commits 格式：type(scope): subject
    • 

  • Subject 使用祈使语气、首字母小写、50 字符以内、不加句号
    • 

  • Body 回答三个问题：出了什么问题、怎么修的、为什么不用其他方案
    • 

  • JSDoc 第一行用第三人称单数描述功能，@param 不重复类型信息
    • 

  • 所有注释在代码变更时必须同步更新，过时的注释比没有注释更有害
    •
