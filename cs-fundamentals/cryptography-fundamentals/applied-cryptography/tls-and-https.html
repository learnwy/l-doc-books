TLS 与 HTTPS

核心概念

TLS（Transport Layer Security）是互联网最广泛部署的安全协议——HTTPS、SMTPS、IMAPS、FTPS、SIPS、QUIC 全部建立在 TLS 之上。它把所有密码学原语（对称加密、非对称加密、签名、KDF、hash、MAC）组合成一个 secure channel——客户端与服务器协商 cipher suite、交换 key、验证身份、加密数据。TLS 1.3（2018，RFC 8446）是最新版本，相比 1.2 简化了 handshake、删除不安全选项、加快 1-RTT 连接、支持 0-RTT 资源 reuse。本节介绍 TLS handshake 流程、cipher suite 含义、HTTPS 完整链条、TLS 1.2 vs 1.3 区别、常见漏洞与防御、性能优化。

维度 TLS 1.2 TLS 1.3
发布 2008 2018
Handshake 2-RTT 1-RTT (or 0-RTT)
Cipher suite 复杂（37+） 简化（5 种）
Key exchange RSA / DH / ECDH (EC)DHE only
AEAD only 否（CBC 仍兼容） 是
Session resumption 复杂 0-RTT PSK

TLS 1.3 Handshake

Client                                           Server

ClientHello
  + supported versions (TLS 1.3)
  + supported cipher suites
  + key_share (X25519 public key)
  + signature algorithms
  + server_name (SNI)
  ─────────────────────────────────────────────►

                              ServerHello
                                + selected version
                                + selected cipher suite
                                + key_share (server's X25519 public)
                              EncryptedExtensions
                              Certificate（+ chain）
                              CertificateVerify（私钥签名 handshake）
                              Finished
  ◄─────────────────────────────────────────────

Finished
  ─────────────────────────────────────────────►

[Application Data 加密传输]
  ◄────────────────────────────────────────────►

1-RTT：第一个数据包能在 1 round trip 后加密发送（vs TLS 1.2 的 2-RTT）。

Cipher Suite
TLS 1.2 cipher suite 名（复杂）：


TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
   ↑      ↑     ↑   ↑       ↑      ↑
   key   auth  enc mode  hash    PRF
   exchange
TLS 1.3 简化为 5 种：


    

  • TLS_AES_128_GCM_SHA256
    • 

  • TLS_AES_256_GCM_SHA384
    • 

  • TLS_CHACHA20_POLY1305_SHA256
    • 

  • TLS_AES_128_CCM_SHA256
    • 

  • TLS_AES_128_CCM_8_SHA256
    • 



为什么简化：


    

  • TLS 1.2 cipher suite 组合爆炸（数百种），实现错误概率高。
    • 

  • 1.3 只 cover AEAD（无单纯 CBC + MAC），强制 (EC)DHE forward secrecy。
    • 

  • 减少 vulnerabilities like POODLE、Lucky 13。
    • 



Forward Secrecy
Forward Secrecy（前向保密）：未来私钥泄露不影响过去通讯：


    

  • TLS 1.2 RSA key exchange 不提供 FS——session key 由 RSA encryption 传输，私钥泄露后所有过去 session 可解。
    • 

  • TLS 1.2 DHE / ECDHE 提供 FS——session key 协商后即销毁。
    • 

  • TLS 1.3 强制 (EC)DHE，所有 session 默认 FS。
    • 



为什么 RSA key exchange 被废：


    

  • 国家 actor 大量记录加密流量。
    • 

  • 未来私钥泄露后批量解密。
    • 

  • ECDHE 防御此攻击。
    • 



证书验证
TLS handshake 的 Certificate 阶段：


1. 服务器发送 cert chain。
2. 客户端验证：
   a. 每张证书签名（用 issuer 公钥）。
   b. Chain 终于 root CA in trust store。
   c. valid period（now ∈ [Not Before, Not After]）。
   d. SAN 匹配 hostname（SNI）。
   e. Revocation（OCSP / CRL）。
   f. Certificate Transparency（SCT）。
3. CertificateVerify：服务器用私钥签名整个 handshake，证明它持有 cert 对应私钥。
SNI（Server Name Indication）：


    

  • 客户端在 ClientHello 中指明 hostname。
    • 

  • 服务器用 SNI 选择 cert（一个 IP 多个 cert）。
    • 

  • TLS 1.2 SNI 明文，1.3 + ESNI / ECH 加密。
    • 



0-RTT（早期数据）
TLS 1.3 支持 0-RTT：


Client                                           Server

ClientHello + early_data
  ─────────────────────────────────────────────►
[Application Data 加密用 PSK derived key]
  ─────────────────────────────────────────────►

                              ServerHello
                              ...
0-RTT 应用数据在 ClientHello 同时发送——延迟为 0。


风险：


    

  • Replay attack——攻击者重放 0-RTT 消息。
    • 

  • 必须只用于 idempotent 操作（GET 不 POST）。
    • 



实战：


    

  • Chrome、Firefox 默认禁用（risk）。
    • 

  • CDN（Cloudflare）opt-in。
    • 

  • HTTPS API 需谨慎。
    • 



TLS 1.2 vs 1.3 安全性对比
TLS 1.2 已知问题：


    

  • BEAST（CBC 漏洞）。
    • 

  • POODLE（CBC padding oracle）。
    • 

  • Lucky 13（CBC timing）。
    • 

  • Heartbleed（OpenSSL 实现 bug）。
    • 

  • ROBOT（PKCS#1 v1.5 padding oracle）。
    • 

  • SLOTH（弱 hash 在 RSA）。
    • 

  • 弱 cipher（RC4、3DES、MD5、SHA-1）兼容性。
    • 



TLS 1.3 修复：


    

  • 删除 CBC（仅 AEAD）。
    • 

  • 删除 RSA key exchange（仅 (EC)DHE）。
    • 

  • 删除 DSA、PKCS#1 v1.5。
    • 

  • 删除 RC4 / 3DES / MD5 / SHA-1。
    • 

  • 删除 export ciphers（FREAK / Logjam 历史）。
    • 

  • 删除 compression（CRIME 历史）。
    • 



Encrypted SNI（ECH）
问题：TLS 1.2/1.3 SNI 明文——攻击者看 ClientHello 知道访问哪 hostname。


ESNI / ECH（Encrypted Client Hello）：


    

  • 用 server 的 public key（DNS HTTPS record）加密 ClientHello 中 SNI。
    • 

  • 防 SNI 监听 / 审查。
    • 



部署：


    

  • Cloudflare 2018 起 ECH 实验。
    • 

  • 2025 部分浏览器默认。
    • 

  • 中国 / 伊朗等国家审查 SNI——ECH 是抗审查工具。
    • 



QUIC 与 HTTP/3
QUIC（IETF 标准化）：


    

  • UDP 替代 TCP。
    • 

  • TLS 1.3 内嵌（QUIC 与 TLS 1.3 整合）。
    • 

  • 0-RTT 默认。
    • 

  • 多路复用（避免 HoL blocking）。
    • 

  • 连接迁移（IP 变化不重连）。
    • 



HTTP/3：


    

  • HTTP over QUIC。
    • 

  • Google QUIC 2013 实验，2021 标准化。
    • 

  • Cloudflare、Google、Facebook 大规模部署。
    • 

  • 性能：移动 / lossy 网络下 30-50% 提升。
    • 



TLS 性能优化
1. Session Resumption：


    

  • TLS 1.2 session ID / ticket。
    • 

  • TLS 1.3 PSK + 0-RTT。
    • 

  • 跳过证书验证 → 大幅减少 handshake 开销。
    • 



2. OCSP Stapling：


    

  • Server 提前从 CA 获取 OCSP response。
    • 

  • 在 handshake 中提供。
    • 

  • 避免客户端单独查询。
    • 



3. Cert chain 优化：


    

  • 不发不必要的 root CA（客户端 trust store 已有）。
    • 

  • Chain 长度 2-3 是 sweet spot。
    • 



4. ECDSA cert > RSA cert：


    

  • ECDSA 签名 64 byte vs RSA 256 byte。
    • 

  • 减小 handshake size。
    • 

  • 移动 / lossy 网络收益大。
    • 



5. HTTP/2 / 3 multiplexing：


    

  • 多 request 共享 TLS connection。
    • 

  • 减少 handshake 总数。
    • 



实战配置（nginx）
server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    # TLS 1.2 + 1.3
    ssl_protocols TLSv1.2 TLSv1.3;

    # 现代 cipher
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:...
    ssl_prefer_server_ciphers off;  # TLS 1.3 让 client 选

    # OCSP stapling
    ssl_stapling on;
    ssl_stapling_verify on;

    # HSTS
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload";
}
常见 TLS 漏洞
1. Heartbleed（2014）：


    

  • OpenSSL bug：heartbeat 过度读取 server 内存。
    • 

  • 泄露私钥、cookies、passwords。
    • 

  • 修复后 reissue 所有 cert。
    • 



2. POODLE（2014）：


    

  • SSL 3.0 CBC padding oracle。
    • 

  • 修复：禁用 SSL 3.0。
    • 



3. Heartbleed-style：


    

  • 任何 implementation bug 可能 catastrophic。
    • 

  • 防御：用 BoringSSL / rustls 等 memory-safe 实现、fuzzing、模糊测试。
    • 



4. CRIME / BREACH：


    

  • 加密前 compression 泄露。
    • 

  • TLS 1.3 删 compression。
    • 



5. FREAK / Logjam：


    

  • Export-grade RSA / DH 弱 key。
    • 

  • TLS 1.3 删除。
    • 



6. ROBOT：


    

  • PKCS#1 v1.5 padding oracle。
    • 

  • 修复：用 OAEP。
    • 



量子威胁
Shor 算法破 RSA / ECDHE → TLS 1.3 失效。


Post-quantum TLS：


    

  • NIST 2024 标准化 ML-KEM。
    • 

  • Cloudflare、Google 2024 起 hybrid X25519 + ML-KEM。
    • 

  • TLS 草案 ML-KEM cipher suite。
    • 

  • 完全转换 5-10 年。
    • 



监控与测试
1. SSL Labs（ssllabs.com）：


    

  • 测试服务器 TLS 配置。
    • 

  • Grade A+ 到 F。
    • 

  • 必备 deployment check。
    • 



2. testssl.sh：


    

  • 命令行 TLS 测试。
    • 

  • 详细漏洞报告。
    • 



3. tls-scan：


    

  • 批量扫描。
    • 

  • 适合 fleet。
    • 



小结
TLS 是互联网最广泛部署的安全协议——HTTPS / SMTPS / QUIC 全部建立其上。TLS 1.3（2018）相比 1.2 简化 handshake（1-RTT vs 2-RTT）、删除不安全选项、强制 AEAD 与 (EC)DHE forward secrecy、cipher suite 从数百简化到 5 种。Cipher suite 包含 key exchange + auth + enc + hash 四要素。Forward Secrecy 让未来私钥泄露不影响过去通讯——TLS 1.3 强制。证书验证包含签名、chain、有效期、SAN、revocation、CT。0-RTT 早期数据延迟 0 但有 replay 风险——仅用于 idempotent 操作。TLS 1.2 已知漏洞（BEAST、POODLE、Lucky 13、Heartbleed、ROBOT、CRIME、FREAK、Logjam）TLS 1.3 大部分修复。Encrypted SNI / ECH 加密 ClientHello 防审查。QUIC + HTTP/3 把 TLS 1.3 内嵌 UDP 协议，0-RTT 默认 + 连接迁移 + 多路复用。性能优化——session resumption、OCSP stapling、ECDSA cert、HTTP/2 multiplexing。Nginx 配置示例展示现代部署。常见漏洞——实现 bug（Heartbleed）、协议设计（POODLE / CRIME）、弱 crypto（FREAK / Logjam）。Quantum 威胁——Cloudflare / Google 2024 起 hybrid X25519 + ML-KEM 部署。监控工具——SSL Labs、testssl.sh、tls-scan。一个简单的检验：你能解释 TLS 1.3 1-RTT handshake 的 3 步？如果不能，handshake 流程还需巩固。TLS 是密码学的"互联网应用层"——把所有原语（对称、非对称、hash、MAC、KDF、签名）组合成 90% 互联网流量信赖的安全 channel。
