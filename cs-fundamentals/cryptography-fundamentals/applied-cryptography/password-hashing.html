密码 Hash 与存储

核心概念

密码存储是现代 Web 应用最常被破坏的安全环节——data breach 中泄露的密码 hash 经常因为算法选择错误（用 MD5 / SHA-256 而非 bcrypt / Argon2）让攻击者用 GPU 几小时还原数百万用户密码。"用 SHA-256 哈希密码"看似安全实则灾难——因为 SHA-256 设计为快（10^9 hash/s on GPU），而密码 hash 应该故意慢（让暴力穷举不可行）。本节介绍密码存储的工程化框架——为什么不能用通用 hash、salt 防 rainbow table、pepper 给 server-side 额外保护、bcrypt / scrypt / Argon2 三大现代算法、work factor 调优、密码 hash 的迁移策略。

算法 年代 内存硬度 GPU 抗性 ASIC 抗性 推荐场景
MD5 1992 无 无 无 永不（用于密码）
SHA-256 2001 无 无 无 永不（用于密码）
bcrypt 1999 4KB 中 中 兼容 / legacy
scrypt 2009 任意（GB） 强 中 数据加密
PBKDF2 2000 无 弱 弱 NIST 兼容（不推荐）
Argon2id 2015 任意（GB） 强 强 OWASP 推荐

为什么不能直接 SHA-256

通用 hash 太快：

  • SHA-256 在现代 GPU：~ 10^10 hash / second。
  • 8 字符 lowercase password（26^8 ≈ 2 × 10^11）→ 几十秒暴力。
  • 12 字符任意 ASCII（95^12 ≈ 5 × 10^23）→ 仍数十年。
  • 但 80% 用户密码进 top 10000 list，几毫秒就能 try。

Rainbow table 攻击：

  • 攻击者预计算所有常见密码的 SHA-256。
  • 拿到泄露的 hash 直接 lookup。
  • TB 级 rainbow table 覆盖大部分密码。

结论：通用 hash 不适合密码存储。需要故意慢的 password hashing 函数。

Salt：防 Rainbow Table

Salt 是给每用户 unique 的随机数，与 password 一起 hash：

H(salt ‖ password)

作用：

  • Rainbow table 失效——攻击者必须为每个 salt 重新 build。
  • 相同密码不同用户产生不同 hash → 攻击者看到两同 hash 知道两人密码相同的信息也丢失。

Salt 要求：

  • Per-user unique（不要全局 salt）。
  • 至少 16 byte random（用 OS CSPRNG）。
  • 与 hash 一起存（不是 secret）。

实战：所有现代 password hash 函数（bcrypt / Argon2）内置 salt 处理——不需手动管理。

Pepper：服务器端额外保护

Pepper 是全应用共享的 secret（不存数据库，存配置 / KMS）：

H(salt ‖ password ‖ pepper)

作用：

  • 数据库泄露但 pepper 不泄露 → 攻击者无法暴力（缺 pepper）。
  • 即使密码极弱，pepper 仍提供保护。

实战：

  • 把 pepper 存 HSM / KMS / 系统环境变量。
  • DB 拿到 hash 后无法 offline 暴力。
  • 增加一层防御。

注意：pepper 不是 silver bullet——pepper 与 hash 都泄露时同 salt-only 一样脆。

bcrypt（1999）

bcrypt（Niels Provos and David Mazières）：

  • 基于 Blowfish cipher 的"expensive key setup"。
  • 故意慢——work factor 控制慢度。
  • 默认输出 60 char string（含 salt）：
$2b$12$N9qo8uLOickgx2ZMRZoMye.IjPeMS9Ckti.yJUJxApNtTxK0r.IBO
 ↑   ↑  ↑                      ↑
 ver cost  salt（22 char）    hash（31 char）

Work factor：

  • cost = 12 意味 2^12 = 4096 iterations。
  • 现代推荐 cost 12（约 250ms 单 hash）。
  • 每年 cost +1 跟上硬件进步。

优势：

  • 经过验证（25 年）。
  • 广泛部署（Ruby on Rails、Django、Spring Security 默认）。
  • 简单 API。

劣势：

  • 只用 4KB memory——GPU 仍可加速。
  • Password ≤ 72 byte（bcrypt limit）。

scrypt（2009）

scrypt（Colin Percival）：

  • 内存硬度：要求大量 memory。
  • GPU / ASIC 内存有限 → 无法平行大规模。

参数：

  • N（cost factor）：CPU/memory cost。
  • r（block size）：通常 8。
  • p（parallelization）：通常 1。

推荐：N = 16384, r = 8, p = 1（用 ~ 16MB memory）。

应用：

  • Litecoin / Dogecoin（POW hash）。
  • 部分 disk encryption。
  • 较少用于 web password（bcrypt 与 Argon2 更主流）。

Argon2（2015）

Argon2（PHC 竞赛 2015 winner）：

  • 内存硬度 + 多线程并行。
  • 三变体：Argon2d（GPU 抗）、Argon2i（side-channel 抗）、Argon2id（hybrid，OWASP 推荐）。

OWASP 推荐 Argon2id 参数（2024）：

m = 19 MiB（19456 KiB）
t = 2 iterations
p = 1 parallelism

输出格式：

$argon2id$v=19$m=19456,t=2,p=1$<salt-base64>$<hash-base64>

优势：

  • 现代标准（PHC 推荐）。
  • 内存硬度 → ASIC / GPU 抗性强。
  • OWASP top recommendation。

PBKDF2（2000）

PBKDF2（PKCS #5 v2.1，RFC 2898）：

  • 反复 HMAC-SHA-256 / SHA-512。
  • NIST FIPS 兼容。

致命弱点：

  • 无 memory hardness。
  • GPU 可加速。

仍使用场景：

  • FIPS / NIST 合规（许多政府要求）。
  • 推荐 ≥ 600,000 iterations（OWASP 2024）。

现代实战 API

Argon2id（Python argon2-cffi）：

from argon2 import PasswordHasher

ph = PasswordHasher(time_cost=2, memory_cost=19456, parallelism=1)

# 注册
hash = ph.hash(password)  # 含 salt

# 登录
try:
    ph.verify(hash, password)
    if ph.check_needs_rehash(hash):  # 参数升级
        new_hash = ph.hash(password)
        # update in db
except VerifyMismatchError:
    # 错密码
    pass

bcrypt（Python bcrypt）：

import bcrypt

# 注册
hash = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))

# 登录
if bcrypt.checkpw(password.encode(), hash):
    # 正确密码
    pass

Go（golang.org/x/crypto/argon2）：

key := argon2.IDKey([]byte(password), salt, 2, 64*1024, 1, 32)
Work Factor 调优
目标：单 hash 100-500ms（用户登录可接受 + 攻击者每秒只能 ~ 2-10 attempts）。


测试：


import time
ph = PasswordHasher(...)
start = time.time()
ph.hash("test")
elapsed = (time.time() - start) * 1000
print(f"{elapsed:.0f}ms")
调优：


    

  • 慢于 500ms：用户感受。
    • 

  • 快于 100ms：攻击者太轻松。
    • 



横向扩容：


    

  • 部分公司用 dedicated password hashing 服务。
    • 

  • 高并发不影响主应用。
    • 



Year-by-year update：


    

  • 硬件每 2 年快 2x。
    • 

  • 每年 work factor +1（bcrypt cost）或 m/t +50%（Argon2）。
    • 

  • 用户登录时 check_needs_rehash 自动迁移。
    • 



迁移策略
从弱 hash（MD5 / SHA-256）迁移到 Argon2id：


方法 1：Layered hash：


new_hash = Argon2(legacy_hash)
    

  • 旧 user 登录时：先 SHA-256(password) → 再 Argon2 verify。
    • 

  • 新 user：直接 Argon2(password)。
    • 

  • DB 标记 hash type。
    • 



方法 2：Force reset：


    

  • 发邮件让所有用户 reset password。
    • 

  • 极端但 cleanest。
    • 



方法 3：Lazy migration：


    

  • 用户登录时如果是 legacy hash → 用密码（已知）→ 重新 Argon2 hash → update。
    • 

  • 渐进迁移。
    • 



不要做的事
反模式 1：直接 SHA-256(password)：


    

  • GPU 几秒暴力。
    • 

  • 灾难。
    • 



反模式 2：自己实现密码 hash：


    

  • 微妙错误几乎必然。
    • 

  • 用 bcrypt / Argon2 库。
    • 



反模式 3：Salt 太短 / 全局：


    

  • 16 byte minimum, per-user random。
    • 



反模式 4：硬编码 cost / parameters：


    

  • 不能 update。
    • 

  • 用 store-with-hash format（bcrypt / Argon2 标准格式自带）。
    • 



反模式 5：明文存密码：


    

  • 任何 breach 灾难。
    • 

  • 即使是"内部"系统也不应。
    • 



反模式 6：Reversible encryption：


    

  • 用 AES 加密 password 而非 hash。
    • 

  • 任何泄露 + key 泄露 = 灾难。
    • 



反模式 7：Limit password length：


    

  • max 8 char password 限制 entropy。
    • 

  • Argon2 / bcrypt 支持 long password（除 bcrypt 72 byte limit）。
    • 



密码强度政策
密码本身的强度：


    

  • 长度 ≥ 12（NIST 2024）。
    • 

  • 不强制特殊字符（用户用 P@ssw0rd1 不更安全）。
    • 

  • 不要 force frequent change（让用户写到便签上）。
    • 

  • 检查 against common password list（HaveIBeenPwned）。
    • 



MFA：


    

  • 密码即使被破，second factor（TOTP / FIDO2）保护。
    • 

  • 现代标准。
    • 



数据 breach 应对
发现 breach 后：


    

  1. 立即 disable 受影响 user accounts。
    2. 

  2. Force password reset 给所有 user。
    3. 

  3. 通知用户。
    4. 

  4. 监控 dark web（看密码是否流通）。
    5. 

  5. 法律披露（GDPR / 各州 breach notification laws）。
    6. 

  6. 复盘并改进。
    7. 



小结
密码存储是 Web 应用最常被破坏的安全环节——选错算法让数据 breach 灾难升级。通用 hash（SHA-256 / MD5）太快（GPU 10^9 hash/s）不适合密码——需要故意慢的 password hashing 函数。Salt（per-user 16 byte random）防 rainbow table，Pepper（应用级 secret 存 KMS）给 server-side 额外保护。bcrypt（1999）基于 Blowfish 故意慢，cost factor 12 推荐（~250ms），password ≤ 72 byte。scrypt（2009）内存硬度（GPU/ASIC 抗），用于 Litecoin / disk encryption。Argon2（2015 PHC winner）内存硬度 + 多线程，Argon2id 是 OWASP top recommendation（m=19MiB, t=2, p=1）。PBKDF2 NIST FIPS 兼容但无 memory hardness，仅 600k+ iterations 才安全。Work factor 调优——单 hash 100-500ms 是 sweet spot，每年 update 跟硬件。迁移策略——layered hash、force reset、lazy migration。常见反模式——直接 SHA-256、自实现、salt 短/全局、硬编码 cost、明文存、reversible encryption、limit length。密码政策——长度 ≥12、不强制特殊字符、不 frequent change、检查 common password list、强制 MFA。Breach 应对——disable、reset、通知、监控、披露、复盘。一个简单的检验：你能解释为什么"用 SHA-256(password) 是灾难但 SHA-256 用作 hash 是 fine"？如果不能，密码 hash 与通用 hash 的区别还需巩固。密码 hash 是密码学应用的"低悬果实"——选对算法 + 正确参数让 breach 损害降低 100x，但仍是大量公司的失败点。
