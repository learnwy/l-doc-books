公钥基础设施（PKI）

核心概念

PKI（Public Key Infrastructure）解决公钥密码学最核心的"信任问题"——你拿到一个公钥，怎么确信它真是你想要联系对象的公钥而不是攻击者的？没有 PKI 任何 secure 通信都建立在"我已经有对方公钥"的假设上——而初次通信不可能。PKI 引入"可信第三方"（CA：Certificate Authority）：CA 验证身份后给公钥发证书（certificate），任何 trust CA 的人都 trust 证书。本节介绍 X.509 证书结构、CA 信任链、证书生命周期、Let's Encrypt 让 HTTPS 民主化、Certificate Transparency 监督 CA、未来的 Web of Trust 与去中心化 PKI。

组件 职责 例子
Subject 证书持有者 google.com
Issuer (CA) 签发者 Let's Encrypt
Public Key Subject 的公钥 RSA 2048 / ECDSA P-256
Validity 起止时间 90 天 / 13 月
Signature CA 私钥对证书签名 SHA-256 + RSA
Extensions 用途、SAN、policies Server auth, *.com

X.509 证书结构

X.509 v3 是最广泛部署的证书格式（RFC 5280）：

Certificate ::= {
  Version (v3)
  Serial Number
  Signature Algorithm（CA 签名用什么）
  Issuer（CA 名）
  Validity（Not Before, Not After）
  Subject（证书持有者）
  Subject Public Key Info（公钥 + 算法）
  Extensions（v3）
    - Subject Alternative Name (SAN)
    - Key Usage（digital signature, key encipherment...）
    - Extended Key Usage（serverAuth, clientAuth...）
    - Basic Constraints（CA: TRUE/FALSE）
    - CRL Distribution Points
    - OCSP Responder URL
  Signature（CA 私钥签整个证书）
}

SAN（Subject Alternative Name）：

  • 现代 HTTPS 必须用 SAN（Common Name 已弃用）。
  • 列出所有匹配域名（example.com, www.example.com, *.example.com）。

Wildcard 证书：

  • *.example.com 匹配 a.example.com 但不匹配 a.b.example.com。
  • 不能 *.com（CA 拒绝）。

密钥用途（Key Usage / EKU）：

  • serverAuth（HTTPS server）。
  • clientAuth（mTLS client）。
  • codeSigning（代码签名）。
  • emailProtection（S/MIME）。

证书签名流程

1. CSR（Certificate Signing Request）生成：

openssl req -new -newkey rsa:2048 -keyout private.key -out request.csr \
    -subj "/CN=example.com"

CSR 包含 subject + 公钥 + 用 subject 私钥的自签名（证明 subject 持有私钥）。

2. CA 验证身份：

  • DV（Domain Validation）：确认你控制 example.com（HTTP-01 / DNS-01 challenge）。
  • OV（Organization Validation）：人工审核组织身份。
  • EV（Extended Validation）：严格审核（绿条已弃用）。

3. CA 签发证书：

  • CA 用自己私钥签 CSR。
  • 返回签好的 certificate。

4. 部署：

  • Web server 配置 cert + key。
  • 客户端验证。
信任链
根 CA → 中间 CA → 终端证书：


Root CA: ISRG Root X1（Let's Encrypt 的根）
  ↓ 签发
Intermediate CA: R3（Let's Encrypt 的中间证书）
  ↓ 签发
End Cert: example.com
为什么有中间 CA：


    

  • Root 私钥 offline 安全（HSM、physical safe）。
    • 

  • Intermediate 在线签发证书。
    • 

  • 中间 CA 泄露不影响 root（可 revoke 中间 CA）。
    • 



浏览器 trust store：


    

  • Chrome、Firefox、Safari、OS 各有 trust store。
    • 

  • 包含 ~100-200 root CA。
    • 

  • 验证证书时反向构建 chain 直到 trust store 中的 root。
    • 



Mozilla CA 政策：


    

  • Mozilla 维护开源 root CA 列表。
    • 

  • Linux distribution、Python certifi 等基于此。
    • 



证书验证流程
浏览器收到证书后：


1. 解析证书 → 拿到 cert chain。
2. 验证每张证书的签名（用上一级 CA 的公钥）。
3. 检查 root CA 在 trust store 中。
4. 验证 valid period（now ∈ [Not Before, Not After]）。
5. 检查 SAN 匹配 hostname。
6. 检查 revocation（CRL / OCSP）。
7. 验证 EKU 包含 serverAuth。
8. 验证 Certificate Transparency（部分浏览器）。
任一步失败 → 证书 invalid → 连接拒绝（除非用户 override）。


CRL 与 OCSP（撤销）
为什么需要撤销：


    

  • 私钥泄露 → 证书必须 invalidate before 自然过期。
    • 

  • CA 错误签发 → revoke。
    • 



CRL（Certificate Revocation List）：


    

  • CA 定期发布"已撤销"列表（每周）。
    • 

  • 客户端下载后查询。
    • 

  • 缺点：大（数千证书）、不实时。
    • 



OCSP（Online Certificate Status Protocol）：


    

  • 客户端实时查询 CA："这张证书还有效吗？"
    • 

  • 缺点：privacy（CA 知道用户访问哪些站）、性能、依赖 CA 在线。
    • 



OCSP Stapling：


    

  • Server 提前从 CA 获取 OCSP response。
    • 

  • 在 TLS handshake 中提供。
    • 

  • 解决 privacy + 性能问题。
    • 



Short-lived certs：


    

  • Let's Encrypt 90 天有效。
    • 

  • 缩短 revocation window，部分替代 OCSP。
    • 



Let's Encrypt 民主化 HTTPS
背景：2015 之前 HTTPS 证书每年 $50-500，让小网站不愿用。


Let's Encrypt（2016）：


    

  • 免费 DV 证书。
    • 

  • 自动化（ACME 协议）。
    • 

  • 90 天证书 + 自动 renewal。
    • 

  • 现在签发 ~ 50% 互联网证书。
    • 



ACME 协议：


1. 客户端（certbot）联系 Let's Encrypt。
2. LE 提供 challenge：
   - HTTP-01：在 /.well-known/acme-challenge/X 放文件。
   - DNS-01：添加 _acme-challenge.example.com TXT 记录。
3. 客户端完成 challenge。
4. LE 验证 → 签发证书。
5. 客户端 90 天前自动续期。
影响：


    

  • 全球 HTTPS 普及率从 ~30%（2015）到 ~90%（2025）。
    • 

  • 小网站、博客、IoT 设备都能 HTTPS。
    • 



Certificate Transparency
问题：CA 错误 / 恶意签发证书无人发现：


    

  • 2011 DigiNotar 被入侵 → 签发假 google.com 证书 → 用于伊朗 MITM。
    • 

  • 2015 Symantec 错误签发 google.com 测试证书 → 信任危机。
    • 



Certificate Transparency（CT，RFC 6962）：


    

  • CA 把签发的证书提交到 CT log（append-only Merkle tree）。
    • 

  • Log 是公开的——任何人可监督。
    • 

  • 浏览器要求 cert 必须有 CT log 证明（SCT：Signed Certificate Timestamp）。
    • 



好处：


    

  • Domain 拥有者可监控 CT log → 检测未授权签发。
    • 

  • CA 的错误 / 恶意被公开发现。
    • 

  • 多个 log（Google、Cloudflare、Sectigo 等）增强可信度。
    • 



Chrome 2018 起强制：所有公开信任 cert 必须有 CT。


CA 历史事件
2011 DigiNotar：


    

  • 荷兰 CA 被入侵。
    • 

  • 签发假 google.com 证书。
    • 

  • 用于伊朗政府 MITM Gmail。
    • 

  • DigiNotar 倒闭。
    • 



2015 Symantec：


    

  • 错误签发数千 cert。
    • 

  • 浏览器 distrust，最终所有 Symantec cert 失效。
    • 

  • Symantec 卖 cert 业务给 DigiCert。
    • 



2017 WoSign：


    

  • 中国 CA 不当签发。
    • 

  • 浏览器 distrust。
    • 



教训：CA 是单点信任——出错影响巨大。CT + 浏览器 policy + 监督机制必须强。


自签名证书
自签名 cert：


    

  • subject = issuer（自己签自己）。
    • 

  • 不在 trust chain 中。
    • 

  • 浏览器警告"NOT SECURE"。
    • 



用途：


    

  • 内部 / 开发环境（绕过 CA）。
    • 

  • 自建 CA（企业内部 PKI）。
    • 



不要用于公开网站——用户看到警告会忽略，反而 train 不安全行为。


企业 PKI
自建内部 CA：


    

  • 企业 root CA + intermediate。
    • 

  • 部署到员工设备 trust store。
    • 

  • 签发内部服务证书、员工 client cert（mTLS）。
    • 



用途：


    

  • mTLS（mutual TLS）—— client 也持证书。
    • 

  • VPN（IPsec / OpenVPN）。
    • 

  • 内部 service mesh（Istio、Linkerd）。
    • 

  • 代码签名（内部 build）。
    • 



工具：


    

  • HashiCorp Vault PKI engine。
    • 

  • step-ca（开源）。
    • 

  • AWS Private CA。
    • 



去中心化 PKI 的探索
Web of Trust（PGP）：


    

  • 没有中央 CA。
    • 

  • 用户互相签名 → 信任图。
    • 

  • 部分朋友签 Alice 公钥 → 你 trust。
    • 

  • 历史：PGP / GPG 用，但 UX 差，没有规模化。
    • 



DNS-based（DANE）：


    

  • DNSSEC 中存证书 hash。
    • 

  • 不依赖 CA。
    • 

  • 部署不广。
    • 



区块链 PKI：


    

  • 把证书放区块链。
    • 

  • ENS（Ethereum Name Service）。
    • 

  • 早期实验。
    • 



Decentralized Identity（DID）：


    

  • W3C 标准。
    • 

  • 用户控制自己 DID。
    • 

  • 与 verifiable credentials 配合。
    • 



未来：post-quantum PKI
威胁：Shor 算法破 RSA / ECC → 所有 X.509 证书失效。


应对：


    

  • NIST 2024 标准化 ML-DSA（lattice 签名）。
    • 

  • Hybrid 证书（RSA + ML-DSA）transition。
    • 

  • 可能 10-15 年完全替换。
    • 



小结
PKI 解决公钥密码学的"信任问题"——通过 CA 签发证书让任何人 trust 公钥。X.509 v3 证书结构包含 subject、issuer、public key、validity、extensions（SAN、key usage、basic constraints）、signature。证书签发流程——CSR 生成 → CA 验证（DV / OV / EV）→ CA 签发 → 部署。信任链——root CA → intermediate CA → end cert，浏览器 trust store ~100-200 root。证书验证——签名、有效期、SAN 匹配、revocation、EKU、CT。CRL 慢，OCSP 实时但有 privacy 问题，OCSP Stapling 是现代解。Let's Encrypt 2016 用 ACME 协议免费自动化签发，HTTPS 全球普及率从 30% 到 90%。Certificate Transparency 让 CA 签发公开可监督——Chrome 2018 强制。CA 历史事件——DigiNotar（2011）、Symantec（2015）、WoSign（2017）证明 CA 是单点信任风险。自签名证书仅内部 / 开发用。企业自建 CA 用于 mTLS / VPN / service mesh / 代码签名（Vault、step-ca、AWS PCA）。去中心化 PKI 探索——Web of Trust（PGP，UX 差）、DANE（部署不广）、区块链 PKI / DID（早期）。未来 post-quantum PKI——ML-DSA hybrid transition，10-15 年完全替换。一个简单的检验：你能解释 Let's Encrypt ACME 协议的 4 个步骤？如果不能，证书签发流程还需巩固。PKI 是密码学落地到互联网的"最后一公里"——让公钥密码不只是数学，而是支撑 90% 互联网流量的信任基础设施。
