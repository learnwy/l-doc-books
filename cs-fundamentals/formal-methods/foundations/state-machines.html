状态机与形式化建模

核心概念

状态机（State Machine）是形式化方法中最基础、最直观的建模工具。它通过有限个状态和状态之间的转换关系来描述系统的动态行为。在形式化方法中，状态机不仅是理解系统行为的思维工具，更是模型检测和自动化验证的输入模型。

有限状态机可以分为确定性有限自动机（DFA）和非确定性有限自动机（NFA），在系统建模中通常使用扩展有限状态机（EFSM）或层次状态机（Statecharts）。不同类型的状态机在表达能力和分析复杂度之间存在不同的权衡。

Kripke 结构与模型检测基础
Kripke 结构是模型检测理论中最重要的语义模型。一个 Kripke 结构 M = (S, S₀, R, L) 由四个部分组成：状态集合 S、初始状态集合 S₀、转换关系 R ⊆ S × S 和标记函数 L: S → 2^AP（AP 是原子命题集）。


与普通有限自动机不同，Kripke 结构没有接受状态的概念，它的重点在于刻画系统的所有可能执行路径。每条从初始状态开始的无限路径代表系统的一次可能执行，模型检测就是在所有这些路径上检查给定的时序逻辑属性。


考虑一个简单的互斥锁协议，两个进程 P1 和 P2 竞争一个共享资源：


状态空间:
  s0: (idle, idle)       -- 两进程都空闲
  s1: (trying, idle)     -- P1 尝试获取锁
  s2: (idle, trying)     -- P2 尝试获取锁
  s3: (trying, trying)   -- 两进程同时尝试
  s4: (critical, idle)   -- P1 在临界区
  s5: (idle, critical)   -- P2 在临界区

转换关系:
  s0 → s1, s0 → s2
  s1 → s3, s1 → s4
  s2 → s3, s2 → s5
  s3 → s4, s3 → s5
  s4 → s0, s5 → s0

需要验证的属性:
  互斥性: AG ¬(critical₁ ∧ critical₂)   -- 永远不会两个进程同时在临界区
  无饥饿: AG(trying₁ → AF critical₁)    -- 如果尝试获取锁，最终会成功
Kripke 结构的一个关键挑战是状态爆炸问题（State Explosion）。当系统由多个并发组件组成时，全局状态空间是各组件状态空间的笛卡尔积，导致指数级增长。应对这一挑战的主要技术包括符号模型检测（BDD）、偏序归约和抽象精化。


扩展有限状态机
扩展有限状态机（EFSM）在传统有限状态机基础上增加了变量、守卫条件（Guard）和动作（Action）。这使得 EFSM 能够表达比纯有限状态机更复杂的行为，同时保持状态图的直观性。


EFSM 的形式化定义为六元组 (S, s₀, V, I, O, T)，其中 T 是转换集合，每个转换 t = (sₛ, sₜ, i, g, a) 包含源状态、目标状态、输入、守卫条件和动作。


以 TCP 连接管理的简化模型为例：


EFSM: SimplifiedTCP

Variables:
  seq_num : nat := 0
  ack_num : nat := 0
  retries : nat := 0

States: {CLOSED, LISTEN, SYN_SENT, SYN_RCVD, ESTABLISHED, FIN_WAIT, CLOSE_WAIT, TIME_WAIT}

Transitions:
  CLOSED --[passive_open]--> LISTEN
  CLOSED --[active_open / send SYN(seq_num)]--> SYN_SENT
  LISTEN --[recv SYN(n) / ack_num:=n+1; send SYN_ACK(seq_num, ack_num)]--> SYN_RCVD
  SYN_SENT --[recv SYN_ACK(n,m) [m == seq_num+1] / seq_num:=m; send ACK(seq_num, n+1)]--> ESTABLISHED
  SYN_RCVD --[recv ACK(n) [n == seq_num+1] / seq_num:=n]--> ESTABLISHED
  ESTABLISHED --[close / send FIN(seq_num)]--> FIN_WAIT
  ESTABLISHED --[recv FIN(n) / send ACK(n+1)]--> CLOSE_WAIT
  FIN_WAIT --[recv ACK / ]--> TIME_WAIT
  TIME_WAIT --[timeout]--> CLOSED
  CLOSE_WAIT --[close / send FIN(seq_num)]--> CLOSED
EFSM 的验证方法通常需要将变量域有限化（通过抽象或边界限制），然后展开为纯有限状态系统进行模型检测。TLA+ 和 UPPAAL 等工具原生支持 EFSM 风格的建模。


Statecharts 与层次状态机
Statecharts 由 David Harel 在 1987 年提出，是对传统状态图的三个重要扩展：层次性（Hierarchy）、并发性（Concurrency）和通信机制（Communication）。这些扩展使得 Statecharts 能够紧凑地描述复杂的反应式系统。


层次性通过超状态（Superstate）实现，一个超状态包含多个子状态。当系统处于某个子状态时，它同时也处于其父超状态中。这种层次关系允许在不同抽象层次上描述系统行为：


Statecharts 的并发性通过正交区域（Orthogonal Region）实现。一个超状态可以包含多个正交区域，每个区域独立运行自己的子状态机。正交区域之间通过广播事件进行通信。

在前端开发中，XState 库将 Statecharts 理论带入了 JavaScript 世界。XState 允许开发者使用状态机管理复杂的 UI 状态，避免了传统状态管理中常见的不可能状态和隐式状态转换问题：


import { createMachine } from 'xstate';

const fetchMachine = createMachine({
  id: 'fetch',
  initial: 'idle',
  context: { retries: 0, data: null },
  states: {
    idle: { on: { FETCH: 'loading' } },
    loading: {
      invoke: {
        src: 'fetchData',
        onDone: { target: 'success', actions: 'setData' },
        onError: [{ target: 'loading', guard: 'canRetry', actions: 'incrementRetry' }, { target: 'failure' }],
      },
    },
    success: { type: 'final' },
    failure: { on: { RETRY: 'loading' } },
  },
});
Petri 网与并发建模
Petri 网是 Carl Adam Petri 在 1962 年提出的并发系统建模工具。与状态机不同，Petri 网天然支持并发和同步的表达，无需展开所有全局状态。一个 Petri 网由库所（Place）、变迁（Transition）和弧（Arc）组成，库所中的令牌（Token）表示系统的当前状态。


Petri 网的执行规则简单但强大：当一个变迁的所有输入库所都有足够的令牌时，该变迁是使能的（enabled），使能的变迁可以发射（fire），消耗输入令牌并在输出库所中产生新令牌。

Petri 网的分析方法包括可达性分析（Reachability Analysis）、不变量分析（Invariant Analysis）和结构分析。可达性分析构造可达性图来检查是否存在死锁（某个可达标记下没有使能的变迁），不变量分析通过求解线性方程来发现系统的守恒性质。


有色 Petri 网（CPN, Colored Petri Net）是 Petri 网的重要扩展，它允许令牌携带数据（颜色），使得建模更加紧凑。CPN Tools 是使用最广泛的有色 Petri 网建模和分析工具。


小结
    

  • 状态机是形式化建模的基础工具，不同类型的状态机在表达能力和分析复杂度之间各有权衡
    • 

  • Kripke 结构是模型检测的语义基础，但面临状态爆炸的核心挑战
    • 

  • 扩展有限状态机通过变量和守卫条件增强了表达能力，适合描述通信协议等数据相关行为
    • 

  • Statecharts 通过层次、并发和通信三个扩展使得复杂系统的建模更加紧凑
    • 

  • Petri 网天然支持并发和同步的建模，能够直接表达冲突、互斥等并发模式
    • 

  • 前端领域的 XState 库证明了状态机理论在实际软件开发中的实用价值
    • 

  • 选择合适的状态机形式取决于系统特性：顺序用 FSM，带数据用 EFSM，层次并发用 Statecharts，纯并发用 Petri 网
    •
