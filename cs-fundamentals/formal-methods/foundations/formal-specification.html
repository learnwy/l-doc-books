形式化规约

核心概念

形式化规约（Formal Specification）是使用数学化语言精确描述软件系统行为和属性的方法。与自然语言需求文档不同，形式化规约具有无二义性、可验证性和可推理性等特点，能够在软件开发早期发现设计缺陷，从而大幅降低后期修复成本。

形式化规约的核心思想是将系统需求转化为数学对象，使得需求可以被严格检验和推导。在航空航天、医疗设备、金融交易等高可靠性领域，形式化规约已成为质量保证的关键手段。

Z 语言与模型规约
Z 语言是由牛津大学开发的基于集合论和一阶谓词逻辑的规约语言，它通过"Schema"（模式）来组织规约的各个部分。每个 Schema 包含声明部分和谓词部分，声明定义变量及其类型，谓词则约束变量之间的关系。


Z 语言的核心构造是 Schema Box，形式如下：


┌── BirthdayBook ──────────────
│ known : ℙ NAME
│ birthday : NAME ⇸ DATE
├──────────────────────────────
│ known = dom birthday
└──────────────────────────────
这个 Schema 描述了一个生日簿系统：known 是已知姓名的集合，birthday 是从姓名到日期的偏函数，谓词部分约束 known 恰好是 birthday 函数的定义域。


Z 语言的操作通过 ΔSchema（状态变更）和 ΞSchema（状态不变）来描述。例如添加生日的操作：


┌── AddBirthday ───────────────
│ ΔBirthdayBook
│ name? : NAME
│ date? : DATE
├──────────────────────────────
│ name? ∉ known
│ birthday' = birthday ∪ {name? ↦ date?}
└──────────────────────────────
其中 ? 后缀表示输入变量，' 后缀表示操作后的状态。这种表示法使得前置条件（name? ∉ known）和后置条件的关系一目了然。


Z 语言的优势在于其数学基础坚实、表达能力强大，适合描述复杂的数据结构和操作语义。它在 IBM CICS 交易系统的重新规约中取得了巨大成功，将文档从数千页非形式化描述精简为精确的数学规约。


VDM 方法
VDM（Vienna Development Method）是最早的形式化开发方法之一，由 IBM 维也纳实验室在 1970 年代开发。VDM 不仅是一种规约语言（VDM-SL），更是一套完整的软件开发方法学，涵盖从抽象规约到具体实现的逐步精化过程。


VDM-SL 提供了丰富的类型系统，包括基本类型、复合类型、集合类型、序列类型和映射类型：


types
  StudentId = nat
  Grade = nat
  inv g == g >= 0 and g <= 100

  GradeBook = map StudentId to Grade

functions
  addGrade: GradeBook * StudentId * Grade -> GradeBook
  addGrade(book, sid, grade) ==
    book munion {sid |-> grade}
  pre sid not in set dom book

  getAverage: GradeBook -> real
  getAverage(book) ==
    let grades = rng book in
      sum(grades) / card grades
  pre card dom book > 0
VDM 的精化过程包含数据精化和操作精化两个维度。数据精化将抽象数据表示转换为更具体的数据结构，操作精化将抽象操作转换为可执行的算法。每次精化都需要通过精化证明来保证正确性。


VDM 的精化证明关注两个关键性质：






证明义务
含义
验证内容





充分性（Adequacy）
具体表示能覆盖所有抽象状态
检索函数是满射




正确性（Correctness）
具体操作保持抽象语义

域规则（Domain Rule）
具体操作的定义域不小于抽象操作
前置条件放宽或不变




结果规则（Result Rule）
具体操作的结果满足抽象后置条件
后置条件收紧或不变





VDM Overture 工具支持 VDM-SL 规约的编辑、类型检查和测试执行，使得 VDM 方法在教学和工业实践中得到广泛应用。


B 方法与 Event-B
B 方法由 Jean-Raymond Abrial 在 1990 年代提出，是一种基于抽象机（Abstract Machine）概念的形式化开发方法。B 方法的核心特点是将规约和精化统一在一个框架内，通过工具自动生成证明义务。


B 方法中的抽象机由三个主要部分组成：变量（VARIABLES）、不变式（INVARIANT）和操作（OPERATIONS）：


MACHINE SimpleStack
VARIABLES
  stack, size
INVARIANT
  stack : seq(INTEGER) &
  size : NAT &
  size = card(stack)
INITIALISATION
  stack := <> ||
  size := 0
OPERATIONS
  push(val) =
    PRE val : INTEGER
    THEN
      stack := val -> stack ||
      size := size + 1
    END;
  val <-- pop =
    PRE size > 0
    THEN
      val := first(stack) ||
      stack := tail(stack) ||
      size := size - 1
    END
END
Event-B 是 B 方法的演进版本，引入了事件（Event）概念替代操作，更适合对反应式系统和并发系统建模。Event-B 使用 Rodin 平台作为开发工具，提供自动和交互式证明支持。

B 方法在巴黎地铁 14 号线自动驾驶系统中得到了成功应用。该项目使用 B 方法对列车控制软件进行了完整的形式化开发，从抽象规约到可执行代码的全过程都经过了严格证明，最终系统投入运行后未发现任何安全关键缺陷。


规约的精化与验证
形式化规约的价值不仅在于精确描述需求，更在于它为系统的正确性验证提供了坚实基础。规约的精化（Refinement）是连接抽象需求和具体实现的桥梁，而验证则确保每一步精化都保持了原有的语义属性。


精化过程可以分为多个层次：


精化的正确性通过模拟关系（Simulation Relation）来保证。设抽象规约为 A，具体实现为 C，检索函数（Retrieve Function）R 建立两者之间的对应关系。正向模拟要求：对于 A 的每一步转换，C 都能通过一步或多步转换来模拟。


在实际开发中，精化策略的选择直接影响开发效率和证明难度。常见的策略包括：


    

  • 数据精化：将抽象数据类型替换为更具体的数据结构（如集合→数组）
    • 

  • 算法精化：将非确定性规约替换为确定性算法
    • 

  • 分解精化：将单一操作分解为多个子步骤
    • 

  • 并发精化：在顺序规约基础上引入并行结构
    • 



规约验证的工具链通常包括类型检查器、模型检测器和定理证明器。类型检查器可以自动发现类型错误，模型检测器可以在有限状态空间内穷举检查属性，定理证明器则可以处理无限状态空间的证明任务。这三种工具互为补充，构成了完整的验证体系。


小结
    

  • 形式化规约使用数学语言精确描述系统行为，消除自然语言的二义性
    • 

  • Z 语言基于集合论和谓词逻辑，通过 Schema 组织规约，适合描述复杂数据结构
    • 

  • VDM 是完整的开发方法学，提供从规约到实现的逐步精化框架
    • 

  • B 方法通过抽象机概念统一规约和精化，Event-B 扩展了并发系统建模能力
    • 

  • 精化过程通过模拟关系保证正确性，每一步精化都需要证明义务
    • 

  • 形式化规约在安全关键系统（航空、铁路、医疗）中已有成功的工业应用
    • 

  • 选择规约方法需要权衡表达能力、工具支持和团队技能等因素
    •
