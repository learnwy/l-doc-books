Paxos 协议

概述

Paxos 是 Leslie Lamport 于 1990 年提出的分布式共识算法，是第一个被严格证明正确性的共识协议。尽管以"难以理解"著称，Paxos 的核心思想——通过两阶段提案实现多数派共识——仍然是所有现代共识算法的理论基础。

角色定义

角色 职责 说明
Proposer 发起提案（Proposal） 可以有多个，竞争提案权
Acceptor 接受或拒绝提案 构成投票的多数派
Learner 学习最终确定的值 不参与投票，只接收结果

在实际系统中，一个节点通常同时扮演多个角色。

活锁问题
当两个 Proposer 交替用更高编号打断对方时，可能导致无限循环：


Proposer A: Prepare(1) → 成功
Proposer B: Prepare(2) → 成功，A 的 Accept(1) 被拒绝
Proposer A: Prepare(3) → 成功，B 的 Accept(2) 被拒绝
... 无限循环
解决方案：选举一个 Leader Proposer（Distinguished Proposer），避免多个 Proposer 竞争。

提案编号生成
提案编号必须全局唯一且递增，常见方案：


class ProposalNumber:
    def __init__(self, node_id: int, total_nodes: int):
        self.node_id = node_id
        self.total_nodes = total_nodes
        self.round = 0

    def next(self) -> int:
        self.round += 1
        return self.round * self.total_nodes + self.node_id

工程实现注意事项
    

  • 提案编号必须持久化到磁盘，崩溃恢复后不能重复使用
    • 

  • Acceptor 的 Promise 和 Accept 状态必须在回复前落盘
    • 

  • 网络分区时 Paxos 保证安全性但可能阻塞（牺牲活性）
    • 

  • 实际系统通常使用 Multi-Paxos 而非 Basic Paxos
    • 

  • Google Chubby 和 Spanner 是 Paxos 在工业界的典型应用
    • 





最佳实践
    

  • 理解 Paxos 的理论价值，但工程实现优先考虑 Raft（更易正确实现）
    • 

  • 使用 Multi-Paxos 的 Leader 优化减少消息轮次
    • 

  • 持久化是正确性的前提——所有承诺和接受决定必须先写 WAL 再回复
    • 

  • 通过随机退避解决活锁，而非确定性等待
    • 

  • 使用 Paxos Made Simple 而非原始论文作为学习起点
    •
