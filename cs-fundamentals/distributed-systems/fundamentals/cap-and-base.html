CAP 定理与 BASE

概述

CAP 定理是分布式系统设计的基石理论。它指出一个分布式系统不可能同时满足一致性（Consistency）、可用性（Availability）和分区容错性（Partition Tolerance）三个保证。理解 CAP 及其实际影响，是做出正确架构决策的前提。

CAP 定理

三要素定义

属性 含义 通俗解释
一致性 Consistency 所有节点同一时刻看到相同数据 读到的永远是最新写入
可用性 Availability 每个请求都能收到非错误响应 系统始终能响应
分区容错 Partition Tolerance 网络分区时系统仍能运行 节点间断网不影响服务

BASE 三要素详解
Basically Available（基本可用）
系统在出现故障时仍能提供服务，但可能降级：


    

  • 响应时间变长（从 100ms 到 2s）
    • 

  • 功能降级（电商降级为只读模式）
    • 

  • 部分数据不可用（某分片离线）
    • 



Soft State（软状态）
系统中的数据状态可能在没有外部输入的情况下随时间变化：


Eventually Consistent（最终一致性）
在没有新的写入操作的前提下，所有副本最终会收敛到相同状态。

实际系统的 CAP 策略
分级一致性
class ConsistencyLevel:
    ONE = 1
    QUORUM = 2
    ALL = 3

def write(key, value, consistency=ConsistencyLevel.QUORUM):
    acks = replicate_to_nodes(key, value)
    if acks >= consistency:
        return "OK"
    raise ConsistencyError("Not enough acknowledgements")

最佳实践
    

  • 不要在整个系统层面做 CAP 选择——不同业务域可以有不同策略
    • 

  • 金融核心链路选择 CP，用户体验链路选择 AP
    • 

  • 使用 Quorum 机制（W + R > N）在一致性和延迟之间取得平衡
    • 

  • 理解 PACELC：正常运行时的延迟权衡往往比分区时的选择更常见
    • 

  • 设计补偿机制（如 saga pattern）处理最终一致性带来的中间状态
