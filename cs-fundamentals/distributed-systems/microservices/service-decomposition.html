服务拆分与边界

概述

微服务架构的首要挑战是如何合理拆分服务。拆分过粗，无法享受微服务的灵活性；拆分过细，分布式通信和数据一致性的成本会吞噬所有收益。领域驱动设计（DDD）提供了一套方法论，帮助我们识别业务边界，将系统分解为高内聚、低耦合的服务。

单体 vs 微服务

维度 单体架构 微服务架构
部署 整体部署 独立部署
技术栈 统一 可异构
扩展 整体扩展 按服务扩展
数据库 共享数据库 每服务独立数据库
团队 大团队协作 小团队自治
复杂度 代码复杂度 运维复杂度

最佳实践
    

  • 遵循"两个比萨团队"原则——每个服务由一个小团队（6-8 人）负责
    • 

  • 从单体出发，在业务成熟、边界清晰后再拆分（Monolith First）
    • 

  • 每个服务拥有自己的数据存储，通过 API 或事件共享数据
    • 

  • 使用事件驱动（异步消息）替代同步链式调用，降低耦合
    • 

  • 拆分后务必建立完善的 CI/CD 流水线，支持独立部署
    • 

  • 定期评审服务边界，根据业务变化调整拆分策略
