单体与微服务

单体架构

单体架构（Monolith）将应用的所有功能模块打包在一个部署单元中。所有代码共享同一个进程、同一个数据库、同一个部署管道。

单体的优势
const MONOLITH_ADVANTAGES = {
  simpleDevelopment: '所有代码在一个仓库，IDE 直接导航和重构',
  easyDebugging: '单进程调试，调用链清晰',
  simpleDeployment: '一个制品、一次部署',
  noNetworkOverhead: '模块间调用是函数调用，没有网络延迟',
  transactionSimple: '数据库事务直接保证一致性',
  teamAlignment: '小团队高效协作，无需跨服务沟通',
};
单体的痛点
随着系统规模增长，单体架构会逐渐暴露问题：






问题
描述





部署耦合
修改任何模块都需要重新部署整个应用




扩展受限
无法独立扩展高负载模块




技术栈锁定
所有模块必须使用相同的语言和框架




启动时间
应用体积增大，启动时间越来越长




可靠性风险
一个模块的内存泄漏可能导致整个应用崩溃




团队瓶颈
代码冲突频繁，发布需要多团队协调







微服务架构
微服务架构将应用拆分为多个独立部署的小服务，每个服务围绕一个业务能力构建，拥有自己的数据存储和部署管道。


微服务的核心原则




原则
描述





单一职责
每个服务围绕一个业务能力




独立部署
修改一个服务不需要重新部署其他服务




数据自治
每个服务拥有自己的数据存储




技术异构
每个服务可以使用最合适的技术栈




容错设计
一个服务故障不应导致整个系统不可用





服务间通信
interface ServiceRegistry {
  register(name: string, address: string): Promise<void>;
  discover(name: string): Promise<string[]>;
  deregister(name: string, address: string): Promise<void>;
}

class HttpServiceClient {
  private registry: ServiceRegistry;

  constructor(registry: ServiceRegistry) {
    this.registry = registry;
  }

  async call<T>(serviceName: string, path: string): Promise<T> {
    const instances = await this.registry.discover(serviceName);
    if (instances.length === 0) {
      throw new Error(`No instances available for ${serviceName}`);
    }

    const instance = instances[Math.floor(Math.random() * instances.length)];
    const response = await fetch(`${instance}${path}`);

    if (!response.ok) {
      throw new Error(`Service call failed: ${response.status}`);
    }

    return response.json() as Promise<T>;
  }
}

演进路径
Amazon 的演进经验特别有代表性：2001 年的 Amazon 是一个庞大的单体应用，随着团队和业务的增长，逐步拆分为独立的服务。Jeff Bezos 著名的"API Mandate"要求所有团队通过 API 暴露功能、不允许直接访问其他团队的数据库——这个决定奠定了 Amazon 微服务架构的基础，也间接催生了 AWS。


何时该拆分
const SPLIT_SIGNALS = {
  deploymentPain: '每次部署需要多个团队协调，发布周期越来越长',
  scaleBottleneck: '某个模块需要 10x 算力但只能整体扩展',
  teamGrowth: '团队超过 15-20 人，代码冲突严重',
  techDebt: '想引入新技术但被现有框架限制',
  reliabilityIssue: '非核心模块的 bug 导致核心服务不可用',
};

const DONT_SPLIT_SIGNALS = {
  earlyStage: '产品还在寻找 PMF，需求变化快',
  smallTeam: '团队不到 10 人',
  noOperationalMaturity: '没有容器化、CI/CD、监控等基础设施',
  domainUnclear: '业务边界不清晰，不知道怎么拆',
};


小结
    

  • 单体不是反模式——对于小团队和早期产品，单体是最高效的选择。
    • 

  • 微服务的核心价值是独立部署和独立扩展，但代价是分布式系统的复杂性。
    • 

  • "先单体，后微服务"是被广泛验证的演进路径。
    • 

  • 拆分的时机取决于团队规模、部署痛点和扩展需求。
