Part IV · 网络与分布式 (Networks & Distributed)系统设计 简介基础概念 简介CAP 定理与权衡

CAP 定理与权衡

CAP 定理的核心内容

CAP 定理（又称布鲁尔定理）是分布式系统设计中最基础的理论框架。它指出，在一个分布式系统中，以下三个属性最多只能同时满足两个：

  • C（Consistency）一致性：所有节点在同一时刻看到相同的数据
  • A（Availability）可用性：每个请求都能收到非错误的响应（不保证是最新数据）
  • P（Partition Tolerance）分区容错性：即使网络分区发生，系统仍能继续运行
在网络环境中，分区（Partition）是不可避免的——网络延迟、交换机故障、光纤切断随时可能发生。因此，P 是必须保证的。这意味着实际的选择是在 C 和 A 之间做权衡。

CP 系统的行为
当网络分区发生时，CP 系统拒绝不一致的请求：


interface CPNode {
  id: string;
  data: Map<string, string>;
  peers: CPNode[];
  isPartitioned: boolean;
}

function cpRead(node: CPNode, key: string): string | Error {
  if (node.isPartitioned) {
    throw new Error('Service Unavailable: cannot guarantee consistency');
  }

  const quorumSize = Math.floor(node.peers.length / 2) + 1;
  const responses = node.peers.filter((peer) => !peer.isPartitioned).map((peer) => peer.data.get(key));

  if (responses.length < quorumSize) {
    throw new Error('Service Unavailable: quorum not reached');
  }

  return responses[0] ?? '';
}
典型的 CP 系统：


    

  • ZooKeeper：分布式协调服务，必须保证配置数据的强一致性
    • 

  • HBase：强一致性的列族数据库
    • 

  • etcd：Kubernetes 的元数据存储，使用 Raft 共识算法

AP 系统的行为
当网络分区发生时，AP 系统继续提供服务但可能返回过期数据：


interface APNode {
  id: string;
  data: Map<string, { value: string; timestamp: number }>;
  peers: APNode[];
}

function apRead(node: APNode, key: string): string {
  const entry = node.data.get(key);
  return entry?.value ?? '';
}

function apWrite(node: APNode, key: string, value: string): void {
  const timestamp = Date.now();
  node.data.set(key, { value, timestamp });

  for (const peer of node.peers) {
    try {
      syncToPeer(peer, key, value, timestamp);
    } catch {
      queueForLaterSync(peer, key, value, timestamp);
    }
  }
}

function syncToPeer(peer: APNode, key: string, value: string, timestamp: number): void {
  const existing = peer.data.get(key);
  if (!existing || existing.timestamp < timestamp) {
    peer.data.set(key, { value, timestamp });
  }
}

function queueForLaterSync(_peer: APNode, _key: string, _value: string, _timestamp: number): void {
  // ...
}
典型的 AP 系统：


    

  • Cassandra：最终一致性的列族数据库，优先保证可用性
    • 

  • DynamoDB：Amazon 的键值存储，支持最终一致性读取
    • 

  • DNS：域名系统，允许短暂的不一致以保证全球可用

最终一致性的实现
最终一致性是工程实践中最常用的折中方案。典型实现策略包括：


读时修复（Read Repair）：


interface Replica {
  id: string;
  get(key: string): { value: string; version: number } | null;
  set(key: string, value: string, version: number): void;
}

async function readWithRepair(replicas: Replica[], key: string): Promise<string> {
  const results = await Promise.all(replicas.map(async (r) => ({ replica: r, data: r.get(key) })));

  const validResults = results.filter((r) => r.data !== null);
  if (validResults.length === 0) throw new Error('Key not found');

  const latest = validResults.reduce((a, b) => (a.data!.version > b.data!.version ? a : b));

  for (const result of validResults) {
    if (result.data!.version < latest.data!.version) {
      result.replica.set(key, latest.data!.value, latest.data!.version);
    }
  }

  return latest.data!.value;
}

PACELC 定理

PACELC 比 CAP 更实用，因为在大多数时间里网络并没有分区，此时延迟与一致性的权衡才是日常需要面对的核心问题。




真实世界的权衡案例
Amazon DynamoDB 的选择
DynamoDB 是一个典型的 AP 系统。Amazon 选择牺牲强一致性来保证：


    

  • 购物车服务在任何时候都可用
    • 

  • 即使数据中心故障，用户也能继续添加商品
    • 

  • 最终一致性在大多数场景下用户无感知（毫秒级同步延迟）
    • 



但 DynamoDB 同时也提供了强一致性读取选项（代价是更高的延迟和成本），将选择权交给开发者。


Google Spanner 的突破
Google Spanner 是第一个实现全球分布式强一致性的数据库。它通过 TrueTime API（基于原子钟和 GPS 接收器的精确时间服务）来实现全球范围内的线性一致性。这证明了在足够的工程投入下，CAP 的限制可以在实践中被大幅缓解——但其代价是极其昂贵的基础设施。




小结
    

  • CAP 定理的核心结论：在网络分区不可避免的前提下，一致性与可用性只能取其一。
    • 

  • 实际系统通常在一致性光谱中选择一个合适的级别，而非非此即彼。
    • 

  • 最终一致性是最常用的折中方案，通过读时修复、反熵协议等机制实现。
    • 

  • PACELC 将 CAP 扩展到无分区场景，更贴近日常工程决策。
    • 

  • 没有"最好"的选择，只有最适合业务场景的权衡。
    •
