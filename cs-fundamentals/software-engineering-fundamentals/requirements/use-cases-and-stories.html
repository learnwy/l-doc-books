用例与用户故事

核心概念

用例（Use Case）和用户故事（User Story）是两种主流的需求表达技术。两者都旨在从用户视角描述系统行为，但在形式化程度、适用场景和团队协作方式上有显著差异。用例源自面向对象分析方法论，强调完整性和精确性；用户故事源自敏捷开发，强调简洁性和可对话性。

理解两者的设计哲学差异是关键：用例假设"需求可以在前期完整描述"，通过详细的文档来减少后期歧义；用户故事假设"需求需要在对话中逐步澄清"，通过简短的描述来促进团队沟通。两种方法并非互斥——许多团队在敏捷实践中将用户故事作为日常沟通工具，同时为复杂业务流程编写用例级别的详细描述。

用例的结构与编写
用例描述一个参与者（Actor）为达成某个目标而与系统进行的完整交互。Alistair Cockburn 在其经典著作中定义了用例编写的标准模板，包含以下核心元素：


参与者是与系统交互的外部角色，可以是人（如管理员、普通用户）或其他系统（如支付网关、消息队列）。一个常见错误是将参与者定义为具体的人名或部门名——参与者应该是角色（"审批者"而非"张经理"）。


前置条件描述用例开始执行时系统必须满足的状态。"用户已登录且拥有管理员权限"是前置条件；"用户打开浏览器"不是——那太泛了。


主成功场景（Main Success Scenario）描述最常见的、一切顺利的执行路径，以编号步骤表达。每个步骤应该是参与者或系统执行的一个可观察的动作。


扩展场景（Extensions）描述主流程中可能出现的异常、分支和变体。扩展场景的编号引用主流程的步骤号，如"3a. 用户输入的邮箱格式无效"表示在主流程第 3 步的一个异常分支。


interface UseCase {
  id: string;
  name: string;
  actor: string;
  goal: string;
  preconditions: string[];
  postconditions: {
    success: string[];
    failure: string[];
  };
  mainScenario: Array<{
    step: number;
    action: string;
    actor: 'user' | 'system';
  }>;
  extensions: Array<{
    ref: string;
    condition: string;
    steps: string[];
  }>;
}

const loginUseCase: UseCase = {
  id: 'UC-001',
  name: '用户登录',
  actor: '注册用户',
  goal: '验证身份并进入系统',
  preconditions: ['用户已完成注册', '系统正常运行'],
  postconditions: {
    success: ['用户进入主页', '系统记录登录日志'],
    failure: ['显示错误信息', '账户锁定（连续5次失败后）'],
  },
  mainScenario: [
    { step: 1, action: '用户打开登录页面', actor: 'user' },
    { step: 2, action: '用户输入邮箱和密码', actor: 'user' },
    { step: 3, action: '系统验证凭证', actor: 'system' },
    { step: 4, action: '系统创建会话并跳转到主页', actor: 'system' },
  ],
  extensions: [
    { ref: '3a', condition: '邮箱未注册', steps: ['显示提示: 该邮箱未注册'] },
    { ref: '3b', condition: '密码错误', steps: ['显示错误提示', '失败计数+1'] },
    { ref: '3c', condition: '账户已锁定', steps: ['显示锁定提示及解锁方式'] },
  ],
};
用例编写的常见陷阱包括：把 UI 细节写入用例（"用户点击蓝色按钮"），在步骤中混入实现细节（"系统查询 MySQL 数据库"），以及遗漏异常流程——用例的价值很大程度上来自对异常场景的系统化梳理。


用户故事的三要素
用户故事采用固定的句式模板——"作为[角色]，我想要[功能]，以便[价值]"（As a [role], I want [feature], so that [benefit]）。这个模板被称为三要素（3C）：Card（卡片，简短的描述）、Conversation（对话，团队围绕故事的讨论）和 Confirmation（确认，验收标准）。


三要素中，Conversation 是最重要也最容易被忽视的部分。卡片上的一句话描述不是完整的需求规格——它是一个"对话的占位符"。真正的需求理解产生于产品负责人与开发团队围绕这个故事展开的讨论。这就是为什么用户故事在远程团队中的实践难度更高——缺乏面对面的对话机会。


验收标准（Acceptance Criteria）是将模糊的故事描述转化为可验证的测试条件。采用 Given-When-Then 格式（也称为 Gherkin 语法）编写的验收标准可以直接用于行为驱动开发（BDD）：


Given（前提条件）：系统处于什么状态When（触发动作）：用户执行什么操作Then（预期结果）：系统应产生什么响应


好的用户故事应满足 INVEST 原则：Independent（独立的，可独立交付）、Negotiable（可协商的，细节通过对话确定）、Valuable（有价值的，对用户有可感知的业务价值）、Estimable（可估算的，团队能评估工作量）、Small（足够小，一个 Sprint 内可完成）和 Testable（可测试的，有明确的验收标准）。


故事拆分与层次结构
在实际项目中，需求的粒度管理是关键挑战。一个大的业务特性（如"用户管理模块"）无法直接放入 Sprint，需要拆分为可独立交付的用户故事。


故事的层次结构通常分为三层：史诗（Epic）是大型的业务能力，跨多个 Sprint 交付，如"电商平台的订单管理"。特性（Feature）是 Epic 下的中等粒度分组，如"订单创建流程"和"订单退款流程"。用户故事是最小的可交付增量，如"用户可以选择收货地址"。


故事拆分有多种策略。按工作流步骤拆分将一个完整流程拆为多个步骤的故事（如"创建订单""支付订单""取消订单"）。按业务规则拆分将复杂的规则分解为基本版和增强版（如先实现"固定运费"，再实现"按区域阶梯运费"）。按数据变体拆分将不同数据类型的处理分为独立故事（如"导入 CSV 文件""导入 Excel 文件"）。按角色拆分为不同用户角色创建独立故事（如"管理员查看所有订单""普通用户查看自己的订单"）。


interface StoryHierarchy {
  epic: {
    title: string;
    features: Array<{
      title: string;
      stories: Array<{
        title: string;
        storyPoints: number;
        acceptanceCriteria: string[];
      }>;
    }>;
  };
}

const orderEpic: StoryHierarchy = {
  epic: {
    title: '订单管理',
    features: [
      {
        title: '订单创建',
        stories: [
          {
            title: '用户可以将商品加入购物车',
            storyPoints: 3,
            acceptanceCriteria: ['Given 商品有库存, When 点击加入购物车, Then 购物车数量+1'],
          },
          {
            title: '用户可以选择收货地址',
            storyPoints: 2,
            acceptanceCriteria: ['Given 用户有已保存地址, When 进入地址选择, Then 显示地址列表'],
          },
          {
            title: '用户可以提交订单',
            storyPoints: 5,
            acceptanceCriteria: ['Given 购物车非空且已选地址, When 点击提交, Then 生成订单号'],
          },
        ],
      },
    ],
  },
};
拆分的黄金法则是每个故事都应该端到端可交付——用户可以看到可感知的价值变化。"完成数据库表设计"不是一个好的用户故事，因为它对用户没有可见价值；"用户可以查看商品详情页"才是，即使只有基础信息。


需求表达的质量评估
无论使用用例还是用户故事，需求的表达质量直接影响后续开发的效率和质量。以下是评估需求表达质量的实用框架。


无歧义性是最基本的要求。"系统应该快速响应"是有歧义的——什么是"快速"？对谁来说？在什么负载条件下？改为"在 1000 并发用户条件下，P95 响应时间不超过 200ms"就消除了歧义。


完整性要求覆盖所有场景。功能需求容易被记住，但边界条件和异常场景常常被遗漏。检查完整性的方法是系统地思考：输入无效时怎么办？网络中断时怎么办？并发操作时怎么办？数据量极大时怎么办？


一致性要求不同需求之间不矛盾。在大型 SRS 中，不同章节由不同人编写，容易出现术语不一致（同一概念使用不同名称）或逻辑矛盾（一条需求要求实时同步，另一条要求异步处理同一数据）。


可测试性要求每条需求都能被验证。如果无法设计测试用例来验证某条需求是否被满足，说明这条需求的描述不够具体。每条功能需求至少对应一条验收标准，每条非功能需求至少对应一个可度量的指标。


小结
    

  • 用例适合需要完整文档化的复杂业务流程，用户故事适合敏捷环境中的迭代式需求管理
    • 

  • 用例的核心价值在于对异常场景的系统化梳理，避免遗漏边界条件
    • 

  • 用户故事的三要素中 Conversation 最重要——卡片只是对话的占位符
    • 

  • 好的用户故事满足 INVEST 原则，每个故事都应端到端可交付
    • 

  • 故事拆分可按工作流步骤、业务规则、数据变体或角色进行
    • 

  • 需求表达质量通过无歧义性、完整性、一致性和可测试性四个维度评估
    • 

  • 两种方法可以混合使用——敏捷团队中用户故事做日常沟通，复杂流程用用例补充
    •
