设计文档化

核心概念

设计文档是将架构决策和技术方案从个人头脑中外化为可共享、可评审、可追溯的工程产出物。它的价值不仅在于记录"系统长什么样"，更在于记录"为什么做出这样的设计选择"。代码只能表达最终结果，设计文档记录了选择背后的推理过程——被考虑过但被否决的方案、权衡的因素、做出决策时的约束条件。

设计文档的核心挑战是保持文档与代码的一致性。过时的文档比没有文档更危险——它会误导后来的开发者做出错误的假设。因此，设计文档化的实践不仅关注"如何写"，更关注"如何维护"和"何时更新"。

架构决策记录
架构决策记录（Architecture Decision Record, ADR）是一种轻量级的文档格式，用于记录每个重要的架构决策。Michael Nygard 在 2011 年提出 ADR 时，核心理念是：每个决策一个文件，格式固定，按时间序列编号，一旦创建永不删除。


ADR 的标准模板包含四个核心部分：


# ADR-001: 选择 PostgreSQL 作为主数据库

## 状态

已接受 (2024-03-15)

## 背景

系统需要一个关系型数据库来存储用户、订单和商品数据。预期数据量在百万级，需要支持复杂查询和事务。团队有 PostgreSQL 和 MySQL 的使用经验。

## 决策

选择 PostgreSQL 作为主数据库。

## 理由

- PostgreSQL 的 JSON 支持更成熟，可满足半结构化数据存储需求
- 支持更丰富的索引类型（GIN、GiST）
- 更严格的 SQL 标准遵从性
- 团队的 PostgreSQL 经验更深

## 后果

- 需要在 CI 环境中配置 PostgreSQL
- 部署环境需要维护 PostgreSQL 集群
- 被否决的方案：MySQL（JSON 支持较弱）、MongoDB（事务支持不满足需求）
ADR 的核心原则是不可变性——已经接受的 ADR 不会被修改或删除。如果一个决策后来被推翻，创建一个新的 ADR 引用旧的，标记旧的为"已废弃"。这保留了决策的完整历史。


interface ADR {
  id: number;
  title: string;
  status: 'proposed' | 'accepted' | 'deprecated' | 'superseded';
  context: string;
  decision: string;
  rationale: string[];
  consequences: string[];
  supersededBy?: number;
  date: string;
}
ADR 的最佳存储位置是与代码同仓库——通常放在 docs/adr/ 目录中。这确保了文档与代码的版本一致性，也让代码评审可以同时评审相关的架构决策。


ADR 的编写纪律是"先记录后实施"——在编写代码之前先创建 ADR，经团队评审后再开始实施。这不是官僚流程，而是确保决策经过充分思考。许多"紧急"的技术决策如果被要求写下理由，往往会在书写过程中发现逻辑漏洞。


常见的 ADR 决策触发点包括：引入新的外部依赖或框架、选择数据库或存储方案、定义服务间通信协议、决定认证和授权机制、选择部署和基础设施方案。不需要为每个小的编码决策都写 ADR——只有"影响多个模块或难以逆转"的决策才值得记录。


系统架构图的表达方法
架构图是设计文档中最直观的表达方式，但也是最容易误用的。一张试图表达所有信息的架构图往往什么都表达不清。C4 模型（Context, Containers, Components, Code）提供了一种分层架构可视化方法，按照抽象级别从高到低组织架构视图。


Context 图（Level 1）展示系统与外部实体（用户、第三方系统）的关系，回答"系统在更大的生态中处于什么位置"。这是最高层的视图，适合向非技术的利益相关者展示。


Container 图（Level 2）展示系统内部的主要技术容器（Web 应用、API 服务、数据库、消息队列）及其交互关系。这是架构师最常用的视图，展示了技术选型和部署拓扑。


Component 图（Level 3）展示每个容器内部的主要组件（模块、服务类）及其关系。这是开发者理解模块结构的关键视图。


架构图的常见错误包括：在一张图上混合多个抽象层次（如同时展示用户、微服务和数据库表）、使用不一致的图例（方框有时代表服务有时代表模块）、以及缺少关系说明（箭头没有标注交互方式和数据格式）。

设计文档的生命周期管理
设计文档的价值随时间衰减——如果不主动维护，文档在几周内就会开始偏离实际代码。生命周期管理的核心目标是在文档的价值和维护成本之间找到平衡。


文档即代码（Docs as Code）是现代的文档管理理念。它将文档纳入与代码相同的工具链：用 Markdown 编写（版本控制友好）、存储在代码仓库中（与代码同步版本）、通过 CI 流水线验证（检查链接有效性、格式规范）、通过 PR 评审（确保文档变更经过审查）。


文档更新的触发点应该与开发流程集成：PR 模板中包含"是否需要更新相关文档"的检查项、代码评审时同步检查文档一致性、Sprint 定义完成（DoD）中包含文档更新作为完成条件。


自动生成的文档可以大幅降低维护成本。API 文档通过 OpenAPI 规范从代码注解自动生成（如 Swagger），数据库 ER 图从数据库 Schema 自动生成，依赖关系图从代码的 import 语句自动生成。自动生成的文档永远比手写的文档更准确——因为它直接反映代码的当前状态。


手写文档和自动生成文档的分工是：手写文档负责记录"为什么"（架构决策的背景和理由），自动生成文档负责记录"是什么"（接口定义、数据结构、依赖关系）。将两者混为一谈是文档腐化的主要原因——手写的接口文档必然会与代码脱节，而自动生成的文档无法表达设计意图。


文档版本策略也需要与代码版本管理对齐。对于 API 文档，每次破坏性变更都应伴随版本号更新（如 v1 → v2），旧版本文档保留供正在迁移的消费者参考。对于架构文档，在主要架构变更的 PR 中同步更新，利用 Git 的版本历史自然保留文档的演化记录。


面向团队的文档策略
不同的团队规模和协作模式需要不同的文档策略。小团队（3-5 人）通过频繁的面对面沟通可以维持共识，文档需求较低；大团队（20+ 人）或分布式团队高度依赖文档进行知识传递。


最小文档集是每个项目都应该维护的核心文档：


    

  1. README — 项目概述、快速启动、技术栈一览
    2. 

  2. 架构总览 — 一张 Container 级别的架构图 + 关键组件说明
    3. 

  3. ADR 集合 — 所有重要架构决策的记录
    4. 

  4. API 文档 — 自动生成的接口规范
    5. 

  5. 开发指南 — 本地环境搭建、编码规范、PR 流程
    6. 



超出这个最小集的文档应该按需创建——当一个主题被反复询问时（超过 3 次），就值得为它创建文档。这种"按需文档化"策略避免了预先编写大量可能永远不会被阅读的文档。


文档的格式标准化对团队协作至关重要。统一使用 Markdown（便于版本控制和工具链集成）、约定文档模板（ADR 模板、设计方案模板）、定义术语表（避免同一概念在不同文档中使用不同名称）。格式标准化降低了编写和阅读文档的认知成本，让团队成员能快速定位自己需要的信息。


文档的度量帮助评估文档策略的有效性。关键指标包括：文档使用率（有多少人实际阅读了文档）、文档新鲜度（距上次更新多久）、Onboarding 时间（新成员从加入到独立贡献的时间）和重复提问率（同一问题被问到的次数）。当 Onboarding 时间持续缩短、重复提问率下降时，说明文档策略在发挥作用。

文档的可发现性同样重要。分散在各处（Wiki、Confluence、Google Docs、代码仓库）的文档等于不存在——没有人知道在哪里找。建立一个文档目录页（Documentation Index），列出所有文档的位置、类型和维护者，是提高文档可用性的简单有效手段。


文档的审计和清理也是生命周期管理的一部分。每季度对文档库进行一次审计：删除已确认过时的文档（或标记为"归档"）、更新仍有价值但内容落后的文档、识别缺失但急需的文档主题。文档与代码一样需要"重构"——合并重叠的文档、拆分过长的文档、统一格式和术语。

文档化的终极目标不是创建完美的文档体系，而是让知识从个人头脑中流入组织共识。当团队中的关键成员离开时，项目能否继续正常运行——这是衡量文档化成败的终极标准。


小结
    

  • 设计文档的核心价值是记录"为什么这样设计"，而不仅仅是"系统长什么样"
    • 

  • ADR 以不可变的方式记录每个架构决策，保留完整的决策历史
    • 

  • ADR 模式捕获架构决策的完整上下文——问题、选项、权衡和结论
    • 

  • ADR 的评审应纳入 PR 流程，确保架构决策经过团队讨论而非个人独断
    • 

  • ADR 的状态管理遵循"不删除旧决策"原则——新决策替代旧决策，但旧决策保留为历史参考
    • 

  • C4 模型通过四个抽象层次组织架构图，避免一张图混合多个层次
    • 

  • Docs as Code 将文档纳入代码工具链，PR 评审确保文档与代码同步
    • 

  • 自动生成文档覆盖"是什么"，手写文档覆盖"为什么"，两者互补而非替代
    • 

  • 文档度量（新鲜度、Onboarding 时间、重复提问率）评估文档策略的实际效果
    • 

  • 文档的审计和清理应定期进行，删除过时内容、合并重叠文档、补充缺失主题
    • 

  • 按需文档化策略避免预先编写大量不会被阅读的文档
    • 

  • 文档的格式标准化降低编写和阅读的认知成本
    • 

  • 每个文档应该有一个明确的"文档所有者"，对文档的准确性和时效性负责
    • 

  • 文档可发现性与文档质量同等重要，建立文档目录页是基本实践
    • 

  • 定期文档审计（每季度）清理过时内容，保持文档库的信息密度和可信度
    • 

  • 文档版本策略应与代码版本管理对齐，破坏性 API 变更需同步更新文档版本
    • 

  • Container 图标注技术栈信息，Component 图只展示架构意义上的重要组件
    •
