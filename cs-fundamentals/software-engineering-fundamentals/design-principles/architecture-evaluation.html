架构评估

核心概念

架构评估是在系统构建之前或演化过程中，系统化地分析架构方案的质量属性、识别潜在风险并做出改进决策的过程。它回答的核心问题是："这个架构能否满足系统的质量需求——性能、可用性、安全性、可维护性等？"

架构决策是软件项目中影响最深远、修改成本最高的决策。数据库选型、通信协议、部署架构、模块划分方式——这些决策一旦确定并在此基础上构建了大量代码，推翻重来的成本往往是灾难性的。架构评估的目的正是在这些决策被固化为代码之前，尽可能发现潜在问题。

ATAM 评估方法
架构权衡分析方法（Architecture Tradeoff Analysis Method, ATAM）是 SEI（软件工程研究所）开发的最系统化的架构评估方法。ATAM 的核心理念是：架构决策总是涉及质量属性之间的权衡——提高性能可能降低可维护性，增强安全性可能影响易用性。ATAM 的目标不是找到"完美"的架构，而是让所有利益相关者理解这些权衡并做出知情的决策。


ATAM 的执行过程分为四个阶段：


阶段一：展示。架构团队向评估团队介绍系统的业务驱动因素、架构方案和关键技术决策。这个阶段的输出是一份共享的系统理解。


阶段二：质量属性树构建。将系统的质量需求组织为树状结构：根节点是高层质量属性（如性能），叶节点是具体的、可度量的质量属性场景（如"在 1000 并发用户下，订单提交的 P99 响应时间不超过 500ms"）。每个叶节点标注优先级（H/M/L）和实现难度。


interface QualityAttributeScenario {
  source: string;
  stimulus: string;
  environment: string;
  artifact: string;
  response: string;
  responseMeasure: string;
  priority: 'H' | 'M' | 'L';
  difficulty: 'H' | 'M' | 'L';
}

const performanceScenario: QualityAttributeScenario = {
  source: '终端用户',
  stimulus: '提交订单请求',
  environment: '正常负载（1000 并发用户）',
  artifact: '订单服务',
  response: '处理订单并返回确认',
  responseMeasure: 'P99 响应时间 < 500ms',
  priority: 'H',
  difficulty: 'M',
};
阶段三：架构分析。针对每个高优先级场景，分析当前架构如何响应。识别三类关键发现：敏感点（影响特定质量属性的架构决策）、权衡点（影响多个质量属性的架构决策，改善一个可能恶化另一个）和风险（可能导致质量属性未达标的架构弱点）。


阶段四：结果报告。汇总所有发现的风险、非风险、敏感点和权衡点，形成架构评估报告。报告不做出通过/不通过的判断——决策权留给项目利益相关者。


质量属性场景化分析
质量属性的分析必须基于具体的、可度量的场景——"系统性能要好"这样的表述没有评估价值。场景化分析将模糊的质量需求转化为可验证的技术指标。


性能场景需要明确负载条件、操作类型和度量指标。例如："在 10000 个活跃用户同时浏览商品列表的情况下，95% 的请求在 200ms 内响应，99% 在 500ms 内响应，系统 CPU 使用率不超过 70%。"


架构师基于场景分析技术方案：如果当前架构是单体应用 + 关系型数据库，面对 10000 并发的商品浏览可能需要引入缓存层（Redis）和 CDN。这是一个典型的性能 vs 复杂度权衡——缓存引入了数据一致性问题和运维复杂度，但换取了显著的性能提升。


可用性场景需要明确故障类型和恢复期望。例如："当一个数据库节点宕机时，系统在 30 秒内自动切换到备用节点，服务中断时间不超过 30 秒，不丢失已提交的事务。"


这个场景驱动了具体的架构决策：需要数据库主从复制、自动故障检测和切换机制（如 PostgreSQL 的 Patroni）、以及应用层的连接池重试逻辑。每个决策都有成本——额外的服务器资源、运维复杂度和一致性延迟。


可维护性场景需要明确变更类型和期望的变更成本。例如："添加一种新的支付方式，从开发到上线不超过 3 个工作日，不需要修改现有支付逻辑的代码。"这个场景检验了支付模块的扩展性设计——如果满足，说明支付模块的抽象层（支付网关接口 + 适配器模式）设计合理。

轻量级评估方法
ATAM 适合大型关键系统，但对于中小型项目来说过于重量级。几种轻量级评估方法可以在更低成本下获得架构反馈。


架构代码评审（Architecture Code Review）是将架构审查嵌入日常代码评审流程。当 PR 涉及新模块创建、跨模块依赖引入或公共接口变更时，由架构师参与评审，检查变更是否与既定架构一致。


技术债务评审会（Tech Debt Review）定期（如每月一次）召集技术团队回顾系统中的架构腐化迹象：模块边界被越来越多的"临时"依赖穿透、性能热点持续恶化但没有从架构层面解决、测试覆盖率在关键路径上持续下降。


架构适应度函数（Architecture Fitness Functions）是将架构质量指标自动化为可执行的测试。与传统的单元测试验证功能正确性不同，适应度函数验证架构属性：


function checkNoCircularDependencies(modules: DependencyGraph): boolean {
  return !modules.hasCycle();
}

function checkLayerViolation(imports: ImportMap): string[] {
  const violations: string[] = [];
  for (const [source, targets] of imports) {
    if (source.startsWith('domain/') && targets.some((t) => t.startsWith('infrastructure/'))) {
      violations.push(`${source} → ${targets.find((t) => t.startsWith('infrastructure/'))}`);
    }
  }
  return violations;
}

function checkResponseTimeP99(metrics: PerformanceMetrics): boolean {
  return metrics.p99 < 500;
}
适应度函数可以集成到 CI 流水线中持续执行——当架构约束被违反时（如出现循环依赖、层次违规或性能退化），构建自动失败。这比人工评审更可靠、更及时。


风险风暴（Risk Storming）是一种可视化的团队协作评估方法。团队成员在架构图上用不同颜色的便签标注风险区域：红色代表高风险（如"单点故障的消息队列"），黄色代表中等风险（如"未经压测的新数据库"），绿色代表已知并已缓解的风险。通过所有人的共同标注，快速识别架构中的风险集中区域。


架构演化与治理
架构不是一次性的设计产出，而是随着系统和业务持续演化的活体。架构治理（Architecture Governance）的目标是确保这种演化是有意识的、可控的，而不是因为随意的技术决策而逐步腐化。


架构原则是治理的基础。它们是一组高层的技术决策指导方针，如"优先选择成熟的开源方案而非自研"、"每个服务拥有自己的数据存储"、"所有服务间通信必须通过 API 网关"。原则不是死板的规则——它们可以在充分论证后被例外突破，但突破必须被记录（通过 ADR）。


架构守护者（Architecture Guardians）机制指定团队中的资深成员担任架构守护角色——不是全职架构师，而是在日常开发中关注架构一致性的人。他们在代码评审中检查架构约束，在设计讨论中提供架构视角，在技术决策中确保与架构原则一致。


架构评估应该是持续的而非一次性的。在项目初期通过 ATAM 或类似方法做全面评估，在项目过程中通过适应度函数和架构代码评审做持续验证，在关键里程碑通过技术债务评审做周期性回顾。这种"持续架构"的理念与敏捷开发的持续改进思想一脉相承。

架构评估的输出应该驱动行动。每次评估发现的风险应该被记录到技术债务列表中，分配优先级，并在后续的迭代中安排修复。评估发现的权衡点应该被记录为 ADR，确保所有人理解为什么接受了某个质量属性的折衷。


技术雷达（Technology Radar）是一种持续的技术评估工具。团队定期（如每季度）审视当前使用的技术栈，将技术按成熟度和推荐程度分为四个象限：采纳（积极使用）、试验（小范围尝试）、评估（关注但不投入）和暂缓（停止使用）。这帮助团队及时发现过时技术的风险，也为引入新技术提供结构化的评估框架。


架构评估的一个常被忽视的方面是非技术因素的评估。架构的好坏不仅取决于技术质量属性，还取决于它与团队能力的匹配度。一个在技术上完美的微服务架构，对于只有 3 个人的团队来说可能是灾难——运维复杂度远超团队的承受能力。架构决策必须考虑团队的规模、经验水平和组织的运维能力。

小结
    

  • 架构评估的目标是在高成本决策被固化之前识别风险和权衡
    • 

  • ATAM 通过质量属性场景系统化地分析架构，适合大型关键系统
    • 

  • 质量属性必须场景化——"系统要快"没有评估价值，需要量化指标
    • 

  • 适应度函数将架构约束自动化为可执行测试，集成到 CI 流水线持续守护
    • 

  • 风险风暴是一种低成本的团队协作评估方法，适合快速识别架构风险
    • 

  • 架构治理通过原则、守护者和持续评估确保架构演化是可控的
    • 

  • 适应度函数与架构代码评审形成日常和自动化的双重架构守护机制
    • 

  • 架构评估应该是持续的——项目初期全面评估，过程中持续验证，里程碑周期性回顾
    • 

  • 架构决策必须考虑团队能力的匹配度，技术完美但超出团队能力的架构同样是失败的
    • 

  • 技术雷达为团队提供结构化的技术评估框架，帮助及时发现过时技术并评估新技术
    • 

  • 每次评估发现的风险应转化为技术债务条目，通过 ADR 记录权衡决策
    • 

  • ATAM 在项目早期识别架构风险，适应度函数在运行时持续守护架构约束
    •
