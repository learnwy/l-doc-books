测试设计技术

核心概念

测试设计技术是系统化地从需求和代码中导出测试用例的方法。与随机测试或凭直觉测试不同，测试设计技术提供了可重复的、有理论保证的用例生成策略，确保在有限的测试资源下获得最大的缺陷发现效率。

测试设计技术分为两大流派：黑盒技术（只关注输入输出，不了解内部实现）和白盒技术（基于代码结构设计用例）。黑盒技术用于验证"系统是否做了它应该做的事"，白盒技术用于验证"代码中所有路径是否都被正确执行"。两者互补——黑盒技术发现遗漏的功能，白盒技术发现隐藏的逻辑错误。

等价类划分与边界值分析
等价类划分（Equivalence Partitioning）将输入域划分为若干"等价类"——同一类中的任何输入值预期产生相同的系统行为。从每个等价类中只需选取一个代表值进行测试，即可推断该类中所有值的行为。这大幅减少了需要的测试用例数量。


等价类分为有效等价类（系统应正常处理的合法输入）和无效等价类（系统应拒绝或特殊处理的非法输入）。设计用例时必须同时覆盖两者——许多缺陷恰恰发生在系统处理无效输入时。


// 以年龄验证为例
// 有效等价类：[18, 60] 合法工作年龄
// 无效等价类：[-∞, 0) 负数, [0, 18) 未成年, (60, 150] 退休年龄, (150, +∞] 不合理值

function classifyAge(age: number): string {
  if (age < 0) return 'invalid';
  if (age < 18) return 'minor';
  if (age <= 60) return 'working-age';
  if (age <= 150) return 'retired';
  return 'invalid';
}

// 等价类测试用例
const testCases = [
  { input: -5, expected: 'invalid', class: '负数' },
  { input: 10, expected: 'minor', class: '未成年' },
  { input: 30, expected: 'working-age', class: '工作年龄' },
  { input: 80, expected: 'retired', class: '退休年龄' },
  { input: 200, expected: 'invalid', class: '不合理值' },
];
边界值分析（Boundary Value Analysis）基于一个经验观察：缺陷往往集中在等价类的边界上。编程中常见的 off-by-one 错误（<= 写成 <）正是边界缺陷的典型表现。边界值分析要求在每个边界点及其两侧各选取一个测试值。


对于上述年龄验证，边界值测试用例应包括：-1, 0, 1（0 的边界）、17, 18, 19（18 的边界）、59, 60, 61（60 的边界）、149, 150, 151（150 的边界）。这些边界值测试用例与等价类代表值测试用例共同构成了完整的黑盒测试集。


在多参数的场景中，边界值测试的用例数量可能迅速增长。正交试验法（Orthogonal Array Testing）提供了一种在多参数组合中选取最小代表集的数学方法，确保每对参数的每种组合至少被测试一次（两两覆盖）。


等价类划分和边界值分析的组合使用是最常见的黑盒测试设计策略。先用等价类划分确定输入域的分区，再在每个分区的边界上加密测试用例。这种组合策略以相对少的用例覆盖了最高缺陷概率的区域。

决策表与状态转换测试
决策表（Decision Table）是处理复杂条件组合逻辑的系统化方法。当系统的行为取决于多个条件的组合时，决策表列出所有可能的条件组合及其对应的动作，确保没有组合被遗漏。


// 电商免运费决策逻辑
// 条件：会员等级（普通/VIP）、订单金额（>= 99 / < 99）、商品类型（普通/特殊）
// 动作：免运费 / 收取运费

interface ShippingDecision {
  conditions: {
    memberLevel: 'vip' | 'regular';
    orderAmount: 'high' | 'low';
    productType: 'normal' | 'special';
  };
  action: 'free' | 'charged';
}

const decisionTable: ShippingDecision[] = [
  { conditions: { memberLevel: 'vip', orderAmount: 'high', productType: 'normal' }, action: 'free' },
  { conditions: { memberLevel: 'vip', orderAmount: 'high', productType: 'special' }, action: 'free' },
  { conditions: { memberLevel: 'vip', orderAmount: 'low', productType: 'normal' }, action: 'free' },
  { conditions: { memberLevel: 'vip', orderAmount: 'low', productType: 'special' }, action: 'charged' },
  { conditions: { memberLevel: 'regular', orderAmount: 'high', productType: 'normal' }, action: 'free' },
  { conditions: { memberLevel: 'regular', orderAmount: 'high', productType: 'special' }, action: 'charged' },
  { conditions: { memberLevel: 'regular', orderAmount: 'low', productType: 'normal' }, action: 'charged' },
  { conditions: { memberLevel: 'regular', orderAmount: 'low', productType: 'special' }, action: 'charged' },
];
当条件数量增多时，完整的决策表（2^n 行）可能不切实际。可以通过规则合并（合并动作相同的行）和省略无关条件（某些动作不受某条件影响时用"*"标记）来简化。


因果图法（Cause-Effect Graphing）是决策表的前置分析工具。它将输入条件（原因）和输出动作（结果）之间的逻辑关系用图形表示，然后从因果图自动导出决策表。对于条件间存在约束关系（如两个条件不能同时为真）的场景，因果图可以自然地排除不可能的组合，比直接构建决策表更高效。


成对测试（Pairwise Testing）在条件数量多（5个以上）时特别有用。它基于一个统计发现：大多数缺陷是由两个参数的交互引起的，而非三个或更多参数的复杂组合。成对测试只确保每对参数的每种组合至少被测试一次，用远少于全组合的用例数量达到接近全覆盖的缺陷发现率。工具如 PICT（Microsoft）可以自动生成成对测试用例集。


状态转换测试（State Transition Testing）适用于系统行为依赖于当前状态和输入事件的组合。通过状态转换图和状态转换表，系统化地设计覆盖所有合法转换和检测非法转换的测试用例。


状态转换测试的用例设计有不同深度：0-switch coverage 覆盖每个状态至少一次，1-switch coverage 覆盖每个状态转换至少一次，N-switch coverage 覆盖所有长度为 N 的转换序列。对于关键业务流程（如支付、订单），至少应达到 1-switch coverage。


状态转换测试的一个重要扩展是非法转换检测。除了验证所有合法的状态转换是否正确执行，还需要验证系统是否正确拒绝了非法转换。例如"已取消"的订单不应能直接转为"配送中"——测试应验证系统在收到这种非法操作时返回恰当的错误。


const illegalTransitions = [
  { from: 'cancelled', event: 'ship', expected: 'error' },
  { from: 'completed', event: 'cancel', expected: 'error' },
  { from: 'pending', event: 'deliver', expected: 'error' },
];
白盒覆盖准则
白盒测试基于代码结构设计用例，覆盖率是衡量测试充分性的量化指标。不同的覆盖准则对"充分性"的定义不同，覆盖力度也不同。


语句覆盖（Statement Coverage）要求每一行可执行语句至少被执行一次。这是最弱的覆盖准则——100% 的语句覆盖率并不意味着所有分支都被测试了。


分支覆盖（Branch Coverage）要求每个条件判断的真假分支都至少被执行一次。分支覆盖隐含了语句覆盖——如果所有分支都被执行，那么所有语句必然都被执行。大多数工业项目以 80% 的分支覆盖率作为标准。


条件覆盖（Condition Coverage）要求复合条件中的每个原子条件都取过真和假。但条件覆盖不保证分支覆盖——可能所有原子条件都取过真假，但某些分支组合从未被测试。


MC/DC（Modified Condition/Decision Coverage）是航空软件标准 DO-178B 要求的覆盖准则。它要求每个原子条件的变化都能独立影响判定结果。MC/DC 在分支覆盖和完全条件覆盖之间取得了良好平衡——用较少的用例获得较强的覆盖保证。

覆盖率是必要条件但非充分条件。100% 的覆盖率不等于零缺陷——测试可能覆盖了所有代码路径但使用了不恰当的断言（或根本没有断言）。覆盖率应该作为识别测试盲区的工具，而不是作为质量的唯一度量。


变异测试（Mutation Testing）是评估测试质量的更严格方法。它通过在代码中引入小的变异（如将 > 改为 >=、删除一行语句），然后运行测试套件检查是否能检测到这些变异。如果一个变异没有导致任何测试失败，说明测试套件在这个位置存在盲区。变异测试的变异检出率（Mutation Score）比代码覆盖率更准确地反映测试的有效性，但执行成本也更高。


在实际项目中，测试设计技术的选择应基于风险分析。核心业务逻辑（如支付计算、权限校验）值得投入等价类 + 边界值 + 决策表的完整黑盒测试；辅助功能（如日志格式化、缓存更新）用基本的等价类测试即可；安全敏感代码（如输入验证、SQL 参数处理）需要额外的负面测试和模糊测试（Fuzz Testing）。


小结
    

  • 等价类划分将输入域分区以减少冗余用例，必须同时覆盖有效和无效等价类
    • 

  • 边界值分析针对缺陷高发的边界区域，与等价类划分共同构成黑盒测试基础
    • 

  • 决策表系统化覆盖条件组合逻辑，可通过规则合并控制用例数量
    • 

  • 状态转换测试适用于有状态的业务对象，至少达到 1-switch coverage
    • 

  • 成对测试在多参数场景下显著减少用例数量，同时保持高缺陷发现率
    • 

  • 因果图法是决策表的前置分析工具，帮助排除不可能的条件组合
    • 

  • 非法状态转换检测是状态测试的重要补充，确保系统正确拒绝无效操作
    • 

  • 分支覆盖是大多数商业软件的标准，MC/DC 用于安全关键系统
    • 

  • 变异测试通过注入代码变异评估测试质量，比覆盖率更准确地反映测试有效性
    • 

  • 覆盖率是识别测试盲区的工具，不是质量的唯一度量——有断言的测试才有价值
    • 

  • 正交试验法在多参数场景中找到最小代表集，确保参数两两组合被测试
    • 

  • 测试设计技术的选择应基于风险分析，核心业务值得完整的黑盒测试组合
    • 

  • 安全敏感代码需要额外的负面测试和模糊测试来覆盖恶意输入场景
    • 

  • 每种技术有其最佳适用场景——组合使用多种技术比单一技术能发现更多缺陷
    • 

  • 随着系统复杂度增加，自动化测试用例生成工具可以辅助人工测试设计
    •
