事后分析 Postmortem

概述

Postmortem（事后分析）是在故障恢复后进行的结构化复盘，目的是理解故障的根本原因、评估影响范围、并制定防止复发的改进行动。在无责文化下，Postmortem 不是追究"谁的错"，而是探讨"系统哪里可以更好"。它是将每次故障转化为组织学习机会的核心机制。

核心概念

无责文化（Blameless Culture）

无责文化的核心假设：






假设
说明





人会犯错
这是系统应该容忍和防范的，不是个人缺陷




环境塑造行为
人在当时的信息和压力下做了"合理"的决定




系统应防错
如果一个人的失误能导致故障，说明系统缺少防护




透明促进改进
只有人们不怕说出错误，才能找到真正的改进点

根因分析技术
5 Whys 方法
five_whys_example = """
问题: 订单服务在部署后返回 500 错误

Why 1: 为什么返回 500?
→ 新版本的 OrderMapper 对 null address 抛出 NPE

Why 2: 为什么 address 是 null?
→ 新版本移除了 address 的默认值逻辑（重构遗漏）

Why 3: 为什么重构遗漏了这个逻辑?
→ 默认值逻辑在另一个类中，重构者不知道有依赖关系

Why 4: 为什么依赖关系没被发现?
→ 没有测试覆盖 address=null 的场景

Why 5: 为什么没有这个测试?
→ 缺少对 nullable 字段的系统化测试规范

根因: 缺少 nullable 字段的测试覆盖规范
     + 代码间的隐式依赖未被文档化
"""

实战指南
完整 Postmortem 示例
# Postmortem: 2024-03-15 订单服务 P1 故障

## 元数据

- 日期: 2024-03-15
- 级别: P1
- 持续时间: 22 分钟 (14:03 - 14:25)
- 影响: 约 1,200 笔订单创建失败
- 收入影响: 约 ¥180,000
- 作者: 李四
- IC: 张三

## 概要

v2.3.4 部署后，OrderMapper 对 shipping_address 为 null 的历史订单抛出 NullPointerException，导致订单查询和创建接口 2% 返回 500。22 分钟后通过回滚恢复。

## 时间线

| 时间  | 事件                                   |
| ----- | -------------------------------------- |
| 14:03 | v2.3.4 部署完成（含 OrderMapper 重构） |
| 14:05 | 错误率从 0.01% 升至 2.1%               |
| 14:08 | 告警触发，On-Call @李四 收到 PagerDuty |
| 14:10 | @李四 ACK，检查最近部署                |
| 14:12 | 确认错误始于部署时间点，@张三 作为 IC  |
| 14:15 | IC 决定回滚                            |
| 14:18 | 执行 kubectl rollout undo              |
| 14:25 | 错误率恢复正常                         |
| 14:30 | IC 宣布故障关闭                        |

## 根因分析 (5 Whys)

1. 为什么 500? → NPE in OrderMapper.toDTO()
2. 为什么 NPE? → shipping_address 可能为 null（历史数据）
3. 为什么重构后不兼容? → 重构移除了旧的 null 保护代码
4. 为什么没在 CR 中发现? → reviewer 不知道有 null 数据的存在
5. 为什么没有测试覆盖? → 测试只用了新创建的数据，无历史数据

## 影响评估

- 受影响用户: ~3,000 (占活跃用户 0.5%)
- 失败请求: ~15,000 次
- 失败订单: ~1,200 笔
- 收入损失: ~¥180,000 (部分用户会重试)
- 品牌影响: 低（持续时间短，无社交媒体扩散）

## 经验教训

### 做得好的

- 告警在 3 分钟内触发（检测快速）
- On-Call 在 2 分钟内 ACK（响应迅速）
- 快速决策回滚而非尝试热修复（止血优先）
- 回滚流程顺畅（7 分钟完成）

### 做得不好的

- 部署前没有灰度（直接全量发布）
- Code Review 未注意到 null safety
- 测试数据不包含 null 字段的边界情况
- 告警阈值设为 2%（应该 0.5% 就触发）

### 运气因素

- 故障发生在工作时间（如果是凌晨，MTTR 会更长）
- 回滚路径畅通（如果有数据库 migration 就无法回滚）

## 行动项

| ID  | 行动                                   | 负责人 | 截止日 | 优先级 |
| --- | -------------------------------------- | ------ | ------ | ------ |
| 1   | 增加 nullable 字段单元测试             | @王五  | 03-22  | High   |
| 2   | 部署策略改为金丝雀（10% → 50% → 100%） | @赵六  | 03-29  | High   |
| 3   | 告警阈值从 2% 调低到 0.5%              | @李四  | 03-18  | Medium |
| 4   | CI 中增加历史数据兼容性测试            | @王五  | 04-05  | Medium |
| 5   | Runbook 增加 "部署后快速验证" 步骤     | @张三  | 03-22  | Low    |

时长: 45-60 分钟
参与者: 相关团队成员 + 管理层（可选旁听）

议程:
1. (5min) 故障概述：IC 用 2 分钟总结
2. (15min) 时间线 Walk-through：逐步回顾关键事件
3. (15min) 根因讨论：
   - 大家对根因分析是否有补充？
   - 是否有被忽略的贡献因素？
4. (10min) 行动项 Review：
   - 优先级是否合理？
   - 截止日期是否可行？
   - 是否需要增加/删除行动项？
5. (5min) 全局反思：
   - 是否有其他服务存在类似风险？
   - 是否需要更新团队规范？

原则:
- 不追究个人责任
- 关注系统和流程改进
- 鼓励提问和补充信息
- 会议记录公开（knowledge sharing）
"""

总结
Postmortem 是将"故障"转化为"组织智慧"的核心机制。关键实践：建立无责文化、标准化文档结构、重建精确时间线、深入根因分析（不止于表面原因）、产出可执行的 Action Items 并跟踪闭环。最终目标不是"零故障"（不可能），而是"同类故障不再重复发生"。每一份 Postmortem 都应该让系统比故障前更加健壮。
