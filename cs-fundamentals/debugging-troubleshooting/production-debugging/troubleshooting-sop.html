故障排查 SOP

概述

故障排查 SOP（Standard Operating Procedure）是生产环境问题处理的标准化操作手册。它提供从接收告警到问题定位的结构化流程，确保不同经验水平的工程师都能按照统一的步骤高效排查。SOP 的核心原则是"先止血后查因"——在深入分析根因之前，优先恢复服务可用性。

通用排查流程
general_troubleshooting_flow = """
Step 1: 确认问题
  □ 告警内容是什么？影响范围？开始时间？
  □ 能否从用户视角复现？
  □ 监控面板显示什么异常？

Step 2: 快速止血评估
  □ 是否有最近的部署？→ 考虑回滚
  □ 是否有配置变更？→ 考虑恢复配置
  □ 是否可以降级（关闭非核心功能）？
  □ 是否可以扩容缓解？

Step 3: 信息收集
  □ 相关服务的错误日志
  □ 异常时间段的 metrics 变化
  □ 分布式追踪（trace_id）
  □ 最近的部署/变更记录
  □ 外部依赖状态

Step 4: 假设与验证
  □ 根据信息形成 2-3 个假设
  □ 按概率排序，逐一验证
  □ 确认根因

Step 5: 修复与验证
  □ 实施修复
  □ 验证监控恢复正常
  □ 观察 15-30 分钟确认稳定

Step 6: 善后
  □ 更新事件 timeline
  □ 通知相关方问题已解决
  □ 创建 Postmortem 任务
"""

SERVICE=$1

echo "=== 最近部署 ==="
kubectl -n $NAMESPACE rollout history deployment/$SERVICE | tail -5

kubectl -n $NAMESPACE top pods -l app=$SERVICE

场景二：数据库连接耗尽
-- 排查步骤 1: 确认连接状态
SELECT state, count(*), max(now() - state_change) as max_duration
FROM pg_stat_activity
WHERE datname = 'production'
GROUP BY state;

-- 排查步骤 2: 找到长事务
SELECT pid, now() - xact_start as duration, query
FROM pg_stat_activity
WHERE state = 'active' AND xact_start < now() - interval '5 minutes'
ORDER BY xact_start;

-- 排查步骤 3: 找到等待锁的查询
SELECT blocked.pid, blocked.query as blocked_query,
       blocking.pid as blocking_pid, blocking.query as blocking_query
FROM pg_stat_activity blocked
JOIN pg_locks bl ON bl.pid = blocked.pid
JOIN pg_locks bk ON bk.relation = bl.relation AND bk.pid != bl.pid
JOIN pg_stat_activity blocking ON blocking.pid = bk.pid
WHERE NOT bl.granted;
# 紧急止血：终止长事务
psql -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity
         WHERE state = 'active' AND xact_start < now() - interval '10 minutes';"

# 临时扩大连接池（如果应用支持热更新）
curl -X PUT http://service:8080/admin/config \
  -d '{"db.pool.max": 100}'
场景三：内存持续增长 OOM
# 步骤 1: 确认内存增长趋势
kubectl top pods -l app=order-service --no-headers | sort -k3 -h

# 步骤 2: 进入容器查看内存分布
kubectl exec -it order-service-abc123 -- /bin/sh
# Go 服务
curl http://localhost:6060/debug/pprof/heap > /tmp/heap.prof
# 或查看 goroutine 数量
curl http://localhost:6060/debug/pprof/goroutine?debug=2 | head -50

# 步骤 3: 对比两个时间点的 heap profile
# (从外部)
kubectl cp order-service-abc123:/tmp/heap.prof ./heap_t0.prof
sleep 300
kubectl exec order-service-abc123 -- curl -s http://localhost:6060/debug/pprof/heap -o /tmp/heap2.prof
kubectl cp order-service-abc123:/tmp/heap2.prof ./heap_t1.prof

go tool pprof -base heap_t0.prof heap_t1.prof
# (pprof) top → 找到内存增长最快的分配点

Runbook 设计标准
每个核心服务应有标准 Runbook：


# order-service Runbook

## 服务概述

- 功能: 订单创建、查询、状态管理
- 依赖: PostgreSQL, Redis, payment-service, inventory-service
- 部署: 3 实例, 2CPU/4GB, Kubernetes

## 监控面板

- Grafana: https://grafana.internal/d/order-service
- 告警规则: https://prometheus.internal/alerts#order-service

## 常见问题处理

### 错误率 > 1%

1. 检查最近部署: `kubectl rollout history deploy/order-service`
2. 检查依赖健康: payment-service, inventory-service 状态
3. 检查 DB 连接池: `/actuator/metrics/hikari.connections`
4. 若为最近部署导致: `kubectl rollout undo deploy/order-service`

### P99 延迟 > 500ms

1. 检查 DB 慢查询: 登录 pg_stat_statements 查看
2. 检查 Redis 命中率: `/actuator/metrics/cache.hits`
3. 检查 GC 日志: `kubectl logs ... | grep "GC pause"`

### OOM Kill

1. 检查 heap dump: 进入容器执行 pprof
2. 临时扩容: `kubectl scale deploy/order-service --replicas=5`
3. 重启泄漏实例: `kubectl delete pod <highest-memory-pod>`

总结
故障排查 SOP 的核心价值是将"英雄式救火"转化为"流程化处理"。关键原则：先止血后查因、按清单逐步排查、收集充分证据后再做假设、标准化 Runbook 降低人员依赖。好的 SOP 让初级工程师也能处理 80% 的常见故障，释放高级工程师去解决真正困难的问题。
