着色器编程

核心概念

着色器（Shader）是运行在 GPU 上的小型程序，控制渲染管线中可编程阶段的行为。着色器程序决定了每个顶点的位置变换、每个像素的颜色计算以及各种视觉效果的实现方式。

现代图形编程的核心工作就是编写着色器。

GPU 的执行模型与 CPU 截然不同。GPU 拥有数千个简单的处理核心，以 SIMT（Single Instruction, Multiple Threads）方式同时执行相同的着色器代码在不同的数据上。这意味着着色器代码中的分支（if/else）会导致线程束（Warp/Wavefront）中的部分线程空转，产生性能损失。

着色器语言是图形 API 的一部分：OpenGL 使用 GLSL，DirectX 使用 HLSL，Vulkan 使用 SPIR-V（通常从 GLSL 或 HLSL 编译），Metal 使用 MSL。WebGPU 使用 WGSL。不同着色器语言在语法和特性上各有差异，但核心概念（顶点/片元阶段、Uniform、纹理采样）是通用的。


着色器的开发和调试工作流通常包括：在文本编辑器中编写着色器代码，使用离线编译器验证语法（如 glslangValidator），在引擎中实时预览效果，使用 GPU 调试工具分析性能。支持着色器热重载的引擎可以在修改保存后立即看到效果变化，大幅提升迭代速度。


GLSL 基础语法与数据类型
GLSL（OpenGL Shading Language）是最广泛使用的着色器语言之一，其语法接近 C 语言但针对图形计算进行了大量扩展。


GLSL 的核心数据类型围绕向量和矩阵设计。vec2、vec3、vec4 表示 2/3/4 分量的浮点向量，mat3、mat4 表示 3×3 和 4×4 矩阵。向量支持灵活的 Swizzle 操作——可以用 .xyzw、.rgba 或 .stpq 任意组合分量：


vec4 color = vec4(1.0, 0.5, 0.0, 1.0);
vec3 rgb = color.rgb;
vec2 rg = color.xy;
vec3 bgr = color.bgr;
float r = color.r;
着色器之间通过 in/out 变量传递数据。顶点着色器的 out 变量经过光栅化阶段的插值后成为片元着色器的 in 变量。Uniform 变量是从 CPU 端设置的全局常量，在一次绘制调用中所有着色器实例共享相同的值：


layout(location = 0) in vec3 aPos;
layout(location = 1) in vec2 aTexCoord;

uniform mat4 uMVP;
uniform float uTime;

out vec2 vTexCoord;

void main() {
    gl_Position = uMVP * vec4(aPos, 1.0);
    vTexCoord = aTexCoord;
}
GLSL 提供丰富的内置函数：mix(a, b, t) 执行线性插值，clamp(x, min, max) 限制范围，smoothstep(edge0, edge1, x) 产生平滑的 Hermite 插值，normalize(v) 归一化向量，reflect(I, N) 计算反射方向。这些函数在 GPU 上有硬件加速的实现。


GLSL 的精度限定符（lowp、mediump、highp）在桌面 GPU 上通常被忽略（全部作为 highp 处理），但在移动 GPU 上会直接影响寄存器宽度和计算吞吐量。mediump 使用 16 位浮点，精度约 3 位有效数字，适用于颜色和归一化向量；highp 使用 32 位浮点，精度约 7 位，用于位置和坐标计算。


着色器中的流程控制与 CPU 代码有本质区别。GPU 以 Warp（NVIDIA 32 线程）或 Wavefront（AMD 64 线程）为单位执行。当 Warp 中的线程遇到分支时，如果不同线程走不同路径（divergent branch），Warp 必须依次执行两条路径，未激活的线程被屏蔽。因此应尽量让 Warp 中相邻的片元走相同的分支——基于屏幕空间位置或 Uniform 的分支通常是 coherent 的。


Uniform Buffer 与资源绑定
现代着色器程序通过结构化的方式管理 GPU 资源。Uniform Buffer Object（UBO）将多个 Uniform 变量打包为一个缓冲区，减少 CPU 到 GPU 的数据传输次数。


layout(std140, binding = 0) uniform CameraData {
    mat4 view;
    mat4 projection;
    vec3 cameraPos;
    float nearPlane;
    float farPlane;
};

layout(std140, binding = 1) uniform LightData {
    vec4 lightPositions[16];
    vec4 lightColors[16];
    int lightCount;
};
std140 布局规则确保 CPU 和 GPU 端的内存对齐一致。关键规则包括：vec4 对齐到 16 字节边界，mat4 按列存储且每列对齐到 16 字节，标量和 vec2 有各自的对齐要求。不正确的对齐是着色器开发中最常见的 Bug 来源之一。


Shader Storage Buffer Object（SSBO）比 UBO 更灵活——大小可变、支持读写。但 SSBO 的访问速度通常低于 UBO，因为 UBO 的数据会被缓存在 GPU 的常量缓存中。SSBO 在计算着色器中尤为重要，是 GPU 通用计算的主要数据传输方式。


在计算着色器中，SSBO 是主要的数据输入输出手段。


纹理采样器（Sampler）是另一类重要资源。sampler2D 表示二维纹理，samplerCube 表示立方体贴图，sampler2DShadow 专用于阴影比较。纹理采样时 GPU 自动处理过滤（双线性/三线性）和 Mipmap 选择。采样器状态（过滤模式、环绕模式、各向异性等级）可以与纹理数据分离设置，允许同一张纹理以不同的采样参数使用。

着色器变体与编译优化
实际的渲染引擎需要处理大量的材质和渲染路径组合。同一个着色器可能需要在有无法线贴图、不同光源数量、不同阴影质量等条件下工作。着色器变体（Shader Variants / Permutations）通过预处理器宏来管理这些组合：


#ifdef HAS_NORMAL_MAP
    vec3 normal = texture(uNormalMap, vTexCoord).rgb * 2.0 - 1.0;
    normal = normalize(vTBN * normal);
#else
    vec3 normal = normalize(vNormal);
#endif

#if NUM_LIGHTS > 0
    for (int i = 0; i < NUM_LIGHTS; i++) {
        color += calculateLight(lights[i], normal, viewDir);
    }
#endif
变体数量随功能开关指数增长。10 个布尔开关就产生 1024 个变体，编译和管理成本巨大。现代引擎使用着色器缓存（预编译并缓存 SPIR-V 字节码）和特化常量（Specialization Constants，Vulkan 特性）来缓解这个问题。特化常量允许在管线创建时指定常量值，编译器可以基于这些值进行死代码消除和常量折叠。


Specialization Constants（Vulkan）和 Static Branch（HLSL [branch]）在编译时替换常量值。引擎根据材质需求设置不同的 Specialization Constants，编译器可以优化掉不需要的分支。


这种方案在减少变体数量的同时保持了接近手写的性能。


GPU 编译器的优化能力直接影响着色器性能。寄存器压力（Register Pressure）是关键指标——一个着色器使用的寄存器越多，GPU 能同时调度的线程数越少（Occupancy 降低），隐藏内存延迟的能力越差。减少临时变量、避免复杂的控制流、利用向量化操作都有助于降低寄存器压力。


着色器占用率（Shader Occupancy）是衡量 GPU 利用率的核心指标。它定义为实际活跃的 Warp 数量与 SM 支持的最大 Warp 数量的比值。低占用率意味着 GPU 在等待内存返回数据时没有足够的其他 Warp 可以切换执行，计算单元空闲。但过高的占用率也不一定最优——有时减少 Warp 数量可以让每个 Warp 使用更多缓存，总吞吐量反而更高。这种现象被称为"缓存节拍"（Cache Thrashing），需要通过实测来确定最佳占用率。


跨着色器语言与工具链
现代图形开发面临多平台着色器问题。DirectX 使用 HLSL，OpenGL/Vulkan 使用 GLSL，Metal 使用 MSL，WebGPU 使用 WGSL。维护四套着色器代码是不现实的，因此出现了多种跨语言方案。


SPIR-V 是 Khronos 定义的中间表示（IR），Vulkan 原生使用 SPIR-V。通过 glslang（GLSL→SPIR-V）和 DXC（HLSL→SPIR-V）等编译器，可以从高级语言编译到 SPIR-V。再通过 SPIRV-Cross 将 SPIR-V 反编译为 GLSL、HLSL 或 MSL，实现跨平台部署。这种"编译到 IR → 反编译到目标语言"的方案使得开发团队可以使用单一的着色器源码（通常选择 HLSL 或 GLSL）覆盖所有平台。


Slang（NVIDIA 开源）是一种新兴的着色器语言，提供泛型、接口和模块化等高级语言特性，可以编译到 SPIR-V、HLSL、GLSL、CUDA 等多个目标。它特别适合需要大量着色器变体和复杂材质系统的引擎。


着色器调试是图形开发的痛点。RenderDoc、Nsight Graphics 和 Xcode GPU Debugger 等工具可以捕获帧、单步执行着色器、检查中间变量。但 GPU 着色器的并行执行特性使得传统的断点调试方式受限，通常需要通过将中间值输出到颜色通道（"颜色调试"）或使用 printf 风格的缓冲区来诊断问题。


着色器热重载（Hot Reload）是提升开发效率的重要特性。引擎监控着色器文件变化，检测到修改后自动重新编译并替换当前使用的着色器程序，无需重启应用。实现热重载需要在引擎层面管理着色器对象的生命周期，确保新编译的着色器能正确替换旧版本并绑定到正确的资源。


着色器性能分析通常通过 GPU 性能计数器和着色器分析器完成。NVIDIA 的 Nsight Shader Profiler 可以报告着色器的指令数、寄存器使用量、ALU 和纹理采样的吞吐量。AMD 的 Radeon GPU Profiler 提供类似的功能。关键优化策略包括：


    

  • 减少纹理采样次数（合并通道、降低分辨率）
    • 

  • 避免在循环内部进行分支操作
    • 

  • 使用 mediump 精度（移动端）降低寄存器压力
    • 

  • 将复杂计算预计算到查找纹理中
    • 

  • 利用 GPU 的标量和向量 ALU 平衡负载
    • 



小结
    

  • 着色器是运行在 GPU 上的并行程序，分支会导致 SIMT 执行中的线程空转
    • 

  • GLSL 的向量和矩阵类型支持灵活的 Swizzle 操作，内置函数有硬件加速
    • 

  • 精度限定符在移动 GPU 上影响寄存器宽度和计算吞吐量
    • 

  • 着色器占用率是衡量 GPU 利用率的核心指标，需通过实测确定最佳值
    • 

  • UBO 将多个 Uniform 打包传输，std140 布局确保内存对齐一致
    • 

  • SSBO 支持可变大小的读写缓冲，是 GPU 通用计算的核心数据接口
    • 

  • 着色器变体通过预处理器宏管理功能组合，特化常量提供更高效的替代方案
    • 

  • 寄存器压力影响 GPU 占用率，是着色器性能优化的核心指标
    • 

  • SPIR-V 作为中间表示连接了不同着色器语言和图形 API
    • 

  • 着色器热重载和性能分析工具是高效图形开发的必备基础设施
