WebGPU 与 Vulkan

核心概念

WebGPU 和 Vulkan 代表了新一代图形 API 的设计理念——显式控制。与 OpenGL 等传统 API 隐藏大量状态管理和资源同步的细节不同，新一代 API 将这些责任交给开发者，换取更高的性能上限和更可预测的行为。Vulkan 是桌面/移动端的底层图形 API，WebGPU 是面向 Web 平台的现代图形 API。

传统 API（OpenGL/DirectX 11）使用隐式状态机模型——驱动程序在幕后进行资源追踪、同步、内存管理和着色器编译。这导致了两个问题：驱动层面的优化不透明且不可预测（同一代码在不同驱动上性能差异巨大），以及单线程命令提交成为 CPU 端的瓶颈。新一代 API 通过显式的命令缓冲区、资源屏障和管线状态对象解决了这些问题。

Vulkan 核心架构
Vulkan 的设计围绕几个核心抽象：实例（Instance）→ 物理设备（Physical Device）→ 逻辑设备（Logical Device）→ 队列（Queue）。逻辑设备代表应用对 GPU 的使用，队列是命令提交的通道——图形队列执行渲染命令，计算队列执行计算着色器，传输队列执行数据拷贝。


命令缓冲区（Command Buffer）是 Vulkan 多线程命令提交的关键。应用在多个 CPU 线程上并行录制命令到各自的命令缓冲区，最后在主线程一次性提交到队列执行。这消除了 OpenGL 中单线程命令提交的瓶颈。


Vulkan 渲染一帧的典型流程:
1. 从交换链获取下一个可用图像
2. 重置/分配命令缓冲区
3. 开始命令录制
   a. 开始 Render Pass
   b. 绑定管线、描述符集
   c. 设置视口、裁剪矩形
   d. 绑定顶点/索引缓冲
   e. 绘制调用 (vkCmdDraw/vkCmdDrawIndexed)
   f. 结束 Render Pass
4. 结束命令录制
5. 提交命令缓冲区到图形队列
6. 呈现图像到交换链
管线状态对象（Pipeline State Object, PSO）将渲染管线的所有状态（着色器、混合模式、深度测试、顶点输入布局等）预编译为一个不可变对象。


状态切换只需绑定不同的 PSO，不需要逐个设置状态——这避免了 OpenGL 中频繁状态切换的验证开销。


描述符集（Descriptor Set）管理着色器的资源绑定（UBO、纹理、采样器等）。描述符集可以预先分配和更新，渲染时只需绑定到命令缓冲区。


常见的组织策略是按更新频率分层：Set 0 存放全局数据（相机、光照），Set 1 存放每 Pass 数据，Set 2 存放每材质数据，Set 3 存放每物体数据。


Vulkan 同步与资源屏障
Vulkan 要求开发者显式管理 GPU 操作之间的同步和资源状态转换。这是 Vulkan 最复杂也最容易出错的部分。


信号量（Semaphore）用于 GPU 队列之间的同步——例如确保图形队列等待计算队列完成后再使用计算结果。


栅栏（Fence）用于 CPU-GPU 同步——CPU 等待 GPU 完成特定命令缓冲区的执行后再复用资源。


管线屏障（Pipeline Barrier）定义资源状态转换和内存依赖。当一个纹理从 "颜色附件写入" 状态切换到 "着色器采样读取" 状态时，屏障确保写入完成且缓存刷新，后续的读取能看到正确的数据。


vkCmdPipelineBarrier 的关键参数:
- srcStageMask: 屏障前必须完成的管线阶段
- dstStageMask: 屏障后才能开始的管线阶段
- srcAccessMask: 必须刷新的内存写入类型
- dstAccessMask: 必须可见的内存读取类型
- oldLayout → newLayout: 图像布局转换
Render Pass 是 Vulkan 的另一个核心概念。它声明了一次渲染操作使用的附件（颜色/深度目标）、子 Pass 之间的依赖关系、以及每个附件的加载/存储操作。Render Pass 的声明式设计让 Tile-Based GPU（移动端）可以优化片上缓存的使用——只有最终结果需要写回显存。


Vulkan 1.3 引入了动态渲染（Dynamic Rendering, VK_KHR_dynamic_rendering），简化了 Render Pass 的使用。传统 Render Pass 需要预先声明所有附件和子 Pass 的完整依赖关系，动态渲染允许在命令缓冲区录制时直接指定渲染目标，减少了预先创建 Render Pass 和 Framebuffer 对象的样板代码。


大多数桌面端应用已迁移到动态渲染，但移动端仍需要传统 Render Pass 以利用 TBR 优化。

WebGPU 设计理念
WebGPU 是 W3C 标准的下一代 Web 图形 API，设计目标是在 Web 平台上提供接近原生的 GPU 性能。它在 Vulkan/Metal/DirectX 12 之上提供了一层安全的抽象——保留了显式控制的核心优势（命令编码器、管线状态对象、绑定组），同时由浏览器实现自动管理内存、同步和验证，避免了 Vulkan 的复杂性和安全风险。


@vertex
fn vs_main(@location(0) position: vec3f,
           @location(1) color: vec3f) -> @builtin(position) vec4f {
    return vec4f(position, 1.0);
}

@fragment
fn fs_main() -> @location(0) vec4f {
    return vec4f(1.0, 0.0, 0.0, 1.0);
}
WebGPU 使用 WGSL（WebGPU Shading Language）作为着色器语言。WGSL 的语法结合了 Rust 和 HLSL 的元素，使用类型后缀（vec3f、mat4x4f）和属性注解（@location、@binding）。WGSL 的设计确保了在所有后端（Vulkan、Metal、D3D12）上的一致行为。


WebGPU 的绑定组（Bind Group）对应 Vulkan 的描述符集，渲染管线（Render Pipeline）对应 PSO，命令编码器（Command Encoder）对应命令缓冲区的录制。关键区别在于 WebGPU 自动管理资源同步——开发者不需要手动插入屏障或管理图像布局转换。


Bind Group 是 WebGPU 中的资源绑定机制，对应 Vulkan 的描述符集。一个 Bind Group 包含多个资源绑定（缓冲区、纹理、采样器），通过 Bind Group Layout 定义绑定的类型和可见性。


与 Vulkan 的描述符池/集不同，WebGPU 的 Bind Group 是不可变的——创建后不能修改。要更换绑定的资源需要创建新的 Bind Group。


wgpu 是 Rust 实现的 WebGPU 标准库，不仅用于 Firefox 浏览器的 WebGPU 支持，还可以作为独立的原生图形库在桌面和移动端使用。这使得 WebGPU API 超越了 Web 平台，成为了一个真正的跨平台图形抽象层。


WebGPU 的资源创建模型更加简洁。创建缓冲区时指定 usage flags（如 VERTEX | COPY_DST），创建纹理时指定 format、size 和 usage。浏览器的 WebGPU 实现负责底层的内存分配和布局，开发者不需要像 Vulkan 那样手动选择内存堆（Memory Heap）和分配对齐。


WebGPU 的错误处理模型也与 Vulkan 不同。Vulkan 的验证层是可选的开发工具，生产环境中通常禁用以提升性能。WebGPU 则始终进行完整的验证——每个 API 调用都会检查参数合法性，非法操作会产生验证错误而非未定义行为。这种"安全优先"的设计确保了 Web 平台上的 GPU 程序不会因为 Bug 而导致浏览器崩溃或安全漏洞。


WebGPU 的计算管线（Compute Pipeline）与 Vulkan 的计算着色器功能对等，支持工作组、共享内存、原子操作和存储缓冲。这为 Web 平台带来了 GPGPU 能力——物理模拟、AI 推理、图像处理等计算密集型任务可以在浏览器中使用 GPU 加速执行。


WebGPU vs WebGL 的实际性能差异:
- Draw Call 开销: WebGPU 比 WebGL 低 10-50 倍
- 多线程: WebGPU 支持 Worker 中录制命令
- 计算着色器: WebGL 无此能力
- 资源绑定: WebGPU 的绑定组比 WebGL 的逐次设置高效得多

小结
    

  • 新一代图形 API 以显式控制替代隐式状态机，换取更高的性能上限
    • 

  • Vulkan 的多线程命令缓冲区消除了传统 API 的单线程提交瓶颈
    • 

  • 管线状态对象预编译所有渲染状态，避免运行时的状态验证开销
    • 

  • Vulkan 的同步机制（信号量、栅栏、屏障）需要开发者精确管理资源依赖
    • 

  • Render Pass 的声明式设计使 Tile-Based GPU 可以优化片上缓存使用
    • 

  • WebGPU 在 Vulkan/Metal/D3D12 之上提供安全的自动同步抽象
    • 

  • WGSL 是 WebGPU 的着色器语言，确保跨后端的一致行为
    • 

  • wgpu 使 WebGPU API 可以在原生平台上使用，成为跨平台图形抽象层
    • 

  • WebGPU 的计算管线为 Web 平台带来了 GPGPU 能力
    • 

  • WebGPU 相比 WebGL 在 Draw Call 开销、多线程和资源绑定方面有显著优势
