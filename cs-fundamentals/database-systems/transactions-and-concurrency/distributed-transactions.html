分布式事务

核心概念

当数据分布在多个数据库或服务中时，需要跨节点保证事务的一致性。分布式事务比单机事务复杂得多，需要在一致性、可用性和分区容错性之间做出权衡。



CAP 定理
CAP 定理指出，分布式系统最多同时满足以下三个特性中的两个：

每个请求都能收到响应（不保证最新数据）




Partition tolerance (P)
网络分区时系统仍能运行

Saga 模式
Saga 将一个分布式事务拆分为一系列本地事务，每个本地事务有对应的补偿操作。如果某一步失败，依次执行前面步骤的补偿操作。






执行模式
说明
适用场景





编排式
中央协调器控制执行顺序
流程明确




协同式
各服务通过事件驱动自行协调
松耦合





编排式 Saga 示例：
1. 订单服务：创建订单（状态=PENDING）
2. 库存服务：扣减库存 → 成功
3. 支付服务：扣款 → 失败
4. 补偿：库存服务恢复库存
5. 补偿：订单服务取消订单（状态=CANCELLED）

TCC（Try-Confirm-Cancel）
TCC 是一种基于业务层面的两阶段协议，每个参与服务需要实现三个方法：






阶段
操作
示例





Try
预留资源，检查业务可行性
冻结账户余额




Confirm
确认执行，使用预留资源
实际扣款




Cancel
取消执行，释放预留资源
解冻余额





TCC 转账流程：

Try 阶段：
  - 账户 A：冻结 1000 元（available -= 1000, frozen += 1000）
  - 账户 B：无操作或预检查

Confirm 阶段（全部 Try 成功）：
  - 账户 A：扣减冻结金额（frozen -= 1000）
  - 账户 B：增加余额（available += 1000）

Cancel 阶段（任一 Try 失败）：
  - 账户 A：解冻金额（available += 1000, frozen -= 1000）

小结
    

  • CAP 定理决定了分布式系统必须在一致性和可用性之间权衡。
    • 

  • 2PC 是经典的强一致方案，但存在同步阻塞和单点故障问题。
    • 

  • Saga 通过补偿机制实现最终一致性，适合微服务架构的长事务。
    • 

  • TCC 在业务层实现两阶段协议，需要处理空回滚、悬挂和幂等问题。
    • 

  • 选择方案的关键因素是一致性要求、性能预算和实现复杂度。
