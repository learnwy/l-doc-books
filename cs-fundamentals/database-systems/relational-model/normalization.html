范式与规范化

核心概念

数据库规范化（Normalization）是通过分解关系来消除数据冗余和更新异常的过程。其理论基础是函数依赖，目标是让每个关系都符合特定的范式（Normal Form），从而保证数据一致性和存储效率。



函数依赖
函数依赖是规范化理论的基石。若属性集 X 的值能唯一确定属性集 Y 的值，则称 Y 函数依赖于 X，记作 X → Y。






依赖类型
定义
示例





完全函数依赖
Y 依赖于 X 的全部属性
(学号, 课程号) → 成绩




部分函数依赖
Y 仅依赖于 X 的部分属性
(学号, 课程号) → 姓名




传递函数依赖
X → Z 通过 X → Y → Z 间接推导
学号 → 系号 → 系主任





-- 示例表：存在函数依赖问题
CREATE TABLE 选课_未规范化 (
    学号     VARCHAR(10),
    姓名     VARCHAR(20),
    系号     VARCHAR(10),
    系主任   VARCHAR(20),
    课程号   VARCHAR(10),
    成绩     INT,
    PRIMARY KEY (学号, 课程号)
);
-- 函数依赖分析：
-- (学号, 课程号) → 成绩         完全依赖
-- 学号 → 姓名, 系号             部分依赖（仅依赖学号）
-- 学号 → 系号 → 系主任          传递依赖


范式层级
第一范式（1NF）
关系中每个属性的值都是不可再分的原子值。


-- 违反 1NF：电话列包含多个值
-- | 姓名 | 电话                |
-- | 张三 | 138xxx, 139xxx      |

-- 符合 1NF：拆分为原子值
CREATE TABLE 联系方式 (
    姓名     VARCHAR(20),
    电话     VARCHAR(15),
    PRIMARY KEY (姓名, 电话)
);
第二范式（2NF）
在满足 1NF 的基础上，消除部分函数依赖——所有非主属性必须完全依赖于候选键。


-- 违反 2NF：姓名仅依赖于学号（部分依赖）
-- 选课(学号, 课程号, 姓名, 成绩)

-- 分解为 2NF：
CREATE TABLE 学生 (
    学号 VARCHAR(10) PRIMARY KEY,
    姓名 VARCHAR(20)
);

CREATE TABLE 选课 (
    学号   VARCHAR(10),
    课程号 VARCHAR(10),
    成绩   INT,
    PRIMARY KEY (学号, 课程号),
    FOREIGN KEY (学号) REFERENCES 学生(学号)
);
第三范式（3NF）
在满足 2NF 的基础上，消除传递函数依赖——非主属性不能依赖于另一个非主属性。


-- 违反 3NF：学号 → 系号 → 系主任（传递依赖）
-- 学生(学号, 姓名, 系号, 系主任)

-- 分解为 3NF：
CREATE TABLE 院系 (
    系号   VARCHAR(10) PRIMARY KEY,
    系主任 VARCHAR(20)
);

CREATE TABLE 学生 (
    学号 VARCHAR(10) PRIMARY KEY,
    姓名 VARCHAR(20),
    系号 VARCHAR(10),
    FOREIGN KEY (系号) REFERENCES 院系(系号)
);
BCNF（Boyce-Codd 范式）
在满足 3NF 的基础上，要求每个非平凡函数依赖 X → Y 中，X 都是超键。BCNF 比 3NF 更严格，能消除主属性对候选键的部分或传递依赖。


-- 违反 BCNF 的经典案例：
-- 仓库管理(仓库号, 物品号, 管理员, 数量)
-- 候选键：(仓库号, 物品号)
-- 函数依赖：仓库号 → 管理员, 管理员 → 仓库号
-- "管理员 → 仓库号" 中管理员不是超键，违反 BCNF

-- 分解为 BCNF：
CREATE TABLE 仓库 (
    仓库号   VARCHAR(10) PRIMARY KEY,
    管理员   VARCHAR(20) UNIQUE
);

CREATE TABLE 库存 (
    仓库号 VARCHAR(10),
    物品号 VARCHAR(10),
    数量   INT,
    PRIMARY KEY (仓库号, 物品号),
    FOREIGN KEY (仓库号) REFERENCES 仓库(仓库号)
);

分解算法
无损连接分解
分解后的关系通过自然连接能恢复原始关系，不丢失信息。


原关系 R(A, B, C)，依赖 A → B
分解为 R1(A, B) 和 R2(A, C)
验证：R1 ⋈ R2 = R  ✓ 无损
保持依赖分解
分解后的各子关系上的函数依赖集合并后，能推导出原始的所有函数依赖。




反范式化权衡
在实际生产环境中，过度规范化可能导致大量连接操作，影响查询性能。反范式化（Denormalization）通过适当引入冗余来提升读取效率。






场景
策略
示例





高频读取低频写入
冗余存储常用字段
订单表冗余存储商品名称




避免多表连接
预计算汇总字段
用户表冗余存储订单总数




报表/分析场景
宽表设计
将多个维度合并到一张事实表




日志/事件流
完全反范式化
每条记录包含所有上下文信息





-- 反范式化示例：订单表冗余存储用户名
CREATE TABLE orders (
    order_id    BIGINT PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    user_name   VARCHAR(50),
    total_amount DECIMAL(10, 2),
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);


小结
    

  • 函数依赖是规范化的理论基础，分析依赖关系是分解表的前提。
    • 

  • 3NF 是工业实践中最常用的规范化目标，BCNF 更严格但分解可能不保持依赖。
    • 

  • 分解时需同时满足无损连接和保持依赖两个原则。
    • 

  • 在读多写少的 OLAP 场景中，适当反范式化可以显著提升查询性能。
    • 

  • 规范化与反范式化的选择取决于业务场景的读写比和一致性要求。
