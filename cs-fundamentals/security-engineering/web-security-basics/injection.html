SQL 注入与 NoSQL 注入

注入攻击概述

注入攻击是将恶意数据作为代码的一部分发送给解释器执行的攻击方式。SQL 注入长期占据 OWASP Top 10 的首位，而随着 NoSQL 数据库和 ORM 框架的普及，注入攻击的形态也在不断演变。注入漏洞的根本原因是程序将不可信的用户输入与可执行的指令混在一起，未做严格的边界分离。



SQL 注入
攻击原理
当应用程序将用户输入直接拼接到 SQL 语句中时，攻击者可以修改查询逻辑：


-- 原始查询（存在漏洞）
SELECT * FROM users WHERE username = '{input}' AND password = '{input}'

-- 攻击者输入: ' OR '1'='1' --
SELECT * FROM users WHERE username = '' OR '1'='1' --' AND password = ''

真实案例
2017 年 Equifax 数据泄露事件是注入攻击造成严重后果的典型案例。攻击者利用 Apache Struts 的远程代码执行漏洞入侵系统后，通过 SQL 注入从数据库中提取了 1.47 亿美国消费者的个人信息，包括社会安全号码、出生日期和信用卡号。




NoSQL 注入
MongoDB 注入
NoSQL 数据库同样存在注入风险。MongoDB 接受 JSON 对象作为查询条件，攻击者可注入操作符：


// 存在漏洞的查询
db.users.find({ username: req.body.username, password: req.body.password })

// 攻击者提交的 JSON
{ "username": "admin", "password": { "$ne": "" } }
// 效果：匹配 username 为 admin 且 password 不为空的记录，绕过认证

NoSQL 注入防御
针对 MongoDB 的注入防御需要在输入验证阶段过滤掉 $ 开头的键名，或使用 mongo-sanitize 等库自动剥离操作符。同时应避免使用 $where 子句，因为它允许执行任意 JavaScript。

防御策略
参数化查询
参数化查询将数据和代码严格分离，是防御 SQL 注入的最佳实践：


-- 参数化查询（安全）
SELECT * FROM users WHERE username = ? AND password = ?
各语言的参数化查询实现：


# Python + psycopg2
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
// Node.js + pg
pool.query('SELECT * FROM users WHERE id = $1', [userId]);

小结
    

  • SQL 注入通过拼接用户输入到查询语句来篡改查询逻辑
    • 

  • 参数化查询是防御 SQL 注入的黄金标准，ORM 是第二选择
    • 

  • NoSQL 同样存在注入风险，MongoDB 的操作符注入最为常见
    • 

  • 命令注入需通过避免直接调用系统命令和输入白名单验证来防御
    • 

  • 纵深防御：参数化查询 + 输入验证 + 最小权限 + WAF 多层配合
