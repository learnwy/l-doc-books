CSRF 与请求伪造

CSRF 概述

跨站请求伪造（Cross-Site Request Forgery，CSRF）是一种利用用户已认证身份在目标网站上执行非预期操作的攻击。攻击者诱导用户访问恶意页面，该页面自动向目标网站发送请求，浏览器会自动附带用户的 Cookie，使得请求看起来完全合法。CSRF 不需要获取用户的凭证，只需要用户在目标网站已登录即可发起攻击。



攻击方式
GET 型 CSRF
最简单的攻击形式，通过 <img> 标签即可触发：


<img src="https://bank.com/transfer?to=attacker&amount=10000" />
GET 型 CSRF 也可以通过 <link>、<script> 等标签或 CSS 中的 url() 发起。任何能触发 HTTP GET 请求的 HTML 元素都是潜在的攻击载体。


POST 型 CSRF
通过自动提交的隐藏表单发起：


<form action="https://bank.com/transfer" method="POST" id="csrf-form">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="10000" />
</form>
<script>
  document.getElementById('csrf-form').submit();
</script>
JSON 型 CSRF
现代 API 常使用 JSON 格式的请求体。在某些配置下，攻击者可以通过设置 enctype="text/plain" 的表单发送近似 JSON 格式的数据：


<form action="https://api.example.com/transfer" method="POST" enctype="text/plain">
  <input name='{"to":"attacker","amount":10000,"padding":"' value='"}' />
</form>
如果服务端未严格校验 Content-Type，这种请求可能被错误接受。

防御策略
CSRF Token
服务端为每个会话生成唯一的随机 Token，嵌入表单或请求头中。攻击者无法获取该 Token，因此无法伪造合法请求。Token 必须满足以下安全要求：使用密码学安全的随机数生成器、长度至少 128 位、绑定用户会话且一次性使用或限时有效。

自 2020 年起，Chrome 将 SameSite 的默认值从 None 改为 Lax，这一变更大幅降低了 CSRF 攻击的影响面。但依赖 GET 请求执行状态变更的应用仍然存在风险。


双重提交 Cookie
将 CSRF Token 同时放在 Cookie 和请求参数中。服务端验证两者是否一致。由于同源策略限制，攻击者无法读取目标域的 Cookie 值。这种方式的优势是无需服务端维护 Token 状态，适合无状态架构。

小结
    

  • CSRF 利用浏览器自动携带 Cookie 的机制伪造用户请求
    • 

  • CSRF Token 是最经典的防御方式，Token 需足够随机且绑定会话
    • 

  • SameSite=Lax 是现代浏览器的默认值，能阻止大部分 CSRF 攻击
    • 

  • 双重提交 Cookie 适用于无状态服务的场景
    • 

  • 多层防御（Token + SameSite + Origin 校验）才能提供最完善的保护
    • 

  • 所有状态变更操作必须使用 POST/PUT/DELETE，绝不能使用 GET
    •
