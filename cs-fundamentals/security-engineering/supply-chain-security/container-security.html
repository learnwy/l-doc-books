容器安全与镜像扫描

容器安全概述

容器技术以其轻量化和一致性优势成为现代应用部署的标准方式，但也引入了新的攻击面。从基础镜像到运行时环境，容器安全需要在构建、分发、运行三个阶段全面加固。

与传统虚拟机不同，容器共享宿主机内核，这意味着内核漏洞可能直接影响所有容器。攻击者一旦突破容器边界（容器逃逸），就能获得宿主机访问权限。因此，容器安全不仅要关注应用层面的漏洞，更要从操作系统内核、容器运行时、编排平台三个层面构建纵深防御体系。

选择基础镜像时需要权衡安全性与可调试性。distroless 镜像没有 shell 和包管理器，攻击者即使进入容器也无法安装工具链。但在排查问题时，可以使用调试版本（如 gcr.io/distroless/base:debug）临时获得 busybox shell。

多阶段构建是减小镜像攻击面的核心手段。第一阶段安装编译工具链和依赖进行构建，第二阶段仅从第一阶段拷贝编译产物到最小基础镜像中。这样最终镜像中不会包含 gcc、make 等构建工具，大幅减少可利用的二进制文件数量。

漏洞扫描的一个常见挑战是误报率。建议建立漏洞白名单机制：对于已确认不影响实际使用场景的漏洞（例如某个 CVE 只在特定配置下可利用，而你的容器不使用该配置），通过 .trivyignore 文件将其标记为已接受风险。同时定期审查白名单，确保过期的豁免条目被及时清理。

Seccomp 配置文件定义了容器可以执行的系统调用白名单。Docker 默认的 Seccomp 配置已经阻止了约 44 个危险的系统调用（如 reboot、mount、ptrace），但对于高安全性场景，建议创建自定义 Seccomp 配置文件，只允许应用实际需要的系统调用。

容器安全策略
Kubernetes Pod Security




级别

Kubernetes 1.25 正式引入 Pod Security Admission（PSA）替代已废弃的 PodSecurityPolicy。PSA 在命名空间级别设置安全策略，通过 enforce、audit、warn 三种模式灵活控制。生产集群建议对所有业务命名空间至少启用 Baseline 级别的 enforce 模式。

小结
    

  • 容器安全覆盖构建、分发、运行三个阶段
    • 

  • 使用 distroless 或 scratch 最小化基础镜像，减少攻击面
    • 

  • Trivy 是最全面的开源镜像扫描工具，覆盖 OS 包和语言依赖
    • 

  • Rootless 容器从根本上降低容器逃逸的风险
    • 

  • 运行时应启用 Seccomp + AppArmor 限制容器的系统调用和文件访问
    • 

  • 建立漏洞白名单机制处理误报，定期审查确保安全策略不过时
