整洁架构

核心概念

整洁架构（Clean Architecture）是 Robert C. Martin（Uncle Bob）提出的架构设计原则。它的核心规则只有一条：依赖方向由外向内——外层可以依赖内层，内层不能依赖外层。这确保了业务规则不受框架、数据库、UI 等外部细节的影响。

实现示例：用户管理系统
Entities（核心层）
class User {
  constructor(
    public readonly id: string,
    public readonly email: string,
    public readonly name: string,
    public readonly createdAt: Date,
  ) {
    this.validate();
  }

  private validate(): void {
    if (!this.email.match(/^[^\s@]+@[^\s@]+\.[^\s@]+$/)) {
      throw new Error(`Invalid email: ${this.email}`);
    }
    if (this.name.trim().length < 2) {
      throw new Error('Name must be at least 2 characters');
    }
  }

  updateName(newName: string): User {
    return new User(this.id, this.email, newName, this.createdAt);
  }

  updateEmail(newEmail: string): User {
    return new User(this.id, newEmail, this.name, this.createdAt);
  }
}
Use Cases（应用层）
interface UserRepository {
  findById(id: string): Promise<User | null>;
  findByEmail(email: string): Promise<User | null>;
  save(user: User): Promise<void>;
  delete(id: string): Promise<void>;
}

interface IdGenerator {
  generate(): string;
}

interface CreateUserInput {
  email: string;
  name: string;
}

interface CreateUserOutput {
  id: string;
  email: string;
  name: string;
}

class CreateUserUseCase {
  constructor(
    private userRepo: UserRepository,
    private idGenerator: IdGenerator,
  ) {}

  async execute(input: CreateUserInput): Promise<CreateUserOutput> {
    const existing = await this.userRepo.findByEmail(input.email);
    if (existing) {
      throw new Error(`User with email ${input.email} already exists`);
    }

    const user = new User(this.idGenerator.generate(), input.email, input.name, new Date());

    await this.userRepo.save(user);

    return {
      id: user.id,
      email: user.email,
      name: user.name,
    };
  }
}

class GetUserUseCase {
  constructor(private userRepo: UserRepository) {}

  async execute(id: string): Promise<CreateUserOutput | null> {
    const user = await this.userRepo.findById(id);
    if (!user) return null;
    return {
      id: user.id,
      email: user.email,
      name: user.name,
    };
  }
}
Interface Adapters（适配层）
class InMemoryUserRepository implements UserRepository {
  private users = new Map<string, User>();

  async findById(id: string): Promise<User | null> {
    return this.users.get(id) ?? null;
  }

  async findByEmail(email: string): Promise<User | null> {
    for (const user of this.users.values()) {
      if (user.email === email) return user;
    }
    return null;
  }

  async save(user: User): Promise<void> {
    this.users.set(user.id, user);
  }

  async delete(id: string): Promise<void> {
    this.users.delete(id);
  }
}

class UuidGenerator implements IdGenerator {
  generate(): string {
    return crypto.randomUUID();
  }
}
组装
const userRepo = new InMemoryUserRepository();
const idGenerator = new UuidGenerator();

const createUser = new CreateUserUseCase(userRepo, idGenerator);
const getUser = new GetUserUseCase(userRepo);

async function main() {
  const result = await createUser.execute({
    email: 'alice@example.com',
    name: 'Alice',
  });
  console.log('Created:', result);

  const found = await getUser.execute(result.id);
  console.log('Found:', found);
}

main();


依赖规则
关键观察：


    

  • User 实体不依赖任何外部组件
    • 

  • CreateUserUseCase 依赖 UserRepository 接口（而非具体实现）
    • 

  • InMemoryUserRepository 实现了 UserRepository 接口，属于外层
    • 

  • 更换数据库时，只需要新写一个 Repository 实现，核心业务逻辑不变
    • 





整洁架构的测试优势
class MockUserRepository implements UserRepository {
  private users: User[] = [];

  async findById(id: string): Promise<User | null> {
    return this.users.find((u) => u.id === id) ?? null;
  }

  async findByEmail(email: string): Promise<User | null> {
    return this.users.find((u) => u.email === email) ?? null;
  }

  async save(user: User): Promise<void> {
    this.users.push(user);
  }

  async delete(id: string): Promise<void> {
    this.users = this.users.filter((u) => u.id !== id);
  }
}

class FixedIdGenerator implements IdGenerator {
  constructor(private id: string) {}
  generate(): string {
    return this.id;
  }
}

async function testCreateUser() {
  const repo = new MockUserRepository();
  const idGen = new FixedIdGenerator('test-id-123');
  const useCase = new CreateUserUseCase(repo, idGen);

  const result = await useCase.execute({
    email: 'test@example.com',
    name: 'Test User',
  });

  console.assert(result.id === 'test-id-123');
  console.assert(result.email === 'test@example.com');
  console.log('Test passed!');
}

testCreateUser();
由于 Use Case 依赖接口而非具体实现，测试时可以轻松注入 Mock 对象，无需真实数据库。




常见误区
误区一：每个项目都需要整洁架构
整洁架构适合中大型、长期维护的项目。小型项目或原型开发中，它的分层开销可能大于收益。


误区二：层数越多越好
整洁架构的核心是依赖方向，而非层数。不要机械地创建层级，根据项目复杂度灵活调整。


误区三：DTO 到处传递
每层之间用 DTO 转换数据是整洁架构的常见做法，但过度的 DTO 转换会导致大量样板代码。在保持依赖方向正确的前提下，适度简化。




小结
    

  • 整洁架构的核心规则是依赖方向由外向内。
    • 

  • 内层定义接口，外层提供实现。
    • 

  • 核心业务逻辑不依赖框架、数据库等外部细节。
    • 

  • 通过接口注入依赖，实现高可测试性。
    •
