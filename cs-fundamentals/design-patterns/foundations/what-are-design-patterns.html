什么是设计模式

核心概念

设计模式（Design Pattern）是针对软件设计中反复出现的问题而总结出的通用解决方案。它不是一段可以直接使用的代码，而是一个描述问题、解决方案以及应用场景的模板。你可以把它理解为一份"经过验证的设计蓝图"。

设计模式的概念最早源于建筑学。建筑师 Christopher Alexander 在 1977 年出版的《A Pattern Language》中首次提出：每个模式描述了一个在我们的环境中反复出现的问题，以及该问题解决方案的核心，使你可以反复使用这个方案而不必每次重新发明。


1994 年，Erich Gamma、Richard Helm、Ralph Johnson 和 John Vlissides 四人（被称为 GoF，Gang of Four）将这一思想引入软件工程领域，出版了经典著作《Design Patterns: Elements of Reusable Object-Oriented Software》。这本书系统总结了 23 种设计模式，成为软件设计领域最具影响力的作品之一。




模式的分类体系
GoF 将 23 种设计模式分为三大类：






类别
关注点
核心问题





创建型
对象的创建机制
如何灵活地创建对象而不硬编码依赖？




结构型
对象的组合方式
如何将类和对象组合成更大的结构？




行为型
对象间的交互
如何分配职责并管理对象间的通信？







模式的标准描述结构
每个设计模式通常包含以下核心要素：


interface DesignPattern {
  name: string;
  intent: string;
  motivation: string;
  applicability: string[];
  structure: string;
  participants: Participant[];
  collaborations: string;
  consequences: string[];
  implementation: string;
  knownUses: string[];
  relatedPatterns: string[];
}

interface Participant {
  name: string;
  role: string;
}
以最简单的模式为例，来感受这种描述结构：


const strategyPattern = {
  name: 'Strategy',
  intent: '定义一系列算法，将每个算法封装起来，并使它们可以互换',
  motivation: '当一个系统需要在多种算法中动态选择时，硬编码会导致代码僵化',
  applicability: ['需要在运行时切换算法', '多个类仅在行为上有差异', '需要隔离算法的实现细节'],
};


模式与相似概念的区别
模式 vs 算法
算法是解决特定计算问题的确定步骤（如排序、搜索），输入输出明确。设计模式是解决设计问题的方案模板，描述的是代码的组织方式而非计算逻辑。


模式 vs 框架
框架是可复用的半成品代码，提供了应用程序的骨架。设计模式是比框架更高层次的抽象——框架中通常包含了多种设计模式的运用。


模式 vs 原则
原则（如 SOLID）是指导设计决策的通用准则。设计模式则是这些原则在特定场景下的具体实现方案。原则告诉你"应该怎样"，模式告诉你"具体如何做到"。




实际应用
为什么要学习设计模式
共同词汇：当团队成员都理解设计模式时，一句"这里用观察者模式"就能传达复杂的设计意图，极大提升沟通效率。


经过验证的方案：模式不是理论推演的产物，而是从大量成功项目中提炼出的实践经验。使用模式意味着站在前人的肩膀上。


设计灵活性：模式帮助你在正确的地方引入抽象层，让系统在面对变化时更容易扩展和修改。


现代语境下的设计模式
GoF 的 23 种模式诞生于 1994 年，当时的主流语言是 C++ 和 Smalltalk。在现代语言（如 TypeScript、Kotlin、Swift）中，一些模式的实现方式发生了显著变化：


const strategies = new Map<string, (a: number, b: number) => number>([
  ['add', (a, b) => a + b],
  ['subtract', (a, b) => a - b],
  ['multiply', (a, b) => a * b],
]);

function calculate(strategy: string, a: number, b: number): number {
  const fn = strategies.get(strategy);
  if (!fn) throw new Error(`Unknown strategy: ${strategy}`);
  return fn(a, b);
}

console.log(calculate('add', 10, 5));
console.log(calculate('multiply', 3, 4));
在上面的例子中，TypeScript 的一等函数特性让策略模式的实现变得极为简洁——不再需要定义接口和多个类，一个 Map 加上箭头函数就够了。




常见误区
误区一：每个项目都要用设计模式
设计模式是工具，不是目标。简单问题不需要复杂的模式。当代码足够直接且不太可能变化时，引入模式反而增加了不必要的抽象层。


误区二：模式只适用于面向对象编程
虽然 GoF 模式植根于 OOP，但很多模式的核心思想（如关注点分离、控制反转、依赖解耦）在函数式编程、响应式编程等范式中同样适用，只是实现形式不同。


误区三：死记硬背 UML 图
理解模式的本质意图比记忆其 UML 结构更重要。在实际开发中，你更需要的是识别"何时该用"的能力，而非精确复现某个类图。




小结
    

  • 设计模式是针对软件设计中反复出现问题的通用解决方案模板。
    • 

  • GoF 将模式分为创建型、结构型、行为型三大类，共 23 种经典模式。
    • 

  • 模式的价值在于提供共同词汇和经过验证的方案。
    • 

  • 在现代语言中，模式的实现方式可能更简洁，但核心思想不变。
    • 

  • 学习模式的重点是理解意图和适用场景，而非死记 UML 图。
