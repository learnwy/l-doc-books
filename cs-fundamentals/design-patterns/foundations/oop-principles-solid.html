面向对象原则与 SOLID

核心概念

SOLID 是面向对象编程和设计中最重要的五大原则的首字母缩写。这些原则是设计模式的理论基石——几乎每一个 GoF 模式都在践行其中一个或多个原则。理解 SOLID，你才能真正理解设计模式"为什么这样设计"。





原则
英文全称
核心思想





S
Single Responsibility Principle
一个类只做一件事




O
Open/Closed Principle
对扩展开放，对修改关闭




L
Liskov Substitution Principle
子类能替换父类且行为不变




I
Interface Segregation Principle
不强迫依赖不需要的接口




D
Dependency Inversion Principle
依赖抽象而非具体实现







单一职责原则（SRP）
一个类应该只有一个引起它变化的原因。换言之，一个类只承担一项职责。


class UserService {
  createUser(name: string, email: string): User {
    const user: User = { id: crypto.randomUUID(), name, email };
    return user;
  }
}

class UserRepository {
  private db: Map<string, User> = new Map();

  save(user: User): void {
    this.db.set(user.id, user);
  }

  findById(id: string): User | undefined {
    return this.db.get(id);
  }
}

class EmailNotifier {
  sendWelcome(user: User): void {
    console.log(`Sending welcome email to ${user.email}`);
  }
}

interface User {
  id: string;
  name: string;
  email: string;
}
上面将用户创建、数据持久化、邮件通知分离为三个独立的类。每个类只有一个变化的原因：业务规则变化影响 UserService，存储方式变化影响 UserRepository，通知方式变化影响 EmailNotifier。




开放封闭原则（OCP）
软件实体应该对扩展开放，对修改关闭。你应该能够在不修改现有代码的情况下添加新功能。


interface Shape {
  area(): number;
}

class Rectangle implements Shape {
  constructor(
    private width: number,
    private height: number,
  ) {}

  area(): number {
    return this.width * this.height;
  }
}

class Circle implements Shape {
  constructor(private radius: number) {}

  area(): number {
    return Math.PI * this.radius ** 2;
  }
}

class Triangle implements Shape {
  constructor(
    private base: number,
    private height: number,
  ) {}

  area(): number {
    return (this.base * this.height) / 2;
  }
}

function totalArea(shapes: Shape[]): number {
  return shapes.reduce((sum, shape) => sum + shape.area(), 0);
}
totalArea 函数无需知道具体有哪些形状。新增 Triangle 时，不需要修改 totalArea 或其他任何已有代码——这就是"对扩展开放，对修改关闭"。




里氏替换原则（LSP）
子类对象应该能够替换其父类对象出现的任何地方，而不影响程序的正确性。


class Bird {
  fly(): string {
    return 'flying';
  }
}

class Penguin extends Bird {
  fly(): string {
    throw new Error('Penguins cannot fly!');
  }
}
上面是 LSP 的经典反例。Penguin 继承了 Bird 却无法执行 fly，这意味着任何期望 Bird 的代码在接收 Penguin 时都可能崩溃。正确的做法是重新设计继承层次：


interface Movable {
  move(): string;
}

interface Flyable extends Movable {
  fly(): string;
}

class Sparrow implements Flyable {
  move(): string {
    return 'flying';
  }
  fly(): string {
    return 'soaring through the sky';
  }
}

class Penguin implements Movable {
  move(): string {
    return 'swimming';
  }
}
通过接口分离，Penguin 不再被迫实现它无法完成的 fly 方法。




接口隔离原则（ISP）
不应该强迫客户端依赖它不需要的接口。接口应该小而专注。


interface Printable {
  print(): void;
}

interface Scannable {
  scan(): void;
}

interface Faxable {
  fax(): void;
}

class MultiFunctionPrinter implements Printable, Scannable, Faxable {
  print(): void {
    console.log('Printing...');
  }
  scan(): void {
    console.log('Scanning...');
  }
  fax(): void {
    console.log('Faxing...');
  }
}

class SimplePrinter implements Printable {
  print(): void {
    console.log('Printing...');
  }
}
将一个臃肿的 Machine 接口拆分为 Printable、Scannable、Faxable 三个小接口。SimplePrinter 只需实现 Printable，无需被迫提供它不支持的扫描和传真功能。




依赖倒置原则（DIP）
高层模块不应该依赖低层模块，二者都应该依赖抽象。抽象不应该依赖细节，细节应该依赖抽象。


interface Database {
  save(table: string, data: Record<string, unknown>): void;
  find(table: string, id: string): Record<string, unknown> | undefined;
}

class MySQLDatabase implements Database {
  save(table: string, data: Record<string, unknown>): void {
    console.log(`MySQL: INSERT INTO ${table}`, data);
  }
  find(table: string, id: string): Record<string, unknown> | undefined {
    console.log(`MySQL: SELECT * FROM ${table} WHERE id = ${id}`);
    return undefined;
  }
}

class OrderService {
  constructor(private db: Database) {}

  createOrder(order: Record<string, unknown>): void {
    this.db.save('orders', order);
  }

  getOrder(id: string): Record<string, unknown> | undefined {
    return this.db.find('orders', id);
  }
}

const db = new MySQLDatabase();
const orderService = new OrderService(db);
OrderService 依赖 Database 抽象接口而非 MySQLDatabase 具体类。更换数据库实现时，OrderService 无需任何修改。




SOLID 与设计模式的关系




原则
直接相关的模式





SRP
Facade, Command, Mediator




OCP
Strategy, Decorator, Observer




LSP
Template Method, Factory Method




ISP
Adapter, Proxy




DIP
Abstract Factory, Dependency Injection







常见误区
误区一：严格遵循每一条原则
SOLID 是指导原则，不是铁律。在简单场景下过度应用 SOLID 会导致过度设计——大量的接口和抽象层让代码变得更难理解。关键是在复杂度和灵活性之间找到平衡。


误区二：SRP 意味着每个类只有一个方法
SRP 说的是"一个变化的原因"，而非"一个方法"。一个类可以有多个方法，只要它们围绕同一个职责展开。


误区三：DIP 就是依赖注入
依赖倒置原则（DIP）是一个设计原则，依赖注入（DI）是实现该原则的一种技术手段。DIP 强调的是依赖方向（依赖抽象），DI 强调的是依赖提供方式（从外部注入）。




小结
    

  • SRP：每个类只承担一个职责，只有一个变化的原因。
    • 

  • OCP：通过抽象和多态实现扩展，而不是修改现有代码。
    • 

  • LSP：子类必须能够安全替换父类，保持行为一致性。
    • 

  • ISP：将大接口拆分为多个小接口，避免强迫依赖。
    • 

  • DIP：高层模块和低层模块都依赖抽象，细节依赖抽象。
    • 

  • SOLID 是设计模式的理论根基，几乎每个模式都在践行这些原则。
