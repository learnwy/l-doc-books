如何选择设计模式

核心概念

选择设计模式是一项需要经验和判断力的决策。面对一个设计问题，你需要回答三个层层递进的问题：是否需要模式？需要哪个模式？如何在当前语境下适配模式？ 盲目套用模式和完全忽视模式都是极端——优秀的工程师懂得在两者之间找到平衡。

不需要模式的场景
function calculateDiscount(price: number, rate: number): number {
  return price * rate;
}
这段代码简单直接，不存在变化点，没有复杂的依赖关系。为它引入策略模式或工厂模式纯粹是过度设计。


判断准则：如果你无法清晰地说出"这个模式解决了什么具体问题"，那就不需要它。

决策框架
三步决策法
interface PatternDecision {
  step1_identify: '找出代码中的变化点（哪些部分最可能改变？）';
  step2_classify: '判断变化点属于哪种类型（创建/结构/行为）';
  step3_match: '在该类型的模式中，找到最匹配问题特征的模式';
}
实战示例：支付系统
假设你正在构建一个支付系统，需要支持多种支付方式（微信、支付宝、信用卡），未来还会新增更多。


Step 1 - 识别变化点：支付方式是变化点，新增支付方式不应修改已有代码。


Step 2 - 分类：这是一个"行为"问题——不同支付方式有不同的处理算法。


Step 3 - 匹配：多种算法可切换 → Strategy 模式。


interface PaymentStrategy {
  pay(amount: number): PaymentResult;
}

interface PaymentResult {
  success: boolean;
  transactionId: string;
}

class WeChatPayment implements PaymentStrategy {
  pay(amount: number): PaymentResult {
    console.log(`WeChat Pay: ¥${amount}`);
    return { success: true, transactionId: `wx_${Date.now()}` };
  }
}

class AlipayPayment implements PaymentStrategy {
  pay(amount: number): PaymentResult {
    console.log(`Alipay: ¥${amount}`);
    return { success: true, transactionId: `ali_${Date.now()}` };
  }
}

class PaymentProcessor {
  constructor(private strategy: PaymentStrategy) {}

  setStrategy(strategy: PaymentStrategy): void {
    this.strategy = strategy;
  }

  processPayment(amount: number): PaymentResult {
    return this.strategy.pay(amount);
  }
}

const processor = new PaymentProcessor(new WeChatPayment());
processor.processPayment(100);

processor.setStrategy(new AlipayPayment());
processor.processPayment(200);


模式组合
现实项目中，单一模式往往不够，需要多个模式协同工作：


class PaymentStrategyFactory {
  private static strategies = new Map<string, () => PaymentStrategy>([
    ['wechat', () => new WeChatPayment()],
    ['alipay', () => new AlipayPayment()],
  ]);

  static create(type: string): PaymentStrategy {
    const factory = this.strategies.get(type);
    if (!factory) throw new Error(`Unknown payment type: ${type}`);
    return factory();
  }
}

class LoggingDecorator implements PaymentStrategy {
  constructor(private wrapped: PaymentStrategy) {}

  pay(amount: number): PaymentResult {
    console.log(`[LOG] Payment started: ¥${amount}`);
    const result = this.wrapped.pay(amount);
    console.log(`[LOG] Payment result:`, result);
    return result;
  }
}

const strategy = PaymentStrategyFactory.create('wechat');
const logged = new LoggingDecorator(strategy);
logged.pay(500);
这个例子组合了 Factory（创建策略）、Strategy（支付算法切换）、Decorator（添加日志功能）三个模式。




常见误区
误区一：先选模式再找问题
正确顺序是先分析问题，再匹配模式。如果你发现自己在说"这里可以用 XX 模式"而说不清解决了什么问题，说明方向搞反了。


误区二：一个问题只能用一个模式
如上文所示，实际项目中经常需要组合多个模式。不要局限于"一个场景只用一个模式"的思维。


误区三：模式越多越好
每引入一个模式都增加了一层抽象。抽象是有成本的——它增加了代码量、增加了学习门槛、增加了间接调用。只在抽象带来的收益大于其成本时才使用。


误区四：必须严格遵循 GoF 的实现
GoF 的实现是基于 1994 年的 C++ 语境。在现代 TypeScript 中，你完全可以用函数、闭包、泛型等特性来简化模式的实现，只要保留模式的核心意图即可。




小结
    

  • 选择模式的第一步是识别代码中的变化点。
    • 

  • 按变化点的类型（创建/结构/行为）缩小候选范围。
    • 

  • 使用三步决策法：识别变化点 → 分类问题类型 → 匹配模式。
    • 

  • 实际项目中经常需要组合多个模式协同工作。
    • 

  • 始终先理解问题再选模式，避免过度设计。
