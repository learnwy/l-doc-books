重构到模式

核心概念

重构到模式（Refactoring to Patterns）是一种将设计模式引入已有代码的渐进式方法。你不是从零开始"设计"模式，而是在代码演进过程中，当坏味道出现时，逐步引入合适的模式来消除它们。这比一开始就过度设计更安全、更务实。

案例一：从 switch 到 Strategy
重构前
class PriceCalculator {
  calculate(customerType: string, amount: number): number {
    switch (customerType) {
      case 'regular':
        return amount;
      case 'premium':
        return amount * 0.9;
      case 'vip':
        return amount * 0.8;
      case 'employee':
        return amount * 0.7;
      default:
        throw new Error(`Unknown customer type: ${customerType}`);
    }
  }
}
问题：新增客户类型必须修改 calculate 方法，违反开放封闭原则。


重构后
type PricingRule = (amount: number) => number;

class PriceCalculatorV2 {
  private rules = new Map<string, PricingRule>();

  registerRule(customerType: string, rule: PricingRule): void {
    this.rules.set(customerType, rule);
  }

  calculate(customerType: string, amount: number): number {
    const rule = this.rules.get(customerType);
    if (!rule) throw new Error(`Unknown customer type: ${customerType}`);
    return rule(amount);
  }
}

const calculator = new PriceCalculatorV2();
calculator.registerRule('regular', (amount) => amount);
calculator.registerRule('premium', (amount) => amount * 0.9);
calculator.registerRule('vip', (amount) => amount * 0.8);
calculator.registerRule('employee', (amount) => amount * 0.7);

console.log(calculator.calculate('vip', 100));

calculator.registerRule('seasonal', (amount) => amount * 0.75);
console.log(calculator.calculate('seasonal', 100));


案例二：从回调地狱到命令模式
重构前
class FormHandler {
  private history: string[] = [];

  submit(data: Record<string, string>): void {
    console.log('Validating...');
    if (!data.name) throw new Error('Name required');

    console.log('Saving...');
    this.history.push(JSON.stringify(data));

    console.log('Notifying...');
    console.log(`Form submitted: ${data.name}`);

    console.log('Logging...');
    console.log(`[${new Date().toISOString()}] Form submitted`);
  }
}
重构后
interface FormCommand {
  execute(data: Record<string, string>): void;
  undo?(data: Record<string, string>): void;
}

class ValidateCommand implements FormCommand {
  execute(data: Record<string, string>): void {
    if (!data.name) throw new Error('Name required');
    if (!data.email) throw new Error('Email required');
  }
}

class SaveCommand implements FormCommand {
  private store: string[] = [];

  execute(data: Record<string, string>): void {
    this.store.push(JSON.stringify(data));
  }

  undo(): void {
    this.store.pop();
  }
}

class NotifyCommand implements FormCommand {
  execute(data: Record<string, string>): void {
    console.log(`Notification: Form submitted by ${data.name}`);
  }
}

class FormPipeline {
  private commands: FormCommand[] = [];

  addCommand(command: FormCommand): this {
    this.commands.push(command);
    return this;
  }

  execute(data: Record<string, string>): void {
    for (const command of this.commands) {
      command.execute(data);
    }
  }
}

const pipeline = new FormPipeline()
  .addCommand(new ValidateCommand())
  .addCommand(new SaveCommand())
  .addCommand(new NotifyCommand());

pipeline.execute({ name: 'Alice', email: 'alice@example.com' });


案例三：从紧耦合到观察者模式
重构前
class ShoppingCartBad {
  private items: string[] = [];

  addItem(item: string): void {
    this.items.push(item);
    this.updateUI();
    this.updateBadge();
    this.saveToLocalStorage();
    this.sendAnalytics();
  }

  private updateUI(): void {
    console.log('UI updated');
  }
  private updateBadge(): void {
    console.log('Badge updated');
  }
  private saveToLocalStorage(): void {
    console.log('Saved to storage');
  }
  private sendAnalytics(): void {
    console.log('Analytics sent');
  }
}
重构后
type CartEventHandler = (items: string[]) => void;

class ShoppingCart {
  private items: string[] = [];
  private listeners = new Map<string, Set<CartEventHandler>>();

  on(event: string, handler: CartEventHandler): () => void {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, new Set());
    }
    this.listeners.get(event)!.add(handler);
    return () => this.listeners.get(event)?.delete(handler);
  }

  private emit(event: string): void {
    this.listeners.get(event)?.forEach((fn) => fn([...this.items]));
  }

  addItem(item: string): void {
    this.items.push(item);
    this.emit('change');
  }

  removeItem(item: string): void {
    const index = this.items.indexOf(item);
    if (index !== -1) {
      this.items.splice(index, 1);
      this.emit('change');
    }
  }

  getItems(): string[] {
    return [...this.items];
  }
}

const cart = new ShoppingCart();

cart.on('change', (items) => console.log('UI:', items));
cart.on('change', (items) => console.log('Badge:', items.length));
cart.on('change', () => console.log('Saved to storage'));
cart.on('change', (items) => console.log('Analytics:', items.length, 'items'));

cart.addItem('TypeScript Book');
cart.addItem('Design Patterns Book');
ShoppingCart 不再知道任何具体的响应行为——关注点完全分离。




重构安全守则
    

  1. 先有测试，再重构——确保重构不改变行为
    2. 

  2. 小步前进——每次只做一个小改动
    3. 

  3. 每步验证——改动后立即运行测试
    4. 

  4. 可随时回退——Git commit 保驾护航
    5. 





常见误区
误区一：一次性大规模重构
大规模重构风险极高。应该识别代码中最痛的点，逐步改善，每次只引入一个模式。


误区二：重构时添加新功能
重构和功能开发是两种不同的活动。重构时只改善代码结构，不改变行为。功能开发时再利用改善后的结构添加新功能。


误区三：追求"完美"的模式实现
实际项目中的模式往往是变体或简化版。不必严格遵循 GoF 的类图，关键是解决了具体问题。




小结
    

  • 设计模式应该在重构过程中引入，而非预先设计。
    • 

  • 识别代码坏味道是触发重构的信号。
    • 

  • 遵循先测试、小步走、每步验证的安全重构守则。
    • 

  • 不追求完美实现，关键是解决具体问题。
