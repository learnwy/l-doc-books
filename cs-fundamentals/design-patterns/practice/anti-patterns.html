反模式

核心概念

反模式（Anti-Pattern）是看似合理甚至一度流行，但实际上会导致糟糕结果的常见做法。识别反模式与识别设计模式同等重要——知道什么不该做，有时比知道什么该做更有价值。



God Object（上帝对象）
一个类承担了过多的职责，知道并控制着系统中太多的内容。


class ApplicationManager {
  private users: Map<string, unknown> = new Map();
  private orders: Map<string, unknown> = new Map();
  private products: Map<string, unknown> = new Map();
  private config: Record<string, unknown> = {};
  private logs: string[] = [];

  createUser(name: string): void {
    /* ... */
  }
  deleteUser(id: string): void {
    /* ... */
  }
  authenticateUser(email: string, password: string): boolean {
    return false;
  }
  createOrder(userId: string, items: unknown[]): void {
    /* ... */
  }
  cancelOrder(orderId: string): void {
    /* ... */
  }
  addProduct(product: unknown): void {
    /* ... */
  }
  updateInventory(productId: string, qty: number): void {
    /* ... */
  }
  getConfig(key: string): unknown {
    return this.config[key];
  }
  setConfig(key: string, value: unknown): void {
    this.config[key] = value;
  }
  log(message: string): void {
    this.logs.push(message);
  }
  sendEmail(to: string, subject: string): void {
    /* ... */
  }
  generateReport(): string {
    return '';
  }
}
解决方案：按职责拆分为 UserService、OrderService、ProductService、ConfigService、Logger、EmailService、ReportService。每个类只做一件事（SRP）。




Spaghetti Code（意面代码）
代码结构混乱，控制流交错缠绕，难以追踪逻辑。


function processRequest(req: Record<string, unknown>): string {
  let result = '';
  if (req.type === 'A') {
    if (req.subType === 'A1') {
      if (req.priority === 'high') {
        result = 'fast-A1';
        if (req.amount && (req.amount as number) > 1000) {
          result += '-large';
          if (req.region === 'CN') {
            result += '-cn';
          }
        }
      } else {
        result = 'normal-A1';
      }
    } else if (req.subType === 'A2') {
      result = 'A2-processed';
      if (req.flag) {
        result = 'A2-flagged';
      }
    }
  } else if (req.type === 'B') {
    result = 'B-default';
  }
  return result;
}
解决方案：使用策略模式或职责链模式消除嵌套条件，提取各分支为独立的处理函数。


type RequestProcessor = (req: Record<string, unknown>) => string | null;

const processors: RequestProcessor[] = [
  (req) => (req.type === 'A' && req.subType === 'A1' && req.priority === 'high' ? buildFastA1Result(req) : null),
  (req) => (req.type === 'A' && req.subType === 'A1' ? 'normal-A1' : null),
  (req) => (req.type === 'A' && req.subType === 'A2' ? (req.flag ? 'A2-flagged' : 'A2-processed') : null),
  (req) => (req.type === 'B' ? 'B-default' : null),
];

function buildFastA1Result(req: Record<string, unknown>): string {
  let result = 'fast-A1';
  if ((req.amount as number) > 1000) result += '-large';
  if (req.region === 'CN') result += '-cn';
  return result;
}

function processRequestV2(req: Record<string, unknown>): string {
  for (const processor of processors) {
    const result = processor(req);
    if (result !== null) return result;
  }
  return 'unknown';
}


Golden Hammer（金锤子）
"如果你手里只有一把锤子，所有东西看起来都像钉子。"——用同一种技术/模式解决所有问题。


解决方案：根据具体问题选择合适的工具。简单场景用简单方案，复杂场景才用复杂方案。




Premature Optimization（过早优化）


"过早优化是万恶之源。" —— Donald Knuth




class OverEngineeredList<T> {
  private data: ArrayBuffer;
  private view: DataView;
  private size = 0;
  private capacity: number;

  constructor(initialCapacity = 1024) {
    this.capacity = initialCapacity;
    this.data = new ArrayBuffer(initialCapacity * 8);
    this.view = new DataView(this.data);
  }
}
在不确定性能瓶颈在哪里的情况下，就开始用 ArrayBuffer 实现列表。


解决方案：先用最简单、最清晰的实现，然后通过性能分析定位真正的瓶颈，再针对性优化。




Cargo Cult Programming（货物崇拜编程）
不理解原因就照搬做法——"别人用了设计模式，所以我也要用"。


interface IUserServiceFactory {
  createUserService(): IUserService;
}

interface IUserService {
  getUser(id: string): IUser;
}

interface IUser {
  getId(): string;
  getName(): string;
}

class UserImpl implements IUser {
  constructor(
    private id: string,
    private name: string,
  ) {}
  getId(): string {
    return this.id;
  }
  getName(): string {
    return this.name;
  }
}

class UserServiceImpl implements IUserService {
  getUser(id: string): IUser {
    return new UserImpl(id, 'Alice');
  }
}

class UserServiceFactoryImpl implements IUserServiceFactory {
  createUserService(): IUserService {
    return new UserServiceImpl();
  }
}
三层抽象只为了获取一个用户——这就是没有理解模式意图就机械套用的后果。


更合理的版本：


interface User {
  id: string;
  name: string;
}

function getUser(id: string): User {
  return { id, name: 'Alice' };
}


Lava Flow（熔岩流）
无人敢动的遗留代码和配置，因为没人知道它是否还在使用。


解决方案：


    

  • 添加监控和日志，确认代码是否被调用
    • 

  • 提升测试覆盖率
    • 

  • 渐进式移除，每次删除一小部分并验证

反模式识别清单
interface AntiPatternCheck {
  name: string;
  symptoms: string[];
  risk: 'high' | 'medium' | 'low';
}

const checks: AntiPatternCheck[] = [
  {
    name: 'God Object',
    symptoms: ['文件超过 500 行', '类有超过 10 个公开方法', '构造函数有超过 5 个依赖'],
    risk: 'high',
  },
  {
    name: 'Spaghetti Code',
    symptoms: ['嵌套超过 3 层的 if/else', '函数超过 50 行', '圈复杂度超过 10'],
    risk: 'high',
  },
  {
    name: 'Golden Hammer',
    symptoms: ['项目中只用了一种设计模式', '所有问题都用同一种框架/库解决', '拒绝学习新的解决方案'],
    risk: 'medium',
  },
  {
    name: 'Premature Optimization',
    symptoms: ['没有性能数据就开始优化', '为了性能牺牲可读性', '使用复杂数据结构处理小数据集'],
    risk: 'medium',
  },
  {
    name: 'Cargo Cult',
    symptoms: ['说不清为什么用某个模式', '每个类都有对应接口但只有一个实现', '照搬其他项目的架构而未评估适用性'],
    risk: 'medium',
  },
];


常见误区
误区一：所有反模式都应该立即修复
反模式需要根据影响程度和修复成本来排列优先级。有些低风险的反模式在当前阶段可以接受。


误区二：反模式是二元的
代码不是"有反模式"或"没有反模式"那么简单。大多数代码处于"不完美但可以接受"的灰色地带。


误区三：重构就能消除所有反模式
有些反模式的根源是组织问题（如沟通不足、缺乏代码审查），而非纯粹的技术问题。




小结
    

  • 反模式是看似合理但长期有害的常见做法。
    • 

  • God Object 和 Spaghetti Code 是最常见也最有害的反模式。
    • 

  • 避免 Golden Hammer——根据问题选择工具，而非用工具定义问题。
    • 

  • 理解"为什么"比"怎么做"更重要，避免 Cargo Cult。
    •
