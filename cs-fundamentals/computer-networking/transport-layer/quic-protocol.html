Part IV · 网络与分布式 (Networks & Distributed)计算机网络 简介传输层 简介QUIC 协议

QUIC 协议

QUIC 的诞生背景

TCP 作为传输层协议已服务互联网数十年，但其固有限制在现代网络环境中日益突出：三次握手的连接建立延迟、队头阻塞（Head-of-Line Blocking）、操作系统内核升级困难等。QUIC（Quick UDP Internet Connections）由 Google 设计，运行在 UDP 之上，在用户空间实现了可靠传输、加密和多路复用，成为 HTTP/3 的底层传输协议。

QUIC 与 TCP+TLS 对比

特性 TCP + TLS 1.3 QUIC
握手延迟 1-RTT (TCP) + 1-RTT (TLS) 1-RTT（首次），0-RTT（恢复）
队头阻塞 有（TCP 层） 无（流级别独立）
多路复用 应用层模拟 协议原生支持
连接迁移 不支持（绑定四元组） 支持（Connection ID）
加密范围 仅应用数据 几乎所有头部和数据
部署升级 内核协议栈 用户空间，可快速迭代

连接建立：0-RTT 与 1-RTT

QUIC 将传输层握手和加密握手合并为一个过程，首次连接仅需 1-RTT，后续连接可实现 0-RTT。

0-RTT 的安全风险：0-RTT 数据可能被重放攻击，服务端需要对 0-RTT 请求做幂等性检查。




多路复用与流（Stream）
QUIC 在单个连接上支持多个独立的流，每个流有独立的流控和有序交付。一个流的丢包不会阻塞其他流。

Connection ID 与连接迁移
传统 TCP 连接由四元组（源 IP、源端口、目标 IP、目标端口）标识。当用户从 Wi-Fi 切换到蜂窝网络时，IP 地址改变，TCP 连接断开。


QUIC 使用 Connection ID 标识连接，与 IP 地址和端口无关：


网络切换时，客户端使用新的 IP 地址发送包含相同 Connection ID 的 QUIC 包，服务端验证后继续会话，用户无感知中断。

HTTP/3：QUIC 之上的应用层
HTTP/3 是 HTTP 协议的第三个大版本，将底层传输从 TCP 替换为 QUIC。


HTTP/3 使用 QPACK（而非 HPACK）进行头部压缩，QPACK 避免了 HPACK 在 QUIC 多流环境下的队头阻塞问题。

小结
    

  • QUIC 在 UDP 上实现了可靠传输、加密和多路复用，解决了 TCP 的队头阻塞和连接建立延迟问题。
    • 

  • 0-RTT 连接恢复显著降低了重复访问的延迟，但需注意重放攻击风险。
    • 

  • Connection ID 机制使连接不再绑定 IP 地址，支持无缝网络切换。
    • 

  • HTTP/3 基于 QUIC 构建，是 HTTP 协议演进的最新方向。
    • 

  • QUIC 运行在用户空间，拥塞控制算法可插拔，便于快速迭代和部署。
