零拷贝与高性能 IO

传统 I/O 的问题

传统的文件传输（读取文件并通过网络发送）涉及多次数据拷贝和上下文切换：





开销
次数





数据拷贝
4 次（2 次 DMA + 2 次 CPU）




上下文切换
4 次（read 进/出 + write 进/出）




系统调用
2 次（read + write）





对于只需要转发文件内容的场景（如 Web 服务器发送静态文件），用户空间的两次拷贝完全是浪费。




sendfile
sendfile 将数据直接从文件描述符传输到 Socket，无需经过用户空间。


ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);
数据流




开销
次数





数据拷贝
3 次（2 次 DMA + 1 次 CPU）




上下文切换
2 次




系统调用
1 次





带 SG-DMA 的 sendfile
当网卡支持 SG-DMA（Scatter-Gather DMA）时，可以进一步消除内核中的 CPU 拷贝：






开销
次数





数据拷贝
2 次（仅 DMA，零 CPU 拷贝）




上下文切换
2 次




系统调用
1 次





这是真正意义上的零拷贝。




splice
splice 在两个文件描述符之间通过管道（pipe）移动数据，无需经过用户空间。


ssize_t splice(int fd_in, off_t *off_in, int fd_out, off_t *off_out,
               size_t len, unsigned int flags);




特性
说明





要求
至少一端必须是管道




数据拷贝
内核内部移动页面引用，不拷贝数据




用途
文件到 Socket、Socket 到文件





splice 的典型用法
splice 通过移动内核缓冲区的页面引用而非复制数据来实现零拷贝。




mmap + write
通过 mmap 将文件映射到进程地址空间，然后直接 write 到 Socket。






开销
次数





数据拷贝
3 次（2 次 DMA + 1 次 CPU）




上下文切换
4 次




系统调用
2 次（mmap + write）





mmap + write 减少了一次 CPU 拷贝（省去了从内核缓冲区到用户缓冲区的拷贝），但上下文切换没有减少。

Page Cache 的角色
零拷贝技术的基础是 Linux 的 Page Cache：






特性
说明





读缓存
文件数据首次读取后缓存在 Page Cache




写缓存
写入先到 Page Cache，异步刷盘




预读
检测到顺序读取时自动预读后续页面




内存回收
内存不足时回收 Page Cache

Nginx 配置示例
http {
    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;
}


Direct I/O
某些场景下应用需要绕过 Page Cache 直接访问磁盘：






场景
原因





数据库
自行管理缓存（Buffer Pool），避免双重缓存




大文件传输
避免大文件污染 Page Cache




实时性要求
需要确保数据立即落盘





int fd = open("/path/to/file", O_RDONLY | O_DIRECT);
Direct I/O 要求用户缓冲区地址和大小都必须按扇区对齐。




小结
    

  • 传统 I/O 涉及 4 次数据拷贝和 4 次上下文切换，性能浪费严重
    • 

  • sendfile 将拷贝限制在内核空间，配合 SG-DMA 可实现真正的零 CPU 拷贝
    • 

  • splice 通过管道在内核内部移动页面引用实现零拷贝
    • 

  • Page Cache 是零拷贝技术的基础，提供读缓存和预读优化
    • 

  • Direct I/O 绕过 Page Cache，适合数据库等自管理缓存的场景
    • 

  • Nginx 使用 sendfile，Kafka 使用 sendfile，RocketMQ 使用 mmap
    •
