正则引擎实现

核心概念

正则引擎（Regex Engine）是将正则表达式转换为可执行匹配逻辑的软件组件。在编译器的上下文中，正则引擎是词法分析器的底层驱动——它将词法规则（正则表达式）编译为高效的自动机，然后用这些自动机扫描源代码字符流。

正则引擎有两大实现流派：基于自动机的引擎（DFA/NFA 引擎）保证线性时间匹配，适用于编译器词法分析；基于回溯的引擎（Backtracking Engine）支持更丰富的特性（如反向引用），但最坏情况下可能指数级慢。

理解两者的差异对选择正确的工具至关重要。自动机引擎基于形式语言理论，有严格的复杂度保证；回溯引擎基于递归搜索，更灵活但缺乏最坏情况保证。编译器几乎总是选择自动机引擎。

Thompson NFA 模拟
Thompson NFA 模拟是自动机引擎的核心算法，由 Ken Thompson 于 1968 年在 QED 编辑器中首次实现。其核心思想是同时追踪 NFA 的所有可能状态，而不是像回溯引擎那样逐一探索每条路径。


算法维护一个"当前状态集合"。对每个输入字符，计算所有当前状态在该字符上的转移目标，加上 ε 闭包，得到新的状态集合。如果最终状态集合包含接受状态，则匹配成功。这种"宽度优先"的探索方式是 Thompson 算法避免回溯的关键。


Thompson NFA 模拟算法:

function match(nfa, input):
    current = epsilonClosure({nfa.start})

    for ch in input:
        next = {}
        for state in current:
            for target in transition(state, ch):
                next.add(target)
        current = epsilonClosure(next)

    return current.intersect(nfa.acceptStates).isNotEmpty()
这个算法的时间复杂度是 O(n × m)，其中 n 是输入长度，m 是 NFA 状态数。由于 Thompson 构造保证 NFA 状态数为 O(r)（r 为正则表达式长度），总复杂度为 O(n × r)。


对于编译器词法分析中长度固定的正则表达式，r 是常数，所以匹配时间是 O(n)。这个线性时间保证是自动机引擎相比回溯引擎的核心优势。


Thompson 算法的关键优势是没有回溯——它通过并行追踪所有状态来避免指数级的路径探索。


一个经典的对比案例是正则表达式 (a?){n}a{n} 匹配字符串 aⁿ：


    

  • 回溯引擎：需要 O(2ⁿ) 时间（尝试 2ⁿ 种 a? 匹配或不匹配的组合）
    • 

  • Thompson 算法：仅需 O(n²) 时间（每步最多 n 个活跃状态，共 n 步）
    • 



当 n = 30 时，回溯引擎需要超过 10 亿次操作，而 Thompson 算法仅需约 900 次。这个差异在实践中意味着秒级与微秒级的区别。


惰性 DFA 构造
纯 DFA 引擎在匹配速度上最优（每个字符一次查表，O(1)），但预先构造完整 DFA 可能面临指数级状态膨胀。


惰性 DFA 构造（Lazy DFA Construction）是一种折中方案：仅在需要时才创建 DFA 状态，将构造开销分摊到匹配过程中。这种"按需构造"的思想在计算机科学中非常常见——类似于操作系统的按需分页和编程语言的惰性求值。


惰性 DFA 的工作流程：


    

  1. 从 NFA 起始状态的 ε 闭包开始，作为 DFA 的初始状态
    2. 

  2. 对当前 DFA 状态和输入字符，计算 NFA 转移目标的 ε 闭包
    3. 

  3. 检查这个 NFA 状态集合是否已经有对应的 DFA 状态（查哈希表）
    4. 

  4. 如果已存在，直接使用；如果不存在，创建新的 DFA 状态并缓存
    5. 



Google RE2 引擎就采用这种策略。它设置了 DFA 缓存的上限（默认 8MB），当缓存满时淘汰最近最少使用的状态。


在实践中，由于输入的局部性（相似的输入倾向于访问相似的状态），惰性 DFA 通常只创建很少的状态就能覆盖大部分匹配路径。


这种策略的另一个优势是它优雅地处理了 Unicode。完整的 Unicode 字母表有超过 100 万个码点，预构造完整 DFA 的状态转移表会非常庞大。惰性 DFA 只为实际出现的字符范围创建转移，避免了这种膨胀。

回溯引擎与灾难性回溯
回溯引擎（Backtracking Engine）的实现更直观：将正则表达式转换为递归函数调用，选择分支时先尝试一个方向，如果失败则回溯到选择点尝试另一个方向。


这种方式天然支持反向引用和捕获组，因为每条路径的匹配历史都被保存在调用栈中。反向引用（如 \1 引用第一个捕获组的内容）要求引擎记住之前匹配的文本，这在自动机模型中难以表达。


回溯引擎伪代码 (表达式 a|b):

function matchAlternation(input, pos):
    saved = pos
    if matchA(input, pos):
        return true
    pos = saved          // 回溯
    return matchB(input, pos)
回溯引擎的问题在于灾难性回溯（Catastrophic Backtracking）。当正则表达式包含嵌套的量词和选择时，回溯路径数量可能指数级增长。


这个问题的根源在于：回溯引擎对选择分支的探索是深度优先的，而深度优先搜索在有大量重叠路径时会反复探索相同的子问题。


经典的灾难性回溯案例：


正则: (a+)+$
输入: "aaaaaaaaaaaaaaaaaab"

回溯引擎尝试所有可能的 a+ 分组方式:
(a)(a)(a)...(a)b  → 失败
(aa)(a)(a)...(a)b → 失败
(a)(aa)(a)...(a)b → 失败
...
分组方式数量: 2^(n-1)（n 为 a 的个数）
这个问题在 Web 安全领域被称为 ReDoS（Regular Expression Denial of Service）。攻击者可以构造特定的输入，使得服务器的正则匹配陷入指数级的回溯，导致拒绝服务。编译器的词法分析器由于使用自动机引擎，天然不受 ReDoS 影响。


避免灾难性回溯的策略包括：


    

  • 使用自动机引擎（根本性解决方案）
    • 

  • 设置匹配超时（防御性措施）
    • 

  • 使用原子分组（Atomic Groups）减少回溯点
    • 

  • 使用占有量词（Possessive Quantifiers）防止回退
    • 

  • 重写正则表达式避免嵌套量词
    • 



多模式匹配与 Aho-Corasick
编译器的词法分析器需要同时匹配多个 token 规则（标识符、关键字、数字、运算符等）。这与单模式正则匹配不同——词法分析器每次从当前位置开始，需要找到所有规则中最长匹配的那个。


Aho-Corasick 算法是多模式字符串匹配的经典算法，而将多个正则表达式合并为一个 NFA 则是编译器词法分析的标准做法。


将 N 个正则表达式 R₁, R₂, ..., Rₙ 合并为一个 NFA 的方法：创建一个新的起始状态 S，从 S 向每个 Rᵢ 的 NFA 起始状态添加 ε 转移。每个 Rᵢ 的接受状态标记为不同的 token 类型。当 DFA 的一个状态包含多个接受状态时，选择优先级最高的 token 类型。


合并 NFA 结构:

新起始状态 S
  ├──ε──→ NFA(keyword "if") → Accept(KEYWORD_IF)
  ├──ε──→ NFA(identifier)   → Accept(IDENT)
  ├──ε──→ NFA(integer)      → Accept(INT_LIT)
  ├──ε──→ NFA(operator)     → Accept(OPERATOR)
  └──ε──→ NFA(whitespace)   → Accept(SKIP)
将合并后的 NFA 转换为 DFA，就得到了一个能同时匹配所有 token 规则的自动机。DFA 的每个接受状态知道它匹配的是哪种 token 类型。这就是 flex/lex 工具的核心原理。


在处理关键字时，一个常见的优化是不为每个关键字生成独立的 NFA 分支，而是先将所有类似标识符的 token 匹配为 IDENT，然后通过关键字哈希表查找确认是否为关键字。这避免了关键字数量增加时 DFA 状态数的膨胀。


另一个重要的优化是字符类合并。多个 token 规则中重复出现的字符类（如 [a-zA-Z]）可以在 NFA 构造阶段合并，减少重复的状态转移。flex 和 re2c 都实现了这种优化。


Aho-Corasick 算法本身是多模式精确字符串匹配的最优算法（O(n + m + z)，z 为匹配数），但编译器词法分析需要的是正则模式匹配。因此实际的词法分析器使用的是"多正则表达式合并 NFA/DFA"方案，而非纯 Aho-Corasick。


小结
    

  • 正则引擎分为自动机引擎（保证线性）和回溯引擎（支持更多特性但可能指数级慢）
    • 

  • Thompson NFA 模拟通过并行追踪所有状态避免回溯，时间 O(nm)
    • 

  • 惰性 DFA 构造按需创建状态，平衡了构造开销和匹配性能
    • 

  • 灾难性回溯是回溯引擎的固有风险，编译器通过自动机引擎规避
    • 

  • 多个正则表达式可以合并为一个 NFA/DFA，实现同时匹配所有 token 规则
    • 

  • 关键字识别通常采用"先匹配标识符，再查哈希表"的优化策略
    • 

  • 字符类合并和 NFA 状态压缩进一步减少自动机的规模
    • 

  • 理解正则引擎的内部机制有助于编写高效的词法规则和避免性能陷阱
    •
