词法分析与分词

核心概念

词法分析（Lexical Analysis）是编译器前端的第一个阶段，负责将源代码的字符流转换为有意义的词法单元（Token）序列。这个过程也称为分词（Tokenization）或扫描（Scanning）。词法分析器（Lexer/Scanner）逐字符读取源代码，根据预定义的词法规则识别出每个 token 的类型和值。

从编译器架构的角度看，词法分析的意义在于建立字符级输入与结构化 token 流之间的桥梁。它屏蔽了空白符、注释等对语法分析无关的细节，使得后续的语法分析器可以在更高的抽象层次上工作。

一个设计良好的词法分析器通常以 O(n) 时间完成扫描（n 为源代码字符数），是编译器中最高效的阶段之一。词法分析还负责维护位置信息（行号、列号），为后续阶段的错误报告提供基础数据。

Token 的分类与结构
Token 通常表示为一个包含类型和属性的结构体。不同的编程语言有不同的 token 分类，但核心类别是通用的：


Token 分类体系:

关键字 (Keyword):     if, else, while, return, class, function
标识符 (Identifier):  变量名、函数名、类名
字面量 (Literal):     整数 42, 浮点数 3.14, 字符串 "hello", 布尔 true
运算符 (Operator):    +, -, *, /, ==, !=, >=, &&, ||
分隔符 (Delimiter):   (, ), {, }, [, ], ;, ,
赋值符 (Assignment):  =, +=, -=, *=, /=
注释 (Comment):       // 行注释, /* 块注释 */
空白 (Whitespace):    空格, 制表符, 换行符
Token 的内部表示通常包含以下字段：


type Token = {
  type: TokenType;
  lexeme: string;
  line: number;
  column: number;
  literal?: number | string | boolean;
};
位置信息（行号和列号）对错误报告至关重要。当编译器在后续阶段发现语义错误时，它需要能够追溯到源代码的具体位置。现代编译器通常还记录 token 的字节偏移量，以支持增量解析和 IDE 集成。


关键字与标识符的区分是词法分析中的常见问题。两种主流策略：


一是在正则表达式层面为每个关键字定义独立的规则（如 "if" → KEYWORD_IF），并通过优先级保证关键字优先于标识符匹配。


二是先将所有类似标识符的 token 识别为 IDENT，然后查表将关键字替换为对应的 token 类型。后者更灵活，适合关键字集合可能变化的语言。


最长匹配与优先级规则
词法分析器在遇到可能匹配多个规则的输入时，需要明确的消歧策略。两条核心规则是最长匹配（Maximal Munch）和优先级匹配（Priority Match）。


最长匹配要求词法分析器尽可能多地消耗输入字符。例如，对于输入 ifx，即使 if 是关键字，词法分析器仍然会将整个 ifx 识别为标识符，因为 ifx 比 if 更长。同样，>= 会被识别为一个大于等于运算符，而非 > 和 = 两个独立 token。


优先级匹配在最长匹配长度相同时启用。例如，if 同时匹配关键字规则和标识符规则，但因为关键字规则定义在前（优先级更高），所以 if 被识别为关键字。


输入: "iffy >= 42"

分词过程:
1. 尝试匹配 → "iffy" (IDENT, 最长匹配, 跳过 "if" 关键字)
2. 跳过空白
3. 尝试匹配 → ">=" (GE, 最长匹配, 不拆分为 ">" + "=")
4. 跳过空白
5. 尝试匹配 → "42" (INT_LIT)

结果: [IDENT("iffy"), GE(">="), INT_LIT(42)]
这两条规则虽然简单，但它们的交互可能产生微妙的问题。例如 C++ 中的 >> 在模板上下文中可能是两个 >（模板闭合），在其他上下文中是右移运算符。C++11 通过修改语法规则解决了这个问题，但 C++03 时代需要程序员手动插入空格 > >。


有限自动机驱动的扫描
大多数编译器的词法分析器基于 DFA（确定性有限自动机）实现。扫描过程的核心是一个状态转移循环：从初始状态开始，读入一个字符，根据当前状态和字符查转移表得到下一个状态，重复直到无法继续转移或到达接受状态。


DFA 驱动的扫描器伪代码:

function nextToken():
    state = START
    lexeme = ""
    lastAcceptState = NONE
    lastAcceptPos = 0

    while state != ERROR:
        ch = peek()
        next = transition[state][ch]
        if next == ERROR:
            break
        advance()
        lexeme += ch
        state = next
        if isAccept(state):
            lastAcceptState = state
            lastAcceptPos = position

    if lastAcceptState != NONE:
        rollback(position - lastAcceptPos)
        return Token(tokenType[lastAcceptState], lexeme)
    else:
        reportError()
上面的伪代码展示了回退策略——当 DFA 无法继续时，回退到最后一次接受的位置。这对处理某些 token 边界至关重要。例如对于输入 3.method()，DFA 在读到 3. 后期望浮点数的小数部分，但遇到 m 后必须回退到 3，将其识别为整数 token。


状态转移表通常在编译时生成（通过 flex 等工具）或手工编码。表的大小为 |States| × |Σ|，其中 |Σ| 通常是 128（ASCII）或 256。对于大型词法规范，转移表可能很大，此时可以采用压缩表技术（如行差分编码）来减少内存占用。


特殊 Token 的处理
实际编程语言中存在一些正则表达式难以优雅处理的词法结构，通常需要在词法分析器中添加特殊逻辑。


字符串字面量是最常见的特殊情况。转义序列（\n、\t、\\、\"）需要在扫描过程中解析。多行字符串（Python 的 """、JavaScript 的模板字符串）需要追踪嵌套状态。原始字符串（Rust 的 r#"..."#、Python 的 r"..."）需要不同的转义处理规则。


嵌套注释（如 Rust 和 Swift 的 /* /* ... */ */）需要一个计数器追踪嵌套深度，这超出了纯正则语言的能力。实践中通常在 DFA 的框架内通过手工编写计数逻辑来处理。


缩进敏感语法（如 Python、Haskell）要求词法分析器维护一个缩进栈。在每行的开头，比较当前缩进级别与栈顶：如果增加则生成 INDENT token，如果减少则生成一个或多个 DEDENT token。这种逻辑完全超出正则语言的能力范围，需要在词法分析器中嵌入有状态的处理逻辑。

错误恢复与诊断
当词法分析器遇到无法匹配任何规则的字符时，需要进行错误处理。简单的策略是报告错误并跳过该字符，继续扫描。更好的策略是尝试提供有意义的错误信息。


常见的词法错误类型包括：非法字符（如中文标点出现在代码中）、未终结的字符串字面量、未终结的块注释、非法数字格式（如 0x 后没有十六进制数字）。


错误恢复策略:

1. 恐慌模式 (Panic Mode):
   跳过字符直到遇到已知的同步点（空白符或分隔符）
   优点: 简单可靠
   缺点: 可能跳过过多有效内容

2. 错误 Token 模式:
   将无法识别的字符序列包装为 ERROR token
   传递给语法分析器处理
   优点: 不丢失信息
   缺点: 增加语法分析器复杂度

3. 修复模式:
   尝试自动修复（如插入缺失的引号）
   优点: 用户体验好
   缺点: 修复可能不正确
现代编译器通常结合多种策略，并且在错误发生时记录详细的位置信息，以生成高质量的诊断消息。Rust 编译器的错误信息是业界标杆——它不仅指出错误位置，还提供修复建议和上下文高亮。


小结
    

  • 词法分析将字符流转换为 Token 流，是编译器的第一个阶段
    • 

  • Token 包含类型、词素、位置等信息，位置信息对错误报告至关重要
    • 

  • 最长匹配和优先级匹配是两条核心消歧规则
    • 

  • DFA 驱动的扫描器通过状态转移表实现 O(n) 时间复杂度
    • 

  • 字符串、嵌套注释、缩进语法等需要超出纯 DFA 的特殊处理
    • 

  • 高质量的错误恢复和诊断信息显著提升开发者体验
    • 

  • 词法分析器的设计直接影响编译器的整体性能和可用性
