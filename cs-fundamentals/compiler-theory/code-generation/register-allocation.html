寄存器分配

核心概念

寄存器分配（Register Allocation）是编译器后端最关键的优化之一。它将 IR 中无限数量的虚拟寄存器映射到目标架构有限数量的物理寄存器上。当物理寄存器不够用时，必须将某些值溢出（Spill）到内存中。

寄存器和内存之间的性能差距是数量级的——寄存器访问通常是 1 个时钟周期，而 L1 缓存是 3-5 个周期，主内存是 100+ 个周期。因此，寄存器分配的质量直接影响生成代码的执行速度。

寄存器分配的核心是一个 NP 完全问题——最优解不可行，实际编译器使用启发式算法。两种主流方法是图着色和线性扫描。

活跃性分析
在进行寄存器分配之前，编译器需要知道每个虚拟寄存器在哪些程序点上是"活跃的"。一个变量在某个程序点是活跃的，当且仅当存在一条从该点到该变量某个使用点的路径，且路径上没有该变量的重新定义。


活跃性分析是一种逆向数据流分析——信息从变量的使用点向定义点方向流动。


数据流方程:
  LiveIn(B) = Use(B) ∪ (LiveOut(B) - Def(B))
  LiveOut(B) = ∪ LiveIn(S), S 是 B 的后继块

Use(B): 在 B 中使用但未在使用前定义的变量
Def(B): 在 B 中定义的变量
以一个简单的例子说明：


BB1:
  a = 1          Def: {a}
  b = 2          Def: {a, b}     Use: {}
  goto BB2

BB2:
  c = a + b      Def: {c}       Use: {a, b}
  if c > 0       Use: {a, b, c}
    goto BB3
    goto BB4

BB3:
  d = a * 2      Use: {a}       Def: {d}
  return d

BB4:
  return b                       Use: {b}
活跃区间（Live Range）：


    

  • a: 从 BB1 的定义到 BB2 和 BB3 的最后使用
    • 

  • b: 从 BB1 的定义到 BB2 和 BB4 的最后使用
    • 

  • c: 从 BB2 的定义到 BB2 的使用
    • 



两个变量如果活跃区间重叠，就不能分配到同一个物理寄存器。


图着色寄存器分配
图着色（Graph Coloring）是经典的寄存器分配方法。


干涉图（Interference Graph）是一个无向图：


    

  • 每个虚拟寄存器是一个节点
    • 

  • 如果两个虚拟寄存器的活跃区间重叠，则在它们之间添加一条边
    • 



寄存器分配问题等价于：用 k 种颜色（k 是物理寄存器数量）给干涉图着色，使得相邻节点颜色不同。


Chaitin 的算法（1981，后经 Briggs 改进）：


1. 构建: 构建干涉图
2. 简化: 找到度数 < k 的节点，移除并压栈
          (如果不存在，选择一个节点溢出)
3. 着色: 从栈中弹出节点，分配一个与邻居不同的颜色
4. 溢出: 如果无法着色，将该变量溢出到内存，
         重写代码（插入 load/store），回到步骤 1
合并（Coalescing）是图着色的一个重要优化。如果两个虚拟寄存器之间存在复制操作（a = b），且它们在干涉图中不相邻，就可以将它们合并为一个节点。合并消除了复制操作，但可能增加节点的度数，使着色更困难。


如果有 3 个物理寄存器（k=3），上面的干涉图可以着色为：a=R1, b=R2, c=R3, d=R1（d 和 a 不相邻，可以共享寄存器）。

线性扫描寄存器分配
线性扫描（Linear Scan）是一种更快速的寄存器分配算法，适合 JIT 编译器。它的核心思想是将活跃区间排序，然后从前到后扫描，贪心地分配寄存器。


算法:
1. 计算所有变量的活跃区间 [start, end]
2. 按 start 排序
3. 维护一个"活跃集合"（当前占用寄存器的变量）

for each interval I in sorted order:
    // 移除已结束的区间
    expire(I.start)

    if 有空闲寄存器:
        分配空闲寄存器给 I
        加入活跃集合
    else:
        // 溢出：选择结束最晚的区间（可能是 I 自己）
        spill(longest in active set or I)
线性扫描的时间复杂度是 O(n log n)（排序主导）。相比图着色的 O(n²)，它在大规模代码上显著更快。


线性扫描的代码质量通常比图着色差 5-15%。但对于 JIT 编译器，编译速度本身就是性能的一部分——花太长时间编译意味着程序启动变慢。

调用约定与寄存器约束
寄存器分配不是在真空中进行的——它必须遵守目标架构的调用约定（Calling Convention）。调用约定规定了函数参数如何传递、返回值如何返回、哪些寄存器是调用者保存（caller-saved）和被调用者保存（callee-saved）。


x86-64 System V 调用约定:
参数寄存器: rdi, rsi, rdx, rcx, r8, r9
返回值:     rax (整数), xmm0 (浮点)
调用者保存: rax, rcx, rdx, rsi, rdi, r8-r11
被调用者保存: rbx, rbp, r12-r15
栈指针:     rsp
调用者保存（Caller-Saved）寄存器在函数调用后可能被破坏。如果调用者需要在调用后继续使用某个值，必须在调用前保存它。


被调用者保存（Callee-Saved）寄存器的值在函数返回后保持不变。如果被调用函数要使用这些寄存器，它必须先保存旧值，返回前恢复。


寄存器分配器需要在函数调用点插入必要的保存/恢复指令。一个聪明的分配器会尽量将跨调用存活的值放在被调用者保存寄存器中，以减少保存/恢复的开销。


对于 SIMD 寄存器（如 x86 的 xmm/ymm 寄存器），调用约定通常规定所有 SIMD 寄存器都是调用者保存的。这意味着使用 SIMD 指令的代码在函数调用前后需要额外的保存/恢复操作。


小结
    

  • 寄存器分配将无限虚拟寄存器映射到有限物理寄存器
    • 

  • 活跃性分析确定每个变量的活跃区间，是寄存器分配的基础
    • 

  • 图着色方法产生高质量代码，是 AOT 编译器的主流选择
    • 

  • 线性扫描更快但代码质量略低，适合 JIT 编译器
    • 

  • 调用约定规定了寄存器在函数调用时的保存和恢复规则
    • 

  • 溢出处理是寄存器不足时的必要手段，需要最小化性能影响
    • 

  • 寄存器分配是 NP 完全问题，所有实际算法都是启发式近似
    •
