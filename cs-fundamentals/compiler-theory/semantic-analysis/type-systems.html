类型系统

核心概念

类型系统（Type System）是编程语言中用于分类值和表达式的形式化框架。它为每个程序构造赋予一个类型标签，然后通过类型规则检查这些标签的一致性。类型检查的目标是在编译期捕获一类常见错误——类型不匹配。

从编译器的角度看，类型系统是语义分析阶段的核心组件。语法分析器确保程序的结构合法（"括号配对了吗？"），而类型检查器确保程序的语义合法（"你不能把字符串和整数相加"）。

类型系统的理论基础是类型论（Type Theory），一个源自数学逻辑的分支。Curry-Howard 同构揭示了类型与命题之间的深刻对应——类型是命题，程序是证明。这一对应关系是依赖类型语言（如 Agda、Idris）的理论基石。

类型检查规则
类型检查通过类型判断（Type Judgment）的形式化规则进行。一个类型判断写作 Γ ⊢ e : T，读作"在类型环境 Γ 下，表达式 e 具有类型 T"。


类型环境 Γ 是一个从变量名到类型的映射（类似符号表）。类型规则以推理规则的形式定义——给定前提条件，推导出结论。


常见的类型规则：


变量规则:
  x : T ∈ Γ
  ─────────────
  Γ ⊢ x : T

函数应用规则:
  Γ ⊢ f : T₁ → T₂    Γ ⊢ e : T₁
  ──────────────────────────────────
  Γ ⊢ f(e) : T₂

If 表达式规则:
  Γ ⊢ cond : Bool    Γ ⊢ e₁ : T    Γ ⊢ e₂ : T
  ─────────────────────────────────────────────────
  Γ ⊢ if cond then e₁ else e₂ : T

二元运算规则:
  Γ ⊢ e₁ : Int    Γ ⊢ e₂ : Int
  ────────────────────────────────
  Γ ⊢ e₁ + e₂ : Int
实现类型检查器时，这些规则直接对应 AST 节点的处理逻辑：


function typeCheck(env: TypeEnv, node: Expression): Type {
  switch (node.type) {
    case 'Identifier':
      return env.lookup(node.name);

    case 'BinaryExpression':
      const leftType = typeCheck(env, node.left);
      const rightType = typeCheck(env, node.right);
      if (node.operator === '+') {
        if (leftType === INT && rightType === INT) return INT;
        if (leftType === STRING && rightType === STRING) return STRING;
        throw new TypeError('type mismatch in +');
      }
      break;

    case 'CallExpression':
      const fnType = typeCheck(env, node.callee);
      if (fnType.kind !== 'Function') throw new TypeError('not callable');
      const argTypes = node.args.map((a) => typeCheck(env, a));
      checkParamTypes(fnType.params, argTypes);
      return fnType.returnType;
  }
}
子类型与型变
子类型（Subtyping）允许类型之间存在层级关系。如果 S 是 T 的子类型（S <: T），则任何需要 T 的地方都可以安全地使用 S。这就是 Liskov 替换原则的类型论表述。


面向对象语言中，子类型通常通过继承实现： Dog <: Animal 意味着 Dog 的实例可以用在期望 Animal 的任何地方。


型变（Variance）描述了复合类型的子类型关系如何随其组成类型的子类型关系变化：


    

  • 协变（Covariant）：如果 S <: T，则 F(S) <: F(T)。只读容器是协变的：ReadonlyArray<Dog> <: ReadonlyArray<Animal>。
    

    • 

  • 逆变（Contravariant）：如果 S <: T，则 F(T) <: F(S)。函数参数是逆变的：接受 Animal 参数的函数可以用在期望接受 Dog 参数的地方。
    

    • 

  • 不变（Invariant）：S <: T 不意味着 F(S) 和 F(T) 之间有任何关系。可变容器是不变的：Array<Dog> 和 Array<Animal> 之间没有子类型关系。
    

    •

结构化类型与名义类型
类型兼容性的判断有两种哲学：结构化类型（Structural Typing）和名义类型（Nominal Typing）。


结构化类型关注类型的形状——两个类型如果具有相同的结构（相同的字段和方法），就被认为兼容。


type Point = { x: number; y: number };
type Vector = { x: number; y: number };

const p: Point = { x: 1, y: 2 };
const v: Vector = p;
TypeScript 和 Go 的接口系统使用结构化类型。上面的代码在 TypeScript 中完全合法——Point 和 Vector 结构相同，因此兼容。


名义类型关注类型的名字——即使两个类型结构完全相同，只要名字不同就不兼容。


Java、C#、Rust 的 struct/class 使用名义类型。在 Java 中，两个结构相同但名字不同的类不能互相赋值。

泛型与参数多态
泛型（Generics）允许类型被参数化——一个数据结构或函数可以在不同类型上工作，同时保持类型安全。泛型在类型论中对应参数多态（Parametric Polymorphism）。


function identity<T>(x: T): T {
  return x;
}

type List<T> = {
  head: T;
  tail: List<T> | null;
};

function map<T, U>(list: List<T>, f: (item: T) => U): List<U> {
  if (list === null) return null;
  return { head: f(list.head), tail: map(list.tail, f) };
}
泛型的编译实现有两种主要策略：


类型擦除（Type Erasure）：编译后删除所有泛型类型信息，用统一的表示（通常是指针/引用）替代。Java 和 TypeScript 采用这种策略。优点是不增加代码体积，缺点是运行时无法获取泛型类型信息。


单态化（Monomorphization）：为每种具体类型参数生成独立的代码副本。Rust 和 C++ 的模板采用这种策略。优点是零运行时开销（具体类型已知），缺点是可能导致代码膨胀（code bloat）。

小结
    

  • 类型系统为程序构造赋予类型标签，在编译期捕获类型不匹配错误
    • 

  • 类型检查通过形式化的类型规则对 AST 进行自底向上的类型推导
    • 

  • 子类型允许类型间的层级关系，型变描述复合类型的子类型传递方向
    • 

  • 结构化类型看形状，名义类型看名字——两种哲学各有利弊
    • 

  • 泛型实现分为类型擦除（Java）和单态化（Rust）两种策略
    • 

  • 现代类型系统是编译器最复杂的组件之一，直接影响语言的表达力和安全性
