Part III · 系统 (Systems)线程与并发 简介原子操作 简介原子操作的核心思想

原子操作的核心思想

问题背景

在并发编程中，保护共享数据的传统方式是使用锁（Lock）。锁虽然有效，但带来了显著的性能开销：线程在等待锁的过程中被挂起，涉及上下文切换、内核调度等昂贵的操作。对于简单的数据操作（如计数器加一、标志位翻转），使用锁就像用大炮打蚊子——过度重量级。

原子操作的核心思想就是：在不使用锁的前提下，通过硬件级别的支持来保证操作的不可分割性。



原子操作是"轻量级同步"的代表：用最小的代价解决最常见的并发问题。






核心原理
思想一：不可分割性
原子操作最根本的思想是不可分割性（Indivisibility）——在操作执行过程中，没有任何其他线程能够介入或观察到中间状态。


这意味着从任何外部观察者的角度来看，原子操作要么还没开始，要么已经完成，永远不会处于"执行了一半"的状态。


// 非原子操作：三个步骤，其他线程可在任意间隙介入
temp = 读取(counter)        // ← 其他线程可在此处介入
temp = temp + 1              // ← 或此处
写回(counter, temp)          // ← 或此处

// 原子操作：整体不可分割，外部只能看到操作前或操作后的状态
原子执行 {
  temp = 读取(counter)
  temp = temp + 1
  写回(counter, temp)
}  // 整个过程对外部是"瞬间"完成的
思想二：无锁线程安全
原子操作的第二个核心思想是不需要显式的同步原语（如锁）就能实现线程安全。


使用锁时，线程需要经历"获取锁 → 执行操作 → 释放锁"的流程，如果锁被其他线程持有，当前线程就会阻塞等待。而原子操作跳过了这个中间环节，直接在硬件层面保证操作的安全性。


对比两种方式的线程安全实现：


// ---- 基于锁的线程安全 ----
class LockedCounter {
  private value = 0;
  private lock = new Mutex();

  increment(): void {
    this.lock.acquire(); // 可能阻塞
    this.value += 1;
    this.lock.release();
  }
}

// ---- 基于原子操作的线程安全 ----
class AtomicCounter {
  private value = new AtomicInteger(0);

  increment(): void {
    this.value.fetchAdd(1); // 永不阻塞，硬件保证安全
  }
}
思想三：硬件级高效性
原子操作的第三个核心思想是充分利用硬件能力来实现高效的并发控制。


现代 CPU 提供了专门的原子指令，这些指令在硬件层面保证了操作的不可分割性。相比于操作系统层面的锁机制，硬件原子指令的开销小得多：

分类与变体
CAS：比较并交换
CAS（Compare-And-Swap） 是最重要的原子操作原语，几乎所有高级原子操作都基于它实现。CAS 的语义是：




如果变量的当前值等于期望值，则将其更新为新值；否则不做任何修改。整个过程是原子的。




函数 CAS(地址, 期望值, 新值) -> 布尔值:
    原子执行 {
        如果 *地址 == 期望值:
            *地址 = 新值
            返回 真    // 交换成功
        否则:
            返回 假    // 交换失败，当前值已被其他线程修改
    }
CAS 的典型使用模式是自旋重试——如果 CAS 失败（说明有其他线程抢先修改了值），就重新读取当前值并再次尝试：


用 CAS 实现原子加一：


function atomicIncrement(atom: AtomicInteger): void {
  let success = false;
  while (!success) {
    const current = atom.load();
    const next = current + 1;
    success = atom.compareAndSwap(current, next);
  }
}
CAS 的 ABA 问题
CAS 有一个经典的陷阱——ABA 问题：


初始状态: value = A

线程 1: 读取 value → A
线程 2: 将 value 从 A 改为 B
线程 2: 将 value 从 B 改回 A
线程 1: CAS(期望=A, 新值=C) → 成功！

// 线程 1 的 CAS 成功了，但它并不知道 value 曾经被改变过
// 在某些场景下（如链表操作），这可能导致逻辑错误
解决 ABA 问题的常见方法是给值附加一个版本号，每次修改时版本号递增：


原子变量 = { 值: A, 版本: 1 }

线程 1: 读取 → { A, 1 }
线程 2: 修改 → { B, 2 } → { A, 3 }
线程 1: CAS(期望={A, 1}, 新值={C, 2}) → 失败！版本不匹配

在低竞争场景下，原子操作的性能优势非常明显。但在高竞争场景下（大量线程频繁争抢同一变量），自旋重试的开销会急剧增加，此时锁反而可能更合适。






小结
    

  • 原子操作的核心思想是不可分割性——操作对外界表现为瞬间完成，无中间状态
    • 

  • 原子操作实现了无锁的线程安全，避免了锁带来的阻塞、上下文切换和死锁风险
    • 

  • 原子操作依赖硬件级支持（CPU 原子指令），性能远优于操作系统级的锁机制
    • 

  • CAS（比较并交换） 是最核心的原子操作原语，配合自旋重试构成无锁编程的基础
    • 

  • 需要注意 CAS 的 ABA 问题，可通过版本号机制解决
    • 

  • 原子操作最适合低竞争、简单操作的场景；高竞争或复杂操作场景仍应考虑使用锁
    •
