原型与迭代

核心概念

原型设计是把想法转化为可测试的产物——从纸质草图到可交互的 Figma 原型再到代码原型，每一级保真度适合不同的问题。迭代是设计流程的核心——第一版必然有误，要通过原型 → 测试 → 学习 → 修改 → 重复来改进。Steve Jobs 说过："设计不是产品看起来如何，而是它如何运作"——只有原型才能让设计在接触现实后得到改进。本节介绍保真度阶梯（低保真纸质 → 中保真线框 → 高保真视觉稿 → 可交互原型 → 代码原型）、不同保真度适合的问题、Figma/Sketch/Framer/ProtoPie 工具、用原型做测试、以及"构建-度量-学习"循环。

保真度 工具 时间 适合的问题
纸质草图 笔 + 纸 分钟 概念/流程
线框图 Figma、Balsamiq 1-3小时 布局/信息架构
视觉稿 Figma、Sketch 半天-1天 视觉设计
可交互原型 Figma、Framer 1-3 天 交互/流程
代码原型 React、Flutter 1-N 天 性能/开发可行性

保真度阶梯

低保真：

  • 纸质草图/白板。
  • 快速且廉价。
  • 适合头脑风暴和对齐共识。
  • 用户不会被视觉细节分散注意。
  • 有些用户可能不太认真对待。

中保真：

  • 线框图（灰度色块）。
  • 关注布局和信息架构。
  • 跳过色彩和排版细节。

高保真：

  • 视觉稿，带有真实色彩、排版和图片。
  • 接近最终外观。
  • 适合利益相关者评审。

可交互：

  • 点击热区、页面转场。
  • 接近真实应用感受。
  • 适合可用性测试。

代码原型：

  • 真正的 React/Flutter/Swift 代码。
  • 获得性能反馈。
  • 接近生产环境。

选择保真度的规则

问题决定保真度：

  • "概念是否合理？" → 纸质。
  • "流程对不对？" → 线框图。
  • "看起来如何？" → 视觉稿。
  • "用起来如何？" → 可交互。
  • "性能是否可以？" → 代码。

时间决定保真度：

  • 1 小时头脑风暴 → 纸质。
  • 1 周迭代周期 → 线框图 + 视觉稿。
  • 1 个月项目 → 代码原型。

受众决定保真度：

  • 内部头脑风暴 → 低保真。
  • 利益相关者评审 → 中/高保真。
  • 用户测试 → 可交互。
  • 工程师交付 → 视觉稿含标注。

纸质原型

优势：

  • 极快且极便宜。
  • 任何人都能参与（不需软件技能）。
  • 用户不被视觉细节分散注意。

方法：

  • 在索引卡上画界面。
  • "操作员"充当系统（用户操作时手动切换卡片）。
  • 用户像使用真实应用一样操作。

工作坊：

  • "疯狂八格"：8 分钟画 8 个方案。
  • "设计工作室"：参与者轮流画草图 + 互评。

Figma 实战

主流设计工具（2024年）：

  • 基于 Web 的协作。
  • 组件库。
  • 自动布局（响应式）。
  • 变体（状态变化）。
  • 原型模式（热区 + 转场）。
  • 开发者模式（标注 + 尺寸测量）。

实战工作流：

  1. 纸上画草图 5 分钟。
  2. 在 Figma 中画线框 1 小时。
  3. 高保真视觉稿 1 天。
  4. 添加交互效果 半天。
  5. 分享给团队/用户。
  6. 根据反馈迭代。

插件生态：

  • Stark（无障碍检查）。
  • Content Reel（真实内容填充）。
  • AI 插件（自动生成）。
构建-度量-学习
精益创业（Eric Ries）：


    

  • 构建最小可行原型。
    • 

  • 度量用户反应。
    • 

  • 学习什么有效。
    • 

  • 迭代。
    • 



应用于设计：


    

  • 不为未验证的想法构建生产版本。
    • 

  • 原型 + 测试让风险早暴露。
    • 

  • 方向错误时快速调整。
    • 



原型测试
目的：在投入工程资源前尽早获取反馈。


方法：


    

  • 每轮 5 名用户（Nielsen 1993——5 名用户发现 80% 问题）。
    • 

  • 出声思维（用户描述想法）。
    • 

  • 任务场景（如"试着找到你朋友的主页"）。
    • 

  • 记录哪里失败。
    • 



产出：


    

  • 可用性问题列表。
    • 

  • 严重程度评级。
    • 

  • 改进建议。
    • 



迭代：


    

  • 修复主要问题。
    • 

  • 进行新一轮测试。
    • 

  • 对比指标变化。
    • 



A/B 测试
生产环境中的原型：


    

  • 部署 A 版和 B 版给不同用户。
    • 

  • 测量指标（转化率、参与度）。
    • 

  • 选择胜出版本。
    • 



适合场景：


    

  • 定量决策。
    • 

  • 已有用户基础。
    • 

  • 单一变量变化。
    • 



不适合场景：


    

  • 概念验证（变化太大）。
    • 

  • 长期效果（测试通常短期）。
    • 



样本量：


    

  • 需要统计功效。
    • 

  • 工具：Optimizely、VWO。
    • 



迭代速度
快速迭代优于缓慢完善：


    

  • 多轮 1 周迭代优于 1 轮 6 周。
    • 

  • 早期且频繁的反馈优于晚期且稀少的反馈。
    • 



瓶颈：


    

  • 招募用户慢——建立用户池/面板。
    • 

  • 利益相关者评审慢——安排定期评审。
    • 

  • 工程交付慢——使用设计系统/令牌。
    • 



冲刺结构：


    

  • 第 1-2 天：调研/构思。
    • 

  • 第 3-4 天：原型。
    • 

  • 第 5 天：测试 + 决策。
    • 

  • 每周重复。
    • 



设计评审
内部评审：


    

  • 团队成员互相评审设计。
    • 

  • 使用共同词汇（原则、启发规则）。
    • 

  • 不进行人身攻击。
    • 



流程：


    

  • 设计师展示设计 + 决策依据。
    • 

  • 同伴给出结构化反馈。
    • 

  • 讨论 + 决定。
    • 



评审文化：


    

  • 高频率、低风险。
    • 

  • 鼓励分歧意见。
    • 

  • 书面记录决策。
    • 



工具比较
Figma：


    

  • 主流协作设计 + 原型工具。
    • 

  • 基于 Web。
    • 

  • 个人免费、团队订阅制。
    • 



Sketch：


    

  • 仅限 Mac。
    • 

  • 较早的 Mac 原生工具。
    • 

  • 热度下降。
    • 



Adobe XD：


    

  • Adobe 生态。
    • 

  • 已于 2023 年停止维护。
    • 



Framer：


    

  • 对代码友好的原型工具。
    • 

  • 更高保真度的交互。
    • 



ProtoPie：


    

  • 传感器/触觉交互。
    • 

  • 适合移动端原型。
    • 



Whimsical：


    

  • 快速线框 + 流程图。
    • 



Penpot：


    

  • 开源的 Figma 替代品。
    • 



设计系统
设计系统是可复用的组件库 + 原则 + 令牌：


组件：


    

  • 按钮、表单、卡片、对话框。
    • 

  • 预构建且经过测试。
    • 



令牌：


    

  • 颜色、间距、排版的命名变量。
    • 

  • 如"主色调"、"中等间距"。
    • 

  • 跨平台共享（iOS/Android/Web）。
    • 



文档：


    

  • 何时使用什么组件。
    • 

  • 应做与不应做。
    • 



好处：


    

  • 一致性。
    • 

  • 速度（不重复设计）。
    • 

  • 对工程师友好的交付。
    • 



示例：


    

  • Material Design。
    • 

  • Apple HIG。
    • 

  • IBM Carbon。
    • 

  • Atlassian Design。
    • 



设计师与工程师的协作
过去（传统方式）：


    

  • 设计师提供静态视觉稿。
    • 

  • 工程师重新实现。
    • 

  • 标注误解频发。
    • 



现在（现代方式）：


    

  • Figma 开发者模式：工程师查看标注 + 提取值。
    • 

  • 设计系统：工程师使用共享组件。
    • 

  • Storybook：交互式代码组件库。
    • 



最佳实践：


    

  • 设计师 + 工程师尽早结对。
    • 

  • 一起迭代。
    • 

  • 避免隔墙抛砖式交付。
    • 



原型设计中的反模式
1. 跳过原型直接生产：


    

  • 为未验证的想法构建生产版本。
    • 

  • 错误方向成本极高。
    • 



2. 过度打磨低保真：


    

  • 花时间完善纸质草图。
    • 

  • 浪费成本。
    • 



3. 跳过用户测试：


    

  • 设计师觉得没问题 ≠ 用户觉得没问题。
    • 

  • 永远要测试。
    • 



4. 仅用团队成员测试：


    

  • 团队有偏见（了解产品）。
    • 

  • 需要新鲜视角。
    • 



5. 忽略反馈：


    

  • 测试了但忽略发现。
    • 

  • 浪费流程。
    • 



6. 只做一轮：


    

  • 一轮不够。
    • 

  • 多轮迭代必要。
    • 



现代 AI 原型工具
AI 工具加速原型设计：


    

  • Galileo AI / Uizard：文本 → 界面视觉稿。
    • 

  • Figma AI 插件：自动生成变体。
    • 

  • v0 by Vercel：文本 → React 代码。
    • 



权衡：


    

  • 速度快但缺乏设计意图。
    • 

  • 设计师的判断仍然关键。
    • 

  • AI 提供起点，不替代设计师。
    • 



代码原型
Storybook：


    

  • 组件库 + 交互式演练场。
    • 

  • 代码可在生产环境复用。
    • 



React / Vue / Svelte：


    

  • 真实性能反馈。
    • 

  • 真实数据。
    • 



Flutter / SwiftUI：


    

  • 移动端原型。
    • 

  • 跨平台。
    • 



好处：


    

  • 测试真实性能。
    • 

  • 真实交互（手势、动画）。
    • 

  • 工程师可复用。
    • 



成本：


    

  • 比 Figma 慢。
    • 

  • 需要编码能力。
    • 



实战建议
1. 从低保真开始：


    

  • 先画草图概念。
    • 

  • 不要一开始就打磨细节。
    • 



2. 展示粗糙版本：


    

  • 利益相关者看到打磨过的视觉稿会觉得已完成。
    • 

  • 展示粗糙版本鼓励反馈。
    • 



3. 早且多地测试：


    

  • 不要等到完美再测试。
    • 

  • 每一轮都在改进。
    • 



4. 记录决策：


    

  • 不仅保留视觉稿，还要记录决策依据。
    • 

  • 帮助未来团队不重复犯错。
    • 



5. 尽早与工程师协作：


    

  • 避免隔墙抛砖。
    • 

  • 共同拥有用户体验。
    • 



小结
原型设计把想法转为可测试的产物——保真度阶梯（纸质草图 → 线框图 → 视觉稿 → 可交互 → 代码）每级适合不同问题。问题/时间/受众决定保真度。纸质原型极快且任何人可参与，"疯狂八格"和"设计工作室"是常用工作坊方法。Figma 是 2024 年主流工具（Web 协作 + 组件 + 自动布局 + 变体 + 开发者模式 + 插件），工作流为草图 → 线框 → 视觉稿 → 交互 → 测试 → 迭代。构建-度量-学习（精益创业）——最小可行原型 + 度量 + 学习 + 迭代。原型测试每轮 5 名用户发现 80% 问题（Nielsen），使用出声思维 + 任务场景。A/B 测试是生产级的定量验证。快速迭代优于缓慢完善——每周冲刺结构。设计评审高频率低风险，使用共同词汇。工具——Figma 主流、Sketch 下降、XD 停维、Framer 对代码友好、ProtoPie 传感器、Whimsical 快速线框、Penpot 开源。设计系统 = 组件 + 令牌 + 文档，保证一致性和交付效率。设计师与工程师协作现代方式用 Figma 开发者模式 + 设计系统 + Storybook + 尽早结对。反模式——跳过原型、过度打磨低保真、跳过测试、仅用团队测试、忽略反馈、只做一轮。现代 AI 原型工具（Galileo/Uizard/v0）加速但设计师判断仍关键。代码原型（Storybook、React、Flutter）提供真实性能和可复用性但速度较慢。建议——从低保真开始、展示粗糙版本、早且多地测试、记录决策、尽早与工程师协作。一个简单的检验：你能在一周内从纸质原型到用户测试吗？如果不能，原型设计的速度还需练习。原型设计是设计的"假设检验"——让想法在接触现实中演化，是设计质量的根源。
