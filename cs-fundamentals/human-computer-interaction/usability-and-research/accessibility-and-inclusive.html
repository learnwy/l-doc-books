无障碍与包容性设计

核心概念

无障碍设计让残障人士也能使用产品——全球有 13 亿残障人士（WHO 2024），包括视觉障碍（盲人、低视力、色盲）、听觉障碍、运动障碍（无法使用鼠标）、认知障碍（阅读障碍、自闭症、注意力缺陷）。WCAG 2.2（W3C 2023）是国际标准——4 项原则（可感知、可操作、可理解、健壮性）+ 3 个合规级别（A、AA、AAA）。包容性设计扩展了这一概念——"为个体解决问题，惠及大众"，无障碍功能让所有人受益（路缘斜坡效应）。本节给出 WCAG 实战、屏幕阅读器、键盘导航、色彩对比、语言清晰度、无障碍测试以及法律要求（ADA、EAA、Section 508）。

残障类型 影响 主要无障碍措施
视觉（盲） 无法看到 屏幕阅读器、替代文本
视觉（低视力） 看不清楚 大字体、高对比度
色盲 无法分辨某些颜色 不单靠颜色传达信息
听觉障碍 无法听到 字幕、文字稿
运动障碍 无法使用鼠标 键盘导航、大触控目标
认知障碍 处理困难 简单语言、行为一致

WCAG 2.2 四大原则（POUR）

可感知：

  • 信息和界面组件必须是用户可感知的。
  • 图片需替代文本。
  • 视频需字幕。
  • 颜色不能是唯一信号。
  • 充足的对比度。

可操作：

  • 功能必须是可使用的。
  • 键盘可访问。
  • 充足的操作时间。
  • 不触发癫痫（避免闪烁）。
  • 导航便捷。

可理解：

  • 信息和操作必须是可理解的。
  • 语言清晰。
  • 行为可预测。
  • 错误帮助。

健壮性：

  • 兼容辅助技术。
  • 有效的 HTML/ARIA。
  • 支持多种用户代理。

合规级别

A（最低）：

  • 基本合规。
  • 仍有很多用户无法使用。

AA（推荐）：

  • 大多数国家和公司的标准。
  • ADA、EAA 通常要求 AA。
  • 文本对比度 4.5:1。

AAA（增强）：

  • 高标准。
  • 文本对比度 7:1。
  • 适合特殊用户群体（医疗、政府）。
  • 实际产品中难以全面达到。

实战建议：

  • 至少达到 AA。
  • 选择性实施 AAA 中的部分条目。
屏幕阅读器
屏幕阅读器把界面内容读出来：


    

  • VoiceOver（macOS/iOS，内置免费）。
    • 

  • NVDA（Windows，免费）。
    • 

  • JAWS（Windows，付费）。
    • 

  • TalkBack（Android）。
    • 



测试方法：


    

  • 戴耳机使用屏幕阅读器。
    • 

  • 关闭显示器。
    • 

  • 完成任务。
    • 

  • 无法完成即为无障碍问题。
    • 



语义化 HTML：


    

  • 使用正确标签（<button> 而非 <div onclick>）。
    • 

  • 标题层级（h1 → h2 → h3）。
    • 

  • 列表 <ul> <ol>。
    • 

  • 表单 <label> 与输入关联。
    • 



ARIA（当 HTML 不够时）：


    

  • aria-label：可访问名称。
    • 

  • aria-describedby：描述。
    • 

  • aria-live：动态内容播报。
    • 

  • role：当 HTML 元素不合适时使用。
    • 



规则：语义化 HTML 优先于 ARIA。仅在必要时使用 ARIA。


色彩与对比度
对比度比率：


    

  • 文本与背景的对比。
    • 

  • AA：4.5:1（常规文本）、3:1（大文本）。
    • 

  • AAA：7:1。
    • 



工具：


    

  • WebAIM 对比度检查器。
    • 

  • Stark（Figma 插件）。
    • 

  • 开发者工具内置。
    • 



色盲：


    

  • 8% 男性、0.5% 女性受影响。
    • 

  • 红绿色盲最常见。
    • 

  • 颜色不能是唯一信号——要加图标、文字、图案。
    • 



示例：


    

  • "必填"字段加 *（不只用红色标签）。
    • 

  • 状态指示器加图标（✓ ✗）不只用颜色。
    • 

  • 错误提示加 ⚠️。
    • 



键盘导航
很多用户无法使用鼠标：


    

  • 运动障碍人群。
    • 

  • 高级用户偏好。
    • 

  • 屏幕阅读器用户。
    • 



要求：


    

  • 所有交互元素可通过键盘到达。
    • 

  • Tab 顺序合理。
    • 

  • 焦点指示器可见（不能只移除默认边框）。
    • 

  • Esc 关闭对话框。
    • 

  • Enter 激活操作。
    • 



测试方法：


    

  • 拔掉鼠标。
    • 

  • 仅用键盘完成所有任务。
    • 

  • 无法完成即为缺陷。
    • 



常见问题：


    

  • 对话框焦点陷阱（Tab 跳出对话框）。
    • 

  • 自定义组件不支持键盘（用 div 模拟按钮）。
    • 

  • 焦点指示器被移除（CSS outline: none 且无替代方案）。
    • 



触控目标
WCAG 2.2 SC 2.5.8：


    

  • 最小 24×24 CSS 像素（AA 新增于 2.2）。
    • 

  • Apple HIG 推荐 44×44。
    • 

  • Material Design 推荐 48×48。
    • 



间距：


    

  • 目标之间 8 像素间距。
    • 

  • 防止误触。
    • 



语言与认知
简明语言：


    

  • 不用行话术语。
    • 

  • 短句子。
    • 

  • 主动语态。
    • 

  • 常用词（用"使用"而非"利用"）。
    • 



阅读级别：


    

  • 八年级水平（美国平均）。
    • 

  • 工具：Hemingway、可读性评分。
    • 



一致性：


    

  • 同一事物用同一词语。
    • 

  • 行为可预测。
    • 



避免：


    

  • 习语（有文化局限）。
    • 

  • 讽刺表达。
    • 

  • 大段文本。
    • 



字幕与文字稿
视频：


    

  • 字幕（口语内容）。
    • 

  • 音频描述（视觉内容）。
    • 

  • 手语（高优先场景）。
    • 



音频：


    

  • 文字稿。
    • 



工具：


    

  • YouTube 自动字幕（需人工校对）。
    • 

  • Otter.ai。
    • 

  • Rev（专业服务）。
    • 



直播：


    

  • 实时字幕。
    • 

  • Apple FaceTime/Zoom 支持。
    • 



表单无障碍
标签：


    

  • 始终用 <label> 关联输入。
    • 

  • 不依赖占位文本（聚焦后消失）。
    • 



错误提示：


    

  • 在字段下方（靠近输入）。
    • 

  • 简明语言（"邮箱格式无效"而非"错误 422"）。
    • 

  • 建议修正方法。
    • 

  • 用 aria-live 播报。
    • 



分组：


    

  • 相关输入用 <fieldset> + <legend>。
    • 



必填：


    

  • "必填" + * + 视觉标识。
    • 

  • aria-required 属性。
    • 



对话框无障碍
焦点管理：


    

  • Tab 不离开对话框。
    • 

  • 第一个可聚焦元素自动获焦。
    • 

  • Esc 关闭。
    • 



播报：


    

  • aria-modal="true"。
    • 

  • aria-labelledby（标题）。
    • 

  • 屏幕阅读器播报"对话框已打开"。
    • 



背景：


    

  • 背景设 aria-hidden="true"。
    • 

  • 防止屏幕阅读器读到隐藏内容。
    • 



图片替代文本
装饰性图片：


    

  • alt=""（空字符串）。
    • 

  • 屏幕阅读器跳过。
    • 



信息性图片：


    

  • 描述内容和语境。
    • 

  • 例："图表显示第三季度销售增长 20%"。
    • 



功能性图片：


    

  • 描述功能。
    • 

  • 例："搜索按钮"。
    • 



复杂图片（图表）：


    

  • 详细描述。
    • 

  • 或 longdesc。
    • 

  • 或旁边提供文本替代。
    • 



现代工具
自动化测试：


    

  • axe DevTools（浏览器扩展）。
    • 

  • Lighthouse（Chrome 内置）。
    • 

  • WAVE（webaim.org）。
    • 

  • 可自动检测约 30-40% 的问题。
    • 



手动测试：


    

  • 屏幕阅读器（必须）。
    • 

  • 键盘导航。
    • 

  • 放大 200%。
    • 

  • 高对比度模式。
    • 



用户测试：


    

  • 招募残障用户。
    • 

  • 使用他们自己的辅助技术。
    • 

  • 不要模拟（不具代表性）。
    • 



ARIA 模式
WAI-ARIA 创作实践：


    

  • 标准模式（手风琴、标签页、轮播、对话框）。
    • 

  • 提供实现指导。
    • 



使用现有模式：


    

  • 不重复发明。
    • 

  • 组件库（Radix UI、Headless UI、ARIA Patterns）。
    • 



自定义组件：


    

  • 难以做到无障碍。
    • 

  • 尽可能使用原生 HTML。
    • 



法律框架
ADA（美国）：


    

  • 1990 年《美国残疾人法案》。
    • 

  • 适用于公共场所（法院判定网站也算）。
    • 

  • 诉讼数量在增长。
    • 



EAA（欧盟）：


    

  • 《欧洲无障碍法案》2025 年执行。
    • 

  • 面向消费者的产品必须无障碍。
    • 



Section 508：


    

  • 美国联邦政府要求。
    • 

  • 供应商必须提供无障碍产品。
    • 



ACT（加拿大）：


    

  • 《加拿大无障碍法》。
    • 



各国均有类似法律。


商业影响：


    

  • 诉讼成本 5 万至 100万+ 美元。
    • 

  • 声誉损害。
    • 

  • 流失客户。
    • 



包容性设计
微软包容性设计工具包：


    

  • "为个体解决问题，惠及大众"。
    • 

  • 永久障碍（盲人）→ 情境障碍（黑暗房间）→ 暂时障碍（瞳孔扩张）。
    • 

  • 为永久障碍设计的方案惠及所有人。
    • 



路缘斜坡效应：


    

  • 人行道的路缘斜坡为轮椅设计。
    • 

  • 也惠及婴儿车、自行车、行李箱。
    • 

  • 数字产品类似：字幕惠及聋人 + 外语环境 + 嘈杂环境。
    • 



示例：


    

  • 语音控制原本为残障人士设计 → 现在人人使用（Siri/Alexa）。
    • 

  • 短信原本为聋人设计 → 现在人人使用。
    • 

  • 预测输入原本为运动障碍设计 → 现在人人使用。
    • 



无障碍融入流程
1. 早期就纳入：


    

  • 设计阶段就考虑无障碍。
    • 

  • 不做事后补救。
    • 



2. 设计系统：


    

  • 无障碍内置于组件中。
    • 

  • 复用带来一致性。
    • 



3. 代码检查器：


    

  • ESLint 无障碍插件。
    • 

  • 开发过程中自动检查。
    • 



4. 持续集成测试：


    

  • 在 CI 中运行 Lighthouse/axe。
    • 

  • 出现退步则阻止合并。
    • 



5. 与残障用户测试：


    

  • 招募残障用户。
    • 

  • 获取真实世界反馈。
    • 



6. 定期审计：


    

  • 每季度外部无障碍审计。
    • 

  • 捕获偏移问题。
    • 



反模式
1. "以后再加"：


    

  • 事后补救难度大得多。
    • 



2. 仅用自动化测试：


    

  • 自动化只能发现 30-40%。
    • 

  • 手动测试 + 用户测试覆盖其余。
    • 



3. 移除焦点指示器：


    

  • outline: none 且无替代方案。
    • 

  • 键盘用户失去位置追踪。
    • 



4. 仅用颜色传达信号：


    

  • 红色 = 错误不够，加图标 + 文字。
    • 



5. 缺少替代文本：


    

  • 装饰性图片用 alt=""，信息性图片用描述。
    • 



6. 伪造按钮：


    

  • <div onclick> 模拟按钮。
    • 

  • 键盘不可访问。
    • 

  • 用 <button>。
    • 



投资回报
成本：


    

  • 从一开始构建无障碍：约额外 10% 成本。
    • 

  • 事后补救：额外 50-200%。
    • 



收益：


    

  • 13 亿残障人群市场。
    • 

  • SEO 收益（语义化 HTML）。
    • 

  • 避免诉讼。
    • 

  • 对所有人更好的体验。
    • 



投资回报通常为正——尤其考虑法律风险。


小结
无障碍设计让 13 亿残障人士能使用产品——视觉/听觉/运动/认知障碍。WCAG 2.2 四原则 POUR（可感知/可操作/可理解/健壮性）+ 三个合规级别（A/AA 推荐/AAA 增强）。屏幕阅读器（VoiceOver/NVDA/JAWS/TalkBack）测试必要。语义化 HTML 优先于 ARIA——正确标签、标题层级、<label>，仅在必要时使用 ARIA（aria-label/aria-live/role）。色彩对比 AA 4.5:1（常规）/3:1（大文本），AAA 7:1，工具 WebAIM/Stark。色盲影响 8% 男性，颜色不能是唯一信号——加图标 + 文字。键盘导航——全可达 + Tab 顺序 + 焦点可见 + Esc + Enter，测试方法拔掉鼠标。触控目标 WCAG 2.2 24×24px/Apple 44/Material 48 + 8px 间距。简明语言八年级阅读水平 + 术语一致。视频/音频需字幕 + 文字稿。表单——<label> + 字段下方简明错误 + fieldset 分组 + 必填视觉标识 + aria。对话框——焦点陷阱 + aria-modal + 背景 aria-hidden。图片替代文本——装饰性""、信息性描述、功能性功能描述、复杂图 longdesc。工具——自动化 axe/Lighthouse/WAVE 发现 30-40%、手动屏幕阅读器/键盘/放大/高对比度、招募残障用户。ARIA 创作实践提供标准模式。法律——ADA 美国/EAA 欧盟/Section 508 联邦/ACT 加拿大，诉讼成本 5 万至 100万+。包容性设计"为个体解决惠及大众"，路缘斜坡效应（字幕惠及聋人 + 嘈杂环境 + 外语环境）。流程——早期纳入 + 设计系统 + 检查器 + CI 测试 + 用户测试 + 定期审计。反模式——以后再加、仅自动测试、移除焦点、仅用颜色、缺少替代文本、伪造按钮。投资回报：从一开始 10% vs 事后 50-200%，13 亿市场 + SEO + 避免诉讼。一个简单的检验：你能仅用键盘完成你产品的所有任务吗？如果不能，无障碍还需紧急修复。无障碍不是可选项——是法律要求 + 道德义务 + 商业收益 + 对所有人更好的设计。
