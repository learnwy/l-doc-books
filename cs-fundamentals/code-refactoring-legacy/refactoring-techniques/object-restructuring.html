对象与继承结构重构

对象结构重构的核心目标

面向对象设计的质量取决于职责分配是否合理——每个类应该拥有与其身份相匹配的数据和行为，类之间的协作应该通过清晰定义的接口进行。当职责错位时，代码表现出耦合度高、内聚性低的特征：修改一个功能需要触碰多个类，或者一个类中不相关的方法混杂在一起。

对象结构重构的目标是重新分配职责，使每个类更加内聚、类之间的耦合最小化。与函数级重构不同，对象级重构涉及更大范围的结构变动——它改变的不仅是代码的组织方式，还包括对象之间的协作关系和继承体系的层次结构。

Move Function（搬移函数）

动机

Move Function 将一个函数从当前所在的上下文（类、模块、文件）移动到另一个上下文。移动的判断标准是函数的"亲密度"——它更多地使用哪个类的数据和方法？如果一个函数频繁访问另一个对象的数据（Feature Envy），它很可能应该属于那个对象。

判断标准

Martin Fowler 提出的判断指引：

指标 移动的信号
数据引用 函数引用目标类数据多于源类数据
被调用模式 目标类的多个方法都调用此函数
变更频率 此函数总是随目标类一起修改
概念归属 函数的业务含义更接近目标类的职责

操作步骤

1. 检查函数引用的所有数据和方法
2. 确认函数在源上下文中没有多态重写
3. 将函数复制到目标上下文
4. 调整函数以适应新环境（修改引用路径）
5. 在源上下文中创建委托调用
6. 逐步将所有调用方改为直接调用目标
7. 删除源上下文中的委托
8. 运行测试

嵌套函数的搬移考虑

嵌套函数（闭包）的搬移比顶层方法更复杂——它可能捕获了外层作用域的变量。搬移时需要：

  • 将捕获的变量转为显式参数
  • 或者将嵌套函数和其依赖的上下文一起搬移
  • 或者先 Extract Function 使其成为独立函数，再搬移

Move Field（搬移字段）

动机

Move Field 将一个字段从一个类移到另一个类。字段归属不当是设计退化的早期信号——当你发现操作某个字段的逻辑大部分在另一个类中时，字段应该跟随逻辑一起移动。

良好的数据结构设计使行为代码更简洁；糟糕的数据结构则迫使行为代码进行大量的数据导航和适配。因此，Move Field 虽然看似简单，但对代码质量的影响往往超过更复杂的重构。

Pull Up Method（方法上移）
动机
当多个子类包含相同或高度相似的方法时，Pull Up Method 将公共方法移到超类中，消除重复。这是 DRY 原则在继承体系中的直接应用。


前提条件
方法上移的前提是：各子类中的方法做的是"同一件事"。如果它们恰好代码相似但语义不同（只是巧合的重复），不应上移——未来它们可能会分化。


处理差异
子类方法通常不完全相同——它们可能引用子类特有的字段或方法。处理策略：


1. 如果方法引用子类特有字段 → 先 Pull Up Field
2. 如果方法中有少量子类特有逻辑 → 先 Extract Function 分离差异部分
3. 如果差异部分是"模板方法"中的步骤 → 上移模板方法，将差异定义为抽象方法
4. 如果各子类方法签名不同但行为相同 → 先 Change Function Declaration 统一签名
Template Method 模式
Pull Up Method 与 Template Method 设计模式的结合特别强大：将算法的骨架上移到超类，将可变步骤定义为抽象方法让子类实现。


// 超类
function calculateBill() {
  const base = baseCharge();        // 抽象方法，子类实现
  const tax = taxAmount(base);      // 通用逻辑
  const discount = discountFor();   // 抽象方法，子类实现
  return base + tax - discount;
}
Push Down Method（方法下移）
动机
与 Pull Up 相反——当超类中的方法只与特定子类相关时，Push Down Method 将其移到那些子类中。一个只被部分子类使用的方法放在超类中，会误导读者认为它是所有子类的共同行为。


适用判断

Pull Up Field / Push Down Field（字段上移/下移）
字段的上移和下移遵循与方法相同的逻辑：


    

  • Pull Up Field：当多个子类有相同字段时，将其上移消除重复
    • 

  • Push Down Field：当超类字段只被部分子类使用时，将其下移到需要的子类
    • 



字段上移还有一个额外的好处：它使得操作该字段的方法有机会也上移到超类，进一步减少重复。


Replace Inheritance with Delegation（以委托取代继承）
动机
继承是面向对象中最强的耦合关系——子类依赖超类的全部实现细节。当子类只需要超类的部分行为时，继承就成为了负担。Refused Bequest（被拒绝的遗产）坏味道正是这种过度继承的信号。


Replace Inheritance with Delegation 将 is-a 关系转变为 has-a 关系：子类不再继承超类，而是持有一个委托对象的引用，只转发需要的方法调用。


何时替代
操作步骤
1. 在子类中创建一个指向超类实例的字段（委托字段）
2. 对于需要保留的超类方法，在子类中创建转发方法
3. 逐一删除继承的方法，改为通过委托字段调用
4. 移除继承关系（extends/implements）
5. 运行测试
6. 考虑是否需要为委托字段的类型定义接口

经典的设计原则："优先使用组合而非继承"（Favor Composition over Inheritance）正是基于此权衡。在实践中，只有当 is-a 关系明确且稳定时才使用继承，其他情况优先选择委托。


Replace Delegation with Inheritance（以继承取代委托）
这是上述操作的逆向。当一个类的大部分方法都只是转发给委托对象，且转发关系非常稳定时，继承可以消除大量的样板转发代码。


适用条件（所有条件必须同时满足）：


    

  • 委托类的全部或绝大部分接口都被使用
    • 

  • 委托关系在类的生命周期内不会改变
    • 

  • 语义上构成 is-a 关系
    • 

  • 没有其他竞争的继承关系（Java 等单继承语言的限制）
    • 



Replace Superclass with Delegate（以委托取代超类）
特殊场景
当继承层次中超类的职责与子类的职责不匹配时，与其调整继承关系，不如将超类"降级"为委托对象。这常出现在"滥用继承获取代码复用"的场景中。


经典案例：Stack extends Vector（Java 标准库的历史错误）——Stack 不是一种 Vector，它只是内部使用了 Vector 的数据结构。正确做法是 Stack 持有一个 List 作为委托。

小结
对象与继承结构重构是重构技巧中最具设计深度的类别。Move Function/Field 调整职责归属，Pull Up/Push Down 优化继承层次分配，Replace Inheritance with Delegation 在继承和组合之间做出更优选择。这些手法的应用需要深入理解面向对象设计原则——SOLID、组合优于继承、接口隔离等。在 2026 年的实践中，函数式编程思想（不可变数据、纯函数、类型组合）正在影响对象结构重构的方向，越来越多的场景中组合和委托被优先于继承使用。理解这些趋势有助于在重构时做出面向未来的设计选择。
