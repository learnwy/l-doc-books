提取与内联：重构的基础操作

提取与内联的对偶关系

提取（Extract）和内联（Inline）是重构手法中最基础、使用频率最高的一对互逆操作。提取将代码片段从原始上下文中抽离为独立的命名单元（函数、变量、类），内联则将一个命名单元的内容直接展开到调用处。两者如同呼与吸——提取增加间接层以改善可读性和复用性，内联消除多余间接层以保持代码的直接性。

理解这对操作的关键在于：没有绝对"正确"的方向。过度提取导致代码碎片化（需要在多个小函数间跳转才能理解逻辑），过度内联导致函数膨胀。判断何时提取、何时内联，是重构实践中最需要经验积累的直觉。

Martin Fowler 的指导原则是：**当你需要注释来解释一段代码在做什么时，就该把那段代码提取为一个命名良好的函数。**函数名本身就是最好的注释。

Extract Function（提取函数）

动机与时机

Extract Function 是所有重构手法中最重要的一个。它的核心价值在于：将"做什么"（意图）与"怎么做"（实现）分离。当你看到一个函数中有一段代码需要看几秒才能理解其目的时，就应该将其提取为独立函数。

即使被提取的代码只有一行，只要这一行的意图不是一眼可知的，提取都有价值。函数长度不是提取的判断标准——语义间距（意图与实现之间的认知距离）才是。

操作步骤

1. 创建新函数，用意图命名（函数名描述"做什么"而非"怎么做"）
2. 将目标代码从源函数复制到新函数
3. 检查被提取代码引用的局部变量：
   - 只读引用 → 作为参数传入
   - 被修改的变量 → 作为返回值返回
   - 既读又写的多个变量 → 考虑先拆分变量用途
4. 编译检查
5. 将源函数中的原代码替换为新函数的调用
6. 运行测试

处理局部变量的策略

局部变量是 Extract Function 中最常见的复杂因素。按照处理难度递增排列：

变量类型 处理方式 复杂度
不被使用的变量 不传递 低
只读取的变量 作为参数传入 低
被赋值一次的变量 作为返回值 中
被赋值多次的变量 先 Split Variable 再提取 高
累加器类型的变量 通过参数传入初始值，返回最终值 高

当变量处理变得复杂时，通常是一个信号——可能需要先执行 Replace Temp with Query 或 Split Variable，消除复杂的临时变量后再进行提取。

命名的艺术

好的函数名是 Extract Function 成功的关键。命名原则：

  • 以动词开头描述行为：calculateTotal、validateEmail、formatAddress
  • 描述"做什么"而非"怎么做"：highlightOverdueItems 优于 setColorToRed
  • 不包含实现细节：getAge 优于 subtractBirthYearFromCurrentYear
  • 层级一致：被提取的函数应与调用方处于相同的抽象层级

Extract Variable（提取变量）

动机与时机

当一个表达式过于复杂以至于难以理解其含义时，Extract Variable 通过引入一个命名良好的局部变量来解释表达式的意图。

// 提取前：意图不明确
if (platform.toUpperCase().includes('MAC') && browser.toUpperCase().includes('IE') && wasInitialized() && resize > 0) {
  // ...
}

// 提取后：意图清晰
const isMacOS = platform.toUpperCase().includes('MAC');
const isIE = browser.toUpperCase().includes('IE');
const wasResized = wasInitialized() && resize > 0;
if (isMacOS && isIE && wasResized) {
  // ...
}

Extract Variable 的价值在于：为表达式的计算结果赋予语义化名称。如果引入的变量名与表达式本身一样晦涩，则提取没有意义。

何时选择 Extract Variable vs Extract Function

两者都能为复杂表达式赋予名称，选择依据是：

  • 表达式的含义仅在当前函数上下文中有意义 → Extract Variable
  • 表达式的计算逻辑可能被其他地方复用 → Extract Function
  • 表达式依赖的数据属于另一个对象 → Extract Function + Move Function

Extract Class（提取类）

动机与时机

当一个类承担了两个或更多不相关的职责时，Extract Class 将其中一组相关的字段和方法抽离为新类。判断标准：如果你能给类的一组字段和方法起一个有意义的名字，那它就该成为独立的类。

典型信号：

  • 类中的方法可以分为两个不相互调用的组
  • 类的某些字段只在部分方法中使用
  • 修改一组功能时，另一组功能完全不需要了解

操作步骤

1. 决定如何分离职责——确定哪些字段和方法属于新类
2. 创建新类，赋予职责描述性名称
3. 在原类中创建新类的实例（通常作为字段）
4. 逐一将字段移动到新类（Move Field）
5. 逐一将方法移动到新类（Move Function）
6. 审查接口：减少双向依赖，清理不需要公开的方法
7. 决定是否需要公开新类（或保持为原类的内部委托）
8. 运行测试

Inline Function（内联函数）

动机与时机

内联函数与 Extract Function 互逆。当函数体与函数名同样清晰，或者间接层反而增加了理解负担时，应该将函数体内联回调用处。

典型场景：

  • 函数体只有一行且不比函数名更难理解
  • 一组函数的内部结构有问题，需要先内联再重新提取
  • 过度委托——函数只是简单地调用另一个函数

与 Extract Function 的平衡

内联和提取之间的平衡取决于抽象是否带来了理解上的收益：

Inline Variable（内联变量）
当变量名并不比它所指向的表达式更有表达力时，消除该变量。这通常发生在 Extract Variable 过度使用后，或者变量妨碍了其他重构操作时。


// 内联前：变量没有增加可读性
const basePrice = anOrder.basePrice;
return basePrice > 1000;

// 内联后：直接使用原表达式
return anOrder.basePrice > 1000;
Inline Class（内联类）
与 Extract Class 互逆——当一个类的职责萎缩到不足以支撑其作为独立类的存在时，将其内容合并回另一个类。


适用场景：


    

  • 重构过程中，某个类的大部分职责已经移出，剩余内容不成体系
    • 

  • 两个类的职责经过演进已经密不可分，合并比委托更清晰
    • 

  • 准备重新分配职责前的中间步骤——先内联到一处，再按新的维度重新提取

使用 IDE 的自动化重构比手动编辑更安全——IDE 会分析作用域、依赖关系和副作用，自动处理变量传递和返回值。但即使使用 IDE 辅助，每次重构后仍应运行测试确认。


小结
提取与内联是重构工具箱中的基础工具，如同工匠手中的锤子和凿子。掌握它们的关键不在于操作步骤（IDE 可以自动化），而在于判断力——何时提取能增加清晰度、何时内联能减少噪音。这种判断力只能通过在真实代码中反复练习来培养。初学者常见的错误是过度提取（产生过多只有一两行的小函数），而经验丰富的开发者知道在可读性和间接层之间找到平衡点。
