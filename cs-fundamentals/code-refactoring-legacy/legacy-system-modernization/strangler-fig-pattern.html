Strangler Fig 模式：渐进式系统替换

模式起源与核心思想

Strangler Fig 模式由 Martin Fowler 于 2004 年提出，灵感来源于澳大利亚热带雨林中的绞杀榕（Strangler Fig）。绞杀榕的种子落在宿主树的枝丫上，向下生长根系逐步包裹宿主树干，最终完全替代宿主成为独立的大树——整个过程是渐进的、持续的，不存在突然的"切换时刻"。

这一自然过程完美类比了遗留系统的渐进式替换策略：新系统在旧系统旁边逐步生长，一个功能一个功能地接管请求，直到旧系统被完全替代后可以安全拆除。

与"推倒重写"（Big Bang Rewrite）相比，Strangler Fig 模式的核心优势：

维度 推倒重写 Strangler Fig
交付价值时间 项目结束时才交付 每次迁移一个功能即交付
风险暴露 全量切换时集中爆发 渐进暴露，逐步验证
回滚能力 几乎不可能回滚 每步都可回滚
团队压力 长时间无可见产出 持续的小胜利
学习机会 事后总结 过程中持续学习调整
业务连续性 切换窗口风险 零停机

架构模式详解

核心组件

Strangler Fig 模式的实现依赖以下核心组件：

路由层（Router/Facade）：所有请求的入口点，负责根据规则将请求分发到新系统或旧系统。路由层是整个模式的关键——它将"使用哪个系统"的决策从客户端中解耦出来。


新系统（New）：逐步构建的替代实现，每次只实现一个功能模块。


遗留系统（Legacy）：继续服务尚未迁移的功能，在迁移过程中保持稳定运行。


数据同步层：在新旧系统并行期间保持数据一致性的机制。

三种变体
Asset Capture（资产捕获）：新系统逐步"捕获"旧系统的功能资产。从外围功能开始，逐步向核心推进。


Event Interception（事件截获）：新系统监听旧系统发出的事件，先建立与旧系统的数据同步，然后逐步接管事件的处理责任。


Feature Toggle Migration（特性开关迁移）：通过特性开关控制每个功能使用新实现还是旧实现，支持按用户/百分比/地域的渐进切换。


实施步骤
阶段一：建立路由层
    

  1. 在客户端和遗留系统之间插入路由层
    2. 

  2. 初始配置：所有请求透明转发给遗留系统
    3. 

  3. 验证：路由层不改变任何行为（等同于透明代理）
    4. 

  4. 建立监控：请求量、延迟、错误率的基线数据
    5. 



这一步的唯一目标是建立控制点。路由层就位后，后续的每次迁移都变为路由配置的修改，而非客户端的变更。


阶段二：迁移首个功能
选择第一个迁移的功能遵循以下原则：


    

  • 低风险：选择非核心功能，即使出问题影响可控
    • 

  • 高独立性：与其他功能的数据依赖最少
    • 

  • 高可验证性：行为正确性容易判断
    • 

  • 有代表性：能验证迁移模式的可行性
    • 



典型的首选候选：健康检查端点、静态页面、只读查询接口、辅助功能（如导出、通知）。


阶段三：渐进迁移
每个功能的迁移遵循统一的步骤：


    

  1. 实现：在新系统中实现该功能
    2. 

  2. 验证：通过测试确认行为与旧系统一致
    3. 

  3. 灰度：将少量流量（如 5%）切换到新系统
    4. 

  4. 监控：对比新旧系统的响应结果和性能指标
    5. 

  5. 扩大：逐步增加新系统的流量比例
    6. 

  6. 切换：100% 流量切到新系统
    7. 

  7. 清理：移除旧系统中该功能的代码
    8. 



阶段四：遗留系统退役
当所有功能迁移完成后：


    

  1. 确认遗留系统的流量降为零
    2. 

  2. 保持遗留系统"待命"运行一段观察期（建议 2-4 周）
    3. 

  3. 确认无回退需求后，关闭遗留系统
    4. 

  4. 拆除路由层中的旧系统路由规则
    5. 

  5. 归档遗留系统的代码和文档
    6. 



路由切换策略
金丝雀发布（Canary Release）
按百分比逐步切换流量，配合实时监控：


Day 1:  1% → 新系统（验证基本功能）
Day 3:  10% → 新系统（验证性能和稳定性）
Day 7:  50% → 新系统（验证负载）
Day 14: 100% → 新系统（全量切换）
用户分群切换
按用户特征分群，从低风险群体开始：


    

  • 内部员工 → Beta 用户 → 新注册用户 → 全量老用户
    • 

  • 低活跃度用户 → 中活跃度 → 高活跃度（VIP 用户最后切换）
    • 



地域切换
多地域部署的系统，按地域逐步切换：


    

  • 流量最小的地域 → 次要地域 → 主要地域
    • 



回滚策略
Strangler Fig 模式的核心优势之一是强大的回滚能力。每一步迁移都必须设计清晰的回滚方案：


即时回滚
路由层将流量切回旧系统——最快速的回滚方式（秒级）。前提是旧系统在迁移期间仍保持运行状态。


数据回滚
如果新系统已经产生了新数据，回滚需要考虑数据一致性：


    

  • 只读功能：无数据状态变更，路由切换即完成回滚
    • 

  • 写入功能：需要将新系统中产生的数据同步回旧系统
    • 

  • 双写期间：新旧系统同时写入，回滚无需数据同步
    •

常见挑战与应对
数据一致性
新旧系统并行期间，同一份业务数据可能存在于两个系统中。解决方案：


    

  • 单一数据源：新旧系统共享数据库（简单但限制了架构演进）
    • 

  • 事件同步：通过事件流保持数据最终一致
    • 

  • 双写：写入操作同时发给新旧系统（复杂但保证了两侧一致性）
    • 



会话和状态管理
用户请求可能在新旧系统间切换，需要保证状态不丢失：


    

  • 使用外部化的会话存储（如 Redis）
    • 

  • 确保会话数据格式在新旧系统间兼容
    • 

  • 切换时注意 Cookie/Token 的域名配置
    • 



迁移顺序规划
功能之间存在依赖关系，迁移顺序不是随意的：


    

  • 先迁移下游服务，再迁移上游调用者
    • 

  • 先迁移读操作，再迁移写操作
    • 

  • 先迁移无状态功能，再迁移有状态功能
    • 



小结
Strangler Fig 模式将"大爆炸式替换"分解为一系列可控的小步骤，每步都可独立验证、独立回滚。它的实施成本（路由层建设、双系统维护）是明确的、可预算的；而它避免的风险（全量切换失败、长期无法交付）往往是项目致命的。在 2026 年的实践中，Service Mesh（如 Istio）、API Gateway（如 Kong、AWS API Gateway）和特性管理平台（如 LaunchDarkly）为 Strangler Fig 模式提供了成熟的基础设施支撑，使其实施门槛大幅降低。对于任何超过中等规模的遗留系统改造，Strangler Fig 应该是默认的首选策略。
