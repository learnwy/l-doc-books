增量迁移实战：数据库、API 与微服务拆分

增量迁移的工程原则

增量迁移是将 Strangler Fig 模式的宏观策略落实到具体技术层面的工程实践。它涉及三个最困难的技术领域：数据库迁移、API 层替换和单体到微服务的拆分。每个领域都有其特定的复杂性和成熟的解决方案。

增量迁移的核心工程原则：

  1. 每一步都可回退：任何迁移步骤都不应造成不可逆转的状态变更
  2. 新旧并行期：新旧系统在一段时间内同时运行，通过对比验证正确性
  3. 数据先行：先解决数据层面的迁移和同步，再切换业务逻辑
  4. 渐进验证：从小规模验证开始，确认无误后逐步扩大范围
  5. 可观测性贯穿：迁移全程必须有充分的监控和告警

数据库迁移策略

数据库迁移是遗留系统改造中风险最高的环节——数据丢失或损坏是不可接受的，而数据库的结构变更往往影响系统的每一个角落。

Expand-Contract 模式

也称为"Parallel Change"模式，是数据库 schema 迁移的黄金标准方法：

Expand：添加新的数据结构而不删除旧的。此阶段完成后，新旧结构同时存在，旧代码继续正常工作。


Migrate：将数据从旧结构迁移到新结构。可以通过批处理脚本、触发器或双写机制实现。同时将应用代码逐步切换到使用新结构。


Contract：确认所有代码都已使用新结构后，安全删除旧结构。

Backend for Frontend (BFF) 适配层
当遗留系统的 API 契约与现代客户端需求严重不匹配时，BFF 层作为适配器：


BFF 的价值在于：客户端只与 BFF 通信，不需要知道后端是新系统还是旧系统。当某个功能从旧系统迁移到新系统时，只需修改 BFF 的内部路由，客户端完全无感。

拆分过程中的数据分离
微服务的核心原则之一是"每个服务拥有自己的数据"。但在从单体拆分时，数据通常共享在一个数据库中。数据分离的渐进步骤：


1. 代码分离（保持共享数据库）
   - 将代码拆分为独立部署单元
   - 但仍然访问同一个数据库

2. Schema 逻辑隔离
   - 在代码中约束每个服务只访问"自己的"表
   - 通过 API 而非直接查表获取其他服务的数据

3. 物理数据库分离
   - 将每个服务的表迁移到独立数据库
   - 建立服务间数据同步机制

4. 数据所有权清晰化
   - 每份数据有且只有一个所有者服务
   - 其他服务通过 API 或事件获取数据视图

影子流量测试（Shadow Traffic）
在正式切换前，将生产流量同时发送到新系统（但不使用其响应），对比新旧系统的行为差异：


影子流量测试的优势：使用真实生产数据和流量模式验证新系统，比任何模拟测试都更接近真实情况。但需注意副作用控制——影子流量不应触发实际的外部操作（如发送邮件、扣款）。


小结
增量迁移是将遗留系统现代化从战略愿景落实为工程实践的关键环节。数据库迁移通过 Expand-Contract 模式实现零停机 schema 演进，API 层通过版本并行和契约测试保证兼容性，微服务拆分通过渐进式数据分离避免"分布式单体"陷阱。贯穿始终的原则是：每一步都可回退、每一步都有验证、每一步都在可控范围内。2026 年的工具生态（CDC 工具、Service Mesh、API Gateway、可观测性平台）已经为增量迁移提供了成熟的基础设施，但正确的迁移顺序规划和严格的验证纪律仍然是人做出的关键决策。
