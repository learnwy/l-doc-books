内存泄漏检测

核心概念

内存泄漏（Memory Leak）是指程序分配的内存在不再需要后未被正确释放，导致可用内存持续减少。内存泄漏是长期运行服务（Web 服务器、数据库、后台任务）的头号稳定性威胁。与崩溃不同，内存泄漏是渐进式的——可能在几天甚至几周后才触发 OOM Kill，而且问题发生时往往已经远离了泄漏的根因。检测和预防内存泄漏需要专门的工具和系统化的方法。

C/C++ 泄漏检测工具
C/C++ 没有垃圾回收器，内存管理完全由程序员负责。这使得泄漏检测工具成为必需品。


Valgrind (Memcheck) 是最经典的内存错误检测工具。它通过二进制插桩跟踪每一次分配和释放，程序退出时报告所有未释放的内存块：


valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./myapp

# 输出示例:
# ==12345== 48 bytes in 3 blocks are definitely lost in loss record 1 of 5
# ==12345==    at 0x4C2FB0F: malloc (in /usr/lib/valgrind/vgpreload_memcheck.so)
# ==12345==    by 0x401234: create_node (tree.c:42)
# ==12345==    by 0x401456: insert (tree.c:78)
# ==12345==    by 0x401678: main (main.c:15)
Valgrind 的分类系统：


    

  • definitely lost: 没有任何指针指向该内存——确定泄漏
    • 

  • indirectly lost: 通过已泄漏的指针才能到达——间接泄漏
    • 

  • possibly lost: 有指向内存块内部（非起始位置）的指针——可能泄漏
    • 

  • still reachable: 程序退出时仍有指针指向——通常不是问题
    • 



AddressSanitizer (ASan) 是编译器内建的内存检测工具（GCC/Clang），比 Valgrind 快 2-5 倍，但需要重新编译：


# 编译时启用
gcc -fsanitize=address -fno-omit-frame-pointer -g -O1 myapp.c -o myapp
# 启用泄漏检测
ASAN_OPTIONS=detect_leaks=1 ./myapp
LeakSanitizer (LSan) 可以独立使用，也可以与 ASan 结合。它使用更轻量的方式检测泄漏：


gcc -fsanitize=leak -g myapp.c -o myapp
./myapp

GC 语言中的内存泄漏
即使在有垃圾回收器的语言（Java、Go、JavaScript、Python）中，内存泄漏仍然存在——只是形式不同。GC 语言中的泄漏通常是逻辑泄漏：对象仍然被引用但永远不会再被使用。


Java 中常见的泄漏模式和检测方法：


// 泄漏模式 1: 集合类只增不减
class EventBus {
    private final List<EventListener> listeners = new ArrayList<>();

    public void register(EventListener listener) {
        listeners.add(listener);
    }
    // 缺少 unregister 方法 → 监听器永远不会被 GC
}

// 泄漏模式 2: 静态集合持有对象引用
class Cache {
    private static final Map<String, byte[]> cache = new HashMap<>();

    public static void put(String key, byte[] data) {
        cache.put(key, data);  // 无上限、无淘汰 → 持续增长
    }
}

// 泄漏模式 3: ThreadLocal 未清理
class RequestContext {
    private static final ThreadLocal<Map<String, Object>> context =
        ThreadLocal.withInitial(HashMap::new);

    public static void set(String key, Object value) {
        context.get().put(key, value);
    }
    // 线程池场景下，线程被复用，ThreadLocal 数据不断积累
}
# Java Heap Dump 分析
jmap -dump:format=b,file=heap.hprof $(pgrep java)
# 使用 Eclipse MAT 或 VisualVM 分析 heap dump
# 关注 "Dominator Tree" 和 "Leak Suspects" 报告
Go 中使用 pprof 分析内存：


import _ "net/http/pprof"

// 采集堆内存 profile
// curl http://localhost:6060/debug/pprof/heap > heap.pb.gz
// go tool pprof -http=:8080 heap.pb.gz

// 对比两个时间点的 heap profile 找增长点
// go tool pprof -base heap1.pb.gz heap2.pb.gz
JavaScript/Node.js 中常见泄漏源是闭包、事件监听器和全局变量：


const EventEmitter = require('events');

class Connection extends EventEmitter {
  constructor() {
    super();
    this.buffer = Buffer.alloc(1024 * 1024);
  }
}

function createConnections() {
  const connections = [];
  for (let i = 0; i < 1000; i++) {
    const conn = new Connection();
    conn.on('data', (data) => {
      console.log(conn.buffer.length); // 闭包持有 conn 引用
    });
    connections.push(conn);
  }
  // connections 数组被清空，但事件监听器的闭包仍持有引用
}
生产环境泄漏监控
在生产环境中，不能运行 Valgrind 或 ASan（开销太大）。需要依赖轻量级监控来发现泄漏。


核心监控指标：


    

  • RSS（Resident Set Size）：进程实际占用的物理内存
    • 

  • VSZ（Virtual Size）：进程的虚拟内存总量
    • 

  • 堆内存增量：一段时间内堆内存的净增长
    • 

  • GC 压力：GC 频率、GC 暂停时间、GC 后存活对象大小
    • 



# 实时监控进程内存（Linux）
watch -n 1 'ps -p $(pgrep myapp) -o pid,rss,vsz,pcpu --no-headers'

# 使用 /proc 获取详细内存信息
cat /proc/$(pgrep myapp)/status | grep -E "VmRSS|VmSize|VmSwap"

# 使用 smem 获取 PSS（比 RSS 更准确地反映进程实际消耗）
smem -p -s pss | head -20
自动化泄漏检测的策略：


# Prometheus 告警规则示例
groups:
  - name: memory_leak_detection
    rules:
      - alert: PossibleMemoryLeak
        expr: |
          deriv(process_resident_memory_bytes[1h]) > 10 * 1024 * 1024
        for: 2h
        labels:
          severity: warning
        annotations:
          summary: '进程内存持续增长超过 10MB/小时，持续 2 小时'

      - alert: HighMemoryUsage
        expr: |
          process_resident_memory_bytes / node_memory_MemTotal_bytes > 0.8
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: '进程内存使用超过物理内存 80%'
泄漏排查的工作流程：发现 RSS 持续增长 → 确认不是正常增长（如缓存预热）→ 获取两个时间点的 heap dump → 对比分析新增的大对象 → 追踪引用链找到根因 → 修复并验证。


小结
    

  • 内存泄漏是长期运行服务的首要稳定性威胁，渐进式退化使其难以及时发现
    • 

  • C/C++ 使用 Valgrind 或 AddressSanitizer 检测泄漏，两者互补（Valgrind 精确但慢，ASan 快但需重编译）
    • 

  • GC 语言的泄漏本质是逻辑泄漏——对象可达但不再使用，常见于集合、监听器和闭包
    • 

  • 生产环境通过 RSS 趋势监控 + 告警规则主动发现泄漏，通过 heap dump 对比定位根因
    • 

  • 预防泄漏比检测泄漏更重要——使用 RAII/defer 模式、设置缓存上限、及时移除事件监听器
    • 

  • 泄漏排查的核心方法：两个时间点的快照对比 → 找到持续增长的对象类型 → 追踪引用链
    •
