内存布局

核心概念

内存布局决定了数据在内存中的物理排列方式，直接影响 CPU 缓存的利用效率和内存访问的性能。同样的算法，仅仅因为数据布局不同，性能差距可以达到一个数量级。理解内存布局的核心是理解硬件如何访问数据——CPU 缓存以 64 字节缓存行为单位工作，内存控制器以突发传输（Burst）模式工作，TLB（Translation Lookaside Buffer）缓存虚拟地址到物理地址的映射。这些硬件特性决定了什么样的数据布局是"友好"的。

结构体对齐与填充
CPU 访问未对齐的数据会产生性能惩罚——在某些架构上甚至会触发硬件异常。编译器会自动在结构体成员之间插入填充字节（Padding）以满足对齐要求。每个类型都有自然对齐要求：char 对齐到 1 字节，int 对齐到 4 字节，double 和指针对齐到 8 字节。结构体整体的对齐要求等于其最大成员的对齐要求。


#include <stdio.h>
#include <stddef.h>

struct Wasteful {
    char a;       // offset 0, size 1
                  // 7 bytes padding
    double b;     // offset 8, size 8
    char c;       // offset 16, size 1
                  // 3 bytes padding
    int d;        // offset 20, size 4
};               // Total: 24 bytes, 10 bytes wasted (42%)

struct Compact {
    double b;     // offset 0, size 8
    int d;        // offset 8, size 4
    char a;       // offset 12, size 1
    char c;       // offset 13, size 1
                  // 2 bytes padding
};               // Total: 16 bytes, 2 bytes wasted (12.5%)

int main() {
    printf("Wasteful: %zu bytes\n", sizeof(struct Wasteful));  // 24
    printf("Compact:  %zu bytes\n", sizeof(struct Compact));   // 16
    printf("Savings:  %.0f%%\n", (1.0 - 16.0/24.0) * 100);   // 33%
}
成员排序的经验法则：按对齐要求从大到小排列。这样可以最小化填充字节，让更多的结构体实例装入同一个缓存行。当结构体数组包含百万级元素时，33% 的空间节省意味着更少的缓存未命中和更低的内存带宽消耗。


在需要精确控制布局的场景中（如网络协议解析、硬件寄存器映射），可以使用编译器的打包属性：


struct __attribute__((packed)) NetworkHeader {
    uint8_t version;
    uint8_t type;
    uint16_t length;
    uint32_t sequence;
};  // 精确 8 字节，无填充

struct __attribute__((aligned(64))) CacheAligned {
    int data[16];
};  // 强制 64 字节对齐（缓存行对齐）
AoS 与 SoA 布局选择
AoS（Array of Structures）和 SoA（Structure of Arrays）是两种根本不同的数据组织方式。选择哪种取决于数据的访问模式。


#define N 1000000

// AoS: 每个粒子的所有属性存放在一起
struct Particle_AoS {
    float x, y, z;    // 位置
    float vx, vy, vz; // 速度
    float mass;        // 质量
    int type;          // 类型
};
struct Particle_AoS particles_aos[N];

// SoA: 同类属性连续存放
struct ParticleSystem_SoA {
    float x[N], y[N], z[N];
    float vx[N], vy[N], vz[N];
    float mass[N];
    int type[N];
};
struct ParticleSystem_SoA particles_soa;
当处理只涉及部分字段时，SoA 的优势明显。例如，仅更新所有粒子的位置：


// AoS: 每次缓存行加载 32 字节的 Particle_AoS，但只用了 12 字节 (x,y,z)
// 缓存有效利用率: 12/32 = 37.5%
void update_positions_aos(struct Particle_AoS* p, int n, float dt) {
    for (int i = 0; i < n; i++) {
        p[i].x += p[i].vx * dt;
        p[i].y += p[i].vy * dt;
        p[i].z += p[i].vz * dt;
    }
}

// SoA: 缓存行加载的全是 x 坐标，有效利用率 100%
void update_positions_soa(struct ParticleSystem_SoA* ps, int n, float dt) {
    for (int i = 0; i < n; i++) ps->x[i] += ps->vx[i] * dt;
    for (int i = 0; i < n; i++) ps->y[i] += ps->vy[i] * dt;
    for (int i = 0; i < n; i++) ps->z[i] += ps->vz[i] * dt;
}
SoA 布局还天然适合 SIMD 向量化——每个数组都是连续的同类型数据，可以直接加载到 SIMD 寄存器中并行处理。


但 AoS 并非一无是处——当需要访问单个实体的所有属性时（如渲染一个粒子），AoS 的所有数据在同一个缓存行内，而 SoA 需要跨多个数组跳跃读取。混合方案 AoSoA（Array of Structures of Arrays）在实践中是一种折中：将 N 个元素分成大小为 K（如 8 或 16，匹配 SIMD 宽度）的小块，块内使用 SoA 布局。


面向数据的设计 (DOD)
面向数据的设计（Data-Oriented Design, DOD）是一种以数据的存储和访问模式为中心的系统架构思想，与传统的面向对象设计（OOD）形成对比。DOD 的核心原则是：先设计数据布局，再组织处理逻辑。


在 OOD 中，数据被封装在对象内部，对象之间通过指针或引用相互关联，形成复杂的对象图。这种模式对缓存极不友好——遍历对象图意味着大量的指针追逐（Pointer Chasing），每次跳转都可能触发缓存未命中。


DOD 的设计原则：


1. 将数据按处理阶段组织，而非按实体类型组织
2. 批量处理同类操作，而非逐个实体处理
3. 消除指针间接访问，使用索引和偏移量
4. 按访问频率分离热数据和冷数据
一个典型的例子是游戏引擎的实体组件系统（Entity Component System, ECS）。传统 OOP 做法是每个游戏对象包含所有组件的指针，DOD 做法是将同类组件存放在连续数组中：


struct PositionComponent { float x, y, z; };
struct VelocityComponent { float vx, vy, vz; };
struct HealthComponent { int hp, max_hp; };

struct World {
    struct PositionComponent positions[MAX_ENTITIES];
    struct VelocityComponent velocities[MAX_ENTITIES];
    struct HealthComponent healths[MAX_ENTITIES];
    uint64_t alive_mask[MAX_ENTITIES / 64];
};

void update_movement(struct World* w, int count, float dt) {
    for (int i = 0; i < count; i++) {
        w->positions[i].x += w->velocities[i].vx * dt;
        w->positions[i].y += w->velocities[i].vy * dt;
        w->positions[i].z += w->velocities[i].vz * dt;
    }
}

小结
    

  • 结构体成员按对齐要求从大到小排列可以最小化填充字节，节省 20-40% 的内存
    • 

  • SoA 布局在批量处理部分字段时缓存利用率远高于 AoS，且天然适合 SIMD 向量化
    • 

  • AoS 布局在单实体完整访问时更优，实际选择取决于主要的访问模式
    • 

  • 面向数据的设计（DOD）将数据布局置于设计的核心，消除指针追逐，提升批量处理性能
    • 

  • 内存布局优化的本质是让硬件以它最擅长的方式工作——连续、对齐、可预测的访问模式
    • 

  • 在百万级数据量的场景下，布局优化通常比算法优化带来更直接的性能提升
    •
