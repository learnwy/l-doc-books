性能指标与度量

核心概念

性能指标是描述系统行为和健康状态的量化数据，是性能工程的基础语言。没有精确的度量，优化就变成了猜谜游戏。性能指标可以分为两大类：资源指标（描述系统组件的状态）和工作负载指标（描述系统对外提供服务的能力）。理解这些指标之间的关系，是正确诊断性能问题的前提。

延迟与响应时间
延迟（Latency）是衡量系统性能最直观的指标，但它的定义比表面看起来复杂得多。首先要区分两个常被混淆的概念：响应时间是从客户端发出请求到收到完整响应的总时间，包含网络传输时间；服务时间是服务端处理请求的纯计算时间。性能优化中通常关注的是服务端延迟，但用户感知到的是端到端的响应时间。


延迟的分布特征比平均值重要得多。一个平均延迟 50ms 的服务，可能 99% 的请求在 20ms 内完成，但 1% 的请求需要 3 秒。平均值完全掩盖了这个致命的长尾问题。因此，工程实践中必须使用百分位数（Percentile）来描述延迟分布：


P50（中位数）：50% 的请求在此延迟内完成 → 反映典型体验
P90：90% 的请求在此延迟内完成 → 反映大多数用户体验
P99：99% 的请求在此延迟内完成 → 反映长尾延迟
P999：99.9% 的请求在此延迟内完成 → 反映极端情况
在微服务架构中，延迟具有放大效应。如果一个请求需要串行调用 5 个下游服务，每个服务的 P99 延迟是 100ms，那么整体请求的 P99 延迟可能远超 500ms——因为只要任何一个服务命中长尾，整个请求就会变慢。这就是为什么高扇出架构对尾延迟格外敏感。


测量延迟时要注意协调遗漏（Coordinated Omission）问题。很多基准测试工具在上一个请求完成后才发送下一个，这意味着当系统变慢时，测量到的请求数反而更少，导致延迟数据被严重低估。Gil Tene 提出的修正方法是记录每个请求的预期发送时间和实际完成时间之差。


import time
import numpy as np

class LatencyTracker:
    def __init__(self):
        self.samples = []

    def record(self, latency_ms: float):
        self.samples.append(latency_ms)

    def percentile(self, p: float) -> float:
        return float(np.percentile(self.samples, p))

    def report(self) -> dict:
        return {
            "count": len(self.samples),
            "p50": self.percentile(50),
            "p90": self.percentile(90),
            "p99": self.percentile(99),
            "p999": self.percentile(99.9),
            "max": max(self.samples),
        }
吞吐量与带宽
吞吐量（Throughput）衡量的是系统在单位时间内完成的工作量，常见的单位包括 QPS（每秒查询数）、TPS（每秒事务数）和 RPS（每秒请求数）。吞吐量和延迟之间存在复杂的非线性关系——在低负载下，增加负载通常不会显著增加延迟，吞吐量接近线性增长；但当负载接近系统容量时，延迟会急剧上升，吞吐量增长放缓甚至下降。


这种关系可以用排队论来解释。系统中的每个资源（CPU 核心、磁盘、网络连接）都可以建模为一个带队列的服务器。利特尔法则（Little's Law）给出了三个关键指标之间的稳态关系：


L = λ × W

L = 系统中的平均请求数（并发数）
λ = 请求到达率（吞吐量）
W = 平均响应时间（延迟）
这个简单的公式有强大的实用价值。比如，如果系统的平均响应时间是 200ms，目标吞吐量是 1000 QPS，那么系统需要能够同时处理 1000 × 0.2 = 200 个并发请求。如果每个请求需要一个线程，线程池至少需要 200 个线程。


带宽和吞吐量密切相关但有本质区别。带宽是系统的理论最大传输速率（比如 10Gbps 网络），而吞吐量是实际达到的传输速率。两者之间的差距反映了协议开销、拥塞控制、应用层处理等因素的影响。带宽利用率（Throughput / Bandwidth）是评估网络效率的重要指标。


type ThroughputCounter struct {
    mu       sync.Mutex
    count    int64
    start    time.Time
    interval time.Duration
}

func (tc *ThroughputCounter) Record() {
    tc.mu.Lock()
    defer tc.mu.Unlock()
    tc.count++
}

func (tc *ThroughputCounter) Rate() float64 {
    tc.mu.Lock()
    defer tc.mu.Unlock()
    elapsed := time.Since(tc.start).Seconds()
    if elapsed == 0 {
        return 0
    }
    return float64(tc.count) / elapsed
}
USE 方法与 RED 方法
在度量指标体系建立之后，需要一个系统化的框架来组织和使用这些指标。业界最广泛使用的两个方法论是 Brendan Gregg 提出的 USE 方法和 Tom Wilkie 提出的 RED 方法。


USE 方法面向资源：对系统中的每个资源（CPU、内存、磁盘、网络），检查三个维度——Utilization（利用率）、Saturation（饱和度）和 Errors（错误）。这个方法的优势在于系统性强，不会遗漏任何关键资源的问题。


RED 方法面向服务：对每个服务接口，监控三个维度——Rate（请求速率）、Errors（错误率）和 Duration（延迟）。RED 方法更贴近业务视角，适合微服务架构中的服务级监控。


两种方法并不互斥，优秀的监控体系同时覆盖两者：USE 用于基础设施层面的早期预警和容量规划，RED 用于服务层面的 SLO 监控和业务告警。在实践中，当 RED 指标出现异常（如延迟升高）时，使用 USE 方法逐一排查底层资源，往往能快速定位根因。

SLA、SLO 与 SLI
在工程实践中，性能指标需要与业务目标对齐。Google SRE 体系提出了三层金字塔：


SLI（Service Level Indicator，服务等级指标）是对服务行为的量化度量，通常表示为百分比。例如："过去 5 分钟内，成功请求（HTTP 2xx）占总请求的比例"或"P99 延迟低于 300ms 的请求占总请求的比例"。好的 SLI 应该直接反映用户体验。


SLO（Service Level Objective，服务等级目标）是 SLI 的目标值。例如："可用性 SLI ≥ 99.95%"或"延迟 SLI ≥ 99%（即 P99 延迟 < 300ms 的比例超过 99%）"。SLO 定义了"足够好"的标准，是团队内部的承诺。


SLA（Service Level Agreement，服务等级协议）是 SLO 加上违约后果的正式合同。SLA 通常比 SLO 更宽松（留出安全边际），违反 SLA 可能触发退款、积分补偿等商业后果。


错误预算（Error Budget）是 SLO 的逆向应用。如果 SLO 是 99.9%，那么每月允许 0.1% 的时间不达标——大约 43 分钟。这个预算让团队可以在可靠性和迭代速度之间做出量化的权衡：当错误预算充足时，可以加快发布节奏；当预算即将耗尽时，应该暂停功能发布，专注于稳定性。


slos:
  - name: 'API 可用性'
    sli: 'successful_requests / total_requests'
    target: 0.999
    window: '30d'
    error_budget_minutes: 43.2

  - name: 'API 延迟'
    sli: 'requests_under_300ms / total_requests'
    target: 0.99
    window: '30d'

  - name: '批处理完成率'
    sli: 'completed_jobs / submitted_jobs'
    target: 0.995
    window: '7d'
选择正确的 SLI 是整个体系的关键。糟糕的 SLI 选择会导致"指标绿灯但用户在骂"的局面。选择 SLI 的原则是：它必须反映用户真正感知的体验，而不仅仅是系统内部状态。


小结
    

  • 性能度量的核心是延迟和吞吐量，但必须结合资源指标才能完整描述系统状态
    • 

  • 延迟必须用百分位数而非平均值来描述，P99 和 P999 对高可用系统尤为重要
    • 

  • 利特尔法则 L = λ × W 连接了并发数、吞吐量和延迟，是容量规划的基础工具
    • 

  • USE 方法和 RED 方法提供了系统化的指标组织框架，两者互补而非互斥
    • 

  • SLI → SLO → SLA 三层体系将性能指标与业务目标对齐，错误预算是连接可靠性与迭代速度的桥梁
    • 

  • 选择正确的度量指标比收集更多指标更重要——关注用户真正感知的体验
