网络优化

核心概念

网络通信是分布式系统的基础，也是微服务架构中最常见的性能瓶颈。网络优化需要在延迟（单次请求的耗时）和吞吐量（单位时间传输的数据量）之间找到平衡。与磁盘 I/O 不同，网络性能受到物理距离、协议开销、拥塞控制和对端处理能力等多重因素的约束。优化策略需要覆盖从应用层协议到内核网络栈的完整链路。

TCP 参数调优
TCP 是互联网的基础传输协议，其默认参数为通用场景设计。针对特定工作负载调优 TCP 参数可以显著提升网络性能。


发送和接收缓冲区决定了 TCP 窗口大小，直接影响高延迟网络上的吞吐量。根据带宽延迟积（BDP = 带宽 × RTT）设置缓冲区：


# 查看当前 TCP 缓冲区设置
sysctl net.ipv4.tcp_rmem  # 读缓冲区: min default max
sysctl net.ipv4.tcp_wmem  # 写缓冲区: min default max

# 优化高带宽高延迟网络 (10Gbps, 100ms RTT → BDP = 125MB)
sysctl -w net.ipv4.tcp_rmem="4096 1048576 16777216"
sysctl -w net.ipv4.tcp_wmem="4096 1048576 16777216"
sysctl -w net.core.rmem_max=16777216
sysctl -w net.core.wmem_max=16777216

# 启用窗口缩放（默认已启用）
sysctl -w net.ipv4.tcp_window_scaling=1
连接管理参数影响服务器在高并发下的连接处理能力：


# 增大连接队列
sysctl -w net.core.somaxconn=65535         # listen() 队列最大长度
sysctl -w net.ipv4.tcp_max_syn_backlog=65535  # SYN 队列长度

# TIME_WAIT 优化
sysctl -w net.ipv4.tcp_tw_reuse=1          # 允许复用 TIME_WAIT 连接
sysctl -w net.ipv4.tcp_fin_timeout=15      # FIN_WAIT2 超时时间

# 快速回收和保活
sysctl -w net.ipv4.tcp_keepalive_time=60   # 保活探测间隔
sysctl -w net.ipv4.tcp_keepalive_intvl=10  # 保活重试间隔
sysctl -w net.ipv4.tcp_keepalive_probes=6  # 保活重试次数

连接池与多路复用
每次 TCP 连接的建立需要三次握手（1 RTT），加上 TLS 握手可能需要额外 1-2 RTT。对于频繁的短连接请求，连接建立的开销可能占总延迟的 50% 以上。连接池（Connection Pool）通过复用已建立的连接来消除这个开销。


import (
    "net/http"
    "time"
)

var client = &http.Client{
    Transport: &http.Transport{
        MaxIdleConns:        100,
        MaxIdleConnsPerHost: 20,
        MaxConnsPerHost:     50,
        IdleConnTimeout:     90 * time.Second,
        DisableKeepAlives:   false,
    },
    Timeout: 30 * time.Second,
}

func makeRequest(url string) (*http.Response, error) {
    return client.Do(&http.Request{})  // 自动复用连接
}
HTTP/2 多路复用在单个 TCP 连接上并发传输多个请求/响应流，消除了 HTTP/1.1 的队头阻塞（Head-of-Line Blocking）问题：


HTTP/3（基于 QUIC）在 UDP 之上实现可靠传输，进一步解决了 TCP 层的队头阻塞：当一个流的包丢失时，不影响其他流的传输。对于移动网络等高丢包环境，HTTP/3 比 HTTP/2 有显著优势。

数据压缩是减少传输量的直接手段。在 CPU 充裕但带宽有限的场景下，压缩可以显著提升有效吞吐量：


# HTTP 响应压缩（Nginx 配置）
gzip on;
gzip_types text/plain application/json application/javascript;
gzip_min_length 1024;
gzip_comp_level 6;

# 使用 Brotli（比 gzip 压缩率高 15-25%）
brotli on;
brotli_types text/plain application/json;
brotli_comp_level 6;
减少传输数据量的应用层策略：


    

  • 字段过滤：GraphQL 或 REST 的 ?fields=id,name 参数，只返回需要的字段
    • 

  • 增量传输：使用 ETag/Last-Modified 条件请求，返回 304 避免传输未变更的数据
    • 

  • 分页：避免一次返回所有结果，使用游标分页控制每次返回量

Nagle 算法与延迟优化
Nagle 算法合并小包以减少网络中的小包数量，但会引入最多 200ms 的延迟。对于实时性要求高的应用（如游戏、交易系统、交互式 SSH），应该禁用 Nagle 算法：


#include <netinet/tcp.h>

int flag = 1;
setsockopt(sockfd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));
与 Nagle 算法相关的是 TCP_CORK（Linux）/TCP_NOPUSH（BSD），它将多次 write() 的数据积攒到一起，在解除 CORK 后一次性发送。适用于明确知道数据边界的场景（如 HTTP 响应 = Headers + Body）：


int cork = 1;
setsockopt(sockfd, IPPROTO_TCP, TCP_CORK, &cork, sizeof(cork));

write(sockfd, http_headers, headers_len);
write(sockfd, http_body, body_len);

cork = 0;
setsockopt(sockfd, IPPROTO_TCP, TCP_CORK, &cork, sizeof(cork));
// 此时内核会将 headers 和 body 合并为一个 TCP 段发送

小结
    

  • TCP 参数调优的核心是匹配网络环境：缓冲区大小由 BDP 决定，BBR 适合高丢包网络
    • 

  • 连接池消除重复的握手开销，HTTP/2 多路复用在单连接上并行传输多个流
    • 

  • 序列化格式选择影响 CPU 和带宽：JSON 适合调试，Protobuf/FlatBuffers 适合生产
    • 

  • TCP_NODELAY 对低延迟场景至关重要——禁用 Nagle 算法避免小包延迟
    • 

  • 网络优化的优先级：减少 RTT 次数 > 减少传输量 > 增大吞吐量 > 降低单包延迟
    • 

  • 在分布式系统中，网络延迟的变异性往往比均值更影响用户体验——关注 P99 延迟
    •
