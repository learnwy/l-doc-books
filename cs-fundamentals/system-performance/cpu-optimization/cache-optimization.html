CPU 缓存优化

核心概念

CPU 缓存是位于 CPU 和主内存之间的高速存储层，弥补了处理器速度和内存速度之间数量级的差距。现代 CPU 通常有三级缓存（L1/L2/L3），访问延迟从 1 纳秒到 10 纳秒不等，而主内存访问延迟约 100 纳秒。这意味着一次缓存未命中的代价相当于几十到上百个 CPU 周期的等待。对于数据密集型应用，缓存命中率往往比算法复杂度更决定实际性能。

缓存行与空间局部性
CPU 缓存以缓存行（Cache Line）为最小读写单位，通常为 64 字节。当 CPU 需要读取一个 4 字节的 int 变量时，它实际上会将包含这个变量的整个 64 字节缓存行都加载进来。这个设计利用了空间局部性（Spatial Locality）——程序访问了某个地址后，很可能会接着访问附近的地址。


理解缓存行大小对数据结构设计有直接影响。考虑遍历数组和遍历链表的性能差异：


#define N 10000000

struct ArrayData {
    int values[N];
};

struct Node {
    int value;
    struct Node *next;
};

void sum_array(struct ArrayData *data) {
    long sum = 0;
    for (int i = 0; i < N; i++) {
        sum += data->values[i];  // 每 16 次访问才触发 1 次缓存未命中
    }
}

void sum_linked_list(struct Node *head) {
    long sum = 0;
    struct Node *curr = head;
    while (curr) {
        sum += curr->value;  // 每次访问可能都触发缓存未命中
        curr = curr->next;
    }
}
数组遍历每次缓存行加载（64 字节）可以满足 16 个 int（4 字节）的后续访问，缓存未命中率约 1/16。而链表节点如果在内存中随机分布，每次访问都可能触发缓存未命中。这就是为什么相同算法复杂度下，数组比链表快得多——本质上是缓存友好性的差异。


结构体填充与对齐也与缓存行密切相关。编译器会在结构体成员之间插入填充字节以满足对齐要求。不恰当的成员排列会导致结构体占用更多的缓存行：


struct BadLayout {
    char a;       // 1 byte + 7 padding
    double b;     // 8 bytes
    char c;       // 1 byte + 3 padding
    int d;        // 4 bytes
};               // Total: 24 bytes (跨多缓存行)

struct GoodLayout {
    double b;     // 8 bytes
    int d;        // 4 bytes
    char a;       // 1 byte
    char c;       // 1 byte + 2 padding
};               // Total: 16 bytes (更紧凑)
时间局部性与热数据分离
时间局部性（Temporal Locality）是指最近访问的数据很可能在短时间内再次被访问。优化时间局部性的核心策略是将热数据（频繁访问的数据）和冷数据（很少访问的数据）分离存放，让热数据能够持续驻留在缓存中。


struct HotCold_Bad {
    int id;              // 热: 每次查询都需要
    float score;         // 热: 排序/过滤时频繁访问
    char name[64];       // 冷: 只在显示时需要
    char description[256]; // 冷: 很少访问
    int category;        // 热: 过滤条件
    long last_updated;   // 冷: 偶尔访问
};

struct HotData {
    int id;
    float score;
    int category;
};

struct ColdData {
    char name[64];
    char description[256];
    long last_updated;
};

struct HotCold_Good {
    struct HotData *hot;   // 紧凑的热数据数组
    struct ColdData *cold; // 按需加载的冷数据
    size_t count;
};
这种SoA（Structure of Arrays）模式在游戏引擎和数据库引擎中广泛使用。将同类型的热字段打包到连续数组中，遍历时每次缓存行加载都是有效数据，不会被冷字段"浪费"空间。


伪共享与缓存一致性
在多核 CPU 中，每个核心有独立的 L1/L2 缓存。当两个核心修改同一缓存行中的不同变量时，会触发伪共享（False Sharing）——缓存一致性协议（如 MESI）会在核心之间反复传递缓存行的所有权，即使两个核心操作的是完全独立的数据。伪共享可以导致 10 倍以上的性能下降。


struct CounterBad {
    long counter_a;  // 核心 0 频繁写入
    long counter_b;  // 核心 1 频繁写入
    // 两个 long（16 字节）在同一个 64 字节缓存行中 → 伪共享!
};

#define CACHE_LINE_SIZE 64

struct CounterGood {
    long counter_a;
    char padding_a[CACHE_LINE_SIZE - sizeof(long)];  // 填充至独立缓存行
    long counter_b;
    char padding_b[CACHE_LINE_SIZE - sizeof(long)];
};
在 Java 中，可以使用 @Contended 注解来自动避免伪共享：


import sun.misc.Contended;

public class PaddedCounter {
    @Contended
    volatile long counterA;

    @Contended
    volatile long counterB;
}
// 需要 JVM 参数: -XX:-RestrictContended
检测伪共享的方法是使用 perf c2c（cache-to-cache）工具：


perf c2c record -g -- ./myapp
perf c2c report --stdio
# 关注 "Shared Data Cache Line Table" 中 HITM（跨核命中）比例高的缓存行
预取策略与缓存污染
CPU 有硬件预取器（Hardware Prefetcher），能够检测到顺序访问模式并提前加载后续缓存行。但对于不规则的访问模式（如哈希表查找、树遍历），硬件预取器无法有效工作。此时可以使用软件预取指令手动提示 CPU：


#include <xmmintrin.h>

void sum_with_prefetch(int *data, int n) {
    long sum = 0;
    for (int i = 0; i < n; i++) {
        _mm_prefetch(&data[i + 16], _MM_HINT_T0);  // 提前 16 个元素预取
        sum += data[i];
    }
}

void hash_lookup_with_prefetch(HashTable *ht, int *keys, int n) {
    for (int i = 0; i < n - 4; i++) {
        size_t hash = hash_function(keys[i + 4]);
        _mm_prefetch(&ht->buckets[hash], _MM_HINT_T0);

        process(ht, keys[i]);
    }
}
与预取相对的问题是缓存污染（Cache Pollution）——将大量不会被重用的数据加载进缓存，把真正有用的热数据挤出去。典型场景是扫描大数组时会把整个 L3 缓存刷掉。解决方法包括使用 _MM_HINT_NTA（Non-Temporal Access）提示数据不需要缓存，或者使用非临时存储指令 _mm_stream_si128 绕过缓存直接写入内存。

小结
    

  • CPU 缓存未命中是数据密集型应用的首要性能杀手，一次 L3 未命中 ≈ 200 个 CPU 周期的等待
    • 

  • 以缓存行（64 字节）为单位思考数据布局，紧凑排列热数据，按照访问模式组织内存
    • 

  • SoA 模式（Structure of Arrays）在批量遍历场景下远优于 AoS，是高性能数据处理的标准模式
    • 

  • 伪共享是多核编程中的隐蔽杀手，通过缓存行对齐填充或 @Contended 注解来避免
    • 

  • 软件预取可以弥补硬件预取器在不规则访问模式下的不足，但需要谨慎使用避免缓存污染
    • 

  • 优化缓存友好性通常比优化算法复杂度有更直接的性能收益——常数因子往往决定实际表现
    •
