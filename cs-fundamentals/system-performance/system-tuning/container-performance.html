Part III · 系统 (Systems)系统性能与优化 简介系统调优 简介容器性能

容器性能

核心概念

容器（Docker/Kubernetes）通过 Linux 的 cgroups 和 namespace 实现资源隔离，但这种隔离并非免费的——它引入了额外的抽象层，并改变了应用感知系统资源的方式。在容器环境中，很多传统的性能假设不再成立：/proc/cpuinfo 可能显示宿主机的全部 CPU 核心而非容器分配的核心数，free -m 可能报告宿主机的总内存。这种"资源视图不匹配"是容器性能问题的首要来源。

CPU 限制与 Throttling
容器的 CPU 限制通过 cgroup 的 CPU quota 实现。当设置 --cpus=2 时，实际含义是在每个调度周期（默认 100ms）内，容器的所有线程最多使用 200ms 的 CPU 时间。一旦配额耗尽，容器内的所有线程会被节流（Throttled）直到下一个周期。


# Docker CPU 限制
docker run --cpus=2 --cpu-shares=1024 myapp

# Kubernetes CPU 限制
# resources:
#   requests:
#     cpu: "1"       # 调度保证
#   limits:
#     cpu: "2"       # 硬上限

# 检查 cgroup CPU 配额
cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us    # -1 表示无限制
cat /sys/fs/cgroup/cpu/cpu.cfs_period_us   # 默认 100000 (100ms)

# 检查 throttling 状态
cat /sys/fs/cgroup/cpu/cpu.stat
# nr_periods: 总周期数
# nr_throttled: 被节流的周期数
# throttled_time: 被节流的总纳秒数
CPU Throttling 是容器环境中最常见的性能问题。一个典型的陷阱：Java 或 Go 应用默认根据 runtime.NumCPU() 创建线程池，在 32 核宿主机上会创建 32 个线程，但容器只有 2 核的配额。32 个线程竞争 2 核的配额，导致频繁的上下文切换和节流。


import "runtime"

func init() {
    // Go 1.19+ 自动感知 cgroup 限制
    // 但旧版本需要手动设置
    // runtime.GOMAXPROCS(2)
}
// Java 10+ 自动感知容器 CPU 限制
// 旧版本需要手动设置
// -XX:ActiveProcessorCount=2
// -XX:ParallelGCThreads=2

// 检查 JVM 感知到的 CPU 数
System.out.println(Runtime.getRuntime().availableProcessors());
建议：对延迟敏感的服务，CPU limits 设为 requests 的 1.5-2 倍，留出突发余量。对批处理任务，可以紧密设置 limits。


内存限制与 OOM
容器的内存限制通过 cgroup 的 memory.limit_in_bytes 实现。当容器内存使用超过限制时，内核的 OOM Killer 会杀掉容器中的进程。


# Docker 内存限制
docker run --memory=4g --memory-swap=4g myapp  # 4GB 内存，无 swap

# 检查容器内存使用
cat /sys/fs/cgroup/memory/memory.usage_in_bytes
cat /sys/fs/cgroup/memory/memory.limit_in_bytes
cat /sys/fs/cgroup/memory/memory.stat
关键问题是内存视图不匹配。容器内的 free 和 /proc/meminfo 默认显示宿主机的内存信息，导致应用（特别是 JVM）的自动内存调优出错：


# 容器内正确获取内存限制
cat /sys/fs/cgroup/memory/memory.limit_in_bytes

# cgroup v2
cat /sys/fs/cgroup/memory.max
// Java 8u191+ / Java 10+ 自动感知容器内存限制
// 旧版本的 JVM 需要手动设置
// -XX:MaxRAMPercentage=75.0   (使用容器内存限制的 75%)
// -Xmx=3g                     (直接指定堆大小)
内存使用监控应该关注容器级的指标，而非宿主机级：


# Kubernetes Pod 内存指标
# container_memory_working_set_bytes → cgroup 实际使用量（比 RSS 更准确）
# container_memory_usage_bytes → 含缓存的总使用量
# container_memory_rss → RSS（匿名内存）

# Prometheus 告警：容器内存接近限制
- alert: ContainerMemoryHigh
  expr: |
    container_memory_working_set_bytes / container_spec_memory_limit_bytes > 0.85
  for: 5m
网络与存储开销
容器网络引入了额外的虚拟化层（veth pair + 网桥或 overlay 网络），会增加延迟和降低吞吐量。


# 网络模式对比
docker run --network=bridge myapp    # 默认：veth + docker0 网桥，有开销
docker run --network=host myapp      # 直接使用宿主机网络栈，无额外开销

# 测量网络开销
# 容器内
iperf3 -c host_ip -t 10
# 宿主机
iperf3 -c host_ip -t 10
# 对比两者的吞吐量差异

存储层的 overlay 文件系统（如 overlay2）在容器内的读写操作上引入了写时复制（Copy-on-Write）开销。对于 I/O 密集的应用，应该使用 volume 挂载直接访问宿主机文件系统：


# 使用 volume 挂载绕过 overlay FS
docker run -v /data/mysql:/var/lib/mysql myapp

# 使用 tmpfs 挂载（内存文件系统，适合临时数据）
docker run --tmpfs /tmp:rw,size=1g myapp
Kubernetes 调度与资源优化
在 Kubernetes 中，资源的 requests 和 limits 不仅影响运行时性能，还影响调度决策和 QoS 分类。


apiVersion: v1
kind: Pod
spec:
  containers:
    - name: app
      resources:
        requests:
          cpu: '500m' # 调度保证：至少 0.5 核
          memory: '1Gi' # 调度保证：至少 1GB
        limits:
          cpu: '2' # 上限：最多 2 核
          memory: '4Gi' # 上限：最多 4GB（超限即 OOM Kill）
Kubernetes 的 QoS 分类影响驱逐优先级：


    

  • Guaranteed：requests = limits → 最高优先级，最后被驱逐
    • 

  • Burstable：requests < limits → 中等优先级
    • 

  • BestEffort：未设置 requests/limits → 最低优先级，最先被驱逐
    • 



性能优化建议：


    

  • 关键服务设为 Guaranteed QoS（requests = limits）
    • 

  • 使用 Vertical Pod Autoscaler（VPA）自动推荐合适的 requests
    • 

  • 使用 Topology Manager 确保 CPU 和内存的 NUMA 亲和性
    • 

  • 启用 CPU Manager 的 static 策略为 Guaranteed Pod 分配独占 CPU
    • 



小结
    

  • 容器环境的首要问题是资源视图不匹配——确保应用正确感知容器的 CPU 和内存限制
    • 

  • CPU Throttling 是最常见的容器性能问题，通过 cpu.stat 中的 nr_throttled 检测
    • 

  • JVM/Go 的现代版本已支持自动感知 cgroup 限制，但仍需验证和可能的手动配置
    • 

  • 容器网络的 host 模式几乎零开销，overlay 网络可增加 50-200μs 的延迟
    • 

  • I/O 密集应用应使用 Volume 挂载绕过 overlay FS 的写时复制开销
    • 

  • Kubernetes 中关键服务应设置 Guaranteed QoS（requests = limits）以获得最高调度优先级
    •
