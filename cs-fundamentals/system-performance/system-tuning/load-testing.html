负载测试

核心概念

负载测试（Load Testing）是在受控条件下模拟真实用户请求，测量系统在不同负载水平下的性能表现。它回答的核心问题是：系统能承受多大的负载？在目标负载下表现如何？何时会崩溃？ 负载测试不是上线前的一次性工作，而应该嵌入 CI/CD 流程，成为持续性能验证的一部分。

工具选型与脚本编写
现代负载测试工具可以分为脚本驱动和配置驱动两类。选择工具时需要考虑：协议支持、脚本灵活性、分布式执行能力和结果分析功能。


k6 是当前最流行的开发者友好型负载测试工具，使用 JavaScript 编写测试脚本：


import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate, Trend } from 'k6/metrics';

const errorRate = new Rate('error_rate');
const latencyP99 = new Trend('latency_p99');

export const options = {
  stages: [
    { duration: '2m', target: 100 }, // 2分钟 ramp up 到 100 VU
    { duration: '5m', target: 100 }, // 稳定 100 VU 持续 5 分钟
    { duration: '2m', target: 200 }, // ramp up 到 200 VU
    { duration: '5m', target: 200 }, // 稳定 200 VU
    { duration: '2m', target: 0 }, // ramp down
  ],
  thresholds: {
    http_req_duration: ['p(99)<500'], // P99 延迟 < 500ms
    error_rate: ['rate<0.01'], // 错误率 < 1%
  },
};

export default function () {
  const payload = JSON.stringify({
    username: `user_${__VU}`,
    query: 'performance testing',
  });

  const params = {
    headers: { 'Content-Type': 'application/json' },
  };

  const res = http.post('http://api.example.com/search', payload, params);

  check(res, {
    'status is 200': (r) => r.status === 200,
    'response time < 500ms': (r) => r.timings.duration < 500,
  });

  errorRate.add(res.status !== 200);
  latencyP99.add(res.timings.duration);

  sleep(Math.random() * 2 + 1); // 模拟用户思考时间
}
wrk 是一个轻量级的 HTTP 基准测试工具，适合快速测试单个端点：


# 基本用法: 12 线程, 400 连接, 30 秒
wrk -t12 -c400 -d30s http://localhost:8080/api/search

# 使用 Lua 脚本自定义请求
wrk -t12 -c400 -d30s -s script.lua http://localhost:8080/api/search

测试场景设计
好的负载测试必须模拟真实的用户行为，而不是简单地对单个 API 发送请求。关键是设计贴近生产的测试场景。


流量模型的设计需要基于生产数据：


// k6: 模拟真实流量比例
export default function () {
  const scenario = Math.random();

  if (scenario < 0.6) {
    // 60% 的请求是浏览/搜索
    http.get('http://api.example.com/products?q=' + randomQuery());
  } else if (scenario < 0.85) {
    // 25% 是查看详情
    http.get('http://api.example.com/products/' + randomProductId());
  } else if (scenario < 0.95) {
    // 10% 是加入购物车
    http.post(
      'http://api.example.com/cart',
      JSON.stringify({
        product_id: randomProductId(),
        quantity: 1,
      }),
    );
  } else {
    // 5% 是下单
    http.post(
      'http://api.example.com/orders',
      JSON.stringify({
        cart_id: randomCartId(),
        payment_method: 'credit_card',
      }),
    );
  }

  sleep(Math.random() * 3 + 1);
}
注意事项：


    

  • 思考时间：真实用户在请求之间有停顿（阅读页面、填写表单），不模拟思考时间会过估并发
    • 

  • 数据多样性：使用足够多的不同数据，避免测试被缓存命中率过高而美化
    • 

  • 依赖隔离：第三方 API 应使用 Mock 或 Stub，避免外部依赖影响测试结果
    • 

  • 预热：测试开始前给系统足够的预热时间（JIT 编译、缓存填充、连接池初始化）
    • 



结果分析与报告
负载测试的价值在于结果分析而非执行本身。关键指标需要从多个维度交叉分析。


延迟分析：


# k6 输出的关键指标
# http_req_duration
#   avg=45.2ms  min=2.1ms  med=32.1ms  max=2.1s  p(90)=85.3ms  p(95)=120.5ms  p(99)=450.2ms

# 重点关注:
# 1. P99 是否满足 SLO (例如 < 500ms)
# 2. P99/P50 比值 — 反映延迟分布的"肥尾"程度
# 3. max 值是否异常 — 可能存在偶发的严重问题
吞吐量与延迟的关系曲线是最重要的分析图表。随着负载增加，观察延迟的变化：


QPS    P50(ms)  P99(ms)  错误率
100    15       45       0%
200    18       55       0%
500    25       80       0%
1000   35       150      0%     ← 线性增长阶段
1500   55       350      0%     ← 拐点出现
2000   120      800      0.5%   ← 开始降级
2500   350      2100     5%     ← 严重过载
3000   超时     超时     25%    ← 系统崩溃
性能回归检测：将负载测试嵌入 CI/CD，每次发布前与基线对比：


# GitHub Actions 中运行 k6
- name: Run load test
  run: |
    k6 run --out json=results.json load-test.js

- name: Check thresholds
  run: |
    jq '.metrics.http_req_duration.values["p(99)"]' results.json | \
    awk '{if ($1 > 500) {print "P99 regression: " $1 "ms"; exit 1}}'

分布式负载生成
当单台测试机的资源不足以生成目标负载时，需要分布式负载生成。k6 Cloud、Locust 和 Gatling 都支持分布式执行。


# Locust: 分布式负载测试
# Master 节点
# locust --master -f locustfile.py

# Worker 节点（可以启动多个）
# locust --worker --master-host=master_ip -f locustfile.py

from locust import HttpUser, task, between

class WebsiteUser(HttpUser):
    wait_time = between(1, 5)

    @task(6)
    def browse(self):
        self.client.get("/products")

    @task(3)
    def view_detail(self):
        self.client.get(f"/products/{self.random_id()}")

    @task(1)
    def purchase(self):
        self.client.post("/orders", json={"product_id": self.random_id()})

    def random_id(self):
        import random
        return random.randint(1, 10000)
分布式测试的注意事项：


    

  • 负载生成器本身不应成为瓶颈——监控测试机的 CPU 和网络
    • 

  • 确保所有 Worker 节点的时钟同步
    • 

  • 测试网络带宽应远大于目标系统的预期吞吐量
    • 

  • 从不同地理位置生成负载更贴近真实场景
    • 



小结
    

  • 负载测试的目标是在生产问题发生之前发现它们，应该嵌入 CI/CD 而非仅在上线前执行
    • 

  • 测试场景必须模拟真实用户行为，包括流量比例、思考时间和数据多样性
    • 

  • 吞吐量-延迟曲线是最重要的分析产出，拐点标识了系统的安全容量边界
    • 

  • P99/P50 比值反映了延迟分布的肥尾程度，比值越大说明长尾问题越严重
    • 

  • 性能回归检测通过与历史基线对比实现，在 CI 中设置自动化门禁防止性能退化
    • 

  • 负载测试的常见陷阱：忽略思考时间（过估并发）、缓存命中率偏高（过于乐观）、忽视预热阶段
    •
