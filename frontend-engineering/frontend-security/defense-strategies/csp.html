内容安全策略 CSP

核心概念

内容安全策略（Content Security Policy, CSP）是一种浏览器安全机制，通过 HTTP 响应头或 <meta> 标签声明页面允许加载和执行的资源来源。CSP 的核心设计思想是"白名单机制"——默认禁止所有不在白名单中的资源，从根本上减少 XSS 和数据注入攻击的攻击面。

CSP 不是替代输入验证和输出转义的银弹，而是纵深防御体系的最后一道防线。即使攻击者成功注入了恶意脚本，CSP 也能阻止其加载外部资源或执行内联代码。

策略配置实践
从宽松到严格的渐进式 CSP 配置：


const strictCsp = (req: Request, res: Response, next: NextFunction) => {
  const nonce = crypto.randomBytes(16).toString('base64');
  res.locals.cspNonce = nonce;

  const policy = [
    "default-src 'self'",
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'`,
    "style-src 'self' 'unsafe-inline'",
    "img-src 'self' data: https:",
    "font-src 'self' https://fonts.gstatic.com",
    `connect-src 'self' ${process.env.API_ORIGIN}`,
    "frame-src 'none'",
    "frame-ancestors 'none'",
    "base-uri 'self'",
    "form-action 'self'",
    'upgrade-insecure-requests',
  ].join('; ');

  res.setHeader('Content-Security-Policy', policy);
  next();
};

const reportOnlyCsp = (req: Request, res: Response, next: NextFunction) => {
  const policy = [
    "default-src 'self'",
    "script-src 'self'",
    'report-uri /api/csp-report',
    'report-to csp-endpoint',
  ].join('; ');

  res.setHeader('Content-Security-Policy-Report-Only', policy);
  next();
};

app.post('/api/csp-report', (req, res) => {
  const report = req.body['csp-report'] || req.body;
  console.warn('CSP 违规:', {
    blockedUri: report['blocked-uri'],
    violatedDirective: report['violated-directive'],
    documentUri: report['document-uri'],
    sourceFile: report['source-file'],
    lineNumber: report['line-number'],
  });
  res.status(204).end();
});
Nonce 与 Hash 机制
Nonce 和 Hash 是在避免 unsafe-inline 的同时允许特定内联脚本执行的安全方式：


const generateCspPage = (nonce: string) => `
<!DOCTYPE html>
<html>
<head>
  <meta charset="UTF-8">
  <script nonce="${nonce}">
    window.__APP_CONFIG__ = { apiUrl: '/api' }
  </script>
  <script nonce="${nonce}" src="/app.js"></script>
</head>
<body>
  <div id="root"></div>
</body>
</html>
`;

// script-src 'sha256-xxx' 允许特定哈希的内联脚本
const computeScriptHash = (script: string): string => {
  const hash = crypto.createHash('sha256').update(script).digest('base64');
  return `'sha256-${hash}'`;
};

const inlineScript = "console.log('hello')";
const scriptHash = computeScriptHash(inlineScript);
// CSP: script-src 'self' 'sha256-xxxxx'

// strict-dynamic 传递信任：被信任的脚本加载的脚本也被信任
// script-src 'nonce-abc123' 'strict-dynamic'
// 带 nonce 的脚本加载的所有子脚本自动获得信任
React/Vite 项目中集成 CSP Nonce：


import type { FC } from 'react'

interface HtmlDocumentProps {
  nonce: string
  scripts: string[]
  styles: string[]
}

const HtmlDocument: FC<HtmlDocumentProps> = ({ nonce, scripts, styles }) => {
  return (
    <html>
      <head>
        {styles.map((href) => (
          <link key={href} rel="stylesheet" href={href} nonce={nonce} />
        ))}
      </head>
      <body>
        <div id="root" />
        {scripts.map((src) => (
          <script key={src} src={src} nonce={nonce} />
        ))}
      </body>
    </html>
  )
}
常见陷阱与解决方案
CSP 部署中经常遇到的问题及解决方案：


// 问题1: 第三方脚本（Google Analytics, Sentry 等）
// 解决: 使用 strict-dynamic + nonce
const thirdPartyFriendlyCsp = [
  "default-src 'self'",
  "script-src 'nonce-${nonce}' 'strict-dynamic' https:",
  "style-src 'self' 'unsafe-inline'", // 许多库需要内联样式
  `connect-src 'self' https://www.google-analytics.com https://sentry.io`,
].join('; ');

// 问题2: 内联事件处理器（onclick 等）被 CSP 阻止
// 解决: 使用 addEventListener 替代内联事件
// 错误: <button onclick="handleClick()">
// 正确: document.querySelector('button').addEventListener('click', handleClick)

// 问题3: eval() 和 new Function() 被阻止
// 解决: 重构代码避免动态代码执行
// 如果确实需要（如某些模板引擎），添加 'unsafe-eval'（不推荐）

// 问题4: CSS-in-JS 库需要 unsafe-inline
// 解决: 使用支持 nonce 的 CSS-in-JS 库
// Emotion: <CacheProvider value={createCache({ key: 'css', nonce })} />
// styled-components: <StyleSheetManager nonce={nonce} />

// 问题5: Web Worker 和 Service Worker
const workerCsp = [
  "default-src 'self'",
  "worker-src 'self' blob:", // 允许 blob URL 创建 Worker
  "child-src 'self' blob:",
].join('; ');
渐进式部署策略
在现有项目中部署 CSP 应采用渐进式策略：


// 阶段1: 仅报告模式（不阻止，只收集违规）
const phase1 = {
  header: 'Content-Security-Policy-Report-Only',
  policy: "default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; report-uri /csp-report",
};

// 阶段2: 收紧策略，移除 unsafe-eval
const phase2 = {
  header: 'Content-Security-Policy-Report-Only',
  policy: "default-src 'self'; script-src 'self' 'unsafe-inline'; report-uri /csp-report",
};

// 阶段3: 引入 nonce，移除 unsafe-inline
const phase3 = {
  header: 'Content-Security-Policy-Report-Only',
  policy: "default-src 'self'; script-src 'self' 'nonce-xxx' 'strict-dynamic'; report-uri /csp-report",
};

// 阶段4: 切换到强制模式
const phase4 = {
  header: 'Content-Security-Policy',
  policy: "default-src 'self'; script-src 'self' 'nonce-xxx' 'strict-dynamic'; report-uri /csp-report",
};
小结
    

  • CSP 是浏览器级别的资源加载白名单机制，是 XSS 防御的最后一道防线
    • 

  • script-src 是最关键的指令，推荐使用 nonce + strict-dynamic 方案
    • 

  • 避免 unsafe-inline 和 unsafe-eval——它们极大削弱 CSP 的防护能力
    • 

  • 渐进式部署：Report-Only → 收紧策略 → 强制模式，通过 CSP 报告逐步修复违规
    • 

  • strict-dynamic 实现信任传递——被信任脚本加载的子脚本自动获得信任
    • 

  • 第三方脚本（分析、监控等）需要在 CSP 策略中明确允许其来源
    • 

  • CSP 报告端点用于收集线上违规数据，是持续优化策略的重要数据源
    • 

  • Nonce 每次请求都需要重新生成，确保不可预测性
    •
