Part IV · 浏览器与平台 (Browser & Platform)PWA 与离线优先离线数据同步策略与冲突解决

同步策略与冲突解决

核心概念

离线优先应用允许用户在断网时继续编辑——但重新连接时客户端与服务器数据可能已经分歧，需要同步策略和冲突解决机制。主要策略包括：推拉同步、操作变换（Operational Transformation，Google Docs 使用）、CRDT（无冲突复制数据类型，自动合并无需协调）、最后写入者胜出（简单但可能丢数据）。同步引擎的选择包括 PouchDB + CouchDB、Replicache、Yjs、Automerge、Liveblocks 等。本节涵盖同步模型、冲突解决策略、CRDT 与操作变换的对比，以及实际工具选型。

策略 冲突解决方式 复杂度 适用场景
最后写入者胜出 最新时间戳优先 低 简单场景
手动合并 用户选择 中 文档编辑
操作变换（OT） 服务器协调操作 高 Google Docs
CRDT 数学保证自动合并 高 Figma、Liveblocks
基于版本的拉取 If-Match 请求头 中 REST API

同步模型

推送（Push）：本地变更发送到服务器。在没有冲突时操作简单。

拉取（Pull）：从服务器获取最新变更。在没有冲突时操作简单。

双向同步（Bidirectional）：双向同步，冲突在所难免。

订阅（Subscription）：服务器实时推送更新，通过 WebSocket 或 SSE 实现。

同步队列
待处理操作队列模式：


// 数据变更时
async function updateTask(id, changes) {
  await db.tasks.update(id, changes);
  await db.syncQueue.add({
    type: 'update',
    table: 'tasks',
    id,
    changes,
    timestamp: Date.now(),
  });

  // 如果在线则立即尝试同步
  if (navigator.onLine) {
    syncNow();
  }
}

async function syncNow() {
  const pending = await db.syncQueue.toArray();
  for (const op of pending) {
    try {
      await fetch('/api/sync', { method: 'POST', body: JSON.stringify(op) });
      await db.syncQueue.delete(op.id);
    } catch (err) {
      // 稍后重试
      break;
    }
  }
}

// 网络恢复时触发同步
window.addEventListener('online', syncNow);

触发时机：网络恢复后或浏览器空闲时自动触发。


浏览器支持：Chrome / Edge 完整支持；Firefox / Safari 支持有限。


最后写入者胜出（LWW）
逻辑：比较时间戳，最新的更新覆盖旧的。


function resolve(local, remote) {
  return local.updatedAt > remote.updatedAt ? local : remote;
}
优点：实现极其简单，行为可预测。


缺点：可能导致更新丢失；存在时钟偏差问题。


适用场景：非关键数据、以追加为主的场景。


操作变换（OT）
Google Docs / Etherpad 使用的方案：服务器协调各客户端的操作，基于并发操作进行变换。


示例：


    

  • 用户 A 在位置 0 插入字符 "X"。
    • 

  • 用户 B 同时在位置 0 插入字符 "Y"。
    • 

  • 服务器进行变换：A 在位置 0 插入，B 的插入位置偏移到 1。
    • 



特点：服务器逻辑复杂，边界情况多。


适用场景：实时协作编辑，服务器权威的场景。


CRDT（无冲突复制数据类型）
核心思想：通过数学结构保证多副本合并后结果一致，无需服务器协调，支持点对点去中心化。


两种类型：


    

  • 基于状态的 CRDT（CvRDT）：合并完整状态。
    • 

  • 基于操作的 CRDT（CmRDT）：合并操作记录。
    • 



常见 CRDT 数据结构：


    

  • G-Counter：只增计数器。
    • 

  • PN-Counter：支持增减的计数器。
    • 

  • LWW-Register：最后写入者胜出寄存器。
    • 

  • OR-Set：可观察移除集合。
    • 

  • Sequence CRDT：文本编辑序列（Yjs、Automerge 使用）。
    • 



优点：自动合并、无需服务器协调、支持点对点。


缺点：实现复杂、内存开销大（需跟踪所有操作）、并非所有数据类型都有对应的 CRDT。


工具库：


    

  • Yjs：JavaScript CRDT 库，被 Liveblocks、JupyterLab 等使用。
    • 

  • Automerge：JavaScript CRDT 库，适用于协作写作应用。
    • 



Yjs 使用示例
import * as Y from 'yjs';
import { WebsocketProvider } from 'y-websocket';

const ydoc = new Y.Doc();
const provider = new WebsocketProvider('wss://example.com', 'room1', ydoc);

// 共享文本
const ytext = ydoc.getText('content');

// 本地编辑自动同步
ytext.insert(0, 'Hello ');
ytext.insert(6, 'World');

// 监听变更
ytext.observe((event) => {
  console.log('内容变更:', ytext.toString());
});
效果：多个客户端实时同步，并发编辑自动合并。


手动合并
冲突界面：让用户选择保留本地版本还是服务器版本，或查看差异后手动编辑。


适合场景：文档编辑、高价值数据。


典型案例：Git 合并冲突界面、Notion 冲突解决。


版本化更新（HTTP 乐观并发控制）
PUT /api/tasks/1
If-Match: "version-3"
{ "title": "New" }
服务器在版本不匹配时返回 412 Precondition Failed。


客户端处理：拉取最新版本，重新应用变更。


PouchDB + CouchDB
同步引擎：PouchDB 在本地使用 IndexedDB，CouchDB 作为远程数据库，自动双向同步。使用 MVCC（多版本并发控制）进行冲突检测——同一文档可能存在多个修订版本，由应用层决定如何解决冲突。


适用场景：已有 CouchDB 基础设施、面向文档的数据模型。


Replicache
现代同步引擎：支持乐观变更（Mutation）、自动通过推拉方式同步、后端无关。


适用场景：现代 Web 应用，与 React / Solid 等框架集成良好。


Liveblocks
商业实时协作服务：基于 CRDT，提供预构建的 React Hooks，支持光标、选区、共享状态等协作功能。


适用场景：快速实现协作功能、跳过 CRDT 的底层实现。


同步模式
最终一致性（Eventual Consistency）：所有客户端最终收敛到一致状态，不保证严格顺序。


强一致性（Strong Consistency）：所有客户端立即看到相同数据，需要服务器协调。


本地优先（Local-first）（现代趋势）：本地数据是唯一真实来源，服务器仅作为同步层。


本地优先软件
Ink & Switch 提出的理念，包含七大理想特性：无缝网络体验、多设备同步、无限撤销、数据所有权、安全性、持久性、真正拥有数据的感觉。


代表产品：Notion（部分）、Linear、Obsidian。


工具支持：Yjs / Automerge / Replicache。


冲突的用户体验
向用户展示冲突：内联差异对比、"你的版本"与"服务器版本"并排显示、合并按钮。


自动解决（透明处理）：用户无感知，CRDT 通常采用这种方式。


状态通知：显示"已同步"、"同步失败，正在重试"等状态，建立用户信任。


同步性能优化
乐观 UI（Optimistic UI）：立即显示变更，后台同步，失败时回滚。


批量同步：一次同步一批操作，而非每个操作都立即同步。


差异压缩：仅同步变更的差异部分，而非完整状态。


分页同步：大数据集使用增量分页同步。


离线优先架构
四个核心步骤：


    

  1. 本地数据库（IndexedDB）作为主存储：所有读写先操作本地。
    2. 

  2. 同步队列跟踪待处理操作：后台异步同步到服务器。
    3. 

  3. 服务器端协调合并：返回权威的合并结果。
    4. 

  4. 本地用服务器数据更新：拉取权威状态保持一致。
    5. 



常见反模式
1. 不处理冲突：最后写入静默覆盖，导致数据丢失。


2. 每次按键都同步：请求过于频繁，应使用批量加防抖。


3. 同步时阻塞界面：未使用乐观 UI，用户体验差。


4. 显示过期数据但不标注：用户会感到困惑。


5. 崩溃时丢失待处理操作：未持久化同步队列。


6. 自己实现 CRDT：极其困难，应使用 Yjs / Automerge 等成熟库。


最佳实践
1. 本地优先：本地数据库作为主存储，服务器作为同步层。


2. 乐观 UI：立即展示变更，提升用户感知速度。


3. 持久化同步队列：确保应用崩溃后待处理操作不丢失。


4. 协作编辑使用 Yjs：不要重新发明 CRDT。


5. 冲突处理要明确：让用户知晓并参与解决。


6. 测试重连场景：使用 DevTools 限速和真实离线环境测试。


小结
离线优先同步让用户断网时仍可编辑，重连时自动协调数据。核心策略包括最后写入者胜出（简单但可能丢数据）、手动合并（用户决定）、操作变换（服务器协调复杂操作）、CRDT（数学保证无冲突合并）、HTTP 版本化乐观并发控制。同步队列应持久化到 IndexedDB，结合 Background Sync API 实现网络恢复后自动同步。CRDT 工具库如 Yjs 和 Automerge 让协作编辑变得可行。本地优先架构以本地数据库为主存储、服务器为同步层，配合乐观 UI 和明确的冲突处理体验，是构建可靠离线优先应用的最佳实践。
