Workbox 与工具链

核心概念

Workbox 是 Google 于 2017 年开源的 Service Worker 工具库，已成为 PWA 开发的事实标准。它将常见的 PWA 模式——预缓存、路由匹配、缓存策略、过期管理、后台同步、更新广播——封装为声明式 API。原始 Service Worker 代码容易冗长且易出错（生命周期管理、缓存版本控制、旧缓存清理等），Workbox 可将生产级 Service Worker 精简到约 50 行代码。Workbox 分为多个独立模块，按需引入以减小打包体积。

Workbox 的设计理念是将经过社区验证的最佳实践封装为可复用的模块。开发者无需从零开始实现缓存策略、过期管理、预缓存等复杂逻辑，只需通过简单的配置就能获得生产级的 Service Worker 能力。这种方式大幅降低了 PWA 的开发门槛，同时也减少了因手动实现导致的各种错误和安全风险。

模块 用途
workbox-precaching 预缓存构建产物
workbox-routing URL 模式匹配与路由
workbox-strategies 缓存优先、网络优先等策略类
workbox-expiration 缓存过期与容量限制
workbox-background-sync 失败 POST 请求自动重试
workbox-broadcast-update 通知页面缓存已更新
workbox-cacheable-response 按状态码/响应头过滤可缓存内容
workbox-range-requests 视频分片请求支持
workbox-google-analytics 离线分析数据收集

每个模块都是独立的 npm 包，开发者可以按需引入需要的模块，避免加载不必要的代码。这种模块化设计使得最终的 Service Worker 文件体积可控，同时保持了功能的完整性和灵活性。

Workbox 与原始 Service Worker 对比

原始 Service Worker：

使用原始 Service Worker API 开发缓存逻辑时，开发者需要手动处理所有细节。缓存版本控制、旧缓存清理、缓存过期管理、错误处理等都需要从零开始编写。这种方式虽然提供了最大的灵活性，但代码量大、容易出错，生产级的实现通常需要 200 行以上的代码，且需要深入理解 Service Worker 的生命周期和各种边界情况。

  • 完全手动控制。
  • 需手写缓存版本控制。
  • 需手写过期逻辑。
  • 生产级代码约 200 行以上。

Workbox：

使用 Workbox 后，开发者只需通过声明式的配置来描述想要实现的缓存行为，Workbox 会自动处理所有底层细节。这种方式大幅简化了代码量，同时利用了经过充分测试的模式封装，降低了出错的可能性。Workbox 由 Google Chrome 团队持续维护，保证了代码质量和对新浏览器特性的支持。

  • 声明式配置。
  • 经过充分测试的模式封装。
  • 生产级代码约 50 行。
  • 持续活跃维护。

建议：除了学习目的，生产环境推荐使用 Workbox。对于初学者来说，建议先理解原始 Service Worker 的工作原理和各种缓存策略的逻辑，然后在实际项目中使用 Workbox 来简化开发工作。

两种配置模式

Workbox 提供了两种截然不同的配置模式，适用于不同复杂度的项目需求。理解两种模式的区别和适用场景，对于正确使用 Workbox 至关重要。

1. generateSW（自动生成模式）：

自动生成模式是最简单的使用方式。Workbox 根据开发者提供的配置参数，自动生成一个完整的 Service Worker 文件。开发者无需手写任何 Service Worker 代码，只需要指定需要预缓存的资源模式、运行时缓存规则等配置项，Workbox 就会生成一个功能完整的 Service Worker。

  • Workbox 根据配置自动生成完整的 Service Worker 文件。
  • 通过构建脚本或插件配置参数。
  • 无需手写 Service Worker 代码。
  • 适合简单的 PWA 场景。

2. injectManifest（注入清单模式）：

注入清单模式适合需要自定义逻辑的复杂场景。开发者自己编写 Service Worker 代码，可以包含任何自定义的事件处理器、消息监听、路由逻辑等。Workbox 的角色仅限于在构建时将预缓存清单（__WB_MANIFEST）注入到开发者编写的 Service Worker 文件中。这种方式保持了完全的灵活性，同时享受 Workbox 的预缓存管理能力。

  • 开发者自己编写 Service Worker 代码。
  • Workbox 仅负责注入预缓存清单（__WB_MANIFEST）。
  • 保持完全灵活性。
  • 适合需要自定义逻辑的场景。

选择建议：

选择哪种模式取决于项目的复杂度和自定义需求。对于简单的静态网站或博客，generateSW 模式通常就够用了。但如果项目需要自定义的离线回退页面、复杂的路由逻辑、自定义的消息通信等，应该选择 injectManifest 模式。

  • 简单 PWA → generateSW。
  • 复杂业务逻辑 / 自定义需求 → injectManifest。

Vite + vite-plugin-pwa

Vite 是现代前端项目最流行的构建工具之一，通过 vite-plugin-pwa 插件可以快速集成 Workbox 和 PWA 能力。这个插件封装了 Workbox 的配置细节，提供了开箱即用的 PWA 支持。

安装：

通过 npm 安装 vite-plugin-pwa 作为开发依赖，这个插件会自动处理 Workbox 的引入和配置工作。

npm i -D vite-plugin-pwa

配置：

下面的配置展示了 vite-plugin-pwa 的典型用法。registerType 决定了 Service Worker 的更新策略，strategies 决定使用 generateSW 还是 injectManifest 模式。workbox 对象包含了缓存相关的配置，manifest 对象定义了 Web App Manifest 清单文件的内容。

// vite.config.js
import { VitePWA } from 'vite-plugin-pwa';

export default {
  plugins: [
    VitePWA({
      registerType: 'autoUpdate',
      strategies: 'injectManifest', // 或 'generateSW'
      srcDir: 'src',
      filename: 'sw.ts',

      // generateSW 模式配置
      workbox: {
        globPatterns: ['**/*.{js,css,html,png,svg,woff2}'],
        runtimeCaching: [
          {
            urlPattern: ({ request }) => request.mode === 'navigate',
            handler: 'NetworkFirst',
            options: { cacheName: 'pages' },
          },
        ],
      },

      manifest: {
        name: 'My App',
        short_name: 'MyApp',
        theme_color: '#3b82f6',
        icons: [{ src: '/icon-192.png', sizes: '192x192', type: 'image/png' }],
      },
    }),
  ],
};

自动生成内容：

vite-plugin-pwa 会自动生成以下内容，开发者无需手动创建。Web App Manifest 清单文件定义了应用的名称、图标、主题色等信息。Service Worker 包含了预缓存和运行时缓存配置。更新提示组件提供了用户友好的更新通知界面。

  • Web App Manifest 清单文件。
  • 包含预缓存和运行时缓存配置的 Service Worker。
  • 更新提示 UI 组件。

Next.js + next-pwa

Next.js 是 React 生态中最流行的全栈框架，通过 next-pwa 插件可以快速为 Next.js 应用添加 PWA 能力。这个插件基于 Workbox，提供了与 Next.js 深度集成的 PWA 支持。

安装：

通过 npm 安装 next-pwa 作为项目依赖。

npm i next-pwa

配置：

下面的配置展示了 next-pwa 的典型用法。dest 指定了 Service Worker 文件的输出目录，register 控制是否自动注册 Service Worker，skipWaiting 决定新版本是否立即激活。在开发环境下通常禁用 PWA 功能，避免干扰开发调试工作。

// next.config.js
const withPWA = require('next-pwa')({
  dest: 'public',
  register: true,
  skipWaiting: true,
  disable: process.env.NODE_ENV === 'development',
});

module.exports = withPWA({
  reactStrictMode: true,
});

next-pwa 会自动生成 Service Worker 和清单文件，与 Next.js 的路由系统深度集成，支持页面级别的缓存策略配置。

自定义 Service Worker（injectManifest 模式）

使用 injectManifest 模式时，开发者拥有对 Service Worker 的完全控制权。下面的代码展示了一个完整的自定义 Service Worker，包含预缓存、页面路由、静态资源缓存、图片缓存、API 缓存和消息驱动跳过等待等功能。每个功能模块都使用了 Workbox 提供的策略类和插件，组合成一个功能完整的 Service Worker。

这种方式的优势在于开发者可以精确控制每种资源的缓存行为。预缓存负责关键资源的提前下载，导航路由确保 HTML 页面始终从网络获取最新版本，静态资源和图片使用缓存优先提供极快的响应，API 请求使用过期重验证兼顾速度与新鲜度。

// sw.js
import { precacheAndRoute, cleanupOutdatedCaches } from 'workbox-precaching';
import { registerRoute, NavigationRoute } from 'workbox-routing';
import { CacheFirst, NetworkFirst, StaleWhileRevalidate } from 'workbox-strategies';
import { ExpirationPlugin } from 'workbox-expiration';
import { CacheableResponsePlugin } from 'workbox-cacheable-response';

// 1. 预缓存（由 Workbox 构建注入清单）
precacheAndRoute(self.__WB_MANIFEST);
cleanupOutdatedCaches();

// 2. HTML 页面路由
registerRoute(
  new NavigationRoute(
    new NetworkFirst({
      cacheName: 'pages',
      plugins: [new CacheableResponsePlugin({ statuses: [200] })],
    }),
  ),
);

// 3. CSS / JS 静态资源
registerRoute(
  ({ request }) => request.destination === 'style' || request.destination === 'script',
  new CacheFirst({ cacheName: 'static' }),
);

// 4. 图片资源
registerRoute(
  ({ request }) => request.destination === 'image',
  new CacheFirst({
    cacheName: 'images',
    plugins: [
      new ExpirationPlugin({
        maxEntries: 60,
        maxAgeSeconds: 30 * 24 * 60 * 60, // 30 天
      }),
    ],
  }),
);

// 5. API 请求
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/'),
  new StaleWhileRevalidate({
    cacheName: 'api',
    plugins: [new ExpirationPlugin({ maxAgeSeconds: 5 * 60 })],
  }),
);

// 6. 跳过等待 + 接管客户端
self.addEventListener('message', (event) => {
  if (event.data?.type === 'SKIP_WAITING') {
    self.skipWaiting();
  }
});

下面的流程图展示了这个自定义 Service Worker 的整体架构。各个功能模块之间相互独立，通过 Workbox 的路由系统协调工作。预缓存在安装阶段处理构建产物，运行时路由在请求发生时根据规则选择合适的策略。

预缓存详解
在安装阶段预缓存资源：


预缓存是 Workbox 的核心功能之一，它允许开发者在 Service Worker 安装阶段一次性下载并缓存一组已知的资源。这些资源通常是构建产物，如 JavaScript、CSS、字体等文件。预缓存确保了这些关键资源在用户首次访问后立即可以离线使用，无需等待用户再次访问才触发缓存。


import { precacheAndRoute } from 'workbox-precaching';

precacheAndRoute([
  { url: '/', revision: 'abc123' },
  { url: '/styles.css', revision: 'def456' },
]);
__WB_MANIFEST 由 Workbox 构建工具在打包时注入——包含所有构建产物的 URL 和修订哈希列表。修订哈希用于检测资源是否有变化，只有哈希变化的资源才会被重新下载，避免不必要的网络请求。


效果：


预缓存的工作效果是确保关键资源始终可用。安装事件触发时下载并缓存所有清单中的资源，后续匹配的网络请求直接返回预缓存内容。新构建产生新的修订哈希时，Workbox 自动识别并重新缓存更新的资源，删除不再需要的旧版本。


    

  • 安装事件时下载并缓存这些资源。
    • 

  • 后续匹配的网络请求直接返回预缓存内容。
    • 

  • 新构建产生新清单，自动失效旧版本。
    • 



路由匹配
URL 模式匹配方式：


Workbox 的路由系统支持多种匹配方式，开发者可以根据需求选择最合适的匹配规则。正则表达式匹配适合基于文件扩展名或路径模式的规则，函数匹配提供了最大的灵活性，请求类型匹配则利用了浏览器的资源类型标识。


// 正则匹配
registerRoute(/\.(png|jpg|webp)$/, new CacheFirst());

// 函数匹配
registerRoute(({ url }) => url.pathname.startsWith('/api/'), new NetworkFirst());

// 请求类型匹配
registerRoute(({ request }) => request.destination === 'image', new CacheFirst());
NavigationRoute：


NavigationRoute 是 Workbox 提供的专门处理导航请求的路由类型。导航请求指的是用户通过地址栏输入 URL、点击链接或前进后退导航产生的 HTML 页面请求。在单页应用中，NavigationRoute 通常用于将所有导航请求路由到预缓存的应用外壳 HTML。


    

  • 专门处理导航请求（HTML 页面）。
    • 

  • 用于 SPA 的应用外壳分发。
    • 



策略类详解
CacheFirst（缓存优先）：


缓存优先策略优先从缓存读取，缓存未命中时再请求网络。下面的配置展示了如何组合使用多个插件来增强策略的能力。CacheableResponsePlugin 用于过滤可缓存的响应（只缓存状态码为 0 或 200 的响应），ExpirationPlugin 用于限制缓存条目数量。


new CacheFirst({
  cacheName: 'static',
  plugins: [new CacheableResponsePlugin({ statuses: [0, 200] }), new ExpirationPlugin({ maxEntries: 60 })],
});
NetworkFirst（网络优先）：


网络优先策略优先请求网络，网络不可用时使用缓存。networkTimeoutSeconds 参数设置了网络请求的超时时间，超过这个时间后自动回退到缓存，避免用户在弱网环境下长时间等待。


new NetworkFirst({
  cacheName: 'pages',
  networkTimeoutSeconds: 3,
});
StaleWhileRevalidate（过期重验证）：


过期重验证策略立即返回缓存内容，同时在后台发起网络请求更新缓存。这种策略提供了最佳的响应速度和数据新鲜度的平衡，是大多数场景的推荐默认策略。


new StaleWhileRevalidate({ cacheName: 'api' });
NetworkOnly（仅网络） 和 CacheOnly（仅缓存）：


仅网络策略完全绕过缓存，适合变更操作和实时数据。仅缓存策略完全依赖缓存，适合预缓存的不可变资源。两者都是简单直接的策略，适用于明确知道数据特性的场景。


new NetworkOnly();
new CacheOnly({ cacheName: 'static' });
过期控制插件
限制缓存大小和存储时间：


ExpirationPlugin 是 Workbox 中最常用的插件之一，它能够自动管理缓存的生命周期。通过设置 maxEntries 限制最大条目数和 maxAgeSeconds 限制最大存储时间，可以有效防止缓存无限增长。purgeOnQuotaError 选项在存储配额耗尽时自动清除缓存，避免因配额不足导致新的缓存写入失败。


new ExpirationPlugin({
  maxEntries: 60, // 最大条目数
  maxAgeSeconds: 30 * 86400, // 30 天
  purgeOnQuotaError: true, // 存储满时清除
});
自动清理：超龄条目自动删除，存储容量可控。开发者无需手动编写清理逻辑，ExpirationPlugin 会在每次缓存写入时自动检查并清理过期或超出限制的条目。


可缓存响应插件
仅缓存特定状态码或响应头的响应：


CacheableResponsePlugin 插件用于控制哪些响应可以被缓存。并非所有响应都适合缓存，例如服务器错误响应（5xx）或重定向响应（3xx）通常不应该被缓存。通过设置允许缓存的状态码和响应头条件，可以确保只有有效的响应被写入缓存。


new CacheableResponsePlugin({
  statuses: [0, 200], // 200 成功 + 0 不透明跨域响应
  headers: { 'X-Cache': 'true' },
});
状态码 0 表示不透明的跨域响应，虽然无法读取其内容，但仍然可以缓存。200 表示成功响应，是最常见的可缓存状态码。通过响应头条件，开发者可以实现更精细的缓存控制，例如只缓存带有特定标记的响应。


后台同步插件
失败的 POST 请求自动重试：


BackgroundSyncPlugin 是 Workbox 提供的后台同步插件，它可以自动捕获失败的网络请求并在网络恢复后重试。这对于离线场景下的表单提交、数据上传等场景非常有用。当用户在离线状态下提交数据时，请求会被暂存到 IndexedDB 队列中，等网络恢复后自动重新发送。


import { BackgroundSyncPlugin } from 'workbox-background-sync';

const bgSyncPlugin = new BackgroundSyncPlugin('apiQueue', {
  maxRetentionTime: 24 * 60, // 保留 24 小时
});

registerRoute(({ url }) => url.pathname.startsWith('/api/'), new NetworkOnly({ plugins: [bgSyncPlugin] }), 'POST');
效果：POST 请求失败后进入队列，网络恢复后自动重试。maxRetentionTime 参数控制请求在队列中的最大保留时间，超过这个时间的请求会被自动丢弃，避免发送过于陈旧的数据。


广播更新插件
缓存更新时通知页面：


BroadcastUpdatePlugin 是 Workbox 提供的缓存更新通知机制。当使用过期重验证策略时，后台网络请求可能获取到了新的内容。这个插件会在缓存被更新时通过 BroadcastChannel 通知所有打开的页面，让页面有机会提示用户刷新以获取最新内容。


import { BroadcastUpdatePlugin } from 'workbox-broadcast-update';

new StaleWhileRevalidate({
  plugins: [new BroadcastUpdatePlugin()],
});
页面监听：


在页面中监听来自 Service Worker 的广播消息，当接收到缓存更新的通知时，可以显示一个刷新提示，让用户自行决定是否刷新页面。这种方式尊重了用户的选择，避免了自动刷新导致用户工作中断的问题。


navigator.serviceWorker.addEventListener('message', (event) => {
  if (event.data.meta === 'workbox-broadcast-update') {
    showRefreshNotification();
  }
});
Workbox CLI
独立于框架的 Service Worker 生成工具：


Workbox CLI 是一个命令行工具，可以在不依赖任何前端框架的情况下生成 Service Worker。对于不使用 Webpack、Vite 等现代构建工具的项目，Workbox CLI 提供了一种简单的方式来添加 PWA 能力。workbox wizard 命令提供了交互式的配置向导，帮助开发者快速生成配置文件。


npm i -D workbox-cli
npx workbox wizard        # 交互式初始化配置
npx workbox generateSW workbox-config.js  # 生成 SW
跳过等待与更新通知
Service Worker 的更新机制默认比较保守，新版本安装后需要等待所有使用旧版本的标签页关闭才会激活。这种机制虽然安全，但可能导致用户长时间使用旧版本。Workbox 提供了多种方式来控制更新行为。


自动跳过等待：


最简单的方式是在 Service Worker 中直接调用 skipWaiting()，新版本安装后立即激活，不等待旧标签页关闭。但这种方式可能导致用户在操作过程中被中断。


self.skipWaiting();
消息驱动跳过（推荐）：


更好的方式是通过消息机制，让页面在合适的时机（如用户点击"更新"按钮后）通知 Service Worker 跳过等待。这种方式给予用户选择权，避免了突然的更新中断用户当前操作。


self.addEventListener('message', (event) => {
  if (event.data?.type === 'SKIP_WAITING') {
    self.skipWaiting();
  }
});
更新提示 UI 示例（React）：


下面的 React 组件展示了如何使用 vite-plugin-pwa 提供的 useRegisterSW 钩子来检测更新并显示提示。当检测到新版本可用时，显示一个更新横幅，用户点击后触发 Service Worker 更新和页面刷新。


import { useRegisterSW } from 'virtual:pwa-register/react';

function App() {
  const { needRefresh, updateServiceWorker } = useRegisterSW();

  return (
    <>
      {needRefresh && <UpdateBanner onClick={() => updateServiceWorker(true)} />}
      <App />
    </>
  );
}
现代框架集成
主流前端框架均提供 Workbox 集成方案：


各个现代前端框架都有官方或社区维护的 Workbox 集成插件，这些插件将 Workbox 的能力与框架的构建系统深度结合，提供了开箱即用的 PWA 支持。开发者只需安装插件并配置少量选项，即可获得完整的 Service Worker 能力。


    

  • Next.js（next-pwa）：支持按页面路由配置缓存策略。
    • 

  • Vite（vite-plugin-pwa）：支持 TypeScript 和热模块替换。
    • 

  • Remix：内置对 Service Worker 的支持。
    • 

  • SvelteKit：通过适配器支持 PWA 能力。
    • 

  • Nuxt（nuxt-pwa）：Vue 生态的 PWA 解决方案。
    • 



各框架有各自的集成插件，但底层都基于 Workbox。选择哪个框架的集成方案取决于项目的技术栈，核心的缓存策略和配置理念是相通的。


常见反模式
1. 生产环境使用原始 Service Worker：


直接在生产环境使用原始 Service Worker 代码容易出错，缓存失效、版本控制、过期管理等细节很容易遗漏。应使用 Workbox 来获得经过充分测试的缓存逻辑，避免因手动实现导致的各种问题。


2. 不设置过期策略：


缓存如果没有过期策略，会无限增长，最终占满浏览器分配的存储配额。应该始终为运行时缓存配置 ExpirationPlugin，设置合理的条目数和存储时间限制。


3. 不限制最大条目数：


即使设置了过期时间，如果不限制最大条目数，在短时间内大量请求可能导致缓存快速增长。应该同时设置 maxEntries 和 maxAgeSeconds，双重保护避免存储空间被耗尽。


4. 跳过等待但不通知用户：


使用 skipWaiting() 后 Service Worker 会立即接管页面，但如果新版本的缓存结构与页面不兼容，可能导致用户操作中途被中断或出现错误。应该在跳过等待前通知用户，让用户选择合适的时机刷新。


5. 不预缓存关键资源：


如果不预缓存应用外壳和关键资源，首次访问时需要等待所有资源从网络加载完成，无法立即支持离线使用。应该将关键的应用外壳资源（HTML、CSS、核心 JS）加入预缓存清单。


6. 不提示更新：


如果部署新版本后不主动检测和提示更新，用户可能长时间停留在旧版本。应该实现更新检测和通知机制，确保用户能够及时获取到新版本的功能和修复。


小结
Workbox 是 Service Worker 开发的行业标准工具——将复杂的 PWA 模式封装为声明式 API，让生产级 Service Worker 仅需约 50 行配置。它提供两种配置模式：generateSW 适合简单场景自动生成，injectManifest 适合需要自定义逻辑的复杂场景。配合 vite-plugin-pwa、next-pwa 等框架插件，可快速集成到现代前端项目中。其插件体系——过期控制、可缓存响应过滤、后台同步重试、广播更新通知——覆盖了 PWA 缓存工程的所有常见需求。


在实际项目中，建议优先使用 Workbox 而非手写原始 Service Worker 代码。Workbox 经过了大量生产环境的验证，代码质量高且持续维护。通过合理配置预缓存、运行时缓存策略和各种插件，开发者可以快速构建出性能优异、离线可用、更新流畅的 PWA 应用。
