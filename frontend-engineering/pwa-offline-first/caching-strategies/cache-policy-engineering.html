缓存策略工程化

核心概念

选好策略只是第一步。策略要真正在生产环境稳定运行，还需要回答一组工程问题：请求该被路由到哪条策略、缓存叫什么名字、怎么随版本更新、能占多少空间、遇到认证和跨域请求怎么办、过期由谁清理、以及如何用工具库替代手写实现。

  • 按资源类型路由：把请求按 mode、路径与 destination 分发到不同策略，是策略从概念走向配置的第一步。
  • 命名与版本：版本化缓存名称让新版本部署后旧缓存能被自动清理；按资源类型分离缓存让失效可以精确到某一类。
  • 容量与配额：浏览器按源分配配额并采用 LRU 驱逐，需要主动设置上限而非依赖自动管理。
  • 边界陷阱：认证请求的缓存键不含用户信息，可能造成跨用户串数据；跨域不透明响应上报大小为 0，会误导配额计算。
  • 工具化：Workbox 把上述工程细节封装为声明式 API 与插件，过期控制插件负责回答"缓存条目何时该消失"。

下表把上述工程关注点整理为可逐条对照的清单：

工程关注点 做法 要避免的风险
按资源类型路由 按 mode、路径与 destination 把请求分发到不同策略 所有请求走同一条策略，导致过时或缓慢
命名与版本 版本化缓存名称，并按资源类型分离缓存 新版本部署后旧缓存无法被自动清理
容量与配额 主动设置上限，而非依赖浏览器自动管理 浏览器按 LRU 驱逐最旧条目，重要缓存被清掉
认证请求 不缓存带认证的 API，或在缓存键中包含用户 ID 缓存键不含用户信息，造成跨用户串数据
跨域请求 需要完整内容时使用 mode: 'cors' 不透明响应上报大小为 0，误导配额计算
过期控制 用过期控制插件回答"条目何时该消失" 缓存条目无限增长，耗尽配额

按资源类型选择策略

实战 Service Worker 配置：

在实际项目中，不同类型的资源应该使用不同的缓存策略。下面的代码展示了一个完整的 Service Worker 配置示例，根据请求的资源类型自动选择合适的缓存策略。HTML 页面使用网络优先策略确保用户看到最新内容，静态资源使用缓存优先策略保证快速加载，API 请求使用过期重验证策略兼顾速度与新鲜度，图片资源同样使用缓存优先策略。

下面的实现首先解析请求 URL，然后根据请求的类型和路径选择相应的策略。对于导航请求（HTML 页面），使用网络优先策略；对于 JavaScript、CSS、字体等静态资源，使用缓存优先策略；对于 API 请求，使用过期重验证策略；对于图片资源，同样使用缓存优先策略。这种方式能够为不同类型的资源提供最优的缓存策略。

self.addEventListener('fetch', (event) => {
  const url = new URL(event.request.url);

  // HTML 页面 → 网络优先
  if (event.request.mode === 'navigate') {
    event.respondWith(networkFirst(event.request));
  }

  // 静态资源 → 缓存优先
  if (/\.(js|css|woff2)$/.test(url.pathname)) {
    event.respondWith(cacheFirst(event.request));
  }

  // API 请求 → 过期重验证
  if (url.pathname.startsWith('/api/')) {
    event.respondWith(staleWhileRevalidate(event.request));
  }

  // 图片 → 缓存优先
  if (/\.(png|jpg|webp)$/.test(url.pathname)) {
    event.respondWith(cacheFirst(event.request));
  }
});

下面的流程图清晰地展示了按资源类型选择策略的决策过程。当请求到达时，首先判断资源类型，然后路由到相应的缓存策略。HTML 页面走网络优先路径，静态资源走缓存优先路径，API 请求走过期重验证路径，POST 请求走仅网络路径。这种分层策略能够为不同类型的资源提供最优的处理方式。

缓存命名与版本控制

版本化缓存名称：

在实际项目中，使用版本化的缓存名称是管理缓存的重要手段。下面的代码展示了如何定义版本化的缓存名称，将缓存名称与版本号结合，方便在部署新版本时自动清理旧缓存。不同的资源类型使用不同的缓存名称，便于独立管理和失效。静态资源缓存、API 缓存、图片缓存分开存储，各有各的生命周期和更新策略。

const CACHE_VERSION = 'v3';
const STATIC_CACHE = `static-${CACHE_VERSION}`;
const API_CACHE = `api-${CACHE_VERSION}`;
const IMAGE_CACHE = `image-${CACHE_VERSION}`;

不同资源不同生命周期：

不同类型的资源应该有不同的缓存生命周期。静态资源如 JavaScript、CSS、字体文件，由于使用哈希文件名，可以长期缓存，直到新版本部署。API 数据通常需要较短的生命周期，确保用户能看到较新的内容。图片资源的生命周期介于两者之间，通常设置中等长度的缓存周期。

  • 静态资源：长期缓存。
  • API 数据：短生命周期。
  • 图片：长期缓存。

在 activate 事件中清理旧缓存：

当新版本的 Service Worker 激活时，应该清理旧版本的缓存以释放存储空间。下面的代码展示了如何在 activate 事件中删除所有不以当前版本号结尾的缓存。这种方式确保了每次部署新版本时，旧缓存会被自动清理，避免存储空间被无用的旧缓存占用。

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((names) => {
      return Promise.all(names.filter((name) => !name.endsWith(CACHE_VERSION)).map((name) => caches.delete(name)));
    }),
  );
});

缓存容量限制

浏览器配额：

浏览器对每个源（origin）的缓存容量都有限制，通常约为磁盘空间的百分之五十左右。这个配额是按源分配的，同一源下的所有缓存（包括 Cache API 和 IndexedDB）共享这个配额。当缓存超出配额时，浏览器会根据最近最少使用（LRU）策略自动驱逐最旧的缓存条目，为新的缓存腾出空间。

  • 默认约占磁盘空间的 50%。
  • 按源（origin）分配。
  • 超出配额时浏览器会驱逐最旧的缓存。

手动限制缓存大小：

除了依赖浏览器的自动管理，开发者也可以主动限制缓存的大小。下面的代码展示了如何手动限制缓存条目数量，当缓存中的条目超过预设的最大值时，删除最旧的条目。这种方式能够更精确地控制缓存占用的存储空间，避免缓存无限增长导致超出配额。

async function trimCache(cacheName, maxItem) {
  const cache = await caches.open(cacheName);
  const keys = await cache.keys();
  if (keys.length > maxItem) {
    await cache.delete(keys[0]);
    trimCache(cacheName, maxItem);
  }
}

认证请求的缓存

注意事项：

缓存带认证的请求时需要特别小心。认证头（Authorization）通常包含用户的身份信息，不同用户的认证信息不同。如果简单地缓存带认证的响应，可能导致用户 A 的数据被用户 B 看到，造成严重的安全问题。默认情况下，缓存键只包含请求的 URL 和方法，不包含认证头等用户特定的信息。

  • 认证头（Authorization）因用户而异。
  • 默认缓存不区分用户。
  • 可能导致 A 用户的数据被 B 用户看到。

解决方案：

针对认证请求的缓存问题，有两种主要的解决方案。第一种是干脆不缓存带认证的 API 请求，让这类请求始终走网络，虽然牺牲了一些性能，但保证了安全性。第二种方案是在缓存键中包含用户 ID 等用户特定的信息，这样不同用户的响应会被存储在不同的缓存条目中，互不干扰。

  • 不缓存带认证的 API 请求。
  • 或在缓存键中包含用户 ID。

跨域请求与缓存

跨域请求特殊性：

跨域请求在 Service Worker 中有一些特殊的限制。默认情况下，Service Worker 无法读取跨域响应的内容，这种响应被称为不透明响应（Opaque Response）。虽然可以缓存不透明响应，但无法获知响应的实际大小，这可能导致配额计算不准确。如果需要完整访问跨域响应的内容，需要使用 mode: 'cors' 来发起跨域请求。

  • Service Worker 默认无法读取跨域响应体（不透明响应）。
  • 可以缓存不透明响应，但无法获知实际大小。
  • 使用 mode: 'cors' 来获取完整的跨域响应。

Workbox 策略抽象

Workbox 库将上述策略封装为声明式 API：

Workbox 是 Google 开源的 Service Worker 工具库，它将各种缓存策略封装成声明式的 API，大大简化了 Service Worker 的开发。下面的代码展示了如何使用 Workbox 快速配置缓存策略。首先使用 precacheAndRoute() 预缓存构建产物，然后使用 registerRoute() 注册各种路由规则，每种规则使用相应的策略类。Workbox 的代码更加简洁，经过充分测试，且有良好的社区维护。

import { precacheAndRoute } from 'workbox-precaching';
import { registerRoute } from 'workbox-routing';
import { CacheFirst, NetworkFirst, StaleWhileRevalidate, NetworkOnly } from 'workbox-strategies';

precacheAndRoute(self.__WB_MANIFEST);

registerRoute(({ request }) => request.mode === 'navigate', new NetworkFirst({ cacheName: 'pages' }));

registerRoute(({ url }) => url.pathname.startsWith('/api/'), new StaleWhileRevalidate({ cacheName: 'api' }));

registerRoute(({ request }) => request.destination === 'image', new CacheFirst({ cacheName: 'images' }));

Workbox 代码更简洁、经过充分测试、且有良好的社区维护。使用 Workbox 可以避免手动实现缓存策略时容易出现的各种错误，同时代码也更易于维护和理解。

缓存过期控制

Workbox 过期插件：

Workbox 提供了 ExpirationPlugin 插件来自动管理缓存的过期。下面的代码展示了如何配置过期插件，设置最大条目数和最大存储时间。超过最大条目数的旧条目会被自动删除，存储时间超过最大存储时间的条目也会被自动清理。这种方式能够有效防止缓存无限增长，确保存储空间得到合理利用。

import { ExpirationPlugin } from 'workbox-expiration';

new CacheFirst({
  cacheName: 'images',
  plugins: [
    new ExpirationPlugin({
      maxEntries: 60,
      maxAgeSeconds: 30 * 24 * 60 * 60, // 30 天
    }),
  ],
});

自动清理：

Workbox 的过期插件会自动清理超龄条目，开发者可以同时限制条目数量和存储时间，实现精细化的缓存管理。这种方式比手动实现清理逻辑更加可靠和高效，是生产环境推荐的做法。

  • 超龄条目自动删除。
  • 可同时限制条目数量和存储时间。

常见误区

1. 对 HTML 使用缓存优先：

对 HTML 页面使用缓存优先策略是一个非常常见的错误。HTML 是应用的入口，如果被长期缓存，用户将无法获取到最新版本的应用，可能停留在旧版本很长一段时间。正确的做法是对 HTML 使用网络优先或过期重验证策略，确保用户总能获取到最新的 HTML，从而获得最新的资源引用。

  • 用户将永远看到旧页面。
  • 应使用网络优先或过期重验证。

2. 从不刷新缓存：

另一个常见错误是部署新版本后从不主动刷新缓存。这导致用户可能长时间停留在旧版本，无法体验到新功能或修复的 bug。应该使用版本化的缓存名称，在部署新版本时更新版本号，让 Service Worker 在激活时清理旧缓存。

  • 部署新版本后用户仍看到旧版。
  • 应使用版本化缓存名称。

3. 缓存 POST 请求：

POST 请求通常用于变更操作，会改变服务器状态，不应该被缓存。如果缓存了 POST 请求的响应，可能导致用户的变更操作被重复执行，造成数据不一致。POST 请求应该使用仅网络策略，确保每次请求都被正确处理。

  • POST 应始终走网络。
  • 不应缓存变更操作。

4. 所有资源使用同一个缓存：

将所有资源存储在同一个缓存中会导致难以按需失效。不同类型的资源有不同的更新频率和生命周期，应该分开存储在不同的缓存中。这样当需要更新某一类资源时，可以只清理对应的缓存，而不影响其他类型的资源。

  • 难以按需失效。
  • 应按资源类型分开缓存。

5. 不控制缓存大小：

如果不主动控制缓存大小，缓存可能会无限增长，最终超出浏览器的存储配额。当超出配额时，浏览器会随机驱逐缓存条目，可能导致重要的缓存被清理。应该设置缓存容量上限，通过过期插件或手动清理机制控制缓存大小。

  • 浏览器会随机驱逐缓存。
  • 应设置缓存容量上限。

6. 不透明响应的大小误判：

跨域的不透明响应在上报大小时为 0，但实际仍然占用存储空间。如果大量缓存不透明响应，可能导致配额计算不准确，最终超出实际可用的存储空间。应该尽量避免缓存大量不透明响应，或者在计算配额时考虑这个因素。

  • 跨域响应上报大小为 0，实际占用空间。
  • 可能导致配额计算不准确。

最佳实践

1. 按资源类型选择策略：不同资源用不同缓存和策略。静态资源用缓存优先，API 数据用过期重验证或网络优先，POST 请求用仅网络。这种分层策略能够为不同类型的资源提供最优的处理方式。

2. 版本化缓存名称：部署时更新版本号。每次部署新版本时，更新缓存名称中的版本号，让 Service Worker 在激活时自动清理旧缓存，确保用户能够获取到最新版本的内容。

3. 使用 Workbox：经过验证的策略封装。Workbox 是经过充分测试和社区验证的工具库，使用它可以避免手动实现缓存策略时容易出现的各种错误，同时代码也更简洁易维护。

4. 设置过期策略：自动清理过期缓存。使用过期插件或手动清理机制，确保缓存不会无限增长，存储空间得到合理利用。

5. 测试离线场景：使用 DevTools 的离线模式。在开发过程中应该充分测试离线场景，确保缓存的资源能够支撑应用在离线状态下正常运行，用户体验不会因为离线而严重下降。

6. 监控缓存大小：通过 navigator.storage.estimate() 检查。定期检查缓存的实际使用量和剩余配额，及时发现和解决缓存过大或配额不足的问题。

实战案例

新闻网站：

新闻网站的缓存策略需要平衡内容的实时性和访问速度。HTML 页面使用网络优先策略，确保用户看到最新的文章列表。文章正文使用过期重验证策略，缓存内容提供快速访问，后台刷新保持新鲜。图片使用缓存优先策略长期有效。评论 API 使用仅网络策略，确保用户总能看到最新评论。

  • HTML：网络优先（获取最新文章）。
  • 文章正文：过期重验证（缓存 + 后台刷新）。
  • 图片：缓存优先（长期有效）。
  • 评论 API：仅网络（获取最新评论）。

电商网站：

电商网站对性能和数据新鲜度都有较高要求。商品页面使用过期重验证策略，缓存商品信息提供快速访问，后台刷新价格和库存。商品图片使用缓存优先策略长期缓存。购物车 API 使用仅网络策略，确保库存和价格实时准确。搜索使用带超时的网络优先策略，平衡新鲜度和响应速度。

  • 商品页：过期重验证。
  • 商品图片：缓存优先。
  • 购物车 API：仅网络。
  • 搜索：带超时的网络优先。

SaaS 后台：

SaaS 后台应用通常有固定的应用外壳和动态的业务数据。应用外壳使用缓存优先策略，提供快速的应用启动体验。仪表盘数据使用网络优先策略，因为数据新鲜度对业务决策至关重要。用户头像使用缓存优先策略长期缓存。变更操作使用仅网络策略，确保数据一致性。

  • 应用外壳：缓存优先。
  • 仪表盘数据：网络优先（数据新鲜度关键）。
  • 用户头像：缓存优先。
  • 变更操作：仅网络。

小结

本篇列出的工程机制——按资源类型路由、版本化命名、容量上限、认证与跨域处理、Workbox 抽象与过期控制——共同回答一个问题：如何让缓存随时间和规模推移而保持可控。文末的常见误区与六条最佳实践，是上线前最值得逐条核对的项目。
