缓存策略

核心概念

Service Worker 的 fetch 事件处理器拦截每一个网络请求，可以选择从缓存返回、从网络获取、或两者结合。五个核心缓存策略覆盖了几乎所有场景：缓存优先（Cache-first，适合离线友好的静态资源）、网络优先（Network-first，适合需要最新数据的请求）、过期重验证（Stale-while-revalidate，兼顾速度与新鲜度）、仅网络（Network-only，适合 POST 变更请求）、仅缓存（Cache-only，适合不可变的构建产物）。选错策略会导致缓存永远过时或响应始终缓慢，因此理解每种策略的适用场景至关重要。

理解这些策略的本质非常重要。缓存优先策略意味着尽可能从缓存中获取资源，只有在缓存未命中时才回退到网络请求，这种方式能够提供最快的响应速度，特别适合那些内容稳定、更新频率低的静态资源。网络优先策略则相反，优先从网络获取最新数据，网络不可用时才使用缓存，这确保了数据的新鲜度，但代价是响应速度较慢。

过期重验证策略是一种折中方案，它立即返回缓存中的内容保证快速响应，同时在后台发起网络请求更新缓存，下次访问时用户就能看到更新后的内容。这种策略适合那些对实时性要求不是特别高，但用户期望快速响应的场景。仅网络策略完全绕过缓存，适用于需要保证数据绝对实时性或涉及用户隐私的操作。仅缓存策略则假设所有需要的资源都已经被预先缓存，完全依赖缓存，适用于离线优先的应用架构。

策略 首次请求 后续请求 适用资源
缓存优先 网络获取并缓存 优先返回缓存（网络兜底） 静态资源（字体/图片）
网络优先 网络获取并缓存 优先网络（缓存兜底） API 数据（需要最新）
过期重验证 网络获取并缓存 返回缓存 + 后台刷新 中等新鲜度的 API
仅网络 网络获取 网络获取 POST / 变更请求
仅缓存 预缓存 仅返回缓存 不可变的构建产物

缓存优先（Cache-first）

逻辑：

缓存优先策略的工作原理是首先检查缓存中是否存在匹配的响应。如果找到了缓存条目，直接将其返回给请求者，整个过程无需任何网络请求，因此响应速度极快。只有当缓存中不存在所需资源时，才会发起网络请求，获取到响应后将其存入缓存并返回给用户。这种方式的核心优势在于最大化利用已有缓存，减少不必要的网络请求。

  1. 检查缓存是否有匹配。
  2. 如果命中缓存，直接返回。
  3. 否则请求网络，返回响应并写入缓存。

代码：

下面的代码展示了缓存优先策略的典型实现。首先调用 caches.match() 检查请求是否在缓存中，如果找到则直接返回。否则发起 fetch() 网络请求，获取响应后通过 response.clone() 创建副本存入缓存，原始响应返回给用户。注意响应体只能读取一次，所以必须克隆后再存入缓存。

self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return (
        cached ||
        fetch(event.request).then((response) => {
          const cacheCopy = response.clone();
          caches.open('v1').then((c) => c.put(event.request, cacheCopy));
          return response;
        })
      );
    }),
  );
});

优点：

缓存优先策略的主要优点是响应速度极快，特别是在缓存命中的情况下，用户几乎感受不到任何延迟。这种策略还能提供完全的离线访问能力，因为只要资源被缓存过，即使网络完全不可用也能正常访问。

  • 响应极快（缓存命中时）。
  • 完全支持离线访问。

缺点：

这种策略的主要缺点是缓存可能会过时。由于优先使用缓存，用户可能长时间无法获取到最新的资源版本，直到缓存被显式失效或 Service Worker 版本更新。对于需要保持数据新鲜度的场景，这种策略并不适合。

  • 缓存可能过时，直到失效或版本更新。

适用场景：

缓存优先策略最适合那些内容稳定、更新频率低、体积适中的静态资源。字体文件和图片资源是典型代表，它们通常带有哈希文件名，内容变化时文件名也会改变，因此可以安全地长期缓存。带有哈希文件名的 JavaScript 和 CSS 文件同样适用，因为哈希值保证了文件名与内容的唯一对应关系。

  • 字体文件。
  • 图片资源。
  • 带哈希文件名的静态资源（JS/CSS）。
  • 构建产物。

不适用：

缓存优先策略不适合需要实时数据的场景，特别是需要获取最新数据的 API 请求。此外，HTML 页面通常也不适合使用这种策略，因为用户期望看到最新的页面内容，而不是可能已经过时的缓存版本。对于这类需要保持新鲜度的资源，应该选择网络优先或过期重验证策略。

  • 需要最新数据的 API。
  • 需要保持新鲜的 HTML 页面。

网络优先（Network-first）

逻辑：

网络优先策略的核心思想是优先保证数据的新鲜度。当请求到达时，首先尝试发起网络请求获取最新数据，如果网络请求成功，将响应存入缓存并返回给用户。只有当网络请求失败（可能是网络不可用或请求超时）时，才会回退到缓存中的响应。这种方式确保了在线状态下用户总能获取到最新数据，同时离线时也有缓存兜底。

  1. 尝试网络请求。
  2. 成功则返回响应并缓存。
  3. 失败则返回缓存。

代码：

下面的实现展示了网络优先策略的基本模式。首先尝试 fetch() 发起网络请求，成功后将响应副本存入缓存并返回。如果网络请求失败（通过 .catch() 捕获），则回退到 caches.match() 从缓存中查找匹配的响应。这种方式保证了在线时数据的新鲜度，离线时有缓存可用。

self.addEventListener('fetch', (event) => {
  event.respondWith(
    fetch(event.request)
      .then((response) => {
        const cacheCopy = response.clone();
        caches.open('v1').then((c) => c.put(event.request, cacheCopy));
        return response;
      })
      .catch(() => caches.match(event.request)),
  );
});

优点：

网络优先策略的最大优点是在线时总是能获取到最新数据，保证了数据的新鲜度。同时，当网络不可用时还能通过缓存提供降级服务，确保用户体验的连续性。这种策略特别适合那些用户期望看到最新内容，但同时也希望离线时能够正常访问的场景。

  • 在线时总是获取最新数据。
  • 离线时有缓存兜底。

缺点：

由于优先使用网络，用户每次请求都需要等待网络往返完成，响应速度相对较慢。在弱网环境下，用户可能需要等待较长时间才能看到内容，体验较差。为了改善这种情况，可以引入超时机制，当网络请求超过一定时间后自动回退到缓存。

  • 需要等待网络往返，速度较慢。
  • 弱网环境下体验更差。

适用场景：

网络优先策略特别适合需要获取最新数据的 API 请求，比如新闻列表、商品信息等用户期望看到实时更新的内容。对于没有使用应用外壳（App Shell）架构的 HTML 页面，这种策略也很合适，因为用户总能获取到最新的页面内容。

  • 需要最新数据的 API 请求。
  • HTML 页面（没有 App Shell 的场景）。

变体：带超时的网络优先——网络请求超过 3 秒则使用缓存。

带超时的网络优先策略是对基本网络优先策略的改进。当网络请求超过预设的时间阈值（如 3 秒）后，自动放弃等待并回退到缓存。这种方式在弱网环境下能显著改善用户体验，避免了长时间等待白屏的问题。实现上可以使用 Promise.race() 让网络请求和超时计时器竞争，先完成的作为最终结果。

过期重验证（Stale-While-Revalidate）

逻辑：

过期重验证策略是一种兼顾速度与新鲜度的折中方案。当请求到达时，它首先检查缓存中是否存在响应，如果存在则立即返回，用户无需等待网络请求完成。与此同时，它在后台异步发起网络请求获取最新内容，并用新响应更新缓存。这样，用户第一次看到的是可能稍旧的缓存内容，但下次访问时就能看到最新数据了。

这种策略特别适合那些对实时性要求不是特别高，但用户期望快速响应的场景。比如用户头像、商品图片、文章内容等，用户通常能容忍一次访问周期的延迟，但同时期望页面能够快速加载。过期重验证策略正好满足了这种需求，在保证用户体验的同时自动保持数据的新鲜度。

  1. 立即返回缓存的响应。
  2. 同时在后台发起网络请求。
  3. 用网络响应更新缓存，供下次使用。

代码：

下面的实现展示了过期重验证策略的核心逻辑。首先检查缓存是否存在匹配的响应，同时启动网络请求。无论缓存是否存在，网络请求都会执行。如果缓存命中，立即返回缓存内容，网络请求在后台更新缓存。如果缓存未命中，则等待网络请求完成后返回。这种方式确保了缓存命中时的极快响应，同时通过后台刷新保持数据新鲜。

self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      const fetchPromise = fetch(event.request).then((response) => {
        const cacheCopy = response.clone();
        caches.open('v1').then((c) => c.put(event.request, cacheCopy));
        return response;
      });
      return cached || fetchPromise;
    }),
  );
});

优点：

过期重验证策略的最大优点是响应速度极快，特别是在缓存命中的情况下，用户几乎感受不到任何延迟。它通过后台自动刷新机制保持缓存的新鲜度，用户下次访问时就能看到更新后的内容。这种策略通常能提供最佳的用户体验，因为它既保证了快速响应，又不会让用户长时间停留在过时内容上。

  • 响应极快（缓存命中时）。
  • 自动后台刷新，保持缓存新鲜。
  • 用户体验最佳。

缺点：

过期重验证策略的主要缺点是用户首次看到的可能是旧数据。由于立即返回缓存内容，用户可能不知道有新版本可用，直到下次访问。此外，每次请求都会同时发起缓存读取和网络请求，造成双重开销，可能会增加服务器负载和网络流量。

  • 用户首次看到的可能是旧数据。
  • 同时发起缓存读取和网络请求（双重开销）。

适用场景：

过期重验证策略适合大多数可以容忍一次延迟刷新的场景。它特别适合用户头像图片、通用的配置数据、文章内容等用户期望快速访问但不需要绝对实时的资源。在实际项目中，过期重验证策略经常被推荐作为默认策略，因为它在大多数场景下都能提供良好的用户体验。

  • 大部分可容忍一次延迟刷新的场景。
  • 头像图片、通用数据。
  • 推荐作为默认策略。

仅网络（Network-only）

逻辑：始终请求网络，不使用缓存。

仅网络策略是最简单的缓存策略，它完全绕过 Service Worker 的缓存机制，所有请求都直接发往网络服务器。这种策略适用于那些必须保证实时性或安全性的请求，比如用户的变更操作、需要认证的 API 调用、实时数据查询等。虽然这种策略无法提供离线支持，但它保证了数据的绝对实时性和安全性。

代码：

仅网络策略的实现非常简单，只需要将请求直接转发给网络，不进行任何缓存操作。下面的代码展示了这种策略的基本实现，直接调用 fetch() 发起网络请求并返回响应，不涉及任何缓存读写操作。这种策略虽然简单，但在需要保证数据实时性的场景中非常重要。

self.addEventListener('fetch', (event) => {
  event.respondWith(fetch(event.request));
});

适用场景：

仅网络策略适合那些必须保证实时性或涉及用户隐私安全的请求。POST、PUT、DELETE、PATCH 等变更操作通常不应该缓存，因为它们会改变服务器状态，需要确保每次请求都被正确处理。需要认证的 API 请求也不适合缓存，因为认证信息可能因用户而异。实时数据如聊天消息、股票行情等同样需要使用仅网络策略。

  • POST / PUT / DELETE / PATCH 变更请求。
  • 需要认证的 API。
  • 实时数据。
  • 不需要缓存的请求。

仅缓存（Cache-only）

逻辑：只从缓存读取，缓存不存在则失败。

仅缓存策略假设所有需要的资源都已经被预先缓存，完全依赖缓存提供服务，不发起任何网络请求。这种策略通常用于预缓存场景，在 Service Worker 安装阶段将所有需要的资源下载并存储到缓存中，后续所有请求都从缓存中获取。这种方式能提供极致的离线体验，但前提是必须确保所有需要的资源都被正确预缓存。

代码：

仅缓存策略的实现也非常简洁，直接从缓存中查找匹配的响应，不发起任何网络请求。下面的代码展示了这种策略的基本实现，调用 caches.match() 查找缓存，找到则返回，找不到则请求失败。这种策略需要配合预缓存机制使用，确保所有可能被请求的资源在安装阶段都已缓存完毕。

self.addEventListener('fetch', (event) => {
  event.respondWith(caches.match(event.request));
});

适用场景：

仅缓存策略主要用于那些已经在安装阶段预缓存的资源。这些资源通常是不可变的构建产物，如带有哈希文件名的 JavaScript 和 CSS 文件，它们在部署后内容不会改变，可以安全地从缓存中直接返回。使用这种策略的前提是必须确保预缓存清单完整准确，否则请求会直接失败。

  • 已在安装阶段预缓存的资源。
  • 确定不会变化的不可变资源。

风险：若未命中缓存则直接失败。

仅缓存策略的最大风险是如果缓存中不存在请求的资源，请求会直接失败，用户将看到错误页面或无法正常使用应用。因此，使用这种策略时必须非常小心，确保所有可能被请求的资源都被包含在预缓存清单中。通常建议仅在确定资源一定存在的情况下使用这种策略。

缓存与网络竞速

逻辑：同时发起缓存读取和网络请求，谁先返回用谁。

缓存与网络竞速策略是一种追求极致性能的方案。当请求到达时，同时发起缓存读取和网络请求，使用 Promise.race() 等待两者中先完成的一个作为最终响应。这种方式能够在网络状况良好时获得最新数据，在网络较慢时从缓存快速返回，兼顾了速度与新鲜度。但实现上较为复杂，需要处理缓存未命中的情况。

代码：

下面的代码展示了缓存与网络竞速策略的基本实现。使用 Promise.race() 让缓存读取和网络请求竞争，先完成的作为最终结果。注意缓存未命中时返回一个永远不会 resolve 的 Promise，确保竞速时网络请求能够正常完成。这种实现方式相对复杂，需要仔细处理各种边界情况。

self.addEventListener('fetch', (event) => {
  event.respondWith(
    Promise.race([fetch(event.request), caches.match(event.request).then((cached) => cached || new Promise(() => {}))]),
  );
});

适用场景：

缓存与网络竞速策略适合对速度有极致要求的场景，特别是那些网络状况不稳定的环境。当网络状况好时，网络请求可能比缓存读取更快完成，用户能获得最新数据；当网络状况差时，缓存读取更快完成，用户能获得快速响应。但这种策略实现较为复杂，需要权衡使用。

  • 对速度有极致要求的场景。
  • 实现较复杂，需要权衡使用。

按资源类型选择策略

实战 Service Worker 配置：

在实际项目中，不同类型的资源应该使用不同的缓存策略。下面的代码展示了一个完整的 Service Worker 配置示例，根据请求的资源类型自动选择合适的缓存策略。HTML 页面使用网络优先策略确保用户看到最新内容，静态资源使用缓存优先策略保证快速加载，API 请求使用过期重验证策略兼顾速度与新鲜度，图片资源同样使用缓存优先策略。

下面的实现首先解析请求 URL，然后根据请求的类型和路径选择相应的策略。对于导航请求（HTML 页面），使用网络优先策略；对于 JavaScript、CSS、字体等静态资源，使用缓存优先策略；对于 API 请求，使用过期重验证策略；对于图片资源，同样使用缓存优先策略。这种方式能够为不同类型的资源提供最优的缓存策略。

self.addEventListener('fetch', (event) => {
  const url = new URL(event.request.url);

  // HTML 页面 → 网络优先
  if (event.request.mode === 'navigate') {
    event.respondWith(networkFirst(event.request));
  }

  // 静态资源 → 缓存优先
  if (/\.(js|css|woff2)$/.test(url.pathname)) {
    event.respondWith(cacheFirst(event.request));
  }

  // API 请求 → 过期重验证
  if (url.pathname.startsWith('/api/')) {
    event.respondWith(staleWhileRevalidate(event.request));
  }

  // 图片 → 缓存优先
  if (/\.(png|jpg|webp)$/.test(url.pathname)) {
    event.respondWith(cacheFirst(event.request));
  }
});

下面的流程图清晰地展示了按资源类型选择策略的决策过程。当请求到达时，首先判断资源类型，然后路由到相应的缓存策略。HTML 页面走网络优先路径，静态资源走缓存优先路径，API 请求走过期重验证路径，POST 请求走仅网络路径。这种分层策略能够为不同类型的资源提供最优的处理方式。

缓存命名与版本控制
版本化缓存名称：


在实际项目中，使用版本化的缓存名称是管理缓存的重要手段。下面的代码展示了如何定义版本化的缓存名称，将缓存名称与版本号结合，方便在部署新版本时自动清理旧缓存。不同的资源类型使用不同的缓存名称，便于独立管理和失效。静态资源缓存、API 缓存、图片缓存分开存储，各有各的生命周期和更新策略。


const CACHE_VERSION = 'v3';
const STATIC_CACHE = `static-${CACHE_VERSION}`;
const API_CACHE = `api-${CACHE_VERSION}`;
const IMAGE_CACHE = `image-${CACHE_VERSION}`;
不同资源不同生命周期：


不同类型的资源应该有不同的缓存生命周期。静态资源如 JavaScript、CSS、字体文件，由于使用哈希文件名，可以长期缓存，直到新版本部署。API 数据通常需要较短的生命周期，确保用户能看到较新的内容。图片资源的生命周期介于两者之间，通常设置中等长度的缓存周期。


    

  • 静态资源：长期缓存。
    • 

  • API 数据：短生命周期。
    • 

  • 图片：长期缓存。
    • 



在 activate 事件中清理旧缓存：


当新版本的 Service Worker 激活时，应该清理旧版本的缓存以释放存储空间。下面的代码展示了如何在 activate 事件中删除所有不以当前版本号结尾的缓存。这种方式确保了每次部署新版本时，旧缓存会被自动清理，避免存储空间被无用的旧缓存占用。


self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((names) => {
      return Promise.all(names.filter((name) => !name.endsWith(CACHE_VERSION)).map((name) => caches.delete(name)));
    }),
  );
});
缓存容量限制
浏览器配额：


浏览器对每个源（origin）的缓存容量都有限制，通常约为磁盘空间的百分之五十左右。这个配额是按源分配的，同一源下的所有缓存（包括 Cache API 和 IndexedDB）共享这个配额。当缓存超出配额时，浏览器会根据最近最少使用（LRU）策略自动驱逐最旧的缓存条目，为新的缓存腾出空间。


    

  • 默认约占磁盘空间的 50%。
    • 

  • 按源（origin）分配。
    • 

  • 超出配额时浏览器会驱逐最旧的缓存。
    • 



手动限制缓存大小：


除了依赖浏览器的自动管理，开发者也可以主动限制缓存的大小。下面的代码展示了如何手动限制缓存条目数量，当缓存中的条目超过预设的最大值时，删除最旧的条目。这种方式能够更精确地控制缓存占用的存储空间，避免缓存无限增长导致超出配额。


async function trimCache(cacheName, maxItem) {
  const cache = await caches.open(cacheName);
  const keys = await cache.keys();
  if (keys.length > maxItem) {
    await cache.delete(keys[0]);
    trimCache(cacheName, maxItem);
  }
}
认证请求的缓存
注意事项：


缓存带认证的请求时需要特别小心。认证头（Authorization）通常包含用户的身份信息，不同用户的认证信息不同。如果简单地缓存带认证的响应，可能导致用户 A 的数据被用户 B 看到，造成严重的安全问题。默认情况下，缓存键只包含请求的 URL 和方法，不包含认证头等用户特定的信息。


    

  • 认证头（Authorization）因用户而异。
    • 

  • 默认缓存不区分用户。
    • 

  • 可能导致 A 用户的数据被 B 用户看到。
    • 



解决方案：


针对认证请求的缓存问题，有两种主要的解决方案。第一种是干脆不缓存带认证的 API 请求，让这类请求始终走网络，虽然牺牲了一些性能，但保证了安全性。第二种方案是在缓存键中包含用户 ID 等用户特定的信息，这样不同用户的响应会被存储在不同的缓存条目中，互不干扰。


    

  • 不缓存带认证的 API 请求。
    • 

  • 或在缓存键中包含用户 ID。
    • 



跨域请求与缓存
跨域请求特殊性：


跨域请求在 Service Worker 中有一些特殊的限制。默认情况下，Service Worker 无法读取跨域响应的内容，这种响应被称为不透明响应（Opaque Response）。虽然可以缓存不透明响应，但无法获知响应的实际大小，这可能导致配额计算不准确。如果需要完整访问跨域响应的内容，需要使用 mode: 'cors' 来发起跨域请求。


    

  • Service Worker 默认无法读取跨域响应体（不透明响应）。
    • 

  • 可以缓存不透明响应，但无法获知实际大小。
    • 

  • 使用 mode: 'cors' 来获取完整的跨域响应。
    • 



Workbox 策略抽象
Workbox 库将上述策略封装为声明式 API：


Workbox 是 Google 开源的 Service Worker 工具库，它将各种缓存策略封装成声明式的 API，大大简化了 Service Worker 的开发。下面的代码展示了如何使用 Workbox 快速配置缓存策略。首先使用 precacheAndRoute() 预缓存构建产物，然后使用 registerRoute() 注册各种路由规则，每种规则使用相应的策略类。Workbox 的代码更加简洁，经过充分测试，且有良好的社区维护。


import { precacheAndRoute } from 'workbox-precaching';
import { registerRoute } from 'workbox-routing';
import { CacheFirst, NetworkFirst, StaleWhileRevalidate, NetworkOnly } from 'workbox-strategies';

precacheAndRoute(self.__WB_MANIFEST);

registerRoute(({ request }) => request.mode === 'navigate', new NetworkFirst({ cacheName: 'pages' }));

registerRoute(({ url }) => url.pathname.startsWith('/api/'), new StaleWhileRevalidate({ cacheName: 'api' }));

registerRoute(({ request }) => request.destination === 'image', new CacheFirst({ cacheName: 'images' }));
Workbox 代码更简洁、经过充分测试、且有良好的社区维护。使用 Workbox 可以避免手动实现缓存策略时容易出现的各种错误，同时代码也更易于维护和理解。


缓存过期控制
Workbox 过期插件：


Workbox 提供了 ExpirationPlugin 插件来自动管理缓存的过期。下面的代码展示了如何配置过期插件，设置最大条目数和最大存储时间。超过最大条目数的旧条目会被自动删除，存储时间超过最大存储时间的条目也会被自动清理。这种方式能够有效防止缓存无限增长，确保存储空间得到合理利用。


import { ExpirationPlugin } from 'workbox-expiration';

new CacheFirst({
  cacheName: 'images',
  plugins: [
    new ExpirationPlugin({
      maxEntries: 60,
      maxAgeSeconds: 30 * 24 * 60 * 60, // 30 天
    }),
  ],
});
自动清理：


Workbox 的过期插件会自动清理超龄条目，开发者可以同时限制条目数量和存储时间，实现精细化的缓存管理。这种方式比手动实现清理逻辑更加可靠和高效，是生产环境推荐的做法。


    

  • 超龄条目自动删除。
    • 

  • 可同时限制条目数量和存储时间。
    • 



常见误区
1. 对 HTML 使用缓存优先：


对 HTML 页面使用缓存优先策略是一个非常常见的错误。HTML 是应用的入口，如果被长期缓存，用户将无法获取到最新版本的应用，可能停留在旧版本很长一段时间。正确的做法是对 HTML 使用网络优先或过期重验证策略，确保用户总能获取到最新的 HTML，从而获得最新的资源引用。


    

  • 用户将永远看到旧页面。
    • 

  • 应使用网络优先或过期重验证。
    • 



2. 从不刷新缓存：


另一个常见错误是部署新版本后从不主动刷新缓存。这导致用户可能长时间停留在旧版本，无法体验到新功能或修复的 bug。应该使用版本化的缓存名称，在部署新版本时更新版本号，让 Service Worker 在激活时清理旧缓存。


    

  • 部署新版本后用户仍看到旧版。
    • 

  • 应使用版本化缓存名称。
    • 



3. 缓存 POST 请求：


POST 请求通常用于变更操作，会改变服务器状态，不应该被缓存。如果缓存了 POST 请求的响应，可能导致用户的变更操作被重复执行，造成数据不一致。POST 请求应该使用仅网络策略，确保每次请求都被正确处理。


    

  • POST 应始终走网络。
    • 

  • 不应缓存变更操作。
    • 



4. 所有资源使用同一个缓存：


将所有资源存储在同一个缓存中会导致难以按需失效。不同类型的资源有不同的更新频率和生命周期，应该分开存储在不同的缓存中。这样当需要更新某一类资源时，可以只清理对应的缓存，而不影响其他类型的资源。


    

  • 难以按需失效。
    • 

  • 应按资源类型分开缓存。
    • 



5. 不控制缓存大小：


如果不主动控制缓存大小，缓存可能会无限增长，最终超出浏览器的存储配额。当超出配额时，浏览器会随机驱逐缓存条目，可能导致重要的缓存被清理。应该设置缓存容量上限，通过过期插件或手动清理机制控制缓存大小。


    

  • 浏览器会随机驱逐缓存。
    • 

  • 应设置缓存容量上限。
    • 



6. 不透明响应的大小误判：


跨域的不透明响应在上报大小时为 0，但实际仍然占用存储空间。如果大量缓存不透明响应，可能导致配额计算不准确，最终超出实际可用的存储空间。应该尽量避免缓存大量不透明响应，或者在计算配额时考虑这个因素。


    

  • 跨域响应上报大小为 0，实际占用空间。
    • 

  • 可能导致配额计算不准确。
    • 



最佳实践
1. 按资源类型选择策略：不同资源用不同缓存和策略。静态资源用缓存优先，API 数据用过期重验证或网络优先，POST 请求用仅网络。这种分层策略能够为不同类型的资源提供最优的处理方式。


2. 版本化缓存名称：部署时更新版本号。每次部署新版本时，更新缓存名称中的版本号，让 Service Worker 在激活时自动清理旧缓存，确保用户能够获取到最新版本的内容。


3. 使用 Workbox：经过验证的策略封装。Workbox 是经过充分测试和社区验证的工具库，使用它可以避免手动实现缓存策略时容易出现的各种错误，同时代码也更简洁易维护。


4. 设置过期策略：自动清理过期缓存。使用过期插件或手动清理机制，确保缓存不会无限增长，存储空间得到合理利用。


5. 测试离线场景：使用 DevTools 的离线模式。在开发过程中应该充分测试离线场景，确保缓存的资源能够支撑应用在离线状态下正常运行，用户体验不会因为离线而严重下降。


6. 监控缓存大小：通过 navigator.storage.estimate() 检查。定期检查缓存的实际使用量和剩余配额，及时发现和解决缓存过大或配额不足的问题。


实战案例
新闻网站：


新闻网站的缓存策略需要平衡内容的实时性和访问速度。HTML 页面使用网络优先策略，确保用户看到最新的文章列表。文章正文使用过期重验证策略，缓存内容提供快速访问，后台刷新保持新鲜。图片使用缓存优先策略长期有效。评论 API 使用仅网络策略，确保用户总能看到最新评论。


    

  • HTML：网络优先（获取最新文章）。
    • 

  • 文章正文：过期重验证（缓存 + 后台刷新）。
    • 

  • 图片：缓存优先（长期有效）。
    • 

  • 评论 API：仅网络（获取最新评论）。
    • 



电商网站：


电商网站对性能和数据新鲜度都有较高要求。商品页面使用过期重验证策略，缓存商品信息提供快速访问，后台刷新价格和库存。商品图片使用缓存优先策略长期缓存。购物车 API 使用仅网络策略，确保库存和价格实时准确。搜索使用带超时的网络优先策略，平衡新鲜度和响应速度。


    

  • 商品页：过期重验证。
    • 

  • 商品图片：缓存优先。
    • 

  • 购物车 API：仅网络。
    • 

  • 搜索：带超时的网络优先。
    • 



SaaS 后台：


SaaS 后台应用通常有固定的应用外壳和动态的业务数据。应用外壳使用缓存优先策略，提供快速的应用启动体验。仪表盘数据使用网络优先策略，因为数据新鲜度对业务决策至关重要。用户头像使用缓存优先策略长期缓存。变更操作使用仅网络策略，确保数据一致性。


    

  • 应用外壳：缓存优先。
    • 

  • 仪表盘数据：网络优先（数据新鲜度关键）。
    • 

  • 用户头像：缓存优先。
    • 

  • 变更操作：仅网络。
    • 



小结
五个核心缓存策略是 Service Worker 工程化的基石：缓存优先提供极速离线体验，适合静态资源；网络优先保证数据新鲜，适合 HTML 和 API；过期重验证兼顾速度与新鲜度，是大多数场景的默认选择；仅网络用于 POST 等变更操作；仅缓存用于不可变的预缓存资源。按资源类型组合使用不同策略，配合版本化缓存命名、容量限制和 Workbox 工具库，即可构建出快速、可靠、始终保持新鲜的 PWA 缓存层。


理解每种策略的适用场景和权衡非常重要。缓存优先策略虽然能提供最快的响应速度，但代价是数据可能过时；网络优先策略保证了数据新鲜度，但响应速度较慢；过期重验证策略在两者之间取得了平衡，通常是推荐的首选策略。在实际项目中，应该根据具体的业务需求和用户期望，为不同类型的资源选择合适的缓存策略，同时配合版本控制、容量限制等机制，确保缓存系统稳定可靠地运行。
