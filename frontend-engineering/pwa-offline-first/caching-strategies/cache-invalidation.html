缓存失效

核心概念

"计算机科学中只有两件真正困难的事：缓存失效和命名。"——Phil Karlton。缓存失效是 PWA 中最棘手的问题：缓存过久导致用户看到旧版本，缓存清除太激进则失去性能收益。主要的失效策略包括：哈希文件名（构建工具自动生成，永久缓存）、缓存名版本号（新部署时更新版本号）、ETag 条件请求（HTTP 层面验证）、基于 TTL 的过期清理、用户手动刷新、以及广播更新通知。

缓存失效的核心挑战在于平衡新鲜度与性能。缓存存在的目的是减少网络请求、加速页面加载，但如果缓存永远不更新，用户就会一直看到过时的内容。理想的缓存失效策略应该在不显著影响性能的前提下，确保用户尽快看到最新内容。不同类型的资源对新鲜度的要求不同，因此需要针对每种资源类型设计合适的失效策略。

策略 何时失效 适用场景
哈希文件名 新部署自动失效 JS / CSS / 静态资源
缓存名版本号 Service Worker 激活时 所有缓存
ETag / 304 每次请求验证 API、HTML
TTL 过期 基于时间 图片、API
用户手动刷新 用户点击"刷新" 备用 / 可选
广播更新 新数据可用时 通知用户

哈希文件名

构建工具自动生成带哈希的文件名：

哈希文件名是最可靠的缓存失效策略。现代构建工具（如 Webpack、Vite、Rollup）会自动根据文件内容生成唯一的哈希值，并将其作为文件名的一部分。当文件内容发生变化时，哈希值也随之改变，生成的文件名不同。由于文件名唯一对应文件内容，可以安全地对这些文件设置永久缓存。

  • app.123abc.js
  • styles.456def.css

效果：

哈希文件名策略的效果是实现了自动化的精确失效。每次新部署时，内容变化的文件会获得新的文件名，浏览器在请求这些新文件名时不会命中旧缓存，自动从网络获取。而内容未变的文件保持原有文件名，继续使用缓存，避免不必要的下载。

  • 新构建产生新文件名。
  • 旧文件名虽然仍在缓存中，但不再被请求。
  • 可安全设置 max-age=31536000 永久缓存。

实现方式：Webpack、Vite、Next.js 等构建工具均自动支持。开发者只需在构建配置中启用内容哈希即可，无需手动管理文件版本。

HTML 的角色：

HTML 文件在哈希文件名策略中扮演着关键的桥梁角色。HTML 引用了带哈希的资源文件名，每次部署时 HTML 中的资源引用会自动更新为新的哈希文件名。因此，HTML 本身不能长期缓存，否则用户就无法获取到新的资源引用。通常对 HTML 使用短缓存或网络优先策略。

  • HTML 引用新的文件名。
  • HTML 本身不做长期缓存（或使用短缓存）。
  • 用户拉取最新 HTML 后即获得新资源引用。

下面的流程图展示了哈希文件名策略的完整工作流程。从新部署开始，构建工具生成新的资源哈希，HTML 引用新的文件名，浏览器请求最新 HTML 后发起对新资源的请求，由于是新的文件名，缓存未命中，从网络获取后永久缓存。

缓存名版本控制
部署时更新缓存名版本号：


缓存名版本控制是一种简单粗暴但有效的失效策略。通过在缓存名称中包含版本号，每次部署新版本时递增版本号，在 Service Worker 激活时删除所有不匹配当前版本号的旧缓存。这种方式能够保证每次部署后用户获取到全新的缓存内容。


const CACHE_VERSION = 'v3'; // 部署时递增
const STATIC_CACHE = `static-${CACHE_VERSION}`;
在 activate 事件中清理旧缓存：


下面的代码展示了如何在 Service Worker 的 activate 事件中清理旧版本的缓存。获取所有缓存名称列表，过滤出不以当前版本号结尾的旧缓存，然后逐一删除。event.waitUntil() 确保清理完成后才完成激活过程。


self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((names) => {
      return Promise.all(names.filter((name) => !name.endsWith(CACHE_VERSION)).map((name) => caches.delete(name)));
    }),
  );
});
效果：


缓存名版本控制的效果是在 Service Worker 激活时一次性清理所有旧缓存。旧缓存被删除后，新缓存按需填充，用户获取到全新的内容。这种方式简单直接，适合作为全局的缓存失效兜底策略。


    

  • 旧缓存被删除。
    • 

  • 新缓存按需填充。
    • 

  • 强制使用最新内容。
    • 



注意：更新后首次导航所有资源都会缓存未命中，速度稍慢。这是因为旧缓存被完全清理，所有资源都需要重新从网络获取。对于追求平滑更新体验的场景，可以结合哈希文件名策略，只更新变化的资源。


ETag 条件请求
HTTP 缓存验证机制：


ETag 条件请求是 HTTP 协议层面的缓存验证机制。服务器在响应中包含一个 ETag 标识（通常是文件内容的哈希值），客户端下次请求同一资源时，将 ETag 值通过 If-None-Match 请求头发送给服务器。服务器比较当前资源的 ETag 与客户端发送的值，如果相同则返回 304 状态码（未修改），无需传输响应体，节省带宽。


    

  • 服务器返回 ETag: "abc123"。
    • 

  • 客户端下次请求带上 If-None-Match: "abc123"。
    • 

  • 服务器返回 304（未修改，无响应体）。
    • 

  • 或返回 200（有新内容）。
    • 



在 Service Worker 中使用：


下面的代码展示了如何在 Service Worker 中实现基于 ETag 的条件验证。当缓存存在时，使用缓存中的 ETag 值发起条件请求。如果服务器返回 304，说明内容未变化，继续使用缓存。如果返回 200，说明有新内容，更新缓存并返回新响应。这种方式在保持数据新鲜度的同时最小化网络传输。


self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      if (cached) {
        const fetchPromise = fetch(event.request, {
          headers: { 'If-None-Match': cached.headers.get('ETag') },
        }).then((response) => {
          if (response.status === 304) return cached;
          caches.open('v1').then((c) => c.put(event.request, response.clone()));
          return response;
        });
        return cached; // 先返回缓存（过期重验证模式）
      }
      return fetch(event.request);
    }),
  );
});
效果：304 响应无需传输体（节省带宽），200 表示有新内容并更新缓存。这种策略特别适合那些更新频率不确定的资源，如 API 响应和 HTML 页面，既能保持数据新鲜又能节省网络流量。


TTL 过期策略
基于时间自动过期：


TTL（Time To Live）过期策略是最直观的缓存失效方式——为每个缓存条目设置一个存储时间上限，超过这个时间后条目自动失效。Workbox 的 ExpirationPlugin 提供了开箱即用的 TTL 支持，只需设置 maxAgeSeconds 参数即可。


import { ExpirationPlugin } from 'workbox-expiration';

new CacheFirst({
  plugins: [
    new ExpirationPlugin({
      maxAgeSeconds: 30 * 24 * 60 * 60, // 30 天
    }),
  ],
});
效果：超过 30 天的缓存条目自动删除，下次请求从网络获取新内容。TTL 策略的优势在于简单可预测，不需要服务器配合，适合那些更新频率相对固定的资源。


适用场景：


不同类型的资源应该设置不同的 TTL 值。图片资源通常变化较少，可以设置较长的 TTL（如 30 天或更长）。API 响应数据变化较快，应该设置较短的 TTL（如 5 分钟到 1 小时）。关键是根据资源的实际更新频率来选择合适的过期时间。


    

  • 图片（较长 TTL）。
    • 

  • API 响应（较短 TTL）。
    • 



用户手动刷新
下拉刷新或显式按钮：


用户手动刷新是一种兜底的缓存失效方式。当自动失效机制不够及时，或者用户明确知道有新内容可用时，可以通过手动刷新来强制获取最新数据。这种方式通常作为其他自动失效策略的补充，给予用户主动控制缓存的能力。


下面的代码展示了两种手动刷新的实现方式。第一种通过 cache: 'no-store' 参数绕过所有缓存直接请求网络。第二种通过 Service Worker 的 update() 方法触发 Service Worker 更新检查，如果有新版本则安装并激活。


function refresh() {
  // 绕过 SW 缓存
  fetch('/api/data', { cache: 'no-store' }).then(...);

  // 或触发 SW 更新检查
  navigator.serviceWorker.getRegistrations().then((regs) => {
    regs.forEach((reg) => reg.update());
  });
}
cache: 'no-store' 强制走网络，完全绕过 HTTP 缓存。这是最彻底的刷新方式，确保获取到服务器上的最新数据，但同时也放弃了所有缓存带来的性能优势。


广播更新
当缓存中有新数据时通知用户：


广播更新是一种用户友好的缓存失效通知机制。当过期重验证策略在后台获取到新内容并更新缓存时，BroadcastUpdatePlugin 会通过 BroadcastChannel 通知所有打开的页面。页面收到通知后可以显示提示，让用户选择是否刷新以查看最新内容。


import { BroadcastUpdatePlugin } from 'workbox-broadcast-update';

new StaleWhileRevalidate({
  plugins: [new BroadcastUpdatePlugin()],
});
页面监听：


在页面中监听 Service Worker 发送的广播消息。当接收到缓存更新的通知时，显示一个非侵入式的刷新提示横幅，让用户在方便的时候选择刷新页面。


navigator.serviceWorker.addEventListener('message', (event) => {
  if (event.data.meta === 'workbox-broadcast-update') {
    showRefreshBanner();
  }
});
用户体验：显示"有新版本可用，点击刷新"的提示，由用户决定是否刷新。这种方式尊重了用户的当前操作，不会因为自动刷新而中断用户正在进行的工作。


Service Worker 更新策略
默认行为：


Service Worker 的默认更新行为是比较保守的：浏览器检测到新版本后，新 Service Worker 会进入安装状态，但不会立即激活。它需要等待所有使用旧版本 Service Worker 的标签页全部关闭后，才会激活新版本。这种行为保证了同一用户在不同标签页中看到一致的应用版本。


    

  • 新 Service Worker 安装。
    • 

  • 等待所有标签页关闭。
    • 

  • 然后激活。
    • 



问题：用户可能数天不关闭标签页，一直停留在旧版本。在实际使用中，许多用户习惯长时间保持标签页打开，这导致新版本的 Service Worker 虽然已经安装完成，但迟迟无法激活，用户一直使用旧版本的应用。


解决方案：


针对这个问题有两种主要的解决方案。第一种是使用 skipWaiting() 加 clientsClaim() 立即接管所有标签页，这种方式更新最快但可能导致页面中断。第二种是通知用户有新版本可用，让用户选择合适的时机刷新，这种方式更加用户友好。


    

  • skipWaiting + clientsClaim → 立即更新。
    • 

  • 或通知用户手动刷新。
    • 



建议：关键更新使用 skipWaiting，一般更新通知用户选择。对于安全修复等关键更新，应该立即激活新版本；对于功能更新等非关键变更，让用户选择更新时机更加友好。


综合失效方案
实际项目通常组合多种策略：


在真实的生产环境中，单一的缓存失效策略很难满足所有需求。不同类型的资源有不同的更新频率和重要性，需要针对性地设计失效策略。下面展示了一个典型的综合失效方案，为每种资源类型选择了最合适的失效策略。


    

  • 静态资源：哈希文件名（自动失效）。构建产物通过内容哈希命名，内容变化时文件名自动改变，无需手动管理失效。
    • 

  • Service Worker：缓存名版本号。新部署时更新版本号，激活时清理旧缓存。
    • 

  • API 数据：ETag 条件验证。通过条件请求检查数据是否有更新，节省带宽。
    • 

  • 图片：TTL 过期（如 30 天）。图片变化频率低，使用较长的过期时间。
    • 

  • 兜底：用户手动刷新。当自动失效不够及时时，用户可以主动刷新。
    • 



过时检测
如何判断缓存已过时：


除了被动等待缓存过期，还可以主动检测缓存是否已经过时。以下是几种常见的过时检测机制，每种适用于不同的场景和实时性要求。


    

  • 后台请求对比：过期重验证模式，下次请求自动刷新。通过后台网络请求获取最新内容，与缓存内容对比，发现不同则更新缓存。
    • 

  • 周期性检查：Periodic Background Sync 后台定期刷新。浏览器在合适的时机（如设备充电、连接 WiFi 时）自动发起后台同步，检查并更新过时的缓存。
    • 

  • 服务端推送：Push Notification 通知客户端"缓存已失效"。服务器主动推送消息告知客户端某些缓存已经失效，客户端收到通知后主动刷新。
    • 

  • WebSocket：实时失效通知。通过 WebSocket 长连接实时接收服务器的失效通知，适合对实时性要求极高的场景。
    • 



常见陷阱
1. 缓存的 HTML 仍引用旧哈希资源：


这是一个非常隐蔽的问题。如果 HTML 被长期缓存，其中引用的资源文件名是旧的哈希值，即使新版本的资源已经部署，用户仍然会请求旧版本。解决方案是确保 HTML 使用网络优先或短 TTL 策略，让用户总能获取到最新的 HTML，从而获取最新的资源引用。


2. CDN 缓存与 Service Worker 缓存多层叠加：


当应用同时存在 CDN 边缘缓存和 Service Worker 客户端缓存时，多层缓存的协调变得复杂。CDN 可能缓存了旧版本的资源，Service Worker 又缓存了 CDN 返回的旧内容，导致即使源服务器已更新，用户仍然看到旧版本。解决方案是每层都设计各自的失效策略，通过 ETag 贯穿全链路保证一致性。


3. Service Worker 文件本身被缓存：


如果浏览器或 CDN 缓存了 Service Worker 文件本身，即使部署了新版本，浏览器也无法检测到更新。Chrome 默认最长缓存 sw.js 24 小时。建议对 Service Worker 文件设置 Cache-Control: max-age=0，确保每次访问都从服务器验证是否有更新。


常见反模式
1. 不使用哈希文件名：


如果静态资源不使用哈希文件名，新部署后浏览器可能继续使用旧的缓存内容，因为 URL 没有变化。开发者需要手动管理版本号或等待缓存自然过期，这种方式既不可靠又增加了运维复杂度。


2. 永久缓存 HTML：


HTML 是应用的入口，如果对 HTML 设置了长期缓存或使用缓存优先策略，用户将永远看到旧版本的页面内容。即使静态资源使用了哈希文件名，HTML 中的引用也不会更新。


3. 没有缓存版本号：


没有缓存版本号意味着无法在 Service Worker 更新时清理旧缓存。旧缓存可能被新 Service Worker 继续使用，导致新旧版本混合的问题。


4. 不设置 ETag：


服务器不返回 ETag 响应头，则无法进行条件验证。客户端无法高效地判断缓存是否过时，只能选择每次都下载完整响应或盲目使用缓存。


5. TTL 设置过长：


过长的 TTL 意味着缓存很长时间内不会自动过期，用户可能在很长一段时间内都看到过时的内容。应该根据资源的实际更新频率来选择合适的 TTL 值。


6. TTL 设置过短：


过短的 TTL 会导致缓存频繁过期，每次请求都需要从网络获取，失去了缓存带来的性能优势。缓存还没来得及被复用就被清除了，等于没有缓存。


实战案例
新闻网站的失效策略：


新闻网站对内容的时效性要求很高，需要精心设计缓存失效策略以平衡性能和新鲜度。HTML 页面使用网络优先策略确保用户始终看到最新的文章列表和内容。文章图片使用缓存优先策略配合 30 天过期，因为文章发布后图片通常不会改变。CSS 和 JS 使用哈希文件名配合永久缓存，实现自动化的精确失效。


    

  • HTML：网络优先（始终获取最新）。
    • 

  • 文章内容：过期重验证。
    • 

  • 图片：缓存优先，30 天过期。
    • 

  • CSS / JS：哈希文件名 + 永久缓存。
    • 



更新流程：


完整的更新流程是一个有序的过程。首先部署新版本到服务器，构建产物获得新的哈希文件名。浏览器在下次导航时检测到 Service Worker 有更新，安装新版本。新 Service Worker 激活后清理旧缓存。同时通知用户有新版本可用，用户点击刷新后获取最新的 HTML 和资源引用。

小结
缓存失效决定了 PWA 的用户体验——处理得当用户总能看到最新且快速的内容，处理不当则陷入永远过时或始终缓慢的困境。哈希文件名让静态资源自动失效；缓存名版本号在 activate 事件中清理旧缓存；ETag 条件请求通过 304 响应节省带宽；TTL 过期自动清理时间敏感的缓存；广播更新让用户选择是否刷新。生产环境通常组合多种策略，并确保 HTML 始终使用网络优先或短缓存，以便用户总能获取到最新的资源引用。


设计缓存失效策略时，最重要的原则是"分而治之"——为不同类型的资源选择最合适的失效机制，而非用单一策略覆盖所有场景。静态资源的哈希文件名提供了最优雅的自动失效，API 数据的 ETag 验证在保证新鲜度的同时节省带宽，图片的 TTL 过期提供了可预测的缓存行为。组合使用这些策略，配合合理的 Service Worker 更新和用户通知机制，就能构建出既快速又始终保持新鲜的 PWA 应用。
