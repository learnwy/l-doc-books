预缓存与运行时缓存

核心概念

PWA 的缓存分为两大类：预缓存（Precache，在安装阶段缓存已知资源）和运行时缓存（Runtime Cache，在请求发生时动态缓存）。预缓存适合构建产物（JS/CSS/字体，带哈希文件名），让首次访问后即可离线使用。运行时缓存适合动态内容（API 响应、用户上传的图片等）。两者协作让 PWA 既快速又可离线。

预缓存和运行时缓存的区别在于资源获取的时机和方式。预缓存是主动式的——在 Service Worker 安装阶段就将所有已知的关键资源下载并存入缓存，确保应用在首次访问后即具备离线能力。运行时缓存则是被动式的——只有当用户实际发起请求时，才将响应存入缓存，属于按需缓存。两者各有优劣，合理搭配才能实现最佳的性能和离线体验。

维度 预缓存 运行时缓存
时机 Service Worker 安装阶段 用户实际请求时
内容 已知的构建产物 未知的动态内容
速度 首次访问较慢（需下载全部） 惰性加载
可预测性 完全已知 尽力而为
更新方式 缓存版本号更新 由策略决定
存储占用 可预测的固定大小 大小不确定

预缓存

概念：安装阶段一次性下载并缓存一组已知资源。

预缓存的核心思想是将应用的关键资源在安装阶段就准备好，这样即使用户在首次访问后立即断网，应用的核心功能仍然可以正常运行。预缓存的资源列表通常由构建工具自动生成，包含了应用运行所必需的所有静态文件。

Workbox 实现：

下面的代码展示了使用 Workbox 实现预缓存的标准方式。precacheAndRoute() 函数接受一个资源清单，在 Service Worker 安装时下载并缓存所有清单中的资源，同时自动注册路由规则，后续匹配的请求直接从预缓存返回。

import { precacheAndRoute } from 'workbox-precaching';

precacheAndRoute(self.__WB_MANIFEST);

__WB_MANIFEST 详解：

__WB_MANIFEST 是 Workbox 的预缓存清单占位符，由构建工具在打包时自动替换为实际的资源列表。每个条目包含资源的 URL 和修订哈希，修订哈希用于检测资源是否有变化。构建工具会扫描输出目录中的所有文件，自动生成这个清单。

  • 由构建工具在打包时注入。
  • 包含所有构建产物的 URL 和修订哈希列表。
  • 示例：[{ url: '/app.js', revision: 'abc123' }, ...]。

工作流程：

预缓存的工作流程分为三个阶段。安装阶段，Service Worker 下载并缓存清单中的所有资源。运行阶段，匹配预缓存清单的请求直接从缓存返回，无需网络请求。更新阶段，新构建产生新的清单，Service Worker 检测到哈希变化的资源会重新下载并缓存。

  • 安装事件触发时：下载并缓存所有清单中的资源。
  • 后续匹配请求：直接返回预缓存内容。
  • 修订哈希变化时：重新缓存更新的资源。

下面的流程图展示了预缓存从构建到运行的完整流程。构建阶段生成资源清单，注入 Service Worker 代码。Service Worker 安装时下载所有清单资源。运行时匹配请求直接返回缓存。新构建产生不同的哈希值时，触发更新流程。

哪些资源适合预缓存
应该预缓存的：


选择预缓存资源时，应该优先考虑那些应用运行必需的关键资源。应用外壳 HTML 是最基础的预缓存对象，它定义了应用的基本结构。关键的 JavaScript 入口文件和 CSS 样式确保应用能正常渲染和运行。Logo 图标和默认字体保证了应用的视觉一致性，即使在离线状态下也能正确显示。


    

  • 应用外壳 HTML。
    • 

  • 关键 JS 入口文件。
    • 

  • 关键 CSS 样式。
    • 

  • Logo 图标。
    • 

  • 默认字体。
    • 



不应预缓存的：


并非所有资源都适合预缓存。大量的图片资源（如图片库中的缩略图）如果全部预缓存，会导致安装时间过长且占用大量存储空间。用户个人数据不应预缓存，因为这些数据因用户而异，且可能涉及隐私问题。频繁变更的内容（如新闻列表、实时数据）也不适合预缓存，因为缓存的内容很快就会过时。


    

  • 大量图片（图片库）。
    • 

  • 用户个人数据。
    • 

  • 频繁变更的内容。
    • 



容量预算：


预缓存的资源总量应该控制在合理范围内。过大的预缓存清单会导致 Service Worker 安装时间过长，用户可能在安装完成前就离开了页面。同时，过大的预缓存也会占用大量的存储空间，可能影响其他缓存的可用空间。


    

  • 推荐预缓存总量不超过 5 MB。
    • 

  • 过大会导致首次安装缓慢和存储浪费。
    • 



运行时缓存
概念：用户实际发起请求时才进行缓存，属于惰性加载模式。


运行时缓存与预缓存的最大区别在于缓存的时机。预缓存是主动提前缓存，运行时缓存是被动按需缓存。只有当用户实际访问某个资源时，Service Worker 才会将其缓存起来。这种方式的优势在于不会提前占用存储空间，只缓存用户真正需要的内容，且不会影响首次安装的速度。


Workbox 实现：


下面的代码展示了使用 Workbox 实现运行时缓存的方式。通过 registerRoute() 注册路由规则，指定匹配条件和缓存策略。当用户请求匹配规则的资源时，Workbox 会自动应用指定的策略来处理缓存逻辑。


import { registerRoute } from 'workbox-routing';
import { CacheFirst } from 'workbox-strategies';

registerRoute(({ request }) => request.destination === 'image', new CacheFirst({ cacheName: 'images' }));
工作流程：


运行时缓存的工作流程是典型的惰性加载模式。用户首次访问某个资源时，从网络获取并写入缓存。下次访问相同资源时，根据配置的策略决定是从缓存返回还是从网络获取。这种方式确保了只有用户真正访问过的资源才会被缓存。


    

  • 用户访问时发起请求 → 获取图片 → 写入缓存。
    • 

  • 下次访问 → 直接从缓存返回。
    • 



适用场景：


运行时缓存适合那些无法在构建时确定的动态资源。大量的图片资源（如用户上传的头像、商品图片等）数量庞大且不断增长，不适合全部预缓存。API 响应数据因用户和时间而异，只能在请求时动态缓存。用户生成的内容（如评论、帖子等）同样需要运行时缓存。


    

  • 大量图片（图片库）。
    • 

  • API 响应数据。
    • 

  • 用户生成的内容。
    • 



协作模式
分层缓存架构：


在实际项目中，预缓存和运行时缓存通常配合使用，形成分层的缓存架构。应用外壳和关键静态资源使用预缓存保证离线可用性，动态内容使用运行时缓存按需加载。这种分层设计让应用既能快速启动（应用外壳从预缓存即时加载），又能覆盖用户访问过的所有内容。


    

  • 应用外壳 → 预缓存。
    • 

  • 静态资源（带哈希文件名） → 预缓存。
    • 

  • API 数据 → 运行时缓存（过期重验证策略）。
    • 

  • 图片 → 运行时缓存（缓存优先策略）。
    • 



完整 Service Worker 示例：


下面的代码展示了一个完整的分层缓存 Service Worker 配置。预缓存负责构建产物的提前缓存和自动更新，运行时路由为不同类型的动态资源配置了最合适的策略。导航请求使用网络优先确保页面新鲜度，API 使用过期重验证兼顾速度与新鲜度，图片使用缓存优先配合过期控制。


import { precacheAndRoute, cleanupOutdatedCaches } from 'workbox-precaching';
import { registerRoute, NavigationRoute } from 'workbox-routing';
import { CacheFirst, NetworkFirst, StaleWhileRevalidate } from 'workbox-strategies';
import { ExpirationPlugin } from 'workbox-expiration';

// 预缓存构建产物
precacheAndRoute(self.__WB_MANIFEST);
cleanupOutdatedCaches();

// 导航请求 → 应用外壳
registerRoute(new NavigationRoute(new NetworkFirst({ cacheName: 'pages' })));

// API → 过期重验证（运行时）
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/'),
  new StaleWhileRevalidate({
    cacheName: 'api',
    plugins: [new ExpirationPlugin({ maxAgeSeconds: 5 * 60 })],
  }),
);

// 用户图片 → 缓存优先（运行时）
registerRoute(
  ({ url }) => url.hostname.includes('images.example.com'),
  new CacheFirst({
    cacheName: 'images',
    plugins: [
      new ExpirationPlugin({
        maxEntries: 100,
        maxAgeSeconds: 30 * 86400,
      }),
    ],
  }),
);
首次访问性能影响
预缓存的代价：


预缓存虽然能提供优秀的离线体验，但它也有代价。在 Service Worker 安装阶段，所有预缓存清单中的资源都需要从网络下载。如果预缓存清单过大，首次安装时用户需要等待额外的下载完成，这在弱网环境下尤其明显。


    

  • 安装阶段需下载所有预缓存资源。
    • 

  • 预缓存 5MB 意味着首次安装需额外下载 5MB。
    • 

  • 弱网环境下首次加载明显变慢。
    • 



缓解措施：


为了缓解预缓存对首次访问性能的影响，应该严格控制预缓存的资源范围。只预缓存应用运行真正必需的最小资源集，将非关键资源留给运行时缓存按需加载。这种方式在保证离线能力的同时，最小化了对首次访问速度的影响。


    

  • 仅预缓存关键资源。
    • 

  • 非关键资源使用运行时缓存按需加载。
    • 



容量目标：


制定明确的缓存容量目标有助于保持合理的性能水平。预缓存的目标应该是尽可能小，只包含应用外壳和关键入口资源。总缓存占用也应该有上限，避免因缓存过大导致存储配额被耗尽。


    

  • 预缓存目标控制在 1MB 以内。
    • 

  • 总缓存占用控制在 5MB 以内。
    • 



存储配额管理
浏览器配额：


浏览器为每个源分配了有限的存储配额，这个配额由 Cache API、IndexedDB、localStorage 等所有存储 API 共享。了解配额限制对于合理设计缓存策略非常重要，避免因超出配额而导致缓存写入失败或被浏览器强制清理。


    

  • 大约为磁盘空间的 50%，按源（origin）分配。
    • 

  • 与 Cache API 共享配额。
    • 



检查存储使用量：


通过 Storage API 可以查询当前源的存储使用量和总配额。下面的代码展示了如何获取这些信息，这对于监控缓存健康状况和做出缓存管理决策很有帮助。


const { quota, usage } = await navigator.storage.estimate();
console.log(`${usage} / ${quota}`);
持久化存储：


默认情况下，浏览器在存储压力大时可能会自动清理某些源的数据。通过请求持久化存储，可以告诉浏览器不要在存储压力下驱逐该源的数据。这对于关键的离线应用非常重要，确保用户的离线数据不会被意外清除。


const granted = await navigator.storage.persist();
持久化后浏览器不会在存储压力下驱逐该源的数据，适合关键的离线应用。但需要注意的是，浏览器可能不会批准所有的持久化请求，通常只有用户经常访问的站点才能获得批准。


实际预算：


合理的存储预算应该考虑到预缓存和运行时缓存的总量。预缓存应该尽量精简，运行时缓存通过过期插件控制大小。总体存储使用量保持在浏览器配额的合理范围内。


    

  • 预缓存：< 5 MB。
    • 

  • 运行时缓存：通过 Workbox ExpirationPlugin 限制每个缓存的条目数。
    • 

  • 总计：通常不超过 50 MB。
    • 



何时使用预缓存
适合预缓存的条件：


选择预缓存资源时，应该从以下几个维度评估。频繁访问的资源预缓存后可以避免重复的网络请求。离线时必需的资源必须预缓存才能保证离线可用性。URL 稳定的资源或使用哈希命名的资源可以精确管理版本。非用户特定的公共资源适合在所有用户间共享缓存。


    

  • 频繁访问的资源。
    • 

  • 离线时必需的资源。
    • 

  • URL 稳定或使用哈希命名。
    • 

  • 非用户特定的公共资源。
    • 



不适合预缓存的条件：


某些资源不适合预缓存。大文件会显著增加安装时间。仅使用一次的资源预缓存后很少被复用，造成存储浪费。用户个人内容因用户而异，无法在 Service Worker 安装阶段确定内容。


    

  • 大文件。
    • 

  • 仅使用一次的资源。
    • 

  • 用户个人内容。
    • 



何时使用运行时缓存
适合运行时缓存的条件：


运行时缓存适合那些无法或不适合在构建时确定的资源。按需惰性加载的资源只在用户实际访问时才需要，没必要提前缓存。用户特定的内容（如个人头像、收藏列表）在登录前无法确定，只能在运行时按需缓存。大量的资源集合（如图片库中的所有图片）不可能全部预缓存，只能对用户访问过的进行缓存。


    

  • 按需惰性加载的资源。
    • 

  • 用户特定的内容。
    • 

  • 大量资源（图片库）。
    • 

  • 无法提前预知 URL 的资源。
    • 



混合策略
在实际项目中，预缓存和运行时缓存的边界需要根据资源的特性来划分。下面展示了典型的混合策略设计：


应用外壳 → 预缓存：页头、导航栏、布局框架。这些是应用运行的基础结构，需要在任何情况下都可用。


首页关键资源 → 预缓存：首屏核心内容。确保用户首次访问后再次打开时能立即看到完整的首屏内容。


其他页面 → 运行时缓存：按需加载。只有用户实际访问的页面才会被缓存，避免不必要的预加载。


静态资源 → 预缓存：JS / CSS / 字体。这些是应用正确运行和渲染的基础，必须保证可用性。


动态数据 → 运行时缓存：API 数据、用户内容。这些数据在构建时无法确定，只能在运行时按需处理。


缓存更新机制
预缓存更新：


预缓存的更新机制是自动化的。每次新构建产生新的 __WB_MANIFEST 清单，包含更新后的资源 URL 和修订哈希。当浏览器检测到 Service Worker 文件有变化并安装新版本时，Workbox 会比较新旧清单，自动重新缓存哈希变化的资源。激活时旧版本的缓存条目会被自动清理。


    

  • 新构建产生新的 __WB_MANIFEST。
    • 

  • Service Worker 安装时自动重新缓存变更的资源。
    • 

  • 激活时删除旧版缓存。
    • 



运行时缓存更新：


运行时缓存的更新行为由配置的策略决定。使用过期重验证策略的缓存会在每次请求时自动后台刷新。使用缓存优先策略的资源可能长时间不更新，直到 TTL 过期或被手动清理。选择合适的策略需要权衡数据新鲜度和响应速度。


    

  • 由缓存策略决定。
    • 

  • 过期重验证策略会自动后台刷新。
    • 

  • 缓存优先策略可能导致数据过时。
    • 



清理策略
Workbox 自动清理：


Workbox 提供了多种自动清理机制。ExpirationPlugin 按条目数和存储时间自动删除过期或超出限制的缓存条目。cleanupOutdatedCaches() 用于清理旧版本预缓存留下的缓存数据。这些机制确保了缓存占用始终在可控范围内。


    

  • ExpirationPlugin 按条目数和存储时间自动清理。
    • 

  • cleanupOutdatedCaches() 清理旧版预缓存。
    • 



手动清理：


在某些场景下可能需要手动清理缓存。下面的代码展示了一个简单的缓存修剪函数，当缓存中的条目超过最大值时，按先进先出的顺序删除最旧的条目。这种手动清理方式可以作为 Workbox 自动清理的补充。


async function trimCache(cacheName, maxItems) {
  const cache = await caches.open(cacheName);
  const keys = await cache.keys();
  if (keys.length > maxItems) {
    await cache.delete(keys[0]);
    trimCache(cacheName, maxItems);
  }
}
用户特定数据的缓存
按用户分离缓存：


当需要缓存用户特定的数据时，应该为每个用户创建独立的缓存空间，避免不同用户之间的数据互相污染。下面的代码展示了如何在用户登录后为该用户创建独立的缓存，将用户的个人资料和头像等数据缓存到用户专属的缓存空间中。


async function precacheForUser(userId) {
  const cache = await caches.open(`user-${userId}`);
  await cache.addAll([`/users/${userId}/profile`, `/users/${userId}/avatar`]);
}
此模式在用户登录后触发，而非标准的预缓存流程。用户登出时应该清理对应的缓存空间，避免下一个用户看到前一个用户的数据。


实战案例

Twitter Lite 是预缓存与运行时缓存协作的经典案例。它的预缓存策略非常精简，只预缓存了约 200 KB 的应用外壳和关键入口资源，确保了快速安装和即时离线能力。运行时缓存则覆盖了用户实际访问的推文图片和 API 响应，按需缓存用户感兴趣的内容。总体缓存占用不到 1 MB，在保证离线能力的同时不会占用过多存储空间。

常见反模式
1. 预缓存所有资源：


将所有资源都放入预缓存清单是一个常见错误。如果预缓存清单包含 50 MB 的资源，首次安装需要下载 50 MB 的额外数据，在弱网环境下可能导致安装失败或用户体验极差。应该严格筛选预缓存资源，只包含应用运行必需的最小集。


2. 预缓存用户特定内容：


如果在 Service Worker 安装阶段缓存了用户特定的内容，可能导致不同用户之间的数据泄露。因为 Service Worker 是全局共享的，一个用户的数据可能被另一个用户看到。用户特定的内容应该通过运行时缓存处理，并按用户隔离。


3. 完全不预缓存：


完全放弃预缓存意味着首次访问后应用没有任何离线能力。用户必须在线状态下访问所有页面才能建立缓存，应用外壳也无法离线使用。至少应该预缓存最基本的应用外壳资源。


4. 运行时缓存不设过期：


运行时缓存如果不配置过期策略，缓存会随着用户访问不断增长，最终可能耗尽存储配额。应该始终配合 ExpirationPlugin 设置合理的条目数和存储时间限制。


5. 不控制缓存预算：


如果不主动控制缓存的总体积，可能超出浏览器配额被强制清除。一旦被强制清除，预缓存和运行时缓存可能同时丢失，应用的离线能力瞬间消失。应该制定明确的缓存预算并持续监控。


6. 安装失败时静默忽略：


预缓存在下载资源时如果有任何一个资源下载失败，整个 Service Worker 安装都会失败。如果对这种情况不做处理，用户可能一直无法获得 Service Worker 的缓存能力。应该监控安装失败的情况，并考虑将非关键资源从预缓存清单中移除。


最佳实践
1. 审核资源清单：明确决定哪些预缓存、哪些运行时缓存，目标 < 1 MB 预缓存。定期审核预缓存清单中的资源，确保每个条目都是真正必需的。


2. 使用哈希文件名：预缓存的前提条件，部署时自动失效。哈希文件名让 Workbox 能精确识别哪些资源需要更新，避免不必要的重新下载。


3. 按资源类型选择运行时策略：API 用过期重验证、图片用缓存优先。根据每种资源的更新频率和用户期望选择最合适的策略。


4. 必须设置过期插件：防止缓存无限增长。每个运行时缓存都应该配置 ExpirationPlugin，设置合理的条目数和存储时间限制。


5. 测试离线场景：确认预缓存的资源足够支撑离线外壳。在开发过程中使用 Chrome DevTools 的离线模式测试，确保应用在离线状态下能正确显示应用外壳和关键内容。


6. 监控存储用量：通过 navigator.storage.estimate() 检查。定期检查缓存的实际使用量和剩余配额，及时发现和处理存储压力问题。


小结
预缓存和运行时缓存是 PWA 速度与可靠性的两大支柱。预缓存在安装阶段下载已知的关键资源，保证离线可用；运行时缓存按需动态缓存用户访问的内容。合理的分层策略——小体积预缓存保证即时离线外壳，积极的运行时缓存覆盖其余内容——让 PWA 既能快速首次加载，又能在离线环境下稳健运行。


设计缓存分层策略时，最重要的原则是"精简预缓存、积极运行时"。预缓存只包含应用核心骨架（应用外壳 HTML、入口 JS、关键 CSS、核心字体），总量控制在 1 MB 以内。运行时缓存则积极覆盖用户访问的各类动态内容，通过过期插件和容量限制确保存储可控。这种策略让应用既能在安装后立即离线使用，又不会因为过大的预缓存而拖慢首次访问速度。
