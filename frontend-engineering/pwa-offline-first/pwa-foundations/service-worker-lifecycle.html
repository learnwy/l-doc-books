Service Worker 生命周期

核心概念

Service Worker 是在浏览器独立线程中运行的后台 JavaScript——可拦截网络请求、缓存资源、处理推送通知和后台同步。它拥有独特的生命周期——install → activate → idle / fetch → terminate。理解生命周期是 PWA 工程化的基础——错误的处理会导致更新卡住、缓存过期、用户看到旧版本。Service Worker 是事件驱动且无状态的（频繁重启），与主线程 JS 的思维模式不同。本节详解 Service Worker 生命周期、事件处理器、作用域、更新策略、skipWaiting / clientsClaim 及调试方法。

生命周期事件 触发时机 用途
install 首次注册 预缓存静态资源
activate 安装完成且旧 SW 结束后 清理旧缓存
fetch 每次网络请求 拦截并缓存
message 页面 postMessage 通信
push 收到服务器推送 显示通知
sync 后台同步触发 重试失败请求
notificationclick 用户点击通知 打开 URL

Service Worker 基础

文件位置：/sw.js（根作用域）。

注册代码：

// 在主 JS 中注册
if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker
      .register('/sw.js')
      .then((reg) => console.log('SW registered', reg))
      .catch((err) => console.error('SW reg failed', err));
  });
}

运行环境：

  • 后台线程。
  • 无法访问 DOM。
  • 无法直接访问 localStorage（通过 Cache API + IndexedDB 异步存储）。

生命周期状态

Parsed：JS 文件已下载并解析。


Installing：install 事件正在触发。


Installed（waiting）：已安装但旧 Service Worker 仍在运行。


Activating：activate 事件正在触发。


Activated：正在处理 fetch 请求。


Idle：等待事件。


Terminated：浏览器为节省内存将其终止。


Install 事件
用途：预缓存关键资源。


self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('v1').then((cache) => {
      return cache.addAll(['/', '/styles.css', '/app.js', '/icon-192.png']);
    }),
  );
});
event.waitUntil：


    

  • 告知浏览器安装过程仍在进行。
    • 

  • 在 Promise resolve 前不要激活。
    • 

  • 失败则安装失败，下次注册时重试。
    • 



Activate 事件
用途：清理旧缓存。


self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((cacheNames) => {
      return Promise.all(cacheNames.filter((name) => name !== 'v1').map((name) => caches.delete(name)));
    }),
  );
});
为什么要清理：


    

  • 新版本 Service Worker 会使用新的缓存名称（v1 → v2）。
    • 

  • 旧缓存占用存储空间。
    • 

  • 需要删除旧缓存。
    • 



Fetch 事件
Service Worker 的核心——每个网络请求都经过这里。


self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return cached || fetch(event.request);
    }),
  );
});
event.respondWith：


    

  • 向浏览器返回一个 Response。
    • 

  • 必须同步调用（但可以返回 Promise）。
    • 



常见模式（详见缓存策略章节）：


    

  • Cache-first（缓存优先）。
    • 

  • Network-first（网络优先）。
    • 

  • Stale-while-revalidate（先缓存后更新）。
    • 



更新策略
浏览器自动检查 Service Worker 更新：


    

  • 每次页面导航时。
    • 

  • 文件内容有变化则更新。
    • 



更新流程：


    

  1. 下载新的 Service Worker 文件。
    2. 

  2. 触发新 Service Worker 的 install 事件。
    3. 

  3. 新 Service Worker 状态变为 installed (waiting)。
    4. 

  4. 旧 Service Worker 仍在运行。
    5. 

  5. 等待所有标签页关闭。
    6. 

  6. 触发新 Service Worker 的 activate 事件。
    7. 

  7. 新 Service Worker 接管。
    8. 



问题：


    

  • 用户可能一直开着标签页。
    • 

  • 可能要等很久才能更新。
    • 



解决方案：


    

  • 使用 skipWaiting + clientsClaim。
    • 



skipWaiting
跳过等待状态：


self.addEventListener('install', (event) => {
  self.skipWaiting();  // 安装完成后立即激活
  event.waitUntil(...);
});
效果：


    

  • 新 Service Worker 立即激活。
    • 

  • 不等待旧 Service Worker 释放控制权。
    • 



风险：


    

  • 页面可能使用旧 Service Worker 缓存的资源 → 版本不匹配。
    • 

  • 适合小型变更。
    • 



clientsClaim
接管现有客户端：


self.addEventListener('activate', (event) => {
  event.waitUntil(self.clients.claim());
});
效果：


    

  • 新激活的 Service Worker 立即控制所有打开的标签页。
    • 

  • 不等待页面导航。
    • 



用途：


    

  • 与 skipWaiting 配合使用。
    • 

  • 新 Service Worker 立即生效。
    • 



skipWaiting + clientsClaim 组合
self.addEventListener('install', (event) => {
  self.skipWaiting();
});

self.addEventListener('activate', (event) => {
  event.waitUntil(self.clients.claim());
});
结果：


    

  • 新 Service Worker 部署后立即生效。
    • 

  • 不等待标签页关闭。
    • 



风险：


    

  • 用户正在操作时可能出现版本不匹配。
    • 

  • 某些场景下等待更稳妥。
    • 



更新通知
最佳实践：


    

  • 不要自动 skipWaiting。
    • 

  • 通知用户"有新版本可用"。
    • 

  • 让用户点击"重新加载"按钮激活新版本。
    • 



// 主 JS
navigator.serviceWorker.addEventListener('controllerchange', () => {
  window.location.reload();
});

navigator.serviceWorker.register('/sw.js').then((reg) => {
  reg.addEventListener('updatefound', () => {
    const newSW = reg.installing;
    newSW.addEventListener('statechange', () => {
      if (newSW.state === 'installed' && navigator.serviceWorker.controller) {
        showUpdateButton(); // "有更新，点击重新加载"
      }
    });
  });
});

updateButton.onclick = () => {
  registration.waiting.postMessage({ type: 'SKIP_WAITING' });
};
// Service Worker
self.addEventListener('message', (event) => {
  if (event.data.type === 'SKIP_WAITING') {
    self.skipWaiting();
  }
});
作用域
Service Worker 作用域：


    

  • 控制的 URL 前缀。
    • 

  • 默认为 Service Worker 文件所在目录。
    • 

  • /sw.js → 作用域 /。
    • 

  • /app/sw.js → 作用域 /app/。
    • 



限制：


    

  • Service Worker 只能拦截作用域内的 fetch 请求。
    • 

  • 无法控制作用域外的页面。
    • 



自定义作用域：


navigator.serviceWorker.register('/sw.js', { scope: '/app/' });
通过 HTTPS 响应头 Service-Worker-Allowed 可提升作用域。


Service Worker 与浏览器交互
频繁重启：


    

  • 浏览器在空闲时终止 Service Worker。
    • 

  • 有事件时重启。
    • 



跨重启无状态：


    

  • 变量会丢失。
    • 

  • 使用 IndexedDB / Cache 保持持久化。
    • 



无法访问 DOM：


    

  • 不能访问 window / document。
    • 



通信机制
Service Worker → 页面：


// Service Worker
self.clients.matchAll().then((clients) => {
  clients.forEach((client) => client.postMessage({ msg: 'hello' }));
});
页面 → Service Worker：


navigator.serviceWorker.controller.postMessage({ msg: 'hello' });
Service Worker 监听：


self.addEventListener('message', (event) => {
  console.log(event.data);
});
调试方法
Chrome DevTools Application 面板：


    

  • Service Workers 区域。
    • 

  • 状态（running / waiting / redundant）。
    • 

  • Update on reload（刷新时更新）。
    • 

  • Bypass for network（绕过 Service Worker）。
    • 

  • Unregister（注销）。
    • 



Network 面板：


    

  • 查看哪些请求来自 Service Worker（对比缓存和网络）。
    • 



Service Worker 中的 console.log：


    

  • 日志出现在单独的控制台。
    • 

  • 在 Application 面板的 Service Worker 区域点击"Inspect"。
    • 



清除站点数据：


    

  • 右键点击站点 → Clear。
    • 

  • 重置 Service Worker + 缓存 + 存储。
    • 



常见陷阱
1. 难以更新：


    

  • skipWaiting / waiting 状态处理不当。
    • 

  • 使用更新通知机制。
    • 



2. 缓存永不过期：


    

  • Cache-first 策略没有重新验证。
    • 

  • 更新时更换缓存名称。
    • 



3. Service Worker 开发缓存：


    

  • 浏览器缓存了 sw.js 文件本身。
    • 

  • 为 sw.js 设置 Cache-Control: no-cache。
    • 



4. Fetch 处理器不总是运行：


    

  • 首次访问时页面不受 Service Worker 控制。
    • 

  • 第一次加载后才受控。
    • 



5. 异步 respondWith：


    

  • 必须同步调用 respondWith。
    • 

  • 内部返回 Promise 是允许的。
    • 



最佳实践
1. 使用版本化的缓存名称：


const CACHE_VERSION = 'v3';
caches.open(CACHE_VERSION);
2. 在 activate 时清理旧缓存：


    

  • 参见上文示例。
    • 



3. 不要缓存所有内容：


    

  • API 响应需谨慎处理。
    • 

  • POST / 需认证的请求不缓存。
    • 



4. 优雅处理离线：


    

  • 提供备用页面。
    • 



5. 更新策略：


    

  • 优先使用用户可见的更新通知。
    • 



6. 在无痕模式测试：


    

  • 获得干净的初始状态。
    •

小结
Service Worker 是在浏览器独立线程运行的后台 JavaScript——可拦截网络请求、处理缓存、推送通知、后台同步，采用事件驱动、无状态模式且无法访问 DOM。生命周期状态：parsed → installing → installed (waiting) → activating → activated → idle → terminated。Install 事件用于预缓存关键资源，使用 event.waitUntil(caches.open().addAll([...]))。Activate 事件用于清理旧缓存（过滤缓存名称并删除）。Fetch 事件是 Service Worker 的核心，event.respondWith(...) 必须同步调用，常见模式包括缓存优先、网络优先、先缓存后更新。默认更新策略需等待所有标签页关闭，skipWaiting 可立即激活，clientsClaim 可立即控制现有标签页，组合使用让新版本立即生效但有中途操作版本不匹配的风险。最佳实践是不自动 skipWaiting——通知用户"有更新"并提供重新加载按钮，通过 postMessage 触发 SKIP_WAITING。作用域控制 URL 前缀（默认为文件所在目录），可通过 register 选项自定义。Service Worker 频繁重启（浏览器在空闲时终止），跨重启无状态需使用 IndexedDB / Cache 持久化。通信方式包括 Service Worker 通过 clients.postMessage 发送消息、页面通过 navigator.serviceWorker.controller.postMessage 发送、Service Worker 通过 message 事件监听。调试工具包括 Chrome DevTools Application 面板查看状态/更新/注销、Network 面板区分请求来源、单独的 Service Worker 控制台查看日志。常见陷阱包括更新困难、缓存永不过期、sw.js 本身被缓存、首次访问不受控、异步调用 respondWith。最佳实践包括版本化缓存名称、activate 时清理旧缓存、不缓存所有内容、优雅处理离线、更新通知、无痕模式测试。现代工具 Workbox 抽象 Service Worker 模式，vite-plugin-pwa 和 next-pwa 提供框架集成。
