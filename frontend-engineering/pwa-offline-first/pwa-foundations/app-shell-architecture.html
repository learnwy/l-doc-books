App Shell 架构

核心概念

App Shell（应用外壳）是 PWA 的经典架构模式——把应用的"外壳"（核心 UI 导航和布局，不含动态内容）预缓存并从缓存提供，动态内容后续从网络获取。这让首次绘制极快（几百毫秒），内容加载后填充。Twitter Lite、Pinterest、Tinder Web 都是典型案例。对比传统服务端渲染（每页下载完整 HTML）和传统 SPA（大型初始包），App Shell 是 SPA 的"性能优化"版本。本节详解 App Shell 概念、与 SPA/SSR 对比、实现模式、与流式 SSR/岛屿架构的关系。

维度 服务端渲染 SPA App Shell
首次绘制 中等（需发送 HTML） 慢（需下载 JS） 极快（缓存外壳）
路由 服务端往返 客户端 客户端
离线 不支持 部分支持 完全支持
SEO 优秀 不友好 中等（需配合 SSR）
页面切换 完整重载 即时 即时

App Shell 组件划分

外壳（Shell）：

  • 页头 / 页脚 / 导航。
  • 布局结构。
  • 持久性 UI 元素。

内容（Content）：

  • 动态数据。
  • 各页面特定内容。
  • 延迟加载。

模式公式：

外壳（已缓存）+ 内容（网络获取）= 完整页面

示例：

  • Twitter 外壳：顶部导航 + 侧边菜单 + 发推按钮。
  • Twitter 内容：时间线推文。

为什么选择 App Shell

1. 快速首次绘制：

  • 外壳从缓存即时可用。
  • LCP 控制在 1 秒以内。

2. 可靠性：

  • 外壳离线可用。
  • 内容加载失败时可优雅降级。

3. 原生应用体验：

  • 导航无整页重载。
  • 过渡流畅。

4. 与 PWA 天然契合：

  • Service Worker 自然缓存外壳。

实现步骤

第一步：识别外壳内容：

  • 页头、导航、布局。
  • 不包含用户特定或动态数据。

第二步：积极缓存外壳：

// Service Worker install 事件
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('shell-v1').then((cache) => {
      return cache.addAll(['/', '/styles/main.css', '/scripts/app.js', '/scripts/router.js', '/icons/icon-192.png']);
    }),
  );
});

第三步：从缓存提供外壳：

self.addEventListener('fetch', (event) => {
  const url = new URL(event.request.url);

  // 导航请求 → 返回缓存的外壳
  if (event.request.mode === 'navigate') {
    event.respondWith(caches.match('/'));
    return;
  }

  // 静态资源 → 缓存优先
  event.respondWith(caches.match(event.request).then((cached) => cached || fetch(event.request)));
});

第四步：客户端获取内容：

function HomePage() {
  const [tweets, setTweets] = useState([]);

  useEffect(() => {
    fetch('/api/tweets')
      .then((r) => r.json())
      .then(setTweets);
  }, []);

  return <Timeline tweets={tweets} />;
}
流式 SSR 与 App Shell 对比
流式 SSR：


    

  • 服务端先发送外壳 → 客户端渲染。
    • 

  • 内容就绪后流式传输。
    • 

  • React 18 / Next.js Suspense 支持。
    • 



App Shell：


    

  • 外壳预缓存在客户端。
    • 

  • 无需服务端往返获取外壳。
    • 



对比：


    

  • 流式 SSR：首字节时间快（服务端）。
    • 

  • App Shell：缓存最快（客户端）。
    • 



混合方案：


    

  • 流式 SSR + 缓存外壳。
    • 

  • 兼得两者优势。
    • 



静态站点生成（SSG）
SSG + App Shell：


    

  • 构建时生成外壳。
    • 

  • 通过 Service Worker 缓存。
    • 

  • 运行时通过 API 获取内容。
    • 



框架支持：


    

  • Next.js、Gatsby、Astro、SvelteKit。
    • 



岛屿架构
Astro 等框架采用：


    

  • 服务端渲染大部分页面（静态）。
    • 

  • "岛屿"区域在客户端水合交互。
    • 



与 App Shell 对比：


    

  • 岛屿：服务端渲染 + 选择性交互。
    • 

  • App Shell：客户端渲染 + 缓存外壳。
    • 



现代混合方案：


    

  • 服务端渲染带岛屿的外壳。
    • 

  • 通过 Service Worker 缓存。
    • 



路由处理
客户端路由：


import { Routes, Route } from 'react-router';

<Routes>
  <Route path="/" element={<Home />} />
  <Route path="/profile" element={<Profile />} />
</Routes>;
导航特点：


    

  • 无服务端往返。
    • 

  • 更新 URL + 渲染组件。
    • 



按路由数据加载：


    

  • 使用 React Query / SWR / loader。
    • 



加载状态处理
关键点：


    

  • 外壳立即可见。
    • 

  • 内容仍在加载 → 显示骨架屏。
    • 



function Page() {
  const { data, isLoading } = useQuery('tweets');

  if (isLoading) return <SkeletonLoader />;
  return <Timeline data={data} />;
}
骨架屏：


    

  • 布局占位的灰色形状。
    • 

  • 比加载转圈体验更好。
    • 



乐观更新
立即显示用户操作结果：


function postTweet(text) {
  // 乐观更新
  setTweets([{ text, status: 'sending' }, ...tweets]);

  // 服务端请求
  fetch('/api/tweets', { method: 'POST', body: text })
    .then(() => updateStatus('sent'))
    .catch(() => updateStatus('failed'));
}
应用体验即时响应——即使在慢网络上。


后台刷新
模式：


    

  • 立即显示缓存内容。
    • 

  • 后台获取最新数据。
    • 

  • 新数据到达时更新 UI。
    • 



先缓存后更新策略：


// Service Worker
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      const fetchPromise = fetch(event.request).then((response) => {
        const cache = caches.open('v1');
        cache.then((c) => c.put(event.request, response.clone()));
        return response;
      });
      return cached || fetchPromise;
    }),
  );
});
动态外壳部分
部分外壳也是动态的：


    

  • 用户头像（每个用户不同）。
    • 

  • 通知数量。
    • 



处理策略：


    

  • 缓存带占位符的外壳。
    • 

  • 加载后填充占位符。
    • 



<header>
  <img id="avatar" src="/default-avatar.png" />
  <span id="notif-count">--</span>
</header>
// 加载后填充
fetch('/api/me')
  .then((r) => r.json())
  .then((me) => {
    document.getElementById('avatar').src = me.avatar;
    document.getElementById('notif-count').textContent = me.notifCount;
  });
多页面外壳
单页应用（SPA）单一外壳：


    

  • 整个应用一个 HTML。
    • 

  • 客户端路由。
    • 



多页应用（MPA）多外壳：


    

  • 不同页面有不同外壳。
    • 

  • 每个页面有各自的最小外壳。
    • 



选择建议：


    

  • SPA：单一外壳最常见。
    • 

  • MPA：不希望全 JS 化时使用。
    • 



缓存注意事项
外壳版本控制：


    

  • 外壳更新时刷新缓存。
    • 

  • 新缓存名称（shell-v2）。
    • 

  • activate 时清理旧缓存。
    • 



内容缓存：


    

  • 按 API 端点区分。
    • 

  • 根据数据类型设置 TTL。
    • 



存储限制：


    

  • 浏览器配额（通常为磁盘 50%）。
    • 

  • 注意控制。
    • 



Twitter Lite 案例
App Shell 实现：


    

  • 极小外壳（约 30KB）。
    • 

  • React 应用负责内容。
    • 

  • Service Worker 缓存外壳 + 关键 API。
    • 



成果：


    

  • LCP 控制在 1 秒。
    • 

  • 离线时间线可用。
    • 

  • 推送通知重新吸引用户。
    • 



反模式
1. 无外壳设计：


    

  • 每次导航完整重载。
    • 

  • 无法快速响应。
    • 



2. 外壳过大：


    

  • 100KB 的外壳违背初衷。
    • 



3. 不更新外壳：


    

  • 用户困在旧版本。
    • 



4. 内容无降级方案：


    

  • 内容加载失败 → 白屏。
    • 



5. 不区分外壳和内容：


    

  • 全部一起缓存。
    • 

  • 更新困难。
    • 



现代模式
1. React Server Components：


    

  • 服务端渲染数据 + 客户端外壳。
    • 



2. 流式 SSR：


    

  • 服务端发送外壳 → 流式传输内容。
    • 



3. 岛屿架构（Astro）：


    

  • 静态外壳 + 岛屿交互区。
    • 



4. 边缘 SSR：


    

  • 在靠近用户的边缘节点渲染。
    • 



趋势：


    

  • 纯 SPA App Shell 现在较少见。
    • 

  • 更多采用混合 SSR + Service Worker 缓存。
    • 



实战配置
Vite + PWA：


// vite.config.js
import { VitePWA } from 'vite-plugin-pwa';

export default {
  plugins: [
    VitePWA({
      registerType: 'autoUpdate',
      workbox: {
        globPatterns: ['**/*.{js,css,html,png,svg}'],

      },
    }),
  ],
};

  • 带外壳和运行时缓存的 Service Worker。

  • Manifest 文件。

小结
App Shell 架构将应用外壳（核心 UI，不含动态内容）预缓存并从缓存提供，动态内容后续获取——首次绘制极快、离线可靠、体验接近原生。组件划分为外壳（页头/导航/布局）+ 内容（动态数据/页面特定内容）。实现步骤：识别外壳 → Service Worker install 预缓存 → fetch 处理器返回缓存的外壳 → 客户端获取内容。流式 SSR 首字节快，App Shell 缓存最快，混合方案最佳。SSG + App Shell（Next.js/Gatsby/Astro/SvelteKit）构建时生成外壳，通过 Service Worker 缓存。岛屿架构（Astro）服务端渲染主体 + 选择性交互水合，与 App Shell 是不同范式。客户端路由无服务端往返，按路由数据通过 React Query/SWR/loader 加载。加载状态处理：外壳立即可见 + 骨架屏占位内容。乐观更新立即显示用户操作，服务端确认后更新，失败则回滚。后台刷新采用先缓存后更新策略。动态外壳部分（头像/通知数）用占位符 + 后填充。多页面外壳：SPA 单一外壳最常见，MPA 按页面最小外壳。缓存注意版本控制、内容按端点 TTL、存储配额。Twitter Lite 案例约 30KB 外壳，1 秒 LCP，离线时间线可用。反模式：无外壳、外壳过大、不更新、无降级、不区分。现代趋势是混合 React Server Components/流式 SSR/岛屿/边缘 SSR + Service Worker 缓存。Vite + PWA 插件自动生成 Service Worker 和 Manifest。
