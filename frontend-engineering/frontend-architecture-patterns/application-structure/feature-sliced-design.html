Feature Sliced Design 方法论

概述

Feature Sliced Design (FSD) 是一套标准化的前端架构方法论，通过分层（Layers）和切片（Slices）两个维度组织代码。与随意的 components/pages/utils 目录结构不同，FSD 提供了严格的导入规则和职责边界，从架构层面消除循环依赖、降低耦合度。2026 年，FSD 已从俄罗斯前端社区走向全球，配套的 Steiger 静态分析工具可以在 CI 中自动检测架构违规。

核心概念

七层架构

FSD 将代码组织为 7 个标准化层，从高到低排列：

核心导入规则：一个模块只能导入其正下方层级的模块。features 可以导入 entities 和 shared，但不能导入 widgets 或 pages。同层级的切片之间互相不可导入。

shared
可复用工具、UI 组件、配置
shared/ui, shared/api, shared/lib





Slice 与 Segment
每一层内部由多个 Slice（切片）组成，每个 Slice 代表一个独立的业务概念。每个 Slice 内部通过 Segment（段）划分技术关注点：


src/features/add-to-cart/
├── ui/          → React 组件
│   ├── AddToCartButton.tsx
│   └── CartQuantityInput.tsx
├── model/       → 业务逻辑和状态
│   ├── store.ts
│   └── types.ts
├── api/         → 数据请求
│   └── addToCart.ts
├── lib/         → 工具函数
│   └── validateQuantity.ts
└── index.ts     → Public API (唯一出口)
Public API 原则：外部只能通过 Slice 根目录的 index.ts 访问内容。任何内部模块的直接导入都是架构违规。


// ✅ 正确：通过 Public API 导入
import { AddToCartButton } from '@/features/add-to-cart';

// ❌ 错误：直接访问内部模块
import { AddToCartButton } from '@/features/add-to-cart/ui/AddToCartButton';

与 Next.js App Router 集成
FSD 与 Next.js App Router 的关键整合点在于路由目录(/app) 与业务逻辑(/src) 的分离：


// app/ 目录只负责路由，不包含业务逻辑
// app/articles/[id]/page.tsx
import { ArticlePage } from '@/pages/article-read';

export default function Page({ params }: { params: { id: string } }) {
  return <ArticlePage articleId={params.id} />;
}

// src/pages/article-read/ui/ArticlePage.tsx
import { ArticleCard } from '@/widgets/article-card';
import { CommentSection } from '@/features/article-comments';
import { getArticle } from '@/entities/article';

export async function ArticlePage({ articleId }: { articleId: string }) {
  const article = await getArticle(articleId);
  return (
    <main>
      <ArticleCard article={article} />
      <CommentSection articleId={articleId} />
    </main>
  );
}

      "@/features/*": ["src/features/*"],
      "@/entities/*": ["src/entities/*"],
      "@/shared/*": ["src/shared/*"]
    }
  }

最佳实践
Feature vs Entity 的区分
这是 FSD 中最常见的困惑点：


    

  • Entity（实体）：业务域中的"名词"。user、article、product、order 是实体。它们代表数据模型、展示 UI 和基础 CRUD。
    • 

  • Feature（功能）：用户可执行的"动词"。auth（登录/注册）、add-to-cart（加入购物车）、leave-comment（发表评论）是功能。
    • 



// entities/article - 文章的展示和数据模型
export { ArticlePreview } from './ui/ArticlePreview';
export { type Article } from './model/types';
export { getArticles } from './api/getArticles';

// features/article-bookmark - 收藏文章的交互功能
export { BookmarkButton } from './ui/BookmarkButton';
export { useBookmarkStore } from './model/store';
渐进式迁移策略
对已有项目，推荐的迁移顺序：


    

  1. 先建 shared 层：提取公共 UI 组件、API 客户端、工具函数
    2. 

  2. 建立 entities 层：识别核心业务模型，将其数据获取和类型定义归类
    3. 

  3. 建立 features 层：将用户交互逻辑从页面组件中抽离
    4. 

  4. 最后处理 pages 和 widgets：将页面组件中的直接导入替换为层级间的正确导入
    5. 



Steiger 静态检查配置
// steiger.config.ts
import { defineConfig } from '@feature-sliced/steiger';

export default defineConfig({
  rules: {
    'no-cross-slice-imports': 'error', // 禁止同层切片间导入
    'no-public-api-bypass': 'error', // 禁止绕过 index.ts
    'no-layer-violation': 'error', // 禁止向上层导入
    'no-deprecated-layers': 'warn', // 警告使用 processes 层
  },
});

总结
FSD 的核心价值在于用规则替代约定——通过严格的层级导入规则和 Public API 边界，从架构层面防止"代码腐烂"。它特别适合 3 人以上团队维护的中大型项目，能显著降低新成员上手成本和跨功能修改的风险。结合 Steiger 等自动化工具，FSD 的架构约束可以在 CI 中持续验证，确保项目随时间推移保持结构清晰。选择 FSD 的关键前提是团队愿意投入学习成本——理解 entity 和 feature 的边界、掌握 Public API 的设计——这个前期投入将在项目中后期获得数倍的维护效率回报。
