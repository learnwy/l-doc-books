渐进式迁移模式

概述

前端架构迁移中最危险的策略是"大爆炸重写"——暂停业务开发数月，用全新技术栈重建整个应用。历史数据表明超过 70% 的大重写项目延期或失败。渐进式迁移则相反：在持续交付业务价值的同时，逐步用新架构替代旧实现，直到旧代码被完全淘汰。本文总结从 SPA 到 SSR/Islands、从 Webpack 到 Rspack/Vite、从整体式到微前端的典型迁移路径，以及 Strangler Fig 模式、路由级灰度等经过验证的迁移策略。

核心概念

Strangler Fig 模式

命名来自热带的绞杀榕——新系统包裹旧系统生长，最终完全替代，旧系统自然消亡。关键原则：


    

  • 新旧系统共存运行，新功能在新架构中实现
    • 

  • 通过路由层控制流量分配，对用户无感知
    • 

  • 旧系统不再接收新功能，仅维护修复
    • 

  • 迁移进度可量化（已迁移路由数/总路由数）
    •

迁移路径 1：SPA → SSR/Islands
// 阶段 1: 在现有 SPA 外围包裹 Astro/Next.js 壳
// next.config.js - 新旧共存
module.exports = {
  async rewrites() {
    return [
      // 已迁移的路由走 Next.js
      { source: '/blog/:path*', destination: '/blog/:path*' },
      { source: '/docs/:path*', destination: '/docs/:path*' },
      // 未迁移的路由代理到旧 SPA
      {
        source: '/:path*',
        destination: 'http://localhost:3001/:path*', // 旧 SPA dev server
      },
    ];
  },
};
// 阶段 2: 将旧 SPA 作为 Next.js 的一个 client-only 路由
// app/app/[[...slug]]/page.tsx
'use client';
import { LegacySPA } from '@/legacy/LegacySPA';

export default function LegacyAppRoute() {
  return <LegacySPA />;
}
// 逐步将旧 SPA 中的页面迁移为 Next.js Server Components
// 阶段 3: 共享认证和状态
// 旧 SPA 和新 SSR 页面之间通过 Cookie/Token 共享会话
// middleware.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(request: NextRequest) {
  const token = request.cookies.get('auth-token');
  if (!token && request.nextUrl.pathname.startsWith('/dashboard')) {
    return NextResponse.redirect(new URL('/login', request.url));
  }
  return NextResponse.next();
}

Rspack 提供了与 Webpack 高度兼容的 API，迁移通常在 1-4 周内完成：


// 步骤 1: 安装 Rspack
// npm install @rspack/core @rspack/cli -D

// 步骤 2: 重命名配置文件
// webpack.config.js → rspack.config.ts

// 步骤 3: 替换不兼容的 loader/plugin
// rspack.config.ts
import { defineConfig } from '@rspack/cli';

export default defineConfig({
  module: {
    rules: [
      {
        test: /\.(ts|tsx)$/,
        // 替换: babel-loader → builtin:swc-loader (内置，更快)
        use: {
          loader: 'builtin:swc-loader',
          options: {
            jsc: {
              parser: { syntax: 'typescript', tsx: true },
              transform: { react: { runtime: 'automatic' } },
            },
          },
        },
      },
    ],
  },
  plugins: [
    // 大部分 Webpack 插件可直接复用
    // 不兼容的替换为 Rspack 内置能力
  ],
});

迁移路径 3：Monolith → 微前端
阶段 1：识别团队边界和功能边界，确定第一个待抽取的子应用（选择变更频率最高、团队职责最清晰的模块）。


阶段 2：提取共享基础设施（设计系统、API 客户端、认证逻辑）为独立包。


阶段 3：将第一个功能模块抽取为独立构建的远程应用，通过 Module Federation 集成回 Shell。


阶段 4：逐步抽取更多模块，每次只迁移一个功能域。


阶段 5：旧 monolith 缩减为纯 Shell + 路由，所有功能都在独立远程中运行。

总结
成功的前端架构迁移遵循一个核心原则：每一步都是可部署的、可回滚的、对用户透明的。Strangler Fig 模式是实现这一原则的最佳框架——新系统在旧系统周围生长，通过路由层控制流量，从最小切面开始验证新架构的可行性。迁移速度取决于三个因素：测试覆盖率（决定回归信心）、Feature Flag 粒度（决定回滚速度）、监控灵敏度（决定问题发现时间）。将架构迁移视为持续进行的日常工作，而非一次性的"项目"——这种心态转变是渐进式迁移成功的根本保障。
