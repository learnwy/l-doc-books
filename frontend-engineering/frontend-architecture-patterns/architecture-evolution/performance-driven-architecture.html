性能驱动架构决策

概述

架构决策不应由技术热度驱动，而应由可量化的性能目标倒推。Core Web Vitals（LCP、INP、CLS）已成为 Google 搜索排名因素和用户体验的量化标尺。本文将这些指标转化为架构选型的决策依据：从性能预算的建立，到基于真实用户数据的架构取舍，再到持续的性能守护机制。核心观点是——每一个架构决策都有对应的性能代价和收益，这些代价必须被量化而非凭直觉判断。

实战指南
基于 LCP 的渲染策略选择
// 决策框架：根据 LCP 目标反推渲染策略
function chooseRenderingStrategy(page: PageProfile): RenderingStrategy {
  const { lcpTarget, dynamicDataRatio, trafficVolume, seoRequired } = page;

  // LCP < 1.5s 且不需要个性化 → SSG
  if (lcpTarget < 1500 && dynamicDataRatio < 0.2 && !page.needsPersonalization) {
    return 'SSG';
  }

  // LCP < 2.5s 且需要数据但 SEO 重要 → ISR or SSR + Streaming
  if (lcpTarget < 2500 && seoRequired) {
    return dynamicDataRatio < 0.5 ? 'ISR' : 'SSR_STREAMING';
  }

  // 纯交互不需要 SEO → CSR (但控制 bundle size)
  if (!seoRequired && dynamicDataRatio > 0.8) {
    return 'CSR_WITH_CODE_SPLITTING';
  }

  // 内容为主 + 少量交互 → Islands
  if (dynamicDataRatio < 0.3 && page.interactiveComponentRatio < 0.2) {
    return 'ISLANDS';
  }

  return 'SSR_STREAMING'; // 默认安全选择
}

性能与功能的权衡决策
当新功能会突破性能预算时的决策流程：


    

  1. 量化影响：该功能增加多少 KB？影响哪些 CWV 指标？
    2. 

  2. 探索替代：有无更轻量的实现方式？能否 lazy load？
    3. 

  3. 交换空间：能否通过优化其他模块腾出预算？
    4. 

  4. 业务论证：功能的商业价值是否值得性能代价？
    5. 

  5. 条件加载：能否仅在特定用户群/设备上加载？

// 基于 RUM 数据的架构决策反馈循环
// lib/performance-reporter.ts
import { onLCP, onINP, onCLS } from 'web-vitals';

function reportToAnalytics(metric: Metric) {
  // 按页面、设备、网络分段上报
  const payload = {
    name: metric.name,
    value: metric.value,
    page: window.location.pathname,
    device: getDeviceType(),
    connection: (navigator as any).connection?.effectiveType,
    renderStrategy: document.querySelector('meta[name="render-strategy"]')?.content,
  };

  navigator.sendBeacon('/api/vitals', JSON.stringify(payload));
}

onLCP(reportToAnalytics);

总结
性能驱动架构决策的核心是建立"性能预算 → 测量 → 决策 → 验证"的闭环。每个架构选择都应有对应的性能预期和验证手段。LCP 目标决定渲染策略，INP 目标决定 JS 加载量，CLS 目标决定布局方案。将性能约束写入 CI 流水线（Lighthouse CI + Bundlewatch），让性能回归像 TypeScript 类型错误一样在合并前被拦截。最终目标不是追求极致性能，而是让性能决策从"凭经验猜测"变成"用数据说话"——当团队对性能影响有清晰的量化认知时，架构权衡就变得理性而高效。
