什么是设计系统

核心概念

设计系统（Design System）是产品界面的"工业化"——将散乱的临时样式、分散的组件、不一致的设计提升为系统化、版本化、跨平台的产品基础设施。它不只是组件库，也不只是样式指南——而是组件、设计原则、令牌、文档、治理流程与工具链的综合体。Material Design（Google 2014）开创了行业级设计系统的先河，IBM Carbon、Atlassian Design、Salesforce Lightning、Adobe Spectrum、Shopify Polaris、Microsoft Fluent 是业界标杆案例。一个成熟的设计系统让公司多个产品团队共享界面基元、保证一致性、加速开发、降低维护成本。本节介绍设计系统定义、与组件库和样式指南的区别、成熟度模型、企业为何需要、以及投资回报率。

维度 样式指南 组件库 设计系统
包含 仅文档 代码组件 组件 + 令牌 + 原则 + 文档 + 工具
令牌 无 有时有 必须包含
文档 是核心产出 可选 必须包含
治理 无 轻量 有专属团队
工具链 无 轻量 完整流水线
跨平台 无 有时 必须
代表案例 纽约时报样式指南 Bootstrap Material Design

设计系统包含什么

1. 基础层（Foundations）：

  • 颜色色板与令牌。
  • 排版比例系统。
  • 间距比例系统。
  • 图标体系。
  • 动效与动画。
  • 声音与触觉反馈。

2. 组件层（Components）：

  • 按钮、表单、卡片、模态框、标签页等。
  • 预构建且经过测试的组件。
  • 每个组件包含多个变体。

3. 模式层（Patterns）：

  • 表单模式、导航模式、反馈模式等。
  • 高层级的可复用解决方案。

4. 指导原则（Guidelines）：

  • 品牌语气与风格。
  • 设计原则（无障碍性、一致性等）。
  • 推荐与不推荐的用法。

5. 文档层（Documentation）：

  • 每个组件的使用场景。
  • 代码示例。
  • 无障碍注释。
  • 组件结构图。

6. 工具链（Tooling）：

  • Figma 组件库。
  • npm 包（Web 端）。
  • iOS / Android 原生库。
  • Storybook / Zeroheight 文档平台。

7. 治理层（Governance）：

  • 专属团队负责。
  • 贡献流程。
  • 版本管理。
  • 废弃策略。

设计系统与组件库、样式指南的区别

样式指南（最早期形态）：

  • 仅文档形式（PDF 或网站）。
  • 如"使用 Helvetica 字体"、"主色为 #007AFF"。
  • 没有代码实现，无强制力。
  • 仅供设计师参考。

组件库（进阶形态）：

  • 提供代码组件。
  • Bootstrap、Tailwind UI 等。
  • 用户安装后即可使用。
  • 但缺乏整体设计约束。

设计系统（综合形态）：

  • 组件库 + 设计原则 + 令牌 + 文档 + 治理 + 工具链。
  • 跨平台支持。
  • 当作产品来运营。
成熟度模型
级别 0 — 无：


    

  • 每个产品团队各自构建界面。
    • 

  • 没有共享资源。
    • 

  • 不一致性严重。
    • 



级别 1 — 样式指南：


    

  • 有 PDF 或网站文档。
    • 

  • 但难以强制执行。
    • 



级别 2 — 组件库：


    

  • 共享代码组件。
    • 

  • 但没有系统化的治理和文档。
    • 



级别 3 — 设计系统：


    

  • 整体系统化。
    • 

  • 有专属团队。
    • 

  • 多产品使用。
    • 



级别 4 — 设计语言：


    

  • 跨多品牌支持。
    • 

  • 完善的主题化能力。
    • 

  • 成熟的工具链。
    • 



典范级别 4 案例：


    

  • Material Design（Google）。
    • 

  • Apple Human Interface Guidelines。
    • 

  • Carbon（IBM）。
    • 



为什么公司需要设计系统
1. 一致性：


    

  • 多个产品团队保持一致的用户体验。
    • 

  • 用户在不同产品间可迁移使用经验。
    • 



2. 速度：


    

  • 不重复设计和构建组件。
    • 

  • 加快产品开发速度。
    • 



3. 质量：


    

  • 组件经过充分测试。
    • 

  • 无障碍性内建其中。
    • 



4. 维护性：


    

  • 单一真实来源。
    • 

  • 修改一处即影响所有产品。
    • 



5. 新人上手：


    

  • 新加入的设计师和工程师学习一次系统即可开始工作。
    • 



6. 品牌统一：


    

  • 跨产品的品牌一致性。
    • 



7. 可扩展性：


    

  • 从一个产品到一百个产品无需重新设计。
    • 



反例：没有设计系统的后果
典型症状：


    

  • 多个团队各自实现按钮组件，出现三十种按钮变体。
    • 

  • 颜色值散落在代码各处，无法系统化更新。
    • 

  • 设计师与工程师反复讨论"按钮应该多大"。
    • 

  • 无障碍性不一致——某产品合规而另一个不合规。
    • 

  • 品牌更新时需修改上百处代码。
    • 



代价：


    

  • 时间成本极高。
    • 

  • 用户感受到不一致。
    • 

  • 维护负担持续增长。
    • 



投资回报率
建设成本：


    

  • 首年需要 4-10 名专属全职人员。
    • 

  • 持续维护需 4-6 名全职人员。
    • 

  • 工具链投入。
    • 



回报：


    

  • Atlassian 内部研究显示节省 30-50% 的界面开发时间。
    • 

  • 加快产品交付。
    • 

  • 减少设计债务。
    • 

  • 团队间对齐成本降低。
    • 



投资回报率通常很高——但前 6-12 个月投入大、回报慢。


行业案例
Material Design（Google）：


    

  • 2014 年发布。
    • 

  • 横跨 Google 全产品线。
    • 

  • 开源。
    • 

  • 影响了整个行业。
    • 



Apple HIG：


    

  • 自 1980 年代持续演进。
    • 

  • 非开源。
    • 

  • 深度集成到平台中。
    • 



Carbon（IBM）：


    

  • 2017 年开源。
    • 

  • 覆盖 IBM Watson、Cloud 等产品。
    • 



Polaris（Shopify）：


    

  • 2017 年发布。
    • 

  • 面向商家界面。
    • 



Spectrum（Adobe）：


    

  • 2018 年发布。
    • 

  • 跨越 Photoshop、Illustrator 等 Creative Cloud 产品。
    • 



Fluent（Microsoft）：


    

  • 2017 年发布。
    • 

  • 覆盖 Office 365 和 Windows。
    • 



Lightning（Salesforce）：


    

  • 2014 年发布。
    • 

  • 在内部和客户端都非常成功。
    • 



设计系统团队组织
集中式团队：


    

  • 全公司共享同一个设计系统。
    • 

  • 优点：一致性高。
    • 

  • 缺点：容易成为瓶颈。
    • 



联邦式：


    

  • 核心团队加产品团队贡献者。
    • 

  • 优点：可扩展性强。
    • 

  • 缺点：治理复杂。
    • 



混合式（最常见）：


    

  • 核心团队维护框架。
    • 

  • 产品团队通过提交代码来贡献。
    • 



角色：


    

  • 设计系统设计师。
    • 

  • 设计系统工程师。
    • 

  • 设计系统产品经理。
    • 

  • 文档撰写者。
    • 

  • 设计运营。
    • 



何时应建设设计系统
适合建设的信号：


    

  • 多个产品团队。
    • 

  • 多平台（Web / iOS / Android）。
    • 

  • 不一致性投诉增多。
    • 

  • 重复设计和构建。
    • 

  • 品牌更新频繁。
    • 



暂不建设的信号：


    

  • 单一产品早期阶段。
    • 

  • 设计师少于五人。
    • 

  • 使用 Material 或 Bootstrap 即可满足需求。
    • 

  • 资源不足以投入专属人员。
    • 



第三方 vs 自建：


    

  • 早期：使用 Material 或 Tailwind UI。
    • 

  • 中期：定制化改造。
    • 

  • 大公司：自建以控制品牌和需求。
    • 



设计系统与工程
代码库：


    

  • React 组件库。
    • 

  • iOS / Android 原生库。
    • 

  • 主题与令牌集中管理。
    • 



分发方式：


    

  • npm（Web 端）。
    • 

  • CocoaPods / SPM（iOS 端）。
    • 

  • Maven（Android 端）。
    • 

  • Tauri / Electron（桌面端）。
    • 



持续集成/持续交付：


    

  • 自动化测试。
    • 

  • 视觉回归测试。
    • 

  • Storybook 自动部署。
    • 

  • 语义化版本管理。
    • 



设计系统与设计师
Figma 组件库：


    

  • 组件以 Figma 组件形式存在。
    • 

  • 令牌以 Figma 变量或样式形式存在。
    • 

  • 设计师在设计时直接使用组件。
    • 



Figma 与代码的偏差问题：


    

  • 设计师在 Figma 中修改后，工程师实现可能跟不上，导致偏差。
    • 

  • 解决方案：Tokens Studio 同步 Git，自动更新 Figma 和代码。
    • 



文档
设计系统文档是核心交付物：


组件文档：


    

  • 结构标注（各部分标签）。
    • 

  • 变体（主要、次要、禁用等）。
    • 

  • 状态（悬停、激活、焦点）。
    • 

  • 规格（内边距、圆角、颜色）。
    • 

  • 代码示例。
    • 

  • 推荐与不推荐用法。
    • 

  • 无障碍注释。
    • 



文档工具：


    

  • Storybook（组件演示平台）。
    • 

  • Zeroheight（设计与代码文档合一）。
    • 

  • 静态站点（Jekyll、Docusaurus）。
    • 



质量标准：


    

  • 可搜索。
    • 

  • 持续更新。
    • 

  • 示例可直接复制使用。
    • 



反模式
1. 只建不推广：


    

  • 建好了但没人使用。
    • 

  • 从一开始就要规划采纳策略。
    • 



2. 冻结不更新：


    

  • 不演进，产品团队觉得受限。
    • 

  • 需要积极维护。
    • 



3. 仅设计师主导：


    

  • 没有工程师协作导致实施差距。
    • 



4. 缺少治理：


    

  • 任何人随意更改导致混乱。
    • 

  • 必须有流程规范。
    • 



5. 过度约束：


    

  • 锁定一切。
    • 

  • 产品团队感到沮丧。
    • 

  • 需要允许一定灵活性。
    • 



6. 不衡量采纳率：


    

  • 不知道系统是否生效。
    • 

  • 应追踪使用设计系统组件的界面占比。
    • 



现代趋势
1. AI 辅助设计：


    

  • Figma AI、Galileo 等。
    • 

  • 自动生成变体。
    • 



2. 设计令牌标准化：


    

  • W3C Design Tokens 规范。
    • 

  • 跨工具互操作。
    • 



3. 无样式组件（Headless）：


    

  • Radix UI、Headless UI。
    • 

  • 逻辑和无障碍性封装好，样式由用户自定义。
    • 



4. 跨平台统一：


    

  • 同一套令牌覆盖 Web / iOS / Android。
    • 

  • React Native + Web 通用方案。
    • 



5. AI 智能体集成：


    

  • 大语言模型利用设计系统自动构建界面。
    • 



实战建议
1. 从小处开始：


    

  • 先做颜色 + 排版 + 五个核心组件。
    • 

  • 然后逐步扩展。
    • 



2. 先服务真实产品：


    

  • 与实际产品团队一起构建。
    • 

  • 不在真空中闭门造车。
    • 



3. 文档与组件同步：


    

  • 不作为事后补充。
    • 

  • 组件与文档在同一次提交中完成。
    • 



4. 以采纳率为目标：


    

  • "有多少产品在使用？"比"构建了多少组件？"更重要。
    • 



5. 尽早建立治理：


    

  • 确定谁负责、如何贡献。
    • 



6. 当作产品来运营：


    

  • 路线图、发布计划、废弃策略。
    • 



小结
设计系统是产品界面的工业化——超越组件库和样式指南，包含令牌、组件、原则、文档、治理、工具链的综合体。Material Design、Apple HIG、Carbon、Polaris、Spectrum、Fluent、Lightning 是行业标杆。它包含基础层（颜色/排版/间距/图标/动效）、组件层、模式层、指导原则、文档层、工具链和治理层。从样式指南到组件库再到设计系统是一个渐进过程。成熟度分为 0-4 级。公司需要设计系统是因为一致性、速度、质量、维护性、新人上手、品牌统一和可扩展性。投资回报率通常很高——Atlassian 研究显示节省 30-50% 开发时间。团队组织可以是集中式、联邦式或混合式。适合建设的条件是多产品、多平台、不一致性投诉增多。反模式包括只建不推广、冻结不更新、缺少治理等。现代趋势包括 AI 辅助设计、W3C 令牌标准、无样式组件、跨平台统一和 AI 智能体集成。核心建议是从小处开始、服务真实产品、文档同步、以采纳率为目标、尽早建立治理、当作产品来运营。一个简单的检验：你能区分设计系统与组件库的本质差异吗？如果不能，概念边界还需巩固。设计系统是成熟公司的界面基础设施——投资期长但长期回报巨大。
