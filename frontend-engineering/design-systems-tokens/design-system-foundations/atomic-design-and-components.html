Atomic Design 与组件化

核心概念

Atomic Design（Brad Frost 2013）是设计系统组件组织的方法论——将界面分为五个抽象层级：原子（最小元素，如按钮、输入框、标签）→ 分子（原子组合，如搜索栏 = 输入框 + 按钮）→ 有机体（分子与原子组合，如导航栏 = 标志 + 搜索栏 + 菜单）→ 模板（有机体与原子组成的布局，无真实内容）→ 页面（模板加真实内容）。这种层级思维让组件可以系统化地构建和复用。本节介绍 Atomic Design 五个层级、与 React 组件的关系、组件化决策（什么进入系统、什么不进入）、组合模式（复合组件、渲染属性、无样式组件）、现代趋势（设计系统框架、无样式界面组件库）。

层级 例子 复用率 是否进设计系统
原子 Button、Input、Label 极高 必须包含
分子 SearchBar、FormField 高 必须包含
有机体 Header、CardList 中 大部分
模板 PageLayout 低 少数
页面 特定页面 极低 不进入

Atomic Design 五个层级

原子（Atom）：

  • 最小界面元素。
  • 无法再拆分为有用的界面单元。
  • 例子：按钮、输入框、标签、图标、头像。
  • 到处高频复用。

分子（Molecule）：

  • 多个原子组合形成的简单组件。
  • 仍具有单一用途。
  • 例子：搜索栏 = 输入框 + 按钮。
  • 表单字段 = 标签 + 输入框 + 提示文本。

有机体（Organism）：

  • 多个分子和原子组成的独立界面区块。
  • 自包含。
  • 例子：导航栏 = 标志 + 搜索栏 + 菜单项 + 用户头像。
  • 卡片网格 = 多个卡片。

模板（Template）：

  • 页面级结构。
  • 内容占位符。
  • 聚焦于布局。
  • 例子：文章模板 = 页头 + 侧边栏 + 主内容区。

页面（Page）：

  • 模板的具体实例。
  • 真实内容。
  • 用户最终看到的输出。
原子组件设计
目标：


    

  • 极度可复用。
    • 

  • 尽可能无状态。
    • 

  • 最小化接口。
    • 



构成要素：


    

  • 视觉样式（颜色、内边距、圆角）。
    • 

  • 行为（悬停、焦点、禁用状态）。
    • 

  • 变体（主要、次要、危险）。
    • 

  • 尺寸（小、中、大）。
    • 



按钮实例：


<Button variant="primary" size="md" onClick={...}>
  保存
</Button>
变体通过属性控制——而不是创建不同的组件。


分子组件设计
目标：


    

  • 组合原子实现特定任务功能。
    • 

  • 仍然可复用。
    • 



搜索栏实例：


<SearchBar
  placeholder="搜索..."
  onSearch={(query) => ...}
/>
内部实现：


<div className="search-bar">
  <Input ... />
  <Button icon="search" ... />
</div>
有机体组件设计
目标：


    

  • 页面的独立区块。
    • 

  • 多个分子和原子组合。
    • 



商品卡片实例：


    

  • 图片原子。
    • 

  • 标题和价格分子。
    • 

  • 评分分子。
    • 

  • 添加到购物车按钮原子。
    • 



<ProductCard product={product} onAddToCart={...} />
React 组件与 Atomic Design
对应关系：


    

  • 原子 → 底层 React 组件。
    • 

  • 分子 → 复合组件。
    • 

  • 有机体 → 功能组件。
    • 

  • 模板 → 布局组件。
    • 

  • 页面 → 路由级组件。
    • 



实际文件结构：


components/
  atoms/
    Button/
    Input/
  molecules/
    SearchBar/
    FormField/
  organisms/
    Header/
    ProductCard/
  templates/
    DashboardLayout/
  pages/
    HomePage/
但：现代代码库不严格分五层——更加灵活。


组件化决策
什么进入设计系统：


应该进入：


    

  • 跨产品多次使用。
    • 

  • 稳定（少变化）。
    • 

  • 通用目的。
    • 



不应进入：


    

  • 仅使用一次。
    • 

  • 产品特定。
    • 

  • 频繁变化。
    • 



进入系统的例子：


    

  • Button、Input、Card、Modal、Toast。
    • 



不进入系统的例子：


    

  • "第四季度营销横幅"组件（一次性）。
    • 

  • 特定功能的内部组件。
    • 



组合模式
1. 基于属性的变体：


<Button variant="primary" size="md">
  保存
</Button>
简单但属性多时会混乱。


2. 复合组件：


<Card>
  <Card.Header>标题</Card.Header>
  <Card.Body>内容</Card.Body>
  <Card.Footer>
    <Button>操作</Button>
  </Card.Footer>
</Card>
灵活，让用户控制内部结构。


3. 渲染属性：


<DataFetcher url="/api">{(data) => <Display data={data} />}</DataFetcher>
灵活分离逻辑与界面。


4. 自定义钩子：


const { data, loading } = useFetch('/api');
return <Display data={data} loading={loading} />;
现代 React 惯用写法。


5. 无样式组件（Headless）：


    

  • 组件只提供逻辑和无障碍性，无视觉样式。
    • 

  • 用户自定义样式。
    • 

  • Radix UI、Headless UI。
    • 

  • 灵活但用户需要更多代码。
    • 



插槽模式
插槽（Slot）：让用户替换组件内部某部分。


<Modal header={<CustomHeader />} footer={<CustomFooter />}>
  内容
</Modal>
灵活替代子元素覆盖。


变体命名
常见变体名称：


    

  • primary、secondary、tertiary。
    • 

  • destructive / danger（红色）。
    • 

  • warning（黄色）。
    • 

  • success（绿色）。
    • 

  • ghost（极简）。
    • 

  • link（下划线）。
    • 



尺寸命名：


    

  • xs、sm、md、lg、xl。
    • 

  • 或 small、medium、large。
    • 

  • 或 dense、normal（Material）。
    • 



一致性原则：


    

  • 同一变体名在所有组件中含义一致。
    • 

  • 跨组件命名风格统一。
    • 



状态设计
常见状态：


    

  • 默认状态。
    • 

  • 悬停（鼠标移入）。
    • 

  • 激活 / 按下。
    • 

  • 焦点（键盘 Tab）。
    • 

  • 禁用。
    • 

  • 加载中。
    • 

  • 错误。
    • 



每个状态的视觉提示：


    

  • 颜色变化。
    • 

  • 微妙缩放。
    • 

  • 边框 / 轮廓。
    • 

  • 光标变化。
    • 



无障碍性注意：


    

  • 焦点可见（不能直接移除默认样式）。
    • 

  • 禁用不仅靠颜色（需添加 aria-disabled）。
    • 



组件接口设计
原则：


    

  • 简单的默认值。
    • 

  • 常见场景易用。
    • 

  • 边缘场景可行。
    • 



糟糕的接口：


<Button primary large rounded shadowed bordered />
布尔属性爆炸。


更好的接口：


<Button variant="primary" size="lg" />
基于枚举。


TypeScript：


type ButtonProps = {
  variant: 'primary' | 'secondary' | 'destructive';
  size: 'sm' | 'md' | 'lg';
  // ...
};
强类型防止拼写错误。


组件中的无障碍性
内置支持：


    

  • 语义化 HTML（使用 <button> 而非 <div>）。
    • 

  • ARIA 属性（aria-label、aria-pressed）。
    • 

  • 键盘支持（Tab、Enter、Esc）。
    • 

  • 焦点管理。
    • 

  • 屏幕阅读器文本。
    • 



示例：


<Button
  aria-pressed={isPressed}
  onKeyDown={handleKey}
  ...
>
  保存
</Button>
无样式组件库：


    

  • Radix UI、Headless UI、Ariakit。
    • 

  • 无障碍性内置。
    • 

  • 样式自定义。
    • 



Storybook
组件演示平台：


    

  • 每个组件的故事。
    • 

  • 变体展示。
    • 

  • 属性面板。
    • 

  • 自动生成文档。
    • 



工作流：


    

  • 编写故事与组件同步。
    • 

  • 设计师、工程师、产品经理共同查看。
    • 

  • 用于视觉回归测试。
    • 



现代趋势
1. 无样式组件：


    

  • Radix UI、Headless UI。
    • 

  • 逻辑与无障碍性分离于样式。
    • 



2. CSS-in-JS / Tailwind：


    

  • 样式与组件同位置。
    • 

  • 或工具类样式（Tailwind）。
    • 



3. 服务端组件（React）：


    

  • 部分组件在服务端渲染。
    • 

  • 无客户端交互。
    • 

  • 改变组件设计思路。
    • 



4. Web Components：


    

  • 框架无关。
    • 

  • 标准化。
    • 

  • 但采纳仍然有限。
    • 



5. AI 生成组件：


    

  • v0、Galileo。
    • 

  • 从文本生成组件。
    • 

  • 仍需设计师审查。
    • 



反模式
1. 万能组件：


    

  • 一个组件通过属性包所有场景。
    • 

  • 50 个属性。
    • 

  • 维护噩梦。
    • 



2. 紧耦合：


    

  • 组件假定特定数据结构。
    • 

  • 不可复用。
    • 



3. 无变体系统：


    

  • 每个用例新建组件。
    • 

  • 不系统化。
    • 



4. 硬编码值：


    

  • 组件内有魔法数字、颜色值。
    • 

  • 不基于令牌。
    • 



5. 无无障碍性：


    

  • 用 div 当按钮。
    • 

  • 不支持键盘。
    • 



6. 复制粘贴复用：


    

  • 不组件化。
    • 

  • 多个实例产生偏差。
    • 



实战建议
1. 从 5-10 个原子开始：


    

  • Button、Input、Label、Icon、Avatar、Badge、Spinner、Tag、Divider、Card。
    • 

  • 打好基础。
    • 



2. 按需构建分子：


    

  • 需要时从原子拉取。
    • 

  • 不要过度构建。
    • 



3. 为每个组件编写文档：


    

  • Storybook 故事。
    • 

  • 使用场景示例。
    • 

  • 推荐与不推荐用法。
    • 



4. 测试组合：


    

  • 视觉回归测试。
    • 

  • 无障碍性测试。
    • 



5. 迭代改进：


    

  • 第一版不必完美。
    • 

  • 听取产品团队反馈。
    • 



小结
Atomic Design（Brad Frost 2013）五个抽象层级——原子（最小元素，如按钮、输入框、标签）→ 分子（组合，如搜索栏）→ 有机体（独立区块，如导航页头）→ 模板（布局占位符）→ 页面（真实内容）。原子设计目标是极度可复用、无状态、最小接口，包含变体和尺寸。分子组合原子实现特定任务功能。有机体是页面的独立区块。React 组件与 Atomic Design大致对应但不严格。组件化决策基于使用频率、稳定性、通用性判断是否进入系统。组合模式包括属性变体（简单但多属性时混乱）、复合组件（Card.Header）、渲染属性、自定义钩子、无样式组件（Radix UI 仅逻辑和无障碍性，样式由用户定义）。插槽模式让用户替换内部部分。变体命名保持一致——primary/secondary/destructive/ghost、xs/sm/md/lg/xl。状态设计包括默认/悬停/激活/焦点/禁用/加载/错误。组件接口设计原则是简单默认、常见场景易用、边缘场景可行，避免布尔属性爆炸，使用 TypeScript 枚举。无障碍性内置——语义化 HTML + ARIA + 键盘支持 + 焦点管理 + 无样式组件库。Storybook 用于组件演示和视觉回归测试。现代趋势包括无样式组件、CSS-in-JS 或 Tailwind、服务端组件、Web Components、AI 生成组件。反模式包括万能组件、紧耦合、无变体系统、硬编码值、无无障碍性、复制粘贴复用。建议从 5-10 个原子开始、按需构建分子、为每个组件编写文档、测试组合、迭代改进。一个简单的检验：你能识别界面中的原子、分子、有机体吗？如果不能，Atomic Design 层级结构还需巩固。Atomic Design 是组件组织的思维模型——让设计系统架构有系统化的规范可循。
