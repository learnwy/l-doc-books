设计系统治理

核心概念

设计系统治理（Governance）决定设计系统如何演进、谁来负责、如何贡献、如何废弃——没有治理会让设计系统沦为"架上摆设"或陷入混乱。成熟的治理体系包含专属团队、路线图、贡献模型（集中式/联邦式/开放式）、版本管理（语义化版本）、废弃协议、度量指标（采纳率）、以及与产品对齐的路线图。Atlassian、Salesforce、Shopify 提供了行业最佳实践。本节给出治理模型、团队结构、贡献工作流、版本管理与废弃策略、度量方法、以及避免设计系统"失败"的模式。

维度 集中式 联邦式 开放式
决策 核心团队 核心 + 产品 社区
速度 慢 中 快
质量 高 中 不一致
扩展性 瓶颈 较好 最佳
代表案例 Apple HIG Atlassian Material Design（开源）

为什么需要治理

没有治理的后果：

  • 任何人都能随意修改，导致不一致。
  • 组件泛滥（出现十种按钮变体）。
  • Figma 设计与代码之间产生偏差。
  • 无废弃策略导致系统臃肿。
  • 权责不清导致无人维护。

有治理的好处：

  • 清晰的流程。
  • 质量控制。
  • 可预测的演进。
  • 长期可持续。

团队结构

专属团队（推荐）：

  • 设计师（视觉 + 交互）。
  • 工程师（组件代码）。
  • 产品经理/负责人。
  • 文档撰写者。
  • 设计运营（流程管理）。

规模：

  • 小型组织：1-2 人兼职。
  • 中型组织：3-5 人全职。
  • 大型组织：10-30 人以上。

角色职责：

设计系统设计师：

  • 视觉与交互设计。
  • 组件变体决策。

设计系统工程师：

  • 组件实现。
  • 工具链。
  • 无障碍性。

产品经理/负责人：

  • 路线图规划。
  • 利益相关者对齐。
  • 发布管理。

文档撰写者：

  • 组件文档。
  • 教程。

设计运营：

  • 流程管理。
  • 新人引导。
  • 采纳率追踪。
治理模型
1. 集中式：


    

  • 核心团队做所有决策。
    • 

  • 产品团队只是使用者。
    • 

  • 优点：一致性高、质量高。
    • 

  • 缺点：速度慢、容易成为瓶颈。
    • 

  • 案例：Apple HIG。
    • 



2. 联邦式：


    

  • 核心团队加产品团队贡献者。
    • 

  • 核心定义框架并接受贡献。
    • 

  • 优点：可扩展、有产品输入。
    • 

  • 缺点：治理复杂。
    • 

  • 案例：Atlassian、Shopify。
    • 



3. 开放式：


    

  • 任何人都可以贡献。
    • 

  • 社区维护。
    • 

  • 优点：扩展性最好。
    • 

  • 缺点：质量不一致。
    • 

  • 案例：Material Design（Google 主导但开源）。
    • 



混合式最常见：


    

  • 核心团队加结构化的贡献流程。
    • 



贡献工作流
联邦式典型工作流：


1. 提议阶段：


    

  • 产品团队识别需求。
    • 

  • 提交议题或征求意见稿（RFC）。
    • 



2. 设计评审：


    

  • 核心团队和设计师评审。
    • 

  • 与设计原则对齐。
    • 



3. 规格制定：


    

  • 详细规格：变体、状态、无障碍性。
    • 



4. 实现：


    

  • 代码 + Storybook + 测试 + 无障碍性。
    • 

  • 向设计系统仓库提交合并请求。
    • 



5. 审核：


    

  • 核心团队批准。
    • 

  • 无障碍性审核。
    • 

  • 视觉回归测试。
    • 



6. 发布：


    

  • 版本化。
    • 

  • 文档化。
    • 

  • 对外公告。
    • 



时间：


    

  • 简单组件：2-4 周。
    • 

  • 复杂组件：数月。
    • 



版本管理
语义化版本（Semver）：


    

  • 主版本.次版本.补丁版本。
    • 

  • 主版本：破坏性变更（移除组件、重命名令牌）。
    • 

  • 次版本：新功能（新组件/变体）。
    • 

  • 补丁版本：缺陷修复。
    • 



发布节奏：


    

  • 补丁：按需发布。
    • 

  • 次版本：每两周或每月。
    • 

  • 主版本：较少（每季度或每年）。
    • 



沟通方式：


    

  • 变更日志。
    • 

  • 发布说明。
    • 

  • 主版本附迁移指南。
    • 



工具：


    

  • changesets（npm 生态）。
    • 

  • Lerna（Monorepo）。
    • 

  • semantic-release（自动化）。
    • 



废弃协议
不能直接删除——会破坏多个产品。


流程：


    

  1. 标记废弃：
    2. 



    

  • 控制台警告。
    • 

  • 文档标注。
    • 

  • 代码检查规则。
    • 



    

  1. 建议替代方案：
    2. 



    

  • "请使用新组件替代旧组件，原因是..."。
    • 



    

  1. 宽限期：
    2. 



    

  • 3-12 个月。
    • 

  • 让产品团队完成迁移。
    • 



    

  1. 追踪使用量：
    2. 



    

  • 遥测数据。
    • 

  • 等待使用量降到接近零。
    • 



    

  1. 正式移除：
    2. 



    

  • 主版本升级。
    • 



废弃警告示例：


console.warn('OldButton 已废弃。请使用 Button 替代。将在 v3.0 中移除。');
采纳率度量
为什么要度量：


    

  • "建好了但没人用"是设计系统失败的主要原因之一。
    • 

  • 不度量就不知道问题所在。
    • 



指标：


1. 采纳率：


    

  • 使用设计系统组件的界面百分比。
    • 

  • 工具：类似 Lighthouse 的分析器。
    • 



2. 组件覆盖率：


    

  • 多少产品使用了每个组件。
    • 



3. 令牌覆盖率：


    

  • 使用令牌的样式百分比（相对于硬编码值）。
    • 



4. 贡献率：


    

  • 产品团队提交的合并请求数量。
    • 

  • 新组件提议数量。
    • 



5. 满意度（NPS）：


    

  • 调查产品团队。
    • 

  • "你对设计系统的满意度如何？"
    • 



6. 交付速度：


    

  • 产品团队功能交付时间。
    • 

  • 越快说明系统越有效。
    • 



工具：


    

  • 自定义分析平台。
    • 

  • Atlassian Atlaskit 度量系统。
    • 

  • 组件使用量追踪。
    • 



沟通
路线图：


    

  • 公开路线图。
    • 

  • 季度计划。
    • 

  • 不让产品团队感到意外。
    • 



通讯/变更日志：


    

  • 每次发布进行公告。
    • 

  • 突出新功能。
    • 

  • 附迁移指南。
    • 



答疑时间：


    

  • 每周固定时段。
    • 

  • 产品团队可以提问。
    • 



即时通讯频道：


    

  • 实时支持。
    • 

  • 社区建设。
    • 



培训：


    

  • 新产品团队引导。
    • 

  • 高级用户培训。
    • 



利益相关者对齐
工程管理层：


    

  • 展示投资回报率。
    • 

  • 证明投入合理性。
    • 



设计管理层：


    

  • 视觉一致性。
    • 

  • 品牌统一。
    • 



产品管理层：


    

  • 加快功能交付。
    • 

  • 不被设计系统阻塞。
    • 



高管层：


    

  • 战略价值。
    • 

  • 跨产品一致性。
    • 



不同角色需要不同沟通方式：


    

  • 工程师：指标和技术细节。
    • 

  • 设计师：视觉效果和用户影响。
    • 

  • 产品经理：速度和采纳率。
    • 

  • 高管：投资回报率和商业成果。
    • 



RFC 流程
RFC（征求意见稿）：


    

  • 重大变更有文档记录。
    • 

  • 利益相关者评审。
    • 

  • 决策有记录。
    • 



模板：


    

  • 问题描述。
    • 

  • 提议方案。
    • 

  • 备选方案。
    • 

  • 迁移影响。
    • 

  • 时间线。
    • 



流程：


    

  • 在 GitHub 上创建 RFC 议题。
    • 

  • 两周评论期。
    • 

  • 决策结果记录存档。
    • 



反模式
1. 无治理：


    

  • 任何人都能随意修改。
    • 

  • 混乱。
    • 



2. 过度治理：


    

  • 小改动也要一百步流程。
    • 

  • 令人沮丧。
    • 



3. 仅设计师主导：


    

  • 缺少工程师协作。
    • 

  • 实施差距。
    • 



4. 不废弃旧组件：


    

  • 不移除过时组件。
    • 

  • 系统越来越臃肿。
    • 



5. 不度量：


    

  • 不知道成功与否。
    • 



6. 单人英雄：


    

  • 一个人包揽一切。
    • 

  • 巴士因子为 1。
    • 



7. 冻结不更新：


    

  • 不演进。
    • 

  • 产品团队感到沮丧。
    • 



8. 象牙塔：


    

  • 不听产品团队意见。
    • 

  • 设计系统变得无关紧要。
    • 



组织模式
从草根到正式团队：


    

  • 许多设计系统起源于草根项目。
    • 

  • 成功后推广到全公司。
    • 

  • 需要管理层支持。
    • 



外部招聘与内部培养：


    

  • 外部招聘专属负责人。
    • 

  • 从内部设计师/工程师中培养。
    • 

  • 通常是混合方式。
    • 



论证投资回报
Atlassian 内部研究：


    

  • 节省 30-50% 界面开发时间。
    • 

  • 年节省数百万。
    • 



向领导层传达：


    

  • 每个产品团队节省的时间。
    • 

  • 质量提升（无障碍性、一致性）。
    • 

  • 新人上手更快。
    • 

  • 减少设计债务。
    • 



没有设计系统时：


    

  • 每个团队重复构建。
    • 

  • 不一致性的成本。
    • 

  • 品牌更新成为噩梦。
    • 



实战建议
1. 先获得领导层支持：


    

  • 没有支持就没有资源。
    • 



2. 尽早组建专属团队：


    

  • 不兼职。
    • 

  • 需要专注。
    • 



3. 服务真实产品需求：


    

  • 与有实际需求的产品团队合作。
    • 

  • 不在真空中闭门造车。
    • 



4. 将治理流程文档化：


    

  • 流程可见。
    • 

  • 产品团队可预期。
    • 



5. 迭代治理流程：


    

  • 流程不是一成不变的。
    • 

  • 基于反馈不断改进。
    • 



6. 当作产品来运营：


    

  • 路线图、发布、变更日志、技术支持。
    • 



不同阶段公司的治理
创业公司（<50 人）：


    

  • 不需要自建设计系统。
    • 

  • 使用外部方案（Material、Tailwind UI）。
    • 



成长期（50-500 人）：


    

  • 轻量设计系统 + 兼职负责人。
    • 



成熟期（500-5000 人）：


    

  • 3-5 人专属团队。
    • 



大型企业（5000 人以上）：


    

  • 10-30 人团队。
    • 

  • 联邦式。
    • 

  • 多产品支持。
    • 



失败案例
常见失败模式：


1. 只建不推广：


    

  • 设计系统建好了。
    • 

  • 没人使用。
    • 

  • 最终被砍。
    • 



2. 单人英雄离开：


    

  • 一个人主导一切。
    • 

  • 离开后设计系统消亡。
    • 



3. 组织架构变动：


    

  • 重组打断。
    • 

  • 设计系统团队被解散。
    • 



4. 质量问题：


    

  • 无障碍性或性能问题。
    • 

  • 产品团队绕过不用。
    • 



5. 跟不上时代：


    

  • 不跟进设计趋势。
    • 

  • 产品团队转向其他方案。
    • 



小结
设计系统治理决定系统如何演进、谁负责、如何贡献、如何废弃——没有治理会让系统成为摆设或混乱。团队结构包括设计师、工程师、产品经理、文档撰写者、设计运营，规模取决于组织大小。治理模型有集中式（Apple HIG，慢但一致）、联邦式（Atlassian/Shopify，扩展性与质量平衡）、开放式（Material 开源社区），混合式最常见。贡献工作流为提议、设计评审、规格制定、实现、审核、发布，简单组件 2-4 周。语义化版本管理，发布节奏为补丁按需、次版本双周、主版本较少，工具有 changesets、Lerna、semantic-release。废弃协议为标记、建议替代、宽限期 3-12 个月、追踪使用量、主版本移除。采纳率度量包括采纳率、组件覆盖率、令牌覆盖率、贡献率、满意度、交付速度。沟通方式包括路线图、变更日志、答疑时间、即时通讯、培训。利益相关者对齐要对不同角色用不同方式沟通。RFC 流程记录重大变更决策。反模式包括无治理、过度治理、仅设计师主导、不废弃、不度量、单人英雄、冻结不更新、象牙塔。不同阶段公司的治理方式不同。常见失败模式包括只建不推广、单人英雄离开、组织变动、质量问题、跟不上时代。一个简单的检验：你能列出你们公司设计系统的治理流程吗？如果不能，治理还需明确化。治理是设计系统长期生存的关键——好的治理让系统持续演进服务产品团队，差的治理让系统短命或失败。
