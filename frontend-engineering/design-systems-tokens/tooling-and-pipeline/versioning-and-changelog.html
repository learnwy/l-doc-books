版本管理与变更日志

核心概念

设计系统是长期维护的产品，必须通过严谨的版本管理让消费方安全升级。语义化版本号（Semver，MAJOR.MINOR.PATCH）是行业标准——主版本（MAJOR）是破坏性变更（删除组件、重命名令牌、API 变更）、次版本（MINOR）是向后兼容的新功能、补丁版本（PATCH）是缺陷修复。变更日志（KeepAChangelog 格式）让消费方了解变更内容和迁移方法。弃用协议（标记 + 警告 + 宽限期 + 移除）让破坏性变更优雅过渡。自动化工具包括 changesets、semantic-release、Lerna 等。本节详细讲解语义化版本、变更日志编写、弃用协议、破坏性变更流程和工具选择。

版本部分 含义 示例
主版本 破坏性变更 1.0.0 → 2.0.0
次版本 向后兼容的新功能 1.0.0 → 1.1.0
补丁版本 缺陷修复 1.0.0 → 1.0.1
预发布 内测 / 公测 / 候选 1.0.0-alpha.1
构建号 构建元数据 1.0.0+build.123

语义化版本详解

主版本（MAJOR）：

  • 破坏性变更，消费方需要修改代码。
  • 示例：
    • 删除组件或令牌。
    • 重命名 API。
    • 修改函数签名。
    • 放弃平台支持。

次版本（MINOR）：

  • 向后兼容的新功能。
  • 示例：
    • 新增组件或变体。
    • 新增令牌。
    • 新增可选属性。
    • 新增工具函数。

补丁版本（PATCH）：

  • 向后兼容的缺陷修复。
  • 示例：
    • 修复视觉缺陷。
    • 修复无障碍问题。
    • 修复文档错字。
    • 更新内部依赖。

什么是破坏性变更

明确的破坏性变更：

  • 删除公开组件。
  • 删除公开令牌。
  • 重命名导出名称。
  • 修改必需属性。

可能的破坏性变更（需讨论）：

  • 视觉变化（颜色微调）。
  • 默认值修改。
  • 行为变更（如按钮点击行为调整）。

安全策略：

  • 不确定时按主版本处理。
  • 使用弃用策略过渡。

实战参考：

  • Atlassian、Material Design 通常每年发布一次主版本。

预发布版本

格式：主版本.次版本.补丁-{标签}.{编号}

  • 1.0.0-alpha.0：早期实验性版本。
  • 1.0.0-beta.0：功能完整，进入测试。
  • 1.0.0-rc.1：候选发布版本。
  • 1.0.0：正式稳定版本。

使用场景：

  • 主版本发布前让用户提前体验。
  • 在正式发布前收集反馈。

变更日志

格式：KeepAChangelog 标准。

# 变更日志

## [未发布]

## [2.1.0] - 2024-03-15

### 新增

- 新增 `<Combobox>` 组件
- 新增 `--color-action-tertiary` 令牌

### 变更

- 改进 `<Modal>` 无障碍（焦点陷阱）

### 弃用

- `<DialogV1>` 将在 v3.0 移除，请使用 `<Dialog>`

### 修复

- 修复暗色模式下按钮悬停状态

## [2.0.0] - 2024-01-10

### 破坏性变更

- 移除 `<OldButton>`（请使用 `<Button>`）
- `<Card>` 中 `theme` 属性重命名为 `variant`

### 迁移指南

详见 [migration-guide.md](./migration-guide.md)

标准章节：

  • 新增：新功能。
  • 变更：现有功能调整（非破坏性）。
  • 弃用：将要移除的功能。
  • 移除：已移除的功能。
  • 修复：缺陷修复。
  • 安全：安全相关修复。

迁移指南

主版本迁移指南示例：

# 从 v1 迁移到 v2

## OldButton → Button

### 之前（v1）

```jsx
import { OldButton } from '@design-system';
<OldButton primary>点击</OldButton>;
```

### 之后（v2）

```jsx
import { Button } from '@design-system';
<Button variant="primary">点击</Button>;
```

### 原因

- 统一各组件的变体 API
- 更好的 TypeScript 支持

### 自动迁移

运行自动迁移命令：

```bash
npx @design-system/codemods v2-button
```

每个破坏性变更都应包含：

  • 变更前后的代码对比。
  • 变更原因说明。
  • 自动迁移工具或手动步骤。

弃用协议

第 1 步：标记为弃用：

/**
 * @deprecated 请使用 `Button` 替代。将在 v3.0 移除。
 */
export const OldButton = (props) => {
  console.warn('OldButton 已弃用。请使用 Button 替代。将在 v3.0 移除。');
  return <Button {...props} />;
};

第 2 步：更新文档：

  • 在 Storybook 中标记为已弃用。
  • 建议替代方案。

第 3 步：添加 Lint 规则：

  • 自定义 ESLint 规则。
  • 高亮已弃用用法。

第 4 步：监控使用情况（可选）：

  • 追踪哪些消费方仍在使用已弃用功能。
  • 等待使用量降为零。

第 5 步：正式移除：

  • 主版本升级。
  • 提供迁移指南。

宽限期：

  • 通常 3-12 个月。
  • 大型公司：12 个月以上。

版本管理工具

changesets（npm 生态主流）：

  • 每个 PR 添加变更集文件。
  • 描述变更内容和版本类型。
  • 自动生成变更日志。
  • 自动升级版本号。
npx changeset
# 交互式提示：选择版本类型 + 描述变更

semantic-release：

  • 基于提交信息自动升级。
  • feat: → 次版本。
  • fix: → 补丁版本。
  • BREAKING CHANGE: → 主版本。

Lerna：

  • Monorepo 版本管理。
  • 独立模式或固定模式。

大型公司（Atlassian / Microsoft）：

  • 针对复杂需求自建工具。

约定式提交

标准提交信息格式：

<类型>(<范围>): <主题>

<正文>

<脚注>

类型：

  • feat：新功能 → 次版本。
  • fix：缺陷修复 → 补丁版本。
  • docs：仅文档变更。
  • style：格式和 Lint。
  • refactor：重构（无功能变化）。
  • test：仅测试变更。
  • chore：构建和依赖。
  • 脚注中包含 BREAKING CHANGE → 主版本。

示例：

feat(button): 新增危险操作变体

添加 variant="destructive" 用于删除操作。
包含红色配色和确认对话框。

BREAKING CHANGE: 移除旧的 `danger` 属性。请使用 variant="destructive"。

发布节奏

策略选择：

持续发布：

  • 每次合并即发布。
  • 补丁版本频繁。
  • 功能就绪时发布次版本。

定期发布：

  • 补丁版本按需发布。
  • 次版本每周或每两周。
  • 主版本每季度或每年。

预发布优先：

  • 主版本经历 alpha / beta / RC。
  • 测试后发布稳定版。

常见节奏：

  • 主版本：每 6-12 个月。
  • 次版本：每几周。
  • 补丁版本：按需。

沟通机制

发布公告：

  • 邮件或即时通讯通知。
  • 重点说明重大变更。
  • 迁移截止日期。

路线图：

  • 公开预告即将发布的内容。
  • 避免让消费方措手不及。

答疑时间：

  • 帮助消费方完成迁移。

Lint 规则：

  • 在代码中显示已弃用用法。

稳定版 vs 实验版

稳定版：

  • 高质量。
  • 可用于生产环境。
  • 语义化版本保证。

实验版：

  • 明确标记。
  • 可能随时变更。
  • 不建议用于生产环境。

示例：

// 实验性组件
import { ExperimentalCombobox } from '@design-system/experimental';

晋升路径：

  • 实验版 → 收集反馈后晋升为稳定版。

长期支持

多版本并行维护：

  • v1 继续维护安全修复。
  • v2 活跃开发。

策略：

  • 长期支持分支。
  • 关键修复回溯移植。

维护时长：

  • 大型公司：1-2 年长期支持。
  • 小型团队：仅维护最新版。

破坏性变更沟通

发布前：

  • 提前 3 个月公告。
  • 提供预发布版本供测试。
  • 迁移指南准备就绪。

发布时：

  • 发布主版本。
  • 邮件通知公告。
  • 在沟通渠道发帖。

发布后：

  • 提供答疑支持。
  • 追踪迁移进度。
  • 按需发布修复版本。

反模式

1. 补丁或次版本中引入破坏性变更：

  • 极其不当的做法。
  • 消费方意外中断。

2. 没有变更日志：

  • 消费方无法知道变了什么。

3. 没有弃用宽限期：

  • 不经警告直接移除。

4. 主版本过于频繁：

  • 不稳定。
  • 消费方疲于应对。

5. 不提供自动迁移工具：

  • 手动迁移繁琐。
  • 自动化工具价值巨大。

6. 不做沟通：

  • 静默发布。
  • 意外 = 愤怒。

实战案例

Atlassian Atlaskit：

  • 各包独立版本管理。
  • 活跃的弃用实践。
  • 每两周发布一次。

Material Design：

  • 每年发布主版本。
  • 提供充分的迁移时间。

Tailwind：

  • 每 1-2 年发布主版本。
  • 详细的迁移指南。
  • 提供自动迁移工具。

工具总结

工具 用途
changesets 手动变更集 + 自动发布
semantic-release 基于提交信息自动发布
Lerna Monorepo 版本管理与发布
约定式提交 提交信息标准格式
KeepAChangelog 变更日志格式标准
Standard Version 从提交自动生成变更日志

实战建议

1. 使用 changesets：

  • npm 生态主流工具。
  • 易于上手。

2. 采用约定式提交：

  • 帮助自动化发布。

3. 主版本周期 6-12 个月：

  • 不过于频繁。
  • 也不积压功能。

4. 弃用宽限期 3 个月：

  • 给消费方充分的迁移时间。

5. 主版本提供自动迁移工具：

  • 降低消费方迁移成本。

6. 主版本先发预发布版：

  • alpha → beta → RC → 正式版。

7. 清晰沟通：

  • 通过邮件、即时通讯和文档通知。

小结

设计系统版本管理使用语义化版本 MAJOR.MINOR.PATCH——主版本用于破坏性变更（删除/重命名/API 变更），次版本用于向后兼容的新功能，补丁版本用于向后兼容的缺陷修复。预发布版本 1.0.0-alpha.0 / beta.0 / rc.1 让用户提前体验。变更日志采用 KeepAChangelog 格式，包含新增/变更/弃用/移除/修复/安全等章节。迁移指南应包含变更前后代码对比 + 原因说明 + 自动迁移工具或手动步骤。弃用协议五步走：标记 @deprecated + 控制台警告 + 更新文档 + Lint 规则 + 监控用量 + 主版本正式移除，宽限期 3-12 个月。工具方面，changesets（npm 生态主流，每个 PR 添加变更集 + 自动生成变更日志 + 版本升级）、semantic-release（基于提交信息自动化）、Lerna（Monorepo 管理）。约定式提交标准格式 <类型>(<范围>): <主题>，类型包括 feat/fix/docs/style/refactor/test/chore + BREAKING CHANGE 脚注触发主版本。发布节奏有持续（每次合并）vs 定期（每周次版本 / 每年主版本）vs 预发布优先，常见为主版本 6-12 月 / 次版本每周 / 补丁按需。沟通机制包括发布公告（邮件/即时通讯）、路线图、答疑时间和 Lint 规则。稳定版与实验版明确区分，实验版收集反馈后晋升。长期支持多版本并行 1-2 年。破坏性变更沟通三阶段：发布前公告 3 月 + 预发布，发布时通知，发布后答疑和追踪。应避免的反模式：补丁中引入破坏性变更、无变更日志、无弃用期、主版本过频、无自动迁移工具、不做沟通。Atlassian（独立版本 + 两周发布）/ Material（年度主版本）/ Tailwind（1-2 年主版本 + 自动迁移）是业界参考案例。建议使用 changesets + 约定式提交 + 主版本 6-12 月 + 3 月弃用期 + 自动迁移 + 预发布 + 清晰沟通。版本管理与变更日志是设计系统专业性的体现——做对了让消费方信任并长期使用，做不对让消费方厌烦并弃用。
