多品牌与主题

核心概念

多品牌（Multi-brand）与多主题（Multi-theme）是设计系统规模化的关键挑战——Atlassian 的 Jira、Confluence、Trello 拥有不同的品牌但共享基础系统，Material You 让用户壁纸驱动主题，企业 SaaS 需要客户专属品牌定制（白标）。成熟的设计系统通过令牌覆盖架构实现：基础令牌 + 品牌特定覆盖 + 主题特定覆盖，组件代码不变。本节介绍多品牌架构、亮色/暗色模式、白标定制、动态主题（用户偏好）、主题提供者模式、CSS 变量切换。

维度 亮色/暗色 多品牌 白标
触发条件 用户偏好 产品线 客户配置
令牌层级 系统层 引用层 + 系统层 引用层 + 系统层
组件 不变 不变 不变
切换时机 即时 构建/运行时 运行时（按租户）
示例 iOS / Android Atlassian Salesforce、Slack

令牌覆盖架构

第 0 层（基础层）：

  • 默认值。
  • 例：color.action.primary = blue.500。

第 1 层（主题覆盖）：

  • 亮色 vs 暗色：color.action.primary 通常相同，但 color.bg 不同。

第 2 层（品牌覆盖）：

  • Jira 主题：color.brand.primary = blue。
  • Confluence 主题：color.brand.primary = teal。
  • Trello 主题：color.brand.primary = blue。

第 3 层（白标）：

  • 客户 X：color.brand.primary = orange。

级联规则：

  • 客户覆盖 > 品牌 > 主题 > 基础。
亮色/暗色模式
系统层覆盖：


// tokens-light.json
{
  "color.background.default": "{color.gray.50}",
  "color.text.primary": "{color.gray.900}"
}

// tokens-dark.json
{
  "color.background.default": "{color.gray.900}",
  "color.text.primary": "{color.gray.50}"
}
组件层不变：


{
  "card.background": "{color.background.default}" // 自动跟随主题
}
Web 实现：


:root {
  --color-bg: white;
  --color-text: black;
}

[data-theme='dark'] {
  --color-bg: black;
  --color-text: white;
}

/* 或使用媒体查询 */
@media (prefers-color-scheme: dark) {
  :root {
    --color-bg: black;
  }
}
iOS 实现：


    

  • 动态 UIColor 包含亮色 + 暗色变体。
    • 

  • 系统变化时自动切换。
    • 



Android 实现：


    

  • Theme.DayNight。
    • 

  • values-night/colors.xml。
    • 



主题提供者模式（React）
const ThemeContext = createContext();

function ThemeProvider({ theme, children }) {
  return (
    <ThemeContext.Provider value={theme}>
      <div data-theme={theme}>{children}</div>
    </ThemeContext.Provider>
  );
}

// 应用
<ThemeProvider theme="dark">
  <App />
</ThemeProvider>;
钩子：


const theme = useTheme();
多品牌实现
策略一：按品牌构建：


    

  • 每个品牌独立 npm 包 + CSS。
    • 

  • @design-system/jira-theme、@design-system/confluence-theme。
    • 

  • 编译时确定。
    • 



策略二：运行时切换：


    

  • 单个 CSS 包含所有品牌。
    • 

  • [data-brand="jira"] 选择器。
    • 

  • 运行时切换。
    • 



权衡对比：


    

  • 构建策略：每个应用包体积更小。
    • 

  • 运行时策略：一个包支持多品牌。
    • 



白标定制
客户专属定制：


// customer-acme.json
{
  "color.brand.primary": "#ff6b35",
  "logo.url": "/customer/acme/logo.svg"
}
运行时应用：


    

  • 每个客户加载自己的主题。
    • 

  • 初始化时注入 CSS 变量。
    • 

  • 或使用客户配置进行服务端渲染。
    • 



常见于 B2B SaaS：


    

  • Salesforce Lightning。
    • 

  • Slack Enterprise Grid。
    • 

  • HubSpot。
    • 



动态取色（Material You）
Android 12+：


    

  • 从用户壁纸提取颜色。
    • 

  • 生成完整 Material 调色板。
    • 

  • 应用到整个系统。
    • 



实现方式：


    

  • Material Color Utilities（npm 包）。
    • 

  • 量化 + 评分算法。
    • 



Web 等效方案：


    

  • 采用有限。
    • 

  • 通过 Color Thief 手动提取。
    • 



CSS 变量 vs JS 主题对象
CSS 变量：


.button {
  background: var(--color-action-primary);
}
优点：


    

  • 原生 CSS。
    • 

  • 运行时切换零成本。
    • 

  • :hover 样式正常工作。
    • 



缺点：


    

  • 无类型检查。
    • 

  • 限于 CSS 上下文。
    • 



JS 主题对象（styled-components / Emotion）：


const theme = { colors: { primary: '#3b82f6' } };

styled.button`
  background: ${(props) => props.theme.colors.primary};
`;
优点：


    

  • 类型安全。
    • 

  • 可编程逻辑。
    • 

  • JSX 中可访问。
    • 



缺点：


    

  • 运行时开销。
    • 

  • 需要配置才能 SSR 友好。
    • 



现代做法：


    

  • CSS 变量承载令牌。
    • 

  • TypeScript 类型同步提供。
    • 



主题库
Material UI：


    

  • ThemeProvider + 主题对象。
    • 

  • 强大的定制能力。
    • 

  • 包体积较大。
    • 



Chakra UI：


    

  • 主题对象 + CSS-in-JS。
    • 

  • 易于定制。
    • 



Tailwind CSS：


    

  • 配置驱动主题。
    • 

  • 无运行时开销。
    • 

  • 构建时确定。
    • 



Stitches / Vanilla Extract：


    

  • 类型安全的 CSS-in-JS。
    • 

  • 零运行时。
    • 



选择建议：


    

  • 小定制需求：Tailwind。
    • 

  • 大定制需求：Material UI / Chakra。
    • 

  • 类型安全 + 性能：Vanilla Extract。
    • 



SSR 主题处理
挑战：


    

  • 服务端不知道用户偏好。
    • 

  • 默认主题 → 客户端闪烁。
    • 



解决方案：


1. Cookie：


    

  • 用户偏好存入 cookie。
    • 

  • 服务端请求时读取。
    • 



2. localStorage + 脚本：


    

  • 内联脚本首次加载检查 localStorage。
    • 

  • 主渲染前设置主题。
    • 



3. 无闪烁技巧（Next.js）：


// layout.js
<html data-theme={theme}>
  <head>
    <script
      dangerouslySetInnerHTML={{
        __html: `
      const theme = localStorage.getItem('theme') || 'light';
      document.documentElement.dataset.theme = theme;
    `,
      }}
    />
  </head>
  <body>...</body>
</html>
主题检测
系统偏好：


const prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
监听变化：


window.matchMedia('(prefers-color-scheme: dark)').addEventListener('change', (e) => {
  setTheme(e.matches ? 'dark' : 'light');
});
用户覆盖：


    

  • 用户显式选择覆盖系统设置。
    • 

  • 存储在 localStorage。
    • 



多品牌实战案例
Atlassian：


    

  • Jira（蓝色）、Confluence（紫色）、Trello（蓝色）、Bitbucket（橙色）。
    • 

  • 共享基础组件。
    • 

  • 品牌令牌覆盖。
    • 



实现方式：


    

  • 每个产品使用品牌主题提供者包裹。
    • 

  • 每个产品的 CSS 变量覆盖。
    • 



白标实战案例
Salesforce Lightning：


    

  • 客户配置主题。
    • 

  • 100+ 个令牌可定制。
    • 

  • 上传 logo / icon。
    • 



实现方式：


    

  • 服务端编译客户专属 CSS。
    • 

  • 或运行时 CSS 变量注入。
    • 



性能考量
主题切换成本：


    

  • CSS 变量切换：快速（浏览器处理）。
    • 

  • 大页面重算样式。
    • 

  • 现代浏览器已优化。
    • 



包体积：


    

  • 按主题分包：多主题时体积大。
    • 

  • 单包 + CSS 变量：体积小。
    • 



运行时成本：


    

  • CSS 变量可忽略不计。
    • 

  • 重新编译 CSS-in-JS 则较高。
    • 



反模式
1. 通过组件变体实现主题：


<ButtonDark />
<ButtonLight />
变体爆炸。错误做法。


2. 直接覆盖组件：


<Button style={{ background: 'red' }} />
不可主题化。错误做法。


3. 主题值不在令牌中：


    

  • 主题值硬编码在组件中。
    • 

  • 不成体系。
    • 



4. 主题过多：


    

  • 每个主题 50 个可定制令牌。
    • 

  • 维护噩梦。
    • 

  • 限制在 10-20 个以内。
    • 



5. 不测试所有主题：


    

  • 亮色好看，暗色破损。
    • 

  • CI 测试所有主题。
    • 



6. SSR 闪烁：


    

  • 首次渲染错误主题。
    • 

  • 闪烁很难看。
    • 



主题测试
视觉回归测试：


    

  • Chromatic、Percy。
    • 

  • 测试每个组件在每个主题下的表现。
    • 



Storybook：


    

  • 主题切换插件。
    • 

  • 展示组件在所有主题下的样子。
    • 



Playwright：


    

  • 每个主题自动截图。
    • 



工具
Theme UI：


    

  • React + 主题规范。
    • 



Stitches：


    

  • 类型安全 + 主题支持。
    • 



Tailwind 暗色模式：


    

  • dark: 前缀。
    • 

  • 基于类或媒体查询。
    • 



原生 CSS 变量：


    

  • 简单 + 强大。
    • 



实战建议
1. 基于令牌的主题：


    

  • 所有主题值放入令牌。
    • 

  • 不在组件中硬编码。
    • 



2. 测试所有主题：


    

  • 视觉回归测试。
    • 

  • Storybook 验证。
    • 



3. SSR 使用 cookie：


    

  • 避免闪烁。
    • 



4. 允许用户覆盖：


    

  • 支持显式主题选择。
    • 



5. 限制白标范围：


    

  • 约 10-20 个令牌可定制。
    • 

  • 不是所有令牌。
    • 



6. 文档化主题 API：


    

  • 客户/消费者知道如何定制。
    • 



小结
多品牌/多主题是设计系统规模化的关键——通过令牌覆盖架构（第 0 层基础 + 第 1 层主题 + 第 2 层品牌 + 第 3 层客户）实现，组件代码不变。亮色/暗色模式覆盖系统层，CSS 变量 + [data-theme] / prefers-color-scheme / 基于类，iOS 动态 UIColor + Android Theme.DayNight。主题提供者模式（React Context）+ useTheme 钩子。多品牌策略按品牌构建（每个应用包体积小）vs 运行时切换（单包多品牌）。白标 B2B SaaS（Salesforce Lightning / Slack / HubSpot）客户专属配置，服务端编译或运行时 CSS 变量注入。Material You 从壁纸动态取色（Android 12+ Material Color Utilities）。CSS 变量 vs JS 主题对象——CSS 变量原生 + 零成本运行时切换 + :hover 正常工作但无类型检查，JS 主题类型安全 + 可编程但有运行时开销。主题库——Material UI（ThemeProvider）/ Chakra（CSS-in-JS）/ Tailwind（构建时配置）/ Vanilla Extract（类型安全零运行时）。SSR 主题处理——cookie + 内联脚本检查 localStorage 避免闪烁。系统偏好检测 prefers-color-scheme + 监听变化 + 用户显式覆盖 localStorage。Atlassian（Jira/Confluence/Trello 基础 + 品牌覆盖）/ Salesforce Lightning（100+ 令牌可定制 + 客户 CSS 编译）案例。性能方面 CSS 变量切换快速浏览器优化 + 单包体积更小，CSS-in-JS 重新编译则运行时成本高。反模式——通过变体实现主题导致爆炸、直接样式覆盖、主题值不在令牌中、主题过多（限制 10-20 个）、不测试所有主题、SSR 闪烁。主题测试——视觉回归 Chromatic/Percy + Storybook 切换插件 + Playwright 每主题截图。工具 Theme UI / Stitches / Tailwind dark / 原生 CSS 变量。建议——基于令牌 + 测试所有 + SSR cookie + 用户覆盖 + 限制白标范围约 10-20 个令牌 + 文档化主题 API。一个简单的检验：你能实现亮色/暗色 + 多品牌 + 1 个白标定制吗？如果不能，主题架构还需练习。
