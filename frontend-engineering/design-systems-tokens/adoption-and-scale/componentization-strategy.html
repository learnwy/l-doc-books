组件化策略

核心概念

组件化策略决定设计系统包含什么、不包含什么——错误的决策让系统要么太窄（产品团队仍需构建大量自定义组件）要么太宽（包含了不该包含的内容，维护负担过重）。正确的策略纳入使用频率×稳定性×通用性高的组件（原子+分子为主，部分有机体）；不纳入特定产品专属的、实验性的、低频使用的组件。插槽模式（Slot Pattern）+ 组合模式 + 无头组件（Headless）让系统灵活适应产品变化。本节详细讲解组件化的决策标准、何时拒绝贡献、无头组件与样式组件的权衡、插槽模式，以及实战案例分析。

决策标准 高 → 纳入系统 低 → 不纳入
使用频率 多个产品使用 单个产品使用
稳定性 API 极少变更 频繁演进
通用性 通用目的 领域特定
视觉一致性 一致性要求高 产品特定外观
无障碍复杂度 高（值得共同投入） 简单（各自实现即可）

组件化决策标准

决策矩阵：

适合纳入系统的组件：

  • 多个产品使用。
  • API 稳定。
  • 通用目的。
  • 无障碍实现复杂（值得共同投入）。

典型示例：

  • Button、Input、Modal、Card、Toast——普遍使用。
  • Combobox（无障碍复杂）。
  • 日期选择器。
  • 工具提示。

不适合纳入系统的组件：

  • 仅一个产品使用。
  • 频繁演进变化。
  • 领域特定（医疗表单、金融图表）。
  • 过于简单（分隔线）。

典型示例：

  • "营销活动 Q4 横幅"。
  • "员工入职向导"。
  • 高度产品特定的界面。

决策工作流

1. 产品团队提议组件：

  • 提交 RFC（征求意见稿）。
  • 描述使用场景。

2. 核心团队审查：

  • 多个产品需要吗？
  • 是通用组件吗？
  • API 足够稳定吗？

3. 做出决策：

  • 同意：编写规格 → 实现。
  • 拒绝：建议替代方案（产品内自建）。
  • 待定：以实验性组件方式纳入。
无头组件 vs 样式组件
样式组件：


    

  • 包含视觉样式和行为逻辑。
    • 

  • 不易定制。
    • 

  • 例如：Material Button。
    • 



无头组件：


    

  • 仅包含逻辑和无障碍能力。
    • 

  • 样式由使用方自行提供。
    • 

  • 例如：Radix UI Tabs、Headless UI Combobox。
    • 



权衡比较：


样式组件：


    

  • 使用简单。
    • 

  • 视觉一致。
    • 

  • 定制受限。
    • 



无头组件：


    

  • 极度灵活。
    • 

  • 不绑定特定品牌。
    • 

  • 但使用方需自行处理样式。
    • 



现代最佳方案：


    

  • 混合模式——提供样式化的默认外观 + 暴露无头接口给高级用户。
    • 

  • 例如：shadcn/ui（Radix 无头组件 + Tailwind 样式）。
    • 



插槽模式
插槽 = 让使用方替换组件的内部部分：


<Modal header={<CustomHeader />} footer={<CustomFooter />}>
  <CustomContent />
</Modal>
灵活性：


    

  • 使用方无需 fork 即可定制。
    • 



复合组件模式：


<Card>
  <Card.Header>标题</Card.Header>
  <Card.Body>内容</Card.Body>
  <Card.Footer>操作</Card.Footer>
</Card>
组合模式
让使用方将原子组件组合成分子组件：


    

  • 不发布每一种组合变体。
    • 

  • 使用方按需组合。
    • 



模式：


<Stack gap="md">
  <Heading level={2}>标题</Heading>
  <Text>描述内容</Text>
  <Button>操作</Button>
</Stack>
原子组件 + 间距 + 弹性布局——组合出无限变体。


何时拒绝纳入
拒绝场景：


    

  • 仅单个产品使用。
    • 

  • 实验性界面。
    • 

  • 领域特定。
    • 

  • 频繁变化。
    • 



拒绝后让产品团队自建：


    

  • 节省设计系统团队时间。
    • 

  • 产品团队掌控自己的界面。
    • 



清晰沟通：


    

  • 说明拒绝原因。
    • 

  • 建议替代方案。
    • 

  • 如果后续多个产品需要，可以重新讨论。
    • 



实验性层级
实验性组件：


    

  • 明确标记。
    • 

  • API 可能变更。
    • 

  • 不建议用于生产环境。
    • 



使用场景：


    

  • 新想法的测试。
    • 

  • 尚未确认是否多产品需要。
    • 



晋升路径：


    

  • 稳定后从实验性晋升为正式组件。
    • 



参考案例 React Aria：


    

  • Adobe React Spectrum 中的实验性组件。
    • 



变体策略
通过属性控制变体（推荐）：


<Button variant="primary" size="md" />
简洁，不会导致组件数量膨胀。


为每个变体创建独立组件（不推荐）：


<PrimaryButton />
<SecondaryButton />
<DestructiveButton />
避免这种做法——会导致变体爆炸。


最佳实践：


    

  • 通过属性（props）控制变体。
    • 

  • 每个组件最多 5-10 个变体。
    • 



无障碍投入
组件级无障碍的复杂性：


    

  • Combobox：键盘导航、aria-activedescendant、状态播报。
    • 

  • Modal：焦点陷阱、aria-modal、Esc 关闭。
    • 

  • 下拉菜单：角色 + 键盘导航。
    • 



值得设计系统统一投入：


    

  • 每个产品团队重复实现成本高昂。
    • 

  • 容易出错。
    • 



无头组件库：


    

  • Radix UI、Headless UI、Ariakit。
    • 

  • 内置完善的无障碍能力。
    • 

  • 自行提供样式。
    • 



API 设计
简单的默认用法：


<Button>保存</Button>
常见场景便捷使用：


<Button variant="primary" size="lg" onClick={...}>保存</Button>
边缘场景也能支持：


<Button variant="primary" asChild>
  <Link to="/save">保存</Link>
</Button>
asChild 模式（Radix）让使用方替换渲染元素。


组件与设计模式
组件：


    

  • 可复用的代码。
    • 

  • 导入后直接使用。
    • 



设计模式（Pattern）：


    

  • 可复用的设计方案。
    • 

  • 仅以文档形式存在。
    • 

  • 例如："表单验证模式"。
    • 



部分模式会演变为组件：


    

  • 高频使用后升级为组件。
    • 



部分内容仅保持为模式：


    

  • 太过领域特定。
    • 

  • 仅提供设计指导。
    • 



实战案例
Material Design：


    

  • 100+ 组件。
    • 

  • 主要是原子和分子组件。
    • 

  • 部分有机体组件（应用栏、抽屉）。
    • 

  • 有机体和模板以设计模式文档形式提供。
    • 



Atlassian Atlaskit：


    

  • 多包架构。
    • 

  • 频繁新增组件。
    • 

  • 活跃的弃用实践。
    • 



Shopify Polaris：


    

  • 面向商家的场景。
    • 

  • 包含部分电商领域特定组件。
    • 



shadcn/ui：


    

  • 不是 npm 包。
    • 

  • 复制粘贴到项目中。
    • 

  • 自由定制。
    • 

  • 改变了组件分发模式。
    • 



反模式
1. 上帝组件：


    

  • 一个组件通过 50 个属性覆盖所有场景。
    • 

  • 维护噩梦。
    • 



2. 每个变体一个组件：


    

  • PrimaryButton、SecondaryButton、TertiaryButton 各自独立。
    • 

  • 变体爆炸。
    • 



3. 来者不拒：


    

  • 接受所有产品团队的提议。
    • 

  • 系统臃肿。
    • 



4. 严格禁止定制：


    

  • 不提供任何灵活性。
    • 

  • 产品团队被迫绕过系统。
    • 



5. 不做弃用：


    

  • 新旧组件并存。
    • 

  • 消费方困惑。
    • 



决策框架
使用频率 × 稳定性 × 通用性：


    

  • 三项均高 → 纳入系统。
    • 

  • 一项高其他低 → 实验性。
    • 

  • 多项低 → 不纳入。
    • 



时间分配：


    

  • 60% 维护现有组件。
    • 

  • 30% 新组件开发。
    • 

  • 10% 实验性探索。
    • 



沟通
拒绝决策：


    

  • "我们不纳入 X 因为 Y"。
    • 

  • 建议替代方案。
    • 

  • 条件变化时欢迎重新讨论。
    • 



同意决策：


    

  • "已批准纳入设计系统"。
    • 

  • 规格说明 + 时间计划。
    • 

  • 追踪进度。
    • 



实战建议
1. 使用频率优先：


    

  • 优先构建多产品需要的组件。
    • 



2. 无障碍复杂度优先：


    

  • Combobox、Modal、日期选择器——产品团队很难做对。
    • 



3. 设置实验性层级：


    

  • 给探索空间，不急于承诺。
    • 



4. 提供无头选项：


    

  • 部分场景下提供。
    • 



5. 使用插槽模式：


    

  • 无需 fork 即可灵活定制。
    • 



6. 优雅拒绝：


    

  • 不对立冲突。
    • 

  • 追求双赢。
    • 



小结
组件化策略决定设计系统包含什么——基于使用频率×稳定性×通用性三维度评估。纳入标准为多产品使用 + API 稳定 + 通用目的 + 无障碍复杂。不纳入的场景为单产品使用 / 频繁演进 / 领域特定 / 过于简单。决策工作流为产品团队提议 RFC → 核心团队审查 → 同意/拒绝/待定（实验性）。无头组件与样式组件的权衡——样式组件使用简单且视觉一致但定制受限；无头组件极度灵活但需自行处理样式，现代方案采用混合模式（shadcn/ui = Radix 无头 + Tailwind 样式）。插槽模式 + 复合组件（Card.Header / Card.Body）+ 组合模式（Stack + 原子组件）让使用方无需 fork 即可定制。拒绝的场景为单产品 / 实验性 / 领域特定 / 频繁变化，让产品团队自建节省系统团队时间。实验性层级明确标记 + API 可变 + 稳定后晋升为正式组件。变体策略通过属性控制（每组件最多 5-10 个）而非独立组件（避免变体爆炸）。无障碍投入值得共同承担（Combobox / Modal / 下拉菜单），无头组件库 Radix UI / Headless UI / Ariakit 内置完善能力。API 设计遵循简单默认 + 常见便捷 + 边缘可支持（asChild 模式）。组件是可复用代码、设计模式是文档化的设计方案，部分模式高频使用后升级为组件。实战案例有 Material 100+ 组件以原子/分子为主、Atlaskit 多包+活跃弃用、Polaris 面向商家、shadcn/ui 复制粘贴改变分发模式。反模式包括上帝组件、每变体一组件、来者不拒、禁止定制和不做弃用。决策框架为频率×稳定性×通用性 + 时间分配 60% 维护 / 30% 新开发 / 10% 实验探索。建议使用频率优先 + 无障碍优先 + 实验性层级 + 无头选项 + 插槽模式 + 优雅拒绝。组件化是设计系统"范围"管理的核心——做对了让系统既有用又可维护。
