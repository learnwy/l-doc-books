权限与角色

核心概念

协作应用(Collaborative App)必须实现访问控制——决定谁可以编辑、查看、评论、分享和删除。常见角色包括所有者(Owner)、编辑者(Editor)、评论者(Commenter)和查看者(Viewer)，这一模式源自 Google Docs。分享体验包含链接分享（任何拥有链接的人）、邮件邀请和组织级范围限定。权限检查不仅仅是服务端的事——客户端界面也需要反映权限状态（例如对查看者禁用编辑按钮）。现代 PaaS 方案（如 Liveblocks）和自建后端各有取舍。本节讲解角色层级、权限模型、分享体验、双端执行（客户端+服务端）以及审计日志。

角色 权限 界面表现
所有者 全部权限 + 删除 + 转让所有权 完整编辑 + 管理功能
编辑者 读取 + 写入 + 评论 + 分享 完整编辑
评论者 读取 + 评论 查看 + 添加评论
查看者 仅读取 仅查看，隐藏编辑界面
匿名用户 取决于分享设置 可能的受限查看

角色层级

标准层级：

Owner > Editor > Commenter > Viewer

每个高级角色继承低级角色的全部权限：

  • 所有者可以执行编辑者的所有操作。
  • 编辑者可以执行评论者的所有操作。

自定义角色（部分应用支持）：

  • 按功能粒度授权。
  • 例如：可以编辑 X 但不能编辑 Y。

权限检查

服务端为权威来源：

async function canEdit(userId, docId) {
  const member = await db.members.findOne({ userId, docId });
  return member && ['owner', 'editor'].includes(member.role);
}

// 每次变更操作都进行检查
if (!(await canEdit(userId, docId))) {
  throw new Error('Forbidden');
}

客户端界面适配：

{
  userRole === 'editor' || userRole === 'owner' ? <EditButton /> : <ViewOnlyIndicator />;
}

两端都不可或缺：

  • 客户端体验层面：不展示用户无权执行的操作。
  • 服务端强制校验：不信任客户端。

邮件邀请
流程：


    

  1. 所有者输入邮箱地址并选择角色。
    2. 

  2. 服务端发送包含链接的邀请邮件。
    3. 

  3. 收件人点击链接 → 登录（如需要）→ 接受邀请。
    4. 

  4. 写入成员表。
    5. 



待处理的邀请：


    

  • 在成员列表中显示"待接受"标记。
    • 

  • 提供取消选项。
    • 



链接分享
任何拥有链接的人可访问：


    

  • 生成分享令牌(Share Token)。
    • 

  • 链接格式：/doc/abc?share=token123。
    • 

  • 链接中的令牌用于授予相应角色。
    • 



风险：


    

  • 链接一旦公开，任何人都能访问。
    • 

  • 撤销方式：轮换令牌。
    • 



限制策略：


    

  • 邮箱白名单。
    • 

  • 组织范围限定。
    • 



组织级范围
公司内部：


    

  • 所有员工默认拥有查看或评论权限。
    • 

  • 也可逐文档设置。
    • 



外部用户：


    

  • 需要显式邀请。
    • 

  • 可能赋予更严格的角色。
    • 



设置：


    

  • 所有者可选择默认权限级别。
    • 



基于 CRDT 操作的权限控制
使用 Yjs 时：


    

  • 服务端中间件在应用操作前进行检查。
    • 



function authorizeUpdate(userId, docId, update) {
  const role = getRole(userId, docId);
  if (role === 'viewer') return false;
  if (role === 'commenter') {
    // 仅允许评论相关的操作
    return isCommentOp(update);
  }
  if (role === 'editor' || role === 'owner') {
    return true;
  }
  return false;
}
操作级粒度控制：


    

  • 对原始 CRDT 操作实现细粒度控制较困难。
    • 

  • 对结构化操作（如评论与正文内容分离）则更容易实现。
    •

const editor = useEditor({

不发布光标：

不可以：

界面表现：

实时权限变更
当所有者移除用户时：


    

  • 服务端踢出用户（关闭 WebSocket 连接）。
    • 

  • 客户端收到断开通知。
    • 

  • 界面更新为"访问已撤销"。
    • 



// 服务端
function removeMember(userId, docId) {
  db.members.delete({ userId, docId });
  // 断开该用户的连接
  for (const ws of getSocketsForUser(userId, docId)) {
    ws.close(1008, 'Access revoked');
  }
}

Liveblocks 权限方案
托管模式：


import { authorize } from '@liveblocks/node';

app.post('/api/liveblocks-auth', async (req, res) => {
  const userId = await getUser(req);
  const role = await getRole(userId, req.body.room);

  const response = await authorize({
    room: req.body.room,
    userId,
    userInfo: { name, color },
    permissions: role === 'editor' ? ['room:write'] : ['room:read'],
  });

  res.send(response);
});
服务端签发令牌——客户端使用令牌连接。


权限相关接口
服务端接口设计：


    

  • POST /docs/:id/share（邀请成员）
    • 

  • DELETE /docs/:id/members/:userId（移除成员）
    • 

  • PATCH /docs/:id/members/:userId（变更角色）
    • 

  • PATCH /docs/:id（修改可见性/链接分享设置）
    • 

  • GET /docs/:id/audit（审计日志）
    • 



反模式
1. 仅在客户端检查权限：


    

  • 可通过开发者工具绕过。
    • 

  • 必须在服务端强制校验。
    • 



2. 不记录审计日志：


    

  • 出问题时无法追溯。
    • 



3. 角色过多：


    

  • 用户容易混淆。
    • 

  • 建议不超过 4-5 个角色。
    • 



4. 撤销权限后不立即断开连接：


    

  • 被移除的用户仍能看到实时更新。
    • 

  • 应立即强制断开连接。
    • 



5. 默认公开：


    

  • 存在隐私泄露风险。
    • 

  • 应默认私有。
    • 



6. 不向用户展示其当前角色：


    

  • 用户会困惑"为什么我不能编辑？"
    • 

  • 应显示"仅查看"指示器。
    • 



实战建议
1. 以服务端校验为主：


    

  • 永远不信任客户端。
    • 



2. 客户端做界面提示：


    

  • 对查看者禁用编辑功能。
    • 



3. 使用标准角色层级：


    

  • 所有者、编辑者、评论者、查看者。
    • 



4. 同时支持邮件邀请和链接分享：


    

  • 两者都是常见的分享方式。
    • 



5. 对关键操作记录审计日志：


    

  • 分享、角色变更、删除等操作。
    • 



6. 权限变更实时生效：


    

  • 撤销权限时立即断开连接。
    •

小结
协作应用的访问控制核心是角色体系——所有者、编辑者、评论者、查看者，配合邮件邀请、链接分享和组织级范围三种分享方式。服务端对每次变更操作进行权威校验，客户端则做界面层提示（不展示用户无权操作的功能）。分享弹窗遵循行业标准模式（Google Docs / Notion）——成员列表配角色选择器、邮箱添加、链接分享开关配角色选择。邮件邀请流程为输入邮箱和角色 → 服务端发送邮件 → 收件人点击登录并接受，待处理的邀请可取消。链接分享通过令牌实现，可轮换令牌来撤销，可通过邮箱白名单或组织范围加以限制。组织内部默认给予查看或评论权限，外部用户需显式邀请且权限更严格。基于 CRDT 操作的权限控制通过中间件在应用操作前检查，操作级粒度对原始 CRDT 较难实现但对结构化操作（评论与正文分离）较容易。只读模式设置编辑器为不可编辑且不发布感知状态。仅评论模式允许阅读和添加评论但不能编辑正文。审计日志记录用户、文档、操作类型和时间戳，仅管理员或所有者可在"活动记录"标签页查看。实时权限变更时服务端关闭 WebSocket 连接，客户端收到断开通知并显示"访问已撤销"。企业场景使用 SAML/OIDC 单点登录并根据用户组自动分配角色。公开文档可被搜索引擎索引，需确认才能设为公开，并记录审计。权限可从文件夹或工作区继承，也可单独覆盖。Liveblocks 提供内置权限令牌签发机制，自建方案则更灵活。应避免的反模式包括：仅客户端检查（可绕过）、不记录审计日志（无法追溯）、角色过多（用户混淆）、撤销后不立即断开（残留访问）、默认公开（隐私泄露）、不展示当前角色（用户困惑）。实战建议：服务端校验为主、客户端做界面提示、使用标准角色层级、同时支持邮件和链接分享、对关键操作记录审计、权限变更实时生效。
