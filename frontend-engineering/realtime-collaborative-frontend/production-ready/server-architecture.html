Part IV · 浏览器与平台 (Browser & Platform)实时协作前端生产就绪服务器架构

服务器架构

核心概念

将协作原型推向生产环境时，服务器架构决定了系统的可靠性、可扩展性、成本和延迟。常见模式包括：单节点有状态 WebSocket 服务器（适合小规模）、水平集群 + Redis 消息代理（中等规模）、边缘有状态的持久化对象(Durable Objects)（现代方案）、无服务器（受限场景）以及平台即服务(PaaS)。持久化方面通常选择数据库或对象存储（存储 Y.Doc 二进制数据）。认证通过信令端点下发令牌实现。监控关注连接数、延迟和错误率。本节详细介绍服务器架构模式、持久化策略、扩容决策和运维注意事项。

模式 规模 延迟 复杂度 成本
单节点有状态 10万连接 低 低 低
集群 + Redis 100万-1000万 低 中 中
边缘有状态 全球 极低 中 中（按消息计费）
无服务器 有限 中 低 不确定
平台即服务 任意 低 极低 高（按消息计费）

单节点有状态服务器

架构特点：

  • 单个 Node.js / Go / Rust 进程承载所有连接。
  • 所有 WebSocket 连接由同一进程管理。
  • 文档状态保存在内存或数据库中。

适用场景：

  • 并发连接数小于 10 万。
  • 月活用户小于 100 万。
  • 小团队或初创公司。

优势：

  • 部署极其简单。
  • 无需处理分布式系统的复杂性。

劣势：

  • 存在单点故障风险。
  • 存在扩展上限。

技术栈：

  • Node.js + ws + Yjs。
  • 通过回调方式持久化到数据库。
import { WebSocketServer } from 'ws';
import * as Y from 'yjs';

const wss = new WebSocketServer({ port: 1234 });
const docs = new Map();  // roomId → Y.Doc

wss.on('connection', (ws, req) => {
  const roomId = getRoomId(req);
  let doc = docs.get(roomId);
  if (!doc) {
    doc = await loadDocFromDB(roomId);
    docs.set(roomId, doc);
  }

  // 接收并应用客户端发来的更新
  ws.on('message', (data) => {
    Y.applyUpdate(doc, new Uint8Array(data));
    // 广播给房间内其他客户端
    broadcastToRoom(roomId, data, ws);
    // 持久化到数据库
    saveDocToDB(roomId, doc);
  });

  // 发送初始状态
  const state = Y.encodeStateAsUpdate(doc);
  ws.send(state);
});

水平集群

多服务器 + Redis 消息代理架构：

每台服务器订阅 Redis 对应房间的频道。


收到消息后的处理流程：


    

  • 在本地应用更新。
    • 

  • 发布到 Redis。
    • 

  • 其他服务器收到消息后，转发给本机上该房间的所有客户端。
    • 



会话粘滞(Sticky Session)：


    

  • 负载均衡器将同一用户路由到同一台服务器。
    • 

  • 通常基于 Cookie 实现。
    • 



边缘有状态
Cloudflare 持久化对象(Durable Objects)：


    

  • 每个房间在全球拥有唯一的单实例。
    • 

  • 实例自动迁移到离用户最近的数据中心。
    • 

  • 提供强一致性保证。
    • 



架构实现：


export class RoomDurableObject {
  constructor(state, env) {
    this.state = state;
    this.sessions = [];
    this.doc = new Y.Doc();
  }

  async fetch(request) {
    const url = new URL(request.url);

    if (url.pathname === '/connect') {
      const [client, server] = Object.values(new WebSocketPair());
      this.handleSession(server);
      return new Response(null, { status: 101, webSocket: client });
    }
  }

  handleSession(ws) {
    ws.accept();
    this.sessions.push(ws);

    ws.addEventListener('message', (event) => {
      Y.applyUpdate(this.doc, new Uint8Array(event.data));
      // 广播给该持久化对象中的所有会话
      this.sessions.forEach((s) => s !== ws && s.send(event.data));
    });

    ws.addEventListener('close', () => {
      this.sessions = this.sessions.filter((s) => s !== ws);
    });

    // 发送当前状态
    ws.send(Y.encodeStateAsUpdate(this.doc));
  }
}
自动扩展——Cloudflare 自动处理实例管理。


费用：


    

  • 每百万条 WebSocket 消息 $0.65。
    • 

  • 每百万次持久化对象请求 $0.50。

增量保存
避免每次都保存完整文档：


let pendingUpdates = [];

doc.on('update', (update) => {
  pendingUpdates.push(update);
  debouncedSave();
});

const debouncedSave = debounce(async () => {
  const batch = pendingUpdates;
  pendingUpdates = [];
  await db.docUpdates.insertMany(
    batch.map((u, i) => ({
      docId,
      update: u,
      ts: Date.now(),
    })),
  );
}, 5000);
恢复流程：


    

  • 加载所有增量更新。
    • 

  • 按时间顺序依次应用。
    • 



压缩合并：


    

  • 定期将多个增量更新合并为一个快照。
    • 

  • 减少存储空间和加载时间。
    • 



快照 + 增量更新
混合策略：


    

  • 定期保存完整快照。
    • 

  • 快照之后的更新以增量方式追加。
    • 

  • 恢复时先加载快照，再重放后续的增量更新。
    • 



async function loadDoc(id) {
  const { snapshot, snapshotTs } = await db.snapshots.findById(id);
  const updates = await db.updates.find({ id, ts: { $gt: snapshotTs } });

  const doc = new Y.Doc();
  Y.applyUpdate(doc, snapshot);
  for (const update of updates) {
    Y.applyUpdate(doc, update.data);
  }
  return doc;
}
快照频率：


    

  • 每小时一次或达到 N 次更新时触发。
    • 

  • 通过后台定时任务执行。

重连机制
客户端自动重连：


class ReconnectingWS {
  connect() {
    this.ws = new WebSocket(this.url);
    this.ws.addEventListener('close', () => {
      const delay = Math.min(1000 * 2 ** this.attempt++, 30000);
      setTimeout(() => this.connect(), delay);
    });
    this.ws.addEventListener('open', () => {
      this.attempt = 0;
    });
  }
}
状态恢复：


    

  • 重连后发送 Y.encodeStateVector，服务器只返回差量数据。
    • 

  • 无需重新传输完整状态。

心跳检测
检测失效连接：


setInterval(() => {
  wss.clients.forEach((ws) => {
    if (ws.isAlive === false) return ws.terminate();
    ws.isAlive = false;
    ws.ping();
  });
}, 30000);

wss.on('connection', (ws) => {
  ws.isAlive = true;
  ws.on('pong', () => {
    ws.isAlive = true;
  });
});

小结
生产环境的协作服务器架构有五种主要模式：单节点有状态服务器（适合 10 万以下并发的简单场景）、集群 + Redis 消息代理（支持百万到千万级别，依赖会话粘滞和跨服务器发布/订阅）、边缘有状态的 Cloudflare 持久化对象（全球低延迟，每个房间单实例，自动迁移到最近的用户）、无服务器（适用场景有限）、平台即服务如 Liveblocks（按消息计费）。


持久化方面，将 Y.Doc 编码为二进制通过 Y.encodeStateAsUpdate 保存、通过 Y.applyUpdate 加载，存储可选 Postgres BYTEA、MongoDB Binary、S3（大文档）或 IndexedDB（客户端）。保存频率根据文档大小选择即时保存、防抖保存或断连时保存。增量保存通过批量追加更新记录并定期压缩为快照来减少存储和加载时间。混合策略结合定期快照和增量更新，恢复时先加载快照再重放后续更新。


认证采用基于 JWT 的令牌验证，短期令牌（5-15 分钟）配合 HTTP 端点刷新。重连采用指数退避策略（最大 30 秒），重连后通过状态向量实现差量同步而非全量传输。心跳通过 ping/pong 机制每 30 秒检测一次，清除失效连接。


负载测试使用 Artillery 或 k6，模拟万级并发和高频消息持续一小时。监控使用 Prometheus + Grafana 或 Datadog，设置连接断开、高延迟和服务器崩溃的告警。成本方面，自托管 10 万并发约每月 200−500，百万并发约每月200-500，百万并发约每月200−500，百万并发约每月5000-20000，Cloudflare 按消息计费，Liveblocks 按月活计费约每千人 $30-200。


一个简单的检验标准：你能否为 10 万并发用户设计一个完整的协作服务器架构，包括持久化、认证、重连、心跳和监控方案？
