WebRTC 与点对点通信

核心概念

WebRTC（Web Real-Time Communication，2011 年规范）让浏览器之间建立直接的点对点（P2P）连接——无需服务器转发数据，延迟极低且不占用服务器带宽。它最初为视频/语音通话设计（Google Meet、Zoom Web、Discord、Whereby 使用），但 RTCDataChannel 允许任意二进制/文本数据的 P2P 传输——实时游戏、协作白板、文件分享、P2P 的 CRDT 同步。然而 P2P 的 NAT 穿透非常复杂——需要 STUN（检测公网 IP）+ TURN（P2P 失败时的中继回退）+ 信令服务器（初始握手）。本节介绍 WebRTC 架构、SDP/ICE 协议、STUN/TURN 服务器、DataChannel 以及典型应用场景。

组件 作用
信令服务器 协商 offer/answer（通过服务器中转）
STUN 检测 NAT 后的公网 IP
TURN P2P 失败时的中继回退
ICE 连接建立机制
DTLS/SRTP 加密传输
RTCPeerConnection 浏览器 API
RTCDataChannel 任意数据的 P2P 传输

WebRTC 的三大 API

三个主要接口：

  • MediaStream：摄像头/麦克风音视频流。
  • RTCPeerConnection：对等连接状态管理。
  • RTCDataChannel：任意数据传输。

按场景组合使用：

  • 视频通话：MediaStream + PeerConnection。
  • 游戏同步：DataChannel + PeerConnection。
  • 综合场景：三者结合。

连接建立流程

步骤：

1. 信令阶段（通过服务器中转）：

  • 对等方 A 发送 SDP offer。
  • 对等方 B 收到后生成 SDP answer。
  • 双方交换 ICE 候选地址。
  • 信令服务器（通常使用 WebSocket）负责转发。

2. STUN 查询：

  • 各对等方向 STUN 服务器询问"我的公网 IP 和端口是什么？"
  • 结果作为 ICE 候选地址。

3. ICE 连接：

  • 尝试在对等方之间建立直接连接。
  • 若 NAT 类型友好 → 连接成功。
  • 若失败 → 使用 TURN 中继。

4. 连接就绪：

  • DTLS 握手完成。
  • 数据加密传输。
  • 音视频和数据开始流动。
SDP 与 ICE
SDP（会话描述协议）：


    

  • 描述媒体和连接参数。
    • 

  • 包含编解码器、分辨率、带宽信息。
    • 

  • 包含 IP 和端口。
    • 



ICE（交互式连接建立）：


    

  • 候选地址列表（IP/端口/协议）。
    • 

  • 逐对尝试连接。
    • 

  • 选择最佳路径。
    • 



Trickle ICE（逐步发现）：


    

  • 发现候选地址后立即发送（不等全部收集完）。
    • 

  • 加速连接建立。
    • 



STUN 服务器
NAT 会话穿越工具：


    

  • 服务器返回客户端的公网 IP 和端口。
    • 

  • 简单、轻量。
    • 

  • 有免费的公共服务器（如 Google 的 stun.l.google.com）。
    • 



使用方式：


new RTCPeerConnection({
  iceServers: [{ urls: 'stun:stun.l.google.com:19302' }],
});
TURN 服务器
NAT 中继穿越：


    

  • 当 P2P 无法建立时使用（对称型 NAT、防火墙阻断）。
    • 

  • 服务器中继转发流量。
    • 



成本：


    

  • 占用服务器带宽。
    • 

  • 通常需付费（CoTURN、Twilio、Cloudflare Realtime）。
    • 



使用方式：


new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    {
      urls: 'turn:turn.example.com:3478',
      username: 'user',
      credential: 'pass',
    },
  ],
});
RTCPeerConnection API
建立连接：


const pc = new RTCPeerConnection({
  iceServers: [{ urls: 'stun:stun.l.google.com:19302' }],
});

// 监听 ICE 候选地址
pc.addEventListener('icecandidate', (event) => {
  if (event.candidate) {
    sendToSignaling({ type: 'candidate', candidate: event.candidate });
  }
});

// 监听远端媒体轨道
pc.addEventListener('track', (event) => {
  remoteVideo.srcObject = event.streams[0];
});

// 发起方创建 offer
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
sendToSignaling({ type: 'offer', sdp: offer });

// 收到 answer
await pc.setRemoteDescription(msg.sdp);

// 收到远端候选地址
await pc.addIceCandidate(msg.candidate);

// 被叫方处理 offer
async function onOffer(msg) {
  await pc.setRemoteDescription(msg.sdp);
  const answer = await pc.createAnswer();
  await pc.setLocalDescription(answer);
  sendToSignaling({ type: 'answer', sdp: answer });
}
RTCDataChannel
任意数据的点对点传输：


// 发起方创建数据通道
const channel = pc.createDataChannel('chat', {
  ordered: true, // 保持顺序
  maxRetransmits: 3, // 或使用 maxPacketLifeTime 实现不可靠传输
});

channel.addEventListener('open', () => {
  channel.send('Hello');
});

channel.addEventListener('message', (event) => {
  console.log(event.data);
});

// 被叫方监听数据通道
pc.addEventListener('datachannel', (event) => {
  const channel = event.channel;
  channel.addEventListener('message', (event) => {
    console.log(event.data);
  });
});
传输模式：


    

  • 可靠且有序（默认，类似 TCP）。
    • 

  • 不可靠（类似 UDP，适合游戏）。
    • 

  • 无序。
    • 



应用场景示例
视频通话：


    

  • MediaStream + PeerConnection。
    • 

  • 小型群组用 Mesh 拓扑，大型群组用 SFU（选择性转发单元）。
    • 



P2P 游戏：


    

  • DataChannel 传输游戏状态。
    • 

  • 延迟极低。
    • 

  • 存在作弊风险 → 关键操作需服务器验证。
    • 



协作白板：


    

  • DataChannel + Yjs。
    • 

  • 无需服务器的 P2P 同步。
    • 



文件分享：


    

  • DataChannel 分块传输。
    • 

  • WebTorrent、PeerCalls 等项目。
    • 



Mesh 与 SFU 对比
Mesh 拓扑（所有人互连）：


    

  • N 个对等方 → 每人 N×(N-1)/2 个连接。
    • 

  • 每人上传 N-1 路流。
    • 

  • 适合小型群组（≤ 4 人）。
    • 



SFU（选择性转发单元）：


    

  • 中央服务器转发（但不转码）。
    • 

  • 每人上传 1 路，下载 N-1 路。
    • 

  • 适合中型群组（5-100 人）。
    • 



MCU（多点控制单元）：


    

  • 服务器转码并合成画面。
    • 

  • 每人上传和下载各 1 路。
    • 

  • 服务器成本高。
    • 

  • 适合大规模或特殊场景。
    • 



信令服务器
规范不定义具体实现——可使用任何机制：


    

  • WebSocket（最常用）。
    • 

  • SSE。
    • 

  • HTTP 轮询。
    • 



需要完成的任务：


    

  • 转发 SDP offer/answer。
    • 

  • 转发 ICE 候选地址。
    • 

  • 通常还包含用户列表和房间管理。
    • 



常见陷阱
1. 不提供 TURN 回退：


    

  • 部分用户无法建立连接。
    • 

  • TURN 是必备的回退方案。
    • 



2. 大群组使用 Mesh：


    

  • 带宽急剧增长。
    • 

  • 应使用 SFU。
    • 



3. 不做自适应码率：


    

  • 网络状况差时视频卡顿。
    • 



4. 不监控连接状态：


    

  • 连接中断后无法检测。
    • 



安全性
强制加密：


    

  • DTLS 保护信令和 ICE 数据。
    • 

  • SRTP 保护媒体流。
    • 

  • 没有明文传输的选项。
    • 



权限控制：


    

  • 摄像头/麦克风需用户授权。
    • 

  • 信令阶段需认证用户身份。
    • 



现代工具链
库和框架：


    

  • simple-peer：简化 API。
    • 

  • PeerJS：封装了信令。
    • 

  • LiveKit：SFU + 客户端 SDK。
    • 

  • Agora、Twilio Video：商业方案。
    • 



SFU 服务器：


    

  • Janus。
    • 

  • mediasoup。
    • 

  • LiveKit（开源）。
    • 



TURN 服务：


    

  • coturn（开源）。
    • 

  • Twilio TURN。
    • 

  • Cloudflare Realtime（2024 年推出）。
    • 



实战建议
1. 使用封装库：


    

  • simple-peer / PeerJS / LiveKit。
    • 

  • 生产环境不建议直接使用原始 API。
    • 



2. 必须提供 TURN：


    

  • 作为 P2P 失败时的回退。
    • 



3. 处理重连：


    

  • ICE 连接失败时触发 ICE 重启。
    • 



4. 监控关键指标：


    

  • 码率、丢包率、延迟。
    • 



5. 超过 4 人时使用 SFU：


    

  • LiveKit / mediasoup。
    • 



6. 测试多种网络环境：


    

  • 企业防火墙、移动蜂窝网络、VPN。
    • 



小结
WebRTC（2011 年规范）让浏览器之间建立 P2P 连接——不经服务器转发，延迟极低且不占服务器带宽。三大 API 包括 MediaStream（摄像头/麦克风）、RTCPeerConnection（连接管理）和 RTCDataChannel（任意数据传输）。连接建立需要信令服务器转发 SDP offer/answer 和 ICE 候选地址、STUN 服务器检测公网 IP、TURN 中继作为回退方案。ICE 机制负责在多个候选路径中选择最优连接，DTLS/SRTP 保证传输加密。拓扑方面，Mesh 适合 4 人以下小组，SFU 适合 5-100 人中型群组，MCU 适合大规模场景。DataChannel 支持可靠有序（类 TCP）和不可靠（类 UDP）两种模式。现代方案推荐使用 simple-peer、LiveKit 等封装库，并配置 TURN 回退、自适应码率和连接状态监控。
