Part IV · 浏览器与平台 (Browser & Platform)实时协作前端实时基础传输协议选择

传输协议选择

核心概念

实时 Web 应用的传输协议选择决定了延迟、成本和复杂度——五种主流方案包括 WebSocket、SSE、长轮询、WebRTC 和 HTTP 轮询。选择依据包括通信方向（单向/双向）、延迟要求、扩展规模、防火墙兼容性和数据格式（二进制/文本）。现代应用通常混合使用——WebSocket 用于协作数据同步、SSE 用于 AI 流式输出、WebRTC 用于音视频、HTTP 用于一次性 API 请求。本节介绍传输选择框架、决策树、常见组合方案和成本考量。

传输方式 方向 延迟 成本特征 最适场景
WebSocket 双向 极低 有状态 聊天/协作/游戏
SSE 服务器→客户端 极低 有状态 通知/流式输出
长轮询 模拟双向 中 无状态 旧系统/降级方案
WebRTC P2P 极低 TURN 成本 音视频/P2P 数据
HTTP 轮询 模拟双向 高 无状态 简单/低成本

决策框架

1. 通信方向：

  • 仅需服务器推送 → SSE。
  • 需要双向通信 → WebSocket / WebRTC。

2. 延迟要求：

  • 小于 100 毫秒 → WebSocket / WebRTC。
  • 1 秒可接受 → SSE / 轮询。
  • 无实时要求 → HTTP。

3. 扩展规模：

  • 百万级并发 → 考虑无状态方案（HTTP 轮询）或边缘有状态方案（Cloudflare Durable Objects）。
  • 十万级 → 标准 WebSocket 集群。

4. 防火墙兼容性：

  • 企业严格防火墙 → SSE / HTTP（443 端口）。
  • 普通环境 → WebSocket 通常没问题。

5. 数据格式：

  • 二进制数据 → WebSocket / WebRTC DataChannel。
  • 纯文本 → SSE / HTTP。

6. 带宽来源：

  • 服务器带宽受限 → P2P（WebRTC）。
  • 服务器带宽充足 → WebSocket。
场景匹配
聊天应用：


    

  • 消息通信：WebSocket。
    • 

  • 通知推送（服务器驱动）：SSE 或推送通知。
    • 

  • 表情回应：WebSocket。
    • 



类 Google Docs 协作：


    

  • 文档同步：WebSocket。
    • 

  • 光标/在线感知：WebSocket。
    • 

  • 部分场景可用 WebRTC P2P。
    • 



实时交易面板：


    

  • 价格更新：SSE 或 WebSocket。
    • 

  • 下单操作：HTTP POST。
    • 



多人游戏：


    

  • 实时状态：WebSocket / WebRTC。
    • 

  • 大厅匹配：HTTP。
    • 

  • 语音通话：WebRTC。
    • 



类 ChatGPT 流式输出：


    

  • LLM 响应流：SSE。
    • 

  • 用户输入：HTTP POST 触发 SSE 流。
    • 



视频通话：


    

  • 音视频：WebRTC。
    • 

  • 信令交换：WebSocket。
    • 

  • 聊天侧边栏：同一个 WebSocket 连接。
    • 



常见组合
1. WebSocket + HTTP：


    

  • HTTP 处理增删改查（初始加载、数据变更）。
    • 

  • WebSocket 处理实时通信（协作、通知）。
    • 

  • 大多数协作应用采用此方案。
    • 



2. SSE + HTTP：


    

  • HTTP 处理用户输入。
    • 

  • SSE 处理服务器输出（AI 流式、通知流）。
    • 



3. WebRTC + WebSocket：


    

  • WebRTC 处理音视频媒体。
    • 

  • WebSocket 处理信令和文字聊天。
    • 



4. HTTP + 推送通知：


    

  • 不保持持久连接。
    • 

  • 通过推送通知重新唤起用户。
    • 



5. 四者兼用：


    

  • 复杂应用：HTTP 增删改查 + WebSocket 协作 + SSE 通知 + WebRTC 语音。
    • 



延迟对比
单程平均延迟（典型值）：


    

  • WebRTC P2P：5-20 毫秒。
    • 

  • WebRTC TURN 中继：30-100 毫秒。
    • 

  • WebSocket：30-100 毫秒。
    • 

  • SSE：30-100 毫秒。
    • 

  • 长轮询：50-500 毫秒。
    • 

  • HTTP 轮询（5秒间隔）：平均 2.5 秒。
    • 



实时游戏：


    

  • 理想小于 50 毫秒。
    • 

  • 必须使用 WebRTC。
    • 



聊天应用：


    

  • 200 毫秒以内可接受。
    • 

  • WebSocket 完全满足。
    • 



成本对比
百万并发的服务器成本：


    

  • WebSocket：较高（有状态，每连接占用内存）。
    • 

  • SSE：与 WebSocket 类似。
    • 

  • 长轮询：较高（每轮询周期一个连接）。
    • 

  • HTTP 轮询：较低（无状态）。
    • 

  • WebRTC P2P：较低（仅需信令 + STUN，必要时加 TURN）。
    • 



带宽方面：


    

  • WebRTC P2P 不占用服务器带宽。
    • 

  • WebSocket / SSE 全部流量经由服务器。
    • 



防火墙与代理
WebSocket：


    

  • 大多数场景通过 443 端口（WSS）正常工作。
    • 

  • 部分企业防火墙会阻断。
    • 



SSE：


    

  • 基于 HTTP 协议。
    • 

  • 几乎所有防火墙均可通过。
    • 



HTTP 轮询：


    

  • 防火墙兼容性最好。
    • 

  • 始终可用。
    • 



WebRTC：


    

  • 部分防火墙阻断 P2P 连接。
    • 

  • TURN 回退使用类 HTTPS 的方式穿越。
    • 



实战建议：


    

  • 敌对网络环境 → SSE / HTTP。
    • 

  • 其他环境 → WebSocket。
    • 



有状态与无状态服务器
有状态：


    

  • WebSocket / SSE / WebRTC 信令。
    • 

  • 每台服务器维护连接状态。
    • 

  • 扩展需要粘性会话或消息中间件（Redis 发布/订阅）。
    • 



无状态：


    

  • HTTP / 轮询。
    • 

  • 容易扩展。
    • 

  • 延迟较高。
    • 



边缘有状态：


    

  • Cloudflare Durable Objects。
    • 

  • 每个房间全球唯一实例。
    • 

  • 强一致性。
    • 

  • 趋势上升中。
    • 



现代模式
1. 边缘实时：


    

  • Cloudflare Durable Objects + WebSocket。
    • 

  • PartyKit、Cloudflare Realtime。
    • 

  • 每个房间全球唯一实例。
    • 



2. SSE 用于 AI：


    

  • ChatGPT、Claude 的主流方案。
    • 

  • OpenAI / Anthropic SDK 内置 SSE 处理。
    • 



3. WebRTC + 边缘 SFU：


    

  • Cloudflare Realtime（2024 年推出）。
    • 

  • 提供免费套餐。
    • 



4. WebTransport（HTTP/3）：


    

  • WebSocket 的替代方案。
    • 

  • 支持多路复用和不可靠传输模式。
    • 

  • 浏览器支持正在扩展。
    • 



反模式
1. 一次性数据用 WebSocket：


    

  • 开销过大，应使用 HTTP。
    • 



2. 高频 HTTP 轮询：


    

  • 服务器负载高且延迟大。
    • 

  • 应使用 WebSocket 或 SSE。
    • 



3. 所有场景用 WebRTC：


    

  • 过于复杂且成本高。
    • 

  • 仅用于音视频和低延迟 P2P 场景。
    • 



4. 不提供降级方案：


    

  • 在敌对网络环境中会失败。
    • 

  • 应提供 SSE / HTTP 降级。
    • 



5. 全局只用一种传输：


    

  • 应根据不同场景选择不同协议。
    • 



实战建议
1. 根据需求匹配传输协议：


    

  • 使用决策树做判断。
    • 



2. 不要过度设计：


    

  • 简单场景用 HTTP 即可。
    • 



3. 混合使用多种传输：


    

  • 没有单一的万能答案。
    • 



4. 测试多种网络环境：


    

  • 办公网络、移动网络、VPN。
    • 



5. 监控延迟指标：


    

  • 基于真实用户数据。
    • 



6. 面向未来：


    

  • WebTransport 即将成熟。
    • 



小结
实时传输协议的选择决定了延迟、成本和复杂度。五种方案各有定位：WebSocket 适合双向低延迟的聊天/协作/游戏场景；SSE 适合服务器推送的通知和流式输出；长轮询作为旧系统的兼容方案；WebRTC 适合音视频和 P2P 数据传输；HTTP 轮询最简单但延迟最高。选择框架包括通信方向、延迟要求、扩展规模、防火墙兼容性和数据格式五个维度。现代应用通常组合使用多种协议。延迟方面，WebRTC P2P 最低（5-20 毫秒），WebSocket 和 SSE 居中（30-100 毫秒），HTTP 轮询最高。成本方面，P2P 不占服务器带宽，有状态连接（WebSocket/SSE）每连接需内存和进程资源。现代趋势包括边缘有状态（Cloudflare Durable Objects）、SSE 用于 AI 流式输出和 WebTransport 作为下一代协议。
