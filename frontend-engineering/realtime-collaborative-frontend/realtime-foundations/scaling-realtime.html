Part IV · 浏览器与平台 (Browser & Platform)实时协作前端实时基础实时系统扩展

实时系统扩展

核心概念

实时服务器的扩展比无状态 HTTP 困难得多——连接是有状态的（长期保持的用户连接）、连接状态存在于进程内存中、水平扩展需要跨服务器的消息路由。单台服务器通常支撑 5-10 万 WebSocket 连接，百万级并发需要集群 + Redis 发布/订阅中间件（或 Kafka、NATS）。现代替代方案包括边缘有状态架构（Cloudflare Durable Objects 提供每房间全球唯一实例）和 PaaS 平台（Pusher / Ably / Liveblocks / PartyKit）抽象了扩展复杂性。本节介绍有状态服务器扩展、房间架构、消息中间件模式、边缘实时和成本考量。

方案 规模 复杂度 成本 适用场景
单服务器 10 万 低 低 小型应用
集群 + Redis 百万-千万 中 中 中大型应用
边缘有状态 全球 中 中 现代协作应用
PaaS 平台 任意 极低 高（按消息计费） 跳过基础设施建设

单服务器上限

单台服务器的典型能力：

  • 约 5-10 万 WebSocket 连接（经调优的 Node.js）。
  • 约 20 万 SSE 连接（每连接状态更轻量）。
  • 受限于文件描述符和内存。

调优手段：

  • 增大 ulimit。
  • 增大 TCP socket 缓冲区。
  • 使用高效框架（uWebSockets.js、Bun）。

瓶颈因素：

  • CPU：序列化开销。
  • 内存：连接状态占用。
  • 网络：带宽限制。

水平扩展

多服务器架构：

  • N 台服务器，约 N × 10 万连接。
  • 负载均衡器分发连接。

核心挑战：

  • 用户 A 在服务器 1，用户 B 在服务器 2。
  • A 发送消息后，如何路由到 B？

解决方案：

  • 消息中间件（Redis 发布/订阅、Kafka、NATS）。
房间架构
核心概念：


    

  • 每个协作会话是一个"房间"。
    • 

  • 同一房间内的用户能看到彼此的更新。
    • 

  • 不同房间互不干扰。
    • 



实现方式：


    

  • 每台 WebSocket 服务器订阅 Redis 频道 room:${id}。
    • 

  • 用户加入房间 → 服务器订阅对应频道。
    • 

  • 消息发布到频道 → 所有订阅的服务器收到 → 转发给本地房间内的客户端。
    • 



代码示例（Node.js）：


import Redis from 'ioredis';

const sub = new Redis();
const pub = new Redis();
const rooms = new Map(); // roomId → Set<WebSocket>

sub.psubscribe('room:*');
sub.on('pmessage', (pattern, channel, message) => {
  const roomId = channel.split(':')[1];
  const clients = rooms.get(roomId) || new Set();
  for (const ws of clients) {
    ws.send(message);
  }
});

wss.on('connection', (ws, req) => {
  const roomId = getRoomId(req);
  if (!rooms.has(roomId)) rooms.set(roomId, new Set());
  rooms.get(roomId).add(ws);

  ws.on('message', (data) => {
    pub.publish(`room:${roomId}`, data.toString());
  });

  ws.on('close', () => {
    rooms.get(roomId).delete(ws);
  });
});
消息中间件选型
Redis 发布/订阅：


    

  • 简单且快速。
    • 

  • 即发即忘（不支持消息回放）。
    • 

  • 按频道扩展。
    • 



Kafka：


    

  • 持久化存储，支持消息回放。
    • 

  • 吞吐量极高。
    • 

  • 部署和维护较复杂。
    • 



NATS：


    

  • 轻量且快速。
    • 

  • 内置集群支持。
    • 



RabbitMQ：


    

  • 传统消息队列。
    • 

  • 路由策略灵活。
    • 



选择建议：


    

  • 实时广播分发 → Redis（最常用）。
    • 

  • 需要消息回放 → Kafka。
    • 

  • 追求高性能且架构简单 → NATS。
    • 



连接状态存储
内存存储：


    

  • 访问最快。
    • 

  • 但服务器崩溃即丢失。
    • 



Redis 哈希：


    

  • 跨服务器共享。
    • 

  • 速度稍慢。
    • 



数据库持久化：


    

  • 可靠性最高。
    • 

  • 速度最慢。
    • 



常见策略：


    

  • 热数据（光标、在线状态）：内存 + Redis 备份。
    • 

  • 持久数据（文档内容）：数据库。
    • 



粘性会话
负载均衡器将同一用户路由到同一服务器：


    

  • 基于 Cookie。
    • 

  • 基于 IP。
    • 



为何需要：


    

  • 连接状态在单台服务器内存中。
    • 

  • 重连到不同服务器会丢失状态。
    • 



解决方案：


    

  • 粘性会话。
    • 

  • 或通过 Redis 共享状态。
    • 



实践中：


    

  • 多数应用采用粘性会话 + Redis 结合。
    • 



边缘实时架构
Cloudflare Durable Objects：


    

  • 每个对象（房间）全球唯一实例。
    • 

  • 强一致性保证。
    • 

  • 自动迁移到最近的用户位置。
    • 



每房间模型：


    

  • 每个房间一个实例。
    • 

  • 所有该房间的用户连接到同一实例。
    • 

  • 无需跨服务器消息传递。
    • 



代码示例：


export class RoomDurableObject {
  constructor(state, env) {
    this.state = state;
    this.sessions = [];
  }

  async fetch(request) {
    const [client, server] = Object.values(new WebSocketPair());
    this.sessions.push(server);
    server.accept();

    server.addEventListener('message', (event) => {
      this.sessions.forEach((s) => s !== server && s.send(event.data));
    });

    return new Response(null, { status: 101, webSocket: client });
  }
}
定价：


    

  • 约 $0.65 每百万条 WebSocket 消息。
    • 

  • 按实例请求计费。
    • 



PaaS 平台选项
Pusher / Ably：


    

  • 实时消息广播。
    • 

  • 支持 WebSocket 和 SSE。
    • 

  • 按消息计费。
    • 



Liveblocks：


    

  • 面向 React 的协作平台。
    • 

  • 内置光标、共享状态、文档功能。
    • 

  • 集成 Yjs。
    • 



Convex：


    

  • 实时数据库 + 同步引擎。
    • 

  • 全栈方案。
    • 



Replicache：


    

  • 同步引擎。
    • 

  • 后端无关。
    • 



权衡：


    

  • PaaS 简化开发。
    • 

  • 但成本随规模增长。
    • 

  • 存在供应商锁定。
    • 



成本分析
自建 WebSocket 集群：


    

  • 百万并发约 $5k-20k/月（服务器 + Redis + 带宽）。
    • 

  • 工程师时间成本大。
    • 



Cloudflare Durable Objects：


    

  • 按消息计费。
    • 

  • 根据实际流量估算。
    • 



Liveblocks（托管服务）：


    

  • 按月活用户计费。
    • 

  • 约 $30-200 每千月活。
    • 



Pusher / Ably：


    

  • 按消息计费。
    • 

  • 约 $50-500 每百万条消息。
    • 



可靠性保障
服务器崩溃恢复：


    

  • 持久状态存储在数据库中。
    • 

  • 客户端重连到其他服务器。
    • 

  • 从最后已知状态恢复。
    • 



网络分区：


    

  • 部分用户断连。
    • 

  • 指数退避重连。
    • 



背压处理：


    

  • 慢客户端 → 丢弃消息或关闭连接。
    • 

  • 不能无限缓冲。
    • 



监控指标
关键指标：


    

  • 并发连接数。
    • 

  • 消息吞吐率。
    • 

  • 延迟（服务器到客户端往返时间）。
    • 

  • 错误率。
    • 

  • 重连率。
    • 



工具：


    

  • Prometheus + Grafana。
    • 

  • Datadog。
    • 

  • 自建仪表盘。
    • 



反模式
1. 单服务器硬撑：


    

  • 遇到性能瓶颈。
    • 



2. 不用消息中间件：


    

  • 跨服务器消息无法路由。
    • 



3. 不处理背压：


    

  • 慢客户端占满服务器资源。
    • 



4. 不做监控：


    

  • 故障无法及时发现。
    • 



5. 单个房间订阅过多服务器：


    

  • Redis 过载。
    • 



6. 持久状态只存内存：


    

  • 服务器崩溃即丢失数据。
    • 



实战建议
1. 从简单开始：


    

  • 单服务器起步，需要时再扩展为集群。
    • 



2. 用 PaaS 快速启动：


    

  • Liveblocks / PartyKit。
    • 

  • 成本增长后再考虑自建。
    • 



3. 全球部署选边缘方案：


    

  • Cloudflare Durable Objects 提供全球低延迟。
    • 



4. 尽早建立监控：


    

  • 关注延迟指标。
    • 



5. 做负载测试：


    

  • 模拟万级并发。
    • 

  • 找到瓶颈所在。
    • 



6. 为崩溃做好预案：


    

  • 持久化状态。
    • 

  • 完善重连逻辑。
    • 



小结
实时服务器扩展远比无状态 HTTP 困难——连接有状态、状态存于进程内存、水平扩展需要消息中间件。单服务器支撑 5-10 万 WebSocket 连接，瓶颈在 CPU、内存和网络。水平扩展通过 N 台服务器 + 负载均衡 + 消息中间件实现跨服务器路由。房间架构是核心模式——每个协作会话一个房间，服务器订阅 Redis 频道，消息发布后所有订阅者转发给本地客户端。消息中间件选择：Redis 发布/订阅最常用（即发即忘）、Kafka 支持回放（吞吐高但复杂）、NATS 轻量快速。连接状态存储策略：热数据用内存 + Redis 备份，持久数据用数据库。边缘方案（Cloudflare Durable Objects）提供每房间全球唯一实例、自动就近迁移和强一致性。PaaS 平台（Liveblocks、PartyKit、Pusher/Ably）简化开发但成本随规模增长。生产环境必须关注：粘性会话、持久化、重连、心跳、监控和负载测试。
