CRDT 基础

核心概念

CRDT（Conflict-free Replicated Data Types，无冲突复制数据类型）是分布式系统的数学结构——保证多个副本上的并发编辑能够自动合并收敛到相同状态，无需服务器协调。这使 P2P 协作应用和离线优先同步成为可能。Marc Shapiro 等人于 2011 年的论文系统化了 CRDT 理论。现代 Web 应用（Figma、Linear、Liveblocks）广泛采用 CRDT。两大流派包括：基于状态的 CvRDT 合并整体状态、基于操作的 CmRDT 合并操作序列。常见类型包括 G-Counter、PN-Counter、LWW-Register、OR-Set 和序列类型（文本）。本节介绍 CRDT 的数学概念、各类型工作原理、CRDT 与 OT 的对比以及局限性。

CRDT 类型 适用场景 复杂度
G-Counter 只增计数器 低
PN-Counter 可增可减计数器 低
LWW-Register 最后写入胜出的值 低
MV-Register 多值寄存器 中
OR-Set 观察删除集合 中
RGA / Yata 序列（文本编辑） 高
Y.Map / Y.Array 映射/数组（Yjs） 高

CRDT 核心特性

最终一致性：

  • 所有副本收到相同的操作集合 → 最终收敛。
  • 不要求操作有序。
  • 不要求协调同步。

数学保证：

  • 交换律（操作顺序不影响结果）。
  • 结合律。
  • 幂等性（同一操作多次应用结果相同）。

这是 P2P 可能的基础——任意副本都可以传播更新，最终所有副本状态相同。

基于状态的 CRDT（CvRDT）

收敛复制数据类型：

  • 每个副本维护本地状态。
  • 周期性地与其他副本共享完整状态。
  • 合并函数结合两个状态。

属性要求：

  • 幂等性：merge(s, s) = s。
  • 交换性：merge(a, b) = merge(b, a)。
  • 结合性：merge(merge(a, b), c) = merge(a, merge(b, c))。
  • 形成半格结构。

优点：

  • 健壮——可容忍消息丢失或乱序。
  • 最终一定收敛。

缺点：

  • 传输完整状态开销大。

G-Counter 示例：

// 每个节点维护计数向量
const node1 = { node1: 5, node2: 3 };
const node2 = { node1: 2, node2: 4 };

// 合并 = 每键取最大值
function merge(a, b) {
  const result = {};
  for (const key of new Set([...Object.keys(a), ...Object.keys(b)])) {
    result[key] = Math.max(a[key] || 0, b[key] || 0);
  }
  return result;
}

// 求和 = 总计数值
function value(state) {
  return Object.values(state).reduce((a, b) => a + b, 0);
}

基于操作的 CRDT（CmRDT）

交换复制数据类型：

  • 广播操作而非状态。
  • 每个副本应用收到的操作。
  • 需要可靠广播（不丢消息）。

属性要求：

  • 操作必须在因果交付后满足交换性。

优点：

  • 消息体积小（仅发送操作）。

缺点：

  • 需要可靠广播机制。
  • 需要因果有序传输。

示例：

// 广播操作
{ type: 'increment', node: 'node1' }

// 在每个副本上应用
function apply(state, op) {
  if (op.type === 'increment') {
    state[op.node] = (state[op.node] || 0) + 1;
  }
}

G-Counter（只增计数器）

仅支持增加的计数器。

状态结构：

  • Map<NodeID, count> 映射表。

操作：

  • Increment：增加本节点的计数值。

合并策略：

  • 每个键取最大值。

值计算：

  • 所有计数值求和。

适用场景：

  • 点赞计数。
  • 访问计数。

PN-Counter（正负计数器）

支持增加和减少的计数器。

状态结构：

  • 两个 G-Counter（正向 + 负向）。

操作：

  • Increment：增加正向计数器。
  • Decrement：增加负向计数器。

值计算：

  • 正向总和减去负向总和。

适用场景：

  • 库存数量。
  • 分数统计。

LWW-Register（最后写入胜出）

带时间戳的单值。

状态结构：

  • (value, timestamp, replicaId) 三元组。

合并策略：

  • 时间戳更大的胜出。
  • 时间戳相同时按副本 ID 比较决胜。

优点：

  • 实现简单。

缺点：

  • 可能丢失更新（并发写入时一方静默丢失）。

适用场景：

  • 非关键的并发写入场景。
  • 用户配置设置。

MV-Register（多值寄存器）

追踪并发写入：

  • 不会静默丢失数据。
  • 返回所有并发写入的值。
  • 由应用层决定如何解决。

适用场景：

  • 需要展示冲突界面的文档标题。

OR-Set（观察删除集合）

支持添加和删除的集合。

朴素方案的问题：

  • 简单的添加/删除操作在并发时会产生歧义。

OR-Set 方案：

  • 每次添加操作附带唯一标识符。
  • 删除操作删除特定的添加标记（仅删除已观察到的）。
  • 解决添加与删除的并发冲突。

状态结构：

{
  added: Map<element, Set<tag>>,
  removed: Set<tag>
}

元素存在于集合中的条件：有添加标记且未被删除。

适用场景：

  • 多用户标签列表。
  • 群组成员管理。

序列 CRDT

最具挑战性——顺序对序列（文本）至关重要。

主要方案：

1. RGA（可复制增长数组）：

  • 每个字符有唯一 ID 和父节点引用。
  • 树形结构组织。

2. Yata（Yjs 采用）：

  • 链表结构存储元素。
  • 每个元素记录左右邻居作为原点。
  • 通过原点比较解决冲突。

3. Logoot / LSEQ：

  • 每个位置分配稠密的唯一标识符。
  • 不需要父节点引用。

应用项目：

  • Yjs（采用 Yata）。
  • Automerge（采用 RGA）。
  • Loro。

CRDT 与 OT 对比

OT（操作变换）：

  • 服务器协调操作。
  • 根据并发情况变换操作。
  • Google Docs、Etherpad 采用。

CRDT：

  • 数学保证收敛。
  • 不需要服务器协调。
  • 天然支持 P2P。

对比总结：

维度 OT CRDT
服务器 必需 可选
复杂度所在 服务器逻辑复杂 数据结构复杂
性能 快 较慢（需追踪历史）
内存占用 小 大（需追踪墓碑）
P2P 支持 原生不支持 原生支持
实际案例 Google Docs Figma、Linear、Notion 
CRDT 的局限性
1. 内存开销：


    

  • 需追踪墓碑（已删除元素的标记）。
    • 

  • 向量时钟。
    • 

  • 长期运行的文档会持续增长。
    • 



2. 垃圾回收：


    

  • Yjs、Automerge 提供 GC 策略。
    • 



3. 序列并非完美：


    

  • 极端并发编辑可能产生意外的顺序。
    • 

  • 但 99% 的场景用户可接受。
    • 



4. 数学收敛 ≠ 用户体验最优：


    

  • 收敛后的状态可能不符合用户预期。
    • 

  • 人工冲突界面仍有价值。
    • 



CRDT 库
Yjs（主流选择）：


    

  • 高性能。
    • 

  • 提供 Y.Text、Y.Map、Y.Array、Y.XmlFragment。
    • 

  • 被 Liveblocks、JupyterLab、Tiptap、HedgeDoc 使用。
    • 



Automerge：


    

  • 函数式/不可变 API。
    • 

  • 类 JSON 的接口设计。
    • 



Loro（2024 年新项目）：


    

  • Rust + JS 绑定。
    • 

  • 性能极高。
    • 



何时选择 CRDT
应该用：


    

  • 实时协作编辑。
    • 

  • 离线优先同步。
    • 

  • 需要 P2P 支持。
    • 

  • 不想承担服务器协调的复杂性。
    • 



不应使用：


    

  • 简单的单写入者数据。
    • 

  • 严格顺序要求的关键系统（如金融交易）。
    • 

  • 内存资源极度受限的环境。
    • 



何时选择 OT
应该用：


    

  • 已有中心服务器架构。
    • 

  • 内存极度受限。
    • 

  • 希望客户端逻辑极简。
    • 



不应使用：


    

  • 需要 P2P 支持。
    • 

  • 不想承担服务器复杂性。
    • 

  • 现代技术栈（CRDT 更主流）。
    • 



因果顺序
基于操作的 CRDT 需要：


    

  • 操作 A 因果先于 B → A 必须先于 B 被应用。
    • 



实现方式：


    

  • 向量时钟。
    • 

  • 逻辑时钟（Lamport 时间戳）。
    • 



Yjs 的方案：


    

  • 每个操作有客户端 ID + 顺序时钟。
    • 

  • 追踪每个客户端已应用的操作。
    • 



性能特征
Yjs 基准测试：


    

  • 10 万字符文档编辑流畅。
    • 

  • 百万字符可行。
    • 

  • 十亿字符过大。
    • 



优化手段：


    

  • 垃圾回收。
    • 

  • 紧凑表示。
    • 

  • 懒加载。
    • 



反模式
1. 朴素的集合添加/删除：


    

  • 并发时会丢失数据。
    • 

  • 应使用 OR-Set。
    • 



2. 关键数据使用朴素 LWW：


    

  • 会丢失更新。
    • 

  • 应使用 MV-Register 或自定义合并逻辑。
    • 



3. 自己实现序列 CRDT：


    

  • 极其困难。
    • 

  • 应使用 Yjs 或 Automerge。
    • 



4. 不做垃圾回收：


    

  • 内存持续增长。
    • 



5. 所有数据都用 CRDT：


    

  • 开销过大。
    • 

  • 简单数据用简单同步即可。
    • 



实战建议
1. 首选 Yjs：


    

  • 主流且经过充分测试。
    • 



2. 为数据选择合适的 CRDT 类型：


    

  • 计数器用 Counter。
    • 

  • 标签用 Set。
    • 

  • 文本用 Sequence。
    • 



3. 制定 GC 策略：


    

  • 定期压缩。
    • 



4. 桥接到 UI 框架：


    

  • y-react、y-vue 等绑定库。
    • 



5. 监控内存：


    

  • 关注 Yjs 文档大小。
    • 



6. 规划持久化方案：


    

  • IndexedDB 本地存储 + 服务器备份。
    • 



小结
CRDT 是分布式系统的数学结构，保证多个副本上的并发编辑能够自动合并收敛，无需服务器协调——是 P2P、离线优先和协作应用的关键技术。核心特性包括最终一致性、交换性、结合性和幂等性。基于状态的 CvRDT 合并完整状态，基于操作的 CmRDT 广播操作（需可靠传输和因果有序）。常见类型包括：G-Counter（只增计数器）、PN-Counter（可增可减）、LWW-Register（最后写入胜出，简单但会丢失更新）、MV-Register（保留多值，不丢失并发数据）、OR-Set（观察删除集合，解决添加/删除并发冲突）、序列 CRDT（RGA 树结构用于 Automerge，Yata 链表用于 Yjs）。CRDT 与 OT 相比，OT 需服务器变换操作（Google Docs 方案），CRDT 通过数据结构保证收敛，天然支持 P2P。局限性包括内存开销（墓碑、向量时钟）、垃圾回收需求、序列极端情况可能不符合预期。主流库包括 Yjs（高性能，广泛采用）、Automerge（函数式 API）、Loro（2024 年新项目，极快）。选择建议：实时协作、离线优先、P2P 场景首选 CRDT；已有中心服务器、内存极度受限可考虑 OT。
