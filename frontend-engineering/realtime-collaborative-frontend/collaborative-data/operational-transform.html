操作变换（OT）

核心概念

操作变换（Operational Transformation，简称 OT）由 Ellis 和 Gibbs 于 1989 年提出，是协作编辑领域的"另一条路"——通过服务器协调操作，将并发操作变换为可交换的形式。Google Docs（2006）和 Etherpad 是 OT 的经典实现。在 CRDT 出现之前，OT 是唯一可用于生产环境的协作编辑方案。OT 与 CRDT 的核心区别在于：OT 的服务器逻辑复杂但客户端简单，CRDT 的数据结构复杂但天然支持点对点（P2P）通信。现代应用（Figma、Notion、Linear、Liveblocks）大多采用 CRDT，但 Google Docs 仍在使用 OT，混合方案也存在。本节讲解 OT 算法原理、Google Docs 案例、与 CRDT 的对比，以及如何选择。

维度 OT CRDT
服务器 权威服务器 + 变换操作 可选 / 简单中继
客户端 发送操作，应用服务器返回的变换结果 直接应用 + 同步
内存 小（无墓碑） 大（追踪墓碑）
性能 快速收敛 较慢（保留历史）
数学证明 复杂且易出错 数学保证
P2P 支持 非原生 原生支持
代表实现 Google Docs、Etherpad Figma、Linear、Notion

OT 基本原理

核心思想：

  • 多个客户端各自生成操作（Operation）。
  • 服务器（或客户端）根据并发操作进行变换（Transform）。
  • 双方应用变换后的操作，最终收敛到相同状态。

文本编辑示例：

  • 初始文本："abcde"。
  • 用户 A 在位置 2 插入 'X' → "abXcde"。
  • 用户 B（并发）删除位置 1 → "acde"。
  • 按顺序应用（先 A 后 B）："abXcde" → 删除位置 1 → "aXcde" ✗ 不符预期。
  • 需要变换：B 的删除操作必须根据 A 的插入进行位置调整。
  • 变换后的 B：删除位置 1（无需偏移，因为 A 在该位置之后插入）。

OT 的任务：

  • 定义 transform(opA, opB) 函数。
  • 确保无论应用顺序如何，最终状态一致。

OT 算法流程

基于服务器模式（Google Docs 方案）：

  1. 客户端发送操作 + 基准版本号。
  2. 服务器将操作与基准版本之后的所有操作进行变换。
  3. 服务器应用操作并广播变换后的结果。
  4. 其他客户端将本地待确认操作与服务器操作进行变换。

难点：

  • 多个并发操作同时存在。
  • 操作类型多样（插入 / 删除 / 格式化）。
  • 数学证明正确性极为困难。

变换函数

文本插入的变换函数：

function transform(insertA, opB) {
  if (opB.type === 'insert') {
    if (opB.pos < insertA.pos) {
      // B 的插入在 A 之前 → A 右移
      return { ...insertA, pos: insertA.pos + opB.text.length };
    } else if (opB.pos > insertA.pos) {
      // B 的插入在 A 之后 → 无需调整
      return insertA;
    } else {
      // 同一位置 → 通过用户 ID 等规则打破平局
      return tiebreaker(insertA, opB);
    }
  }
  if (opB.type === 'delete') {
    if (opB.pos < insertA.pos) {
      // B 的删除在 A 之前 → A 左移
      return { ...insertA, pos: insertA.pos - opB.length };
    } else {
      // B 的删除在 A 之后 → 无需调整
      return insertA;
    }
  }
}

对称性：transform(B, A) 具有平行的对称逻辑。

OT 性质
TP1（收敛性质）：


    

  • 按不同顺序应用操作后，最终到达相同状态。
    • 



TP2（包含变换性质）：


    

  • 多个并发操作之间能正确变换。
    • 



许多 OT 系统无法完全满足 TP2：


    

  • 容易产生 Bug。
    • 

  • 部分情况下无法正确收敛。
    • 



解决方案：


    

  • 严格的服务器线性化排序（将操作线性化）。
    • 

  • 或使用更丰富的 OT 算法（如 Jupiter 算法）。
    • 



Google Docs 的 OT 实现
架构：


    

  • 服务器将所有操作线性化（分配序列号）。
    • 

  • 客户端发送操作 + 版本号。
    • 

  • 服务器将操作与该版本之后的所有操作进行变换。
    • 

  • 服务器广播新操作。
    • 



客户端维护：


    

  • 已应用的操作列表。
    • 

  • 待确认操作（已发送但未收到服务器确认）。
    • 

  • 收到服务器操作后，将待确认操作与其进行变换。
    • 



可靠性：


    

  • 服务器具有权威性。
    • 

  • 不支持 P2P。
    • 

  • 适用于大型文档。
    • 



Etherpad 的 OT 实现
开源协作编辑器。


使用变更集（Changeset）格式：


    

  • 基于差异（Diff）的表示方式。
    • 

  • 服务器变换变更集。
    • 



影响了：


    

  • 许多后续的 OT 系统。
    • 



OT 操作类型
文本编辑操作：


    

  • 插入（位置，文本内容）。
    • 

  • 删除（位置，长度）。
    • 

  • 格式化（位置，长度，属性）。
    • 



每种类型需要：


    

  • 与其他每种类型进行变换。
    • 

  • 共 N×N 个变换函数。
    • 



当增加以下操作时更加复杂：


    

  • 基于选区的操作。
    • 

  • 多光标操作。
    • 

  • 富文本格式操作。
    • 



为什么 OT 很难
1. 变换函数数量多：


    

  • 插入与插入、插入与删除、删除与删除、与格式化...
    • 

  • 大量边界情况。
    • 



2. 容易出 Bug：


    

  • 数学证明正确性极为困难。
    • 

  • 即使 Google Docs 早期也存在 Bug。
    • 



3. 依赖服务器：


    

  • 需要权威服务器。
    • 

  • 对 P2P 不友好。
    • 



4. 回放慢：


    

  • 通过重新应用操作来重建状态。
    • 

  • 大文档重建速度慢。
    • 



为什么 CRDT 成为主流
现代偏好转向 CRDT：


1. 数学证明更简单：


    

  • CRDT 的数据结构本身保证收敛。
    • 

  • 无需手动编写变换函数。
    • 



2. 天然支持 P2P：


    

  • 不需要服务器。
    • 

  • 对本地优先（Local-first）友好。
    • 



3. 库已成熟：


    

  • Yjs / Automerge 已达生产可用状态。
    • 



4. 性能已接近：


    

  • Yjs 基准测试性能接近 OT。
    • 

  • 内存开销对典型文档可接受。
    • 



何时仍使用 OT
Google Docs：


    

  • 历史遗留原因。
    • 

  • 迁移到 CRDT 是大规模工程。
    • 



ShareDB / OT.js：


    

  • npm 上的库仍在活跃维护。
    • 

  • 部分使用场景。
    • 



自定义服务器权威场景：


    

  • 有特殊需求时。
    • 



通常：


    

  • 新项目选 CRDT。
    • 

  • 不选 OT。
    • 



混合方案
部分应用：


    

  • 服务器线性化 + CRDT 结合。
    • 

  • 取两者之长。
    • 



Liveblocks（早期）：


    

  • 使用 CRDT 但保留服务器权威。
    • 



趋势：


    

  • 现代项目大多使用纯 CRDT。
    • 



实现库
ShareDB（npm）：


    

  • 基于 OT 的实时数据库。
    • 

  • 用于部分协作编辑器。
    • 



OT.js：


    

  • OT 原语工具。
    • 

  • 可基于其构建自定义方案。
    • 



与 CRDT 相比：


    

  • 使用量更少。
    • 

  • Yjs / Automerge 占据主导。
    • 



取舍总结
选择 OT 的场景：


    

  • 已有 OT 系统（历史遗留）。
    • 

  • 服务器必须是权威的。
    • 

  • 内存严格受限。
    • 

  • 严格排序至关重要。
    • 



选择 CRDT 的场景：


    

  • 新项目。
    • 

  • 实时协作编辑器。
    • 

  • 本地优先 / 离线优先。
    • 

  • 需要 P2P。
    • 

  • 希望数学证明更简单。
    • 



性能对比
OT：


    

  • 收敛更快（无历史记录）。
    • 

  • 内存占用小。
    • 



CRDT：


    

  • 内存占用大（墓碑、向量时钟）。
    • 

  • 更新较慢（追踪历史）。
    • 



实际场景：


    

  • 对典型文档大小，两者都实用。
    • 

  • 大文档下 CRDT 较慢。
    • 



现代趋势
大多数新协作工具：


    

  • 采用 Yjs / Automerge / Loro。
    • 

  • 不使用 OT。
    • 



Google Docs：


    

  • 仍使用 OT。
    • 

  • 属于历史遗留。
    • 



Notion / Linear / Figma：


    

  • 全部使用 CRDT。
    • 



反模式
1. 自行实现 OT：


    

  • 极难做对。
    • 

  • 应使用现有库。
    • 



2. 假设 OT 比 CRDT 简单：


    

  • 实际并非如此。
    • 



3. 用 OT 做 P2P：


    

  • 不适合。
    • 



4. 高估 OT 的内存优势：


    

  • 仅在内存极度受限时才值得。
    • 



5. 在纯服务器场景盲目选 CRDT：


    

  • 可能带来不必要的开销。
    • 



6. 不理解 CRDT 就自行实现：


    

  • 容易重新发明轮子并引入 Bug。
    • 



未来展望
OT 不会消失：


    

  • 现有系统将继续使用。
    • 



CRDT 已成主流：


    

  • 新项目默认选择。
    • 



混合方案可能：


    

  • 部分研究方向正在探索。
    • 



实战建议
1. 新项目选 CRDT：


    

  • Yjs 是主流选择。
    • 



2. 已有 OT 系统：


    

  • 非必要不重写。
    • 



3. 两者都要理解：


    

  • 做出知情的技术决策。
    • 



4. 测试边界情况：


    

  • 多用户并发编辑。
    • 

  • 网络分区。
    • 



5. 监控收敛状态：


    

  • 在生产环境中验证一致性。
    • 



小结
OT（操作变换）由 Ellis 和 Gibbs 于 1989 年提出，是协作编辑的"另一条路"——通过服务器协调操作，将并发操作变换为可交换形式。Google Docs（2006）和 Etherpad 是经典实现。OT 与 CRDT 的核心区别：OT 服务器逻辑复杂但客户端简单，CRDT 数据结构复杂但天然支持 P2P。OT 基本原理：多客户端各自生成操作，服务器（或客户端）对并发操作进行变换，双方应用变换后收敛到相同状态。变换函数处理插入与插入（位置偏移）、插入与删除（左右偏移）等情况，具有对称性。OT 性质包括 TP1（收敛性，不同顺序达到相同状态）和 TP2（包含变换，多并发正确变换），许多系统无法完全满足 TP2，通过严格服务器排序或 Jupiter 算法解决。Google Docs 架构：服务器线性化操作并分配序列号，客户端维护已应用和待确认操作。为什么 OT 难：变换函数多、易出 Bug、依赖服务器、大文档回放慢。为什么 CRDT 胜出：数学证明更简单、天然 P2P、库已成熟、性能接近。何时仍用 OT：Google Docs 遗留、ShareDB/OT.js 库、自定义服务器权威场景。混合方案：服务器线性化 + CRDT（Liveblocks 早期），趋势是纯 CRDT。实战建议：新项目选 CRDT（Yjs 主流）、已有 OT 不轻易重写、两者都要理解、测试边界情况、监控收敛。
