设计评审与交付

核心概念

设计评审与 Code Review 同源，都是上线前的把关闸门，检验需求满足度、规范一致性与技术可行性。评审分级实施（自查、同行、跨职能、领导、用户），方法上以 Nielsen 启发式走查与**设计批评（Design Critique）**为主——批评规则「聚焦目标、提问而非评判、具体而非抽象、建设性建议、区分优先级」中，提问代替断言能保留作者思考链、降低防御。设计 QA 是逐像素核对的最后防线。核心分工认知：机器审客观偏差（像素/对比度/ARIA），人审设计意图（是否符合用户需求），因此设计内审必须前置于 QA。

设计评审的目标

设计评审（Design Review）不是"评判设计好不好看"，而是系统性地检验设计方案是否满足用户需求、遵循设计规范、在技术上可行。它与代码世界的 Code Review 同源——都是「合并/上线前的把关闸门」，区别只在审查对象。本文讲设计评审的流程与方法；自动化视觉回归（Chromatic、Playwright 截图比对）、axe 无障碍 CI 等工程化手段见兄弟 hub ../../40_frontend-testing/ 与 ../../11_testing-quality-engineering/，无障碍审查标准见 ../../34_web-accessibility/。

flowchart LR
    A["用户需求是否满足"] --> B["设计规范是否遵循"]
    B --> C["交互逻辑是否完整"]
    C --> D["技术实现是否可行"]
    D --> E["无障碍是否达标"]

评审类型

类型 参与者 频率 目标
自查 设计师本人 每次提交前 基础质量保证
同行评审 设计团队 每周 一致性和创意反馈
跨职能评审 设计+开发+产品 每个 Sprint 可行性和需求对齐
领导评审 设计负责人 重大改版时 战略方向把控
用户评审 真实用户 每个版本 可用性验证

设计自查清单

检查维度 检查项
信息架构 页面层级清晰，导航路径合理
视觉一致性 使用 Design Token，无硬编码颜色/间距
交互完整性 所有状态已设计（空、加载、错误、成功）
边界情况 超长文本、空数据、大量数据
响应式 主要断点的布局已设计
无障碍 对比度达标，焦点顺序合理
文案 文字简洁准确，错误提示有指导性

评审方法

启发式走查

按照 Nielsen 十大启发式逐条检查：

启发式 检查问题
系统状态可见性 加载状态和操作结果是否有明确反馈？
系统与现实匹配 术语和图标是否符合用户心智模型？
用户控制与自由 是否提供撤销和返回的途径？
一致性与标准 同类操作的交互方式是否统一？
防错设计 危险操作是否有确认机制？
识别而非回忆 选项和操作是否可见，无需记忆？

设计批评（Design Critique）

规则 说明
聚焦目标 围绕设计目标讨论，而非个人偏好
提问而非评判 "这个间距的考虑是什么？" vs "间距太大了"
具体而非抽象 指出具体问题和位置
建设性建议 指出问题的同时提供改进方向
区分优先级 区分"必须修改"和"建议优化"

设计 QA 流程

设计 QA（Quality Assurance）在开发完成后，由设计师逐像素对比实现与设计稿的差异。

flowchart TD
    A["开发完成提测"] --> B["设计师打开页面"]
    B --> C["对比设计稿<br/>逐页面检查"]
    C --> D{"有偏差？"}
    D -->|是| E["记录 Bug<br/>标注截图+预期效果"]
    D -->|否| F["通过"]
    E --> G["开发修复"]
    G --> B

QA 检查矩阵

维度 具体检查项 允许偏差
间距 padding, margin, gap ≤ 2px
颜色 文字、背景、边框 必须使用 Token 值
字体 字号、字重、行高 必须精确
圆角 border-radius 必须精确
对齐 水平/垂直对齐 ≤ 1px
动画 时长、缓动曲线 视觉感知一致

反馈与迭代循环

flowchart TD
    A["收集反馈<br/>评审/测试/上线数据"] --> B["分类整理<br/>按严重程度排序"]
    B --> C["设计迭代<br/>修改方案"]
    C --> D["验证改进<br/>A/B 测试或可用性测试"]
    D --> A
反馈来源 反馈类型 响应方式
设计评审 设计规范偏差 当前版本修复
用户测试 可用性问题 优先级排序后迭代
上线数据 转化率/跳出率异常 数据分析后假设验证
客户反馈 功能需求/体验投诉 纳入需求池评估

为什么「提问而非评判」能产出更好的设计

设计批评（Design Critique）最反直觉的一条规则是「用提问代替断言」（"这个间距的考虑是什么？" 而非 "间距太大了"）。这不是客套，而是认知机制：

  • 保留作者的思考链：断言式批评（"这里不对"）直接给结论，剥夺了设计师解释取舍的机会——很多「看起来奇怪」的决策背后有真实约束（如适配超长文案）。提问先暴露约束，再共同判断。
  • 对事不对人，降低防御：被评判时人会本能防御、固守原案；被提问时大脑进入解释模式，更愿协作修改。这与 Code Review 里「评论代码而非作者」是同一条原则（见 ../../11_testing-quality-engineering/）。
  • 区分「必须改」与「建议优化」：批评必须分级，否则设计师无法判断哪些是阻塞项。这对应可用性测试发现分级 P0~P3（见 UX 流程）。

设计 QA 与自动化的分工：人审「意图」，机器审「偏差」

设计 QA 逐像素对比是质量最后防线，但「全靠人手抄对照」既慢又易漏。2025 年的合理分工是：

检查类型 谁来做 工具
像素/间距偏差回归 机器 Chromatic / Playwright 视觉回归截图比对
对比度、ARIA、焦点顺序 机器为主 axe-core / axe DevTools，可入 CI
交互状态是否齐全（空/载/错/禁） 人 对照状态矩阵手动走查
「这符合用户意图吗」 人 启发式走查、用户测试

关键认知：自动化能抓「实现 ≠ 设计稿」的客观偏差，但抓不到「设计稿本身就错了」的意图缺陷——后者只能靠人对照规格判断。这也是为什么设计内审（堵意图）必须前置于 QA（堵偏差），呼应 设计开发协作 的衰减曲线。自动化视觉回归的搭建见 ../../40_frontend-testing/。

设计交付规范

交付物 格式 检查标准
设计稿 Figma 链接 所有页面和状态完整
交互说明 Figma 批注 每个交互都有文字描述
切图 SVG/PNG 命名规范，多倍图齐全
Token JSON/Figma Variables 与代码仓库同步
变更日志 文档 记录本版本的设计变更

小结

  • 设计评审的核心是检验需求满足度、规范一致性和技术可行性
  • 自查、同行评审和跨职能评审分别解决不同层面的质量问题
  • 设计批评应聚焦目标、提问而非评判、具体而非抽象
  • 设计 QA 是保证实现质量的最后防线，需要逐像素对比
  • 反馈循环是持续改进的引擎——收集 → 分类 → 迭代 → 验证
  • 「提问而非评判」保留作者思考链、降低防御；机器审客观偏差，人审设计意图
