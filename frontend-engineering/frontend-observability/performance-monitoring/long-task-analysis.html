长任务检测与主线程分析

核心概念

长任务（Long Task）是指占用主线程超过 50ms 的任务，它是导致页面卡顿、交互延迟和动画掉帧的根本原因。浏览器的渲染和事件处理都运行在主线程上，当一个 JavaScript 任务执行时间超过 50ms，它会阻塞后续的渲染帧（60fps 要求每帧 16.7ms）和用户交互事件的响应。Long Task API 提供了检测和量化主线程阻塞的原生能力。

Long Task API 采集
Long Task API 通过 PerformanceObserver 自动检测所有超过 50ms 的任务，并提供任务的来源归因信息：


interface LongTaskMetric {
  readonly name: string;
  readonly duration: number;
  readonly startTime: number;
  readonly attribution: ReadonlyArray<TaskAttribution>;
  readonly blockingDuration: number;
}

interface TaskAttribution {
  readonly name: string;
  readonly entryType: string;
  readonly containerType: 'window' | 'iframe' | 'embed' | 'object';
  readonly containerSrc?: string;
  readonly containerId?: string;
  readonly containerName?: string;
}

const createLongTaskMonitor = (
  onLongTask: (task: LongTaskMetric) => void,
  threshold: number = 50,
): PerformanceObserver => {
  const observer = new PerformanceObserver((list) => {
    list.getEntries().forEach((entry) => {
      if (entry.duration < threshold) return;

      const attribution =
        (
          entry as PerformanceEntry & {
            attribution?: ReadonlyArray<TaskAttribution>;
          }
        ).attribution ?? [];

      onLongTask({
        name: entry.name,
        duration: entry.duration,
        startTime: entry.startTime,
        attribution,
        blockingDuration: entry.duration - 50,
      });
    });
  });

  observer.observe({ type: 'longtask', buffered: true });
  return observer;
};
Long Task 的归因信息有限（只能指向 iframe 或 script 来源），更精确的调用栈分析需要借助 Performance.mark() 和 Performance.measure() 手动插桩：


interface InstrumentedTask {
  readonly name: string;
  readonly category: 'render' | 'data' | 'computation' | 'dom' | 'network';
  readonly duration: number;
  readonly metadata: Readonly<Record<string, string>>;
}

const measureTask = async <T>(
  name: string,
  category: InstrumentedTask['category'],
  fn: () => T | Promise<T>,
  metadata: Record<string, string> = {},
): Promise<T> => {
  const markStart = `${name}-start`;
  const markEnd = `${name}-end`;

  performance.mark(markStart);
  const result = await fn();
  performance.mark(markEnd);

  const measure = performance.measure(name, markStart, markEnd);

  if (measure.duration > 50) {
    reportLongTask({
      name,
      category,
      duration: measure.duration,
      metadata,
    });
  }

  performance.clearMarks(markStart);
  performance.clearMarks(markEnd);
  performance.clearMeasures(name);

  return result;
};
主线程分析与火焰图
深度主线程分析需要在运行时采集函数调用的耗时分布，生成类似 Chrome DevTools 的火焰图数据。虽然浏览器不暴露原生的函数级别 profiling API（Performance.profile 仍是实验性的），但可以通过采样和手动插桩相结合的方式获取近似结果：


interface FlameNode {
  readonly name: string;
  readonly startTime: number;
  readonly endTime: number;
  readonly children: ReadonlyArray<FlameNode>;
  readonly selfTime: number;
}

interface ProfileSession {
  readonly enter: (name: string) => void;
  readonly exit: () => void;
  readonly getFlameGraph: () => FlameNode;
}

const createProfileSession = (): ProfileSession => {
  const root: FlameNode & { children: Array<FlameNode> } = {
    name: 'root',
    startTime: performance.now(),
    endTime: 0,
    children: [],
    selfTime: 0,
  };
  const stack: Array<FlameNode & { children: Array<FlameNode> }> = [root];

  const enter = (name: string): void => {
    const node: FlameNode & { children: Array<FlameNode> } = {
      name,
      startTime: performance.now(),
      endTime: 0,
      children: [],
      selfTime: 0,
    };
    stack[stack.length - 1].children.push(node);
    stack.push(node);
  };

  const exit = (): void => {
    if (stack.length <= 1) return;
    const node = stack.pop()!;
    (node as { endTime: number }).endTime = performance.now();
    const childTime = node.children.reduce((sum, c) => sum + (c.endTime - c.startTime), 0);
    (node as { selfTime: number }).selfTime = node.endTime - node.startTime - childTime;
  };

  const getFlameGraph = (): FlameNode => {
    (root as { endTime: number }).endTime = performance.now();
    return root;
  };

  return { enter, exit, getFlameGraph };
};
任务拆分与调度优化
识别出长任务后，下一步是将其拆分为多个小任务，让浏览器有机会在任务间隙处理渲染和用户事件。现代浏览器提供了多种任务调度 API：


type TaskPriority = 'user-blocking' | 'user-visible' | 'background';

interface SchedulerAPI {
  readonly postTask: <T>(
    callback: () => T,
    options?: { readonly priority?: TaskPriority; readonly delay?: number },
  ) => Promise<T>;
  readonly yield: () => Promise<void>;
}

const scheduleTask = async <T>(callback: () => T, priority: TaskPriority = 'user-visible'): Promise<T> => {
  if ('scheduler' in globalThis) {
    const scheduler = (globalThis as unknown as { scheduler: SchedulerAPI }).scheduler;
    return scheduler.postTask(callback, { priority });
  }

  return new Promise<T>((resolve) => {
    if (priority === 'background') {
      requestIdleCallback(() => resolve(callback()));
    } else {
      setTimeout(() => resolve(callback()), 0);
    }
  });
};

const chunkWork = async <T, R>(
  items: ReadonlyArray<T>,
  processor: (item: T) => R,
  chunkSize: number = 5,
  priority: TaskPriority = 'user-visible',
): Promise<ReadonlyArray<R>> => {
  const results: Array<R> = [];

  for (let i = 0; i < items.length; i += chunkSize) {
    const chunk = items.slice(i, i + chunkSize);
    const chunkResults = await scheduleTask(() => chunk.map(processor), priority);
    results.push(...chunkResults);
  }

  return results;
};

TBT 监控与告警
TBT（Total Blocking Time）是 Long Task 的聚合指标，衡量 FCP 到 TTI 之间所有长任务超出 50ms 部分的总和。它是 Lighthouse 中权重最高的性能指标之一：


interface TBTMetric {
  readonly totalBlockingTime: number;
  readonly longTaskCount: number;
  readonly worstTask: { readonly name: string; readonly duration: number };
  readonly topBlockers: ReadonlyArray<{ readonly source: string; readonly blockingTime: number }>;
}

const calculateTBT = (longTasks: ReadonlyArray<LongTaskMetric>, fcpTime: number, ttiTime: number): TBTMetric => {
  const tasksInRange = longTasks.filter(
    (task) => task.startTime >= fcpTime && task.startTime + task.duration <= ttiTime,
  );

  let totalBlockingTime = 0;
  let worstTask = { name: '', duration: 0 };
  const blockerMap = new Map<string, number>();

  tasksInRange.forEach((task) => {
    const blockingTime = Math.max(0, task.duration - 50);
    totalBlockingTime += blockingTime;

    if (task.duration > worstTask.duration) {
      worstTask = { name: task.name, duration: task.duration };
    }

    const source = task.attribution[0]?.containerSrc ?? task.name;
    blockerMap.set(source, (blockerMap.get(source) ?? 0) + blockingTime);
  });

  const topBlockers = Array.from(blockerMap.entries())
    .map(([source, blockingTime]) => ({ source, blockingTime }))
    .sort((a, b) => b.blockingTime - a.blockingTime)
    .slice(0, 5);

  return {
    totalBlockingTime,
    longTaskCount: tasksInRange.length,
    worstTask,
    topBlockers,
  };
};
小结
    

  • 长任务（> 50ms）是导致页面卡顿和 INP 恶化的根本原因，Long Task API 提供原生检测能力
    • 

  • Long Task 归因信息有限，精确的函数级分析需要通过 Performance.measure() 手动插桩
    • 

  • 任务拆分通过 scheduler.postTask / scheduler.yield / requestIdleCallback 让出主线程
    • 

  • TBT 是 FCP 到 TTI 之间所有长任务超出 50ms 部分的总和，是 Lighthouse 权重最高的指标
    • 

  • 优先使用 scheduler.yield()（Chrome 115+）优化 INP，降级方案使用 setTimeout(0)
    • 

  • 长任务监控应与 INP 指标联动，形成「检测 → 归因 → 拆分 → 验证」的闭环优化流程
