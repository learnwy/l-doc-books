错误聚合与降噪

核心概念

错误聚合（Error Aggregation）是将海量原始错误事件归并为可管理的 Issue 的过程。一个生产环境中的前端应用每天可能产生数十万条错误事件，但其中大部分是同一个 Bug 的重复触发。错误聚合的目标是将这些重复事件合并为一个 Issue，并统计其影响范围（受影响用户数、发生频率、首次/最后出现时间）。同时，降噪机制过滤掉浏览器扩展、爬虫脚本和已知无害错误等噪音，确保告警系统只关注真正需要处理的问题。

错误指纹算法
错误指纹（Fingerprint）是将错误事件映射为唯一标识符的过程，相同指纹的事件被视为同一个 Issue。好的指纹算法需要平衡两个目标：同一 Bug 的不同触发应该生成相同指纹（不过度拆分），不同 Bug 应该生成不同指纹（不错误合并）。


最常见的指纹方式是基于堆栈帧：提取堆栈中每一帧的文件名、函数名和行号，过滤掉框架内部帧（如 React 的调度帧、Zone.js 的包装帧），对剩余帧生成哈希值。Sentry 的默认分组策略还会去除帧中的动态部分（如查询参数、哈希值和构建版本号）。


interface ErrorEvent {
  readonly type: string;
  readonly message: string;
  readonly stack: ReadonlyArray<StackFrame>;
  readonly url: string;
  readonly userAgent: string;
  readonly timestamp: number;
  readonly userId?: string;
  readonly release?: string;
  readonly tags: ReadonlyMap<string, string>;
}

interface StackFrame {
  readonly filename: string;
  readonly function: string;
  readonly lineno: number;
  readonly colno: number;
  readonly inApp: boolean;
}

interface FingerprintConfig {
  readonly strategy: 'stack' | 'message' | 'component' | 'hybrid';
  readonly maxFrames: number;
  readonly excludePatterns: ReadonlyArray<RegExp>;
  readonly normalizeMessages: boolean;
}

function computeFingerprint(event: ErrorEvent, config: FingerprintConfig): string {
  switch (config.strategy) {
    case 'stack':
      return stackFingerprint(event.stack, config);
    case 'message':
      return messageFingerprint(event.type, event.message, config);
    case 'hybrid':
      return hybridFingerprint(event, config);
    default:
      return stackFingerprint(event.stack, config);
  }
}

function stackFingerprint(stack: ReadonlyArray<StackFrame>, config: FingerprintConfig): string {
  const significantFrames = stack
    .filter((frame) => frame.inApp)
    .filter((frame) => !config.excludePatterns.some((p) => p.test(frame.filename)))
    .slice(0, config.maxFrames);

  const parts = significantFrames.map(
    (frame) => `${normalizeFilename(frame.filename)}:${frame.function}:${frame.lineno}`,
  );

  return hashString(parts.join('|'));
}

function messageFingerprint(type: string, message: string, config: FingerprintConfig): string {
  const normalized = config.normalizeMessages ? normalizeMessage(message) : message;
  return hashString(`${type}:${normalized}`);
}

function normalizeMessage(message: string): string {
  return message
    .replace(/\b\d+\b/g, '<NUM>')
    .replace(/https?:\/\/[^\s]+/g, '<URL>')
    .replace(/'[^']*'/g, "'<STR>'")
    .replace(/"[^"]*"/g, '"<STR>"');
}

function normalizeFilename(filename: string): string {
  return filename
    .replace(/[?#].*$/, '')
    .replace(/\.[a-f0-9]{8,}\.(js|css)/g, '.<HASH>.$1')
    .replace(/\/\d+\.\w+\.js/g, '/<CHUNK>.js');
}

function hybridFingerprint(event: ErrorEvent, config: FingerprintConfig): string {
  const stackFp = event.stack.length > 0 ? stackFingerprint(event.stack, config) : '';
  const msgFp = messageFingerprint(event.type, event.message, config);
  return hashString(`${stackFp}:${msgFp}`);
}

function hashString(input: string): string {
  let hash = 0;
  for (let i = 0; i < input.length; i++) {
    const char = input.charCodeAt(i);
    hash = (hash << 5) - hash + char;
    hash = hash & hash;
  }
  return Math.abs(hash).toString(36);
}
降噪过滤策略
生产环境的错误流中包含大量噪音：浏览器扩展注入的脚本错误、爬虫触发的兼容性问题、用户网络波动导致的资源加载失败等。这些错误虽然真实发生，但不属于应用自身的 Bug，不应占据开发者的注意力。


降噪过滤分为静态规则和动态规则两类。静态规则在 SDK 初始化时配置，包括：忽略特定错误消息（如 ResizeObserver loop limit exceeded）、过滤来自第三方脚本的错误（通过文件路径匹配）、排除特定浏览器版本（如已不支持的 IE 11）。动态规则基于统计分析：如果某个错误在短时间内突增但不影响业务指标（如点击率、转化率），可能是外部因素导致的噪音。


interface NoiseFilter {
  readonly name: string;
  readonly type: 'static' | 'dynamic';
  readonly check: (event: ErrorEvent) => boolean;
}

function createDefaultFilters(): ReadonlyArray<NoiseFilter> {
  return [
    {
      name: 'browser-extension',
      type: 'static',
      check: (event) => event.stack.some((f) => /^(chrome|moz|safari)-extension:\/\//.test(f.filename)),
    },
    {
      name: 'known-benign',
      type: 'static',
      check: (event) => {
        const benignMessages = [
          'ResizeObserver loop limit exceeded',
          'ResizeObserver loop completed with undelivered notifications',
          'Non-Error promise rejection captured',
          'Loading chunk',
          'Loading CSS chunk',
        ];
        return benignMessages.some((msg) => event.message.includes(msg));
      },
    },
    {
      name: 'crawler-bot',
      type: 'static',
      check: (event) => /bot|crawl|spider|slurp|Baiduspider|Googlebot/i.test(event.userAgent),
    },
    {
      name: 'third-party-script',
      type: 'static',
      check: (event) => {
        const thirdPartyDomains = ['googletagmanager.com', 'facebook.net', 'doubleclick.net', 'hotjar.com'];
        return event.stack.every((f) => thirdPartyDomains.some((d) => f.filename.includes(d)));
      },
    },
  ];
}

告警策略设计
告警是错误聚合的最终输出环节。好的告警策略应该满足：关键错误快速触达、非关键错误不打扰、新问题优先于已知问题。实践中常见的告警策略包括：新 Issue 创建时立即告警、Issue 频率突增时告警、影响用户数超过阈值时告警。


interface AlertRule {
  readonly name: string;
  readonly condition: AlertCondition;
  readonly channels: ReadonlyArray<AlertChannel>;
  readonly cooldown: number;
  readonly severity: 'critical' | 'warning' | 'info';
}

interface AlertCondition {
  readonly type: 'new_issue' | 'frequency_spike' | 'user_impact' | 'regression';
  readonly threshold?: number;
  readonly window?: number;
  readonly filter?: Record<string, string>;
}

type AlertChannel = 'slack' | 'email' | 'pagerduty' | 'webhook' | 'dingtalk';

interface IssueStats {
  readonly issueId: string;
  readonly fingerprint: string;
  readonly firstSeen: number;
  readonly lastSeen: number;
  readonly eventCount: number;
  readonly userCount: number;
  readonly isRegression: boolean;
  readonly trend: 'increasing' | 'stable' | 'decreasing';
}

function shouldAlert(issue: IssueStats, rule: AlertRule, now: number): boolean {
  switch (rule.condition.type) {
    case 'new_issue':
      return now - issue.firstSeen < 60_000;
    case 'frequency_spike':
      return issue.trend === 'increasing' && issue.eventCount > (rule.condition.threshold ?? 100);
    case 'user_impact':
      return issue.userCount > (rule.condition.threshold ?? 50);
    case 'regression':
      return issue.isRegression;
    default:
      return false;
  }
}
告警风暴（Alert Fatigue）是告警系统的头号敌人。当大量告警同时触发时，开发者会产生"告警疲劳"并忽略所有告警。防止告警风暴的方法包括：设置冷却时间（同一 Issue 在 N 分钟内只告警一次）、告警聚合（多个 Issue 合并为一条摘要通知）和升级策略（先 Slack 通知，30 分钟未处理再电话告警）。


小结
    

  • 错误指纹通过堆栈帧、错误消息或混合策略将重复事件归并为 Issue
    • 

  • 指纹归一化需要去除动态内容（哈希值、数字、URL）以避免过度拆分
    • 

  • 降噪过滤剔除浏览器扩展、爬虫、已知无害错误等噪音，通常可减少 40-60% 事件量
    • 

  • 告警策略应区分新 Issue、频率突增、用户影响和回归四种场景
    • 

  • 告警冷却、聚合和升级策略是防止告警风暴的关键
    • 

  • SDK 端过滤减少上报量，服务端聚合降低存储和分析成本
    • 

  • 错误聚合质量直接影响团队的错误响应效率和修复速度
    •
