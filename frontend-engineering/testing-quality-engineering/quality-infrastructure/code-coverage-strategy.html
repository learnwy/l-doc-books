覆盖率策略

核心概念

代码覆盖率（Code Coverage）衡量测试执行了多少比例的代码。它是质量度量的重要指标，但不是唯一指标。高覆盖率不等于高质量测试，但低覆盖率几乎一定意味着测试不足。制定合理的覆盖率策略，需要理解各种覆盖率维度的含义、设定务实的目标，并避免覆盖率驱动的反模式。

覆盖率维度示例
function calculateDiscount(amount: number, memberLevel: 'gold' | 'silver' | 'regular'): number {
  if (amount <= 0) {
    return 0;
  }

  let rate = 0;

  switch (memberLevel) {
    case 'gold':
      rate = 0.2;
      break;
    case 'silver':
      rate = 0.1;
      break;
    case 'regular':
      rate = 0;
      break;
  }

  if (amount > 1000) {
    rate += 0.05;
  }

  return Math.round(amount * rate * 100) / 100;
}
import { describe, it, expect } from 'vitest';

describe('calculateDiscount 覆盖率分析', () => {
  it('金牌会员大额订单', () => {
    expect(calculateDiscount(2000, 'gold')).toBe(500);
  });
});
上面这个测试只覆盖了：


    

  • 行覆盖率：约 60%（未覆盖 amount <= 0、silver、regular 分支）
    • 

  • 分支覆盖率：约 33%（3 个 switch 分支只走了 1 个，2 个 if 只走了部分）
    • 

  • 函数覆盖率：100%（函数被调用了）
    • 



完整覆盖需要：


describe('calculateDiscount 完整覆盖', () => {
  it('金额为 0 返回 0', () => {
    expect(calculateDiscount(0, 'gold')).toBe(0);
  });

  it('负数金额返回 0', () => {
    expect(calculateDiscount(-100, 'gold')).toBe(0);
  });

  it('金牌会员', () => {
    expect(calculateDiscount(500, 'gold')).toBe(100);
  });

  it('银牌会员', () => {
    expect(calculateDiscount(500, 'silver')).toBe(50);
  });

  it('普通会员', () => {
    expect(calculateDiscount(500, 'regular')).toBe(0);
  });

  it('大额订单额外折扣', () => {
    expect(calculateDiscount(2000, 'silver')).toBe(300);
  });

  it('临界值 1000', () => {
    expect(calculateDiscount(1000, 'gold')).toBe(200);
  });

  it('超过 1000', () => {
    expect(calculateDiscount(1001, 'gold')).toBe(250.25);
  });
});

增量覆盖率
增量覆盖率只检查新增或修改的代码的覆盖率，比全量覆盖率更实用。


import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    coverage: {
      thresholds: {
        '100': true,
      },
    },
  },
});
Git 差异覆盖率脚本
import { execSync } from 'child_process';

function getChangedFiles(): string[] {
  const output = execSync('git diff --name-only HEAD~1 -- "*.ts" "*.tsx"', {
    encoding: 'utf-8',
  });
  return output.trim().split('\n').filter(Boolean);
}

function checkIncrementalCoverage(): void {
  const changedFiles = getChangedFiles();
  console.log(`检查 ${changedFiles.length} 个变更文件的覆盖率`);

  const coverageData = JSON.parse(execSync('cat coverage/coverage-summary.json', { encoding: 'utf-8' }));

  const failures: string[] = [];

  for (const file of changedFiles) {
    const fileCoverage = coverageData[file];
    if (!fileCoverage) continue;

    const linePct = fileCoverage.lines.pct;
    if (linePct < 80) {
      failures.push(`${file}: 行覆盖率 ${linePct}% (要求 ≥ 80%)`);
    }
  }

  if (failures.length > 0) {
    console.error('增量覆盖率不达标:');
    failures.forEach((f) => console.error(`  ❌ ${f}`));
    process.exit(1);
  }

  console.log('✅ 增量覆盖率检查通过');
}

checkIncrementalCoverage();
覆盖率陷阱
陷阱一：无效的 100% 覆盖
import { describe, it, expect } from 'vitest';

function divide(a: number, b: number): number {
  if (b === 0) throw new Error('除数不能为零');
  return a / b;
}

describe('无效的 100% 覆盖', () => {
  it('正常除法', () => {
    divide(10, 2);
  });

  it('除零', () => {
    try {
      divide(10, 0);
    } catch {}
  });
});
上面的测试达到 100% 覆盖率，但没有任何有意义的断言！正确写法：


describe('有效的覆盖', () => {
  it('正常除法应返回正确结果', () => {
    expect(divide(10, 2)).toBe(5);
    expect(divide(9, 3)).toBe(3);
  });

  it('除零应抛出异常', () => {
    expect(() => divide(10, 0)).toThrow('除数不能为零');
  });
});
陷阱二：为了覆盖率而测试
describe('仅为覆盖率而写的测试', () => {
  it('覆盖 getter', () => {
    const user = { name: 'Alice', age: 25 };
    expect(user.name).toBeDefined();
    expect(user.age).toBeDefined();
  });
});
这类测试不验证任何逻辑，只为提高数字。应关注行为而非行数。


陷阱三：排除难测代码
通过排除复杂代码来"提高"覆盖率是自欺欺人。难测代码往往更需要测试。

    echo "最低覆盖率: ${COVERAGE}%"

常见误区与纠正
误区一：100% 覆盖率是终极目标
100% 覆盖率的维护成本极高，且不意味着零 Bug。80% 是大多数项目的最佳平衡点。


误区二：覆盖率 = 测试质量
覆盖率只衡量"执行了什么代码"，不衡量"验证了什么行为"。无断言的测试可以达到高覆盖率但毫无价值。


误区三：全量覆盖率卡死 PR
全量覆盖率可能因历史遗留代码而阻止新功能合并。应使用增量覆盖率检查变更代码。


误区四：手动查看覆盖率报告
覆盖率检查应自动化集成到 CI，不依赖人工查看。


小结
覆盖率是测试效果的度量工具，而非目标本身。


核心要点回顾：


    

  • 四种覆盖率维度：行、分支、函数、语句
    • 

  • 分支覆盖率最有价值，能发现未测试的条件路径
    • 

  • 新项目起步 80% 行覆盖，核心逻辑 90%
    • 

  • 增量覆盖率聚焦变更代码，避免历史债务拖累
    • 

  • 排除类型定义、配置文件等无逻辑代码
    • 

  • 覆盖率陷阱：无断言测试、为覆盖率而测试、排除难测代码
    • 

  • 自动化集成到 CI，用 Codecov 追踪趋势
    • 

  • 质量优先于数量，有效断言比行覆盖率数字更重要
    •
