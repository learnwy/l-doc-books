Code Review 实践

Code Review 的价值

Code Review 不仅仅是"找 bug"——它是知识共享、架构守护和团队文化建设的综合实践。自动化工具能够发现格式问题和类型错误，但架构合理性、业务逻辑正确性和代码可维护性的判断，仍然需要人的参与。

架构层面
interface ArchitectureChecklist {
  items: string[];
}

const architectureChecklist: ArchitectureChecklist = {
  items: [
    '变更是否符合项目的目录约定？',
    '新模块的依赖方向是否正确？（features 不互相依赖）',
    '是否有可以复用的现有代码？避免重复实现',
    '新增依赖是否必要？包体积影响如何？',
    'API 设计是否向后兼容？',
  ],
};
代码层面




检查项
关注点





命名清晰度
变量名、函数名是否准确表达意图




函数复杂度
是否可以拆分为更小的函数




错误处理
边界情况和异常路径是否覆盖




类型安全
是否存在 any、类型断言是否合理




性能影响
是否有不必要的重渲染、大量计算




安全风险
XSS、敏感数据暴露、不安全的第三方依赖

GitHub Actions 自动化检查
name: PR Checks
on:
  pull_request:
    branches: [main, develop]

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm run typecheck
      - run: pnpm run lint
      - run: pnpm run test
      - run: pnpm run build

  bundle-size:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm run build
      - uses: andresz1/size-limit-action@v1
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}

Review 文化建设
Review 的沟通原则




原则
说明





对事不对人
Review 的是代码，不是写代码的人




提问而非指令
"这里是否考虑过边界情况？" > "这里写错了"




给出理由
不仅指出问题，还要解释为什么




区分严重程度
使用标签区分：blocker、suggestion、nit、question




肯定优秀之处
遇到好的实现主动肯定，鼓励正向行为





Review 评论标签
<!-- blocker: 必须修复才能合并 -->

[blocker] 这里的 API 调用没有错误处理，用户可能看到白屏。

<!-- suggestion: 建议优化，非阻塞 -->

[suggestion] 这个逻辑可以用 `Array.prototype.flatMap` 简化。

<!-- nit: 微小问题，不影响合并 -->

[nit] 变量名 `d` 建议改为 `data`，更具可读性。

<!-- question: 纯粹的疑问，寻求理解 -->

[question] 为什么这里选择了 useRef 而不是 useState？


Review 效率优化
控制 PR 大小
Stacked PRs
对于大型功能，使用 Stacked PRs 将一个大变更拆分为多个有序的小 PR：


main
 └── feature/user-auth-1-models       (PR #1: 数据模型)
      └── feature/user-auth-2-api     (PR #2: API 层)
           └── feature/user-auth-3-ui (PR #3: UI 层)
每个 PR 独立 Review、独立合并，大幅降低单次 Review 的认知负担。




小结
    

  • Code Review 是质量保障、知识共享、架构守护和文化建设的综合实践。
    • 

  • PR 模板和 Review 清单让 Review 过程更加结构化、可重复。
    • 

  • 自动化检查（CI、CODEOWNERS、Bundle Size）减少人工 Review 的负担。
    • 

  • 健康的 Review 文化强调"对事不对人"、给出理由、区分严重程度。
    • 

  • 控制 PR 大小（< 200 行最佳）是提升 Review 效率的关键策略。
