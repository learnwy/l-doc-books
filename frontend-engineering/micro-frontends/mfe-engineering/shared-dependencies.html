共享依赖管理

核心概念

共享依赖管理是微前端工程化的核心挑战之一。当多个子应用独立构建和部署时，它们各自打包的公共依赖（如 React、lodash、UI 组件库）会导致 bundle 冗余、版本冲突和运行时错误。合理的共享依赖策略需要在独立性和资源效率之间找到最佳平衡点。

External 化与 CDN 加载
External 化是最简单直接的共享策略：将公共依赖排除在 bundle 之外，通过 CDN 的 <script> 标签全局加载。所有子应用通过全局变量（如 window.React）访问共享依赖：


interface ExternalConfig {
  readonly name: string;
  readonly globalVar: string;
  readonly cdnUrl: string;
  readonly version: string;
  readonly integrity?: string;
}

const externals: ReadonlyArray<ExternalConfig> = [
  {
    name: 'react',
    globalVar: 'React',
    cdnUrl: 'https://cdn.example.com/react/18.3.1/umd/react.production.min.js',
    version: '18.3.1',
    integrity: 'sha384-xxxxx',
  },
  {
    name: 'react-dom',
    globalVar: 'ReactDOM',
    cdnUrl: 'https://cdn.example.com/react-dom/18.3.1/umd/react-dom.production.min.js',
    version: '18.3.1',
    integrity: 'sha384-xxxxx',
  },
];

const loadExternals = async (configs: ReadonlyArray<ExternalConfig>): Promise<void> => {
  const loadScript = (config: ExternalConfig): Promise<void> => {
    if ((window as Record<string, unknown>)[config.globalVar]) {
      return Promise.resolve();
    }

    return new Promise((resolve, reject) => {
      const script = document.createElement('script');
      script.src = config.cdnUrl;
      script.crossOrigin = 'anonymous';
      if (config.integrity) {
        script.integrity = config.integrity;
      }
      script.onload = () => resolve();
      script.onerror = () => reject(new Error(`Failed to load ${config.name}`));
      document.head.appendChild(script);
    });
  };

  for (const config of configs) {
    await loadScript(config);
  }
};
External 策略的问题在于所有子应用必须使用完全相同的版本，缺乏版本协商能力。当某个子应用需要升级 React 版本而其他应用尚未准备好时，就会陷入「木桶效应」。


依赖版本协商
高级的共享依赖管理需要支持版本协商——在满足所有消费者版本约束的前提下，选择最优的共享版本。这是 Module Federation 和 Import Map 方案的核心能力：


interface SemverRange {
  readonly raw: string;
  readonly major: number;
  readonly minor: number;
  readonly patch: number;
  readonly comparator: '^' | '~' | '>=' | '=' | '*';
}

interface VersionRequest {
  readonly consumer: string;
  readonly package: string;
  readonly range: SemverRange;
}

interface NegotiationResult {
  readonly package: string;
  readonly resolvedVersion: string;
  readonly satisfiedConsumers: ReadonlyArray<string>;
  readonly unsatisfiedConsumers: ReadonlyArray<string>;
  readonly strategy: 'shared' | 'duplicated';
}

const parseSemver = (range: string): SemverRange => {
  const match = range.match(/^([~^>=]*)(\d+)\.(\d+)\.(\d+)$/);
  if (!match) throw new Error(`Invalid semver range: ${range}`);
  return {
    raw: range,
    comparator: (match[1] || '^') as SemverRange['comparator'],
    major: parseInt(match[2], 10),
    minor: parseInt(match[3], 10),
    patch: parseInt(match[4], 10),
  };
};

const satisfies = (version: SemverRange, constraint: SemverRange): boolean => {
  switch (constraint.comparator) {
    case '=':
      return (
        version.major === constraint.major && version.minor === constraint.minor && version.patch === constraint.patch
      );
    case '^':
      return (
        version.major === constraint.major &&
        (version.minor > constraint.minor || (version.minor === constraint.minor && version.patch >= constraint.patch))
      );
    case '~':
      return (
        version.major === constraint.major && version.minor === constraint.minor && version.patch >= constraint.patch
      );
    case '>=':
      return (
        version.major > constraint.major ||
        (version.major === constraint.major && version.minor > constraint.minor) ||
        (version.major === constraint.major && version.minor === constraint.minor && version.patch >= constraint.patch)
      );
    default:
      return true;
  }
};

const negotiate = (
  requests: ReadonlyArray<VersionRequest>,
  availableVersions: ReadonlyArray<string>,
): NegotiationResult => {
  const packageName = requests[0].package;
  const available = availableVersions.map((v) => parseSemver(`=${v}`));

  for (const version of available.reverse()) {
    const satisfied = requests.filter((r) => satisfies(version, r.range));
    if (satisfied.length === requests.length) {
      return {
        package: packageName,
        resolvedVersion: `${version.major}.${version.minor}.${version.patch}`,
        satisfiedConsumers: requests.map((r) => r.consumer),
        unsatisfiedConsumers: [],
        strategy: 'shared',
      };
    }
  }

  return {
    package: packageName,
    resolvedVersion: availableVersions[availableVersions.length - 1],
    satisfiedConsumers: [],
    unsatisfiedConsumers: requests.map((r) => r.consumer),
    strategy: 'duplicated',
  };
};

依赖冲突检测与告警
在微前端运行时，依赖冲突可能导致隐蔽的运行时错误。建立自动化的依赖冲突检测机制对于保障应用稳定性至关重要：


interface ConflictReport {
  readonly package: string;
  readonly severity: 'error' | 'warning' | 'info';
  readonly versions: ReadonlyArray<{ app: string; version: string }>;
  readonly message: string;
}

const detectConflicts = (
  apps: ReadonlyArray<{ name: string; dependencies: Record<string, string> }>,
  rules: ReadonlyArray<SharedPackageConfig>,
): ReadonlyArray<ConflictReport> => {
  const reports: Array<ConflictReport> = [];

  const depMap = new Map<string, Array<{ app: string; version: string }>>();
  apps.forEach((app) => {
    Object.entries(app.dependencies).forEach(([pkg, ver]) => {
      if (!depMap.has(pkg)) depMap.set(pkg, []);
      depMap.get(pkg)!.push({ app: app.name, version: ver });
    });
  });

  depMap.forEach((versions, pkg) => {
    const rule = rules.find((r) => r.name === pkg);
    const uniqueVersions = [...new Set(versions.map((v) => v.version))];

    if (uniqueVersions.length > 1) {
      const severity = rule?.singleton ? 'error' : 'warning';
      reports.push({
        package: pkg,
        severity,
        versions,
        message: rule?.singleton
          ? `单例依赖 ${pkg} 存在版本冲突: ${uniqueVersions.join(', ')}`
          : `依赖 ${pkg} 存在多版本: ${uniqueVersions.join(', ')}`,
      });
    }
  });

  return reports;
};
将依赖冲突检测集成到 CI/CD 管线中，可以在子应用发布前自动发现潜在的版本冲突问题。对于单例依赖的冲突设置为阻断发布的错误级别，对于非单例依赖的多版本并存设置为告警级别。


小结
    

  • 共享依赖管理需要在独立部署能力和资源效率之间取得平衡，没有银弹方案
    • 

  • External + CDN 最简单但缺乏版本协商能力；Module Federation 提供运行时自动协商
    • 

  • 依赖应按框架层、工具层、业务层分层管理，每层采用不同的共享策略和缓存时间
    • 

  • 版本协商的核心是在满足所有消费者 semver 约束的前提下选择最优共享版本
    • 

  • 自动化的依赖冲突检测应集成到 CI/CD 管线中，单例依赖冲突必须阻断发布
    • 

  • 大型微前端项目推荐组合策略：框架层 CDN 强制单例 + 工具层 MF 协商 + 业务层动态加载
