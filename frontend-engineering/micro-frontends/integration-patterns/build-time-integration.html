构建时集成

核心概念

构建时集成（Build-Time Integration）是将多个独立开发的子应用在构建阶段合并为一个整体产物的微前端集成策略。与运行时集成相比，构建时集成通过编译器和打包工具在编译期完成应用组合，产出的是一个经过 Tree Shaking、代码分割和依赖去重的优化 bundle。

NPM 包集成模式
NPM 包模式是最成熟的构建时集成方案。每个子应用作为独立的 npm 包发布，主应用通过包管理器安装并在构建时引入。这种模式完全复用现有的 npm 生态，无需额外的微前端框架：


interface MicroAppPackage {
  readonly name: string;
  readonly version: string;
  readonly entry: string;
  readonly routes: ReadonlyArray<RouteConfig>;
}

interface RouteConfig {
  readonly path: string;
  readonly component: () => Promise<{ readonly default: React.ComponentType }>;
  readonly exact?: boolean;
}

const appRegistry: ReadonlyArray<MicroAppPackage> = [
  {
    name: '@company/order-app',
    version: '2.3.1',
    entry: '@company/order-app',
    routes: [
      {
        path: '/order',
        component: () => import('@company/order-app'),
      },
    ],
  },
  {
    name: '@company/product-app',
    version: '1.8.0',
    entry: '@company/product-app',
    routes: [
      {
        path: '/product',
        component: () => import('@company/product-app'),
      },
    ],
  },
];

const buildRoutes = (apps: ReadonlyArray<MicroAppPackage>): ReadonlyArray<RouteConfig> => {
  return apps.flatMap((app) => app.routes);
};
NPM 包模式的关键挑战在于版本管理。当子应用 A 依赖 v1.0 的共享库而子应用 B 依赖 v2.0 时，打包工具需要通过 deduplication 或 alias 策略解决冲突：


interface DependencyResolution {
  readonly package: string;
  readonly requestedVersions: ReadonlyArray<string>;
  readonly resolvedVersion: string;
  readonly strategy: 'hoist' | 'alias' | 'duplicate';
}

const resolveConflicts = (deps: ReadonlyArray<DependencyResolution>): Map<string, string> => {
  const resolutions = new Map<string, string>();
  deps.forEach((dep) => {
    if (dep.strategy === 'hoist') {
      resolutions.set(dep.package, dep.resolvedVersion);
    } else if (dep.strategy === 'alias') {
      dep.requestedVersions.forEach((ver, idx) => {
        resolutions.set(`${dep.package}_v${idx}`, ver);
      });
    }
  });
  return resolutions;
};

Monorepo 构建集成
Monorepo 是构建时集成的天然载体。所有子应用共享一个代码仓库，通过 workspace 机制实现本地依赖链接，构建工具可以利用 DAG（有向无环图）分析依赖关系并实现增量构建：


interface WorkspacePackage {
  readonly name: string;
  readonly path: string;
  readonly dependencies: ReadonlyArray<string>;
  readonly isApp: boolean;
}

interface BuildGraph {
  readonly packages: ReadonlyArray<WorkspacePackage>;
  readonly edges: ReadonlyArray<readonly [string, string]>;
}

const buildTopologicalOrder = (graph: BuildGraph): ReadonlyArray<string> => {
  const inDegree = new Map<string, number>();
  const adjacency = new Map<string, ReadonlyArray<string>>();

  graph.packages.forEach((pkg) => {
    inDegree.set(pkg.name, 0);
    adjacency.set(pkg.name, []);
  });

  graph.edges.forEach(([from, to]) => {
    inDegree.set(to, (inDegree.get(to) ?? 0) + 1);
    adjacency.set(from, [...(adjacency.get(from) ?? []), to]);
  });

  const queue: Array<string> = [];
  inDegree.forEach((degree, name) => {
    if (degree === 0) queue.push(name);
  });

  const order: Array<string> = [];
  while (queue.length > 0) {
    const current = queue.shift()!;
    order.push(current);
    (adjacency.get(current) ?? []).forEach((neighbor) => {
      const newDegree = (inDegree.get(neighbor) ?? 1) - 1;
      inDegree.set(neighbor, newDegree);
      if (newDegree === 0) queue.push(neighbor);
    });
  }

  return order;
};
Monorepo 构建集成的核心优势在于变更检测。通过分析 git diff 和依赖图的交叉，只构建受影响的子应用及其下游依赖：


interface ChangeDetection {
  readonly changedFiles: ReadonlyArray<string>;
  readonly affectedPackages: ReadonlyArray<string>;
  readonly buildTargets: ReadonlyArray<string>;
}

const detectAffectedPackages = (changedFiles: ReadonlyArray<string>, graph: BuildGraph): ChangeDetection => {
  const fileToPackage = (file: string): string | undefined => {
    return graph.packages.find((pkg) => file.startsWith(pkg.path))?.name;
  };

  const directlyAffected = new Set(changedFiles.map(fileToPackage).filter(Boolean) as ReadonlyArray<string>);

  const allAffected = new Set(directlyAffected);
  const visited = new Set<string>();

  const propagate = (pkg: string): void => {
    if (visited.has(pkg)) return;
    visited.add(pkg);
    allAffected.add(pkg);
    graph.edges.filter(([dep]) => dep === pkg).forEach(([, dependent]) => propagate(dependent));
  };

  directlyAffected.forEach(propagate);

  return {
    changedFiles,
    affectedPackages: Array.from(allAffected),
    buildTargets: Array.from(allAffected).filter((name) => graph.packages.find((p) => p.name === name)?.isApp),
  };
};
构建优化策略
构建时集成的独特优势在于可以在编译期进行深度优化。主应用作为构建入口，打包工具能够全局分析代码依赖关系，执行 Tree Shaking、Scope Hoisting 和 Chunk Splitting：


interface ChunkStrategy {
  readonly name: string;
  readonly test: RegExp | ((module: { readonly resource: string }) => boolean);
  readonly priority: number;
  readonly minSize: number;
  readonly maxSize: number;
  readonly reuseExistingChunk: boolean;
}

const createOptimizationConfig = (apps: ReadonlyArray<string>): ReadonlyArray<ChunkStrategy> => {
  const vendorChunk: ChunkStrategy = {
    name: 'vendors',
    test: /[\\/]node_modules[\\/]/,
    priority: 10,
    minSize: 30000,
    maxSize: 250000,
    reuseExistingChunk: true,
  };

  const sharedChunk: ChunkStrategy = {
    name: 'shared',
    test: /[\\/]packages[\\/]shared[\\/]/,
    priority: 5,
    minSize: 10000,
    maxSize: 150000,
    reuseExistingChunk: true,
  };

  const appChunks: ReadonlyArray<ChunkStrategy> = apps.map((app, idx) => ({
    name: `app-${app}`,
    test: new RegExp(`[\\\\/]apps[\\\\/]${app}[\\\\/]`),
    priority: 20 + idx,
    minSize: 5000,
    maxSize: 200000,
    reuseExistingChunk: false,
  }));

  return [vendorChunk, sharedChunk, ...appChunks];
};

构建时集成的局限与权衡
构建时集成并非万能方案，其核心局限在于发布耦合。任何子应用的更新都需要触发整个主应用的重新构建和部署，这在大型团队中可能成为发布瓶颈。


构建时间随项目规模线性增长也是重要挑战。虽然 Monorepo 工具（Turborepo、Nx）通过远程缓存和增量构建缓解了这一问题，但当子应用数量超过一定阈值（通常 20+），构建管线的维护成本会显著上升。


混合集成策略正在成为业界趋势：核心模块采用构建时集成以获取最佳性能和类型安全，非核心或高频变更的模块采用运行时集成（如 Module Federation）以获取独立发布能力。这种策略将在后续章节的 Module Federation 部分深入讨论。


小结
    

  • 构建时集成在编译期合并子应用，产出经过深度优化的单一产物，性能优于运行时集成
    • 

  • NPM 包模式复用现有生态，通过版本管理和 peerDependencies 实现依赖共享
    • 

  • Monorepo 提供最佳的本地开发体验，配合 DAG 分析实现增量构建和变更检测
    • 

  • 构建优化（Tree Shaking、Chunk Splitting、Content Hash）可最大化产物性能和缓存命中率
    • 

  • 核心局限在于发布耦合和构建时间增长，大型项目推荐构建时+运行时混合策略
    • 

  • 技术选型应根据团队规模、发布频率和性能要求在构建时和运行时集成之间取得平衡
    •
