微前端概述

核心概念

微前端（Micro Frontends）是一种将前端单体应用拆分为多个独立开发、独立部署、独立运行的小型前端应用的架构模式。其核心理念借鉴了微服务架构在后端的成功实践——让不同团队能够自主地选择技术栈、独立地开发和发布各自负责的业务模块，同时在用户侧呈现为一个完整的应用。

微前端的适用场景
微前端不是万能方案——它引入了额外的架构复杂性。在决定是否采用微前端之前，需要评估以下条件：产品规模是否足够大（通常 10+ 人的前端团队才有拆分价值）、是否存在多个业务域需要独立迭代、是否有跨技术栈集成的需求（如收购整合、渐进式迁移）。


适合微前端的典型场景包括大型 B 端 SaaS 平台（不同业务模块由不同团队负责）、企业内部门户（聚合多个独立子系统）、遗留系统渐进迁移（新模块用新框架，老模块保持不变）。


interface MicroFrontendApp {
  readonly name: string;
  readonly version: string;
  readonly entry: string;
  readonly activeRule: string | ((location: Location) => boolean);
  readonly container: string;
  readonly props?: Record<string, unknown>;
}

interface MFERegistry {
  register(app: MicroFrontendApp): void;
  getApp(name: string): MicroFrontendApp | undefined;
  getActiveApps(location: Location): ReadonlyArray<MicroFrontendApp>;
}

const createRegistry = (): MFERegistry => {
  const apps = new Map<string, MicroFrontendApp>();
  return {
    register: (app) => apps.set(app.name, app),
    getApp: (name) => apps.get(name),
    getActiveApps: (location) =>
      [...apps.values()].filter((app) =>
        typeof app.activeRule === 'function' ? app.activeRule(location) : location.pathname.startsWith(app.activeRule),
      ),
  };
};
不适合微前端的场景包括小型项目（拆分带来的收益不足以抵消复杂性开销）、高度耦合的 UI（如所见即所得编辑器，各模块间需要频繁细粒度交互）和性能极度敏感的 C 端应用（微前端的运行时开销可能影响核心 Web Vitals）。

微前端的核心挑战
微前端架构需要解决四个核心工程挑战：应用加载与路由、样式隔离、JavaScript 沙箱和跨应用通信。


应用加载需要解决「何时加载、加载什么、如何激活」的问题。主应用需要根据路由规则动态加载对应的子应用，加载完成后将子应用挂载到指定的 DOM 容器中。


样式隔离防止不同子应用的 CSS 互相污染。CSS Modules、Shadow DOM 和运行时样式前缀是三种主流方案。


JavaScript 沙箱防止子应用修改全局变量影响其他应用。Proxy 沙箱通过拦截 window 属性的读写实现全局变量隔离。


interface Sandbox {
  activate(): void;
  deactivate(): void;
  getProxy(): WindowProxy;
}

const createProxySandbox = (name: string): Sandbox => {
  const fakeWindow = Object.create(null);
  let isActive = false;
  const proxy = new Proxy(fakeWindow, {
    get: (target, key: string) => {
      if (key in target) return target[key];
      const value = (window as Record<string, unknown>)[key];
      return typeof value === 'function' ? value.bind(window) : value;
    },
    set: (target, key: string, value) => {
      if (isActive) {
        target[key] = value;
      }
      return true;
    },
  });
  return {
    activate: () => {
      isActive = true;
    },
    deactivate: () => {
      isActive = false;
    },
    getProxy: () => proxy as unknown as WindowProxy,
  };
};
技术栈无关性
技术栈无关性是微前端最吸引人的特性之一——不同子应用可以使用不同的前端框架（React、Vue、Angular、Svelte 等）。但这个自由度是有代价的：不同框架的运行时会被重复加载，增加整体包体积和内存占用。


实践中的建议是「允许不同但鼓励统一」——在组织层面提供推荐技术栈和共享组件库，只在有充分理由时（如遗留代码、特殊性能要求）才使用不同的框架。同时通过共享依赖机制（Module Federation 的 shared 配置）避免重复加载相同的运行时。


小结
    

  • 微前端将前端单体拆分为独立开发、独立部署的子应用，实现团队自治和技术栈灵活性
    • 

  • 适用于大型 B 端平台、企业门户聚合和渐进式技术迁移等场景
    • 

  • 核心挑战包括应用加载与路由、样式隔离、JS 沙箱和跨应用通信
    • 

  • Proxy 沙箱通过拦截 window 属性读写实现全局变量隔离
    • 

  • 技术栈无关性应遵循「允许不同但鼓励统一」的原则，避免运行时冗余
    • 

  • 微前端引入的架构复杂性需要与团队规模和业务需求匹配，小型项目不建议采用
