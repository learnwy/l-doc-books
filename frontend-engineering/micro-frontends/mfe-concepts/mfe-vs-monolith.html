微前端与单体架构对比

核心概念

微前端与单体前端的选择不是「先进 vs 落后」的问题，而是「复杂性在哪里管理」的权衡。单体架构将复杂性集中在应用内部（模块划分、代码组织），微前端将复杂性转移到应用之间（集成、通信、部署）。理解这个本质差异是做出正确架构决策的前提。

复杂性分析
单体架构的复杂性主要体现在三个方面。代码耦合——随着应用规模增长，模块之间的隐式依赖越来越多，任何修改都可能产生意想不到的影响。构建速度——当代码量超过一定阈值（通常 50 万行以上），即使使用 Vite 等现代工具，冷启动和 HMR 也会变慢。发布风险——整体发布意味着任何一个模块的 bug 都可能阻塞其他模块的上线。


微前端的复杂性则体现在集成层面。运行时集成——多个应用在同一页面中运行，需要处理资源加载、样式隔离和 JS 沙箱。版本协调——共享依赖的版本升级需要跨团队协调。一致性维护——多个应用保持一致的用户体验（设计系统、交互模式）需要额外的治理成本。


interface ArchitectureDecision {
  readonly scenario: string;
  readonly recommendation: 'monolith' | 'micro-frontend' | 'modular-monolith';
  readonly factors: ReadonlyArray<DecisionFactor>;
}

interface DecisionFactor {
  readonly name: string;
  readonly weight: number;
  readonly monolithScore: number;
  readonly mfeScore: number;
  readonly explanation: string;
}

const evaluateArchitecture = (
  factors: ReadonlyArray<DecisionFactor>,
): { recommendation: string; scores: { monolith: number; mfe: number } } => {
  let monolithTotal = 0;
  let mfeTotal = 0;
  for (const factor of factors) {
    monolithTotal += factor.monolithScore * factor.weight;
    mfeTotal += factor.mfeScore * factor.weight;
  }
  return {
    recommendation: mfeTotal > monolithTotal ? 'micro-frontend' : 'monolith',
    scores: { monolith: monolithTotal, mfe: mfeTotal },
  };
};
性能对比
性能是微前端架构最常被质疑的方面。理论上，微前端的运行时加载和多框架共存会带来性能开销。但通过合理的优化策略，这个开销可以控制在可接受的范围内。


首屏加载方面，单体应用通过 Tree-shaking 和代码分割可以实现最优的首屏 bundle。微前端的主应用 + 首个子应用的加载会引入额外的网络请求和解析开销。优化策略包括子应用预加载（在空闲时间提前加载可能需要的子应用）和共享依赖提取（React、React-DOM 等只加载一次）。

运行时性能方面，微前端的主要开销来自子应用切换。每次路由导航到不同子应用时，需要卸载当前子应用并加载新子应用。使用 KeepAlive 策略可以将已加载的子应用保留在内存中，以空间换时间避免重复加载。


模块化单体作为中间方案
模块化单体（Modular Monolith）是介于纯单体和微前端之间的方案——在单体应用内部通过严格的模块边界和依赖规则来实现类似微前端的团队自治效果，但不引入运行时集成的复杂性。


模块化单体使用 monorepo 组织代码，每个业务模块作为独立的 package，通过明确的公开 API 交互。Nx、Turborepo 等工具提供了模块边界检查和按模块构建的能力。这种方案保留了单体应用的性能优势和开发体验，同时通过工具约束实现了一定程度的模块独立性。


interface ModularMonolith {
  readonly modules: ReadonlyArray<AppModule>;

interface AppModule {

小结
    

  • 微前端与单体的选择是「复杂性管理位置」的权衡，不是技术先进性的比较
    • 

  • 单体架构的核心挑战是代码耦合和构建速度，微前端的挑战在集成和一致性
    • 

  • 微前端的首屏加载和路由切换有额外性能开销，但通过预加载和 KeepAlive 可优化到可接受范围
    • 

  • 模块化单体是有效的中间方案，保留性能优势的同时通过工具约束实现模块自治
    • 

  • 架构决策应基于团队规模、发布频率、技术迁移需求和性能要求的综合评估
    • 

  • 从单体到微前端的迁移通常是渐进的，先做好模块化再考虑运行时拆分
    •
