性能边界

何时使用 WASM

WASM 不是银弹。理解 JS 与 WASM 各自的性能特点，才能在正确的场景使用正确的工具。

场景 JS 表现 WASM 表现 推荐选择
DOM 操作 ✅ 原生 ❌ 需跨边界 JS
字符串处理 ✅ 快 ⚠️ 有拷贝开销 JS
JSON 解析 ✅ 原生优化 ⚠️ 序列化开销 JS
图像像素处理 ⚠️ 较慢 ✅ 快 WASM
密集数值计算 ⚠️ 较慢 ✅ 快 WASM
加密/哈希 ⚠️ 较慢 ✅ 快 WASM
物理模拟 ❌ 慢 ✅ 快 WASM
压缩/解压 ⚠️ 较慢 ✅ 快 WASM
简单业务逻辑 ✅ 快 ⚠️ 过度工程 JS 


提示： 一个经验法则：如果你的函数在 JS 中的执行时间已经小于 1ms，切换到 WASM 大概率不会带来可感知的提升。WASM 的优势在计算时间超过 10ms 的场景中最为显著。






序列化开销量化
跨边界传递数据的序列化/反序列化开销是 WASM 性能的最大陷阱。


function measureOverhead() {
  const sizes = [100, 1_000, 10_000, 100_000, 1_000_000];

  for (const size of sizes) {
    const data = new Float64Array(size);
    for (let i = 0; i < size; i++) data[i] = Math.random();

    const start = performance.now();
    for (let i = 0; i < 100; i++) {
      wasmInstance.processArray(data);
    }
    const elapsed = performance.now() - start;

    console.log(`${size} 元素: ${(elapsed / 100).toFixed(3)}ms/次`);
  }
}

零拷贝模式
通过直接操作共享线性内存，可以消除数据拷贝的开销。


class ZeroCopyBridge {
  private memory: WebAssembly.Memory;
  private allocate: (size: number) => number;
  private deallocate: (ptr: number, size: number) => void;
  private processInPlace: (ptr: number, len: number) => void;

  constructor(instance: WebAssembly.Instance) {
    const exports = instance.exports as any;
    this.memory = exports.memory;
    this.allocate = exports.allocate;
    this.deallocate = exports.deallocate;
    this.processInPlace = exports.process_in_place;
  }

  process(input: Float64Array): Float64Array {
    const byteLen = input.byteLength;
    const ptr = this.allocate(byteLen);

    const view = new Float64Array(this.memory.buffer, ptr, input.length);
    view.set(input);

    this.processInPlace(ptr, input.length);

    const result = new Float64Array(this.memory.buffer, ptr, input.length);
    const output = result.slice();

    this.deallocate(ptr, byteLen);
    return output;
  }

  processInMemory(offset: number, length: number): void {
    this.processInPlace(offset, length);
  }
}

pub fn process_in_place(ptr: *mut f64, len: usize) {
    let data = unsafe { std::slice::from_raw_parts_mut(ptr, len) };
    for val in data.iter_mut() {
        *val = (*val * 2.0).sin();
    }

提示： 零拷贝模式需要手动管理内存，容易引入 bug。建议仅在经过基准测试确认序列化是瓶颈时才使用。对于大多数场景，wasm-bindgen 的自动传参已经足够高效。






基准测试方法论
可靠的基准测试是做性能决策的基础。


class Benchmark {
  private results: Map<string, number[]> = new Map();

  async run(name: string, fn: () => void, iterations = 1000): Promise<void> {
    for (let i = 0; i < 100; i++) fn();

    const times: number[] = [];
    for (let i = 0; i < iterations; i++) {
      const start = performance.now();
      fn();
      times.push(performance.now() - start);
    }

    times.sort((a, b) => a - b);
    const trimmed = times.slice(Math.floor(times.length * 0.05), Math.floor(times.length * 0.95));

    this.results.set(name, trimmed);
  }

  report(): void {
    for (const [name, times] of this.results) {
      const avg = times.reduce((a, b) => a + b, 0) / times.length;
      const p50 = times[Math.floor(times.length * 0.5)];
      const p99 = times[Math.floor(times.length * 0.99)];
      console.log(`${name}: avg=${avg.toFixed(3)}ms p50=${p50.toFixed(3)}ms p99=${p99.toFixed(3)}ms`);
    }
  }
}

真实热点识别
在真实应用中识别性能热点，决定哪些代码值得迁移到 WASM。


class Profiler {
  private marks: Map<string, number[]> = new Map();

  wrap<T extends (...args: any[]) => any>(name: string, fn: T): T {
    const marks = this.marks;
    return ((...args: any[]) => {
      const start = performance.now();
      const result = fn(...args);
      const elapsed = performance.now() - start;
      if (!marks.has(name)) marks.set(name, []);
      marks.get(name)!.push(elapsed);
      return result;
    }) as T;
  }

  getHotspots(threshold = 1.0): string[] {
    return Array.from(this.marks.entries())
      .filter(([, times]) => {
        const avg = times.reduce((a, b) => a + b, 0) / times.length;
        return avg > threshold;
      })
      .sort(([, a], [, b]) => {
        const avgA = a.reduce((s, v) => s + v, 0) / a.length;
        const avgB = b.reduce((s, v) => s + v, 0) / b.length;
        return avgB - avgA;
      })
      .map(([name]) => name);
  }
}

提示： 迁移到 WASM 前先优化 JS 代码本身。很多"性能问题"的根源是低效的算法或不必要的内存分配，而不是 JS 本身的执行速度。V8 的 TurboFan 优化器对热代码的 JIT 编译效果非常好。






小结
    

  • WASM 的优势在计算密集型任务（数值运算、像素处理、加密），DOM 操作和字符串处理应留在 JS。
    • 

  • 跨边界序列化开销是最大的性能陷阱，数据量越大绝对开销越高，但占总耗时比例通常稳定。
    • 

  • 零拷贝模式通过直接操作共享线性内存消除拷贝开销，但增加代码复杂度。
    • 

  • 可靠的基准测试需要预热、大样本、修剪异常值，报告 p50/p95/p99 而非平均值。
    • 

  • 迁移到 WASM 前应先通过火焰图确认热点，并先尝试优化 JS 代码本身。
