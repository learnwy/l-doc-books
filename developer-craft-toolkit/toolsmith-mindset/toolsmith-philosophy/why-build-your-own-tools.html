为什么自制工具

概述

每一个改变了软件行业的工具，最初都源于一位开发者的个人需求。Daniel Stenberg 在 1996 年只想为 IRC 机器人获取汇率数据，于是写了不到 300 行的 C 代码——这就是 curl 的前身 httpget。Stephen Bourne 需要一种更灵活的 shell 脚本方式，创造了 sh。Ken Thompson 想在文本中搜索模式，写出了 grep。这些故事揭示了一个深刻的规律：伟大的工具诞生于"自己的问题自己解决"的匠人冲动。

自制工具不是"重复造轮子"的借口，而是一种深度学习和效率倍增的策略。当你为自己构建工具时，你获得的不仅是一个程序，更是对问题域的深刻理解、对技术栈的全面掌控、以及一笔持续产生回报的技术资产。

核心概念

痛点驱动的创造

最好的工具从来不是"为了造工具而造"的产物。它们诞生于一个具体的、反复出现的痛点：

  • curl 的诞生：1996 年，Daniel Stenberg 需要定期从网页抓取汇率数据给 IRC 机器人。他找到了 Rafael Sagula 的 httpget（不到 300 行 C 代码），开始为它贡献代码。几经改名（httpget → urlget → curl），到 2026 年 curl 已经内置于 Windows、macOS、Linux、iOS、Android、PlayStation、Nintendo Switch 等几乎所有联网设备
  • jq 的诞生：Stephen Dolan 在处理 JSON API 返回数据时，发现 Unix 传统工具（sed、awk、grep）对 JSON 格式极不友好，于是用 C 写了一个专门处理 JSON 的命令行工具
  • ripgrep 的诞生：Andrew Galloway 发现 grep 在大型代码库上太慢，且不尊重 .gitignore，于是用 Rust 重写了搜索工具，性能提升 10-100 倍

这些案例的共同模式是：创作者本人就是最忠实的用户。他们日复一日地使用自己的工具，所以能敏锐感知每一个摩擦点并持续优化。

深度理解的副产品

当你使用别人的工具时，你理解的是它的接口（API）。当你自己构建工具时，你理解的是它的本质。

使用 Git：你知道 `git rebase` 的用法
构建 Git：你理解有向无环图（DAG）、内容寻址存储、三路合并算法

这种深度理解带来的价值远超工具本身：

  1. 问题诊断能力 — 当工具出问题时，你能快速定位根因而不是盲目搜索
  2. 架构判断力 — 你积累了"怎样的设计能经受时间考验"的直觉
  3. 跨领域迁移 — 在构建工具时学到的模式（解析器、状态机、管道）适用于无数其他场景

可控性与自主权

使用第三方工具意味着将工作流的关键环节交给他人掌控：

风险类型 第三方工具 自制工具
停止维护 被动等待或被迫迁移 自主演进
不兼容升级 适应或锁定版本 按需升级
功能缺失 提 Issue 等待或 workaround 直接实现
性能瓶颈 受限于维护者优先级 针对性优化
隐私安全 信任第三方代码审计 完全透明

这不意味着要拒绝所有第三方工具。关键是对于核心工作流中的高频操作，自制工具能给你最大的自主权和演进灵活性。

实战指南

识别值得自制的工具

不是所有问题都值得自制工具。以下决策框架帮助你判断：

Quick Win 判断标准：


    

  • 如果一个 20 行的脚本就能解决问题 → 立刻写
    • 

  • 如果需要 200 行但每天节省 10 分钟 → 一周内写
    • 

  • 如果需要 2000 行但改变工作方式 → 做详细 ROI 评估后决定
    • 



从 scratch 到第一个可用版本
以一个实际场景为例——你频繁需要从 Git 日志中提取特定格式的信息：


#!/bin/bash
# v0.1: git-digest — 快速生成 Git 提交摘要
# 最初版本：仅 15 行，解决 80% 的需求

SINCE="${1:-yesterday}"
FORMAT="${2:-oneline}"

case "$FORMAT" in
  oneline)  git log --since="$SINCE" --oneline ;;
  stats)    git log --since="$SINCE" --stat --format="%h %s" ;;
  author)   git log --since="$SINCE" --format="%an: %s" | sort ;;
  *)        echo "Usage: git-digest [since] [oneline|stats|author]" ;;
esac
这个 15 行的脚本已经能解决日常 80% 的需求。关键原则是先让它跑起来，再让它变好。

最佳实践
"三次法则"的应用
    

  • 第一次：手动完成任务，观察步骤
    • 

  • 第二次：如果步骤相同，记录下来（笔记或注释）
    • 

  • 第三次：不再手动——写脚本自动化
    • 



这个法则的关键在于第二次的"观察"：你需要确认这确实是一个重复模式，而不是偶发任务。过早自动化和过晚自动化一样有害。


保持"可丢弃"心态
工具的第一个版本应该是可以随时丢弃的。不要在初始版本上追求完美——追求的是验证想法。给自己设定约束：


    

  • 第一版不超过 50 行
    • 

  • 不添加配置文件
    • 

  • 不处理边缘情况
    • 

  • 硬编码所有能硬编码的东西
    • 



当你发现自己反复使用这个"丑陋"的脚本时，才是优化的时机。


记录动机而非代码
在工具的 README 或注释中，优先记录为什么而非怎么做：


## Why this exists

每天早上我需要花 15 分钟手动检查 5 个服务的健康状态。现有的监控工具（Grafana、Datadog）需要打开浏览器和多个 Tab。我想要一个终端里一行命令就能看到所有服务状态的东西。
这样的文档能帮助未来的你（或其他人）理解这个工具存在的价值，也能指导后续的演进方向。

灵感来源
以下资源能帮助你培养"发现可工具化问题"的眼光：


    

  • awesome-cli-apps (GitHub) — 发现他人解决了什么问题
    • 

  • Hacker News "Show HN" — 观察什么样的个人项目引发共鸣
    • 

  • 自己的终端历史 — history | awk '{print $2}' | sort | uniq -c | sort -rn | head -20 找到最高频命令
    • 

  • 团队的重复抱怨 — 如果同事反复遇到同一个问题，那就是工具的机会
    • 



总结
自制工具的核心价值不在于工具本身，而在于这个过程塑造的思维方式。当你习惯性地思考"这能不能被自动化""这能不能被做得更好"时，你就从一个被动的工具使用者，变成了一个主动的问题解决者。


关键要点：


    

  • 伟大的工具始于微小的个人痛点，curl 的第一版不到 300 行
    • 

  • 自制工具让你获得深度理解、完全可控性和持续的复合收益
    • 

  • 使用"三次法则"判断何时该动手：第一次观察，第二次记录，第三次自动化
    • 

  • 第一版追求"能用就行"，只有验证了价值才值得投入更多
    • 

  • 记录"为什么"比记录"怎么做"更重要
    •
