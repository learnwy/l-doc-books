开源准备清单

概述

把代码上传到 GitHub 不等于开源。真正的开源意味着你的项目对陌生人是可发现、可理解、可安装、可使用、可贡献的。一个准备不充分就匆忙公开的项目，第一印象会定义它的命运——访客在 30 秒内决定是否值得尝试，如果 README 混乱、安装失败、示例不工作，他们就再也不会回来。

本文提供一个可执行的系统性清单，确保你的工具在公开的第一天就给人留下专业印象。这不意味着需要完美——但需要达到"有人愿意用"的最低标准。重点不是面面俱到，而是在关键环节做对。

核心概念

开源就绪度模型

每个 Gate 都有明确的通过标准。通过所有 Gate 后，你的项目就"开源就绪"了。

实战指南
README 模板
# tool-name

> 一行描述这个工具做什么

[![CI Status](badge-url)](ci-url) [![npm version](badge-url)](npm-url)

## Why?

2-3 句话说明为什么需要这个工具，现有方案的不足。

## Quick Start

最快让用户看到效果的命令（不超过 3 行）。

## Installation

每种安装方式一个代码块。

## Usage

最常见的 3-5 个使用场景。

## Configuration

配置文件位置和选项说明。

## Contributing

链接到 CONTRIBUTING.md

## License

MIT © Your Name
许可证选择决策树
Git 历史清理
在公开前清理 Git 历史：


# 检查是否有大文件
git rev-list --objects --all | \
  git cat-file --batch-check='%(objectname) %(objecttype) %(rest)' | \
  sort -k3 -n -r | head -20

# 检查是否有敏感信息
git log --all --diff-filter=A -- "*.env" "*secret*" "*credential*"

# 如果需要重写历史（慎用）
# 推荐 git-filter-repo 而非 BFG（更现代）
pip install git-filter-repo
git filter-repo --path-glob '*.env' --invert-paths
CI 配置模板
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
        node: [18, 20]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test
      - run: npm run lint
最佳实践
"干净环境"验证
在发布前，在一个干净的环境中验证安装流程：


# 使用 Docker 模拟干净环境
docker run --rm -it node:20-slim bash
# 在容器内按照 README 的步骤安装和运行
npm install -g your-tool
your-tool --version
your-tool --help
# 运行 README 中的示例，确保都能正常工作
如果在干净环境中安装失败，那用户也会失败。


渐进开源策略
不需要一次性做完所有事。可以分阶段公开：


    

  1. 第一天：代码 + README + LICENSE + 基本 CI
    2. 

  2. 第一周：收集早期用户反馈，修复安装问题
    3. 

  3. 第一月：添加 CONTRIBUTING.md，处理第一批 Issue
    4. 

  4. 第一季度：建立发布节奏，添加更多平台支持
    5. 



安全检查清单
公开代码前的安全自检：


    

  •  扫描所有 commit 历史中的密钥（使用 gitleaks 或 trufflehog）
    • 

  •  检查依赖的已知漏洞（npm audit / cargo audit）
    • 

  •  确认无内网 URL 或内部服务地址
    • 

  •  如果处理用户输入，确认有基本的输入验证
    • 

  •  如果涉及文件操作，确认有路径遍历防护
    •

总结
开源准备不是一个周末就能完成的突击任务，而是一个有清晰步骤的系统工程。通过四个 Gate（代码质量、文档、分发、社区基建）逐项检查，确保你的项目在公开时达到专业标准。


关键要点：


    

  • 密钥和个人信息是必须在公开前清除的——没有商量余地
    • 

  • README 是你项目的门面——投入时间让它在 30 秒内打动访客
    • 

  • 在干净环境验证安装流程——你电脑上能跑不代表别人也能跑
    • 

  • 不需要一次性完美——渐进式公开，根据反馈迭代
    • 

  • LICENSE 文件不可缺少——没有许可证 = 默认保留所有权利 = 他人无法使用
    •
