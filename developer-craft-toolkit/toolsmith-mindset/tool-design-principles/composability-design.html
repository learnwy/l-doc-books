可组合性设计

概述

可组合性是 Unix 工具生态的生命力源泉。单个工具可能只做一件简单的事，但当它们通过管道、配置和脚本组合起来时，能完成无限复杂的任务。设计一个可组合的工具意味着：你的工具不需要知道它将与什么搭配使用，但它提供的接口让任何搭配都成为可能。这就像乐高积木——每块积木本身很简单，但组合的可能性是无穷的。

2026 年的可组合性已经超越了传统的文本管道。现代工具需要支持结构化数据交换（JSON Lines）、事件驱动的工作流（webhook/pubsub）、插件系统扩展、以及与 AI Agent 的协作（MCP 协议）。理解这些层次的可组合性，能让你设计出在当今生态中真正"好用"的工具。

核心概念

可组合性的三个层次

Level 1 — 流式组合（管道）


    

  • stdin/stdout 数据流
    • 

  • 退出码传递
    • 

  • 信号处理（SIGPIPE）
    • 

  • 代表：grep | sort | uniq
    • 



Level 2 — 配置组合（声明式）


    

  • 配置文件组合多个行为
    • 

  • 环境变量覆盖
    • 

  • 代表：Docker Compose、GitHub Actions
    • 



Level 3 — 插件/API 组合（编程式）


    

  • 插件系统
    • 

  • 库 API（libcurl、libgit2）
    • 

  • MCP 协议（AI Agent 工具调用）
    • 

  • 代表：VS Code 扩展、Webpack 插件
    • 



输入输出契约
可组合的工具必须有清晰的输入输出契约：


┌─────────────────────────────────────┐
│            Your Tool                 │
├─────────────────────────────────────┤
│ INPUT:                               │
│   - stdin (text lines / JSON)        │
│   - positional args (files/URLs)     │
│   - flags (--json, --quiet)          │
│   - env vars (TOOL_CONFIG)           │
│   - config file (~/.config/tool/)    │
├─────────────────────────────────────┤
│ OUTPUT:                              │
│   - stdout (results, structured)     │
│   - stderr (logs, errors, progress)  │
│   - exit code (0=ok, 1=error)        │
│   - files (if explicitly requested)  │
└─────────────────────────────────────┘
核心约定：


    

  • 数据输出永远走 stdout
    • 

  • 人类可读的状态信息走 stderr
    • 

  • 这样 tool1 | tool2 时，tool1 的进度条不会污染 tool2 的输入
    • 



JSON Lines (Ndjson) — 现代管道的通用语
传统管道以"行"为单位。现代工具越来越多地使用 JSON Lines 格式——每行一个 JSON 对象：


# 输出 JSON Lines
mytool --json-lines << output:
{"file": "src/app.ts", "issues": 3, "severity": "warn"}
{"file": "src/utils.ts", "issues": 0, "severity": "ok"}
{"file": "src/api.ts", "issues": 1, "severity": "error"}

# 下游工具可以用 jq 过滤
mytool --json-lines | jq 'select(.severity == "error")'
JSON Lines 的优势：


    

  • 流式处理（不需要等全部数据加载）
    • 

  • 结构化（比纯文本更容易解析）
    • 

  • 自描述（字段名即文档）
    • 

  • 容错（一行解析失败不影响其他行）
    • 



实战指南
设计多格式输出
一个好的可组合工具应该支持多种输出格式：


# 人类友好模式（默认，当 stdout 是 TTY 时）
$ disk-usage ~/projects
  12.0 GB  node_modules/
   4.7 GB  .git/
   2.1 GB  dist/

# 机器友好模式
$ disk-usage ~/projects --json
[
  {"path": "node_modules/", "bytes": 12884901888},
  {"path": ".git/", "bytes": 5046586572},
  {"path": "dist/", "bytes": 2254857830}
]

# Tab 分隔（方便 awk/cut 处理）
$ disk-usage ~/projects --tsv
12884901888	node_modules/
5046586572	.git/
2254857830	dist/

# 单值模式（方便嵌入脚本）
$ disk-usage ~/projects --total --bytes
20506334002
实现模式：


function formatOutput(data, options) {
  if (options.json) return JSON.stringify(data);
  if (options.tsv) return data.map((d) => `${d.bytes}\t${d.path}`).join('\n');
  if (!process.stdout.isTTY) return formatPlain(data); // 管道时自动简化
  return formatHuman(data); // TTY 时带颜色和对齐
}
实现标准信号处理
可组合的工具必须正确处理 Unix 信号：


// SIGPIPE: 下游管道关闭时优雅退出（不报错）
process.on('SIGPIPE', () => process.exit(0));

// SIGINT (Ctrl-C): 清理并退出
process.on('SIGINT', () => {
  cleanup();
  process.exit(130); // 128 + signal number
});

// SIGTERM: 优雅关闭
process.on('SIGTERM', () => {
  cleanup();
  process.exit(143);
});
忽略 SIGPIPE 是新手最常犯的错误——当用户执行 your-tool | head -5 时，head 读完 5 行后关闭管道，如果你的工具不处理 SIGPIPE，就会抛出一个丑陋的错误。


配置优先级设计
可组合的工具应该接受来自多个来源的配置，并有清晰的优先级：


优先级（从高到低）：
1. 命令行参数        --output=json
2. 环境变量          TOOL_OUTPUT=json
3. 项目配置文件      ./.toolrc.json
4. 用户配置文件      ~/.config/tool/config.json
5. 系统配置          /etc/tool/config.json
6. 内置默认值        output: "human"
这让工具在不同场景下都能正确工作：


    

  • 个人使用时：修改用户配置文件
    • 

  • 项目范围：提交 .toolrc.json 到仓库
    • 

  • CI 环境：通过环境变量覆盖
    • 

  • 临时调整：命令行参数
    • 



最佳实践
成为好的管道公民
# 检测是否在管道中（stdin 不是 TTY）
if [ ! -t 0 ]; then
  # 在管道中：从 stdin 读取
  INPUT=$(cat)
else
  # 交互模式：使用参数或提示用户
  INPUT="$1"
fi

# 检测 stdout 是否被管道（输出不是 TTY）
if [ ! -t 1 ]; then
  # 输出被管道：简化格式，去除颜色
  echo "$RESULT"
else
  # 输出到终端：带颜色和格式
  echo -e "\033[32m$RESULT\033[0m"
fi
NO_COLOR 标准
尊重 NO_COLOR 环境变量（https://no-color.org/）：


const useColor = process.stdout.isTTY && !process.env.NO_COLOR && process.env.TERM !== 'dumb';
渐进增强而非全有全无
不要让缺少某个功能的支持导致整个工具失败：


// 不好：json 解析失败就整个崩溃
const data = JSON.parse(input); // throws on invalid JSON

// 好：优雅降级
try {
  const data = JSON.parse(input);
  return processStructured(data);
} catch {
  // 如果不是 JSON，当作纯文本处理
  return processPlainText(input);
}

总结
可组合性是工具长期生命力的关键。一个不可组合的工具是一座孤岛；一个可组合的工具是生态系统的一部分。


设计可组合工具的核心原则：


    

  • 数据走 stdout，状态走 stderr——永远不要混淆
    • 

  • 支持多格式输出（human/json/tsv）——让人和机器都能消费
    • 

  • 正确处理信号——做一个好的管道公民
    • 

  • 配置有明确优先级——命令行 > 环境变量 > 配置文件 > 默认值
    • 

  • 优雅降级——处理不了的输入格式回退而非崩溃
    • 

  • 尊重 NO_COLOR 和 TTY 检测——在不同环境下自适应
    •
