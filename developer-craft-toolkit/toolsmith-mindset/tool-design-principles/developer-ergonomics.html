人机工程学

概述

工具的功能再强大，如果用户不愿意使用它，就没有价值。人机工程学（Developer Ergonomics）研究的是如何让工具"好用"——不仅指功能上能完成任务，更指整个使用过程的流畅、直觉和愉悦。一个符合人机工程学的工具，用户不需要查文档就知道怎么用；遇到错误时知道怎么修；使用一周后发现它已经融入了日常工作流，像呼吸一样自然。

Git 的强大毋庸置疑，但它的人机工程学长期被诟病——反直觉的命令命名（checkout 既能切换分支又能恢复文件）、让人困惑的错误信息、陡峭的学习曲线。相比之下，GitHub CLI（gh）展示了如何在保持功能强大的同时提供优秀的用户体验：直觉的子命令、有帮助的错误信息、上下文感知的默认值。

核心概念

人机工程学的五个维度

1. 可学习性（Learnability） — 新用户能多快上手？


    

  • 零配置即可使用（sensible defaults）
    • 

  • 帮助信息清晰且带示例
    • 

  • 命名符合用户的心智模型
    • 



2. 效率（Efficiency） — 熟练用户能多快完成任务？


    

  • 常用操作有快捷方式（短参数、别名）
    • 

  • 减少键入量（自动补全、模糊匹配）
    • 

  • 避免不必要的确认步骤
    • 



3. 可记忆性（Memorability） — 隔段时间再用还记得怎么用？


    

  • 一致的命名规律
    • 

  • 可预测的行为模式
    • 

  • 及时的上下文提示
    • 



4. 错误恢复（Error Recovery） — 犯错后能多容易恢复？


    

  • 错误信息说明原因和修复方法
    • 

  • 危险操作有确认步骤
    • 

  • 支持 --dry-run 预览效果
    • 

  • 操作可撤销
    • 



5. 满意度（Satisfaction） — 使用时是否感到愉悦？


    

  • 快速响应（无不必要的等待）
    • 

  • 视觉美感（对齐、颜色、符号）
    • 

  • 完成时的正向反馈
    • 



命名的艺术
命名是工具设计中最容易被低估、却影响最大的环节：






原则
好的例子
差的例子





用动词描述操作
git push, docker pull
git transport, docker get




常见词汇
--output, --verbose
--emit-to, --loquacious




一致性
--no-color 禁用颜色
--plain 有时禁用颜色有时不




避免缩写
--recursive
--recur (非标准缩写)




对称性
--include / --exclude
--include / --skip





命名自检清单：


    

  • 新用户不看文档能猜出这个命令做什么吗？
    • 

  • 命令名和参数名是否使用了用户群体熟悉的词汇？
    • 

  • 相似功能是否使用了一致的命名模式？
    • 



渐进式复杂度暴露
好的工具不会一次性把所有功能展示给用户。它应该像洋葱一样分层：


Layer 0: tool                     → 最常见用法（合理默认值）
Layer 1: tool --flag              → 常用选项调整
Layer 2: tool subcommand          → 进阶功能
Layer 3: tool --config file.toml  → 完整配置
Layer 4: TOOL_INTERNAL_X=1 tool   → 实验性/调试功能
curl 的完美示例：


    

  • curl https://api.com — 零参数，GET 请求
    • 

  • curl -o file.zip https://... — 常用操作
    • 

  • curl -X POST -H "..." -d "..." — 进阶用法
    • 

  • curl --libcurl output.c — 专家功能
    • 



用户在每个层级都能完成有意义的工作，不需要了解更深层级的功能。

设计可操作的错误信息
错误信息的质量直接决定用户体验：


# 差：只说出错了
Error: ENOENT

# 中等：说明了什么出错
Error: File 'config.toml' not found

# 好：说明原因 + 建议修复
Error: Configuration file not found at './config.toml'

  This file is required for deployment. Create it with:
    tool init --config

  Or specify a custom path:
    tool deploy --config /path/to/config.toml

# 优秀：上下文感知 + 猜测意图
Error: Configuration file not found at './config.toml'

  Found similar files in this directory:
    ./config.yaml  (wrong format? Run: tool migrate-config config.yaml)
    ./old-config.toml  (renamed? Run: mv old-config.toml config.toml)
实现智能默认值
// 上下文感知默认值：根据环境自动选择合理配置
function resolveDefaults(options) {
  return {
    // 如果在 Git repo 中，用仓库名作为项目名
    name: options.name || path.basename(findGitRoot() || process.cwd()),

    // 如果 CI 环境中，自动禁用交互和颜色
    interactive: options.interactive ?? (!process.env.CI && process.stdin.isTTY),

    // 如果检测到 package.json，推断语言为 Node.js
    language: options.language || detectProjectLanguage(),

    // 输出格式：管道中自动 JSON，终端中人类格式
    format: options.format || (process.stdout.isTTY ? 'human' : 'json'),
  };
}
进度反馈设计
长时间操作必须提供进度反馈，但方式要恰当：


# TTY 环境：动态进度条
$ tool build
Building... ████████████████░░░░ 78% (312/400 files)

# 管道/CI 环境：简洁的里程碑输出
$ tool build 2>&1
[1/4] Resolving dependencies...
[2/4] Compiling source files...
[3/4] Running post-build checks...
[4/4] Build complete (4.2s)
原则：


    

  • 确定性进度用进度条（知道总量）
    • 

  • 不确定进度用 spinner（不知道何时结束）
    • 

  • 完成时显示耗时（便于性能追踪）
    • 

  • stderr 输出进度信息，不影响 stdout 的数据流
    • 



最佳实践
确认步骤的设计
危险操作需要确认，但不能过度确认：


# 原则：默认安全，--force 跳过确认
$ tool delete-all
This will permanently delete 47 items. This cannot be undone.
Continue? [y/N]

# 脚本中使用 --force 或 --yes 跳过
$ tool delete-all --yes

# 提供 --dry-run 预览
$ tool delete-all --dry-run
Would delete:
  - item-1 (created 2024-01-15)
  - item-2 (created 2024-03-22)
  ... (45 more)
自动补全
现代 CLI 工具应该提供 shell 自动补全：


# 生成补全脚本
tool --completions bash > /etc/bash_completion.d/tool
tool --completions zsh > ~/.zfunc/_tool
tool --completions fish > ~/.config/fish/completions/tool.fish
自动补全极大提升效率——用户不需要记住所有子命令和选项名，Tab 就能发现。


一致性胜过完美
如果你有多个工具或一个有多个子命令的工具，一致性比任何单个设计决策都重要：


    

  • 所有子命令使用相同的 flag 名（--json, --verbose, --quiet）
    • 

  • 错误信息格式统一
    • 

  • 颜色含义一致（红色=错误，黄色=警告，绿色=成功）
    • 

  • 确认提示格式统一（[y/N] 大写表示默认选项）
    •

总结
人机工程学是让工具从"能用"升级到"好用"的关键。技术上完美但用户体验糟糕的工具，最终会被技术上普通但体验优秀的工具取代。


人机工程学核心原则：


    

  • 命名要直觉：用户不查文档也能猜到命令的含义
    • 

  • 默认值要智能：零配置即可完成 80% 的常见场景
    • 

  • 错误要可操作：告诉用户该怎么修复，而不只是说"出错了"
    • 

  • 复杂度要分层：新手和专家各取所需，互不干扰
    • 

  • 反馈要及时：进度条、成功确认、耗时统计
    • 

  • 一致性优先：宁可所有地方都"中等"，也不要一些地方"优秀"一些地方"糟糕"
    •
