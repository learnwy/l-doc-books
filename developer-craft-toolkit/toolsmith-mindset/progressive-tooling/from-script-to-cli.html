从脚本到 CLI

概述

每个优秀的命令行工具都有一个卑微的起点——通常是一个 20 行的 bash 脚本。从脚本到 CLI 的升级不是一个突变，而是一个渐进的过程：当你的脚本开始需要参数、需要帮助信息、需要错误处理时，它就在向你发出"该升级了"的信号。掌握这个升级的时机和方法，是工具匠人的核心技能之一。

本文将通过一个完整的实例，展示一个脚本如何经历多个里程碑逐步演化为一个规范的 CLI 工具，并提供明确的升级判断标准和每个阶段的技术选型建议。

核心概念

脚本与 CLI 的本质差异

特征 脚本 CLI 工具
受众 自己 自己 + 他人
接口 硬编码或位置参数 命名参数 + flags
文档 注释（或无） --help + man page
错误处理 报错就退出 有意义的错误信息 + 退出码
配置 环境变量或编辑源码 配置文件 + 参数覆盖
分发 复制文件 包管理器安装
测试 手动运行验证 自动化测试
版本 无 语义化版本号

升级信号识别

以下信号表明你的脚本准备好升级为 CLI 了：

  1. 参数硬编码不够用 — 你开始频繁修改脚本中的常量来适应不同场景
  2. 别人想用 — 同事问你"那个脚本能给我一份吗"
  3. 自己忘了怎么用 — 隔一周回来不记得参数顺序
  4. 出错时一头雾水 — 脚本失败了但看不出原因
  5. 多个变体并存 — 同一个脚本出现了多份略有不同的拷贝

CLI 工具的分级

不是所有 CLI 都需要同样的复杂度。根据使用场景分级：

Level 1 — 个人工具

  • 命名参数 + --help
  • 基本错误信息
  • 一个源文件搞定

Level 2 — 团队工具

  • 配置文件支持
  • 详细错误信息 + 退出码
  • 基本测试覆盖
  • README 文档

Level 3 — 公开工具

  • 完整的帮助系统
  • 多平台支持
  • 自动补全
  • 包管理器分发
  • CI/CD + 发布自动化

实战指南

完整演化实例

让我们跟踪一个工具从脚本到 CLI 的完整演化过程。

起点：一个 15 行的 bash 脚本

#!/bin/bash
# cleanup-branches: 删除已合并的本地 Git 分支
git branch --merged main | grep -v "main\|master\|\*" | xargs git branch -d
echo "Done! Merged branches cleaned."

问题：硬编码了 main 分支名、没有 dry-run 模式、没有确认步骤。

第一次升级：添加参数

#!/bin/bash
# cleanup-branches v0.2: 添加参数支持
set -e

BASE="${1:-main}"
DRY_RUN="${2:-false}"

BRANCHES=$(git branch --merged "$BASE" | grep -v "$BASE\|master\|\*")

if [ -z "$BRANCHES" ]; then
  echo "No merged branches to clean."
  exit 0
fi

echo "Branches to remove:"
echo "$BRANCHES"

if [ "$DRY_RUN" = "true" ] || [ "$DRY_RUN" = "--dry-run" ]; then
  echo "(dry run - no branches deleted)"
  exit 0
fi

echo "$BRANCHES" | xargs git branch -d
echo "Done!"

仍然是位置参数——用户必须记住顺序。是时候引入命名参数了。

第二次升级：命名参数 + 帮助信息

#!/bin/bash
# cleanup-branches v0.3: proper CLI interface
set -e

VERSION="0.3.0"
BASE="main"
DRY_RUN=false
FORCE=false

show_help() {
  cat << EOF
cleanup-branches v$VERSION — Remove merged Git branches

USAGE:
  cleanup-branches [OPTIONS]

OPTIONS:
  -b, --base <branch>   Base branch to compare (default: main)
  -d, --dry-run         Show branches without deleting
  -f, --force           Skip confirmation prompt
  -h, --help            Show this help message
  -v, --version         Show version

EXAMPLES:
  cleanup-branches                    # Clean branches merged into main
  cleanup-branches -b develop         # Clean branches merged into develop
  cleanup-branches --dry-run          # Preview what would be deleted
EOF
}

while [[ $# -gt 0 ]]; do
  case $1 in
    -b|--base) BASE="$2"; shift 2 ;;
    -d|--dry-run) DRY_RUN=true; shift ;;
    -f|--force) FORCE=true; shift ;;
    -h|--help) show_help; exit 0 ;;
    -v|--version) echo "cleanup-branches v$VERSION"; exit 0 ;;
    *) echo "Unknown option: $1"; show_help; exit 1 ;;
  esac
done

BRANCHES=$(git branch --merged "$BASE" 2>/dev/null | grep -v "$BASE\|master\|\*" || true)

if [ -z "$BRANCHES" ]; then
  echo "✓ No merged branches to clean."
  exit 0
fi

echo "Branches merged into '$BASE':"
echo "$BRANCHES" | sed 's/^/  /'
echo ""

if [ "$DRY_RUN" = true ]; then
  echo "(dry run — no changes made)"
  exit 0
fi

if [ "$FORCE" = false ]; then
  read -p "Delete these branches? [y/N] " -n 1 -r
  echo
  [[ $REPLY =~ ^[Yy]$ ]] || exit 0
fi

echo "$BRANCHES" | xargs git branch -d
echo "✓ Cleaned $(echo "$BRANCHES" | wc -l | tr -d ' ') branches."

这已经是一个合格的 Level 1 CLI 工具了。但如果你想分享给团队或跨平台使用，Bash 的局限就开始显现。

第三次升级：迁移到编程语言

当以下情况出现时，考虑迁移到 Python/Node/Go/Rust：

  • 需要复杂的数据处理（JSON/YAML 解析）
  • 需要跨平台兼容
  • 需要网络请求
  • 逻辑复杂度超过 100 行 bash
  • 需要单元测试

语言选型指南

需求特征 推荐语言 框架 优势
快速原型，系统管理 Python Click / Typer 标准库丰富，上手快
TypeScript 生态 Node.js/Deno citty / Commander 前端团队友好
高性能，单二进制 Go Cobra 编译快，交叉编译简单
极致性能，安全 Rust Clap 零成本抽象，无运行时
简单任务，无依赖 Bash — 处处可用

关键技术要素清单

一个合格的 CLI 工具应该具备以下要素：

## CLI 工具升级检查清单

### 必须 (Level 1)

- [ ] 命名参数 (--flag 和 -f 短格式)
- [ ] --help 显示用法、选项、示例
- [ ] --version 显示版本号
- [ ] 有意义的退出码 (0=成功, 1=用户错误, 2=系统错误)
- [ ] 错误信息指向解决方案而非仅报告问题

### 推荐 (Level 2)

- [ ] 配置文件支持 (~/.config/tool/config.toml)
- [ ] 环境变量覆盖 (TOOL_OPTION=value)
- [ ] 彩色输出 (尊重 NO_COLOR 环境变量)
- [ ] stdin 管道输入支持
- [ ] 结构化输出选项 (--json)

### 进阶 (Level 3)

- [ ] Shell 自动补全 (bash/zsh/fish)
- [ ] man page
- [ ] 子命令结构 (tool <command> [options])
- [ ] 进度条/spinner (长时间操作)
- [ ] 调试模式 (--verbose / --debug)

最佳实践

POSIX 兼容性

遵循 POSIX 参数约定让用户在使用你的工具时感到熟悉：

  • 短选项用单横线 + 单字母：-v
  • 长选项用双横线 + 单词：--verbose
  • 短选项可组合：-abc 等价于 -a -b -c
  • -- 表示选项结束，后面都是位置参数
  • 选项值可用 = 或空格：--output=file 或 --output file

错误信息设计

反面：Error: invalid argument 正面：Error (E001): Branch 'featur/login' not found. Did you mean 'feature/login'? Run 'cleanup-branches --help' for usage.

好的错误信息要素：

  1. 明确说明什么出错了
  2. 解释为什么出错（如果能判断）
  3. 建议怎么修复
  4. 提供错误码方便搜索

渐进式复杂度暴露

不要一开始就展示所有选项。好的 CLI 工具有"洋葱层"设计：

  • 零参数可用：cleanup-branches（用默认值即可完成基本任务）
  • 常用参数少：cleanup-branches --dry-run（80% 场景只需 1-2 个选项）
  • 高级参数隐藏：cleanup-branches --help-advanced（20% 场景的复杂选项）

工具与生态

参数解析库推荐（2026）

语言 库 特点
Python Typer 类型注解自动生成 CLI，零样板代码
Node.js citty UnJS 生态，零依赖，TypeScript 原生
Go Cobra + Viper 子命令 + 配置管理，Hugo/kubectl 同款
Rust Clap (derive) 宏驱动，编译时验证
Bash — 手动 while+case 或 getopts

测试框架

  • Shell 脚本测试：bats-core（Bash Automated Testing System）
  • 快照测试：insta (Rust) / Jest snapshot (Node)
  • 集成测试：assert_cmd (Rust) / execa (Node)

总结

从脚本到 CLI 的升级是一个自然的演化过程，不需要一步到位。关键是识别升级信号、选择合适的时机、按需逐步添加功能。

演化路线图：

  1. 先写一个"能跑就行"的脚本解决问题（30 分钟内）
  2. 当你开始忘记参数顺序时，添加 --help 和命名参数
  3. 当别人想用时，添加错误处理和配置文件
  4. 当 bash 成为瓶颈时，迁移到编程语言
  5. 当要公开发布时，添加测试、文档和分发

每一步都应该是由实际需求驱动的——如果当前阶段已经够用，就不要过早升级。最好的 CLI 工具是那些在每个阶段都恰好满足需求的工具。
