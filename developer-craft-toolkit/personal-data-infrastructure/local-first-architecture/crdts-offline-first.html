CRDTs 与离线优先

概述

Conflict-free Replicated Data Types（CRDTs）是 Local-first 架构的数学基石。它们允许多个设备独立修改共享数据，然后在任意时刻合并，数学上保证最终一致性——无需中心服务器协调、无需锁、无需在线。2026 年，CRDTs 已从学术论文走向生产系统：Figma 用它实现离线协作、Linear 用它同步 issue 元数据、Notion 用它处理块结构。对个人开发者而言，CRDTs 意味着你的笔记应用、任务管理工具、日记系统可以在飞机上、地铁里、任何断网环境中完美工作，回到网络后无缝同步。

核心概念

什么是 CRDT

CRDT 的核心约束用一句话概括：任何两个副本，无论以何种顺序接收到何种更新，最终都会收敛到相同状态。这通过代数性质保证：

  • 交换律（Commutativity）：操作的应用顺序不影响最终结果
  • 结合律（Associativity）：操作的分组方式不影响最终结果
  • 幂等性（Idempotence）：重复应用同一操作不改变结果

满足这些性质的数据结构，天然适合在不可靠网络中使用——丢包、乱序、重复传输都不会破坏一致性。

两大变体

维度 State-based (CvRDT) Operation-based (CmRDT)
同步内容 完整状态 单个操作
网络要求 仅需最终送达 需要因果序（可靠广播）
带宽消耗 较高（传输全状态） 较低（仅传增量）
合并方式 Lattice join（取上界） 直接应用操作
代表实现 Automerge Yjs

Delta-state CRDT 是二者的折衷：只传输状态变化的增量（delta），既保留了 State-based 对网络的宽容性，又减少了带宽消耗。

常见 CRDT 数据结构

    

  • G-Counter / PN-Counter：分布式计数，每个节点维护自己的计数向量
    • 

  • LWW-Register：Last-Writer-Wins，用时间戳解决冲突（Figma 的 per-property 策略）
    • 

  • OR-Set（Observed-Remove Set）：支持添加和删除的集合，每个元素附带唯一标记
    • 

  • RGA / YATA：序列 CRDT，用于协作文本编辑
    • 



实战指南
Yjs：性能之王
Yjs 是 2026 年 Web 生态中性能最优的 CRDT 库，由 Kevin Jahns 维护。核心指标：


    

  • 文本编辑：26K-156K ops/s
    • 

  • 编码效率：100KB 文档仅需 160KB 磁盘空间
    • 

  • 内存中：约 3MB（包含完整历史元数据）
    • 



import * as Y from 'yjs';
import { WebsocketProvider } from 'y-websocket';
import { IndexeddbPersistence } from 'y-indexeddb';

// 创建文档
const doc = new Y.Doc();

// 本地持久化到 IndexedDB
const persistence = new IndexeddbPersistence('my-notes', doc);

// 网络同步（可选，断网时本地正常工作）
const wsProvider = new WebsocketProvider('wss://my-sync.server.com', 'my-notes-room', doc);

// 使用共享数据类型
const notes = doc.getMap('notes');
const todoList = doc.getArray('todos');

// 本地修改——即时生效，后台同步
doc.transact(() => {
  notes.set('2026-05-08', {
    title: '学习 CRDTs',
    content: '今天深入理解了 Yjs 的 YATA 算法...',
    tags: ['tech', 'distributed-systems'],
  });
});

Automerge：文档模型的优雅
Automerge 由 Martin Kleppmann（《Designing Data-Intensive Applications》作者）主导开发，以 JSON-like 文档模型为核心抽象：


import { next as Automerge } from '@automerge/automerge';

// 初始化文档
let doc = Automerge.init();

// 设备 A：创建任务
doc = Automerge.change(doc, 'Create task board', (d) => {
  d.tasks = [];
  d.metadata = { title: 'Sprint 42', createdAt: Date.now() };
});

// 设备 B（离线）：添加任务
let docB = Automerge.clone(doc);
docB = Automerge.change(docB, 'Add task from phone', (d) => {
  d.tasks.push({ id: 'task-1', title: '修复登录 Bug', done: false });
});

// 设备 A（离线）：也添加任务
doc = Automerge.change(doc, 'Add task from laptop', (d) => {
  d.tasks.push({ id: 'task-2', title: '更新文档', done: false });
});

// 重新连接——自动合并，两个任务都保留
let merged = Automerge.merge(doc, docB);
// merged.tasks = [{ id: 'task-2', ... }, { id: 'task-1', ... }]
Automerge 2.0 的性能飞跃：处理 260,000 次击键从 2 秒/字符 优化到总计 600ms，这得益于列式编码和 Rust WASM 后端。

最佳实践
墓碑问题与垃圾回收
CRDT 删除操作通常不会真正移除数据，而是标记为"墓碑"（tombstone）。大量删除后，墓碑积累会导致严重的空间膨胀——极端案例下，10M 个墓碑可膨胀至 GB 级。


应对策略：


    

  1. 定期压缩（Compaction）：当所有活跃节点都确认收到某墓碑后，安全删除
    2. 

  2. TTL 策略：为墓碑设置存活期，超时后假定所有节点已同步
    3. 

  3. 快照 + 增量：定期生成全量快照，新节点从快照开始而非重放全部历史
    4. 

  4. 混合架构：用中心服务器追踪"已确认删除"的元数据，减轻客户端负担
    5. 



适用性边界判断
Local-first + CRDTs 不是万能解——2026 年的实战经验总结出三条决策标准：


    

  1. 数据主权敏感度 > 协作复杂度？ 个人笔记、健康数据 → 适合；多人实时白板、审计系统 → 不适合
    2. 

  2. 离线是核心体验还是锦上添花？ 野外数据采集、飞行中使用 → 核心；社交媒体 feed → 非核心
    3. 

  3. 团队能否调试分布式状态？ CRDT 的最终一致性在测试环境难以复现，需要专门的调试工具链
    4. 



工程复杂度预期
根据 2026 年的生产经验数据，同等功能规模下：


    

  • 前端代码量增加 40-60%（同步状态机、冲突 UI、一致性测试）
    • 

  • 具备 CRDT 调试经验的工程师薪资溢价约 35%
    • 

  • 选型错误的技术债平均需要 6-8 人周偿还

总结
CRDTs 为 Local-first 应用提供了数学上严谨的冲突解决基础。2026 年的工具链已足够成熟——Yjs 和 Automerge 都经过了大规模生产验证。关键不是"能不能用"，而是"该不该用"：当你的个人工具需要离线可靠性、多设备同步和数据自主权时，CRDTs 是正确的架构选择；但当协作复杂度超过 5 人实时编辑、或需要审计追踪时，传统服务端架构可能更合适。从个人笔记工具或任务管理器开始，先小范围验证 CRDT 的开发体验，再逐步扩展到更复杂的场景。
