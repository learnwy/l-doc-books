同步协议设计

概述

Local-first 应用的数据存在于多个设备上，同步协议决定了这些副本如何交换变更、解决冲突、最终收敛。这不仅仅是"把数据发过去"——它涉及因果序追踪、增量传输、断点续传、权限控制和冲突感知。2026 年，同步层已从自建方案演进为成熟的中间件生态：Electric SQL 将 Postgres 变更流实时推送到客户端 SQLite，PowerSync 提供托管的双向同步，而 Yjs 和 Automerge 内置了可插拔的同步传输层。对个人开发者，选择或构建正确的同步协议，是让多设备体验从"勉强能用"跃升到"丝滑自然"的关键。

核心概念

同步的四层模型

    

  • 应用层：只与本地存储交互，不关心同步细节
    • 

  • 冲突解决层：定义如何合并并发修改（CRDT、LWW、自定义规则）
    • 

  • 同步引擎层：检测本地变更、计算增量、管理同步状态
    • 

  • 传输层：实际的网络通信（WebSocket、WebRTC、HTTP Long-poll）
    •

对个人数据基础设施，星形同步是最优起点——用你的自托管服务器作为中心枢纽，所有设备向它同步。这简化了权限管理、备份策略和在线状态追踪。


因果序与向量时钟
多设备同步必须追踪操作的因果关系——不是物理时间（设备时钟不可信），而是逻辑时间：


设备 A: [A:1] → [A:2] → [A:3]
设备 B:           [B:1] → [B:2]

向量时钟状态:
A 视角: {A:3, B:0}  （未收到 B 的更新）
B 视角: {A:1, B:2}  （只收到 A 的第一个更新）

合并后: {A:3, B:2}  （两边的最新状态）
向量时钟的大小随参与设备数线性增长。对个人场景（2-5 设备），开销可忽略；但如果设计面向数百用户的协作，需要考虑压缩策略（如 dotted version vectors）。


实战指南
Electric SQL：Postgres 到本地的实时同步
Electric SQL 将 Postgres 的 WAL（Write-Ahead Log）变更实时流式传输到客户端的本地 SQLite，实现双向同步：


// Electric SQL 客户端配置
import { electrify } from 'electric-sql/wa-sqlite';
import { schema } from './generated/client';

// 初始化：本地 SQLite 与云端 Postgres 自动同步
const electric = await electrify(db, schema, {
  url: 'https://my-electric-server.com',
  auth: { token: await getAuthToken() },
});

// 定义同步形状（Shape）——只同步需要的数据子集
await electric.sync.subscribe({
  shape: {
    tables: ['notes', 'tags'],
    where: { user_id: currentUserId }, // 只同步自己的数据
  },
});

// 本地读写——即时，无网络延迟
const notes = await db.notes.findMany({
  where: { archived: false },
  orderBy: { updated_at: 'desc' },
});

// 写入自动同步
await db.notes.create({
  data: { title: '新想法', content: '...', user_id: currentUserId },
});
Electric SQL 的架构约束：


    

  • 需要 Postgres 作为后端（不适合纯 P2P）
    • 

  • 冲突解决策略较简单（LWW 为主）
    • 

  • 适合个人多设备同步，不太适合多用户实时协作
    • 



PowerSync：托管的 SQLite 同步
PowerSync 提供从云端 Postgres/MongoDB 到客户端 SQLite 的单向或双向同步，以 SDK 形式集成：


// PowerSync + React 集成
import { PowerSyncDatabase } from '@powersync/web';

const schema = new Schema([
  new Table({
    name: 'habits',
    columns: [
      new Column({ name: 'name', type: ColumnType.TEXT }),
      new Column({ name: 'streak', type: ColumnType.INTEGER }),
      new Column({ name: 'last_done', type: ColumnType.TEXT }),
    ],
  }),
]);

const db = new PowerSyncDatabase({
  schema,
  database: { dbFilename: 'habits.db' },
});

// 连接 PowerSync 服务
await db.connect(new MyConnector());

// 本地写入 + 自动上传
await db.execute('INSERT INTO habits (id, name, streak, last_done) VALUES (uuid(), ?, 0, ?)', [
  '冥想',
  new Date().toISOString(),
]);

// 响应式查询——数据变更时自动更新 UI
const habits = db.watch('SELECT * FROM habits ORDER BY streak DESC');
自建同步层：WebSocket 方案
当现有方案不满足需求时（如自定义冲突策略、特殊加密要求），可基于 WebSocket 自建：


// 服务端：Node.js + ws
import { WebSocketServer } from 'ws';
import { createServer } from 'http';

const server = createServer();
const wss = new WebSocketServer({ server });

// 每个文档一个房间
const rooms = new Map();

wss.on('connection', (ws, req) => {
  const docId = new URL(req.url, 'http://localhost').searchParams.get('doc');

  // 加入房间
  if (!rooms.has(docId)) rooms.set(docId, new Set());
  rooms.get(docId).add(ws);

  // 发送当前状态向量（让客户端知道服务端有什么）
  ws.send(
    JSON.stringify({
      type: 'sync-state',
      vector: getStateVector(docId),
    }),
  );

  ws.on('message', (data) => {
    const msg = JSON.parse(data);

    if (msg.type === 'update') {
      // 持久化增量
      applyUpdate(docId, msg.payload);

      // 广播给同文档的其他客户端
      for (const peer of rooms.get(docId)) {
        if (peer !== ws && peer.readyState === 1) {
          peer.send(data);
        }
      }
    }

    if (msg.type === 'sync-request') {
      // 客户端请求它缺失的更新
      const diff = computeDiff(docId, msg.vector);
      ws.send(JSON.stringify({ type: 'sync-response', payload: diff }));
    }
  });

  ws.on('close', () => rooms.get(docId)?.delete(ws));
});
// 客户端：带断线重连和增量同步
class SyncClient {
  constructor(docId, localStore) {
    this.docId = docId;
    this.localStore = localStore;
    this.connect();
  }

  connect() {
    this.ws = new WebSocket(`wss://sync.myserver.com?doc=${this.docId}`);

    this.ws.onopen = () => {
      // 发送本地状态向量
      this.ws.send(
        JSON.stringify({
          type: 'sync-request',
          vector: this.localStore.getStateVector(),
        }),
      );
    };

    this.ws.onmessage = (event) => {
      const msg = JSON.parse(event.data);
      if (msg.type === 'sync-response' || msg.type === 'update') {
        this.localStore.applyUpdate(msg.payload);
      }
    };

    this.ws.onclose = () => {
      // 指数退避重连
      setTimeout(() => this.connect(), this.getBackoff());
    };
  }

  // 本地变更时调用
  pushUpdate(update) {
    this.localStore.applyUpdate(update);
    if (this.ws.readyState === WebSocket.OPEN) {
      this.ws.send(JSON.stringify({ type: 'update', payload: update }));
    }
    // 离线时更新会在重连后通过 sync-request 补发
  }
}

网络弹性设计
    

  1. 乐观更新：本地写入立即生效，不等待服务端确认
    2. 

  2. 增量同步：只传输自上次同步以来的变更，而非全量
    3. 

  3. 断点续传：记录最后同步的状态向量，重连时从断点开始
    4. 

  4. 冲突指示：当自动合并可能丢失用户意图时，提供 UI 选择
    5. 

  5. 带宽适应：弱网环境下降低同步频率，批量发送
    6. 



安全考量
    

  • 传输加密：必须使用 WSS（WebSocket Secure），裸 WS 在公网不可接受
    • 

  • 认证：连接时验证 JWT token，过期后断开要求重新认证
    • 

  • 授权：服务端验证客户端只能同步自己有权限的文档
    • 

  • 端到端加密：对高敏感数据，在 CRDT 层之上加一层 E2E 加密
    •

总结
同步协议是 Local-first 架构中将"本地孤岛"连接为"多设备一体"的桥梁。对个人数据基础设施，星形同步模型（多设备 → 自托管服务器）兼顾了简单性和可控性。如果你已有 Postgres 后端，Electric SQL 或 PowerSync 几乎是零成本的选择；如果你用 Yjs 管理文档状态，y-websocket 开箱即用；如果有特殊需求（E2E 加密、自定义冲突策略），自建 WebSocket 层也不过百行代码的核心逻辑。关键是在设计之初就将同步视为一等公民——不是"做完了加个同步功能"，而是"架构本身就是分布式的"。
