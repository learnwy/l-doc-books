WAL 模式与并发

概述

SQLite 默认使用 rollback journal 模式——写入时锁定整个数据库，读者必须等待写者完成。对个人应用而言，这在大多数场景下足够，但当你的应用需要同时读写（如后台同步进程写入、前台 UI 读取），或者多个进程共享同一个数据库文件时，WAL（Write-Ahead Logging）模式带来质的飞跃：读者永远不会被写者阻塞，写者也不会被读者阻塞。理解 WAL 的工作原理和调优手段，是将 SQLite 从"够用"提升到"高性能"的关键一步。

核心概念

WAL 的工作原理

传统 rollback journal：修改前将旧数据复制到 journal 文件，然后直接修改数据库。如果崩溃，用 journal 恢复。


WAL 模式：新数据追加到 WAL 文件末尾，数据库文件保持不变。读者通过 WAL 索引（wal-index，即 .shm 文件）判断应该读 WAL 中的新版本还是数据库中的旧版本。


核心优势：


    

  • 读写并发：写入只追加 WAL，不修改数据库文件，读者不受影响
    • 

  • 更快的写入：顺序追加比随机写效率更高
    • 

  • 读者不阻塞写者：多个读者可以同时与一个写者并存
    • 

  • 崩溃安全：WAL 中的未提交数据在恢复时被忽略
    • 



并发模型：多读者单写者
WAL 模式下的 SQLite 遵循 MRSW（Multiple Readers, Single Writer）模型：

事务隔离级别
SQLite WAL 模式提供的是 快照隔离（Snapshot Isolation）：


-- 事务开始时获取一致性快照
BEGIN;
SELECT * FROM notes;  -- 看到此刻的一致状态
-- 即使其他进程在此期间写入了新数据，本事务看到的仍是开始时的快照
COMMIT;
这比"读已提交"更强（避免了不可重复读），但弱于"可串行化"（允许写倾斜异常）。对个人应用场景，快照隔离已经足够。


实战指南
启用 WAL 模式
import Database from 'better-sqlite3';

const db = new Database('personal.db');

// 启用 WAL（持久设置，关闭重开后仍然生效）
db.pragma('journal_mode = WAL');

// 推荐配合设置
db.pragma('synchronous = NORMAL'); // WAL 模式下 NORMAL 已足够安全
db.pragma('busy_timeout = 5000'); // 写锁等待 5 秒
db.pragma('wal_autocheckpoint = 1000'); // 每 1000 页自动 checkpoint
db.pragma('cache_size = -64000'); // 64MB 读缓存
busy_timeout 与写冲突处理
当两个进程同时尝试写入时，后到的写者会收到 SQLITE_BUSY 错误。busy_timeout 设置等待时间：


// 方案 1：设置 busy_timeout（简单但不够灵活）
db.pragma('busy_timeout = 5000'); // 等待最多 5 秒

// 方案 2：自定义 busy handler（更精细的控制）
// better-sqlite3 不支持自定义 handler，但 Python 的 sqlite3 支持
// 在 Node.js 中，配合重试逻辑：

function writeWithRetry(fn, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      return fn();
    } catch (err) {
      if (err.code === 'SQLITE_BUSY' && i < maxRetries - 1) {
        // 指数退避
        const delay = Math.min(100 * Math.pow(2, i), 2000);
        Atomics.wait(new Int32Array(new SharedArrayBuffer(4)), 0, 0, delay);
        continue;
      }
      throw err;
    }
  }
}
BEGIN IMMEDIATE：避免死锁
普通 BEGIN 启动的事务是延迟（DEFERRED）模式——只在第一次写操作时才获取写锁。如果两个事务都先读后写，可能产生死锁：


-- 进程 A                           -- 进程 B
BEGIN;                              BEGIN;
SELECT * FROM notes;                SELECT * FROM notes;
-- A 尝试升级为写锁                  -- B 也尝试升级为写锁
INSERT INTO notes ...;              INSERT INTO notes ...;
-- 死锁！双方都持有读锁，等待对方释放
解决方案：对写事务使用 BEGIN IMMEDIATE：


// 写事务始终用 IMMEDIATE
const writeTransaction = db.transaction((data) => {
  // better-sqlite3 的 transaction() 默认使用 BEGIN IMMEDIATE
  db.prepare('INSERT INTO notes (id, title) VALUES (?, ?)').run(data.id, data.title);
});

// 如果用原始 SQL：
db.exec('BEGIN IMMEDIATE');
try {
  // ... 写入操作
  db.exec('COMMIT');
} catch (e) {
  db.exec('ROLLBACK');
  throw e;
}
Checkpoint 策略
WAL 文件会持续增长，直到 checkpoint 将其内容回写到主数据库：


// 检查 WAL 大小
const walInfo = db.pragma('wal_checkpoint(PASSIVE)');
// 返回: [{ busy: 0, log: 1500, checkpointed: 1200 }]
// log: WAL 中总页面数, checkpointed: 已回写的页面数

// 手动触发 checkpoint（不阻塞读写）
db.pragma('wal_checkpoint(PASSIVE)');

// 完整 checkpoint（等待所有读者完成后截断 WAL）
db.pragma('wal_checkpoint(TRUNCATE)');

// 限制 WAL 大小
db.pragma('journal_size_limit = 67108864'); // WAL 最大 64MB

最佳实践
多进程架构推荐
    

  • UI 进程：只做读取，永不被阻塞
    • 

  • 同步进程：用 BEGIN IMMEDIATE 写入远程拉取的数据
    • 

  • 搜索进程：读取 FTS 表，提供搜索建议
    • 

  • 备份进程：定期执行 PASSIVE checkpoint 后复制数据库文件
    •

何时不用 WAL
WAL 并非万能——以下场景应保持默认 journal 模式：


    

  • 网络文件系统：WAL 依赖共享内存（.shm），NFS/SMB 不支持
    • 

  • 只读数据库：WAL 需要写 .wal 和 .shm 文件
    • 

  • 极端写入密集：单进程连续写入时，WAL 的额外间接层略慢于 DELETE 模式
    • 

  • 需要原子跨库事务：ATTACH 的数据库不共享 WAL
    •

总结
WAL 模式是 SQLite 从"单用户嵌入式数据库"进化为"多进程并发数据引擎"的关键特性。对个人数据基础设施，WAL 解决了最常见的架构需求：后台同步进程写入时，前台 UI 依然流畅响应。配置只需三行 pragma（journal_mode=WAL、synchronous=NORMAL、busy_timeout=5000），但理解其背后的原理——快照隔离、MRSW 模型、checkpoint 机制——能帮助你在遇到性能瓶颈或奇怪锁错误时快速定位问题。记住核心规则：读事务用 BEGIN，写事务用 BEGIN IMMEDIATE，定期 checkpoint 控制 WAL 大小。
