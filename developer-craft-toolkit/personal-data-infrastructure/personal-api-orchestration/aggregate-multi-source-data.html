聚合多源个人数据

概述

个人数据分散在数十个平台——GitHub 记录代码贡献、Fitbit 追踪健康指标、Kindle 保存阅读标注、银行存储消费记录、Google Calendar 管理时间分配。每个平台都有独立的 API、认证方式和数据格式，但没有任何一个平台会帮你将这些数据关联起来。聚合多源数据就是将这些碎片化的信息流统一到你自己控制的基础设施中，形成完整的个人数据全景图。

本文从 OAuth 授权流与 Token 生命周期管理出发，系统讲解 API 限流应对策略、数据归一化与 Schema 映射、增量同步机制设计，以及生产级 ETL 管道的错误处理与重试模式。目标是让你能够可靠地从 10+ 个数据源持续拉取数据，而不必为每次 Token 过期或限流封禁而手动干预。

核心概念

OAuth 授权与 Token 生命周期

个人数据聚合的第一道关卡是认证。主流平台的认证方式分布如下：

平台 认证方式 Token 有效期 刷新机制
GitHub OAuth 2.0 + PAT PAT 不过期/OAuth 8h Refresh Token
Google (Fit/Calendar) OAuth 2.0 + PKCE 1h Refresh Token（可撤销）
Spotify OAuth 2.0 1h Refresh Token
Notion OAuth 2.0 不过期（Internal） 无需刷新
Pocket OAuth 自定义 不过期 Consumer Key
Fitbit OAuth 2.0 8h Refresh Token
银行 Open Banking OAuth 2.0 + mTLS 5-30min Consent 重授权

Token 管理的核心原则：存储 access_token + refresh_token + expires_at 三元组，在每次 API 调用前检查是否需要主动刷新。

interface TokenRecord {
  provider: string;
  accessToken: string;
  refreshToken: string | null;
  expiresAt: number; // Unix timestamp
  scopes: string[];
}

async function getValidToken(record: TokenRecord): Promise<string> {
  const BUFFER_SECONDS = 300; // 5 分钟提前量
  if (Date.now() / 1000 < record.expiresAt - BUFFER_SECONDS) {
    return record.accessToken;
  }
  // 主动刷新
  const refreshed = await refreshOAuthToken(record);
  await saveTokenRecord(refreshed);
  return refreshed.accessToken;
}

Token 刷新的并发安全

当多个同步任务同时触发刷新时，必须避免竞态条件。某些 OAuth 提供商（如 Google）会在每次刷新时轮换 Refresh Token——如果两个请求同时刷新，后一个会使用已失效的旧 Refresh Token，导致整个连接断开。

解决方案是为每个 provider 维护一个互斥锁：

const refreshLocks = new Map<string, Promise<TokenRecord>>();

async function getValidTokenSafe(record: TokenRecord): Promise<string> {
  if (!needsRefresh(record)) return record.accessToken;

  const lockKey = `${record.provider}:${record.userId}`;
  if (refreshLocks.has(lockKey)) {
    const result = await refreshLocks.get(lockKey)!;
    return result.accessToken;
  }

  const refreshPromise = refreshOAuthToken(record);
  refreshLocks.set(lockKey, refreshPromise);
  try {
    const result = await refreshPromise;
    await saveTokenRecord(result);
    return result.accessToken;
  } finally {
    refreshLocks.delete(lockKey);
  }
}

实战指南

构建限流感知的请求客户端

生产级的限流处理需要结合令牌桶算法和指数退避：

class RateLimitedClient {
  private remaining: number = Infinity;
  private resetAt: number = 0;
  private backoffMs: number = 1000;

  async request(url: string, options: RequestInit): Promise<Response> {
    // 预检：已知限额不足时主动等待
    if (this.remaining <= 1 && Date.now() < this.resetAt) {
      const waitMs = this.resetAt - Date.now() + 100;
      await sleep(waitMs);
    }

    const response = await fetch(url, options);

    // 解析限流头
    this.remaining = parseInt(response.headers.get('X-RateLimit-Remaining') ?? 'Infinity');
    this.resetAt = parseInt(response.headers.get('X-RateLimit-Reset') ?? '0') * 1000;

    if (response.status === 429) {
      const retryAfter = parseInt(response.headers.get('Retry-After') ?? '60');
      await sleep(retryAfter * 1000 + this.backoffMs);
      this.backoffMs = Math.min(this.backoffMs * 2, 60000);
      return this.request(url, options); // 递归重试
    }

    this.backoffMs = 1000; // 成功后重置退避
    return response;
  }
}

数据归一化与 Schema 映射

从多个平台拉取的数据需要映射到统一的内部 Schema。以"活动事件"为例：

// 统一内部 Schema
interface PersonalEvent {
  id: string;
  source: 'github' | 'calendar' | 'fitbit' | 'spotify';
  type: string;
  title: string;
  timestamp: string; // ISO 8601
  metadata: Record<string, unknown>;
  raw: unknown; // 保留原始数据
}

// GitHub Commit -> PersonalEvent
function normalizeGitHubCommit(commit: GitHubCommit): PersonalEvent {
  return {
    id: `github:commit:${commit.sha}`,
    source: 'github',
    type: 'code.commit',
    title: commit.message.split('\n')[0],
    timestamp: commit.author.date, // 已是 ISO 8601
    metadata: {
      repo: commit.repository,
      additions: commit.stats?.additions,
      deletions: commit.stats?.deletions,
      files: commit.files?.length,
    },
    raw: commit,
  };
}

// Fitbit Activity -> PersonalEvent
function normalizeFitbitActivity(activity: FitbitActivity): PersonalEvent {
  return {
    id: `fitbit:activity:${activity.logId}`,
    source: 'fitbit',
    type: `health.${activity.activityName.toLowerCase()}`,
    title: `${activity.activityName} - ${activity.duration}min`,
    timestamp: `${activity.startDate}T${activity.startTime}`,
    metadata: {
      calories: activity.calories,
      steps: activity.steps,
      heartRateZones: activity.heartRateZones,
      distance: activity.distance,
    },
    raw: activity,
  };
}

完整的 ETL 管道实现
将上述组件组合为生产级管道：


class PersonalDataPipeline {
  private db: Database;
  private clients: Map<string, RateLimitedClient>;
  private extractors: Map<string, DataExtractor>;

  async syncProvider(provider: string): Promise<SyncResult> {
    const state = await this.loadSyncState(provider);
    const client = this.clients.get(provider)!;
    const extractor = this.extractors.get(provider)!;

    try {
      // Extract
      const rawData = await extractor.extract(client, state.cursor);

      // Transform
      const normalized = rawData.items.map((item) => extractor.normalize(item));

      // Load
      await this.db.transaction(async (tx) => {
        for (const event of normalized) {
          await tx.run(
            `INSERT OR REPLACE INTO events 
             (id, source, type, title, timestamp, metadata, raw)
             VALUES (?, ?, ?, ?, ?, ?, ?)`,
            [
              event.id,
              event.source,
              event.type,
              event.title,
              event.timestamp,
              JSON.stringify(event.metadata),
              JSON.stringify(event.raw),
            ],
          );
        }
        // 更新游标
        await tx.run(
          `UPDATE sync_state SET cursor = ?, last_sync_at = ?,
           total_synced = total_synced + ?, consecutive_errors = 0
           WHERE provider = ?`,
          [rawData.nextCursor, new Date().toISOString(), normalized.length, provider],
        );
      });

      return { success: true, count: normalized.length };
    } catch (error) {
      await this.recordError(provider, error);
      throw error;
    }
  }
}

错误处理分级策略
enum ErrorSeverity {
  TRANSIENT = 'transient', // 网络超时、5xx -> 自动重试
  RATE_LIMIT = 'rate_limit', // 429 -> 等待后重试
  AUTH_EXPIRED = 'auth', // 401 -> 刷新 Token
  PERMANENT = 'permanent', // 403/404 -> 需人工介入
}

function classifyError(status: number, error: Error): ErrorSeverity {
  if (status === 429) return ErrorSeverity.RATE_LIMIT;
  if (status === 401) return ErrorSeverity.AUTH_EXPIRED;
  if (status >= 500) return ErrorSeverity.TRANSIENT;
  if (status === 403 || status === 404) return ErrorSeverity.PERMANENT;
  if (error.message.includes('ECONNRESET')) return ErrorSeverity.TRANSIENT;
  return ErrorSeverity.PERMANENT;
}

总结
多源数据聚合是个人数据基础设施的入口层。核心挑战不在于"如何调用 API"，而在于如何可靠地、持续地、安全地管理数十个平台的授权状态和数据同步。关键要点：


    

  1. Token 生命周期管理是基础中的基础——主动刷新、并发安全、安全存储三位一体
    2. 

  2. 限流处理必须是客户端级别的第一公民——不是 catch 之后打日志，而是预判式等待
    3. 

  3. 数据归一化在写入时完成——统一 Schema 让下游查询和关联分析成为可能
    4. 

  4. 增量同步 + 幂等写入——cursor 机制 + UPSERT 保证重复运行不产生脏数据
    5. 

  5. 错误分级决定处理策略——瞬态错误自动重试，永久错误报警通知
    6. 



建好这一层，后续的 Webhook 管道和 Personal API 才有干净的数据源可以消费。
