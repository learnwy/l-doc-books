API 连接器开发

概述

即便 n8n 有 500+ 内置节点、Zapier 有 7000+ 集成，你依然会遇到需要对接的服务不在支持列表中的情况——内部 API、小众 SaaS、自建微服务、或者现有集成功能不够细致。这时你需要开发自定义 API 连接器。

API 连接器是自动化体系的"长尾能力"——它决定了你的自动化边界能扩展到多远。本文将从 HTTP 基础出发，覆盖 OAuth 认证封装、Webhook 设计、错误处理策略和各平台的连接器开发规范。

核心概念

连接器架构模型

一个完整的 API 连接器需要处理四个层面的问题：

层面 职责 关键挑战
认证层 身份验证与令牌管理 OAuth 刷新、API Key 存储
请求层 构造和发送 HTTP 请求 参数序列化、Content-Type
响应层 解析和转换响应数据 分页、嵌套结构展平
错误层 异常检测与恢复策略 重试、降级、速率限制

认证模式分类

模式 复杂度 适用场景 安全性
API Key（Header/Query） 低 内部服务、简单 API 中
Bearer Token 低 已有 Token 的服务 中
Basic Auth 低 传统服务 低
OAuth 2.0 (Authorization Code) 高 第三方 SaaS 高
OAuth 2.0 (Client Credentials) 中 服务间通信 高
Webhook Signature 中 接收回调验证 高

Webhook 架构

Webhook 是从"轮询"到"推送"的范式转变——服务主动通知你的自动化系统：

传统轮询模式（浪费资源）：
你的系统 →[每分钟查询]→ 外部API → "没有新数据"
你的系统 →[每分钟查询]→ 外部API → "没有新数据"
你的系统 →[每分钟查询]→ 外部API → "有新数据！"

Webhook 推送模式（高效）：
外部API →[事件发生]→ POST /your-webhook → 立即处理

实战指南

n8n 自定义节点开发

n8n 允许通过社区节点系统开发完全自定义的集成：

// nodes/MyApi/MyApi.node.ts
import { INodeType, INodeTypeDescription } from 'n8n-workflow';

export class MyApi implements INodeType {
  description: INodeTypeDescription = {
    displayName: 'My Custom API',
    name: 'myApi',
    group: ['transform'],
    version: 1,
    description: 'Interact with My Custom API',
    defaults: { name: 'My API' },
    inputs: ['main'],
    outputs: ['main'],
    credentials: [{ name: 'myApiCredentials', required: true }],
    properties: [
      {
        displayName: 'Operation',
        name: 'operation',
        type: 'options',
        options: [
          { name: 'Get Record', value: 'get' },
          { name: 'Create Record', value: 'create' },
          { name: 'List Records', value: 'list' },
        ],
        default: 'get',
      },
      {
        displayName: 'Record ID',
        name: 'recordId',
        type: 'string',
        default: '',
        displayOptions: {
          show: { operation: ['get'] },
        },
      },
    ],
  };

  async execute(this: IExecuteFunctions) {
    const items = this.getInputData();
    const operation = this.getNodeParameter('operation', 0);
    const credentials = await this.getCredentials('myApiCredentials');
    const results = [];

    for (let i = 0; i < items.length; i++) {
      if (operation === 'get') {
        const id = this.getNodeParameter('recordId', i) as string;
        const response = await this.helpers.httpRequest({
          method: 'GET',
          url: `${credentials.baseUrl}/records/${id}`,
          headers: { Authorization: `Bearer ${credentials.apiKey}` },
        });
        results.push({ json: response });
      }
    }
    return [results];
  }
}

Webhook 监听器设计

在 n8n 中创建自定义 Webhook 端点接收外部事件：

// n8n Webhook 节点 + Function 节点处理签名验证
const crypto = require('crypto');

// 获取请求数据
const body = $input.first().json.body;
const signature = $input.first().json.headers['x-webhook-signature'];
const secret = $env.WEBHOOK_SECRET;

// HMAC 签名验证
const expectedSignature = crypto.createHmac('sha256', secret).update(JSON.stringify(body)).digest('hex');

if (signature !== `sha256=${expectedSignature}`) {
  throw new Error('Invalid webhook signature');
}

// 签名验证通过，继续处理
return [{ json: body }];

分页处理模式

大多数 API 使用分页返回数据，连接器需要自动处理：

// n8n Function 节点：自动分页获取所有记录
const allRecords = [];
let page = 1;
let hasMore = true;

while (hasMore) {
  const response = await $http.request({
    method: 'GET',
    url: 'https://api.example.com/records',
    qs: { page, per_page: 100 },
    headers: { Authorization: `Bearer ${$credentials.apiKey}` },
  });

  allRecords.push(...response.data);
  hasMore = response.meta.has_next_page;
  page++;

  // 防止无限循环
  if (page > 100) break;
  // 速率限制保护
  await new Promise((r) => setTimeout(r, 200));
}

return allRecords.map((record) => ({ json: record }));

错误处理策略

采用分级错误处理：

HTTP 状态 策略 说明
429 指数退避重试 等待 Retry-After 头指定的时间
500-503 固定间隔重试 最多重试 3 次
401 刷新令牌后重试 OAuth Token 过期
400 立即失败 请求参数错误，重试无意义
404 立即失败 资源不存在 
async function requestWithRetry(config, maxRetries = 3) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await $http.request(config);
    } catch (error) {
      const status = error.response?.status;
      if (status === 429) {
        const retryAfter = error.response.headers['retry-after'] || 60;
        await new Promise((r) => setTimeout(r, retryAfter * 1000));
      } else if (status >= 500 && attempt < maxRetries) {
        await new Promise((r) => setTimeout(r, Math.pow(2, attempt) * 1000));
      } else {
        throw error;
      }
    }
  }
}

数据映射规范

  • 字段命名统一：将外部 API 的 camelCase/snake_case 统一转换为内部规范
  • 日期标准化：所有日期转为 ISO 8601 格式
  • 空值处理：明确区分 null、undefined、空字符串的语义
  • 类型安全：验证响应数据类型是否符合预期

速率限制管理

// 令牌桶算法的简单实现
class RateLimiter {
  constructor(maxTokens, refillRate) {
    this.tokens = maxTokens;
    this.maxTokens = maxTokens;
    this.refillRate = refillRate; // tokens per second
    this.lastRefill = Date.now();
  }

  async acquire() {
    this.refill();
    if (this.tokens <= 0) {
      const waitTime = (1 / this.refillRate) * 1000;
      await new Promise((r) => setTimeout(r, waitTime));
      this.refill();
    }
    this.tokens--;
  }

  refill() {
    const now = Date.now();
    const elapsed = (now - this.lastRefill) / 1000;
    this.tokens = Math.min(this.maxTokens, this.tokens + elapsed * this.refillRate);
    this.lastRefill = now;
  }
}

测试策略

  • 单元测试：Mock HTTP 响应测试数据转换逻辑
  • 集成测试：用沙箱环境验证完整认证流程
  • 契约测试：确保连接器兼容 API 版本变更
  • Webhook 测试：用 curl 或 Postman 模拟事件推送

总结

API 连接器开发是将自动化边界从"现有集成目录"扩展到"任何有 API 的服务"的关键能力。核心要点：

  1. 认证层是连接器最复杂的部分——优先支持 OAuth 2.0 以覆盖大多数现代 SaaS
  2. 自动分页和速率限制是生产环境的必备处理
  3. 错误处理采用分级策略——不是所有错误都应该重试
  4. Webhook 优于轮询——节省资源且实时性更好
  5. 从 OpenAPI/Swagger 规范出发能大幅加速开发
  6. 签名验证是 Webhook 安全的底线——永远不要跳过
