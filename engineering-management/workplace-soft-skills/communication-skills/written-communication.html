书面沟通

书面沟通是远程和混合办公时代的核心协作方式。与口头沟通不同，书面内容会被永久记录、广泛传播、反复引用——这意味着写得好可以成倍放大你的影响力，写得差则可能造成持久的误解。对于工程师来说，从邮件到 Slack 消息、从技术文档到 RFC，每一种书面形式都是你专业能力和职业形象的延伸。

邮件写作的 5C 原则




原则
说明
示例





Clear（清晰）
避免歧义，一个邮件一个主题
不在同一封邮件中讨论三件不相关的事




Concise（简洁）
能三句话说清就不写五段
使用要点列表而非大段文字




Complete（完整）
包含所有必要信息
避免来回追问"那个文件在哪？"




Courteous（礼貌）
尊重对方时间
"感谢你的快速回复"而非理所当然




Correct（准确）
事实和数据要核实
发送前检查附件、链接、数据





不同场景的邮件模板
场景 1：请求技术决策


主题：[需要决策] 缓存层技术选型 - Redis vs Memcached

TL;DR：建议选择 Redis，原因是我们需要持久化和丰富数据结构。
请各位在本周五前回复意见。

背景：
用户会话缓存目前直接读数据库，P99 延迟已达 800ms，
需要引入缓存层。

方案对比：
• Redis：支持持久化、数据结构丰富、可做消息队列
• Memcached：更简单、纯内存、略高的读取性能

推荐 Redis 的理由：
1. 排行榜功能需要 Sorted Set
2. 会话数据需要持久化以应对重启
3. 后续消息队列可复用

行动项：
• @张三 @李四 请在周五前回复意见或 +1
• 如无反对意见，周一开始实施

异步沟通的黄金法则




法则
说明





一条消息说完
不要分多条发送碎片信息，组织好再发




给上下文
不要假设对方记得之前的讨论，提供必要背景




明确期望
"这周五前需要你的反馈"而非"有空看看"

非紧急事项不 @，紧急事项才使用通知

小结
    

  • 邮件写作遵循 5C 原则，主题行标注类型和期望行动，TL;DR 确保核心信息不被遗漏。
    • 

  • Slack 沟通的核心是减少打断、一条消息说完、善用线程、明确响应时间预期。
    • 

  • 技术文档以读者为中心，倒金字塔结构确保最重要的信息最先被看到。
    • 

  • 异步沟通需要团队建立共同的沟通合约，定义响应时间和升级规则。
    • 

  • 书面沟通中的语气容易被放大解读，有意识地增加温和措辞能避免不必要的冲突。
