Part IV · 领导 (Leading)工程管理 简介项目管理 简介评估与规划

评估与规划

核心概念

评估与规划是项目管理的基石。好的评估不是精确预测未来，而是建立合理的期望、识别风险、做出明智的决策。规划也不是制定一成不变的计划，而是持续调整、适应变化的过程。

为什么评估和规划困难

挑战 说明
不确定性 软件开发充满未知
范围模糊 需求不清晰，边界不明确
技术未知 可能遇到未预见的技术难点
人员因素 团队能力、效率、协作方式不同
外部依赖 第三方服务、API、团队协作
变化 需求、优先级、环境都可能变化

评估的目标

评估不是为了"得到正确答案"，而是为了：

  1. 建立合理的期望：让利益相关者理解范围、时间、成本的关系
  2. 识别风险：提前发现不确定性和潜在问题
  3. 做出决策：基于信息选择优先级、权衡取舍
  4. 规划资源：合理分配人力、时间、预算
  5. 跟踪进展：有基准可以对比实际和计划

评估方法

1. 专家判断（Expert Judgment）

定义： 依靠有经验的团队成员或专家进行估算。

适用场景：

  • 快速估算，不需要高精度
  • 类似项目做过很多
  • 专家对领域非常熟悉

优点：

  • 快速、灵活
  • 利用经验和直觉
  • 不需要太多数据

缺点：

  • 主观，依赖个人
  • 容易受偏见影响
  • 不可重复

最佳实践：

  • 多个专家独立估算，然后取平均值或讨论
  • 让专家解释估算的理由
  • 记录假设和推理过程
  • 对比历史数据验证

2. 类比估算（Analogous Estimating）

定义： 参考类似项目的实际数据进行估算。

适用场景：

  • 有类似项目的历史数据
  • 新项目与历史项目相似
  • 需要快速、粗略的估算

优点：

  • 基于实际数据，而非猜测
  • 相对准确（如果项目相似）
  • 快速、低成本

缺点：

  • 需要类似项目的数据
  • 如果项目不相似，误差很大
  • 不考虑项目间的差异

如何做好类比估算：

步骤 1：选择类比项目

  • 选择最相似的 2-3 个项目
  • 考虑：技术栈、团队规模、复杂度、领域
  • 记录相似点和不同点

步骤 2：收集历史数据

  • 实际工作量（人天、人月）
  • 实际工期
  • 遇到的问题和返工
  • 最终范围 vs 初始范围

步骤 3：调整差异

  • 识别新项目与类比项目的差异
  • 量化差异的影响（+/- X%）
  • 说明调整的理由

示例：

interface AnalogousEstimate {
  referenceProject: {
    name: string;
    actualEffort: number; // 人天
    actualDuration: number; // 天
    scope: string;
  };
  newProject: {
    scope: string;
    differences: Difference[];
  };
  adjustments: Adjustment[];
  finalEstimate: {
    effort: number;
    duration: number;
    confidence: number; // 0-1
  };
}

// 示例：
// 参考项目 A：电商后台，100 人天，60 天
// 新项目：电商后台 + 新支付模块
// 调整：+20%（新支付模块），+10%（新团队）
// 最终估算：100 * 1.3 = 130 人天

3. 参数估算（Parametric Estimating）

定义： 使用统计模型或参数公式进行估算。

适用场景：

  • 有大量历史数据
  • 工作可以标准化
  • 参数与工作量有强相关性

优点：

  • 客观、可重复
  • 基于数据和统计
  • 可以快速调整参数

缺点：

  • 需要大量历史数据
  • 模型可能不准确
  • 不适合创新性工作

常见参数模型：

功能点（Function Points）：

  • 基于功能数量和复杂度
  • 适合业务应用
  • 需要专门的培训和工具

用例点（Use Case Points）：

  • 基于用例数量和复杂度
  • 适合面向对象项目
  • 考虑技术和环境因素

故事点（Story Points）：

  • 相对估算，基于复杂度
  • 敏捷团队常用
  • 需要团队校准

代码行数（LOC）：

  • 基于历史代码行数
  • 简单但有争议
  • 容易受编码风格影响

4. 三点估算（Three-Point Estimating）

定义： 使用最乐观、最可能、最悲观三个值进行估算。

适用场景：

  • 不确定性高的工作
  • 需要量化风险
  • 想要更稳健的估算

公式：

三角分布（简单平均）：

期望值 = (O + M + P) / 3

Beta 分布（PERT 加权平均）：

期望值 = (O + 4M + P) / 6
标准差 = (P - O) / 6

其中：

  • O (Optimistic)：最乐观情况，一切顺利
  • M (Most Likely)：最可能情况，正常进行
  • P (Pessimistic)：最悲观情况，遇到各种问题

为什么 Beta 分布？

  • 最可能情况的权重更高（4 倍）
  • 更接近实际情况
  • 来自 PERT（计划评审技术）

示例：

interface ThreePointEstimate {
  task: string;
  optimistic: number; // 人天
  mostLikely: number; // 人天
  pessimistic: number; // 人天
  expected: number; // (O + 4M + P) / 6
  standardDeviation: number; // (P - O) / 6
}

// 示例：
// 任务：开发用户认证模块
// O: 5 人天（一切顺利，没有问题）
// M: 10 人天（正常情况，有小问题）
// P: 20 人天（遇到技术难点，需要返工）
// Expected: (5 + 4*10 + 20) / 6 = 65 / 6 ≈ 10.8 人天
// SD: (20 - 5) / 6 = 2.5 人天
// 结果：10.8 ± 2.5 人天

如何使用标准差：

  • ±1 SD：68% 的概率在此范围内
  • ±2 SD：95% 的概率在此范围内
  • ±3 SD：99.7% 的概率在此范围内

示例解释：

  • 68% 概率：8.3 - 13.3 人天
  • 95% 概率：5.8 - 15.8 人天
  • 99.7% 概率：3.3 - 18.3 人天

5. 自下而上估算（Bottom-Up Estimating）

定义： 将工作分解为小任务，估算每个小任务，然后汇总。

适用场景：

  • 范围清晰，可以详细分解
  • 需要高精度
  • 团队参与估算

优点：

  • 准确度高（如果分解合理）
  • 团队参与，认同度高
  • 详细，可以用于跟踪

缺点：

  • 耗时，需要详细分解
  • 容易遗漏工作
  • 不适合早期阶段

步骤：

  1. 分解工作：使用 WBS 分解到可估算的小任务
  2. 估算任务：每个任务由负责人估算
  3. 汇总：将所有任务的估算相加
  4. 验证：检查是否合理，与其他方法对比

任务分解的原则：

  • 每个任务 1-5 天（可管理）
  • 明确的负责人
  • 清晰的完成标准
  • 可以独立交付

6. Planning Poker（计划扑克）

定义： 团队成员独立估算，然后讨论差异，达成共识。

适用场景：

  • 敏捷团队
  • 相对估算（故事点）
  • 团队参与和共识

流程：

  1. 准备：

    • 一副扑克牌（0, 0.5, 1, 2, 3, 5, 8, 13, 20, 40, 100, ?, ☕）
    • 待估算的 Backlog 条目

  2. 讲解需求：

    • Product Owner 讲解需求
    • 团队提问，澄清疑问
    • 讨论验收标准

  3. 独立估算：

    • 每个人独立选择一张牌
    • 不要讨论，不要看别人

  4. 同时亮牌：

    • 所有人同时亮牌
    • 不要解释，先看结果

  5. 讨论差异：

    • 如果估算一致，接受
    • 如果差异大，请最高和最低的人解释
    • 讨论假设和理由

  6. 重新估算：

    • 基于讨论，重新选择
    • 重复直到达成共识（或接近）

牌的含义：

  • 0： trivial，几乎不需要时间
  • 0.5, 1, 2, 3, 5, 8, 13：斐波那契数列，相对大小
  • 20, 40, 100：大的，可能需要分解
  • ?：不确定，需要更多信息
  • ☕：需要休息，讨论太久了

为什么斐波那契数列？

  • 反映不确定性：大的任务不确定性更高
  • 避免虚假精度：不使用 11, 12 这种精确数字
  • 相对估算：关注相对大小，而非绝对时间

最佳实践：

  • 限时讨论（每轮 2-3 分钟）
  • 如果多次无法达成一致，取中间值或分解任务
  • 定期校准（回顾实际 vs 估算）
  • 记住：故事点是相对的，不是绝对的

7. 亲和估算（Affinity Mapping）

定义： 将 Backlog 条目分组，与已知大小的条目对比。

适用场景：

  • 大量条目需要快速估算
  • 团队刚成立，需要建立基准
  • 相对估算

流程：

  1. 准备基准：

    • 选择几个已知大小的条目作为基准
    • 标记为 Small（1）、Medium（2）、Large（3）等
    • 贴在墙上或白板上

  2. 分组：

    • 团队成员将待估算的条目贴到相应的组
    • 如果有分歧，讨论
    • 不需要精确，快速分组

  3. 分配点数：

    • 给每个组分配故事点
    • Small: 1, Medium: 2, Large: 3, Extra Large: 5
    • 或者使用斐波那契数列

优点：

  • 快速，适合大量条目
  • 团队参与
  • 建立共同的理解

规划实践

Work Breakdown Structure (WBS)

定义： 将项目分解为可管理的小任务的层次结构。

为什么 WBS 重要？

  • 确保没有遗漏工作
  • 使工作可估算、可分配、可跟踪
  • 清晰的责任边界
  • 更好的进度管理

WBS 原则：

  1. 100% 规则：

    • WBS 包含所有工作
    • 没有遗漏，也没有多余
    • 下一级的和等于上一级

  2. 相互独立：

    • 工作包之间没有重叠
    • 清晰的边界
    • 避免重复计算

  3. 可管理：

    • 每个工作包可以分配给一个人或团队
    • 有明确的完成标准
    • 可以估算和跟踪

  4. 面向交付：

    • 关注交付什么，而不是如何做
    • 以产品为导向
    • 不是活动列表

WBS 示例：

电商网站项目
├─ 用户系统
│  ├─ 用户注册
│  ├─ 用户登录
│  └─ 用户信息管理
├─ 商品系统
│  ├─ 商品展示
│  ├─ 商品搜索
│  └─ 商品管理（后台）
├─ 购物车
│  ├─ 添加商品
│  ├─ 修改数量
│  └─ 删除商品
├─ 订单系统
│  ├─ 创建订单
│  ├─ 支付集成
│  └─ 订单管理
└─ 后台系统
   ├─ 数据分析
   ├─ 库存管理
   └─ 系统设置

WBS vs 活动列表：

WBS 活动列表
面向交付（What） 面向活动（How）
层次结构 线性列表
关注结果 关注过程
适合规划和跟踪 适合执行

里程碑（Milestones）

定义： 项目中的关键检查点，标记重要阶段的完成。

为什么里程碑重要？

  • 提供可见的进展
  • 建立信心和动力
  • 检查点，可以调整计划
  • 对齐利益相关者

好的里程碑的特征：

  • 具体、可验证
  • 有明确的完成标准
  • 有时间点
  • 与业务价值相关

关键路径法（Critical Path Method, CPM）
定义： 识别项目中最长的任务序列，决定项目最短工期。


为什么关键路径重要？


    

  • 知道什么决定项目工期
    • 

  • 优先关注关键任务
    • 

  • 识别可以并行的工作
    • 

  • 合理安排资源
    • 



关键路径的特征：


    

  • 最长的路径（总工期）
    • 

  • 没有浮动时间（Slack = 0）
    • 

  • 任何延迟都会影响项目工期
    • 

  • 需要重点关注和管理
    • 



如何计算关键路径：


    

  1. 绘制网络图：
    

      

    • 节点表示任务
      • 

    • 箭头表示依赖关系
      • 

    • 标注每个任务的工期
      • 

    

    2. 

  2. 正向计算（Early Start/Early Finish）：
    

      

    • 从左到右
      • 

    • ES = max(所有前置任务的 EF)
      • 

    • EF = ES + 工期
      • 

    

    3. 

  3. 反向计算（Late Start/Late Finish）：
    

      

    • 从右到左
      • 

    • LF = min(所有后续任务的 LS)
      • 

    • LS = LF - 工期
      • 

    

    4. 

  4. 计算浮动时间（Slack/Float）：
    

      

    • Slack = LS - ES 或 LF - EF
      • 

    • Slack = 0 的任务在关键路径上
      • 

    

    5. 



示例：


interface Task {
  id: string;
  name: string;
  duration: number; // 天
  dependencies: string[];
  es?: number; // Early Start
  ef?: number; // Early Finish
  ls?: number; // Late Start
  lf?: number; // Late Finish
  slack?: number;
  isCritical?: boolean;
}

// 示例任务：
// A: 需求分析, 5天, 无依赖
// B: 设计, 3天, 依赖A
// C: 前端开发, 8天, 依赖B
// D: 后端开发, 10天, 依赖B
// E: 测试, 4天, 依赖C和D
// F: 部署, 2天, 依赖E

// 关键路径: A → B → D → E → F
// 总工期: 5 + 3 + 10 + 4 + 2 = 24天
// C有2天浮动时间（10-8=2）
如何使用关键路径：


    

  1. 缩短工期：
    

      

    • 只有关键路径上的任务能缩短总工期
      • 

    • 可以并行关键任务
      • 

    • 可以增加资源（Crashing）
      • 

    • 可以调整范围（Fast Tracking）
      • 

    

    2. 

  2. 风险管理：
    

      

    • 关键任务风险更高
      • 

    • 重点关注关键任务
      • 

    • 准备应急预案
      • 

    

    3. 

  3. 资源管理：
    

      

    • 优先保证关键任务资源
      • 

    • 非关键任务可以灵活安排
      • 

    • 利用浮动时间平衡资源
      • 

    

    4. 





缓冲时间（Buffer/Contingency）
定义： 为不确定性预留的额外时间。


为什么需要缓冲？


    

  • 软件开发充满不确定性
    • 

  • 估算不准确
    • 

  • 可能遇到未预见的问题
    • 

  • 范围可能蔓延
    • 



缓冲的类型：


    

  1. 项目缓冲（Project Buffer）：
    

      

    • 在项目末尾预留
      • 

    • 保护整个项目工期
      • 

    • 通常 10-20% 的总工期
      • 

    

    2. 

  2. 关键链缓冲（Critical Chain Buffer）：
    

      

    • 在关键路径末端
      • 

    • 保护关键链
      • 

    • 基于关键链的不确定性
      • 

    

    3. 

  3. 接驳缓冲（Feeding Buffer）：
    

      

    • 在非关键路径汇入关键路径处
      • 

    • 保护关键路径不受非关键路径影响
      • 

    • 基于汇入路径的不确定性
      • 

    

    4. 

  4. 资源缓冲（Resource Buffer）：
    

      

    • 预留资源能力
      • 

    • 应对资源不确定性
      • 

    • 例如：预留部分人力时间
      • 

    

    5. 



多少缓冲合适？


考虑因素：


    

  • 不确定性程度：高不确定性需要更多缓冲
    • 

  • 项目重要性：重要项目需要更多缓冲
    • 

  • 团队经验：经验少需要更多缓冲
    • 

  • 历史数据：有数据可以更精确
    • 

  • 风险承受能力：保守型需要更多缓冲
    • 



常见范围：


    

  • 低风险：5-10%
    • 

  • 中等风险：10-20%
    • 

  • 高风险：20-30%+
    • 



如何管理缓冲：


    

  1. 不要提前使用：
    

      

    • 缓冲是应对不确定性的
      • 

    • 不要用缓冲来填充宽松的估算
      • 

    • 保留到真正需要时
      • 

    

    2. 

  2. 监控缓冲使用：
    

      

    • 跟踪缓冲消耗速度
      • 

    • 提前预警
      • 

    • 及时调整
      • 

    

    3. 

  3. 缓冲用完时：
    

      

    • 重新评估风险
      • 

    • 调整范围或时间
      • 

    • 与利益相关者沟通
      • 

    

    4. 



常见估算陷阱
陷阱 1：过度乐观（Optimism Bias）
表现：


    

  • 低估工作量
    • 

  • 忽视风险
    • 

  • 假设一切顺利
    • 

  • "这次会不一样"
    • 



原因：


    

  • 计划谬误（Planning Fallacy）
    • 

  • 过度自信
    • 

  • 只考虑最好情况
    • 

  • 忽视历史教训
    • 



应对：


    

  • 使用三点估算（考虑悲观情况）
    • 

  • 参考历史数据
    • 

  • 外部评审
    • 

  • 建立"悲观主义者"角色
    • 





陷阱 2：锚定效应（Anchoring）
表现：


    

  • 被第一个数字影响
    • 

  • 不独立思考
    • 

  • "别人说 3 个月，那就 3 个月吧"
    • 



原因：


    

  • 认知偏差
    • 

  • 不愿挑战权威
    • 

  • 害怕冲突
    • 



应对：


    

  • 先独立估算，再讨论
    • 

  • 使用 Planning Poker（同时亮牌）
    • 

  • 询问理由，不只是数字
    • 

  • 多个来源的数据
    • 





陷阱 3：范围蔓延（Scope Creep）
表现：


    

  • 初始范围小，后来越来越大
    • 

  • "就加这一个小功能"
    • 

  • 没有相应调整时间和资源
    • 



原因：


    

  • 需求不清晰
    • 

  • 没有变更控制
    • 

  • 客户或利益相关者不断加需求
    • 

  • 团队不好意思拒绝
    • 



应对：


    

  • 清晰的范围定义和验收标准
    • 

  • 变更控制流程
    • 

  • "Yes, and..."（可以，但需要调整时间/资源）
    • 

  • 优先级排序
    • 





陷阱 4：不切实际的截止日期（Imposed Deadline）
表现：


    

  • 截止日期先定，然后倒推范围
    • 

  • "6 月必须上线，不管怎样"
    • 

  • 没有协商空间
    • 



原因：


    

  • 业务压力
    • 

  • 不理解软件开发
    • 

  • 过去的成功（但条件不同）
    • 

  • 政治因素
    • 



应对：


    

  • 用数据和事实说话
    • 

  • 明确范围、时间、质量的权衡
    • 

  • 分阶段交付（MVP first）
    • 

  • 管理期望，教育利益相关者
    • 





陷阱 5：忽略风险（Ignoring Risks）
表现：


    

  • "不会有问题的"
    • 

  • 不识别风险
    • 

  • 不准备应急预案
    • 



原因：


    

  • 过度乐观
    • 

  • 没有风险管理习惯
    • 

  • 害怕承认不确定性
    • 



应对：


    

  • 正式的风险管理流程
    • 

  • 风险识别会议
    • 

  • 预留缓冲
    • 

  • 准备应急预案
    • 





陷阱 6：为了估算而估算（Estimation Theatre）
表现：


    

  • 花费大量时间估算
    • 

  • 追求虚假的精度
    • 

  • 估算后就扔在一边
    • 

  • 不跟踪实际 vs 估算
    • 



原因：


    

  • 误解估算的目的
    • 

  • 形式主义
    • 

  • 没有反馈循环
    • 



应对：


    

  • 记住：估算的目的是决策，不是精确预测
    • 

  • 按需投入时间（早期粗略，后期详细）
    • 

  • 跟踪实际 vs 估算
    • 

  • 持续改进估算方法
    • 



估算的最佳实践
1. 多个方法，交叉验证
不要依赖单一方法：


    

  • 使用 2-3 种不同方法
    • 

  • 对比结果
    • 

  • 理解差异的原因
    • 

  • 综合判断
    • 



示例组合：


    

  • 类比估算 + 三点估算
    • 

  • Planning Poker + 自下而上
    • 

  • 专家判断 + 历史数据
    • 





2. 团队参与
为什么团队参与重要？


    

  • 团队最了解工作
    • 

  • 认同度更高
    • 

  • 知识共享
    • 

  • 更好的质量
    • 



如何让团队参与：


    

  • Planning Poker
    • 

  • 自下而上估算
    • 

  • 让负责人估算自己的任务
    • 

  • 讨论和共识
    • 





3. 明确假设
记录假设：


    

  • 范围假设
    • 

  • 技术假设
    • 

  • 资源假设
    • 

  • 依赖假设
    • 



为什么重要：


    

  • 假设变化时，重新评估
    • 

  • 理解估算的前提
    • 

  • 沟通期望
    • 

  • 追溯原因
    • 





4. 表达不确定性
不要给单一数字：


    

  • 给出范围（8-12 周）
    • 

  • 给出置信度（80% 概率 10 周内）
    • 

  • 给出乐观/悲观
    • 

  • 说明风险
    • 



示例：


    

  • ❌ "10 周"
    • 

  • ✅ "8-12 周，置信度 80%。主要风险是第三方 API 集成，如果不顺利可能需要额外 2 周。"
    • 





5. 跟踪和反馈
建立反馈循环：


    

  • 记录估算
    • 

  • 跟踪实际结果
    • 

  • 对比分析
    • 

  • 持续改进
    • 



回顾问题：


    

  • 估算准确吗？
    • 

  • 为什么有差异？
    • 

  • 什么假设错了？
    • 

  • 下次如何改进？
    • 





6. 渐进明细（Progressive Elaboration）
不是一次估算完成：


    

  • 早期：粗略估算（±50%）
    • 

  • 需求明确后：中等精度（±25%）
    • 

  • 设计完成后：详细估算（±10%）
    • 

  • 执行中：持续调整
    • 



为什么？


    

  • 早期信息少
    • 

  • 不要浪费时间在不确定的事情上
    • 

  • 随着信息增加，估算更精确
    • 



规划不是一次性的
滚动规划（Rolling Wave Planning）
定义： 近期详细规划，远期粗略规划。


示例：


    

  • Sprint 1：详细到天
    • 

  • Sprint 2：详细到任务
    • 

  • Sprint 3-4：粗略到功能
    • 

  • 之后：只有 Epic
    • 



优点：


    

  • 不浪费时间在不确定的事情上
    • 

  • 随着信息增加，逐步细化
    • 

  • 适应变化
    • 





调整和重规划
计划不是一成不变的：


    

  • 定期回顾（每周/每月）
    • 

  • 识别偏差
    • 

  • 分析原因
    • 

  • 调整计划
    • 



触发重规划的情况：


    

  • 范围重大变化
    • 

  • 关键风险发生
    • 

  • 进度严重偏差
    • 

  • 优先级变化
    • 





沟通变化
及时沟通：


    

  • 不要隐瞒
    • 

  • 解释原因
    • 

  • 说明影响
    • 

  • 共同决策
    • 



沟通原则：


    

  • 透明
    • 

  • 及时
    • 

  • 具体
    • 

  • 建设性
    • 



小结
评估与规划是项目管理的核心技能，但要记住：估算不是预言，规划不是枷锁。


核心要点回顾：


    

  • 评估的目的是决策，不是精确预测
    • 

  • 使用多种方法，交叉验证
    • 

  • 团队参与，共识更重要
    • 

  • 明确假设，表达不确定性
    • 

  • 三点估算考虑乐观、可能、悲观
    • 

  • WBS 确保没有遗漏工作
    • 

  • 关键路径决定项目工期
    • 

  • 缓冲应对不确定性
    • 

  • 避免常见陷阱：过度乐观、锚定效应、范围蔓延
    • 

  • 渐进明细，滚动规划
    • 

  • 跟踪实际 vs 估算，持续改进
    • 

  • 计划不是一成不变的，要适应变化
    •
