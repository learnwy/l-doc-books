Agile、Scrum 与 Kanban

核心概念

Agile（敏捷）是一种思维方式和价值观，Scrum 和 Kanban 是实现敏捷的两种常用框架。敏捷不是"快速做"，而是"快速学习"和"快速适应"。

敏捷的历史背景

2001 年，敏捷宣言（Agile Manifesto）：

17 位软件开发者在犹他州 Snowbird 聚会，总结了他们共同认同的价值观：

四条核心价值观：

  • 个体和互动 高于 流程和工具
  • 可工作的软件 高于 详尽的文档
  • 客户合作 高于 合同谈判
  • 响应变化 高于 遵循计划

十二条原则：

  1. 我们最重要的目标，是通过持续不断地及早交付有价值的软件使客户满意。
  2. 欣然面对需求变化，即使在开发后期也一样。敏捷过程利用变化为客户创造竞争优势。
  3. 经常性地交付可以工作的软件，交付的间隔可以从几周到几个月，越短越好。
  4. 业务人员和开发人员必须天天在一起工作，直到项目结束。
  5. 围绕被激励起来的个人来构建项目。给他们提供所需要的环境和支持，并且信任他们能够完成工作。
  6. 在团队内部，最有效果和最有效率的传递信息的方法，就是面对面的交谈。
  7. 可工作的软件是进度的首要度量标准。
  8. 敏捷过程倡导可持续发展。责任人、开发人员和用户要能够共同维持其步调稳定延续。
  9. 坚持不懈地追求技术卓越和良好设计，敏捷能力由此增强。
  10. 以简洁为本，它是极力减少不必要工作量的艺术。
  11. 最好的架构、需求和设计出自自组织团队。
  12. 团队定期地反思如何能提高成效，并依此调整自身的举止表现。


Scrum
Scrum 概述
Scrum 是一个轻量级的框架，用于开发和维护复杂产品。


Scrum 的三个支柱（ empiricism，经验主义）：


    

  1. 透明（Transparency）：过程和结果可见
    2. 

  2. 检查（Inspection）：定期检查进展和成果
    3. 

  3. 适应（Adaptation）：根据检查结果调整
    4. 



Scrum 的价值观：


    

  • 承诺（Commitment）：对目标的承诺
    • 

  • 专注（Focus）：专注于 Sprint 目标
    • 

  • 开放（Openness）：开放沟通
    • 

  • 尊重（Respect）：互相尊重
    • 

  • 勇气（Courage）：做正确的事
    •

核心职责：


    

  • 代表客户和利益相关者
    • 

  • 定义产品愿景和路线图
    • 

  • 维护 Product Backlog
    • 

  • 优先级排序
    • 

  • 验收产品增量
    • 

  • 最大化产品价值
    • 



Product Backlog 管理：


    

  • 清晰描述 Backlog 条目
    • 

  • 优先级排序（基于价值、风险、依赖）
    • 

  • 添加细节（验收标准、规模估算）
    • 

  • 确保团队理解
    • 

  • 定期调整和更新
    •

Product Owner 的一天：


    

  • 上午：与利益相关者沟通，整理需求
    • 

  • 中午：Sprint Planning/Daily Standup
    • 

  • 下午：解答团队疑问，验收工作
    • 

  • 晚上：整理 Backlog，准备下一个 Sprint
    • 





2. Scrum Master
核心职责：


    

  • 服务式领导（Servant Leadership）
    • 

  • 移除障碍（Impediments）
    • 

  • 促进 Scrum 事件
    • 

  • 指导团队实践 Scrum
    • 

  • 帮助团队持续改进
    • 

  • 与 Product Owner 协作
    •

命令控制（Command & Control）

移除障碍的步骤：


    

  1. 识别障碍：团队提出障碍
    2. 

  2. 分类：技术、流程、组织、外部
    3. 

  3. 优先级：影响和紧急程度
    4. 

  4. 行动：直接解决、 escalate、寻求帮助
    5. 

  5. 跟踪：直到解决
    6. 



Scrum Master 的常见误区：


    

  • ❌ "项目经理"：不管理任务，而是管理过程
    • 

  • ❌ "秘书"：不只是安排会议
    • 

  • ❌ "警察"：不强制执行规则，而是帮助理解
    • 

  • ❌ "救火队员"：不只是解决问题，而是预防问题
    • 





3. Development Team（开发团队）
核心特征：


    

  1. 自组织（Self-Organizing）：
    

      

    • 自己决定如何完成工作
      • 

    • 没有外部指定任务分配
      • 

    • 团队共同承担责任
      • 

    

    2. 

  2. 跨职能（Cross-Functional）：
    

      

    • 拥有交付产品所需的所有技能
      • 

    • 不依赖团队外部
      • 

    • 典型角色：开发、测试、设计、DevOps
      • 

    

    3. 

  3. 规模合适（Right Size）：
    

      

    • 3-9 人（2 披萨团队）
      • 

    • 太小：技能不足
      • 

    • 太大：沟通成本高
      • 

    

    4. 

  4. 专注（Focused）：
    

      

    • 通常只在一个 Scrum Team
      • 

    • 不频繁切换上下文
      • 

    • 专注于 Sprint 目标
      • 

    

    5. 



团队决策：


    

  • 技术决策：团队决定技术方案
    • 

  • 任务分配：团队自己分配任务
    • 

  • 流程改进：团队决定如何改进
    • 

  • 工具选择：团队选择合适的工具
    •

1. Sprint Planning（Sprint 规划会）
两个主题：


主题 1：我们能做什么？（What）


    

  • Product Owner 提出最重要的 Backlog 条目
    • 

  • 团队讨论和理解
    • 

  • 考虑过去的速率（Velocity）
    • 

  • 共同确定 Sprint 目标
    • 



主题 2：我们如何做？（How）


    

  • 团队分解 Backlog 条目为任务
    • 

  • 估算工作量
    • 

  • 制定 Sprint 计划
    • 

  • 识别依赖和风险
    • 



输入：


    

  • Product Backlog
    • 

  • 最新的产品增量
    • 

  • 团队过去的速率
    • 

  • 团队能力
    • 



输出：


    

  • Sprint 目标（Sprint Goal）
    • 

  • Sprint Backlog
    • 

  • Sprint 计划
    • 



Sprint 目标（Sprint Goal）：


    

  • Sprint 的单一目标
    • 

  • 团队共同承诺
    • 

  • 提供灵活性（如果细节有变化）
    • 

  • 可测量、有价值
    • 



示例 Sprint 目标：


    

  • ❌ "完成这 10 个用户故事"
    • 

  • ✅ "让用户能够查看和管理他们的订单历史"
    • 





2. Daily Scrum（每日站会）
目的：


    

  • 同步前一天的进展
    • 

  • 计划今天的工作
    • 

  • 快速识别障碍
    • 

  • 促进团队沟通
    • 



三个经典问题：


    

  1. "昨天我完成了什么帮助团队达成 Sprint 目标的工作？"
    2. 

  2. "今天我计划做什么帮助团队达成 Sprint 目标的工作？"
    3. 

  3. "有什么障碍阻止我或团队达成 Sprint 目标？"
    4. 



最佳实践：


    

  • ⏰ 同一时间、同一地点
    • 

  • ⏱️ 15 分钟准时结束
    • 

  • 👥 所有人站着
    • 

  • 🎯 聚焦 Sprint 目标
    • 

  • 🚫 不是状态汇报给经理
    • 

  • 🚫 不是解决问题的会议（会后单独讨论）
    • 



常见变体：


    

  • Walking the Board：边走边讲，看任务板
    • 

  • Pass the Token：传令牌，拿到的人发言
    • 

  • Focus on Obstacles：更多关注障碍
    • 





3. Sprint Review（Sprint 评审会）
目的：


    

  • 演示产品增量
    • 

  • 收集利益相关者反馈
    • 

  • 协作调整 Product Backlog
    • 

  • 检查产品的进展
    • 



不是：


    

  • ❌ 演示报告
    • 

  • ❌ 验收测试
    • 

  • ❌ 批评会
    • 

  • ❌ 只看"成功"的功能
    • 



参与者：


    

  • Scrum Team
    • 

  • 利益相关者（客户、用户、管理层）
    • 

  • 其他感兴趣的人
    • 



流程：


    

  1. Product Owner 介绍 Sprint 目标和完成的工作
    2. 

  2. 团队演示"完成"的产品增量
    3. 

  3. 利益相关者提供反馈
    4. 

  4. 一起讨论和协作
    5. 

  5. 调整 Product Backlog
    6. 

  6. 展望下一个 Sprint
    7. 



关键：


    

  • 真实的产品，不是幻灯片
    • 

  • 互动，不是单向演示
    • 

  • 收集真实反馈
    • 

  • 协作，不是"评审"
    • 





4. Sprint Retrospective（Sprint 回顾会）
目的：


    

  • 回顾 Sprint 过程
    • 

  • 识别做得好的和可以改进的
    • 

  • 制定改进计划
    • 

  • 持续改进（Continuous Improvement）
    • 



不是：


    

  • ❌ 指责会
    • 

  • ❌ 只说问题
    • 

  • ❌ 走过场
    • 

  • ❌ 讨论产品（那是 Review）
    • 



经典框架：


Start-Stop-Continue：


    

  • Start：开始做什么
    • 

  • Stop：停止做什么
    • 

  • Continue：继续做什么
    • 



Mad-Sad-Glad：


    

  • Mad：什么让你生气/沮丧
    • 

  • Sad：什么让你难过/失望
    • 

  • Glad：什么让你开心/满意
    • 



4 Ls：


    

  • Liked：喜欢什么
    • 

  • Learned：学到了什么
    • 

  • Lacked：缺少什么
    • 

  • Longed for：渴望什么
    • 



流程：


    

  1. 设定会场（Set the Stage）：5-10 分钟
    

      

    • 欢迎，重申目标
      • 

    • 建立安全氛围
      • 

    • 回顾上次的改进项
      • 

    

    2. 

  2. 收集数据（Gather Data）：10-15 分钟
    

      

    • 回顾 Sprint
      • 

    • 收集事实和感受
      • 

    • 使用各种活动
      • 

    

    3. 

  3. 产生洞察（Generate Insights）：10-15 分钟
    

      

    • 分析数据
      • 

    • 寻找模式
      • 

    • 讨论根本原因
      • 

    

    4. 

  4. 决定做什么（Decide What to Do）：10-15 分钟
    

      

    • 选择改进项
      • 

    • 制定行动计划
      • 

    • 分配责任人
      • 

    

    5. 

  5. 结束（Close）：5 分钟
    

      

    • 总结
      • 

    • 感谢参与
      • 

    • 记录改进项
      • 

    

    6. 



改进项的 SMART：


    

  • Specific：具体
    • 

  • Measurable：可测量
    • 

  • Achievable：可实现
    • 

  • Relevant：相关
    • 

  • Time-boxed：有时限
    • 



示例改进项：


    

  • ❌ "改进代码评审"
    • 

  • ✅ "下个 Sprint，每个 PR 在 4 小时内得到第一轮反馈"（责任人：张三）
    •

1. Product Backlog（产品待办列表）
定义：


    

  • 产品的所有需求列表
    • 

  • 唯一的需求来源
    • 

  • 动态的，不断变化
    • 

  • 优先级排序
    • 



Product Backlog 条目（PBI）：


    

  • 用户故事（User Stories）
    • 

  • 功能（Features）
    • 

  • 需求（Requirements）
    • 

  • 缺陷修复（Bug Fixes）
    • 

  • 技术改进（Technical Work）
    • 

  • 知识获取（Knowledge Acquisition）
    • 



好的 PBI 的特征（INVEST）：


    

  • Independent：独立
    • 

  • Negotiable：可协商
    • 

  • Valuable：有价值
    • 

  • Estimable：可估算
    • 

  • Small：小
    • 

  • Testable：可测试
    • 



用户故事（User Story）格式：


作为 [角色]，我想要 [功能]，以便 [价值]
验收标准（Acceptance Criteria）：


    

  • 清晰的完成条件
    • 

  • 可测试
    • 

  • 团队和 PO 共同理解
    • 

  • 确定"完成"
    • 



示例：


作为在线购物的用户，
我想要查看我的订单历史，
以便追踪我的购买记录。

验收标准：
- 显示最近 6 个月的订单
- 每个订单显示：日期、商品、金额、状态
- 可以点击查看订单详情
- 可以按日期范围筛选
Product Backlog 梳理（Refinement）：


    

  • 持续进行的活动
    • 

  • 添加细节
    • 

  • 估算
    • 

  • 分解大的条目
    • 

  • 优先级调整
    • 

  • 通常占用团队 5-10% 的时间
    • 





2. Sprint Backlog（Sprint 待办列表）
定义：


    

  • 当前 Sprint 的工作
    • 

  • Sprint Planning 时选定
    • 

  • 团队拥有
    • 

  • 实时更新
    • 



包含：


    

  • Sprint 目标
    • 

  • 选定的 PBI
    • 

  • 分解后的任务
    • 

  • 任务状态
    • 

  • 剩余工作量
    • 



燃尽图（Burndown Chart）：


    

  • Y 轴：剩余工作量
    • 

  • X 轴：Sprint 天数
    • 

  • 向下的趋势线
    • 

  • 可视化进展
    • 



注意：


    

  • Sprint Backlog 是团队的计划
    • 

  • 可以在 Sprint 中调整
    • 

  • 但 Sprint 目标保持稳定
    • 

  • 团队共同负责
    • 





3. Increment（产品增量）
定义：


    

  • 每个 Sprint 交付的"完成"的产品
    • 

  • 可工作的
    • 

  • 可用的
    • 

  • 达到"完成的定义"（Definition of Done, DoD）
    • 



完成的定义（Definition of Done, DoD）：


    

  • 共享的完成标准
    • 

  • 确保质量
    • 

  • 可测量
    • 

  • 透明
    • 



示例 DoD：


    

  •  代码通过所有测试（单元、集成、E2E）
    • 

  •  代码已评审
    • 

  •  没有已知的严重 Bug
    • 

  •  文档已更新
    • 

  •  可以部署到生产环境
    • 

  •  Product Owner 验收
    • 



可工作的软件是进度的首要度量标准！




速率（Velocity）
定义：


    

  • 团队在一个 Sprint 中完成的 Story Points 总量
    • 

  • 用于预测未来的容量
    • 

  • 不是绩效指标
    • 

  • 只在团队内部使用
    • 



用途：


    

  • Sprint Planning 时预测能做多少
    • 

  • 规划发布日期
    • 

  • 识别趋势（不要用于比较团队！）
    • 



注意：


    

  • ❌ 不要比较不同团队的速率
    • 

  • ❌ 不要用速率来评估团队绩效
    • 

  • ❌ 不要"优化"速率
    • 

  • ✅ 用于预测和规划
    • 

  • ✅ 关注趋势，不是单个 Sprint
    • 





Kanban
Kanban 概述
Kanban（看板）是一种可视化工作流、限制在制品、管理流动的方法。


起源：


    

  • 丰田生产系统（TPS）
    • 

  • 精益制造（Lean Manufacturing）
    • 

  • 后来应用到软件开发
    • 



核心思想：


    

  • 可视化（Visualize）
    • 

  • 限制在制品（Limit WIP）
    • 

  • 管理流动（Manage Flow）
    • 

  • 明确过程策略（Make Process Policies Explicit）
    • 

  • 实施反馈循环（Implement Feedback Loops）
    • 

  • 协作改进（Improve Collaboratively）
    • 





Kanban 核心实践
1. 可视化工作流（Visualize）
为什么？


    

  • 让工作可见
    • 

  • 识别瓶颈
    • 

  • 共享理解
    • 

  • 减少沟通成本
    • 



Kanban 板（Kanban Board）：


基本列：


Backlog → Ready → In Progress → Review → Done
更详细的例子（软件开发）：


Backlog
  ↓
Analysis
  ↓
Development
  ↓
Code Review
  ↓
Testing
  ↓
UAT
  ↓
Deployed
  ↓
Done
卡片（Cards）：


    

  • 代表工作项
    • 

  • 包含信息：描述、负责人、优先级、到期日等
    • 

  • 颜色可以代表类型：功能、Bug、技术改进等
    • 

  • 可以移动
    • 



物理板 vs 电子板：






物理板
电子板





看得见、摸得着
远程友好




站会时大家一起看
可以自动化




简单、低成本
可以追踪历史




适合同地团队
适合分布式团队





常见电子工具：


    

  • Jira
    • 

  • Trello
    • 

  • Miro
    • 

  • Asana
    • 

  • Azure DevOps
    • 





2. 限制在制品（Limit WIP, Work in Progress）
为什么？


    

  • 减少上下文切换
    • 

  • 更快的流动
    • 

  • 暴露瓶颈
    • 

  • 提高质量
    • 



Little's Law（利特尔法则）：


平均周期时间 = 在制品数量 / 平均吞吐率
解释：


    

  • WIP 越少，周期时间越短
    • 

  • 限制 WIP 可以让工作更快完成
    • 

  • 不要让太多工作同时进行
    • 



如何设置 WIP 限制：


    

  • 从当前 WIP 的 70-80% 开始
    • 

  • 逐步调整
    • 

  • 每个列都有 WIP 限制
    • 

  • 当达到限制时，停止开始新工作
    • 



示例 WIP 限制：


Backlog (无限制)
  ↓
Ready (限制 5)
  ↓
In Progress (限制 3)
  ↓
Review (限制 2)
  ↓
Done (无限制)
当达到 WIP 限制时：


    

  • ❌ 不要打破限制
    • 

  • ✅ 帮助完成进行中的工作
    • 

  • ✅ 关注"拉动"（Pull），不是"推动"（Push）
    • 

  • ✅ 识别和解决瓶颈
    • 





3. 管理流动（Manage Flow）
目标：


    

  • 让工作平滑流动
    • 

  • 减少等待时间
    • 

  • 识别和消除瓶颈
    • 

  • 持续改进
    • 



拉动系统（Pull System）：


    

  • 下游拉动上游
    • 

  • 有能力时才开始新工作
    • 

  • 不是推动工作
    • 

  • 类似于餐厅：只有空桌子才安排新客人
    • 



对比：推动 vs 拉动：






推动（Push）
拉动（Pull）





"尽可能多做"
"有能力时才做"




WIP 高
WIP 低




周期时间长
周期时间短




瓶颈被隐藏
瓶颈被暴露





流动度量：


    

  1. 周期时间（Cycle Time）：
    

      

    • 工作从开始到完成的时间
      • 

    • 从 Ready 到 Done
      • 

    • 越快越好
      • 

    

    2. 

  2. 吞吐率（Throughput）：
    

      

    • 单位时间内完成的工作项
      • 

    • 每周、每月完成多少
      • 

    • 越多越好
      • 

    

    3. 

  3. 在制品（WIP）：
    

      

    • 进行中的工作项数量
      • 

    • 稳定或下降好
      • 

    

    4. 



累积流图（Cumulative Flow Diagram, CFD）：


    

  • X 轴：时间
    • 

  • Y 轴：工作项数量
    • 

  • 每一层代表一个状态
    • 

  • 可以看出趋势、瓶颈、周期时间
    • 





4. 明确过程策略（Make Process Policies Explicit）
为什么？


    

  • 共享理解
    • 

  • 减少歧义
    • 

  • 一致执行
    • 

  • 改进的基础
    • 



过程策略的例子：


    

  • 何时将卡片移动到下一列
    • 

  • DoD（完成的定义）
    • 

  • 优先级规则
    • 

  • 升级路径
    • 

  • 会议节奏
    • 



示例规则：


    

  • "只有代码评审通过才能移动到 Testing"
    • 

  • "Bug 的优先级总是高于新功能"
    • 

  • "如果阻塞超过 24 小时，升级给团队领导"
    • 



写下来，让大家都看到！




5. 实施反馈循环（Implement Feedback Loops）
反馈循环的类型：


    

  1. 工作项级：
    

      

    • 代码评审
      • 

    • 测试反馈
      • 

    • 用户反馈
      • 

    

    2. 

  2. 工作流级：
    

      

    • 每日站会
      • 

    • 回顾会议
      • 

    • 度量回顾
      • 

    

    3. 

  3. 组织级：
    

      

    • 跨团队协作
      • 

    • 战略对齐
      • 

    • 客户反馈
      • 

    

    4. 





6. 协作改进，使用模型和科学方法（Improve Collaboratively, Evolve Experimentally）
核心：


    

  • 持续改进
    • 

  • 小步实验
    • 

  • 数据驱动
    • 

  • 协作
    • 



改进循环（PDCA / Plan-Do-Check-Act）：


    

  1. Plan：计划改进
    2. 

  2. Do：小范围实施
    3. 

  3. Check：检查结果
    4. 

  4. Act：采纳或调整
    5. 



Kaizen（改善）：


    

  • 持续、渐进的改进
    • 

  • 每个人都参与
    • 

  • 小步走，不停步
    • 

  • 积累成大的改进
    • 





Kanban 板设计示例
简单的软件开发看板：


┌─────────────┬─────────────┬─────────────┬─────────────┬─────────────┐
│   Backlog   │    Ready    │ In Progress │   Review    │    Done     │

│ 🟢 订单详情  │ 🟡 个人中心  │             │             │             │
│ 🟡 购物车    │             │             │             │             │
└─────────────┴─────────────┴─────────────┴─────────────┴─────────────┘

🔴 = 高优先级
🟡 = 中优先级
🟢 = 低优先级
带服务类别的看板：


服务类别说明：Expedite（加急，立即处理）/ Fixed Date（有时间限制）/ Standard（常规工作）/ Intangible（低优先级）

选择合适的框架
Scrum 的适用场景
✅ 选择 Scrum，如果：


    

  • 新产品开发
    • 

  • 需求相对清晰但可能变化
    • 

  • 需要固定的节奏
    • 

  • 团队可以稳定投入
    • 

  • 需要明确的角色和结构
    • 



示例：


    

  • 新功能开发
    • 

  • 产品迭代
    • 

  • 探索性项目
    • 





Kanban 的适用场景
✅ 选择 Kanban，如果：


    

  • 运维和支持
    • 

  • 工作项大小差异大
    • 

  • 需要快速响应
    • 

  • 无法使用时间盒
    • 

  • 想要从当前过程开始改进
    • 



示例：


    

  • 运维支持
    • 

  • Bug 修复
    • 

  • 客户请求处理
    • 

  • 持续改进
    • 





Scrumban（混合）
结合 Scrum 和 Kanban 的元素：


    

  • 使用 Scrum 的事件
    • 

  • 使用 Kanban 的看板和 WIP 限制
    • 

  • 灵活性更高
    • 





常见误区
Scrum 误区
    

  1. Sprint 是"截止日期"
    

      

    • ❌ 错误：Sprint 是时间盒，不是必须完成所有工作
      • 

    • ✅ 正确：关注 Sprint 目标，调整范围
      • 

    

    2. 

  2. Scrum Master 是项目经理
    

      

    • ❌ 错误：分配任务、跟踪进度
      • 

    • ✅ 正确：服务式领导，移除障碍，促进 Scrum
      • 

    

    3. 

  3. Velocity 是绩效指标
    

      

    • ❌ 错误：比较团队，要求"提高"速率
      • 

    • ✅ 正确：用于预测，关注趋势
      • 

    

    4. 

  4. Scrum 是"快速做"
    

      

    • ❌ 错误：牺牲质量，赶进度
      • 

    • ✅ 正确：快速学习，快速调整，持续改进
      • 

    

    5. 

  5. Scrum 只适合小团队
    

      

    • ❌ 错误：只能 3-9 人
      • 

    • ✅ 正确：可以规模化（LeSS、SAFe、Nexus）
      • 

    

    6. 





Kanban 误区
    

  1. Kanban 只是看板
    

      

    • ❌ 错误：只是弄一个白板
      • 

    • ✅ 正确：6 个核心实践，持续改进
      • 

    

    2. 

  2. Kanban 没有规则
    

      

    • ❌ 错误：很灵活，没有限制
      • 

    • ✅ 正确：有 WIP 限制，有明确的过程策略
      • 

    

    3. 

  3. Kanban 不做计划
    

      

    • ❌ 错误：只看当前，不看未来
      • 

    • ✅ 正确：可以有中期和长期规划
      • 

    

    4. 

  4. Kanban 是"慢"的
    

      

    • ❌ 错误：WIP 限制，所以做得少
      • 

    • ✅ 正确：限制 WIP，所以更快完成，周期时间更短
      • 

    

    5. 





最佳实践
Scrum 最佳实践
    

  1. 产品负责人
    

      

    • 花时间与团队沟通
      • 

    • 清晰的验收标准
      • 

    • 及时的决策
      • 

    • 参与所有 Scrum 事件
      • 

    

    2. 

  2. Scrum Master
    

      

    • 服务式领导，不是命令
      • 

    • 教练，不是警察
      • 

    • 关注持续改进
      • 

    • 保护团队不受干扰
      • 

    

    3. 

  3. 开发团队
    

      

    • 自组织，自己决定如何工作
      • 

    • 跨职能，不需要外部依赖
      • 

    • 专注 Sprint 目标
      • 

    • 每天协作
      • 

    

    4. 

  4. 事件
    

      

    • 准时开始，准时结束
      • 

    • 所有团队成员参与
      • 

    • 有明确的目标
      • 

    • 产出明确的结果
      • 

    

    5. 

  5. 工件
    

      

    • Product Backlog 持续梳理
      • 

    • Sprint Backlog 实时更新
      • 

    • 清晰的 DoD
      • 

    • 透明，所有人都能看到
      • 

    

    6. 





Kanban 最佳实践
    

  1. 可视化
    

      

    • 让所有工作都可见
      • 

    • 清晰的列定义
      • 

    • 有意义的信息在卡片上
      • 

    • 大家都能轻松访问
      • 

    

    2. 

  2. WIP 限制
    

      

    • 从保守开始
      • 

    • 逐步调整
      • 

    • 不要打破限制
      • 

    • 关注拉动，不是推动
      • 

    

    3. 

  3. 流动
    

      

    • 测量周期时间和吞吐率
      • 

    • 使用 CFD 可视化
      • 

    • 识别和消除瓶颈
      • 

    • 持续优化流动
      • 

    

    4. 

  4. 反馈循环
    

      

    • 定期回顾
      • 

    • 收集反馈
      • 

    • 快速响应
      • 

    • 闭环
      • 

    

    5. 

  5. 持续改进
    

      

    • 小步实验
      • 

    • 数据驱动
      • 

    • 协作
      • 

    • 永不停步
      • 

    

    6. 





小结
Agile 是价值观和思维方式，Scrum 和 Kanban 是两种常用的实现框架。


核心要点回顾：


    

  • Agile 四条核心价值观：个体和互动、可工作的软件、客户合作、响应变化
    • 

  • Scrum 的三个角色：PO、SM、Dev Team
    • 

  • Scrum 的四个事件：Planning、Daily、Review、Retro
    • 

  • Scrum 的三个工件：Product Backlog、Sprint Backlog、Increment
    • 

  • Kanban 的六个核心实践：可视化、限制 WIP、管理流动、明确策略、反馈循环、协作改进
    • 

  • Scrum 适合新产品开发，有固定节奏
    • 

  • Kanban 适合运维支持，持续流动
    • 

  • 不要教条，根据实际情况调整
    • 

  • 持续改进，永不停步
    • 

  • 记住：敏捷是一种思维方式，不是流程
    •
