Kanban 与框架选择

核心概念

Kanban（看板）通过可视化工作流、限制在制品（WIP）来管理流动，与 Scrum 的固定迭代形成互补。选择框架的依据是工作性质：新产品开发偏向 Scrum 的节奏与结构，运维与支持偏向 Kanban 的持续流动。两种框架都能裁剪与混合，核心是匹配团队的实际工作方式，而不是教条。

Kanban

Kanban 概述

Kanban（看板）是一种可视化工作流、限制在制品、管理流动的方法。

起源：

  • 丰田生产系统（TPS）
  • 精益制造（Lean Manufacturing）
  • 后来应用到软件开发

核心思想：

  • 可视化（Visualize）
  • 限制在制品（Limit WIP）
  • 管理流动（Manage Flow）
  • 明确过程策略（Make Process Policies Explicit）
  • 实施反馈循环（Implement Feedback Loops）
  • 协作改进（Improve Collaboratively）

Kanban 核心实践

1. 可视化工作流（Visualize）

为什么？

  • 让工作可见
  • 识别瓶颈
  • 共享理解
  • 减少沟通成本

Kanban 板（Kanban Board）：

基本列：

Backlog → Ready → In Progress → Review → Done

更详细的例子（软件开发）：

Backlog
  ↓
Analysis
  ↓
Development
  ↓
Code Review
  ↓
Testing
  ↓
UAT
  ↓
Deployed
  ↓
Done

卡片（Cards）：

  • 代表工作项
  • 包含信息：描述、负责人、优先级、到期日等
  • 颜色可以代表类型：功能、Bug、技术改进等
  • 可以移动

物理板 vs 电子板：

物理板 电子板
看得见、摸得着 远程友好
站会时大家一起看 可以自动化
简单、低成本 可以追踪历史
适合同地团队 适合分布式团队

常见电子工具：

  • Jira
  • Trello
  • Miro
  • Asana
  • Azure DevOps

2. 限制在制品（Limit WIP, Work in Progress）

为什么？

  • 减少上下文切换
  • 更快的流动
  • 暴露瓶颈
  • 提高质量

Little's Law（利特尔法则）：

平均周期时间 = 在制品数量 / 平均吞吐率

解释：

  • WIP 越少，周期时间越短
  • 限制 WIP 可以让工作更快完成
  • 不要让太多工作同时进行

如何设置 WIP 限制：

  • 从当前 WIP 的 70-80% 开始
  • 逐步调整
  • 每个列都有 WIP 限制
  • 当达到限制时，停止开始新工作

示例 WIP 限制：

Backlog (无限制)
  ↓
Ready (限制 5)
  ↓
In Progress (限制 3)
  ↓
Review (限制 2)
  ↓
Done (无限制)

当达到 WIP 限制时：

  • ❌ 不要打破限制
  • ✅ 帮助完成进行中的工作
  • ✅ 关注"拉动"（Pull），不是"推动"（Push）
  • ✅ 识别和解决瓶颈

3. 管理流动（Manage Flow）

目标：

  • 让工作平滑流动
  • 减少等待时间
  • 识别和消除瓶颈
  • 持续改进

拉动系统（Pull System）：

  • 下游拉动上游
  • 有能力时才开始新工作
  • 不是推动工作
  • 类似于餐厅：只有空桌子才安排新客人

对比：推动 vs 拉动：

推动（Push） 拉动（Pull）
"尽可能多做" "有能力时才做"
WIP 高 WIP 低
周期时间长 周期时间短
瓶颈被隐藏 瓶颈被暴露

流动度量：

  1. 周期时间（Cycle Time）：

    • 工作从开始到完成的时间
    • 从 Ready 到 Done
    • 越快越好

  2. 吞吐率（Throughput）：

    • 单位时间内完成的工作项
    • 每周、每月完成多少
    • 越多越好

  3. 在制品（WIP）：

    • 进行中的工作项数量
    • 稳定或下降好

累积流图（Cumulative Flow Diagram, CFD）：

  • X 轴：时间
  • Y 轴：工作项数量
  • 每一层代表一个状态
  • 可以看出趋势、瓶颈、周期时间

4. 明确过程策略（Make Process Policies Explicit）

为什么？

  • 共享理解
  • 减少歧义
  • 一致执行
  • 改进的基础

过程策略的例子：

  • 何时将卡片移动到下一列
  • DoD（完成的定义）
  • 优先级规则
  • 升级路径
  • 会议节奏

示例规则：

  • "只有代码评审通过才能移动到 Testing"
  • "Bug 的优先级总是高于新功能"
  • "如果阻塞超过 24 小时，升级给团队领导"

写下来，让大家都看到！

5. 实施反馈循环（Implement Feedback Loops）

反馈循环的类型：

  1. 工作项级：

    • 代码评审
    • 测试反馈
    • 用户反馈

  2. 工作流级：

    • 每日站会
    • 回顾会议
    • 度量回顾

  3. 组织级：

    • 跨团队协作
    • 战略对齐
    • 客户反馈

6. 协作改进，使用模型和科学方法（Improve Collaboratively, Evolve Experimentally）

核心：

  • 持续改进
  • 小步实验
  • 数据驱动
  • 协作

改进循环（PDCA / Plan-Do-Check-Act）：

  1. Plan：计划改进
  2. Do：小范围实施
  3. Check：检查结果
  4. Act：采纳或调整

Kaizen（改善）：

  • 持续、渐进的改进
  • 每个人都参与
  • 小步走，不停步
  • 积累成大的改进

Kanban 板设计示例

简单的软件开发看板：

┌─────────────┬─────────────┬─────────────┬─────────────┬─────────────┐
│   Backlog   │    Ready    │ In Progress │   Review    │    Done     │
│             │  (限制 5)   │  (限制 3)   │  (限制 2)   │             │
├─────────────┼─────────────┼─────────────┼─────────────┼─────────────┤
│ 🔴 用户登录  │ 🟢 订单列表  │ 🟡 支付集成  │ 🟢 UI 优化   │ ✅ 搜索功能  │
│ 🟢 订单详情  │ 🟡 个人中心  │             │             │             │
│ 🟡 购物车    │             │             │             │             │
└─────────────┴─────────────┴─────────────┴─────────────┴─────────────┘

🔴 = 高优先级
🟡 = 中优先级
🟢 = 低优先级

带服务类别的看板：

block-beta
    columns 5
    block:backlog["Backlog"]:1
        B1["生产故障 Expedite"]
    end
    block:ready["Ready (限制2)"]:1
        R1["用户登录 Fixed Date"]
        R2["订单列表 Intangible"]
    end
    block:progress["In Progress (限制3)"]:1
        P1["支付集成 Standard"]
    end
    block:review["Review (限制2)"]:1
        V1["UI 优化 Intangible"]
    end
    block:done["Done"]:1
        D1["搜索功能 ✅"]
    end

服务类别说明：Expedite（加急，立即处理）/ Fixed Date（有时间限制）/ Standard（常规工作）/ Intangible（低优先级）

Scrum vs Kanban

维度 Scrum Kanban
时间盒（Timebox） ✅ Sprint（1-4 周） ❌ 无时间盒，持续流动
角色 ✅ PO、SM、Dev Team ❌ 无特定角色
WIP 限制 ❌ 无明确限制（隐含限制） ✅ 明确的 WIP 限制
变更 ❌ Sprint 内尽量不变 ✅ 持续变更
工件 ✅ Product Backlog、Sprint Backlog、Increment ❌ 无特定工件，看板本身
事件 ✅ Planning、Daily、Review、Retro ❌ 无必需事件，可选
开始方式 ✅ 需要重置（重新开始） ❌ 可以从当前过程开始
节奏 ✅ 固定的 Sprint 节奏 ❌ 连续的流动
估算 ✅ 推荐（Velocity） ❌ 可选
适合场景 产品开发、新项目 运维、支持、持续改进

选择合适的框架

Scrum 的适用场景

✅ 选择 Scrum，如果：

  • 新产品开发
  • 需求相对清晰但可能变化
  • 需要固定的节奏
  • 团队可以稳定投入
  • 需要明确的角色和结构

示例：

  • 新功能开发
  • 产品迭代
  • 探索性项目

Kanban 的适用场景

✅ 选择 Kanban，如果：

  • 运维和支持
  • 工作项大小差异大
  • 需要快速响应
  • 无法使用时间盒
  • 想要从当前过程开始改进

示例：

  • 运维支持
  • Bug 修复
  • 客户请求处理
  • 持续改进

Scrumban（混合）

结合 Scrum 和 Kanban 的元素：

  • 使用 Scrum 的事件
  • 使用 Kanban 的看板和 WIP 限制
  • 灵活性更高

常见误区

Scrum 误区

  1. Sprint 是"截止日期"

    • ❌ 错误：Sprint 是时间盒，不是必须完成所有工作
    • ✅ 正确：关注 Sprint 目标，调整范围

  2. Scrum Master 是项目经理

    • ❌ 错误：分配任务、跟踪进度
    • ✅ 正确：服务式领导，移除障碍，促进 Scrum

  3. Velocity 是绩效指标

    • ❌ 错误：比较团队，要求"提高"速率
    • ✅ 正确：用于预测，关注趋势

  4. Scrum 是"快速做"

    • ❌ 错误：牺牲质量，赶进度
    • ✅ 正确：快速学习，快速调整，持续改进

  5. Scrum 只适合小团队

    • ❌ 错误：只能 3-9 人
    • ✅ 正确：可以规模化（LeSS、SAFe、Nexus）

Kanban 误区

  1. Kanban 只是看板

    • ❌ 错误：只是弄一个白板
    • ✅ 正确：6 个核心实践，持续改进

  2. Kanban 没有规则

    • ❌ 错误：很灵活，没有限制
    • ✅ 正确：有 WIP 限制，有明确的过程策略

  3. Kanban 不做计划

    • ❌ 错误：只看当前，不看未来
    • ✅ 正确：可以有中期和长期规划

  4. Kanban 是"慢"的

    • ❌ 错误：WIP 限制，所以做得少
    • ✅ 正确：限制 WIP，所以更快完成，周期时间更短

最佳实践

Scrum 最佳实践

  1. 产品负责人

    • 花时间与团队沟通
    • 清晰的验收标准
    • 及时的决策
    • 参与所有 Scrum 事件

  2. Scrum Master

    • 服务式领导，不是命令
    • 教练，不是警察
    • 关注持续改进
    • 保护团队不受干扰

  3. 开发团队

    • 自组织，自己决定如何工作
    • 跨职能，不需要外部依赖
    • 专注 Sprint 目标
    • 每天协作

  4. 事件

    • 准时开始，准时结束
    • 所有团队成员参与
    • 有明确的目标
    • 产出明确的结果

  5. 工件

    • Product Backlog 持续梳理
    • Sprint Backlog 实时更新
    • 清晰的 DoD
    • 透明，所有人都能看到

Kanban 最佳实践

  1. 可视化

    • 让所有工作都可见
    • 清晰的列定义
    • 有意义的信息在卡片上
    • 大家都能轻松访问

  2. WIP 限制

    • 从保守开始
    • 逐步调整
    • 不要打破限制
    • 关注拉动，不是推动

  3. 流动

    • 测量周期时间和吞吐率
    • 使用 CFD 可视化
    • 识别和消除瓶颈
    • 持续优化流动

  4. 反馈循环

    • 定期回顾
    • 收集反馈
    • 快速响应
    • 闭环

  5. 持续改进

    • 小步实验
    • 数据驱动
    • 协作
    • 永不停步

小结

mindmap
  root((敏捷方法))
    Scrum
      角色: PO/SM/Team
      事件: Planning/Daily/Review/Retro
      工件: Backlog/Increment
    Kanban
      可视化
      限制 WIP
      管理流动
    选择依据
      新产品→Scrum
      运维→Kanban
      混合→Scrumban

Agile 是价值观和思维方式，Scrum 和 Kanban 是两种常用的实现框架。

核心要点回顾：

  • Agile 四条核心价值观：个体和互动、可工作的软件、客户合作、响应变化
  • Scrum 的三个角色：PO、SM、Dev Team
  • Scrum 的四个事件：Planning、Daily、Review、Retro
  • Scrum 的三个工件：Product Backlog、Sprint Backlog、Increment
  • Kanban 的六个核心实践：可视化、限制 WIP、管理流动、明确策略、反馈循环、协作改进
  • Scrum 适合新产品开发，有固定节奏
  • Kanban 适合运维支持，持续流动
  • 不要教条，根据实际情况调整
  • 持续改进，永不停步
  • 记住：敏捷是一种思维方式，不是流程

Scrum 的角色、事件、工件与敏捷价值观见保留篇 Agile、Scrum 与 Kanban。
