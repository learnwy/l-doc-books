规划实践与滚动规划

核心概念

估算回答"这一块要做多久"，规划回答"这些工作如何组织和排程"。规划把估算结果落地为可管理、可跟踪、可调整的结构：先分解工作，再排定时间与依赖，最后为不确定性留出余地。

规划实践

Work Breakdown Structure (WBS)

定义： 将项目分解为可管理的小任务的层次结构。

为什么 WBS 重要？

  • 确保没有遗漏工作
  • 使工作可估算、可分配、可跟踪
  • 清晰的责任边界
  • 更好的进度管理

WBS 原则：

  1. 100% 规则：

    • WBS 包含所有工作
    • 没有遗漏，也没有多余
    • 下一级的和等于上一级

  2. 相互独立：

    • 工作包之间没有重叠
    • 清晰的边界
    • 避免重复计算

  3. 可管理：

    • 每个工作包可以分配给一个人或团队
    • 有明确的完成标准
    • 可以估算和跟踪

  4. 面向交付：

    • 关注交付什么，而不是如何做
    • 以产品为导向
    • 不是活动列表

WBS 示例：

电商网站项目
├─ 用户系统
│  ├─ 用户注册
│  ├─ 用户登录
│  └─ 用户信息管理
├─ 商品系统
│  ├─ 商品展示
│  ├─ 商品搜索
│  └─ 商品管理（后台）
├─ 购物车
│  ├─ 添加商品
│  ├─ 修改数量
│  └─ 删除商品
├─ 订单系统
│  ├─ 创建订单
│  ├─ 支付集成
│  └─ 订单管理
└─ 后台系统
   ├─ 数据分析
   ├─ 库存管理
   └─ 系统设置

WBS vs 活动列表：

WBS 活动列表
面向交付（What） 面向活动（How）
层次结构 线性列表
关注结果 关注过程
适合规划和跟踪 适合执行

里程碑（Milestones）

定义： 项目中的关键检查点，标记重要阶段的完成。

为什么里程碑重要？

  • 提供可见的进展
  • 建立信心和动力
  • 检查点，可以调整计划
  • 对齐利益相关者

好的里程碑的特征：

  • 具体、可验证
  • 有明确的完成标准
  • 有时间点
  • 与业务价值相关

里程碑示例：

timeline
    title 项目里程碑
    Week 1 : 项目启动
           : 需求确认
           : 团队组建
    Week 4 : 基础架构完成
           : 开发环境就绪
           : CI/CD 搭建
    Week 8 : MVP 功能完成
           : 核心功能开发
           : 内部测试
    Week 12 : UAT 完成
            : 用户验收测试
            : Bug 修复
    Week 14 : 上线发布
            : 生产环境部署
            : 监控和运维

如何使用里程碑：

  1. 规划时：

    • 识别关键交付物
    • 设置里程碑时间
    • 定义完成标准

  2. 执行时：

    • 跟踪里程碑进展
    • 提前识别风险
    • 及时调整计划

  3. 到达时：

    • 验证完成标准
    • 庆祝成功
    • 回顾和调整
    • 沟通进展

关键路径法（Critical Path Method, CPM）

定义： 识别项目中最长的任务序列，决定项目最短工期。

为什么关键路径重要？

  • 知道什么决定项目工期
  • 优先关注关键任务
  • 识别可以并行的工作
  • 合理安排资源

关键路径的特征：

  • 最长的路径（总工期）
  • 没有浮动时间（Slack = 0）
  • 任何延迟都会影响项目工期
  • 需要重点关注和管理

如何计算关键路径：

  1. 绘制网络图：

    • 节点表示任务
    • 箭头表示依赖关系
    • 标注每个任务的工期

  2. 正向计算（Early Start/Early Finish）：

    • 从左到右
    • ES = max(所有前置任务的 EF)
    • EF = ES + 工期

  3. 反向计算（Late Start/Late Finish）：

    • 从右到左
    • LF = min(所有后续任务的 LS)
    • LS = LF - 工期

  4. 计算浮动时间（Slack/Float）：

    • Slack = LS - ES 或 LF - EF
    • Slack = 0 的任务在关键路径上

示例：

interface Task {
  id: string;
  name: string;
  duration: number; // 天
  dependencies: string[];
  es?: number; // Early Start
  ef?: number; // Early Finish
  ls?: number; // Late Start
  lf?: number; // Late Finish
  slack?: number;
  isCritical?: boolean;
}

// 示例任务：
// A: 需求分析, 5天, 无依赖
// B: 设计, 3天, 依赖A
// C: 前端开发, 8天, 依赖B
// D: 后端开发, 10天, 依赖B
// E: 测试, 4天, 依赖C和D
// F: 部署, 2天, 依赖E

// 关键路径: A → B → D → E → F
// 总工期: 5 + 3 + 10 + 4 + 2 = 24天
// C有2天浮动时间（10-8=2）

如何使用关键路径：

  1. 缩短工期：

    • 只有关键路径上的任务能缩短总工期
    • 可以并行关键任务
    • 可以增加资源（Crashing）
    • 可以调整范围（Fast Tracking）

  2. 风险管理：

    • 关键任务风险更高
    • 重点关注关键任务
    • 准备应急预案

  3. 资源管理：

    • 优先保证关键任务资源
    • 非关键任务可以灵活安排
    • 利用浮动时间平衡资源

缓冲时间（Buffer/Contingency）

定义： 为不确定性预留的额外时间。

为什么需要缓冲？

  • 软件开发充满不确定性
  • 估算不准确
  • 可能遇到未预见的问题
  • 范围可能蔓延

缓冲的类型：

  1. 项目缓冲（Project Buffer）：

    • 在项目末尾预留
    • 保护整个项目工期
    • 通常 10-20% 的总工期

  2. 关键链缓冲（Critical Chain Buffer）：

    • 在关键路径末端
    • 保护关键链
    • 基于关键链的不确定性

  3. 接驳缓冲（Feeding Buffer）：

    • 在非关键路径汇入关键路径处
    • 保护关键路径不受非关键路径影响
    • 基于汇入路径的不确定性

  4. 资源缓冲（Resource Buffer）：

    • 预留资源能力
    • 应对资源不确定性
    • 例如：预留部分人力时间

多少缓冲合适？

考虑因素：

  • 不确定性程度：高不确定性需要更多缓冲
  • 项目重要性：重要项目需要更多缓冲
  • 团队经验：经验少需要更多缓冲
  • 历史数据：有数据可以更精确
  • 风险承受能力：保守型需要更多缓冲

常见范围：

  • 低风险：5-10%
  • 中等风险：10-20%
  • 高风险：20-30%+

如何管理缓冲：

  1. 不要提前使用：

    • 缓冲是应对不确定性的
    • 不要用缓冲来填充宽松的估算
    • 保留到真正需要时

  2. 监控缓冲使用：

    • 跟踪缓冲消耗速度
    • 提前预警
    • 及时调整

  3. 缓冲用完时：

    • 重新评估风险
    • 调整范围或时间
    • 与利益相关者沟通

规划不是一次性的

滚动规划（Rolling Wave Planning）

定义： 近期详细规划，远期粗略规划。

示例：

  • Sprint 1：详细到天
  • Sprint 2：详细到任务
  • Sprint 3-4：粗略到功能
  • 之后：只有 Epic

优点：

  • 不浪费时间在不确定的事情上
  • 随着信息增加，逐步细化
  • 适应变化

调整和重规划

计划不是一成不变的：

  • 定期回顾（每周/每月）
  • 识别偏差
  • 分析原因
  • 调整计划

触发重规划的情况：

  • 范围重大变化
  • 关键风险发生
  • 进度严重偏差
  • 优先级变化

沟通变化

及时沟通：

  • 不要隐瞒
  • 解释原因
  • 说明影响
  • 共同决策

沟通原则：

  • 透明
  • 及时
  • 具体
  • 建设性

小结

  • WBS 确保没有遗漏工作，遵循 100% 规则与相互独立原则
  • 里程碑提供可见进展并建立信心，好的里程碑具体、可验证、与业务价值相关
  • 关键路径决定项目最短工期，只有关键路径上的任务能缩短总工期
  • 缓冲应对不确定性，关键是不提前消耗并按风险等级设定比例
  • 滚动规划：近期详细、远期粗略，计划随信息增加逐步细化
