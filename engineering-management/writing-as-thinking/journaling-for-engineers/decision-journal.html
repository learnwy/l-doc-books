决策日志

核心概念：什么是决策日志

决策日志（Decision Journal）是一种专门记录决策过程的写作实践。它不仅记录你做出了什么决策，更重要的是记录你在做决策时的思考过程：考虑了哪些因素、掌握了哪些信息、做出了哪些假设、预期了什么结果。

决策日志的核心价值在于它创建了一个"决策反馈闭环"。在日常工作中，我们不断做出决策——技术选型、架构设计、优先级排序、人员分配——但很少回头检验这些决策的质量。决策日志让回顾和改进成为可能。


对于程序员来说，决策日志尤其重要，因为软件工程中的决策往往具有长期影响：今天选择的框架可能会用三年，今天的架构设计会影响未来所有功能的开发速度。


为什么"拍脑袋"决策是高风险的
程序员经常在时间压力下做出技术决策，而且很少有机会系统性地回顾这些决策的质量。这导致了一系列认知偏误反复出现而不被察觉。






认知偏误
在工程决策中的表现
决策日志如何帮助





锚定效应
第一个想到的方案权重过高
强制列出多个选项再评估




确认偏误
只寻找支持自己方案的证据
记录每个方案的优劣两面




可得性偏误
最近用过的技术被优先选择
回顾历史决策，发现偏好模式




沉没成本
不愿放弃已投入大量时间的方案
记录客观标准，基于标准而非情感决策




结果偏误
用结果好坏判断决策质量
区分"好决策坏结果"和"坏决策好结果"





决策日志的结构化方法
决策记录模板
一条完整的决策日志条目应包含以下要素：


## 决策：选择 PostgreSQL 作为订单系统的主数据库

### 日期

2026-04-03

### 上下文

- 新的订单系统需要选择数据库
- 预期日订单量：50 万笔（峰值 100 万）
- 团队熟悉 MySQL，对 PostgreSQL 有基础了解
- 数据包含大量 JSON 格式的订单扩展信息

### 考虑的选项

1. MySQL 8.0 + JSON 列
2. PostgreSQL 15 + JSONB
3. MySQL + MongoDB（混合存储）

### 决策

选择 PostgreSQL 15

### 推理过程

- JSONB 的查询性能和索引能力显著优于 MySQL 的 JSON 列
- 避免引入混合存储的运维复杂度
- 虽然团队更熟悉 MySQL，但 SQL 基础通用，学习成本可控
- 隐含假设：团队能在 2 周内完成 PostgreSQL 特性学习

### 预期结果

- JSON 查询性能提升 3-5 倍
- 减少一个数据库组件的运维成本
- 团队需要 2 周适应期

### 风险

- 团队学习曲线可能超预期
- PostgreSQL 的运维经验不足

### 回顾日期

2026-07-03（上线后 3 个月）
决策质量评估框架
决策日志不仅记录决策，还应定期评估决策质量。关键区分：决策质量≠结果质量。一个优秀的决策可能因为运气不好而产生坏结果，一个糟糕的决策也可能碰巧成功。


评估决策质量的标准：


    

  • 是否充分收集了可获得的信息？
    • 

  • 是否考虑了足够多的选项？
    • 

  • 是否识别并显式化了关键假设？
    • 

  • 推理过程是否有逻辑漏洞？
    • 

  • 是否考虑了主要风险和应对方案？
    • 



一个实用的评分框架：


## 决策质量评分卡

信息收集（1-5）：**\_\_** 1 = 几乎没有收集信息就做了决策 5 = 充分调研了可获得的所有相关信息

选项多样性（1-5）：**\_\_** 1 = 只考虑了一个方案 5 = 考虑了 3 个以上有实质差异的方案

假设识别（1-5）：**\_\_** 1 = 没有识别任何隐含假设 5 = 所有关键假设都被显式记录并验证

推理质量（1-5）：**\_\_** 1 = 凭直觉做决策 5 = 有清晰的因果链和权衡分析

风险评估（1-5）：**\_\_** 1 = 没有考虑风险 5 = 识别了主要风险并有应对方案

总分 = **\_\_** / 25
定期回顾机制
决策日志的最大价值在回顾阶段释放。建议按以下频率回顾：


interface ReviewSchedule {
  weekly: string;
  monthly: string;
  quarterly: string;
}

const schedule: ReviewSchedule = {
  weekly: '快速浏览本周决策，检查是否有遗漏记录',
  monthly: '回顾到期的决策，对比预期和实际结果',
  quarterly: '分析决策模式，识别系统性偏误和改进方向',
};
实战应用：程序员的决策日志场景
场景一：技术选型决策
技术选型是影响最深远的工程决策之一。记录选型过程不仅帮助当下思考，也为未来可能的技术迁移提供重要上下文。


关键记录要素：


    

  • 当时的业务需求和技术约束
    • 

  • 候选技术的评估标准和权重
    • 

  • 概念验证（PoC）的结论
    • 

  • 团队能力和学习成本的考量
    • 

  • 未来可扩展性的预判
    • 



场景二：架构设计决策
使用 ADR（Architecture Decision Record）格式记录架构决策，是决策日志在团队层面的延伸。


# ADR-007: 采用事件驱动架构处理订单状态变更

## 状态

已采纳

## 上下文

订单系统需要在状态变更时通知多个下游服务（库存、物流、财务）。当前的同步调用方式导致响应时间长、耦合度高。

## 决策

采用事件驱动架构，订单状态变更发布事件，下游服务通过订阅事件来响应。

## 后果

- 正面：服务间解耦，可独立扩展和部署
- 负面：引入最终一致性，需要处理事件丢失和重复
- 风险：事件溯源和排查的工具链需要建设
场景三：日常工程决策
不只是大的技术决策，日常的小决策也值得记录——选择哪种设计模式、如何命名一个接口、是否引入一个新依赖。这些"微决策"的累积效应往往被忽视。


日常微决策记录示例：


### 2026-04-03 微决策记录

决策 1：用户通知偏好的 API 方法

- 选择 PATCH 而非 PUT
- 理由：用户通常只修改单个偏好项
- 假设：前端不会批量更新所有偏好

决策 2：是否引入 zod 做运行时类型校验

- 选择引入
- 理由：当前 5 个 API 端点的请求体验证散落在各处
- 风险：增加了一个新依赖，团队需要学习成本
- 回顾日期：1 个月后评估使用体验
决策日志与团队协作
决策日志不仅是个人工具，也可以成为团队知识共享的载体。将重要决策日志公开（通过 ADR 或团队 Wiki），能够：


    

  • 减少重复讨论：新成员可以直接查看决策背景
    • 

  • 提高决策质量：知道决策会被记录，你会更谨慎
    • 

  • 加速新人融入：新人通过阅读历史决策快速理解项目上下文
    • 

  • 建立组织记忆：即使决策者离职，决策的理由依然可追溯
    •

决策能力的成长阶梯
    

  • L1 直觉决策：凭经验和直觉做出决策，不记录过程，无法事后复盘
    • 

  • L2 记录决策：开始记录决策和理由，但尚未形成回顾习惯
    • 

  • L3 结构化决策：使用系统化的框架来评估选项、识别风险、记录假设
    • 

  • L4 系统化改进：定期回顾决策质量，识别认知偏误模式，持续改善决策框架
    • 



本节小结
决策日志是提升工程决策质量的核心工具。它不是记录"做了什么"，而是记录"为什么这样做"——这些决策上下文是未来回顾和改进的基础。


核心要点回顾：


    

  • 决策质量和结果质量是两个独立维度，需要分别评估
    • 

  • 结构化的决策记录模板帮助你避免遗漏关键思考环节
    • 

  • 定期回顾是释放决策日志价值的关键——记录而不回顾等于没记
    • 

  • 从个人决策日志到团队 ADR，是知识从个人到组织的重要通路
    • 



关键行动：


    

  1. 回忆最近一个重要的技术决策，用决策记录模板写下完整的决策过程
    2. 

  2. 为这个决策设定一个回顾日期（通常 1-3 个月后）
    3. 

  3. 在团队中推广 ADR 实践，为每个架构决策留下文字记录
    4. 

  4. 每月花 30 分钟回顾到期的决策日志，对比预期和实际结果
    5. 

  5. 识别你最常见的决策偏误，制定针对性的纠正策略
    6.
