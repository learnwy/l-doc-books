RFC 与设计文档写作

为什么 RFC 和设计文档是工程影响力的核心载体

在技术组织中，代码是最终产出，但 RFC（Request for Comments）和设计文档才是推动技术决策的关键杠杆。一份高质量的设计文档能在代码写出之前就解决方向性问题，避免数周甚至数月的返工。更重要的是，设计文档是工程师展示系统思考能力和技术领导力的最佳舞台——它让你的思考过程可见、可评审、可追溯。

RFC 与设计文档的战略价值

价值维度 说明
决策质量 通过书面分析在编码前发现方案缺陷
知识传承 记录技术决策的上下文和理由
团队对齐 确保所有参与者对方案有共同理解
影响力展示 体现系统思考和架构能力
异步协作 让分布式团队能高效参与技术决策

问题陈述的工艺
问题陈述是整篇 RFC 最重要的部分——如果问题定义得不清晰，再好的方案也是无的放矢。


问题陈述框架
现状（Current State）： 描述当前系统的运作方式和限制。


痛点（Pain Points）： 用数据量化当前方案的问题。


影响（Impact）： 说明问题对用户、业务和团队的影响。


紧迫性（Urgency）： 为什么现在需要解决这个问题。


好的问题陈述 vs 差的问题陈述




维度
差的问题陈述
好的问题陈述





具体性
"系统性能不好"
"在日均 100 万请求下，订单查询 API 的 P99 延迟达到 2.3s，超出 SLA 200ms 目标 10 倍"




量化程度
"用户经常投诉"
"过去 30 天收到 47 次用户投诉，NPS 从 62 降至 41"




影响范围
"需要优化"
"影响 35% 的企业客户，预计导致 Q3 续约率下降 8%"




因果关系
"数据库太慢"
"随着数据量从 50GB 增长至 200GB，缺乏分区策略导致全表扫描增加 5 倍"

决策记录（ADR）
ADR 模板
ADR（Architecture Decision Record）是轻量级的决策记录格式，用于记录每个重要的技术决策。

ADR 与 RFC 的关系
RFC 是提案过程的完整记录，ADR 是最终决策的精简记录。一个 RFC 可能产生多个 ADR。

实战场景
场景一：数据库迁移 RFC
结构要点：




摘要： 提议将订单服务数据库从 MySQL 5.7 迁移至 PostgreSQL 15，以支持 JSON 查询、更好的并发性能和即将到期的 MySQL 商业许可替代。


问题： MySQL 5.7 将于 2025 年 10 月 EOL，商业许可续约成本增加 60%；同时，新的订单分析功能需要 JSON 查询能力，MySQL 5.7 的 JSON 支持有限。


目标： 零停机迁移，迁移后查询性能不低于当前水平，3 个月内完成。


非目标： 不改变应用层 ORM 框架，不重构数据模型。




场景二：API 版本策略 RFC
关键讨论点：


    

  • URL 路径版本 vs Header 版本 vs Query 参数版本

    • 

  • 向后兼容性保证
    • 

  • 客户端迁移支持计划

场景三：微服务拆分提案
核心结构：

改进方法





过度设计
方案复杂度远超问题复杂度
问自己"最简单的解决方案是什么"




假设共识
跳过问题陈述直接讲方案
用数据验证所有人对问题的理解一致




方案恋爱
只详细写了一个方案
强制自己分析至少 2-3 个替代方案




遗漏运维视角
只考虑开发，不考虑运维和监控
邀请 SRE 参与 RFC 评审




忽略向后兼容
新方案破坏了现有客户端
明确列出兼容性需求和迁移策略

本章小结
RFC 和设计文档不仅是技术方案的载体，更是工程师展示系统思考和技术领导力的舞台。掌握标准化的 RFC 结构、精准的问题陈述技巧、充分的替代方案分析和高效的评审流程，你写出的每一份设计文档都将成为推动技术决策、沉淀团队知识的高质量资产。记住：写设计文档的过程本身就是设计——如果你无法清晰地写出方案，说明你还没有想清楚。
