架构决策记录

ADR 的价值

架构决策记录（Architecture Decision Record, ADR）是一种轻量级文档格式，用于记录重要的架构和技术决策。它的核心价值是回答一个每个工程师迟早都会问的问题："当时为什么要这样设计？"

Michael Nygard 在 2011 年提出 ADR 的概念，强调它的轻量性——一份 ADR 应该能在 10-15 分钟内写完。如果需要更长时间，说明决策本身需要更深入的分析（此时应该先写 RFC）。




ADR 格式标准
经典模板
一份标准的 ADR 包含以下部分：


# ADR-NNN: 标题（动词短语描述决策）

## 状态

[提议 | 已接受 | 已废弃 | 已被 ADR-XXX 取代]

## 日期

YYYY-MM-DD

## 背景

描述推动这个决策的上下文和驱动力。包括技术约束、业务需求、团队情况等。

## 决策

我们决定 [具体决策内容]。

## 后果

### 正面

- ...

### 负面

- ...

### 风险

- ...
实际 ADR 示例
interface ADR {
  id: string;
  title: string;
  status: 'proposed' | 'accepted' | 'deprecated' | 'superseded';
  date: string;
  deciders: string[];
  context: string;
  decision: string;
  consequences: {
    positive: string[];
    negative: string[];
    risks: string[];
  };
  relatedADRs?: string[];
}
# ADR-015: 采用 pnpm Workspace 管理 Monorepo

## 状态

已接受

## 日期

2024-02-20

## 背景

项目已增长到 8 个内部包和 3 个应用。当前使用独立仓库管理，面临以下问题：

1. 跨包改动需要在多个仓库分别提 PR
2. 版本同步困难，经常出现不兼容
3. 共享代码通过 npm 发布，开发体验差
4. CI/CD 流水线重复配置

评估了 npm workspace、yarn workspace、pnpm workspace 和 Nx 四个方案。

## 决策

采用 pnpm workspace 管理 Monorepo。

选择 pnpm 的理由：

- 磁盘效率高（硬链接和符号链接）
- 严格的依赖隔离（防止幻影依赖）
- 内置 workspace 支持，无需额外工具
- 团队已有 pnpm 使用经验

未选择 Nx 的理由：

- 当前项目规模不需要 Nx 的高级功能
- 引入复杂度与收益不成比例
- 未来如需要可以叠加 Nx

## 后果

### 正面

- 跨包改动在单个 PR 中完成
- 共享代码实时链接，无需发布
- 依赖安装速度提升 3x
- CI 配置统一管理

### 负面

- 仓库体积增大
- CI 需要改造（从多仓库到 Monorepo）
- 需要学习 pnpm workspace 命令

### 风险

- 如果项目继续高速增长（> 20 个包），可能需要引入 Turborepo 或 Nx 做构建优化

ADR 作为活文档
ADR 的生命周期
关键原则：ADR 一旦接受，就不修改内容。如果情况变了需要不同的决策，写一份新的 ADR 并标记旧的为"已被取代"。这保证了决策历史的完整性。

async function createADR(title: string): Promise<string> {
  const adrDir = 'docs/adr';
  const existing = readdirSync(adrDir).filter((f) => f.endsWith('.md') && f !== 'INDEX.md');
  const nextNum = String(existing.length + 1).padStart(4, '0');

ADR 是工程组织知识管理的基石。它不是官僚流程，而是对团队智慧的尊重——每一个经过深思熟虑的决策都值得被记录，每一个未来的同事都值得了解"为什么是这样"。当 ADR 成为团队习惯时，知识不再因人员流动而丢失，决策质量也会随着经验积累而持续提升。
