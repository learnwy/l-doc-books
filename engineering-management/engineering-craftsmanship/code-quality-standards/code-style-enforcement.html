代码风格强制

为什么需要强制风格

代码风格争论是团队中最常见的"自行车棚问题"——每个人都有自己偏好的缩进方式、括号位置和引号类型。手动维护风格一致性既低效又容易引发不必要的摩擦。自动化风格强制让团队将注意力从格式争论转移到真正重要的事情上：逻辑正确性和架构质量。

Google 的工程实践手册明确指出：代码风格没有绝对正确，重要的是一致性。一旦团队选定了风格，就通过工具固化它，不再反复讨论。

EditorConfig 配置
EditorConfig 是所有风格统一的起点，因为它不依赖任何具体的语言工具链：


root = true

[*]
indent_style = space
indent_size = 2
end_of_line = lf
charset = utf-8
trim_trailing_whitespace = true
insert_final_newline = true

[*.md]
trim_trailing_whitespace = false

[Makefile]
indent_style = tab
几乎所有主流编辑器都原生支持或通过插件支持 EditorConfig。它解决了最基础的格式统一问题——缩进用空格还是 Tab、换行符用 LF 还是 CRLF。




Prettier：格式化的终极方案
Prettier 是一个有主见的 (Opinionated) 代码格式化工具。它的核心理念是减少配置项，让团队在格式问题上没有争论空间。


{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "trailingComma": "all",
  "printWidth": 100,
  "bracketSpacing": true,
  "arrowParens": "always"
}

Prettier 与 ESLint 的分工
一个常见误区是用 ESLint 来做格式化。现代实践的共识是格式化归 Prettier，逻辑检查归 ESLint：


import eslint from '@eslint/js';
import tseslint from 'typescript-eslint';
import prettier from 'eslint-config-prettier';

export default tseslint.config(eslint.configs.recommended, ...tseslint.configs.recommended, prettier);
eslint-config-prettier 的作用是关闭 ESLint 中所有与 Prettier 冲突的规则，确保两者和平共处。




ESLint 深度配置
ESLint 9+ 采用了全新的 Flat Config 格式，配置文件为 eslint.config.mjs：


import eslint from '@eslint/js';
import tseslint from 'typescript-eslint';

export default tseslint.config(
  eslint.configs.recommended,
  ...tseslint.configs.strictTypeChecked,
  {
    languageOptions: {
      parserOptions: {
        projectService: true,
        tsconfigRootDir: import.meta.dirname,
      },
    },
  },
  {
    rules: {
      'max-lines-per-function': ['warn', { max: 30, skipBlankLines: true, skipComments: true }],
      complexity: ['warn', 10],
      'max-depth': ['warn', 3],
      'max-params': ['warn', 3],
      'no-nested-ternary': 'error',
      '@typescript-eslint/no-explicit-any': 'error',
      '@typescript-eslint/explicit-function-return-type': [
        'warn',
        {
          allowExpressions: true,
          allowTypedFunctionExpressions: true,
        },
      ],
    },
  },
);

Biome：新一代全能工具
Biome 是 Rust 实现的代码工具，集格式化和 Lint 于一身，速度比 Prettier + ESLint 快 10-100 倍：


{
  "$schema": "https://biomejs.dev/schemas/1.9.0/schema.json",
  "formatter": {
    "enabled": true,
    "indentStyle": "space",
    "indentWidth": 2,
    "lineWidth": 100
  },
  "linter": {
    "enabled": true,
    "rules": {
      "recommended": true,
      "complexity": {
        "noExcessiveCognitiveComplexity": {
          "level": "warn",
          "options": { "maxAllowedComplexity": 15 }
        }
      },
      "suspicious": {
        "noExplicitAny": "error"
      }
    }
  }
}

预提交检查
格式化和 Lint 应该在代码进入仓库之前就被保证。husky + lint-staged 是 Node.js 生态的标准方案：


{
  "lint-staged": {
    "*.{ts,tsx}": ["prettier --write", "eslint --fix --max-warnings=0"],
    "*.{json,md,yml}": ["prettier --write"]
  }
}
配合 husky 的 pre-commit 钩子：


#!/usr/bin/env sh
. "$(dirname -- "$0")/_/husky.sh"
npx lint-staged

CI 集成
CI 是风格检查的最终防线。即使开发者绕过了本地钩子，CI 也能阻止不合规代码合并。


name: Code Quality
on: [pull_request]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm run format:check
      - run: pnpm run lint
      - run: pnpm run typecheck

风格指南的核心原则是有主见但可讨论。初始版本应该快速确定，遇到争议时由团队 Tech Lead 拍板。持续迭代比一次完美更重要。

风格一致性的终极目标是让代码看起来像是"一个人"写的。当团队的每个成员都遵循相同的风格规范时，代码库的认知一致性显著提升，新成员上手速度加快，代码评审也能真正聚焦在业务逻辑和设计质量上。
