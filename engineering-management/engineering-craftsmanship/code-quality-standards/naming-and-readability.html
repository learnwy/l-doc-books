命名与可读性

命名的重要性

程序员的大部分时间花在阅读代码而非编写代码上。研究数据表明，阅读与编写的时间比例约为 10:1。这意味着每一个命名决策都是对未来阅读体验的投资——或负债。好的命名能让代码自解释，差的命名迫使阅读者不断中断思维、跳转上下文去理解"这个变量到底是什么"。

Phil Karlton 有句名言："计算机科学中只有两件难事：缓存失效和命名。" 命名之所以难，是因为它要求你真正理解一个概念的本质，然后用最精炼的方式表达出来。




命名的基本原则
意图揭示原则
名字应该回答三个问题：它是什么？它做什么？它为什么存在？如果一个名字需要注释来解释，那这个名字就是失败的。


const d = 30;
const elapsed = 30;
const elapsedDays = 30;
const daysSinceLastLogin = 30;
从 d 到 daysSinceLastLogin，每一步都让意图更加清晰。在现代编辑器的自动补全下，长名字的输入成本几乎为零，但其阅读收益是永久的。

有意义的区分
当需要区分相似的概念时，差异应该体现在名字中：


function copyItems(source: Item[], destination: Item[]): void {
  for (const item of source) {
    destination.push(structuredClone(item));
  }
}

interface CreateUserInput {
  name: string;
  email: string;
}

interface UserRecord {
  id: string;
  name: string;
  email: string;
  createdAt: Date;
}

interface UserViewModel {
  displayName: string;
  avatarUrl: string;
  memberSince: string;
}
Input、Record、ViewModel 三个后缀清晰地区分了用户数据在不同阶段的形态。




各类实体的命名策略
变量命名
布尔变量的命名尤其重要，因为它们直接出现在条件判断中：


if (isActive) { ... }
if (hasPermission) { ... }
if (canEdit && !isArchived) { ... }

if (active) { ... }
if (permission) { ... }
if (edit && !archived) { ... }
上面三行读起来像自然语言，下面三行则需要读者自行推断语义。

类与接口命名
类名应该是名词或名词短语。接口名在不同团队有不同约定：


interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  findByStatus(status: OrderStatus): Promise<Order[]>;
  save(order: Order): Promise<void>;
}

class PostgresOrderRepository implements OrderRepository {
  async findById(id: string): Promise<Order | null> {
    const row = await this.pool.query('SELECT * FROM orders WHERE id = $1', [id]);
    return row.rows[0] ? mapRowToOrder(row.rows[0]) : null;
  }

  async findByStatus(status: OrderStatus): Promise<Order[]> {
    const rows = await this.pool.query('SELECT * FROM orders WHERE status = $1', [status]);
    return rows.rows.map(mapRowToOrder);
  }

  async save(order: Order): Promise<void> {
    await this.pool.query(
      'INSERT INTO orders (id, status, total) VALUES ($1, $2, $3) ON CONFLICT (id) DO UPDATE SET status = $2, total = $3',
      [order.id, order.status, order.total],
    );
  }
}
接口 OrderRepository 描述能力，实现类 PostgresOrderRepository 包含技术选型细节。




可读性进阶技巧
卫语句消除嵌套
深度嵌套的条件是可读性的天敌。卫语句（Guard Clause）通过提前返回来扁平化代码结构：


function getDiscountRate(user: User): number {
  if (!user.isActive) return 0;
  if (!user.subscription) return 0;
  if (user.subscription.isTrial) return 0.05;
  if (user.loyaltyYears >= 5) return 0.2;
  if (user.loyaltyYears >= 2) return 0.1;
  return 0.05;
}

嵌套结构要求读者同时记住所有外层条件；卫语句结构每一行都是独立的，消除了就不再占用工作记忆。


用解释变量替代复杂表达式
当一个表达式的含义不能一眼看出时，引入一个命名中间变量：


const isEligibleForFreeShipping =
  order.subtotal >= FREE_SHIPPING_THRESHOLD && !order.hasOversizedItems && shippingZone !== ShippingZone.Remote;

const requiresManagerApproval =
  order.total >= APPROVAL_THRESHOLD || order.containsRestrictedItems || customer.riskScore > HIGH_RISK_THRESHOLD;

if (isEligibleForFreeShipping && !requiresManagerApproval) {
  applyFreeShipping(order);
}
用查找表替代条件链
const statusConfig: Record<OrderStatus, StatusDisplay> = {
  pending: { label: '待处理', color: '#f59e0b', icon: 'clock' },
  confirmed: { label: '已确认', color: '#3b82f6', icon: 'check' },
  shipped: { label: '已发货', color: '#8b5cf6', icon: 'truck' },
  delivered: { label: '已送达', color: '#10b981', icon: 'package' },
  cancelled: { label: '已取消', color: '#ef4444', icon: 'x' },
};

function getStatusDisplay(status: OrderStatus): StatusDisplay {
  return statusConfig[status] ?? { label: '未知', color: '#6b7280', icon: 'question' };
}
查找表比 switch/case 更紧凑，且修改时只需调整数据，不需要改逻辑。

命名的演进
命名不是一次性决策。随着对领域理解的加深，名字应该随之演进。重命名是最安全的重构之一——现代 IDE 可以在毫秒内完成全局重命名，而好名字带来的理解收益是持续的。

领域理解

深度理解

不要害怕重命名。每一次重命名都是对代码理解的一次提升，也是给下一个阅读者的礼物。命名越精准，代码越能在未来的变更中保持清晰。


优秀的命名是整洁代码的基石。当团队中的每个成员都对命名保持高标准时，代码库会自然地趋向自解释，评审效率随之提升，新成员的上手速度也会显著加快。命名不是小事——它是代码质量最直观的指标。
