整洁代码原则

什么是整洁代码

整洁代码不是追求字符数最少的代码，也不是写得最"聪明"的代码。Robert C. Martin 在《Clean Code》中给出了一个经典定义：整洁代码是别人能轻松读懂、修改和扩展的代码。Bjarne Stroustrup 则强调整洁代码应该"只做好一件事"。这两个视角共同指向一个核心——代码的首要读者是人，而非机器。

整洁代码与糟糕代码之间的差距，往往不是"能不能跑"，而是"半年后还能不能改"。下面这个对比表清晰地展示了两者的差异：

SOLID 原则深度解析
SOLID 是面向对象设计的五条基本原则，但其思想远超 OOP 范畴，在函数式编程和模块化设计中同样适用。


单一职责原则 (SRP)
一个模块应该只有一个引起它变化的理由。违反 SRP 的典型症状是一个函数既处理业务逻辑又操作 DOM 又发送网络请求。


function processOrder(order: Order): void {
  const validated = validateOrder(order);
  const priced = calculateTotal(validated);
  const saved = persistOrder(priced);
  notifyCustomer(saved);
}

function validateOrder(order: Order): ValidatedOrder {
  if (!order.items.length) {
    throw new InvalidOrderError('订单不能为空');
  }
  if (order.items.some((item) => item.quantity <= 0)) {
    throw new InvalidOrderError('商品数量必须为正数');
  }
  return { ...order, validated: true };
}

function calculateTotal(order: ValidatedOrder): PricedOrder {
  const subtotal = order.items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  const tax = subtotal * order.taxRate;
  return { ...order, subtotal, tax, total: subtotal + tax };
}
每个函数只做一件事，processOrder 成为一个编排函数，清晰展现了业务流程。


开闭原则 (OCP)
软件实体应该对扩展开放、对修改关闭。在 TypeScript 中，策略模式是实现 OCP 的经典方法：


interface PricingStrategy {
  calculate(items: OrderItem[]): number;
}

const standardPricing: PricingStrategy = {
  calculate: (items) => items.reduce((sum, i) => sum + i.price * i.quantity, 0),
};

const memberPricing: PricingStrategy = {
  calculate: (items) => items.reduce((sum, i) => sum + i.price * i.quantity * 0.9, 0),
};

function checkout(items: OrderItem[], strategy: PricingStrategy): number {
  return strategy.calculate(items);
}
新增 VIP 定价时，不需要修改 checkout 函数，只需新增一个策略对象。


依赖反转原则 (DIP)
高层模块不应依赖低层模块，两者都应依赖抽象。这在前端工程中意味着组件不应直接 import 具体的 API 客户端或存储实现。


interface UserRepository {
  findById(id: string): Promise<User | null>;
  save(user: User): Promise<void>;
}

class UserService {
  constructor(private readonly repo: UserRepository) {}

  async updateProfile(id: string, updates: Partial<User>): Promise<User> {
    const user = await this.repo.findById(id);
    if (!user) throw new NotFoundError(`用户 ${id} 不存在`);
    const updated = { ...user, ...updates, updatedAt: new Date() };
    await this.repo.save(updated);
    return updated;
  }
}
测试时可以传入内存实现，生产环境传入真实的数据库实现——这就是 DIP 的力量。




函数设计的黄金法则
函数长度与认知负荷
研究表明，人类工作记忆的容量约为 7±2 个信息块。一个超过 20 行的函数，阅读者需要在脑中同时维持过多的上下文，认知负荷急剧上升。


参数数量控制
函数参数越多，理解和测试的难度越高。Martin 建议理想参数数量为 0-2 个，超过 3 个时应考虑使用配置对象。


function createUser(config: {
  name: string;
  email: string;
  role?: UserRole;
  department?: string;
  notifyOnCreate?: boolean;
}): User {
  const defaults = {
    role: UserRole.Member,
    notifyOnCreate: true,
  };
  return buildUser({ ...defaults, ...config });
}

createUser({ name: '张三', email: 'zhang@example.com' });
避免副作用
纯函数是整洁代码的理想形态。当副作用不可避免时，将其隔离到系统边界。


const calculateDiscount = (price: number, tier: CustomerTier): number => {
  const rates: Record<CustomerTier, number> = {
    bronze: 0.05,
    silver: 0.1,
    gold: 0.15,
    platinum: 0.2,
  };
  return price * (rates[tier] ?? 0);
};

const applyDiscountToOrder = async (orderId: string, repo: OrderRepository): Promise<void> => {
  const order = await repo.findById(orderId);
  const discount = calculateDiscount(order.total, order.customerTier);
  await repo.updateDiscount(orderId, discount);
};
calculateDiscount 是纯函数，可独立测试；applyDiscountToOrder 封装了副作用，是整个操作的边界。




抽象层次一致性
一个函数内部的所有语句应该处于同一个抽象层次。混合层次是代码变得难以理解的最常见原因之一。


async function onboardNewEmployee(employee: NewEmployee): Promise<void> {
  const account = await createAccount(employee);
  await assignDefaultPermissions(account);
  await provisionWorkspace(account);
  await sendWelcomeEmail(account);
  await notifyManager(employee.managerId, account);
}
每一行都在同一个抽象层次——"入职流程的步骤"。如果其中某行变成了 await db.query('INSERT INTO accounts...')，抽象层次就被打破了。

一个函数内部不应该跨越超过一个层次的距离。战略层调用战术层，战术层调用实现层——每一层都是对下一层的编排。




错误处理作为一等公民
不要忽略错误
type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E };

function parseConfig(raw: string): Result<AppConfig, ConfigError> {
  try {
    const parsed = JSON.parse(raw);
    if (!isValidConfig(parsed)) {
      return { ok: false, error: new ConfigError('配置格式无效') };
    }
    return { ok: true, value: parsed as AppConfig };
  } catch {
    return { ok: false, error: new ConfigError('JSON 解析失败') };
  }
}

const result = parseConfig(rawInput);
if (!result.ok) {
  logger.error('配置加载失败', { error: result.error });
  process.exit(1);
}
const config = result.value;
Result 类型让错误成为类型系统的一部分，调用方无法"忘记"处理错误。

重构前后对比
改造前——一个承担了过多职责的函数：


async function handle(req: Request): Promise<Response> {
  const body = await req.json();
  if (!body.email || !body.password) {
    return new Response(JSON.stringify({ error: '缺少必填字段' }), { status: 400 });
  }
  const existing = await db.query('SELECT * FROM users WHERE email = $1', [body.email]);
  if (existing.rows.length > 0) {
    return new Response(JSON.stringify({ error: '邮箱已存在' }), { status: 409 });
  }
  const hashed = await bcrypt.hash(body.password, 10);
  const result = await db.query('INSERT INTO users (email, password) VALUES ($1, $2) RETURNING *', [
    body.email,
    hashed,
  ]);
  return new Response(JSON.stringify(result.rows[0]), { status: 201 });
}
改造后——每个函数只做一件事：


async function handleRegister(req: Request): Promise<Response> {
  const input = await parseRegistrationInput(req);
  if (!input.ok) return errorResponse(input.error, 400);

  const conflict = await checkEmailConflict(input.value.email);
  if (conflict) return errorResponse('邮箱已存在', 409);

  const user = await createUser(input.value);
  return jsonResponse(user, 201);
}

async function parseRegistrationInput(req: Request): Promise<Result<RegistrationInput>> {
  const body = await req.json();
  if (!body.email || !body.password) {
    return { ok: false, error: '缺少必填字段' };
  }
  return { ok: true, value: { email: body.email, password: body.password } };
}

async function createUser(input: RegistrationInput): Promise<User> {
  const hashed = await hashPassword(input.password);
  return userRepository.create({ email: input.email, passwordHash: hashed });
}

这些数字不是教条，而是触发审视的信号。当某个函数的圈复杂度超过 10 时，不是必须立刻重构，而是应该问自己：这个复杂度是本质的还是偶然的？


本质复杂度来自业务需求本身——复杂的定价规则、多状态的工作流。偶然复杂度来自糟糕的设计选择——过度嵌套、职责混淆、抽象泄漏。整洁代码的目标是消除偶然复杂度，让本质复杂度以最清晰的方式呈现。
