高效评审技巧

评审的系统化方法

大多数开发者评审代码时采用"从头到尾扫一遍"的线性方式。这种方法在小 PR 中尚可，但面对数百行的变更就会捉襟见肘——重要问题淹没在海量 diff 中，评审者疲劳后质量急剧下降。高效评审需要一套结构化的方法论。



分层评审法
将评审分为四个层次，每层关注不同的问题域：


第一层：理解变更意图
在看任何一行代码之前，先理解这个 PR 要解决什么问题。






信息来源
获取什么
为什么重要

理解"为什么要改"




文件变更列表
影响范围
判断变更是否过大




Commit 历史
实现思路的演进
理解作者的推理过程





如果 PR 没有描述或关联 Issue，这本身就是第一个评审意见——要求作者补充上下文。


第二层：架构与设计
这一层关注的是"做法对不对"，而非"做得好不好"。


interface ArchitectureChecklist {
  responsibility: '新代码放在了正确的模块中？';
  coupling: '是否引入了不必要的依赖？';
  abstraction: '抽象层次是否合适？过度设计还是不足？';
  consistency: '是否与现有架构模式一致？';
  extensibility: '未来需求变更时，修改成本是否可控？';
}
第三层：逻辑正确性
这一层是评审的核心——验证代码是否正确地实现了预期功能。


关键的检查点包括：

异步

并发调用是否安全？是否需要锁或幂等保护？





第四层：可维护性细节

公开 API 是否有 TSDoc？




可读性
逻辑流是否一目了然？

大 PR 的处理策略
当收到一个超大 PR 时，直接要求拆分是最高效的做法：


这个 PR 包含了 1200 行变更，涵盖了 3 个独立的功能。建议拆分为：

1. 数据库 migration 和模型定义（约 200 行）
2. API 端点实现（约 500 行）
3. 前端页面和组件（约 500 行）

拆分后每个 PR 可以独立评审和合并，降低评审负担和合并冲突风险。


高效发现问题的技巧
反向思维法
不要只验证代码在正常情况下是否工作，主动思考"什么情况下会出问题"：


async function transferMoney(from: Account, to: Account, amount: number): Promise<void> {
  await from.debit(amount);
  await to.credit(amount);
}
反向思维的提问：


    

  • 如果 debit 成功但 credit 失败怎么办？
    • 

  • 如果 amount 是负数呢？
    • 

  • 如果 from 和 to 是同一个账户呢？
    • 

  • 如果并发调用导致余额为负怎么办？
    • 



变异测试思维
想象一下，如果把代码中的某个条件取反，测试还能通过吗？


function isEligible(user: User): boolean {
  return user.age >= 18 && user.isVerified;
}
如果改成 user.age >= 18 || user.isVerified，测试还通过吗？如果通过，说明测试覆盖不足。


数据流追踪
从数据的入口追踪到出口，确保每一步转换都是正确的：


在每个节点问自己：


    

  • 数据的类型是否正确？
    • 

  • 是否有数据丢失或意外修改？
    • 

  • 错误信息是否传播正确？

高效评审的核心不在于更快地扫代码，而在于用结构化的方法将注意力集中在最高价值的地方。当你用分层法评审一个 PR 时，架构问题在前 5 分钟被发现，逻辑错误在 15 分钟内定位，细节问题在最后 10 分钟扫描——这比线性阅读 60 分钟的效率高出数倍。
