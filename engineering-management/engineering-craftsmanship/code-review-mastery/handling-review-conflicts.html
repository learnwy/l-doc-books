处理评审冲突

冲突的本质

代码评审中的分歧是正常的，甚至是有价值的——它说明团队成员在认真思考。问题不在于分歧本身，而在于分歧是否被建设性地处理。处理不当的评审冲突会消耗团队信任，降低评审的积极性；处理得当的冲突则能推动团队建立更好的工程标准。



冲突的三个层次
层次一：风格与偏好冲突
这是最低价值但最频繁的冲突类型——缩进用 2 空格还是 4 空格、函数声明用 function 关键字还是箭头函数、import 排序方式等。






场景
错误处理
正确处理





"应该用 forEach 而不是 for...of"
三轮评论争论性能差异
检查团队 lint 规则，按规则执行




"我觉得变量名 idx 比 index 好"
坚持自己的偏好
认识到这是主观偏好，不阻塞




"import 顺序不对"
手动指出每个 import
配置自动排序工具





核心原则：风格争论一旦发生，说明团队缺少自动化强制工具。正确的响应不是讨论谁对谁错，而是建立规则并让机器执行。


const styleConflictResolution = {
  step1: '检查是否有 lint 规则覆盖此场景',
  step2: '如果没有，创建一个 RFC 提案新增规则',
  step3: '团队投票决定后配置工具自动化',
  step4: '此后该类问题不再出现在评审中',
};

承认不确定性
评审者不是全知全能的。承认自己可能是错的，反而增强了意见的可信度：






过于确定的表达
开放的表达





"这肯定会有性能问题"
"我担心这里可能有性能问题，你做过基准测试吗？"




"应该用 X 方案"
"我倾向于 X 方案，原因是...你觉得呢？"




"这个设计是错误的"
"这个设计让我有些担心 Y 方面，我们能讨论一下吗？"







升级路径
当评审中的分歧无法在两轮讨论内解决时，应该果断升级，而不是陷入无休止的评论乒乓。

Tech Lead 的角色

做最终决定，不是选边站




决策涉及跨团队影响

Tech Lead 的裁决应该附带理由说明，并记录在 ADR 中，这样未来遇到类似情况时有据可循。




使用 RFC 解决争议
RFC (Request for Comments) 是处理重大技术争议的标准流程。


interface RFC {
  title: string;
  author: string;
  status: 'draft' | 'open' | 'accepted' | 'rejected' | 'superseded';
  problem: string;
  proposedSolution: string;
  alternatives: Array<{
    name: string;
    description: string;
    prosAndCons: string;
  }>;
  openQuestions: string[];
  decisionDeadline: Date;
}

冲突后的修复
当评审冲突处理不当，导致了负面情绪时，需要主动修复：






场景
修复行动





评审语气过于严厉
私下道歉，重新提交措辞温和的评审




强行推翻了作者方案
解释做决定的完整理由，听取作者的感受




公开场合批评了代码
找机会公开肯定作者在其他方面的贡献




长时间未响应导致积压
主动承担评审任务，帮助清理积压







预防胜于治疗
最好的冲突处理是在冲突发生前就建立清晰的规则：






预防措施
覆盖的冲突类型





自动化格式工具 (Prettier/Biome)
消除所有风格争论




团队编码规范文档
减少"应该这样写还是那样写"的讨论




PR 大小限制（< 400 行）
减少因疲劳导致的评审质量下降




评审 SLA（24 小时内响应）
减少因等待导致的积怨




评论分级标签
明确什么必须改、什么是建议




RFC 模板和流程
给重大分歧提供结构化的解决路径





代码评审中的冲突处理能力，是区分普通工程师和资深工程师的关键维度之一。它考验的不是谁的技术更好，而是谁能在分歧中保持专业、推动决策、维护关系。当你能把每一次冲突都转化为团队学习的契机时，你就成为了团队中不可或缺的稳定力量。
