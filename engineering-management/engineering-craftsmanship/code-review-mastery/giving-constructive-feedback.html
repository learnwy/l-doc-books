建设性反馈

反馈的艺术

代码评审中的每一条评论都是一次沟通行为。同样的技术意见，用不同的方式表达，效果可能天壤之别。建设性反馈的目标不仅是让代码变好，更是让作者在过程中有所成长，并保持对评审流程的积极态度。



评论分级体系
不是每条评论都同等重要。评审者应该对自己的每条评论进行分级，让作者明确知道什么必须改、什么是建议、什么只是讨论。






前缀标签
含义
作者需要做什么





[must-fix]
存在 Bug、安全问题或严重违反规范
必须修复后才能合并




[suggestion]
有更好的做法，但当前方案也可接受
可以选择采纳或解释为什么不改




[nit]
极小的风格偏好
完全可选，不影响 approve




[question]
评审者想理解某段代码的意图
解释即可，不一定需要改代码




[praise]
做得好的地方
继续保持




[discussion]
开放性讨论，无对错
可以异步或同步讨论





interface ReviewComment {
  type: 'must-fix' | 'suggestion' | 'nit' | 'question' | 'praise' | 'discussion';
  content: string;
  lineRange?: { start: number; end: number };
  suggestedCode?: string;
}

一个 PR 评审中的评论可能是这样的：






评论

must-fix
存在 Bug




"考虑用 Map 替代对象，查找性能更好"

有改进空间但不阻塞

正面反馈







用提问代替指令
提问式的反馈比命令式更容易被接受，而且往往能引出更好的解决方案——因为作者比评审者更了解上下文。


对比示例




命令式
提问式





"把这里改成 const"
"这个变量后面有被重新赋值吗？如果没有，用 const 是否更合适？"




"这个函数太长了，拆开"
"这个函数做了几件事情？是否可以按职责拆分来提高可测试性？"




"不要用 any"
"这里用 any 是因为类型难以表达吗？我们可以讨论一下如何给它一个更精确的类型"




"这段代码有 Bug"
"如果用户传入空数组，这里的行为是什么？是否符合预期？"





提问的力量
提问不仅仅是一种表达技巧，它还有认知层面的价值：




赞美比例
研究表明，在持续的反馈关系中，正面反馈与负面反馈的最佳比例约为 3:1（Losada Ratio）。在代码评审中，这意味着每指出 3 个问题，应该至少有 1 条积极反馈。


什么值得赞美




赞美类型
示例





好的设计决策
"用策略模式来处理这个需求真的很优雅，扩展性很好"




完善的错误处理
"错误场景考虑得很全面，特别是网络超时的处理"




清晰的测试
"测试用例的命名非常清楚，读测试就能理解功能规格"




好的命名
"isEligibleForRefund 这个命名让代码逻辑一目了然"




学习进步
"和上次相比，这次的 TypeScript 类型用得更精准了"




主动的文档
"主动写了 ADR 来记录这个决策，给你点赞"





赞美要具体——"不错"没有信息量，"错误处理做得很好，特别是考虑了重试退避和最大重试次数限制"才是有效的正面反馈。




提供替代方案
当建议修改时，提供具体的替代代码比抽象的描述更有效。


差的反馈


"这段代码可以优化一下"




作者的反应：优化什么？怎么优化？


好的反馈


[suggestion] 当前的实现用了嵌套循环来查找匹配项，时间复杂度是 O(n²)。考虑用 Map 来做索引，可以降到 O(n)：


const itemMap = new Map(items.map((item) => [item.id, item]));
const matches = ids.map((id) => itemMap.get(id)).filter((item): item is Item => item !== undefined);


反馈模板框架
一条高质量的评审反馈应包含三个要素：






要素
说明
示例





观察
客观描述看到的内容
"这个函数有 45 行，包含 3 层嵌套"




影响
解释为什么这是个问题
"嵌套结构增加了认知负荷，修改时容易引入 Bug"




建议
提供具体改进方向
"可以用卫语句消除嵌套，或按职责提取子函数"







处理重复问题
当多个地方存在同样的问题时，不需要在每处都留详细评论：


[must-fix] 这里的用户输入没有做验证。类似的问题在 `updateUser()`（第 45 行）和 `deleteUser()`（第 78 行）也存在。建议提取一个统一的 `validateUserInput()` 函数。
这比在三个地方分别留评论更高效，也更清楚地传达了根本问题——缺少统一的输入验证策略。




异步评审的沟通效率
代码评审本质上是异步沟通。每一轮评审往返都有时间成本，因此应该追求单轮高质量的评审，而非多轮碎片化的交流。


一次性完成评审




做法
效果





全部看完再提交所有评论
评论之间可以关联，避免矛盾




明确标注整体态度（approve/request changes）
作者知道下一步该做什么




如果需要讨论，建议切换到同步沟通
复杂问题异步效率太低





评论的完整性
interface ComprehensiveReview {
  overallAssessment: 'approve' | 'approve_with_nits' | 'request_changes';
  summary: string;
  mustFix: ReviewComment[];
  suggestions: ReviewComment[];
  nits: ReviewComment[];
  questions: ReviewComment[];
  praises: ReviewComment[];
}


给新成员的评审特别指南
新成员的代码评审是团队投资回报率最高的活动之一。对新成员的评审应该更加细致和教育性。






评审策略
普通成员
新成员





解释深度
简要指出问题
详细解释原因和背景




建议具体度
给出方向
给出完整代码示例




关注范围
侧重代码质量
同时关注对代码库的理解




响应速度
24 小时内
尽量 4 小时内




跟进方式
异步为主
必要时安排 1:1 讲解





建设性反馈是代码评审中最需要修炼的软技能。技术能力决定你能否发现问题，而反馈能力决定发现的问题能否被有效解决。当你的每条评论都让作者感到"学到了"而非"被批评了"时，你就成为了团队中最有价值的评审者。
