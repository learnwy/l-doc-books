事后复盘写作

复盘的价值

事后复盘（Postmortem）不是为了追责，而是为了学习。Google SRE 手册将无指责的事后复盘（Blameless Postmortem）列为 SRE 文化的基石之一。每一次故障都是一个昂贵的"学费"，如果不通过复盘将教训沉淀为组织知识，这些学费就白交了。



无指责文化
为什么要无指责




有指责的复盘
无指责的复盘





"谁写了这段有 Bug 的代码？"

"谁批准了这次部署？"

结果：人们隐瞒错误，规避责任
结果：人们主动暴露问题，积极改进





无指责的本质
无指责不是说"没有人有责任"，而是说系统设计应该让人难以犯错。如果一个人的操作失误能导致系统级故障，那问题不在人，而在系统缺少足够的安全屏障。




复盘文档模板
标准模板结构
interface PostmortemDocument {
  title: string;
  date: string;
  authors: string[];
  status: 'draft' | 'review' | 'final';
  severity: 'P0' | 'P1' | 'P2' | 'P3';

  summary: string;

  impact: {
    duration: string;
    affectedUsers: number | string;
    affectedServices: string[];
    financialImpact?: string;
    slaViolation: boolean;
  };

  timeline: Array<{
    time: string;
    event: string;
    actor?: string;
  }>;

  rootCause: string;
  triggeringEvent: string;

  detection: {
    howDetected: string;
    detectionDelay: string;
    improvementNeeded: string;
  };

  resolution: {
    immediateAction: string;
    timeToResolve: string;
  };

  actionItems: Array<{
    description: string;
    owner: string;
    priority: 'P0' | 'P1' | 'P2';
    deadline: string;
    ticketId: string;
  }>;

  lessonsLearned: {
    whatWentWell: string[];
    whatWentWrong: string[];
    whereWeGotLucky: string[];
  };
}
实际复盘示例
# 事后复盘：2024-03-15 订单服务不可用事件

## 概要

订单服务因数据库连接池耗尽导致不可用，持续 45 分钟，影响约 12,000 名用户，预估损失订单金额 ¥850,000。

## 严重等级

P1 - 核心业务功能完全不可用

## 影响

- **持续时间**: 15:30 - 16:15（45 分钟）
- **受影响用户**: ~12,000（下单操作）
- **受影响服务**: 订单服务、支付服务、库存服务
- **SLA 违反**: 月度可用性降至 99.89%（目标 99.95%）

## 时间线

| 时间  | 事件                                  |
| ----- | ------------------------------------- |
| 14:00 | PR #237（报表查询优化）合并并自动部署 |
| 15:15 | 数据库慢查询告警触发                  |
| 15:30 | 用户开始报告下单失败                  |
| 15:35 | 值班工程师确认故障，开始排查          |
| 15:45 | 定位到数据库连接池耗尽                |
| 15:55 | 识别出慢查询来源为新上线的报表功能    |
| 16:00 | 回滚 PR #237                          |
| 16:10 | 数据库连接恢复正常                    |
| 16:15 | 服务完全恢复，确认用户可正常下单      |

## 根因分析

PR #237 新增的报表查询在大数据量下（>100 万行）缺少索引，单次查询耗时超过 30 秒。当多个用户同时访问报表时，长耗时查询占满了连接池中的所有连接，导致正常的订单操作无法获取数据库连接。

## 行动项

| 描述                       | 负责人 | 优先级 | 截止日 | 工单     |
| -------------------------- | ------ | ------ | ------ | -------- |
| 为报表查询添加索引         | 张三   | P0     | 03-17  | ORD-1234 |
| CI 添加慢查询检测          | 李四   | P1     | 03-22  | ORD-1235 |
| 读写分离：报表走只读副本   | 王五   | P1     | 03-29  | ORD-1236 |
| 连接池添加超时和队列机制   | 赵六   | P1     | 03-29  | ORD-1237 |
| 建立数据库变更性能测试规范 | 张三   | P2     | 04-05  | ORD-1238 |

事后复盘是将故障从"灾难"转化为"投资"的关键机制。一份高质量的复盘文档不仅修复了当前的问题，更为组织建立了持久的免疫力。最好的工程团队不是从不犯错的团队，而是从每次错误中学得最多、改进最快的团队。
