日志分析技术

核心概念

日志是系统的黑匣子，其质量在正常时无人关注，却在故障时直接决定定位速度；因此日志应作为可观测性的一部分在编码时内建，而非事后补丁。

  • 质量决定速度：好日志 5 分钟定位，差日志可能数小时且需要重新部署复现。
  • 结构化优先：用结构化（JSON 等）日志替代拼接字符串，让日志可被程序化查询与聚合。
  • 级别纪律：级别表达的是"需要谁来处理"，误用级别（如把错误打成 info）会淹没信号。
  • 上下文丰富：在关键路径上带齐请求 ID、用户与耗时等上下文，单条日志才有诊断价值。
  • 可观测性三支柱：日志、指标、追踪各有分工，分布式追踪用于串联跨服务调用链。
  • 聚合与检索：集中聚合与命令式检索（grep/jq）让海量日志可用。

本文后续的结构化日志设计、级别策略、检索技巧、分布式追踪与最佳实践清单，都是这些概念的具体展开。

日志的工程价值

日志是系统的"黑匣子"——当一切正常时无人在意，但当故障发生时，日志质量直接决定了问题定位的速度。好的日志体系能让你在 5 分钟内定位问题，差的日志体系可能让你花 5 小时都找不到头绪。

graph TD
    A[故障告警] --> B{日志质量?}
    B -->|好| C[5 分钟定位问题]
    B -->|差| D[数小时盲目排查]
    C --> E[快速修复]
    D --> F[临时加日志\n重新部署\n等待复现]
    F --> G[问题早已不在]

结构化日志

非结构化 vs 结构化

传统的纯文本日志难以被程序解析和检索。结构化日志使用 JSON 格式，让日志成为可查询的数据。

维度 非结构化日志 结构化日志
格式 [2024-03-15 10:30:45] ERROR - Failed to process order 12345 {"timestamp":"2024-03-15T10:30:45Z","level":"error","msg":"Failed to process order","orderId":"12345"}
搜索 正则匹配，容易遗漏 字段精确查询
聚合 几乎不可能 按字段分组统计
告警 文本匹配，高误报 基于字段的精确告警
分析 人工阅读 机器自动分析

日志结构设计

interface StructuredLog {
  timestamp: string;
  level: 'debug' | 'info' | 'warn' | 'error' | 'fatal';
  message: string;
  service: string;
  traceId?: string;
  spanId?: string;
  userId?: string;
  requestId?: string;
  duration?: number;
  error?: {
    name: string;
    message: string;
    stack: string;
  };
  context?: Record<string, unknown>;
}

实现示例

import pino from 'pino';

const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  formatters: {
    level: (label) => ({ level: label }),
  },
  timestamp: pino.stdTimeFunctions.isoTime,
  base: {
    service: 'order-service',
    env: process.env.NODE_ENV,
  },
});

const requestLogger = (req: Request) =>
  logger.child({
    requestId: req.headers.get('x-request-id'),
    traceId: req.headers.get('x-trace-id'),
    method: req.method,
    path: new URL(req.url).pathname,
  });

日志级别策略

级别定义与使用场景

级别 语义 使用场景 生产环境输出
fatal 系统即将崩溃 不可恢复的错误，进程即将退出 ✅ 始终
error 操作失败 请求失败、外部服务不可用 ✅ 始终
warn 潜在问题 重试成功、降级策略生效、配置不推荐 ✅ 始终
info 业务里程碑 请求开始/结束、订单状态变更、用户登录 ✅ 始终
debug 开发调试 变量值、函数参数、中间状态 ❌ 按需
trace 极细粒度 循环每步、SQL 查询内容 ❌ 仅调试

日志级别决策树

flowchart TD
    A[需要记录日志] --> B{是否影响功能?}
    B -->|是: 操作失败| C{可恢复?}
    C -->|否| D[fatal/error]
    C -->|是: 重试成功| E[warn]
    B -->|否| F{是业务事件?}
    F -->|是| G[info]
    F -->|否| H{是否有助于调试?}
    H -->|是| I[debug]
    H -->|否| J[不记录]

避免常见错误

logger.error('发生错误');
logger.error('用户登录失败', {
  userId: 'user-123',
  error: err.message,
  ip: req.ip,
  userAgent: req.headers['user-agent'],
});

logger.info(`处理订单 ${orderId}`);
logger.info('处理订单', { orderId, itemCount: order.items.length });

logger.debug(`密码是 ${password}`);
logger.debug('用户认证', { userId, method: 'password' });

日志搜索与分析

grep/jq 命令行技巧

cat app.log | jq 'select(.level == "error")'

cat app.log | jq 'select(.orderId == "12345")'

cat app.log | jq 'select(.level == "error") | {time: .timestamp, msg: .message, err: .error.message}'

cat app.log | jq -s 'group_by(.level) | map({level: .[0].level, count: length})'

cat app.log | jq 'select(.timestamp >= "2024-03-15T10:00:00" and .timestamp <= "2024-03-15T11:00:00")'

常用搜索模式

场景 命令/查询 目的
找特定请求 jq 'select(.requestId == "xxx")' 追踪单个请求全链路
错误统计 jq -s 'map(select(.level=="error")) | group_by(.error.name)' 发现最频繁的错误类型
延迟分析 jq 'select(.duration > 1000)' 找出慢请求
时间段过滤 jq 'select(.timestamp | . >= "T1" and . <= "T2")' 故障时间窗口内的日志

分布式追踪

在微服务架构中，一个用户请求可能经过多个服务。分布式追踪通过 Trace ID 将跨服务的日志串联起来。

graph LR
    A[用户请求] --> B[API Gateway]
    B -->|traceId: abc123| C[Order Service]
    C -->|traceId: abc123| D[Payment Service]
    C -->|traceId: abc123| E[Inventory Service]
    D -->|traceId: abc123| F[Stripe API]

OpenTelemetry 集成

import { trace, context, SpanStatusCode } from '@opentelemetry/api';

const tracer = trace.getTracer('order-service');

async function processOrder(order: Order): Promise<OrderResult> {
  return tracer.startActiveSpan('processOrder', async (span) => {
    try {
      span.setAttribute('order.id', order.id);
      span.setAttribute('order.itemCount', order.items.length);

      const validated = await tracer.startActiveSpan('validateOrder', async (childSpan) => {
        const result = await validateOrder(order);
        childSpan.end();
        return result;
      });

      const result = await chargeAndFulfill(validated);
      span.setStatus({ code: SpanStatusCode.OK });
      return result;
    } catch (error) {
      span.setStatus({
        code: SpanStatusCode.ERROR,
        message: error instanceof Error ? error.message : 'Unknown error',
      });
      span.recordException(error as Error);
      throw error;
    } finally {
      span.end();
    }
  });
}

追踪数据模型

概念 说明 类比
Trace 一个请求的完整生命周期 一次客户服务工单
Span Trace 中的一个操作单元 工单中的每个处理步骤
Trace ID 全局唯一标识符 工单编号
Span ID 单个操作的标识符 步骤编号
Parent Span ID 父操作的标识符 触发当前步骤的上一步
Baggage 跨服务传递的上下文 工单附件

日志最佳实践清单

实践 原因 示例
每个请求必须有唯一 ID 追踪完整链路 x-request-id: uuid
错误日志必须包含上下文 否则无法重现 用户 ID、输入参数
敏感信息不入日志 合规和安全要求 脱敏密码、信用卡号

设置合理的日志保留策略 控制存储成本 30 天热存储 + 90 天冷存储 
function createRequestMiddleware(logger: Logger) {
  return async (req: Request, next: () => Promise<Response>): Promise<Response> => {
    const requestId = req.headers.get('x-request-id') ?? crypto.randomUUID();
    const start = performance.now();
    const reqLogger = logger.child({ requestId });

    reqLogger.info('请求开始', {
      method: req.method,
      path: new URL(req.url).pathname,
    });

    try {
      const response = await next();
      const duration = Math.round(performance.now() - start);

      reqLogger.info('请求完成', {
        status: response.status,
        duration,
      });

      return response;
    } catch (error) {
      const duration = Math.round(performance.now() - start);

      reqLogger.error('请求失败', {
        error:
          error instanceof Error
            ? {
                name: error.name,
                message: error.message,
                stack: error.stack,
              }
            : String(error),
        duration,
      });

      throw error;
    }
  };
}

日志是工程师最重要的"感知系统"。好的日志实践不是故障发生后的补救措施，而是在编写代码时就内建的可观测性能力。当你养成在关键路径上打出结构化、上下文丰富的日志的习惯时，未来的每一次故障排查都会感谢今天的你。

小结

  • 日志质量是故障定位速度的直接决定因素，属于设计时就要内建的能力。
  • 结构化日志让机器可查询、可聚合，是后续所有分析的基础。
  • 日志级别要有纪律：它表达"需要谁响应"，而非编码者的随意选择。
  • 上下文（请求 ID、耗时、用户）让单条日志具备诊断价值，否则只能看到孤立事实。
  • 分布式系统靠追踪把日志串成调用链，单一服务的日志无法还原全局。
  • grep/jq 检索与集中聚合，把海量日志变成可用的诊断素材。
