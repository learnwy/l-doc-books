系统设计面试

系统设计面试的本质

系统设计面试不是考你能不能画出一个完美的架构图，而是考察你面对模糊问题时的思考方式。面试官想看到的是：你如何分解问题、如何做权衡取舍、如何在约束条件下做出合理决策。没有标准答案，只有适合当前场景的方案。

面试官的评估框架





级别
面试官期望





中级
能设计基本功能，理解常见组件的用途




高级
能独立完成完整设计，深入讨论权衡取舍




Staff+
能驱动讨论方向，提出面试官没想到的考量





系统设计面试框架
四步框架
Step 1：需求澄清
这是最关键但最容易被跳过的步骤。好的需求澄清能为后面的设计奠定正确方向。


功能性需求：






问题类型
示例问题





核心功能
"用户的主要操作流程是什么？"




用户角色
"有哪些类型的用户？权限有什么区别？"




数据流向
"数据从哪里来？流向哪里？"




边界情况
"需要支持离线使用吗？需要多语言吗？"





非功能性需求：






维度
需要明确的





规模
DAU、QPS、数据量




延迟
可接受的响应时间




可用性
99.9% 还是 99.99%




一致性
强一致还是最终一致




地理分布
单区域还是全球部署





容量估算：






估算项
计算方式
示例





日活用户
题目给出或假设
10M DAU




QPS
DAU × 每用户操作数 / 86400
~1,200 QPS




峰值 QPS
QPS × 峰值系数（通常 2-5x）
~6,000 QPS




存储
每条数据大小 × 数据量 × 保留时间
~10 TB/年




带宽
QPS × 平均响应大小
~60 MB/s





Step 2：高层设计
在白板上画出系统的核心组件和数据流。


高层设计的关键原则：


    

  • 先画最简单的版本，再逐步添加复杂性
    • 

  • 每个组件都能说清楚为什么需要它
    • 

  • 标注数据流的方向和格式
    • 

  • 标注关键的 API 接口
    • 



Step 3：深入设计
面试官会要求你深入某 1-2 个组件。常见深入方向：






深入方向
讨论内容





数据库设计
Schema 设计、索引策略、分库分表




缓存策略
缓存粒度、失效策略、一致性保证




消息队列
消息模型、顺序保证、幂等处理




API 设计
RESTful vs GraphQL、分页、版本控制




数据分片
分片键选择、数据迁移、热点处理





Step 4：总结与扩展




扩展方向
讨论要点





可扩展性
如何应对 10 倍流量增长




容错性
某个组件挂了怎么办




监控
如何知道系统是否健康




安全
认证、授权、数据加密




成本优化
有没有更省钱的方案

常见题型详解
设计 URL 短链服务
需求：


    

  • 给定长 URL，生成短链
    • 

  • 短链访问时 301 重定向到原始 URL
    • 

  • 日均 1 亿次重定向，1000 万次新建
    • 



关键设计决策：






决策点
方案
理由





ID 生成
自增 ID + Base62 编码
简单，短链最短




存储
关系型数据库 + Redis 缓存
读多写少，缓存加速




重定向
301（永久）vs 302（临时）
301 适合 SEO，302 便于统计




冲突处理
数据库唯一索引 + 重试
简单可靠

应对方式

小结
系统设计面试的核心要点：


    

  • 没有标准答案——面试官看的是你的思考过程和权衡能力
    • 

  • 需求澄清是最关键的步骤——问对问题比给出答案更重要
    • 

  • 四步框架保证不遗漏——需求→高层→深入→总结
    • 

  • 容量估算要信手拈来——记住常见数字，能做快速估算
    • 

  • 权衡取舍要说清楚——每个决策都有代价，要能解释
    • 

  • 沟通驱动设计——把面试官当作队友，一起推进方案
    • 

  • 广度和深度兼顾——先展示全局视野，再深入关键组件
    •
