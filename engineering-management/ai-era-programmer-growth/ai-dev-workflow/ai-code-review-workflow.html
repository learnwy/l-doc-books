AI 代码评审工作流

代码评审的痛点

代码评审是软件工程中最重要也最耗时的环节之一。团队常见的评审痛点：

痛点 影响 发生频率
评审周期长 PR 积压，合并延迟 几乎每天
评审质量不均 有人精细有人敷衍 经常
重复性问题 同样的错误反复出现 经常
上下文切换 打断开发者心流 每次评审
评审盲区 安全、性能问题被忽略 偶尔但影响大

AI 不是要取代人类评审者，而是作为第一道自动化过滤层，让人类评审聚焦于真正需要人类判断的部分。

AI 代码评审的能力范围
AI 擅长检测的问题
AI 不擅长的领域
    

  • 业务逻辑正确性：AI 不了解业务上下文，无法判断逻辑是否正确
    • 

  • 架构一致性：AI 难以判断新代码是否符合项目的整体架构风格
    • 

  • 产品需求匹配：AI 无法验证代码是否真正解决了用户需求
    • 

  • 团队约定：项目特有的非正式约定，AI 可能不知道
    • 

  • 政治和协作：评审中的沟通技巧和团队关系管理
    • 



自动化 PR 分析
PR 摘要生成
AI 可以自动为 PR 生成结构化摘要：


## PR 摘要（AI 生成）

### 变更概述
本次变更实现了订单退款功能，涉及 8 个文件的修改。

### 主要变更
- 新增 RefundService，处理退款业务逻辑
- 新增 POST /api/orders/:id/refund 端点
- 修改 OrderRepository，添加退款状态更新方法
- 新增退款相关的数据库迁移

### 影响范围
- 订单模块：新增退款状态和转换逻辑
- 支付模块：调用支付网关的退款 API
- 通知模块：新增退款通知模板

### 风险评估
- 中风险：涉及支付操作，需要仔细验证金额计算
- 低风险：数据库迁移为追加操作，不修改现有列

AI 评审规则配置
项目级规则定义
为项目配置 AI 评审的检查规则：


ai-review:
  rules:
    security:
      severity: error
      checks:
        - no-hardcoded-secrets
        - no-sql-injection
        - no-xss-vulnerability
        - no-eval-usage

    performance:
      severity: warning
      checks:
        - no-n-plus-one-queries
        - no-blocking-main-thread
        - no-unnecessary-re-renders
        - bundle-size-limit: 50kb

    code-quality:
      severity: info
      checks:
        - max-function-length: 50
        - max-cyclomatic-complexity: 10
        - no-duplicate-code
        - consistent-error-handling

    project-conventions:
      severity: warning
      checks:
        - use-result-type-for-errors
        - async-await-over-then
        - no-default-exports
        - barrel-exports-required
自定义检查提示词
为特定的项目约定编写 AI 检查提示词：


检查以下代码变更，重点关注我们项目的以下约定：

1. 所有 Service 方法必须返回 Result<T, AppError> 类型
2. Controller 不允许直接调用 Repository
3. 所有数据库查询必须通过 QueryBuilder，不允许裸 SQL
4. 日志必须使用结构化日志格式 logger.info({ event, data })
5. 所有公开的 API 端点必须有 rate limiting 中间件

对于违反的条目，指出具体的文件和行号，并给出修改建议。

人类评审者的注意事项
在 AI 已经完成第一轮评审的情况下，人类评审者应该：


    

  • 信任 AI 对风格和格式的检查，不重复这部分工作
    • 

  • 重点关注 AI 无法覆盖的领域（业务正确性、架构合理性）
    • 

  • 对 AI 标记的安全和性能问题进行二次确认
    • 

  • 关注代码的可维护性和可读性
    • 

  • 评估变更对系统整体的影响
    • 



减少评审瓶颈
评审队列优化
异步评审流程
    

  • AI 在 PR 提交时立即生成评审报告（秒级）
    • 

  • 开发者根据 AI 反馈自行修复明显问题（分钟级）
    • 

  • 人类评审者在空闲时进行深度评审（小时级）
    • 

  • 减少了人类评审者的等待时间和来回次数

实施路线
第 1 步： 选择一个 AI 代码评审工具（如 CodeRabbit、GitHub Copilot PR Review），在一个项目中试点


第 2 步： 配置项目特定的评审规则，运行两周收集数据


第 3 步： 根据反馈调整规则，减少误报，增加有价值的检查


第 4 步： 在团队中推广，建立人机结合的评审规范


第 5 步： 持续追踪评审效率和质量指标，迭代改进


代码评审的目标不是找茬，而是提升代码质量、传播知识、建立团队共识。AI 帮你解决了"找茬"中机械的部分，让人类评审回归到知识传播和技术讨论的核心价值上。
