AI 原生架构

从 AI 附加到 AI 原生

大多数团队在现有系统上"粘贴"AI 功能——在搜索框旁边加一个"AI 助手"按钮，在工单系统里加一个"AI 分类"标签。这是 AI 附加（AI-Attached）架构。AI 原生（AI-Native）架构则从一开始就围绕 AI 能力来设计整个系统。

事件驱动 AI 架构
核心模式
为什么事件驱动适合 AI 系统：


    

  • 异步性：AI 推理需要时间，事件驱动天然支持异步处理
    • 

  • 可观测性：每个事件都可以被监控和回溯
    • 

  • 弹性：AI 服务不可用时，事件可以排队等待恢复
    • 

  • 可扩展：可以独立扩缩 AI 处理管道的容量
    • 



事件设计
interface AIEvent {
  id: string;
  type: 'inference.request' | 'inference.result' | 'inference.error';
  timestamp: Date;
  payload: {
    model: string;
    input: unknown;
    output?: unknown;
    latencyMs?: number;
    tokenUsage?: { prompt: number; completion: number };
  };
  metadata: {
    userId: string;
    requestId: string;
    traceId: string;
  };
}

可靠性设计
AI 系统的可靠性挑战
传统系统的可靠性是确定性的——要么正常，要么故障。AI 系统的"故障"更加微妙：


    

  • 性能退化：模型精度下降但仍然返回结果
    • 

  • 幻觉：返回看似合理但事实错误的结果
    • 

  • 偏差漂移：输入数据分布变化导致模型表现变差
    • 

  • 级联失败：一个 AI 组件的错误输出被下游组件放大
    •

成本优化策略
    

  • 分层模型：简单任务用便宜模型，复杂任务用贵的模型
    • 

  • 语义缓存：相似请求复用之前的结果
    • 

  • 批量处理：非实时任务攒批处理，降低单价
    • 

  • Token 优化：精简提示词，减少输入输出 Token 数
    • 

  • 本地模型：高频低复杂度任务使用本地部署的小模型
    • 



实践框架
设计 AI 原生架构时的决策清单：


    

  1. AI 是核心路径还是辅助功能？ → 决定架构耦合程度
    2. 

  2. 延迟要求是什么？ → 决定在线/批量/混合模式
    3. 

  3. 数据敏感度如何？ → 决定云端/本地/混合部署
    4. 

  4. 预期规模多大？ → 决定基础设施选型
    5. 

  5. 成本预算多少？ → 决定模型选择和优化策略
    6. 

  6. 可靠性要求多高？ → 决定冗余和降级方案
    7. 



AI 原生架构不是为了"用上最新技术"，而是为了让 AI 能力自然地融入系统的每一个角落，同时保持工程系统的可靠性、可观测性和可维护性。
