ADR 架构决策记录

核心概念

架构决策记录（Architecture Decision Record, ADR）是一种轻量级的文档实践，用于记录架构层面的重要技术决策。每个 ADR 描述一个特定的架构决策，包括上下文、考虑的选项、最终的决定以及决策的后果。ADR 不是重量级的架构文档，而是帮助团队理解"我们为什么这样做"的决策日志。

为什么需要 ADR

问题场景 没有 ADR 的后果 有 ADR 的收益
新人入职问"为什么用这个技术？" 没人记得，猜测和传说 查阅 ADR，完整了解决策背景
要修改一个旧的架构决策 不知道当时的约束，盲目修改 了解原始约束，做出合理的变更
团队对技术选型产生分歧 反复讨论，浪费时间 参考 ADR 流程，结构化做出决策
架构评审时回顾历史 没有记录，无法系统回顾 有完整的决策链条，可追溯
技术领导离职 大量隐性知识流失 决策知识被显性化，可传承

ADR 的核心价值

关键认知：


    

  • ADR 不是为了增加文档负担，而是为了减少沟通成本
    • 

  • ADR 记录的是"为什么"，而不仅仅是"是什么"
    • 

  • 一个被否决的 ADR 同样有价值——它记录了我们考虑过但没有选择的路径
    • 

  • ADR 是活的文档，旧的 ADR 可以被新的 ADR 替代
    • 



ADR 模板
标准 ADR 模板
一个好的 ADR 模板应该简洁但完整：


# ADR-{编号}: {决策标题}

## 状态
{提议 | 已接受 | 已废弃 | 已替代}

## 日期
{YYYY-MM-DD}

## 上下文
{描述做出这个决策的背景。我们面临什么问题？有什么约束？}

## 决策
{描述我们做出了什么决定。用明确的语言。}

## 考虑的选项

### 选项 1: {名称}
- 优势: ...
- 劣势: ...

### 选项 2: {名称}
- 优势: ...
- 劣势: ...

### 选项 3: {名称}
- 优势: ...
- 劣势: ...

## 决策理由
{解释为什么选择了这个选项，而非其他。}

## 后果
{这个决策带来的正面和负面后果是什么？}

## 参与者
{参与决策的人员}
完整 ADR 示例
# ADR-001: 使用 PostgreSQL 作为主数据库

## 状态
已接受

## 日期
2024-03-15

## 上下文
我们正在构建一个新的订单管理系统，需要选择主数据库。
系统预计需要处理：
- 日均 100 万订单
- 复杂的查询需求（多表 JOIN、聚合统计）
- 事务一致性要求高
- 团队有 3 名后端工程师，2 人熟悉 PostgreSQL，1 人熟悉 MySQL

约束条件：
- 预算有限，优先选择开源方案
- 需要在云环境部署（AWS）
- 6 个月内上线

## 决策
使用 PostgreSQL 14 作为主数据库，部署在 AWS RDS 上。

## 考虑的选项

### 选项 1: PostgreSQL
- 优势: 团队熟悉；强大的查询能力；优秀的 JSON 支持；
  开源免费；AWS RDS 完善支持
- 劣势: 写入性能在极端场景下不如 MySQL

### 选项 2: MySQL
- 优势: 生态成熟；写入性能好；运维资料丰富
- 劣势: 团队不够熟悉（仅 1 人）；复杂查询支持不如 PG

### 选项 3: MongoDB
- 优势: Schema 灵活；水平扩展能力强
- 劣势: 不适合强事务需求；团队无人熟悉；
  复杂查询需要额外开发

## 决策理由
1. 团队能力：2/3 的工程师熟悉 PostgreSQL，可以快速启动
2. 业务需求：复杂查询和事务一致性是核心需求，PG 最适合
3. 成本：开源 + AWS RDS，成本可控
4. 时间：团队熟悉度可以显著减少开发时间

## 后果
正面：
- 团队可以快速上手，减少学习成本
- 利用 PG 的高级特性（JSON、全文搜索）减少外部依赖

负面：
- 如果未来需要极高的写入吞吐量，可能需要引入分库分表
- 需要建立 PG 的运维能力和监控体系

## 参与者
- 张三（Tech Lead）
- 李四（高级工程师）
- 王五（架构师）

从提出到落地的完整流程
步骤 1：识别决策需求


    

  • 在技术讨论中识别需要正式决策的问题
    • 

  • 任何人都可以发起 ADR，不仅仅是技术领导
    • 



步骤 2：起草 ADR


    

  • 使用团队约定的模板
    • 

  • 充分描述上下文和约束
    • 

  • 列出所有考虑过的选项（至少 2 个）
    • 

  • 给出初步推荐
    • 



步骤 3：团队评审


    

  • 通过 PR/MR 的方式评审 ADR
    • 

  • 所有受影响的人都应该参与评审
    • 

  • 鼓励异步评审 + 必要时同步讨论
    • 



步骤 4：达成共识


    

  • 不要求所有人同意，但要求所有人被听到
    • 

  • 用"不同意但承诺执行"原则处理分歧
    • 

  • 记录反对意见和最终的决策理由
    • 



步骤 5：正式接受


    

  • 更新 ADR 状态为"已接受"
    • 

  • 合并到代码仓库
    • 

  • 通知所有相关方
    • 



步骤 6：实施与回顾


    

  • 按 ADR 的决策实施
    • 

  • 定期回顾 ADR 是否仍然适用
    • 

  • 当约束条件变化时，可以提出新的 ADR 替代旧的
    •

  • 与代码一起版本管理

  • 通过 PR 流程评审

  • 搜索方便
    • 

  • 不会丢失
    • 

  • 和代码变更关联
    •

实践 4：及时记录
黄金法则： 在做出决策后的 24 小时内记录 ADR。


时间越久，记忆越模糊：


    

  • 当天记录：完整准确
    • 

  • 一周后记录：大致准确，细节模糊
    • 

  • 一个月后记录：很多关键信息已经遗忘
    • 

  • 半年后记录：基本上是事后编造
    •

每半年

项目里程碑

新人入职
让新人阅读关键 ADR 作为入职材料

使用决策矩阵的注意事项：

方法 4：时间盒决策
为决策设定时间限制，避免无限讨论：


原则： 一个及时的好决策，胜过一个完美但迟来的决策。


处理决策中的分歧
分歧处理流程：


处理分歧的原则：


    

  • 关注问题而非人
    • 

  • 用数据和事实说话
    • 

  • 承认不确定性
    • 

  • 设定决策的回顾时间
    • 

  • 记录不同观点，未来可以重新评估
    •

小结
ADR 是技术领导确保决策质量和知识传承的轻量级但高价值的实践。


核心要点回顾：


    

  • ADR 记录"为什么"，而不仅仅是"是什么"——上下文和决策理由最重要
    • 

  • 使用简洁的模板：上下文→选项→决策→理由→后果
    • 

  • ADR 存放在代码仓库中，通过 PR 流程评审
    • 

  • 不是所有决策都需要 ADR，只为重要的、难以逆转的决策写 ADR
    • 

  • 24 小时内记录决策，越早越准确
    • 

  • 否决的选项同样有记录价值
    • 

  • 团队决策方法：RFC、DACI、决策矩阵、时间盒，根据场景选择
    • 

  • 定期回顾 ADR，标记过时的，用新的替代
    • 

  • 从领导示范开始，逐步建立团队的 ADR 文化
    • 

  • ADR 是减少沟通成本的投资，不是增加文档负担
    •
