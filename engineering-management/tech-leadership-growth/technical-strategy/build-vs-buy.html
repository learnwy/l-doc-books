自建与采购决策

核心概念

"自建还是采购"（Build vs Buy）是技术领导面临的最常见的战略决策之一。每当团队需要新的能力时，都会面临这个选择：自己开发还是购买/使用现有的服务或产品？这个决策影响深远——它决定了团队的资源分配、技术栈演进、长期维护成本和竞争优势。

为什么这个决策如此重要

维度 影响
资源分配 自建需要工程时间，采购需要预算
时间 自建周期长，采购可以快速上线
竞争优势 核心能力自建可以形成壁垒
技术债务 自建需要长期维护，采购依赖供应商
团队成长 自建可以积累能力，采购可能限制成长
风险 自建风险在内部，采购风险在外部

Build vs Buy 的频谱

关键认知：


    

  • Build vs Buy 不是非黑即白，而是一个频谱
    • 

  • 决策应该基于战略价值，而不是技术偏好
    • 

  • "我们的工程师可以做得更好"通常是一个危险的假设
    • 

  • 决策需要定期重新评估，环境在变化
    •

降低风险的策略
降低自建风险：


    

  • 先做 MVP/原型验证可行性
    • 

  • 分阶段开发，每阶段验证价值
    • 

  • 建立知识共享机制，减少人员依赖
    • 

  • 使用成熟的框架和库，减少重复造轮子
    • 

  • 投资自动化测试，确保质量
    • 



降低采购风险：


    

  • 选择有退出策略的供应商（数据可导出、标准 API）
    • 

  • 合同中明确 SLA、数据所有权、退出条款
    • 

  • 保持一定的抽象层，便于未来替换
    • 

  • 评估供应商的财务健康度和发展前景
    • 

  • 定期评估是否需要切换
    •

决策审批流程
混合策略
不一定是非此即彼
很多时候，最佳策略是混合使用：


策略 1：先 Buy 后 Build


    

  • 先用采购方案快速验证业务价值
    • 

  • 业务验证成功后，再投入自建
    • 

  • 适用于：不确定业务需求是否稳定的场景
    • 



策略 2：核心 Build + 外围 Buy


    

  • 核心的差异化部分自建
    • 

  • 周边的通用能力采购
    • 

  • 适用于：核心竞争力明确的场景
    • 



策略 3：Open Source + 自定义


    

  • 基于开源方案进行定制
    • 

  • 兼顾控制力和开发效率
    • 

  • 适用于：需要一定定制但不需要从零开始的场景
    • 



策略 4：Build to Replace


    

  • 先用采购方案运行
    • 

  • 同时在背后自建替代方案
    • 

  • 验证自建方案成熟后切换
    • 

  • 适用于：当前采购但长期需要自建的场景
    • 



混合策略的实践
常见决策陷阱
陷阱 1："我们的工程师可以做得更好"
这是最常见的自建偏见。工程师天然倾向于自建，因为：


    

  • 写代码比评估第三方产品更有趣
    • 

  • 自建给了工程师更多控制感和成就感
    • 

  • 低估了"看不见的"工作（安全、运维、升级、文档）
    • 

  • 高估了自建方案的质量和第三方方案的缺陷
    • 



应对方式： 要求提供完整的 TCO 分析，包括 3 年的维护成本和机会成本。


陷阱 2："这个第三方服务太贵了"




看起来贵
实际算账





SaaS 年费 10 万
自建需要 2 个工程师 × 6 个月




每月费用在涨
自建的维护成本也在涨




按用量计费不可控
但用量增长说明业务在增长




功能只用了 30%
但这 30% 也需要自建才能替代





陷阱 3："先自建一个简单版本"
简单版本的陷阱：


    

  • "简单版本"往往不够用，需要持续投入
    • 

  • 一旦开始就很难停下来（沉没成本谬误）
    • 

  • 简单版本的维护成本不简单
    • 

  • 当第三方方案更成熟时，切换成本已经很高
    • 



应对方式： 如果决定自建"简单版本"，提前定义清楚范围和停止条件。


陷阱 4：忽略退出成本
无论选择自建还是采购，都要考虑退出成本：

小结
Build vs Buy 是技术领导最频繁面临的战略决策之一，没有放之四海而皆准的答案。


核心要点回顾：


    

  • Build vs Buy 是一个频谱，不是二选一；还有开源、低代码、混合等选项
    • 

  • 核心竞争力倾向自建，通用能力倾向采购——关键是判断什么是核心
    • 

  • TCO 分析要全面：开发只是开始，维护、机会成本、人员风险都要算
    • 

  • 风险评估要双向：自建有交付和人员风险，采购有锁定和供应商风险
    • 

  • 常见陷阱：低估自建成本、忽略维护负担、"我们能做得更好"的假设
    • 

  • 混合策略经常是最优解：先 Buy 后 Build、核心 Build + 外围 Buy
    • 

  • 决策后的执行同样重要：POC 验证、合同条款、退出策略
    • 

  • 定期重新评估：环境在变，当初的决策可能不再适用
    • 

  • 用 ADR 记录 Build vs Buy 的决策过程，为未来的重新评估提供依据
    • 

  • 决策的质量取决于信息的充分性和分析的系统性
    •
