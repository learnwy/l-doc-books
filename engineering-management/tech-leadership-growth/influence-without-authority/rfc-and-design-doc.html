RFC 和设计文档

核心概念

RFC（Request for Comments）和设计文档是技术组织中最重要的异步决策工具。它们将技术决策从"会议室里最大声音获胜"转变为"最好的论证获胜"，让每个人——不论性格内向还是外向、不论时区差异——都能平等地参与技术讨论和决策。

RFC 和设计文档的战略价值

价值维度 说明
异步决策 跨时区、跨团队的协作决策，不依赖会议
深度思考 写作迫使作者进行深入的思考和分析
知识沉淀 决策的上下文和理由被永久记录
组织学习 新成员可以通过历史 RFC 理解技术决策脉络
质量保证 多人评审提高方案质量，减少盲点
对齐共识 所有利益相关者在实施前达成一致

关键洞察：


    

  • RFC 不是官僚流程，而是确保重要决策得到充分讨论的机制
    • 

  • 好的 RFC 文化能够避免"谁说了算"的政治问题
    • 

  • 设计文档是实施的蓝图，RFC 是决策的依据
    • 

  • ADR 是轻量级的决策日志，记录"我们为什么这样做"
    • 





RFC 流程
RFC 的生命周期
RFC 流程的各阶段
阶段 1：构思（Ideation）






活动
说明





问题定义
明确要解决什么问题




初步调研
了解已有的解决方案和相关技术




非正式讨论
与关键人员进行初步讨论，验证方向




决定是否需要 RFC
评估变更的影响范围，决定是否值得写 RFC





什么时候需要写 RFC：


    

  • ✅ 影响多个团队的架构变更
    • 

  • ✅ 引入新的技术栈或框架
    • 

  • ✅ 废弃现有系统或接口
    • 

  • ✅ 改变开发流程或规范
    • 

  • ✅ 重大的数据模型变更
    • 

  • ❌ Bug 修复或小型优化
    • 

  • ❌ 团队内部的实现细节
    • 

  • ❌ 已有明确共识的变更
    • 



阶段 2：草稿（Draft）


作者撰写 RFC 文档，包含完整的问题描述、方案设计、替代方案分析和实施计划。


草稿阶段的最佳实践：


    

  • 在正式提交评审前，先请 1-2 个信任的同事 Pre-review
    • 

  • Pre-review 可以帮助发现明显的逻辑漏洞和遗漏
    • 

  • 不要追求完美才提交——RFC 就是为了收集反馈
    • 



阶段 3：评审（Review）






角色
职责





作者（Author）
回应评审意见，更新 RFC




评审者（Reviewer）
提供建设性反馈，指出问题和改进点




赞助者（Sponsor）
高级技术负责人，确保 RFC 得到充分讨论




决策者（Decider）
最终决策权，通常是技术负责人或架构师





评审的时间框架：


    

  • 评审期通常为 5-10 个工作日
    • 

  • 对于紧急变更，可以缩短到 2-3 天
    • 

  • 评审期结束后，作者汇总反馈并更新 RFC
    • 

  • 如果有重大分歧，安排同步会议讨论
    • 



阶段 4：决策（Decision）


决策不是投票——它是基于充分讨论后的判断。决策者需要：


    

  1. 确保所有关键利益相关者的意见被听取
    2. 

  2. 权衡各方观点和技术权衡
    3. 

  3. 做出明确的决策并记录原因
    4. 

  4. 对于有争议的决策，解释为什么选择了这个方向
    5. 





提示： RFC 的决策模型推荐使用"Disagree and Commit"——允许不同意，但决策一旦做出，所有人都应该全力支持执行。

评审流程
评审的目标
评审的目标不是找错或证明作者是错的，而是：


    

  1. 确保方案是完备的，没有重大遗漏
    2. 

  2. 发现潜在的风险和问题
    3. 

  3. 分享不同视角的知识和经验
    4. 

  4. 建立共识，对齐期望
    5. 



评审者的最佳实践
✅ 好的评审行为：


    

  • 先理解整体方案，再提出具体问题
    • 

  • 区分"必须解决"和"建议考虑"的反馈
    • 

  • 提供替代方案或改进建议，而非只指出问题
    • 

  • 承认方案的优点，不只关注缺点
    • 

  • 及时回复，不阻塞流程
    • 



❌ 避免的评审行为：


    

  • 不读完就开始提意见
    • 

  • 纠结于不重要的细节而忽略核心问题
    • 

  • 只提问题不提建议
    • 

  • 用反对来彰显自己的技术水平
    • 

  • 拖延评审时间
    •

  • 寻找共同的评判标准

建立 RFC 文化
从零开始建立 RFC 文化的步骤：


    

  1. 选择试点：从一个愿意尝试的团队开始
    2. 

  2. 制定模板：创建简洁实用的 RFC 模板
    3. 

  3. 定义流程：明确 RFC 的生命周期和角色
    4. 

  4. 领导示范：技术负责人带头写第一批 RFC
    5. 

  5. 降低门槛：初期不要求完美，鼓励参与
    6. 

  6. 收集反馈：定期回顾流程的效果和改进点
    7. 

  7. 逐步推广：成功后推广到更多团队
    8. 



RFC 文化的成熟度模型：






阶段
特征
挑战





初始
偶尔有人写 RFC
缺乏流程和模板




规范
有标准模板和流程
评审参与度不高




成熟
RFC 是重大决策的标准流程
避免过度流程化




优化
RFC 文化深入人心，异步决策高效
持续改进，保持活力







提示： RFC 文化最大的敌人是"过度流程化"——当小的变更也需要写 RFC 时，人们会开始绕过流程。保持 RFC 用于真正重要的决策，让流程服务于人，而不是人服务于流程。






小结
    

  • RFC 和设计文档是技术组织最重要的异步决策工具，让最好的论证获胜
    • 

  • RFC 适用于跨团队的重大变更，设计文档适用于详细方案设计，ADR 适用于决策记录
    • 

  • RFC 的生命周期：构思→草稿→评审→决策→实施→完成
    • 

  • 好的设计文档包含：摘要、背景、目标、方案、替代方案、实施计划、风险
    • 

  • 评审的目标是完善方案而非找错——区分 Blocker、Major、Minor、Nit 的评审意见
    • 

  • 处理分歧要聚焦技术事实，遵循升级路径，最终"Disagree and Commit"
    • 

  • 异步决策的优势在于深度思考、平等参与和完整记录
    • 

  • 建立 RFC 文化需要从试点开始，领导示范，逐步推广
    • 

  • 避免过度流程化——RFC 服务于决策质量，而不是增加官僚负担
    • 





RFC 的实际写作技巧
好的 RFC 摘要示例
✅ 好的摘要：




本 RFC 提议将订单服务的数据库从 MySQL 迁移到 TiDB。当前 MySQL 主库已接近写入瓶颈（峰值 QPS 达到单机上限的 80%），且分库分表方案的运维复杂度不可接受。TiDB 提供透明的水平扩展能力，预估可支撑未来 3 年 10 倍的增长。迁移采用双写方案，预计 3 个月内完成，风险可控。




❌ 差的摘要：




我们打算把数据库换成 TiDB，因为 MySQL 快不行了。




写好"替代方案"章节
替代方案章节是 RFC 最能展示思考深度的部分。写好替代方案的要点：


    

  • 至少包含 2-3 个替代方案
    • 

  • 每个方案都给予公正的分析
    • 

  • 说明为什么不选择它们——原因要具体
    • 

  • 如果有人提议了你考虑过但淘汰的方案，他能在这里找到原因
    •
