渐进式总结 (Progressive Summarization)

核心概念

渐进式总结（Progressive Summarization）是 Tiago Forte 提出的笔记提炼方法。它的核心理念是：不要在第一次遇到信息时就试图完美总结，而是在多次接触中逐层提炼。

这解决了 PKM 中的一个经典矛盾：


矛盾：
├── 如果捕获时不整理 → 以后找不到、看不懂
├── 如果捕获时过度整理 → 花太多时间，降低捕获频率
└── 渐进式总结的解答 → 每次接触时多做一点提炼
为什么传统总结方法失败




传统方法
问题
结果





读完立即写详细总结
耗时太长，降低阅读量
要么不读，要么不总结




不做任何总结
内容在需要时找不到或看不懂
等于没有笔记




只划线标注
划太多等于没划
无法快速定位核心内容




一次性整理完
整理时已忘记当初为什么保存
整理出的结果脱离真实需求





渐进式总结的洞见是：总结的最佳时机不是第一次阅读时，而是需要使用时。




五层提炼模型
渐进式总结采用五层逐步深入的提炼方式。


层次概览
第 0 层：原始内容
   ↓  [首次捕获]
第 1 层：加粗关键段落
   ↓  [首次回顾]
第 2 层：高亮核心句子
   ↓  [再次回顾]
第 3 层：执行摘要
   ↓  [需要使用时]
第 4 层：重新混合
   ↓  [创作输出时]
第 0 层：原始内容
直接保存的原始信息。可以是文章摘录、会议记录、阅读笔记等。


示例：保存的一篇技术文章笔记

MongoDB 和 PostgreSQL 是两种不同类型的数据库。MongoDB 是
文档数据库，使用类 JSON 的 BSON 格式存储数据。PostgreSQL
是关系型数据库，使用表和行来存储数据。在选择数据库时，需要
考虑数据结构的灵活性需求。如果数据结构经常变化，MongoDB
的无模式特性更有优势。如果需要复杂的关联查询和事务支持，
PostgreSQL 更合适。在性能方面，MongoDB 在写入密集型场景
表现更好，PostgreSQL 在复杂查询方面更优。但这只是一般性
结论，具体性能取决于索引设计、查询模式和数据量。在团队
能力方面，也需要考虑团队对 SQL 和 NoSQL 的熟悉程度。
很多团队选择同时使用两种数据库，利用各自的优势处理不同
类型的数据。
在第 0 层，你只需要保存，不需要做任何处理。

第 3 层：执行摘要
在笔记顶部写一段用自己的话概括的执行摘要。这通常发生在你需要实际使用这条笔记的时候。

第 4 层：重新混合

按需提炼原则
渐进式总结的核心哲学是"按需提炼"（Just-in-time summarization）。


与"预先总结"的对比




维度
预先总结
按需提炼





时机
捕获时立即总结
需要用时才深度总结




投入
前期投入大
分散到每次使用




效率
可能总结了永远不会用的内容
只总结真正用到的内容




风险
可能遗漏未来需要的信息
原始内容始终保留




适用
已知会频繁使用的内容
不确定未来是否会用





触发提炼的时机
什么时候从第 0 层提炼到第 1 层？
→ 当你第一次回顾这条笔记时

什么时候从第 1 层提炼到第 2 层？
→ 当你第二次需要参考这条笔记时

什么时候写第 3 层执行摘要？
→ 当你需要在项目中使用这条笔记的内容时

什么时候进行第 4 层重新混合？
→ 当你在创作输出（文章、演讲、方案）时
关键洞见：大部分笔记永远不会超过第 0-1 层，这是正常的。只有真正有价值的笔记才会被逐步提炼到第 3-4 层。


提炼深度分布
一个健康的 PKM 系统中，各层笔记的比例大致如下：


第 0 层 ████████████████████ 100% 所有笔记
第 1 层 ████████████         60%  回顾过一次的
第 2 层 ██████               30%  回顾过两次的
第 3 层 ███                  15%  需要使用的
第 4 层 █                     5%  用于创作的

与费曼技巧的结合
费曼技巧要求你用简单语言解释概念。这可以作为第 3 层执行摘要的质量标准：


第 3 层执行摘要 = 费曼式解释
├── 用最简单的语言
├── 不使用术语（或解释术语）
├── 用类比帮助理解
└── 如果解释不清楚，说明你还没真正理解


实操示例：完整的渐进式总结流程
场景：阅读一篇关于"事件驱动架构"的文章
第 0 层（捕获）：


来源：Martin Fowler - Event-Driven Architecture
日期：2024-03-01

事件驱动架构（EDA）是一种软件架构模式，其中系统的各个
组件通过事件进行通信。事件是系统中发生的重要状态变化。
EDA 有几种主要模式：事件通知（Event Notification）、
事件携带状态转移（Event-Carried State Transfer）和
事件溯源（Event Sourcing）。事件通知是最简单的模式，
组件只发送"某事发生了"的通知，接收方需要回查源系统获取
详细信息。事件携带状态转移则在事件中包含所有必要数据，
接收方不需要回查。事件溯源将所有状态变化都记录为事件
序列，系统状态可以通过重放事件来重建...
第 1 层（首次回顾时加粗）：

第 3 层（需要用于架构设计时写摘要）：


## 执行摘要

EDA 三种模式的选择：
- 事件通知：最简单，适合松耦合通知，但增加了回查开销
- 事件携带状态转移：数据自包含，适合高性能场景，但事件体积大
- 事件溯源：完整历史记录，适合审计和调试，但查询当前状态需要重建

选择决策树：
- 需要审计追踪？→ 事件溯源
- 对延迟敏感？→ 事件携带状态转移
- 只需要解耦？→ 事件通知

小结
渐进式总结是一种务实的笔记提炼方法，它解决了"过度整理"和"不整理"之间的矛盾。


核心要点回顾：


    

  • 核心理念：不在第一次就完美总结，而是在多次接触中逐层提炼
    • 

  • 五层提炼：原始内容 → 加粗关键段落 → 高亮核心句子 → 执行摘要 → 重新混合
    • 

  • 按需提炼：只有真正用到的笔记才需要深层提炼，大部分笔记停留在第 0-1 层是正常的
    • 

  • 健康比例：100% → 60% → 30% → 15% → 5%，层层递减
    • 

  • 与 Zettelkasten 结合：渐进式总结用于文献笔记阶段，永久笔记直接是深度提炼
    • 

  • 核心错误是过度标注和强迫全部提炼——记住，提炼是投资，只投有回报的
    •
