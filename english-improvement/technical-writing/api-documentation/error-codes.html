错误码文档

错误码设计模式

良好的错误码体系能帮助开发者快速定位问题。设计错误码时遵循以下原则：

原则 说明 示例
唯一性 每个错误码全局唯一，可追溯 USER_NOT_FOUND
可读性 错误码本身具有含义 PAYMENT_INSUFFICIENT_BALANCE
分层性 通过前缀区分模块 AUTH_、ORDER_、USER_
稳定性 已发布的错误码不可变更语义 仅可新增，不可修改

错误码命名规范

{模块}_{描述}

AUTH_TOKEN_EXPIRED        → 认证模块，Token 过期
ORDER_ITEM_OUT_OF_STOCK   → 订单模块，商品库存不足
USER_EMAIL_ALREADY_EXISTS → 用户模块，邮箱已存在

HTTP 状态码映射

业务错误码应与 HTTP 状态码正确映射：

HTTP 状态码 含义 使用场景 错误码示例
400 Bad Request 请求参数不合法 INVALID_PARAMETER
401 Unauthorized 未提供或无效的认证凭证 AUTH_TOKEN_INVALID
403 Forbidden 认证通过但权限不足 AUTH_PERMISSION_DENIED
404 Not Found 请求的资源不存在 USER_NOT_FOUND
409 Conflict 资源冲突 USER_EMAIL_ALREADY_EXISTS
422 Unprocessable Entity 参数格式正确但语义错误 ORDER_AMOUNT_EXCEEDS_LIMIT
429 Too Many Requests 请求频率超限 RATE_LIMIT_EXCEEDED
500 Internal Server Error 服务器内部错误 INTERNAL_ERROR
502 Bad Gateway 上游服务异常 UPSTREAM_SERVICE_ERROR
503 Service Unavailable 服务暂不可用 SERVICE_MAINTENANCE

错误响应格式

统一的错误响应结构便于客户端统一处理：

{
  "code": "AUTH_TOKEN_EXPIRED",
  "message": "访问令牌已过期，请重新获取",
  "details": {
    "expiredAt": "2025-03-15T10:30:00Z",
    "tokenType": "access_token"
  },
  "requestId": "req_7f8a9b2c",
  "docUrl": "https://docs.example.com/errors/AUTH_TOKEN_EXPIRED"
}
字段 类型 必填 说明
code string 是 业务错误码，全局唯一标识
message string 是 人类可读的错误描述
details object 否 错误的上下文信息
requestId string 是 请求唯一标识，用于日志追踪
docUrl string 否 指向该错误码详细文档的链接

错误码速查表

按模块组织的错误码速查表是 API 文档的核心参考内容：

认证模块

错误码 HTTP 状态码 描述 排查建议
AUTH_TOKEN_INVALID 401 Token 格式不正确或已被吊销 检查 Token 格式，确认未被手动吊销
AUTH_TOKEN_EXPIRED 401 Token 已过期 使用 refresh_token 重新获取
AUTH_PERMISSION_DENIED 403 当前用户无权访问该资源 确认用户角色是否包含所需权限
AUTH_MFA_REQUIRED 403 需要多因素认证 引导用户完成 MFA 验证

用户模块

错误码 HTTP 状态码 描述 排查建议
USER_NOT_FOUND 404 指定用户不存在 确认用户 ID 是否正确
USER_EMAIL_ALREADY_EXISTS 409 邮箱已被注册 引导用户使用该邮箱登录
USER_ACCOUNT_DISABLED 403 账户已被禁用 联系管理员恢复账户

订单模块

错误码 HTTP 状态码 描述 排查建议
ORDER_ITEM_OUT_OF_STOCK 422 商品库存不足 减少购买数量或等待补货
ORDER_AMOUNT_EXCEEDS_LIMIT 422 订单金额超出限制 拆分订单或联系客服提额
ORDER_ALREADY_CANCELLED 409 订单已被取消，不可重复操作 无需重复取消

客户端错误处理文档

帮助调用方正确处理错误是 API 文档的重要职责：

async function callAPI(url, options) {
  const response = await fetch(url, options);

  if (!response.ok) {
    const error = await response.json();

    switch (response.status) {
      case 401:
        if (error.code === 'AUTH_TOKEN_EXPIRED') {
          await refreshToken();
          return callAPI(url, options);
        }
        redirectToLogin();
        break;
      case 429:
        const retryAfter = response.headers.get('Retry-After');
        await delay(retryAfter * 1000);
        return callAPI(url, options);
      default:
        throw new APIError(error.code, error.message);
    }
  }

  return response.json();
}

错误处理策略

状态码范围 策略 说明
400-499 客户端修正 检查请求参数、认证信息、权限
401 自动刷新 Token Token 过期时自动刷新并重试
429 退避重试 根据 Retry-After 头延迟后重试
500-599 指数退避重试 服务端错误，最多重试 3 次

错误码排查指南

文档中应为常见错误提供完整的排查路径：

问题：调用 POST /v2/orders 返回 422 ORDER_ITEM_OUT_OF_STOCK

排查步骤：
1. 确认请求体中的 itemId 是否正确
2. 调用 GET /v2/products/{itemId} 查询当前库存
3. 若库存为 0，等待补货或选择替代商品
4. 若库存充足但仍报错，检查是否有并发下单竞争
5. 携带 requestId 联系技术支持进一步排查

最佳实践

  • 每个错误码附带排查建议：减少开发者查阅外部资料的成本
  • 提供 requestId：确保每个错误响应都包含可追溯的请求标识
  • 文档链接嵌入响应：在 docUrl 字段中链接到具体错误码文档
  • 区分面向用户与面向开发者的信息：message 给终端用户，details 给开发者
  • 版本化错误码：新增错误码时在变更日志中记录，永不删除已有错误码
  • 监控高频错误码：通过错误码统计发现文档缺失或 API 设计问题
