写作原则与风格

核心概念

技术文档的核心使命是帮助读者快速找到信息、准确理解概念、顺利完成任务。与文学写作追求美学表达不同，技术写作追求的是传达效率——让正确的信息以最小的认知成本抵达读者。

优秀的技术文档建立在四大支柱之上：准确性、一致性、可维护性和适应性。这四个原则彼此交织，共同构成技术写作的质量基线。

理解这四大原则之间的关系和侧重点，是技术写作者建立专业判断力的第一步。

准确性工程
准确性是技术文档的生命线。一篇文档如果信息不准确，其他所有优点都将失去意义——读者会对整篇文档产生怀疑。准确性不是"写完后检查一下"就能保证的，它需要一套系统化的工程实践。


事实准确是最基础的要求。文档中的每一个技术描述都必须与系统的实际行为一致。这包括 API 的参数和返回值、配置项的默认值、命令行工具的选项和输出格式。技术作者应当通过实际操作来验证文档内容，而不是凭记忆或推测来编写。


代码可运行是准确性的硬指标。所有出现在文档中的代码示例都必须能够直接复制并成功执行。许多团队采用"文档即测试"的策略，在 CI 流水线中自动提取并运行文档中的代码块。

版本同步是准确性维护中最容易被忽视的环节。每当软件发布新版本时，文档必须同步更新。最佳实践是将文档纳入发布检查清单，并在 Pull Request 模板中加入"文档是否已更新"的必选项。


一致性体系
一致性让文档"看起来是一个整体"。当读者在不同页面之间切换时，如果术语、格式和语气始终统一，读者的认知负担会显著降低，阅读体验也会更加流畅。


术语一致是最核心的一致性要求。同一个概念在整个文档站点中必须使用同一个名称。例如，如果选择了"容器"这个术语，就不应该在其他地方用"实例"来指代同一个概念。建立和维护术语表是保证术语一致性的标准方法。


术语表的建立遵循以下规则：


    

  • 每个概念指定唯一的标准术语和英文对照
    • 

  • 列出该术语常见的误用形式，帮助审稿人识别不一致
    • 

  • 标注术语的使用上下文，避免在不当场景使用
    • 

  • 术语表作为项目级文件维护，全团队共享
    • 



格式一致覆盖标题层级、代码块风格、表格布局、告示框使用等各个方面。一个成熟的技术写作团队会建立风格指南，明确规定每一种格式元素的使用标准。

语气一致确保读者在整篇文档中感受到统一的声调。技术文档最常用的语气是第二人称祈使语气，直接告诉读者"你做什么"。在同一篇文档中切换人称是常见的一致性失误。


风格指南构建
风格指南是技术写作团队的宪法文件。它将一致性从"个人习惯"升级为"团队标准"，是多人协作的文档项目中不可或缺的基础设施。


语气与人称的选择取决于文档类型和目标受众：

时态选择在技术文档中有明确的规则：


    

  • 一般现在时用于描述系统当前行为（"该函数返回一个布尔值"）
    • 

  • 祈使语气用于操作指导（"点击保存按钮"）
    • 

  • 过去时用于变更日志和版本说明（"修复了内存泄漏问题"）
    • 

  • 将来时用于路线图和计划说明（"下一版本将支持批量导入"）
    • 



中文技术写作的排版规范是中文技术文档特有的风格要素，这些细节直接影响文档的专业度：


    

  • 中英文之间加空格：使用 Docker 部署 而非 使用Docker部署
    • 

  • 专有名词使用正确大小写：GitHub、JavaScript、macOS
    • 

  • 数字与单位之间加空格：100 MB 而非 100MB
    • 

  • 全角标点：中文语境使用全角标点（，。！？），代码内容使用半角
    • 

  • 半角括号内全部使用半角标点：(see RFC 7231) 而非 （see RFC 7231）
    • 



构建风格指南时，建议从已有的成熟规范开始（如 Google Developer Documentation Style Guide 或中文技术文档写作规范），根据团队实际情况进行裁剪和补充，而不是从零开始制定。


可维护性策略
文档不是写完就结束的一次性产物，而是需要持续维护的活资产。可维护性决定了一篇文档在六个月、一年之后是否还能保持准确和有用。


模块化写作是可维护性的基石。每篇文档应该独立成篇，聚焦于一个明确的主题。当一个概念被多篇文档引用时，应该将它写在一处，其他地方通过链接引用。这就是"单一信息源"（Single Source of Truth）原则。


模块化还体现在文档的粒度控制上。一篇文档不宜过长（超过 2000 字读者容易迷失），也不宜过短（不到 300 字的页面增加导航成本）。合理的粒度是：每篇文档回答一个主要问题，包含 3-6 个小节。


版本控制是文档可维护性的技术保障。使用 Git 管理文档变更历史，可以追溯每次修改的原因和内容。在文档项目中推荐以下实践：

文档生命周期管理也是可维护性的重要组成部分。当一个功能被废弃时，相应的文档应该被标记为已废弃（而非直接删除），并指引读者去往替代方案的文档页面。


小结
    

  • 技术文档建立在准确性、一致性、可维护性和适应性四大原则之上，准确性是最基础的要求
    • 

  • 准确性需要系统化的工程实践：代码可运行验证、版本同步检查、外部链接检测
    • 

  • 一致性覆盖术语、格式和语气三个层面，术语表是保证术语一致性的标准工具
    • 

  • 风格指南将一致性从个人习惯升级为团队标准，涵盖人称、时态和排版规范
    • 

  • 可维护性依靠模块化写作、单一信息源、版本控制和自动化检查来保障
    • 

  • 文档是持续维护的活资产，需要生命周期管理而非"写完即弃"
    •
