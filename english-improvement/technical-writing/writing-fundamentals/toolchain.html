工具链

文档编写工具

Markdown 编辑器

工具 特点 适用场景
VS Code 丰富的插件生态，Git 集成 开发者日常写作
Typora 所见即所得的 Markdown 编辑 纯文档写作
Obsidian 双向链接、知识图谱 知识管理和内部文档
Notion 协作编辑、数据库视图 团队协作文档

选择编辑器时应考虑团队规模和协作需求。对于单人维护的开源项目，VS Code 配合 Markdown All in One 插件已经足够；对于需要多人实时协作的团队文档，Notion 或 Confluence 更合适。关键原则是不要在工具选型上花费过多时间——能让团队顺畅写作的工具就是好工具。

文档站点生成器

工具 技术栈 特点 部署复杂度
Docusaurus React 版本化、国际化、搜索 中等
VitePress Vue 轻量快速、Markdown 扩展 低
MkDocs Python Material 主题、简单配置 低
GitBook 云服务 零配置、团队协作 极低
Nextra React 基于 Next.js，支持 MDX 中等
Sphinx Python reStructuredText，自动文档生成 中等

文档站点生成器的选择通常与团队的技术栈一致。React 项目倾向于 Docusaurus，Vue 项目选择 VitePress，Python 项目用 MkDocs 或 Sphinx。如果文档需要从代码注释自动生成 API 文档，Sphinx（配合 autodoc）和 TypeDoc 是更好的选择。

API 文档工具

API 文档是技术文档中特殊而重要的一类，需要专门的工具来保证文档与代码的同步。

工具 适用场景 核心功能
Swagger / OpenAPI REST API 交互式文档、代码生成、Mock 服务
TypeDoc TypeScript 库 从类型定义自动生成文档
Storybook UI 组件 组件文档、可交互示例
Javadoc Java 项目 从注释生成 HTML 文档
Doxygen C/C++ 项目 多语言支持，调用关系图

API 文档最佳实践是"文档即代码"——将 OpenAPI 规范文件（openapi.yaml）纳入版本控制，通过 CI 自动生成文档页面。这确保了文档始终与实际 API 保持一致，避免手动维护导致的过期问题。

文档质量工具

语法与拼写检查

工具 功能 集成方式
markdownlint Markdown 格式规范检查 CLI / VS Code 插件
textlint 可定制的文本检查 CLI / CI 集成
Vale 企业级文档风格检查 CLI / GitHub Actions
cspell 代码感知的拼写检查 CLI / VS Code 插件

Vale 值得特别关注。它支持通过 YAML 定义自定义风格规则，可以检查术语一致性（如统一使用"用户"而非混用"使用者"）、禁止被动语态、限制句子长度等。Microsoft、Google 和 Red Hat 都开源了自己的 Vale 风格包，可以直接复用或参考。

链接检查

文档中的失效链接是常见的质量问题。推荐在 CI 流程中加入链接检查：

  • markdown-link-check：检查 Markdown 文件中的所有链接是否可达
  • lychee：Rust 编写的高性能链接检查器，支持并发请求和多种输出格式
  • broken-link-checker：适用于已部署的文档站点，爬取所有页面检查链接

CI/CD 集成

文档质量检查应纳入 CI 流水线：

# GitHub Actions 示例
docs-lint:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - name: Lint Markdown
      run: npx markdownlint-cli docs/**/*.md
    - name: Check spelling
      run: npx cspell docs/**/*.md
    - name: Validate links
      run: npx markdown-link-check docs/**/*.md
    - name: Style check
      run: vale docs/

将文档检查作为 PR 合入的必要条件，与代码 lint 同等对待。这样能在问题引入时立即发现，而不是在文档发布后才被用户报告。

文档协作工具

版本控制

  • Git：所有文档使用 Git 管理变更
  • 分支策略：docs/feature-name 分支用于新文档
  • PR 评审：文档变更需要至少一人评审
  • 提交规范：使用 docs: 前缀的 Conventional Commits

文档的 Git 工作流与代码类似但有一个关键区别：文档 PR 的评审重点不是逻辑正确性，而是表达清晰度和读者友好性。建议让非作者（最好是文档的目标读者角色）来评审，因为作者往往对自己写的内容有"知识诅咒"盲区。

图表工具

工具 类型 适用场景
Mermaid 文本转图表 流程图、序列图、ER 图
Draw.io 可视化编辑 架构图、网络拓扑
PlantUML 文本转 UML 类图、时序图
Excalidraw 手绘风格 概念图、头脑风暴

文本转图表工具（Mermaid、PlantUML）的最大优势是可以纳入版本控制——图表的变更历史和代码一样清晰可追溯。可视化编辑工具（Draw.io）适合复杂的架构图，但要注意将源文件（.drawio 或 .svg）而非截图纳入仓库。

截图与录屏

  • 截图标注：使用 CleanShot X 或 Snagit 添加标注
  • GIF 录制：使用 LICEcap 或 Kap 录制操作演示
  • 视频教程：使用 OBS Studio 录制完整教程

截图和录屏的命名应具有描述性（如 login-flow-step3.png 而非 screenshot1.png），并集中存放在 docs/assets/ 或 docs/images/ 目录下。对于需要频繁更新的 UI 截图，考虑使用 Playwright 或 Cypress 自动化截图脚本，在 CI 中自动更新。

文档搜索与分析

文档站点的搜索体验直接影响用户满意度。主流方案包括：

方案 类型 特点
Algolia DocSearch 托管服务 免费（开源项目）、自动爬取、即时搜索
Pagefind 静态搜索 无服务端、构建时索引、体积极小
Typesense 自托管 容错搜索、Facet 过滤
FlexSearch 客户端 纯 JS、离线可用

文档分析工具能帮助了解哪些页面被频繁访问、用户在哪里流失。Google Analytics 或 Plausible 可以追踪页面浏览量和停留时间，结合搜索日志分析"搜索无结果"的关键词，能发现文档的内容缺口。

文档发布与托管

方案 特点 成本
GitHub Pages 免费、Git 集成 免费
Vercel 自动部署、预览环境 免费/付费
Netlify 自动构建、表单收集 免费/付费
Cloudflare Pages 全球 CDN、无限带宽 免费
ReadTheDocs 版本管理、搜索 免费/付费

文档的部署应做到每次 PR 合入后自动构建发布。Vercel 和 Netlify 的预览部署功能特别有价值——每个 PR 都会生成一个独立的预览链接，评审者可以直接在浏览器中查看文档渲染效果，而不是在 Markdown 源码中猜测最终样式。
