变更日志

什么是变更日志

变更日志（CHANGELOG）是一个按时间倒序排列的文件，记录项目每个版本的显著变更。它面向用户和开发者，帮助他们了解项目的演进过程和升级影响。

变更日志 vs 发布说明

维度 变更日志 (CHANGELOG) 发布说明 (Release Notes)
受众 开发者和技术用户 所有用户（包括非技术）
内容 所有技术变更的完整记录 关键变更的概括性描述
格式 结构化列表，按类型分组 自由格式，可包含截图和演示
位置 仓库根目录 CHANGELOG.md GitHub Releases、博客
语气 简洁客观的技术描述 面向市场的功能介绍

Keep a Changelog 格式

Keep a Changelog 是被广泛采用的变更日志格式标准。

变更类型

类型 英文 说明
新增 Added 新功能
变更 Changed 对已有功能的变更
废弃 Deprecated 即将移除的功能
移除 Removed 已移除的功能
修复 Fixed Bug 修复
安全 Security 安全漏洞修复

格式示例

# 变更日志

本项目所有显著变更都将记录在此文件中。

格式基于 [Keep a Changelog](https://keepachangelog.com/zh-CN/)，版本管理遵循 [语义化版本](https://semver.org/lang/zh-CN/)。

## [Unreleased]

### 新增

- 支持暗色模式主题切换

## [1.2.0] - 2024-08-15

### 新增

- 新增导出为 PDF 功能
- 支持自定义快捷键绑定

### 变更

- 将默认分页大小从 20 调整为 50

### 修复

- 修复中文搜索分词不准确的问题
- 修复大文件上传超时的问题

## [1.1.0] - 2024-07-01

### 新增

- 新增批量操作功能

### 废弃

- `legacyAuth()` 方法将在 2.0 版本移除，请迁移至 `auth()`

## [1.0.0] - 2024-06-01

### 新增

- 初始版本发布

语义化版本关联

变更日志与语义化版本 (SemVer) 紧密配合，帮助用户评估升级风险。

版本号与变更类型对应

版本变更 格式 变更类型 升级风险
主版本 X.0.0 包含破坏性变更（Removed、不兼容的 Changed） 高，需要迁移
次版本 x.Y.0 新增功能（Added），向后兼容的 Changed 低，建议阅读变更
修订版 x.y.Z 修复 Bug（Fixed、Security） 极低，建议立即升级

破坏性变更标注

## [2.0.0] - 2024-10-01

### ⚠ 破坏性变更

- `createUser(name)` 签名变更为 `createUser(options)`
- 最低 Node.js 版本要求提升至 18

### 迁移指南

将原有的调用方式：createUser('张三') 修改为：createUser({ name: '张三', role: 'user' })

约定式提交 (Conventional Commits)

使用约定式提交规范可以从 Git 提交记录自动生成变更日志。

提交消息格式

<类型>(<作用域>): <描述>

[可选的正文]

[可选的脚注]

类型与变更日志映射

提交类型 说明 对应变更日志类型
feat 新功能 新增 (Added)
fix Bug 修复 修复 (Fixed)
perf 性能优化 变更 (Changed)
refactor 重构 不记入变更日志
docs 文档变更 不记入变更日志
chore 构建/工具变更 不记入变更日志

破坏性变更标记

feat(auth)!: 将认证模块迁移至 OAuth 2.0

BREAKING CHANGE: 旧的 API Key 认证方式已移除，
所有客户端需迁移至 OAuth 2.0 授权流程。

自动生成变更日志

常用工具

工具 语言/生态 功能
conventional-changelog Node.js 从约定式提交生成 CHANGELOG
standard-version Node.js 自动版本号 + 变更日志
changesets Node.js (Monorepo) 多包变更管理和变更日志
git-cliff Rust/通用 高度可配置的变更日志生成器
release-please GitHub Action Google 维护的自动发布工具

工具集成示例

{
  "scripts": {
    "changelog": "conventional-changelog -p angular -i CHANGELOG.md -s",
    "release": "standard-version",
    "release:major": "standard-version --release-as major",
    "release:minor": "standard-version --release-as minor"
  }
}

最佳实践

  • 每个版本发布前审核自动生成的内容，确保描述清晰
  • 将 [Unreleased] 部分作为开发过程中的变更缓冲区
  • 破坏性变更务必提供迁移指南或链接
  • 使用 CI 检查提交消息是否符合约定式提交规范
