Slack 礼仪

核心概念

Slack 已成为技术团队的主要即时通讯工具，但即时通讯不等于"随意沟通"。Slack 消息的写法直接影响团队的沟通效率和协作氛围。与邮件不同，Slack 消息更短、更频繁、更非正式，但同样需要遵循一定的规范和礼仪。

Slack 消息与邮件在沟通特征上有本质区别：

核心原则是 Respect others' attention — 每条 Slack 消息都在消耗他人的注意力，因此必须确保每条消息都有价值。


频道选择与消息分流
选择正确的频道发送消息是 Slack 礼仪的第一步。错误的频道选择要么让信息到达不了需要看到的人，要么打扰了不需要关注的人。


常见的频道类型和适用场景：

发消息前的心理 checklist：


    

  • 这条消息的受众是谁？选择最窄的频道
    • 

  • 这条消息需要即时响应吗？如果不需要，考虑邮件
    • 

  • 这条消息适合公开讨论吗？如果涉及敏感内容，使用 DM
    • 

  • 这条消息会打断别人的工作吗？如果是，考虑使用 scheduled send
    • 



在发送 @channel 或 @here 前三思：




@here — 通知频道中当前在线的成员（较温和） @channel — 通知频道中所有成员（包括离线的，侵入性强）




一般规则是：只在真正紧急（如生产事故）时使用 @channel；日常通知使用 @here 或不使用 @ 通知。


消息结构与 Thread 规范
Slack 消息虽短，但仍需要结构。最佳实践是在一条消息中包含完整信息，避免发送多条碎片化消息（每条消息都会触发一次通知）。


坏的消息习惯（连续多条）：




hey are you there? I have a question about the API the auth endpoint is returning 500




好的消息习惯（一条完整消息）：




Hey Sarah 👋 Quick question about the auth API — the POST /api/auth/token endpoint is returning 500 on staging. I've checked the logs and see a NullPointerException in TokenService.validate(). Have you seen this before? Here's the error trace: [link to log]




Thread 回复是 Slack 中最重要的功能之一。所有对初始消息的回复和讨论都应在 thread 中进行，而非在频道主时间线中。


Thread 的使用规则：


    

  • 对任何消息的回复一律使用 thread
    • 

  • 如果 thread 中产生了重要结论，使用 Also send to #channel 将结论发回频道
    • 

  • 避免在 thread 中讨论与原消息无关的话题
    • 

  • 长 thread（>20 条回复）通常意味着应该转为会议
    • 



在 thread 中标记结论：




✅ Decision: We'll go with Option A (blue-green deployment). David will start implementation tomorrow.




@-Mention 策略与通知管理
@-mention 是 Slack 中最直接的通知方式。合理使用 @ 可以确保信息到达正确的人，滥用则会导致通知疲劳。


@-mention 的使用原则：


    

  • 只在确实需要某人关注或行动时使用 @
    • 

  • 如果只是 FYI，不要 @，让对方自行浏览频道
    • 

  • 在请求帮助时，@ 一个最可能帮助你的人，而非 @ 整个团队
    • 

  • 使用 @usergroup（如 @backend-team）代替逐个 @ 多人
    • 



有效的 @-mention 示例：




@david Could you take a look at PR #1234 when you get a chance? No rush — just want to get it in before the end of sprint.






@backend-team Heads up: we're rolling out the new rate limiter to production at 3pm PST today. Please monitor your services for any unexpected 429 responses.




无效的 @-mention（通知轰炸）：




@david @sarah @tom @alice @bob @carol Does anyone know where the API keys are stored?




更好的做法：




Does anyone know where the API keys are stored? (cc @david who set them up originally)




关于 Do Not Disturb 和跨时区通知：


    

  • 尊重他人的 DND 设置，除非是真正的紧急情况
    • 

  • 如果你在对方的非工作时间发消息，使用 Slack 的 Schedule send 功能
    • 

  • 在跨时区消息中标注你的时区：Quick note (sending this from PST, no need to respond until your morning):
    • 



敏感话题与冲突处理
Slack 的公开性意味着所有频道消息都可能被更多人看到。处理敏感话题和冲突时需要特别谨慎。


不适合在 Slack 公开频道讨论的话题：


    

  • 绩效问题或人事变动
    • 

  • 薪酬或晋升相关
    • 

  • 对特定人的批评
    • 

  • 涉及客户机密的信息
    • 

  • 还未官方宣布的组织变动
    • 



当 Slack 讨论出现分歧时的处理策略：


如果你发现自己在 thread 中写了超过 3 条回复且讨论越来越激烈，立即转换沟通方式：




I think we have differing perspectives on this. Would it be helpful to jump on a quick call to hash it out? I'll set up a 15-min huddle.




在公开频道中表达不同意见时，聚焦于问题本身而非个人：




I see the tradeoff differently. The caching approach would add complexity that outweighs the performance gain in our use case. Here's my reasoning: [...]




而非：




That's not a good idea. You're not considering the complexity.




使用 emoji reaction 代替无信息量的回复。用 ✅ 表示"收到/完成"，用 👀 表示"看了/在处理"，用 👍 表示"同意"，避免频道中出现大量 ok、got it、thanks 的单词消息。

异步沟通最佳实践
远程和分布式团队中，Slack 的异步沟通能力尤为重要。异步沟通意味着不期望对方立即回复，但消息本身必须包含足够的上下文让对方在方便时独立处理。


异步消息的黄金法则是 front-load context——把所有必要信息放在第一条消息中：




Hey David, async question about the caching strategy:


Context: We're seeing cache hit rates drop to 60% during peak hours (target is 85%). What I've investigated: Checked eviction policies, verified TTL settings, reviewed recent traffic patterns. My hypothesis: The issue is key cardinality explosion from the new personalization feature. What I need: Your thoughts on whether we should (a) increase cache size, (b) adjust the key strategy, or (c) something else. Timeline: Not urgent — would appreciate your input by Thursday.




这种格式让 David 在任何时区、任何时间看到消息都能直接回复，而无需来回追问背景信息。


另一个重要实践是在消息中注明期望的响应时间：


    

  • No rush — whenever you get a chance this week.
    • 

  • Would appreciate a response by end of day tomorrow.
    • 

  • Time-sensitive — need input before our 3pm meeting today.
    • 



小结
    

  • 选择最窄的频道发送消息，只在紧急情况使用 @channel
    • 

  • 一条消息包含完整信息：称呼 + 问题 + 已做调查 + 需要的帮助
    • 

  • 所有回复使用 Thread，重要结论发回频道主时间线
    • 

  • @-mention 精准定向，避免 @ 整个团队
    • 

  • 尊重他人的 DND 设置，跨时区消息使用 Schedule send
    • 

  • 敏感话题和人事问题不在公开频道讨论
    • 

  • 超过 3 条回复的分歧立即转为 huddle 或会议
    • 

  • 善用 emoji reaction（✅ 👀 👍）减少无信息量的文字回复
    •
