PR 与 Code Review 英语

PR Description 写作框架

Pull Request（PR）描述是开发者技术写作中最高频的场景。一个好的 PR Description 能让 Reviewer 在查看代码之前就理解改动的目的、范围和影响，大幅提升审查效率。

PR Title 的写作公式

PR Title 应当是一个简洁的句子，遵循以下格式：

<type>(<scope>): <concise description of what this PR does>

高频 type 前缀及其含义：

前缀 含义 示例
feat 新功能 feat(auth): add OAuth2 login with Google
fix 修复 Bug fix(cart): resolve race condition in quantity update
refactor 重构 refactor(api): extract validation logic into middleware
perf 性能优化 perf(query): add index for user lookup by email
docs 文档 docs(api): update authentication examples
test 测试 test(payment): add integration tests for Stripe webhook
chore 杂项 chore(deps): upgrade React to v19

Title 写作要点：

  • 保持在 72 个字符以内
  • 使用祈使句（imperative mood）："Add feature" 而非 "Added feature"
  • 说明"做了什么"而非"在做什么"

PR Body 模板

## What

Brief description of what this PR does (1-3 sentences).

## Why

The motivation behind these changes. Link to issue if applicable. Fixes #123

## How

Describe the approach taken and any important design decisions.

## Testing

- [ ] Unit tests added/updated
- [ ] Integration tests pass
- [ ] Manual testing done (describe what was tested)

## Screenshots (if applicable)

Before / After screenshots for UI changes.

## Notes for Reviewers

Any specific areas where you'd like focused feedback.

实际 PR Description 示例

## What

Add rate limiting to the public API endpoints using a sliding window algorithm with Redis as the backing store.

## Why

Our API has been experiencing abuse from automated scrapers, causing degraded performance for legitimate users. This implements the rate limiting strategy agreed upon in ADR-047.

## How

- Implemented sliding window counter using Redis MULTI/EXEC
- Added `RateLimitMiddleware` that checks limits before routing
- Default limit: 100 requests per minute per API key
- Returns 429 with `Retry-After` header when limit exceeded

## Testing

- Unit tests for the sliding window algorithm
- Integration tests with Redis test container
- Load tested with k6: confirmed correct behavior at 200 rps

## Notes for Reviewers

The Redis key expiration strategy in `rate-limiter.ts:45-60` could use a second look. I'm not 100% sure the TTL handling is correct for edge cases near the window boundary.

Code Review 评论表达

Code Review 评论需要在"清晰传达技术观点"和"维护团队关系"之间取得平衡。英语中有一套成熟的表达梯度系统来实现这一点。

评论严重性前缀

在评论开头使用标准前缀来表示严重程度：

前缀 含义 必须修改
blocker: 阻塞问题，不修不能合 是
issue: 需要修改的问题 是
nit: 小瑕疵，改不改都行 否
suggestion: 建议，可以讨论 否
question: 需要作者解释 —
praise: 写得好的地方 —
thought: 发散想法，不针对本次 PR —

请求修改的表达梯度

直接请求（适合明确的问题）：

"This should be extracted into a separate function."
"Please rename this variable to something more descriptive."
"We need to add error handling here."
"This constant should be defined at the module level."

委婉建议（团队中更受欢迎的风格）：

"What do you think about extracting this into a helper?"
"Could we consider using a more descriptive name here?"
"Would it make sense to add a try-catch block around this?"
"I wonder if we could simplify this with a reduce()."
"Have you considered using a Map instead of an object here?"

提供替代方案：

"One alternative approach could be..."
"Another option would be to..."
"We could potentially simplify this by..."
"A pattern I've seen work well for this is..."

提问的表达方式

询问意图/原因：

"What's the reasoning behind this approach?"
"Could you help me understand why we're doing it this way?"
"Is there a specific reason for choosing X over Y?"
"I'm curious about the motivation for this change."
"What led to this design decision?"

确认行为：

"Just to confirm — this will also handle the case when X is null?"
"Does this work correctly when the list is empty?"
"Have we considered what happens if the API returns a 5xx?"
"Will this be backwards-compatible with the existing clients?"

询问边界情况：

"What happens if the user submits the form twice rapidly?"
"How does this behave under high concurrency?"
"Have we accounted for the timezone differences here?"
"Is there a maximum size limit we should validate against?"

给予肯定

好的 Code Review 不只是挑问题，还要肯定优秀的代码：

"Nice refactoring! This is much cleaner."
"Great catch on the edge case handling."
"I like this approach — it's both simple and extensible."
"TIL! I didn't know about this API. Thanks for introducing it."
"Clever use of generics here. Very elegant solution."
"This test is really thorough. Good coverage of edge cases."

处理分歧

当你和 PR 作者意见不同时：

"I see your point, but I'm slightly concerned about..."
"I understand the trade-off you're making here. My concern is..."
"I think we might want to discuss this further before merging."
"Let's sync on this offline — I think there might be a misunderstanding."
"I could be wrong here, but my understanding is that..."
"Fair point — I'll defer to your judgment on this one."

Code Review 常用缩略语

技术团队中使用一套简洁的缩略语来提高沟通效率：

缩写 全称 含义
LGTM Looks Good To Me 审阅通过
SGTM Sounds Good To Me 同意你的方案
PTAL Please Take A Look 请审阅
WIP Work In Progress 还没做完
RFC Request For Comments 征求意见
TL;DR Too Long; Didn't Read 摘要（用于长文前）
AFAIK As Far As I Know 据我所知
IIRC If I Recall Correctly 如果我没记错
IMO / IMHO In My (Humble) Opinion 个人看法
FYI For Your Information 供参考
NB Nota Bene 注意
WDYT What Do You Think? 你觉得怎样？
TBD To Be Decided/Determined 待定
N/A Not Applicable 不适用

Commit Message 英语

Conventional Commits 规范

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]

常用 description 动词（祈使句）：

add       — 添加新功能/文件
remove    — 移除功能/文件
update    — 更新已有功能
fix       — 修复问题
refactor  — 重构（不改变行为）
improve   — 改善性能/可读性
implement — 实现（新功能）
replace   — 替换实现
simplify  — 简化逻辑
extract   — 提取为独立模块
migrate   — 迁移到新方案
deprecate — 标记为弃用

实际 Commit Message 示例

feat(auth): implement JWT refresh token rotation

Add automatic token refresh when access token expires within 5 minutes
of the request. Uses rotating refresh tokens to improve security.

Breaking change: refresh_token response field is now single-use.
Clients must store the new refresh token from each response.

Refs: AUTH-234
fix(search): prevent XSS in search query highlighting

Sanitize HTML entities in the search term before injecting into
the highlighted result markup. Previously, user input was rendered
as raw HTML which allowed script injection.

Fixes #891

Code Review 英语的核心不在于语法的完美，而在于清晰、具体、尊重。直接指出问题所在、给出具体建议或替代方案、尊重对方的工作付出——这三点做到了，你的 Review 就是专业的。

用 AI 起草 PR 描述与 Review 回复

AI 工具（Claude / GPT / Cursor / Copilot Chat）在 PR 写作链路上有两个高 ROI 入口：起草 PR description 与 整理 review 回复。但 AI 初稿有典型的"AI 味"，需要人调。

起草 PR description 的 prompt 模式

You are drafting a PR description. Given the diff below, produce a
PR description following this template:

**What**: 1-2 sentences on what changed.
**Why**: the business or technical reason, with linked issue if any.
**How**: 3-5 bullets on the implementation approach.
**Testing**: what was tested manually + what's covered by automated tests.
**Notes**: optional caveats, follow-ups, or out-of-scope items.

Constraints:
- Use imperative mood in section bodies ("Add", "Remove", "Refactor").
- Cite specific files/functions affected.
- Do not invent test cases — list only what's actually present.
- Keep under 200 words.

Diff:
[paste diff or refer to the staged changes]

要点：

  • 明确不要让 AI 编造测试——这是 LLM 最容易"幻觉"的地方
  • 指定 imperative mood——LLM 默认偏向 "This PR adds..."，需要明确切到 "Add..."
  • 字数上限——LLM 默认啰嗦；设上限能逼出重点

起草 review reply 的 prompt 模式

You're writing a polite review reply. The reviewer asked: "[paste comment]"
My intended response is: "[short Chinese or rough English version]"

Rewrite this as a concise, professional review reply that:
- Acknowledges the reviewer's point first
- States my position with a clear reason
- Ends with an open invitation if there's disagreement

Avoid "I think" hedging more than once. Avoid "Let me know your thoughts"
if I've already given a clear answer.

这一个 prompt 设计有意降低了"礼貌冗余"——母语者的 review reply 通常比中文母语者起草的更直接。

AI 起草的 PR / Review 的 3 类"AI 味"信号

人调阶段重点检查：

AI 味信号 例子 怎么改
过度礼貌 "Thank you so much for your kind feedback! I really appreciate..." 删到 "Thanks for the review."
模糊修饰 "This significantly improves..." / "vastly better" 改成具体数字 "Reduces p99 from 800ms to 120ms"
重复声明 前文说了 "added tests"，结尾又说 "I've also added tests to ensure quality" 删后者

用 AI 做 review 检查清单

AI 不仅能起草，也能反向 review 你自己的 PR description / commit message：

Review my PR description below. Flag:
- Missing context (would a reviewer with no background understand why?)
- Vague statements that should cite specific files/tests/metrics
- Imperative-mood violations (e.g., "This adds X" → "Add X")
- Length issues (is it under 200 words?)

[paste your draft]

把 AI 当成第二双眼睛——但第一双眼睛仍是你自己。AI 不知道 codebase 的隐式约定（团队偏好的 PR 长度、不写 "Notes" 节的惯例等），人审不可替代。

Review 阶段的 AI 风险

  • 不要让 AI 直接 review 别人 PR 的 diff 并发表评论——这相当于把 AI 的判断当成你的判断，对作者不公平
  • 可以让 AI 帮你理解别人 PR 的改动（"explain this diff in 5 bullets"），但 review 评论必须是你自己看完后写的
  • 如果团队接受 AI 辅助 review，显式标注："I used AI to summarize the changes; the comments below are my own."
