开源协作英语

参与开源是程序员练英语 + 建立国际声誉的高 ROI 路径——同一份贡献既改进了项目，也留下可追溯的英文表达记录。本文档聚焦"对外参与"场景下的英语：第一次提 issue / drive-by PR / RFC 讨论 / 维护者回应。与 02_pr-code-review-english.md（聚焦"我提 PR、别人 review 我的代码"）形成对照。

开源沟通的三重特征

参与开源前要先理解它的沟通语境，与公司内沟通有显著差异：

维度 公司内沟通 开源社区沟通
异步性 半同步（Slack / 电话） 完全异步（issue / PR 评论）
公开度 内部可见 公开可索引、长期留存
关系预设 已有同事关系 陌生人之间
文化背景 多数同质 极度多元（母语 ≠ 英语者占多数）
时间响应预期 当天 几天到几周

对英语的影响：句子要更慢、更明确、更克制；不能依赖语调、表情、即时澄清，所以写出来一遍读懂比"差不多说清"更重要。

第一次贡献的英语模板

自我介绍 / 表达兴趣

Hi! I'm a Go developer working on internal tooling at my company.
I've been using {project} for the past 6 months and would love to
contribute back. I noticed {issue #N} is marked as `good first issue`
— would it be OK if I take a stab at it?

要点：

  • 一句话身份（避免详细简历）
  • 表明已是用户（不是"路过看见"）
  • 引用具体 issue 号 + good first issue 标签
  • "take a stab at it" 是地道、低承诺的表达

提问的英语姿态

新贡献者最容易踩的坑是问问题时给得太少 / 索取太多：

# Bad — 索取式
Hi, can someone explain how this project works?

# Bad — 缺少功课展示
How do I run the tests?

# Good — 展示努力 + 明确卡点
I'm trying to run the integration tests locally per CONTRIBUTING.md
section 3, but `make integration-test` fails with the error below.
I've installed Docker and confirmed it's running. Has anyone run
into this on macOS arm64?

[error log]

公式：「我尝试了 X」+「期望 Y」+「得到 Z」+「环境信息」——和 bug report 同构。

报 Bug 的标题与正文

标题写法决定维护者是否点开。差对照：

# Bad
"Help!" / "Bug" / "Not working"

# Good — 现象 + 触发条件 + 上下文
"TypeError when passing null to parseConfig() on v2.3.1"
"Memory leak in connection pool when MAX_CONNECTIONS > 100"
"Build fails on Node 22 due to crypto API deprecation"

正文模板（5 段，缺一不可）：

**What happened**
The `parseConfig()` function throws TypeError instead of returning
defaults when given null.

**What I expected**
Per the README example, null input should produce {timeout: 30, retries: 3}.

**Steps to reproduce**
1. Install v2.3.1: `npm install pkg@2.3.1`
2. Run: `node -e "console.log(require('pkg').parseConfig(null))"`

**Environment**
- pkg: 2.3.1
- node: 20.11.0
- OS: macOS 14.3 arm64

**Possible cause** (optional)
Looks like the null-check at line 47 was removed in #189.

最后一段 "Possible cause" 是高级用法——把对 codebase 的初步阅读结果摆出来，立刻把贡献者标记为"认真的"。

Drive-by PR 的英语

Drive-by = 偶遇问题顺手修，不打算长期参与。这类 PR 90% 的失败在于不告诉维护者"为什么这一改"：

# PR Title
fix(parser): handle null input in parseConfig

# PR Description
Closes #234.

**Problem**
When `parseConfig(null)` is called, the function throws TypeError at
line 47 because `opts.timeout` is accessed before the null check.

**Fix**
Move the null check before option access. Returns the documented
default config object when input is null.

**Testing**
- Added test case `parseConfig.test.ts:42` covering null input
- All existing tests pass
- Verified locally on Node 20 and 22

**Notes**
- This is my first contribution to {project}; happy to adjust to match
  your conventions if anything is off.
- I did not change the related `parseAdvancedConfig` function — it has
  the same pattern but is out of scope for this PR.

关键英语点：

  • Closes #234 是 GitHub 关键字，合并时自动关闭 issue（其他动词：fixes / resolves）
  • "out of scope for this PR" 主动声明边界，避免被要求扩大改动
  • "happy to adjust" 表示愿意配合而不卑微

回应 Review 评论

社区维护者的 review 评论有 4 种典型形态，每种有对应的英语回应模式：

1. 同意 + 已修

Reviewer: "This could be simplified using array.flatMap()."

You: "Good catch — pushed the change in 3a7f2c1."

短促、积极。如果改动比较大，可以多一句："Also simplified the related loop in formatInput() using the same pattern."

2. 同意但延后处理

Reviewer: "We should also update the docs."

You: "Agreed. I'll keep this PR focused on the fix and follow up with
a docs PR after merge. Created #245 to track."

要点：承诺 + 立刻创建跟踪 issue。"follow up with X after merge" 是社区常见的范围控制句式。

3. 不同意但保留尊重

Reviewer: "Why didn't you use the existing helper in utils/parse.ts?"

You: "I considered that, but the existing helper validates the schema
which we don't need here — and the validation adds about 20ms in the
hot path we're benchmarking. Open to using it if perf isn't a concern,
let me know."

公式：「我看过 X」+「我的判断 Y」+「但听你的」。"Open to ... let me know" 把球还给维护者，避免对抗。

4. 不理解 / 需要澄清

Reviewer: "This should be `Optional<T>` not `T?`."

You: "Could you point me to where the codebase preferred convention is
documented? I followed the pattern in `Config.ts` but if there's a
different convention in this module I'm happy to update."

要点：不要假装懂；直接问；同时展示你有依据地做了原来的选择。

RFC / 重大提案的英语

参与 RFC 是更高阶的开源贡献。RFC 的写作语气比 PR 更克制——你是在邀请讨论而不是宣布结论：

语气 弱（避免） 强（推荐）
论断 "This is the right approach." "I believe this approach has the best fit for X because..."
否定既有方案 "The current design is broken." "The current design works but has limitations when..."
时间承诺 "I will implement this." "I'd be willing to drive the implementation, depending on the timeline the team is comfortable with."
决策权 "We should adopt this." "I'd love to hear what the maintainers think about this direction."

RFC 文档自身的结构遵循社区惯例（Summary / Motivation / Detailed Design / Drawbacks / Alternatives），具体见 12_specialized-english（已归档但保留）或 Rust / TC39 / Python PEP 等公开 RFC 仓库。

维护者视角：评审他人 PR 的英语

终有一天你会从贡献者升级到 reviewer。给陌生人 review 的英语 比给同事更需要克制：

给同事 给开源贡献者
"fix this" "Could you address this?"
"use X instead" "Consider using X for {reason}."
"tests?" "Could you add a test covering the {edge case}? This will help us prevent regressions."
"nope" "Thanks for the contribution! We're not planning to add this feature because... but I appreciate the effort."

拒绝是 maintainer 最难写的英语。模板：

Hi @{user}, thanks for taking the time to put this together.

After discussion with other maintainers, we've decided not to merge
this PR because:

1. The feature adds complexity to the core path that affects all users,
   while solving a problem that only a small subset encounters.
2. There's an existing workaround (see {docs link}) that doesn't
   require library changes.

We do appreciate the contribution and the careful implementation. If
you have time, we'd welcome PRs on {good-first-issue-link} where there's
clear demand.

Closing this for now, but please don't hesitate to open a new PR or
issue in the future!

要点：先感谢 → 给具体理由（编号）→ 提替代路径 → 指引未来贡献 → 不带火气地关闭。

AI 时代的开源贡献

LLM 改变了 drive-by 贡献的门槛与节奏：

旧路径 AI 时代
读完整 CONTRIBUTING.md 才动手 用 AI 总结 contributing 文档关键点
翻 codebase 找类似 PR 模仿 用 AI 在仓内 grep + 总结模式
手写 commit message AI 起草，人修语气
翻译母语 issue 描述到英语 AI 翻译 + 人调地道度

风险与"对策"：

  • 风险：AI 翻译过的 issue 听起来"AI 味太重"——过度礼貌、模糊修饰词、缺少具体细节。维护者一眼能看出。
  • 对策：用 AI 做初稿，人主动加 3 类信息：版本号、复现命令、自己已经试过的 workaround。这三类信息 LLM 无法编造，是"真人参与"的强信号。
# AI 翻译初稿 — 太"AI 味"
Hi! I have encountered an issue with this wonderful library. When I
try to use the function, it seems to not work as expected. Could you
please kindly help me understand what might be the problem?

# 人调整后 — 加入具体证据
Hi, hitting an issue on v2.3.1: `parseConfig(null)` throws TypeError
instead of returning defaults. Repro: `node -e "require('pkg').parseConfig(null)"`.
I tried catching the error and falling back to `{}` but that breaks
downstream validation. macOS arm64 / Node 20.11. Happy to send a PR
if a maintainer can confirm the desired behavior.

小结

  • 开源沟通是完全异步、公开、跨文化的——一遍读懂比"差不多说清"更重要
  • 报 bug 用 5 段模板：What happened / What I expected / Steps to reproduce / Environment / Possible cause
  • Drive-by PR 必须告诉维护者"为什么这一改"+"为什么不扩大范围"
  • 回应 review 有 4 种典型场景（同意已修 / 同意延后 / 不同意 / 不理解），各有对应英语模板
  • RFC 与提案的语气比 PR 更克制——你是在邀请讨论，不是宣布结论
  • 维护者 review 给陌生人比给同事更需克制；拒绝 PR 有固定礼貌模板
  • AI 工具降低了贡献门槛，但 AI 初稿要由人加入"版本号 / 复现命令 / 已试方案"才有可信度
  • 持续贡献开源是程序员英语 + 国际声誉双增长的最高 ROI 路径之一
