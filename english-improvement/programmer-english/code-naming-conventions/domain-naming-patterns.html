领域术语与命名模式

设计模式命名惯例

设计模式是软件工程中最成熟的命名体系之一。每个模式都有约定俗成的类名后缀，开发者看到这些后缀就能立即理解类的角色和行为。掌握这套命名语言，等同于掌握了一种跨项目、跨团队的通用沟通协议。

创建型模式命名

模式 命名后缀 典型类名 职责说明
Factory Method Factory ConnectionFactory 创建对象，隐藏实例化逻辑
Abstract Factory AbstractFactory / Factory UIComponentFactory 创建一族相关对象
Builder Builder QueryBuilder, ConfigBuilder 分步构建复杂对象
Singleton 无特殊后缀 AppConfig, Logger 全局唯一实例
Prototype Prototype ShapePrototype 通过克隆创建对象 
// Factory 模式命名示例
class NotificationFactory {
  create(type: 'email' | 'sms' | 'push'): Notification {
    switch (type) {
      case 'email':
        return new EmailNotification();
      case 'sms':
        return new SmsNotification();
      case 'push':
        return new PushNotification();
    }
  }
}

// Builder 模式命名示例
class HttpRequestBuilder {
  private request: Partial<HttpRequest> = {};

  setMethod(method: string): this {
    /* ... */ return this;
  }
  setUrl(url: string): this {
    /* ... */ return this;
  }
  addHeader(key: string, value: string): this {
    /* ... */ return this;
  }
  setBody(body: unknown): this {
    /* ... */ return this;
  }
  build(): HttpRequest {
    /* ... */
  }
}

结构型模式命名

模式 命名后缀 典型类名 职责说明
Adapter Adapter LegacyApiAdapter 转换接口兼容性
Decorator Decorator LoggingDecorator 动态添加功能
Facade Facade PaymentFacade 简化复杂子系统接口
Proxy Proxy CachingProxy 控制访问/延迟加载
Bridge Bridge / Impl RenderingBridge 分离抽象与实现
Composite Composite / Group MenuComposite 树形结构统一处理 
// Adapter 模式 — 注意类名如何传达转换意图
class StripePaymentAdapter implements PaymentGateway {
  private stripeClient: Stripe;

  async charge(amount: number, currency: string): Promise<PaymentResult> {
    // 将统一接口转换为 Stripe 专有 API 调用
    const intent = await this.stripeClient.paymentIntents.create({
      amount: amount * 100, // Stripe 使用分
      currency,
    });
    return this.mapToPaymentResult(intent);
  }
}

// Decorator 模式
class RetryDecorator implements HttpClient {
  constructor(
    private client: HttpClient,
    private maxRetries: number,
  ) {}

  async request(config: RequestConfig): Promise<Response> {
    // 在原有功能上增加重试逻辑
  }
}

模式 命名后缀 典型类名 职责说明

领域驱动设计命名

领域驱动设计（DDD）引入了一套精确的术语体系来描述业务领域中的概念。这套命名语言强调使用通用语言（Ubiquitous Language），即开发团队和业务团队共享的词汇。

DDD 核心概念命名

概念 英文术语 命名方式 示例
实体 Entity 业务名词 Order, Customer, Product
值对象 Value Object 描述性名词 Money, Address, DateRange
聚合根 Aggregate Root 业务名词 Order（包含 OrderLine）
领域事件 Domain Event 过去时态动词短语 OrderPlaced, PaymentReceived
领域服务 Domain Service 名词 + Service PricingService, ShippingService
仓储 Repository 实体名 + Repository OrderRepository, CustomerRepository
应用服务 Application Service 用例名 + Service PlaceOrderService

领域事件的命名艺术

领域事件使用过去分词形式，因为事件表示"已经发生的事实"：

// Good — 过去时态，表示已发生
class OrderPlaced {
  constructor(
    public readonly orderId: string,
    public readonly customerId: string,
    public readonly totalAmount: Money,
    public readonly occurredAt: Date,
  ) {}
}

class PaymentProcessed {
  /* ... */
}
class ItemShipped {
  /* ... */
}
class UserRegistered {
  /* ... */
}
class InventoryDepleted {
  /* ... */
}

// Bad — 现在时态或命令式
class PlaceOrder {} // 这是命令，不是事件
class ProcessPayment {} // 这是动作，不是事实

命令与查询的命名

CQRS（Command Query Responsibility Segregation）模式中，命令和查询有清晰的命名规范：

// 命令：祈使句式 — 动词 + 名词
class PlaceOrder {
  constructor(
    public readonly customerId: string,
    public readonly items: OrderItem[],
  ) {}
}

class CancelSubscription {
  /* ... */
}
class UpdateShippingAddress {
  /* ... */
}
class ApproveRefund {
  /* ... */
}

// 查询：名词短语（描述期望的结果）
class OrdersByCustomer {
  constructor(public readonly customerId: string) {}
}

class ActiveSubscriptions {
  /* ... */
}
class MonthlyRevenueReport {
  /* ... */
}

限界上下文命名

Bounded Context 的命名反映业务子域：

事件驱动架构命名

在现代微服务架构中，事件和消息的命名是跨服务沟通的关键。

API 端点命名（RESTful）

REST API 的 URL 命名遵循资源导向原则：

# 资源用复数名词
GET    /api/v2/users          # 获取用户列表
POST   /api/v2/users          # 创建用户
GET    /api/v2/users/:id      # 获取单个用户
PUT    /api/v2/users/:id      # 更新用户
DELETE /api/v2/users/:id      # 删除用户

# 嵌套资源
GET    /api/v2/users/:id/orders        # 用户的订单
GET    /api/v2/orders/:id/items        # 订单的商品项

# 动作类端点（非 CRUD 时使用动词）
POST   /api/v2/orders/:id/cancel       # 取消订单
POST   /api/v2/users/:id/verify-email  # 验证邮箱

测试命名的英语模式

测试函数的命名是一种特殊的技术写作，它需要清晰传达被测试的行为和期望的结果。

常见命名格式

should + 行为描述——最流行的 JavaScript/TypeScript 测试命名：

describe('UserService', () => {
  it('should return user when valid id is provided', () => {});
  it('should throw NotFoundError when user does not exist', () => {});
  it('should hash password before saving', () => {});
  it('should send welcome email after registration', () => {});
});

given-when-then 格式——BDD 风格：

describe('OrderService', () => {
  describe('given a cart with items', () => {
    describe('when user places order', () => {
      it('then creates order with correct total', () => {});
      it('then reduces inventory stock', () => {});
      it('then sends confirmation email', () => {});
    });
  });
});

方法名场景期望结果——Java/C# 传统：

@Test
void calculateTotal_withDiscountCode_appliesDiscount() {}

@Test
void findById_withNonExistentId_throwsNotFoundException() {}

@Test
void register_withDuplicateEmail_returnsConflictError() {}

配置与环境变量命名

# 环境变量：SCREAMING_SNAKE_CASE，按层级用下划线分隔
DATABASE_HOST=localhost
DATABASE_PORT=5432
DATABASE_NAME=myapp
REDIS_CACHE_TTL=3600
AWS_S3_BUCKET_NAME=uploads
JWT_ACCESS_TOKEN_EXPIRY=900
SMTP_SENDER_EMAIL=noreply@example.com

# 前缀规范
APP_*          # 应用级配置
DB_* / DATABASE_*  # 数据库相关
REDIS_*        # Redis 相关
AWS_*          # AWS 服务相关

设计模式和领域术语构成了程序员英语的高阶词汇。当你在代码中看到 OrderFactory、PaymentAdapter、UserRegistered，即使不看实现代码也能推断出类的职责和系统的架构风格——这就是规范命名的力量。

AI 时代的领域命名

设计模式名称是 LLM 训练语料里密度最高的术语之一——这是双刃剑：

好处：在 prompt 中说 "Use the Strategy pattern" / "Implement as a Saga" 比解释 8 行架构更高效。LLM 几乎一定能跟上经典模式名。

陷阱：LLM 会过度套用模式——把不需要 Factory 的地方包成 Factory、给只用一次的逻辑套 Strategy。Review 时常见错位：

AI 易过度套用 何时其实不需要
Factory 只有一个具体实现时（直接 new 即可）
Strategy 策略只有 2 种且不会增加时（用 if/switch 更清晰）
Observer 同步流程在一个文件内（直接函数调用）
Repository 直接 SQL 一两行就能搞定的查询

Prompt 反模式：避免说 "Use design patterns where appropriate" 这类含糊指令——LLM 会默认套用。改成 "Implement with the simplest control flow that handles the listed requirements; do not introduce factories or strategies unless multiple variants exist."

Event Sourcing / DDD 类术语的英语稳定性

UserRegistered / OrderShipped 这类过去时分词事件命名在 DDD 与 Event Sourcing 项目中是社区惯例。始终用过去时（UserRegistered），不要混用现在时（RegisterUser 那是 command 不是 event）。这条对 LLM 同样重要——LLM 会按训练语料惯例区分二者，混用会让 AI 生成的事件 handler 在 type 层就出错。
