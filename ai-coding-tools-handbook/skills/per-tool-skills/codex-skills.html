Codex Skills 实现与安全模型

OpenAI Codex 在 2026 年的 Skills 实现遵循 agentskills.io base spec，但把"OpenAI 私有元数据"放到了同目录 openai.yaml 文件而不是 frontmatter——这是 vendor extension 的另一种实现形态：spec 字段静默兼容、vendor 字段独立文件。Codex 的 untrusted-projects 安全模型决定了 .codex/ 默认不读、scripts 执行需要 explicit approval。本文讲发现路径、openai.yaml 元数据、与 AGENTS.md 的协作、安全模型与跨工具互通。

核心概念

Codex 把 skill 视为"知识 + 可执行片段"，与 AGENTS.md 项目协议互补——skill 是过程性知识（"如何做某事"），AGENTS 是项目级声明（"这个项目的命令、约束、目录意义"）。两者通过 prompt 拼接共同进入 turn context。

两类发现路径
Codex 的发现路径只有两档：


    

  • .codex/skills/<name>/SKILL.md——项目本地，commit 进 git 与团队共享。
    • 

  • ~/.codex/skills/<name>/SKILL.md——用户全局，跨项目共享。
    • 



没有 plugin-bundled 层（Codex 当前不发布 plugin marketplace）。同名时 project 优先于 user——project 通常代表团队约定，应当压过个人偏好。


注意 Codex 的 untrusted-projects 默认策略：第一次进入新仓库时，Codex 提示"是否信任此项目"，未确认前 .codex/ 整个目录都不读、skill 不加载、scripts/ 不执行。这与 Claude Code 默认信任项目目录的策略不同，是 OpenAI 内部安全审查的硬要求——团队在引入 Codex 时必须把"trust 当前项目"作为 onboarding 一步。


openai.yaml 元数据 vendor extension
openai.yaml 与 SKILL.md 放在同一目录里，由 Codex 私有解析：


# .codex/skills/db-migration/openai.yaml
model_pin: gpt-5-codex
approval_policy: explicit # auto | explicit | never
sandbox_mode: read-write-restricted
tools_allowlist:
  - shell
  - apply_patch
字段语义（基于 2026-05 公开文档与 changelog）：

openai.yaml 是 spec 的标准 vendor extension 形态——Claude Code 与 OpenCode 不读该文件、字段也不在 frontmatter，对它们而言这个 skill 看上去就是个普通 base SKILL.md。这是跨工具兼容的优雅设计。


与 AGENTS.md 的协作
Codex 把 AGENTS.md（项目根目录的 agent 协议文件）与 Skills 视为两个互补层：


    

  • AGENTS.md：项目级约束。声明命令前缀（pnpm test、make lint）、目录意义（src/ 是源码、fixtures/ 不可改）、禁止行为（不删数据、不 force push）。session start 时整文件直接注入 system prompt。
    • 

  • Skills：过程性知识。"如何运行 DB migration"、"如何 review PR"、"如何写 release note"。session start 仅 name+desc 进 inventory、触发后 body 注入。
    • 



两者在 prompt 中的拼接顺序是 AGENTS.md 先（确立项目宪法）、skill body 后（具体步骤）。前置 hub ../../1_prompt-engineering/ 已展开 AGENTS.md 角色，这里只强调"过程性 vs 协议性"的职责分工——一份 skill 涉及项目级强约束时应当外迁到 AGENTS.md，否则 inventory 膨胀且重复。


untrusted-projects 安全模型
Codex 的安全模型核心是"默认不信任、信任由 user explicit 表达"：


    

  1. 首次进入 repo → Codex 提示 trust prompt → 用户选 yes 才读 .codex/。
    2. 

  2. skill 体内的 scripts/foo.sh 默认 approval_policy: explicit——agent 调用前必须 user 确认。
    3. 

  3. sandbox_mode 决定脚本能 touch 哪些文件、能不能上网（read-write-restricted 是最常用安全档）。
    4. 



这与 Claude Code 的"配置 allowed-tools + sandbox 由 user OS 提供"不同——Codex 把更多安全逻辑内置到 harness。团队跨工具复用 skill 时要意识到：同一份 skill 在 Codex 下默认有 approval 拦截、在 Claude Code 下取决于会话 sandbox 配置；安全边界由 harness 不由 skill 自身保证。


跨工具互通性
base SKILL.md 是跨工具互通的最大公约数：


    

  • name / description / argument-hint / $ARGUMENTS：Codex 全识别。
    • 

  • disable-model-invocation / user-invocable / mode / model / effort / context / agent：Codex 静默忽略。
    • 

  • allowed-tools：Codex 部分识别（对常见 tool 名如 shell 生效，对 Claude 私有 tool 名如 Edit 当 noop）。
    • 

  • !command 预加载语法：Codex 不实现，行首 ! 视作普通文本注入 body。
    • 



最佳实践是为 Codex 设计的 skill 用 base 字段 + openai.yaml，不依赖任何 Claude 私有 frontmatter。这样 skill 在 Claude / OpenCode 下也能加载，只是少了 OpenAI 特有的安全/模型钉策略。


陷阱与常见问题
    

  • 未 trust project 时 skill 无声失效：第一次切到新 repo，agent 找不到本应存在的 skill；用 /skills 列表确认；解决：trust 项目。
    • 

  • openai.yaml 写在 .claude/skills/ 路径：Claude Code 不读该文件——把 vendor 元数据放错位置等于没写。
    • 

  • approval_policy: auto 配合危险脚本：误设 auto 让破坏性 skill 静默执行；建议默认 explicit、需要时再放宽。
    • 

  • AGENTS.md 与 skill body 内容重复：项目级强约束应只在 AGENTS.md，skill body 重复一遍只会膨胀 inventory。
    • 

  • 依赖 Claude 私有字段做 Codex skill 设计：写了 context: fork 以为 Codex 隔离了——实则在主会话跑，长输出污染主 context。
    • 



小结
    

  • 路径两档 .codex/skills/ + ~/.codex/skills/，无 plugin 层
    • 

  • 元数据 vendor extension 走 sibling openai.yaml 文件，不污染 frontmatter
    • 

  • AGENTS.md = 项目协议、Skills = 过程性知识，两者 prompt 拼接互补
    • 

  • untrusted-projects 默认不读 .codex/，scripts 执行需 explicit approval
    • 

  • 与 Claude/OpenCode 互通靠 base SKILL.md；openai.yaml 各家自管不冲突
    • 

  • 设计跨工具 skill 时优先 base 字段，把 OpenAI 私有放 openai.yaml
    •
