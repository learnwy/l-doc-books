跨工具路径互通与发现顺序

Skills 的核心商业价值是"一次写好、所有兼容工具直读"，但 spec 没规定路径在哪儿。每个工具默认扫自己的 .<tool>/skills/，于是 mono-repo 里同时用 Claude / Codex / OpenCode 的团队就会面临"同一份 skill 要不要 copy 三遍"的实际问题。2026 起 agentskills.io 推荐的中性路径 .agents/skills/ 已成事实标准——本文讲中性路径配置、plugin/user/built-in 优先级、团队 commit 策略、IDE 与 CLI 协同。

核心概念

跨工具互通的关键是"把 skill 放在所有工具都能扫到的位置"。OpenCode 原生扫 .agents/skills/；Claude / Codex 通过 symlink 或工具配置 alias 把 .claude/skills/ 与 .codex/skills/ 指向 .agents/skills/。

.agents/skills/ 中性路径
agentskills.io 在 2026 Q1 推荐 .agents/skills/ 作为团队共享 skill 的中性路径——名字不带任何工具品牌（.agents 取 "AI agents 通用"）、路径下放 base SKILL.md（不放 Claude 私有字段或 openai.yaml），所有 spec-compliant 工具都能读。


落地方式：


    

  • OpenCode：原生支持，扫描 .agents/skills/ 与 .opencode/skills/ 同时进入合并 inventory。
    • 

  • Claude Code：默认不读 .agents/skills/。两种 workaround：(1) 创建 symlink .claude/skills -> .agents/skills；(2) Claude Code 配置文件 ~/.claude/settings.json 里加 skillsPaths: [".agents/skills/", ".claude/skills/"]（2026 Q1 引入）。symlink 方式简单但 commit 要带；配置方式需要每个团队成员本地设置一次。
    • 

  • Codex：默认不读 .agents/skills/。同样靠 symlink 或 Codex 配置 ~/.codex/config.toml 的 skills_paths 数组。
    • 



写 .agents/skills/ 下的 skill 时要严格遵循 base SKILL.md——只用 name / description / argument-hint / $ARGUMENTS / version 这几个跨工具识别的字段，Claude 私有 context: fork 与 Codex 私有 openai.yaml 都不放进来。需要工具特化时在各自 .tool/skills/ 下放工具专属版本（同名时该工具仍优先用自己路径下的）。


Plugin vs User-written 优先级
四类来源的优先级总规则是"plugin 最高、project 居中、user 最低、built-in 兜底"——但具体细节因工具而异：






工具
优先级顺序
同名冲突策略





Claude Code
plugin > project > user > built-in
高优先级覆盖低优先级，built-in 仅在前三者都没有时启用




Codex
project > user（无 plugin/built-in 层）
project 覆盖 user




OpenCode
plugin > .opencode > .claude > .agents > user
数组先发现的留下、后扫到的同名去重；可配置顺序





plugin > project 这个规则的设计意图是"plugin 升级要可预测"——如果 user 偶然写一个同名 skill 把 plugin 行为 shadow 了，plugin 升级带来的新功能就被吃掉。代价是 plugin 维护者必须用前缀避免与常见 user skill 重名。


社区约定的 plugin 命名前缀：<org>-<tool>-<verb> 形式，例如 acme-deploy-runner、stripe-checkout-tester、linear-issue-helper。

.agents/skills/ 加 .gitignore 例外白名单是最干净的工程实践：


# Ignore tool-private skill directories by default
.claude/skills/
.opencode/skills/
.codex/skills/
# But always commit the neutral team-shared path
!.agents/skills/
这样新加入团队的人 clone 仓库后 .agents/skills/ 直接可用、其它工具私有路径按需本地配置。


IDE 与 CLI 协同
2026 Q1 之前 Skills 是 CLI 工具独享——VS Code / Cursor / Windsurf 等 IDE 内置 AI 不读 SKILL.md。VS Code Copilot 在 2026 Q1 的 1.95 release 加入 SKILL.md 支持后，同一份 skill 在 IDE 内的 Copilot Chat 与终端的 Claude Code / Codex / OpenCode 都能触发——这是 Skills 标准走向"全栈统一"的关键一步。


VS Code Copilot 当前读取的路径：


    

  • .vscode/skills/<name>/SKILL.md（VS Code 项目本地）
    • 

  • .agents/skills/<name>/SKILL.md（自动扫，与 OpenCode 一致）
    • 



字段支持仍是 base 集——VS Code 不实现 Claude 私有的 context: fork、!command、allowed-tools。对团队的实际意义是：在 .agents/skills/ 下写跨工具 skill 时，VS Code Copilot 也能读到，IDE 内的轻量 AI 任务（如"生成 commit message"）与 CLI 内的重型 agent 任务（如"运行 PR review skill"）共用同一份 skill。


陷阱与常见问题
    

  • symlink 跨平台不一致：Windows 上 ln -s 行为与 macOS/Linux 不同，团队混 OS 时改用 skillsPaths 配置而不是 symlink。
    • 

  • .agents/skills/ 里塞 Claude 私有字段：跨工具复用时这些字段被静默忽略，导致 Codex/OpenCode 用户得到不同行为，违反"中性路径只放 base"原则。
    • 

  • plugin 与 user skill 同名 shadowing：装 plugin 后用户自写的 deploy skill 突然失效（被 plugin 同名版覆盖），用 /skills 命令对比 inventory 即可发现。
    • 

  • commit 了 ~/.config/<tool>/skills/：偶然把全局 user skill 软链到项目导致 commit 进 git——含个人 token、内网 URL 等私密信息时是泄密事故。
    • 

  • VS Code Copilot 不读项目专属字段：以为 context: fork 隔离了主 context，VS Code 里实则全在主会话——IDE/CLI 行为不一致是迁移痛点。
    • 



小结
    

  • .agents/skills/ 是 2026 跨工具共享 skill 的中性路径事实标准
    • 

  • OpenCode 与 VS Code Copilot 原生支持；Claude / Codex 通过 symlink 或 skillsPaths 配置加入
    • 

  • 优先级总规则：plugin > project > user > built-in，OpenCode 数组先发现优先
    • 

  • 团队 commit 策略：.agents/skills/ 必 commit，工具私有路径按约定，user 全局不 commit
    • 

  • IDE 与 CLI 在 2026 Q1 后真正共享 skill 体系，但 IDE 仅 base 字段
    • 

  • 跨平台 symlink 不稳，混合 OS 团队用配置文件 skillsPaths 更可靠
    •
