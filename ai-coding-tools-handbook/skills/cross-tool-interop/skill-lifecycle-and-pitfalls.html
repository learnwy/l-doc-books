Skills 生命周期与安全陷阱

写完一条 skill 不是终点——团队规模化后会面临版本管理、迁移、retire、prompt-injection 审计等 spec 没回答的实战问题。一份用了 6 个月、跨 4 个项目的 skill 怎样不破坏依赖它的工作流去 retire？第三方公开 skill 安装前怎样审计 prompt-injection 风险？2026 已发生几起公开 skill 投毒案例 agentskills.io 维护 advisory——本文把 lifecycle 五阶段、版本管理双轨、prompt-injection 审计 checklist、常见陷阱一次收齐。

核心概念

skill lifecycle 类比软件包：从 write → test → ship → adopt → retire，每个阶段有明确的产物与责任人。

Lifecycle 五阶段详解
write：选定 skill 边界（一个 skill 一件事，别堆功能）、定 kebab-case name（与外层目录名一致）、写 description（前置动词、覆盖典型触发场景）、写 body（保持 < 500 行、复杂步骤外挂到 references/）。Frontmatter 最少 name + description + version: 1.0.0，按目标工具加 vendor 字段。


test：dry-run 是必备步骤——/skill-name 在测试 repo 触发一次、看 body 注入是否符合预期、!command 是否预加载成功、scripts/ 是否被正确 spawn。edge case 列表至少包含：(1) 参数缺失时 body 行为；(2) 当前目录无 git/无对应文件时；(3) 模型多 turn 触发是否产生递归依赖。Skill 也建议跑一次 prompt-injection 自检（详见下文 audit checklist）。


ship：commit 到 .agents/skills/<name>/ 或对应工具私有路径、打 git tag（skill/<name>/v1.0.0 形式）、更新 CHANGELOG（描述新 skill 用途、典型触发例、依赖工具）。CI 跑 spec 校验（lint frontmatter、确认 body < 500 行）。


adopt：在团队内部 announce、写一篇 internal wiki 解释"什么时候用这个 skill"。adoption metric 至少跟踪：触发率（每周触发次数）、命中率（触发后是否产出预期结果）、误触率（模型自动调但实际不该调）。/skills 命令的运行日志可作为 metric 数据源。


retire：决定 retire 后先在 description 加 [DEPRECATED] 前缀、body 头部加迁移指引（"请改用 new-skill-name"），grace period 1-2 周后从仓库删。删除前用 git grep 找一遍引用、把 in-flight PR 里的引用一并迁。这套节奏比 silent 删除友好得多。


版本管理双轨
Skills 没有 npm 那种依赖解析——version 字段当前所有工具都不做 semver 比对。但版本管理仍重要，社区采用 version 字段 + git tag 双轨：






维度
version 字段
git tag





形式
version: 1.2.0
skill/<name>/v1.2.0




作用
/skills 列表展示、changelog 引用
历史回滚、git checkout 旧版




谁读
人 / agent
git 工具




何时改
改 body / frontmatter 时 bump
每次 ship 打 tag





breaking change 时改 name 而不只是 bump version——这是 2026 社区收敛的最佳实践。原因：


    

  • 版本号没人 enforce，模型与用户都不知道用的是 v1 还是 v2 行为。
    • 

  • in-flight 任务（agent 已经决定要调 deploy skill、turn 还在跑）切到 v2 立刻挂掉。
    • 

  • 改 name（deploy → deploy-v2）让旧引用显式失败、新调用走新名，迁移期可控。
    • 



非 breaking 改动（描述更新、body 文案优化、加 example）才 bump version。


Prompt-injection 安全审计
第三方 skill（来自公开 marketplace、社区分享、其他团队）安装前必须做 prompt-injection 审计——SKILL.md 内容就是 agent 看到的 prompt、!command 可执行任意 shell、scripts/ 可放任意可执行。2026 已发生数起公开 skill 投毒案例：

影响

审计 checklist（团队 review 公开 skill 时按下面表逐项查）：






检查项
通过标准





name / description 是否声明明确用途
描述清楚 use-when，无歧义




body 是否含 invisible char / zero-width space
用 hexdump 或 IDE 显示控制字符




!command 行是否只读、安全
仅 git status、cat README.md 等只读




scripts/ 内脚本是否经过 review
每行都看得懂、无网络请求、无破坏性写入




allowed-tools 是否真的限了权
列表里没有 Bash 或限到具体子命令




第三方依赖是否锁定版本
scripts/ 内 pip install / npm install 有版本号




是否引用外部 URL 拉内容
没有；或 URL 来自可信源（GitHub raw、内网）





agentskills.io 维护公开 advisory 列表，团队可在 CI 加自动比对——已知投毒 skill 的 hash 在 advisory 里出现时阻止 git commit。


常见陷阱
下面是 2026 团队实践里最常见的几类隐性故障：


    

  • 同名 skill 静默选错：plugin 装上后 user 自写 deploy 被 shadow，用户以为 /deploy 还是自己那份，实则 plugin 版。预防：plugin 用前缀（acme-deploy）；定期用 /skills 列表 diff。
    • 

  • disable-model-invocation 拼成 disable_model_invocation：hyphen vs underscore，spec 字段静默忽略——skill 名义上"仅 user 触发"，实际模型仍能自动调。预防：lint frontmatter、引入 agentskills.io 提供的 schema 校验工具。
    • 

  • allowed-tools 在不支持工具被忽略：在 Codex 写 allowed-tools: [Read] 想限只读，Codex 静默忽略——agent 全权限。预防：靠 harness 层 sandbox（sandbox_mode）补强、不能只靠 skill 字段。
    • 

  • !command 输出过大撑爆 context：!cat large-file.log 把几千行日志注入 body，turn context 立刻爆。预防：用 head -100 或 tail -50 限制输出。
    • 

  • breaking change 只 bump version 不改 name：v2 上线后 in-flight agent 半途行为变更、产物错乱。预防：breaking 一律改 name。
    • 

  • retire 直接删 skill 不留迁移：依赖该 skill 的 agent / 文档 / 团队成员瞬间找不到，工作流断裂。预防：grace period + deprecation mark + 显式迁移指引。
    • 



小结
    

  • lifecycle 五阶段 write → test → ship → adopt → retire，每阶段有明确产物
    • 

  • 版本管理双轨：version 字段做 UI 展示、git tag 做历史回滚
    • 

  • breaking change 改 name 而非 bump version，避免 in-flight 任务中断
    • 

  • prompt-injection 审计 checklist 七项，第三方 skill 安装前必跑
    • 

  • agentskills.io 维护公开 advisory，CI 可自动比对已知投毒 skill
    • 

  • 同名冲突、拼写错误、!command 输出过大、retire 不留迁移是高频陷阱
    •
