Hermes 使用场景与横向对比

核心概念

Hermes 的"persistent memory + 自创 skills + 多 terminal 后端"定位映射到现实工作流，能压缩为三类高频场景：跨次会话长期记忆复用、自创 skill 固化个人/团队约定、跨 terminal 同设备体验一致。本节按这三类拆开看适合谁、不适合谁，并配一张 4 工具横向对比表（Hermes vs Claude Code memory vs ChatGPT memory vs Anthropic API memory），帮助读者一图厘清生态位。

三类场景在实际工作流里常交叉出现，但用户的核心痛点决定了"先解决哪个"。


场景一：跨次会话长期记忆复用
典型用户画像：每天起多次 coding session 的开发者；每次 session 结束都要"再解释一遍上下文"——项目背景、最近的 architecture 决策、coding style 偏好、上次跟你讨论过的 bug 假设——觉得这种重复浪费。


Hermes 在这种场景下给出三件具体的事：


    

  1. session 起手自动拉 memory：coding agent 通过反向 MCP 调 hermes.memory.query(project='X', recency='7d')，session 一开始 working memory 里就有过去一周的相关条目。
    2. 

  2. 结束时回写关键决策：session 末尾 agent 调 hermes.memory.write(content='今天决定 X，理由 Y')，下次 session 起手能再读到。
    3. 

  3. importance + recency 双维排序：curator 按 importance score 重排，老但重要的决策不会被新的小记录挤掉。
    4. 



适合：长期跑同一个项目的开发者；多项目并行需要切上下文的咨询顾问；teaching / mentoring 场景需要回顾历史互动的导师。
不适合：纯一次性脚本任务——配置 Hermes 比直接重新解释更慢。


场景二：自创 skill 固化个人/团队约定
典型用户画像：工程师发现自己的 coding agent 总是要被反复纠正同一个偏好——"我们项目用 4 空格不是 tab"、"commit message 必须 conventional commit 格式"、"PR description 必须含 test plan section"。这种"每次都要纠"的偏好，最适合固化成 Hermes skill。


Hermes 在这种场景下做的事：


    

  1. skill 是本地 markdown 文件：frontmatter 写 name / description / trigger，body 写具体规范；放在 ~/.learnwy/hermes/skills/<name>/SKILL.md。
    2. 

  2. trigger 命中即注入：coding agent 通过反向 MCP 拿到 skill 列表，当 prompt 命中 trigger phrase 时自动把 SKILL.md 内容注入上下文。
    3. 

  3. 团队 skill 通过 git 共享：把 ~/.learnwy/hermes/skills/team/ 做成 git submodule，团队成员各自 clone 即获得统一规范。
    4. 



适合：有明确 coding style 偏好的开发者；想把"团队 review checklist"沉淀为 AI 可消费形式的 tech lead；做 design system 想让 AI 严格遵循的前端工程师。
不适合：偏好经常变 / 还在探索期 — 频繁改 skill 比直接 prompt 更慢。


场景三：跨 terminal 同设备体验一致
典型用户画像：在 macOS 上同时跑 iTerm2（日常）+ Ghostty（试新）+ tmux（远程 SSH 嵌套）的开发者；希望同一个 Hermes 实例在每种 terminal 都能正常工作，不被键位 / 颜色 / TUI 渲染问题困扰。


Hermes 在这种场景下做的事：


    

  1. 7 种 terminal 后端官方适配：macOS Terminal / iTerm2 / Ghostty / kitty / wezterm / tmux / WSL 都有官方测试覆盖与 quirk 补丁；详见 5_seven-terminal-backends.md。
    2. 

  2. memory + skill 与 terminal 解耦：换 terminal 不丢数据；同一 ~/.learnwy/hermes/ 数据目录被所有 terminal 后端共享。
    3. 

  3. 键位 / 颜色 / TUI 渲染 quirk 处理：例如 Kitty keyboard protocol 在 SSH 隧道里 fallback、tmux 嵌套时 truecolor 透传，都内置处理。
    4. 



适合：terminal heavy user 经常切换工具；服务器远程 + 本地混合工作流；多种 OS（macOS + WSL）混跑的用户。
不适合：纯 macOS Terminal 单一环境——多 terminal 抽象层是空头开销。

生态位关键洞察：四种 memory 不是替代关系，是 nesting + 互补关系。同一个开发者可以：


    

  • 在 ChatGPT 里聊周末 hobby（ChatGPT memory）；
    • 

  • 在 Claude Code 里跑工作（Claude working memory + Hermes persistent memory 一起用）；
    • 

  • 在自建 SaaS 后端用 Anthropic API（API memory）；
    • 

  • 让 Hermes 跨上述所有"工作场景"提供长期一致性。
    • 



何时不要用 Hermes
明确反例避免误用：


    

  • 临时性 demo / hackathon 项目：项目命短，记忆资产无 ROI。
    • 

  • 单一工具单一 session：如果只在 Claude Code 里跑、且每个 session 都是独立任务，Claude working memory 已够。
    • 

  • 极敏感数据 + 无私钥管理：Hermes 本地 SQLite 默认未加密；处理敏感数据请先按 6_curator-and-skill-self-improvement.md 或 LUKS / FileVault 加密层兜底。
    • 

  • 完全云端工作流：远程 dev container 频繁销毁重建时，本地 Hermes 数据难同步；这种场景更适合走 SaaS 类记忆方案。
    •

按主导场景做选型：场景 1 主导 → 先配 memory + curator；场景 2 主导 → 先写 5-10 个 skill；场景 3 主导 → 先把多 terminal 兼容跑通。


陷阱与常见问题
    

  • 以为 Hermes 自动学新偏好：memory 只记你写入的内容，curator 只 review 不主动抓取；新偏好仍需 agent 显式 memory.write。
    • 

  • skill trigger 写太宽：trigger 是 "code"、"function" 这种通用词，会在不该激活时也激活；要具体到项目名 / 团队名 / 工具名。
    • 

  • 多 terminal 共享时 lock 冲突：SQLite 单 writer；多 terminal 同时写偶发冲突，curator 设计上避开这一点（cron 单进程）。
    • 

  • 把 4 工具 memory 当替代关系：纵向比较应该看"时间尺度 + 数据所有权 + 跨工具复用"三维。
    • 



小结
    

  • 三类场景：跨会话长期记忆 / 自创 skill 固化约定 / 跨 terminal 体验一致。
    • 

  • 每个场景有"适合 vs 不适合"边界，不要错配。
    • 

  • 4 工具横向对比：四种 memory 是 nesting + 互补关系，不是替代。
