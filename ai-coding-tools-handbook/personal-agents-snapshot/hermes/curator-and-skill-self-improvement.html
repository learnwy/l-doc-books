Hermes Curator 与 GEPA self-improvement

核心概念

Hermes 区别于"无脑日志"型记忆工具的核心是 curator 后台 review + GEPA self-improvement。curator 负责让 memory 长期保持高信噪比——按 importance 重排、去重、退役 stale；GEPA（Generalized Evolutionary Policy Adaptation，ICLR-2026 paper 落地）负责让 skill 在使用反馈下自我精炼——成功率高的 skill 强化、失败的 skill 退化、长期不用的 skill 退役。两套机制结合，让 Hermes 是"会自己保养自己"的 personal-agent 工具。

curator 是低频但高质量的后台进程；它的输出（metric dashboard）是用户看 Hermes "健不健康"的窗口。


Curator 触发机制
curator 有三种触发路径：


    

  1. Cron 触发（默认）：通过 hermes init 时登记的 launchd / systemd cron，默认每天 03:00 跑。
    2. 

  2. Event 触发：在 config.toml 里配 [curator.events] 段，可绑"new session 后"、"memory 写入 > N 条后"等条件触发。
    3. 

  3. Manual 触发：hermes curator run 立刻跑一次（生产 / dry-run / 部分维度三种模式）。
    4. 



[curator]
schedule = "0 3 * * *"
importance_threshold = 0.3
stale_days = 90

[curator.events]
after_session_count = 10
after_memory_writes = 50
实际部署建议：默认 daily cron 足够；只有当 memory 增长极快（如团队场景每天数百条）才加 event 触发。


Memory Review 三件事
每次 curator 周期对 memory 做三件事，按顺序执行：


1. importance re-rank
每条 memory entry 有一个 importance score（范围 0-1），初始值在写入时按规则估算（字数、显式 priority 标签）。re-rank 在每次 curator 跑时按下面公式重算综合分：


scorefinal=importance×decay(t)+access_boostscore_{final} = importance \times decay(t) + access\_boostscorefinal​=importance×decay(t)+access_boost
其中：


    

  • decay(t)=e−λtdecay(t) = e^{-\lambda t}decay(t)=e−λt，λ\lambdaλ 是衰减系数（默认 ln⁡(2)/30\ln(2)/30ln(2)/30 days），新条目分数高、老条目自然衰减。
    • 

  • access_boost=log⁡(1+access_count)access\_boost = \log(1 + access\_count)access_boost=log(1+access_count)，频繁被查询的条目分数被推回。
    • 



查询 memory.query 时按 scorefinalscore_{final}scorefinal​ 倒序返回，确保"重要 + 新 + 常用"的条目最先被 agent 看到。


2. dedupe
curator 用 FTS5 全文索引快速找内容近似的条目：


    

  • 提取每条 entry 的 normalized text（小写、去停用词、词干化）。
    • 

  • 用 SHA-256 hash 找完全重复。
    • 

  • 对近重复（编辑距离 < 阈值 + 同 tag）跑 trigram 相似度计算。
    • 

  • 同组中保留 scorefinalscore_{final}scorefinal​ 最高的，其它标 superseded（不删除，便于审计）。
    • 



dedupe 行为是保守的：默认只标记不删除，用户可手动 hermes memory delete --status superseded --older-than 180d 清理。


3. retire stale
超过 stale_days（默认 90 天）且 access_count = 0 的条目标 retired 状态，不再返回给 memory.query，但仍在数据库里以便审计 / 复活。


退役公式：


should_retire = (now - created_at).days > stale_days
              AND access_count == 0
              AND status == 'active'
被退役的条目可以 hermes memory revive --id <id> 重新激活；这种"软退役"避免误删。


GEPA：skill self-improvement
GEPA（Generalized Evolutionary Policy Adaptation）是 ICLR-2026 paper 提出的演化策略，Hermes 把它落地到 skill 自我精炼。每条 skill 维护四个使用信号：






信号
含义
采集时机





trigger_count
命中次数
每次 skill.dispatch




success_rate
用户后续未否认 / 未撤回的比例
session 结束后回写




user_correction
用户在 dispatch 后明确纠正的次数
session 内 detect 关键词




last_used
最近一次使用时间
dispatch 时更新





GEPA 根据四个信号在每次 curator 周期对 skill 做三类操作：


具体到三类操作：


    

  1. 强化：成功率高且频繁的 skill，被提升 trigger_priority，下次同 prompt 时优先于其他 skill 触发。
    2. 

  2. 退化（自动精炼）：用户经常纠正的 skill，GEPA 会从纠正样本里提取 pattern 并 propose 一份 refined body——用户审阅后接受 / 拒绝。这是 GEPA 的核心 evolutionary loop。
    3. 

  3. 退役：90 天未触发的 skill 标 dormant，不再加载到 trigger 列表，节约 mcp-serve 启动时间。
    4. 



GEPA 是 Hermes 独有的能力——其他 memory 工具或 skill 系统多是静态的，Hermes 通过 GEPA 让 skill 是"活的"。

不健康信号：active 比例 < 50% → curator 太激进 retire，调大 stale_days；refinement_proposed 持续 > 10 → 某些 skill trigger 写太宽，检查 user_correction 高的 skill。


与 docs/02_ai-llm/ 的关系
需要特别澄清：本节谈的 GEPA 是工程落地视角——一条 paper 在 Hermes 这个具体工具里如何被实现为 skill 自我精炼。GEPA 的理论数学公式、policy gradient 推导、与同类 evolutionary 方法（CMA-ES / NEAT）的对比，不在本 hub 范围——这些属于 LLM/ML 理论范畴，本 hub 与 docs/02_ai-llm/ 维持零交叉的明确边界。


读者如想深挖 GEPA 理论，自行查 ICLR-2026 paper；想深挖 Hermes 工程实现，进 ../../../02_personal-agents/3_skills-self-creation/。


用户体感：GEPA 落地的实际效果
一位长期用 Hermes 的开发者，3 个月后可能观察到：


    

  • 频繁使用的 commit-message-format skill 优先级被推到第一，写 commit 时几乎不再被其他 skill 干扰。
    • 

  • 写得太宽的 general-coding-tips skill 多次被纠正后，GEPA propose 了一份更具体的 refined body（限定到 TypeScript），用户接受后 user_correction 下降到 0。
    • 

  • 三个月前写过的 wedding-planning skill 因为活动结束未再触发，被标 dormant 不再加载——但条目还在，万一明年再办类似事可以 revive。
    • 



这种"自适应"行为不需要用户 actively 调参，是 GEPA 在后台默默工作的结果。


陷阱与常见问题
    

  • dedupe 误判同义不同主题：FTS5 + trigram 偶尔把"同样讲 React 但讲不同子主题"的两条 entry 标重复；建议加细粒度 tag 区分。
    • 

  • GEPA propose 的精炼直接 auto-accept：默认 propose-only，需要用户审阅；千万别开 auto-accept，否则 skill 会偏离原意。
    • 

  • stale_days 设太短：30 天会把许多季节性 skill 误退役；建议 90 天起步，按使用反馈调整。
    • 

  • importance score 全部手动改：违反 GEPA 自适应初衷；让 access_boost 自然推回更稳。
    • 

  • 跨设备 mesh 时 curator 多机并发：必须只在一台机器跑 curator，其它机器读结果；多机并发会写冲突。
    • 



小结
    

  • curator 三件事：importance re-rank / dedupe / retire stale，按 cron 或 event 触发。
    • 

  • GEPA self-improvement：四个使用信号 → 三类操作（强化 / 退化 propose refine / 退役）。
    • 

  • Metric dashboard 三件套：memory health / skill hit rate / refinement count，是健康监控入口。
    • 

  • 与 docs/02_ai-llm/ 零交叉：本 hub 是工程落地视角，理论部分在 LLM 系列。
    • 

  • 长期效果：常用 skill 优先级上升、写宽的被自动精炼、活动结束的被 dormant。
    • 

  • 至此 Hermes 速览完结；深入模块请转 ../../../02_personal-agents/。
    •
