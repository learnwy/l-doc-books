OpenClaw chat-platform 接入

核心概念

OpenClaw 本体跑起来后，下一步是把 persona 接到具体的 chat platform——飞书 / Slack / Telegram / Discord 等。接入分三个动作：OAuth 授权 → webhook 配置 → 第一条路由规则。本节以飞书为主、Slack / Telegram 简要带过，让读者拿到 hands-on 的最小可路由链路。路由规则按 peer → parent → guild/roles → account → channel → fallback 多级 lookup 解析，可读且可审计。

OAuth 授权：以飞书为例
飞书接入分三步（其它平台流程类似）。


Step 1: 在飞书开放平台创建应用
进入飞书开放平台，新建一个 Custom App（不是 ISV App）：


    

  1. 应用名建议带 persona 后缀，如 OpenClaw-dev；
    2. 

  2. 启用"机器人"能力；
    3. 

  3. 在"权限管理"里开 im:message、im:message.group_at_msg、im:chat:readonly 三个 scope；
    4. 

  4. 在"事件订阅"里先留空 URL，等下一步 OpenClaw 端起 webhook 再填回；
    5. 

  5. 拿到 App ID 与 App Secret，下一步用。
    6. 



Step 2: 在 OpenClaw 里注册 chat platform
openclaw chat-platform add feishu \
  --persona dev \
  --app-id cli_xxxxx \
  --app-secret xxxxxxxxxxxx
注册后 OpenClaw 会启动一个 webhook listener，默认监听 :8080/webhook/feishu/<persona>。把这个 URL 填回飞书开放平台的"事件订阅"，飞书会发一个 challenge 请求做校验，OpenClaw 自动响应。


Step 3: 验证 OAuth + webhook 链路
openclaw chat-platform status --persona dev
输出里看到 feishu: oauth=ok, webhook=verified, last-event=<timestamp> 即接入成功。

OpenClaw 把这四类元数据 normalize 成统一的 (peer, parent, guild, roles, account, channel) 六元组，路由规则只针对六元组写，不需关心平台具体字段——这是 OpenClaw 路由层抽象的核心价值。


第一条路由规则
接入完成后，所有 incoming message 都会进 fallback persona（默认 = 注册时指定的 persona）。这显然不够；下一步是写第一条显式规则。


编辑 ~/.openclaw/personas/dev/routes.yaml：


routes:
  - name: 'team-eng-channel-to-dev'
    match:
      platform: feishu
      channel: oc_xxxxx_eng_review
    persona: dev
    action: deliver

  - name: 'personal-dm-from-mentor'
    match:
      platform: feishu
      peer: ou_yyyyy_mentor_id
    persona: dev
    action: deliver
    priority: high

  - name: 'spam-channel-mute'
    match:
      platform: feishu
      channel: oc_zzzzz_random_chat
    action: mute
加载新规则不需要重启：


openclaw route reload --persona dev
openclaw route list --persona dev 可以看当前生效的规则列表，便于审查覆盖关系。


多级 lookup 语法详解
路由规则的 match 段支持六级字段，按 peer → parent → guild/roles → account → channel → fallback 顺序求值。理解这个顺序至关重要——前面命中后就不再尝试后续。


match:
  peer: ou_yyyy # 第 1 级：具体某人 DM
  parent: ou_xxxx # 第 2 级：parent peer（如线程父节点）
  guild: g_xxxx # 第 3 级：guild 级（Discord guild / Slack workspace）
  roles: ['admin'] # 同级：role 匹配
  account: a_xxxx # 第 4 级：account 级
  channel: c_xxxx # 第 5 级：channel 级
  # 不写则进入 fallback
实际写规则的建议：


    

  • 粒度越细 priority 越高：peer 级规则覆盖 channel 级。
    • 

  • fallback 一定要有：否则 unmatched message 直接落到 audit log 里、agent 看不到。
    • 

  • mute 类规则放最前：避免 spam channel 的消息误触发 agent 推理。
    • 



coding agent 通过 reverse MCP 操作路由
接入完成后，coding agent（如 Claude Code）能调用三类 tool：


- openclaw.persona.switch(persona)         # 切换当前 active persona
- openclaw.message.send(channel, text)     # 以 active persona 发消息
- openclaw.route.list(persona)             # 列当前 persona 的路由规则
典型场景：在 Claude Code 里完成一段代码 review 后，让 agent 调 openclaw.message.send 把 review 摘要发到 oc_xxxxx_eng_review 频道——OpenClaw 自动用 dev persona 的 identity 与 signature。


陷阱与常见问题
    

  • OAuth scope 不全：忘开 im:message.group_at_msg 时机器人收不到群消息；现象是 webhook 一直没 event。
    • 

  • webhook URL 填错或没公网：开放平台校验失败；本地开发用 ngrok 等工具暴露公网 URL。
    • 

  • fallback 漏写：unmatched message 沉到 audit log 里；agent 无感知，问题不易暴露。
    • 

  • 多 persona 共用 webhook 端口：默认 :8080 全 tenant 共享；多 persona 同时跑要 reverse-proxy 区分 path。
    • 

  • App Secret 写进 git：经典 leak；用环境变量或 OpenClaw 内置 keychain（macOS）/ libsecret（Linux）。
    • 



小结
    

  • 接入分三步：OAuth 授权 → webhook 配置 → 第一条路由规则。
    • 

  • 飞书 / Slack / Telegram / Discord 平台字段不同，OpenClaw 归一化成六元组（peer/parent/guild/roles/account/channel）。
    • 

  • 路由规则 yaml 可读、可 reload、可审计；优先级按"粒度细 > priority 高"。
    • 

  • coding agent 通过 reverse MCP 拿到 persona.switch / message.send / route.list 三类 tool。
    • 

  • 下一篇 5_deployment-modes.md 对比四种部署形态。
