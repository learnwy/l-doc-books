OpenClaw 四种部署形态

核心概念

OpenClaw 二进制本身是单一可执行体，但落地到不同设备 / 操作系统 / 网络环境时，需要选不同的进程托管方式。官方文档把这件事抽象成四种部署形态：launchd（macOS 开发机常驻）、systemd（Linux 服务器常驻）、Docker 容器（K8s 或隔离环境）、iOS node（移动随身节点）。本节横向对比 trade-off，并给出"什么场景选哪种"的决策路径。

四种形态并不互斥：典型企业用户会同时跑 systemd + Docker，开发者会同时跑 launchd + iOS node。


形态一：launchd（macOS 本地常驻）
适用场景：macOS 桌面开发机，开发者本人主要工作站；希望 OpenClaw 跟随登录自动起、退出登录自动关、与 Claude Code 等 GUI 工具共生。


launchd 是 macOS 的原生进程托管器，本地常驻成本最低、与系统集成最深。安装路径上一节 3_install-and-first-tenant.md 已经走过 npm / Homebrew；这里只补充 launchd plist：


<?xml version="1.0" encoding="UTF-8"?>
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>com.openclaw.agent</string>
  <key>ProgramArguments</key>
  <array>
    <string>/usr/local/bin/openclaw</string>
    <string>mcp-serve</string>
    <string>--port</string>
    <string>8765</string>
  </array>
  <key>RunAtLoad</key>
  <true/>
  <key>KeepAlive</key>
  <true/>
  <key>StandardOutPath</key>
  <string>/tmp/openclaw.log</string>
</dict>
</plist>
放到 ~/Library/LaunchAgents/com.openclaw.agent.plist，然后 launchctl load -w 加载即可。


优势：开机自启、KeepAlive 自动恢复、与 Keychain 原生集成。
劣势：仅 macOS、单机部署、不适合多人共享。


形态二：systemd（Linux 服务器常驻）
适用场景：Linux 服务器、生产环境、多 tenant 共享一台机器；需要稳定 24×7 跑、与现有 syslog / journald 集成、可被运维标准化纳管。


systemd unit 模板：


[Unit]
Description=OpenClaw multi-tenant agent
After=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/openclaw mcp-serve --port 8765
Restart=on-failure
RestartSec=5s
User=openclaw
Group=openclaw
WorkingDirectory=/var/lib/openclaw
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
放到 /etc/systemd/system/openclaw.service，systemctl enable --now openclaw 即开机自启 + 立刻拉起。日志走 journald，journalctl -u openclaw -f 实时查看。


优势：Linux 生态标准、Restart 策略丰富、journald 集成、易于纳入运维监控。
劣势：仅 Linux、不带容器隔离（多 tenant 共用 host 文件系统）。


形态三：Docker（容器 / K8s 集群）
适用场景：需要完全环境隔离、跑在 K8s 集群、CI/CD 流水线里、或希望快速版本回滚的团队。


最小 docker-compose：


version: '3.8'
services:
  openclaw:
    image: openclaw/openclaw:latest
    ports:
      - '8080:8080'
      - '8765:8765'
    volumes:
      - ./data:/root/.openclaw
    environment:
      - OPENCLAW_LOG_LEVEL=info
    restart: unless-stopped
K8s 部署只需把上面映射到 Deployment + PVC + Service 三件套；多副本场景把 storage 换成 NFS 或 cloud volume 即可。


优势：环境完全隔离、镜像版本可固定、回滚一行 docker compose pull + restart 即可；天然适合 K8s。
劣势：端口映射 / 卷挂载需显式配置、容器内访问 macOS Keychain 等系统能力受限。


形态四：iOS node（移动随身节点）
适用场景：开发者希望在 iPhone / iPad 上跑一个 OpenClaw 节点，作为"随身边缘转发器"——出差时本地节点收 chat platform webhook，再通过反向 MCP 同步给笔记本上的 coding agent。


iOS node 不是把完整 OpenClaw 装到 iOS——iOS 沙箱不允许常驻 daemon。它的实现路径是：OpenClaw 提供轻量 iOS 客户端 app，与桌面端通过 OpenClaw 自研的 sync protocol 双向同步 persona 状态。iOS 端负责"收消息 + 缓存 + push 通知"，桌面端负责"实际推理 + 路由决策"。


优势：移动设备也能收到 persona 消息、出差时不离线、可作为多设备 mesh 节点。
劣势：能力受 iOS 沙箱限制、依赖桌面端常驻配合、网络断时仅缓存不推理。

决策路径
直接的"什么场景选哪种"决策路径：


经验法则：


    

  • 个人 macOS 开发机：launchd 起步，单实例足够。
    • 

  • 企业 Linux 生产：systemd 起步，需要多 tenant 强隔离时升级到 Docker。
    • 

  • K8s 集群：Docker 是唯一合理选项。
    • 

  • 多设备同步：桌面跑 launchd / systemd + iOS 上装 iOS node app。
    • 



陷阱与常见问题
    

  • launchd 装到 LaunchDaemons 而不是 LaunchAgents：前者以 root 跑、后者跟用户会话；OpenClaw 需要访问 Keychain，必须放 LaunchAgents。
    • 

  • systemd unit 跑 root：违反最小权限原则；建议建专用 user openclaw 并 chown 数据目录。
    • 

  • Docker 没挂卷：容器重建后 persona / audit log 全丢；务必 -v 挂卷。
    • 

  • K8s 多副本未同步 storage：两副本各自写 SQLite，路由规则脑裂；多副本必须共享 NFS / cloud volume。
    • 

  • iOS node 当推理节点：iOS 端只做收消息与缓存，桌面端不在线时不要指望它做路由决策。
    • 



小结
    

  • 四种部署形态：launchd（macOS 开发机）/ systemd（Linux 生产）/ Docker（K8s 隔离）/ iOS node（移动随身）。
    • 

  • 选择维度：平台、隔离强度、资源占用、升级回滚、多 tenant、调试便捷度。
    • 

  • 常见组合：launchd + iOS node（个人多设备）、systemd + Docker（企业 + K8s）。
    • 

  • 下一篇 6_security-and-audit.md 讲 per-tenant key 隔离与 audit log 设计。
    •
