Session 检索与 closed-loop agent observation

可观测 stack 配好之后，2026 年真正区分团队成熟度的是两件事：按内容搜历史 session 与 让 agent 查自己 telemetry 修 production bug。本文讲这两块的协议层支撑、加 audit log 合规集成、最后讲 agent 自我 instrument 的反向陷阱。

核心概念

closed-loop 与传统监控的差别在于"观察者就是被观察对象"。

Session 检索机制
OTel telemetry 默认把 session transcript 以 OTLP log signal 形式落 backend，按 session.id 做索引。要做"按内容搜 session"需 backend 支持全文搜索（FTS）。

按 session 内容搜索的典型 OpenObserve 查询：


SELECT
  attributes['session.id'] AS sid,
  body
FROM logs
WHERE name = 'gen_ai.client.prompt'
  AND body LIKE '%refactor%'
  AND _timestamp > NOW() - INTERVAL '7 DAYS'
ORDER BY _timestamp DESC
LIMIT 50;
注意前提：content 字段必须 opt-in 开启（参见 ../1_otel-fundamentals/1_otel-and-stream-json-protocols.md content vs structural 章节）。没开 opt-in 的团队只能按 session.id / 用户 / 时间筛选，无法按内容搜。


Hermes 用 SQLite FTS5 做本地 session 检索的设计深度在 ../../../02_personal-agents/2_persistent-memory/ 展开——本地 first 比落 backend 更快、且不必把 prompt 推到云端，适合 PII 敏感场景。本 hub 只做引述。


Closed-loop agent observation
closed-loop 的 2026 关键演化：backend 把自己暴露成 MCP server，coding agent 直接通过 MCP tool 查自己 telemetry。代表实现是 OpenObserve 与 Dynatrace。


典型 MCP tool 函数签名（简化）：


@mcp_tool
def query_otel_logs(
    backend: str,
    session_id: str | None = None,
    error_filter: str | None = None,
    since: str = "1h",
) -> list[dict]:
    """Query OTel logs by session / error / time window."""
    ...

@mcp_tool
def get_recent_errors(service: str, limit: int = 20) -> list[dict]:
    """Get most recent error events from production."""
    ...
闭环工作流四步：


    

  1. agent 完成 PR、merge、自动部署
    2. 

  2. 部署后 24 小时内 OTel 抓到新的 gen_ai.client.event error
    3. 

  3. agent 起新 session、调 get_recent_errors MCP tool 查到自己引入的 error
    4. 

  4. agent 自动 file 修复 PR（带 backlink 到原 PR + error sample）
    5. 



这模式在 2026 年被 OpenObserve、Dynatrace、Honeycomb 三家先后实现。Anthropic 把"MCP servers exceeded 97M downloads in 2025"作为 2026 年 MCP ecosystem 成熟度的关键里程碑。

Audit log 与 Compliance 集成
合规视角下 OTel 不是孤岛——SOC2 / ISO 27001 evidence 要求覆盖 所有 agent 活动，包括 web UI（claude.ai、chat.openai.com）。OTel 只抓 endpoint（CLI / IDE plugin）；web UI 活动要走 Anthropic Compliance API 独立抓。

合并策略：SIEM 按 user.email + timestamp 做 join，把同一用户的端点活动与 web 活动串起来。SIEM 选 Splunk / Sumo Logic / Datadog Security 都行。


实际 evidence 包至少包含三类：


    

  1. agent 运行 audit log（OTel）：哪个用户、哪个时间、调了哪个 tool
    2. 

  2. web UI audit log（Compliance API）：claude.ai 上发过什么 message
    3. 

  3. permission change log：managed-settings.json 变更历史（git log 即可）
    4. 



Agent 自我 instrument 的反向陷阱
closed-loop 模式下，agent 经常被要求"给我加 OTel instrumentation"——LLM 写 OTel SDK 代码非常容易踩坑。


最常见的陷阱：把 user ID / session ID / prompt ID 当 metric label。


# 错误：cardinality 爆炸
counter = meter.create_counter("requests_total")
counter.add(1, attributes={"user_email": user.email, "session_id": sid})
OTel metric label 的 cardinality 上限通常是几千；每个独立 user_email 是一条独立时间序列，10 万用户的话直接打爆 Prometheus 内存。


正确做法：


# user 维度放 log event 或 resource attribute，不放 metric label
counter = meter.create_counter("requests_total")
counter.add(1, attributes={"model": "claude-sonnet-4-7"})  # 低 cardinality
logger.emit({
    "name": "gen_ai.client.api_request",
    "attributes": {"user.email": user.email, "session.id": sid},
})

防御措施：在项目里装一份 OTel-specific skill 或 hook，agent 写 OTel 代码时静态扫 metric label cardinality；或 backend 端配 cardinality limiter（Prometheus 2.45+ 内置）。


陷阱与常见问题
    

  • 以为 OTel 默认能搜 prompt 内容：默认 content 不记，搜不到；先开 opt-in 再回填历史搜不了
    • 

  • MCP server 暴露生产 backend 没加 auth：agent 能查也能改，安全风险大；MCP transport 必须配 token
    • 

  • SIEM join 没对 user.email 做规范化：alice@acme.com 与 Alice@acme.com 算两个用户
    • 

  • Compliance API 拉取漏了 web UI 活动：合规审计被打回；定期 reconcile OTel 与 Compliance API 总量
    • 

  • agent 写 OTel 时把 PII 直接放 metric label：cardinality 爆炸 + GDPR 违规；review 必查
    • 

  • session 检索没按 retention 删数据：GDPR 七天删除请求达不到；retention policy 默认要配
    • 



小结
    

  • session 检索按内容搜需 backend 支持 FTS + content 字段 opt-in
    • 

  • Hermes 本地 FTS5 路径在 personal-agents-modules 章节展开
    • 

  • closed-loop：backend 暴露 MCP server，agent 自己查 telemetry 修 bug
    • 

  • OpenObserve / Dynatrace / Honeycomb 三家 2026 年都内置 MCP server
    • 

  • SOC2 evidence = OTel + Compliance API + permission change log 三源
    • 

  • agent 写 OTel 易把 user ID 当 metric label，需 skill / hook 拦截
    •
