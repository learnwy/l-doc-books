Backend 横向比较与典型部署组合

OTLP 数据导出来之后，下一个问题是落到哪个 backend。2026 年主流选择有六家：SigNoz、Dynatrace、Elastic、OpenObserve、Grafana+Loki+Prometheus、Logfire+Honeycomb+Sentry。本文按四轴打分、给三套典型部署组合的 trade-off、再附 dashboard 三件套查询模板。

核心概念

backend 选型要回答三个问题：自托管还是 SaaS、单产品三合一还是分布式拼装、AI 行业插件成不成熟。

四轴解读：


    

  • 想最便宜：自建 Grafana+Loki+Prometheus 或 OpenObserve；前者运维成本高，后者运维成本低
    • 

  • 想最省事：Dynatrace SaaS；最贵但开箱即用
    • 

  • 想 AI 行业插件：Dynatrace（官方）或 Logfire（社区 Python AI agent 最深度）
    • 

  • 想极致存储节省：OpenObserve（基于 Parquet 列存，2026 年披露 140× 存储节省 vs Elastic）
    •

OpenObserve 在 2026 年获得最大关注的核心数据：140× 存储成本节省（相比 Elasticsearch 同等数据量）；秘诀是 columnar Parquet + Snappy 压缩 + 时间分区。SQL 查询接口让 SRE 直接写 SQL 出报表，不必学 LogQL/PromQL。


-- OpenObserve 查询：过去 24h 各 model 的 cost top 10
SELECT
  attributes['gen_ai.request.model'] AS model,
  SUM(CAST(attributes['gen_ai.usage.cost_usd'] AS DOUBLE)) AS cost_usd
FROM logs
WHERE _timestamp > NOW() - INTERVAL '24 HOURS'
  AND name = 'gen_ai.client.api_request'
GROUP BY model
ORDER BY cost_usd DESC
LIMIT 10;
Sample dashboard 三件套
无论选哪个 backend，2026 年 AI agent 监控 dashboard 都包含三张核心图。


Cost burn-down
按用户、按团队、按 model 看每日 token cost 累加。


PromQL 版本（Prometheus + counter）：


sum by (model) (
  increase(gen_ai_client_token_usage_cost_usd_total{
    organization_id="acme-corp"
  }[1d])
)
LogQL 版本（Loki + log event）：


sum by (model) (
  sum_over_time(
    {service_name="claude-code"}
    |= "gen_ai.client.api_request"
    | json
    | unwrap cost_usd [1d]
  )
)
Tool usage heatmap
按 tool 名 × 时间格子看哪些 tool 调用频率最高。


sum by (tool_name, hour) (
  rate(gen_ai_client_tool_invocations_total[1h])
)
可视化：Grafana heatmap panel + X 轴时间 + Y 轴 tool_name + 值 = invocation count。


Error rate by tool
按 tool 计算成功率与失败率，定位最不稳定的 tool。


1 - (
  sum by (tool_name) (
    rate(gen_ai_client_tool_invocations_total{status="success"}[1h])
  )
  /
  sum by (tool_name) (
    rate(gen_ai_client_tool_invocations_total[1h])
  )
)
这三张图是 2026 年 SRE 给"AI agent 出问题给我看哪几个数"提供的最小答案集。

策略建议：主 backend 选 SQL 友好（OpenObserve）或 PromQL 通用（Prometheus），避免投入到只有自家用的私有 DSL。


陷阱与常见问题
    

  • Dynatrace 按 host 计费而非按 GB：以为是数据量定价，实际 CLI 跑过的每台 dev 机都计费，dev 多了爆炸
    • 

  • OpenObserve 没配 retention policy：默认无限保留，几个月后磁盘满
    • 

  • Grafana stack 三件套版本不匹配：Prometheus 升级 Loki 不升级导致 metric label 不兼容；保持版本同步
    • 

  • Elastic 用全字段索引：default mapping 把 prompt 文本也建倒排索引，存储翻 3 倍；显式标记 index: false
    • 

  • Logfire 默认抓 prompt 全文：与 Claude 的 content opt-in 反向；要在 Logfire 端配 redactor
    • 



小结
    

  • 四轴评估：self-hosted vs SaaS / cost / 三合一 / AI 插件
    • 

  • 六家主流 backend 各有侧重；OpenObserve 在存储成本上领先 140×
    • 

  • 三套部署组合按团队规模选：OpenObserve（小）/ Grafana stack（中）/ Dynatrace（大）
    • 

  • Dashboard 三件套：cost burn-down / tool usage heatmap / error rate by tool
    • 

  • 查询语言：优先选 SQL（OpenObserve）或 PromQL（通用），别绑定私有 DSL
    •
