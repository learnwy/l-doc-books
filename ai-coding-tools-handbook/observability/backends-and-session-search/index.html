Backend 选型与 Session 检索 简介

OTel export 配好之后，下一个问题是数据进哪个 backend。2026 主流选择有 SigNoz、Dynatrace、Elastic、OpenObserve、Grafana+Loki+Prometheus、Logfire+Honeycomb+Sentry 等十几个；按 self-hosted vs SaaS、cost、metric+log+trace 三合一支持度、AI 行业插件成熟度四轴评估各有 trade-off。本章一篇做 backend 对比、一篇讲 session 检索与 agent 闭环——这两块是 2026 真正的实战分水岭，配好后能从"看 dashboard"升级到"agent 自己查 telemetry 修 bug"。

本章包含两篇 L4 文档。

1_backend-comparison.md —— 主流 backend 横向比较。第一块按四轴打分——self-hosted vs SaaS（成本 vs 运维）、cost 量级（存储 ¥/GB·月）、三合一支持度（metric + log + trace 是否一站式）、AI 插件成熟度（是否有专门 Claude/Codex dashboard 模板）；六个主流 backend（SigNoz / Dynatrace / Elastic / OpenObserve / Grafana+Loki+Prometheus / Logfire+Honeycomb+Sentry）各打分。第二块讲三套典型组合 trade-off——自托管 OTel Collector → Prometheus + Loki + Grafana（开源 stack，最便宜，运维成本高）；OpenObserve 单 binary 自托管（140× 存储成本节省，SQL 查询，部署简）；Dynatrace SaaS（AI 插件最成熟，自动 dashboard，最贵）。第三块讲 sample dashboard 三件套——cost burn-down、tool usage heatmap、error rate by tool；附查询模板（PromQL / LogQL / SQL）。

2_session-search-and-agent-loop.md —— Session 检索与 agent 闭环。第一块讲 session 检索机制——OTel transcript 默认以 OTLP log signal 形式落 backend，按 session.id 索引；要做"按内容搜 session"需要 backend 支持全文搜（Elastic / OpenObserve 原生支持，Loki 需 LogQL regex）。Hermes 用 SQLite FTS5 做本地 session 检索的设计深度在 ../../../02_personal-agents/2_persistent-memory/ 展开，此处仅引述。第二块讲 closed-loop agent observation——OpenObserve / Dynatrace 等 backend 把自己暴露成 MCP server，让 coding agent 通过 MCP tool 查自己的 telemetry；典型工作流：agent 写代码 → 部署 → 看到 production error log → 自己 file PR fix。这是 "agent 修 production bug" 的协议层支撑。第三块讲 audit log 与 Compliance 集成——OTel telemetry 抓 endpoint agent 活动（CLI / IDE），但 web UI 活动（claude.ai）需要 Anthropic Compliance API 独立抓；两源合并才完整覆盖；适合 SOC2 / ISO 27001 evidence。第四块讲 agent 自我 instrument 的反向问题——agent 写 OTel SDK 代码时容易把 user ID 放成 metric label（cardinality 爆炸），需要给 agent 装 OTel-specific skill 或 hook 校验。

学习建议是 1_ 先做 backend 选型决策，再读 2_ 把 session 检索与 agent 闭环搭起来；如果短期不做 closed-loop，可以只读 1_。
