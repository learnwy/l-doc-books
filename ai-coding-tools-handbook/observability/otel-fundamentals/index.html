OTel 协议本体与三家 export 配置 简介

OpenTelemetry 在 2026 年成为 AI 编程代理可观测的事实标准——Claude Code / Codex CLI / Gemini CLI 都内置 OTel instrumentation、span/metric/log 三信号都通过 OTLP 协议导出、五类标准 event 跨三家一致。本章把 OTel 协议本体（与 stream-json wrapper 模式的区别）讲清，再把三家工具的具体 export 配置拉平比较。

本章包含两篇 L4 文档。

1_otel-and-stream-json-protocols.md —— OTel 协议本体 + stream-json wrapper 模式。第一块讲 OTel native instrumentation——span 包 model request 与 tool execution、metric 包 token + cost counter、log event 包 prompt 与 tool result；五类标准 event 跨三家一致（api_request / tool_result / session / prompt / event.sequence）；每 event 含 user.email / organization.id / session.id / prompt.id / event.sequence 等标准 attribute；cost / token 字段在 api_request 上。第二块讲 content vs structural 隐私默认——telemetry structural by default（duration / model / tool name 都记），content（prompt 与 tool args）默认不记；opt-in 字段 OTEL_LOG_USER_PROMPTS=1 / OTEL_LOG_TOOL_DETAILS=1 才会记内容；这是 GDPR / SOC2 合规友好的设计。第三块讲 stream-json wrapper 模式——claudia 类工具替代 claude 二进制做 wrapper-level 抓取、把原始 streaming response 捕获后 push 到 Logfire / Sentry / Honeycomb / Datadog；与 OTel native 互补：wrapper 抓更多 raw payload，OTel 抓 structural 与跨工具 unified。第四块讲性能开销——telemetry async、不阻塞 agent 主线、典型 <10ms per operation。

2_per-tool-otel-export-config.md —— 三家具体 export 配置。第一块讲 Claude Code——env var CLAUDE_CODE_ENABLE_TELEMETRY=1 启用 + 选 OTLP HTTP / gRPC / console exporter + endpoint env vars；admin 通过 managed-settings.json 中央化控制全 org 配置（避免 dev 各自配错）；opt-in content 字段如上。第二块讲 Codex CLI——opt-in OTel 监控、CLI / IDE / app / Cloud 各 surface 共享同一份 telemetry pipeline；cloud execution 自动 Anthropic-managed exporter；on-prem 需手动配。第三块讲 Gemini CLI——内置 OTel + 预配 Dynatrace dashboard、与 Google Cloud Operations 默认集成；on-prem 走标准 OTLP。第四块讲 跨工具 unified export pattern——三家共享同一份 OTel Collector、单一 dashboard 看所有 agent 活动、关键好处是 SRE 不必维护三套监控。

学习建议是 1_ 先读完吃透 OTel 协议本体（理解 span/metric/log 三信号的角色），再读 2_ 配自己用的工具；首次部署的 SRE 建议把第 2 篇当 deployment checklist。
