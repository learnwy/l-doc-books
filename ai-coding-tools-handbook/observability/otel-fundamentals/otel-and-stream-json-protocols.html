OTel 协议本体与 stream-json wrapper 模式

OpenTelemetry 在 2026 年成为 AI 编程代理的事实可观测协议。Claude Code、Codex CLI、Gemini CLI 三家同时把 OTel instrumentation 内置进 CLI 主循环，按 span / metric / log 三信号导出 OTLP 数据。本文先把"协议本身长什么样"讲清，再说 wrapper 模式如何与 native OTel 互补。

核心概念

OTel 在 AI coding agent 上下文里有三层结构。第一层是 三信号模型——span 描述请求生命周期（model request、tool execution）；metric 是聚合计数器（token、cost、retry）；log 是离散事件（prompt 文本、tool result、error）。第二层是 跨工具一致的标准 event schema——5 类 event 跨 Claude / Codex / Gemini 字段几乎完全相同。第三层是 content vs structural 二分——默认只记结构（duration、model、tool 名），内容（prompt 文本、tool 参数）opt-in 才记。

五类标准 event 跨三家一致
OTel 在 GenAI 子规范里定义了一组面向 AI agent 的 event 名，Claude / Codex / Gemini 在 2026 年都按这套 schema 发送。

每条 event 都带一组 resource attribute：user.email、organization.id、session.id、prompt.id、event.sequence、host.name、service.version。这些字段保证跨工具 join 同一个用户、同一个 prompt 链路。


Content vs structural 隐私默认
OTel SDK 默认只记 structural 字段：span duration、tool 名、token 数、HTTP status code。这套数据足以做性能监控与配额告警，但不足以做问题复盘——复盘要看 prompt 原文与 tool 参数。


要开启 content 字段，需 opt-in 两个环境变量。


export OTEL_LOG_USER_PROMPTS=1
export OTEL_LOG_TOOL_DETAILS=1
打开后会多记三类内容：


    

  • gen_ai.client.prompt.content：完整 user prompt 文本
    • 

  • gen_ai.client.tool_result.arguments：tool 入参 JSON
    • 

  • gen_ai.client.tool_result.output：tool 返回内容
    •

合规友好的设计哲学：默认安全，只有团队明确签署数据处理协议、做完 DPIA（Data Protection Impact Assessment）才开启 content 字段。Anthropic、OpenAI、Google 三家文档都强调这是 "privacy by default" 的实现。


Stream-json wrapper 模式作为补充
OTel native instrumentation 抓的是结构化信号，但有时候团队需要拿到 完整的原始 streaming payload——比如调试某个 model response 在哪一帧丢字、审计某次 tool 返回的全文。这时候 wrapper-level 抓取登场。


代表工具是 claudia。它的设计：以二进制 wrapper 身份替代 claude CLI，把 stream-json 协议（Claude / Codex 内部用的 NDJSON 协议）逐帧捕获，再 push 到 Logfire、Sentry、Honeycomb、Datadog 等。

实际部署建议：90% 场景用 OTel native，留 1 台机器配 wrapper 做 spot check。Wrapper 抓全量 payload 体积大、且默认就记 PII，长期不可控。


性能开销与故障隔离
OTel SDK 默认 async export——span 写入 in-memory queue，后台批量推送到 Collector。这设计保证 agent 主循环不阻塞。


实测开销（2026 年三家官方文档披露的数字）：


    

  • 单 event 写入 queue：约 50 微秒
    • 

  • 单次 API request span 全链路开销：< 10 毫秒
    • 

  • queue 满（backend 挂）行为：drop 老数据、不阻塞写入
    • 



故障隔离三层：


    

  1. Exporter 失败：不重试到失败，drop 后写本地 log warn
    2. 

  2. Collector 不可达：retry 3 次后 drop，agent 继续工作
    3. 

  3. OTel SDK 自己 panic：try-catch 包裹，绝不传播到 agent 主线
    4. 



这种"telemetry 永远不能阻挡 agent 工作"的设计是 OTel 在 2026 年获得三家厂商集体采用的核心原因之一。


陷阱与常见问题
    

  • 以为 OTel 默认抓 prompt 内容：默认不抓，需 opt-in；忘了开会导致复盘时只看到 span 没看到内容
    • 

  • 用 user.email 做 metric label：cardinality 爆炸；user 维度应放 resource attribute 或 log event，不放 metric label
    • 

  • wrapper 与 native 双开记重了：两条路径都进同一 backend，同一事件会被记两次；要么各进各家 backend，要么 wrapper 关掉 native export
    • 

  • OTel Collector 没配 retry queue：backend 短暂挂时 drop 数据；生产环境必须配 persistent queue（disk-backed）
    • 

  • stream-json wrapper 拦截 stdin/stdout：与 claude --print 这种 non-interactive 模式冲突，CI 跑会卡
    • 



小结
    

  • OTel 三信号（span / metric / log）覆盖 AI agent 全生命周期
    • 

  • 5 类标准 event（session / prompt / api_request / tool_result / event.sequence）跨 Claude / Codex / Gemini 一致
    • 

  • Content 字段默认关闭，opt-in OTEL_LOG_USER_PROMPTS=1 / OTEL_LOG_TOOL_DETAILS=1
    • 

  • stream-json wrapper（claudia 等）与 OTel native 互补：wrapper 抓 raw payload，native 抓 structural unified
    • 

  • async export + 三层故障隔离保证 telemetry 永远不阻塞 agent 主线
    •
