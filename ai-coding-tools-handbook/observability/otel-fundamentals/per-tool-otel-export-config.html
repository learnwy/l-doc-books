三家 CLI 的 OTel export 配置

OTel 协议本体讲完，下一步是把三家工具配起来：env var 怎么设、exporter 怎么选、admin 怎么中央化、cloud 模式怎么处理。本文按 Claude Code / Codex CLI / Gemini CLI 三家依次过一遍，再讲跨工具 unified export 的部署模式。

核心概念

三家 CLI 的 OTel 启用都走 opt-in env var + OTLP exporter 两层。差别在：

  • 谁默认配好 dashboard：Gemini 与 Dynatrace 深度集成、Claude 与 Codex 不绑定 backend
  • admin 怎么中央化：Claude 用 managed-settings.json、Codex 用 cloud-managed config、Gemini 用 gcloud config
  • cloud 模式自动 export：Codex Cloud 与 Anthropic 自管 exporter、本地装机要手动配

Claude Code 配置
Claude Code 的 OTel 启用最小命令。


export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_ENDPOINT=http://collector.internal:4318
可选 exporter 三种：console（stdout 调试）、otlp（生产 OTLP HTTP/gRPC）、prometheus（pull-based 暴露 metric 端口）。


Admin 中央化通过 managed-settings.json——放在 /etc/claude/managed-settings.json 或 macOS /Library/Application Support/Claude/，全 org 用户共享配置。


{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.internal:4318",
    "OTEL_LOG_USER_PROMPTS": "0",
    "OTEL_LOG_TOOL_DETAILS": "0"
  },
  "permissions": {
    "deny": ["mcp__filesystem__delete"]
  }
}
中央化的核心好处：dev 自己改 env var 也覆盖不了——managed-settings 优先级最高。SRE 一处配好，全 org 一致；避免出现"老王把 endpoint 配错导致他那条 metric 丢了"。


Codex CLI 配置
Codex 的 OTel 启用：


export CODEX_TELEMETRY=1
export OTEL_EXPORTER_OTLP_ENDPOINT=http://collector.internal:4318
Codex 的设计哲学是 跨 surface unified——CLI、IDE plugin、ChatGPT app、Codex Cloud 共享同一份 telemetry pipeline。在 Cloud 模式（agent 跑在 OpenAI 数据中心）时，Anthropic-managed exporter 自动 push 到你绑定的 backend；本地装机要手动配 OTLP endpoint。


跨 surface 的好处：在同一个 dashboard 里能同时看到 dev 用 CLI、PM 用 ChatGPT app、CI 用 Codex Cloud 三类活动；同一个 user.email 把三个 surface 串成一个用户视图。

Gemini CLI 配置
Gemini 的特殊在于"开箱即用"——内置 OTel + 与 Google Cloud Operations 默认集成 + 预配 Dynatrace dashboard 模板。


最小启用：


export GEMINI_TELEMETRY=1
# 默认 export 到 gcloud project 当前用户的 Cloud Operations
gcloud config set project my-team-2026
Cloud Operations 集成意味着：trace、metric、log 三信号直接出现在 GCP console；无需另装 Collector。对小团队特别友好——5 分钟就能看到 dashboard。


如果走 on-prem 自托管，标准 OTLP 配置即可：


export GEMINI_TELEMETRY=1
export OTEL_EXPORTER_OTLP_ENDPOINT=http://collector.internal:4318
unset GEMINI_USE_CLOUD_OPERATIONS  # 显式关掉默认 GCP 集成
Dynatrace 与 Gemini 的合作在 2026 推出了一套 AI coding agent monitoring 模板——一键导入后自动出现五张 dashboard：

这套模板是 2026 年 SRE 圈最常被复制的"开箱可观测"基线。


跨工具 unified export pattern
三家 CLI 都遵循 OTel 标准 OTLP 协议，意味着可以让它们共享同一份 OTel Collector，最终落到同一份 backend。这是 platform 团队 2026 年最常采用的部署模式。

最小 docker-compose Collector 配置：


version: '3'
services:
  otel-collector:
    image: otel/opentelemetry-collector-contrib:0.106.0
    ports:
      - '4317:4317'
      - '4318:4318'
    volumes:
      - ./otel-config.yaml:/etc/otel-config.yaml
    command: ['--config=/etc/otel-config.yaml']
otel-config.yaml 关键骨架：


receivers:
  otlp:
    protocols:
      http: { endpoint: 0.0.0.0:4318 }
      grpc: { endpoint: 0.0.0.0:4317 }
processors:
  batch: {}
exporters:
  prometheus:
    endpoint: 0.0.0.0:9090
  loki:
    endpoint: http://loki:3100/loki/api/v1/push
service:
  pipelines:
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [prometheus]
    logs:
      receivers: [otlp]
      processors: [batch]
      exporters: [loki]
陷阱与常见问题
    

  • 三家 env var 名字不同：Claude 是 CLAUDE_CODE_ENABLE_TELEMETRY、Codex 是 CODEX_TELEMETRY、Gemini 是 GEMINI_TELEMETRY；写脚本要分别 export
    • 

  • Gemini 没显式 unset Cloud Operations：on-prem 自托管时 telemetry 同时进 GCP 与本地 Collector，cost 翻倍
    • 

  • managed-settings.json 与 user settings 优先级搞反：managed > user，dev 改不掉的项要确认在 managed 文件里
    • 

  • Collector 没配资源 limit：高并发时 OOM；生产必须设 memory_limiter processor
    • 

  • Codex Cloud auto-export 与 on-prem 双开：同一事件被记两次；选一种导出路径
    • 



小结
    

  • 三家都走 opt-in env var + OTLP exporter 两层
    • 

  • Claude 中央化用 managed-settings.json、Codex 用 cloud config、Gemini 用 gcloud
    • 

  • Gemini 默认与 GCP Cloud Operations 集成、附 Dynatrace dashboard 模板
    • 

  • 跨工具 unified pattern：三家共享一份 OTel Collector，统一 dashboard 看所有代理
    • 

  • Docker-compose Collector + Prometheus + Loki 是 2026 最小可观测 stack
    •
