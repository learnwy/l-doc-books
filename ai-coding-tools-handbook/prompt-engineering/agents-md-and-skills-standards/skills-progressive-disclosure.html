SKILL.md 与渐进披露机制

"AGENTS.md 是静态项目协议，SKILL.md 是动态过程性知识"——两条标准在 token 经济学上互补而不重叠。

SKILL.md 解决的不是"项目偏好怎么写"，而是另一个更尖锐的问题：当一个 agent 被装上 50 个领域技能（写 SQL / 调试 GDB / 跑 K8s / 设计 React 组件 ...），怎么避免把所有指令一次性塞进 system prompt、把 8K context 烧个精光？答案是 progressive disclosure——会话启动只载入每个 skill 的 name + description（约 30-50 token / 个），匹配任务时才把对应 SKILL.md body（500-3000 token）注入上下文。这个机制由 Anthropic PM Mahesh Murag 在 2025 年下半年提出、2026 年 1 月以 Apache-2.0 协议发布到 agentskills.io。

核心概念

Skills 的格式与加载流程可以拆成三阶段：注册（agent 启动时扫描所有 skill-name/SKILL.md）、匹配（用户输入触发 description 匹配）、注入（命中的 skill body 进入 context）。

Progressive disclosure 的关键洞察是：模型本身就擅长根据短描述匹配能力——这与 GPT-4 系列被广泛用于"函数调用 description-based dispatch"是同一机制。把 description 写好（清晰说明触发场景），匹配准确率就高，不需要额外的 RAG 索引或向量库。


数学上，若 nnn 是 skill 数量、ddd 是平均 description token、bbb 是平均 body token、hhh 是命中率（通常 1，因为模型一次只调一个 skill），则会话总 token 开销为：


T=n⋅d+h⋅bT = n \cdot d + h \cdot bT=n⋅d+h⋅b
相比全量装入的 n⋅bn \cdot bn⋅b，节省比例为 1−n⋅d+h⋅bn⋅b≈1−db1 - \frac{n \cdot d + h \cdot b}{n \cdot b} \approx 1 - \frac{d}{b}1−n⋅bn⋅d+h⋅b​≈1−bd​，在 d=40,b=1500d=40, b=1500d=40,b=1500 时约节省 97%。


2026 跨工具适配
SKILL.md 在 2026 上半年已被 16+ 工具支持，但分两层：base SKILL.md 跨工具直读——任何合规 SKILL.md 在任何支持的工具里都能加载；扩展字段各家叠加——工具可在 frontmatter 添加自家 namespace 字段，遵守 agentskills.io 的 RFC 流程。


典型扩展示例：


    

  • Claude Code 在 frontmatter 加 context: fork（控制 skill body 是否进入子 agent context）、allowed-tools 限制可调用工具
    • 

  • Codex 加 openai.yaml sidecar 文件 + frontmatter openai.role: developer | assistant 字段
    • 

  • OpenCode 加 instructions.attach: true 让 skill 也参与 instructions 字段聚合
    • 

  • Cursor 加 cursor.rules.scope 把 skill 限定在编辑器特定模式下激活
    • 



关键点：base SKILL.md 字段（name / description / version / license / tags / requires / inputs / outputs / examples 等）跨工具语义一致，扩展字段被不支持的工具静默忽略，不破坏可移植性。


与 AGENTS.md 的角色分工
两份开放标准在同一仓库里并存的典型布局：


my-project/
  AGENTS.md                # 项目协议：测试命令、代码规范、commit 风格
  AGENTS.local.md          # 个人偏好（gitignored）
  .agents/skills/          # 团队共享 skill 目录
    code-reviewer/
      SKILL.md
    db-migrator/
      SKILL.md
  ~/.agents/skills/        # 用户级 skill（跨项目）
    

  • AGENTS.md 回答"在这个仓库工作时永远要遵守的偏好" → 100% 进入 context
    • 

  • SKILL.md 回答"具备这些可调用的过程性能力" → 仅 description 进入 context，body 按需注入
    • 



两者在 token 上完全互补：AGENTS.md 应当短（< 300 行）、SKILL.md 数量可以多（progressive disclosure 控制开销）。


陷阱与常见问题
    

  • description 写得太泛：写"用于数据库"，模型在面对"GraphQL schema 设计"时也可能误调；正确做法是把触发条件写具体——"当用户提到 PostgreSQL / EXPLAIN / 慢查询 / 索引时调用"。
    • 

  • body 写得太长：单份 SKILL.md body 超过 5000 token 时，本身就把 progressive disclosure 的节省吃掉一半；应当拆成多个细粒度 skill，每个聚焦一个动作。
    • 

  • 依赖未声明：skill A 调 skill B 但没写 requires: [B]，B 没装时 A 静默失效——agentskills.io 规范要求 requires 字段必须被工具校验。
    • 

  • scripts/ 路径不可移植：在 SKILL.md body 里写绝对路径 /Users/foo/scripts/analyze.py 会让 skill 无法跨机器使用，正确做法是用相对路径 ./scripts/analyze.py。
    • 

  • 混淆 SKILL.md 与 MCP server：两者都是"agent 的可调用能力"，但 SKILL.md 是同进程文本指令、MCP 是跨进程 RPC——选型见 ../../2_mcp/。
    • 



小结
    

  • SKILL.md 是 agentskills.io（Apache-2.0）2026-01 发布的开放标准，与 AGENTS.md 同属 AAIF / Linux Foundation 治理
    • 

  • 核心设计 progressive disclosure：启动仅载入 name + description（约 50 个 skill ≈ 1500-2500 token），匹配任务才注入 body
    • 

  • 必填字段仅两个（name / description），可选 14+ 字段覆盖版本、依赖、IO schema、示例等
    • 

  • 跨工具：base 字段直读，扩展字段（Claude Code context / Codex openai.yaml / OpenCode instructions.attach）由各家叠加
    • 

  • 与 AGENTS.md 角色互补：前者是动态过程性能力（按需注入），后者是静态项目协议（常驻 context）
    • 

  • 实战陷阱：description 写泛、body 过长、依赖未声明、scripts 绝对路径
    •
