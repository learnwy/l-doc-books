Hermes bundled claude-code skill：Tier 2 单向委派

核心概念

Hermes Agent 在仓库（github.com/NousResearch/hermes-agent-self-evolution）内置一个开箱即用的 bundled skill —— ~/.config/hermes/skills/claude-code/SKILL.md。它把"Hermes 在合适时序触发 Claude Code 子进程跑编程任务、把结果回收到 memory"封装成 SKILL.md spec 兼容的可调用单元。bundled 表示与 Hermes 同步发布、同步升级，user 不需要单独维护；single-direction 表示 Hermes 调 Claude Code，Claude Code 不能反过来进入 Hermes（反向通道用 reverse-MCP，见 ./3_reverse-mcp-tier-2-as-server.md）。这种委派模式专门解决一类问题：Hermes curator 在后台发现需要写代码（例如根据 memory 自动改 dotfile / 改 hooks 配置），但 Hermes 本身不是编程 agent，把这一步外包给 Claude Code 是合理分工。

SKILL.md frontmatter 与契约
bundled 文件的 frontmatter 完整呈现 SKILL.md spec 的"最小可执行集"。关键字段如下：


---
name: claude-code
description: Delegate coding tasks to Claude Code subprocess
allowed-tools:
  - subprocess.invoke
model: claude-opus-4-7
timeout: 600
cost_max_usd: 1.0
---
name 是 skill 触发入口；description 把"什么时候用"压成一句话给 LLM 自检；allowed-tools 把 skill 能调的系统能力限死在 subprocess.invoke，不开放文件系统写、网络访问等扩展面；model pin 到 Claude Opus 4.7 是因为 Hermes 委派的任务往往是"长 context + 需要规划"的混合负载，pin 一个固定模型避免 Hermes 升级后 Claude Code default 变更引入回归；timeout 与 cost_max_usd 是硬上限，触发后 subprocess 强制 kill。


description 字段必须够具体——Hermes LLM 在选择 skill 时只看 description，模糊描述会导致误触发（例如把"写一段说明文档"也分给 Claude Code，但其实 Hermes 自身就能 inline 完成）。bundled 的描述"Delegate coding tasks to Claude Code subprocess"已经把"coding"做了显式锚定。


调用协议：stdio invoke 三种模式
bundled skill 实际调用 Claude Code 时有三种典型 stdio 模式：


模式 A：headless claude -p <prompt> + JSON 输出


claude -p "重写这个 hook 让它兼容 pnpm" --output-format json
stdout 是单一 JSON object（含 text / cost_usd / model / stop_reason）。Hermes 直接 JSON.parse(stdout)、取 text 作 final result、cost_usd 累计 budget。这是默认模式，适合"一次性 prompt 能讲清楚"的任务。


模式 B：claude --continue 复用上次 session


claude --continue --output-format json < new-input.txt
把 Hermes 阶段性产出 pipe 进同一个 Claude session（保留上下文），适合多轮"先看代码 → 再改 → 再 review"工作流。session 落盘由 Claude Code 自管，Hermes 只持有 session id。


模式 C：claude -p + 显式 context 注入


claude -p "$(cat context.md)\n\n任务: 修 telemetry 上报" --output-format json
把 Hermes memory 检索结果通过 cat 拼成 prompt，适合"任务依赖一段已知 context、Claude 不需要自己再去拉"。


三种模式都用 --output-format json 保证 stdout 可机器解析——纯文本输出在跨语言 parse 时容易破。


错误处理与 retry 策略
bundled skill 把四类错误显式分类处理：


    

  • subprocess crash（exit code 非 0）：retry 1 次；第二次仍失败写 audit log（~/.local/state/hermes/audit/skill-failures.ndjson）后放弃，不再继续 retry。这样既扛住偶发网络错误，又防止"出错的任务被无限重试"导致 cost 爆炸。
    • 

  • timeout（默认 600 秒 / 10 分钟）：到时间直接 SIGKILL subprocess，回收 stdout buffer 中已收到的部分作 partial result 落 audit，不计入 retry budget。
    • 

  • cost budget exceeded（per-call 默认 $1）：Hermes 在 invoke 前估算 prompt token 数 + 预期 max output token，若已超 budget 直接拒绝调用，不进 subprocess。
    • 

  • permission denied（user 在系统级关闭了 subprocess 调用）：立刻 fail，写 audit 提示 user。
    • 



与 Hermes curator 的协同
bundled skill 不是"调完 Claude Code 就把 stdout 一股脑塞进 memory"——它走 curator 过滤通道：


    

  1. Claude Code 返回 result（含 text + cost）
    2. 

  2. Hermes 把 result 包装成 candidate memory entry（source: claude_code_session）
    3. 

  3. curator 在下次 cycle 评估：判断该 candidate 重不重要、有没有跟现有 entry 冲突、要不要立刻升 hot；详见 ../../../02_personal-agents/2_modules-deep/2_curator-self-evolution/
    4. 

  4. 调用历史落 ~/.local/state/hermes/audit/skill-calls.ndjson（频率、cost、耗时、success/fail）
    5. 

  5. 触发频率监控：同一 user 短时间内（默认 10 分钟）触发超过 5 次 → curator 暂停该 skill 一段时间
    6. 



这种"先 candidate 后 promote"的设计避免 Claude Code 的输出污染 memory；audit log 是事后排查依据。


不应使用 bundled skill 的反例
bundled skill 不是万能 hammer，三类场景明确不该用：


    

  • 单次轻量 prompt 任务：例如"把这个函数注释翻译成英文"。subprocess 启动 + Opus 4.7 cold prompt 至少几秒延迟 + 几美分成本，远高于 Hermes 自己 inline 用便宜模型完成。判断标准：预期 output < 500 token 且不需要 file IO → 别走 bundled skill。
    • 

  • 需要 user 实时交互的任务：headless claude -p 不支持中途 user 确认、permission prompt 也走不通。需要交互改 file 这种任务用 reverse-MCP（Tier 1 Claude Code 作为入口） 是更对的路径。
    • 

  • 安全敏感任务：subprocess 与 Hermes 共享一个 shell user，文件系统隔离不够。涉及读 secret、改 keychain、改 .ssh/ 的任务应该走专门的 sandboxed agent 或 user 手动确认通道，不要让 curator 在后台自动 dispatch。
    • 



陷阱与常见问题
    

  • description 太宽：fork bundled skill 后改 description 时，常见错误是改成"Run any task"，导致 Hermes LLM 把 non-coding 任务也分到 Claude Code。修复：description 必须显式说 coding / programming / file editing。
    • 

  • subprocess 环境变量泄漏：claude -p 继承 Hermes 进程的全部 env，包括 ANTHROPIC_API_KEY。bundled skill 默认 inherit；如果 user 在 Hermes 配了 high-permission key 但不希望 Claude Code 用，需在 SKILL.md 的 invoke wrapper 里显式 env -i 重置后再注入 scoped key。
    • 

  • session id 复用过期：模式 B 的 --continue 依赖最近一次 session 还存活；如果 Hermes 重启 / Claude Code 升级后 session 格式变更，--continue 会静默 fallback 到新 session（context 丢了）。建议显式检查 session id。
    • 

  • cost budget 不含 prompt cache：cost_max_usd: 1.0 是预算上限；如果 Hermes 重复用同一 prompt prefix（context 很长但不变），Claude Code 的 prompt cache 会显著降低实际 cost，user 可以放心调高 budget 而不增预算线性。
    • 



小结
    

  • bundled claude-code skill 是 Hermes 仓库自带的 Tier 2 → Tier 1 单向委派通道，SKILL.md spec 兼容、与 Hermes 同步升级、无需 user 自维护协议层。
    • 

  • 三种 stdio invoke 模式（headless / continue / 显式 context）覆盖典型场景；错误处理分 crash / timeout / budget / permission 四类，retry 仅 1 次，audit log 落盘。
    • 

  • 与 curator 协同走"candidate → promote"通道，避免 Claude Code 输出直接污染 memory；触发频率有监控、有 backoff。
    • 

  • 反例三条要记牢：轻量任务别走、需要交互别走、安全敏感别走。
    • 

  • 选型时如果方向是 Tier 1 主导（Claude Code 作入口）→ 走 ./3_reverse-mcp-tier-2-as-server.md；如果完全是静态 prompt 共享 → 走 ./2_skills-path-interop.md；选型决策详见 ./4_selection-decision-framework.md。
    •
