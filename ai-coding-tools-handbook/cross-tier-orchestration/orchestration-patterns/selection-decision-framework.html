跨 Tier 编排选型决策框架

核心概念

前三篇分别讲清三种 cross-tier 模式（bundled skill / Skills 路径互通 / reverse-MCP）的协议契约与典型工作流。但实际工程里 user 面对的不是"实现某个 pattern"，而是"当前需求该用哪个 pattern"。本篇给出可执行的选型决策框架：从需求出发，经过 4 个判断节点，落到 4 个 pattern 之一（其中包括"完全 decouple、不跨 tier"作合法选项）。框架背后是一条核心原则——先问需不需要 cross-tier，再问方向，再问 runtime / static，最后才挑具体 pattern。这条顺序避免最常见的失败模式：一上来就纠结 reverse-MCP 还是 bundled skill，结果实际需求根本不需要跨 tier。

决策节点 1：是否需要 cross-tier state share
第一道闸门。问自己：


    

  • 用户的请求在单一 tier 内能完成吗？"帮我写一个 Python 函数" → Claude Code 单 tier 完成、不需要 Hermes 介入。
    • 

  • 跨 tier 是为了 user 体验提升还是 user 必须？比如 Hermes memory 注入可让 Claude Code 答案更贴 user 偏好，但用户不主动要求时未必必须。
    • 

  • 没有 cross-tier 会损失什么？如果回答是"没什么"，那就别加复杂度。
    • 



反例：很多 user 看到 reverse-MCP 演示后立刻在所有项目接上，结果一次会话拉 10 条不相关 memory、prompt 被噪声污染、回答质量反而下降。修复：在 hermes server 端用 high-precision tag 过滤 + 把 reverse-MCP 留给"真有跨会话连续性诉求"的项目（如长期 dotfile 维护、个人 wiki 写作）。


如果回答"不需要"——选完全 decouple：两 tier 各自独立运行、互不调用、用户手工切换工具。这不是失败选项，是合理选项。


决策节点 2：runtime call 还是静态共享
确定需要 cross-tier 后，第二道闸门是"是 runtime 调用还是静态共享"：


    

  • 静态共享：两 tier 复用同一份 prompt / skill 定义，但运行时各跑各的，互不调用对方进程。例如 review-pr 这个 skill，Claude Code 用它跑、Hermes 也用它跑，但两个工具不互相发请求。
    • 

  • runtime call：A tier 进程在执行过程中需要触发 B tier 进程（subprocess 或 IPC）、等结果回来再继续。
    • 



判断标准：


静态共享场景例子：


    

  • 团队 review-pr 流程定义，每个人不同工具但同一份评审规则
    • 

  • coding style 规则的 prompt 模板
    • 

  • 常用 deploy / rollback 操作的封装
    • 



runtime 调用场景例子：


    

  • 拉 hermes memory 当 context 注入 prompt（reverse-MCP）
    • 

  • hermes curator 自动触发 Claude Code 修代码（bundled skill）
    • 

  • OpenClaw 把多租户对话记录回写到 hermes（在两个工具间转发 state）
    • 



回答"静态"→ 进 Skills 路径互通（.agents/skills/）。详见 ./2_skills-path-interop.md。


决策节点 3：谁主导
runtime call 还需要分主导方：


    

  • Tier 2 主导：personal-agent（Hermes / OpenClaw）在后台 curator cycle、event 监听、定时 schedule 中主动决定要调用 Tier 1 跑编程任务。用户不参与触发。
    • 

  • Tier 1 主导：user 在 Claude Code / Codex 会话里发起请求，coding tool 在执行过程中需要拉 Tier 2 的 context。
    •

Anti-pattern：递归调用与显式 message queue
无论选哪个 pattern，递归 call chain（A → B → A → B → ...）是必须严防的反例。每个 pattern 内置 reentry-guard：

reentry-guard 机制

subprocess timeout / cost budget / retry=1 上限

但有时设计层面就想做 A → B → A 形式：


    

  • Hermes curator 想要"先调 Claude Code 写一段代码、Claude Code 写完后再触发另一个 curator step、curator 再调一次 Claude Code 验证"
    • 

  • OpenClaw 想要"收到群消息后 Hermes 记 memory，Hermes 再调 Claude Code 出建议，建议回到 OpenClaw 群"
    • 



这种设计正确做法是用 explicit message queue 解耦，而不是 chain 起来：


queue 让 chain 在 message 处"断"——每个 consumer 是独立 process，没有 in-flight 调用栈、不会触发 reentry-guard、可以独立 retry / backoff。Hermes 自带的 curator_schedule 就是 internal message queue 的典型用法。


实施 checklist
选好 pattern 后的落地清单：


bundled skill：


    

  • 在 ~/.config/hermes/skills/claude-code/SKILL.md 确认存在并未被 user 改坏
    • 

  • hermes config get skill.claude_code.timeout 确认 timeout 合理
    • 

  • hermes config get skill.claude_code.cost_max_usd 确认 budget
    • 

  • 测试：手动触发一次 hermes invoke claude-code "test" 看 stdout + audit log
    • 

  • monitoring：~/.local/state/hermes/audit/skill-calls.ndjson 行数 / 失败率
    • 



reverse-MCP：


    

  • .mcp.json 或 ~/.codex/config.toml 注册 hermes server
    • 

  • claude --debug-mcp / codex mcp ls 确认 server 启动成功
    • 

  • 测试：会话里说"查我之前关于 X 的记忆"看 tool call 链路
    • 

  • monitoring：每会话 MCP call 数（status bar 提示）+ hermes server stderr 错误率
    • 



Skills 路径互通：


    

  • 在 mono-repo 根创建 .agents/skills/<name>/SKILL.md
    • 

  • git add .agents/ 并提交
    • 

  • 测试：在所有团队工具里触发该 skill 一次确认行为对称
    • 

  • monitoring：每个工具的 skill resolution（用 claude --list-skills 等命令对比）
    • 



完全 decouple：


    

  • 仅保证两 tier 各自正常运行
    • 

  • 监控：各 tier 独立日志即可
    • 



陷阱与常见问题
    

  • 过度跨 tier：上来就 reverse-MCP + bundled skill 全开，结果两套 budget 互相消耗、cost 翻倍、调试复杂度爆炸。修复：从决策节点 1 重做、只保留必要 pattern。
    • 

  • 方向选错：Tier 1 主导的需求选了 bundled skill，结果"用户输入 prompt 必须先去 Hermes 触发"延迟巨大。修复：方向决定 pattern，不是 pattern 决定方向。
    • 

  • 静态需求用了 runtime pattern：明明只是想跨工具复用 review-pr 规则，却接 reverse-MCP，结果每次 review 都有 MCP roundtrip。修复：判断节点 2 严格执行。
    • 

  • 缺 reentry-guard 配置：自己 fork bundled skill 后改了 timeout=3600 没改 budget，runaway 任务跑了一小时烧掉 $50。修复：fork 后逐项 review reentry-guard 配置。
    • 

  • monitoring 缺失：上线 pattern 但没接 audit log / cost dashboard，问题发生时无法 root-cause。修复：每个 pattern 的 monitoring 项目对应 implement。
    • 



小结
    

  • 跨 tier 编排选型走"四节点决策"：是否需要 → static vs runtime → 谁主导 → 落到 4 种 pattern 之一。
    • 

  • 4 种 pattern 各有适用场景：bundled skill（Tier 2 主导单向）、reverse-MCP（Tier 1 主导长会话）、Skills 路径互通（静态共享）、完全 decouple（不需要 cross-tier）。
    • 

  • 选型矩阵五维度（状态方向 / 主导 tier / runtime call / context 注入 / cost 模型）让对比一目了然。
    • 

  • Anti-pattern：递归 call chain 严禁；如果 design 上需要 A → B → A，必须改用 explicit message queue 解耦。
    • 

  • 实施 checklist 涵盖配置文件、测试、monitoring 三方面，落地后才算完成 pattern 实施。
    • 

  • 前三篇 ./1_hermes-bundled-claude-code-skill.md / ./2_skills-path-interop.md / ./3_reverse-mcp-tier-2-as-server.md 是细节，本篇是顶层选型；整 hub 与 ../../../02_personal-agents/2_modules-deep/3_mcp-bidirectional/ "双向 MCP"专册互为镜像。
    •
