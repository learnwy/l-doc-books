OpenCode 与 Claude Code / Codex / Crush 的对比定位

核心概念

读者在选型时几乎一定会同时把 OpenCode、Claude Code、Codex CLI 三家放到桌面比较；如果偏好 Go 生态还会顺手看一眼 Charm Crush。本文不展开模块级细节（那是 01_coding-tools/ 的工作），只回答两件事："四者定位差在哪一刀" 和 "哪些读者画像最适合选 OpenCode"。如果读完之后判定自己不属于"为 OpenCode 而生"的画像，可以直接转去 Codex / Claude Code 的对应 hub。

一句话归纳：Claude Code 是"闭源 ecosystem 最厚"、Codex CLI 是"OpenAI 主线最新"、Crush 是"Go 生态最轻"、OpenCode 是"开源 + 协议中立 + 远程会话"。四条路线没有谁更优，看读者的取舍。


三大差异化卖点
OpenCode 在同类工具里站住脚，不靠"再做一个 TUI"，而是靠三个共同生效的设计决定。


Provider-agnostic + 75+ models：通过 Models.dev 接入 Anthropic / OpenAI / Vertex / Bedrock / Azure / xAI / Groq / DeepSeek 等主流提供商，加 Ollama / LM Studio / llama.cpp 本地推理；官方还运营付费 gateway OpenCode Zen 与订阅 OpenCode Go，给不想自管多家 API key 的用户提供一站式入口。这一点相对于 Claude Code 仅绑 Anthropic、Codex 默认绑 OpenAI 的形态，是真正的"中立"。


Client / Server 架构：server 可以跑在 $5/月 的 VPS 上，桌面 / 移动 client 通过 HTTP + SSE 接入，会话状态完全留在 server。读者可以早上在 Mac 用 TUI 起一个长跑任务、晚上在 iPad 上看输出——这是同类里唯一原生支持这种部署形态的。Codex 的 codex remote-control 需要自己拉部署、Claude Code 走 SaaS 而非自托管。


Plan / Build 双主 agent：Tab 一键切换；build agent 默认有 edit / bash / task 等改写权限，plan agent 只读、适合让 AI 先推演方案再下手。对应"先规划再执行"的工作流，区别于 Claude Code 的 plan mode（同一 agent 切权限模式）与 Codex 的 /plan slash command（无独立 agent）。


目标读者画像
OpenCode 真正合适的人群分三类。


第一类：terminal-first 工程师。习惯 tmux + neovim + ripgrep、本能抗拒"必须在 VS Code 装插件才能用 AI"的开发者。OpenCode 的 TUI 不是把网页塞进终端，而是按 keyboard-first 重新设计的——Tab 切 agent、Ctrl+P 打开命令面板、/ 触发 slash commands、@filename 嵌入文件路径。


第二类：自建 LLM gateway 的团队。组织有自己的 vLLM / SGLang / Bedrock / Azure OpenAI 部署，希望工程师"统一入口、统一审计、按组织许可的 model 名单"接 AI。OpenCode 的 providers 字段允许把内部 endpoint 与公有 model 混在同一份 opencode.json 里管，OAuth + RFC 7591 Dynamic Client Registration 让接 MCP server 也走标准协议。


第三类：桌面 + 移动 + 远端协同的开发者。CI 长跑任务、容器内代码扫描、远程 staging 修复——这些场景下"server 在远端，UI 在本地"的拆分天然吻合 OpenCode 的 client/server 模型。其它工具走到类似形态需要自己拉 IDE 扩展 + 代理服务器。

陷阱与常见误解
    

  • "OpenCode = Claude Code 的开源平替"：定位重叠但不完全替换——Claude Code 的 ecosystem（Subagent / Hooks 29 锚点 / Plugin marketplace）OpenCode 暂时追不齐。OpenCode 优势在"中立 + 远程"，不是"功能更厚"。
    • 

  • "既然有 OpenCode Zen，那等于商业 SaaS"：Zen 只是按 token 计费的 gateway，本质仍是 BYO-model；要走 zero-ops 还得自己挂 server。
    • 

  • "两边都能读 .claude/skills/，所以 skill 通用"：路径互通≠frontmatter 字段全兼容。Claude Code 独有的 context: fork、disable-model-invocation 在 OpenCode 里会被忽略，必要时回退到 OpenCode 兼容的最小 frontmatter（name / description / triggers）。
    • 

  • "远程 server 等于把代码上云"：server 跑在你自己的 VPS 上，仓库还是 git clone 进 VPS 的本地目录。仍然是 self-hosted，不是 SaaS。
    • 



小结
    

  • 选型一刀：完全开源 + provider-agnostic + 远程会话 → OpenCode；其它路径下 Claude Code / Codex / Crush 各有更优解。
    • 

  • 三大差异化：75+ provider（含 Zen 与本地）、client/server 架构、plan/build 双主 agent。
    • 

  • 三类目标读者：terminal-first 工程师、自建 LLM gateway 的团队、桌面/移动/远端协同的开发者。
    • 

  • 不适合：VS Code 重度依赖、已沉淀 Claude Code skill 资产、需要零 ops SaaS、绑定 OpenAI 主线最新模型的场景。
    • 

  • 模块级别（MCP / Skills / Hooks / Agents）的横向比较在 01_coding-tools/ 各 hub 展开；本文只到定位维度。
    •
