Curator 维护周期与自演进

核心概念

Curator 是 Hermes 长期记忆系统的独立后台进程，把"什么条目升进 hot head / 什么条目降进 cold storage / 什么条目彻底退役"这套决策从 runtime 剥离到一个可观测、可重放的周期性 job。它在 cron 触发与 event-driven 触发之间双轨工作，每次跑出三类操作（importance re-rank / 去重 / stale 退役），并把决策写进 audit log 供后续分析。更关键的是 curator 自己也用 GEPA 做 self-improvement——决策质量随时间提升而非固定规则。

Stage 1: importance re-rank
re-rank 把所有 entry 的 importance 按当前 persona / 最近 activity / user 显式信号重算。算法核心是把上一节描述的三因子公式跑一遍：


importance=0.3⋅σ(recency_days−1)+0.4⋅cos⁡(ventry,vpersona)+0.3⋅user_signal\text{importance} = 0.3 \cdot \sigma(\text{recency\_days}^{-1}) + 0.4 \cdot \cos(v_{\text{entry}}, v_{\text{persona}}) + 0.3 \cdot \text{user\_signal}importance=0.3⋅σ(recency_days−1)+0.4⋅cos(ventry​,vpersona​)+0.3⋅user_signal
但 curator 不是无脑跑公式——它对边界情况有特殊处理。Pinned 条目跳过 re-rank（用户显式 pin 的不能因为 recency 衰减被打下去）；recency 因子对 user_signal > 0.8 的条目衰减更慢（用户多次引用的不轻易冷落）；新条目第一次 re-rank 有 grace period（前 7 天 importance 不下调）。


re-rank 结果按 0.7 / 0.4 两条阈值切：

Stage 2: 去重
人写记忆免不了重复——同一个 API 偏好在三个月内被写过 4 次。Curator 用两层检测识别 duplicate：


第一层 lexical hash：MinHash / SimHash 比较，O(n) 快但只能抓字面近似。第二层 embedding：cos 相似度 >= 0.85 进入第三层 LLM judge——curator 用一个小模型（默认 Haiku 量级）问 "这两条是否表达同一事实"。三层级联让"95% case 用快算法，5% 边界用慢但准的 LLM"。


合并时保留 importance 较高的一份，另一份的 hit_count 加进保留方——历史命中次数不丢。被合并方进 audit log。

Curator 自身的 GEPA self-improvement
Curator 用的"什么算 duplicate / 什么 importance 阈值"这套规则不是 hardcoded，而是一个 DSPy module，被 GEPA 算法周期 refine。每次 curator 跑完后采样 10% 决策给 user 看，user 的更正信号（"这两条不该合 / 这条不该退役"）作为 ASI 反馈进 GEPA。

陷阱与常见问题
    

  • 频繁手动 trigger curator：每次 trigger 都重排所有 entry，把刚写的"未来 7 天 grace period"机制空转。建议除非调试，每天最多 1 次 manual run。
    • 

  • 关闭 archive 直接删除：用户为节省磁盘改 config archive_retention_days: 0，导致 retire 后无恢复路径。强烈建议保留至少 30 天 archive。
    • 

  • 以为 dedupe LLM judge 免费：第三层 LLM judge 走真实 inference，10^4 候选对的 90% 走第一层快算法但仍有 1000 个进 LLM。手动 backfill 长历史前先估算成本。
    • 

  • persona switch 不 trigger curator：默认开启，但用户在 config 关掉后切换 persona 时 importance 不更新，老 persona 的记忆继续占 hot head。
    • 

  • dashboard 数字不对劲：curator metric 落 SQLite，进程被 kill -9 可能丢最后一次。看到 last_run 时间过旧时先检查 hermes curator status。
    • 



小结
Curator 是 Hermes 长期记忆系统的"自维护肌肉"——把 importance 重排、去重、退役从 runtime 剥离到周期 job，让 hot head 始终保持 signal-to-noise 高的状态。三件套 metric dashboard（health / runs / refinement）暴露 curator 内部状态，GEPA self-improvement 让 curator 自己也在演进。一个健康的 Hermes 实例 curator 应该每天跑一次，avg_duration 在秒级，dedupe 占比稳定 10-30%，retire 后恢复率 < 5%——这些数字一旦偏离，说明记忆系统本身或用户的 write 习惯出了问题。下一章进入 Skills 自创，看 GEPA 如何在 skill 层面驱动同样的自演进。
