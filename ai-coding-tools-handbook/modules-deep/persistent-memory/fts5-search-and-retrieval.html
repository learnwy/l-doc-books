SQLite FTS5 全文检索与召回

核心概念

Hermes 把 MEMORY.md 头部之外的 cold storage 条目、所有 session transcript、以及 curator 历史决策日志，统一索引进一个 SQLite 数据库的 FTS5 虚表。FTS5 是 SQLite 3.9+ 自带的全文检索模块，相比向量数据库的优势是零依赖、单文件、毫秒级查询、支持复杂布尔语法——对于 10^5 到 10^6 量级文档的个人记忆场景完全够用，且不需要 embedding 服务。Hermes 的 memory_query 工具暴露 FTS5 查询能力给所有 Tier 1 client 反向调用。

FTS5 索引结构
Hermes 创建一个 contentless FTS5 虚表，正文不在虚表里重复存储，只存倒排索引——节省磁盘并允许同一份 MEMORY.md 文件作为唯一 source of truth：


CREATE VIRTUAL TABLE memory_idx USING fts5(
  entry_id UNINDEXED,
  title,
  body,
  tags,
  tokenize = 'unicode61 remove_diacritics 2'
);

CREATE TABLE memory_meta (
  entry_id TEXT PRIMARY KEY,
  importance REAL,
  created_at INTEGER,
  last_hit_at INTEGER,
  source TEXT  -- memory_md / session / curator_log
);
title / body / tags 三列分别建索引，查询时可以分别 weight：


SELECT entry_id, rank
FROM memory_idx
WHERE memory_idx MATCH '{title body tags}: rpc kitex'
ORDER BY rank LIMIT 10;
{title body tags}: rpc kitex 是 FTS5 列过滤语法，把搜索范围限定到这三列、词为 "rpc" 与 "kitex"。


memory_query API 语法
memory_query 工具的 input schema 把 FTS5 原生语法封装为更友好的字段：


{
  "query": "rpc OR kitex NOT deprecated",
  "top_k": 10,
  "filters": {
    "tags": ["bytedance", "rpc"],
    "min_importance": 0.5,
    "since": "2026-04-01",
    "source": ["memory_md", "curator_log"]
  },
  "rank_mode": "bm25_importance"
}

含义

bm25_importance 模式把 FTS5 内置的 BM25 分数与 memory_meta.importance 加权乘积，公式：


score=bm25(q,d)⋅(0.5+0.5⋅importance(d))\text{score} = \text{bm25}(q, d) \cdot (0.5 + 0.5 \cdot \text{importance}(d))score=bm25(q,d)⋅(0.5+0.5⋅importance(d))
让"importance 高但词形不完全匹配的条目"和"词形完美匹配但 importance 低的条目"取得平衡。


Tokenizer 选型
FTS5 支持多种 tokenizer，Hermes 默认 unicode61 remove_diacritics 2，按 Unicode 类别切分、去除变音符号、保留汉字。但中文场景下 unicode61 把整句汉字按字符切，召回精度低——Hermes 提供两个可切换的 tokenizer：






Tokenizer
适用语言
优点
缺点





unicode61
拉丁 + 通用
零依赖，零配置
中文按单字切，无语义边界




porter
英文为主
词干合并（run/running/ran）
不支持中文




jieba（第三方）
中文
真正分词，召回准确
需 build flag 编译





中文用户在 ~/.learnwy/hermes/config.toml 切换：


[memory.fts]
tokenizer = "jieba"
jieba_dict = "~/.learnwy/hermes/jieba.dict"
切换后必须 hermes memory reindex 重建索引——FTS5 的 tokenizer 是建表期决定的，运行时不可改。

陷阱与常见问题
    

  • 直接拷 MEMORY.md 不重建索引：FTS5 不是自动同步的，curator 跑完才重建。手动改完 MEMORY.md 需要 hermes memory reindex。
    • 

  • 中文召回为零：默认 unicode61 把 "RPC调用" 切成 "R" "P" "C" "调" "用"，搜 "RPC" 找不到含 "RPC调用" 的条目。切 jieba 或在查询里 quote "RPC"。
    • 

  • top_k 太大返回慢：bm25_importance rerank 是 O(k log k)，top_k=1000 比 top_k=10 慢 50x。建议 top_k <= 20。
    • 

  • 以为 FTS5 支持模糊匹配：FTS5 是词形匹配不是模糊匹配，"kitex" 找不到 "kitexx" 拼错条目。需要 trigram tokenizer 或额外 levenshtein 处理。
    • 

  • 跨语言混合索引：英文条目用 porter 词干合并、中文条目用 jieba 分词——FTS5 单表只能一个 tokenizer。建议分两表或都用 unicode61 + phrase quote。
    • 



小结
FTS5 是 Hermes 在"个人记忆检索"场景对"零依赖 + 毫秒响应 + 布尔表达力"的工程取舍。它不解决语义相似度（"汽车"找"机动车"），但在结构化标签 + importance 加权配合下，对个人记忆 10^5 量级体感优于裸向量检索。memory_query 工具把 FTS5 能力暴露给 Tier 1 客户端反向调用，是 Hermes 双向 MCP 架构的核心 tool 之一。下一篇看 curator 如何周期重排 importance、维护这个索引、退役过时条目。
