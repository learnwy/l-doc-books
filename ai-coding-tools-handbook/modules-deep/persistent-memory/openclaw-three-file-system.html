OpenClaw 三件套：AGENTS + SOUL + USER

核心概念

OpenClaw 把长期上下文拆成三个物理独立的 Markdown 文件——AGENTS.md / SOUL.md / USER.md——而不是 Hermes 那样塞进单一 MEMORY.md。这种拆分对应"团队共享 / 角色化人格 / 个人偏好"三种语义截然不同的上下文：协议层信息要跟仓库走，角色语气要按 persona 走，个人习惯要按用户走。三文件按固定层级合并加载，后加载者只能在自己作用域内覆盖前者的字段，不能擦除外层信息。

AGENTS.md：团队协议层
AGENTS.md 是仓库级 commit 进 git 的协议文件，写"这个项目所有人都要遵守的硬约束"。典型内容：API 命名规范、commit message 格式、code review checklist、特定模块的禁忌操作。因为它进 git，所以所有团队成员的 OpenClaw 实例在 clone 仓库后自动获得这层上下文——不需要每个人单独 import skill。


# AGENTS.md

## 协议

- 所有内部 RPC 调用必须经过 trace-context propagation
- commit message 用 `<scope>: <subject>` 格式
- 严禁直接操作 production 库,所有 schema change 走 migration

## 工具白名单

- bytedance-golang-expert（必须使用）
- lark-cli（已配置 oauth）
AGENTS.md 的字段不会被 SOUL/USER 擦除：用户即使在 USER.md 写 prefer_no_trace_context: true 也无法 override AGENTS.md 的 trace-context 协议，因为 OpenClaw 在 merge 时识别 AGENTS.md 的字段为"hard constraint"，下层只能 append 不能 negate。


SOUL.md：角色化语气与价值观
SOUL.md 是 per-persona 文件，每个 persona 一份。OpenClaw 用 persona 划分"上班正式 / 内部协作 / 朋友圈聊天"等使用场景，每个 persona 有独立的语气、value 排序、tool 偏好。SOUL.md 写"这个角色怎么说话、怎么决策"，比 AGENTS.md 软（建议而非约束），比 USER.md 公共（同 persona 在不同用户机器上一致）。


# SOUL.md — Tech Lead persona

## 语气

- 简短直接,避免堆砌形容词
- 决策给出 2-3 个 trade-off 选项,不一锤定音
- 引用论文/spec 给出版本号和日期

## 价值排序

1. 可维护性 > 性能 > 简洁性
2. 数据一致性 > 可用性（除非明确 BASE 系统）
SOUL.md gitignored 不进 git，但跟 repo 走（<repo>/.openclaw/personas/<id>/）——同一个 repo 在不同 user 的机器上 SOUL 可以不同，因为它对应"这台机器上这个用户在这个 repo 扮演什么角色"。


USER.md：个人偏好与习惯
USER.md 是 ~/.openclaw/USER.md 全局单实例文件，写"我这个人在所有 repo / 所有 persona 都一样的习惯"。典型内容：时区、母语、首选编辑器、有特殊偏好的 commit signoff 风格、不喜欢被怎样的话术对待。


# USER.md

## 个人偏好

- 时区: Asia/Shanghai
- 母语: 中文,技术名词保留英文
- 不要在 commit 加 Co-Authored-By trailer（仓库 hook 会拒）
- 偏好 brief reply,默认不超过 200 字
USER.md 在 merge 顺序中最后加载，因此覆盖力最强——但仅限"个人风格"维度。它无法 override AGENTS.md 的协议约束（OpenClaw 识别为 hard constraint）；可以 override SOUL.md 的软建议（例如个人偏好 brief，即使 persona SOUL 默认 verbose，输出最终走 brief）。

实现上，OpenClaw 把三文件 parse 成结构化对象后按字段语义合并而非文本拼接，这是与 Hermes "MEMORY.md 单文件追加"的本质差异。

迁移建议：从 Claude Code 迁来 OpenClaw 的用户，把项目级 CLAUDE.md 内容拆成"协议 → AGENTS.md / 语气 → SOUL.md"两份；用户级 CLAUDE.md 基本可以直接拷成 USER.md。


陷阱与常见问题
    

  • 把 SOUL.md commit 进 git：会导致同事的 persona 被你的语气 override，且 SOUL 可能含个人敏感语境。OpenClaw 的 .gitignore 模板已经默认排除，但 force-add 会绕过——保持谨慎。
    • 

  • AGENTS.md 写软偏好：把"我喜欢 4-space 缩进"写进 AGENTS.md 会强制全团队。这种语气偏好应放 SOUL.md 或 USER.md。
    • 

  • USER.md 期望 override 协议：在 USER.md 写 "skip code review" 不会生效——AGENTS.md 的 hard constraint 不可被下层 negate。
    • 

  • 三文件总和超出预算：OpenClaw 没有 Hermes 的 200 行硬截断，但 merged context 进 system prompt 仍受 model context window 限制。建议三文件总和 < 15KB。
    • 



小结
AGENTS+SOUL+USER 三件套是 OpenClaw 对长期上下文 "团队 vs 角色 vs 个人" 三种作用域的物理分离方案。相比 Hermes 单文件四区块，三件套的好处是：协议层跟仓库 commit 自动同步、人格层跟 persona 独立维护、个人偏好层不污染团队。代价是合并语义更复杂，需要 runtime 区分 hard / soft / append 三类字段。两套方案在 2026 personal-agent 工具栈各占一半场景，没有 universal winner。下一篇深入 Hermes FTS5 全文检索如何在 cold storage 里找到正确条目。
