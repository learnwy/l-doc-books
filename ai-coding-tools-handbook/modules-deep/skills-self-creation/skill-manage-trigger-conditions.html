skill_manage 工具的触发条件

核心概念

Hermes 的 skill_manage 工具实现"agent 自己提议新 skill"的能力，而非 Tier 1 那种"用户手写 SKILL.md 再 commit"的纯手工流程。它在两条路径触发：一是用户重复工作流的自动检测——Hermes 持续观察用户交互，发现相似 task 重复 3 次以上时主动提议把它固化为 skill；二是用户显式 /promote-to-skill 命令——用户认为某次会话值得沉淀，主动指示 Hermes 把当前 trajectory 抽成 skill。两条路径之后是同一个 propose-review-accept 三段流程，由 user 拥有最终 accept/reject 决定权。

自动检测算法
自动检测核心是滑动窗口 + 命名相似度阈值 + 关键操作序列匹配三个组件级联。Hermes 维护最近 30 天的 task trajectory ring buffer，每个 trajectory 包含 user 第一条 message / Hermes 调用的 tool 序列 / 关键中间产物 / 最终输出。

cluster 用 DBSCAN，eps=0.28（对应 sim=0.72），min_samples=3。当 cluster 形成时 trigger propose。


阈值 0.72 不是凭空——Hermes telemetry 在 1000 条 trajectory 标注集上做过 grid search，0.72 时 precision=0.88 / recall=0.61。低于 0.65 时误触多到用户烦躁，高于 0.78 时漏触率超 50% 让自动检测意义不大。


关键操作序列匹配
不是所有相似都值得提议 skill——"用户每天问当天天气" 表层 message 相似，但工具调用单调，没有 skill 化价值。Hermes 加一道关键操作序列长度 >= 3 的过滤：trajectory 内必须至少有 3 个不重复的 tool 调用（不含纯文本回复），才进入 cluster 计算。


def is_skillable(trajectory):
    tools = [step.tool for step in trajectory if step.is_tool_call]
    unique_tools = set(tools)
    if len(unique_tools) < 3:
        return False
    if len(tools) < 5:
        return False
    return True
这道过滤保留"多步骤多工具协作"的 trajectory，过滤掉"单一 query/response" 的轻量交互。


/promote-to-skill 显式命令
用户在会话中输入 /promote-to-skill <name> 或 /promote-to-skill --auto 时，Hermes 把当前会话从开头到这一刻的 trajectory 全部送进 skill 抽取流程。--auto 模式下 name / description / triggers 都由 Hermes 自动生成；不带 --auto 时只生成 description 与 triggers，name 用用户给的。


> 我刚搞清楚怎么用 lark-base + lark-doc 组合做项目周报了
> /promote-to-skill weekly-report-base-to-doc

[Hermes] 我会基于刚才的对话抽出 skill 草案。给我 3 秒...

[Skill draft]
name: weekly-report-base-to-doc
description: 从指定 lark-base 表汇总本周条目,渲染成 lark-doc 周报模板
triggers:
  - "本周项目周报"
  - "汇总 base 到周报"
  - "/weekly-report"
steps: [...]

接受这份草案吗？[y/edit/n]
显式命令路径比自动检测的相似度门槛松——只要 trajectory 包含 >= 2 个 tool 调用就接受 promote。

Accept 写入文件后 Hermes 立即 reload skill registry，下一条 user message 触发 skill matcher 时新 skill 就在候选集里。Reject 不删 trajectory，但把 trajectory 标 skill_reject: true，自动检测器后续不再为它出 propose。


防误触机制
自动检测过于热情会让用户烦——每 3 天就被弹一次 "要不要把这个变 skill"。Hermes 加四道防误触：

第一道与第三道避免 propose 风暴，第二道避免重复 propose 同一类，第四道给"我自己写 skill"的用户完全控制权。

Tier 1 SKILL.md 是"我现在需要这个能力 → 手写一份"，Tier 2 是"系统观察到我重复这件事 → 系统主动提议"。两者不互斥——Tier 1 写完 SKILL.md commit 进 git 后，Hermes 也能 import 进自己 registry 用。


陷阱与常见问题
    

  • 自动 propose 一直不触发：检查日志，多半是关键操作序列长度门槛没过——用户大量交互是单一 tool 调用，正常。考虑用 /promote-to-skill 主动提议。
    • 

  • 同一类 task 反复被提议：上次 reject 了但 trajectory 哈希变了（user message 措辞略改），mute 没覆盖。手动 hermes skill mute <pattern>。
    • 

  • 新 skill 创建后不生效：可能 reload failed。检查 hermes skill reload --verbose 输出，常见原因是 SKILL.md frontmatter 语法错。
    • 

  • 不希望系统观察 trajectory：hermes config skill.auto_propose=false 关闭自动，但 trajectory 仍被记录用于 curator——彻底关需要 hermes config telemetry=false。
    • 



小结
skill_manage 把"识别用户重复模式 + 提议 skill 草案"从手工劳动变成 agent 主动行为。自动检测靠"相似度 0.72 + 关键操作序列 >= 3 + 滑动窗口 cluster"三层级联，user 显式 /promote-to-skill 走更松的旁路，最终都收敛到 propose-review-accept 三段交接给用户裁决。这套机制减少了"我应该把这件事固化"的 cognitive load，但代价是需要细致的防误触阈值。下一篇看 curator 如何在 skill 创建之后周期 review、决定 keep / refine / retire。
