Curator 周期 review skill 的 keep / refine / retire 决策

核心概念

Skill 创建只是开始——一个 skill 在用了 30 天后可能仍然准确、可能在 schema 变化后开始失败、也可能因为用户工作流转移而无人触发。Hermes Curator 把 memory 周期维护的同一套框架移植到 skill：每天 03:00（与 memory 同周期）扫描所有 skill 的近 7 / 30 / 90 天 telemetry，对每个 skill 做 keep / refine / retire 三态决策。Refine 不是简单"重写一遍"，而是把 skill 当成 prompt-program 喂给 GEPA 做反思式演进。

触发条件
后续动作





keep

仅 telemetry 累计，不改文件

中等成功率或用户多次纠正

Skill 的三类 metric
每个 skill 在 SQLite 里有一条 row 累积 telemetry：


CREATE TABLE skill_telemetry (
  skill_name TEXT PRIMARY KEY,
  total_invocations INTEGER,
  success_count INTEGER,
  failure_count INTEGER,
  user_correction_count INTEGER,
  last_invocation_at INTEGER,
  conflict_with TEXT[],
  version TEXT
);

任一指标越界即触发对应决策；多指标边界时取最保守（refine 优先于 retire，避免误杀）。


成功 vs 失败的判定
Hermes 不让 skill 自己声明成功——成功由三个 signal 推断：


    

  1. Skill 在用户 confirm 前完成所有步骤：用户没在中途打断或要求重做。
    2. 

  2. Skill 完成后用户没有立刻发"不对" / "重做" / "回到上一步"：使用 LLM 分类 user follow-up 是 satisfied / dissatisfied / neutral。
    3. 

  3. 下游 metric 无异常：例如 commit skill 后 commit 在仓库 hook 里被 reject 算失败。
    4. 



任意一项 dissatisfied 算 failure，三项 neutral 算 success（保守乐观）。


refine 子流程
Refine 不是 curator 自己改 SKILL.md，而是把 skill 当成 DSPy program 喂给 GEPA：


ASI（Actionable Side Information）是 GEPA 的关键概念——评估器返回的诊断 feedback 不是单一 reward 数字，而是自然语言的"为什么失败"。例如：


ASI for skill weekly-report-base-to-doc, failure trajectory #42:
  Step 3 调用 lark-base +query 时传了 view_id="grid_default",
  但目标 base 已删除该 view。skill 应先 lark-base +list-views
  确认 view_id 有效,失败时 fallback 用 fields_select 而非 view。
GEPA 把这段 ASI 当成"text-optimization analogue of a gradient"，反思后产出 skill v2 的草案。完整 GEPA 机制见下一篇。

graduate 决策：v2 在 ramp 阶段 success_rate >= v1 + 0.05 且 user_correction <= v1 时 graduate；否则 rollback。这套规则避免"5% 改进，但增加 20% correction"的虚假优化通过。


retire 决策的三条触发线
长期 0 触发
usage_30d == 0 AND usage_90d == 0 触发"长期未用"退役。Skill archive 到 ~/.learnwy/hermes/skills/_archive/<name>/，registry 移除条目。这条线针对的是用户工作流变化后已经不需要的 skill——保留它在 registry 只是无效占用 skill matcher 的搜索预算。


持续失败
success_rate < 0.5 over last 30d 触发"失败率过高"退役。但这条线有保护：refine 已经在前一轮尝试过；如果 refine 后两轮 ramp 都失败才走 retire。直接 retire 罕见，多数情况下 refine 能救回。


与新 skill 冲突
用户 install 新 skill 后，curator 计算新旧 skill 的 trigger overlap：


overlap(s1,s2)=J(triggers1,triggers2)\text{overlap}(s_1, s_2) = J(\text{triggers}_1, \text{triggers}_2)overlap(s1​,s2​)=J(triggers1​,triggers2​)
overlap > 0.6 且新 skill success_rate 显著高（>= 0.10 absolute）时，老 skill 进入"冲突 retire"候选。Curator 先弹通知给用户："skill X 与 skill Y 高度重叠，X 在最近一个月内成功率高 12pp，建议 retire Y"；用户 confirm 后退役。

陷阱与常见问题
    

  • canary 阶段把 v2 推到 100%：用户着急测试改进版手动 graduate，绕过 100 invocations gate。允许但风险自负——A/B 数据不足时 v2 可能在 long-tail trajectory 翻车。
    • 

  • skill_telemetry 被手动改：用户为"救活"一个 skill 改 success_count，curator 下次跑会重算（不依赖单次 telemetry 累积）。改 SQLite 没用，应改 SKILL.md 让 GEPA refine 时考虑新 prompt。
    • 

  • 新 skill install 立刻被旧 skill 冲突 retire：新 skill 还没积累 metric 就被认定为"低优先"，curator 误判。新 skill 有 grace period（前 30 天 conflict 不触发 retire）。
    • 

  • refine 后忘了 reload：curator 不会自动 hot-reload runtime registry。改完 SKILL.md 后下个 session 才生效，或用 hermes skill reload。
    • 



小结
Skill curator 把 memory curator 的"周期评估 + 三态决策"模式移植到 skill 层面，并叠加了"GEPA refine + A/B canary"两个独有机制。三个 metric（success_rate / usage_30d / correction_rate）形成决策矩阵，A/B 测试避免 refine 引入新问题，metric-driven retire 让 skill registry 不会无限膨胀。这套机制把 skill 从"创建后冻结"变成"持续演进的活体"。下一篇深入 refine 背后的 GEPA 算法，理解为什么"自然语言 ASI"能像 gradient 一样驱动 prompt-level 优化。
