transform_* 管线的链式调用语义

核心概念

Hermes 把"中间改写 event"的能力抽象成一组 transform_* hook。它们既不属于 Gateway 也不属于 Shell 的边界处理，而是横跨三层的"中间件"：transform_in 在 Gateway 出口 → Plugin 入口之间执行，统一 payload 形态；transform_out 在 Plugin 出口 → Shell 入口之间执行，挂载出站元数据；transform_persona 可注入到任意层，把 persona context 织入 event。三个 hook 都是函数式：输入一个 event，输出一组 event（可能 0 个 = 拦截，1 个 = 改写，N 个 = 扇出）。这种纯函数语义让多个 transform 可以无副作用链式串联，也让 GEPA 能把 transform 函数本身作为优化对象（详见 ../2_skills-self-creation/3_gepa-self-improvement-iclr-2026.md）。

transform_in：入口归一化
transform_in 主要解决"Gateway 已归一化协议、但 payload 内部仍可能千差万别"的问题。例如来自 lark 的消息包含 mention 段、来自 slack 的消息包含 block element、来自 stdio 的消息是纯 JSON。Plugin 不希望关心这些差异，所以 transform_in 把它们都拉平成统一 schema：


def transform_in(evt: InternalEvent) -> list[InternalEvent]:
    if evt.source.platform == "lark":
        evt.payload["text"] = strip_lark_mentions(evt.payload["text"])
    elif evt.source.platform == "slack":
        evt.payload["text"] = flatten_slack_blocks(evt.payload["blocks"])
    evt.payload["normalized_text"] = evt.payload["text"]
    return [evt]
返回 [] 表示拦截——event 不再继续走入 Plugin。这适合做 inbound rate-limit 或敏感词预拦截。


transform_out：出口元数据挂载
transform_out 在 Plugin 已经处理完业务、Shell 即将 dispatch 之前介入。典型用途是给 outbound event 加上 metadata 让 Shell 知道"如何送出":


def transform_out(evt: InternalEvent) -> list[InternalEvent]:
    if evt.event_type == "outbound_event":
        evt.payload["signed_at"] = now()
        evt.payload["signature"] = hmac_sign(
            evt.payload, secret=load_tenant_secret(evt.tenant)
        )
        evt.payload["retry_policy"] = {"max": 5, "backoff": "exp"}
    return [evt]
返回 N>1 event 表示扇出——一个 plugin emit 的 outbound_event 经过 transform_out 后可能扩展为同时 dispatch 到 webhook + fs + stdout 三处。


transform_persona：persona 上下文注入
transform_persona 是 multi-tenant 场景的关键 hook。它的作用是给所有流经的 event 自动打上 persona / tenant 字段，并加载该 persona 的 secret store。它可以挂在 transform_in（入口注入）或 transform_out（出口注入）的任一位置：


实现层的 lookup 走 ../5_multi-tenant-personas/1_five-level-routing-lookup.md 描述的 5 级规则。注入失败（找不到合适 persona）默认走 fallback persona。


链式调用语义
多 plugin 各自注册自己的 transform_in / transform_out，runtime 按注册顺序串行执行。串行而非并行的原因是transform 之间可能有依赖——后一个可能读前一个写入的字段：






语义
描述





顺序
按 plugin 注册顺序，可在 config 显式重排




合并
每个 transform 返回的 event 列表 flatten 进入下一个 transform 输入




短路
任何 transform 返回 [] 时链中断




错误
transform 抛出异常时链中断，event 回退到 raw payload + 错误日志





显式排序示例：


[transform_in.order]
plugins = ["persona", "i18n", "rate_limit", "memory_enrich"]

[transform_out.order]
plugins = ["audit_tag", "sign", "retry_wrap"]
注意 persona 通常排第一——后续 transform 都需要 persona 字段才能正确工作。


错误处理与回退
任何 transform 抛异常都会触发 fallback 链：


fallback 是显式策略选择，三种选项可配置：

描述

跳过抛错 transform，继续后续链

默认 raw——这保证 Hermes 在 transform code bug 时仍能保持基本功能。但 transform_persona 通常配置 abort——如果 persona 注入失败，宁可整条 event 不处理也不希望以错误 persona 执行业务。


与 GEPA 的协同
transform_* 本身可以作为 GEPA 优化对象——它们的代码可以被表达成"接受 event 描述 + 返回处理 logic"的 prompt-like 形式，进 DSPy module 由 GEPA 演化：


例如某 transformin 持续在 emoji-heavy 消息上"normalize 失败"，evaluator 反思后 emit ASI 指出"应在 strip 之前先做 unicode NFC normalize"，mutation LLM 把这步插入到 transform code 里。GEPA 把这种"我自己的代码生成器"形成闭环——transform* 越用越对。


陷阱与常见问题
    

  • transform 修改 event 的同时返回原 event：Python 的对象引用让"修改后再返回"看似 fine，但下一个 transform 拿到的是同一对象，并行调试时会困惑。建议 transform 内部 evt = evt.copy() 之后再改。
    • 

  • transform 内做 IO：transform 应保持纯函数。需要 IO 的应 emit event 让 Plugin / Shell 异步处理。
    • 

  • transform 顺序未显式声明：plugin 加载顺序与 transform 执行顺序不一定一致。生产环境必须 transform_in.order 显式列出。
    • 

  • fallback=raw 时遗漏 audit log：raw 策略会"假装没发生过"，但失败痕迹必须写 audit log。fallback handler 永远不能跳过 audit write。
    • 

  • transform_persona 注入失败配 skip：会导致 event 以 fallback persona 走业务，可能跨租户串数据。务必 abort。
    • 



小结
transform_in / transform_out / transform_persona 三个 hook 把"中间改写 event"做成可组合、可观测、可演化的管线。链式调用通过显式顺序与三选一 fallback 策略保证可预测性。transform 本身的纯函数语义让它能被 GEPA 当成优化对象，让 Hermes 从"硬编码 transform"演进到"transform 也会自己变好"。下一篇看 OpenClaw 的 outbound webhook 模型如何为 Shell 层提供另一种 dispatch 方案。
