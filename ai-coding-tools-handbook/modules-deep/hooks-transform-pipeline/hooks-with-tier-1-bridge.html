与 Tier 1 Hooks 协同的跨 tier 桥接模式

核心概念

Hermes transform pipeline 与 OpenClaw outbound webhook 是 Tier 2 personal-agent 工具栈的事件机制；Claude Code 的 Hook（SessionStart / PreToolUse / Stop 等）是 Tier 1 工具栈的事件机制。两者各自独立运行，但通过 stdin/stdout JSON-RPC 与 HTTP webhook 这两条标准通道可以互相调用，形成跨 tier 编排。本篇讲两条核心桥接模式：(A) Hermes Plugin 内 spawn Claude Code subprocess 把 hook stdout 当 transform 输入——让 Tier 2 借用 Tier 1 的 Claude 推理能力；(B) OpenClaw webhook 作 Claude Code Stop hook 的 SOP enforcement 后端——让 Tier 2 的合规决策能反向 block Tier 1 agent stop。两条模式覆盖了 95% 跨 tier 协同需求，剩余的 5% 走通用 ../../../03_bridges/。

模式 A：Hermes Plugin spawn Claude Code
Hermes Plugin 在业务处理过程中可能需要"问一下 Claude 该怎么办"——例如 curator 看见某 skill 上次失败的 trajectory，想让 Claude 反思失败原因。Plugin 不直接调 Anthropic API（避免 secret 在 plugin 层暴露），而是 spawn 一个 Claude Code subprocess，把问题塞 stdin，等待 stdout 返回：


实现示例：


def curator_evaluate_trajectory(plugin_ctx, trajectory):
    proc = subprocess.run(
        ["claude", "-p", "--output-format", "json"],
        input=json.dumps({"trajectory": trajectory}),
        capture_output=True,
        timeout=60,
    )
    assessment = json.loads(proc.stdout)
    plugin_ctx.emit(InternalEvent(
        event_type="trajectory_assessed",
        payload=assessment,
    ))

depth=0 限制就是为了避免 ../3_mcp-bidirectional/4_anti-recursion-and-orchestration.md 里描述的循环——subprocess 内若再回调 Hermes 会形成 trace_id 重复。


hook stdout 作 transform 输入
更精巧的用法是：spawn 的 Claude Code 配置自定义 hook，hook 的 stdout 不是给 CC agent 看的 context，而是直接给 plugin 当 transform 输入。这样 plugin 等于借用了 Tier 1 hook 的可插拔机制：


举例：plugin 想从 spawn 出的 CC 那里得到"当前项目的最新 git status"。它把 SessionStart hook 配置成 git status --porcelain，hook stdout 直接被 plugin 接住作为 fact source，无需让 Claude agent 自己跑 bash。这种"绕开 agent loop 借用 hook"模式可以把跨 tier 调用延迟从分钟级压到秒级。


模式 B：OpenClaw webhook 作 Stop hook 后端
第二条模式方向相反——Tier 1 Claude Code agent 想结束工作时（Stop hook 触发），需要 Tier 2 OpenClaw 判定"SOP 还没走完，不允许 stop"。这是合规与质量门禁的典型场景：


Stop hook 是 Claude Code 标准 hook，返回 exit code 2 + stderr 强制 agent 继续工作而不能 stop。配合 OpenClaw 的 outbound webhook，"agent 是否能停"的决策被外置到 Tier 2：


#!/usr/bin/env bash
# .claude/hooks/stop-sop-check.sh
payload=$(cat)
resp=$(curl -sS -X POST https://openclaw.local/sop/check \
  -H "Content-Type: application/json" \
  -H "X-Signature: $(sign "$payload")" \
  -d "$payload")
if echo "$resp" | jq -e '.allow == true' > /dev/null; then
  exit 0
else
  reason=$(echo "$resp" | jq -r '.reason')
  prompt=$(echo "$resp" | jq -r '.continue_prompt')
  echo "SOP check failed: $reason" >&2
  echo "$prompt" >&2
  exit 2
fi
OpenClaw 的判定逻辑可能涉及"该 persona 必须完成 audit-trail-write 才能 stop"或"还有未确认的 cross-tenant access 申请"——这种业务规则不应放进 CC hook 脚本，而由 OpenClaw 集中维护。

陷阱与常见问题
    

  • subprocess spawn 不设 timeout：CC subprocess 卡死可以拖垮 Hermes plugin 进程。timeout 必须显式。
    • 

  • trace_id 在跨 tier 边界丢失：每个边界点 (subprocess argv / webhook header) 都得显式透传。debug 痛苦多半源于此。
    • 

  • Stop hook 频繁返回 exit 2：如果 OpenClaw 一直拒绝 stop，agent 陷入"被强制继续"循环。OpenClaw 应在判定逻辑里加 max attempts，超过后允许 stop 并 raise alert。
    • 

  • subprocess 共用同一 working dir：多个 plugin 并发 spawn CC 容易抢占 tmp 文件。每次 spawn 用独立 tempdir。
    • 

  • webhook secret 全局共用：模式 B 用的 secret 应 per-OpenClaw-tenant 独立，不与 outbound webhook 通用 secret 复用。
    • 



小结
跨 tier 协同有两条简单可靠的模式：Hermes Plugin 通过 spawn Claude Code subprocess 借用 Tier 1 的推理 / hook 能力，OpenClaw 通过 webhook 作 Stop hook 后端实现合规与 SOP enforcement。trace_id 透传是两条模式的共同约束，timeout 与 depth=0 是防止跨 tier 循环的硬保险。本章四篇覆盖完 Hermes transform pipeline + OpenClaw outbound webhook + 两套机制的跨 tier 编排——下一章进入 multi-tenant 路由与 persona 隔离，看 OpenClaw 如何用 5 级 lookup + DM pairing 把"一个物理用户多个 persona"做成系统化产品。
