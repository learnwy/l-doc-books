OpenClaw outbound webhooks 与 HMAC 签名模型

核心概念

OpenClaw 的事件出站走 outbound webhooks——内部任何 persona 切换、消息路由、审计动作、租户生命周期变更，都会被序列化为 HTTP POST 推送到 admin 预先注册的 URL。这是 OpenClaw 与第三方系统（Hermes / 自建 n8n / Temporal / 内部 SIEM）集成的主要通道。webhook 模型在 Hermes 三子系统的 Shell 层有对应物，但 OpenClaw 把它做得更"productized"：声明式触发条件 / 标准 payload schema / 指数退避重试 / idempotency key 去重 / HMAC SHA-256 签名。配合 Hermes Gateway 订阅 OpenClaw webhook 这条路径，两个 personal-agent 工具栈就能在不直接耦合 internal API 的前提下做事件级联动。

触发条件清单
OpenClaw 不允许"任意 internal event 都 emit webhook"——这会让 admin 被海量噪音淹没。webhook 触发条件被限定在 4 个 event_type，每个都有明确语义：

audit_event 是唯一不限速的——合规相关事件必须保证送达。其他三类有 rate limit 的话，触发频次会先在 OpenClaw 内部聚合，超出窗口的合并为 batch event 一次性 push。

HMAC SHA-256 签名
接收端如何验证一条 POST 真来自 OpenClaw 而非伪造？OpenClaw 用 HMAC SHA-256 对 body 与 timestamp 一起签名，附在专属 header：


X-OpenClaw-Signature: t=1715670069,v1=4e8b...c2a1
X-OpenClaw-Event-Id: evt_oc_8a3c91
X-OpenClaw-Event-Type: persona_switch
签名材料是 f"{t}.{raw_body}"。验证步骤：


def verify(headers, raw_body, secret):
    sig_header = headers["X-OpenClaw-Signature"]
    parts = dict(p.split("=") for p in sig_header.split(","))
    t = parts["t"]
    v1 = parts["v1"]
    # 1. 时间窗（默认 5 min）防 replay
    if abs(now() - int(t)) > 300:
        raise ReplayAttack
    # 2. HMAC 验证
    expected = hmac.new(
        secret.encode(),
        f"{t}.{raw_body}".encode(),
        hashlib.sha256
    ).hexdigest()
    # 3. 常时比较防 timing attack
    if not hmac.compare_digest(expected, v1):
        raise SignatureInvalid
    return True
secret 通过 OpenClaw admin UI 注册，per-tenant 独立。轮换 secret 时支持 grace period——新旧 secret 同时有效 24 小时让接收端平滑切换。

at-least-once 意味着接收端必须实现幂等。OpenClaw 提供 idempotency_key 字段让接收端在自家 db 用 unique index 拒绝重复处理。典型实现：


def receive(payload):
    if db.exists("webhook_dedup", key=payload["idempotency_key"]):
        return "200 already processed"
    db.insert("webhook_dedup", key=payload["idempotency_key"])
    process(payload)
    return "200 ok"

桥接后，OpenClaw 的 persona 切换可以触发 Hermes 调整 memory 视图，OpenClaw 的 audit_event 可以让 Hermes 的 skill_manage 自动 disable 风险 skill——两个工具栈在不直接共享 internal API 的前提下达到事件级联动。


陷阱与常见问题
    

  • 接收端不校 timestamp 仅校 HMAC：攻击者抓取一次合法 POST 后无限 replay。timestamp window 必须强制。
    • 

  • idempotency_key 用 event_id：两者不一定相同——event_id 是 OpenClaw 内部 ID，idempotency_key 是 delivery-level 标识，retry 时 event_id 不变但 idempotency_key 保持一致即可。
    • 

  • DLQ 不监控：消息进 DLQ 但 admin 没告警，故障静默累积。OpenClaw 提供 dlq_alert_webhook 二级配置，DLQ 累积超阈值时单独 push。
    • 

  • 接收端 5xx 但 OpenClaw 收到 2xx：例如反向代理把 5xx 改写为 200。务必让 webhook 端点直连，不经反代或确保反代透传状态码。
    • 

  • secret 写进 git：webhook secret 必须用 keychain / vault 保存，不能进版本控制。OpenClaw 推荐 1Password CLI / macOS Keychain。
    • 



小结
OpenClaw 的 outbound webhook 模型用"声明式触发 + 标准 schema + HMAC 签名 + 指数退避重试 + idempotency key"五件套，把"OpenClaw → 外部系统"的事件流量做成生产可用的协议。HMAC + timestamp 双重防御让伪造和 replay 都被堵死，at-least-once + idempotency 让接收端可以放心实现"宁可重收也不丢"的语义。和 Hermes Gateway 的 HTTP listener 配合，两个 personal-agent 工具栈可以在没有 internal API 耦合的前提下做事件级联动。下一篇看 transform pipeline 如何与 Tier 1 Hook 协作出更强力的工作流。
