Hermes Gateway / Plugin / Shell 三子系统

核心概念

Hermes runtime 在进程内部把事件流分成三个职责明确的子系统：Gateway 处理入口（把异构 protocol 统一成内部 event）、Plugin 处理业务（每个 module 订阅 event 并 transform）、Shell 处理出口（把内部 event 落到外部副作用）。这种切分对应 personal-agent 工具栈最常被踩坑的三类问题：协议混乱、业务耦合、副作用难审计。Tier 1 的 Hook 只在"已经在 Claude Code 进程里"的前提下做 PreToolUse / PostToolUse 触发，而 Hermes 三子系统是一个多协议入口 + 多 plugin 业务 + 多出口 dispatch 的事件 broker——同一个 inbound 消息可以扇入 N 个 plugin，同一个内部事件可以扇出 N 个 shell sink。

Gateway：协议归一化层
Gateway 不写业务逻辑——它只做三件事：listen / parse / normalize。Hermes 当前内置三类 listener：


[gateway.listeners]
stdio = { enabled = true, protocol = "jsonrpc-2.0" }
http  = { enabled = true, port = 7821, path = "/webhook" }
chat  = { enabled = true, platforms = ["lark", "slack", "discord"] }
每个 listener 输出统一的 InternalEvent：


{
  "event_id": "evt_8a3c91",
  "event_type": "message_received",
  "source": { "kind": "chat", "platform": "lark", "channel_id": "oc_abc" },
  "actor": { "kind": "user", "id": "ou_xyz" },
  "payload": { "text": "整理今天的会议", "ts": 1715670000 },
  "trace_id": "trc_4f2e"
}
Gateway 还负责 trace_id 注入与 inbound rate-limit。任何 Plugin 看到的 event 都已经被归一化过，无需关心来源协议是 stdio 还是 chat。这一层的设计准则是"瘦"——Gateway 代码尽量不引入业务依赖，方便单测覆盖。


Plugin：业务 transform 层
Plugin 是 Hermes 中最厚的一层。每个 plugin 注册自己关心的 event_type，runtime 把 event 按订阅关系扇入：


Plugin 之间通过 event bus 而非直接函数调用通信——这避免了 plugin 间硬耦合，并让 GEPA 可以单独 swap 一个 plugin 的实现而不影响其他。

Plugin 内部典型骨架：


class MemoryPlugin(HermesPlugin):
    subscriptions = ["message_received", "session_start"]

    def handle(self, evt: InternalEvent) -> list[InternalEvent]:
        hits = self.memory_query(evt.payload["text"])
        enriched = evt.with_context({"memory_hits": hits})
        return [enriched]
handle 返回一组新 event——可以是原 event 的 enriched 版本，也可以派生新 event 类型（如 memory_enriched），后者再被其他 plugin 订阅。


Shell：副作用 dispatch 层
Shell 反过来——它不做业务，只把 plugin 处理完的 event 翻译成具体外部副作用。当前 Hermes 内置四类 sink：

Shell 是唯一允许 IO 副作用的位置——Plugin 不能直接写文件或发请求，必须 emit file_write / external_call 事件让 Shell 执行。这种约束让 audit log 单点化（详见 ../5_multi-tenant-personas/3_per-tenant-key-and-audit.md）：要审计 Hermes 对外做了什么，只看 Shell 日志即可。

Plugin 想要"读文件"必须通过 emit fs_read_request event 让 Shell 异步读，结果再回 Plugin。这种受限通信看似繁琐，但收益是任意 plugin 都不会成为安全漏洞 surface——secret 只暴露给 Shell，Plugin 永远拿不到原始凭证。

差异在于：Tier 1 Hook 是"嵌入 Claude Code 单进程"的同步阻塞模型，Hermes 三子系统是"独立 broker 进程"的异步事件模型。前者擅长"卡在工具调用关键点做检查"，后者擅长"接受多协议 inbound + 协调多 plugin 业务 + dispatch 多 sink"。具体如何让两套机制协作详见 ./4_hooks-with-tier-1-bridge.md。


陷阱与常见问题
    

  • 把业务逻辑写进 Gateway：例如在 Gateway 里直接做 memory_query，导致协议层与业务耦合，无法单测。正确做法是 Gateway 仅归一化，Plugin 处理业务。
    • 

  • Plugin 直接调 fs / network：绕过 Shell 会让 audit log 不全。新 plugin code review 第一条检查项就是"有没有任何 fs / network 直接调用"。
    • 

  • Shell 内做条件分支业务：例如 Shell 写文件前判断 importance score——这种业务条件应在 Plugin emit 时决定。Shell 只做"无条件 dispatch"。
    • 

  • event bus 形成环：Plugin A emit 触发 Plugin B emit 又回到 A，无限循环。Hermes 在 event 元数据里维护 causation_chain，链长超 5 直接 reject。
    • 

  • Plugin 内 hold mutable global state：plugin 自带状态可以，但应只在 plugin 内部 scope；跨 plugin 共享状态走 event bus 而非 module-level 变量。
    • 



小结
Gateway / Plugin / Shell 三子系统不是 Hermes 偶然的代码分层，而是"协议归一化 + 业务 transform + 副作用 dispatch"三个工程关注点的物理隔离。Gateway 让 Hermes 能接入任意 inbound protocol 而不污染业务，Plugin 让业务逻辑可独立演进与 GEPA 优化，Shell 让所有副作用单点 audit。Tier 1 的 Hook 是"在单进程内插桩"，Hermes 三子系统是"做一个真正的事件 broker"——理解这个差异是看懂 Hermes runtime 的关键。下一篇深入 transform_* 系列 hook 的链式调用语义。
