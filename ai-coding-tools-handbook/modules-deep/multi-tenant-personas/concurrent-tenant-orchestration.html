并发多租户编排与资源调度

核心概念

OpenClaw runtime 在单进程内同时承载多个 active persona——dev_oss 在和 GitHub issue 互动、dev_bytedance 在处理飞书消息、hobby_writing 在跑定时写作脚本，三者并行。要让这些 persona 平稳共存，OpenClaw 引入资源 quota + 消息队列优先级 + 跨 persona event 显式转发三件套：每 persona 有 CPU / memory / outbound quota 上限避免互相吃光资源；message 队列按 persona 配置 high / normal / low 优先级让重要 persona 不被低优 persona 阻塞；跨 persona 通信必须用户显式 /share-event 命令触发，杜绝 implicit 数据流泄漏。本篇按"调度模型 / quota 算法 / 队列优先级 / 跨 persona 通信 / 超限处理"五块讲。

调度模型：fair-share scheduler
OpenClaw 用 weighted fair-share 而非 strict round-robin。每 persona 有 weight，调度器按 weight 比例分配 CPU 时间片：


def select_next_persona(personas, history):
    # 累计 deficit：weight 期望与实际执行的差距
    deficits = {p: p.weight * total_ticks - history[p] for p in personas}
    return max(deficits, key=deficits.get)

实际占比受真实工作量影响——空闲 persona 不占片，权重让给忙的。这避免"高 weight persona 空闲时间片浪费"的问题。


CPU / memory quota 执行
quota 不是软建议，是硬约束。CPU 用 cgroup（Linux）/ macOS 的 Task Policy / Windows Job Object 实现；memory 用 RSS 监控 + 超限触发 graceful degrade 或 hard kill：

强 kill 是最后手段，因为它可能丢未持久化状态。OpenClaw 的 plugin 框架要求所有状态在每次 event 处理后 flush 到 fs，让强 kill 损失最小。

queue_depth 是 inbound buffer 上限——超过时新消息直接 reject（带 retry-after header 让 chat 平台稍后重发）。


跨 persona event 转发
OpenClaw 强制：persona 之间不能 implicit 共享 event。任何"把 persona A 收到的消息给 persona B 看"的需求必须由用户显式触发：


/share-event 命令的 payload 会标 provenance: shared_from=dev_oss，让接收 persona 知道这条信息不是它"原生"上下文。这种显式机制避免两个 persona 的 memory 互相串数据。

quota 超限的三种处置策略
quota 超限时不是统一行为——admin 可以按 quota 类型配置 degrade / reject / queue 三选一：






策略
行为
适用场景





degrade
降级到精简流程（不走 GEPA、不写 memory）
一过性高负载




reject
直接拒绝新 event，返回 429
严格 quota




queue
写入 overflow buffer，恢复后处理

quota_policy:
  cpu_exceed: degrade
  memory_exceed: reject
  outbound_rps_exceed: queue
  inbound_queue_full: reject
每种 quota 类型最适合的策略不同——memory 超限继续 degrade 风险大（OOM kill），所以 reject；outbound 限流通常对端会重试，queue 兜底即可。


telemetry 与 admin 视图
admin 通过 openclaw status 看实时 quota 使用：

Tier 1 适合"一次一件事"的开发场景，Tier 2 multi-tenant 适合"多 persona 同时活跃"的 24/7 personal assistant 场景。两者互补而非互替。


陷阱与常见问题
    

  • persona weight 全设一样：失去 fair-share 意义，退化为 round-robin。重要 persona 应给 weight > 1。
    • 

  • memory hard cap 设太低：512MB 对带 embedding 的 plugin 容易触发 hard kill。建议 plugin 不在内存维护大状态。
    • 

  • /share-event 滥用：每条消息都 share，等于多 persona 共享 memory。该机制是 exception path 而非 daily flow。
    • 

  • quota_exceed 用 degrade 而不审计：degrade 可能让用户感知不到的输出质量下降。admin 应配合 audit_event 告警。
    • 

  • inbound queue full reject 不带 retry-after：chat 平台不知道何时重试，会立即重发雪崩。reject 响应必须带 retry-after header。
    • 

  • 跨平台 outbound rps 共享 quota：lark + Slack 两条 outbound 都吃同一 quota，可能误以为"每个平台独立"。配置层应明确 quota 是否 per-platform。
    • 



小结
并发多租户编排靠"weighted fair-share + per-persona quota + priority queue + 显式 share-event"四件套保证多 persona 能在单进程内安全共存。quota 超限的三种处置策略（degrade / reject / queue）让 admin 按业务特性匹配资源行为。跨 persona event 必须用户显式触发——这是 OpenClaw 在并发场景下守住 multi-tenant 隔离边界的最后一道防线。本章五篇覆盖完 OpenClaw 多租户协议——本 hub 的两个 Tier 2 工具栈差异主题（Hermes 记忆 + skill 自演化 + transform pipeline，OpenClaw multi-tenant + outbound webhook）至此全部展开。跨 tier 编排选型走 ../../../03_bridges/。
