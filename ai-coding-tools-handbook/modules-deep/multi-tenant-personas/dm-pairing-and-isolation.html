DM pairing 与 persona 隔离工作空间

核心概念

5 级路由 lookup 解决"消息进来该归哪个 persona"的决策，但落到 DM（私聊）场景还有额外细节——DM 没有"频道角色"概念，路由必须靠"和谁聊"。OpenClaw 把这层做成显式的 DM pairing：每个 persona 绑定到一组对端用户，binding 是双向显式的，不允许隐式 fallback。pairing 建立后，OpenClaw 同时为该 persona 创建一个隔离工作空间：filesystem 路径独立、memory 索引独立、scheduled task 独立、skill 列表独立。本篇分两块讲：DM pairing 的 API 与跨平台一致性，以及 isolation 的具体边界（fs / db / process）。

DM pairing

DM pairing 的 API
openclaw dm 子命令管理 pairing。绑定与解绑都是 idempotent 操作：


# 把 persona 绑定到一个 DM 对端
openclaw dm bind dev_oss --platform discord --peer-id uxxx_bob

# 解绑
openclaw dm unbind dev_oss --platform discord --peer-id uxxx_bob

# 列出 persona 的所有 pair
openclaw dm list --persona dev_oss

# 查询某 peer 当前绑定到哪个 persona
openclaw dm whois --platform slack --peer-id u12345




命令
行为





bind
创建 pair，若已存在覆盖




unbind
删除 pair，找不到时静默成功




list
列出 persona 所有 active pair




whois
反向查询





binding 写入 ~/.learnwy/openclaw/pairings.json 与 audit log 双份。这文件被 backup 工具默认包含，迁移设备时 pairing 跟随。


跨平台 DM 一致性
OpenClaw 的设计目标之一是"persona 是用户的，不是 channel 的"——同一个 persona 在飞书与 Slack 应保持一致体验。如果用户在飞书私聊里跟 Alice 用 dev_bytedance，跨到 Slack 私聊跟 Alice（同一个人，不同账号）也应该是 dev_bytedance：


实现层走"identity bridge"——OpenClaw 维护一张身份联邦表把 Slack uid_alice_slack 与飞书 ou_alice_lark 关联到同一 logical peer peer_alice。pair 写在 logical peer 上而非 platform-specific uid 上：


identity_bridges:
  - logical_peer_id: 'peer_alice'
    platform_ids:
      lark: 'ou_alice_lark'
      slack: 'uid_alice_slack'
      discord: 'uxxx_alice_discord'
bridge 表的维护可以手动也可以半自动——OpenClaw 提供 dm suggest-bridge 命令根据"两个 peer 在两个平台同时被 pair 到同一 persona"自动推断身份关联。


隔离工作空间
DM pairing 命中后，OpenClaw 把对话引流进对应 persona 的隔离工作空间。隔离边界覆盖四个维度：






维度
隔离实现





Filesystem
~/.learnwy/openclaw/personas/<persona>/ 独立子树




Memory
MEMORY.md per-persona，互不可见




Skill
skill registry per-persona 加载




Schedule
scheduled task 列表 per-persona





文件系统级隔离意味着 persona A 的进程在文件 IO 时直接被 chroot / sandbox-exec / namespace 限制访问范围。运行时实现层因平台而异：






OS
沙盒机制





macOS
sandbox-exec profile per-persona




Linux
unshare + bind mount




Windows
Job Object + AppContainer（实验性）





沙盒不是"软隔离"——它是 OS-level 的硬约束。persona A 的代码即便有 bug 想读 persona B 的 ~/.learnwy/openclaw/personas/dev_bytedance/MEMORY.md，OS 层 EACCES 直接拒绝。


数据隔离边界
文件级隔离不够——某些资源是共享 db 行（如统一 audit log）。这种共享资源用 db row-level 隔离：


-- audit_log 表所有 persona 共享 schema，但行级 ACL
CREATE TABLE audit_log (
  id BIGSERIAL,
  persona_id TEXT NOT NULL,
  event_type TEXT,
  payload JSONB,
  ts TIMESTAMPTZ
);

-- per-persona view 强制 persona_id filter
CREATE VIEW audit_log_dev_oss AS
  SELECT * FROM audit_log WHERE persona_id = 'dev_oss';
实施上 row-level 用 PostgreSQL RLS（Row Level Security）policy + per-persona db role。即便绕过 ORM 直连数据库，RLS policy 也会自动过滤。


persona 切换与 session
用户主动切换 persona（例如在终端跑 openclaw persona switch dev_oss）时，OpenClaw 做几件事：






步骤
持续时间（典型）





flush current state
<100ms




load new workspace
200-500ms（含 MEMORY.md 重读）




skill registry re-init
100-300ms




webhook emit
异步，不阻塞切换





切换不是"重启进程"——OpenClaw runtime 进程内部维护多 persona context，switch 只改 active pointer。这让切换开销控制在亚秒级。


陷阱与常见问题
    

  • DM pair 后未配 identity_bridge：用户跨平台切换时 pair 不生效，因为 OpenClaw 把 Slack uid 与 lark open_id 视为不同 peer。务必同时配 bridge。
    • 

  • 隔离工作空间下 git config 全局共享：注意 ~/.gitconfig 仍是全局的。如果 dev_oss 与 dev_bytedance 需要不同 commit author，需 per-persona override 用 git -c user.email=...。
    • 

  • persona 切换后旧 session 仍在前台：长 running task（例如正在生成的回复）不会因 switch 而中止。要中止须显式 openclaw persona kill <old>。
    • 

  • shared audit log RLS bypass：admin 用 superuser 直连 db 可绕过 RLS。审计动作应仅通过 OpenClaw API，不直连 db。
    • 

  • identity_bridge 错误关联：把不同人误关联会导致跨人数据泄漏。bridge 变更应进 audit log 并要求 admin 二次确认。
    • 

  • sandbox profile drift：升级 OpenClaw 后 sandbox profile 模板可能变，旧 persona 文件夹的 profile 没自动更新。每次升级跑一次 openclaw persona resync-sandbox。
    • 



小结
DM pairing 把"persona 与对端人的绑定"从 5 级路由的隐式 fallback 提升为显式声明，避免私聊场景的不可预测路由。跨平台 identity_bridge 让"persona 是用户的，不是 channel 的"成立。隔离工作空间走 OS-level sandbox（fs / process）+ db row-level（RLS）双重保险，让一个进程内多 persona 仍互相隔离。下一篇深入 per-tenant 安全：每 persona 独立的 secret store、horizontal access 拒绝、与企业 compliance 的接入。
