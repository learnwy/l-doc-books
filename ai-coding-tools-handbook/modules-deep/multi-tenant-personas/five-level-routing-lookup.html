OpenClaw 路由 5 级 lookup 详解

核心概念

OpenClaw 的核心差异化能力是同一物理用户可绑定多个 persona，每个 persona 看到自己的隔离世界。把一条 inbound 消息映射到正确 persona 的过程被实现为 5 级有序 lookup：peer → parent → guild/roles → account → channel → fallback。lookup 按这个顺序逐级匹配，"earlier wins"——越具体的规则优先级越高。这种设计的好处是 admin 只需要给少数特殊情况写显式规则，大部分流量由更粗粒度的 channel / account fallback 兜底。本篇按"为什么是 5 级、每级语义、命中优先级、规则 DSL"四块讲清，DM pairing 与 isolation 细节走 ./2_dm-pairing-and-isolation.md。

第 1 级：peer 点对点路由
peer rule 写"和某个具体用户 1:1 沟通时用某 persona"。它最具体，所以优先级最高。例子：用户在飞书私聊里 1:1 跟同事 Alice 沟通时永远用 dev_bytedance persona，跟开源社区贡献者 Bob 沟通时永远用 dev_oss persona——不管这两个 DM channel 在哪个 channel id 下。


peer_rules:
  - peer_id: 'ou_alice_xxx'
    persona: 'dev_bytedance'
    reason: '同事工作沟通'
  - peer_id: 'uxxx_bob_oss'
    persona: 'dev_oss'
    reason: '开源贡献者'
peer 规则数量通常少（5-20），因为人不会和无限多人有"绝对 persona 绑定"。这一级的命中场景集中在"长期工作关系 + 工作私聊"。


第 2 级：parent 父群继承
OpenClaw 把群组关系建模为可嵌套的 parent-child tree。父群有规则时，子群自动继承——除非子群有自己的更具体规则。这一级解决"团队 workspace 下有多个项目 channel，希望统一 persona 但不想每 channel 写一遍"的痛点：


parent_rules:
  - parent_id: 'workspace_bytedance'
    persona: 'dev_bytedance'
    inherit_to_children: true
  - parent_id: 'workspace_oss_lynx'
    persona: 'dev_oss'
    inherit_to_children: true
子 channel 上若有显式 channel rule 会覆盖 parent rule——只是父子级别上 parent 在 lookup 优先级里靠前，是因为它通常是 admin 显式声明的"团队级"决定。


第 3 级：guild/roles 角色组
guild 与 roles 是平台原生概念（Discord 称 role，Slack 称 user group，飞书称群角色）。规则按角色匹配——只要消息发送者在某角色组里就触发：


role_rules:
  - role_id: 'moderator'
    persona: 'ops_admin'
    reason: 'moderator 行为需要 ops 上下文'
  - role_id: 'external_contractor'
    persona: 'dev_external_safe'
    reason: '外部合作者用受限 persona'
这一级适合"按角色而非具体人"的策略。例如把"所有 moderator 的请求"路由到 ops_admin persona——admin 不必维护谁是 moderator 名单，平台自身的角色变更会自动反映到路由。


第 4 级：account 账号级 fallback
account 规则按"消息所在平台账号"匹配。这是个比较粗的兜底层，通常一个 platform 一条规则：


account_rules:
  - account_id: 'lark_account_self'
    persona: 'personal_default'
  - account_id: 'slack_workspace_oss'
    persona: 'dev_oss'
它的作用是"如果这个平台账号本身就属于某 persona（如 OSS 专用 Slack workspace），所有未被前 3 级匹配的消息都默认归到该 persona"。


第 5 级：channel 频道默认
channel rule 是数量最多的一级（50-200）。它写"某个具体 channel 默认归哪个 persona"。这一级排在 account 之后是有意为之——同一 account 下的不同 channel 通常归同一 persona，account 规则可以一次性兜底，channel rule 只写少数异常 channel：


channel_rules:
  - channel_id: 'lark_oc_abc'
    persona: 'hobby_writing'
    reason: '写作社群'
  - channel_id: 'slack_C12345'
    persona: 'dev_oss'
    reason: 'Lynx framework channel'
第 6 级：fallback 全局兜底
最后一级是单一 fallback persona。没有任何级别命中时，消息归到这里。fallback 通常是 personal_default——最受限制、最少权限的 persona：


fallback:
  persona: 'personal_default'
  warn_on_use: true
  audit_event_type: 'fallback_routing'
warn_on_use: true 表示每次 fallback 命中都 emit 一条 audit_event，提醒 admin 检查"是不是有漏写规则"。


命中优先级与冲突
规则 lookup 严格按 1-6 顺序，earlier wins：






冲突类型
处理

按 rule 内 priority 字段决定（默认按声明顺序）




跨级别多条匹配
level 数字小者优先




完全冲突（应平局）
OpenClaw 启动时静态检测，admin 必须显式排序





启动时的冲突检测是关键保护——避免运行时不可预测的路由行为。规则文件改动后 OpenClaw 会 dry-run 一遍所有规则组合，检测到歧义就拒绝 reload。


缺省行为与 routing rule DSL
规则用一种小型 DSL 表达：


peer_rules:
  - match:
      peer_id: 'ou_alice_*'
      platform: 'lark'
    persona: 'dev_bytedance'
    priority: 10
    audit: true




DSL 字段
作用





match
匹配条件，支持 glob / regex




persona
命中后的 persona




priority
同级多条时的次序




audit
是否 emit audit_event




valid_until
规则有效期，过期自动失效





valid_until 让"临时 persona 绑定"成为可能：例如"这周与外部审计 Bob 的所有消息走 audit_persona，下周自动恢复"。


陷阱与常见问题
    

  • 以为 lookup 是"先到先得"：实际是"按 5 级严格排序"。即便 channel rule 先写，peer rule 后写，命中时 peer 仍优先。
    • 

  • parent rule 没声明 inherit_to_children：默认 false，admin 经常误以为有继承。明确写 true。
    • 

  • role_id 在不同平台 ID 重名：飞书 vs Slack 的 moderator role id 完全不同。规则的 role_id 应带 platform 前缀。
    • 

  • fallback 用 admin persona：极度危险——任何漏写规则都让消息以 admin 权限处理。fallback 必须是最受限 persona。
    • 

  • valid_until 过期前未告警：rule 静默过期，admin 不知。OpenClaw 提供"过期前 24h 告警"配置。
    • 

  • 同级 priority 全为 default：多条 peer rule 都按声明顺序，但 rule 文件被 git merge 后顺序可能变。重要规则必须显式 priority。
    • 



小结
OpenClaw 的 5 级 lookup（peer → parent → guild/roles → account → channel → fallback）是 multi-tenant 工具栈的核心路由协议。"earlier wins"让 admin 只需写少量具体规则覆盖特例，粗粒度规则兜底大部分流量。规则文件改动后的启动期冲突检测、valid_until 临时绑定、audit_event emit on fallback——这三处工程细节让 5 级 lookup 在实际部署里既灵活又可审计。下一篇讲 DM pairing 模型与 persona 之间的隔离边界，看路由命中后 persona 如何真正生效。
