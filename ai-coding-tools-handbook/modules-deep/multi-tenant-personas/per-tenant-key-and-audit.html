Per-tenant 密钥隔离与审计日志 schema

核心概念

multi-tenant 不只是工作空间隔离，还包括安全凭证隔离与审计可追溯。OpenClaw 把这两个能力做成系统化机制：per-tenant secret store 让每个 persona 持有独立 API key / token / OAuth credential，跨 persona 读取被 OS 与应用层双重拒绝；统一 audit log 记录所有跨 persona 访问尝试、secret 取用、合规相关动作，schema 设计支持 SOC2 evidence 提取、GDPR right-to-be-forgotten 删除、HIPAA partition。本篇按"secret store 实现"、"horizontal access 拒绝路径"、"audit log schema 与 cause chain"、"企业合规接入"四块讲。前置阅读：./2_dm-pairing-and-isolation.md 的 isolated workspace 部分。

写入 secret 通过 openclaw secret 命令，never via plain config file edit：


openclaw secret set --persona dev_oss \
  --key github_token --value "ghp_xxx"

openclaw secret get --persona dev_oss --key github_token
openclaw secret list --persona dev_oss
openclaw secret rotate --persona dev_oss --key github_token
rotate 是关键操作——它生成新 secret、更新外部服务、保留旧 secret 在 grace period 内可读，然后切换。这套流程让 secret 轮换不停服。


horizontal access 拒绝路径
跨 persona 读 secret 应当被双重拒绝——OS 层与应用层各拦一道：


应用层检查的逻辑：


def secret_get(req_persona, key, *, ctx):
    if ctx.active_persona != req_persona:
        audit.emit(
            event_type="cross_persona_attempt",
            actor=ctx.active_persona,
            target=req_persona,
            key=key,
            outcome="denied",
        )
        raise CrossPersonaAccessDenied
    return store.read(req_persona, key)
任何 cross_persona_attempt 都被记录——即便最终允许（admin override），痕迹保留。这是"零信任 + 全审计"在 OpenClaw 的体现。

cause_chain 是 OpenClaw audit 的独到设计——单条 audit 记录不只说"发生了什么"，还说"为什么发生"。这让审计员能从一条可疑动作上溯追因。


合规接入：SOC2 / GDPR / HIPAA
OpenClaw 的 compliance 子系统针对三种主流合规体系各做了 export profile：

Tier 1 不是不能做合规，而是依赖用户自建脚本/外部 SIEM 兜底。OpenClaw 把这套机制内置化，省掉每个用户重新发明的工作。


陷阱与常见问题
    

  • secret 写入 settings/config 文件：永远走 openclaw secret set，不要让 secret 出现在任何明文 yaml/json。配合 git pre-commit hook 防止误提交。
    • 

  • rotate 没设 grace period：旧 secret 立即作废 + 新 secret 还没通知到外部服务 = 一段空窗期 service down。grace 时间应根据服务通知延迟设置（典型 24h）。
    • 

  • audit log cause_chain 缺失：某些 fast-path 代码绕过 emit。code review 必须检查"任何 secret_access / cross_persona / data_export"路径都 emit。
    • 

  • deletion_certificate 未保留：误以为"删除就完全消失"。GDPR 也要求保留删除证明，certificate 必须留。
    • 

  • compliance_tags 写错对应 control 编号：SOC2 control 编号变动时需要全表更新映射。compliance engine 启动期校验 tag 词表。
    • 

  • OPS 用 root 直读 fs：绕过沙盒。生产环境应禁止任何人有 sudo 进入 persona 目录，或所有 sudo 操作必须自动写 audit。
    • 



小结
per-tenant secret store + horizontal access 双重拒绝 + 统一 audit log w/ cause chain + 三种合规 export profile——这四件套让 OpenClaw 把"个人版 multi-tenant"做出企业级合规可证可审的水准。secret 隔离不依赖应用层善意，OS-level sandbox 是底线；audit log 的 cause_chain 让事后追责能从一条可疑动作上溯到最初触发；compliance engine 的三种 profile 让 SOC2 / GDPR / HIPAA 不必每次 hand-roll。下一篇看并发多租户的资源编排——多 persona 同时运行时如何调度、限流、防资源抢占。
