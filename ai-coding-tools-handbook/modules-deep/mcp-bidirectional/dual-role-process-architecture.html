Tier 2 · Personal Agents 工具栈Personal-agent 模块深度 简介MCP 双向调用 简介同进程双角色：server thread + client thread

同进程双角色：server thread + client thread

核心概念

hermes mcp serve 与 openclaw mcp serve 进程内部并不只是被动的 server——它们同时作 MCP client 调用 Tier 1 工具（Claude Code / Codex）协同完成复杂任务。例如 Hermes 自己跑 curator 时可能需要让 Claude Code 帮忙写一段代码评估 skill；OpenClaw message_route 中可能让 Codex 起草一个回复 draft 再由 OpenClaw 发出。这就形成"同进程既作 server 又作 client"的双角色架构。实现挑战：reentry-guard 防递归调用、resource isolation 防 server/client 互相阻塞、lifecycle 协调让 startup/shutdown 顺序正确。

server thread
Server thread 监 stdin，按 JSON-RPC framing 拆消息，dispatch 到 tool handler。它是 single reader——只有一个 thread 读 stdin，避免 partial-frame race。但 tool handler 跑在独立 thread pool 里，handler 间可以并行（除非同 tenant 同 tool 有锁）。


server thread pool 默认 8 worker。Tool handler 内部可以再调 client thread 触发 Tier 1 call——这条路径正是双角色的关键。


client thread
Client thread 不被外部触发，而被 server tool handler 内部 push task 触发。例如 Hermes 的 memory_query tool 在内部决定"FTS5 召回的 entries 需要 Claude Code 重新归纳"，会向 client 队列 push 一个 spawn-claude-code task。


def memory_query_handler(args):
    raw_entries = fts5.search(args.query)
    if args.get("rephrase"):
        # 调 client thread 让 Claude Code 处理
        rephrased = client_thread.invoke(
            "claude_code",
            args={"task": "rephrase", "input": raw_entries}
        )
        return rephrased
    return raw_entries
client thread 也用独立 thread pool（默认 4 worker），spawn 子进程 Claude Code，通过 stdio 与之通信，收 result 后回 server handler。


reentry guard
最大风险是无限递归——Claude Code 调 Hermes memory_query，Hermes 内部又调 Claude Code，Claude Code 又调 Hermes...


Reentry guard 在每个 server call 入口注入 X-Call-Chain header 追踪调用链：

内容

唯一标识本次跨进程链

"claude_code → hermes → claude_code" 字符串





进入第二层时 depth=1，进入第三层 depth=2。默认 max_depth=2——超过直接 reject：


{
  "error": {
    "code": -32603,
    "message": "reentry_guard: max_depth=2 exceeded",
    "data": {
      "chain": "claude_code → hermes → claude_code → hermes",
      "current_depth": 3
    }
  }
}
这条规则让"一层往返"完全允许（Claude Code → Hermes 拉 memory → 回到 Claude Code），但"两层以上嵌套"被拒绝。两层以上几乎必然是循环。


详细的"防递归 + 跨 tier 编排"模式在 ./4_anti-recursion-and-orchestration.md。


resource isolation
server thread pool 与 client thread pool 是独立 thread pool。这避免一个常见死锁：所有 worker 都被"server handler 等 client call 返回" block，而 client call 又需要 server pool 的 worker 处理 server-side state——server pool 满，新请求进不来，client 永远等不到。

注意"OOM 隔离否"——双 pool 同进程，单 worker 内存爆炸仍 OOM 整个进程。这是 OpenClaw 限制 client pool size = 4 的另一原因：减少同时 spawn 子进程的内存压力。

代价是耦合性高——server bug 可能拖垮 client 端 task。但 personal-agent 场景下"一台机器上一个用户"的简单性远超分进程隔离的好处。


陷阱与常见问题
    

  • server 阻塞导致 client 也阻塞：误以为双 pool 隔离万事大吉，实际 SQLite 锁是全进程共享。长 query 仍能拖慢全局。监控 SQLite busy 率。
    • 

  • reentry guard chain 没正确传：自己写的 client 没继承 X-Call-Chain header，触发误判。chain 传递必须显式 propagate。
    • 

  • client pool 满后 server handler 卡死：默认是 block，不是 error。看到 server response 时间陡升查 client pool queue 长度。
    • 

  • hot reload 后旧 in-flight 用新 registry：实际是用旧的（copy-on-write），但用户可能误以为热加载是全替换。说明文档要解释清楚。
    • 

  • Shutdown 30s 限制不够：极少数 skill_dispatch 启动了长任务（10 min），shutdown 直接 abort。需要 explicit cancellation token。
    • 



小结
双角色架构（server thread + client thread）让 hermes / openclaw 既能被 Tier 1 调用，又能反过来调用 Tier 1，从而实现"持久层 + 协议层 + 工具层三方协作"的复杂工作流。Reentry guard / resource isolation / lifecycle 三套机制让这种双向架构不会陷入递归或死锁。单进程双 pool 设计在简单性与隔离性之间取了 personal-agent 场景的最优解。下一篇深入跨 tier 编排范式与 anti-recursion 的具体工作流模板。
