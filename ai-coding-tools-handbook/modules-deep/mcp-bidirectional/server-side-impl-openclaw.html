openclaw mcp serve：multi-tenant 隔离的 server 实现

核心概念

openclaw mcp serve 与 Hermes 一样把自己的核心能力暴露为 MCP server，但承担一项 Hermes 不需要解决的额外复杂度：multi-tenant 隔离。OpenClaw 是为聊天平台代接而生——一个用户实例同时维护数个甚至数十个 chat-platform 通道（Slack / Discord / Lark / 自建 IM），每个通道独立一个 tenant，各有自己的 secret store / persona / 历史消息 / outbound webhook。Server 暴露的每个 tool 都要在调用时识别 tenant 上下文、在隔离边界里执行、把跨 tenant 数据泄漏防死。stdio-only 而非可选 HTTP 也是为了同样的理由——multi-tenant 加 HTTP 让 audience 校验复杂度爆炸。

四个核心 tool
persona_switch
切换当前活跃 persona。Persona 是 OpenClaw 把"角色 + 价值观 + 语气"打包的概念，与 SOUL.md 一对一。Input：


{
  "tenant_id": "tn_lark_team_a",
  "persona_id": "tech-lead",
  "ttl_minutes": 120
}
Output：


{
  "active_persona": "tech-lead",
  "tenant_id": "tn_lark_team_a",
  "expires_at": "2026-05-14T15:30:00Z",
  "soul_path": ".openclaw/personas/tech-lead/SOUL.md"
}
ttl 让"切换 persona 帮忙写一封正式邮件后自动切回"成为可能，避免 stale persona 污染后续消息。


message_route
把一条入站消息按 5 级 lookup 路由到合适的 persona + skill。这是 OpenClaw 最核心的工作 unit。Input：


{
  "tenant_id": "tn_lark_team_a",
  "from": "u_3ab8",
  "channel": "ch_proj_alpha",
  "content": "周报怎么填本周 OKR 进度?",
  "thread_id": "t_91f"
}
Output：


{
  "routed_to": {
    "persona": "tech-lead",
    "skill": "weekly-report-base-to-doc",
    "lookup_path": ["thread", "channel", "tenant"],
    "matched_level": "channel"
  },
  "invocation_id": "inv_22de"
}
lookup_path 字段展示 OpenClaw 5 级路由经过了哪些层级（peer → parent → guild/roles → account → channel → fallback）才命中。5 级路由细节见 ../5_multi-tenant-personas/。


tenant_list
列出当前用户所有 tenant 的元数据。Input：


{ "filter": { "platform": "lark" } }
Output：


{
  "tenants": [
    {
      "tenant_id": "tn_lark_team_a",
      "platform": "lark",
      "display_name": "Team A 飞书",
      "channel_count": 14,
      "last_active": "2026-05-14T11:23:00Z"
    }
  ]
}
提供给 client 的目的是让 client（如 Claude Code）能问"我现在有哪些 tenant 在线"，从而做 cross-tenant 协调时显式列出。注意 output 不包含任何 secret——secret 是 server-side opaque。


channel_send
把一条消息从 OpenClaw 经指定 tenant 发到指定 channel。Input：


{
  "tenant_id": "tn_lark_team_a",
  "channel": "ch_proj_alpha",
  "content_type": "text",
  "content": "本周周报已生成,详见: <link>",
  "persona": "tech-lead"
}
Output：


{
  "message_id": "msg_8a4e",
  "status": "sent",
  "delivered_at": "2026-05-14T13:30:14Z",
  "audit_log_id": "alog_7f9d"
}
每次 send 都生成 audit_log_id 进合规日志，包含 tenant / persona / channel / content_hash / sender_chain。后续可按 audit_log_id 查整条消息的来龙去脉。


multi-tenant 隔离的 server 端实现
per-tenant secret store
每个 tenant 的 platform API token 加密存储在独立 keystore 条目：


Keystore 默认用 OS 原生 secure storage（Keychain on macOS / Secret Service on Linux / DPAPI on Windows）。Server 进程在启动时不解密所有 secret——按需 decrypt，使用完毕立即从内存抹除（zeroize）。


def call_with_tenant(tool, args):
    tenant_id = args.pop("tenant_id")
    secret = keystore.decrypt(tenant_id)  # 临时持有
    try:
        return tool.execute(secret, args)
    finally:
        secret.zeroize()  # 立即清内存
这种"短暂持有 + 立即清除"策略让"server 进程 memory dump 一次最多泄漏当前正在用的一个 tenant"，而不是所有 tenant。


audit log
每个 tool call 都写一条 audit log，schema：






字段
内容





log_id
UUID




tenant_id
对应 tenant




tool_name
调用的 tool




input_hash
input args 的 SHA256（不存原文）




outcome
success / failure / partial




sender_chain
触发链（client → server → platform）




duration_ms
延时




timestamp
UTC





audit log 写 append-only file（默认 ~/.openclaw/audit/<tenant>/YYYY-MM-DD.ndjson），加上 HMAC chain 防篡改——每条 log 的 hmac 包含前一条 hmac，整条 chain 中间被改会断链。


防跨 tenant 泄漏
最常见的泄漏路径是 server 内部 tool 调用时把 tenant_a 的 context 错传给 tenant_b。OpenClaw 的防御：






防御层
实现





类型系统
TenantId 是 nominal type，不能与字符串混用




资源 prefix
SQLite 表名 / 文件路径包含 tenant_id 前缀




测试断言
集成测试有 cross-tenant red-team case




运行时检查
tool 入口断言 args.tenant_id == ctx.tenant_id





四道防线让"逻辑错误导致泄漏"概率近零。


stdio-only 的设计
OpenClaw 比 Hermes 更严格：不提供 HTTP 模式。原因：






维度
风险





HTTP + multi-tenant
必须每 request 验 tenant + token + audience，复杂度爆炸




网络层
截获一次 token 可能泄漏多个 tenant secret




部署模型
用户期望"个人工具不开 port"





跨机器场景需要 SSH tunnel 后用 stdio：


# 远端机器
ssh -R 0:openclaw-mcp.sock my-laptop
# 本地 Claude Code 把 mcp 配置指向 unix domain socket
不优雅但安全。OpenClaw 团队的判断是：multi-tenant 工具暴露 HTTP 的合规风险大于 cross-machine 便利。


Tier 1 client 接入示例
# ~/.codex/config.toml
[[mcp_servers]]
name = "openclaw"
command = "openclaw"
args = ["mcp", "serve"]
env = { OPENCLAW_HOME = "~/.openclaw" }
Claude Code 配置同结构。Server 启动后会读 ~/.openclaw/tenants.yml 注册所有 tenant，每个 tenant 的 secret 已经在初次配置时进 keystore。

陷阱与常见问题
    

  • 忘了传 tenant_id：所有 tool 都必带，传空字符串或漏字段 server 直接 reject。
    • 

  • 同一 client 在不同 tool call 间 tenant 切换：是允许的，但 server 不维护"上一次 tenant"状态——每次 call 都要显式带。
    • 

  • audit log 文件膨胀：每天一个 ndjson，~10MB / tenant / 高活跃日。建议 90 天后 gzip 归档。
    • 

  • 跨机器接入忘记 SSH tunnel：openclaw 不开 HTTP，TCP 直连不存在。错误信息明确指向 stdio-only。
    • 

  • keystore 跨用户共享：多用户共用一台机器时 OS keystore 默认按 user 隔离，不会泄漏。但 root 仍能读所有 user keystore——多用户机请用文件级加密 + per-user 密码。
    • 



小结
OpenClaw MCP server 在 Hermes server 的设计上叠加了"multi-tenant 强隔离"维度：per-tenant secret keystore + 每 tool call audit log + 类型系统/资源 prefix 多层防泄漏 + stdio-only 拒绝 HTTP。4 个 tool（persona_switch / message_route / tenant_list / channel_send）覆盖聊天平台代接的所有核心动作，每个都按 tenant_id 隔离执行。这套设计让"一个个人 agent 同时管十个聊天 channel"在工程上 viable。下一篇看 hermes 与 openclaw 这种"同进程既作 server 又作 client"的双角色架构如何实现。
