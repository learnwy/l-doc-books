防递归与跨 tier 编排范式

核心概念

双向 MCP 把 Tier 1 与 Tier 2 工具栈拼成图，任意节点能调任意邻居。这种灵活性的代价是递归与死锁的风险陡升——一旦 call chain 形成环，资源耗尽与超时连锁是必然结局。本篇从 anti-recursion 的具体规则讲起，过渡到推荐的跨 tier 编排工作流模板（"Claude Code 拉 hermes memory → 写代码 → memory_write 落回"是典型 success case；"Claude Code 内部触发 Hermes 任务又触发 Claude" 是典型反例），最后把"再深入"指向 ../../../03_bridges/ 这本编排选型专册。

depth limit = 2 的理论依据
为什么是 2 而不是 3 或更多？因为 personal-agent 工具栈合理的工作流深度上限就是 2：






深度
典型工作流
例子





0
用户直接 Tier 1 调用
"帮我写一个 Python 函数"




1
Tier 1 调 Tier 2 拉上下文
"从 hermes memory 找出我对 RPC 的偏好"




2
Tier 2 调回 Tier 1 协作处理上下文
hermes curator 调 Claude Code 评估 trajectory




3+
几乎必然循环
hermes 调 Claude Code 又调 hermes...





depth=3 的合法场景非常稀有——Hermes 团队 telemetry 分析 10^6 次跨 tier call，depth=3 的 case 99.7% 是误触发循环。剩余 0.3% 真合理需求可通过 explicit override 解决（详见下文）。


timeout 熔断
每个 hop 默认 10 秒超时。timeout 不是"等到 10 秒再失败"，而是协调式 cancellation：


partial=... 字段把"abort 前已完成的部分"返回给 client，让 client 决定重试还是 fail。例如 curator 跑到 3/5 step 被 timeout，partial 字段写明已完成 step 与剩余 step，client 可以选择"只跑剩余 step"而非全部重来。


circular detection
depth 限制是浅层防御——如果 chain.path 显示同一节点出现两次，即便 depth=2 也是 cycle。Hermes/OpenClaw 在 X-Call-Chain header 里维护 path 字段：


path = "claude_code → hermes → claude_code → hermes"
              ↑                       ↑
              第 0 跳                 第 2 跳，重复出现
任何节点检测到自己 path 里出现两次立即 reject，避免浪费一跳 budget。


budget limit
单一顶层 task 累计 hop 数也有上限——默认 5。这覆盖"不递归但 fan-out 很大"的情况：


budget 防止"一个 task 撞穿所有跨 tier 通道"。budget 在顶层 task 起始时分配，所有派生 hop 共享同一 budget counter。


典型 success case
流：Claude Code 拉 memory → 写代码 → 写回
depth=1，hop 数 = 2，timeout 无触发——这是健康范例。


流：Hermes curator refine → 调 Claude Code 评估
depth=1（curator 是顶层 task，CC 是它派生的第 1 跳），整个 task 在 hermes 进程内闭环。


典型反例
反例 1：Claude Code 内部递归
用户: "用 hermes memory 把我的 todo 排序好"
Claude Code: → hermes memory_query "todo"
hermes: 返回 entries，但 entries 里有引用 "如需排序请调 Claude"
Claude Code 又: → hermes memory_query "如何排序 todo"
hermes: 返回 entries，含 "调 Claude 排序"
... 无限循环
depth=2 时 hermes reject 第 3 跳。如果没有 depth limit 会陷入无限。


反例 2：fan-out 撞穿 budget
用户: "把我所有 lark 群当周 OKR 都生成周报"
Claude Code: 列群 → 5 个群
对每个群: → openclaw channel_send → openclaw message_route 5 次
总 hop = 1 + 5 * 2 = 11
budget=5 时第 4 个群之后被 reject。建议改造为 batch：单 hop 内处理所有群，而非每群独立 hop。


explicit override 渠道
少数合法场景需要 depth=3 或 budget>5。Hermes 提供 X-Override-Budget header 让 client 显式声明：


{
  "method": "tools/call",
  "params": {
    "name": "memory_query",
    "_meta": {
      "X-Override-Budget": { "max_depth": 4, "max_hops": 10 },
      "justification": "annual report generation"
    }
  }
}
override 需带 justification，理由进 audit log 供人审计。default 不允许 override——必须在 hermes config 显式 enable：


[reentry]
allow_override = true
override_audit = true
合规要求严的场景应保持 allow_override = false。


编排深入指向
本篇覆盖"防递归"机制；"跨 tier 编排选型"是更大的话题——什么时候应该让 Tier 1 主导、什么时候让 Tier 2 主导、什么时候让两者并行 fan-out、orchestrator 该放在哪一层——这些内容在 ../../../03_bridges/ 一整本 hub 展开。本表给个速查：

陷阱与常见问题
    

  • 以为 depth=2 永远够：年报 / 全量迁移 / 数据回填这类 task 真需要 depth=3。看到 reject 后第一反应不是 override，而是问 "能不能合 hop"。
    • 

  • timeout 改成 60s 解决所有问题：实际是 hop 设计不合理。改 hop 内部 batch，让单 hop 在 10s 内完成。
    • 

  • circular detection 误判：同一进程 A 调 B 调 B 内部 self-call 不算 cycle，但 path 字段如果记错可能误判。debug 时打印 path 完整内容。
    • 

  • override 滥用：每次都开 override，等于没有 limit。Audit log 应定期 review 看 override 是否合理。
    • 

  • budget 共享语义被忽视：fan-out 派生多个 hop 共享同一 budget。client 没意识到时容易撞穿。
    • 



小结
防递归四件套——depth limit / timeout / circular detection / budget limit——让双向 MCP 架构在工程上 viable。depth=2 / hop=5 / timeout=10s 是 Hermes/OpenClaw 经验值，覆盖 99.7% 健康工作流，剩余通过显式 override 解决。本章结束 chapter 3——下一章进入 Hooks transform pipeline，看 Hermes Gateway/Plugin/Shell 三子系统如何与 OpenClaw 的 outbound webhook 协作完成另一种"跨进程协作"模式。本 hub 的编排深入选型请转 ../../../03_bridges/。
