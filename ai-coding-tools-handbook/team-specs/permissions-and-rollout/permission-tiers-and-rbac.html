权限三态与 Enterprise RBAC

Permission 模型是团队规模化用 AI 编程代理的硬门槛——写得太松 dev 误删 production，写得太严 agent 卡在 ask prompt 寸步难行。本篇按 Claude Code 三态语义、Enterprise RBAC 双 ON 模型、MCP server allowlist、组织级 spend cap 四块展开，目标是给 platform / security 团队一份可直接 enforce 的权限规约。

核心概念

Claude Code 的 permission 是 每个 tool call 都过一遍 rule engine 的三态模型：allow（无 prompt 直接执行）、ask（每次弹窗确认）、deny（永远拒绝、不 prompt）。规则按 deny → ask → allow 顺序匹配，first-match wins，deny 一旦命中后面 allow 不会救它。这与防火墙规则的 explicit-deny 是同一逻辑。

deny 与 ask 的差别经常被混淆——deny 完全不 prompt，agent 内部都收不到 confirm 信号，等同于这个 tool call 不存在；ask 会弹窗给 user 看，user 拒绝后 agent 知道"被拒了"，可以换策略。


deny → ask → allow 优先级
实际部署时这三态会写到 managed settings、user settings、project settings 三层文件里，但优先级排序与文件层次 正交——deny 永远先匹配，无论来自哪一层。配合 managed settings 不可被 user 覆盖的特性，企业能做到：


    

  • managed deny Bash(rm -rf *) —— user / project 任何 allow 都救不了
    • 

  • user ask Bash(npm publish *) —— 项目级 allow 也救不了，每次发包必须确认
    • 

  • project allow Bash(pnpm test *) —— 仅在该项目无感跑测试
    • 



hook 决策对 deny 与 ask 同样不能绕过。Claude Code 的 PreToolUse hook 可以返回 allow / deny / block，但如果 rule engine 已经判定 deny，hook 的 allow 不会生效——这一条在 2026-Q1 多个企业的 incident review 里反复被强调，因为有团队曾经写 hook 想"放行特定 rm 命令"被无声拦截。


Enterprise RBAC 双 ON 模型
Anthropic 2026-04 admin controls release 把 RBAC 接进 Claude Code Enterprise tier。核心机制是 org setting + role setting 双 ON 才生效——任意一层 OFF，权限就退化到默认。这与 AWS IAM 的 explicit-allow 双授权类似，目的是防止 admin 误开权限。


    

  • Owners / Primary Owners 始终拥有 full access，custom roles 不能 override（写多了 RBAC 误锁自己门外的 incident，这是逃生通道）
    • 

  • custom roles 只能在 org setting 允许范围内 缩窄 权限，不能扩展
    • 

  • dual-seat plan（Chat seat + Claude Code seat）下，RBAC 限制需 seat 级 + role 级同时满足——某 user 即便 role 给了 advanced agent 权限，如果 Claude Code seat 没分配，照样不能用
    •

紧急关停（org-level OFF）是 incident response 的关键工具——出了安全事件几秒钟就能全员断电，不需要逐个改 role。


MCP server allowlist
MCP（Model Context Protocol）server 让 agent 能连第三方工具（Linear、Sentry、Datadog），但每个 server 都是潜在的 secret 泄漏面 / 数据外发面。企业必须用 allowManagedMcpServersOnly: true 锁定。


关键约束：


    

  • allowManagedMcpServersOnly: true 与 enableAllProjectMcpServers: true 是 互斥语义——后者会被前者一票否决，dev 项目里加 .mcp.json 等于白写
    • 

  • managed 列表里的 server 命令路径建议指向 OS 级路径（如 /opt/acme/mcp/），防止 dev 把同名 binary 放 PATH 前面劫持
    • 

  • 每个 managed MCP server 都建议开 read-only 模式，避免 agent 一边查 issue 一边误改 Linear ticket
    • 



Organization spend cap
2026-04 admin controls 同时引入了 org-level + per-user spend cap。机制：每个 user 每月有 token 上限，到顶后该 user 在 org 内无法发起新 agent call；org 也有总 ceiling，到顶后全员限流。


实操建议：


    

  • per-user cap 设到 P95 用量的 1.5 倍，留出 burst 空间但能挡住失控 loop
    • 

  • org 总 ceiling 略低于 finance 给的预算（如 95%），剩 5% 给月底突发
    • 

  • cap 触顶时 admin 收 webhook，配合 OTel telemetry 能立刻定位是哪个 dev、哪类 task 失控
    • 

  • pilot 阶段必开 cap，防止 dev 第一周用 prompt 调试 agent 撞天花板
    • 



陷阱与常见问题
    

  • 陷阱 1：以为 ask 等于"agent 还会问 user"。如果 user 拒绝，agent 会 retry 不同策略——若没设好上限，会陷入 ask 循环烧 token。
    • 

  • 陷阱 2：hook 想绕 deny。PreToolUse hook 的 allow 不能救 rule engine 的 deny，写 hook 时先确认 deny rule 没卡住。
    • 

  • 陷阱 3：custom role 想给比 org 更多权限。RBAC 是收口语义，custom role 只能 缩窄，给 org 没开的 feature 是无效配置。
    • 

  • 陷阱 4：dual-seat plan 漏分 seat。某 user role 配齐了但忘分 Claude Code seat，dev 一脸懵——查 audit log 才能定位。
    • 

  • 陷阱 5：MCP allowlist 路径写相对路径。./mcp/sentry 会被 dev cwd 劫持，必须写绝对路径或固定 OS 级路径。
    • 

  • 陷阱 6：spend cap 撞墙没告警。cap 触发时若没接 webhook，dev 只看到 agent 罢工，admin 不知发生啥；上线必配告警。
    • 



小结
    

  • Claude Code permission 三态：allow（无感）/ ask（弹窗确认）/ deny（永远拒绝），按 deny → ask → allow 顺序 first-match wins。
    • 

  • hook 决策不能绕过 deny / ask，rule engine 永远先判。
    • 

  • Enterprise RBAC 双 ON：org setting + role setting 同时 ON 才生效，Owners 永远 full access，custom roles 只能缩窄。
    • 

  • MCP server 必锁 allowManagedMcpServersOnly: true，与 enableAllProjectMcpServers 互斥；server 路径用绝对 OS 路径。
    • 

  • spend cap 双层：per-user 设 P95 * 1.5、org 设预算 95%，配 webhook 告警；pilot 必开。
    •
