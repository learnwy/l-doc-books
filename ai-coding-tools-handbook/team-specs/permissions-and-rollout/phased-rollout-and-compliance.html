分阶段 rollout 与 Compliance 接入

把 AGENTS.md 模板、managed settings、permission 三套都准备好之后，最后一关是怎么把这些 enforce 到全公司而不一次性 break 所有 dev。本篇按三阶段 rollout 路径、Anthropic 2026-04 Compliance API 接入、SOC2 / ISO 27001 evidence 抓取、回滚预案四块展开，目标是给 SRE / 合规团队一份可直接搬到内部 runbook 的部署框架。

核心概念

分阶段 rollout 的本质是 把 blast radius 控制在可恢复范围——任何一次 managed settings 推送都可能误锁全员，必须按 pilot → 团队 → org-wide 三档逐步扩面，每档明确 rollback 路径与验证 metrics。Anthropic 2026-04 同时上线的 Compliance API + Claude Code OTel telemetry 让 audit log 两源合并，刚好对应 SOC2 CC6 / CC7 与 ISO 27001 A.12 控制项。

Phase 1 pilot
pilot 期挑 5 个对工具敏感、愿意主动反馈的 dev，给他们装 baseline managed settings + AGENTS.md template，每天 standup 收 issue。这阶段的目的不是验证 ROI，而是把"agent 跑不动 / 撞 deny / 配置冲突"这些 sharp edge 在小规模暴露。常见 pilot 期发现：


    

  • managed deny 写得太严：Bash(rm *) 把 rm node_modules 也封了，dev 没法清依赖
    • 

  • permission ask 写得太多：Bash(git *) 让每次 status 都弹窗，dev 烦到关 agent
    • 

  • MCP allowlist 漏了 Linear：team 工具链里 Linear 是核心，没加进 managed 列表 dev 没法用
    • 

  • AGENTS.md 200 行写 1500 行：agent 启动慢、context 占满 50%
    • 



pilot 期建议每天 EOD 总结一次 issue，每周 release 一版 managed settings；pilot 结束的退出标准是 连续 3 天 0 个 P1 issue。


Phase 2 团队
Phase 2 把范围扩到 20-50 人的整个团队，目的从"找 bug"切到"验证 baseline"。这阶段开始接 OTel telemetry 收集量化 metrics——agent 调用频次、tool 分布、token 消耗、permission prompt 频率——用数据决定 baseline 该收紧还是放松。


退出标准：


    

  • 90% dev 主动用 agent ≥ 3 次 / 日（adoption 验证）
    • 

  • P50 task 完成时间从 baseline 降 15% 以上（productivity 验证）
    • 

  • permission prompt 频率 ≤ 5 次 / dev / 日（friction 验证）
    • 

  • 0 个 P1 安全 incident（不含 dev 误操作）
    • 



Phase 2 的 managed settings 还允许频繁调整（一周一版），到 Phase 3 之后改动节奏要降到月度，避免影响全员。


Phase 3 org-wide + Compliance API
Phase 3 推 MDM 全员，开 SSO 强制，启用 Compliance API 拉 audit log。Anthropic 2026-04 Compliance API 提供两类事件源：


    

  • web UI 的 admin events：login activity、permission changes、role assignments、org admin actions
    • 

  • Claude Code OTel telemetry：agent 调用、tool execution、token usage、permission denials
    • 



合并这两源得到 full coverage——纯 web UI 看不到本地 CLI 行为，纯 OTel 看不到 admin 在控制台改了什么。


Phase 3 还要 enforce 一组合规必备字段：


    

  • managed settings 的 telemetry.required: true 不可绕过
    • 

  • SSO 强制（个人 OAuth 关闭，所有 user 走 IdP）
    • 

  • audit log retention 至少 1 年（SOC2 通用要求）
    • 

  • managed settings 变更走 change ticket（ISO 27001 A.12.1.2）
    •

抓取脚本可直接用 Compliance API：


curl -X POST https://api.anthropic.com/v1/compliance/events \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "event_types": ["permission_changes", "role_assignments"],
    "since": "2025-05-01T00:00:00Z",
    "until": "2026-05-01T00:00:00Z",
    "format": "ndjson"
  }' > evidence-permissions-2025-2026.ndjson
输出 NDJSON 直接喂给 SIEM 或合规平台 Drata / Vanta，免人工整理。


回滚预案
managed settings 推下去若严重影响 dev 效率（如 deny rule 太严导致 agent 寸步难行），回滚不是 git revert 那么简单——MDM endpoint 缓存可能 24h 才更新，期间全员都被卡。标准回滚流程：


    

  1. admin 在 MDM 控制台 push 一份 反向覆盖 的 managed-settings.json（把刚加的 deny 改 allow 或干脆删除）
    2. 

  2. 强制触发 endpoint sync（MDM 推 force-resync 信号，部分 endpoint 仍要等下次 heartbeat）
    3. 

  3. 同步在 Slack / 邮件通知全员"已回滚到 vX，请重启 Claude Code"
    4. 

  4. dev 重启 agent 后 managed settings 立即重读，新策略生效
    5. 



避免回滚噩梦的最佳实践是 每次 production push 前先 staging endpoint 验证——把一批 staging 设备配成 production endpoint 镜像，先推那批，跑 24h 无 issue 再推 production。这一招在 2026 多个企业的 case study 里把 P1 incident 砍掉 80%。


陷阱与常见问题
    

  • 陷阱 1：跳过 Phase 1 直接全员推。看似省时间，实际 sharp edge 全砸到全员头上，回滚成本远高于 pilot 周期。
    • 

  • 陷阱 2：Compliance API 接了但不接 SIEM。raw NDJSON 堆在 S3 没人看，等于没接；至少接 alert 规则。
    • 

  • 陷阱 3：audit log retention < 1 年。SOC2 默认要 1 年，部分客户合同要 7 年；提前与法务确认 retention 策略。
    • 

  • 陷阱 4：紧急回滚靠 user 自己改 settings。dev 改不动 managed settings（这是设计目的）——必须走 MDM 推送，没 MDM endpoint 的"应急通道"等于裸奔。
    • 

  • 陷阱 5：endpoint sync 假设 < 1h。多数 MDM 默认 8h heartbeat，紧急回滚要按 24h worst case 算，提前部署 force-resync 通道。
    • 

  • 陷阱 6：变更没走 ticket。审计员问 "这条 deny 谁加的、为什么"，没 ticket 答不出 → SOC2 失分。
    • 



小结
    

  • 分阶段 rollout 三档：Phase 1 pilot 5 人 / 1 周（找 sharp edge）→ Phase 2 团队 20-50 人 / 2-3 周（验证 metrics）→ Phase 3 org-wide + Compliance API。
    • 

  • Phase 3 接 Compliance API + OTel telemetry 双源合并：web UI 抓 admin 行为，OTel 抓 CLI 行为，缺一不可。
    • 

  • SOC2 / ISO 27001 evidence 用 Compliance API NDJSON 导出，喂给 SIEM 或 Drata / Vanta，免手工整理。
    • 

  • 回滚预案：admin 推反向 managed-settings.json + force-resync + 通知重启；endpoint 缓存 24h 是 worst case，要按这个时间设计应急。
    • 

  • 每次 production push 前先 staging endpoint 跑 24h，按 2026 case study 能砍 80% P1 incident。
    •
