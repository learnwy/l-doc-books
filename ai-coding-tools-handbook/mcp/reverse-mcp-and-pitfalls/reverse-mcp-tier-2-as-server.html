反向 MCP：Tier 2 personal-agent 工具作为 server

前两章的视角都是"编程代理调外部 server"——95% 用户的入门姿势。但 MCP 协议本身是对称的：任何应用都可以同时作为 client 和 server。当一个 personal-agent 工具（Hermes、OpenClaw 这类 Tier 2 工具）以 mcp serve 形态把自己的 memory / persona / skill 暴露成 MCP server、再被 Claude Code / Codex 反向调用时，coding agent 就获得了"角色化的世界知识"。这是 2026 年跨 tier 编排的核心模式。本节讲清反向 MCP 的架构动机、两款典型 Tier 2 工具的 server 入口、以及在 coding 工具里接入的最短配置。深入选型、编排、防递归的内容请转 ../../../03_bridges/1_cross-tier-orchestration/。

核心概念

把 Tier 2 工具暴露为 MCP server 解决的不是"调外部 API"问题——那部分 Tier 1 工具直接对接更直接。它解决的是"软上下文持久化与跨会话注入"：






软上下文类型
不暴露给 coding agent 的代价
通过 MCP 注入后的收益





memory（用户偏好、历史决策、项目背景）
每次新会话重新解释 context
agent 一开口就知道用户做哪个项目




persona（角色化系统提示、口吻、语气偏好）
跨会话风格漂移
输出风格保持一致




skill（用户自定义的过程性知识 SKILL.md）
同样的 workflow 每次手把手讲
skill 加载即可、命中触发器自动应用




curator scheduling（待办、提醒、周期任务）
coding agent 看不到全局节奏
在 coding 间隙触发提醒





Tier 1 与 Tier 2 工具的分工因此清晰：Tier 1 干代码相关的活、Tier 2 维护"我是谁、我在做什么、我偏好什么"，两者通过反向 MCP 拼接成一个完整的助理体验。


架构动机：为什么不直接让 coding agent 调外部 API
反对意见自然存在——既然 coding agent 可以直接调 GitHub API、查 Notion 数据库、查日历，为什么还要再过一层 Tier 2 工具？三条具体原因：


    

  • 持久化层不在 coding agent 内：Claude Code 一次会话结束 context 就清掉，下次新开会话不知道你昨天跟它聊了什么。Tier 2 工具是用户的"长期记忆载体"，把跨会话状态托管出来。
    • 

  • 角色化软上下文需要专门工具维护：persona 不是几行 system prompt 就能解决——需要 curator 定期 review、需要 skill 命中触发器、需要 memory 按相关度排序。这些 ops 工作 coding agent 不擅长，让专门的 personal-agent 工具做。
    • 

  • 跨 tool 复用同一份软上下文：同样的"我是 frontend 工程师、目前做 lynx 项目、偏好 TypeScript 严格类型"语境，Claude Code、Codex、OpenCode 都应该共享。Tier 2 工具作为 single source of truth，三个 client 通过 MCP 反向调用，避免在每个 tool 各自配一份。
    • 



Hermes：hermes mcp serve 暴露的 tool
Hermes（learnwy-internal 系列工具中的 memory / curator 中枢）通过 hermes mcp serve 子命令把内部状态暴露成 MCP server。stdio 模式启动后 client 看到的 tool 列表大致是：






Tool
输入
返回
典型场景





memory_query
{ query: string, top_k: int }
相关 memory 片段列表
coding agent 问"我之前怎么处理这个问题"




memory_write
{ topic, content, tags }
confirm
把会话里的关键决策写回长期记忆




curator_schedule_list
{ window: "today" | "week" }
周期任务清单
看当前周期内的复习任务




persona_active
{}
当前激活的 persona 描述
agent 启动时拿语气基线




skill_dispatch
{ trigger: string }
命中的 skill 列表
关键词触发 SKILL.md 加载





Hermes 的 server 实现走 stdio——hermes mcp serve 把 stdin/stdout 接给 MCP SDK；不开 HTTP 端口、不暴露公网。这与 Hermes "本地优先、用户数据不出本机"的设计哲学一致。从 client 角度，接入它就是普通 stdio server。


OpenClaw：mcp serve 暴露 multi-tenant 能力
OpenClaw（多租户 chat-platform 编排工具）的 mcp serve 子命令暴露另一组 tool：






Tool
用途





persona_switch
在 multi-tenant 场景切换激活的 persona




message_route
通过 chat-platform router 发消息到飞书 / Slack / Telegram




tenant_list
列出当前用户挂载的所有 tenant




channel_send
向指定 channel push 通知





OpenClaw 与 Hermes 一个关键差异是 multi-tenant 隔离——同一个 OpenClaw 实例可能服务多个 persona / tenant，persona_switch 让 coding agent 在会话内显式切换"我现在以哪个身份操作"。这条 tool 对个人开发者价值不大，但对企业内多角色用户（白天 dev、晚上做 OSS、周末做 hobby）非常重要。


OpenClaw 同样优先 stdio——multi-tenant 数据敏感，HTTP 暴露需要 OAuth + audience 校验，本地 stdio 直接避免这一层复杂度。


Client 端接入：最短配置
在三款编程工具里把 Hermes / OpenClaw 作为 stdio server 接进来：


// Claude Code .mcp.json（项目根 or ~/.claude.json）
{
  "mcpServers": {
    "hermes": {
      "type": "stdio",
      "command": "hermes",
      "args": ["mcp", "serve"],
    },
    "openclaw": {
      "type": "stdio",
      "command": "openclaw",
      "args": ["mcp", "serve"],
    },
  },
}
# Codex ~/.codex/config.toml
[mcp_servers.hermes]
type = "stdio"
command = "hermes"
args = ["mcp", "serve"]

[mcp_servers.openclaw]
type = "stdio"
command = "openclaw"
args = ["mcp", "serve"]
// OpenCode opencode.json
{
  "mcp": {
    "hermes": { "type": "local", "command": "hermes", "args": ["mcp", "serve"] },
    "openclaw": { "type": "local", "command": "openclaw", "args": ["mcp", "serve"] },
  },
}
接入后会话启动 coding agent 就能看到 hermes / openclaw 的 tool 清单——memory_query、persona_active、skill_dispatch 等成为日常对话里可被模型主动调用的操作。


深入主题转引
反向 MCP 把 Tier 1 / Tier 2 拼成统一工作流后，会涌出一批二阶问题：


    

  • 如何在 client 端做 tool 预算管理：Hermes + OpenClaw 两个 server 加起来轻松超过 10 个 tool，需要用 Codex tools allowlist 或 Claude Code 运行时 disconnect 控制。
    • 

  • 如何编排 Tier 1 调用 Tier 2 的多步工作流：典型场景如"开发前先从 hermes 拉项目背景 memory、用 persona_active 校准语气、写代码、写完用 memory_write 落回结果"。
    • 

  • 如何防止递归调用：Tier 2 工具自己内部也可能调 Tier 1（例如 OpenClaw 让 Claude Code 帮它跑某代码任务），形成环。需要协议层 + 实现层双重防护。
    • 

  • 跨 tier 数据流向治理：哪些 memory 可以从 Tier 2 流到 Tier 1、哪些反向流回、persona 在两边的一致性。
    • 



这四类问题不在本节深入——属于 cross-tier-orchestration 范畴。详细方案、Hermes 的 reentry-guard、OpenClaw 的 tenant-aware 调度算法、以及完整工作流模板请转 ../../../03_bridges/1_cross-tier-orchestration/。


陷阱与常见问题
    

  • 把 Hermes / OpenClaw 配到 HTTP 模式：两款工具的 stdio-first 设计意味着 HTTP 实现可能不完整或没有 OAuth audience 校验。生产环境坚持 stdio。
    • 

  • persona_active 拿到的描述被模型当 system prompt 直注入：MCP Prompts primitive 应该是用户 explicit 选用，不是 system 注入。让 coding agent 自己决定要不要参考 persona，不要硬编码"每次开局必读 persona"。
    • 

  • memory_write 把敏感片段也写回：会话里讨论了 secret / API key，被 memory_write 落入长期记忆。Hermes 内置 redactor 但需要确认开启状态。
    • 

  • 递归调用形成环：Tier 2 工具自己内部调 Tier 1、Tier 1 又通过 MCP 调 Tier 2，无限递归。所有 Tier 2 工具都应实现 reentry-guard（同一调用链最多 1 层）。
    • 

  • 同时挂多个 Tier 2 工具：Hermes 与 OpenClaw 都暴露 skill / persona 类 tool，命名相近，模型选错。建议 Codex tools.rename 加前缀 hermes_* / openclaw_* 消歧。
    • 



小结
    

  • 反向 MCP 把 Tier 2 personal-agent 工具暴露为 MCP server，被 Tier 1 coding agent 反向调用，注入"软上下文"（memory / persona / skill）。
    • 

  • 架构动机三条：跨会话持久化、专门工具维护角色化状态、跨 coding tool 共享同一份软上下文。
    • 

  • Hermes hermes mcp serve 暴露 memory query/write + curator scheduling + persona + skill dispatch；OpenClaw mcp serve 暴露 multi-tenant persona switch + chat-platform router。
    • 

  • Client 端接入是普通 stdio server 配置，三款编程工具语法略异、核心都是 command + args。
    • 

  • 深入选型 / 编排 / 防递归内容在 ../../../03_bridges/1_cross-tier-orchestration/。
    •
