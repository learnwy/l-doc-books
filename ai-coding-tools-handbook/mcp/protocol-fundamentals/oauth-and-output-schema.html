OAuth 2.1 授权与 outputSchema 类型化返回

2025-06-18 是 MCP 协议史上影响最大的一次 spec 升级——HTTP transport 上的 OAuth 2.1 + PKCE 被标记为 MUST，outputSchema 与 structuredContent 让 tool 返回值从 free-form text 升级为可校验的 typed object。两项改动一起把 MCP 从"能跑通"推到"可生产部署"。本节把这两块协议要求拆开讲清楚：HTTP 授权的发现机制、stdio 上的等价方案、tool 返回值三层 fallback、以及 production 部署的硬性建议。

核心概念

OAuth 2.1 是 OAuth 2.0 + 历年 BCP（best current practice）合订本——强制 PKCE、禁用 implicit flow、禁用 resource owner password credentials、refresh token 必须 rotate。把这套标准搬到 MCP 上需要解决三个具体问题：MCP server 是 OAuth 体系里的哪个角色？client 怎么发现 server 用的是哪个 authorization server？怎么防止用户在 server A 拿到的 token 被恶意用到 server B？

OAuth 角色 在 MCP 里对应 职责
Resource Server MCP server（HTTP transport） 校验 access token、返回受保护资源
OAuth Client MCP client（编程代理） 引导用户完成授权、持有 access/refresh token
Authorization Server 通常独立部署 颁发 token、托管 consent UI
Resource Owner 用户 授权 client 访问自己的 server 数据

关键观察：spec 把 MCP server 与 authorization server 解耦——一个企业可以把内部 SSO（Okta / Auth0 / 自建 Keycloak）作为 authorization server 服务多个 MCP server。client 不需要预先知道 authorization server 在哪，靠 discovery 机制现场拉。

HTTP transport 的 OAuth 2.1 + PKCE 流
完整流程基于三份 RFC：


    

  • RFC 9728（Protected Resource Metadata）：MCP server 在 /.well-known/oauth-protected-resource 暴露元数据，列出"我信任哪些 authorization server"、"我的 resource identifier 是什么"。client 第一次收到 401 时根据 WWW-Authenticate header 里的 resource_metadata URL 拉这份文件。
    • 

  • RFC 7591（Dynamic Client Registration）：可选。如果 client 之前没在 authorization server 注册过，可以走 DCR endpoint 自动拿 client_id。企业 SSO 通常关闭 DCR、要求管理员预先注册 client；公开 server 则普遍打开 DCR 方便接入。
    • 

  • RFC 8707（Resource Indicators）：核心安全机制。client 在 /authorize 与 /token 请求里携带 resource=https://server-a.example.com 参数，authorization server 把这个值绑进 access token 的 audience claim；MCP server 收到 token 后必须校验 audience 与自己的 resource identifier 一致，否则拒绝。这条防止"用户在 server A 授权的 token 被恶意 client 拿去调 server B"。
    • 



PKCE 是强制项：client 发起 /authorize 时生成 random code_verifier、SHA256 哈希成 code_challenge 带在 URL 里；换 token 时把原始 code_verifier 带在 /token 请求里。authorization server 校验两者匹配。PKCE 防的是"授权码被截获后被替换成攻击者的 client_id 换 token"——在公共 client（CLI、桌面 app）场景里这是必备防御。


stdio transport 的等价授权方案
stdio transport 没有 HTTP 级别的授权——client 启动 server 子进程时通过 env 变量传 credentials，server 在初始化时直接读 env：


{
  "mcpServers": {
    "linear": {
      "type": "stdio",
      "command": "linear-mcp-server",
      "env": { "LINEAR_API_KEY": "${LINEAR_API_KEY}" },
    },
  },
}
${LINEAR_API_KEY} 由 client 在启动子进程前从自己的 env 展开（OpenCode / Claude Code 都支持这种 env 引用语法），避免 API key 写进配置文件被 commit 进 git。子进程继承的 env 只对该子进程可见，client 重启后 token 不会持久化在子进程里。


stdio 等价模型的优势是简单——没有 OAuth 多步握手、没有 token rotation、没有 audience 校验；劣势是无法支持多用户共享 server，因为 server 进程的 env 是单租户的。所以 stdio 主要服务"个人本地工具"，而 HTTP+OAuth 服务"团队/企业共享 server"。


outputSchema 与 structuredContent
2025-06-18 spec 之前，tool 调用返回的 CallToolResult 只有 content: [{ type: "text", text: "..." }] + isError: bool 两个字段。client 拿到的永远是字符串，要解析成结构化数据全靠 server 在 text 里"礼貌地"返回 JSON、client 端用 JSON.parse 试一下。这套设计在 agent 场景里很脆弱——模型偶尔被 server 自然语言回复带偏、解析失败时 fallback 行为不一致。


新 spec 引入两件事：


    

  • outputSchema：tool 声明里多了一个字段，值是一份 JSON Schema，描述返回值的结构。client 看到 schema 后知道这个 tool 是有 typed 返回的。
    • 

  • structuredContent：tool 调用返回的 CallToolResult 多了一个字段 structuredContent: object，是按 outputSchema 校验过的强类型对象。
    • 



// server 端 tool 声明
{
  "name": "get_pr_status",
  "description": "查询 GitHub PR 当前状态",
  "inputSchema": { "type": "object", "properties": { "pr_number": { "type": "number" } } },
  "outputSchema": {
    "type": "object",
    "properties": {
      "state": { "enum": ["open", "merged", "closed"] },
      "checks_passing": { "type": "boolean" },
      "review_count": { "type": "integer" },
    },
    "required": ["state", "checks_passing"],
  },
}
client 调用 tools/call 后拿到的响应里同时有 content（向后兼容的 text 表示）与 structuredContent（typed object）。client 实现采用三层 fallback 策略保证稳健性：


    

  1. 优先用 structuredContent：server 声明了 outputSchema 时，直接拿强类型对象交给 agent，可以用 zod / valibot / pydantic 等做校验。
    2. 

  2. 退而从 content[0].text parse JSON：server 没声明 outputSchema 但 text 看起来是 JSON 时，尝试解析。
    3. 

  3. 最终 fallback 是 raw CallToolResult { content, isError }：把原始 text 作为 string 交给模型，让模型自己理解。
    4. 



新 server 实现应该把 outputSchema 作为硬性要求：每个 tool 都声明 outputSchema、运行时验证返回值匹配 schema、不匹配时返回 isError: true。这让 client 端有了可靠的契约。

陷阱与常见问题
    

  • token 不绑 audience：server 直接信任 authorization server 颁发的任意 token，没有校验 aud claim 匹配自己——攻击者用其他 MCP server 的 token 就能横向访问。
    • 

  • DCR 暴露在公网且无限速：恶意 client 海量注册占满数据库或申请 token。生产部署必须给 DCR 端点加速率限制 + 反垃圾。
    • 

  • refresh token 不 rotate：OAuth 2.1 要求 refresh token 一次性使用，刷新后旧 token 立刻失效。复用旧 refresh token 是常见实现错误。
    • 

  • outputSchema 与实际返回不匹配：声明了 schema 但运行时返回不符合，client 端校验失败抛错。CI 里应该用合成 server 调用校验。
    • 

  • stdio env 泄漏到日志：server 在 stderr 打印 startup env，token 被记进日志聚合系统。生产 server 应明确 redact 敏感 env。
    • 



小结
    

  • HTTP transport 强制 OAuth 2.1 + PKCE：MCP server 是 Resource Server、client 是 OAuth Client、authorization server 解耦部署。
    • 

  • discovery 链路：401 + WWW-Authenticate → RFC 9728 protected resource metadata → authorization server metadata → 可选 RFC 7591 DCR → /authorize → /token。
    • 

  • RFC 8707 Resource Indicators 把 token audience 绑定到具体 server，是防 token 跨 server 滥用的核心机制。
    • 

  • stdio transport 用 env 变量传 credentials，client 启动子进程时展开，简单但只能单租户。
    • 

  • outputSchema + structuredContent 让 tool 返回值变成 typed object，client 端三层 fallback：structuredContent → text-parsed JSON → raw text。
    • 

  • production 部署 pin spec 版本到具体修订、强制 PKCE、audience 校验、outputSchema 必填。
    •
