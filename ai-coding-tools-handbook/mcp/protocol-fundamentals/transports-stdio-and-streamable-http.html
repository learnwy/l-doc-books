两种传输与三类 primitive：stdio 与 Streamable HTTP

JSON-RPC 2.0 是 MCP 的语言层，但语言只是协议表面——真正决定 server 部署形态的是 transport：进程内 stdio 还是网络 Streamable HTTP。2024-11 Anthropic 开源 MCP 时只有 stdio；2025-03 引入旧版 HTTP+SSE 双 endpoint；2025-06-18 spec 把双 endpoint 标记 deprecated；2025-11 spec 把 Streamable HTTP 单 endpoint 列为唯一推荐。到 2026-05-14 这一刻，modelcontextprotocol.io 的 SDK 月下载量已经 97M+、GitHub stars 81K+，但社区里仍有大量 server 是 2025 年初写的旧 SSE 实现——选对 transport 与处理旧 server 互通，是接入 MCP 的第一道选型。

核心概念

MCP 在 JSON-RPC 2.0 之上定义了三类 server 暴露给 client 的 primitive：Tools、Resources、Prompts。三者职责正交，混用会让 agent 行为不可预测。

Primitive 语义 谁主动 典型例子 常见误用
Tools 副作用动作 模型决定调用 create_issue、run_query、send_email 把只读检索硬塞成 tool
Resources 可读上下文片段 client 主动 pull file://...、db://schema、memory:// 把动作型 API 当 resource 暴露
Prompts 可参数化 prompt 模板 用户主动选 summarize_pr、triage_bug 当成 system message 自动注入

Tools 由模型在对话中自行决定调用、需要副作用承诺；Resources 是 client 显式 fetch 的只读 blob；Prompts 是用户在 UI 里 explicit invoke 的 prompt 模板。三者都通过 JSON-RPC 方法暴露：tools/list、tools/call、resources/list、resources/read、prompts/list、prompts/get。

stdio transport：本地子进程的标准选型
stdio 是 MCP 协议的默认 transport，也是 2024-11 首发版本唯一支持的形式。语义极简：client 把 server 作为子进程启动，stdin 写 JSON-RPC 请求帧、stdout 读响应帧、stderr 留给 server 写日志。这种"管道里的 RPC"模型把网络复杂度全部规避——没有端口、没有 TLS、没有授权、没有 CORS、没有 reverse-proxy。


帧格式是 newline-delimited JSON：每条 JSON-RPC 消息序列化为单行、\n 结束，禁止内嵌换行（否则下游 parser 错位）。这意味着 server 实现必须确保 JSON 输出是单行紧凑形式，且任何 print/log/debug 输出必须走 stderr，否则会污染消息流。SDK（typescript、python、go、rust 等）都内置这条约束。


stdio 没有 transport 级别的授权——client 启动子进程时通过 env 变量传 API key / token / OAuth credentials。client 进程可见 server 子进程的所有 env，所以"谁能启动 client、谁就能调 server"是隐式的信任模型。对应的部署形态是：server 二进制 / npm 包 / Python 脚本本地安装，client 在配置文件里写 command + args + env 三元组。


// Claude Code .mcp.json 里的 stdio 配置片段
{
  "mcpServers": {
    "github": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" },
    },
  },
}
stdio 的局限性也来自子进程模型本身：不能跨机器、不能多 client 共享、不能云端托管、生命周期与 client 绑死。一旦需要把 server 部署成共享服务（团队共享 issue tracker server、企业内部知识库 server），stdio 就无法胜任，必须切到 HTTP transport。


Streamable HTTP transport：单一 endpoint 与 SSE 流
Streamable HTTP 是 2025-11 spec 替换旧版 HTTP+SSE 双 endpoint 的最终形态。设计目标只有一个：把"请求-响应"与"服务端推送通知"合并到同一个 URL 之下，让 server 部署像普通 REST API 一样简单。


关键点四条：


    

  • 单一 endpoint：server 只需提供一个 URL（例如 https://api.example.com/mcp），同时接受 POST（client 发 JSON-RPC 请求）与 GET（client 升级为 SSE 流读服务端通知）。
    • 

  • Mcp-Session-Id header：server 在第一次响应里返回会话 ID（spec 建议 UUID / JWT / hash，必须可见 ASCII 字符），client 后续请求都要回带，server 借此把多次 HTTP 请求绑成一个逻辑会话。
    • 

  • Origin 验证：server 必须校验 Origin header，拒绝来自非预期源的请求——这是防 DNS rebinding 攻击的关键，否则恶意网页可以诱导本地浏览器调用本地 MCP server。
    • 

  • Backwards-compat 回退：spec 规定一个明确算法——client 第一次 POST 收到 4xx 时，回退到旧版"双 endpoint SSE+POST"协议；这让 2025 年初的旧 server 不需要立刻升级。
    •

与旧版 SSE transport 的互通
2025-03 至 2025-06-18 的旧 spec 用的是"双 endpoint SSE"模型：一个 /sse GET 端点供 client 订阅、一个 /messages POST 端点供 client 发请求；两个 endpoint 用 session_id query 参数串起来。这套设计的问题是 server 必须维护"半开 SSE 连接"状态，而很多 serverless / edge 平台（Cloudflare Workers、Vercel Edge、AWS Lambda）不支持长连接，导致部署门槛过高。


2025-11 Streamable HTTP 替换之后，旧 server 并没有强制下线。spec 给出的兼容路径是：


    

  • 新 client + 旧 server：client 第一次 POST 收到 4xx 后按算法回退到 SSE+POST 双 endpoint 模式。SDK 默认实现这套回退。
    • 

  • 新 server 同时兼容旧 client：server 在单 endpoint 之外再额外暴露旧的 /sse + /messages 双 endpoint，6-12 个月平滑迁移期。
    • 

  • 新 server 只支持单 endpoint：直接拒绝旧 client，靠 client 升级 SDK 解决。
    • 



2026 上半年大部分官方 server（GitHub、Notion、Linear、Slack）已经只暴露 Streamable HTTP；剩余的社区 server（很多是 2025-03 写的）还在双 endpoint 模式。生产部署时建议把 spec 版本 pin 到 2025-11-05 这个具体修订号，而不是 latest，避免下次 spec 升级导致 client / server 版本错位。


陷阱与常见问题
    

  • stdout 被日志污染：server 用了 console.log 或 print 写调试信息到 stdout，破坏 JSON-RPC 帧。所有日志必须走 stderr，SDK 通常提供 logger helper。
    • 

  • JSON 内嵌换行：序列化时用了 JSON.stringify(obj, null, 2) 带缩进，单条消息变成多行。生产代码必须 compact 序列化。
    • 

  • Streamable HTTP 没验 Origin：server 在公网暴露但未校验 Origin，浏览器里的恶意页面可以诱导调用。spec 明确把这列为 MUST。
    • 

  • 会话 ID 用了不可见字符：Mcp-Session-Id 必须是可见 ASCII，用了 base64 padding = 也合法但常见错误是写入 UTF-8 或控制字符。
    • 

  • 生产 server pin 错版本：写代码时 client 装 2026 SDK、server 还在 2025-06 实现，capabilities 协商时双方 spec 版本号不匹配，行为不可预测。
    • 



小结
    

  • JSON-RPC 2.0 之上分三类 primitive：Tools（动作）、Resources（只读上下文）、Prompts（参数化模板），职责正交。
    • 

  • stdio transport 用子进程 + stdin/stdout JSON-RPC 帧，零网络复杂度，env 变量传授权，适合本地工具。
    • 

  • Streamable HTTP 是 2025-11 spec 唯一推荐的网络 transport：单 endpoint POST+GET、Mcp-Session-Id header、Origin 验证防 DNS rebinding。
    • 

  • 旧 SSE+POST 双 endpoint 在 2025-06-18 起 deprecated，新 client 通过 4xx 回退算法兼容旧 server。
    • 

  • 生产部署 pin spec 版本号到具体修订（如 2025-11-05），避免追 latest。
    •
