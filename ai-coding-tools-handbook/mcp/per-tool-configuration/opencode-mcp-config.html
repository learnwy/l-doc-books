OpenCode 的 MCP 配置：local、remote 与 OAuth

OpenCode 是 2025-2026 期间快速崛起的开源编程代理之一，对 MCP 的支持设计偏"原生"——opencode.json 顶层有专门的 mcp section、配置语法直接映射协议层概念，而不是像 Claude Code 那样另起一套字段命名。这种设计的好处是看完 spec 之后能立刻读懂 OpenCode 的配置；坏处是配置文件的优先级和 OAuth 触发方式藏在 CLI 子命令里，第一次接入容易困惑。本节按"配置语法 → OAuth 流 → 优先级模型 → 最小示例"四块讲清楚。

核心概念

opencode.json 用一份 JSON 描述 client 的全部行为，mcp 字段是其中的 server 注册表：每个键是 server 名（client 端唯一标识）、值是 server 描述。OpenCode 把 MCP 协议层的两种 transport 直接映射为两个 type：

type 对应 MCP transport 必填字段 用途
local stdio command 本地子进程，env 传授权
remote Streamable HTTP url 远程 server，可选 OAuth 
type: local 配置必填 command，可选 args、env、enabled；启动子进程时 OpenCode 把 env 与当前进程的 env 合并传给子进程。type: remote 配置必填 url（必须是 https）、可选 headers 静态注入、可选 oauth: {} 触发 OAuth 自动协商。


type: local stdio 配置
local 模式是 OpenCode 接入本地工具的最短路径。最小化的 GitHub server 配置：


// opencode.json (项目根)
{
  "mcp": {
    "github": {
      "type": "local",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" },
    },
  },
}
    

  • command + args 等价于 shell 里手动跑 npx -y @modelcontextprotocol/server-github；OpenCode 启动 server 时直接 spawn 这个进程、stdin/stdout 走 MCP 协议。
    • 

  • env 里的 ${GITHUB_TOKEN} 会在 spawn 前从 OpenCode 自己的 env 里展开——这避免了把 token 字面值写进 JSON 文件 commit 进 git。
    • 

  • 默认 server enabled；如果需要临时关掉某个 server 而不删配置，加 "enabled": false。
    • 



local 模式不涉及任何授权握手——所有授权都通过 env 在子进程里现场解决。OpenCode 启动 / 重启时重新 spawn 子进程，token 不会持久化在 OpenCode 进程内。


type: remote Streamable HTTP 与 OAuth 流
remote 模式配置 server 的访问形式。最简单的"已经持有 API key、走静态 header"形式：


{
  "mcp": {
    "linear-remote": {
      "type": "remote",
      "url": "https://mcp.linear.app/sse",
      "headers": { "Authorization": "Bearer ${LINEAR_API_KEY}" },
    },
  },
}
headers 字段被 OpenCode 直接拼到每次 HTTP 请求里。${VAR} 展开规则与 env 一致，仍然从 OpenCode 进程的 env 拉值。


当 server 端要求 OAuth 2.1 + PKCE 而不是静态 token 时，把 headers 换成 oauth: {}：


{
  "mcp": {
    "notion": {
      "type": "remote",
      "url": "https://mcp.notion.com/mcp",
      "oauth": {},
    },
  },
}
oauth: {} 表示"按 spec 自动协商"——OpenCode 不需要手填 authorization endpoint，靠协议层的 discovery（401 → WWW-Authenticate → RFC 9728 protected resource metadata → authorization server metadata）现场拉。第一次使用前必须手动跑一次：


opencode mcp auth notion
这条命令触发完整 OAuth flow：


    

  1. OpenCode 在本地起一个临时回调监听端口（默认随机高位）。
    2. 

  2. 打开浏览器跳到 authorization server 的 consent UI、附带 PKCE code_challenge。
    3. 

  3. 用户同意后浏览器 redirect 到本地 callback、OpenCode 拿到 authorization code。
    4. 

  4. POST /token 用 code_verifier 换 access token + refresh token。
    5. 

  5. token 持久化到 ~/.config/opencode/（操作系统 keychain 优先、fallback 加密文件）。
    6. 



后续会话自动用 refresh token 续期，无需再跑 opencode mcp auth。


配置优先级与 admin managed
OpenCode 把"配置来源"做了显式四级，加载顺序明确——晚加载者覆盖早加载者：






优先级
来源
路径
典型用途





1（最低）
remote 组织配置
https://<org>/.well-known/opencode
公司统一推送 MCP server 清单




2
global 用户配置
~/.config/opencode/opencode.json
个人通用 server（GitHub、Slack）




3
custom env-pointed
OPENCODE_CONFIG=/path/to.json
CI / 临时切换配置




4（最高）
project 配置
<repo>/opencode.json
项目专用 server（项目数据库、特定 wiki）





合并规则是"按 key 深合并":相同 server 名后加载者整体替换前者；不同 server 名累加。一个例外是企业管理员通过 admin managed 配置（remote 组织配置里加 managed: true 标记的 server）锁定的项目，project 级覆盖会被忽略——这套机制让企业可以强制部署某些 server（如审计 logger、安全代理）而不被项目个人配置绕过。


admin managed: true 的 server 在最终生效列表里以企业配置版本为准、project / global 同名 server 被忽略；非 managed server 走标准覆盖语义。


最小可运行示例
把两类配置写成一份完整、最小、可直接跑的 opencode.json：


{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "filesystem": {
      "type": "local",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/projects"],
    },
    "notion": {
      "type": "remote",
      "url": "https://mcp.notion.com/mcp",
      "oauth": {},
    },
  },
}
跑通顺序：


    

  1. opencode mcp auth notion 完成 OAuth flow。
    2. 

  2. 启动 OpenCode 会话，agent 自动看到 filesystem 与 notion 两个 server 提供的 tool。
    3. 

  3. 在 OpenCode 内用 /mcp 命令（或对应的查看 server 状态命令）验证连接、必要时手动 disconnect/reconnect。
    4. 



把这份配置 commit 进 git 是安全的——oauth: {} 没有 secret、filesystem 没有 env、敏感 token 都通过 OpenCode 的本地 token store 持久化。


陷阱与常见问题
    

  • ${VAR} 展开为空：env 变量没设置时，OpenCode 展开为空字符串而不是报错，导致 server 启动失败但 error message 难定位。建议在 shell config 里显式设置 + 启动前 env | grep 验证。
    • 

  • 改完 opencode.json 不重启：正在运行的会话不读新配置，重启 OpenCode 才生效。详细见 ../3_reverse-mcp-and-pitfalls/2_pitfalls-and-tool-budget.md。
    • 

  • OAuth token 过期、refresh 失败：authorization server 把 refresh token 也失效后，会话突然报 401。手动重新跑 opencode mcp auth <name> 重新授权。
    • 

  • project 配置覆盖被 admin managed 阻挡：以为 project opencode.json 改了某 server 配置生效，实际被企业 managed 配置锁定。检查 .well-known/opencode 内容确认。
    • 

  • type: remote 没用 https：OpenCode 会拒绝 http URL（防御中间人）；如果是内网开发 server，搭一个反代或本地 TLS 证书。
    • 



小结
    

  • OpenCode mcp section 把协议 transport 直接映射为 type: local（stdio）与 type: remote（Streamable HTTP）。
    • 

  • local 模式用 command + args + env，${VAR} 展开避免 secret 入库。
    • 

  • remote 模式可选 oauth: {} 触发 OAuth 2.1 + PKCE 自动协商；首次需手动 opencode mcp auth <name>，token 存到 ~/.config/opencode/。
    • 

  • 配置四级优先级：remote 组织 → global → custom env → project，晚加载覆盖早加载，admin managed 锁定例外。
    • 

  • 把 OAuth oauth: {} 配置 commit 进 git 安全，敏感 token 在本地 token store。
    •
