Codex CLI 的 MCP 配置：TOML、三种 transport 与 tools 字段

OpenAI Codex CLI 是 2025 年初推出、2025-2026 持续迭代的官方编程代理，配置面与 OpenCode / Claude Code 都不一样——文件格式是 TOML 而不是 JSON、配置位置只接受 user 级、引入了 tools 字段做精细的 allowlist / rename，企业部署还能用 requirements.toml 强制 admin override。本节按"文件位置 → transport 三型 → tools 字段三种语义 → 企业管控"四块讲清，重点是 tools 字段——它是 2026 上半年解决"多 server 同名 tool 冲突"最干净的方案，但在其他两款工具里都没有等价物。

核心概念

Codex 把 MCP server 配置写在 ~/.codex/config.toml 的 [mcp_servers.<id>] table 下，每个 server 一段：

[mcp_servers.github]
type = "stdio"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-github"]

[mcp_servers.linear]
type = "streamable-http"
url = "https://mcp.linear.app/mcp"

<id> 是 client 端 server 标识，跨 server 必须唯一；type 是协议 transport（三选一）；剩余字段按 transport 类型不同而不同。config.toml 默认只读 user 级文件——出于 untrusted-projects 安全策略，Codex 默认不读项目里的 .codex/config.toml（这点与 OpenCode / Claude Code 不同），需要 user 级显式 opt-in。

维度 Codex 行为 与 OpenCode 对比 与 Claude Code 对比
文件位置 ~/.codex/config.toml user 级 多级合并，project 级最高 .mcp.json project + ~/.claude.json user
文件格式 TOML JSON JSON
项目级配置 默认禁用 默认启用 默认启用
tool 过滤 tools 字段精细 allowlist/rename 无内置 无内置（靠 hook）

三种 transport：stdio、streamable-http、sse

type = "stdio"：本地子进程模型，与 OpenCode type: local 等价。最小例子：


[mcp_servers.fs]
type = "stdio"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/work"]

[mcp_servers.fs.env]
NODE_OPTIONS = "--max-old-space-size=4096"
env 用单独的 sub-table 写、不是 inline map（TOML 习惯），${VAR} 展开规则与其他工具类似。


type = "streamable-http"：2025-11 spec 单 endpoint Streamable HTTP，是 2026 上半年新部署 server 的默认选项：


[mcp_servers.linear]
type = "streamable-http"
url = "https://mcp.linear.app/mcp"

[mcp_servers.linear.oauth]
# 空 table 触发自动协商，等价于 OpenCode 的 oauth: {}
OAuth 触发后第一次会话 Codex 会打开浏览器跳转授权、token 写到 ~/.codex/auth/。


type = "sse"：旧版 SSE+POST 双 endpoint 协议（2025-03 spec）。spec 在 2025-06-18 标记 deprecated、2025-11 spec 推荐回退算法兼容；Codex 仍然保留这个选项是为了兼容 2025 年初的 server。新接入不应使用——文档明确建议优先 streamable-http，旧 server 会自动通过 4xx 回退路径 fallback。


tools 字段：allowlist、blocklist、rename
这是 Codex 最值得单独讲一节的设计。一个 MCP server 通常暴露十几到几十个 tool，但具体场景里 agent 只需要其中几个；多 server 并存时还会出现同名 tool 冲突。Codex tools 字段三种语义解决这两类问题：


# 1. allowlist：只暴露指定 tool
[mcp_servers.github]
type = "stdio"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-github"]
tools = ["create_issue", "list_issues", "create_pull_request"]

# 2. blocklist：暴露除了指定 tool 之外的所有
[mcp_servers.notion]
type = "streamable-http"
url = "https://mcp.notion.com/mcp"

[mcp_servers.notion.tools]
exclude = ["delete_page", "archive_page"]

# 3. rename：重命名 tool 解决冲突
[mcp_servers.gitlab]
type = "stdio"
command = "gitlab-mcp"

[mcp_servers.gitlab.tools]
rename = { create_issue = "gitlab_create_issue", list_repos = "gitlab_list_repos" }
三种语义可以叠加：先 exclude 过滤、再 rename 调整剩余 tool 名。语义优先级是 allowlist 严格——一旦写了 tools = [...] 数组形式，未列出的 tool 一律不暴露。


工程价值在三处：


    

  • 缩小 tool budget：agent context 里的 tool description 越多、模型抓重点越差，2026 主流建议保留 5-6 个常用 tool。allowlist 是从 server 角度做精简的最干净姿势。
    • 

  • 避免 prompt-injection：高危 tool（delete_*、exec_command）用 blocklist 主动屏蔽，留下回滚空间。
    • 

  • 解决跨 server 命名冲突：GitHub server 和 GitLab server 都有 create_issue、list_repos，模型在调用时分不清。rename 加 server 前缀（gitlab_create_issue）让模型推理更明确。
    • 



企业管控：requirements.toml
Codex 2026 上半年新增 requirements.toml 机制，让企业管理员在用户 config.toml 之外强制覆盖关键配置。文件位置由企业部署脚本决定（典型放在 /etc/codex/requirements.toml 或环境变量指向的路径）；Codex 启动时先读 requirements.toml、后读 config.toml，相同字段以前者为准。


# /etc/codex/requirements.toml（企业管理员部署）
[mcp_servers.audit_logger]
type = "streamable-http"
url = "https://audit.corp.example.com/mcp"
required = true  # 用户禁用不生效，必须连接

[mcp_servers.github]
# 强制把 github server 切到企业自建网关
type = "streamable-http"
url = "https://github-mcp-gateway.corp.example.com/mcp"
required = true 让 server 即使用户在 config.toml 里写了 enabled = false 也强制启用——典型场景是企业审计 logger、合规拦截器。这与 OpenCode admin managed: true 的设计目标一致，只是落地形式不同。


最小可运行配置
把上面元素拼到一份完整 ~/.codex/config.toml：


[mcp_servers.fs]
type = "stdio"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/work"]
tools = ["read_file", "list_directory", "search_files"]

[mcp_servers.linear]
type = "streamable-http"
url = "https://mcp.linear.app/mcp"

[mcp_servers.linear.oauth]

[mcp_servers.linear.tools]
exclude = ["delete_issue", "delete_project"]
跑通顺序：


    

  1. codex mcp auth linear（与 OpenCode 类似的 CLI 子命令）完成 OAuth。
    2. 

  2. 启动 Codex 会话，看到 fs 暴露 3 个文件 tool、linear 暴露 issue/project tool 但删除类被屏蔽。
    3. 

  3. /mcp status 或等价命令查看连接健康。
    4. 



陷阱与常见问题
    

  • 写到 .codex/config.toml 项目级被忽略：默认 untrusted-projects 策略不读项目级配置，必须放 ~/.codex/config.toml。
    • 

  • TOML 语法错误整段失效：JSON 写错通常报具体行号，TOML 表 / inline table 混用错误信息晦涩。建议先 toml-cli validate 一遍。
    • 

  • tools = [] 空数组当成 allowlist 全屏蔽：写空数组等于"什么都不暴露"，意图模糊时用 tools.exclude 显式表达。
    • 

  • rename 之后旧 tool 名仍出现：rename 是 client 端层级，server 自己 prompt template 引用了旧名时仍可能从 prompt 通道触发。审慎评估。
    • 

  • requirements.toml 路径配错：企业部署写错路径，强制配置静默失效。Codex 启动时应有日志确认 requirements.toml 加载状态。
    • 



小结
    

  • Codex 用 ~/.codex/config.toml 的 [mcp_servers.<id>] table 注册 server，默认不读项目级 .codex/。
    • 

  • transport 三型：stdio、streamable-http（推荐）、sse（deprecated 仅兼容旧 server）。
    • 

  • tools 字段三种语义：allowlist 数组、exclude blocklist、rename map，解决 tool 数量过多与跨 server 同名冲突。
    • 

  • 企业 requirements.toml 强制覆盖 user 配置，required = true 让 server 用户禁用无效——审计 logger / 合规拦截器的典型部署形式。
    • 

  • 配置面与 OpenCode / Claude Code 的差异点主要在三处：TOML vs JSON、user-only vs multi-level、tools 字段 vs 无内置过滤。
    •
