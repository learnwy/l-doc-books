命令的发现路径与调用模式

合并完成后，三款工具都按"扫描多路径 → 合并去重 → description 入 context → 匹配后注入 body"的统一流程处理命令。但具体扫描哪些目录、按什么优先级合并、什么时候 model 自动激活、什么时候必须 user explicit，每家细节差很大。理解这套机制能直接解释一类高频问题：为什么我写的命令在某个工具里就是不出现、为什么 description 写得很完整 model 却不主动用、为什么两个团队成员同名命令调出不同的逻辑。

核心概念

下表把三款工具在 2026 Q2 的发现路径与调用机制汇总成一张对照表。

工具 主要发现路径 兼容/扩展路径 调用模式 implicit 触发依据
Claude Code .claude/skills/<name>/SKILL.md .claude/commands/<name>.md（legacy） explicit /name 为主，部分 skill 支持 implicit description 关键词匹配
Codex .agents/skills/<name>/SKILL.md（walk-up） .codex/commands/<name>.md（deprecated） implicit + explicit 双轨 description + openai.yaml invocation policy
OpenCode .opencode/skills/<name>/SKILL.md .opencode/commands/ + .agents/skills/ + .claude/skills/ explicit /name，plugin 可触发 implicit plugin instructions provider

下图展示 session start 时三款工具加载命令到 context 的统一流程。

跨工具发现路径机制
三款工具的扫描策略差异很大，主要体现在两点：扫描根目录与walk-up 行为。


Claude Code 只扫描两条路径：<cwd>/.claude/commands/ 与 <cwd>/.claude/skills/。不向父目录走、不向用户主目录走（用户级 skill 走 ~/.claude/skills/，但是单独配置不混入 project 扫描）。这种"严格当前项目"策略对单仓库项目很清晰，但 monorepo 里子项目想共享父级命令需要软链或复制。


Codex 走 walk-up：从 cwd 一路向上找直到 git repo root（或文件系统根），途中每一层只要存在 .agents/skills/ 就纳入扫描。这让 monorepo 的 packages/foo/、packages/bar/ 都能共享根目录的 .agents/skills/，无需复制。但 walk-up 也带来安全风险——untrusted-projects 策略默认禁止读 project 级 .codex/，因为父目录可能藏恶意命令文件。


OpenCode 同时扫四路径：.opencode/skills/（项目专属）+ .agents/skills/（中性，跨工具共享）+ .claude/skills/（直接复用 Claude 项目）+ .opencode/commands/（legacy）。合并去重时按 plugin > project > user > legacy 顺序——同名时插件捆绑的 skill 优先，避免用户随便复制覆盖团队基建。


implicit 与 explicit 调用的本质差异
调用模式决定了命令"什么时候被激活"。


explicit 调用是 user 主动输入 /cmd-name args（Claude / OpenCode）或 $skill-name（Codex）。这是最早的调用方式，特点是确定性强、可预期、不依赖 description 写得好不好。代价是 user 必须记住命令名、参数顺序、前缀语法。


implicit 调用是 model 在每轮 chat 时读 description，发现 user prompt 关键词匹配某个 skill 就自动激活——"帮我审一下这个 PR" 自动激活 pr-review skill，"把这段 TS 类型简化下" 自动激活 ts-refactor skill。这种调用的好处是 user 不需要记命令名、自然语言流畅，坏处是匹配不准时 model 会激活错误的 skill（或漏激活该激活的 skill）。


Codex 在这两条线之间引入了第三种 hybrid 模式：openai.yaml 的 invocation_policy: hybrid 表示该 skill 在 user explicit 时优先、未 explicit 时也允许 model implicit 触发。这让安全敏感命令可以走 manual 模式（必须 explicit），高频自然语言任务走 auto 模式（implicit 优先）。


下面这段 frontmatter 示例展示 description 关键词如何决定 implicit 匹配。


---
name: ts-refactor-simplify
description: 简化 TypeScript 类型 / 用 mapped types 或 conditional types
  重构复杂的接口定义。触发：TS 类型太复杂 / 想用 utility
  types 重写 / 想抽 generic 共用。
allowed-tools: [Read, Edit, Bash(tsc:*)]
model: claude-opus-4-7-20260423
---
关键词"TypeScript 类型 / mapped types / conditional types / utility types / generic"被 model 看到后，"帮我把 UserPreferences 这个接口拆成 generic" 这种 prompt 会触发 implicit 激活。description 写得越具体、关键词越多，implicit 匹配越准。


description budget 与截断机制
合并后的所有 skill 的 name + description 都要装进 session start 的 system prompt，但 context window 有限。Anthropic 给的硬约束是 description budget 占 context window 1%——200K context 下大约 2000 token 给所有 description 共享。超出时按 8000 char fallback 截断（按字母序从尾部砍）。


这条约束直接决定两件事。


第一是命令总数有上限：description 平均 100 token 时，2000 token 装得下 20 个；想要装 50 个就必须把每条 description 压到 40 token 以下。压得太死会让 implicit 匹配失败——关键词不够、model 看不见适用场景。社区建议是控制 active skill 在 30 以下，临时启用的 skill 用 disable-model-invocation: true 保留文件但不入 budget。


第二是 description 写得不准 = skill 永不被调用：description 截断后丢失关键词，model 无法 implicit 匹配；user 用 explicit /cmd-name 还能调到，但 implicit 路径完全失效。修复方式是把高优先级关键词放在 description 前半部分——不要把"触发：xxx"放最后，要放最前。


命名空间在发现机制里的作用
Claude Code 不支持目录式 namespace——.claude/skills/refactor/rename/SKILL.md 这种二级目录会被忽略，只识别 .claude/skills/<single-name>/SKILL.md。社区惯例是用 - 分隔 namespace 与命令名，目录写成 .claude/skills/refactor-rename-pattern/SKILL.md，name frontmatter 字段写 refactor-rename-pattern，user 调用 /refactor-rename-pattern。这种扁平 + 前缀的方式跟 npm 包命名相似。


Codex 与 OpenCode 都支持目录嵌套但行为略不同：Codex .agents/skills/<group>/<name>/SKILL.md 自动把目录前缀作为 namespace；OpenCode 必须在 plugin manifest 显式声明 namespace 而不是从目录推断。


具体 namespacing 策略详见 ../3_patterns-and-pitfalls/2_namespacing-and-best-practices.md。


陷阱与常见问题
第一是 walk-up 扫描"找错父目录"：Codex 在不是 git 仓库的目录运行时 walk-up 会一直走到文件系统根，途中可能扫到不期望的 .agents/skills/（比如 ~/projects/ 共享目录）。修复是给项目根放个 .git 占位文件或显式设 CODEX_PROJECT_ROOT 环境变量。


第二是 budget 截断悄无声息：超 budget 后被截掉的 skill 不会报错、不会出现在 /skills 列表，user 完全感知不到为什么命令"消失"。调试时跑 claude code --debug-skills 看 system prompt 里到底装了哪些 skill。


第三是 implicit 匹配命中"错误的 skill"：两个 skill 关键词重叠（比如 ts-refactor 与 js-refactor 都包含"重构"），model 在 "重构这段代码" 时可能激活错的那一个。修复是 description 里加更精确的限定（"仅 TypeScript / 不处理 JavaScript"），或者把高优先级命令 pin 在 description 前半。


第四是新增 skill 不立即生效：Claude Code session 已经启动时新加 SKILL.md 不会自动发现，要 /clear 或重启 session。OpenCode 的 plugin-bundled skill 是热加载的，但项目级 .opencode/skills/ 也需要重启。


小结
    

  • Claude Code 严格只扫 cwd 的 .claude/；Codex walk-up 到 repo root；OpenCode 四路径合并
    • 

  • explicit /name 始终可用，implicit 由 description 关键词匹配触发，Codex invocation_policy 控制是否允许 implicit
    • 

  • description budget 占 context 1%（约 2000 token / 8000 char），超量按字母序截尾，被砍的 skill implicit 完全失效
    • 

  • 命名空间靠 - 前缀扁平表达，Claude 不识别目录嵌套，详细模式见 ../3_patterns-and-pitfalls/2_namespacing-and-best-practices.md
    • 

  • 调试发现问题的最有效手段是 --debug-skills 看实际加载列表，比看文档脑补强
