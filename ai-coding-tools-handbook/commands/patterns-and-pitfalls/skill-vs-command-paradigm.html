范式决策：skill-derived 命令还是 standalone .md 命令

合并完成后团队最常问的问题不是"怎么写"，而是"我这条命令到底该写成 skill-derived 还是继续用 standalone .md"。这个决策表面看是格式偏好，实际上影响 token 经济、跨工具 portability、维护成本三条独立的线。本篇把两种范式的本质差异讲透，再给一套五条线的决策框架，最后讲清楚迁移路径与回滚策略——所有结论都对应 2026 Q2 三家工具实际行为。

核心概念

下表把两种范式的关键属性正交列出。

属性 standalone .md（legacy commands） skill-derived
文件结构 单个 .md 目录 + SKILL.md + 可选 references/ scripts/
context 加载方式 v2.1.101 前全量入 context，之后随合并也 description-first description-first（progressive disclosure）
多文件组织 不支持 支持（split prompt/examples/scripts）
frontmatter 表达力 少（description / arguments / model / tools） 多（+ allowed-tools / disable-model-invocation / argument-hint / context: fork 等）
跨工具 portability 不可移植 三家工具直接复用
review 难度 容易（单文件 diff） 容易（frontmatter 字段标准化）
适合场景 简单 prompt template、跨项目不复用 复杂工作流、团队规模化、跨工具复用

两种范式的本质差异
最容易被误解的一点：v2.1.101 之后 standalone .md 也支持 description-first 加载，那为什么还要费力迁移成 skill？


答案是多文件组织能力。skill 不只是 SKILL.md 单文件——目录里可以放：


    

  • references/：长文档（最佳实践、错误码表、API 详情），只在 SKILL.md 内显式 reference 时按需读
    • 

  • scripts/：可执行脚本（部署脚本、迁移工具），通过 !script-name 触发
    • 

  • examples/：完整示例项目结构，调试时给 model 看
    • 



standalone .md 把所有内容压在一个文件里，复杂工作流要么塞爆单文件（5000 行 prompt 模板不可读），要么砍掉细节降低准确率。skill 形态用 references 单独存长文档，SKILL.md 保持 200 行以内可读，model 在需要细节时按 reference 读特定文件——既保 quality 又省 token。


第二个差异是 frontmatter 表达力。standalone .md 没有 allowed-tools 细粒度白名单，安全敏感命令（执行 git push、调 production API）无法限定只能调哪些 bash 子命令；skill 形态用 allowed-tools: [Bash(git push:*)] 锁死。standalone 也没有 context: fork——产生大量中间输出的命令会污染主 chat 历史；skill 在 fork context 里跑完只回传结果。


五条线的决策框架
落地决策时按下面五条线快速判断：


五条线展开：


第一线 调用频率：每周调多次的命令，description 持续占 budget；用 skill 省每个 session 的累积成本。每月一次的命令哪种范式都行。


第二线 跨工具 portability：团队同时用 Claude + Codex 时必须 skill-derived，standalone .md 不可移植。即使现在只用一家，未来切换工具的可能性也建议 skill。


第三线 命令复杂度：超过 200 行 prompt 模板的命令建议拆成 SKILL.md + references/；带可执行脚本的必须 skill（standalone 不支持 scripts/）。


第四线 review 流程：团队对命令变更走 PR review 时 skill 的 frontmatter 标准字段更易 review—— reviewer 一眼看出 model 是否 pin、tools 是否限制、是否禁 implicit；standalone 字段非标 review 时容易漏。


第五线 安全敏感度：执行写操作、调外部 API、操作 git 历史的命令建议 skill——allowed-tools 细粒度白名单 + disable-model-invocation 禁 implicit + context: fork 隔离，三道防线 standalone 都做不到。


迁移路径：standalone .md → skill-derived
迁移老命令时按下面步骤走。


第一步 frontmatter 字段映射：


# 原 .claude/commands/review.md
---
description: 审阅指定 git ref 的所有 diff
arguments: <git-ref>
model: claude-opus
---
# 新 .claude/skills/review/SKILL.md
---
name: review
description: 审阅指定 git ref 的所有 diff，可选 focus 维度（security/perf/style）
argument-hint: <git-ref> [focus]
allowed-tools: [Read, Bash(git diff:*), Bash(git log:*)]
model: claude-opus-4-7-20260423
disable-model-invocation: false
---
注意 arguments 改成 argument-hint、model 从 alias 换成完整版本号、description 加更多触发关键词、新增 allowed-tools 细粒度白名单。


第二步 参数语法替换：body 内 $ARGUMENTS 一律换 $@ 或具体 $1 $2，注意单变量到多参数的语义差异。


第三步 提取 references：超过 200 行的 prompt body 把长段落（错误码表、最佳实践、详细示例）抽到 references/<topic>.md，SKILL.md 用 详见 references/error-codes.md 引导 model 按需读。


第四步 保留旧文件作 fallback：迁移期间 .claude/commands/review.md 改名为 .claude/commands/review.legacy.md 保留，新 skill 跑通后再删旧文件；同名时 skill 优先所以不冲突。


第五步 A/B 验证 description：让两个团队成员一个用新 skill 一个用 standalone 跑一周，观察 implicit 匹配率（说"帮我审这个 PR"时多少次自动激活）。description 关键词不准时迭代调整。


回滚策略
skill 表现不符预期时不要急着删，按下面顺序退：


    

  • 轻症（implicit 误触发）：frontmatter 加 disable-model-invocation: true 临时禁 implicit，user 仍可 explicit /cmd-name 调用，观察 standalone 模式是否符合预期
    • 

  • 中症（行为漂移）：改 skill 目录名加 .disabled 后缀（如 review.disabled/），发现路径扫不到，恢复 legacy .claude/commands/review.md 作为唯一入口
    • 

  • 重症（架构问题）：彻底回退到 standalone .md，把 skill 目录 git rm，团队复盘 description 关键词与 allowed-tools 配置
    • 



回滚不丢工作——skill 目录与 legacy .md 是两套独立文件，互不影响。这种"双轨保留"是合并范式的核心优势：可逆。


陷阱与常见问题
第一是过早全员迁移：团队 30 个命令一周内全部从 standalone 改 skill，结果出现行为漂移调试困难。建议按频率从高到低分批迁，每批 3 ~ 5 个，每批跑两周观察后再下一批。


第二是迁移后忘删 legacy：skill 已经跑通但 legacy .claude/commands/foo.md 留着没删，未来某天 skill 被改名时 legacy "重新生效"产生意外行为。迁移完成后明确 git rm legacy 文件。


第三是 description 写不全 implicit 永不命中：迁移后 description 直接抄旧 description 字段一行话，缺少触发关键词；user 自然语言里说"审 PR"但 description 写"审阅 git ref" model 看不出关联。迁移时 description 至少加 3 ~ 5 个常见触发表述。


第四是 model alias 漂移：旧命令写 model: claude-opus 在 2025 漂到 v4.5、2026 漂到 v4.7，行为悄无声息地变了。迁移时一律 pin 完整版本号 claude-opus-4-7-20260423。


小结
    

  • skill-derived 与 standalone .md 本质差异在多文件组织 + frontmatter 表达力，token 经济在 v2.1.101 后已经追平
    • 

  • 五条线决策：调用频率 / 跨工具 / 复杂度 / review / 安全敏感度——任一条偏 skill 即建议迁
    • 

  • 迁移按"字段映射 → 参数语法 → 提取 references → 保 legacy 作 fallback → A/B 验证"五步走
    • 

  • 回滚分轻中重三档：disable-model-invocation → 改名 .disabled → git rm 重写
    • 

  • 跟 namespacing / model pin / 安全审计配合见下一篇 ./2_namespacing-and-best-practices.md
    • 

  • 跨工具 portable 写法的字段映射详见 ../../3_skills/3_cross-tool-interop/
    •
