命令实践范式与陷阱 简介

读完合并架构与三家实现之后，本章收尾两类实战话题：第一类是范式决策——同样一个工作流，写成 skill-derived 命令还是 standalone .md 命令？这不是单纯偏好问题，影响 token 经济、跨工具 portability、维护成本三条线。第二类是规模化实践——团队几十个命令时怎么命名、怎么 pin model 版本、怎么把 slash command 当成"会花钱的资源"管理而非"免费快捷键"用。两篇 L4 都附 2026 实战案例。

本章包含两篇 L4 文档。

1_skill-vs-command-paradigm.md —— 范式决策框架。第一块讲两种范式的本质差异——skill-derived（progressive disclosure，session 初只载 name + description，匹配后才注入 body，省 token）vs standalone .md legacy（命令 body 在 session start 全部装入 context，每次会话都付费）。第二块讲决策框架五条线——命令调用频率（高频用 skill-derived 省持续 token）、跨工具 portability 需求（必须 skill-derived）、命令复杂度（复杂工作流用 skill 的多文件 + scripts）、团队 review 流程（skill 的 frontmatter 更易 review）、安全敏感度（skill 的 allowed-tools + disable-model-invocation 表达力强）。第三块讲迁移路径——从 .claude/commands/<name>.md 到 .claude/skills/<name>/SKILL.md 的字段映射、保留旧路径作为 fallback、A/B 验证 description 匹配率。第四块讲回滚策略——skill 加载行为不符合预期时如何快速 disable（disable-model-invocation: true 临时禁、改名后重新观察）。

2_namespacing-and-best-practices.md —— 规模化实践。第一块讲 namespacing 模式：扁平结构在 20 个命令以上变得难发现，建议按动作分组 /refactor/rename-pattern / /test/add-edge-cases / /db/migration-draft；目录结构 .claude/skills/refactor-rename-pattern/SKILL.md 通过 name 字段表达。第二块讲 model 版本 pin——critical 命令应该 pin 具体 model（claude-opus-4-7-20260423 这种），避免 Anthropic 默认 model 切换后 silent drift；Codex openai.yaml 同理 model_pin: "gpt-5.5-20260205"。第三块讲 计费认知——slash command 不是免费 hotkey，每次调用消耗 token；description 在 session start 始终入 context，太多 skill 会让 description budget 撑爆。第四块讲 安全审计——2026 已发现公开 skill registry（如 ClawHub）投毒事件、SKILL.md 内可执行 !command 与 scripts/ 可任意执行代码；公开 skill 安装前必 review、第三方 plugin 按 npm 包风险等级处理；附 2026 advisory 入口 agentskills.io/advisory。

学习建议是按章节顺序读完即可。运行中的团队建议把第 2 篇直接搬到内部 wiki 作为命令维护规范——尤其 namespacing 与 model pin 两条，越早立规越能避免后期重构。
