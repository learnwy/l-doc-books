跨行业 use case 综述：五类 cross-industry pattern

从上一篇 1_industry-scenarios-link-index.md 索引的几十个 source 出发，提炼出五类 cross-industry pattern：CI 自动化、代码审查、大型 refactor 协同、文档自动生成、客户回报循环。每个 pattern 给「哪些行业最先采用 / 哪些工具最适合 / 实施门槛与 ROI 区间」三轴判断，附 2026 典型案例描述。本文不引用具体 URL——所有判断都建立在公开 source 的"共识 / 多次出现 / 跨厂商一致"基础上，单一 source 的断言不收录。

核心概念

把五类 pattern 与八个行业放在二维矩阵里能直观看出渗透度差异。下图展示「行业 × pattern」的采用早晚关系——越靠左的行业越早采用某 pattern，越靠右的越晚。这不是完整真值表，而是 source 索引读出的相对印象。

读这张图的方式是：左侧节点是 pattern，右侧从左到右是采用先后顺序。比如「CI 自动化」最早是 DevOps 行业先行，最晚到达医疗 / 游戏 / 嵌入式。


Pattern 1：CI 自动化
形态：PR 自动 review（agent 跑 review 后 comment）、commit message 自动生成、lint / format auto-fix 集成、release notes 草稿生成、failing test 自动定位与建议修复。本质是把 CI 流水线中"机械且有客观正确性"的步骤交给 agent。


哪些行业最先采用：DevOps & SRE 是绝对先行者——他们日常就在调 CI，对 agent 在 CI 里跑没有心理障碍；Web 后端紧随其后，因为 PR 数量大、单次 review 成本高；安全 / 金融跟进但加上"agent 输出需经人复核"约束；Mobile / Data 在 build 时长与 SQL 验证两个 friction 下进度慢一些；医疗 / 游戏 / 嵌入式最慢，前者是合规、后者是工具链碎片化。


哪些工具最适合：Claude Code 的 Hooks + Skills 组合最全——可以在 pre-commit / pre-push / on-pr-open 多个阶段挂入 agent；Codex Cloud 的"长任务 batch 模式"最强——一次提交后台跑几十个 PR review 然后回汇总；OpenCode 的 plugin 系统最灵活，适合需要深度定制 CI 集成的团队。GitHub Copilot 的 PR-level workflow 在 GitHub Actions 原生集成度上有优势。


门槛与 ROI 区间：实施门槛低——一个 well-configured .github/workflows/*.yml + 一个 Claude Code skill 就能上线 80% 价值；ROI 中高——典型公开 case 报告「PR review 时间下降 30%-60%、人工 review pass rate 上升」，但实际 ROI 与 PR 数量正相关，月 100 PR 以下的小团队 ROI 不显著。


2026 典型案例描述：某中型 SaaS 团队（约 150 工程师）在 2026 Q1 全量铺开 PR 自动 review + commit message 自动生成；六个月数据显示 review 平均 latency 从 8 小时下降到 2 小时，但 false positive comment 仍有约 15%，需要 reviewer 二次过滤。Anthropic 与 OpenAI 官方 case 中类似数据出现多次。


Pattern 2：代码审查（security review + architecture review）
形态：security review skill（专门审 OWASP Top 10、secret 泄露、CVE 已知模式）、architecture review subagent（审 layering / coupling / 命名一致性）、license / dependency 审查、accessibility 审查。与 Pattern 1 的区别是这一类审查需要更深的 domain 知识与 multi-file context。


哪些行业最先采用：安全行业天然领先——把 SAST 工具能力扩展到 LLM 上是顺势而为；金融跟进快，合规审计需求强；Web 后端中等，主要用 architecture review 控制 monorepo 腐化；DevOps / Mobile 用得选择性；Data 用得少（SQL 审查需要 schema 上下文，门槛高）；医疗 / 游戏 / 嵌入式样本稀少。


哪些工具最适合：Claude Code 的 Subagents + security-review skill 是当前最完整的方案——Subagent 提供独立 context，避免审查噪声污染主流；Codex Cloud 适合 batch 审查历史 PR；OpenCode 的 multi-agent 能力适合需要"多视角并行审查"（security + architecture + a11y 同时跑）的团队。


门槛与 ROI 区间：门槛中等——需要团队预先制定「审查标准 = prompt + checklist」并维护；ROI 高但隐性——找到 1 个 high-severity 漏洞的价值远超日常 review 的累积价值，但难量化。多数 case 用「avoided incidents」估算 ROI，方法学有争议。


2026 典型案例描述：某 fintech 公司将 security-review skill 接入 PR 流水线后，发现两个 secret 泄露与一个 SQL injection 风险（上线 4 个月内）。同期 architecture review subagent 帮助标记了 30+ 处违反公司 layering 规则的 commit，由 reviewer 决定是否合并。


Pattern 3：大型 refactor 协同
形态：1M context 一次性吞整个 module 做重构（适合中大型 monorepo）、Agent Teams 多 agent 协调（一个 agent 改 schema、另一个改 API、第三个改 client）、framework major version 升级（如 React 18→19 / Rails 7→8）、language migration（如 JS→TS / Python 2→3 残留）。


哪些行业最先采用：Web 后端 monorepo 是最早场景——Rails / Django / Next.js 大 monorepo 升级痛点强；Mobile monorepo（RN / Flutter / Lynx 跨平台或多 app 复用 module）跟进快；游戏 engine code base 大、coupling 高，refactor 协同价值显著；Data / DevOps / 安全的 refactor 多以「IaC / schema 迁移」形式存在；金融 / 医疗最谨慎——refactor 频率低但单次价值高。


哪些工具最适合：Claude Code 的 1M context（Sonnet 4 系列）+ Subagents 是当前唯一能"一次性吞 monorepo 一个 sub-tree + 多 agent 协同"的方案；Codex Cloud 在「长任务 batch refactor」上有 ergonomics 优势——提交后离开几小时回来看 PR；Cursor 的 indexing 在 IDE 内交互式 refactor 上更顺手，但缺少 agent 协同。


门槛与 ROI 区间：门槛高——需要团队对 agent output 有较强的 review 能力，否则 agent 改坏的代码引入隐性 bug 成本极高；ROI 极端两极——成功 case 节省人月，失败 case 引入数月的 debugging。建议初期用「agent 提议 + 人工 apply」模式，再逐步给更多自主权。


2026 典型案例描述：某大型 mobile 团队（RN + 原生混合）在 2026 Q1 用 Claude Code Subagents 协同完成了 React Native 0.72→0.78 的全量升级，涉及 800+ 文件；agent 自动生成的 PR 中 70% 一次通过 review，30% 需要 reviewer 调整。同期一个 web SaaS 团队用类似方案做 Rails 7→8 升级失败，原因是 test coverage 不足导致 agent 改坏的逻辑没被 CI 捕获。


Pattern 4：文档自动生成
形态：API 文档（从代码注释 + 调用 site 反推）、changelog（从 commit 与 PR 描述合成）、runbook（从 oncall ticket 与 incident 复盘合成）、onboarding doc（从 code base + git log 合成）、内部知识库自动 update。


哪些行业最先采用：所有行业都用，但 quality 差异大。Web 后端 / DevOps / 安全 quality 最稳定——他们的 code 本身规范度高、注释多；Data / 金融 quality 中等——业务术语多、agent 容易误译；Mobile / 游戏 / 嵌入式 / 医疗 quality 最不稳——平台特定术语 + 引擎 / 硬件细节 agent 容易 confabulate。


哪些工具最适合：所有主流工具都能做基本 docs 生成；区别在于「是否 enforce link 回 source code 行号、是否 enforce 引用准确」。Claude Code 的 Skills + Hooks 可以强制「output 必须 cite line range」；Codex 在 cloud 模式下生成的 doc 通常更长但准确性需手工抽检；Cursor 在 IDE 内边写边生 doc 体验最顺。


门槛与 ROI 区间：门槛低——一个 prompt 就能起步；ROI 隐性——节省的人时多但单次价值小，累积起来很可观。最大风险是「agent 生成的 doc 不准但读者不知道」——doc 一旦上线，错误信息扩散后纠正成本高。


2026 典型案例描述：多数公开 case 不再单独写"用 AI 生成 doc"——它已成为基础 workflow 的一部分，类似几年前的 prettier / eslint。新出现的 pattern 是「agent 主动检测代码与 doc 不一致并提 PR 修 doc」，部分团队公开过这类自动化数据，但样本仍小。


Pattern 5：客户回报循环（agent observe production → file PR）
形态：agent 监听 production 日志 / 错误率 / latency 异常 → 自动定位涉及代码 → 生成 PR 提交修复或 mitigation。这是上述四类 pattern 之上的"闭环"——把 agent 从「写代码」推进到「写代码 + 观测代码 + 改代码」。


哪些行业最先采用：早期采用者集中在 Web SaaS——他们 telemetry 全、PR 周期短、风险可控；DevOps / 安全工具厂商跟进，他们做 observability / SAST 工具时顺势把 agent 接进来；Mobile SaaS 中等，因为 mobile telemetry 与代码距离更远；金融 / 医疗 / 游戏 / 嵌入式几乎没有公开 case——前者合规、后者闭源 / 工具链碎片。


哪些工具最适合：Claude Code 的 Hooks + Background Tasks + Skills 组合是当前最完整方案——Hooks 接 alert，Background Tasks 异步分析，Skills 生成 PR；Codex Cloud 的"长任务 batch + scheduled"配合 webhook 也可以；OpenCode 的 plugin 系统对接 observability 平台更直接。


门槛与 ROI 区间：门槛极高——需要团队同时具备 observability 成熟度、telemetry quality、agent 自动 PR 信任度三件事；ROI 区间极宽——成熟团队能做到「typical incident 30 分钟内有 mitigation PR」，不成熟团队会被 agent 自动 PR 淹没噪声。建议从「agent 只 comment 不 PR」起步。


2026 典型案例描述：少数 Web SaaS 公开过早期实验——agent 监听 Sentry / Datadog alert，自动定位代码并生成 PR；六个月数据显示约 30% 的 PR 直接合并，40% 需要人工修改后合并，30% 被驳回。Anthropic / OpenAI 官方 case 中类似实践仍稀少，多以"Future Direction"提及。

综合判断与展望
把五类 pattern 与八个行业组合起来读，能看出 2026 年 AI coding agent 在产业渗透中的几个共性规律。第一，telemetry 成熟度决定了 agent 价值上限——没 observability 的团队最多用到 Pattern 1-2，Pattern 5 完全不可达。第二，code review 文化决定了门槛——已有强 review 文化的团队能更快接受 agent 输出（因为团队习惯 "提议 + 审查"），review 文化弱的团队反而风险更高。第三，合规与监管会持续把医疗 / 金融 / 安全的 Pattern 3 / 5 推迟，但同时给 Pattern 2 加速——这是 regulated 行业的特征。


读完本综述后建议：选型阶段回到 1_industry-scenarios-link-index.md 找自己行业的具体 source 深读；实施阶段参考 ../1_team-specs/ 章节看 CLAUDE.md / Skills / Subagents 怎么写；ops 阶段参考 ../3_observability/ 章节看 telemetry 与监控怎么配。
