多 agent 模式与防递归 简介

理解了三家具体实现之后，本章把"什么时候用哪种多 agent 模式"与"怎么防递归"两件事讲清。前者是实战决策——不是所有任务都该上 Agent Teams、subagent 也不是越多越好；后者是工程纪律——多 agent 系统一旦放任不管，很容易出现"agent A 调 agent B 调 agent A"的死锁或无限递归，特别是 Tier 1 / Tier 2 反向 MCP 编排场景。两篇 L4 都附 2026 实战决策框架与可直接照搬的代码片段。

本章包含两篇 L4 文档。

1_when-to-use-each-pattern.md —— 模式选型决策框架。第一块讲四种模式的 lineup——single session（主 agent 一人干完，最便宜，适合短任务或紧反馈）、subagent delegation（主 agent 派一个 subagent 跑重活、隔离 context）、Agent Teams（多 teammate 并行 + peer messaging + shared task list）、/batch worktree-isolated parallel（Claude Code /batch 命令对多个独立 task 自动开 worktree 并行）。第二块讲 决策三轴——(a) 并行需求：单任务 single session、独立子任务 /batch、长协作 Agent Teams；(b) 共享 context：任务间不需 share 用 /batch、需要 share state 用 Agent Teams；(c) 任务依赖度：无依赖 /batch、有依赖 Agent Teams（task list 自动 unblock）。第三块讲 worktree + subagent 组合——最被低估的强组合：subagent 在 worktree 里独立改代码、主 agent 看 summary、跨 worktree 用 git merge 整合；典型场景是"我有 3 个并行 bug 要修但不想互相干扰"。第四块讲 anti-pattern——同文件 edits 上 Agent Teams 反而慢（teammate 互相 wait）、紧依赖任务用 /batch 失败（无任务依赖支持）。

2_anti-recursion-and-coordination.md —— 防递归与协调。第一块讲 fork-can't-fork 规则的底层逻辑——为什么硬限一层 fork？因为 fork 复用 parent prompt cache，多层 fork 会让 prompt cache invalidation 变得 unpredictable；spawn fresh subagent 不复用 cache，可以多层嵌套但成本高。第二块讲 message-passing 协调的 race condition——Agent Teams 两 teammate 同时 claim 同一 task 时 task list 用 atomic update 保证唯一 claimer；teammate 给 teammate 发消息时 message 进 inbox file（JSONL append-only）；user 在 lead agent 处可监控所有 message 流。第三块讲 task list state machine 的 dependency 解锁——task 用 blocked_by: [task_id, ...] 声明依赖、依赖完成后由 lead agent 主动 unblock、避免 polling；附 task list YAML 例。第四块讲 Tier 2 反向 MCP 场景的 reentry-guard——personal-agent 工具（Hermes / OpenClaw）作为 MCP server 被 Claude 反向调用、若它内部又调 Claude 形成环路，server 端必须实现 reentry-guard（同 call chain 最多 1 层）；附最小实现思路。第五块讲 infinite-loop 防护套件——subagent budget（一个 main agent session 最多 N 个 subagent）、worktree budget（最多 M 个 active worktree）、time budget（subagent 跑 > X 分钟自动 abort），都在 settings 配置。

学习建议是 1_ 选型决策必读，2_ 防递归在多 agent setup 上线前必读；如果只跑 single session 模式 2_ 可暂时跳过。
