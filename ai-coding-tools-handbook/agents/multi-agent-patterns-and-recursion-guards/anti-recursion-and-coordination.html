防递归与协调

多 agent 系统一旦放任不管，三种问题会同时来:递归无限派生 (agent 派 agent 派 agent...) / race condition (两 teammate 同时 claim 同 task) / reverse-MCP 环路 (personal-agent 工具 MCP server 又调 Claude 反向回来)。本文把工程纪律讲清——fork-can't-fork 的底层逻辑、message passing 的 atomic update、task list dependency 解锁、Tier 2 反向 MCP 的 reentry-guard、infinite-loop 防护套件。

fork-can't-fork 的底层逻辑
../1_subagent-fundamentals/2_fork-mode-and-prompt-cache.md 提过 fork 不能再 fork 的硬规则。底层逻辑是 prompt cache 语义:


不论 fork-2 复用哪个 parent，cache invalidation 都变 unpredictable。Anthropic 选择在 runtime 硬禁第二层 fork，让 cache 语义保持简单:"fork 永远命中 parent 的初始 prompt cache"。需要更深嵌套用 spawn fresh，付正常 token 费且不依赖 cache。


这条规则也是天然的 递归无限派生 防护——fork 链断在一层，攻击者或 buggy agent 想用 fork 无限派生不可能。但它只防 fork 路径，spawn fresh 不受限，需要额外的 subagent budget。


Message-passing 协调 race condition
Agent Teams 多 teammate 并发场景的核心 race:两个 teammate 同时看到一个 pending task 都想 claim。错误的 naive 实现:


# 错误: 非原子
task = task_list.get(id)
if task.status == 'pending':
    task.owner = self.name        # race: 两个 teammate 同时跑到这
    task.status = 'in_progress'
    task_list.put(task)
正确实现用 compare-and-swap (CAS):


# 正确: atomic compare-and-set
success = task_list.atomic_claim(
    id=task_id,
    expected_status='pending',
    new_owner=self.name,
    new_status='in_progress',
)
if not success:
    # 另一 teammate 已经 claim, 去下一个 task
    continue
atomic_claim 在底层是单条 update with WHERE 子句 (SQL / 文件 fcntl / Redis WATCH-MULTI-EXEC)，保证整个 list 任意时刻只有一个 claimer 成功。


Teammate 间的 peer message 走 inbox file (JSONL append-only)，append 操作天然原子，多发不冲突。读端按时间戳 / 自增 id 顺序消费即可。整个 mesh-style 通信图:


Task list state machine 的 dependency 解锁
task list 三态 pending / in_progress / completed + 依赖字段:


- id: t1
  subject: 'Add auth middleware to /api/admin/*'
  status: completed
  owner: backend-agent
  blocks: [t2, t3]

- id: t2
  subject: 'Update README with auth headers'
  status: pending # 依赖 t1 完成后由 lead AI 解锁
  owner: docs-agent
  blocked_by: [t1]

- id: t3
  subject: 'E2E test the protected route'
  status: pending
  owner: qa-agent
  blocked_by: [t1]
blocked_by 与 blocks 是双向关系——任一字段更新另一字段。机制是 push 而非 poll:t1 status 转 completed 时, lead AI 主动扫描 t1.blocks, 把每个被 blocked task 的 blocked_by 中去掉 t1, 当 blocked_by 空时自动 unblock。Teammate 不必轮询 task list 等待——unblock 是 lead AI 推过来的状态变更，teammate 收到通知再 CAS claim 即可。


这套机制把 "任务依赖图" 当作 DAG，lead AI 做 topological 推进。循环依赖在创建 task 时被拒 (blocks + blocked_by 反向闭环检测)，避免 deadlock。


Tier 2 反向 MCP 的 reentry-guard
反向 MCP 场景是这样:personal-agent 工具 (Hermes / OpenClaw 等 Tier 2) 注册自己为 MCP server, Claude 通过 mcp client 调用它的 tool。如果这个 server 内部又通过 Claude API 调 Claude (例如 server 想让 LLM 处理一段内容)，形成环路:


环路风险:server 在处理 mcp tool call 时调 Claude API，Claude API 输出又触发 server 调自己 (例如 prompt 里要求 Claude 调某 tool, server 误认为是自己的 tool)，无限递归 + token 烧光。


防护机制是 reentry-guard:server 端给每个 mcp call 分配 call-chain-id，同一 call-chain 内最多允许 1 层 LLM 反向调用。最小实现思路:


async def handle_tool_call(req):
    chain_id = req.context.get('call_chain_id') or new_chain_id()
    depth = req.context.get('mcp_depth', 0)

    if depth >= 1:
        raise ReentryError("MCP reentry depth > 1 in chain " + chain_id)

    # 传给内部 LLM 调用时带上 depth+1
    result = await call_internal_llm(
        prompt=...,
        context={'call_chain_id': chain_id, 'mcp_depth': depth + 1},
    )
    return result
depth >= 1 时拒绝，硬规则。这是 server 实现的责任，不在 Claude 内核——Claude Code 不知道下游 MCP server 内部会不会反调自己，由 server 自己 guard。详细 reverse-MCP 反模式见 ../../2_mcp/3_reverse-mcp-and-pitfalls/。


更广的反向 MCP bridge 设计见 ../../../03_bridges/ 桥接章节。


Infinite-loop 防护套件
settings.json 配置三个 budget:


{
  "agentLimits": {
    "subagentPerSession": 20,
    "activeWorktrees": 8,
    "subagentTimeoutMinutes": 30
  }
}
    

  • subagentPerSession:一个 main agent session 最多 N 个 subagent，超限拒绝派生。防 buggy agent 把 token 烧光。
    • 

  • activeWorktrees:同时存在的 worktree 上限，超过拒绝新派生 (sub 必须等其他完成 cleanup)。防 worktree 失控吃磁盘。
    • 

  • subagentTimeoutMinutes:subagent 跑 > X 分钟自动 abort + cleanup。防 hung / loop 的 subagent 永远不回。
    • 



三者叠加 + fork-can't-fork + reentry-guard，覆盖了 2026 多 agent 系统的主要无限派生 / 死循环风险。监控层面建议在 hooks 里 log 每次 subagent 派生 + 耗时 + worktree 状态，方便 audit。


陷阱与常见问题
第一坑是依赖 fork-can't-fork 当全部防护——它只限 fork 路径，spawn fresh + 无 budget 一样可以失控。必须三件套都开。


第二坑是 task list dependency 写循环——t1 blocked_by [t2]、t2 blocked_by [t1] 永远 deadlock。Lead AI 应在 task 创建时拒绝循环 (DAG 检测)，未检测的 Teams 实现可能挂死。


第三坑是反向 MCP server 没 reentry-guard——server 作者只想着 "我的 server 怎么处理 Claude 的请求"，忘了 "如果我内部也调 Claude"，环路在生产里才暴露。Tier 2 personal-agent 工具开发者必须 review 这条。


第四坑是 budget 设过紧——subagentPerSession: 3 在多并行 bug fix 场景一秒触顶，应根据团队工作流校准。生产环境给个宽松默认 + dashboard 监控比硬限更好。


小结
    

  • 四类风险:递归无限派生 / race condition / 反向 MCP 环路 / infinite loop
    • 

  • fork-can't-fork 源于 prompt cache 语义歧义, 同时是天然递归防护; 但只防 fork 路径
    • 

  • Race condition 用 atomic compare-and-swap claim, peer message 走 append-only JSONL inbox
    • 

  • Task list state machine 三态 + dependency, lead AI push-driven unblock 而非 teammate poll
    • 

  • Tier 2 反向 MCP 必须 实现 reentry-guard, 同 call chain 限 1 层
    • 

  • Infinite-loop 防护套件:subagent budget / worktree budget / time budget, settings.json 配
    • 

  • 单一防护不够, 多层组合才安全
    •
