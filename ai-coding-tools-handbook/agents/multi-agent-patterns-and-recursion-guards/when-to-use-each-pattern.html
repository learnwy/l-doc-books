多 agent 模式选型决策框架

不是所有任务都该派 subagent、subagent 也不是越多越好。2026 编程代理生态稳定了四种多 agent 模式:single session / subagent delegation / Agent Teams / /batch worktree-isolated parallel。本文给一套基于 "并行需求 / 共享 context / 任务依赖度" 三轴的决策框架，附 worktree + subagent 组合的最佳实践与几个反模式。

四种模式的 lineup
Single session 是最被低估的选择。任务短 (< 5 个 tool call)、反馈紧 (每步看结果)、不需要并行时，主 agent 一人干完最快最便宜。开 subagent / Teams 的 overhead 在这个尺度反而拖慢。判定标准:"我能用 single session 30 秒讲清任务并 5 分钟内做完吗?" 是 → single session.


Subagent delegation 适合 "我有个脏活想隔离 context"。reviewer / researcher / data-cruncher 都是典型——sub 自己跑 search / grep / build，把 token-heavy 过程关在它的 context 里，只回主 agent 一段 summary。带 isolation: worktree 可同时派多个 sub 并行改文件不互相覆盖。


Agent Teams 适合长协作有依赖的任务。需要 task list / dependency 解锁 / teammate 互发消息时上 Teams。一次性脏活别开 Teams，那是把吊车开来钉钉子。


/batch worktree-isolated parallel 是 Claude Code 命令对 "多个独立 task" 自动开 worktree 并行的简化入口。给 /batch 一组任务，它给每个开一个 worktree、并行跑、最后汇总。比手动派多 subagent 简单，但没有任务依赖支持——/batch 假设任务间完全独立。

三轴叠加举例:


    

  • "修 3 个独立 bug" → 并行 + 无 share + 无依赖 → /batch
    • 

  • "做 Auth 重构, 拆 backend / docs / qa 三人协作" → 并行 + 有 share + 有依赖 → Agent Teams
    •

    • 

  • "改个 typo" → 单任务 + 主 checkout 即可 → Single session

Worktree + subagent 组合最被低估
这个组合的价值常常被人忽视:


典型场景:"我有 3 个并行 bug 要修但不想互相干扰"。手动用 Agent Teams 太重 (没有任务依赖, 不需要 peer messaging)、手动 /batch 不够灵活 (想各自 sub 自定义 prompt)、单 subagent 串行又慢。三个 subagent + 各自 worktree 是最优解:并行跑、互不干扰、commit 独立、主 agent 整合。


实战配方:


// 同时派 3 个
{"tool": "Agent", "parameters": {"subagent_type": "bug-fixer", "description": "fix issue #101", "isolation": "worktree"}}
{"tool": "Agent", "parameters": {"subagent_type": "bug-fixer", "description": "fix issue #102", "isolation": "worktree"}}
{"tool": "Agent", "parameters": {"subagent_type": "bug-fixer", "description": "fix issue #103", "isolation": "worktree"}}
每个 subagent 跑完返回 commit hash + 修复 summary，主 agent 把 3 个 commit cherry-pick 回主分支或合 PR。如果开了 CLAUDE_CODE_FORK_SUBAGENT=1，prompt cache HIT 让 3 个并发成本接近 1 个的 token 消费。详见 ../1_subagent-fundamentals/2_fork-mode-and-prompt-cache.md。


Anti-pattern
反模式 1:同文件 edits 上 Agent Teams
Teams 适合任务间有逻辑依赖但物理上不冲突的场景。如果 backend-agent 与 docs-agent 都要改 README.md，他们会互相 wait task list 或文件 lock，反而比 single session 串行慢。同文件并发改用 single session 或 subagent + worktree (再 merge)。


反模式 2:紧依赖任务用 /batch
/batch 没有任务依赖支持，假设输入任务完全独立。给 /batch 一组 "A 完成才能 B 开始" 的任务，B 会在 A 还没好时就开跑，依赖前置条件，失败。这种场景用 Agent Teams 的 blocked_by。


反模式 3:为隔离 context 滥开 Teams
只是想让主 session 清爽就开 Agent Teams，三个 teammate 互相等空 task 一小时。隔离 context 用 subagent (sub 跑完 return)、不必动 Teams。


反模式 4:不开 fork 的多 worker 并行
并行 5 个 subagent 不开 CLAUDE_CODE_FORK_SUBAGENT=1 时每个都 cache MISS，token 账单震惊。任何 ≥ 2 个并行 subagent 都该开 fork。


陷阱与常见问题
第一坑是把决策三轴当独立 axis 用——三轴有强关联性 (并行 → 多任务 → 大概率有 share 或依赖)，决策实际上是一个 path 而非笛卡尔积。


第二坑是高估 Agent Teams 的 ROI——它的协调 overhead 不小，3 个 teammate 以下且任务时长 < 30 分钟时往往不如 subagent + worktree 划算。


第三坑是忘了主 agent 也要付 orchestration token——派 5 个 sub 主 agent 收 5 份 summary 要 5 倍 read，长 summary 会撑爆主 context。Sub 设计要求 "返回简洁 summary"。


小结
    

  • 四种多 agent 模式:single session / subagent delegation / Agent Teams / /batch worktree-parallel
    • 

  • 决策三轴:并行需求 / 共享 context / 任务依赖度
    • 

  • 默认偏好 single session, 只在三轴明显需要时上更重的模式
    • 

  • subagent + worktree 是并行无依赖任务的最优组合, 配 fork mode token 成本最低
    • 

  • 反模式:同文件 Teams / 紧依赖 /batch / 滥开 Teams / 不开 fork 的多并行
    •
