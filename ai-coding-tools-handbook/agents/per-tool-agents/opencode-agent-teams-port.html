OpenCode 的 Agent Teams port 与 cross-provider 模型混搭

OpenCode 是开源 / 自托管路线的编程代理，2026 上半年完成了 Claude Code Agent Teams 的功能 port。架构层面与 Claude 哲学接近（fire-and-forget spawn、file-based inbox、explicit sub-agent isolation），但有 Claude Code 做不到的独有能力——cross-provider model mix:同一个 agent team 里 teammate 可以来自不同 provider（Anthropic Claude + OpenAI GPT + Google Gemini + 本地 Ollama）。本文把 port 动机、架构差异、trade-off 讲清。

Port 动机与时间线
完整 port 故事在 dev.to 文章 uenyioha/porting-claude-codes-agent-teams-to-opencode-4hol（2026 上半年）。三句话概括动机:


    

  • Claude Code Agent Teams 设计被认为优秀，OpenCode 社区希望复刻
    • 

  • OpenCode 用户多在本地 / 自托管环境跑，需要 provider 中立的 Teams 实现
    • 

  • 把 Claude 的 task list + peer messaging 抽象成 provider-agnostic 协议
    • 



时间线:2026-Q1 启动 port、2026 上半年完成基础版本、随后渐进添加 cross-provider 能力。OpenCode 的实现并非 Claude Code 内核的直接移植——内核闭源——而是基于 Claude 公开文档与 transcript 观察反推协议、再用 OpenCode 自己的运行时实现。


Cross-provider model mix 独有能力
这是 OpenCode 相对 Claude Code 的杀手锏:


# .opencode/team.yaml 示例
lead:
  provider: anthropic
  model: claude-opus-4-7
teammates:
  - name: backend-agent
    provider: anthropic
    model: claude-opus-4-7
    role: 'Senior backend engineer, owns API + DB'
  - name: docs-agent
    provider: openai
    model: gpt-5.3
    role: 'Technical writer, owns README + ADR'
  - name: experimental-agent
    provider: google
    model: gemini-2.0-pro
    role: 'Tries unconventional approaches'
  - name: lint-agent
    provider: ollama
    model: qwen2.5-coder:32b
    role: 'Style + lint enforcement, runs locally for cost'
四个 teammate 来自四家 provider:Anthropic / OpenAI / Google / 本地 Ollama。Claude Code 因绑 Anthropic 模型做不到——所有 teammate 必须是 Claude。OpenCode 的价值在三类场景:


    

  • 成本敏感:把 cheap 任务 (lint / format / docstring 补全) 路由到本地 Ollama 节省 API 费
    • 

  • 能力组合:不同 provider 模型在 SWE-bench / FrontendBench / ReasoningBench 各有所长，让 backend 用 Claude、UI 用 GPT、reasoning 用 Gemini
    • 

  • 冗余 / 抗 provider 故障:一家 API 宕了不影响整 team
    •

JSONL append-only 设计的优点是 持久化任务流:整 team 的完整历史就是几个 JSONL 文件，崩溃后可 replay 恢复，审计与 debug 都直接。缺点是单进程瓶颈——所有 lock 在内存，多 server instance 不共享 storage，因此 OpenCode Teams 不能多机分布式跑。


Single-process 的硬限
OpenCode 的 single-process 决定不是疏忽，是 trade-off。给跨进程上 file-based lock 会:


    

  • 增加实现复杂度 (需处理 stale lock / crash recovery)
    • 

  • 在本地 dev 场景没有实际收益 (一台开发机器跑一个 OpenCode 进程足够)
    • 

  • 拖慢 message-passing (每条消息一次 fsync)
    • 



Claude Code 选了跨进程因为它要支持企业级 multi-IDE / multi-CLI session 同步；OpenCode 选 single-process 因为它的用户主要是单机 dev。两种选择都合理，团队规模与部署模型决定哪种更适合。

混合用法也有人尝试:OpenCode 跑本地实验性多 provider team，Claude Code 跑日常稳定 dev loop，仓库层面交接 commit。多 agent 编排还在快速演化，把工具当 protocol 兼容的 commodity 看待是健康心态。


陷阱与常见问题
第一坑是期待 OpenCode Teams 与 Claude Code Teams 行为像素级一致——实现细节不同 (JSONL vs Claude 内部、single-process vs 跨进程)，迁移 team 配置需要重写。


第二坑是 cross-provider mix 在 prompt cache 上没优势——每家 provider 自己的 cache 不共享，OpenCode 没法做 Claude fork mode 那种跨 teammate 的 cache HIT。


第三坑是 single-process 在 long session 内存膨胀——所有 JSONL 状态在内存，跑 8 小时以上 team 会显著吃 RAM，需要定期 restart 或开 housekeeping job。


小结
    

  • OpenCode 2026 上半年完成 Claude Code Agent Teams 的功能 port，架构哲学接近 (fire-and-forget / sub-agent worktree / shared task list)
    • 

  • 杀手锏:cross-provider model mix——teammate 可来自 Anthropic / OpenAI / Google / 本地 Ollama，Claude 做不到
    • 

  • 实现差异:Event-driven JSONL / append-only / single-process / 两级 state machine
    • 

  • Trade-off:灵活性 + provider 中立 vs 工业级稳定 + 多进程同步
    • 

  • 选型按 "需要 model mix? 自托管? 多 surface 同步?" 三问决定
    •
