Claude Code subagents 与 Agent Teams

Claude Code 把 agent 体系做成两层:subagent（fire-and-forget 子任务，跑完返回一次 result）与 Agent Teams（长期协作的多 peer agent，shared task list + peer messaging）。前者从 v2.0.x 就在，后者是 Opus 4.6 release (2026-02) 随 v2.1.32+ 引入的 experimental 能力。两者用同一份 .claude/agents/<name>.md 定义文件、共享 isolation 机制，但生命周期与协调模型截然不同。

Subagent 定义文件
.claude/agents/code-reviewer.md 的最小可用形:


---
name: code-reviewer
description: Review staged diff for bugs, security, style issues
tools:
  - Read
  - Grep
  - Bash
isolation: worktree
model: claude-opus-4-7
permission-mode: plan
---

You are a senior code reviewer. Output a structured report with
sections: Bugs / Security / Style / Suggestions. Be specific with
file paths and line numbers.
frontmatter 五个字段都不是必填，但生产实践里都该填：name 是派生时的引用名，description 是主 agent description 匹配的关键字源，tools 限制可调工具，isolation: worktree 启用 worktree 隔离，model 显式指定模型，permission-mode 控制 subagent 的写权限。body 部分整段作为 subagent 的 system prompt。


主 agent 通过 description 自动匹配派生——用户说 "帮我 review 一下" 或主 agent 推理出需要 review 时，自动派 code-reviewer。也可在 Agent tool 调用里显式 subagent_type: "code-reviewer" 强制指定。


Agent Teams 启用与结构
Agent Teams 是 Opus 4.6 release (2026-02) 推出的 experimental 能力。启用方式两种:


# env var
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude
或 settings.json:


{
  "experimental": {
    "agentTeams": true
  }
}
启用后主 agent 升级为 lead AI，负责:


    

  • spawn teammates（与 subagent 同一 .claude/agents/<name>.md 定义）
    • 

  • 维护 shared task list（source of truth, 三态 pending / in_progress / completed）
    • 

  • 在 dependency 完成时 unblock 阻塞 task
    • 

  • 协调 user 干预（user 可向 lead 或单个 teammate 发指令）
    • 



task list 结构:


- id: t1
  subject: 'Add auth middleware to /api/admin/*'
  status: in_progress
  owner: backend-agent
  blocks: [t3]
- id: t2
  subject: 'Update README with auth headers'
  status: pending
  owner: docs-agent
  blocked_by: [t1]
- id: t3
  subject: 'E2E test the protected route'
  status: pending
  owner: qa-agent
  blocked_by: [t1]
t2 与 t3 都 blocked_by t1——t1 完成时 lead AI 把它们的 status 推进到 pending → 可被 owner 自动 claim。teammate 之间通过 peer message 互相通知 (例如 backend-agent 给 qa-agent 发 "endpoint 上线了, request payload 见附录")，不必经 lead AI 转交。


Peer-to-peer messaging
Agent Teams 的核心机制之一是 teammate 直连通信:


user 可在任意时刻插入指令到 lead AI 或直接发给某 teammate；teammate 收到指令后更新自己的 plan、必要时给其他 teammate 发协调消息。这种 mesh-style 协调避免 lead AI 成为瓶颈，多 teammate 并发推进的实际吞吐显著高于 "全部经主 agent 转交" 的模式。

过度设计





一个朴素的判断:"我是否需要 task list?" 需要 → Agent Teams；不需要 → subagent。Subagent 是 fire-and-forget 的子函数，Agent Teams 是常驻协作的迷你公司。


陷阱与常见问题
第一坑是把 Agent Teams 当成 "subagent 的多个实例"——Teams 有 task list / peer messaging / 长生命周期等 subagent 没有的机制，不是简单的并行 subagent。


第二坑是没开 flag 就期待 Teams 行为——CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 不开时主 agent 派 subagent 还是单次 fire-and-forget。


第三坑是同一 .claude/agents/<name>.md 同时被 subagent 派生与 Teams teammate 使用——两种用法定义文件共享但运行时语义不同，subagent 期望返回一次 summary、teammate 期望长期在线，prompt 措辞 ("Return a structured report" vs "Coordinate with other teammates") 应根据预期场景调整。


第四坑是用 Teams 跑同文件并发 edits——teammates 互相 wait 反而比 single session 慢。Teams 适合任务间有逻辑依赖但物理上不冲突的场景。


小结
    

  • Claude Code agent 两层结构:subagent (fire-and-forget) + Agent Teams (长期协作)
    • 

  • 共享 .claude/agents/<name>.md 定义文件 (frontmatter + body)
    • 

  • Agent Teams 需 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 启用，依赖 v2.1.32+ / Opus 4.6 (2026-02)
    • 

  • 核心机制:shared task list + 三态 + dependency 解锁 + teammate peer messaging
    • 

  • 边界:需要 task list 与多 worker 协调用 Teams，单次脏活用 subagent
    •
