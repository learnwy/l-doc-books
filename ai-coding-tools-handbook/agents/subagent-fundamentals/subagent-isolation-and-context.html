Subagent 隔离与 context 模型

Subagent 在 Claude Code 里不是"主 agent 内嵌的一段子流程"，而是一个完整的迷你 agent 实例：自己的 context window、自己的 system prompt、自己的 tool 集、自己的 permission。理解这个 isolation 模型，是后续看懂 isolation: worktree、fork mode 与 Agent Teams 三层机制的前提。

核心概念

四种 isolation 维度叠在一起决定一个 subagent 与主对话的"距离":

Subagent 的四层 isolation
第一层是 context window 隔离——主 agent 调用 subagent 时只把"任务描述 + 必要片段"放进 subagent 的 context，主 session 累积的 search result、log、file content 不会泄漏过去。Subagent 跑完只回报一段 summary，summary 进主 context、过程不进。这是 subagent 最被低估的价值：把脏活的 token 开销隔离在 subagent 那一侧。


第二层是 system prompt 隔离。Subagent 定义在 .claude/agents/<name>.md：


---
name: code-reviewer
description: Reviews staged changes for quality and security issues
tools:
  - Read
  - Grep
  - Bash
isolation: worktree
model: claude-opus-4-7
---

You are a senior code reviewer. For each diff hunk, identify:

- Logic bugs / off-by-one errors
- Security: SQL injection, XSS, secrets in code
- Style violations against project conventions
  Return a structured report grouped by file.
主 agent 通过 description 自动匹配——用户说"帮我 review 一下"或主 agent 推理出需要 review 时，自动派生 code-reviewer。body 部分整段作为 subagent 的 system prompt，与主 agent 的 CLAUDE.md 完全无关。


第三层是 tool 集隔离。frontmatter tools: 列出哪些 tool 可用，不在列表里的 tool 在 subagent 里调不出来。安全场景里 reviewer 不该有 Edit / Write，只给 Read / Grep / Bash 即可。


第四层是 permission 隔离。派生时可显式 --permission-mode plan，subagent 跑 plan mode 而主 session 仍在 default mode；反向也成立。这让"主 agent 自由改 / subagent 严格审"成为可能。


isolation: worktree 机制
Frontmatter 加 isolation: worktree 之后，Claude 在派生 subagent 前自动做四件事:


四件事:auto-name 工作树、新建分支基于 origin 默认分支或当前 HEAD（由 worktree.baseRef 控制）、cwd 指向新 worktree、附着 per-worktree state（plan mode 状态、memory / hooks / permissions、transcript），原仓库的 checkout 完全不受影响。这意味着主 agent 可以继续在主 checkout 上工作，subagent 在 worktree 里改文件互不干扰。


两 subagent 互不见对方的 edits
这是 worktree 模式的核心价值。同时派生两个 subagent A 与 B，各自走自己的 worktree：


A 改了 src/auth.ts 不影响 B 看到的 src/auth.ts——B 看到的是它自己 worktree 里的版本。主 agent 在主 checkout 看到的仍是派生前的状态。这让"3 个并行 bug fix 用 3 个 subagent 同时跑"变得安全：不会出现"A 改完 B 在旧版本上接着改"的冲突。整合阶段主 agent 把每个 worktree 的 commit cherry-pick 或 merge 回主分支即可。


收尾 cleanup 与保留
subagent 跑完，Claude Code 检查 worktree 的两件事:是否有 uncommitted changes、是否有未在原仓库分支上的 commit。两件事都为空时自动 git worktree remove、删除分支；任一非空则拒绝 cleanup、保留 worktree、向主 agent 报告路径让用户决定。这是数据安全的硬规则——绝不主动丢失 subagent 工作成果。用户决定的方式有两种:ExitWorktree action: keep 保留 worktree + 分支供继续使用，或 ExitWorktree action: remove discard_changes: true 显式确认抛弃。后者必须显式带 discard_changes，避免误操作。


陷阱与常见问题
第一坑是把 subagent 当作"在主 context 里复用工具"——subagent 是另一个 context、另一个 prompt、另一个 tool 集，主 session 的 memory 不会被 subagent 自动看到。需要传 context 时显式把片段放进派生 prompt。


第二坑是 isolation: worktree 没设但又派生多个 subagent 并行改同一文件——这会在主 checkout 上互相覆盖，因为四个 subagent 共用 cwd。规则：任何"改文件的并行 subagent"都该上 worktree。


第三坑是忘了 cleanup 检查——subagent 跑完留下一堆 worktree 占磁盘。可以用 git worktree list 看哪些是 .claude/worktrees/ 下的、git worktree remove 显式清理。常驻 worktree 上有未合并 commit 时优先 cherry-pick 回主分支再 remove。


小结
    

  • Subagent 是有 context / prompt / tool / permission 四层 isolation 的迷你 agent 实例，主对话的 token 开销与 tool 列表都不会污染它
    • 

  • 通过 .claude/agents/<name>.md 的 frontmatter 配置定义 / 自动 description 匹配派生 / body 作 system prompt
    • 

  • isolation: worktree 让 subagent 在 fresh git worktree 跑，自动 name / branch / cleanup
    • 

  • 两个 worktree subagent 互不见对方 edits 是核心价值，并行 bug fix 的正解
    • 

  • Cleanup 严格——有 uncommitted changes / unmerged commits 时拒绝删除，由用户显式 discard_changes 抛弃
    •
