Fork mode 与 prompt cache 经济学

派生一个 subagent 看似只是 "另起一个 context"，实际 token 账单的差距可以达到一个数量级——关键在选 fork 还是 spawn fresh。fork 复用 parent 的 system prompt 与 tool 定义、命中 prompt cache；spawn fresh 把 system prompt 与 tools 重 boot 一次、cache miss。本文把两种派生模式的机制、成本曲线、何时选谁讲透。

Fork 与 spawn 都通过 Agent tool 派生 subagent，但 runtime 内部走的路径不同——fork 把 parent 的 prompt + tool definitions 当作 "已经发过的 context" 在新 session 第一次 request 里复用，触发 Anthropic API 的 prompt cache；spawn fresh 不带任何 parent 信息，新 session 从零开始 boot。


Fork 复用 parent prompt cache 的机制
Anthropic API 的 prompt cache 按前缀匹配——同样的前几千 token（system prompt + tool schema + 早期 turn）被认作可缓存的前缀，命中后只收 1/10 的输入 token 费率。fork mode 利用了这个特性：派生 subagent 时把 parent 的完整 prompt + tools 当作 "未变动前缀"，subagent 的第一次 request 在这个前缀后面加上 "subagent 任务描述" 作为变化部分。Anthropic API 看到前缀完全相同，命中 cache，只为变化部分付钱。


数量级感受：假设 parent system prompt + tool schema 共 12k token、subagent 任务描述 500 token：

并行派生 5 个 subagent 时差距放大 5 倍——fork 派生 5 个 subagent 的成本接近 spawn 派生 1 个的成本，这是 Agent Teams 与 /batch 能 cost-effective 跑起来的底层原因。


启用 fork mode
环境变量启用:


CLAUDE_CODE_FORK_SUBAGENT=1 claude
interactive REPL、non-interactive claude -p、Agent SDK 三种入口都生效。Agent tool 调用时同时给 isolation: "worktree" 让 fork 在隔离 worktree 里改文件，避免主 checkout 被并行 subagent 互相覆盖：


{
  "tool": "Agent",
  "parameters": {
    "description": "review staged changes for security issues",
    "subagent_type": "code-reviewer",
    "isolation": "worktree",
  },
}
settings.json 里也可以全局开:


{
  "env": {
    "CLAUDE_CODE_FORK_SUBAGENT": "1"
  }
}
启用后所有 Agent tool 调用默认走 fork、除非显式声明 spawn fresh（通过 subagent 定义里换不同 system prompt 体现 "异 prompt"，runtime 自动判断走 spawn）。


Fork-can't-fork: 一层深度限制
fork mode 有一条硬规则:fork 出来的 subagent 不能再 fork。也就是 fork 嵌套深度最多一层:


为什么硬限?因为 fork 命中 prompt cache 的前提是 "parent prompt 与 subagent 前缀完全相同"。如果 fork 出来的 F1 又 fork F2，F2 的 "parent prompt" 应该是谁的?如果是主 agent 的，F1 在中间做过的 turn 会让前缀差异化，cache invalidation 变得 unpredictable；如果是 F1 的（含 F1 自己的工作过程），实际上又退化成 spawn fresh 因为 F1 自己的 turn 没有进 cache。规则简化为 "fork 最多一层"，避开 cache 语义的歧义；要更深嵌套用 spawn fresh，付正常 token 费。


这条规则也是天然的递归防护——防止 "subagent 派 subagent 派 subagent" 一路 fork 下去 token 成本以为很便宜实际产生大量调用。具体反递归在 ../3_multi-agent-patterns-and-recursion-guards/2_anti-recursion-and-coordination.md 详述。

实战经验：把项目里的 .claude/agents/<name>.md 设计成 "尽量贴近主 agent prompt 风格" 让 fork 命中率最大化，只在需要明显不同行为时（reviewer / researcher / writer）换 prompt 走 spawn。一组同 prompt 的 "改 file 任务 worker" subagent 并行用 fork + worktree 是当下最具性价比的派生姿势。


陷阱与常见问题
第一坑是以为 "subagent 一定是 fork"——没有 CLAUDE_CODE_FORK_SUBAGENT=1 时所有派生默认走 spawn fresh，token 账单会震惊。


第二坑是 fork 后 subagent 改了 system prompt 期待 cache 还命中——subagent 的 system prompt 与 parent 不一样时前缀就变了，cache miss。fork 只在 prompt + tools 相同时省钱。


第三坑是依赖 fork-can't-fork 当唯一防递归——这只是 fork 路径的限制，spawn fresh 不受限。深嵌套场景必须额外配 subagent budget / time budget。


第四坑是 fork 派生 + 同 checkout 改文件并行——多个 worker 并发写主 checkout 会互相覆盖，fork 派生必须搭 isolation: worktree 才安全。


小结
    

  • Fork 复用 parent system prompt + tool definitions，命中 Anthropic prompt cache，首次 request 费率约为 spawn 的 1/7
    • 

  • 启用方式：CLAUDE_CODE_FORK_SUBAGENT=1 env var，interactive / non-interactive / Agent SDK 都生效
    • 

  • Fork-can't-fork 是硬规则——避开多层 fork 时 cache 语义的歧义；需要深嵌套用 spawn fresh
    • 

  • 决策三问：同 prompt 同 tools? → fork；异领域? → spawn；长协作多 worker? → Agent Teams
    • 

  • 任何 "并行改文件的 fork subagent" 都该搭 isolation: worktree 防互相覆盖
    •
