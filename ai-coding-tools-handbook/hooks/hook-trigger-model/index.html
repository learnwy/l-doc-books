Hook 触发模型 简介

Hooks 的协议设计极简——JSON via stdin、exit code 控制阻塞与否、stderr 作错误反馈、stdout 可选返回结构化 JSON 进一步控制 agent 行为。这套"管道里的协议"使 hook 可以用任何能读 stdin / 写 stdout/stderr / 返回 exit code 的语言写：bash、python、node、go 都行，无需特定 SDK。但协议的语义点（exit 0 vs exit 2 vs 其它、JSON output 的 schema、哪些事件 stdout 进 context）需要逐一理解清楚，否则写出的 hook 可能 silent fail 或行为非预期。本章用两篇讲清整套触发模型。

本章包含两篇 L4 文档。

1_exit-code-and-stderr-semantics.md —— exit code + stderr 语义。第一块讲 exit 0 success 路径——agent parse stdout 为 JSON（如果是合法 JSON）、否则把 stdout 写 debug log 不展示；UserPromptSubmit / UserPromptExpansion / SessionStart 三个事件特殊：stdout 直接作 context 注入 Claude 视野，可见可读。第二块讲 exit 2 blocking 路径——agent 忽略 stdout 与其中 JSON、把 stderr 作 error message 反馈给 Claude；effect 按事件类型：PreToolUse 拒绝工具调用、UserPromptSubmit 拒绝用户 prompt、Stop 强制 agent 继续工作等。第三块讲其它 non-zero（exit 1 / 3 / 等）——agent treat 为非阻塞 error、显示 hook error notice + stderr 首行、execution 继续；exception 是 WorktreeCreate：任何 non-zero exit 都 abort worktree 创建。第四块讲 policy enforcement 实战：要硬拦截就 exit 2 + stderr 写原因，不要 exit 1（被当 warning 略过）。

2_json-stdout-structured-control.md —— JSON stdout 结构化控制。第一块讲 schema 总览——agent parse stdout 为 JSON 后认可的 control fields 因事件而异：PreToolUse 接受 {decision: "allow"|"deny"|"ask"}、PostToolUse / Stop 接受 {block: true}、几乎所有事件接受 {additionalContext: "string"} 把额外信息注入 Claude 视野；事件不支持的字段静默忽略。第二块讲 UserPromptSubmit / UserPromptExpansion / SessionStart 三事件——stdout 不需 JSON 也能进 context，直接作 system context append；这是把 git status、当前 branch、CI 状态、用户日志等动态信息每次会话注入的核心机制。第三块讲与 exit code 的协同——exit 0 + JSON 是常规组合，exit 2 + stderr 是阻塞组合；两者混用（exit 2 + JSON stdout）行为是 exit 2 优先、JSON 被忽略。第四块讲 HTTP hooks——同样的 JSON schema 但 input 来自 POST body、output 通过 HTTP response body 返回；适合把 hook 部署成共享服务（团队共享 policy server）。

学习建议是 1_ 先读完吃透 exit code 语义（这是写 hook 90% 的坑），再读 2_ 把 JSON schema 当工具书查；后续每写新 hook 都先想"该 exit 0 还是 exit 2"，再决定要不要 JSON output。
