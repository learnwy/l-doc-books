Exit code 与 stderr 语义

写 hook 90% 的疑难都收敛到一句话——agent 怎么解释脚本的 exit code 与三条标准流。Claude Code、Codex、OpenCode 三家在 2026 年的 hook 协议上已经收敛到同一套约定：进程退出码决定"放行 / 阻塞 / 报错"三态，stderr 是阻塞场景里反馈给 LLM 的唯一文本通道，stdout 在不同事件下有截然不同的含义。本文把这套退出码与流的语义讲到可以照搬到任何语言写 hook 的程度。

核心概念

三态退出码对应三条决策路径：exit 0 是正常返回，stdout 才有解析价值；exit 2 是结构化阻塞，stderr 是反馈通道，stdout 此时被丢弃；其它非零是非阻塞 warning，转录里出现一条提示但不影响后续工作。下表把三态的语义和最常用 effect 拉平：

WorktreeCreate 是唯一一条"任何非 0 都 abort"的事件——这是因为 worktree 的创建是一个不可中途撤销的状态变更，只要 hook 不点头就不应该继续。其它所有事件都按上表三态走。


exit 0：成功路径与 stdout 解析
退出码为 0 意味着 hook 同意当前操作继续。这一路径上 agent 的处理逻辑分三种：第一种，stdout 是一段合法 JSON、且 JSON 顶层字段是当前事件认可的控制 field（下一篇详讲 schema），agent 把它解析为对自身行为的进一步控制——比如 {"additionalContext": "..."} 会把字符串作为额外上下文注入 LLM 视野；第二种，stdout 是非 JSON 或 JSON 不带任何认可 field，agent 把它整段写到 debug log（~/.claude/logs/hooks/<event>-<ts>.log 风格），不在 transcript 中展示；第三种属于三个特殊事件——UserPromptSubmit、UserPromptExpansion、SessionStart——这三个事件的 stdout 不需要是 JSON，整段都会作为 system context 注入到下一次 LLM 调用，等价于"会话级动态变量"。


特殊事件的存在让 hook 不仅可以"放行 / 阻塞"，还可以"注入信息"。最常见的场景是 SessionStart hook 注入 git 状态：


#!/usr/bin/env bash
# SessionStart hook 注入 git 状态作为 system context
{
  echo "## 当前仓库状态"
  echo ""
  echo "**Branch**: $(git rev-parse --abbrev-ref HEAD)"
  echo "**Last commit**: $(git log -1 --oneline)"
  echo ""
  echo "**Working tree**:"
  echo '```'
  git status --short
  echo '```'
} # stdout 整段进 Claude 视野
exit 0
这段 hook 每次会话启动都会把 branch、最新 commit、未提交变更注入 LLM 的 system context，让 Claude 一开口就知道"现在站在哪条 branch、有哪些脏文件"。注意所有诊断打印（echo "debug: ..."）必须走 stderr，否则会污染 stdout 破坏注入内容。


exit 2：阻塞路径与 stderr 反馈
退出码为 2 是协议里唯一的"结构化阻塞"信号。agent 看到 exit 2 后会忽略 stdout（包括 stdout 里的 JSON），把 stderr 整段作为错误消息——这段错误消息会喂给 LLM、按事件类型产生不同 effect：


    

  • PreToolUse: 工具调用被拒绝，stderr 内容作为拒绝理由给 Claude，Claude 通常会换一个工具或者向用户解释；
    • 

  • UserPromptSubmit: 用户刚提交的 prompt 被拦截，stderr 作为拒绝理由展示给用户与 Claude；
    • 

  • PostToolUse: 工具已经执行完，但 stderr 内容作为"事后批评"反馈给 Claude，触发其重做或道歉；
    • 

  • Stop / SubagentStop: agent 试图结束工作时被强制继续，stderr 内容作为"还没干完什么"的提示重新喂给 Claude，常用于 SOP enforcement；
    • 

  • WorktreeCreate: worktree 创建 abort，stderr 在终端展示。
    • 



#!/usr/bin/env python3
# PreToolUse hook 拦截 Bash 工具里的 rm -rf 风险命令
import json, sys

evt = json.load(sys.stdin)
if evt.get("tool_name") == "Bash":
    cmd = evt.get("tool_input", {}).get("command", "")
    if "rm -rf" in cmd and "/tmp" not in cmd:
        print("拒绝执行：检测到 rm -rf 在非 /tmp 目录，请确认后改用更精确的命令", file=sys.stderr)
        sys.exit(2)
sys.exit(0)
这是一段典型的 policy hook：在 Bash 工具调用前检查命令文本，发现高风险 rm 时 exit 2 + stderr 写理由，Claude 会被告知"为什么不让做"，并在下一轮中重新规划。


exit 其它非零：非阻塞错误
exit 1、3、N（除 WorktreeCreate 外）属于"hook 自己出错"——agent 把它当 warning 处理：在 transcript 里写一行 hook error notice（含 stderr 首行），不会拦截操作、也不会喂给 LLM 作上下文。这条语义存在的意义是让 hook 写崩了不会硬阻塞 agent 工作流：脚本里语法错误、外部依赖缺失、临时网络故障等场景，开发者宁愿 agent 继续工作并显式记录"hook 挂了"，而不是 silent fail 或硬阻塞用户。


由此引出一条 policy enforcement 实战守则：要硬拦截就 exit 2 + stderr 写原因，不要 exit 1。新手写 hook 常用 set -e + 一段 [ -z "$x" ] && exit 1，结果以为加了校验、实际只是在 transcript 写了行 warning 后照常放行。正确写法见下：


#!/usr/bin/env bash
# 错误：用 exit 1 想拦截，实际只产生 warning
if [ "$RISK" = "high" ]; then
  echo "high risk operation"  # 这行进 stdout 被 debug log 忽略
  exit 1                        # 只是 warning、不阻塞
fi

# 正确：用 exit 2 + stderr
if [ "$RISK" = "high" ]; then
  echo "拒绝：high risk operation，请改用 low-risk 模式" >&2
  exit 2
fi
多语言最小模板
下面三段是三种语言写 hook 的最小骨架，按统一约定输出：


#!/usr/bin/env bash
set -e
INPUT=$(cat)                           # stdin JSON 字符串
TOOL=$(jq -r '.tool_name // empty' <<< "$INPUT")
[ "$TOOL" = "Bash" ] || { exit 0; }
CMD=$(jq -r '.tool_input.command // empty' <<< "$INPUT")
if grep -q 'force-push' <<< "$CMD"; then
  echo "拒绝：force-push 需要管理员批准" >&2
  exit 2
fi
exit 0
#!/usr/bin/env python3
import json, sys
evt = json.load(sys.stdin)
if evt.get("tool_name") != "Bash":
    sys.exit(0)
cmd = evt.get("tool_input", {}).get("command", "")
if "force-push" in cmd:
    print("拒绝：force-push 需要管理员批准", file=sys.stderr)
    sys.exit(2)
sys.exit(0)
#!/usr/bin/env node
const chunks = [];
process.stdin.on('data', (c) => chunks.push(c));
process.stdin.on('end', () => {
  const evt = JSON.parse(Buffer.concat(chunks).toString());
  if (evt.tool_name !== 'Bash') return process.exit(0);
  const cmd = evt.tool_input?.command ?? '';
  if (cmd.includes('force-push')) {
    process.stderr.write('拒绝：force-push 需要管理员批准\n');
    return process.exit(2);
  }
  process.exit(0);
});
三段功能等价：读 stdin JSON、检查工具名与命令文本、命中规则 exit 2 + stderr 拒绝、否则 exit 0 放行。任何更复杂的 hook 都在此基础上加判断与 IO。


陷阱与常见问题
    

  • 混淆 exit 1 与 exit 2：exit 1 是 warning（不阻塞），exit 2 才是阻塞。新手最常见错误。
    • 

  • stderr 与 stdout 混用：诊断 echo 不带 >&2 会污染 stdout、破坏 JSON 解析，hook silent fail。
    • 

  • 认为所有事件都能阻塞：实际只有 PreToolUse / UserPromptSubmit / Stop 等少数事件的 exit 2 真正阻塞；PostToolUse 的 exit 2 是事后批评、tool 已经执行完不能撤销。
    • 

  • 依赖 stdout JSON 在 exit 2 时生效：exit 2 一律忽略 stdout JSON，需要反馈走 stderr 文本，不要写 {"reason": "..."}。
    • 

  • WorktreeCreate 用 exit 1 想"软警告"：WorktreeCreate 任意非 0 都 abort，与其它事件语义相反。
    • 

  • hook 自身崩溃影响 agent 工作流：未捕获异常导致 exit 非 0，被当 warning 但用户看不到原因；建议入口 try/catch + 兜底 exit 0。
    • 



小结
    

  • exit 0 是放行；UserPromptSubmit / UserPromptExpansion / SessionStart 三事件的 stdout 直接进 LLM context，其它事件需要 JSON 才能控制。
    • 

  • exit 2 是结构化阻塞；agent 忽略 stdout、读 stderr 作反馈喂回 LLM；按事件类型产生 deny / 强制继续 / 事后批评等不同 effect。
    • 

  • 其它非 0 是非阻塞 warning（WorktreeCreate 例外，任何非 0 即 abort）；要硬拦截必须 exit 2，不要用 exit 1 误以为生效。
    • 

  • 诊断信息一律 >&2，stdout 留给 JSON 控制 / context 注入两种用途。
    •
