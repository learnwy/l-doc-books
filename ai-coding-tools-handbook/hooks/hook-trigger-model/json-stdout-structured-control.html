JSON stdout 结构化控制

退出码决定"放行 / 阻塞 / 报错"三态，但 hook 能做的远不止这些——把 stdout 写成事件认可的 JSON，agent 会按字段进一步控制自身行为：放行还是拒绝某次工具调用、把额外信息注入 LLM 视野、要求用户二次确认、强制 agent 继续工作。本文把 2026 年三家工具收敛后的 JSON schema、特殊事件的 raw stdout 注入、JSON 与 exit code 的协同、以及 HTTP hook 的等价语义讲清。

核心概念

agent 看到 stdout 后的判断顺序：先看事件类型，三个特殊事件直接把 stdout 整段作为 system context append；其它事件尝试 JSON parse，成功则按事件认可的顶层字段控制后续行为，不认可的字段静默忽略；JSON parse 失败则整段写 debug log。事件认可字段的差异是这一套 schema 的核心复杂度。

事件特定 JSON schema
PreToolUse 是 schema 最丰富的事件——decision 字段接受三个枚举值：allow 显式放行（与 exit 0 + 空 stdout 等价但语义更明确）、deny 拒绝并把 reason 喂回 LLM（与 exit 2 + stderr 等价，但避免了"诊断信息也算 stderr"的歧义）、ask 触发用户在终端二次确认，常用于"中等风险操作不想硬阻塞、但希望人在环里"的策略。下面是把"任何写 .env 文件的 Edit 调用都要求人工确认"写成 hook 的样子：


#!/usr/bin/env python3
import json, sys
evt = json.load(sys.stdin)
if evt.get("tool_name") in ("Edit", "Write"):
    fp = evt.get("tool_input", {}).get("file_path", "")
    if ".env" in fp:
        print(json.dumps({
            "decision": "ask",
            "reason": f"将修改敏感文件 {fp}，确认继续？"
        }))
        sys.exit(0)
sys.exit(0)
注意是 exit 0 + JSON——decision: "ask" 不等于阻塞，所以走的是 exit 0 路径让 agent 解析 JSON；与之相对，写成 exit 2 + stderr 的话 JSON 会被忽略、reason 会作错误消息硬拦截，达不到"请用户确认"的中间态。


PostToolUse 和 Stop 用的是 block: true——前者是事后批评（工具已经执行，但反馈结果让 Claude 重做或道歉），后者是强制继续（agent 试图 stop 时把它拽回来）。additionalContext 是几乎所有事件都接受的通用字段，用于"放行但额外注入一段信息给 LLM"，最常见于 SessionStart 把环境信息按结构化字段写入而不是 raw stdout。


raw stdout 注入：三个特殊事件
UserPromptSubmit、UserPromptExpansion、SessionStart 三个事件不需要 stdout 是 JSON——整段 stdout 都会作为 system context append 到下一次 LLM 调用。这是把"动态信息每次会话注入"的核心机制：git 状态、当前 branch、CI status、用户最近的 log、团队 SOP——任何随时间变化、不适合写死在 system prompt 里的信息，都通过这三个事件的 raw stdout 注入。


#!/usr/bin/env bash
# SessionStart hook 注入完整环境状态
{
  echo "## 当前工作环境"
  echo ""
  echo "**仓库**: $(basename $(git rev-parse --show-toplevel 2>/dev/null || echo .))"
  echo "**Branch**: $(git rev-parse --abbrev-ref HEAD 2>/dev/null || echo unknown)"
  echo "**CI 状态**: $(gh run list -L1 --json status,conclusion --jq '.[0] | "\(.status) / \(.conclusion)"' 2>/dev/null || echo n/a)"
  echo ""
  echo "## 团队近期 SOP 提醒"
  cat ~/.team/sop-latest.md 2>/dev/null || true
}
exit 0
UserPromptSubmit 与 UserPromptExpansion 的区别细微但重要：前者在用户每次提交 prompt 时触发、注入的内容是"prompt 之外的额外背景"，后者在 prompt 被 expand 时触发（比如调用 slash command）、注入内容可以是"对原 prompt 的改写或扩展"。


JSON 与 exit code 的协同
JSON stdout 与 exit code 的组合行为有四种情形，开发者写 hook 时必须心里有数：






退出码
stdout 状态
行为





0
合法 JSON + 认可字段
按 JSON 字段控制（典型组合）




0
非 JSON 或不认可字段
写 debug log（三特殊事件除外）




2
任何内容
忽略 stdout，stderr 作反馈（阻塞组合）




其它非 0
任何内容
仅 transcript warning，stdout 不解析





最常见的混淆是写了 exit 2 + JSON stdout——期望 agent 既阻塞又解析 JSON。实际行为是 exit 2 优先：stdout 被丢弃，JSON 里的 reason 字段不被读取，agent 读的是 stderr。要让 reason 生效，要么写 exit 0 + JSON {decision: "deny", reason: "..."}（PreToolUse 专用，更优雅），要么写 exit 2 + stderr "..."（适用全部事件、传统做法）。


HTTP hooks：JSON 走 POST body
Claude Code 自 v2.0 起允许把 hook 配置成 HTTP endpoint 而不是本地命令——handler: "http" + url: "https://..." 让 agent 把原本写到 stdin 的 JSON 通过 POST body 发送，把 stdout 的 JSON 通过 HTTP response body 读回。整套 schema 不变，只是 IO 通道从 stdin/stdout 换成 HTTP。响应里 HTTP status code 取代 exit code 语义：200 等价于 exit 0、424 / 422 等价于 exit 2（实现一致）、5xx 等价于其它非 0 warning。


HTTP hook 的使用价值在两个场景突出：团队共享 policy server——所有人 settings.json 引用同一台 hook 服务、规则更新一处生效；重逻辑 hook——本地命令受制于 200ms 性能预算，HTTP 服务可以并发处理、利用缓存数据库、调用 LLM 二次审查。下面是一台 Express HTTP hook server 的最小实现：


import express from 'express';
const app = express();
app.use(express.json());

app.post('/hooks/pretooluse', (req, res) => {
  const { tool_name, tool_input } = req.body;
  if (tool_name === 'Bash' && tool_input?.command?.includes('rm -rf /')) {
    return res.status(422).type('text/plain').send('拒绝：rm -rf 根目录绝对禁止');
  }
  res.status(200).json({
    decision: 'allow',
    additionalContext: 'Bash 命令通过 policy server 审核',
  });
});

app.listen(8788);
对应的 ~/.claude/settings.json 片段：


{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "handler": "http",
        "url": "http://localhost:8788/hooks/pretooluse"
      }
    ]
  }
}
注意 HTTP hook 的两个权衡：响应延迟直接计入 agent 主循环、慢一点 agent 体验劣化；server 挂掉时 agent 端如何 fallback 需要配置（默认是按 timeout 当 exit 0 处理还是当阻塞，按版本不同有差异，部署前必读 release notes）。


陷阱与常见问题
    

  • PreToolUse 写 block: true：block 只对 PostToolUse / Stop 有效，PreToolUse 用 decision；写错字段被静默忽略。
    • 

  • exit 2 同时写 JSON reason：JSON 被忽略，reason 不生效；需要走 exit 0 + {decision:"deny"} 或 exit 2 + stderr。
    • 

  • 三特殊事件混用 JSON 与 raw stdout：SessionStart 同时输出 raw 文本和 JSON 会变成"JSON 整段当文本注入"，因为 raw 模式生效。要么纯 raw、要么用 additionalContext 字段。
    • 

  • HTTP hook 没设 timeout：server 卡死会让 agent 主循环挂住几十秒；配置侧务必加 "timeout_ms": 2000 或类似字段。
    • 

  • 依赖 unrecognized 字段做 side-channel：写 {custom_field: ...} 想存数据被静默忽略；要做 logging 走 stderr 或单独写文件。
    • 



小结
    

  • PreToolUse 用 decision: "allow"/"deny"/"ask" + reason；PostToolUse / Stop 用 block: true；几乎所有事件接受 additionalContext。
    • 

  • UserPromptSubmit / UserPromptExpansion / SessionStart 三事件的 raw stdout 直接作 system context append，是动态信息注入的核心机制。
    • 

  • exit 0 + JSON 是常规控制路径；exit 2 + stderr 是阻塞反馈路径；混用时 exit 2 优先、JSON 被忽略。
    • 

  • HTTP hook 把 stdin/stdout 换成 POST body / response body，schema 不变，适合团队共享 policy server 与重逻辑场景。
    •
