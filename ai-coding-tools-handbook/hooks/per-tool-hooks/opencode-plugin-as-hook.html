OpenCode 的 "plugin = hook" 设计哲学

OpenCode 走了第三条路——不原生兼容 Claude Code hook、也不抄 Codex 的 [hooks] 表，而是把 hook 抽象成 plugin 系统的一部分。社区 issue #12472 长期讨论"是否补一套 Claude 兼容 hooks"，官方明确回应：plugin 系统是更通用的扩展模型，能同时实现 hook + 自定义 tool + UI 注入，没必要拆出独立 hook 体系。这一哲学差异对单工具用户影响小、对跨工具维护用户影响大——本文把 OpenCode 的 plugin 事件、写法、与 Claude hook 的差异、以及"双份维护"痛点讲清。

核心概念

OpenCode plugin 是一份 JavaScript / TypeScript 模块，导出几个 lifecycle 函数与运行时事件 handler。它能做的事比 hook 多：除了在工具调用前后做检查（hook 的本职），还能注册新的 tool 供 LLM 调用、向 UI 注入元素（侧栏面板、状态条等）。"plugin = hook 的超集"是这一设计的核心定位。


为什么不抄 Claude hooks
社区 issue #12472 的官方回应整理出三条理由：






维度
Claude Code hook
OpenCode plugin





配置位置
~/.claude/settings.json
npm 包 / 本地 plugin 目录




编程模型
shell 脚本 + stdin/stdout
JS/TS module export




能力范围
仅 lifecycle 拦截
hook + tool + UI




分发方式
手工复制脚本
npm 包 / OpenCode plugin registry




运行时
子进程
Bun in-process





第一条理由是能力的通用性：plugin 已经能覆盖 hook 的所有用途（拦截、注入、policy），再加一套 hook 体系是重复。第二条是分发模型：plugin 走 npm + plugin registry，可以版本化、依赖管理、自动更新；hook 是 shell 脚本散落各地，分发与升级都不方便。第三条是性能：Bun in-process load 比 fork shell 子进程快两个数量级（毫秒级 vs 几十毫秒），适合高频事件（每次工具调用都触发）。


代价是 OpenCode 用户不能直接复用 Claude Code 社区里大量的 hook 脚本——这就是第 3 章的 bridge pattern 要解决的问题。


三类运行时事件
OpenCode plugin 的运行时 hook 事件只有三个：






事件
触发时机
Claude Code 对应
备注





tool.execute.before
LLM 调用 tool 前
PreToolUse
几乎 1:1 等价




tool.execute.after
LLM 调用 tool 后
PostToolUse
几乎 1:1 等价




session.idle
会话空闲（用户回合或 agent 自然 stop）
Stop（部分等价）
触发条件更广





session.idle 是 OpenCode 独特的事件——它不只在 agent 主动 stop 时触发，用户回合（agent 等用户输入）也触发；要做"agent 试图 stop 时强制继续"需要在 plugin 内部判断是哪种 idle，比 Claude Code 的 Stop hook 多一层逻辑。


Claude Code 的 SessionStart、UserPromptSubmit、SubagentStart 等事件 OpenCode 都没有对应——需要在 plugin 的 enable lifecycle 里做一次性初始化（约等于 SessionStart），或者通过其它 plugin API（如 session.on("message")）间接实现。


写法：plugin 是一个 module
OpenCode plugin 走 JS/TS module，最简版本：


// my-policy-plugin/index.ts
import type { Plugin } from 'opencode-plugin-types';

const plugin: Plugin = {
  name: 'my-policy-plugin',
  version: '1.0.0',

  async onEnable(ctx) {
    ctx.log.info('policy plugin enabled');
  },

  hooks: {
    'tool.execute.before': async (event, ctx) => {
      if (event.tool === 'Bash' && /rm -rf [^\/]/.test(event.input?.command ?? '')) {
        return {
          decision: 'deny',
          reason: '拒绝 rm -rf 非 /tmp 路径，请改用更精确命令',
        };
      }
    },
    'tool.execute.after': async (event, ctx) => {
      if (event.tool === 'Edit' && event.error) {
        ctx.log.warn(`Edit failed: ${event.error}`);
      }
    },
    'session.idle': async (event, ctx) => {
      const sopChecked = await ctx.storage.get('sop_checked');
      if (!sopChecked && event.cause === 'agent_stop') {
        return {
          decision: 'continue',
          message: '请先完成 SOP checklist，再 stop',
        };
      }
    },
  },
};

export default plugin;
关键点：


    

  • lifecycle hook：onEnable / onDisable / onInstall / onUninstall，对应 plugin 启用 / 禁用 / 安装 / 卸载时调用；
    • 

  • runtime hook：hooks.<event_name> 是 async 函数，输入 (event, ctx)，返回 {decision, reason} 或 undefined；
    • 

  • ctx 对象：plugin 间共享的 runtime context，包含 logger、storage（持久化 KV）、其它 plugin API；
    • 

  • TypeScript-first：官方 opencode-plugin-types 包提供完整类型，IDE 自动补全；
    • 

  • Bun 加载：plugin 由 Bun in-process require，无子进程开销，但也意味着 plugin 崩溃可能影响 agent 进程稳定性。
    • 



安装与配置
OpenCode plugin 通过 npm 包或本地路径加载：


// ~/.config/opencode/config.json
{
  "plugins": [
    "opencode-plugin-team-policy",
    "/Users/me/dev/my-local-plugin",
    {
      "name": "opencode-plugin-audit",
      "version": "2.1.0",
      "config": {
        "endpoint": "https://audit.team.io/log"
      }
    }
  ]
}
字段约定：plugin 项可以是字符串（npm 包名或本地路径）或对象（含 name / version / config）。config 字段会在 plugin 的 onEnable 里通过 ctx.config 访问，让同一个 plugin 在不同用户处可以有不同配置。


plugin registry 还在早期阶段——2026 年的 OpenCode 主要靠 npm 直接安装 + 社区维护清单；与 Claude Code 的 plugin marketplace（Anthropic 内部管理）模型不同，OpenCode 更去中心化。


双份维护的痛点
跨工具用户最大的痛是同一份 policy 必须在 Claude settings.json 写一份、在 OpenCode plugin 写一份。下面这张表给出"同一个拦截策略"在两边的对照：






策略
Claude Code
OpenCode





配置位置
~/.claude/settings.json
~/.config/opencode/config.json + plugin 包




拦截 Bash rm -rf
bash 脚本 + exit 2
JS/TS plugin + decision: "deny"




注入 git 状态
SessionStart hook 写 raw stdout
plugin onEnable 调 ctx.session.injectContext()




强制 SOP 完成
Stop hook exit 2
plugin session.idle decision: "continue"




更新策略
改 shell 脚本
npm publish plugin 新版本





两套配置文件、两种编程模型、两种分发渠道——团队规模一大就开始出现"Claude 端规则改了忘改 OpenCode"导致策略不一致。第 3 章 ../3_hooks-pitfalls-and-bridges/2_cross-tool-bridge-patterns.md 给出 bridge 方案——写一个 OpenCode plugin 自动读 ~/.claude/settings.json、map 成 plugin 行为，从而单一信源维护两套工具的 hook 规则。


陷阱与常见问题
    

  • 以为 OpenCode 有 ~/.claude/settings.json 兼容：官方明确不会兼容；需要 plugin bridge 或双份配置。
    • 

  • session.idle 当 Stop hook 用：忘记区分 idle cause 会导致用户输入回合也触发"SOP 检查"，体验崩溃；务必 event.cause === "agent_stop" 判定。
    • 

  • plugin 内同步阻塞：plugin 在 main thread，长时阻塞会让 agent UI 卡顿；async / Promise 必须用对。
    • 

  • lifecycle hook 抛异常：会让 plugin 加载失败，影响其它 plugin；务必 try/catch 兜底。
    • 

  • ctx.storage 不是事务安全：并发 plugin 写同一 key 会竞争；高频写场景需要外部锁或 IndexedDB。
    • 

  • plugin 版本与 OpenCode 不兼容：plugin types 包跟 OpenCode 主版本绑定；升级 OpenCode 后 plugin 可能要重新构建。
    • 



小结
    

  • OpenCode 选择 plugin 作为 hook 的实现方式，不原生兼容 Claude Code hook 体系；issue #12472 官方回应明确这是"plugin 更通用"的设计哲学。
    • 

  • 运行时 hook 事件只有三个：tool.execute.before（≈ PreToolUse）/ tool.execute.after（≈ PostToolUse）/ session.idle（部分 ≈ Stop）；其它 lifecycle 通过 plugin onEnable 等近似实现。
    • 

  • Plugin 是 JS/TS module、Bun in-process load、走 npm 分发；写法比 shell 脚本"应用化"，性能更好但崩溃风险更直接。
    • 

  • 跨工具用户面临双份维护痛点，解决方案是 plugin bridge（详见第 3 章第 2 节）。
    • 

  • 下一篇 ../3_hooks-pitfalls-and-bridges/1_stdout-discipline-and-loop-guards.md 先讲新手最常踩的两个坑。
    •
