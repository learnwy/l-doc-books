Claude Code 事件清单与 5 类 handler

Claude Code 在 2026 年的 hook 体系是三家工具里最完整的——20+ 个事件覆盖 agent 生命周期几乎每一个可观测节点，5 类 handler 把"用哪种方式响应"的选择面从 shell 扩展到 HTTP / MCP / prompt / sub-agent。本文把事件清单、handler 类型、settings.json 配置范式、以及 skill / subagent frontmatter 内嵌 hook 的局部生效语义讲清。

核心概念

事件触发后，agent 按"配置位置 → matcher 过滤 → handler 类型"三步定位到具体响应代码。配置位置决定生效范围（全局 / 项目 / skill / subagent），matcher 决定本次事件是否匹配（按工具名、prompt 正则、文件路径等），handler 决定如何执行（5 类 handler 走完全不同的路径）。

Claude Code 2026 minor 版本在 18-29 个事件之间变动，下表列出主要事件、触发时机、最常见用途：

事件命名遵守"Pre/Post + 名词"或"动词 + 时态"的模式，新版本主要在补全 lifecycle 缺口（如 v2.0 后新增的 PreCompact / PostCompact、TaskCreated / TaskCompleted）。具体清单以 code.claude.com/docs/en/hooks 最新文档为准——升级 minor 时建议过一遍 release notes 看是否新增可用 hook 点。


5 类 handler
Claude Code 的 handler 类型决定 hook 实际执行的形态：


{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash", "command": "~/.team/hooks/check-bash.sh" },
      { "matcher": "Edit", "handler": "http", "url": "https://policy.team.io/hooks/pre" },
      { "matcher": "Read", "handler": "mcp_tool", "server": "audit", "tool": "log_read" },
      { "matcher": ".*", "handler": "prompt", "prompt": "审核当前工具调用是否符合 SOP" },
      { "matcher": "Write", "handler": "agent", "agent": "security-reviewer" }
    ]
  }
}




Handler
执行形态
适合场景
性能预算





command
shell 子进程
简单脚本、本地工具
<200ms




http
HTTP POST
团队共享 policy server
受网络延迟




mcp_tool
调用 MCP server tool
借用已有 MCP 工具能力
取决于 MCP server




prompt
发新 prompt 给同一 LLM
让 LLM 自审、零额外脚本
LLM 响应延迟




agent
spawn sub-agent 处理
复杂判断、独立上下文
sub-agent 启动 + 推理





prompt handler 是 Claude Code 独有的设计——agent 不去 fork 子进程或 HTTP 请求，而是把 hook 当作"给自己发一条 prompt"处理。这让"用 LLM 审 LLM"成本极低，但代价是延迟和 token 消耗——典型场景是 PostToolUse 触发"检查刚才的 Edit 是否符合代码风格"，让 LLM 自己出诊断。


agent handler 则把工作转给一个独立 sub-agent，常用于安全审查、复杂合规检查——sub-agent 有独立 system prompt、独立上下文、可以并发，不污染主对话。


settings.json 配置范式
~/.claude/settings.json 是全局配置，每个项目可以有自己的 <project>/.claude/settings.json 覆盖或补充。完整配置示例：


{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "command": "~/.team/hooks/check-bash-cmd.sh",
        "timeout_ms": 2000
      },
      {
        "matcher": "Edit|Write",
        "handler": "http",
        "url": "http://localhost:8788/hooks/edit",
        "timeout_ms": 3000,
        "on_timeout": "allow"
      }
    ],
    "SessionStart": [{ "command": "~/.team/hooks/inject-git-status.sh" }],
    "Stop": [
      {
        "command": "~/.team/hooks/check-sop-completion.sh",
        "matcher": "main-agent"
      }
    ],
    "UserPromptSubmit": [
      {
        "matcher": "^(deploy|release)",
        "command": "~/.team/hooks/require-confirmation.sh"
      }
    ]
  }
}
字段约定：matcher 是工具名 / prompt 文本的正则；command 是本地脚本绝对路径或 shell 表达式；handler 取 http / mcp_tool / prompt / agent 时填对应字段；timeout_ms 超时；on_timeout 取 allow / deny 决定超时后的兜底行为。


项目级配置优先级高于全局——同一事件、相同 matcher 的 hook 会按"项目 → 全局"顺序执行，任一返回 exit 2 都阻塞。


skill / subagent frontmatter 内嵌
不希望某条 hook 在所有 session 都生效，只想在特定 skill 或 subagent 工作时生效——这种"局部 hook"通过 frontmatter 内嵌实现：


---
name: deploy-helper
description: 部署相关操作的助手 skill
hooks:
  PreToolUse:
    - matcher: 'Bash'
      command: '~/.team/hooks/deploy-policy.sh'
  PostToolUse:
    - matcher: 'Bash'
      handler: prompt
      prompt: '刚执行的部署命令是否符合 checklist？'
---

# Deploy Helper

...
内嵌 hook 只在该 skill 被 invoke 期间生效——skill 进入时 agent 注册 hook、skill 退出时撤销。subagent 同理。这一机制让"hook 范围 = skill 范围"，避免一个 deploy-only policy 污染 daily coding session。


skill / subagent 内嵌 hook 与 settings.json 全局 hook 并存时，两者都会被触发——按"全局 → skill 局部"顺序，任一阻塞均生效；通常局部 hook 会写得更严格（细化 matcher 或加额外检查）。


陷阱与常见问题
    

  • matcher 写正则却没转义特殊字符：Bash|Edit 写成 Bash | Edit（带空格）匹配失败；正则按字面理解写。
    • 

  • timeout 不设兜底：默认超时为阻塞、整个 agent 卡住；要在 server 不稳时给 on_timeout: "allow"。
    • 

  • 同一事件配多个 command 想"任一通过即放行"：实际是"任一 exit 2 即阻塞"，AND 逻辑不是 OR；需要 OR 用单个 hook 内自己判断。
    • 

  • 项目 settings.json 与全局冲突：项目级覆盖语义按字段而非整体（hooks 数组累加），删除全局需写 null。
    • 

  • prompt handler 占用主对话 token：高频事件配 prompt handler 会快速耗 token；建议配低频事件（Stop / SessionStart 等）。
    • 

  • skill frontmatter hooks: 拼错字段：写成 hook: 或 Hooks: 静默不生效，YAML 大小写敏感。
    • 



小结
    

  • 18-29 个事件覆盖 agent 生命周期，PreToolUse / PostToolUse / SessionStart / Stop 是日常 90% 用途的核心。
    • 

  • 5 类 handler（command / http / mcp_tool / prompt / agent）按延迟 / 复杂度 / 独立性选择；简单 policy 用 command，团队共享用 http，让 LLM 自审用 prompt，复杂判断用 agent。
    • 

  • settings.json 全局 vs 项目级 vs skill/subagent frontmatter 三层配置，按"全局 → 项目 → 局部"叠加生效；任一 exit 2 即阻塞。
    • 

  • 局部 hook 解决"只在某 skill 内严格、其它放宽"的常见需求；通过 frontmatter hooks: 字段配置。
    •
