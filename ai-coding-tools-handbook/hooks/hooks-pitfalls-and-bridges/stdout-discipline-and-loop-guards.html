stdout 纪律与无限循环防护

写 hook 的两个高频翻车场景：一是 echo / printf / 调试日志没区分 stdout 与 stderr，导致 agent 解析 JSON 失败、hook silent fail 或返回意外控制结果；二是 hook 自身的副作用再次触发同一 hook，形成 infinite loop 拖垮 agent。这两类坑在三家工具上都存在，本文把 stdout discipline、loop guard 的三层防护、debug vs prod 分离、以及性能预算讲清，并附 bash / python / node 各一份可照搬的最小模板。

核心概念

四条 discipline 互相独立但都必须遵守——只要任一条破了，hook 就可能在某次会话里悄无声息地失效。下面按"discipline → loop guard → 性能预算"顺序讲，每一节给出可照搬模板。

stdout discipline：诊断一律 stderr
agent 把 stdout 作 JSON parser 输入或 context 注入源——任何额外字节都污染。新手写 bash hook 常见这样：


#!/usr/bin/env bash
# 错误示范：echo 诊断信息进 stdout
INPUT=$(cat)
echo "DEBUG: 收到 input: $INPUT"          # 污染 stdout
TOOL=$(jq -r '.tool_name' <<< "$INPUT")
if [ "$TOOL" = "Bash" ]; then
  echo "DEBUG: 命中 Bash branch"           # 污染 stdout
  echo '{"decision": "allow"}'             # 与 DEBUG 拼在一起、JSON 无效
fi
exit 0
这段脚本看起来"先打日志、最后输出 JSON"，但 stdout 实际是：


DEBUG: 收到 input: {"tool_name":"Bash",...}
DEBUG: 命中 Bash branch
{"decision": "allow"}
agent JSON.parse 第一行就失败、整段被当 debug log 丢弃、decision: "allow" 不生效。修正方法是把所有诊断 >&2：


#!/usr/bin/env bash
INPUT=$(cat)
echo "DEBUG: 收到 input: $INPUT" >&2       # 走 stderr
TOOL=$(jq -r '.tool_name' <<< "$INPUT")
if [ "$TOOL" = "Bash" ]; then
  echo "DEBUG: 命中 Bash branch" >&2
  echo '{"decision": "allow"}'             # 唯一 stdout 输出
fi
exit 0
三条规则记牢：诊断信息一律 >&2；stdout 只在 exit 0 + 需返回 JSON 时才写；exit 2 时 stderr 是反馈通道、stdout 完全不用。


Python 最小模板
#!/usr/bin/env python3
import json, sys

def log(*args):
    print(*args, file=sys.stderr)  # 诊断一律走 stderr

def main():
    try:
        evt = json.load(sys.stdin)
    except json.JSONDecodeError as e:
        log(f"hook input not JSON: {e}")
        sys.exit(0)  # 自身错误不阻塞 agent

    log(f"event tool: {evt.get('tool_name')}")

    if evt.get("tool_name") == "Bash":
        cmd = evt.get("tool_input", {}).get("command", "")
        if "rm -rf /" in cmd:
            print("拒绝：禁止 rm -rf 根目录", file=sys.stderr)
            sys.exit(2)

    sys.exit(0)

if __name__ == "__main__":
    try:
        main()
    except Exception as e:
        log(f"hook crash: {e}")
        sys.exit(0)  # 兜底：crash 也不影响 agent
Node 最小模板
#!/usr/bin/env node
const log = (...args) => process.stderr.write(args.join(' ') + '\n');

const chunks = [];
process.stdin.on('data', (c) => chunks.push(c));
process.stdin.on('end', () => {
  let evt;
  try {
    evt = JSON.parse(Buffer.concat(chunks).toString());
  } catch (e) {
    log('hook input not JSON:', e.message);
    return process.exit(0);
  }
  log('event tool:', evt.tool_name);
  if (evt.tool_name === 'Bash') {
    const cmd = evt.tool_input?.command ?? '';
    if (cmd.includes('rm -rf /')) {
      log('拒绝：禁止 rm -rf 根目录');
      return process.exit(2);
    }
  }
  process.exit(0);
});
三段模板共同遵守：logger 走 stderr、JSON parse 包 try/catch、入口 try/catch 兜底 exit 0、阻塞场景 stderr 写理由 + exit 2。


无限循环防护：三层 guard
infinite loop 在 hook 系统里最常见的三个场景：






场景
触发链
危险事件





文件副作用
FileChanged hook 写文件到被监听路径
FileChanged → 自己




会话副作用
SessionStart hook 调命令引发新 session
SessionStart → 新 session → SessionStart




工具递归
PostToolUse 在 hook 内调用同名工具
Bash → PostToolUse → Bash → ...





三层防护按"易到难"叠加使用：


第一层 — 路径 / 名称 exclude：FileChanged hook 必须明确排除"自己会写"的路径。借用 .gitignore 风格的 .hookignore 文件：


# .hookignore
.hooks-log/
.cache/
*.tmp
import fnmatch, pathlib

def is_excluded(path: str) -> bool:
    patterns = pathlib.Path(".hookignore").read_text().splitlines()
    return any(fnmatch.fnmatch(path, p.strip()) for p in patterns if p.strip())
第二层 — re-entry guard：用环境变量或锁文件标记"当前在 hook 内执行"，进入时设、退出时清，hook 入口检查到已设就早退：


#!/usr/bin/env bash
if [ -n "${IN_HOOK:-}" ]; then
  echo "re-entry detected, skip" >&2
  exit 0
fi
export IN_HOOK=1
trap 'unset IN_HOOK' EXIT
# ... 真正的 hook 逻辑 ...
第三层 — call counter：同一事件链触发次数计数，超过 N 次就主动 exit 2 报错。用一个临时文件作计数器：


#!/usr/bin/env bash
COUNTER_FILE="/tmp/hook-counter-$$"
COUNT=$(cat "$COUNTER_FILE" 2>/dev/null || echo 0)
COUNT=$((COUNT + 1))
echo "$COUNT" > "$COUNTER_FILE"
if [ "$COUNT" -gt 5 ]; then
  echo "hook chain depth > 5, aborting" >&2
  rm -f "$COUNTER_FILE"
  exit 2
fi
# ... hook 逻辑 ...
三层叠加用：第一层防可预测的路径副作用、第二层防同进程链 re-entry、第三层兜底防"漏配"。生产环境 hook 至少配置前两层。


debug log 与生产分离
开发阶段 hook 通常配大量 stderr 诊断、加 2>>$LOG_FILE 把 stderr 落盘：


exec 2>>"$HOME/.hook-logs/$(date +%Y%m%d).log"
生产环境必须切掉这条——一来 disk 会被高频事件刷满，二来诊断信息泄露内部行为可能被恶意构造的输入利用。建议用环境变量切换：


if [ "${HOOK_DEBUG:-0}" = "1" ]; then
  LOG="$HOME/.hook-logs/$(date +%Y%m%d).log"
  mkdir -p "$(dirname "$LOG")"
  exec 2>>"$LOG"
fi
对应 ~/.claude/settings.json 设 "env": { "HOOK_DEBUG": "1" } 开启诊断、生产环境删掉环境变量即可关。


性能预算：<200ms 同步 vs async fire-and-forget
synchronous hook 阻塞 agent 主循环——hook 执行时长直接计入用户感知延迟。经验阈值：单次 hook 应 <200ms。常见超标场景：


    

  • hook 内做网络请求（HTTP API 调用、git 远程操作）—— 200ms+ 起步；
    • 

  • hook 内启动 Python / node 解释器 —— 50-100ms 冷启动成本；
    • 

  • hook 内调 LLM —— 秒级；
    • 

  • hook 内读大文件做静态分析 —— 取决于文件大小。
    • 



慢逻辑的处理方式是async fire-and-forget：把慢部分后台跑、同步部分立即 exit 0：


#!/usr/bin/env bash
INPUT=$(cat)
# 同步部分：快速检查
TOOL=$(jq -r '.tool_name' <<< "$INPUT")
[ "$TOOL" = "Bash" ] || exit 0

# 异步部分：后台跑慢逻辑（审计、上报）
(
  CMD=$(jq -r '.tool_input.command' <<< "$INPUT")
  curl -s -X POST https://audit.team.io/log \
    -H "Content-Type: application/json" \
    -d "{\"cmd\": $(jq -Rn --arg c "$CMD" '$c')}"
) >/dev/null 2>&1 &

# 立即 exit
exit 0
代价是 agent 不等异步任务结果——审计上报失败、外部系统不一致都需要异步任务自己重试。fire-and-forget 适合"记录性"逻辑（审计、metrics、通知），不适合"决策性"逻辑（policy enforcement、确认必须在工具调用前完成）。


陷阱与常见问题
    

  • printf 比 echo 更隐蔽：忘加 >&2 同样污染 stdout，且 printf 没换行容易拼坏 JSON。
    • 

  • set -x 调试模式 stderr 满地跑：开发时方便，但 2>>$LOG 时整段 trace 进 log，文件爆得快；调试完务必关掉。
    • 

  • re-entry guard 用全局环境变量：跨进程不共享，子进程的 hook 看不到父进程的标记；建议改用临时文件 + pid。
    • 

  • call counter 文件名不带 pid：多个 agent 进程共用一个 counter 文件，正常并发被误判循环。
    • 

  • fire-and-forget 漏 redirect：后台任务的 stdout / stderr 没 >/dev/null 2>&1 会污染 hook stdout、破坏 JSON。
    • 

  • 认为 timeout 能救慢 hook：timeout 是兜底、不是性能优化；agent 等 timeout 整段等于阻塞了 timeout_ms。
    • 



小结
    

  • stdout 只用于 JSON / 三特殊事件 raw 注入；所有诊断信息走 stderr；exit 2 时 stdout 完全不用。
    • 

  • 三层 loop guard 叠加：.hookignore 路径 exclude、re-entry 标记、call counter；生产至少配前两层。
    • 

  • debug log 用环境变量切换；生产环境关闭以免 disk 爆与信息泄露。
    • 

  • 性能预算 <200ms 同步；慢逻辑用 async fire-and-forget，但承担"agent 不等"代价、仅适合记录性任务。
