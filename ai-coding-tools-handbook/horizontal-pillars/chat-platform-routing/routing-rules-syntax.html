路由规则 DSL 语法

核心概念

5 级 lookup 的优先级架构已经在 ../../2_modules-deep/5_multi-tenant-personas/1_five-level-routing-lookup.md 讲清。本篇换一个视角——从"管理员"的角度，看怎么把一条业务诉求（"我希望 DM 都走默认 persona、incident-room 走 on-call"）写成 YAML / JSON 规则文件。重点是 DSL 的字段语义、guard 条件、fallback 链、四种最常见的场景模板。规则文件 OpenClaw 启动时静态校验、运行时热加载。

YAML / JSON 双 schema
OpenClaw 的规则文件支持 YAML（默认推荐）与 JSON 两种 schema，语义等价。YAML 更适合手写——人类读 / 写 / git diff 都更舒服；JSON 适合程序生成（例如 admin UI 导出）。两种 schema 共用同一份 JSON Schema 校验：


# routing.yaml — 推荐手写格式
version: '1'
peer_rules:
  - peer_id: 'ou_alice_xxx'
    platform: 'lark'
    persona: 'dev_bytedance'
    audit: true
parent_rules:
  - parent_id: 'workspace_bytedance'
    persona: 'dev_bytedance'
    inherit_to_children: true
fallback:
  persona: 'personal_default'
  warn_on_use: true
{
  "version": "1",
  "peer_rules": [{ "peer_id": "ou_alice_xxx", "platform": "lark", "persona": "dev_bytedance", "audit": true }],
  "fallback": { "persona": "personal_default", "warn_on_use": true }
}
OpenClaw 启动时验证：unknown 字段拒绝（防 typo）、persona 必须在 personas catalog 中已定义、字段类型严格。


guard 条件：sender / channel / regex
每条规则可以挂一组 guard 条件作为额外过滤。命中 lookup 级别后还要 guard 都通过才算 hit。guard 支持三种主要形态：


peer_rules:
  - peer_id: 'ou_alice_xxx'
    persona: 'dev_bytedance'
    guard:
      sender_role_in: ['leader', 'tech_lead'] # 仅特定角色发的消息
      channel_kind: 'im' # 仅在 DM
      text_regex: '^/deploy ' # 命令前缀匹配
      time_window:
        start: '09:00'
        end: '19:00'
        tz: 'Asia/Shanghai'

语义

guard 失败时不是"路由失败"，而是继续在同 lookup 级别向后看下一条规则——这与 lookup 级别本身的优先级机制正交。


fallback 链：多级兜底
OpenClaw 支持把 fallback 写成一条链而不是单一 persona——按顺序尝试，前者拒绝才退到后者：


fallback:
  chain:
    - condition: 'channel_kind == "im"'
      persona: 'personal_dm'
    - condition: 'sender_external == true'
      persona: 'public_safe'
    - default: true
      persona: 'personal_default'
  warn_on_use: true




链元素
触发条件
适用场景





condition 表达式
表达式 true 才命中
按 message 属性分流




default: true
链尾，任何前面未命中都走此
全局兜底





fallback 链让"按 channel kind 区分默认 persona"成为可能——不需要在 channel_rules 里枚举所有 channel id。


场景模板（一）：DM 默认 persona
最常见的需求："1:1 私聊都用一个默认 persona，不写每个 peer"。用 fallback 链 + channel kind guard 实现：


fallback:
  chain:
    - condition: 'channel_kind == "im"'
      persona: 'dm_default'
    - default: true
      persona: 'personal_default'
或者更显式——给 IM 写专门的 channel rule（但只写一条通配）：


channel_rules:
  - channel_kind: 'im' # 所有 DM
    persona: 'dm_default'
    priority: 100
两种写法等价；维护者偏好 fallback chain 写法因为它更 explicit "this is the catch-all"。


场景模板（二）：channel keyword 触发 persona
需求："某 channel 在消息以 /oncall 开头时切换到 oncall persona，其他时候保持默认"。用 channel rule + text_regex guard：


channel_rules:
  - channel_id: 'lark_oc_incidents'
    persona: 'oncall_engineer'
    guard:
      text_regex: '^/oncall '
    priority: 10
  - channel_id: 'lark_oc_incidents' # 同 channel 默认
    persona: 'engineer_default'
    priority: 20
priority 数字小者先匹配——/oncall 前缀命中 oncall persona，其他流量走 engineer_default。


场景模板（三）：sender role 决定 persona
需求："来自 admin 的所有消息走 ops persona、外部承包商走受限 persona"。这是 role-based 路由的典型场景：


role_rules:
  - role_id: 'lark_admin'
    platform: 'lark'
    persona: 'ops_admin'
    audit: true
  - role_id: 'lark_external_contractor'
    platform: 'lark'
    persona: 'dev_external_safe'
    guard:
      channel_kind_in: ['im', 'group'] # 不在公共频道触发
role_id 必须带平台前缀（如 lark_* / slack_*）避免跨平台同名冲突——这是 multi-platform OpenClaw 部署的高频陷阱。


场景模板（四）：time-of-day on-call
需求："工作时间外的 incident-room 消息走 on-call persona、工作时间内走 engineer persona"。time_window guard 直接表达：


channel_rules:
  - channel_id: 'lark_oc_incidents'
    persona: 'oncall_after_hours'
    guard:
      time_window:
        start: '19:00'
        end: '09:00' # 跨午夜
        tz: 'Asia/Shanghai'
    priority: 5
  - channel_id: 'lark_oc_incidents'
    persona: 'engineer_default'
    priority: 50
OpenClaw 在 evaluator 里把"跨午夜"区间正确处理——start > end 视为"夜间窗口"。时区固定到规则配置而不是 server 时区，便于跨地区部署。

陷阱与常见问题
    

  • persona 写错被静默忽略：未在 personas catalog 注册的 persona 名会导致整条规则被跳过——OpenClaw 启动校验已经检测，但 reload 时若 personas 文件先变 OpenClaw 可能 race。reload 顺序：先 personas、再 routing。
    • 

  • guard 用错运算符：sender_role_in 接列表，写成单字符串会报 schema error；channel_kind 接单值，写列表用 channel_kind_in。两者名称区分清楚。
    • 

  • time_window 没写时区：默认 UTC——admin 在中国常忘改，导致工作时间窗口错位 8 小时。强烈建议每条 time_window 显式 tz。
    • 

  • fallback chain default 缺失：所有 condition 都不命中时静默不路由——消息丢失。default: true 必须存在。
    • 

  • 正则没 anchored：text_regex: '/deploy ' 不带 ^ 匹配子串，会被 spam 文本意外触发。命令型规则用 ^/cmd 显式 anchor。
    • 

  • 跨平台 role_id 同名冲突：飞书 / Slack 的 moderator role id 字符串相同但语义不同。必须 platform 前缀。
    • 



小结
routing DSL 把 5 级 lookup 的配置语法标准化为 YAML / JSON 两种 schema，外加一组 guard（sender_role / channel_kind / text_regex / time_window / platform）做二级过滤。fallback 链让"按 message 属性分流到不同默认 persona"成为可能，比硬编码 channel rule 更简洁。四种场景模板（DM 默认 / channel 关键字 / sender role / time-of-day）覆盖了 90% 实际部署。下一篇讲规则命中的 persona 如何与 channel 形成 N:M 绑定、绑定如何持久化、跨设备/跨重启一致性怎么保。
