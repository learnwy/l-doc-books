IM 触发自动化

核心概念

Cron 是 agent 自动触发，IM 触发是用户主动输入命令——本质都是把 inbound event 接到同一 transform 管线。"在飞书发 /deploy staging" 比"打开 CI 网页点 deploy 按钮"快两个数量级，且天然带审计（消息记录在 chat 历史里）。本篇按"slash command 语法 + 命令解析 + persona 权限校验 + 异常处理 + audit log"五块讲清。三个高频典型场景：/deploy <env> 触发 CI、/status <service> 拉 dashboard、/oncall handoff 切换 on-call persona。

Slash command 语法
OpenClaw 沿用业界惯例的 slash command 风格：/<cmd> [<positional> ...] [--flag value]。命令本身用斜杠开头是为了区分自然语言对话——agent 看到 / 前缀知道走结构化解析路径而不是 LLM 自由理解。


/deploy staging --service api-gateway --version v2.3.1
/status prod --service api-gateway
/oncall handoff --to alice@example.com
/recall yesterday --range "9:00-12:00"
/lock-prod --confirm-totp 123456

LLM 自由理解的版本（"帮我部署 staging"）也能跑通，但要经过 NL → 结构化命令的二次转换——slash command 是 fast path，自然语言是 slow path。


命令解析器
解析器输入是 Message.text，输出是结构化 Command 对象：


@dataclass
class Command:
    name: str
    args: list[str]
    flags: dict[str, str]
    raw_text: str
    sender_id: str
    channel_id: str

def parse(text: str) -> Command | None:
    if not text.startswith("/"):
        return None
    tokens = shlex.split(text[1:])
    name, rest = tokens[0], tokens[1:]
    args, flags = [], {}
    i = 0
    while i < len(rest):
        if rest[i].startswith("--"):
            key = rest[i][2:]
            val = rest[i+1] if i+1 < len(rest) and not rest[i+1].startswith("--") else "true"
            flags[key] = val
            i += 2
        else:
            args.append(rest[i])
            i += 1
    return Command(name=name, args=args, flags=flags, raw_text=text, ...)
shlex.split 是关键——它正确处理引号、转义、空格，避免 --message "hello world" 被错误分割。后续命令注册表按 name 路由到 handler。


命令注册表
Personal-agent 在启动时把"哪些命令存在 / 谁能用"扫描进注册表：


# ~/.openclaw/commands.yaml
commands:
  - name: deploy
    handler: 'ci.deploy'
    args:
      - name: env
        choices: ['staging', 'prod']
        required: true
    flags:
      service: { type: 'string', required: true }
      version: { type: 'string', default: 'latest' }
    persona_allow: ['work_focus', 'oncall']
    risk: 'high'
    require_confirm_if: 'env == "prod"'

  - name: status
    handler: 'observability.status'
    args:
      - name: env
        choices: ['staging', 'prod']
    persona_allow: ['*']
    risk: 'low'

注册表也是 SoT——admin 改 yaml 后 reload 立即生效，未注册命令一律 reject（防止 typo 触发未预期 action）。

persona_allow 列表决定哪个 persona 能跑该命令——这是 IM 触发自动化的核心防护：

注意"sender 当前 persona"由路由 5 级 lookup 决定——同一用户在不同 channel / 时段下当前 persona 不同。这是 IM 触发自动化与 cron 的根本区别：cron 自带 persona 配置，IM 触发的 persona 由路由动态决定。


三个典型场景
场景一：/deploy staging
[work_chat] 用户: /deploy staging --service api-gateway
[bot]      正在调用 CI（job_id: build-12345）...
           20s 后:
[bot]      Deploy staging api-gateway v2.3.1 完成 ✓
           Dashboard: https://ci.example.com/jobs/12345
幕后：persona work_focus → command deploy + env=staging → risk=high but env != "prod" → 不需 confirm → 调 CI webhook → 等结果 → 投回 chat。


场景二：/status prod
[any_chat] 用户: /status prod
[bot]      Prod 服务状态（拉自 grafana）：
           - api-gateway:   healthy, p95=42ms, rps=1.2k
           - search:        healthy, p95=130ms, rps=300
           - billing:       degraded, error_rate=2%, alarms=1
低风险查询命令 persona_allow 配 *——任何 persona 都可查询。结果直接 fetch + 格式化回复，不走 confirm。


场景三：/oncall handoff --to alice
[oncall_chat] 用户: /oncall handoff --to alice@example.com
[bot]         正在校验 alice 接班资格 ...
[bot]         alice 已确认接班 ✓
              Oncall persona 已绑定到 alice 的飞书 DM
              Audit: handoff_event_id=h-7821
oncall handoff 是 persona-switching 操作——需要 alice push confirm。confirm 成功后路由规则原子更新（oncall persona 绑定从旧 sender 切到 alice），新 alerts 自动路由到 alice。

所有异常都走相同格式：简短 + 可操作。CI 调用失败时回复必须含 trace_id 或 job_id，让用户能跳到 dashboard 查根因——不是"failed, please retry"这种无信息回复。


Audit log
每一条 IM 触发命令都写 audit log——这是 IM 触发自动化最大的安全优势：


{
  "event_id": "im-cmd-9821",
  "ts": "2026-05-14T15:42:33Z",
  "sender": "u-12345",
  "persona": "work_focus",
  "channel": "lark_oc_deploy",
  "command": "deploy staging --service api-gateway",
  "decision": "allow",
  "confirm": null,
  "execution": {
    "started_at": "2026-05-14T15:42:34Z",
    "duration_ms": 20100,
    "status": "success",
    "downstream_id": "ci-build-12345"
  }
}
audit log 存到 ../../2_modules-deep/5_multi-tenant-personas/3_per-tenant-key-and-audit.md 讲的 per-tenant audit store——按 persona 分库 + 加密，admin 可按 sender / command / 时间范围 query。


陷阱与常见问题
    

  • 命令前缀冲突：/deploy 在两套不同 personas catalog 注册不同 handler。注册表必须 namespaced 或全局唯一。
    • 

  • shlex 处理 emoji：用户可能复制带 emoji 的 message——shlex 多数版本能正确处理，但旧版有 bug。CI 单测必须覆盖含 emoji 的 message。
    • 

  • flag 值含 --：--message "--help me" 可能被误解析为新 flag。registry 应允许显式声明 "rest is positional"。
    • 

  • persona_allow 写 *：低风险查询命令可以，但 /deploy /lock-prod 绝不可——所有 high-risk 命令必须显式列 allow。
    • 

  • confirm push 失败静默通过：与 home action 同理，fail-secure——push 服务挂了视为 deny。
    • 

  • 回复中泄露内部 trace_id 格式：trace_id 可以暴露，但内部 IP / 主机名 / token 不应。回复模板要 redact 敏感字段。
    • 



小结
IM 触发自动化把 slash command 接到 transform 管线——用户 /deploy staging 经过解析 → persona 权限校验 → 风险评估 → 可选 confirm → 执行 → audit。命令注册表是 single source of truth，未注册命令一律 reject。三类典型场景（CI/CD 触发、状态查询、persona 切换）覆盖 90% 实际使用；异常处理必须包含可操作的 trace_id；所有命令都写 audit log 进 per-tenant store。结合本章前两篇——smart-home 提供物理动作、cron 提供时间触发、IM 触发提供用户主动入口——personal-agent 把"日常生活自动化"做成有结构、可审计、安全可控的工程系统。下一章进入 7 种 terminal 沙箱后端。
