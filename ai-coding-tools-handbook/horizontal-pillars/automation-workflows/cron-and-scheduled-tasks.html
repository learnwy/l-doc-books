Cron 周期任务与 hooks 协同

核心概念

Personal-agent 的"自动化"价值很大一块来自 cron 周期任务——既不需要用户主动触发，也不依赖外部消息推送。Hermes 的 curator daily 03:00 整理 memory、用户自定义 skill "每天 09:00 拉昨天 memory summary 进 inbox"、月底总结脚本等都属此类。本篇按"Hermes curator schedule + user-defined cron skill + hooks transform 协同 + 失败重试与漂移修正"四块讲清。

Hermes curator schedule
Hermes 的 curator 是 ../../2_modules-deep/1_persistent-memory/4_curator-maintenance-cycle.md 详述的 memory 维护循环——默认每天本地时间 03:00 运行。它在所有 personas / sessions 全部 idle 后才启动，避免与 active session 抢锁。


# ~/.hermes/config.yaml
curator:
  schedule: 'daily'
  at: '03:00'
  tz: 'Asia/Shanghai'
  prerequisites:
    - 'all_sessions_idle'
    - 'disk_free_gb > 5'
  on_failure:
    - 'log + retry_next_day'
    - 'notify_user_after_3_consecutive_failures'




配置项
语义





schedule
daily / hourly / cron expression




at
触发时间（带 tz）




prerequisites
启动前置条件




on_failure
失败处理策略





curator 是"系统级"cron，与下面用户自定义 skill 走同一个 scheduler 但有不同的 reliability 要求——curator 失败必须重试且通知用户。


用户自定义 cron skill 范式
用户写一个 skill 标注 trigger: cron 即可注入到 scheduler。典型场景：






场景
cron 表达式
行为





每日早间 brief
0 9 * * *
拉前一天 MEMORY summary 投 IM




周一晨会 prep
0 8 * * 1
拉上周 OKR 进展 + 本周日历




月底总结
0 23 28-31 * *
月底最后一天，跑总结写文档




每小时 health check
0 * * * *
检查 agent 各模块状态




每 5 分钟轮询
*/5 * * * *
检查未读 PR / issue





# ~/.hermes/skills/daily-brief/skill.yaml
name: daily-brief
trigger:
  cron: '7 9 * * *' # 9:07 而非整点 0，避开 cron 高峰
  tz: 'Asia/Shanghai'
run:
  - shell: 'hermes summarize --range "yesterday"'
  - shell: 'lark-cli im send --chat-id "$DAILY_BRIEF_CHAT" --md $OUT'
注意 cron 表达式用 9:07 而非 9:00——大量 cron 任务同时落在整点会让 IM / API 突发，错峰几分钟显著减少 rate-limit 撞车（这点在 schedule skill 文档里也强调）。


Cron 与 hooks transform 管线协同
Cron 触发 event 后不会"直接执行命令"——它走 ../../2_modules-deep/4_hooks-transform-pipeline/ 讲的 transform 管线。流程：






Transform 阶段
作用





enrich context
注入当前时间 / persona / 环境变量




persona resolve
决定以哪个 persona 运行




permission check
校验 persona 是否可执行此 cron




(optional) human-confirm
高敏感 cron 可要求 push confirm





persona resolve 是关键——同一个 daily-brief skill 在不同 persona 下行为不同（work persona 走工作 chat、hobby persona 走个人 chat）。cron skill 在 skill.yaml 里声明 persona: work_focus 或 persona: $auto（按时间窗口推断）。


失败重试与时间漂移修正
Cron 调度不是"承诺准时"，是"在指定时间后尽快触发一次"。系统休眠 / 进程崩溃 / 时钟跳变都会导致漂移。Hermes scheduler 应对：






catch-up 策略
行为
适用





once
错过 N 次只补跑最近一次（默认）
daily brief / 通知




all
错过 N 次依次补跑全部
累积型任务（少见）




skip
错过全部跳过
与时间强相关任务（如打卡）





合理默认是 once——错过的早间 brief 在中午醒来时跑一次足够，跑三次反而 spam。打卡 / 闹钟类用 skip——错过就错过。


失败重试与告警
任务失败时的策略：


on_failure:
  retry:
    max_attempts: 3
    backoff: 'exponential' # 1m, 5m, 25m
  alert:
    after_consecutive: 3 # 连续 3 次失败才告警
    channel: 'lark_dm_self'




失败类别
处理





暂时网络错误
指数回退重试




API 鉴权失败
立即告警，无重试




内部 bug（panic）
立即告警 + audit




资源不足（disk full）
等待 + 重试





连续 3 次失败才告警——避免单次抖动 spam push。但鉴权类失败（token 过期）必须立即告警，因为再多重试也无济于事。


时钟跳变与 DST
cron 的两个隐藏陷阱：






现象
表现
处理





系统休眠 / 待机
wake 后 cron 时间已过
用 monotonic timer 检测 missed




DST 切换
02:30 任务在 spring-forward 不存在
推后到下一存在的 02:30 / 提前 1h




NTP 时钟跳变
时间向前跳跃
重计算 next fire time




时区配置错误
任务在错误的本地时间触发
tz 必须显式而非依赖 system tz





Hermes scheduler 用 monotonic clock + wall clock 双源校对——任何不一致都 log warning 并按 wall clock 重新计算。


Cron skill 实战：daily memory summary
完整端到端例子——每日早 9:07 把昨天的 memory 拉成 summary 投 IM：


# ~/.hermes/skills/daily-memory-summary/skill.yaml
name: daily-memory-summary
trigger:
  cron: '7 9 * * *'
  tz: 'Asia/Shanghai'
  catch_up: 'once'
persona: work_focus
permission:
  - 'read_memory'
  - 'send_im'
run:
  - shell: |
      hermes recall --range "yesterday" --format markdown > /tmp/brief.md
  - shell: |
      lark-cli im send \
        --chat-id "$DAILY_BRIEF_CHAT" \
        --md /tmp/brief.md
on_failure:
  retry:
    max_attempts: 3
    backoff: exponential
  alert:
    after_consecutive: 3
    channel: lark_dm_self




字段
作用





persona
决定运行身份




permission
声明所需权限，scheduler 启动期校验




run
步骤化命令，顺序执行




catch_up
漂移恢复策略




on_failure
失败处理





这套 skill yaml 提交后 scheduler 自动注册——无需 restart agent。运行时通过 transform 管线确认 persona 与 permission 后实际跑 shell。


陷阱与常见问题
    

  • 所有 cron 都写 0 9 * * *：所有用户全球 9:00 整撞 API rate-limit。错峰几分钟（7 9、13 9）显著减少撞车。
    • 

  • 不写 tz：默认 UTC——admin 在中国常忘改，导致任务在错误时间触发。强制 tz。
    • 

  • catch_up: all 用错地方：错过 7 天的 daily brief 一次性跑 7 次刷 IM——用 once 即可。
    • 

  • persona 漂移：cron 注册时 persona 还在白名单，后来管理员删了 persona，scheduler 启动期校验失败。skill yaml 改动后必须 reload 校验。
    • 

  • DST 跨时区任务：用户在跨时区差旅时 cron 还按原 tz 触发，导致"早间 brief"半夜响。可加 follow_user_tz: true 让 scheduler 用当前时区。
    • 

  • shell 命令引号缺失：--md $OUT 在路径含空格时失败——脚本步骤必须严格 quote 变量。
    • 



小结
cron 周期任务是 personal-agent 自动化的核心模式。Hermes curator + 用户自定义 cron skill 共用同一 scheduler，所有触发都走 hooks transform 管线（enrich → persona resolve → permission check → action）。失败重试默认指数回退、连续 3 次告警；catch-up 默认 once 避免补跑过多；时钟跳变 / DST / 跨时区是隐藏雷区。整套设计把"准时"放在第二位，把"可观察 + fail-secure + 不 spam"放在第一位。下一篇讲 IM 触发自动化——把同一套 transform 管线接到用户主动输入的 slash command 上。
