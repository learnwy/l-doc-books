智能家居集成与安全策略

核心概念

Personal-agent 接入智能家居（HomeKit / Home Assistant）是 Tier 2 工具栈"生活自动化"价值的入口——让 agent 根据日程、IM 消息、用户状态自动调灯 / 温控 / 门锁 / 摄像头。但 home automation 远比纯 software action 危险：误调温控、误锁门、误开摄像头都有实际后果。本篇按"两套主流平台 + 设备状态访问 + 安全策略 + persona-aware 触发"四块讲清。安全策略部分是重点——比集成本身更需要严格设计。

HomeKit：Apple 平台内的安全模型
HomeKit 用 HAP（HomeKit Accessory Protocol）通信，设备直接与 Apple 设备配对，云端是可选的。Personal-agent 想接 HomeKit 必须通过 bridge——常见做法是用 Homebridge（Node 实现的 HAP server）或 Home Assistant 的 HomeKit Bridge 把 agent 暴露成 HAP accessory。


// Homebridge plugin 暴露 agent action
const accessory = new Accessory('Personal Agent', uuid);
accessory
  .getService(Service.Switch)
  .getCharacteristic(Characteristic.On)
  .on('set', async (value, callback) => {
    if (value === true) {
      await agent.triggerScene('evening_focus');
    }
    callback();
  });
bridge.publish({ port: 51826, pincode: '031-45-154' });
HomeKit 的 user-presence 与 device state 在 HAP 协议里以 characteristic 形式暴露——例如 CurrentTemperature / LockTargetState。Agent 通过 read characteristic 拿状态、write characteristic 改状态。所有通信只走本地 Wi-Fi——这是 HomeKit 的隐私优势，也意味着 agent 必须与 device 同子网。


Home Assistant：跨平台开源 hub
Home Assistant 是事实标准的开源 home hub，支持 1000+ 集成（MQTT / Zigbee2MQTT / Z-Wave JS / Tuya / Xiaomi 等）。Personal-agent 接 HA 走三类入口：


import requests

HA_URL = "http://homeassistant.local:8123"
TOKEN = "long-lived-access-token"

# REST: 读状态
resp = requests.get(
    f"{HA_URL}/api/states/light.living_room",
    headers={"Authorization": f"Bearer {TOKEN}"},
)
state = resp.json()["state"]  # "on" / "off"

# REST: 服务调用
requests.post(
    f"{HA_URL}/api/services/light/turn_on",
    headers={"Authorization": f"Bearer {TOKEN}"},
    json={"entity_id": "light.living_room", "brightness": 128},
)

WebSocket 订阅是 personal-agent 监控家庭状态的核心——state_changed 事件流推送每次设备变化，agent 可基于此做出反应（如门锁 unlocked 时记录 audit、温度过低时调高）。

灯属于低风险——agent 可在用户登录工作 persona 后自动调到 work scene。温控是中风险——误操作可能让家里太冷/太热。门锁与摄像头是高风险——任何 unlock / 开监控都属于安全敏感操作。

L1 与 L4 经常配合：work persona 可直接调灯 + 温控（L4 跳过），但门锁 unlock 必须 hobby_home persona 在场 + L4 confirm。


Persona-aware actions
不同 persona 对应不同的"角色场景"——personal-agent 工作时段下用 work_focus persona、晚上用 home_relax persona。Home action 白名单按 persona 区分：


personas:
  work_focus:
    home_actions:
      allow:
        - light.work_room.* # 工作房灯
        - climate.work_room.set # 工作房温控
      deny:
        - lock.* # 工作中不应解锁门
        - camera.* # 工作中不应开摄像头

  home_relax:
    home_actions:
      allow:
        - light.* # 全屋灯
        - climate.*
      deny:
        - lock.front_door.unlock # 即使家用 persona 也要 confirm
      require_confirm:
        - camera.*
work persona 在白天误触发"unlock front door"——L1 直接 reject 因为 unlock 不在 work allow 列表里。这种"以 persona 为安全边界"的设计比单纯写"用户身份"更细——同一个用户在不同时段下的权限就该不同。

深夜（0–6 时）大部分操作 reject——agent 既不应该在用户睡觉时突然调温控，也不应该让任何人在深夜远程 unlock 门。这层约束硬编码在 OpenClaw 默认配置，用户可显式覆盖（但必须 explicit override）。

Push 是默认——agent 触发 unlock 时立刻发 push："Confirm unlock front door? [Allow] [Deny]"。用户 30 秒内不响应视为 deny（fail-secure）。极高敏感操作（如重置家庭网络密码、解锁全部摄像头）走 TOTP——用户输 6 位码才执行。


与 cron / IM 触发的协议关系
Home action 不只来自用户对话，也可能由本章第 2 / 3 篇讲的 ./2_cron-and-scheduled-tasks.md 与 ./3_im-triggered-automation.md 触发——例如 cron "每晚 23:30 关全屋灯"、IM /home goodnight 命令。无论触发源是什么，都走相同的四层防护——不能因为是 cron 触发就跳过 persona 权限校验。


陷阱与常见问题
    

  • HomeKit 跨子网失败：HAP 走 mDNS，agent 必须与设备在同子网。VPN / 容器网络常导致设备不可见。
    • 

  • HA token 长期不轮换：long-lived access token 默认无过期。token 泄露后整个家暴露——建议每季度轮换。
    • 

  • WebSocket 重连不处理：HA 重启或 wifi 飘移时 WS 断开，agent 未实现重连会错过事件。SDK 必须有 exponential backoff 重连。
    • 

  • persona 白名单写 *.*：figure 简洁但开过大权限。白名单永远显式列 entity pattern。
    • 

  • 深夜窗口未考虑跨时区：用户出差到不同时区，深夜窗口仍按原时区计算可能错位。基于设备本地时区或用户当前时区都可，但要在 audit 里标清。
    • 

  • confirm push 失败静默通过：push 服务挂了视为"deny"而不是"allow"——fail-secure 是 home action 的强约束。
    • 



小结
智能家居集成把 personal-agent 的能力延伸到物理世界，HomeKit / Home Assistant 是两套主流入口。集成本身不难，难的是安全策略——四层防护（persona 白名单 → 时间窗 → 风险等级 → user confirm）把误触发风险压到可控。深夜禁危险、unlock 必 confirm、push fail-secure 三条是默认必备。下一篇讲 cron 周期任务如何与 hooks transform 管线协同。
