安全模型与进程隔离

核心概念

Personal-agent 在终端里跑 shell 命令、写文件、调网络——意味着每个 terminal 后端的"沙箱模型"决定了 agent 实际拥有的能力上限。同一份 rm -rf /tmp/foo 在 macOS App Sandbox 内的 Ghostty 里看到的 / 与在 Linux 全权限 tmux 里看到的 / 不是同一个东西。本篇按"进程隔离方式 + 文件系统视图 + 环境变量传递 + 平台 sandbox 边界"四块讲清。重点对照不是"哪个最安全"，而是"agent 能假设什么、不能假设什么"。

进程隔离方式
五种 GUI 终端都遵循同一物理模型：terminal 主进程 fork shell 子进程，通过 PTY (pseudo-terminal) 转发输入输出。tmux 略有不同——是 server-client 架构。WSL 更不同——它是轻量 VM 而非进程。

shell 在 VM 内，与 Windows host 文件系统通过 9P 协议互通





tmux 的 server-client 是 agent 最关心的——它意味着 agent + tmux 模式下 agent 进程崩了 / SSH 断了，shell 仍在跑，重连后可拿回 PTY 输出。

每个后端"看到"的文件系统不同。GUI 终端基本是 host 全盘视图，但 macOS 还有 TCC（Transparency, Consent, Control）—— /Documents /Desktop /Downloads 都受 TCC 保护，第一次访问弹窗确认。

WSL 的 /mnt/c 是关键——agent 在 WSL 里能看到 Windows host 整个 C 盘，反过来 host 通过 \\wsl$\Ubuntu\ 能看到 WSL rootfs。这种"双向可见"在隔离上比真 VM 弱，但对 agent 工作流是必须的（编辑 Windows 文件 / 运行 Linux 工具）。


环境变量传递策略
agent 启动 shell 时，哪些环境变量从 host 传到 shell？三种策略：

# Ghostty config 例
env-passthrough:
  allowlist:
    - 'PATH'
    - 'HOME'
    - 'LANG'
    - 'LC_*'
    - 'TERM'
  denylist:
    - '*TOKEN*'
    - '*PASSWORD*'
    - '*SECRET*'
Passthrough 是默认且方便——但意味着 agent 启动的 shell 会"自动继承"用户敏感 env（GitHub PAT、API key 等）。enterprise 环境常用 allowlist 包一层 wrapper。


macOS App Sandbox
App Sandbox 是 macOS 上 GUI 应用的标准 sandbox 机制——通过 entitlements 显式声明允许的资源。Ghostty 是少数严格遵守 App Sandbox 的终端：

iTerm2 / macOS Terminal 历史上 sandbox 较弱（旧 Apple 工具的兼容性遗留）；Ghostty 因其新——直接采用强 sandbox 默认。这导致 agent 在 Ghostty 里跑某些"想 listen 端口"的开发任务可能被 sandbox 拒绝——开发者必须显式开 server entitlement。


Linux user namespace
Linux 上 kitty / wezterm 默认不进 user namespace——shell 继承启动用户的全部权限。要做沙箱必须手动包：


# 用 bwrap (bubblewrap) 包一层
bwrap --ro-bind / / \
      --tmpfs /tmp \
      --tmpfs /home/u/sensitive \
      --dev /dev \
      bash
或更彻底——用 systemd-nspawn / podman 起容器跑 shell。Personal-agent 在 Linux 上跑信任度不高的 agent code 时建议用 bwrap 包：

bwrap 是 personal-agent 在 Linux 上常见的轻量隔离选择——既能限制文件系统视图，又不引入 container 启动开销。

agent 在 WSL 内跑 rm -rf / 只能擦 Linux rootfs（vhdx），擦不到 Windows C 盘——除非显式 cd 到 /mnt/c。但 /mnt/c 默认可写，所以 rm -rf /mnt/c/foo 真的会删 Windows 的 C:\foo。

"用户隔离 uid 级"是各后端共同点——shell 都以启动 GUI 终端的用户身份跑。要做更严格隔离必须额外加 bwrap / sandbox-exec / sudo -u 。


陷阱与常见问题
    

  • 以为 tmux server 重启会刷新 env：env 在 server 第一次启动定型。改 ~/.profile 后 new session 仍用旧 env，必须 tmux kill-server 重启。
    • 

  • WSL /mnt/c 误删 host 文件：agent 在 WSL 内跑 rm -rf /mnt/c/Users/... 真的删 Windows 文件——不是"隔离的"。
    • 

  • Ghostty sandbox 拒 server entitlement：开发用 python -m http.server 失败——必须在 Ghostty 配置加 server entitlement。
    • 

  • macOS TCC 弹窗在 SSH session 不显示：通过 SSH 远程触发 Documents 访问，TCC 弹在物理屏幕——SSH 用户不知。被拒后看 syslog 才知。
    • 

  • bwrap 漏 --dev /dev：很多工具需要 /dev/null /dev/tty，没绑 fail 但 error 不明确。bwrap 套餐先加 --dev /dev --proc /proc --tmpfs /tmp。
    • 

  • env 透传 token 进 LLM：agent 启动 shell 时 env 全透传，LLM 子进程读到 GITHUB_TOKEN—— allowlist 必须 mask sensitive vars。
    • 



小结
七后端在安全模型上分四档：macOS Terminal / iTerm2 弱 sandbox 但有 TCC；Ghostty 强 App Sandbox；kitty / wezterm Linux 默认无 sandbox（需手动 bwrap）；tmux server-client 有独特 socket 风险；WSL 是 lightweight VM 与 host 双向可见。共通点是所有后端都 uid 级隔离——要更细必须额外加 namespace / sandbox-exec / container。Personal-agent 在生产部署应 explicit 选择 sandbox 策略，最常见组合：macOS 用 Ghostty + sandbox 默认 / Linux 用 wezterm + bwrap / 远程用 tmux + 严格 socket 权限。下一篇按场景给出成本权衡与选型决策树。
