Part II · 架构实践软件架构师 简介架构思维 简介架构定义

架构定义

什么是软件架构

软件架构是关于软件系统高层结构的一组重要决策。这些决策涉及系统的组织方式、组成元素的选取、元素之间的交互关系，以及这些元素的行为约束。与日常编码不同，架构决策的影响范围广泛且难以撤回，它们从根本上决定了系统的能力边界和演化方向。

理解软件架构，首先需要回答一个基本问题：架构到底是"什么"。不同的研究者和实践者给出了不同的定义，但核心要素是一致的。

IEEE 1471 标准将架构定义为"系统在其环境中的基本组织，体现为其组件、组件之间的关系、组件与环境之间的关系，以及指导其设计与演化的原则"。这个定义强调了架构的结构性和原则性。

Martin Fowler 给出了一个更实用的观察："架构是那些重要的东西，不论那是什么。"这个看似模糊的定义实际上揭示了架构的本质——架构关注的是对系统影响最大的那些决策。

Ralph Johnson 则从另一个角度指出："架构是我们希望在项目早期就做对的那些决策，因为以后改变它们会非常困难。"这个视角强调了架构决策的不可逆性。

综合这些定义，我们可以提炼出软件架构的四个核心特征：

架构与设计的边界
"架构"和"设计"这两个词在日常交流中常常被混用，但它们之间存在本质区别。理解这个边界，是建立架构思维的关键一步。


本质区别
架构关注的是系统的宏观结构和重大决策，而设计关注的是模块内部的具体实现方案。一个简单的判断标准是：如果一个决策的改变会影响到多个团队或模块，那它就是架构决策；如果只影响一个模块的内部实现，那它就是设计决策。

模糊地带
需要注意的是，架构与设计之间并没有一条非黑即白的分界线。很多决策处于两者之间的模糊地带。例如，选择使用 REST 还是 gRPC 作为服务间通信协议，既是架构决策（影响系统整体的通信模式），也包含设计层面的考虑（具体的接口定义和序列化方式）。


在实践中，架构师需要做的是识别出那些"重要程度高、变更成本大"的决策，将其纳入架构治理的范畴，而将其余决策留给各团队自主处理。


Grady Booch 的观察
Grady Booch 曾经说过："所有的架构都是设计，但并非所有的设计都是架构。"这句话精准地概括了两者的关系。架构是设计的子集，但它是那个最重要、最具约束力、最难以改变的子集。


架构决策记录（ADR）
架构决策记录（Architecture Decision Record，ADR）是记录和管理架构决策的实践工具。每一个重要的架构决策都应该被显式记录下来，包括决策的上下文、考虑的备选方案、最终的选择及其理由。


为什么需要 ADR
在很多团队中，架构决策要么只存在于少数人的脑海中，要么散落在各种会议纪要和即时通讯记录里。这导致了几个严重的问题：


第一，新加入团队的成员无法理解系统为什么是现在这个样子。他们看到的是决策的结果，却不知道背后的原因和权衡。


第二，当业务需求发生变化时，团队不清楚当初的架构决策是基于什么前提做出的，因此无法判断该决策是否仍然适用。


第三，类似的决策场景反复出现时，团队没有可参考的历史经验，每次都在重复讨论。


ADR 通过将决策过程结构化记录，解决了上述问题。

ADR 的生命周期
ADR 不是写完就束之高阁的文档。它有自己的生命周期：


当业务环境变化导致某个架构决策不再适用时，不应该直接修改原始 ADR，而应该创建一个新的 ADR 来替代它，并在原始 ADR 中标注"被 ADR-xxx 替代"。这样做的好处是保留了完整的决策演化历史。


ADR 的实践建议
在团队中推行 ADR 时，需要注意以下几点：


第一，不是所有决策都需要 ADR。只记录那些对系统有重大影响、难以逆转的架构级决策。日常的技术选择和设计决策不需要这种形式化的记录。


第二，ADR 应该与代码一起管理。将 ADR 文件存放在代码仓库中（通常放在 docs/adr/ 或 docs/architecture/decisions/ 目录下），随代码一起版本控制。


第三，保持 ADR 简洁。一个 ADR 通常不超过两页。过于冗长的记录反而会降低团队维护和阅读的意愿。


第四，建立定期回顾机制。每隔一段时间（如每季度），团队应该回顾现有的 ADR，检查哪些决策的前提条件已经发生了变化。

架构师不应该试图控制所有的技术细节。他们的工作是确定系统的大方向和关键约束，然后信任团队在这个框架内做出正确的设计决策。这种"战略控制、战术放权"的方式，既保证了系统的一致性，又给了团队足够的自主空间。


架构定义的常见误区
在实践中，关于架构定义存在一些常见的误区需要避免：


误区一：架构就是技术选型。 选择用 Java 还是 Go，用 MySQL 还是 PostgreSQL，这些确实是架构决策的一部分，但架构远不止于此。架构更关注的是系统的结构组织、组件之间的关系以及满足质量属性的策略。


误区二：架构是项目开始前一次性完成的。 这种"大设计前置"（Big Design Up Front）的思维方式已经被证明不适合大多数现代软件项目。架构应该随着对问题域理解的加深而不断演化。


误区三：架构只是高层设计，不需要关注细节。 好的架构师确实应该保持高层视角，但他们也需要对关键技术细节有足够的理解。不了解实现细节的架构师，做出的决策往往脱离实际。


误区四：好的架构一定很复杂。 恰恰相反，好的架构应该是"恰到好处"的。过度设计和设计不足都是架构的反模式。架构的复杂度应该与问题的复杂度相匹配。


本节小结
软件架构是关于系统结构的重大决策集合。理解架构需要从多个视角出发，区分架构与设计的边界，并通过 ADR 等工具将决策过程显式化。作为架构师，你的核心价值不在于掌握多少技术栈，而在于能否在复杂约束条件下做出合理的系统级决策，并让团队理解和执行这些决策。
