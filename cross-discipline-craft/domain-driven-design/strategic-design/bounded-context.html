Part II · 架构实践领域驱动设计 简介战略设计 简介限界上下文

限界上下文

核心概念

限界上下文（Bounded Context）是领域驱动设计中最关键的战略模式。它定义了一个模型的适用范围——在这个边界内，领域模型中的每个术语都有唯一且明确的含义。跨越边界后，同一个词可能代表完全不同的概念。

例如，"账户"在用户认证上下文中指登录凭证，在财务上下文中指资金账户，在社交上下文中指用户主页。如果将这三个含义塞进同一个模型，代码将不可避免地变成混乱的条件分支。





维度
无边界设计

边界识别策略
识别限界上下文的边界是战略设计中最具挑战性的工作。常见的识别方法包括语言边界分析、业务能力分解和组织结构映射。


语言边界分析是最直观的方法。当领域专家在描述业务时，如果同一个词在不同场景下含义发生变化，或者不同团队对同一概念使用不同术语，就意味着存在上下文边界。


// 订单上下文中的 Product —— 关注价格、数量、折扣
interface OrderProduct {
  productId: string;
  name: string;
  unitPrice: Money;
  quantity: number;
  discount: Percentage;
}

// 库存上下文中的 Product —— 关注库位、批次、保质期
interface InventoryProduct {
  sku: string;
  warehouseLocation: string;
  batchNumber: string;
  expirationDate: Date;
  availableQuantity: number;
}

// 商品目录上下文中的 Product —— 关注展示、分类、SEO
interface CatalogProduct {
  slug: string;
  title: string;
  description: string;
  categories: Category[];
  images: ProductImage[];
  seoMetadata: SeoMeta;
}
业务能力分解从企业价值链出发，将业务拆分为独立的能力单元。每个能力单元通常对应一个或多个限界上下文。


组织结构映射利用康威定律的逆向思维——既然系统架构会趋向组织结构，那么组织中的团队边界往往暗示了合理的上下文边界。


上下文划分策略
划分限界上下文需要在粒度上找到平衡点。过粗的划分等于没有划分，过细的划分则导致集成爆炸。


划分的核心原则：


// 原则一：业务自治性 —— 上下文应该能独立完成一个完整的业务场景
// 反例：将"创建订单"拆到三个上下文，每次下单都需跨上下文事务
// 正例：订单上下文包含从下单到支付确认的完整流程

// 原则二：数据主权 —— 每个上下文拥有自己的数据，不共享数据库
interface OrderRepository {
  save(order: Order): Promise<void>;
  findById(id: OrderId): Promise<Order | null>;
}

// 原则三：独立演进 —— 变更频率相近的概念放在同一上下文
// 促销规则变更频繁 → 独立为营销上下文
// 用户基础信息变更缓慢 → 独立为身份上下文

// 原则四：团队认知边界 —— 一个团队能完整理解和维护的范围
type TeamCapacity = {
  maxContextsPerTeam: number; // 建议 1-2
  maxConceptsPerContext: number; // 建议 < 20 核心概念
};
团队与上下文对齐
限界上下文不仅是技术概念，更是组织设计工具。团队与上下文的对齐方式直接影响软件的质量和交付速度。


康威定律指出：系统的通信结构会映射组织的沟通结构。DDD 的战略设计利用这一规律，主张让团队边界与上下文边界对齐，而不是反过来让代码去适应混乱的组织。


// 团队-上下文对齐模型
interface TeamContextAlignment {
  team: {
    name: string;
    size: number; // 建议 5-9 人
    skills: string[];
  };
  contexts: BoundedContext[]; // 建议 1-2 个
  ownership: 'full' | 'shared'; // 强烈建议 full
  communicationChannels: {
    upstream: string[];
    downstream: string[];
  };
}

// 反模式：多个团队共享一个上下文
// 结果 → 频繁的合并冲突、模糊的责任边界、无人负责的"公地悲剧"

// 正模式：一个团队完整拥有一到两个上下文
// 结果 → 清晰的代码所有权、快速决策、独立发布节奏

关键实践是确保每次拆分都基于真实的业务边界而非技术偏好。如果两个概念在业务上高度耦合，即使由不同团队维护，也不应该强行拆分到不同上下文。


上下文边界的演进
限界上下文的边界不是一次设计就固定不变的。随着业务发展和团队对领域理解的深入，边界需要持续调整。


// 边界演进的信号
type BoundaryEvolutionSignal =
  | 'cross_context_changes_always_paired' // 跨上下文变更总是成对出现
  | 'single_context_too_many_concepts' // 单个上下文概念过多
  | 'team_cognitive_overload' // 团队认知超载
  | 'deployment_coupling' // 部署耦合严重
  | 'ubiquitous_language_diverging'; // 统一语言内部出现分歧

// 合并信号：两个上下文总是一起变更，合并可降低集成成本
// 拆分信号：一个上下文内部出现语言分歧，拆分可提升内聚性

function evaluateBoundary(signals: BoundaryEvolutionSignal[]): 'merge' | 'split' | 'keep' {
  if (signals.includes('cross_context_changes_always_paired')) return 'merge';
  if (signals.includes('ubiquitous_language_diverging')) return 'split';
  if (signals.includes('single_context_too_many_concepts')) return 'split';
  return 'keep';
}
演进式设计的核心是延迟决策——在信息不充分时保持较粗的边界，随着理解加深再逐步细化。过早的精细划分往往导致错误的边界，修正成本远高于渐进拆分。


小结
    

  • 限界上下文定义了模型的适用范围，边界内术语含义唯一
    • 

  • 语言边界分析是最直观的识别方法——同一词不同含义即暗示边界
    • 

  • 划分粒度需要在自治性和集成成本之间取得平衡
    • 

  • 团队与上下文一对一或一对二对齐是最佳实践
    • 

  • 边界是演进的，保持延迟决策原则，避免过早精细划分
    • 

  • 限界上下文是从战略设计到具体实现的桥梁，决定了系统的整体架构走向
    •
