Part II · 架构实践领域驱动设计 简介战略设计 简介子域分类

子域分类

核心概念

子域（Subdomain）是业务领域的自然分区，反映了企业在不同业务方向上的能力分布。领域驱动设计将子域分为三类：核心域（Core Domain）、支撑域（Supporting Subdomain）和通用域（Generic Subdomain）。这个分类决定了资源投入策略——不是所有代码都值得同等对待。

核心域是企业的竞争优势所在，必须投入最优秀的人才和最大的精力。支撑域为核心域提供必要支持，但本身不构成差异化优势。通用域是所有企业都需要但无差异化价值的能力，通常可以购买或采用开源方案。

核心域识别
核心域是企业存在的理由。识别核心域需要回答一个根本问题：如果这个能力被竞争对手完全复制，企业是否会失去竞争优势？


// 核心域识别框架
interface CoreDomainAssessment {
  capability: string;
  differentiationScore: 1 | 2 | 3 | 4 | 5; // 差异化程度
  strategicImportance: 1 | 2 | 3 | 4 | 5; // 战略重要性
  complexityLevel: 'low' | 'medium' | 'high';
  competitorParity: boolean; // 竞争对手是否已有同等能力
}

function classifyDomain(assessment: CoreDomainAssessment): DomainType {
  const { differentiationScore, strategicImportance, competitorParity } = assessment;

  if (differentiationScore >= 4 && strategicImportance >= 4 && !competitorParity) {
    return 'core';
  }
  if (strategicImportance >= 3 && differentiationScore < 4) {
    return 'supporting';
  }
  return 'generic';
}

type DomainType = 'core' | 'supporting' | 'generic';
以电商平台为例：


// 电商平台子域分类
const ecommerceDomains = {
  core: [
    '个性化推荐引擎', // 这是淘宝和拼多多的核心差异
    '供应链智能调度', // 京东的核心竞争力
    '社交裂变营销', // 拼多多的核心壁垒
  ],
  supporting: [
    '订单管理', // 必须有，但不是核心差异
    '商品管理', // 支撑业务运转
    '客服工单系统', // 业务必需但非差异化
    '商家入驻审核', // 支撑平台运营
  ],
  generic: [
    '用户认证与授权', // 所有系统都需要
    '支付网关集成', // 标准化能力
    '短信/邮件通知', // 通用基础设施
    '文件存储服务', // 完全通用
  ],
};
核心域的一个重要特征是随时间漂移。今天的核心域可能因为行业成熟而变成通用域，而新的技术突破可能催生新的核心域。


投资策略与资源分配
子域分类的直接产出是差异化的投资策略。在有限的资源下，错误的分配方式会导致核心能力建设不足。


// 每种子域的技术决策框架
interface DomainInvestmentStrategy {
  domainType: DomainType;
  architecture: string;
  testingStrategy: string;
  teamComposition: string;
  buildVsBuy: string;
}

const strategies: Record<DomainType, DomainInvestmentStrategy> = {
  core: {
    domainType: 'core',
    architecture: '充血模型 + 事件驱动 + CQRS',
    testingStrategy: '全面的领域层单测 + 集成测试 + 契约测试',
    teamComposition: '领域专家 + 资深工程师 + 产品经理紧密协作',
    buildVsBuy: '100% 自研',
  },
  supporting: {
    domainType: 'supporting',
    architecture: '简单分层 + 事务脚本或轻量 DDD',
    testingStrategy: '关键路径集成测试 + 核心逻辑单测',
    teamComposition: '合格的全栈开发团队',
    buildVsBuy: '自研为主，可用低代码平台加速',
  },
  generic: {
    domainType: 'generic',
    architecture: '直接集成第三方服务',
    testingStrategy: '集成测试 + 契约测试',
    teamComposition: '最少维护人员',
    buildVsBuy: '优先购买 / 开源，仅在必要时薄封装',
  },
};
一个常见的反模式是通用域镀金——在用户认证、文件上传等通用能力上花费大量精力自研，结果既不比成熟方案更好，又消耗了本应投入核心域的资源。


子域边界与限界上下文的关系
子域是问题空间的概念，限界上下文是解决方案空间的概念。理想情况下，一个子域对应一个限界上下文，但现实中两者的映射并非总是一对一。


// 理想映射：一个子域 → 一个限界上下文
// 子域: 个性化推荐 → 限界上下文: RecommendationContext

// 现实中的多种映射情况
type DomainToContextMapping =
  | { type: 'one_to_one'; subdomain: string; context: string }
  | { type: 'one_to_many'; subdomain: string; contexts: string[] }
  | { type: 'many_to_one'; subdomains: string[]; context: string };

// 一对多：一个复杂子域拆分为多个上下文
// 例：订单子域 → 订单创建上下文 + 订单履约上下文 + 订单退款上下文

// 多对一：多个简单子域合并为一个上下文（初期常见）
// 例：通知子域 + 日志子域 → 通用基础设施上下文

子域评估工作坊
在实践中，子域分类通常通过工作坊形式完成。参与者包括领域专家、产品经理和技术负责人。


// 子域评估卡片
interface SubdomainCard {
  name: string;
  description: string;
  businessCapabilities: string[];

  // 评估维度 (1-5 分)
  scores: {
    differentiation: number; // 差异化：这个能力让我们与众不同吗？
    strategicImportance: number; // 战略性：这个能力对业务战略重要吗？
    complexity: number; // 复杂度：实现这个能力有多复杂？
    changeFrequency: number; // 变更频率：这个领域的规则多久变一次？
    dataVolatility: number; // 数据波动：相关数据的变化频率？
  };

  classification?: DomainType;
}

// 评估规则
function evaluateSubdomain(card: SubdomainCard): DomainType {
  const { differentiation, strategicImportance } = card.scores;

  if (differentiation >= 4 && strategicImportance >= 4) return 'core';
  if (strategicImportance >= 3) return 'supporting';
  return 'generic';
}

// 工作坊流程：
// 1. 列出所有业务能力（头脑风暴）
// 2. 聚类为候选子域
// 3. 填写评估卡片（全体打分）
// 4. 分类讨论并达成共识
// 5. 映射到限界上下文
// 6. 制定投资策略
工作坊的关键产出是一张子域地图，标注每个子域的分类、负责团队和技术策略。这张地图应该定期（每季度或半年）回顾更新。


小结
    

  • 子域分类（核心/支撑/通用）决定了资源投入的优先级
    • 

  • 核心域是企业竞争优势所在，必须投入最优秀的人才自研
    • 

  • 通用域应优先购买或使用开源方案，避免"通用域镀金"反模式
    • 

  • 子域是问题空间概念，限界上下文是解决方案空间概念，两者理想一对一映射
    • 

  • 子域分类不是静态的，需要定期回顾——今天的核心域可能变成明天的通用域
    • 

  • 通过工作坊形式完成子域评估，产出子域地图指导技术投资决策
