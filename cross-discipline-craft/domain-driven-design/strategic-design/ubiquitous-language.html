统一语言

核心概念

统一语言（Ubiquitous Language）是领域驱动设计的基石。它要求开发团队和领域专家使用同一套语言来描述业务——这套语言贯穿于对话、文档、代码和测试中，不存在"技术翻译"或"业务翻译"的中间层。

当产品经理说"用户下单"，代码中就应该有 placeOrder 方法；当领域专家说"库存预留"，系统中就应该有 reserveInventory 操作。如果代码中用的是 createRecord 或 insertData，那么每次沟通都需要额外的心智翻译，误解和 bug 就在这个翻译过程中诞生。

语言提炼过程
统一语言不是一次性定义的产物，而是通过持续对话和迭代提炼出来的。这个过程需要开发者和领域专家深度协作。


// 提炼前：模糊的技术化命名
class OrderManager {
  processItem(data: Record<string, unknown>): void {
    /* ... */
  }
  updateStatus(id: string, code: number): void {
    /* ... */
  }
  handleReturn(id: string): void {
    /* ... */
  }
}

// 提炼后：反映业务语言的精确命名
class Order {
  place(items: OrderLineItem[], shippingAddress: Address): OrderConfirmation {
    /* 下单 */
    return {} as OrderConfirmation;
  }

  confirm(paymentReceipt: PaymentReceipt): void {
    /* 确认订单 */
  }

  requestReturn(reason: ReturnReason, items: OrderLineItem[]): ReturnRequest {
    /* 申请退货 */
    return {} as ReturnRequest;
  }

  cancel(reason: CancellationReason): void {
    /* 取消订单 */
  }
}
语言提炼的关键步骤：


// 第一步：收集原始术语
// 在工作坊中，让领域专家用自然语言描述业务流程
// "顾客在购物车里选好商品后，提交订单。系统验证库存，
//  如果库存充足就锁定库存，生成待支付订单。"

// 第二步：识别核心概念并建立词汇表
interface DomainGlossary {
  terms: GlossaryEntry[];
}

interface GlossaryEntry {
  term: string; // 统一术语
  definition: string; // 在此上下文中的精确含义
  aliases: string[]; // 同义词（标记为已废弃）
  context: string; // 所属限界上下文
  examples: string[]; // 使用示例
}

// 第三步：在代码中强制使用统一术语
// 代码审查中拒绝不符合统一语言的命名
代码与业务语言一致性
统一语言的终极目标是让代码成为领域模型的直接表达。当领域专家能读懂核心业务代码（即使不懂语法细节），统一语言就达到了目标。


// 业务规则："VIP 客户在大促期间享受满减优惠，
// 但需要满足最低消费金额且商品不在排除列表中"

// 统一语言直接映射为代码
class PromotionPolicy {
  canApplyDiscount(customer: Customer, order: Order, promotion: Promotion): DiscountEligibility {
    if (!customer.isVIP()) {
      return DiscountEligibility.ineligible('非 VIP 客户');
    }

    if (!promotion.isActive()) {
      return DiscountEligibility.ineligible('促销活动未开始或已结束');
    }

    if (order.totalAmount().isLessThan(promotion.minimumSpend())) {
      return DiscountEligibility.ineligible('未达到最低消费金额');
    }

    const excludedItems = order.items().filter((item) => promotion.isExcluded(item.productId()));

    if (excludedItems.length === order.items().length) {
      return DiscountEligibility.ineligible('所有商品均在排除列表中');
    }

    const eligibleAmount = order.totalAmountExcluding(excludedItems);
    return DiscountEligibility.eligible(promotion.calculateDiscount(eligibleAmount));
  }
}

领域专家协作模式
建立统一语言需要结构化的协作流程。以下是经过验证的协作模式。


// 模式一：领域对话（Domain Storytelling）
// 领域专家讲述业务故事，开发者记录并提炼术语
// "仓库管理员每天早上检查库存水位，
//  如果某个 SKU 的可用库存低于安全库存，
//  就生成一个补货申请发给采购部门。"

// 提炼出的领域概念：
interface InventoryLevel {
  sku: SKU;
  availableQuantity: number;
  safetyStock: number;

  isBelowSafetyStock(): boolean;
}

interface ReplenishmentRequest {
  sku: SKU;
  requestedQuantity: number;
  requestedBy: WarehouseKeeper;
  status: 'pending' | 'approved' | 'rejected';
}

// 模式二：示例映射（Example Mapping）
// 用具体的业务示例来验证术语的精确性
// 规则：订单总金额超过 500 元免运费
// 示例 1：订单 480 元 → 收运费 10 元
// 示例 2：订单 500 元 → 免运费
// 示例 3：订单 480 元 + 优惠券减 20 元 = 实付 460 元 → 收运费？
// （发现歧义：免运费的"总金额"是优惠前还是优惠后？需要澄清）
协作的反模式：


// 反模式一：开发者单方面定义术语
// 领域专家从不参与代码审查，代码中的术语与业务脱节

// 反模式二：技术黑话入侵业务语言
// "我们需要一个 handler 来 process 这个 entity 的 state transition"
// 应改为："我们需要在订单确认时更新库存预留状态"

// 反模式三：术语表停留在文档不更新
// 术语表写好后就没人维护，代码已经演进但术语表还是旧版
统一语言的边界与演进
统一语言有明确的适用范围——它只在一个限界上下文内有效。不同上下文可以（而且经常）对同一个词有不同的定义。


// 在"交易上下文"中
interface Account {
  balance: Money;
  deposit(amount: Money): void;
  withdraw(amount: Money): void;
}

// 在"身份认证上下文"中
interface Account {
  email: Email;
  passwordHash: string;
  login(credentials: Credentials): AuthToken;
  resetPassword(token: ResetToken): void;
}

// 两个 Account 在各自上下文中含义完全不同
// 这不是命名冲突，而是限界上下文的正常表现
语言演进的治理机制：


interface LanguageGovernance {
  glossaryLocation: string; // 术语表存放位置
  updateFrequency: 'weekly' | 'biweekly';
  reviewProcess: {
    proposer: 'anyone'; // 任何人可提议新术语
    reviewer: 'domain_expert'; // 领域专家审核
    approver: 'team_lead'; // 技术负责人批准代码变更
  };
  codeEnforcement: {
    lintRules: boolean; // 是否有命名规范 lint
    codeReviewChecklist: boolean; // 代码审查是否检查术语一致性
    automatedGlossarySync: boolean; // 是否自动同步术语表
  };
}
小结
    

  • 统一语言是 DDD 的基石，要求业务和技术使用同一套术语
    • 

  • 语言提炼是持续迭代过程，通过领域对话和示例映射逐步精确
    • 

  • 代码应该成为领域模型的直接表达，让领域专家能读懂核心逻辑
    • 

  • 统一语言只在限界上下文内有效，不同上下文中同一词可有不同含义
    • 

  • 领域专家必须深度参与术语定义和代码审查，避免技术团队单方面定义
    • 

  • 建立术语表治理机制，确保语言随业务演进持续更新
    •
