DDD 陷阱与权衡

核心概念

领域驱动设计是一套强大的方法论，但它不是银弹。在实践中，DDD 的每一个模式都有其适用边界和代价。过度设计、错误的边界划分、教条式的模式应用——这些陷阱消耗了大量团队的时间和精力，却没有带来预期的收益。

成熟的 DDD 实践者需要知道何时使用 DDD和何时不使用 DDD。这比掌握 DDD 的每一个模式都更重要。

graph TB
    A[项目评估] --> B{业务复杂度?}
    B -->|高| C{团队规模?}
    B -->|低| D[不需要 DDD<br/>CRUD 就够了]
    C -->|大| E[全套 DDD<br/>战略 + 战术]
    C -->|小| F{核心域明确?}
    F -->|是| G[轻量 DDD<br/>聚合 + 事件]
    F -->|否| H[先做事件风暴<br/>再决定]
维度 DDD 适合 DDD 不适合
业务复杂度 高，规则多且变化频繁 低，简单 CRUD
领域专家 可获取，愿意合作 不存在或无法参与
项目周期 长期演进 短期一次性项目
团队经验 有 OOP/建模经验 全部是初级开发者
技术与业务对齐 需求频繁变化 需求已完全确定
投入回报 长期降低维护成本 短期增加开发成本

过度设计陷阱

最常见的 DDD 陷阱是过度设计——在不需要复杂模式的地方引入全套 DDD 战术模式。

// 陷阱一：简单 CRUD 强行 DDD
// 一个只有增删改查的配置管理模块，真的需要聚合根、值对象、领域事件吗？

// 过度设计版本
class SystemConfigAggregate extends AggregateRoot {
  private configs: Map<string, ConfigValueObject> = new Map();

  updateConfig(key: ConfigKeyVO, value: ConfigValueObject): void {
    this.configs.set(key.value, value);
    this.addDomainEvent(new ConfigUpdated(this.id, key.value, value.value, new Date()));
  }
}

class ConfigValueObject {
  private constructor(readonly value: string) {
    Object.freeze(this);
  }
  static create(value: string): ConfigValueObject {
    return new ConfigValueObject(value);
  }
  equals(other: ConfigValueObject): boolean {
    return this.value === other.value;
  }
}

// 简单版本（足够好）
interface ConfigService {
  get(key: string): Promise<string | null>;
  set(key: string, value: string): Promise<void>;
  delete(key: string): Promise<void>;
}
// 陷阱二：值对象过度封装
// 不是每个字符串都需要变成值对象

// 过度
class FirstName {
  private constructor(readonly value: string) {}
  static create(value: string): FirstName {
    return new FirstName(value.trim());
  }
}

class LastName {
  private constructor(readonly value: string) {}
  static create(value: string): LastName {
    return new LastName(value.trim());
  }
}

class MiddleName {
  private constructor(readonly value: string) {}
  static create(value: string): MiddleName {
    return new MiddleName(value.trim());
  }
}

// 适度
class PersonName {
  private constructor(
    readonly firstName: string,
    readonly lastName: string,
    readonly middleName?: string,
  ) {}

  static create(first: string, last: string, middle?: string): PersonName {
    if (!first.trim() || !last.trim()) throw new Error('Name cannot be empty');
    return new PersonName(first.trim(), last.trim(), middle?.trim());
  }

  get fullName(): string {
    return this.middleName
      ? `${this.firstName} ${this.middleName} ${this.lastName}`
      : `${this.firstName} ${this.lastName}`;
  }
}

错误的边界划分

边界划分错误是最昂贵的陷阱，修正成本远高于其他错误。

// 陷阱三：按技术层拆分而非按业务拆分
// 反模式：UserService、OrderService、PaymentService 各自是一个"上下文"
// 但"创建订单"这个业务操作需要同时修改三个"上下文"

// 陷阱四：过早精细拆分
// 初创团队 5 个人，拆出 12 个限界上下文
// 结果：每个简单功能都需要跨上下文通信，开发速度骤降

// 正确做法：从粗粒度开始，逐步细化
type BoundarySplitTimeline = {
  stage: string;
  teamSize: string;
  contextCount: string;
  strategy: string;
}[];

const timeline: BoundarySplitTimeline = [
  {
    stage: '初创期',
    teamSize: '3-5 人',
    contextCount: '1-2 个',
    strategy: '单体 + 模块化，统一数据库',
  },
  {
    stage: '成长期',
    teamSize: '10-20 人',
    contextCount: '3-6 个',
    strategy: '识别核心域，拆分第一个微服务',
  },
  {
    stage: '规模期',
    teamSize: '50+ 人',
    contextCount: '10+ 个',
    strategy: '平台化，团队与上下文对齐',
  },
];

教条式模式应用

DDD 的模式是工具箱，不是清单。不需要在每个项目中使用所有模式。

// 陷阱五：所有操作都走领域事件
// 反模式：同一个聚合内的简单操作也通过事件通信
class User {
  updateProfile(name: string, bio: string): void {
    this.addDomainEvent(new ProfileUpdateRequested(this.id, name, bio));
  }
}

class ProfileUpdateHandler {
  async handle(event: ProfileUpdateRequested): Promise<void> {
    const user = await this.userRepo.findById(event.userId);
    if (!user) return;
    user.name = event.name;
    user.bio = event.bio;
    await this.userRepo.save(user);
  }
}

// 简单直接的做法更好
class User {
  updateProfile(name: string, bio: string): void {
    if (!name.trim()) throw new Error('Name cannot be empty');
    this.name = name.trim();
    this.bio = bio.trim();
  }
}

// 陷阱六：强制所有数据访问走仓储
// 报表查询、数据导出这类纯读场景，直接写 SQL 更高效
// 仓储是为聚合的写操作设计的，不是所有数据访问的入口
模式 使用时机 不需要时
聚合 有复杂的一致性不变量 简单 CRUD，无业务规则
值对象 有行为的复合数据 简单的单值属性
领域事件 跨聚合/上下文的解耦 同一聚合内的简单操作
仓储 聚合的持久化抽象 纯读查询、报表
CQRS 读写模型差异大 简单应用
事件溯源 需要完整审计轨迹 大多数普通系统

常见认知误区

type Misconception = {
  myth: string;
  reality: string;
  impact: string;
};

const misconceptions: Misconception[] = [
  {
    myth: 'DDD = 技术架构模式',
    reality: 'DDD 首先是沟通和建模方法论，战术模式只是实现手段',
    impact: '忽略战略设计，直接上代码模式，失去最大价值',
  },
  {
    myth: '所有项目都应该用 DDD',
    reality: '只有业务复杂度足够高的项目才值得投入 DDD',
    impact: '简单项目过度设计，开发效率反而下降',
  },
  {
    myth: 'DDD 意味着完全面向对象',
    reality: 'DDD 可以用函数式、过程式实现，核心是领域建模',
    impact: '教条式的 OOP 设计，忽略更简洁的实现方式',
  },
  {
    myth: '限界上下文越多越好',
    reality: '上下文数量应该与团队规模和业务复杂度匹配',
    impact: '过细拆分导致集成爆炸，维护成本急剧上升',
  },
  {
    myth: '聚合必须用类实现',
    reality: '聚合是概念模式，可以用函数、模块或任何方式实现',
    impact: '语言选型受限，TypeScript 中不必要的类层次结构',
  },
  {
    myth: '引入 DDD 后立即看到收益',
    reality: 'DDD 的收益是长期的，短期可能增加开发成本',
    impact: '管理层在短期看不到效果后放弃 DDD',
  },
];

何时不用 DDD

graph TB
    A[新项目评估] --> B{业务规则复杂?}
    B -->|少于 5 条核心规则| C[事务脚本 / CRUD]
    B -->|复杂| D{有领域专家?}
    D -->|无法获取| E[先做技术原型]
    D -->|有| F{长期维护?}
    F -->|一次性项目| G[快速开发框架]
    F -->|长期演进| H[DDD 值得投入]
场景 推荐方案 理由
内部管理工具 低代码 / CRUD 框架 业务规则简单，快速交付优先
数据管道 ETL 工具 + 脚本 无复杂领域逻辑
营销活动页 静态生成 + 简单后端 短生命周期
核心交易系统 全套 DDD 高复杂度，长期演进
推荐/搜索引擎 DDD 战略 + 算法工程 核心域但不一定需要战术模式

小结

mindmap
  root((DDD 陷阱与权衡))
    过度设计
      简单 CRUD 强行 DDD
      值对象过度封装
      模式堆砌
    边界错误
      技术层拆分
      过早精细拆分
      渐进演进
    教条应用
      不是所有操作需要事件
      不是所有查询走仓储
      模式是工具不是清单
    何时不用
      业务简单
      一次性项目
      无领域专家
  • 过度设计是 DDD 最常见的陷阱——简单 CRUD 不需要聚合和领域事件
  • 边界划分错误是最昂贵的错误，从粗粒度开始逐步细化是安全策略
  • DDD 模式是工具箱不是清单，只在需要时使用对应模式
  • 知道何时不用 DDD 比掌握所有 DDD 模式更重要
  • DDD 的核心价值在于战略设计（统一语言、限界上下文），而非战术模式
  • 成熟的 DDD 实践是在复杂度收益和实现成本之间找到最佳平衡点
