DDD 与微服务

核心概念

DDD 与微服务的关系是战略设计的自然延伸：限界上下文为微服务边界提供了理论基础，而微服务架构为限界上下文提供了物理隔离的部署形态。但"一个限界上下文 = 一个微服务"并不是铁律，而是一个需要根据实际情况权衡的起点。

微服务拆分最常见的失败原因是按技术层拆分（用户服务、订单服务、支付服务听起来合理，但如果边界划错了，就变成了分布式单体）。DDD 提供了业务驱动的拆分指导——先划定限界上下文，再决定哪些上下文值得独立为微服务。

限界上下文到微服务边界
将限界上下文映射为微服务边界时，需要考虑多个因素，不是所有上下文都应该独立为微服务。


interface ContextToServiceDecision {
  contextName: string;
  domainType: 'core' | 'supporting' | 'generic';
  teamOwnership: 'dedicated' | 'shared';
  changeFrequency: 'high' | 'medium' | 'low';
  scalingNeeds: 'independent' | 'uniform';
  dataVolume: 'high' | 'medium' | 'low';
}

function shouldBeIndependentService(ctx: ContextToServiceDecision): boolean {
  if (ctx.domainType === 'core' && ctx.teamOwnership === 'dedicated') return true;
  if (ctx.changeFrequency === 'high' && ctx.scalingNeeds === 'independent') return true;
  if (ctx.dataVolume === 'high' && ctx.scalingNeeds === 'independent') return true;
  return false;
}

数据主权与跨服务查询
每个微服务拥有自己的数据（数据主权），这是微服务架构的基本原则。但这也带来了跨服务查询的挑战。


// 反模式：共享数据库
// 订单服务直接查询用户服务的表
// SELECT o.*, u.name FROM orders o JOIN users u ON o.user_id = u.id
// 问题：用户服务修改表结构会直接破坏订单服务

// 正确模式一：API 调用 + 数据冗余
class OrderService {
  constructor(
    private readonly orderRepo: OrderRepository,
    private readonly customerClient: CustomerServiceClient,
  ) {}

  async getOrderWithCustomerInfo(orderId: OrderId): Promise<OrderWithCustomer> {
    const order = await this.orderRepo.findById(orderId);
    if (!order) throw new Error('Order not found');

    const customer = await this.customerClient.getCustomer(order.customerId);
    return { ...order, customerName: customer.name, customerEmail: customer.email };
  }
}

// 正确模式二：事件驱动的数据复制
class CustomerProjection {
  constructor(private readonly readStore: ReadStore) {}

  async handleCustomerUpdated(event: CustomerUpdated): Promise<void> {
    await this.readStore.upsert('customer_cache', {
      customerId: event.customerId,
      name: event.name,
      email: event.email,
      updatedAt: event.occurredAt,
    });
  }
}

// 订单服务查询本地的客户缓存表，无需跨服务调用
class OrderQueryService {
  constructor(private readonly readDb: ReadDatabase) {}

  async getOrderDetails(orderId: string): Promise<OrderDetailsView> {
    return this.readDb.query(
      `SELECT o.*, cc.name as customer_name
       FROM orders o
       LEFT JOIN customer_cache cc ON o.customer_id = cc.customer_id
       WHERE o.id = $1`,
      [orderId],
    );
  }
}

跨服务的领域事件
微服务之间的协作主要通过领域事件实现。事件通过消息中间件异步传递，实现服务间的松耦合。


// 事件发布：订单服务发布事件到消息队列
class OrderEventPublisher {
  constructor(private readonly messageBroker: MessageBroker) {}

  async publish(event: DomainEvent): Promise<void> {
    await this.messageBroker.publish({
      topic: `domain.events.${event.eventType}`,
      payload: JSON.stringify({
        eventId: event.eventId,
        eventType: event.eventType,
        aggregateId: event.aggregateId,
        occurredAt: event.occurredAt.toISOString(),
        data: event,
      }),
      headers: {
        'content-type': 'application/json',
        'event-type': event.eventType,
        'source-service': 'order-service',
      },
    });
  }
}

// 事件消费：库存服务订阅订单事件
class InventoryEventConsumer {
  constructor(
    private readonly messageBroker: MessageBroker,
    private readonly inventoryService: InventoryApplicationService,
  ) {}

  async start(): Promise<void> {
    await this.messageBroker.subscribe('domain.events.OrderPlaced', async (message) => {
      const event = JSON.parse(message.payload) as OrderPlacedEvent;
      await this.inventoryService.reserveStock(event);
      await message.ack();
    });
  }
}
Saga 模式与分布式事务
跨微服务的业务流程不能使用传统的数据库事务，需要使用 Saga 模式实现补偿式的最终一致性。


// 编排式 Saga：创建订单的跨服务流程
class CreateOrderSaga {
  private steps: SagaStep[] = [];
  private compensations: Array<() => Promise<void>> = [];

  constructor(
    private readonly orderService: OrderServiceClient,
    private readonly paymentService: PaymentServiceClient,
    private readonly inventoryService: InventoryServiceClient,
  ) {}

  async execute(command: CreateOrderCommand): Promise<string> {
    try {
      const orderId = await this.orderService.createOrder(command);
      this.compensations.push(() => this.orderService.cancelOrder(orderId));

      await this.inventoryService.reserveStock(orderId, command.items);
      this.compensations.push(() => this.inventoryService.releaseStock(orderId));

      await this.paymentService.processPayment(orderId, command.totalAmount);
      this.compensations.push(() => this.paymentService.refund(orderId));

      await this.orderService.confirmOrder(orderId);
      return orderId;
    } catch (error) {
      await this.compensate();
      throw error;
    }
  }

  private async compensate(): Promise<void> {
    for (const compensation of this.compensations.reverse()) {
      try {
        await compensation();
      } catch (compensationError) {
        console.error('Compensation failed', compensationError);
      }
    }
  }
}

小结
    

  • 限界上下文是微服务边界的理论基础，但不是一对一映射
    • 

  • 只有核心域、高变更频率或独立扩展需求的上下文才值得独立为微服务
    • 

  • 每个微服务拥有自己的数据（数据主权），跨服务查询通过事件复制或 API 调用
    • 

  • 微服务间通过领域事件异步协作，实现松耦合
    • 

  • 跨服务的业务流程使用 Saga 模式实现补偿式最终一致性
    • 

  • 微服务 + DDD 的前提是团队有足够的运维能力和分布式系统经验
