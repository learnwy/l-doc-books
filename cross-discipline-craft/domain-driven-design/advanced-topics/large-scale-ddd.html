大规模 DDD

核心概念

当组织从几个团队增长到几十甚至上百个团队时，DDD 的实践方式需要相应升级。大规模 DDD 不再只是技术建模问题，而是组织架构、团队协作和治理机制的综合挑战。康威定律在这个尺度上的影响尤为突出——系统架构不可避免地反映组织沟通结构。

大规模 DDD 的核心主题是：如何让多个团队在各自的限界上下文内高效自治，同时保证系统整体的一致性和可演进性。

团队拓扑与上下文对齐
Team Topologies（团队拓扑）框架与 DDD 的结合，为大规模组织提供了团队结构设计方法。四种基本团队类型直接映射到 DDD 的角色。


type TeamType =
  | 'stream_aligned' // 流对齐团队：负责一个业务流的端到端交付
  | 'platform' // 平台团队：提供共享基础能力
  | 'enabling' // 赋能团队：帮助其他团队掌握新技术/方法
  | 'complicated_subsystem'; // 复杂子系统团队：管理需要专家知识的组件

interface TeamContextMapping {
  team: { name: string; type: TeamType; size: number };
  ownedContexts: string[];
  interactionMode: 'collaboration' | 'x_as_a_service' | 'facilitating';
}

多团队协作模式
大规模 DDD 中，团队间的协作不能依赖非正式沟通，需要明确的交互模式和协议。


// 协作模式一：内部开源 (Inner Source)
// 上游团队维护核心，下游团队可提交 PR
interface InnerSourceProtocol {
  repository: string;
  maintainers: string[];
  contributionGuide: string;
  prReviewSLA: string; // 例如 "2 个工作日内"
  breakingChangePolicy: 'semver' | 'deprecation_period';
}

// 协作模式二：API 契约 (Contract-First)
// 先定义接口契约，再各自实现
interface ContractFirstProtocol {
  contractFormat: 'openapi' | 'protobuf' | 'graphql';
  contractRepository: string;
  versioningStrategy: 'url_versioning' | 'header_versioning';
  breakingChangeWindow: string; // 例如 "30 天弃用期"
  contractTestSuite: string;
}

// 协作模式三：事件契约 (Event Contract)
// 发布方定义事件 schema，消费方遵守
interface EventContractProtocol {
  schemaRegistry: string;
  eventCatalog: string;
  compatibilityMode: 'backward' | 'forward' | 'full';
  evolutionPolicy: string;
}

组织架构与限界上下文的协同演进
在大规模组织中，组织架构和系统架构需要协同演进。逆康威定律（Inverse Conway Maneuver）建议主动调整组织结构以获得期望的系统架构。


// 协同演进的触发信号
type EvolutionSignal =
  | 'team_too_large' // 团队超过 9 人
  | 'cross_team_changes_frequent' // 跨团队变更频率过高
  | 'deployment_coupling' // 部署耦合
  | 'communication_bottleneck' // 沟通瓶颈
  | 'cognitive_overload'; // 团队认知过载

interface EvolutionAction {
  signal: EvolutionSignal;
  teamAction: string;
  architectureAction: string;
}

const evolutionPlaybook: EvolutionAction[] = [
  {
    signal: 'team_too_large',
    teamAction: '拆分为两个流对齐团队',
    architectureAction: '相应拆分限界上下文',
  },
  {
    signal: 'cross_team_changes_frequent',
    teamAction: '考虑合并团队或建立协作通道',
    architectureAction: '评估是否应合并上下文或提取共享内核',
  },
  {
    signal: 'deployment_coupling',
    teamAction: '明确 API 契约和版本策略',
    architectureAction: '引入防腐层隔离变更传播',
  },
  {
    signal: 'communication_bottleneck',
    teamAction: '建立平台团队提供自助服务',
    architectureAction: '将瓶颈能力平台化（开放主机服务）',
  },
  {
    signal: 'cognitive_overload',
    teamAction: '限制团队拥有的上下文数量（最多 2 个）',
    architectureAction: '提取复杂子系统为独立上下文',
  },
];
架构治理框架
大规模 DDD 需要架构治理来保证一致性，同时不扼杀各团队的自主决策权。


interface ArchitectureGovernance {
  decisionFramework: {
    centralDecisions: string[]; // 全局统一的决策
    teamDecisions: string[]; // 团队自治的决策
    advisoryDecisions: string[]; // 建议但不强制
  };
  reviewCadence: {
    contextMapReview: 'quarterly';
    contractReview: 'monthly';
    architectureSync: 'biweekly';
  };
  qualityGates: {
    contractBreakingChangeApproval: boolean;
    crossContextDependencyLimit: number;
    eventSchemaCompatibilityCheck: boolean;
  };
}

const governance: ArchitectureGovernance = {
  decisionFramework: {
    centralDecisions: [
      '跨上下文通信协议（HTTP/gRPC/事件）',
      '事件 schema 注册和兼容性策略',
      '认证和授权标准',
      '可观测性标准（日志/指标/链路追踪）',
    ],
    teamDecisions: ['上下文内部的编程语言和框架', '数据库选型', '内部代码架构', '测试策略'],
    advisoryDecisions: ['DDD 战术模式的使用深度', 'CQRS / 事件溯源的采用', '缓存策略'],
  },

  },

  },

小结
    

  • 大规模 DDD 是组织架构、团队协作和技术架构的综合挑战
    • 

  • Team Topologies 的四种团队类型直接映射到 DDD 的角色分工
    • 

  • 团队间需要明确的交互模式：协作式、X-as-a-Service 或促进式
    • 

  • 逆康威定律建议主动调整组织结构以获得期望的系统架构
    • 

  • 架构治理需要平衡全局一致性和团队自治权
    • 

  • 定期审查上下文地图和团队拓扑，确保组织和架构协同演进
    •
