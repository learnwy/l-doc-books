PRD 结构

核心概念

PRD（Product Requirements Document） 是产品需求文档，是产品经理向工程团队传达产品意图的核心载体。一份好的 PRD 不在于篇幅多长，而在于能否清晰、完整、无歧义地传达"要做什么"和"为什么要做"，让工程师能够据此做出正确的技术决策和实现方案。

对于工程师而言，PRD 是你理解需求的第一手资料。能够快速解读 PRD 的结构和关键信息，是高效开发的基础。更重要的是，当你能够评价甚至编写高质量的 PRD 时，你就具备了从产品视角思考问题的能力。

核心章节详解


关键要素
背景与目标
背景回答"为什么现在要做这件事"，目标回答"做完后要达到什么效果"。


好的背景描述：


    

  • 基于数据："当前注册流程的完成率为 35%，远低于行业平均的 60%"
    • 

  • 基于用户反馈："近 30 天收到 47 条关于注册流程复杂的客诉"
    • 

  • 基于竞品："主要竞品 A 和 B 都已支持社交登录，我们是唯一仍只支持邮箱注册的"
    • 



好的目标描述：


    

  • 可量化："将注册完成率从 35% 提升至 55%"
    • 

  • 有时间限制："上线后 30 天内达成目标"
    • 

  • 与业务相关："预计增加月新增用户 2000 人"
    •

PRD 写作技巧
面向工程师的写作原则




原则
说明
示例





说明"是什么"
描述行为而非实现
"用户看到加载指示器" 而非 "显示 Spinner 组件"




明确边界
清楚写明不做什么

用 P0/P1/P2 标注





PRD 写作流程


常见误区
误区一：PRD 越详细越好
过度详细的 PRD 反而降低可读性。工程师不需要在 PRD 中看到每一个像素的位置——他们需要的是清晰的行为描述和验收标准。视觉细节应该在设计稿中，而非 PRD 中。


误区二：PRD 写完就不改了
PRD 是活文档。在开发过程中发现的问题、变更的需求都应该反映在 PRD 中。保持 PRD 与实际实现的一致性，否则它很快就变成了"过期文档"。


误区三：PRD 中写技术方案
PRD 描述"做什么"，技术方案文档描述"怎么做"。在 PRD 中混入技术实现细节会限制工程师的方案选择空间。唯一的例外是有特定技术约束时，应在非功能需求中说明。


误区四：忽视"不做什么"
明确的 Out of Scope 和"不做什么"不做什么在 PRD 中非常重要。它能防止范围蔓延，也能让工程师知道哪些边界情况可以暂时不处理。




小结
    

  • PRD 是产品经理向工程团队传达产品意图的核心载体，回答"做什么"和"为什么"。
    • 

  • 标准 PRD 包含背景目标、功能需求、非功能需求、成功指标和范围定义等核心章节。
    • 

  • 不同类型的 PRD（新功能、优化迭代、技术重构）在侧重点上有显著差异。
    • 

  • 好的 PRD 应描述行为而非实现、量化模糊词、明确做与不做的边界。
    • 

  • PRD 是活文档，应在开发过程中持续更新，保持与实际实现的一致性。
    •
