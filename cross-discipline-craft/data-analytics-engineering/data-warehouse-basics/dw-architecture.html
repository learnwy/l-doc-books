数据仓库概述

数据仓库是面向分析的、集成的、稳定的、随时间变化的数据集合。它的核心使命是将散落在各个业务系统中的数据统一整合，为数据分析和决策提供可靠的数据基础。

Lambda 架构
Lambda 架构由 Nathan Marz 提出，通过批处理层和实时处理层的组合来满足对数据及时性和准确性的双重需求。






层级
职责
技术选型
数据特点





批处理层
全量数据的准确计算
Spark/Hive/Flink
完整、准确、延迟高




速度层
增量数据的近实时计算
Flink/Kafka Streams
及时、可能不完整




服务层
合并批处理和实时结果供查询
HBase/Redis/Druid
可查询的最终结果





Lambda 架构的优劣




优点
缺点





批处理保证数据最终一致性
同一逻辑需要在两套系统中实现




实时层提供低延迟数据
维护成本高（两套代码、两套测试）




容错性强，批处理可覆盖实时错误
技术栈复杂，学习成本高







Kappa 架构
Kappa 架构由 Jay Kreps 提出，是对 Lambda 架构的简化。它去掉了批处理层，所有数据处理都通过流处理完成。






对比维度
Lambda 架构
Kappa 架构





处理方式
批处理 + 流处理
仅流处理




代码维护
两套逻辑
一套逻辑




数据回溯
批处理层自然支持
需要消息队列支持重放




复杂度
高
相对低




适用场景
复杂计算、强一致性要求
简单聚合、低延迟要求




技术栈
Spark + Flink + HDFS
Flink + Kafka

数据仓库分层设计
分层设计是数据仓库架构的核心，通过将数据处理过程分为多个层次，实现数据的逐步加工和复用。


各层详解




层级
全称
职责
数据特点





ODS
Operational Data Store
原始数据落地，保持源系统结构
未加工、冗余、不一致




DWD
Data Warehouse Detail
数据清洗、标准化、关联
清洁、一致、最细粒度




DWS
Data Warehouse Summary
面向主题的轻度汇总
预聚合、面向分析主题




ADS
Application Data Store
面向具体应用的高度聚合
直接支撑报表和应用





ODS 层：贴源层
CREATE TABLE ods_order_raw (
    order_id        VARCHAR(32),
    user_id         VARCHAR(32),
    product_id      VARCHAR(32),
    amount          DECIMAL(10,2),
    status          VARCHAR(20),
    created_at      TIMESTAMP,
    updated_at      TIMESTAMP,
    etl_load_time   TIMESTAMP DEFAULT NOW(),
    etl_source      VARCHAR(50) DEFAULT 'mysql_order_db'
);




ODS 设计原则
说明





保持原样
不做任何业务逻辑转换




全量 + 增量
首次全量同步，后续增量更新




记录来源和时间
每条记录标注数据来源和加载时间




保留历史
不做物理删除，保留所有历史版本





DWD 层：明细层
CREATE TABLE dwd_order_detail (
    order_key       BIGINT,
    order_id        VARCHAR(32),
    user_key        BIGINT,
    product_key     BIGINT,
    date_key        INT,
    order_amount    DECIMAL(10,2),
    discount_amount DECIMAL(10,2),

小结
    

  • 数据仓库是面向分析的集成数据平台，与 OLTP 系统在设计目标和数据模型上有根本差异
    • 

  • Lambda 架构通过批处理层和速度层的组合保证数据准确性和及时性，但维护成本高
    • 

  • Kappa 架构去掉批处理层仅使用流处理，适合处理逻辑简单、延迟要求高的场景
    • 

  • 数据仓库分层（ODS→DWD→DWS→ADS）通过逐层加工实现数据复用和职责分离
    • 

  • ODS 保持源数据原样，DWD 负责清洗标准化，DWS 面向主题汇总，ADS 直接服务应用
    •
