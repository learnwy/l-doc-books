查询优化：执行计划分析、索引策略、慢查询诊断

执行计划基础

执行计划是数据库优化器对 SQL 查询的具体执行方案，理解执行计划是查询优化的第一步。每个数据库在收到 SQL 语句后，都会经历解析、优化和执行三个阶段，执行计划就是优化阶段的输出产物。

查看执行计划
-- PostgreSQL
EXPLAIN ANALYZE
SELECT u.user_name, COUNT(o.order_id) AS order_count
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
WHERE u.created_at >= '2025-01-01'
GROUP BY u.user_name
ORDER BY order_count DESC
LIMIT 10;
-- MySQL
EXPLAIN FORMAT=JSON
SELECT u.user_name, COUNT(o.order_id) AS order_count
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
WHERE u.created_at >= '2025-01-01'
GROUP BY u.user_name
ORDER BY order_count DESC
LIMIT 10;

复合索引设计原则
-- 遵循最左前缀原则
CREATE INDEX idx_orders_composite
ON orders (user_id, status, created_at DESC);

-- 以下查询可以利用该索引
SELECT * FROM orders WHERE user_id = 100;
SELECT * FROM orders WHERE user_id = 100 AND status = 'completed';
SELECT * FROM orders WHERE user_id = 100 AND status = 'completed' AND created_at > '2025-01-01';

-- 以下查询无法利用该索引的第一列
SELECT * FROM orders WHERE status = 'completed';
SELECT * FROM orders WHERE created_at > '2025-01-01';

实现 Index Only Scan





覆盖索引
-- 创建覆盖索引，包含查询所需的所有列
CREATE INDEX idx_orders_covering
ON orders (user_id, status) INCLUDE (amount, created_at);

-- 以下查询可以仅通过索引完成，无需回表
SELECT user_id, status, amount, created_at
FROM orders
WHERE user_id = 100 AND status = 'completed';
部分索引
-- 只为活跃订单创建索引
CREATE INDEX idx_active_orders
ON orders (user_id, created_at)
WHERE status = 'active';

-- 只为非空值创建索引
CREATE INDEX idx_users_email
ON users (email)
WHERE email IS NOT NULL;
表达式索引
-- 为计算表达式创建索引
CREATE INDEX idx_users_lower_email
ON users (LOWER(email));

-- 为 JSONB 字段创建索引
CREATE INDEX idx_events_properties
ON events USING GIN ((properties -> 'tags'));

-- 为日期截断创建索引
CREATE INDEX idx_orders_month
ON orders (DATE_TRUNC('month', created_at));


慢查询诊断
慢查询识别
-- PostgreSQL：查看当前运行时间最长的查询
SELECT
    pid,
    now() - pg_stat_activity.query_start AS duration,
    query,
    state
FROM pg_stat_activity
WHERE (now() - pg_stat_activity.query_start) > interval '5 seconds'
    AND state != 'idle'
ORDER BY duration DESC;
-- PostgreSQL：查看最耗时的查询（需要 pg_stat_statements 扩展）
SELECT
    query,
    calls,
    total_exec_time / 1000 AS total_seconds,
    mean_exec_time AS avg_ms,
    rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

索引失效的常见场景
-- 隐式类型转换导致索引失效
-- 假设 user_id 列是 INTEGER 类型
SELECT * FROM orders WHERE user_id = '12345';  -- 字符串导致索引失效
SELECT * FROM orders WHERE user_id = 12345;    -- 正确的类型匹配

-- 对索引列使用函数
SELECT * FROM users WHERE YEAR(created_at) = 2025;  -- 索引失效
SELECT * FROM users WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01';  -- 索引生效

-- 前导通配符
SELECT * FROM users WHERE name LIKE '%张';    -- 索引失效
SELECT * FROM users WHERE name LIKE '张%';    -- 索引生效

-- OR 条件
SELECT * FROM orders WHERE user_id = 100 OR status = 'pending';  -- 可能索引失效
-- 改写为 UNION ALL
SELECT * FROM orders WHERE user_id = 100
UNION ALL
SELECT * FROM orders WHERE status = 'pending' AND user_id != 100;
查询优化检查清单
-- 步骤 1：使用 EXPLAIN ANALYZE 获取实际执行计划
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT ...;

-- 步骤 2：检查是否有不必要的全表扫描
-- 步骤 3：检查 JOIN 的驱动顺序是否合理
-- 步骤 4：检查排序和聚合操作的内存使用
-- 步骤 5：检查估算行数与实际行数的偏差
-- 步骤 6：考虑是否需要创建或调整索引

-- 更新统计信息
ANALYZE table_name;

-- 检查索引使用情况
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan ASC;


查询改写技巧
避免 SELECT *
-- 低效：返回所有列
SELECT * FROM orders WHERE user_id = 100;

-- 高效：只查询需要的列
SELECT order_id, amount, status, created_at
FROM orders
WHERE user_id = 100;
批量操作优化
-- 低效：逐行插入
INSERT INTO logs (user_id, action) VALUES (1, 'click');
INSERT INTO logs (user_id, action) VALUES (2, 'view');
INSERT INTO logs (user_id, action) VALUES (3, 'click');

-- 高效：批量插入
INSERT INTO logs (user_id, action)
VALUES
    (1, 'click'),
    (2, 'view'),
    (3, 'click');
分页查询优化
-- 传统 OFFSET 分页（深分页性能差）
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

-- 游标分页（Keyset Pagination）
SELECT * FROM orders
WHERE created_at < '2025-03-15T10:30:00'
ORDER BY created_at DESC
LIMIT 20;

小结
    

  • 执行计划是查询优化的起点，EXPLAIN ANALYZE 提供实际执行的耗时和行数信息
    • 

  • B-Tree 索引是最通用的索引类型，复合索引应遵循等值优先、范围其次、排序最后的列排序原则
    • 

  • 覆盖索引通过 INCLUDE 子句避免回表，部分索引通过 WHERE 条件减少索引体积
    • 

  • 索引失效的常见原因包括隐式类型转换、函数包裹索引列和前导通配符
    • 

  • 深分页应使用 Keyset Pagination 或延迟关联替代 OFFSET
    • 

  • 定期更新统计信息（ANALYZE）确保优化器生成正确的执行计划
    •
