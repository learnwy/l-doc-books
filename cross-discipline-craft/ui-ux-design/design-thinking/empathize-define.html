设计思维流程

概述

设计思维是由斯坦福大学 d.school 和设计公司 IDEO 推广的一套创新方法论。它的核心假设是：好的解决方案来自于对用户的深入理解，而不是来自于技术人员的自我想象。对于程序员来说，设计思维提供了一种在写代码之前就验证方向正确性的系统化方法，避免了"花三个月开发出来才发现没人用"的悲剧。



设计思维不是一条直线，而是一个循环。每一次测试的反馈都可能让你重新回到共情阶段，这种迭代精神与敏捷开发的理念高度一致。






五阶段详解
第一阶段：共情（Empathize）
共情是设计思维的起点，也是最容易被跳过的阶段。共情的目标不是"我觉得用户需要什么"，而是"用户实际上在经历什么"。

共情的三个层次：


共情阶段的关键原则是"悬挂判断"——暂时放下你作为技术人员的解决方案思维，纯粹地去理解用户的世界。当你听到用户说"这个功能太慢了"，不要立刻想到性能优化，而是追问"慢对你意味着什么？你在等待的时候会做什么？"。


常见陷阱：


    

  • 用封闭式问题代替开放式问题（"你觉得这个好用吗？"vs"你能描述一下你平时是怎么用的吗？"）
    • 

  • 在访谈中引导用户给出你想要的答案
    • 

  • 只关注产品功能而忽略用户的情感和场景
    • 

  • 样本太小或太同质化，无法代表真实用户群体
    • 



第二阶段：定义（Define）
定义阶段的任务是将共情阶段收集的大量信息综合提炼为一个清晰的问题陈述。最常用的工具是"POV 陈述"（Point of View Statement）和"我们如何能"（How Might We）问题。


POV 陈述格式：




[用户] 需要 [需求]，因为 [洞察]。




示例对比：

用户具体、需求清晰、洞察深刻





How Might We（HMW）转化：


从 POV 陈述推导出 HMW 问题是从"问题空间"走向"方案空间"的桥梁。


好的 HMW 问题既不能太宽泛（"我们如何能让购物更好？"），也不能太窄（"我们如何能加一个一键复购按钮？"）。它需要足够开放以激发创意，又足够聚焦以指向有意义的方向。


第三阶段：构思（Ideate）
构思阶段的目标是针对 HMW 问题产生尽可能多的解决方案，然后从中筛选出最值得推进的想法。

第四阶段：原型（Prototype）
原型的目的不是展示最终产品的样子，而是用最低成本把关键假设具象化，以便进行测试。原型的保真度应该与你要验证的假设相匹配。

选择原型保真度的决策框架：


原型制作的核心原则是"刚刚好"——不要在原型上投入超过必要的精力。程序员特别容易犯的错误是把原型做成了完整的 MVP，结果投入了大量时间后发现方向本身就是错的。


第五阶段：测试（Test）
测试是用真实用户来验证原型的阶段。测试的目标不是证明你的设计是对的，而是尽可能多地发现问题和改进空间。

双钻模型
双钻模型（Double Diamond）由英国设计委员会提出，将设计过程分为四个阶段、两次"发散-收敛"的过程，为设计思维提供了更宏观的框架。

双钻模型的关键洞察是：大多数团队的失败不是因为"把事做错了"，而是因为"做了错误的事"。第一颗钻石确保你在解决正确的问题，第二颗钻石确保你用正确的方式解决它。




设计思维与敏捷开发的结合
对程序员来说，设计思维不应该是一个独立于开发流程之外的活动，而应该与敏捷开发紧密结合。

实践框架
程序员如何在日常工作中应用设计思维
你不需要正式地走完五个阶段才能应用设计思维。以下是一些可以立即使用的微实践：


需求评审时：


    

  • 追问"这个需求背后的用户场景是什么？"
    • 

  • 要求看到用户研究数据而不只是产品经理的描述
    • 

  • 思考"有没有更简单的方式满足同样的需求？"
    • 



技术方案设计时：


    

  • 考虑"这个技术方案对用户体验有什么影响？"
    • 

  • 在性能、成本和体验之间做有意识的权衡
    • 

  • 用原型验证交互方案的可行性
    • 



代码评审时：


    

  • 关注代码变更对用户体验的影响
    • 

  • 考虑"用户会如何触发这个功能？异常路径处理是否友好？"
    •

小结
设计思维的五个阶段和双钻模型为程序员提供了一套结构化的思考框架。核心要点是：花时间理解问题比急于编写代码更重要，用原型验证方向比直接开发 MVP 更经济，而持续的用户测试和迭代反馈是确保产品成功的基础。在下一节中，我们将深入共情图谱的制作方法，帮你系统性地捕捉和分析用户需求。
