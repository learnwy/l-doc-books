文档 Lint 与校验

核心概念

文档 Lint 是对文档源文件进行自动化质量检查的工程实践，类比代码 Lint 对源代码的作用——它在文档提交前检测格式错误、风格不一致、拼写错误和断链等问题，将人工审查中的机械性检查自动化，使审查者能专注于内容的准确性和逻辑性。文档 Lint 是 Docs-as-Code 流程中质量保障的第一道防线。

markdownlint 格式规范
markdownlint 是 Markdown 格式检查的事实标准。它检查 Markdown 文件是否遵循一致的格式规范，包括标题层级、列表缩进、空行规则、代码块格式等。


规则配置：markdownlint 提供约 50 条内置规则（MD001-MD053），每条规则可以独立启用/禁用/配置参数。配置文件为 .markdownlint.json 或 .markdownlint-cli2.yaml。


{
  "MD013": { "line_length": 120 },
  "MD024": { "siblings_only": true },
  "MD033": { "allowed_elements": ["details", "summary", "br"] },
  "MD041": false,
  "MD046": { "style": "fenced" }
}
高频规则说明：


    

  • MD013（行长度限制）：默认 80 字符，技术文档通常放宽到 120 或禁用
    • 

  • MD024（重复标题）：siblings_only: true 允许不同章节使用相同标题
    • 

  • MD033（内联 HTML）：文档站常需要 <details> 等 HTML 元素，通过白名单放行
    • 

  • MD041（首行标题）：与 Front Matter 冲突时需禁用
    • 



自定义规则：当内置规则无法覆盖团队特定需求时，可以编写自定义规则。每条自定义规则是一个接收文件内容、返回违规位置的函数。例如禁止在文档中使用特定术语、要求每个文档必须包含特定章节。


vale 风格校验
vale 是一个可编程的自然语言风格检查器，它不仅检查拼写和语法，还能执行复杂的风格规则——术语一致性、被动语态检测、句子复杂度评估、品牌用语规范等。vale 的核心理念是"编写规则，而非使用预设"。


风格包：vale 通过 .vale.ini 配置文件指定使用的风格包。社区提供了多个现成的风格包：Microsoft（微软写作风格）、Google（Google 开发者文档风格）、write-good（通用写作改善）。


StylesPath = .vale/styles
MinAlertLevel = suggestion

[*.md]
BasedOnStyles = Microsoft, write-good

[*.md]
Microsoft.Headings = YES
Microsoft.Passive = suggestion
write-good.TooWordy = warning
自定义规则编写：vale 使用 YAML 格式定义规则，支持正则匹配、词典匹配和作用域限定。例如强制使用特定术语：


extends: substitution
message: "使用 '%s' 替代 '%s'"
level: error
ignorecase: true
swap:
  死锁: 死锁
  deadlock: 死锁
  后端: 后端
  backend: 后端
链接检查与断链防护
断链是文档质量最常见的问题之一——文档重组后的内部链接失效、外部 URL 过期、锚点引用的标题被修改。自动化链接检查是防止断链的关键手段。


内部链接检查：验证文档间的相对链接和锚点链接是否指向有效目标。构建框架（Docusaurus、VitePress）通常在构建时检测内部断链并输出警告。额外的工具如 remark-lint-no-dead-urls 可以在 Markdown 管道中集成链接检查。


外部链接检查：验证文档中引用的外部 URL 是否仍然可访问。linkinator 和 lychee 是两款常用工具，支持并发检查和缓存机制以加速大规模扫描。外部链接检查应在 CI 中定期运行（而非每次提交都运行），因为外部服务的临时不可用会导致误报。


锚点链接检查：验证页面内的 #section-name 锚点是否对应有效的标题 ID。标题重命名是最常见的锚点断链原因。remark-lint-no-undefined-references 插件可以在 Markdown 层面检测无效锚点。


链接检查策略：推荐的策略是在每次 PR 中检查内部链接和锚点（快速、无误报），每周定时检查外部链接（避免频繁外部请求和临时误报），每次大规模文档重组后全量检查所有链接。


CI 集成最佳实践
将文档 Lint 工具集成到 CI 流水线是确保文档质量的最后一道自动化防线。


渐进式引入：对于已有大量文档的项目，一次性启用所有 Lint 规则会产生数百个错误，令团队不知所措。推荐的策略是：先以 warning 级别启用所有规则，逐步将最重要的规则提升为 error，设置基线（baseline）忽略存量问题。


本地开发集成：通过 IDE 插件（VS Code markdownlint 扩展、vale VS Code 扩展）在编辑器中实时显示 Lint 问题。通过 Git pre-commit 钩子（husky + lint-staged）在提交前自动运行检查。这两层本地保障能在问题到达 CI 之前就被发现。


错误输出格式化：CI 中的 Lint 输出应格式化为 GitHub Annotations（通过 --format 选项或 Problem Matcher），使错误信息直接显示在 PR 的 Files Changed 视图中对应行上。开发者无需跳转到 CI 日志即可看到具体问题。


性能优化：只对本次 PR 变更的文件运行 Lint（通过 git diff --name-only 筛选），避免全量扫描导致的时间浪费。缓存 vale 的风格包下载和 cspell 的词典加载，减少 CI 冷启动时间。


小结
    

  • 文档 Lint 是 Docs-as-Code 质量保障的第一道防线，自动化机械性检查
    • 

  • markdownlint 检查格式规范，约 50 条规则可按项目需求精细配置
    • 

  • vale 检查自然语言风格，通过自定义规则确保术语一致性和写作规范
    • 

  • 链接检查应分层策略：PR 内检查内部链接，定期检查外部链接
    • 

  • CI 集成推荐渐进式引入，配合本地 IDE 插件和 pre-commit 钩子
    •
