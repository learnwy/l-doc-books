文档保鲜策略

核心概念

文档保鲜是指通过系统化的方法确保文档内容与产品实际行为保持同步的持续性工程活动。过时文档的危害往往比缺失文档更大——开发者依据过时文档编写的代码会在运行时出错，而缺失文档至少不会产生误导。研究表明，企业级软件文档在发布 6 个月后有 30-40% 的内容已不再准确。文档保鲜的目标是将这一比例控制在 5% 以下。

过时检测机制
主动检测过时文档是保鲜策略的第一步。等到用户发现并报告问题时，信任已经受损。


基于 Git 历史的新鲜度分析：通过分析每个文档文件的最后修改时间和对应代码文件的最后修改时间，计算两者的时间差。当代码文件在文档最后更新之后发生了变更，文档可能已过时。


interface FreshnessReport {
  filePath: string;
  lastDocUpdate: Date;
  lastCodeUpdate: Date;
  daysSinceDocUpdate: number;
  relatedCodeChanged: boolean;
  freshnessScore: 'fresh' | 'stale' | 'critical';
}

const calculateFreshness = (docPath: string, codePatterns: string[]): FreshnessReport => {
  const docLastModified = getGitLastModified(docPath);
  const codeLastModified = codePatterns.map(getGitLastModified).sort((a, b) => b.getTime() - a.getTime())[0];

  const daysSince = daysBetween(docLastModified, new Date());
  const codeChanged = codeLastModified > docLastModified;

  return {
    filePath: docPath,
    lastDocUpdate: docLastModified,
    lastCodeUpdate: codeLastModified,
    daysSinceDocUpdate: daysSince,
    relatedCodeChanged: codeChanged,
    freshnessScore: codeChanged ? 'critical' : daysSince > 180 ? 'stale' : 'fresh',
  };
};
API 规范一致性检测：对比 OpenAPI 规范文件与文档中描述的 API 行为是否一致。检测维度包括：端点路径和方法是否匹配、参数列表是否完整、响应字段是否准确。不一致的部分标记为需要更新。


截图比对：对于包含 UI 截图的文档，使用视觉回归测试工具（如 Percy）定期对比文档中的截图与产品实际界面。UI 变更后截图不一致的文档自动标记为需要更新。


代码变更联动
将文档更新与代码变更紧密关联，是防止文档过时的最有效机制。


PR 检查机制：在 CI 流水线中检测代码变更是否涉及公共 API 修改。如果涉及，检查是否同时包含文档更新。对缺少文档更新的 PR 添加警告标签或阻止合并。


文档关联映射：维护一份代码路径到文档路径的映射表。当 src/api/users.ts 被修改时，系统自动检查 docs/api/users.md 是否在同一 PR 中被修改。映射关系可以通过文件命名约定自动推断，也可以在配置文件中显式声明。


doc-code-mapping:
  - code: src/api/users/**
    docs: docs/api/users.md
  - code: src/auth/**
    docs: docs/guides/authentication.md
  - code: src/config/schema.ts
    docs: docs/reference/configuration.md
自动生成内容刷新：对于从代码自动生成的文档（如 TypeDoc API 参考、OpenAPI 文档），在代码变更后自动重新生成并提交更新。这类文档的保鲜完全自动化，无需人工介入。


弃用通知传播：当代码中的函数或 API 被标记为 @deprecated 时，自动检测引用该 API 的文档，并创建 Issue 或 PR 更新文档中的相关描述。


定期审查计划
定期审查是捕获自动化手段无法覆盖的过时内容的补充机制。


季度保鲜审查：每季度组织一次全量文档保鲜审查。将文档按模块分配给对应的技术负责人，每人负责验证自己模块文档的准确性。审查结果记录在 Issue 追踪系统中，设定修复期限。


保鲜日历：为每篇文档设定审查周期（基于变更频率）。高变更频率的 API 文档每月审查，概念文档每季度审查，架构文档每半年审查。保鲜日历通过 Front Matter 中的 review_date 字段管理，CI 定期扫描并创建审查提醒。


用户反馈闭环：文档页面的"内容是否准确？"反馈按钮不仅收集满意度数据，还为过时检测提供信号。当某篇文档收到多个"不准确"反馈时，优先安排审查。反馈处理后，通知原反馈者问题已修复，完成闭环。

保鲜度可视化
将文档保鲜状态可视化，帮助团队快速掌握文档体系的整体健康状况。


保鲜度热力图：以文档目录结构为维度，用颜色编码展示每篇文档的新鲜度——绿色（0-30 天内更新）、黄色（31-90 天）、橙色（91-180 天）、红色（超过 180 天）。热力图使过时文档的分布一目了然。


保鲜度趋势图：追踪"新鲜文档占比"的时间趋势。理想的趋势是新鲜文档占比稳定在 90% 以上。如果趋势下降，说明文档更新速度跟不上产品迭代速度，需要增加文档资源投入或优化保鲜流程。


负责人仪表板：每位文档负责人看到自己负责的文档列表及其新鲜度状态。仪表板突出显示需要立即关注的文档（红色状态），并提供一键创建更新 Issue 的功能。


自动化报告：每周自动生成保鲜度报告，通过邮件或 Slack 发送给文档团队和工程 Lead。报告包含本周新过时的文档数量、已修复的文档数量和整体新鲜度评分。


小结
    

  • 过时文档的危害大于缺失文档，保鲜目标是将不准确比例控制在 5% 以下
    • 

  • 过时检测结合 Git 时间分析、API 规范对比和截图比对实现多维度覆盖
    • 

  • 代码变更联动是最有效的保鲜机制，通过 PR 检查和映射表确保文档与代码同步
    • 

  • 定期审查弥补自动化的盲区，按文档类型设定不同的审查周期
    • 

  • 保鲜度热力图和趋势图使文档健康状况一目了然，驱动团队持续投入
    •
