API 变更日志

核心概念

API 变更日志是记录 API 每次版本发布中所有变更的结构化文档，它是 API 提供者与消费者之间的变更契约。与普通软件的 CHANGELOG 不同，API 变更日志需要特别关注向后兼容性——每一个字段的添加、修改或移除都可能影响成千上万的下游应用。一份清晰、及时、结构化的变更日志，能让开发者在几分钟内评估升级影响并制定迁移计划。

变更分类体系
API 变更的分类直接影响消费者的评估效率。业界通用的四级分类法是：


新增（Added）：新的端点、新的请求参数（可选）、新的响应字段、新的查询过滤器。这类变更通常不影响现有集成，是最安全的变更类型。


变更（Changed）：现有行为的修改——响应字段类型变化、默认值调整、错误码语义变化、速率限制调整。即使技术上向后兼容，行为变更也需要消费者评估是否影响其业务逻辑。


弃用（Deprecated）：标记即将移除的功能。弃用通知必须包含：弃用生效时间、计划移除时间、替代方案、迁移指引链接。弃用不等于移除——弃用的功能在公告的生命周期内必须继续正常工作。


移除（Removed）：破坏性变更，已弃用功能的最终移除。这类变更必须在大版本升级中进行，必须在至少一个完整版本周期前发布弃用通知。


破坏性变更的判定标准：移除端点或请求参数、修改必填参数的约束条件（如将可选变为必填）、修改响应字段的类型或结构、修改认证方式、修改错误码的 HTTP 状态码。一个关键原则是：新增总是安全的，移除和修改需要谨慎评估。


自动化变更检测
手动维护变更日志容易遗漏变更或描述不准确。自动化工具从 OpenAPI 规范的版本差异中精确检测每一处变更。


oasdiff 是专为 OpenAPI 设计的差异检测工具，能对比两个版本的规范文件并生成结构化的变更报告。它可以区分破坏性变更和非破坏性变更，并按端点、参数、响应等维度分类输出。


oasdiff diff openapi-v1.yaml openapi-v2.yaml --format yaml
oasdiff breaking openapi-v1.yaml openapi-v2.yaml
oasdiff changelog openapi-v1.yaml openapi-v2.yaml --format markdown
CI 集成：在 Pull Request 阶段运行变更检测，自动在 PR 中评论变更摘要。对于检测到的破坏性变更，阻止合并并要求开发者确认是否有意引入。这种"变更感知"的 CI 流水线能在设计阶段就捕获意外的破坏性变更。


Conventional Commits 驱动：如果团队采用约定式提交（如 feat(api): fix(api): BREAKING CHANGE:），可以从 Git 提交历史自动生成变更日志。工具如 standard-version 或 semantic-release 能基于提交类型自动确定版本号和生成 CHANGELOG。


GraphQL 变更检测：对于 GraphQL API，使用 graphql-inspector 对比 Schema 差异。它能检测字段移除、类型变更、弃用标记等变更，并判断是否属于破坏性变更。


变更日志格式设计
一份优秀的变更日志应兼顾机器可读性和人类可读性。


时间线结构：按发布日期倒序排列，最新版本在最上方。每个版本条目包含版本号、发布日期和变更列表。遵循 Keep a Changelog 格式规范。


## [2.3.0] - 2025-03-15

### Added

- `GET /users` 新增 `sort` 查询参数，支持按 `created_at` 和 `name` 排序
- 用户响应新增 `avatar_url` 字段

### Changed

- `GET /users` 默认分页大小从 20 调整为 50
- 速率限制从每分钟 100 次提升到每分钟 200 次

### Deprecated

- `GET /users` 的 `offset` 参数将在 v3.0 移除，请使用 `cursor` 参数替代
  - 迁移指南: [从 offset 迁移到 cursor 分页](/guides/cursor-migration)
  - 计划移除时间: 2025-09-01

## [2.2.1] - 2025-02-28

### Fixed

- 修复 `PATCH /users/:id` 在并发更新时返回 500 的问题
API Diff 视图：除了文字描述外，提供结构化的 Diff 视图展示规范文件的具体差异。类似代码 Diff，用红色标注移除的字段/参数，绿色标注新增的部分。这种视图对技术深度了解的消费者特别有用。


多渠道发布：变更日志不应只存在于文档站。关键变更应通过邮件列表、Webhook、RSS Feed 等渠道主动推送给消费者。对于破坏性变更，应在计划执行前至少 30 天通过多个渠道反复通知。


弃用生命周期管理
弃用管理是 API 变更日志中最复杂也最重要的部分。一个清晰的弃用流程建立消费者信任，一个混乱的弃用流程则可能导致消费者流失。


弃用时间线：标准的弃用生命周期包含四个阶段——公告（Announce）、警告（Warn）、迁移期（Migration）、移除（Remove）。每个阶段有明确的起止时间和行为定义。

运行时弃用信号：在弃用阶段，API 响应中添加 Deprecation 和 Sunset HTTP 头（RFC 8594），告知消费者弃用时间和计划移除日期。SDK 在收到这些头时应输出警告日志。


使用量驱动决策：通过 API 网关的统计数据了解弃用功能的实际使用量。如果某个即将移除的端点仍有大量调用，应考虑延长迁移期或主动联系主要消费者提供迁移支持。


小结
    

  • API 变更日志记录每次版本发布的所有变更，是提供者与消费者之间的变更契约
    • 

  • 变更分类为新增、变更、弃用和移除四类，破坏性变更必须在大版本中进行
    • 

  • 自动化工具（oasdiff、graphql-inspector）从规范差异精确检测变更，CI 集成阻止意外破坏
    • 

  • 变更日志应兼顾机器可读和人类可读，通过多渠道主动推送关键变更
    • 

  • 弃用生命周期包含公告、警告、迁移期和移除四个阶段，运行时通过 HTTP 头传递信号
    •
