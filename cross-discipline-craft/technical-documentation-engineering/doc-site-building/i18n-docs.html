多语言文档

核心概念

多语言文档（i18n 文档）是为不同语言的用户提供本地化文档内容的工程实践。对于全球化的开源项目和产品，多语言文档不仅是翻译文本的问题，还涉及内容同步、翻译工作流、语言切换体验和构建部署等一系列工程挑战。据统计，提供本地化文档的开源项目比仅提供英文文档的项目采纳率高出 30-50%。

翻译工作流设计
翻译工作流是多语言文档工程的核心环节。一个高效的工作流需要平衡翻译质量、同步速度和维护成本。


源语言确定：选择一种语言作为源语言（通常是英语），所有内容首先以源语言编写，其他语言通过翻译获得。源语言文档的变更驱动翻译更新。


翻译平台集成：专业翻译平台（如 Crowdin、Transifex、Weblate）提供完整的翻译管理功能——翻译记忆库、术语表、协作审查和自动同步。Docusaurus 原生支持 Crowdin 集成，可以自动将源文件上传到 Crowdin 并将翻译结果拉回仓库。


npx docusaurus write-translations --locale zh-Hans
npx crowdin upload sources
npx crowdin download
社区翻译模式：开源项目常采用社区驱动的翻译模式。贡献者通过 Pull Request 提交翻译，维护者审查合并。关键实践包括：提供翻译贡献指南（说明术语约定和格式要求）、使用翻译覆盖率仪表板追踪进度、对活跃翻译者给予公开致谢。


AI 辅助翻译：大语言模型在技术文档翻译中表现出色——能准确处理技术术语、保持代码块不被翻译、维持 Markdown 格式。推荐的工作流是 AI 初译 → 人工审查 → 修正术语和表达。相比纯人工翻译，AI 辅助可以将翻译速度提升 3-5 倍。


框架层面的 i18n 支持
主流文档框架对多语言的支持程度各不相同。


Docusaurus i18n：Docusaurus 提供最完整的文档 i18n 支持。通过 i18n 配置声明支持的语言列表和默认语言。使用 docusaurus write-translations 命令提取 UI 字符串（导航栏、侧边栏标签等）的翻译模板。翻译后的文档文件放在 i18n/{locale}/ 目录下，构建时自动合并。


const config: Config = {
  i18n: {
    defaultLocale: 'en',
    locales: ['en', 'zh-Hans', 'ja'],
    localeConfigs: {
      en: { label: 'English' },
      'zh-Hans': { label: '简体中文' },
      ja: { label: '日本語' },
    },
  },
};
VitePress i18n：VitePress 通过目录前缀实现多语言路由。例如 /zh/guide/intro.md 对应中文版本。需要手动配置每种语言的导航栏和侧边栏。VitePress 没有内置的 UI 字符串翻译机制，需要通过主题扩展实现。


MkDocs i18n：通过 mkdocs-i18n 插件或 mkdocs-static-i18n 插件支持多语言。每种语言使用独立的配置文件，可以定制不同语言版本的导航结构。


翻译同步与新鲜度
翻译内容与源文档的同步是多语言文档最大的工程挑战。源文档频繁更新时，翻译版本很容易变得过时。


变更追踪机制：记录每个翻译文件与源文件的同步状态。实现方式包括：在翻译文件的 Front Matter 中记录源文件的 Git commit hash；使用脚本对比源文件和翻译文件的最后修改时间；翻译平台的内置同步状态追踪。


过时翻译提示：当翻译内容落后于源文档时，在页面上显示醒目提示——"本页翻译可能已过时，最新内容请参阅英文版"，并提供指向对应英文页面的链接。这比展示过时内容而不提示更能保护用户信任。


翻译覆盖率仪表板：建立可视化的翻译覆盖率报告——每种语言的翻译完成百分比、过时翻译数量、待审查翻译数量。仪表板帮助团队确定翻译优先级，也为社区贡献者指明最需要帮助的区域。


渐进式翻译策略：不要求所有页面都完成翻译才上线。对于未翻译的页面，回退到源语言版本并显示"该页面尚未翻译"的提示。优先翻译高流量页面（快速入门、核心概念），长尾页面留给社区逐步补完。


语言切换与用户体验
多语言文档的用户体验设计影响用户能否顺畅地使用本地化内容。


语言选择器：通常放置在导航栏右侧，使用下拉菜单展示所有可用语言。每种语言使用其本地名称标记（如"简体中文"而非"Chinese"），方便非英语用户识别。当前语言应有视觉标识。


自动语言检测：根据浏览器的 Accept-Language 头自动将用户重定向到最匹配的语言版本。如果用户手动切换了语言，将选择存储在 Cookie 或 localStorage 中，后续访问维持用户选择。


语言切换行为：切换语言时，应尝试导航到目标语言的对应页面。如果该页面尚未翻译，回退到目标语言的首页，并提示"该页面暂无翻译"。避免在语言切换时丢失用户的浏览位置。


SEO 多语言：为每个页面添加 hreflang 标签，告知搜索引擎页面的各语言版本关系。URL 结构推荐使用子路径模式（/zh/docs/）而非子域名模式（zh.docs.example.com），前者管理更简单且 SEO 权重更集中。


小结
    

  • 多语言文档将本地化文档的采纳率提升 30-50%，是全球化项目的必要投入
    • 

  • 翻译工作流的选择取决于团队规模——专业平台适合商业产品，社区翻译适合开源项目
    • 

  • AI 辅助翻译能将技术文档翻译速度提升 3-5 倍，但仍需人工审查术语和表达
    • 

  • 翻译同步是最大挑战，通过变更追踪、过时提示和渐进式翻译策略应对
    • 

  • 语言选择器使用本地名称、支持自动检测、切换时保持页面对应关系
    •
