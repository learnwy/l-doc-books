ETL 设计模式

核心概念

ETL（Extract-Transform-Load）和 ELT（Extract-Load-Transform）是数据仓库数据集成的两大范式。ETL 设计模式关注的是如何可靠、高效、可维护地将数据从源系统搬运到数据仓库，并在过程中完成必要的清洗和转换。对于程序员而言，ETL 管道本质上是一个复杂的数据处理流水线，其设计质量直接影响数据仓库的可靠性。

增量加载模式
增量加载是 ETL 性能优化的核心手段。全量加载每次处理所有数据，简单但低效；增量加载只处理自上次执行以来变化的数据，大幅减少处理量和延迟。


基于时间戳的增量加载是最常见的模式。它依赖源表中的 updated_at 字段，每次 ETL 只抽取 updated_at > last_run_timestamp 的记录。这种模式简单高效，但有两个限制：源表必须有可靠的更新时间戳，且无法捕获物理删除。


基于 CDC 的增量加载通过监听数据库的变更日志（如 MySQL binlog、PostgreSQL WAL）来捕获所有数据变更，包括插入、更新和删除。CDC 能提供更完整的增量数据，但引入了额外的基础设施复杂度。


水位线（Watermark）模式是增量加载的通用抽象。ETL 管道维护一个状态表，记录每个数据源的最后处理位置（时间戳、偏移量或 LSN）。每次执行时，从水位线位置开始抽取，完成后更新水位线。


幂等性设计
幂等性意味着同一个 ETL 任务执行一次和执行多次的结果完全相同。这个属性在分布式系统中至关重要——当任务因超时或网络错误失败后重试时，幂等性保证不会产生重复数据。


实现幂等性的核心策略有三种：分区替换（按日期分区，每次执行先删除目标分区再插入，确保重复执行只替换同一分区）；MERGE/UPSERT（使用数据库的 MERGE 或 INSERT ON CONFLICT 语法，存在则更新、不存在则插入）；临时表 + 原子替换（先写入临时表，验证通过后以原子操作替换目标表）。

数据质量保障模式
数据质量是 ETL 管道中最容易被忽视但影响最大的环节。"垃圾进，垃圾出"——如果 ETL 不做数据质量检查，脏数据会直接污染数据仓库，导致分析结果不可信。


数据质量检查应该嵌入 ETL 流程的每个关键节点：抽取后检查（源数据是否完整、记录数是否在预期范围内）；转换后检查（主键是否唯一、必填字段是否为空、引用完整性是否满足）；加载后检查（目标表记录数变化是否合理、关键指标是否异常波动）。


dbt 提供了内置的数据测试框架，支持 unique（唯一性）、not_null（非空）、accepted_values（值域）、relationships（引用完整性）四种开箱即用的测试，以及自定义 SQL 测试。


当质量检查失败时，ETL 管道应该遵循"失败安全"原则——宁可暂停数据更新（保持昨天的数据），也不要让脏数据流入数据仓库。配合告警通知，让数据工程师在第一时间介入处理。


调度与编排模式
ETL 管道通常由多个相互依赖的任务组成，需要调度系统来管理执行顺序、处理失败重试和监控运行状态。


Apache Airflow 是目前最流行的 ETL 调度框架。它使用 Python 代码定义 DAG（有向无环图）来描述任务之间的依赖关系。每个任务是 DAG 中的一个节点，依赖关系通过边来表达。Airflow 的调度器会根据依赖关系和时间调度策略自动执行任务。


调度设计的关键考量包括：执行频率（根据业务需求选择小时级、天级或实时）；依赖管理（确保上游任务完成后才触发下游）；重试策略（失败任务的重试次数、间隔和回退策略）；并发控制（限制对源系统的并发访问，避免影响线上服务）。


小结
    

  • ETL 设计的核心原则是幂等性、可观测性和错误恢复能力
    • 

  • 增量加载通过水位线机制只处理变化数据，大幅提升效率
    • 

  • 幂等性可通过分区替换、MERGE 和临时表替换等策略实现
    • 

  • 数据质量检查应嵌入 ETL 流程的每个关键节点
    • 

  • dbt 提供了强大的数据测试框架，支持多种开箱即用的质量检查
    • 

  • Airflow 是最流行的 ETL 调度框架，通过 DAG 管理任务依赖
    •
