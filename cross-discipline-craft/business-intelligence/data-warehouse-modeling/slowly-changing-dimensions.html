缓慢变化维

核心概念

缓慢变化维（Slowly Changing Dimension，SCD）是数据仓库中处理维度属性历史变化的方法论。在现实业务中，维度属性并非一成不变——用户会搬家、产品会改名、员工会换部门。如何在维度表中正确记录这些变化，是数据仓库建模的核心挑战之一。

SCD 的处理方式决定了分析师能否回答"某用户在搬家之前的消费行为如何"这类历史关联问题。不同的 SCD 类型在历史保留能力、查询复杂度和存储开销之间做出不同的权衡。

SCD Type 1：直接覆盖
Type 1 是最简单的处理方式——当维度属性发生变化时，直接用新值覆盖旧值。这意味着维度表中永远只保存最新状态，历史信息被丢弃。


Type 1 适用于两类场景：一是数据纠错（修正录入错误的地址），这种变更本身就不应该产生历史记录；二是业务上不关心历史变化的属性（如用户头像 URL）。


Type 1 的优势是实现简单——ETL 逻辑只需要一个 UPDATE 语句。但它的致命缺陷是不可逆——一旦覆盖，旧值就永久丢失了。如果后续业务提出"按用户之前的地址统计销售额"的需求，你将无法满足。


SCD Type 2：新增行保留完整历史
Type 2 是最常用也最强大的 SCD 策略。当维度属性发生变化时，不修改现有行，而是新增一行来记录新状态。通过有效开始日期、有效结束日期和当前标志位来区分同一实体的不同历史版本。


Type 2 的实现需要在维度表中额外维护三个字段：effective_start_date（该版本的生效日期）、effective_end_date（该版本的失效日期，当前有效版本为 NULL 或一个极大值如 9999-12-31）、以及 is_current（是否为当前有效版本的布尔标志）。


Type 2 的核心优势是完整的历史追溯能力。你可以查询任意历史时间点上用户的属性状态，实现精确的历史分析。但它也带来了明显的复杂度：维度表行数膨胀（一个变更频繁的用户可能有数十行）、JOIN 逻辑需要考虑有效期过滤、以及代理键与自然键的映射维护。


ETL 实现 Type 2 的标准流程是：用自然键匹配现有记录 → 比较属性值是否变化 → 如有变化，关闭旧版本（设置 end_date 和 is_current=false）→ 插入新版本 → 生成新的代理键。


SCD Type 3 与 Type 6
Type 3 通过在维度表中新增列（而非新增行）来记录变更前后的值。典型的实现是增加 previous_city 和 current_city 两个列。这种方式只能保留最近一次变更的历史，适用于只关心"从 A 变成了 B"的分析场景。


Type 6（也称为 Hybrid SCD）是 Type 1、2、3 的混合。它在 Type 2 的基础上，通过额外的列存储当前值，使查询既能获取历史版本的完整属性（Type 2），又能直接拿到最新属性（Type 1/3），无需额外 JOIN。

混合策略与工程实践
在实际项目中，一个维度表中的不同属性可能需要不同的 SCD 策略。例如，用户维度表中的"出生日期"适合 Type 0（永不变更），"邮箱"适合 Type 1（纠错覆盖），"城市"适合 Type 2（保留搬家历史）。


这种按属性粒度选择 SCD 类型的混合策略是业界最佳实践。dbt 的 dbt-snapshot 功能原生支持 Type 2 的自动化管理——它通过对比每次运行的数据快照来自动检测变更、关闭旧版本、插入新版本。


工程实践中还需要注意以下问题：批量变更处理（当上游系统做了大规模数据迁移时，不应该将所有变更都视为真实的业务变化）；变更频率控制（对于变更极其频繁的属性，Type 2 可能导致维度表急剧膨胀，需要考虑 Type 4 或定期归档）；补数据场景（历史数据回填时需要正确设置有效期，避免与现有记录冲突）。


小结
    

  • 缓慢变化维定义了维度属性历史变化的处理策略
    • 

  • Type 2 是最常用的策略，通过新增行保留完整历史
    • 

  • 实际项目中通常对同一维度表的不同属性采用不同 SCD 类型
    • 

  • dbt-snapshot 可以自动化 Type 2 的变更检测和版本管理
    • 

  • 工程实践需要关注批量变更、变更频率和补数据等场景
    • 

  • SCD 策略选择的核心是在历史保留能力和实现复杂度之间权衡
    •
