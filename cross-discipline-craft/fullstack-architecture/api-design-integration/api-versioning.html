API 版本管理与演进

版本化的本质问题

API 版本管理的核心挑战不是技术实现，而是一个产品决策：如何在不破坏现有消费者的前提下持续演进 API 能力。每一次 Breaking Change 都可能导致客户端中断、移动应用审核延迟、合作伙伴集成失败。因此，好的版本管理策略的目标是最小化 Breaking Change 的频率和影响范围，而非简单地提供版本切换机制。

Breaking Change 的定义需要精确：

变更类型 是否 Breaking 说明
新增可选字段 否 现有客户端忽略新字段
新增必填请求参数 是 现有客户端缺少该参数会报错
删除响应字段 是 依赖该字段的客户端将崩溃
修改字段类型 是 反序列化将失败
修改字段语义 是（隐性） 最危险——不报错但行为错误
新增端点 否 不影响现有调用
删除端点 是 依赖该端点的客户端将失败

REST API 版本管理策略

URL 路径版本化

最直观的版本化方案：将版本号嵌入 URL 路径。

GET /api/v1/orders/123
GET /api/v2/orders/123

优势：

  • 版本一目了然，调试友好
  • CDN 和代理可基于路径轻松路由
  • 客户端升级路径明确

劣势：

  • 大版本升级时需要维护多套端点实现
  • 倾向于积累大量的"一次性版本跳跃"
  • 资源 URL 变化破坏 RESTful 的资源标识一致性

适用场景：公开 API、合作伙伴集成、移动端（App Store 审核导致客户端无法同步升级）。

Header 版本化

通过自定义 Header 或 Accept 头传递版本信息：

GET /api/orders/123
Accept: application/vnd.myapp.v2+json

或自定义 Header：

GET /api/orders/123
X-API-Version: 2024-03-01

优势：

  • URL 保持稳定，符合 REST 资源标识原则
  • 支持基于日期的版本（GitHub API 风格）
  • 便于实现渐进式灰度切换

劣势：

  • 对客户端不够直观，容易遗漏
  • 浏览器直接访问不携带自定义 Header
  • API 文档展示复杂

查询参数版本化

GET /api/orders/123?version=2

实践中较少采用，因为查询参数通常用于筛选和分页，混入版本信息容易造成语义混乱。

日期版本化（推荐趋势）

Stripe 首创的日期版本化策略在 2026 年被越来越多的 API 产品采纳：

Stripe-Version: 2026-03-15

核心理念：每次 Breaking Change 对应一个日期版本，API 服务端根据客户端声明的版本日期返回对应行为。新注册的客户端自动获得最新版本，已有客户端保持在其声明的版本直到主动升级。

实现方式：服务端维护一个变更日志，通过中间件层根据请求版本动态调整响应格式。


GraphQL 的 Schema 演进
GraphQL 的设计哲学从根本上排斥传统版本化——它通过 Schema 的渐进式演进实现向后兼容：


字段废弃（Deprecation）：


type User {
  id: ID!
  name: String!
  fullName: String! # 新字段
  username: String @deprecated(reason: "Use fullName instead. Removal: 2026-09-01")
}
字段监控驱动下线：


通过 Apollo Studio 或自建监控追踪已废弃字段的实际调用量，当调用降至零（或低于阈值）时安全移除。


Schema 扩展而非修改：


    

  • 新增字段：总是安全的，客户端只查询自己需要的字段
    • 

  • 新增类型：安全，不影响现有查询
    • 

  • 新增枚举值：客户端需要处理未知枚举（推荐模式：使用 UNKNOWN 兜底）
    •

api-compatibility-check:
  steps:
    - name: Compare OpenAPI Specs
      run: |
        oasdiff breaking api/v1/openapi.yaml api/v1/openapi-new.yaml
    - name: GraphQL Schema Check
      run: |
        rover subgraph check my-graph --schema schema.graphql

向后兼容设计模式
与其在事后管理版本，不如在设计时就最大化向后兼容性：


Tolerant Reader 模式：客户端只解析自己需要的字段，忽略未知字段。JSON 天然支持此模式。


Postel's Law（稳健性原则）：对输入宽容，对输出严格。接受多种格式的输入参数，但输出始终使用最严格的格式。


Additive Change Only：只增不删。新功能通过新增字段/端点实现，旧端点保持行为不变直到显式废弃。


Feature Flag 控制：新的 API 行为通过 Feature Flag 控制灰度开启，而非通过版本号硬切换。


这些模式共同构成了一种"演进友好"的 API 设计文化：每一次变更都默认向后兼容，Breaking Change 成为需要充分论证的例外情况而非常态。
