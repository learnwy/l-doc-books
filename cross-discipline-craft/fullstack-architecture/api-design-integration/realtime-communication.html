实时通信架构设计

实时通信的场景光谱

现代应用对"实时性"的需求存在巨大差异。消息通知需要秒级推送，协作编辑需要毫秒级同步，金融行情需要微秒级更新。不同的实时性需求对应不同的技术选型和架构复杂度。在选择实时通信方案之前，首先需要明确场景的核心约束。

场景 延迟要求 通信模式 连接数规模 推荐方案
通知推送 1-5s 服务端→客户端 百万级 SSE / Push API
即时消息 < 500ms 双向 十万级 WebSocket
协作编辑 < 100ms 双向多播 千级/文档 WebSocket + CRDT
实时仪表盘 1-10s 服务端→客户端 万级 SSE / GraphQL Subscription
在线游戏 < 50ms 双向高频 千级/房间 WebSocket / WebRTC
金融行情 < 10ms 服务端→客户端 万级 WebSocket + 二进制协议

WebSocket 深入解析

WebSocket 是全双工通信的标准协议，通过 HTTP Upgrade 握手后在单个 TCP 连接上建立持久的双向通道。它是实时通信领域最通用的解决方案。

多节点广播架构：


当应用服务需要向特定用户推送消息时，它将消息发布到 Redis Pub/Sub 频道。所有 WebSocket 节点都订阅该频道，收到消息后各自检查目标用户是否连接在自己节点上，有则推送。


Server-Sent Events（SSE）
SSE 是基于 HTTP 的服务端单向推送协议。它利用标准的 HTTP 连接传输文本事件流，天然兼容所有 HTTP 基础设施（代理、CDN、负载均衡器）。

SSE 服务端实现：


app.get('/events', (req, res) => {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    Connection: 'keep-alive',
    'X-Accel-Buffering': 'no', // 禁止 Nginx 缓冲
  });

  // 发送事件
  const sendEvent = (event: string, data: unknown) => {
    res.write(`event: ${event}\n`);
    res.write(`data: ${JSON.stringify(data)}\n`);
    res.write(`id: ${Date.now()}\n\n`);
  };

  // 订阅消息源
  const unsubscribe = eventBus.subscribe('notifications', (msg) => {
    sendEvent('notification', msg);
  });

  // 连接关闭时清理
  req.on('close', () => {
    unsubscribe();
    res.end();
  });
});

gRPC 流式通信
gRPC 支持四种调用模式，其中流式模式为高性能实时通信提供了强类型、高效率的选择：


service ChatService {
  // 一元调用
  rpc SendMessage(ChatMessage) returns (SendResult);

  // 服务端流 - 订阅消息
  rpc SubscribeMessages(SubscribeRequest) returns (stream ChatMessage);

  // 客户端流 - 批量上传
  rpc UploadMedia(stream MediaChunk) returns (UploadResult);

  // 双向流 - 实时聊天
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);
}
gRPC 流的优势：


    

  • Protobuf 序列化：比 JSON 小 3-10 倍，解析快 5-20 倍
    • 

  • HTTP/2 多路复用：单连接支持多个并发流
    • 

  • 强类型契约：编译时检查消息格式
    • 

  • 流量控制：内置背压机制防止快生产者淹没慢消费者
    • 

  • 截止时间传播：超时自动从客户端传播到整个调用链
    • 



gRPC 流的局限：


    

  • 浏览器不能直接使用，需要 gRPC-Web 代理（如 Envoy）
    • 

  • 调试不如 WebSocket/SSE 直观（二进制协议）
    • 

  • 生态工具相比 WebSocket 仍在追赶
    • 

  • 不适合需要浏览器原生支持的场景
    • 



GraphQL Subscription
GraphQL Subscription 将实时通信能力集成到 GraphQL Schema 中，客户端使用与查询相同的声明式语法订阅数据变更：


subscription OnOrderStatusChanged($orderId: ID!) {
  orderStatusChanged(orderId: $orderId) {
    status
    updatedAt
    estimatedDelivery
  }
}
底层通常基于 WebSocket 实现（GraphQL over WebSocket 协议），但对客户端暴露统一的 GraphQL 体验。


适用场景：已使用 GraphQL 作为数据层的项目中，需要为部分数据添加实时更新能力。避免引入独立的实时通信栈。


局限：大规模 Subscription 的性能管理（每个活跃订阅对应后端的一个事件监听器）需要精心设计。
