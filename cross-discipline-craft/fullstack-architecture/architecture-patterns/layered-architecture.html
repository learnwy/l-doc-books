分层架构与关注点分离

分层架构的核心思想

分层架构（Layered Architecture）是软件工程中最持久的设计范式之一，其核心目标是通过职责分离降低系统复杂度。每一层只关注自身领域的逻辑，通过定义良好的接口与相邻层交互，形成清晰的依赖方向。在全栈系统中，这意味着用户界面的变更不应波及业务规则，数据库的替换不应影响上层服务逻辑。

经典的三层模型将系统划分为：

层次 职责 典型实现
Presentation Layer 用户交互、请求路由、响应渲染 React/Vue 组件、Express 路由
Business Logic Layer 领域规则、工作流编排、数据校验 Service 类、Domain Model
Data Access Layer 数据持久化、查询优化、事务管理 Repository、ORM、SQL Builder

这种分层的核心价值在于可替换性：任何一层的实现变更只要不改变接口契约，就不会影响其他层。2026 年的大型系统中，这一原则依然是架构稳定性的基石。

依赖方向与依赖倒置

传统分层架构中，依赖方向是自上而下的——表现层依赖业务层，业务层依赖数据层。这在简单系统中运作良好，但当业务层需要与外部服务（消息队列、第三方 API、缓存）交互时，直接依赖具体实现会导致业务逻辑与基础设施紧耦合。

依赖倒置原则（Dependency Inversion Principle, DIP）提供了解决方案：高层模块不应依赖低层模块的具体实现，双方都应依赖抽象。

在 TypeScript 全栈项目中，这种模式的实际应用非常普遍：


// 业务层定义接口（抽象）
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
}

// 数据层提供具体实现
class PostgresOrderRepository implements OrderRepository {
  async findById(id: string): Promise<Order | null> {
    return this.prisma.order.findUnique({ where: { id } });
  }
  async save(order: Order): Promise<void> {
    await this.prisma.order.upsert({ where: { id: order.id }, update: order, create: order });
  }
}
这样做的好处在于：业务层可以在不接触真实数据库的情况下进行完整的单元测试，只需注入一个内存实现即可。


六边形架构与端口-适配器模式
Alistair Cockburn 提出的六边形架构（Hexagonal Architecture，又称 Ports & Adapters）是对传统分层架构的重要升级。它将系统视为一个核心领域模型，通过「端口」定义输入输出的抽象契约，通过「适配器」完成与外部世界的具体交互。


六边形架构的核心优势：


    

  • 对称性：入站（driving）和出站（driven）适配器处于同等地位，没有"上下"之分
    • 

  • 可测试性：通过替换适配器即可实现完整的集成测试
    • 

  • 技术无关性：核心领域不依赖任何框架或基础设施细节
    • 



在 2026 年的微服务实践中，六边形架构已成为单个服务内部组织代码的首选模式。每个微服务内部采用端口-适配器结构，对外暴露 gRPC 或 REST 接口作为入站适配器，通过 Repository 端口隔离数据库细节。


清洁架构：融合与演进
Robert C. Martin 的清洁架构（Clean Architecture）将六边形架构、DDD 的洋葱架构等多种思想融合为一套统一的分层原则。其核心规则是依赖规则（The Dependency Rule）：源码依赖只能指向内层，内层不知道外层的存在。


清洁架构在全栈项目中的典型目录结构：


src/
├── domain/           # 企业业务规则 - 纯领域模型，零外部依赖
│   ├── entities/
│   └── value-objects/
├── application/      # 应用业务规则 - Use Case 编排
│   ├── commands/
│   ├── queries/
│   └── ports/        # 接口定义
├── infrastructure/   # 基础设施适配器
│   ├── persistence/
│   ├── messaging/
│   └── external-apis/
└── interfaces/       # 入站接口
    ├── http/
    ├── graphql/
    └── cli/

对于大多数新项目的建议是从简单分层开始，随复杂度增长向六边形架构演进。过早引入复杂分层会增加不必要的间接层，而过晚引入则会导致业务逻辑与框架代码深度耦合、难以测试。


关键的演进信号包括：


    

  • 当你发现业务逻辑散落在 Controller 中时，需要引入独立的 Service/Use Case 层
    • 

  • 当你需要支持多种入站渠道（HTTP + 消息队列 + 定时任务）时，需要显式定义入站端口
    • 

  • 当更换数据库或缓存方案成为痛苦的大规模重构时，需要通过 Repository 接口隔离数据层
    • 



前端分层的演进
传统后端分层思想在前端同样适用。2026 年的大型前端应用通常采用以下分层结构：






层次
职责
典型实现





UI Layer
纯展示组件、样式、动画
React/Vue 组件




Feature Layer
业务逻辑编排、状态管理
Custom Hooks / Composables




Data Layer
API 调用、缓存、乐观更新
TanStack Query / Apollo Client




Core Layer
领域模型、校验规则、工具函数
纯 TypeScript 模块





这种分层的关键价值在于：UI 组件可以独立于数据获取逻辑进行测试和复用，Feature 层可以在不同 UI 框架间迁移（例如从 React 到 React Native），Core 层则完全与框架无关。


在 React Server Components 与 Next.js 15 的 Server Actions 普及后，前后端的分层边界进一步模糊——服务端组件直接在 Server 执行数据获取，消除了传统的 API 中间层。但分层思想的核心原则——关注点分离与依赖方向控制——依然是保持代码可维护性的基石。
