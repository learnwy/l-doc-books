全栈可观测性设计

可观测性的三支柱

可观测性（Observability）不同于传统监控（Monitoring）——监控回答"系统是否正常"，可观测性回答"系统为什么异常"。在分布式全栈系统中，一个用户请求可能跨越前端渲染、API Gateway、BFF 层、3-5 个微服务和 2-3 个数据存储。没有完整的可观测性体系，排障就像在黑暗中摸索。

可观测性三支柱的协同关系：

典型排障流程：Metrics 告警发现错误率上升 → Traces 定位到是 Payment Service 的延迟飙升 → Logs 确认是第三方支付网关超时。


OpenTelemetry 统一采集框架
OpenTelemetry（OTel）已在 2026 年成为可观测性数据采集的事实标准。它提供统一的 SDK 和 API，将 Metrics、Logs、Traces 三种信号通过标准化协议（OTLP）发送到任意后端（Datadog、Grafana、New Relic、自建系统）。


架构概览：


Node.js 服务接入示例：


import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { OTLPMetricExporter } from '@opentelemetry/exporter-metrics-otlp-http';

const sdk = new NodeSDK({
  serviceName: 'order-bff',
  traceExporter: new OTLPTraceExporter({
    url: 'http://otel-collector:4318/v1/traces',
  }),
  metricReader: new PeriodicExportingMetricReader({
    exporter: new OTLPMetricExporter({
      url: 'http://otel-collector:4318/v1/metrics',
    }),
  }),
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();
自动插桩覆盖 HTTP、gRPC、数据库客户端、消息队列等常见库，无需手动在每个调用点添加追踪代码。

前端 Trace 串联：关键是将前端发起的请求与后端链路追踪关联。通过在 HTTP 请求头中注入 Trace Context（W3C Trace Context 标准），实现端到端的链路可见：


// 前端 Fetch 拦截 - 注入 Trace Context
const originalFetch = window.fetch;
window.fetch = async (url, options = {}) => {
  const span = tracer.startSpan(`HTTP ${options.method || 'GET'} ${url}`);
  const headers = new Headers(options.headers);

  // 注入 W3C Trace Context
  propagator.inject(context.active(), headers, {
    set: (carrier, key, value) => carrier.set(key, value),
  });

  try {
    const response = await originalFetch(url, { ...options, headers });
    span.setStatus({ code: response.ok ? SpanStatusCode.OK : SpanStatusCode.ERROR });
    return response;
  } catch (error) {
    span.recordException(error);
    throw error;
  } finally {
    span.end();
  }
};
分布式链路追踪
在微服务架构中，链路追踪是定位性能瓶颈和故障传播路径的核心工具。


Trace 的数据结构：


Trace (全局唯一 ID)
└── Span: API Gateway (12ms)
    ├── Span: Auth Middleware (2ms)
    └── Span: BFF Service (10ms)
        ├── Span: User Service Call (3ms)
        │   └── Span: PostgreSQL Query (1ms)
        ├── Span: Order Service Call (5ms)
        │   ├── Span: Redis Cache Lookup (0.5ms)
        │   └── Span: MongoDB Query (3ms)
        └── Span: Response Serialization (1ms)

告警设计原则
好的告警系统遵循"尽早发现、精准通知、快速定位"原则：


SLO 驱动告警：不监控每个中间指标，而是围绕 Service Level Objective 设置告警：


# SLO 定义示例
slos:
  - name: order-api-availability
    target: 99.9% # 每月允许 43 分钟不可用
    indicator:
      type: availability
      good_events: "http_requests_total{status!~'5..'}"
      total_events: 'http_requests_total'
    alerts:
      - burn_rate: 14.4x # 1小时窗口，1小时耗尽月度预算
        severity: critical
        notify: [pagerduty, slack-oncall]
      - burn_rate: 6x # 6小时窗口
        severity: warning
        notify: [slack-alerts]
告警金字塔：


告警应从上到下触发：先告知"有业务影响"，再引导定位原因。避免让 On-call 工程师淹没在大量底层告警中。


可观测性成熟度模型




等级
能力
关键标志





L1 基础
基本日志 + 基础指标
能发现"系统挂了"




L2 结构化
结构化日志 + APM + 基础告警
能定位"哪个服务挂了"




L3 关联
分布式追踪 + 日志关联 + SLO 告警
能回答"为什么挂了"




L4 预测
异常检测 + 容量预测 + 变更关联
能预防"即将出问题"




L5 自愈
AI 辅助根因分析 + 自动修复
系统自行恢复





2026 年大多数组织处于 L2-L3 之间。L4/L5 需要大量历史数据积累和 AIOps 平台支持，是长期投入方向。

全栈可观测性的终极目标是：当任何环节出现问题时，On-call 工程师能在 5 分钟内定位到根因服务和具体错误，而不是花费 30 分钟在多个工具间切换、猜测问题所在。
