数据库拆分与数据迁移

数据层解耦的核心挑战

在微服务迁移中，代码拆分相对直接——重新组织模块边界、定义 API 接口、部署独立服务。但数据库拆分是真正的深水区。当多个服务共享同一个数据库时，表面上的服务独立部署毫无意义——一次 Schema 变更仍然需要协调所有相关服务，一个慢查询仍然会拖垮所有服务的性能。

共享数据库模式（Shared Database）是"分布式单体"的核心症状：

微服务架构中，这些能力都不再免费获得——需要在应用层重新实现。


渐进式数据拆分路径
数据库拆分不应一步到位，而应遵循渐进式路径：


Phase 1：Schema 逻辑隔离
在同一个数据库实例中，按限界上下文划分 Schema 或表前缀。通过代码规范和 Review 机制强制执行访问规则——服务只能访问自己 Schema 下的表。


-- 逻辑隔离：同一数据库，不同 Schema
CREATE SCHEMA orders;
CREATE SCHEMA users;
CREATE SCHEMA inventory;

-- Order Service 只访问 orders Schema
CREATE TABLE orders.orders (...);
CREATE TABLE orders.order_items (...);

-- User Service 只访问 users Schema
CREATE TABLE users.users (...);
CREATE TABLE users.addresses (...);
优势：零迁移风险，通过静态分析工具检测跨 Schema 访问。


局限：仍然共享数据库连接池和 I/O 资源，无法独立扩缩。


Phase 2：读写分离与 API 化
为每个限界上下文创建数据访问 API，其他服务不再直接查询其数据表，而是通过 API 获取数据：


Phase 3：物理数据库分离
当逻辑隔离和 API 化完成后，物理分离变成低风险操作——只需将表迁移到独立的数据库实例，更新连接字符串。


数据同步策略
物理分离后，跨服务的数据需求通过以下策略满足：


Change Data Capture（CDC）
CDC 通过监听数据库的变更日志（WAL/Binlog），将数据变更实时传播到其他服务。它不侵入业务代码，也不增加写入延迟。

双写（Dual Write）
在迁移过渡期，应用同时写入新旧两个数据库：


async function createOrder(order: Order) {
  // 写入旧数据库（主）
  await legacyDb.orders.insert(order);

  // 写入新数据库（副）
  try {
    await newOrderDb.orders.insert(transformOrder(order));
  } catch (err) {
    // 记录不一致，不阻塞主流程
    await inconsistencyLog.record({
      entity: 'order',
      id: order.id,
      error: err.message,
    });
  }
}
双写的陷阱：


    

  • 两次写入不在同一事务中，可能出现部分成功
    • 

  • 并发场景下顺序可能不一致
    • 

  • 长期双写消耗双倍写入资源
    • 



双写的安全实践：


    

  1. 设定明确的双写期限（通常 2-4 周）
    2. 

  2. 定期运行一致性校验（Reconciliation Job）
    3. 

  3. 通过 Feature Flag 控制新数据库何时成为"主"
    4. 

  4. 双写期间只读新库用于验证，不将新库数据暴露给用户

事件溯源（Event Sourcing）
对于需要完整历史记录的领域，事件溯源提供了一种天然支持数据迁移的架构：


事件溯源将"真相"存储为不可变的事件流，多个消费者可以从同一事件流构建不同的物化视图。数据库迁移时，只需重放事件到新的数据存储即可。


Saga 模式：跨服务事务
数据库拆分后，跨服务的事务一致性通过 Saga 模式实现。Saga 将一个全局事务分解为一系列本地事务，每个本地事务完成后发布事件触发下一步，失败时执行补偿操作。

跨服务查询的解决方案
数据库拆分后，原本的 SQL JOIN 不再可用。以下是替代方案：


API 组合（API Composition）：BFF 或 API Gateway 调用多个服务的查询接口，在应用层组合结果。


CQRS + 物化视图：为查询需求创建专门的读模型，通过 CDC 或事件同步数据：


数据网格（Data Mesh）：每个领域团队除了提供操作 API 外，还负责发布其数据产品——标准化的、可供其他团队消费的数据集。


数据迁移的验证体系
迁移正确性验证是整个流程中最不可省略的环节：


// 一致性校验 Job - 定期对比新旧数据源
async function reconciliationJob() {
  const legacyOrders = await legacyDb.query('SELECT * FROM orders WHERE updated_at > ?', [lastCheckpoint]);
  const newOrders = await newOrderDb.query('SELECT * FROM orders WHERE updated_at > ?', [lastCheckpoint]);

  const discrepancies = findDiscrepancies(legacyOrders, newOrders);

  if (discrepancies.length > 0) {
    await alerting.send({
      severity: discrepancies.length > 100 ? 'critical' : 'warning',
      message: `Data reconciliation found ${discrepancies.length} discrepancies`,
      details: discrepancies.slice(0, 10),
    });
  }

  metrics.gauge('reconciliation.discrepancy_count', discrepancies.length);
}
验证维度：


    

  • 行数对比：新旧数据源的记录总数是否匹配
    • 

  • 内容校验：采样对比具体记录的字段值
    • 

  • 时序一致：事件顺序是否正确
    • 

  • 业务指标：核心业务指标（GMV、转化率）在迁移前后是否一致
    •
