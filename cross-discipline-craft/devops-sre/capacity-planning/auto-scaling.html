自动伸缩

为什么需要自动伸缩

在传统模式下，容量规划依赖人工预判和手动调整。但云原生环境的流量波动更加频繁和剧烈——日常业务有明显的峰谷周期，营销活动可能带来数倍的流量突增。自动伸缩（Auto Scaling）让系统能够根据实时负载动态调整资源，实现"按需使用、按需付费"。



Kubernetes 自动伸缩体系


HPA（水平 Pod 自动伸缩）
工作原理
HPA 通过监控 Pod 的指标（CPU、内存或自定义指标），自动调整 Deployment 的副本数：


计算公式
期望副本数 = ceil(当前副本数 × (当前指标值 / 目标指标值))
例如：当前 3 个 Pod，平均 CPU 利用率 80%，目标 50%：


期望副本数 = ceil(3 × (80/50)) = ceil(4.8) = 5
HPA 配置
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 75
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: '1000'
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Pods
          value: 4
          periodSeconds: 60
        - type: Percent
          value: 100
          periodSeconds: 60
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60

VPA（垂直 Pod 自动伸缩）
VPA 自动调整 Pod 的 CPU 和内存的 requests/limits，而不是调整副本数：


apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-app-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  updatePolicy:
    updateMode: 'Auto'
  resourcePolicy:
    containerPolicies:
      - containerName: app
        minAllowed:
          cpu: 100m
          memory: 128Mi
        maxAllowed:
          cpu: 2000m
          memory: 4Gi

KEDA（事件驱动自动伸缩）
KEDA 扩展了 K8s 的自动伸缩能力，支持基于外部事件源（消息队列、数据库、HTTP 请求等）进行伸缩：


apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-processor
spec:
  scaleTargetRef:
    name: order-processor
  pollingInterval: 15
  cooldownPeriod: 300
  minReplicaCount: 1
  maxReplicaCount: 50
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka:9092
        consumerGroup: order-group
        topic: orders
        lagThreshold: '100'
    - type: prometheus
      metadata:
        serverAddress: http://prometheus:9090
        metricName: order_processing_queue_size
        threshold: '50'
        query: |
          sum(order_processing_queue_size)

kind: ScaledObject

  name: web-app-scheduled
spec:
  scaleTargetRef:
    name: web-app

    - type: cron
      metadata:
        timezone: Asia/Shanghai

伸缩速率控制
核心原则：扩容要快，缩容要慢。扩容不及时会导致服务降级，缩容过快会导致流量反弹时再次不足。




自动伸缩的常见问题




问题
说明
解决方案





伸缩震荡
频繁扩容缩容
增加稳定窗口时间




冷启动延迟
新 Pod 启动慢影响响应时间
预热池、优化启动时间

指标采集有延迟导致伸缩滞后

数据库瓶颈
应用扩容后数据库成为瓶颈
数据库连接池管理、读写分离







小结
自动伸缩是云原生环境中平衡性能和成本的核心机制。HPA 适合无状态服务的水平扩展，VPA 适合有状态服务的垂直调整，KEDA 适合事件驱动场景。伸缩策略的核心原则是"扩容要快、缩容要慢"。通过合理的预热、冷却和稳定窗口配置，可以避免伸缩震荡。自动伸缩不是万能的——它需要配合良好的应用设计（快速启动、无状态）和基础设施支撑（Cluster Autoscaler）才能发挥最大效果。
