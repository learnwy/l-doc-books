分布式追踪

为什么需要分布式追踪

在单体应用中，一个请求的完整执行路径可以通过本地堆栈和日志轻松追踪。但在微服务架构下，一个用户请求可能经过数十个服务的协作处理，跨越多个进程、容器甚至数据中心。当出现延迟异常或错误时，仅靠单个服务的日志和指标无法定位问题发生在哪个环节。

分布式追踪通过为每个请求分配全局唯一的 Trace ID，并在服务间传播上下文信息，将一个请求的完整调用链路串联起来。

OpenTelemetry
什么是 OpenTelemetry
OpenTelemetry（简称 OTel）是 CNCF 的可观测性标准项目，统一了分布式追踪、指标和日志的采集和传输协议。它合并了之前的 OpenTracing 和 OpenCensus 两个项目，是当前可观测性领域的事实标准。

Collector 配置示例
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 5s
    send_batch_size: 1024
  filter:
    spans:
      exclude:
        match_type: strict
        attributes:
          - key: http.target
            value: /healthz

exporters:
  jaeger:
    endpoint: jaeger-collector:14250
    tls:
      insecure: true
  prometheus:
    endpoint: 0.0.0.0:8889

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch, filter]
      exporters: [jaeger]
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [prometheus]

选型建议


采样策略
全量采集所有请求的追踪数据在高流量系统中不可行。采样策略决定了哪些请求的追踪数据会被保留。


采样类型




类型
说明
优点
缺点





头部采样
请求入口时决定是否采样
实现简单、低开销
可能遗漏异常请求




尾部采样
请求完成后根据结果决定
保证异常请求被采集
需要缓存完整 Trace、实现复杂




自适应采样
根据流量和错误率动态调整
兼顾效率和覆盖率
需要后端支持





采样策略配置
processors:
  tail_sampling:
    decision_wait: 10s
    num_traces: 100000
    policies:
      - name: errors-policy
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow-traces
        type: latency
        latency: { threshold_ms: 1000 }
      - name: probabilistic-policy
        type: probabilistic
        probabilistic: { sampling_percentage: 10 }
上述配置的含义：


    

  • 所有错误请求 100% 采集
    • 

  • 延迟超过 1 秒的请求 100% 采集
    • 

  • 其余请求按 10% 比率采样
    • 





链路分析实战
瀑布图分析
瀑布图（Waterfall View）是分析 Trace 最常用的视图。它以时间轴为横轴，以服务调用层级为纵轴，直观展示每个 Span 的耗时和层级关系：


Trace: abc123 (总耗时 850ms)
├── API Gateway (50ms)
│   ├── Auth Service (20ms)
│   └── Order Service (780ms)
│       ├── Inventory Check (100ms)
│       ├── Price Calculation (30ms)
│       └── Payment Service (600ms)  ← 瓶颈
│           ├── Risk Check (50ms)
│           └── Bank API Call (520ms) ← 根因
└── Response Serialization (20ms)

追踪与日志、指标的关联
Exemplar：指标到追踪的桥梁
Exemplar 是 Prometheus 2.26+ 引入的特性，允许在指标数据点上附加 Trace ID，实现从指标异常点直接跳转到对应的追踪数据：


这种关联能力让排障流程从"指标发现异常 → 手动搜索日志"变为"指标发现异常 → 一键跳转到追踪 → 一键查看关联日志"，排障效率可提升数倍。


统一可观测性平台
Grafana 生态的 Prometheus + Loki + Tempo 组合是目前最流行的统一可观测性平台方案。三者共享 Grafana 作为查询和可视化前端，通过 Trace ID 实现跨数据源的无缝跳转。




小结
分布式追踪是微服务架构中不可或缺的可观测性能力。OpenTelemetry 已经成为采集标准，选择 Jaeger 或 Tempo 作为后端取决于团队的查询需求和成本偏好。合理的采样策略是平衡数据完整性和系统开销的关键。追踪数据的最大价值不仅在于单次排障，更在于通过链路分析持续发现架构中的性能瓶颈和设计缺陷。
