日志最佳实践

为什么日志是可观测性的基础

日志是系统可观测性三大支柱中最古老也最直观的一种。每一条日志都是系统在某个时刻发生的离散事件的记录，包含了时间戳、事件描述和相关上下文信息。与指标（聚合数值）和追踪（调用链路）不同，日志提供的是最细粒度的事件详情，是排查问题时的"最后一公里"。

在可观测性体系中，日志、指标和追踪三者相互补充：

一个典型的排障流程是：指标告警发现系统异常 → 追踪定位到具体服务和请求 → 日志提供该请求的详细执行上下文。三者协同工作，才能实现高效的故障诊断。




结构化日志
从非结构化到结构化
传统日志是纯文本字符串，虽然人类可读，但机器难以解析和检索：


2024-03-15 10:23:45 ERROR Failed to process order #12345 for user john_doe
结构化日志将每条记录表示为键值对或 JSON 对象，每个字段都可独立检索：


{
  "timestamp": "2024-03-15T10:23:45.123Z",
  "level": "ERROR",
  "service": "order-service",
  "trace_id": "abc123def456",
  "user_id": "john_doe",
  "order_id": "12345",
  "message": "Failed to process order",
  "error": "PaymentGatewayTimeout",
  "duration_ms": 30000
}

结构化日志的优势
结构化日志在大规模系统中具有决定性优势：


    

  • 可检索性：可按任意字段组合查询，如"过去 1 小时内 order-service 的所有 ERROR 级别日志"
    • 

  • 可聚合性：可对数值字段进行统计分析，如"各服务的平均响应时间"
    • 

  • 可关联性：通过 trace_id 将日志与追踪系统关联
    • 

  • 可解析性：日志采集器无需复杂的正则表达式就能解析字段
    • 





日志级别
合理使用日志级别是控制日志质量和数量的关键。过多的日志会增加存储成本和降低信噪比，过少的日志则在排障时缺乏必要信息。

日志级别使用原则
黄金法则：


    

  • ERROR 日志必须包含足够的上下文信息，让工程师无需查看其他日志就能理解问题
    • 

  • WARN 日志表示"现在没事但可能很快就有事"
    • 

  • INFO 日志记录业务流程的关键里程碑，不是每个函数调用
    • 

  • 避免在循环体内写 INFO 及以上级别的日志
    •

日志实践规范
日志输出位置
在容器化环境中，应用应将日志输出到标准输出（stdout/stderr），由容器运行时和日志采集器统一处理：


# 查看 Pod 日志
kubectl logs -f <pod-name> --tail=100

# 查看前一个容器实例的日志（用于排查 CrashLoopBackOff）
kubectl logs <pod-name> --previous
日志采样策略
高流量系统中，全量日志采集可能带来巨大的存储和网络开销。常用的采样策略：

敏感信息脱敏
日志中不得包含以下敏感信息：


    

  • 用户密码和认证令牌
    • 

  • 信用卡号和银行账号
    • 

  • 身份证号和手机号（需脱敏处理）
    • 

  • API 密钥和私钥
    • 



脱敏处理示例：


{
  "user_id": "john_doe",
  "phone": "138****5678",
  "card_number": "****-****-****-1234",
  "message": "Payment processed successfully"
}

小结
结构化日志是现代可观测性体系的基础设施。选择合适的日志方案（ELK 或 Loki）、建立统一的日志规范（级别使用、字段定义、脱敏处理）、实现日志与追踪的关联，这三步构成了日志最佳实践的核心。记住日志的终极目标不是"记录一切"，而是"在需要时能快速找到有价值的信息"。
