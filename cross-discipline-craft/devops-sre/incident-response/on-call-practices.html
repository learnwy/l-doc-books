On-Call 实践

什么是 On-Call

On-Call 是一种轮值待命机制，确保在任何时间都有指定的工程师负责响应生产系统的告警和事故。On-Call 工程师是系统可靠性的第一道防线——当告警触发时，他们需要在规定时间内响应、诊断并处理问题。

On-Call Runbook
什么是 Runbook
Runbook 是一份标准化的操作手册，指导 On-Call 工程师在收到特定告警时应该执行的具体步骤。好的 Runbook 应该让任何值班人员（即使不熟悉该服务）都能有效响应。


Runbook 模板
## 告警: HighErrorRate - 服务错误率超过 1%

### 影响

- 用户可能遇到请求失败
- 影响范围: 订单服务的所有端点

### 检查步骤

1. 打开 Grafana 仪表盘: [链接]
2. 确认错误率趋势（是突增还是渐增）
3. 检查最近是否有部署: `kubectl rollout history deployment/order-service`
4. 查看错误日志: `kubectl logs -l app=order-service --tail=100 | grep ERROR`
5. 检查下游依赖状态: [依赖状态页面链接]

### 常见原因和处理

| 原因             | 判断方式                    | 处理                                                             |
| ---------------- | --------------------------- | ---------------------------------------------------------------- |
| 最近部署引入 Bug | 错误时间与部署时间吻合      | 回滚: `kubectl rollout undo deployment/order-service`            |
| 数据库连接池耗尽 | 日志中有 connection refused | 重启 Pod: `kubectl rollout restart deployment/order-service`     |
| 下游服务故障     | 错误集中在特定外部调用      | 启用降级开关: [降级开关操作链接]                                 |
| 流量突增超过容量 | QPS 指标显著高于正常值      | 手动扩容: `kubectl scale deployment/order-service --replicas=10` |

### 升级条件

- 5 分钟内无法定位原因 → 升级至 Secondary On-Call
- 15 分钟内无法恢复 → 启动事故响应流程
- 影响超过 50% 用户 → 直接升级至团队 Lead

小结
On-Call 是 SRE 团队保障系统可靠性的核心机制。合理的排班设计（≥5 人团队、≤1/4 时间值班）、清晰的升级策略、完善的工具链和高质量的 Runbook 是成功 On-Call 实践的四个支柱。持续衡量和改善 On-Call 质量指标，降低告警噪声，增加自动化修复能力，是让 On-Call 可持续运转的关键。
