事后复盘文化

什么是 Blameless Postmortem

事后复盘（Postmortem）是在事故恢复后进行的结构化回顾，目的是理解事故的根因、评估响应过程、并制定防止复发的行动计划。Blameless（无指责）是复盘文化的核心原则——它关注系统和流程的改进，而不是追究个人的过失。

为什么 Blameless 很重要

真正的系统改进





Blameless 不等于 Accountless。我们不追究"谁犯了错"，但我们追究"系统为什么允许这个错误发生"以及"如何改进系统防止再犯"。

5-Whys 根因分析
5-Whys 是一种通过连续追问"为什么"来挖掘根本原因的分析方法。目标是超越表面症状，找到系统性的改进机会。


示例
5-Whys 的注意事项




原则
说明





关注系统而非个人
"为什么系统允许这种错误发生"而非"谁犯了错"




可能有多条根因链
一个事故通常有多个贡献因素




不一定正好 5 个 Why
有时 3 个就够，有时需要 7 个




每个 Why 都基于事实
不要猜测，用证据说话




根因应该指向可改进的系统
"工程师犯了错"不是有效的根因

复盘文档模板
# 事故复盘: [事故标题]

## 元信息

- **事故编号**: INC-2024-042
- **事故等级**: P1
- **影响时间**: 2024-03-15 10:00 ~ 10:40 (40 分钟)
- **影响范围**: 约 30% 用户的订单功能
- **事故指挥官**: @张工
- **复盘负责人**: @李工
- **复盘日期**: 2024-03-17

## 摘要

2024年3月15日10:00，订单服务 v2.3.1 部署后错误率从 0.1% 飙升至 15%，影响约 30% 用户无法正常下单。10:25 回滚至 v2.3.0 后恢复正常。根因是支付回调处理函数中的空指针异常。

## 影响

- **用户影响**: 约 30% 用户下单失败
- **业务影响**: 预估丢失订单约 500 笔
- **SLO 影响**: 可用性 SLI 从 99.95% 降至 99.7%，消耗 35% 错误预算

## 时间线

| 时间  | 事件                             |
| ----- | -------------------------------- |
| 09:45 | v2.3.1 通过 CI/CD 部署到生产环境 |
| 10:00 | Prometheus 告警: 错误率超过 1%   |
| 10:02 | On-Call @张工确认告警            |
| 10:05 | @张工声明为 IC                   |
| 10:15 | 定位到 v2.3.1 部署引入的问题     |
| 10:20 | 决定回滚                         |
| 10:25 | 回滚完成                         |
| 10:35 | 错误率恢复正常                   |
| 10:40 | IC 宣布事故关闭                  |

## 根因分析

### 直接原因

支付回调处理函数在 v2.3.1 中被重构，新代码未处理支付网关返回空 callback_id 的边界情况，导致空指针异常。

### 5-Whys

1. 为什么错误率飙升? → v2.3.1 引入了空指针 Bug
2. 为什么代码审查未发现? → 审查者不了解支付网关的边界行为
3. 为什么测试未覆盖? → 缺少支付回调的边界测试用例
4. 为什么灰度发布未拦截? → 灰度比例 5% 且观察时间仅 5 分钟
5. 为什么 5 分钟观察不够? → 告警阈值需要 5 分钟才能触发

### 贡献因素

- 支付网关的空 callback_id 行为未记录在接口文档中
- 灰度发布观察时间过短

## 做得好的地方

- On-Call 响应迅速（2 分钟确认）
- IC 快速做出回滚决策
- 回滚流程顺畅

## 需要改进的地方

- 缺少支付回调的集成测试
- 灰度发布观察时间不足
- 支付网关接口文档不完整

小结
事后复盘是将事故从"坏事"转化为"学习机会"的关键机制。Blameless 文化是复盘有效性的前提——只有在安全的环境中，团队成员才会坦诚分享事故的完整细节。5-Whys 帮助我们超越表面症状找到系统性根因。行动项的跟踪和闭环是复盘价值的最终体现——没有行动的复盘只是纸上谈兵。建立复盘知识库和定期分析事故趋势，是推动组织级可靠性持续改进的长期策略。
