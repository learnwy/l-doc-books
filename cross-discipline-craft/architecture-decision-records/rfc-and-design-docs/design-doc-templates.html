设计文档模板与写作方法

概述

设计文档（Design Document）是比 RFC 更详细的技术方案描述文档。如果说 RFC 回答的是「我们应该做什么以及为什么」，设计文档回答的是「我们具体怎么做」。Google、Uber、Stripe 等公司都有着成熟的设计文档文化——在 Google，一个经验法则是「如果项目需要超过一个工程师一周的工作量，就写设计文档」。本文对比业界主流的设计文档模板，讲解写作方法，帮助读者掌握在有限篇幅内清晰传达复杂技术方案的技巧。

核心概念

设计文档与 RFC/ADR 的区别

三者的关系是递进的：


    

  • ADR 捕获单个决策的背景和结果
    • 

  • RFC 提出一个方向并寻求共识
    • 

  • Design Doc 在方向确定后详细描述实现方案
    • 



一个典型的技术项目流程：先写 RFC 确定方向 → RFC 被接受后写 Design Doc 描述方案 → 实施过程中的关键决策用 ADR 记录。


Google 风格设计文档结构
Google 的设计文档是业界标杆。其核心结构由 Riona MacNamara 在多次技术写作演讲中公开分享：


# [项目名称] Design Document

## Metadata

- Author(s): [姓名]
- Reviewers: [评审人列表]
- Status: Draft / In Review / Approved / Implemented
- Last Updated: [日期]

## Context and Scope

[这个文档覆盖什么？不覆盖什么？ 系统的哪个部分受影响？]

## Goals and Non-Goals

### Goals

- [明确的目标 1]
- [明确的目标 2]

### Non-Goals

- [明确不在范围内的事项 1]
- [明确不在范围内的事项 2]

## The Actual Design

### System-context Diagram

[展示系统边界和外部依赖的图表]

### APIs

[公共 API 的定义]

### Data Storage

[数据模型、存储方案]

### Code and Pseudo-code

[关键算法或复杂逻辑的伪代码]

### Degree of Constraint

[方案在多大程度上受限于现有架构]

## Alternatives Considered

[详细描述被否决的方案及原因]

## Cross-cutting Concerns

- Security considerations
- Privacy implications
- Performance requirements

## Timeline and Milestones

[实施阶段划分和时间估算]
Uber 风格设计文档
Uber 的设计文档更强调「影响面分析」和「回滚策略」：


# Design Doc: [功能名称]

## Problem Statement

[要解决的核心问题，2-3 句话]

## Background

[必要的背景知识，让不熟悉该领域的人也能理解]

## Proposed Solution

[详细的技术方案]

## Impact Analysis

- **Affected Services:** [列出受影响的服务]
- **Traffic Impact:** [预期的流量变化]
- **Data Migration:** [是否需要数据迁移]
- **Rollback Plan:** [出问题时如何回滚]

## Metrics and Monitoring

- [成功指标 1 及目标值]
- [成功指标 2 及目标值]
- [需要新增的监控告警]

## Testing Strategy

- Unit tests for [关键模块]
- Integration tests for [关键路径]
- Load test targeting [性能指标]
- Shadow/canary deployment plan

## Open Questions and Risks

[未解决的问题和已知风险]

Goals 和 Non-Goals 的写作技巧
Goals 和 Non-Goals 是设计文档中最重要却最常被写烂的部分。好的 Goals 应该是具体的、可衡量的、有约束的：


## 错误的写法

### Goals

- 提高系统性能
- 改善用户体验
- 增强系统可靠性

### Non-Goals

- 不重构所有代码

## 正确的写法

### Goals

- 将订单创建 API 的 P99 延迟从 800ms 降至 200ms 以内
- 支持每秒 5,000 笔并发订单创建（当前峰值的 3 倍）
- 保证订单数据在主库和副本间的复制延迟 < 100ms

### Non-Goals

- 优化订单查询 API 的性能（将在 Q3 作为独立项目处理）
- 修改前端订单创建流程的 UI（前端团队自行规划）
- 支持跨区域多活部署（当前单区域已满足 SLA）
关键技巧：Non-Goals 不是「不重要的事」，而是「重要但不在这次做的事」。Non-Goals 帮助界定范围边界，防止设计蔓延。


Alternatives Considered 的分析框架
这是设计文档中最体现工程判断力的部分。一个好的替代方案分析应该：


## Alternatives Considered

### Option A: 使用 Redis Sorted Set 实现排行榜

**描述：** 利用 Redis ZADD/ZRANGE 命令直接实现实时排名计算。

**优势：**

- 实现简单，团队对 Redis 熟悉
- 读写性能极高（单节点 10 万+ QPS）
- 天然支持按分数排序

**劣势：**

- 数据完全在内存中，成本随用户量线性增长
- Redis 集群的 Sorted Set 不支持跨 slot 操作
- 缺乏持久化保证（AOF 有性能开销）

**工作量估算：** 2 周

**为什么不选择：** 当用户量超过 1000 万时，内存成本将超出预算。且数据丢失风险不可接受。

---

### Option B: 使用 ClickHouse 做离线计算（推荐）

**描述：** 用 ClickHouse 的物化视图做准实时排名聚合，T+5min 更新排行榜。

**优势：**

- 存储成本低（列式压缩）
- 支持复杂的排名逻辑（多维度、时间窗口）
- 数据持久化，有完整审计记录

**劣势：**

- 非严格实时（5 分钟延迟）
- ClickHouse 运维复杂度较高
- 团队需要学习 ClickHouse

**工作量估算：** 4 周

**为什么选择：** 5 分钟延迟对排行榜场景可接受，存储成本可控，且为后续复杂排名需求留有空间。
设计文档的评审清单
作为评审人，检查设计文档时应关注：


## Design Doc Review Checklist

### 完整性

- [ ] Goals 和 Non-Goals 是否清晰且可衡量？
- [ ] 是否包含系统上下文图？
- [ ] 是否描述了 API 接口（如适用）？
- [ ] 是否分析了至少 2 个替代方案？
- [ ] 是否考虑了安全性影响？
- [ ] 是否有回滚方案？

### 技术合理性

- [ ] 方案是否考虑了失败场景？
- [ ] 性能估算是否有数据支撑（benchmark/计算）？
- [ ] 数据模型是否满足未来 12 个月的扩展需求？
- [ ] 依赖的外部服务是否有降级方案？

### 可执行性

- [ ] 工作量估算是否合理？
- [ ] 是否有明确的里程碑划分？
- [ ] 是否识别了需要其他团队支持的部分？
- [ ] 测试策略是否覆盖关键路径？

### 文档质量

- [ ] 非该领域专家能否理解？
- [ ] 是否过长（>15 页可能需要拆分）？
- [ ] 图表是否有说明文字？
- [ ] 是否有悬而未决的问题被标注为 Open Question？

设计文档的长度控制
控制篇幅的技巧：


    

  • 详细的 API 定义移到 API Spec 文件中，Design Doc 只放概要
    • 

  • 数据库 Schema 详情移到附录
    • 

  • 性能测试数据用链接引用，不嵌入正文
    • 

  • 会议讨论记录作为单独的 Meeting Notes 链接
    • 



从设计文档到 ADR 的转化
设计文档中的关键决策应被提取为独立的 ADR：


## 设计文档中的决策标注

在设计文档中，用特殊标记标注需要被提取为 ADR 的决策：

> **📌 Decision Point:** 选择 ClickHouse 而非 Redis 作为排行榜数据存储。详见 ADR-023。

这样做的好处：

1. 设计文档可以详细展开论证过程
2. ADR 保持精简，只记录最终决策和核心原因
3. 两者互相引用，读者可以按需深入

AI 辅助设计文档写作
2026 年的新趋势是使用 AI 辅助设计文档的创建：


## AI 辅助工作流

1. **结构生成**：向 AI 提供项目需求，生成 Design Doc 骨架
2. **替代方案分析**：让 AI 列出可能的技术选项及优劣势
3. **风险识别**：基于方案描述，AI 识别潜在风险
4. **评审辅助**：AI 预审文档完整性，标注遗漏的部分

⚠️ 注意事项：

- AI 生成的内容需要人工验证准确性
- 业务约束和组织上下文必须由人提供
- 最终决策和权衡判断是人的责任
- AI 适合辅助结构化思考，不适合替代深度技术分析
总结
设计文档的核心目的是「在实现之前发现问题」。一份好的设计文档不是项目的负担，而是降低重构风险的投资。关键是把握好详细度——足够详细以支撑有意义的评审，又不至于变成实现说明书。记住 Google 的经验法则：设计文档应该在两周内从 Draft 到 Approved，如果需要更长时间，说明范围太大应该拆分。
