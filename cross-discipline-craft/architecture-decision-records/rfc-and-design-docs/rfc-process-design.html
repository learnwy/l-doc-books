RFC 流程设计与落地

概述

RFC（Request for Comments）是一种源自互联网工程任务组（IETF）的技术提案机制，经过数十年的演进，已被 Google、Meta、Uber、Stripe 等世界顶级工程组织广泛采用。在软件工程语境中，RFC 是一份结构化文档，它在代码编写之前提出技术方案、征求团队反馈、建立共识。与 ADR 聚焦于「记录已做出的决策」不同，RFC 的核心目的是「在决策做出之前促成高质量的讨论」。本文详解如何在团队中从零开始建立有效的 RFC 流程，以及如何避免 RFC 沦为形式主义。

核心概念

RFC 与 ADR 的关系

RFC 和 ADR 是互补的，而非替代关系：

维度 RFC ADR
时间点 决策前（提案阶段） 决策后（记录阶段）
目的 征求意见、建立共识 记录决策、保存上下文
篇幅 1-5 页 0.5-2 页
生命周期 Draft → Review → Accepted/Rejected Proposed → Accepted → Superseded
参与者 作者 + 指定评审人 决策参与者
产出 技术方案 + 实施计划 决策记录

典型流程：RFC 讨论 → 团队决策 → ADR 记录决策 → 实施方案

## 需要 RFC 的场景

✅ 定义新的子系统或服务 ✅ 制定公共 API 契约（会被其他团队消费）✅ 选择影响多个团队的技术栈 ✅ 涉及重大的架构模式变更（如从单体到微服务）✅ 引入新的跨切面关注点（如新的认证机制）✅ 超过 2 周工作量的技术投入 ✅ 团队内部对方案存在明显分歧

## 不需要 RFC 的场景

❌ 实现细节不影响对外契约 ❌ 内部性能优化（对其他模块透明）❌ Bug 修复方案 ❌ 临时的解决方案或实验 ❌ 单人可独立完成的小型重构
One-Page RFC 格式
传统 RFC 的最大问题是篇幅过长导致无人阅读。ScaledByDesign 在 2026 年提出了「One-Page RFC」理念：如果你的 RFC 超过两页，大多数人不会读完它。


# RFC: [标题]

**Author:** [姓名] | **Date:** [日期] | **Status:** Draft **Reviewers:** [2-4 个具体评审人] **Decision needed by:** [截止日期]

## Context（3-5 句话）

要解决什么问题？为什么是现在？业务影响是什么？

## Proposal（1 段 + 1 张图）

要构建什么？包含一张架构图。

## Alternatives Considered

| 方案           | 优势 | 劣势 | 工作量 |
| -------------- | ---- | ---- | ------ |
| 方案 A（推荐） | ...  | ...  | 4 周   |
| 方案 B         | ...  | ...  | 6 周   |
| 方案 C（不做） | ...  | ...  | 0      |

## Key Decisions

1. [具体决策点] — 推荐：[选择]。原因：[理由]
2. [具体决策点] — 推荐：[选择]。原因：[理由]

## Risks

- [风险 1]：缓解措施：[方案]
- [风险 2]：缓解措施：[方案]

## Open Questions

- [ ] [需要评审人回答的具体问题 1]
- [ ] [需要评审人回答的具体问题 2]
实战指南
从零建立 RFC 流程的六步法
第一步：定义流程范围


确定哪些类型的变更需要 RFC。过窄会漏掉重要决策，过宽会造成流程负担。推荐起始规则：「任何影响两个以上团队或需要超过两周开发时间的技术变更需要 RFC」。


第二步：设计模板


从 One-Page RFC 格式开始。不要一开始就设计 10 个字段的复杂模板——团队会因为高摩擦而放弃。


第三步：建立存储结构


project-root/
├── docs/
│   └── rfcs/
│       ├── 000-template.md          # RFC 模板
│       ├── 001-adopt-grpc.md        # 第一份 RFC
│       ├── 002-event-sourcing.md
│       └── README.md                # RFC 索引和流程说明
第四步：定义评审流程


rfc_process:
  writing:
    duration: '1-3 days'
    author_actions:
      - 使用模板创建 RFC
      - 指定 2-4 名评审人
      - 设定决策截止日期（通常 1 周）
      - 通过 PR 提交 RFC

  review:
    duration: '3-5 business days'
    reviewer_actions:
      - 在 PR 中留下具体的技术评论
      - 标注 Approve / Request Changes / Comment
      - 必须在截止日期前回复

    escalation:
      - 截止日期到达但未达成共识 → 安排 30 分钟同步会议
      - 会议后仍有分歧 → 技术负责人做最终决策

  decision:
    actions:
      - 在 RFC 顶部添加决策结果和日期
      - 合并 PR
      - 创建对应的 ADR（如果需要）
      - 在团队频道公告决策结果
第五步：试运行


选择一个即将开始的项目，要求负责人按 RFC 流程推进。收集参与者反馈后调整流程细节。


第六步：制度化


    

  • 在项目启动清单中加入「是否需要 RFC？」检查项
    • 

  • 在 PR 模板中添加「此 PR 是否需要 RFC 支持？」字段
    • 

  • 每月汇总 RFC 指标（提交数、平均评审时间、接受率）
    •

避免 RFC 失败的关键策略
策略一：指定具体评审人。「发给所有人」等于「发给没有人」。指定 2-4 个必须回复的评审人，并设置明确的截止日期。


策略二：前置同步对齐。在正式撰写 RFC 之前，先用 10 分钟和关键干系人口头沟通方向。避免花两周写一份注定会被否决的 RFC。


策略三：控制篇幅。如果 RFC 超过 5 页，将详细设计移到附录或单独的设计文档中，RFC 本身只保留决策相关内容。


策略四：明确「Open Questions」。在 RFC 中明确列出你不确定的问题和需要评审人帮助回答的具体问题。这给评审人明确的关注方向。

RFC 的文化建设
良好的 RFC 文化特征：


## 健康的 RFC 文化标志

- RFC 被视为"学习工具"而非"审批关卡"
- 被拒绝的 RFC 是正常的，代表思考过程有价值
- 评审人提供具体的技术反馈，而非泛泛的"看起来不错"
- RFC 讨论聚焦于技术权衡，而非个人偏好
- 初级工程师也被鼓励撰写 RFC

## 不健康的 RFC 文化信号

- RFC 变成了"走过场"——100% 通过率
- 评审人只是点了👍但没有实质评论
- RFC 被视为延迟交付的障碍
- 只有高级工程师才写 RFC
- RFC 内容与最终实现严重不符但无人跟进

GitHub PR 作为 RFC 平台的实践
# 创建 RFC 分支
git checkout -b rfc/adopt-event-sourcing

# 从模板创建 RFC
cp docs/rfcs/000-template.md docs/rfcs/003-event-sourcing.md

# 编辑 RFC 内容
vim docs/rfcs/003-event-sourcing.md

# 提交并创建 PR
git add docs/rfcs/003-event-sourcing.md
git commit -m "docs(rfc): propose event sourcing for order service"
git push origin rfc/adopt-event-sourcing

# 在 GitHub 上创建 PR，描述中标注：
# - Reviewers: @alice @bob @charlie
# - Decision needed by: 2026-05-20

总结
RFC 流程的核心价值不在于文档本身，而在于它创造的「被迫思考和沟通的机制」。一份好的 RFC 迫使作者在编码前理清思路、考虑替代方案、识别风险；同时给评审人提供结构化的参与途径。建立 RFC 流程的关键是从最小可行版本开始（One-Page 模板 + 2 人评审 + 1 周时间窗口），在实践中根据团队反馈逐步完善，绝不要从一个完美但复杂的流程开始。
