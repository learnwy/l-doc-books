ADR 模板设计与最佳实践

概述

ADR 模板是决策记录实践能否在团队中落地的关键因素。一个过于简单的模板可能遗漏重要信息，一个过于复杂的模板则会因高摩擦而被团队放弃。从 Michael Nygard 2011 年提出的经典五段式模板，到 MADR（Markdown Architectural Decision Records）的结构化扩展，再到各种企业定制版本，业界已经积累了丰富的模板设计经验。本文将系统对比主流模板风格，并提供根据团队特征选择或定制模板的实用指南。

核心概念

Nygard 经典模板

Michael Nygard 在其开创性文章中定义了 ADR 的最小化结构。这个模板以极致的简洁著称，它认为一份有效的 ADR 只需要回答三个核心问题：背景是什么、决策是什么、后果是什么。

# ADR-NNNN: [简短决策标题]

## Status

[Proposed | Accepted | Deprecated | Superseded by ADR-XXXX]

## Context

[描述促使这个决策产生的情境。有哪些约束力在起作用？ 技术约束、业务需求、团队能力、时间压力。]

## Decision

[清晰明确地陈述决策。用现在时态表述。 "We will use X" 而非 "We decided to use X"。]

## Consequences

[决策的后果——好的和坏的。 每个决策都有代价，诚实记录权衡取舍。]

这个模板的核心优势是低摩擦——一份 ADR 可以在 15 分钟内完成。它特别适合：小型团队（5-15 人）、刚开始引入 ADR 实践的组织、以及需要快速记录频繁决策的敏捷环境。

MADR（Markdown Architectural Decision Records）

MADR 由 Oliver Kopp 等人在 Nygard 模板基础上发展而来，增加了更多结构化字段以支撑更严格的决策分析。当前最新版本为 MADR 4.0。

# [简短决策标题]

## Context and Problem Statement

[描述上下文和问题陈述，例如自由形式的两到三句话， 或者一个说明性的用户故事格式]

## Decision Drivers

- [driver 1: 例如"必须支持 10K req/s，P99 < 200ms"]
- [driver 2: 例如"团队对技术 X 经验有限"]
- [driver 3: 例如"必须在 6 周内上线"]

## Considered Options

- [Option 1]
- [Option 2]
- [Option 3]

## Decision Outcome

Chosen option: "[Option N]", because [justification].

### Consequences

- Good, because [positive consequence]
- Bad, because [negative consequence]
- Neutral, because [tradeoff with unclear impact]

### Confirmation

[描述如何确认决策被正确实施。 例如：代码评审标准、自动化测试、架构适应度函数]

## Pros and Cons of the Options

### [Option 1]

[描述 | 示例 | 链接]

- Good, because [argument a]
- Good, because [argument b]
- Bad, because [argument c]

### [Option 2]

[描述 | 示例 | 链接]

- Good, because [argument a]
- Bad, because [argument b]
- Bad, because [argument c]

## More Information

[相关 ADR 链接、会议记录、调研文档等]

MADR 的独特价值在于 Decision Drivers（决策驱动因素）和 Confirmation（确认机制）两个部分。前者迫使作者明确评估标准，后者确保决策不只是纸面文章而能被验证执行。

Y-Statement 模板

Y-Statement 是一种极简的单句式 ADR 格式，适用于需要大量快速记录的场景：

In the context of [situation/problem],
facing [concern],
we decided for [option]
and against [other options],
to achieve [quality goals],
accepting [downsides].

实际使用示例：

In the context of inter-service communication, facing the need for low-latency and type-safe APIs, we decided for gRPC with Protocol Buffers and against REST with JSON and GraphQL, to achieve sub-10ms P99 latency and compile-time type checking, accepting higher complexity in debugging and limited browser support.

模板选择决策矩阵

不同的团队环境适合不同的模板风格。以下矩阵帮助做出选择：

企业级定制模板设计

大型组织通常需要在标准模板基础上增加组织特有的字段。以下是一个综合了多家科技公司实践的企业级模板：

# ADR-[NNN]: [决策标题]

| 字段             | 内容                                                     |
| ---------------- | -------------------------------------------------------- |
| **Status**       | Proposed / Accepted / Deprecated / Superseded by ADR-NNN |
| **Date**         | YYYY-MM-DD                                               |
| **Author**       | [姓名]                                                   |
| **Reviewers**    | [评审人列表]                                             |
| **Approver**     | [最终决策人]                                             |
| **Related ADRs** | [关联决策链接]                                           |
| **Confidence**   | High / Medium / Low                                      |
| **Revisit By**   | [建议重新评估的日期或触发条件]                           |

## Context

[2-3 段描述当前情况、面临的问题、存在的约束]

## Decision Drivers

- [驱动因素 1]
- [驱动因素 2]
- [驱动因素 3]

[明确、具体地陈述决策内容]

模板演进策略

模板不是一成不变的。推荐以下演进路径：

关键原则是从最小化开始，按需添加字段。只有当团队持续感到某个信息缺失时，才增加新的模板字段。避免一开始就使用完整模板导致的写作疲劳。


最佳实践
模板中的写作技巧
Context 部分的写法：不要写成需求文档。聚焦于解释「为什么现在需要做这个决策」。好的 Context 回答三个问题：发生了什么变化？面临什么问题？如果不做决策会怎样？


Decision 部分的写法：使用祈使语气和现在时态。「We will use PostgreSQL as the primary database」而非「After careful consideration, the team has decided that PostgreSQL would be the best choice.」前者清晰直接，后者冗长模糊。


Consequences 部分的写法：区分「必然后果」和「可能风险」。必然后果是决策的直接结果（如选择 NoSQL 就意味着放弃强一致性），可能风险是不确定的未来影响（如该技术可能在三年后停止维护）。

在项目中初始化 ADR 模板
使用 adr-tools 的典型初始化流程：


# 安装 adr-tools
brew install adr-tools

# 在项目中初始化 ADR 目录
adr init doc/architecture/decisions

# 创建自定义模板
cat > doc/architecture/decisions/template.md << 'EOF'
# NUMBER. TITLE

Date: DATE

## Status

STATUS

## Context

[What is the issue we're addressing?]

## Decision

[What have we decided to do?]

## Consequences

[What becomes easier or more difficult?]
EOF

# 创建第一个 ADR
adr new "Use PostgreSQL for primary database"
总结
模板设计的黄金法则是：足够结构化以确保关键信息不被遗漏，又足够简洁以避免成为团队的写作负担。从 Nygard 经典模板开始，在实践中根据团队的具体需求逐步演进。记住，最好的模板不是最全面的那个，而是团队实际愿意使用的那个。一份被认真填写的简单模板，永远好于一份被敷衍应付的复杂模板。
