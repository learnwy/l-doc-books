决策记录的价值与原则

概述

每一个软件系统都是无数架构决策的产物。选择微服务还是单体、用 PostgreSQL 还是 MongoDB、采用事件驱动还是请求响应——这些选择塑造了系统的基因。然而在大多数团队中，这些关键决策的上下文——为什么做出这个选择、考虑了哪些替代方案、接受了什么权衡——往往随着时间流逝而消散。架构决策记录（Architecture Decision Records，ADR）正是为解决这一「决策失忆症」而设计的轻量级实践。

Martin Fowler 在 2026 年 3 月更新的文章中明确指出：ADR 的价值不仅在于为后来者提供决策记录，更在于编写过程本身迫使团队成员将隐含分歧显性化、讨论并解决。这种「通过写作来思考」的方式，让许多潜在的架构冲突在设计阶段就被发现，而非在实现阶段才暴露。

核心概念

决策上下文丢失的隐性成本

当决策上下文丢失时，组织会为之付出多重隐性代价：

重复讨论成本：新成员不了解历史决策的原因，提出看似合理但实际已被否决的方案，团队不得不重新经历一轮讨论。据行业调查，一个中等规模的工程团队每年花在重新辩论已解决问题上的时间约占总会议时间的 15-20%。

错误推翻成本：在不了解原始决策约束的情况下修改架构，可能引入已被规避的风险。例如，团队曾因特定的数据一致性需求选择了同步调用，后来的开发者在不知道这一约束的情况下改为异步消息，导致了严重的数据不一致问题。

新人融入成本：新加入团队的工程师面对一个「不明所以」的系统，需要大量时间通过考古式代码阅读和非正式询问来理解系统为何如此。没有 ADR 的团队，新人的有效产出时间通常延迟 2-4 周。

架构漂移成本：没有决策记录作为锚点，团队在长期迭代中容易偏离最初的设计意图，产生难以察觉的架构退化。

ADR 的核心定义

架构决策记录是一份简短的文档，它捕获并解释一个与产品或生态系统相关的重要决策。Michael Nygard 在 2011 年首次定义了这一概念，核心理念是：

ADR = Context（背景） + Decision（决策） + Consequences（后果）

一份有效的 ADR 应当：

  • 聚焦单一决策，而非记录整个系统设计
  • 保持简短，通常不超过一到两页
  • 记录「为什么」而非「怎么做」
  • 一旦接受便不再修改，只能被新的 ADR 取代

什么时候需要编写 ADR

并非所有技术选择都需要 ADR。以下是判断是否需要编写 ADR 的启发式规则：

## 需要 ADR 的情况

- 影响多个服务或组件的决策
- 难以逆转或逆转代价高昂的选择
- 团队内部存在明显分歧的问题
- 涉及非显而易见的权衡取舍
- 拒绝了一个「看似显然」的方案（需要解释为什么）

## 不需要 ADR 的情况

- 变量命名约定
- 小型库的选择（如日期处理工具）
- Bug 修复方案
- UI 组件样式选择
- 容易逆转的技术选择

实战指南

编写 ADR 的核心原则

倒金字塔写作法：借鉴新闻写作的倒金字塔结构，将最重要的信息放在文档开头。读者应该在前三行就能理解这个 ADR 要解决什么问题和最终决策是什么。

现在时态表述决策：用「我们将使用 X」而非「我们决定使用 X」。现在时暗示这是一个活跃的、正在执行的决策，而非一段历史记录。

诚实记录负面后果：每个决策都有代价。如果你无法列出任何缺点，说明还没有充分思考。强制自己列出至少两个负面后果，这有助于建立团队对决策限制的清醒认识。

保持不可变性：一旦 ADR 被接受，就不应该修改其内容。如果决策需要变更，应创建新的 ADR 并标注旧 ADR 为「被取代」状态，同时链接到新决策。这保持了完整的决策演进历史。

从零开始引入 ADR 的步骤

第 1 周：种子期

- 选择一个近期做出的重要架构决策
- 由技术负责人编写第一份 ADR 作为示范
- 在团队内部分享并收集格式反馈

第 2 周：试运行期

- 建立 doc/adr/ 目录结构
- 约定编号和命名规则
- 要求新的架构决策必须附带 ADR

第 3-4 周：习惯养成期

- 在 PR 评审中检查是否需要 ADR
- 将 ADR 链接到相关的代码变更
- 定期在团队会议中回顾近期 ADR

实际案例：Spotify 的 ADR 实践

Spotify 的工程博客记录了他们在微服务架构中引入 ADR 的历程。关键经验包括：

  • 将 ADR 存放在对应服务的代码仓库中（docs/decisions/ 目录）
  • 使用单调递增编号（如 0001-use-grpc-for-internal-communication.md）
  • 在 Pull Request 模板中添加「此变更是否需要 ADR？」的复选框
  • 每季度进行一次 ADR 审查，识别可能需要更新的过时决策

最佳实践

高效 ADR 的八项准则

准则 说明 反模式
单一决策 每份 ADR 只记录一个决策 在一份文档中塞入多个相关决策
简洁精炼 目标一到两页，最多不超过三页 编写 10 页以上的详细设计文档
聚焦原因 重点解释为什么，而非详述如何实现 将实现细节混入决策记录
列出替代方案 明确列出考虑过的其他选项 只记录最终选择，不提及被否决的方案
承认不确定性 记录决策的信心水平和重新评估触发条件 将每个决策都表述为「唯一正确答案」
独立可读 每份 ADR 无需其他上下文即可理解 大量引用未公开的口头讨论内容
时间戳明确 记录决策日期和参与者 省略时间和上下文信息
链接完整 关联相关 ADR、RFC 和代码变更 孤立的、与其他文档无连接的记录

常见陷阱与应对

陷阱一：追求完美导致不写。ADR 的敌人不是低质量，而是不存在。一份简短的、只有三段话的 ADR 远好于什么都没有。

陷阱二：事后补写变成虚构。决策记录应在决策做出时或之后不久编写。事后数月补写的 ADR 往往会美化决策过程、遗忘被否决的方案。

陷阱三：将 ADR 变成设计文档。ADR 记录决策点，设计文档描述解决方案。两者互补但不可替代。如果你的 ADR 超过三页，它可能应该是一份设计文档加一份 ADR。

工具与生态

存储与组织方案

最常见且最推荐的做法是将 ADR 存放在代码仓库中：

project-root/
├── doc/
│   └── adr/
│       ├── 0001-use-postgresql-for-primary-database.md
│       ├── 0002-adopt-event-sourcing-for-order-service.md
│       ├── 0003-choose-grpc-over-rest-for-internal-apis.md
│       └── template.md
├── src/
└── ...

这种方式的优势：

  • ADR 与代码一起被版本控制，可以看到决策随时间的演进
  • Pull Request 中可以同时 review 代码变更和相关的 ADR
  • 开发者无需离开开发环境即可查阅决策记录
  • 可以通过 git blame 追溯每个 ADR 的作者和时间线

发布与可见性

仅存放在代码仓库中的 ADR 对非开发者（如产品经理、管理层）不够友好。可通过构建任务将 ADR 发布到团队内部网站：

# GitHub Actions 示例：自动发布 ADR 到内部文档站
name: Publish ADRs
on:
  push:
    paths: ['doc/adr/**']
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Generate ADR index
        run: |
          echo "# Architecture Decision Records" > doc/adr/INDEX.md
          for f in doc/adr/0*.md; do
            title=$(head -1 "$f" | sed 's/^# //')
            echo "- [$title](./$f)" >> doc/adr/INDEX.md
          done
      - name: Deploy to docs site
        uses: peaceiris/actions-gh-pages@v4
        with:
          publish_dir: ./doc/adr

总结

架构决策记录的核心价值在于将转瞬即逝的讨论转化为持久的组织知识。它不需要复杂的工具或流程，只需要团队达成共识：重要的架构决策值得用几分钟时间写下来。记住三个关键原则——简短、不可变、聚焦原因——你就已经掌握了 ADR 实践的精髓。最重要的一步不是设计完美的模板，而是今天就为最近的一个架构决策写下你的第一份 ADR。
