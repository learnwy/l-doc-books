ADR 生命周期与工具链

概述

架构决策记录不是一次性文档——它有完整的生命周期，从最初的提议到最终被新决策取代，每个阶段都有其特定的规则和管理需求。有效管理 ADR 生命周期是确保决策日志长期健康的关键。同时，随着 ADR 实践的普及，一系列专用工具链的出现让创建、管理和发布 ADR 变得更加高效。本文将系统讲解 ADR 的完整状态流转机制，并深入介绍当前主流的 ADR 工具链及其最佳使用方式。

核心概念

ADR 状态模型

一份 ADR 在其生命周期中会经历以下状态：

Proposed（提议中）：ADR 刚被创建，正在讨论中。此时文档内容可以自由修改、补充信息、调整方案。团队成员可以在这个阶段提供反馈、提出疑问、建议替代方案。


Accepted（已接受）：团队达成共识并接受了这个决策。从这一刻起，ADR 进入「不可变」状态——其内容不应被修改。这不是技术上的强制限制，而是一种团队约定，目的是保持决策记录的历史真实性。


Rejected（已拒绝）：经过讨论后，团队决定不采纳这个提议。被拒绝的 ADR 同样有保留价值——它记录了「我们考虑过但决定不做的事」，防止未来重复提出相同方案。


Deprecated（已废弃）：决策曾经有效，但由于外部条件变化（如技术栈升级、业务需求变更）而不再适用。与 Superseded 不同，Deprecated 通常没有直接的替代决策。


Superseded（已取代）：最重要的状态转换。当需要修改一个已接受的决策时，不是编辑原始 ADR，而是创建新的 ADR 并将原始 ADR 标记为 Superseded，同时添加到新 ADR 的链接。


不可变性原则的深层含义
不可变性是 ADR 实践区别于普通文档的核心特征。其背后的设计哲学是：


    

  • 历史真实性：ADR 记录的是「在那个时刻，基于那些信息，团队做出了什么决策」。事后修改会扭曲这一历史记录。
    • 

  • 决策链可追溯：通过 Superseded 链接形成的决策链，可以完整还原一个架构选择的演进过程。
    • 

  • Git 友好：不可变文件与 git 的追加式历史模型天然契合，diff 清晰、blame 可靠。
    •

实战指南
状态转换工作流
在实际工作中，以下是管理 ADR 状态转换的推荐流程：


## 创建新 ADR

1. 从模板创建新文件，编号递增
2. 设置 Status: Proposed
3. 填写 Context 和初步 Decision
4. 提交 PR / 在团队频道分享
5. 收集反馈，更新内容

## 接受决策

1. 确认所有必要的评审人已提供反馈
2. 在团队会议中（或异步确认）达成共识
3. 更新 Status: Accepted
4. 记录决策日期和参与决策的人员
5. 合并 PR

## 取代旧决策

1. 创建新 ADR，引用旧 ADR 编号
2. 在新 ADR 的 Context 中解释为什么旧决策不再适用
3. 更新旧 ADR 的状态为 Superseded by ADR-[新编号]
4. 两个变更应在同一个 PR 中提交
定期审查机制
ADR 不是写完就忘的。推荐建立定期审查机制：


# ADR 审查日历配置示例
adr_review:
  frequency: quarterly
  scope: all-accepted-adrs
  checklist:
    - 决策的前提条件是否仍然成立？
    - 是否有新的技术选项使当前决策不再最优？
    - 决策产生的负面后果是否超出预期？
    - 是否有团队成员对当前决策有未表达的疑虑？
  actions:
    - reaffirm: 确认决策仍然有效，添加审查日期注释
    - supersede: 创建新 ADR 取代当前决策
    - deprecate: 标记为不再适用
与 Git 工作流的集成
ADR 应当与代码变更关联。以下是推荐的 Git 集成实践：


# 提交 ADR 时的 commit message 格式
git commit -m "docs(adr): add ADR-042 use event sourcing for order service

Relates to: JIRA-1234
Reviewers: @alice, @bob, @charlie"

# 在功能分支中同时包含 ADR 和实现代码
git log --oneline
# a1b2c3d feat(order): implement event sourcing pattern
# d4e5f6g docs(adr): add ADR-042 use event sourcing for order service
# 7h8i9j0 refactor(order): prepare for event sourcing migration

推荐策略：对于大多数团队，全局单调递增 是最佳选择。它简单、无歧义、在目录列表中自然排序。文件名应包含决策标题的 slug 形式（如 0001-use-postgresql-for-primary-database.md），这样即使不打开文件也能快速识别决策内容。


ADR 存储位置的选择
垃圾收集策略
随着时间推移，ADR 日志会不断增长。如何处理历史 ADR：


    

  • 永不删除：所有 ADR（包括 Rejected 和 Superseded）都保留，它们记录了组织的学习过程
    • 

  • 分层归档：活跃 ADR 保持在主目录，超过 2 年的非活跃 ADR 移到 archive/ 子目录
    • 

  • 索引维护：维护一份 INDEX.md 按主题和状态分类列出所有 ADR
    •

Log4brains 深度实践
Log4brains 是目前最完善的 ADR 发布工具，它将 ADR 转化为可搜索的静态网站：


# 安装
npm install -g log4brains

# 初始化项目
log4brains init

# 创建新 ADR
log4brains adr new "Use Redis for session management"

# 本地预览 ADR 文档站
log4brains preview

# 构建静态站点用于部署
log4brains build
Log4brains 的配置文件 .log4brains.yml 支持多仓库 ADR 聚合：


project:
  name: 'My Platform'
  tz: 'Asia/Shanghai'
  adrFolder: 'docs/adr'

packages:
  - name: 'api-gateway'
    path: '../api-gateway'
    adrFolder: 'doc/adr'
  - name: 'user-service'
    path: '../user-service'
    adrFolder: 'doc/adr'
CI/CD 集成自动化
将 ADR 管理集成到持续交付流程中：


# .github/workflows/adr-quality.yml
name: ADR Quality Check
on:
  pull_request:
    paths: ['doc/adr/**']

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Check ADR format
        run: |
          for f in doc/adr/0*.md; do
            # 检查必须包含 Status 字段
            grep -q "^## Status" "$f" || echo "ERROR: $f missing Status"
            # 检查必须包含 Context 字段
            grep -q "^## Context" "$f" || echo "ERROR: $f missing Context"
            # 检查必须包含 Decision 字段
            grep -q "^## Decision" "$f" || echo "ERROR: $f missing Decision"
          done

      - name: Check superseded links
        run: |
          # 验证所有 Superseded 引用指向存在的 ADR
          grep -rh "Superseded by ADR-" doc/adr/ | \
            grep -oP 'ADR-\d+' | while read ref; do
              num=$(echo "$ref" | grep -oP '\d+')
              if ! ls doc/adr/$(printf "%04d" $num)*.md 2>/dev/null; then
                echo "ERROR: Reference to non-existent $ref"
              fi
            done
总结
ADR 生命周期管理的核心是不可变性和可追溯性。每份 ADR 一旦被接受就成为历史记录的一部分，只能通过创建新 ADR 来「覆盖」而非「修改」。工具链的选择应遵循渐进原则：从最简单的目录结构和手动管理开始，当团队积累了足够多的 ADR 后再引入 Log4brains 等发布工具。记住，工具是为流程服务的——先建立正确的流程习惯，再用工具来降低摩擦。
