架构图即代码实践

概述

传统的架构图绘制方式——使用 Visio、Lucidchart 或 Draw.io 等拖拽式工具——面临一个根本性问题：图表与代码之间缺乏连接，随着系统演进，文档不可避免地腐化。「架构图即代码」（Diagrams as Code）运动提出了一种根本不同的方法：用文本描述语言定义架构模型，通过渲染引擎生成可视化图表。这意味着架构图可以像代码一样被版本控制、代码评审、自动构建和持续部署。Structurizr DSL、PlantUML、D2 等工具正在让这一理念成为主流实践。

核心概念

从图表到模型的范式转变

传统方法是「绘制图表」——关注的是视觉呈现。Diagrams as Code 的核心转变是「定义模型」——关注的是结构关系。一个模型可以生成多个视图，每个视图服务于不同的受众和目的。

这种模型驱动的方法带来了核心优势：


    

  • 单一事实来源：模型定义一次，多视图自动生成
    • 

  • 版本控制：DSL 文件存储在 Git 中，每次变更都有完整历史
    • 

  • 代码评审：架构变更通过 Pull Request 评审，而非邮件中的截图
    • 

  • 自动化：CI/CD 管道自动渲染最新版图表，发布到文档站
    • 



Diagrams as Code 工具分类
当前的 Diagrams as Code 工具可分为两类：


图表驱动工具（Diagram-centric）：每个文件定义一张图表，语法直接描述视觉元素。


    

  • PlantUML、Mermaid、D2、Graphviz
    • 



模型驱动工具（Model-centric）：定义一个底层模型（元素和关系），在此基础上定义多个视图。


    

  • Structurizr DSL、Ilograph、Carbide
    • 



## 对比示例

### 图表驱动（PlantUML）— 每张图独立定义

@startuml actor User rectangle "Web App" as webapp database "Database" as db User --> webapp : uses webapp --> db : reads/writes @enduml

### 模型驱动（Structurizr DSL）— 定义一次，多视图

workspace { model { u = person "User" s = softwareSystem "System" { webapp = container "Web App" db = container "Database" } u -> s.webapp "Uses" s.webapp -> s.db "Reads/writes" } views { systemContext s { include _ } container s { include _ } } }
实战指南
PlantUML + C4-PlantUML 实践
PlantUML 通过 C4-PlantUML 扩展库支持 C4 模型语法。这是最广泛使用的免费开源方案：


@startuml
!include <C4/C4_Context>
!include <C4/C4_Container>

title System Context - E-Commerce Platform

Person(customer, "Customer", "Browses and buys products")
Person(admin, "Admin", "Manages catalog and orders")

System(ecommerce, "E-Commerce Platform", "Allows customers to browse and purchase products")

System_Ext(payment, "Payment Gateway", "Processes payments via Stripe")
System_Ext(shipping, "Shipping Service", "Handles logistics via FedEx API")
System_Ext(email, "Email Service", "Sends transactional emails via SendGrid")

Rel(customer, ecommerce, "Browses catalog, places orders", "HTTPS")
Rel(admin, ecommerce, "Manages products, processes returns", "HTTPS")
Rel(ecommerce, payment, "Processes payments", "HTTPS/API")
Rel(ecommerce, shipping, "Creates shipments", "HTTPS/API")
Rel(ecommerce, email, "Sends notifications", "SMTP/API")

@enduml

!include <C4/C4_Container>

D2 语言实践
D2 是 2023 年后兴起的新一代图表语言，语法更加直观且支持主题化：


direction: right

customer: Customer {
  shape: person
}

ecommerce: E-Commerce Platform {
  style.stroke: "#0077b6"

  frontend: React SPA {
    shape: rectangle
    style.fill: "#caf0f8"
  }

  api: API Server (Node.js) {
    shape: rectangle
    style.fill: "#90e0ef"
  }

  db: PostgreSQL {
    shape: cylinder
    style.fill: "#0096c7"
  }

  redis: Redis Cache {
    shape: cylinder
    style.fill: "#ff6b6b"
  }
}

stripe: Stripe Payment {
  shape: rectangle
  style.stroke-dash: 3
}

ecommerce.frontend -> ecommerce.api: REST/JSON
ecommerce.api -> ecommerce.db: SQL
ecommerce.api -> ecommerce.redis: Cache
ecommerce.api -> stripe: Payment API
CI/CD 集成：自动生成和发布架构图
将架构图的渲染集成到 CI/CD 流水线中，确保文档站始终展示最新版本：


# .github/workflows/architecture-docs.yml
name: Build Architecture Diagrams
on:
  push:
    paths:
      - 'docs/architecture/**'
      - '.structurizr/**'

jobs:
  render-diagrams:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Render Structurizr DSL
        uses: docker://structurizr/cli:latest
        with:
          args: export -workspace .structurizr/workspace.dsl -format plantuml/c4plantuml -output docs/diagrams/

      - name: Render PlantUML to SVG
        uses: docker://plantuml/plantuml-server:latest
        run: |
          for f in docs/diagrams/*.puml; do
            java -jar /opt/plantuml.jar -tsvg "$f"
          done

      - name: Render Mermaid diagrams
        uses: docker://minlag/mermaid-cli:latest
        with:
          args: -i docs/architecture/ -o docs/rendered/ -e svg

      - name: Deploy to docs site
        uses: peaceiris/actions-gh-pages@v4
        with:
          publish_dir: ./docs/rendered
Git 工作流与图表变更评审
架构图作为代码意味着变更必须经过评审：


# 创建架构变更分支
git checkout -b arch/add-notification-service

# 修改 Structurizr DSL
vim .structurizr/workspace.dsl

# 本地预览变更
docker run -it --rm -p 8080:8080 \
  -v $(pwd)/.structurizr:/usr/local/structurizr \
  structurizr/lite

# 提交并创建 PR
git add .structurizr/
git commit -m "docs(arch): add notification service to container diagram"
git push origin arch/add-notification-service
PR 中的架构变更 diff 清晰可读：


  model {
      u = person "User"
      s = softwareSystem "Platform" {
          api = container "API Server"
          db = container "Database"
+         notifier = container "Notification Service" "Sends push/email/SMS"
+         queue = container "Message Queue" "RabbitMQ"
      }
      u -> s.api "Uses"
      s.api -> s.db "Reads/writes"
+     s.api -> s.queue "Publishes events"
+     s.queue -> s.notifier "Delivers notifications"
  }

避免的常见陷阱
陷阱一：过度建模。不需要为每一个微服务都创建完整的四层 C4。聚焦于核心系统和变化频繁的区域。


陷阱二：忽略渲染一致性。不同版本的渲染工具可能产生不同的布局。在 CI 中固定工具版本号。


陷阱三：模型与代码脱节。设置定期检查机制，确保 DSL 中定义的服务和容器仍然反映实际系统。

总结
架构图即代码将架构文档从静态的、容易过时的 PNG 文件转变为活的、可演进的代码资产。选择合适的工具时考虑三个维度：团队技术栈兼容性（是否已经使用 PlantUML/Mermaid）、模型复杂度（单图还是多视图）、以及协作需求（是否需要非开发者参与）。从最轻量的 Mermaid 或 PlantUML 开始，在需要时升级到 Structurizr DSL 的完整模型驱动方案。
