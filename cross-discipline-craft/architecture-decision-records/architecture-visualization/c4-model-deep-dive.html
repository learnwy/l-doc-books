C4 模型深度解析

概述

C4 模型是由 Simon Brown 创建的一种分层架构可视化方法，它将软件架构描述组织为四个递进的抽象层次：Context（系统上下文）、Container（容器）、Component（组件）和 Code（代码）。C4 模型的核心理念是：像地图一样思考架构文档——你不会在一张地图上同时展示国家边界和街道门牌号。每个层次回答不同的问题，服务于不同的受众。截至 2026 年，C4 已成为全球使用最广泛的软件架构可视化标准之一，被 Structurizr、Visual C4、PlantUML 等数十种工具支持。

核心概念

四层抽象模型

C4 模型的四个层次形成严格的父子层级关系，每个层次分解上一层的内容，同时保留外部上下文：

层级 名称 用途 展示内容 主要受众
Level 1 System Context 全局视角 系统作为单一方框，加上用户和外部系统 所有人（技术和非技术）
Level 2 Container 高层部署结构 独立部署单元：Web 应用、API、数据库、消息队列 架构师、开发者、DevOps
Level 3 Component 逻辑组织 容器内部的模块：服务、仓储、控制器 开发者、技术负责人
Level 4 Code 实现细节 类、接口、数据库表 开发者、代码评审者

关键洞察：Level 1 和 Level 2 提供了约 80% 的沟通价值。Level 3 和 Level 4 是可选的，仅在解决具体文档需求时才使用。

Level 1：System Context Diagram

系统上下文图是所有 C4 文档的起点。它将你的系统描绘为单一方框，周围是与之交互的用户和外部系统。

┌─────────────────────────────────────────────────────┐
│                  System Context                      │
│                                                     │
│    ┌──────┐         ┌──────────┐       ┌────────┐  │
│    │ User │────────▶│ Banking  │──────▶│ Email  │  │
│    │      │         │ System   │       │ System │  │
│    └──────┘         └──────────┘       └────────┘  │
│                          │                          │
│                          ▼                          │
│                     ┌──────────┐                    │
│                     │Mainframe │                    │
│                     │ System   │                    │
│                     └──────────┘                    │
└─────────────────────────────────────────────────────┘

绘制原则：

  • 你的系统永远是中心的单一方框
  • 明确显示所有外部依赖
  • 用户角色用人形图标（Person）表示
  • 关系用有标签的箭头表示方向和协议

Level 2：Container Diagram

容器图展开系统的内部高层结构，揭示主要的技术选择和部署单元：

┌─ Banking System ────────────────────────────────────┐
│                                                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────┐  │
│  │ Web App  │  │Mobile App│  │   API Gateway    │  │
│  │ (React)  │  │(Swift/   │  │   (Node.js)      │  │
│  │          │  │ Kotlin)  │  │                   │  │
│  └────┬─────┘  └────┬─────┘  └────────┬─────────┘  │
│       │              │                  │            │
│       └──────────────┴──────────────────┘            │
│                      │                               │
│              ┌───────▼──────┐                        │
│              │  Database    │                        │
│              │ (PostgreSQL) │                        │
│              └──────────────┘                        │
└──────────────────────────────────────────────────────┘

容器类型包括：Web 应用、移动应用、桌面应用、API 服务、数据库、文件系统、消息队列、定时任务等。

Level 3：Component Diagram

组件图深入单个容器的内部，展示其逻辑模块：

组件图最佳实践：


    

  • 将相关功能分组
    • 

  • 显示清晰的接口和依赖关系
    • 

  • 避免过多细节——如果超过 15 个组件，考虑是否容器本身需要拆分
    • 



Level 4：Code Diagram（通常可选）
代码级图表映射到实际的类、接口和数据库表。大多数情况下，这一层可以由 IDE 自动生成，无需手动维护。只在以下情况才手动创建 Level 4 图表：


    

  • 复杂的设计模式需要解释
    • 

  • 数据模型需要 ER 图
    • 

  • 遗留代码需要重构前的全景理解
    • 



实战指南
构建第一个 C4 模型的步骤
步骤一：定义系统边界（Level 1）


1. 将你的系统放在中心位置
2. 识别所有用户角色（如：客户、管理员、运维人员）
3. 列出所有外部依赖（如：Stripe、AWS S3、SMTP 服务）
4. 绘制带标签的方向箭头，标注协议和数据类型例如：Frontend → API: REST/HTTPS (GET /orders)
步骤二：识别容器（Level 2）


核心问题：哪些是独立部署或独立运行的单元？


常见容器清单检查：□ Web 前端应用（SPA/SSR）□ 移动端应用 □ 后端 API 服务 □ 后台任务处理器 □ 主数据库 □ 缓存层 □ 消息队列 □ 文件存储 □ 搜索引擎
步骤三：分解为组件（Level 3）


选择一个容器深入：


    

  • 按业务功能分组组件
    • 

  • 识别每个组件的职责
    • 

  • 标注组件间的调用关系和数据流
    • 



用 Structurizr DSL 实现 C4
Structurizr 是 C4 模型的参考实现工具，使用 DSL 语法定义模型：


workspace "Online Banking" "C4 model of the banking system" {

    !identifiers hierarchical

    model {
        customer = person "Personal Banking Customer" "A customer of the bank"

        bankingSystem = softwareSystem "Internet Banking System" {
            webapp = container "Web Application" "React SPA" "JavaScript, React"
            apiApp = container "API Application" "Node.js Express" "JavaScript"
            database = container "Database" "PostgreSQL 16" "SQL" {
                tags "Database"
            }
        }

        emailSystem = softwareSystem "E-mail System" "SendGrid" {
            tags "External"
        }

        customer -> bankingSystem "Views account and makes payments"
        customer -> bankingSystem.webapp "Uses" "HTTPS"
        bankingSystem.webapp -> bankingSystem.apiApp "Makes API calls" "JSON/HTTPS"
        bankingSystem.apiApp -> bankingSystem.database "Reads/writes" "SQL/TLS"
        bankingSystem.apiApp -> emailSystem "Sends notifications" "SMTP"
    }

    views {
        systemContext bankingSystem "SystemContext" {
            include *
            autolayout lr
        }

        container bankingSystem "Containers" {
            include *
            autolayout lr
        }

        styles {
            element "External" {
                background #999999
                color #ffffff
            }
            element "Database" {
                shape Cylinder
            }
        }
    }
}
实际案例：Netflix 的架构文档实践
Netflix 的架构文档采用 C4 模型的变体，特点包括：


    

  • Level 1 使用极简化的系统上下文图展示核心领域（Streaming、Content、Studio）
    • 

  • Level 2 重点标注服务网格和数据流方向，使用颜色区分同步/异步通信
    • 

  • Level 3 仅对核心路径（如推荐算法管道、内容分发管道）创建组件图
    • 

  • 所有图表使用内部工具 Atlas 管理，支持从服务注册表自动生成 Level 2 视图
    • 



最佳实践
C4 绘图的十条黄金规则




规则
说明





1. 永远标注关系的方向和协议
Frontend → API: REST/HTTPS 而非无标签的线




2. 为每个元素添加技术栈标签
"Web App" (React, TypeScript)




3. 保持每层图表的元素数量可控
Level 1: ≤10, Level 2: ≤15, Level 3: ≤20




4. 不要在一张图上混合抽象层次
一张图只表达一个层次




5. 外部系统统一用灰色标识
快速区分系统边界内外




6. 为每张图添加图例
解释颜色、形状、线型的含义




7. 先画 Level 1 和 Level 2
这两层覆盖 80% 的沟通需求




8. Level 3/4 按需创建
只为复杂或关键的部分创建




9. 定期验证图表与代码的一致性
至少每季度检查一次




10. 用动词描述关系
"Sends email via" 而非 "Email"





常见错误与修正
错误一：过早深入细节。在系统边界还不清晰时就绘制组件图——先确保 Level 1 正确再深入。


错误二：把架构图当流程图。C4 图展示结构关系，不展示时间序列。需要展示调用顺序时使用 Supplementary Diagram（如 Dynamic Diagram）。


错误三：忽视受众差异。给管理层看 Level 3 组件图是无效的。为不同受众准备不同层次的视图。

总结
C4 模型的力量在于其简洁性——四个层次、统一的表示法、明确的受众划分。掌握 C4 不需要学习复杂的标准（如 UML 的 14 种图表类型），只需要理解「为不同受众提供不同抽象层次的视图」这一核心理念。在实践中，从 Level 1 System Context 开始，为你当前负责的系统画出第一张图——这通常只需要 30 分钟，但能带来与团队沟通时效率的显著提升。
