Mermaid 与团队协作图表

概述

Mermaid 是一种基于 JavaScript 的图表渲染引擎，它允许用户通过类似 Markdown 的文本语法创建各种图表。自 2022 年 GitHub 原生支持 Mermaid 渲染以来，它已经成为技术文档中最广泛使用的内嵌图表工具。Mermaid 的核心优势在于零部署成本——无需安装任何软件，只要在 Markdown 文件中写入 Mermaid 代码块，主流平台（GitHub、GitLab、Azure DevOps、Notion）就能自动渲染。对于架构可视化，Mermaid 提供了一种在日常文档中快速嵌入系统图的低摩擦方式。

核心概念

Mermaid 在架构文档中的定位

Mermaid 不是要替代 Structurizr 或 PlantUML 这类专业架构建模工具，而是填补了一个重要的空白：在普通 Markdown 文档中快速嵌入可视化。

实战指南
在 ADR 中使用 Mermaid
ADR 的 Context 部分经常需要图形化地展示当前系统状态和决策影响范围。以下是一个完整的 ADR 中嵌入 Mermaid 的实例：


# ADR-012: Adopt Event-Driven Architecture for Order Processing

## Status

Accepted

## Context

Current synchronous request chain causes cascading failures:

    ```mermaid
    graph LR
        A["Order API"] -->|sync| B["Payment Service"]
        B -->|sync| C["Inventory Service"]
        C -->|sync| D["Shipping Service"]
        D -->|sync| E["Notification Service"]

    ```

## Decision

We will adopt event-driven architecture using Kafka:

    ```mermaid
    graph LR
        A["Order API"] -->|publish| K{{"Kafka"}}
        K -->|subscribe| B["Payment Consumer"]
        K -->|subscribe| C["Inventory Consumer"]
        K -->|subscribe| D["Shipping Consumer"]
        K -->|subscribe| E["Notification Consumer"]
    ```

Mermaid 语法陷阱与修复
陷阱一：节点 ID 中的特殊字符


# 错误：ID 包含斜杠

graph LR /api/users --> /api/orders

# 正确：使用合法 ID + 标签

graph LR apiUsers["/api/users"] --> apiOrders["/api/orders"]
陷阱二：中文在圆括号节点中


# 错误：圆括号内中文

graph LR A(用户服务) --> B(订单服务)

# 正确：使用方括号

graph LR A["用户服务"] --> B["订单服务"]
陷阱三：引号嵌套


# 错误：引号内再嵌引号

graph LR A["Say "hello""]

# 正确：使用 HTML 实体

graph LR A["Say #quot;hello#quot;"]
最佳实践
Mermaid 图表的设计规范
为团队制定统一的 Mermaid 使用规范：


## 团队 Mermaid 规范

### 命名约定

- 节点 ID 使用 camelCase：`apiGateway`, `userService`
- 标签使用中英文均可，用方括号包裹：`["API Gateway"]`
- 外部系统用虚线边框或灰色标识

### 图表大小

- 单张图不超过 15 个节点
- 复杂系统拆分为多张图，每张聚焦一个视角

### 方向选择

- 数据流图：LR（从左到右）
- 层级架构：TB（从上到下）
- 状态机：LR 或 TB（视状态数量）
- 时序图：默认垂直

### 颜色使用

- 新增组件：#90EE90（浅绿）
- 变更组件：#FFD700（金色）
- 删除/废弃：#FF6B6B（红色）
- 外部系统：#D3D3D3（灰色）
自动化图表验证
在 CI 中验证 Mermaid 语法正确性：


# .github/workflows/mermaid-lint.yml
name: Mermaid Syntax Check
on:
  pull_request:
    paths: ['**/*.md']

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm install -g @mermaid-js/mermaid-cli
      - name: Validate all Mermaid blocks
        run: |
          # Extract and validate Mermaid blocks from Markdown
          find . -name "*.md" -exec grep -l "mermaid" {} \; | while read f; do
            echo "Checking $f..."
            mmdc -i "$f" -o /tmp/test.svg --quiet 2>&1 || echo "WARN: $f has mermaid issues"
          done

从 Mermaid 升级到专业工具的时机
当以下信号出现时，考虑从 Mermaid 升级到 Structurizr 或 PlantUML：


    

  • 需要从一个模型生成多个视图
    • 

  • 图表节点超过 20 个且布局不满意
    • 

  • 需要保证多张图之间的一致性（相同元素在不同图中用相同名称）
    • 

  • 需要交互式的可缩放图表
    • 

  • 需要自动化检查架构约束
    • 



总结
Mermaid 的核心价值在于将架构可视化的门槛降到最低。它不是最强大的工具，但它是摩擦最小的工具——任何能写 Markdown 的人都能在两分钟内画出一张系统关系图。在团队协作中，Mermaid 让每一份 ADR、RFC、PR 描述都有可能包含直观的视觉化辅助信息，从而显著提升技术文档的沟通效率。记住 Mermaid 的最佳使用原则：保持图表简洁（≤15 节点），服务于当前文档的叙述目标，不要试图在一张 Mermaid 图中展示整个系统架构。
