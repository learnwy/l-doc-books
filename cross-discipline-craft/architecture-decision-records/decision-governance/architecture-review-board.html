架构评审委员会运作机制

概述

架构评审委员会（Architecture Review Board，ARB）是组织级架构治理的核心机构。它的职责是确保跨团队的技术决策保持一致性、质量标准和战略对齐。然而在实践中，许多 ARB 沦为官僚机构——要么成为「盖章机器」走过场，要么成为「瓶颈关卡」阻碍团队交付。2026 年的最佳实践是将 ARB 重新定位为「架构咨询服务」而非「审批关卡」，结合轻量级的分级评审策略，在保障架构质量的同时最小化对团队速度的影响。

核心概念

ARB 的使命重定义

传统 ARB 的问题在于其定位为「门禁」——任何架构变更都必须经过 ARB 批准。这在快速迭代的环境中不可持续。现代 ARB 应被定义为：

## ARB 的核心使命

1. **保障架构一致性**：确保跨团队的决策不互相矛盾
2. **传播最佳实践**：将一个团队的成功经验推广到其他团队
3. **识别系统性风险**：发现单个团队视角无法看到的全局风险
4. **提供专家咨询**：为团队提供架构建议而非强制指令
5. **维护架构原则**：确保组织架构原则被理解和遵循

## ARB 不应该做的事

- ❌ 批准所有微小的技术决策
- ❌ 决定团队内部的实现细节
- ❌ 作为项目进度的阻塞点
- ❌ 成为少数人控制技术选型的工具
- ❌ 维护过时的标准而阻止创新

分级评审策略

不是所有架构决策都需要相同强度的评审。有效的 ARB 采用分级策略：

级别 触发条件 评审方式 时间 审批人
L0 无需评审 团队内部技术决策 自主决策 + ADR 0 团队自己
L1 轻量评审 单团队影响，但使用新技术 异步 RFC 评审 3-5 天 1 名 ARB 成员
L2 标准评审 跨 2-3 团队影响 异步评审 + 可选同步 5-10 天 2 名 ARB 成员
L3 深度评审 全组织影响或不可逆变更 评审会议 + 设计文档 2-3 周 全体 ARB 
ARB 的组成与运营
成员构成：


arb_composition:
  permanent_members:
    - role: '首席架构师'
      responsibility: '主持会议、最终裁决'
    - role: '平台架构师'
      responsibility: '基础设施和平台视角'
    - role: '安全架构师'
      responsibility: '安全合规视角'

  rotating_members: # 每季度轮换
    count: 3-4
    source: '各业务线技术负责人'
    tenure: '6 个月'
    purpose: '引入一线视角、培养架构能力'

  guest_members: # 按需参与
    when: '评审涉及其专业领域'
    examples: ['数据架构师', '前端架构师', 'ML 工程师']
运营节奏：


arb_operations:
  regular_meeting:
    frequency: '每两周一次'
    duration: '60 分钟'
    agenda:
      - 活跃 RFC/Design Doc 状态更新 (10 min)
      - L2/L3 评审讨论 (30 min)
      - 架构趋势和风险通报 (10 min)
      - 开放问答 (10 min)

  async_review:
    channel: '#architecture-review'
    sla: 'L1 在 3 天内回复，L2 在 5 天内回复'
    escalation: '超时自动升级到下次会议讨论'

  quarterly_activities:
    - 技术雷达更新
    - 架构原则审查和修订
    - ARB 成员轮换
    - 架构健康度报告发布
实战指南
评审触发条件的精确定义
模糊的触发条件会导致两个问题：应该评审的被跳过、不需要评审的浪费时间。以下是一套精确的判断规则：


## 必须提交 ARB 评审（L2+）

### 技术选型类

- 引入不在技术雷达 Adopt/Trial 中的新技术
- 更换团队的主要编程语言或框架
- 选择新的数据库类型
- 引入新的云服务提供商

### 架构变更类

- 将单体服务拆分为微服务（或反向合并）
- 引入新的服务间通信模式（如从 REST 到 gRPC）
- 变更数据的所有权或共享方式
- 添加新的异步消息通道

### 数据变更类

- 跨服务的数据模型变更
- 引入新的数据存储系统
- 修改数据保留或归档策略
- 涉及 PII（个人可识别信息）的新数据流

### 安全变更类

- 修改认证或授权机制
- 添加新的外部 API 暴露
- 修改数据加密策略
- 引入新的第三方集成
评审会议的高效运作
会前准备（评审人责任）：


## 评审人会前清单

- [ ] 完整阅读 RFC/Design Doc（至少 30 分钟）
- [ ] 在文档中留下异步评论
- [ ] 标注 2-3 个想在会议中讨论的关键问题
- [ ] 检查与已有架构原则和现有系统的一致性

## 禁止在会议中做的事

- ❌ 第一次阅读文档
- ❌ 讨论已在异步评论中解决的问题
- ❌ 纠结于文档格式或措辞
- ❌ 要求完美方案（完美是好的敌人）
会议结构（60 分钟）：


review_meeting_structure:
  - phase: 'Context Setting'
    duration: '5 min'
    lead: 'Author'
    content: '30 秒电梯演讲 + 需要 ARB 帮助决策的关键问题'

  - phase: 'Clarification Questions'
    duration: '10 min'
    lead: 'All'
    content: '纯提问，不讨论。确保所有人理解方案'

  - phase: 'Concern Discussion'
    duration: '30 min'
    lead: 'Facilitator'
    content: '按优先级讨论已标注的关注点'

  - phase: 'Decision'
    duration: '10 min'
    lead: 'Chief Architect'
    content: '总结讨论、明确决策、分配行动项'

  - phase: 'Next Steps'
    duration: '5 min'
    lead: 'Author'
    content: '确认需要修改的内容和时间线'
评审输出物标准化
每次 ARB 评审的输出应包含结构化的决策记录：


# ARB Review Record

**RFC/Design Doc:** [链接] **Review Date:** [日期] **Review Level:** L2 **Reviewers:** [参与的 ARB 成员]

## Decision

☐ Approved — 无修改要求 ☑ Approved with Conditions — 需满足以下条件后实施 ☐ Request Revision — 需要重大修改后重新评审 ☐ Rejected — 方案不被接受（附理由）

## Conditions (if applicable)

1. 添加 Circuit Breaker 在下游服务调用处
2. 性能测试需证明 P99 < 200ms
3. 迁移计划需包含回滚步骤

## Architectural Concerns Noted

- 数据一致性在异步场景下的保证方式需要进一步验证
- 建议与平台团队确认 Kafka 集群容量是否充足

## Follow-up Actions

| 行动项                       | 负责人         | 截止日期   |
| ---------------------------- | -------------- | ---------- |
| 更新 Design Doc 反映评审建议 | @author        | 2026-05-15 |
| 提供性能测试报告             | @author        | 2026-05-20 |
| 确认 Kafka 容量              | @platform-team | 2026-05-12 |
避免 ARB 成为瓶颈
策略一：SLA 承诺


arb_sla:
  l1_review: '3 个工作日内回复'
  l2_review: '5 个工作日内回复或安排会议'
  l3_review: '10 个工作日内完成全流程'
  violation: 'SLA 超时则默认 Approved with Conditions'
策略二：预批准模式（Golden Paths）


将常见的、已验证的架构模式预先批准，团队使用时无需评审：


## 预批准的架构模式

以下模式已获 ARB 预批准，团队可直接使用：

- PostgreSQL 作为关系型数据存储（标准配置）
- Redis 作为缓存层
- Kafka 作为事件总线（已有集群的业务）
- React + TypeScript 作为 Web 前端技术栈
- gRPC 用于内部服务间通信
- GitHub Actions 作为 CI/CD 工具
策略三：授权决策（Delegate Pattern）


## 授权规则

ARB 将以下类型的决策权授予各团队技术负责人：

- 团队内部的框架版本升级
- 技术雷达 Adopt 区域内的技术选择
- 不涉及跨团队接口的内部重构
- 测试策略和工具选择

团队技术负责人仍需创建 ADR 记录决策。

ARB 的文化建设
## 健康的 ARB 文化特征

✅ ARB 被视为"帮助团队做出好决策的资源" ✅ 团队主动寻求 ARB 的早期输入（而非被强制）✅ 评审聚焦于风险识别和经验分享 ✅ ARB 成员承认自己可能是错的 ✅ 评审结论有明确的理由记录 ✅ 被拒绝的提案得到建设性的改进建议

## 不健康的 ARB 文化信号

❌ 团队试图绕过 ARB（隐藏架构变更）❌ ARB 只会说"不"，不提供替代建议 ❌ 评审变成了资深工程师展示优越感的舞台 ❌ 决策没有记录理由（"ARB 说了不行"）❌ 同一决策被反复讨论无法收敛

总结
成功的 ARB 是一个「服务型」机构而非「管控型」机构。它的存在目的是帮助团队做出更好的决策，而非阻止团队做出决策。关键的设计原则是：分级评审（不是所有事都需要 ARB 审）、SLA 承诺（不成为瓶颈）、预批准模式（Golden Paths 消除重复评审）、以及结构化输出（每次评审产生可追溯的决策记录）。如果你的 ARB 让团队感到沮丧，说明需要调整——要么是评审触发条件太低（太多事找 ARB），要么是评审过程太慢（SLA 不合理），要么是评审输出不明确（团队不知道要改什么）。
