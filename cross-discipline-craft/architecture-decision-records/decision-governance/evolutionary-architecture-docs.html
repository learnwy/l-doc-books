演进式架构文档体系

概述

传统架构文档面临一个根本性矛盾：文档在完成的那一刻就开始过时。系统在持续演进，而文档却停留在某个时间快照上。演进式架构文档体系（Evolutionary Architecture Documentation）提出了一种与之截然不同的方法论——将文档视为活的系统而非静态产物，通过自动化、版本控制和适应度函数让文档随系统同步演进。这一方法融合了 ADR 的决策记录、C4 的架构可视化、技术雷达的技术治理，以及持续交付的自动化理念，形成一个完整的架构知识管理闭环。

核心概念

文档腐化（Documentation Rot）的根因

架构文档腐化不是因为团队懒惰，而是因为传统文档模式的固有缺陷：

腐化原因 表现 根本问题
文档与代码分离 架构图还是半年前的版本 更新文档需要额外的手动步骤
单一快照思维 只记录当前状态，不记录演进过程 缺乏变更的时间线视角
缺乏验证机制 文档描述与实际系统不符 没有自动化的一致性检查
维护责任不明 没人知道该谁更新文档 文档没有 Owner
工具与流程脱节 文档在 Wiki 中，代码在 Git 中 两个系统的变更没有关联

演进式文档的核心原则

原则 1：文档即代码（Docs as Code）


    

  • 所有架构文档存储在版本控制系统中
    • 

  • 使用 Markdown/AsciiDoc 等轻量级标记语言
    • 

  • 通过 Pull Request 评审文档变更
    • 

  • CI/CD 自动构建和发布
    • 



原则 2：自动化生成


    

  • 从代码/配置自动生成部分文档（如 API 文档、依赖图）
    • 

  • 架构图从 DSL 自动渲染
    • 

  • 文档站从源文件自动构建
    • 



原则 3：持续验证


    

  • 适应度函数检查架构约束是否被违反
    • 

  • 自动化测试验证文档描述与实际系统的一致性
    • 

  • 定期的文档健康度报告
    • 



原则 4：决策链追溯


    

  • 每个架构选择都可追溯到具体的 ADR
    • 

  • ADR 之间的 Superseded 链记录演进历程
    • 

  • 通过 git blame 追溯每次文档变更的原因
    • 



原则 5：最小必要量


    

  • 只维护必需的文档，不追求大而全
    • 

  • 优先维护高价值文档（Level 1-2 C4 图、核心 ADR）
    • 

  • 允许低价值文档自然衰减
    • 



适应度函数（Fitness Functions）
适应度函数是 Neal Ford 和 Rebecca Parsons 在《Building Evolutionary Architectures》中提出的概念——用自动化测试来持续验证架构约束。在文档体系中，适应度函数用于确保文档与实际系统保持一致：


// 示例：验证服务依赖关系图与实际通信一致
describe('Architecture Documentation Fitness', () => {
  it('documented services match deployed services', async () => {
    const documentedServices = parseC4Model('architecture/workspace.dsl');
    const deployedServices = await getKubernetesServices();

    const undocumented = deployedServices.filter((s) => !documentedServices.includes(s.name));

    expect(undocumented).toHaveLength(0, `Services not in architecture docs: ${undocumented.join(', ')}`);
  });

  it('documented dependencies match actual network calls', async () => {
    const documentedDeps = parseC4Dependencies('architecture/workspace.dsl');
    const actualDeps = await getServiceMeshTopology();

    const undocumentedDeps = actualDeps.filter(
      (dep) => !documentedDeps.some((d) => d.from === dep.source && d.to === dep.target),
    );

    expect(undocumentedDeps.length).toBeLessThan(3, 'Too many undocumented service dependencies');
  });

  it('ADR decisions are still valid', async () => {
    const adrs = await loadActiveADRs();

    for (const adr of adrs) {
      if (adr.revisitBy && new Date(adr.revisitBy) < new Date()) {
        console.warn(`ADR-${adr.number} "${adr.title}" needs review`);
      }
    }
  });
});

自动化文档流水线
# .github/workflows/docs-build.yml
name: Architecture Documentation Pipeline
on:
  push:
    branches: [main]
    paths:
      - 'architecture/**'
      - 'decisions/**'
      - 'api/**'

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Validate Structurizr DSL
        run: |
          docker run --rm \
            -v $(pwd)/architecture:/workspace \
            structurizr/cli:latest \
            validate -workspace /workspace/workspace.dsl

      - name: Check ADR format
        run: node scripts/validate-adrs.js

  generate:
    needs: validate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Render C4 diagrams
        run: |
          docker run --rm \
            -v $(pwd)/architecture:/workspace \
            structurizr/cli:latest \
            export -workspace /workspace/workspace.dsl \
            -format svg -output /workspace/diagrams/

      - name: Generate ADR index
        run: node scripts/generate-adr-index.js

      - name: Generate API docs
        run: npx @redocly/cli build-docs api/openapi.yaml -o docs/api.html

  fitness:
    needs: validate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run architecture fitness functions
        run: npm test -- --testPathPattern=architecture/fitness/

  publish:
    needs: [generate, fitness]
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to docs site
        uses: peaceiris/actions-gh-pages@v4
        with:
          publish_dir: ./docs-output

文档的退役策略
不是所有文档都需要永久维护：


## 文档退役规则

### 永不退役

- ADR（所有状态，包括 Superseded 和 Rejected）
- 系统级 C4 Context 图
- 架构原则文档

### 定期审查是否退役

- 超过 12 个月未更新的组件图
- 不再活跃的服务的详细设计文档
- 过时的运维手册

### 退役流程

1. 在文档顶部添加 ⚠️ ARCHIVED 标注
2. 记录退役日期和原因
3. 如有替代文档，添加指向替代的链接
4. 将文件移动到 archive/ 目录
5. 保留在版本控制中但从文档站移除

# 推荐的文档即代码技术栈

small_team: # 5-20 人团队
  source: 'Markdown in Git repo'
  diagrams: 'Mermaid (embedded in .md)'
  decisions: 'ADR files (adr-tools)'
  publishing: 'GitHub Pages + MkDocs'
  validation: 'Simple CI scripts'

medium_team: # 20-100 人团队
  source: 'Markdown + Structurizr DSL'
  diagrams: 'Structurizr + Mermaid'
  decisions: 'ADR + RFC (Log4brains)'
  publishing: 'Backstage TechDocs'
  validation: 'Fitness functions + CODEOWNERS'

large_org: # 100+ 人组织
  source: 'Monorepo docs/ + per-service docs/'
  diagrams: 'Structurizr Cloud + auto-generated'
  decisions: 'ADR + RFC + Design Docs (Confluence + Git sync)'
  publishing: 'Internal developer portal'
  validation: 'Fitness functions + Architecture scorecard'
  governance: 'ARB + Tech Radar + automated compliance'
总结
演进式架构文档体系的核心理念是：接受文档会过时这个现实，但建立机制让过时的速度慢于系统演进的速度，并在过时发生时快速发现和修复。实现这一目标的三根支柱是：自动化（减少手动更新的需要）、适应度函数（快速发现不一致）、以及 ADR 决策链（保留完整的演进历史即使某些具体文档过时了）。最终目标不是拥有完美的文档，而是拥有一个「足够好且持续改进」的文档系统——它能在 30 秒内回答「系统为什么是这样」这个最核心的问题。
