实验平台架构设计

核心概念

实验平台是支撑 A/B 测试工程化运作的基础设施。它将实验的设计、分组、配置下发、数据收集和结果分析集成为一个统一的系统，使产品团队能够自助式地创建和管理实验。一个成熟的实验平台需要解决三个核心问题：如何高效地进行流量分配、如何可靠地下发实验配置、如何准确地收集和分析数据。Google、Microsoft、Netflix 等公司的实验平台每天支撑数千个并行实验，是这些公司数据驱动决策的技术底座。

分流引擎设计
分流引擎是实验平台的核心组件，负责将每个用户确定性地分配到正确的实验和分组中。其设计需要满足以下要求：


确定性：相同的用户在相同的实验中必须始终返回相同的分组结果。这通过哈希函数实现——用户 ID + 实验 ID 经过哈希后映射到固定的桶。


正交性：不同实验层的分组结果必须统计独立。如果实验 A 和实验 B 在不同层，用户在 A 中的分组不应影响在 B 中的分组。


灵活性：支持动态调整流量比例、添加新实验组、紧急停止实验等操作，且不影响已有分组的稳定性。


interface ExperimentConfig {
  id: string;
  layerId: string;
  trafficAllocation: Array<{
    groupId: string;
    rangeStart: number;
    rangeEnd: number;
  }>;
  targetingRules: TargetingRule[];
  status: 'draft' | 'running' | 'paused' | 'completed';
}

interface AssignmentResult {
  experimentId: string;
  groupId: string;
  bucket: number;
}

function evaluateExperiments(userId: string, experiments: ExperimentConfig[]): AssignmentResult[] {
  const results: AssignmentResult[] = [];

  const layerGroups = groupBy(experiments, (e) => e.layerId);

  for (const [layerId, layerExps] of Object.entries(layerGroups)) {
    const bucket = hash(`${layerId}_${userId}`) % 10000;

    for (const exp of layerExps) {
      if (exp.status !== 'running') continue;
      if (!matchTargeting(userId, exp.targetingRules)) continue;

      const allocation = exp.trafficAllocation.find((a) => bucket >= a.rangeStart && bucket < a.rangeEnd);
      if (allocation) {
        results.push({
          experimentId: exp.id,
          groupId: allocation.groupId,
          bucket,
        });
      }
    }
  }

  return results;
}
配置下发与 SDK 设计
实验配置的下发链路直接影响实验的时效性和用户体验。两种主要的下发模式：


Pull 模式：客户端定期拉取最新的实验配置。实现简单，但存在延迟——如果拉取间隔为 5 分钟，紧急停止实验最多需要等 5 分钟才能生效。


Push 模式：服务端主动推送配置变更。实时性好，但需要维护长连接，增加了服务端的复杂度。


实际中常用的是混合模式：启动时全量拉取 + 运行时增量推送 + 定期全量同步兜底。

SDK 设计的关键考量：


    

  • 本地缓存：缓存最近的分组结果，避免网络请求阻塞页面渲染
    • 

  • 默认值策略：配置拉取失败时使用预设的默认值（通常为对照组）
    • 

  • 曝光日志：只有当用户实际看到了实验变体时才记录曝光，避免意图分配（intent-to-treat）与实际曝光（as-treated）的偏差
    • 

  • 批量上报：事件先缓存在本地，批量上报以减少网络请求
    •

数据管道与质量保障
从用户行为到实验报告，数据需要经过收集、传输、清洗、聚合和存储等多个环节。每个环节都可能引入误差，数据质量是实验结论可靠性的基础。

SRM（Sample Ratio Mismatch） 是最重要的数据质量检查。如果实验设计为 50/50 分组，但实际观测到 51/49，这可能是随机波动；但如果观测到 55/45，则几乎可以确定存在技术问题（如某个分组的用户更容易触发事件、或分流逻辑有 bug）。通过卡方检验可以精确判断样本比例偏差是否显著。


小结
    

  • 实验平台的核心组件包括分流引擎、配置中心、SDK、数据管道和分析引擎
    • 

  • 分流引擎需要满足确定性、正交性和灵活性三个要求
    • 

  • 配置下发推荐混合模式：启动全量拉取 + 运行时增量推送 + 定期兜底同步
    • 

  • SDK 设计需关注本地缓存、默认值策略、曝光日志和批量上报
    • 

  • SRM 检查是最关键的数据质量验证，样本比例异常通常意味着技术问题
    • 

  • 数据管道的每个环节都可能引入误差，端到端的质量检查不可或缺
    •
