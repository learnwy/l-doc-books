Feature Flag 系统

核心概念

Feature Flag（特性开关）是一种将代码部署与功能发布解耦的软件工程技术。它允许在不重新部署代码的情况下，动态地开启或关闭某个功能。在 A/B 测试场景中，Feature Flag 是实验分流的执行层——实验平台决定用户属于哪个分组，Feature Flag 系统负责根据分组结果展示不同的功能版本。Feature Flag 的价值远不止于实验：它还支持渐进式发布、灰度测试、紧急回滚、运维开关等多种场景。

Feature Flag 的实现架构
一个生产级 Feature Flag 系统包含三个核心模块：规则引擎、配置存储和评估 SDK。


规则引擎定义了 Feature Flag 的评估逻辑。一个 Flag 的规则通常包含多个条件层次：默认值 → 定向规则（targeting rules）→ 百分比灰度（percentage rollout）。评估顺序从上到下，第一个匹配的规则决定最终结果。


interface FeatureFlag {
  key: string;
  defaultValue: boolean | string | number;
  rules: EvaluationRule[];
  enabled: boolean;
}

interface EvaluationRule {
  id: string;
  conditions: Condition[];
  serve: FlagValue;
  percentage?: number;
}

interface Condition {
  attribute: string;
  operator: 'eq' | 'neq' | 'in' | 'gt' | 'lt' | 'regex';
  value: unknown;
}

function evaluateFlag(flag: FeatureFlag, context: UserContext): FlagValue {
  if (!flag.enabled) return flag.defaultValue;

  for (const rule of flag.rules) {
    if (matchAllConditions(rule.conditions, context)) {
      if (rule.percentage !== undefined) {
        const bucket = hash(`${flag.key}_${context.userId}`) % 100;
        if (bucket < rule.percentage) {
          return rule.serve;
        }
      } else {
        return rule.serve;
      }
    }
  }

  return flag.defaultValue;
}
与实验平台的集成
Feature Flag 系统和实验平台之间的集成方式决定了实验的工程效率和数据准确性。两种主要的集成模式：


松耦合模式：实验平台和 Feature Flag 系统独立运行。实验平台负责分组决策，将结果通过 API 或配置同步给 Feature Flag 系统。这种模式灵活但存在配置同步延迟和一致性风险。


紧耦合模式：实验平台内置 Feature Flag 能力，或反过来 Feature Flag 系统内置实验分流能力。分组和配置下发在同一个系统中完成，一致性更好。LaunchDarkly、Optimizely 等商业工具采用这种模式。

集成中的关键注意事项：


曝光一致性：用户的分组结果和实际看到的功能版本必须一致。如果实验平台将用户分到实验组，但 Feature Flag 因缓存问题仍展示对照组版本，就会产生数据偏差。


分组稳定性：在实验运行期间，用户的分组不应因为 Feature Flag 规则变更而改变。如果需要调整灰度比例，应该使用"只增不减"策略——新增的用户进入实验组，已有的对照组用户不受影响。


清理机制：实验结束后，相关的 Feature Flag 必须及时清理（移除条件判断代码，保留最终方案的代码）。长期积累的废弃 Flag 会增加代码复杂度和潜在 bug。


渐进式发布策略
Feature Flag 支持多种渐进式发布策略，每种策略在风险控制和发布速度之间有不同的权衡：


百分比灰度：最常用的方式。从 1% → 5% → 20% → 50% → 100% 逐步放量。每个阶段观察核心指标是否正常，异常时立即回滚。


金丝雀发布（Canary Release）：先在一小批用户（通常是内部员工或低风险用户）上验证，确认无问题后再扩大范围。


环形发布（Ring-based Rollout）：Microsoft 使用的模式——Ring 0（开发团队）→ Ring 1（内部员工）→ Ring 2（早期采用者）→ Ring 3（全量用户）。每一环都是一个验证门槛。

Feature Flag 的治理与技术债
Feature Flag 是一把双刃剑。它带来了部署灵活性，但每个 Flag 都增加了代码的条件分支复杂度。如果不加以治理，大量废弃的 Flag 会形成严重的技术债。


治理策略包括：


生命周期管理：每个 Flag 创建时就设定预期的清理日期。超期未清理的 Flag 自动触发告警。


所有权归属：每个 Flag 必须有明确的 Owner（通常是创建人或其团队）。Owner 负责在 Flag 完成使命后清理代码。


命名规范：统一的命名前缀帮助区分 Flag 类型。例如 exp_ 前缀表示实验开关，ops_ 前缀表示运维开关，release_ 前缀表示发布开关。


定期审计：每季度审查所有活跃的 Flag，清理已完成的实验 Flag 和不再需要的发布 Flag。

小结
    

  • Feature Flag 将代码部署与功能发布解耦，是实验分流的执行层
    • 

  • 开关类型包括发布、实验、运维和权限四种，各有不同的生命周期
    • 

  • 规则引擎按优先级匹配条件，支持定向投放和百分比灰度
    • 

  • 与实验平台的集成需要确保曝光一致性和分组稳定性
    • 

  • 渐进式发布策略在风险控制和发布速度之间做权衡
    • 

  • Flag 治理是防止技术债的关键，需要生命周期管理和定期审计
