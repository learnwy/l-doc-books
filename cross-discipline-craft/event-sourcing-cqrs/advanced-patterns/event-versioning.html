事件版本化

核心概念

事件溯源系统中的事件是不可变的——一旦写入就永远不会被修改。但产生和消费这些事件的代码却在不断演进。当业务需求变化导致事件的数据结构需要改变时，如何在不破坏历史事件的前提下安全升级？这就是事件版本化要解决的核心问题。

事件版本化的核心原则是永远不修改已有事件的含义。已存在的事件代表了历史事实，改变其含义等同于篡改历史。所有的版本演进都必须保持对历史事件的正确理解。


向上转换器
向上转换器（Upcaster）是事件版本化的核心工具。它在读取事件时动态地将旧版本转换为新版本，使消费者代码只需处理最新版本的事件格式。


interface Upcaster {
  readonly eventType: string;
  readonly fromVersion: number;
  readonly toVersion: number;
  upcast(data: Record<string, unknown>): Record<string, unknown>;
}

class UpcasterChain {
  private upcasters: Map<string, Upcaster[]> = new Map();

  register(upcaster: Upcaster): void {
    const key = upcaster.eventType;
    const chain = this.upcasters.get(key) ?? [];
    chain.push(upcaster);
    chain.sort((a, b) => a.fromVersion - b.fromVersion);
    this.upcasters.set(key, chain);
  }

  upcast(
    eventType: string,
    data: Record<string, unknown>,
    currentVersion: number,
  ): { data: Record<string, unknown>; version: number } {
    const chain = this.upcasters.get(eventType);
    if (!chain) return { data, version: currentVersion };

    let result = { ...data };
    let version = currentVersion;

    for (const upcaster of chain) {
      if (upcaster.fromVersion === version) {
        result = upcaster.upcast(result);
        version = upcaster.toVersion;
      }
    }

    return { data: result, version };
  }
}

const orderCreatedUpcasters: Upcaster[] = [
  {
    eventType: 'OrderCreated',
    fromVersion: 1,
    toVersion: 2,
    upcast: (data) => ({
      ...data,
      currency: 'CNY',
      source: 'web',
    }),
  },
  {
    eventType: 'OrderCreated',
    fromVersion: 2,
    toVersion: 3,
    upcast: (data) => ({
      ...data,
      shippingAddress: data.address ?? null,
      billingAddress: data.address ?? null,
    }),
  },
];
向上转换的执行时机有两种选择：读取时转换（Lazy Upcasting）在每次读取事件时实时转换，简单但有运行时开销；写入时转换（Eager Upcasting）在后台批量将旧事件转换为新版本写入新流，一次性开销但后续零成本。


弱 Schema 策略
弱 Schema 是最简单的版本化策略——不显式管理版本号，而是通过宽容的反序列化和可选字段来兼容不同版本的事件。


interface WeakSchemaDeserializer<T> {
  deserialize(raw: Record<string, unknown>): T;
}

interface OrderCreatedData {
  readonly customerId: string;
  readonly items: ReadonlyArray<OrderItem>;
  readonly totalAmount: number;
  readonly currency: string;
  readonly source: string;
  readonly shippingAddress: Address | null;
}

const createOrderCreatedDeserializer = (): WeakSchemaDeserializer<OrderCreatedData> => ({
  deserialize(raw) {
    return {
      customerId: raw.customerId as string,
      items: raw.items as ReadonlyArray<OrderItem>,
      totalAmount: raw.totalAmount as number,
      currency: (raw.currency as string) ?? 'CNY',
      source: (raw.source as string) ?? 'unknown',
      shippingAddress: (raw.shippingAddress as Address) ?? (raw.address as Address) ?? null,
    };
  },
});

const createVersionAwareEventReader = (
  eventStore: EventStore,
  upcasterChain: UpcasterChain,
  deserializers: Map<string, WeakSchemaDeserializer<unknown>>,
) => ({
  async readAndDeserialize<T>(streamId: string, eventType: string): Promise<ReadonlyArray<T>> {
    const events = await eventStore.readStream(streamId);
    const deserializer = deserializers.get(eventType);
    if (!deserializer) throw new Error(`No deserializer for ${eventType}`);

    return events
      .filter((e) => e.eventType === eventType)
      .map((e) => {
        const raw = JSON.parse(e.data.toString()) as Record<string, unknown>;
        const version = ((e.metadata as Record<string, unknown>).schemaVersion as number) ?? 1;
        const { data } = upcasterChain.upcast(eventType, raw, version);
        return deserializer.deserialize(data) as T;
      });
  },
});
弱 Schema 的优势是简单——不需要维护版本号和升级链。但它的隐患在于：当字段语义发生变化（例如 amount 从分变为元）时，宽容的反序列化会静默地产生错误数据。因此，弱 Schema 适合小团队、事件类型少的早期系统，复杂系统应采用显式版本化。


多版本共存管理
在大型系统中，可能存在数十种事件类型，每种都有多个版本。需要一个系统化的方法来管理版本注册、兼容性检查和升级链。


interface EventVersionRegistry {
  registerVersion(eventType: string, version: number, schema: EventSchema, upcaster?: Upcaster): void;

  getCurrentVersion(eventType: string): number;
  getSchema(eventType: string, version: number): EventSchema | undefined;
  getUpcastChain(eventType: string, fromVersion: number): ReadonlyArray<Upcaster>;
}

interface EventSchema {
  readonly version: number;
  readonly fields: ReadonlyArray<{
    name: string;
    type: string;
    required: boolean;
    defaultValue?: unknown;
  }>;
}

const createEventVersionRegistry = (): EventVersionRegistry => {
  const schemas = new Map<string, Map<number, EventSchema>>();
  const upcasters = new Map<string, Upcaster[]>();

  return {
    registerVersion(eventType, version, schema, upcaster) {
      if (!schemas.has(eventType)) schemas.set(eventType, new Map());
      schemas.get(eventType)!.set(version, schema);
      if (upcaster) {
        if (!upcasters.has(eventType)) upcasters.set(eventType, []);
        upcasters.get(eventType)!.push(upcaster);
      }
    },

    getCurrentVersion(eventType) {
      const versions = schemas.get(eventType);
      if (!versions) return 0;
      return Math.max(...versions.keys());
    },

    getSchema(eventType, version) {
      return schemas.get(eventType)?.get(version);
    },

    getUpcastChain(eventType, fromVersion) {
      const chain = upcasters.get(eventType) ?? [];
      return chain.filter((u) => u.fromVersion >= fromVersion).sort((a, b) => a.fromVersion - b.fromVersion);
    },
  };
};




版本管理实践
说明





每个事件类型独立版本
不同事件类型的版本号互不影响




只增不减
版本号只递增，不能跳过或回退




升级链完整
从任意历史版本都能升级到最新版本




写入标注版本
写入时在 metadata 中标注当前版本号




测试覆盖
每个升级步骤都有对应的单元测试





版本管理的黄金法则：新增字段给默认值，语义变更创建新事件类型，不要删除已有字段。如果必须做破坏性变更，优先选择创建新事件类型（如 OrderCreatedV2），这比复杂的升级链更简单可靠。


小结
    

  • 向上转换器在读取时将旧版本事件动态升级为新版本，使消费者只需处理最新格式
    • 

  • 升级链必须完整：从任意历史版本都能通过链式转换升级到最新版本
    • 

  • 弱 Schema 通过宽容反序列化处理版本差异，适合早期系统，复杂系统应采用显式版本化
    • 

  • 版本管理的黄金法则：新增给默认值、语义变更创建新事件类型、不删除已有字段
    • 

  • 每个升级步骤都应有单元测试覆盖，确保历史事件能正确升级
    • 

  • 破坏性变更优先选择创建新事件类型而非复杂的升级链
