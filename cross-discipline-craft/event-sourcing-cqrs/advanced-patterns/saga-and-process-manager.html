Saga 与流程管理器

核心概念

在事件溯源系统中，每个命令只修改一个聚合——这是保证一致性边界的核心原则。但真实业务常常需要跨多个聚合的协调操作：下单需要同时处理订单、库存和支付。Saga 模式通过一系列本地事务和补偿操作来实现跨聚合的最终一致性，替代了传统的分布式事务。

Saga 的核心思想是"前进或补偿"：每个步骤要么成功执行，要么执行对应的补偿操作来撤销已完成步骤的影响。与分布式事务的"全有或全无"不同，Saga 在执行过程中会经历中间状态——这就是为什么 Saga 提供的是最终一致性而非强一致性。


编排式 Saga
编排式 Saga（Orchestration）由一个中央协调器（Orchestrator）控制整个流程。协调器本身就是一个事件溯源的聚合，维护流程的当前状态，并根据接收到的事件决定下一步操作。


interface SagaStep<TContext> {
  readonly name: string;
  execute(context: TContext): Promise<Command>;
  compensate(context: TContext): Promise<Command>;
}

interface SagaDefinition<TContext> {
  readonly sagaType: string;
  readonly steps: ReadonlyArray<SagaStep<TContext>>;
}

type SagaStatus = 'running' | 'completed' | 'compensating' | 'failed';

interface SagaState<TContext> {
  readonly sagaId: string;
  readonly sagaType: string;
  readonly status: SagaStatus;
  readonly currentStep: number;
  readonly context: TContext;
  readonly completedSteps: ReadonlyArray<string>;
  readonly startedAt: Date;
}

const createOrderFulfillmentSaga = (): SagaDefinition<OrderFulfillmentContext> => ({
  sagaType: 'OrderFulfillment',
  steps: [
    {
      name: 'ReserveInventory',
      execute: (ctx) =>
        Promise.resolve({
          type: 'ReserveInventory',
          aggregateId: ctx.inventoryId,
          items: ctx.items,
          orderId: ctx.orderId,
        } as Command),
      compensate: (ctx) =>
        Promise.resolve({
          type: 'ReleaseInventory',
          aggregateId: ctx.inventoryId,
          items: ctx.items,
          orderId: ctx.orderId,
        } as Command),
    },
    {
      name: 'ProcessPayment',
      execute: (ctx) =>
        Promise.resolve({
          type: 'ChargePayment',
          aggregateId: ctx.paymentId,
          amount: ctx.totalAmount,
          orderId: ctx.orderId,
        } as Command),
      compensate: (ctx) =>
        Promise.resolve({
          type: 'RefundPayment',
          aggregateId: ctx.paymentId,
          amount: ctx.totalAmount,
          orderId: ctx.orderId,
        } as Command),
    },
    {
      name: 'ConfirmOrder',
      execute: (ctx) =>
        Promise.resolve({
          type: 'ConfirmOrder',
          aggregateId: ctx.orderId,
        } as Command),
      compensate: (ctx) =>
        Promise.resolve({
          type: 'RejectOrder',
          aggregateId: ctx.orderId,
          reason: 'Saga compensation',
        } as Command),
    },
  ],
});
编排器的优势在于流程可见性——所有业务逻辑集中在一处，容易理解和修改。当需要添加新步骤或改变执行顺序时，只需修改 Saga 定义，无需改动参与者。


协调式 Saga
协调式 Saga（Choreography）没有中央控制器，每个参与者监听事件并自主决定下一步操作。流程通过事件链隐式编排。


interface SagaParticipant {
  readonly participantName: string;
  readonly subscribedEvents: ReadonlyArray<string>;
  handle(event: DomainEvent): Promise<Command | null>;
}

const createInventoryParticipant = (): SagaParticipant => ({
  participantName: 'InventoryService',
  subscribedEvents: ['OrderCreated', 'PaymentFailed'],

  async handle(event) {
    switch (event.eventType) {
      case 'OrderCreated': {
        const payload = event.payload as OrderCreatedPayload;
        return {
          type: 'ReserveInventory',
          aggregateId: `inventory-${payload.items[0].productId}`,
          items: payload.items,
          orderId: event.aggregateId,
          timestamp: new Date(),
          commandId: crypto.randomUUID(),
        };
      }
      case 'PaymentFailed': {
        const payload = event.payload as PaymentFailedPayload;
        return {
          type: 'ReleaseInventory',
          aggregateId: `inventory-${payload.orderId}`,
          orderId: payload.orderId,
          timestamp: new Date(),
          commandId: crypto.randomUUID(),
        };
      }
      default:
        return null;
    }
  },
});

const createPaymentParticipant = (): SagaParticipant => ({
  participantName: 'PaymentService',
  subscribedEvents: ['InventoryReserved'],

  async handle(event) {
    if (event.eventType === 'InventoryReserved') {
      const payload = event.payload as InventoryReservedPayload;
      return {
        type: 'ChargePayment',
        aggregateId: `payment-${payload.orderId}`,
        amount: payload.totalAmount,
        orderId: payload.orderId,
        timestamp: new Date(),
        commandId: crypto.randomUUID(),
      };
    }
    return null;
  },
});
协调式 Saga 的优势是松耦合——参与者只依赖事件契约，不依赖中央协调器。但随着流程复杂度增加，事件链的调试和理解变得困难，且难以实现条件分支和并行步骤。


状态机实现
将 Saga 建模为状态机是最稳健的实现方式。每个状态有明确的允许转换，非法转换被拒绝，使得流程行为完全可预测。


interface SagaStateMachine<TState extends string, TEvent extends string> {
  readonly currentState: TState;
  transition(event: TEvent): TState | null;
  getAllowedEvents(): ReadonlyArray<TEvent>;
}

type OrderSagaState =
  | 'created'
  | 'inventory_reserved'
  | 'payment_processed'
  | 'confirmed'
  | 'compensating_payment'
  | 'compensating_inventory'
  | 'failed';

type OrderSagaEvent =
  | 'InventoryReserved'
  | 'InventoryFailed'
  | 'PaymentProcessed'
  | 'PaymentFailed'
  | 'OrderConfirmed'
  | 'PaymentRefunded'
  | 'InventoryReleased';

const orderSagaTransitions: Record<OrderSagaState, Partial<Record<OrderSagaEvent, OrderSagaState>>> = {
  created: {
    InventoryReserved: 'inventory_reserved',
    InventoryFailed: 'failed',
  },
  inventory_reserved: {
    PaymentProcessed: 'payment_processed',
    PaymentFailed: 'compensating_inventory',
  },
  payment_processed: {
    OrderConfirmed: 'confirmed',
  },
  compensating_inventory: {
    InventoryReleased: 'failed',
  },
  compensating_payment: {
    PaymentRefunded: 'compensating_inventory',
  },
  confirmed: {},
  failed: {},
};

const createSagaStateMachine = (initialState: OrderSagaState): SagaStateMachine<OrderSagaState, OrderSagaEvent> => {
  let currentState = initialState;

  return {
    get currentState() {
      return currentState;
    },
    transition(event) {
      const nextState = orderSagaTransitions[currentState][event];
      if (!nextState) return null;
      currentState = nextState;
      return currentState;
    },
    getAllowedEvents() {
      return Object.keys(orderSagaTransitions[currentState]) as OrderSagaEvent[];
    },
  };
};
状态机保证了 Saga 不会进入非法状态——只有预定义的转换才会被执行。结合事件溯源，Saga 的每次状态变迁都作为事件持久化，崩溃后可以从事件流中重建精确的状态。


小结
    

  • Saga 通过本地事务 + 补偿操作实现跨聚合的最终一致性，替代分布式事务
    • 

  • 编排式 Saga 由中央协调器控制，适合复杂业务流程，提供集中的可见性
    • 

  • 协调式 Saga 通过事件链实现松耦合，适合简单链式流程
    • 

  • 状态机建模保证 Saga 不会进入非法状态，结合事件溯源实现崩溃恢复
    • 

  • 补偿操作必须是幂等的，因为补偿本身也可能失败并被重试
    • 

  • 选择编排还是协调取决于流程复杂度——超过 3 个步骤或有条件分支时优先考虑编排式
    •
