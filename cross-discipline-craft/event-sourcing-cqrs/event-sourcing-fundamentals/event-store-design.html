事件存储设计

核心概念

事件存储（Event Store）是事件溯源架构的基础设施核心——它是所有事件的持久化层，承担着"系统记忆"的角色。与传统数据库存储当前状态不同，事件存储只做一件事：按顺序追加和读取事件。这种简单的语义使得事件存储的设计可以针对追加写入进行深度优化。

事件存储的核心 API 极其精简：写入（Append）、按流读取（Read Stream）、全局读取（Read All）和订阅（Subscribe）。这种极简接口背后是对事件溯源特定访问模式的深度优化。


事件流结构
事件流（Event Stream）是事件存储中的基本组织单元，通常与聚合实例一一对应。每个流包含一个有序的事件序列，通过流标识符（Stream ID）进行寻址。


interface EventStream {
  readonly streamId: string;
  readonly events: ReadonlyArray<PersistedEvent>;
  readonly currentVersion: number;
}

interface PersistedEvent {
  readonly eventId: string;
  readonly streamId: string;
  readonly eventType: string;
  readonly version: number;
  readonly globalPosition: bigint;
  readonly timestamp: Date;
  readonly data: Uint8Array;
  readonly metadata: Uint8Array;
}

interface EventStore {
  appendToStream(streamId: string, events: ReadonlyArray<NewEvent>, expectedVersion: number): Promise<AppendResult>;

  readStream(streamId: string, fromVersion?: number, count?: number): Promise<ReadonlyArray<PersistedEvent>>;

  readAll(fromPosition?: bigint, count?: number): Promise<ReadonlyArray<PersistedEvent>>;

  subscribe(fromPosition: bigint, handler: (event: PersistedEvent) => Promise<void>): Subscription;
}
流命名约定通常采用 {聚合类型}-{聚合ID} 的格式，例如 order-f47ac10b 或 account-550e8400。部分事件存储支持按前缀分类（Category），允许订阅某一类聚合的所有事件——这对构建跨聚合的读模型至关重要。


每个事件同时拥有两个位置标识：流内版本号（Stream Version，从 1 开始递增）和全局位置（Global Position，跨所有流的单调递增序号）。流内版本号用于乐观并发控制，全局位置用于构建全局有序的投影。


追加写入与并发控制
事件存储的写操作只有一种：追加（Append）。这种仅追加的特性使得写入路径可以做到极致优化——类似日志文件的顺序写入，无需随机 I/O。


type AppendResult =
  | { success: true; nextExpectedVersion: number }
  | { success: false; error: 'WrongExpectedVersion'; currentVersion: number };

const appendWithRetry = async (
  store: EventStore,
  streamId: string,
  buildEvents: (currentVersion: number) => ReadonlyArray<NewEvent>,
  maxRetries = 3,
): Promise<AppendResult> => {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const existingEvents = await store.readStream(streamId);
    const currentVersion = existingEvents.length;
    const newEvents = buildEvents(currentVersion);
    const result = await store.appendToStream(streamId, newEvents, currentVersion);
    if (result.success) {
      return result;
    }
  }
  throw new Error(`Failed to append after ${maxRetries} retries`);
};
乐观并发控制的语义很简单：追加时传入预期版本号（Expected Version），如果当前流的实际版本号与预期不符，说明有并发写入，操作被拒绝。调用方需要重新加载事件流、重新应用业务逻辑，然后再次尝试追加。


对于不需要并发保护的场景（如日志型事件流），可以使用 ExpectedVersion.Any 跳过版本检查，允许无条件追加。


分区策略
当事件存储的数据量增长到单节点无法承载时，需要引入分区（Partitioning）策略。事件流的天然独立性使得按聚合 ID 分区成为最自然的选择。


interface PartitionedEventStore {
  readonly partitions: ReadonlyArray<EventStorePartition>;

  resolvePartition(streamId: string): EventStorePartition;
}

const createHashPartitioner = (partitions: ReadonlyArray<EventStorePartition>): PartitionedEventStore => {
  const resolvePartition = (streamId: string): EventStorePartition => {
    const hash = fnv1aHash(streamId);
    const index = hash % partitions.length;
    return partitions[index];
  };

  return { partitions, resolvePartition };
};

const createCategoryPartitioner = (
  categoryMap: Map<string, EventStorePartition>,
  defaultPartition: EventStorePartition,
): PartitionedEventStore => {
  const resolvePartition = (streamId: string): EventStorePartition => {
    const category = streamId.split('-')[0];
    return categoryMap.get(category) ?? defaultPartition;
  };

  return {
    partitions: [...categoryMap.values(), defaultPartition],
    resolvePartition,
  };
};

分区后最大的挑战是全局有序性。单个分区内的事件顺序可以保证，但跨分区的全局顺序需要额外的协调机制——通常通过引入全局序号生成器或基于时间戳的近似排序来解决。


存储引擎实现
基于关系型数据库实现事件存储是最常见的起步方案。PostgreSQL 的 JSONB 支持和 NOTIFY/LISTEN 机制使其成为理想的事件存储底层。


const createPostgresEventStore = (pool: Pool): EventStore => {
  const appendToStream = async (
    streamId: string,
    events: ReadonlyArray<NewEvent>,
    expectedVersion: number,
  ): Promise<AppendResult> => {
    const client = await pool.connect();
    try {
      await client.query('BEGIN');
      const { rows } = await client.query(
        'SELECT MAX(version) as current_version FROM events WHERE stream_id = $1 FOR UPDATE',
        [streamId],
      );
      const currentVersion = rows[0].current_version ?? 0;
      if (currentVersion !== expectedVersion) {
        await client.query('ROLLBACK');
        return { success: false, error: 'WrongExpectedVersion', currentVersion };
      }
      for (let i = 0; i < events.length; i++) {
        const event = events[i];
        await client.query(
          `INSERT INTO events (event_id, stream_id, event_type, version, data, metadata)
           VALUES ($1, $2, $3, $4, $5, $6)`,
          [
            event.eventId,
            streamId,
            event.eventType,
            expectedVersion + i + 1,
            JSON.stringify(event.data),
            JSON.stringify(event.metadata),
          ],
        );
      }
      await client.query('COMMIT');
      return { success: true, nextExpectedVersion: expectedVersion + events.length };
    } finally {
      client.release();
    }
  };

  return {
    appendToStream,
    readStream: createReadStream(pool),
    readAll: createReadAll(pool),
    subscribe: createSubscription(pool),
  };
};
表结构设计的关键是将 (stream_id, version) 设为唯一约束——这在数据库层面保证了乐观并发控制的正确性，即使应用层的版本检查存在竞态条件，数据库约束也能兜底。


小结
    

  • 事件存储的核心职责是追加写入和有序读取，API 极其精简
    • 

  • 事件流是基本组织单元，每个事件拥有流内版本号和全局位置两个坐标
    • 

  • 乐观并发控制通过预期版本号防止并发冲突，失败时需要重新加载并重试
    • 

  • 分区策略需要根据业务特点选择：哈希分区适合均匀负载，类别分区适合业务隔离
    • 

  • 基于 PostgreSQL 实现事件存储是最实用的起步方案，(stream_id, version) 唯一约束是并发安全的最后防线
    • 

  • 追加写入的特性使得事件存储可以利用顺序 I/O 获得极高的写入吞吐量
