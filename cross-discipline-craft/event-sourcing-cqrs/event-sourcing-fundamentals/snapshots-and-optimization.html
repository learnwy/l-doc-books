快照与性能优化

核心概念

事件溯源中，聚合的当前状态通过重放全部历史事件计算得到。当一个聚合积累了数千甚至数万个事件时，每次加载都从头重放会带来显著的延迟。快照（Snapshot）是解决这一问题的核心手段——定期将聚合的中间状态持久化，后续重建只需从最近的快照开始重放之后的增量事件。

快照机制的核心权衡是存储空间 vs 重放时间。快照过于频繁会消耗大量存储和写入带宽，过于稀疏则重放时间过长。实践中通常采用基于事件数量的阈值策略——每积累 N 个新事件后生成一个新快照。


快照策略设计
快照策略决定了何时创建快照、如何存储快照以及如何利用快照加速重建。一个完整的快照机制需要与事件存储协同工作。


interface Snapshot<TState> {
  readonly aggregateId: string;
  readonly version: number;
  readonly state: TState;
  readonly timestamp: Date;
}

interface SnapshotStore<TState> {
  save(snapshot: Snapshot<TState>): Promise<void>;
  load(aggregateId: string): Promise<Snapshot<TState> | undefined>;
}

interface SnapshotPolicy {
  shouldSnapshot(currentVersion: number, lastSnapshotVersion: number): boolean;
}

const createIntervalPolicy = (interval: number): SnapshotPolicy => ({
  shouldSnapshot: (currentVersion, lastSnapshotVersion) => currentVersion - lastSnapshotVersion >= interval,
});

const createCompositePolicy = (policies: ReadonlyArray<SnapshotPolicy>): SnapshotPolicy => ({
  shouldSnapshot: (currentVersion, lastSnapshotVersion) =>
    policies.some((p) => p.shouldSnapshot(currentVersion, lastSnapshotVersion)),
});
将快照集成到聚合仓储层，对上层代码完全透明：


class SnapshotAwareRepository<TState> {
  constructor(
    private readonly eventStore: EventStore,
    private readonly snapshotStore: SnapshotStore<TState>,
    private readonly policy: SnapshotPolicy,
    private readonly rehydrate: (state: TState, events: ReadonlyArray<PersistedEvent>) => TState,
    private readonly initialState: TState,
  ) {}

  async load(aggregateId: string): Promise<{ state: TState; version: number }> {
    const snapshot = await this.snapshotStore.load(aggregateId);
    const fromVersion = snapshot ? snapshot.version + 1 : 0;
    const events = await this.eventStore.readStream(aggregateId, fromVersion);
    const baseState = snapshot?.state ?? this.initialState;
    const state = this.rehydrate(baseState, events);
    const version = snapshot ? snapshot.version + events.length : events.length;

    return { state, version };
  }

  async save(
    aggregateId: string,
    newEvents: ReadonlyArray<NewEvent>,
    expectedVersion: number,
    currentState: TState,
  ): Promise<void> {
    await this.eventStore.appendToStream(aggregateId, newEvents, expectedVersion);
    const newVersion = expectedVersion + newEvents.length;
    const snapshot = await this.snapshotStore.load(aggregateId);
    const lastSnapshotVersion = snapshot?.version ?? 0;

    if (this.policy.shouldSnapshot(newVersion, lastSnapshotVersion)) {
      await this.snapshotStore.save({
        aggregateId,
        version: newVersion,
        state: currentState,
        timestamp: new Date(),
      });
    }
  }
}
快照存储可以独立于事件存储，使用更适合随机读写的存储引擎（如 Redis 或 DynamoDB）。快照数据本质上是缓存——即使所有快照丢失，系统仍然可以通过重放事件完整恢复。


事件压缩
事件压缩（Event Compaction）通过合并或归档历史事件来减少事件流的长度。这与快照不同——快照保留所有原始事件，压缩则会永久移除部分事件。


interface CompactionStrategy {
  compact(events: ReadonlyArray<PersistedEvent>): ReadonlyArray<PersistedEvent>;
}

const createFoldCompaction = (foldableTypes: Set<string>): CompactionStrategy => ({
  compact(events) {
    const result: PersistedEvent[] = [];
    const foldBuffer = new Map<string, PersistedEvent>();

    for (const event of events) {
      if (foldableTypes.has(event.eventType)) {
        foldBuffer.set(event.eventType, event);
      } else {
        if (foldBuffer.size > 0) {
          result.push(...foldBuffer.values());
          foldBuffer.clear();
        }
        result.push(event);
      }
    }
    if (foldBuffer.size > 0) {
      result.push(...foldBuffer.values());
    }
    return result;
  },
});

const createArchiveCompaction = (
  eventStore: EventStore,
  archiveStore: EventStore,
  cutoffVersion: number,
): CompactionStrategy => ({
  compact(events) {
    const toArchive = events.filter((e) => e.version <= cutoffVersion);
    const toKeep = events.filter((e) => e.version > cutoffVersion);
    return toKeep;
  },
});
事件压缩需要格外谨慎——它会丢失历史细节。在金融、医疗等对审计有严格要求的领域，事件压缩通常不可接受。压缩前必须确保所有依赖原始事件的投影已经处理完毕，否则投影重建时会因缺少事件而产生错误。


读取性能优化
除了快照和压缩，还有多种策略可以优化事件溯源系统的读取性能。


class AggregateCache<TState> {
  private cache: Map<string, { state: TState; version: number; lastAccess: number }>;
  private readonly maxSize: number;
  private readonly ttlMs: number;

  constructor(maxSize = 1000, ttlMs = 60_000) {
    this.cache = new Map();
    this.maxSize = maxSize;
    this.ttlMs = ttlMs;
  }

  get(aggregateId: string): { state: TState; version: number } | undefined {
    const entry = this.cache.get(aggregateId);
    if (!entry) return undefined;
    if (Date.now() - entry.lastAccess > this.ttlMs) {
      this.cache.delete(aggregateId);
      return undefined;
    }
    entry.lastAccess = Date.now();
    return { state: entry.state, version: entry.version };
  }

  set(aggregateId: string, state: TState, version: number): void {
    if (this.cache.size >= this.maxSize) {
      this.evictOldest();
    }
    this.cache.set(aggregateId, { state, version, lastAccess: Date.now() });
  }

  private evictOldest(): void {
    let oldestKey = '';
    let oldestTime = Infinity;
    for (const [key, entry] of this.cache) {
      if (entry.lastAccess < oldestTime) {
        oldestTime = entry.lastAccess;
        oldestKey = key;
      }
    }
    if (oldestKey) this.cache.delete(oldestKey);
  }
}

const createCachedRepository = <TState>(
  repository: SnapshotAwareRepository<TState>,
  cache: AggregateCache<TState>,
  eventStore: EventStore,
  rehydrate: (state: TState, events: ReadonlyArray<PersistedEvent>) => TState,
): { load: (id: string) => Promise<{ state: TState; version: number }> } => ({
  async load(aggregateId: string) {
    const cached = cache.get(aggregateId);
    if (cached) {
      const newEvents = await eventStore.readStream(aggregateId, cached.version + 1);
      if (newEvents.length === 0) return cached;
      const state = rehydrate(cached.state, newEvents);
      const version = cached.version + newEvents.length;
      cache.set(aggregateId, state, version);
      return { state, version };
    }
    const result = await repository.load(aggregateId);
    cache.set(aggregateId, result.state, result.version);
    return result;
  },
});

内存缓存与快照的协作方式是：缓存命中时只需加载从缓存版本到最新版本的增量事件；缓存未命中时回退到快照 + 增量事件的方式。这种分层策略确保了在各种场景下都能获得合理的性能表现。


小结
    

  • 快照通过缓存聚合中间状态将重建开销从 O(N) 降低到 O(N-S)，S 为快照点
    • 

  • 基于事件数量的间隔策略是最常用的快照触发方式，通常每 100-500 个事件创建一次
    • 

  • 快照本质上是缓存，丢失后可通过完整重放恢复，不影响数据完整性
    • 

  • 事件压缩通过合并冗余事件减少流长度，但会丢失历史细节，在审计敏感领域需谨慎使用
    • 

  • 内存缓存 + 快照 + 增量追赶的分层策略可以覆盖从热点访问到冷启动的全部场景
    • 

  • 所有优化都是在一致性、延迟、存储空间和实现复杂度之间做权衡
    •
