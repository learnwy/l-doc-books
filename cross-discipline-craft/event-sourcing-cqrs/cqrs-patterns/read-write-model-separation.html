读写模型分离

核心概念

读写模型分离是 CQRS 的核心实践——将系统的数据表示拆分为两个完全独立的模型：命令模型（Command Model / Write Model）负责处理所有写操作和业务规则验证，查询模型（Query Model / Read Model）负责响应所有查询请求。两个模型可以使用不同的数据结构、不同的存储引擎，甚至运行在不同的服务上。

命令模型和查询模型之间通过同步机制保持数据一致。同步方式可以是同步的（同一事务中更新两个模型）或异步的（通过事件/CDC 延迟同步）。异步方式引入了最终一致性，但获得了更好的性能和更高的可用性。


命令模型设计
命令模型的核心职责是维护业务不变量（Invariants）。它包含完整的领域逻辑，以聚合为单位进行事务保护。命令模型不需要为查询做任何妥协——它的数据结构完全服务于业务规则的表达和验证。


interface CommandHandler<TCommand extends Command> {
  handle(command: TCommand): Promise<CommandResult>;
}

class CreateOrderHandler implements CommandHandler<CreateOrderCommand> {
  constructor(
    private readonly repository: OrderRepository,
    private readonly inventoryService: InventoryService,
  ) {}

  async handle(command: CreateOrderCommand): Promise<CommandResult> {
    const inventoryCheck = await this.inventoryService.checkAvailability(command.items);
    if (!inventoryCheck.available) {
      return {
        success: false,
        error: `库存不足: ${inventoryCheck.unavailableItems.join(', ')}`,
      };
    }

    const order = OrderAggregate.create({
      customerId: command.customerId,
      items: command.items,
      shippingAddress: command.shippingAddress,
    });

    await this.repository.save(order);

    return {
      success: true,
      eventIds: order.getUncommittedEvents().map((e) => e.eventId),
    };
  }
}

class ConfirmOrderHandler implements CommandHandler<ConfirmOrderCommand> {
  constructor(private readonly repository: OrderRepository) {}

  async handle(command: ConfirmOrderCommand): Promise<CommandResult> {
    const order = await this.repository.load(command.orderId);
    if (!order) {
      return { success: false, error: '订单不存在' };
    }
    order.confirm(command.confirmedBy);
    await this.repository.save(order);
    return { success: true };
  }
}
命令处理器的模式非常统一：加载聚合 → 执行业务逻辑 → 保存状态变更。这种一致性使得命令处理层很容易编写中间件——验证中间件负责参数校验，授权中间件负责权限检查，重试中间件负责处理并发冲突。


查询模型设计
查询模型为读取请求量身定做——数据结构预先按查询维度组织，避免运行时的联表和计算。一个业务实体可以有多个查询模型，每个服务于不同的查询场景。


interface QueryHandler<TQuery extends Query, TResult> {
  handle(query: TQuery): Promise<TResult>;
}

interface OrderListQuery extends Query {
  readonly type: 'OrderList';
  readonly customerId?: string;
  readonly status?: string;
  readonly page: number;
  readonly pageSize: number;
}

interface OrderListResult {
  readonly items: ReadonlyArray<OrderListItem>;
  readonly total: number;
  readonly page: number;
  readonly pageSize: number;
}

class OrderListQueryHandler implements QueryHandler<OrderListQuery, OrderListResult> {
  constructor(private readonly readDb: ReadDatabase) {}

  async handle(query: OrderListQuery): Promise<OrderListResult> {
    const filters: Record<string, unknown> = {};
    if (query.customerId) filters.customerId = query.customerId;
    if (query.status) filters.status = query.status;

    const { items, total } = await this.readDb.query('order_list_view', {
      filters,
      offset: (query.page - 1) * query.pageSize,
      limit: query.pageSize,
      orderBy: { createdAt: 'desc' },
    });

    return { items: items as ReadonlyArray<OrderListItem>, total, page: query.page, pageSize: query.pageSize };
  }
}
查询模型的一个重要设计原则是反规范化（Denormalization）。与传统数据库设计追求的范式化相反，查询模型会将查询所需的所有数据冗余存储在同一张表或同一个文档中。例如，订单列表视图中直接存储客户名称而不是客户 ID——这样查询时无需联表。


独立存储策略
读写模型使用不同的存储引擎是 CQRS 的一个强大特性。写端使用保证事务安全的关系型数据库或事件存储，读端使用查询性能最优的存储引擎。


interface StorageTopology {
  writeStore: WriteStoreConfig;
  readStores: ReadonlyArray<ReadStoreConfig>;
  syncMechanism: SyncConfig;
}

const ecommerceTopology: StorageTopology = {
  writeStore: {
    type: 'event-store',
    engine: 'postgresql',
    purpose: '事件持久化 + 聚合重建',
  },
  readStores: [
    {
      type: 'document-db',
      engine: 'mongodb',
      views: ['order-detail', 'customer-profile'],
      purpose: '灵活文档查询',
    },
    {
      type: 'search-engine',
      engine: 'elasticsearch',
      views: ['product-search', 'order-search'],
      purpose: '全文搜索 + 聚合分析',
    },
    {
      type: 'cache',
      engine: 'redis',
      views: ['dashboard-summary', 'hot-products'],
      purpose: '高频热点数据',
    },
  ],
  syncMechanism: {
    type: 'event-driven',
    transport: 'kafka',
    guarantees: 'at-least-once',
  },
};

const createReadModelSynchronizer = (
  eventStore: EventStore,
  readStores: ReadonlyArray<ReadStoreUpdater>,
): EventSubscription => {
  return eventStore.subscribe(0n, async (event) => {
    const updatePromises = readStores.map((store) =>
      store.handleEvent(event).catch((error) => {
        console.error(`Failed to sync to ${store.name}:`, error);
      }),
    );
    await Promise.allSettled(updatePromises);
  });
};

选择读存储的核心原则是"查询模式决定存储引擎"。不要用同一种数据库勉强服务所有查询场景——全文搜索用 Elasticsearch，热点数据用 Redis，分析报表用 ClickHouse，各司其职。


小结
    

  • 命令模型以聚合为单位维护业务不变量，数据结构完全服务于业务规则
    • 

  • 查询模型通过反规范化为每种查询场景预先组织数据，避免运行时联表
    • 

  • 一个业务实体可以有多个查询模型，分别服务于列表、详情、搜索、分析等场景
    • 

  • 读写模型可以使用不同的存储引擎，"查询模式决定存储引擎"是选型核心原则
    • 

  • 读写模型通过事件驱动的异步同步机制保持最终一致，获得更好的性能和可用性
    • 

  • 反规范化是查询模型的常见策略，用存储冗余换取查询性能
    •
