Part II · 架构实践事件溯源与 CQRS 简介CQRS 模式 简介CQRS 基础

CQRS 基础

核心概念

CQRS（Command Query Responsibility Segregation，命令查询职责分离）是一种将数据的写操作（命令）和读操作（查询）拆分为两个独立模型的架构模式。传统的 CRUD 架构中，同一个模型既负责处理写入又负责响应查询，这在复杂系统中会导致模型臃肿、难以优化。CQRS 通过将读写职责彻底分离，让每一侧都能针对自己的需求进行独立优化。

CQRS 的理论根基来自 Bertrand Meyer 的命令查询分离（CQS）原则：一个方法要么改变状态（命令），要么返回结果（查询），绝不同时做两件事。CQRS 将这个方法级别的原则提升到了架构级别。


命令查询分离原则
CQS 原则在代码层面的体现非常直观：命令方法返回 void（只有副作用），查询方法是纯函数（只有返回值）。CQRS 将这个原则扩展到整个系统架构。


interface CommandBus {
  dispatch<TCommand extends Command>(command: TCommand): Promise<CommandResult>;
}

interface QueryBus {
  execute<TQuery extends Query, TResult>(query: TQuery): Promise<TResult>;
}

interface Command {
  readonly type: string;
  readonly aggregateId: string;
  readonly timestamp: Date;
}

interface Query {
  readonly type: string;
}

interface CommandResult {
  readonly success: boolean;
  readonly eventIds?: ReadonlyArray<string>;
  readonly error?: string;
}

const createCommandBus = (handlers: Map<string, CommandHandler>): CommandBus => ({
  async dispatch(command) {
    const handler = handlers.get(command.type);
    if (!handler) {
      return { success: false, error: `No handler for ${command.type}` };
    }
    return handler.handle(command);
  },
});

const createQueryBus = (handlers: Map<string, QueryHandler>): QueryBus => ({
  async execute(query) {
    const handler = handlers.get(query.type);
    if (!handler) {
      throw new Error(`No handler for ${query.type}`);
    }
    return handler.handle(query);
  },
});
命令总线和查询总线的分离不仅是代码组织的改善，更重要的是它为两条路径提供了不同的中间件栈。命令路径需要验证、授权、事务管理、事件发布；查询路径需要缓存、分页、权限过滤。统一的处理管道无法为两者都做到最优。


动机与收益
CQRS 不是银弹——它通过增加架构复杂度来换取特定场景下的显著收益。理解其适用的业务场景比掌握技术细节更为重要。


典型适用场景包括：读写比极度悬殊的系统（如社交平台，写入量远小于读取量）、读模型和写模型差异巨大的领域（如电商的商品管理 vs 商品搜索）、以及需要多种查询视图的复杂系统。

写模型包含完整的业务实体和不变量验证逻辑，而读模型则是为特定查询预先计算好的扁平化数据结构。订单列表视图不需要知道具体的收货地址，分析报表不需要知道每个订单的明细——各取所需。


适用场景评估
并非所有系统都需要 CQRS。对于简单的 CRUD 应用，引入 CQRS 会带来不必要的复杂度。评估是否需要 CQRS，可以从以下几个维度考量：

interface CqrsAssessment {
  readWriteRatio: number;
  modelDivergence: 'low' | 'medium' | 'high';
  scalingNeeds: 'uniform' | 'read-heavy' | 'write-heavy';
  queryComplexity: 'simple' | 'moderate' | 'complex';
  consistencyRequirement: 'strong' | 'eventual';
}

const assessCqrsViability = (
  assessment: CqrsAssessment,
): {
  recommendation: 'recommended' | 'consider' | 'avoid';
  reasons: ReadonlyArray<string>;
} => {
  const scores: number[] = [];
  scores.push(assessment.readWriteRatio > 10 ? 2 : assessment.readWriteRatio > 3 ? 1 : 0);
  scores.push(assessment.modelDivergence === 'high' ? 2 : assessment.modelDivergence === 'medium' ? 1 : 0);
  scores.push(assessment.scalingNeeds !== 'uniform' ? 2 : 0);
  scores.push(assessment.queryComplexity === 'complex' ? 2 : assessment.queryComplexity === 'moderate' ? 1 : 0);
  scores.push(assessment.consistencyRequirement === 'eventual' ? 1 : -1);

  const total = scores.reduce((a, b) => a + b, 0);
  if (total >= 6) return { recommendation: 'recommended', reasons: ['多维度评估显示高度适合'] };
  if (total >= 3) return { recommendation: 'consider', reasons: ['部分维度匹配，需权衡成本'] };
  return { recommendation: 'avoid', reasons: ['复杂度收益比不足'] };
};
CQRS 与事件溯源是天然的搭配，但二者并非绑定关系。CQRS 可以在没有事件溯源的系统中使用（写模型用传统 ORM，读模型用物化视图），事件溯源也可以在没有 CQRS 的系统中使用（读写共用事件流重建的状态）。


小结
    

  • CQRS 将写操作（命令）和读操作（查询）拆分为两个独立模型，各自针对性优化
    • 

  • 命令总线和查询总线分离，为两条路径提供不同的中间件栈
    • 

  • 适用于读写比悬殊、读写模型差异大、需要多种查询视图的复杂系统
    • 

  • CQRS 与事件溯源天然搭配但非绑定——两者可以独立使用
    • 

  • 对于简单 CRUD 应用，引入 CQRS 会带来不必要的复杂度，需要通过多维度评估决定是否采用
    • 

  • 最终一致性是 CQRS 架构的常见特征，如果业务严格要求强一致性，需要额外的设计处理
    •
