Part II · 架构实践事件溯源与 CQRS 简介CQRS 模式 简介最终一致性

最终一致性

核心概念

在 CQRS 架构中，命令模型和查询模型通过异步同步机制连接，这意味着写入操作完成后，读模型不会立即反映最新状态——存在一个时间窗口，在此期间系统处于"不一致"状态。这就是最终一致性（Eventual Consistency）：系统保证在没有新写入的情况下，所有读模型最终会收敛到与写模型一致的状态。

最终一致性不是"不一致"——它是一种明确的一致性保证：给定足够的时间和没有新的写入，系统将达到一致状态。在实践中，这个"最终"通常是毫秒到秒级别，而非分钟或小时。


不一致窗口管理
不一致窗口（Inconsistency Window）是写入完成到读模型更新完成之间的时间差。管理好这个窗口是最终一致性系统的核心挑战。


interface ConsistencyTracker {
  recordWrite(aggregateId: string, version: number): Promise<void>;
  checkConsistency(aggregateId: string, expectedVersion: number): Promise<ConsistencyStatus>;
}

type ConsistencyStatus =
  | { consistent: true }
  | { consistent: false; currentVersion: number; expectedVersion: number; lagMs: number };

const createConsistencyTracker = (readModelVersionStore: VersionStore): ConsistencyTracker => ({
  async recordWrite(aggregateId, version) {
    await readModelVersionStore.setExpectedVersion(aggregateId, version, Date.now());
  },

  async checkConsistency(aggregateId, expectedVersion) {
    const currentVersion = await readModelVersionStore.getCurrentVersion(aggregateId);
    if (currentVersion >= expectedVersion) {
      return { consistent: true };
    }
    const writeTimestamp = await readModelVersionStore.getWriteTimestamp(aggregateId);
    return {
      consistent: false,
      currentVersion,
      expectedVersion,
      lagMs: Date.now() - writeTimestamp,
    };
  },
});

const waitForConsistency = async (
  tracker: ConsistencyTracker,
  aggregateId: string,
  expectedVersion: number,
  timeoutMs = 5000,
  pollIntervalMs = 100,
): Promise<boolean> => {
  const deadline = Date.now() + timeoutMs;
  while (Date.now() < deadline) {
    const status = await tracker.checkConsistency(aggregateId, expectedVersion);
    if (status.consistent) return true;
    await new Promise((resolve) => setTimeout(resolve, pollIntervalMs));
  }
  return false;
};
在关键场景下（如用户刚创建订单后立即查看订单详情），可以使用"读己所写"（Read Your Own Writes）策略：命令完成后返回新版本号，查询时附带版本号要求，如果读模型尚未追赶到该版本则等待或回退到命令模型直接查询。


补偿机制
在最终一致性系统中，某些操作序列可能因为时序问题产生不期望的中间状态。补偿机制（Compensation）用于检测和修复这些不一致。


interface CompensationHandler {
  detect(event: DomainEvent): Promise<ReadonlyArray<Inconsistency>>;
  compensate(inconsistency: Inconsistency): Promise<void>;
}

interface Inconsistency {
  readonly type: string;
  readonly aggregateId: string;
  readonly description: string;
  readonly detectedAt: Date;
}

const createInventoryCompensation = (
  inventoryReadModel: InventoryReadModel,
  eventStore: EventStore,
): CompensationHandler => ({
  async detect(event) {
    if (event.eventType !== 'OrderCreated') return [];

    const payload = JSON.parse(event.data.toString()) as OrderCreatedPayload;
    const inconsistencies: Inconsistency[] = [];

    for (const item of payload.items) {
      const readModelStock = await inventoryReadModel.getStock(item.productId);
      const events = await eventStore.readStream(`inventory-${item.productId}`);
      const actualStock = recomputeStock(events);

      if (readModelStock !== actualStock) {
        inconsistencies.push({
          type: 'StockMismatch',
          aggregateId: `inventory-${item.productId}`,
          description: `读模型库存 ${readModelStock} 与实际 ${actualStock} 不一致`,
          detectedAt: new Date(),
        });
      }
    }
    return inconsistencies;
  },

  async compensate(inconsistency) {
    const events = await eventStore.readStream(inconsistency.aggregateId);
    const correctStock = recomputeStock(events);
    await inventoryReadModel.forceUpdate(inconsistency.aggregateId, correctStock);
  },
});
补偿机制通常以后台任务的形式运行，定期扫描或事件触发。关键是不一致被检测到时能够自动修复，并且修复过程本身是幂等的——重复执行不会产生额外的副作用。


用户体验处理
最终一致性对用户体验的影响是架构师必须重视的问题。用户提交了一个操作后立即看到旧数据，会产生"操作没生效"的错觉。以下是几种常用的 UX 策略：


interface OptimisticUpdateConfig {
  commandType: string;
  localStateTransform: (currentState: unknown, command: Command) => unknown;
  rollbackOnFailure: boolean;
}

const createOptimisticUpdater = (config: OptimisticUpdateConfig) => ({
  applyOptimistically(
    currentState: unknown,
    command: Command,
  ): {
    optimisticState: unknown;
    revert: () => unknown;
  } {
    const optimisticState = config.localStateTransform(currentState, command);
    return {
      optimisticState,
      revert: () => currentState,
    };
  },
});

interface PollingStrategy {
  initialDelayMs: number;
  maxAttempts: number;
  backoffMultiplier: number;
  condition: (response: unknown) => boolean;
}

const pollUntilConsistent = async <T>(queryFn: () => Promise<T>, strategy: PollingStrategy): Promise<T | null> => {
  let delay = strategy.initialDelayMs;
  for (let i = 0; i < strategy.maxAttempts; i++) {
    await new Promise((resolve) => setTimeout(resolve, delay));
    const result = await queryFn();
    if (strategy.condition(result)) return result;
    delay *= strategy.backoffMultiplier;
  }
  return null;
};

最佳实践是组合使用多种策略：对于用户"读己所写"的场景（如创建后查看详情）使用乐观更新或命令端直读；对于列表页等非关键场景接受短暂延迟；对于后台运营报表则直接标明数据延迟时间。


小结
    

  • 最终一致性意味着写入后读模型存在短暂的不一致窗口，通常为毫秒到秒级别
    • 

  • "读己所写"策略通过版本号追踪确保用户能看到自己刚刚提交的变更
    • 

  • 补偿机制以幂等方式自动检测和修复不一致，是系统可靠性的安全网
    • 

  • 用户体验处理需要组合多种策略：关键路径用乐观更新，非关键路径接受延迟
    • 

  • 最终一致性不是"不一致"，而是一种明确的保证——给定足够时间，系统必将收敛
    • 

  • 不一致窗口的大小取决于事件处理管道的延迟，优化管道性能可以缩小窗口
    •
