Part II · 架构实践事件溯源与 CQRS 简介实战应用 简介从 CRUD 迁移

从 CRUD 迁移

核心概念

将一个已有的 CRUD 系统迁移到事件溯源架构是一个高风险的工程决策。直接"大爆炸"式的全量重写几乎注定失败——业务不能停摆，数据不能丢失，团队需要逐步积累事件溯源的经验。渐进式迁移（Strangler Fig Pattern）是唯一可行的策略：新功能用事件溯源实现，旧功能逐步迁移，两套系统在过渡期内并行运行。

迁移的核心原则是始终保持系统可用——任何时刻都能回退到上一个稳定状态，不允许出现"两个系统都不工作"的中间态。


渐进式迁移策略
渐进式迁移的第一步不是修改现有代码，而是在旁路捕获状态变更。通过数据库触发器或 CDC（Change Data Capture），将 CRUD 操作转化为事件，写入事件存储。


interface MigrationPhase {
  readonly name: string;
  readonly readSource: 'crud' | 'event-sourcing' | 'both';
  readonly writeTarget: 'crud' | 'event-sourcing' | 'both';
  readonly rollbackPlan: string;
}

const migrationPhases: ReadonlyArray<MigrationPhase> = [
  {
    name: '旁路捕获',
    readSource: 'crud',
    writeTarget: 'crud',
    rollbackPlan: '停止 CDC 连接器，无影响',
  },
  {
    name: '双写验证',
    readSource: 'crud',
    writeTarget: 'both',
    rollbackPlan: '停止写入事件存储，清理事件数据',
  },
  {
    name: '影子读取',
    readSource: 'both',
    writeTarget: 'both',
    rollbackPlan: '切换读取回 CRUD',
  },
  {
    name: '事件优先',
    readSource: 'event-sourcing',
    writeTarget: 'both',
    rollbackPlan: '切换读取回 CRUD',
  },
  {
    name: '完全切换',
    readSource: 'event-sourcing',
    writeTarget: 'event-sourcing',
    rollbackPlan: '需要数据回填到 CRUD（紧急情况）',
  },
];

const createCDCEventCapture = (
  cdcSource: CDCSource,
  eventStore: EventStore,
  transformer: (change: DatabaseChange) => DomainEvent | null,
) => ({
  async start(): Promise<void> {
    cdcSource.onChange(async (change) => {
      const event = transformer(change);
      if (event) {
        await eventStore.appendToStream(event.aggregateId, [event], -1);
      }
    });
  },
});
旁路捕获阶段完全不影响现有系统——CDC 在数据库层面监听变更，将其转化为事件。如果 CDC 出问题，CRUD 系统毫无感知。这给团队提供了一个安全的学习和验证环境。


双写过渡
双写阶段是迁移的关键转折点——写操作同时写入 CRUD 数据库和事件存储，读操作仍然使用 CRUD 数据库。这个阶段的目的是验证事件存储的写入正确性。


interface DualWriteRepository<T> {
  save(entity: T): Promise<void>;
  findById(id: string): Promise<T | null>;
}

const createDualWriteRepository = <T extends { id: string }>(
  crudRepo: CrudRepository<T>,
  eventStore: EventStore,
  toEvents: (entity: T, previous: T | null) => ReadonlyArray<NewEvent>,
  consistencyChecker: ConsistencyChecker<T>,
): DualWriteRepository<T> => ({
  async save(entity) {
    const previous = await crudRepo.findById(entity.id);

    await crudRepo.save(entity);

    const events = toEvents(entity, previous);
    try {
      await eventStore.appendToStream(entity.id, events, -1);
    } catch (error) {
      console.error('事件存储写入失败（不影响主流程）:', error);
    }

    if (previous) {
      await consistencyChecker.schedule(entity.id);
    }
  },

  async findById(id) {
    return crudRepo.findById(id);
  },
});

interface ConsistencyChecker<T> {
  schedule(entityId: string): Promise<void>;
  verify(entityId: string): Promise<ConsistencyResult>;
}

const createConsistencyChecker = <T>(
  crudRepo: CrudRepository<T>,
  eventStore: EventStore,
  rehydrate: (events: ReadonlyArray<PersistedEvent>) => T,
  compare: (crud: T, es: T) => ReadonlyArray<string>,
): ConsistencyChecker<T> => ({
  async schedule(entityId) {
    setTimeout(async () => {
      const result = await this.verify(entityId);
      if (!result.consistent) {
        console.warn(`一致性检查失败 [${entityId}]:`, result.differences);
      }
    }, 5000);
  },

  async verify(entityId) {
    const crudEntity = await crudRepo.findById(entityId);
    const events = await eventStore.readStream(entityId);
    const esEntity = rehydrate(events);

    if (!crudEntity || !esEntity) {
      return { consistent: false, differences: ['实体缺失'] };
    }

    const differences = compare(crudEntity, esEntity);
    return {
      consistent: differences.length === 0,
      differences,
    };
  },
});
双写阶段的关键是一致性检查器——异步对比 CRUD 数据库和事件存储中的数据，发现不一致时记录并告警。这些不一致可能暴露转换逻辑的缺陷，修复后才能进入下一阶段。


数据回填
数据回填（Backfill）是将 CRUD 数据库中的存量数据转化为事件流的过程。这是迁移中最复杂的步骤之一——历史数据可能不完整，原始操作的时间和操作者信息可能已丢失。


interface BackfillConfig {
  readonly batchSize: number;
  readonly parallelism: number;
  readonly checkpoint: BackfillCheckpoint;
  readonly transformer: RecordToEventsTransformer;
}

interface RecordToEventsTransformer {
  transform(record: DatabaseRecord): ReadonlyArray<SyntheticEvent>;
}

interface SyntheticEvent extends NewEvent {
  readonly synthetic: true;
  readonly sourceTable: string;
  readonly sourceId: string;
  readonly originalTimestamp: Date | null;
}

const createBackfillRunner = (
  config: BackfillConfig,
  source: DatabaseSource,
  eventStore: EventStore,
): { run: () => Promise<BackfillResult> } => ({
  async run() {
    let processed = 0;
    let failed = 0;
    const startFrom = await config.checkpoint.getLastProcessedId();

    const batches = source.readBatches(startFrom, config.batchSize);

    for await (const batch of batches) {
      const results = await Promise.allSettled(
        batch.map(async (record) => {
          const events = config.transformer.transform(record);
          const streamId = `${record.tableName}-${record.id}`;
          await eventStore.appendToStream(streamId, events, -1);
          return record.id;
        }),
      );

      const succeeded = results.filter((r) => r.status === 'fulfilled');
      const failedResults = results.filter((r) => r.status === 'rejected');

      processed += succeeded.length;
      failed += failedResults.length;

      if (succeeded.length > 0) {
        const lastId = (succeeded[succeeded.length - 1] as PromiseFulfilledResult<string>).value;
        await config.checkpoint.save(lastId);
      }
    }

    return { processed, failed, completedAt: new Date() };
  },
});




回填挑战
应对策略





历史时间丢失
用 created_at 或 updated_at 近似




操作者未知
标记为 system-backfill




中间状态缺失
只能从最终状态生成合成事件




数据量大
分批处理 + 检查点续传




关联数据
按依赖顺序回填




数据不一致
先清洗再回填





回填生成的事件应被标记为合成事件（synthetic: true），与真实业务事件区分。合成事件的质量取决于源数据的完整性——如果 CRUD 系统没有记录操作历史，回填只能生成一个"创建"事件来表示当前状态，中间的变更历史将永久丢失。


小结
    

  • 渐进式迁移（Strangler Fig）是唯一可行的策略，避免大爆炸重写的风险
    • 

  • 旁路捕获阶段通过 CDC 在不影响现有系统的前提下学习和验证事件溯源
    • 

  • 双写阶段通过一致性检查器发现转换逻辑的缺陷，确保数据一致
    • 

  • 数据回填将存量数据转化为事件流，但历史细节可能因源数据不完整而丢失
    • 

  • 迁移的核心原则是"始终可用、始终可回退"——任何时刻都能安全回退到上一阶段
    • 

  • 回填事件应标记为合成事件，与真实业务事件区分
    •
