事件存储技术选型

核心概念

事件存储是事件溯源系统的基础设施核心，其选型直接影响系统的性能上限、运维复杂度和功能边界。市面上的方案分为三大阵营：专用事件存储数据库（如 EventStoreDB）、通用消息平台（如 Apache Kafka）、以及基于关系型数据库的自建方案（如 PostgreSQL）。每种方案的设计哲学和适用场景截然不同。

选型的核心考量因素是团队能力、系统规模和功能需求。没有"最好"的事件存储，只有"最适合"的。


EventStoreDB 深度分析
EventStoreDB 是唯一从底层专门为事件溯源设计的数据库。它的核心概念就是事件流——不需要任何映射层或适配器。


interface EventStoreDBClient {
  appendToStream(
    streamName: string,
    events: ReadonlyArray<EventData>,
    options?: AppendToStreamOptions,
  ): Promise<AppendResult>;

  readStream(streamName: string, options?: ReadStreamOptions): ReadableStream<ResolvedEvent>;

  subscribeToAll(options?: SubscribeToAllOptions): ReadableStream<ResolvedEvent>;

  subscribeToStream(streamName: string, options?: SubscribeToStreamOptions): ReadableStream<ResolvedEvent>;
}

const connectToEventStoreDB = (connectionString: string): EventStoreDBClient => {
  const client = EventStoreDBClient.connectionString(connectionString);
  return client;
};

const appendOrderEvent = async (
  client: EventStoreDBClient,
  orderId: string,
  event: OrderEvent,
  expectedRevision: bigint,
): Promise<void> => {
  const eventData = jsonEvent({
    type: event.eventType,
    data: event.payload,
    metadata: event.metadata,
  });

  await client.appendToStream(`order-${orderId}`, [eventData], {
    expectedRevision,
  });
};
EventStoreDB 的独特优势包括：按流类别订阅（$ce-order 可以订阅所有 order 开头的流）、内置的投影引擎（用 JavaScript 编写服务端投影）、以及竞争消费者（多个消费者实例自动负载均衡）。其劣势在于社区规模较小、运维经验不如传统数据库丰富。


Kafka 作为事件存储
Apache Kafka 的分区日志模型天然适合事件的追加写入和有序消费。但将 Kafka 用作事件存储需要解决几个关键差异：Kafka 不支持流级别的乐观并发控制，且分区而非流是基本的排序单元。


interface KafkaEventStore {
  appendToStream(streamId: string, events: ReadonlyArray<NewEvent>): Promise<void>;

  readStream(streamId: string): Promise<ReadonlyArray<PersistedEvent>>;
}

const createKafkaEventStore = (
  producer: KafkaProducer,
  consumer: KafkaConsumer,
  topicPrefix: string,
): KafkaEventStore => ({
  async appendToStream(streamId, events) {
    const topic = `${topicPrefix}.events`;
    const messages = events.map((event) => ({
      key: streamId,
      value: JSON.stringify({
        streamId,
        eventType: event.eventType,
        data: event.data,
        metadata: event.metadata,
        timestamp: Date.now(),
      }),
      headers: {
        'event-type': event.eventType,
        'stream-id': streamId,
      },
    }));

    await producer.send({ topic, messages });
  },

  async readStream(streamId) {
    const events: PersistedEvent[] = [];
    await consumer.subscribe({ topic: `${topicPrefix}.events` });

    return events.filter((e) => e.streamId === streamId);
  },
});
Kafka 的优势在于极高的吞吐量、成熟的运维生态和强大的消费者组机制。但它作为事件存储有固有的局限：无法按流读取（需要消费整个分区过滤），不支持乐观并发控制（需要外部机制），保留策略可能导致旧事件被清理。


PostgreSQL 自建方案
对于大多数初创项目，基于 PostgreSQL 自建事件存储是最务实的选择。团队对 PostgreSQL 的运维经验可以直接复用，且灵活的查询能力为调试和运维提供了极大便利。


const createPostgresSchema = `
  CREATE TABLE IF NOT EXISTS event_streams (
    stream_id VARCHAR(255) PRIMARY KEY,
    stream_type VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW()
  );

  CREATE TABLE IF NOT EXISTS events (
    global_position BIGSERIAL PRIMARY KEY,
    event_id UUID NOT NULL UNIQUE,
    stream_id VARCHAR(255) NOT NULL REFERENCES event_streams(stream_id),
    event_type VARCHAR(100) NOT NULL,
    stream_version INTEGER NOT NULL,
    data JSONB NOT NULL,
    metadata JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(stream_id, stream_version)
  );

  CREATE INDEX idx_events_stream_id ON events(stream_id, stream_version);
  CREATE INDEX idx_events_event_type ON events(event_type);
`;

const createPostgresSubscription = (
  pool: Pool,
  channel: string,
  handler: (event: PersistedEvent) => Promise<void>,
): { start: () => Promise<void>; stop: () => Promise<void> } => {
  let client: PoolClient | null = null;

  return {
    async start() {
      client = await pool.connect();
      await client.query(`LISTEN ${channel}`);
      client.on('notification', async (msg) => {
        if (msg.channel === channel && msg.payload) {
          const event = JSON.parse(msg.payload) as PersistedEvent;
          await handler(event);
        }
      });
    },
    async stop() {
      if (client) {
        await client.query(`UNLISTEN ${channel}`);
        client.release();
      }
    },
  };
};

PostgreSQL 方案的核心限制是订阅能力——NOTIFY/LISTEN 不保证消息不丢失，适合非关键路径的实时推送。对于关键投影，仍需使用轮询 + 检查点的方式。

选型不是一锤子买卖——从 PostgreSQL 起步，在系统成熟后根据实际瓶颈迁移到 EventStoreDB 或 Kafka，是很多成功项目的路径。关键是从第一天就设计好事件存储的抽象接口，使底层实现可替换。


小结
    

  • EventStoreDB 是唯一专为事件溯源设计的数据库，原生支持事件流、投影和竞争消费
    • 

  • Kafka 的高吞吐量适合大规模系统，但缺乏流级别的乐观并发和按流读取能力
    • 

  • PostgreSQL 自建方案最适合起步阶段，团队可以复用现有运维经验
    • 

  • 选型的核心是团队能力和系统规模，而非技术先进性
    • 

  • 无论选择哪种方案，从第一天就设计好事件存储抽象接口，为未来迁移预留空间
    • 

  • 从 PostgreSQL 起步 → 成长后按需迁移，是被验证的务实路径
