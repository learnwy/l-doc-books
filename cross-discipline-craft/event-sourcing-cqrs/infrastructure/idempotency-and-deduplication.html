Part II · 架构实践事件溯源与 CQRS 简介基础设施 简介幂等性与去重

幂等性与去重

核心概念

在分布式事件溯源系统中，消息传递失败和重试是常态而非异常。网络抖动、消费者崩溃重启、消息代理重新投递——这些场景都可能导致同一事件被处理多次。幂等性（Idempotency）保证同一操作执行一次和执行多次产生相同结果，是构建可靠事件处理管道的基石。

graph TB
    A[消息代理] --> |投递事件| B[消费者]
    B --> |处理成功| C[确认ACK]
    B --> |处理中崩溃| D[未确认]
    D --> |超时重投| A
    A --> |再次投递| B
    B --> |幂等处理| E[结果与首次相同]
投递语义 含义 重复风险 丢失风险 实现难度
At-most-once 最多一次 无 有 低
At-least-once 至少一次 有 无 中
Exactly-once 恰好一次 无 无 高

大多数消息系统提供的是 At-least-once 语义——消息至少被投递一次，但可能被投递多次。在此基础上，通过幂等消费者（Idempotent Consumer）实现应用层面的 Exactly-once 语义，是最实际的工程方案。

幂等消费者模式

幂等消费者的核心思路是记录已处理的事件标识，在处理前检查是否已经处理过。这种"先检查再处理"的模式需要与业务处理放在同一个事务中，否则检查和处理之间的间隙仍然可能导致重复。

interface IdempotentConsumer<T> {
  process(event: PersistedEvent): Promise<T | null>;
}

interface ProcessedEventStore {
  isProcessed(eventId: string, consumerId: string): Promise<boolean>;
  markProcessed(eventId: string, consumerId: string): Promise<void>;
}

const createIdempotentConsumer = <T>(
  consumerId: string,
  processedStore: ProcessedEventStore,
  handler: (event: PersistedEvent) => Promise<T>,
): IdempotentConsumer<T> => ({
  async process(event) {
    const alreadyProcessed = await processedStore.isProcessed(event.eventId, consumerId);
    if (alreadyProcessed) {
      return null;
    }

    const result = await handler(event);
    await processedStore.markProcessed(event.eventId, consumerId);
    return result;
  },
});

const createTransactionalIdempotentConsumer = <T>(
  consumerId: string,
  pool: Pool,
  handler: (event: PersistedEvent, client: PoolClient) => Promise<T>,
): IdempotentConsumer<T> => ({
  async process(event) {
    const client = await pool.connect();
    try {
      await client.query('BEGIN');

      const { rows } = await client.query(
        `SELECT 1 FROM processed_events 
         WHERE event_id = $1 AND consumer_id = $2 FOR UPDATE`,
        [event.eventId, consumerId],
      );

      if (rows.length > 0) {
        await client.query('ROLLBACK');
        return null;
      }

      const result = await handler(event, client);

      await client.query(
        `INSERT INTO processed_events (event_id, consumer_id, processed_at)
         VALUES ($1, $2, NOW())`,
        [event.eventId, consumerId],
      );

      await client.query('COMMIT');
      return result;
    } catch (error) {
      await client.query('ROLLBACK');
      throw error;
    } finally {
      client.release();
    }
  },
});

事务性幂等消费者将"检查是否处理过"、"执行业务逻辑"和"标记已处理"放在同一个数据库事务中。即使消费者在事务提交前崩溃，重启后事务会回滚，消息会被重新投递，不会产生部分处理的问题。

去重策略

去重不仅适用于事件消费端，命令端同样需要防止重复提交。不同场景下的去重策略各有权衡。

interface DeduplicationStrategy {
  isDuplicate(key: string): Promise<boolean>;
  record(key: string, ttlMs?: number): Promise<void>;
}

const createDatabaseDedup = (pool: Pool): DeduplicationStrategy => ({
  async isDuplicate(key) {
    const { rows } = await pool.query(`SELECT 1 FROM dedup_keys WHERE dedup_key = $1`, [key]);
    return rows.length > 0;
  },

  async record(key, ttlMs) {
    const expiresAt = ttlMs ? new Date(Date.now() + ttlMs) : null;
    await pool.query(
      `INSERT INTO dedup_keys (dedup_key, created_at, expires_at)
       VALUES ($1, NOW(), $2) ON CONFLICT DO NOTHING`,
      [key, expiresAt],
    );
  },
});

const createRedisDedup = (redis: RedisClient): DeduplicationStrategy => ({
  async isDuplicate(key) {
    const exists = await redis.exists(`dedup:${key}`);
    return exists === 1;
  },

  async record(key, ttlMs = 86_400_000) {
    await redis.set(`dedup:${key}`, '1', 'PX', ttlMs);
  },
});

const createBloomFilterDedup = (expectedItems: number, falsePositiveRate: number): DeduplicationStrategy => {
  const filter = createBloomFilter(expectedItems, falsePositiveRate);

  return {
    async isDuplicate(key) {
      return filter.mightContain(key);
    },
    async record(key) {
      filter.add(key);
    },
  };
};
去重策略 精确度 延迟 存储开销 适用场景
数据库唯一约束 精确 高 大 关键业务操作
Redis 键值 精确（TTL内） 低 中 高频率事件消费
Bloom Filter 近似（有假阳性） 极低 极小 海量数据初筛
乐观并发（版本号） 精确 低 无额外 聚合级别去重 
graph TB
    A[收到事件] --> B{Bloom Filter}
    B --> |可能存在| C{Redis 确认}
    C --> |确认存在| D[跳过处理]
    C --> |不存在| E[处理事件]
    B --> |一定不存在| E
    E --> F[记录到Redis]
    F --> G[异步写入DB]

分层去重策略将 Bloom Filter 作为第一层快速过滤（极低延迟），Redis 作为第二层精确确认，数据库作为最终的持久化记录。这种策略在高吞吐场景下可以将绝大部分重复消息在第一层就过滤掉。

Exactly-once 语义实现

真正的 Exactly-once 需要将消息消费和业务处理放在同一个原子操作中。Kafka 的事务性消费者提供了在 Kafka 生态内的 Exactly-once 保证。

interface ExactlyOnceProcessor {
  processWithTransaction(messages: ReadonlyArray<KafkaMessage>): Promise<void>;
}

const createExactlyOnceProcessor = (
  consumer: KafkaConsumer,
  producer: KafkaProducer,
  handler: (event: DomainEvent) => Promise<ReadonlyArray<DomainEvent>>,
): ExactlyOnceProcessor => ({
  async processWithTransaction(messages) {
    const transaction = await producer.transaction();

    try {
      for (const message of messages) {
        const event = JSON.parse(message.value?.toString() ?? '{}') as DomainEvent;
        const outputEvents = await handler(event);

        for (const outputEvent of outputEvents) {
          await transaction.send({
            topic: 'output-events',
            messages: [
              {
                key: outputEvent.aggregateId,
                value: JSON.stringify(outputEvent),
              },
            ],
          });
        }
      }

      await transaction.sendOffsets({
        consumerGroupId: 'my-group',
        topics: extractTopicPartitions(messages),
      });

      await transaction.commit();
    } catch (error) {
      await transaction.abort();
      throw error;
    }
  },
});

Kafka 事务将"提交消费偏移量"和"发送输出消息"绑定在同一个事务中。如果事务失败，消费偏移量不会提交，消息会被重新消费；输出消息也不会对下游可见。这实现了端到端的 Exactly-once 语义。

对于跨系统的场景（例如从 Kafka 消费后写入 PostgreSQL），无法使用 Kafka 事务，此时回退到幂等消费者 + At-least-once 的组合是最实际的方案。

小结

  root((幂等性与去重))
    幂等消费者
      先检查后处理
      事务性保护
      防止部分处理
    去重策略
      数据库唯一约束
      Redis键值TTL

    Exactly-once
      Kafka事务
      偏移量+消息原子

    分层架构
      快速过滤
      精确确认
      持久化记录
  • At-least-once + 幂等消费者是实现应用层 Exactly-once 的最实际方案
  • 事务性幂等消费者将检查、处理和标记放在同一事务中，防止部分处理问题
  • 分层去重策略（Bloom Filter → Redis → 数据库）在高吞吐场景下平衡了性能和精确度
  • Kafka 事务提供了 Kafka 生态内的端到端 Exactly-once 语义
  • 跨系统场景无法使用单一事务，需要回退到幂等消费者模式
  • 去重键的设计至关重要——通常使用 eventId 或 correlationId + sequenceNumber 的组合
