序列化与模式演进

核心概念

事件一旦写入事件存储就永久存在，而产生和消费事件的代码却在不断演化。序列化格式的选择和模式演进（Schema Evolution）策略决定了系统能否在不停机、不丢失历史数据的前提下持续进化。这是事件溯源系统在工程层面最具挑战性的问题之一。

向前兼容（Forward Compatibility）意味着旧代码能读取新格式的事件——旧版消费者忽略它不认识的字段。向后兼容（Backward Compatibility）意味着新代码能读取旧格式的事件——新版消费者为缺失的字段提供默认值。事件溯源系统必须同时保证两个方向的兼容性。


JSON 序列化策略
JSON 是事件溯源系统中最常用的序列化格式，因为它的可读性极大地降低了调试和运维成本。但缺乏强制 Schema 也意味着兼容性需要靠约定和纪律来保证。


interface EventSerializer {
  serialize(event: DomainEvent): Uint8Array;
  deserialize(data: Uint8Array, eventType: string): DomainEvent;
}

const createJsonEventSerializer = (upgraders: Map<string, EventUpgrader>): EventSerializer => ({
  serialize(event) {
    const envelope = {
      schemaVersion: event.metadata?.schemaVersion ?? 1,
      eventType: event.eventType,
      data: event.payload,
      metadata: event.metadata,
    };
    return new TextEncoder().encode(JSON.stringify(envelope));
  },

  deserialize(data, eventType) {
    const envelope = JSON.parse(new TextDecoder().decode(data)) as EventEnvelope;
    const upgrader = upgraders.get(eventType);

    let payload = envelope.data;
    let version = envelope.schemaVersion;

    if (upgrader) {
      const upgraded = upgrader.upgrade(payload, version);
      payload = upgraded.data;
      version = upgraded.version;
    }

    return {
      eventId: envelope.metadata?.eventId ?? '',
      aggregateId: envelope.metadata?.aggregateId ?? '',
      eventType,
      version: 0,
      timestamp: new Date(envelope.metadata?.timestamp ?? 0),
      payload,
      metadata: { ...envelope.metadata, schemaVersion: version },
    };
  },
});
JSON 序列化的安全演进规则：只增不删不改。可以添加新字段（给默认值），不要删除已有字段，不要改变字段的语义或类型。如果必须做破坏性变更，创建一个新的事件类型而不是修改现有的。


Protocol Buffers 与 Avro
对于性能敏感或大规模系统，Protocol Buffers（Protobuf）和 Apache Avro 提供了更紧凑的二进制编码和强制的 Schema 演进规则。


interface ProtobufEventSerializer {
  serialize(event: DomainEvent, schema: ProtobufSchema): Uint8Array;
  deserialize(data: Uint8Array, schema: ProtobufSchema): DomainEvent;
}

interface SchemaRegistry {
  register(eventType: string, schema: string): Promise<number>;
  getSchema(eventType: string, version: number): Promise<string>;
  getLatestSchema(eventType: string): Promise<{ schema: string; version: number }>;
  checkCompatibility(eventType: string, newSchema: string): Promise<CompatibilityResult>;
}

type CompatibilityResult = { compatible: true } | { compatible: false; errors: ReadonlyArray<string> };

const createSchemaRegistry = (store: SchemaStore): SchemaRegistry => ({
  async register(eventType, schema) {
    const existing = await store.getLatest(eventType);
    const version = existing ? existing.version + 1 : 1;
    await store.save(eventType, version, schema);
    return version;
  },

  async getSchema(eventType, version) {
    const result = await store.get(eventType, version);
    if (!result) throw new Error(`Schema not found: ${eventType} v${version}`);
    return result.schema;
  },

  async getLatestSchema(eventType) {
    const result = await store.getLatest(eventType);
    if (!result) throw new Error(`No schema for ${eventType}`);
    return { schema: result.schema, version: result.version };
  },

  async checkCompatibility(eventType, newSchema) {
    const existing = await store.getLatest(eventType);
    if (!existing) return { compatible: true };
    return validateCompatibility(existing.schema, newSchema);
  },
});

Schema Registry（模式注册中心）是生产系统中管理 Schema 演进的关键组件。它集中存储所有事件类型的 Schema 版本，在写入时验证新 Schema 与旧版本的兼容性，拒绝破坏性变更。Confluent Schema Registry 是 Kafka 生态中最成熟的实现。


向前兼容策略
向前兼容确保旧版消费者能够处理新版事件。核心原则是"忽略未知字段"——当旧代码遇到它不认识的字段时，安全地跳过而不是抛出错误。


interface ForwardCompatibleDeserializer {
  deserialize<T>(data: unknown, schema: ObjectSchema<T>): T;
}

interface ObjectSchema<T> {
  readonly fields: ReadonlyArray<FieldSchema>;
  readonly factory: (values: Record<string, unknown>) => T;
}

interface FieldSchema {
  readonly name: string;
  readonly type: 'string' | 'number' | 'boolean' | 'object' | 'array';
  readonly required: boolean;
  readonly defaultValue?: unknown;
}

const createForwardCompatibleDeserializer = (): ForwardCompatibleDeserializer => ({
  deserialize<T>(data: unknown, schema: ObjectSchema<T>): T {
    const raw = data as Record<string, unknown>;
    const values: Record<string, unknown> = {};

    for (const field of schema.fields) {
      if (field.name in raw) {
        values[field.name] = raw[field.name];
      } else if (field.required && field.defaultValue !== undefined) {
        values[field.name] = field.defaultValue;
      } else if (field.required) {
        throw new Error(`Missing required field: ${field.name}`);
      }
    }

    return schema.factory(values);
  },
});

const orderCreatedV1Schema: ObjectSchema<OrderCreatedV1> = {
  fields: [
    { name: 'customerId', type: 'string', required: true },
    { name: 'items', type: 'array', required: true },
    { name: 'totalAmount', type: 'number', required: true },
  ],
  factory: (v) => v as OrderCreatedV1,
};
这种宽容的反序列化策略是事件溯源系统长期演进的基石。新增的字段对旧消费者透明，旧消费者继续正常工作直到被逐步升级。


事件升级器
当事件 Schema 发生不兼容变更时，事件升级器（Event Upcaster）在读取时将旧版本事件动态转换为新版本格式。


interface EventUpgrader {
  upgrade(
    data: Record<string, unknown>,
    fromVersion: number,
  ): {
    data: Record<string, unknown>;
    version: number;
  };
}

const createChainedUpgrader = (
  steps: ReadonlyArray<{
    fromVersion: number;
    toVersion: number;
    transform: (data: Record<string, unknown>) => Record<string, unknown>;
  }>,
): EventUpgrader => ({
  upgrade(data, fromVersion) {
    let current = { ...data };
    let version = fromVersion;

    for (const step of steps) {
      if (step.fromVersion === version) {
        current = step.transform(current);
        version = step.toVersion;
      }
    }

    return { data: current, version };
  },
});

const orderCreatedUpgrader = createChainedUpgrader([
  {
    fromVersion: 1,
    toVersion: 2,
    transform: (data) => ({
      ...data,
      currency: data.currency ?? 'CNY',
      createdBy: data.createdBy ?? 'system',
    }),
  },
  {
    fromVersion: 2,
    toVersion: 3,
    transform: (data) => ({
      ...data,
      shippingMethod: data.shippingMethod ?? 'standard',
      estimatedDelivery: data.estimatedDelivery ?? null,
    }),
  },
]);
升级器是链式的——v1 事件经过 v1→v2 和 v2→v3 两步升级到达 v3 格式。新的升级步骤只需要处理相邻版本之间的差异，不需要考虑更早的版本。


小结
    

  • JSON 的可读性使其成为大多数事件溯源系统的首选序列化格式
    • 

  • 事件 Schema 演进的核心规则是"只增不删不改"，必须同时保证向前和向后兼容
    • 

  • Schema Registry 在写入时验证兼容性，是防止破坏性变更进入生产环境的安全网
    • 

  • 事件升级器在读取时将旧版本事件动态转换为新格式，支持链式多版本升级
    • 

  • 向前兼容的关键是"忽略未知字段"，让旧消费者安全地处理新版本事件
    • 

  • Protobuf 和 Avro 适合性能敏感或大规模系统，但增加了开发时的 Schema 管理成本
