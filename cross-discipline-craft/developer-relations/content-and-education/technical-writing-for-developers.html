面向开发者的技术写作

核心概念

Technical writing 是 DevRel 最 scalable 杠杆——一篇 well-crafted blog 可以被 10k+ 开发者读、3 年内仍带流量、被 retweet 数千次。但 dev-targeted writing 跟一般 marketing copy 截然不同——dev 看到 fluff 立即 detect 不诚实、看到错误代码立即关 tab、看到夸大数据立即丧失信任。一篇好的 dev-targeted blog 必须——技术正确（code 真的跑通、版本对得上）、structure 清晰（H2/H3 让人 skim）、honest（提 caveat、谈 trade-off）、actionable（读完能动手）。本节给 dev-writing 原则、structure 模板、editing process、SEO 与发布 channel。

类型 长度 主要受众 例
Quickstart 500-1500 字 New user "Hello world in 5 min"
Tutorial 2000-5000 字 Builder "Build chat with X"
How-to 800-2500 字 Builder（已知 X） "How to add auth to X"
Conceptual 1500-4000 字 Decision-maker "Understanding X 架构"
Case study 1500-3000 字 Decision-maker "How Y scaled with X"
Reference 长（API doc） All API reference
Opinion / thinkpiece 1500-3000 字 Influencer "Why X is wrong"

Diátaxis 框架

4 种 doc type（Daniele Procida 提出）：

关键差异：


    

  • Tutorial：目的"学"，hand-hold，linear。
    • 

  • How-to：目的"做"，假设知识，goal-oriented。
    • 

  • Reference：目的"查"，结构化，无 narrative。
    • 

  • Explanation：目的"懂"，narrative，无 step。
    • 



反模式：


    

  • 把 tutorial 写成 reference（dev 学不会）。
    • 

  • 把 reference 写成 tutorial（dev 查不到）。
    • 



写作原则
1. Lead with value：


    

  • 第一段必须告诉读者：读完能干什么。
    • 

  • 不要 fluffy intro "在这个 post-pandemic world..."。
    • 



2. Show, don't tell：


    

  • 代码 + 输出 > 描述。
    • 

  • 一个 working sample > 一段说明文字。
    • 



3. Honest about caveats：


    

  • "X works great for use case A, less so for B because Y"。
    • 

  • 反例："X is the best solution for everything"——dev 立即 trust 崩。
    • 



4. Active voice + short sentence：


    

  • "Configure X in step 3" > "Step 3 requires the configuration of X"。
    • 



5. Skim-able structure：


    

  • H2 / H3 多。
    • 

  • Code block + table + diagram 多。
    • 

  • 避免 wall of text。
    • 



6. Acknowledge prior art：


    

  • "Similar to X (link)，but with Y advantage"。
    • 

  • 不假装 invent。
    • 



7. End with next step：


    

  • 读完 → 试 sample → 加 community → buy。
    • 

  • 不要 dead end。
    • 



结构模板（Tutorial）
# Title (50 chars max, action-oriented)

## What you'll build
（1 段 + 截图 / GIF 看到最终成品）

## Prerequisites
- Node 18+
- A free X account

## Step 1: Setup
（含 code）

## Step 2: Add feature A
...

## Step N: Deploy
...

## Troubleshooting
| 错误 | 原因 | Fix |

## Next steps
- [Advanced tutorial](...)
- [Join Discord](...)

## Related docs
- ...
结构模板（Conceptual）
# Why X works the way it does

## Background
（问题起源）

## The naive approach (and why it fails)
（先讲 alternative）

## How X solves it
（核心 idea）

## The trade-offs
（caveat）

## Compared to alternatives Y, Z
（fair comparison）

## When to use X (and when not to)

## Further reading
SEO 写作（不牺牲 quality）
1. Title H1 含 main keyword：


    

  • "How to set up Stripe webhooks in Next.js" > "Webhooks 101"。
    • 



2. URL slug 短 + descriptive：


    

  • /blog/stripe-webhooks-nextjs > /blog/2024-01-stripe-tutorial-final-v2。
    • 



3. Meta description 150 字：


    

  • 第一段 condensed。
    • 



4. Internal link：


    

  • 引你 own docs / blog。
    • 



5. Code 在 page：


    

  • 不仅 image——dev 想 copy。
    • 

  • Google 可 index code。
    • 



6. 不堆砌 keyword：


    

  • "Stripe Stripe Stripe webhooks"——Google penalize + dev annoy。
    • 



7. Update 老 post：


    

  • Google 喜欢 fresh。
    • 

  • 一年 review 一次 top 10 post 更新版本。
    • 



Editing Process
1. First draft：自己 dump：


    

  • Don't edit while writing。
    • 

  • 1-3 小时一气写完。
    • 



2. 隔夜放置：


    

  • 不立即 edit。
    • 

  • 第二天看才 catch awkward。
    • 



3. Edit pass 1：structure：


    

  • H2 / H3 是否 logical？
    • 

  • 删 fluff paragraph。
    • 



4. Edit pass 2：sentence：


    

  • Active voice。
    • 

  • 砍长句。
    • 



5. Edit pass 3：code：


    

  • 在 fresh env 跑一遍。
    • 

  • 跟 final post 中代码对齐。
    • 



6. Edit pass 4：peer review：


    

  • 队友 / external dev 读。
    • 

  • 改 confusing 处。
    • 



7. Final pass：SEO + meta：


    

  • Title、description、tag。
    • 



Code Sample 在 Blog
1. 完整可跑：


    

  • 不是 pseudo code。
    • 

  • 不省"// initialize the client" 假设。
    • 



2. 短：


    

  • 一 block 不超 30 行。
    • 

  • 长 sample link to GitHub repo。
    • 



3. Comment 关键步：


    

  • 但不要 over-comment。
    • 



4. 标语言：


    

  • ts js Markdown syntax highlight。
    • 



5. 错误处理：


    

  • 真正 production code 含 try/catch 等。
    • 

  • 不简化掉关键 production concern。
    • 



Voice & Tone
Voice（who you are）：


    

  • DevRel 工程师写文章——you 是 working dev who happens to advocate。
    • 

  • 不 corporate "We at X believe..."。
    • 



Tone（per post）：


    

  • Tutorial：friendly + helpful。
    • 

  • Opinion piece：confident + measured。
    • 

  • Post-mortem：humble + transparent。
    • 



Adjust：


    

  • "I" vs "we" vs "you"——一篇文章保一致。
    • 

  • 不混 "I think" 和 "we recommend"。
    • 



发布 Channel
1. 公司 blog：


    

  • Primary。
    • 

  • SEO + brand。
    • 



2. Dev.to / Hashnode / Medium：


    

  • 重发或 cross-post。
    • 

  • 触达不同 audience。
    • 

  • Dev.to 对 dev 友好 SEO。
    • 



3. Substack / personal blog：


    

  • 一些 advocate own brand。
    • 

  • 对 audience 长尾。
    • 



4. Twitter thread：


    

  • 摘要核心 idea 6-10 tweet。
    • 

  • 链接 full post。
    • 



5. Reddit / HN：


    

  • 选 timing + subreddit submit。
    • 

  • 不要 self-promo 太频——会 ban。
    • 



6. LinkedIn：


    

  • For decision-maker post。
    • 



Cross-post Etiquette
Canonical URL：


    

  • HTML <link rel="canonical"> 指公司 blog。
    • 

  • 防 SEO duplicate penalty。
    • 



Wait time：


    

  • 公司 blog 先发 1-2 周再 cross-post。
    • 



Note 来源：


    

  • "Originally posted on X.com/blog"。
    • 



反模式
1. Marketing fluff：


    

  • "In today's fast-paced world..."——dev 立即跳过。
    • 



2. Hidden caveat：


    

  • 把 limitation 藏到末尾——不诚实。
    • 



3. Outdated code：


    

  • v1 syntax 但产品 v3——读者 get error。
    • 



4. Wall of text：


    

  • 一屏没 H2 / code / image。
    • 



5. 过度 SEO：


    

  • 关键词堆砌 readability 牺牲。
    • 



6. 没 "what next"：


    

  • 读完 dead end。
    • 



7. 不 link community：


    

  • 错失 retention。
    • 



实战 advice
1. 一周 1 篇 long-form：


    

  • 不要 burst 5 篇 then 1 月不写。
    • 

  • Consistent cadence > peak quality。
    • 



2. Edit 时间 = write 时间 × 2：


    

  • 1 小时 draft + 2 小时 edit。
    • 



3. Code review by engineer：


    

  • DevRel 写 code 不该自我 merge——engineer review。
    • 



4. Cross-post 但 canonical：


    

  • Reach 多 source 但 SEO concentrate。
    • 



5. Update top post quarterly：


    

  • Old top-3 post 季度 refresh。
    • 



6. 写自己用过的：


    

  • 没用过 build 一个 demo 再写。
    • 

  • 真实经验 reads through。
    • 



7. Track post performance：


    

  • View、scroll depth、conversion 看哪类 work。
    • 



Newsletter
Companion to blog：


    

  • 周 / 双周 1 期。
    • 

  • 摘要近期 blog + community highlight + roadmap teaser。
    • 



Tools：


    

  • Substack、Buttondown、ConvertKit、Mailchimp。
    • 



Cadence：


    

  • Reliable > frequent。
    • 

  • 月 1 期 better than 周 1 期 inconsistent。
    • 



Engagement metric：


    

  • Open rate（≥ 30% good for dev）。
    • 

  • Click-through（≥ 5% good）。
    • 



小结
Dev-targeted technical writing 是 DevRel 最 scalable 杠杆——一篇 well-crafted blog 可触达 10k+ 开发者持续 3 年带流量，但与 marketing copy 截然不同——dev detect fluff / 错代码 / 夸大立即丧失信任。一篇好 dev-targeted blog 必须 technical correct（code 跑通版本对）、structure 清晰（H2/H3 skim）、honest（caveat / trade-off）、actionable（动手）。Diátaxis 框架 4 种 doc type——tutorial 学习导向 hand-hold step-by-step、how-to 任务导向 goal-oriented recipe、reference 信息导向 API spec 结构化、explanation 理解导向 narrative concept why；反模式把 tutorial 写成 reference 学不会 / 把 reference 写成 tutorial 查不到。写作原则——lead with value 第一段说读完能干什么不要 fluffy intro、show don't tell 代码+输出 > 描述、honest about caveats 提 limitation、active voice + short sentence、skim-able structure H2/H3/code/table/diagram 多 避免 wall of text、acknowledge prior art "similar to X but Y" 不假装 invent、end with next step 不 dead end。结构模板 tutorial（what you'll build + prerequisites + step 1-N + troubleshooting + next steps + related）、conceptual（background + naive approach why fails + how X solves + trade-offs + compared to Y/Z + when to use + further reading）。SEO 写作——title H1 含 main keyword、URL slug 短 descriptive、meta description 150 字、internal link own docs/blog、code 在 page 不仅 image dev 想 copy + Google index code、不堆砌 keyword penalize + annoy、update 老 post Google 喜 fresh 季度 refresh top 10。Editing process——first draft 1-3h dump 不 edit while writing、隔夜放置第二天看 catch awkward、pass 1 structure H2/H3 logical 删 fluff、pass 2 sentence active voice 砍长句、pass 3 code fresh env 跑一遍对齐、pass 4 peer review 队友/external dev、final pass SEO+meta。Code sample——完整可跑不 pseudo / 不省 init / 短一 block ≤ 30 行长 link GitHub / comment 关键步不 over-comment / 标语言 syntax highlight / 真 production try/catch 不简化关键 concern。Voice & tone——voice working dev who happens to advocate 不 corporate "we believe"、tone tutorial friendly + opinion confident measured + post-mortem humble transparent、I vs we vs you 一文一致。发布 channel——公司 blog primary SEO+brand、dev.to/hashnode/medium 重发触达不同 audience、Substack/personal own brand 长尾、Twitter thread 6-10 tweet 摘要 + link、Reddit/HN timing+subreddit 不 self-promo 频 ban、LinkedIn decision-maker。Cross-post etiquette——canonical URL HTML link rel canonical 指公司 blog 防 SEO duplicate、wait 1-2 周再 cross-post、note 来源 "originally posted"。反模式——marketing fluff dev 跳过、hidden caveat 不诚实、outdated code v1 syntax v3 产品、wall of text 一屏无 H2/code/image、过度 SEO 关键词堆砌牺牲 readability、没 "what next" dead end、不 link community 错失 retention。Advice——一周 1 篇 long-form consistent cadence > peak quality、edit time = write time × 2、code review by engineer 不自我 merge、cross-post canonical 多 reach SEO concentrate、quarterly refresh top 3 post、写自己用过 没用过 build demo 再写、track post performance view/scroll depth/conversion。Newsletter companion to blog 周/双周 摘要 blog+community highlight+roadmap teaser tools Substack/Buttondown/ConvertKit/Mailchimp cadence reliable > frequent 月 1 better than 周 1 inconsistent metric open ≥30% click ≥5%。一个简单的检验：你能用 Diátaxis 4 种类型分类近期 10 篇 blog + 写 1 篇 honest tutorial 含 caveat + setup canonical URL 防 SEO penalty 吗？如果不能，technical writing 还需 practice。Technical writing 是 DevRel 的"印钞机"——做对让一篇 blog 持续 3 年带流量 + 信任 + signup，做不对沦为 marketing fluff dev 立即跳过。
