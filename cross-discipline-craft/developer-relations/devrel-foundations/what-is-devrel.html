什么是 DevRel

核心概念

DevRel = Developer Relations，是面向开发者群体的"非传统营销 + 技术教育 + 产品反馈"复合职能。它不是 Marketing（不写 ad copy）、不是 Pre-sales（不背 quota）、不是 Tech Support（不解 ticket）——它是开发者社群的"技术布道 + 教育 + 倾听"。三大支柱（Mary Thengvall 提出）——Advocate（向公司内部传达开发者诉求）、Educate（向开发者讲解产品技术）、Amplify（让开发者声音被外界听到）。本节给 DevRel 定义、起源、与其它职能边界、以及典型 DevRel 工程师一周时间分配。

角色 主要受众 KPI 与 DevRel 边界
Marketing 决策者 / 买家 MQL、SQL、品牌 awareness DevRel 不写 ad copy
Pre-sales Buyer 决策方 Closed-won deal DevRel 不背 quota
Tech Support 已签约客户 Ticket SLA、CSAT DevRel 不解 1-on-1 ticket
PMM 产品发布定位 GTM、launch 效果 DevRel 是 PMM 的执行手
DevRel 开发者社群 Activation、advocacy —

DevRel 起源

Sun Microsystems Java Evangelist (1996)：

  • James Gosling、Bill Joy 时代——Java 上市需要"传教士"。
  • 第一批 Title 叫 Evangelist——直译"传教士"。
  • 工作内容：写 white paper、跑 conference、教 enterprise 用 Java。

Microsoft Developer Evangelism (2000s)：

  • Steve Ballmer "Developers, developers, developers!" 2000 年的 PDC 视频成为 meme。
  • MSDN + Channel 9 + MVP program 是早期 DevRel 三支柱。

Google Developer Relations (2005)：

  • Don Dodge、Chris DiBona 把"DevRel"作为正式 title 用进 Google。
  • Google Developer Day、Google I/O 是 DevRel-driven event。
  • 此前更多叫 "Developer Evangelist" 或 "Developer Advocate"。

Stripe / Twilio (2010s)：

  • API-first 公司发现：开发者本身就是 buyer。
  • DevRel 不再是辅助——是核心获客通道（PLG 时代）。
  • 这一阶段 DevRel 工程化（API 文档、SDK 质量、quickstart 时间）。

Vercel / Supabase / Linear (2020s)：

  • DevRel 高度产品化——Lee Robinson、Guillermo Rauch 把 DevRel 做成"founder + advocate" 模式。
  • Twitter / X 是主战场——一条优秀的 thread 触达数十万 dev。
三大支柱（Three Pillars）
Advocate（向内倡导）：


    

  • 把开发者反馈带回公司——bug、feature request、DX 痛点。
    • 

  • 在 product review meeting 代表 dev voice。
    • 

  • 与 PM、engineering team 推进 fix / improvement。
    • 



Educate（向外教育）：


    

  • 写 tutorial、blog、文档、sample code。
    • 

  • 上 conference 讲 talk、做 workshop。
    • 

  • 维护 demo project、video series。
    • 



Amplify（双向放大）：


    

  • 帮 dev 讲他们用产品做的事（success story、case study）。
    • 

  • Retweet、feature 用户作品、邀请上 podcast。
    • 

  • 让 community member 也变成"二级 advocate"。
    • 



DevRel vs 邻近职能
DevRel vs Marketing：


    

  • Marketing：optimize for funnel conversion，message 精炼简化。
    • 

  • DevRel：optimize for 开发者信任，信息深度准确不夸大。
    • 

  • 协同：MQL 由 Marketing 负责，PQL（Product-Qualified Lead）由 DevRel 影响。
    • 



DevRel vs Pre-sales / Solutions Engineering：


    

  • Pre-sales：1-on-1，针对单 deal。
    • 

  • DevRel：1-to-many，针对 community。
    • 

  • 协同：DevRel 写的 sample code 被 SE 用作 demo。
    • 



DevRel vs Customer Support：


    

  • Support：reactive，响应已签约客户问题。
    • 

  • DevRel：proactive，写文档/教程减少 ticket 量。
    • 

  • 协同：DevRel 监听 support ticket 找出 doc gap。
    • 



DevRel vs Product Management：


    

  • PM：决定 build what。
    • 

  • DevRel：把外界声音 feed 进 PM 决策。
    • 

  • 协同：DevRel 不直接写 PRD，但是 PM 的 input source。
    • 



DevRel vs Engineering：


    

  • Engineering：build product。
    • 

  • DevRel：write code that uses product (sample, tutorial, demo)。
    • 

  • 协同：DevRel 是 engineering 的"first user"，发现 DX 问题。
    •

关键：Senior DevRel 一周可能只写 1-2 千字 production content + 30+ 条 community 回复 + 1 个 talk。"看起来 output 少"是常态——DevRel 是 craft + endurance 工作。


DevRel 与 PLG / Bottom-up
Product-Led Growth：


    

  • 产品本身是获客通道——free tier + self-serve onboarding。
    • 

  • DevRel 是 PLG 的"教育层"——把开发者从 awareness 推到 activation。
    • 

  • 例：Vercel 的 free tier + 优秀 quickstart = 大量 weekend hacker 转付费。
    • 



Bottom-up sales：


    

  • Dev 试用 → team 试用 → org 采购。
    • 

  • DevRel 影响第一步（dev 试用），不直接 close deal。
    • 

  • 常见 KPI：dev signup → activated → org adopt 漏斗每段转化率。
    • 



DevRel 的"看不见"难度
1. 度量难：


    

  • Reach（多少人看了）容易，influence（多少人因此用产品）难。
    • 

  • 多渠道 attribution——一个 dev 可能 看 talk → 读 blog → 用 sample → 才 sign up。
    • 



2. ROI 长尾：


    

  • 一篇好 tutorial 可能持续 3 年带流量。
    • 

  • 也可能花 30 小时只有 1k 阅读。
    • 

  • 早期投入大、收益滞后。
    • 



3. 跨职能 stakeholder 多：


    

  • Marketing 想 dictate message。
    • 

  • Engineering 觉得 DevRel "不写 production code"。
    • 

  • Sales 想 DevRel 帮 close deal。
    • 



DevRel 工程师画像
Technical baseline：


    

  • 真实 production 工程经验（≥ 3 年）。
    • 

  • 能 code 出可读 sample（不是 toy demo）。
    • 

  • 跟 framework / language / cloud 演进。
    • 



Communication：


    

  • Written：blog、tutorial、tweet、PR description。
    • 

  • Spoken：talk、workshop、podcast。
    • 

  • Listen：community 回复、bug triage。
    • 



Empathy + Patience：


    

  • 对开发者 frustration 有 patience。
    • 

  • Toxic / entitled user 也能 keep professional。
    • 



Self-direction：


    

  • 没有 ticket queue 给你 follow——自己定 priority。
    • 



不是 DevRel 的几件事
1. 不是 "免费 marketing"：


    

  • 一些公司把 DevRel 当 cheap 替代 marketing——失败。
    • 

  • DevRel 的 content 必须 technical depth + 真实工程价值。
    • 



2. 不是 "技术 sales"：


    

  • 不背 quota。
    • 

  • 不 push 产品给不合适用户——会 lose 信任。
    • 



3. 不是 "教程工厂"：


    

  • 写文档很重要，但只写文档 = doc writer。
    • 

  • DevRel 还要 community + advocacy + product input。
    • 



4. 不是 "twitter celebrity"：


    

  • Follower 数不是 KPI。
    • 

  • Influence + signal 才是 KPI。
    • 



反模式
1. 招"演讲明星"忽略 craft：


    

  • 上台漂亮但写不出 working sample。
    • 

  • 长期 community 信任崩塌。
    • 



2. KPI 只 count activity：


    

  • "本季度发了 12 篇 blog"——不知 impact。
    • 

  • 必须配 outcome metric (signup、activation)。
    • 



3. DevRel "向 Marketing 汇报"无 product input channel：


    

  • 失去 advocate 支柱——退化为 content marketing。
    • 



4. 单 advocate 撑全公司：


    

  • 一两个人无法 cover 全 portfolio。
    • 

  • 早期可，规模化后必须建团队。
    • 



实战 advice
1. 先有 1-2 个产品再招 DevRel：


    

  • 没产品 → 没东西讲。
    • 

  • DevRel 最早合适 product-market-fit 之后。
    • 



2. DevRel 第一员工：senior advocate：


    

  • 招过资深的——能定义角色、招后续团队。
    • 

  • 而不是 entry-level evangelist。
    • 



3. 给 DevRel 真实 product input channel：


    

  • 直 report 给 CTO 或 VPE 或 product 副总。
    • 

  • 不要嵌在 marketing org 深处。
    • 



4. 度量配 outcome：


    

  • 上层 OKR：dev activation rate。
    • 

  • Activity（content count、event count）只 leading indicator。
    • 



5. 早期 founder-led DevRel 最有效：


    

  • 创始人 tweet、写 blog、上 podcast。
    • 

  • 后期再 scale 团队。
    • 



DevRel as Career
Path 1：Senior IC：


    

  • Principal Developer Advocate / Distinguished Advocate。
    • 

  • 类似 Senior Staff engineer 的 IC track。
    • 



Path 2：Manager：


    

  • DevRel Manager → Director → VP DevRel。
    • 

  • 管 5-50 人 advocacy 团队。
    • 



Path 3：转 PM / Founder：


    

  • DevRel 给 product instinct——许多 advocate 后转 PM 或创业。
    • 

  • 例：Vercel CEO Guillermo Rauch（开源 advocacy 起家）。
    • 



Skill ladder：


    

  • Junior：write tutorial、attend event。
    • 

  • Senior：design content strategy、lead community。
    • 

  • Principal：define DevRel for company、cross-org influence。
    • 



小结
DevRel = Developer Relations，是面向开发者社群的 advocate / educate / amplify 三支柱复合职能——不是 Marketing（不写 ad copy）、不是 Pre-sales（不背 quota）、不是 Tech Support（不解 1-on-1 ticket）、不是 PMM（不做 GTM positioning）但是是 PMM 执行手。起源 Sun 1996 Java Evangelist → Microsoft 2000 DevEvangelism → Google 2005 formalize → Stripe/Twilio 2010 API-first PLG-driven → Vercel/Supabase 2020 founder-led 模式。三支柱——advocate 向内（带开发者反馈到 product review）、educate 向外（写 tutorial / 上 talk / 维护 sample）、amplify 双向（feature 用户作品、retweet、邀 podcast）。与邻近职能边界——Marketing optimize funnel vs DevRel optimize 信任、Pre-sales 1-on-1 vs DevRel 1-to-many、Support reactive vs DevRel proactive、PM 决定 build what vs DevRel feed input、Engineering build vs DevRel "first user" 发现 DX 问题。典型一周——30% 写作 + 15% 内部会议 + 20% community + 15% 演讲准备 + 10% 出差 + 10% 学习 code，senior DevRel 一周 1-2k 字 + 30 条回复 + 1 talk 就是良好 output。PLG / bottom-up 时代——产品 free tier + DevRel 教育层 + dev signup → team → org 漏斗，DevRel 影响第一步。"看不见"难度——度量难（reach 易 influence 难 attribution 多渠道）、ROI 长尾（一篇 tutorial 持续 3 年 vs 30h 1k 阅读）、跨职能 stakeholder 多（Marketing dictate / Engineering 看轻 / Sales push close）。工程师画像——technical baseline ≥3y production 经验 + 写 readable sample、written + spoken + listen communication、empathy + patience（toxic user 也 professional）、self-direction（无 ticket queue 自己定 priority）。不是 DevRel——不是免费 marketing（必须 technical depth）、不是技术 sales（不 push 不合适用户）、不是教程工厂（还要 community + advocacy）、不是 Twitter celebrity（influence ≠ follower）。反模式——演讲明星无 craft、KPI 只 count activity、向 Marketing 汇报失去 advocate 支柱、单 advocate 撑全公司。Advice——先有 product-market-fit 再招 DevRel、第一员工 senior advocate 不要 entry-level、给真实 product input channel direct report CTO/VPE、度量配 outcome activation rate、早期 founder-led 最有效。Career path——senior IC track Principal Advocate / Manager track DevRel Director / 转 PM 或创业 founder（Vercel CEO 起家 OSS advocacy）。一个简单的检验：你能向 CFO 解释 DevRel 不是 Marketing 也不是 Sales 而值得每年 $5M 投入吗？如果不能，DevRel 定义还需 practice。DevRel 是开发者时代企业获客与产品反馈的"双向 bridge"——做对让产品借开发者群体复利增长，做不对沦为表面热闹的 content factory。
