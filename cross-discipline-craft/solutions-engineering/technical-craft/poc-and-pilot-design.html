POC 与 pilot 设计

核心概念

POC（Proof of Concept）与 pilot 是 deal 的"决战点"——30 至 90 天的试点期里，客户工程师亲手用产品解决 1 至 2 个高优先级用例，POC 通过则签约概率超过 70%，POC 失败则基本失单。SE 必须把 POC 设计成可量化、有时间盒、有清晰退出条件的项目——不是"先试试看"。一个糟糕的 POC 让客户感觉产品复杂、文档差、性能不达标，即使实际不是这样；一个精心设计的 POC 让客户工程师变成内部"二级拥护者"，在采购评审时替你说话。本节给出 POC 与 pilot 的差异、成功标准设计、时间盒、风险、客户工程师 onboarding、POC 报告、退出条件。

类型 时长 范围 客户投入 SE 投入
Demo POC 1-3 天 SE 演示 旁观 5-10 小时
Hands-on POC 1-2 周 客户跑 1 用例 1 工程师 50% 时间 20-40 小时
Full POC 4-6 周 1-2 用例 2 工程师 50% 时间 40-80 小时
Pilot 8-12 周 真实生产场景 团队 + 业务方 80-150 小时
Pilot 后扩展 持续 扩规模 全团队 持续支持

POC 与 pilot 的差异

POC：

  • 概念验证。
  • 在沙箱环境跑。
  • 不接真实生产流量。
  • 决定"产品能不能解决问题"。

Pilot：

  • 试运营。
  • 在真实生产环境跑（小规模或灰度）。
  • 接真实流量。
  • 决定"产品在我们规模下稳不稳"。

取舍：

  • 大多数 deal 走 POC 即可。
  • Pilot 适合 mission-critical 场景（数据库迁移、核心 API 替换）。

成功标准设计

SMART 原则：

  • Specific：具体。
  • Measurable：可量化。
  • Achievable：可达成。
  • Relevant：相关。
  • Time-bound：有时间限制。

反例（不好的标准）：

  • "提升性能"。
  • "证明产品好用"。
  • "工程师满意"。

好例：

  • "API 响应时间 P99 低于 100ms"。
  • "支持 10000 QPS 持续 1 小时"。
  • "工程师在 5 天内完成集成 demo 部署"。

标准数量：

  • 3 至 5 个标准刚好。
  • 太多 deal 永远不结束。
  • 太少不有说服力。

共同商定标准

关键：

  • POC 开始前与客户签字确认标准。
  • 不在 POC 进行中改标准（除非双方共识）。

共商过程：

文档化：


    

  • 共享 Notion 文档或邮件留底。
    • 

  • 每个标准的成功度量方式。
    • 

  • 谁负责测量。
    • 



时间盒
典型时间盒：


    

  • Demo POC：1 至 3 天。
    • 

  • Hands-on POC：1 至 2 周。
    • 

  • Full POC：4 至 6 周。
    • 

  • Pilot：8 至 12 周。
    • 



为什么时间盒重要：


    

  • 防止 POC 无限拖延。
    • 

  • 客户工程师注意力有限。
    • 

  • 销售周期内必须收尾。
    • 



超时处理：


    

  • 提前 1 周打招呼。
    • 

  • 共商延期决策。
    • 

  • 如果客户没投入资源，应果断终止。
    • 



POC 阶段
1. 启动会（kickoff）
   - 双方介绍干系人
   - 共识标准与时间盒
   - 工具与凭证发放
2. Onboarding（第 1 周）
   - 文档与教程指引
   - SE 1-on-1 帮客户工程师跑通 hello world
3. 用例实现（第 2-N 周）
   - 客户工程师亲手实现
   - SE 每周同步处理阻塞
4. 测量（最后 1 周）
   - 跑性能基准
   - 收集数据对比标准
5. POC 报告
   - 通过 / 部分通过 / 失败
   - 推荐意见
6. 决策会
   - 客户内部讨论
   - 推进采购或终止
SE 在 POC 中的职责
搭建环境：


    

  • 沙箱 instance。
    • 

  • API 凭证。
    • 

  • 样本数据。
    • 



Onboarding：


    

  • 第一周帮客户工程师跑通 hello world。
    • 

  • 文档导航。
    • 

  • 排查常见问题。
    • 



每周同步：


    

  • 30 分钟 standup。
    • 

  • 客户工程师汇报进展。
    • 

  • SE 提供答疑与建议。
    • 



阻塞处理：


    

  • 客户卡住 4 小时以上 escalate。
    • 

  • SE 当天回应。
    • 

  • 重大阻塞直接接管解决。
    • 



性能基准：


    

  • 跑负载测试。
    • 

  • 数据收集与可视化。
    • 

  • 与标准对比。
    • 



报告撰写：


    

  • POC 结束撰写报告。
    • 

  • 客户工程师 review 后 sign-off。
    • 



客户工程师 onboarding
关键 metric：TTFHW（time to first hello world）


    

  • POC 第一天客户工程师能跑通 hello world 吗？
    • 

  • 5 分钟内通过 = 优秀。
    • 

  • 30 分钟以上 = onboarding 设计糟糕。
    • 



优化：


    

  • Quickstart 文档极简（5 分钟跑通）。
    • 

  • 沙箱预先 provision 好。
    • 

  • SE 1-on-1 第一天陪跑。
    • 



阻塞处理
常见阻塞：


    

  • 文档不全或过时。
    • 

  • 权限问题。
    • 

  • 集成与现有系统冲突。
    • 

  • 性能瓶颈。
    • 



Escalation 路径：


客户工程师卡住 → Slack 给 SE → SE 4 小时内回应
↓ 解决不了
SE escalate 给产品工程师 → 24 小时内回应
↓ 仍解决不了
SE 与产品 manager 商讨 workaround

## 下一步推荐
Sign-off：


    

  • 客户工程师与 SE 双方签字。
    • 

  • 报告后续作为采购决策依据。
    • 



POC 失败原因
1. 标准未量化：


    

  • "工程师满意"——主观难判断。
    • 



2. 客户没投入资源：


    

  • 客户工程师其他项目缠身。
    • 

  • POC 拖延 2 个月。
    • 



3. 产品功能缺口：


    

  • 关键用例做不到。
    • 

  • 早识别就该改 scope 或终止。
    • 



4. 文档与 SE 支持不到位：


    

  • 客户卡住没人答。
    • 



5. 集成与现有系统冲突：


    

  • 没在 discovery 阶段发现。
    • 



6. 客户工程师没有内部权威：


    

  • 即使 POC 通过，客户内部决策方不买账。
    • 



风险与缓解
风险 1：客户工程师离职 POC 中：


    

  • 缓解：早期识别，与客户技术 lead 多线程。
    • 



风险 2：竞品同时跑 POC：


    

  • 缓解：差异化体现在 POC 设计中。
    • 



风险 3：Scope creep：


    

  • 缓解：标准签字后不轻易加。
    • 



风险 4：客户决策权变更：


    

  • 缓解：每周与客户技术 lead 同步。
    • 



风险 5：基础设施成本超预算：


    

  • 缓解：明确谁付（你 trial credit 还是客户付）。
    • 



Free vs paid POC
Free POC：


    

  • 通常 SE 标配。
    • 

  • 客户不投入金钱风险。
    • 



Paid POC（pilot）：


    

  • 大 deal 适合（年合同 100 万美元以上）。
    • 

  • 客户付一定金额获得 pilot。
    • 

  • 客户投入提高承诺度。
    • 

  • 失败后可冲抵正式合同。
    • 



反模式
1. POC 没有成功标准：


    

  • "我们试一试看"——deal 永远不结束。
    • 



2. 标准只衡量功能：


    

  • 没量化性能、可用性、安全。
    • 



3. 不签字：


    

  • 标准口头约定——POC 中改来改去。
    • 



4. 一个 POC 跑 3 个月：


    

  • 时间盒失效。
    • 



5. SE 替客户做完 POC：


    

  • 客户工程师没真正动手——失去验证意义。
    • 



6. 报告不写或不签字：


    

  • POC 结果模糊——采购方无据可依。
    • 



7. 不识别 deal-breaker 标准：


    

  • 一两个标准远超过其他重要程度，应单独标。
    • 



实战建议
1. 永远要有标准：


    

  • 不接受"先试试看"。
    • 



2. 标准 3 至 5 个：


    

  • SMART 原则。
    • 



3. 双方签字：


    

  • POC 启动前。
    • 



4. 时间盒严格：


    

  • 超时果断处理。
    • 



5. 每周同步：


    

  • 不让客户失联。
    • 



6. TTFHW 5 分钟内：


    

  • 第一天体验决定 50% 成败。
    • 



7. POC 报告必写：


    

  • 客户内部决策依据。
    • 



8. 多线程：


    

  • 不只一个客户工程师。
    • 



小结
POC（Proof of Concept）与 pilot 是 deal 的决战点——30 至 90 天试点客户工程师亲手用产品解 1 至 2 个高优先级用例，POC 通过签约概率超 70% POC 失败基本失单，SE 必须把 POC 设计成可量化加有时间盒加清晰退出条件的项目不是"先试试看"。POC 与 pilot 差异——POC 概念验证沙箱环境不接真实生产流量决定能不能解决问题；pilot 试运营真实生产环境（小规模或灰度）接真实流量决定我们规模下稳不稳；取舍多数 deal POC 即可加 pilot 适合 mission-critical（数据库迁移核心 API 替换）。POC 类型对比——demo POC 1 至 3 天 SE 演示客户旁观 SE 5 至 10 小时；hands-on POC 1 至 2 周客户跑 1 用例 1 工程师 50% 时间 SE 20 至 40 小时；full POC 4 至 6 周 1 至 2 用例 2 工程师 50% SE 40 至 80 小时；pilot 8 至 12 周真实生产团队加业务方 SE 80 至 150 小时；pilot 后扩展持续全团队持续支持。成功标准 SMART——具体加可量化加可达成加相关加有时间限制；反例提升性能加证明产品好用加工程师满意；好例 P99 低于 100ms 加 10000 QPS 持续 1 小时加 5 天完成集成 demo；标准 3 至 5 个刚好太多 deal 永远不结束太少不有说服力。共同商定关键——POC 开始前与客户签字确认标准加不在 POC 中改（除非双方共识）；共商过程 SE 草案 → 客户工程师评审 → 客户技术 lead 评审 → 共识 → 文档化签字 → POC 启动；文档化共享 Notion 或邮件留底加每标准成功度量方式加谁负责测量。时间盒——demo POC 1 至 3 天加 hands-on 1 至 2 周加 full 4 至 6 周加 pilot 8 至 12 周；为什么重要防 POC 无限拖延加客户工程师注意力有限加销售周期必须收尾；超时处理提前 1 周打招呼加共商延期加客户没投入资源果断终止。POC 阶段 6 步——启动会双方介绍干系人加共识标准与时间盒加工具凭证发放、onboarding 第 1 周文档教程指引加 SE 1-on-1 帮 hello world、用例实现第 2-N 周客户亲手加 SE 每周同步处理阻塞、测量最后 1 周性能基准加数据对比标准、POC 报告通过或部分或失败加推荐意见、决策会客户内部讨论加推进采购或终止。SE 在 POC 中的职责——搭建环境沙箱加凭证加样本数据、onboarding 第一周陪跑 hello world 加文档导航加常见问题排查、每周同步 30 分钟 standup 加客户汇报进展加 SE 答疑建议、阻塞处理 4 小时以上 escalate 加 SE 当天回应加重大直接接管、性能基准跑负载测试加数据可视化加与标准对比、报告撰写 POC 结束加客户工程师 review 加 sign-off。客户工程师 onboarding 关键 TTFHW——POC 第一天能跑通 hello world 吗加 5 分钟通过优秀加 30 分钟以上 onboarding 糟糕；优化 quickstart 极简 5 分钟跑通加沙箱预先 provision 好加 SE 1-on-1 第一天陪跑。阻塞处理常见——文档不全过时加权限问题加集成与现有系统冲突加性能瓶颈；escalation 路径客户工程师卡住 → Slack 给 SE → SE 4 小时回应 → 解决不了 escalate 产品工程师 24 小时回应 → 仍不行 SE 与产品 manager 商讨 workaround。POC 报告模板——摘要起止时间加用例加结论、成功标准表格、详细结果用例实现细节、性能基准图表、客户反馈 quote、下一步推荐；sign-off 客户工程师与 SE 双方签字加报告作为采购决策依据。POC 失败常见——标准未量化主观难判断、客户没投入资源工程师其他项目缠身 POC 拖 2 月、产品功能缺口关键用例做不到早识别改 scope 或终止、文档与 SE 支持不到位客户卡住没人答、集成与现有系统冲突 discovery 没发现、客户工程师没内部权威 POC 通过决策方不买账。风险与缓解——客户工程师离职多线程、竞品同时跑差异化、scope creep 标准签字不轻易加、客户决策权变更每周与技术 lead 同步、基础设施成本超预算明确谁付（trial credit 还是客户付）。Free vs paid——free SE 标配客户无金钱风险；paid 大 deal（100 万美元年合同以上）适合客户付一定金额加投入提高承诺度加失败可冲抵正式合同。反模式——POC 无成功标准 deal 永远不结束、标准只衡量功能没量化性能可用性安全、不签字 POC 中改来改去、一个 POC 跑 3 月时间盒失效、SE 替客户做完客户没动手失验证意义、报告不写不签字结果模糊采购无据、不识别 deal-breaker 标准应单独标。实战建议——永远要有标准不接受先试试看、标准 3 至 5 个 SMART、双方签字 POC 启动前、时间盒严格超时果断处理、每周同步不失联、TTFHW 5 分钟第一天决定 50% 成败、POC 报告必写客户决策依据、多线程不只一个客户工程师。一个简单的检验：你能为一个 6 周 POC 写出 5 个 SMART 成功标准并让客户签字吗？如果不能，POC 设计还需要继续 practice。POC 设计是 SE 让"产品价值可被客户工程师亲手验证"的工程——做对让 70% 通过 POC 的 deal 最终签约，做错让 deal 在沙箱里拖延半年最终失单。
