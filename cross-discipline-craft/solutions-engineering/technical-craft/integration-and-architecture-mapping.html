集成与架构映射

核心概念

集成与架构映射是 SE 让客户工程师相信"你的产品能融入我们现有系统"的关键工程——demo 证明产品好用，集成映射证明产品能落地。SE 必须在 discovery 与 demo 阶段就摸清客户的技术栈、数据流、安全边界，画出"你的产品在客户架构中的位置"图。客户工程师看到清晰的集成图加数据流后会问"哦那这块谁负责重试"加"那个超时多少"——这些追问表明客户已经在心里把产品装上了。本节给出客户技术栈调研、数据流映射、API 表面、安全边界、部署模式、典型集成模式。

集成维度 关注点 工具或方法
技术栈 语言、框架、数据库 Discovery 问卷
数据流 输入、变换、输出 Mermaid sequence 图
API 表面 REST、gRPC、Webhook OpenAPI 文档
安全边界 认证、授权、加密 安全问卷
部署模式 SaaS、自托管、混合 架构图
性能 QPS、延迟、吞吐 基准测试

客户技术栈调研

Discovery 阶段问到：

  • 编程语言（多个语言混合很常见）。
  • 主框架（React、Spring、Django、Rails）。
  • 数据库（PostgreSQL、MySQL、Mongo、Redis）。
  • 消息队列（Kafka、RabbitMQ、SQS）。
  • 云（AWS、GCP、Azure、私有云）。
  • 容器编排（Kubernetes、ECS、Nomad）。
  • 认证服务（Auth0、Okta、Cognito、自建）。
  • 监控（Datadog、New Relic、Prometheus）。
  • CI/CD（GitHub Actions、CircleCI、Jenkins）。

问的方式：

  • 不要发问卷给客户填——客户嫌烦。
  • Discovery call 30 分钟自然问出来。
  • 边问边记笔记。

数据流映射

核心问题：

  • 数据从哪来？
  • 经过你的产品做什么变换？
  • 数据到哪去？
  • 失败时怎么处理？

示例：电商订单流接入支付平台

关键追问：


    

  • 失败重试机制？
    • 

  • Idempotency 怎么保证？
    • 

  • 退款流程？
    • 

  • 对账？
    • 



API 表面
REST API：


    

  • 最常见。
    • 

  • HTTP + JSON。
    • 

  • 适合大多数集成。
    • 



gRPC：


    

  • 内部服务高频调用。
    • 

  • Schema-driven。
    • 

  • 适合高性能场景。
    • 



Webhook：


    

  • 事件推送。
    • 

  • 客户端无需轮询。
    • 

  • 必须有重试与签名验证。
    • 



SDK：


    

  • Wrap API 提供语言原生接口。
    • 

  • 减少客户集成成本。
    • 

  • 主流语言要全（TypeScript、Python、Go、Java、Ruby、PHP）。
    • 



事件流：


    

  • Kafka、Kinesis、Pub/Sub。
    • 

  • 高吞吐场景。
    • 



安全边界
认证：


    

  • API key（简单、容易泄漏）。
    • 

  • OAuth 2.0（标准、复杂）。
    • 

  • mTLS（高安全场景）。
    • 

  • JWT（自包含、有失效时间）。
    • 



授权：


    

  • RBAC（基于角色）。
    • 

  • ABAC（基于属性）。
    • 

  • 资源级粒度（每个对象的访问权限）。
    • 



数据加密：


    

  • 传输加密（TLS 1.2 以上）。
    • 

  • 静态加密（At-rest）。
    • 

  • 字段级加密（PII）。
    • 



合规：


    

  • SOC 2 Type II。
    • 

  • ISO 27001。
    • 

  • GDPR。
    • 

  • HIPAA（医疗）。
    • 

  • PCI DSS（支付卡）。
    • 

  • FedRAMP（美国政府）。
    • 



SE 必备：


    

  • 客户问"你们 SOC 2 吗"答得出。
    • 

  • 客户问"数据存哪个 region"答得出。
    • 

  • 客户问"密钥轮换怎么做"答得出。
    • 



部署模式
SaaS（多租户）：


    

  • 你托管，客户消费。
    • 

  • 最简单、最快。
    • 

  • 不适合数据敏感行业。
    • 



SaaS（单租户）：


    

  • 每个客户独立 instance。
    • 

  • 数据隔离。
    • 

  • 比多租户贵。
    • 



自托管（On-prem）：


    

  • 客户自己运维。
    • 

  • 适合金融、政府。
    • 

  • 升级与支持复杂。
    • 



混合：


    

  • 控制面在 SaaS、数据面在客户。
    • 

  • 平衡安全与运维成本。
    • 



气隙（air-gapped）：


    

  • 完全离线环境。
    • 

  • 政府、军工。
    • 

  • 升级靠物理介质。
    • 



集成架构图
好架构图的特征：


    

  • 5 至 15 个节点（不要画 50 个节点的"全家福"）。
    • 

  • 数据流向清晰。
    • 

  • 信任边界明确（用框圈出"客户管辖区域"）。
    • 

  • 关键 API 标注。
    • 



绘图工具：


    

  • Mermaid（最方便代码化）。
    • 

  • Excalidraw（手绘风格）。
    • 

  • Lucidchart（企业级）。
    • 

  • Miro / FigJam（协作白板）。
    • 



示例：你的产品作为客户的搜索后端


性能基准
关键指标：


    

  • 延迟（P50、P95、P99）。
    • 

  • 吞吐（QPS、TPS）。
    • 

  • 错误率（5xx、超时）。
    • 

  • 可用性 SLA（99.9% / 99.99%）。
    • 



SE 在 POC 阶段验证：


    

  • 客户负载下产品性能。
    • 

  • 与客户当前方案对比。
    • 



常见集成模式
模式 1：API 直接集成：


    

  • 客户应用直接调你的 API。
    • 

  • 最简单。
    • 

  • 适合大多数场景。
    • 



模式 2：SDK 嵌入：


    

  • 客户在前端或后端用你的 SDK。
    • 

  • 适合需要客户端逻辑的场景（埋点、加密、状态管理）。
    • 



模式 3：CDC（Change Data Capture）：


    

  • 你监听客户数据库变更。
    • 

  • 实时同步。
    • 

  • 适合搜索、分析、推荐场景。
    • 



模式 4：Webhook 双向：


    

  • 客户系统事件推给你。
    • 

  • 你系统事件推给客户。
    • 

  • 异步事件驱动。
    • 



模式 5：Queue 中介：


    

  • 客户系统写 queue。
    • 

  • 你的产品消费 queue。
    • 

  • 解耦削峰。
    • 



模式 6：Iframe 嵌入：


    

  • 你的 UI 嵌入客户应用。
    • 

  • 简单但定制性差。
    • 



模式 7：API Gateway 代理：


    

  • 客户的 gateway 反代你的 API。
    • 

  • 客户控制限流、认证。
    • 



集成清单
SE 在 POC 启动前向客户确认：


[ ] 编程语言加 SDK 是否支持
[ ] 认证方式（API key / OAuth / mTLS）
[ ] 数据 region（GDPR / 数据主权）
[ ] 限流策略（QPS、并发）
[ ] 重试策略（指数退避 / circuit breaker）
[ ] 监控接入（webhook 推 metric / 日志格式）
[ ] 错误处理（HTTP 状态码 / 业务错误码）
[ ] Idempotency（去重 key）
[ ] 灰度策略（按用户 / 流量 % / 时间）
[ ] 回滚机制（kill switch）
常见集成阻塞
阻塞 1：客户老技术栈：


    

  • COBOL / VB6 与现代 SDK 不兼容。
    • 

  • 解：提供 REST API + 客户写适配层。
    • 



阻塞 2：网络隔离：


    

  • 客户 VPC 内、不能访问公网。
    • 

  • 解：VPC peering 或 PrivateLink。
    • 



阻塞 3：合规限制：


    

  • 数据不能出某个 region。
    • 

  • 解：你产品在那个 region 部署。
    • 



阻塞 4：现有系统冲突：


    

  • 客户已有竞品在用。
    • 

  • 解：迁移工具加 dual-write 过渡期。
    • 



阻塞 5：性能瓶颈：


    

  • 客户负载远超你的 SLA。
    • 

  • 解：分级 SLA 或专属基础设施。
    • 



反模式
1. SE 不懂客户技术栈强讲：


    

  • 客户立刻识破——失去信任。
    • 



2. 架构图 50 个节点：


    

  • 看不懂——客户无法承接讨论。
    • 



3. 假设客户用 latest tech：


    

  • 现实多数客户用 5 年前的栈。
    • 



4. 不问安全合规：


    

  • 卡到法务阶段才发现合规缺口。
    • 



5. 集成模式只有一种：


    

  • 不灵活——失大客户。
    • 



6. 不画图只口头讲：


    

  • 客户记不住。
    • 



7. 不留追问空间：


    

  • 客户没问题——可能是没在心里装上。
    • 



实战建议
1. Discovery 必问技术栈：


    

  • 30 分钟内问清。
    • 



2. 数据流图必画：


    

  • Mermaid sequence 图。
    • 



3. 安全合规答案准备好：


    

  • SOC 2、GDPR、region。
    • 



4. 部署模式 3 选 1 推荐：


    

  • 不让客户选 5 种。
    • 



5. 集成清单签字：


    

  • POC 启动前。
    • 



6. 多准备几个集成模式：


    

  • 客户场景不同。
    • 



7. SE 自己也要懂部署：


    

  • 客户问 K8s、helm、terraform 答得上。
    • 



8. 与产品工程师定期同步：


    

  • 新部署模式与功能。
    • 



小结
集成与架构映射是 SE 让客户工程师相信"你的产品能融入我们现有系统"的关键——demo 证明产品好用加集成映射证明产品能落地，SE 必须在 discovery 与 demo 阶段摸清客户技术栈加数据流加安全边界加画"你的产品在客户架构中位置"图，客户看到清晰图后追问"这块谁负责重试加那个超时多少"——表明已在心里装上。集成维度——技术栈语言加框架加数据库；数据流输入加变换加输出；API 表面 REST 与 gRPC 与 Webhook；安全边界认证加授权加加密；部署模式 SaaS 与自托管与混合；性能 QPS 加延迟加吞吐。客户技术栈调研——discovery 阶段问语言（多语言混合常见）与主框架（React Spring Django Rails）与数据库（PostgreSQL MySQL Mongo Redis）与消息队列（Kafka RabbitMQ SQS）与云（AWS GCP Azure 私有云）与容器编排（K8s ECS Nomad）与认证（Auth0 Okta Cognito 自建）与监控（Datadog New Relic Prometheus）与 CI/CD（Actions CircleCI Jenkins）；问的方式不发问卷加 discovery call 30 分钟自然问出来加边问边记。数据流映射核心问题——数据从哪来加经过你的产品做什么变换加数据到哪去加失败怎么处理；电商订单流示例 mermaid sequence 图覆盖用户加客户网站加你的支付 API 加银行加客户订单库；关键追问失败重试机制加 idempotency 怎么保证加退款流程加对账。API 表面——REST 最常见 HTTP+JSON；gRPC 内部服务高频 schema-driven 高性能；Webhook 事件推送客户端无需轮询必须重试与签名验证；SDK wrap API 语言原生接口减少集成成本主流语言要全（TS Python Go Java Ruby PHP）；事件流 Kafka Kinesis PubSub 高吞吐。安全边界——认证 API key 简单容易泄漏加 OAuth 2.0 标准复杂加 mTLS 高安全加 JWT 自包含；授权 RBAC 基于角色加 ABAC 基于属性加资源级粒度；数据加密传输 TLS 1.2 加静态 at-rest 加字段级 PII；合规 SOC 2 Type II 加 ISO 27001 加 GDPR 加 HIPAA 加 PCI DSS 加 FedRAMP；SE 必备客户问 SOC 2 答得出加数据存哪个 region 答得出加密钥轮换答得出。部署模式——多租户 SaaS 你托管客户消费最简单不适合敏感行业；单租户 SaaS 每客户独立 instance 数据隔离比多贵；自托管 on-prem 客户运维适合金融政府升级支持复杂；混合控制面 SaaS 数据面客户平衡安全与运维；气隙完全离线政府军工升级靠物理介质。集成架构图——好特征 5 至 15 节点不画 50 节点全家福加数据流向清晰加信任边界明确（框圈客户管辖）加关键 API 标注；绘图 Mermaid 代码化加 Excalidraw 手绘加 Lucidchart 企业加 Miro/FigJam 协作；示例搜索后端 mermaid 客户管辖加你的产品双 subgraph。性能基准关键指标——延迟 P50/P95/P99 加吞吐 QPS/TPS 加错误率 5xx/超时 加可用性 SLA 99.9% 或 99.99%；SE 在 POC 阶段验证客户负载下性能加与当前方案对比。常见集成模式——模式 1 API 直接集成最简单适合多数；模式 2 SDK idempotency 加灰度策略加回滚机制。常见集成阻塞——客户老技术栈 COBOL/VB6 解 REST + 适配层；网络隔离 VPC 内不通公网解 VPC peering 或 PrivateLink；合规限制数据不出 region 解你产品在那个 region 部署；现有系统冲突已有竞品解迁移工具加 dual-write 过渡；性能瓶颈客户负载超 SLA 解分级 SLA SOC 2 加 GDPR 加 region、部署模式 3 选 1 推荐不让客户选 5 种、集成清单签字 POC 启动前、多准备几个集成模式客户场景不同、SE 自己懂部署 K8s helm terraform、与产品工程师定期同步新部署与功能。一个简单的检验：你能在 30 分钟 discovery 后画出 5 至 15 节点的客户架构集成图吗？如果不能，集成与架构映射还需要继续 practice。集成与架构映射是 SE 让"你的产品在客户系统里的位置"具象化的工程——做对让客户工程师在心里装上产品并主动追问细节，做错沦为客户问"那怎么接进来"时一脸茫然的尴尬现场。
