SE 与 DevRel、销售的边界

核心概念

SE、DevRel、销售（AE）三者都与客户接触、都参与 deal cycle，但 KPI、服务单元、时间跨度、内容形态都不同。SE 一对一服务具体客户、关闭企业级 deal；DevRel 一对多服务社区、优化开发者信任与激活；销售 AE 一对一关闭商业 deal、背配额。三者必须协同——AE 把 lead 带进来，SE 跑技术路径，DevRel 提供可复用素材让 SE 借力，并维护长期品牌。本节给出三角 RACI、协同场景、冲突场景，以及如何避免角色合并。

维度 销售 AE SE DevRel
服务单元 单个具体 deal 单个具体 deal 整个社区
触达方式 一对一商业 一对一技术 一对多
核心 KPI 配额（ARR） 配额（与 AE 联背） 激活 / NPS
时间跨度 季度 季度 季度加长尾
主要内容 合同条款、RFP 定制 demo、POC 教程、talk
报告线 VP Sales VP Sales 或 SE Lead CTO/VPE 或 CMO

三角协同模型

SE 与销售 AE 的协同
销售的主要职责：


    

  • 商业侧 discovery（预算、决策权、时间表）。
    • 

  • 价格谈判。
    • 

  • 合同谈判。
    • 

  • 关单。
    • 

  • 背配额。
    • 



SE 的主要职责：


    

  • 技术侧 discovery（技术栈、痛点、成功标准）。
    • 

  • 交付 demo 与 POC。
    • 

  • 担任架构顾问。
    • 

  • 技术侧关单。
    • 



联合负责：


    

  • Deal 策略。
    • 

  • 客户关系。
    • 

  • 销售预测。
    • 



冲突点：


    

  • AE 想快速关单，SE 想做扎实的 POC。
    • 

  • 解法：双方在 deal 阶段门槛上达成一致。
    • 



SE 与 DevRel 的协同
DevRel 的主要职责：


    

  • 面向社区的广覆盖触达。
    • 

  • 可复用内容（博客、教程、sample）。
    • 

  • 品牌声音。
    • 

  • 长尾认知度。
    • 



SE 的主要职责：


    

  • 聚焦在具体客户。
    • 

  • 定制内容（每客户定制的 demo）。
    • 

  • 销售周期内的战术执行。
    • 



联合协作：


    

  • DevRel 写 sample，SE 拿来当 demo 模板。
    • 

  • SE 听到客户反馈，DevRel 整理成 digest 反馈给产品。
    • 

  • DevRel 办 launch event，SE 在展位接 hot lead。
    • 



冲突点：


    

  • DevRel 在公开场合宣传不太适合所有客户的用例，SE 拿到客户后还要纠偏。
    • 

  • 解法：DevRel 的内容由 SE leadership review 把关。
    • 



SE 与 DevRel 的关键差异
受众：


    

  • DevRel 服务任何开发者，包括业余玩家。
    • 

  • SE 只服务已进 pipeline 的企业级客户。
    • 



互动密度：


    

  • DevRel 与单个开发者一周接触 1 至 2 次。
    • 

  • SE 在 deal cycle 中与单个客户一周接触 5 至 10 次。
    • 



内容：


    

  • DevRel 的内容公开可复用。
    • 

  • SE 的内容针对具体客户、不公开。
    • 



产出指标：


    

  • DevRel 一篇博客触达 1 万开发者。
    • 

  • SE 一个 deal 关下 100 万美元。
    •

协同场景
博客带来入站 lead：


DevRel 发博客 → 5000 阅读 → 200 注册 → 50 企业兴趣
→ Marketing/SDR 资格筛选 → 10 SQL 交给 AE
→ AE 做 discovery call → SE 跟进技术
→ SE 做 demo → POC → 关单
→ 交接给 CSM
大会赞助：


    

  • DevRel 负责演讲、workshop、展位值班。
    • 

  • AE 处理展位接到的 hot lead 名片。
    • 

  • SE 跟进客户的技术追问。
    • 

  • DevRel 把演讲录像 post 出去做长尾。
    • 



已签约客户出现重大故障：


    

  • CSM 主导问题解决。
    • 

  • SE 在需要技术深挖时偶尔回援。
    • 

  • DevRel 监控社区是否有更广影响。
    • 



冲突场景
冲突一：DevRel 公开的基准测试显示产品不如竞品 X：


    

  • AE 不想公开承认。
    • 

  • DevRel 看重诚实的价值。
    • 

  • 解法：DevRel 公开但加上 caveat 与场景区分。
    • 



冲突二：AE 让 SE 跳过 POC 加速关单：


    

  • SE 知道 POC 是 deal 的资格筛选关键。
    • 

  • 跳过后客户上线后流失率高。
    • 

  • 解法：SE Lead 与 AE Lead 在 deal 阶段门槛上达成一致。
    • 



冲突三：DevRel 拉 SE 去做社区 webinar：


    

  • SE 时间被 deal 锁定。
    • 

  • Webinar 触达广，但 SE 配额并不归功于此。
    • 

  • 解法：SE 季度性参加大型社区活动，而不是每周。
    • 



冲突四：销售让 SE 越界谈商业：


    

  • AE 不在场时让 SE 谈定价。
    • 

  • 越界会让客户混乱，并引发 AE 与 SE 的内部冲突。
    • 

  • 解法：SE 在商业话题上叫停，转给 AE。
    •

报告线
销售 AE：


    

  • 向 VP Sales 汇报。
    • 



SE：


    

  • 向 SE Lead 汇报，再向 VP Sales 汇报；或者 SE 独立 line 直接向 CRO 汇报。
    • 

  • Stripe、Snowflake 走的是 SE 独立 line，给 SE 单独的话语权。
    • 



DevRel：


    

  • 向 CTO、VPE 或 CEO 汇报（参考前一章的讨论）。
    • 

  • 不被销售导向。
    • 



谁不应做什么
SE 不应：


    

  • 谈定价或合同（这是 AE 的活）。
    • 

  • 写公开博客或大会演讲（这是 DevRel 的活）。
    • 

  • 解决一对一已签约客户的工单（这是 Support 与 CSM 的活）。
    • 



DevRel 不应：


    

  • 帮 SE 做客户专属的 demo。
    • 

  • 跑一对一的 deal 推进。
    • 

  • 背单个 deal 的配额。
    • 



销售不应：


    

  • 写技术内容。
    • 

  • 在没有 SE 的情况下跑技术 demo。
    • 

  • 把 SE 拉去越界。
    • 



招聘顺序
早期 startup：


    

  1. 创始人一手包办（advocate + sell + demo）。
    2. 

  2. 第一个 AE（关闭商业 deal）。
    3. 

  3. 第一个 SE（当 AE 自己 demo 太多时）。
    4. 

  4. 第一个 DevRel（PMF 后加社区信号）。
    5. 



成长期：


    

  • AE 与 SE 比 1 比 1。
    • 

  • DevRel 占 GTM 总人头 5% 至 10%。
    • 



成熟期：


    

  • 职能化组织。
    • 

  • 跨职能委员会协调。
    • 



反模式
1. SE、AE、DevRel 角色合并：


    

  • 一个人覆盖三角，三件事都平庸。
    • 



2. SE 嵌在销售组织深处、缺产品输入通道：


    

  • SE 听到客户反馈没法 feed 给产品。
    • 



3. DevRel 被劫持去做 SE 的工作：


    

  • "你帮 SE 跑这个客户的 demo"——失去社区焦点。
    • 



4. 销售不让 SE 做架构顾问：


    

  • SE 只 demo 不做顾问，信任不深。
    • 



5. 三角 KPI 各做各的：


    

  • AE 看配额、SE 看配额、DevRel 看激活，各看各的不联通——短视。
    • 



6. 不分享客户洞察：


    

  • SE 听到 deal 失败的原因不告诉 DevRel 与 PM。
    • 



7. 报告线错位：


    

  • DevRel 嵌在销售、SE 嵌在市场——错位。
    • 



实战建议
1. RACI 写下来：


    

  • 在 sprint planning 时拿出来用。
    • 



2. 每周联合 pipeline 复盘：


    

  • AE、SE、DevRel 代表同步预测视图。
    • 



3. SE 与 AE 一对一搭档：


    

  • 不要 SE 资源池。
    • 



4. SE 与 DevRel 月度同步：


    

  • DevRel 给 SE 可复用素材清单。
    • 

  • SE 反馈客户的真实声音。
    • 



5. 失单复盘：


    

  • 为什么输 deal？DevRel 调整内容、SE 调整流程。
    • 



6. 透明 KPI：


    

  • AE 配额、SE technical close rate、DevRel 激活率共用一个看板。
    • 



7. DevRel 与销售联合 OKR：


    

  • 部分 KR 共背（来自社区的 pipeline 创建数）。
    • 



小结
SE、DevRel、销售三者都接触客户、参与 deal cycle，但 KPI、服务单元、时间跨度、内容形态都不同——SE 一对一服务具体客户关闭企业级 deal、DevRel 一对多服务社区优化信任与激活、销售 AE 一对一关闭商业 deal 背配额，三角必须协同：AE 把 lead 带进来、SE 跑技术路径、DevRel 提供可复用素材并维护长期品牌。维度对比——服务单元 AE 与 SE 是单个 deal 而 DevRel 是整个社区；触达方式 AE 一对一商业、SE 一对一技术、DevRel 一对多；KPI AE 配额 ARR、SE 配额联背、DevRel 激活与 NPS；时间跨度 AE 与 SE 是季度而 DevRel 是季度加长尾；主要内容 AE 合同条款与 RFP、SE 定制 demo 与 POC、DevRel 教程与 talk；报告线 AE 给 VP Sales、SE 给 VP Sales 或 SE Lead、DevRel 给 CTO 或 VPE 或 CMO。SE 与 AE 协同——销售职责 discovery 商业侧（预算、决策权、时间表）加价格与合同谈判加关单加背配额；SE 职责 discovery 技术侧（技术栈、痛点、成功标准）加交付 demo 与 POC 加架构顾问加技术关单；联合 deal 策略与客户关系与销售预测；冲突 AE 想快速关单 SE 想扎实 POC，解法在 deal 阶段门槛达成一致。SE 与 DevRel 协同——DevRel 职责广覆盖触达加可复用内容加品牌声音加长尾认知；SE 职责聚焦客户加定制内容加战术执行；联合 DevRel 写 sample SE 拿来当 demo 模板加 SE 听反馈 DevRel 整 digest 给产品加 DevRel 办 launch event SE 在展位接 hot lead；冲突 DevRel 公开宣传不太适合所有用例 SE 纠偏，解法 DevRel 内容 SE leadership review。关键差异——受众 DevRel 任何开发者包括业余玩家、SE 只服务企业级 pipeline；互动密度 DevRel 单开发者一周 1 至 2 次、SE 单客户一周 5 至 10 次；内容 DevRel 公开可复用、SE 客户专属不公开；产出 DevRel 一篇博客 1 万、SE 一个 deal 100 万。RACI——入站 lead AE 主责，商业 discovery AE 主责加 SE 咨询，技术 discovery AE 咨询加 SE 主责，客户专属 demo SE 主责，可复用 demo DevRel 主责加 SE 咨询，POC 设计 SE 主责，定价合同 AE 主责，架构顾问 SE 主责，大会演讲 DevRel 主责加 SE 咨询，教程 DevRel 主责，RFP SE 主责，签约交接 SE 主责加 CSM 咨询，续约 CSM 主责加 SE 咨询。协同场景——博客带入站 lead（DevRel 5000 阅读 → 200 注册 → 50 兴趣 → Marketing/SDR 筛选 → 10 SQL 给 AE → AE discovery → SE 跟进 → demo → POC → 关单 → 交接 CSM）、大会赞助（DevRel 演讲与 workshop 与展位值班加 AE 接名片加 SE 技术追问加 DevRel 后期录像长尾）、客户重大故障（CSM 主导加 SE 必要时回援加 DevRel 监控更广影响）。冲突场景——DevRel 基准测试不如竞品 AE 不想公开（解法 caveat 与场景区分）、AE 让 SE 跳过 POC（解法 SE Lead 与 AE Lead 阶段门槛一致）、DevRel 拉 SE 做 webinar（解法 季度参加而非每周）、销售让 SE 越界谈商业（解法 SE 叫停转 AE）。内容归属——公开博客与教程归 DevRel、客户专属 demo 归 SE、公开 sample 归 DevRel、POC 实现归 SE、白皮书归 DevRel、case study PMM 主导加 SE 与 DevRel review、RFP 归 SE、大会演讲归 DevRel、客户参考通话归 SE 或 CSM、技术 webinar 归 DevRel、客户一对一答疑归 SE。报告线——销售给 VP Sales、SE 给 SE Lead 加 VP Sales 或独立 line 给 CRO（Stripe 与 Snowflake 走独立 line）、DevRel 给 CTO 或 VPE 或 CEO 不被销售导向。谁不应做——SE 不谈定价合同与不写公开博客与不解一对一工单；DevRel 不帮 SE 客户专属 demo 与不跑一对一 deal 与不背单 deal 配额；销售不写技术内容与不无 SE 跑 demo 与不拉 SE 越界。招聘顺序——早期创始人一手包办 → 第一 AE 关商业 → 第一 SE AE 自演太多时 → 第一 DevRel PMF 后；成长期 AE 与 SE 1 比 1 加 DevRel 占 GTM 头 5 至 10%；成熟期职能化加跨职能委员会协调。反模式——三角角色合并都平庸、SE 嵌销售深处缺产品输入通道、DevRel 被劫做 SE 工作失社区焦点、销售不让 SE 做架构顾问只 demo 信任不深、三角 KPI 各做各短视、不分享客户洞察 SE 失单原因不告诉 DevRel 与 PM、报告线错位（DevRel 嵌销售或 SE 嵌市场）。实战建议——RACI 写下来 sprint 用、每周联合 pipeline 复盘三角同步、SE 与 AE 一对一搭档不资源池、SE 与 DevRel 月度同步给可复用素材并反馈客户声音、失单复盘 DevRel 调内容 SE 调流程、透明 KPI 共看板、DevRel 与销售联合 OKR 部分 KR 共背（社区带入 pipeline 数）。一个简单的检验：你能画出 RACI 矩阵，并解释签约后交接由谁负责吗？如果不能，三角边界还需要继续 practice。三角边界清晰让 AE 与 SE 与 DevRel 各负其责协同关单加长期品牌加客户信任，模糊则是内耗加错配 KPI 加客户混乱。
