限流与节流

核心概念

限流（Rate Limiting）和节流（Throttling）是保护后端服务免受过载的核心防御机制。当请求速率超过服务处理能力时，限流策略决定哪些请求被接受、哪些被拒绝，从而保障服务的可用性和公平性。

限流的本质是对资源访问施加速率约束。不同的限流算法在精度、内存消耗、突发处理和实现复杂度上各有权衡。在分布式系统中，限流还需要考虑跨节点的状态共享问题。

令牌桶算法
令牌桶（Token Bucket）是最常用的限流算法，它以固定速率向桶中添加令牌，每个请求消耗一个令牌。桶满时新令牌被丢弃，桶空时请求被拒绝。这种设计天然支持突发流量——桶中积累的令牌允许短时间内处理超过平均速率的请求。


interface TokenBucket {
  consume(tokens?: number): boolean;
  getState(): { tokens: number; capacity: number; lastRefill: number };
}

const createTokenBucket = (options: {
  capacity: number;
  refillRate: number;
  refillIntervalMs: number;
}): TokenBucket => {
  let tokens = options.capacity;
  let lastRefill = Date.now();

  const refill = () => {
    const now = Date.now();
    const elapsed = now - lastRefill;
    const newTokens = Math.floor(elapsed / options.refillIntervalMs) * options.refillRate;

    if (newTokens > 0) {
      tokens = Math.min(options.capacity, tokens + newTokens);
      lastRefill = now;
    }
  };

  return {
    consume(count = 1) {
      refill();
      if (tokens >= count) {
        tokens -= count;
        return true;
      }
      return false;
    },
    getState: () => ({ tokens, capacity: options.capacity, lastRefill }),
  };
};

const apiLimiter = createTokenBucket({
  capacity: 100,
  refillRate: 10,
  refillIntervalMs: 1000,
});
令牌桶的优势在于允许突发——如果桶中有 100 个令牌，客户端可以一次性发送 100 个请求。令牌按固定速率补充，长期来看请求速率不会超过补充速率。


滑动窗口计数器
滑动窗口计数器是固定窗口和滑动窗口日志的折中方案。它使用两个固定窗口的加权计数来近似滑动窗口，既保持了 O(1) 的内存消耗，又避免了固定窗口的边界突发问题。


interface SlidingWindowCounter {
  isAllowed(key: string): boolean;
  getCount(key: string): number;
}

const createSlidingWindowCounter = (options: { windowMs: number; maxRequests: number }): SlidingWindowCounter => {
  const windows = new Map<string, { current: number; previous: number; windowStart: number }>();

  const getOrCreate = (key: string) => {
    if (!windows.has(key)) {
      windows.set(key, { current: 0, previous: 0, windowStart: Date.now() });
    }
    return windows.get(key)!;
  };

  const rollWindow = (state: { current: number; previous: number; windowStart: number }) => {
    const now = Date.now();
    const elapsed = now - state.windowStart;

    if (elapsed >= options.windowMs * 2) {
      state.previous = 0;
      state.current = 0;
      state.windowStart = now;
    } else if (elapsed >= options.windowMs) {
      state.previous = state.current;
      state.current = 0;
      state.windowStart = now;
    }
  };

  return {
    isAllowed(key) {
      const state = getOrCreate(key);
      rollWindow(state);

      const elapsed = Date.now() - state.windowStart;
      const weight = 1 - elapsed / options.windowMs;
      const count = state.previous * weight + state.current;

      if (count >= options.maxRequests) return false;

      state.current++;
      return true;
    },

    getCount(key) {
      const state = getOrCreate(key);
      rollWindow(state);
      const elapsed = Date.now() - state.windowStart;
      const weight = 1 - elapsed / options.windowMs;
      return Math.floor(state.previous * weight + state.current);
    },
  };
};
加权计算的精度取决于请求在前一窗口中的分布假设。实际上，请求分布越均匀，近似越准确。对于绝大多数 API 限流场景，这种近似已经足够精确。


分布式限流
单实例限流无法应对多实例部署场景——每个实例独立计数，总速率可能超过预期。分布式限流通过共享存储（通常是 Redis）实现跨实例的全局速率控制。


import type { Redis } from 'ioredis';

const createDistributedLimiter = (redis: Redis) => {
  const slidingWindowCheck = async (
    key: string,
    windowMs: number,
    maxRequests: number,
  ): Promise<{ allowed: boolean; remaining: number; resetAt: number }> => {
    const now = Date.now();
    const windowStart = now - windowMs;

    const pipeline = redis.pipeline();
    pipeline.zremrangebyscore(key, 0, windowStart);
    pipeline.zadd(key, now, `${now}:${crypto.randomUUID()}`);
    pipeline.zcard(key);
    pipeline.expire(key, Math.ceil(windowMs / 1000));

    const results = await pipeline.exec();
    const count = (results?.[2]?.[1] as number) ?? 0;

    if (count > maxRequests) {
      await redis.zrem(key, `${now}:${crypto.randomUUID()}`);
      const oldestStr = await redis.zrange(key, 0, 0, 'WITHSCORES');
      const resetAt = oldestStr.length >= 2 ? Number(oldestStr[1]) + windowMs : now + windowMs;

      return { allowed: false, remaining: 0, resetAt };
    }

    return {
      allowed: true,
      remaining: maxRequests - count,
      resetAt: now + windowMs,
    };
  };

  return { check: slidingWindowCheck };
};
Redis Sorted Set 天然适合滑动窗口日志模式：分数为时间戳，值为请求标识。ZREMRANGEBYSCORE 清除过期记录，ZCARD 获取窗口内的请求数。Pipeline 批量执行确保原子性和低延迟。


限流中间件集成
将限流策略集成到框架中间件中，是实际应用的关键步骤。中间件需要返回标准的限流响应头。


import { Hono } from 'hono';
import type { MiddlewareHandler } from 'hono';

const createRateLimitMiddleware = (options: {
  windowMs: number;
  max: number;
  keyGenerator?: (c: { req: { header: (name: string) => string | undefined } }) => string;
}): MiddlewareHandler => {
  const limiter = createSlidingWindowCounter({
    windowMs: options.windowMs,
    maxRequests: options.max,
  });

  return async (c, next) => {
    const key = options.keyGenerator?.(c) ?? c.req.header('x-forwarded-for') ?? 'global';
    const count = limiter.getCount(key);

    c.header('X-RateLimit-Limit', String(options.max));
    c.header('X-RateLimit-Remaining', String(Math.max(0, options.max - count - 1)));
    c.header('X-RateLimit-Reset', String(Math.ceil((Date.now() + options.windowMs) / 1000)));

    if (!limiter.isAllowed(key)) {
      c.header('Retry-After', String(Math.ceil(options.windowMs / 1000)));
      return c.json({ error: 'Too many requests' }, 429);
    }

    await next();
  };
};

const app = new Hono();

app.use('/api/*', createRateLimitMiddleware({ windowMs: 60_000, max: 100 }));
app.use('/api/auth/*', createRateLimitMiddleware({ windowMs: 60_000, max: 10 }));

不同的 API 端点可以配置不同的限流策略。认证相关端点（如登录、注册）通常需要更严格的限流以防止暴力破解。


小结
    

  • 令牌桶算法是最通用的限流方案，天然支持突发流量
    • 

  • 滑动窗口计数器用 O(1) 内存近似滑动窗口，适合大多数场景
    • 

  • 分布式限流通过 Redis Sorted Set 实现跨实例的全局速率控制
    • 

  • 限流中间件应返回标准的 X-RateLimit-* 响应头
    • 

  • 不同端点应配置不同的限流策略，敏感端点需更严格
    •
