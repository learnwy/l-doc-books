API 版本策略

核心概念

API 版本管理是后端服务演进的核心挑战。当 API 需要引入不兼容的变更（如字段重命名、参数调整、响应结构变化）时，版本策略决定了如何在不破坏现有客户端的前提下推进迭代。一个好的版本策略需要平衡向后兼容性、维护成本和开发体验。

API 版本化的本质是管理契约变更——服务端和客户端之间的接口契约不能单方面打破。不同的版本传递方式各有优劣，选择取决于团队规模、客户端多样性和发布节奏。

URL 路径版本实现
URL 路径版本是最直观、最广泛采用的方案。版本号作为 URL 前缀的一部分，客户端通过不同的 URL 访问不同版本的 API。GitHub、Stripe、Google 等主流 API 都采用这种方式。


import { Hono } from 'hono';

const createUserRoutesV1 = () => {
  const router = new Hono();

  router.get('/users', async (c) => {
    const users = await listUsers();
    return c.json(
      users.map((u) => ({
        id: u.id,
        name: u.name,
        email: u.email,
      })),
    );
  });

  router.get('/users/:id', async (c) => {
    const user = await findUser(c.req.param('id'));
    return c.json({ id: user.id, name: user.name, email: user.email });
  });

  return router;
};

const createUserRoutesV2 = () => {
  const router = new Hono();

  router.get('/users', async (c) => {
    const users = await listUsers();
    return c.json({
      data: users.map((u) => ({
        id: u.id,
        fullName: u.name,
        emailAddress: u.email,
        createdAt: u.createdAt.toISOString(),
        role: u.role,
      })),
      meta: { total: users.length },
    });
  });

  router.get('/users/:id', async (c) => {
    const user = await findUser(c.req.param('id'));
    return c.json({
      data: {
        id: user.id,
        fullName: user.name,
        emailAddress: user.email,
        createdAt: user.createdAt.toISOString(),
        role: user.role,
      },
    });
  });

  return router;
};

const app = new Hono();
app.route('/api/v1', createUserRoutesV1());
app.route('/api/v2', createUserRoutesV2());
V1 和 V2 的路由完全独立，可以共享业务逻辑层但各自控制响应格式。这种隔离确保了版本间的变更不会互相影响。


Header 版本与路由分发
Header 版本通过自定义请求头传递版本信息，URL 保持不变。这种方式适合内部微服务通信，URL 干净但版本信息不够直观。


import { Hono } from 'hono';
import type { MiddlewareHandler } from 'hono';

interface VersionedHandler {
  [version: string]: (c: Context) => Promise<Response>;
}

const createVersionRouter = (handlers: VersionedHandler, defaultVersion = '1'): MiddlewareHandler => {
  return async (c, next) => {
    const version =
      c.req.header('x-api-version') ?? c.req.header('accept')?.match(/version=(\d+)/)?.[1] ?? defaultVersion;

    const handler = handlers[version];
    if (!handler) {
      return c.json(
        { error: { code: 'UNSUPPORTED_VERSION', message: `API version ${version} is not supported` } },
        400,
      );
    }

    return handler(c);
  };
};

const app = new Hono();

app.get(
  '/api/users',
  createVersionRouter({
    '1': async (c) => {
      const users = await listUsers();
      return c.json(users.map(serializeUserV1));
    },
    '2': async (c) => {
      const users = await listUsers();
      return c.json({ data: users.map(serializeUserV2), meta: { total: users.length } });
    },
  }),
);
Header 版本的优势是 URL 不变，方便代理和缓存配置。但客户端需要在每次请求中设置头部，且浏览器调试时不如 URL 版本直观。


语义化版本与兼容性规则
语义化版本（SemVer）为 API 变更提供了明确的兼容性契约。理解什么构成破坏性变更，是制定版本策略的基础。


interface VersionInfo {
  major: number;
  minor: number;
  patch: number;
  deprecated: boolean;
  sunset?: string;
}

const API_VERSIONS: Record<string, VersionInfo> = {
  '1': { major: 1, minor: 5, patch: 3, deprecated: true, sunset: '2025-06-01' },
  '2': { major: 2, minor: 2, patch: 0, deprecated: false },
};

const versionInfoMiddleware: MiddlewareHandler = async (c, next) => {
  const version = c.req.header('x-api-version') ?? '2';
  const info = API_VERSIONS[version];

  if (info) {
    c.header('X-API-Version', version);
    if (info.deprecated) {
      c.header('Deprecation', 'true');
      c.header('Sunset', info.sunset ?? '');
      c.header('Link', '</api/v2>; rel="successor-version"');
    }
  }

  await next();
};

废弃通知是版本生命周期管理的重要环节。Deprecation 头告知客户端当前版本即将下线，Sunset 头指定具体的下线日期，Link 头指向新版本。


版本共存与代码组织
多版本并存是版本策略的实施难点。如何组织代码使多版本共享业务逻辑同时保持各自的序列化层，是架构层面的关键决策。


interface UserDTO_V1 {
  id: string;
  name: string;
  email: string;
}

interface UserDTO_V2 {
  id: string;
  fullName: string;
  emailAddress: string;
  createdAt: string;
  role: string;
}

const toUserDTOV1 = (user: User): UserDTO_V1 => ({
  id: user.id,
  name: user.name,
  email: user.email,
});

const toUserDTOV2 = (user: User): UserDTO_V2 => ({
  id: user.id,
  fullName: user.name,
  emailAddress: user.email,
  createdAt: user.createdAt.toISOString(),
  role: user.role,
});

const createUserService = (repo: UserRepository) => ({
  async getUser(id: string): Promise<User> {
    const user = await repo.findById(id);
    if (!user) throw new AppError(404, 'User not found', 'USER_NOT_FOUND');
    return user;
  },

  async listUsers(options: PaginationOptions): Promise<PaginatedResult<User>> {
    return repo.search('', options);
  },
});
业务逻辑层（Service）返回领域对象，序列化层（DTO 转换）按版本独立实现。这种分层确保了业务逻辑只有一份，变更的只是数据映射方式。当旧版本下线时，只需删除对应的 DTO 和路由，不影响核心逻辑。


小结
    

  • URL 路径版本是最直观、缓存最友好的版本策略，适合公开 API
    • 

  • Header 版本适合内部微服务，URL 干净但可见性低
    • 

  • 语义化版本明确定义兼容性契约，新增可选字段为 Minor，移除字段为 Major
    • 

  • 废弃通知通过 Deprecation 和 Sunset 响应头告知客户端版本生命周期
    • 

  • 业务逻辑层共享、序列化层按版本独立是多版本代码组织的最佳实践
    • 

  • 版本下线时只需删除 DTO 和路由，不影响核心业务逻辑
