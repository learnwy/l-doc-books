容器与编排

知识要点

容器技术彻底改变了软件的打包和部署方式——"在我机器上能跑"不再是问题，因为应用及其所有依赖被封装在标准化的容器镜像中。Docker 实现了单机容器化，Kubernetes（K8s）则解决了大规模容器的编排和管理问题。2026 年容器化已成为企业级应用部署的默认选择。

Docker 核心概念

Docker 的三个核心组件：

组件 作用 类比
镜像 (Image) 只读模板，包含运行所需的一切 类 (Class)
容器 (Container) 镜像的运行实例 对象 (Instance)
仓库 (Registry) 存储和分发镜像 Maven 仓库

Dockerfile 与镜像构建

Dockerfile 是构建镜像的"配方"：

# 多阶段构建 — 缩小最终镜像体积
FROM maven:3.9-eclipse-temurin-21 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src/ src/
RUN mvn package -DskipTests

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/myapp.jar app.jar

# 非 root 用户运行
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

EXPOSE 8080
ENTRYPOINT ["java", "-Xmx256m", "-jar", "app.jar"]

镜像优化策略：

  • 多阶段构建：编译环境不进入最终镜像
  • 使用 Alpine 基础镜像：从 ~300MB 缩减到 ~80MB
  • 层缓存利用：不常变化的依赖放在前面
  • .dockerignore 排除不需要的文件
# 构建与运行
docker build -t myapp:1.0 .
docker run -d -p 8080:8080 --name myapp myapp:1.0
docker logs -f myapp

Docker Compose 多容器编排

真实应用通常由多个服务组成（应用 + 数据库 + 缓存），Compose 用 YAML 定义多容器环境：

# docker-compose.yml
version: '3.8'
services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      - SPRING_DATASOURCE_URL=jdbc:mysql://db:3306/myapp
      - SPRING_REDIS_HOST=redis
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    
  db:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root123
      MYSQL_DATABASE: myapp
    volumes:
      - mysql_data:/var/lib/mysql
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      timeout: 5s
      retries: 3
    
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"

volumes:
  mysql_data:
docker compose up -d        # 启动所有服务
docker compose logs -f app  # 查看应用日志
docker compose down -v      # 停止并清理

Kubernetes 核心架构

K8s 将容器集群抽象为声明式资源管理系统：

核心资源对象：






资源
作用
示例





Pod
最小调度单位，一个或多个容器
运行一个 Java 应用容器




Deployment
声明式管理 Pod 副本数和更新策略
保持 3 个副本运行




Service
稳定的网络入口，负载均衡
暴露 HTTP 端口




ConfigMap
配置数据注入
数据库连接字符串




Secret
敏感信息管理
密码、密钥




HPA
自动水平扩缩容
CPU > 70% 时扩容





K8s 部署实战
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  labels:
    app: myapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp
        image: registry.example.com/myapp:1.0
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "256Mi"
            cpu: "200m"
          limits:
            memory: "512Mi"
            cpu: "500m"
        livenessProbe:
          httpGet:
            path: /actuator/health
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata:
  name: myapp-svc
spec:
  selector:
    app: myapp
  ports:
  - port: 80
    targetPort: 8080
  type: ClusterIP
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
kubectl apply -f deployment.yaml
kubectl get pods -w                    # 观察 Pod 启动
kubectl describe pod myapp-xxx        # 查看详情
kubectl logs myapp-xxx -f             # 查看日志
kubectl rollout restart deploy/myapp  # 滚动重启
滚动更新与回滚
K8s 默认采用滚动更新策略，新版本 Pod 逐步替换旧版本，保证服务不中断：


spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 最多多出1个Pod
      maxUnavailable: 0  # 不允许不可用Pod
# 更新镜像版本
kubectl set image deploy/myapp myapp=registry.example.com/myapp:2.0

# 发现问题立即回滚
kubectl rollout undo deploy/myapp
kubectl rollout history deploy/myapp  # 查看历史版本
前沿动态
    

  • Kubernetes 1.30+ Gateway API：取代 Ingress 成为流量管理的标准 API，支持更细粒度的路由规则
    • 

  • WebAssembly (Wasm) 容器：比传统容器启动更快、体积更小，SpinKube 项目让 Wasm 工作负载原生运行在 K8s 上
    • 

  • GitOps 成为标准：ArgoCD/Flux 监听 Git 仓库变化，自动将集群状态同步为代码声明的状态
    • 

  • AI 驱动的 K8s 运维：Kubernetes Copilot 类工具可根据自然语言生成 YAML 配置、排查 Pod 故障
    • 

  • Serverless Container：阿里云 ASK、AWS Fargate 等无服务器容器平台消除了节点管理负担
    •

  2. 使用 Minikube 或 Kind 搭建本地 K8s 集群，将上述应用部署为 3 副本 Deployment + Service，配置 HPA 使 CPU 使用率超过 70%70\%70% 时自动扩容至最多 5 个 Pod。使用 kubectl top 验证资源监控。

  3. 模拟滚动发布：将应用从 v1.0 更新到 v2.0，观察更新过程中 Pod 的替换顺序。然后模拟 v2.0 有 Bug（健康检查失败），验证 K8s 是否自动停止更新并可手动回滚。

小结
容器与编排是云原生架构的基石。Docker 解决了"环境一致性"问题，让应用从开发到生产的交付过程标准化；Kubernetes 解决了"规模化运行"问题，通过声明式配置、自动扩缩容和滚动更新保障了服务的高可用性。掌握 Docker + K8s 的组合，就掌握了 2026 年企业级应用部署的主流方式。
