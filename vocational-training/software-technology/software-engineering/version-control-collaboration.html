版本控制与协作

知识要点

版本控制是多人协作开发的基础设施，Git 是当今业界使用最广泛的分布式版本控制系统。掌握 Git 工作流和团队协作规范是从"个人编码"到"团队交付"的关键跨越，也是入职任何软件公司的第一天就需要用到的技能。

Git 基本概念与操作

Git 将项目历史记录为一系列快照（commit），通过有向无环图（DAG）组织版本关系：

核心概念：






概念
说明





工作区 (Working Directory)
实际文件目录




暂存区 (Staging Area)
git add 后的待提交内容




本地仓库 (Local Repo)
git commit 后的版本历史




远程仓库 (Remote Repo)
GitLab/GitHub 上的共享仓库





常用命令组合：


# 日常开发流程
git checkout -b feature/user-profile    # 创建并切换分支
git add src/UserProfile.java            # 暂存具体文件
git commit -m "feat(user): add profile page"  # 提交
git push origin feature/user-profile    # 推送到远程

# 同步最新代码
git fetch origin
git rebase origin/main                  # 变基保持线性历史

# 冲突解决
git mergetool                           # 可视化解决冲突
git rebase --continue                   # 解决后继续变基

Trunk Based Development 适用于持续交付团队：所有开发者直接向 main 提交，通过 Feature Flag 控制功能可见性，配合短生命周期分支（< 1天）和完善的 CI 管道。


高职项目推荐使用简化版 Git Flow：main + develop + feature/* 三层即可。


GitLab 平台与 Code Review
GitLab 提供了从代码托管到 CI/CD 的全流程 DevOps 平台。Merge Request（MR）是 Code Review 的载体：


## MR 标题: feat(user): 添加用户头像上传功能

### 变更说明
- 新增 /api/users/avatar 上传接口
- 前端添加头像裁剪组件
- 图片存储到 OSS

### 自测清单
- [x] 上传 JPG/PNG 格式正常
- [x] 文件大小超限提示正确
- [x] 裁剪后预览效果正常

### 关联 Issue
Closes #42
Code Review 的核心价值：


    

  1. 发现缺陷：第二双眼睛捕获逻辑错误、边界情况遗漏
    2. 

  2. 知识传播：团队成员了解彼此负责的模块
    3. 

  3. 代码一致性：维护统一的编码风格和架构规范
    4. 

  4. 促进成长：新人通过 Review 快速学习项目规范
    5. 



Review 规范：评论区分 Blocking（必须修改）和 Suggestion（建议优化），24 小时内完成 Review，避免过大 MR（单次 < 400 行变更）。


CI 触发机制
GitLab CI 通过 .gitlab-ci.yml 定义流水线，每次推送自动触发：


stages:
  - build
  - test
  - deploy

build:
  stage: build
  script:
    - mvn clean package -DskipTests
  artifacts:
    paths:
      - target/*.jar

unit-test:
  stage: test
  script:
    - mvn test
  coverage: '/Total.*?([0-9]{1,3})%/'

deploy-dev:
  stage: deploy
  script:
    - scp target/app.jar user@dev-server:/opt/app/
    - ssh user@dev-server 'systemctl restart app'
  only:
    - develop
CI 的"门禁"作用：编译失败、测试不通过、覆盖率低于阈值时自动阻止合并，保证 main 分支始终处于可部署状态。


提交信息规范
约定式提交（Conventional Commits）让 Git 历史可读且可自动化处理：


<type>(<scope>): <description>

类型: feat / fix / docs / style / refactor / test / chore
范围: 模块名
描述: 祈使语气，说明做了什么
配合 commitlint + husky 实现提交信息格式自动校验，不符合规范的提交直接被拒绝。


前沿动态
    

  • AI Code Review：2026 年 GitHub Copilot for Pull Requests 和 CodeRabbit 可自动分析 PR diff 并给出代码质量建议，但人工 Review 仍不可替代
    • 

  • GitOps：基础设施变更也通过 Git 管理（ArgoCD 监听仓库变化自动部署），Git 成为唯一的变更入口
    • 

  • Trunk Based + Feature Flags：大厂普遍采用的模式——代码合入主干但功能通过开关控制灰度发布
    • 

  • Monorepo 工具：Nx、Turborepo 管理多项目单仓库，统一版本和 CI 流水线
    • 



练习与思考
    

  1. 在 GitLab 上创建一个团队项目，设置分支保护规则（禁止直接 push main，MR 至少 1 人 Approve），模拟 3 人协作开发一个功能模块的完整流程。
    

    2. 

  2. 制造一个合并冲突场景：两人同时修改同一文件的同一行，分别通过 merge 和 rebase 两种方式解决冲突。对比两种方式产生的 commit 历史差异。
    

    3. 

  3. 编写一个 .gitlab-ci.yml，包含三个阶段：编译（mvn package）、测试（mvn test + JaCoCo 覆盖率报告）、部署到开发环境。设置覆盖率低于 60% 时流水线失败。
    

    4. 



小结
版本控制与协作不仅仅是"会用 git 命令"，它是一套完整的团队工作方式：分支策略决定了代码如何流动，Code Review 保障了代码质量和知识共享，CI 管道确保了每一次变更的可靠性。Git 技能是软件工程师职业生涯第一天就开始使用、最后一天仍在使用的核心工具。
