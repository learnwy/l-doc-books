游戏网络模型

核心概念

游戏网络模型决定了多人游戏中各个参与节点如何组织通信、分配职责和同步状态。不同的网络拓扑结构在延迟、安全性、可扩展性和开发复杂度上有着本质差异。理解这些模型是设计任何多人游戏系统的基础。

在早期的局域网游戏中，点对点（P2P）模型因其简单直接而广泛使用。随着互联网游戏的兴起，客户端-服务器（C/S）模型逐渐成为主流，它通过中心化的权威服务器解决了作弊和状态一致性问题。现代大型游戏则常采用混合架构，结合两种模型的优势。

点对点网络架构
P2P 网络中每个客户端同时充当主机和客户端角色，所有玩家直接相互通信。这种模型消除了中心服务器的需求，降低了基础设施成本。


在纯 P2P 模式下，每个客户端需要维护与其他所有客户端的连接。当玩家数量为 n 时，总连接数为 n(n-1)/2，这使得 P2P 在大规模场景下面临严重的带宽压力。


interface PeerConnection {
  peerId: string;
  socket: WebSocket;
  latency: number;
  lastHeartbeat: number;
}

interface P2PNetworkManager {
  localPeerId: string;
  peers: Map<string, PeerConnection>;
  messageBuffer: ArrayBuffer[];
}

const createP2PManager = (localId: string): P2PNetworkManager => ({
  localPeerId: localId,
  peers: new Map(),
  messageBuffer: [],
});

const broadcastToPeers = (manager: P2PNetworkManager, message: ArrayBuffer): void => {
  for (const [, peer] of manager.peers) {
    if (peer.socket.readyState === WebSocket.OPEN) {
      peer.socket.send(message);
    }
  }
};

const addPeer = (manager: P2PNetworkManager, peerId: string, socket: WebSocket): void => {
  manager.peers.set(peerId, {
    peerId,
    socket,
    latency: 0,
    lastHeartbeat: Date.now(),
  });
};
P2P 模型的核心挑战在于确定性同步。由于没有权威服务器，所有客户端必须对相同的输入产生相同的结果。这要求游戏逻辑必须是完全确定性的，包括浮点运算、随机数生成和物理模拟都需要保证跨平台一致性。


常见的 P2P 同步策略包括帧锁定（Lockstep）和输入延迟（Input Delay）。帧锁定要求所有玩家在同一帧收到所有输入后才推进游戏逻辑，这保证了完美同步但会受到最慢玩家的影响。


客户端-服务器架构
客户端-服务器模型是现代在线游戏最常用的网络架构。服务器作为唯一的权威节点运行完整的游戏逻辑，客户端发送输入并接收状态更新。


服务器在 C/S 架构中承担以下职责：接收并验证客户端输入、运行物理和游戏逻辑模拟、管理游戏状态、定期向客户端广播状态快照、处理玩家连接和断线重连。


interface GameServer {
  tickRate: number;
  clients: Map<string, ClientSession>;
  gameState: GameState;
  inputQueue: InputCommand[];
}

interface ClientSession {
  clientId: string;
  socket: WebSocket;
  lastInputSeq: number;
  rtt: number;
}

interface InputCommand {
  clientId: string;
  sequence: number;
  tick: number;
  actions: PlayerAction[];
}

interface PlayerAction {
  type: 'move' | 'shoot' | 'interact';
  payload: Record<string, number>;
}

interface GameState {
  tick: number;
  players: Map<string, PlayerState>;
  entities: Map<string, EntityState>;
}

interface PlayerState {
  position: { x: number; y: number; z: number };
  velocity: { x: number; y: number; z: number };
  health: number;
}

interface EntityState {
  id: string;
  type: string;
  position: { x: number; y: number; z: number };
  active: boolean;
}

const processServerTick = (server: GameServer): void => {
  const { inputQueue, gameState } = server;

  while (inputQueue.length > 0) {
    const cmd = inputQueue.shift()!;
    const session = server.clients.get(cmd.clientId);
    if (!session || cmd.sequence <= session.lastInputSeq) continue;

    applyInput(gameState, cmd);
    session.lastInputSeq = cmd.sequence;
  }

  updatePhysics(gameState);
  gameState.tick++;
  broadcastState(server);
};

const applyInput = (state: GameState, cmd: InputCommand): void => {
  const player = state.players.get(cmd.clientId);
  if (!player) return;

  for (const action of cmd.actions) {
    if (action.type === 'move') {
      player.velocity.x = action.payload.dx ?? 0;
      player.velocity.z = action.payload.dz ?? 0;
    }
  }
};

const updatePhysics = (state: GameState): void => {
  for (const [, player] of state.players) {
    player.position.x += player.velocity.x;
    player.position.y += player.velocity.y;
    player.position.z += player.velocity.z;
  }
};

const broadcastState = (server: GameServer): void => {
  const snapshot = serializeState(server.gameState);
  for (const [, client] of server.clients) {
    client.socket.send(snapshot);
  }
};

const serializeState = (state: GameState): ArrayBuffer => {
  const encoder = new TextEncoder();
  return encoder.encode(
    JSON.stringify({
      tick: state.tick,
      players: Object.fromEntries(state.players),
    }),
  ).buffer as ArrayBuffer;
};
C/S 架构的最大优势在于安全性。由于服务器拥有完整的游戏状态且是唯一的权威来源，客户端无法通过修改本地数据来影响游戏结果。服务器可以对客户端的每一个输入进行合法性验证，从根本上杜绝了大部分作弊手段。


混合网络架构
混合架构结合了 P2P 和 C/S 两种模型的优势，根据数据的重要程度选择不同的传输路径。关键的游戏状态（如生命值、得分、物品）通过权威服务器同步，而非关键的辅助数据（如语音、表情、非战斗区域的位置）可以通过 P2P 直连传输。


混合架构的一个典型应用是大逃杀类游戏。在这类游戏中，100 名玩家同时在线，服务器负责核心战斗判定和圈缩机制，而玩家之间的语音通信、非战斗区域的详细动画同步则通过 P2P 中继完成，大幅降低了服务器的带宽压力。


interface HybridConfig {
  serverEndpoint: string;
  peerConfig: RTCConfiguration;
  criticalChannels: string[];
  auxiliaryChannels: string[];
}

interface HybridNetworkManager {
  serverConnection: WebSocket;
  peerConnections: Map<string, RTCPeerConnection>;
  dataChannels: Map<string, RTCDataChannel>;
  config: HybridConfig;
}

const createHybridManager = (config: HybridConfig): HybridNetworkManager => ({
  serverConnection: new WebSocket(config.serverEndpoint),
  peerConnections: new Map(),
  dataChannels: new Map(),
  config,
});

const sendMessage = (manager: HybridNetworkManager, channel: string, data: ArrayBuffer): void => {
  if (manager.config.criticalChannels.includes(channel)) {
    manager.serverConnection.send(data);
  } else {
    const dc = manager.dataChannels.get(channel);
    if (dc && dc.readyState === 'open') {
      dc.send(data);
    }
  }
};
现代游戏引擎如 Unreal Engine 的 Replication 系统和 Unity 的 Netcode for GameObjects 都支持灵活配置网络拓扑。开发者可以根据游戏类型和规模选择最合适的架构，甚至在同一个游戏中根据不同场景动态切换。


网络模型选型策略
选择合适的网络模型需要综合考虑游戏类型、玩家规模、延迟容忍度和安全需求等因素。

Listen Server 是一种特殊的混合形态，其中一个玩家的客户端同时充当服务器角色。这种模式常用于合作类游戏，它避免了维护专用服务器的成本，但主机玩家拥有延迟优势，且主机断线会导致整局游戏中断。


选型时还需要考虑运营成本。P2P 模型几乎没有服务器成本，但需要 NAT 穿透和中继服务器作为后备。C/S 模型的服务器成本随玩家规模线性增长，需要合理规划服务器容量和弹性伸缩策略。


小结
    

  • P2P 模型适合小规模、低延迟需求的场景，核心挑战是确定性同步和 NAT 穿透
    • 

  • 客户端-服务器模型是主流架构，通过权威服务器保障安全性和一致性，但带来额外延迟
    • 

  • 混合架构按数据重要程度分流，在大规模场景下平衡了安全性和性能
    • 

  • 选型需要综合考虑游戏类型、玩家规模、延迟容忍度和运营成本
    • 

  • Listen Server 作为折中方案适用于合作类游戏
    • 

  • 现代引擎提供了灵活的网络拓扑配置能力
