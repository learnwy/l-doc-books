Part III · 网络与设计游戏网络与多人联机 简介网络基础 简介传输协议选型

传输协议选型

核心概念

传输协议是游戏网络通信的基础层，它决定了数据包如何在客户端和服务器之间可靠且高效地传递。游戏开发中最常用的两种传输协议是 TCP 和 UDP，它们在可靠性、延迟和吞吐量上有着根本性的差异。

TCP 提供可靠的有序字节流传输，通过三次握手建立连接、滑动窗口流控和重传机制保证数据不丢失。但这些保证也带来了额外的延迟开销。UDP 则是一种无连接的不可靠协议，它不保证数据包的到达顺序和可靠性，但提供了最低的传输延迟。

大多数现代游戏选择在 UDP 之上构建自定义可靠层，这样可以精细控制哪些数据需要可靠传输、哪些可以容忍丢失，从而在可靠性和延迟之间取得最佳平衡。

TCP 在游戏中的应用
TCP 在游戏网络中并非不可用，而是需要根据数据特性合理使用。对于不频繁但必须可靠的操作，TCP 仍然是最简洁的选择。


典型的 TCP 使用场景包括：玩家登录认证、游戏大厅、匹配系统、聊天系统、交易系统和排行榜查询。这些操作对延迟不敏感，但对数据完整性要求极高。


interface TcpGameClient {
  socket: WebSocket;
  reconnectAttempts: number;
  maxReconnects: number;
  heartbeatInterval: number;
  lastPong: number;
}

const createTcpClient = (url: string): TcpGameClient => {
  const socket = new WebSocket(url);
  const client: TcpGameClient = {
    socket,
    reconnectAttempts: 0,
    maxReconnects: 5,
    heartbeatInterval: 5000,
    lastPong: Date.now(),
  };
  return client;
};

const setupHeartbeat = (client: TcpGameClient): NodeJS.Timeout =>
  setInterval(() => {
    if (Date.now() - client.lastPong > client.heartbeatInterval * 3) {
      client.socket.close();
      return;
    }
    client.socket.send(JSON.stringify({ type: 'ping', t: Date.now() }));
  }, client.heartbeatInterval);

  type: 'login';

  clientVersion: string;

  type: 'login_result';
  success: boolean;
  sessionId: string;

const handleLogin = (client: TcpGameClient, token: string, version: string): Promise<LoginResponse> =>
  new Promise((resolve, reject) => {
    const request: LoginRequest = {
      type: 'login',
      token,
      clientVersion: version,
    };
    client.socket.send(JSON.stringify(request));

    const handler = (event: MessageEvent) => {
      const data = JSON.parse(event.data as string) as LoginResponse;
      if (data.type === 'login_result') {
        client.socket.removeEventListener('message', handler);
        data.success ? resolve(data) : reject(new Error('Login failed'));
      }
    };
    client.socket.addEventListener('message', handler);
  });
TCP 的核心问题在于队头阻塞（Head-of-Line Blocking）。当一个 TCP 数据包丢失时，后续所有数据包都必须等待该包重传成功后才能被处理，即使后续包已经到达。在游戏场景中，这意味着一个丢失的旧数据包会阻塞最新的游戏状态更新，造成突然的卡顿。


Nagle 算法也是 TCP 在游戏中需要注意的问题。该算法会缓冲小数据包合并发送以提高带宽利用率，但这引入了额外的发送延迟。游戏客户端通常需要设置 TCP_NODELAY 选项禁用 Nagle 算法。


UDP 与自定义可靠层
基于 UDP 构建的自定义可靠层是现代游戏网络的核心技术。它允许开发者为不同类型的数据选择不同的传输策略，而不是像 TCP 那样对所有数据一视同仁。


自定义可靠层通常实现以下功能：序列号追踪、选择性确认应答（SACK）、RTT 估算、按需重传和多通道复用。


const enum ChannelType {
  Unreliable = 0,
  Reliable = 1,
  ReliableOrdered = 2,
}

interface PacketHeader {
  protocolId: number;
  sequence: number;
  ack: number;
  ackBits: number;
  channelId: number;
  channelType: ChannelType;
}

interface ReliableChannel {
  channelId: number;
  type: ChannelType;
  localSequence: number;
  remoteSequence: number;
  sentPackets: Map<number, SentPacketInfo>;
  receiveBuffer: Map<number, Uint8Array>;
  ackBitfield: number;
}

interface SentPacketInfo {
  sequence: number;
  sendTime: number;
  data: Uint8Array;
  acked: boolean;
  retransmitCount: number;
}

const createReliableChannel = (id: number, type: ChannelType): ReliableChannel => ({
  channelId: id,
  type,
  localSequence: 0,
  remoteSequence: 0,
  sentPackets: new Map(),
  receiveBuffer: new Map(),
  ackBitfield: 0,
});

const sendPacket = (channel: ReliableChannel, data: Uint8Array): PacketHeader => {
  const seq = channel.localSequence++;
  const header: PacketHeader = {
    protocolId: 0x47414d45,
    sequence: seq,
    ack: channel.remoteSequence,
    ackBits: channel.ackBitfield,
    channelId: channel.channelId,
    channelType: channel.type,
  };

  if (channel.type !== ChannelType.Unreliable) {
    channel.sentPackets.set(seq, {
      sequence: seq,
      sendTime: performance.now(),
      data,
      acked: false,
      retransmitCount: 0,
    });
  }
  return header;
};

const processAck = (channel: ReliableChannel, ack: number, ackBits: number, rttEstimator: RttEstimator): void => {
  const info = channel.sentPackets.get(ack);
  if (info && !info.acked) {
    info.acked = true;
    const rtt = performance.now() - info.sendTime;
    updateRtt(rttEstimator, rtt);
  }

  for (let i = 0; i < 32; i++) {
    if (ackBits & (1 << i)) {
      const seq = ack - 1 - i;
      const prev = channel.sentPackets.get(seq);
      if (prev) prev.acked = true;
    }
  }
};

interface RttEstimator {
  smoothedRtt: number;
  rttVariance: number;
  rto: number;
}

const createRttEstimator = (): RttEstimator => ({
  smoothedRtt: 100,
  rttVariance: 50,
  rto: 300,
});

const updateRtt = (est: RttEstimator, sample: number): void => {
  const alpha = 0.125;
  const beta = 0.25;
  est.rttVariance = (1 - beta) * est.rttVariance + beta * Math.abs(est.smoothedRtt - sample);
  est.smoothedRtt = (1 - alpha) * est.smoothedRtt + alpha * sample;
  est.rto = est.smoothedRtt + 4 * est.rttVariance;
};
通道类型的选择直接影响游戏体验。位置更新使用不可靠通道，因为过时的位置数据没有价值；射击和技能释放使用可靠通道，因为这些事件不能丢失；聊天消息使用可靠有序通道，因为消息顺序很重要。


WebRTC 与现代传输方案
WebRTC 为基于浏览器的游戏提供了 P2P 数据传输能力。它的 DataChannel API 支持可靠和不可靠两种模式，底层使用 SCTP over DTLS over UDP，同时内置了 NAT 穿透（ICE/STUN/TURN）支持。


interface WebRTCGameConnection {
  peerConnection: RTCPeerConnection;
  reliableChannel: RTCDataChannel;
  unreliableChannel: RTCDataChannel;
  iceCandidates: RTCIceCandidate[];
}

const createGameConnection = async (
  config: RTCConfiguration,
  signalingServer: WebSocket,
): Promise<WebRTCGameConnection> => {
  const pc = new RTCPeerConnection(config);

  const reliable = pc.createDataChannel('reliable', {
    ordered: true,
  });

  const unreliable = pc.createDataChannel('unreliable', {
    ordered: false,
    maxRetransmits: 0,
  });

  const candidates: RTCIceCandidate[] = [];

  pc.onicecandidate = (event) => {
    if (event.candidate) {
      candidates.push(event.candidate);
      signalingServer.send(JSON.stringify({ type: 'ice', candidate: event.candidate }));
    }
  };

  const offer = await pc.createOffer();
  await pc.setLocalDescription(offer);
  signalingServer.send(JSON.stringify({ type: 'offer', sdp: offer }));

  return {
    peerConnection: pc,
    reliableChannel: reliable,
    unreliableChannel: unreliable,
    iceCandidates: candidates,
  };
};

协议选型决策框架
选择传输协议时，需要根据游戏类型和具体需求进行系统化决策。


对于大多数实时竞技游戏，推荐的方案是：使用自定义 UDP 可靠层作为主通信通道，同时维护一条 TCP/WebSocket 连接用于登录、匹配等辅助功能。这样既保证了游戏操作的低延迟，又简化了非实时功能的开发。


游戏的 Tick Rate 也会影响协议选型。20-30 Tick 的游戏（如 MMO）对延迟容忍度较高，TCP 的额外延迟可能在可接受范围内。而 64-128 Tick 的竞技 FPS 游戏，每个 Tick 的时间预算只有 8-16ms，TCP 的队头阻塞和重传延迟将直接影响游戏体验，必须使用 UDP 方案。


小结
    

  • TCP 适用于登录、聊天等不频繁但需要可靠的场景，注意禁用 Nagle 算法
    • 

  • UDP 是实时游戏数据传输的首选，但需要在其上构建自定义可靠层
    • 

  • 自定义可靠层的核心是多通道复用和按需可靠性，避免了 TCP 的队头阻塞问题
    • 

  • WebRTC DataChannel 为浏览器游戏提供了原生的 P2P 数据传输能力
    • 

  • QUIC 是未来游戏网络的重要方向，提供了多路复用和 0-RTT 连接建立
    • 

  • 协议选型需要综合考虑平台、实时性需求和 Tick Rate
