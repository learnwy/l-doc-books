关卡原型与迭代

核心概念

关卡原型（Level Prototype）是关卡设计从概念到成品的关键桥梁。原型的目的不是制作精美的关卡，而是以最低成本验证设计假设——空间布局是否合理、节奏感是否舒适、教学是否有效、挑战是否公平。关卡设计的行业共识是：一个关卡至少需要经历三到五轮原型迭代才能达到发行品质。

关卡原型遵循"保真度递进"原则——从最粗糙的概念验证逐步提升到接近成品的精细度。每个保真度层级回答不同的设计问题，过早投入高保真资源是最大的效率陷阱。

纸面原型与空间规划
纸面原型是关卡设计的起点，用纸笔或简单的数字工具绘制关卡的俯视图和流程图。这个阶段的价值在于零成本的快速迭代——在纸上修改一条路径只需几秒钟，而在引擎中修改可能需要数小时。


纸面原型需要回答的核心问题：


路径结构——主路径是否清晰？支路数量是否合适？是否有无意义的死胡同？


空间比例——各区域的相对大小是否匹配其功能？Boss 房是否足够大？过渡空间是否过长？


节奏分布——战斗区、探索区、叙事区的交替是否合理？是否存在连续的同类区域？


连通性——区域间的连接是否符合导航直觉？回溯路线是否被考虑？


interface PaperPrototype {
  zones: Zone[];
  connections: Connection[];
  criticalPath: string[];
}

interface Zone {
  id: string;
  type: 'combat' | 'exploration' | 'narrative' | 'puzzle' | 'boss' | 'safe';
  relativeSize: 'small' | 'medium' | 'large';
  intensity: number;
  mechanics: string[];
}

interface Connection {
  from: string;
  to: string;
  type: 'direct' | 'locked' | 'shortcut' | 'hidden';
  bidirectional: boolean;
}

function validatePaperPrototype(proto: PaperPrototype): ValidationResult {
  const issues: string[] = [];

  const deadEnds = proto.zones.filter(
    (zone) => proto.connections.filter((c) => c.from === zone.id || c.to === zone.id).length <= 1,
  );
  if (deadEnds.length > proto.zones.length * 0.2) {
    issues.push('excessive_dead_ends');
  }

  for (let i = 1; i < proto.criticalPath.length; i++) {
    const prevZone = proto.zones.find((z) => z.id === proto.criticalPath[i - 1])!;
    const currZone = proto.zones.find((z) => z.id === proto.criticalPath[i])!;
    if (Math.abs(prevZone.intensity - currZone.intensity) > 4) {
      issues.push(`intensity_spike_at_${currZone.id}`);
    }
  }

  return { valid: issues.length === 0, issues };
}
纸面原型的工具选择取决于项目规模。小型独立团队用方格纸就足够，大型项目则可以使用 Miro 或 Figma 进行协作式的空间规划，方便与关卡设计组和美术团队共享和讨论。


灰盒构建与度量验证
灰盒原型（Greybox）是用最简单的几何体（方块、圆柱、斜面）在游戏引擎中搭建的可运行关卡。它是关卡设计中最重要的阶段——在灰盒中发现的问题修复成本最低，而遗漏到后期的问题修复成本则呈指数增长。


灰盒构建的核心原则是"只用基础形状"。禁止使用任何美术资源——没有纹理、没有模型、没有特效。这种"丑陋"的视觉确保评审时所有人都聚焦于设计本身而非视觉表现。

灰盒的另一个关键实践是"度量验证"——将角色放入空间中，实际测量每个跳跃间距、掩体高度和视线距离是否与度量表匹配。这种测量应该系统化，而非凭感觉判断。


interface GreyboxMetricsTest {
  testPoints: Array<{
    position: Vector3;
    type: 'jump_gap' | 'cover_height' | 'sight_distance' | 'ceiling_height';
    measuredValue: number;
    expectedRange: [number, number];
  }>;
}

function runMetricsValidation(test: GreyboxMetricsTest): MetricsReport {
  const results = test.testPoints.map((point) => ({
    ...point,
    passed: point.measuredValue >= point.expectedRange[0] && point.measuredValue <= point.expectedRange[1],
    deviation:
      point.measuredValue < point.expectedRange[0]
        ? point.measuredValue - point.expectedRange[0]
        : point.measuredValue > point.expectedRange[1]
          ? point.measuredValue - point.expectedRange[1]
          : 0,
  }));

  return {
    totalTests: results.length,
    passed: results.filter((r) => r.passed).length,
    failed: results.filter((r) => !r.passed),
    passRate: results.filter((r) => r.passed).length / results.length,
  };
}
游戏测试与反馈收集
游戏测试（Playtesting）是关卡原型迭代的核心驱动力。设计者永远无法客观评估自己的关卡——因为他们知道所有的秘密和解法。只有让不了解关卡的测试者来玩，才能揭示真实的设计问题。


游戏测试的三种层次：


开发者测试——团队内部的日常测试。优势是快速且频繁，劣势是测试者对关卡过于熟悉。适用于功能验证和基础度量检查。


焦点测试——邀请目标用户群体的小规模测试（5-8 人）。使用出声思维协议（Think-Aloud Protocol），让测试者在游玩时持续说出想法。这是发现导航问题和教学缺陷的最有效方法。


大规模测试——内部 beta 或外部体验版，数百到数千名测试者。通过遥测数据定量分析关卡表现。适用于难度调优和平衡验证。

焦点测试的执行要点：


不要打断测试者——即使他们明显走错路或操作失误，也不要提示。记录下他们困惑的每个时刻，这些都是设计需要改进的信号。


不要问"你觉得好玩吗"——这类主观问题无法产生可操作的反馈。改为"你刚才在那个房间停了很久，能说说你当时在想什么吗？"


迭代策略与收敛原则
关卡迭代遵循"先粗后细、先整体后局部"的原则。早期迭代聚焦大方向问题（路径结构是否合理、节奏感是否舒适），后期迭代关注细节调优（某个跳跃点的精确距离、某个敌人的放置角度）。


迭代收敛的"三轮法则"：


第一轮（探索性迭代）——大幅度修改。可能重构整个区域的布局、删除或新增路径、改变空间比例。这一轮的目标是找到"对的方向"。


第二轮（调整性迭代）——中幅度修改。在已确定的结构框架内调整细节，如改变敌人配置、调整跳跃距离、优化视觉引导。


第三轮（抛光性迭代）——小幅度修改。微调参数、修复边缘情况、优化流畅度。这一轮的改动不应改变关卡的基本体验。


interface IterationPlan {
  round: number;
  scope: 'structural' | 'adjustmental' | 'polish';
  changeLimit: number;
  focusAreas: string[];
  exitCriteria: {
    metric: string;
    threshold: number;
  }[];
}

const iterationStrategy: IterationPlan[] = [
  {
    round: 1,
    scope: 'structural',
    changeLimit: Infinity,
    focusAreas: ['path_structure', 'pacing', 'spatial_proportion'],
    exitCriteria: [
      { metric: 'completion_rate', threshold: 0.6 },
      { metric: 'navigation_confusion_rate', threshold: 0.3 },
    ],
  },
  {
    round: 2,

    changeLimit: 20,

    exitCriteria: [

      { metric: 'average_deaths', threshold: 5 },
    ],
  },
  {
    round: 3,
    scope: 'polish',
    changeLimit: 10,
    focusAreas: ['parameter_tuning', 'edge_cases', 'flow_optimization'],
    exitCriteria: [

      { metric: 'satisfaction_score', threshold: 7.5 },
    ],

每轮迭代都应有明确的退出标准（Exit Criteria）。没有退出标准的迭代会陷入"无限打磨"陷阱——关卡永远不够完美，但项目有截止日期。设计者需要学会在"足够好"和"完美"之间做出务实的判断。


小结
    

  • 关卡原型遵循"保真度递进"原则，从纸面到灰盒到白盒逐步提升
    • 

  • 灰盒是最重要的原型阶段，此阶段发现的问题修复成本最低
    • 

  • 度量验证应系统化执行，确保每个空间元素与角色运动参数匹配
    • 

  • 焦点测试使用出声思维协议，不打断测试者、不问主观问题
    • 

  • 迭代收敛遵循"三轮法则"：探索性→调整性→抛光性，逐步缩小改动范围
    • 

  • 每轮迭代必须设定明确的退出标准，避免"无限打磨"陷阱
