确定性指标与 LLM-as-judge

评测体系的判定器分为两大类：确定性指标用代码做精确检查，结果可复现、零成本、绝对可信；LLM-as-judge 用一个模型给另一个模型的输出打分，能处理「忠实度」「有用性」这类无法写成正则的判断类标准，但自身带有噪声与偏差。成熟的评测体系几乎总是两者混用——关键是知道每类问题该交给谁，以及如何让 judge 的判断值得信赖。

核心概念

判定器（grader）负责把「一条输出」映射为「一个分数或通过标记」。它分为两大类：确定性指标由代码做精确检查，可复现、零成本、绝对可信但只看形式；LLM-as-judge 由模型依据评分标准做语义判断，能覆盖「忠实度」「有用性」这类写不成正则的标准，但带有可预测的系统性偏差，必须经过人工校准才能采信。

graph TD
    OUT["被测系统的输出"] --> DET{"存在客观可程序化的判定标准?"}
    DET -- 是 --> C1["确定性指标:解析/schema/工具调用/禁词/精确比对"]
    DET -- 否 --> J["LLM-as-judge:先推理再给结构化分数+理由"]
    C1 --> MIX["混用决策表:确定性守底线,judge 管上限"]
    J --> CAL["人工标注校准:一致率/kappa,迭代 rubric"]
    CAL --> MIX

这张图的两条分支对应一个总原则：能下沉为确定性检查的判断尽量下沉，留给 judge 的每一个维度都要配上经过人工校准的 rubric，因为判定器本身也是被测系统的一部分。

确定性指标：能用代码判定的绝不用模型

凡是存在客观、可程序化判定标准的属性，都应当用确定性检查，因为它快、免费、无噪声，且失败信息精确到具体条目。常见的确定性指标包括：

指标 检查内容 实现方式
解析成功率 输出能否被解析为合法的 JSON、XML 或指定结构 解析器直接验证，配合 schema 校验（如 JSON Schema）
工具调用正确性 是否调用了预期的工具、参数名与类型是否正确、调用顺序是否合法 与期望调用序列做结构化比对
引用存在性 声称引用的文档编号是否真实存在于检索结果中、链接是否可解析 集合包含检查、URL 校验
禁词与敏感内容 是否出现黑名单词汇、内部代号、竞品名称、PII 模式 词表匹配、正则、专用 PII 检测器
格式合规 长度上限、语言种类、是否包含要求的小节、Markdown 结构是否完整 长度统计、语言检测、结构解析
精确答案比对 分类标签、抽取字段、数值结果与参考答案一致 等值或归一化后比较

确定性指标的另一重价值是作为流水线的前置闸门：解析都失败的输出没有必要再送去 judge 打分，既省成本又避免 judge 对垃圾输出给出误导性分数。这类检查同时可以复用为运行时护栏——评测期定义一次，离线回归与线上拦截共用同一套逻辑。

确定性指标的局限同样清楚：它只能判定「形式正确」，无法判定「内容好」。一段 JSON 完全合法、引用编号全部真实，但答案可以驴唇不对马嘴。这就是第二类判定器存在的理由。

LLM-as-judge：把判断类标准交给模型

LLM-as-judge 指用一个（通常更强的）模型，依据给定的评分标准对被测系统的输出打分或做选择。它适合处理需要语义理解与价值判断的维度：

维度 典型问题 判定要点
忠实度（faithfulness） 回答是否只依据给定上下文，有没有编造 把回答拆成原子断言，逐条核对是否被上下文支持
正确性（correctness） 回答与参考答案的事实要点是否一致 对照要点清单逐项判定包含、矛盾或遗漏
有用性（helpfulness） 是否真正解决了用户的问题，而非答非所问 结合用户意图判断完整性与可操作性
语气与风格 是否符合品牌语气、是否礼貌、是否过度道歉 依据带行为描述的 rubric 判定
安全性 是否给出有害建议、是否越权承诺 依据安全政策清单判定

judge 的提示工程有几条公认的实践：给出具体的 rubric 而不是抽象形容词；要求 judge 先写出推理过程再给结论（链式推理显著提升判定质量）；提供少量打分示例对齐尺度；输出结构化结果（分数加理由）便于聚合与抽查。

judge 的系统性偏差

LLM-as-judge 不是中立的裁判，研究与实践反复证实它带有可预测的偏差。使用前必须了解，否则评测结果会系统性失真：

偏差 表现 缓解手段
位置偏差 成对比较时偏好排在某个位置（常见偏好第一个）的答案 交换顺序各评一次，结果不一致则记为平局
长度偏差 偏好更长、更详尽的回答，即使冗长并无增益 在 rubric 中显式惩罚冗余；对比时控制长度变量
自恋偏好（self-preference） 偏好与自己风格相近或自己生成的答案 用与被测模型不同家族的模型当 judge，或多 judge 投票
格式与表面特征偏好 偏好带列表、标题、自信语气的回答，忽视实质内容 rubric 强调按事实要点评分；抽查理由是否言之有物
尺度漂移 单点打分时分数集中在高分段，区分度差 改用成对比较或要点核对；为每档分数提供锚定示例

这些偏差的共同含义是：judge 的原始分数不可直接当真，必须经过校准。

校准：让 judge 与人对齐

校准的核心方法是把 judge 当作一个待验证的分类器，用人工标注做基准来测量它：

  • 建立人工基准。 抽取一两百条被测输出，由人按同一份 rubric 标注，作为「真值」。
  • 测量一致性。 计算 judge 与人工标注的一致率、相关系数或 Cohen's kappa。同时测量人与人之间的一致率作为天花板——judge 不可能比标注标准本身更一致。
  • 迭代 judge 提示。 一致率不足时，分析分歧案例，细化 rubric、补充锚定示例、调整判定粒度，重新测量。judge 的提示本身也应当版本化并回归测试。
  • 持续抽查。 上线后定期抽取 judge 的判定让人复核，监控一致率是否漂移（被测系统分布变化或 judge 模型升级都会引起漂移）。

在打分形态上，两种主流方案各有适用场景：

方案 优点 缺点 适用
成对比较（pairwise） 判定更稳定，区分度高，对尺度漂移免疫 只给相对结论，成本随候选数增长，需处理位置偏差 模型选型、prompt A/B、排行榜
单点打分（pointwise） 给出绝对分数，可跨时间追踪，可设阈值告警 尺度不稳，分数挤在高段，跨版本可比性弱 持续回归监控、线上采样评分
二元判定加要点核对 把主观打分拆成多个客观小判断，一致率最高 需要为每条样本写要点清单，标注成本前移 忠实度、正确性这类可分解的维度

实践经验是尽量把判断「降维」：与其让 judge 给有用性打一到五分，不如拆成若干个是否问题（是否回答了问题、是否包含要点 A、是否出现编造），每个问题二元判定后再聚合。二元判定的人机一致率远高于多档打分。

混用决策表

为某个质量维度选择判定器时，按下表决策：

待检属性 推荐判定器 说明
结构、格式、可解析性 确定性 解析器与 schema 校验，零成本零噪声
工具调用、API 参数 确定性 结构化比对期望调用
禁词、PII、合规黑名单 确定性 词表与正则，兼作运行时护栏
有唯一标准答案的任务 确定性 归一化后精确比对
事实正确性（有参考要点） judge 做要点核对 二元判定逐项核对，一致率最高
忠实度、幻觉检测 judge 断言级核对上下文支持度
有用性、语气、写作质量 judge 配 rubric 必须先与人工标注校准
两个版本孰优孰劣 judge 成对比较 交换位置去偏，配合确定性指标交叉验证

总原则：确定性检查负责「不出错的底线」，LLM-as-judge 负责「足够好的上限」；能下沉为确定性检查的判断尽量下沉，留给 judge 的每一个维度都配上经过人工校准的 rubric。判定器本身也是被测系统的一部分——它的提示、版本与一致率指标，应当和被测应用享受同等的工程待遇。

小结

  • 判定器分两类：确定性指标快、免费、无噪声且失败信息精确，但只能判形式；LLM-as-judge 能判语义，但带噪声与偏差，必须校准。
  • 确定性检查的另一重价值是作为流水线前置闸门与运行时护栏：解析都失败的输出不必再送给 judge，评测期定义一次即可离线与线上共用。
  • judge 适合忠实度、正确性、有用性、语气、安全性这类需要语义理解与价值判断的维度；提示上要给具体 rubric、要求先推理后结论、提供打分示例、输出结构化结果。
  • judge 的系统性偏差可预测，至少包括位置偏差、长度偏差、自恋偏好、表面特征偏好与尺度漂移，各有对应的缓解手段，原始分数不可直接当真。
  • 校准把 judge 当待验证分类器：建立人工基准、测量一致率（并测量人与人一致率作为天花板）、迭代 judge 提示、上线后持续抽查。
  • 打分形态上，成对比较更稳定、单点打分可跨时间追踪、二元判定加要点核对一致率最高；经验法则是尽量把判断「降维」成若干是否问题再聚合。
