评测驱动的迭代节奏

很多团队改 prompt 的方式仍停留在「在 playground 里试两个例子，看着不错就上线」。这种方式在原型期没问题，但产品有了真实用户之后，每一次未经验证的改动都是在拿线上质量赌运气——prompt 的改动对不同输入分布的影响高度非线性，修好你盯着的三个案例、悄悄弄坏另外三十个，是再常见不过的事。评测驱动的迭代把「改 prompt」从手艺活变成工程循环：每次改动有假设、有离线回归、有受控放量、有线上验证、有沉淀。

核心概念

评测驱动的迭代把一次质量改动看作可证伪的实验：先写下「改什么、预期改善哪个指标、可能伤害哪个指标」，再经离线回归、金丝雀放量、线上对比三条闸门，最后无论成败都沉淀为可检索的记录。它依赖两组资产——被测行为的版本化（prompt、模型、检索配置）与判定标准的版本化（golden 集、rubric、judge 提示）。

graph TD
    H["提出假设:一句可证伪的陈述"] --> V["实施改动:带版本号、可一键回滚"]
    V --> OFF["离线回归:golden 集 + 失败簇,目标指标改善、守护指标不退化"]
    OFF --> CAN["金丝雀放量:1%-5% 真实流量"]
    CAN --> AB["线上对比:A/B 或 interleaving"]
    AB --> DEC{"达到预设决策标准?"}
    DEC -- 是 --> FULL["全量发布"]
    DEC -- 否 --> ARCH["归档被否决的改动与数据"]
    FULL --> PIT["沉淀:更新评测集、记录结论"]
    ARCH --> PIT
    PIT -. 新失败成为假设来源 .-> H

两个容易被省略但不该省的环节：一是假设陈述（事后再解释任何结果都能自圆其说），二是失败实验的沉淀（避免三个月后另一个同事把同样的想法再试一遍）。离线回归是这条链上性价比最高的闸门——便宜、快、可重复。

一次迭代的标准循环

完整的循环包含六个阶段，每个阶段有明确的产物与通过条件。

阶段 做什么 产物 / 通过条件
提出假设 基于失败挖掘或反馈数据，明确「改什么、预期改善哪个指标、可能伤害哪个指标」 一句可证伪的假设陈述
实施改动 修改 prompt、检索参数或模型配置，作为新版本登记 带版本号的变更，可一键回滚
离线回归 在 golden 集与相关失败簇上对比新旧版本 目标指标改善、守护指标不退化
金丝雀放量 对小比例真实流量（如 1%–5%）启用新版本 在线指标与错误率无异常
线上对比 A/B 或 interleaving 对比新旧版本的反馈与隐式信号 达到预设的决策标准
沉淀 记录结论、更新评测集、归档实验 无论成败都留下可检索的记录

两个容易被省略但不该省的环节。一是假设陈述：写下「把检索片段数从 4 提到 8，预期降低答非所问类失败，风险是延迟与跑题增加」，事后才能判断实验成功与否，否则任何结果都能被事后解释。二是失败实验的沉淀：被否决的改动连同数据归档，避免三个月后另一个同事把同样的想法再试一遍。

离线回归是这条链上性价比最高的闸门。它便宜（不消耗真实用户）、快（分钟级出结果）、可重复。守护指标的概念尤其重要：除了你想改善的指标，固定监控一组「不许变差」的指标（格式合规率、拒答率、延迟、成本），防止局部优化造成全局回退。

prompt 版本管理与 A/B

prompt 是行为定义，应当享受和代码同级的工程待遇。

  • 版本化存储：prompt 模板进版本控制（Git 或专门的 prompt 管理平台），每个版本有唯一标识；线上 trace 记录当次调用使用的 prompt 版本，否则线上问题无法归因到具体版本。
  • 模板与参数分离：把易变的业务内容（少样本示例、检索片段）与稳定的指令骨架分开管理，缩小每次变更的 diff 面。
  • 环境隔离：开发、预发、生产使用各自的版本指针，晋级是显式操作而非直接改生产配置。
  • 回滚预案：版本指针切换应当秒级生效，出问题先回滚再分析。

线上 A/B 有几个 LLM 应用特有的注意点。其一，按用户而不是按请求分桶——同一用户在两个版本间反复横跳会污染会话体验与隐式信号。其二，反馈信号稀疏导致 A/B 需要的样本量比传统功能实验大得多，低流量产品可以用 interleaving（同一请求生成两版、让用户选择）或在线 LLM-as-judge 的对比评分作为更高灵敏度的代理。其三，注意新颖性效应与时间混杂：观察期太短的「显著改善」常常是用户对变化本身的反应。其四，预先写下决策标准（提升多少、置信度多少就全量），避免盯着实时面板择时收割。

该动哪一层：决策框架

线上出现质量问题时，可调的旋钮很多：prompt、少样本示例、检索、上下文工程、工具定义、模型本身。乱调的代价是每个旋钮都动一点、不知道哪个起了作用。一个实用的决策框架是按归因证据和改动成本排序。

失败证据 优先动作 理由
检索结果里没有正确依据 动检索：chunking、索引、query 改写、rerank prompt 救不了不存在的信息
依据在上下文里但模型答错 动 prompt：指令措辞、示例、输出约束 改动成本最低、迭代最快
指令已经清晰但模型仍不稳定遵循 加结构性约束：structured output、校验重试、拆分步骤 确定性手段优于反复措辞
多类任务互相牵制、prompt 越改越长 拆分路由：按任务类型分 prompt 或分流程 单一巨型 prompt 是常见的腐化形态
同一问题在多家强模型上都失败 动任务设计：拆解任务、补充工具、收窄产品边界 问题超出当代模型能力
prompt 与检索已到瓶颈、新模型在评测集上显著更好 换模型 用全量回归与成本核算支撑决策

经验法则：自上而下先验证便宜的假设（prompt、示例），但要带着 trace 证据走，而不是默认一切问题都是 prompt 问题。换模型是改动面最大的选项——它会同时改变所有任务的行为分布，必须有覆盖面足够的评测集才能负责任地做这个决定；这也是为什么模型迁移往往成为检验一个团队评测资产厚度的时刻。

评测资产是团队的知识沉淀

把视角拉长，评测体系最被低估的价值是组织层面的：它是团队对「这个产品什么叫好」的可执行定义。

  • golden 集是需求的具象化。新成员读一百个带期望行为的案例，比读十页产品文档更快理解产品边界与质量标准。
  • 失败簇与归因统计是产品的「已知问题地图」。它让团队的优化讨论从「我感觉最近变笨了」升级为「跑题类失败占比从 8% 升到 14%，集中在长文档场景」。
  • 实验归档是决策记忆。哪些方向试过、为什么放弃、当时的数据如何，这些记录防止团队在人员流动后反复踩同一个坑。
  • judge prompt 与评分细则是质量标准的版本化表达。对「好回答」的理解变化时，diff 一目了然。

维护上的纪律：评测资产要有 owner 与例行维护节奏，定期清理与线上分布脱节的陈旧案例；评测集本身的变更也要走评审，因为改判定标准等于改产品定义。当 prompt 因模型升级全部重写、甚至框架整体更换时，代码可能大面积作废，而评测集、失败库与实验记录几乎完整保值——它们沉淀的是对问题域的理解，这正是评测资产作为团队知识载体的核心理由。

常见反模式

迭代节奏被破坏时，通常不是流程缺环，而是某个环节被悄悄绕过。

  • playground 试几个例子就上线：样本有偏、记忆有偏，修好盯着看的三个案例、弄坏另外三十个，是原型期之后最贵的错误。
  • 跳过假设陈述与守护指标：没有可证伪的陈述，任何结果都能被事后解释；没有「不许变差」的指标，局部优化会带来全局回退。
  • 按请求而不是按用户分桶：同一用户在两个版本间反复横跳，污染会话体验与隐式信号，A/B 结论随之失真。
  • 盯着实时面板择时收割：事先不写决策标准，看到指标好就宣布胜利，本质上是多重比较下的假阳性。
  • 乱调旋钮：每个可调项都动一点、不知道哪个起了作用，应当按归因证据与改动成本排序，带着 trace 证据自上而下验证便宜的假设。
  • 只动 prompt 的惯性：把一切问题都默认成 prompt 问题，而检索缺失、指令已清晰但模型不稳定遵循等情形，需要的是结构性约束或换任务设计，而非反复措辞。

小结

  • 评测驱动的迭代把改 prompt 变成工程循环：假设、实施、离线回归、金丝雀放量、线上对比、沉淀六个阶段，每阶段有明确产物与通过条件。
  • 假设陈述与失败实验沉淀是最容易被省略却不该省的两步；离线回归是性价比最高的闸门，守护指标（格式合规率、拒答率、延迟、成本）防止局部优化造成全局回退。
  • prompt 应享受与代码同级的工程待遇：版本化存储、模板与参数分离、环境隔离、秒级回滚；线上 A/B 要注意按用户分桶、样本量需求大、新颖性效应与预先写下决策标准。
  • 该动哪一层要有决策框架：按归因证据与改动成本排序，检索缺失动检索、依据在但答错动 prompt、指令清晰仍不稳定加结构性约束、多任务互相牵制则拆分路由、多家强模型都失败则动任务设计、最后才考虑换模型。
  • 评测资产是团队对「这个产品什么叫好」的可执行定义：golden 集具象化需求、失败簇是已知问题地图、实验归档是决策记忆、judge 提示是质量标准的版本化表达。
  • 常见反模式包括 playground 试几例就上线、跳过假设与守护指标、按请求分桶、择时收割、乱调旋钮与只动 prompt 的惯性，它们破坏的正是迭代循环的可证伪性与可比性。
