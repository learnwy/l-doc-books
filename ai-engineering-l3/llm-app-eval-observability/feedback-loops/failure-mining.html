失败样本挖掘

线上轨迹里埋着团队最需要的评测素材：真实用户在真实场景下触发的真实失败。失败样本挖掘（failure mining）就是把这些坏案例从海量正常流量中系统性地筛出来、归因分类、脱敏入库，最终变成驱动修复与回归的评测资产。与凭印象收集「群里有人反馈了一个 bug」相比，系统化挖掘的差别在于覆盖面、可重复性和优先级排序——它能告诉你哪类失败最多、最严重、最值得先修。

核心概念

失败挖掘是一条从线上流量到评测资产的加工流水线：候选筛选产出坏例、归因分类回答「该由哪个环节负责」、脱敏去重把坏例变成可入库的资产、最终驱动针对性修复并回灌线上验证。它的每一步都有明确产物，跳过任何一步都会让失败库退化成「一堆不知道为什么坏的坏例子」。

graph TD
    S1["候选筛选:低分抽样 / 负反馈 / 高重试 / 转人工 / 聚类 / 硬错误 / 护栏"] --> S2["归因分类:检索/生成/工具/上下文/意图/越界"]
    S2 --> S3["脱敏:替换 PII,等价替换保住可复现性"]
    S3 --> S4["去重:精确哈希 + 语义聚类,每簇留代表并记频次"]
    S4 --> S5["人工审核写入期望行为"]
    S5 --> G["进入 golden 集并版本化"]
    G --> FIX["针对性修复:prompt / 检索 / 工具 / 结构手段"]
    FIX -. 回查出现频率下降 .-> S1

这张图的关键读法是：归因必须基于 trace 证据而非只看最终回答——同样一句错误回答，依据在不在检索结果里决定了该修检索还是该修 prompt，跳过这一步的「修复」经常修错地方；而闭环验证（修复后回查同一失败模式的线上频率是否下降）才是修复真正生效的证据。

候选失败的来源与筛选策略

没有任何单一信号能可靠地标出失败，实践中通常并行运行多条筛选策略，各自产出候选队列，再合并去重。

筛选策略 数据来源 召回特点 误报特点
低分抽样 在线 LLM-as-judge 或规则打分的低分段 覆盖广、可量化 judge 本身的偏差会传导
负反馈关联 点踩、低评分、负面评论关联的 trace 精确率高 量极少、受反馈偏差影响
高重试请求 同一意图短窗口内多次 regenerate / 改述 捕捉「judge 看不出」的不满 探索型重试混入
转人工 / 升级 客服场景的 escalation 事件 强负面、业务意义明确 仅适用于特定产品形态
异常模式聚类 对输出或 embedding 做聚类，找离群簇 能发现未知失败模式 需要人看簇才能定性
硬性错误信号 JSON 解析失败、工具调用报错、超时、截断 确定性高、零误报 只覆盖结构性失败
守护规则命中 拒答模板、敏感词、幻觉检测器触发 定向、可解释 规则覆盖面有限

几点实践经验。低分抽样不要只取最低分：最低分段往往被少数几类「显而易见的失败」霸占，按分数分桶分层抽样能让长尾失败也进入视野。异常聚类适合周期性跑而非实时跑，它的价值是发现「你还没想到要监控的失败类型」，比如某次模型升级后突然出现的新口癖或新格式错误。高重试请求是被低估的金矿——用户懒得点踩但愿意再试一次，重试前后两次输出的对比常常直接揭示模型哪里没接住。

失败案例的归因分类

筛出候选只是第一步，不归因的失败库只是一堆「不知道为什么坏」的坏例子。归因的目标是回答：这个失败应该由系统的哪个环节负责。常用的一级分类沿着 RAG / agent 应用的执行链展开。

归因类别 典型表现 验证方法
检索失败 答案所需信息不在检索结果里；命中无关文档 检查 trace 中的检索片段是否包含正确依据
生成失败 检索到了正确依据但模型答错、幻觉、格式错误 把同样上下文重放给模型，观察是否稳定复现
工具失败 工具选错、参数错、工具本身报错或返回脏数据 单独审查工具调用的输入输出对
上下文失败 历史轮次污染、上下文超长被截断、系统指令被覆盖 对比裁剪上下文后的重放结果
意图理解失败 用户问题本身含糊，模型理解成另一个意思 人工判断问题是否可被合理消歧
预期之外的输入 越界请求、对抗性输入、产品本不支持的任务 对照产品边界定义

归因可以先用 LLM 辅助粗分（把完整 trace 喂给一个归因 prompt，输出类别加理由），再由人工抽检校准。关键纪律是：归因必须基于 trace 证据而不是只看最终回答。同样一句错误回答，依据在不在检索结果里决定了该修检索还是该修 prompt，跳过这一步的「修复」经常修错地方。归因结果要回写到失败记录上，成为后续统计「哪个环节贡献了多少失败」的基础。

脱敏、去重与进入 golden 集

确认有价值的失败案例要沉淀进 golden 评测集，但中间隔着两道必须认真做的工序。

脱敏。线上 trace 几乎必然包含 PII 与业务敏感信息。进入评测集前需要：识别并替换人名、联系方式、账号、内部 ID 等实体（自动识别加人工复核）；对业务敏感的数值与专有名词做等价替换而非简单打码，保证案例仍然「可跑」；记录脱敏版本与规则，原始 trace 按数据保留策略另行管理。一个常见错误是脱敏破坏了失败的成因——比如失败本来就源于某个特殊格式的输入，替换后案例不再触发问题。脱敏后应当重放一次，确认失败仍可复现。

去重。线上同类失败会大量重复，golden 集不需要五十个本质相同的案例。去重通常分两层：精确层用规范化后的输入哈希去掉完全重复；语义层用 embedding 相似度或聚类把「同一失败模式的不同表述」归簇，每簇保留一到三个代表，优先保留最简洁和最极端的版本。同时给案例打上模式标签，记录该簇在线上出现的频次——频次是后续修复排优先级的依据，即使案例本身只入库一份。

入库流程建议显式化：候选 → 归因 → 脱敏 → 去重 → 人工审核写入期望行为（这个案例「正确」应该长什么样）→ 进入 golden 集并版本化。期望行为这一步不可省略，没有判定标准的案例进了评测集也无法自动回归。

用失败案例驱动针对性修复

失败库的最终价值在于驱动修复，并且让修复有据可查、有回归可守。

  • 按归因统计排优先级：如果 60% 的失败归因到检索，先优化 chunking 或召回策略，比反复打磨生成 prompt 的收益高一个量级。
  • 修 prompt 时把失败案例当测试用例：针对某簇失败修改 prompt 后，先在该簇案例上验证修复，再在全量 golden 集上跑回归，确认没有按下葫芦浮起瓢。
  • 修检索时用失败案例构造检索评测：从失败 trace 里提取「问题与本应命中的文档」对，直接评测召回率的改进，而不是只看端到端结果。
  • 工具类失败优先考虑结构性修复：参数校验、工具描述改写、错误重试策略，这些确定性手段比指望模型「下次小心」可靠。
  • 闭环验证：修复上线后回查同一失败模式的线上出现频率是否下降，这是修复真正生效的证据。

最后是节奏问题。失败挖掘适合作为固定周期的例行活动（比如每周一次的失败评审会，过一遍新增簇与高频簇），而不是出了事故才临时翻日志。持续运转的挖掘管道让 golden 集随着产品演进自然生长，评测体系也因此始终贴着线上真实分布，而不是停留在上线前拍脑袋构造的那批用例上。

常见反模式与权衡

挖掘管道本身也会腐化，几个高频的反模式值得警惕。

  • 只看点踩：负反馈精确但量极少且有偏，只依赖它会让失败库长期覆盖不到沉默用户的体验，必须与低分抽样、重试等信号并行。
  • 归因跳过 trace 证据：把「模型答错了」当作归因终点，不区分是检索没给到依据还是生成环节出错，结果是修错了地方。
  • 脱敏破坏成因：把触发失败的关键格式或实体一并替换掉，案例不再复现问题却不自知，因此脱敏后必须重放验证失败仍可复现。
  • 无期望行为入库：没有判定标准的案例进了评测集也无法自动回归，人工审核写入「正确应该长什么样」这一步不可省略。
  • 只囤不修：失败库沦为陈列馆，没有按归因统计排优先级、没有回查修复后的频率变化，挖掘就没有产生价值。

权衡点在于覆盖面与成本：候选来源越多、归因越细，召回越全但人工审核负担越重。务实的次序是先用低成本的确定性信号（硬性错误、护栏命中）与低分抽样把量做起来，再用聚类发现未知模式，把昂贵的人工归因留给频次最高与业务影响最大簇。

小结

  • 失败挖掘把线上坏案例系统性地筛出、归因、脱敏入库，最终变成驱动修复与回归的评测资产，价值在于覆盖面、可重复性与优先级排序。
  • 候选筛选需并行多路策略（低分抽样、负反馈关联、高重试、转人工、异常聚类、硬性错误、护栏命中），没有单一信号可靠；低分要分桶分层抽样，聚类适合周期性跑以发现未知失败类型。
  • 归因沿执行链分类（检索、生成、工具、上下文、意图、越界），必须基于 trace 证据，结果要回写到失败记录，成为统计环节贡献度的基础。
  • 入库前两道工序不可省：脱敏要对敏感实体做等价替换并重放确认失败仍可复现；去重分精确哈希与语义聚类两层，每簇留代表并记录线上频次作为修复优先级依据。
  • 修复要按归因排序、把失败案例当测试用例、用失败 trace 构造检索评测、对工具类失败优先结构性修复，并用线上频率下降做闭环验证。
  • 挖掘应做成固定周期的例行活动而非事故驱动的临时翻日志；同时警惕只看点踩、跳过 trace 证据、脱敏破坏成因、无期望行为入库、只囤不修等反模式。
