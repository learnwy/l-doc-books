Agent 轨迹评测

单轮问答的评测只需要看「输入对应的输出好不好」，而 Agent 的评测面对的是一条由多轮模型调用、工具执行与环境反馈交织而成的轨迹（trajectory）。同一个任务可能有多条合理的完成路径，也可能「结果碰巧对了但过程完全不可靠」。因此 Agent 评测不能只看终点，需要把度量拆成三个互补的层面：结果层回答「任务完成了吗」，轨迹层回答「过程合理吗」，效率层回答「代价可接受吗」。三层结合才能区分真正稳健的 Agent 与靠运气通过的 Agent。

核心概念

Agent 评测的对象不是「一次输出」，而是一条轨迹：由多轮模型调用、工具执行与环境反馈交织成的执行历史。这决定了它的度量必须分层——结果层判「任务成不成」、轨迹层判「过程合不合理」、效率层判「代价可不可控」——并且要求轨迹被完整采集、可在可重置的沙箱中重执行，才能做到两次运行可比。

三个层面的读法是互补而非叠加：结果层是地基优先建设，轨迹层捕捉结果层看不见的病态过程，效率层把成本变成显式约束——只看其中一层都会得出片面结论。

三层评测模型

层面 核心问题 典型指标 判定方式
结果层 任务最终是否成功 任务成功率、pass@k、子目标完成度 可验证任务集 + 程序化校验器
轨迹层 完成过程是否合理 工具调用正确率、轮数、重复动作率、违规动作数 规则检测 + LLM-judge 审轨迹
效率层 完成代价是否可控 总 token 消耗、API 成本、墙钟时长、工具调用次数 直接从 trace 统计

结果层是地基，优先建设。最有价值的资产是「可验证任务集」：每个任务附带一个程序可以自动执行的校验器，例如「修复这个 bug」以单元测试是否通过为准、「整理这批文件」以最终目录结构断言为准、「查询并填写表单」以数据库最终状态为准。可验证任务集的成功判定不依赖任何模型，稳定且廉价，是 SWE-bench 一类基准被广泛信任的根本原因。构建时要注意防「作弊解」：校验器应检查任务的实质效果而非表面特征，否则 Agent 会学到删除失败测试而不是修复代码这类捷径。

轨迹层捕捉结果层看不到的问题。两个都完成任务的 Agent，一个用 4 步干净利落，另一个兜了 30 圈、反复调用同一个搜索、中途还误删过文件再恢复——结果层给它们同样的分数，轨迹层才能区分。常用的规则检测包括：轮数是否超过任务级上限、是否出现连续相同参数的重复工具调用、是否调用了任务不需要的高危工具、工具报错后是否原样重试而非调整策略、是否在拿到答案后仍继续无意义动作。这些检测都是确定性的，应作为轨迹层的第一道筛子，把明显病态的轨迹直接标红。

效率层把成本变成显式约束。token 消耗与时长直接来自 trace 统计，重点是设定对比基线：同一任务集上新旧版本的成本分布对比，比绝对数值更有意义。一次「成功率提升 2%、平均成本上升 3 倍」的变更在多数产品里是退步而非进步，只看结果层会得出相反结论。

轨迹的采集与回放

轨迹评测的前提是完整、结构化地记下 Agent 做过的每一件事。一条可评测的轨迹至少包含：每一轮的模型输入（含系统 prompt 与上下文窗口实际内容）、模型输出（文本与工具调用意图）、每次工具执行的参数、返回值、耗时与错误、以及环境状态的关键快照。采集方式上，主流做法是在 Agent 编排层埋点并输出标准化格式（如 OpenTelemetry 的 GenAI span 约定），离线评测与线上观测共用同一套 trace schema，避免「评测看到的」与「生产发生的」是两套数据。

回放（replay）有两种语义，需要明确区分：

回放模式 含义 用途 局限
记录回放 重新呈现已录制的轨迹，不重新执行 人工审查、judge 评分、失败分析 不能验证改动后的新行为
重执行回放 用相同任务与初始环境重新跑 Agent 回归评测、A/B 对比、修复验证 要求环境可重置，外部依赖需 mock 或快照

重执行回放是回归评测的主体，它对环境提出了苛刻要求：任务开始时的世界状态必须可以精确还原。文件系统用容器镜像或快照解决，数据库用每次评测前重建的种子数据解决，外部 API 则要么录制响应做 mock、要么使用专门的沙箱副本。任何一个不可重置的依赖都会让「两次运行不可比」，这是 Agent 评测与单轮评测最大的工程差异。

用 LLM-judge 审轨迹的 rubric 设计

规则检测覆盖不了「这个搜索关键词选得合不合理」「在信息不足时该不该先问用户」这类需要判断力的标准，这部分交给 LLM-as-judge。但让 judge 直接读一条几万 token 的原始轨迹然后「打个总分」效果很差——分数不稳定、不可解释、且 judge 容易被轨迹长度与表面流畅度迷惑。有效的做法是把评审拆成 rubric 上的逐项判定。

rubric 设计的要点：

  • 每项一个二元或三档判定，而不是 1 到 10 的连续打分。「工具选择：每一步选用的工具是否是当时最直接的手段（是/部分/否）」远比「过程质量打几分」稳定。
  • 每项要求 judge 引用轨迹中的具体步骤编号作为证据，强制其落地到事实而非整体印象。
  • 把轨迹预处理成结构化摘要再喂给 judge：每步压缩为「轮次、动作、参数要点、结果要点」的列表，超长的工具返回值截断并标注。这同时降低成本与噪声。
  • 维度分而治之：规划合理性、工具使用、错误恢复、信息忠实度（有没有捏造工具没返回的内容）、安全边界（有没有越权动作）各自独立判定，最后加权汇总。
  • judge 自身要被校准：抽取 50 到 100 条轨迹做人工标注，统计 judge 与人类标注的一致率，低于约 85% 的维度需要重写该项 rubric 或更换 judge 模型。judge 的模型版本与 prompt 同样要 pin 并版本化。

常见偏置也要主动对冲：judge 偏好更长更详细的轨迹（长度偏置）、偏好与自己同系模型的输出风格（自我偏好）。对策包括在 rubric 中显式声明「步骤更少且达成同样效果应得更高评价」、用与被测 Agent 不同家族的模型当 judge、以及对关键维度用两个不同 judge 取一致结果。

沙箱化的可重复执行环境

Agent 评测必须在沙箱中重执行，原因有两个：可重复性要求环境每次从同一状态出发，安全性要求 Agent 的任意动作（删文件、发请求、执行代码）不会伤害真实系统。

沙箱的典型分层：

隔离层 手段 解决的问题
计算与文件系统 容器（Docker）或微虚拟机（Firecracker、gVisor） 每个任务独立的干净文件系统，跑完即弃
网络 默认断网 + 显式 allowlist 代理 防止 Agent 访问真实服务或泄露数据
外部服务 录制回放 mock 或专用测试副本 第三方 API 的响应可重复
时间与随机性 注入固定时钟与种子 消除与时间相关的行为漂移
资源配额 CPU、内存、磁盘与执行时长上限 防失控 Agent 拖垮评测集群

工程上每个评测任务对应一个「任务包」：初始环境定义（镜像 + 种子数据）、任务指令、校验器脚本、资源与权限声明。评测调度器为每条用例启动一个隔离实例、注入任务、采集轨迹、运行校验器、销毁实例。并发跑几十个沙箱实例时，环境构建本身可能比模型调用更耗时，常用镜像分层缓存与实例池预热来摊薄。

最后一个容易踩的坑是「评测环境与生产环境的偏差」：沙箱里的工具版本、网络延迟、数据规模与真实环境差异过大时，评测分数对生产表现的预测力会下降。定期把生产中失败的真实轨迹脱敏后转化为评测任务包，是让任务集贴近现实、持续保持区分度的最可靠途径。

为什么不能只评结果

只评结果——只跑一遍任务、看校验器是否通过——是最容易上线也最容易失效的做法，原因有三层。

  • 结果的运气成分：Agent 可能靠重试、靠碰巧命中，甚至靠删掉失败测试这类捷径「通过」，校验器只能看表面效果，看不到过程是否可复现。
  • 归因缺失：任务失败时，只看结果无法回答是规划错了、工具选错了、还是环境有问题，修复就无从下手；轨迹层的规则检测与 rubric 正是为了补上这段归因链。
  • 成本盲区：同样成功的两条轨迹可能相差数倍 token 与时长，忽略效率层会把「成功率微升、成本翻三倍」的变更误判为进步。

权衡在于：分层越细，采集与判定成本越高。务实的次序是先建结果层的可验证任务集（最稳定也最廉价），再补确定性的轨迹规则检测，最后才为「判断类」标准引入经校准的 judge；不要一上来就追求全维度打分，那样往往得到一堆不稳定、不可解释的分数。

小结

  • Agent 评测的对象是一条轨迹，度量必须分层：结果层判任务是否成功、轨迹层判过程是否合理、效率层判代价是否可控，三层互补。
  • 结果层优先建设，核心资产是「可验证任务集」——每个任务附带程序可执行的校验器，并警惕删除测试这类作弊解。
  • 轨迹层用确定性规则检测做第一道筛子（轮数上限、重复调用、高危工具、报错后原样重试等），覆盖不了的部分交给 LLM-judge。
  • judge 审轨迹要拆成 rubric 逐项判定：二元或三档、要求引用步骤编号作证据、先预处理成结构化摘要、维度分而治之，并主动对冲长度与自我偏好。
  • 重执行回放是回归评测主体，前提是环境可精确重置——沙箱按计算、网络、外部服务、时间随机性、资源配额分层隔离。
  • 评测环境与生产偏差过大会削弱预测力，定期把脱敏后的真实失败轨迹转化为任务包是保持区分度最可靠的手段。
