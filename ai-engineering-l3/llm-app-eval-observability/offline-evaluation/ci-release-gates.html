接入 CI 与发布门禁

评测只有嵌进交付流程才能持续发挥作用。一套放在仓库角落、靠人想起来才跑的评测脚本，挡不住任何一次回归；只有当它成为 CI 的常规检查项与发布前的强制门禁，「改坏了」才会在合并前被发现而不是在用户投诉里被发现。把评测接入 CI 的核心工程问题有四个：在速度与覆盖之间分级、把门禁阈值定得既不误杀也不放水、确保所有影响行为的变更都触发评测、以及在失败时给出可行动的归因报告——同时把这一切的成本控制在团队能长期负担的范围内。

核心概念

发布门禁是「评测结论 → 合并决策」的转换器：它把统计结果按预设规则变成阻断或放行。要让这个转换器长期可信，需要同时满足四个条件：分级（不同时机跑不同规模）、双线阈值（绝对底线加相对回退）、全触发面（任何影响行为的变更都进门禁）、可行动归因（亮红灯的同时说清哪里坏、多半为什么）。

graph TD
    PR["代码 / prompt / 配置变更"] --> TRIG{"变更路径命中哪些评测标签?"}
    TRIG --> SMOKE["冒烟集:20-50 条,< 5 分钟"]
    TRIG --> GATE["PR 门禁集:分层抽样,10-30 分钟"]
    GATE --> TH{"双线阈值判定"}
    TH -- 跌破绝对线 --> BLOCK["阻断 + 归因报告"]
    TH -- 相对回退超噪声余量 --> BLOCK
    TH -- 通过 --> MERGE["合并"]
    NIGHT["夜间全量:全量 + 多次采样"] --> BASE["更新基线"]
    BASE --> TH
    NIGHT -. 新失败晋升 .-> GATE

两个关键读法：门禁集是夜间全量的分层抽样子集，夜间发现的新失败自动晋升进快跑集，形成「全量发现、快跑拦截」的循环；阈值判定必须双线并行，否则质量会在绝对线上方缓慢阴跌，或让基线被一连串小跌越拉越低。

分级运行：PR 快跑与夜间全量

LLM 评测的单条用例成本是传统单元测试的成百上千倍，全量评测集放进每个 PR 既慢又贵。标准解法是按触发时机分级：

级别 触发时机 数据集规模 目标时长 角色
冒烟集 每次 push / PR 更新 20–50 条核心用例 < 5 分钟 抓灾难性破坏（格式崩坏、工具调用全错）
PR 门禁集 PR 标记 ready / 合并前 100–500 条分层抽样 10–30 分钟 合并的硬门禁，覆盖各核心场景
夜间全量 每日定时（主干最新版本） 全量数据集 + 多次采样 数小时 统计置信的质量基线、长尾场景、趋势追踪
发布候选全量 切发布分支 / 发布前 全量 + Agent 重执行回放 数小时 发布的最终门禁

分级的关键是层与层之间的关系：PR 门禁集是夜间全量集的分层抽样子集，按场景标签与历史失败率抽取——历史上易碎的用例优先入选，长期稳定通过的用例降低抽样权重。夜间全量发现的新失败用例自动晋升进 PR 门禁集，形成「全量发现、快跑拦截」的循环。冒烟集则只放绝对不能挂的用例，目的是让开发者在几分钟内得到第一轮信号。

夜间全量还承担一个 PR 评测做不到的职责：因为它每天在同一套主干代码上运行，其分数序列是最干净的质量时间序列，模型供应商的静默变化、数据漂移、judge 漂移都最先在这条曲线上显形。

门禁阈值：绝对线与相对回退线

门禁判定不能只用一个数字。成熟的做法是双线并行：

  • 绝对线（floor）：质量的硬底线，与历史无关。例如核心场景通过率 ≥ 95%、安全类用例通过率 = 100%、JSON 格式有效率 ≥ 99%。绝对线表达的是产品承诺，跌破即阻断，没有商量余地。
  • 相对回退线（regression bar）：与基线 run（通常是主干最近一次夜间全量、或本 PR 的 base commit 评测结果）对比，总分下降超过噪声余量即阻断。例如「总通过率相对基线下降 > 2 个百分点」或「任一标签组下降 > 5 个百分点」。

两条线缺一不可：只有绝对线时，质量可以在线上方缓慢阴跌而不触发任何告警；只有相对线时，一连串「每次只跌一点」的合并会把基线越拉越低（基线漂移），而且当基线本身已低于可接受水平时相对线毫无意义。

噪声余量的设定要有依据：对同一版本重复运行 PR 门禁集 10 次以上，测出通过率的标准差，相对回退线至少留出 2 到 3 个标准差，否则误杀会迅速消耗团队对门禁的信任——被狼来了训练过的团队最终会习惯性点击「跳过检查」。除通过率外，逐用例 regression 清单也应参与门禁：即使总分持平，核心标签下出现「由通过转失败」的用例超过 N 条同样阻断，防止净分数掩盖行为漂移。

最后要设计显式的逃生通道：紧急修复可以由负责人书面豁免门禁，但豁免记录自动开 issue 跟踪，要求在限期内补齐评测。隐蔽的绕过比公开的豁免危险得多。

触发面：任何影响行为的变更都要进门禁

LLM 应用的行为由远不止代码的多种工件共同决定，CI 触发规则必须覆盖全部行为面。漏掉任何一类，就等于给该类变更发了免检通行证。

变更类型 典型载体 常见疏漏
应用代码 编排逻辑、工具实现、解析器 一般不会漏
prompt 系统 prompt、few-shot 示例、judge prompt 存在数据库或配置平台里、不走代码评审
模型配置 模型版本 pin、温度、最大 token、工具定义 改一个温度参数被当作「无关紧要」
检索配置 embedding 模型、chunk 策略、top-k、重排序器、索引版本 索引重建在数据管道里发生、CI 无感知
依赖 SDK 升级、框架版本 lockfile 变更未关联评测
评测资产自身 数据集、rubric、阈值 改阈值放水无人审

落地原则是「一切进版本库、按路径触发」：prompt 与模型/检索配置一律以文件形式与代码同仓，CI 按变更路径决定触发哪些评测——只改了检索配置就重点跑 RAG 相关标签的用例集，只改了某个工具的 prompt 就跑该工具相关场景。对确实无法进仓库的远端配置（如供应商侧模型升级），用夜间全量的基线曲线兜底，并在应用层记录配置指纹（prompt hash、模型快照 ID、索引版本号）写入每次评测 run 的元数据，保证任何分数变化都能回答「当时跑的到底是哪套配置」。

评测资产自身的变更要走更严的评审：放宽阈值或删除用例的 PR 必须说明理由并由质量负责人批准，否则门禁会被「让测试通过」的捷径慢慢掏空。

失败时的归因报告

门禁的价值不在于亮红灯，而在于让开发者在几分钟内知道「哪里坏了、多半为什么坏」。一份可行动的失败报告应自动包含以下内容，按归因效率排序：

  • 与基线的逐用例 diff：明确列出 regression 清单（由通过转失败）与 improvement 清单，按标签分组。开发者第一眼要看到的是「坏掉的集中在哪类场景」。
  • 失败模式聚类：把失败用例按判定失败的具体断言分组——格式解析失败、工具调用参数错误、judge 判不切题、超时——同一断言批量失败通常指向同一个根因。
  • 单用例下钻：每条失败用例附带可点开的完整 trace（输入、逐轮输出、工具调用、judge 评语），以及与基线 run 同一用例输出的并排对比。
  • 噪声排除信息：失败用例的自动复跑结果（复跑通过则标记为疑似噪声）、该用例的历史通过率（一个历史上 60% 通过率的用例失败，信息量远低于一个长期 100% 的用例失败）。
  • 配置指纹对比：本次 run 与基线 run 的模型版本、prompt hash、索引版本逐项对比，把「环境变了」与「代码改坏了」分开。

报告投递到 PR 评论与团队频道，正文只放摘要与 regression 清单前几条，详情链接到评测平台。归因报告做得越好，门禁的红灯就越被当作帮助而不是阻碍。

评测成本控制

评测成本失控的团队最终会缩减运行频率，门禁随之名存实亡。成本控制有三个主要杠杆：

杠杆 做法 节省幅度
分级数据集 冒烟/门禁/全量三级，PR 只跑抽样子集 把每 PR 成本压到全量的 5%–20%
缓存 输入（prompt + 配置指纹）未变的用例直接复用上次结果；judge 判定按（输出、rubric 版本）缓存；供应商侧 prompt caching 降低重复前缀成本 增量变更场景下常见 50% 以上
模型分级 judge 用小模型跑常规维度、大模型只复核分歧项与关键维度；确定性断言能覆盖的绝不用 judge judge 成本降为原来的 1/5 到 1/3

抽样策略值得单独强调：与其均匀抽样，不如按「信息量」加权——历史失败率高的、最近相关代码路径变更过的、覆盖稀缺标签的用例优先。同样 200 条预算，加权抽样对回归的检出率显著高于随机抽样。

缓存的正确性边界要守住：任何参与生成的配置（模型版本、温度、prompt、工具定义、检索索引版本）变了就必须失效，因此缓存 key 应直接由配置指纹拼成。最后把评测开销本身纳入观测——每次 run 记录总 token 与费用，当某次改动让评测成本翻倍时，这条曲线会先于账单提醒你。

小结

  • 评测只有嵌进交付流程才能持续发挥作用：成为 CI 常规检查项与发布强制门禁，回归才会在合并前而非用户投诉里被发现。
  • 按触发时机分级：冒烟集抓灾难性破坏，PR 门禁集做合并硬门禁，夜间全量做统计置信基线与趋势追踪，发布候选全量做最终门禁；门禁集是全量的分层抽样子集，新失败自动晋升。
  • 门禁阈值必须双线并行：绝对线（floor）表达产品承诺，相对回退线（regression bar）与基线对比；噪声余量至少留两到三个标准差，并让逐用例 regression 清单也参与判定。
  • 触发面要覆盖全部行为载体：应用代码、prompt、模型配置、检索配置、依赖、以及评测资产自身——落地原则是「一切进版本库、按路径触发」，并为远端配置记录配置指纹。
  • 失败报告的价值在于可行动：逐用例 diff、失败模式聚类、单用例下钻、噪声排除信息、配置指纹对比，按归因效率排序。
  • 成本控制有三个杠杆：分级数据集、缓存、模型分级，配合按信息量加权的抽样策略；同时把评测开销本身纳入观测，防止扩缩减频率导致门禁名存实亡。
