回归评测流水线

回归评测流水线是把 LLM 应用质量检验自动化的核心基础设施。它的目标与传统软件的回归测试一致：在每次变更后重新运行一组固定的测试用例，确认新版本没有破坏旧版本已经做对的事情。区别在于 LLM 的输出是概率性的、判定往往是模糊的、单次运行的成本远高于普通单元测试。一条成熟的回归流水线需要在结构设计上同时应对这三个难题：用标准化的阶段划分保证可重复性，用环境固定与多次采样驯服非确定性，用结果存储与趋势对比把单次「通过/失败」升级为长期的质量曲线。

核心概念

回归评测的可信度建立在三个不变量上：可比性（两次运行之间唯一的变量是被测改动）、可复现性（同一版本任意时刻重跑得到同一结论）、可追溯性（每次运行的结果与配置指纹被结构化存储）。围绕这三个不变量，流水线收敛出稳定的四段式结构，并把「非确定性」当作一等公民处理，而不是靠提高判定精度硬碰。

graph TD
    A["数据集加载:golden 文件 → 标准化用例列表(版本化 + schema 校验)"] --> B["并发执行:信号量限流 + 退避重试 + trace 落盘"]
    B --> C["判定:确定性断言 + LLM-as-judge 混用,判定可缓存"]
    C --> D["汇总报告:总分、分维度、逐用例 diff"]
    D --> E["结果存储:run/用例/对比三级 schema"]
    E --> F["历史趋势对比:regression 与 improvement 清单"]
    F -. 新失败晋升用例 .-> A

关键设计点：

  • 数据集进版本控制，每条用例有稳定 ID、输入、期望行为与标签，schema 校验放在加载时做。
  • 执行阶段用信号量把并发控制在 5 到 20，对 429 与 5xx 做指数退避重试，并落盘完整 trace。
  • 判定阶段优先用确定性断言，主观维度交给 judge，但 judge 的 prompt 与模型版本同样要固定。
  • 存储阶段保证三种查询能力：任意两次 run 的逐用例对比、单用例的跨时间曲线、按标签聚合的趋势。
  • 对比阶段显式输出 regression 与 improvement 两个清单，避免净分数掩盖行为漂移。

四段式结构

绝大多数评测框架与自建系统最终都收敛到同一个四段式结构：数据集加载、并发执行、判定、汇总报告。每一段职责清晰、接口稳定，便于独立替换与扩展。

阶段 输入 输出 关键设计点
数据集加载 golden 数据集文件（JSONL/CSV/数据库） 标准化的用例列表 版本化数据集、schema 校验、按标签筛选子集
并发执行 用例列表 + 被测系统配置 每个用例的原始输出与 trace 并发上限、重试与退避、超时控制、速率限制
判定 原始输出 + 期望/rubric 每个用例的分数或通过标记 确定性断言与 LLM-as-judge 混用、判定本身可缓存
汇总报告 全部判定结果 总分、分维度报告、失败明细 与历史基线对比、按用例标签分组、失败可下钻到单条

数据集加载阶段最容易被轻视。golden 数据集应该和代码一样进版本控制：每条用例有稳定的 ID、输入、期望行为描述与标签（难度、场景、来源）。schema 校验放在加载时做，避免坏数据在执行几百次昂贵的模型调用之后才暴露。

并发执行阶段决定流水线的运行时长与成本。LLM 调用延迟通常在秒级，串行跑几百条用例不可接受；但并发过高会触发供应商的速率限制。常见做法是用信号量控制并发在 5 到 20 之间，对 429 与 5xx 错误做指数退避重试，并把每条用例的完整请求与响应（包括中间工具调用）落盘为 trace，供后续判定与人工排查使用。

判定阶段把原始输出转成分数。能用确定性断言的优先用确定性断言：JSON 是否可解析、必填字段是否存在、工具调用的名称与参数是否正确、输出是否包含禁止内容。需要主观判断的标准（回答是否切题、语气是否合适、推理是否合理）交给 LLM-as-judge，但 judge 的 prompt 与模型版本同样要固定并纳入版本控制。

环境固定：让两次运行可比

回归评测的前提是「两次运行之间唯一的变量是被测改动」。任何未固定的环境因素都会污染对比结论。

固定项 做法 不固定的后果
采样温度 设为 0 或固定低值 输出方差放大，分数抖动掩盖真实回归
随机种子 支持 seed 参数的供应商显式传入 同输入不同输出，无法定位差异来源
模型版本 pin 到带日期的具体快照而非浮动别名 供应商静默升级模型，分数变化被误判为代码问题
系统 prompt 与工具定义 与代码同仓版本控制 评测跑的不是线上真实配置
检索语料与索引 评测用快照索引或固定语料 检索结果漂移导致端到端分数不可比
judge 模型与 rubric 单独 pin 版本 评分尺度漂移，历史趋势失真

模型版本 pin 是其中最常被忽略的一项。使用浮动别名时，供应商升级底层模型会让评测分数在没有任何代码变更的情况下跳变。正确做法是评测与生产都引用带日期的快照版本，把「升级模型」本身变成一次显式的、走完整回归评测的变更。

需要说明的是，即使温度为 0 且传入固定种子，多数托管推理服务仍不保证逐 token 完全确定——批处理调度与浮点运算顺序都会引入微小差异。环境固定的目标是把方差压到判定层可以容忍的程度，而不是追求逐字节一致。

非确定性的处理：从单次断言到通过率

既然输出无法做到完全确定，回归流水线就不能依赖「单次运行、精确匹配」的判定模型，而要把统计思维内建进来。

常用手段有三类。第一是多次采样（常记作 pass@k 或 pass^k）：对同一用例独立运行 k 次，按需要选择口径——pass@k 衡量「k 次中至少一次成功」，适合有外部校验器兜底的场景；pass^k 衡量「k 次全部成功」，更贴近用户每次都期望成功的产品语境。第二是通过率阈值：不要求 100% 通过，而是为整体或每个标签组设定阈值，例如核心场景通过率不得低于 95%，长尾场景不得低于 80%。阈值应基于历史分布设定，留出约两到三个标准差的噪声余量。第三是判定层的容差设计：数值答案允许误差区间、文本答案比对归一化后的语义要点而非逐字匹配，从源头减少假失败。

多次采样直接乘大成本，因此实践中常分级处理：高风险核心用例跑 3 到 5 次取通过率，普通用例跑 1 次；当 1 次失败时自动追加重跑以区分真回归与随机噪声。这种「失败即复检」策略能在控制成本的同时把误报率压低一个数量级。

结果存储与历史趋势对比

只输出一次性报告的评测脚本价值有限。回归流水线的长期价值来自把每次运行的结果结构化存储，形成可查询的质量历史。

最小可用的存储 schema 包含三层：运行级（run ID、时间戳、被测版本号、模型版本、数据集版本、总分与分组分数）、用例级（用例 ID、输出、各判定项分数、延迟、token 消耗）、对比级（与指定基线 run 的逐用例 diff）。存储介质从一个 SQLite 文件到专门的评测平台都可以，关键是保证三个查询能力：任意两次 run 的逐用例对比、单个用例跨时间的分数曲线、按标签聚合的趋势图。

逐用例 diff 尤其重要。两次 run 总分相同并不代表没有变化——可能 5 个用例由失败转通过，同时另外 5 个由通过转失败，净分数不变但行为已经漂移。回归报告应明确列出 regression（由通过变失败）与 improvement（由失败变通过）两个清单，前者是阻断发布的依据，后者用来确认改动达到了预期。

常用框架与自建的取舍

评测流水线可以基于开源框架搭建，也可以完全自建。两条路线各有清晰的适用边界。

维度 采用现成框架（如 promptfoo、DeepEval、OpenAI Evals、Langfuse 评测模块、Braintrust） 自建轻量流水线
起步速度 快，内置数据集格式、常见判定器、报告界面 慢，所有环节自己写
与自有系统集成 取决于框架对自定义被测目标的支持程度 完全贴合自身调用链与 trace 格式
判定器生态 内置语义相似度、毒性、JSON 校验、judge 模板等 需要的才写，无冗余
多轮 Agent 支持 各框架成熟度差异大，常需绕过其抽象 可按自身 Agent 架构原生设计
长期维护 跟随框架升级，可能遇到 breaking change 维护成本完全自担，但面积小
结果存储与趋势 多数提供托管或自托管的历史看板 需自建存储与可视化

一个常见的务实结论是：单轮调用为主、判定标准常规的应用，用现成框架性价比最高；而深度定制的多轮 Agent 系统，框架的抽象往往与自身的编排层冲突，自建一个几百行的流水线（加载、带并发的执行器、判定函数注册表、SQLite 存储）反而更可控。无论哪条路线，前文的四段式结构、环境固定与通过率口径都同样适用——框架只是这些原则的一种封装，而不是替代。

小结

  • 回归流水线的可信度依赖三个不变量：可比性、可复现性、可追溯性，所有设计都围绕它们展开。
  • 结构上收敛为四段：数据集加载、并发执行、判定、汇总报告，各段接口稳定、可独立替换。
  • 环境固定是可比性的前提：温度、种子、模型版本、prompt 与工具定义、检索语料、judge 版本都必须固定；模型版本 pin 最常被忽略，也是收益最大的一项。
  • 非确定性必须内建处理：多次采样（pass@k / pass^k）、按标签设通过率阈值、判定层容差设计，配合「失败即复检」控制成本。
  • 只出一次性报告的脚本价值有限，长期价值来自结构化存储（run/用例/对比三级）与趋势对比，尤其是逐用例的 regression 与 improvement 清单。
  • 框架与自建各有清晰边界：常规单轮应用用框架起步快，深度定制多轮 Agent 自建更可控；无论哪条路线，四段式、环境固定、通过率口径都同样适用。
