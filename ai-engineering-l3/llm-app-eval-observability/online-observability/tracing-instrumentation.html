全链路追踪与埋点

传统 Web 服务的可观测性以指标和日志为主，而 LLM 应用的故障往往藏在「模型到底看到了什么、说了什么」这一层语义细节里。一条用户投诉「回答不对」的请求，可能源于检索召回了错误文档、上下文被截断、工具返回了脏数据，或模型本身的不稳定输出——只看状态码和耗时无法区分这些原因。因此全链路追踪（tracing）在 LLM 应用中的地位远高于普通服务：它不仅记录「发生了什么」，还要完整还原「模型当时的输入输出」，使每一次线上交互都可回放、可归因、可用于后续评测。

核心概念

一条 LLM trace 是一棵 span 树：根 span 对应整个用户请求，子 span 覆盖上下文组装、模型调用、工具执行、输出处理等阶段。与微服务追踪的关键差异在于，这棵树的形态高度动态（agent 的工具调用轮数与分支运行时才确定），且它的核心价值集中在语义负载（payload）——模型实际消费和产出的内容，而不仅是耗时与状态码。

graph TD
    REQ["request span:用户/会话/版本/渠道(脱敏)"] --> CTX["context_assembly:prompt 版本、检索 query、召回文档"]
    CTX --> LLM1["llm_call:模型版本、完整 prompt、采样参数、token 数"]
    LLM1 --> TOOL["tool_call:工具名、入参、返回摘要、错误"]
    TOOL --> LLM2["llm_call(下一轮):循环产生交替子树"]
    LLM2 --> POST["post_process:解析结果、护栏判定、TTFB"]
    POST --> OUT["响应 + trace_id 回传前端"]

从这里可以读出两条设计纪律：span 的父子关系必须忠实反映因果（否则排障时无法判断第几轮出了问题），并且必须用会话 ID 把多轮对话串起来——上下文遗忘这类问题只有在会话视角下才看得出来。

LLM 应用的 trace 结构：从请求到输出的 span 树

一次典型的 LLM 应用请求可以建模为一棵 span 树：根 span 对应整个用户请求，子 span 依次覆盖各个处理阶段。与微服务追踪不同的是，这棵树的形态高度动态——agent 应用中工具调用的轮数和分支在运行时才确定。

阶段 典型 span 关键属性
请求接入 request 用户 ID（脱敏后）、会话 ID、应用版本、入口渠道
上下文组装 context_assembly system prompt 版本、检索 query、召回文档 ID 与得分、记忆/历史截断策略
模型调用 llm_call（可多次） 模型名与版本、完整 prompt、采样参数、输入/输出 token 数、是否命中 prompt caching
工具执行 tool_call（可嵌套） 工具名、入参、返回值摘要、耗时、错误信息
输出处理 post_process 结构化解析结果、护栏（guardrail）判定、流式首字节时间

需要特别注意两点。其一是嵌套与循环：agent 的「思考→调工具→再思考」循环会产生多层 llm_call 与 tool_call 交替的子树，span 之间的父子关系必须忠实反映因果，否则排障时无法判断「第几轮调用出了问题」。其二是会话维度：多轮对话中单条 trace 只覆盖一次请求，还需要用会话 ID 把同一对话串起来，许多质量问题（如上下文遗忘）只有在会话视角下才能看出。

要记录什么：宁全勿缺的语义负载

LLM trace 的核心价值在于语义负载（payload），即模型实际消费和产出的内容。推荐的记录清单如下。

  • 完整 prompt 与响应：包括 system prompt、对话历史、检索注入的内容。只记「用户输入」而不记最终拼装结果是常见错误——很多 bug 恰恰出在拼装环节。
  • token 计数：输入、输出、缓存读取分别记录，这是成本归因和延迟分析的基础。
  • 模型版本：不仅是模型名，还要记下服务方返回的精确版本标识或 API 版本，否则上游静默更新后无从对照。
  • 检索结果：召回文档的 ID、相似度得分、最终进入上下文的片段，便于区分「没召回」与「召回了但模型没用」。
  • 工具参数与返回：模型生成的工具调用入参常常是错误源头，需原样保留；返回值过大时记摘要加哈希。
  • 失败与重试：超时、限流、解析失败、重试次数，这些事件本身就是质量信号。

记录粒度与存储成本之间存在张力。一条带完整 prompt 的 trace 可能有几十 KB 甚至更大，但经验上仍建议「先全量记、再靠采样和保留期控制成本」，因为缺失的语义负载事后无法补回，而它正是构建回归评测集、做漂移分析的原料。

敏感信息脱敏

完整记录 prompt 与响应意味着用户的个人信息、业务机密可能原样进入可观测系统，必须把脱敏当作埋点设计的一等公民而非事后补丁。常见策略分层如下。

策略 做法 适用场景
字段级排除 对已知敏感字段（手机号、证件号、密钥）在写入前正则或 NER 识别并替换为占位符 大多数应用的基线要求
哈希化保留可关联性 用户 ID 等标识做加盐哈希，既能聚合分析又不暴露原值 分群分析、滥用排查
分级存储与访问控制 完整 payload 单独存放、短保留期、按角色授权查看；常规仪表盘只用脱敏后的元数据 合规要求较高的行业
端侧不出域 payload 留在自有基础设施内，仅向外部平台发送指标与脱敏摘要 使用 SaaS 可观测平台但数据不能出境/出域

此外要注意：模型输出同样可能包含敏感信息（例如模型复述了用户输入），脱敏需覆盖输入和输出两侧；日志、trace、评测数据集三条数据通路要使用同一套脱敏规则，避免某一路成为泄漏旁路。

OpenTelemetry 与专用平台的取舍

技术选型上主要有两条路线：基于 OpenTelemetry（OTel）的通用追踪体系，以及 LangSmith、Arize Phoenix、Helicone、Langfuse 这类面向 LLM 的专用平台。两者并非互斥，但侧重点不同。

维度 OpenTelemetry 路线 LLM 专用平台
数据归属 自有后端（Jaeger、Tempo、ClickHouse 等），完全可控 SaaS 为主，部分支持自托管（Phoenix、Langfuse 开源）
与现有体系融合 与微服务 trace 同一条链路，跨服务归因方便 通常独立成岛，需要额外打通
LLM 语义支持 依赖 GenAI 语义约定（semantic conventions），生态仍在收敛 原生支持 prompt 对比、token 成本、评测集回流、LLM-as-judge 打分
上手成本 需自建存储与查询界面，前期投入大 SDK 或代理（proxy）模式接入快，Helicone 类网关甚至只需改 base URL
长期风险 标准开放、无厂商锁定 平台绑定、payload 出域的合规顾虑

一个务实的折中是「OTel 作为传输层、专用平台作为分析层」：埋点统一采用 OTel SDK 与 GenAI 语义约定，通过 collector 同时导出到自有后端和专用平台，既保留数据主权又获得开箱即用的 LLM 分析能力。已有成熟可观测体系的团队倾向此路线；早期小团队则常直接用专用平台换取速度，待规模上来再迁移。

采样策略

全量保留所有 trace 的完整 payload 在量大之后并不现实，需要分层采样。LLM 场景的采样有别于普通服务：单条 trace 的信息价值差异极大，均匀采样会浪费配额在大量「正常且雷同」的请求上。

  • 头部采样（head sampling）：按固定比例在入口决定是否记录，实现简单、开销低，适合作为兜底基线（例如 10%）。
  • 尾部采样（tail sampling）：请求完成后根据结果决定保留与否——错误、超时、用户点踩、护栏触发、token 异常多的请求 100% 保留，正常请求低比例保留。这是 LLM 应用最推荐的主策略。
  • 维度分层：新上线的 prompt 版本、灰度分组、重点客户的流量提高采样率；稳定老路径降低采样率。
  • 元数据全量加 payload 抽样：所有请求都记录轻量元数据（token 数、延迟、模型版本），只对抽样命中的请求保留完整 prompt/响应，兼顾统计完整性与存储成本。

无论采用哪种组合，都应保证「出问题的请求一定查得到」：错误类与负反馈类 trace 不参与丢弃，这是排障与回归评测集建设的底线。

小结

  • LLM 应用的故障藏在语义细节里，仅看状态码与耗时无法归因，因此追踪的地位远高于普通服务，必须完整还原模型当时的输入输出。
  • trace 是一棵动态的 span 树：请求接入、上下文组装、模型调用、工具执行、输出处理，agent 场景下 llm_call 与 tool_call 交替产生多层子树。
  • 记录的重点是语义负载：完整 prompt 与响应、分项 token 计数、精确模型版本、检索结果、工具参数与返回、失败与重试；经验上「先全量记、再靠采样与保留期控成本」，因为缺失的负载事后无法补回。
  • 脱敏是埋点设计的一等公民：字段级排除、哈希化保留可关联性、分级存储与访问控制、端侧不出域，且日志、trace、评测集三条通路要用同一套规则以减少泄漏旁路。
  • 选型上 OTel 路线数据可控、无厂商锁定但前期投入大，LLM 专用平台接入快、原生支持 LLM 分析但有绑定与出域顾虑；务实折中是「OTel 作传输层、专用平台作分析层」。
  • 采样要分层：尾部采样作为主策略、头部采样作兜底、按维度提高重点流量采样率、元数据全量加 payload 抽样，并保证错误与负反馈 trace 永不丢弃。
