成本、延迟与质量仪表盘

LLM 应用的线上健康度无法用单一指标概括：成本决定业务可持续性、延迟决定交互体验、质量决定产品价值，三者还彼此牵制——换更强的模型常常同时推高成本与延迟，激进的缓存与截断又可能损害质量。仪表盘的职责就是把这三类指标以一致的口径组织起来，让工程师在一处看到全貌、在版本变更时看到差异、在异常出现时能够下钻到具体请求。本文给出三类指标的定义与拆解方式、对比分析的组织方法，以及从图表异常到单条 trace 的下钻路径。

核心概念

仪表盘把线上健康度拆成成本、延迟、质量三类指标，用一致口径组织、用版本与分群做切分、用共享标签打到 trace 元数据上形成「异常曲线 → 根因」的导航路径。三类指标彼此牵制，正是它们必须并排呈现而非单独追踪的原因。

读法很简单：三类指标共享同一套由埋点阶段写入的维度标签，切分与对比才有意义；下钻链路的最后一步是把确认的坏例回灌回归评测集，让线上发现的问题在下次发布前被离线拦截。

成本指标：从总账单到每请求归因

云账单只能告诉你「这个月花了多少」，仪表盘需要回答的是「钱花在哪、为什么涨」。成本拆解的核心维度如下。

指标 定义 用途
每请求 token 数 单次请求的输入/输出/缓存读取 token 分布（均值与 P95） 发现 prompt 膨胀、上下文失控
每请求成本 token 数 × 对应单价，区分输入、输出与缓存价格档 与业务单位经济性对账
缓存命中率 prompt caching 命中的 token 占输入 token 的比例 评估缓存设计有效性，命中率下跌往往意味着 prompt 前缀被无意改动
按功能归集 以 feature/route 标签聚合的成本占比 识别「烧钱大户」，指导优化优先级
按模型归集 各模型的调用量与成本占比 验证模型路由策略（如简单任务降级到小模型）是否生效

两个常见陷阱值得标注在仪表盘设计中。其一是输出 token 单价通常数倍于输入，均值掩盖结构：输入 token 总量大但便宜，少数长输出请求可能贡献了主要成本，因此成本要按价格档分开画。其二是重试与级联调用的隐藏成本：一次用户请求背后可能有多次模型调用（agent 多轮、解析失败重试），成本归因必须挂在根 trace 上汇总，而不是只统计「成功的那一次」。

延迟指标：TTFT 与端到端的分层拆解

LLM 的延迟体验有双重结构：流式场景下用户感知的是首 token 时间（TTFT，time to first token），而任务完成依赖端到端时间。两者改善手段不同，必须分开度量。

  • TTFT：从请求发出到收到第一个输出 token。受排队、上下文长度（prefill 阶段与输入 token 数近似线性相关）、缓存命中影响。交互式应用的核心体验指标，建议盯 P50/P95/P99 而非均值。
  • 端到端延迟：从用户请求到完整响应。除 TTFT 外还取决于输出长度与生成速率（token/s），agent 应用中还要叠加多轮工具调用。
  • 分环节延迟：把 trace 中各 span 的耗时聚合成「时间都去哪了」的分布图——检索耗时、上下文组装、模型 prefill、生成、工具执行、后处理各占多少。没有这一层，「变慢了」就只能靠猜。
  • 排队与限流：被上游限流重试的等待时间应单独标出，它的优化手段（配额、削峰）与模型本身无关。

仪表盘上推荐用分位数时序图加环节堆叠图的组合：前者发现「什么时候变慢」，后者回答「慢在哪一段」。同时把延迟与输入 token 数做散点关联，可以快速识别「是流量变重了还是服务变慢了」。

质量指标：把主观体验变成可趋势化的数字

质量是三类指标中最难量化的，线上不可能对每条请求做人工评审，只能用多个代理信号互相印证。

信号 定义 特点
线上抽样评分 对采样请求用 LLM-as-judge 按预设标准（正确性、依据充分性、格式合规）自动打分 覆盖面可控、可趋势化；judge 本身需要校准与版本管理
用户显式反馈率 点赞/点踩、采纳/拒绝建议的比例 最接近真实体验，但反馈率通常很低且有偏（不满者更爱投票）
用户隐式信号 重新生成、追问改写、复制使用、会话中途放弃 量大、无打扰，需要谨慎解释（追问未必是不满）
拒答率 模型拒绝回答或护栏拦截的比例 突升常意味着上游模型行为变化或护栏误伤
重试率/解析失败率 结构化输出解析失败、工具调用格式错误导致的重试比例 对 agent 与结构化输出场景是最灵敏的回归信号

这些信号没有哪个单独可信，仪表盘的价值在于并排呈现：当抽样评分下跌、点踩率上升、重新生成率同步上升时，质量回归的判断就有了交叉证据；若只有某一个信号波动，先怀疑该信号自身的偏差。

按版本与分群对比

绝对值的意义有限，对比才产生洞察。仪表盘应将所有核心指标支持至少三种切分。

  • 按版本：prompt 版本、模型版本、应用发布版本。每次变更前后指标并排对比，是「发布即评测」的基础；配合灰度发布可以做到新旧版本同时段对照，排除时间因素干扰。
  • 按分群：用户层级（免费/付费）、语言、地区、任务类型。质量问题经常只发生在某个分群——例如某语种的检索质量差、某类长文档任务的截断率高——全局均值会把它们抹平。
  • 按渠道/入口：API 直连、网页端、嵌入第三方的流量行为模式不同，混在一起会互相污染基线。

实现上要求埋点阶段就把这些维度作为标签写入 trace 元数据，事后补维度的成本极高。同时注意分群样本量：小分群的分位数和比例指标波动大，仪表盘应显示样本数并对过小的分组降权展示，避免对噪声做出反应。

异常的下钻路径

仪表盘的终点不是图表，而是「从异常曲线到根因」的导航路径。一条顺畅的下钻链路通常是：

  1. 发现异常：某指标的时序图偏离基线（例如 P95 端到端延迟突升）。
  2. 定位维度：按版本、模型、功能、分群逐一切分，找到异常集中的切片（例如只有某个 prompt 新版本受影响）。
  3. 环节归因：在该切片内看分环节延迟或成本分布，确定异常发生在哪个 span 类型（例如工具执行耗时翻倍）。
  4. 落到样本：跳转到该切片内的具体 trace 列表，按异常程度排序，打开单条 trace 查看完整的 prompt、工具参数与返回。
  5. 沉淀闭环：把确认的坏例加入回归评测集，使同类问题在下次发布前就能被离线评测拦截。

这条路径能否走通，取决于指标系统与 trace 系统是否共享同一套标签口径——如果仪表盘上的「版本」与 trace 里的「版本」是两套定义，下钻就会在第 4 步断裂。因此建议把维度标签的定义集中管理，指标聚合与 trace 检索都从同一份元数据派生。

小结

  • LLM 应用的线上健康度无法用单一指标概括：成本、延迟、质量三者彼此牵制，换更强模型常常同时推高成本与延迟，激进的缓存与截断又可能损害质量。
  • 成本要把总账单拆到每请求：token 分布、分价格档成本、缓存命中率、按功能与模型归集；注意输出单价数倍于输入，以及重试与级联调用必须挂在根 trace 上汇总。
  • 延迟要分层度量：TTFT 反映交互体验、端到端延迟反映任务完成、分环节 span 耗时回答「慢在哪一段」、排队限流等待要单独标出，统一看 P50/P95/P99 而非均值。
  • 质量靠多个代理信号交叉印证：抽样评分、显式反馈率、隐式信号、拒答率、重试率；单信号波动先怀疑该信号自身的偏差。
  • 绝对值意义有限，对比才产生洞察：按版本、分群、渠道切分，这要求埋点阶段就把维度写入 trace 元数据，并注意小分群的样本量与降权展示。
  • 仪表盘的终点是下钻路径：发现异常、定位维度、环节归因、落到样本、沉淀闭环；能否走通取决于指标系统与 trace 系统是否共享同一套标签口径。
