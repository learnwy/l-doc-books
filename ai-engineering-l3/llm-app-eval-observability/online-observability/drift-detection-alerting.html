漂移检测与告警

传统软件「不改代码就不会变」，LLM 应用打破了这条假设：即便你的代码、prompt 与配置一行未动，系统行为也可能悄悄变化——上游模型更新了、用户问的问题变了、知识库过期了。这种在没有显式发布的情况下发生的行为变化统称为漂移（drift）。漂移的危险在于渐进与无声：没有报错、没有崩溃，只有质量缓慢滑坡，等用户投诉积累起来时往往已经持续了数周。本文梳理漂移的主要来源、可落地的检测手段、告警阈值与降噪设计，以及确认漂移后的响应流程。

核心概念

漂移指在没有显式发布的情况下发生的行为变化，它按来源分类（上游模型静默更新、输入分布变化、知识库陈旧、prompt 演进副作用、依赖变更），不同来源需要不同的探测器。检测的总体思路是建立基线、持续对比、多探测器交叉印证——单一手段都有盲区，组合使用才能既灵敏又可归因。

关键读法是三个探测器各自回答不同的问题：抽样评测看真实质量、分布统计看全量形状、金丝雀重放隔离「上游变了」与「用户变了」。它们只有在共享同一基线时才构成交叉印证，也只有在响应流程把坏例回灌基线后，检测能力才会随事件积累而增强。

漂移的来源

把漂移按来源分类是检测设计的前提，因为不同来源需要不同的探测器。

来源 机制 典型表现
上游模型静默更新 模型服务方在同一模型别名下更新权重或推理栈，调用方无感知 输出风格、长度、拒答倾向、格式遵循度同时段整体变化
输入分布变化 用户群体、使用场景、问题类型随时间迁移（新市场、新功能带来新流量） 某类此前罕见的输入占比上升，针对旧分布调好的 prompt 在新分布上表现差
知识库陈旧 RAG 知识库未跟上现实世界变化，检索内容过期 模型「自信地」给出过时答案，引用的文档本身就是错的
prompt 演进的副作用 为修某个 case 改了 prompt，无意中影响了其他场景 修复发布后另一些任务的指标缓慢恶化
依赖与数据管道变化 embedding 模型更换、分块策略调整、工具接口返回格式变化 检索召回质量或工具调用成功率阶跃式变化

值得注意的是，prompt 演进严格说是「有发布的变化」，但因为团队常常只验证目标 case 而缺少全面回归，其副作用在体感上与漂移无异，所以通常纳入同一套检测体系。

检测手段

漂移检测的总体思路是建立基线、持续对比、多探测器交叉印证。常用手段有三类。

**线上抽样持续评测。**对生产流量按比例抽样，用 LLM-as-judge 按固定标准持续打分，把得分做成时序曲线。这是最直接的质量探测器，关键工程要求是评测器本身要稳定：judge 的模型与 prompt 必须版本固定，否则「尺子在变」会制造假漂移；judge 升级时要在重叠窗口内新旧并跑以校准基线。

**输入/输出分布统计。**不评判好坏，只监控「统计形状」是否变化，成本低、覆盖全量。

  • 输入侧：请求长度分布、语言占比、话题聚类占比（按 embedding 聚类后跟踪各簇流量）、新意图占比。
  • 输出侧：响应长度、拒答率、格式合规率、工具调用占比、特定关键词或免责声明出现频率。
  • 统计方法：对连续量用 PSI（population stability index）或 KS 检验对比当前窗口与基线窗口；对比例类指标用控制图思路设置波动带。

分布统计的优点是不依赖任何评测器，对「上游模型静默更新」尤其灵敏——权重更新几乎总会在输出长度与风格统计上留下痕迹。

**金丝雀查询集定期重放。**维护一组固定的代表性查询（金丝雀集），按固定频率（如每小时或每日）向生产环境重放，比对输出与历史基线的差异（精确匹配、embedding 相似度或 judge 评分）。因为输入恒定，任何输出变化都只能来自系统自身，这使金丝雀集成为隔离「上游变了」与「用户变了」的最干净手段。金丝雀集应覆盖核心任务类型、已知易碎场景与安全边界 case，并随产品演进定期增补。

三类手段互补：抽样评测看真实质量、分布统计看全量形状、金丝雀重放做受控对照。单一手段都有盲区，组合使用才能既灵敏又可归因。

告警阈值与降噪

漂移信号天然嘈杂——LLM 输出本身有随机性、流量有周期波动、judge 有抖动——告警设计的核心矛盾是灵敏度与误报率。实践中有效的降噪手段包括以下几种。

  • 相对基线而非绝对阈值：用「偏离过去 N 天同时段基线超过 k 个标准差」代替固定阈值，自动适应周期性波动。
  • 持续性条件：要求异常在连续多个窗口（如连续 3 个小时窗）成立才触发，过滤瞬时抖动；代价是检出延迟，按指标重要性分级设置。
  • 样本量门槛：小流量切片的比例指标不告警或只告低优先级，避免几条请求的波动刷屏。
  • 分级告警：观察级（仪表盘标注、日报汇总）、警告级（工作时间通知负责人）、紧急级（拒答率/错误率阶跃等硬信号才升级到即时呼叫）。多数漂移是慢性问题，适合日报与周报通道而非深夜呼叫。
  • 交叉确认升级：单一探测器触发记为观察，两类以上探测器（如金丝雀差异加抽样评分下跌）同时触发才升级，显著降低误报。
  • 告警聚合与抑制：同一根因常引发多条指标同时报警，按时间窗与维度聚合成一个事件，避免告警风暴掩盖真实信息。

一个常被忽略的实践是为告警本身建立质量回路：每条告警在处理后标记「真实/误报」，定期回顾误报率并据此调阈值——没有这条回路，告警系统会在半年内退化为「全员静音」。

漂移确认后的响应流程

检测到异常只是开始，需要一条标准化流程把信号转化为处置。

  1. 确认与定性：排除评测器故障与数据管道问题（先怀疑尺子再怀疑系统）；用下钻路径确定影响面——哪些任务类型、分群、版本受影响，严重程度如何。
  2. 归因到来源：对照金丝雀结果区分「系统变了」与「输入变了」；检查上游模型的变更公告与版本标识；核对近期 prompt 与知识库的变更记录。
  3. 快速止损：按来源选择手段——上游模型更新导致的回归可临时锁定到旧版本（若服务方支持版本固定）或切换备用模型；prompt 副作用直接回滚；知识库陈旧先下线明确过期的内容。
  4. 系统性修复：输入分布变化通常无法「回滚」，需要针对新分布补充 few-shot 示例、调整 prompt 或扩充知识库；修复方案先过离线评测再灰度上线。
  5. 沉淀与防御：把本次漂移中暴露的坏例加入回归评测集与金丝雀集；若来源是上游静默更新，评估引入版本固定（pinning）策略与多供应商备份；复盘检测延迟——从漂移发生到告警触发隔了多久，是否需要调整探测器灵敏度。

成熟团队会把「漂移响应」当作与「线上故障响应」并列的运维流程来建设：有值班归属、有处置预案、有事后复盘。区别只在节奏——故障以分钟计、漂移以天计，但两者都遵循同一条原则：检测、归因、止损、修复、防御，缺一环都会让同样的问题反复发生。

小结

  • 漂移是「代码一行未动、行为却悄悄变化」的现象，危险在于渐进与无声，等投诉积累时往往已持续数周。
  • 按来源分类是检测设计的前提：上游模型静默更新、输入分布变化、知识库陈旧、prompt 演进副作用、依赖与数据管道变化，各自需要不同的探测器。
  • 三类检测手段互补：线上抽样持续评测看真实质量、输入/输出分布统计看全量形状、金丝雀查询集定期重放做受控对照；judge 必须版本固定，否则尺子在变会制造假漂移。
  • 告警的核心矛盾是灵敏度与误报率，降噪手段包括相对基线而非绝对阈值、持续性条件、样本量门槛、分级告警、交叉确认升级与告警聚合抑制。
  • 告警本身也要质量回路：每条告警处理后标记真实或误报，定期回顾误报率调阈值，否则系统会在半年内退化为全员静音。
  • 响应流程标准化为确认与定性、归因到来源、快速止损、系统性修复、沉淀与防御五步；成熟团队把它当作与故障响应并列的运维流程建设，并把坏例回灌回归集与金丝雀集。
