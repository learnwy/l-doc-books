输出格式控制

核心概念

输出格式控制是提示工程中确保模型输出可被程序可靠解析的关键技术。在生产环境中，LLM 的输出通常需要被下游系统消费——无论是前端渲染、API 响应还是数据管道，都要求输出符合预定义的结构。格式控制技术解决了 LLM 输出的不确定性问题，将自由文本转化为结构化数据。

格式控制的核心矛盾在于：越严格的格式约束通常需要越多的 Token 来描述，但带来更高的解析可靠性。工程师需要根据场景在可靠性和成本之间找到平衡点。


JSON 输出控制
JSON 是 LLM 输出格式化的首选方案，因为它具有严格的语法、广泛的解析器支持以及良好的可读性。


基础方法：指令 + 示例


分析以下代码的质量问题，以 JSON 格式输出。

JSON 格式要求：
{
  "file": "文件名",
  "issues": [
    {
      "line": 行号,
      "severity": "error" | "warning" | "info",
      "category": "security" | "performance" | "style" | "logic",
      "description": "问题描述",
      "suggestion": "修复建议"
    }
  ],
  "summary": {
    "total": 总问题数,
    "errors": 错误数,
    "warnings": 警告数,
    "score": 0-100 的质量分数
  }
}

只输出 JSON，不要添加任何其他文字或 markdown 代码块标记。

XML 与标记语言控制
当输出包含复杂嵌套结构或混合内容（结构化数据 + 自由文本）时，XML 标记是更合适的选择。Claude 系列模型对 XML 标签的遵循度尤其高。


请按以下 XML 格式输出代码审查结果：

<review>
  <file path="文件路径">
    <issue severity="error|warning|info">
      <location line="行号" column="列号"/>
      <description>问题描述</description>
      <fix>
        <before>修改前的代码</before>
        <after>修改后的代码</after>
      </fix>
    </issue>
  </file>
  <summary>
    <score>0-100</score>
    <recommendation>通过|需修改|拒绝</recommendation>
  </summary>
</review>
XML 标记的独特优势：


在 Claude 模型中，XML 标签还有一个特殊用途——作为输入的结构化分隔符：


<context>
这是一个电商平台的后端系统，使用 Node.js + PostgreSQL。
</context>

<task>
优化以下慢查询，要求响应时间从 2 秒降低到 200 毫秒。
</task>

<code>
SELECT * FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
WHERE o.created_at > '2024-01-01'
ORDER BY o.total_amount DESC;
</code>

<output_format>
返回优化后的 SQL 和性能分析说明。
</output_format>
多格式混合输出
实际应用中，往往需要在单次输出中混合使用多种格式。例如，代码审查需要同时输出结构化问题列表和自然语言总结。


请分析以下代码并按照下面的格式输出结果。

===分析结果===

[问题列表]
以 JSON 数组格式列出所有发现的问题：
(JSON 数组)

[修复建议]
以 Markdown 格式给出修复建议，使用有序列表。

[整体评估]
一段 3-5 句话的自然语言总结。

===结束===
混合格式的设计原则：


    

  • 明确的分区标识：使用一致的分隔符（===、---、XML 标签）划分不同格式区域
    • 

  • 每个区域独立可解析：即使某一区域解析失败，不影响其他区域
    • 

  • 格式描述前置：在提示开头就声明完整的输出格式规范
    • 



interface ParsedReviewOutput {
  issues: ReviewIssue[];
  suggestions: string;
  summary: string;
}

const parseReviewOutput = (raw: string): ParsedReviewOutput => {
  const issueMatch = raw.match(/\[问题列表\]\n([\s\S]*?)\n\[修复建议\]/);
  const suggestionMatch = raw.match(/\[修复建议\]\n([\s\S]*?)\n\[整体评估\]/);
  const summaryMatch = raw.match(/\[整体评估\]\n([\s\S]*?)===结束===/);

  return {
    issues: issueMatch ? JSON.parse(issueMatch[1].trim()) : [],
    suggestions: suggestionMatch ? suggestionMatch[1].trim() : '',
    summary: summaryMatch ? summaryMatch[1].trim() : '',
  };
};
格式可靠性增强策略
即使使用了格式约束，模型输出仍可能偏离预期。以下策略可以进一步提升可靠性：


重试与修复机制：


const getStructuredOutput = async <T>(prompt: string, schema: JSONSchema, maxRetries: number = 3): Promise<T> => {
  for (let i = 0; i < maxRetries; i++) {
    const response = await callLLM(prompt);
    try {
      const parsed = JSON.parse(response);
      const valid = validateSchema(parsed, schema);
      if (valid) return parsed as T;
    } catch {
      prompt = `${prompt}\n\n上一次输出的 JSON 格式有误，请严格按照 Schema 重新输出。`;
    }
  }
  throw new Error('Failed to get valid structured output');
};
分段生成：对于复杂输出，将一次生成拆分为多次，每次只生成输出的一个部分。

小结
    

  • 输出格式控制是将 LLM 输出接入生产系统的必备技术
    • 

  • JSON 是最通用的格式选择，配合 Schema 约束可达到高可靠性
    • 

  • XML 标记适合复杂嵌套和混合内容场景，Claude 模型对其支持尤佳
    • 

  • 多格式混合输出需要明确的分区标识和独立可解析设计
    • 

  • 生产环境必须配备重试、容错解析和后处理管道
    • 

  • Function Calling / JSON Mode 等 API 级别方案是格式控制的终极手段
    •
