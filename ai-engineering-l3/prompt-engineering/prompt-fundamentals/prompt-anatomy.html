Prompt 解剖学

核心概念

一个高质量的 Prompt 并非随意拼凑的文字，而是由多个功能明确的结构组件有机组合而成。理解这些组件的作用和组合方式，是从"凭直觉写 Prompt"跨越到"系统化设计 Prompt"的关键转折点。

并非每个 Prompt 都需要包含所有五个组件——简单任务可能只需要一个指令，而复杂任务可能需要五个组件的完整配合。关键是理解每个组件的作用，然后根据任务需求灵活组合。




五大核心组件
一、指令（Instruction）
指令是 Prompt 的核心——它告诉模型"做什么"。一个清晰的指令应该明确动作和目标。


弱指令：
关于这段代码说点什么。

强指令：
审查以下 TypeScript 代码，找出潜在的类型安全问题，并为每个问题提供修复建议。
有效指令的特征：






特征
反面示例
正面示例





动词明确
"处理这些数据"
"将这些 CSV 数据转换为 JSON 格式"




范围清晰
"优化代码"
"优化这个函数的时间复杂度，目标从 O(n²) 降到 O(n log n)"




可衡量
"写个好的函数"
"写一个函数，通过所有提供的测试用例"




无歧义
"简单解释一下"
"用不超过 3 句话，面向非技术人员解释"





二、上下文（Context）
上下文为模型提供完成任务所需的背景信息。没有上下文的指令就像在真空中提问——模型只能基于训练数据中的通用知识来回答。


无上下文：
写一个用户注册的 API 接口。

有上下文：
## 项目上下文
- 后端框架：Express.js + TypeScript
- 数据库：PostgreSQL，使用 Prisma ORM
- 认证方案：JWT
- 现有用户模型包含字段：id, email, passwordHash, name, createdAt

## 任务
基于以上项目上下文，编写一个用户注册的 API 接口。
上下文可以包含以下类型的信息：


    

  • 技术上下文：编程语言、框架版本、依赖库、项目架构
    • 

  • 业务上下文：业务规则、用户画像、使用场景
    • 

  • 约束上下文：性能要求、安全限制、兼容性需求
    • 

  • 风格上下文：编码规范、命名约定、文档标准
    • 

  • 参考上下文：相关代码片段、API 文档、设计稿
    • 



三、输入（Input）
输入是模型需要直接处理的具体数据。它与上下文不同——上下文是背景信息，输入是操作对象。


## 指令
将以下英文技术文档翻译为中文，保留代码块不翻译。

## 上下文
这是一份面向初级开发者的 React 教程文档。

## 输入
React components let you split the UI into independent, reusable pieces,
and think about each piece in isolation. Conceptually, components are like
JavaScript functions. They accept arbitrary inputs (called "props") and
return React elements describing what should appear on the screen.
在这个例子中，"指令"说明做什么（翻译），"上下文"说明背景（初级开发者教程），"输入"是需要翻译的具体文本。三者各司其职。


四、输出格式（Output Format）
输出格式定义了模型回复的结构和形式。明确的输出格式能大幅减少后处理工作，并提高输出的一致性。


## 输出格式要求
以 JSON 格式返回审查结果，包含以下字段：

{
  "summary": "审查总结（一句话）",
  "issues": [
    {
      "severity": "error | warning | info",
      "line": "行号",
      "description": "问题描述",
      "suggestion": "修复建议"
    }
  ],
  "score": "代码质量评分（1-10）"
}
常见的输出格式约束：






格式类型
适用场景
示例约束





JSON
API 集成、数据处理
"以 JSON 格式返回，不包含 markdown 代码块"




Markdown
文档生成、报告
"使用 H2 标题分节，每节包含一个表格"




表格
对比分析、数据展示
"以 markdown 表格形式列出，包含 X/Y/Z 三列"




列表
枚举、步骤说明
"使用编号列表，每项不超过 20 字"




代码
代码生成
"只输出代码，不要包含解释性文字"




自由文本
创意写作、分析报告
"以学术论文的风格，限 500 字以内"





五、示例（Examples）
示例是 Prompt 中最强大的组件之一——它通过具体的输入-输出对来展示期望的模式，让模型通过"模仿"来理解任务要求。


## 任务
将用户的自然语言查询转换为 SQL 语句。

## 示例

用户: 查找所有价格超过 100 元的商品
SQL: SELECT * FROM products WHERE price > 100;

用户: 统计每个分类下的商品数量
SQL: SELECT category, COUNT(*) as count FROM products GROUP BY category;

用户: 找出最近 7 天注册的用户
SQL: SELECT * FROM users WHERE created_at >= NOW() - INTERVAL '7 days';

## 输入
用户: 查找购买次数最多的前 10 个用户
示例的设计原则：


    

  • 覆盖典型情况：示例应包含最常见的场景
    • 

  • 覆盖边界情况：至少一个示例展示非典型输入的处理方式
    • 

  • 格式一致：所有示例的格式保持统一
    • 

  • 数量适度：通常 2-5 个示例足够，过多会消耗 Token 且可能引入干扰
    •

CRISPE 示例
[Capacity - 角色]
你是一位拥有 15 年经验的高级后端架构师，专精于分布式系统设计和微服务架构。

[Request - 请求]
请为一个日活 100 万用户的电商平台设计订单服务的技术架构。

[Insight - 背景]
当前系统是单体架构，数据库为 MySQL 单实例，峰值 QPS 约 5000。
团队有 8 名后端开发者，熟悉 Java/Spring Boot 技术栈。

[Statement - 约束]
- 需要支持水平扩展
- 数据一致性要求：订单创建和支付必须强一致
- 预算限制：云服务月费不超过 5 万元
- 迁移必须支持灰度发布，不可停服

[Personality - 风格]
以技术方案评审的口吻，专业但不晦涩。使用图表辅助说明。

[Experiment - 格式]
输出结构：
1. 架构总览（含架构图描述）
2. 核心组件设计
3. 数据库方案
4. 迁移策略
5. 风险评估

RISEN 示例

[Instructions - 指令]
为以下 REST API 端点编写标准的 API 参考文档。

[Steps - 步骤]
请按以下步骤组织文档：
1. 编写端点概述（一句话描述用途）
2. 列出请求参数（路径参数、查询参数、请求体）
3. 描述响应格式（成功和错误响应）
4. 提供请求示例（使用 curl）
5. 列出可能的错误码及其含义

[Expectations - 期望]
- 参数描述必须包含：名称、类型、是否必填、说明
- 每个响应码都需要示例 JSON
- curl 示例必须可以直接复制执行
- 风格参考 Stripe API 文档

[Narrowing - 缩窄]
- 不要包含认证方式的说明（已有独立文档）
- 不要包含 SDK 示例（只需 curl）
- 不要解释 REST 的基本概念

重要认知：框架是工具，不是教条。在实际工作中，很少有人严格按照某个框架的每个组件来编写 Prompt。更常见的做法是理解各框架的核心思想，然后根据具体任务灵活组合。




结构化 Prompt 的设计原则
使用清晰的分节标记
Markdown 标题、XML 标签和分隔线是三种最有效的分节方式：


方式一：Markdown 标题
## 角色
你是一位数据分析师。

## 任务
分析以下销售数据的趋势。

## 数据
[数据内容]

## 输出要求
以表格形式展示月度趋势。
方式二：XML 标签
<role>你是一位数据分析师。</role>
<task>分析以下销售数据的趋势。</task>
<data>[数据内容]</data>
<output_format>以表格形式展示月度趋势。</output_format>
方式三：分隔线
你是一位数据分析师。
---
任务：分析以下销售数据的趋势。
---
数据：
[数据内容]
---
输出要求：以表格形式展示月度趋势。
三种方式的效果相近。Markdown 标题最直观，XML 标签在需要嵌套结构时更灵活（Claude 对 XML 标签有特别好的支持），分隔线最简洁。


信息排列的最佳顺序
基于注意力机制和"迷失在中间"现象，推荐的信息排列顺序为：


1. 角色/身份定义          ← 开头：建立基调
2. 核心任务指令          ← 紧跟：最重要的内容
3. 约束和规则            ← 中上：限定行为边界
4. 上下文/参考资料       ← 中间：背景信息
5. 输入数据              ← 中下：操作对象
6. 输出格式要求          ← 结尾：最后的强约束
7. 示例（如有）          ← 紧接输出格式
8. 提醒/重申关键约束     ← 最后：防止遗忘


常见结构性反模式
反模式一：信息墙（Wall of Text）
❌ 反模式：
我需要你帮我分析一下这段代码的问题然后给出修复建议代码是用 TypeScript 写的是一个 React 组件用来展示用户列表数据从 API 获取使用了 useEffect 和 useState 但是有时候会出现内存泄漏的警告我不太确定是不是因为组件卸载后异步请求还在执行导致的请你帮我看看然后给出一个完整的修复方案要求保持现有功能不变

✅ 改进后：
## 任务
分析以下 React 组件中的内存泄漏问题，并提供修复方案。

## 问题描述
- 组件功能：展示用户列表，数据从 API 获取
- 使用的 Hooks：useEffect, useState
- 症状：组件卸载后出现内存泄漏警告
- 疑似原因：组件卸载后异步请求仍在执行

## 要求
- 保持现有功能不变
- 给出完整的修复代码

## 代码
[粘贴代码]
反模式二：矛盾指令
❌ 反模式：
请详细解释每一步的实现原理。
回复要简洁，控制在 100 字以内。

✅ 改进后：
请用 100 字以内概述实现原理的关键点。
当 Prompt 中存在矛盾指令时，模型无法同时满足两个冲突的要求，输出质量会显著下降。常见的矛盾对包括：






矛盾对
问题





"详细" vs "简洁"
长度要求冲突




"创造性" vs "严格按示例"
创造力与约束冲突




"只输出代码" vs "解释思路"
输出内容冲突




"用中文" vs 示例全是英文
语言信号冲突





反模式三：模糊代词
❌ 反模式：
用户提交了一个表单，它验证失败了，把它的错误信息显示在那个地方。
这里的"它""那个"指代不清。

✅ 改进后：
当用户提交注册表单时，如果 email 字段验证失败，
在 email 输入框下方显示红色错误提示："请输入有效的邮箱地址"。
反模式四：过度约束
❌ 反模式：
写一个函数。
- 必须用 TypeScript
- 必须用箭头函数
- 必须用 const 声明
- 变量名必须是 camelCase
- 必须有 JSDoc 注释
- 必须用 2 空格缩进
- 返回值类型必须显式标注
- 参数必须有默认值
- 必须处理 null 和 undefined
- 函数体不超过 10 行
- 不使用 any 类型
- 不使用三元表达式
...（20 条约束）

✅ 改进后：
写一个 TypeScript 箭头函数。遵循以下编码规范：

```typescript
// 示例：期望的代码风格
const greet = (name: string = "World"): string => {
  if (!name) {
    return "Hello, World!";
  }
  return `Hello, ${name}!`;
};
```
用一个示例展示风格，比 20 条规则更有效且消耗更少的 Token。




实际应用：组装一个完整的 Prompt
以下是一个综合运用五大组件的完整 Prompt 示例，用于构建一个代码迁移助手：


## 角色

你是一位精通 React 生态系统的前端架构师，尤其擅长 Class Component 到 Hooks 的迁移。

## 任务

将以下 React Class Component 迁移为使用 Hooks 的 Function Component。

## 上下文

- 项目使用 React 18 + TypeScript 5
- 状态管理已从 Redux 迁移到 Zustand
- 项目启用了 strict mode
- 编码规范要求所有组件使用函数式写法

## 约束

- 保持所有现有功能和对外接口（props）不变
- 生命周期方法需正确映射到对应的 Hook
- componentDidCatch 如果存在，需要保留为 Error Boundary（Class Component）
- 不引入新的依赖

## 输出格式

1. 先列出迁移要点（3-5 条，每条一行）
2. 然后输出完整的迁移后代码
3. 最后列出需要注意的风险点

## 示例

迁移前：class Timer extends React.Component { state = { count: 0 }; interval = null; componentDidMount() { this.interval = setInterval(() => { this.setState(prev => ({ count: prev.count + 1 })); }, 1000); } componentWillUnmount() { clearInterval(this.interval); } render() { return <div>{this.state.count}</div>; } }

迁移后：const Timer: React.FC = () => { const [count, setCount] = useState(0);

useEffect(() => { const interval = setInterval(() => { setCount(prev => prev + 1); }, 1000); return () => clearInterval(interval); }, []);

return <div>{count}</div>; };

## 输入（需要迁移的代码）

[在此粘贴需要迁移的 Class Component 代码]

这个 Prompt 包含了所有五大组件：指令（任务）、上下文（项目信息和约束）、输入（需要迁移的代码）、输出格式（三段式结构）、示例（Timer 组件的迁移对比）。每个组件用 Markdown 标题清晰分隔，信息排列遵循推荐顺序。




小结
    

  • 高质量 Prompt 由指令、上下文、输入、输出格式、示例五大组件构成，根据任务复杂度灵活组合。
    • 

  • CRISPE 框架强调角色人格和输出风格，适合需要特定"人格"的场景。
    • 

  • RISEN 框架强调执行步骤和质量标准，适合复杂的结构化任务。
    • 

  • 框架是工具而非教条——理解核心思想后，应根据实际需求灵活组合。
    • 

  • 使用 Markdown 标题、XML 标签或分隔线来清晰分隔 Prompt 的不同部分。
    • 

  • 避免四大反模式：信息墙（缺乏结构）、矛盾指令（冲突要求）、模糊代词（指代不清）、过度约束（规则过多，用示例替代）。
    •
