Token 与上下文窗口

核心概念

Token 是大语言模型处理信息的基本单位——它既是 LLM 的"计费单位"，也是"记忆单位"。理解 Token 的本质和上下文窗口的约束，是 Prompt Engineering 中最具实操价值的知识之一。它直接决定了你能向模型传递多少信息、每次调用的成本是多少、以及如何在有限资源内最大化输出质量。



什么是 Token
Token 的本质
Token 是 Tokenizer（分词器）将文本切分后的最小单元。现代 LLM 使用的 Tokenizer 大多基于两种算法：


BPE（Byte Pair Encoding）：GPT 系列和 Claude 使用的主流算法。它从单个字节出发，通过统计频率不断合并相邻的字节对，形成一个固定大小的词表（通常 50,000-100,000 个 Token）。高频词汇会被编码为单个 Token，低频或生僻词汇会被拆分为多个 Token。


SentencePiece：Google 的 Gemini 和 Meta 的 Llama 使用的算法。它将文本视为原始字节流，不依赖预分词，对多语言支持更友好。


Token 拆分示例
不同类型的文本，Token 拆分方式差异很大：


英文常见词（通常 1 Token）：
"the" → [the]
"hello" → [hello]
"code" → [code]

英文长词（可能 2-3 Token）：
"tokenization" → [token] [ization]
"unbelievable" → [un] [believ] [able]
"implementation" → [implement] [ation]

中文（通常每 1-2 字 1 Token）：
"你好" → [你好]           (1 Token)
"大语言模型" → [大] [语言] [模型]  (3 Token)
"人工智能" → [人工] [智能]     (2 Token)

代码（Token 拆分较细）：
"console.log('hello')" → [console] [.] [log] [(] ['hello'] [')]  (约 6 Token)
"if (x > 0) {" → [if] [ (] [x] [ >] [ 0] [)] [ {]              (约 7 Token)

特殊字符和数字：
"2024-01-15" → [202] [4] [-] [01] [-] [15]  (约 6 Token)
"user@email.com" → [user] [@] [email] [.] [com]  (约 5 Token)

上下文窗口
什么是上下文窗口
上下文窗口（Context Window）是 LLM 在单次请求中能处理的最大 Token 数量。它包括输入 Token（Prompt）和输出 Token（Completion）的总和。


上下文窗口 = Prompt Token + Completion Token

示例（128K 上下文窗口）：
- 如果 Prompt 占用 100K Token → 最多只能生成 28K Token 的回复
- 如果 Prompt 占用 10K Token → 最多可以生成 118K Token 的回复

上下文窗口的扩大是近年来 LLM 发展的重要趋势。从 GPT-3 的 4K 到 Gemini 的 2M，增长了 500 倍。但更大的上下文窗口不等于更好的信息利用能力。




"迷失在中间"问题
现象描述
2023 年斯坦福大学的一项研究揭示了一个重要现象：当 LLM 处理长文本时，放置在输入开头和结尾的信息被利用得最好，而放置在中间的信息最容易被忽略。


这被称为**"Lost in the Middle"**（迷失在中间）现象。它意味着即使上下文窗口足够大，模型也不会均匀地处理所有输入信息。


实验验证
场景：从 20 篇文档中找到包含特定答案的那一篇

答案放在第 1 篇（开头）：准确率 ~95%
答案放在第 10 篇（中间）：准确率 ~55%
答案放在第 20 篇（结尾）：准确率 ~90%
注意力呈现明显的 U 形曲线——开头和结尾高，中间低。


对 Prompt 设计的影响
基于这个现象，在设计长 Prompt 时应遵循以下策略：


核心指令放在开头和结尾：


## 关键要求（放在开头）
你必须以 JSON 格式返回结果，且只返回 JSON，不要包含任何其他文字。

[中间部分：大量的参考文档和上下文信息]

## 再次提醒（放在结尾）
输出格式：纯 JSON，不要包含 markdown 代码块标记。
关键信息重复出现：将最重要的约束条件在 Prompt 的不同位置重复，确保至少一次能被模型充分注意到。


精简中间部分：对中间的参考资料进行预处理，去除无关内容，只保留与当前任务直接相关的信息。




有效的上下文使用策略
策略一：Prompt 预算规划
在设计 Prompt 之前，先做一个 Token 预算规划：


总预算：128,000 Token
├── 系统提示：~2,000 Token
├── 任务指令：~500 Token
├── 参考资料：~5,000 Token
├── 用户输入：~1,000 Token（可变）
├── 历史对话：~10,000 Token（可变）
├── 安全缓冲：~5,000 Token
└── 模型回复预留：~16,000 Token
    ─────────────────────────
    已规划：~39,500 Token
    剩余可用：~88,500 Token
策略二：渐进式上下文加载
不要一次性将所有信息塞进 Prompt，而是根据任务需要分步加载：


第一轮：系统提示 + 任务描述 + 核心约束
→ 模型理解任务

第二轮：追加关键参考资料
→ 模型获取必要知识

第三轮：追加用户的具体输入
→ 模型生成最终输出

策略四：利用摘要中继
当需要处理超长文档时，可以使用"摘要中继"策略：


步骤 1：将长文档分成多段，让模型逐段摘要
Prompt: "请用 200 字摘要以下内容：[文档第 1 部分]"
输出: 摘要 1

步骤 2：汇总所有摘要
Prompt: "请用 200 字摘要以下内容：[文档第 2 部分]"
输出: 摘要 2

步骤 3：基于所有摘要执行最终任务
Prompt: "基于以下摘要，回答用户的问题：
[摘要 1]
[摘要 2]
[摘要 3]
用户问题：[具体问题]"

关键观察：输出 Token 通常比输入 Token 贵 4-5 倍。这意味着要求模型"详细解释每一步"会显著增加成本，而要求"只输出最终结果"可以大幅节省。


成本优化策略
高成本 Prompt：
请详细解释 quicksort 算法的工作原理，然后用 Python 实现它，
最后逐行解释代码的含义。

低成本 Prompt（同等效果）：
用 Python 实现 quicksort。代码上方用单行注释标注关键步骤。
第一个 Prompt 可能生成 500+ Token 的输出，第二个可能只需 100 Token。在大规模 API 调用场景下，这个差异会转化为显著的成本差距。

小结
    

  • Token 是 LLM 处理的最小单位，由 BPE 或 SentencePiece 算法生成，同一文本在不同模型上的 Token 数可能不同。
    • 

  • CJK 文字的 Token 效率低于 Latin 文字——表达相同语义，中文约消耗英文的 1.5-2.5 倍 Token。
    • 

  • 上下文窗口是单次请求的 Token 总容量，包含输入和输出，从 4K 发展到了 2M，但更大不代表更好。
    • 

  • **"迷失在中间"**现象表明模型对输入开头和结尾的关注度高于中间，设计长 Prompt 时应将关键信息放在首尾。
    • 

  • Token 预算规划是专业 Prompt Engineering 的必备实践——在设计 Prompt 之前先规划各部分的 Token 分配。
    • 

  • 输出 Token 比输入 Token 贵 4-5 倍，精简输出要求和按需加载上下文是有效的成本控制手段。
    •
