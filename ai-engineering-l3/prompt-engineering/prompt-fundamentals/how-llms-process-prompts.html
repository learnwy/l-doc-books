LLM 如何处理 Prompt

核心概念

大语言模型（LLM）接收到 Prompt 后，并不像人类一样"理解"语义，而是通过一系列精密的数学运算将输入文本转化为输出文本。理解这个处理过程，是有效设计 Prompt 的理论基础——你不需要成为机器学习专家，但需要建立足够的直觉来指导实践决策。

从宏观上看，LLM 处理 Prompt 的流程可以概括为：将文本切分为 Token → 将 Token 转化为数字向量 → 通过注意力机制计算 Token 之间的关系 → 生成下一个 Token 的概率分布 → 通过采样策略选择输出 Token → 将输出 Token 拼接回输入，重复以上过程。


这个过程中的每一步都对 Prompt 的设计产生直接影响。




Tokenization：文本的"数字化"
什么是 Tokenization
LLM 无法直接处理文字，它需要先将文字转化为数字。Tokenization（分词）就是这个转化过程——将原始文本拆分为一个个 Token（词元），每个 Token 对应一个整数 ID。


输入文本: "Prompt Engineering 是一门新兴技能"

Tokenization 结果（示意）:
["Prompt", " Engineering", " 是", "一", "门", "新", "兴", "技", "能"]

Token IDs（示意）:
[42059, 17009, 11571, 1002, 8421, 3789, 5510, 2390, 4800]
需要注意的关键点：


Token ≠ 词：一个英文单词可能被拆成多个 Token（如 "tokenization" → "token" + "ization"），而一个常见短语可能被合并为一个 Token。中文通常每 1-2 个字对应一个 Token。


空格和标点也是 Token 的一部分：空格通常被编码进后续 Token 的前缀中，标点符号独立成 Token。这意味着 Prompt 中的空行、缩进、标点都会消耗 Token 配额。


不同模型的 Tokenizer 不同：GPT-4 使用 cl100k_base，Claude 使用自己的 Tokenizer，Llama 使用 SentencePiece。同一段文本在不同模型上的 Token 数量可能不同。

注意力机制：Token 如何"看到"彼此
自注意力的工作原理
Transformer 架构的核心是自注意力机制（Self-Attention）。它让模型中的每一个 Token 都能"关注"到输入序列中的所有其他 Token，并根据相关性分配不同的权重。


上图是一个简化示意：当模型处理到"函数"这个 Token 时，它会回头"看"序列中的所有其他 Token。"排序"和"写"获得较高的注意力权重（因为它们与"函数"语义关联度高），而"请"和"用"获得较低的权重。


在实际的 Transformer 中，这个过程通过 Query-Key-Value（QKV）矩阵运算实现：


    

  1. 每个 Token 生成三个向量：Query（我在找什么）、Key（我是什么）、Value（我的内容是什么）
    2. 

  2. 通过 Query 和所有 Key 的点积计算注意力分数
    3. 

  3. 分数经过 Softmax 归一化后作为权重
    4. 

  4. 用权重对所有 Value 加权求和，得到该 Token 的最终表示
    5. 



多头注意力
实际的 LLM 不止有一个注意力"头"，而是有数十甚至上百个并行运行的注意力头。每个头关注不同维度的模式：


    

  • 某些头关注语法结构（主语-谓语-宾语的关系）
    • 

  • 某些头关注语义相似性（近义词、同主题词汇）
    • 

  • 某些头关注位置模式（相邻 Token、段落首尾）
    • 

  • 某些头关注指令跟随（识别"请"、"要求"等指令标记）
    • 



对 Prompt 设计的影响
注意力机制的工作方式解释了许多 Prompt 设计经验：


词序很重要：注意力权重受位置影响。将最重要的指令放在 Prompt 的开头或结尾（而非中间），通常能获得更好的遵循度。这与"Lost in the Middle"现象直接相关。


结构化格式有效：使用标题、列表、分隔线等结构化元素，帮助注意力机制更容易识别和区分不同的语义单元。


低效（连续文本）：
我需要你帮我写一个 Python 函数它的功能是对列表进行排序要求使用快速排序算法并且支持自定义比较函数输出要包含类型注解

高效（结构化）：
## 任务
编写一个 Python 排序函数

## 要求
- 算法：快速排序
- 支持自定义比较函数
- 包含类型注解

## 输入
- 列表类型：List[T]
- 比较函数：Callable[[T, T], int]（可选）
上下文长度影响注意力分布：当 Prompt 很长时，注意力资源被稀释。模型可能无法同等程度地关注所有内容。精简 Prompt 能让注意力更集中。




Next-Token Prediction：生成的核心机制
工作原理
LLM 的核心能力——文本生成——本质上是一个不断重复的 Next-Token Prediction（下一个 Token 预测）过程：


每一步，模型都会：


    

  1. 将当前所有 Token（原始 Prompt + 已生成的 Token）作为输入
    2. 

  2. 通过 Transformer 的多层注意力计算
    3. 

  3. 输出词表中每一个 Token 的概率分布（logits）
    4. 

  4. 根据采样策略从概率分布中选择一个 Token
    5. 

  5. 将选中的 Token 追加到序列末尾，重复步骤 1
    6. 



这个过程持续进行，直到模型生成一个特殊的结束标记（End-of-Sequence Token）或达到最大长度限制。


自回归的关键含义
模型只能向前生成，无法"回头修改"。一旦某个 Token 被选中并追加到序列中，后续的所有生成都会基于这个 Token。如果第一个 Token 选错了方向，后续可能越走越偏。


这对 Prompt 设计的启示是深远的：


    

  • 引导模型"先思考再回答"（Chain-of-Thought）可以显著提升输出质量，因为思考过程中生成的 Token 为后续推理提供了正确的上下文基础。
    • 

  • 要求模型输出结构化格式（如 JSON）时，模型的生成顺序会影响正确性——先生成的字段可以被后续字段参考。
    • 

  • Prompt 的最后一句话尤为重要，因为它直接影响模型生成的第一个 Token，而第一个 Token 会影响后续所有 Token。
    • 





Temperature 与采样策略
Temperature 的作用
模型在每一步生成的并不是一个确定的 Token，而是一个概率分布。Temperature 参数控制这个概率分布的"尖锐程度"：






Temperature 值
概率分布特征
输出特征
适用场景





0
始终选择最高概率
确定性、可复现
代码生成、数据提取




0.1 - 0.3
接近贪心，偶有变化
高度一致、略有创造性
翻译、摘要




0.5 - 0.7
中等随机性
平衡一致性与多样性
通用对话、写作辅助




0.8 - 1.0
较高随机性
多样、富有创造性
创意写作、头脑风暴




> 1.0
高度随机
不可预测、可能不连贯
极少使用





Temperature = 0 时：
输入: "最好的编程语言是"
输出: "Python，因为它简洁、易学、生态丰富。" （每次相同）

Temperature = 1.0 时：
输入: "最好的编程语言是"
输出 1: "一个永远没有定论的话题，每种语言都有其独特的魅力。"
输出 2: "取决于你的使用场景——Web 开发选 JavaScript，数据科学选 Python。"
输出 3: "Rust，因为它在安全性和性能之间取得了完美平衡。"
Top-p（核采样）
Top-p 是另一种控制采样的策略。它不直接调整概率分布，而是设定一个累积概率阈值，只从累积概率达到阈值的最小 Token 集合中采样：


模型输出的 Token 概率分布：
  "Python"   → 0.35
  "JavaScript" → 0.25
  "Rust"     → 0.15
  "Go"       → 0.10
  "Java"     → 0.08
  "C++"      → 0.04
  "Ruby"     → 0.03

Top-p = 0.75 时：
  候选集 = {"Python", "JavaScript", "Rust"} (0.35 + 0.25 + 0.15 = 0.75)
  从这三个中按归一化概率采样

Top-p = 0.5 时：
  候选集 = {"Python", "JavaScript"} (0.35 + 0.25 = 0.60 ≥ 0.5)
  从这两个中按归一化概率采样
对 Prompt 设计的影响
Temperature 和 Top-p 的选择应该与 Prompt 的设计目标相匹配：


需要确定性输出时：Temperature 设为 0，同时在 Prompt 中给出明确的输出格式约束。这在 API 调用、数据提取等场景中至关重要。


需要创造性输出时：Temperature 设为 0.7-1.0，同时在 Prompt 中鼓励多样性（如"请提供多个不同角度的观点"）。Temperature 和 Prompt 指令应该协同工作，而非互相矛盾。


Temperature 和 Prompt 的交互：即使 Temperature = 0，不同的 Prompt 仍然会产生不同的输出。Temperature 控制的是在给定 Prompt 下的输出变异性，而 Prompt 控制的是输出的方向性。




词序为什么重要
位置编码
Transformer 本身没有序列顺序的概念——它通过位置编码（Positional Encoding）来感知 Token 的先后关系。不同的位置编码方案（绝对位置编码、旋转位置编码 RoPE、ALiBi 等）赋予模型不同的位置感知能力。


核心启示是：Prompt 中信息的排列顺序会影响模型对信息的权重分配。


Prompt A：
先写代码，然后解释你的设计思路。
任务：实现一个 LRU 缓存。

Prompt B：
任务：实现一个 LRU 缓存。
先解释你的设计思路，然后写代码。
这两个 Prompt 的信息内容相同，但排列顺序不同，输出也会不同。Prompt A 倾向于先生成代码，Prompt B 倾向于先生成解释。模型会遵循最近的指令和最后的指令的倾向性。


为什么措辞变化会影响输出
同义但不同措辞的 Prompt 可能产出不同质量的结果：


Prompt A: "列出 5 个提高代码质量的方法"
Prompt B: "作为一名资深软件工程师，请分析并列出 5 个经过实践验证的提高代码质量的策略，每个策略附带一个简短的理由"
Prompt B 更好的原因不仅在于它更详细，还在于它触发了模型训练数据中不同的知识区域。"资深软件工程师"触发了专业知识模式，"经过实践验证"触发了实证模式，"策略"比"方法"触发了更系统化的思维模式。




"随机鹦鹉" vs "推理能力"
关于 LLM 是否真正"理解"语言，学术界存在持续的争论：


"随机鹦鹉"观点
LLM 本质上是一个极其复杂的模式匹配系统。它通过在海量文本上训练，学会了文本序列的统计规律。它不"理解"含义，只是在概率上预测"什么 Token 最可能出现在这里"。所谓的"推理"只是对训练数据中推理模式的模仿。


"涌现推理"观点
当模型规模达到一定阈值后，涌现出了训练数据中未直接存在的能力。GPT-4 能解决从未在训练数据中出现过的数学问题，Claude 能在复杂的多步推理任务中表现出类似逻辑推演的行为。这些能力似乎超越了简单的模式匹配。


对 Prompt 设计的实际意义
无论哪种观点正确，对 Prompt 设计者来说，实际意义是明确的：






原则
原因





不要假设模型"理解"你的意图
即使模型表现得像在理解，也应该通过明确的指令来消除歧义




利用模式匹配的优势
提供示例（Few-Shot）让模型"模仿"正确的模式，比抽象描述更有效




引导推理过程
通过 Chain-of-Thought 让模型逐步展示推理，减少跳步带来的错误




验证而非信任
模型可能自信地输出错误答案（幻觉），始终需要验证关键信息




利用结构化输出
结构化格式（JSON、表格）迫使模型在模式匹配层面保持一致性







小结
    

  • LLM 通过 Tokenization → Embedding → Attention → Prediction → Sampling 的流水线处理 Prompt。
    • 

  • Tokenization 将文本切分为 Token，Token 数量决定成本和上下文容量，中英文的 Token 效率存在差异。
    • 

  • 注意力机制让每个 Token 关注序列中所有其他 Token，结构化格式和合理的信息排列能帮助注意力更有效地工作。
    • 

  • Next-Token Prediction 是自回归过程——模型只能向前生成，无法回头修改，因此引导模型"先思考再回答"至关重要。
    • 

  • Temperature 控制输出的随机性，应根据任务性质选择合适的值，并与 Prompt 指令协同设计。
    • 

  • 无论 LLM 是否真正"理解"语言，Prompt 设计者都应该明确指令、提供示例、引导推理、验证输出。
    •
