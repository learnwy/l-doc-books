Prompt 评估方法

核心概念

Prompt 评估是指通过系统化的方法衡量 Prompt 输出质量的实践。它是 Prompt Engineering 从"凭感觉调参"走向"数据驱动优化"的关键环节。评估方法可分为人工评估、自动化指标和 LLM-as-Judge 三大类，各有适用场景和局限性。

为什么评估至关重要
Prompt 优化的核心矛盾在于：人类直觉对 Prompt 质量的判断极不可靠。一个开发者认为"更好"的改写，可能在 100 个真实输入上只有 52% 的胜率——统计上与随机无异。没有系统化的评估方法，Prompt 迭代就会退化为"凭感觉调参"，既无法复现也无法积累。


评估方法解决三个根本问题：


    

  1. 当前 Prompt 的绝对质量如何？ ——需要评分体系
    2. 

  2. 新版本是否比旧版本更好？ ——需要对比方法
    3. 

  3. 改进在统计上是否显著？ ——需要置信度分析
    4. 



人工评估方法
人工评估是 Prompt 评估的"金标准"，尤其适用于开放式生成任务。


盲评打分（Blind Rating）
评估者在不知道 Prompt 版本的情况下对输出打分，消除先入为主的偏见。


评估流程示例：

1. 准备 50 条测试输入
2. 用 Prompt A 和 Prompt B 分别生成 50 条输出
3. 将 100 条输出随机打乱，去除版本标识
4. 3 名评估者独立对每条输出打 1-5 分
5. 计算每个版本的平均分和评估者间一致性（Cohen's Kappa）
对比排序（Comparative Ranking）
让评估者直接比较两个输出，选择更好的一个。相比绝对打分，人类在相对比较上更加可靠。


对比排序模板：

输入：{用户问题}

输出 A：{Prompt A 的回复}
输出 B：{Prompt B 的回复}

请选择：
[ ] A 明显更好
[ ] A 略好
[ ] 差不多
[ ] B 略好
[ ] B 明显更好

判断依据（必填）：_______________
李克特量表（Likert Scale）评估
针对多个维度分别打分，适合需要细粒度反馈的场景。


评估维度与量表：

准确性：  1 - 2 - 3 - 4 - 5  （信息是否正确无误）
完整性：  1 - 2 - 3 - 4 - 5  （是否覆盖了关键信息）
简洁性：  1 - 2 - 3 - 4 - 5  （是否没有冗余内容）
语气适当：1 - 2 - 3 - 4 - 5  （是否符合场景要求）
可操作性：1 - 2 - 3 - 4 - 5  （用户是否能据此行动）

当评估规模扩大到数百或数千条时，自动化指标是唯一可行的方案。

代码生成指标：pass@k
对于代码生成类 Prompt，pass@k 衡量的是"生成 k 个候选中至少一个通过全部测试用例"的概率。


import numpy as np

def pass_at_k(n, c, k):
    """
    n: 总生成数量
    c: 通过测试的数量
    k: 取 top-k 个候选
    """
    if n - c < k:
        return 1.0
    return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))

print(f"pass@1:  {pass_at_k(200, 50, 1):.4f}")
print(f"pass@10: {pass_at_k(200, 50, 10):.4f}")
print(f"pass@100:{pass_at_k(200, 50, 100):.4f}")
LLM-as-Judge 评估模式
使用一个强大的 LLM（如 GPT-4）来评估另一个 LLM 的输出，是近年来最重要的评估范式创新。


基础评分模式
你是一个专业的文本质量评估专家。请根据以下评分标准对回复进行评分。

评分标准：
- 5分：完全准确，内容完整，表述专业
- 4分：基本准确，有minor遗漏，表述清晰
- 3分：部分准确，有明显遗漏或小错误
- 2分：多处错误，信息不完整
- 1分：严重错误或完全偏题

用户问题：
{question}

待评估回复：
{response}

请先分析回复的优缺点，然后给出 1-5 的评分。

输出格式：
分析：<你的分析>
评分：<1-5的整数>
对比评判模式
你是一个公正的评判者。请比较以下两个回复，判断哪个更好。

用户问题：
{question}

回复 A：
{response_a}

回复 B：
{response_b}

请从以下维度分别比较：
1. 准确性
2. 完整性
3. 表述质量
4. 实用性

然后给出最终判断。为了避免位置偏见，请忽略回复的呈现顺序。

输出格式：
维度分析：<逐维度比较>
最终判断：A更好 / B更好 / 平局
置信度：高 / 中 / 低
减少 LLM-as-Judge 偏见的策略




偏见类型
表现
缓解策略





位置偏见
倾向选择第一个或最后一个回复
随机交换 A/B 位置，取两次结果




冗长偏见
倾向选择更长的回复
在评分标准中明确"简洁优先"




自我偏见
倾向选择风格与自身相似的回复
使用不同模型交叉评判




格式偏见
倾向选择带 markdown 格式的回复
统一输出格式后再评判





评估数据集设计
高质量的评估数据集是整个评估体系的基石。


设计原则
    

  1. 代表性：覆盖生产环境中的真实分布，而非人为构造的理想输入
    2. 

  2. 多样性：包含简单、中等、困难三个层次，以及各类边界情况
    3. 

  3. 稳定性：评估集一旦确定，不应频繁修改（否则无法纵向对比）
    4. 

  4. 规模适当：通常 50-200 条即可支撑有统计意义的对比
    5. 



Golden Test Set 构建流程
第 1 步：从生产日志中随机抽样 500 条真实输入
第 2 步：人工筛选，去除重复和异常，保留 200 条
第 3 步：按难度和类别分层抽样，选出 100 条
第 4 步：3 名专家为每条输入编写"标准答案"
第 5 步：交叉审核标准答案，解决分歧
第 6 步：冻结数据集，记录版本号（如 eval-set-v1.2）

数据集结构：
eval-dataset/
├── metadata.json          # 版本号、创建日期、类别分布
├── inputs.jsonl           # 测试输入
├── golden_outputs.jsonl   # 标准答案
└── rubrics.jsonl          # 每条用例的评分标准

Rubric-Based 评估
基于评分准则（Rubric）的评估将主观判断转化为可操作的标准化流程。


评估准则示例 —— 客服回复质量

维度 1：问题识别（0-2分）
  0分：未能正确理解用户问题
  1分：部分理解用户问题，遗漏关键信息
  2分：完全理解用户问题，包括隐含需求

维度 2：解决方案（0-3分）
  0分：未提供任何解决方案
  1分：提供了方案但不可行或不相关
  2分：提供了可行方案但不是最优
  3分：提供了最优方案且步骤清晰

维度 3：沟通质量（0-2分）
  0分：语气不当或难以理解
  1分：语气适当但缺乏共情
  2分：语气专业、有共情、易于理解

总分范围：0-7分
合格线：5分及以上
统计显著性
在对比两个 Prompt 版本时，必须确认差异是否具有统计显著性，而非随机波动。


配对 t 检验示例
from scipy import stats

scores_a = [4, 3, 5, 4, 3, 5, 4, 4, 3, 5, 4, 3, 4, 5, 4, 3, 5, 4, 4, 3]
scores_b = [5, 4, 5, 5, 4, 5, 4, 5, 4, 5, 5, 4, 5, 5, 4, 4, 5, 5, 4, 4]

t_stat, p_value = stats.ttest_rel(scores_a, scores_b)

print(f"Prompt A 平均分: {sum(scores_a)/len(scores_a):.2f}")
print(f"Prompt B 平均分: {sum(scores_b)/len(scores_b):.2f}")
print(f"t 统计量: {t_stat:.4f}")
print(f"p 值: {p_value:.4f}")

if p_value < 0.05:
    print("结论：差异具有统计显著性（p < 0.05）")
else:
    print("结论：差异不显著，需要更多样本或更大改动")
样本量估算
效应量（Effect Size）与所需样本量的关系：

| 期望提升幅度 | Cohen's d | 所需样本量（α=0.05, power=0.8） |
|-------------|-----------|-------------------------------|
| 微小提升     | 0.2       | ~400 条                        |
| 中等提升     | 0.5       | ~65 条                         |
| 大幅提升     | 0.8       | ~26 条                         |

实践建议：
- 快速迭代阶段：50 条测试集，接受中等效应量
- 上线前验证：200+ 条测试集，要求 p < 0.01
- 关键场景：针对性测试集 + 人工复审

构建评估流水线
一个完整的评估流水线将上述所有方法串联成自动化工作流。


评估成本考量
成本估算示例（100 条测试集，对比 2 个 Prompt 版本）：

推理成本：
- 输入 tokens: ~500/条 × 100条 × 2版本 = 100,000 tokens
- 输出 tokens: ~300/条 × 100条 × 2版本 = 60,000 tokens
- GPT-4o 成本: ~$0.60

LLM-as-Judge 成本：
- 评判 tokens: ~800/条 × 200条 = 160,000 tokens
- GPT-4o 成本: ~$1.20

总成本: ~$1.80/次评估运行

优化策略：
- 日常迭代使用 GPT-4o-mini 评判（成本降低 10x）
- 仅在上线前使用 GPT-4o 做最终评估
- 缓存不变的推理结果，避免重复计算
最佳实践总结




原则
说明





先定义评估，再优化 Prompt
没有评估标准的优化是盲目的




混合使用多种评估方法
自动指标做初筛，LLM-as-Judge 做精评，人工做终审




保持评估集稳定
频繁更改评估集会导致历史数据失去可比性




记录每次评估的完整上下文
模型版本、温度参数、系统 Prompt 版本都要记录

平均 4.2 分的 Prompt 可能有 10% 的输出得 1 分

每次 Prompt 变更自动触发评估，阻止回退





小结
    

  • Prompt 评估是将主观的"感觉更好"转化为可量化、可复现的质量判断的系统方法。
    • 

  • 人工评估是金标准，适合开放式任务；盲评和对比排序可消除评估偏见。
    • 

  • 自动化指标（BLEU、ROUGE、BERTScore）适合大规模初筛，但无法完全替代人工判断。
    • 

  • LLM-as-Judge 是近年最重要的范式创新，需注意位置偏见、冗长偏见等系统性偏差。
    • 

  • 评估数据集是评估体系的基石，必须保持代表性、多样性和稳定性。
    • 

  • 对比两个版本时，必须通过统计显著性检验确认差异并非随机波动。
    • 

  • 完整的评估流水线应串联自动指标、LLM-as-Judge 和人工复审，并纳入 CI/CD。
    •
