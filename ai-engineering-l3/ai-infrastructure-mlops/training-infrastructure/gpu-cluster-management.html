GPU 集群管理

核心概念

GPU 集群是大规模模型训练的核心计算基础设施。与 CPU 集群不同，GPU 集群的管理面临独特挑战：GPU 资源昂贵（单块 H100 约 3 万美元）、GPU 之间的通信拓扑直接影响训练效率、显存管理需要精细化控制、硬件故障在大规模集群中不可避免。

高效的 GPU 集群管理需要在资源利用率、任务延迟和公平性之间找到平衡。

调度策略与资源分配
GPU 调度的核心挑战是如何将有限的 GPU 资源分配给多个竞争的训练任务，同时最大化整体利用率。Kubernetes 是当前 GPU 集群管理的事实标准，通过 NVIDIA Device Plugin 将 GPU 暴露为可调度资源。


基础的 GPU 调度使用 Kubernetes 的资源请求机制，每个 Pod 通过 nvidia.com/gpu: N 声明所需的 GPU 数量。但这种方式存在明显局限：无法感知 GPU 之间的物理拓扑，可能将需要高带宽通信的任务分配到跨交换机的 GPU 上，严重影响分布式训练的通信效率。


拓扑感知调度（Topology-Aware Scheduling）是解决这一问题的关键技术。它将集群中 GPU 的物理拓扑（同一节点内的 NVLink 连接、跨节点的 InfiniBand 网络）纳入调度决策，优先将通信密集的训练任务分配到拓扑距离最近的 GPU 上。Volcano 和 Kueue 是两个支持拓扑感知的 Kubernetes 调度器。


apiVersion: scheduling.volcano.sh/v1beta1
kind: PodGroup
metadata:
  name: llm-training-job
spec:
  minMember: 8
  queue: high-priority
  minResources:
    nvidia.com/gpu: '64'
---
apiVersion: batch.volcano.sh/v1alpha1
kind: Job
metadata:
  name: llm-training
spec:
  schedulerName: volcano
  plugins:
    sla: ['--max-wait=1h']
    gang: ['--min-available=8']
  tasks:
    - replicas: 8
      template:
        spec:
          containers:
            - name: trainer
              image: training:latest
              resources:
                limits:
                  nvidia.com/gpu: '8'
Gang 调度是分布式训练的必备能力。它确保一个训练任务的所有 Worker 要么同时启动，要么都不启动。如果只有部分 GPU 可用，任务会排队等待而不是部分启动，避免已启动的 Worker 空等其他 Worker 造成资源浪费。


多租户资源隔离
大型组织中多个团队共享 GPU 集群，需要建立完善的多租户资源隔离机制。资源隔离包含三个层面：配额管理、优先级控制和公平共享。


配额管理为每个团队设置 GPU 资源的上限（Hard Quota）和保底（Soft Quota）。Hard Quota 防止单个团队占用过多资源，Soft Quota 保证每个团队在需要时至少能获得一定量的 GPU。当集群整体利用率较低时，允许团队超出 Soft Quota 使用空闲资源，实现弹性共享。


优先级控制通过 Priority Class 为不同类型的任务设置优先级。生产模型的重训练任务通常设为高优先级，实验性的探索任务设为低优先级。当高优先级任务需要资源时，调度器可以抢占（Preempt）低优先级任务释放的 GPU。抢占时需要给被抢占的任务足够的时间保存检查点，避免训练进度丢失。


公平共享算法（如 Dominant Resource Fairness, DRF）确保在多维资源（GPU、CPU、内存）竞争时，每个团队获得公平的资源份额。DRF 的核心思想是比较每个团队已分配资源中占比最大的维度（Dominant Resource），优先服务 Dominant Resource 占比最小的团队。


显存管理与优化
GPU 显存是最稀缺的资源。一块 A100 只有 80GB 显存，而一个 70B 参数的模型仅权重就需要 140GB（FP16 精度）。显存管理的核心目标是在有限的显存中最大化训练吞吐量。


显存消耗的三大组成部分是模型参数、梯度和优化器状态、激活值。对于 Adam 优化器，每个参数需要额外 12 字节存储一阶矩和二阶矩。激活值在前向传播中产生，在反向传播中消耗，其大小与 batch size 和序列长度成正比。


梯度检查点（Gradient Checkpointing / Activation Recomputation）是节省激活值显存的核心技术。它只保存前向传播中关键层的激活值，在反向传播时重新计算中间层的激活值。这以增加约 30% 的计算时间为代价，可以将激活值的显存占用降低到原来的 1/√N（N 为网络层数）。


import torch
from torch.utils.checkpoint import checkpoint_sequential

class LargeModel(torch.nn.Module):
    def __init__(self, num_layers=48):
        super().__init__()
        self.layers = torch.nn.ModuleList([
            TransformerBlock(hidden_size=4096)
            for _ in range(num_layers)
        ])
        self.checkpoint_segments = 8

    def forward(self, x):
        return checkpoint_sequential(
            self.layers,
            self.checkpoint_segments,
            x,
            use_reentrant=False,
        )
显存碎片化是长时间训练中常见的问题。频繁的显存分配和释放导致显存中出现大量不连续的小块空闲区域，即使总空闲显存足够，也无法分配大块连续空间。PyTorch 的 CUDA 缓存分配器通过 block 池化机制缓解了这一问题，但在极端情况下仍需定期调用 torch.cuda.empty_cache() 主动释放缓存。


故障检测与自动恢复
大规模 GPU 集群中硬件故障是常态而非异常。一个包含 1000 块 GPU 的集群，每天至少会遇到 1-2 次硬件故障（GPU 掉卡、ECC 错误、NVLink 断链、InfiniBand 超时）。训练任务需要在故障面前保持弹性。


故障检测分为主动检测和被动检测两种模式。主动检测通过 NVIDIA DCGM（Data Center GPU Manager）定期采集 GPU 健康状态指标，包括温度、功耗、ECC 错误计数、NVLink 带宽等，当指标超过阈值时提前标记 GPU 为不健康状态。被动检测通过监控训练进程的心跳信号和 NCCL 通信超时来发现运行时故障。


自动恢复的核心机制是检查点恢复。训练过程定期保存检查点（模型权重 + 优化器状态 + 学习率调度器状态 + 随机数种子），当故障发生时，调度系统自动在健康的 GPU 上重启训练任务并从最近的检查点恢复。

弹性训练（Elastic Training）是更高级的容错方案。它允许训练任务在部分 Worker 故障时自动缩减规模继续训练，并在新的 GPU 可用时自动扩展规模。PyTorch Elastic（TorchElastic）和 Horovod Elastic 提供了这一能力，但实现弹性训练需要仔细处理学习率调整和梯度累积策略的适配。


小结
    

  • GPU 集群管理的核心挑战是在利用率、延迟和公平性之间找到平衡
    • 

  • 拓扑感知调度和 Gang 调度是分布式训练场景下的必备能力
    • 

  • 多租户资源隔离需要配额、优先级和公平共享三层机制协同工作
    • 

  • 显存管理是 GPU 训练的关键瓶颈，梯度检查点是最常用的优化手段
    • 

  • 大规模集群必须建立完善的故障检测和自动恢复机制，检查点是容错的基石
