批量与实时推理

核心概念

ML 推理服务按时效性要求分为两种基本范式：实时推理（Real-Time Inference）和批量推理（Batch Inference）。实时推理在请求到达时立即处理并返回结果，延迟通常要求在毫秒到秒级；批量推理对大量数据进行离线处理，关注的是吞吐量而非单请求延迟。两种范式在架构设计、资源规划和成本模型上有本质差异。

选择推理范式需要综合考虑业务需求、延迟要求和成本预算。

实时推理架构设计
实时推理的核心挑战是在严格的延迟 SLA（如 P99 < 100ms）下最大化吞吐量。这需要从请求处理流程的每个环节进行优化：请求解析、特征获取、模型推理和结果后处理。


动态批处理（Dynamic Batching）是提升实时推理吞吐量的关键技术。当多个请求在短时间内到达时，将它们组装为一个 batch 一次性送入模型推理，batch 内的请求共享 GPU 计算资源。batch 大小需要在吞吐量和延迟之间权衡——batch 越大吞吐量越高，但等待凑 batch 的时间也越长。


import asyncio
from collections import deque

class DynamicBatcher:
    def __init__(self, model, max_batch_size=32, max_wait_ms=10):
        self.model = model
        self.max_batch_size = max_batch_size
        self.max_wait_ms = max_wait_ms
        self.queue = deque()
        self.running = True

    async def predict(self, input_data):
        future = asyncio.get_event_loop().create_future()
        self.queue.append((input_data, future))
        return await future

    async def batch_loop(self):
        while self.running:
            if not self.queue:
                await asyncio.sleep(0.001)
                continue

            batch_inputs = []
            batch_futures = []

            deadline = asyncio.get_event_loop().time() + self.max_wait_ms / 1000

            while len(batch_inputs) < self.max_batch_size:
                if not self.queue:
                    remaining = deadline - asyncio.get_event_loop().time()
                    if remaining <= 0:
                        break
                    await asyncio.sleep(min(remaining, 0.001))
                    continue
                inp, fut = self.queue.popleft()
                batch_inputs.append(inp)
                batch_futures.append(fut)

            if batch_inputs:
                results = self.model.batch_predict(batch_inputs)
                for fut, result in zip(batch_futures, results):
                    fut.set_result(result)
请求优先级管理是实时推理的进阶优化。不同来源或不同用户等级的请求可以设置不同的优先级，高优先级请求跳过普通队列优先处理。这在付费用户和免费用户共享推理资源的场景中尤为重要。


批量推理架构设计
批量推理的核心目标是在给定的计算预算和时间窗口内处理尽可能多的数据。与实时推理不同，批量推理可以充分利用大 batch size、数据预排序和资源动态分配等策略来最大化 GPU 利用率。


大 batch size 是批量推理效率的关键。不受延迟约束时，可以将 batch size 提升到 GPU 显存允许的最大值，使每个 GPU 周期处理更多样本。对于变长输入（如 NLP 文本），按长度分桶（Bucketing）——将相似长度的输入组成一个 batch——可以显著减少 Padding 浪费。


import torch
from torch.utils.data import DataLoader

class BatchInferencePipeline:
    def __init__(self, model, batch_size=256, num_workers=4):
        self.model = model.eval()
        self.batch_size = batch_size
        self.num_workers = num_workers

    def run(self, dataset, output_path):
        dataloader = DataLoader(
            dataset,
            batch_size=self.batch_size,
            num_workers=self.num_workers,
            pin_memory=True,
            collate_fn=self.bucket_collate,
        )

        all_results = []
        with torch.no_grad(), torch.cuda.amp.autocast():
            for batch in dataloader:
                batch = {k: v.cuda(non_blocking=True) for k, v in batch.items()}
                outputs = self.model(**batch)
                all_results.extend(outputs.cpu().tolist())

        self.save_results(all_results, output_path)

    def bucket_collate(self, samples):
        samples.sort(key=lambda x: len(x["input_ids"]), reverse=True)
        return default_collate(samples)

混合推理架构
实际业务中，同一个模型往往同时需要实时和批量两种推理能力。例如，推荐系统需要实时推理为当前请求生成推荐结果，同时需要批量推理为全量用户预计算候选集。


混合架构的核心设计是资源隔离与共享的平衡。实时推理和批量推理使用不同的 GPU 资源池，避免批量任务抢占实时任务的 GPU 导致延迟飙升。但在实时流量低谷时，批量任务可以临时使用空闲的实时推理 GPU，提高整体资源利用率。


Lambda Architecture 是一种经典的混合架构模式。批处理层（Batch Layer）定期对全量数据运行批量推理，生成基础预测结果存入结果库。速度层（Speed Layer）对增量数据运行实时推理，生成最新的预测更新。服务层（Serving Layer）合并批处理结果和实时更新，提供最终的查询服务。这种架构既保证了全量数据的处理完整性，又提供了最新数据的实时性。


预计算与实时推理的混合策略在推荐系统中尤为常见。离线批量推理预先为每个用户计算候选集（如 top-1000 候选商品），存入 Redis 等高速缓存。实时推理在用户请求到来时，从缓存读取候选集，结合用户实时行为特征进行精排，返回最终推荐结果。


成本与性能权衡
不同推理范式的成本结构差异显著。实时推理需要常驻 GPU 实例以保证低延迟响应，即使在低流量时段也需要维持一定的实例数；批量推理可以使用竞价实例（Spot Instances）大幅降低成本，因为任务可以容忍中断和重试。


推理成本优化的核心策略包括：模型量化降低每次推理的计算成本、动态批处理提升 GPU 利用率、自动扩缩容匹配流量波动、竞价实例用于批量任务和非关键的实时任务。

  • 动态批处理是实时推理提升吞吐量的核心技术，分桶策略是批量推理减少浪费的关键
