Harness 架构

核心概念

ML Harness 是封装和管理机器学习工作流的工程框架。"Harness"（线束/框架）的含义是为 ML 系统的各个组件提供统一的连接和控制界面，就像汽车线束将电子元件连接为一个整体。一个设计良好的 Harness 架构使团队能够以标准化、可扩展的方式开发、测试和部署 ML 模型。

Harness 架构的核心设计目标是将 ML 工作流的"变化部分"（模型架构、数据处理逻辑）与"稳定部分"（编排、监控、容错）分离。

插件化架构设计
插件化是 Harness 架构的灵魂。ML 工作流中的每个环节（数据加载、模型定义、训练循环、评估指标、部署目标）都抽象为插件接口，用户通过实现接口来定制行为，框架负责插件的发现、加载和生命周期管理。


插件接口的设计需要在灵活性和简洁性之间找到平衡。过于简单的接口无法覆盖复杂场景，过于复杂的接口降低了易用性。PyTorch Lightning 的 Callback 系统是优秀的插件设计范例——它在训练循环的每个关键节点（epoch 开始/结束、batch 开始/结束、验证阶段等）提供钩子，用户通过继承 Callback 基类并重写特定钩子方法来注入自定义逻辑。


from abc import ABC, abstractmethod
from typing import Any

class DataPlugin(ABC):
    @abstractmethod
    def load_train_data(self, config: dict) -> Any:
        pass

    @abstractmethod
    def load_eval_data(self, config: dict) -> Any:
        pass

class ModelPlugin(ABC):
    @abstractmethod
    def create_model(self, config: dict) -> Any:
        pass

    @abstractmethod
    def create_optimizer(self, model: Any, config: dict) -> Any:
        pass

class TrainerPlugin(ABC):
    @abstractmethod
    def train_step(self, model: Any, batch: Any) -> dict:
        pass

    @abstractmethod
    def eval_step(self, model: Any, batch: Any) -> dict:
        pass

class PluginRegistry:
    _plugins: dict = {}

    @classmethod
    def register(cls, name: str, plugin_cls: type):
        cls._plugins[name] = plugin_cls

    @classmethod
    def get(cls, name: str) -> type:
        return cls._plugins[name]
插件发现机制通常基于 Python 的 Entry Points（setuptools）或约定式的目录扫描。用户将自定义插件打包为 Python 包，通过 entry_points 注册到 Harness 框架，框架在启动时自动扫描并加载所有注册的插件。这种机制使得第三方可以开发和分享插件，形成生态系统。


Pipeline 抽象与 DAG 执行
Harness 将 ML 工作流抽象为 Pipeline——由多个 Step 组成的有向无环图。每个 Step 封装一个原子操作（数据加载、特征工程、训练、评估等），Step 之间通过 Artifact（数据产物）连接。


Pipeline 的执行引擎负责解析 DAG 依赖关系、调度 Step 执行、管理 Artifact 传递和处理错误恢复。执行模式包括本地顺序执行（开发调试）、本地并行执行（利用多核 CPU）和分布式执行（提交到 Kubernetes 集群）。


from dataclasses import dataclass

@dataclass
class StepConfig:
    name: str
    plugin: str
    inputs: list[str]
    outputs: list[str]
    params: dict

@dataclass
class PipelineConfig:
    name: str
    steps: list[StepConfig]

class PipelineEngine:
    def __init__(self, config: PipelineConfig, registry: PluginRegistry):
        self.config = config
        self.registry = registry
        self.artifacts = {}

    def run(self):
        execution_order = self._topological_sort()
        for step_config in execution_order:
            plugin = self.registry.get(step_config.plugin)()
            inputs = {name: self.artifacts[name] for name in step_config.inputs}
            outputs = plugin.execute(inputs, step_config.params)
            for name, artifact in zip(step_config.outputs, outputs):
                self.artifacts[name] = artifact

    def _topological_sort(self):
        visited = set()
        order = []
        for step in self.config.steps:
            self._dfs(step, visited, order)
        return order
配置即代码（Configuration as Code）是 Pipeline 定义的核心原则。Pipeline 的结构、参数和执行策略都通过 YAML 或 Python 配置文件声明，存储在版本控制系统中，确保每次实验都可以精确复现。


扩展机制与自定义 Hook
除了插件系统，Harness 还需要提供细粒度的扩展机制，让用户在不修改框架代码的情况下注入自定义逻辑。Hook（钩子）和 Callback（回调）是两种主要的扩展模式。


Hook 系统在框架的关键执行点预留了扩展接口。例如训练循环中的 on_train_begin、on_batch_start、on_batch_end、on_epoch_end 等。用户注册的 Hook 函数在对应时机被调用，可以执行指标记录、学习率调整、早停检查、检查点保存等横切关注点。


class HookManager:
    def __init__(self):
        self.hooks: dict[str, list] = {}

    def register(self, event: str, callback):
        self.hooks.setdefault(event, []).append(callback)

    def trigger(self, event: str, **kwargs):
        for callback in self.hooks.get(event, []):
            callback(**kwargs)

class EarlyStoppingHook:
    def __init__(self, patience=5, min_delta=0.001):
        self.patience = patience
        self.min_delta = min_delta
        self.best_score = None
        self.counter = 0

    def on_epoch_end(self, metrics, trainer):
        score = metrics.get("val_loss", float("inf"))
        if self.best_score is None or score < self.best_score - self.min_delta:
            self.best_score = score
            self.counter = 0
        else:
            self.counter += 1
            if self.counter >= self.patience:
                trainer.stop_training = True
Mixin 模式是另一种灵活的扩展方式。通过多重继承，用户可以将多个功能模块（如分布式训练能力、混合精度训练能力、梯度累积能力）组合到训练器中，而无需修改基类代码。

多环境运行时
Harness 架构需要支持在不同环境中运行同一个 Pipeline：开发者本地机器、CI/CD 服务器、GPU 训练集群和生产推理环境。运行时抽象层屏蔽了不同环境的差异，让 Pipeline 代码无需修改即可在任何环境中执行。


运行时抽象的核心接口包括：资源申请（CPU/GPU/内存）、Artifact 存储（本地文件/S3/GCS）、日志和指标输出（标准输出/MLflow/W&B）、Secret 管理（环境变量/Vault）。每个运行时实现这些接口，Pipeline 代码只依赖抽象接口而非具体实现。


Hydra 和 OmegaConf 是配置管理的常用工具，它们支持配置的层次化组合、命令行覆盖和环境变量插值。通过配置组合，同一个 Pipeline 可以用不同的配置运行在不同环境中。


小结
    

  • Harness 架构将 ML 工作流的变化部分与稳定部分分离，通过插件化实现灵活扩展
    • 

  • Pipeline 抽象将 ML 工作流组织为 DAG，配置即代码保证了实验的可复现性
    • 

  • Hook/Callback 系统提供了细粒度的扩展能力，是注入横切关注点的标准模式
    • 

  • 多环境运行时抽象使 Pipeline 可以无修改地在开发到生产的各个环境中运行
    • 

  • 好的 Harness 设计是 ML 团队工程效率的倍增器
    •
