可观测性与监控

核心概念

ML 系统的可观测性（Observability）是通过外部输出（指标、日志、追踪）来理解系统内部状态的能力。与传统软件系统不同，ML 系统的"正确性"不仅取决于代码逻辑，还取决于数据质量和模型行为——这两者都会随时间变化。因此，ML 可观测性需要在传统的系统监控之上，增加数据监控和模型监控两个维度。

三个层面的监控形成了 ML 系统可观测性的完整图景。

数据漂移检测
数据漂移（Data Drift）是指生产环境中的数据分布相比训练数据发生了变化。数据漂移是模型性能退化最常见的根因，因为模型在训练数据分布上学习的模式可能在新分布上不再适用。


数据漂移分为三种类型：协变量漂移（Covariate Drift，输入特征分布变化）、先验概率漂移（Prior Probability Drift，标签分布变化）和概念漂移（Concept Drift，输入与输出之间的关系变化）。三种漂移的检测方法和应对策略各不相同。


统计检验是检测协变量漂移的标准方法。对于数值特征，可以使用 KS 检验（Kolmogorov-Smirnov Test）比较两个分布的差异，或计算 PSI（Population Stability Index）量化分布偏移程度。对于类别特征，可以使用卡方检验（Chi-Square Test）。


from scipy import stats
import numpy as np

class DriftDetector:
    def __init__(self, reference_data, threshold=0.05):
        self.reference = reference_data
        self.threshold = threshold

    def detect_drift(self, production_data):
        drift_report = {}
        for feature in self.reference.columns:
            ref_values = self.reference[feature].dropna()
            prod_values = production_data[feature].dropna()

            if ref_values.dtype in [np.float64, np.int64]:
                statistic, p_value = stats.ks_2samp(ref_values, prod_values)
                psi = self._calculate_psi(ref_values, prod_values)
                drift_report[feature] = {
                    "ks_statistic": statistic,
                    "p_value": p_value,
                    "psi": psi,
                    "drifted": p_value < self.threshold or psi > 0.2,
                }
        return drift_report

    def _calculate_psi(self, reference, production, bins=10):
        ref_hist, edges = np.histogram(reference, bins=bins)
        prod_hist, _ = np.histogram(production, bins=edges)
        ref_pct = ref_hist / len(reference) + 1e-6
        prod_pct = prod_hist / len(production) + 1e-6
        psi = np.sum((prod_pct - ref_pct) * np.log(prod_pct / ref_pct))
        return psi

模型性能退化监控
模型性能退化（Model Degradation）是指模型在生产环境中的预测质量随时间下降。退化的原因可能是数据漂移、数据质量问题、上游系统变更或业务环境变化。


直接的性能监控需要真实标签（Ground Truth），但在很多场景中标签获取有延迟。例如，推荐系统的点击标签在推荐展示后立即可得，但电商的购买标签可能在数天后才能确认。因此，需要设计代理指标（Proxy Metrics）来提前发现退化趋势。


常用的代理指标包括：预测分布漂移（模型输出的概率分布与历史模式的偏差）、预测置信度分布（平均置信度显著下降可能暗示模型困惑）、特征重要性变化（特征对预测的贡献度与训练时不一致）和预测一致性（相似输入产生不一致的预测结果）。


class ModelMonitor:
    def __init__(self, baseline_predictions):
        self.baseline = baseline_predictions
        self.metrics_history = []

    def check_prediction_drift(self, current_predictions):
        baseline_dist = np.histogram(self.baseline, bins=50, density=True)[0]
        current_dist = np.histogram(current_predictions, bins=50, density=True)[0]

        kl_divergence = stats.entropy(current_dist + 1e-10, baseline_dist + 1e-10)
        js_divergence = self._jensen_shannon(baseline_dist, current_dist)

        return {
            "kl_divergence": kl_divergence,
            "js_divergence": js_divergence,
            "mean_shift": np.mean(current_predictions) - np.mean(self.baseline),
            "std_shift": np.std(current_predictions) - np.std(self.baseline),
        }

    def check_confidence_distribution(self, confidences):
        avg_confidence = np.mean(confidences)
        low_confidence_ratio = np.mean(confidences < 0.5)
        return {
            "avg_confidence": avg_confidence,
            "low_confidence_ratio": low_confidence_ratio,
            "alert": low_confidence_ratio > 0.3,
        }

分布式追踪与日志管理
ML 系统的请求链路通常跨越多个服务：API 网关 → 特征服务 → 模型推理 → 后处理 → 响应返回。分布式追踪（Distributed Tracing）通过在整个链路中传递唯一的 Trace ID 和 Span ID，将分散在不同服务中的日志和指标关联为一条完整的调用链。


OpenTelemetry 是分布式追踪的开放标准，它提供了统一的 API 来生成 Trace、Metric 和 Log 数据，支持导出到 Jaeger、Zipkin、Prometheus 等多种后端。对于 ML 服务，需要在追踪中记录推理相关的元数据：使用的模型版本、输入特征的摘要、推理延迟的分解（预处理时间 + 推理时间 + 后处理时间）。


from opentelemetry import trace

tracer = trace.get_tracer("ml-inference-service")

async def predict_endpoint(request):
    with tracer.start_as_current_span("predict") as span:
        span.set_attribute("model.name", request.model_name)
        span.set_attribute("model.version", request.model_version)

        with tracer.start_as_current_span("feature_retrieval"):
            features = await get_features(request)
            span.set_attribute("features.count", len(features))

        with tracer.start_as_current_span("model_inference"):
            result = await run_inference(features)
            span.set_attribute("inference.latency_ms", result.latency_ms)
            span.set_attribute("prediction.confidence", result.confidence)

        return result

告警体系与自动响应
告警体系是可观测性的最后一环，它将监控数据转化为可操作的通知和自动化响应。ML 系统的告警设计需要特别注意告警疲劳——过多的低优先级告警会导致团队忽视真正重要的告警。


告警分级是应对告警疲劳的核心策略。P0 告警（服务不可用、严重数据泄漏）需要立即响应，通过电话和 PagerDuty 通知值班人员。P1 告警（模型性能显著退化、资源瓶颈）在工作时间内处理，通过 Slack 通知团队。P2 告警（轻微漂移、非关键指标波动）在周报中审视，通过邮件通知。


自动响应（Auto-Remediation）减少了人工干预的需求。常见的自动响应包括：推理延迟超标时自动扩容、模型错误率飙升时自动回滚到上一版本、数据漂移检测到异常时自动触发重训练流水线、GPU 内存泄漏时自动重启推理服务。
