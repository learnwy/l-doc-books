生命周期管理

核心概念

模型生命周期管理（Model Lifecycle Management）是对 ML 模型从创建到退役的完整过程进行系统化管控的工程实践。它确保每个模型在任何时刻都有明确的状态、清晰的责任人和可追溯的变更历史。在企业级 ML 系统中，同时运行着数十甚至数百个模型，没有系统化的生命周期管理，模型治理将陷入混乱。

模型生命周期的每个阶段都有明确的准入和准出条件。

模型注册与版本控制
模型注册表（Model Registry）是生命周期管理的中枢系统。它存储每个模型版本的权重文件、元数据、血缘信息和阶段状态，提供统一的查询和管理接口。


模型版本控制需要处理三个层面的版本：模型架构版本（网络结构变更）、训练数据版本（数据集更新）和权重版本（同一架构在不同数据或参数下训练的产物）。MLflow Model Registry 使用"Model Name + Version Number"的二级命名空间，每个 Model Name 下可以有多个 Version，每个 Version 标记为 None、Staging、Production 或 Archived 状态。


from mlflow import MlflowClient

client = MlflowClient()

client.create_registered_model(
    "recommendation-ranker",
    description="推荐系统精排模型",
    tags={"team": "rec-engine", "business": "e-commerce"},
)

model_version = client.create_model_version(
    name="recommendation-ranker",
    source="s3://models/ranker-v5/",
    run_id="exp_run_abc123",
    description="新增用户行为序列特征",
    tags={
        "training_data_version": "2024-03-15",
        "framework": "pytorch",
        "metrics.ndcg@10": "0.482",
    },
)
模型血缘（Model Lineage）记录了模型的完整来源信息：训练使用的数据集版本、代码提交的 Git SHA、超参数快照、依赖环境和父模型（如果是微调产物）。当生产模型出现问题时，血缘信息是排查根因的关键线索。


审批与晋级策略
从 Staging 到 Production 的晋级是模型生命周期中最关键的控制点。这个环节需要自动化检查与人工审批相结合，确保只有质量合格、安全可靠的模型才能进入生产环境。


自动化门控（Automated Gates）在晋级前自动运行一系列检查，包括性能门控（核心指标不低于当前生产模型）、延迟门控（P99 延迟在 SLA 范围内）、资源门控（内存/GPU 占用在预算内）、安全门控（对抗样本鲁棒性测试通过）和公平性门控（在不同用户群体上表现无显著偏差）。


class PromotionGate:
    def __init__(self, production_model, candidate_model):
        self.production = production_model
        self.candidate = candidate_model
        self.gates = []

    def add_gate(self, gate_fn, name, threshold):
        self.gates.append((gate_fn, name, threshold))

    def evaluate(self, eval_data):
        results = []
        for gate_fn, name, threshold in self.gates:
            prod_score = gate_fn(self.production, eval_data)
            cand_score = gate_fn(self.candidate, eval_data)
            passed = cand_score >= threshold
            results.append({
                "gate": name,
                "production_score": prod_score,
                "candidate_score": cand_score,
                "threshold": threshold,
                "passed": passed,
            })
        return results

    def should_promote(self, eval_data):
        results = self.evaluate(eval_data)
        return all(r["passed"] for r in results)
人工审批环节评估自动化检查无法覆盖的维度：业务影响评估（新模型对用户体验的预期影响）、发布时机评估（是否在业务低峰期发布）、回滚计划确认（回滚操作已准备就绪）和合规审查（是否满足数据保护和行业法规要求）。


灰度发布与回滚机制
模型上线后的灰度发布策略决定了新模型接收流量的方式和速度。渐进式灰度（Progressive Rollout）按时间或流量比例逐步增加新模型的服务范围：5% → 25% → 50% → 100%。每个阶段都设有自动回滚触发条件——当监控指标超出预设阈值时，系统自动将流量切回旧模型。


回滚机制的设计需要考虑速度和完整性。即时回滚（Hot Rollback）在流量路由层切换，不需要重新部署模型，可以在秒级完成。冷回滚（Cold Rollback）需要重新加载旧版本模型，可能需要数分钟。对于关键业务，建议始终保持上一个生产版本的模型实例处于热备状态，确保即时回滚能力。

模型退役与归档
模型退役是生命周期中经常被忽视但非常重要的环节。长期运行但不再被使用的模型浪费计算资源，过时的模型可能产生低质量的预测结果，未清理的模型增加了系统的维护负担和安全攻击面。


退役前的影响分析是必要步骤。需要确认：哪些下游服务依赖该模型、退役后是否有替代方案、历史预测结果是否需要保留（审计要求）。退役后的模型应归档到低成本存储中，保留元数据和血缘信息以满足审计和合规需求，但释放 GPU 和高速存储资源。


退役策略可以是即时下线（停止服务后删除实例）、渐进退役（逐步将流量迁移到新模型）或冻结保留（停止接受新请求但保留历史数据查询能力）。选择哪种策略取决于业务连续性要求和合规规定。


小结
    

  • 模型生命周期管理确保每个模型在任何时刻都有明确的状态和责任人
    • 

  • 模型注册表是生命周期管理的中枢，血缘追踪是问题排查和合规审计的基础
    • 

  • 晋级流程需要自动化门控与人工审批相结合，确保生产环境的质量和安全
    • 

  • 灰度发布配合自动回滚机制是模型上线的标准实践，关键业务需保持热备回滚能力
    • 

  • 模型退役是经常被忽视但同样重要的环节，需要系统化的影响分析和归档流程
