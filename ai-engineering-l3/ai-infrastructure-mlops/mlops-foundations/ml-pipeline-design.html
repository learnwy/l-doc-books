ML 流水线设计

核心概念

ML 流水线（Pipeline）是将数据处理、特征工程、模型训练、评估和部署等步骤组织为可复现、可编排的有向无环图（DAG）的工程实践。流水线设计的核心目标是将手动的、不可靠的 ML 工作流转化为自动化的、可审计的生产系统。

一个设计良好的 ML 流水线不仅仅是脚本的串联执行，它需要具备数据血缘追踪、缓存复用、失败重试、并行调度和版本快照等能力。

DAG 编排与依赖管理
ML 流水线的核心抽象是有向无环图（DAG），图中的节点代表计算步骤，边代表数据依赖关系。DAG 编排引擎负责按依赖顺序调度步骤、管理并行执行和处理失败恢复。


Apache Airflow 是最成熟的通用 DAG 编排工具，通过 Python 代码定义 DAG 和 Operator。但 Airflow 最初为 ETL 场景设计，在 ML 场景下存在一些不足：缺少原生的数据传递机制（XCom 限制大小）、不支持动态 DAG 生成、缺乏 ML 特定功能。


Kubeflow Pipelines 是专为 ML 设计的编排系统，运行在 Kubernetes 上，每个步骤是一个容器。它提供了原生的 Artifact 传递、实验追踪和流水线版本管理功能。其 Python SDK 允许用装饰器定义组件，并通过 DSL 组合为流水线。


from kfp import dsl

@dsl.component(base_image="python:3.11")
def preprocess(input_path: str, output_path: dsl.Output[dsl.Dataset]):
    import pandas as pd
    df = pd.read_csv(input_path)
    df = df.dropna()
    df.to_parquet(output_path.path)

@dsl.component(base_image="pytorch/pytorch:2.1.0-cuda12.1-cudnn8-runtime")
def train(dataset: dsl.Input[dsl.Dataset], model: dsl.Output[dsl.Model]):
    import torch
    data = load_data(dataset.path)
    trained_model = train_model(data)
    torch.save(trained_model, model.path)

@dsl.pipeline(name="training-pipeline")
def ml_pipeline(data_path: str):
    prep_task = preprocess(input_path=data_path)
    train_task = train(dataset=prep_task.outputs["output_path"])
Prefect 和 Dagster 是新一代编排框架，在开发体验上有显著提升。Prefect 采用"函数即任务"的设计理念，通过装饰器将普通 Python 函数转化为流水线步骤，开发体验接近本地代码。Dagster 引入了 Software-Defined Assets 的概念，将流水线的焦点从"做什么"转向"产出什么"，更符合数据工程的思维模式。


步骤容器化与环境隔离
生产级 ML 流水线的每个步骤都应该在隔离的容器环境中运行，这样做有三个关键好处：依赖隔离（不同步骤可以使用不同版本的库）、可复现性（容器镜像固定了执行环境）和资源控制（可以为每个步骤分配不同的 CPU/GPU 资源）。


容器化的核心挑战在于镜像管理。ML 团队往往需要维护多个基础镜像：CPU 基础镜像（用于数据处理步骤）、GPU 训练镜像（包含 CUDA 和深度学习框架）和推理镜像（轻量级，仅包含推理依赖）。这些镜像需要建立分层构建策略，通过共享基础层来减少构建时间和存储成本。


# 多阶段构建示例：训练镜像
FROM nvidia/cuda:12.1-devel AS builder
RUN pip install --no-cache-dir torch==2.1.0 transformers==4.35.0

FROM nvidia/cuda:12.1-runtime AS runtime
COPY --from=builder /usr/local/lib/python3.11/site-packages /usr/local/lib/python3.11/site-packages
COPY src/ /app/src/
WORKDIR /app
ENTRYPOINT ["python", "-m", "src.train"]
环境隔离还需要处理数据传递问题。步骤之间的中间数据（Artifact）需要通过共享存储传递，常见方案包括 NFS 挂载、对象存储（S3/GCS）和分布式缓存。选择方案时需要权衡数据大小、访问延迟和成本。


缓存策略与增量计算
在大规模 ML 流水线中，缓存策略可以将迭代速度提升一个数量级。核心思想是：如果某个步骤的输入（代码 + 数据 + 参数）没有变化，就直接复用之前的输出。


输入哈希是缓存匹配的关键。每个步骤的缓存键由以下元素组合生成：步骤代码的哈希、输入数据的哈希、配置参数的哈希和基础镜像版本。当缓存命中时，引擎跳过该步骤直接使用缓存结果，并继续执行后续步骤。


增量计算是缓存的进阶形态。对于数据处理步骤，如果输入数据集新增了 1% 的数据，完全重新处理效率极低。增量计算框架（如 Hamilton、Feast）可以检测数据变更范围，只对变更部分执行计算，再与历史结果合并。


缓存失效策略同样重要。过于激进的缓存可能导致使用过期数据训练模型，因此需要设置合理的 TTL（存活时间）和强制刷新机制。对于训练数据处理步骤，建议按天设置缓存失效；对于特征计算步骤，可以按周或按月。


流水线测试与持续集成
ML 流水线的测试分为三个层次：单步骤测试、集成测试和端到端测试。


单步骤测试验证每个处理步骤在给定输入下产生正确输出。对于数据处理步骤，测试应检查输出数据的 Schema、统计分布和边界条件；对于训练步骤，测试应验证模型能在小数据集上收敛、输出格式正确且性能指标在预期范围内。


集成测试验证步骤之间的数据传递正确性。ML 系统中最常见的集成问题是训练-推理偏差（Training-Serving Skew）：训练流水线中的特征处理逻辑与推理服务中的特征处理逻辑不一致，导致模型在生产环境中表现与离线评估差异巨大。


def test_training_serving_consistency():
    raw_input = load_test_data("sample_request.json")

    training_features = training_pipeline.transform(raw_input)
    serving_features = serving_pipeline.transform(raw_input)

    assert_features_equal(training_features, serving_features, tolerance=1e-6)

def test_pipeline_end_to_end():
    small_dataset = load_test_data("mini_dataset.parquet")

    result = pipeline.run(
        data=small_dataset,
        config={"epochs": 2, "batch_size": 8}

    assert result.model is not None

端到端测试在 CI 中运行完整的流水线（使用小规模数据和少量训练轮次），验证从数据摄取到模型产出的全流程无错误。这类测试通常运行时间较长（分钟级），建议放在 PR 合并前的必要检查中。

小结
    

  • ML 流水线将 ML 工作流组织为可复现的 DAG，是 MLOps 工程化的核心基础设施
    • 

  • 编排框架的选择取决于团队规模和技术栈，Kubeflow 适合 K8s 原生团队，Prefect/Dagster 适合追求开发体验的团队
    • 

  • 每个步骤应容器化运行以保证环境隔离和可复现性，镜像管理需要分层构建策略
    • 

  • 缓存和增量计算可以将流水线迭代速度提升一个数量级，但需要合理的失效策略
    • 

  • 流水线测试的重中之重是训练-推理一致性验证，这是避免生产事故的关键防线
    •
