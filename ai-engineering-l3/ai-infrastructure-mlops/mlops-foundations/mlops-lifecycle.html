MLOps 生命周期

核心概念

MLOps 生命周期定义了机器学习系统从数据准备到模型退役的完整流程。与传统软件开发的线性发布流程不同，ML 系统需要同时管理代码、数据和模型三个维度的变更，形成了独特的持续训练（CT）、持续集成（CI）和持续部署（CD）三环联动体系。

理解 MLOps 生命周期的关键在于认识到它不是一次性的流水线，而是一个需要持续迭代的闭环系统。每个环节都有其特有的工程挑战和最佳实践。

成熟度模型与演进路径
Google 在其 MLOps 白皮书中定义了三个成熟度级别，清晰刻画了组织在 ML 工程化道路上的演进阶段。Level 0 是手动流程阶段，数据科学家在 Notebook 中完成所有工作，模型部署依赖手动操作，没有持续训练的概念。Level 1 引入了 ML 流水线自动化，实现了持续训练能力，数据和模型的流转通过编排系统管理。Level 2 是完整的 CI/CD/CT 体系，代码变更触发自动构建和测试，数据变更触发自动重训练，模型性能退化触发自动告警和回滚。


从 Level 0 到 Level 2 的演进不是一蹴而就的。大多数团队应该先聚焦 Level 1 的核心能力：可复现的训练流水线和自动化的模型评估。在这个基础上，再逐步引入 CI/CD 管道和监控体系。过早追求完整自动化往往导致系统复杂度失控，反而降低团队效率。


实践中，成熟度提升的关键瓶颈往往不是技术能力，而是组织协作。ML 团队需要与数据工程、平台工程和业务团队紧密配合，建立清晰的职责边界和协作流程。


持续训练闭环
持续训练（Continuous Training, CT）是 MLOps 区别于传统 DevOps 的核心特征。在传统软件中，部署后的应用行为是确定性的；但 ML 模型的性能会随数据分布变化而退化，因此必须建立自动化的重训练机制。


CT 闭环的核心组件包括数据漂移检测器、触发策略引擎、训练流水线和模型评估网关。数据漂移检测器持续比较生产数据与训练数据的统计分布，当检测到显著漂移时触发重训练。触发策略可以是基于时间的定期触发、基于数据量的阈值触发，或基于模型性能指标的退化触发。


重训练流程不是简单地重新运行训练脚本。生产级的 CT 系统需要处理数据版本锁定、增量训练与全量训练的选择、超参数继承策略、训练资源动态分配等问题。例如，对于推荐系统这类数据更新频繁的场景，增量训练可以在数小时内完成模型更新；而对于 NLP 模型，通常需要全量重训练以避免灾难性遗忘。


模型评估网关是 CT 闭环的质量守门人。新训练的模型必须通过一系列自动化测试才能进入部署流程：离线评估（准确率、召回率等指标）、对比评估（与当前生产模型对比）、稳定性评估（在多个数据子集上表现一致）和安全性评估（对抗样本鲁棒性）。


class ContinuousTrainingPipeline:
    def __init__(self, config):
        self.drift_detector = DriftDetector(config.drift_threshold)
        self.trigger_policy = TriggerPolicy(config.trigger_type)
        self.trainer = ModelTrainer(config.training_config)
        self.evaluator = ModelEvaluator(config.eval_config)
        self.deployer = ModelDeployer(config.deploy_config)

    def run_cycle(self, production_data, baseline_model):
        drift_report = self.drift_detector.detect(production_data)
        if not self.trigger_policy.should_trigger(drift_report):
            return None

        new_model = self.trainer.train(production_data)
        eval_result = self.evaluator.evaluate(
            new_model, baseline_model, production_data
        )

        if eval_result.passes_all_gates():
            self.deployer.deploy(new_model, strategy="canary")
            return new_model
        return None
数据与模型版本管理
ML 系统的可复现性依赖于对代码、数据和模型的精确版本控制。代码版本管理可以直接复用 Git 等成熟工具，但数据和模型的版本管理面临独特挑战：数据集通常以 TB 计，无法存储在 Git 仓库中；模型文件体积大且格式多样；训练过程的随机性使得相同输入不一定产生完全相同的输出。


DVC（Data Version Control）是目前最流行的数据版本管理工具，它在 Git 之上提供了一层数据版本抽象。DVC 不存储实际数据，而是存储数据的哈希指针（.dvc 文件），实际数据存放在远程存储（S3、GCS 等）。这种设计使得数据版本可以与代码版本一起被 Git 跟踪，同时避免了仓库膨胀。


模型注册表（Model Registry）是管理模型版本的核心组件。MLflow Model Registry、Weights & Biases 和 Vertex AI Model Registry 等工具提供了模型版本管理、阶段标记（Staging → Production → Archived）、元数据追踪和模型血缘（Lineage）记录等功能。模型血缘尤为重要，它记录了每个模型版本是由哪份数据、哪个代码版本、哪套超参数训练产生的，这是排查模型问题和满足审计要求的关键能力。


# DVC pipeline 配置示例
stages:
  prepare_data:
    cmd: python src/prepare.py
    deps:
      - src/prepare.py
      - data/raw/
    outs:
      - data/processed/
  train:
    cmd: python src/train.py
    deps:
      - src/train.py
      - data/processed/
    params:
      - train.learning_rate
      - train.epochs
    outs:
      - models/model.pkl
    metrics:
      - metrics/scores.json
部署策略与渐进发布
ML 模型的部署不同于传统应用部署，需要考虑模型行为的不确定性和业务影响的可量化评估。生产环境中常用的部署策略包括影子部署（Shadow Deployment）、金丝雀发布（Canary Release）和蓝绿部署（Blue-Green Deployment）。


影子部署是最安全的验证方式。新模型在生产环境中接收真实流量并产生预测结果，但这些结果不返回给用户，仅用于与现有模型的结果对比分析。这种方式可以在零风险的情况下评估新模型的生产表现，但缺点是无法评估用户对新模型结果的实际反馈。


金丝雀发布将少量流量（通常 5%-10%）导向新模型，同时大部分流量继续由旧模型服务。通过监控金丝雀流量的业务指标（点击率、转化率、用户停留时间等），可以在小范围内验证新模型的实际效果。如果指标异常，可以立即回滚而不影响大部分用户。


蓝绿部署维护两套完整的推理环境。新模型部署到"绿色"环境并完成预热和验证后，通过流量切换将全部请求从"蓝色"环境切到"绿色"环境。如果出现问题，可以瞬间切回"蓝色"环境。这种策略的资源成本最高，但切换速度最快。

小结
    

  • MLOps 生命周期是管理代码、数据、模型三维变更的持续闭环系统，其核心特征是持续训练能力
    • 

  • 成熟度演进从手动操作到流水线自动化再到完整 CI/CD/CT，建议渐进式推进而非一步到位
    • 

  • 持续训练闭环通过漂移检测、触发策略和评估网关实现模型的自动更新和质量保障
    • 

  • 数据和模型的版本管理是可复现性的基石，DVC 和 Model Registry 是核心工具
    • 

  • 部署策略的选择取决于风险容忍度和资源预算，影子部署和金丝雀发布是最常用的渐进式方案
