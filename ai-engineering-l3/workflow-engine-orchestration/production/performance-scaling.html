工作流引擎性能与扩展

工作流系统的容量不是“每秒能启动多少实例”一个数字。一次业务过程会产生 Workflow Task、Activity Task、Timer、Signal、Update、重试和历史写入；外部依赖变慢时，重试还会放大负载。生产扩展必须同时控制到达率、Worker 槽位、Task Queue 背压、下游配额、事件历史和租户公平性。

本章以 Temporal 的 Worker 与 Task Queue 模型说明方法。具体默认值、服务端吞吐和存储选型会随版本、部署形态及负载变化，不应使用未经测量的“每个 Shard 固定 actions/s”或“某数据库适合某 RPS”作为容量承诺。

核心概念

  • 动作预算：容量以 Workflow Task、Activity attempt、Timer、消息和历史写入建模，不只看实例数。
  • Slot Supplier：固定、资源型或自定义供应器控制 Worker 可接纳的任务并发。
  • 可传递背压：队列积压、下游限额和租户配额必须一路反馈到入口。
  • 恢复容量：扩展计划同时覆盖版本并存、积压排空和跨区域故障转移。

建立负载模型

先把每个 Workflow Type 展开成动作预算。对一次实例，记录正常路径和异常路径分别会产生多少 Workflow Task、Activity attempt、Timer、Signal、子工作流和外部调用。重试策略、Heartbeat 频率、并行扇出和 Continue-As-New 都会改变这个预算。

维度 需要测量的分布 主要瓶颈
实例到达 平均、峰值、突发长度、租户占比 Frontend、History、首个 Workflow Task
Workflow Task 每实例次数、重放时间、缓存命中、历史长度 Worker CPU、缓存、History 读取
Activity Task 每类型到达率、服务时间、attempt 放大 Worker 槽位、下游容量、网络
Timer/Signal/Update 数量、集中唤醒、消息竞争 History 写入、Worker 调度
事件历史 事件数、字节数、增长速率 持久化、传输、重放
外部副作用 操作 ID、回执延迟、未知结果率 下游幂等存储、对账队列

Little 定律给出稳定系统的第一阶估算：平均并发工作量 L=λWL = \lambda WL=λW，其中 λ\lambdaλ 是任务到达率，WWW 是平均服务时间。若某类 Activity 峰值到达率为 λ\lambdaλ，平均执行时间为 E[S]E[S]E[S]，目标槽位利用率为 ρ\rhoρ，起始槽位预算可写为：

C≥λE[S]ρC \ge \frac{\lambda E[S]}{\rho}C≥ρλE[S]​

这个等式不是最终配置。服务时间长尾、事件循环阻塞、内存占用、下游并发限制、重试相关性和突发流量都会使平均值低估风险。先用分布与峰值建模，再在预发布负载测试中测量 schedule-to-start、backlog age、槽位与业务 SLO，最后决定安全余量。不存在对所有流程都正确的“预留 100%”。

Worker 槽位与 Poller

当前 Temporal Worker 调优围绕 Slot Supplier。固定槽位供应器适合资源占用可预测的任务；资源型供应器根据 Worker 的 CPU/内存目标动态发放槽位；自定义供应器用于专门的许可或资源模型。Worker Tuner 统一配置不同任务类型的供应器，它与旧的 maxConcurrent... 并发选项不能混用。升级 SDK 时应以对应版本文档和实际启动配置为准。

选择策略时要区分 Workflow Task 与 Activity Task：

  • Workflow Task 通常消耗 CPU 和缓存，不能因为它“没有外部 I/O”就无限并发。
  • I/O 型 Activity 会等待网络，但仍占用连接、内存和下游配额；槽位不能只按 CPU计算。
  • CPU 或内存型 Activity 应拥有独立 Worker 池，并以单任务资源分布约束槽位。
  • Local Activity 与普通 Activity 的持久化和重试边界不同，容量模型也应分别测量。

Poller 负责从 Task Queue 获取任务。Temporal 的 Worker 性能指南推荐在支持时使用 poller autoscaling，让 poller 数量随需求调整；盲目增加 poller 可能增加空轮询与服务端负担，也不会突破 Worker 槽位或下游限额。观察“有积压但没有任务被接走”时，应同时检查 poller、槽位、版本匹配、Task Queue 名称和 Worker 注册类型。

扩缩容器不应只读 CPU。Activity 大多在等待网络时，CPU 低而 backlog age 可以持续增长；Workflow 重放密集时，CPU 高却未必需要更多 Activity Worker。更可靠的输入是 backlog age、add/dispatch rate、schedule-to-start、可用槽位、资源利用率和下游饱和度的组合。

Task Queue、隔离与背压

Task Queue 是逻辑路由面，不会仅凭名字自动提供资源隔离。只有不同队列由不同 Worker 池、槽位预算、速率限制和扩缩容策略消费时，批处理队列才不会挤占在线队列。同一个进程同时轮询多个队列并共享连接池，仍可能互相争抢。

Temporal 的增强 Task Queue 描述提供近似的 ApproximateBacklogCount、ApproximateBacklogAge、TasksAddRate、TasksDispatchRate 和 BacklogIncreaseRate。这些值适合趋势和容量控制，不应被当作精确账本。schedule-to-start 延迟则反映已开始任务之前等待了多久；二者结合能区分短暂突发与持续消费不足。

信号组合 可能原因 首选动作
backlog age 上升、槽位几乎用尽、下游健康 Worker 容量不足 增加槽位或 Worker，并验证 SLO 恢复
backlog age 上升、槽位可用、poller 少 轮询或注册问题 检查 poller autoscaling、队列名和任务类型
backlog age 上升、下游限流 下游是瓶颈 限制入口与 Activity 速率，不靠扩 Worker 加压
add rate 突增、dispatch 随后追平 可吸收的短突发 用 SLO 容忍窗口观察，不立即抖动扩容
单租户 backlog 主导 公平性或配额缺失 分区、权重、租户限流或独立 Worker 池
仅旧 Build 队列积压 版本覆盖不足 恢复对应 Pinned Worker 或迁移实例

背压应一路传回入口。若下游只允许每秒固定调用量，Task Queue 级或 Worker 级速率限制用于平滑调用，API 则限制新 Workflow 启动、降低非关键扇出或返回可重试的过载结果。让队列无限积累只是把即时失败变成长尾 SLO 违约，还会扩大历史、保留和排空成本。

队列拆分也有成本：更多部署、监控、版本路由和空闲容量。按所有权、资源类型、优先级、数据驻留或租户隔离拆分是合理边界；为每个 Activity 创建队列通常会让运维复杂度超过收益。

重试、超时与放大因子

容量计算必须使用 attempt 到达率，而不是业务操作数。若下游故障导致每个 Activity 平均尝试四次，Worker、队列和历史负载都可能接近四倍。指数退避只能拉开尝试，并不保证下游恢复后不会形成同步洪峰；应加入引擎支持的退避策略、有限最大间隔、下游限流和必要的抖动语义，并区分不可重试业务拒绝。

四类时间边界承担不同职责：Schedule-to-Start 观测队列等待，Start-to-Close 约束单次尝试，Schedule-to-Close 约束所有尝试总窗口，Heartbeat Timeout 检测长 Activity 失联。把 Schedule-to-Start 配成短超时再自动重试，通常只会把容量不足转化为更多调度事件；更好的做法是对其告警并扩容或限流。

结果未知的 Activity 不能通过无限重试“提高成功率”。它需要稳定操作 ID和回执查询，必要时转入对账或人工队列。容量看板应单独显示未知结果和对账年龄，因为这类工作即使不占普通 Worker 槽位，也在消耗业务风险预算。

历史长度、缓存与 Continue-As-New

Temporal Cloud/Server 对单个 Workflow Execution 的历史有事件数和字节数限制；当前文档列出的上限是 51,200 个事件或 50 MB，并在 10,240 个事件或 10 MB 附近给出警告。具体限制可能随服务与版本变化，部署时应以当前官方限制和 Namespace 配置为准。

Continue-As-New 用新的 Run 延续同一 Workflow ID，并把必要状态作为新输入，从而重置历史。不要用固定“每处理 100 项”作为通用阈值；SDK 可提供 Continue-As-New 建议，团队还应根据状态大小、重放时间、版本升级点和业务边界提前切换。切换前必须确认没有尚未完成的消息处理器或结果未知的副作用，并把去重状态、业务策略版本和回执引用带入新 Run。

Sticky Execution 让后续 Workflow Task 优先回到缓存了执行状态的 Worker，减少完整重放，但缓存不是持久真相。Worker 扩缩容、驱逐、故障或版本切换都会触发重放，因此系统必须在无 sticky cache 时仍满足正确性与可接受性能。监控 replay latency、缓存大小与强制驱逐，并用长历史冷启动测试验证最坏路径，不能承诺未经测量的固定“减少 90%”。

大载荷不应塞进事件历史。把文件、模型输出或批量记录存入受治理的对象存储或数据库，历史只保存不可变引用、校验摘要、schema 版本和授权上下文。引用目标必须至少覆盖工作流保留期和灾难恢复期，否则历史可重放却无法恢复业务数据。

服务端、持久化与可见性容量

自托管 Temporal 的 Frontend、History、Matching、Worker Service、持久化和 Visibility 各有独立负载。服务端扩展应以官方容量规划、实际指标和基准测试为依据。History Shard 数通常是早期的重要规划参数，但它不是一个可随时无成本修改的并发旋钮，也不能乘以通用的每 Shard 吞吐常数得出可靠上限。

持久化选择要根据官方支持矩阵、团队运维能力、写入延迟、可用性和恢复要求评估，而不是简单给 PostgreSQL、MySQL、Cassandra 或其他后端贴“小/大规模”标签。Visibility 存储负责检索视图，不应承载强一致业务查询。压测必须同时覆盖历史写入、任务匹配、长历史读取、Visibility 索引和故障恢复，避免只测 start API。

托管服务也不意味着无限容量。Namespace 限额、操作速率、并发任务、历史限制和外部 Worker 容量仍需治理。遇到 ResourceExhausted 时应记录原因与 Scope，先保护系统并降低流量，再与实际限额和容量计划对齐。

多租户公平与安全边界

多租户共享 Namespace、Task Queue 或 Worker 池时，一个租户的突发、重试风暴或大载荷可能消耗公共槽位。隔离手段从软到硬包括：入口配额、按租户权重调度、Activity 速率限制、独立 Task Queue/Worker 池、独立 Namespace，以及在法规或信任边界要求下独立集群。选择依据是故障半径和数据边界，不是租户数量本身。

容量标签要避免泄露租户名称和高基数标识。Worker 身份只应访问所属 Namespace 和下游资源；自托管服务要启用 mTLS 与自定义 Authorizer，因为默认的 no-op Authorizer 不会替你建立租户隔离。Payload Codec、Codec Server、Visibility 与历史导出权限也必须遵守同一边界。

公平性要有可测试 SLO：在噪声租户达到配额时，其他租户的 backlog age 和完成期限仍受保护；限流返回可解释且可重试；回收容量后积压在目标时间内下降。只在架构图上画多条队列不能证明隔离成立。

跨区域、故障转移与版本容量

Temporal Global Namespace 在一个时刻有一个 active cluster，复制到其他 cluster 并通过 failover 切换。不能把同一 Namespace描述为多个区域同时无冲突写入的通用 active-active。若要多区域同时处理，可把不同 Namespace 主动分布在不同 cluster，但每个 Namespace 仍有明确活动位置和故障边界。

容量计划必须为 failover 预留接管能力，并明确复制延迟、RPO、RTO、Worker 在目标区域的版本与凭据。只复制服务端历史而没有对应 Worker Build、下游网络、密钥和操作回执，无法恢复流程。演练应在存在长流程、Timer、结果未知和旧 Pinned 版本时执行，而不是只启动一个新实例验证 API 可达。

Worker Versioning 也会消耗额外容量。Ramping 期间新旧 Build 并存，Pinned 工作流要求旧池长期可用；扩缩容器如果只看 Current Build，会让旧实例的 schedule-to-start 悄悄增长。版本看板需要显示每个 Build 的实例数、任务积压、最老年龄、槽位和可退役证据。

压测与容量变更闭环

一次可用的容量验证包含四个阶段：

  1. 校准：从生产脱敏统计提取到达率、服务时间、重试、历史和租户分布。
  2. 施压：分别模拟稳态、计划峰值、突发、下游降速、Worker 滚动发布和旧版本排空。
  3. 观测：记录业务 SLO、backlog age、add/dispatch rate、schedule-to-start、槽位、资源、历史增长与未知结果。
  4. 恢复：停止故障后验证积压下降时间、重试是否形成洪峰、限流是否解除以及错误预算损耗。

扩容、改槽位、拆队列、调整重试和启用 Continue-As-New 都是独立变更，每次只改变少量变量，并保存前后证据。性能优化不能破坏所有权边界：增加并发前要取得下游容量契约；缩短超时前要确认业务操作能安全取消；迁移队列前要保证对应 Worker 版本覆盖。

可观测性与调试定义了这些闭环所需的指标与 SLO，测试策略则把过载、噪声租户、版本并存和外部提交后失联变成可重复的门禁。容量合格的标志不是队列永远为零，而是在已知负载和故障下，背压受控、租户公平、业务期限可预测、结果证据可闭合。

小结

容量规划从实测到达率、服务时间和重试放大出发，以 Little 定律得到起点，再用 backlog age、add/dispatch rate、schedule-to-start、槽位与业务 SLO 校准。Task Queue 只有配合独立资源与限额才形成隔离，Continue-As-New 与 sticky cache 只能优化历史成本而不能替代正确性。最终门是峰值、依赖降速、版本并存和故障转移后仍能受控背压、公平排空并闭合副作用证据。
