工作流测试策略

工作流测试的目标不是证明“快乐路径能跑完”，而是证明系统在重放、重复执行、超时竞争、版本并存和结果未知时仍保持业务不变量。一个测试即使看到 Workflow 最终成功，也可能漏掉外部扣款执行了两次、取消请求没有送达、旧历史无法由新 Worker 重放，或补偿失败后没有任何人接管。

Temporal 当前的 TypeScript 测试建议强调以集成测试为主体：真实测试服务、真实 Worker 和尽量接近生产的 Workflow/Activity 边界可以发现序列化、注册、超时、重试与历史行为问题。单元测试仍适合纯领域函数和 Activity 适配器，但不能用大量 Mock 代替引擎语义验证。

核心概念

  • 不变量驱动：先定义重复、故障和并发下不可破坏的业务事实，再分配测试层级。
  • 结果未知窗口：重点注入外部提交成功但 Activity 完成确认丢失的故障。
  • 历史重放门：当前 Workflow Bundle 必须能解释仍可能执行的代表性旧历史。
  • 可审计故障演练：每次注入都验证历史、回执、告警、责任人和恢复时限。

从不变量设计测试组合

先列出流程必须永远成立的事实，再决定测试层级。订单工作流的典型不变量包括：同一操作 ID 最多产生一个已确认扣款；库存与支付若无法同时完成，最终进入补偿完成或人工介入；未经授权的审批不会改变状态；任何结果未知都能通过回执对账；新 Build 能解释仍可能到达的旧历史。

测试层 主要对象 最能发现的问题 不能单独证明的事情
纯函数单元测试 决策表、状态转换、金额与权限规则 边界值、领域不变量 引擎历史、重试与序列化
Activity 契约测试 下游适配器、操作 ID、回执、错误分类 幂等、未知结果、鉴权、schema Workflow 是否正确调度
Worker 集成测试 真实测试服务、Workflow、Activity Timer、Signal、Update、重试、取消、历史 真实云依赖与容量
历史重放测试 生产脱敏历史与当前 Workflow Bundle 命令不兼容、解码问题 新业务语义是否正确
端到端与故障演练 预发布环境、真实依赖或沙箱 网络、凭据、配额、观测与运维动作 所有输入组合
负载与耐久测试 峰值流量、长历史、版本并存 背压、公平性、资源泄漏 每个领域分支正确性

测试数量不应按固定百分比分配。风险高、外部副作用不可逆的 Activity 需要更深的契约与故障测试；纯等待型流程可能把更多预算放在 Timer、Signal 竞争和版本重放。真正的质量门是关键不变量在多个层次都有独立证据。

flowchart TD
  I[业务不变量] --> U[纯逻辑单元测试]
  I --> A[Activity 回执与幂等测试]
  I --> W[真实 Worker 集成测试]
  W --> H[历史样本]
  H --> R[每次发布重放]
  W --> F[故障注入]
  F --> O[验证历史 日志 回执 告警]

Activity：测试至少一次边界

Activity 应被假定为可能执行多次。最关键的测试窗口是：外部系统已经提交副作用，但 Worker 尚未把完成结果确认给服务端时进程被杀或网络中断。下一次 attempt 会再次调用 Activity；如果它使用新幂等键，最终 Workflow 成功也可能掩盖双重副作用。

一个可测试的 Activity 契约包含四项：稳定操作 ID、下游原子去重或本地 Inbox、可查询的结果回执，以及把错误分为可重试、不可重试和结果未知的规则。测试应让网关在提交后故意丢弃响应，再以同一个操作 ID 重试，并断言返回同一回执。

it('reuses the committed receipt after the response is lost', async () => {
  const operationId = 'charge/order-42';

  gateway.failAfterCommitOnce(operationId);

  await expect(chargePayment({ operationId, amount: 5000 })).rejects.toThrow();
  const recovered = await chargePayment({ operationId, amount: 5000 });

  expect(recovered.receiptId).toBe(gateway.receiptFor(operationId).receiptId);
  expect(gateway.committedChargeCount(operationId)).toBe(1);
});

还要覆盖：下游明确拒绝是否被标记为不可重试；限流和短暂不可用是否保留重试；Heartbeat 是否携带可恢复进度；取消是否只在安全点中止；凭据过期是否触发可行动告警；租户 ID 是否参与授权却不被错误地拼成全局幂等键。不要把普通 HTTP 超时统一解释为“未执行”。

真实 Worker 集成与时间跳跃

TypeScript SDK 的测试环境可以启动本地或 time-skipping 服务。Worker 必须真实运行；只创建 Worker 后直接等待 client.workflow.execute 会让测试没有消费者。runUntil 把 Worker 生命周期与待测 Promise 绑定，是一个清晰的基本模式。

import { TestWorkflowEnvironment } from '@temporalio/testing';
import { Worker } from '@temporalio/worker';

it('escalates when approval expires', async () => {
  const env = await TestWorkflowEnvironment.createTimeSkipping();
  const taskQueue = `approval-${crypto.randomUUID()}`;
  const worker = await Worker.create({
    connection: env.nativeConnection,
    taskQueue,
    workflowsPath: require.resolve('../workflows'),
    activities: testActivities,
  });

  const result = await worker.runUntil(() =>
    env.client.workflow.execute(approvalWorkflow, {
      workflowId: crypto.randomUUID(),
      taskQueue,
      args: [{ requestId: 'request-1' }],
    }),
  );

  expect(result.status).toBe('escalated');
  await env.teardown();
});

Time skipping 会在没有正在执行的 Activity 时推进测试服务的虚拟时间，让数天 Timer 快速到期。虚拟时钟是测试服务级共享资源；并发测试可能互相推进时间，因此涉及精确时序的用例应隔离环境或串行运行。它也不会模拟真实 Worker CPU 饥饿、队列积压和下游延迟，这些问题需要负载或故障环境。

Timer 与外部事件的竞争必须测试双方以及边界：事件先到、Timer 先到、二者几乎同时到、重复事件、事件在 Workflow 尚未注册处理器时到达。断言不只看终态，还应检查只有一个决策胜出，输掉的 Timer 或取消作用域被正确清理，并且审计信封记录了事件 ID、主体、策略版本和接收时间。

Signal、Update、Query 与取消

外部消息是工作流最常见的并发入口。测试矩阵至少覆盖：重复消息 ID、乱序消息、互相冲突的审批、关闭后到达、Continue-As-New 前后到达，以及两个调用方同时提交 Update。Workflow 内的处理器必须是确定性的，但入口鉴权通常属于调用工作流的 API 边界；集成测试需要证明未授权主体无法把消息送入执行历史。

Query 不写历史，测试应验证它只读取状态、在 Worker 暂不可达时调用方能表达“未知”，且 Query 结果不会被当作付款或审批的强一致提交证据。Update 会等待接收或完成确认，应测试验证器拒绝、处理器失败和客户端重试是否产生预期语义。

取消不是进程信号的同义词。对普通 Activity，Worker 通常需要通过 Heartbeat 才能及时收到取消。测试应启动长 Activity、发送取消、验证 Heartbeat 触发取消异常，并确认外部资源被释放或转入补偿。再做一次“Activity 不 Heartbeat”的反例，证明其只能等到超时或完成，从而校准运行手册而不是依赖想象中的即时中断。

历史重放是发布门

静态检查可以阻止某些不安全模块进入 Workflow Bundle，但它无法证明所有控制流变化都保持命令兼容。每次修改会产生命令的 Workflow 代码、升级 SDK 或更改序列化器时，都应重放仍在保留期或仍可能运行的历史。

历史样本应覆盖最老 Build、长历史、每个补丁分支、重试后完成、等待 Signal、取消中、补偿中、Continue-As-New 和不同 schema 版本。生产历史在进入测试仓库前必须脱敏；若 Payload Codec 需要密钥，应在受控环境解码后生成最小 fixture，而不是把生产密钥放入 CI。

TypeScript SDK 提供 Worker.runReplayHistory 与批量历史重放能力。一个最小门可表达为：加载脱敏历史，用当前 Workflow Bundle 重放，任何非确定性或解码错误都阻断发布。

import { readFile } from 'node:fs/promises';
import { Worker } from '@temporalio/worker';

const history = JSON.parse(await readFile('fixtures/approval-v1-waiting.json', 'utf8'));

await Worker.runReplayHistory({
  workflowsPath: require.resolve('../workflows'),
  history,
});

fixture 清单需要记录来源 Build、Workflow Type、状态分支、schema、脱敏方式和最后验证日期。只保存已成功结束的短历史会让门失去价值。版本策略及旧分支何时可删除，应与版本化与迁移中的排空证据一致。

故障演练：验证恢复证据

故障注入不是随机杀进程后看到“最终成功”就结束。每个演练要预先写出注入点、不变量、期望历史、回执、告警、责任人和恢复时限。

注入点 必须守住的不变量 通过证据
外部提交后、Activity 确认前杀 Worker 同一操作只产生一个业务结果 相同操作 ID、单一回执、多 attempt 历史
Heartbeat 之间杀 Worker 从已确认进度恢复，不重复已完成分片 Heartbeat details、分片回执、最终集合
Worker 与服务端断网 任务不丢失，恢复后由合格版本接管 schedule-to-start、attempt、Build 与恢复时间线
下游持续限流 重试受控，不形成重试风暴 backoff、有限 attempt、队列与下游 SLO
Signal 重复与乱序 决策至多一次且冲突可审计 消息 ID 去重、决策信封、拒绝原因
补偿持续失败 不无限自动重试，进入人工介入 最终补偿状态、告警、冻结资源与工单
新 Worker 放量后回滚 旧实例仍可执行，新副作用被识别 历史重放、版本路由、不可逆操作清单
Task Queue 人为饱和 高优先级或其他租户仍有公平份额 backlog age、槽位、限额与恢复时间

故障演练还要验证观测链：告警能否指向正确 Task Queue 和 Build，值班者能否在不读取敏感正文的情况下判断结果未知，操作回执能否从 Workflow ID 追到下游，恢复后错误预算是否被正确扣减。没有这些证据的“自愈”无法审计，也难以在真实事故中复现。

负载、耐久与多租户测试

负载测试的输入应来自峰值到达率、Activity 服务时间分布、重试放大、长历史比例和租户混合，而不是只提高 Workflow start QPS。分别测量 Workflow Task 与 Activity Task 的 add/dispatch rate、schedule-to-start、backlog age、槽位、下游限流、历史增长和端到端业务 SLO。

耐久测试让 Worker 运行足够久以暴露缓存、连接、内存和 poller 问题；版本并存测试则保持旧 Pinned Worker，同时放量新 Build，确认容量模型没有只计算 Current Version。多租户测试要制造一个噪声租户，验证队列、速率限制、Namespace 或 Worker 池的隔离确实能保护其他租户，并确认 Search Attributes、日志和回执不会跨租户泄露。

持续交付质量门

工作流变更进入生产前，建议按风险依次执行：静态与类型检查、纯逻辑单测、Activity 契约与回执测试、真实 Worker 集成、历史重放、schema 兼容、受控故障注入，最后才是渐进版本放量。任何一步都要产出机器可判定结果；“人工看起来正常”不能成为长期质量门。

测试夹具、工作流实现、Activity 适配器和观测断言应分离所有权。领域团队拥有业务不变量，平台团队拥有引擎与故障设施，下游团队拥有幂等与回执契约。这样，当测试失败时可以定位责任边界，而不是把所有问题都归为“工作流不稳定”。可观测性与调试定义了演练证据，性能与扩展定义了负载测试需要测量的背压信号。

小结

可靠的工作流测试以真实 Worker 集成为主体，用纯函数单测定位领域规则，用 Activity 契约测试证明幂等与回执，用 time skipping 覆盖时间竞争，用生产脱敏历史阻断不兼容发布。故障演练只有同时守住业务不变量并产出历史、回执、告警和恢复证据才算通过；“最终成功”本身不足以证明没有重复副作用或隐藏积压。
