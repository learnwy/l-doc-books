工作流可观测性与调试

工作流把一次业务过程拆成许多跨进程、跨时间的尝试。普通请求追踪回答“这次 HTTP 调用经过哪里”，工作流可观测性还必须回答：实例正等待什么、等待是否符合业务期限、外部操作是否已经发生但确认丢失、哪个 Worker 版本拥有下一条任务，以及租户是否正在耗尽共享容量。

事件历史是控制流的权威记录，但不是外部世界的完整事实。Activity 在外部扣款后、向引擎确认前崩溃，历史里可能只有超时；此时“没有 ActivityCompleted”不等于“没有扣款”。生产调试必须把历史、Activity 操作回执、队列状态和业务对账证据放在一起。

核心概念

  • 控制流证据：事件历史说明引擎确认了什么，不单独证明外部世界没有未确认副作用。
  • 四层观测：实例、队列与 Worker、引擎与依赖、业务与对账共同闭环。
  • SLO 派生告警：阈值来自业务期限和错误预算，不复制通用百分比或秒数。
  • 尝试级关联：Activity attempt、稳定操作 ID与结果回执共同解释重复执行。

四层观测模型

只看引擎健康会漏掉业务停滞，只看单实例又会漏掉系统性积压。推荐把信号分成四层，并为每层指定所有者与处置动作。

层次 要回答的问题 主要信号 典型所有者
实例与历史 这个实例执行到哪一步，为什么等待 Event History、Pending Activity、Timer、Signal、失败原因、版本 工作流代码所有者
队列与 Worker 任务能否及时被有能力的 Worker 接走 schedule-to-start、backlog age、槽位、poller、版本覆盖 Worker 平台所有者
引擎与依赖 服务端、持久化和下游是否健康 请求失败、资源耗尽、存储延迟、下游限流 平台与依赖所有者
业务与对账 过程是否在期限内完成，副作用是否一致 完成率、期限违约、未知结果、回执缺口、补偿与人工队列 领域所有者

这四层共享稳定的关联键：namespace、workflowType、workflowId、runId、taskQueue、workerDeploymentVersion、activityType、activityId、attempt、tenantId 和领域操作 ID。高基数字段不应无条件成为指标标签；通常把实例 ID 放到结构化日志、追踪和查询系统，把类型、队列、版本、租户等级等受控维度用于指标。

flowchart LR
  B[业务 SLO 违约] --> I[定位实例集合]
  I --> H[检查事件历史]
  H --> Q[检查队列与 Worker]
  H --> R[核对副作用回执]
  Q --> P[检查引擎与依赖]
  R --> D{结果是否已确认?}
  D -->|是| C[恢复控制流]
  D -->|否| M[对账或人工处置]

事件历史：控制流证据而非世界快照

事件历史记录 Workflow Execution 的启动、Workflow Task、Activity 调度与结果、Timer、Signal、Update、子工作流等事件。它适合回答命令如何产生、重试发生几次、当前等待哪个条件以及新代码是否能重放旧历史。历史中的 Activity 输入输出可以证明引擎收到了什么，却不能单独证明外部系统此刻的状态。

调试单个实例时，按以下顺序缩小范围：

  1. 确认 Workflow ID、Run ID、Namespace、Workflow Type 和执行版本，避免把 Continue-As-New 的不同 Run 混为一谈。
  2. 找到最后一个成功的业务状态转换，而不只是最后一条技术事件。
  3. 检查 Pending Activity 的 attempt、超时类型、最后心跳和下次重试时间。
  4. 若 Activity 结果未知，用稳定操作 ID 查询下游回执或对账表；不要根据历史缺少完成事件直接重试不可幂等操作。
  5. 检查实例是否在等预期的 Signal/Timer，以及等待期限是否由业务时钟而非告警脚本定义。
  6. 对非确定性错误，用同一历史和对应 Worker Build 离线重放，再比较产生命令的代码变化。

事件历史可能包含工作流输入、Activity 参数与结果、Signal 内容和错误详情。它们会持久化并进入 Web UI、导出文件或 Codec Server 的解码路径。生产系统应最小化载荷，使用不透明引用替代敏感正文，在需要时配置 Payload Codec/Encryption，并对 UI、历史导出、Codec Server 与运维身份分别授权。Search Attributes 用于检索，不适合存放秘密、支付资料或任意个人信息。

指标、SLO 与错误预算

指标名称会随 SDK、服务端版本和 Prometheus 前缀配置变化，因此监控契约应以语义和标签集合为主，在部署时对实际暴露名称做验收。以下信号比固定的通用阈值更可靠。

信号 意义 应如何告警
Workflow/Activity Task schedule-to-start latency 任务在队列等待 Worker 的时间 对照该队列的调度 SLO，结合 backlog age 与可用槽位
Task Queue ApproximateBacklogAge 最老积压任务的大致年龄 年龄持续越过该任务类型的可接受等待时间
TasksAddRate / TasksDispatchRate / BacklogIncreaseRate 生产与消费是否失衡 增长持续为正且没有计划内原因
Activity start-to-close 与端到端耗时 执行本身或下游变慢 按 Activity 类型和版本比较基线与尾延迟
retry、timeout、non-retryable failure 可靠性策略是否掩盖持续故障 以尝试数和最终结果共同衡量，避免只看终态成功
Worker task slots used/available、poller、CPU/内存 Worker 是否被槽位或资源限制 与队列延迟联动，不凭 CPU 单指标扩缩容
resource exhausted 与服务请求失败 服务端或租户配额被触发 按 Namespace、操作和原因分组，关联容量变更
unknown-result、receipt-missing、reconciliation-age 外部副作用证据是否闭合 任何超过业务恢复期限的未知结果都应升级
version backlog、oldest pinned age 旧 Worker 能否安全退役 超过版本排空期限或旧版无可用 Worker 时告警

SLO 应来自业务期限。例如“99.9% 的支付编排在接单后 5 分钟内到达已确认终态”，可以分解为任务调度预算、Activity 执行预算、允许重试预算和对账恢复预算。告警应基于剩余错误预算和持续窗口，而不是把“失败率 1%”或“排队 10 秒”复制到所有队列。人工审批三天是正常等待，支付授权排队三天则是事故；两者都显示 Running，语义完全不同。

业务仪表盘至少区分：成功终态、预期业务拒绝、技术失败、等待外部事件、补偿中、补偿失败、结果未知和人工介入。把业务拒绝计入系统失败率会制造噪声，把补偿后完成当作无损成功又会隐藏真实成本。

Visibility、查询与索引边界

Temporal Visibility 能按执行状态、Workflow Type、时间和 Search Attributes 检索实例，适合找到“哪个集合需要调查”。它是异步索引视图，不应被当作强一致的业务数据库或授权来源。领域系统仍需维护自己的读取模型和权限边界。

Search Attributes 应选择低敏、稳定、可治理的字段，例如业务状态代码、租户分区、风险等级和处理区域。每个字段要有类型、基数、保留期与访问者清单。把完整客户 ID、自由文本错误或每次尝试 ID 都做索引，会同时放大隐私风险和索引成本。

Query 用于读取 Workflow 当前状态，不会产生历史命令。它适合实例详情页，但在 Worker 不可达、实例已关闭或缓存需要重放时可能不可用或延迟。运维页面应呈现“状态未知/暂不可查询”，而不是把 Query 失败解释为业务失败。

日志与追踪：一次尝试一份证据

Workflow 代码会重放，直接使用普通 logger 可能重复输出历史路径。应使用 SDK 的 Workflow logger 或带 replay 标记的拦截器。Activity 本身不会以 Workflow 重放方式执行，但在至少一次执行边界下可能真正运行多次；Activity 日志必须包含 activityId、attempt 和稳定操作 ID，日志消费方不能把重复日志当作重复业务事实。

一个持续数天的根 Span 往往超过追踪后端的保留和查询模型。更实用的做法是为启动请求、每个 Workflow Task、每次 Activity attempt 和下游调用创建有界 Span，用 Workflow ID、Run ID 与操作 ID 建立 Links 或结构化关联。追踪采样不能丢失失败、超时、补偿和未知结果；成功高流量路径可以概率采样，异常路径应保留。

日志内容同样需要数据分级。输入输出正文、审批意见和异常堆栈可能包含受保护数据；默认记录标识、状态、大小、哈希和回执位置，只有获得授权的诊断流程才解码正文。删除策略要同时覆盖日志、历史导出、追踪属性和临时故障包。

版本化调试手册

同一 Workflow Type 可能同时由多个 Build 服务。所有看板、告警和故障包都应带 Worker Deployment Version，否则新版本 5% 流量的错误会被旧版本 95% 的成功稀释。发布期间至少比较：非确定性错误、Workflow Task 失败、Activity 尾延迟、每实例重试数、业务不变量、未知结果、队列积压和最老 Pinned 实例。

现象 首要证据 不应直接下的结论 下一步
Workflow 长时间 Running 当前阶段、Timer/Signal、业务期限 “引擎卡住了” 区分正常等待、队列等待和状态丢失
Activity 多次超时 timeout 类型、heartbeat、attempt、下游回执 “外部操作没有发生” 查询操作 ID 回执并决定恢复动作
schedule-to-start 上升 backlog age、dispatch rate、槽位、版本 Worker “只要多加 Pod” 判断槽位、poller、下游限流或版本覆盖问题
Non-Determinism 失败历史、Build ID、命令变化 “重启 Worker 会恢复” 重放历史，恢复旧 Build 或加入兼容补丁
Signal 已发送但状态未变 Signal 事件、去重 ID、处理器失败 “用户需要再点一次” 验证是否已接收、冲突或等待其他条件
补偿队列增长 原操作回执、补偿 attempt、人工期限 “最终会自动成功” 有限重试后升级人工处置并冻结相关资源

每次事故应保存最小、脱敏、可重放的证据包：执行标识、Build ID、相关历史、队列快照、Activity 回执、关键指标窗口、配置版本和时间线。证据包不是无限期保存的原始数据仓库，应有访问审计和销毁时间。

仪表盘与运行门

生产仪表盘应围绕行动组织，而不是堆满指标：

  1. 业务 SLO：按流程与租户等级显示期限达成、未知结果和人工队列年龄。
  2. 调度与容量：按 Task Queue 和 Build 显示 backlog age、add/dispatch rate、schedule-to-start 与槽位。
  3. 失败恢复：按 Activity 类型显示 attempt、超时、补偿、回执缺口和恢复时长。
  4. 版本排空：显示 Current/Ramping/Pinned 版本、存量实例、最老年龄和不可达 Worker。
  5. 平台依赖：显示服务端请求、资源耗尽、持久化和下游依赖健康。

上线门要求这些视图真实可用：测试告警能找到责任人；从一个业务实例可以跳到历史、日志和回执；从一个队列告警可以看到拥有它的 Worker Deployment；在不暴露敏感载荷的情况下仍能判断恢复动作。下一节的测试策略会把这些能力作为故障演练的证据，而性能与扩展会说明如何用队列信号闭环容量控制。

小结

生产可观测性必须把事件历史与外部回执、队列状态和业务 SLO 关联起来。历史是控制流权威，但外部结果未知时仍需对账。指标按 Task Queue、Worker Build 和受控租户维度组织，日志与追踪按 attempt 留证且保护载荷；这样告警才能直接导向扩容、版本恢复、补偿或人工介入，而不是只报告“Workflow 仍在运行”。
