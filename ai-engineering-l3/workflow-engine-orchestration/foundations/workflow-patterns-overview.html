工作流模式概览

核心概念

  • 工作流模式（Workflow Pattern）：对多步骤业务流程中控制流结构的抽象与命名，是构建复杂编排的原子积木
  • 控制流原语：顺序、并行分支、条件分支、同步合并、循环——五种基础模式可组合覆盖绝大多数业务场景
  • Workflow 与 Activity：前者保存确定性的控制状态，后者执行网络、数据库和文件系统等外部副作用
  • Task 与 Worker：Task 是引擎持久化后派发的执行机会，Worker 是轮询队列并承载版本化代码的进程
  • 子工作流（Child Workflow）：将一段流程封装为独立的可调用单元，拥有独立的事件历史和生命周期
  • 定时器（Durable Timer）：引擎原生的持久化等待能力，进程可重启而定时器不丢失

为什么需要工作流模式

一个订单从创建到发货，要经历支付校验、库存扣减、物流分配、通知发送等十余步操作，跨越 4-6 个服务，耗时从毫秒级到数天不等。当这些步骤用零散的 API 调用和消息队列拼凑时，流程的可见性、故障恢复、超时处理都是逐个手写的胶水代码。工作流模式为这类问题提供了一组经过验证的结构化解法：把「多步骤、跨服务、有状态的业务流程」抽象为可复用的控制流原语。

工作流模式的价值不在于「发明新概念」，而在于把隐含在代码中的流程结构显式化——一旦显式化，引擎就能接管持久化、重试、超时、并发控制等横切关注点，开发者只需描述「做什么」和「做的顺序」。

五大基础模式

下表总结了工作流引擎普遍支持的五种基础控制流模式，它们是构建复杂业务流程的原子积木：

模式 语义 典型场景 引擎支持示例
顺序（Sequence） 步骤 A 完成后执行 B 订单创建→支付→发货 所有引擎原生支持
并行分支（Parallel Split） 同时启动多条独立路径 同时发邮件+短信+Push Temporal: Promise.all; Step Functions: Parallel state
条件分支（Exclusive Choice） 根据条件走不同路径 金额>1000 走人工审批 Temporal: if/switch; Step Functions: Choice state
同步合并（Synchronization） 等所有并行分支完成后继续 所有通知都发完才标记完成 Temporal: await Promise.all; Step Functions: Parallel 自动汇合
循环（Loop/Iteration） 重复执行直到条件满足 轮询外部审批结果 Temporal: while 循环; Step Functions: Iterator 模式

这些原语是控制流的最小词汇，而不是可靠性的完整答案。生产流程还必须为每条边定义输入契约、超时、重试、取消、补偿和结果证据。控制流图能说明下一步是谁，却不能证明上一步的外部效果只发生过一次。

顺序与依赖

顺序执行是最简单也最常见的模式——步骤之间有数据依赖或因果依赖：

graph LR
    A[创建订单] --> B[扣减库存]
    B --> C[发起支付]
    C --> D[生成物流单]
    D --> E[发送通知]

在持久执行引擎中，引擎确认接收的步骤结果会进入事件历史。如果进程在步骤 C 的完成事件已经持久化后、步骤 D 调度前崩溃，引擎可重放历史并从 D 继续。若 C 的外部写入已经发生，但 Worker 在上报完成前失联，C 仍可能被再次执行；这时必须依靠幂等键或查询外部回执收敛未知结果。

并行与扇出-汇合

并行模式将一个流程分叉为多条独立路径同时执行，然后在某个同步点等待全部完成（Fan-Out / Fan-In）：

// Temporal TypeScript SDK 示例
const [inventory, payment, notification] = await Promise.all([
  reserveInventory(orderId),
  processPayment(orderId, amount),
  sendOrderConfirmation(userId),
]);
// 三个 Activity 并行执行，全部完成后继续
await createShipment(orderId, inventory.warehouseId);

并行模式的关键设计决策：

  1. 全部完成 vs 任一完成：Promise.all 等全部完成；Promise.race 只等最快的一个（竞争模式，常用于超时兜底）。
  2. 部分失败策略：一条分支失败时，是取消其他分支（补偿），还是等其他分支完成后再统一处理？
  3. 动态扇出：分支数量在运行时才确定（如「为购物车中每个商品检查库存」），需要引擎支持动态并行。

条件分支与动态路由

条件分支让流程根据运行时数据走不同路径，是实现业务规则的核心模式：

graph TD
    A[接收贷款申请] --> B{金额判断}
    B -->|金额 ≤ 50万| C[自动审批]
    B -->|50万 < 金额 ≤ 500万| D[单人审批]
    B -->|金额 > 500万| E[委员会审批]
    C --> F[放款]
    D --> F
    E --> F

与简单的 if-else 不同，工作流中的条件分支需要考虑：

  • 确定性约束：在 Temporal 等重放引擎中，分支条件的计算必须是确定性的——不能依赖当前时间、随机数或外部状态，否则重放时会走不同路径导致 Non-Determinism Error。
  • 状态可见性：走了哪条分支应该被记录在事件历史中，供后续排查和审计。
  • 多路合并：多条条件分支最终需要汇合到统一的后续步骤。

子工作流与组合

当流程变得复杂时，可以把一段逻辑封装为子工作流（Child Workflow），被父工作流调用。子工作流有独立的事件历史和生命周期：

维度 Activity（活动） Child Workflow（子工作流）
执行时间 单次外部操作；长任务应心跳和保存进度 可跨越多个步骤和长期等待
状态持久化 完成结果进入调用方历史；尝试本身可重复 拥有独立事件历史和运行标识
重试粒度 整个 Activity 尝试 子流程内部按各步骤恢复
取消行为 通常需心跳或取消感知点才能协作停止 由父关闭策略与子流程清理语义共同决定
适用场景 API、数据库、文件或计算等副作用边界 需要独立生命周期的多步业务能力

子工作流模式让大型业务流程可以分层组织：顶层工作流编排全局流程，每个阶段委托给子工作流处理细节。这类似于编程中的函数抽象——控制复杂度的基本手段。

定时器与延迟执行

定时器是工作流引擎区别于普通任务队列的关键能力之一。引擎原生支持「等待一段时间后继续」，且等待期间不消耗计算资源：

// 等待 72 小时用户确认，超时自动取消
const confirmed = await condition(
  () => userConfirmed,
  '72 hours', // 72 小时超时
);
if (!confirmed) {
  await cancelOrder(orderId);
}

定时器在引擎内部实现为持久化的时间戳：到达时间后引擎唤醒工作流继续执行。这与 setTimeout 的根本区别在于——进程可以重启、服务器可以迁移，定时器依然会按时触发。

定时器的典型应用：

  • 超时控制：等待人工审批，超时自动流转
  • 延迟执行：支付后 7 天无异议自动确认收货
  • 周期调度：每日对账、每小时同步状态
  • 退避重试：以指数退避间隔重试失败操作

从控制流到可执行契约

把流程图交给引擎之前，应为每个外部步骤写出执行契约。下面的所有权划分能避免把引擎能力误读为端到端精确一次：

所有者 必须保证的内容 不能假设的内容
Workflow 决策顺序、持久等待、终止条件、补偿选择 直接执行不可重放的外部 I/O
引擎 历史持久化、Task 派发、定时与配置化重试 外部系统已产生唯一副作用
Worker / Activity 执行操作、心跳、错误分类、响应取消 一次函数调用就等于一次业务效果
目标服务 幂等键、状态查询、业务回执、并发约束 调用方永远不会重复发送请求

一个可恢复的写操作至少携带 workflowId + operationId 组成的稳定幂等键。目标服务应原子地记录“幂等键—结果回执”映射；Activity 收到成功后把回执编号作为返回值交给引擎。若 Activity 超时，下一次尝试先按幂等键查询：已有回执就返回同一结果，确认为未执行才重新写入。这个协议把“效果已发生、确认未知”的灰区变成可查询状态。

重试、超时和取消也必须分开设计：

  • 重试回答“失败后何时再次尝试”，只适用于被分类为暂时性的错误。
  • Start-To-Close 限制单次尝试，Schedule-To-Close 限制包含所有重试的总体窗口，排队超时反映容量而不是业务失败。
  • 取消是协作协议，不是进程级强杀。长 Activity 需要心跳或显式取消感知点，并定义中途退出后保留还是清理部分成果。
  • 到达尝试上限后，Workflow 应进入明确的人工处置、补偿或失败终态，不能无限重试掩盖永久错误。

模式组合的复杂度

真实业务流程通常是多种模式的组合。以一个电商退款流程为例：

graph TD
    A[收到退款申请] --> B{退款金额}
    B -->|≤ 100元| C[自动审批]
    B -->|> 100元| D[人工审批]
    D --> E{审批结果}
    E -->|拒绝| F[通知用户]
    E -->|通过| G[并行执行]
    C --> G
    G --> H[退款到账户]
    G --> I[恢复库存]
    G --> J[更新订单状态]
    H --> K[同步等待]
    I --> K
    J --> K
    K --> L[发送退款通知]

这个流程组合了条件分支（金额判断）、定时器（人工审批等待）、并行分支（退款+恢复库存+更新状态）和同步合并（等所有并行步骤完成）。工作流引擎的价值在于：开发者只需声明这些模式的组合，引擎处理其中的持久化、重试、超时和故障恢复。

小结

工作流模式是构建复杂业务流程的结构化词汇——顺序处理数据依赖、并行缩短关键路径、条件分支实现业务规则、子工作流控制生命周期、定时器处理时间维度。模式只定义控制结构；端到端可靠性还依赖 Activity 的至少一次尝试、外部幂等回执、超时与取消协议。后续章节将讨论如何选择编排 vs 协同的实现风格，以及如何用形式化方法对复杂流程进行建模验证。

截至 2026 年 8 月，Activity 至少一次边界、心跳取消和超时语义可对照 Temporal Activity 官方定义与 Activity 超时文档核验。
