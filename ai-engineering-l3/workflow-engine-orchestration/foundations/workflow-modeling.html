工作流建模方法

核心概念

  • 状态机（FSM）：用离散状态和事件驱动的转换建模流程，适合步骤少、状态明确的场景
  • 有向无环图（DAG）：用节点和依赖边建模流程，天然表达并行机会，不支持循环
  • 代码即流程（Code-as-Workflow）：用通用编程语言的控制流作为建模语言，表达能力最强
  • 业务状态与执行状态：订单“已批准”是业务事实，Activity“第 2 次尝试超时”是运行时事实，两者必须分层建模
  • 可达性/终止性验证：通过模型检查、属性测试和历史重放在部署前发现死锁、活锁、非法转换与兼容性缺陷

建模的必要性

工作流引擎让「实现」变得容易——用代码或配置描述流程即可。但「实现得正确」仍然困难：流程中是否有死锁？每条路径是否能进入可解释终态？外部效果未知时会不会被误判为失败？取消到达时哪些步骤必须完成清理？这些问题靠流程图和代码审查都难以穷尽。工作流建模的目标是先写出状态、不变式和失败语义，再选择能够执行它们的表示法。

建模不是为了装饰文档，而是为了在部署之前生成可证伪的问题：不可达步骤、永远不满足的条件、缺少补偿的分支、无限循环、重复信号、超时与完成竞争，以及“外部效果已发生但回执未知”的状态。

三种建模范式

工作流建模有三种主流范式，每种对应不同的引擎实现风格：

范式 核心抽象 适合场景 对应引擎
状态机（FSM） 状态 + 转换 + 事件 步骤少、状态明确的审批流 AWS Step Functions、XState
有向无环图（DAG） 节点 + 边 + 依赖 数据管道、批处理 Airflow、Dagster、Prefect
代码即流程（Code-as-Workflow） 普通代码 + 持久化运行时 复杂业务逻辑、动态流程 Temporal、Durable Functions

每种范式的表达能力不同。状态机在有限状态下能精确验证不变式，但难以表达动态并发；DAG 天然表达依赖关系和并行机会，但不支持循环；代码即流程的表达能力最强（图灵完备），但也最难做静态分析。

状态机建模

有限状态机（FSM）将流程建模为一组离散状态和状态之间的转换。每个状态代表流程的一个阶段，转换由事件触发：

stateDiagram-v2
    [*] --> 待审批: 提交申请
    待审批 --> 审批中: 分配审批人
    审批中 --> 已通过: 审批通过
    审批中 --> 已拒绝: 审批拒绝
    审批中 --> 待审批: 退回修改
    已通过 --> 执行中: 开始执行
    执行中 --> 已完成: 执行成功
    执行中 --> 已失败: 执行失败
    已失败 --> 执行中: 重试
    已完成 --> [*]
    已拒绝 --> [*]

状态机建模的优势在于可验证性。对于一个有 N 个状态的 FSM，可以形式化检查：

  • 可达性（Reachability）：从初始状态出发，是否所有状态都可以到达？
  • 终止性（Termination）：是否所有路径最终都能到达终态？是否存在活锁？
  • 安全性（Safety）：是否存在从「已通过」直接到「已拒绝」的非法转换？
  • 完整性（Completeness）：每个状态对每个可能的事件是否都定义了响应？

状态机的局限在于「状态爆炸」：当流程有并发路径时，状态数量按指数增长。两个并行的 3 步子流程，组合后有 3×3=93 \times 3 = 93×3=9 种可能的状态组合。实际系统中 5-6 个并行路径就会让状态机不可维护。

DAG 建模

DAG 将流程建模为一组带依赖关系的任务节点。每个节点是一个计算步骤，边表示数据或控制依赖：

graph TD
    A[提取原始数据] --> B[清洗数据]
    A --> C[获取汇率]
    B --> D[转换货币]
    C --> D
    D --> E[计算报表]
    D --> F[生成图表]
    E --> G[合并输出]
    F --> G
    G --> H[发送邮件]

DAG 建模的核心优势是天然表达并行机会——没有依赖边连接的节点可以并行执行。调度器通过拓扑排序确定执行顺序，通过关键路径分析确定流程的最短执行时间。

DAG 建模时关注的指标：

  • 关键路径长度：流程的最小执行时间由最长依赖链决定
  • 并行度：同时可执行的最大任务数，决定资源需求
  • 扇入/扇出比：高扇出节点是性能瓶颈候选，高扇入节点是同步等待点

DAG 的定义要求无环，因此业务循环不能直接成为回边。某些 DAG 引擎把单节点重试、传感器或重新触发作为调度器元数据提供，但这不改变原图无环；当循环本身携带业务状态、人工输入或复杂终止条件时，状态机或代码即流程通常更诚实。

代码即流程建模

Temporal 等持久执行引擎的核心创新是：用普通编程语言的控制流作为流程建模语言。if/else 就是条件分支，for/while 就是循环，Promise.all 就是并行，try/catch 就是异常处理——工作流定义就是一段看起来像顺序代码的程序。

// 这段代码既是流程建模也是可执行的工作流定义
async function loanApproval(application: LoanApplication): Promise<Decision> {
  const score = await checkCreditScore(application.userId);

  if (score >= 750) {
    return { approved: true, rate: 3.5 };
  }

  if (application.amount > 500000) {
    // 人工审批，等待最长 7 天
    const approval = await waitForHumanApproval(application, '7 days');
    if (!approval) return { approved: false, reason: 'timeout' };
  }

  const risk = await assessRisk(application, score);
  return { approved: risk.level <= 3, rate: risk.suggestedRate };
}

这种范式的建模优势在于可组合性和可测试性——工作流定义就是函数，可以用普通的单元测试框架验证逻辑。但代价是失去了静态分析能力：图灵完备的语言无法被自动证明「一定会终止」或「不会进入死循环」。

把业务状态与运行时状态分开

最常见的建模缺陷是把技术尝试状态写进业务状态。例如“付款处理中”可能同时指代已向支付方发起请求、请求超时且结果未知、支付成功但回执尚未落库。它们需要不同处置，却被一个枚举吞掉。

可以把模型拆成两层：

层次 示例 权威所有者 允许的恢复动作
业务事实 PaymentCaptured、OrderCancelled 支付/订单 bounded context 补偿、后续业务转换
执行事实 attempt=2、receipt=unknown、deadlineAt 工作流引擎与 Activity 重试、查询、等待、人工升级

每个副作用节点至少要有四个结果：成功并有回执、明确失败、结果未知、被取消。把“未知”折叠进失败会造成重复扣款，把“取消请求已发送”折叠进“已取消”会造成资源泄漏。

模型中的不变式应写成可检查断言，例如：

  • 每个 PaymentCaptured 必须关联唯一的支付回执。
  • ShipmentCreated 之前必须存在有效库存预留。
  • 取消完成后不存在无所有者的运行中 Activity。
  • 任一非终态都有定时器、外部事件或可调度 Task 使其继续推进。

建模验证工具

不同范式有不同的验证手段：

范式 验证方法 工具 能发现的问题
状态机 模型检查 TLA+、Alloy 死锁、活锁、不变式违反
DAG 拓扑分析 引擎内置调度器 循环依赖、不可达节点
代码即流程 单元测试 + 重放测试 Temporal Test Framework 逻辑错误、非确定性
通用 BPMN 形式化分析 Camunda Modeler 未处理的结束事件

对于 Temporal 等代码即流程的引擎，验证策略是：

  1. SDK 隔离与代码审查：不同 SDK 对时间、随机数和模块导入的处理不同；只使用该 SDK 明确提供的重放安全 API，外部 I/O 放入 Activity。
  2. 重放测试：用开放中和已关闭实例的代表性事件历史验证新代码是否保持 Command 序列兼容。
  3. 属性测试：随机生成信号顺序、超时、重复回执与取消竞态，断言业务不变式始终成立。
  4. 故障注入：在副作用完成、完成回执持久化、补偿启动等边界杀死 Worker，验证未知结果能通过稳定幂等键收敛。

BPMN 与工程实践的桥梁

BPMN（Business Process Model and Notation）由 ISO/IEC 19510 标准化，适合让业务角色与工程团队共享流程词汇。它可以直接由 BPMN 引擎执行，也可以作为代码即流程实现的设计输入：

  • 任务（Task）：一个原子操作，对应 Activity
  • 网关（Gateway）：分支/合并点，分 XOR（排他）、AND（并行）、OR（包容）
  • 事件（Event）：起始、中间、结束事件，对应信号/定时器/错误
  • 泳道（Lane）：标识操作的执行者（哪个服务/角色）

从 BPMN 翻译到代码时必须补齐图上通常没有的运行时契约：Activity 幂等键、错误分类、总体期限、取消传播、回执 schema 和版本策略。BPMN 图与代码应共享状态名称和不变式，避免形成两套逐渐漂移的语言。

小结

工作流建模的三种范式各有适用场景：状态机适合状态和事件边界明确的流程，DAG 适合依赖主导的数据处理，代码即流程适合动态且长期的业务编排。选择方法时先写业务不变式，再区分业务状态与执行状态，最后采用足够但不过度的表达能力。前文的基础模式和编排 vs 协同提供了粒度与所有权判断框架。

截至 2026 年 8 月，Temporal 对 Command 兼容性和重放安全变更的权威说明见其 Workflow Definition；落地时应再核对所用语言 SDK 的具体安全 API。
