编排与协同的架构选择

核心概念

  • 编排（Orchestration）：中心化协调模式，编排器持有完整流程定义，主动驱动各参与服务执行
  • 协同（Choreography）：去中心化模式，各服务通过监听事件自主决定何时执行自己的操作
  • 流程可见性：能否从单一位置理解完整流程——编排天然具备，协同需要额外工具
  • 域内编排/域间协同：实践中最常见的混合模式，兼顾可靠性与解耦

两种流程协调范式

分布式系统中，多个服务协同完成一个业务流程有两种根本不同的协调方式：编排（Orchestration） 和 协同（Choreography）。前者有一个中心指挥者告诉每个参与者「该你了，做这个」；后者没有指挥者，每个参与者根据观察到的事件自主决定「轮到我了，我该做这个」。

这个选择不仅是技术偏好，而是对系统耦合度、可见性、故障处理方式的根本性决定。选错了，轻则开发效率低下，重则在生产环境中面对无法追踪的幽灵流程。

编排模式详解

编排模式中，一个中心化的编排器（Orchestrator）持有流程定义，按序驱动各参与服务执行：

sequenceDiagram
    participant O as 编排器
    participant A as 订单服务
    participant B as 支付服务
    participant C as 库存服务
    participant D as 物流服务
    O->>A: 创建订单
    A-->>O: 订单已创建
    O->>B: 发起支付
    B-->>O: 支付成功
    O->>C: 扣减库存
    C-->>O: 库存已扣
    O->>D: 创建发货单
    D-->>O: 发货单已创建

编排模式的核心特征：

  • 单点控制：编排器知道完整流程，每个参与服务只知道自己被调用时要做什么。
  • 显式流程定义：流程逻辑集中在编排器代码中，可以直接阅读和理解。
  • 显式命令与结果：编排器可通过同步调用、异步 Task、回调或事件驱动参与者，关键在于它拥有下一步决策，而不在于传输协议必须同步。

编排模式的典型实现包括 Temporal Workflow、AWS Step Functions、Azure Durable Functions——它们本质上都是提供了一个持久化的编排器运行时。

协同模式详解

协同模式中，没有中心编排器，每个服务监听事件并根据事件自主触发自己的操作：

sequenceDiagram
    participant A as 订单服务
    participant Bus as 事件总线
    participant B as 支付服务
    participant C as 库存服务
    participant D as 物流服务
    A->>Bus: OrderCreated
    Bus->>B: OrderCreated
    B->>Bus: PaymentCompleted
    Bus->>C: PaymentCompleted
    C->>Bus: InventoryReserved
    Bus->>D: InventoryReserved
    D->>Bus: ShipmentCreated

协同模式的核心特征：

  • 去中心化：没有任何一个节点知道完整流程，每个服务只知道「收到 X 事件后做 Y 并发出 Z 事件」。
  • 隐式流程：整体流程是所有参与者反应规则的涌现效果，不存在单一的流程定义。
  • 事件驱动通信：服务之间通过事件总线（Kafka、RabbitMQ、EventBridge）异步通信。

核心维度对比

维度 编排（Orchestration） 协同（Choreography）
耦合方向 参与者→编排器：逻辑耦合 参与者→事件契约：数据耦合
流程可见性 高：查看编排器代码即可理解全流程 低：需追踪多个服务的事件订阅
可用性依赖 引擎、存储与 Worker 构成控制面依赖 事件总线、消费者状态与契约共同构成依赖
变更影响面 改编排器即可调整流程 需协调多个服务同时变更
流程复杂度上限 高：条件/循环/补偿易表达 中：复杂逻辑难以用纯事件表达
服务自治 低：服务被编排器驱动 高：服务自主响应事件
调试效率 高：编排器有完整执行记录 低：需跨服务关联追踪
容量耦合 受引擎写入、队列与 Worker 容量共同限制 消费者可独立伸缩，但热点分区和积压会传播

决策框架

选择编排还是协同，关键看四个问题：

1. 流程是否有明确的「主人」？

如果一个业务流程有清晰的起点、终点和所有者（如「订单履约」归订单域），编排更自然——编排器就住在流程所有者的域内。如果流程是多个域平等协作的涌现行为（如「用户注册后各系统初始化」），协同更合适。

2. 谁拥有跨步骤不变式？

如果“支付成功前不能发货”“任一预留失败必须释放已成功预留”这类不变式有单一业务所有者，编排能把决策和证据集中在该边界。若各域只需独立响应一个已发生事实，没有跨域原子不变式，协同更自然。步骤数量只能提示复杂度，不能替代所有权判断。

3. 故障处理的要求？

需要跨步骤的超时、选择性补偿和统一人工升级：编排更容易形成闭环。容忍最终一致、每个消费者可独立重试并能从事件重建状态：协同可以降低跨域控制耦合。

4. 团队能否承担隐式流程的运营成本？

协同并不消除流程状态，只是把状态分散到事件日志、消费者偏移和各服务数据库。若没有统一的关联标识、事件目录、积压监控和重放工具，所谓“解耦”会变成无人拥有的故障面。

判断信号 更偏向编排 更偏向协同
流程所有者 单一 bounded context 对结果负责 多个域只订阅公共事实
不变式 需要跨步骤顺序、期限和补偿 各消费者可独立最终一致
变更方式 希望在一处修改决策图 希望新增消费者不改发布者
运营证据 需要单实例时间线和人工处置入口 能从事件目录与追踪重建全链路

混合模式：实践中的常见选择

生产系统很少纯粹使用一种模式。更常见的是域内编排、域间协同：

  • 一个业务域内部（如订单域）用编排模式处理自己的多步流程
  • 域之间通过事件进行松耦合的协同
  • 编排器完成本域流程后发出领域事件，其他域各自响应
graph TB
    subgraph 订单域-编排
        O[订单编排器] --> A[创建订单]
        O --> B[预留库存]
        O --> C[发起支付]
    end
    subgraph 事件总线-协同
        E[OrderCompleted 事件]
    end
    subgraph 通知域
        N[发送确认邮件]
    end
    subgraph 积分域
        P[增加积分]
    end
    C -->|完成| E
    E --> N
    E --> P

这种混合模式兼顾了两者的优势：域内流程有明确的编排器保证可靠推进与可见性，域间通过事件保持松耦合与自治。

编排的反模式

即使选择了编排，也要警惕以下退化模式：

上帝编排器（God Orchestrator）：一个编排器管理所有域的所有流程，变成了分布式单体。正确做法是每个域有自己的编排器。

持锁等待外部结果：在数据库事务或请求线程里同步等待远端步骤，既扩大故障半径又阻塞资源。应把等待转成持久 Task、回调或事件，把业务期限记录为引擎定时器。

泄漏的编排器（Leaking Orchestrator）：编排器复制参与域的实体模型和局部规则，成为另一个权威源。编排器应拥有跨步骤策略与流程状态；折扣计算等参与域不变式仍由该域完成，并通过稳定契约返回决策证据。

协同的反模式

隐式依赖链（Implicit Chain）：A→B→C→D 通过事件串联，但没有任何地方记录这个依赖链。解法是维护事件 schema、生产者与消费者目录、关联标识和所有者，而不是把消息主题当成架构文档。

事件风暴（Event Storm Loop）：服务 A 发事件触发 B，B 发事件触发 A，形成循环。解法：严格区分 Command 和 Event，避免事件触发回向命令。

把事件重放当成副作用重放：无论编排还是协同，恢复控制状态都不等于可以再次执行外部效果。协同消费者应使用 Inbox 去重或稳定事件 ID，发布者用事务 Outbox 保证本地状态与事件一致；补数据前先区分“重建投影”与“重新发起业务动作”。

跨域契约与故障所有权

混合架构要为每条跨域边界指定一个故障所有者。订单编排器可以决定何时放弃履约，却不应直接修改支付域账本；支付域返回带业务操作 ID 的收款回执，并提供按幂等键查询状态的接口。若回执未知，编排器进入“核对支付”步骤，而不是直接再次扣款。

协同事件也必须区分命令与事实。命令表达“希望某个所有者执行”，可能被拒绝；事件表达“权威状态已经改变”，订阅者不能借事件反向篡改发布者状态。这个区分让重试、补偿和权限边界都可以被测试。

对每个集成点记录以下四项即可形成最小契约：消息 ID 与因果 ID、schema 版本、幂等/去重窗口、失败后的升级所有者。没有这些信息，切换编排或协同都不会自动提高可靠性。

小结

编排与协同不是按步骤数选择的模板，而是对控制权、数据权威和故障所有权的安排。编排集中跨步骤决策，协同让各域围绕已发生事实自治；两者都需要幂等、版本化契约和可恢复证据。实践中的常见组合是域内编排、域间事件，但边界应由 bounded context 和业务不变式决定。下一节将讨论如何用形式化方法验证这些流程；上一节的基础模式则提供控制流原语。
