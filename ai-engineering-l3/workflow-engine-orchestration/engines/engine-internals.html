工作流引擎内核原理

核心概念

  • 事件日志（Event Log）：只追加的不可变日志，记录工作流实例执行过程中的每个外部效果
  • 确定性重放（Deterministic Replay）：从事件日志恢复状态的机制——重新执行代码，用历史值替代已完成的操作
  • Task Queue 拉模式：Worker 主动从 Server 拉取任务，天然具备背压和故障转移能力
  • History Shard：将工作流实例按哈希分散到多个分片，实现线性可扩展
  • 副作用回执（Effect Receipt）：目标系统对稳定操作 ID 返回的权威结果，用于把“结果未知”收敛为成功或明确失败
  • 尝试栅栏（Attempt Fencing）：用租约、epoch 或版本拒绝过期 Worker 的迟到写入，避免失联尝试与新尝试并发生效

引擎的本质问题

剥去各引擎的 API 差异和品牌包装，工作流引擎的内核解决的是同一个问题：如何让一段可能运行数天的代码，在进程崩溃、机器重启、网络中断后，精确地从断点恢复继续执行？

答案涉及事件历史持久化、重放或检查点恢复、任务调度和副作用协议的协作。前面三项恢复控制状态，最后一项处理外部世界已经改变但确认可能丢失的边界。忽略副作用回执，就会错误地把“控制流只观察一次完成”宣传成“业务效果精确一次”。

事件日志：持久执行的基石

工作流引擎的持久性保证建立在一个核心数据结构上——只追加的事件日志（Append-Only Event Log）。每个工作流实例有一个独立的事件日志，记录了执行过程中所有有意义的「发生过的事」：

事件类型 记录内容 触发时机
WorkflowStarted 输入参数 工作流创建
ActivityScheduled Activity 名称、输入 调度 Activity
ActivityCompleted Activity 返回值 Activity 成功
ActivityFailed 错误信息 Activity 失败
TimerStarted 到期时间 设置定时器
TimerFired — 定时器到期
SignalReceived Signal 名称、数据 外部信号到达
WorkflowCompleted 输出结果 工作流正常结束

事件日志的两个关键性质：

  1. 不可变性：事件一旦写入就不会被修改或删除，保证重放的确定性
  2. 有序性：事件按因果顺序编号，重放时按序回放

存储选型直接影响引擎的性能和可靠性。Temporal 自托管把历史写入配置的受支持持久化后端；Azure Durable Functions 可使用不同 Durable Task 存储提供方；Restate Server 则把 journal、状态与幂等元数据放在自己的分区化日志和物化存储中，应用服务保持无状态。不能因为某个运行时内部使用 RocksDB 就说日志嵌入了业务应用进程。

确定性重放：从日志恢复状态

持久执行的核心保证是：即使进程崩溃，工作流也能从断点精确恢复。实现机制是确定性重放（Deterministic Replay）：

graph TD
    A[Worker 崩溃] --> B[新 Worker 获取任务]
    B --> C[从 Server 拉取事件历史]
    C --> D[从头执行工作流代码]
    D --> E{遇到 Activity 调用?}
    E -->|历史中有结果| F[直接返回历史值]
    E -->|历史中无结果| G[这是新的调度,正常执行]
    F --> D
    G --> H[Activity 执行完成]
    H --> I[结果追加到事件历史]
    I --> D

重放的具体机制：

  1. 新 Worker 获取一个需要恢复的工作流任务
  2. 从 Server 下载该工作流的完整事件历史
  3. 从工作流函数的入口点开始执行代码
  4. 执行到每个 Activity/Timer/Signal 调用时，检查事件历史中是否已有该操作的结果
  5. 如果有已被 Service 确认的完成事件，直接返回历史结果——不重新执行该已确认步骤
  6. 如果没有（这是崩溃点之后的新操作），正常调度执行
  7. 当代码执行到与事件历史齐平的位置时，重放结束，进入正常执行模式

这个机制对工作流代码施加了一个根本约束：确定性 Command 序列。普通内存计算可以重复，产生 Timer、Activity、Child Workflow 等外部 Command 的顺序必须与历史兼容。如果第一次执行调度了 Activity，重放却在同一位置启动 Timer，引擎会报告非确定性，而不是继续写出自相矛盾的历史。

重放也不是唯一实现。Lambda durable functions 和 Restate 都使用检查点/journal 跳过已提交步骤，但具体协议不同。架构评审应问“哪个提交点定义步骤已经发生、旧尝试如何被拒绝、journal 保留多久”，而不是只看产品是否使用“Durable Execution”这个名字。

任务队列调度

在 Worker 驱动的引擎中，调度器通常让 Worker 长轮询 Task Queue。托管状态机直接调用云服务时可能没有用户可见的 Worker，因此拉模式不是所有产品的普遍规律。对 Temporal 这类架构，拉模式带来以下性质：

设计决策 拉模式选择 理由
负载均衡 Worker 有能力才拉 天然背压，不会过载
Worker 故障 任务留在队列中 其他 Worker 可接管
伸缩 加 Worker 即增吞吐 无需重新分配
任务路由 按 Task Queue 分类 不同类型任务隔离

调度器的两个关键任务：

Workflow Task 调度：当工作流有新事件需要处理时（Activity 完成、Signal 到达、Timer 触发），Server 向对应 Task Queue 投放一个 Workflow Task。Worker 拉取后执行工作流代码（可能触发新的 Activity 调度）。

Activity Task 调度：工作流代码调度一个 Activity 时，Server 向指定 Task Queue 投放一个 Activity Task。Activity Worker 拉取后执行实际的副作用操作。

拉模式只能形成接收侧背压，不能自动保护下游。Worker 有空闲槽位并不意味着支付 API 或数据库有容量；Activity 仍需并发限制、速率限制和下游错误预算。队列隔离也只有在配套独立 Worker 池与资源配额时才成立。

Shard 与多租户

为支持百万级并发工作流实例，引擎需要分片（Sharding）：

graph TB
    subgraph Temporal Server 集群
        FE[Frontend Service] --> H1[History Shard 1]
        FE --> H2[History Shard 2]
        FE --> H3[History Shard 3]
        FE --> HN[History Shard N]
    end
    H1 --> DB[(持久化存储)]
    H2 --> DB
    H3 --> DB
    HN --> DB

    subgraph Worker 池
        W1[Worker 1]
        W2[Worker 2]
        W3[Worker 3]
    end
    H1 -.-> W1
    H2 -.-> W2
    H3 -.-> W3

Temporal 的分片模型：

  • 每个 Workflow 实例通过 Workflow ID 的哈希被分配到一个 History Shard
  • 每个 Shard 由集群中的一个 History 节点负责
  • 一个 History 节点可负责多个 Shard，具体 Shard 数是部署级容量决策，不能照抄示例默认值
  • 节点故障时，其负责的 Shard 被重新分配给其他节点

分片提供并行处理单元，但不保证线性扩展。热点 Workflow、存储写入延迟、Matching、Visibility 和网络都可能先成为瓶颈；某些引擎的 Shard 数还在集群初始化时固定。容量结论必须来自目标拓扑的负载测试。

Timer 实现

定时器是工作流引擎区别于普通任务队列的核心能力之一。引擎中定时器的实现原理：

  1. 工作流代码执行 sleep(duration) 或 waitForTimeout(duration)
  2. Server 在事件历史中记录 TimerStarted{fireAt: now + duration}
  3. Server 通过持久化定时任务索引或等价机制发现到期项
  4. 到期时，Server 投放一个 Workflow Task，触发工作流继续执行
  5. 工作流代码在重放时遇到 TimerFired 事件，从 sleep 返回

关键设计：定时器等待期间不消耗任何计算资源——没有进程在等待，没有线程在阻塞。状态完全持久化在 Server 端。一个定时器可以等待数秒到数年，成本相同。

不同引擎可能使用时间分桶、有序索引或数据库任务队列。用户可依赖的是“等待不占用应用 Worker 线程且到期会产生可恢复事件”，不能依赖未公开的内部数据结构或复杂度。

Activity 交付与副作用回执

网络分区可能导致 Activity Worker 完成了外部写入但 Service 未收到确认。多数可重试 Activity 因此是至少一次尝试：引擎可保证 Workflow 最终只观察一个成功结果，却不能保证 Activity 函数体或其中的部分效果只执行一次。

  • Activity Heartbeat：长时间 Activity 定期向 Server 发心跳，Server 据此判断 Worker 是否存活
  • Schedule-to-Start Timeout：Activity 任务在队列中等待的最大时间
  • Start-to-Close Timeout：Activity 开始执行到完成的最大时间
  • Heartbeat Timeout：两次心跳之间的最大间隔

超时后 Server 认为 Worker 失败，重新调度 Activity。因此 Activity 实现必须是幂等的——可能被执行多次但效果等同于执行一次。

生产级协议应包含：

sequenceDiagram
    participant W as Workflow
    participant A as Activity Worker
    participant P as 支付服务
    W->>A: charge(operationId, amount)
    A->>P: PUT /charges/operationId
    P-->>A: receiptId, status=committed
    Note over A: Worker 可能在上报前崩溃
    W->>A: 重试同一 operationId
    A->>P: GET /charges/operationId
    P-->>A: 同一 receiptId
    A-->>W: 返回权威回执

目标系统应把幂等键与结果在同一事务边界写入。若目标不支持幂等写入，Activity 需要自有操作账本与状态查询，但账本和外部效果之间仍可能存在双写缝隙，此时只能通过对账、补偿或人工处置收敛，不能虚构精确一次。

对长 Activity，Heartbeat 既是存活信号也可携带恢复进度；取消通常在 Heartbeat 或 SDK 取消感知点交付。租约型外部任务还应携带单调 epoch，目标端拒绝旧 epoch 的迟到写入，防止“已被判死的 Worker”在网络恢复后继续提交。

Restate：新一代引擎设计

Restate 展示了另一种服务集成方式：业务 handler 仍以普通 HTTP 服务部署，Restate Server 持有 invocation journal、幂等元数据、状态和定时器。handler 通过 Context 提交 durable action；失败后 Server 带着 journal 重新调用，SDK 跳过已有结果。架构要点不是“日志在应用本地”，而是服务端对提交点和尝试 epoch 的控制。

维度 Temporal Restate
应用执行单元 独立 Worker 轮询 Task Queue 普通服务 handler 被 Restate 调用
持久控制状态 Temporal Service 的 Workflow History Restate Server 的 invocation journal 与状态
已提交步骤 Event 与 Command 匹配后重放 journal 命中后跳过执行并返回记录结果
迟到尝试 Task 超时与重新派发，外部效果仍需幂等 单调 epoch 拒绝 superseded attempt 的 journal 写入
外部副作用 Activity 幂等键与回执 run 等 durable action 仍需理解目标副作用边界

安全与多租户边界

事件历史会持久化 Workflow、Activity、Signal、错误等输入输出，因此天然属于敏感数据面。生产部署至少需要传输加密、客户端/Worker 身份认证、按 Namespace 或租户授权、载荷加密、保留期与删除策略。Temporal 自托管若不配置 Authorizer，官方文档明确指出默认 noopAuthorizer 会允许所有可达 API 请求，不能把 VPC 可达性当成完整授权。

Namespace 提供标识和配置隔离，但同一 Namespace 仍可由多个应用共享。强租户隔离还要配合独立凭据、Task Queue 命名、速率/并发配额、Search Attribute 访问控制和审计。对于不能让控制面看到的载荷，应在 Client/Worker 侧用 Payload Codec 加密；Web UI 解密端点本身是高权限系统，也必须单独鉴权。

小结

工作流引擎的内核由持久历史、重放/检查点、任务调度和副作用协议共同组成。前三者让控制流跨故障恢复；幂等回执、尝试栅栏、取消与人工对账让外部世界收敛。理解这些边界，有助于在使用 Temporal 或云原生方案时判断何时 Continue-As-New、何时隔离 Worker，以及哪些“精确一次”仍需业务系统证明。

截至 2026 年 8 月，本节对 Temporal Activity 至少一次边界的描述依据 Activity Definition，安全边界依据 Self-hosted security与 Payload encryption，Restate 架构依据其 Architecture。
