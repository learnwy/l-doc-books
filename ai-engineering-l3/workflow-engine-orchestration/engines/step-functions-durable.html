云原生编排服务：Step Functions 与 Durable Functions

核心概念

  • Amazon States Language（ASL）：Step Functions 的 JSON DSL，用状态和转换定义工作流
  • Standard vs Express Workflow：持久历史与高吞吐之间的执行模式选择；保证针对工作流执行，不自动覆盖所有下游副作用
  • Lambda durable functions：Lambda 内的代码优先检查点与重放方案，与 Step Functions 并存
  • 零运维编排：云厂商全托管，无需运维集群和存储，代价是受限于特定云生态

云厂商的编排策略

AWS、Azure、Google Cloud 都提供托管的工作流编排服务，但不能简单归为 DSL：Step Functions 与 Google Cloud Workflows 以声明式状态机为主，Azure Durable Functions 和 Lambda durable functions 则把检查点与重放嵌入通用语言。全托管减少了控制面运维，却把配额、版本、身份、数据驻留和服务集成约束纳入云平台边界。

AWS Step Functions

Step Functions 用 Amazon States Language（ASL）——一种 JSON DSL——定义状态机。每个状态（State）是流程中的一步，状态之间的转换由规则驱动：

状态类型 用途 对应工作流模式
Task 调用 Lambda/ECS/API Activity 执行
Choice 条件分支 排他网关
Parallel 并行分支 并行网关
Map 动态扇出 集合并行处理
Wait 定时等待 定时器
Pass 数据转换 变量赋值
Succeed/Fail 终态 流程结束

Step Functions 提供两种工作流类型：

  • Standard Workflow：持久保存状态与详细执行历史，AWS 将其描述为“exactly-once workflow execution”；显式 Retry 仍会再次运行 Task，外部 API 也必须按自身契约处理重复和未知结果。
  • Asynchronous Express Workflow：高吞吐、至少一次工作流执行；每个下游写入必须幂等。
  • Synchronous Express Workflow：请求等待结果且 AWS 文档将其描述为至多一次工作流执行；至多一次意味着可能不执行，不是更强的业务成功保证。
{
  "Comment": "订单处理",
  "StartAt": "ValidateOrder",
  "States": {
    "ValidateOrder": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:validateOrder",
      "Next": "CheckAmount"
    },
    "CheckAmount": {
      "Type": "Choice",
      "Choices": [
        {
          "Variable": "$.amount",
          "NumericGreaterThan": 10000,
          "Next": "ManualApproval"
        }
      ],
      "Default": "ProcessPayment"
    },
    "ManualApproval": {
      "Type": "Task",
      "Resource": "arn:aws:states:::sqs:sendMessage.waitForTaskToken",
      "TimeoutSeconds": 86400,
      "Next": "ProcessPayment"
    },
    "ProcessPayment": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:processPayment",
      "End": true
    }
  }
}

AWS Lambda durable functions

2026 年 AWS 推出了 Lambda Durable Functions——直接在 Lambda 内部实现持久执行，将工作流定义从 JSON DSL 回归到代码：

graph TB
    subgraph Step Functions 模式
        DSL[JSON ASL 定义] --> SF[Step Functions 服务]
        SF --> L1[Lambda A]
        SF --> L2[Lambda B]
        SF --> L3[Lambda C]
    end
    subgraph Durable Functions 模式
        DF[Lambda 内代码定义] --> RT[Durable 运行时]
        RT --> A1[Activity A]
        RT --> A2[Activity B]
        RT --> A3[Activity C]
    end

Lambda Durable Functions 的核心选型考量：

维度 Step Functions Lambda Durable Functions
编程模型 JSON DSL（ASL） 代码优先（Node.js、Python、Java、.NET 等受支持运行时）
流程可视化 原生可视化编辑器 无内置可视化
服务集成 优化的 AWS 服务集成 通过代码或 SDK 调用
运维负担 全托管，零运维 Lambda 内托管
长期执行 Standard 面向长流程 执行超时可配置，当前上限为一年
最适场景 跨多 AWS 服务编排 Lambda 内应用级流程
调试体验 Web Console 执行历史 IDE + 单元测试
版本管理 JSON diff 难读 代码 diff 清晰

Lambda durable function 的每次执行必须使用版本、别名或 $LATEST 等限定标识；生产应使用不可变编号版本或受控别名，使运行中的执行继续绑定到启动时的代码版本。它的 step 默认仍是至少一次执行，已检查点完成的 step 在重放时复用结果，但完成前失败的 step 必须幂等。执行名称可为启动请求提供幂等性，事件源映射则不会自动为每次投递复用同一个执行。

选择建议：如果流程主要是协调 AWS 服务并需要可视化状态机、跨服务连接器与声明式 IAM，Step Functions 更直接。如果主要复杂度位于一个 Lambda 应用中的条件、循环和本地代码结构，durable function 更自然。二者可以混合，但要明确哪一层拥有重试，避免 Lambda SDK、Step Functions 和下游客户端同时重试形成乘法放大。

Azure Durable Functions

Azure Durable Functions 是最早将「代码即流程」引入 Serverless 的方案（2017 年），比 AWS 的同名方案早了数年。它在 Azure Functions 的基础上增加了编排能力：

  • Orchestrator Function：编排函数，类似 Temporal 的 Workflow——持久化状态，支持 await、循环、条件分支
  • Activity Function：执行实际工作的函数，类似 Temporal 的 Activity
  • Entity Function：有状态的实体，支持 Actor 模式
// Azure Durable Functions 隔离 Worker 模型的示意代码
[Function(nameof(OrderOrchestrator))]
public static async Task<OrderResult> OrderOrchestrator(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var order = context.GetInput<Order>()!;

    // Activity 调用——结果被持久化
    var payment = await context.CallActivityAsync<Payment>(
        nameof(ProcessPayment), order);

    // 此处只示意外部事件；生产代码应另与 durable timer 竞争
    var approved = await context.WaitForExternalEvent<bool>("ApprovalEvent");

    if (!approved)
    {
        await context.CallActivityAsync(nameof(RefundPayment), payment.Id);
        return new OrderResult { Status = "Cancelled" };
    }

    await context.CallActivityAsync(nameof(ShipOrder), order.Id);
    return new OrderResult { Status = "Completed" };
}

Durable Functions 通过历史重放恢复 Orchestrator，并支持多种存储提供方。当前官方版本策略可把版本永久关联到编排实例，并用 Strict 或默认的 CurrentOrOlder 等匹配策略约束 Worker；移除旧代码前必须确认旧版本实例已经终止。仍在使用 .NET in-process 模型的团队还需注意官方给出的 2026 年 11 月 10 日支持终止日期，并迁移到 isolated worker 模型。

Google Cloud Workflows

Google Cloud Workflows 采用 YAML DSL 定义流程，定位介于 Step Functions 和 Temporal 之间：

  • 支持条件分支、循环、并行步骤
  • 原生集成 Google Cloud 服务
  • 内置 HTTP 连接器，可调用任意 REST API

选型决策树

按以下顺序回答问题，逐步缩小选择范围：

  1. 是否必须让同一 Worker 代码跨云运行？ → 是：优先评估独立持久执行平台；只要求调用跨云 HTTP API 并不足以排除托管服务
  2. 是否全 AWS 技术栈？ → 是：Step Functions（声明式跨服务）或 Lambda durable functions（代码优先）
  3. 是否全 Azure 技术栈？ → 是：Azure Durable Functions
  4. 流程是否需要长期保留多个 Worker 代码版本？ → 核对平台的版本固定、排空和回滚模型，而不是只看 DSL 表达能力
  5. 团队是否愿意承担控制面和持久化存储运维？ → 否：优先托管方案，同时接受其配额、区域和身份边界

无论选择哪种产品，都要逐项验证：启动请求如何去重、单步是什么投递语义、完成回执保存在哪里、取消是否能到达正在运行的任务、历史保存多久、旧代码何时可下线、租户数据如何加密与授权访问。

小结

云厂商服务把控制面运维交给平台，但不会替应用完成端到端幂等、业务授权和版本迁移。声明式状态机与代码优先检查点并非高低关系，它们让不同所有者承担变化成本。选型应围绕执行语义、版本固定、可观测证据、租户边界和退出成本，而不是用步骤数量或主观“表达能力”排序。前文的 Temporal/Cadence 深入了代码优先范式，下一节将剖析共享的内核原理。

截至 2026 年 8 月，本节的 AWS 事实依据 Step Functions execution guarantees、Lambda durable functions 与 Step Functions 对比及 durable step 幂等语义；Azure 版本事实依据 Orchestration versioning。
