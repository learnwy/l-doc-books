Temporal 与 Cadence 持久执行平台

核心概念

  • 持久执行（Durable Execution）：引擎保证工作流代码执行到完成，无论进程崩溃、网络中断还是服务器重启
  • 事件溯源重放（Event Sourcing Replay）：通过记录每个外部效果并重放来恢复工作流状态
  • 确定性约束：Workflow 代码在相同输入下必须产生相同执行路径，否则重放会失败
  • Activity：执行外部副作用的函数；已被 Service 确认的完成结果会在重放时复用，但确认前失联的尝试可能再次执行

起源与演进

Cadence 起源于 Uber 的微服务编排实践，Temporal 随后从同一技术谱系发展出独立的平台与多语言 SDK。二者都用持久事件历史和确定性重放恢复 Workflow，但 API、部署能力和版本演进机制已经各自发展，不能把面向某一平台的新接口直接套到另一平台。

截至 2026 年 8 月，Temporal 官方文档已经包含 Worker Deployment Version、Pinned/Auto-Upgrade Workflow、Serverless Workers、Standalone Activities 和 Workflow Streams 等能力。时效性最强的是 Worker Versioning：官方生产指南将它作为大多数团队部署 Workflow 变更的首选，补丁机制则用于无法保留多版本 Worker或采用自动升级的场景。

核心编程模型

Temporal 的编程模型建立在两个核心抽象之上：

概念 职责 确定性/交付边界 生命周期
Workflow 持有流程状态并产生定时、Activity、子流程等 Command 相同历史必须产生兼容的 Command 序列 可跨多个 Worker 和代码部署
Activity 执行 API、数据库、文件等副作用 普通代码；一次逻辑调用可能对应多次尝试 受总体期限、单次超时和重试策略约束
Task Service 派发的一次 Workflow/Activity 执行机会 一个 Task 尝试只交给一个 Worker，失败后可重新派发 短暂、可租约式恢复
Worker 轮询 Task Queue 并承载某个代码版本 必须声明自己能执行的 Workflow/Activity 类型 可替换进程，部署版本需受控
Temporal Service 持久化历史、计时、匹配任务和可见性元数据 不执行用户的 Activity 业务代码 高可用控制面

Workflow 看起来像普通函数，但真正的契约是：给定同一历史，应产生兼容的 Command 序列。Activity 是执行实际工作的地方，可以读取外部状态；不过它默认面对至少一次尝试边界，不能因为“完成结果最终会进入历史”就省略幂等设计。

// Workflow 定义——确定性代码
export async function orderWorkflow(order: Order): Promise<OrderResult> {
  // Activity 调用通过代理，结果被持久化
  const payment = await chargeCard(order.cardToken, order.amount);

  // 条件分支——确定性的，因为 payment 来自事件历史
  if (payment.requiresVerification) {
    const verified = await waitForVerification(order.id, '24 hours');
    if (!verified) {
      await refundPayment(payment.id);
      return { status: 'cancelled', reason: 'verification_timeout' };
    }
  }

  await reserveInventory(order.items);
  await createShipment(order.id);
  return { status: 'completed', paymentId: payment.id };
}

事件溯源与重放机制

Temporal 的持久性保证建立在事件历史与重放之上：Workflow 的 Command 及其结果被记录为事件。当 Worker 进程崩溃后，Service 把历史交给可用 Worker；Workflow 代码从入口重新求值，在遇到已确认的 Activity 完成事件时复用结果，而不是再次发起该已确认步骤。

sequenceDiagram
    participant W as Workflow Worker
    participant S as Temporal Server
    participant A as Activity Worker

    Note over W,S: 首次执行
    W->>S: 调度 Activity: chargeCard
    S->>A: 派发任务
    A-->>S: 结果: {paymentId: "p123"}
    S-->>W: Activity 完成,结果记入历史

    Note over W,S: Worker 崩溃后重放
    W->>S: 拉取事件历史
    S-->>W: [WorkflowStarted, ActivityScheduled, ActivityCompleted{paymentId: p123}]
    Note over W: 重放代码到 chargeCard 调用点
    Note over W: 直接返回历史中的结果 {paymentId: "p123"}
    Note over W: 从断点继续执行后续逻辑

事件历史是一个只追加的日志，存储在 Temporal Service 配置的持久化后端。关键设计：

  • 每个 Workflow 实例有独立的事件历史，互不干扰
  • 事件是不可变的——一旦写入不会修改，保证重放的确定性
  • 事件历史有保护上限：当前官方文档给出的限制是 51,200 个事件或 50 MB，并在 10,240 个事件或 10 MB 发出警告；长期流程应在到达警告前 Continue-As-New

这个机制只证明“Service 已确认的 Activity 完成会在 Workflow 视角观察一次”。若 Activity 已扣款但 Worker 在上报成功前崩溃，历史没有完成事件，下一次尝试仍会执行。生产 Activity 应把稳定幂等键交给目标服务，并返回其业务回执；结果未知时先查询同一键，而不是创建新键重试。

确定性约束与违规检测

Temporal 最严格的约束不是“每行纯函数”，而是重放时产生的 Command 必须和历史兼容。不同 SDK 对时间、随机数和隔离沙箱的 API 不同，因此应以所用 SDK 文档为准：

操作 风险 可靠做法
本地时钟、随机数、环境变量参与分支 重放可能选择另一条 Command 路径 使用 SDK 明确标记为重放安全的时间、随机或 Side Effect API
HTTP、数据库、文件、LLM 调用 外部结果随时间变化并产生副作用 放入 Activity，结果与错误由历史记录
新增、删除或重排 Activity/Timer/Child Workflow Command 序列与旧历史不匹配 Worker Versioning 或 patch/version API
无序来源影响分支 迭代顺序可能改变 Command 序列 在 Workflow 内先稳定排序或规范化

SDK 的隔离、构建检查能提前阻止一部分不安全依赖，最终门仍是历史重放。当当前代码产生的 Command 与已有事件不匹配时，Worker 报告非确定性错误；运行中的实例不会靠猜测继续。

Task Queue 与 Worker 架构

Temporal 采用拉模式（Pull-based）的任务分发架构：

graph LR
    S[Temporal Server] --> TQ1[Task Queue: orders]
    S --> TQ2[Task Queue: payments]
    S --> TQ3[Task Queue: notifications]
    TQ1 --> W1[Worker Pod 1]
    TQ1 --> W2[Worker Pod 2]
    TQ2 --> W3[Worker Pod 3]
    TQ3 --> W4[Worker Pod 4]
    TQ3 --> W5[Worker Pod 5]
  • Task Queue：逻辑通道，Worker 从中拉取任务。不同的 Activity 类型可以分配到不同的 Task Queue，实现资源隔离。
  • Worker：可替换进程，注册 Workflow 和 Activity 实现，并可持有仅用于加速的 Sticky Workflow 缓存。多个 Worker 从同一 Task Queue 竞争 Task；某次 Task 尝试只由一个 Worker 获取，但超时或连接丢失后可重新派发。
  • Sticky Execution：Workflow 任务倾向于分配给上次执行它的 Worker（利用本地缓存的 Workflow 状态），减少重放开销。

Task Queue 名称不是安全边界，也不会自动提供资源配额。若希望隔离 CPU 密集 Activity、低优先级批处理或不同租户，需要把队列、Worker 池、速率限制和扩缩容策略一起配置，并监控 backlog age 与 schedule-to-start latency。

Signal、Query 与 Update

Temporal 提供三种与运行中 Workflow 交互的方式：

交互方式 方向 语义 典型用途
Signal 外部→Workflow 异步通知，改变 Workflow 状态 人工审批结果、外部事件通知
Query 外部→Workflow 只读查询，不改变状态 获取当前进度、状态报告
Update 外部→Workflow 同步请求-响应，可改变状态 需要即时确认的操作

Signal 是实现人工介入环节的核心机制——外部系统（如审批 UI）通过 Signal 通知 Workflow「审批通过了」，Workflow 从等待状态恢复继续执行。Query 用于实时展示工作流进度而不干扰执行。

三种消息都需要业务级授权和去重。Service 能把消息送到指定 Workflow，不代表调用者有权批准该订单；Handler 应验证不可伪造的审批主体、决策版本和请求 ID，并让重复 Signal/Update 返回同一业务结果。Query 必须保持只读，不能偷偷写外部系统。

重试、超时与取消的责任链

Activity 的超时不是同一个旋钮：Schedule-To-Close 覆盖排队与全部尝试，Start-To-Close 限制单次尝试，Schedule-To-Start 反映队列等待，Heartbeat Timeout 用于发现长任务失联并携带进度。永久业务拒绝应标记为不可重试；暂时性依赖错误才适合指数退避。

取消是协作式的。普通 Activity 通常需要发送 Heartbeat 才能及时收到取消请求；未实现取消感知的外部调用可能在 Workflow 已取消后继续产生效果。长任务应定义取消点、心跳进度和清理语义，Workflow 则要区分“已请求取消”“Activity 已确认停止”和“业务补偿完成”。

Temporal Cloud 与自托管

部署方式 运维责任 适合规模 成本模型
Temporal Cloud Temporal 公司运维 Server 中小团队 按 Action 计费
自托管 团队自行运维 大规模/合规要求 基础设施成本

自托管时，Temporal Server 集群包含 Frontend、History、Matching 和内部 Worker 等服务角色，并连接受支持的持久化存储；Visibility 可按部署选择 SQL 或专用搜索后端。应用 Worker 不属于 Server 集群，应独立部署、扩缩容和版本化。

小结

Temporal/Cadence 通过持久历史与重放恢复 Workflow 控制状态，但外部副作用仍由 Activity、幂等键和目标系统回执共同保证。Task Queue 与 Worker 让执行资源可替换和伸缩，Worker Versioning 则决定长期实例应落到哪版代码。Signal、Query、Update提供交互入口，但业务鉴权与去重仍由应用负责。后续将对比云厂商的编排服务，并进入引擎内核的通用实现。

本节时效性事实依据 Temporal 官方的 Workflow Definition、Activity Definition、Workflow limits 与 Worker Versioning；截至 2026 年 8 月核对。
