Saga 补偿模式在工作流引擎中的实现

核心概念

  • 引擎托管 Saga：工作流引擎接管 Saga 的状态持久化、步骤重试、超时管理和崩溃恢复，开发者只需编写正向和补偿逻辑
  • 补偿栈（Compensation Stack）：按注册顺序的反向执行补偿操作的数据结构
  • 幂等补偿：补偿操作必须幂等——可能因网络超时被重试多次，效果应等同于执行一次
  • 不可补偿步骤：某些操作无法语义撤销（如已发邮件），需通过后置、预留-确认或人工升级处理

从手写 Saga 到引擎托管 Saga

在没有工作流引擎的世界里，实现 Saga 模式需要开发者手动处理：状态持久化、补偿触发、重试、超时和恢复。引擎能够接管这些控制面机制，但不能替业务定义“什么算补偿成功”，也不能替外部系统生成幂等回执。

工作流引擎接管 Saga 的持久控制状态、定时器和 Task 重派发。应用仍需负责正向操作、补偿操作、幂等键、未知结果查询、业务期限与人工升级。把这些责任全部归给引擎，会在第一次“外部写入成功但完成回执丢失”时暴露双重效果。

Temporal 中的 Saga 实现

在 Temporal 中，Saga 不需要特殊的 SDK 或框架——它就是普通的 try/catch 代码加上一个补偿栈：

async function orderSaga(order: Order): Promise<SagaResult> {
  const compensations: Array<() => Promise<EffectReceipt>> = [];
  const compensationFailures: unknown[] = [];

  try {
    // Step 1: 创建订单
    const orderOperation = operationId('create-order');
    compensations.push(() => cancelOrder(orderOperation));
    const orderReceipt = await createOrder(orderOperation, order);

    // Step 2: 扣减库存
    const inventoryOperation = operationId('reserve-inventory');
    compensations.push(() => releaseInventory(inventoryOperation));
    const inventoryReceipt = await reserveInventory(inventoryOperation, order.items);

    // Step 3: 扣款
    const paymentOperation = operationId('charge-payment');
    compensations.push(() => refundPayment(paymentOperation));
    const paymentReceipt = await chargePayment(paymentOperation, order.userId, order.amount);

    // Step 4: 创建发货单
    await createShipment(operationId('create-shipment'), orderReceipt.orderId);
    // 最后一步不需要补偿——如果它成功了 Saga 就完成了

    return { status: 'completed', orderId: orderReceipt.orderId };
  } catch (error) {
    // 反向执行所有已注册的补偿
    for (const compensate of compensations.reverse()) {
      try {
        await compensate();
      } catch (compError) {
        // 收集失败；所有补偿尝试结束后进入人工处置，不能谎报 compensated
        compensationFailures.push(compError);
      }
    }
    if (compensationFailures.length > 0) {
      return { status: 'manual_intervention', failures: compensationFailures };
    }
    return { status: 'compensated', cause: failureSummary(error) };
  }
}

示例故意在正向操作前注册补偿，并让正向与补偿共享稳定 operationId。原因是正向 Activity 超时只能说明完成回执未知，不能证明外部效果没有发生；补偿必须能够按同一个操作 ID 查询并撤销已存在的效果，对明确不存在的效果则安全返回“无需补偿”。

补偿栈的设计模式

在工作流引擎中实现 Saga 补偿有三种常见模式：

模式 实现方式 优势 适用场景
内联补偿栈 try/catch + 数组 简单直观 步骤 ≤5 的简单 Saga
Saga 类封装 专用类管理补偿注册 可复用，强类型 通用 Saga 模板
子工作流补偿 每步是子工作流 独立生命周期 超长时间步骤

Saga 类封装模式的典型实现：

class SagaBuilder {
  private steps: Array<{
    forward: () => Promise<unknown>;
    compensate: () => Promise<void>;
  }> = [];

  addStep(forward: () => Promise<unknown>, compensate: () => Promise<void>) {
    this.steps.push({ forward, compensate });
    return this;
  }

  async execute(): Promise<void> {
    const registered: typeof this.steps = [];

    for (const step of this.steps) {
      registered.push(step);
      try {
        await step.forward();
      } catch (error) {
        // 反向核对并补偿所有可能已产生效果的步骤
        for (const done of registered.reverse()) {
          await done.compensate();
        }
        throw error;
      }
    }
  }
}

引擎如何保证补偿的可靠性

工作流引擎为 Saga 补偿提供了手写代码难以实现的可靠性保证：

graph TD
    A[正向步骤执行] --> B{步骤成功?}
    B -->|是| C[记录到事件历史]
    C --> D[继续下一步]
    B -->|否| E[进入补偿流程]
    E --> F[从补偿栈取最后一项]
    F --> G[执行补偿 Activity]
    G --> H{补偿成功?}
    H -->|是| I[记录补偿完成]
    I --> J{还有待补偿?}
    J -->|是| F
    J -->|否| K[Saga 补偿完成]
    H -->|否| L[重试补偿]
    L --> G

关键保证：

  1. 补偿意图可持久恢复：Worker 崩溃后，引擎能依据历史继续调度尚未确认完成的补偿。
  2. 已确认完成在 Workflow 中只观察一次：重放会复用完成事件；完成上报前失联的补偿 Activity 仍可能再次尝试。
  3. 补偿有独立策略：退款、释放预留等操作应根据业务期限设置错误分类、退避和最大尝试，而不是复制正向步骤配置。
  4. 补偿失败有明确终态：达到预算后进入 manual_intervention，保留正向与补偿回执，交给指定所有者处理。

补偿设计的关键原则

在工作流引擎中设计补偿操作时，需遵循以下原则：

幂等性（Idempotency）：补偿操作必须幂等——执行一次和执行多次的效果相同。典型做法是以 Saga 实例 ID、步骤 ID 和动作类型组成幂等键，并让目标系统返回稳定回执。补偿不能每次重试生成新的退款请求 ID。

依赖显式化：只有证明两个补偿互不依赖时才能并行。反向顺序是安全起点，不是形式保证；退款和释放库存是否可交换，应由业务不变式和目标系统并发语义证明。

语义正确性：补偿不是「撤销」，而是「产生等价的逆效果」。退款不是删除支付记录，而是创建一笔新的退款交易。这保证了审计轨迹的完整性。

并行 Saga 模式

当 Saga 中的某些步骤相互独立时，可以并行执行以缩短总耗时，但补偿逻辑变得更复杂：

graph TD
    A[开始订单 Saga] --> B[创建订单]
    B --> C[并行执行]
    C --> D[扣减库存]
    C --> E[扣款]
    C --> F[预约配送时间]
    D --> G[等待所有完成]
    E --> G
    F --> G
    G --> H{全部成功?}
    H -->|是| I[确认订单]
    H -->|否| J[补偿已成功的步骤]
    J --> K[根据成功集合选择性补偿]

并行 Saga 中，不能只补偿调用方收到“成功”的步骤，因为超时分支可能已经产生外部效果。每个并行步骤必须暴露按 operationId 查询结果的能力；汇合点先把成功、失败、未知分类，再对“成功或未知”执行核对与选择性补偿。Promise.allSettled 只收集调用结果，不能替代外部状态查询。

Saga 与工作流引擎的超时配合

工作流引擎的定时器能力让 Saga 的超时处理变得简洁：

超时场景 引擎处理方式 手写实现所需
单步超时 Activity startToCloseTimeout 定时器线程 + 状态检查
全局业务期限 Workflow durable timer + 显式期限状态 外部调度器 + 状态持久化
等待外部确认超时 condition(fn, timeout) 轮询 + 状态机
补偿操作超时 补偿 Activity 的总体期限、重试预算与人工升级 死信队列 + 告警

Workflow 级运行超时是平台保护，不应替代业务期限。平台超时可能直接终止执行，未必给补偿逻辑留下运行窗口；业务截止应由 Workflow 内的持久定时器驱动，并在终止前显式进入补偿或人工处置。

取消同样不能等同于补偿。取消请求可能在某个 Activity 已产生效果后到达，Activity 也可能尚未观察到取消。Workflow 应先记录取消意图，等待在途步骤返回或查询其回执，再按真实效果集计算补偿计划。

不可补偿步骤的处理

现实中并非所有操作都可以补偿——已发送的邮件无法收回，已打印的发票无法撤销。工作流引擎中处理不可补偿步骤的策略：

  1. 后置不可补偿步骤：将不可补偿的操作放在 Saga 的最后执行，这样如果它成功了，Saga 就完成了；如果它失败了，前面的步骤可以正常补偿。
  2. 预留-确认模式：将不可补偿操作拆成两步——先「预留」（可补偿），确认无误后再「确认」（不可补偿）。如：先冻结额度（可解冻），全部步骤成功后再真正扣款。
  3. 人工干预升级：当不可补偿步骤的补偿确实需要时，触发人工干预工作流——通过 Signal 通知运维人员处理。

小结

工作流引擎让 Saga 的补偿意图、期限和尝试可持久恢复，但不承诺外部补偿只执行一次。可靠 Saga 需要稳定操作 ID、权威回执、未知结果查询、有限重试和人工处置终态。补偿是新的业务交易，不是时间倒流。下一节讨论人工审批环节，版本迁移则处理 Saga 逻辑变化时的兼容性。

Activity 可能重复尝试且完成前失联的边界可对照 Temporal Activity Definition；截至 2026 年 8 月核对。
