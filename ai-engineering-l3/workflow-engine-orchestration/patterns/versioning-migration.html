工作流版本化与迁移

长生命周期工作流会跨越多次发布。新代码不仅要能启动新实例，还要能够继续解释旧实例已经写入的事件历史。这里存在两条必须分别治理的兼容轴：一条是运行时的重放兼容性，另一条是领域层的业务语义兼容性。前者回答“新 Worker 能否对旧历史生成相同的命令序列”，后者回答“旧实例是否应该继续遵守旧价格、旧审批链或旧合规规则”。把两者混为一个 version 字段，往往会让发布成功却让业务结果悄悄改变。

本章以 Temporal 的事件历史模型为主线，同时比较 AWS Step Functions、Lambda durable functions 与 Azure Durable Functions 的版本边界。重点不是记住某个 SDK API，而是建立一套可审计的升级协议：识别存量历史、选择路由策略、验证重放、渐进放量、排空旧版本，并为无法自动迁移的实例保留人工处置路径。

核心概念

  • 重放兼容性：新代码对旧事件历史仍产生兼容的命令序列。
  • 业务语义版本：实例应遵守的价格、审批、风控或合规契约，与 Worker Build 分开记录。
  • Worker Versioning：用不可变 Build、Pinned/Auto-Upgrade 行为和 Current/Ramping 路由管理代码并存。
  • 迁移安全点：没有未知副作用、状态可解码且领域政策允许切换的显式边界。

两条兼容轴

工作流代码执行到定时器、Activity、子工作流等边界时，会向服务端发出命令。重放旧历史时，运行时重新执行工作流代码，并检查当前代码产生的命令是否仍与历史兼容。因此，“确定性”不是要求所有代码都没有分支，而是要求在同一历史与同一版本决策下产生兼容的命令序列。

业务语义兼容则是另一回事。例如，订单在规则 v1 下已经完成信用审查，发布 v2 后新增制裁名单检查。新实例必须走 v2，但存量实例可能需要继续 v1、在安全点升级，或暂停后由人工复核。这个选择属于领域政策，不应由 Worker 恰好拉到哪条任务来决定。

兼容轴 典型变化 失败表现 所有者 主要证据
重放兼容 增删或重排会产生命令的调用 非确定性错误、任务反复失败 工作流平台团队与代码所有者 生产历史重放、版本路由、部署清单
业务语义兼容 价格、审批、风控、补偿政策变化 结果合法但不符合实例启动时契约 领域所有者 实例策略版本、决策记录、迁移批准

一个稳健的实例输入通常会固化 policyVersion、关键合同版本和租户策略，而运行时版本由部署系统管理。领域决策不应该读取“当前日期”“当前配置中心值”来偷偷漂移；需要动态更新时，应通过 Signal、Update 或 Activity 获取，并把结果记录进历史。

Temporal 的首选策略：Worker Versioning

当前 Temporal 文档建议大多数能够运行版本化部署的团队优先使用 Worker Versioning。一个 Worker Deployment 由稳定的 Deployment Name 和不可变的 Build ID 标识。发布系统把新 Build 注册为 Deployment Version，再设置 Current 或 Ramping Version。这样，兼容选择成为服务端可观察的路由状态，而不是散落在业务代码中的环境变量。

Temporal 提供两类工作流行为：

  • Pinned：一个 Workflow Execution 固定到某个 Deployment Version，适合长流程和存在不兼容代码变化的流程。旧 Worker 必须继续服务存量实例，直到它们完成、迁移或被明确终止。
  • Auto-Upgrade：任务会跟随 Deployment 的 Current Version，适合短流程或已经通过补丁 API 保持重放兼容的流程。切换 Current 前仍必须重放代表性历史。

Ramping Version 可以把一部分新启动或可升级流量送到新 Build，逐步观察失败率、任务延迟和业务结果，再提升为 Current。回滚路由只能阻止更多流量进入坏版本；已经执行过新命令或产生新副作用的实例，不能假设仅靠把 Current 指回旧 Build 就能安全倒退。

Pinned 策略常被称为 rainbow deployment：多个版本并存并各自排空。它降低了代码补丁的复杂度，却增加了部署寿命、容量与安全补丁维护成本。团队必须维护“版本—实例数—最老实例年龄—可删除时间”的清单，而不能凭 Pod 已无 CPU 使用就删除旧 Build。

Continue-As-New 不是自动升级

Continue-As-New 会以新 Run 继续同一个 Workflow ID，并截断不断增长的历史，但它不是天然的版本迁移按钮。对 Pinned 工作流，新的 Run 通常继承版本行为；只有在设计并配置了明确的升级边界时，才应把 Continue-As-New 与新版本路由结合。对 Auto-Upgrade 工作流，新任务可能进入 Current Version，但代码仍需保持历史与状态输入兼容。

因此，每个 Continue-As-New 输入都应携带足够的领域状态和 schema 版本，并满足以下条件：

  1. 当前阶段没有结果未知的外部操作。
  2. 所有已确认副作用都有稳定操作 ID 与结果回执。
  3. 新版本能够解码继续运行所需的状态。
  4. 领域所有者明确允许实例在此安全点切换策略。
  5. 迁移失败时可以把实例隔离到旧版本或人工队列。

代码补丁：兼容分支的生命周期

当团队不能为每个版本保留独立 Worker，或使用 Auto-Upgrade 行为时，可以用 SDK 的补丁机制把版本选择写进历史。以 TypeScript SDK 的 patched 为例，生命周期不是永久堆叠条件，而是三个阶段：

import { patched } from '@temporalio/workflow';

export async function fulfillmentWorkflow(input: Input): Promise<Result> {
  if (patched('split-risk-review-v2')) {
    await runIdentityReview(input);
    await runRiskReview(input);
  } else {
    await runLegacyReview(input);
  }

  return finalize(input);
}

第一阶段加入补丁分支，新历史记录补丁决策，旧历史仍走兼容路径。第二阶段等待旧历史排空，并用生产历史重放证明不再需要旧分支。第三阶段调用 SDK 提供的弃用补丁能力，随后在确认所有相关历史都包含新决策或已完成后，才删除条件。补丁 ID 是持久协议的一部分，必须全局稳定，不能重命名后当作普通重构。

补丁机制只解决命令序列兼容，不会自动迁移业务状态，也不会撤销已经执行的 Activity。若新旧 Activity 对同一个外部系统使用不同幂等键，仍可能产生双重副作用；迁移设计必须保留原操作 ID，或通过防腐层把旧回执转换成新契约。

云服务的版本边界并不相同

各平台都提供“版本”概念，但它们固定的对象不同，不能把名称相同当作语义相同。

平台 版本固定对象 存量实例行为 迁移关注点
Temporal Worker Versioning Worker Deployment Version Pinned 固定；Auto-Upgrade 跟随路由并要求兼容 Build 排空、重放、补丁与安全升级
AWS Step Functions 状态机 Version，可由 Alias 路由 执行关联启动时版本；redrive 使用原版本与定义 Alias 放量不能修改已启动执行
Lambda durable functions 已发布函数版本或 Alias 指向的版本 执行固定到启动时解析出的函数版本 生产调用应使用限定版本，保留到执行完成
Azure Durable Functions orchestration version 实例永久关联版本；匹配策略决定 Worker 接受范围 CurrentOrOlder、Strict 等策略与 Worker 生命周期

Step Functions Alias 适合渐进启动新执行，但不会把正在运行的执行搬到新定义。Lambda durable functions 的执行会固定到启动时的函数版本，因此删除旧版本前必须确认相关执行和保留窗口都已结束。Azure Durable Functions 的内置 orchestration versioning 会为实例记录版本；默认兼容策略与严格策略影响旧实例能否由当前 Worker 继续处理，发布前要用实际宿主语言和扩展版本验证配置。

这些机制都不替代领域迁移。比如“审批由一人改为两人”仍需决定存量实例是维持旧合同、补做一次审批，还是进入人工复核，而不是只调整 Alias 权重。

可执行的迁移计划

迁移应从实例和历史清单开始，而不是从部署按钮开始。对每个工作流类型收集：活跃实例数、最老年龄、历史大小、当前业务阶段、运行时版本、策略版本、未确认副作用、等待中的 Timer/Signal、关联租户及数据驻留要求。然后为每一类实例选择“原地兼容、固定排空、Continue-As-New 升级、导出后重建、人工终止”之一。

推荐的发布序列如下：

  1. 冻结契约：为新 Build 分配不可变 ID，记录输入/结果 schema、策略版本和下游幂等契约。
  2. 采样历史：覆盖最老实例、最长分支、定时器、失败重试、人工等待、补偿中和不同租户的历史。
  3. 离线重放：把历史送入新工作流实现；任何非确定性或解码失败都阻断发布。
  4. 影子验证：在不调用真实副作用的环境验证 Activity 契约、回执读取和查询输出。
  5. 渐进路由：先启动少量新实例或设置 Ramping Version，观察版本维度指标和业务不变量。
  6. 故障演练：在 Activity 完成但确认丢失、Worker 被杀、服务端短暂不可用和回滚期间验证重复执行与恢复。
  7. 排空旧版：持续跟踪旧版本实例与任务积压；对超过期限的实例走人工决策，而非强制删除 Worker。
  8. 清理兼容层：只有在查询、历史样本和保留窗口共同证明旧分支不可达后，才移除补丁、旧 schema 和旧 Build。

重放测试至少要固定一组来自生产的脱敏历史，并在 CI 中使用当前 SDK 的 replay API。例如 TypeScript SDK 提供 Worker.runReplayHistory 和批量历史重放能力。样本不能只保存“成功的短流程”；最有价值的是跨发布、经历重试、收到重复消息以及停在人工环节的历史。

回滚、数据迁移与不可逆副作用

回滚分为三层。路由回滚停止新流量进入新 Build；代码回滚让任务重新由旧实现执行；业务补救处理新版本已经提交的不可逆结果。前两层都不能代替第三层。若新版本已经扣款、发货或写入监管记录，应使用带回执的补偿、对账或人工处置，而不是删除事件历史。

工作流状态迁移和业务数据库迁移也应解耦。数据库可以采用扩展—迁移—收缩：先让新旧 Worker 都能读写兼容字段，再回填数据，最后在旧 Worker 排空后收缩 schema。工作流输入和 Activity 结果则使用显式 schema 版本与适配器。读取旧结构的逻辑应位于契约边界，不要让版本判断扩散到每个领域函数。

若迁移过程发现副作用结果未知，应先用稳定操作 ID查询下游回执或对账表。没有证据时不得简单重试不可幂等操作，也不得凭工作流历史里缺少“完成事件”断言外部操作未发生。这个原则与 Saga 补偿 的恢复模型一致；涉及审批政策变化时，还应把处置依据记录到 人机协同 的决策信封中。

发布门与退役门

新版本进入生产前，应满足以下可验证条件：

  • 代表性历史在新代码上重放通过，样本清单可追溯。
  • 新旧 schema 的解码、默认值和不可逆字段变更经过契约测试。
  • Activity 的操作 ID、回执和重试策略在版本切换前后保持一致。
  • Ramping 或 Alias 指标按版本分组，能看到任务失败、延迟、积压和业务不变量。
  • 回滚操作手册明确说明哪些实例可以路由回滚，哪些需要补偿或人工介入。
  • 旧 Worker 的容量、安全补丁与凭据在排空期间仍受维护。

旧版本退役则必须有更强证据：没有该版本可执行的活跃实例、没有关联的待处理任务、保留期内历史已验证可由保留代码解释、下游回执可审计，并且删除 Build 不会破坏灾难恢复。退役是一次受控的数据与运行时生命周期操作，不是镜像仓库清理。

小结

工作流升级同时治理重放、业务语义、数据和外部副作用四类兼容。Worker Versioning 将代码路由变成可观察的部署状态，补丁机制为必须原地兼容的历史保留稳定分支；两者都不能替代领域迁移决策。安全发布以代表性历史重放、渐进路由、回执闭合和旧版本排空证据为门，回滚则明确区分路由回滚与不可逆业务补救。
