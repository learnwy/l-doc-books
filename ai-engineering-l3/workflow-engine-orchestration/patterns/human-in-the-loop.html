人工审批环节的建模与实现

核心概念

  • Human-in-the-Loop（HITL）：工作流中需要人类判断力介入的环节，等待时间从分钟到数天不等
  • Signal：外部系统向运行中工作流传递数据的异步通知机制，用于传入审批结果
  • Condition + Timer：等待条件满足或超时的组合，是 HITL 的基础实现模式
  • Human-Veto 模式：默认自动执行，仅在人工明确否决时停止——与阻塞审批相反的交互模式
  • 决策信封：包含请求 ID、规则版本、审批主体、权限证明、决定和时间戳的不可变输入，用于鉴权、去重与审计

为什么工作流需要人工介入

全自动化是理想状态，但现实业务中大量场景需要人的判断力介入：高金额交易需要风控人员审批、AI 生成的内容需要人工确认、异常订单需要客服裁定、合规要求某些操作必须有人签字。这些「人工环节」（Human-in-the-Loop, HITL）的特殊性在于：等待时间不确定（分钟到天），且等待期间工作流必须保持状态——不能占用计算资源、不能丢失上下文。

工作流引擎适合保存长期等待状态，但“能收到 Signal”只是传输能力。审批 API 仍需认证调用者、验证其在当前规则版本下有权决定、生成不可重复使用的决策 ID，并把审计证据发送给 Workflow。否则任何能访问引擎的客户端都可能伪造审批。

HITL 的四种交互模式

人工介入环节在工作流中有四种典型的交互模式：

模式 语义 超时行为 典型场景
阻塞审批 等待人工批准/拒绝才继续 超时=拒绝或升级 贷款审批、采购审批
人工否决 自动执行除非人工阻止 超时=自动通过 AI 决策人工复核
信息补充 等待人工提供缺失数据 超时=提醒或取消 表单补填、身份验证
人工分派 等待人工选择后续路径 超时=默认路径 异常工单路由

这四种模式的工作流实现结构相似——核心都是「等待外部信号 + 超时兜底」——但业务语义不同导致超时行为不同。

Temporal 中的 HITL 实现

Temporal 通过 Signal + Condition + Timer 的组合实现 HITL。以一个贷款审批流程为例：

export async function loanApprovalWorkflow(application: LoanApplication): Promise<LoanDecision> {
  let decision: ApprovalDecision | null = null;

  setHandler(approvalSignal, (incoming) => {
    if (incoming.requestId !== application.approvalRequestId) return;
    if (decision !== null) return;
    decision = incoming;
  });

  // 自动化前置检查
  const creditScore = await checkCreditScore(application.userId);
  const riskLevel = await assessRisk(application, creditScore);

  // 低风险自动通过
  if (riskLevel === 'low') {
    return { approved: true, rate: calculateRate(creditScore) };
  }

  // 中高风险需要人工审批
  await notifyApprover(application, riskLevel);

  // 等待审批结果——最长 72 小时
  const approved = await condition(
    () => decision !== null, // 条件：收到审批信号
    '72 hours', // 超时：72 小时
  );

  if (!approved) {
    // 超时未审批——升级到上级
    await escalateToManager(application);
    const escalated = await condition(() => decision !== null, '24 hours');
    if (!escalated) {
      return { approved: false, reason: 'approval_timeout' };
    }
  }

  return {
    approved: decision!.result === 'approve',
    rate: decision!.suggestedRate,
    approver: decision!.approverId,
  };
}

Signal Handler 定义了工作流如何接收外部输入：

// Signal Handler——外部审批系统通过 Signal 传入审批结果
const approvalSignal = defineSignal<[ApprovalDecision]>('approval');

// 在工作流中注册 Handler
setHandler(approvalSignal, (result: ApprovalDecision) => {
  if (result.requestId !== pendingRequestId) return;
  if (decision !== null) return;
  decision = result;
});

示例中的 Handler 只负责确定性的状态转换；身份认证、角色校验和签名验证应在审批 API 或专门 Activity 中完成，因为 Workflow 不能访问外部身份系统。Workflow 仍要核对请求 ID、规则版本与当前等待阶段，并让重复决定幂等。若先收到“通过”后又收到“拒绝”，不能用最后写入覆盖审计事实，而应拒绝冲突并触发调查。

审批流程的完整架构

sequenceDiagram
    participant WF as 工作流实例
    participant S as Temporal Server
    participant API as 审批 API
    participant UI as 审批 UI
    participant Approver as 审批人

    WF->>S: 进入等待状态(condition)
    Note over WF: 休眠,不消耗资源
    WF->>API: 发送待审批通知
    API->>UI: 创建审批任务
    UI->>Approver: 展示待审批列表

    Note over Approver: 数小时后...
    Approver->>UI: 点击「通过」
    UI->>API: POST /approve
    API->>S: Signal(workflowId, 'approval', {result: 'approve'})
    S->>WF: 传递 Signal
    Note over WF: condition 满足,恢复执行
    WF->>WF: 继续后续流程

关键实现细节：

  1. 审批 API 持有受限的 Workflow 引用：UI 不应直接持有通用 Temporal 凭据；API 把经过鉴权的业务决定映射到指定 Workflow 和请求 ID
  2. 等待期间零资源消耗：工作流状态持久化在 Server 端，Worker 可以处理其他任务
  3. 审批消息可持久交付：Worker 不在线时 Signal 进入历史；应用仍要处理调用重试造成的重复消息与过期决定

决策信封与权限边界

审批输入不应只有布尔值。最小决策信封可以包含：

字段 作用
requestId 绑定一次具体审批请求并用于去重
workflowId / businessId 建立执行实例与业务实体的关联
policyVersion 证明该决定依据哪版规则与阈值
actorId / actorRole 记录谁以何种角色决定；由可信边界断言
decision / reasonCode 表达结构化结果，避免自由文本驱动控制流
decidedAt / expiresAt 拒绝过期或窗口外的决定
decisionId 让 API、审计库和 Workflow 共享同一回执

审批 API 应先在自己的审计库原子写入 decisionId，再向 Workflow 发送 Signal 或 Update；发送超时时按相同 ID 重试。Workflow 接收后把 ID 保存在状态中，重复消息返回同一结果。若要求调用方同步知道“决定已被 Workflow 接受”，Update 比异步 Signal 更合适，但仍不能替代业务审计库。

多级审批与会签

复杂的审批场景往往需要多级审批或多人会签。工作流引擎让这类逻辑的表达非常自然：

// 多级审批：按金额分级
async function multiLevelApproval(amount: number): Promise<boolean> {
  // Level 1: 直接主管
  const l1 = await waitForApproval('supervisor', '48 hours');
  if (!l1.approved) return false;

  // Level 2: 部门经理（仅大额）
  if (amount > 100000) {
    const l2 = await waitForApproval('department_head', '48 hours');
    if (!l2.approved) return false;
  }

  // Level 3: CFO（仅超大额）
  if (amount > 1000000) {
    const l3 = await waitForApproval('cfo', '72 hours');
    if (!l3.approved) return false;
  }

  return true;
}

// 会签：多人并行审批，需要全部通过
async function parallelApproval(approvers: string[]): Promise<boolean> {
  const results = await Promise.all(approvers.map((approver) => waitForApproval(approver, '48 hours')));
  return results.every((r) => r.approved);
}

Query 实现进度查询

审批等待期间，业务方和审批人需要实时了解流程进度。Temporal 的 Query 机制提供了不改变状态的只读查询：

交互方式 用途 是否修改状态 响应方式
Signal 传入审批结果 是 异步
Query 查询当前进度 否 同步返回
Update 即时交互 是 同步返回 
// Query Handler——随时可查询工作流当前状态
const statusQuery = defineQuery<WorkflowStatus>('status');
setHandler(statusQuery, () => ({
  currentStep: currentStep,
  waitingFor: pendingApprover,
  waitingSince: waitStartTime,
  timeoutAt: deadlineTime,
}));

审批 UI 可以通过 Query 读取最新内存状态，但 Query 需要兼容 Worker 在线处理，也不会成为持久业务证据。大规模列表和报表应使用 Visibility/Search Attributes 或业务读模型；最终审计应以事件历史和审批系统的不可变决策记录交叉核对。

超时与升级策略

HITL 场景中，超时处理策略直接影响业务体验：

stateDiagram-v2
    [*] --> 等待审批
    等待审批 --> 已通过: 审批人通过
    等待审批 --> 已拒绝: 审批人拒绝
    等待审批 --> 催办: 24h 未响应
    催办 --> 已通过: 审批人通过
    催办 --> 已拒绝: 审批人拒绝
    催办 --> 升级: 48h 仍未响应
    升级 --> 上级审批: 转交上级
    上级审批 --> 已通过: 上级通过
    上级审批 --> 已拒绝: 上级拒绝
    上级审批 --> 自动处理: 72h 超时
    自动处理 --> 已拒绝: 默认拒绝
    已通过 --> [*]
    已拒绝 --> [*]

渐进式超时策略的实现：

  1. T+24h：发送催办通知（邮件/IM/短信）
  2. T+48h：自动升级到上级审批人
  3. T+72h：按业务规则自动处理（通过或拒绝）
  4. 全程：记录完整审计轨迹

计时窗口应基于 Workflow 的重放安全时钟，并把截止时间固化为业务状态。提醒 Activity 可以失败重试，但提醒失败不应悄悄延长审批期限。收到决定与 Timer 到期可能在相邻事件中竞争，因此必须定义稳定优先级：例如“Service 接收时间不晚于 expiresAt 才有效”，而不是依赖 Worker 本地处理顺序。

人工否决模式（Human-Veto）

与阻塞审批相反，Human-Veto 模式默认自动执行，只在人工明确否决时才停止：

async function humanVetoPattern(action: Action): Promise<ActionResult> {
  let vetoed = false;
  setHandler(vetoSignal, (veto) => {
    if (veto.requestId === action.reviewRequestId) vetoed = true;
  });

  // 通知人工——给一个窗口期
  await notifyReviewer(action);

  // 等待 4 小时否决窗口
  await sleep('4 hours');

  if (vetoed) {
    return { status: 'vetoed', action: 'none' };
  }

  // 窗口期内无否决——自动执行
  return await executeAction(action);
}

Human-Veto 只适合风险受限、可逆且组织已经明确批准“沉默即放行”的动作。转账、删除、公开发布、权限提升和合规决定不应因审批人未响应而自动执行。用于 AI Agent 时还应把工具、参数、资源范围和计划摘要固化在审查版本中；审查后任何计划变化都必须生成新的请求，不能沿用旧窗口。

取消、转交与数据保护

审批人离职、权限变化、请假转交和发起方撤销都是独立事件。取消 Workflow 不等于撤销审批任务；流程需要 Activity 关闭外部待办，并用同一请求 ID确认任务已失效。迟到决定到达时，Handler 根据当前阶段和 expiresAt 拒绝，而不是重新打开流程。

Signal、Query、Search Attributes 和事件历史可能包含个人身份、意见与业务敏感字段。只把路由所需的低敏字段放入可检索属性，正文载荷使用加密 codec 或外部受控存储；审批 UI、Codec 解密端点与运维人员的读取权限都要进入审计。

小结

工作流引擎为长期等待提供 Signal、Timer 与持久状态，但生产级人工环节还需要决策信封、鉴权、幂等、冲突规则、取消传播和数据保护。开发者不仅要描述“等谁、等多久”，还要证明“谁有权决定、重复或迟到决定怎样处理、证据保存在哪里”。前文的 Saga 补偿处理部分成功，下一节版本迁移处理审批规则和 Worker 代码变化。

Temporal 对 Signal、Query、Update 的当前边界可对照 Workflow message passing，载荷保护可对照 Codecs and Encryption；截至 2026 年 8 月核对。
