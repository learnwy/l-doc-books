Part IV · Control PlaneAI 护栏与内容安全·总览基础护栏架构 输入/输出

护栏架构 输入/输出

当你要给一个 LLM 应用加护栏时，最先要回答的不是「用哪个检测器」，而是「检测器挂在哪」。同一个 PII 扫描器挂在用户输入上、挂在检索结果上、挂在模型输出上，意义完全不同。这一篇给出护栏在系统架构里的标准落点——业界以 NeMo Guardrails 的五 rail 模型为事实标准——以及每个落点的延迟、成本、失败模式权衡。理解了这套架构，前面威胁地图上的每个威胁，你都能立刻说出它该被哪道护栏拦在哪一段。

核心概念：五种 rail 的标准落点

NVIDIA NeMo Guardrails 把护栏沿请求生命周期分成五类 rail，这套划分已成为讨论护栏架构时的通用语言。它们各自守住请求路径的一段。

flowchart TD
  U[用户输入] --> R1[输入 rail<br/>注入/越狱/PII 检测]
  R1 --> R2[对话 rail<br/>话题/意图边界]
  R2 --> RET[检索]
  RET --> R3[检索 rail<br/>过滤知识库结果]
  R3 --> M[LLM 推理]
  M --> R4[执行 rail<br/>工具调用前的鉴权/校验]
  R4 --> TOOL[工具/Agent]
  M --> R5[输出 rail<br/>内容审核/事实校验/策略]
  R5 --> OUT[返回用户]

输入 rail 处理刚进来的用户消息，是注入检测、越狱判定、PII 脱敏的所在。对话 rail 控制对话流——哪些话题允许、什么意图该怎么回应，这是 NeMo 用 Colang 声明对话形状的地方。检索 rail 在 RAG 场景里过滤检索结果，挡掉间接注入和不该被引用的内容。执行 rail 在模型要调用工具时介入，做参数校验和鉴权，是 Agent 越权的最后一道闸。输出 rail 处理即将返回的回答，做内容审核、事实校验、格式与策略强制。

下表把五种 rail 与它们处理的威胁、典型实现对应起来。

Rail 守住的环节 处理的威胁 典型实现
输入 rail 用户输入入口 直接注入、越狱、PII 分类器 + 正则 + Presidio
对话 rail 意图与话题 越界话题、系统提示套取 Colang 流程 / 意图分类
检索 rail RAG 检索结果 间接注入、嵌入投毒 来源白名单 + 内容扫描
执行 rail 工具调用 Agent 越权、SSRF 参数 schema + 鉴权策略
输出 rail 模型回答出口 有害内容、幻觉、泄露 Llama Guard + RAGAS + 策略引擎

入口与出口的对称性

把五种 rail 再压缩，最小心智模型就是「入口 + 出口」两组。这种对称很重要：很多检查需要两头都做。PII 在入口脱敏（不让敏感数据进模型上下文），在出口还要再扫一遍（防止模型从别处把它复述出来）；注入检测主要在入口，但出口也要查「模型是否泄露了系统提示」这种注入得逞的迹象。

入口护栏和出口护栏的工程取舍不同。入口护栏在模型推理之前，拦截几乎零成本——拦下就直接返回拒绝，省下了一整次昂贵的模型调用。出口护栏在推理之后，它拦截时模型 token 已经烧掉了，所以出口护栏的拦截只省了「把坏内容发给用户」的损失，不省算力。这意味着：能在入口拦的，尽量在入口拦。

fail-open 还是 fail-closed

护栏自己也会出故障——分类器服务超时、依赖的 API 挂了。这时护栏该怎么办，是整个架构里最该被显式决策、却最常被忽略的一点。

fail-open：护栏故障时放行请求。系统可用性优先，代价是故障窗口内完全没有防护。 fail-closed：护栏故障时拒绝请求。安全优先，代价是护栏一挂，业务就停。

选择取决于这道护栏守的是什么。一道挡有害内容的输出 rail，宁可 fail-closed——漏一条有害回答的代价高于短暂不可用。一道做体验优化的弱护栏，可以 fail-open。原则是：按被保护资产的损失量级决定，并且这个决策必须写进配置、被评测覆盖，而不是默认成代码里某个没人注意的 try/except。残余风险可以沿用 为何需要护栏 里的式子估算——fail-open 等于在故障窗口内把召回 rrr 临时归零。

延迟与成本预算

每加一道护栏，都在给请求加延迟、给账单加钱。一个串了输入分类器、PII 扫描、输出审核、事实校验四道护栏的系统，护栏本身的延迟可能逼近甚至超过模型推理。设计时要给护栏立预算。两个降本提速的手段是标准做法：

第一，并行执行。彼此独立的 rail 不必串行。NeMo Guardrails 在 2026 年的版本里引入了并行 rail 执行，多个输入 rail 并发跑而非顺序跑，显著降低延迟——这一点在 护栏框架 里会展开。设独立护栏各自延迟为 tit_iti​，串行总延迟是 ∑iti\sum_i t_i∑i​ti​，并行则是 max⁡iti\max_i t_imaxi​ti​。

第二，分级路由。先用便宜的启发式（正则、关键词）做粗筛，只有可疑的请求才升级到昂贵的分类器或 LLM 判定。绝大多数正常请求在第一级就放行，把昂贵判定的调用量压到很低。

旁路风险：护栏必须在路径上

一个常见的架构错误是把护栏做成「事后审计」——异步地扫日志、发现问题再告警。这不是护栏，是监控。真正的护栏必须同步地横在请求路径上，有能力拦截，否则坏内容已经发给用户了。架构上要保证没有绕过护栏的旁路：所有进出模型的流量，都必须穿过这圈闸门。把护栏做成网关中间件、而不是散落在各业务代码里的调用，是保证「无旁路」的工程手段。

小结

  • 护栏沿请求生命周期分五种 rail：输入、对话、检索、执行、输出；每种守住特定环节、处理特定威胁，构成业界通用语言。
  • 压缩成入口 + 出口两组：很多检查（尤其 PII）两头都要做；能在入口拦的尽量入口拦，因为入口拦截省下整次模型调用。
  • fail-open 与 fail-closed 必须按被保护资产显式决策，并写进配置、被评测覆盖，不能默认成隐式的异常处理。
  • 护栏会加延迟与成本，用并行执行与分级路由控预算；护栏必须同步横在路径上、无旁路，否则只是监控不是防护。
