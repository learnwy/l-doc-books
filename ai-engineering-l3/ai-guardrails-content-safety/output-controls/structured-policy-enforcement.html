Part IV · Control PlaneAI 护栏与内容安全·总览输出管控策略强制

策略强制

前面几篇的护栏都是「先让模型自由生成，再在出口检查、不合格就拦」。这套「生成—检查—拒绝」的循环有个固有浪费：模型可能生成了一大段不合规的内容，全被丢弃，token 白烧，还得重试。策略强制换了个思路——与其事后检查，不如从源头约束，让模型在格式与策略上从一开始就走不出边界。这一篇讲受约束解码、Schema 强制、与策略引擎，以及它们如何与出口检查叠成纵深。

核心概念：检查范式 vs 约束范式

把出口管控分成两类，差别在干预的时机。

flowchart TD
  subgraph 检查范式
    G1[自由生成] --> C1[出口检查]
    C1 -->|合格| OK1[放行]
    C1 -->|不合格| RETRY[拒绝/重试]
  end
  subgraph 约束范式
    G2[受约束生成<br/>只能产出合法 token] --> OK2[天然合规]
  end

检查范式事后裁决，灵活、能处理「语义合规」这类无法形式化的约束（比如「是否有害」），但浪费算力、且有漏检风险。约束范式在解码时就限制模型只能产出合法 token，对「结构合规」这类能形式化的约束（必须是合法 JSON、必须从枚举里选、必须匹配某语法）几乎能给出 100% 保证——因为非法 token 在采样时根本不被允许。两者不是替代，是分工：能形式化的用约束，不能形式化的用检查。

受约束解码：让非法输出不可能

受约束解码（constrained decoding）的原理是在每一步采样时，根据一套语法（grammar）把不符合规则的 token 的概率强制置零，模型只能在合法 token 里选。这意味着输出必然符合语法——不是「大概率符合」，是「不可能不符合」。

最常见的应用是强制合法 JSON：给定一个 JSON Schema，把它编译成一套状态机约束，模型逐 token 生成时被约束在「当前位置语法上允许的字符」内，于是产出的永远是能解析、且字段齐全、类型正确的 JSON。这对需要把 LLM 输出喂给下游程序的场景（function calling、结构化抽取、API 编排）是刚需——下游不必再写一堆「万一模型吐了非法 JSON 怎么办」的容错。

形式化地说，设第 ttt 步的原始 logits 为 ztz_tzt​，语法在当前状态允许的 token 集合为 AtA_tAt​，受约束解码把采样分布改成：

P(xt∣x<t)=softmax(zt)xt⋅1[xt∈At]/ZP(x_t \mid x_{<t}) = \text{softmax}(z_t)_{x_t} \cdot \mathbb{1}[x_t \in A_t] \big/ ZP(xt​∣x<t​)=softmax(zt​)xt​​⋅1[xt​∈At​]/Z

其中 1\mathbb{1}1 是指示函数、ZZZ 是归一化常数。落在 AtA_tAt​ 之外的 token 概率被归零，所以输出逐 token 都合法。代价是：约束过强会扭曲模型本来的分布，偶尔牺牲一点回答质量；且语法编译有工程成本。

Schema 强制与参数校验

受约束解码保证了「格式合法」，但还有一层「语义合法」要管——字段值是否在允许范围内、参数是否通过业务校验。这是 function calling 安全的关键：模型生成了一个合法的工具调用 JSON，不代表这个调用该被执行。一个被 提示注入 劫持的 Agent 可能生成格式完美、但参数恶意的工具调用（delete_user(id="*")）。

所以执行 rail（见 护栏架构）里要做两层校验：先用 Schema 验证结构与类型，再用业务规则验证值与权限。下表区分这两层。

层 校验什么 手段 拦得住的问题
结构层 合法 JSON、字段齐全、类型对 JSON Schema / 受约束解码 格式错误、缺字段
语义层 值在范围内、参数合法 业务校验函数 越界值、注入污染的参数
权限层 此调用是否被授权 鉴权策略 / 策略引擎 越权动作（LLM06）

策略引擎：把合规规则外置

当合规规则变多变杂（不同用户角色能调不同工具、不同地区有不同数据策略、某些动作需人工审批），把这些规则散在代码里会变成噩梦。成熟做法是引入策略引擎——把策略写成独立的、声明式的规则集（OPA/Rego 风格在传统系统里很成熟，LLM 系统里 NeMo 的 Colang 也承担类似角色），让护栏在执行动作前查询策略引擎「这个调用，这个用户，此刻，允许吗」。

外置策略的好处和 为何需要护栏 里讲的护栏优势一脉相承：规则可热更新、可审计、与业务代码解耦。一条策略变更不必改代码、不必重新部署模型，改规则文件即可，每次裁决都留痕可追溯。

与检查范式叠成纵深

策略强制不取代前面的内容审核与事实校验，而是和它们叠成完整的出口纵深。一次输出离开模型，理想的串联是：受约束解码保证格式合法 → Schema/参数校验保证结构与值合规 → 策略引擎裁决动作权限 → 内容审核 判是否有害 → 幻觉与事实校验 判是否属实。前两道是约束范式（便宜、确定），后两道是检查范式（处理语义）。能用约束兜住的就别留给检查，因为约束是确定性的、零漏检，而检查是概率性的。把可形式化的约束尽量前移到解码阶段，是降低整体漏检率和成本的关键设计。

小结

  • 出口管控有两种范式：检查（事后裁决，灵活但浪费且有漏检）与约束（解码时限制，对可形式化的结构约束给确定性保证）；二者分工而非替代。
  • 受约束解码在采样时把非法 token 概率归零，使输出必然合法（如强制合法 JSON），是 function calling 与结构化抽取的刚需，代价是可能轻微扭曲分布。
  • function calling 安全需三层校验：结构层（Schema）、语义层（业务校验值）、权限层（策略引擎裁决授权），挡住格式错误、注入污染的参数、与越权动作。
  • 策略引擎把合规规则外置为声明式规则集，可热更新、可审计、解耦；与内容审核、事实校验叠成出口纵深，可形式化的约束尽量前移到解码。
