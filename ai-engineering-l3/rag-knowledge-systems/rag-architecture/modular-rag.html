模块化 RAG

核心概念

模块化 RAG 是将 RAG 系统拆分成独立、可替换的模块，每个模块有明确的职责和接口。这种架构模式借鉴了微服务的设计理念，但粒度更细——模块通常在同一进程内通过接口调用，而非网络通信。模块化设计的核心价值在于降低变更成本：当你需要替换嵌入模型、升级检索策略或切换 LLM 供应商时，只需要修改对应模块的实现，其他模块完全不受影响。

为什么需要模块化

单体 RAG 的问题 模块化 RAG 的好处
代码耦合 模块独立
难以修改 易于替换
难以测试 易于测试
难以复用 易于复用
团队协作困难 团队协作容易

职责:

  • 处理错误

def orchestrate(query):
    processed_query = query_processor.process(query)
    docs = retriever.retrieve(processed_query)

模块化的优势
1. 易于替换
示例: 替换嵌入模型


// 旧的 OpenAI 嵌入
class OpenAIEmbedding implements EmbeddingModel {
  /* ... */
}

// 新的 BGE 嵌入
class BgeEmbedding implements EmbeddingModel {
  /* ... */
}

// 只需要替换这里
const embeddingModel = new BgeEmbedding();
2. 易于测试
示例: 单元测试检索器


// 可以 Mock 向量数据库
const mockVectorDB = createMockVectorDB(sampleDocs);
const retriever = new Retriever(embeddingModel, mockVectorDB);

// 测试检索
const results = retriever.retrieve('test query', 5);
expect(results.length).toBe(5);
3. 易于复用
示例: 多个应用共享模块


应用 A: 客服机器人
应用 B: 内部知识库
应用 C: 文档问答

都使用:
- 同一个检索器
- 同一个嵌入模型
- 同一个向量数据库
4. 团队协作
示例: 多人并行开发


团队成员 A: 开发检索器
团队成员 B: 开发查询处理器
团队成员 C: 开发答案生成器

通过接口定义，并行开发，最后集成
模块化的实现原则
1. 接口隔离
每个模块只定义必要的接口，不要暴露内部细节。


2. 依赖注入
通过构造函数传入依赖，不要在模块内部创建。


// 👍 好：依赖注入
class Retriever {
  constructor(
    private embedding: EmbeddingModel,
    private vectorDB: VectorDB,
  ) {}
}

// ❌ 不好：内部创建
class Retriever {
  constructor() {
    this.embedding = new OpenAIEmbedding(); // 硬编码
    this.vectorDB = new Pinecone(); // 硬编码
  }
}
3. 错误处理
每个模块处理自己的错误，或者向上抛出明确的错误类型。


4. 可观测性
每个模块记录日志和指标，方便调试和监控。

何时不需要过度模块化
    

  • 简单的原型（模块化开销大于收益）
    • 

  • 一次性脚本（不需要可维护性）
    • 

  • 非常小的项目（代码量不足以分模块）
    • 

  • 团队只有 1 人（无协作需求）
    • 



过度模块化会导致间接层过多、调试困难、代码跳转频繁。正确的做法是先用最简单的结构跑通流程，当某个模块需要替换或独立测试时再抽象。


小结
    

  • 拆分成独立模块，每个模块职责明确
    • 

  • 定义清晰的接口
    • 

  • 使用依赖注入
    • 

  • 易于替换、测试、复用、协作
    • 

  • 不要过度模块化，根据需要
    •
