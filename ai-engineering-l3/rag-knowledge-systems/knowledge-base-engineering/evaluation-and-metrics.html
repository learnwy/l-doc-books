Part III · RetrievalRAG 与知识系统 简介知识库工程 简介评估与指标

评估与指标

核心概念

评估是衡量 RAG 系统效果的过程，通过指标量化质量，指导优化方向。

为什么需要评估

没有评估的问题 评估的好处
不知道效果好坏 客观量化效果
优化方向模糊 指导优化方向
无法对比方案 A/B 测试有依据
问题难以定位 快速发现问题
难以向他人证明 数据支撑说服力

评估维度

1. 检索质量 (Retrieval Quality)

目标: 衡量检索到的文档是否相关。

常见指标

指标 全称 说明
Precision@k 精确率 前 k 个结果中相关的比例
Recall@k 召回率 所有相关文档中在前 k 个的比例
MAP Mean Average Precision 平均精度，综合衡量
NDCG@k Normalized Discounted Cumulative Gain 考虑排序的相关性
MRR Mean Reciprocal Rank 第一个相关结果的排名倒数

示例:

相关文档: [A, B, C]
检索结果: [B, X, A, Y, C]

Precision@3: 2/3 = 0.67 (前 3 个有 2 个相关)
Recall@5: 3/3 = 1.0 (前 5 个包含所有相关)
MRR: 1/1 = 1.0 (第一个结果就是相关的)

如何获取标注数据

  • 人工标注: 找人判断结果是否相关
  • 用户反馈: 点击、点赞、差评
  • 自动标注: 用 LLM 判断（便宜但有误差）

2. 答案质量 (Answer Quality)

目标: 衡量最终答案的好坏。

常见评估方法

方法 说明 优点 缺点
人工评估 人直接打分 准确、全面 成本高、慢
用户反馈 实际用户的评价 真实、低成本 样本可能少
LLM 评估 用 LLM 打分 自动化、快速 可能有偏见
自动化指标 ROUGE, BLEU, F1 完全自动 不一定贴合人类判断

LLM 评估提示词示例

请评估以下 RAG 答案的质量，用 0-5 分打分：
5 = 极其优秀，完全符合要求
4 = 很好，基本符合要求
3 = 一般，有小问题
2 = 较差，有明显问题
1 = 很差，基本没用
0 = 完全错误

评估维度：
1. 准确性: 答案是否正确？
2. 完整性: 是否包含所有必要信息？
3. 相关性: 是否回答了问题？
4. 清晰性: 表达是否清晰？

问题: {question}
上下文: {context}
答案: {answer}

请输出 JSON 格式：
{
  "overall_score": 0-5,
  "accuracy_score": 0-5,
  "completeness_score": 0-5,
  "relevance_score": 0-5,
  "clarity_score": 0-5,
  "reasoning": "简短说明"
}

3. 系统性能 (System Performance)

目标: 衡量系统的技术性能。

常见指标

指标 说明 目标
延迟 (Latency) 用户提问到看到答案的时间 P95 < 3s
吞吐量 (Throughput) 每秒处理的请求数 根据需求
可用性 (Availability) 系统正常运行的时间比例 99.9%+
错误率 (Error Rate) 失败请求的比例 < 1%

延迟分解

总延迟 = 查询向量化 + 检索 + 提示词构建 + LLM 生成 + 网络

可以逐个优化。

4. 成本 (Cost)

目标: 衡量系统的经济成本。

常见成本项

成本项 说明
嵌入成本 向量化文档和查询
LLM 成本 生成答案
向量数据库 存储和查询
基础设施 服务器、带宽等
人工 标注、运维等

单位经济

每次查询成本 = (嵌入成本 + LLM 成本 + 数据库成本) / 查询数

评估方法

1. 离线评估 (Offline Evaluation)

定义: 在真实用户之前，用测试集评估。

流程:

  1. 准备测试集（问题 + 标注答案/相关文档）
  2. 运行 RAG 系统
  3. 计算指标
  4. 分析结果

优点:

  • 可重复
  • 成本低
  • 可以快速迭代
  • 不影响用户

缺点:

  • 测试集可能不真实
  • 与线上效果可能有差距

2. A/B 测试 (A/B Testing)

定义: 同时运行两个版本，对比效果。

要点:


    

  • 随机分流
    • 

  • 足够的样本量
    • 

  • 统计显著性检验
    • 

  • 只改一个变量
    • 



优点:


    

  • 真实效果
    • 

  • 可信
    • 



缺点:


    

  • 需要流量
    • 

  • 周期长
    • 

  • 可能影响用户
    • 



3. 在线监控 (Online Monitoring)
定义: 持续监控线上系统的指标。


监控内容:


    

  • 系统性能（延迟、错误率）
    • 

  • 业务指标（用户满意度、留存）
    • 

  • 成本指标
    • 



告警:


    

  • 延迟过高
    • 

  • 错误率突增
    • 

  • 成本超预期
    •

实际应用
评估流程建议
    

  1. 建立基线: 先评估当前版本，建立基准
    2. 

  2. 离线评估: 优化后先离线测，有提升再上线
    3. 

  3. A/B 测试: 小流量 A/B 测试
    4. 

  4. 全量发布: 确认效果好再全量
    5. 

  5. 持续监控: 上线后持续监控
    6. 



常见陷阱
❌ 只看单一指标:


    

  • 不要只看 Precision，忽略 Recall
    • 

  • 不要只看自动指标，忽略人工评估
    • 

  • 不要只看效果，忽略成本和延迟
    • 



❌ 过度优化离线指标:


    

  • 离线指标好 ≠ 线上效果好
    • 

  • 要结合用户反馈
    • 



❌ 不建立基线:


    

  • 不知道优化是否有用
    • 

  • 无法衡量进步
    • 



小结
    

  • 分三层评估：检索、生成、端到端
    • 

  • 检索关注 Recall 和 Precision
    • 

  • 生成关注忠实度和答案相关性
    • 

  • 使用 Ragas 等框架自动化评估
    • 

  • 建立基准和回归检测
    • 

  • 持续优化，避免过拟合评估集
    •
