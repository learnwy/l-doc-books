增量更新

核心概念

增量更新是只处理新增或修改的文档，而不是每次都重新处理所有文档的策略。

为什么需要增量更新

全量更新的问题 增量更新的好处
成本高 节省成本
速度慢 更新更快
资源浪费 高效利用资源
影响服务 对服务影响小

检测变化的方法

1. 基于修改时间

核心思想: 比较文档的最后修改时间。

实现方式:


    

  • 文件系统: mtime
    • 

  • S3: LastModified
    • 

  • 数据库: updated_at 字段
    • 



优点:


    

  • 实现简单
    • 

  • 速度快
    • 

  • 资源消耗小
    • 



缺点:


    

  • 可能误判（修改时间变了但内容没变）
    • 

  • 时钟同步问题
    • 

  • 有些系统不支持
    • 



2. 基于内容哈希
核心思想: 计算文档内容的哈希值，比较是否变化。


SHA256("文档内容") = "a1b2c3d4..."
实现方式:


    

  • 计算文件内容的哈希（推荐 SHA-256，速度和安全性平衡最优）
    • 

  • 存储历史哈希到元数据库
    • 

  • 比较新旧哈希，只有哈希变化才触发重新处理
    • 



优点:


    

  • 准确（内容真的变了才处理）
    • 

  • 不受修改时间影响
    • 

  • 可验证，支持数据完整性校验
    • 



缺点:


    

  • 计算哈希需要读取整个文件，大文件较慢
    • 

  • 存储哈希需要额外空间
    • 

  • 对于频繁小修改的文件，仍然需要全量读取来计算哈希
    • 



3. 基于事件通知
核心思想: 文档变化时触发通知。


实现方式:


    

  • 文件系统: inotify, watchman
    • 

  • S3: S3 Event Notifications
    • 

  • 数据库: triggers, CDC (Change Data Capture)
    • 

  • 自定义: Webhook
    • 



优点:


    

  • 实时性好
    • 

  • 无需轮询
    • 

  • 资源效率高
    • 



缺点:


    

  • 实现复杂
    • 

  • 可能丢失事件
    • 

  • 需要处理重复事件
    • 



4. 混合方法
核心思想: 结合多种方法，互补长短。


常见组合:


    

  • 先用修改时间快速过滤
    • 

  • 对疑似变化的文件再计算哈希
    • 

  • 关键路径用事件通知
    • 



优点:


    

  • 平衡准确性和效率
    • 

  • 容错性好
    • 



增量更新的操作
1. 新增文档
流程:


    

  1. 检测到新文档
    2. 

  2. 处理文档（加载、清洗、分割、向量化）
    3. 

  3. 插入向量数据库
    4. 

  4. 记录文档信息（ID、哈希、时间等）
    5. 



2. 修改文档
流程:


    

  1. 检测到文档修改
    2. 

  2. 查询旧的文档块
    3. 

  3. 删除旧的向量
    4. 

  4. 处理新文档
    5. 

  5. 插入新的向量
    6. 

  6. 更新文档信息
    7. 



注意:


    

  • 要删除旧数据，避免重复
    • 

  • 考虑事务（要么全成功，要么全失败）
    • 

  • 可能需要短暂的服务不可用（或用双写）
    • 



3. 删除文档
流程:


    

  1. 检测到文档删除
    2. 

  2. 查询文档的所有块
    3. 

  3. 删除向量
    4. 

  4. 删除文档信息记录
    5. 



注意:


    

  • 不要漏删
    • 

  • 考虑软删除 vs 硬删除
    • 

  • 软删除可以恢复，但占用空间
    • 



增量更新的架构
简单版本
定时任务 → 扫描文档 → 比较 → 处理变化 → 更新向量库
适用场景:


    

  • 更新不频繁（小时级或天级）
    • 

  • 数据量不大
    • 

  • 简单需求
    • 



优点:


    

  • 实现简单
    • 

  • 易理解
    • 



缺点:


    

  • 有延迟
    • 

  • 扫描可能慢
    • 



生产级版本
组件:


    

  • 事件通知: 实时感知变化
    • 

  • 定时扫描: 兜底，防止事件丢失
    • 

  • 消息队列: 缓冲和解耦
    • 

  • 去重: 避免重复处理
    • 

  • 工作节点: 实际处理逻辑
    • 

  • 元数据存储: 记录文档状态
    • 



实际应用
状态存储
需要存储的信息:


    

  • 文档唯一 ID
    • 

  • 最后处理时间
    • 

  • 内容哈希（如果用）
    • 

  • 文档块的 ID 列表（用于删除）
    • 

  • 处理状态（成功、失败、处理中）
    • 



存储选择:


    

  • 小数据: JSON 文件
    • 

  • 中等数据: SQLite
    • 

  • 大数据: PostgreSQL, MySQL
    • 



一致性保证
挑战:


    

  • 处理一半失败了怎么办？（旧向量已删、新向量未插入）
    • 

  • 向量数据库和元数据存储不一致？（元数据说已更新，但向量库还是旧的）
    • 



解决方案:


    

  • 事务（如果数据库支持原子操作，将删除旧向量和插入新向量放在同一事务中）
    • 

  • 幂等操作（同一文档多次处理结果一致，避免重复插入导致数据膨胀）
    • 

  • 定期全量校验（按周期扫描全部文档，比对向量库和元数据库，发现不一致自动修复）
    • 

  • 补偿操作（失败时自动触发反向操作，回滚到上一个已知正确状态）
    • 

  • 双写策略（同时写入新旧两套向量，切换时原子替换，避免服务不可用窗口）
    • 



性能优化
技巧:


    

  • 批量处理变化（累积到一定数量或时间窗口后一次性处理，减少 API 调用次数）
    • 

  • 并行处理多个文档（使用工作者池，根据 CPU 和 API 限制设置并发度）
    • 

  • 缓存嵌入结果（对于未变化的文档块，直接复用旧的嵌入向量）
    • 

  • 优先处理重要文档（按访问频率或业务权重排序处理队列）
    • 

  • 低谷期处理大更新（将大批量更新调度到流量低谷时执行）
    • 



小结
    

  • 检测变化：修改时间、内容哈希、事件通知
    • 

  • 操作类型：新增、修改、删除
    • 

  • 从小开始，逐步完善
    • 

  • 保证一致性
    • 

  • 考虑性能优化
    •
