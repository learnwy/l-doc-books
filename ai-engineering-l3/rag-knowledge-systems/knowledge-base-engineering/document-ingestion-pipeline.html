文档摄入流水线

核心概念

文档摄入流水线是将原始文档转换为 RAG 可用的向量化块的自动化流程。

为什么需要流水线

手动处理的问题 流水线的好处
容易出错 一致可靠
速度慢 自动化高效
难以扩展 可水平扩展
不可重复 可复现
难以监控 可观测

流水线的核心阶段

1. 文档加载 (Loading)
职责: 读取各种格式的文档，提取文本内容。


常见格式:


    

  • 纯文本: .txt, .md
    • 

  • 文档: .docx, .pdf, .pptx
    • 

  • 网页: .html, .url
    • 

  • 表格: .xlsx, .csv
    • 

  • 代码: .py, .js, .java
    • 

  • 其他: JSON, XML, EML
    • 



常用工具:


    

  • LangChain Document Loaders
    • 

  • LlamaIndex Readers
    • 

  • Unstructured.io
    • 

  • PyMuPDF (PDF)
    • 

  • python-docx (Word)
    • 



考虑点:


    

  • 格式支持的全面性
    • 

  • 提取质量
    • 

  • 处理速度
    • 

  • 元数据保留
    • 



2. 文档清洗 (Cleaning)
职责: 去除噪声，提高文本质量。


常见清洗任务:


    

  • 去除页眉页脚
    • 

  • 去除目录、索引
    • 

  • 去除重复内容
    • 

  • 去除广告、导航
    • 

  • 统一格式（换行、空格）
    • 

  • 修正 OCR 错误
    • 

  • 处理特殊字符
    • 



示例规则:


- 去除少于 3 个字符的行
- 去除全是数字的行
- 合并过短的段落
- 去除重复的段落
重要性:


    

  • 提升检索质量
    • 

  • 减少嵌入噪音
    • 

  • 节省存储和成本
    • 

  • 提升答案质量
    • 



3. 文档分割 (Splitting)
职责: 将长文档切分成合适大小的块。


详见 Chapter 02，关键点:


    

  • 选择合适的分割策略
    • 

  • 考虑文档结构
    • 

  • 优化块大小
    • 

  • 使用重叠窗口
    • 



流水线中的分割:


    

  • 可以按文档类型用不同策略
    • 

  • 可以自动检测文档类型
    • 

  • 可以配置多种参数组合
    • 



4. 元数据提取 (Metadata Extraction)
职责: 提取有用的元数据，用于过滤和排序。


常见元数据: | 元数据 | 来源 | 用途 | |--------|------|------| | 标题 | 文档内容/文件名 | 展示、检索增强 | | 作者 | 文档属性 | 过滤、排序 | | 创建时间 | 文件系统 | 时间过滤 | | 更新时间 | 文件系统 | 新鲜度排序 | | 文档类型 | 扩展名 | 分块策略选择 | | 来源 URL | 网页 | 引用、溯源 | | 标签 | 手动/自动 | 分类过滤 | | 语言 | 检测 | 嵌入模型选择 |


提取方法:


    

  • 从文件系统读取
    • 

  • 从文档内容解析
    • 

  • 用 LLM 自动提取
    • 

  • 用户手动输入
    • 



5. 向量化 (Embedding)
职责: 将文本块转换成向量。


详见 Chapter 01，关键点:


    

  • 选择合适的嵌入模型
    • 

  • 批量处理提升效率
    • 

  • 失败重试机制
    • 

  • 缓存避免重复计算
    • 



流水线中的向量化:


    

  • 可以按语言用不同模型
    • 

  • 可以用轻量模型做预览
    • 

  • 可以增量更新（只向量化变化的块）
    • 



6. 存储 (Storage)
职责: 将向量和元数据存储到向量数据库。


详见 Chapter 03，关键点:


    

  • 选择合适的向量数据库
    • 

  • 批量插入提升效率
    • 

  • 错误处理和重试
    • 

  • 索引构建
    • 



流水线中的存储:


    

  • 可以分批次处理
    • 

  • 可以并行处理多个文档
    • 

  • 可以监控进度
    • 



流水线架构
简单流水线
文档目录 → 脚本处理 → 向量数据库
适用场景:


    

  • 数据量小（< 1k 文档）
    • 

  • 不常更新
    • 

  • 快速原型
    • 



优点:


    

  • 实现简单
    • 

  • 快速上线
    • 



缺点:


    

  • 难以监控
    • 

  • 错误处理弱
    • 

  • 难以扩展
    • 



生产级流水线
组件说明:


    

  • 文档源: 文档存储位置
    • 

  • 消息队列: 解耦和缓冲
    • 

  • 工作节点: 实际处理逻辑
    • 

  • 监控: 指标收集和展示
    • 

  • 日志: 问题排查
    • 



优点:


    

  • 可扩展
    • 

  • 可监控
    • 

  • 容错性好
    • 

  • 可并行
    • 



缺点:


    

  • 实现复杂
    • 

  • 需要运维
    • 



流水线最佳实践
1. 幂等性 (Idempotency)
定义: 重复执行同一次操作，结果相同。


实现方式:


    

  • 每个文档有唯一 ID
    • 

  • 记录已处理的文档
    • 

  • 处理前检查是否已存在
    • 

  • 支持覆盖更新
    • 



重要性:


    

  • 可以安全重试
    • 

  • 避免重复数据
    • 

  • 可以中断后继续
    • 



2. 错误处理
常见错误:


    

  • 文档格式损坏
    • 

  • 嵌入 API 失败
    • 

  • 向量数据库超时
    • 

  • 网络中断
    • 



处理策略:


    

  • 记录失败的文档
    • 

  • 重试机制（指数退避）
    • 

  • 死信队列（Dead Letter Queue）
    • 

  • 告警通知
    • 



3. 可观测性
监控指标:


    

  • 处理速度（文档/秒）
    • 

  • 成功率/失败率
    • 

  • 延迟分布
    • 

  • 队列长度
    • 

  • 资源使用（CPU、内存）
    • 



日志记录:


    

  • 每个文档的处理状态
    • 

  • 失败原因
    • 

  • 处理时间
    • 

  • 关键步骤的时间点
    • 



4. 增量更新
策略:


    

  • 检查文档是否变化（修改时间、哈希）
    • 

  • 只处理新增或修改的文档
    • 

  • 删除已删除的文档
    • 

  • 定期全量校验
    • 



实际应用
何时需要复杂流水线
✅ 需要:


    

  • 文档 > 1k
    • 

  • 频繁更新
    • 

  • 多种文档格式
    • 

  • 生产级可用性
    • 



❌ 不需要:


    

  • 快速原型
    • 

  • 数据量小
    • 

  • 不常更新
    •

需求

小结
文档摄入流水线是 RAG 系统的基础，好的流水线可以提升质量、效率和可靠性。


核心要点回顾：


    

  • 流水线阶段：加载 → 清洗 → 分割 → 元数据 → 向量化 → 存储
    • 

  • 生产级需要消息队列、监控、日志
    • 

  • 保证幂等性
    • 

  • 完善错误处理
    • 

  • 考虑增量更新
    •
