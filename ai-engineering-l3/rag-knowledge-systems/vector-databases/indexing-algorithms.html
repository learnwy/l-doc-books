索引算法

核心概念

向量索引算法是让我们能够在大规模向量数据中快速找到最近邻的关键技术。

为什么需要索引

搜索方式 复杂度 100万向量 1亿向量
暴力搜索 O(n) ~1秒 ~100秒
索引搜索 O(log n) 或近似 ~10ms ~100ms

暴力搜索的问题:

  • 每次查询都要和所有向量比较
  • 数据量一大就太慢
  • 无法满足实时查询需求

索引的作用:

  • 牺牲一点精度（近似搜索）
  • 换来极大的速度提升
  • 大多数场景下精度损失可以接受

常见索引算法

1. HNSW (Hierarchical Navigable Small Worlds)

核心思想: 构建多层小世界图，上层是下层的采样。

搜索过程:


    

  1. 从最上层的随机节点开始
    2. 

  2. 在当前层贪心搜索，找到局部最近点
    3. 

  3. 下降到下一层，从该点继续搜索
    4. 

  4. 重复直到最底层
    5. 

  5. 在最底层找到 top-k 结果
    6. 







优点
缺点





查询速度极快
内存占用较高




构建相对较快
删除操作复杂




参数调优简单
不适合动态更新太频繁




精度/速度平衡好
索引文件较大





适用场景: 大多数生产场景、Pinecone、Weaviate 默认、Qdrant。


关键参数:


    

  • efConstruction: 构建时的探索大小（影响构建时间和索引质量）
    • 

  • efSearch: 查询时的探索大小（影响查询时间和精度）
    • 

  • M: 每个节点的最大连接数
    • 



调优指南: | 场景 | efConstruction | efSearch | M | |------|----------------|----------|---| | 平衡 | 200 | 128 | 16 | | 追求速度 | 100 | 64 | 12 | | 追求精度 | 400 | 256 | 24 |


2. IVF (Inverted File)
核心思想: 先聚类，搜索时只查相关的聚类。


步骤:


    

  1. 构建阶段:
      

    • 用 k-means 将向量聚类成 N 个中心
      • 

    • 每个向量分配到最近的簇
      • 

    • 存储簇中心和每个簇的向量
      • 

    

    2. 

  2. 查询阶段:
      

    • 找到查询向量最近的 K 个簇
      • 

    • 只在这 K 个簇内做暴力搜索
      • 

    • 返回 top-k 结果
      • 

    

    3. 







优点
缺点





内存占用低
查询精度稍低




索引构建快
参数调优复杂




适合大规模数据
需要训练聚类




可压缩
聚类边界处效果差





适用场景: 超大规模数据、需要内存优化、Milvus、FAISS 常用。


关键参数:


    

  • nlist: 聚类中心数量
    • 

  • nprobe: 查询时探查的簇数量
    • 



调优指南: | 数据量 | nlist | nprobe | |--------|-------|--------| | < 100万 | 1024 | 8 | | 100万-1000万 | 4096 | 16 | | > 1000万 | 16384 | 32 |


3. FAISS 索引族
核心思想: Facebook AI 开源的一系列索引，组合多种技术。


常见 FAISS 索引:


    

  • IndexFlatL2: 暴力搜索，精确
    • 

  • IndexIVFFlat: IVF + 未压缩向量
    • 

  • IndexIVFPQ: IVF + 乘积量化压缩
    • 

  • IndexHNSWFlat: HNSW + 未压缩向量
    • 

  • IndexScalarQuantizer: 标量量化
    • 



特点:


    

  • 高度优化的 C++ 实现
    • 

  • 支持 GPU 加速
    • 

  • 组合灵活
    • 

  • 工业界广泛使用
    • 



适用场景: 需要极致性能、可以自己组合索引、Python/ C++ 项目。


4. Annoy (Approximate Nearest Neighbors Oh Yeah)
核心思想: 构建随机投影树森林。


特点:


    

  • 索引构建慢，但查询快
    • 

  • 内存占用适中
    • 

  • 实现简单
    • 

  • 适合静态数据
    • 



适用场景: 推荐系统、静态数据集、Spotify 开源。


5. SPTAG (Space Partition Tree And Graph)
核心思想: 结合树和图的优势。


特点:


    

  • 微软开源
    • 

  • 内存优化
    • 

  • 适合超大规模
    • 

  • 查询速度快
    • 



适用场景: Bing 搜索、超大规模生产环境。

实际选择指南
大多数情况: HNSW
为什么:


    

  • 平衡最好
    • 

  • 参数简单
    • 

  • 大多数向量数据库默认
    • 

  • 效果通常让人满意
    • 



超大规模: IVF 或 IVFPQ
什么时候:


    

  • 超过 1 亿向量
    • 

  • 内存紧张
    • 

  • 可以接受稍低的精度
    • 



需要极致性能: FAISS
什么时候:


    

  • 有 C++/Python 能力
    • 

  • 需要 GPU 加速
    • 

  • 愿意自己组合索引
    • 



静态数据: Annoy
什么时候:


    

  • 数据不怎么更新
    • 

  • 推荐系统场景
    • 

  • 简单的需求
    • 



索引调优原则
1. 先测默认配置
大多数向量数据库的默认配置已经不错了，先测默认的。


2. 明确目标
你想要:


    

  • 更高的精度？
    • 

  • 更快的查询？
    • 

  • 更低的内存？
    • 

  • 更快的索引构建？
    • 



不可能同时都最好，需要权衡。


3. 渐进式调优
    

  1. 从默认开始
    2. 

  2. 调整一个参数
    3. 

  3. 评估效果
    4. 

  4. 继续调整或回退
    5. 



4. 用真实数据测试
    

  • 合成数据可能有误导
    • 

  • 用你的真实数据测试
    • 

  • 测试你的真实查询模式
    • 



小结
索引算法是向量搜索性能的关键，理解各种算法的特点和适用场景很重要。


核心要点回顾：


    

  • HNSW 是大多数场景的首选
    • 

  • IVF 适合超大规模和内存优化
    • 

  • FAISS 最灵活，适合有经验的团队
    • 

  • 先测默认配置，再调优
    • 

  • 明确你的目标（精度、速度、内存）
    • 

  • 用真实数据测试
    •
