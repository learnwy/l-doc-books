评测即 CI：AI 产品的持续集成

核心概念

传统软件工程的持续集成（CI）核心是"代码改动 → 自动化测试 → 通过则合并、失败则阻止"。AI 产品需要把这个工作流扩展到提示词、模型版本、RAG 索引、工具定义等所有可能影响 AI 行为的产物——任何一处变更都自动触发评测，分数下降就阻止合并。这种"评测即 CI"的工程实践把 AI 产品的演进从"凭直觉冒险"升级为"有指标护栏"。

为什么 AI 产品更需要 CI
传统软件 CI 的价值是"阻止破坏性改动"。在 AI 产品中，这个价值被放大了 N 倍，因为：


    

  • 小改动后果难预测：传统代码的影响通常是局部的；AI 产品中改一个提示词或换一个模型可能让某些场景显著变好、另一些场景悄悄变差。
    • 

  • 缺少传统测试覆盖：传统单元测试在 AI 产品里大多失效——你无法用 assertEqual 来测试一个生成式回答是否合格。评测集成为唯一的回归保护。
    • 

  • 变更频率高：AI 产品的提示词、模型、RAG 索引可能每周甚至每天都在变。手动验证每次改动几乎不可能。
    • 

  • 回滚成本高：传统代码回滚很快；但如果一个有问题的提示词上线一周才被发现，期间用户已经形成印象、产生数据，回滚的真实代价远超 git revert 那一行命令。
    • 



CI 流水线的构成
一个完整的 AI 产品 CI 流水线通常包含以下阶段：


各阶段的关键设计：


提示词语法验证：检查提示词模板的语法（变量插值、JSON Schema 合法性、特殊 token 配对）。这一步速度极快，能在 30 秒内完成。


小评测集快速回归：选 20-50 条核心评测样本做快速反馈，目标是 5 分钟内出结果。这一步过滤掉大部分明显的破坏性改动。


完整评测集：跑全部 100-500 条评测样本，目标是 30 分钟内出结果。这一步是主要的质量护栏。


安全测试子集：跑专门的安全/红队评测样本，覆盖越狱、注入、隐私等敏感场景。


人审排队：评测分数下降的 PR 自动排到人工 review 队列，由领域专家逐条审查具体哪些样本失败、是否可接受。

许多团队在初期会自建一套简单的评测脚本——读 YAML 评测集、调模型、对比期望、输出 JSON 报告。这种最小实现能在第一天就跑起来，并随着需求复杂化逐步迁移到成熟框架。


评测集的版本化
评测集本身也需要版本化和质量管理。常见的实践：


    

  • Git 管理：评测集与代码一起放 Git 仓库，每次变更走 PR 流程。
    • 

  • 样本元数据：每个样本带上"创建日期、来源、标注者、难度、维度标签"等元数据。
    • 

  • 基线快照：每个评测集版本对应当前最优提示词在该版本上的分数，作为后续回归基线。
    • 

  • 样本生命周期：定期淘汰过时样本（场景已不存在）、补充新样本（覆盖新发现的失败模式）。
    • 



评测集的健康度本身也要监控——样本是否保持多样性？是否过拟合（提示词专门为某个样本优化导致整体分数失真）？是否覆盖最新的失败模式？这些问题让评测集维护成为一项持续的工程活动。


实战中的常见挑战
把"评测即 CI"落地到团队实践中会遇到一些具体挑战：


评测速度：完整评测集跑一次可能耗时 30 分钟到几小时（特别是当评测涉及人工或大模型评判时）。解决方法：分层评测（小集 5 分钟 + 大集异步），并行调用，结果缓存。


LLM-as-Judge 的稳定性：用 LLM 做自动评判时，同一输入两次可能得到不同评分。解决方法：固定 temperature=0、用足够大的模型做 Judge、关键场景用多个 Judge 投票。


成本控制：每次 PR 都跑全量评测集会让 API 成本激增。解决方法：缓存（提示词未变的样本不重跑）、采样（PR 阶段只跑 30% 样本，合并到主分支再跑全量）、分级（只对核心场景做高频回归）。


误报噪声：偶尔的随机失败会触发 CI 阻止，影响开发效率。解决方法：失败样本自动重试 1-2 次、连续多次失败才真正阻止合并。


与传统 CI 的整合
AI CI 不应该独立于传统 CI 存在，而应该作为同一套 CI 流水线的不同阶段：


    

  • 代码 PR 同时触发传统 CI（lint、单测、集成测试）与 AI CI（评测集回归）。
    • 

  • 两套 CI 的结果合并到同一个 PR 状态检查，全部通过才允许合并。
    • 

  • 监控告警与运营仪表盘也整合在一起，让团队在同一个看板看到代码与 AI 行为的健康状况。
    • 



这种整合让 AI 不再是"研发过程之外的特殊环节"，而是工程流程的自然一部分。


小结
评测即 CI 把 AI 产品的演进从"凭感觉的冒险"升级为"有指标护栏的工程实践"。任何影响 AI 行为的变更（提示词、模型、RAG、工具）都自动触发评测、分数下降阻止合并、关键变更走人审。把这套机制建立起来需要 1-2 个月的工程投入，但回报是后续几年里产品能稳定演进而不被随机崩塌打乱节奏。一个团队是否真正"工程化"了 AI 产品，就看它有没有一条持续运行的 AI CI 流水线。把"评测即 CI"作为 AI 产品成熟度的核心指标，是衡量团队工程化水平的最简单标准。
