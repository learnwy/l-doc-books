重试、超时与取消

模型调用卡住三十秒后，运行时发起第二次请求；第一请求随后返回，两个结果又各自触发工具。这个事故不是“网络不稳定”，而是系统没有统一的时间与取消语义。重试、超时和取消必须作为一个协议设计，因为任何一个单独存在都会在其他两个边界制造幽灵工作。

核心概念

超时定义一次等待何时不再值得继续，重试决定失败后是否再次尝试，取消把“不再需要结果”传播给正在消耗资源的下游。三者共享同一个上层 deadline 和尝试预算。若各层各设独立时钟，上游可能早已放弃，下游仍在运行；若各层各自重试，调用数量会呈乘法增长。

AWS Well-Architected 的重试指南强调指数退避、抖动与最大重试值，指出无界队列和多层重试会让过载恶化。REL05-BP03还要求只重试可安全重复的请求。这些原则对 LLM 更重要，因为一次失败尝试可能已经消耗大量 token，甚至已触发外部工具。

从运行截止时间向下切片

时间控制应从用户或业务给出的绝对截止时间开始。每个步骤获得剩余时间的一部分，每次尝试再从步骤预算中切片，并预留保存回执、取消传播和人工接管所需时间。绝对时间比“再等三十秒”更适合跨进程恢复，因为恢复后仍能计算真实剩余量。

可以用以下约束检查时间分配：

Trun≥∑i=1n(Tstepi+Tpersisti)+TrecoveryT_{run} \geq \sum_{i=1}^{n}(T_{step_i} + T_{persist_i}) + T_{recovery}Trun​≥i=1∑n​(Tstepi​​+Tpersisti​​)+Trecovery​

单步内部的尝试预算则满足：

Tstep≥∑j=1m(Tattemptj+Tbackoffj)+TreconcileT_{step} \geq \sum_{j=1}^{m}(T_{attempt_j} + T_{backoff_j}) + T_{reconcile}Tstep​≥j=1∑m​(Tattemptj​​+Tbackoffj​​)+Treconcile​

公式不是要求所有步骤串行，而是提醒架构师把持久化与对账时间算进预算。若最后一次工具尝试刚好耗尽运行期限，系统就没有时间确认效果或安全取消。

不同依赖需要不同超时。模型首 token 延迟、完整响应时间、流式空闲时间和工具执行时间不是同一个指标。对模型流可设置首事件 deadline 与事件间 idle timeout；对长工具设置启动超时、心跳超时和总体超时；对审批设置到期时间而不是占用执行线程。

gRPC 的核心语义指出，客户端和服务端可能对同一次 RPC 得出不同结论：服务端已经成功发送，客户端却因 deadline 认为失败；取消也不会回滚此前已发生的改变。gRPC Core Concepts说明为什么“deadline exceeded”必须和副作用回执配合，而不能直接重发新动作。

重试策略由错误分类驱动

重试函数的输入不应只有异常类型，还应包含动作可重试性、剩余时间、累计成本、供应商提示、当前过载状态和先前尝试轨迹。策略返回重试、对账、改计划、等待或终止，而不是一个布尔值。

export type RetryContext = {
  actionId: string;
  attempt: number;
  elapsedMs: number;
  remainingMs: number;
  costUsed: number;
  errorClass: 'transient' | 'overload' | 'permanent' | 'conflict' | 'unknown';
  idempotent: boolean;
  retryAfterMs: number | null;
};

export type RetryDecision =
  { kind: 'retry'; delayMs: number } | { kind: 'reconcile' } | { kind: 'replan' } | { kind: 'stop'; reason: string };

export function decideRetry(input: RetryContext): RetryDecision {
  if (input.remainingMs <= 0 || input.attempt >= 4) return { kind: 'stop', reason: 'budget_exhausted' };
  if (input.errorClass === 'unknown') return { kind: 'reconcile' };
  if (input.errorClass === 'permanent') return { kind: 'stop', reason: 'permanent_error' };
  if (!input.idempotent) return { kind: 'reconcile' };
  const cap = Math.min(8000, 250 * 2 ** input.attempt);
  const delayMs = input.retryAfterMs ?? Math.floor(Math.random() * cap);
  return delayMs < input.remainingMs ? { kind: 'retry', delayMs } : { kind: 'stop', reason: 'deadline' };
}

示例中的 full jitter 只用于说明，生产实现应使用可注入随机源以便测试，并尊重供应商的 Retry-After。真正的分类应在工具适配器内完成，因为只有它理解供应商错误语义。运行时保存分类结果和原始证据，避免恢复后由新代码把同一错误重新解释成另一类别。

重试层级只选一个负责跨时间恢复。HTTP 客户端可以处理连接建立前的极短传输重试，模型网关可以处理供应商路由，而 agent 运行时负责业务动作的长重试；但三层必须共享尝试计数或明确禁用重叠默认值。否则每层最多三次会放大成 33=273^3=2733=27 次调用。

退避、抖动与重试配额

指数退避的目标不是礼貌等待，而是降低故障期间的同步压力。无抖动时，大量运行会在相同时间点醒来，形成周期性尖峰；full jitter 从 [0,cap][0, cap][0,cap] 随机选择延迟，使请求分散。退避上限防止等待无限增长，最大累计时间确保任务不会静默挂起数小时。

重试还需要共享配额。可为每个租户、依赖和错误类别维护 token bucket：正常成功补充 token，失败重试消耗 token；配额用尽后快速失败或延迟入队。这样单个故障供应商不会让所有运行把容量花在重复尝试上。

重试预算应同时计入钱和时间。一次高价模型重试可能比十次轻量元数据查询更昂贵。运行信封可以定义模型 token、工具调用和总成本上限，策略根据已消费回执扣减。恢复不能重置预算，否则反复崩溃会绕过控制。

过载错误的最佳响应通常是减少工作，而不是更努力重试。运行时可以降低并发、切换已验证的降级路径、缩短低优先级输出，或把任务推迟到有业务价值的最晚时间。无法在有效期内完成的请求应明确拒绝，避免把陈旧任务留在队列拖累新流量。

取消是持久命令

取消不是杀掉当前进程，而是记录“调用方不再要求继续”的持久意图，并将其传播到所有子动作。取消事件应包含发起者、原因、时间、目标范围和策略版本。worker 在模型流、工具心跳、队列消费和长循环的安全点检查取消令牌。

gRPC 取消指南要求服务端主动停止本地处理并理想地向上游调用传播取消，同时指出库通常无法强行中断应用处理器，处理器必须协作检查。gRPC Cancellation对 agent 工具同样适用：运行时可以发送取消信号，但工具必须实现可中断点，且此前修改不会自动回滚。

取消状态机应区分 cancel_requested、cancelling 与 cancelled。收到请求先阻止签发新动作，再取消可中断调用，等待或强制终止剩余尝试，最后对已确认副作用进行保留、补偿或人工处置。只有对账完成才能进入 cancelled 终态。

若外部系统不支持取消，运行时仍应停止消费结果作为新计划输入，但必须保存晚到回执。否则动作已经发生却不在账本中，后续审计会误以为取消成功。晚到成功可能触发补偿，也可能按业务规则保留效果。

取消还应沿父子关系传播，但传播策略不是永远级联。父运行取消后，专属于它的子运行应取消；已经转化为独立业务责任的子运行可能继续。父子创建时就要声明 abandon、request_cancel 或 wait_for_cleanup 策略。

推测执行与请求对冲

对只读、无副作用且尾延迟严重的请求，可以在延迟分位数达到阈值后发起对冲请求，采用先成功者并取消其余。这不是普通重试，因为原请求仍在运行。若对写操作使用对冲，即使有幂等键也会增加供应端争用和冲突，默认应禁止。

对模型生成进行对冲还会引入输出选择问题和双倍成本。只有当产品明确允许多个候选、预算已授权，并且选择器本身可评估时才使用。不能把“取最快响应”当作可靠性，因为最快输出可能质量更差。

熔断器与重试配额互补。熔断器在依赖持续失败时阻止新尝试，让系统快速降级；半开探针用于判断恢复。熔断状态要按供应商、区域、模型或工具能力隔离，不能因为一个模型超时就关闭整个 agent 平台。

验证时间与取消语义

测试环境需要可控时钟、可控随机源和可注入故障。使用真实睡眠会让测试缓慢且不稳定；虚拟时钟可以推进 deadline，验证退避顺序、预算耗尽和审批到期。每次尝试记录计划时间与实际开始时间，以发现队列延迟已经吞掉预算。

故障矩阵至少包含：请求发送前超时、服务端成功后客户端超时、429 带或不带 Retry-After、取消与成功同时到达、取消无法传播、晚到响应、多个层默认重试、worker 重启后剩余 deadline 计算。每个场景都要断言外部效果数量、最终状态、尝试成本和取消原因。

对有副作用动作，时间控制必须与幂等与副作用回执一起验证；运行级资源上限和队列行为在并发、资源预算与背压继续展开。

小结

  • 从运行绝对 deadline 向步骤和尝试切片，并为持久化、对账与清理预留时间。
  • 根据具体依赖的错误语义分类，结果未知先对账，永久错误不重试。
  • 采用有上限的指数退避、抖动和共享重试配额，避免多层乘法放大。
  • 把取消记录为持久命令，在安全点传播，并承认已经发生的副作用不会自动回滚。
  • 仅对安全只读调用谨慎使用对冲，把模型成本与质量选择纳入授权。
  • 用可控时钟和精确崩溃点测试时间协议，而不是只测快乐路径。
