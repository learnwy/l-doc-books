人工审批、中断与恢复

让 agent 在删除生产数据前“问一下人”并不难，难的是审批人第二天点击同意时，系统仍能证明她看到的参数与即将执行的参数完全一致。若暂停只是内存中的 Promise，进程重启会丢失等待；若批准只是一枚布尔值，规划器重算后可能把它套到另一项动作上。

核心概念

人工审批是一个持久、版本化的中断协议。运行时先提交待审批动作与证据包，释放 worker，然后把运行置为等待状态。审批服务验证决策者身份并追加不可变决定。恢复器重新加载当前动作，核对决定的适用范围、版本和有效期，最后才签发工具执行。

OpenAI Agents SDK 的 HITL 文档把待审批工具调用作为 interruption 暴露，RunState 可以序列化并在批准或拒绝后恢复；它还说明嵌套 agent 的中断会提升到外层运行处理。Human-in-the-loop证明审批可以成为运行状态的一部分，但生产平台仍需自行定义身份、策略与存储边界。

审批请求是一份不可变提案

审批请求必须在人看到之前冻结。至少包含 approval_id、action_id、规范化参数摘要、可读摘要、目标资源、预期效果、可逆性、风险级别、请求策略、有效期和证据引用。若模型或用户修改参数，应创建新版本并把旧请求标记为 superseded。

export type ApprovalRequest = {
  approvalId: string;
  version: number;
  runId: string;
  actionId: string;
  actionDigest: string;
  toolName: string;
  targetRef: string;
  riskClass: 'medium' | 'high' | 'critical';
  reversibility: 'reversible' | 'compensable' | 'irreversible';
  evidenceRef: string;
  requestedPolicyVersion: string;
  expiresAt: string;
};

export type ApprovalDecision = {
  decisionId: string;
  approvalId: string;
  approvalVersion: number;
  subjectId: string;
  decision: 'approve' | 'reject';
  reason: string;
  decidedAt: string;
  authContextDigest: string;
};

人类可读摘要不能替代原参数摘要。界面显示“退款 100 元”时，应同时明确币种、订单、收款对象、环境和不可逆影响。运行时最终比较的是 actionDigest，界面则帮助人理解风险。若摘要生成失败或关键字段无法展示，应拒绝批准，而不是让审批者盲签。

证据包要足够让人做决定，但遵守最小披露。它可以包含相关业务规则、来源数据版本、模型给出的理由、历史工具回执和差异预览。秘密、完整 prompt 或无关客户数据不应为了“上下文完整”全部暴露给审批界面。

审批不等于授权

审批回答“这个人在当时是否同意此动作”，授权回答“这个主体当前是否有权使动作发生”。二者缺一不可。管理者批准一笔退款，不代表执行用的服务身份可以操作任意账户；反之，服务身份具备 API 权限，也不代表用户同意高风险操作。

运行时在创建请求时验证发起者权限，在决策时验证审批者角色与职责分离，在恢复执行前再次验证目标资源、策略和凭据。三次检查服务于不同时间点，不能因为前面通过就省略后面。

高风险场景可要求多方审批或角色分离。例如提交人与批准人不能相同，金额超过阈值需要财务和业务双签。多方策略应表达为可计算条件，而不是在 UI 中写一句说明。决定集合满足条件后生成一份 approval grant，执行回执再引用该 grant。

发起权限 无权用户制造审批噪音 创建请求前

资源授权 目标所有权已变化 执行前

审批决定应数字签名或至少写入防篡改审计存储，记录认证强度与会话摘要。不要在普通业务表上提供无审计的 approved=true 更新接口。

中断点必须可重复进入

许多框架在恢复时会从节点开头重新执行，而不是从源码某一行继续。LangGraph Interrupts 文档明确指出，恢复会重新运行整个 node，因此 interrupt 前的副作用必须幂等，也不能随意重排 interrupt 调用。LangGraph Interrupts揭示了通用规则：中断是控制事件，不是语言级续体。

中断前必须先持久化动作意图和审批请求，再把运行状态改为等待。若先通知审批系统再提交状态，审批者可能作出决定，而运行时恢复后找不到对应请求。通知属于可重建投影，可以从审批请求事件重新发送。

恢复时不要执行“interrupt 后下一行”，而应重新进入审批节点：加载最新请求，查找决定，校验运行修订和动作摘要。没有决定就继续等待；决定过期或请求被取代就生成新请求；拒绝则把结构化理由交给规划器或终止；批准且仍合法才签发动作。

这样设计也自然支持重复决定消息。审批服务可能至少一次投递，运行时收件箱按 decision_id 去重；同一请求版本出现互相冲突的决定时，停止自动执行并报警，而不是以后到消息覆盖先到决定。

恢复前必须重新验证世界

人工等待期间，价格、库存、代码分支、目标资源所有者、策略和凭据都可能改变。审批只绑定当时展示的提案，不是对未来任意状态的授权。恢复器要验证动作参数摘要不变，并针对易变前置条件执行只读校验。

可把前置条件表达成版本断言，例如订单版本仍为 17、部署目标仍是提交 abc123、账户状态仍可退款。若断言失败，旧批准失效，规划器可根据新事实提出新动作并请求新审批。

策略升级也需要规则。若新策略更严格，通常应重新审批；若只是展示文本变化且动作摘要与权限要求相同，可以由策略兼容表允许沿用。兼容决定必须由策略所有者声明，不能由恢复器凭字段相似度猜测。

审批有效期应结合业务风险。发布确认可能只在半小时内有效，低风险数据导出可持续一天。到期后运行进入明确分支：自动重新请求、转人工处置或取消。无限有效的审批会变成长期能力令牌。

人工队列也需要背压与 SLO

把异常全部交给人不是可靠性方案，只是把积压移到另一个系统。审批队列需要按风险、到期时间和业务价值排序，限制每个运行的未决请求数，并提供合并与批量决策的严格条件。多个不同参数的高风险动作不能因为界面方便就合成一个模糊批准。

审批等待不占 worker，但占用用户承诺和业务期限。运行状态应暴露等待年龄、剩余期限、责任组和升级路径。接近到期时提醒，超过团队 SLO 时升级；没有可用审批者时快速失败或切换到安全降级方案。

对审批结果做质量分析也很重要：批准后补偿率、拒绝原因、平均等待时间、被取代请求比例、重复请求率和审批者负载可以暴露策略问题。若某类动作几乎总被批准，可能适合更细粒度的自动策略；若经常被拒绝，规划器或上下文可能有缺陷。

审批体验要让决定可逆到“执行前”。批准后若动作尚未签发，可以允许撤销 grant；一旦外部效果确认，撤销就转化为新的取消或补偿意图，不能改写历史决定。

拒绝、取消与超时的语义

拒绝不是工具错误。它是人类提供的新约束，可以终止运行、要求规划器寻找低风险替代，或让用户修改目标。运行时应把结构化拒绝理由传给规划器，但要防止模型反复提出本质相同的动作绕过人类决定。可用 denied_action_family 和参数范围记录禁区。

用户取消运行时，所有未决审批请求标记取消，后到决定不能恢复执行。审批者取消请求与运行取消要区分：前者只撤销一个提案，后者停止整个责任。状态机需要不同命令和审计事件。

审批超时可能意味着业务价值消失，也可能只是人员离线。策略应预先定义：只读动作可安全跳过，关键写动作进入人工修复，或整个运行取消。不要在超时后默认批准，也不要让模型自行缩小参数并静默执行。

长等待运行需要版本化 pending task。OpenAI Agents SDK 文档特别提醒长时间审批要考虑 pending task versioning；这与动作摘要绑定原则一致。恢复 API 应拒绝旧客户端针对旧版本提交的决定，并返回当前待决请求。

安全失败与可观察证据

审批服务不可用时，高风险动作应 fail closed；但只读或明确低风险动作可按策略继续。安全失败不等于整个平台瘫痪，因此审批依赖要按风险类别隔离，运行时也要保留取消与查询能力。

追踪系统应连接 run_id、approval_id、decision_id、action_id 与 receipt_id，同时避免记录完整敏感参数。操作人员从任一效果都能反查谁批准、批准时看到了哪个摘要、恢复时做了哪些重验证。

告警应覆盖：批准后动作摘要不匹配、无授权决定、同版本冲突决定、过期批准被使用、审批请求重复增长、等待超过 SLO、执行回执缺少 approval grant。单纯监控 HTTP 错误无法发现这些语义违规。

验收测试

测试要跨进程与跨时间。创建审批请求后终止所有 worker，使用新进程提交决定并恢复；在等待期间升级策略、修改目标资源版本、取消运行和替换动作参数；重复、乱序和冲突投递决定；让决定在动作签发前与签发后撤销。

每个案例断言：执行的动作摘要等于获批摘要；过期或被取代决定不能执行；审批者权限在决定时和恢复时都有效；worker 无需保持内存；拒绝不会被规划器用等价动作绕过；最终回执能反查完整批准链。

时间与取消控制见重试、超时与取消，人工队列的容量保护见并发、资源预算与背压。

小结

  • 把人工审批建模为持久中断协议，而不是内存 Promise 或布尔字段。
  • 冻结动作身份、参数摘要、风险、证据和期限；参数改变就创建新版本。
  • 将同意与授权分开，在发起、决定和执行三个时点验证不同控制。
  • 恢复时重新进入审批节点并验证当前世界，不从源码下一行盲目继续。
  • 为人工队列定义背压、优先级、等待 SLO 和升级路径。
  • 让批准、拒绝、取消、过期和补偿各自拥有明确且可审计的语义。
