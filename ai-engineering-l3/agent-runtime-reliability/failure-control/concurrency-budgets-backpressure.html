并发、资源预算与背压

Agent 运行的负载形状比普通 API 更难预测：同一个请求可能只问一次模型，也可能生成几十次工具调用、并行浏览多个数据源并等待数分钟。若平台只按入口 QPS 限流，一个看似低流量的租户仍能耗尽模型配额、worker 槽位、文件句柄和下游连接。

核心概念

资源治理需要同时回答三个问题：一次运行最多能花多少，一组运行可以并发占用多少，系统过载时新工作如何感知并减速。预算约束单项责任，配额隔离租户与依赖，背压把下游容量信号传回上游准入。只有限流而没有背压，会把请求藏进无限队列；只有队列而没有预算，会让一个长运行占满所有消费者。

flowchart LR
    Request[新运行请求] --> Admission{准入控制}
    Admission -->|预算合法且有容量| Queue[有界优先队列]
    Admission -->|容量不足| Reject[拒绝或稍后重试]
    Queue --> Scheduler[公平调度器]
    Scheduler --> Worker[运行槽位]
    Worker --> Model[模型并发池]
    Worker --> Tool[工具并发池]
    Model --> Feedback[延迟与限流反馈]
    Tool --> Feedback
    Feedback --> Admission
    Feedback --> Scheduler
层级 主要约束 典型维度 超限动作
单动作 一次调用不可失控 超时、响应字节、工具 CPU 取消动作
单运行 用户授权边界 token、工具次数、成本、墙钟 降级或终止
单租户 防止邻居受损 并发运行、队列长度、日预算 排队或拒绝
单依赖 保护供应商和连接池 模型并发、API RPS、重试数 背压与熔断
全平台 保留恢复余量 worker、内存、数据库连接 负载卸除

Kubernetes 把 resource request 用于调度，把 limit 交给 kubelet 与内核执行；CPU 超限会被节流，内存限制则可能在压力下触发 OOM 终止。Kubernetes Resource Management提醒我们，声明预算与执行预算是两个不同层次。Agent 运行时同样需要在准入时预估资源，又要在执行时持续计量并强制停止。

预算是随运行递减的权利

运行预算应来自产品套餐、用户授权和风险策略的交集，在启动信封中冻结。常见维度包括输入与输出 token、模型费用、工具调用数、并行分支数、外部写操作数、存储字节、墙钟时间和人工等待期限。预算不是监控标签，而是每次签发动作前必须检查的前置条件。

对可预估动作，先做 reservation，再在收到回执后按实际 consumption 结算并释放差额。若只在调用完成后记账，多个并发分支都可能看到相同余额并共同超支。reservation 必须带到期时间，worker 崩溃后由恢复器根据动作回执结算或释放。

export type ResourceVector = {
  modelTokens: number;
  modelCostMicros: number;
  toolCalls: number;
  externalWrites: number;
  wallClockMs: number;
};

export type BudgetState = {
  limit: ResourceVector;
  consumed: ResourceVector;
  reserved: ResourceVector;
  revision: number;
};

export type Reservation = {
  reservationId: string;
  runId: string;
  actionId: string;
  amount: ResourceVector;
  expiresAt: string;
};

预算计算要保守但不能无限夸大。模型输出上限可直接用于 token reservation；工具执行时间可用历史高分位加安全系数；未知工具可以先分配小额度，在明确进度点续租。一次性预留整个最大额度会降低利用率，不做预留则失去强上限。

运行时还应维护不可花完的恢复储备，例如总 deadline 的最后 10% 只用于保存状态、对账和取消，成本预算留一小部分用于查询外部动作结果。否则预算耗尽发生在副作用之后，系统连确认是否成功的能力都没有。

准入控制应在排队之前

准入控制验证请求是否合法、预算是否可承诺、队列是否仍有业务价值，以及依赖是否健康。无法在截止时间前启动的任务应立刻返回容量错误或提供稍后重试时间，而不是先接受再悄悄超时。

可以用 Little 定律粗略检查积压：

L=λWL = \lambda WL=λW

其中 LLL 是系统中平均任务数，λ\lambdaλ 是到达率，WWW 是平均停留时间。若到达率持续高于处理率，任何有限队列最终都会满；扩队列只会增加等待时间。对有截止时间的 agent，排队时间达到剩余期限的一定比例后，任务应被淘汰或降级。

准入决策可返回接受、降级接受、延迟接受或拒绝。降级方案必须预先验证，例如限制并行分支、换用较小模型、只执行只读分析、减少生成长度；不能在过载时临时让模型“尽量简单”，因为它不可预测且难审计。

高风险写操作与低风险只读请求应使用独立容量池。否则一次批量分析可能占满 worker，阻止紧急取消或补偿动作。控制平面、恢复器和审批处理器也要保留专用连接与线程，确保数据平面过载时仍能刹车。

队列必须有界且感知年龄

队列平滑突发流量，但积压会把实时请求变成陈旧工作。AWS 的 Fail Fast and Limit Queues 指南建议测量消息年龄、配置死信队列，并在结果不再有价值时丢弃旧消息；它也警告复杂和简单请求混在一个队列会导致资源互相干扰。REL05-BP04给出了 agent 调度可以直接采用的原则。

每条排队项应带 enqueued_at、not_before、deadline_at、优先级、预计资源向量和公平性键。调度前重新检查，而不是相信入队时状态：用户可能已取消，审批可能过期，依赖可能熔断，预算也可能被同一运行的其他分支消费。

有界队列的满载策略需显式选择：拒绝最新任务保护已承诺工作；丢弃最旧任务保护新鲜度；转入 spillover 队列供离线处理；或只接收高优先级控制动作。每种选择都要对用户可见，不能无声丢弃。

死信队列不是长期仓库。进入死信需要结构化原因、原动作身份、最后回执和可执行的处置路径；系统监控死信年龄与数量，并提供重放前的策略与参数复核。直接把死信批量重投会重现原过载或重复副作用。

公平调度防止大任务独占

简单 FIFO 会让一个拥有大量并行分支的运行占满槽位。可以按租户或运行使用加权公平队列，每轮只发放有限量子，再把仍可运行的任务放回队列。高优先级可以影响权重，但要设置配额，防止所有调用者都声明最高优先级。

调度单位应比整个运行小、比单个 token 大，通常是一次模型调用或一次工具动作。运行在等待外部结果时释放 worker 槽位，只保留持久状态；恢复事件到达后再重新入队。阻塞线程等待审批数小时会虚耗容量，也让扩容错误地跟随等待量。

调度策略 优点 风险 适用场景
FIFO 简单、顺序直观 队首阻塞 同质短任务
严格优先级 紧急任务快 低优先级饥饿 控制与恢复通道
加权公平 租户隔离 实现与调参复杂 多租户平台
最早截止时间 减少过期 长期限任务可能饥饿 强 deadline 服务
成本感知量子 提高资源利用率 估算偏差 模型与工具混合负载

调度器需要同时限制每运行的并发宽度。模型规划出二十个并行搜索，不代表平台应同时执行；可以按依赖容量和剩余预算分批。并行度提高会缩短关键路径，但也增加重试放大、外部限流和上下文合并成本。

背压要跨越协议边界

下游容量不足时，背压信号应一路返回到动作签发与运行准入。模型 API 的 429、工具连接池等待、队列年龄、数据库延迟和 worker 饱和度都可成为信号。仅把它们记录成指标，而继续接受工作，不构成背压。

同步接口可返回明确的 overloaded 状态和重试建议；异步接口可降低消费速率、推迟 not_before 或暂停特定能力的新动作签发。流式模型响应需要有界缓冲：消费者变慢时暂停读取、减少生成，或取消调用，不能让内存无限积累 chunk。

背压控制器应使用平滑窗口和迟滞，避免容量在开关状态间频繁抖动。恢复要逐步放量，因为积压和重试会在依赖刚恢复时同时涌入。可设置冷启动并发、每周期增量和错误率回退阈值。

熔断与背压的区别在于：背压表达“当前容量有限，请减速”，熔断表达“这个依赖持续失败，暂时不要调用”。二者都应按能力隔离。例如图像模型限流不应阻止文本模型和取消操作。

运行资源与沙箱资源要双层约束

逻辑预算控制 token、工具次数和成本，操作系统预算控制 CPU、内存、进程、磁盘和网络。两层必须同时存在。运行时可能认为一个工具只调用一次，但该工具在沙箱内创建数千进程或填满磁盘。

Kubernetes 的 CPU limit 会节流，内存 limit 可能触发 OOM；因此运行时收到容器终止时要区分资源耗尽与业务失败。资源耗尽通常不应原样重试，因为相同输入很可能再次耗尽。策略可以缩小输入、提高经过授权的额度、换专用池或转人工。

每个沙箱应有 CPU、内存、PID、临时磁盘、网络字节和最大持续时间限制。多租户还要限制每租户同时存在的沙箱数。宿主资源水位达到保护阈值时，优先终止可恢复的低优先级尝试，并依赖检查点续跑；不要挤占状态存储和控制平面。

资源回执与业务回执同样重要。模型网关返回实际 token 与费用，沙箱返回峰值内存、CPU 时间和网络用量，工具适配器返回外部配额消耗。运行时以这些事实结算 reservation，并将偏差反馈给下一次估算。

过载状态机与降级策略

平台可定义 normal、constrained、shedding 和 recovery 四个容量状态。正常时按标准预算接受；受限时降低并行度并延迟低优先级任务；卸载时只接受控制、恢复和高价值请求；恢复时小步增加容量并观察错误率。

容量状态变化必须带原因和有效范围，并进入运行账本。若一个运行在 constrained 状态下被换用降级模型，终态应记录这一事实，评估系统也要分组比较，避免把容量降级误判成模型自然波动。

降级顺序应由产品提前确认。一个报告 agent 可以从“完整分析”降为“只提供已有数据摘要”；一个支付 agent 不能因为过载就跳过风控。安全和授权控制永远不能作为性能降级项。

验收与演练

负载测试不能只增加入口 QPS，还要混合短运行、长运行、宽并行、审批等待、失败重试和大输出。观察每租户公平性、队列年龄、预算超支率、控制请求延迟和依赖恢复后的流量尖峰。

关键断言包括：任何运行不能超过冻结预算；任何租户不能占满全局槽位；队列满时有明确拒绝；取消和补偿在过载时仍有保留容量；worker OOM 后从检查点恢复且不重置预算；供应商解除限流后没有重试洪峰。

时间与重试策略见重试、超时与取消，跨小时释放容量并等待决策的设计见人工审批、中断与恢复。

小结

  • 以动作、运行、租户、依赖和平台五层预算共同控制不可预测负载。
  • 在动作签发前 reservation，按真实回执结算，恢复时不重置余额。
  • 把准入放在排队之前，队列必须有界、感知 deadline 与消息年龄。
  • 用公平调度和每运行并发宽度防止一个大任务或租户独占资源。
  • 把下游容量信号传播回准入与动作签发，建立逐步恢复而非瞬间放量。
  • 为控制、取消、对账和补偿保留独立资源池，使过载时仍能安全停机。
