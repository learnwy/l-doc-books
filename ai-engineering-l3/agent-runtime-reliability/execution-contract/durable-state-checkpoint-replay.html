持久状态、检查点与回放

“保存一下状态”听起来简单，直到运行在模型回复后、写数据库前崩溃，或在工具成功后、保存结果前断电。可靠运行时不能假设崩溃只发生在步骤边界；它必须定义每个边界两侧的事实，并让恢复过程在最坏时刻仍得到唯一、可解释的下一步。

核心概念

持久化不是把内存对象序列化一次，而是建立一条可恢复的事实链。常用的三层结构是追加事件、状态投影与周期检查点：事件说明发生了什么，投影服务当前查询与调度，检查点缩短重建路径。外部副作用的结果需要独立回执，不能靠检查点中的布尔字段冒充。

flowchart LR
    Input[启动信封] --> EventLog[追加事件日志]
    EventLog --> Projector[状态投影器]
    Projector --> Current[当前运行状态]
    EventLog --> Snapshotter[检查点生成器]
    Snapshotter --> Checkpoint[版本化检查点]
    Checkpoint --> Recovery[恢复器]
    EventLog --> Recovery
    Recovery --> Worker[新 Worker]
    Worker --> EventLog
载体 主要用途 写入模式 不能独自证明什么
事件日志 顺序事实与审计 仅追加 当前查询是否高效
状态投影 调度、检索、条件更新 覆盖但带修订 历史为什么变成这样
检查点 缩短恢复和分叉路径 周期替换 检查点后发生的事件
副作用回执 证明外部动作结果 按动作身份写一次 整个运行是否完成
对象存储产物 大模型输出、文件、证据包 内容寻址 控制流是否已消费它

LangGraph 的持久化层会按 step 保存 checkpoint，并用 thread_id 定位状态；其文档还明确区分 replay 与读取缓存：从旧检查点之后的节点会重新执行，包括 LLM 调用、API 请求和中断。LangGraph Persistence提供了一个重要警告——回到旧状态不等于安全复现旧世界，非确定性调用仍可能产生新结果。

原子边界决定能否恢复

运行时最重要的事务边界是“接受一个结果并决定下一动作”。如果工具结果写入回执表，但运行游标尚未推进，恢复器应读取同一回执并重新计算决策；如果游标已经推进却没有结果事实，状态就是损坏的。前者允许至少一次投递，后者只能靠人工猜测。

在单数据库内，可以用同一事务完成四件事：验证当前修订，写入输入或回执引用，追加事件，更新状态投影。向队列发布后续工作则需要事务外箱：事务里写 outbox 记录，由独立投递器发送并以消息身份去重。不要在数据库提交后直接调用消息系统并期望两个系统同时成功。

一个恢复友好的提交接口可以表达为：

export type TransitionInput = {
  runId: string;
  expectedRevision: number;
  commandId: string;
  eventType: string;
  payloadRef: string;
  nextPhase: string;
  nextCursor: string | null;
  outboxMessages: Array<{
    messageId: string;
    topic: string;
    bodyRef: string;
  }>;
};

export type TransitionResult =
  | { kind: 'committed'; revision: number }
  | { kind: 'already_committed'; revision: number }
  | { kind: 'revision_conflict'; actualRevision: number };

commandId 让同一状态转换可以安全重送。若数据库发现该命令已提交，就返回原修订，而不是再追加一份事件。payloadRef 指向不可变内容，避免在事件日志中复制大段模型输出。内容存储应以摘要校验，读取失败要进入明确的存储损坏路径。

跨数据库或跨地域时，很难获得一个全局事务。此时应选择单一事实所有者，并把其他写入视为可重试的投影。比如运行事件库是事实源，搜索索引、分析仓库和通知服务都可以从事件重建；反过来让多个系统各自声明“当前状态”会造成无法裁决的分叉。

检查点不是任意内存快照

可恢复检查点只保存稳定、可版本化、可验证的数据。打开的 socket、线程句柄、未完成 Promise、临时凭据和 SDK 私有对象都不应直接进入检查点。应保存恢复这些资源所需的逻辑身份，例如工具调用身份、响应游标、凭据引用和等待条件。

检查点建议包含：

  • schema_version 与解释器版本，决定由哪段迁移代码读取。
  • run_revision 与最后消费的事件序号，阻止把旧快照覆盖到新事实上。
  • 规划状态的规范化表示，包括目标、已知事实和待决动作，但不保存无法审计的进程闭包。
  • 预算余额与截止时间，恢复不能重置 token、工具次数或墙钟预算。
  • 待处理审批、定时器和取消请求的稳定身份。
  • 对大对象的内容摘要与引用，恢复时先校验再使用。

检查点频率是恢复成本与写放大的权衡。若每个模型 token 都做快照，存储与锁争用会吞噬吞吐；若只在运行结束保存，长运行恢复就要读取巨大历史。更稳妥的策略是在语义边界保存：模型响应完整落地、工具回执被接收、进入长时间等待、预算跨过阈值，以及事件历史达到大小上限。

检查点创建必须基于已提交事件序号。生成器先读取一致视图，写入内容寻址对象，再用条件更新把“最新检查点指针”指向它。若指针更新失败，未引用对象可以由垃圾回收清理，不能反过来删除可能已被另一个并发恢复器引用的对象。

回放、重算与复用结果是三件事

回放是用已记录事实重新运行确定性决策代码，以重建状态或验证兼容性；重算是再次调用模型或函数产生新结果；复用结果是读取先前持久化输出。三者成本、风险和语义完全不同，接口必须显式区分。

Temporal 的 Replay 会把代码生成的命令与既有 Event History 比较；如果历史中已有对应事件，执行继续，如果生成的命令序列不匹配，则报告非确定性错误。Temporal Workflow Definition明确要求把 LLM 调用、API 调用和数据库查询等非确定性交互放到回放路径之外。这意味着运行逻辑可以重放，但世界交互只能读取记录或作为新的有身份动作执行。

操作 是否调用外部系统 是否可能产生不同结果 典型用途
回放 否 确定性代码不应不同 状态重建、兼容测试
复用 否 读取同一内容摘要 崩溃恢复、重复投递
重算 是 是 人工要求刷新、显式分叉
对账 只读查询 可能看到更新状态 结果未知时确认事实

模型输出天然非确定，哪怕模型名和参数不变也不能作为可重放函数。正确路径是先把请求规范化并签发 model_call_id，调用模型网关，完整保存响应与用量回执，再让决策代码消费该响应。恢复时若回执已存在就复用；不存在时才按同一调用身份重送，并依赖供应端或网关幂等策略避免重复计费与重复输出混淆。

重新从旧检查点运行应创建分叉身份，不能把新事件附加到原历史上。分叉记录父检查点、触发者、原因和新的策略版本，使评估人员能够比较两条轨迹，也防止调试操作篡改生产审计链。

代码升级需要历史兼容测试

正在等待审批的运行可能跨过多次部署。任何改变状态机边、步骤顺序、动作身份或序列化格式的代码，都可能让旧历史无法解释。迁移策略必须在部署前决定，而不是让第一个恢复请求充当实验。

三种常用策略各有代价：旧 worker 排空最简单，但长等待会拖延数月；版本化解释器让新旧逻辑并存，维护成本更高；检查点迁移能收敛版本，但必须证明迁移前后完成语义等价。不要通过直接改事件历史修复兼容问题，历史一旦可改就不再是证据。

历史兼容门应收集脱敏的真实事件样本，至少覆盖成功、失败、取消、审批等待、结果未知和补偿路径。新版本对每段历史做 dry replay，比较生成的命令类型、动作身份、预算余额与预期终态。若差异是有意的，需要显式版本标记；若不是，就阻止发布。

序列化迁移要保持未知字段容忍与必需字段校验之间的平衡。读取器可以忽略新版本的可选字段，但不能为缺失的身份、修订或策略版本猜默认值。缺少关键字段时进入隔离队列，让迁移器或人工处理。

存储损坏与灾难恢复

“数据库高可用”不等于运行历史永不损坏。应用 bug 可能写入不合法事件，运维操作可能恢复到不一致时间点，对象存储也可能缺少被事件引用的产物。运行时需要数据级不变量和定期恢复演练。

每条事件可以包含前一事件摘要，形成运行内哈希链，用于检测删改和顺序破坏；这不是替代访问控制的区块链方案，而是低成本完整性校验。检查点保存事件序号、状态摘要和引用对象摘要。恢复器发现任一不一致时停止自动执行，避免在错误上下文中继续产生副作用。

备份恢复目标应同时描述恢复点目标和恢复时间目标。更关键的是，恢复后的系统必须防止旧队列消息与新数据库状态交叉：切换前冻结或隔离消费者，恢复事实库，重建投影，再按事件序号恢复投递。仅恢复数据库而保留原消息积压，可能让已完成动作被再次消费。

灾难演练至少验证：从备份恢复一条等待中的长运行；重建状态投影；校验内容引用；恢复审批定时器；拒绝旧租约持有者；复用已保存模型与工具回执；继续剩余预算而不是重置预算。

恢复算法与测试矩阵

恢复器可以遵循固定顺序：加载启动信封与最新有效检查点，验证摘要和 schema，读取检查点后的事件，重建状态，核对当前租约与取消请求，再为未决动作查找回执。只有在事实完整、预算未耗尽、策略兼容时，才签发新租约继续。

不要只测试“步骤开始前崩溃”。对每个外部动作注入至少四个崩溃点：意图提交前、意图提交后但调用前、外部成功后但回执保存前、回执保存后但状态推进前。第四种应直接复用结果；第三种必须查询外部状态或进入结果未知处置，绝不能自动假定未执行。

还要测试重复消息、乱序消息、检查点落后、对象引用缺失、代码版本不兼容、长审批跨部署、取消与成功同时到达。每个场景的断言不是“任务最终没报错”，而是事件历史合法、外部副作用数量正确、预算未重置、终态可解释。

运行身份与状态机的基础见运行时执行契约，外部动作证明机制见幂等与副作用回执。

小结

  • 事件保存顺序事实，投影服务当前查询，检查点缩短恢复路径，回执证明外部结果。
  • 在同一事务中提交输入事实、事件、状态修订和 outbox，避免内部半提交。
  • 检查点只保存稳定逻辑身份和内容引用，不序列化进程资源。
  • 明确区分确定性回放、复用持久结果和重新调用外部系统。
  • 通过真实历史 dry replay 验证代码升级兼容性，不修改旧事件掩盖问题。
  • 为最坏崩溃点、数据损坏和备份恢复建立持续测试矩阵。
