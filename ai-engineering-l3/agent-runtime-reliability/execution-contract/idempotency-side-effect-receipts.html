幂等与副作用回执

一次退款请求超时后，最危险的做法是立刻再发一次。超时只说明调用方没有及时看到结果，不能证明支付系统没有完成退款。Agent 会自动重试并组合多个工具，因此它比普通客户端更容易把“结果未知”误判成“尚未执行”，最终产生重复邮件、重复部署或重复资金动作。

核心概念

可靠副作用协议把一次动作拆成意图、传输尝试、外部执行与回执四层。意图描述业务上只应发生一次的事情；传输尝试允许因网络故障重复；外部系统以幂等键识别同一意图；回执记录外部系统认可的最终结果。运行时只有看到可信回执或完成对账，才能推进后续步骤。

sequenceDiagram
    participant R as Agent运行时
    participant S as 意图存储
    participant T as 工具适配器
    participant E as 外部系统
    R->>S: 提交动作意图与参数摘要
    S-->>R: 返回稳定 action_id
    R->>T: 执行 action_id
    T->>E: 请求 + idempotency_key
    E-->>T: 外部对象与 request_id
    T->>S: 保存规范回执
    S-->>R: 回执已提交
    R->>R: 验证效果后推进状态
身份 表示什么 重试时是否变化 典型生成方
action_id 运行内一次语义副作用 不变 Agent 运行时
idempotency_key 外部 API 的去重范围 不变 工具适配器
attempt_id 一次网络或 worker 尝试 变化 调度器
provider_request_id 外部系统收到的一次请求 可能变化 外部系统
effect_id 已创建的真实业务对象 成功后稳定 外部系统
receipt_id 本地保存的一份规范证据 不变 回执存储

Stripe 的 API 文档说明，带同一幂等键的创建或更新请求可以安全重发，其 v1 实现会保存第一次开始执行后的状态码和响应体，连 500 结果也会被复用；相同键配不同参数会报错。Stripe Idempotent Requests展示了一个成熟但有范围限制的实现：键会过期、校验失败可能不会保存结果、不同 API 版本语义也不同。运行时不能把“供应商支持幂等”缩写成永远的 exactly-once 保证。

动作身份必须从业务意图派生

幂等键如果每次重试都随机生成，就没有去重作用；如果只用 run_id，同一运行中的两封不同邮件又会错误合并。正确粒度通常是 tenant_id + run_id + logical_step + action_kind + target_identity，再加规范化参数摘要防止同一身份被换参复用。

动作身份应在模型输出通过 schema 与策略验证后、任何外部调用前创建。模型可以重新措辞计划，但相同语义步骤必须解析到同一个 action_id。如果规划器真正改变了目标或参数，就需要新动作身份，并以“取代旧动作”的显式事件连接两者。

export type EffectIntent = {
  actionId: string;
  runId: string;
  stepId: string;
  tenantId: string;
  toolName: string;
  targetKey: string;
  canonicalArgsDigest: string;
  policyVersion: string;
  approvalId: string | null;
  createdAt: string;
};

export type EffectReceipt = {
  receiptId: string;
  actionId: string;
  status: 'confirmed' | 'rejected' | 'unknown' | 'compensated';
  providerRequestId: string | null;
  effectId: string | null;
  responseDigest: string | null;
  observedAt: string;
  evidenceRef: string;
};

规范化参数不能简单使用原始 JSON 字符串，因为键顺序、默认值、时间格式和空字段会制造伪差异。适配器应定义 canonical form：排序对象键、展开影响效果的默认值、统一单位，并只排除明确不影响语义的传输字段。参数摘要与原参数引用同时保存，摘要用于比较，引用用于审计。

目标身份同样重要。send_email(user@example.com) 与 send_email(customer_id=42) 可能指向同一收件人，但运行时不知道业务是否允许合并。工具契约应暴露稳定业务主键，或由适配器解析后回写。不要让模型自行决定幂等作用域。

回执是一等领域对象

回执不是一行“tool succeeded”日志。它要能回答外部系统接收了什么、产生了哪个对象、什么时候观察到、证据能否再次查询，以及本地参数是否与外部效果一致。高风险动作还应包含审批身份、执行主体、凭据作用域和策略版本。

回执状态至少区分：确认成功、明确拒绝、结果未知和已补偿。网络超时、进程崩溃或响应解析失败都属于未知，不能自动落成失败。回执写入使用 action_id 唯一约束；重复响应到达时，若内容摘要相同就返回原回执，若不同则触发冲突告警而不是覆盖。

本地观察 可推断结论 下一动作
连接前失败 外部系统大概率未收到，但仍按契约处理 同键重试
收到明确业务拒绝 动作未成功且原因稳定 记录拒绝，不盲目重试
收到限流或暂时错误 是否执行取决于供应商语义 按文档与预算重试
请求已发送后超时 结果未知 同键重试或查询效果
收到成功但保存回执失败 外部已成功、本地未知 查询并重建回执
回执已保存后进程崩溃 结果可恢复 读取回执并推进

回执存储最好与运行事件存储共享事务边界。若工具适配器独立部署，它可先把回执写入自己的耐久 inbox，再向运行时发布“回执可用”消息；运行时消费消息时按 receipt_id 去重。消息本身不是回执，丢失消息后仍应能按 action_id 查询证据。

回执中不应默认保存完整敏感结果。可把密文或受控对象放入专用存储，事件只保留内容摘要和授权引用。观测系统需要知道动作类型与状态，不必得到信用卡、邮件正文或访问令牌。

事务外箱与收件箱

本地状态更新与消息发布之间存在经典双写问题。事务外箱通过在业务事务中同时写入状态和待发送消息，让投递器可以至少一次发送；消费者通过收件箱记录已处理的消息身份，从而把重复投递转化为重复读取同一结果。

外箱解决“状态已提交但消息丢失”，收件箱解决“消息重复导致状态重复推进”，二者都不直接解决外部 API 的副作用。对外部 API 仍需动作身份、供应商幂等键和回执。把三层去重串起来，才能覆盖运行时、消息系统和业务系统之间的失败窗口。

一个稳健的处理顺序是：

  1. 以运行修订为条件插入动作意图，并写出箱消息。
  2. 投递器读取出箱，向工具 worker 至少一次发送 action_id。
  3. worker 先查本地回执；已有确认结果就直接返回。
  4. 未有回执时，用稳定幂等键调用外部系统。
  5. 保存外部响应和效果身份，再发布回执消息。
  6. 运行时收件箱去重，验证回执参数摘要，推进游标。

每一层都允许崩溃后重新开始，但每次重新开始都先查询事实，而不是重新创造身份。这比追求跨系统分布式事务更现实，也更容易审计。

结果未知必须先对账

有些系统不支持幂等键，或键的保留时间短于运行寿命。此时工具适配器需要专门的 reconciliation API：按业务键查询效果、按时间窗和参数匹配候选结果，必要时请求人工确认。若无法唯一确认，就进入 repair_required，而不是猜测。

对账逻辑应优先使用外部业务主键。例如创建部署前先生成 deployment_ref 并传给外部系统；恢复时按该引用查询。若只能用模糊时间窗搜索，匹配结果必须标注置信度，多个候选就停止自动化。

Stripe 的低层错误指南指出，网络错误会让客户端不知道服务器是否收到请求，建议用相同幂等键和相同参数持续重试到获得确定结果；它也说明某些限流与认证错误发生在幂等层之前，可能不被缓存。Stripe Advanced Error Handling说明错误分类必须来自具体供应商契约，不能仅按 HTTP 状态码写一个全局重试表。

对账也是事故后的核心能力。操作人员需要从 action_id 跳转到外部 effect_id，从外部对象反查发起运行，并看到参数摘要与审批。缺少双向索引时，人工只好在日志里猜哪个请求造成了哪个效果。

重试安全来自有界策略

幂等不意味着可以无限重试。每次重试仍消耗队列、连接、配额和供应商成本；供应端过载时，无界重试会放大故障。AWS Well-Architected 建议使用指数退避、抖动与最大重试次数，并警告多层同时重试会形成乘法级重试风暴，也不要重试非幂等操作。控制和限制重试把“验证服务幂等”列为实现重试前提。

动作策略应定义可重试错误集合、最大尝试次数、最大累计时间、退避上限和一次负责重试的层。若模型 SDK、模型网关、运行时和工具客户端都默认重试三次，最坏调用数可达到 34=813^4=8134=81 次。可靠架构通常把传输级短重试留给最接近依赖的一层，把跨秒或跨分钟的业务重试交给运行时，并让上层只观察同一 action_id。

永久错误需要改变计划或交给人，而不是换一个随机参数再试。权限拒绝、参数验证失败、资源不存在和不可补偿的业务冲突应进入明确分类。模型可以提出修正，但新参数意味着新动作身份和重新审批。

幂等、补偿与 exactly-once 的边界

幂等让同一意图重复提交不会产生额外效果；补偿用一个新动作抵消已确认效果；exactly-once 是端到端可观察语义，不是消息中间件的单个开关。即使消息系统承诺恰好一次处理，外部工具仍可能在提交响应前崩溃。

补偿动作也需要独立 action_id、幂等键和回执。例如退款的补偿不是“删除退款记录”，而可能是重新扣款或建立应收，这涉及新的业务与法律约束。必须记录 compensates_action_id 关系，保留原回执，不能覆盖成“好像从未发生”。

有些效果不可补偿：邮件已被阅读、代码已公开、秘密已泄露。运行时应把可逆性纳入动作风险级别，在执行前要求更强审批或使用预览与两阶段提交。工具元数据只能是提示，不能替代本地策略验证；MCP 的 schema 甚至明确说明工具 annotations 不保证真实，客户端不应基于不可信服务器提供的提示做安全决定。MCP Schema Reference中的 idempotentHint 和 destructiveHint 适合发现能力，不适合成为唯一控制依据。

故障注入验收

副作用协议需要在精确故障点验证。测试用替身外部系统记录每个幂等键与效果，运行时在请求前、请求已接收、响应返回、回执写入和状态推进处随机终止 worker。恢复后断言每个语义动作至多产生一个未补偿效果，并且所有运行都到达确认、拒绝或需修复终态。

还应测试幂等键过期、相同键换参数、供应商返回冲突响应、回执消息重复、回执乱序、对账发现多个候选、补偿失败与人工修复。成功路径的单元测试无法覆盖这些协议窗口。

运行的稳定身份与终态见运行时执行契约，检查点如何复用回执见持久状态、检查点与回放。

小结

  • 为一次语义副作用创建稳定 action_id，把网络尝试身份与业务意图身份分开。
  • 在外部调用前持久化意图，在结果后保存带效果身份的规范回执。
  • 将超时视为结果未知，优先同键重试或查询外部事实，绝不自动当作未执行。
  • 用事务外箱、收件箱和供应商幂等协议覆盖三个不同的重复窗口。
  • 让重试有错误分类、尝试预算、截止时间和唯一负责层。
  • 把补偿建模为新的可失败动作，承认不可逆效果不存在真正回滚。
