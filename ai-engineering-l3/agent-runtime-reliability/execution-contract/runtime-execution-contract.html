运行时执行契约

用户说“把退款处理完”，模型可能先查订单、再判断规则、最后调用退款工具。对演示程序而言，这是一串函数调用；对生产系统而言，它是一项可能跨进程、跨服务、跨小时的责任。运行时执行契约的价值，是让任何接手者都能回答：这项责任是谁发起的、当前走到哪里、下一步允许做什么、已经产生了哪些外部影响，以及什么结果才算结束。

核心概念

运行实例是具有稳定身份和受控生命周期的执行实体。它不是聊天会话的别名，也不是某次 HTTP 请求的临时上下文。会话可以包含多次运行，一次运行也可能经历多次 worker 尝试；如果把三者混为一谈，重连就会生成第二个任务，重试就会变成第二次业务动作。

契约至少包含四类事实：不可变的启动信封、可版本化的运行状态、追加式的动作记录，以及明确的终态结果。启动信封冻结目标、租户、授权范围和输入摘要；运行状态只描述当前可执行位置；动作记录证明每一步发生过什么；终态说明责任已经成功、失败、取消还是需要人工处置。

stateDiagram-v2
    [*] --> Accepted
    Accepted --> Running: 获得执行租约
    Running --> Waiting: 等待工具或审批
    Waiting --> Running: 收到结果或决定
    Running --> Succeeded: 目标达成
    Running --> Failed: 不可恢复故障
    Running --> Cancelling: 收到取消请求
    Waiting --> Cancelling: 收到取消请求
    Cancelling --> Cancelled: 清理与对账完成
    Failed --> RepairRequired: 外部状态不确定
    RepairRequired --> Succeeded: 人工确认已完成
    RepairRequired --> Failed: 人工确认未完成

状态机中的每条边都应由一条带版本的命令触发，而不是任意代码直接改字段。这样才能用比较并交换防止两个 worker 同时推进同一运行，也能在事故后解释一次状态变化为何合法。

概念 稳定身份 可重复次数 所有权
会话 session_id 包含多次运行 产品交互层
运行 run_id 对一个用户目标唯一 Agent 运行时
尝试 attempt_id 故障后可增加 调度与 worker
步骤 step_id 运行内稳定 规划器与运行时共同约定
动作 action_id 同一语义动作稳定 运行时
外部请求 request_id 每次传输可不同 工具适配器

Temporal 将 Workflow Execution 描述为可持久、可恢复的执行单元，并用事件历史支持回放；它同时区分 Workflow Definition 与 Workflow Execution。这一分离提示我们：代码版本不是运行身份，worker 进程也不是事实存储。Temporal Workflow Execution 文档给出的“从最后记录事件继续”是强实现之一，但这里的契约同样适用于数据库加队列的自研运行时。

启动信封冻结责任

启动信封要在接受运行时一次写入。它应保存原始请求的内容寻址摘要，而不是只保存可能被后续覆盖的对象引用；同时记录调用者身份、租户、数据边界、策略版本和可接受的终态。若目标依赖一个会变化的业务对象，应同时保存对象版本或读取时间点。

一个最小契约可以写成如下类型。代码中的字段名是稳定协议，字段含义需要在服务端校验，不能把类型检查当授权检查。

export type RunEnvelope = {
  runId: string;
  sessionId: string | null;
  tenantId: string;
  subjectId: string;
  goal: string;
  inputDigest: string;
  inputRef: string;
  policyVersion: string;
  plannerVersion: string;
  deadlineAt: string;
  budget: {
    modelTokens: number;
    toolCalls: number;
    wallClockMs: number;
  };
};

export type RunState = {
  runId: string;
  revision: number;
  phase: 'accepted' | 'running' | 'waiting' | 'cancelling' | 'terminal';
  cursor: string | null;
  leaseOwner: string | null;
  leaseExpiresAt: string | null;
  terminalKind: 'succeeded' | 'failed' | 'cancelled' | 'repair_required' | null;
};

runId 应由接入层根据一次明确的创建意图生成，并通过客户端请求键去重。不要让 worker 在每次投递时生成它。deadlineAt 是整项责任的最终截止时间，单步超时只能从剩余时间中切片，不能反过来延长总期限。预算也属于启动信封，因为在运行中悄悄扩容会改变用户授权的成本与风险。

策略和规划器版本应按“运行开始时使用的规则”冻结。系统可以为后续步骤选择兼容升级，但必须把升级决定记成事件。否则相同输入在恢复后可能获得不同权限或生成完全不同的动作，而操作人员无法分辨这是模型随机性还是策略漂移。

状态转换必须满足不变量

可靠运行时不直接提供 setStatus("running") 这种宽接口，而提供表达意图的命令，例如“获取租约”“记录等待条件”“请求取消”“确认终态”。命令处理器同时验证当前修订、允许的前置状态和调用者权限。

建议至少维护以下不变量：

  • 每个 run_id 在任意时刻至多有一个有效执行租约；租约过期可以被接管，但旧持有者的写入必须因修订不匹配而失败。
  • terminal 状态不可被普通命令重新打开；修复应创建显式的人工处置事件，必要时派生新的运行。
  • 一个 action_id 只能对应一个规范化参数摘要；相同动作身份不得在恢复时换参数。
  • 等待状态必须包含等待对象、到期时间和恢复条件，不能只写一个布尔值。
  • 任何推进运行游标的提交，必须与产生该推进所需的内部事实原子写入。
  • 外部副作用不能仅凭运行游标推断完成，必须有可验证回执或进入结果不确定状态。

数据库中的典型推进语句以 run_id 和 revision 为条件更新。若受影响行数为零，worker 应重新加载事实，而不是盲目重试原写入。这样，晚到的模型响应、重复队列消息和已失效 worker 都无法覆盖更晚状态。

运行状态与事件历史承担不同职责。状态是当前视图，适合调度与查询；事件是变化证据，适合恢复、审计和派生新视图。只存事件会让热路径查询昂贵，只存状态则无法解释覆盖与回放。常见做法是在一个事务中追加事件并更新带修订的状态投影。

规划器只提议，运行时才承诺

规划器的输出应被视为动作提议，而不是已经发生的事实。提议可以包含工具、参数、预期效果和完成判据；运行时负责验证 schema、权限、预算、幂等能力和审批要求，再决定拒绝、等待或签发动作意图。

这条边界能阻止模型文本越过控制平面。例如模型生成“删除项目”，运行时不会因为字符串看起来确定就直接调用工具，而是把它规范化为受策略约束的动作对象，计算参数摘要，并检查当前主体是否拥有目标项目的删除能力。

阶段 规划器负责 运行时负责
感知 解释可用上下文 提供经过授权与裁剪的上下文
选择 提议下一语义动作 校验动作和参数
执行 不直接承诺外部状态 签发动作身份并调用工具
观察 解释工具结果 保存原始回执并分类结果
结束 提议目标已达成 验证完成判据并写终态

完成判据也不能只依赖模型说“已经完成”。退款运行应通过退款对象状态或支付系统回执验证；代码修改运行应通过工作区差异和质量门验证。自然语言总结是终态的解释，不是终态的证据。

终态要表达责任而非进程结果

进程退出码为零，只能证明 worker 没抛出未处理异常。用户关心的是目标是否完成、结果在哪里、是否产生副作用、是否还需动作。因此终态应携带 result_ref、完成判据、成本汇总、未解决风险和所有关键回执的引用。

建议区分四种主要终态：成功表示完成判据已验证；失败表示明确知道目标没有完成且无需继续自动恢复；取消表示系统已停止未来工作并完成必要对账；需要修复表示外部结果不确定或补偿失败，需要人类接手。把最后一种误报为失败，会诱导上层创建第二次运行，从而放大重复副作用。

客户端轮询或订阅的对象应是运行状态，而不是 worker 状态。即使 worker 重启、换节点或等待数天，run_id 的查询入口保持稳定。客户端取消也应写成请求并返回当前处置状态，因为取消无法撤销已经提交的外部操作。

契约版本与兼容迁移

长期运行会跨越代码部署。修改状态机、动作身份算法或事件 schema 时，必须明确旧运行如何继续。可选择让旧 worker 版本排空、使用版本化解释器，或在检查点处执行可审计迁移，但不能用新代码无条件回放旧事件。

Temporal 的确定性约束要求相同历史生成相同命令序列，并建议把 API、数据库和 LLM 等非确定性交互放入回放路径之外的 Activity；Workflow Definition 文档也指出，重排会产生命令的调用可能导致非确定性错误。自研系统即使不做严格确定性回放，也应借用同一原则：旧事实必须由兼容的解释器读取，非确定性结果必须先持久化再被决策代码消费。

迁移前应以真实事件历史做兼容测试：加载旧版本运行，执行到下一个安全点，比较新旧解释器生成的动作身份和终态。任何差异都要么通过版本分支解释，要么明确创建新运行，绝不能在生产恢复时才发现。

验收清单

可以用一组破坏性问题检查契约是否真实存在：重复发送创建请求会不会得到同一个 run_id；两个 worker 同时拿到消息时能否只有一个推进修订；等待审批时进程全部重启是否仍能恢复；旧模型响应晚到后是否会被拒绝；用户取消后已有工具动作如何对账；结果未知时上层是否会停止自动复制任务。

还应从数据层随机抽取一次运行，只依靠启动信封、状态、事件和回执重建完整时间线。若仍必须阅读某台机器的本地日志，说明事实所有权没有进入运行契约。

本章后续的持久状态、检查点与回放会展开状态如何重建，幂等与副作用回执则处理外部动作如何证明。章节概览可回到执行契约与持久状态简介。

小结

  • 用稳定 run_id 表示用户责任，用 attempt_id 表示可替换的执行尝试。
  • 把启动信封、带修订状态、追加事件和终态结果分开建模。
  • 让规划器提议动作，让运行时校验并承诺动作。
  • 通过租约与乐观并发控制拒绝晚到写入，不让重复投递变成重复推进。
  • 以完成判据和外部回执验证终态，不以模型声明或进程退出码代替证据。
  • 为跨部署恢复建立契约版本和历史兼容测试。
