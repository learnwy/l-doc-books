恢复、补偿与状态对账

Agent 在创建云资源、发出通知和更新工单后，最后一步失败。把数据库回滚到运行前并不能让邮件消失，也不能让外部资源自动删除。分布式副作用已经进入现实世界，恢复必须用新的业务动作把系统带到可接受终态，而不是假装历史从未发生。

核心概念

恢复首先分类事实，再选择方向。前向恢复继续完成原目标；后向恢复用补偿动作抵消已确认效果；状态对账处理调用结果未知；人工修复接管无法安全自动化的残余。四者不能互相替代，尤其不能在不知道动作是否发生时直接补偿。

flowchart TD
    Failure[步骤未正常返回] --> Known{结果是否确定}
    Known -->|明确未发生| Retryable{故障可恢复}
    Retryable -->|是| Forward[前向重试或替代路径]
    Retryable -->|否| Compensate[评估补偿]
    Known -->|明确已发生| Continue{目标仍可完成}
    Continue -->|是| Forward
    Continue -->|否| Compensate
    Known -->|未知| Reconcile[查询外部事实]
    Reconcile -->|唯一确认| Continue
    Reconcile -->|确认未发生| Retryable
    Reconcile -->|仍不确定| Manual[人工修复]
    Compensate -->|补偿完成| Terminal[可解释终态]
    Compensate -->|补偿失败| Manual
恢复方式 前提 产生的新副作用 目标
原动作重试 幂等且故障可重试 不应新增语义效果 完成原步骤
替代前向路径 业务允许替代 可能产生不同效果 完成用户目标
状态对账 有稳定业务键或查询接口 原则上只读 确认现实事实
补偿 原效果已确认且可抵消 一定会产生新效果 达到可接受一致状态
人工修复 自动证据不足或风险过高 由授权人员决定 收敛不确定性

AWS 的 Saga 指南把 saga 描述为一系列本地事务，失败时通过 continuation 做前向恢复或 compensation 做后向恢复；编排模式由中心协调器保存生命周期。AWS Saga Patterns提供了跨服务一致性的基础，但 agent 运行时还要处理模型重规划、审批与结果未知。

先构建故障结果格

异常类型不足以决定恢复。TimeoutError 既可能发生在请求尚未发出，也可能发生在外部已成功后。运行时需要综合传输阶段、动作回执、外部查询、幂等能力和业务对象版本，把结果归入“未发生、已发生、被拒绝、部分发生、未知”之一。

部分发生尤其危险。批量工具可能成功处理 100 个对象中的 73 个，再因限流返回失败。回执应列出每个子效果或提供可查询批次身份；恢复器只能重试剩余集合，不能把整个批次当一个布尔动作。

export type EffectObservation = {
  actionId: string;
  outcome: 'not_applied' | 'applied' | 'rejected' | 'partial' | 'unknown';
  effectRefs: string[];
  remainingTargetRefs: string[];
  evidenceRef: string;
  observedAt: string;
};

export type RecoveryPlan = {
  recoveryId: string;
  runId: string;
  mode: 'forward' | 'reconcile' | 'compensate' | 'manual';
  basedOnRevision: number;
  actions: string[];
  successCriteriaRef: string;
  deadlineAt: string;
};

故障分类本身要持久化，并引用当时的原始证据。恢复后代码升级可能改进分类器，但不能静默改写旧决定；如果重分类，就追加一条带操作者或新规则版本的事件。

优先前向恢复

前向恢复往往比补偿更符合用户目标。酒店预订失败时，更换酒店可能比取消已经买好的机票更好；生成报告时，替换不可用数据源可能比删除已计算结果更合理。运行时应先判断原完成判据能否通过重试、替代工具、降级结果或延迟继续满足。

前向重试要求动作幂等、剩余 deadline 和预算充足，并且错误分类是暂时性。替代路径是新计划，需要新的动作身份和可能的新审批；不能把替代供应商请求塞进原幂等键，因为它会产生不同外部效果。

对 pivot 之后的步骤，系统通常只能前向完成。pivot 是不可逆转折点，例如邮件发送、法律签署或资金最终结算。运行设计应把所有可验证前置条件放在 pivot 前，尽量缩短 pivot 后路径，并为后续动作提供强幂等与重试保证。

前向恢复也要有停止条件。若系统不断换模型、换工具和改计划，可能从“完成原目标”漂移成无边界探索。RecoveryPlan 冻结允许的替代范围、最大步骤和完成判据，超出就转人工。

补偿不是时间倒流

补偿是一项新的领域命令，目标是抵消业务影响或把系统带到另一可接受状态。它不一定按原步骤严格逆序，也不一定恢复原始数据，因为并发事务可能已经基于中间状态继续工作。

Microsoft 在 2026 年更新的 Compensating Transaction 模式强调，补偿必须考虑并发工作，步骤本身要幂等，补偿也可能失败，并且某些场景只有人工干预才能恢复。Compensating Transaction还建议记录每步如何撤销及其进度，让补偿可以从失败处恢复。

原动作 可能补偿 无法恢复的部分
预留库存 释放预留 等待期间错失的销售
创建部署 回滚版本或删除环境 已曝光的短暂行为
发送通知 发送更正通知 已读内容与外泄信息
创建退款 发起重新扣款或应收 手续费、用户体验、合规影响
写入工单 关闭或标记作废 已触发的人工流程

每个可补偿动作在执行前就应登记补偿模板、所需事实和不可逆条件。等待失败后再让模型“想一个撤销办法”会缺少原始参数、权限和业务约束。模板可以参数化，但最终补偿仍需策略校验与动作回执。

补偿序列可能并行，也可能因业务依赖需要特定顺序。比如先撤销公开 DNS，再删除后端资源能更快降低暴露；而退款流程可能必须先确认资金状态再恢复库存。顺序属于领域设计，不应由通用运行时猜测。

补偿失败不能覆盖原失败。运行账本保留原动作、原回执、补偿意图、每次补偿尝试和当前残余风险。最终状态可以是 compensation_incomplete 或 repair_required，并附上操作手册。

状态对账收敛未知结果

对账的首选依据是稳定业务键。运行时在动作前生成外部可接受的引用，例如订单操作号、部署引用或消息去重键；恢复时按该引用查询。若供应商只提供请求 ID，也要把它保存到中间发送记录，便于支持团队定位。

对账查询应只读、可重试、返回可验证版本。结果可能有三类：唯一对象与参数摘要匹配，确认已发生；明确不存在且供应商一致性窗口已过，确认未发生；存在多个候选或查询不可靠，保持未知。

最终一致系统需要等待窗口。刚写入后查询不到不能立刻判定未发生，运行时要根据供应商文档设置 not_before，使用有界退避。窗口结束仍无证据才进入未发生或人工路径。

如果没有稳定业务键，可用时间、主体、目标和参数摘要匹配，但这种推断必须携带置信度与候选列表。高风险动作只接受唯一强匹配；低风险可由策略允许自动选择。模型可以帮助摘要候选差异，但不能自行提升证据强度。

对账也适用于补偿。补偿超时后先确认其效果，再决定重试；否则会重复发出反向动作。所有写路径最终都回到同一套意图、回执和未知结果协议。

恢复计划需要自己的状态机

恢复不是原运行的一段异常处理代码，而是一项可暂停、可重试、可审计的子流程。它有稳定 recovery_id、依据的运行修订、选择模式、动作列表、预算、审批和终态。运行本身进入 recovering 或 repair_required，避免普通 worker 同时继续原计划。

恢复计划的每个动作仍走标准运行时：策略检查、预算预留、审批、沙箱、回执和对账。不要为“修故障”开管理员后门；事故压力正是越权与误操作最容易发生的时候。

可以把恢复状态分为 planned、executing、waiting、verified、failed 和 manual。verified 需要重新检查业务不变量，而不是补偿 API 返回 200 就算完成。例如释放库存后还要确认订单状态与库存数量一致。

多个恢复器争抢同一运行时，使用基于修订的恢复租约。较旧计划看到修订变化就停止，不能继续执行已经被人工修改的补偿序列。人工编辑恢复计划也产生新版本并使旧审批失效。

死信与人工修复面

自动恢复耗尽后，运行进入人工修复队列。队列项应是可行动的证据包：用户目标、当前终态、已确认效果、未知动作、失败的补偿、外部查询入口、建议选项和风险。只丢一条异常堆栈给值班人员会延长不确定状态。

人工修复接口提供受约束命令，例如“标记外部效果已确认”“重新执行指定补偿”“接受当前部分完成结果”“创建替代运行”，而不是允许任意改数据库状态。每条命令验证版本、权限与必需证据。

死信项要有责任组、严重度、业务 deadline 和升级规则。资金、权限和公开发布的未知效果应立即升级；低风险分析任务可以自动到期取消。队列年龄是用户风险指标，不只是运维积压。

修复完成后，不删除死信记录，而是写 resolution：采用何种证据、执行哪些动作、残余影响、是否需要事故复盘。之后将相同故障场景加入自动演练和评估集。

业务不变量与完成验证

恢复的目标不是所有技术步骤变绿，而是业务不变量重新成立。可把不变量写成可执行检查：每个订单最多一个有效退款；每次部署只有一个对外版本；取消运行不再签发新写动作；所有已确认外部效果都能追溯到审批和回执。

检查器必须从权威系统读取当前事实，并记录读取版本。模型输出可以解释差异，但不应单独决定金额、权限或一致性。复杂不变量可由多个确定性检查加人工确认组成。

恢复后的终态包含三个层次：技术流程结束、业务不变量验证、用户影响解释。只有三者齐全才标记 recovered。若业务接受部分完成，应明确记录接受者与范围，不要伪装成完全成功。

故障演练与验收

演练要覆盖结果未知和补偿失败，而不只是依赖返回错误。注入外部成功后断网、回执库不可写、对账读到陈旧副本、补偿执行一半、人工在恢复中修改对象，以及两个恢复器并发接管。

断言包括：原动作没有被重复执行；对账在一致性窗口内不误判；补偿使用新动作身份并可自身恢复；旧恢复计划无法覆盖新修订；人工修复有完整证据；最终业务不变量可验证。

执行隔离与能力限制见工具沙箱与安全边界，恢复责任如何与工作流引擎等系统分配见运行时边界与系统集成。

小结

  • 先把外部结果分类为未发生、已发生、被拒绝、部分发生或未知，再选择恢复方向。
  • 优先在完成判据允许时前向恢复，对替代路径创建新动作身份与审批。
  • 把补偿当新的、领域特定且可能失败的副作用，不把它当时间倒流。
  • 用稳定业务键、供应商请求 ID 与一致性窗口完成状态对账。
  • 为恢复计划建立独立身份、版本、租约、预算与终态。
  • 以业务不变量和用户影响验证恢复，而不是以异常处理代码结束为准。
