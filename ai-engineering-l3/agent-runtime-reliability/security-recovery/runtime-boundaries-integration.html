运行时边界与系统集成

Agent 平台常把规划、模型路由、工具调用、工作流调度和持久化都塞进一个“orchestrator”服务。初期代码很少，故障后却没人知道由哪一层重试、哪一层记账、谁拥有终态。清晰边界不是为了画更多盒子，而是为了让每个事实只有一个所有者、每个控制动作只有一个执行点。

核心概念

Agent 运行时拥有一次运行的生命周期与安全推进：稳定身份、状态修订、动作意图、等待、预算、取消、回执和终态。规划器拥有语义动作选择；模型网关拥有单次模型流量治理；工具适配器拥有特定外部系统协议；工作流引擎拥有跨服务流程和调度耐久性。运行时可以建立在工作流引擎之上，但不能把业务语义所有权交给引擎默认值。

AWS 的 agentic orchestration 指南区分规则式工作流与 AI 原生编排，并建议受控流程使用 Step Functions、自然语言与灵活目标使用 agent。Orchestration Models说明两种控制方式可以组合。运行时边界的任务，就是让确定性耐久机制承载非确定性规划，而不把二者混成一套隐式控制流。

与规划器的边界：提议与承诺

规划器输入是经过运行时选择的事实视图：目标、已确认观察、剩余预算、可用能力和拒绝约束。输出是结构化动作提议，包括动作类型、参数、理由、预期效果和完成判据。运行时不把自由文本当命令，而是验证 schema、策略、预算和幂等能力后签发 action_id。

export type PlanningSnapshot = {
  runId: string;
  revision: number;
  goal: string;
  factsRef: string;
  capabilityCatalogVersion: string;
  remainingBudgetRef: string;
  deniedConstraintsRef: string | null;
};

export type ActionProposal = {
  basedOnRevision: number;
  kind: 'model' | 'tool' | 'ask_user' | 'finish';
  capability: string;
  args: unknown;
  expectedEffect: string;
  completionEvidence: string;
};

basedOnRevision 防止晚到规划结果覆盖新事实。若运行在规划期间收到取消、工具回执或用户输入，修订已变化，运行时丢弃旧提议并重新规划。规划器无需自己锁数据库，也不应直接修改运行状态。

规划失败包括模型不可用、输出不合 schema、动作违反策略和无法在预算内给出计划。前两者可能重试，后两者应反馈结构化约束或转人工。不要让规划器通过换措辞反复试探策略；运行时记录被拒动作族和次数。

完成提议只是一个候选终态。运行时按业务完成判据验证必要回执和状态，才能提交 succeeded。规划器可以生成用户解释，但不能以自然语言声明取代事实。

与模型网关的边界：调用与运行

模型网关拥有供应商适配、认证、模型目录、路由、速率限制、熔断、缓存、单次请求计量和统一错误。Agent 运行时拥有为何调用、调用属于哪一步、是否可重试、剩余总预算和响应被哪个运行修订消费。

运行时向网关提交稳定 model_call_id、请求摘要、模型能力要求、最大 token、deadline、租户和追踪上下文。网关返回供应商请求 ID、实际模型、用量、费用、缓存命中、完成原因和内容引用。网关不应自行把失败模型响应变成新的 agent 步骤。

决策 模型网关 Agent 运行时
供应商认证与 API 差异 负责 不负责
选择满足能力的模型实例 按策略负责 提供能力与上限
单次请求短重试 可负责 读取尝试回执
跨步骤业务重试 不负责 负责
token 与费用事实 产生回执 计入运行预算
响应是否仍适用于当前状态 不判断 按修订判断
用户目标是否完成 不判断 验证完成判据

缓存也要分层。网关可按规范化模型请求缓存纯生成结果，运行时按 model_call_id 复用已确认响应。涉及实时数据、工具状态或不同授权上下文的 prompt 不能仅因文本相同就共享缓存。运行时把数据版本和策略摘要纳入请求身份，网关执行声明的缓存范围。

当网关过载时，它返回结构化容量信号，运行时决定等待、降级、改计划或终止。网关不应为了“成功率”无声换成不满足安全或质量要求的模型；任何 fallback 都返回实际选择与原因，进入运行账本与评估分组。

与工具适配器的边界：协议与业务事实

工具适配器把稳定动作协议映射到供应商 API，负责参数规范化、幂等键、凭据、错误分类、回执解析和状态查询。运行时负责动作身份、策略、审批、预算和跨工具完成判据。

适配器接口不只是 execute(args)，至少需要 prepare、execute、query、cancel 和可选 compensate 能力描述。prepare 解析目标并返回风险与预估资源；query 让结果未知可以对账；cancel 明确是否只是请求取消；compensate 返回新动作模板而不是直接改历史。

适配器发布的工具 schema 与运行时策略版本要关联。schema 升级若改变默认参数或幂等语义，正在等待审批的动作可能失效。兼容更新可继续，破坏性更新使旧动作进入重新准备或人工路径。

工具内部短传输重试必须回报尝试数，运行时才能防多层放大。适配器不能在收到永久业务拒绝后自行换参数，因为那是新业务动作，必须回到规划与审批边界。

与工作流引擎的边界：耐久调度与领域状态

工作流引擎擅长耐久定时器、事件历史、worker 重启、重试和跨服务步骤编排。Agent 运行时可以把“等待模型回执”“等待工具回执”“等待审批”“到 deadline 唤醒”实现为 workflow activities、signals 或 tasks，但 run_id、动作语义和业务终态仍属于运行时领域模型。

OpenAI Agents SDK 的运行文档列出 Dapr、Temporal 和 Restate 的 durable execution 集成，用于长运行、重启恢复与人工审批。Running Agents反映了合理组合：agent SDK 提供行为抽象，耐久引擎承载执行，但集成方仍要定义状态与副作用契约。

避免直接把引擎 task ID 当 run_id。引擎迁移、continue-as-new 或子工作流可能改变 task/run 标识，而用户责任需稳定。建立映射表：领域 run_id 对应一个或多个引擎 execution ID，运行事件保存映射变化。

也不要同时在引擎和运行时独立配置长重试。可让引擎负责可靠唤醒与消息投递，运行时的 RetryDecision 决定下一次时间和是否允许；或把特定 activity 的重试完全交给引擎，但将尝试回执纳入预算。唯一原则是某层拥有策略，其他层执行并报告。

workflow event history 不一定适合长期存储完整模型内容、敏感工具结果和业务审计。运行时账本保存领域证据与受控引用，引擎历史只保存恢复所需的最小命令和引用。这样可以独立管理保留期、加密和访问权限。

与评估和可观测系统的边界

追踪系统接收事件但不决定状态；评估系统读取完成轨迹并产生质量标签，但不直接重开运行；SLO 控制器可以触发降载或发布冻结，却通过明确命令影响运行时。避免让监控脚本直接修改业务表。

运行时发出统一 envelope：run_id、step_id、action_id、修订、事件类型、时间、状态与受控属性。模型网关和工具适配器延续 trace context，但各自保存本域详细回执。敏感内容通过引用和按需授权访问。

评估反馈可以更新未来策略版本、模型路由或规划提示，但不能改变已完成运行的事实。对历史重新评分产生新的 evaluation revision，并保留评分器版本。质量漂移与执行故障要分开：前者可能模型输出不佳，后者是运行时没有兑现契约。

跨边界错误的规范形状

所有集成都应返回结构化错误，包括 domain、code、retryability、outcome certainty、provider ID、建议等待和证据引用。运行时根据这些字段执行统一策略，同时保留原始错误供诊断。仅传异常字符串会迫使模型猜测是否重试。

export type BoundaryError = {
  domain: 'planner' | 'model_gateway' | 'tool' | 'workflow' | 'policy';
  code: string;
  retryability: 'retryable' | 'permanent' | 'conditional';
  outcome: 'not_applied' | 'applied' | 'unknown';
  retryAfterMs: number | null;
  providerRequestId: string | null;
  evidenceRef: string;
};

错误 owner 负责准确分类，运行时 owner 负责跨域决策。例如网关知道 429 是否发生在供应商接收请求前，工具适配器知道 409 是幂等命中还是业务冲突。运行时不应维护所有供应商状态码字典。

每条错误都携带 outcome certainty，防止“可重试”掩盖已发生副作用。一个请求可以技术上可重试但结果未知，此时运行时先对账而不是直接重复执行。

部署拓扑与演进

边界是逻辑所有权，不要求每个组件一开始都是独立服务。小团队可以在一个进程内用模块和接口隔离，保持各自数据模型与测试；当容量、安全或发布节奏不同再拆服务。过早远程化会增加分布式故障，却不会自动带来架构清晰。

推荐的抽取顺序通常是模型网关和沙箱 worker，因为它们凭据、容量与故障域独特；审批与策略可能因合规独立；运行状态和规划循环可以先同进程。工作流引擎是基础设施选择，不应迫使所有领域对象采用它的命名。

协议演进使用版本化 schema、能力协商和兼容窗口。运行时启动时记录各依赖版本；长运行恢复时若某依赖不再支持旧协议，进入迁移或人工路径。不要在工具 schema 删除后让模型看到“工具不存在”就重新规划高风险动作。

集成验收

使用 contract tests 验证每条边界：规划器晚到提议被修订拒绝；网关 fallback 回报实际模型与成本；工具超时返回 outcome unknown；工作流消息重复不会重复推进；评估重跑不会修改运行事实；策略升级使旧审批失效。

再做端到端故障注入：依次关闭规划器、网关、工具、审批和工作流 worker，确认运行分别进入可恢复等待、降级、对账或人工终态。任何组件故障都不应迫使其他组件伪造成功。

工具执行的安全底座见工具沙箱与安全边界，跨系统效果如何收敛见恢复、补偿与状态对账。

小结

  • 让 Agent 运行时唯一拥有运行生命周期、动作承诺、预算、等待、取消和终态。
  • 规划器提议语义动作，模型网关治理单次模型流量，工具适配器解释外部协议。
  • 用工作流引擎承载耐久调度，但保留领域 run_id 与业务事实所有权。
  • 每个重试策略只有一个 owner，其他层执行、计量并报告，避免乘法放大。
  • 以结构化错误传递 retryability 与 outcome certainty，不让上层猜状态码。
  • 先建立逻辑模块边界，再按安全、容量和发布节奏选择物理拆分。
