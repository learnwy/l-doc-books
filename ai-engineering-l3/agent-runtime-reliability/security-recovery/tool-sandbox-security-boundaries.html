工具沙箱与安全边界

模型把网页中的恶意文字当成指令后，真正决定事故规模的不是模型有没有“听话”，而是运行时给它什么能力。一个只能读取临时目录的 agent 与一个持有生产管理员令牌的 agent，面对同一提示注入会产生完全不同的后果。可靠性因此必须包含能力约束：系统只能在授权范围内成功。

核心概念

工具安全边界由四层共同形成：动作策略决定是否允许，身份与凭据限定外部权限，沙箱隔离本地执行，资源与网络控制限制影响范围。任何单层都不是完整答案。容器隔离不能阻止合法凭据删除云资源，工具 allowlist 也不能阻止被允许的 shell 逃逸宿主。

flowchart TD
    Proposal[模型动作提议] --> Schema[参数与类型校验]
    Schema --> Policy[能力策略判定]
    Policy --> Approval[风险审批]
    Approval --> Credential[短期凭据签发]
    Credential --> Sandbox[隔离执行环境]
    Sandbox --> Egress[网络出口代理]
    Sandbox --> Files[受控文件视图]
    Egress --> External[外部服务]
    Files --> Receipt[动作回执]
    External --> Receipt
    Receipt --> Audit[审计与检测]
边界 保护对象 主要控制 典型失败
动作边界 业务资源 schema、策略、审批 参数走私、越权动作
身份边界 账户与租户 短期凭据、audience、scope 令牌复用、混淆代理
进程边界 宿主与邻居 sandbox、namespace、VM 容器逃逸、横向读取
数据边界 文件与上下文 最小挂载、内容分类 秘密泄露、跨租户访问

资源边界 可用性与成本 CPU、内存、PID、时间 fork bomb、磁盘填满

MCP 规范把 tools 描述为模型控制的能力，但工具 annotations 只是提示，不能保证服务端真实行为。运行时应把远程工具当不可信能力描述，独立实施策略与授权，而不是因为它声明 readOnlyHint=true 就跳过审批。MCP Schema Reference明确要求客户端不要基于不可信服务器的 annotations 做工具使用决定。

从能力而不是工具名授权

allow tool=github 粒度过粗：同一工具可以读 issue、推送分支、删除仓库或修改组织权限。策略应描述动作、资源范围、环境、可逆性和数据类别，例如“允许读取当前仓库的 issue”“允许向工作分支推送，但禁止 main”“删除操作必须人工批准”。

运行时先把模型参数规范化为资源标识，再评估策略。路径需要解析符号链接与大小写，云资源需要标准 ARN 或项目 ID，URL 需要解析主机、端口和重定向目标。仅对原始字符串做前缀判断容易被 ../、重定向或编码差异绕过。

export type CapabilityRequest = {
  tenantId: string;
  subjectId: string;
  runId: string;
  action: string;
  resource: {
    kind: string;
    canonicalId: string;
    environment: 'local' | 'staging' | 'production';
  };
  dataClasses: string[];
  reversible: boolean;
  argsDigest: string;
};

export type CapabilityDecision =
  | { kind: 'allow'; grantId: string; constraints: Record<string, string> }
  | { kind: 'approval_required'; policyId: string }
  | { kind: 'deny'; policyId: string; reason: string };

grant 应只对一个动作或一组严格受限动作有效，并绑定 run_id、action_id、资源与参数摘要。不要把审批结果转换成长效管理员令牌。执行适配器收到 grant 后仍要校验约束，形成策略决策点与执行点的双重防线。

工具接口本身要减少危险组合能力。与其暴露任意 shell(command)，不如提供 run_tests(target)、apply_patch(workspace,path,diff) 等意图 API；若确实需要 shell，就把文件系统、网络、命令、环境变量和时间限制放进沙箱策略，而不是靠 prompt 约束。

沙箱提供隔离而非信任

原生容器共享宿主内核，namespace、seccomp、AppArmor 和 cgroup 能减少暴露面，但配置错误或内核漏洞仍可能突破边界。更强隔离可使用用户态应用内核或 microVM，并按风险选择性能与安全权衡。

gVisor 把系统接口移入每沙箱的用户态应用内核，让工作负载不直接接触宿主 Linux 内核；其安全介绍同时列出边界：它不解决更高层容器运行时被攻破、沙箱内应用自身漏洞、CPU 侧信道，也依赖宿主 cgroup 防资源耗尽。gVisor Security Introduction说明“使用了沙箱”不是停止威胁建模的理由。

沙箱模板至少应定义：只读基础镜像、非 root 用户、最小 syscall、无特权设备、临时可写层、工作目录挂载、PID 与文件描述符限制、CPU 与内存上限、网络模式、执行期限和销毁策略。不同租户或不同信任级别不得共用可写层或进程命名空间。

需要执行不可信代码时，强隔离沙箱应默认无网络、无宿主 socket、无 Docker daemon、无云元数据服务和无真实秘密。能力通过窄代理按调用临时授予。即使沙箱逃逸概率很低，也要限制宿主 IAM、网络段和可见数据，形成纵深防御。

沙箱销毁后仍可能留下对象存储产物、缓存层或日志。清理策略要覆盖临时卷、构建缓存、进程、端口和凭据，并用运行身份标记所有资源。清理失败进入回收队列与告警，不能因为主动作成功就忽略。

凭据必须短期、定向且不可转发

把长期 API key 注入环境变量是最常见的危险捷径。模型生成的命令、依赖包、子进程和错误日志都可能读到它。更可靠的方式是由凭据代理在动作获批后签发短期、最小 scope、绑定目标 audience 的令牌，工具通过受控通道按需获取。

MCP 授权规范要求服务器验证令牌是否专门为自己签发，客户端使用 resource 参数绑定目标，并明确禁止把收到的 access token 原样传给下游服务。MCP Authorization给出了防止 token passthrough 与 confused deputy 的强制边界。Agent 工具代理同样应为每个上游 API 获取独立令牌。

凭据回执应记录 grant 身份、scope、audience、签发和失效时间，而不记录令牌本身。日志和追踪处理器要对 Authorization header、cookie、连接串和模型上下文中的秘密统一脱敏。仅在 UI 隐藏字符串而后台全量采集并不安全。

撤销需要考虑正在运行的动作。策略变更或用户取消后，凭据代理拒绝续租并尽可能撤销短期令牌；已开始的外部操作仍需回执与对账。把令牌撤销误认为业务动作回滚，会留下不可见效果。

网络出口与数据流控制

默认开放互联网会让提示注入可以外传数据、下载恶意代码或访问内网管理面。网络策略应默认拒绝，只允许与动作能力匹配的域名、端口和协议，并通过出口代理执行 DNS 解析、重定向复核、速率限制与审计。

域名 allowlist 不能只检查初始 URL。代理需要防 DNS rebinding，拒绝解析到环回、链路本地和私有管理网段，重新校验每次重定向，并限制响应体大小与内容类型。访问云元数据地址应在网络层硬拒绝。

下载内容进入沙箱前可做类型、大小和恶意内容检查，但检查结果不能成为模型指令的信任背书。外部数据始终作为数据标记，工具返回结构化字段并区分可信系统元数据与不可信正文。运行时不要把网页或工具错误原样拼接进最高优先级指令。

出站写操作可以要求目标与数据类别匹配。例如客户数据只能发送到获批的客户系统，不能上传到任意文件分享站。策略决策记录数据分类、来源和目标，形成最小的数据流账本。

文件系统与工作区隔离

给 agent 一个“项目目录”时，要明确它是快照、工作树还是共享目录。最安全的默认是每运行独立工作区，基础仓库只读或通过写时复制挂载，写入集中在有限路径。跨运行共享同一工作树会产生数据竞争，也让一个运行读取另一个运行的秘密或未提交改动。

路径授权在打开文件描述符时执行，而不是先字符串校验后再打开，避免符号链接和竞态切换。支持的平台可使用 openat 一类相对目录句柄 API，将访问锚定到已授权目录。压缩包解包也要防路径穿越、符号链接和超额展开。

运行时应限制单文件大小、总写入字节、inode 数和临时磁盘。磁盘满会让回执和检查点保存失败，属于可靠性事故。达到阈值时先停止新的工具动作，尝试保存最小终态，再隔离工作区供人工检查。

产物离开沙箱前经过显式 export：计算摘要、分类敏感性、检查目标路径并生成产物回执。不要把整个工作目录自动上传，因为其中可能含依赖缓存、凭据文件和工具临时输出。

工具输出也必须受约束

工具返回可以很大、带恶意文本、包含秘密或伪造结构。适配器先验证最大字节、schema、编码和内容类型，把原始证据存入受控对象存储，再给模型提供经过裁剪的结构化观察。裁剪应可追溯到原始摘要，避免调试时只有模型看到的残片。

工具错误分为协议错误、策略拒绝、业务拒绝、暂时故障和安全违规。模型可以根据业务拒绝改计划，但不应看到能帮助绕过安全策略的内部细节。安全违规触发中止、凭据撤销和审计，而不是作为普通错误交给模型“自行修复”。

输出守卫不能替代副作用回执。工具说“删除成功”只是响应；运行时仍需外部对象身份、请求 ID 或可查询证据。对于不可信工具服务器，甚至 success 字段也要根据本地契约验证。

边界失败的处置

策略服务不可用时，高风险与写操作 fail closed；只读本地操作可由缓存策略在短时间内继续，但缓存必须绑定版本和过期时间。不能让“可靠性降级”成为绕过安全的开关。

沙箱启动失败、资源超限或出口拒绝都应产生结构化终态。运行时根据分类决定缩小任务、换隔离池、等待容量或交给人。原样重试相同不可信代码通常只会再次触发限制。

发现秘密泄露或越权效果时，立即停止相关运行和凭据续租，保全工作区与回执，按租户和 grant 追踪影响范围，再执行轮换与补偿。审计链要能回答哪些运行看到过秘密、哪些工具获得过 grant、哪些外部目标收到过数据。

验收测试

安全测试应从能力滥用而非 prompt 文本开始。让模型请求路径穿越、访问云元数据、使用重定向进入内网、读取其他租户工作区、创建大量进程、填满磁盘、转发令牌、调用未声明资源和伪造工具 annotations。

每个测试断言控制发生在哪一层、是否留下拒绝事件、秘密是否未进入追踪、运行能否安全终止，以及控制平面在数据平面耗尽时仍可操作。还要用真实 sandbox escape 假设做桌面演练：即使沙箱被突破，宿主身份和网络是否仍限制爆炸半径。

动作未知与外部效果的恢复见恢复、补偿与状态对账，各控制面的所有权见运行时边界与系统集成。

小结

  • 以动作、资源、环境和数据类别定义能力，不以宽泛工具名授权。
  • 组合策略、短期凭据、沙箱、网络、文件与资源控制，任何单层都不够。
  • 把远程工具描述与 annotations 当提示，不当可信安全事实。
  • 使用 audience 绑定的短期令牌，禁止令牌透传，并让执行 grant 绑定动作摘要。
  • 默认拒绝网络和宿主访问，以受控代理授予窄能力并记录数据流。
  • 从能力滥用和沙箱突破假设出发验证爆炸半径，而不仅测试已知提示注入句式。
