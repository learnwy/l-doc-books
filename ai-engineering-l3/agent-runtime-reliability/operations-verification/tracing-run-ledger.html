追踪与运行账本

一次 agent 运行最终失败，团队看到模型调用成功、工具 API 也返回成功，却解释不了为什么用户目标没有完成。普通分布式追踪擅长定位延迟和错误，但它不一定保存“哪个动作获批”“外部效果是否确认”“哪个状态修订消费了结果”。可靠运行需要追踪与运行账本协同，而不是把所有责任塞进日志。

核心概念

追踪描述一次请求如何跨组件传播，运行账本描述领域事实如何合法演进，副作用回执证明外部世界发生了什么，指标聚合大量运行的趋势。四者通过稳定身份关联，但保留不同的完整性、保留期与访问控制。

flowchart LR
    Run[run_id] --> Trace[端到端 Trace]
    Run --> Ledger[追加式运行账本]
    Trace --> Span[模型与工具 Span]
    Ledger --> Event[状态与策略事件]
    Event --> Receipt[副作用回执]
    Span --> Metrics[聚合指标]
    Event --> Metrics
    Receipt --> Audit[审计查询]
    Ledger --> Eval[轨迹评估]
证据面 主要问题 完整性要求 典型保留期
Trace 时间花在哪里、调用如何传播 允许采样 天到月
Log 组件诊断细节是什么 可采样与轮转 天到月
Run Ledger 状态为何改变、谁授权 关键事件不可缺 月到年
Effect Receipt 外部动作产生什么效果 动作级强一致 依业务合规
Metric 群体趋势是否异常 聚合准确 月到年
Eval Record 质量是否达到定义 评分器版本化 随评估集演进

OpenAI Agents SDK 的 tracing 会记录模型生成、工具调用、handoff、guardrail 与自定义事件，并用 trace、span、group ID 组织一次工作流及会话关系。Agents SDK Tracing也指出 Zero Data Retention 组织不可使用其托管 tracing。这提醒平台把观测能力设计为可替换出口，并明确敏感数据与保留策略。

关联身份构成证据骨架

每个事件至少携带 run_id 和 run_revision。步骤带 step_id，模型调用带 model_call_id，工具动作带 action_id，审批带 approval_id，外部效果带 receipt_id。Trace ID 用于传输关联，但不能替代这些领域身份，因为采样、重试和跨天恢复可能产生多个 trace。

一次运行可以跨多个 trace：首次执行一个，等待审批后恢复一个，灾难恢复再一个。账本保存 trace_started 事件或 trace refs，UI 以 run_id 汇总。反过来，同一会话可包含多次运行，使用 session_id 或 group ID 关联，但不合并状态与预算。

export type RunEventEnvelope = {
  eventId: string;
  sequence: number;
  runId: string;
  runRevision: number;
  stepId: string | null;
  actionId: string | null;
  traceId: string | null;
  spanId: string | null;
  type: string;
  occurredAt: string;
  recordedAt: string;
  actorRef: string;
  policyVersion: string;
  payloadRef: string;
  payloadDigest: string;
};

occurredAt 是事件在来源系统发生的时间，recordedAt 是账本接收时间。跨系统时钟可能漂移，领域顺序应依靠每运行 sequence 与因果引用，而不是全局时间排序。工具回执晚到仍按新 sequence 追加，同时保存供应商发生时间。

Span attributes 可以携带领域身份，但不要把完整模型输入、工具参数和结果默认放入 attribute。高基数字段会增加成本，敏感内容也会扩散到多个 exporter。把大内容写入受控对象存储，span 只记录摘要、大小、分类与授权引用。

账本事件表达意图与结果

好的事件名称描述已发生事实，例如 run_accepted、lease_acquired、action_intent_committed、approval_granted、effect_confirmed、cancellation_requested、run_repair_required。避免 process_step 这类无法审计的通用事件，也不要记录尚未提交的未来计划为既成事实。

关键状态转换与账本追加应在同一事务内。若观测 exporter 不可用，运行仍能写事实库；异步投影器再把事件导出到追踪和指标系统。反过来把日志平台当唯一账本，会受到采样、轮转、摄入故障和字段解析变化影响。

每个状态事件包含前一修订、命令身份、actor、策略版本和载荷摘要。需要更强防篡改时，可加入前一事件摘要形成运行内链，并定期把批次根摘要写入独立存储。完整性机制仍需要访问控制和备份，不能替代它们。

事件 必需字段 审计问题
action_intent_committed 动作、参数摘要、grant 为什么允许执行
approval_decided 请求版本、主体、决定 谁看了哪个提案
effect_confirmed 外部对象、回执、证据 现实发生了什么
retry_scheduled 错误类别、剩余预算、时间 为什么再次尝试
run_cancelled 请求者、清理结果、残余效果 取消是否安全完成
repair_resolved 证据、操作者、处置 未知状态如何收敛

账本读取 API 要区分用户视图、支持视图、安全审计和评估导出。用户可看到进度与结果，不一定能看到内部策略；支持人员按租户授权查看受控证据；评估管道使用脱敏轨迹；安全团队访问高风险动作与凭据 grant。

Trace 结构要贴近运行语义

推荐用一次恢复阶段或入口请求作为 trace，在其中为规划、模型调用、动作准备、策略判定、审批、工具执行、回执保存和状态提交建立 span。父子关系表达同步因果，span links 连接异步队列、重试和跨 trace 恢复。

模型调用 span 记录实际模型、供应商、完成原因、输入输出 token、缓存使用、deadline 和错误类别。工具 span 记录工具名、动作身份、尝试、outcome certainty、外部请求 ID 与回执状态。策略 span 记录 policy ID 与 allow、deny、approval_required，不记录完整秘密参数。

OpenTelemetry 的生成式 AI 属性注册表定义了 gen_ai.tool.call.arguments、gen_ai.tool.call.result、token usage 等字段，同时明确警告工具参数与结果可能包含敏感信息，并建议不要默认填充大型可选字段。OpenTelemetry GenAI Attributes适合作为跨供应商字段基线，但处于演进中的语义约定应通过内部映射层隔离。

不要为每个流式 token 创建 span。可以记录首 token、流完成、chunk 数和空闲超时等事件，必要时在受控采样下保存原始流。过细 span 会提高成本并掩盖真正的状态边界。

敏感内容与最小化采集

Agent 轨迹可能包含客户数据、源代码、凭据、内部 prompt 和工具结果。观测设计从数据分类开始：哪些字段永不采集，哪些只存摘要，哪些加密保存并需要 break-glass，哪些可进入聚合指标。

脱敏应在数据离开信任边界前完成。Exporter 端再删字段已经太晚，因为内存队列、重试缓存和中间代理可能保存原值。工具适配器知道字段语义，应负责第一层结构化脱敏；统一管道再做秘密模式与大小检查。

采样策略按风险与结果分层。成功低风险运行可采样 trace，但账本关键事件不采样；失败、结果未知、安全拒绝、补偿和高价值运行提高 trace 保留率。采样决定本身记录版本，避免指标分母与调查证据不一致。

内容引用使用带租户和数据分类的对象 ACL，链接短期签名而非永久公网 URL。删除与保留请求要沿引用图传播：账本可以保留不含内容的动作摘要，受保护内容按法规到期删除。

从账本派生指标

指标应从稳定事件定义派生，而不是从可变日志文本正则匹配。运行接收与终态事件计算成功率和总延迟；动作意图与回执计算重复、副作用未知和对账时间；审批请求与决定计算等待 SLO；预算 reservation 与结算计算超支和估算误差。

常用运行时指标包括：

  • 运行终态分布及按目标类型、模型、策略版本分组的成功率。
  • 接受到首个有效动作、首个用户可见进展和最终完成的延迟分位数。
  • 每运行模型调用、工具调用、token、费用和墙钟资源分布。
  • retry amplification，即总尝试数除以语义动作数。
  • unknown outcome 比例与从未知到确认的对账时长。
  • 取消请求到无新动作签发、到完全清理的两段延迟。
  • 审批等待年龄、过期率、被取代率与批准后补偿率。
  • 恢复次数、检查点读取失败、历史不兼容和人工修复积压。

指标标签必须控制基数。run_id 和 action_id 放在 trace 与日志中，不作为时序数据库标签；租户也可按套餐或隔离组聚合，只有受控诊断临时开启细粒度。高基数会让观测系统本身成为故障源。

轨迹重建与时间旅行

操作界面应能按 run_id 重建时间线，显示状态修订、规划提议、策略决定、模型与工具回执、审批和终态。默认展示摘要，按权限展开原始证据。时间线标出等待、重试和结果未知区间，使事故人员快速看到事实缺口。

重放调试要创建只读 simulation 或分叉运行。读取历史模型与工具结果可验证决策逻辑；若选择重新调用，则使用新身份和隔离环境，绝不把调试事件写进原账本。UI 明确标记“历史复用”与“外部重算”。

账本也支持因果查询：某次外部删除由哪个规划提议、策略 grant 和审批导致；某个模型 fallback 影响了哪些运行；某版本工具 schema 的 unknown outcome 是否升高。为此事件 payload 要保存版本和稳定引用，而不是只有人类文本。

观测系统故障时的行为

Trace exporter 故障不应阻塞普通运行，但要有有界缓冲、丢弃计数和恢复策略。运行账本写入失败则不能安全推进关键状态，因为事实会丢失；系统应停止新副作用并保留控制平面能力。

若指标管道延迟，准入控制不能盲目认为容量正常。使用本地或近实时的连接池、队列深度和供应商错误作为保护信号，中心指标用于较慢反馈。安全审计导出失败则告警并保留本地加密事件，不能静默丢弃。

观测依赖也有资源预算。限制 span 数、事件 payload、缓冲字节和导出重试；过载时优先保留终态、策略、审批、动作与回执，丢弃细粒度调试事件。优先级策略需测试而不是事故时临时决定。

验收测试

从每种终态抽取运行，只使用账本与引用重建完整因果链。随机删除 trace，业务审计仍应完整；模拟 exporter 不可用，运行可继续且有丢弃指标；模拟账本不可写，新副作用必须停止。

隐私测试向模型输入和工具结果放置 canary secrets，验证它们不出现在 span attributes、日志、指标或错误页面。权限测试确保跨租户无法通过 run_id 枚举读取证据，过期链接不可访问。

最后做 schema 兼容测试：旧事件经过新投影器能重建相同状态，新字段不会破坏 exporter，评分管道记录使用的事件与评分器版本。追踪字段升级不应改变业务事实。

这些证据会在评估、SLO 与错误预算中转化为目标，并在混沌实验与故障演练中验证控制是否真实生效。

小结

  • 用 trace 诊断传播，用账本证明状态，用回执证明外部效果，用指标观察群体趋势。
  • 以领域身份关联证据，不把易变或采样的 trace ID 当运行身份。
  • 关键状态与账本事件原子提交，观测导出从账本异步派生。
  • 在来源边界脱敏，大内容只存受控引用，对关键账本事件不采样。
  • 从稳定事件派生低基数指标，并为用户、支持、安全与评估提供不同读取面。
  • 在观测故障时优先保留终态、策略、审批、动作与回执，账本不可写就停止副作用。
