混沌实验与故障演练

可靠性声明本质上是假设：限流时系统会退避，进程崩溃后不会重复扣款，审批过期后旧决定不能继续生效，存储损坏时运行会停在可对账状态。常规成功路径测试只能说明系统在理想条件下工作；混沌实验与故障演练主动制造受控偏差，验证这些假设在真实的并发、时间和恢复条件下仍成立。

核心概念

混沌工程不是随机破坏生产环境，而是围绕稳态假设设计有边界、可停止、可复现的实验。一个合格实验先声明用户可感知的稳态指标，再注入单一或组合故障，持续观测系统是否守住不变量，最后保存证据并缩小未知区域。

flowchart LR
    Hypothesis[可靠性假设] --> Steady[定义稳态与不变量]
    Steady --> Design[设计故障与爆炸半径]
    Design --> Guard{安全门通过}
    Guard -->|否| Reject[拒绝执行]
    Guard -->|是| Inject[注入故障]
    Inject --> Observe[追踪运行与用户结果]
    Observe --> Stop{停止条件触发}
    Stop -->|是| Halt[停止并恢复环境]
    Stop -->|否| Decide{假设成立}
    Decide -->|是| Expand[记录证据并逐级扩大]
    Decide -->|否| Learn[修复、补充评估与演练]
    Learn --> Hypothesis

Principles of Chaos Engineering强调先定义可测量的稳态、引入现实事件、在生产流量附近验证并持续缩小爆炸半径。对 agent 运行时，稳态不能只写 CPU 或错误率，还必须包含执行语义：副作用唯一、取消后不再签发动作、审批绑定未漂移、未知结果进入对账、恢复后仍能解释终态。

实验要素 必须回答的问题 不合格写法
假设 哪条运行时保证在何种故障下仍成立 “看看会发生什么”
稳态 用户结果与内部不变量如何量化 “服务没挂”
故障 在哪个控制点注入何种偏差 随机杀进程
爆炸半径 哪些租户、任务、资源和时间窗受影响 全量生产
停止条件 哪个实时信号触发自动停止 人工感觉不对再停
恢复计划 如何撤销注入并验证环境已恢复 重启应该就好
证据 哪些事件、回执与指标支持结论 一张监控截图

实验契约

每次实验都应是一个版本化对象，而不是操作手册中的散文命令。它引用运行时版本、策略版本、目标任务族与已审查的故障注入器；执行器只能在授权作用域内解析这些引用，不能接受任意 shell 文本。

{
  "experiment_id": "exp_tool_reply_loss_v3",
  "hypothesis": "工具已提交但响应丢失时，不会产生第二个业务效果",
  "target": {
    "environment": "staging",
    "tenant_allowlist": ["chaos-fixture"],
    "task_family": "refund",
    "max_runs": 100
  },
  "fault": {
    "control_point": "after_tool_commit_before_receipt",
    "mode": "drop_response",
    "probability": 0.2
  },
  "steady_state": [
    "duplicate_effect_count == 0",
    "unknown_outcome_age_p99_seconds < 300",
    "terminal_run_ratio >= 0.99"
  ],
  "stop_conditions": ["critical_policy_violation_count > 0", "duplicate_effect_count > 0", "unknown_outcome_count > 5"],
  "expires_at": "2026-09-01T10:30:00Z"
}

实验的 steady state 与 stop condition 不是同一件事。稳态用于判断假设是否成立；停止条件是保护栏，只要触发就立刻撤销注入，即使样本量尚不足。停止也不等于失败结论：传感器异常、基线已经退化或实验配置漂移都可能要求安全停止，结论应标记为 inconclusive。

Amazon Fault Injection Service 的实验模板把 actions、targets、stop conditions 与角色组合成可重复定义，并建议在监控告警触发时停止运行中的实验。AWS FIS experiments与Stop conditions提供了通用的控制面思路：停止信号必须在实验前存在并被验证，不能依赖故障发生后临时观察。

实验控制器与被测运行时分离部署。若它们共享同一队列、数据库或凭证，资源故障可能同时摧毁停止能力。控制器需要独立的紧急停止路径、短期授权、不可变审计记录和自动到期；注入器失联时按 fail-closed 撤销所有持续故障。

Agent 特有的故障目录

传统服务的网络、计算和存储故障仍然适用，但 agent 还引入模型非确定性、长轨迹、外部工具效果、人类等待与动态策略。故障目录要按责任边界建模，避免只杀 Pod 却从不触碰真正危险的语义边缘。

故障域 代表性注入 应验证的运行时性质
模型 429、超时、流中断、畸形结构、长上下文拒绝 有界退避、候选切换、预算不超支
工具 响应丢失、重复投递、部分成功、schema 变更 幂等、回执、结果未知与对账
状态 checkpoint 写失败、事件延迟、旧版本重放 原子提交、兼容门、可恢复终态
调度 队列积压、worker 崩溃、租约过期、时钟偏差 单 owner、fencing、背压、公平性
资源 token、连接、内存、磁盘或并发耗尽 硬预算、降级、拒绝新工作
人类环 审批延迟、拒绝、撤销、策略在等待中变化 冻结意图、重新校验、可解释恢复
安全 凭证拒绝、非法出站、跨租户目标、恶意工具输出 默认拒绝、隔离、无旁路升级
可观测 trace exporter 丢包、采样偏差、时钟乱序 核心账本独立、证据不因遥测失败丢失

故障注入点最好是运行时的显式 seams，例如“远端已提交、回执尚未写入”或“checkpoint 已落盘、消息 ack 尚未完成”。在任意代码行睡眠或抛异常虽然容易，却很难稳定命中语义窗口，也无法证明关键竞态被覆盖。

组合故障要建立在单故障已理解之上。现实事故常是限流加队列积压、审批延迟加策略升级、工具响应丢失加 worker 崩溃。未经分层直接组合会让失败不可归因，团队只能得到“系统不稳定”的低价值结论。

演练阶梯

故障验证应从确定性、廉价环境逐级接近真实负载。每一级有进入条件和退出证据；不是所有实验都必须进入生产，但高风险保证不能永远只在 mock 中成立。

  1. 状态机属性测试使用虚拟时钟、受控随机种子与内存工具替身，穷举取消、重试、崩溃和恢复的事件排列。
  2. 组件集成测试使用真实持久层与消息系统，验证事务边界、fencing token、schema 兼容和队列重投。
  3. 隔离环境演练连接沙箱工具，验证外部协议、回执查询和补偿，不接触真实业务对象。
  4. 预发布 game day 以接近生产的拓扑、并发和数据规模运行，验证监控、值班响应与恢复手册。
  5. 生产 canary 只选择低风险任务、允许租户和小流量，设置自动停止、值班 owner 与完整回滚路径。

晋级依据不是“上一次没出事”，而是证据充分：故障确实被触发、检测信号在目标时间内出现、运行时采取预期动作、用户 SLI 保持或按设计降级、环境清理完成。若注入器没有命中控制点，实验结果是 invalid，不能算通过。

生产实验必须避开已有事故和错误预算快速消耗期。运行前冻结目标版本与流量范围，确认备份与对账通道可用，执行 dry run 检查权限和停止条件。高风险写操作通常只在完全隔离的业务账户验证；真实生产验证可聚焦调度、模型与只读工具故障。

关键实验一：模型限流与延迟

按阶段注入模型 429、连接建立超时、流式输出半途断开和长尾延迟。假设应明确：运行时在 deadline 和 attempt budget 内指数退避，必要时只切换到政策允许且能力兼容的模型；不会因为 fallback 放宽数据边界或重复已完成工具动作。

观测 attempt_id、选择的模型、剩余 deadline、退避时间、token 与成本预算。验收不是最终“有答案”，而是没有重试风暴、每次尝试受同一个根 deadline 约束、切换理由可解释，超时后到达明确 terminal state。

若所有 worker 同步退避后同时重试，会形成惊群。实验应以多个并发运行验证 jitter 分散效果，并测队列年龄和供应商配额。AWS Well-Architected 建议限制自动重试次数、采用指数退避与随机抖动，并确保重试不会造成更大拥塞。Limit retries可作为这一实验的设计基线。

关键实验二：工具提交后响应丢失

这是副作用可靠性的核心实验。工具服务先真实提交一个沙箱效果，再由代理丢弃响应或断开连接，使运行时无法立即知道结果。正确行为是记录 unknown outcome，使用原 operation_id 查询权威结果；不能用一个新 idempotency key 盲目重发。

分别验证三种工具能力：支持幂等查询、仅支持结果查询、两者都不支持。前两类应自动对账到 committed 或 not_committed；最后一类必须停止自动化并请求人工接管。任何重复业务效果都是硬失败，即使补偿随后成功。

再在 unknown outcome 期间杀死 worker，确认 checkpoint 恢复后仍携带原 operation_id 与效果摘要。向队列重复投递同一消息，确认 fencing token 和效果回执阻止第二个 owner 执行。最后让工具返回相同 HTTP 状态但不同业务回执，确保系统以权威业务标识而非传输状态判定结果。

关键实验三：状态损坏与版本重放

在 checkpoint 写入前、写入中和写入后分别终止进程，验证事件与状态快照的原子性。对快照制造校验和错误、缺失 blob 和孤立事件，运行时应隔离受损实例并报警，而不是带着部分状态继续调用工具。

保留旧版本历史，在新 runtime 与新状态 schema 下执行 replay dry run。若确定性决策、事件解释或工具 intent 发生不兼容变化，部署门应阻止迁移，或选择旧 worker 完成现有实例。不要用新代码重放时重新访问真实模型或工具；重放只消费已记录决定，外部执行通过回执恢复。

为灾难恢复演练整库备份还原：从某个恢复点启动只读验证，计算丢失窗口内的 run 与 effect，逐个进入对账。RPO 和 RTO 必须落到用户语义，例如“最多多少个运行需要人工核对”和“多久停止签发重复动作”，而非只报告数据库恢复耗时。

关键实验四：审批等待与策略变化

创建需要批准的冻结 intent，在审批到达前注入长延迟、重复点击、拒绝、撤销和错误 approver。等待期间升级策略、工具 schema 或目标对象版本，验证 resume 会重新检查 subject、action digest、policy version、expiry 与 effect precondition。

正确恢复不意味着永远沿旧轨迹继续。如果策略变严格、对象状态已变化或批准过期，运行应转为 reapproval_required 或 terminal_rejected，而不是悄悄生成新参数复用旧批准。相反，完全相同的重复批准应被去重，并留下同一 decision_id 的审计事件。

演练还要覆盖通知系统不可用。批准能力不应依赖消息渠道回调的唯一一次投递；审批决定存入权威系统，runtime 通过 durable subscription 或查询恢复。通知失败影响等待时长 SLI，但不能导致默认批准。

关键实验五：资源耗尽与取消风暴

逐步收紧模型并发、工具连接池、内存、磁盘和租户配额，同时增加队列输入。验证 admission control 在容量边缘拒绝或延后新运行，保留恢复、取消和高优先级对账所需资源。若所有槽位都被普通任务占满，系统可能连“停止工作”都做不到。

触发大量用户取消和 deadline 到期，观察取消信号从根 run 传播到子尝试、工具调用与等待任务。已经提交的远端副作用不能假装被取消；它们进入对账或补偿。未提交动作不再签发，后台 worker 最终释放租约与预算。

验收包括队列年龄不无限增长、单租户不能饿死其他租户、过载时成功任务的单位成本不爆炸、拒绝原因明确且可重试。Amazon 的 fail-fast guidance 建议在系统无法可靠处理请求时快速失败，并通过队列长度等指标及时拒绝新工作。Fail fast and limit queues支持把背压本身作为可测试行为。

关键实验六：安全边界失效

让工具尝试访问未允许域名、跨租户对象、宿主文件和未声明 secret；向模型返回包含提示注入的工具输出；撤销运行时短期凭证；让沙箱网络代理失联。期待结果均为默认拒绝，且拒绝不会通过 fallback、人工 resume 或重试路径被绕过。

沙箱逃逸演练不应在共享生产宿主运行真实 exploit。可以验证 syscall、文件、网络和资源策略的阻断行为，使用隔离测试镜像与无敏感凭证账户。若必须验证更底层边界，应由安全 owner 在专用环境执行，运行时团队消费其证据与修复结论。

同时破坏 trace exporter，确认安全审计与效果账本仍持久化。可观测性后端不是授权依据；遥测不可用时，高风险动作应按政策降级或暂停，但不能因为“记录不了”而静默执行。

Game day 与人员演练

自动实验验证机器行为，game day 验证组织能否识别、决策和恢复。演练设置 incident commander、runtime owner、工具 owner、security owner 与观察员；参与者只获得正常值班可见信息，不提前泄露具体故障。

场景按时间线注入：首先是轻微 SLO 燃烧，然后出现 unknown outcome、审批积压或策略告警。观察团队是否找到权威 run ledger、区分模型失败与工具已提交、选择停止新流量而不破坏恢复 worker，并按明确 owner 发起对账。

演练记录检测时间、确认时间、缓解时间、对账完成时间和用户沟通时间。结束条件是所有故障注入撤销、实验资源清理、受影响 run 有归属、账本与外部事实一致；“服务图表恢复绿色”不足以结束。

复盘避免评价个人反应快慢，聚焦系统是否提供足够信号与安全操作面。每个发现转成一个带 owner 和验证方式的变更：新增不变量检查、完善 stop condition、收紧权限、补充 runbook、加入离线 eval 或安排下一次更窄的实验。

证据、评分与学习闭环

实验记录至少包含模板版本、审批、开始与结束时间、实际目标、故障控制点命中证据、基线窗口、运行样本、停止原因、账本查询、外部回执与环境清理证明。图表可以帮助理解，但结论必须能从结构化事实重新计算。

对每条假设给出 pass、fail、inconclusive 或 invalid：

  • pass：故障命中，样本达到预设门槛，所有硬不变量成立，稳态在容差内。
  • fail：故障命中且至少一个硬不变量或稳态阈值被破坏。
  • inconclusive：安全停止、样本不足或基线异常，不能判断假设。
  • invalid：故障没有命中、配置漂移、传感器不可用或目标超出声明范围。

失败实验首先生成可复现回归样本，再修复实现。修复需通过确定性测试、离线轨迹 eval 与相同实验，不能只凭代码审查关闭。若某类缺陷反复出现，升级运行时契约或发布门，而不是不断增加一次性告警。

实验覆盖率不以“注入了多少故障”衡量。更有意义的是关键运行时保证是否至少有一个有效实验、多久未验证、最近一次在哪个环境通过、失败后是否完成闭环。高风险保证随版本或架构变化重新验证，不能永久继承旧证据。

验收清单

选择一个工具写操作实验，确认能稳定命中“已提交、回执未持久化”窗口，worker 崩溃并重启后仍以同一 operation_id 对账，外部系统只有一个效果。选择一个取消实验，确认 deadline 后不再出现新 intent，已提交效果被标记并处理。

在执行生产 canary 前，验证目标 allowlist、最大运行数、最长持续时间、独立停止通道、值班 owner 和恢复计划；模拟 stop condition，确认注入器确实撤销故障。实验后比较用户 SLI、内部不变量与外部回执，逐项关闭受影响运行。

检查事故库中的每个重大故障是否已有可重复实验或明确的不适用理由。长期从未触发的停止条件也应演练，否则它只是配置。实验产生的 trace 和账本证据结构见追踪与运行账本，稳态与错误预算选择见评估、SLO 与错误预算。

小结

  • 把可靠性保证写成可证伪假设，以用户稳态和运行时不变量判断结果。
  • 每个实验预先限定目标、故障、爆炸半径、停止条件、恢复计划与证据。
  • 覆盖模型、工具、持久状态、调度、资源、人类审批、安全与遥测故障。
  • 从确定性状态机测试逐级走向隔离环境、game day 和小范围生产 canary。
  • 重点验证响应丢失、崩溃重放、审批漂移、过载取消与默认拒绝等语义窗口。
  • 用 pass、fail、inconclusive、invalid 区分结论，并把失败固化为评估和发布门。
