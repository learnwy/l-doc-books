评估、SLO 与错误预算

Agent 服务返回 200 并不代表用户目标成功，模型答案看似合理也不代表系统可靠。一次运行可能语言质量很高，却重复执行了工具；也可能所有基础设施正常，却在截止时间后交付失效结果。生产目标需要同时测量行为质量、执行语义、时间、成本与安全。

核心概念

Eval 回答“这条轨迹或结果是否达到任务标准”，SLI 把用户可感知结果转成可聚合测量，SLO 定义一段时间内可接受水平，错误预算把允许失败量变成运营决策。四者形成从样本到服务治理的链，而不是一组互相独立的仪表盘。

flowchart LR
    Goal[用户目标] --> Criteria[完成与质量标准]
    Criteria --> Offline[离线评估集]
    Criteria --> Online[在线SLI]
    Offline --> Release[发布门]
    Online --> SLO[服务目标]
    SLO --> Budget[错误预算]
    Budget --> Decision{预算状态}
    Decision -->|健康| Iterate[继续迭代]
    Decision -->|快速消耗| Mitigate[降载或回滚]
    Decision -->|耗尽| Freeze[冻结高风险变更]
    Mitigate --> Offline

Google SRE 把错误预算定义为 1−SLO1-SLO1−SLO，并用它平衡可靠性与变更速度；其示例政策在前四周预算耗尽时冻结除最高优先级与安全修复外的发布。Error Budget Policy强调预算不是惩罚，而是将可靠性工作优先级变成可执行规则。

先定义完成，再定义指标

每类 agent 任务需要领域完成判据。客服退款以退款对象与账本回执为准，代码修复以差异、测试与审查状态为准，研究报告以引用完整性和用户接受为准。通用的“模型最终输出非空”只能测进程结束，不能测责任完成。

完成判据分成硬条件和质量条件。硬条件包括无未对账副作用、授权链完整、状态合法和结果产物存在；任一失败就不能算成功。质量条件可以由确定性检查、人工标注或 grader 给分。先过硬门，再计算质量，避免高语言分掩盖安全失败。

对线上 SLI，可定义 good run：在 deadline 内到达可接受终态，所有外部效果有回执，无高严重度策略违规，质量分超过任务阈值，成本未超过授权。于是：

SLIsuccess=good runseligible runsSLI_{success} = \frac{\text{good runs}}{\text{eligible runs}}SLIsuccess​=eligible runsgood runs​

eligible runs 要排除明确的用户取消、测试流量和上游已声明不可用的范围，但排除规则必须版本化且可审计。若把困难任务或失败供应商全部移出分母，SLO 会失去意义。

不同任务价值与风险差异大，不宜只有一个全局目标。可按写操作与只读、实时与异步、生产与沙箱、高价值与普通租户分层；每层有自己的成功、延迟、安全与成本 SLO。全局汇总用于趋势，运营决策依赖具体层。

离线评估覆盖行为与故障

离线评估集不只包含输入和理想文本，还应包含环境状态、工具替身、允许动作、完成证据和故障脚本。对 agent 而言，轨迹是被测对象：是否选择正确工具、参数是否正确、是否在拒绝后绕过、人类审批是否绑定同一动作、恢复后是否重复副作用。

评估样本来源包括真实失败脱敏、产品关键路径、边界案例、安全红队和故障演练。每个事故至少转化成一个可复现案例，并记录它保护的风险。样本随产品演进更新，但保留固定核心集用于纵向比较。

OpenAI 对内部 data agent 的介绍说明，其持续 eval 同时比较生成 SQL 与实际查询结果，用手写 golden SQL 和 grader 捕捉语法不同但语义正确的输出。Inside OpenAI's In-house Data Agent体现了一个通用原则：评估应尽量落到可执行结果，不依赖字符串完全相等。

模型 grader 需要版本、校准集和人工一致性抽查。不能用同一模型自评自己所有失败，也不要只看总平均分。记录 grader 理由、置信度和输入引用；阈值附近或高风险样本进入人工复核。

在线 SLI 必须面向用户结果

基础设施指标仍重要，但它们是诊断信号。核心 SLI 应包含：运行成功率、deadline 内成功率、副作用正确率、结果未知率、恢复成功率、人工等待时长和单位成功成本。每个指标由账本事件与回执计算，避免日志文本漂移。

延迟可拆成接收至首个有效进展、有效执行时间、外部等待、人工等待和最终完成。若异步任务允许数小时，用户仍需要快速看到已接受与当前阻塞原因。仅看最终延迟会掩盖平台长时间无反馈。

可靠性的强约束可以写为多个 SLO，而不是把所有维度平均成一分：

  • 99.5% 的 eligible 高价值运行在业务 deadline 内到达非未知终态。
  • 99.99% 的已确认写动作没有重复未补偿效果。
  • 99.9% 的取消请求在一分钟内停止签发新动作。
  • 99% 的结果未知在十五分钟内经对账或人工接管。
  • 100% 的 critical 动作都有有效授权、审批与回执链。

安全维度通常不适合用平均错误预算容忍严重事件。零容忍不意味着观测目标设成虚假的 100% 可用，而是 critical policy violation 一旦发生就触发事故与发布门，不被其他高成功率抵消。

错误预算驱动行动

若一个 30 天 SLO 为 99.5%，允许错误比例为 0.5%。有 100,000 次 eligible 运行时预算是 500 次 bad run。预算消耗率可以按窗口比较实际错误率与允许错误率：

burn rate=1−SLIobserved1−SLOtargetburn\ rate = \frac{1 - SLI_{observed}}{1 - SLO_{target}}burn rate=1−SLOtarget​1−SLIobserved​​

burn rate 为 10 表示以当前速度十倍消耗预算。多窗口告警同时看短窗口的急性事故和长窗口的慢性回归，减少单次低流量失败造成的噪音。低流量服务可结合合成探针和绝对失败数。

Google SRE 的 SLO 告警指南建议以对错误预算的具体威胁触发可行动告警，而不是每次错误都分页。Alerting on SLOs指出低流量服务中一次失败就可能形成极高 burn rate，因此需要根据流量形状调整策略。

预算政策在发布前写清：健康时允许实验；消耗加速时降低并发、关闭不稳定 fallback、提高人工抽样；预算耗尽时冻结能力扩张，优先修复与回滚。安全事件、重复资金效果和跨租户泄露可直接进入紧急政策，不等待统计预算耗尽。

发布门与渐进放量

新模型、prompt、规划器、工具 schema、重试策略和运行时代码都可能改变行为。每次变更携带 component version，先通过历史兼容与固定核心评估，再在 shadow 或隔离租户运行，最后 canary 渐进放量。

发布门至少比较基线与候选的任务成功、安全硬门、重复效果、unknown outcome、延迟和单位成功成本。只优化总成功率可能以更高成本或更多高风险动作换分。为每个维度定义不可退化阈值和允许的统计不确定性。

小样本不要宣称微小提升。对二项成功率使用置信区间或贝叶斯后验，并对高风险失败采用逐例审查。若候选成功率接近但错误类型更严重，应拒绝发布。

线上 canary 按租户、任务类型和风险分层，避免只在简单流量上成功。每阶段观察完整业务周期，包括跨天审批和恢复；过早扩大流量会错过长尾故障。回滚不仅切回模型或代码，还要保证正在运行实例由兼容版本继续或安全迁移。

分群分析避免平均数欺骗

总体成功率可能掩盖某个模型供应商、工具版本、语言、租户或恢复路径的严重退化。所有 eval 和 SLI 至少按任务族、风险、模型实际选择、工具 schema、策略版本、是否重试、是否恢复和是否经过审批分群。

分群数量要与样本量平衡。预先定义关键切片，自动寻找异常只用于生成假设，避免在大量切片中挑选偶然结果。低样本高风险切片采用人工审查和合成测试补充。

成本指标使用“每个 good run 成本”，而不是每请求平均成本。一个便宜但经常失败的模型会让请求成本下降，却提高完成一个目标所需总尝试。也要包含人工审批与修复时间，否则平台把自动化失败成本转嫁给运营团队。

质量漂移与数据治理

评估集会老化，grader 会漂移，产品目标也会变化。每份分数记录 eval set revision、环境版本、grader version、模型与策略版本。重新评分旧轨迹生成新评估记录，不覆盖历史，才能区分系统变了还是尺子变了。

真实轨迹进入评估集前脱敏并获得适当使用授权。抽样应覆盖失败而不过度保存用户内容。可保存结构化事实、摘要和可控重放 fixture，把原始敏感数据留在更严格边界。

防止评估污染：生产 prompt 或训练数据若包含固定答案，离线分数会虚高。保留隐藏集、轮换一部分案例，并用新事故与对抗样本持续扩充。模型 grader 的 prompt 与样例也属于评估资产，要版本控制和访问限制。

运营闭环

每周可靠性评审关注最弱维度与错误预算消耗来源：模型质量、工具故障、审批等待、资源过载还是恢复缺陷。每个来源对应不同 owner，不能把所有失败都丢给 prompt 优化。

事故复盘产出可验证行动：新增一条账本不变量、一个对账接口、一个失败评估样本或一个混沌实验。修复上线后在离线集和 canary 验证，再观察对应预算消耗是否下降。

SLO 也需要产品共同确认。过高目标可能阻止有价值迭代，过低目标会正常化用户伤害。选择用户可感知阈值，并用错误预算讨论可靠性与速度，而不是把“多少个九”当声望指标。

验收清单

随机抽取 good 与 bad run，确认分类能由权威回执重算；从账本重建分母，检查排除项；改变 grader version，历史分数仍保留；模拟预算快速燃烧，降载与发布冻结按政策触发。

发布前验证评估集包含崩溃恢复、结果未知、取消竞态、审批过期、重复消息和资源耗尽。只测试任务内容而不测试运行语义，无法证明这个 hub 讨论的可靠性。

指标证据来源见追踪与运行账本，把 SLO 假设变成受控扰动的方法见混沌实验与故障演练。

小结

  • 先用权威证据定义任务完成，再建立 eval、SLI、SLO 与错误预算。
  • 将状态合法、授权和副作用正确性设为硬门，不让语言质量平均分掩盖它们。
  • 用离线环境结果、确定性检查、校准 grader 与人工复核组合评估轨迹。
  • 以用户结果和 deadline 建在线 SLI，按任务风险分层而非只看全局平均。
  • 用 burn rate 与预先约定的预算政策驱动降载、回滚和发布冻结。
  • 对所有分数和事件记录版本，防止尺子变化被误认为系统进步。
