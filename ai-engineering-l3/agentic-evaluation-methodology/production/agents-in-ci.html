Agent 进 CI 门禁

评测从实验室搬进持续集成流水线的那一刻，身份就变了：从一份供人参考的报表，变成一个有权拦下合并的执法者。这个身份转换带来的不是技术问题而是制度设计问题——阈值定松了，退化照常流入主干，门禁沦为装饰；定紧了，噪声触发的误杀让开发者天天和门禁搏斗，最终整个团队学会的第一件事是绕过它。

核心概念：阈值的三层设计与统计依据

成熟的门禁不是一条线而是一套分级响应。阻断级直接拒绝合并，只配给最核心、最稳定、判定完全确定性的任务子集；警告级在 PR 上留下标注但不拦人，用于波动较大但值得关注的指标；观测级只记录不上报，用来积累新指标的基线数据，等方差特征摸清后再升级。三级之间的晋升与降级应该是显式的流程动作，而不是默认所有指标一上来就拦人。

阈值的数字从哪来

阈值的数字本身必须来自方差与功效分析的区间计算，而不是拍脑袋。原则只有一句话：阻断阈值必须大于该指标在此样本量下的置信区间半宽。如果你的核心集只有一百次运行，成功率的标准误就在四五个百分点，把阻断线设在「跌两个点就拦」等于把随机噪声请进了执法席——正确的做法要么扩大样本量，要么放宽阈值到噪声带之外，要么换用配对比较这种高分辨率的检验形式。反过来说，「这版掉了三个点但没显著」的正确处理是不拦并记录，而不是凭直觉放行或拦截。

层级 触发条件 动作 适用指标
阻断 核心集 pass@1 越过下界 / 成本超硬上限 拒绝合并 确定性判定的核心回归集
警告 波动型指标越过软阈值 PR 标注 + 通知 过程评分、效率指标
观测 新指标尚无稳定基线 仅落库 一切新上线的测量

预合并窗口里的取舍

全量套件动辄数小时的墙钟时间和数百美元的调用费，塞进每次提交既拖垮反馈回路又烧穿预算——评估成本管理的五板斧在这里从「省钱技巧」升级为「可行性前提」。

预合并的三层结构

预合并窗口的标配是三层结构：冒烟层几十条金标准任务，分钟级出结果，负责拦住灾难性倒退；切片层按本次改动影响的模块唤醒对应任务子集，负责拦住局部退化；全量层只在夜间或发版前运行，负责慢变量的监控。三层的任务分配随时间动态调整：切片层反复报警的任务晋升进冒烟层，冒烟层连续百日无事的任务可以降回切片层。

CI 里还有一个容易被忽视的工程约束：超时即信号。单轨迹的墙钟上限要和流水线的超时预算一起设计，失控的 agent 循环不该由 CI 超时来兜底——那会让整条流水线的失败原因变成一句没有诊断价值的 "timeout"。预算熔断要在评测 harness 内部先发生，并把「触线终止」作为结构化失败原因上报，而不是让外层流水线粗暴杀进程。

flaky：门禁公信力的头号杀手

门禁最致命的敌人不是漏拦也不是误拦，而是不可预期的误拦。一条十次里挂三次的任务出现在阻断层，一个月制造几十次假警报，开发者的信任被消耗光之后，团队会集体学会「re-run until green」——从此门禁在制度上还在，在实际中已死。重建信任比建立信任难得多，所以 flaky 治理要走在门禁升级的前面。

分类重试政策

治理的第一步是分类重试政策：环境级错误（容器启动失败、网络抖动）自动重试且不计入成绩，agent 行为导致的确定性失败绝不重试。这条纪律在评估环境与沙箱构建已经确立，CI 场景下还要求重试次数和「重试后通过」的事实都被记录在案——悄悄重试到绿等于篡改数据。

隔离区与 flaky 率门禁化

第二步是隔离区（quarantine）机制：确认 flaky 但一时修不好的任务移入隔离区继续观测但不参与阻断，同时开修复工单；隔离区要有强制清零期限，防止它变成垃圾抽屉。第三步是flaky 率本身的门禁化：新增任务的 flaky 率超过阈值就不准入库，存量任务的 flaky 率进入周报。

红了之后的两小时

门禁的价值一半在拦下，另一半在拦下之后的归因速度。一套合格的门禁失败应该在两小时内给出可行动的诊断，而不是甩出一屏日志让人考古。

自动归因报告

这要求评测设施在红的时候自动产出归因报告：失败任务按症状聚类（同类失败集中爆发指向系统性回归）、每类附代表性轨迹的首错步骤定位、成本与步数的异常标注（这次失败伴随 token 用量翻倍，指向循环而非能力缺失）。过程级评判的产出在这里兑现价值——过程级评判打的维度分能把「哪一步开始走偏」直接标在报告上。

    P[PR / 定时触发] --> S[冒烟层<br/>分钟级 金标准]
    S -->|崩| H[立即阻断 + 自动归因报告]
    S -->|过| C[影响切片层<br/>并行执行]
    C -->|越阻断阈值| H
    C -->|越警告阈值| W[PR 标注 不拦]
    C -->|过| N[夜间全量层]
    H --> T{归因}
    T -->|环境故障| Q[自动重试不计成绩]
    T -->|疑似 flaky| U[移入隔离区开工单]
    T -->|真实退化| B[打回 开发者修复]
    W --> M[人工判断是否升级规则]
    N --> D[趋势入库 供给阈值校准]

门禁的自我反哺

门禁系统的最后一项职责是反哺自身：每一次真实拦下的退化和每一次误伤，都是校准阈值与任务集的数据点。季度回顾应该回答三个问题——拦对率多少、平均归因时长多少、有没有指标长期处于警告区却从未升级或退役。当这些问题有了答案，门禁就从「上线了一个功能」进化成「长出了一个会自我修正的免疫系统」，而它的下一站是与线上流量打通：生产环境的真实故障如何流回这套体系，正是线上影子评估的主题。

小结

  • 门禁分阻断、警告、观测三层，逐级晋升要走显式流程。
  • 阈值必须大于当前样本量的置信区间半宽，否则是在执法席上安置噪声。
  • 预合并靠冒烟-切片-全量三层结构，预算熔断必须在 harness 内先于 CI 超时发生。
  • flaky 治理走在门禁前面：分类重试、隔离区限期、flaky 率本身也要门禁。
  • 红了之后两小时内给出聚类加首错定位的归因报告，门禁才有公信力。
