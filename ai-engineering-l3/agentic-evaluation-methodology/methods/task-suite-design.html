任务套件设计原则

模型没有变，换了套件，排名整个洗牌——这类事在 agentic 领域不是丑闻而是常态，因为分数从来不是模型的属性，而是「模型 × 套件」这个组合的属性。套件是你评测系统的光学仪器：焦距选歪了，后面的统计做得再精密，看到的也是一个变形的世界。本篇只谈一件事：怎样造一套能稳定分辨好坏系统的任务集。

核心概念：任务的四个来源

任务从哪来，决定了套件的天花板。实践中可用的来源有四类，价值密度差异很大。真实失败案例永远排第一：生产环境的工单、用户投诉的会话、CI 里反复红掉的构建，天然带着真实世界的纠缠度和明确的判定标准，而且和你的业务分布同分布。现场式改编次之：把真实仓库里的已解决问题改造成任务，SWE-bench 就是这么造出来的——从 12 个流行 Python 仓库的真实 GitHub issue 及其对应 PR 中筛出 2294 个问题，任务描述就是 issue 本身，判定就是仓库自己的测试套件（arXiv 2310.06770）。这种「借真实项目之力」的思路让任务的成本可控而保真度高。

全真模拟环境中的工作样本是第三条路：TheAgentCompany 自建了一个模拟小型软件公司的完整数字世界——内部 wiki、git 服务器、聊天工具、工单系统都有，任务就是这家「公司」里员工会遇到的活儿，agent 要像数字员工一样浏览网页、写代码、跑程序、和模拟同事沟通（arXiv 2412.14161）。第四类是参数化合成：用模板批量生成带标准答案的变体，量大管饱但容易同质化，适合做特定技能的压力测试而非主套件。

来源 保真度 造价 最佳用途
真实失败案例 最高 高（需脱敏清洗） 核心回归集
真实工件改编 高 中 主套件主体
全真模拟环境 高 很高（基建重） 端到端能力画像
参数化合成 低-中 极低 技能专项与扩量

四类来源的正确用法是混编而不是二选一：核心回归集用真实失败案例守住「上次坏过的不能再现」，主套件用改编任务铺广度，模拟环境做季度级的能力体检，合成变体在需要大样本统计功效时补量。

难度要为分辨力服务

套件的使命是把候选系统拉开差距，因此难度分布的设计目标是最大化区分度而不是堆难度。全员都会做的题和全军覆没的题对比较两个系统几乎没有信息量，真正干活的是那些「部分系统通过」的中段题。一个实用的标定流程：先用两三个已知水平的系统跑全量，按通过率给每道题标注难度档，然后检查各难度档的占比，刻意把中段（通过率三到七成）撑到套件的一半以上。

人类基线是难度标定的第二根尺子，它把抽象的百分比翻译成直觉。GAIA 的设计者专门测了人类受访者：92% 的正确率对照当时装备插件的 GPT-4 的 15%，这道鸿沟本身就是论文的核心论点（arXiv 2311.12983）。MLE-bench 走得更远——直接借用 Kaggle 公开排行榜给每场比赛建立人类奖牌基线，「至少达到铜牌水平」成了可机判的人类参照（arXiv 2410.07095）。METR 则给人类被试计时，用「人类平均花多久完成」给每个任务贴上时间标签，进而定义出模型的 50% 完成时间地平线（METR，2025 年，metr.org）。三种做法共同点在于：人类表现被当成测量系统的校准砝码，而不是可有可无的花边。

覆盖矩阵：防止套件偏科

有了好题目还要会编排。agentic 能力是多维的，单维总分必然掩盖结构性缺陷——一个检索很强但从不验证写入结果的 agent 和一个反之的 agent，总分可能一样难看。解法是维护一张覆盖矩阵，行是能力维度，列是场景维度，每道任务落在至少一个格子里：

维度 示例取值 配比考量
工具域 shell / 浏览器 / API / 文件系统 贴近部署形态
技能类型 检索定位 / 多步规划 / 校验修复 / 恢复重试 中段难度为主
故障注入 无 / 工具报错 / 权限拒绝 / 环境抖动 故障轨迹占两成以上
时程长度 短（<5 步）/ 中 / 长（>30 步） 长程题按预算控量

矩阵的价值在汇报时兑现：报告按格子切片输出，而不是只有一个总分。「恢复重试」列的骤降和「短程检索」格的持平，指向的是完全不同的修复路径。切片越细，单格样本量越小，噪声越大，所以切片粒度必须和方差与功效分析给出的样本量计算联动——这是套件设计和统计之间最实际的一条接口。

flowchart TD
    S[候选任务来源<br/>失败案例 / 改编 / 模拟 / 合成] --> V{查重与来源核验}
    V -->|泄漏嫌疑| X[拒收或改写]
    V -->|通过| P[试跑标定难度档]
    P --> D{通过率落点}
    D -->|全员通过或全灭| R[改造或退役<br/>无分辨力的题不占预算]
    D -->|中段三至七成| M[登记进覆盖矩阵格子]
    M --> G{该格样本充足?}
    G -->|否| S
    G -->|是| H[划入日常回归池]
    H --> K[同源扣留一份入私有保留池]

这张入库流程图里最容易被跳过的是「试跑标定」：未经真实系统试过的任务，难度档只是作者的想象，而分辨力恰恰由实际通过率决定。

保留集与任务的新陈代谢

套件一旦公开或长期使用，就会开始「变质」：被测方对着固定题目反复调优，分数涨了而能力没涨，这是 Goodhart 定律在评测上的显形，对策体系详见污染与过拟合基准。套件设计阶段的应对有两手。第一手是划出私有保留集：从每种来源各扣下一部分高质量任务不进日常回归，只在重大版本决策时启用，让保留集成为无法被刷的终审法庭。第二手是让任务保持新陈代谢：定期补充新来源的任务、退役被反复暴露的旧任务。LiveCodeBench 在代码领域把这个思想做成了机制——持续从竞赛平台收录新题，并支持按时间窗口切分「模型训练截止前/后」的题目来对照评估污染影响（arXiv 2403.07974）。

参数化生成是低成本供给新鲜任务的杠杆：把一道任务的骨架（初始状态、目标谓词、判定脚本）抽成模板，对实体、数值、文件布局做随机化，一次投入产出几百个同构不同面的实例。代价是必须警惕合成偏置——模板生成的任务分布窄于真实世界，所以它适合当配菜，主力仍然应当是真实来源。套件设计的全部原则归结为一句话：你不可能比你的任务集更了解一个 agent，所以把工程投资的大头押在任务的质量与覆盖上，永远不亏。任务造好后，下一步是给它们一个跑得起、停得下、复得位的家，即评估环境与沙箱构建的主题。

小结

  • 任务来源按价值排序：真实失败案例 > 真实工件改编 > 全真模拟 > 参数化合成。
  • 难度分布以分辨力为目标，中段题撑半壁江山，人类基线充当校准砝码。
  • 覆盖矩阵按工具、技能、故障、时程四维编排，汇报必须按格子切片而非只报总分。
  • 私有保留集对抗刷分，参数化与持续补给维持任务的新鲜度。
