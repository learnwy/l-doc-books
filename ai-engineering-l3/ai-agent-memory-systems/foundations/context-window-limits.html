上下文窗口与局限

2026 年，十三个以上的主流模型都把上下文窗口推到了百万 token 量级——Claude Opus 4.8、GPT-5.5、Gemini 3.1 Pro 都在其列，Llama 4 Scout 甚至号称一千万 token。于是一个诱人的想法浮出水面：既然窗口这么大，把所有历史一股脑塞进去，不就不需要记忆系统了吗？这一篇要证明这个想法为什么错，从而说清楚记忆系统存在的根本理由。

核心概念：上下文窗口是工作台，不是档案库

上下文窗口是模型单次调用能「看到」的 token 总量，包括系统提示、对话历史、检索到的资料和当前问题。它是模型的瞬时工作区——所有推理都发生在这块区域内，超出的部分模型完全无感知。

关键在于它的三个固有属性，决定了它无法替代外部记忆：有限（再大也有上限）、易失（每次调用都得重新加载，调用结束即清空）、昂贵且不均匀（token 越多越贵，且并非每个位置都被同等利用）。

flowchart TD
    A[所有历史信息<br/>可能数百万条] --> B{全塞进窗口?}
    B -->|是| C[成本爆炸<br/>+ 中间迷失<br/>+ 仍有上限]
    B -->|否·记忆方案| D[长期存储在外部]
    D --> E[按相关性检索<br/>只取最相关几条]
    E --> F[小而精的上下文]
    F --> G[准确·便宜·可扩展]

下表对比「把窗口当记忆」和「用记忆系统喂窗口」两种思路：

维度 全塞进大窗口 外部记忆 + 检索
容量上限 受窗口物理上限封顶 近乎无限（外部存储）
单次成本 随历史线性增长 仅相关片段，恒定可控
准确性 受中间迷失拖累 相关信息置于显著位置
持久性 调用结束即清空 跨会话持久
时延 长上下文显著变慢 检索快、推理上下文短

窗口尺寸：2026 年的真实数字

先把事实摆清楚。截至 2026 年，上下文窗口的格局大致如下：

  • 百万 token 俱乐部已有十三家以上，包括 Claude Opus 4.8/4.7/4.6、Claude Sonnet 4.6、GPT-5.5/5.4、Gemini 3.1 Pro、DeepSeek V4、MiniMax M3、Qwen3.5-Plus 等。
  • 极端者是开源自托管的 Llama 4 Scout，号称一千万 token 窗口。
  • 作为对照，被广泛使用的上一代里 Gemini 1.5 Pro 为 100 万、Claude 3.5 Sonnet 为 20 万、GPT-4o 为 12.8 万 token。

数字确实在涨。但「能塞进去」和「塞进去有用、划算」是两回事，下面两节就是泼冷水。

来源：Morph LLM Context Window Comparison 2026、Pristren LLM Context Window Sizes Compared 2026。

中间迷失：大窗口的准确性陷阱

最早在 2023 年的论文里被记录、此后在多个模型上反复复现的「中间迷失」（lost in the middle）效应，是大窗口最致命的暗病：模型对位于长上下文中间的信息，检索和推理准确率显著低于开头和结尾的信息。

具体到数字：对处于中间位置的信息，准确率可能下降 20% 到 40%。换句话说，你把一份九十万 token 的文档塞进百万窗口，问其中第六百页的内容，模型可能自信地给出错误答案——信息明明在里面，但模型的注意力「飘」过去了。

可以把它粗略理解为：注意力机制虽然理论上能覆盖全窗口，但有效注意力在序列上呈 U 形分布，两端强、中间弱。设上下文长度为 LLL，则有用信息越靠近 L/2L/2L/2，被准确利用的概率越低。这意味着「窗口大」不等于「记得清」——大窗口给了你塞东西的空间，却没保证模型真的用得上。

这正是记忆系统的价值所在：与其把一万条记忆一股脑摊在中间任其被淹没，不如只检索出最相关的三五条，放在上下文的显著位置。如何挑出这「最相关几条」，是检索与相关性的核心议题。

来源：Pristren Context Window Explained。

成本与时延：每次都重新加载的账

中间迷失是准确性问题，成本与时延则是经济性问题，同样致命。

上下文窗口是易失的：模型不在两次调用之间「记住」窗口内容，每一次调用你都得把需要它看到的所有历史重新发送一遍。假设一段对话已经积累了 50 万 token 的历史，若每轮都全量回传，那么聊到第十轮，你已经为这 50 万 token 付了十次钱，时延也随上下文长度显著拉长。

记忆系统把这笔账彻底改写：历史存在外部，每轮只检索出相关的几百到几千 token 回传。成本从「随历史线性增长」变成「恒定可控」，时延也大幅下降。对于长期运行、动辄数百轮的智能体，这个差异是「能不能用」级别的。

把窗口预算花在刀刃上、而非全量回灌，正是工作记忆组装要解决的问题，详见短期与工作记忆。

长上下文与记忆系统：互补而非替代

需要纠正一个误解：本篇不是要否定长上下文。长窗口是极有价值的工具——一次性分析整本书、处理大型代码库、容纳更丰富的少样本示例，这些都受益于大窗口。

正确的心智模型是两者互补：长上下文是更大的工作台，适合「这一次任务需要同时看到大量材料」；记忆系统是档案库，负责「跨任务、跨会话地持久保存并精准取用」。一个成熟系统往往是「大窗口 + 检索记忆」的组合——用记忆系统决定哪些信息进窗口，用大窗口容纳这些被精选信息加上当前任务材料。

所以记忆系统不是等更大窗口来淘汰的临时方案。只要模型仍是无状态的、窗口仍有上限和中间迷失、且每次调用都要重新加载，外部记忆就是结构性的刚需——这也回应了智能体为何需要记忆里埋下的伏笔。

小结

  • 上下文窗口是模型的瞬时工作台，具有有限、易失、昂贵且利用不均三个固有属性。
  • 2026 年百万 token 窗口已普及十三家以上，但「能塞」不等于「有用且划算」。
  • 中间迷失效应让长上下文中部信息的准确率下降 20%-40%，大窗口不保证记得清。
  • 窗口易失意味着每次调用都要重新加载历史，全量回灌会让成本随历史线性增长、时延飙升。
  • 长上下文与记忆系统互补：前者是更大的工作台，后者是档案库，成熟系统用记忆决定哪些信息进窗口。
