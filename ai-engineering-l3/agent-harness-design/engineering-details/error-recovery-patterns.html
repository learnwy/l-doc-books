错误恢复与重试模式

跑了一夜的 agent 任务，第二天早上翻轨迹时你会发现一个规律：区分好坏结果的不是「有没有出错」——长任务里出错是必然——而是出错之后的那两三轮发生了什么。好的 harness 把错误变成一次廉价的改道，差的 harness 让同一个错误以五种姿势反复出现直到烧完预算。错误恢复不是异常处理的附属品，它是 agent 架构的主干逻辑之一。

核心概念：先分类再处置

所有错误混在一个 try-catch 里是 agent 工程最常见的反模式。按成因与正确响应，错误天然分成四类：

类别 典型例子 正确响应 执行者
瞬态 限流 429、网络抖动、上游 5xx 指数退避自动重试 harness 基础设施层
确定性 参数类型错、文件不存在、权限被拒 结构化错误文本交模型自纠 工具层
语义 实现方向整体走偏、修复后测试仍全红 反馈入上下文并回滚到检查点 循环策略层
环境 磁盘写满、依赖缺失、沙箱拦截 升级为人类任务或切换环境 升级路径

分类的价值在于避免用高成本手段处理低级问题：让模型「思考」怎么解决限流是荒谬的——那是退避定时器的活；反过来，让基础设施盲目重试语义性失败则是灾难——方向错的方案重试十次只会更错。状态机应当把四类分流画清楚：

stateDiagram-v2
    [*] --> 执行中
    执行中 --> 已成功: 结果符合预期
    执行中 --> 瞬态失败: 限流或超时
    瞬态失败 --> 退避等待
    退避等待 --> 执行中: 未达重试上限
    瞬态失败 --> 升级人工: 重试耗尽
    执行中 --> 确定性失败: 参数或环境错误
    确定性失败 --> 模型自纠: 错误作为观测
    模型自纠 --> 执行中
    模型自纠 --> 升级人工: 连续未解

瞬态错误：退避、抖动与熔断

瞬态失败的工业标准做法是指数退避加抖动：第 kkk 次重试前等待

tk=min⁡(t0⋅2k+uk, tmax⁡)t_k = \min\left(t_0 \cdot 2^k + u_k,\ t_{\max}\right)tk​=min(t0​⋅2k+uk​, tmax​)

其中 uku_kuk​ 是均匀随机抖动，用于打散同时撞上限流的重试风暴。OpenAI 的限流指南明确建议指数退避，并要求优先尊重响应里的 Retry-After 头而不是自己猜（platform.openai.com 限流指南）。设单次尝试成功率为 ppp，允许重试 kkk 次后的总体成功率为

Pk=1−(1−p)k+1P_k = 1 - (1 - p)^{k+1}Pk​=1−(1−p)k+1

p=0.5p = 0.5p=0.5 时三次重试就把成功率推到约 94%94\%94%——瞬态错误值得自动化，因为数学上便宜。

但要配两个保险丝。一是重试上限与总时限并存，防止慢速泄漏式失败（每次都成功一半）无限占用会话；二是熔断：同一目标连续多轮触发退避就暂停该目标的后续调用并上报，避免一个坏掉的端点拖垮整个循环。这些机制全部住在 harness 基础设施层，对模型完全透明——模型不需要知道也不应该知道限流的存在。

确定性错误：把报错写成教材

参数错、文件不存在这类失败不会因重试而好转，唯一正确的出口是让模型拿到可执行的修正信息。这要求工具层把两类信息分得干干净净：给人看的日志进事件流，给模型看的错误进观测。结构化的错误文本应包含三段：出了什么错（具体字段与实际值）、约束是什么（期望格式与边界）、怎么改（可直接照做的建议）。「Error code -32602」是零信息量的，「参数 path 指向目录而非文件；如需列出目录内容请使用 list_dir」是一轮自愈。

在错误到达模型之前还有一道便宜的防线：执行前校验。schema 校验、路径存在性检查、权限预判都能在不消耗一轮推理的情况下拦截大半确定性错误。校验器拒绝时给出的消息同样按教材标准写——它和运行期错误一样是模型的输入。接口侧的配套原则见工具接口在 harness 中的设计，此处强调分工：接口设计决定错误长什么样，本篇决定错误之后流程往哪走。

语义错误：反馈、回滚与重复采样

最难的一类是「每一步都执行成功了，但整件事做错了」。三层武器按成本递增排列。

第一层是语言化反馈：把失败的证据（报错栈、失败的测试名、评审意见）整理后注入下一轮上下文，让模型显式反思再行动。Reflexion 证明这种「口头强化」无需微调就能显著提升多轮解决率，其本质是把环境反馈当作免费的训练信号（arXiv 2303.11366）。

第二层是检查点回滚：发现方向性错误时，与其在废墟上打补丁，不如回到上一个健康状态重走。git 是现成的实现——Aider 的实践是每次修改都自动生成规范提交，出问题直接 revert 到任意节点，版本历史成为 agent 的撤销栈（aider.chat FAQ）。harness 要做的决定是检查点密度：每步一提交安全但噪音大，按里程碑提交快但回滚粒度粗。

第三层是重复采样：同一任务独立跑多次取最优。Large Language Monkeys 的系统测量显示覆盖率随采样数对数线性上升，Gemini 1.5 Pro 在 SWE-bench Lite 上单次解决率 15.9%，采样 250 次后覆盖率达 56%（arXiv 2407.21787）。代价是成本严格线性增长且需要可靠的验收器来筛选样本——它适合离线批量场景，不适合交互式会话。

重试语义的实现要点

把退避公式变成正确的代码，还有四个工程细节。幂等性优先：重试的前提是重复执行无害，读操作天然幂等，写操作必须先有幂等键（请求 ID、条件写入、或以 git 提交为单位的原子变更），否则网络抖动会让一次「创建工单」变成三张。两级重试预算分开管：基础设施层的瞬态重试对模型不可见，不该消耗模型的轮次预算；而模型可见的失败（工具返回错误文本）每轮都在花推理钱，两者的上限、监控与告警必须分列。抖动要真随机：固定间隔的重试风暴会与限流窗口共振，均匀抖动的实现只需一行，省掉的是整批任务同时撞墙的排障之夜。区分「失败」与「慢」：超时后发起重试前先确认前次调用确实终止，否则两个调用并行写同一状态，故障面瞬间翻倍。

故障注入：恢复路径也要回归测试

恢复逻辑最大的尴尬是平时不运行、运行时没测过。故障注入把它拉进日常：在 harness 的工具层和网络层埋设可控故障点——返回 429 与 Retry-After、制造半途断连、让某个依赖延迟三十秒——然后在 CI 里验证三类断言：退避曲线符合公式且带抖动；熔断在预设次数内触发并上报；升级移交的说明文档包含已试选项清单。更进一步可以做混沌演练：定期在生产影子环境里随机注入组合故障（限流叠加磁盘写满），观察循环是优雅降级还是雪崩。这些演练产出的不是分数而是信心——知道每个保险丝真的装在了正确位置。

升级路径与错误预算

恢复设计的最后一环是承认有些错误不该由 agent 再试。连续 mmm 轮同类失败、同一动作签名重复出现、或用户明确表达不满时，harness 应停止自主尝试，产出结构化的移交说明：已试过什么、证据是什么、剩余选项有哪些。判断阈值可以用简单的错误预算制：给每个会话分配 β\betaβ 个「失败额度」，额度随语义性失败扣减、随成功核验返还，归零即强制移交——这把「何时叫人」从一个模糊的工程直觉变成一条可配置的策略。

所有恢复动作都应是事件流上的一等公民：重试、回滚、升级都要留下带原因码的事件记录，事后才能统计各类错误的真实发生率与处理成本，反过来指导预算与阈值的调优（观测管道见事件流与可观测 UI）。

小结

  • 先分类再处置：瞬态交给退避器，确定性交给模型自纠，语义靠反馈加回滚。
  • 退避公式带抖动与上限，配熔断防止单点拖垮全局。
  • 报错按教材标准写：现象、约束、改法三段齐全才值一轮推理。
  • 回滚用 git 当撤销栈，重复采样留给离线场景，错误预算决定何时叫人。
