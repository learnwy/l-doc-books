事件流与可观测 UI

用户敢不敢把任务整个交给 agent，决定往往发生在最初三十秒：如果屏幕上只有一行沉默的光标，多数人会在第十秒按下 Ctrl-C。反过来，一个实时滚动的 diff、一条清晰的「正在运行测试（第 2 次，共 3 次）」，能把同样的等待变成可控的进度。事件流不只是 UI 的数据源——它是 harness 的神经系统，同一套事件既喂给人看，也喂给 CI、审计器和计费器。

核心概念：事件作为唯一事实源

OpenHands 的架构决策最有代表性：agent 与环境的全部交互被统一编码为事件流上的条目——动作、观测、消息、状态变更、错误——循环本身只是事件的消费者与生产者（arXiv 2407.16741）。这个选择带来三个连锁好处：可回放（持久化的事件序列足以重建任意时刻的会话状态，恢复逻辑因此变薄）、可审计（权限审批、危险操作都有不可篡改的流水记录）、多消费者解耦（终端渲染、Web 面板、评估器读同一条流互不干扰）。

事件类型 关键载荷 人的界面如何处理 机器消费方
回合开始 目标摘要、预算上限 状态栏复位、目标置顶 计费与追踪起点
文本增量 流式文本片段 即时渲染打字效果 转写与索引
工具调用开始与结束 名称、参数摘要、耗时 折叠面板加旋转指示器 时延分布统计
权限请求 工具、参数、风险分级、变更预览 高亮审批框、默认聚焦拒绝 合规留痕
错误与恢复动作 错误码、退避轮次、处置决策 警示色、可展开的完整栈 告警与错误率看板
用量上报 token 明细、缓存命中数 成本角标实时累加 预算熔断判断

设计事件 schema 时的两条纪律：类型封闭——新增语义靠新增类型而不是往自由字段里塞字符串，否则下游解析者各自猜；载荷自足——每条事件携带理解它所需的上下文快照，回放时不需要翻找前文。这两条决定了事件流能否在一年后仍然可用。

从内核到屏幕：流的分发拓扑

    participant U as 终端 UI
    participant L as 持久化日志
    M-->>K: 文本增量流
    K->>B: assistant_text_delta
    B->>U: 实时渲染
    K->>B: tool_call_start 与结果
    B->>L: 追加落盘
    U->>K: 用户按键打断
    K->>B: interrupted 事件

传输层通常直接复用模型 API 的流式协议：Anthropic 的消息接口以 SSE 推送 message_start、content_block_delta、message_stop 等类型化事件，harness 把上游增量与自己的工具事件合流成统一的下游流（docs.claude.com 流式接口）。合流点要处理一个容易被忽略的细节：顺序一致性——工具执行期间的文本增量、权限弹窗与用量上报可能乱序到达，事件总线必须给出全序，否则回放与实时画面会出现两个不同的历史。合流还牵出格式化的归属问题：同一次工具执行，人需要折叠摘要与高亮 diff，模型需要带锚点的纯文本观测——两种视图必须出自同一份原始结果而非两条执行路径，接口层的分工原则见工具接口在 harness 中的设计。

流式渲染的心理学与数学

流式输出的价值可以量化。设回答共 nnn 个 token、生成速率为 rrr，非流式模式下用户的感知等待就是全程 n/rn/rn/r；流式模式下首个可见 token 在首字节延迟 tttfbt_{\text{ttfb}}tttfb​ 后出现，此后用户持续获得进展信号。等待体验的主导项从总时长变成

tttfb+1rt_{\text{ttfb}} + \frac{1}{r}tttfb​+r1​

即「多久开始动」加「每个字隔多久」——两者都可以用工程手段压低：预热连接、减少首轮前置处理、以及避免在首个 token 前做任何阻塞式装配。这也是为什么 harness 应该把权限检查这类轻量工作放在流已开始之后按需进行，而不是攒一个大而全的前置阶段。

呈现层还有一套为「扫读」优化的细节：工具调用默认折叠为一行摘要（名称加关键参数），展开才见全量；正在运行的步骤给旋转指示器；diff 用行级着色并只显示改动窗口；长命令的输出尾部优先——错误几乎总在最后几十行。这些约定在 Claude Code 的终端实现里已成事实标准（interactive-mode 文档）。

Schema 的版本化：让一年后的回放仍可读

事件流的寿命以年计，而消费它的代码以周迭代，版本策略因此不能事后补。三条经过验证的纪律：每条事件携带 schema_version 字段且只做加法演进——新增字段允许，改义与删除禁止，确需淘汰就引入新类型并保留旧类型双写一个过渡期；载荷里的枚举值同样封闭管理，下游遇到未知值时按「最接近的已知类型降级处理」而不是崩溃。回放器要能跨版本读取：持久层保留各版本的解析器或升级函数，让半年前的会话在今天的工具里打开时不丢语义。这些约束看似繁琐，但事件流一旦成为审计与恢复的事实源，任何一次不兼容变更都是对历史记录的损毁。

终端之外：同一总线的其他渲染器

终端不是事件流的唯一客户。Web 面板把折叠面板换成可搜索的时间线，审批请求可以推送到手机上由值班者放行——权限决策从「坐在终端前的人」解耦为「有权限的人 wherever」，这对长时任务与团队值守场景是质变。CI 消费者则走无头 JSON 行流（下节展开）。多渲染器并存时有一条铁律：呈现逻辑永不回写内核状态——面板上的折叠、过滤、标注都只是视图偏好，唯一的写路径仍是用户指令与审批决定走的事件总线。守住这条边界，加一个新的消费者就不会变成一次架构手术。

一套内核，两种消费者

同一个事件流要同时服务两种口味完全相反的消费者。人要的是渐进披露与视觉降噪；程序要的是稳定 schema 与完备性。成熟 harness 的解法是输出格式分层：交互模式渲染富文本，无头模式提供 JSON 行流——Claude Code 的 --output-format 支持 text、json 与 stream-json，后者把每个事件作为独立 JSON 对象按序吐出，CI 与编排器逐行消费即可获得与人眼等价的完整过程记录（CLI 参考）。这层设计的意义在于让「放进流水线」不需要另造一个精简版 agent——评测与回归测试因此可以直接驱动真实 harness，这正是第四章消融方法的前提之一。

可观测指标：从看到了什么到跑得怎样

有了结构化事件，观测就只是聚合问题。行业正在收敛到 OpenTelemetry 的生成式 AI 语义约定：模型名、token 用量（区分输入输出与缓存命中）、请求耗时等以 gen_ai.* 属性标准化，跨 harness 可比（OTel GenAI 语义约定）。在此之上，harness 值得常驻四个仪表：单步时延分布（P50/P95，定位慢在模型还是工具）、每任务成本曲线（联动上下文管理的预算表）、工具调用频率与失败率（暴露接口设计与文档缺陷）、人工干预密度（每十轮几次打断或改道，是信任度的直接量化）。这四条曲线放在一起，harness 的健康状况一眼可辨——它们也是下一章消融实验的自变量监测仪。

小结

  • 事件流是唯一事实源：可回放、可审计、多消费者共享。
  • 类型封闭加载荷自足，保证一年后的事件仍能被机器理解。
  • 流式渲染把等待主导项压到首字延迟加单字间隔。
  • 无头 JSON 行流让 CI 与人看到同一份过程；四条核心曲线守护健康度。
