Harness 与 Agent 框架的分界

「我们该用哪个 agent 框架？」——这个问题在评审会上出现时往往已经问错了方向。框架和 harness 不是同类事物的两个品牌，而是两种不同抽象层级、不同交付单位的实体：框架给你循环的原语，harness 给你一台完整运转的机器。混淆两者会导致典型的错位决策——用框架拼了三周发现权限审批、会话恢复这些真正难的部分全都不在货架上的覆盖范围内；或者反过来，任务明明只需要一个百行脚本却引入了整套状态图依赖。本篇把这两类实体的边界画清楚。

核心概念：分界线在「谁拥有循环」

agent 框架是嵌入你进程的库或 SDK：它提供构建循环的预制件——状态图节点、消息传递、检查点持久化、人工介入断点——但何时调用模型、调用之后发生什么，控制权在你手里。产品级 harness 是一个可运行的完整体：它拥有循环本身，你通过配置、说明文件和审批交互来约束它，而不是编写它。判断归属的最快办法是回到Harness 是什么：模型之外的另一半给出的六子系统清单——框架通常只覆盖其中一两个，而外壳必须六个齐装。Anthropic 在总结 agent 构建经验时给出的建议从侧面印证了这条线：多数生产场景用少量可组合的简单模式就够了，重框架常常是不必要的间接层（Anthropic，2024 年 12 月，building-effective-agents）。

框架提供什么：循环原语与其真实覆盖度

主流框架的能力清单高度趋同。OpenAI Agents SDK 把原语归纳为 agent、handoffs、guardrails、sessions 与 tracing 五件套，定位是「Swarm 的生产化继任」（OpenAI Agents SDK 文档）。Google 的 ADK 用顺序、并行、循环三种工作流 agent 加多层多代理组合来覆盖编排需求，并附带评估工具（Google ADK 文档）。LangGraph 一系则以图结构表达状态机，主打检查点与人在环路中断。

把这些清单对齐到第一章的六子系统表格，会发现一个一致的缺口：框架普遍覆盖循环与部分持久化，对权限闸门和面向人的呈现几乎不置一词。这不是缺陷而是定位使然——它们是库，而审批 UI 和沙箱是产品。可以用覆盖率粗算工作量：设六子系统中框架直接供给的比例为 α\alphaα，则你仍需自建的部分占

1−α1 - \alpha1−α

以典型框架 α≈13\alpha \approx \tfrac{1}{3}α≈31​ 计，三分之二的 harness 工程——恰恰是最难的权限、呈现与深度上下文治理——仍在你的肩上。评估框架时的正确问题因此不是「它有什么」，而是「剩下什么」。

harness 提供什么：被固化的判断

产品级 harness 的价值在于它把无数微小判断固化成了默认行为：工具结果太长时截断还是折叠、用户在执行中发消息时排队还是打断、压缩历史时保留哪些锚点、危险命令是询问一次还是每次都问。这些决定单个都不起眼，合起来决定了系统「敢不敢让它跑」。Claude Code 的终端体验、Codex CLI 的沙箱审批档位、Devin 的云端隔离环境，本质都是各自对这些判断的答案（参见参照系：Claude Code、Codex CLI 与开源 harness；Codex 的沙箱档位见其沙箱文档）。

固化的另一面是刚性：外壳的循环语义你改不动，遇到不合适的步进粒度只能绕行。这就是为什么重度定制需求的团队最终走向「借壳生蛋」——把成熟 harness 抽成库来用。Claude Agent SDK 正是这个方向的产物：把驱动 Claude Code 的同一套循环、工具与权限机制作为 SDK 开放，让应用直接继承产品级 harness 的判断（Anthropic，2025 年，building-agents-with-the-claude-agent-sdk）。

决策框架：三条问题定去留

选择时依次问三个问题。第一，循环语义是否需要专属？若你的领域有强自定义的步进逻辑——比如编译器式的多阶段流水线、需要严格审计的审批链——框架的图表达是对的投资；若循环就是标准的「思考—行动—观测」，自建或借用现成壳都更省。第二，权限与合规是否是硬约束？碰支付、生产数据、客户租户的系统，产品级 harness 内建的审批与沙箱能省掉数月自研，且这些组件的正确性极难验证。第三，团队要维护的是差异化还是通用件？通用件（重试、追踪、状态管理）交给框架，差异化的领域工具与上下文策略自己写——这个分工原则同样适用于仓库级工具选型（见兄弟 hub 对项目内工具化的讨论，此处不再展开）。

一个务实的混合形态正在成为主流：内核用最小自研循环（mini-swe-agent 证明了百行即可，SWE-agent/mini-swe-agent），按需引入框架的单个原语而非全家桶，权限与呈现层借鉴成熟 harness 的设计再裁剪。它的好处是每一层的替换成本都被压低——当模型厂商下一次把某层能力吸收进 API 时，拆掉的只是那一层。

两个场景的完整推演

抽象标准落到具体场景才有判断力。场景 A：内部数据平台的自然语言查询助手。循环就是「理解问题—查 schema—写查询—核对结果」，权限面只有只读数据库账号，失败重试成本低，用户是公司同事而非外部客户。三个问题的答案：循环不需要专属（标准形态）、权限非硬约束（只读兜底）、要维护的差异化在数据语义层。结论：框架甚至百行自研循环都绰绰有余，引入产品级外壳反而让用户多学一套终端交互。

场景 B：支付对账 agent，每晚在生产只读副本上追查资金差异，必要时对中间环境执行修正脚本。此时循环仍不特殊，但权限是硬约束——每一次写操作都要可审计、可回滚、有审批链；会话必须跨夜存活且崩溃后能续跑；过程记录要能直接进合规报告。自建这套闸门与持久化的成本远高于借用成熟产品壳或其 SDK 化形态，且正确性风险不可控。结论：产品级 harness 或其 SDK，自研部分收缩为领域工具与对账规则。

两个推演暴露了决策表的一个隐藏维度：错误的代价不对称性。框架选错可以重构（代码是你自己的），harness 的安全默认选错则可能直接变成事故——所以边界两边的迁移成本不对称，向保守档位迁移永远更便宜。

小结

  • 框架交付循环原语，harness 交付包含权限与呈现的完整判断，二者不在同一层。
  • 框架普遍不覆盖权限闸门与人类界面，这部分永远是自建项。
  • 选型三问：循环要不要专属、权限是不是硬约束、维护的是差异化还是通用件。
  • Claude Agent SDK 代表「产品壳 SDK 化」趋势，混合形态正成为务实主流。
