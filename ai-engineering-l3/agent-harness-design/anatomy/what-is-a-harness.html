Harness 是什么：模型之外的另一半

给同一个模型换一套外壳，能力表现能差出几条街：Agentless 不用显式 agent 循环，仅靠定位、修复、验证三段流水线，就在 SWE-bench Lite 上以平均约 $0.34 的成本解决了 27.33% 的 issue，压过当时一票结构复杂的 agent 系统（arXiv 2407.01489）；反过来，SWE-agent 团队发现只要重新设计模型操作计算机的界面，同样的底层模型就能多解决一大截真实 GitHub issue（arXiv 2405.15793）。这两个方向相反的实验指向同一件事：在 agentic 系统里，围绕模型的工程与模型本身同等重要。这套「之外的工程」就是本 hub 的主题——harness。

核心概念：六个子系统

harness 是包裹语言模型的完整运行时外壳：它决定每一步何时开始、喂给模型什么、允许模型碰什么、以及过程如何呈现给人。按职责可以拆成六个子系统，任何 agent 产品——从终端里的 Claude Code 到云端托管的 Devin——都是这六件的某种组合（参见参照系：Claude Code、Codex CLI 与开源 harness）。

子系统 职责 典型设计决策
循环引擎 决定「下一步」何时由谁触发 单步还是连续、最大轮数、停止条件
上下文装配器 每一步喂给模型什么 预算分配、历史裁剪、检索注入
工具执行器 把模型意图变成真实世界动作 接口粒度、返回值体积、并发控制
权限闸门 在副作用前插入人类或规则审查 审批模式、沙箱边界、审计日志
事件流与呈现 让过程对人可见可控 流式渲染、打断入口、diff 展示
会话持久化 让工作跨越进程与时间存活 断点续跑、检查点回退、跨端迁移

这六个子系统的具体设计取舍分别在后续章节展开：循环见Agent 循环设计：步进、中断与恢复，上下文见第二章第二篇，权限见第二章第三篇。

术语源流：测试台架 → 评测 harness → agent harness

harness 一词不是 AI 原生词汇。软件测试里的 test harness 指驱动被测代码、喂入用例、收集结果的台架；LLM 时代 EleutherAI 的 lm-evaluation-harness 把这个词带火，专指统一跑基准、保证可比性的评测框架（EleutherAI/lm-evaluation-harness）。agent 文献里同义的词是 scaffold（脚手架）：SWE-bench 论文用它指包裹模型的求解程序，与被测的底层模型明确区分（arXiv 2310.06770）。

本 hub 采用最宽口径的 harness：既包含纯代码的编排层，也包含权限 UI、终端渲染这些产品层。理由很实际——对用户而言，「这个 agent 能不能干成活」由整只壳决定，拆开讨论反而丢信息。评测语境下需要更窄的「脚手架」概念时，会在Harness 消融里单独收紧定义。

能力包络：为什么换壳如此有效

把任务成功建模为两个独立环节的串联：模型要解对子问题，harness 要把正确的材料与操作面递到它手上。设两者概率分别为 pmp_mpm​ 与 php_hph​，则

P(success)=pm⋅phP(\text{success}) = p_m \cdot p_hP(success)=pm​⋅ph​

一个 pm=0.9p_m = 0.9pm​=0.9 的强模型配上 ph=0.5p_h = 0.5ph​=0.5 的粗糙外壳，成功率只有 0.9×0.5=0.450.9 \times 0.5 = 0.450.9×0.5=0.45；而把外壳做到 ph=0.85p_h = 0.85ph​=0.85，同样的模型成功率升到约 0.770.770.77——不换模型白拿三十多个点的提升，这就是 ACI 论文的核心发现：接口设计的收益常常大于换更强的模型（arXiv 2405.15793）。乘法模型还解释了另一个现象：当模型侧快速进步时，粗糙外壳的短板会更刺眼。METR 用「50% 可靠度任务所需的人类工时」度量模型长程能力，发现该指标约每七个月翻一番（arXiv 2503.14499）；地平线拉长意味着轨迹步数 nnn 变大，任何单步层面的摩擦都会被串联放大。

反方向的证据同样有力：Agentless 用最朴素的流水线拿到高性价比成绩，说明「更多自主循环」并不天然更好——harness 设计是关于匹配任务的，不是关于堆机制的（arXiv 2407.01489）。

边界内与边界外

有几样东西经常被误算进 harness，值得切出去。模型内置的能力不算：function calling 的原生支持、缓存命中、系统提示里的安全训练，都在权重与服务端，harness 只是消费它们。应用业务逻辑不算：你的领域规则、数据模型、产品需求属于上层应用，正如变速箱逻辑不属于底盘制造学。评测设施单列：跑分用的评测 harness 与运行时的 agent harness 共享名字但职责不同，前者追求可比性与复现，后者追求任务完成率与安全性，两者的交集只在消融实验里出现。

而下面这些灰色地带属于 harness 的核心领地，恰恰是最容易被忽略的：系统提示与项目说明文件的组装顺序、工具结果的截断策略、用户消息排队时的行为、会话恢复时重放哪些事件。它们太细，细到没有论文专门写，但每天都被成千上万的用户摸到——Claude Code 把 CLAUDE.md 的加载、压缩阈值、快捷键打断都做成了一等公民，正是因为这些细节就是产品本身（Claude Code 文档）。

最小可行 harness：一百行的启示

六个子系统听起来庞大，但它们的最小实现可以惊人地紧凑。SWE-agent 团队后来发布的 mini-swe-agent 把整套 agent 压进约百行 Python：循环就是「问模型、执行 bash、把输出拼回去」，没有压缩、没有检索、没有复杂权限——却能在 SWE-bench 上拿到接近完整版的成绩（SWE-agent/mini-swe-agent）。它的存在证明了一件事：harness 的价值不在机制数量，而在每一环是否与任务形态咬合。

while True:
    obs = collect_context(history, env_state)   # 上下文装配
    action = model(obs)                          # 模型决策
    result, done = execute(action)               # 工具执行
    history.append(action, result)               # 追加记忆
    if done: break                               # 停止条件

对照六子系统清单看这段伪代码：循环引擎是 while True 加停止判断，上下文装配是 collect_context，工具面只有 bash 一个入口，权限闸门完全缺位，呈现层为零，持久化就是进程内存。生产级 harness 的演化史几乎就是把缺失的四环逐个补上的历史——而补的顺序应该由任务的风险等级决定：碰生产数据的先补权限，跑八小时以上的先补持久化。

三类作者与他们的盲区

harness 的作者大致三类，各自的起点决定了他们的系统性盲区。模型厂商做的外壳（Claude Code、Codex CLI）默认自家模型的下一代会更好，因此倾向于把判断做进产品而非配置面——好处是体验一致，代价是换模型的成本被刻意抬高。开源平台（OpenHands 一系）优先考虑可替换性与社区扩展，六子系统都留了插槽，代价是默认组合缺乏打磨，装完还要自己回答权限与呈现的所有问题。应用团队自研的外壳最懂业务，但几乎总是低估持久化与恢复——前两周没人需要断点续跑，第三周起它变成每周都在流血的伤口。

识别自己属于哪类、以及即将雇佣哪类，能提前暴露风险面。一个实用的交叉检验：让候选方案现场演示「用户在第 20 步打断并追加一条新约束」和「进程崩溃后从上一步继续」这两个场景——前者暴露中断语义的成色，后者暴露持久化的深度。两个场景都能优雅通过的 harness，六个子系统大概率是齐装的。

设计含义

第一，把 harness 当作有独立架构的软件来评审，而不是模型 API 调用周边的一次性胶水；六个子系统各自值得一张设计文档。第二，改进前先归因：用固定模型变外壳、固定外壳变模型的对照实验确认瓶颈在哪一侧，方法见第四章。第三，承认外壳的时效性——模型每次升级都会吸收掉一些脚手架功能（原生工具调用取代手写解析、长窗口降低检索复杂度），好的 harness 设计要把「某天可以删掉」作为模块的美德而不是失败。

小结

  • harness = 循环 + 上下文 + 工具 + 权限 + 呈现 + 持久化六个子系统的组合。
  • 成功率近似为模型可靠率与 harness 供给率的乘积，两边都可投资。
  • 术语源自测试台架与评测框架，agent 语境下与「脚手架」同义。
  • 设计目标是匹配任务形态，而非堆砌自主机制。
