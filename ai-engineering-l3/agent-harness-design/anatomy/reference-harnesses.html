参照系：Claude Code、Codex CLI 与开源 harness

自己动手设计之前，先花一个下午解剖五个成熟标本，能省掉之后几个月的重复试错。这一篇不评优劣——每个 harness 都是特定约束下的答案——而是逐个回答同一组问题：循环怎么走、权限闸门在哪、记忆放在哪里、会话怎么活过进程重启。见过足够多的不同器官排布，你在自己的设计图前才不会把某个厂商的局部选择当成物理定律。

核心概念：五个样本的横向解剖

先给结论性的全景。选样覆盖了三种形态：终端原生（Claude Code、Codex CLI、Aider）、开放平台（OpenHands）、云端托管（Devin），正好张成当前 harness 设计的空间。

维度 Claude Code Codex CLI OpenHands Aider Devin
形态 终端 CLI + IDE 插件 终端 CLI（Rust 实现） Web 平台 终端 CLI 云端托管服务
循环特征 自主多步，可打断、消息排队 自主多步 + 显式审批策略 事件流驱动的 agent 循环 人机交替的结对节奏 长时自主会话，可并行多开
权限模型 审批提示、hooks、可选命令沙箱 read-only / workspace-write / danger-full-access 三档沙箱加审批策略 Docker 隔离运行时 以 git 提交为安全网，无 shell 自动执行默认面 云虚拟机隔离 + 平台管控

Claude Code：终端原生的完整闭环

Claude Code 于 2025 年 2 月以研究预览形式发布，把「agent 该住在哪」的答案从 IDE 和网页拉回了终端。它的六个子系统都有清晰对应物：循环是带预算的自主步进，用户随时可以按键打断或排队追加消息；上下文装配围绕 CLAUDE.md 展开的项目级说明文件，接近窗口上限时自动压缩；工具面是读、写、bash 等一组窄接口；权限层由审批提示、hooks 生命周期钩子和可选的 bash 沙箱组成；持久化提供会话恢复与继续对话（交互模式文档、CLI 参考、设置文档）。它还支持无头模式以 JSON 流输出事件供程序消费，这让它能同时扮演人的助手和 CI 的执行器（成本与用量文档）。

值得学的是它对「打断」的处理：中断不是异常而是常态操作，正在执行的工具跑完即停、排队消息在下一个安全点注入——这些语义细节见Agent 循环设计。

Codex CLI：沙箱档位作为一等公民

OpenAI 于 2025 年 4 月开源 Codex CLI，后以 Rust 重写核心（openai/codex、CLI 文档）。它最鲜明的设计是把沙箱强度做成显式档位：read-only 只读参考、workspace-write 限定工作区写入、danger-full-access 解除网络与文件限制，再叠加独立的审批策略决定何时询问用户（沙箱文档）。这套词汇表已经成为讨论 agent 安全时的通用语言之一。

第二个贡献是指令文件的标准化：AGENTS.md 作为开放的仓库说明格式被数万个项目采纳，任何兼容的 harness 进场先读它（agents.md）。这说明「项目记忆」可以像 README 一样成为跨工具契约——具体写法属于兄弟 hub 的主题，本 hub 关注的是 harness 如何加载与注入这份契约。

OpenHands 与 Aider：两条开源路线

OpenHands（前身 OpenDevin）代表「平台化」路线：所有交互被统一为事件流上的条目——动作、观测、消息、状态变更——agent 循环只是事件的消费者与生产者，运行时跑在 Docker 隔离的沙箱里，支持浏览器操作与多 agent 委派（arXiv 2407.16741、OpenHands 文档）。事件流架构让「发生了什么」天然可审计、可回放，也为第三方 UI 和评估器提供了统一挂点，这层设计的展开见事件流与可观测 UI。

Aider 代表「最小信任面」路线：不追求全自主，而是人机交替的结对节奏；每次修改自动生成规范的 git 提交，出问题直接 revert；跨文件编辑靠 tree-sitter 抽取符号依赖图再做排序的仓库地图来定位上下文（aider.chat、Aider-AI/aider、常见问题见其 FAQ）。它证明了一个重要命题：harness 的安全下限可以由「版本控制系统即回滚机制」兜底，而不必依赖复杂的运行时隔离。

Devin 与云端托管形态

Devin 在 2024 年 3 月发布时给出了另一种回答：把整个开发环境搬进云端虚拟机，shell、编辑器、浏览器齐备，用户只面对一个任务队列与会话界面（Cognition，introducing-devin）。托管形态的优势是隔离天然彻底、长时任务不怕本地断电、并行多会话成本低；代价是调试半径变长——你看到的永远是屏幕录像式的转述而非本机现场。云壳与本机壳的选择本质是在「环境保真度」与「爆炸半径控制」之间定价。

解剖之外的第四个维度：扩展机制

六子系统之外，区分 harness 成熟度的还有一条暗线：用户能不能在不改源码的情况下改变它的行为。Claude Code 的答案是三层扩展——hooks 在工具调用的生命周期上暴露确定性挂点（团队用它强制执行「提交前必须跑 lint」这类铁律），斜杠命令与技能文件把常用流程封装成可分发的包，MCP 则把外部系统能力接进工具面（settings 文档）。Codex CLI 走配置文件路线：config.toml 定义模型、审批与沙箱偏好，自定义提示词沉淀为可复用的指令集（openai/codex）。

扩展机制之所以是暗线而非明面，因为它决定了 harness 是「产品」还是「平台」。没有 hooks 的外壳只能被使用，有 hooks 的外壳能被治理——企业落地时前者会卡在合规评审上。评估任何新 harness 时，建议把这张检查单加进解剖流程：能否注入确定性行为（hooks）、能否封装领域流程（命令与技能）、能否外接工具生态（协议支持）、以及这三者的配置是否随仓库版本化管理而不是散落在个人机器上。

提炼设计坐标：自治度 × 信任半径

把五个样本放进同一个坐标系：横轴是单次授权后的自治跨度，纵轴是一次失误的最大影响范围。用一个小模型刻画审批摩擦的代价：设每步需要人工审批的概率为 qqq、平均等待时长 τ\tauτ、纯执行期望 tet_ete​，则 nnn 步任务的墙钟期望为

E[T]=n⋅(te+q⋅τ)E[T] = n \cdot (t_e + q \cdot \tau)E[T]=n⋅(te​+q⋅τ)

当 τ\tauτ 达到分钟级时，把 qqq 从 1 压到 0.1 就能把总等待压缩约九成——这正是各家用沙箱档位换取审批频率的量化动因。但压低 qqq 同时放大纵轴的信任半径，于是真正的设计自由度只剩一个：用什么机制让低 qqq 与小半径并存。Claude Code 的答案是 hooks 加细粒度允许清单，Codex 的答案是强沙箱兜底下的宽松审批，Aider 的答案是 git 兜底下的最小自动执行。你的 harness 也必须给出自己的组合，具体分层技术见权限与安全分层。

小结

  • 五个标本覆盖终端、平台、云端三种形态，六子系统的解法各不相同。
  • Claude Code 示范打断与恢复语义，Codex CLI 把沙箱做成显式档位。
  • OpenHands 的事件流架构服务于可审计性，Aider 用 git 兜底最小化信任面。
  • 设计自由度的核心是让低审批频率与小爆炸半径并存。
