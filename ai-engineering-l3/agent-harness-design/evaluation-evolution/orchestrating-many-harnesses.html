编排多个 harness

「一个 harness 通吃所有任务」的假设，在任务谱系变宽的那一刻就会裂开：检索型研究要宽而浅的并行探索，实现型编码要窄而深的连续上下文，评审型工作要独立的第二意见。当单线会话的历史开始互相污染、当串行等待让墙钟时间不可接受，你就站在了多 harness 编排的门口。这一篇讨论的不是多 agent 算法——那是文献的富矿——而是工程问题：几个外壳怎么连接、共享什么、隔离什么、以及失败时怎么兜底。

核心概念：四个触发信号

先确认真的需要多个 harness。下面四个信号出现任意两个，才值得支付编排的成本；只中一个时，更好的答案通常是改进单个外壳。

触发信号 具体表现 更便宜的单机替代
任务谱系异构 检索、实现、验证所需工具面完全不同 单壳内换工具集
上下文互斥 子任务细节会污染主线决策 压缩与文件外部化
墙钟不可接受 关键路径上全是串行等待 工具并发与流水线化
需要独立意见 自查无法发现自己的盲区 显式的评审轮提示

第三列值得反复看：多数「我们上了多 agent」的项目，回头看都是这四列右边的方案更便宜。Anthropic 在复盘其研究系统时给出的数据同时说明了收益与代价——编排者加并行子代理的结构把多维度研究请求的耗时削减了九成（90.2%），但多代理系统消耗的 token 约为普通对话的十五倍（Anthropic，2025 年 6 月，built-multi-agent-research-system）。用十五倍的 token 买九成的时间，只在时间真正值钱的场景成立。

四种拓扑及其失效模式

flowchart TD
    U[用户] --> O[主 harness 编排者]
    O --> S1[子 harness 探索]
    O --> S2[子 harness 实现]
    O --> S3[子 harness 核验]
    S1 -- 结论摘要 --> O
    S2 -- 补丁与测试结果 --> O
    S3 -- 审查报告 --> O
    O --> F[汇总交付]

层级如上图：编排者分解任务、派发子代理、回收摘要。它适合可分解且子任务间弱耦合的工作，失效模式是编排者成为信息瓶颈——摘要压太狠丢关键细节，不压则瓶颈退化成新的长上下文。流水线把各 harness 按阶段串联，上游产物是下游输入，适合阶段边界清晰的生成-检查-修复流程，失效模式是误差沿管道放大且尾部延迟等于各段之和。集成让多个配置独立解同一题再择优或表决，失效模式是成本线性翻倍且依赖验收器的公正性。蜂群让对等节点自由协作，工程上最少被采纳：无中心协调使上下文一致性几乎不可维护。

拓扑 时延 token 成本 主要失效模式
层级 并行后收敛 高（约一个量级） 编排者信息瓶颈
流水线 各段串行相加 中 误差级联、尾段排队
集成 最慢路径 最高（线性于样本数） 裁决器偏差
蜂群 不确定 不可控 上下文漂移与冲突编辑

Cognition 从相反立场给出的提醒同样值得刻在墙上：多代理的每个行动都携带隐含决策，两个代理在同一份代码上做出相互冲突的隐含决策时，合并的结果比任何单方都糟；他们的实践原则是优先共享完整上下文的单线程 agent，把子任务交给同一上下文里的顺序推进而非平行世界（Cognition，2025 年 6 月，dont-build-multi-agents）。两条路线并不矛盾——分歧的本质是子任务间的耦合度：耦合高则共享上下文，耦合低才值得物理隔离。

集成与表决：给不确定性定价

best-of-n 是最诚实的编排：承认单次运行有随机性，用重复采样换取覆盖面。覆盖率随样本数上升而饱和的规律已被系统测量——重复采样能把单次解决率不到两成的模型在数百次采样后推到五成以上的覆盖（arXiv 2407.21787）。它的两个前提要写进设计文档：一是验收器必须独立于生成过程，否则只是自欺；二是成本预算要显式，nnn 个样本的成本就是单件的

C(n)=n⋅cC(n) = n \cdot cC(n)=n⋅c

没有饱和。若改用多数表决，nnn 个独立样本、单件正确率 p>12p > \tfrac{1}{2}p>21​ 时，表决正确的概率为

Pmaj(n)=∑k=⌈n/2⌉n(nk) pk (1−p)n−kP_{\text{maj}}(n) = \sum_{k=\lceil n/2 \rceil}^{n} \binom{n}{k}\, p^k\, (1-p)^{n-k}Pmaj​(n)=k=⌈n/2⌉∑n​(kn​)pk(1−p)n−k

随 nnn 单调爬升——但前提「独立」在实践中很脆：同源模型的相关错误会让实际增益远低于公式预测。表决因此更适合异构配置的组合（不同模型或不同脚手架），而不是同一配置的自我重复。

失败域与降级预案

多 harness 系统的故障面是各子系统的并集，设计时就要为每类失败预设降级路径。子代理超时或崩溃：编排者应给每次派发设定时限与重试上限，耗尽后接受部分结果并在汇总中显式标注缺口——「检索子任务失败，以下结论缺少文献支撑」远好于静默拼凑。产出质量不齐：每个子 harness 的交付要过与主链路相同的验收器，不合格就重派或降级，而不是把问题留给最终汇总层。编排者自身故障：层级拓扑的单点在编排者，长任务的派发状态要进检查点（见Agent 循环设计的恢复语义），崩溃后能按已完成的子任务续跑而非全部重来。最后一条纪律来自分布式系统的老经验：隔离失败域——并行写同一工作区的子任务之间必须有工作区级的隔离（git worktree 允许同一仓库挂载多个独立目录各自提交再汇合，git-scm.com/docs/git-worktree），让一个子任务的爆炸半径止步于它自己的目录。

共享底座：协议、契约与工作区

多 harness 能否低成本共存，取决于三件共享设施。第一是工具协议：MCP 让同一个 server 同时服务多个外壳，工具集不必为每个 harness 重写一遍，这是多壳并存的基础设施前提（modelcontextprotocol.io）。第二是指令契约：仓库根部的 AGENTS.md 类说明文件对所有进入的外壳一视同仁地生效，行为约束写在仓库里而不是散落在各家的启动参数里（agents.md）。第三是工作区隔离：并行的实现类 harness 不该共写一个工作树——git 的 worktree 机制允许同一仓库挂载多个独立目录，各自提交再汇合，冲突在合并层显式暴露而不是在文件层静默覆盖。三件设施的共同精神是把协调从「运行时的默契」搬到「结构化的接口」，这与第一章的分界论证一脉相承：能固化的判断不要留给临场发挥。

编排层的可观测性最后兜底：每个子 harness 的成本曲线、干预密度与产出验收率都要回到统一的事件总线（见事件流与可观测 UI），否则多壳系统的第一次故障排查就要靠考古。至于拓扑选择本身如何随模型能力漂移而变化——去年需要三个子代理的任务今年一个就够——正是下一章的主题。

小结

  • 先对照四个触发信号与更便宜的替代品，再决定引入多 harness。
  • 层级换时间但费 token，流水线防不了级联，集成的命门在验收器。
  • 表决要求独立性，异构配置优于同配置自我重复。
  • MCP、说明文件契约与 worktree 隔离是多壳共存的三块地基。
