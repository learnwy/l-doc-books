Part II · Agent ConstructionAgent Harness 设计第二章 · 核心回路权限与安全分层

权限与安全分层

agent 的权限设计与传统应用鉴权有一个本质差异：发起操作的「用户」本身可能被骗。模型读到的每一份网页、每一个仓库文件、每一条工具结果都可能藏着针对它的指令——OWASP 把提示注入列为大模型应用风险清单的第一位，且连续两版都居首不落（OWASP GenAI LLM Top 10）。因此单点防护（弹一个确认框）注定不够，成熟 harness 一律采用纵深分层：任何一层失守，下一层仍在。审批闸门并非独立系统，它就嵌在Agent 循环设计：步进、中断与恢复所定义的步进状态机里——「待审批」是循环的一个常态状态，而不是异常分支。

核心概念：四层防线的分工

层 拦截对象 典型机制 残余风险
模型层 显性的恶意或越界请求 安全训练、系统级行为约束 精心构造的注入可绕过
harness 层 单次危险工具调用 审批模式、允许/拒绝清单、生命周期钩子 规则配置失误
沙箱层 已放行动作的爆炸半径 文件系统与网络隔离、容器边界 极罕见的逃逸
组织层 凭证与账号滥用 最小权限凭证、审计日志、密钥管理 合规内的误用

四层的拦截时机依次靠后，成本也依次升高——在模型层拦住是免费的，到沙箱层才拦住意味着一次真实执行的资源已消耗。设计的艺术在于让危险意图尽量在前层终结：

flowchart TD
    REQ[模型发出工具调用] --> A{harness 策略匹配}
    A -->|命中拒绝规则| DEN[直接驳回并告知理由]
    A -->|需人工审批| ASK[向用户弹出请求]
    ASK -->|拒绝| DEN
    ASK -->|允许| B{沙箱可用}
    A -->|免审白名单| B
    B -->|是| SAN[在隔离环境中执行]
    B -->|否| RAW[宿主机直接执行]
    SAN --> OBS[输出作为观测返回]
    RAW --> OBS

若各层被独立突破的概率分别为 p1,…,pnp_1, \ldots, p_np1​,…,pn​ 且近似相互独立，则整体被击穿概率为

P(breach)=∏i=1npiP(\text{breach}) = \prod_{i=1}^{n} p_iP(breach)=i=1∏n​pi​

取 p1=0.3p_1=0.3p1​=0.3、p2=0.2p_2=0.2p2​=0.2、p3=0.1p_3=0.1p3​=0.1 三层叠加得 0.0060.0060.006——比任何单层都低一个量级。这个乘法结构也解释了为什么「模型越来越安全」并不能取消后面几层：每层的 pip_ipi​ 都只能压低，无法归零。

威胁模型：致命三要素

Simon Willison 概括的「致命三要素」给出了判断暴露面的最简公式：当系统同时具备访问私密数据、接触不可信内容、拥有对外发送的通道三者时，数据外泄链条即告闭合——agent 场景几乎天然凑齐三样（The Lethal Trifecta）。一个典型链路：agent 被要求阅读一份含恶意指令的网页或 issue，指令诱导它把环境变量里的密钥写进看似正常的构建输出并推送到远端。防御要点因此不是「识别恶意页面」——那做不到——而是切断三要素中任意一条：给网络出口设白名单、把密钥移出可达范围、对「读后写外」的组合强制人工审批。

工具描述本身也是注入面：模型高度信任工具元数据里的文字，第三方 MCP server 的描述字段可以携带操纵性内容。接入外部工具时的信任评估属于选型侧的功课，harness 侧的对策是把来源不明的工具默认降级为需审批。

harness 层：审批模式与策略引擎

这一层是产品差异最集中的地方。Claude Code 提供多档权限模式加细粒度的允许/拒绝规则（按工具与参数模式匹配），并在工具调用的前后暴露钩子，团队可以把自定义策略——比如「禁改 CI 配置」「禁止 curl 内网」——写成代码强制执行；配合可选的 bash 沙箱做文件系统与网络的二次圈禁（settings、sandboxing）。Codex CLI 则把审批拆成两个正交旋钮：沙箱强度三档（read-only / workspace-write / danger-full-access）与独立的审批策略决定何时询问用户，两者组合出「宽松询问但严格兜底」等不同姿势（codex/sandbox）。

策略引擎的设计要点有三条。其一，默认值决定下限：新会话应落在保守档位，提权动作要显式且可审计。其二，授权要有粒度语义：「本次允许」「本会话内允许」「永久写入项目配置」是三种不同的承诺，混用会让允许清单迅速腐烂。其三，拒绝要可解释：驳回信息会回到模型成为观测，一句「该操作违反项目规则 R-12」能让模型自行改道，而干巴巴的错误码只会诱发重试——这与错误恢复与重试模式中的「错误即输入」原则一脉相承。

策略即代码：规则、钩子与评审

权限策略散落在个人配置里是治理的起点性错误——十台机器十个策略，审计无从谈起。工程化做法是把策略当代码管理：允许与拒绝规则写成版本化的清单文件随仓库走，复杂判断下沉到钩子脚本，策略变更走与代码相同的评审流程。

permissions:
  deny:
    - tool: Bash
      arg_pattern: "rm\\s+-rf\\s+/"
      reason: 禁止根路径递归删除
    - tool: Edit
      path_pattern: ".github/workflows/**"
      reason: CI 配置变更需人工通道
  allow:
    - tool: Read
    - tool: Grep
  ask:
    - tool: Bash
      except_arg_pattern: "(git status|ls|cat) .*"

清单之上再叠一层钩子兜底：规则匹配不了语义级约束（「不得把客户名写入日志」），就由工具调用前后的钩子程序做最终裁决，钩子的判定结果同样落进审计流。策略本身也要测试——把历史事故回放成用例（那次误删、那次越权推送），断言新策略能拦住它们；这条回归集是权限层的「黄金轨迹」。评审节奏上，每次放宽都要求附带触发场景与回滚开关，每次收紧则要评估对自治度的量化影响：审批频率上升多少、任务完成率掉多少。没有这两组数字，安全讨论会退化成直觉对轰。

沙箱层与组织层：圈住半径与守住钥匙

沙箱的目标不是阻止调用发生，而是限制其后果。操作系统级的 seatbelt 类机制可以精确到「允许写哪些目录、能否出网」，容器与云虚拟机则提供整机隔离——OpenHands 给每个会话配 Docker 运行时（arXiv 2407.16741），Devin 干脆把整个开发环境搬进云端虚拟机（introducing-devin）。选择强度时的量化直觉：沙箱带来的摩擦约等于每次越界操作的额外延迟，而它买回的是 p3p_3p3​ 数量级的直降，对高权限环境几乎总是划算。

组织层常被个人开发者忽略，却在团队落地时第一个爆雷。三条最低配置：agent 使用的凭证一律是最小权限的机器账号而非个人令牌；所有审批决定与工具调用进审计日志，事后能回答「谁在何时允许了那条删除」；无头模式跑进 CI 时，密钥经由短时效的秘密管理注入，而不是躺在环境变量里陪跑全程。这些措施不依赖任何一层的完美性，恰恰是纵深防御的最后一张网。

小结

  • 提示注入使「内容即指令」成为默认假设，单点防护必然失效。
  • 四层防线按拦截时机排序：模型、harness、沙箱、组织，击穿概率相乘。
  • 用致命三要素自查暴露面：私数据 × 不可信内容 × 外发通道。
  • 授权要区分粒度语义，拒绝消息要让模型能据此改道。
