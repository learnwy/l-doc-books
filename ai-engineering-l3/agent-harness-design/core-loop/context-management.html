Harness 内的上下文管理

agent 的每一步都要重新回答一个问题：这一轮把哪些字节塞进窗口。回答得差，轻则账单失控，重则模型「忘」了三步前刚踩过的坑。上下文管理与普通应用的内存管理不同——它同时受三种物理约束挤压：窗口容量有限、注意力随长度稀释、以及处理成本随历史超线性增长。harness 的上下文装配器就是在这三条边上跳舞的调度器。

核心概念：三种约束各自怎么疼

容量是显式的：任何一轮的输入超过上限就直接报错。但真正的天花板往往在容量之前就到——注意力稀释。Liu 等人的实验显示模型对长文档中间位置信息的召回显著弱于首尾，性能随位置呈 U 形（arXiv 2307.03172）；Chroma 的后续研究进一步发现，即便任务在短上下文下几乎必对，性能也随输入变长而普遍退化，且这种「上下文腐烂」横跨被测的十余个模型（arXiv 2507.13333）。第三重约束是经济：Manus 团队复盘时给出的结论相当直白——KV 缓存命中率是决定 agent 成本与时延的最重要单一指标，因为每个 token 的处理开销都随需缓存的序列长度增长（Context Engineering for AI Agents: Lessons from Building Manus）。

约束 失效表现 对应策略
容量上限 请求 400 报错、硬截断 压缩、外部化
注意力稀释 中段指令被忽略、目标漂移 关键内容置首尾、结构化锚点
成本超线性 第 40 轮比第 4 轮贵一个量级 缓存友好布局、及时裁剪

装配管线：每一轮的拼装顺序

harness 每轮发送的不是一条消息而是一份精心排序的文档。典型管线如下：

flowchart LR
    SYS[系统提示] --> ASM[上下文装配器]
    PRJ[项目记忆文件] --> ASM
    HIST[对话与动作历史] --> ASM
    OBS[最新工具观测] --> ASM
    JIT[按需检索片段] --> ASM
    ASM --> OUT[发往模型的有效载荷]

顺序即优先级。系统提示与项目记忆文件占据开头——它们定义行为契约，必须落在注意力最强的区域；历史按时间排布在中段；最新的工具观测贴近末尾；按需检索的片段插在与问题最相关的位置而非一律追加。Claude Code 把 CLAUDE.md 的层级合并（企业、用户、项目三级）做成了装配器的标准输入之一（settings 文档）。装配器还应负责裁剪：单条工具结果超过配额时截断并标注省略标记，让模型知道世界被折叠了而不是以为看见了全部——这个细节与工具接口的设计直接联动（见工具接口在 harness 中的设计）。

压缩与外部化：窗口满了之后的两条路

压缩（compaction）指用摘要替换旧历史后继续会话。触发时机有两种：手动命令（如 /compact）与自动阈值——接近窗口上限时 harness 自动发起摘要再续跑，Claude Code 两者都提供（CLI 参考）。好的压缩不是无差别总结，而是保留「活状态」：当前目标、已完成的里程碑、悬而未决的错误、用户给过的硬约束。丢弃的应是过程性的大段工具输出——反正文件系统里还有原文。

外部化则更进一步：把状态写进环境本身，让窗口只装指针。Manus 的经验是把 todo 清单做成持续改写的 markdown 文件，每轮结尾复述一遍目标以对抗长程漂移；文件系统被当作「最终的上下文」，需要时再读回，而不是永远占着窗口（Manus 博客）。Anthropic 的上下文工程指南把同类手法归纳为结构化笔记与按需检索：与其预载一切，不如保证「要的时候拿得到」（effective-context-engineering）。

隔离：子代理作为上下文防火墙

当单线历史注定膨胀，第三条路是把工作切成互不污染的多条线。Anthropic 的多 agent 研究系统中，主 agent 只保留任务分解与各子代理的结论摘要，每个子代理在全新上下文里并行深挖，最终由主 agent 汇总——子代理的脏细节从不进入主线（Anthropic，2025 年 6 月，built-multi-agent-research-system）。这本质是用进程隔离换注意力纯净度，代价是 token 总量放大与结果一致性风险，边界条件在编排一章展开（见编排多个 harness）。

成本模型：为什么必须主动管理

设第 iii 轮新增 Δ\DeltaΔ 个 token 的历史增量，若从不裁剪，累计处理的 token 数为

T(k)=∑i=1ki⋅Δ=Δ⋅k⋅(k+1)2T(k) = \sum_{i=1}^{k} i \cdot \Delta = \frac{\Delta \cdot k \cdot (k+1)}{2}T(k)=i=1∑k​i⋅Δ=2Δ⋅k⋅(k+1)​

增长是二次的：第 60 轮的处理量相当于第 20 轮的九倍。压缩把上式封顶在窗口规模附近，代价是每次压缩引入一次信息损失与一段延迟。缓存的经济学进一步改变取舍：只要前缀保持稳定，命中缓存部分的读取单价远低于全价——这正是「追加优于改写」原则的来源，中途编辑历史会让缓存整段失效（Manus 博客）。于是装配器的一条纪律浮现：稳定的东西放前面且永不改动，易变的东西放最后。

一张实用的预算起点表（按 200K 窗口、编码类任务校准）：

区块 预算占比 说明
系统提示 + 项目记忆 约 10% 尽量恒定以保缓存命中
历史（含压缩点） 约 55% 超限即触发自动压缩
当前回合观测 约 25% 单条超限先截断
余量与输出预留 约 10% 保证最后一轮完整收尾

压缩的质量检查：摘要是会丢信息的

压缩最大的工程风险不在触发时机而在静默的信息损失：摘要把三小时前的关键约束「用户要求所有日期用 ISO 格式」折叠成一行小字甚至丢掉，模型在第十轮开始用错格式，没人知道为什么。因此生产级压缩必须带质量闸。做法一：锚点清单——装配器维护一份不可压缩的关键事实表（硬约束、凭证位置、已否决的方案），每次压缩后原样重注，摘要只负责过程性内容。做法二：压缩后自检——让模型对摘要回答三个问题（当前目标是什么、哪些约束必须遵守、下一步做什么），答案与压缩前状态不符则回退用更保守的策略重新压缩。做法三：审计留痕——每次压缩事件记录前后 token 数、被丢弃的消息范围，出问题时能定位「哪次压缩吃掉了关键信息」。

大块观测的处理是同一问题的日常形态：单条工具结果超配额时，截断策略应保留头部结构加尾部错误信息（错误几乎总在末尾），中段折叠并显式标注省略量；连续多轮读同一个大文件时，装配器可以缓存上次的截断视图并只追加变更区间，避免每轮重复支付同样的窗口税。

观测驱动的调优：给装配器装仪表

上下文策略不能靠感觉调，需要三个常驻指标。分区占用曲线：系统提示、历史、观测、余量四区的实时占比——它能在请求失败前很多轮就预告「历史区还有六轮到顶」。缓存命中率：前缀稳定性直接决定成本曲线，命中率突然下跌通常意味着某处代码开始改写历史或轮换了系统提示。压缩频率与损失审计：每小时压缩几次、每次丢弃多少字节、自检是否通过——频率过高说明单轮增量过大，该治的是工具返回值而不是压缩器。

这三个指标接进第四章的事件流管道后，上下文管理就从玄学变成有仪表盘的常规工程。调优的典型路径也由此固定：先看分区占用找结构性浪费（通常是某个工具倾倒原始日志），再修工具接口的裁剪，最后才动压缩参数——顺序反了会在错误的层做优化。

小结

  • 三重约束：容量有限、注意力稀释、成本随历史平方增长。
  • 装配顺序即优先级，稳定前缀保缓存，易变内容靠尾部。
  • 压缩保活状态，外部化把窗口换成文件系统指针。
  • 子代理隔离用 token 放大换注意力纯净，适合可分解的宽任务。
