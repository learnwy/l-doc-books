评测集版本化

核心概念

评测集不是一次性产物，而是持续演进的工件。把评测集放进 Git、有变更日志、有基线快照、有发布流程，让评测能力随产品共同成长——这是评测集版本化的核心实践。本节讲解评测集版本化的工程方法：Git 管理、语义版本号、基线快照、A/B 标签、回滚预案。

Git 管理评测集
把评测集纳入 Git 是版本化的最低门槛。常见的存储结构：


evals/
  v1/
    samples.jsonl           # 样本主文件
    metadata.json           # 评测集元数据
    rubric.md               # 评分规范
    baseline-scores.json    # 基线分数
    CHANGELOG.md            # 变更日志
  v2/
    ...
每条样本的标准结构：


    

  • id: 唯一标识符
    • 

  • input: 输入
    • 

  • expected_output / rubric_answer: 期望输出或评分依据
    • 

  • tags: 分类标签（场景、难度、来源等）
    • 

  • created_at / updated_at: 时间戳
    • 

  • annotators: 标注员 ID
    • 

  • consensus_score: 共识分数
    • 



Git 管理让每次变更可追溯、可审查、可回滚。新增样本、修订 rubric、淘汰过时样本都走标准 PR 流程。


语义版本号
借鉴 Semantic Versioning 的思路，评测集也用三段式版本号：


    

  • MAJOR：不兼容更新（rubric 重大调整、维度变化），需要重建基线分数。
    • 

  • MINOR：新增功能（新维度、扩充样本、新标签体系），向后兼容。
    • 

  • PATCH：bug 修复（标注错误、样本格式问题），向后兼容。
    • 



版本号选择的工程经验：


    

  • 增量小改用 PATCH 即可。
    • 

  • 评测集结构性变化（新维度、新分层）用 MINOR。
    • 

  • 改动后让旧基线分数失去意义的，必须用 MAJOR。
    • 



基线快照
每个稳定版本对应一个"基线分数"——当前最优提示词/模型在该版本评测集上的分数。基线快照的作用：


    

  • 回归保护的参照：每次变更对比基线，分数下降则阻止合并。
    • 

  • 进步的可量化：每个版本的基线提升让进展可被衡量。
    • 

  • 跨版本比较：评测集升级后能与旧版本基线对比，看真实改进 vs 评测集变化。
    • 



基线管理的关键工程实践：


    

  • 每个版本都有基线：不允许"现在是 v1.6 但还在用 v1.4 的基线"。
    • 

  • 基线包含具体配置：模型版本、提示词、RAG 索引、超参——基线分数对应具体配置而非抽象。
    • 

  • 多模型基线：用 GPT-4、Claude、Gemini 等多个模型分别跑基线，方便后续模型升级对比。
    • 



A/B 实验标签
评测集中的样本可以有多种标签，支持灵活的子集评测：


    

  • tag:happy-path：核心高频场景。
    • 

  • tag:edge-case：边界 case。
    • 

  • tag:adversarial：对抗性输入。
    • 

  • tag:critical：关键样本（绝对不允许失败）。
    • 

  • tag:experiment-X：特定实验相关的样本。
    • 



通过标签筛选，可以快速跑某个子集而不必每次跑全量。例如修复某类问题后，只跑 tag:critical + 修复相关样本，快速验证。

成熟团队通常给评测集设计正式的发布流程：

这种流程让评测集变更被严肃对待，避免"随手改了几条样本就发布"的失控。


回滚预案
评测集变更后可能发现问题——某个样本标注错了、新维度引入混乱、采样分布失衡。需要回滚预案：


    

  • 能快速切回上一稳定版本：CI 配置中记录评测集版本，切换是改一行配置。
    • 

  • 保留旧版本可用性：旧版本评测集与基线分数都保留至少 1 年。
    • 

  • 变更可追溯：每次发布有详细变更日志，问题归因有依据。
    • 



多团队协作
大公司中评测集可能跨团队共享。版本化让协作更可控：


    

  • 核心评测集：由专门团队维护，作为公司级标准。
    • 

  • 业务专属评测集：各业务线在核心基础上扩充，独立版本管理。
    • 

  • 联合评测：跨团队联合评测时明确使用哪个版本。
    • 

  • 变更通知：核心评测集变更通过邮件、Slack 通告所有依赖团队。
    • 



评测集元数据
每个版本评测集应该有完整的元数据：


    

  • 创建时间与作者
    • 

  • 样本规模与分层比例
    • 

  • 标注员列表与标注一致性指标
    • 

  • 依赖的工具版本（评测脚本版本、judge 模型版本）
    • 

  • 已知局限（哪些场景覆盖不足、哪些 rubric 仍模糊）
    • 



这些元数据让后续接手的人能快速理解评测集的状态与边界。


小结
评测集版本化把"散乱的样本集合"升级为"严肃的工程产物"。Git 管理、语义版本号、基线快照、A/B 标签、发布流程、回滚预案——这些工程实践让评测集成为可持续演进的资产。把评测集版本化作为 AI 产品工程化的标准要求（而不是可选附加），是从研究 demo 走向生产级 AI 产品的关键一步。一个简单的检验：如果团队此刻无法回答"我们的评测集是哪个版本？基线分数是多少？最近一次变更是什么？"——那意味着评测集还没有真正版本化，应该把这一能力作为优先建设事项。
