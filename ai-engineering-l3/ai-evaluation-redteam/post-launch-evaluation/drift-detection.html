漂移检测

核心概念

漂移（Drift）是 AI 产品上线后最隐蔽也最危险的失败模式——产品行为悄悄变差但没有明显报错信号。可能的漂移源很多：底层模型 API 升级、用户输入分布变化、外部数据源改变、依赖库升级、提示词在多次小改后累积偏差。本节系统讲解漂移的类型、检测方法、与早期预警机制，让团队能在用户大量投诉之前发现漂移。

模型漂移
最直接的漂移源是底层模型 API 的升级。OpenAI、Anthropic、Google 都会定期更新它们的模型——有些是显式版本号变化（GPT-4 → GPT-4-turbo），有些是无版本号的"silent update"。


显式升级：


    

  • 通常有提前通知期。
    • 

  • 团队应该在升级前用评测集测试新模型，决定是否切换。
    • 

  • 如果决定不切换，需要锁定到具体版本号（gpt-4-1106-preview）。
    • 



Silent Update：


    

  • 没有版本号变化但模型行为可能改变。
    • 

  • 需要持续监控固定输入的输出变化。
    • 

  • 一旦发现，立即评估影响。
    • 



模型漂移的工程预防：


    

  • 版本固定：在生产环境中始终使用具体版本号（gpt-4-1106-preview），而非别名（gpt-4）。
    • 

  • 每日基线测试：每天跑一组固定样本，比较输出的语义相似度，发现异常立即告警。
    • 

  • 多模型 A/B：在关键场景同时跑多个模型，单一模型异常时能快速切换。
    • 



输入分布漂移
用户输入的分布可能随时间变化——产品扩展到新地区、新增用户群、营销活动带来不同类型的用户。这种漂移让评测集与真实使用脱节。


检测方法：


    

  • 输入特征监控：跟踪用户输入的长度分布、话题分布、语言分布。突然变化预示用户群变化。
    • 

  • 嵌入聚类：把用户输入转化为嵌入向量，定期聚类。新聚类出现说明有新类型用户。
    • 

  • 用户分层指标：按用户群（新用户、活跃用户、付费用户）分别跟踪质量指标，识别哪个群体出现问题。
    • 



应对方法：


    

  • 评测集更新：发现新的用户群后，从他们的输入中采样补充评测集。
    • 

  • 场景特定优化：对新场景做针对性优化（提示词、RAG 索引）。
    • 

  • 及时通信：通知产品、运营团队用户群变化，调整产品策略。
    • 



数据漂移
对依赖 RAG（检索增强生成）的产品，索引中的文档可能在持续变化——新文档加入、旧文档过时、内部规章修订。这种漂移可能让回答基于过时信息。


检测方法：


    

  • 索引快照对比：定期对比索引快照，识别哪些文档变化、新增、删除。
    • 

  • 回答时效性检查：让 Judge LLM 评估"回答是否反映了最新文档"。
    • 

  • 关键事实回归：维护一组"应该有特定答案"的关键问题，定期跑看回答是否稳定。
    • 



应对方法：


    

  • 文档版本化：在 RAG 索引中保留文档版本号与时间戳，让模型能引用具体版本。
    • 

  • 过期内容标记：超过一定时间未更新的文档显式标记，让模型谨慎使用。
    • 

  • 增量更新检验：每次索引更新后跑回归评测，确认未引入回答漂移。
    • 



依赖漂移
第三方库（LangChain、LlamaIndex、提供商 SDK）的升级可能改变行为：


    

  • LangChain 2.0 的 API 与 1.0 有显著差异。
    • 

  • OpenAI Python SDK 默认参数可能变化。
    • 

  • 嵌入模型库的归一化逻辑可能调整。
    • 



依赖漂移的工程预防：


    

  • 版本锁定：requirements.txt 锁定到具体版本（openai==1.30.0），避免意外升级。
    • 

  • 依赖更新流程：升级第三方库通过专门 PR，跑完整评测集验证。
    • 

  • 变更日志审查：每次升级前阅读 changelog，识别可能影响行为的变化。
    • 



提示词漂移
大团队中多人持续小改提示词，累积可能让提示词偏离原本意图。这种漂移最隐蔽——每次单独看都"合理"，整体看才发现严重偏差。


检测方法：


    

  • Git 历史审查：定期回顾提示词的变更历史，看累积改动是否符合预期。
    • 

  • A/B 实验对比：把当前提示词与 N 月前的旧版本对比，看哪个在评测集上更好。
    • 

  • 元评测：让 LLM 评估"当前提示词是否仍然清晰、一致、符合产品定位"。
    • 



应对方法：


    

  • 提示词审查会：每月召开提示词审查会，所有重要提示词共同审视。
    • 

  • 提示词版本化：每次重要变更打 tag，便于回滚。
    • 

  • 提示词所有权：每个提示词有明确的负责人，重大变更需要 review。
    • 



漂移监控仪表盘
把漂移检测做成专门的监控仪表盘，关键面板：


每个面板：


    

  • 当前值：今日/本周指标。
    • 

  • 历史趋势：过去 30 天的曲线图。
    • 

  • 基线对比：与基线对比的偏离度。
    • 

  • 异常告警：偏离超过阈值时触发的告警。
    • 



这个仪表盘应该被产品、研发、SRE 团队共享，作为日常 standup 的标准议题。


早期预警系统
把漂移检测从被动监控升级为主动预警：


    

  • 多指标关联：单一指标变化可能是噪声，多指标同时变化说明真实漂移。
    • 

  • 趋势告警：连续 3-7 天指标恶化触发告警，避免单日波动误报。
    • 

  • 分层告警：轻微漂移给团队邮件，严重漂移直接 PagerDuty。
    • 

  • 可解释告警：告警包含上下文信息（哪个指标、变化多少、可能原因），方便快速判断。
    • 



漂移的根因分析
发现漂移后的根因分析流程：


    

  1. 时间定位：漂移发生在哪个具体时间点？精确到小时。
    2. 

  2. 变更对照：那个时间点附近有哪些变更（代码部署、模型升级、索引更新）？
    3. 

  3. 样本归类：失败样本集中在哪类场景？这指向变更的影响范围。
    4. 

  4. A/B 验证：怀疑是某个变更导致时，A/B 切换确认。
    5. 

  5. 修复或回滚：能修复就修复，不能就回滚。
    6. 



清晰的根因分析流程能让漂移修复时间从数天降到数小时。


小结
漂移是 AI 产品上线后最隐蔽的失败模式。从模型漂移、输入分布漂移、数据漂移、依赖漂移到提示词漂移——多种漂移类型需要不同的检测方法。把漂移检测做成主动的监控仪表盘 + 早期预警系统（而非被动等待用户投诉），是 AI 产品长期稳定运营的关键能力。在工程实践上，把"漂移检测"作为 SRE 的标准职责（与可用性监控同等地位），能让产品在悄悄变差时被及时发现并修复。一个简单的检验：团队此刻能否回答"过去一个月模型的关键指标是否漂移？如果漂移了，是哪个变更导致的？"——能回答说明漂移检测体系成熟，不能回答说明还有提升空间。
