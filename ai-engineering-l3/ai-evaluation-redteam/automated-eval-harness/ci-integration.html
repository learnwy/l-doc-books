评测与 CI 集成

核心概念

把评测嵌入到持续集成流水线（CI）是 AI 产品工程化的关键里程碑。每次提示词、模型、RAG 索引、工具定义的变更都自动触发评测，分数下降时阻止合并——这种"评测即 CI"的实践把 AI 产品的演进从"凭直觉冒险"升级为"有指标护栏"。本节讲解如何在工程上落地评测与 CI 的集成，包括流水线设计、阻塞策略、成本控制、与传统 CI 的整合。

流水线设计
评测 CI 流水线通常分为多层，每层有不同的速度与覆盖度：


1. 即时反馈层（< 1 分钟）：


    

  • 提示词语法检查（变量插值、JSON Schema、特殊 token）。
    • 

  • 简单的格式与配置验证。
    • 

  • 静态分析（提示词长度、敏感词检查）。
    • 



2. 快速回归层（1-10 分钟）：


    

  • 20-50 条核心场景的"smoke test"。
    • 

  • 用快速模型（GPT-4o-mini）做评测，速度优先。
    • 

  • 主要目的是过滤掉明显的破坏性改动。
    • 



3. 完整评测层（10-60 分钟）：


    

  • 跑全部 100-1000 条评测集。
    • 

  • 用主模型（GPT-4 / Claude Opus）做 LLM-as-Judge。
    • 

  • 输出详细评分报告，是合并前的主要质量门。
    • 



4. 大规模评测层（1-3 小时）：


    

  • 跑数千条边界 case + 安全样本。
    • 

  • 通常异步运行，不阻塞 PR 但合并到主分支后必须运行。
    • 

  • 失败触发告警与回滚。
    • 



阻塞策略
不是所有评测失败都应该阻止合并。合理的阻塞策略：


强制阻塞：


    

  • 关键样本失败（"绝对不能错"的核心场景）。
    • 

  • 安全评测失败（越狱、prompt 注入成功）。
    • 

  • 总分下降超过阈值（例如 2 分）。
    • 

  • 任何维度低于绝对阈值（例如正确性 < 80）。
    • 



告警但不阻塞：


    

  • 单个非关键样本失败。
    • 

  • 总分轻微下降（< 1 分）。
    • 

  • 大规模评测层的失败（合并后再处理）。
    • 



忽略：


    

  • 已知不稳定的样本（标记为 flaky）。
    • 

  • 与本次变更无关的偶发波动。
    • 



阻塞策略的关键是"信号-噪声比"——过严阻塞让所有 PR 都被卡住，过松又起不到防护作用。需要根据实际情况持续调整。


增量评测
完整跑所有评测集的成本可能不可承受。增量评测让 CI 只跑"受影响"的样本：


    

  • 受影响样本识别：根据本次变更（修改了哪个提示词模板、哪个 RAG 索引）确定可能受影响的样本子集。
    • 

  • 依赖跟踪：维护"提示词 → 评测样本"的依赖图，变更某个提示词只跑相关样本。
    • 

  • 缓存复用：未变更部分的评测结果直接从缓存复用。
    • 



增量评测能把单次 CI 的成本降低 80-90%，让快速 CI 真正快速。

在每个 PR 的 CI 配置中明确"成本预算上限"——如果 CI 估算成本超过 $X，先要求人工 review 才能跑全量。这种保护避免了意外 API 账单爆炸。


与传统 CI 的整合
评测 CI 不应该独立于传统 CI，而应该作为同一流水线的不同阶段：


整合的工程实践：


    

  • 统一状态检查：传统 CI 和 AI CI 的结果合并在 PR 的 status check 中显示。
    • 

  • 共享流水线工具：用同一套 CI 工具（GitHub Actions、GitLab CI、Jenkins）。
    • 

  • 共同审查：开发、产品、安全团队都关注同一个 PR 状态。
    • 

  • 统一告警：CI 失败、AI 评测失败都通过同一渠道通知。
    • 



报告与可视化
评测 CI 的输出需要清晰的报告：


    

  • PR 评论：在 PR 上自动评论评测结果摘要——总分、维度分、失败样本数、与基线对比。
    • 

  • 完整报告页面：链接到详细报告页面，能浏览每个失败样本、查看具体输出。
    • 

  • 趋势看板：跟踪历史评测分数，可视化产品质量趋势。
    • 

  • 告警与通知：失败时触发 Slack/邮件/PagerDuty 通知相关人员。
    • 



清晰的报告让评测结果对团队真正可用，而不只是 CI 中绿色或红色的小图标。


常见陷阱
评测 CI 集成中的常见陷阱：


Flaky 测试：评测结果在不同次运行中波动，让 CI 偶尔失败但实际无问题。规避：增加重试、使用 temperature=0、对持续 flaky 的样本做特殊标记。


过严阻塞：每个 PR 都被卡，开发效率下降。规避：阈值合理化、人工 override 机制。


评测漂移：评测集本身在演进，让历史比较失去意义。规避：评测集版本化（见上一章）、用稳定基线长期跟踪。


只看总分：总分稳定但某些维度悄悄退化。规避：分维度跟踪、关键 case 单独保护。


小结
评测与 CI 的集成是 AI 产品工程化最重要的实践之一。它把"凭直觉的提示词改动"升级为"有指标护栏的工程实验"，让团队的迭代速度与质量同时提升。多层流水线设计（即时-快速-完整-大规模）、合理的阻塞策略、增量评测与成本控制、清晰的报告与可视化——这些工程实践让评测 CI 真正发挥作用。一个团队是否真正"工程化"了 AI 产品，就看它的评测 CI 是否在每个 PR 上稳定运行。把"评测即 CI"作为 AI 产品成熟度的核心指标，是 AI 产品研发流程升级的标志。
