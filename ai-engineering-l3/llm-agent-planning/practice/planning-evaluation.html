Part II · Agent Construction智能体规划与任务分解实践规划评测

规划评测

一个智能体在 demo 里把"订机票加日历"跑通了，能不能上线？光看这一次成功远远不够——你需要知道它在一百次不同任务上成功几次、过程是否走了冤枉路、失败时是怎么败的。规划评测就是回答这些问题的方法学。它最反直觉的一课是：一次成功只能证明一条轨迹可行，不能证明系统稳定、经济或安全。

核心概念

规划评测要同时回答两类问题：结果对不对（outcome） 与 过程好不好（process）。

  • 结果评估：任务最终是否达成目标。客观、易自动化，但只看终点、看不出过程是否绕路。
  • 过程评估：规划路径是否合理——步数是否最优、是否有无效循环、子目标分解是否得当。信息更丰富，但难自动化（需要一个可靠的"裁判"判断"这步该不该走"）。

静态任务完成分数无法同时刻画可靠性、成本效率、安全性与长程能力。下表是规划评测的核心维度清单：

维度 度量什么 典型指标
成功率 任务是否达成 pass^1、终态正确率
效率 用了多少步/token/钱 平均步数、token 成本
可靠性 多次运行的稳定性 pass^k、方差
过程质量 路径是否合理 无效循环率、最优步数比
安全性 有无危险动作 违规动作率

pass@k 与 pass^k：先定义你在奖励可能性还是稳定性

规划评测最重要、也最容易搞混的两个指标是 pass@k 和 pass^k——符号几乎一样，含义却相反。

  • pass@k：同一任务跑 kkk 次，至少一次成功就算过。它衡量"有没有可能做对"，是个乐观指标。
  • pass^k（有时写作 pass-hat-k）：同一任务跑 kkk 次，每一次都成功才算过。它衡量"能不能稳定做对"，是个悲观但更贴近生产的指标。

两者关系是：设单次成功率 ppp、各次独立，则

pass@k=1−(1−p)k,pass^ k=pk\text{pass@}k = 1 - (1-p)^k,\qquad \text{pass}\hat{}\,k = p^kpass@k=1−(1−p)k,pass^k=pk

kkk 增大时，pass@k 趋近 1，pass^k 趋近 0。选择哪个指标取决于产品契约：允许离线生成多个候选再选最好结果时，pass@k 有意义；用户每次点击都应稳定完成时，pass^k 更接近风险。τ-bench 原始论文报告当时评测的强函数调用智能体整体成功率低于 50%，零售域 pass^8 低于 25%，因此专门提出 pass^k 来揭示多次运行的不一致。不要把该论文的模型分数当作 2026 排行榜，也不要编造一个跨任务通用的固定百分点差。

指标 公式 视角 随 k 增大 贴近
pass@k 1−(1−p)k1-(1-p)^k1−(1−p)k 乐观（至少一次对） →1 demo/benchmark 刷分
pass^k pkp^kpk 悲观（每次都对） →0 真实生产可靠性

基准组合：形式规划、真实执行与时间视界

没有一个基准能同时隔离规划能力、覆盖真实环境并给出长程尺度。实用评测应组合不同证据：

基准 测什么 规模/特点 主要盲区
PlanBench 形式化行动与状态变化推理 可自动生成、可由规划器验证 与开放工具环境有距离
Agent Planning Benchmark 执行前的规划诊断 4,209 个多模态案例、22 个领域、5 种设置 计划正确不等于执行成功
τ-bench / τ²-bench 多轮策略遵循、工具与用户协作 用数据库终态验证，后者加入双控制 领域有限
WebArena 真实网站上的长程交互 812 个可复现实验任务 网站栈与任务分布固定
METR time horizon 不同人类耗时任务上的成功概率 拟合 50% 与 80% 成功时间视界 主要覆盖软件与研究任务 
flowchart TD
    EVAL[规划评测] --> OUT[结果维度]
    EVAL --> PROC[过程维度]
    OUT --> P1["pass^1<br/>单次成功"]
    OUT --> PK["pass^k<br/>悲观, 贴近生产"]
    PROC --> STEP["步数/效率"]
    PROC --> LOOP[无效循环率]
    PROC --> SAFE[违规动作率]
    PK --> BENCH["PlanBench / APB / tau / WebArena / METR"]
    P1 --> BENCH

PlanBench 用经典规划域和自动验证器区分「真的会规划」与从常识文本中猜答案（PlanBench, arXiv 2206.10498）。Agent Planning Benchmark 则把整体规划、反馈条件下逐步规划、无关工具、故障工具和不可解任务分开诊断，并在 ToolSandbox 与 τ²-bench 子集上验证其上游诊断价值（APB, arXiv 2606.04874）。

METR 的时间视界回答另一个问题：当任务按人类专家完成时长衡量难度时，智能体在什么时长附近有 50% 或 80% 成功概率。它通过任务成败与人类耗时拟合逻辑曲线；「两小时时间视界」指人类约需两小时的任务上预测成功率达到阈值，不是智能体能连续运行两小时。报告时必须注明任务域、智能体脚手架与时间视界版本，不能把软件任务结果外推到全部现实工作（METR Time Horizon 1.1）。

过程评估为什么这么难

结果评估有标准答案兜底，过程评估却卡在一个老问题上：谁来判断"这一步该不该走"。让 LLM 当裁判（LLM-as-judge）评过程，就回到了思维树评估函数和反思自评同一个可靠性陷阱——裁判本身可能错。

工程上的折中有三条：(1) 用确定性规则查能客观判定的项，例如是否调用禁用工具、是否超步数、终态是否满足约束；(2) LLM 裁判只评真正需要判断的项，例如分解是否覆盖关键依赖，并用人工样本校准；(3) 对高价值任务保留人工标注做金标准。裁判版本、提示和随机性都要与被测系统一起锁定。

小结

  • 规划评测分结果与过程两类，还必须同时报告成本、稳定性和违规动作，单一完成分不够。
  • pass@k 奖励多次尝试中至少一次成功，pass^k 要求每次都成功；产品契约决定用哪一个，不能虚构统一的分差。
  • PlanBench/APB 隔离规划能力，τ 系列/WebArena 测执行环境，METR 时间视界测任务长度尺度；组合证据比单榜排名可靠。
  • 过程评估难在"谁当裁判"，与思维树评估、反思自评同源；对策是确定性指标+LLM 裁判+人工金标准的混合判定。
