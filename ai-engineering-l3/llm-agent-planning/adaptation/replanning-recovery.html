Part II · Agent Construction智能体规划与任务分解自适应重规划与恢复

重规划与恢复

反思告诉智能体"刚才错了、错在哪"，但诊断完之后总得有人决定下一步动作：是把出错的那一小步重做、把整个子计划推翻重来、还是干脆向人求助？这就是重规划与恢复——自适应闭环里的"治疗"环节，也是把任务分解那种"计划僵化"的脆弱系统救活的关键。没有它，一个再漂亮的计划碰到第一个意外就会卡死。

核心概念

重规划（replanning）指智能体在执行偏离预期时，修改或重建剩余计划的过程。它由三个动作构成一条流水线：

  1. 失败检测（detect）：识别"出问题了"。信号可来自工具报错、结果与预期不符、超出 max_steps、或反思给出的负面判断。
  2. 失败定位与归因（diagnose）：判断是哪一步、什么性质的失败——是临时性的（网络抖动，重试即可）还是结构性的（计划假设根本错了，必须重来）。
  3. 恢复决策（recover）：选择恢复策略——重试、局部重规划、全局重规划、还是升级求助。

    EX[执行某步] --> D{失败检测}
    D -->|正常| NEXT[继续下一步]
    D -->|异常| DIAG[归因: 临时 or 结构性]
    DIAG -->|临时性| RETRY[重试/退避]
    DIAG -->|局部错| LOCAL[局部重规划<br/>只改该子树]
    DIAG -->|结构性错| GLOBAL[全局重规划<br/>推翻重来]
    DIAG -->|无解/高风险| ESC[升级求助]
    RETRY --> EX
    LOCAL --> EX
    GLOBAL --> EX

恢复策略的层级：从最轻到最重

恢复的核心智慧是用最小的代价修复——能重试就别局部重规划，能局部就别全局推翻。下表按代价从轻到重排列四档策略：

策略 改动范围 代价 适用失败类型
重试 / 退避 无（同一步再来） 最低 临时性（超时、限流、偶发）
局部重规划 当前子树/子计划 低 单步假设错（航班售罄换候选）
全局重规划 整个计划 高 顶层策略错（整条路线不可行）
升级求助 交给人/上级智能体 最高 无解、高风险、反复失败

Plan-and-Execute 范式天然支持局部重规划：它的计划是显式步骤表，某步失败时只需对该步重新规划，其余步骤不动。这是它比朴素分解更耐操的原因。2026 年的趋势是把这套"验证—重规划"标准化进编排层：Plan-Execute-Verify-Replan 框架在执行后增加验证环节，发现集体结果未满足原始查询时触发定向重规划（Verified Multi-Agent Orchestration, arXiv 2603.11445）。

重规划最危险的失败：无效循环

重规划自己最容易掉的坑，是陷入无效循环——智能体反复重试同一个注定失败的动作，或在两个状态间来回振荡，白烧 token 还不收敛。这是长程智能体最常见的"卡死"形态。

防循环要靠几道硬约束，下面用伪代码勾勒一个带护栏的重规划控制器：

def recover(state, failure, budget):
    budget.attempts += 1
    if budget.attempts > MAX_RETRY:          # 护栏1: 总尝试上限
        return escalate(state)               # 超限即升级，不再硬试
    if failure in state.seen_failures:       # 护栏2: 同种失败已见过
        return replan_globally(state)        # 别再局部重试，换策略
    if budget.tokens > TOKEN_CAP:            # 护栏3: 算力预算
        return escalate(state)
    state.seen_failures.add(failure)
    if failure.is_transient:                 # 临时性才退避重试
        return retry_with_backoff(state)
    return replan_locally(state, failure)    # 否则局部重规划

三道护栏缺一不可：尝试次数上限防死循环、失败去重防"同一墙撞十次"、token 预算防烧钱。一旦触顶就升级到人在回路，把判断权交还给人——这是工程上"优雅降级"而非"硬扛到崩"的体现。"反复失败应升级"也正是长程可靠性里压制误差复利的手段之一。

失败检测：最难的其实是"发现错了"

上面的恢复策略都建立在一个前提上：你得先知道出错了。而失败检测恰恰是整条链路里最难的一环——很多失败是沉默的：工具返回了一个语法合法但语义错误的结果（查到了航班但日期错了），没有任何报错，智能体浑然不觉地继续往下走，错误就沿步数复利累积。

检测信号按可靠性分几类：

信号类型 可靠性 例子
显式异常 高 工具抛错、HTTP 500、超时
约束违反 高 输出不满足 schema、断言失败
自评判断 中 反思器判定"结果不对"
一致性校验 中 两条独立路径结果不一致
无信号（沉默失败） —— 语义错但语法合法

对付沉默失败，工程上常用的手段是主动校验：在关键步骤后插入显式的断言或验证调用（"刚订的票日期是明天吗？"），把沉默失败转成显式的约束违反。这与反思的接地思想一脉相承——别信模型默认正确，给它装上可验证的检查点。失败检测的可靠性也直接决定了规划评测能否准确度量"哪一步出了问题"。

小结

  • 重规划是自适应闭环的"治疗"环节，由失败检测→归因→恢复决策三步构成，是救活"计划僵化"系统的关键。
  • 恢复策略按代价分四档——重试、局部重规划、全局重规划、升级求助；核心智慧是用最小代价修复，Plan-and-Execute 天然支持局部重规划。
  • 最危险的失败是无效循环；防循环靠三道硬护栏：尝试上限、失败去重、token 预算，触顶即优雅降级到人在回路。
  • 失败检测是最难一环，沉默失败（语法合法语义错）最棘手；对策是在关键步骤后插入主动校验，把沉默失败转成显式约束违反。
