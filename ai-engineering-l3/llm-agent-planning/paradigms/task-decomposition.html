Part II · Agent Construction智能体规划与任务分解范式任务分解

任务分解

人类接到"组织一场五十人线下沙龙"时，不会一头扎进"先发哪封邮件"，而是先在脑子里劈出几块：定场地、定议程、发邀请、订餐、现场执行。每块再往下拆。这种"先把大问题劈成可管理的小问题，再逐块求解"的本能，就是任务分解——与ReAct 交错推理"走一步看一步"恰好相反的另一极。它用前置的全局结构，换取长程任务上的视野与效率。

核心概念

任务分解的标准流程分两步（Understanding the planning of LLM agents, arXiv 2402.02716）：

  1. 分解（decompose）：把复杂任务 TTT 拆成子任务集合 {t1,t2,…,tn}\{t_1, t_2, \dots, t_n\}{t1​,t2​,…,tn​}，并理清它们之间的依赖（哪些必须先于哪些）。
  2. 子规划（sub-plan）：为每个子任务生成执行方案，按依赖顺序串起来。

按"分解与执行的时序关系"，分解又分两大流派：

  • 分解优先（decomposition-first）：先一次性把整棵任务树拆完，再逐个执行。代表是 Plan-and-Execute、least-to-most。视野最全，但树定死后对意外不敏感。
  • 交错分解（interleaved decomposition）：拆一层、执行一层、再根据结果拆下一层。代表是 HTN 式按需展开。比纯分解优先灵活，又比纯 ReAct 有结构。
flowchart TD
    T[复杂任务<br/>组织五十人沙龙] --> D[分解器]
    D --> T1[定场地]
    D --> T2[定议程]
    D --> T3[发邀请]
    D --> T4[订餐]
    T1 --> T3
    T2 --> T3
    T3 --> T4
    T1 --> EX[按依赖拓扑序执行]
    T2 --> EX
    T3 --> EX
    T4 --> EX
    EX --> FB{某步失败?}
    FB -->|是| RP[局部重规划该子树]
    FB -->|否| Done[完成]

四种主流分解策略对比

分解不是单一算法，而是一族策略。下表对比四个最常被实现的策略，它们在依赖处理、token 效率、灵活性上各有侧重：

策略 核心思想 依赖处理 token 效率 灵活性
least-to-most 从最简子问题起逐步累积解 显式线性链 中 低
Plan-and-Solve 先出整体计划再分步求解 计划内隐含 中 低
Plan-and-Execute 规划器出计划+执行器逐步执行 显式步骤表 高 中（可局部重规划）
ReWOO 带占位符一次规划+并行执行+末次合成 占位符变量 最高（约2次调用） 低

least-to-most 适合子问题构成清晰依赖链的场景：先解最简单的，把它的解喂给下一个更难的，逐级递推。Plan-and-Solve 是它的提示工程轻量版，常用一句"Let's first devise a plan"诱导模型先列计划再执行。

Plan-and-Execute 是工程上最实用的一档：一个规划器 LLM 产出高层步骤表，一个（往往更便宜的）执行器 LLM 逐步落地，某步失败时只对该子树局部重规划。2025 年的 Plan-and-Act 把这套两级流水线标准化——规划器出高层计划、执行器做带局部重规划的逐步执行，在网页导航任务上取得当时的最优结果（Plan-and-Act 综述讨论）。这里的"局部重规划"是连接本篇与重规划与恢复的关键接口。

ReWOO（Reasoning Without Observation）是 token 极致优化版：它一次性规划出整条带占位符变量的流程（如 #E1 = search[...]、#E2 = lookup[#E1]），把所有工具调用从推理循环里剥离出来并行执行，最后只用一次 LLM 调用把结果合成答案——总共约两次 LLM 调用，token 效率约为 ReAct 的五倍（The 4 Single-Agent Patterns）。代价是它假设计划在执行前就能定死，遇到强不确定环境会脆。

HTN：分层分解的形式化骨架

当任务深到三四层，扁平的步骤表就力不从心了，需要规划问题形式化里提过的层级任务网络（HTN）：用"方法"把抽象任务逐层分解为子任务，直到全是可直接执行的原始任务。HTN 与上面策略的关系是——它给"交错分解"提供了形式化骨架与正确性保证。

2025 年的 ChatHTN 是 LLM 时代 HTN 的代表：当 HTN 引擎找不到现成方法分解某个任务时，就临时查询 LLM 生成一个分解，再交还引擎按 HTN 规则继续展开；且整套被证明可靠（sound）——任何产出的解都保证正确求解原问题（Online Learning of HTN Methods, arXiv 2511.12901）。这把 LLM 的"任何任务都能即兴拆"与符号规划的"拆得对、解得对"罕见地缝在一起。

flowchart TD
    A[抽象任务<br/>办一次出差] --> M{有现成方法?}
    M -->|是| D1[按方法分解]
    M -->|否, ChatHTN| L[查询 LLM 生成分解]
    L --> D1
    D1 --> S1[子任务: 订票]
    D1 --> S2[子任务: 订酒店]
    S1 --> P{是原始任务?}
    P -->|否| M
    P -->|是| EXEC[执行]

分解的失败模式与边界

分解强在视野与效率，但有三类典型失败，恰好划出它的适用边界。

第一，计划僵化。分解优先把树定死，一旦环境与预设不符（航班售罄、网页改版），整棵树作废。缓解靠 Plan-and-Execute 的局部重规划或外挂的重规划层——这也是为什么 2026 年纯分解几乎不单独上线，总要叠加自适应。

第二，分解粒度失当。拆得太粗，子任务仍然难到无法直接执行；拆得太细，子任务数量爆炸、协调成本超过收益。粒度选择目前仍是经验活，没有通用最优解。

第三，依赖识别错误。把本有先后的子任务误判为可并行（如未拿到行程号就去写日历），会在执行期暴雷。ReWOO 的占位符变量机制正是为显式表达依赖而设计。

什么时候该选分解而非 ReAct？回到范式谱系：任务长、步骤可预判、环境稳定、token/延迟敏感时，分解（尤其 Plan-and-Execute / ReWOO）完胜；环境不可预测、强反馈依赖时，让位给 ReAct。

小结

  • 任务分解走"先谋后动"路线：分解→子规划两步，与 ReAct 的交错恰相反，用前置全局结构换长程视野与效率。
  • 按时序分为分解优先（Plan-and-Execute、least-to-most）与交错分解（HTN 按需展开）。
  • 四策略各有侧重：least-to-most 处理依赖链、Plan-and-Solve 是其提示版、Plan-and-Execute 最实用（可局部重规划）、ReWOO token 效率最高（约两次调用、五倍效率）。
  • HTN/ChatHTN 给分层分解提供形式化骨架与可靠性保证，缝合 LLM 灵活性与符号正确性。
  • 三类失败划出边界：计划僵化（需外挂重规划）、粒度失当、依赖误判；纯分解几乎不单独上线。
