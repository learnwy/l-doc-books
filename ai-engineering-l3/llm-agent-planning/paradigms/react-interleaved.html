ReAct 交错推理

2022 年底的 ReAct 论文做了一件后来被无数智能体框架抄进默认模板的事：它不让模型一口气想完再行动，而是把"推理"和"行动"拧成一股绳——想一句、做一个动作、看一眼结果、再想下一句。这个看似朴素的交错，恰好命中了规划问题形式化里那个最棘手的现实：环境是部分可观测的，你根本无法在动手前知道下一步的结果，所以与其预测不如观察。ReAct 因此成为开放、反馈密集环境里的事实默认范式。

核心概念

ReAct 是 Reasoning + Acting 的缩写。它的运行单元是一个三元组循环：Thought（推理）→ Action（行动）→ Observation（观察），每轮一次 LLM 调用，循环直到模型认为目标达成并输出最终答案。

  • Thought：模型对当前局势的自然语言思考——"我还不知道航班价格，应该先查"。
  • Action：一次结构化的工具调用——search_flights(date="明天", to="上海")。
  • Observation：环境/工具返回的真实结果，被拼回上下文。

关键在于 Observation 会进入下一轮 Thought 的输入：模型的下一步推理建立在真实反馈而非凭空想象之上。这就是"交错"的全部精髓，也是它区别于任务分解那种"先想完整条计划再执行"的根本所在。

flowchart TD
    Start[用户目标] --> T[Thought<br/>分析当前该做什么]
    T --> A[Action<br/>选择并调用一个工具]
    A --> O[Observation<br/>拿到工具真实返回]
    O --> C{目标达成?}
    C -->|否| T
    C -->|是| F[Final Answer<br/>输出结果]

下表把 ReAct 与它最直接的对立面放在一起，凸显交错的代价与收益：

维度 ReAct（交错） Plan-and-Execute（前置）
规划时机 每步现想 开头一次想完
对意外的响应 强，立刻调整 弱，需外挂重规划
LLM 调用数 多（每步一次） 少（计划一次）
token 成本 高 低
全局视野 弱，易局部贪心 强
长链稳定性 易漂移 较稳

为什么交错能赢，又为什么会输

ReAct 的胜场在于反馈接地（grounding）。在网页导航这类任务里，页面长什么样、按钮点下去跳到哪，事前完全无法预知；ReAct 让每一步决策都基于刚拿到的真实页面，避免了"按想象中的网页规划、一执行全错"。这也是为什么纯前置规划在 POMDP 型环境里普遍打不过交错。

但交错有两个结构性弱点，恰好是后续范式要修补的。

第一，缺乏全局视野，易陷局部贪心。每步只看眼前，模型可能为了完成当前子目标做出损害整体的选择，且事后难以察觉。这正是任务分解用"先出全局计划"来弥补的。

第二，长链上推理会漂移、目标会丢失。轮数一多，早期目标被淹没在冗长的 Observation 里，模型开始原地打转或反复调用同一个失败工具。2025 年的 ReflAct 直指此弊：朴素 ReAct 的 Thought 常常脱离真实世界状态空谈，于是它改为让模型持续维护并反思"当前信念—目标"的对齐，把空想的推理拉回到世界状态上（ReflAct, arXiv 2505.15182）。这种"带状态反思的 ReAct"是连接本篇与反思与自我批评的桥梁。

一个最小 ReAct 循环的骨架

下面用伪代码勾勒一个去框架化的 ReAct 循环，便于看清控制流。真实工程框架会封装状态持久化和调度，但不会改变这里的决策—行动—观察闭环：

def react(goal, tools, max_steps=15):
    transcript = [system_prompt(tools), user(goal)]
    for step in range(max_steps):
        out = llm(transcript)            # 产出 Thought + Action
        if out.is_final:
            return out.answer
        obs = call_tool(out.action, tools)   # 执行，得到 Observation
        transcript += [out.thought, out.action, obs]
    return "未在步数上限内完成"          # 触发重规划/上报

两个工程要点值得注意。其一是 max_steps 这道闸——它是防止漂移的最后防线，超限本身就是一个失败信号，应交给重规划与恢复处理而非简单报错。其二是 Action 的解析与执行：ReAct 只决定"调哪个工具、传什么参数"；执行器仍要独立完成 schema 校验、授权、并发控制和注入防护，规划文本不能绕过这些硬边界。

ReAct 的变体与边界

ReAct 不是终点，而是一族变体的起点。下表列出几个常见演化方向及其要解决的问题：

变体 在 ReAct 上加了什么 解决的痛点
ReAct + Reflexion 失败后语言化反思并重试 长链漂移、重复犯错
ReflAct 每步反思信念—目标对齐 Thought 脱离世界状态
Plan-then-ReAct 先粗规划再 ReAct 执行子步 缺全局视野
ReWOO 把观察从循环中移出、批量并行 token 成本与延迟

什么时候不该用 ReAct？当任务步骤高度可预判、环境稳定、且 token/延迟敏感时，每步一次 LLM 调用的开销纯属浪费，此时任务分解的前置规划或 ReWOO 更划算。判据回到范式谱系的两根轴：环境越不可观测、反馈越关键，ReAct 越占优；反之则让位给前置规划。

小结

  • ReAct 把推理与行动交错成 Thought→Action→Observation 循环，每步基于真实反馈再决策，是开放、部分可观测环境的事实默认范式。
  • 其优势是反馈接地，避免按想象规划；代价是每步一次调用、token 贵、缺全局视野、长链易漂移。
  • 全局视野的缺失由任务分解弥补，长链漂移由 ReflAct/Reflexion 式反思缓解。
  • 工程上 max_steps 是防漂移闸门，超限应转交重规划；Action 的调用机制属于工具调用 hub，不在此重复。
  • 任务可预判且 token 敏感时应让位给前置规划或 ReWOO。
