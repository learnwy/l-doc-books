向量数据库

核心概念

向量数据库（Vector Database）是专门为高维向量数据的存储、索引和检索而设计的数据库系统，是稠密检索、RAG 系统和语义搜索的核心基础设施。与传统关系型数据库不同，向量数据库的核心操作是近似最近邻（ANN）搜索，而非精确匹配查询。

索引构建与管理
向量索引的构建是一次性的高成本操作，索引质量直接决定了检索的速度和精度。不同索引类型适合不同的规模和场景。


interface VectorCollection {
  name: string;
  dimension: number;
  metric: 'cosine' | 'l2' | 'ip';
  indexConfig: IndexConfig;
  shardCount: number;
  replicaCount: number;
}

interface IndexConfig {
  type: 'hnsw' | 'ivf_flat' | 'ivf_pq' | 'diskann' | 'flat';
  params: Record<string, number>;
}

const HNSW_CONFIG: IndexConfig = {
  type: 'hnsw',
  params: {
    m: 16,
    efConstruction: 256,
    efSearch: 128,
  },
};

const IVF_PQ_CONFIG: IndexConfig = {
  type: 'ivf_pq',
  params: {
    nlist: 4096,
    nprobe: 64,
    m: 96,
    nbits: 8,
  },
};

interface CollectionOperations {
  createCollection(config: VectorCollection): Promise<void>;
  insert(vectors: Float32Array[], metadata: Record<string, unknown>[]): Promise<string[]>;
  search(query: Float32Array, topK: number, filter?: FilterExpr): Promise<SearchResult[]>;
  delete(ids: string[]): Promise<void>;
  upsert(id: string, vector: Float32Array, metadata: Record<string, unknown>): Promise<void>;
}

interface SearchResult {
  id: string;
  score: number;
  vector?: Float32Array;
  metadata: Record<string, unknown>;
}

interface FilterExpr {
  field: string;
  operator: 'eq' | 'ne' | 'gt' | 'lt' | 'in' | 'range';
  value: unknown;
}
索引构建参数对检索性能影响显著。HNSW 的 M 参数控制图的连接度（更大 = 更高召回但更慢构建和更多内存），efConstruction 控制构建质量，efSearch 控制检索精度。IVF 的 nlist 控制聚类数量，nprobe 控制检索时探查的聚类数。


混合搜索与过滤
实际应用中，向量搜索通常需要与标量过滤（如按日期、类别、权限筛选）结合使用。混合搜索的核心挑战是如何高效地将向量近似搜索与精确的标量过滤结合。


type FilterStrategy = 'pre_filter' | 'post_filter' | 'in_filter';

interface HybridSearchConfig {
  vectorWeight: number;
  sparseWeight: number;
  filterStrategy: FilterStrategy;
  topK: number;
  overFetchFactor: number;
}

async function hybridVectorSearch(
  vectorDB: VectorDB,
  query: Float32Array,
  filter: FilterExpr,
  config: HybridSearchConfig,
): Promise<SearchResult[]> {
  if (config.filterStrategy === 'pre_filter') {
    const filteredIds = await vectorDB.filterIds(filter);
    return vectorDB.searchWithIdSet(query, filteredIds, config.topK);
  }

  if (config.filterStrategy === 'post_filter') {
    const overFetchK = config.topK * config.overFetchFactor;
    const candidates = await vectorDB.search(query, overFetchK);
    return candidates.filter((r) => matchesFilter(r.metadata, filter)).slice(0, config.topK);
  }

  return vectorDB.searchWithFilter(query, filter, config.topK);
}

分布式架构与扩展
当数据规模超过单机容量时，需要将向量数据库扩展为分布式架构。核心设计包括数据分片（Sharding）、副本（Replication）和一致性保证。


分片策略通常基于向量 ID 的哈希值或数据的地理/业务属性。查询时，路由层将查询广播到所有分片，每个分片返回本地 Top-K，路由层再合并排序得到全局 Top-K。分片数量的选择需要平衡查询延迟（分片越多，单分片数据越少，本地搜索越快）和网络开销（分片越多，合并成本越高）。


副本机制提供读扩展和高可用性。写入时采用主从复制或多主复制，读取时可以从任意副本读取以分散负载。向量数据库的写入吞吐通常受限于索引构建成本，因此在写入密集场景需要采用批量写入和异步索引构建。


小结
    

  • 向量数据库是语义搜索和 RAG 的核心基础设施，核心操作是 ANN 近似最近邻搜索
    • 

  • HNSW 索引适合中小规模高精度场景，IVF-PQ 适合大规模低内存场景，DiskANN 适合磁盘级超大规模
    • 

  • 混合搜索需要将向量检索与标量过滤结合，Pre/Post/In-Filter 各有适用场景
    • 

  • 分布式架构通过分片和副本实现水平扩展和高可用，查询时广播到所有分片后合并结果
    • 

  • 选择向量数据库需综合考虑数据规模、查询延迟、过滤需求、运维成本和是否需要托管服务
    •
