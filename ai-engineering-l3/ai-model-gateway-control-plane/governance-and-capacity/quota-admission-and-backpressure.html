配额、准入控制与背压

每分钟请求数只能描述短而均匀的 API 流量，却无法保护模型网关：一个请求可能携带十万 Token 并持续数分钟，另一个只做十字分类；流式客户端还可能消费缓慢，占用连接和缓冲。容量治理必须同时约束速率、并发、Token、成本和排队时间。

核心概念

准入控制发生在远端调用之前。它先验证身份与策略，再为预计资源申请分层配额租约，最后检查部署实时并发。成功申请后才能解封供应商凭证；执行结束依据真实用量结算差额并释放租约。背压则把容量不足变成上游可理解的协议，而非在网关内部无限排队。

flowchart LR
    Request[规范请求] --> Estimate[资源估算]
    Estimate --> Tenant[租户配额]
    Tenant --> Product[产品与意图配额]
    Product --> Provider[供应商账户配额]
    Provider --> Runtime[实时并发准入]
    Runtime --> Lease[资源租约]
    Lease --> Execute[执行调用]
    Execute --> Reconcile[真实用量结算]
    Reconcile --> Tenant

分层配额与公平共享

配额通常具有组织、租户、产品、意图和调用主体五层。一次请求必须同时满足各层限制，不能只扣最细粒度桶。组织层保护合同总额，租户层保证隔离，产品与意图层让高价值在线流量和后台任务使用不同预算，主体层阻止单个工作负载失控。

硬配额定义不可借用上限，公平份额定义压力下的资源分配。空闲时，租户可以借用未使用容量；拥塞时，调度器按权重收回借用并保留每个租户最低份额。若只使用“先到先得”，长流量租户会占满槽位，后来的短请求即使更重要也无法进入。

分布式网关不应让每个实例持有完整全局额度。常见方案是全局配额服务按时间租出租约块，本地实例用令牌桶吸收突发；租约到期或消耗后再续租。这样热路径不必每次同步访问中央存储，同时全局误差有明确上界。配额服务故障时，低风险读请求可在最后租约内继续，高成本或受监管请求应失败关闭，策略必须预先定义。

预留、结算与超额

真实 Token 只有响应结束后才能确定，准入前需要保守估算。输入可以在规范化后精确或近似计数，输出使用调用方上限与意图历史分位数估算。预留过低会超卖，预留过高会降低利用率；可以对稳定意图用历史模型，对新意图使用上限。

export type ResourceReservation = {
  leaseId: string;
  tenantId: string;
  reservedInputTokens: number;
  reservedOutputTokens: number;
  reservedCostMicros: number;
  expiresAt: string;
};

export interface QuotaLedger {
  reserve(demand: EstimatedDemand): Promise<ResourceReservation>;
  reconcile(leaseId: string, usage: ActualUsage): Promise<void>;
  cancel(leaseId: string): Promise<void>;
}

结算时记录输入、缓存、输出、推理与工具分项。真实用量小于预留就返还差额；高于预留则扣减剩余预算并产生预测偏差指标。若供应商尾事件缺失，用量标为估算并保留不确定性，不能当作零。长期偏差超过阈值时，需要更新估算器或降低该意图并发。

月度金额上限不适合直接做热路径唯一控制，因为供应商价格与币种可能变化。控制平面把价格表版本化，数据面用调用时价格快照预估；账单对账再校正。达到硬支出上限时应知道哪些流量停止、哪些进入廉价模型降级、哪些保留紧急额度。

准入顺序与队列纪律

准入顺序影响安全与成本。推荐先做廉价的语法、身份和静态策略检查，再估算资源并申请配额，之后获取部署并发租约，最后解析供应商凭证。若先解封凭证或建立上游连接再发现租户额度不足，拒绝请求也消耗敏感资源。

队列只适用于剩余时限充足且调用方允许等待的请求。每个条目携带绝对截止时间、优先级和估算权重；调度时若预计无法在截止前完成，立即移除。后台批处理可以进入持久队列，交互式流量则倾向短有界队列。两类请求不应共享同一个无差别 FIFO。

背压协议与慢消费者

HTTP 拒绝应返回稳定错误类别、限制维度、可重试性和建议时间，而不是把供应商 429 原样暴露。调用方需要区分租户额度不足、网关容量不足与供应商过载，因为它们的恢复动作不同。对长连接和 SSE，已经开始输出后无法改成普通错误响应，应发送规范终止事件并关闭流。

慢消费者会把供应商速度转换为网关内存。每个输出流使用有界缓冲与写入空闲超时；缓冲达到上限后先暂停上游读取，若协议或 SDK 无法形成有效背压，则取消远端请求。取消结果进入计量，防止调用方通过不读取响应制造无成本资源占用。

上游调用方也必须参与背压。服务端返回明确 retry_after_ms，客户端使用带抖动退避和自身并发上限；如果每个客户端都无条件重试三次，网关的快速拒绝会转化为更大入站流量。SDK 可以默认实现重试预算，但最终端到端截止时间来自业务调用方。

Envoy 的全局限流架构说明本地令牌桶和全局配额可以两阶段组合：本地吸收突发，全局实现公平共享。模型网关应在这一模式上增加 Token 和成本预留，而不是重新发明无界中央计数器。

验证与运营信号

容量测试要使用不同长度和不同消费速度的请求混合，而非只做固定短 Prompt 压测。验证指标包括准入延迟、各维度拒绝率、配额租约误差、队列等待分位数、预留与实际 Token 偏差、慢消费者取消，以及健康租户在 noisy neighbor 压力下的延迟。

故障注入需要断开配额服务、延迟结算、让供应商不返回用量、耗尽单租户预算并填满全局连接池。每种情况下都检查失败开放或关闭是否符合数据等级，租约是否最终过期，额度是否不会永久泄漏。

准入租约最终进入身份与租户策略的授权上下文，真实用量则流向审计与数据治理。容量事实与身份事实分开存储但通过 decision_id 关联，既能对账，也避免配额系统读取用户内容。

小结

  • 模型容量必须同时约束请求、并发、Token、成本、队列时间和流缓冲。
  • 全局配额负责公平，本地令牌桶吸收突发，租约使同步依赖有界。
  • 准入前预留、完成后按实结算，缺失用量标为估算而不是零。
  • 队列携带绝对截止时间与权重，交互流量不能进入无界 FIFO。
  • 背压错误要告诉调用方限制来自哪里，并要求客户端遵守自己的重试预算。
  • 用混合长度、慢消费者和配额服务故障证明容量隔离真实有效。
