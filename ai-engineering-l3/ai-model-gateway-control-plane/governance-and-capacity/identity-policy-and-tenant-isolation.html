身份、策略与多租户隔离

一枚共享供应商 API Key 无法回答谁代表哪个租户、为什么允许使用某个模型、是否可以把数据发送到某区域。模型网关需要在自己的信任边界内认证调用者，用组织身份和策略做决定，再在最后一跳代表租户使用供应商凭证。

核心概念

一次请求至少涉及四类主体：终端用户、发起调用的工作负载、拥有数据与预算的租户、承担供应商账单的计费主体。它们可能相同，也可能完全不同。授权上下文必须分别记录，禁止把一个 user_id 同时当作服务身份与租户边界。

flowchart LR
    User[终端用户] --> App[调用工作负载]
    App --> Authn[工作负载认证]
    Authn --> Context[规范身份上下文]
    Context --> Policy[策略决策点]
    Policy -->|允许| Credential[凭证代理]
    Credential --> Provider[供应商]
    Policy --> Evidence[策略证据]
    Provider --> Evidence
身份维度 典型来源 用途 不可替代
工作负载 mTLS、短期工作负载凭证 认证调用服务 不能用用户字段冒充
终端用户 应用签发的受众限定令牌 风险、滥用与产品授权 不直接获得供应商凭证
租户 可信令牌声明与服务端映射 数据、预算、策略隔离 不接受请求体任意声明
计费主体 控制平面绑定 成本归因与合同 可与租户不同
委托链 代理身份与授权范围 解释代表谁执行 必须限制深度和权限

认证链与凭证代理

工作负载认证优先使用短期、可轮换、受众限定的身份。SPIFFE 的工作负载 API定义了 X.509-SVID 与 JWT-SVID，并由本地端点识别调用进程；官方规范展示了无需在应用中静态分发长期密钥的模式。具体实现可以不同，但原则相同：先证明谁在调用，再映射其允许代表的租户。

终端用户身份由产品应用验证，网关只接受来自可信工作负载的最小声明，并验证签发方、受众、时效和委托范围。对于服务代表用户执行的请求，审计同时记录工作负载与用户，不允许后者覆盖前者。

供应商凭证留在凭证代理或受保护适配器内。控制平面保存凭证引用、适用部署和轮换状态，数据面在策略允许且即将调用时获取短期材料。日志、错误和响应永远不含原始密钥。不同租户若使用自带账户，凭证、连接池、用量账本和供应商请求标识都要按租户分区。

策略决策点与执行点

策略输入应是规范、已认证且尺寸有界的文档，包括主体、租户、意图、所需能力、数据分类、候选部署、估算成本和当前策略版本。策略输出不是一个布尔值，而是允许或拒绝、约束补丁、原因码、审计等级和有效期。

export type PolicyDecision = {
  decisionId: string;
  allowed: boolean;
  reasonCodes: readonly string[];
  allowedDeployments: readonly string[];
  maxOutputTokens: number;
  auditLevel: 'metadata' | 'sampled_content' | 'restricted';
  validUntil: string;
  policyVersion: string;
};

策略决策点负责计算，入口、路由器和适配器是不同的策略执行点。入口阻止未认证请求，路由器只看允许部署，适配器阻止未授权扩展和凭证引用。执行点不能自行放宽决策；若策略服务不可用，使用短期缓存决策必须验证主体、请求指纹和有效期完全匹配。

Open Policy Agent 的HTTP API 授权教程演示了把细粒度、上下文相关策略从服务代码中分离。无论是否采用该实现，策略包都应版本化、先在历史决策上回放、再渐进发布。改变允许范围的策略不能仅靠单元测试验收。

多租户数据与缓存隔离

租户隔离覆盖内存、持久化、缓存、遥测和外部供应商五个平面。请求上下文对象在入口确定 tenant_id 后不可被普通业务字段修改；所有缓存键、队列分区、对象存储路径和成本账本主键都包含可信租户维度。数据库行过滤只是最后一道保护，不是唯一保护。

Prompt Cache 和语义缓存尤其容易跨租户泄漏。默认按租户、策略版本、模型部署和内容哈希分区；只有经过明确数据共享协议的公共前缀才能跨租户复用。缓存命中返回前仍要执行当前策略，因为旧条目可能来自已撤销的模型或数据区域。

流式事件缓冲不能复用可见内容对象，异步任务消息必须携带签名或服务端查回的租户上下文。后台消费者重新认证自己的工作负载身份，并验证它被授权处理消息中的租户，而不是认为“队列里的消息天然可信”。

隔离面 控制措施 验证方式
内存与流 请求作用域对象、有界缓冲 并发交叉测试
缓存 租户加策略版本键 碰撞与撤销测试
队列 分区与签名上下文 篡改消息测试
账本 不可变租户主键 对账属性测试
供应商 独立凭证或元数据标签 请求录制检查
遥测 脱敏与访问分区 权限和泄漏扫描

数据策略、工具与委托

模型请求的数据分类可以来自产品声明与内容检测，但产品声明不能降低服务端已知等级。策略根据最高分类决定允许供应商、区域、保留模式、内容采样和服务器工具。数据区域是硬约束；故障回退不得越界。

工具定义包含风险等级和执行归属，模型生成工具参数不等于授权。工具运行时重新以用户、工作负载、租户和具体调用参数评估权限，高风险写操作还需要人类确认或事务令牌。模型网关只传递稳定 tool_call_id 和签名上下文，不把供应商“允许调用工具”当成组织授权。

委托链应有最大深度和权限递减：Agent A 可以代表用户调用模型，模型建议 Agent B 执行工具，并不意味着 B 获得 A 的所有权限。每一跳记录 actor、subject、scope 与到期时间，新的委托范围必须是上一跳的子集。

策略测试与应急控制

策略测试包括允许样本、拒绝样本、边界属性和历史流量回放。关键属性例如“受限数据永不进入未批准区域”“租户 A 的凭证引用永不出现在租户 B 计划”“安全阻断不能因回退改变”。随机生成请求可比少量手写示例更好地发现组合漏洞。

应急开关也必须受策略治理。关闭某模型、撤销某凭证、禁止某扩展和停止内容采样应有独立权限、原因与有效期；不能提供一个无人审计的全局旁路。break-glass 操作使用强认证、双人审批或事后强制复核，并产生不可删除的审计事件。

身份决策发生在配额准入之前或与其组成原子流程，最终证据写入审计与数据治理。如果配额按请求体里的租户扣款、策略却按令牌租户授权，两套身份来源不一致就会形成跨租户攻击面。

小结

  • 分别建模用户、工作负载、租户、计费主体和委托链，避免身份混用。
  • 供应商凭证只在最后一跳解封，永不发给调用方或写入日志。
  • 策略输出包含约束、原因、版本和有效期，不只是允许或拒绝。
  • 租户隔离覆盖缓存、流、队列、账本、供应商和遥测，而非只靠数据库过滤。
  • 模型工具调用是建议，不是授权；工具运行时必须重新评估具体权限。
  • 策略用属性测试、历史回放与渐进发布验证，应急旁路同样需要治理。
