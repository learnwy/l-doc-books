可观测性、成本归因与服务目标

一次用户请求可能产生一个路由决策、两个供应商尝试、数百个流事件和三种 Token 分项。若只记录入口 HTTP 延迟，系统会把“用户等待”“供应商生成”“对冲浪费”和“客户端消费缓慢”混为一谈；若把模型名、用户和工具参数全塞进指标标签，监控系统又会先因高基数与敏感数据失控。

核心概念

可观测模型分四层：逻辑请求表示用户体验，决策表示策略选择，尝试表示一次远端调用，流事件表示生命周期细节。追踪用标识连接层次，指标只使用有界维度，结构化日志保存受控诊断，审计流保存不可变决策事实。

    R --> A1[attempt span A]
    R --> A2[attempt span B]

    A2 --> S2[取消与尾用量]

层次 关键时间 关键结果 推荐标识
逻辑请求 接收到最终完成 成功、降级、拒绝 request_id
路由决策 策略解析耗时 候选、选择、原因 decision_id

流事件 事件间隔、缓冲等待 序号、终止 stream_id
成本账本 价格生效与结算时间 估算、供应商报告、账单 usage_entry_id

追踪、指标与日志的分工

入口创建逻辑请求 span，策略选择记录为事件或子 span，每个远端尝试使用独立客户端 span。对冲失败的尝试即使被取消也保留；否则追踪只显示胜者，会掩盖额外负载。流 Token 不应逐个创建 span，可聚合首事件、最后事件、事件数、总字节和最大间隔。

指标维度限制在供应商、部署等级、区域、意图类别、终止类别和策略版本等有界集合。request_id、用户、原始模型字符串和工具参数不进入标签，需要排障时通过 exemplar 或追踪跳转。新模型先注册到受控目录，避免临时名字制造无界时间序列。

日志用于异常诊断而非重复追踪。默认记录稳定错误类别、供应商请求标识、有限长度诊断、重试判断与解码状态；内容字段关闭。需要采样内容时走独立数据治理管道。OpenTelemetry 当前的生成式 AI 属性规范提供了模型、操作、Token 与工具相关字段，同时明确标注潜在敏感内容，采用时应锁定语义约定版本并测试升级。

面向用户的服务目标

可用性不能只定义为 HTTP 2xx。逻辑成功至少要求规范流完整终止、必需工具参数通过 Schema、输出满足产品最低质量门，且没有未授权降级。可以分别定义协议成功、语义成功和完全成功，防止“回了点文本”掩盖质量失效。

延迟分解为排队时间、策略时间、连接时间、首 Token 时间、生成时间和下游写入时间。交互体验通常更关注首 Token，结构化任务更关注完整响应。服务目标按意图切片，因为长分析与短分类不应共享一个阈值。

服务目标 示例定义 反例
逻辑可用性 截止前得到满足最低契约的结果 任一供应商尝试返回 2xx
首 Token 交互意图的 p95p_{95}p95​ 首事件时间 所有任务平均总时延
完整性 流有合法终止和用量状态 客户端收到过文本
降级率 按租户和意图统计受控降级 只看最终成功率
成本效率 每个成功意图的全尝试成本 只计胜出尝试
质量护栏 在线抽样与离线评测通过 用 Token 长度代替质量

错误预算需要同时观察供应商失败和网关自损。重试可能提高逻辑可用性，却提高额外尝试率、成本和尾延迟；因此仪表盘同时展示原始尝试成功率与逻辑成功率。两者差距扩大是供应商不稳或策略过度补偿的信号。

用量与成本账本

成本归因使用追加账本，不在指标聚合中直接计算财务数字。每条用量记录绑定租户、产品、意图、请求、尝试、部署、价格版本、币种、Token 分项、供应商工具次数和数据来源。金额以整数最小单位保存，避免浮点累计误差。

export type UsageEntry = {
  usageEntryId: string;
  tenantId: string;
  requestId: string;
  attemptId: string;
  deploymentId: string;
  priceVersion: string;
  currency: string;
  amountMicros: number;
  usage: TokenUsage;
  source: 'provider' | 'estimated' | 'invoice_adjustment';
  occurredAt: string;
};

请求结束时先按供应商报告或估算入账；周期性对账将供应商账单、账户用量导出和内部账本按请求标识与时间窗匹配。差额不修改旧记录，而是追加调整项，保留原因和账单批次。供应商不提供请求级账单时，按账户总额校准模型，并明确分摊不确定性。

逻辑请求成本是所有尝试之和，包括被取消的对冲、失败重试和服务器工具。单位经济性可计算“每个满足质量门的业务结果成本”，而不是每次 API 调用成本。缓存节省也要同时记录命中带来的供应商折扣与额外缓存基础设施成本。

告警、看板与基数控制

告警优先指向用户影响与明确所有者：某意图逻辑成功率下降归产品与平台共同处理，某部署首 Token 变慢归适配器和供应商边界处理，某租户配额拒绝上升归容量或合同处理。供应商原始错误码可以用于诊断，却不适合直接成为所有告警规则。

看板从逻辑请求向下钻取：总览展示成功、降级、拒绝、延迟与单位成本；部署页展示尝试、熔断、配额和协议错误；租户页只展示其授权范围。部署、意图和错误类别都由目录枚举，未知值先进入统一 other 并触发数据质量事件。

追踪采样应保留错误、策略拒绝、降级和高成本离群点，提高正常流量的概率采样。采样决定在尽量早的层完成，但对尾部才知道的高成本请求可用 tail sampling。内容采样与追踪采样是两个独立开关。

校验与故障观测

遥测本身要做契约测试：每条逻辑请求恰有一个完成状态，每个尝试最终结束，每笔供应商用量能关联尝试，价格版本在发生时间有效。使用属性查询可发现孤儿尝试、重复结算、负金额和没有终止的流。

故障演练时不仅看网关是否切换，还验证证据是否完整：首选失败是否记录、备选为何被选中、取消是否到达、两次成本是否入账、降级是否进入客户端响应。缺少其中任何一项，系统虽然“活着”，却无法证明自己的行为。

本章的事实模型建立在审计与数据治理之上，并为评测门与灰度发布提供自动停止指标。可观测性只有接入发布决策与预算管理，才从事后看板变成控制平面传感器。

小结

  • 分别观测逻辑请求、路由决策、供应商尝试和流生命周期。
  • 指标只使用有界维度，高基数标识通过追踪和 exemplar 关联。
  • 服务目标衡量逻辑契约与用户体验，而非供应商 HTTP 状态。
  • 成本账本记录所有尝试、价格版本和调整项，账单差额不覆写历史。
  • 内容采样独立于追踪采样，默认只采必要元数据。
  • 遥测契约同样需要测试，并在故障演练中验证证据完整性。
