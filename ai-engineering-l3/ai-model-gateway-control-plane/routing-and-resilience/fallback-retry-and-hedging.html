回退、重试与对冲的尝试预算

同一次模型请求增加第二次尝试，既可能挽救用户体验，也可能把供应商过载放大一倍。可靠策略的核心不是“多试几次”，而是为端到端时限、额外流量、成本和语义变化分别设预算，并在每次尝试前重新计算剩余空间。

核心概念

重试是在相同部署或同一语义目标上重新执行，回退是切换到不同部署或降级方案，对冲是在前一次尚未结束时并发发起额外请求。三者带来的风险不同，必须由执行计划显式授权。任何尝试都要产生独立 attempt_id，最终只有一个成为对外输出的胜者。

错误分类与未知提交状态

只有明确分类后才能决定下一步。连接建立前失败通常没有远端副作用；发送完成但未收到响应时，供应商是否已开始计费或执行工具可能未知；已经向客户端发布文本后再切换模型，则会把两个模型的输出拼接成不可解释的结果。

模型生成本身通常是只读的，但服务器工具、批处理创建和持久化会话可能有副作用。对这类接口，幂等键必须由逻辑操作生成并跨重试复用。若供应商不支持去重，unknown_commit 默认不自动重试，需要查询状态或由调用方决定补偿。

错误到动作的映射还要考虑剩余时限。即使 provider_overloaded 通常可重试，如果指数退避后的保守完成时间超过截止点，正确动作也是立即失败。安全阻断、权限拒绝和输入无效不可通过换供应商绕过，否则回退会成为策略逃逸通道。

端到端预算与退避

设总时限为 DDD，已经消耗时间为 ttt，收尾与网络余量为 mmm，则下一尝试只有在预计保守耗时 eee 满足下面条件时才可启动：

e≤D−t−me \leq D - t - me≤D−t−m

尝试预算还包括最大额外请求比例与成本。例如每分钟正常请求为 NNN，允许的额外尝试预算为 bbb，则重试与对冲合计应满足 A≤bNA \leq bNA≤bN。这个预算在集群层共享，而不是每个实例各自认为自己可以重试 10%，否则扩容会放大总额外流量。

指数退避应加入随机抖动，避免同一故障触发同步重试。对供应商明确返回的重试时间可以尊重其提示，但仍受总截止时间和全局重试预算限制。长流式请求若在中途断开，通常无法无缝恢复；只有产品契约允许从已确认检查点继续时，才使用新请求续写，并把结果标记为组合输出。

export const canAttempt = (state: AttemptState, candidate: Candidate): boolean => {
  const remainingMs = state.deadlineAtMs - state.nowMs - state.finishMarginMs;
  return (
    state.startedAttempts < state.maxAttempts &&
    state.extraCostMicros + candidate.estimatedCostMicros <= state.extraCostBudgetMicros &&
    candidate.pessimisticDurationMs <= remainingMs
  );
};

回退的语义等级

回退不只是可用性选择，还改变质量保证。建议把回退分为等价、受控降级和禁止三级。等价回退满足相同必需能力与质量门；受控降级可能使用更小模型、非严格 Schema 或不同区域，只有调用方意图和组织策略共同允许才可执行；禁止回退包括安全策略变化、数据驻留越界和不可逆工具权限变化。

回退变化 默认等级 必需证据
同模型同版本、独立区域 等价候选 区域与数据策略一致
不同供应商、相同评测门 等价候选 按意图切片评测通过
更小模型、仍满足最低质量 受控降级 产品声明可降级
严格 Schema 改为事后校验 受控降级 警告与修复预算
改变安全过滤级别 禁止 不得由可用性策略绕过
跨越数据驻留边界 禁止 除非新策略重新授权

完成摘要应记录最终部署与经历过的降级，并给出对用户体验有意义的警告。内部还要保留所有失败尝试的成本和时延，否则“成功请求成本”会被低估。

对冲的安全窗口

对冲适合降低长尾，不适合掩盖持续过载。触发阈值应来自相同意图与部署的动态分位数，例如超过近期首 Token p95p_{95}p95​ 且仍有时限与额外流量预算。固定 500 毫秒阈值会在模型或输出长度变化后失真。

对冲必须发生在承诺点之前。对流式文本，承诺点可以定义为向客户端发布第一段内容；对结构化结果，承诺点可能是完整 Schema 验证通过。胜者选定后，立即请求取消其他尝试，并继续记录它们是否真正终止以及最终用量。

如果多个尝试已经产生可接受结果，选择规则必须预先确定，例如首个通过最低质量与协议验证的结果，而不是事后挑“看起来最好”的输出。否则对冲引入不可重放的选择偏差。对高成本请求可先采用“超时后发起但不取消首请求”的有限对冲，再根据双重计费数据决定是否扩大。

Envoy 的HTTP 路由文档明确指出重试都应受整体请求超时约束，推荐用重试预算避免流量爆炸，并将对冲定义为超时后并行保留原请求。模型网关还需在此基础上增加 Token 成本、输出承诺点和语义降级。

故障注入与停止条件

测试不能只让供应商返回 500。需要覆盖连接前断开、请求已发送但响应丢失、首 Token 延迟、流中断、尾用量缺失、取消无效和两个候选同时成功。每种故障都验证尝试数、对外事件、最终成本账本和错误类别。

上线前定义停止条件：额外尝试率超过预算、取消后计费比例异常、回退质量低于门槛、某租户的降级比例激增，或重试使供应商 429 比例上升。停止动作可以关闭对冲、收紧重试或回滚策略快照，而不必重新部署数据面。

回退候选来自约束驱动路由，候选健康与并发容量由熔断与故障隔离提供。执行器不应越过计划临时挑选未评估模型；如果计划已无可用候选，就把失败事实返回准入层。

小结

  • 重试、回退和对冲是三种不同机制，必须分别授权与计量。
  • 每次额外尝试受端到端时限、全局额外流量和额外成本共同约束。
  • 未知提交状态不能按普通瞬时错误处理，有副作用时需要幂等或查询。
  • 安全阻断、权限拒绝和数据区域限制不得通过换供应商绕过。
  • 对冲只能在输出承诺点前竞争，失败尝试仍要记录实际计费。
  • 用真实生命周期故障注入验证策略，并预先定义可自动回滚的停止条件。
