约束驱动的模型路由与放置

生产路由不是“选分数最高的模型”，而是在一次请求的硬约束内，从一组具体部署中选择可解释的执行计划。模型能力只是候选条件之一；数据区域、租户合同、端到端时限、健康度、预算和缓存位置同样会决定某个部署能否被使用。

核心概念

路由应先过滤、再排序、后分配。过滤阶段只处理不能违反的约束；排序阶段在合格候选之间计算质量、延迟、成本与风险；分配阶段应用容量、粘性和受控探索，最终生成带策略版本的计划。把三步混成一个权重公式，会让高分抵消本不该被抵消的合规限制。

flowchart LR
    Request[规范请求] --> Hard[硬约束过滤]
    Catalog[能力与区域目录] --> Hard
    Hard --> Rank[多目标排序]
    Health[实时健康快照] --> Rank
    Rank --> Allocate[容量与粘性分配]
    Budget[租户预算] --> Allocate
    Allocate --> Plan[可审计执行计划]
决策层 输入 输出 失败方式
硬约束 必需能力、区域、策略、截止时间 合格候选集 无候选时明确拒绝
多目标排序 质量、价格、延迟、风险 有序候选 指标缺失需保守惩罚

执行计划 快照版本、尝试预算 不可变计划 执行中不得任意改写

硬约束与模型目录

硬约束来自调用方意图与组织策略的交集。调用方可以声明需要视觉、工具、严格 Schema 或某数据区域，组织策略还会增加租户允许清单、内容等级和供应商合同。候选部署必须满足所有必需能力；偏好能力可以影响排序，但任何降级都要被记录。

截止时间也属于硬约束。若某部署的保守首 Token 预算已经超过剩余时间，它不应进入候选集。这里使用分位数而非平均值，例如以近期同意图、同区域的 p95p_{95}p95​ 首 Token 延迟加网络余量估算。短时指标不足时使用发布时基线，并降低候选置信度。

目录必须以部署为粒度。model_family 适合表达能力预期，deployment_id 才能承载区域、账户、配额池、价格、数据处理条款和健康状态。一个模型在两个区域可能共享质量基线，却不共享容量和故障域。

多目标排序而非万能分数

排序器可以将不同目标规范化，但必须保留原始分量。一个简单形式是：

S(d,r)=wqQ(d,r)−wlL(d,r)−wcC(d,r)−wrR(d,r)S(d, r) = w_q Q(d, r) - w_l L(d, r) - w_c C(d, r) - w_r R(d, r)S(d,r)=wq​Q(d,r)−wl​L(d,r)−wc​C(d,r)−wr​R(d,r)

其中 QQQ 是针对意图的质量预测，LLL 是延迟惩罚，CCC 是成本估算，RRR 是供应链与健康风险。权重来自版本化策略，而非请求自由输入。即使输出一个总分，决策日志也要保存各分量与数据时间窗，才能在事故后解释选择。

质量预测可以来自离线评测、线上抽样和意图分类器。没有足够证据时，不应把新模型默认设为最高质量；可赋予较宽不确定区间，在小流量探索中收集证据。成本估算要包含输入、缓存、输出、推理 Token 和供应商工具，不能只看标价中的一个 Token 单价。

粘性、缓存与受控探索

对多轮会话，路由粘性可以减少语义漂移和缓存失效，但不能成为永不失效的绑定。粘性键应绑定租户、会话、意图与策略版本，并设置最大年龄；硬约束、健康熔断或发布回滚可以打破粘性。打破时响应带 route_changed 警告，便于产品判断上下文连续性风险。

Prompt Cache 可能与供应商、账户、部署甚至前缀版本绑定。路由器可把预期缓存命中作为成本与延迟分量，却不能为了命中缓存违反区域或能力约束。缓存位置属于部署目录，而不是让应用持有供应商缓存标识。

受控探索用于验证新部署或避免路由器只强化旧证据。探索流量必须有上限、适用意图、风险等级和退出条件；高风险业务默认不参与。探索结果进入评测数据，不能直接把用户满意度的相关性当成模型因果提升。

决策可解释性与确定性

同一规范请求、同一策略快照和同一健康快照应产生相同有序候选。若分配需要随机性，使用由 decision_id 派生的稳定种子，使重放可以复现。实时容量会使最终选择变化，因此决策记录必须保存读取到的容量版本，而不能只记结果。

export type RouteDecision = {
  decisionId: string;
  policyVersion: string;
  catalogVersion: string;
  healthVersion: string;
  eligible: readonly CandidateScore[];
  selected: string;
  fallbacks: readonly string[];
  rejected: readonly RejectionReason[];
};

export interface Router {
  plan(request: CanonicalRequest, snapshot: RoutingSnapshot): RouteDecision;
}

路由器是纯决策模块，不发网络请求、不修改健康度，也不消耗配额。执行器拿到计划后再做原子准入；如果容量在两者之间变化，执行器返回 admission_rejected，由上层在原计划允许范围内选择下一候选。这样路由算法能用固定输入做大量离线回放。

失败模式与验证

最常见的失败是把软目标伪装成硬约束。例如“优先低成本”不等于“超过某价绝对拒绝”；前者属于排序，后者属于预算准入。相反，数据驻留是硬约束，不能因为另一区域更快就加权抵消。设计评审时应逐项标注约束类别。

第二个失败是健康信号自激：大量请求因短暂延迟被路由 away，原部署恢复后没有流量验证，于是永远看似不健康。半开探针与小流量恢复可以打破这个循环。第三个失败是候选集过度集中于同一供应商或区域，名义上有三个模型，实际共享同一故障域。

验证应包括历史流量回放、约束属性测试和故障注入。属性测试证明任何随机输入都不会违反租户允许清单与区域；回放比较新旧策略的成本、延迟和评测代理指标；故障注入将某区域健康度置零，验证备选来自独立故障域。

路由计划只定义优先顺序，额外尝试如何发生由回退、重试与对冲决定；熔断与故障隔离提供健康和容量信号。三者分离后，可以修改重试预算而不改变模型评分，也能熔断某个部署而不重写产品请求。

小结

  • 先应用不可违反的硬约束，再对合格部署做多目标排序。
  • 路由对象是具体部署，不是抽象模型名；区域、账户和配额属于部署属性。
  • 总分必须保留质量、延迟、成本和风险分量，支持事后解释。
  • 粘性、缓存与探索都是策略工具，不能越过能力和合规边界。
  • 路由器保持纯函数，执行器负责原子准入与远端调用。
  • 用回放、属性测试和独立故障域注入验证路由策略，而不是只测一个成功示例。
