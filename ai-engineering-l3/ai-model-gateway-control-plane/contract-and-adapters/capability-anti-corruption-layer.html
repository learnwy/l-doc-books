能力协商与供应商反腐层

供应商兼容端点可以降低接入成本，却无法消除能力差异。同名参数可能被忽略，同一种“工具调用”可能有不同的内容块规则，同一个模型在不同托管平台上还会受到区域、配额和安全配置影响。反腐层的工作不是美化 JSON，而是阻止外部语义悄悄改写内部领域模型。

核心概念

反腐层位于规范契约与官方 SDK 之间，由能力目录、请求编码器、事件解码器和误差账本组成。路由器先用能力目录筛掉不满足必需条件的部署；适配器随后翻译一次已确定的尝试；误差账本记录任何无法无损映射的字段。

flowchart LR
    Canonical[规范请求] --> Negotiate[能力协商]
    Catalog[部署能力快照] --> Negotiate
    Negotiate -->|满足| Encode[供应商编码器]
    Negotiate -->|不满足| Reject[能力错误]
    Encode --> SDK[官方 SDK 或 HTTP]
    SDK --> Decode[事件解码器]
    Decode --> Events[规范事件]
    Encode --> Loss[语义误差账本]
    Decode --> Loss

能力值不应只是布尔值。可靠目录至少区分 supported、unsupported 与 unknown，并附带约束、验证时间、来源和部署范围。unknown 不能被乐观地当作支持；对必需能力应拒绝，对偏好能力可按明确策略降级。

能力状态 必需能力处理 偏好能力处理 证据要求
supported 进入候选集 进入候选集 文档加探针或契约测试
unsupported 排除并说明原因 可降级并告警 官方限制或稳定失败样本
unknown 默认排除 仅在授权策略下尝试 标记最后验证时间
degraded 只有调用方接受才可用 可纳入但加惩罚 明确丢失的保证

能力目录不是产品清单

模型目录需要描述可执行部署，而不仅是市场上的模型名。相同模型在供应商直连、云托管和不同区域上可能有不同端点、上下文限制、工具能力、数据保留和配额。能力键应绑定 deployment_id 与配置版本，并记录来源：官方声明、主动探针、生产观测或人工覆盖。

目录中的约束可以是数值、集合或结构，例如最大上下文、支持的媒体类型、JSON Schema 子集、并行工具调用数、可用区域和流式用量是否可得。路由匹配先做硬约束，再用质量、成本和健康度排序；不要让路由器自己猜某个模型家族的能力。

主动探针使用无敏感数据的小请求，验证鉴权、基础生成、流式完成、工具参数和结构化输出。探针成功不代表所有输入都支持，因此它与官方文档、契约测试是互补证据。任何探针变更都要限速，避免把健康检查变成供应商流量攻击。

编码、解码与误差账本

请求编码器从规范模型生成供应商请求，必须对每个字段做三选一：无损映射、经授权转换、显式拒绝。禁止默认丢弃未知字段。适配器可以应用供应商要求的消息重排或工具包装，但转换规则应有单元测试和版本号。

export type MappingOutcome<T> =
  | { kind: 'exact'; value: T }
  | { kind: 'degraded'; value: T; warning: SemanticWarning }
  | { kind: 'unsupported'; capability: string; reason: string };

export interface ProviderCodec<Request, Event> {
  encode(input: CanonicalRequest, capabilities: CapabilitySnapshot): MappingOutcome<Request>;
  decode(event: Event, state: DecodeState): readonly CanonicalEvent[];
}

解码器是有状态的，因为流事件可能分片。状态只属于一次尝试，包括文本块索引、工具参数缓冲、最后序号和是否收到终止事件；它不能共享到其他租户或请求。遇到未知事件类型时，适配器可记录诊断并根据契约版本决定忽略或失败，但不能把未知载荷直接发给客户端。

误差账本随尝试保存。例如某部署不支持 strict_schema，策略允许退化为“提示加返回后校验”，账本记录保证从“受约束解码”降为“生成后验证”、使用的修复次数和最终是否满足 Schema。这样质量下降、额外成本和路由决策能够关联。

专有能力的受控扩展

最小公分母会阻碍供应商创新，任意透传则摧毁可移植性。折中方案是命名空间扩展，例如 provider.example.reasoning_profile/v1，并要求扩展定义输入 Schema、可用部署、数据风险、回退行为和观测字段。扩展只能被授权租户调用，不能覆盖核心字段。

调用方请求专有扩展时，路由候选自然收窄；如果没有满足条件的部署，结果应是能力不支持，而不是改用另一家供应商并删除扩展。若产品希望有回退路径，应在意图层定义两个可验收方案，而不是依赖适配器猜测。

方案 可移植性 能力完整度 适用场景
只用核心契约 高 中 多供应商通用功能
命名空间扩展 中 高 明确绑定且可治理的高级能力
原始 JSON 透传 低 表面最高 不适合作为共享平台接口
单独供应商通道 低但诚实 最高 无法合理抽象的独立产品

适配器测试与变更检测

每个适配器需要四类测试。编码快照验证规范请求如何落到供应商字段；解码轨迹验证文本、工具、错误与用量事件；负面能力测试证明不支持参数不会被静默丢弃；在线合成探针捕获文档未宣布的行为变化。离线测试必须可在没有供应商凭证时运行。

黄金轨迹应保存最小化、脱敏的事件序列，而不是完整用户 Prompt。测试覆盖正常完成、工具参数跨片、内容阻断、服务端中断、缺失尾事件、重复序号和客户端取消。供应商 SDK 升级时先运行全套轨迹，再以影子流量比较新旧适配器。

适配器返回的原始错误需要限长与脱敏。诊断字段可保存供应商请求标识、HTTP 状态和稳定错误码，但不得默认保存完整请求正文、工具结果或认证头。OpenTelemetry 的生成式 AI 约定明确提示工具参数与结果可能包含敏感数据，这应直接影响默认采集策略。

现实接口的校准

截至 2026 年，多家平台公开提供统一或兼容调用面，同时保留专有字段。Amazon Bedrock 的 Converse API 提供跨模型的共同接口，并通过 additionalModelRequestFields 暴露模型专有参数；官方 Converse 文档正好展示核心契约加扩展的形态。

Google Vertex AI 的OpenAI 库兼容文档说明兼容入口主要用于降低切换代码成本，同时建议新接入优先考虑其原生 SDK。微软的模型推理参考甚至用 parameter_not_supported 展示统一 API 下的能力差异；这类明确失败比静默忽略更适合成为反腐层行为。

供应商文档只能作为能力证据之一。能力可能按模型、区域、账户层级或端点变化，因此控制平面要给目录设置有效期，并在发布前执行探针。文档宣称支持但探针失败时，健康状态应暂时覆盖静态声明，同时保留冲突证据供人工核查。

实施顺序与退出标准

第一步只实现一个狭窄核心：文本、多轮角色、基本流式、终止原因和总用量。第二步引入工具内容块与稳定调用标识。第三步建立能力目录和必需/偏好协商。第四步再开放结构化输出、多模态与供应商扩展。先追求完整接口再补证据，通常会产生大量未经测试的“支持”。

反腐层的退出标准不是“成功请求过一次”，而是：共同契约套件在所有适配器通过；每个公开能力有来源与验证时间；不支持字段会在远端调用前失败；每次降级进入响应警告与遥测；SDK 升级可通过黄金轨迹比较。

能力协商为下一章的路由与放置提供候选集，而规范生成契约定义映射目标。保持这两个方向单向依赖，可以更换路由算法而不重写适配器，也可以跟进供应商协议而不改变产品意图。

小结

  • 反腐层隔离外部协议，不负责跨供应商路由或业务编排。
  • 能力状态至少包含支持、不支持、未知和降级，并绑定具体部署。
  • 每个字段必须无损映射、授权降级或显式拒绝，禁止静默删除。
  • 专有能力使用版本化命名空间扩展，而不是无约束 JSON 透传。
  • 用黄金轨迹、负面测试和在线合成探针共同验证适配器。
  • 能力目录带证据和有效期，成为路由硬约束的唯一来源。
