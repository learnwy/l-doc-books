规范生成与流式契约

供应商之间真正难统一的并非字段拼写，而是生命周期：有的接口一次返回完整对象，有的把文本、工具参数和用量拆成不同事件；有的工具结果属于用户消息，有的拥有独立内容块；有的在开始时就知道模型版本，有的到结束才返回实际部署。规范契约必须保留这些因果关系，而不是只提供一个文本字符串。

核心概念

稳定契约分为请求、事件流和完成摘要三层。请求表达调用方可声明的意图；事件流描述执行过程中已经发生的事实；完成摘要汇总最终状态、用量与降级。三层共享稳定标识，却允许供应商适配器按自己的节奏产生事件。

规范化不是抹平差异，而是给差异一个稳定位置。共同语义进入核心字段；无法无损表达的能力进入带命名空间的扩展；不支持的必需能力在执行前失败；允许降级的可选能力产生机器可读警告。调用方因此知道自己获得了什么，而不是把 HTTP 200 当成语义成功。

契约部分 必需信息 禁止的捷径
请求 租户、意图、内容块、能力需求、时限 直接接受供应商请求对象
流事件 类型、序号、时间、尝试标识、载荷 把所有事件拼成匿名字符串
完成摘要 终止原因、实际模型、用量、警告 只返回最后一段文本
错误 阶段、类别、可重试性、未知提交状态 仅透传供应商错误码
扩展 命名空间、版本、能力声明 任意 JSON 逃生口

请求领域模型

内容应是带类型的块，而不是只允许文本。常见块包括文本、图像引用、文件引用和上一轮工具结果。引用对象需要声明媒体类型、大小、内容哈希和数据分类；网关在策略阶段决定是否允许把它发送到候选区域。原始二进制可以经受控对象存储交换，避免在每一层日志中复制。

工具定义包含稳定名称、描述、输入 JSON Schema、风险等级和执行归属。模型网关只把定义传给模型并规范化工具调用，不执行工具本身。工具执行由拥有领域权限的运行时完成，结果通过 tool_call_id 回填。这样模型供应商的“客户端工具”与“服务器工具”差异不会混淆组织内部的授权边界。

export type CapabilityRequirement = {
  name: 'tools' | 'strict_schema' | 'vision' | 'streaming' | 'data_region';
  level: 'required' | 'preferred';
  value?: string;
};

export type CanonicalRequest = {
  requestId: string;
  tenantId: string;
  intent: string;
  input: readonly ContentBlock[];
  tools: readonly ToolDefinition[];
  requirements: readonly CapabilityRequirement[];
  limits: {
    deadlineAt: string;
    maxOutputTokens: number;
    maxAttempts: number;
  };
};

温度、采样和推理强度等参数不应全部成为公共必填字段。它们跨模型的语义并不稳定。更可靠的方式是由意图映射到平台维护的生成档位，例如 deterministic_extract、balanced_chat、deep_reasoning，再由部署配置翻译为供应商参数。高级调用方可以请求已登记的 profile，但不能绕过策略任意注入参数。

流式事件与取消语义

流式契约必须把“输出增量”和“完成确认”分开。客户端看到文本不代表请求已完成；最终用量、终止原因和安全阻断可能只在尾事件出现。每个事件需要单调递增的 sequence，但不要求所有尝试共享一个序列。网关对外只发布胜出尝试的内容，内部仍记录被取消对冲请求的计费事实。

事件类型至少包括 request.accepted、attempt.started、output.delta、tool_call.delta、tool_call.ready、usage.reported、attempt.failed、request.completed 与 request.cancelled。适配器可把供应商更细的事件合并，却不能在参数 JSON 尚未闭合时伪造 tool_call.ready。

取消是双向协议。下游断开连接时，网关取消未完成尝试并停止向客户端写入；上游若不支持可靠取消，网关将尝试标为 cancel_requested，继续接收或丢弃剩余字节，同时保留最终用量。将“客户端不再读取”误当成“供应商不再计费”，会造成无法解释的成本差异。

背压也属于契约。客户端消费过慢时，网关不能无限缓冲 Token；它应限制每个流的内存、设置空闲写超时，并在超过阈值时取消或截断。流终止需要明确是模型正常停止、达到限制、策略阻断、客户端取消、网关超时还是供应商错误。

工具调用与结构化输出

工具调用由标识、名称和参数组成。参数可能以多个增量到达，因此适配器先累积字节，再在 ready 阶段解析 JSON、验证 Schema 和大小。解析失败是协议错误，不应交给工具执行器“尽量猜”。并行工具调用以独立 tool_call_id 关联结果，绝不能依赖数组位置。

结构化输出需要区分“JSON 可解析”和“满足指定 Schema”。某些供应商支持受约束解码，另一些只提供 JSON 模式或普通文本。调用方若把 strict_schema 标记为必需，只有能力目录确认支持时才可路由；若只是偏好，降级到验证加修复循环也必须产生 semantic_degradation 警告并计入额外尝试预算。

终止原因 是否成功 通常可重试 调用方动作

length_limit 部分 视意图 续写或提高上限需新决策

错误、警告与用量

规范错误同时保留稳定类别和受限的供应商诊断。类别可包括认证失败、策略拒绝、能力不支持、输入无效、配额耗尽、供应商过载、连接失败、协议损坏、超时和内部错误。retryable 不是错误类别的固定属性，而是结合阶段、幂等性、剩余时限和尝试预算计算出的决策。

警告代表调用成功但保证发生变化，例如区域回退、低等级模型、严格 Schema 降级、内容截断或用量估算。警告必须进入响应与遥测，产品可以决定是否向用户展示。网关不应把降级隐藏在内部日志里。

用量模型至少分别记录输入、缓存读取、缓存创建、输出、推理和供应商工具调用；缺失项标记为未知而非零。OpenTelemetry 当前的生成式 AI 属性规范也提醒工具参数与结果可能包含敏感数据，并建议用量包含缓存分项；可参考官方 GenAI 属性注册表。

版本化与契约测试

公共契约采用向后兼容的版本演进：增加可选事件类型或字段可以在小版本发布，改变终止语义、默认值或必需字段则需要大版本。消费者必须忽略未知可选字段，但不能忽略未知的终止状态。对流式协议，事件序列合法性比单个 JSON Schema 更重要，应使用状态机测试。

契约测试分三层。第一层用供应商录制样本验证适配器映射；第二层生成乱序、重复、截断和缺尾事件，验证状态机拒绝非法流；第三层对所有适配器运行同一组抽象用例，例如工具参数分片、客户端取消和尾部用量。测试数据只保存脱敏或合成内容。

OpenAI 的 Responses 流式参考列出带序号的服务器事件与尾部用量，官方事件文档可用于校准事件生命周期；Anthropic 的工具协议使用 tool_use 与 tool_result 内容块，说明供应商之间存在结构差异。契约的目标是忠实映射，而不是声称它们原生相同。

完成本契约后，应继续实现能力反腐层，并回看网关责任边界确认没有把业务编排塞入协议。一个可靠验收项是：给定同一规范请求和两段等价供应商轨迹，完成摘要在共同语义上相同，同时专有差异以扩展或警告保存。

小结

  • 规范契约由请求、事件流和完成摘要三层组成，不能退化为文本字符串。
  • 能力需求分为必需与偏好，任何降级都要产生机器可读警告。
  • 工具参数完成后才可解析与校验，并用稳定调用标识关联结果。
  • 取消、背压、尾部用量和未知提交状态都是流式契约的一部分。
  • 用量缺失应标为未知；错误可重试性由上下文计算，不由错误码硬编码。
  • 通过状态机与跨适配器契约套件证明语义，而不是依赖类型名称相似。
