模型网关的责任边界

把三家模型 SDK 包进一个 switch，只能算连接器；真正的模型网关必须让应用、平台和供应商分别拥有自己的变化理由。应用在意“完成一项受约束的任务”，平台在意“怎样合规、经济、可靠地执行”，供应商 SDK 则在意某个远端协议的字段、鉴权与事件细节。边界清楚，供应商变化才不会反向污染产品域。

核心概念

模型网关同时包含数据面与控制平面。数据面位于同步调用路径，负责准入、解析策略快照、选择候选、执行调用、规范化结果和记录事实；控制平面不承载每个 Token，却拥有模型目录、路由策略、租户预算、凭证引用、发布版本和回滚指针。

flowchart LR
    App[产品应用] --> Intent[意图 API]
    Intent --> Data[网关数据面]
    Control[网关控制平面] --> Snapshot[不可变策略快照]
    Snapshot --> Data
    Data --> Adapter[供应商适配器]
    Adapter --> Provider[模型供应商]
    Data --> Evidence[遥测与审计事实]
    Evidence --> Control

边界的判断标准不是“代码放在哪个仓库”，而是谁能在不协调其他所有者的情况下改变它。产品团队可以改变任务意图与用户体验；平台团队可以改变路由和预算；适配器团队可以跟进供应商协议。三个变化方向通过版本化契约相接，而不是共享供应商对象。

决策 首要所有者 不应泄漏到 说明
任务是否允许低质量降级 产品域 供应商适配器 这是业务风险，不是网络策略
某租户每分钟可消耗多少 Token 控制平面 产品页面逻辑 预算应集中治理并可动态调整

数据面与控制平面

数据面的第一原则是有界工作。一次请求只能读取一个已经发布的策略快照，不能在调用中途重新解释不断变化的配置。快照至少包含版本、模型别名解析、能力约束、路由规则、预算和安全策略哈希。这样同一个 decision_id 可以回答“当时为什么选中这个部署”，而不是用当前配置猜测过去。

控制平面负责写入与验证，却不应成为每次生成请求的同步依赖。配置发布可以经过模式校验、静态冲突检测、离线评测与审批，然后生成不可变快照分发到数据面。若控制平面短暂不可用，数据面继续使用最后一个已验证版本；若快照过期超过风险容忍窗口，再按策略拒绝或进入明示降级，而不是静默拉取半成品配置。

控制平面通常还需要模型目录。目录中的“模型”不是一个字符串，而是一组可寻址部署：供应商、区域、账户、版本、能力、上下文限制、数据策略、价格生效区间和健康状态。业务请求引用稳定的意图或模型类别，路由器再把它解析为某个部署。直接让业务持久化供应商模型名，会把供应链拓扑变成产品数据。

网关与供应商 SDK 的分界

供应商 SDK 很适合处理签名、HTTP 序列化、重连和官方类型，但它不是组织级领域模型。网关可以在适配器内部使用官方 SDK，却不应把 SDK 的请求或响应类型作为公共接口返回。否则一次 SDK 大版本升级会穿透所有调用方，供应商专有的默认值还会变成隐形业务规则。

公共接口应表达意图与约束，例如任务类别、所需模态、是否允许工具、最大输出、端到端时限、数据区域和降级等级。它不接受“请调用供应商甲的某个端点并把未知字段原样转发”这种越权表达。确实需要专有能力时，可以使用受控扩展：扩展带命名空间、能力声明和显式失败语义，并由策略决定哪些租户可用。

网关也不应该吞下产品编排。多轮业务状态、用户确认、工具的领域权限和最终产品文案仍属于应用或 Agent 运行时。网关只保证单次模型交换及其受控尝试；若它开始理解退款流程、招聘决策或代码合并状态，就已经跨越 bounded context。

按变化原因组织模块

一个可维护的实现通常包含六个深模块，而不是一个巨大代理类：入口把传输协议转换为规范请求；策略解析器产生准入与路由计划；执行器管理尝试预算和取消；适配器翻译供应商协议；计量器汇总事实；证据汇写入追踪、成本与审计管道。它们通过小接口组合，禁止横向读取彼此数据库。

export type GatewayRequest = {
  tenantId: string;
  intent: string;
  deadlineAt: string;
  input: readonly ContentBlock[];
};

export type ExecutionPlan = {
  decisionId: string;
  policyVersion: string;
  candidates: readonly DeploymentTarget[];
  attemptBudget: number;
};

export interface PolicyResolver {
  resolve(request: GatewayRequest): Promise<ExecutionPlan>;
}

export interface ProviderAdapter {
  execute(plan: ProviderAttempt): AsyncIterable<CanonicalEvent>;
}

这里的 PolicyResolver 只做查询，不执行远端调用；ProviderAdapter 只翻译一次尝试，不做跨供应商路由。命令与查询分离后，测试可以分别证明策略选择和协议转换，而无需在一个测试里模拟整个世界。

常见越界与纠偏

越界症状 直接后果 纠偏动作
调用方传供应商 API Key 凭证扩散、无法统一轮换 改为租户身份加凭证引用
适配器自行决定回退模型 路由不可解释、预算失控 适配器只返回规范结果与错误
网关保存完整业务会话 数据责任膨胀 仅保存执行所需状态与证据
控制平面在热路径查数据库 尾延迟与故障耦合 发布不可变快照到数据面
公共响应透传供应商 JSON 调用方绑定供应商语义 返回规范字段，原始诊断受控封装
通用 HTTP 网关承担 Token 语义 无法按用量准入与取消 把 L7 边缘层和模型语义层分开

“统一接口”最危险的失败方式是表面统一、实际静默。某供应商不支持严格 JSON Schema 时，适配器若悄悄删除该字段，请求仍可能成功但业务保证已经消失。正确行为是让能力检查在执行前给出 unsupported_capability，或让产品策略明确授权一种可观察的降级。

决策记录与验收

边界设计应通过行为证据验收。第一组契约测试确保公共类型不依赖任何供应商包；第二组适配器测试用录制的事件序列验证翻译；第三组策略测试证明相同快照与相同输入产生相同计划；第四组故障测试证明控制平面离线时数据面仍按最后发布版本工作。

每次调用至少产生 request_id、decision_id、attempt_id 和 policy_version。request_id 关联用户体验，decision_id 解释选择，attempt_id 区分回退或对冲产生的远端调用。把三个标识混成一个，会让一次逻辑请求的多次供应商计费无法对账。

实现下一步应继续定义规范生成契约，再用能力反腐层约束每个供应商适配器。边界文件本身可以写成架构决策记录，并列出“不属于网关”的反向清单，防止平台在便利驱动下无限扩张。

截至 2026 年，官方平台也在同时提供原生接口与兼容接口：Amazon Bedrock 明确区分 Converse、Invoke、Responses 和 Chat Completions 等调用面，其接口选择文档展示了“共同形状”和“完整能力”并存；微软则建议新集成转向 OpenAI v1 兼容面，同时指出不同部署可能返回能力不支持，端点文档说明了这种差异。它们共同证明网关不能把“兼容”误解为“语义完全相同”。

小结

  • 产品域拥有业务意图，控制平面拥有组织策略，适配器拥有供应商协议。
  • 数据面使用不可变策略快照，控制平面不应成为每次调用的同步依赖。
  • 官方 SDK 可以留在适配器内部，但不得成为公共领域类型。
  • 路由、适配、计量和审计按变化原因分开，使用小接口组合。
  • 专有能力必须显式协商，任何语义损失都不能静默发生。
  • 用逻辑请求、路由决策和供应商尝试三个标识保存完整因果链。
