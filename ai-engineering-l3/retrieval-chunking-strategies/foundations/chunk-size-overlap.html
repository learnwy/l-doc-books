Part II · Agent Construction检索分块策略基础分块粒度与重叠

分块粒度与重叠

把块大小从 256 调到 1024、再给相邻块留 15% 的重叠，听起来像随手拧的两个旋钮，实则是分块里最关乎成败的两个数字。它们背后是一对无法同时满足的诉求：块要够小，嵌入才锐利、召回才精准；块又要够大，检索回来才装得下完整答案。这一篇把这对权衡量化，把「该多大、要不要重叠、按什么计量」讲透，但不涉及具体切法——那是「方法」章的事。

核心概念

块大小（chunk size）与重叠（overlap）共同决定了每个检索单位「装多少、和邻居共享多少」。块大小定的是单元的语义粒度；重叠定的是相邻块之间冗余共享的尾首长度，用来对冲「答案恰好被边界切成两半」的风险。二者与检索质量的关系不是单调的，而是各有一个甜区。

flowchart TD
  A[块大小 chunk size] --> B[太小: 嵌入锐利<br/>但单块上下文不足]
  A --> C[太大: 上下文充足<br/>但嵌入被稀释/召回钝]
  B --> D[甜区: 主题单一且自足]
  C --> D
  E[重叠 overlap] --> F[过小: 答案被边界腰斩]
  E --> G[过大: 召回重复/索引膨胀]
  F --> H[甜区: 10-20% 跨边界保险]
  G --> H
  D --> I[可评测的分块配置]
  H --> I

下表给出可用于建立基线的经验区间，而不是跨语料通用的结论。2026 年的系统复现表明，最优策略会随「文档内定位」与「跨语料检索」等任务设定而改变；LREC 2026 的自适应研究也直接按文档指标选择不同切法，而非固定一种配置（Adaptive Chunking）。

内容类型 推荐块大小 推荐重叠 依据/说明
通用散文/网页 约 512 token 10–20% 可复现的起调基线
技术文档/手册 512–1024 token 10–15% 段落较长，适度放大
法律/医疗条款 按逻辑边界，常 256–512 15–20% 跨条款风险高，重叠偏大

代码 按函数/类，非定长 结构边界处 见「多模态分块」专篇

块大小的甜区在哪

块大小的两端都有明确代价。偏小一端，嵌入向量锐利、召回精准，但单块往往装不下完整答案；偏大一端，单块主题混杂、向量被稀释，召回时谁都不像——这就是上一篇 为何分块 讲的语义稀释。NAACL 2025 的对照实验提醒我们，语义上更漂亮的边界并不自动转化为更好的检索式问答结果，必须同时观察检索与生成两层（Qu 等，2025）。

经验甜区落在「一个块恰好覆盖一个自足的语义单元」。约 512 token、10–20% 重叠适合作为通用文本的第一条基线，但不是推荐答案；FAQ 一问一答即自足，法律条款则一条可能跨数段。2026 年的复现研究进一步区分了分割方法与嵌入时机，并发现不同检索设定的赢家不同（Beyond Chunk-Then-Embed）。所以这些数字只负责启动实验，真正的最优要靠 分块评测 量出来。

重叠是跨边界的保险

重叠解决的是一个具体而致命的问题：答案恰好横跨两个块的边界，被切成上半句在 A 块、下半句在 B 块，结果检索任一块都拿不到完整答案。让相邻块共享一段尾首文本（比如 B 块开头重复 A 块结尾的 50 个 token），就给跨边界的内容上了一道保险——无论检索命中 A 还是 B，关键句都不会缺一半。

重叠也有代价。重叠越大，同一段文字会出现在越多块里，检索时可能召回多个高度重复的块，挤占了本可留给其它信息的名额，索引体积也随之膨胀。设重叠比例为 rrr、块大小为 sss，则每前进一个块实际新增的内容只有 s⋅(1−r)s \cdot (1 - r)s⋅(1−r) 个 token，总块数约为 N≈L/(s⋅(1−r))N \approx L / (s \cdot (1 - r))N≈L/(s⋅(1−r))，其中 LLL 是文档总长。可见 rrr 从 0.1 升到 0.3，块数会膨胀约 28%，召回重复与成本同步上升。经验区间是 10–20%，问答类自足内容则常设为 0。重叠制造的重复污染是常见坑，详见 分块陷阱。

token 还是字符：计量方式的陷阱

切块时按什么计长度，看似细节，实则影响一致性。按字符数切实现简单，但同样 500 字符的英文与中文，token 数差异巨大——嵌入模型与生成模型都按 token 计费和限长，按字符切会让实际 token 数在不同语言、不同内容间剧烈漂移。按 token 切则与模型真实约束对齐，但需要先用对应的分词器算长度，略增开销。

实践上推荐按 token 计量，并且用与下游嵌入模型同一套分词器：若用一种分词器切块、另一种嵌入，块的真实 token 数可能超出嵌入模型的最大输入长度而被静默截断，丢失尾部内容。这类「计量与模型不一致」的隐性截断，是上线后最难排查的问题之一。入库前应记录 tokenizer_id、token_count 与 max_input_tokens，并把超限当成失败，而不是让 SDK 隐式截断。

用可执行窗口验证重叠不变量

重叠实现最常见的错误不是比例选错，而是步长为零、尾块重复或最后一段丢失。下面的函数接收已经由目标分词器切出的 token 数组，输出带原始区间的窗口；它可直接用于单元测试，也让 sss 与 rrr 的关系不再藏在 SDK 默认值里。

type TokenWindow = { start: number; end: number; tokens: string[] };

function chunkTokens(tokens: string[], size: number, overlap: number): TokenWindow[] {
  if (size <= 0 || overlap < 0 || overlap >= size) throw new Error('invalid window');
  const step = size - overlap;
  const windows: TokenWindow[] = [];

  for (let start = 0; start < tokens.length; start += step) {
    const end = Math.min(start + size, tokens.length);
    windows.push({ start, end, tokens: tokens.slice(start, end) });
    if (end === tokens.length) break;
  }

  return windows;
}

至少验证四个性质：每个窗口长度不超过 size；相邻窗口共享恰好 overlap 个 token；第一个窗口从 0 开始；最后一个窗口覆盖 tokens.length。这些结构不变量通过后，再用 分块评测 判断重叠是否真的提高 Recall@k，避免把「代码切对了」误当成「业务配置最优」。

小结

  • 块大小是一对张力的旋钮：太小则上下文不足，太大则嵌入被稀释，甜区在「一个块覆盖一个自足语义单元」。
  • 约 512 token + 10–20% 重叠可以作为通用文本基线，但最优配置取决于语料、任务与检索设定。
  • 重叠是跨边界保险，对冲「答案被切成两半」；但 rrr 越大块数越膨胀（N≈L/(s(1−r))N \approx L/(s(1-r))N≈L/(s(1−r))），召回重复与成本上升，问答类常设 0。
  • 按 token 而非字符计量，且与下游嵌入模型用同一分词器，否则会触发隐性截断。
  • 继续阅读本 hub 的 为何分块、分块评测 与 分块陷阱。
