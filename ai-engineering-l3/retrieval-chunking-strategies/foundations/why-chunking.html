Part II · Agent Construction检索分块策略基础为何分块

为何分块

假设你有一份 80 页的产品手册，用户问「保修期内电池鼓包能不能免费换」。把整份手册塞进模型上下文、让它自己找答案，听起来最省事，实际上几乎处处碰壁：上下文塞不下、塞得下也读不准、还贵得离谱。分块（chunking）就是为绕开这一连串约束而生——它把文档切成若干主题相对单一的小单元，让检索系统只把真正相关的那几块送到模型面前。这一篇讲清「为什么必须切」，不涉及任何具体切法。

核心概念

分块的必要性由三个独立约束共同逼出，缺一不可。第一是上下文窗口的物理上限：模型一次能读的 token 有限，长文档根本塞不进去。第二是检索粒度：检索的最小单位就是块，块太大则一次召回里夹带大量无关内容，块太小则单块语义不完整。第三是嵌入向量的语义稀释：把一大段多主题文本压成一个固定维度向量，等于把多个语义平均掉，检索时谁都不像。三者关系如下。

flowchart TD
  A[原始长文档] --> B{为何不能整篇用?}
  B --> C[上下文窗口<br/>塞不下/读不准]
  B --> D[检索粒度<br/>整篇是同一个召回单位]
  B --> E[嵌入稀释<br/>多主题被平均成一个向量]
  C --> F[分块: 切成主题单一的小单元]
  D --> F
  E --> F
  F --> G[检索只送相关块进上下文]
  G --> H[更准/更省/更可控的答案]

下表把「整篇直接用」与「分块后检索」放在同一标尺下对比。

维度 整篇文档直接喂模型 分块 + 检索
上下文占用 整篇，常超窗口 仅相关几块，可控
检索粒度 文档级（要么全要么不要） 块级（精确定位）
嵌入语义 多主题被平均稀释 单块主题集中，向量锐利
推理成本 随文档长度线性增长 与文档总量解耦
答案可溯源 难定位到具体段落 直接指向命中块
多文档场景 几乎不可行 天然支持

上下文窗口不是免费的容器

截至 2026 年，长上下文能力并没有消除分块的必要性。答案藏在「塞得下」与「读得准」之间的鸿沟里：有效信息被埋进大量无关文本后，模型仍可能漏读，检索也失去了把相关证据排到前面的机会。上下文窗口是容量上限，不是相关性排序器；它不能替代一个可度量的证据选择过程。

更现实的是成本。推理成本与输入 token 数直接相关，把 80 页手册作为每次查询的固定输入，意味着每一个问题都要为 79 页无关内容付费。分块加检索把「读多少」与「文档多大」解耦：无论手册是 80 页还是 8000 页，每次只送进相关的几块。长上下文与检索因此是互补关系：前者扩大单次可读范围，后者负责从大语料中选择、排序与追溯证据。

检索的最小单位就是块

检索系统不会「读懂」整篇文档再挑句子，它只在你预先切好的单位之间做相似度比较。这意味着块的边界一旦切定，就框死了召回的分辨率。若把整篇手册当一个块，那么任何查询要么召回整篇、要么一无所获，毫无定位能力；若按页切，召回粒度到页；按段落切，粒度到段落。

这条约束的深层含义是：分块不是预处理的琐碎步骤，而是直接定义了检索系统能多精确。你切块时划下的每一道边界，都在决定「相关」与「无关」的内容会不会被绑在同一个召回单位里。一个把问题答案和无关条款切进同一块的边界，会让检索器永远无法把它们分开。块边界如何一路影响到最终答案，是下一篇 分块对检索的影响 的主题。

嵌入向量偏爱短而专的文本

把文本变成向量的嵌入模型，本质是把一段话压缩成一个固定维度的点。一段只讲「电池保修」的文字，会落在向量空间里「电池」「保修」附近，查询「电池保修」时自然命中。但若这段话同时讲了保修、退货、运输、注册四件事，压出来的向量是四个主题的某种平均——它离任何单一查询都不近，检索时谁都不像。

这就是「语义稀释」。它给块大小定了一个上界：块越大、主题越杂，向量越钝。相反的极端同样危险：为追求主题纯净而切出的原子片段，可能不足以支撑模型作答。NAACL 2025 的系统研究在文档检索、证据检索和检索式问答三类任务上发现，语义分块的额外计算成本并未换来一致收益（Qu 等，2025）。可见「为单一主题而切」与「为完整上下文而留」本身就是一对张力，这正是 分块粒度与重叠 要量化的核心权衡。

把分块定义成可测试的工程契约

生产系统不应把块表示成一段裸字符串。最小契约至少要保留稳定 ID、来源、原文区间和模型实际看到的 token 数；这样召回错误才能回放到原文，重建索引时也能比较同一内容是否发生漂移。下面的 TypeScript 片段可以直接运行，它在入库前拒绝空块、越界块与超过嵌入上限的块。

type Chunk = {
  id: string;
  sourceId: string;
  text: string;
  start: number;
  end: number;
  tokenCount: number;
};

function assertChunk(chunk: Chunk, sourceLength: number, maxTokens: number) {
  if (!chunk.id || !chunk.sourceId) throw new Error('missing identity');
  if (!chunk.text.trim()) throw new Error('empty chunk');
  if (chunk.start < 0 || chunk.end > sourceLength || chunk.start >= chunk.end) {
    throw new Error('invalid source range');
  }
  if (chunk.tokenCount <= 0 || chunk.tokenCount > maxTokens) {
    throw new Error('invalid token count');
  }
}

这份契约建立了四个可验证不变量：块可定位回原文、块可稳定去重、块不会被嵌入模型静默截断、块内容不为空。后续所有高级切法都只是在决定 start 与 end，而不应绕过这些不变量。相关性和完整性仍由 分块对检索的影响 中的指标验证，结构正确只代表具备进入评测的资格。

小结

  • 分块由三个独立约束共同逼出：上下文窗口塞不下、检索以块为最小粒度、大块嵌入被语义稀释。
  • 长上下文模型不能取代分块：有效信息埋在超长上下文里会触发「上下文腐烂」，且每次为无关内容付费成本高昂。
  • 块边界一旦切定，就框死了检索的分辨率——分块直接定义了系统能多精确。
  • 嵌入偏爱短而专的文本，但切得过碎又会内容不足，「主题纯净」与「上下文完整」是贯穿全 hub 的核心张力。
