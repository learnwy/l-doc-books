结构感知分块

一份 Markdown 技术文档已经替你把内容组织好了：## 是章、### 是节、列表是步骤、代码块是示例。既然边界白纸黑字写着，就不必先调用嵌入或生成模型去猜。结构感知分块（structure-aware chunking）的思路就是顺着标题层级、HTML 标签与页面版面切，把天然章节当作优先边界。对技术文档、API 文档和规整网页，这通常是应先评测的方案。

核心概念

结构感知分块的前提是文档带有可解析的显式结构，方法是用对应的解析器识别结构标记、在结构边界处切分，并把结构信息（如所属标题路径）作为元数据挂在块上。不同格式有不同的切分器：Markdown 按标题级别（#/##/###），HTML 按标签（<h1>/<section>/<table>），PDF 按版面区块（标题、正文、表格、页眉页脚）。

flowchart TD
  A[结构化文档] --> B{识别格式}
  B -->|Markdown| C[按 #/##/### 标题切]
  B -->|HTML| D[按 h1/section/table 标签切]
  B -->|PDF| E[按版面区块切]
  C --> F[块 + 标题路径元数据]
  D --> F
  E --> F
  F --> G{块仍超长?}
  G -->|是| H[在块内再递归切分]
  G -->|否| I[输出结构块]
  H --> I

下表对比三类结构感知切分的要点。

格式 切分依据 典型工具/解析器 注意点
Markdown 标题级别 #/##/### Markdown Header Splitter 保留标题路径作元数据
HTML 语义标签 section/article/table HTML 切分器 先去脚本/样式/导航噪声
PDF 版面区块、字号、坐标 版面解析（LlamaParse 等） 双栏/扫描件需 OCR + 版面还原

Markdown 标题切分：把目录当边界

Markdown 是结构感知分块最受益的格式。标题切分器（header splitter）解析标题层级，在每个标题处开新块，并把从根到当前标题的完整路径作为元数据保存，例如 {"h1": "保修政策", "h2": "电池", "h3": "鼓包处理"}。这条路径有双重价值：一是检索时可按标题过滤（只在「保修政策」下检索），二是把它拼回块文本开头能补足上下文——一个只写「需返厂检测」的块，加上「保修政策 > 电池 > 鼓包处理」的标题前缀后，嵌入向量立刻锐利得多。

这其实是一种轻量的上下文增强，与 元数据与上下文增强 讲的思路同源，但几乎零成本——结构本身就免费提供了上下文。当某个 ### 小节内容仍然超长时，做法是在该小节内部再套用 固定与递归分块 的递归切分，形成「先按结构、再按长度」的两段式，兼顾结构完整与长度可控。

HTML 与网页：先除噪再切

网页比 Markdown 脏得多。一个 HTML 页面里，真正的正文常被导航栏、侧边栏、广告、页脚、脚本、样式包围，若直接按标签切，会切出一堆「相关产品」「订阅我们」之类的噪声块，污染检索。所以 HTML 结构感知分块的第一步永远是除噪：剥掉 <script>/<style>/<nav>/<footer>，用正文抽取（如基于密度的 readability 算法）定位主内容区，再在 <article>/<section>/<h2> 等语义标签处切分。

切分时保留语义标签传达的层级，和 Markdown 一样把标题路径作元数据。一个常被忽视的细节是 <table>：HTML 表格若被当作普通文本按标签切，行列关系会丢失。表格应被识别出来单独处理，这属于 表格代码多模态分块 的范畴。处理干净的网页正文之后，还要保存清洗规则版本与原文区间，否则线上出现遗漏时无法区分是正文抽取丢失，还是切分边界错误。

PDF 与版面：最难啃的结构

PDF 是结构感知分块里最棘手的格式，因为它本质是「打印指令」而非结构化文本——字符在页面上的坐标是已知的，但「这是标题还是正文」「这是一栏还是两栏」需要从版面推断。朴素地按文本流提取 PDF，会把双栏论文的左右栏交错读串、把页眉页脚混进正文、把表格压成一行乱码。

截至 2026 年，复杂 PDF 的稳健路径依赖版面解析：先识别标题、段落、表格、图、页眉页脚等区块与阅读顺序，再重建逻辑结构、按区块切分；扫描件还需先 OCR。EMNLP 2025 的 MultiDocFusion 就把视觉区域检测、OCR、LLM 章节树重建与分层块组合成一条流水线，说明分块前的结构恢复本身就是核心步骤（MultiDocFusion）。教训是：PDF 的分块质量上限，由前置版面解析质量决定——版面没还原对，后面再好的切法都是在错误文本上切。这类错误传播是 分块陷阱 的常客。

结构优先、长度兜底的两级算法

结构边界不是取消长度约束，而是改变约束的应用顺序：先尽量保留完整区块，再只对超长区块做递归切分。下面的函数接收解析器产生的结构块，保留标题路径，并把超长块交给前一篇的递归切分器。

type StructuralBlock = { path: string[]; text: string };
type IndexedBlock = StructuralBlock & { id: string };

function splitOversized(text: string, maxLength: number): string[] {
  return Array.from({ length: Math.ceil(text.length / maxLength) }, (_, index) =>
    text.slice(index * maxLength, (index + 1) * maxLength),
  );
}

function chunkStructuralBlocks(sourceId: string, blocks: StructuralBlock[], maxLength: number): IndexedBlock[] {
  return blocks.flatMap((block, blockIndex) => {
    const parts = block.text.length <= maxLength ? [block.text] : splitOversized(block.text, maxLength);
    return parts.map((text, partIndex) => ({
      id: `${sourceId}:${blockIndex}:${partIndex}`,
      path: block.path,
      text: `${block.path.join(' > ')}\n${text}`,
    }));
  });
}

验收不应只看每块是否小于上限，还要抽样验证标题路径是否正确、表格和代码围栏是否保持完整、解析器判定的阅读顺序是否符合页面。对同一份文档保存原始解析树、规范化结构块与最终索引块三层产物，才能在质量回归时定位责任边界。

小结

  • 结构感知分块顺着文档自带的显式结构（Markdown 标题、HTML 标签、PDF 版面）切，对技术文档性价比最高，无需像语义分块那样猜边界。
  • Markdown 标题切分保留完整标题路径作元数据，拼回块开头是几乎零成本的上下文增强；超长小节内部再套递归切分。
  • HTML 必须先除噪（剥 script/nav/footer、正文抽取）再按语义标签切；表格需单独处理。
  • PDF 最难，质量上限由前置版面解析决定，双栏/扫描件需版面还原与 OCR，否则错误会向下传播。
  • 继续阅读本 hub 的 固定与递归分块、元数据与上下文增强 与 表格代码多模态分块。
