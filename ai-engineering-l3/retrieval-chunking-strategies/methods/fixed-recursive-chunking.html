Part II · Agent Construction检索分块策略方法固定与递归分块

固定与递归分块

如果只允许你先掌握一种分块方法，应该是它。固定与递归字符切分不看语义、不调用生成模型，只按长度和分隔符把文本切开——朴素，却是强基线。NAACL 2025 的系统研究发现，语义分块相对固定大小切分并没有稳定覆盖其计算成本；2026 年的大规模复现则进一步说明，简单结构方法在跨语料检索中可优于 LLM 引导方法（Qu 等，2025、2026 复现）。这一篇讲透这一类方法：怎么切、为什么够用、什么时候该升级。

核心概念

这一类方法的共同点是「不理解内容，只依赖结构性信号切分」，由简到繁分两档。固定大小切分最朴素：每 NNN 个字符或 token 切一刀，不管切在哪。递归字符切分（recursive character splitting）则聪明一档：给定一组按优先级排列的分隔符（如先按 \n\n 段落、再按 \n 行、再按 。 句、最后按空格），从最高优先级开始尝试，若切出的块仍超长就递归用下一级分隔符再切，从而尽量在「自然边界」处断开。

flowchart TD
  A[输入文本块] --> B{长度 <= 目标?}
  B -->|是| C[作为一个块输出]
  B -->|否| D[取当前级分隔符<br/>段落->行->句->词]
  D --> E[按该分隔符切分]
  E --> F{每个子块 <= 目标?}
  F -->|是| C
  F -->|否| G[降到下一级分隔符]
  G --> E

下表对比两档方法的取舍。

维度 固定大小切分 递归字符切分
是否尊重自然边界 否，可能切在词中间 是，优先在段/句边界断
实现复杂度 极低 低（一组分隔符 + 递归）
块语义完整性 较差 较好
速度 最快 几乎同样快
2026 推荐度 仅最简单场景 绝大多数场景的默认

固定大小切分：朴素但有用

固定切分就是设定一个目标长度，每到长度就切。它最大的问题是「盲切」：可能把一个单词、一个句子、甚至一个 UTF-8 多字节字符从中间劈开，产出语义破碎的块。但它也有不可替代的用处——当文本完全没有可依赖的结构（如一长串无标点的日志、OCR 出来的连续文本），或你需要绝对均匀的块长度来满足某种批处理约束时，固定切分是唯一稳定的选择。

实践中很少单独用纯固定切分，而是配合上一章 分块粒度与重叠 讲的重叠来缓解盲切：让相邻块共享一段尾首，即便某处被切坏，重叠区也能在邻块里保留完整版本。但重叠只是补救，不能根治盲切——这正是递归切分要改进的地方。

递归字符切分：尊重自然边界

递归切分的核心洞见是：文本自带层级结构（文档 → 段落 → 句子 → 词），在高层级边界断开，块的语义完整性远好于盲切。它维护一个有序分隔符列表，典型如 ["\n\n", "\n", "。", "！", "？", " ", ""]，从段落开始尝试：若按段落切后某块仍超过目标长度，就对这个超长块改用下一级（行）分隔符递归切分，逐级降级，直到所有块都不超长。

这套机制让它在「尽量不破坏语义」与「严格控制长度」之间取得了好平衡，几乎不增加推理成本。实践上可先用约 512 token 与 10–20% 重叠建立基线，再按语料评测；不要把起调值写成平台默认。对中文文本，记得把中文标点（。！？；）加进分隔符列表，否则递归会退化成按空格或字符切。

一个可运行的递归切分核心

下面的 TypeScript 实现展示核心控制流：优先使用高层分隔符，无法满足长度时逐级降级，最后才固定切分。真实系统应把 text.length 替换成目标分词器的 token 计数，但算法的不变量保持一致。

function splitRecursively(text: string, maxLength: number, separators: string[]): string[] {
  if (text.length <= maxLength) return [text];
  if (separators.length === 0) {
    return Array.from({ length: Math.ceil(text.length / maxLength) }, (_, index) =>
      text.slice(index * maxLength, (index + 1) * maxLength),
    );
  }

  const [separator, ...rest] = separators;
  const parts = separator ? text.split(separator) : [...text];
  const chunks: string[] = [];
  let current = '';

  for (const part of parts) {
    const candidate = current ? `${current}${separator}${part}` : part;
    if (candidate.length <= maxLength) {
      current = candidate;
      continue;
    }
    if (current) chunks.push(...splitRecursively(current, maxLength, rest));
    current = part;
  }

  if (current) chunks.push(...splitRecursively(current, maxLength, rest));
  return chunks.filter((chunk) => chunk.trim().length > 0);
}

const chunks = splitRecursively('第一段。第二段很长。第三段。', 8, ['\n\n', '。', '，', '']);

上线前要补三类测试：中英文标点混合时不丢字符；超长无分隔文本最终能降级完成；所有输出按顺序拼接后与输入语义等价。若还要重叠，应在递归切分完成后按 token 区间生成窗口，而不是在每一级递归里重复注入文本，否则很容易制造指数级重复。

什么时候该升级到更高级的方法

递归切分是个强默认，但不是万能。它仍然「不理解内容」：它在句号处断开，却不知道两段话是否其实在讲同一件事、该不该合并。当出现以下信号，就该考虑升级——但要先用 分块评测 确认收益盖过成本，因为更高级的方法往往慢得多、复杂得多。

升级方向取决于瓶颈在哪。若文档有清晰的标题层级（Markdown、技术手册），升级到 结构感知分块 通常立竿见影。若内容是密集交叉引用的通用散文、且递归切分的块主题混杂，可评估 语义分块，但要警惕它易碎成超短块。若问题是「召回准但单块上下文不足」，那不是切法问题，而该上 父子与窗口检索。值得强调：2026 年的基准共识是，绝大多数项目根本不需要升级，递归切分已经够好，过早上语义分块往往是得不偿失的过度工程。

小结

  • 固定与递归切分不理解内容、只依赖结构信号，却是应优先建立的强基线；复杂方法必须在同一评测集上证明收益。
  • 固定切分会盲切词/句，仅适合无结构文本或需绝对均匀块长的场景，常靠重叠缓解。
  • 递归切分按「段→行→句→词」有序分隔符逐级降级，尊重自然边界，几乎零额外成本，是通用默认；中文需把中文标点加入分隔符。
  • 升级到语义/结构/父子方法前，先用评测确认收益，多数项目无需升级——过早上语义分块常是过度工程。
