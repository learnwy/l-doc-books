Part II · Agent Construction检索分块策略进阶父子与窗口检索

父子与窗口检索

基础章反复出现的那个死结——块切小了召回准但上下文不够，切大了上下文够但召回钝——其实有一个优雅的解法：为什么非要用同一个块去「检索」和「喂模型」？父子与窗口检索（small-to-big retrieval）正是把这两件事拆开：用小块去匹配查询（嵌入锐利、召回准），命中后却把它所属的大块或周围的窗口整体送进模型（上下文充足）。这是 LlamaIndex 等框架的核心进阶能力，也是把检索质量推上一个台阶的关键杠杆。

核心概念

核心思想是「检索单位」与「喂给模型的单位」解耦。索引阶段用小块（child / sentence）算嵌入并入库，但同时记录每个小块到其父块（parent）或原文位置的映射。检索阶段，查询匹配的是小块；命中后，不直接把小块给模型，而是顺着映射取回更大的上下文——父块整体，或原句前后若干句的窗口。两种主流实现：父文档检索（parent document retriever）和句子窗口检索（sentence window retrieval）。

flowchart TD
  A[文档] --> B[切成大父块]
  B --> C[父块再切成小子块]
  C --> D[只给子块算嵌入入库]
  E[用户查询] --> F[匹配子块<br/>嵌入锐利/召回准]
  D --> F
  F --> G[顺映射取回父块/窗口]
  G --> H[把大上下文喂给模型]

下表对比两种实现。

维度 父文档检索 句子窗口检索
检索单位 小子块 单个句子

父文档检索：小块进，大块出

父文档检索（small-to-big 的经典形态）分两层切块。先把文档切成较大的父块（如整段或整节），再把每个父块切成更小的子块（如句子或短片段）。只有子块被嵌入入库，父块仅保存原文与 ID 映射。查询时匹配子块——因为子块短、主题单一，嵌入锐利、召回精准；命中某子块后，系统查出它的父块 ID，把整个父块（而非那个小子块）送进模型，于是模型拿到了充足上下文。

这一招直接拆解了 分块对检索的影响 里那条「召回准但上下文不足」的因果链：召回环节用小块保证精度，上下文环节用父块保证完整，两个环节各取所长。一个工程细节是去重——若一个父块下的多个子块同时命中，要避免把同一个父块重复送进上下文，浪费名额。另一个细节是分数聚合：同一父块命中多个子块时，可取最高子块分数用于排序，同时记录命中数作为解释信号，不应简单相加让大父块天然占优。

句子窗口检索：以命中句为中心展开

句子窗口检索把粒度推到极致：检索单位是单个句子。索引时把文档拆成句子，每句单独嵌入，同时在元数据里记录它在原文中的位置。查询匹配到某一句后，用后处理步骤把这个句子替换成它前后各 N 句组成的窗口再送给模型。LlamaIndex 当前 SentenceWindowNodeParser 的 window_size 默认值是 3，表示命中句两侧各取 3 句；这个值只是库默认，仍需按语料评测（LlamaIndex API）。

去重、扩窗与预算控制

Small-to-big 的实现难点不是查父 ID，而是多个命中如何在有限上下文预算里合并。下面的函数按父块去重，保留每个父块最高的子块分数，再按分数选择能放入预算的父块。它使「同一父块多个子块命中」不会重复占用上下文。

type ChildHit = { childId: string; parentId: string; score: number };
type Parent = { id: string; text: string; tokenCount: number };

function selectParents(hits: ChildHit[], parents: Map<string, Parent>, budget: number): Parent[] {
  const bestScore = new Map<string, number>();
  for (const hit of hits) {
    bestScore.set(hit.parentId, Math.max(bestScore.get(hit.parentId) ?? -Infinity, hit.score));
  }

  const ranked = [...bestScore.entries()].sort((a, b) => b[1] - a[1]);
  const selected: Parent[] = [];
  let used = 0;

  for (const [parentId] of ranked) {
    const parent = parents.get(parentId);
    if (!parent || used + parent.tokenCount > budget) continue;
    selected.push(parent);
    used += parent.tokenCount;
  }

  return selected;
}

窗口检索可使用相同预算逻辑，只是候选从固定父块变成原文区间。多个命中窗口相交时，应先合并区间再计 token；否则相邻句同时命中会把同一段文字重复多次。验收时同时记录子块 Recall@k、扩窗后的答案正确率、去重前后 token 数，三者才能说明 small-to-big 是否值回复杂度。

它与父文档检索的区别在于上下文边界是否「动态」。父块检索取回的是预先切定的父块，边界固定；句子窗口围绕实际命中的那一句对称展开，边界随命中位置移动，能更贴合答案所在。这让它特别适合连续散文——答案常分布在命中句紧邻的上下文里。代价是句子级嵌入数量更多、索引更大，且窗口大小 N 又是一个要调的旋钮，调法见 分块调优。

何时用父子/窗口，何时不必

父子与窗口检索不是免费的——它们增加了索引复杂度（双层映射、句子级粒度）与少量检索开销。该不该上，取决于你的瓶颈是不是「召回准但答案上下文不足」。若评测显示检索命中的块确实相关、但模型常因上下文残缺答不全，这正是它们的主场。若问题是召回本身就不准（命中的块不相关），那要回头看切法与嵌入，而非套父子结构。

选型上，有清晰层级结构的文档（技术手册、带 结构感知分块 切出的章节）适合父文档检索，父块天然就是「节」；连续叙述、问答式内容适合句子窗口。这两种结构也常与下一篇 元数据与上下文增强 叠加——父块或窗口提供「取回大上下文」，元数据增强提供「让小块嵌入更准」，二者正交、可同时用。

小结

  • 父子/窗口检索把「检索单位」与「喂模型单位」解耦：用小块召回（精准），取回大块/窗口供模型（上下文充足），直接拆解「召回准但上下文不足」死结。
  • 父文档检索只嵌入子块、命中后取回整个父块，适合有层级结构的文档；注意父块去重。
  • 句子窗口检索以单句为检索单位，命中后替换成前后各 N 句；LlamaIndex 当前默认两侧各 3 句，但应由评测决定。
  • 仅当瓶颈是「召回准但上下文不足」时才上；若召回本身不准，应回头修切法与嵌入。可与元数据增强正交叠加。
