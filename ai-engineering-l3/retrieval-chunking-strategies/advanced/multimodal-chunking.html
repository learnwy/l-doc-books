表格代码多模态分块

到目前为止的所有切法，都默认文档是连续的散文。但真实文档里塞满了非散文内容：一张跨页的财务表格、一段不能从中间断开的函数、一张「见下图」的架构图。把递归切分硬套在这些内容上，会切出语义破碎的灾难——表格被腰斩成无意义的数字行，函数被切断头尾无法编译，图片被当成一句「[图片]」彻底丢失信息。这一篇讲清表格、代码、图像这三类非线性内容各自需要的专门切法。

核心概念

非散文内容的共同特点是「语义不沿文本顺序线性排列」：表格的意义在行列的二维关系里，代码的意义在嵌套的语法结构里，图像的意义根本不在文本里。因此通用切法的「按长度在某处断开」对它们是破坏性的。处理原则是：先识别出这类区块（通常在 结构感知分块 的解析阶段），把它们从散文流里隔离出来，再用各自的专门策略处理。

  B --> C[散文]

下表给出三类内容的处理要点。

内容类型 破坏性切法的后果 专门策略
表格 行列关系丢失、表头与数据分离 整表成块；大表行级展开且每行带表头
代码 函数被腰斩、无法编译、上下文断裂 按 AST/语法边界切，函数/类为单位
图像/图表 信息彻底丢失，只剩占位符 用多模态模型转文字描述再嵌入

表格：保住行列的二维语义

表格的意义在「这一行的这个数，对应哪一列的表头」。一旦按字符或行数盲切，表头留在 A 块、数据落到 B 块，检索到 B 块的模型看到一串脱离表头的数字，完全无法解读。处理表格有两种主流策略，按表格大小选择。

小表（能整体放进一个块）直接整表成块，连同表头与说明文字一起，保持 Markdown 或 HTML 表格的完整结构。大表（行数过多、超出块大小）则行级展开：把每一行（或几行）拆成独立块，但每个块都重复携带表头，这样每个块都自带「这些数是什么」的解释，行列对应不丢。无论哪种，都应在元数据里标记 type: table 并尽量保留表格的标题/上文说明。结构解析阶段如何把表格从 PDF/HTML 里识别并抽出，已在 结构感知分块 讲过，那里用 LlamaParse 把表格抽成独立节点正是为此服务。

代码：按语法结构而非长度切

代码是另一类不能盲切的内容。按字符切代码，几乎必然把一个函数从中间劈开——前半个函数在一块、后半个在另一块，两块都不是可理解的逻辑单元，嵌入向量也无法表达「这是一个做某事的函数」。代码的语义单位是语法结构：函数、方法、类、模块。

正确做法是按语法边界切分：用语言对应的解析器识别函数、方法、类与模块的起止，以完整定义作为基本单位。块过大时，可在方法或成员边界处再切，但不要任意切进表达式。Tree-sitter 会为源码生成包含节点起止位置、父子与兄弟关系的具体语法树，其 query 可按节点类型捕获定义（Tree-sitter 官方文档）。同时保留所属文件、符号限定名、import 与原文区间，因为代码含义高度依赖命名空间。

用 cAST 做分割后合并

仅仅「每个函数一块」仍处理不了两个极端：巨型函数超过上限，许多短成员又造成碎片。EMNLP 2025 的 cAST 从 AST 根节点递归拆解超长节点，再把相邻兄弟节点在大小限制内合并，既保持结构又控制粒度；论文在 RepoEval 上把 Recall@5 提高 4.3 个点，在 SWE-bench 上把 Pass@1 提高 2.67 个点（cAST）。这些结果来自论文设置，应作为值得复现的假设，而非所有代码库的保证。

下面的 TypeScript 核心函数接收解析器输出的 AST 区间。它优先保留未超限节点；超限节点递归处理子节点；叶节点仍超限时才退化为原文窗口。真实实现应按源码 token 而非字符计长。

type AstNode = { start: number; end: number; children: AstNode[] };
type Span = { start: number; end: number };

function astSpans(node: AstNode, maxLength: number): Span[] {
  const length = node.end - node.start;
  if (length <= maxLength) return [{ start: node.start, end: node.end }];
  if (node.children.length === 0) {
    return Array.from({ length: Math.ceil(length / maxLength) }, (_, index) => ({
      start: node.start + index * maxLength,
      end: Math.min(node.start + (index + 1) * maxLength, node.end),
    }));
  }

  const spans = node.children.flatMap((child) => astSpans(child, maxLength));
  return spans.reduce<Span[]>((merged, span) => {
    const previous = merged.at(-1);
    if (previous && span.end - previous.start <= maxLength) previous.end = span.end;
    else merged.push({ ...span });
    return merged;
  }, []);
}

代码块验收要增加文本语料没有的指标：定义被切断率、块到符号的可追溯率、符号查询 Recall@k，以及召回代码能否通过编译或测试。AST 边界改善结构完整性，不代表纯向量排序一定同步变好；词法符号检索、调用关系和向量语义应作为可组合信号分别评测。

图像与图表：转成文字再进检索

图像、图表、流程图的信息根本不在文本层。文档解析时若只提取文字，「见下图」后面那张关键架构图就只剩一个占位符，信息彻底丢失。一条常见路径是先转描述再嵌入：用多模态模型为每张图生成文字描述，把描述作为块入库，并保留原图引用。另一条路径是直接用视觉或多向量模型为页面图像建索引，避免 OCR 或描述漏掉布局信息。两条路径可以并行召回，但必须在同一评测集上比较文本问题、视觉问题与表格问题的表现。

描述路径把图像检索转化成文本检索，能复用前面所有切法与增强手段；它的上限由描述质量决定，漏掉关键数字后检索就永远找不到。直接视觉检索保留布局，却增加索引体积与在线匹配成本。对图表密集的财报、论文或看板，应保存图像块、描述块与来源页坐标的映射，让答案能够回到原始视觉证据，而不是只引用模型生成的描述。

小结

  • 非散文内容语义不沿文本线性排列，通用切法对其是破坏性的；处理原则是解析阶段识别、隔离、再分类专门处理。
  • 表格：小表整表成块，大表行级展开且每行重复携带表头，保住二维语义。
  • 代码：按 AST 边界递归分割、在上限内合并相邻节点，保留符号与原文区间，并单独评测结构完整与排序质量。
  • 图像/图表：可生成描述后做文本检索，也可直接建立视觉多向量索引；两条路径的证据都应映射回原页。
