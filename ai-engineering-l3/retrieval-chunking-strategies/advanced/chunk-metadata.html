Part II · Agent Construction检索分块策略进阶元数据与上下文增强

元数据与上下文增强

「需返厂检测」——单独看这个块，嵌入向量根本不知道它在讲电池鼓包还是屏幕碎裂。问题不在切法，在于切块时丢掉了它赖以理解的文档级背景。给每个块补回这份背景，有两条路：一条是挂上结构化元数据（来源、标题、时间）供过滤和锚定，另一条是用 LLM 给每块生成一句「它在整篇文档里讲什么」再嵌入——这就是 2024 年底 Anthropic 提出、2026 年已成主流的上下文检索（Contextual Retrieval）。这一篇讲清这两条增强路径。

核心概念

分块默认会切断块与其文档语境的联系。增强的本质是「在块被嵌入之前，往块里补回它丢失的上下文」，分两类。结构化元数据是确定性的、可过滤的字段（文档标题、章节路径、作者、日期、文档类型），挂在块上既能锚定语义又能做检索过滤。上下文增强是用 LLM 生成的自然语言摘要，描述这个块在原文中的角色，拼进块文本一起嵌入，让向量携带文档级背景。

flowchart TD
  A[原始块: 需返厂检测] --> B[结构化元数据]
  A --> C[LLM 生成上下文句]
  B --> D[标题路径/来源/日期/类型]
  C --> E[本段讲电池鼓包的返厂处理]
  D --> F[拼接: 上下文 + 元数据 + 原块]
  E --> F
  F --> G[嵌入入库, 向量更锐利]
  D --> H[检索时按元数据过滤]

下表对比两类增强。

维度 结构化元数据 上下文增强（Contextual Retrieval）
生成方式 解析/规则，确定性 LLM 为每块生成，需推理
形态 键值字段 一段自然语言（约 50–100 token）
主要用途 检索过滤 + 锚定 提升嵌入语义完整性
成本 极低 较高（每块一次 LLM 调用）
实测信号 需按过滤命中率评测 Anthropic 实验中检索失败率下降

结构化元数据：让块可过滤、可锚定

结构化元数据是性价比最高的增强，几乎零推理成本。它有两个独立价值。其一是过滤：把文档类型、日期、部门、标题路径等作为可查询字段，检索时先用元数据缩小范围（如「只在 2026 年的财务文档里检索」），再做向量匹配。这能大幅削减无关召回，直接提升精确率——回到 分块对检索的影响 的因果链，过滤是在召回前就排除了一批假阳性。

其二是锚定：把标题路径等元数据拼回块文本开头再嵌入。前面 结构感知分块 已展示过这一招——给「需返厂检测」加上「保修政策 > 电池 > 鼓包处理」前缀，向量立刻锐利。元数据从哪来？结构感知分块切分时天然产出标题路径，文档摄入时可附加来源与时间。设计元数据 schema 时的原则是「只存检索会用到的字段」，无用字段只会膨胀索引。生产端还要验证元数据是否真的进入过滤表达式，避免只生产不消费。

上下文检索：Anthropic 的关键一招

2024 年底 Anthropic 提出的上下文检索，针对的正是「块丢失文档级背景」这个根本问题。做法是：在嵌入每个块之前，用一个 LLM 读「整篇文档 + 这个块」，生成一句简短的上下文说明（典型 50–100 token），形如「本节讨论的是文档 Y 中关于 Z 的 X 部分」，把这句话前置到块文本，再做嵌入与索引。于是「需返厂检测」会被改写成「本段说明保修政策中电池鼓包需返厂检测：需返厂检测」，向量从此携带了它原本丢失的主题信息。

Anthropic 的公开实验以 1 - Recall@20 衡量检索失败率：只加 Contextual Embeddings 时从 5.7% 降到 3.7%，相对下降 35%；同时加入 Contextual BM25 时降到 2.9%，相对下降 49%（Anthropic 工程报告）。这些数字来自其特定语料、模型和 top-20 设置，不应直接外推为你的收益。代价也明确：每个块都要生成上下文，索引构建的成本与时延上升；对超长文档，还需处理文档超出生成模型窗口的问题。它适合文档相对稳定、可离线建索引且检索质量重要的场景。

晚分块：另一条上下文保全路径

与上下文检索并列的，还有晚分块（late chunking）。两者目标相同（让块嵌入携带文档级上下文），路径相反。上下文检索是「先用生成模型写上下文文本、再嵌入」；晚分块是「先把整篇文档过一遍长上下文嵌入模型、得到所有 token 的上下文化向量，再按块边界池化」——上下文由嵌入模型在分块前注入，无需生成额外说明（Late Chunking）。它省去了逐块生成调用，却需要保存或处理整篇 token 表示，受嵌入窗口与显存约束，不能简单称为更便宜。

2026 年的统一分类把「在哪里分割」与「何时生成嵌入」视为两条独立轴：结构、语义或 LLM 引导决定边界；chunk-then-embed 或 contextualized embedding 决定表示时机（Beyond Chunk-Then-Embed）。因此同一套结构边界既能配普通嵌入，也能配晚分块。无论用哪条路，增强是否真带来收益、是否值回成本，都必须用 分块评测 量化。

晚分块不等于晚交互

两个术语常因都含「late」而混淆。晚分块改变的是索引构建时机：先获得整篇上下文化 token 表示，再按边界池化成块向量，最终仍可每块一个向量。晚交互改变的是查询与文档的打分方式：ColBERT 为查询与文档保留 token 级多向量，在线阶段用细粒度 MaxSim 交互，而不是预先把整块压成一个向量（ColBERT、ColBERTv2）。

机制 改变的阶段 索引表示 在线计算 主要目的
上下文检索 分块后、嵌入前 上下文文本 + 块向量 普通向量检索 补回文档语境
晚分块 分块前的编码 上下文化块向量 普通向量检索 让块向量继承全文语境
晚交互 查询—文档打分 每块多组 token 向量 token 级相似度聚合 保留细粒度匹配

三者可以组合，但成本维度不同：上下文检索增加离线生成，晚分块增加长文编码与中间表示，晚交互增加索引空间与在线打分。架构评审必须明确选择的是哪一层，否则团队很容易拿 ColBERT 的检索收益去证明晚分块，或反过来。

type RepresentationPlan = {
  contextualText: boolean;
  embeddingTiming: 'after-chunk' | 'before-pooling';
  vectorsPerChunk: 'single' | 'multi';
};

const lateChunking: RepresentationPlan = {
  contextualText: false,
  embeddingTiming: 'before-pooling',
  vectorsPerChunk: 'single',
};

const lateInteraction: RepresentationPlan = {
  contextualText: false,
  embeddingTiming: 'after-chunk',
  vectorsPerChunk: 'multi',
};

小结

  • 增强的本质是「在嵌入前往块里补回它丢失的文档级上下文」，分结构化元数据与上下文增强两条路。
  • 结构化元数据零推理成本，提供检索过滤（提升精确率）与标题锚定（拼回块开头让向量锐利），只存检索会用的字段。
  • Anthropic 的上下文检索给每块生成 50–100 token 的上下文句；其公开实验中 Contextual Embeddings 使 top-20 检索失败率相对下降 35%，但不能直接外推。
  • 晚分块先整篇编码再按块池化；晚交互则保留多向量并在查询时做 token 级匹配，两者不是同一机制。
