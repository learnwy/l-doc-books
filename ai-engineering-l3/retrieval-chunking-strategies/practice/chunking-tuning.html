分块调优

有了评测这把尺子，下一个问题是：块大小、重叠、切法、父子窗口——这么多旋钮，按什么顺序拧、每拧一个看哪个指标、什么时候该停手？随手乱调，要么陷入「调了某个数字感觉变好了」的自我欺骗，要么在十几个参数的组合空间里迷路。这一篇把分块调优从碰运气变成有方法的搜索：先调影响最大的旋钮、严格控制变量、用评测而非感觉决定每一步。

核心概念

分块调优是一个在评测反馈下的有序搜索过程，核心纪律有三条。一是按影响排序：先调对指标影响最大的参数（块大小、切法），再调次要的（重叠、窗口），别一开始就纠结小数点。二是一次只动一个变量：固定嵌入、检索器、生成模型、评测集，每次只改一个分块参数，否则指标变化无法归因。三是用评测拍板：每一步的取舍都由 分块评测 的数字决定，不靠「看几个例子感觉变好了」。

flowchart TD
  A[固定基线: 递归切分 512/15%] --> B[第一步: 扫块大小]
  B --> C[第二步: 扫重叠]
  C --> D{召回准但答案残缺?}
  D -->|是| E[上父子/窗口检索]
  D -->|否, 召回不准| F[换切法/嵌入]
  E --> G[第三步: 调窗口/父块大小]
  F --> G
  G --> H{评测增益 > 成本?}
  H -->|是| I[采纳]
  H -->|否| J[回退到更简方案]

下表给出旋钮的调节顺序与对应观察指标。

顺序 旋钮 主要影响 观察指标
1 块大小 召回/精确率/上下文完整性 Recall@k 曲线 + 答案正确率
2 重叠比例 跨边界召回 vs 重复污染 Recall 增益 vs 块数膨胀
3 切法 边界质量 端到端答案质量
4 父子/窗口 上下文充足度 忠实度 + 答案正确率
5 元数据/上下文增强 嵌入精准度 Precision@k

从基线开始：先立标杆再优化

调优的第一步永远是建立明确基线，而非直接上花哨方案。可以从「递归字符切分 + 约 512 token + 10–20% 重叠」开始，但要把它标成实验基线而非业界结论。NAACL 2025 说明简单固定切分足以成为强对照，2026 复现又说明任务设定会改变赢家（Qu 等，2025、2026 复现）。在 分块评测 的固定评测集上把检索层与端到端指标全部跑出，作为后续改动的对照。

没有基线，任何「改进」都是悬空的——你无法说清新方案到底好了多少、值不值这份复杂度。建立基线还有个隐藏好处：很多时候基线已经足够好，评测会直接告诉你「不必再调」，省下大量过度工程。这正是 固定与递归分块 强调的「多数项目无需升级」在调优纪律上的体现。

旋钮的调节顺序

参数要按影响力从大到小依次调，每调一个固定其余。第一调块大小：它是影响最大的旋钮，直接牵动召回、精确率与上下文完整性。在基线附近扫一组值（如 256 / 384 / 512 / 768 / 1024 token），看 Recall@k 曲线与答案正确率——你要找的不是 Recall 最高点，而是「检索指标与答案质量共同的甜区」，因为 分块对检索的影响 已说明二者可能背离。

第二调重叠：在选定的块大小上扫重叠比例（0 / 10% / 15% / 20%）。重叠的判据是「Recall 增益是否盖过块数膨胀」——回忆 分块粒度与重叠 里 N≈L/(s(1−r))N \approx L/(s(1-r))N≈L/(s(1−r))，重叠每加大都在膨胀索引，若 Recall 几乎不再上升就该停。第三调切法：仅当块大小/重叠调到头、评测仍不满意时，才比较递归 vs 结构感知 vs 语义分块，且必须连成本一起算。第四步视瓶颈类型决定：若是「召回准但上下文不足」上 父子与窗口检索，若是「嵌入不够精准」上 元数据与上下文增强。

何时停手：避免过度调优

调优最危险的不是调不动，而是停不下来——在指标已经平台期后继续雕花，把精力耗在噪声内的百分点上，或为了刷某个指标引入脆弱复杂度。停手的判据有三。其一，指标进入平台期：连续调整的端到端增益落在置信区间内。其二，增益盖不过成本：质量改善不足以抵消索引构建、存储、在线 token 与运维成本。其三，瓶颈已不在分块：若召回证据正确、答案仍差，问题更可能在生成或提示，继续调分块是缘木求鱼。

用实验清单隔离变量

调优结果应由机器可读清单驱动，而不是散落在笔记里的参数。下面的 TypeScript 类型明确哪些变量必须固定、哪些变量允许变化；每次运行都生成唯一配置 ID，指标、时延与成本都绑定到它。

type Experiment = {
  id: string;
  chunker: 'recursive' | 'semantic' | 'structure' | 'proposition';
  chunkSize: number;
  overlap: number;
  embeddingModel: string;
  retrieverVersion: string;
  generatorModel: string;
  evaluatorVersion: string;
  datasetVersion: string;
};

function changedFields(a: Experiment, b: Experiment): string[] {
  return (Object.keys(a) as Array<keyof Experiment>).filter((key) => a[key] !== b[key]);
}

function assertSingleTreatment(baseline: Experiment, candidate: Experiment) {
  const allowed = new Set(['id', 'chunker', 'chunkSize', 'overlap']);
  const unexpected = changedFields(baseline, candidate).filter((field) => !allowed.has(field));
  if (unexpected.length > 0) throw new Error(`confounded experiment: ${unexpected.join(', ')}`);
}

同一批评测查询应对两个候选做配对比较，因为每个查询的难度差异远大于配置间平均差异。报告至少包含每类查询的均值、胜负平数、置信区间、索引耗时、索引大小和平均送入模型的 token。LREC 2026 的 Adaptive Chunking 展示了逐文档选择方法的价值；如果不同文档类型的赢家不同，就应路由策略，而不是强行找一个全局参数（Adaptive Chunking）。

还要警惕对评测集过拟合：在同一小评测集上反复调，可能调出只对这批查询好的方案。缓解办法是留出一份调优时不可见的验证集，最终方案只在它上面复测一次。调优产物应是一份「配置 → 指标 → 成本 → 数据版本」的记录，让选择可追溯、可复现，而不是一串拍脑袋的最终值。

小结

  • 调优是评测反馈下的有序搜索，三条纪律：按影响排序、一次只动一个变量、用评测而非感觉拍板。
  • 先建明确的递归基线并跑全指标；512/15% 可作起点，但不是跨语料默认答案。
  • 旋钮顺序：块大小 → 重叠 → 切法 → 父子/窗口或元数据增强；块大小找「检索与答案共同甜区」，重叠看「增益是否盖过块数膨胀」。
  • 三种停手信号：指标进入平台期、增益盖不过成本、瓶颈已不在分块；并留验证集防过拟合。
