分块陷阱

分块的坑有个共同的恶劣特性：它们不在切块时报错，而在数月后某个用户提问时，以「检索莫名其妙找不到明明存在的答案」的形式爆发，根因却深埋在当初那行不起眼的切块代码里。这一篇把一线最常见的失败模式集中起来——每个坑给出它的识别信号、为什么会发生、以及怎么修。把它们提前过一遍，能帮你在上线前避开大半返工。

核心概念

分块的失败模式可归为四类：切坏了（边界破坏语义）、补漏了（块缺上下文）、评偏了（评测不反映真实）、没维护（索引随文档漂移）。它们大多源于同一个错误心态——把分块当成「跑通就行」的一次性预处理，而非需要评测、需要随数据演进的系统组件。

flowchart TD
  A[分块陷阱] --> B[切坏了]
  A --> C[补漏了]
  A --> D[评偏了]
  A --> E[没维护]
  B --> B1[答案跨边界腰斩]
  B --> B2[语义分块碎成超短块]
  B --> B3[表格/代码被盲切]
  C --> C1[块丢失指代/标题上下文]
  C --> C2[元数据未被检索利用]
  D --> D1[评测集不像线上查询]
  D --> D2[只看检索不看答案]
  E --> E1[文档更新但索引未重建]
  E --> E2[分词器与嵌入不一致致截断]

下表给出每个坑的识别信号与修法。

坑 识别信号 修法
答案跨边界腰斩 某些查询召回时灵时不灵 加 10–20% 重叠
碎成超短块 块平均长度过小、答案残缺 设 token 下限，慎用语义分块
表格/代码盲切 数字脱离表头、代码无法解读 隔离后专门切
元数据未利用 精确率上不去 检索时启用元数据过滤
评测集失真 离线好、线上差 评测集贴近线上查询分布
索引漂移 答案引用过期内容 增量更新 + 重建策略

切坏了：边界破坏语义

最直接的一类坑是边界切在了不该切的地方。答案跨边界腰斩是经典案例：关键答案恰好横跨两块，检索任一块都只拿到半句，症状是「某些查询时灵时不灵」——同一个问题换种问法就时好时坏。修法是 分块粒度与重叠 讲的 10–20% 重叠，给跨边界内容上保险。

碎成超短块是语义分块的典型风险：边界更纯净，但单块不再自足。NAACL 2025 的系统研究没有发现语义分块足以稳定覆盖其额外成本，提醒团队必须把端到端问答纳入评测（Qu 等，2025）。修法是给块设与语料匹配的 token 下限、合并过短相邻块，并用 语义分块 的评测门决定是否采用。表格或代码盲切则会让表头与数据分离、函数被腰斩，修法是在结构解析阶段识别并隔离区块。

补漏了：块缺失上下文

第二类坑是块本身切得没错，却丢了理解它所必需的上下文。指代/标题上下文丢失最隐蔽：一个块写着「它需返厂」，但「它」指代的主语被切到了上一块，这个块的嵌入向量因此落在含糊位置，检索找不到、模型也读不懂。这正是 分块对检索的影响 因果链里「边界切断指代」那一环的现实爆发。修法是 元数据与上下文增强：把标题路径拼回块开头，或用上下文检索给每块补一句背景。

元数据未被检索利用是另一种浪费：你在切块时辛辛苦苦挂了标题、日期、来源元数据，检索时却根本没用它做过滤，于是该被元数据排除的无关块照样混进召回，精确率上不去。修法是确认检索链路真的启用了元数据过滤——这是一个「做了一半」的常见疏漏：增强信息生产了，但消费侧没接上。

评偏了与没维护：系统性盲区

最后两类坑是系统性的，往往让前面所有努力白费。评测集失真是头号杀手：用一批与线上真实查询分布不像的问题调出「最优分块」，离线指标漂亮、上线却拉胯。根因是 分块评测 强调的「评测集查询必须贴近生产」被违背了。只看检索不看答案是它的孪生坑——指标停在 Recall@k，没评到端到端答案质量，于是被语义分块那种「召回好看答案差」的方案骗到。

索引漂移是上线后才显现的坑：文档更新了，但向量索引没重建，检索返回过期内容，答案引用早已作废的政策。修法是让块 ID 包含来源版本或内容哈希，摄入完成后原子切换索引版本，并能回滚。另一个隐性技术坑是分词器与嵌入模型不一致导致块被静默截断——用一种分词器算块长、另一种嵌入，块真实 token 数超出上限被悄悄截掉尾部，分块粒度与重叠 已警示过这点。这类坑不会主动报错，只能靠不变量、评测与监控发现。

把隐性坑变成摄入门禁

能在入库前确定的错误，不应等用户查询后才发现。下面的 TypeScript 门禁同时检查空块、块长、原文区间、内容哈希重复和缺失的版本元数据；失败即拒绝发布该索引版本。

type CandidateChunk = {
  id: string;
  sourceVersion: string;
  start: number;
  end: number;
  tokenCount: number;
  contentHash: string;
};

function validateCandidates(chunks: CandidateChunk[], maxTokens: number): string[] {
  const errors: string[] = [];
  const hashes = new Set<string>();

  for (const chunk of chunks) {
    if (!chunk.sourceVersion) errors.push(`${chunk.id}: missing source version`);
    if (chunk.start < 0 || chunk.start >= chunk.end) errors.push(`${chunk.id}: invalid range`);
    if (chunk.tokenCount <= 0 || chunk.tokenCount > maxTokens) {
      errors.push(`${chunk.id}: invalid token count`);
    }
    if (hashes.has(chunk.contentHash)) errors.push(`${chunk.id}: duplicate content`);
    hashes.add(chunk.contentHash);
  }

  return errors;
}

门禁之外还要建立分布监控：块长的 p50/p95、过短块占比、重复率、无标题路径占比、解析错误率、索引中文档版本滞后时间。发布新 chunker 时先影子构建新索引，比较这些分布和固定评测集，再切流；指标异常时保留旧索引，而不是在线原地覆盖。

小结

  • 分块陷阱的恶劣之处是不报错、延迟爆发，根因深埋切块代码；归为切坏了/补漏了/评偏了/没维护四类。
  • 切坏了：答案跨边界腰斩（加重叠）、碎成超短块（设 token 下限、慎用语义分块）、表格代码盲切（隔离专门切）。
  • 补漏了：指代/标题上下文丢失（拼回标题或上下文增强）、元数据生产了却没在检索时消费（启用过滤）。
  • 评偏了/没维护：评测集不像线上、只看检索不看答案、索引随文档漂移、分词器与嵌入不一致致静默截断——都只能靠评测与监控发现。
