分块评测

「这套分块方案更好」——凭什么这么说？凭感觉看几个例子，几乎注定踩坑：你看到的好例子可能正是过拟合的那几个，而它在另一批查询上悄悄变差了。整个 hub 反复强调的「先评测再决定」，到这一篇要落地成具体方法：用哪些指标、配什么数据集、怎么把「分块好不好」变成可比较、可复现的数字。没有这把尺子，前面所有切法与增强都只是猜测。

核心概念

分块评测要同时量两件事，缺一不可。检索层指标衡量「相关的块有没有被检出、检出的有多准」，是分块直接影响的环节。端到端指标衡量「最终答案对不对、有没有幻觉、有没有用上检索到的内容」，因为 分块对检索的影响 已证明检索指标好不等于答案好。只看前者会被语义分块那种「召回好看但答案差」的陷阱骗到，所以两层必须一起看。

flowchart TD
  A[固定评测集: 查询 + 标注相关块] --> B[跑某分块方案的检索]
  B --> C[检索层指标]
  C --> D["Recall@k / Precision / MRR / nDCG"]
  B --> E[把召回块喂模型生成答案]
  E --> F[端到端指标]
  F --> G["上下文相关性/忠实度/答案正确率"]
  D --> H[同一评测集横向对比方案]
  G --> H
  H --> I[选出真正更优的分块配置]

下表列出常用指标及其衡量对象。

层级 指标 衡量什么
检索 Recall@k 前 k 个结果里是否包含相关块
检索 Precision@k 前 k 个里有多少真相关
检索 MRR 第一个相关块的排名倒数
检索 nDCG 考虑排序位置的相关性增益
端到端 上下文相关性 召回内容与问题的相关度
端到端 忠实度 答案是否忠于召回内容（防幻觉）
端到端 答案正确率 答案与标准答案是否一致

评测集：一切的前提

没有固定评测集，所有数字都不可比。评测集的最小形态是一组「查询 + 该查询的标准答案 + 标注的相关块」三元组。它的作用是把评测从「凭感觉看例子」变成「在同一批固定输入上跑出可复现的数字」——这样你换块大小、换切法时，指标变化才真实反映方案差异，而非你恰好看了不同的例子。

构造评测集有两条路。一是人工标注：从真实文档里挑代表性问题，人工标出哪些块含答案，最可靠但最贵。二是合成生成：用 LLM 读文档块、反向生成「这个块能回答的问题」，快速规模化但需抽查质量。关键原则是评测集的查询分布要贴近线上真实查询——用一批和生产环境不像的问题调出来的「最优分块」，上线后多半失效，这正是 分块陷阱 里反复出现的坑。还要保存证据在原文中的区间，而不是绑定某一版 chunk ID；否则更换切法后黄金标签会全部失效，无法公平对比。

检索层指标：分块的直接成绩单

检索层指标是分块方案最直接的成绩单，因为分块就发生在检索之前。Recall@k 衡量前 kkk 个召回里是否覆盖了相关块——块切得太碎、答案跨边界，会直接拉低它。Precision@k 衡量召回里有多少真相关——块切得太大、主题混杂，会让无关内容混入而拉低它。这两个指标的此消彼长，正是 分块粒度与重叠 那对张力在评测上的投影。

只看单点 kkk 不够，要看一条曲线：随 kkk 增大 Recall 怎么爬升。一个好的分块方案应在较小的 kkk 就达到高 Recall，意味着相关块排得靠前。MRR 和 nDCG 进一步把排序质量纳入——同样召回到相关块，排在第 1 位远好于第 10 位，因为下游模型的注意力有限、且上下文预算有限。需要提醒：检索指标受嵌入模型和检索器影响，评测分块时要固定嵌入与检索器、只变分块，否则分不清是分块还是嵌入的功劳。控制变量的具体做法见 分块调优。

端到端评测：RAGAS 与答案质量

检索指标好看，答案却可能差，所以必须一路评到答案。Ragas 当前提供 Context Precision、Context Recall、Noise Sensitivity、Response Relevancy 与 Faithfulness 等指标；其中一部分由 LLM 评判，输入字段与评分假设必须随实验一起固定（Ragas 指标文档）。这些指标不是采用复杂方案的自动许可证，而是与人工抽检、任务正确率和成本共同组成证据。

端到端评测里有不少是用 LLM 当裁判（LLM-as-judge）给答案打分，要注意裁判本身的稳定性与偏差。实践流程是：固定评测集 → 固定嵌入、检索器、生成模型与裁判 → 只变分块方案 → 同时记录检索层与端到端两组指标 → 横向对比。当复杂方案相对递归基线没有稳定提升时，就不该承担更多成本。至少重复运行裁判敏感指标，并对关键失败做盲审，防止一次非确定性评分决定架构。

从边界指标到可运行检索指标

ACL 2025 的 MoC 提出 Boundary Clarity 与 Chunk Stickiness，试图直接衡量边界是否清晰、块内语义是否黏合（MoC）；LREC 2026 的 Adaptive Chunking 又加入引用完整性、块内凝聚度、文档上下文连贯性、区块完整性与大小合规（Adaptive Chunking）。这些内在指标适合在无问答标注时筛掉明显坏配置，但不能替代下游检索与答案质量。

下面的 TypeScript 代码计算单个查询的 Precision@k、Recall@k 与 reciprocal rank。黄金标签使用证据 ID；实际项目应先把召回块的原文区间映射到证据 ID，才能跨切法比较。

type RetrievalMetrics = { precision: number; recall: number; reciprocalRank: number };

function retrievalMetrics(rankedIds: string[], relevantIds: Set<string>, k: number): RetrievalMetrics {
  const topK = rankedIds.slice(0, k);
  const hits = topK.filter((id) => relevantIds.has(id));
  const firstRelevant = rankedIds.findIndex((id) => relevantIds.has(id));

  return {
    precision: topK.length === 0 ? 0 : hits.length / topK.length,
    recall: relevantIds.size === 0 ? 1 : new Set(hits).size / relevantIds.size,
    reciprocalRank: firstRelevant < 0 ? 0 : 1 / (firstRelevant + 1),
  };
}

批量报告要按查询类型分层：事实查找、跨段整合、表格、代码与多跳问题不能只汇总成一个平均数。一个方案可能提升短事实检索，却损害跨段答案；分层结果能告诉你该全局替换，还是只对某类文档或查询路由到高级切法。

小结

  • 分块评测必须同时量检索层（Recall@k/Precision/MRR/nDCG）与端到端（上下文相关性/忠实度/答案正确率），只看检索会被「召回好看但答案差」骗。
  • 一切以固定评测集为前提：查询 + 标准答案 + 标注相关块；查询分布必须贴近线上，否则调出的「最优」上线即失效。
  • 评测分块时要固定嵌入/检索器/生成模型、只变分块，否则分不清功劳归属；看 Recall-k 曲线而非单点。
  • Ragas 等端到端框架提供有用信号，但要固定裁判配置、重复运行并配合人工盲审。
  • 继续阅读本 hub 的 分块对检索的影响、分块调优 与 分块陷阱。
