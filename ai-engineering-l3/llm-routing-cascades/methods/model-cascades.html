模型级联与回退

分类器路由要在请求执行前预测难度，而很多请求的真实难点只有答案生成后才暴露。级联换了一种证据顺序：先运行低成本路径，再用结果、验证器或业务约束判断是否接受；证据不足就升级到更强模型或更高 effort。它用更可靠的事后信号换取白跑成本与更长尾延迟。FrugalGPT 的原始研究证明，多模型级联在其特定任务和价格快照上可以显著移动成本—质量前沿；论文中的极高节省是实验条件下的上界，不是生产承诺（FrugalGPT, TMLR 2024）。

核心概念：候选序列、接受器与预算

一个可执行级联至少包含三部分：按预期成本排列的候选路径 P1,P2,…,PkP_1, P_2, \dots, P_kP1​,P2​,…,Pk​，判断当前结果是否足够的接受器 ai(x,yi)a_i(x,y_i)ai​(x,yi​)，以及整条请求的预算 BBB。候选路径不一定只是不同模型，也可以是「同一模型 + 不同 effort + 不同工具权限」。

  A2 -->|否| P3[最终权威路径]
  P3 --> R3[返回/人工复核]

级联成本必须按「到达概率」计算。若路径成本为 cic_ici​，到达第 iii 档的概率为 rir_iri​，接受器与验证器额外成本为 viv_ivi​，则：

E[C]=∑iri(ci+vi)\mathbb{E}[C]=\sum_i r_i(c_i+v_i)E[C]=i∑​ri​(ci​+vi​)

这里的 rir_iri​ 来自真实流量，不是设计文档里的估计。困难请求比例上升、第一档变贵或接受器变保守，都会让前沿快速移动。

接受器：不要把流畅当正确

接受器是级联的命门。小模型过度自信时，错误结果会在第一档被放行；接受器过度保守时，大量正确答案也会升级，成本与延迟收益消失。不同任务应使用不同证据。

信号 适用任务 优点 主要缺陷
token 概率/熵 分类、短答案 低开销 流畅不等于正确，跨模型难校准
规则与 schema 校验 结构化输出、工具参数 确定、可解释 只能证明格式，不能证明语义
可执行验证 代码、SQL、计算 直接验证关键不变量 测试覆盖不足仍会漏错
独立 judge 开放式回答 能覆盖语义 有偏差且增加调用成本
多次采样一致性 可比较的推理答案 能发现不稳定 成本成倍增加，同错仍可能一致
业务结果/人工复核 高风险决策 对准真实目标 延迟高，反馈可能很晚

校准必须在独立验证集完成，并按风险子集分别看 false accept rate。总准确率看起来很好时，医疗、支付、权限或不可逆工具调用的错误仍可能集中在尾部。高风险路径更适合「失败关闭」：证据不足就升级、拒绝或交人工，而不是为了节省强行接受。

跨模型级联与同模型 effort 级联

传统级联在小模型、中模型、旗舰模型之间升级。现在还要把同模型 effort 看成独立候选：低 effort 先处理简单请求，验证失败时以更高 effort 重新执行。当前 OpenAI 与 Claude 接口都提供模型相关的 effort 控制，但支持档位和默认值不同，必须查能力注册表而不是硬编码（OpenAI Models，Claude Effort）。

同模型 effort 级联有三个独特风险。

  1. 不保证单调：更高 effort 通常投入更多计算，但不保证每个样本都更好，必须按任务测量。
  2. 重复生成：第二档通常无法复用第一档全部计算，成本不是「只补差额」。
  3. 会话与缓存耦合：例如 Claude 文档明确说明在同一长会话中改变 effort 会影响提示缓存前缀；依赖缓存的系统应在会话开始固定 effort，或把升级视为新的执行分支。

一个稳健候选注册表可以写成：

path_id = model_snapshot + effort + tool_protocol + prompt_version
expected_cost = input_price_snapshot + output_price_snapshot + tool_cost
constraints = region + retention + capability + deadline

因此「模型没变」不代表实验 arm 没变；effort、工具协议或系统提示变化都要产生新 arm。

质量升级与可用性回退是两条状态机

质量级联回答「结果够不够好」，可用性回退回答「选中的端点能不能完成请求」。超时、限流和服务故障应先在 provider 层处理；结果通过传输却不满足任务质量，才进入质量升级。把两者混成一个 fallback 列表会产生两类错误：网络故障意外换到能力更弱的模型，或质量失败在同一能力端点间反复重试。

stateDiagram-v2
  [*] --> Execute
  Execute --> ProviderRetry: timeout/rate limit
  ProviderRetry --> Execute: alternate endpoint
  Execute --> QualityGate: response complete
  QualityGate --> Accept: evidence passes
  QualityGate --> Escalate: evidence fails
  Escalate --> Execute: next capability path
  Accept --> [*]

每次尝试都要记录 attempt_id、path_id、resolved provider、失败类型和幂等键。工具调用或写操作不能因为质量升级而重复执行；级联只能重放纯推理，副作用必须由执行账本去重或复用已有收据。

推测级联：token 段级的特殊分支

推测级联把回退粒度从整次请求细化到 token 段。小模型先起草，大模型给出参考，策略逐段决定接受草稿还是采用大模型输出。它与经典推测解码不同：经典方案通常以保持目标模型分布为目标，推测级联允许按质量—成本目标接受「足够好」的草稿，因此可能改变输出分布。Google Research 的工作展示了这一混合思路（Speculative Cascades, 2025）。

它适合控制推理栈、词表和批处理调度的团队，不适合把两个远程黑盒 API 简单串起来。网络往返、不同 tokenizer、不可访问 logits 与供应商计费方式，往往会吃掉理论收益。

上线前的失败演练

级联不是把几行 if-else 上线。至少要演练：第一档过度自信、judge 超时、预算服务不可用、模型别名漂移、provider 连续限流、工具副作用已发生但响应丢失，以及最终档也未通过质量门。每种故障都要有终止状态：接受、升级、拒绝、降级输出或人工复核。

上线门应同时包含：第一档接受率、false accept rate、升级后挽救率、每档到达率、完整成本、p95/p99 延迟、预算耗尽率和重复副作用数。只看平均成本会掩盖尾部用户经历的多次白跑。

小结

  • 级联由候选路径、接受器和成本/时间预算共同组成，不是只有一个置信度阈值。
  • 接受器应优先使用任务可验证证据，并按高风险子集测 false accept rate。
  • 候选既可以跨模型，也可以在同一模型内升级 effort；effort 语义绑定模型快照且不保证样本级单调。
  • provider 可用性回退与质量升级是两条状态机，日志和指标必须分开。
  • 副作用不能随级联重放，必须以幂等键和执行收据隔离纯推理与真实写操作。
