Part IV · Control Plane模型路由与级联基础路由方法谱系

路由方法谱系

「路由」现在至少指四件不同的事：在多个模型之间选一个、给同一模型选择推理强度、在多个推理供应商之间选端点，以及让供应商自己的别名或自动路由器代选。它们都能改变成本和延迟，却拥有不同的控制权、证据和故障模式。如果只按「分类器还是级联」分类，工程团队很容易把供应商故障回退当成质量升级，或者把同模型的低 effort 误写成换了一个小模型。本节建立一张同时覆盖研究方法与生产控制面的地图。

核心概念：先确认到底在选择什么

选择对象是所有后续讨论的前提。

选择层 决策对象 典型输入 主要目标 可验证身份
跨模型路由 候选模型快照 请求、任务、风险、预算 质量与成本匹配 模型 ID + 版本/快照
同模型 effort 同一模型的推理强度 请求难度、延迟预算、质量门 用更多或更少推理计算 模型快照 + effort
provider 路由 承载同一模型的供应商或推理端点 可用性、地域、价格、吞吐、合规 可用性与基础设施效率 resolved provider + endpoint
供应商内部路由 别名背后的模型、端点或流水线 供应商私有信号 由供应商定义 元数据足够时才能完全还原

同模型 effort 已成为独立的路由旋钮。OpenAI 的当前模型接口为不同模型提供若干 reasoning effort 档位；Claude 的 effort 也在单一模型内调节整次响应的投入，并会影响文字、思考和工具调用。档位集合与默认值都依赖具体模型，所以路由器不能假设所有模型都支持同一组值，而应从能力注册表读取并以模型快照为键（OpenAI Models，Claude Effort）。

provider 路由则不是质量路由的同义词。它通常在已选定模型后，根据端点可用性、数据保留、地域、价格或吞吐选择承载方。一个系统可以先选「模型 + effort」，再选 provider；两步的决策日志必须分开，否则无法判断质量变化来自能力选择还是服务端点。

flowchart LR
  Q[请求与约束] --> MR{模型选择}
  MR --> M[resolved model snapshot]
  M --> ER{effort 选择}
  ER --> E[resolved effort]
  E --> PR{provider 选择}
  PR --> P[resolved provider/endpoint]
  P --> X[执行与证据]

供应商内部的自动路由最难治理。客户端可能只提交一个 alias，最终模型或端点由服务端决定；如果响应不回传候选、最终选择、尝试链与策略版本，就无法复现实验。此类能力可以用于低风险流量，但不能被当成可审计的自有路由器。

第二层：跨模型路由的四条正交轴

确认选择对象后，再用四条轴定位跨模型方法。

  1. 决策时机：请求前预测，还是运行低成本路径后再决定升级。
  2. 决策器来源：手写规则、离线学习，还是在线学习。
  3. 候选规模：二元、少量分级，还是开放模型池。
  4. 决策粒度：整次请求、会话阶段、Agent 步骤，还是 token 段。
flowchart TD
  Root[跨模型路由] --> A{决策时机}
  A -->|请求前| Pre[预测式]
  A -->|执行后| Post[级联式]
  Root --> B{策略来源}
  B --> Rule[规则]
  B --> Offline[离线学习]
  B --> Online[在线学习]
  Root --> C{候选规模}
  C --> Binary[二元]
  C --> Tiered[分级/模型池]
  Root --> D{决策粒度}
  D --> Request[请求级]
  D --> Step[阶段/步骤级]
  D --> Token[token 段级]

预测式路由只调用一次目标模型，额外开销通常较小，但必须在看到答案前判断难度。级联先运行低成本路径，再用真实中间结果判断是否升级，判断证据更丰富，却给升级请求叠加了白跑成本和尾延迟。二者没有绝对胜负，关键是简单请求占比、错误代价、各档成本和截止时间。

策略来源也不是成熟度排名。规则在合规、租户等级和任务类型等稳定边界上往往最可靠；学习式路由适合规则难以表达的语义差异；在线学习只在奖励信号可信、探索损失受控时成立。把所有规则都替换成模型，反而会丢掉可解释的硬约束。

把常见方法放回地图

方法 选择层 时机 策略来源 粒度 首要风险
元数据/任务规则路由 跨模型 请求前 规则 请求 规则漂移、覆盖不足
RouteLLM 类分类器 跨模型 请求前 离线学习 请求 分布偏移、偏好标签偏差
置信度级联 跨模型 执行后 规则/学习 请求 小模型过度自信、白跑
contextual bandit 跨模型 请求前 在线学习 请求 探索损失、延迟奖励污染
同模型 effort 选择 同模型 请求前 规则/学习 请求/步骤 档位语义随模型版本变化
effort 升级级联 同模型 执行后 规则/学习 请求/步骤 重复生成、缓存失效、预算超支
provider 负载均衡/故障回退 provider 前/后 规则/遥测 尝试 把端点切换误认为能力切换

这张表也揭示一个重要事实：一次生产请求可能连续经过多种路由。应用规则先限制合规候选，学习路由器选择模型，策略再选择 effort，网关最后选择 provider；失败后 provider 回退，质量不足时模型或 effort 升级。它们应共享同一个 trace，却不能共享一个含糊的 route 字段。

决策记录：让每一层都可复现

最小路由收据至少包含：

request_class, policy_version, candidate_set,
requested_model, resolved_model_snapshot, resolved_effort,
requested_provider_constraints, resolved_provider,
decision_reason, attempt, fallback_reason,
input_tokens, output_tokens, reasoning_tokens_when_available,
latency, price_snapshot, quality_outcome

其中 requested_model 与 resolved_model_snapshot 必须分开。别名、自动路由和 provider fallback 都可能让两者不同。price_snapshot 也不能只在报表时查当前价，否则历史成本会随价目表更新而被重写。对于没有暴露 reasoning token 的接口，记录「不可观测」而不是填零。

不要和相邻层混为一谈

混合专家（MoE）的门控发生在单个模型前向内部，把 token 分给模型内部专家；本 hub 讨论的外部路由发生在 API 或执行控制面。Agent 工具选择又在任务控制流层，决定调用什么能力。它们都叫路由，却不能共享同一套候选、奖励或故障语义。

同样，provider fallback 通常处理超时、限流与区域故障；质量 deferral 处理答案不足。前者成功只证明请求有响应，后者成功才说明质量门被满足。监控上要分别统计 availability fallback rate 与 quality escalation rate。

小结

  • 先按选择对象分清跨模型、同模型 effort、provider 和供应商内部四层，再讨论算法。
  • 跨模型方法可沿决策时机、策略来源、候选规模和决策粒度四轴定位。
  • 一次请求可以依次经过多层路由；共享 trace，但模型、effort、provider 和尝试链必须分别记录。
  • effort 的支持档位、默认值和语义绑定模型快照，不能硬编码成跨供应商通用枚举。
  • provider fallback 保可用，模型或 effort deferral 保质量；两类指标不能合并。
