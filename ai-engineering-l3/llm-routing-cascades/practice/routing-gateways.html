Part IV · Control Plane模型路由与级联实践路由网关与中间件

路由网关与中间件

路由算法只负责提出「选哪个能力路径」，生产系统还要把选择变成一次受控执行：校验租户权限、解析模型与 effort、选择 provider、应用预算、处理限流和故障、记录每次尝试。LLM 网关承接的是这组控制面职责。它可以提供统一入口，但不能抹平模型之间的真实语义差异；把网关理解为「所有供应商完全兼容的代理」会在工具调用、结构化输出、思考控制和流式事件上留下隐蔽故障。

核心概念：策略决定与执行适配分离

稳定架构把纯决策与有副作用的调用分开。策略服务输入标准化请求、候选能力和约束，输出不可变的 route plan；执行网关验证计划、调用适配器并产出 execution receipt。

flowchart LR
  App[业务请求] --> Auth[身份/租户/授权]
  Auth --> Policy[路由策略]
  Registry[能力与价格注册表] --> Policy
  Policy --> Plan[route plan]
  Plan --> Gateway[执行网关]
  Gateway --> AdapterA[provider adapter A]
  Gateway --> AdapterB[provider adapter B]
  AdapterA --> Receipt[execution receipt]
  AdapterB --> Receipt
  Receipt --> App
  Receipt --> Eval[评测与成本账本]

route plan 至少钉住 policy_version、candidate set、requested/resolved model snapshot、effort、工具协议、provider 约束、预算、截止时间与 fallback 类型。网关不能在计划之外偷偷换到能力更弱的模型；若允许自动路由或别名解析，最终选择必须进入 receipt。

这条边界让两种变化解耦：算法团队可以改分类器或阈值而不重写供应商 SDK，平台团队可以升级 adapter 而不改变路由目标。策略是可回放的纯函数，执行是受预算和幂等约束的 effectful shell。

三层路由不能混成一个字段

生产网关经常连续做三次选择。

层级 问题 常见依据 失败后的合法动作
模型路由 哪个能力/模型快照回答 质量、任务、风险、成本 质量升级或拒绝
effort 路由 同一模型投入多少推理资源 难度、截止时间、预算、质量门 提高 effort 或换模型
provider 路由 哪个端点承载已选模型 可用性、地域、合规、吞吐、价格 同能力端点重试或故障回退

OpenRouter 的官方文档把 model routing 与 provider routing 明确区分，并允许用 provider 约束控制顺序、fallback、数据收集、ZDR、地域、吞吐、延迟和最高价格；这说明统一入口背后依然需要显式控制平面（Provider Routing）。LiteLLM 的 Router 同样把 deployment load balancing、cooldown、timeout、retry 与 provider fallback 作为可靠性机制，而不是质量评估（LiteLLM Routing，Provider Failover）。

质量 deferral 必须由质量门触发，provider fallback 必须由可用性错误触发。若供应商返回了语义错误但 HTTP 200，网关的成功率不会替你发现；若超时重试换了模型，指标又会把基础设施故障误算成算法决策。

统一 API 是反腐层，不是语义等价证明

一个稳健 adapter 的工作不是简单改字段名，而是显式声明能力与损失。

capability = {
  tool_protocol,
  structured_output_mode,
  streaming_event_model,
  reasoning_controls,
  image_and_file_inputs,
  context_and_output_limits,
  usage_visibility,
  retention_and_region
}

请求进入前，网关先用能力注册表验证所选路径能否满足契约。比如业务要求严格 schema、并行工具调用和特定数据驻留，缺任一能力的 provider 就不应进入候选。无法无损转换的字段应报可分类错误，不能静默丢弃。

响应侧也要保留原始 envelope 的可审计引用，并标准化为领域事件：文本增量、工具调用开始/参数增量/完成、拒绝、思考摘要、用量与终止原因。不同供应商的流式顺序可能不同，adapter 需要状态机与契约测试，而不是假设每个 chunk 都是文本。

路由收据：每次选择都留下证据

最小 execution receipt 可按下面的稳定字段设计：

request_id, tenant_id, idempotency_key,
policy_version, route_plan_hash, candidate_set_hash,
requested_model, resolved_model_snapshot, resolved_effort,
requested_provider_constraints, resolved_provider, region,
attempt_id, fallback_type, fallback_reason,
input/output/reasoning/cache tokens when available,
price_snapshot, latency_breakdown, terminal_status

OpenRouter 的 router metadata 也区分 requested model、strategy、selected endpoint、attempt 和 pipeline stages，说明「客户端请求了什么」与「系统实际做了什么」必须同时可见（Router Metadata）。自建网关即使字段不同，也应守住同一证据边界。

价格必须以调用时快照结算。事后用当前价目表重算，会让历史报表漂移。用量不可见时记录 unknown，不要用零冒充；失败尝试、路由器调用、judge 和级联白跑也应进入完整成本。

控制面所有权

能力 权威 owner 为什么不能混放
模型/effort 候选与质量阈值 路由策略 需要评测、版本化与灰度
provider 健康与部署选择 网关可靠性 依赖实时容量、地域与错误分类
租户可用模型、预算、数据策略 policy/entitlement 属于授权，不应由分类器猜测
供应商协议转换 provider adapter 变化原因是外部 API 演进
用量与成本事实 metering/cost ledger 必须追加、去重、可对账
质量结果 evaluation pipeline 不能用 HTTP 成功替代

网关可以执行授权结果，却不应成为套餐与 entitlement 的唯一真相源；可以发出 usage event，却不应在请求线程内直接生成发票；可以采集质量信号，却不应把观测后门变成未经版本化的路由策略。薄门面和深模块的分界正是「按变化原因组织」。

可靠性：有界重试、隔离与背压

网关的重试必须受 deadline、attempt budget 和错误分类约束。认证失败、参数不支持等永久错误不可重试；限流或暂时故障可在幂等前提下退避；流式响应已经向用户输出或工具副作用已经发生时，不能假装请求可以从头安全重放。

部署还需要每 provider/模型/租户的 bulkhead、并发限制、排队上限与 circuit breaker。没有隔离，一个热门租户或故障 provider 会耗尽整个网关连接池。背压要显式返回可重试语义和 Retry-After，而不是无限排队直到所有请求一起超时。

预算与虚拟 key 是常见网关能力，LiteLLM 也分别提供 spend tracking 与 virtual key 控制（Spend Tracking，Virtual Keys）。但预算拦截必须区分估算、预留与最终结算；把最终 token 数当成调用前已知会导致超卖或误拒绝。

上线与选型

不要用「支持模型数量」选网关。先做能力矩阵和故障演练：严格 schema 是否真的被 provider 接受；工具事件能否完整重建；alias 能否解析到可审计快照；ZDR/region 约束是否在 fallback 后仍成立；预算耗尽、provider 限流和网关依赖失联时终态是什么。

发布采用镜像与灰度：先只生成 route plan 不改变流量，再对低风险租户执行，比较 resolved identity、成本、质量和尾延迟。任何模型、effort、adapter 或策略升级都应能按版本回滚。旁路默认模型只能是显式降级策略，且仍经过授权、用量记录和审计；不能成为绕过控制面的万能后门。

小结

  • 网关把版本化 route plan 变成受授权、预算和幂等约束的执行；策略决定与 provider effect 必须分离。
  • 模型、effort 与 provider 是三层不同路由，分别记录 requested 与 resolved identity。
  • 统一 API 是反腐层，不证明语义等价；adapter 要声明能力、拒绝有损转换并通过流式契约测试。
  • receipt 是评测、成本、审计和故障复盘的共同证据，必须包含尝试链、价格快照与未知用量。
  • 选型看契约、所有权和故障演练，不看营销页上的模型数量。
