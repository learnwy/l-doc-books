Part IV · Control Plane模型路由与级联实践落地与权衡

落地与权衡

生产路由不是选一个算法，而是建立一套有边界的资源分配系统：硬约束先缩小候选，质量策略再选模型与 effort，网关选择 provider，执行后由证据判断接受还是升级。每层都有独立 owner、版本、预算和回滚点。真正的难题也不只在上线那天，而在模型快照、价格、流量与供应商能力持续变化时，系统还能解释「为什么这样选」并安全退回已知基线。

核心概念：先判断是否值得路由

路由的必要条件不是「有多个模型」，而是候选之间存在可利用的互补性，并且收益能覆盖误判与运维成本。

flowchart TD
  Start[考虑路由] --> H{有不可违反的硬约束?}
  H -->|有| Filter[先按授权/地域/能力过滤]
  H -->|无| Dist{请求与候选有互补性?}
  Filter --> Dist
  Dist -->|没有| Fixed[固定合适 arm]
  Dist -->|有| Verify{有可信质量证据?}
  Verify -->|没有| Shadow[先影子采集/人工标注]
  Verify -->|有| Risk{漏降级损失高?}
  Risk -->|高| Conservative[保守级联/失败关闭]
  Risk -->|低| Predictive[预测式或 effort 路由]

以下情况通常不值得上语义路由：流量高度同质；总量太小，节省覆盖不了开发和监控；候选模型质量几乎没有互补；高风险请求缺少可验证质量门；或者 provider alias 不暴露 resolved identity，导致实验不可复现。此时固定模型快照与明确 effort 往往更可靠。

推荐顺序：约束、规则、影子、学习

不要一开始就训练复杂路由器。按可逆性递增的顺序演进：

阶段 主要动作 退出证据
0 固定基线 钉住模型快照、effort、协议与价格 质量/成本/延迟基线可复现
1 硬约束过滤 entitlement、地域、保留策略、能力和 deadline 非法候选为零
2 显式规则 按任务、风险、租户和预算选 arm 每条规则有命中与反事实数据
3 影子决策 新策略只输出 route plan，不改变用户路径 与基线差异可解释
4 离线学习 用独立数据训练和校准，灰度替换语义规则 前沿超过简单基线且高风险门通过
5 在线适应 在有界探索和可信延迟奖励下更新 探索损失、漂移与回滚均受控

硬约束永远不应交给学习路由器。用户套餐不允许的模型、数据不能离开的区域、缺少工具能力的 provider，都应在候选生成阶段被确定性排除。学习模型只能在合法候选中优化软目标。

同模型 effort 是很实用的中间台阶：候选模型不变，只在支持的 effort 档位间选择，可以减少跨供应商协议差异。但它仍需独立 arm、质量 sweep 和预算；档位支持与默认值绑定模型快照，升级模型时必须重测。

一次请求的生产状态机

stateDiagram-v2
  [*] --> Authorize
  Authorize --> Reject: no legal candidate
  Authorize --> Plan: legal candidate set
  Plan --> Reserve: budget/limit reservation
  Reserve --> Execute: reservation granted
  Reserve --> Reject: budget exhausted
  Execute --> RetryProvider: transient availability failure
  RetryProvider --> Execute: alternate compatible endpoint
  Execute --> QualityGate: complete response
  QualityGate --> Settle: quality passes
  QualityGate --> Escalate: quality fails and budget remains
  Escalate --> Execute: stronger model/effort
  Settle --> [*]
  Reject --> [*]

状态机必须有有界终点。provider 重试受 attempt/deadline 限制；质量升级受成本与延迟预算限制；最终路径仍不合格时，按领域选择拒绝、带不确定性返回或人工复核。永远不能「一直 fallback 到某个能返回 200 的东西」。

预算预留与结算也要分开。请求前只能估算上界并预留，完成后根据实际用量结算和释放差额。级联每到下一档都要检查剩余预算，不能只在入口检查一次。价格使用调用时快照，避免事后报表漂移。

回退、幂等与副作用

两类回退要在代码和指标里分开：availability fallback 处理超时、限流和端点故障；quality escalation 处理答案未过验证。前者理想情况下保持同一能力契约，后者有意提高能力或 effort。

模型生成本身通常可重试，但工具调用和外部写入不是。每个 effect 必须通过幂等键、状态检查与执行收据保护。若第一档已经创建订单、发消息或修改数据，第二档只能读取该 effect 的收据继续推理，不能再次执行。流式响应已向用户发送部分内容时，也要定义是终止、续写还是新消息重试，不能静默拼接不同模型的输出。

旁路路径同样受控。网关故障时直连默认模型可以保可用，但旁路仍需鉴权、entitlement、用量事件、数据策略与审计；否则它会成为系统最危险的永久后门。定期演练旁路，并设置自动失效时间。

发布：每一步都能停、能回滚

发布单元是完整版本元组，而不是单个模型：

release = policy_version + registry_version + adapter_version +
          prompt/tool_protocol_version + price_snapshot

先离线回放，再影子，再低风险租户 canary，最后分阶段扩量。每阶段设置相同的联合门：质量非劣、灾难错误为零、完整成本达到目标、p95/p99 在预算内、receipt 完整率足够高。回滚恢复整个版本元组，避免只退策略却保留不兼容 adapter。

模型 alias 与供应商 auto router 需要额外防护。若不能 pin 快照，就至少记录 resolved identity、建立变化告警并保留固定模型基线。provider fallback 后仍要重新检查地域、数据保留、工具能力与价格上限，不能假设备用端点继承所有约束。

漂移：分清哪一层变了

「质量下降」不是可操作告警。先区分：

  • 输入漂移：任务类型、语言、长度、租户或风险比例变化。
  • 能力漂移：模型快照、effort 语义、工具协议或提示模板变化。
  • 执行漂移：resolved provider、量化、地域、限流或 fallback 比例变化。
  • 经济漂移：价格、缓存命中、输出长度或工具成本变化。
  • 反馈漂移：judge、人工 rubric 或用户行为信号变化。

每层有不同 owner 与修复动作。输入漂移可能需要重采样/重训；能力漂移需要重跑 arm sweep；执行漂移由网关容量和 provider 策略处理；经济漂移可能只需重选工作点；反馈漂移先修评测，不能立即让 bandit 学习脏奖励。

监控至少包括候选过滤原因、模型/effort/provider 分布、各档接受与升级率、false downgrade、fallback 原因、完整成本、预算耗尽、尾延迟、receipt 缺失和重复副作用。报警应指向某一所有者，而不是把所有异常都发给「AI 团队」。

失败演练清单

上线前主动注入：模型别名突然变更、effort 参数被 provider 拒绝、第一 provider 限流、网关依赖存储不可用、judge 超时、价格注册表过期、预算预留成功但响应丢失、工具 effect 成功而收据写入延迟、高风险请求被路由器判为简单、最终档也不通过质量门。

每次演练验证四件事：状态机有界终止；用户收到明确语义；预算和副作用可对账；route plan 与 receipt 足以复盘。只有自动测试通过还不够，容量与依赖故障需要在接近真实拓扑的环境演练。

小结

  • 值得路由的前提是候选互补、质量可测、收益覆盖误判与运维成本；否则固定 arm 更好。
  • 先硬约束与规则，再影子、离线学习和有界在线适应；授权与合规不能交给分类器。
  • provider 可用性回退、模型/effort 质量升级和副作用执行是三条边界明确的状态机。
  • 发布与回滚针对完整版本元组，alias、adapter、prompt 和价格变化都可能使前沿失效。
  • 漂移按输入、能力、执行、经济与反馈分层，指标要能直接找到 owner 与动作。
