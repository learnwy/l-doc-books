Part IV · Control Plane模型路由与级联实践路由评测

路由评测

路由策略上线前必须回答：相对固定模型基线，它在什么质量约束下省了多少完整成本；错误集中在哪些请求；模型、effort、provider 或价格变化后结论是否仍成立。评的不是一个分类器，而是「策略 + 候选快照 + 推理强度 + 执行协议 + 价格快照」组成的系统。缺任一身份，漂亮曲线都不可复现。

核心概念：先定义实验 arm

把 model 当成 arm 远远不够。一个可复现实验 arm 至少是：

arm_id = hash(
  model_snapshot,
  effort,
  provider_constraints,
  prompt_and_template_version,
  tool_protocol,
  decoding_parameters,
  price_snapshot
)

同一模型改 effort 就是新 arm；alias 解析到新快照也是新 arm；工具 schema 或 chat template 变化仍会改变行为。provider 若只影响可用性可以作为分层变量，若不同端点有量化、上下文、工具能力或审查差异，就必须进入 arm 身份。

路由器本身也要钉住 policy_version、候选集 hash、特征版本与阈值。离线回放时，从 route receipt 还原「当时可选什么、最终选了什么」，而不是拿今天的注册表解释昨天的请求。

两层评测：离线筛选，在线拍板

flowchart TD
  Spec[冻结 arm/策略/数据协议] --> Off[离线回放与前沿]
  Off --> Gate{离线质量门}
  Gate -->|失败| Stop[停止/改策略]
  Gate -->|通过| Shadow[影子决策]
  Shadow --> Canary[低风险灰度]
  Canary --> AB[在线随机对照]
  AB --> Promote{业务与风险门}
  Promote -->|通过| Rollout[分阶段放量]
  Promote -->|失败| Rollback[回滚]

离线评测快、可复现，适合扫描阈值并画成本—质量前沿。在线评测捕获真实用户反馈、provider 容量与尾延迟，适合最后拍板。影子阶段只记录新策略选择，不改变用户路径；灰度阶段才让少量低风险流量执行新 arm。两层都不可省：离线数据会偏离生产，直接在线探索又会把误路由损失交给用户。

离线前沿：同一裁判、完整成本、独立数据

对每个请求收集所有候选 arm 的结果与质量，按策略选择 arm，再计算整体质量和完整成本。若强模型使用比例为 ccc，可在多个预算点比较路由质量 Qr(c)Q_r(c)Qr​(c)、随机基线 Qrand(c)Q_{rand}(c)Qrand​(c) 和先知上界 Qoracle(c)Q_{oracle}(c)Qoracle​(c)。APGR 一类指标可以压缩整条曲线，但不能替代原始分层结果。

离线核查有五个硬门。

硬门 合格证据 常见造假方式
裁判一致 所有 arm 用同一 rubric/协议 强弱模型用不同 judge
数据独立 训练、阈值校准、最终评测请求不重叠 用训练偏好直接画前沿
分布贴近 按线上任务、租户、风险与长度分层抽样 只用容易的公开聊天集
完整成本 路由器、judge、白跑、失败尝试、工具均计入 只算最终模型 token
身份冻结 模型/effort/provider/协议/价格都有快照 用可漂移 alias 和当前价回算

质量不能只看均值。至少报告高风险子集的 false downgrade rate、每类任务的 regret、最坏分位与灾难错误数。若某类请求一次错误不可逆，应设独立硬门，而不是允许其他简单请求的高分把它平均掉。

基准告诉我们什么，也告诉我们什么不能外推

RouteLLM 在 ICLR 2025 中提供二元强弱模型路由、成本—质量指标与可复现实验，是理解分类器路由的良好起点（RouteLLM）。RouterBench 收集了超过 405,000 条推理结果，用统一数据比较多模型路由，说明候选池与任务覆盖对结论至关重要（RouterBench）。

2026 年的 LLMRouterBench 进一步统一 21 个数据集、33 个模型和 10 类代表性路由基线。其关键发现不是「某个复杂路由器必胜」，而是统一协议下许多方法表现接近，一些近期方法与商业路由并未稳定超过简单基线，且与 oracle 仍有明显差距（LLMRouterBench, Findings of ACL 2026）。这对生产团队有两个直接提醒：

  1. 必须包含 fixed-best、random、简单规则或轻量分类器等强基线，不能只和明显差的全量小模型比。
  2. 公共 benchmark 证明方法可能有效，不证明它适合你的流量；真实工具协议、语言、租户、风险与价格仍要本地重测。

同模型 effort 路由还需要 effort sweep：固定模型快照，对每个支持档位收集质量、输出 token、思考 token（若可见）、工具调用数与延迟。不能假设档位质量严格单调，也不能把不支持的档位补成零结果。

在线实验：随机化单位与污染控制

在线 A/B 的随机化单位通常不是单条消息。多轮会话若在中途换策略，会产生上下文与缓存污染；更稳妥的是按用户或会话稳定分桶，并在实验期固定策略与 arm 版本。Agent 工作流还可能有长时任务，应按 run 分桶，防止同一任务前后步骤跨实验组。

在线指标至少分四组：

  • 质量：任务完成率、人工抽检、重试/纠正、工具结果验证、高风险错误。
  • 经济：完整每任务成本、预算耗尽率、白跑率、路由器与 judge 成本。
  • 性能：TTFT、完成延迟、p95/p99、排队、超时、各档到达率。
  • 可靠性：provider fallback、重试、拒绝、alias 变化、缺失 receipt、重复副作用。

灰度放量应由联合门控制。例如质量非劣、成本达到最小收益、p99 不恶化超过阈值、灾难错误为零。统计显著不等于业务可接受：极大流量下微小差异也显著，仍要先定义最小有意义效应和错误预算。

漂移与持续评测

路由前沿会因三类变化失效：输入分布变了，候选模型/effort 变了，价格或 provider 容量变了。监控要区分数据漂移、概念漂移和执行漂移。prompt 长度变化是数据漂移；同类请求的最佳 arm 改变是概念漂移；requested model 与 resolved model 不一致增加则是执行漂移。

触发重测的事件包括：模型快照或 alias 更新、价格变化、effort 支持表变化、system prompt/tool schema 更新、provider 量化/区域变化、任务分布越界，以及高风险误路由超预算。定时重测只是兜底，事件触发更及时。

历史样本要保留必要的可回放输入与最小证据，同时遵守隐私保留边界。不能为了评测无限期保存原始提示；可采用分层抽样、脱敏、派生特征与受控审计样本，并记录数据版本和删除策略。

小结

  • 实验 arm 是模型快照、effort、provider 约束、提示/工具协议、解码和价格快照的组合，不是一个裸 model 名。
  • 离线前沿负责筛选，影子与在线随机实验负责拍板；高风险请求需要独立硬门。
  • 完整成本必须包含路由器、judge、级联白跑、失败尝试和工具成本。
  • RouterBench 与 LLMRouterBench 提供统一比较框架，也提醒复杂方法未必稳定超过简单基线。
  • 模型、effort、协议、价格或执行解析变化都要触发重测，alias 不能充当可复现实验身份。
