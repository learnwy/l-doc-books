Skill 技能系统

核心概念

工具（Tool）提供的是原子级的操作能力——读文件、执行命令、搜索代码。但实际开发中的任务往往更复杂："为项目初始化 ESLint 配置"、"将组件从 Class 迁移到 Hooks"、"按照团队规范创建新的 API 模块"。这类任务需要编排多个工具、遵循领域知识、适配项目上下文。技能（Skill） 就是为解决这一层问题而设计的——它是将经验和流程封装为可复用的 Agent 能力单元。

简而言之：工具是手，技能是手艺。工具定义了 Agent 能做什么，技能定义了 Agent 该怎么做。

技能的触发流程
技能发现基于描述匹配机制：Agent 将用户意图与各技能的 description 字段进行语义比较，找到最相关的技能后加载其指令作为上下文的一部分，指导后续的工具调用。




关键要素
技能的结构（Skill Anatomy）
一个技能以 SKILL.md 文件的形式存在，包含以下核心字段：


---
name: create-react-component
description: 按照项目规范创建 React 函数组件，包含类型定义、样式文件和测试文件
when_to_use: 当用户要求创建新的 React 组件时
author: team-frontend
version: 1.0.0
---

# 创建 React 组件

## 执行步骤

1. 确认组件名称和目标目录
2. 检查项目是否使用 CSS Modules 或 Styled Components
3. 创建组件文件，遵循以下模板：
   - `ComponentName/index.tsx` — 组件入口
   - `ComponentName/ComponentName.tsx` — 组件实现
   - `ComponentName/ComponentName.module.css` — 样式文件
   - `ComponentName/ComponentName.test.tsx` — 测试文件
4. 在组件中导出类型定义（Props interface）
5. 确保组件使用项目中已有的 UI 库和工具函数

## 约束条件

- 使用函数组件，不使用 Class 组件
- Props 必须定义 interface，不使用 type alias
- 样式使用 CSS Modules，类名使用 camelCase
- 测试使用项目中已配置的测试框架
关键字段说明：






字段
作用





name
技能的唯一标识符，建议使用 kebab-case




description
自然语言描述，用于技能发现时的语义匹配




when_to_use
明确的触发条件，帮助 Agent 判断何时应用此技能




正文
详细的执行指令和约束条件，指导 Agent 的行为

---
name: init-node-project
description: 初始化 Node.js/TypeScript 项目，配置 ESLint、Prettier、tsconfig 等
when_to_use: 当用户要求创建或初始化新的 Node.js 项目时
---

# 初始化 Node.js 项目

## 步骤

1. 执行 `npm init -y` 创建 package.json
2. 安装 TypeScript 及相关依赖
3. 生成 tsconfig.json，使用严格模式配置
4. 配置 ESLint + Prettier
5. 创建 src/index.ts 入口文件
6. 添加 .gitignore
7. 配置 npm scripts: build, dev, lint, test

## 配置模板

### tsconfig.json

使用以下基础配置：

- target: ES2022
- module: NodeNext
- strict: true
- outDir: dist
示例二：代码审查技能
---
name: code-review
description: 对指定文件或变更进行代码审查，检查代码质量、安全性和性能
when_to_use: 当用户要求进行代码审查或 review 时
---

# 代码审查

## 检查清单

1. **类型安全**：是否存在 any 类型、类型断言滥用
2. **错误处理**：异步操作是否有 try-catch，边界条件是否处理
3. **安全性**：是否存在硬编码密钥、SQL 注入、XSS 风险
4. **性能**：是否有不必要的重复计算、内存泄漏风险
5. **可读性**：命名是否清晰、逻辑是否易于理解
6. **测试覆盖**：关键路径是否有测试

## 输出格式

按严重程度分类：🔴 严重 / 🟡 建议 / 🟢 亮点
示例三：技能与工具的协作
当用户说"帮我创建一个用户管理的 API 模块"时，Agent 的执行流程：


[1] 技能发现 → 匹配到 "create-api-module" 技能
[2] 加载技能指令 → 了解项目的 API 模块结构规范
[3] SearchCodebase → 查看现有 API 模块的写法
[4] ReadFile → 读取路由配置和中间件
[5] WriteFile → 创建 controller、service、route 文件
[6] WriteFile → 添加类型定义
[7] SearchReplace → 在路由注册表中添加新路由
[8] RunCommand → 运行 lint 和类型检查


常见误区
误区一：把工具当技能
工具是底层的原子操作，技能是高层的任务编排。将"读取文件"封装为技能毫无意义，因为它已经是一个工具。技能应聚焦于需要领域知识和多步骤编排的任务。


误区二：技能写得太笼统
"帮助用户编写代码"这样的描述过于宽泛，Agent 无法从中获取有用的指导信息。好的技能应该明确：做什么、怎么做、在什么约束下做。


误区三：技能写得太细碎
每个技能文件描述一个极小的操作（如"添加 import 语句"），会导致技能数量膨胀且难以维护。技能的粒度应该对应一个有意义的工作单元。


误区四：忽视技能的维护
项目在演进，技能也需要同步更新。过时的技能指令会误导 Agent，产出不符合当前项目规范的代码。建议定期审查技能内容，特别是在项目架构发生重大变化后。




小结
    

  • 技能是对经验和流程的封装，将多个工具调用编排成可复用的高层任务方案。
    • 

  • 技能以 SKILL.md 文件的形式存在，包含名称、描述、触发条件和执行指令。
    • 

  • 技能通过描述匹配机制被发现和触发，description 和 when_to_use 字段决定匹配精度。
    • 

  • 技能分为项目级（团队/项目特定）和全局级（跨项目通用）两种作用域。
    • 

  • 技能的粒度应对应一个有意义的工作单元——不能太细碎，也不能太笼统。
    • 

  • 技能需要随项目演进持续维护，过时的技能会误导 Agent 行为。
    •
