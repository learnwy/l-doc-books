Rule 规则系统

核心概念

工具赋予 AI Agent 行动能力，技能封装了任务经验，而规则（Rule） 则定义了 Agent 的行为边界。规则告诉 Agent："在这个项目中，你应该遵守这些约定"——比如代码风格、语言偏好、提交规范、安全策略等。没有规则的 Agent 就像没有编码规范的团队，输出质量完全取决于运气。

规则的本质是声明式的行为约束：你不需要告诉 Agent 如何实现约束，只需要声明约束是什么。Agent 会在每次生成内容时自动遵守已加载的规则。




工作原理
规则的加载流程
当 AI Agent 开始处理用户请求时，规则系统按以下流程工作：


规则被加载为系统提示（System Prompt）的一部分，直接影响模型的生成行为。与工具和技能不同，规则不会产生额外的工具调用——它们静默地约束 Agent 的每一次输出。


规则的类型
不同的 AI 编程工具对规则类型的划分各有差异，但核心模式可归纳为三类：






类型
触发条件
适用场景





始终生效（Always Apply）
每次对话都加载，无条件生效
全局代码风格、语言偏好、安全策略




文件匹配（Glob-scoped）
仅当操作的文件匹配指定 glob 模式时生效
特定文件类型的格式规范、框架约定




按需加载（Agent-requested）
Agent 根据任务上下文主动请求加载
特殊场景的规则，如数据库迁移、发布流程







关键要素
规则的结构（Rule Anatomy）
一个规则文件通常由 frontmatter（元数据）和 content（正文）两部分组成：


---
description: TypeScript 代码风格规则
globs: ['**/*.ts', '**/*.tsx']
alwaysApply: false
---

- 使用函数组件，不使用 Class 组件
- Props 使用 interface 定义，不使用 type alias
- 避免使用 any，优先使用 unknown 或具体类型
- 异步函数必须有错误处理
- 导出使用 named export，避免 default export
关键字段说明：






字段
类型
说明





description
string
规则的自然语言描述，用于按需加载时的匹配




globs
string[]
文件匹配模式，决定规则何时生效




alwaysApply
boolean
是否始终加载，不依赖文件匹配





规则的作用域
与技能类似，规则也分为项目级和用户级：


项目目录/
├── .trae/
│   └── rules/                   ← 项目级规则
│       ├── code-style.md
│       ├── doc-language.md
│       └── commit-rules.md
│
~/.trae-cn/
└── user_rules.md                ← 用户级规则




作用域
存放位置
共享范围
典型内容





项目级
<project>/.trae/rules/
团队共享，纳入版本控制
代码规范、框架约定、文档语言




用户级
~/.trae-cn/user_rules.md
仅个人生效
个人偏好、全局工具配置







提示： 项目级规则应纳入 Git 版本控制，确保团队成员使用一致的 AI 行为约束。用户级规则包含个人偏好，不应提交到仓库。




规则的大小限制
规则内容会被注入到上下文窗口中，因此需要控制大小：


    

  • 单条规则建议控制在 500 字节以内，最多不超过 1KB
    • 

  • 规则应精简、声明式，避免冗长的解释和示例
    • 

  • 如果规则内容超过 1KB，考虑拆分为多条规则或转化为技能
    •

# ✅ 规则精简有效
---
description: 代码风格
alwaysApply: true
---
- 变量/函数: camelCase
- 类/接口: PascalCase
- 常量: UPPER_SNAKE_CASE
- 文件名: kebab-case
- 缩进: 2 空格
- 引号: 单引号
- 分号: 不使用


实际应用
示例一：代码风格规则
---
description: TypeScript 编码规范
globs: ['**/*.ts', '**/*.tsx']
alwaysApply: false
---

- 使用 `const` 优先，必要时使用 `let`，禁止 `var`
- 函数参数超过 3 个时使用对象解构
- 避免嵌套超过 3 层的条件语句
- 异步操作使用 async/await，不使用 .then() 链
- 类型导入使用 `import type`
示例二：文档语言规则
---
description: 文档内容使用中文，文件名使用英文
alwaysApply: true
---

- docs/ 目录下的文档内容（标题、正文、表格、标签）使用中文
- 文件名、目录名、slug、JSON key 使用英文
- 代码语言由项目配置决定
示例三：Git 提交规则
---
description: Git 提交信息规范
alwaysApply: false
globs: []
---

- 提交信息使用 Conventional Commits 格式
- 类型: feat, fix, docs, style, refactor, test, chore
- 格式: <type>(<scope>): <description>
- description 使用英文，首字母小写，不加句号
- 单次提交只做一件事

Trae 的规则定义示例：


---
description: React 组件规范
globs: ['src/components/**/*.tsx']
alwaysApply: false
---

- 函数组件使用箭头函数
- Props interface 与组件同文件定义
- 使用 CSS Modules 管理样式
Claude Code 的 CLAUDE.md 示例：


# CLAUDE.md

## 代码风格

- TypeScript strict mode
- 使用 ESM imports
- 2 空格缩进

## 项目结构

- src/components — React 组件
- src/hooks — 自定义 Hooks
- src/utils — 工具函数

## 测试

- 使用 Vitest
- 测试文件放在 **tests** 目录
Cursor 的规则定义示例：


---
description: API 路由编写规范
globs: ['src/api/**/*.ts']
alwaysApply: false
---

- 路由使用 RESTful 命名
- 统一错误响应格式: { error: string, code: number }
- 所有路由必须包含输入验证
- 使用 zod 进行 schema 验证


常见误区
误区一：规则写成教程
规则应该是精简的声明，而不是详细的教学文档。"使用 camelCase 命名变量" 是好规则，"camelCase 是一种命名方式，它的特点是首字母小写，后续单词首字母大写，例如..." 则应该是文档而非规则。


误区二：规则相互矛盾
多条规则之间如果存在冲突，Agent 的行为会变得不可预测。例如，一条规则要求"使用 default export"，另一条要求"禁止 default export"。定义规则时应确保一致性。


误区三：所有规则都设为始终生效
将大量规则设为 alwaysApply: true 会消耗宝贵的上下文窗口。只有真正需要全局生效的规则（如语言偏好、安全策略）才应始终加载，其他规则应通过 glob 或按需加载的方式精确匹配。


误区四：规则替代代码检查工具
规则约束的是 AI 的生成行为，而非代码的最终质量保障。ESLint、Prettier 等工具提供的是确定性的代码检查和格式化，规则无法完全替代它们。两者应配合使用：规则引导 AI 生成符合规范的代码，Lint 工具作为最终的质量门禁。




小结
    

  • 规则是声明式的行为约束，告诉 AI Agent 在生成内容时应遵守哪些约定。
    • 

  • 规则分为三种类型：始终生效、文件匹配（glob-scoped）和按需加载（agent-requested）。
    • 

  • 规则文件由 frontmatter（元数据）和 content（正文）组成，支持 description、globs、alwaysApply 等字段。
    • 

  • 规则分为项目级（团队共享，纳入版本控制）和用户级（个人偏好）两种作用域。
    • 

  • 规则应保持精简（建议 <1KB），采用声明式表达，避免冗长解释。
    • 

  • 不同工具（Trae、Cursor、Claude Code 等）的规则格式各异，但核心理念一致。
    • 

  • 规则与 Lint 工具互补，前者引导生成，后者保障质量。
    •
