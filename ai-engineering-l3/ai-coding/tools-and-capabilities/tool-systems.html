Tool 工具系统

核心概念

大语言模型（LLM）的核心能力是文本生成，但仅靠生成文本无法完成实际的编程任务——它需要读取文件、执行命令、搜索代码库、访问网络。工具（Tool） 是 AI Agent 与外部世界交互的桥梁，每一种能力都被封装为一个可调用的函数，由模型在推理过程中自主决定何时、如何调用。

工具系统的核心思想是：模型负责决策，工具负责执行。模型根据用户意图判断需要调用哪个工具、传入什么参数，工具执行引擎负责真正的操作，并将结果返回给模型继续推理。




工作原理
Function Calling
Function Calling 是 OpenAI 率先提出的工具调用机制，已成为业界标准。其核心流程分为三步：


    

  1. 工具注册：开发者以 JSON Schema 的形式声明可用工具的名称、描述和参数结构
    2. 

  2. 模型决策：模型在推理时，根据上下文决定是否调用工具，并生成结构化的调用请求
    3. 

  3. 结果注入：工具执行后，结果以消息的形式插入对话上下文，模型基于结果继续生成
    4. 



{
  "type": "function",
  "function": {
    "name": "read_file",
    "description": "读取指定路径的文件内容",
    "parameters": {
      "type": "object",
      "properties": {
        "file_path": {
          "type": "string",
          "description": "要读取的文件的绝对路径"
        },
        "offset": {
          "type": "integer",
          "description": "起始行号，从 1 开始"
        },
        "limit": {
          "type": "integer",
          "description": "读取的最大行数"
        }
      },
      "required": ["file_path"]
    }
  }
}
模型生成的调用请求格式如下：


{
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "read_file",
        "arguments": "{\"file_path\": \"/src/index.ts\", \"limit\": 50}"
      }
    }
  ]
}
MCP（Model Context Protocol）
MCP 是 Anthropic 提出的开放协议，旨在标准化模型与外部工具、数据源之间的通信方式。如果说 Function Calling 解决的是"如何调用一个工具"，MCP 解决的则是"如何发现、连接和管理一组工具服务"。


MCP 的关键设计包括：


    

  • Client-Server 架构：AI 应用作为 Host 持有多个 MCP Client，每个 Client 连接一个 MCP Server
    • 

  • 协议标准化：工具的声明、调用、结果返回都遵循统一的 JSON-RPC 协议
    • 

  • 动态发现：Client 启动时自动获取 Server 提供的工具列表，无需硬编码
    • 

  • 传输层灵活：支持 stdio、HTTP+SSE 等多种传输方式
    • 



MCP Server 的配置示例：


{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-filesystem"],
      "env": {
        "ALLOWED_DIRS": "/Users/dev/projects"
      }
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}


关键要素
工具的分类
AI 编程助手中的工具可分为两大类：






类别
说明
典型示例





内置工具
由 AI IDE 或 Agent 框架直接提供，无需额外配置
文件读写、终端命令、代码搜索、Web 搜索




外部工具
通过 MCP 或插件机制动态加载的第三方能力
数据库查询、CI/CD 触发、Figma 设计稿解析





工具 Schema
每个工具都通过 JSON Schema 描述其接口契约。一个完整的工具定义包含：


interface ToolDefinition {
  name: string; // 工具名称，唯一标识
  description: string; // 自然语言描述，帮助模型理解何时使用
  parameters: JSONSchema; // 参数的 JSON Schema 定义
  required?: string[]; // 必填参数列表
}


提示： 工具的 description 字段极为关键——模型完全依赖自然语言描述来决定是否调用某个工具。描述不清晰会导致工具被误用或遗漏。

工具执行安全
工具赋予了 AI 在真实环境中执行操作的能力，因此安全控制至关重要：


安全控制的核心策略：


    

  • 分级权限：读操作（如文件读取、代码搜索）自动执行；写操作（如文件修改、命令执行）可能需要用户确认
    • 

  • 沙箱隔离：终端命令在受限环境中运行，限制可访问的目录和可执行的命令
    • 

  • 路径约束：文件操作限制在项目目录范围内，防止越权访问系统文件
    • 

  • 秘密保护：禁止在代码中硬编码密钥、令牌等敏感信息；环境变量通过引用传入
    • 





实际应用
一次典型的工具调用链
当用户要求"帮我修复这个 TypeScript 编译错误"时，Agent 的工具调用链可能如下：


用户: 帮我修复 src/utils.ts 的编译错误

[1] Agent 调用 RunCommand: npx tsc --noEmit
    → 获取编译错误信息

[2] Agent 调用 ReadFile: /src/utils.ts
    → 读取出错的源文件

[3] Agent 调用 SearchCodebase: "相关类型定义"
    → 查找关联的类型声明

[4] Agent 调用 SearchReplace: 修复类型错误
    → 编辑文件内容

[5] Agent 调用 RunCommand: npx tsc --noEmit
    → 验证修复结果

Agent: 已修复，问题是参数类型不匹配...
并行工具调用
现代 AI Agent 支持在一次推理中同时发起多个独立的工具调用，大幅提升效率：


{
  "tool_calls": [
    {
      "id": "call_1",
      "function": { "name": "ReadFile", "arguments": "{\"file_path\": \"/src/api.ts\"}" }
    },
    {
      "id": "call_2",
      "function": { "name": "ReadFile", "arguments": "{\"file_path\": \"/src/types.ts\"}" }
    },
    {
      "id": "call_3",
      "function": { "name": "Grep", "arguments": "{\"pattern\": \"fetchUser\", \"path\": \"/src\"}" }
    }
  ]
}


提示： 并行调用的前提是各工具之间没有依赖关系。如果后一个工具需要前一个工具的结果作为输入，则必须串行执行。






常见误区
误区一：工具越多越好
过多的工具会增加模型的选择困难，导致调用不准确或延迟增加。好的工具设计应该覆盖核心需求，保持工具集精简。


误区二：工具描述无所谓
模型完全依赖 description 来理解工具的用途和适用场景。模糊的描述会导致模型在不该调用时调用、在该调用时遗漏。编写描述时应明确说明工具的功能、适用场景和使用限制。


误区三：所有操作都需要用户确认
过度的审批机制会严重降低效率。合理的做法是对只读操作自动放行，仅对具有副作用的写操作（特别是不可逆操作）要求确认。


误区四：忽视工具调用的 Token 开销
每个工具的 Schema 定义都会占用上下文窗口。注册 50 个工具，每个工具描述 200 Token，仅工具声明就占用 10,000 Token。应根据当前任务动态加载相关工具，而非一次性注册所有工具。




小结
    

  • 工具是 AI Agent 与外部世界交互的基本单元，将文件操作、命令执行、搜索等能力封装为可调用的函数。
    • 

  • Function Calling 是工具调用的标准机制：模型生成结构化调用请求，执行引擎返回结果。
    • 

  • MCP 协议 标准化了工具服务的发现、连接和管理，支持动态扩展 Agent 能力。
    • 

  • 工具分为内置工具和外部工具，通过 JSON Schema 描述接口契约。
    • 

  • 执行安全是工具系统的核心考量，采用分级权限、沙箱隔离、路径约束等策略。
    • 

  • 并行调用可提升效率，但需确保工具之间无依赖关系。
    •
