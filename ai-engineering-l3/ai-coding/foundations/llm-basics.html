大语言模型基础

核心概念

大语言模型（Large Language Model，LLM）是一种基于 Transformer 架构的深度学习模型，通过在海量文本数据上训练，获得了理解和生成自然语言及代码的能力。LLM 是所有现代 AI 编程工具的核心引擎——无论是代码补全、对话式编程还是智能体系统，底层都依赖 LLM 的文本生成能力。

对于开发者而言，理解 LLM 不需要深入神经网络的数学细节，但需要掌握其核心工作机制和关键参数。这些知识将直接影响你使用 AI 编程工具的效果。



工作原理
下一个 Token 预测
LLM 的核心工作原理极其简洁：给定一段输入文本，预测下一个最可能出现的 Token。这个过程被称为自回归生成（Autoregressive Generation）。


输入: "function add(a: number, b: number): number {"
模型内部思考（简化）:
  → "return" 的概率: 0.85
  → "const" 的概率: 0.06
  → "if" 的概率: 0.04
  → 其他 Token: ...
输出: "return"

继续预测:
输入: "function add(a: number, b: number): number { return"
  → "a" 的概率: 0.72
  → "a + b" 会在后续 Token 中逐步生成
输出: "a"
模型并不"理解"代码的语义，而是基于训练数据中学到的统计模式来预测。但由于训练数据包含了海量高质量代码，这种统计预测在大多数场景下表现出了惊人的准确性。




提示： LLM 不会"执行"代码或"验证"逻辑正确性。它只是根据模式预测最可能的下一个 Token。这是理解 AI 编程工具局限性的关键。




Transformer 架构概览
LLM 基于 Transformer 架构，其核心机制是自注意力（Self-Attention）——模型在生成每个 Token 时，会"关注"输入序列中所有相关的 Token，而非仅关注相邻位置。


自注意力机制让模型能够捕捉长距离依赖关系。例如，在生成一个函数的返回值时，模型可以"关注"到几百个 Token 之前的函数签名和参数类型，从而生成类型正确的代码。




关键要素
Token 与分词
Token 是 LLM 处理文本的基本单位。在将文本输入模型之前，分词器（Tokenizer）会先将文本拆分为 Token 序列。Token 不等于单词——一个单词可能被拆为多个 Token，一个常见短语也可能合并为一个 Token。


输入文本: "function calculateTotal(items: Item[]): number {"
Token 化结果（示意）:
["function", " calculate", "Total", "(", "items", ":", " Item", "[]", "):", " number", " {"]
Token 数量: 11
不同模型使用不同的分词器，Token 边界也不同。分词对开发者的实际影响：

上下文窗口
上下文窗口（Context Window）是 LLM 一次能处理的最大 Token 数，包括输入（Prompt）和输出（Response）的总量。可以类比为模型的"工作记忆容量"。

上下文窗口对 AI 编程的影响是根本性的：


    

  • 窗口越大，工具能"看到"越多的代码文件和项目信息，生成结果越精准
    • 

  • 窗口是有限的，即使是 200K 的窗口也无法容纳一个大型项目的全部代码
    • 

  • 并非越多越好，过长的上下文可能导致模型"迷失"在信息中（称为 Lost in the Middle 问题）
    • 



这就是为什么 AI 编程工具需要精心的上下文管理策略——选择最相关的信息塞入有限的窗口。


Temperature 与采样参数
LLM 在预测下一个 Token 时，会为词表中的每个 Token 计算一个概率。采样参数决定了模型如何从这些概率中选择最终输出。


Temperature（温度） 控制输出的随机性：






Temperature 值
行为
适用场景





0
始终选择概率最高的 Token（贪婪解码）
代码生成、确定性任务




0.1–0.3
低随机性，输出较为稳定
代码补全、技术文档




0.7–0.9
中等随机性，输出更有创意
创意写作、头脑风暴




1.0+
高随机性，输出不可预测
极少使用





Top-p（核采样） 是另一种控制随机性的方式。它不直接调整概率分布，而是限定模型只从累积概率达到 p 值的最小 Token 集合中采样：


假设下一个 Token 的概率分布:
  "return"  → 0.60
  "const"   → 0.15
  "if"      → 0.10
  "let"     → 0.08
  "throw"   → 0.04
  其他      → 0.03

Top-p = 0.85 时:
  候选集 = {"return", "const", "if"} (累积概率 = 0.85)
  从这三个 Token 中按概率采样

Top-p = 0.95 时:
  候选集 = {"return", "const", "if", "let"} (累积概率 = 0.93 → 加入下一个至 ≥ 0.95)
  从更大的候选集中采样


提示： 对于代码生成任务，建议使用较低的 Temperature（0–0.3）以保证输出的确定性和正确性。大多数 AI 编程工具已内置了合理的默认值。

在 AI 编程工具中，开发者通常只直接编写用户提示。但系统提示同样至关重要——它通过规则文件（如 .trae/rules/、.cursorrules）来定义，决定了 AI 的编码风格、语言偏好和行为约束。




实际应用
LLM 如何生成代码
理解 LLM 逐 Token 生成代码的过程，有助于理解 AI 编程工具的行为：


interface User {
  id: string;
  name: string;
  email: string;
  createdAt: Date;
}

function findUserByEmail(users: User[], email: string): User | undefined {
  return users.find((user) => user.email === email);
}
上面这段代码在 LLM 看来，是一个 Token 接一个 Token 依次生成的序列。模型在生成 find 时，"注意力"会关注到参数名 email 和类型 User[]；在生成箭头函数体时，会关注到外部参数 email 和 User 接口的 email 属性。

模型选择的考量
不同场景下应选择不同的模型：


代码补全（低延迟优先）:
  推荐: 小型快速模型
  原因: 补全需要毫秒级响应，精度要求适中

复杂代码生成（质量优先）:
  推荐: 大型旗舰模型（Claude Sonnet, GPT-4o）
  原因: 复杂逻辑需要更强的推理能力

智能体任务（综合能力）:
  推荐: 旗舰模型 + 大上下文窗口
  原因: 需要理解大量代码、多步推理、工具调用


常见误区
误区一：LLM "理解"代码
LLM 不具备人类意义上的"理解"。它通过统计模式匹配来生成看起来正确的输出。当模式匹配与实际语义一致时（大多数常见场景），输出是正确的；当场景偏离训练分布时，模型可能自信地输出错误结果。


误区二：上下文窗口越大越好
更大的上下文窗口确实能容纳更多信息，但研究表明，模型在超长上下文中会出现"注意力稀释"——对中间位置的信息关注度下降。有效利用上下文窗口比盲目扩大窗口更重要。


误区三：Temperature 为 0 就完全确定
即使 Temperature 设为 0，不同的推理框架和硬件环境也可能导致浮点精度差异，从而产生微妙的输出差异。在绝大多数场景下可以视为确定性输出，但不应假设 100% 一致。


误区四：Token 数等于字数
Token 和字符/单词的对应关系因语言和分词器而异。英文中大约 1 Token ≈ 0.75 个单词；中文中 1 个汉字可能消耗 1–3 个 Token。在估算上下文用量时，不能简单地用字数来换算。




小结
    

  • LLM 的核心原理是下一个 Token 预测——逐个生成 Token，基于统计模式而非真正"理解"。
    • 

  • Token 是 LLM 处理文本的基本单位，直接影响 API 成本和上下文容量。
    • 

  • 上下文窗口是模型的工作记忆上限，需要通过上下文管理策略来高效利用。
    • 

  • Temperature 和 Top-p 控制输出的随机性，代码生成任务应使用低 Temperature。
    • 

  • 系统提示定义 AI 的全局行为，在 AI 编程工具中对应规则文件。
    • 

  • 模型的局限性（幻觉、训练截止日期、长上下文注意力衰减）决定了开发者必须始终审查输出。
    •
