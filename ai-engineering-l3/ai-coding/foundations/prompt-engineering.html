提示工程

核心概念

提示工程（Prompt Engineering）是设计和优化发送给大语言模型的输入（Prompt），以获得期望输出的系统方法论。在 AI 编程的语境下，提示工程不仅仅是"写好问题"——它是开发者与 AI 协作的核心接口，直接决定了代码生成的质量、准确性和可用性。

一个好的提示应该做到三点：明确意图——告诉 AI 你要什么；提供上下文——给 AI 足够的背景信息；约束输出——限定 AI 的输出格式和范围。




提示： 在 AI 编程工具（如 Trae、Cursor）中，工具本身会自动处理大量上下文工程（收集文件、注入规则），但开发者编写的用户提示仍然是影响输出质量的关键变量。






工作原理
提示的处理流程
当你在 AI 编程工具中输入一条指令时，工具会将你的输入与大量额外信息组装成最终发送给 LLM 的完整 Prompt：


最终 Prompt 的结构通常如下：


┌─────────────────────────────────────┐
│  系统提示（System Prompt）            │
│  - 工具内置指令                       │
│  - 用户规则文件内容                    │
│  - 行为约束和偏好设置                  │
├─────────────────────────────────────┤
│  上下文信息                           │
│  - 当前文件内容                       │
│  - 相关文件片段                       │
│  - 项目结构信息                       │
├─────────────────────────────────────┤
│  历史对话（多轮场景）                  │
│  - 之前的用户消息                     │
│  - 之前的助手回复                     │
├─────────────────────────────────────┤
│  当前用户提示                         │
│  - 开发者的具体指令                    │
└─────────────────────────────────────┘
开发者可以直接控制的部分是用户提示和规则文件。提示工程的目标就是最大化这两部分的有效性。




关键要素
系统提示
系统提示定义了 AI 的"身份"和"行为边界"。在 AI 编程工具中，系统提示由两部分组成：工具内置的基础提示和用户自定义的规则文件。


规则文件是开发者影响系统提示的主要方式：


# 项目规则

- 使用 TypeScript 严格模式
- 所有函数必须有显式返回类型
- 不允许使用 any 类型
- 优先使用 const 和 readonly
- 错误处理使用自定义 Result 类型
- 组件使用函数式风格，不使用 class 组件
好的系统提示应该遵循以下原则：






原则
说明
示例





具体而非笼统
给出明确规则而非模糊指导
✅ "使用 const 声明" ❌ "写好代码"




正面表述
告诉 AI 该做什么而非不该做什么
✅ "使用 unknown 替代 any" ❌ "不要用 any"




可验证
规则应该是客观可检查的
✅ "函数不超过 30 行" ❌ "函数要简洁"




分层组织
按优先级或类别分组
代码风格、命名规范、架构约束





少样本示例
少样本提示（Few-Shot Prompting）是在提示中提供若干输入-输出示例，引导 LLM 按照相同模式生成输出。这是最有效的提示技巧之一。


请为以下 TypeScript 函数生成单元测试。遵循如下模式：

示例输入:
function add(a: number, b: number): number {
  return a + b;
}

示例输出:
describe('add', () => {
  it('should add two positive numbers', () => {
    expect(add(2, 3)).toBe(5);
  });

  it('should handle negative numbers', () => {
    expect(add(-1, 1)).toBe(0);
  });

  it('should handle zero', () => {
    expect(add(0, 0)).toBe(0);
  });
});

现在请为这个函数生成测试:
function multiply(a: number, b: number): number {
  return a * b;
}
少样本示例的关键在于：


    

  • 示例数量：1–3 个通常就够，过多示例会浪费上下文窗口
    • 

  • 示例质量：示例应该体现你期望的风格、格式和覆盖范围
    • 

  • 示例多样性：覆盖不同的边界情况和场景
    • 



思维链
思维链（Chain-of-Thought，CoT）是引导 LLM 分步骤推理，而非直接给出最终答案。对于复杂的编程任务，思维链能显著提升输出质量。


零样本思维链（添加 "请分步骤思考"）:

Prompt:
  请分步骤分析以下代码的性能问题，然后给出优化方案：

  function findDuplicates(arr: number[]) {
    const result: number[] = [];
    for (let i = 0; i < arr.length; i++) {
      for (let j = i + 1; j < arr.length; j++) {
        if (arr[i] === arr[j]) {
          result.push(arr[i]);
        }
      }
    }
    return result;
  }

模型输出（分步推理）:
1. 时间复杂度分析：双层循环 → O(n²)
2. 空间问题：result 可能包含重复元素
3. 优化方向：使用 Set 将复杂度降为 O(n)
4. 最终方案：[优化后的代码]
思维链的几种变体：

结构化输出
结构化输出（Structured Output）是约束 LLM 以特定格式返回结果，便于程序化处理。


请分析以下函数，以 JSON 格式返回结果：

function processOrder(order: Order): ProcessedOrder {
  // ...
}

请按如下格式返回：
{
  "functionName": "函数名称",
  "parameters": [{"name": "参数名", "type": "类型"}],
  "returnType": "返回类型",
  "complexity": "simple | moderate | complex",
  "suggestions": ["改进建议1", "改进建议2"]
}
结构化输出在以下场景特别有用：


    

  • 代码审查报告（结构化的问题列表）
    • 

  • API 文档生成（统一的格式）
    • 

  • 测试用例生成（可直接运行的代码）
    • 

  • 智能体的工具调用（必须返回特定 JSON Schema）
    • 



提示模板
提示模板（Prompt Template）是预定义的、可复用的提示结构。将常用的提示模式模板化，可以提高一致性和效率。


type PromptTemplate = {
  role: string;
  context: string;
  task: string;
  constraints: string[];
  outputFormat: string;
};

const codeReviewTemplate: PromptTemplate = {
  role: '你是一位资深 TypeScript 代码审查员',
  context: '以下代码来自 {{projectName}} 项目的 {{moduleName}} 模块',
  task: '请对代码进行全面审查',
  constraints: ['关注类型安全性', '检查错误处理是否完善', '评估性能影响', '检查是否符合项目规范'],
  outputFormat: '按严重程度（高/中/低）分类列出问题',
};


实际应用
面向编程任务的常用提示模式
以下是在 AI 编程中最实用的提示模式：


模式一：角色 + 任务 + 约束


角色: 你是一位 TypeScript 专家，熟悉 Node.js 后端开发。
任务: 实现一个速率限制中间件。
约束:
- 使用滑动窗口算法
- 支持按 IP 和按用户两种维度
- 配置项通过参数传入
- 包含完整的类型定义
模式二：上下文 + 指令 + 示例


上下文: 我正在开发一个电商平台的订单模块。当前使用 Express + TypeORM。

指令: 为订单创建接口添加参数校验。

参考现有的用户注册接口的校验方式:
const validateCreateUser = [
  body('email').isEmail().normalizeEmail(),
  body('password').isLength({ min: 8 }),
];
模式三：问题 + 当前代码 + 期望行为


问题: 当并发请求时，计数器值不正确。

当前代码:
let counter = 0;
app.post('/increment', (req, res) => {
  counter++;
  res.json({ counter });
});

期望行为: 即使在高并发场景下，计数器也应该正确递增。
模式四：渐进式细化


第一轮: "创建一个用户认证模块的类型定义"
  → AI 生成基础类型

第二轮: "添加 JWT Token 的刷新机制类型"
  → AI 在已有类型基础上扩展

第三轮: "加上角色权限控制，支持 RBAC 模型"
  → AI 继续细化

第四轮: "为所有公开接口添加 JSDoc 注释"
  → AI 完善文档
这种渐进式细化的策略比一次性描述全部需求更有效，因为每一轮 AI 都能基于上一轮的确定输出继续构建。

在 AI 编程工具中的应用
不同类型的 AI 编程工具中，提示工程的应用方式有所不同：


在代码补全中，提示工程体现为：编写清晰的函数签名和注释，让补全引擎有足够线索：


interface PaginationOptions {
  page: number;
  pageSize: number;
  sortBy?: string;
  sortOrder?: 'asc' | 'desc';
}

interface PaginatedResult<T> {
  data: T[];
  total: number;
  page: number;
  pageSize: number;
  totalPages: number;
}

function paginate<T>(items: T[], options: PaginationOptions): PaginatedResult<T> {
  // AI 补全引擎在此处有足够的类型信息来生成正确的实现
}
在智能体工具中，提示工程扩展为规则文件系统：


# .trae/rules/coding-standards.yaml
code_style:
  language: typescript
  strict_mode: true
  prefer_const: true
  max_function_lines: 30

error_handling:
  pattern: result_type
  never_throw: true
  always_handle_errors: true

testing:
  framework: vitest
  min_coverage: 80
  require_edge_cases: true


常见误区
误区一：提示越详细越好
过度详细的提示可能导致 AI 过度关注细节而忽视整体目标。好的提示应该在"足够具体"和"保留灵活性"之间取得平衡。提供约束和方向，而非微观控制每一步。


误区二：提示工程可以替代领域知识
提示工程是与 AI 沟通的技巧，但无法弥补对业务逻辑和技术栈的不了解。如果你不理解需求本身，再精巧的提示也无法产出正确的代码。开发者的专业知识仍然是保障输出质量的根基。


误区三：固定一套提示模板就够了
不同类型的任务需要不同的提示策略。代码生成、Bug 修复、架构设计、代码审查——每种任务的最优提示结构差异显著。应根据任务特点灵活选择和组合提示模式。


误区四：忽视系统提示的作用
许多开发者只关注用户提示，忽视了通过规则文件影响系统提示的重要性。系统提示对每次交互都起作用，是建立一致编码标准的最有效手段。投入时间完善规则文件，会在长期持续产生回报。


误区五：不迭代提示
第一版提示很少是最优的。应该将提示视为代码一样进行迭代优化——观察输出、分析偏差、调整提示、再次验证。优秀的提示工程是一个持续改进的过程。




小结
    

  • 提示工程是设计 LLM 输入以获得高质量输出的方法论，是开发者与 AI 协作的核心技能。
    • 

  • 好的提示应做到明确意图、提供上下文、约束输出三个要素。
    • 

  • 系统提示通过规则文件定义，影响每次交互的行为，是建立编码标准的长效手段。
    • 

  • 少样本示例是最有效的提示技巧之一，1–3 个高质量示例通常就足够。
    • 

  • 思维链引导 AI 分步推理，对复杂编程任务有显著的质量提升。
    • 

  • 结构化输出约束 AI 以特定格式返回结果，便于程序化处理。
    • 

  • 编程任务中最常用的提示模式包括：角色+任务+约束、上下文+指令+示例、渐进式细化。
    • 

  • 提示工程应持续迭代优化，不存在"一劳永逸"的完美提示。
    •
