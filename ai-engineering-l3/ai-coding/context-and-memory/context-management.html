Context 上下文管理

核心概念

在 AI 编程中，上下文（Context）是指大语言模型在一次推理过程中能够"看到"的全部信息。它包括系统提示词、用户消息、工具调用结果、文件内容等所有输入。上下文的质量直接决定了 AI 输出的质量——正确的上下文带来精准的代码建议，错误或不足的上下文则导致幻觉和无关回答。

上下文窗口（Context Window）是模型一次能处理的 token 总量上限。所有输入和输出共享这个窗口，因此合理分配上下文预算是 AI 编程工具的核心挑战之一。

提示： 1 个 token 大约对应 4 个英文字符或 1-2 个中文字符。一行代码平均约 40 个 token。




窗口的扩大并不意味着可以无脑地塞入所有内容。研究表明，即使模型支持超长上下文，关键信息在窗口中间位置时的召回率依然会下降（即"Lost in the Middle"问题）。因此，信息的位置和密度同样重要。


上下文的组成部分
一次典型的 AI 编程交互中，上下文由以下几个层次构成：


各部分的 token 消耗比例示例：


context_budget:
  system_prompt: ~2000 tokens
  tool_descriptions: ~3000 tokens
  conversation_history: ~8000 tokens
  tool_results: ~15000 tokens
  file_content: ~20000 tokens
  reserved_for_output: ~4000 tokens
  total: ~52000 tokens
上下文预算管理
AI 编程工具通过多种策略来管理有限的上下文预算：


1. 截断与摘要：对话历史过长时，工具会截断早期消息或将其压缩为摘要。


interface ConversationManager {
  messages: Message[];
  maxTokens: number;

  truncate(): void;
  summarize(messages: Message[]): Message;
  getContextWindow(): Message[];
}
2. 按需加载：不将整个代码库塞入上下文，而是根据用户当前的问题动态检索相关代码片段。


3. 优先级排序：最近编辑的文件、当前打开的标签页、用户显式引用的文件优先级最高。




关键要素
检索增强生成（RAG）
RAG（Retrieval-Augmented Generation）是解决上下文窗口限制的核心技术。其基本思路是：不在上下文中放入所有信息，而是建立外部知识库，根据用户查询动态检索最相关的内容注入上下文。


在代码场景中，RAG 的典型流程如下：


interface CodeRAGPipeline {
  embed(code: string): number[];
  index(files: string[]): void;
  retrieve(query: string, topK: number): CodeSnippet[];
  augment(query: string, snippets: CodeSnippet[]): string;
}

interface CodeSnippet {
  filePath: string;
  content: string;
  startLine: number;
  endLine: number;
  similarity: number;
}

@-mentions 与文件引用
在 AI 编程工具中，@-mentions 是用户主动控制上下文的核心机制。通过 @文件名、@符号名 等语法，用户可以精确指定哪些信息应该被加入上下文：


@src/utils/auth.ts 这个认证模块的 token 刷新逻辑有 bug，
刷新失败时没有正确清除旧 token。请帮我修复。
工具收到 @-mention 后，会将指定文件的完整内容或相关符号定义读入上下文，确保 AI 拥有足够的信息来理解和修改代码。


常见的引用方式：


@file        → 引用整个文件
@symbol      → 引用特定函数/类/变量的定义
@folder      → 引用目录结构和关键文件
@docs        → 引用项目文档
@web         → 引用网络搜索结果
@codebase    → 触发全代码库语义搜索


实际应用
场景：大型项目中的精准上下文
在一个拥有数百个文件的项目中，开发者需要 AI 帮忙重构一个跨多模块的功能。直接将所有相关文件塞入上下文会超出窗口限制。合理的做法是：


# 1. 使用 @codebase 让 AI 先理解项目结构
"@codebase 帮我梳理用户认证模块涉及哪些文件"

# 2. 根据 AI 的分析，精确引用关键文件
"@src/auth/token.ts @src/auth/middleware.ts @src/api/user.ts
请将 token 刷新逻辑从同步改为异步"

# 3. AI 在有限的上下文中获得了最关键的信息
场景：上下文污染的处理
长对话中，早期的错误尝试和无关讨论会"污染"上下文，干扰 AI 的判断。处理方式包括：


✅ 开启新对话：清空上下文，从干净状态开始
✅ 明确纠正：在消息中显式告知 "忽略之前的方案，重新考虑"
✅ 精简引用：只 @-mention 当前真正需要的文件
❌ 在同一对话中反复修改需求，导致上下文充斥矛盾信息


常见误区
误区一：上下文越多越好
将大量文件不加筛选地塞入上下文，反而会降低 AI 的表现。模型需要在海量无关信息中寻找关键内容，容易分散注意力。


误区二：忽略上下文窗口限制
当输入超出上下文窗口时，模型会静默截断最早的内容。开发者可能以为 AI 仍然记得对话开头的约定，但实际上那些信息已经丢失。


误区三：只依赖自动上下文
虽然 AI 工具会自动收集当前文件、最近编辑等信息，但在复杂场景下，开发者主动使用 @-mention 精确控制上下文，效果远优于完全依赖自动机制。


误区四：混淆上下文与记忆
上下文是单次对话中可见的信息，它随对话结束而消失。记忆是跨会话持久化的信息。两者互补但本质不同——上下文决定"这一轮 AI 能看到什么"，记忆决定"AI 在新会话中还能记住什么"。




小结
    

  • 上下文是 LLM 在一次推理中能看到的全部信息，由系统提示词、对话历史、工具结果和文件内容组成。
    • 

  • 上下文窗口从 4K 演进到 1M tokens，但窗口大小不等于有效信息量，信息的质量和位置同样关键。
    • 

  • 上下文预算管理通过截断、摘要、按需加载和优先级排序来最大化有限窗口的利用率。
    • 

  • RAG 是突破上下文窗口限制的核心技术，通过外部索引和动态检索将最相关的代码片段注入上下文。
    • 

  • @-mentions 让开发者主动控制上下文，是在复杂项目中获得精准 AI 帮助的关键手段。
    • 

  • 上下文与记忆是互补概念：上下文管理单次会话的可见信息，记忆管理跨会话的持久知识。
    •
