Spec 规范驱动开发

核心概念

规范驱动开发（Spec-Driven Development，简称 SDD）是一种先定义规范，再编写代码的开发范式。在 AI 编程的语境下，它的核心思想是：在让 AI 动手写代码之前，先用结构化的文档描述清楚"要做什么"、"怎么验证"和"有哪些约束"。

传统开发中，开发者习惯于"边想边写"——需求在脑中形成，代码随手敲出。这种方式对经验丰富的人类开发者或许可行，但对 AI 来说极易导致偏离意图、遗漏边界条件、产出不可控的结果。SDD 的价值在于：把隐性的需求变成显性的文档，把模糊的期望变成可验证的标准。




提示： SDD 并非要求你写出完美无缺的规范文档。一份 80% 准确的规范，已经远好于 0% 的规范。规范是"活文档"，可以在执行过程中迭代修正。






工作原理
SDD 的工作流程由三个核心文档和四个阶段组成。


三个核心文档




文档
作用
关键内容





spec.md
定义需求、约束和接口
功能描述、API 设计、技术约束




tasks.md
将规范拆解为可执行的任务列表
任务编号、依赖关系、完成标准




checklist.md
定义验证标准，确认实现是否达标
功能检查项、边界条件、性能要求





spec.md 结构
# 功能名称

## 需求描述

- 用户故事或功能目标的简要说明

## 技术约束

- 使用的框架/语言版本
- 性能要求（如响应时间 < 200ms）
- 兼容性要求

## API 设计

- 接口定义（输入、输出、错误处理）

## 数据模型

- 关键实体及其关系

## 非功能性需求

- 安全性、可维护性、可测试性等
tasks.md 结构
# 任务清单

## 阶段一：基础设施

- [x] 1.1 创建项目目录结构
- [x] 1.2 配置 TypeScript 和 ESLint
- [ ] 1.3 搭建数据库迁移脚本

## 阶段二：核心逻辑

- [ ] 2.1 实现用户认证模块
- [ ] 2.2 实现数据校验层
- [ ] 2.3 编写单元测试

## 阶段三：集成与部署

- [ ] 3.1 API 集成测试
- [ ] 3.2 CI/CD 流水线配置
checklist.md 结构
# 验证清单

## 功能验证

- [ ] 所有 API 端点返回正确的状态码
- [ ] 错误场景返回规范化的错误信息
- [ ] 边界输入（空值、超长字符串）处理正确

## 质量验证

- [ ] 单元测试覆盖率 > 80%
- [ ] 无 TypeScript 类型错误
- [ ] ESLint 检查通过

## 性能验证

- [ ] 核心接口响应时间 < 200ms
- [ ] 无内存泄漏


关键要素
SDD 工作流的四个阶段
阶段一：编写规范。 人类开发者（或在 AI 辅助下）撰写 spec.md，明确功能目标、技术约束和接口设计。这一步的关键是足够具体——不要写"实现一个好用的搜索功能"，而要写"实现基于关键词的全文搜索，支持分页，每页 20 条，响应时间 < 500ms"。


阶段二：分解任务。 基于 spec.md 生成 tasks.md。AI 工具擅长这一步——给它一份规范，它能快速拆解出结构化的任务列表。任务之间应有清晰的依赖关系和执行顺序。


阶段三：逐项实现。 AI 按照 tasks.md 中的顺序逐个实现。每完成一项任务就运行测试，确保不引入回归问题。


阶段四：逐项验证。 根据 checklist.md 逐条检查。未通过的项目回到实现阶段修复。


AI 工具如何实现 SDD
不同的 AI 编程工具以不同方式支持 SDD 理念：






工具/模式
SDD 支持方式





Trae Spec 模式
内置 spec 文件生成，自动从 spec 提取任务并逐步执行




Claude Code
通过 CLAUDE.md 定义项目规范，利用 TodoWrite 管理任务




Cursor Rules
通过 .cursorrules 文件定义编码规范，AI 在生成时自动遵守




手动 SDD
在任何 AI 工具中手动创建 spec/tasks/checklist 文件







提示： 即使你使用的 AI 工具没有内置 Spec 模式，你也可以手动实践 SDD。核心不在于工具，而在于"先规范、后编码"的思维方式。






实际应用
示例：为 REST API 编写规范
假设你要开发一个用户管理模块，以下是 SDD 的实际操作过程。


第一步：编写 spec.md


# spec.md - 用户管理模块

功能目标: 实现用户的增删改查 REST API
技术栈: Node.js + Express + TypeScript
数据库: PostgreSQL

API 端点:
  - POST /api/users # 创建用户
  - GET /api/users/:id # 获取用户详情
  - PUT /api/users/:id # 更新用户信息
  - DELETE /api/users/:id # 删除用户

约束:
  - 密码必须加密存储
  - 所有端点需要 JWT 认证（创建用户除外）
  - 输入校验使用 zod
  - 响应格式统一为 { code, data, message }
第二步：让 AI 生成 tasks.md


提示词: "根据 spec.md 生成 tasks.md，将任务按阶段组织，标注依赖关系。"
AI 会输出结构化的任务列表，包含依赖关系和预估工作量。


第三步：逐步实现与验证


# AI 按任务顺序执行
# 每完成一个任务，运行测试
npm run test
npm run lint
npm run typecheck
适用场景判断


常见误区




误区
问题
正确做法





规范写得过于笼统
AI 理解模糊，产出不可控
用具体的数据格式、约束条件和示例代替模糊描述




规范写得过于详细
花费过多时间在文档上，降低开发效率
抓住关键约束和接口定义，实现细节留给代码




认为规范不可修改
实现过程中发现问题却不敢改规范
规范是活文档，发现问题应及时更新




跳过验证阶段
实现完就认为"做完了"
严格按照 checklist 逐条验证




只给 AI 看 spec，不看 tasks
AI 缺乏执行顺序的上下文，容易乱序实现
spec 和 tasks 配合使用




把 SDD 当作银弹
对简单任务也强制走全流程，效率反而降低
根据任务复杂度灵活选择 SDD 的深度







小结
    

  • 规范驱动开发（SDD）的核心是先规范、后编码，通过结构化文档为 AI 提供明确的上下文和约束。
    • 

  • SDD 依赖三个关键文档：spec.md（需求与约束）、tasks.md（任务分解）、checklist.md（验证标准）。
    • 

  • 完整的 SDD 工作流包含四个阶段：编写规范 → 分解任务 → 逐项实现 → 逐项验证。
    • 

  • SDD 的深度应与任务复杂度匹配——简单任务直接编码，复杂任务需要完整的规范流程。
    • 

  • SDD 不依赖特定工具，核心是一种思维方式：把隐性需求显性化，把模糊期望可验证化。
    •
