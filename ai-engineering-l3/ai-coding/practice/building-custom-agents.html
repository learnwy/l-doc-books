构建自定义 Agent

场景描述

通用的 AI 编程助手能处理大多数日常任务，但在特定领域或重复性工作流中，自定义 Agent（技能/规则/工作流）能带来质的飞跃。通过定义项目规则、创建可复用技能、设计 Agent 行为，你可以让 AI 更精准地理解你的项目上下文，并自动化那些高频但繁琐的开发任务。



核心原则
规则、技能与 Agent 的关系
理解三者的区别和协作方式是构建自定义 Agent 的基础：






概念
定义
作用范围
示例





规则（Rule）
对 AI 行为的约束和偏好设定
项目级或全局级
"使用函数式组件"、"不添加注释"




技能（Skill）
可复用的任务执行模板
可跨项目共享
"生成 API 文档"、"创建组件"




Agent
结合规则和技能的智能执行体
特定工作流
"代码审查 Agent"、"文档生成 Agent"





配置层级与优先级
当全局规则和项目规则冲突时，遵循就近原则：


优先级从高到低：
1. 用户当前对话中的指令
2. 项目级规则（.trae/rules/）
3. 项目级技能（.trae/skills/）
4. 全局规则（~/.trae-cn/skills/）
5. AI 的默认行为


提示： 项目级配置始终优先于全局配置。这确保了每个项目可以有独立的规范，不受全局设定的干扰。






操作步骤
步骤一：创建项目规则
项目规则定义了 AI 在该项目中应遵循的行为约束。规则文件存放在 .trae/rules/ 目录下：


mkdir -p .trae/rules
<!-- .trae/rules/code-style.md -->

# 代码风格规则

- 使用 TypeScript strict 模式
- 组件使用函数式写法，不使用 class
- 所有异步操作使用 async/await
- 错误处理使用 Result 模式而非 try-catch
- 不添加代码注释，代码应自解释
- 命名规范：
  - 变量和函数：camelCase
  - 类型和接口：PascalCase
  - 常量：UPPER_SNAKE_CASE
  - 文件名：kebab-case
<!-- .trae/rules/architecture.md -->

# 架构规则

- 项目采用分层架构：Controller → Service → Repository
- 每层通过接口解耦，禁止跨层直接调用
- 所有外部依赖通过依赖注入引入
- 数据库操作只允许在 Repository 层
- API 响应统一使用 { success, data?, error? } 结构
步骤二：理解 SKILL.md 文件结构
技能文件（SKILL.md）是自定义 Agent 的核心构建单元。它定义了一个可复用的任务模板：


<!-- .trae/skills/component-generator/SKILL.md -->

# 组件生成器

## 描述

根据组件名称和属性定义，生成符合项目规范的 React 函数式组件。

## 触发条件

当用户请求创建新组件时触发。

## 输入

- `name`: 组件名称（PascalCase）
- `props`: 属性列表及类型
- `variant`: 组件类型（page | feature | ui）

## 执行步骤

1. 在对应目录创建组件文件
   - page → `src/pages/{name}/`
   - feature → `src/features/{name}/`
   - ui → `src/components/ui/{name}/`
2. 生成组件代码，遵循项目代码风格规则
3. 生成对应的测试文件
4. 生成 index.ts 导出文件
5. 在父目录的 index.ts 中添加导出

## 输出模板

```typescript
interface {Name}Props {
  // 根据输入的 props 生成
}

export function {Name}({ ...props }: {Name}Props) {
  return (
    <div>
      {/* 组件内容 */}
    </div>
  );
}
```

## 约束

- 必须遵循 .trae/rules/code-style.md
- 测试使用 vitest
- 不生成 CSS 文件，样式使用 Tailwind
步骤三：设计 Agent 行为
Agent 行为定义了 AI 在特定工作流中的完整执行逻辑：


# .trae/skills/doc-generator/SKILL.md 的行为定义
agent_behavior:
  name: doc-generator
  description: 根据代码自动生成 API 文档

  workflow:
    - step: scan
      action: 扫描 src/ 目录下所有导出的函数和类型
      output: 函数签名列表

    - step: analyze
      action: 分析每个函数的参数、返回值和用途
      output: 函数文档草稿

    - step: generate
      action: 按照模板生成 Markdown 文档
      template: docs/api/{module-name}.md
      output: 文档文件

    - step: validate
      action: 检查文档的完整性和格式
      checks:
        - 所有公开函数是否都有文档
        - 参数描述是否完整
        - 返回值是否说明
        - 示例代码是否可运行
步骤四：Skill Creator 工作流
使用 skill-creator 快速生成新技能的标准流程：


# 创建项目级技能
mkdir -p .trae/skills/my-skill
touch .trae/skills/my-skill/SKILL.md

# 创建全局级技能
mkdir -p ~/.trae-cn/skills/my-skill
touch ~/.trae-cn/skills/my-skill/SKILL.md
步骤五：测试和迭代
技能创建后需要反复测试和优化：


测试流程：
1. 用简单的输入测试技能的基本功能
2. 用边界条件测试技能的鲁棒性
3. 在真实项目场景中测试技能的实用性
4. 收集反馈，调整技能定义
5. 记录已知限制和最佳使用场景
# 技能测试清单
test_cases:
  basic:
    - input: '创建一个 Button 组件'
      expected: 生成 Button.tsx + Button.test.tsx + index.ts
    - input: '创建一个 UserProfile 页面组件'
      expected: 在 src/pages/ 下生成完整组件结构

  edge_cases:
    - input: '创建一个名为 a 的组件'
      expected: 提示名称过短，要求重新命名
    - input: '创建一个已存在的组件'
      expected: 提示组件已存在，询问是否覆盖

  integration:
    - scenario: 连续创建 3 个组件
      expected: 每个组件独立生成，导出正确更新


最佳实践
完整示例：构建文档生成技能
以下是一个完整的文档生成技能示例，展示从定义到实现的全过程：


<!-- .trae/skills/api-doc-generator/SKILL.md -->

# API 文档生成器

## 描述

扫描项目中的 TypeScript 源码，自动生成结构化的 API 参考文档。

## 触发短语

- "生成 API 文档"
- "更新文档"
- "为 {module} 生成文档"

## 输入参数

| 参数   | 类型   | 必填 | 说明                        |
| ------ | ------ | ---- | --------------------------- |
| scope  | string | 否   | 生成范围：all / module-name |
| format | string | 否   | 输出格式：markdown（默认）  |
| output | string | 否   | 输出路径：docs/api/（默认） |

## 执行流程

### 1. 扫描源码

```bash
find src/ -name "*.ts" -not -name "*.test.ts" -not -name "*.d.ts"
```

### 2. 提取导出

识别所有 `export` 的函数、类型、接口和常量。

### 3. 生成文档

对每个导出项生成以下结构：

### functionName

**签名：**

```typescript
function functionName(param1: Type1, param2: Type2): ReturnType;
```
参数： | 参数 | 类型 | 说明 | |------|------|------| | param1 | Type1 | 参数说明 |


返回值： ReturnType — 返回值说明


示例：


const result = functionName('value1', 42);

### 4. 验证
- 检查所有公开 API 是否都已记录
- 验证示例代码的类型正确性

## 约束
- 文档内容使用中文
- 文件名使用英文 kebab-case
- 遵循项目已有的文档风格

原则
说明
示例





具体明确
避免模糊的指令
✅ "使用 const" ❌ "用好的变量声明"




正向表述
说"要做什么"而非"不要做什么"
✅ "使用 async/await" ❌ "不要用回调"




可验证
规则应该可以客观判断是否遵守
✅ "函数不超过 50 行" ❌ "函数要简短"




有优先级
标明规则的重要程度
用 MUST / SHOULD / MAY 区分




有范围
明确规则适用的文件或模块
"仅适用于 src/components/"

常见问题
项目规则和全局规则冲突了怎么办？
项目规则始终优先。如果需要在特定项目中覆盖全局规则：


<!-- .trae/rules/override.md -->

# 项目规则覆盖

以下规则覆盖全局设定：

- 全局规则要求使用 Jest，本项目使用 Vitest
- 全局规则要求 4 空格缩进，本项目使用 2 空格
- 全局规则禁止 any，本项目在测试文件中允许
如何在团队中共享自定义技能？
方案 1：Git 仓库共享
  - 将 .trae/ 目录提交到项目仓库
  - 团队成员 clone 后自动获得项目技能
  - 通过 PR 流程管理技能变更

方案 2：独立技能仓库
  - 创建专门的技能仓库
  - 通过 git submodule 或符号链接引入
  - 适合跨项目共享的通用技能

方案 3：技能包管理
  - 将技能打包为 npm 包（如适用）
  - 通过 postinstall 脚本部署到 .trae/skills/
  - 支持版本管理和依赖声明
技能定义写得太复杂，AI 不遵循怎么办？


提示： 技能定义遵循"少即是多"的原则。一个好的技能应该聚焦单一任务，通过组合多个简单技能来实现复杂工作流，而非在一个技能中塞入所有逻辑。






小结
    

  • 规则（Rule）、技能（Skill）、Agent 构成自定义 AI 行为的三层体系：规则约束行为，技能提供能力，Agent 组合执行。
    • 

  • 项目规则存放在 .trae/rules/ 目录下，定义代码风格、架构约束等项目特定的行为规范，始终优先于全局规则。
    • 

  • SKILL.md 文件是技能的核心定义，包含描述、触发条件、输入参数、执行步骤、输出模板和约束条件。
    • 

  • Skill Creator 工作流遵循"识别需求 → 选择范围 → 创建定义 → 测试迭代 → 分享发布"的标准流程。
    • 

  • 技能定义应遵循具体明确、正向表述、可验证、有优先级、有范围五个编写原则。
    • 

  • 通过组合简单技能而非构建复杂的单一技能来实现复杂工作流，是保持可维护性的关键策略。
    •
