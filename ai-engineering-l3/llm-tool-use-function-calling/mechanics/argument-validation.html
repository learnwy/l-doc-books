Part II · Agent Construction工具调用与函数调用机制参数校验与修复

参数校验与修复

开了 strict 模式，参数结构就一定合法了——然后你会在生产日志里看到 {"date":"明天"}、{"city":"上海市"}、{"amount":"100元"} 这类结构完全合法、业务上却没法用的参数。工具模式定义结尾埋的那个边界在这里兑现：strict 保结构，语义靠校验。这一篇讲宿主拿到模型参数后，那道「先校验、能修则修、修不了再回错」的防线怎么建。

核心概念：三层防线

把参数从「模型吐出」到「安全传给真实函数」之间，应当架三层防线，越靠前的失败越廉价。

层 检查什么 strict 能否覆盖 失败处理
结构层 类型、必填、枚举、嵌套形状 能（开 strict 即免疫） 关 strict 时本地校验器拦截
语义层 值是否在业务有效域（城市存在吗、日期可查吗） 不能 规范化修复或回错给模型
安全层 是否越权、是否危险（删全表、转账超额） 不能 拒绝或转人工确认

结构层在开了 strict 后基本免费，重点在语义层和安全层。安全层属于工具调用安全，本篇专注语义层的校验与修复。

flowchart TD
  A[模型生成参数] --> B[结构层: schema 校验]
  B -->|不合法且未开 strict| R1[回错: 结构非法]
  B -->|合法| C[语义层: 业务有效域校验]
  C -->|可自动规范化| D[修复后继续]
  C -->|不可修复| R2[回错: 给模型可纠正的提示]
  C -->|通过| E[安全层: 越权/危险检查]
  E -->|通过| F[执行真实函数]
  D --> E

能修则修：确定性规范化

很多语义错误是可预测、可确定性修复的，应当在宿主侧直接修掉，而不是劳烦模型重来一轮（重来一轮要多一次 API 往返，慢且贵）。典型的可修类别：

  • 同义归一：「上海市」「上海」「Shanghai」归一到内部城市码。
  • 格式宽容解析：把「2026 年 7 月 1 日」「7/1」「明天」解析成 ISO 日期（相对日期需结合当前时间）。
  • 单位剥离：从 "100元" 提取数值 100 与币种 CNY。
  • 默认值回填：缺省的可选字段用业务默认值补齐。

这类修复要遵守一条铁律：只做无歧义的确定性转换，绝不猜。「明天」相对今天可算，但「下周」到底指周一还是周日就有歧义——有歧义就不要擅自修，转而回错让模型澄清。把不确定的修复硬塞进去，等于把一个可见的错误变成一个隐蔽的错误。

修不了就回错：把纠错机会还给模型

当参数无法确定性修复时（城市根本不存在、日期超出可查范围），正确做法不是抛异常中断，而是把一条对模型友好的错误作为工具结果回灌，让模型自己纠正后重试。这正是利用了函数调用循环的那条回边。

错误信息的写法决定模型能否纠正。对比两种回灌：

// 差：模型不知道哪错了、怎么改
{"error": "invalid argument"}

// 好：定位问题 + 给出可选项，模型能据此重填
{"error": "城市『火星』不在支持列表",
 "hint": "请从最近匹配中选择",
 "suggestions": ["上海", "上饶"]}

好错误的三要素：说清哪个参数错、为什么错、怎么改（给候选或格式样例）。这套「面向模型的错误设计」是下一篇工具错误处理的核心，本篇先点明：参数校验失败本质上就是工具错误的一种，复用同一套回错机制。

跨厂商与流式场景的额外裂缝

即便单厂商下 strict 完美，两类工程现实仍会让你收到不完整参数。其一是跨厂商适配层：你的网关同时对接 OpenAI、Anthropic、开源模型，不同后端对 strict 支持程度不一，开源小模型常常根本没有可靠的约束解码，必须在网关侧补一道本地 schema 校验（用 ajv、pydantic 这类成熟库，别手写）。

其二是流式增量：各家流式 API 都可能把参数拆成多个 delta，你在中途拿到的是 {"city":"上 这样的半截串，不能执行也不能当成校验失败。应按调用索引或 call_id 累积片段，在该调用结束后只解析一次。

还要区分「传输被切片」与「服务端取消最终校验」。Anthropic 的 fine-grained tool streaming 在用户定义工具上设置 eager_input_streaming:true 后，会跳过参数值的服务端缓冲与 JSON 校验以降低首片延迟；最终累积串可能非法，也可能因 max_tokens 中途截断。此时宿主要检查停止原因、保护 JSON 解析，并把无法解析的原始输入作为明确错误回灌，而不是运行半截参数。普通流式模式即使最终值由服务端缓冲校验，中间 delta 也仍然不是可执行输入。

小结

  • strict 保结构不保语义，宿主必须再架语义层与安全层两道防线。
  • 语义错误中可确定性修复的（同义归一、格式解析、单位剥离、默认回填）应在宿主侧直接修，避免多一次 API 往返；但只修无歧义的，有歧义绝不猜。
  • 不可修复时回灌「对模型友好」的错误（哪错、为何错、怎么改），利用调用循环的回边让模型自纠，而非抛异常中断。
  • 跨厂商网关与流式增量是两道额外裂缝：用成熟 schema 库补本地校验，流式参数务必拼完整再校验。
  • 校验失败本质是工具错误的一种，统一走下一篇工具错误处理的回错机制。
