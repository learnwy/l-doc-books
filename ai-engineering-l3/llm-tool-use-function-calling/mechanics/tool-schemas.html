工具模式定义

模型选错工具、填错参数，九成不是模型笨，而是工具模式写得让它读不懂。工具模式（tool schema）是你与模型之间唯一的接口文档，模型完全靠这份 JSON Schema 加自然语言描述来决定「用不用、用哪个、怎么填」。写好它，可靠性提升的边际收益往往比换更大的模型还高。

核心概念：一个工具模式的四个部件

一个工具定义由四部分组成，每一部分都直接影响模型的某个决策。下表把部件、作用与常见错误对应起来。

部件 模型用它决定 写好的关键 常见错误
name 这是个什么动作 动词+宾语、语义自解释 func1、doIt 这类无信息名
description 何时该调它 写清适用与不适用场景 只说「获取数据」
参数 properties 每个参数填什么 每个字段单独写 description 字段无描述、命名缩写
required / 枚举 / 类型 哪些必填、取值范围 用 enum 收敛、标 required 该枚举的写成自由字符串

下面是一个写得较好的天气工具模式骨架，注意每个字段都带描述、用 enum 收敛单位、显式声明必填：

{
  "name": "get_weather",
  "description": "查询某城市某天的天气。仅用于查询，不做预测；历史超过 7 天的日期会返回错误。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "城市中文名，如 上海" },
      "date": { "type": "string", "description": "ISO 日期 YYYY-MM-DD，默认今天" },
      "unit": { "type": "string", "enum": ["celsius", "fahrenheit"], "description": "温度单位" }
    },
    "required": ["city"],
    "additionalProperties": false
  }
}

description 是写给模型读的「何时用」说明书

新手最容易把 description 写成「获取天气」，这只回答了「是什么」，没回答模型最需要的「何时该调我、何时不该」。模型在面对多个工具时，正是靠 description 的边界描述来做选择。一句「仅用于查询当前与历史天气，不做未来预测；预测请用 forecast_weather」能显著降低误选率。

把 description 当成给一个聪明但没有上下文的新同事写的工单：他不知道你的业务，只能照字面理解。凡是你脑子里默认的前提（日期格式、单位、不支持的场景），都要显式写出来。这种「边界写清」的收益在工具数量上去后会被放大，与工具选择与路由直接相关。

strict 模式：让参数一定符合 schema

即便 schema 写得完美，模型在自由生成时仍可能吐出不合 schema 的参数——这是工具的 token 表示里讲过的自回归生成的固有风险。strict 模式就是关掉这个风险的开关。

OpenAI 在 2024 年底引入、并在 2025 年完善了 strict 模式：在工具定义里设 strict: true，后端会用工具的 JSON Schema 驱动约束解码，保证生成的参数结构一定合法。它要求每个对象设 additionalProperties: false 且所有字段进 required（可空字段用 union 类型表达）。据 OpenAI 文档，2025 年起 strict 模式已与并行函数调用兼容（非微调模型），官方建议始终开启。Anthropic 侧虽无同名开关，但其工具输入同样走结构化约束，可靠性接近。

flowchart TD
  A[模型准备生成参数] --> B{strict 是否开启?}
  B -->|开启| C[约束解码: schema 编译成语法<br/>逐 token 掩掉非法续写]
  C --> D[结构一定合法的参数]
  B -->|关闭| E[尽力而为自由生成]
  E --> F{恰好合法?}
  F -->|是| D
  F -->|否| G[宿主侧需校验与修复]

需要牢记的边界：strict 只保证结构合法，不保证语义正确。{"city":"不存在的城市","unit":"celsius"} 完全符合 schema，业务上却是错的。语义层面的兜底属于下一道防线。

设计取舍：粗粒度大工具还是细粒度小工具

同一组能力，可以设计成一个带 action 枚举的大工具（如 db(action, table, filter)），也可以拆成 db_query、db_insert、db_delete 多个小工具。两种各有取舍：大工具省 token、定义集中，但参数组合复杂、模型容易填出非法组合；小工具语义清晰、模型选择准，但工具数量膨胀、占上下文。

经验法则是：动作语义差异大、权限不同的能力拆开（尤其要把有破坏性副作用的 delete 单列，便于在工具调用安全里单独加确认）；纯参数差异的同类查询可合并。无论怎么选，都要让每个工具的参数空间小到模型不容易填错。

小结

  • 工具模式是你与模型唯一的接口文档，name 决定「是什么」、description 决定「何时用」、参数与 required/enum 决定「怎么填」。
  • description 要写「何时用、何时不用」的边界，而非只写「是什么」；把模型当没有业务上下文的新同事。
  • strict 模式用约束解码保证参数结构一定合法，2025 年起已与并行调用兼容，官方建议始终开启；但它只保结构不保语义。
  • 粗粒度与细粒度工具各有取舍：动作差异大、有破坏性副作用的拆开，纯参数差异的可合并，核心是收敛每个工具的参数空间。
