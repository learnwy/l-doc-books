工具错误处理

工具一定会失败：网络超时、第三方 API 返回 500、业务规则拒绝、参数语义不对。问题从来不是「会不会失败」，而是「失败时把什么回灌给模型」。把异常 throw 掉，模型就失去自我纠正的机会；把堆栈原样塞回去，又泄露内部细节还可能把模型带沟里。这一篇讲怎样把工具错误设计成「模型能读懂、能据此纠正、且不越界」的结果。

核心概念：错误是回灌物，不是抛出物

工具调用里有一个反直觉的原则：工具错误通常不应作为异常抛给宿主主流程，而应作为一条正常的工具结果回灌给模型。因为模型在函数调用循环里有一条天然的回边——只要它看到「这次失败了、原因是 X」，就有机会调整参数或换个工具重试，整个过程对用户透明。

下表区分了三类失败应当如何处置，关键在于「模型能不能靠重试自救」。

失败类型 例子 模型可自救? 处置
可纠正错误 参数语义错、城市不存在 能 回灌可纠正错误，让模型重填
瞬时错误 超时、限流、502 部分 宿主先自动退避重试，仍失败再回灌
永久/致命错误 鉴权失败、工具不存在 不能 宿主侧拦截，不必反复喂模型

注意第二行：瞬时错误应当先由宿主用退避重试自己消化，因为模型对「等 200ms 再试」无能为力，让它重试只是白烧 token。这条退避重试策略属于工具调用可靠性，本篇只强调分流原则。

flowchart TD
  A[工具执行] --> B{失败了?}
  B -->|成功| Z[正常结果回灌]
  B -->|瞬时错误| C[宿主退避重试]
  C -->|重试成功| Z
  C -->|仍失败| D[回灌瞬时失败说明]
  B -->|可纠正错误| E[回灌结构化错误<br/>哪错+为何+怎么改]
  B -->|永久错误| F[宿主拦截+兜底<br/>不无限喂模型]
  E --> G[模型据此纠正重试]
  D --> G

面向模型的错误信息怎么写

参数校验与修复里已经给过一个好错误的例子，这里把它升级成系统化的三要素加两条禁忌。

三要素：定位（哪个工具、哪个参数出了问题）、归因（为什么失败，用模型能理解的业务语言而非内部错误码）、导向（怎么改，给候选值、格式样例或替代工具）。一条理想的可纠正错误像这样：

{
  "ok": false,
  "error_type": "value_out_of_range",
  "message": "date『2030-01-01』超出可查范围，仅支持最近 7 天",
  "valid_range": { "from": "2026-06-25", "to": "2026-07-01" }
}

两条禁忌：其一，不回灌原始堆栈与内部标识——数据库连接串、内网地址、未脱敏的用户数据塞进上下文，既是工具调用安全讲的信息泄露面，也会干扰模型。其二，不回灌祈使式指令——错误信息里别写「请立即调用 X 工具」，外部数据里的指令式文本正是提示注入的载体，错误信息应只陈述事实，由模型自己决策。

防住错误循环：别让模型在失败里打转

回灌可纠正错误的代价是：模型可能改了又错、错了又改，陷入循环，每一轮都是真金白银的 token。三道护栏可防住它：

  • 单工具重试上限：同一工具连续失败 N 次（常取 2–3）就停止回灌，转兜底。
  • 总轮数上限：整条调用链的总轮数封顶，这与函数调用循环讲的循环终止权一脉相承。
  • 错误去重感知：若模型连续两次提交几乎相同的错误参数，说明它没读懂错误，应换一种更明确的提示或直接降级到人工/默认值。

这些护栏的存在再次印证那条贯穿全 hub 的原则：循环的方向盘握在宿主，模型只是被反复唤醒的推理器。

错误也要可观测

回灌给模型的错误和你记录到日志的错误，应当是两份内容。给模型的那份要简洁、脱敏、导向纠正；给运维的那份要带完整堆栈、调用 ID、耗时、重试次数，便于排障与工具调用评测里统计各工具的真实失败率。把这两份混为一谈，是工具调用系统排障困难的常见根源——你既污染了模型上下文，又丢失了排障细节。

小结

  • 工具错误应作为结果回灌给模型而非抛出，以便利用调用循环的回边让模型自纠。
  • 按「可纠正/瞬时/永久」三类分流：瞬时错误宿主先退避重试，可纠正错误回灌结构化提示，永久错误宿主拦截兜底。
  • 面向模型的错误三要素是定位、归因、导向；两条禁忌是不回灌原始堆栈、不回灌祈使式指令（防泄露与防注入）。
  • 用单工具重试上限、总轮数上限、错误去重三道护栏防止模型在失败里打转。
  • 给模型的错误与给运维的日志是两份内容，分开才能既不污染上下文又不丢排障细节。
