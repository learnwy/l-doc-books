工具调用与函数调用

一个纯语言模型只能输出文本，它不知道今天的汇率，不能读你的数据库，也无法把一封邮件真正发出去。工具调用（tool use，也叫函数调用 function calling）就是给模型装上「手」的那层机制：开发者把若干函数的名字、用途和参数模式告诉模型，模型在需要时不再编造答案，而是输出一段结构化的「调用请求」，由宿主程序执行真实代码，再把结果回灌给模型继续推理。这层看似简单的「模型提议、程序执行」的契约，是今天几乎所有 AI 智能体、检索增强、自动化工作流的共同地基。

本 hub 沿四条主线递进，从「为什么」一路讲到「怎么在生产里不出事」。

第一条线是基础：先讲清工具调用到底解决了参数化知识的哪些固有缺陷，再把一次完整调用拆成「模型生成调用 → 宿主执行 → 结果回灌」的循环，最后下沉到 token 层，说明工具描述与调用请求在模型眼里其实仍然只是序列，从而把函数调用和结构化输出的约束解码机制接上。理解了这三点，后面所有机制都不再是黑盒。

第二条线是机制：一次调用能否成功，先取决于工具模式写得好不好。这一章讲 JSON Schema 如何描述工具、strict 模式如何保证参数一定合法、当参数仍然出错时如何校验与修复、以及工具执行失败时该把什么样的错误信息回给模型才能让它自我纠正。

第三条线是编排：单个工具会用之后，真实任务往往需要一次并行调用多个工具、或把多步调用串成一条依赖链、或在上百个工具里准确选对那一个。这一章处理「多」带来的全部复杂度。

第四条线是实践：把前三条线放进生产环境会遇到可靠性、评测和安全三道坎。我们用 BFCL、tau-bench 这类 2025–2026 年的真实基准谈怎么量化工具调用质量，并直面工具投毒、提示注入这类已经在 MCP 生态里爆发的攻击。

本 hub 与兄弟 hub 的分工边界：本 hub 只讲「模型与工具之间那层调用契约本身」——模式、循环、校验、编排、可靠性。它不讲如何用工具搭一个会自主规划的智能体（那是智能体开发），不讲 LangChain/LangGraph 等具体框架怎样封装工具（那是智能体框架），不讲工具如何跨进程、跨厂商标准化暴露（那是 MCP），也不讲底层如何用语法约束逼模型只能吐合法 JSON（那是结构化输出）。换句话说，本 hub 是上述四者共同的「调用层语义」前置。

推荐学习路径：完全的新手按章节顺序读即可，基础三篇务必先读。已经写过 OpenAI/Claude 工具调用代码、只想补深度的工程师，可直接从「机制」章的 strict 模式与参数修复读起，再跳到「实践」章的可靠性与安全。要做评测或上线的人，重点读「实践」三篇并回看「编排」的多步链。

前置知识：读者应熟悉 JSON 与 HTTP API 的基本概念，了解 LLM 的「提示词进、文本出」基本工作方式，最好读过本目录下大语言模型基础中关于 token 与采样的部分。不需要任何机器学习训练经验。
