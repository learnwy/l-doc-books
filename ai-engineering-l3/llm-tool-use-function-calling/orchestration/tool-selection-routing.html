Part II · Agent Construction工具调用与函数调用编排工具选择与路由

工具选择与路由

3 个工具时，把全部模式塞进上下文让模型自己选，毫无问题。300 个工具时，这套做法会同时撞上三堵墙：光工具定义就吃掉数千 token、模型注意力被几百个候选稀释导致选错率飙升、成本随每次请求线性上涨。工具一多，「让模型看见全部工具」本身就成了问题，于是需要路由——在把工具交给模型之前先做一轮筛选。

核心概念：为什么「全量塞入」会崩

回顾工具的 token 表示：每个工具定义都是要占上下文、要计费的 token。把这条事实放大到几百个工具，三个问题同时出现，下表对应了各自的解法。

问题 全量塞入时的表现 路由解法
token 成本 几百工具定义吃掉数千 token/请求 只塞入候选子集
选择准确率 候选越多越容易选错、混淆相似工具 缩小候选到 5–20 个
上下文窗口 工具定义挤占任务本身的空间 释放窗口给真正的任务上下文
维护与权限 全量暴露=全量攻击面 按需暴露，收敛攻击面

最后一行顺带点出：路由不只是性能优化，也收敛了工具调用安全里讲的攻击面——没暴露给模型的工具就投毒不了。

检索式路由：先召回再交给模型

主流解法是把工具选择本身做成一次检索：把每个工具的名字与描述向量化建索引，请求到来时用用户意图去召回 top-k 个最相关的工具，只把这 k 个的完整定义塞进上下文交给模型最终决策。

flowchart TD
  A[用户请求] --> B[用意图向量召回<br/>top-k 相关工具]
  B --> C{召回是否够准?}
  C -->|是| D[仅塞入 k 个工具定义]
  C -->|漏召回| E[兜底: 加入常用核心工具]
  D --> F[模型在小候选集里选择]
  E --> F
  F --> G[执行选中工具]

这套两阶段架构（检索召回 + 模型精选）和检索增强（RAG）同源，本 hub 不展开向量检索的实现细节。要警惕的核心风险是漏召回：若正确的工具压根没进 top-k，模型再聪明也无能为力。因此 k 不能太小，且常配一个「核心常用工具永远在场」的兜底集，避免高频工具因召回波动而缺席。

命名空间与分层：把扁平工具集变成树

另一条与检索互补的路子是分层路由。不把 300 个工具拍平，而是按领域分组——db.*、calendar.*、email.*——先让模型选「领域」，再在选中领域内选具体工具。这把一次「300 选 1」拆成两次「10 选 1」，每次选择的候选都小、都准。

分层还天然契合权限模型：一个用户可能只能访问 calendar.* 和 email.* 这两个命名空间，路由时直接按权限裁剪可见领域，既减小候选又落实最小权限。跨进程工具协议同样应先按服务器或信任域分层，再向模型暴露其中获准的工具。

用更小的模型先做一轮筛选

第三条路是模型级联：用一个便宜的小模型先做工具选择（甚至只输出工具名），再把选定的工具与任务交给大模型执行。小模型做「300 选 5」的粗筛很划算，把昂贵的大模型留给真正需要推理的执行环节。级联必须记录粗筛召回率，因为第一层漏掉正确工具后，第二层再强也无法补救。

需要权衡的是：级联多了一跳延迟，且小模型选错会向下游传播。是否值得，取决于工具规模与请求量——工具上百、请求量大时级联省的钱通常远超那一跳延迟的代价。

选错工具的后果与缓解

无论用哪种路由，模型仍可能选错工具（选了功能相近的兄弟工具）。三条缓解：其一，把相似工具的 description 写出判别性边界（「本工具只查历史，预测用 X」），这是工具模式定义里强调的判别式描述在大工具集下的放大收益；其二，对破坏性工具加确认环节，选错也不至于造成后果；其三，在评测集里专门构造「易混淆工具对」来度量选择准确率，详见工具调用评测。

小结

  • 工具规模上百时全量塞入会同时撞上 token 成本、选择准确率、上下文窗口、攻击面四堵墙。
  • 检索式路由先用意图召回 top-k 再交模型精选，核心风险是漏召回，需用核心工具兜底集防护。
  • 命名空间分层把「N 选 1」拆成多次小选择，天然契合最小权限的可见性裁剪。
  • 模型级联用小模型做粗筛、大模型做执行，省钱但多一跳延迟且小模型错误会下传。
  • 判别式 description、破坏性工具加确认、易混淆工具对评测，是选错工具的三条缓解。
