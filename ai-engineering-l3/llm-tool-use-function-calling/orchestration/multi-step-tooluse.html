Part II · Agent Construction工具调用与函数调用编排多步工具链

多步工具链

「帮我把上周那个标题含『发布』的文档分享给张伟」——这一句话背后是一条必须按序走的链：先搜文档拿到 ID、再用 ID 查权限、再解析「张伟」的账号、最后调分享接口。每一步的参数都依赖前一步的真实返回，模型只有看到上一步结果才能决定下一步。这种由结果驱动、逐步推进的串行链，是工具调用从「函数封装」迈向「智能体」的真正起点。

核心概念：模型驱动的循环，而非预设的流程图

新手常想把多步工具链写成一张固定的流程图：第一步必调 A、第二步必调 B。但真实任务的分支太多，硬编码会脆得一塌糊涂。多步工具链的精髓恰恰是不预设流程：宿主只是反复执行同一个循环——把当前消息历史喂给模型，模型看完后要么再提议一个工具调用，要么宣布完成——由模型在每一轮根据真实结果自行决定走向。

维度 预设流程图 模型驱动循环（本篇）
下一步谁决定 开发者硬编码 模型按当前结果决定
分支适应性 差，新情况要改代码 强，模型临场判断
可预测性 高 较低，需护栏约束
适用 流程极固定的场景 开放任务、智能体

这条循环就是函数调用循环那条回边的反复触发：模型每看到一个 tool_result 就被唤醒一次，决定继续调还是收尾。

flowchart TD
  A[用户任务] --> B[恢复连续上下文与执行状态]
  B --> C[模型决策]
  C -->|提议下一个工具| D[宿主执行]
  D --> E[结果追加进历史]
  E --> F{触达护栏?<br/>轮数/预算/重复}
  F -->|否| B
  F -->|是| H[强制收尾或兜底]
  C -->|宣布完成 stop| G[输出最终回答]

上下文随链增长：每一步都背着必要状态

多步链有个躲不开的代价：模型每一轮都要重新看到做下一步决策所需的状态。无状态消息 API 通常重放历史；带连续性句柄的 API 由服务端保存上下文；自建运行时也可以从检查点恢复。不论状态放在哪里，一条 8 步链最终都积累了 8 组调用与结果，若不压缩，token 量与存储成本会持续增长。

两种常见缓解：一是结果裁剪，工具返回的大对象只把模型下一步真正需要的字段回灌，其余保存到对象存储并只传引用；二是中途摘要，链很长时把已完成事实压缩成结构化状态再继续。摘要必须保留实体 ID、约束、未完成目标和副作用收据，不能只保留一段听起来流畅的自然语言。这两招都在「保留决策所需信息」与「控制上下文膨胀」之间权衡。

把轨迹做成可恢复执行记录

消息历史解决「模型知道什么」，执行记录解决「系统已经做过什么」。两者不能混为一谈。生产运行时应为每个工具步骤保存至少以下字段：

字段 作用
call_id 关联模型请求、工具结果与日志
tool_name、arguments_hash 识别重复意图并生成幂等键
status、attempt 区分待执行、执行中、成功、可重试失败与终止失败
output_ref 把大结果放在上下文外，只回灌必要投影
effect_receipt 证明邮件、转账、写入等副作用是否已经发生

执行副作用前先原子写入「准备执行」记录，调用成功后再保存不可伪造的业务收据；网络超时后先查收据或目标系统状态，再决定是否重试。仅凭「上一次 API 返回超时」就重新发邮件，会把一次不确定结果放大成重复副作用。恢复时从最后一个确定完成的步骤继续，而不是重新让模型猜整条链做到了哪里。

模型可以动态决定下一步，但运行时必须用确定性状态机约束执行生命周期。开放任务适合模型选择工具；结算、审批、迁移这类固定高风险流程更适合显式工作流，模型只填充某些决策点。把所有流程都塞进自由循环，不是灵活，而是失去可审计性。

失败率的连乘：长链为什么脆

多步链最反直觉的风险是失败率连乘。设每一步成功率为 ppp，一条 nnn 步全对的链整体成功率是 pnp^npn。即便单步高达 0.950.950.95，10 步链的整体成功率也只有 0.9510≈0.600.95^{10} \approx 0.600.9510≈0.60——四成的任务会在某一步翻车。

这条简单的公式有两个工程含义。其一，缩短链长比提升单步精度收益更大：能用一次并行扇出（见并行工具调用）解决的就别拆成串行多步。其二，长链必须有断点续跑或局部重试能力——某一步失败时只重试那一步，而非从头再来，否则前面的成本全部白费。这也是工具调用评测要把「单步指标」和「整条轨迹指标」分开度量的根本原因。

防打转：终止条件与进展检测

模型驱动的循环最怕「原地打转」——反复调用同一个工具拿同样的结果却不收尾。三道护栏：

  • 轮数与预算上限：硬性封顶总轮数和累计 token，触顶强制收尾。这是循环方向盘握在宿主的体现。
  • 重复检测：若模型连续两轮提议几乎相同的调用，判定为卡住，注入一条提示或直接降级。
  • 进展信号：比较新实体、新约束、状态变更和未完成目标是否减少，不依赖模型自述「我正在推进」。客观状态差分比自然语言理由更容易审计。

这些护栏不是可选项。一个没有终止护栏的多步循环，遇到模型误判就会变成烧钱的死循环——这是工具调用智能体上线后最常见的事故。

小结

  • 多步工具链是模型驱动的循环而非预设流程图：宿主反复喂历史、模型按真实结果决定下一步，适应性远胜硬编码。
  • 每轮都要恢复决策所需状态；无状态 API 重放历史，有状态 API 或自建运行时保存上下文。用结果外置、结构化摘要与检查点控制增长。
  • 消息历史记录模型看到什么，执行台账记录系统做过什么；副作用必须用幂等键和业务收据恢复，不能在超时后盲目重试。
  • 整链成功率 pnp^npn 随步数指数衰减，单步 0.95 的 10 步链仅约 0.60；缩短链长比提升单步精度更划算，长链需局部重试。
  • 用轮数/预算上限、重复检测、客观状态差分三道护栏防止模型原地打转，没有护栏的循环会变成烧钱死循环。
  • 单步指标与整条轨迹指标要分开评测，见工具调用评测。
