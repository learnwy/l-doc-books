工具调用可靠性

实验室里调通的工具调用，搬上生产流量后会以你意想不到的方式失败：第三方 API 偶尔超时、同一个下单被模型重复触发两次、依赖服务雪崩时整条链被拖垮。可靠性工程的目标不是消灭失败（做不到），而是让每一种失败都有预案——超时能退避、重复能去幂、雪崩能熔断、实在不行能兜底。这一篇把这些预案串成一套防御体系。

核心概念：可靠性的四道闸

把一次工具调用从「发起」到「拿到可用结果」之间可能出的岔子归类，每类对应一道成熟的工程闸门。

失败模式 后果 对应闸门
瞬时故障（超时、限流、5xx） 偶发失败 重试 + 指数退避
重复执行（模型重发、重试叠加） 重复下单/扣款 幂等键
依赖雪崩（下游持续挂） 线程耗尽、级联崩 断路器
模型无法完成 任务卡死 确定性兜底 + 降级

这四道闸不是工具调用独有，而是分布式系统的通用韧性模式，只是在工具调用里它们的触发者多了一个「会犯错的模型」。工具错误处理里说「瞬时错误宿主先重试」，本篇把那句话展开成完整策略。

flowchart TD
  A[模型提议调用] --> B{幂等键已见过?}
  B -->|是| C[返回缓存结果<br/>不重复执行副作用]
  B -->|否| D{断路器状态?}
  D -->|开路| E[快速失败+兜底]
  D -->|闭合| F[执行工具]
  F -->|瞬时失败| G[指数退避重试]
  G -->|仍失败| H[回灌错误/降级]
  F -->|成功| I[记录幂等键+返回]

重试与退避：给瞬时故障一个台阶

瞬时故障（网络抖动、限流 429、网关 502）的特征是「重试一下大概率就好」。但重试有讲究：固定间隔的密集重试会在下游已经过载时火上浇油，正确做法是指数退避加抖动——第 kkk 次重试等待约 base⋅2kbase \cdot 2^{k}base⋅2k 再叠加一个随机抖动，避免大量客户端同步重试形成「重试风暴」。

两条边界：其一，只对可重试的错误重试（限流、超时可重试；400 参数错、403 鉴权错重试无意义），这要靠工具错误处理的错误分类来判断。其二，重试要有总次数与总耗时上限，否则一个慢工具会把整条调用链拖到用户失去耐心。

幂等键：模型重复触发也只执行一次

工具调用里有个传统 API 没有的重复风险源：模型本身可能在多步链里重复提议同一个有副作用的调用，或重试逻辑与模型重发叠加，导致同一笔订单下两次。解法是工业界成熟的幂等键——为每次有副作用的操作生成一个稳定的唯一键（如基于业务参数哈希），下游用它去重：同一个键的第二次请求直接返回第一次的结果，不再产生新的副作用。

幂等键对一切「写」类工具几乎是必备：下单、转账、发消息、创建资源。把它作为这类工具模式的隐含契约，比事后排查「为什么用户被扣了两次款」要省心得多。

断路器：别让一个挂掉的工具拖垮全局

当某个下游工具持续失败（不是偶发而是真的挂了），继续对它重试只会耗尽线程、堆积超时，最终拖垮整个服务。断路器（circuit breaker）模式给它装一个保险丝：监测某工具的失败率，超过阈值就「开路」——后续调用直接快速失败并走兜底，不再真的发起请求；过一段冷却时间再「半开」放少量探测请求，确认恢复后才「闭合」。

断路器把「一个工具挂了」的影响隔离在该工具范围内，避免级联雪崩。它和重试是互补的：重试应对偶发，断路器应对持续——两者叠加时要注意别让重试在断路器开路前把失败率自己刷高。

兜底与降级：模型实在做不到时

最后一道闸是承认模型可能彻底完不成任务（链太长、工具全挂、触达轮数上限）。这时要有确定性兜底：返回一个安全的默认结果、转人工处理、或明确告知用户「暂时无法完成」，而不是让循环空转或给用户一个幻觉答案。

这与多步工具链讲的轮数护栏是同一件事的两面——护栏负责「何时停」，兜底负责「停了之后给什么」。一个成熟的工具调用系统，任何一条执行路径走到尽头都应落在某个明确定义的兜底上，绝不留「卡死」这个出口。

小结

  • 可靠性不是消灭失败而是给每种失败配预案：重试退避治瞬时故障、幂等键治重复、断路器治雪崩、兜底治彻底失败。
  • 重试用指数退避加抖动防重试风暴，只重试可重试错误，且设总次数与耗时上限。
  • 幂等键对一切「写」类工具近乎必备，让模型重复触发或重试叠加也只产生一次副作用。
  • 断路器把持续失败的工具隔离，避免级联雪崩；与重试互补，一治偶发一治持续。
  • 任何执行路径走到尽头都要落在明确兜底上，绝不留「卡死」出口；护栏管何时停，兜底管停了给什么。
