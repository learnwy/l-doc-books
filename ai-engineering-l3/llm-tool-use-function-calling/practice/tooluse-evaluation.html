Part II · Agent Construction工具调用与函数调用实践工具调用评测

工具调用评测

「换了新模型，工具调用感觉更准了」——这句话在工程上等于没说。工具调用的质量是可以也必须被量化的：选对工具了吗？参数填对了吗？整条多步任务完成了吗？没有数字，你既无法在升级模型时挡住退化，也无法向团队证明某项改动真的有用。这一篇讲怎样把「感觉准了」变成可回归的指标。

核心概念：把工具调用质量拆成三层指标

工具调用不是一个单一的对错判断，而是要分层度量——每一层失败的原因和修法都不同。下表是评测设计的骨架。

指标层 衡量什么 判定方式 失败常由谁导致
工具选择 选对了该用的工具吗 确定性比对工具名 描述含糊、工具混淆
参数正确 参数填对了吗 AST/结构比对，非字符串相等 schema 差、模型理解偏
轨迹完成 整条多步任务达成目标吗 终态校验或 LLM 评判 链太长、中途打转

这三层正好对应本 hub 前面三章的关注点：选择对应工具选择与路由，参数对应参数校验与修复，轨迹对应多步工具链。把指标拆到这三层，一旦某层掉分就能直接定位到该补哪一章的功夫。

flowchart TD
  A[评测样本: 任务+期望] --> B[运行被测系统]
  B --> C[工具选择对吗?]
  C --> D[参数 AST 比对]
  D --> E[执行后终态校验]
  E --> F{多步任务达标?}
  F -->|确定项| G[确定性判定]
  F -->|开放项| H[LLM-as-judge]
  G --> I[分层汇总指标]
  H --> I

业界基准：BFCL、τ-bench 与 τ²-bench

**伯克利函数调用排行榜（BFCL）**从单步函数调用扩展成了分层的智能体评测。基础与 Live 数据继续测单调用、多调用、并行、并行多调用、相关性拒绝和参数结构；多轮部分加入缺函数、缺参数与长上下文；V4 又加入网页搜索、记忆和格式敏感性。AST 判定仍然重要，因为它比较解析后的函数与参数结构，而不是要求字符串逐字相等。

τ-bench 换了个角度：用受任务约束的模拟用户，在航空与零售等多轮领域中考察智能体能否同时遵守政策、调用 API 并达到可验证终态。它度量的不是单次调用对错，而是整条轨迹是否完成任务。τ²-bench 进一步加入双控制环境：智能体和用户各自掌握不同工具，双方必须协调操作同一个动态状态；这能暴露单纯函数调用准确率看不见的沟通与协作失败。

不要把排行榜截图写成长期结论。BFCL 是动态数据集，版本、模型快照、提示格式和评测日期都会改变排序；τ 系列也会修复任务并区分 split。可复现报告必须固定代码提交、数据版本、模型快照、工具模板、重试策略和评测日期。公开基准告诉你通用能力，却代替不了自己的金标准集——你的工具、业务规则和易混淆工具对只有内部数据能覆盖。

轨迹类任务还要报告成功率的统计口径。单次成功率 pass^1 回答「一次运行能否完成」；重复运行的 pass^k 或一致成功率回答「多次尝试至少一次成功」或「每次都稳定成功」。生产自动化更关心低方差与重复成功，不能用允许多次抽样的最好结果掩盖不稳定。

判定方法：确定性优先，LLM 评判兜底

工具调用评测的一大优势是大量判定可以确定性化，比纯文本生成好评得多：

  • 工具选择：模型选的工具名与期望工具名字符串比对，对就是对。
  • 参数正确：用 BFCL 式的 AST 比对，解析成结构后比较，避开无关的格式差异。
  • 是否调用了不该调的工具：检查轨迹里有没有出现禁用工具（尤其破坏性工具）。

只有「开放式」判断才动用 LLM-as-judge——比如「这条 8 步轨迹是否合理地完成了用户的模糊需求」，没有唯一正确答案时才让一个评判模型打分。把能确定性判定的部分确定性化，既快又稳又便宜，是工具调用评测相比通用生成评测的红利。

易混淆与对抗样本：专测系统的脆弱处

光测「正常能跑」不够，要专门构造逼出弱点的样本：

  • 易混淆工具对：放两个功能相近的工具（search_doc 与 search_email），看模型会不会选错——这直接度量工具模式定义里 description 判别性写得够不够。
  • 缺参/歧义请求：用户没给全参数，看模型是擅自瞎填还是回头追问。
  • 不该调工具的请求：纯闲聊却放着工具，看模型会不会没事乱调（过度调用也是常见缺陷）。
  • 注入样本：把恶意指令藏进工具返回结果里，看系统会不会被带偏——这与工具调用安全的评测合流。

把这些对抗样本纳入回归集，每次改模型、改 prompt、改工具描述都重跑一遍，才能在退化发生时第一时间发现。

小结

  • 工具调用质量要拆成工具选择、参数正确、轨迹完成三层指标，分别对应本 hub 的路由、校验、多步链三章，掉分即可定位。
  • BFCL 同时覆盖单步、多轮与 V4 智能体能力；τ-bench 测工具—智能体—用户的多轮终态，τ²-bench 再加入双方各有工具的双控制协作。
  • 基准结论必须固定数据版本、模型快照、模板、重试策略和日期，不能把动态排行榜分数写成恒定事实。
  • 轨迹评测要区分单次 pass^1、多次抽样结果与重复稳定性，生产系统不能只报最好一次。
  • 工具调用评测的红利是大量判定可确定性化（工具名比对、参数 AST 比对），只有开放式判断才用 LLM-as-judge。
  • 必须用易混淆工具对、缺参歧义、不该调工具、注入样本等对抗样本逼出弱点，并纳入每次改动都重跑的回归集。
