工具的 token 表示

很多工程师把「工具」想象成挂在模型旁边的一组真实函数，于是无法理解为什么模型会调用一个不存在的工具、为什么工具一多准确率就掉。真相朴素得多：在模型眼里没有函数，只有 token。工具的定义、调用请求、返回结果，全部是被序列化进同一条 token 流的文本。看清这一层，几乎所有「玄学」的工具调用现象都能被解释。

核心概念：工具定义如何变成上下文 token

当你在 API 里传入一个工具列表，宿主或厂商后端会把它渲染成一段文本注入到模型的上下文（通常拼在系统提示之后）。不同厂商渲染格式不同，但本质都是「告诉模型有哪些工具、各自的名字、用途描述、参数 JSON Schema」。下表对比了同一个工具在两种主流形态下的占位。

维度 OpenAI 风格 Anthropic 风格
工具描述位置 tools 字段，后端渲染入上下文 tools 字段，渲染为系统提示一部分
调用请求形态 tool_calls 数组，含函数名与 JSON 字符串参数 tool_use 内容块，含 input 对象
结果回灌 role:tool 消息 + tool_call_id tool_result 块 + tool_use_id
计费 工具定义计入输入 token 工具定义计入输入 token

最后一行常被忽视却很要命：工具定义是要算钱、占窗口的 token。一个有 80 字段描述的工具可能吃掉几百 token；挂 100 个工具，光定义就可能占掉数千 token，既增加成本又稀释模型注意力。这正是工具一多就要做路由的根本原因，详见工具选择与路由。

flowchart TD
  A[开发者传入 tools 数组] --> B[厂商后端渲染成文本<br/>名字+描述+JSON Schema]
  B --> C[拼入上下文 token 流]
  C --> D[模型自回归生成]
  D --> E{下一个 token 该是<br/>普通文本还是调用?}
  E -->|调用| F[生成特殊标记+工具名<br/>+逐 token 吐参数 JSON]
  E -->|文本| G[生成普通回答 token]
  F --> H[宿主解析 token 还原成结构化调用]

调用请求也是生成出来的 token

模型「发起调用」不是触发了某个开关，而是自回归地、一个 token 一个 token 地生成出工具名和参数 JSON。这意味着参数 JSON 完全有可能在中途生成出非法结构——少个引号、多个逗号、字段名拼错——因为模型本质是在「续写最可能的文本」，没有任何东西天然保证它续出的是合法 JSON。

理解这一点就理解了两件事。其一，为什么会有「幻觉工具」：模型可以续写出一个你根本没定义的工具名，因为它只是在生成看起来合理的 token。其二，为什么参数需要校验与修复，详见参数校验与修复。

约束解码：从「祈祷合法」到「保证合法」

既然非法 JSON 来自「无约束的自由生成」，解法就是给生成过程套上约束。约束解码（constrained decoding）在每一步采样时，用工具的 JSON Schema 编译出的语法（grammar）算出「此刻哪些 token 是合法续写」，把其余 token 的概率直接掩掉。于是模型物理上不可能吐出违反 schema 的 token，合法性从「事后校验」前移到「生成时保证」。

OpenAI 的 strict 模式、各推理引擎的 grammar 约束都是这套机制的产品化。内部通常涉及有限状态机、上下文无关文法或采样时掩码。本篇只需知道：strict 模式能提高结构契约的可靠性，但不能保证语义正确，schema 合法的 {"city":"火星"} 照样可能生成。生产端仍要做业务校验。

特殊标记与「工具调用是另一种结构化输出」

不同模型用不同方式在 token 流里标记「这是一次工具调用而非普通文本」——有的用专门训练的特殊 token，有的用约定的文本分隔符。无论形式如何，宿主拿到生成结果后要做的就是按这套标记把工具调用从普通文本里解析出来，还原成结构化的 tool_calls。

从这个视角看，工具调用其实是结构化输出的一个特例：都是「让模型生成符合某个 schema 的内容」。区别只在工具调用多了「执行并回灌」的副作用闭环。结构约束解决可解析性，执行契约还必须解决权限、幂等与错误恢复。

开源模型的模板与解析器是协议的一部分

使用托管 API 时，厂商隐藏了从结构化 tools 到 token 序列的渲染过程；自托管开源模型时，这层变成你的责任。Transformers 一类推理栈会用 tokenizer 中的 Jinja chat template 把工具 schema、assistant 调用和 tool 结果渲染成模型训练时见过的精确格式，再用响应解析器把生成 token 还原成统一消息对象。

不能把 OpenAI 风格 JSON 原样套给任意开源模型。不同模型可能要求不同特殊 token、参数对象形态、调用结束标记和结果角色；空格或结束标记不匹配都可能让普通文本能力正常、工具能力却大幅退化。上线前至少做四项契约测试：模板能渲染工具定义；单调用能被解析；并行调用 ID 不丢；工具结果回灌后模型能继续回答。

因此，模型制品不只包括权重，也包括 tokenizer、chat template、response parser 与其版本。升级其中任一项都应重跑工具调用回归集；只比较模型名称而忽略模板版本，会把协议退化误判成模型退化。

这个「token 视角」还能解释几个让新手困惑的实战现象。其一，工具描述的措辞会改变模型行为——因为描述就是上下文 token，改一个动词、加一句边界说明，模型读到的「提示」就变了，选择与填参随之变化，这正是工具模式定义里反复打磨 description 的原因。其二，同样的工具集换个模型表现差很多——不同模型在训练时见过的工具调用格式与特殊标记不同，对同一段渲染文本的「理解」就不同。其三，上下文越长工具调用越容易出错——历史 token 堆积会稀释模型对工具定义的注意力，这也是长链需要结果裁剪的底层原因。把这些现象都还原到「一切皆 token」，你就不会再把它们当成无法解释的玄学。

小结

  • 工具在模型眼里不是函数而是 token：定义被渲染进上下文、调用请求被自回归生成、结果被回灌，全程都是文本。
  • 工具定义占输入 token、要计费、稀释注意力，这是工具一多必须做路由的根因。
  • 调用参数是逐 token 生成的，天然可能非法，也能凭空续写出不存在的工具名（幻觉工具）。
  • 约束解码用 schema 编译的语法掩掉非法 token，把合法性从事后校验前移到生成时保证；strict 模式即其产品化，但只保结构不保语义。
  • 工具调用本质是结构化输出的带副作用特例，结构合法之外还要处理执行权限、幂等与恢复。
  • 自托管开源模型必须把 chat template、response parser 与权重一起版本化并做契约测试。
