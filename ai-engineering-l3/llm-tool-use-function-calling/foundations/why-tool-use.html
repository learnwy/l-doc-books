Part II · Agent Construction工具调用与函数调用基础为何需要工具调用

为何需要工具调用

让一个 2025 年初训练完成的模型回答「现在比特币多少钱」，它要么坦白不知道，要么自信地编一个数字——后者更危险。这不是模型「笨」，而是它的全部知识都被冻结在权重里，冻结的那一刻世界就停在了训练截止日。工具调用要补的，正是这种参数化知识无论如何也补不上的三类先天缺口。

核心概念：参数化知识的三道墙

模型在预训练中把海量文本压缩进了几百 GB 的权重，这种「记在脑子里」的知识叫参数化知识（parametric knowledge）。它强大但有三道无法逾越的墙：

  • 时效墙：权重里只有训练截止日之前的世界。今天的股价、刚发布的版本、昨晚的比分，它一概不知。
  • 私域墙：你公司的订单表、用户的日历、这台机器的文件，从未进入它的训练集，它无从知晓。
  • 动作墙：它只能输出文本，无法产生副作用。它能写出一封邮件的内容，却没有任何办法把这封邮件真正发出去。

工具调用用一个统一的机制同时拆掉三道墙：把「查实时价格」「读私有数据库」「发邮件」都封装成函数交给模型，模型需要时提议调用，宿主程序执行后把结果回灌。下表对比了三道墙在没有工具与有工具时的差异。

缺口 纯参数化模型的表现 引入工具后 典型工具
时效 编造或拒答 实时拉取最新数据 搜索、行情 API
私域 完全无知 按需查询专属数据 数据库、向量检索
动作 只能描述动作 真正执行副作用 邮件、下单、写文件
精确计算 大数算错 调用确定性代码 计算器、代码执行

值得单列的是第四行：即便信息都在上下文里，模型做 13 位乘法、精确日期差这类计算也容易出错，因为它是概率生成而非确定性执行。把这类任务外包给一行 Python，准确率从「大概对」变成「一定对」。

为什么不靠扩大上下文或微调解决

有人会问：把实时数据塞进提示词、或者拿私有数据微调一个模型，不就绕过这三道墙了吗？这两条路都只能解决一部分，且代价高昂。

把数据塞进上下文（即检索增强 RAG）能解决「只读」的时效与私域问题，但它解决不了动作墙——上下文里放再多文本，模型也发不出邮件。而且数据必须由你预先取好放进去；如果你事先不知道模型会需要哪条数据（比如它要先搜索再决定查哪个 ID），静态注入就无能为力，这正是多步工具链存在的理由，详见多步工具链。

微调能把私域知识压进权重，但代价是：知识一变就得重训，时效问题原地复现；它同样产生不了副作用；而且微调会让模型记住事实却未必学会「何时该去查」。工业界的共识是：事实与动作交给工具，风格与格式偏好才考虑微调。

调用契约：模型只提议，执行器才执行

整个 hub 反复强调一个容易被误解的点：模型权重本身从不执行函数。当你看到「模型调用了 get_weather」，模型真正做的是生成一个调用意图；随后由某个受控执行器解析意图、调用真实能力，再把结果送回推理上下文。执行器可能在你的应用里，也可能由模型服务商托管，但都不是语言模型本身。

这个分工有三个重要后果。其一，安全责任在宿主：模型提议删库，执不执行完全由你的代码决定，这是工具调用安全的根基。其二，模型提议的参数可能不合法，需要校验，详见参数校验与修复。其三，这段「调用请求」本质仍是 token 序列，如何让它一定合法是约束解码的范畴，详见工具的 token 表示。

三种执行所有权不要混为一谈

截至 2026 年，生产 API 里常见的工具形态已经不止「应用自己写一个函数」。理解执行所有权，才能知道权限、重试和审计应放在哪里。

形态 谁执行 应用看到什么 应用仍需负责什么
自定义函数 应用或自有工作节点 函数调用请求与参数 参数校验、授权、幂等、结果回灌
服务商内置工具 服务商托管执行器 搜索、文件检索、代码执行等调用项与结果 是否启用、数据边界、结果验证、成本与审计
程序化工具编排 服务商沙箱运行编排代码，再调用获准工具 编排调用及其输出 可见工具集、资源预算、沙箱与副作用策略

内置网页搜索、文件搜索、代码解释器、计算机操作和远程 MCP 等能力减少了宿主手写循环的工作量，却没有把治理责任交给模型。应用仍要先决定当前用户能看见哪些工具、哪些数据可以离开信任边界、哪些副作用需要确认。所谓「服务端自动执行」只是把执行器换了位置，不是取消权限边界。

它把模型变成了智能体的引擎

把「提议—执行—回灌」这个单元循环起来，模型就能根据每一步的真实反馈决定下一步，这正是智能体（agent）的核心循环。可以说工具调用是智能体的发动机：没有工具，所谓自主智能体只是会聊天的玩具。但要强调边界——本 hub 只讲发动机本身，也就是调用契约、模式和编排；完整智能体还要额外解决规划、记忆、状态与恢复问题。

小结

  • 参数化知识有时效、私域、动作三道先天墙，外加精确计算的短板，工具调用用统一机制把它们一并拆除。
  • RAG 与微调各能解决一部分，但都无法产生副作用，也无法应对「事先不知道要查什么」的动态场景。
  • 核心契约是「模型提议、执行器执行」：执行器可以在应用侧或服务商侧，模型权重本身不直接产生副作用。
  • 自定义函数、服务商内置工具、程序化工具编排的执行所有权不同，但权限、数据边界、预算和审计都必须由应用明确控制。
  • 把这个单元循环起来就得到智能体的引擎；本 hub 聚焦引擎本身，智能体的整体设计另见兄弟 hub。
