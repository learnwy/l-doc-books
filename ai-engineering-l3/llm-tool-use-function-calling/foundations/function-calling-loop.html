Part II · Agent Construction工具调用与函数调用基础函数调用循环

函数调用循环

把一次工具调用慢放，你会看到一段在四种消息角色之间往返的对话，而不是某个「函数被模型执行」的瞬间。理解这段往返的每一帧——谁说了什么、用什么角色、宿主在两帧之间做了什么——是后面调试一切工具调用问题的显微镜。

核心概念：四帧是语义，不是唯一线格式

一次最简单的工具调用，上下文里至少新增四条消息，分属四种角色。下表以「查上海天气」为例逐帧展开（沿用 OpenAI Chat Completions 的角色命名，Anthropic 用 user/assistant 加 tool_use/tool_result 块，语义一一对应）。

帧 角色 内容 谁产生
1 user 「上海今天天气怎么样」 用户
2 assistant 含 tool_calls：调用 get_weather(city="上海") 模型
3 tool {"temp":28,"cond":"晴"}，带对应调用 ID 宿主执行后回灌
4 assistant 「上海今天晴，28 度」 模型

关键在第 2 帧与第 3 帧之间那道缝：模型在第 2 帧只是输出了一个调用意图；宿主在缝里解析意图、调用真实函数、把结果包成第 3 帧；模型直到看见第 3 帧才被再次唤醒，生成第 4 帧。Chat Completions 用 finish_reason=tool_calls 表示暂停，Anthropic 用 stop_reason=tool_use，Responses API 则让应用检查输出项里是否出现 function_call。四帧语义相同，字段与容器并不相同。

flowchart TD
  U[user: 提问] --> M1[模型: 输出调用意图<br/>及唯一 call_id]
  M1 --> H[宿主: 按 call_id 执行函数]
  H --> T[tool: 回灌结果<br/>携带同一 call_id]
  T --> M2{模型: 信息够了吗?}
  M2 -->|不够| M1
  M2 -->|够了| F[模型: 生成最终回答]

注意图中的回边：如果第 3 帧的结果让模型发现还需更多信息，它会再次输出 tool_calls，循环继续。这条回边就是多步工具链的来源。

一条真实 Responses 调用轨迹

下面的 TypeScript 片段展示应用侧自定义函数的最小闭环。第一次响应返回 function_call 输出项；应用解析参数并执行本地函数；第二次请求用同一个 call_id 发送 function_call_output。previous_response_id 让服务端续接前一轮上下文，因此这里不必重发完整消息数组。

const first = await client.responses.create({
  model: process.env.MODEL!,
  input: '上海今天天气怎么样？',
  tools: [weatherTool],
});

const call = first.output.find((item) => item.type === 'function_call');
if (!call || call.type !== 'function_call') throw new Error('expected function call');

const args = weatherArgs.parse(JSON.parse(call.arguments));
const result = await getWeather(args);
const second = await client.responses.create({
  model: process.env.MODEL!,
  previous_response_id: first.id,
  input: [
    {
      type: 'function_call_output',
      call_id: call.call_id,
      output: JSON.stringify(result),
    },
  ],
});

这条轨迹还暴露了三个生产契约：模型参数先经本地 schema 解析，真实函数只接收已验证值；工具输出被序列化成明确的数据，而不是拼进任意提示词；若工具有副作用，call_id 还应进入幂等键或执行收据，防止网络重试重复执行。

call_id：把请求和结果对上号的纽带

当一轮里有多个调用时，结果可能乱序返回，靠什么把「第 3 帧的某个结果」对应回「第 2 帧的某个请求」？答案是每个调用请求携带的唯一 tool_call_id（Anthropic 里叫 tool_use 块的 id）。回灌结果时必须原样带上同一个 ID，模型与宿主才能在并行场景下不串台。

这个看似琐碎的字段是并行工具调用能成立的前提：少了它，三个并发查询的结果回来后就成了一锅无法归位的浆糊。实现时最常见的 bug 就是回灌结果时漏带或写错 call_id，模型会因此报「找不到对应的工具调用」而整轮失败。

单轮 vs 多轮：状态必须连续，但不一定手工重放

容易混淆的是两种「多次」。一种是单次模型请求内的内部循环：上面四帧其实跨越了至少两次 API 调用（第 2 帧一次、第 4 帧一次），但它们共享同一段不断追加的消息历史。另一种是跨用户回合的外部循环：用户问完天气又问汇率，新的 user 消息追加在后面，之前的工具调用历史全部保留。

两种循环都要求推理上下文连续，但不再都要求应用手工重发完整消息历史。无状态消息 API 需要重放必要历史；带服务端状态的 API 可以使用响应 ID 或 conversation 标识续接；自建推理服务也可以用显式会话存储恢复。三种做法都必须保证调用意图、工具结果与用户任务位于同一逻辑上下文，否则模型会把工具结果当成来历不明的数据。

一个常见的实现误区是「只发送最后一个结果，却没有续接句柄」。开发者拿到调用意图，执行后把孤立的工具结果当成新请求发送；模型既不知道结果对应哪次调用，也不知道用户原本问了什么。正确做法是二选一：要么重放包含调用意图的必要历史，要么携带服务端提供的连续性句柄。句柄失效、过期或跨租户时必须显式失败，不能悄悄开启新上下文。

谁来决定循环何时停

循环的终止权在宿主，不在模型。模型可以通过停止原因或结构化输出项表态，但宿主必须根据「是否仍有待执行调用、是否已经得到最终文本、预算是否耗尽、策略是否允许继续」共同决定下一步。不要把某一家 API 的单个 finish_reason 当成跨厂商状态机。

但模型可能犯傻——它可能无限请求同一个工具，或在已有足够信息时仍坚持调用。因此生产代码必须在宿主侧加一个最大轮数上限，超过就强制停止并兜底。这条护栏属于工具调用可靠性的内容，但根子在这里：循环的方向盘必须握在你手里。

小结

  • 一次工具调用是 user→assistant(tool_calls)→tool→assistant 的四帧闭环，模型在 tool_calls 帧后暂停，宿主在缝里执行真实函数。
  • 推理上下文必须连续：无状态 API 重放必要历史，有状态 API 使用响应或会话句柄续接，二者不可混成孤立工具结果。
  • tool_call_id 把请求与结果一一对应，是并行调用不串台的前提，也是最常见的 bug 来源。
  • 循环的终止权在宿主：停止原因或调用输出项只是信号，宿主还要检查预算、策略与待执行状态，并设置最大轮数护栏。
