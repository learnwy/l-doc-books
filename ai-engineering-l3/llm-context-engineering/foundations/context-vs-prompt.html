上下文工程与提示工程

很多人把 context engineering 当成 prompt engineering 的时髦新名，这会让你在错误的层面优化——花一周打磨措辞，而真正拖垮智能体的是第 30 轮窗口里 80% 的陈旧历史。这两者不是同义词，也不是替代关系，而是一条谱系上的不同位置。本篇把这条谱系画清楚，并顺带划定本 hub 与 RAG、长上下文、记忆系统的分工，免得后面每篇都要重复解释边界。

核心概念

一句话区分：提示工程优化「一段文本怎么写」，上下文工程优化「整个窗口在多轮生命周期里放什么、怎么管」。提示是上下文的一个片段；上下文工程把提示连同检索、记忆、历史、工具定义、状态一起，当作一个随时间演化的系统来经营。

下图把从「一句提示」到「完整上下文生命周期」画成一条递进谱系，本 hub 站在最右端。

flowchart TD
  P1[一句提示<br/>静态文本] --> P2[模板化提示<br/>变量填充]
  P2 --> P3[动态上下文注入<br/>按需拼检索/记忆]
  P3 --> P4[多轮上下文管理<br/>历史压缩/卸载]
  P4 --> P5[完整生命周期<br/>选择·排序·压缩·隔离]
  P1 -.提示工程.-> P3
  P3 -.上下文工程.-> P5

谱系左段（P1–P3）是提示工程的主场，右段（P3–P5）是上下文工程的主场，两者在「动态注入」处交叠。下表把交叠区和各自专属区分清。

能力 归提示工程 交叠区 归上下文工程
指令措辞、角色设定 ✔
少样本示例的选写 ✔
输出格式约束 ✔
动态注入检索/记忆 ✔
决定保留哪几轮历史 ✔
增长历史的压缩时机 ✔
子任务隔离到子智能体 ✔
跨会话的记忆选回 ✔

交叠区的「动态注入」在提示工程 hub 里有专门一篇，见 动态上下文注入；而「保留哪几轮、何时压缩」是本 hub 上下文压缩 的核心。

一个例子看出层级差异

设想一个客服智能体。提示工程层面，你会打磨系统指令：「你是耐心的客服，先共情再解决，不承诺退款政策外的内容。」这段措辞重要，但它是固定的、写一次就好。

上下文工程层面要回答的是另一批问题：这位用户过去三次工单要不要选进窗口（记忆选择）？知识库里检索到的 8 段政策片段，放几段、按什么顺序放（选择 + 排序）？对话到第 20 轮，前面的寒暄历史要不要压成一句摘要（压缩）？查询订单的工具结果是 2KB 的 JSON，全塞还是只留关键字段（压缩 + 选择）？这些问题每一轮都在变，且决定了同一段好提示在真实会话里是发挥还是被淹没。

提示工程把指令写好；上下文工程保证这条好指令在第 20 轮仍然没被历史挤到模型注意力的盲区——后者依赖 排序与位置效应。

与 RAG、长上下文、记忆系统的分工

这三者常被和上下文工程混为一谈，但它们各管一段，本 hub 只在接口处与它们衔接、不重复其内部。

  • RAG（08_rag-knowledge-systems） 是「从外部知识库检索相关片段」的完整管线，含向量化、向量库、重排。本 hub 把检索视为 上下文选择 的一种候选来源——我们关心「检索回来的片段怎么选进窗口、放哪」，不关心向量库怎么建。RAG 的检索管线见 检索排序。
  • 长上下文（62_long-context-llm-techniques） 是供给侧：用 RoPE 外推、稀疏注意力、KV 压缩让模型架构吃得下更长窗口。本 hub 是需求侧：即便吃得下，也主张少喂、喂对。两者互补，见 检索还是长上下文。
  • 记忆系统（51_ai-agent-memory-systems） 深入记忆的分类（情景/语义/工作记忆）与存储引擎。本 hub 只在 记忆卸载与外存 处与它衔接——记忆如何被选进、卸出当前窗口。记忆分类学见 记忆分类法。

为什么要把它们分开看

把这四件事捏成一团，会导致优化错位：以为加大窗口（长上下文）能解决智能体变笨（其实是上下文管理问题），或以为换个 prompt（提示工程）能止住跨轮腐烂（其实需要压缩与卸载）。分清谱系位置，才能把工程力气花在真正的瓶颈上。本 hub 的四章正是上下文工程专属区（谱系右段）的展开。

小结

  • 提示工程优化「一段文本」，上下文工程优化「整个窗口的多轮生命周期」；提示是上下文的一个片段。
  • 两者在「动态注入」处交叠，但「保留哪些历史、何时压缩、如何隔离」是上下文工程专属。
  • RAG 是检索来源、长上下文是供给侧、记忆系统是存储引擎；本 hub 只在「选进/卸出窗口」的接口处与它们衔接，不重复内部。
  • 分清谱系位置能避免优化错位——别用换 prompt 去治跨轮腐烂，也别用加大窗口去治管理缺失。
