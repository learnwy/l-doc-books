上下文工程

模型每生成一个 token，都只能看见你塞进上下文窗口里的那些字节。上下文工程（context engineering）就是关于这块窗口的全部决策：在多轮、长程的智能体运行中，什么该进窗口、什么该被剔除、增长的历史何时该压缩、子任务该如何隔离到独立的上下文里。它把焦点从「写好一句指令」抬升到「为每一次模型调用动态组装出恰到好处的那一份输入」，是 2025 年下半年起从提示工程里独立出来、并在 2026 年成为智能体可靠性核心瓶颈的工程学科。

这个 hub 围绕一条主线展开：上下文是一种稀缺、会腐烂、需要主动经营的资源。四个章节正是这条主线的四个递进阶段。

「基础」回答为什么需要这门学科、窗口预算如何核算、以及它和邻近概念的分界。先理解「为什么塞满窗口反而更差」，才谈得上后面的取舍。

「组装」处理单次调用的静态问题：从海量候选里选什么（选择）、选中的内容怎么排（排序与位置效应）、放不下时怎么缩（压缩）。这是把一份输入装配成型的三道工序。

「管理」处理跨轮、跨会话的动态问题：信息怎么卸载到窗口之外的外存（记忆卸载）、任务进行中怎么用草稿板维持状态（状态与草稿板）、以及上下文如何随轮次累积而败坏、又如何防治（腐烂与污染）。组装是空间问题，管理是时间问题。

「实践」把前三章落到真实智能体上：多智能体如何靠上下文隔离扩展、上下文质量怎么评测、以及一份反模式清单。

本 hub 与兄弟 hub 的分工边界要划清楚。提示工程（07_prompt-engineering）管的是「怎么措辞一条指令」，本 hub 管的是「窗口里整体放什么、按什么生命周期管理」——指令只是上下文的一个片段。长上下文技术（62_long-context-llm-techniques）管的是「如何让模型在架构与推理层面吃得下百万 token」（RoPE 外推、稀疏注意力、KV 压缩），是供给侧；本 hub 管的是「即便吃得下，也该少喂、喂对」，是需求侧。智能体记忆（51_ai-agent-memory-systems）深入记忆的分类学与存储架构（情景/语义/向量库），本 hub 只在「记忆如何被选进、卸出当前窗口」这一接口处与它衔接。RAG（08_rag-knowledge-systems）是「从外部知识库检索片段」的完整管线，本 hub 把检索视为「选择」策略的一种来源，不重复其向量库与重排细节。提示缓存（76_prompt-caching-systems）是上下文稳定排序后的一个收益变现层。

推荐学习路径。若你是刚接触智能体开发的工程师，按 基础 → 组装 → 管理 → 实践 顺序通读即可。若你已在调试一个会「越跑越笨」的智能体，可直接跳到「上下文腐烂与污染」定位症状，再回看「压缩」与「记忆卸载」找对策。若你在做多智能体编排，重点是「智能体上下文工程」与「上下文选择」。

前置知识：理解 token 与注意力的基本概念（见 07_prompt-engineering/1_prompt-fundamentals/2_how-llms-process-prompts.md），知道什么是上下文窗口。不需要预先掌握 RAG 或长上下文的内部机制——本 hub 在需要处会一句点到并链接过去。
