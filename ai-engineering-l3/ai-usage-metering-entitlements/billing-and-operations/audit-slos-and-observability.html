审计、SLO 与业务可观测性

核心概念

一个计量 API 99.99% 可用，仍可能把重复事件计入两次、把事件放错账期或给错误客户收费。基础设施健康与业务正确性必须分开测量。Google SRE 的服务级目标章节强调从用户在意的行为定义 SLI，并明确把正确性视为系统健康的重要指标。

计量控制面的用户包括最终客户、产品请求路径、财务运营和审计者。每类用户在意的行为不同：入口关心接受延迟，在线授权关心决定延迟，财务关心封口与对账，客户关心数量和金额可解释。

SLI、SLO 与错误预算

SLO 明确时间窗、纳入范围、数据来源和目标。例如“最近三十天内，99.9% 合法事件在首次接收后五分钟内进入可查询聚合”比“计量服务高可用”更可执行。具体百分比由客户承诺、收入风险和团队能力决定，不能复制示例。

关键 SLI 至少覆盖摄取正确性、摄取新鲜度、聚合确定性、权益决策、账期最终化、交付完整性和对账差异。金额风险还需要绝对值指标，例如未解释差额金额和受影响客户数；单纯百分比会掩盖大客户事故。

错误预算把可靠性和发布速度连接起来。若聚合重放哈希不一致或未解释金额差异耗尽预算，应停止价格引擎、账本模式和供应商路由等高风险变更，优先恢复正确性。普通产品界面发布可以采用不同预算，不应被一刀切冻结。

指标、日志与追踪

指标用于聚合趋势，日志保存离散状态转换，追踪关联一次业务意图跨越的服务。遵循 OpenTelemetry 通用语义约定可以统一 trace、metric、log 与 event 的字段命名，但计量领域仍需自己的低基数属性。

追踪链从生产者 trace_id 连接入口、账本记录、聚合切片、权益决定、交付批次和供应商回执。财务审计依赖稳定业务 ID，不依赖追踪系统永久保存；trace 是诊断加速器，不是账本。

指标标签禁止客户 ID、event ID、发票 ID 和任意模型名等无界值。按客户调查时使用受控日志或查询接口。日志也不保存提示词、模型输出、支付凭证或完整外部载荷，只保留最小审计字段和安全指针。

审计证据与访问控制

每个会影响金额或访问权的命令记录 actor、authority、intent ID、目标、前后 revision、原因、发生时间、记录时间和结果。自动任务的 actor 是服务身份和部署版本，人工任务关联审批或工单。读取敏感审计数据本身也写审计记录。

证据链 起点 必须可追到
客户用量争议 发票行 切片、价格、账本、原事件
权益拒绝争议 decision ID 策略、快照、用量与预留
信用余额争议 balance revision grant、debit、expire、restore
迁移差异 migration run 源高水位、映射、目标哈希
管理员改价 price version 草稿、审批、激活与客户迁移

审计导出需要租户隔离、字段脱敏、访问时限和用途限制。保留策略区分财务证据、运维日志与调试追踪，不因为“审计”两个字无限保留所有原文。

告警、看板与值班动作

看板按事实路径组织：入口 → 账本 → 聚合 → 权益 → 交付 → 对账，而不是按微服务名称堆 CPU 图。每一段展示吞吐、失败、延迟、水位线和积压，并能钻取到安全的业务 ID。

告警只针对需要行动的用户或金额影响。Google SRE 的生产服务最佳实践把监控输出分成需要立即行动的 page、数日内处理的 ticket 和供分析的 logging。计量系统可据此把“发票即将错过最终化”分页，把“某来源重复率缓慢升高”建工单，把单次无害重试留日志。

每个告警附运行手册：确认影响范围、冻结哪些写入、如何查看高水位、怎样安全重放、对账入口和升级联系人。告警恢复不等于事故结束；金额或权益影响必须对账到零或形成明确客户处置。

小结

  • API 可用性不能代表计量正确性，业务 SLI 独立定义。
  • SLO 从客户、请求路径、财务和审计者在意的结果反推。
  • 指标、日志、追踪和账本各自承担聚合、状态、诊断和证据责任。
  • 稳定业务 ID 贯穿事实到发票，敏感原文不进入低门槛遥测。
  • 错误预算控制高风险变更，告警必须对应具体值班动作。
  • 下一节通过测试、迁移与故障演练验证这些目标不是纸面承诺。
