用量事件模式与维度契约

核心概念

一条用量事件不是“某个接口被调用”的日志，而是产品承认的一次可计量事实。它必须足以支持去重、归属、聚合和审计，又不能提前混入价格、套餐或发票状态。价格会变化，发生过的消费事实不应随之变化。

CloudEvents 核心规范要求每个事件包含 id、source、specversion 与 type，并规定生产者保证 source + id 对不同事件唯一。这个组合非常适合成为计量入口的自然身份，但领域仍需补充消费主体、资源、数量、单位和模式版本。

flowchart LR
    P[消费事实生产者] --> E[事件信封]
    E --> V{模式与语义校验}
    V -->|通过| L[接受账本]
    V -->|拒绝| Q[隔离记录]
    L --> A[聚合与权益读取]
字段 所有者与语义 约束
event_id 生产者为一次消费分配的稳定身份 同一重试保持不变
source 发生事实的服务或设备域 与 event_id 联合唯一
event_type 事实种类及兼容版本 不承载价格名称
occurred_at 消费真正发生的时间 UTC、RFC 3339、不可由接收端覆盖
received_at 计量入口首次接受的时间 由入口时钟写入
subject_id 承担额度或账单归属的稳定主体 使用内部不透明 ID
resource_id 被消费资源或功能 与权益功能键可映射但不等同
quantity 原子消费量 用十进制定点字符串表达
unit 数量单位 由模式版本固定
dimensions 定价或审计需要的有限维度 白名单、低基数优先
schema_version 数据载荷的兼容契约 破坏性变更升主版本
trace_id 诊断关联 不参与去重或计价

同章的幂等与去重会使用 source + event_id，因此这里的身份设计是后续正确性的前置条件。

找到最接近事实的生产者

事件应由最接近资源交付结果、且能判断“消费是否成立”的组件产生。API 网关只知道请求进入，不一定知道模型是否成功返回；模型适配器知道令牌数量，却未必知道业务工作流是否接受结果。团队需要为每个 event_type 指定唯一事实所有者，并写出成立条件。

场景 合理事实点 不宜直接计量的信号
文本生成 供应商响应已验证且结果被产品接受 请求开始、重试次数
Agent 工具调用 工具产生不可逆或可交付结果 模型仅提出调用意图
异步任务 任务进入成功终态并记录资源消耗 队列投递成功
存储占用 采样时点或周期积分的明确快照 任意一次对象读取

若一个业务动作会产生多个可收费资源，就发送多个拥有独立身份的原子事件，并用 correlation_id 关联。不要发送一个包含输入令牌、输出令牌、图片和工具费用的“大事件”，否则部分更正只能覆盖整条记录。

维度治理与基数预算

维度决定未来可以如何分组和定价，也决定存储成本、查询复杂度与隐私风险。OpenMeter 的事件最佳实践建议只携带计量所需的值和分组字段，避免多余与深层嵌套数据；数值用字符串还能避免跨语言 JSON 精度损失。

为每个事件类型维护维度注册表，每个维度至少声明用途、基数上限、敏感等级、缺省行为和移除日期。model_family、region、operation 通常可以受控；完整提示词、电子邮箱、任意 URL 或请求头不应进入计量维度。高基数诊断信息放在受控日志，通过 trace_id 关联即可。

维度缺失不能一律补成 unknown。如果该维度参与价格或客户归属，缺失事件必须隔离；如果只影响分析，可以显式使用版本化缺省值。这样的区分防止数据质量问题静默转成少收或多收。

数量、单位与精度

同一个 event_type + schema_version 只能有一个基本单位。例如令牌按 token、运行时间按 millisecond、存储按 byte_second。不要让生产者自由发送 seconds 或 minutes，也不要在入口读取当前价格后换算成货币。

数量使用非负十进制定点值，模式声明允许的小数位。金额使用最小货币单位或十进制定点金额值对象，不能用二进制浮点。负数不表示更正；更正是另一种带原因和目标身份的补偿事实。这样可以区分真实负消费、退款、取消和价格调整。

对于输出令牌这类供应商给出的权威数字，事件应同时记录 measurement_source=provider。对于本地估算值，使用不同事件类型或显式 measurement_quality=estimated，并禁止它直接进入最终账单，除非价格合同明确接受估算。

模式演进与入口校验

入口校验分三层：信封校验检查身份和时间格式；语义校验检查单位、数量范围和必需维度；归属校验把 subject_id 映射到有效客户或内部账户。校验失败也要留下拒绝回执，其中包含事件身份、错误码、模式版本和安全的载荷指纹，但不应保存未经批准的敏感原文。

兼容新增字段可以保持同一主版本，消费者必须忽略不认识的可选字段；删除字段、改变单位或改变成立条件需要新的事件类型版本。新旧版本并行期由适配层归一到内部规范事件，聚合器不直接理解每个生产者版本。

一个可执行的入口契约可以表示为：

{
  "specversion": "1.0",
  "id": "chatcmpl_01:accepted",
  "source": "urn:service:model-adapter",
  "type": "com.example.ai.tokens.consumed.v1",
  "time": "2026-08-31T05:10:12.104Z",
  "subject": "account_8f2a",
  "data": {
    "resource_id": "text-generation",
    "quantity": "1837",
    "unit": "token",
    "dimensions": {
      "direction": "output",
      "model_family": "frontier"
    },
    "schema_version": "1.2"
  }
}

小结

  • 事件只描述消费事实，不携带套餐、单价或账单状态。
  • source + event_id 必须跨重试稳定，occurred_at 与 received_at 各司其职。
  • 每种事件指定唯一事实所有者与成立条件，复合消费拆成原子事件。
  • 维度实施白名单、基数和敏感等级治理，诊断详情通过追踪关联。
  • 单位与精度由模式版本固定，更正通过补偿事件表达。
  • 入口校验产生可审计回执，为后续只追加计量账本提供干净事实。
