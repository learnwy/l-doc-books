幂等、去重与重放安全

核心概念

分布式交付无法用“一定只到一次”作为事实。客户端超时会重试，消息消费者会在确认前崩溃，运维会重放历史分区；可靠计量的目标不是消灭重复，而是让同一个消费事实无论到达多少次都得到同一个可观察结果。

CloudEvents 规范允许重复发送时复用同一 id，消费者可把相同 source + id 视为重复。Stripe 的用量记录指南也要求为计量事件使用幂等标识，防止延迟或重试造成重复上报。这两者共同说明：幂等身份必须来自业务事实，而不是每次 HTTP 尝试生成的新 UUID。

sequenceDiagram
    participant P as 生产者
    participant I as 计量入口
    participant D as 去重存储
    participant L as 接受账本
    P->>I: event(key, payload)
    I->>D: 原子插入 key + fingerprint
    alt 首次出现
        D-->>I: created
        I->>L: 追加 accepted
        I-->>P: accepted receipt
    else 同键同载荷
        D-->>I: existing receipt
        I-->>P: duplicate receipt
    else 同键异载荷
        D-->>I: conflict
        I-->>P: rejected conflict
    end

幂等处理的稳定返回值称为回执。回执包含 event_key、接受序号、载荷指纹、首次接收时间和状态；重复请求返回原回执，而不是重新执行下游副作用。

幂等键与载荷指纹

最稳妥的键通常是 (tenant_scope, source, event_id)。若生产者已有跨重试稳定的业务操作 ID，可再附加资源分量，例如 workflow_activity_id + billable_component。绝不能使用接收时间、队列偏移或每次请求生成的随机值作为唯一身份。

载荷指纹用于发现同键异义。计算前先执行确定性规范化：固定字段顺序、统一十进制表示、标准化时间和空值，并排除 received_at、追踪字段等每次投递可能变化但不影响语义的内容。指纹只用于冲突检测，不代替原始证据。

到达类型 键比较 指纹比较 处理
首次事件 不存在 不适用 接受并保存回执
网络重试 相同 相同 返回原回执，不重复记量
错误复用键 相同 不同 隔离为冲突，不覆盖旧载荷
新消费事实 不同 任意 独立接受
合法更正 新键且引用原键 新语义 走补偿流程，不伪装成重试

同章的事件模式定义哪些字段进入语义指纹。只看 event_id 而不校验指纹，会让生产者错误静默吞掉真实用量；只看整个 JSON 字节，又会把无关的追踪变化误判成冲突。

原子接受边界

“先查是否存在，再插入事件”存在竞争窗口。两个实例同时查询为空，随后都写入账本，就会重复记量。正确做法是在一个数据库事务内依赖唯一约束执行插入，并把接受账本与回执一起持久化；冲突路径读取已有回执。

对于消息队列，提交消费偏移与写数据库无法天然成为一个事务。可以采用“数据库收件箱”模式：消费者先以事件键原子插入收件箱和账本，成功后再确认消息；确认失败导致重复投递，但唯一约束让第二次成为无害重复。不要用进程内缓存承担财务去重。

去重记录需要明确保留期。若事件可能在十三个月后因审计重放，而去重键只保留三十天，旧事件会重新收费。安全选择是让计量账本中的唯一键与财务证据保留期一致；若成本迫使热去重层更短，仍需在冷账本建立全局唯一索引或重放前装载历史键集。

重放、批次与下游幂等

重放不是异常旁路，而是正式操作。每次重放拥有 replay_run_id、源范围、时间边界、原因、操作者和预期事件数。它不能改写事件身份，也不能绕过去重。重放完成后输出接受数、重复数、冲突数和缺失数，供审计者复核。

批量上报需要逐事件回执。整个批次只有一个幂等键会让部分成功后的重试陷入两难：全部重做会重复，全部跳过会漏记。批次 ID 只用于传输追踪，每条事件仍以自己的业务键去重。

下游也要幂等。聚合切片用 (meter_id, subject_id, window, revision) 标识，供应商交付用 (invoice_candidate_id, line_revision) 标识，Webhook 处理用供应商事件 ID 标识。入口幂等不能自动保护所有后续副作用；每个跨边界命令都要有自己的意图身份。

冲突处理与可观测性

同键异载荷是数据完整性事故，不应选择“最后写入胜出”。系统保存两份安全指纹和字段级差异，标记生产者、部署版本与追踪信息，把事件送入隔离队列，并阻止它进入收费聚合。值班者修复生产者后，以新的更正身份补齐事实。

指标 正常信号 需要行动的信号
重复率 与已知重试率相符 单一生产者突然上升
冲突率 接近零 任一同键异载荷
去重查询延迟 稳定且低于入口预算 尾延迟耗尽摄取 SLO
重放接受率 与计划预估相符 大量“新事件”或缺失
去重键年龄 覆盖最大重放窗口 老键提前过期

故障演练应包含：响应在提交后丢失、消费者在写入后崩溃、双实例同时处理、去重缓存丢失和旧分区重放。每次演练都验证最终账本只出现一个 accepted 事实，同时重复回执可查询。

小结

  • 幂等身份来自消费事实，不来自传输尝试。
  • 同键同指纹返回原回执；同键异指纹必须隔离，绝不覆盖。
  • 唯一约束、接受账本和回执在同一原子边界内写入。
  • 批次只负责传输，每条事件仍独立去重。
  • 去重保留期覆盖最老合法重放，重放本身拥有可审计运行记录。
  • 后续聚合、交付和 Webhook 各自建立幂等键，并把结果写入只追加计量账本。
