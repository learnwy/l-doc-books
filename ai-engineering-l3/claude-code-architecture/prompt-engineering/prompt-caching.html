提示词缓存

缓存作为一等公民

在 Claude Code 中，提示词缓存不是事后优化——它是架构设计的核心约束。系统提示词的静态/动态分界、Attachment 的独立消息设计、甚至消息类型的选择，都受到"最大化缓存命中率"这一目标的深刻影响。src/prompt-cache/promptCacheBreakDetection.ts（727 行）专门用于检测和诊断缓存失效。

// src/prompt-cache/promptCacheBreakDetection.ts — 核心结构（简化）
interface CacheBreakDetector {
  recordPromptState(messages: SDKMessage[], systemPrompt: string): PromptSnapshot;
  checkResponseForCacheBreak(snapshot: PromptSnapshot, response: APIResponse): CacheBreakReport;
}

interface PromptSnapshot {
  systemPromptHash: string;
  messageHashes: string[];
  totalTokenEstimate: number;
  cacheBreakpointPositions: number[];
  trackedSources: TrackedSource[];
  timestamp: number;
}

interface CacheBreakReport {
  cacheHit: boolean;
  cacheReadTokens: number;
  expectedCacheTokens: number;
  breakDetected: boolean;
  breakCause: CacheBreakCause | null;
  diffFile: string | null;
}


cache_control 标记
Claude Code 通过 getCacheControl() 为系统提示词的关键位置添加缓存控制标记。Anthropic API 支持 ephemeral 缓存类型，有不同的 TTL（存活时间）。


// src/prompt-cache/cache-control.ts — 缓存标记（简化）
interface CacheControl {
  type: 'ephemeral';
  ttl?: number;
}

function getCacheControl(section: string): CacheControl | undefined {
  const TTL_MAP: Record<string, number> = {
    'system-prompt-static': 3600,
    'system-prompt-dynamic': 300,
    'tool-prompts': 3600,
    'conversation-history': 300,
  };

  const ttl = TTL_MAP[section];
  if (!ttl) return undefined;

  return { type: 'ephemeral', ttl };
}

缓存断点放置
addCacheBreakpoints() 在系统提示词的战略位置放置 cache_control 标记：


// src/prompt-cache/cache-control.ts — 断点放置（简化）
function addCacheBreakpoints(systemBlocks: ContentBlock[]): ContentBlock[] {
  const breakpoints: BreakpointPosition[] = [
    { after: 'static-prompt-end', ttl: 3600 },
    { after: 'dynamic-prompt-end', ttl: 300 },
    { after: 'tool-prompts-end', ttl: 3600 },
  ];

  return systemBlocks.map((block, index) => {
    const bp = breakpoints.find((b) => b.position === index);
    if (bp) {
      return {
        ...block,
        cache_control: { type: 'ephemeral', ttl: bp.ttl },
      };
    }
    return block;
  });
}


提示： 缓存断点的放置是一个精细的优化。放错位置会导致整个缓存段失效。例如，如果将动态内容混入静态段落，即使只有一个字符变化也会导致静态段落的缓存失效。






缓存失效检测
promptCacheBreakDetection.ts 实现了一套完整的缓存失效检测系统。它在 API 调用前后对比提示词状态，检测缓存是否被正确命中。


调用前：recordPromptState
// src/prompt-cache/promptCacheBreakDetection.ts — 调用前记录（简化）
const MAX_TRACKED_SOURCES = 10;

function recordPromptState(messages: SDKMessage[], systemPrompt: string): PromptSnapshot {
  const systemHash = createHash('sha256').update(systemPrompt).digest('hex');

  const messageHashes = messages.map((msg) => createHash('sha256').update(JSON.stringify(msg)).digest('hex'));

  const trackedSources = identifyCacheSources(systemPrompt, messages).slice(0, MAX_TRACKED_SOURCES);

  return {
    systemPromptHash: systemHash,
    messageHashes,
    totalTokenEstimate: estimateTokens(systemPrompt) + estimateTokens(messages),
    cacheBreakpointPositions: findBreakpointPositions(systemPrompt),
    trackedSources,
    timestamp: Date.now(),
  };
}
调用后：checkResponseForCacheBreak
// src/prompt-cache/promptCacheBreakDetection.ts — 调用后检查（简化）
function checkResponseForCacheBreak(snapshot: PromptSnapshot, response: APIResponse): CacheBreakReport {
  const cacheReadTokens = response.usage.cache_read_input_tokens ?? 0;
  const totalInputTokens = response.usage.input_tokens;
  const cacheHit = cacheReadTokens > 0;
  const cacheRatio = totalInputTokens > 0 ? cacheReadTokens / totalInputTokens : 0;

  const expectedCacheTokens = estimateExpectedCache(snapshot);
  const breakDetected = cacheHit ? cacheReadTokens < expectedCacheTokens * 0.5 : snapshot.timestamp > 0;

  let breakCause: CacheBreakCause | null = null;
  let diffFile: string | null = null;

  if (breakDetected) {
    breakCause = diagnoseCacheBreak(snapshot, response);
    diffFile = generateDiffFile(snapshot, response, breakCause);
  }

  return {
    cacheHit,
    cacheReadTokens,
    expectedCacheTokens,
    breakDetected,
    breakCause,
    diffFile,
  };
}


缓存失效原因诊断
// src/prompt-cache/promptCacheBreakDetection.ts — 原因诊断（简化）
type CacheBreakCause =
  | 'system_prompt_changed'
  | 'message_modified'
  | 'message_removed'
  | 'message_inserted'
  | 'ttl_expired'
  | 'server_side'
  | 'unknown';

function diagnoseCacheBreak(snapshot: PromptSnapshot, response: APIResponse): CacheBreakCause {
  if (snapshot.systemPromptHash !== computeCurrentHash()) {
    return 'system_prompt_changed';
  }

  const currentHashes = getCurrentMessageHashes();
  const removed = snapshot.messageHashes.filter((h) => !currentHashes.includes(h));
  if (removed.length > 0) return 'message_removed';

  const inserted = currentHashes.filter((h) => !snapshot.messageHashes.includes(h));
  if (inserted.length > 0) return 'message_inserted';

  const elapsed = Date.now() - snapshot.timestamp;
  if (elapsed > 300_000) return 'ttl_expired';

  return 'unknown';
}

Diff 文件生成与缓存优化
当检测到缓存失效时，generateDiffFile() 生成调试报告，包含时间戳、失效原因、预期/实际缓存 token 数、缓存比率，以及消息 hash diff 和 tracked source 变更列表。在 verbose 模式下输出到终端，正常模式保存到 ~/.claude/debug/cache-breaks/。

API 的缓存基于前缀匹配——当消息列表从 [msg1, msg2, msg3] 增长到 [msg1, msg2, msg3, msg4] 时，前 3 条消息命中缓存，只有 msg4 需要处理。这就是为什么 Attachment 作为独立消息而非混入系统提示词——保护前缀缓存。




提示： Diff 文件在 verbose 模式下输出到终端。如果你发现 API 成本异常升高，检查 ~/.claude/debug/cache-breaks/ 目录可以帮助定位缓存失效的原因。






小结
    

  • 提示词缓存是 Claude Code 的架构级设计约束，影响了系统提示词分层、消息类型和 Attachment 设计。
    • 

  • cache_control 标记使用 ephemeral 类型，静态段落 TTL=3600s，动态段落 TTL=300s。
    • 

  • promptCacheBreakDetection.ts（727 行）在 API 调用前后记录和对比提示词状态，检测缓存失效。
    • 

  • 支持 6 种失效原因诊断（system_prompt_changed、message_modified/removed/inserted、ttl_expired、server_side）。
    • 

  • MAX_TRACKED_SOURCES = 10，限制跟踪的缓存源数量以控制开销。
    • 

  • 核心优化原则：静态前置 + Attachment 隔离 + 前缀缓存，缓存读取价格仅为正常输入的 1/10。
