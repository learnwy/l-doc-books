工具接口设计

Tool 泛型类型

Tool.ts（792 行）定义了 Claude Code 工具系统的核心类型——Tool<Input, Output, P> 是一个包含约 40 个方法和属性的泛型接口。三个类型参数分别代表输入类型、输出类型和权限检查上下文。

interface Tool<Input, Output, P = void> {
  name: string;
  description: string;
  isEnabled: (context: ToolUseContext) => boolean;
  isConcurrencySafe: boolean;
  isReadOnly: boolean;

  inputSchema: z.ZodType<Input>;
  validateInput: (input: Input, context: ToolUseContext) => Promise<ValidationResult>;
  checkPermissions: (input: Input, context: P) => Promise<PermissionResult>;
  canUseTool: (input: Input, context: ToolUseContext) => Promise<boolean>;
  call: (input: Input, context: ToolUseContext) => Promise<ToolResult<Output>>;

  mapToolResultToToolResultBlockParam: (result: ToolResult<Output>) => ToolResultBlockParam;

  userFacingName: (input: Input) => string;
  progressIndicator: (input: Input) => string;
}

三个泛型参数的设计意图：

类型参数 含义 典型实例
Input 工具输入 { command: string; timeout?: number }
Output 工具输出 { stdout: string; exitCode: number }
P 权限上下文 { allowedPaths: string[] } 


提示： isConcurrencySafe 和 isReadOnly 两个布尔属性看似简单，但它们是工具编排系统决定并行执行策略的关键信号——只有标记为 concurrency-safe 的工具才能并行运行。






ToolUseContext 执行上下文
每次工具调用都会接收一个 ToolUseContext 对象，它封装了工具执行所需的全部环境信息。


interface ToolUseContext {
  abortController: AbortController;
  readFileState: Map<string, FileState>;
  appState: AppState;
  options: {
    maxFileReadBytes: number;
    maxGlobResults: number;
  };
  queryTracker: QueryTracker;
  mcpClients: Map<string, McpClient>;
  agentDefinitions: AgentDefinition[];
  hooks: ToolHooks;
}

interface FileState {
  content: string;
  mtime: number;
  encoding: BufferEncoding;
}

readFileState 缓存尤为重要——FileReadTool 在检测到同一文件内容未变时（mtime 相同）可以返回精简的 file_unchanged 存根而非完整内容，节省大量 prompt token。




提示： abortController 的设计让长时间运行的工具（如 BashTool 执行复杂命令）可以被中途取消，不会阻塞整个对话流。






buildTool 工厂函数
buildTool() 是工具系统的工厂函数，接受一个部分定义的工具对象，填充缺省值后返回完整的 Tool 实例。


function buildTool<Input, Output, P>(
  partial: Partial<Tool<Input, Output, P>> & {
    name: string;
    call: Tool<Input, Output, P>['call'];
    inputSchema: z.ZodType<Input>;
  },
): Tool<Input, Output, P> {
  return {
    isEnabled: () => true,
    isConcurrencySafe: false,
    isReadOnly: false,

    validateInput: async () => ({ valid: true }),
    checkPermissions: async () => ({ result: 'ask' }),
    canUseTool: async () => true,

    userFacingName: () => partial.name,
    progressIndicator: () => `Running ${partial.name}...`,
    mapToolResultToToolResultBlockParam: defaultMapper,

    ...partial,
  };
}

isConcurrencySafe: false 的默认值体现了"fail-closed"安全原则——如果工具开发者忘记声明并发安全性，系统会保守地将其视为不安全，禁止并行执行。




提示： checkPermissions 默认返回 'ask' 而非 'allow'，意味着未明确声明权限策略的工具默认需要用户确认。这是另一个 fail-closed 设计。






惰性 Schema 模式
工具的 Zod Schema 构造可能很昂贵（尤其是包含复杂嵌套类型的工具），lazySchema() 将 Schema 的构造推迟到首次使用时。


function lazySchema<T>(factory: () => z.ZodType<T>): z.ZodType<T> {
  let cached: z.ZodType<T> | null = null;

  return new Proxy({} as z.ZodType<T>, {
    get(_, prop) {
      if (!cached) {
        cached = factory();
      }
      return Reflect.get(cached, prop);
    },
  });
}

const bashToolSchema = lazySchema(() =>
  z.object({
    command: z.string().min(1).describe('Shell command to execute'),
    timeout: z.number().optional().describe('Timeout in milliseconds'),
    background: z.boolean().optional().describe('Run in background'),
  }),
);

当注册了 30+ 工具但用户单次对话可能只用到 3-5 个时，惰性 Schema 显著减少了不必要的初始化开销。




ToolResult 结果类型
所有工具调用统一返回 ToolResult<T> 类型，封装了结果数据、错误标志和可选的 assistant 消息映射。


interface ToolResult<T> {
  data: T;
  isError: boolean;
  resultForAssistant?: string;
}

function successResult<T>(data: T): ToolResult<T> {
  return { data, isError: false };
}

function errorResult<T>(data: T, message?: string): ToolResult<T> {
  return {
    data,
    isError: true,
    resultForAssistant: message,
  };
}




字段
类型
说明

T

isError
boolean
是否为错误结果




resultForAssistant
string?
覆盖默认的结果展示（可选）





resultForAssistant 的设计意图：有时候原始数据对模型来说信息过多或格式不友好，通过 resultForAssistant 可以提供一个经过精简的版本。例如 FileReadTool 在去重命中时，不返回完整文件内容而是返回 "file_unchanged" 字符串。




PermissionResult 权限结果
权限检查返回三种可能的结果，形成了工具安全系统的核心决策模型。


type PermissionResult =
  | { result: 'allow'; reason?: string }
  | { result: 'deny'; reason: string }
  | { result: 'ask'; message: string };




结果
触发场景
后续行为
示例





allow
规则明确允许
直接执行
读取项目内文件




deny
规则明确禁止
返回错误
访问 /etc/shadow




ask
无匹配规则或需确认
展示 UI 等待用户
执行 rm 命令





三值结果比简单的布尔型更灵活——ask 状态让系统能够在不确定时将决策权交给用户，而不是一刀切地允许或拒绝。




提示： allow 和 deny 都可以携带 reason 字段，用于向用户或日志解释权限决策的依据。这对调试权限规则非常有价值。






小结
    

  • Tool<Input, Output, P> 是一个包含 ~40 个方法属性的泛型接口，三个类型参数分别控制输入、输出和权限上下文。
    • 

  • ToolUseContext 封装了工具执行的全部环境信息，其中 readFileState 缓存支持文件读取去重优化。
    • 

  • buildTool() 工厂函数采用 fail-closed 默认策略：isConcurrencySafe: false、checkPermissions: 'ask'。
    • 

  • lazySchema() 通过 Proxy 延迟构造 Zod Schema，在 30+ 工具场景下显著减少启动开销。
    • 

  • PermissionResult 的三值模型（allow/deny/ask）比布尔型更灵活，让不确定场景可以交由用户决策。
    •
