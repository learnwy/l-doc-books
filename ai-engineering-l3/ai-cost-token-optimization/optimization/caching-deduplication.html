缓存与去重策略

核心概念

缓存以存储换推理——存储成本比推理成本低 2-3 个数量级。三层缓存体系：精确/语义缓存（相同或相似请求直接返回历史结果，成本 ≈ 0）、Prompt Cache（厂商内建，重复输入前缀仅付标价 10%）、请求去重（幂等请求合并，消除并发重复）。对高频长前缀场景，综合缓存可节省 70-90% 输入成本。

缓存是"不花钱"的优化

缓存的本质是空间换时间——或更准确地说，存储成本换推理成本。对 LLM 推理而言，存储成本（内存/磁盘）比推理成本（GPU 计算）低 2-3 个数量级，使得缓存成为 ROI 最确定的优化手段之一。

LLM 场景的三层缓存体系：

graph TD
    A[请求到达] --> B{精确缓存命中?}
    B -->|是| C[返回缓存结果<br/>成本 = 0]
    B -->|否| D{语义缓存命中?}
    D -->|是| E[返回相似结果<br/>成本 = 检索成本]
    D -->|否| F{Prompt Cache 命中?}
    F -->|是| G[LLM 调用<br/>输入成本 × 10%]
    F -->|否| H[完整 LLM 调用<br/>全价]

    C --> I[成本节省 100%]
    E --> J[成本节省 ~100%]
    G --> K[成本节省 70-90%]
    H --> L[无节省]

层级一：Prompt Cache（厂商内建）

Prompt Cache 是 2025-2026 年各厂商标配的成本优化功能——重复出现的输入 token 前缀仅需支付标价的 10-25%。

OpenAI 自动缓存

OpenAI 的 Prompt Cache 完全自动触发，无需代码改动：

  • 前缀超过 1024 token 自动进入缓存
  • 缓存命中时输入 token 价格降至标价的 10%
  • TTL 约 5-10 分钟（按调用频率动态调整）
  • 支持跨请求的共享前缀

最佳实践：将不变的内容（系统 Prompt、few-shot 示例、工具描述）放在消息列表的最前面，动态内容放在后面。这样不变部分的缓存命中率最大化。

messages = [
    # 固定前缀 — 高缓存命中率
    {"role": "system", "content": SYSTEM_PROMPT},      # 4000 tokens
    {"role": "user", "content": FEW_SHOT_EXAMPLES},    # 2000 tokens
    # 动态后缀 — 每次不同
    {"role": "user", "content": user_query},           # 200 tokens
]
# 4000 + 2000 = 6000 tokens 缓存命中 → 仅付 10%
# 实际输入成本 = 6000×0.1 + 200×1.0 = 800 等效 token

Anthropic 显式缓存

Anthropic 的缓存需要用 cache_control 标记显式声明缓存断点：

response = client.messages.create(
    model="claude-sonnet-4-6",
    system=[
        {
            "type": "text",
            "text": LONG_SYSTEM_PROMPT,
            "cache_control": {"type": "ephemeral"}  # 标记缓存
        }
    ],
    messages=[{"role": "user", "content": query}]
)

Anthropic 缓存的经济学略有不同：

操作 费用 说明
首次写入缓存 标价 × 125% 比不缓存还贵 25%
后续读取缓存 标价 × 10% 极大折扣
不缓存（基准） 标价 × 100% 每次全价

盈亏平衡点：第 N 次调用后缓存开始盈利：

1.25+(N−1)×0.1<N×1.01.25 + (N-1) \times 0.1 < N \times 1.01.25+(N−1)×0.1<N×1.0

解得 N>1.28N > 1.28N>1.28——即第 2 次调用就开始省钱。但考虑 TTL 过期和命中率，实际盈亏平衡在 3-4 次调用。

缓存效果量化

一个日均 5 万次调用的 Agent 系统（8K 系统 Prompt + 工具描述）：

方案 日输入 token 成本（Sonnet $3/M） 节省
无缓存 5万 × 8000 × 3/M=3/M =3/M=1,200 基线
80% 缓存命中 1万 × 8000 × 3/M+4万×8000×3/M + 4万 × 8000 ×3/M+4万×8000×0.3/M = $336 72%
95% 缓存命中 0.25万 × 8000 × 3/M+4.75万×8000×3/M + 4.75万 × 8000 ×3/M+4.75万×8000×0.3/M = $174 86%

层级二：语义缓存

语义缓存解决的问题：不同措辞但相同意图的请求，不需要每次都重新调用 LLM。

工作原理

  1. 将用户请求编码为向量（embedding）
  2. 在缓存中搜索余弦相似度 > 阈值的历史请求
  3. 命中则直接返回历史响应
  4. 未命中则正常调用 LLM，将结果存入缓存
import numpy as np
from openai import OpenAI

SIMILARITY_THRESHOLD = 0.95  # 高阈值保证准确性
CACHE_TTL_SECONDS = 3600     # 1 小时过期

class SemanticCache:
    def __init__(self):
        self.embeddings = []   # 向量存储
        self.responses = []    # 对应响应
        self.timestamps = []   # 时间戳

    def get(self, query: str) -> str | None:
        query_vec = get_embedding(query)

        for i, cached_vec in enumerate(self.embeddings):
            if self._is_expired(i):
                continue
            similarity = np.dot(query_vec, cached_vec)
            if similarity >= SIMILARITY_THRESHOLD:
                return self.responses[i]

        return None  # 未命中

    def put(self, query: str, response: str):
        self.embeddings.append(get_embedding(query))
        self.responses.append(response)
        self.timestamps.append(time.time())

适用场景与命中率

场景 典型命中率 适用性
FAQ / 客服问答 40-60% 极佳——高重复率
文档摘要 20-40% 好——同文档多次被问
代码生成 5-15% 一般——每次需求差异大
创意写作 <5% 差——几乎无重复
数据分析查询 15-30% 中——相似查询模式

语义缓存的风险与缓解

风险一：过期答案

缓存的响应可能基于过时信息。缓解：设置合理的 TTL，对时效性强的场景（如"今天的天气"）禁用缓存。

风险二：相似但不同的请求

相似度 0.95 的两个请求可能需要不同回答（如"Python 排序"vs"Java 排序"）。缓解：将模型/任务类型作为缓存键的一部分，不仅看语义相似度。

风险三：缓存污染

低质量响应被缓存后反复返回。缓解：只缓存经过质量验证的响应，或对缓存响应做用户反馈追踪。

层级三：请求去重

幂等请求合并

在高并发场景下，同一秒内可能有多个相同请求到达。请求去重在网关层合并这些重复调用：

const inflightRequests = new Map<string, Promise<Response>>();

async function deduplicatedCall(key: string, callFn: () => Promise<Response>) {
  if (inflightRequests.has(key)) {
    return inflightRequests.get(key)!; // 复用进行中的请求
  }

  const promise = callFn();
  inflightRequests.set(key, promise);

  try {
    return await promise;
  } finally {
    inflightRequests.delete(key);
  }
}

批量内去重

批处理场景中，一批请求内可能存在重复项。去重后再发送：

场景 去重率 方法
产品描述生成（同 SKU 多次触发） 20-40% 精确 key 匹配
用户意图分类（相同消息重发） 10-20% 精确 + 规范化
RAG 答案生成（相同文档段落） 15-30% content hash

缓存架构设计

缓存键设计

有效的缓存键需要平衡命中率和准确性：

interface CacheKey {
  model: string; // 不同模型输出不同
  system_prompt_hash: string; // 系统 Prompt 变更时失效
  user_content: string; // 用户输入
  temperature: number; // 不同温度输出不同
  response_format?: string; // 格式要求影响输出
}

缓存层级组合

生产系统通常组合多层缓存，按优先级查询：

层级 存储 TTL 命中率 成本节省
L1 请求去重 进程内存 请求进行中 5-10% 100%
L2 精确缓存 Redis 1-24h 10-30% 100%
L3 语义缓存 Vector DB 1-72h 20-40% ~100%
L4 Prompt Cache 厂商内建 5min-1h 60-90% 70-90%

综合收益估算

一个月 50 万次调用的系统（Sonnet 3/Minput,3/M input,3/Minput,15/M output，平均 6000 input + 500 output tokens）：

缓存层 命中率 月节省金额
精确缓存 15% $1,580
语义缓存 额外 10% $1,053
Prompt Cache 对剩余请求 80% 命中 $5,400
总计 $8,033/月（约 76%）

缓存策略选择决策树

选择缓存策略的核心考量：

  1. 请求重复率高吗？（>20%）→ 优先精确缓存 + 语义缓存
  2. 系统 Prompt 长吗？（>2000 tokens）→ 优先 Prompt Cache
  3. 输出对时效性敏感吗？ → 缩短 TTL 或跳过缓存
  4. 输出需要个性化吗？ → 缓存键需包含用户上下文
  5. 调用频率高吗？（>1000/h）→ Prompt Cache 命中率天然高

小结

缓存策略的核心决策：高重复率场景优先精确缓存和语义缓存（FAQ、文档问答）；长系统 Prompt 场景必开 Prompt Cache（零代码改动或极少改动即可获得 70-90% 输入折扣）；高并发场景加请求去重。三层缓存互补而非互斥——组合使用可实现 76% 以上的总成本节省。注意缓存的风险管理：TTL 设置、过期答案、缓存污染都需要持续监控。
