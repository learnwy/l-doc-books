批处理与异步模式

核心概念

批处理 API 用等待时间换取 50% 价格折扣——不改模型、不改 Prompt、不损质量，仅放弃实时响应。厂商在 GPU 空闲时段处理批量请求，用户以半价获得相同结果。典型的非实时场景（评估、标注、审核、报告生成）占多数 AI 系统调用量的 30-50%，全部迁移到 Batch API 即可节省整体 15-25%。

时间换成本：50% 折扣的获取方式

批处理 API 是所有成本优化策略中最简单的"免费午餐"——无需改变模型、无需改变 Prompt、无需改变输出质量，仅仅是放弃实时响应的要求，就能获得 50% 的价格折扣。

这个折扣的技术基础：GPU 集群在工作日白天满负荷运行以应对实时请求，而夜间和周末则有大量闲置算力。批处理请求填充了这些低谷时段——厂商用折扣价卖掉了原本闲置的算力，用户用等待时间换取一半的成本。

OpenAI Batch API 使用

import json
from openai import OpenAI

client = OpenAI()

# 1. 准备批量请求文件（JSONL 格式）
requests = []
for i, item in enumerate(data_items):
    requests.append({
        "custom_id": f"req-{i}",
        "method": "POST",
        "url": "/v1/chat/completions",
        "body": {
            "model": "gpt-5-mini",
            "messages": [
                {"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": item["text"]}
            ],
            "max_tokens": 500
        }
    })

# 写入 JSONL 文件
with open("batch_input.jsonl", "w") as f:
    for req in requests:
        f.write(json.dumps(req) + "\n")

# 2. 上传文件
batch_file = client.files.create(
    file=open("batch_input.jsonl", "rb"),
    purpose="batch"
)

# 3. 创建批处理任务
batch = client.batches.create(
    input_file_id=batch_file.id,
    endpoint="/v1/chat/completions",
    completion_window="24h"
)

# 4. 轮询状态 / Webhook 通知
status = client.batches.retrieve(batch.id)
# status.status: "validating" → "in_progress" → "completed"

适合批处理的场景识别

核心判据：用户是否在等这个结果？ 如果不是，就应该走批处理。

场景 实时必要性 批处理适用性 预期量级
聊天回复 必须实时 不适用 —
邮件分类 分钟级可接受 适用 千-万/天
内容审核 秒级到分钟级 部分适用 万-十万/天
数据标注 无实时要求 极佳 千-万/批
模型评估 无实时要求 极佳 百-千/批
报告生成 小时级可接受 极佳 十-百/天
文档摘要 分钟级可接受 适用 百-千/天
SEO 内容生成 无实时要求 极佳 百-万/批
翻译任务 分钟到小时 适用 百-千/天

经验法则：一个典型的 AI 产品中，30-50% 的 LLM 调用可以延迟处理而不影响用户体验。

异步架构模式

队列化架构

将 LLM 调用从同步请求-响应模式改为异步队列模式：

interface LLMJob {
  id: string;
  priority: 'realtime' | 'high' | 'normal' | 'batch';
  payload: {
    model: string;
    messages: Message[];
    max_tokens: number;
  };
  callback_url?: string;
  created_at: number;
  deadline: number; // 最晚完成时间
}

优先级分层调度：

优先级 SLA 处理方式 成本
realtime <3s 同步 API，即时返回 全价
high <5min 内部队列，快速消费 全价
normal <1h 内部队列，批量消费 全价或小折扣
batch <24h Batch API 50% 折扣

回调与通知模式

批处理完成后的结果获取方式：

  1. 轮询模式：定时查询批次状态（简单但浪费）
  2. Webhook 回调：任务完成时主动通知（推荐）
  3. 事件流模式：通过消息队列（Kafka/SQS）消费结果
# Webhook 回调示例
@app.post("/webhook/batch-complete")
async def handle_batch_complete(payload: BatchResult):
    batch_id = payload.batch_id
    results = await download_results(payload.output_file_id)

    for result in results:
        await process_result(result.custom_id, result.response)
        await notify_requester(result.custom_id)

混合调度策略

实际生产系统通常需要混合实时和批处理——同一个功能在不同场景下选择不同路径：

async def smart_dispatch(request: LLMRequest) -> LLMResponse:
    if request.requires_realtime:
        return await sync_call(request)

    if request.deadline < now() + timedelta(hours=1):
        # 截止时间紧，走同步但用便宜模型
        return await sync_call(request, model_override="gpt-5-mini")

    if request.deadline > now() + timedelta(hours=24):
        # 时间充裕，走 Batch API
        return await enqueue_batch(request)

    # 中间地带：走内部队列，聚合后发送
    return await enqueue_internal(request)

批次聚合优化

不是每个请求单独走 Batch API，而是聚合后统一提交：

  • 时间窗口聚合：每 5 分钟收集一批，统一提交
  • 数量阈值聚合：累计 100 个请求后统一提交
  • 混合策略：先到先聚，min(5分钟, 100个) 触发提交

成本对比案例

一个内容审核系统，日均 10 万条内容需要 AI 审核：

方案 模型 单次成本 日成本 月成本
全量同步（旗舰） Sonnet $0.006 $600 $18,000
全量同步（轻量） Haiku $0.002 $200 $6,000
全量 Batch（轻量） Haiku Batch $0.001 $100 $3,000
混合（10% 实时 + 90% Batch） Haiku $0.0012 $120 $3,600

从全量同步旗舰切换到混合 Batch 轻量模型：月节省 $14,400（80%）。

批处理的限制与权衡

限制 影响 缓解措施
24h 返回时限不可控 无法承诺精确完成时间 预留缓冲时间
无流式输出 无法做实时进度展示 批量任务加进度条
错误处理延迟 格式错误要等批次完成才知道 小批量试跑验证
请求无法取消 提交后无法撤回单个请求 设计幂等处理逻辑
不支持工具调用 Agent 场景不适用 仅用于单轮无工具场景

小结

批处理是最简单的"免费午餐"——仅放弃实时性就获得 50% 折扣。识别非实时场景（评估、标注、审核、内容生成）并迁移到 Batch API 是第一步；队列化架构和优先级分层让实时与批处理在同一系统中共存；混合调度策略确保紧急请求仍然实时、常规请求享受折扣。限制主要在于 24h 不可控时限和不支持工具调用。
