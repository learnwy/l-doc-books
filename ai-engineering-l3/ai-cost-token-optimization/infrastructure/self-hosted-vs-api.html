自建推理 vs API 采购

核心概念

自建推理集群还是使用云 API 是总拥有成本（TCO）问题——不是技术偏好。关键变量：月支出规模（>$50K 时自建开始有利）、流量稳定性（波动大则 API 弹性更优）、GPU 利用率（<50% 时自建不划算）、团队能力（需要 ML infra 团队）。多数大规模部署最终走向混合架构：基线流量自建（锁定低单价）+ 峰值溢出到 API（按需弹性）。

TCO 视角的选型框架

自建推理集群还是使用云 API？这不是技术偏好问题，而是**总拥有成本（TCO）**问题。答案取决于：调用量、流量稳定性、定制需求、团队能力和风险偏好。

API 采购的真实成本

显性成本

按量付费的 token 费用。以一个月 1000 万次调用的系统为例（平均 4000 input + 600 output tokens）：

模型 月 token 成本 年成本

隐性成本与风险

隐性因素 影响 量化估算
厂商涨价风险 2026 年初多家涨价 460%+ 难预测
延迟不可控 高峰期延迟翻倍 SLA 违约损失
数据隐私合规 数据经过第三方 合规审计成本
厂商锁定 切换成本高（Prompt 适配） 3-6 个月迁移成本

API 的不可替代优势

  • 零运维负担：不需要 GPU 集群管理、模型更新、故障恢复
  • 弹性无限：流量从 100 到 100 万无需容量规划
  • 最新模型：第一时间使用最强模型，无需自己部署
  • 按量付费：用多少付多少，无前期投资

自建的独特优势

  • 单位成本锁定：硬件摊销后边际成本极低
  • 数据隐私：数据不离开自有基础设施
  • 模型定制：可以微调、量化、蒸馏定制模型
  • 无限流量：不受 API 配额限制
  • 低延迟：模型就在本地，网络延迟最小

盈亏平衡分析

简化模型

假设自建一个 8xH100 单节点，运行开源前沿 MoE 的量化版本（以 DeepSeek-V3/R1 级为例：671B 总参 / ~37B 激活；原生 FP8 权重约 700 GB 需跨机部署，社区动态低比特量化版权重可压至 ~130-340 GB、落入单节点——参见 Unsloth 动态量化方案，2025-02）：

固定月成本：

  • GPU 租赁：8 × 2,500=2,500 =2,500=20,000
  • 人力分摊：$10,000
  • 电力/网络：$4,000
  • 总计：$34,000/月

吞吐能力（FP8/INT4 + continuous batching，聚合输出保守估计）：~1,500 tokens/s ≈ 月输出 39 亿 tokens

等效 API 成本（沿用 1:0.15 的输入输出比口径，月输入 ≈ 输出 × 6.7 ≈ 260 亿 tokens）：

  • 对比旗舰中坚 API（Claude Sonnet 3/Minput+3/M input +3/Minput+15/M output）：约 $136,000/月
  • 对比同能力的开源系低价 API（DeepSeek 官方定价口径，输入 ~¥2/M、输出 ~¥8/M）：约 $12,000/月

结论：只对照旗舰中坚 API 时，月用量超过数亿 token 且流量稳定即可显著低于 API——单位硬件吞吐较上一代 dense 70B 算例大幅提升，盈亏平衡点更低了。但 2026 年真正的对照基线是「同能力的最低价 API」：开源前沿模型本身就以低一个数量级的单价通过 API 提供，纯单价维度自建很难胜出。因此自建理由的优先级排序变为：数据隐私/合规 > 极限批量下的单价锁定 > 低延迟与可控性 > 定制微调——「省钱」本身不再是充分条件。

但这假设了：

  1. 开源模型质量满足需求——质量锚点已升级：开源前沿从「对标闭源轻量级」（Llama 3.1 70B ≈ GPT-4o-mini 一档，2024 年口径）进化到「对标闭源中坚层」。可核验锚点：DeepSeek-R1 论文报告其数学/代码推理与 OpenAI-o1 同档（arXiv:2501.12948，2025-01）；Kimi K2（2025-07 开放权重）、GLM-4.5（2025-07）、Qwen3-235B-A22B（2025-04，Apache 2.0）在 agentic 与编码基准上普遍被认为接近 GPT-5-mini / Claude Sonnet 一档（社区基准观察值，非严格等价）。评估问题从「轻量模型够不够用」变成「中坚层够不够用」
  2. 团队有能力维护推理集群
  3. 利用率保持 > 60%

GPU 利用率 等效 token 单价 对比 API

低利用率（<50%）时自建不划算——流量不稳定的场景应该优先使用 API。

开源自建的三档选型地图（2026）

自建不再只有「dense 70B」一种答案。按质量-成本梯度，2026 年的开源自建选型大致分三档：

graph LR
    A[开源自建三档] --> B[前沿 MoE 档<br/>DeepSeek-V3/R1 / Kimi K2<br/>Qwen3-235B / GLM-4.5<br/>8xH100 或 H200 节点起步]
    A --> C[中坚单卡档<br/>gpt-oss-120b MXFP4 / Qwen3-32B<br/>单张 80GB 卡或 24GB 入门卡]
    A --> D[小模型蒸馏档<br/>Qwen3-8B / gpt-oss-20b<br/>消费级卡与边缘设备]

    B --> E[约等于闭源中坚层<br/>GPT-5-mini / Claude Sonnet 一档]
    C --> F[官方模型卡称核心推理<br/>接近 o4-mini 一档]
    D --> G[分类/抽取/路由等窄任务]

选型含义：先用中坚单卡档覆盖大多数流量——硬件投入最小、运维最简单；当中坚档质量不足时，升级路径是「上前沿 MoE 档」而非「采购更强闭源 API」，这正是混合架构中基线层的候选池。各档与闭源模型的对应关系为社区基准与技术报告的观察值（如 gpt-oss-120b 官方模型卡称其核心推理基准接近 o4-mini），非严格等价声明，落地前应在自有任务集上复测。

混合架构：最佳实践

多数大规模部署最终走向混合架构——兼取两者优势：

流量层 处理方式 成本特征
基线流量（P50 以下） 自建集群 固定成本，低单价
正常波动（P50-P90） 自建 + 弹性扩展 混合成本
峰值流量（P90 以上） 溢出到 API 按量付费，高弹性
特殊需求（最强模型） API only 无法自建的能力

路由策略

async def hybrid_route(request: InferenceRequest) -> Response:
    # 需要旗舰能力 → API
    if request.requires_frontier_model:
        return await api_call(request, model="claude-opus-4-6")

    # 自建集群有余量 → 自建
    if self_hosted_cluster.available_capacity() > 0.2:
        return await self_hosted_call(request)

    # 自建满载 → 溢出到 API（用便宜模型）
    return await api_call(request, model="claude-haiku-4-5")

决策清单

在做自建 vs API 决策时，逐项评估：

评估维度 倾向 API 倾向自建
月支出 < $20K > $50K
流量模式 高波动（>3x 峰谷比） 稳定（<2x 峰谷比）
模型需求 需要最新旗舰模型 开源模型质量足够
数据敏感度 一般商业数据 高敏感（医疗/金融/政务）
团队能力 无 ML infra 团队 有 GPU/ML 运维经验
定制需求 标准 API 满足 需要微调/量化定制
延迟要求 秒级可接受 毫秒级要求
合规要求 标准合规 数据不出境/不出司

保守建议：除非至少满足 4 项"倾向自建"条件，否则 API + 优化策略（路由/缓存/批处理）通常是更优选择。自建的机会成本（工程师时间花在基础设施而非产品）经常被低估。

小结

自建 vs API 的决策核心是 TCO 对比和利用率。月支出 < 20K时API优先；>20K 时 API 优先；>20K时API优先；>50K 且流量稳定时评估自建；利用率 < 50% 时自建不划算。多数团队低估了自建的隐性成本（人力、运维、机会成本），高估了 API 的长期风险。混合架构（基线自建 + 峰值 API）是大规模部署的标准答案。保守建议：除非满足 4 项以上"倾向自建"条件，否则 API + 优化策略通常更优。2026 年的补充判断：开源前沿已同时以低价 API 与开放权重两种形态供给，自建的核心动机从「省单价」转向隐私合规、可控性与定制。
