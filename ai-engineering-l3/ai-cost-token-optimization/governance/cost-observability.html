成本可观测性

核心概念

成本可观测性通过计量中间件为每次 LLM API 调用打上多维标签（项目/用户/功能/模型/时间），实现"钱花在哪了"的精确归因。核心能力：实时仪表板展示成本分布和趋势、多维归因回答哪个模块最烧钱、异常检测发现突增和循环 bug、缓存效果追踪验证优化成果。没有可观测性，所有优化都是盲人摸象。

你无法优化你没有计量的东西

成本可观测性是所有优化的前提。没有精确的计量数据，路由策略在盲飞、预算分配无依据、ROI 无法量化。多数团队的第一个问题不是"怎么省钱"，而是"钱花在哪了"——他们甚至不知道哪个功能模块贡献了最多的 LLM 支出。

实现成本可观测性的核心是一个计量中间件——在每次 LLM API 调用的进出路径上，采集、归因、聚合、告警。

graph LR
    A[业务代码] --> B[计量中间件]
    B --> C[LLM API]
    C --> D[响应]
    D --> B
    B --> E[计量数据存储]

    E --> F[实时仪表板]
    E --> G[成本归因报表]
    E --> H[异常告警]
    E --> I[预算追踪]

    B -.->|采集| J[model / tokens / latency<br/>user / project / feature<br/>timestamp / cost]

计量中间件设计

采集的核心字段

每次 LLM 调用需要采集的最小数据集：

字段 类型 用途
timestamp datetime 时序分析
model string 模型维度归因
input_tokens int 输入成本计算
output_tokens int 输出成本计算
cached_tokens int 缓存效果追踪
thinking_tokens int Reasoning 模型专项
total_cost float 计算后的总成本
latency_ms int 性能监控
project string 项目维度归因
feature string 功能模块维度归因
user_id string 用户维度归因
request_type string 请求类型（路由依据）
success bool 失败/重试追踪
cache_hit bool 缓存命中追踪

实现方式

计量中间件有三种实现路径：

方式 优势 劣势 适用规模
SDK 包装器 侵入最小、最快实施 需要所有调用点接入 小团队/起步
API 网关层 统一拦截、无需改业务代码 需要额外基础设施 中大规模
厂商 Dashboard 零开发成本 缺少业务维度归因 仅基础统计

SDK 包装器示例：

interface TokenUsageRecord {
  timestamp: number;
  model: string;
  input_tokens: number;
  output_tokens: number;
  cached_tokens: number;
  total_cost_usd: number;
  latency_ms: number;
  project: string;
  feature: string;
  user_id?: string;
  success: boolean;
}

class CostTracker {
  private records: TokenUsageRecord[] = [];

  async trackedCall(
    params: ChatCompletionParams,
    metadata: { project: string; feature: string; user_id?: string },
  ): Promise<ChatCompletion> {
    const start = Date.now();

    try {
      const response = await openai.chat.completions.create(params);
      const usage = response.usage!;

      this.records.push({
        timestamp: start,
        model: params.model,
        input_tokens: usage.prompt_tokens,
        output_tokens: usage.completion_tokens,
        cached_tokens: usage.prompt_tokens_details?.cached_tokens ?? 0,
        total_cost_usd: this.calculateCost(params.model, usage),
        latency_ms: Date.now() - start,
        ...metadata,
        success: true,
      });

      return response;
    } catch (error) {
      this.records.push({
        timestamp: start,
        model: params.model,
        input_tokens: 0,
        output_tokens: 0,
        cached_tokens: 0,
        total_cost_usd: 0,
        latency_ms: Date.now() - start,
        ...metadata,
        success: false,
      });
      throw error;
    }
  }
}

多维成本归因

维度一：按项目/功能模块

回答"哪个产品功能最烧钱"：

功能模块 日均调用 日均成本 单次均成本 趋势
智能客服 50,000 $300 $0.006 稳定
内容生成 8,000 $480 $0.060 ↑ 20%/周
代码助手 3,000 $180 $0.060 稳定
数据标注 20,000 $40 $0.002 ↓ batch 化
Agent 任务 500 $250 $0.500 ↑ 50%/周

关键发现：Agent 任务调用量仅占 0.6%，但成本占比 19%——单次成本是客服的 83 倍。

维度二：按模型

回答"模型选择是否合理"：

模型 调用占比 成本占比 成本/调用
GPT-5.2 5% 45% $0.112
Claude Sonnet 20% 30% $0.019
GPT-5-mini 50% 15% $0.004
GPT-5 Nano 25% 10% $0.005

如果 GPT-5.2 的调用中有 50% 可以降级到 Sonnet/Mini——立即省下 22% 总成本。

维度三：按用户/租户

回答"谁在花钱"（SaaS 场景尤其重要）：

  • Top 1% 用户贡献 30% 成本（幂律分布）
  • 检测异常用户：单用户日花费突增 > 3 倍标准差 → 告警

维度四：按时间

回答"什么时候花钱最多"：

  • 工作日 vs 周末模式差异
  • 峰值时段识别（用于 batch 化迁移决策）
  • 突增检测（可能是循环 bug 或攻击）

异常检测与告警

需要告警的模式

异常类型 检测方法 告警阈值建议
成本突增 小时成本 > 7 天均值 × 3 3x
单请求异常 单次成本 > P99 × 5 5x
错误率飙升 5min 错误率 > 10% 10%
缓存命中率骤降 命中率 < 历史均值 - 2σ 2σ
Agent 循环 同一 session 调用 > N 次 30 次
Token 膨胀 平均输入 token > 历史 × 2 2x

Agent 循环检测

2025 年底的 $47,000 事故凸显了循环检测的重要性：

MAX_CALLS_PER_SESSION = 50
COST_CEILING_PER_SESSION = 5.0  # $5

class AgentCircuitBreaker:
    def __init__(self):
        self.session_calls: dict[str, int] = {}
        self.session_costs: dict[str, float] = {}

    def check(self, session_id: str, call_cost: float) -> bool:
        self.session_calls[session_id] = self.session_calls.get(session_id, 0) + 1
        self.session_costs[session_id] = self.session_costs.get(session_id, 0) + call_cost

        if self.session_calls[session_id] > MAX_CALLS_PER_SESSION:
            raise BudgetExceededError(f"Session {session_id}: too many calls")

        if self.session_costs[session_id] > COST_CEILING_PER_SESSION:
            raise BudgetExceededError(f"Session {session_id}: cost ceiling hit")

        return True

仪表板核心指标

一个最小可用的 LLM 成本仪表板需要展示：

  1. 总成本趋势：日/周/月成本曲线
  2. 模型分布：各模型的调用量和成本占比
  3. 功能归因：Top 5 成本功能模块
  4. 效率指标：缓存命中率、批处理比例、路由分布
  5. 异常面板：最近 24h 的成本异常事件

从可观测到可行动

可观测性的最终目标不是"看到数据"，而是驱动决策：

观测到的现象 对应行动
某功能成本占比 > 30% 优先对该功能做路由/缓存优化
旗舰模型调用中 60% 是简单请求 部署路由系统
缓存命中率 < 20% 审查缓存键设计、延长 TTL
Agent 平均步骤 > 15 优化 Agent 架构、设置步骤上限
夜间批量任务走同步 API 迁移到 Batch API
单用户成本异常高 检查是否有 bug/滥用

小结

成本可观测性是所有治理能力的基础。第一步是接入计量中间件（SDK 包装器最快落地），采集 model/tokens/cost/project/feature/user 多维数据；第二步是建立仪表板展示成本趋势和归因；第三步是配置异常告警（突增、循环、膨胀）。从"看清"到"行动"的转化是可观测性的最终价值——每个观测到的异常都应该有对应的优化行动。
