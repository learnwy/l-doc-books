成本架构设计

核心概念

LLM 推理成本是沿调用链路逐层累积的系统问题——路由决策（选模型）、上下文构建（组输入）、推理计算（调 API）、输出验证（判成败）、Agent 循环（多步骤）、跨系统 Fan-out（多调用）六个节点各有独立的成本贡献和干预杠杆。用系统视角识别瓶颈节点，才能把有限的优化资源投向最高 ROI 的位置。

成本累积的系统视角

LLM 推理成本不是一个"点"问题——它是沿着整条调用链路逐层累积的系统问题。每个架构层都有独立的成本贡献者和独立的优化杠杆。用系统视角看成本，才能识别最高 ROI 的干预点，而不是东一榔头西一棒子地随机优化。

graph TD
    A[用户请求] --> B[接入层<br/>鉴权/限流/路由决策]

六个成本累积节点

节点 1：路由决策——选错模型的代价

路由决策是成本架构中最早也是杠杆最大的节点。它决定了后续所有 token 的单价。一旦请求被路由到旗舰模型，无论输入多么简单，每个 token 都按旗舰价格计费。

路由策略 成本影响 适用条件
全量旗舰（默认状态） 基线 100% 原型期/验证期
静态规则路由 节省 30-50% 任务类型清晰可分
分类器路由 节省 40-70% 有历史数据训练路由器
Cascade 级联 节省 50-85% 可接受轻微延迟增加

路由器本身的成本通常可忽略：用 Nano 级模型做分类，每次调用成本不到 $0.0001。

节点 2：上下文构建——不可见的 Token 膨胀

每次 API 调用的输入 token 由四部分组成：

Tinput=Tsystem+Thistory+Trag+TuserT_{input} = T_{system} + T_{history} + T_{rag} + T_{user}Tinput​=Tsystem​+Thistory​+Trag​+Tuser​

其中系统 Prompt 和 RAG 上下文往往是静默膨胀的来源：

  • 系统 Prompt：生产系统的 system prompt 经常在迭代中从 500 token 膨胀到 4000-8000 token（加安全规则、加格式要求、加示例），没有人定期审计
  • 对话历史：默认发送全量历史，第 50 轮对话的 history 部分可达 15000-30000 token
  • RAG 注入：检索 top-5 chunks，每个 500 token = 2500 token，且检索质量不保证每个 chunk 都相关

审计方法：为 API 调用加一层日志，记录每部分的 token 占比：

interface TokenBreakdown {
  system_prompt: number;
  conversation_history: number;
  rag_context: number;
  user_message: number;
  total_input: number;
  output: number;
}

典型发现：system_prompt 占 40-60%，history 占 20-40%，用户实际问题仅占 5-10%。

节点 3：推理计算——输入输出的不对称

这是成本实际发生的核心节点。两个关键不对称：

  1. 定价不对称：输出 token 单价是输入的 3-8 倍
  2. 控制力不对称：输入完全由开发者控制，输出受模型行为影响

优化策略在这个节点分为两个方向：

  • 减少输入：压缩 Prompt、管理 History、精选 RAG chunks
  • 控制输出：max_tokens 限制、结构化格式约束、stop sequences、指令约束

节点 4：输出验证——失败重试的隐性翻倍

当模型输出不符合格式要求（JSON 解析失败、缺少必填字段、内容不合规），常见做法是重试。每次重试意味着完整重新计费——包括那些完全相同的输入 token。

重试成本=单次成本×(1+rretry×nretry)\text{重试成本} = \text{单次成本} \times (1 + r_{retry} \times n_{retry})重试成本=单次成本×(1+rretry​×nretry​)

如果重试率 rretryr_{retry}rretry​ = 15%、平均重试次数 nretryn_{retry}nretry​ = 1.5，则实际成本 = 单次成本 × 1.225（隐性增加 22.5%）。

降低重试的关键不是"改 Prompt 让模型更听话"——而是：

  • 使用 JSON Mode / Structured Output 在模型层面强制格式
  • 对非结构性错误做客户端修复（正则提取、容错解析）而非重发

节点 5：Agent 循环——复合增长的根源

Agent 系统的成本结构与单次调用截然不同。一个典型 10 步 Agent 任务的 token 消耗：

步骤 输入 token（累积） 新输出 token 累积成本（相对首步）
1 8,000 (sys + user) 500 1.0x
2 8,500 (+ tool result) 400 2.1x
3 9,400 600 3.4x
5 12,000 500 6.2x
10 18,000 300 12.8x

每步都重发累积上下文，成本增长接近三角数级别（∑i=1ni\sum_{i=1}^{n} i∑i=1n​i 形态）。这就是为什么一个"看起来只花 $0.14"的 Agent 对话，在规模化部署时月支出可达百万美元级。

节点 6：跨系统调用——隐藏的 Fan-out

微服务架构中，一个用户请求可能触发多个下游 LLM 调用：

  • 意图识别 → 1 次调用
  • RAG 检索后总结 → 1 次调用
  • 结果格式化 → 1 次调用
  • 安全审核 → 1 次调用
  • 对话存储前的摘要 → 1 次调用

一个用户"问了一个问题"，实际产生 5 次 LLM 调用。如果每次都用同一个模型且不做任何缓存共享，成本是直觉预期的 5 倍。

成本架构的分层干预模型

将上述节点映射到可操作的干预层：

干预层 节点 策略 预期收益
路由层 1 难度路由、cascade 40-70%
输入层 2 Prompt 压缩、history 管理、RAG 精选 20-40%
调用层 3 Prompt Cache、Batch API 30-90%
验证层 4 Structured Output、容错解析 10-20%
循环层 5 Token budget、摘要注入、提前终止 30-60%
编排层 6 模型分级、共享缓存、合并调用 20-40%

成本架构设计原则

原则一：成本预算前置化

在系统设计阶段就把 token budget 作为架构约束——类似于延迟 SLA 和内存限制：

interface AgentConfig {
  max_tokens_per_step: number; // 单步输出上限
  max_total_tokens: number; // 任务总 token 预算
  escalation_threshold: number; // 超预算升级阈值
  budget_exceeded_action: 'degrade' | 'terminate' | 'alert';
}

原则二：成本与质量的解耦度量

不要用"省了多少钱"单一维度评估优化效果。正确的评估框架是帕累托前沿：

Optimization Goal=min⁡(Cost)s.t.Quality≥Qthreshold\text{Optimization Goal} = \min(\text{Cost}) \quad \text{s.t.} \quad \text{Quality} \geq Q_{threshold}Optimization Goal=min(Cost)s.t.Quality≥Qthreshold​

质量阈值由业务场景决定，不同场景的容忍度差异可达 10 倍。

原则三：可观测性先于优化

在没有完整的 token 计量和归因之前，任何优化都是盲注。第一步永远是"看清楚"——哪个模块在花钱、哪种请求的 cost/quality 比异常、哪些时段出现了用量突增。

原则四：渐进式降级优于硬切

预算耗尽时的最佳策略不是直接拒绝请求，而是渐进降级：旗舰 → 中端 → 轻量 → 缓存结果 → 静态回退。每一级降级都有明确的质量让步和成本收益。

小结

成本架构的核心认知：成本不是一个点问题而是系统问题，六个节点各有独立杠杆；路由决策是最大单一杠杆（40-70%）；Agent 循环是增长最快的成本源（接近三角数增长）；四条设计原则（预算前置、质量-成本解耦、可观测先行、渐进降级）构成优化的方法论基础。后续三章的所有技术都是对这六个节点的具体干预方案。
