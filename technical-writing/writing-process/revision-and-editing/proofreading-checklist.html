校对清单

核心概念

校对（Proofreading）是写作流程的最后一道质量关卡，关注的是文章表面层面的正确性——标点符号、拼写错误、格式规范、排版一致性和链接有效性。与逐行编辑关注"表达质量"不同，校对关注的是"表达正确性"。它不改变文章说什么，只确保文章说得"干净"。

许多写作者低估了校对的重要性，认为"读者会关注内容而不是格式"。事实恰恰相反——表面错误会严重损害读者对作者专业度的信任。一项研究表明，文章中的拼写和语法错误会使读者对作者的信任度降低 40% 以上。对于技术文章而言，一个代码示例中的拼写错误可能导致读者照搬后运行失败，造成实际的时间损失和挫败感。

中文写作的标点规范
中文标点符号系统与英文有显著差异，而技术文章中经常需要中英文混排，这使得标点错误成为最常见的校对问题之一。


最基本的规则是中文语境使用全角标点，英文语境使用半角标点。全角标点包括：，。！？；：""''（）——……。半角标点包括：,. ! ? ; : " " ' ' ( ) - ... 在中英文混排时，中文句子中的标点必须使用全角形式，即使句中插入了英文单词。例如："使用 React 框架，可以提升开发效率。"——句中的逗号和句号都是全角的。


中英文之间的空格规范也是重要的排版细节。推荐在中文与半角英文/数字之间添加一个半角空格："使用 Node.js 14 以上版本"而非"使用Node.js14以上版本"。但中文与全角标点之间不加空格。


引号的使用是另一个容易出错的点。中文使用弯引号（""和''），而非英文直引号（""和''）。在 Markdown 写作中，许多编辑器默认输出英文直引号，需要手动或通过插件替换为中文弯引号。

Markdown 格式检查
技术文章多使用 Markdown 格式发布，Markdown 有其特定的格式规范需要在校对时检查。


标题层级必须严格递进。H1 只用一次作为文章标题，H2 是主要章节，H3 是子章节，以此类推。不能跳级——从 H2 直接跳到 H4 会导致语义混乱和部分渲染引擎的显示问题。检查方法是提取所有标题行，验证层级的递进关系。


列表格式需要全文统一。无序列表统一使用同一种标记符（推荐 -），有序列表统一使用 1. 开头（让 Markdown 渲染器自动编号）。嵌套列表的缩进必须一致——通常是 2 个或 4 个空格，但全文必须统一。


代码块必须标注语言类型。使用三个反引号围起的代码块应该在开头反引号后标注语言名称（如 javascript、python），这不仅影响语法高亮，也影响屏幕阅读器对代码的处理。行内代码使用单反引号包裹，但不要对非代码内容（如普通英文单词）滥用行内代码格式。


图片和链接需要验证。每张图片的 alt 文本应该描述图片内容（而非"图1"这样无意义的标签）。每个链接需要检查是否可访问——过期的链接（链接腐化）是技术文章的常见问题。


空行和空格的一致性影响渲染效果。标题前后各空一行，段落之间空一行，代码块前后各空一行。不要出现连续两个以上的空行。行尾不应有多余的空格（除非是故意的 Markdown 换行标记）。

校对工作流与工具链
高效的校对不依赖于"仔细地从头读到尾"——这种方式容易因为阅读惯性而跳过错误。相反，应该使用系统化的检查流程和自动化工具来确保覆盖率。


自动化优先是校对工作流的第一原则。能用工具检测的问题绝不用人工检查。拼写检查（VS Code 的 Code Spell Checker、语雀的拼写检查）、Markdown 格式检查（markdownlint）、链接有效性检查（markdown-link-check）、中文排版检查（pangu.js 自动加空格）——这些工具可以在几秒钟内完成人工需要几十分钟的检查工作。


自动化之后的人工检查应该采用"反向阅读法"——从文章的最后一段开始，逐段向前阅读。这种方式打破了正常的阅读流，迫使你关注每个段落的文字本身而非故事线，更容易发现表面错误。


"焦点轮转法"是另一种有效的人工校对策略。每一遍只检查一种类型的问题：第一遍只看标点符号，第二遍只看拼写，第三遍只看格式。这种单焦点的检查比多焦点的通读更彻底——大脑在同一时间只需要匹配一种错误模式。


最终校对应该在发布环境中进行。将文章渲染为最终的发布形式（网页、PDF、或在目标平台的预览模式中），然后在发布环境中做最后一次通读。有些排版问题只在最终渲染中可见——比如表格在窄屏上的显示效果、代码块的横向滚动、以及图片在深色模式下的可见度。


团队校对与交叉检查
即使是最仔细的自我校对也会遗漏错误——"知识诅咒"让你的大脑自动补全缺失的信息、自动纠正错误的表述。团队校对通过引入外部视角来弥补自我校对的盲区。


"交叉校对"是最简单的团队校对模式。两个写作者互相校对对方的文章。交叉校对的规则是：校对者只标注问题，不直接修改——因为直接修改可能改变原作者的表达意图。标注时使用统一的标记系统：[SP] 拼写问题、[GR] 语法问题、[FMT] 格式问题、[FACT] 事实存疑、[CLR] 表述不清。


"专项校对员"模式适合大型写作项目。团队中指定一个人专门负责格式一致性，另一个人专门负责技术准确性，再一个人专门负责语言流畅度。每个人只需要在自己擅长的维度上投入注意力，校对质量远高于每个人都"什么都看一点"。


对于技术文章，"代码校对"应该被视为一个独立的环节。代码示例中的错误比文字错误更具破坏性——它们会导致读者复制粘贴后运行失败。所有代码示例都应该在目标环境中实际运行验证，而不是仅靠视觉检查。
