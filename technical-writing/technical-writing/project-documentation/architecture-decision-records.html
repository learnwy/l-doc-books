架构决策记录 (ADR)

什么是 ADR

架构决策记录（Architecture Decision Record）是一种轻量级文档，用于记录项目中重要的架构决策及其背景。ADR 让团队成员理解"为什么这样做"，避免未来重复讨论已决定的问题。

ADR 的核心价值

价值 说明
决策追溯 记录决策的上下文和理由，便于回顾
知识传承 新成员可以快速了解架构演进历程
减少争论 已记录的决策不需要反复讨论
变更管理 后续推翻决策时，能清晰看到原始考量

ADR 的真正价值往往在撰写数月甚至数年后才显现。当团队成员轮换、原始决策者已经离开时，新成员面对一个看起来"奇怪"的技术选型，如果有 ADR 可查，就能理解当时的约束条件和权衡过程，而不是草率地推翻前人的决策。

什么时候需要写 ADR

触发条件

场景 示例
技术选型 选择 PostgreSQL 而非 MongoDB 作为主数据库
架构模式 采用微服务架构而非单体架构
接口设计 API 使用 REST 而非 GraphQL
基础设施 使用 Kubernetes 而非 ECS 部署
编码约定 错误处理统一使用 Result 类型
第三方依赖 选择 Zod 而非 Joi 做数据校验

判断标准

满足以下任一条件，就应该写 ADR：

  1. 该决策影响系统整体结构或开发流程
  2. 团队成员之间存在不同意见需要对齐
  3. 该决策一旦做出，变更成本较高
  4. 未来新成员可能会质疑这个选择

反过来，不需要写 ADR 的情况包括：变量命名风格这类小事（用 linter 规则代替）、团队内无争议的共识、可以轻松撤销的决策。ADR 的目标是记录"重要且不可逆"的决策，不要让 ADR 变成另一种形式的会议纪要。

ADR 标准格式

核心字段

字段 说明 必填
标题 简明描述决策内容 是
状态 决策的当前状态 是
上下文 决策的背景和约束条件 是
决策 具体做出的决策内容 是
后果 决策带来的正面和负面影响 是
日期 决策日期 建议
参与者 参与决策的人员 可选

状态定义

状态 含义
提议中 (Proposed) 正在讨论，尚未做出最终决策
已接受 (Accepted) 团队已达成一致，决策生效
已废弃 (Deprecated) 决策不再适用，但保留历史记录
已取代 (Superseded) 被新的 ADR 取代，标注替代 ADR 编号

状态变更应该在 ADR 文件顶部清晰标注。当一个 ADR 被取代时，在原 ADR 中添加"已被 ADR-XXXX 取代"的说明，在新 ADR 中添加"取代 ADR-YYYY"的引用，形成完整的决策链。

ADR 编号与管理

编号规则

  • 使用递增整数编号：ADR-0001、ADR-0002
  • 编号一旦分配不可复用，即使 ADR 被废弃
  • 文件名格式：adr-0001-use-postgresql.md

目录结构

docs/
└── adr/
    ├── README.md
    ├── adr-0001-use-postgresql.md
    ├── adr-0002-adopt-rest-api.md
    ├── adr-0003-monorepo-structure.md
    └── adr-0004-use-kubernetes.md

自动化管理

对于频繁撰写 ADR 的团队，可以使用命令行工具简化流程。adr-tools（Bash 脚本集）和 log4brains（带有 Web 界面）是两个常用的开源工具。它们可以自动创建编号、生成目录索引、渲染为可浏览的网页。

轻量级 ADR 模板

# ADR-0001: 使用 PostgreSQL 作为主数据库

## 状态

已接受（2024-06-15）

## 上下文

我们的应用需要一个关系型数据库来存储用户数据和业务数据。团队需要在 PostgreSQL 和 MySQL 之间做出选择。主要考量因素：JSON 支持、扩展性、团队经验、社区生态。

## 决策

我们决定使用 PostgreSQL 作为主数据库。

理由：

- 原生 JSONB 支持，满足半结构化数据的存储需求
- 丰富的索引类型（GIN、GiST）提升查询性能
- 团队中 3/5 的成员有 PostgreSQL 使用经验
- 云厂商均提供托管 PostgreSQL 服务

## 后果

### 正面

- JSONB 类型减少了额外 NoSQL 数据库的引入
- 强类型约束和事务支持保证数据一致性

### 负面

- 水平扩展能力弱于 NoSQL 方案
- 需要团队成员学习 PostgreSQL 特有的高级功能

ADR 最佳实践

写作原则

原则 说明
简洁明了 每个 ADR 控制在 1-2 页，聚焦一个决策
记录备选方案 说明考虑过但最终放弃的方案及原因
客观中立 陈述事实和分析，避免主观情绪表达
及时记录 决策做出后尽快记录，避免事后遗忘细节

常见误区

误区 正确做法
只记录最终决策不写备选方案 备选方案和放弃理由同样重要
上下文部分过于简略 详细描述约束条件，未来读者需要这些
决策后不更新状态 状态变更是 ADR 生命周期的一部分
试图用 ADR 记录所有决策 只记录架构级别的重要决策

团队协作流程

  1. 发起者创建 ADR 草稿，状态为"提议中"
  2. 在代码评审或架构评审会议中讨论
  3. 团队达成一致后，状态改为"已接受"
  4. ADR 合入主分支，成为项目历史的一部分
  5. 后续如需修改，创建新 ADR 并标注取代关系

ADR 的评审过程本身就是一种有价值的团队对齐活动。当所有人都参与了决策的讨论和记录，执行阶段的分歧就会减少。对于远程团队，ADR 的异步评审流程比同步会议更高效——成员可以在自己的时间深思熟虑后给出反馈，而不是在会议中仓促表态。
