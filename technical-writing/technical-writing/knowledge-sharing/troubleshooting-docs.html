故障排查文档

故障排查文档的作用

故障排查文档帮助工程师在系统出现问题时快速定位根因并恢复服务。好的排查文档能将 MTTR（平均恢复时间）缩短 50% 以上。

文档类型 用途 使用时机
症状索引 按报错信息或现象查找 收到告警或用户反馈时
决策树 按排查路径逐步缩小范围 复杂问题，原因不明确时
已知问题列表 已确认的 Bug 和临时规避方案 快速确认是否为已知问题
Runbook 标准化的应急处理流程 线上事故应急响应时

症状-原因-方案模式

这是最基本也是最高效的排查文档结构。每条记录包含三要素：

结构模板

### 症状

用户报告 / 监控告警的具体现象描述。

### 可能原因

| 原因   | 概率 | 验证方法      |
| ------ | ---- | ------------- |
| 原因 A | 高   | 检查 XXX 日志 |
| 原因 B | 中   | 执行 XXX 命令 |
| 原因 C | 低   | 查看 XXX 配置 |

### 解决方案

针对每个原因的具体修复步骤。

实际示例

### 症状

API 响应时间从 200ms 飙升到 5s 以上，HTTP 502 错误率 > 10%。

### 可能原因

| 原因                | 概率 | 验证方法           |
| ------------------- | ---- | ------------------ |
| 数据库连接池耗尽    | 高   | 检查连接池监控面板 |
| 下游服务超时        | 中   | 查看链路追踪 Trace |
| GC 停顿导致响应阻塞 | 低   | 检查 JVM GC 日志   |

### 解决方案

**数据库连接池耗尽**：

1. 检查当前活跃连接数：`SELECT count(*) FROM pg_stat_activity;`
2. 如超过最大值，Kill 空闲连接后重启连接池
3. 长期方案：调整 `max_pool_size` 并增加连接超时

决策树方法

当问题原因不明确时，使用决策树引导排查者逐步缩小范围。

服务不可用
├── 能否 ping 通服务器？
│   ├── 否 → 网络或主机故障 → 联系运维
│   └── 是 → 进程是否运行？
│       ├── 否 → 检查进程崩溃日志 → 重启服务
│       └── 是 → 端口是否监听？
│           ├── 否 → 检查启动配置
│           └── 是 → 健康检查是否通过？
│               ├── 否 → 检查依赖服务状态
│               └── 是 → 检查负载均衡配置

决策树设计原则

原则 说明
先验概率排序 最常见的原因放在最前面
成本最低优先 优先执行成本低的检查（如看日志比重启服务优先）
不超过 5 层 决策树深度控制在 5 层以内
每个节点可操作 每一步都有具体命令或检查方法

日志分析指南

常用日志排查命令

# 按时间范围过滤日志
grep "2025-03-15T14:" /var/log/app/error.log

# 统计错误类型分布
awk '{print $5}' /var/log/app/error.log | sort | uniq -c | sort -rn | head -20

# 查看请求延迟分布
grep "duration_ms" /var/log/app/access.log | \
  awk -F'duration_ms=' '{print $2}' | \
  awk '{sum+=$1; count++} END {print "avg:", sum/count, "ms"}'

# 追踪特定请求 ID 的完整链路
grep "trace_id=abc123" /var/log/app/*.log | sort -t' ' -k1

日志级别与排查策略

日志级别 排查策略 注意事项
ERROR 直接定位报错堆栈和上下文 关注首次出现时间
WARN 检查是否为错误的前兆信号 关注频率变化趋势
INFO 追踪请求链路和状态变化 按 trace_id 聚合分析
DEBUG 深入代码执行细节 仅在生产环境临时开启

升级处理流程

当问题超出当前处理能力时，需要按流程升级。

级别 触发条件 处理人 响应时间
L1 已知问题，有标准解决方案 值班工程师 15 分钟
L2 未知问题，需要代码级排查 模块负责人 30 分钟
L3 跨系统问题，影响核心链路 技术负责人 + SRE 15 分钟
P0 全站不可用或数据丢失 CTO + 全员响应 立即

升级通知模板

**问题摘要**：[一句话描述] **影响范围**：[受影响的服务/用户数] **开始时间**：[首次发现时间] **当前状态**：[排查中/已定位/已修复] **已尝试**：[已执行的排查步骤] **需要支持**：[需要什么样的帮助]

已知问题管理

已知问题记录模板

字段 说明
问题编号 唯一标识，如 KI-2025-001
症状描述 用户可见的表现
影响范围 受影响的功能和用户群
根因 已确认的技术原因
规避方案 在正式修复前的临时方案
修复状态 待修复 / 已排期 / 已修复
关联工单 Bug Tracker 的工单链接

已知问题示例

**KI-2025-003**：文件上传超过 100MB 时返回 413 错误

- **影响范围**：所有使用文件上传功能的用户
- **根因**：Nginx 默认 `client_max_body_size` 为 1m，CDN 层限制为 100MB
- **规避方案**：将大文件拆分为多个 < 100MB 的分片上传
- **修复状态**：已排期（v2.5.0）
- **关联工单**：JIRA-4521
