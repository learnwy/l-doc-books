Java 性能调优

核心概念

Java 性能调优是一个从 JVM 参数配置、GC 行为分析到应用层代码优化的系统性工程。Java 应用的性能瓶颈通常表现为高延迟、低吞吐量或频繁的 GC 停顿，而有效的调优需要在可观测性的基础上进行，即先度量、再分析、后优化。理解 JVM 运行时行为和性能分析工具链是做出正确优化决策的前提。

JVM 参数与内存配置
JVM 参数是性能调优的第一道防线。合理的内存配置可以避免大部分 OOM 和频繁 GC 问题。


堆内存配置
# 基础内存配置
java -Xms4g -Xmx4g \
     -XX:NewRatio=2 \
     -XX:SurvivorRatio=8 \
     -XX:MetaspaceSize=256m \
     -XX:MaxMetaspaceSize=512m \
     -jar app.jar

# 容器环境配置（Java 17+自动识别 cgroup 限制）
java -XX:MaxRAMPercentage=75.0 \
     -XX:InitialRAMPercentage=75.0 \
     -jar app.jar

JIT 编译器配置
# 分层编译（默认开启）
java -XX:+TieredCompilation \
     -XX:TieredStopAtLevel=4 \
     -jar app.jar

# 查看 JIT 编译的方法
java -XX:+PrintCompilation -jar app.jar

# GraalVM Native Image（AOT 编译）
native-image --no-fallback -jar app.jar
分层编译将方法从解释执行逐步升级到 C1（快速编译）再到 C2（深度优化），热点方法最终获得最佳性能。在启动敏感的场景中可以使用 CDS（Class Data Sharing）加速类加载：


# 生成共享类列表
java -Xshare:dump -jar app.jar

# 使用共享类数据启动
java -Xshare:on -jar app.jar

G1GC 调优
java -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -XX:G1HeapRegionSize=16m \
     -XX:InitiatingHeapOccupancyPercent=45 \
     -XX:G1MixedGCCountTarget=8 \
     -XX:G1ReservePercent=10 \
     -Xlog:gc*:file=gc.log:time,uptime,level,tags \
     -jar app.jar
G1GC 通过 Region 化的堆布局和可预测的停顿时间模型，在吞吐量和延迟之间取得平衡。MaxGCPauseMillis 是目标停顿时间（非硬限制），G1 会动态调整回收策略来逼近该目标。


ZGC 配置
java -XX:+UseZGC \
     -XX:+ZGenerational \
     -Xmx16g \
     -Xlog:gc*:file=gc.log:time,uptime,level,tags \
     -jar app.jar
ZGC 使用染色指针（Colored Pointers）和读屏障（Load Barriers）实现并发标记和并发重定位，几乎所有 GC 工作都在应用线程运行时并发完成，停顿时间不随堆大小增加而增长。Java 21 引入的分代 ZGC（-XX:+ZGenerational）进一步提升了吞吐量。

性能分析工具链
精确的性能分析是有效调优的基础。Java 生态提供了从 JDK 内置工具到第三方 Profiler 的完整工具链。


JDK 内置工具
# jcmd：统一诊断命令
jcmd <pid> VM.flags            # 查看 JVM 参数
jcmd <pid> GC.heap_info        # 堆内存信息
jcmd <pid> Thread.print        # 线程转储
jcmd <pid> JFR.start duration=60s filename=recording.jfr

# jmap：内存分析
jmap -histo <pid>              # 对象直方图
jmap -dump:live,format=b,file=heap.hprof <pid>

# jstat：GC 统计
jstat -gcutil <pid> 1000       # 每秒输出 GC 统计
# S0   S1   E    O    M    CCS  YGC  YGCT  FGC  FGCT  CGC  CGCT  GCT
# 0.00 98.5 45.2 62.3 95.1 92.8 142  1.523 2    0.312 12   0.045 1.880
Async-profiler
Async-profiler 是 Java 生态最强大的低开销采样分析器，支持 CPU、内存分配和锁竞争分析：


# CPU 火焰图
./asprof -d 30 -f cpu.html <pid>

# 内存分配火焰图
./asprof -e alloc -d 30 -f alloc.html <pid>

# 锁竞争分析
./asprof -e lock -d 30 -f lock.html <pid>

# Wall-clock 模式（包含阻塞时间）
./asprof -e wall -t -d 30 -f wall.html <pid>
JMH 基准测试
JMH（Java Microbenchmark Harness）是 OpenJDK 官方的微基准测试框架，用于精确测量方法级性能：


@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 10, time = 1)
@Fork(2)
@State(Scope.Benchmark)
public class CollectionBenchmark {

    private List<Integer> arrayList;
    private List<Integer> linkedList;

    @Setup
    public void setup() {
        arrayList = new ArrayList<>(IntStream.range(0, 10000).boxed().toList());
        linkedList = new LinkedList<>(arrayList);
    }

    @Benchmark
    public int arrayListIteration() {
        int sum = 0;
        for (int i = 0; i < arrayList.size(); i++) {
            sum += arrayList.get(i);
        }
        return sum;
    }

    @Benchmark
    public int linkedListIteration() {
        int sum = 0;
        for (int val : linkedList) {
            sum += val;
        }
        return sum;
    }
}

代码层性能优化
JVM 参数和 GC 调优解决的是基础设施层面的问题，而代码层优化直接影响应用的业务性能。


对象分配优化
频繁的对象分配是 GC 压力的主要来源。减少不必要的对象创建是最有效的代码优化手段之一：


// 避免在循环中创建对象
// 反模式
for (int i = 0; i < 10000; i++) {
    String key = new StringBuilder("prefix_").append(i).toString();
    map.put(key, process(i));
}

// 优化：复用 StringBuilder
StringBuilder sb = new StringBuilder(32);
for (int i = 0; i < 10000; i++) {
    sb.setLength(0);
    sb.append("prefix_").append(i);
    map.put(sb.toString(), process(i));
}

// 使用基本类型代替包装类型
// 反模式
Map<Integer, Long> counters = new HashMap<>();

// 优化：使用 Eclipse Collections 原始类型集合
IntLongHashMap counters = new IntLongHashMap();
集合与数据结构选择
// 预分配容量避免扩容
List<Order> orders = new ArrayList<>(expectedSize);
Map<String, User> cache = new HashMap<>(expectedSize * 4 / 3 + 1);

// 只读集合使用不可变实现
List<String> configs = List.of("a", "b", "c");
Map<String, Integer> mapping = Map.of("key1", 1, "key2", 2);

// 高并发场景选择合适的并发集合
ConcurrentHashMap<String, AtomicLong> metrics = new ConcurrentHashMap<>();
CopyOnWriteArrayList<EventListener> listeners = new CopyOnWriteArrayList<>();

字符串与 I/O 优化
// 字符串拼接优化
// 反模式：循环中 += 产生大量临时对象
String result = "";
for (String s : items) {
    result += s + ",";
}

// 优化方案 1：StringJoiner
StringJoiner sj = new StringJoiner(",");
items.forEach(sj::add);
String result = sj.toString();

// 优化方案 2：String.join（底层使用 StringJoiner）
String result = String.join(",", items);

// I/O 优化：使用 Buffered 包装
try (BufferedReader reader = new BufferedReader(new FileReader(path), 8192);
     BufferedWriter writer = new BufferedWriter(new FileWriter(output), 8192)) {
    String line;
    while ((line = reader.readLine()) != null) {
        writer.write(processLine(line));
        writer.newLine();
    }
}
小结
    

  • Java 性能调优遵循「度量 → 分析 → 优化 → 验证」的闭环流程，切忌无数据的盲目优化
    • 

  • JVM 内存配置的关键原则：Xms 等于 Xmx 避免堆震荡，容器环境使用 MaxRAMPercentage
    • 

  • GC 选择依据场景：G1GC 适用于通用场景，ZGC 适用于低延迟需求，Parallel GC 适用于批处理
    • 

  • GC 日志是诊断内存问题的第一手数据，重点关注停顿时间、频率和堆使用率趋势
    • 

  • Async-profiler 和 JFR 是生产环境性能分析的首选工具，开销低且信息全面
    • 

  • JMH 是方法级性能对比的标准工具，避免手写 System.nanoTime 式的不可靠测试
    • 

  • 代码层优化的核心策略：减少对象分配、选择合适的数据结构、预分配容量、避免字符串拼接陷阱
