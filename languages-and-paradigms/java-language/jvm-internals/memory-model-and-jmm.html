Java 内存模型与 JMM

核心概念

Java 内存模型（Java Memory Model, JMM）定义了多线程程序中变量的访问规则——即一个线程对共享变量的写入何时对另一个线程可见。JMM 是 Java 并发编程的理论基础，它通过 happens-before 关系来描述操作之间的可见性和有序性保证，屏蔽了不同硬件平台内存一致性模型的差异。

JMM 是一个抽象模型，不直接对应硬件架构。它的核心是定义了一组规则，告诉编译器和 CPU 哪些重排序是允许的，哪些必须被禁止。


Happens-Before 规则
Happens-before 是 JMM 的核心概念——如果操作 A happens-before 操作 B，则 A 的结果对 B 可见，且 A 在逻辑上排在 B 之前。JMM 定义了以下 happens-before 规则：


// 规则1：程序顺序规则
// 同一线程中，前面的操作 happens-before 后面的操作
int a = 1;    // (1)
int b = a;    // (2) → (1) happens-before (2)

// 规则2：监视器锁规则
// 解锁 happens-before 后续对同一锁的加锁
synchronized (lock) {
    x = 1;    // (1) 写入 x
}             // (2) 解锁
// 另一线程
synchronized (lock) {   // (3) 加锁 → (2) happens-before (3)
    int r = x;          // (4) 保证读到 x = 1
}

// 规则3：volatile 变量规则
// 对 volatile 变量的写 happens-before 后续对该变量的读
volatile boolean flag = false;
// 线程 A
x = 42;        // (1)
flag = true;   // (2) volatile 写

// 线程 B
if (flag) {    // (3) volatile 读 → (2) happens-before (3)
    int r = x; // (4) 保证读到 x = 42
}

volatile 语义与内存屏障
volatile 关键字提供了两个保证：可见性（写入立即刷新到主内存，读取从主内存加载）和有序性（禁止 volatile 读写前后的特定重排序）。但 volatile 不保证原子性。


public class DoubleCheckSingleton {
    private static volatile DoubleCheckSingleton instance;

    public static DoubleCheckSingleton getInstance() {
        if (instance == null) {                    // 第一次检查（无锁）
            synchronized (DoubleCheckSingleton.class) {
                if (instance == null) {            // 第二次检查（有锁）
                    instance = new DoubleCheckSingleton();
                    // 没有 volatile，这行可能被重排序为：
                    // 1. 分配内存
                    // 2. 将引用赋值给 instance（此时对象未初始化！）
                    // 3. 执行构造函数
                    // volatile 禁止了 2 和 3 的重排序
                }
            }
        }
        return instance;
    }
}
volatile 的内存屏障实现：


// volatile 写操作前插入 StoreStore 屏障
// volatile 写操作后插入 StoreLoad 屏障（最重的屏障）
// volatile 读操作后插入 LoadLoad + LoadStore 屏障

// 在 x86 架构上：
// volatile 写 → lock 前缀指令（或 mfence）
// volatile 读 → 无需额外指令（x86 天然保证 Load-Load 和 Load-Store 顺序）

final 语义与安全发布
JMM 对 final 字段提供了特殊的初始化安全保证：在构造函数中写入 final 字段，在构造函数完成后，任何线程都能看到正确初始化的 final 字段值——即使对象的引用没有使用 volatile 或同步。


public class ImmutableConfig {
    private final Map<String, String> settings;

    public ImmutableConfig(Map<String, String> src) {
        this.settings = Collections.unmodifiableMap(new HashMap<>(src));
        // JMM 保证：构造函数结束后，任何线程读到 settings 字段
        // 都能看到完整初始化的 HashMap 内容
    }

    public String get(String key) {
        return settings.get(key);
    }
}
但有一个前提条件——对象引用不能在构造函数完成之前泄漏（this 逃逸）：


public class Broken {
    private final int value;

    public Broken(int v) {
        // 危险：在构造函数完成前发布 this
        GlobalRegistry.register(this);  // 其他线程可能看到 value = 0
        this.value = v;
    }
}

常见并发可见性问题
// 问题1：无限循环——缺少可见性保证
public class StopThread {
    private boolean stopped = false;  // 应该用 volatile

    public void run() {
        while (!stopped) {
            // JIT 可能将 stopped 提升到循环外（hoisting）
            // 导致永远看不到 stopped = true
        }
    }

    public void stop() { stopped = true; }
}

// 问题2：volatile 不保证原子性
public class Counter {
    private volatile int count = 0;

    public void increment() {
        count++;  // 非原子操作：read → increment → write
        // 多线程下仍然会丢失更新
        // 应使用 AtomicInteger 或 synchronized
    }
}

// 问题3：long/double 的非原子性
// JMM 不保证 64 位类型的原子读写（32 位 JVM 上）
private long timestamp;  // 应该用 volatile long

小结
    

  • JMM 定义了多线程程序中共享变量的可见性和有序性规则，是 Java 并发的理论基础
    • 

  • Happens-before 是判断操作间可见性的核心工具，八大规则加传递性覆盖所有同步场景
    • 

  • volatile 保证可见性和有序性但不保证原子性，底层通过内存屏障禁止特定重排序
    • 

  • 双重检查锁定必须使用 volatile 防止对象引用的重排序问题
    • 

  • final 字段在构造函数完成后具有初始化安全保证，前提是 this 不在构造期间泄漏
    • 

  • 安全发布对象的方式：volatile 引用、synchronized、final 字段、Atomic 引用、静态初始化器
