JIT 编译

核心概念

JIT（Just-In-Time）编译是 JVM 将热点字节码在运行时编译为本地机器码的优化技术。Java 采用"解释执行 + JIT 编译"的混合模式——程序启动时解释执行字节码，当某段代码被频繁执行（达到热点阈值）后，JIT 编译器将其编译为优化的本地代码。这种设计兼顾了启动速度和峰值性能。

分层编译体系
Java 8+ 默认启用分层编译（Tiered Compilation），将编译过程分为 5 个级别，实现启动速度和峰值性能的最佳平衡：


// Level 0: 解释执行，收集基本 profiling 信息
// Level 1: C1 编译，无 profiling（简单方法的终态）
// Level 2: C1 编译，有限 profiling
// Level 3: C1 编译，完整 profiling（大多数方法的中间态）
// Level 4: C2 编译，深度优化（热点方法的终态）
典型编译路径：


热点检测使用基于计数器的方案——方法调用计数器和回边计数器（循环体内的跳转次数）。当两者之和超过阈值时触发编译：


// -XX:CompileThreshold=10000  (解释模式下的默认阈值)
// 分层编译下由 JVM 动态调整阈值

// 查看 JIT 编译日志
// -XX:+PrintCompilation
//   72   1     3   java.lang.String::hashCode (55 bytes)
//   74   2     4   java.lang.String::hashCode (55 bytes)
// 格式：时间戳 编译ID 级别 方法名 (字节码大小)

关键优化技术
C2 编译器执行多种激进优化，是 Java 能达到接近 C++ 性能的关键：


方法内联（Method Inlining）——将被调方法的代码直接嵌入调用点，消除方法调用开销，并为后续优化开辟空间：


// 优化前
public int compute(int x) {
    return square(x) + 1;
}
private int square(int n) { return n * n; }

// 内联后
public int compute(int x) {
    return x * x + 1;
}

// 控制参数
// -XX:MaxInlineSize=35         小方法直接内联
// -XX:FreqInlineSize=325       热点方法内联上限
// -XX:InlineSmallCode=2000     已编译代码的内联上限
逃逸分析（Escape Analysis）——判断对象的作用域是否逃逸出方法或线程，据此执行标量替换和栈上分配：


public int sumPoints() {
    int total = 0;
    for (int i = 0; i < 1000; i++) {
        Point p = new Point(i, i * 2);  // p 不会逃逸出循环
        total += p.x() + p.y();
    }
    return total;
}

// 经逃逸分析 + 标量替换后等价于：
public int sumPoints() {
    int total = 0;
    for (int i = 0; i < 1000; i++) {
        int x = i;
        int y = i * 2;
        total += x + y;
    }
    return total;
}
// 完全消除了 Point 对象的堆分配
循环优化：


// 循环展开（Loop Unrolling）
for (int i = 0; i < 100; i++) { a[i] = b[i] + c[i]; }
// 展开为：
for (int i = 0; i < 100; i += 4) {
    a[i]   = b[i]   + c[i];
    a[i+1] = b[i+1] + c[i+1];
    a[i+2] = b[i+2] + c[i+2];
    a[i+3] = b[i+3] + c[i+3];
}

// 循环向量化（SIMD）：C2 自动使用 AVX/SSE 指令处理数组运算

逆优化与性能陷阱
JIT 编译是投机性的——基于运行时 profiling 数据做出优化假设。当假设不再成立时，JVM 执行逆优化（Deoptimization），回退到解释执行：


// 假设性内联
public void process(Shape shape) {
    shape.draw();  // profiling 显示 99% 是 Circle
    // C2 直接内联 Circle.draw()
    // 如果突然出现 Rectangle，触发逆优化
}

// 查看逆优化
// -XX:+TraceDeoptimization
// Uncommon trap: reason=class_check action=maybe_recompile
常见性能陷阱：


// 1. 多态调用阻止内联（megamorphic site）
List<Shape> shapes = ...; // 包含 5+ 种 Shape 子类
for (Shape s : shapes) {
    s.draw();  // 多态度过高，C2 放弃内联
}

// 2. Code Cache 溢出
// -XX:ReservedCodeCacheSize=256m (默认)
// 超出后新方法无法被编译，性能骤降

// 3. 编译队列积压
// 启动时大量方法同时触发编译，C2 队列拥塞
// 监控：-XX:+PrintCompilation 中 "made not entrant" 频繁出现

GraalVM 与 AOT 编译
GraalVM 提供了两种替代编译方案：Graal JIT 编译器（替代 C2）和 Native Image（AOT 编译）：


# 使用 Graal JIT（作为 C2 替代）
java -XX:+UseJVMCICompiler -jar app.jar

# Native Image AOT 编译（消除 JIT，毫秒级启动）
native-image -jar app.jar
# 生成独立可执行文件，启动时间 <100ms，内存占用大幅减少

小结
    

  • JIT 编译是 JVM 将热点字节码编译为本地机器码的运行时优化，Java 默认使用分层编译（C1 + C2）
    • 

  • 热点检测基于方法调用计数器和回边计数器，达到阈值后触发编译
    • 

  • 核心优化技术包括方法内联、逃逸分析、标量替换、循环展开和锁消除
    • 

  • 逆优化在运行时假设失效时发生，多态调用过多和 Code Cache 溢出是常见性能陷阱
    • 

  • GraalVM Native Image 提供 AOT 编译方案，以峰值性能换取毫秒级启动和低内存占用
    • 

  • 通过 -XX:+PrintCompilation 和 -XX:+TraceDeoptimization 诊断 JIT 行为
    •
