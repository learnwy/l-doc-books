Java 类加载机制

核心概念

Java 的类加载机制是 JVM 将 .class 字节码文件加载到内存并转换为 java.lang.Class 对象的过程。这一机制采用了委托模型（Delegation Model）和延迟加载策略，是 Java 实现平台无关性、动态扩展和模块隔离的基础。理解类加载的全过程，对于排查 ClassNotFoundException、NoClassDefFoundError 以及设计插件系统至关重要。

类加载遵循按需加载——JVM 规范只要求在首次主动使用时初始化类，而非启动时加载所有类。


双亲委派模型
双亲委派模型（Parent Delegation Model）是 Java 类加载器的标准工作方式：当一个类加载器收到加载请求时，它首先将请求委托给父加载器，只有当父加载器无法完成加载时，才由自己来加载。


protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
            }
            if (c == null) {
                c = findClass(name);
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}

双亲委派的价值：防止核心类被篡改（如自定义 java.lang.String 不会被加载），保证类的唯一性——同一个类由同一个加载器加载时才是同一个类。


打破双亲委派
某些场景需要打破双亲委派的限制。最典型的是 SPI（Service Provider Interface）机制和 Web 容器中的类隔离。


SPI 与线程上下文类加载器：JDBC 驱动加载是经典案例——DriverManager 在 Bootstrap 加载器加载，但需要加载 classpath 上的驱动实现：


// java.sql.DriverManager 使用 ServiceLoader 加载驱动
// ServiceLoader 内部使用线程上下文类加载器
ServiceLoader<Driver> loadedDrivers = ServiceLoader.load(Driver.class);

// 设置线程上下文类加载器
Thread.currentThread().setContextClassLoader(customClassLoader);
Web 容器类加载：Tomcat 等 Web 容器为每个 Web 应用创建独立的类加载器，优先加载 WEB-INF/lib 和 WEB-INF/classes 中的类，实现应用间的类隔离：


// Tomcat 的类加载顺序（打破双亲委派）：
// 1. Bootstrap → JVM 核心类
// 2. Web App ClassLoader → WEB-INF/classes, WEB-INF/lib
// 3. Common ClassLoader → Tomcat 共享库
// 4. System ClassLoader → classpath
自定义类加载器——实现热部署或插件系统：


public class PluginClassLoader extends ClassLoader {
    private final Path pluginDir;

    public PluginClassLoader(Path pluginDir, ClassLoader parent) {
        super(parent);
        this.pluginDir = pluginDir;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            Path classFile = pluginDir.resolve(name.replace('.', '/') + ".class");
            byte[] bytes = Files.readAllBytes(classFile);
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}

类的初始化时机
JVM 规范严格定义了类初始化的触发条件（主动使用）。仅以下六种情况会触发类的初始化：


public class InitOrder {
    static {
        System.out.println("InitOrder 初始化");
    }

    public static final int COMPILE_CONST = 42;
    public static final int RUNTIME_CONST = new Random().nextInt();
}

// 触发初始化的主动使用：
new InitOrder();                           // 1. new 实例
InitOrder.RUNTIME_CONST;                   // 2. 读取非编译期常量的静态字段
InitOrder.class.getDeclaredMethods();      // 3. 反射调用
// 子类初始化时，父类先初始化                     // 4. 子类初始化
// JVM 启动时的主类                           // 5. main 方法所在类
// MethodHandle 解析                        // 6. 动态语言支持

// 不触发初始化的被动引用：
InitOrder.COMPILE_CONST;                   // 编译期常量，不触发
InitOrder[] arr = new InitOrder[10];       // 数组创建，不触发
静态块与静态变量的执行顺序：<clinit> 方法按照源代码中静态语句出现的先后顺序执行。JVM 保证 <clinit> 方法在多线程环境下只执行一次：


public class Singleton {
    private static final Singleton INSTANCE = new Singleton();

    private Singleton() {}

    public static Singleton getInstance() {
        return INSTANCE;
    }
}
这正是基于类加载机制实现线程安全单例的原理——<clinit> 的线程安全由 JVM 保证。

class 版本高于 JVM

小结
    

  • 类加载经历加载、验证、准备、解析、初始化五个阶段，遵循按需加载原则
    • 

  • 双亲委派模型通过向上委托保证核心类安全和唯一性
    • 

  • SPI、Web 容器、热部署等场景需要打破双亲委派，常见方式是线程上下文加载器和自定义加载器
    • 

  • 只有六种主动使用会触发类初始化，编译期常量和数组创建不会触发
    • 

  • 利用 <clinit> 的线程安全保证可以实现高效的单例模式
    • 

  • 类加载相关异常（ClassNotFoundException vs NoClassDefFoundError）的根因不同，需要针对性排查
