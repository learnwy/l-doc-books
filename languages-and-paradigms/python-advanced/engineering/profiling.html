性能分析与优化

概述

Python 以开发效率著称，但在性能敏感场景中可能成为瓶颈。性能优化的核心原则是"先测量，后优化"——使用 profiler 找到真正的瓶颈，然后针对性地应用优化策略。

性能分析工具

cProfile

python -m cProfile -s cumulative my_script.py
import cProfile
import pstats

with cProfile.Profile() as pr:
    result = expensive_function()

stats = pstats.Stats(pr)
stats.sort_stats("cumulative")
stats.print_stats(20)

cProfile 的输出包含每个函数的调用次数（ncalls）、总耗时（tottime）和累计耗时（cumtime）。tottime 是函数自身代码的执行时间，cumtime 包括其调用的所有子函数时间。定位瓶颈时应关注 cumtime 最高的函数，然后用 line_profiler 进一步分析其内部热点行。

line_profiler

pip install line_profiler
kernprof -l -v my_script.py
@profile
def compute():
    a = [i ** 2 for i in range(1000000)]
    b = sum(a)
    return b

工具对比

工具 粒度 开销 适用场景
cProfile 函数级 低 全局瓶颈定位
line_profiler 行级 中 热点函数逐行分析
memory_profiler 行级内存 高 内存泄漏排查
py-spy 采样式 极低 生产环境 profiling
scalene CPU+内存+GPU 低 全面性能分析

py-spy 是生产环境 profiling 的首选工具——它通过系统调用读取目标进程的调用栈，无需修改代码或重启服务。可以直接 attach 到正在运行的 Python 进程，生成火焰图进行可视化分析。

内存分析

pip install memory_profiler
python -m memory_profiler my_script.py
from memory_profiler import profile

@profile
def load_data():
    data = [i for i in range(10_000_000)]
    filtered = [x for x in data if x % 2 == 0]
    return filtered

常见内存问题

问题 症状 解决方案
大列表 内存持续增长 改用生成器
循环引用 对象无法被 GC 使用 weakref
字符串拼接 大量临时对象 使用 "".join()
全局缓存无限增长 内存随时间膨胀 使用 functools.lru_cache

lru_cache 默认的 maxsize=128 会在缓存满后自动淘汰最久未使用的条目。如果缓存的键空间较大（如对大范围参数缓存计算结果），应设置合理的 maxsize 防止内存无限增长。可以通过 func.cache_info() 查看缓存命中率来评估 maxsize 设置是否合理。

常见优化技巧

squares = [x ** 2 for x in range(1000)]

squares_gen = (x ** 2 for x in range(1000))

from functools import lru_cache

@lru_cache(maxsize=256)
def fib(n: int) -> int:
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

lookup = {item["id"]: item for item in items}

列表推导式比等价的 for 循环快约 30%，因为它在 CPython 内部使用专用的 LIST_APPEND 字节码，省去了属性查找和函数调用的开销。生成器表达式则在内存方面有优势——它不创建完整列表，而是按需计算每个元素，适合处理大数据流。

并行与并发加速

from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

def cpu_bound(n: int) -> int:
    return sum(i * i for i in range(n))

with ProcessPoolExecutor(max_workers=4) as executor:
    results = list(executor.map(cpu_bound, [10**7] * 4))

def io_bound(url: str) -> str:
    import urllib.request
    return urllib.request.urlopen(url).read().decode()

with ThreadPoolExecutor(max_workers=10) as executor:
    results = list(executor.map(io_bound, urls))
场景 方案 原因
CPU 密集 ProcessPoolExecutor 绕过 GIL
I/O 密集 ThreadPoolExecutor GIL 在 I/O 时释放
异步 I/O asyncio 单线程高并发

C 扩展加速

Cython

def primes_python(nb_primes: int) -> list[int]:
    primes = []
    n = 2
    while len(primes) < nb_primes:
        for p in primes:
            if n % p == 0:
                break
        else:
            primes.append(n)
        n += 1
    return primes

加速方案对比

方案 加速比 学习成本 适用场景
NumPy 10-100x 低 数组运算
Cython 10-50x 中 通用计算密集型
Numba 10-100x 低 数值计算（JIT）
PyO3/Rust 50-200x 高 极致性能需求
C 扩展 50-200x 高 底层系统交互

最佳实践

  • 先用 cProfile 定位热点函数，再用 line_profiler 逐行分析
  • 优先优化算法复杂度（O(n²) → O(n log n)），再考虑底层加速
  • 生产环境使用 py-spy 进行零开销 profiling
  • 内存敏感场景使用生成器替代列表，使用 __slots__ 减少对象开销
  • 避免过早优化——只在 profiler 证明是瓶颈时才优化
  • 使用 func.cache_info() 监控 lru_cache 命中率，据此调整 maxsize
