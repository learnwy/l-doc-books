pnpm 与 Monorepo

核心概念

pnpm 解决的问题和 Monorepo 的组织方式，共同构成了多包仓库的工程基础：

  • 内容寻址存储 + 硬链接：同一个包在所有项目中只存一份真实文件，其余是硬链接——磁盘占用从 "N 份拷贝" 降为 "1 份存储 + N 个链接"。
  • 严格的 node_modules 结构：根目录只包含 package.json 中声明的直接依赖的符号链接，实际文件放在 .pnpm/ 虚拟存储中。幽灵依赖因此完全不可能出现。
  • Monorepo：把多个相关包放进同一个 Git 仓库，共享工具链、统一版本管理。
  • pnpm Workspace：用 pnpm-workspace.yaml 声明包目录，workspace: 协议让包之间互相引用本地版本。
  • 共享配置与 Turbo 加速：TypeScript 配置可继承，Turborepo 用任务图与缓存加速多包构建。

pnpm 的核心优势

pnpm（Performant npm）是一个革命性的包管理器，它通过内容寻址存储和硬链接机制，从根本上解决了 npm 和 yarn 的两大痛点：磁盘空间浪费和幽灵依赖。

graph TB
    subgraph "npm 传统方式"
        P1["项目 A<br/>express@4.18"] --> NM1["node_modules/<br/>express@4.18<br/>+30 个子依赖"]
        P2["项目 B<br/>express@4.18"] --> NM2["node_modules/<br/>express@4.18<br/>+30 个子依赖"]
    end
    subgraph "pnpm 方式"
        PA[项目 A] --> HLA[硬链接]
        PB[项目 B] --> HLB[硬链接]
        HLA --> STORE["全局存储<br/>~/.local/share/pnpm/store<br/>express@4.18 仅一份"]
        HLB --> STORE
    end
对比维度 npm/yarn pnpm
存储方式 每个项目完整拷贝 全局内容寻址存储 + 硬链接
10 个项目同依赖 10 份完整拷贝 1 份存储 + 10 个硬链接
幽灵依赖 可能访问未声明的包 严格隔离，不可访问
安装速度 中等 最快（已缓存时接近零）

pnpm 的 node_modules 结构

pnpm 使用独特的符号链接 + 硬链接结构来组织 node_modules：

graph TB
    subgraph "项目 node_modules/"
        DIRECT[".pnpm/"]
        EXPRESS["express → .pnpm/express@4.18/node_modules/express"]
    end
    subgraph ".pnpm/ (虚拟存储)"
        EX_DIR[".pnpm/express@4.18/node_modules/"]
        EX_REAL["express/ → 硬链接到全局存储"]
        EX_DEPS["accepts/"]
        EX_DEPS2["body-parser/"]
    end
    subgraph "全局存储 (~/.local/share/pnpm/store/)"
        STORE_EX["express@4.18 内容"]
    end
    EXPRESS -->|符号链接| EX_REAL
    EX_REAL -->|硬链接| STORE_EX

关键设计：

  1. node_modules 根目录只包含 package.json 中声明的直接依赖的符号链接
  2. 所有包的实际文件存储在 .pnpm/ 目录中
  3. .pnpm/ 中的文件通过硬链接指向全局内容寻址存储
  4. 子依赖通过符号链接互相引用

这意味着幽灵依赖完全不可能——只有 package.json 中声明的包才会出现在 node_modules 的根层级。

pnpm 基本使用

npm install -g pnpm

pnpm install
pnpm add express
pnpm add -D typescript
pnpm remove lodash

pnpm run dev
pnpm test
pnpm dlx tsx script.ts

常用配置（.npmrc）

shamefully-hoist=false
strict-peer-dependencies=true
auto-install-peers=true
node-linker=hoisted

shamefully-hoist=true 会将所有依赖提升到根 node_modules，模拟 npm 的行为——这主要用于兼容不支持 pnpm 严格结构的工具，但会失去幽灵依赖防护。

Monorepo 基础

Monorepo（单仓多包）是将多个相关项目放在同一个 Git 仓库中管理的工程实践。

graph TB
    subgraph Monorepo
        ROOT[根目录<br/>package.json<br/>pnpm-workspace.yaml]
        PKG_A[packages/core<br/>核心库]
        PKG_B[packages/cli<br/>CLI 工具]
        PKG_C[packages/ui<br/>UI 组件库]
        APP[apps/web<br/>Web 应用]
        ROOT --> PKG_A
        ROOT --> PKG_B
        ROOT --> PKG_C
        ROOT --> APP
        APP --> PKG_A
        APP --> PKG_C
        PKG_B --> PKG_A
        PKG_C --> PKG_A
    end

优势与挑战

方面 优势 挑战
代码共享 直接引用内部包，无需发布 需要管理包间依赖关系
原子变更 跨包修改在同一个 commit 中 CI/CD 需要识别变更范围
工具统一 统一的 lint、test、build 配置 仓库体积可能很大
版本管理 协调一致的版本发布 版本策略需要精心设计

pnpm Workspace

pnpm 通过 pnpm-workspace.yaml 定义 workspace：

packages:
  - 'packages/*'
  - 'apps/*'
  - 'tools/*'

项目结构示例

├── pnpm-workspace.yaml
├── package.json
├── packages/
│   ├── core/
│   │   ├── package.json
│   │   └── src/
│   ├── utils/
│   │   ├── package.json

│       ├── package.json
│       └── src/
├── apps/

│   │   ├── package.json

│   └── api/
│       ├── package.json
│       └── src/
└── tsconfig.base.json

workspace 协议

{
  "name": "@myorg/web",
  "dependencies": {
    "@myorg/core": "workspace:*",
    "@myorg/utils": "workspace:^1.0.0"
  }
}

workspace: 协议告诉 pnpm 从本地 workspace 解析包，而非从 Registry 下载。发布时，pnpm 会自动将 workspace:* 替换为实际版本号。

协议写法 含义 发布时替换为
workspace:* 匹配当前版本 1.2.3
workspace:^ 兼容当前版本 ^1.2.3
workspace:~ 近似当前版本 ~1.2.3

Workspace 命令

pnpm --filter @myorg/web dev

pnpm --filter @myorg/core build

pnpm --filter "./packages/**" test

pnpm --filter @myorg/web... build

pnpm -r run build

pnpm -r --parallel run lint

过滤器语法

const filterPatterns = {
  '--filter <package>': '指定单个包',
  '--filter <package>...': '指定包及其所有依赖',
  '--filter ...<package>': '指定包及其所有依赖者',
  "--filter './packages/**'": '匹配目录模式',
  "--filter '...[origin/main]'": '自上次发布以来变更的包',
  '-r': '所有 workspace 包',
};

共享配置

TypeScript 配置继承

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/"]
}

根 package.json

{
  "private": true,
  "scripts": {
    "build": "pnpm -r run build",
    "test": "pnpm -r run test",
    "lint": "pnpm -r --parallel run lint",
    "clean": "pnpm -r exec rm -rf dist node_modules"
  },
  "devDependencies": {
    "typescript": "^5.3.0"
  }
}

将所有包共用的 devDependencies 安装在根目录，避免重复声明。

Turborepo 加速构建

pnpm workspace 经常与 Turborepo 搭配使用，实现智能缓存和并行构建：

{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": []
    },
    "lint": {
      "outputs": []
    }
  }
}
flowchart LR
    CORE_BUILD[core:build] --> UTILS_BUILD[utils:build]
    CORE_BUILD --> WEB_BUILD[web:build]
    UTILS_BUILD --> WEB_BUILD
    WEB_BUILD --> WEB_TEST[web:test]

Turborepo 会分析任务依赖图，自动并行执行不相互依赖的任务，并缓存已完成的任务输出。当文件没有变化时，后续构建几乎是即时完成。

小结

  • pnpm 通过内容寻址存储和硬链接实现包的全局去重，大幅节省磁盘空间。
  • pnpm 的严格 node_modules 结构彻底杜绝了幽灵依赖问题。
  • pnpm-workspace.yaml 定义 workspace 包范围，workspace: 协议管理包间依赖。
  • 使用 --filter 精确控制命令执行范围，-r 在所有包中执行。
  • 共享配置（TypeScript、ESLint 等）放在根目录，通过继承机制复用。
  • Turborepo 与 pnpm workspace 搭配使用，实现智能缓存和并行构建。
