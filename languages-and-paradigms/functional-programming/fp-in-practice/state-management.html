Part III · 范式与文本函数式编程 简介FP 实战 简介状态管理

状态管理

函数式状态管理原则

函数式编程对状态管理有着明确的主张：状态应该是不可变的，状态变迁应该通过纯函数描述，副作用应该被隔离到边界。这些原则直接影响了 Redux、Elm Architecture 和事件溯源等架构模式的设计。

type State = { count: number; items: readonly string[] };
type Action =
  | { type: 'INCREMENT' }
  | { type: 'DECREMENT' }
  | { type: 'ADD_ITEM'; item: string }
  | { type: 'REMOVE_ITEM'; index: number };

const reducer = (state: State, action: Action): State => {
  switch (action.type) {
    case 'INCREMENT':
      return { ...state, count: state.count + 1 };
    case 'DECREMENT':
      return { ...state, count: state.count - 1 };
    case 'ADD_ITEM':
      return { ...state, items: [...state.items, action.item] };
    case 'REMOVE_ITEM':
      return {
        ...state,
        items: state.items.filter((_, i) => i !== action.index),
      };
  }
};
原则 传统方案 函数式方案
状态变更 直接修改对象 返回新状态对象
状态读取 随处可读 通过 selector 派生
副作用 混入业务逻辑 隔离到 middleware
可预测性 依赖执行顺序 纯函数保证
调试 断点 + 日志 时间旅行调试 


提示： Reducer 的命名来自 Array.prototype.reduce——它接收累积值（state）和当前元素（action），返回新的累积值（new state）。Redux 的 reducer 本质上就是对 action 流做 reduce 操作。






Redux 与 Elm Architecture
Elm Architecture 是函数式状态管理的典范，Redux 是它在 JavaScript 生态中的实现：


type Model = {
  todos: readonly { id: number; text: string; done: boolean }[];
  filter: 'all' | 'active' | 'completed';
  nextId: number;
};

type Msg =
  | { type: 'ADD_TODO'; text: string }
  | { type: 'TOGGLE_TODO'; id: number }
  | { type: 'SET_FILTER'; filter: Model['filter'] };

const update = (model: Model, msg: Msg): Model => {
  switch (msg.type) {
    case 'ADD_TODO':
      return {
        ...model,
        todos: [...model.todos, { id: model.nextId, text: msg.text, done: false }],
        nextId: model.nextId + 1,
      };
    case 'TOGGLE_TODO':
      return {
        ...model,
        todos: model.todos.map((todo) => (todo.id === msg.id ? { ...todo, done: !todo.done } : todo)),
      };
    case 'SET_FILTER':
      return { ...model, filter: msg.filter };
  }
};

const visibleTodos = (model: Model): Model['todos'] => {
  switch (model.filter) {
    case 'all':
      return model.todos;
    case 'active':
      return model.todos.filter((t) => !t.done);
    case 'completed':
      return model.todos.filter((t) => t.done);
  }
};

不可变状态树
不可变状态树的核心挑战是深层嵌套更新。函数式编程提供了 Lens 和 Optics 来优雅解决这个问题：


type AppState = {
  user: {
    profile: {
      name: string;
      address: {
        city: string;
        zip: string;
      };
    };
  };
};

const updateCity = (state: AppState, city: string): AppState => ({
  ...state,
  user: {
    ...state.user,
    profile: {
      ...state.user.profile,
      address: {
        ...state.user.profile.address,
        city,
      },
    },
  },
});

type Lens<S, A> = {
  get: (s: S) => A;
  set: (a: A) => (s: S) => S;
};

const compose = <S, A, B>(outer: Lens<S, A>, inner: Lens<A, B>): Lens<S, B> => ({
  get: (s) => inner.get(outer.get(s)),
  set: (b) => (s) => outer.set(inner.set(b)(outer.get(s)))(s),
});

事件溯源与 CQRS
事件溯源（Event Sourcing）是函数式状态管理在后端的极致形态——不存储当前状态，而是存储所有状态变更事件，通过 reduce 重建任意时刻的状态：


type Event =
  | { type: 'ACCOUNT_OPENED'; owner: string; id: string }
  | { type: 'DEPOSITED'; amount: number; id: string }
  | { type: 'WITHDRAWN'; amount: number; id: string }
  | { type: 'ACCOUNT_CLOSED'; id: string };

type Account = {
  id: string;
  owner: string;
  balance: number;
  status: 'active' | 'closed';
};

const apply = (state: Account, event: Event): Account => {
  switch (event.type) {
    case 'ACCOUNT_OPENED':
      return { id: event.id, owner: event.owner, balance: 0, status: 'active' };
    case 'DEPOSITED':
      return { ...state, balance: state.balance + event.amount };
    case 'WITHDRAWN':
      return { ...state, balance: state.balance - event.amount };
    case 'ACCOUNT_CLOSED':
      return { ...state, status: 'closed' };
  }
};

const rebuild = (events: readonly Event[]): Account => events.reduce(apply, {} as Account);

小结
    

  • 函数式状态管理的三大原则：不可变状态、纯函数变迁、副作用隔离。
    • 

  • Redux/Elm Architecture 的 reducer 本质上是对 action 流做 reduce 操作。
    • 

  • Lens/Optics 和 Immer 解决了深层嵌套不可变更新的痛点。
    • 

  • 事件溯源将函数式 reduce 模式推广到后端持久化，天然支持历史追踪和时间旅行。
    • 

  • 选择方案时需权衡不可变性带来的安全性与实现复杂度。
