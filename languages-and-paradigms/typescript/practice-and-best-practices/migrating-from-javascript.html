从 JavaScript 迁移

场景描述

将现有 JavaScript 项目迁移到 TypeScript 是一项常见但容易出错的工程任务。错误的迁移策略可能导致大量编译错误让团队陷入泥潭，或者为了快速通过编译而滥用 any，使迁移流于形式。本文介绍渐进式迁移的最佳实践，确保迁移过程平稳可控。



模式与方案
迁移策略对比




策略
描述
适用场景
风险





渐进式迁移
逐文件从 .js 改为 .ts，保持项目可运行

低




一次性迁移
所有文件一次性改名，集中修复类型错误

高（可能阻塞）




新代码 TS
旧代码保持 JS，新功能全用 TS
超大型遗留项目
低但进度慢





推荐使用渐进式迁移，下面是完整的迁移路线图。


阶段一：配置基础环境
初始化 TypeScript 配置，保持最大兼容性：


npm install --save-dev typescript

npx tsc --init
初始 tsconfig.json——宽松配置，确保现有代码能编译：


{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "allowJs": true,
    "checkJs": false,
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": false,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "skipLibCheck": true,
    "resolveJsonModule": true,
    "isolatedModules": true,
    "noEmit": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
关键选项说明：






选项
值
作用





allowJs
true
允许 TypeScript 编译 .js 文件




checkJs
false
暂不对 JS 文件做类型检查




strict
false
暂不启用严格模式




noEmit
true
仅做类型检查，由 bundler 负责编译





阶段二：启用 checkJs 并添加 JSDoc
在不改名文件的前提下，通过 checkJs 和 JSDoc 注释为 JavaScript 代码添加类型信息：


{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": true
  }
}
使用 JSDoc 为函数添加类型：


// @ts-check

/** @param {string} name */
/** @param {number} age */
/** @returns {string} */
function greet(name, age) {
  return `${name} is ${age} years old`;
}
对于暂时无法修复的文件，使用 // @ts-nocheck 跳过：


// @ts-nocheck
// 此文件暂时跳过类型检查
对于单行错误，使用 // @ts-ignore 或更安全的 // @ts-expect-error：


// @ts-expect-error 待迁移：参数类型不匹配
legacyFunction(unsafeArg);
阶段三：逐文件改名为 .ts
按照依赖方向从底层到上层的顺序，逐步将 .js 文件重命名为 .ts：


迁移单个文件的步骤：


mv src/utils/format.js src/utils/format.ts
然后修复该文件中的类型错误。常见的修复模式：


添加参数类型：


// 迁移前
function formatPrice(price, currency) {
  return `${currency} ${price.toFixed(2)}`;
}

// 迁移后
function formatPrice(price: number, currency: string): string {
  return `${currency} ${price.toFixed(2)}`;
}
添加接口定义：


// 迁移前的对象结构不明确
function createUser(data) {
  return { ...data, createdAt: new Date() };
}

// 迁移后有明确的类型
interface CreateUserInput {
  name: string;
  email: string;
  role?: 'admin' | 'user';
}

interface User extends CreateUserInput {
  createdAt: Date;
}

function createUser(data: CreateUserInput): User {
  return { ...data, role: data.role ?? 'user', createdAt: new Date() };
}
阶段四：逐步启用严格选项
全部文件改名为 .ts 后，按以下顺序启用严格选项：


{
  "compilerOptions": {
    "allowJs": false,
    "noImplicitAny": true
  }
}
修复所有 noImplicitAny 错误后，继续：


{
  "compilerOptions": {
    "noImplicitAny": true,
    "strictNullChecks": true
  }
}
strictNullChecks 通常产生最多的错误，常见修复模式：


// 修复前：未处理可能为 null 的情况
function getUser(id: string): User {
  return users.find((u) => u.id === id);
}

// 修复后：返回类型明确包含 null
function getUser(id: string): User | undefined {
  return users.find((u) => u.id === id);
}

// 调用方也需要修改
const user = getUser('123');
if (user) {
  console.log(user.name);
}
最终启用完全严格模式：


{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true
  }
}
为第三方库添加声明文件
许多第三方库没有自带类型声明，需要安装 @types 包或手写声明文件：


npm install --save-dev @types/lodash @types/express
对于没有 @types 包的库，创建自定义声明文件：


// src/types/legacy-lib.d.ts
declare module 'legacy-lib' {
  export function doSomething(input: string): string;
  export function transform(data: unknown[]): unknown[];

  export interface LegacyConfig {
    timeout: number;
    retries: number;
  }

  export class LegacyClient {
    constructor(config: LegacyConfig);
    connect(): Promise<void>;
    disconnect(): void;
  }
}
对于实在无法定义类型的模块，使用宽松声明：


// src/types/untyped-modules.d.ts
declare module 'some-untyped-lib';
declare module 'another-lib' {
  const lib: { init: () => void; version: string };
  export default lib;
}


类型安全技巧
迁移过程中的临时类型策略
当你不确定某个值的完整类型时，可以先用 unknown + 类型断言过渡：


// 阶段性方案：先用 unknown 代替 any
function processLegacyData(data: unknown): string {
  const obj = data as { name: string; value: number };
  return `${obj.name}: ${obj.value}`;
}

// 最终方案：定义完整类型 + 验证
interface LegacyData {
  name: string;
  value: number;
}

function isLegacyData(data: unknown): data is LegacyData {
  return (
    typeof data === 'object' &&
    data !== null &&
    'name' in data &&
    'value' in data &&
    typeof (data as LegacyData).name === 'string' &&
    typeof (data as LegacyData).value === 'number'
  );
}

function processLegacyData2(data: unknown): string {
  if (!isLegacyData(data)) {
    throw new Error('数据格式无效');
  }
  return `${data.name}: ${data.value}`;
}
使用 // @ts-expect-error 标记待修复项
// @ts-expect-error TODO: 迁移完成后移除，需要定义返回类型
const result = legacyCompute(input);
@ts-expect-error 比 @ts-ignore 更好：当底层问题被修复后，@ts-expect-error 会变成编译错误提醒你移除它。

常见迁移错误及修复
隐式 any 参数
// 错误：Parameter 'item' implicitly has an 'any' type
const process = (item) => item.name;

// 修复
interface Item {
  name: string;
  value: number;
}

const process2 = (item: Item): string => item.name;
对象属性访问
// 错误：Property 'name' does not exist on type '{}'
const config = {};
config.name = 'app';

// 修复
interface AppConfig {
  name: string;
  version?: string;
}

const config2: AppConfig = { name: 'app' };
回调函数类型
// 错误：参数类型隐式 any
setTimeout(function () {
  console.log('done');
}, 1000);

// 修复：箭头函数可正确推断，或显式标注
setTimeout(() => {
  console.log('done');
}, 1000);
动态属性访问
// 错误：Element implicitly has an 'any' type
const lookup: Record<string, number> = { a: 1, b: 2 };
function getValue(key: string): number | undefined {
  return lookup[key];
}
小结
    

  • 推荐使用渐进式迁移策略：先启用 allowJs，逐文件改名，逐步启用严格选项。
    • 

  • 迁移顺序应遵循依赖图自底向上的原则——先迁移工具模块和类型定义，再迁移业务逻辑。
    • 

  • checkJs + JSDoc 可以在不改名文件的前提下为 JavaScript 代码添加类型信息，适合作为迁移的第一步。
    • 

  • 第三方库的类型声明通过 @types/* 安装，无类型的库需要手写 .d.ts 声明文件。
    • 

  • 使用 @ts-expect-error 而非 @ts-ignore 标记待修复项——前者在问题修复后会自动提醒移除。
    • 

  • strictNullChecks 通常是迁移中产生错误最多的选项，建议单独启用并集中修复。
    • 

  • 避免用 any 快速通过编译——优先使用 unknown 加类型守卫，确保迁移带来实质性的类型安全提升。
    • 

  • 在 CI 管道中添加 tsc --noEmit 类型检查，防止迁移成果退化。
