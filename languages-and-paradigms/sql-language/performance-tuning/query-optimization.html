查询优化实践

核心概念

查询优化是从 SQL 编写到数据库配置的全链路优化过程。优化的目标不是让每条查询都最快，而是在系统整体负载下达到最优的资源利用率和响应时间。优化遵循"先测量，后优化"原则——不看执行计划就改 SQL 是盲目的。

常见 SQL 反模式
许多性能问题源自 SQL 编写的不良习惯。识别并消除这些反模式是优化的第一步。


const antiPatterns = `
-- 反模式 1：SELECT *（浪费 I/O 和网络带宽）
-- 差
SELECT * FROM orders WHERE user_id = 100;
-- 好
SELECT order_id, amount, created_at FROM orders WHERE user_id = 100;

-- 反模式 2：索引列上使用函数
-- 差（索引失效）
SELECT * FROM users WHERE YEAR(created_at) = 2024;
-- 好（利用索引范围扫描）
SELECT * FROM users 
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';

-- 反模式 3：隐式类型转换
-- 差（varchar 列与数字比较导致全表扫描）
SELECT * FROM users WHERE phone = 13800138000;
-- 好
SELECT * FROM users WHERE phone = '13800138000';

-- 反模式 4：OR 条件导致索引失效
-- 差
SELECT * FROM orders WHERE user_id = 100 OR status = 1;
-- 好（改写为 UNION ALL）
SELECT * FROM orders WHERE user_id = 100
UNION ALL
SELECT * FROM orders WHERE status = 1 AND user_id <> 100;

-- 反模式 5：NOT IN 子查询包含 NULL
-- 差
SELECT * FROM users WHERE user_id NOT IN (SELECT user_id FROM blocked);
-- 好
SELECT * FROM users u 
WHERE NOT EXISTS (SELECT 1 FROM blocked b WHERE b.user_id = u.user_id);
`;

N+1 查询问题
N+1 问题是应用层最常见的性能杀手：先查询主表获取 N 条记录，然后对每条记录发起一次子查询获取关联数据，总共执行 N+1 次查询。


const nPlusOnePatterns = `
-- N+1 问题（应用层伪代码）
-- 1 次查询获取用户列表
-- SELECT user_id, username FROM users LIMIT 100;
-- 然后对每个用户执行 1 次查询
-- for each user: SELECT COUNT(*) FROM orders WHERE user_id = ?

-- 优化：单次 JOIN 查询
SELECT u.user_id, u.username, COALESCE(o.order_count, 0) AS order_count
FROM users u
LEFT JOIN (
    SELECT user_id, COUNT(*) AS order_count
    FROM orders
    GROUP BY user_id
) o ON u.user_id = o.user_id
LIMIT 100;

-- 或者使用 LATERAL
SELECT u.user_id, u.username, o.order_count
FROM users u
CROSS JOIN LATERAL (
    SELECT COUNT(*) AS order_count
    FROM orders
    WHERE orders.user_id = u.user_id
) o
LIMIT 100;

-- 批量 IN 查询（ORM 常用优化）
-- 将 N 次查询合并为 1 次：
SELECT user_id, COUNT(*) AS order_count
FROM orders
WHERE user_id IN (1, 2, 3, ..., 100)
GROUP BY user_id;
`;
大表查询优化
当表的数据量达到千万级别，常规优化手段可能不够，需要从表结构层面考虑。


const largeTableOptimization = `
-- 分区表（PostgreSQL 声明式分区）
CREATE TABLE orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY,
    user_id BIGINT NOT NULL,
    amount DECIMAL(12, 2),
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2024_q1 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');
CREATE TABLE orders_2024_q2 PARTITION OF orders
    FOR VALUES FROM ('2024-04-01') TO ('2024-07-01');

-- 查询自动命中对应分区（Partition Pruning）
SELECT * FROM orders WHERE created_at >= '2024-03-01';
-- 只扫描 orders_2024_q1，跳过其他分区

-- 归档历史数据
-- 将旧数据移到归档表，保持主表精简
INSERT INTO orders_archive SELECT * FROM orders WHERE created_at < '2023-01-01';
DELETE FROM orders WHERE created_at < '2023-01-01';
VACUUM FULL orders;

-- 物化视图（预计算聚合）
CREATE MATERIALIZED VIEW daily_order_stats AS
SELECT 
    DATE_TRUNC('day', created_at) AS day,
    COUNT(*) AS order_count,
    SUM(amount) AS total_amount,
    COUNT(DISTINCT user_id) AS unique_users
FROM orders
GROUP BY DATE_TRUNC('day', created_at);

-- 定期刷新
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_order_stats;
`;

参数调优
数据库配置参数对查询性能有全局性影响。以下是 PostgreSQL 中最重要的几个参数。


const configTuning = `
-- work_mem：排序和哈希操作的内存限制
-- 默认 4MB，复杂查询可能不够
SET work_mem = '256MB';  -- 会话级别

-- shared_buffers：数据缓存池大小
-- 通常设为物理内存的 25%
-- shared_buffers = '4GB'  -- 需要重启

-- effective_cache_size：告诉优化器可用的缓存总量
-- 设为物理内存的 50-75%
-- effective_cache_size = '12GB'

-- random_page_cost：随机 I/O 相对成本
-- SSD 磁盘设为 1.1-1.5（默认 4.0 适合 HDD）
-- random_page_cost = 1.1

-- 查看当前参数
SHOW work_mem;
SHOW shared_buffers;

-- 查看运行时统计
SELECT * FROM pg_stat_user_tables 
WHERE n_dead_tup > 10000;  -- 需要 VACUUM 的表
`;
参数调优应该基于实际的工作负载分析，而非简单照搬推荐值。使用 pg_stat_statements 收集查询统计，找出消耗资源最多的查询，针对性优化。


小结
    

  • 查询优化遵循"先测量（EXPLAIN ANALYZE），后优化"原则，避免盲目调整
    • 

  • SELECT * 、函数包裹索引列、隐式类型转换是最常见的 SQL 反模式
    • 

  • N+1 查询是应用层最大的性能杀手，通过 JOIN 或批量 IN 查询解决
    • 

  • 大表优化从分区、归档、物化视图和读写分离四个层面考虑
    • 

  • 参数调优关注 work_mem（排序/哈希内存）、shared_buffers（缓存池）和 random_page_cost（SSD 调整）
    • 

  • 使用 pg_stat_statements 定位高消耗查询，针对性优化而非全局调参
    •
