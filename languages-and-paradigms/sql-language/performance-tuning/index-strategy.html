索引策略

核心概念

索引是数据库性能优化的第一道防线。索引通过维护数据的有序结构，将查询从全表扫描（O(N)）降低到对数级别查找（O(log N)）。但索引并非越多越好——每个索引都增加写入开销和存储空间。索引策略的核心是在读性能和写性能之间找到最优平衡点。

复合索引设计
复合索引（Composite Index）包含多个列，其列顺序决定了索引的可用性。理解"最左前缀原则"是设计复合索引的基础。


const compositeIndex = `
-- 复合索引 (a, b, c)
CREATE INDEX idx_abc ON orders(status, user_id, created_at);

-- 可以利用该索引的查询模式
WHERE status = 1                                    -- 使用 (a)
WHERE status = 1 AND user_id = 100                  -- 使用 (a, b)
WHERE status = 1 AND user_id = 100 AND created_at > -- 使用 (a, b, c)
WHERE status = 1 AND created_at > '2024-01-01'      -- 使用 (a)，跳过 b

-- 无法利用该索引的查询
WHERE user_id = 100                                 -- 不以 a 开头
WHERE created_at > '2024-01-01'                     -- 不以 a 开头

-- ESR 规则：Equal → Sort → Range
-- 等值条件列放前面，排序列居中，范围条件列放后面
CREATE INDEX idx_esr ON orders(status, created_at, amount);
-- 完美支持：WHERE status = 1 ORDER BY created_at WHERE amount > 100
`;

覆盖索引与 Index-Only Scan
覆盖索引（Covering Index）包含查询所需的所有列，使数据库无需访问表数据（"回表"），直接从索引返回结果。


const coveringIndex = `
-- 创建覆盖索引（包含查询需要的所有列）
CREATE INDEX idx_covering ON orders(user_id, status) 
    INCLUDE (amount, created_at);

-- 此查询可以完全从索引满足（Index-Only Scan）
SELECT user_id, status, amount, created_at
FROM orders
WHERE user_id = 100 AND status = 1;

-- PostgreSQL INCLUDE 语法（额外列不参与索引排序）
CREATE INDEX idx_user_orders ON orders(user_id) 
    INCLUDE (amount, order_date);

-- 验证是否 Index-Only Scan
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
-- 查看 "Index Only Scan" 或 "Heap Fetches: 0"
`;
覆盖索引的代价是增加了索引大小。INCLUDE 列不参与索引的排序和搜索，只作为额外数据存储在叶子节点中。这比把所有列都放进索引键更高效，因为索引键越短，每个页面能存储的条目越多。


部分索引与表达式索引
部分索引（Partial Index）只对满足条件的行建立索引，减少索引大小和维护开销。表达式索引对函数计算结果建立索引。


const specialIndexes = `
-- 部分索引：只索引活跃记录
CREATE INDEX idx_active_users ON users(email) 
    WHERE status = 1;

-- 效果：对 status = 1 的查询更快，索引更小
SELECT * FROM users WHERE email = 'alice@example.com' AND status = 1;

-- 部分索引：只索引未处理的订单
CREATE INDEX idx_pending_orders ON orders(created_at) 
    WHERE status = 0;

-- 表达式索引：对函数结果建索引
CREATE INDEX idx_lower_email ON users(LOWER(email));
-- 查询必须使用相同的表达式
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';

-- JSONB 表达式索引
CREATE INDEX idx_metadata_type ON events((metadata->>'type'));
SELECT * FROM events WHERE metadata->>'type' = 'click';

-- 唯一部分索引（条件唯一约束）
CREATE UNIQUE INDEX idx_unique_active_email 
    ON users(email) WHERE deleted_at IS NULL;
`;

索引维护与诊断
索引需要持续维护。随着数据的增删改，索引可能出现碎片化（膨胀），性能逐渐下降。


const indexMaintenance = `
-- 查看索引使用情况（PostgreSQL）
SELECT 
    schemaname, tablename, indexname,
    idx_scan AS index_scans,
    idx_tup_read AS tuples_read,
    idx_tup_fetch AS tuples_fetched,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;

-- 查找未使用的索引（浪费空间和写入性能）
SELECT indexname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND schemaname = 'public';

-- 查看索引膨胀
SELECT 
    tablename,
    pg_size_pretty(pg_total_relation_size(tablename::regclass)) AS total_size,
    pg_size_pretty(pg_indexes_size(tablename::regclass)) AS index_size
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY pg_total_relation_size(tablename::regclass) DESC;

-- 重建膨胀的索引
REINDEX INDEX CONCURRENTLY idx_orders_user_id;
`;
定期审查索引：删除未使用的索引减少写入开销，重建膨胀的索引恢复查询性能，合并功能重叠的索引简化维护。


小结
    

  • B-Tree 是默认索引类型，覆盖等值和范围查询；GIN 用于全文搜索和 JSONB；BRIN 适合时序大表
    • 

  • 复合索引遵循 ESR 规则：等值列优先、排序列居中、范围列末尾
    • 

  • 覆盖索引通过 INCLUDE 避免回表，实现 Index-Only Scan
    • 

  • 部分索引只对满足条件的行建索引，显著减少索引大小和维护开销
    • 

  • 表达式索引对函数计算结果建索引，查询必须使用完全相同的表达式
    • 

  • 定期审查未使用索引、重建膨胀索引是索引维护的核心工作
    •
