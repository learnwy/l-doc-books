执行计划解读

核心概念

执行计划（Query Plan）是数据库优化器为 SQL 查询制定的执行方案，描述了数据库如何访问表、如何连接、如何排序以完成查询。阅读执行计划是 SQL 性能调优的基本功——不看执行计划的优化等于盲人摸象。EXPLAIN 命令是获取执行计划的标准工具。

扫描算子
扫描算子是执行计划的叶子节点，决定了如何从表中读取数据。选择哪种扫描方式取决于过滤条件的选择率和索引可用性。


const scanOperators = `
-- 顺序扫描（Seq Scan）：逐行读取整张表
EXPLAIN ANALYZE SELECT * FROM orders WHERE amount > 0;
-- Seq Scan on orders  (cost=0.00..15406.00 rows=500000 width=32)
--   Filter: (amount > 0)
--   Rows Removed by Filter: 1000

-- 索引扫描（Index Scan）：通过索引定位后回表读取
EXPLAIN ANALYZE SELECT * FROM orders WHERE order_id = 12345;
-- Index Scan using orders_pkey on orders  (cost=0.42..8.44 rows=1 width=32)
--   Index Cond: (order_id = 12345)

-- 仅索引扫描（Index Only Scan）：只读索引，不回表
EXPLAIN ANALYZE SELECT user_id FROM orders WHERE user_id = 100;
-- Index Only Scan using idx_orders_user_id on orders  (cost=0.42..4.44 rows=10 width=8)
--   Index Cond: (user_id = 100)
--   Heap Fetches: 0  -- 关键指标：0 表示完全不回表

-- 位图扫描（Bitmap Index Scan + Bitmap Heap Scan）
-- 适用于中等选择率，批量收集行位置再访问表
EXPLAIN ANALYZE SELECT * FROM orders WHERE status IN (1, 2, 3);
-- Bitmap Heap Scan on orders
--   Recheck Cond: (status = ANY ('{1,2,3}'))
--   -> Bitmap Index Scan on idx_orders_status
`;

连接算子
连接算子决定了两个表（或中间结果）如何组合。优化器根据表大小、索引可用性和统计信息选择最优算法。


const joinOperators = `
-- Nested Loop Join：小表驱动大表，内层有索引
EXPLAIN ANALYZE 
SELECT o.*, u.username 
FROM orders o 
JOIN users u ON o.user_id = u.user_id
WHERE o.order_id < 100;
-- Nested Loop  (cost=0.71..812.79 rows=100)
--   -> Index Scan using orders_pkey on orders  (cost=0.29..8.43 rows=100)
--   -> Index Scan using users_pkey on users  (cost=0.42..8.44 rows=1)

-- Hash Join：大表等值连接，无合适索引
EXPLAIN ANALYZE 
SELECT o.*, u.username 
FROM orders o 
JOIN users u ON o.user_id = u.user_id;
-- Hash Join  (cost=1500.00..25000.00 rows=500000)
--   Hash Cond: (o.user_id = u.user_id)
--   -> Seq Scan on orders
--   -> Hash
--        -> Seq Scan on users

-- Merge Join：两个大表，数据已排序
EXPLAIN ANALYZE 
SELECT a.*, b.* 
FROM large_table_a a 
JOIN large_table_b b ON a.sort_key = b.sort_key;
-- Merge Join  (cost=...)
--   Merge Cond: (a.sort_key = b.sort_key)
--   -> Index Scan using idx_a_sort_key on large_table_a
--   -> Index Scan using idx_b_sort_key on large_table_b
`;

关键指标解读
执行计划中的成本和统计信息是判断性能瓶颈的关键依据。


const keyMetrics = `
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT u.username, COUNT(*) AS order_count
FROM users u
JOIN orders o ON u.user_id = o.user_id
WHERE o.created_at >= '2024-01-01'
GROUP BY u.username
ORDER BY order_count DESC
LIMIT 10;

-- 关键指标解读：
-- cost=0.00..15406.00 
--   0.00 = 启动成本（返回第一行前的开销）
--   15406.00 = 总成本（返回所有行的开销）

-- rows=500000
--   估算返回行数（基于统计信息）

-- actual time=0.015..125.432
--   实际执行时间（毫秒）

-- Buffers: shared hit=1234 read=56
--   hit = 缓存命中页数
--   read = 磁盘读取页数
--   高 read 值表示缓存不足
`;




指标
含义
关注点





cost
优化器估算的相对开销
起始成本高 → 排序/哈希耗时




rows
估算/实际行数
估算偏差大 → 统计信息过时




actual time
实际执行毫秒数
总时间 vs 各节点时间




Buffers shared hit
缓存命中页数
高命中率 → I/O 效率好




Buffers shared read
磁盘读取页数
高读取 → I/O 瓶颈




Rows Removed by Filter
被过滤丢弃的行
值很大 → 缺少索引





常见性能问题诊断
通过执行计划可以快速定位几类常见的性能问题。


const diagnosisPatterns = `
-- 问题 1：估算行数严重偏差 → 需要更新统计信息
ANALYZE orders;  -- 更新单表统计
ANALYZE;         -- 更新所有表

-- 问题 2：Seq Scan 在大表上 → 缺少索引或索引失效
-- 检查 WHERE 条件列是否有索引
-- 检查是否有函数/类型转换导致索引失效

-- 问题 3：Sort 节点耗时大 → 缺少排序索引
-- Sort  (cost=...)  Sort Method: external merge  Disk: 102400kB
-- 解决：为 ORDER BY 列创建索引

-- 问题 4：Hash 节点内存溢出 → work_mem 不足
-- Hash  (cost=...)  Batches: 8  Memory Usage: 32768kB
-- 解决：SET work_mem = '256MB'; （会话级别调整）

-- 问题 5：大量 Heap Fetches → 索引不覆盖或 VACUUM 不足
-- 解决：创建覆盖索引或运行 VACUUM
VACUUM ANALYZE orders;
`;
诊断流程的核心思路：先看总耗时定位瓶颈节点，再看该节点的扫描类型和行数，最后对症下药（加索引、更新统计、调参数）。


小结
    

  • EXPLAIN ANALYZE 是性能诊断的第一步，BUFFERS 选项帮助定位 I/O 瓶颈
    • 

  • 扫描类型选择取决于选择率：< 5% 用 Index Scan，5-20% 用 Bitmap Scan，> 20% 用 Seq Scan
    • 

  • 连接算法三选一：Nested Loop（小结果集+索引）、Hash Join（大表等值）、Merge Join（已排序）
    • 

  • 估算行数与实际行数的偏差表示统计信息过时，需要运行 ANALYZE
    • 

  • Rows Removed by Filter 值很大说明缺少索引，数据在表扫描后才被过滤
    • 

  • work_mem 不足导致排序和哈希溢出到磁盘，按需在会话级别调整
    •
