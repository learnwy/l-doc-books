事务与并发控制

核心概念

事务（Transaction）是数据库操作的基本逻辑单元，保证一组操作要么全部成功，要么全部回滚。ACID 特性是事务的理论基石，而隔离级别则决定了并发事务之间的可见性规则。理解事务与并发控制是编写可靠数据库应用的前提——没有正确的事务管理，数据一致性无从谈起。

事务基本操作
事务的生命周期由 BEGIN、COMMIT、ROLLBACK 控制。SAVEPOINT 提供了事务内的部分回滚能力。


const transactionBasics = `
-- 基本事务
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT;

-- 出错时回滚
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
-- 如果下一步失败，之前的更新也会撤销
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
ROLLBACK;  -- 两个 UPDATE 都不生效

-- SAVEPOINT：事务内的检查点
BEGIN;
INSERT INTO orders (user_id, amount) VALUES (1, 500);
SAVEPOINT sp1;

INSERT INTO order_items (order_id, product_id, qty) VALUES (1, 100, 2);
-- 如果这步失败，可以只回滚到 savepoint
ROLLBACK TO SAVEPOINT sp1;
-- order 仍然存在，但 order_items 被回滚

INSERT INTO order_items (order_id, product_id, qty) VALUES (1, 200, 1);
COMMIT;  -- order + 新的 order_item 一起提交
`;
事务的持续时间（事务长度）直接影响并发性能。长事务持有锁时间越长，其他事务等待的时间越长。原则是事务尽可能短——只在真正需要原子性的操作之间开启事务。


并发异常与隔离级别
不同的隔离级别防止不同类型的并发异常。理解这些异常的本质有助于选择合适的隔离级别。


const concurrencyAnomalies = `
-- 脏读（Dirty Read）：读到未提交的数据
-- 事务 A: UPDATE products SET stock = 0 WHERE id = 1; (未提交)
-- 事务 B: SELECT stock FROM products WHERE id = 1;  → 读到 0（脏数据）
-- 事务 A: ROLLBACK;  → stock 恢复原值，但 B 已经基于错误数据做了决策

-- 不可重复读（Non-Repeatable Read）：同一事务内两次读取结果不同
-- 事务 A: SELECT price FROM products WHERE id = 1;  → 100
-- 事务 B: UPDATE products SET price = 200 WHERE id = 1; COMMIT;
-- 事务 A: SELECT price FROM products WHERE id = 1;  → 200（同一事务内值变了）

-- 幻读（Phantom Read）：同一事务内范围查询结果集变化
-- 事务 A: SELECT COUNT(*) FROM orders WHERE user_id = 1;  → 5
-- 事务 B: INSERT INTO orders (user_id, amount) VALUES (1, 100); COMMIT;
-- 事务 A: SELECT COUNT(*) FROM orders WHERE user_id = 1;  → 6（多了一行"幻影"）
`;

MVCC 机制
多版本并发控制（MVCC）是 PostgreSQL 和 MySQL/InnoDB 实现事务隔离的核心机制。MVCC 通过为每一行维护多个版本来避免读写冲突——读操作不阻塞写操作，写操作不阻塞读操作。


const mvccExplanation = `
-- PostgreSQL MVCC：每行有 xmin/xmax 系统列
-- xmin = 创建该行版本的事务 ID
-- xmax = 删除/更新该行版本的事务 ID（0 表示未删除）

-- 查看行的版本信息
SELECT xmin, xmax, * FROM products WHERE product_id = 1;

-- UPDATE 在 MVCC 中的实际操作：
-- 1. 将旧行标记为已删除（设置 xmax）
-- 2. 插入一个新版本的行（新 xmin）
-- 3. 旧版本对尚未提交的事务仍然可见

-- 这就是为什么 PostgreSQL 需要 VACUUM：
-- 旧版本不会立即删除，需要 VACUUM 清理
VACUUM ANALYZE products;
-- autovacuum 通常能自动处理，但大批量更新后可能需要手动触发
`;
MVCC 的优势是高并发下的读写不互相阻塞，但代价是额外的存储空间和清理工作。PostgreSQL 的 autovacuum 机制自动清理旧版本，但配置不当可能导致表膨胀。MySQL/InnoDB 使用 undo log 存储旧版本，purge 线程负责清理。


锁与死锁
当 MVCC 无法解决冲突时（如两个事务同时修改同一行），数据库使用锁来保证一致性。


const lockingPatterns = `
-- 行级锁（最常见）
-- SELECT ... FOR UPDATE：获取排他锁，阻止其他事务修改
BEGIN;
SELECT * FROM accounts WHERE account_id = 1 FOR UPDATE;
-- 此时其他事务对 account_id = 1 的 FOR UPDATE 会阻塞
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
COMMIT;

-- SELECT ... FOR SHARE：获取共享锁，阻止修改但允许其他 FOR SHARE
SELECT * FROM products WHERE product_id = 1 FOR SHARE;

-- SKIP LOCKED：跳过已被锁定的行（任务队列模式）
SELECT * FROM tasks 
WHERE status = 'pending' 
ORDER BY created_at 
LIMIT 1 
FOR UPDATE SKIP LOCKED;

-- NOWAIT：如果无法立即获取锁则报错（不等待）
SELECT * FROM accounts WHERE account_id = 1 FOR UPDATE NOWAIT;

-- 死锁示例：
-- 事务 A: UPDATE accounts SET ... WHERE id = 1; (获取行 1 的锁)
-- 事务 B: UPDATE accounts SET ... WHERE id = 2; (获取行 2 的锁)
-- 事务 A: UPDATE accounts SET ... WHERE id = 2; (等待行 2 → 死锁)
-- 事务 B: UPDATE accounts SET ... WHERE id = 1; (等待行 1 → 死锁)

-- 防止死锁：始终按相同顺序获取锁
BEGIN;
SELECT * FROM accounts WHERE account_id IN (1, 2) ORDER BY account_id FOR UPDATE;
-- 按 ID 升序锁定，所有事务遵循同一顺序
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT;
`;

小结
    

  • ACID 是事务的理论基石，隔离级别决定并发事务的可见性规则
    • 

  • READ COMMITTED 是 PostgreSQL 默认隔离级别，REPEATABLE READ 是 MySQL/InnoDB 默认级别
    • 

  • MVCC 通过维护行的多个版本实现读写不互相阻塞，是现代数据库的核心并发控制机制
    • 

  • 事务应尽可能短，长事务持有锁时间过长会严重影响并发性能
    • 

  • FOR UPDATE 获取排他锁保证先读后改的一致性，SKIP LOCKED 适合任务队列模式
    • 

  • 防止死锁的基本策略是所有事务按相同顺序获取锁
    • 

  • PostgreSQL 需要 VACUUM 清理 MVCC 旧版本，MySQL 由 purge 线程自动处理
    •
