数据类型与 DDL

核心概念

SQL（Structured Query Language）的数据定义语言（DDL）是构建数据库结构的基础。DDL 负责创建、修改和删除数据库对象——表、索引、视图和约束。理解数据类型是编写高效 SQL 的前提：选择合适的数据类型不仅影响存储效率，还直接决定查询性能和数据完整性。

数值类型精度选择
数值类型的选择是最容易犯错的地方。FLOAT 和 DOUBLE 使用 IEEE 754 浮点表示，存在精度损失问题，在金融等对精度要求严格的场景中必须使用 DECIMAL（也称 NUMERIC）。


// DECIMAL vs FLOAT 的精度差异
// DECIMAL(10, 2) — 精确存储，适合金额
// FLOAT — 近似存储，0.1 + 0.2 可能不等于 0.3

// 正确的金额字段定义
const createOrderTable = `
CREATE TABLE orders (
    order_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    amount      DECIMAL(12, 2) NOT NULL CHECK (amount >= 0),
    discount    DECIMAL(5, 4) DEFAULT 0.0000,
    created_at  TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);
`;

// 错误示范：用 FLOAT 存储金额
// CREATE TABLE orders (amount FLOAT) — 会导致精度丢失
整数类型的选择影响存储效率和范围。SMALLINT（2字节，±32767）适合枚举值和状态码，INT（4字节，±21亿）覆盖大部分场景，BIGINT（8字节）用于大规模 ID 生成：

表创建与约束体系
表创建不仅是定义列和类型，更重要的是通过约束（Constraints）保证数据完整性。约束是数据库层面的防御机制，比应用层验证更可靠。


const createUserTable = `
CREATE TABLE users (
    user_id     BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       VARCHAR(255) NOT NULL UNIQUE,
    username    VARCHAR(50) NOT NULL,
    status      SMALLINT NOT NULL DEFAULT 1 CHECK (status IN (0, 1, 2)),
    created_at  TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    
    CONSTRAINT chk_email_format 
        CHECK (email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}$')
);

CREATE TABLE user_profiles (
    profile_id  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     BIGINT NOT NULL UNIQUE,
    bio         TEXT,
    avatar_url  VARCHAR(500),
    
    CONSTRAINT fk_user 
        FOREIGN KEY (user_id) REFERENCES users(user_id) 
        ON DELETE CASCADE ON UPDATE CASCADE
);
`;

ALTER 与在线 DDL
生产环境中的 DDL 变更需要特别谨慎。ALTER TABLE 在不同数据库中的行为差异很大——某些操作可能导致长时间的表锁定。


// 安全的 ALTER 操作（大多数数据库中不锁表）
const safeAlters = `
ALTER TABLE users ADD COLUMN phone VARCHAR(20);
ALTER TABLE users ALTER COLUMN phone SET DEFAULT '';
ALTER TABLE users ADD CONSTRAINT chk_phone CHECK (phone ~ '^\\+?[0-9]{7,15}$');
`;

// 危险的 ALTER 操作（可能导致表重建/长时间锁）
const riskyAlters = `
ALTER TABLE users ALTER COLUMN username TYPE VARCHAR(100);  -- 类型变更可能重建表
ALTER TABLE users ADD COLUMN score INT NOT NULL DEFAULT 0;  -- NOT NULL + DEFAULT 在大表上耗时
`;

// PostgreSQL 安全变更策略：分步操作
const safeTypeChange = `
-- 1. 添加新列
ALTER TABLE users ADD COLUMN username_new VARCHAR(100);
-- 2. 批量迁移数据（分批更新，避免长事务）
UPDATE users SET username_new = username WHERE user_id BETWEEN 1 AND 10000;
-- 3. 交换列（在低峰期）
ALTER TABLE users DROP COLUMN username;
ALTER TABLE users RENAME COLUMN username_new TO username;
`;
不同数据库对在线 DDL 的支持差异显著。MySQL 8.0+ 支持大部分 ALGORITHM=INSTANT 操作（如添加列到末尾），PostgreSQL 的 ALTER TABLE ADD COLUMN 如果有 DEFAULT 值在 11+ 版本中是即时操作。


IDENTITY 与序列
自增 ID 的实现方式因数据库而异。传统的 AUTO_INCREMENT（MySQL）和 SERIAL（PostgreSQL 旧版）逐渐被 SQL 标准的 GENERATED AS IDENTITY 取代。


// SQL 标准方式（PostgreSQL 10+, SQL Server, DB2）
const identityColumn = `
CREATE TABLE events (
    event_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_type VARCHAR(50) NOT NULL
);
`;

// 显式序列管理（更灵活）
const sequenceApproach = `
CREATE SEQUENCE order_seq 
    START WITH 1000 
    INCREMENT BY 1 
    NO CYCLE 
    CACHE 20;

CREATE TABLE orders (
    order_id BIGINT DEFAULT nextval('order_seq') PRIMARY KEY,
    amount DECIMAL(12, 2) NOT NULL
);
`;

// 分布式环境：自定义 ID 生成
// 雪花算法等方案在应用层生成，数据库只存储 BIGINT
使用 GENERATED ALWAYS 而非 GENERATED BY DEFAULT 可以防止应用层意外覆盖 ID 值。序列的 CACHE 参数影响并发性能——值越大并发插入越快，但进程崩溃时可能产生 ID 间隙。


小结
    

  • 数据类型选择直接影响存储效率、查询性能和数据正确性，金额字段必须使用 DECIMAL
    • 

  • DDL 约束（PRIMARY KEY、FOREIGN KEY、CHECK、UNIQUE、NOT NULL）是数据完整性的数据库级防线
    • 

  • 外键级联策略（CASCADE、SET NULL、RESTRICT 等）决定了关联数据的维护行为
    • 

  • 生产环境 ALTER TABLE 需要评估锁影响，大表变更建议分步操作
    • 

  • GENERATED AS IDENTITY 是 SQL 标准的自增方案，优于传统的 AUTO_INCREMENT / SERIAL
    • 

  • 序列的 CACHE 参数在并发性能和 ID 连续性之间做权衡
    •
