条件过滤与排序

核心概念

WHERE 子句和 ORDER BY 子句是 SQL 查询中控制"选哪些数据"和"按什么顺序返回"的核心机制。WHERE 通过布尔条件过滤行，ORDER BY 对结果集排序。高效的过滤和排序直接依赖索引设计——一个没有索引支持的 WHERE 条件意味着全表扫描。

比较与范围过滤
基础比较运算符是 WHERE 条件的基石。组合使用多个条件时，AND 和 OR 的优先级以及索引利用率是关键。


const filterExamples = `
-- 等值过滤（最高效，直接命中索引）
SELECT * FROM users WHERE user_id = 12345;
SELECT * FROM users WHERE email = 'alice@example.com';

-- 范围过滤
SELECT * FROM orders 
WHERE created_at >= '2024-01-01' 
  AND created_at < '2024-02-01';

-- BETWEEN 等价于 >= AND <=
SELECT * FROM products 
WHERE price BETWEEN 100 AND 500;

-- IN 列表（优化器通常展开为多个 OR 或使用哈希查找）
SELECT * FROM orders 
WHERE status IN (1, 2, 5);

-- NOT IN 的陷阱：如果列表包含 NULL，结果为空
-- NOT IN (1, 2, NULL) 对任何值都返回 UNKNOWN
-- 安全替代：NOT EXISTS
SELECT * FROM products p
WHERE NOT EXISTS (
    SELECT 1 FROM blacklist b WHERE b.product_id = p.product_id
);
`;
AND 条件可以被复合索引有效利用，而 OR 条件通常需要索引合并（Index Merge）或改写为 UNION：

LIKE 模式匹配
LIKE 运算符用于字符串模式匹配。% 匹配任意字符序列，_ 匹配单个字符。前缀匹配（'abc%'）可以利用 B-Tree 索引，而中缀或后缀匹配需要全表扫描。


const patternMatching = `
-- 前缀匹配（可利用索引）
SELECT * FROM users WHERE username LIKE '张%';

-- 后缀匹配（无法利用普通索引）
SELECT * FROM users WHERE email LIKE '%@gmail.com';

-- 包含匹配（全表扫描）
SELECT * FROM products WHERE description LIKE '%蓝牙%';

-- 转义特殊字符
SELECT * FROM logs WHERE message LIKE '%100\%%' ESCAPE '\\';

-- PostgreSQL 正则匹配（更强大但更慢）
SELECT * FROM users WHERE email ~ '^[a-z]+@gmail\\.com$';

-- 全文搜索替代 LIKE（PostgreSQL）
SELECT * FROM articles 
WHERE to_tsvector('chinese', content) @@ to_tsquery('chinese', '机器学习');
`;
对于频繁的模糊搜索需求，PostgreSQL 的 pg_trgm 扩展提供了 GIN/GiST 索引支持，可以加速 LIKE '%keyword%' 类查询。这是将全表扫描转变为索引扫描的有效方案。


ORDER BY 排序策略
ORDER BY 定义结果集的排列顺序。每个排序表达式可以独立指定 ASC（升序，默认）或 DESC（降序），以及 NULL 值的位置。


const orderByExamples = `
-- 基础排序
SELECT * FROM products ORDER BY price ASC;
SELECT * FROM products ORDER BY created_at DESC;

-- 多列排序（先按 category 升序，同 category 内按 price 降序）
SELECT * FROM products 
ORDER BY category_id ASC, price DESC;

-- NULL 排序控制
SELECT * FROM users 
ORDER BY last_login DESC NULLS LAST;

-- 表达式排序
SELECT *, (price * (1 - discount_rate)) AS final_price
FROM products
ORDER BY final_price ASC;

-- 条件排序（CASE 在 ORDER BY 中）
SELECT * FROM tasks
ORDER BY 
    CASE priority
        WHEN 'critical' THEN 1
        WHEN 'high' THEN 2
        WHEN 'medium' THEN 3
        WHEN 'low' THEN 4
    END ASC,
    created_at ASC;

-- 排序规则（Collation）影响字符串排序
SELECT * FROM users ORDER BY username COLLATE "zh_CN.utf8";
`;
ORDER BY 的性能与索引密切相关。如果 ORDER BY 的列与 WHERE 条件的列可以被同一个复合索引覆盖，数据库可以直接按索引顺序返回结果，避免额外排序：

分页与 LIMIT
LIMIT/OFFSET 是最常用的分页方式，但在大偏移量时性能急剧下降，因为数据库需要扫描并丢弃 OFFSET 行。


const paginationPatterns = `
-- 基础分页（小数据量可用）
SELECT * FROM products 
ORDER BY product_id
LIMIT 20 OFFSET 0;    -- 第 1 页

SELECT * FROM products 
ORDER BY product_id
LIMIT 20 OFFSET 100;  -- 第 6 页

-- 大偏移量性能问题：OFFSET 10000 需要扫描前 10000 行
-- Keyset 分页（游标分页）— 性能恒定
SELECT * FROM products 
WHERE product_id > 10000   -- 上一页最后一条的 ID
ORDER BY product_id
LIMIT 20;

-- 复合排序键的 Keyset 分页
SELECT * FROM products
WHERE (created_at, product_id) > ('2024-01-15', 5678)
ORDER BY created_at, product_id
LIMIT 20;

-- FETCH FIRST（SQL 标准语法）
SELECT * FROM products 
ORDER BY price DESC
FETCH FIRST 10 ROWS ONLY;
`;

小结
    

  • WHERE 条件的索引利用率决定查询性能，AND 条件适合复合索引，OR 条件可能需要改写为 UNION
    • 

  • NOT IN 包含 NULL 值时会导致空结果集，应使用 NOT EXISTS 替代
    • 

  • LIKE 只有前缀匹配能利用 B-Tree 索引，模糊搜索建议使用全文搜索或 pg_trgm
    • 

  • ORDER BY 与 WHERE 共享复合索引可以避免额外排序操作
    • 

  • LIMIT/OFFSET 在大偏移量时性能差，Keyset 分页（游标分页）是大数据集的标准方案
    • 

  • NULL 在排序中默认位置因数据库而异，建议显式指定 NULLS FIRST / NULLS LAST
    •
