脚本测试

核心概念

Shell 脚本测试长期以来被视为不切实际的追求，但随着 DevOps 和基础设施即代码（IaC）的普及，脚本的可靠性要求越来越高。现代 Shell 测试框架（如 Bats、shunit2、ShellSpec）提供了与传统编程语言测试框架类似的能力，使得编写可测试的 Shell 脚本成为工程实践的标准。

编写可测试的 Shell 脚本需要从架构层面做出调整：将逻辑封装在函数中、避免全局副作用、将外部依赖注入化。这些原则与其他编程语言中的测试最佳实践完全一致。

可测试性设计

使脚本可测试的核心原则是将业务逻辑封装在纯函数中：

calculate_disk_usage() {
    local path="$1"
    local threshold="${2:-80}"

    local usage
    usage=$(df "$path" | awk 'NR==2 {print $5}' | tr -d '%')

    if (( usage >= threshold )); then
        echo "WARNING: ${path} 使用率 ${usage}% 超过阈值 ${threshold}%"
        return 1
    fi

    echo "OK: ${path} 使用率 ${usage}%"
    return 0
}

parse_version() {
    local version="$1"

    if [[ ! "$version" =~ ^v?([0-9]+)\.([0-9]+)\.([0-9]+)(.*)$ ]]; then
        echo "无效版本号: $version" >&2
        return 1
    fi

    echo "${BASH_REMATCH[1]} ${BASH_REMATCH[2]} ${BASH_REMATCH[3]}"
}

纯逻辑函数：版本比较

parse_version 用 BASH_REMATCH 提取主次修订号，compare_versions 在此基础上逐段比较——两者都只依赖入参、无副作用，因此极易测试：

compare_versions() {
    local v1="$1" v2="$2"

    local -a parts1 parts2
    read -ra parts1 <<< "$(parse_version "$v1")" || return 2
    read -ra parts2 <<< "$(parse_version "$v2")" || return 2

    for i in 0 1 2; do
        if (( parts1[i] > parts2[i] )); then
            echo "greater"
            return 0
        elif (( parts1[i] < parts2[i] )); then
            echo "lesser"
            return 0
        fi
    done

    echo "equal"
    return 0
}

配置校验函数

validate_config 把所有错误收集进数组后一次性返回，而非遇错即退——这种「累积错误」风格让测试能一次断言多种缺陷：

validate_config() {
    local config_file="$1"
    local errors=()

    [[ -f "$config_file" ]] || { echo "配置文件不存在"; return 1; }

    local port host
    port=$(grep '^PORT=' "$config_file" | cut -d= -f2)
    host=$(grep '^HOST=' "$config_file" | cut -d= -f2)

    [[ -n "$port" ]] || errors+=("缺少 PORT 配置")
    [[ -n "$host" ]] || errors+=("缺少 HOST 配置")

    if [[ -n "$port" ]] && ! [[ "$port" =~ ^[0-9]+$ ]]; then
        errors+=("PORT 必须是数字: $port")
    fi

    if (( ${#errors[@]} > 0 )); then
        printf '%s\n' "${errors[@]}"
        return 1
    fi

    echo "配置验证通过"
    return 0
}

Bats 测试框架

Bats（Bash Automated Testing System）是最流行的 Shell 测试框架。

结构 作用
setup() 每个用例前的初始化
teardown() 每个用例后的清理
@test "..." 定义一个测试用例
run cmd 捕获命令的 status 与 output
assert_success / assert_failure 断言退出码
assert_output 断言 stdout 内容

Bats 测试示例

#!/usr/bin/env bats

setup() {
    load 'test_helper/bats-support/load'
    load 'test_helper/bats-assert/load'

    source "${BATS_TEST_DIRNAME}/../lib/utils.sh"

    TEST_TEMP_DIR=$(mktemp -d)
}

teardown() {
    rm -rf "$TEST_TEMP_DIR"
}

@test "parse_version 解析标准版本号" {
    run parse_version "v1.2.3"
    assert_success
    assert_output "1 2 3"
}

@test "parse_version 拒绝无效版本号" {
    run parse_version "invalid"
    assert_failure
    assert_output --partial "无效版本号"
}

@test "compare_versions 正确比较版本" {
    run compare_versions "v2.0.0" "v1.9.9"
    assert_success
    assert_output "greater"

    run compare_versions "v1.0.0" "v1.0.0"
    assert_success
    assert_output "equal"

    run compare_versions "v1.0.0" "v1.0.1"
    assert_success
    assert_output "lesser"
}

@test "validate_config 验证有效配置" {
    cat > "$TEST_TEMP_DIR/config.env" << 'EOF'
PORT=8080
HOST=localhost
EOF

    run validate_config "$TEST_TEMP_DIR/config.env"
    assert_success
    assert_output "配置验证通过"
}

@test "validate_config 检测缺少字段" {
    cat > "$TEST_TEMP_DIR/config.env" << 'EOF'
HOST=localhost
EOF

    run validate_config "$TEST_TEMP_DIR/config.env"
    assert_failure
    assert_output --partial "缺少 PORT"
}

@test "validate_config 检测非法端口" {
    cat > "$TEST_TEMP_DIR/config.env" << 'EOF'
PORT=abc
HOST=localhost
EOF

    run validate_config "$TEST_TEMP_DIR/config.env"
    assert_failure
    assert_output --partial "PORT 必须是数字"
}

Mock 与依赖注入

Shell 中的 Mock 主要有两种实现路径，分别适用于不同的依赖类型。

Mock 方式 适用场景 原理
函数覆盖 替换 curl、date 等命令 同名函数遮蔽外部命令，export -f 传递给子进程
临时 PATH 注入 替换 docker 等可执行文件 在 $TEST_TEMP_DIR 放置假二进制并前置到 PATH

函数覆盖与 PATH 注入

Shell 中的 Mock 通过函数覆盖或临时 PATH 注入实现：

mock_curl() {
    case "$*" in
        *health*)
            echo '{"status":"ok"}'
            return 0
            ;;
        *error*)
            echo '{"error":"not found"}'
            return 1
            ;;
    esac
}

@test "health check 在服务正常时返回成功" {
    curl() { mock_curl "$@"; }
    export -f curl

    run check_health "http://localhost:8080/health"
    assert_success
}

@test "health check 在服务异常时返回失败" {
    curl() { echo "Connection refused"; return 7; }
    export -f curl

    run check_health "http://localhost:8080/health"
    assert_failure
}

setup_mock_commands() {
    MOCK_BIN="$TEST_TEMP_DIR/mock_bin"
    mkdir -p "$MOCK_BIN"

    cat > "$MOCK_BIN/docker" << 'MOCK'
#!/bin/bash
echo "mock: docker $*" >> "$MOCK_LOG"
echo "mock-container-id"
MOCK
    chmod +x "$MOCK_BIN/docker"

    export PATH="$MOCK_BIN:$PATH"
    export MOCK_LOG="$TEST_TEMP_DIR/mock.log"
}

@test "deploy 调用正确的 docker 命令" {
    setup_mock_commands

    run deploy "production" "v1.2.3"
    assert_success

    assert [ -f "$MOCK_LOG" ]
    run grep "docker.*production.*v1.2.3" "$MOCK_LOG"
    assert_success
}

测试组织与 CI 集成

测试项目的目录结构和 CI 集成方式：

project/
├── lib/
│   ├── utils.sh
│   ├── deploy.sh
│   └── config.sh
├── bin/
│   └── mytool
├── test/
│   ├── test_helper/
│   │   ├── bats-support/
│   │   └── bats-assert/
│   ├── setup_suite.bash
│   ├── utils.bats
│   ├── deploy.bats
│   └── config.bats
└── Makefile
.PHONY: test test-unit test-integration lint

test: lint test-unit

test-unit:
	bats test/*.bats

test-integration:
	bats test/integration/*.bats

lint:
	shellcheck lib/*.sh bin/*
	shfmt -d lib/*.sh bin/*

setup-test:
	git submodule update --init test/test_helper/bats-support
	git submodule update --init test/test_helper/bats-assert

CI 集成

CI 集成（GitHub Actions）：

name: Shell Tests
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          submodules: true

      - name: Install dependencies
        run: |
          sudo apt-get install -y bats shellcheck shfmt

      - name: Lint
        run: make lint

      - name: Unit Tests
        run: make test-unit

      - name: Integration Tests
        run: make test-integration

常见陷阱

让 Shell 脚本可测试需要架构上的克制，下表列出阻碍测试的几类常见反模式。

反模式 问题 改进方式
逻辑与 IO 混在一起 无法在不触发副作用下测试 纯函数 + 薄 IO 外壳
直接调用外部命令 测试依赖真实环境 函数覆盖或 PATH 注入 Mock
全局变量驱动流程 用例间状态泄漏 参数传入、local 隔离
不写 teardown 临时文件/Mock 残留 teardown() 清理
只测正常路径 边界与错误分支无覆盖 三类场景都要测

小结

  • 可测试的 Shell 脚本应将逻辑封装在纯函数中，与 IO 操作分离
  • Bats 是最流行的 Shell 测试框架，配合 bats-assert 和 bats-support 插件提供丰富的断言
  • Mock 通过函数覆盖或临时 PATH 注入实现，用于隔离外部依赖
  • setup() 和 teardown() 函数用于测试前后的资源初始化和清理
  • ShellCheck 用于静态分析，shfmt 用于格式化——两者是 Shell 代码质量的基础工具
  • 测试应覆盖正常路径、边界条件和错误路径三种场景
  • CI 集成确保每次提交都经过 lint + 测试验证
  • 复杂脚本的集成测试建议使用 Docker 容器作为隔离环境
