实时分析与流处理

核心概念

实时分析（Real-Time Analytics）是电商数据基础设施中对时效性要求最高的部分。与传统 T+1 批量处理不同，实时分析追求秒级到分钟级的数据可见性。在大促场景中，运营团队需要实时观察 GMV 增长曲线、库存消耗速度、支付成功率等关键指标；风控团队需要毫秒级响应异常交易；推荐系统需要根据用户最近行为实时调整推荐结果。

实时分析体系的核心挑战在于：保证数据的准确性（Exactly-Once 语义）、应对流量峰值（大促期间数据量可能是平时的 10-50 倍）、平衡延迟与吞吐量、以及与离线数仓的数据一致性校验。

Kafka 消息队列架构
Kafka 在电商实时分析中扮演数据总线的角色，连接数据源和流处理引擎。所有业务事件（订单创建、支付成功、物流状态变更、用户行为日志）统一写入 Kafka Topic，下游消费者按需订阅。


Topic 设计需要平衡粒度和管理成本。电商常见的做法是按业务域划分 Topic：order-events、payment-events、user-behavior、inventory-changes 等。每个 Topic 内部按分区（Partition）实现并行消费，分区键通常选择用户 ID 或订单 ID 以保证同一实体的事件有序。


interface KafkaTopicConfig {
  name: string;
  partitions: number;
  replicationFactor: number;
  retentionMs: number;
  partitionKey: string;
  schema: string;
}

Kafka 生产端需要关注消息可靠性。电商交易数据不能丢失，必须设置 acks=all（所有副本确认写入）和 enable.idempotence=true（幂等性）。行为日志可以容忍少量丢失，设置 acks=1 换取更高吞吐。


大促期间 Kafka 的容量规划是关键。需要根据历史数据预估峰值 QPS，按 2-3 倍冗余配置分区数和 Broker 资源。监控消费者 Lag（积压量），一旦积压超过阈值立即扩容消费者实例。


Flink 流处理引擎
Apache Flink 是电商实时分析的主流流处理引擎。它的核心优势在于：真正的流处理（非微批）、精确一次语义（Exactly-Once）、丰富的窗口操作（滚动/滑动/会话窗口）、以及强大的状态管理能力。


电商场景中 Flink 的典型应用包括：

状态管理是 Flink 在电商场景中的核心难点。例如实时去重（同一个订单事件可能因重试发送多次）、实时 JOIN（订单事件和支付事件的关联）、CEP 复杂事件处理（检测欺诈行为模式）都依赖 Flink 的有状态计算能力。状态后端选择 RocksDB 支撑大状态量，Checkpoint 间隔根据业务容忍度设置（交易类 10-60 秒，行为类 60-300 秒）。


ClickHouse 实时 OLAP 引擎
ClickHouse 是电商实时分析的终端查询引擎。Flink 处理后的聚合数据写入 ClickHouse，BI 看板和分析系统直接查询 ClickHouse 获取实时指标。


ClickHouse 的核心优势在于列式存储和向量化执行。电商场景中，查询通常只涉及少数列（如 SUM(amount) GROUP BY channel, category），列式存储可以跳过无关列，大幅减少 IO。向量化执行利用 CPU SIMD 指令批量处理数据，聚合性能极强。


interface ClickHouseTableConfig {
  name: string;
  engine: string;
  partition_by: string;
  order_by: string[];
  ttl: string;
  settings: Record<string, string | number>;
}

const realtimeTables: ClickHouseTableConfig[] = [
  {
    name: 'ads_realtime_gmv',
    engine: 'ReplacingMergeTree(update_time)',
    partition_by: 'toYYYYMMDD(dt)',
    order_by: ['dt', 'minute', 'channel', 'category_l1'],
    ttl: 'dt + INTERVAL 90 DAY',
    settings: {
      index_granularity: 8192,
      merge_with_ttl_timeout: 86400,
    },
  },
  {
    name: 'ads_realtime_funnel',
    engine: 'AggregatingMergeTree()',
    partition_by: 'toYYYYMMDD(dt)',
    order_by: ['dt', 'funnel_name', 'channel'],
    ttl: 'dt + INTERVAL 30 DAY',
    settings: {
      index_granularity: 8192,
    },
  },
];
MergeTree 引擎家族是 ClickHouse 的核心。电商实时表常用 ReplacingMergeTree（按主键去重，适合幂等写入）和 AggregatingMergeTree（预聚合，适合高频更新的指标表）。分区按天划分，TTL 自动清理历史数据，排序键（ORDER BY）按查询模式设计以加速扫描。


实时写入 ClickHouse 需要注意批量化。不能逐条 INSERT，而是通过 Buffer 引擎或在 Flink Sink 端聚合后批量写入（每秒 1-10 次，每次 1000-10000 行），避免产生大量小 Part 影响查询性能。


Lambda 与 Kappa 架构选型
电商实时数仓的架构选型通常在 Lambda 和 Kappa 之间抉择。


Lambda 架构维护两条数据链路：批处理链路（Spark/Hive → 离线数仓）保证数据准确性，流处理链路（Flink → 实时层）保证时效性。查询层合并两条链路的结果。优点是准确性有保障，缺点是维护两套逻辑成本高、数据口径可能不一致。


Kappa 架构只维护一条流处理链路。所有数据先写入 Kafka（长期保留），下游统一用 Flink 消费。需要重算时，从 Kafka 历史 Offset 重放。优点是逻辑统一，缺点是大规模重算代价高。


interface ArchitectureDecision {
  scenario: string;
  recommendation: 'lambda' | 'kappa' | 'hybrid';
  rationale: string;
}

const architectureGuide: ArchitectureDecision[] = [
  {
    scenario: '核心交易指标（GMV/订单量）',
    recommendation: 'lambda',
    rationale: '准确性要求极高，需要离线链路兜底校验',
  },
  {
    scenario: '实时风控',
    recommendation: 'kappa',
    rationale: '纯实时场景，无需离线对账',
  },
  {
    scenario: '用户行为分析',
    recommendation: 'hybrid',

现代电商实践中，混合架构（Hybrid）最为常见：核心交易指标采用 Lambda 双链路保证准确性，行为分析和推荐特征采用 Kappa 简化维护。两种架构共享 Kafka 作为数据总线，Flink 作为流处理引擎，区别在于是否有离线链路兜底。

小结
    

  • 实时分析是电商数据基础设施的关键能力，核心架构为 Kafka（数据总线）→ Flink（流处理）→ ClickHouse（实时 OLAP）
    • 

  • Kafka 的 Topic 设计按业务域划分，分区键选择保证同一实体事件有序，大促期间需要 2-3 倍容量冗余
    • 

  • Flink 提供真正的流处理和精确一次语义，窗口机制（滚动/滑动/会话）覆盖电商实时聚合的主要场景
    • 

  • ClickHouse 的列式存储和向量化执行使其成为实时 OLAP 的首选，写入端需要批量化避免小 Part 问题
    • 

  • Lambda 和 Kappa 架构各有优劣，电商实践中混合架构最为常见——核心指标走 Lambda，行为分析走 Kappa
    • 

  • 大促是实时分析体系的终极考验，容量规划、消费者弹性扩容、限流降级策略缺一不可
    •
