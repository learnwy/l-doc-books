支付网关架构与集成

核心概念

支付网关是电商平台与金融网络之间的技术桥梁，负责交易信息的加密传输、路由分发、协议转换和状态管理。现代支付网关已从简单的通道转发演进为集成智能路由、风控引擎、令牌管理和商户仪表盘的综合平台。

网关架构设计
一个生产级支付网关的核心模块包括：API 层（接收和验证请求）、路由层（选择最优通道）、通道适配层（协议转换）、异步通知层（处理回调）、对账层（资金核对）。


API 层需要处理幂等性、签名验证和请求限流。幂等性通过商户传入的 idempotencyKey 实现——同一个 Key 的重复请求返回相同结果而不会重复扣款。签名通常采用 HMAC-SHA256 或 RSA-SHA256，请求体参与签名计算防止篡改。


interface GatewayConfig {
  apiVersion: 'v2';
  authentication: {
    type: 'api_key' | 'oauth2' | 'hmac';
    publicKey: string;
    webhookSecret: string;
  };
  retry: {
    maxAttempts: 3;
    backoffMultiplier: 2;
    retryableErrors: string[];
  };
  timeout: {
    connect: 5000;
    read: 30000;
  };
}

const verifyWebhookSignature = (payload: string, signature: string, secret: string): boolean => {
  const computed = crypto.createHmac('sha256', secret).update(payload).digest('hex');
  return crypto.timingSafeEqual(Buffer.from(computed), Buffer.from(signature));
};
通道适配层是网关架构中最复杂的部分。每个支付通道有不同的 API 规范、加密要求和报文格式。适配器模式（Adapter Pattern）将通道差异封装在独立模块中，统一对上层暴露标准化接口。

智能路由引擎
智能路由是现代支付网关的核心竞争力。路由引擎根据交易特征（金额、币种、卡 BIN、用户地区）和通道状态（成功率、延迟、费率、限额）动态选择最优支付通道。


路由策略的优先级通常为：可用性 > 成功率 > 费率 > 延迟。当主通道故障时，路由引擎自动降级到备用通道（Failover）；当主通道成功率下降超过阈值时，流量渐进切换到表现更好的通道（Circuit Breaker + Gradual Shift）。


interface RoutingRule {
  conditions: {
    currency?: string[];
    cardBrand?: ('visa' | 'mastercard' | 'amex')[];
    amountRange?: { min: number; max: number };
    country?: string[];
    riskLevel?: ('low' | 'medium' | 'high')[];
  };
  channels: {
    channelId: string;
    weight: number;
    priority: number;
    maxDailyVolume?: number;
  }[];
  fallbackChannelId: string;
}

interface ChannelHealth {
  channelId: string;
  successRate: number;
  averageLatency: number;
  p99Latency: number;
  failureCount: number;
  circuitBreakerState: 'closed' | 'open' | 'half_open';
  lastHealthCheck: number;
}
级联重试（Cascading Retry）是提升整体支付成功率的重要手段。当首选通道返回可重试错误码（如网络超时、通道限流）时，路由引擎自动将请求转发到次选通道。需要注意区分可重试错误（Retryable）和终态错误（Terminal）——余额不足、卡过期等错误不应重试。


收银台集成方案
电商平台与支付网关的集成方式影响用户体验、安全合规和开发效率。主流集成方案包括托管收银台（Hosted Checkout）、嵌入式组件（Embedded Components）和纯 API 集成三种。


托管收银台将用户重定向到支付网关的支付页面，所有敏感数据在网关侧处理，商户无需处理卡信息，PCI 合规负担最小（SAQ A）。缺点是品牌连续性差，跳转可能增加流失率。


嵌入式组件（如 Stripe Elements、Adyen Drop-in）在商户页面内渲染安全的 iframe 输入框，兼顾安全性和用户体验。卡号输入框运行在独立的安全域内，商户页面无法访问其中的数据。


interface CheckoutSessionConfig {
  mode: 'hosted' | 'embedded' | 'api';
  paymentMethods: string[];
  amount: number;
  currency: string;
  returnUrl: string;
  appearance: {
    theme: 'light' | 'dark' | 'auto';
    borderRadius: string;
    fontFamily: string;
    primaryColor: string;
  };
  features: {
    saveCard: boolean;
    addressCollection: 'auto' | 'required' | 'never';
    walletButtons: ('apple_pay' | 'google_pay')[];
  };
}

Webhook 与异步通知
支付交易的最终状态通过 Webhook 异步通知商户系统。网关在交易状态变更时向商户预注册的 URL 发送 HTTP POST 请求，携带签名和交易详情。商户系统必须在收到通知后正确验签并返回 200 状态码，否则网关会按退避策略重试。


Webhook 处理的关键设计原则：幂等性（同一事件可能多次送达）、顺序无关性（不依赖通知到达顺序）、快速响应（在 5 秒内返回，耗时操作异步处理）。


interface WebhookEvent {
  id: string;
  type: 'payment.authorized' | 'payment.captured' | 'payment.failed' | 'refund.completed';
  created: number;
  data: {
    paymentId: string;
    amount: number;
    currency: string;
    status: string;
    metadata: Record<string, string>;
  };
  deliveryAttempt: number;
}

const RETRY_SCHEDULE = [0, 60, 300, 3600, 7200, 21600, 43200, 86400] as const;
生产环境中还需实现 Webhook 事件的本地持久化和重放机制。将收到的所有事件存入消息队列或数据库，由后台消费者处理业务逻辑。即使处理失败也不会丢失事件，可以手动重试。


小结
    

  • 支付网关架构核心模块：API层（幂等+签名）、路由层（智能选通道）、适配层（协议转换）、通知层（Webhook）、对账层
    • 

  • 智能路由根据成功率、费率、延迟动态选择通道，级联重试可提升整体成功率 3-8%
    • 

  • 集成方案从托管收银台到纯 API 逐步提升品牌控制力，但 PCI 合规负担也随之增大
    • 

  • Webhook 处理必须保证幂等性和快速响应，异步消费 + 本地持久化是生产最佳实践
    • 

  • 选择支付网关应评估：通道覆盖范围、API 设计质量、文档完备性、SDK 支持、仪表盘功能和技术支持响应速度
    •
