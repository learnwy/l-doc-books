高可用与弹性伸缩

核心概念

高可用（High Availability）是指系统在面对硬件故障、网络中断、流量突增等异常情况时仍能持续提供服务的能力。电商平台的可用性目标通常为 99.99%（四个九），意味着全年不可用时间不超过 52.6 分钟。弹性伸缩（Elasticity）则是系统根据负载变化自动调整计算资源的能力，在大促流量高峰时自动扩容，在低谷期自动缩容以节约成本。

高可用架构的核心思想是消除单点故障、实现故障自动恢复。每个层次都需要冗余设计——网络层的多线路接入、计算层的多实例部署、存储层的多副本复制。

负载均衡与流量分发
负载均衡是高可用架构的第一道防线，将请求均匀分配到多个服务实例上，避免单点过载。电商系统通常采用四层（L4）和七层（L7）负载均衡的组合部署。


四层负载均衡（如 LVS、DPVS）工作在传输层，基于 IP 和端口进行流量转发，性能极高（单机百万级 QPS），适合处理南北向流量入口。七层负载均衡（如 Nginx、Envoy）工作在应用层，能够基于 URL 路径、请求头、Cookie 等信息进行智能路由，适合实现灰度发布、A/B 测试和动态权重调整。


interface LoadBalanceStrategy {
  name: string;
  select(instances: ServiceInstance[], request?: RequestContext): ServiceInstance;
}

interface ServiceInstance {
  host: string;
  port: number;
  weight: number;
  healthy: boolean;
  activeConnections: number;
  avgResponseTimeMs: number;
}

const weightedRoundRobin: LoadBalanceStrategy = {
  name: 'weighted_round_robin',
  select(instances) {
    const healthyInstances = instances.filter((i) => i.healthy);
    const totalWeight = healthyInstances.reduce((sum, i) => sum + i.weight, 0);
    let random = Math.random() * totalWeight;
    for (const instance of healthyInstances) {
      random -= instance.weight;
      if (random <= 0) return instance;
    }
    return healthyInstances[0];
  },
};

const leastConnections: LoadBalanceStrategy = {
  name: 'least_connections',
  select(instances) {
    const healthyInstances = instances.filter((i) => i.healthy);
    return healthyInstances.reduce((min, i) => (i.activeConnections < min.activeConnections ? i : min));
  },
};
健康检查是负载均衡的基础。主动健康检查定期向后端实例发送探测请求（HTTP GET 或 TCP 连接），连续失败超过阈值则摘除实例。被动健康检查通过监控实际请求的成功率和响应时间来判断实例健康状态。电商系统通常同时启用主动和被动健康检查，主动检查的间隔设为 5-10 秒，被动检查的窗口设为 30 秒内错误率超过 50% 则摘除。


CDN 加速与边缘计算
CDN（Content Delivery Network）将静态资源和动态内容缓存到离用户最近的边缘节点，显著降低访问延迟。电商平台 70% 以上的请求是静态资源请求（商品图片、CSS、JS 文件），CDN 能将这些请求的响应时间从数百毫秒降低到 10-30 毫秒。


电商场景下 CDN 的使用策略需要根据内容类型区分：商品图片设置较长的缓存时间（7-30 天），通过版本化 URL 实现更新；价格和库存等动态数据不缓存或设置极短 TTL（1-5 秒）；商品详情页采用 ESI（Edge Side Includes）技术，将页面拆分为静态框架和动态片段，静态部分在 CDN 缓存，动态部分实时回源获取。

边缘计算将部分业务逻辑推送到 CDN 节点执行（如 Cloudflare Workers、AWS Lambda@Edge），实现更低延迟的个性化处理。电商场景中，边缘节点可以执行地域化定价、A/B 测试分流、设备适配和 Bot 检测等逻辑。


自动伸缩与容量规划
弹性伸缩使电商系统能够根据实时负载自动调整计算资源。大促场景的流量可能是日常的 10-100 倍，手动扩容无法及时响应。自动伸缩策略通常基于 CPU 使用率、内存使用率、请求队列长度或自定义业务指标触发。


水平自动伸缩（HPA）是最常用的策略：当某个服务的 CPU 使用率持续高于 70% 超过 3 分钟时，自动增加 Pod 副本数；当 CPU 使用率低于 30% 超过 10 分钟时，缩减副本。垂直自动伸缩（VPA）动态调整单个 Pod 的资源配额，适合负载模式稳定的服务。


interface ScalingPolicy {
  serviceName: string;
  minReplicas: number;
  maxReplicas: number;
  metrics: ScalingMetric[];
  scaleUpCooldownSec: number;
  scaleDownCooldownSec: number;
}

interface ScalingMetric {
  type: 'cpu' | 'memory' | 'rps' | 'queue_depth' | 'custom';
  targetValue: number;
  tolerancePercent: number;
}

const orderServiceScaling: ScalingPolicy = {
  serviceName: 'order-service',
  minReplicas: 3,
  maxReplicas: 50,
  metrics: [
    { type: 'cpu', targetValue: 70, tolerancePercent: 10 },
    { type: 'rps', targetValue: 1000, tolerancePercent: 15 },
  ],
  scaleUpCooldownSec: 60,
  scaleDownCooldownSec: 300,
};

function calculateDesiredReplicas(
  currentReplicas: number,
  currentMetricValue: number,
  targetMetricValue: number,
): number {
  const ratio = currentMetricValue / targetMetricValue;
  const desired = Math.ceil(currentReplicas * ratio);
  return desired;
}
大促场景的容量规划遵循「压测 → 预估 → 预扩容 → 实时伸缩」的流程。全链路压测在仿真环境中模拟大促流量，确定每个服务的性能基线和瓶颈点。基于历史数据和业务预估确定目标流量，在大促前提前扩容到预估容量的 120%。活动期间自动伸缩作为兜底策略处理流量预估偏差。


熔断降级与故障隔离
大促期间非核心功能的故障不应影响核心交易链路。熔断降级策略将系统功能分为核心功能和非核心功能，当系统压力超过阈值时主动关闭非核心功能，将资源集中到核心交易上。


降级预案根据系统负载分为多个级别：一级降级关闭推荐和个性化功能，返回热门商品列表；二级降级关闭评价和问答功能，仅保留商品基本信息；三级降级关闭搜索，仅保留类目浏览；四级降级进入「只读模式」，仅允许已创建订单的支付操作。

故障隔离通过舱壁模式（Bulkhead）实现：为不同的服务调用分配独立的线程池或连接池，防止一个慢调用耗尽所有资源。电商系统中，支付服务和物流服务使用独立的连接池，即使物流查询服务响应缓慢，也不会影响支付处理。


小结
    

  • 高可用架构通过消除单点故障、多可用区部署和自动故障转移实现 99.99% 的可用性目标
    • 

  • 负载均衡采用四层和七层组合部署，配合主动和被动健康检查确保流量只分发到健康实例
    • 

  • CDN 加速根据内容类型设置差异化缓存策略，ESI 技术实现动静分离，边缘计算推进逻辑前置
    • 

  • 弹性伸缩基于多维指标自动调整资源，大促场景遵循压测、预估、预扩容和实时伸缩的流程
    • 

  • 降级预案分为四个级别逐步关闭非核心功能，舱壁模式隔离不同服务的资源池防止故障扩散
