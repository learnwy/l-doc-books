API 设计与系统集成

核心概念

API（Application Programming Interface）是电商系统内部服务间通信以及与外部系统集成的标准接口。一个设计良好的 API 体系决定了系统的可维护性、可扩展性和开发者体验。电商平台的 API 设计面临独特的挑战：接口数量庞大（通常数百到数千个）、调用频率极高（大促时可达百万 QPS）、版本兼容要求严格（不能随意破坏已上线的移动端 App）。

电商 API 设计需要在一致性、性能和灵活性之间平衡。不同的客户端（移动端、Web 端、第三方）对同一资源的数据需求不同，API 层需要提供合理的抽象。

RESTful API 设计规范
RESTful API 是电商开放平台和管理后台的主流选择。设计良好的 REST API 遵循资源导向的 URL 设计、标准 HTTP 方法语义和统一的响应格式。


资源命名使用复数名词，层级关系通过路径嵌套表达。查询参数用于过滤、排序和分页。HTTP 方法映射为 CRUD 操作：GET 读取、POST 创建、PUT 全量更新、PATCH 部分更新、DELETE 删除。


interface ApiResponse<T> {
  code: number;
  message: string;
  data: T;
  timestamp: number;
  requestId: string;
}

interface PaginatedResponse<T> extends ApiResponse<T[]> {
  pagination: {
    page: number;
    pageSize: number;
    total: number;
    totalPages: number;
  };
}

API 版本管理是长期维护的关键。电商 App 的旧版本可能在市场上存在数年，API 必须支持多版本共存。URL 路径版本化（/api/v1/、/api/v2/）是最直观的方式，Header 版本化（Accept: application/vnd.shop.v2+json）更符合 REST 理念但实践中使用较少。

GraphQL 在电商前端的应用
GraphQL 允许客户端精确指定需要的数据字段，解决了 REST API 中常见的过度获取（Over-fetching）和不足获取（Under-fetching）问题。电商商品详情页是 GraphQL 的典型应用场景：移动端只需要商品名称、价格和主图，Web 端还需要详情描述、评价统计和推荐商品。


const productSchema = `
  type Product {

    originalPrice: Float
    images: [String!]!

    skus: [SKU!]!

    reviews(first: Int, after: String): ReviewConnection
    relatedProducts(limit: Int): [Product!]
  }

  type SKU {

GraphQL 在电商场景中需要特别注意 N+1 查询问题和查询深度限制。DataLoader 模式通过批量加载解决 N+1 问题——当多个商品需要加载品牌信息时，DataLoader 将多次单独查询合并为一次批量查询。查询深度限制防止恶意客户端构造嵌套极深的查询消耗服务器资源。


interface DataLoaderBatch<K, V> {
  load(key: K): Promise<V>;
  loadMany(keys: K[]): Promise<V[]>;
}

function createBrandLoader(): DataLoaderBatch<string, Brand> {
  const batchFn = async (brandIds: readonly string[]): Promise<Brand[]> => {
    const brands = await db.query<Brand>('SELECT * FROM brands WHERE id IN (?)', [Array.from(brandIds)]);
    const brandMap = new Map(brands.map((b) => [b.id, b]));
    return Array.from(brandIds).map((id) => brandMap.get(id)!);
  };
  return createDataLoader(batchFn);
}

interface Brand {
  id: string;
  name: string;
}
function createDataLoader<K, V>(batchFn: (keys: readonly K[]) => Promise<V[]>): DataLoaderBatch<K, V> {
  return { load: async (key) => (await batchFn([key]))[0], loadMany: (keys) => batchFn(keys) };
}
第三方系统集成与 Webhook
电商平台需要与大量外部系统集成：支付网关（支付宝、微信支付、Stripe）、物流服务商（顺丰、圆通）、ERP 系统、CRM 系统、短信/邮件服务商等。每个外部系统有自己的 API 规范和认证方式，集成层需要提供统一的抽象。


适配器模式（Adapter Pattern）是第三方集成的核心设计。为每个外部系统定义统一的接口，不同供应商实现各自的适配器。当需要替换供应商或新增渠道时，只需添加新的适配器实现。

Webhook 是外部系统向电商平台推送事件通知的标准方式。支付成功回调、物流状态更新、退款结果通知都通过 Webhook 实现。Webhook 接收端必须具备幂等处理能力（同一事件可能被重复推送）、签名验证（防止伪造请求）和快速响应（在 5 秒内返回 200 状态码，业务处理异步执行）。


interface WebhookHandler {
  validateSignature(headers: Record<string, string>, body: string, secret: string): boolean;
  parseEvent(body: string): WebhookEvent;
  processEvent(event: WebhookEvent): Promise<void>;
}

interface WebhookEvent {
  eventId: string;
  eventType: string;
  payload: Record<string, unknown>;
  timestamp: number;
  signature: string;
}

async function handleWebhook(
  handler: WebhookHandler,
  headers: Record<string, string>,
  body: string,
  secret: string,
): Promise<{ status: number }> {
  if (!handler.validateSignature(headers, body, secret)) {
    return { status: 401 };
  }
  const event = handler.parseEvent(body);
  const processed = await idempotencyStore.exists(event.eventId);
  if (processed) {
    return { status: 200 };
  }
  await messageQueue.publish('webhook.events', JSON.stringify(event));
  await idempotencyStore.mark(event.eventId);
  return { status: 200 };
}

const idempotencyStore = {
  exists: async (_id: string): Promise<boolean> => false,
  mark: async (_id: string): Promise<void> => {},
};
const messageQueue = {
  publish: async (_topic: string, _message: string): Promise<void> => {},
};
API 安全与认证授权
电商 API 的安全设计涉及认证（Authentication）、授权（Authorization）、数据加密和防攻击四个层面。用户端 API 采用 JWT 或 OAuth 2.0 认证，开放平台 API 采用 API Key + Secret 签名认证，内部服务间通信采用 mTLS 双向认证。

请求签名机制将请求参数按字典序排列后拼接 Secret 进行 HMAC 签名，接收方用相同的方式计算签名并比对。时间戳字段防止签名被截获后重放，通常允许 5 分钟的时间窗口偏差。


function generateSignature(params: Record<string, string>, secret: string, timestamp: number): string {
  const sortedKeys = Object.keys(params).sort();
  const signString = sortedKeys.map((key) => `${key}=${params[key]}`).join('&');
  const fullString = `${signString}&timestamp=${timestamp}&secret=${secret}`;
  return crypto.createHmac('sha256', secret).update(fullString).digest('hex');
}

function verifySignature(
  params: Record<string, string>,
  signature: string,
  secret: string,
  timestamp: number,
  maxAgeMs: number = 300000,
): boolean {
  if (Date.now() - timestamp > maxAgeMs) return false;
  const expected = generateSignature(params, secret, timestamp);
  return crypto.timingSafeEqual(Buffer.from(signature), Buffer.from(expected));
}

const crypto = {
  createHmac: (_alg: string, _secret: string) => ({
    update: (_str: string) => ({ digest: (_enc: string) => 'hash' }),
  }),
  timingSafeEqual: (_a: Buffer, _b: Buffer) => true,
};
小结
    

  • 电商 API 设计在 RESTful、GraphQL 和 gRPC 三种风格中选择：REST 适合开放平台，GraphQL 适合多端差异化前端，gRPC 适合内部高性能通信
    • 

  • RESTful API 遵循资源导向设计，通过 URL 路径版本化支持多版本共存，统一响应格式和错误码规范
    • 

  • GraphQL 解决过度获取和不足获取问题，DataLoader 批量加载解决 N+1 查询，查询深度限制防止资源滥用
    • 

  • 第三方集成通过适配器模式统一接口，Webhook 接收端需要幂等处理、签名验证和异步处理三重保障
    • 

  • API 安全覆盖认证、授权、签名和加密四个层面，不同场景选用 JWT、OAuth 2.0 或 API Key + HMAC 方案
    •
