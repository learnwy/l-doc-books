微服务架构在电商中的实践

核心概念

微服务架构将电商系统拆分为一组小型、自治的服务，每个服务围绕特定的业务能力构建，独立开发、部署和扩展。与单体架构相比，微服务在应对电商业务的快速迭代和流量波动方面有天然优势：商品搜索可以独立扩容应对大促流量，支付模块可以独立升级不影响其他功能，不同团队可以并行开发不同服务。

微服务架构的核心是服务的合理拆分和高效协作。拆分粒度过细会导致分布式系统的复杂度爆炸，过粗则失去微服务的灵活性优势。

服务拆分与领域边界
服务拆分是微服务架构最关键的决策。拆分的核心原则是围绕业务能力（Business Capability）而非技术层次进行划分。电商系统的典型服务拆分遵循限界上下文（Bounded Context）的思想，每个服务拥有自己的领域模型和数据存储。


电商平台的服务拆分通常分为三个层次：核心交易链路服务（商品、订单、支付、库存）、支撑服务（用户、地址、营销、优惠券）和基础设施服务（认证、网关、配置、日志）。核心链路服务要求最高的可用性和性能，支撑服务可以适当降级，基础设施服务是所有业务服务的底座。


interface ServiceDefinition {
  name: string;
  domain: string;
  ownedEntities: string[];
  publishedEvents: string[];
  consumedEvents: string[];
  syncDependencies: string[];

const orderService: ServiceDefinition = {

  ownedEntities: ['Order', 'OrderItem', 'OrderStatus'],

服务间的数据所有权必须严格划分。商品服务拥有商品主数据，订单服务拥有订单数据，库存服务拥有库存数据。当订单服务需要商品信息时，通过 API 调用或事件订阅获取商品的只读副本，而不是直接查询商品数据库。这种数据隔离保证了服务的自治性。


API 网关与流量治理
API 网关是微服务架构中客户端与后端服务之间的唯一入口，承担请求路由、协议转换、认证授权、限流熔断和请求聚合等职责。电商场景下，网关还需要处理灰度发布、A/B 测试路由和大促流量调度。


限流策略在电商大促中至关重要。常见的限流算法包括固定窗口、滑动窗口、令牌桶和漏桶。电商系统通常采用多层限流：网关层基于 IP 和用户维度限流，服务层基于接口维度限流，数据库层基于连接池限流。


interface RateLimitConfig {
  key: string;
  algorithm: 'fixed_window' | 'sliding_window' | 'token_bucket' | 'leaky_bucket';
  limit: number;
  windowMs: number;
}

const rateLimitRules: RateLimitConfig[] = [
  { key: 'ip:{ip}', algorithm: 'sliding_window', limit: 100, windowMs: 60000 },
  { key: 'user:{userId}:order', algorithm: 'token_bucket', limit: 5, windowMs: 1000 },
  { key: 'api:/products', algorithm: 'fixed_window', limit: 10000, windowMs: 1000 },
  { key: 'api:/seckill', algorithm: 'token_bucket', limit: 1000, windowMs: 1000 },
];

async function checkRateLimit(config: RateLimitConfig, identifier: string): Promise<boolean> {
  const redisKey = `rate_limit:${config.key.replace(/{(\w+)}/g, identifier)}`;
  if (config.algorithm === 'sliding_window') {
    const now = Date.now();
    await redis.zremrangebyscore(redisKey, 0, now - config.windowMs);
    const count = await redis.zcard(redisKey);
    if (count >= config.limit) return false;
    await redis.zadd(redisKey, now, `${now}:${Math.random()}`);
    await redis.pexpire(redisKey, config.windowMs);
    return true;
  }
  return true;
}
BFF（Backend for Frontend）模式是 API 网关的延伸。移动端和 Web 端对同一业务的数据需求不同——移动端需要精简的响应体以节省带宽，Web 端需要完整的商品详情。BFF 层为每个前端提供定制化的 API 聚合，避免前端直接调用多个微服务。


分布式事务与最终一致性
电商下单流程天然涉及多个服务的协作：创建订单、预扣库存、冻结优惠券、发起支付。在微服务架构下，这些操作分布在不同的数据库中，无法使用传统的 ACID 事务保证一致性。分布式事务方案的选择直接影响系统的可靠性和性能。

Saga 模式是电商下单流程的主流方案。编排式 Saga 通过中心协调器定义事务流程，每个步骤执行成功则推进下一步，执行失败则按逆序执行补偿操作。


interface SagaStep {
  name: string;
  execute: (context: SagaContext) => Promise<void>;
  compensate: (context: SagaContext) => Promise<void>;
}

interface SagaContext {
  orderId: string;
  userId: string;
  items: Array<{ skuId: string; quantity: number }>;
  couponId?: string;
  [key: string]: unknown;
}

const createOrderSaga: SagaStep[] = [
  {
    name: 'reserve_inventory',
    execute: async (ctx) => {
      await inventoryClient.reserve(ctx.orderId, ctx.items);
    },
    compensate: async (ctx) => {
      await inventoryClient.release(ctx.orderId, ctx.items);
    },
  },
  {
    name: 'lock_coupon',
    execute: async (ctx) => {
      if (ctx.couponId) await couponClient.lock(ctx.couponId, ctx.orderId);
    },
    compensate: async (ctx) => {
      if (ctx.couponId) await couponClient.unlock(ctx.couponId);
    },
  },
  {
    name: 'create_order',
    execute: async (ctx) => {
      await orderClient.create(ctx);
    },
    compensate: async (ctx) => {
      await orderClient.cancel(ctx.orderId);
    },
  },
  {
    name: 'initiate_payment',
    execute: async (ctx) => {
      await paymentClient.create(ctx.orderId, ctx.userId);
    },
    compensate: async (ctx) => {
      await paymentClient.cancel(ctx.orderId);
    },
  },
];

async function executeSaga(steps: SagaStep[], context: SagaContext): Promise<void> {
  const completedSteps: SagaStep[] = [];
  for (const step of steps) {
    try {
      await step.execute(context);
      completedSteps.push(step);
    } catch (error) {
      for (const completed of completedSteps.reverse()) {
        await completed.compensate(context);
      }
      throw error;
    }
  }
}
TCC（Try-Confirm-Cancel）方案比 Saga 提供更强的隔离性。Try 阶段预留资源（预扣库存但不实际扣减），Confirm 阶段确认（实际扣减），Cancel 阶段释放。TCC 的优势在于 Try 阶段就能发现资源不足，避免后续补偿的开销，适合对一致性要求较高的资金场景。


服务治理与可观测性
微服务规模达到数十个后，服务治理成为运维的核心挑战。服务注册与发现、负载均衡、熔断降级、链路追踪和日志聚合是五大治理支柱。


服务注册与发现是微服务通信的基础。每个服务启动时向注册中心（如 Nacos、Consul）注册自己的地址，调用方通过注册中心发现目标服务的实例列表。健康检查机制定期探测服务实例的可用性，将不健康的实例从列表中摘除。


熔断器模式防止故障在服务间级联扩散。当下游服务的错误率超过阈值时，熔断器打开，后续请求直接返回降级响应而不再调用下游。经过一段冷却期后，熔断器进入半开状态，允许少量请求通过以探测下游是否恢复。


interface CircuitBreakerConfig {
  failureThreshold: number;
  recoveryTimeMs: number;
  halfOpenRequests: number;
}

class CircuitBreaker {
  private state: 'closed' | 'open' | 'half_open' = 'closed';
  private failureCount = 0;
  private lastFailureTime = 0;
  private halfOpenAttempts = 0;

  constructor(private config: CircuitBreakerConfig) {}

  async execute<T>(fn: () => Promise<T>, fallback: () => T): Promise<T> {
    if (this.state === 'open') {
      if (Date.now() - this.lastFailureTime > this.config.recoveryTimeMs) {
        this.state = 'half_open';
        this.halfOpenAttempts = 0;
      } else {
        return fallback();
      }
    }
    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      return fallback();
    }
  }

  private onSuccess(): void {
    this.failureCount = 0;
    this.state = 'closed';
  }

  private onFailure(): void {
    this.failureCount++;
    this.lastFailureTime = Date.now();
    if (this.failureCount >= this.config.failureThreshold) {
      this.state = 'open';
    }
  }
}
分布式链路追踪（如 Jaeger、Zipkin）通过在每个请求中注入 TraceID 和 SpanID，将跨服务的调用链路串联起来。电商下单涉及十多次跨服务调用，链路追踪能清晰展示每一跳的耗时和状态，帮助定位性能瓶颈和故障根因。


小结
    

  • 微服务架构将电商系统按业务能力拆分为自治的服务，核心交易链路服务要求最高可用性，支撑服务可适当降级
    • 

  • 服务拆分遵循限界上下文原则，每个服务拥有独立的数据存储，通过 API 或事件获取其他服务的数据副本
    • 

  • API 网关作为客户端唯一入口，承担路由、认证、限流和聚合职责，BFF 模式为不同端提供定制化 API
    • 

  • Saga 模式是电商下单分布式事务的主流方案，通过编排正向操作和补偿操作实现最终一致性
    • 

  • 服务治理包含注册发现、熔断降级、链路追踪三大支柱，保证数十个微服务的稳定运行
