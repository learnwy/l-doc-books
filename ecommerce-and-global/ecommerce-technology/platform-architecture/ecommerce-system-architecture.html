电商系统架构设计

核心概念

电商系统架构是承载商品展示、交易处理、物流履约和用户服务的技术基座。一个成熟的电商平台需要在高并发访问、海量数据存储、复杂业务流程和极致用户体验之间找到平衡。架构设计的核心挑战在于：如何将业务复杂度映射为技术分层，使每一层职责清晰、独立演进，同时保证跨层协作的高效性。

电商系统通常采用分层架构，从上到下依次为接入层、业务层、中间件层和数据层，每一层承担不同的技术职责。

业务领域建模与模块划分
电商平台的核心领域可以拆分为六大业务模块，每个模块管理自己的数据模型和业务规则。这种划分遵循领域驱动设计（DDD）的思想，以业务边界而非技术边界来组织代码。


商品中心负责 SPU（标准产品单元）和 SKU（库存量单位）的管理。一个 SPU 对应一款商品，一个 SKU 对应具体的规格组合（颜色、尺寸等）。商品中心还管理类目树、属性体系、品牌信息和商品详情页的富文本内容。类目树通常采用多级分类（一般三到四级），配合属性模板实现结构化商品描述。


订单中心是电商系统的核心枢纽，连接用户、商品、支付和物流。订单生命周期从用户下单开始，经过待支付、已支付、待发货、已发货、已收货、已完成等状态流转。每个状态转换都伴随着具体的业务动作：支付回调触发扣减库存、发货触发物流追踪、确认收货触发结算。


interface Order {

支付中心处理多渠道支付接入、支付状态管理和资金对账。库存中心实现预扣、确认和释放三阶段库存管理，防止超卖。用户中心管理账号体系、地址簿和会员等级。营销中心负责优惠券、满减、秒杀等促销活动的规则引擎。


订单状态机与事件驱动
订单状态机是电商系统中最复杂的业务模型之一。状态机定义了订单在不同状态之间的合法转换路径，每次转换都必须满足前置条件并触发相应的副作用。


事件驱动架构将订单状态变更解耦为事件的发布与消费。当订单支付成功时，支付中心发布 OrderPaid 事件，库存中心消费该事件执行实际扣减，物流中心消费该事件创建待发货任务，营销中心消费该事件更新用户积分。这种模式避免了服务间的同步调用依赖，提高了系统的可靠性和可扩展性。


interface DomainEvent {

function handleOrderPaid(event: DomainEvent): void {
  inventoryService.confirmDeduction(event.aggregateId);
  logisticsService.createShipmentTask(event.aggregateId);
  pointsService.addPoints(event.payload.userId as string, event.payload.amount as number);
}
事件的可靠投递通过「本地事件表 + 定时轮询」模式保证：业务操作和事件写入在同一个本地事务中完成，定时任务扫描未发送的事件并推送到消息队列，消费端通过幂等设计保证重复消费的安全性。


分库分表与数据分片策略
当单库数据量突破千万级别、单表行数超过五千万时，电商系统需要引入分库分表策略来保持查询性能。分片策略的选择直接影响数据的均匀分布和跨片查询的复杂度。

订单表通常按用户 ID 进行 Hash 分片，保证同一用户的所有订单在同一个物理分片上，避免下单和查询订单时的跨片操作。商品表可以按商品 ID 进行 Range 分片或 Hash 分片，取决于业务查询模式。交易流水表按时间维度分表，历史数据定期归档到数据仓库。


function getShardIndex(userId: string, totalShards: number): number {
  const hash = murmurhash3(userId);
  return hash % totalShards;
}

function getOrderTableName(userId: string): string {
  const shardIndex = getShardIndex(userId, 64);
  return `order_${String(shardIndex).padStart(3, '0')}`;
}

function routeDataSource(userId: string): string {
  const dbIndex = getShardIndex(userId, 8);
  return `ds_order_${dbIndex}`;
}
分布式 ID 生成是分库分表的前置条件。常见方案包括 Snowflake 算法（时间戳 + 机器 ID + 序列号）、Leaf 号段模式（数据库号段预分配）和 UUID。Snowflake 算法在分布式环境下能保证全局唯一且趋势递增，是电商系统的主流选择。


缓存架构与性能优化
电商系统对缓存的依赖极深。商品详情页每秒数万次访问，如果每次都查询数据库，系统将迅速崩溃。合理的缓存架构采用多级缓存策略：浏览器缓存 → CDN 缓存 → 应用层本地缓存 → 分布式缓存 → 数据库。


缓存一致性是电商场景的核心难题。商品价格变更、库存扣减等操作必须及时反映到缓存中。常用的一致性策略有三种：Cache-Aside（旁路缓存，读时回填、写时删除）、Write-Through（写穿透，写入同时更新缓存和数据库）、Write-Behind（写回，异步批量更新数据库）。电商系统多采用 Cache-Aside 配合消息驱动的缓存失效机制。


async function getProduct(productId: string): Promise<Product> {
  const cacheKey = `product:${productId}`;
  const cached = await localCache.get<Product>(cacheKey);
  if (cached) return cached;

  const redisCached = await redis.get(cacheKey);
  if (redisCached) {
    const product = JSON.parse(redisCached) as Product;
    localCache.set(cacheKey, product, { ttl: 60 });
    return product;
  }

  const product = await db.query<Product>('SELECT * FROM products WHERE id = ?', [productId]);
  await redis.setex(cacheKey, 3600, JSON.stringify(product));
  localCache.set(cacheKey, product, { ttl: 60 });
  return product;
}

async function invalidateProductCache(productId: string): Promise<void> {
  const cacheKey = `product:${productId}`;
  await redis.del(cacheKey);
  localCache.delete(cacheKey);
  await messageBus.publish('cache.invalidate', { key: cacheKey });
}
热点数据的缓存击穿、缓存雪崩和缓存穿透是三个典型问题。缓存击穿通过互斥锁或逻辑过期解决；缓存雪崩通过 TTL 随机化和多级缓存缓解；缓存穿透通过布隆过滤器或空值缓存防御。大促场景下还需要缓存预热——提前将热门商品数据加载到缓存中。


小结
    

  • 电商系统采用四层分层架构：接入层负责流量分发和安全防护，业务层实现核心业务逻辑，中间件层提供异步通信和数据加速，数据层保证持久化和分析能力
    • 

  • 业务领域按 DDD 思想划分为商品、订单、支付、库存、用户、营销六大模块，每个模块拥有独立的数据模型和业务规则
    • 

  • 订单状态机定义了严格的状态转换路径，事件驱动架构将状态变更解耦为事件发布与消费，通过本地事件表保证可靠投递
    • 

  • 分库分表策略根据业务查询模式选择分片维度，订单表按用户 ID Hash 分片，流水表按时间分表，配合 Snowflake 算法生成分布式 ID
    • 

  • 多级缓存架构从浏览器到数据库层层拦截请求，Cache-Aside 策略配合消息驱动的缓存失效机制解决一致性问题
    •
